title: "Role-based deployment"
description: "Run MoleSignal roles in separate processes: what each role does, how nodes find each other, and the current limits of a role-split cluster."
---

MoleSignal is a single binary. The `[node].roles` setting decides which responsibilities a process carries. The default, `standalone`, runs every role in one process. Splitting roles lets intake, query, and background work scale and fail independently.

The `router` role is the entry point of a role-split cluster. It serves the complete HTTP API and the web UI, forwards writes to intake nodes, and sends queries to querier nodes. Every other role serves a small internal HTTP listener for health checks and metrics.

## Roles

| Role | What it runs | State | Scaling |
|---|---|---|---|
| `standalone` | Every role in one process, the full HTTP API, the web UI, internal gRPC, OTLP gRPC, and the Probe Agent gRPC endpoints | Stateful: embeds an intake with a WAL | One process. Not a horizontal scaling unit. |
| `router` | The complete HTTP API and web UI, the OTLP gRPC receiver, forwarding of writes to intake nodes, forwarding of queries to querier nodes, and per-organization rate limiting | Stateless | Scales horizontally behind a load balancer. |
| `intake` | WAL replay, in-memory buffering, periodic flush to Parquet, real-time alert rules, the internal gRPC intake endpoint, and the OTLP gRPC receiver | Stateful: the WAL of the most recent flush window | Sharded by consistent hashing. Plan the WAL volume and the rebalancing before scaling. |
| `querier` | Query execution for SQL and PromQL requests that other nodes send, the Arrow Flight scan endpoint for federated queries, and asynchronous search jobs | Stateless | Scales horizontally. |
| `compactor` | File compaction, retention, and storage maintenance: index rebuild, delayed object deletion, and catalog reconciliation | Stateless between runs | Scales horizontally. Several nodes divide the work by stream and by organization. See [Work division between compactor nodes](#work-division-between-compactor-nodes). |
| `alert` | Rule evaluation, escalation dispatch, scheduled reports, connector runners, pipeline runners, and the Probe Agent gRPC endpoints | Stateless between runs: evaluation state and incidents live in the metadata database | Run a single instance. Several instances would evaluate every rule and run every scheduled job more than once. |

A process can carry several roles, for example `["intake", "querier"]`.

### Listeners

| Role | `[http].port` (5080) | Internal gRPC (5082) | OTLP gRPC (4317) | Other |
|---|---|---|---|---|
| `standalone` | Full HTTP API and web UI | Yes | Yes | Probe Agent ports `5084` and `5085`. Flight SQL on `5083` when enabled. |
| `router` | Full HTTP API and web UI | No | Yes | Flight SQL on `5083` when enabled. |
| `intake` | Health, readiness, and metrics | Yes | Yes | |
| `querier` | Health, readiness, and metrics | Yes | No | Flight SQL on `5083` when enabled. |
| `compactor` | Health, readiness, and metrics | No | No | |
| `alert` | Health, readiness, and metrics | No | No | Probe Agent ports `5084` and `5085`. |

The health, readiness, and metrics listener of a node without the full API answers three unauthenticated paths and nothing else:

| Path | Answer |
|---|---|
| `GET /api/v1/healthz` | `200`, or `503` with a `reason` when a subsystem is degraded. |
| `GET /api/v1/readyz` | `503` until WAL replay has finished, then `200`. |
| `GET /metrics` | Prometheus metrics. |

Keep this listener on the internal network.

## Select roles

Set roles in the configuration file or with environment variables. Environment variables use the `MS_` prefix and join every level of the configuration path with a single underscore: `[node].roles` becomes `MS_NODE_ROLES`, and `[cluster].advertise_addr` becomes `MS_CLUSTER_ADVERTISE_ADDR`. Names with dots are not recognized.

<Tabs>
  <Tab title="TOML">
    ```toml
    [node]
    id = "intake-a1"
    roles = ["intake"]

    [cluster]
    advertise_addr = "10.0.1.21:5082"
    heartbeat_interval_secs = 5
    peer_timeout_secs = 15
    ```
  </Tab>
  <Tab title="Environment variables">
    ```bash
    export MS_NODE_ROLES='["intake"]'
    export MS_NODE_ID=intake-a1
    export MS_CLUSTER_ADVERTISE_ADDR=10.0.1.21:5082
    export MS_SELF_TELEMETRY_CLUSTER_TOKEN="<shared secret>"

    molesignal --config ./conf/config.toml
    ```
  </Tab>
  <Tab title="One process per role">
    ```bash
    MS_NODE_ROLES='["router"]'
    MS_NODE_ROLES='["intake"]'
    MS_NODE_ROLES='["querier"]'
    MS_NODE_ROLES='["compactor"]'
    MS_NODE_ROLES='["alert"]'
    ```
  </Tab>
</Tabs>

Every node of a cluster must use the same PostgreSQL database and the same object storage, and must share these settings: `MS_CIPHER_KEY`, `MS_AUTH_JWT_SECRET_OVERRIDE` (when a fixed signing secret is needed), and `MS_SELF_TELEMETRY_CLUSTER_TOKEN`. Give every node a unique `[node].id` and an `advertise_addr` that its peers can reach on the internal gRPC port.

Two processes that publish the same dataset under one `[node].id` fence each other. Once one of them has published, the flushes of the other are rejected. The fenced process drops the rows it still holds in memory, keeps its WAL on disk, and answers `503` for writes to that dataset until it restarts with a unique id.

## Data flow

### Intake path

A request to an intake endpoint of the router (`/api/v1/intake/*`, or OTLP gRPC) is authenticated and decoded on the router. The router then forwards the batch over the internal gRPC port to an intake node chosen by consistent hashing on the organization and the stream, so the records of one stream reach the same node. When that node cannot be reached, the router tries the other intake nodes. The router answers `503` when no intake node is alive.

The intake node runs the pipelines, masking, and schema evolution, appends each batch to the WAL, then to an in-memory buffer, and answers the router with the result that a standalone node would give. A background flush encodes the buffer into Parquet files and a search index, uploads them to the object store, records them in the file catalog in PostgreSQL, and truncates the flushed WAL segments. Objects at least `[object_store].multipart_threshold_mb` large are uploaded in parts.

A collector can also send OTLP gRPC directly to an intake node. The other roles write the data they generate themselves, such as derived datasets, with the same WAL and flush on their own node.

### Query path

A SQL or PromQL request reaches the router, which checks authorization, admission, and the result cache, then sends the request over the internal gRPC port to a querier node chosen in turn. The querier runs the complete query against its own engine and returns the result. The router tries the other queriers when the chosen one cannot be reached, and answers `503` with `no querier node is available` when none is alive. A query that names remote clusters is merged from their results on the router.

A query reads the files that the file catalog lists. In a role-split cluster, a record that an intake node still buffers becomes visible to queries after the next flush, within `[intake].flush_interval_secs` (30 seconds by default) or sooner when the buffer reaches its size limit.

### Asynchronous search jobs

A query whose estimated size exceeds `[querier].auto_async_threshold_rows` becomes a durable search job. The router stores the job in PostgreSQL, and workers on the querier nodes claim jobs without running the same job twice. See `[search_jobs]` in [Configuration](/en-US/configuration).

### Federated query

Add `?clusters=local,<cluster-name>` to a query to include remote clusters. The node that receives the request scans its own part, requests a scan from every enabled remote cluster with a bearer token, merges the batches, and runs the full SQL. A remote cluster that cannot be reached is reported as degraded in the federation metadata instead of silently becoming local data. Remote clusters are managed in **Settings**.

## Cluster membership

There is no gossip or consensus component. Every node writes a heartbeat row to PostgreSQL with its id, roles, and `advertise_addr`, every `[cluster].heartbeat_interval_secs` (default 5). Peers whose last heartbeat is older than `[cluster].peer_timeout_secs` (default 15) are ignored, and rows that stay silent for five minutes are removed. A node finds peers by reading that table and filtering by role, and caches the result for up to 2 seconds. A `standalone` node handles writes and queries in its own process and forwards nothing.

A node that receives `SIGTERM` or `SIGINT` deletes its own row before it finishes its remaining work, so peers stop using it within 2 seconds instead of waiting for the timeout. A drain through `POST /api/v1/node/drain` deletes the row at the next heartbeat.

The internal gRPC port `5082` carries write forwarding, query forwarding, and scan traffic between nodes without authentication. Keep it on a trusted network.

### Work division between compactor nodes

Several nodes can run the `compactor` role at the same time. Each stream and each organization has exactly one owner among the live compactor nodes, and the owner runs the work of that stream or organization. A `standalone` node counts as one of the compactor nodes. Deletions that are safe to repeat run on every node.

| Work | Divided by | Runs on |
|---|---|---|
| File compaction, metric downsampling, and retention | Stream | The owner of the stream |
| Partition manifest sealing | Stream | The owner of the stream |
| Index rebuild and catalog reconciliation | Organization | The owner of the organization |
| Delayed object deletion | Delete queue entry | Every compactor node. A node claims an entry with a lease of `[storage.gc].lease_secs` before it deletes the object. |
| Expiry of session replay segments and investigation stacks | Not divided | Every compactor node. Deleting an expired item again has no effect. |

The owner comes from rendezvous hashing over the ids of the live compactor nodes. Nodes that see the same members compute the same owner, without a coordinator or a lock table. When a node joins or leaves, only the streams and organizations of that node move.

- **Node failure.** A node that stops sending heartbeats leaves the membership after `[cluster].peer_timeout_secs`. Node discovery is cached for up to 2 seconds, so with the default settings the remaining nodes take over its streams and organizations about 17 seconds after the last heartbeat, and process them in the next round of each worker.
- **Node shutdown.** A node that receives `SIGTERM` or `SIGINT` leaves the membership first and then finishes its in-flight work. The remaining nodes take over its streams and organizations about 2 seconds later, and process them in the next round of each worker.
- **New node.** A node starts taking work after it has been in the membership for `[cluster].peer_timeout_secs`. The other nodes hand over its share as soon as they see it, so that share waits for one timeout window instead of being processed twice.
- **Overlap.** Nodes read the membership at slightly different moments, so two nodes can briefly process the same stream while the membership changes. Every result is published to the file catalog in one atomic step, and the node that loses discards its output. An overlap costs some I/O and never duplicates or loses data.

Set a unique `[node].id` on every node. Nodes that share an id count as one member, and each of them processes the whole share of that member.

Every compactor node applies `[compactor].max_concurrent_groups` on its own, so the total merge concurrency grows with the number of nodes.

On `/metrics`, the gauges `work_ownership_members`, `work_ownership_active`, and `work_ownership_owned_units` report the number of members a node sees, whether the node currently takes work, and how many streams or organizations it owned in its latest round. The `work` label of `work_ownership_owned_units` names the job: `compaction` and `partition_manifest` count streams, and `index_rebuild` and `storage_reconciler` count organizations. When the membership is stable, the values of all compactor nodes add up to the number of streams or organizations.

## Rate limiting

The `router` role limits requests per organization and route class with `[router.rate_limit]`. The intake class covers `/api/v1/intake/*` and the query class covers `/api/v1/query` and the paths below it. The limit counts requests of the authenticated organization and answers `429` with a `Retry-After` header when it is exceeded. Each router replica counts on its own, so the effective limit scales with the number of replicas. A `standalone` node does not apply this limit.

## Scaling and high availability

- **Router.** Add replicas behind a load balancer.
- **Querier.** Add replicas. Each query runs on one querier, so more queriers raise the number of queries that run at the same time.
- **Intake.** Run each node with its own persistent WAL volume (a StatefulSet in Kubernetes). Consistent hashing moves organizations when the number of nodes changes, so make sure the WAL has been flushed before scaling down, and leave time for WAL replay before routing traffic to a restarted node.
- **Compactor.** Add replicas. The nodes divide the work by stream and by organization, the remaining nodes take over when one fails, and rolling updates are safe. See [Work division between compactor nodes](#work-division-between-compactor-nodes).
- **Alert.** Run exactly one instance, and replace it by stopping the old instance before starting the new one (`strategy: Recreate` in Kubernetes). Reliability comes from fast restarts. Evaluation state and incidents live in the metadata database, so a restarted instance resumes from there.
- **Multi-node consensus.** WAL replication between intake nodes is not implemented. Losing an intake node's volume loses the records that were not yet flushed. Changing `[node].roles` requires a restart.
