`molesignal mcp` serves MoleSignal's MCP tools over stdio. An agent tool starts the command
itself and talks to it on standard input and output; the CLI carries every message to the
**Inbound MCP** endpoint of MoleSignal and every answer back. The tools, their permissions, and
their approvals are MoleSignal's: the CLI adds none of its own.

## Add the server to an agent tool

[Sign in](/en-US/cli/sign-in) first, then add a stdio MCP server that runs
`npx -y @molesignal/cli mcp`. In Claude Code:

```bash
claude mcp add --scope user molesignal -- npx -y @molesignal/cli mcp
```

[Connect over stdio](/en-US/inbound-mcp#connect-over-stdio) lists the command or file for Cursor,
Codex, VS Code, and Gemini CLI, and the setup prompt at **Mole Agent → Settings → Inbound MCP**
writes the steps for the instance.

Where nobody signs in, such as on a build machine, give the server its credentials in the
environment instead:

```json
{
  "mcpServers": {
    "molesignal": {
      "command": "npx",
      "args": ["-y", "@molesignal/cli", "mcp"],
      "env": {
        "MOLESIGNAL_URL": "https://molesignal.example.com",
        "MOLESIGNAL_TOKEN": "<token>"
      }
    }
  }
}
```

## How messages are carried

- Until the agent tool sends `notifications/initialized`, messages are carried one at a time, in
  order: MoleSignal opens the session with its answer to `initialize`. After that, messages are
  carried as they come, so a slow tool call does not hold up the others.
- A request that cannot reach MoleSignal is answered with an error, so the agent tool does not
  wait.
- When the agent tool closes standard input, the CLI ends the session at MoleSignal and exits.
- Messages that the CLI writes for the reader, such as a lost connection, go to standard error.
  Standard output carries MCP messages only.

## Check the connection

```bash
molesignal status
```

The tool count matches what the agent tool sees. A count of zero usually means that the
organization's Tool Policy or the user's permissions leave no tool available.
