An incident has at most one internal postmortem, written in Markdown. It is kept apart from the
[status page's postmortems](/en-US/status-pages#postmortems); the pages can copy its summary across. How
the pages use it is in [Major incidents and postmortems](/en-US/alerting/major-incidents#postmortems).

| Method and path | What it does | Permission |
|---|---|---|
| `GET /api/v1/alerts/postmortems` | The organization's postmortems, newest first, with counts of their action items. | `postmortems.read` |
| `GET /api/v1/alerts/incidents/{id}/postmortem` | The incident's postmortem and action items. | `alerts.incidents.read` on the incident, and `postmortems.read` |
| `POST /api/v1/alerts/incidents/{id}/postmortem` | Starts a postmortem for the incident. | `alerts.incidents.read` on the incident, and `postmortems.manage` |
| `PUT /api/v1/alerts/postmortems/{id}` | Changes a postmortem: its title, body, status, owner, and reviewers. | `postmortems.manage` |
| `POST /api/v1/alerts/postmortems/{id}/actions` | Adds an action item. | `postmortems.manage` |
| `PUT /api/v1/alerts/postmortems/{id}/actions/{actionId}` | Changes an action item. | `postmortems.manage` |
| `DELETE /api/v1/alerts/postmortems/{id}/actions/{actionId}` | Deletes an action item. | `postmortems.manage` |
| `POST /api/v1/alerts/postmortems/{id}/actions/{actionId}/ticket` | Creates a ticket for an action item. | `postmortems.manage` |

## Start and change a postmortem

```http
POST /api/v1/alerts/incidents/{id}/postmortem
```

| Field | Type | Required | Notes |
|---|---|---|---|
| `title` | string | Yes | 1 to 200 characters. |
| `body` | string | No | The Markdown body, up to 100000 characters. |

An incident that already has a postmortem answers `409`. The pages first draft the body from a template
(summary, impact, timeline, root cause, what went well, what went badly, action items) and then call this;
the creation is recorded in the audit log. A change sends only the fields to change: `title`, `body`,
`status`, `ownerId` (`null` clears it), and `reviewerIds`.

<RequestExample>
```bash cURL
curl -X PUT http://localhost:5080/api/v1/alerts/postmortems/$POSTMORTEM_ID \
  -H "authorization: Bearer $MS_TOKEN" \
  -H "content-type: application/json" \
  -d '{"status": "in_review", "reviewerIds": ["<user-id>"]}'
```
</RequestExample>

Reading, starting, and changing return `{ "postmortem": { ... }, "actions": [ ... ] }`; `postmortem` is
`null` when the incident has none.


| Field | Notes |
|---|---|
| `status` | `draft`, `in_review`, or `published`. The first change to `published` records `publishedAt`. |

Each row of the list has the postmortem's fields plus the incident summary `incidentSummary`, the action
items still open `openActions`, and those past their due date and still open `overdueActions`.

## Action items

Adding one takes `{ "title": "…", "ownerId": "<user-id>", "dueAt": 1790600000000000 }`, with a title of 1
to 300 characters, at most 50 per postmortem, and `dueAt` in Unix microseconds. A change sends only the
fields to change: `title`, `ownerId` and `dueAt` (`null` clears either), and `status` (`open` or `done`).
Adding and changing return the action item, and deleting returns `{ "deleted": true }`.

```http
POST /api/v1/alerts/postmortems/{id}/actions/{actionId}/ticket
```

The body is `{ "connectorId": "<connector-id>" }`: creates a ticket for the action item with that
[ticket connector](/en-US/api/alerting/tickets) and returns the action item with `ticketKey` and
`ticketUrl`; one that already has a ticket is returned as it is. The ticket gets no comments or
transitions from the incident, and does not resolve the incident when it is done.

**Errors**

| Status | Reason |
|---|---|
| `400` | A field is beyond its limits, or the ticket connector is disabled. |
| `403` | A permission is missing, or the incident is out of reach. |
| `404` | The incident, postmortem, action item, or ticket connector does not exist. |
| `409` | The incident already has a postmortem. |
