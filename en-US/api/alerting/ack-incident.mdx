---
title: "Acknowledge an incident"
description: "Acknowledge an incident and stop its escalation."
"zh-Hans_link": "/zh-Hans/api/alerting/ack-incident"
---

```http
POST /api/v1/alerts/incidents/{id}/ack
```

Acknowledges one `open` incident. The call sets the status to `acknowledged`, records the calling user and the time in `acknowledgedBy` and `acknowledgedAt`, adds the user to `assignees`, and stops escalation, because only `open` incidents advance through an [escalation policy](/en-US/api/alerting/create-escalation). The call also marks the triggered notification as acknowledged and sends an `alert.acknowledged` event. It requires `alerts.incidents.acknowledge`, and the body is empty.

An acknowledged incident stays acknowledged until a user resolves it, unless its escalation policy sets [`ackRetriggerSecs`](/en-US/api/alerting/create-escalation): when it is still unresolved that long after the acknowledgement, it goes back to `open` and is notified again. The evaluator does not resolve it, even when the rule stops matching.

<Note>
  Acknowledging an incident that is already `acknowledged` returns it unchanged. The first user and
  time stay in `acknowledgedBy` and `acknowledgedAt`, and no event is sent again. Acknowledging a
  `resolved` or `closed` incident answers `409`, and the incident keeps its status.
</Note>

<RequestExample>
```bash cURL
curl -X POST http://localhost:5080/api/v1/alerts/incidents/$INCIDENT_ID/ack \
  -H "authorization: Bearer $MS_TOKEN"
```
</RequestExample>

The response is the updated incident. [List incidents](/en-US/api/alerting/list-incidents) describes every field.

**Errors**

| Status | Cause |
|---|---|
| `403` | The token lacks `alerts.incidents.acknowledge`. |
| `404` | The incident does not exist. |
