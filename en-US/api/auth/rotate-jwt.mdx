Both routes require a system-scoped session with `sys.signing_keys.rotate`. An organization-scoped session or an API token receives `403`. Switch a session to the `_sys` organization with [Select a workspace](/en-US/api/auth/select-organization).

## List signing keys

```http
GET /api/v1/auth/jwt/secrets
```

Returns the metadata of the signing keys. Raw key bytes are never returned.

<ResponseExample>
```json 200
[
  {
    "id": "3JtcPZ3AZJFyvBvSkJUia0N7wqo",
    "is_primary": true,
    "created_at_micros": 1790000000000000,
    "retired_at_micros": null
  }
]
```
</ResponseExample>

## Rotate

```http
POST /api/v1/auth/jwt/rotate
```

Creates a new primary key and retires the previous primary. New tokens are signed with the new key. Tokens signed with a retired key stay valid for 24 hours after the retirement.

No node needs a restart. Each node accepts sessions signed with the new key from the first request and signs with it within about 10 seconds. A retired key stops verifying 5 minutes after the 24 hours, which covers that delay and clock differences between nodes.

<ResponseExample>
```json 200
{
  "new_kid": "<new-key-id>",
  "retired_kid": "<previous-key-id>",
  "active_count": 2
}
```
</ResponseExample>

`active_count` is the number of keys that currently verify tokens. A deployment that pins the signing key with `MS_AUTH_JWT_SECRET_OVERRIDE` follows its own rotation policy. See [Security and multi-tenancy](/en-US/security#jwt-signing-keys).
