MoleSignal separates provider credentials from recipients and routing. Configure a connector once,
bind identities or fallback targets, and then choose when the notification engine uses those
routes.

| Resource | Purpose |
|---|---|
| **Connectors** | Store organization-level provider credentials and transport settings. |
| **User routing** | Bind provider identities and order personal delivery endpoints. |
| **Policies** | Match events, resolve recipients, select templates, and control escalation. |
| **Templates** | Reusable message bodies by channel: a general template serves every channel, and SMS, phone and other channels can each have their own. |
| **Fallback routes** | Define ordered team and organization targets after personal delivery fails. |
| **Delivery log** | Inspect attempts, latency, errors, retries, acknowledgement, and escalation. |

All connector timeouts must be between 1 and 60 seconds. URLs must be absolute `http` or `https`
URLs.

A provider's address shows read-only on a connector, ready to copy: Alibaba Cloud and AWS take the
API base URL from the chosen region, a Lark app and a Slack app from the chosen platform, a Teams bot
takes its service URL from the chosen cloud, and the other connectors use the provider's fixed
address, such as a WeCom smart bot's long connection address. Before saving, testing, or sending
directly, MoleSignal checks these addresses against the provider's list and refuses any other address
written through the API, so credentials never go elsewhere. A saved connector keeps its type.

## Create and test a connector

Viewing connectors requires `notify.connectors.read`. Creating, editing, testing, enabling, disabling, or
deleting connectors requires `notify.connectors.manage`.

<Steps>
  <Step title="Open notification management">
    Go to **Settings → Notify → Connectors**.
  </Step>
  <Step title="Choose a provider">
    Click **New connector**, enter a unique name, and select the connector type. Connector type
    cannot change after creation.
  </Step>
  <Step title="Enter provider settings">
    Add the credentials and transport settings described below. Keep **Allow this connector to
    deliver** enabled unless preparing the connector for later use.
  </Step>
  <Step title="Save the connector">
    Click **Save connector**. MoleSignal encrypts the complete configuration at rest. API responses
    replace sensitive values with `***`.
  </Step>
  <Step title="Send a test">
    Edit the saved connector, select a compatible target type, enter a real target, and click
    **Test connection**. The connector status changes to **Connected** or **Error** based on the
    latest test.
  </Step>
</Steps>

<Note>
  Save a new connector before testing. During connector edits, leave a masked `***` value unchanged
  to preserve the stored secret.
</Note>

## Configure each provider

### Email SMTP

Enter the SMTP host, port, username if required, password, and a valid **From address**. Choose one
of these TLS modes:

| TLS mode | Suitable use |
|---|---|
| `none` | The SMTP connection does not use TLS. Avoid this on untrusted networks. |
| `starttls` | The server upgrades the connection with STARTTLS, commonly on port `587`. |
| `tls` | The connection starts with TLS, commonly on port `465`. |

Use `fixed_address` or `direct_user` for the test target and enter a valid mailbox such as
`oncall@example.com`.

### Slack app

Create a Slack app with a bot token that can call `chat.postMessage`. Add the bot to each channel
where notifications must be sent. Enter:

- **Bot token** — the bot token, normally beginning with `xoxb-`;
- **App-level token** — optional; a token beginning with `xapp-` with the `connections:write` scope, which lets Mole Agent answer in Slack over Socket Mode. See [Mole Agent in IM](/en-US/im);
- **Platform** — Slack, or GovSlack for the US government; with GovSlack, the API and the status
  page authorization are on `slack-gov.com`;
- **Client ID** and **Client secret** — from **Basic Information** of the Slack app, for status
  pages whose visitors add the page to their own Slack channels. See
  [Status pages](/en-US/status-pages#slack);
- **Timeout** — a value from 1 to 60 seconds.

The connector needs the bot token, the client ID and secret, or all three. Notifications need the
bot token. The client secret, like the bot token, is kept encrypted with the connector and is never
returned.

Use a Slack member ID for `direct_user` or a channel ID for `fixed_group`. The value must not
contain whitespace. A display name such as `#alerts` is not a channel ID.

Once the connector is turned on under **Mole Agent → Settings → IM**, alert notifications sent
through it carry Acknowledge and Resolve buttons. See [Alert cards](/en-US/im#alert-cards).

### Slack webhook

Create an incoming webhook in Slack and copy the URL into **Webhook URL**. A `fixed_group` target
uses this configured URL. A `webhook` target treats the target value as an alternate URL for that
delivery.

MoleSignal sends a JSON object with a `text` field. Any non-2xx response marks the attempt as
failed.

### Lark app

Create a tenant app that can obtain a tenant access token and send messages. Enter the **App ID**
and **App secret**. Choose **Feishu** or **Lark** as the **Platform**; the API base URL follows from it.

The selected recipient ID type applies to `direct_user` targets:

| Target type | Value |
|---|---|
| `direct_user` | `open_id`, `user_id`, `union_id`, or email, according to **Recipient ID type** |
| `fixed_address` | Email address; MoleSignal sends with `receive_id_type=email` |
| `fixed_group` | Lark chat ID; MoleSignal sends with `receive_id_type=chat_id` |

With events received over a long connection, the app also lets Mole Agent answer in Feishu. See
[Mole Agent in IM](/en-US/im#feishu).

Once the connector is turned on under **Mole Agent → Settings → IM**, alert notifications sent
through it carry Acknowledge and Resolve buttons. See [Alert cards](/en-US/im#alert-cards).

### Lark webhook

Copy the custom bot URL into **Webhook URL**. If bot signature verification is enabled, also enter
the **Signing secret**. MoleSignal generates the timestamp and HMAC-SHA256 signature for every
request.

A `fixed_group` target uses the configured URL. A `webhook` target can override the configured URL with another
absolute URL. See [Webhook connectors](/en-US/notification-channels/webhooks) for the request and signature
format.

### DingTalk app

Use the robot of an internal DingTalk app. Enter the app's **Client ID** and **Client secret**. Leave
**Robot code** empty unless the robot has a code of its own; it then is the Client ID. MoleSignal
exchanges the credentials for an access token and sends Markdown messages through the robot.

| Target type | Value |
|---|---|
| `direct_user` | DingTalk user ID (`userId`) of a person in the app's visible range |
| `fixed_group` | The `openConversationId` of a group the robot is in |

With its messages received over Stream mode, the robot also lets Mole Agent answer in DingTalk.
See [Mole Agent in IM](/en-US/im#dingtalk). With a **Card template ID** as well, alert notifications
are interactive cards with Acknowledge and Resolve buttons; for building the template, see
[DingTalk interactive cards](/en-US/im#dingtalk-interactive-cards).

### DingTalk webhook

Copy the custom robot's URL into **Webhook URL**. If the robot signs requests, also enter the
**Signing secret**: MoleSignal adds the timestamp and HMAC-SHA256 signature to every request. A
`fixed_group` target uses the configured URL; a `webhook` target replaces it.

### WeCom app

Use a self-built WeCom app. Enter the **Corp ID**, the app's **Secret**, and its **AgentId**.
MoleSignal exchanges them for an access token and sends Markdown messages, which WeCom cuts at
4,096 bytes. Add the address MoleSignal connects from to the app's trusted IPs.

| Target type | Value |
|---|---|
| `direct_user` | A member's user ID in the app's visible range |
| `fixed_group` | The chat ID of a group the app created |

With a **Callback token** and **EncodingAESKey**, and the connector's callback URL entered under the
app's **Receive messages**, alert notifications to members are template cards with Acknowledge and
Resolve buttons. See [Buttons from a WeCom app](/en-US/im#buttons-from-a-wecom-app).

### WeCom webhook

Copy a group robot's URL into **Webhook URL**. A `fixed_group` target uses it; a `webhook` target
replaces it.

### WeCom smart bot

A WeCom smart bot in API mode that receives messages over a long connection. Enter the bot's
**Bot ID** and the **Long connection secret** made for it; the **Long connection address** is fixed
at `wss://openws.work.weixin.qq.com`. Once it is turned on under Mole Agent's **IM**, Mole Agent
answers in WeCom (see [Mole Agent in IM](/en-US/im#wecom)) and the bot delivers notifications too,
with messages and replies all over the long connection.

| Target type | Value |
|---|---|
| `direct_user` | A member's userid as the smart bot sees it |
| `fixed_group` | The chat ID of a group |

The bot reaches only conversations where someone messaged it: people who messaged it directly and
chats where someone mentioned it. Alert notifications are template cards with Acknowledge and
Resolve buttons, and other notifications Markdown. When the server sending a notification does not
hold the bot's connection, the server that holds it sends the notification, usually within seconds;
when no server holds it, the delivery fails. A member's notification method on this connector also
recognizes the person asking in IM.

### Microsoft Teams bot

Use a Bot Framework bot. Enter its **App ID**, a **Client secret**, and its **Tenant ID**; for an
older multi-tenant bot, the tenant is `botframework.com`. Choose the bot's **Cloud**: Global, GCC,
GCC High, or DoD; the service URL follows from it. In GCC High and DoD, tokens come from
`login.microsoftonline.us`, and messages to Mole Agent are verified by the government Bot
Framework. The bot must be installed for the people and teams it writes to.

| Target type | Value |
|---|---|
| `direct_user` | A Teams user ID (`29:…`) or the person's Microsoft Entra object ID |
| `fixed_group` | The conversation ID of a channel or group chat (`19:…`) |

With the callback address MoleSignal gives entered as the Azure Bot's messaging endpoint, the bot
also lets Mole Agent answer in Teams. See [Mole Agent in IM](/en-US/im#microsoft-teams).

### Microsoft Teams webhook

Create a channel webhook with a Workflows flow (**Post to a channel when a webhook request is
received**), or use a classic incoming webhook, and copy its URL into **Webhook URL**. MoleSignal
sends each message as an Adaptive Card.

### Google Chat app

Use a Chat app's service account. Paste the account's JSON key into **Service account key**; it is
encrypted with the connector and never returned. MoleSignal signs a token request with the key and
sends messages as the app. The key's `token_uri` must be Google's token endpoint,
`https://oauth2.googleapis.com/token` (`https://accounts.google.com/o/oauth2/token` in older keys); a
key that names any other address is not saved.

| Target type | Value |
|---|---|
| `direct_user` | A user (`users/123…`) who has messaged the app or installed it |
| `fixed_group` | A space the app is in (`spaces/AAAA…`) |

With a **Pub/Sub subscription** (`projects/<project>/subscriptions/<name>`), the app also lets Mole
Agent answer in Google Chat. See [Mole Agent in IM](/en-US/im#google-chat). Leave it empty when the
app only sends notifications.

### Google Chat webhook

Copy a space's incoming webhook URL into **Webhook URL**. A `fixed_group` target uses it; a
`webhook` target replaces it.

### Phone numbers for voice and SMS

Voice and SMS connectors send to one number: the phone number a member binds (`direct_user`), or a
fixed number in a fallback route (`fixed_address`). Write it with `+` and the country code, like
`+14155550100`; spaces and hyphens are removed. Alibaba Cloud, Tencent Cloud, Huawei Cloud and generic HTTP SMS
connectors also take an 11-digit mainland mobile number.

A call reads the notification's title, then its text, up to 400 characters; a text puts the title on
one line and the text on the next, up to 320 characters. When a notify policy chooses a template for
the phone or SMS channel, the call or text is that template's body alone, without the title. Alibaba
Cloud, Tencent Cloud and Huawei Cloud only send approved templates, whose codes and variables are
written into notify templates, as described in [Provider templates in notify
templates](#provider-templates-in-notify-templates).

Providers limit how often one number is called or texted. A call or text refused for that, for a
wrong number, or for an unapproved template fails the delivery, and the policy goes on to the
person's next method and the fallback routes. Whether a call was answered or heard is not reported
back: a successful delivery means the provider accepted the call or the text.

One connector calls one number at most once a minute. Notifications that arrive within the minute
wait on that line, shown as **Queued to merge** in the delivery log; when the minute is over they
are read in one call, each notification's title in turn (one sent with a phone template reads its
body), and those acknowledged meanwhile are left out; Alibaba Cloud, Tencent Cloud and Huawei Cloud
read the template of the first notification, each variable filled with every notification's value in
turn. Alibaba Cloud allows one
call a minute to a number anyway, so a burst of alerts is no longer refused. When a notify policy sets a
longer window to [merge notifications](#merge-notifications), the policy's window is used.

### Alibaba Cloud voice

Voice notifications from Alibaba Cloud Voice Service, to numbers in mainland China only. Complete
the enterprise qualification in the Voice Service console, apply for a **text-to-speech** voice
notification template such as `Hello, ${content}. Please handle it now.`, and create an AccessKey
for a RAM user that can only call Voice Service. Then fill in:

- **AccessKey ID** and **AccessKey secret**;
- **Region** — one of the regions Alibaba Cloud lists; the API base URL follows from it;
- **Caller ID** — empty for the shared mode; the number you bought in the dedicated mode, which then
  shows on every call so on-call people can save it as a contact. The template must be of the same
  mode;
- **Times read** — 1 to 3.

The template code (starting with `TTS_`) and its variables are written into a phone notify template,
which notify policies choose for the phone channel; see [Provider templates in notify
templates](#provider-templates-in-notify-templates). Alibaba Cloud calls one number at most
once a minute, 5 times an hour and 20 times a day, and refuses the calls beyond that. Keep links and
IP addresses out of the variables.

### Alibaba Cloud SMS

Apply for an **SMS signature** and a **notification** template such as `${content}. Please handle it
now.` in the SMS console, then fill in the AccessKey, **Region** and **Signature**. The region is
one of the regions Alibaba Cloud lists; some regions abroad have addresses of their own, and the API
base URL follows from the region. The template code (starting with `SMS_`) and its variables are
written into an SMS notify template, which notify policies choose for the SMS channel; see [Provider
templates in notify templates](#provider-templates-in-notify-templates).

A variable in a notification template holds 35 characters by default; once Alibaba Cloud lifts the
limit for an enterprise account, raise **Characters per variable** in the notify template. Variables
cannot carry links or IP addresses. Numbers can be mainland mobile numbers or international numbers.

### Tencent Cloud voice

In the voice message console, create an application (which gives the `VoiceSdkAppid`) and apply for a
voice notification template, then create an API key for a sub-user. Fill in **SecretId**, **SecretKey**,
**Region** (looked up with that key; the API base URL follows from it), **App ID (SdkAppId)** and
**Times read** (1 to 3). The template ID and its variables go in a phone notify template, with
variables named by position `1`, `2`, `3`; see [Provider templates in notify
templates](#provider-templates-in-notify-templates).

Voice is prepaid: once the package runs out calls fail, and the delivery log says
`InsufficientBalanceInVoicePackage`. The notify policy then goes on to the person's next method, so
do not leave the phone as the only one. A generated call holds at most 350 characters. The documents
give no limit per variable, and a value that is too long is refused (`ContentLengthLimit`); values
are cut at 20 characters by default, and a wider limit goes in the notify template.

### Tencent Cloud SMS

In the SMS console, create an application (which gives the `SmsSdkAppId`), and apply for a signature
and templates. Then fill in **SecretId**, **SecretKey**, **Region**, **App ID (SdkAppId)** and
**Signature** (the signature's text rather than its ID; required for mainland SMS). The template ID
and its variables go in an SMS notify template, with variables named by position `1`, `2`, `3`.

<Warning>
  Accounts opened after January 25, 2024 and accounts left idle hold at most **6 characters** per
  variable by default, and refuse anything longer (`TemplateParameterLengthLimit`). Values are cut
  at 6 characters by default, which leaves little of an alert's title. Once Tencent Cloud has lifted
  the limit for you, write the new one under **Characters per variable** in the notify template.
  Variables cannot carry links.
</Warning>

An API call that succeeds as a whole has not necessarily sent to this number: the result for the
number is what counts. When it is not `Ok`, the delivery fails and the delivery log says why.

### Huawei Cloud voice

In the voice call console, create an application, buy a landline number and submit voice templates.
Then fill in:

- **AppKey**, **AppSecret** and **App address** — all under application management. Copy the address
  as it is; no API lists it;
- **Caller ID** — the landline you bought, written as country code, area code and number.

The template ID and its variables go in a phone notify template, with variables named by position
`1`, `2`, `3`. A variable holds at most 32 bytes, three of them for a Chinese character, and longer
values are cut. Variables cannot contain `$`, `{` or `}`, which are removed.

### Huawei Cloud SMS

In the message and SMS console, create an application and get a signature and templates approved.
Fill in **AppKey**, **AppSecret** and **App address** (all under application management) and **Channel
number** (the one that goes with the signature); a universal template also needs the **Signature
name**. The template ID and its variables go in an SMS notify template, with variables named by
position `1`, `2`, `3`. A template states its own limit per variable (like `TXT_20`); values are cut
at 20 characters by default, and another limit goes in the notify template.

### Twilio voice

Find the **Account SID** and **Auth token** on the Twilio console, then fill in:

- **Calling number** — a voice-capable number on the account, like `+14155550100`;
- **Language** — the language the notification is read in, such as `en-US` or `cmn-CN`;
- **Voice** — optional, such as `Polly.Joanna` or `Polly.Zhiyu`; Twilio's default voice when empty;
- **Times read** — 1 to 3.

### Twilio SMS

Fill in the **Account SID**, **Auth token**, and **Sender**. The sender is a number on the account
(E.164), a Messaging Service (`MG…`), or an alphanumeric sender ID of up to 11 letters and digits
where the destination country allows one. Texts to US numbers need A2P 10DLC registration first.

### AWS voice and SMS

AWS voice (`aws_voice`) calls with `SendVoiceMessage` from AWS End User Messaging and Amazon Polly
reads the notification; AWS SMS (`aws_sms`) sends a transactional text with `SendTextMessage`. Fill
in:

- **Region** — one the account has enabled. The list is asked of AWS with the connector's credentials
  (EC2 `DescribeRegions`) once they are filled in; sending fails in a region without End User
  Messaging;
- **Authentication** — the same ways as the AWS data connectors: access key, temporary key, node
  identity, assumed role, or web identity. To assume a role, its trust policy requires the external
  ID the page shows;
- **Origination identity** — a phone number, phone number ID, pool ID, or the ARN of one. Voice needs
  one, and the number must be voice-capable; SMS can leave it empty for AWS to pick a number for the
  destination, or name a sender ID;
- **Polly voice** — voice only, optional: `MATTHEW` when empty, `ZHIYU` for Mandarin;
- **API base URL** — follows from the region, such as `https://sms-voice.us-east-1.amazonaws.com`.

The identity needs `sms-voice:SendVoiceMessage` or `sms-voice:SendTextMessage`, and
`ec2:DescribeRegions` to list the regions. An AWS account still
in the sandbox only reaches verified numbers.

### Generic HTTP SMS

Hands each text to your own SMS gateway, or to a provider without a connector of its own, as an HTTP
request you set up. Fill in:

- **Gateway URL** — where the request goes; it can hold placeholders, such as
  `https://sms.example.com/send?to={{phone}}&msg={{content}}` for a GET gateway;
- **HTTP method** — POST, PUT, or GET; a GET has no body;
- **Body format** and **Body** — JSON or a form (`x-www-form-urlencoded`);
  `{"phone": "{{phone}}", "content": "{{content}}"}` by default;
- **Headers (JSON)** — such as `{"Authorization": "Bearer {{secret}}"}`;
- **Secret** — a token or password the gateway needs, kept encrypted; refer to it as `{{secret}}` in
  the URL, headers, and body;
- **Number format** — `+8613800138000` (E.164), `8613800138000` (no +), or `13800138000` (mainland
  numbers without the country code);
- **Success field** and **Success value** — optional. A 2xx answer counts as sent; with a success
  field such as `code` or `result.status`, that field of the JSON answer must also equal the success
  value.

| Placeholder | Value |
|---|---|
| `{{phone}}` | The number to text, in the number format |
| `{{content}}` | The text: the title line and the text line, up to 320 characters |
| `{{title}}` | The notification title |
| `{{text}}` | The notification text |
| `{{secret}}` | The secret |

Values are escaped where they go: as JSON strings in a JSON body, URL-encoded in a form or the URL.
The number and the text must appear somewhere in the request, or the connector cannot be saved.

### Generic webhook

Enter a default URL, select `POST`, `PUT`, or `PATCH`, and choose the **Body**:

- **MoleSignal event**, the default: JSON for machines to read, with the version, the event, the alert,
  the rule and the escalation, plus the target and the rendered message;
- **Notify template body**: the body of the template the notify policy chose for the webhook channel,
  sent as written; a JSON template is sent as JSON. See [Conditions](#conditions) and the formats in
  [Create templates and policies](#create-templates-and-policies).

Every request carries `X-MoleSignal-Event` (the notification type) and `X-MoleSignal-Delivery` (the
delivery ID, for the receiver to drop duplicates). With a **Signing secret** of at least 16 characters
it also carries `X-MoleSignal-Timestamp` and `X-MoleSignal-Sign`, by which the receiver confirms the
request came from MoleSignal. The fields of the body, the signature and examples that check it are in
[Webhook notify connectors](/en-US/notification-channels/webhooks#generic-webhook).

For `direct_user`, `fixed_address`, and `fixed_group`, MoleSignal posts to the configured default
URL and includes the target as routing data. For `webhook`, the target value replaces the default
URL. A 2xx response is successful. If the response contains `X-Request-ID`, MoleSignal records the
header value as the provider message ID. Webhooks are never [merged](#merge-notifications): each
notification is its own request.

<Warning>
  Webhook URLs, authorization headers, tokens, passwords, and signing secrets are credentials. Do
  not put credential values in test targets, templates, or event attributes.
</Warning>

## Bind user notification methods

Administrators can open **Settings → Notify → User routing**, select a member, and click
**Bind notify method**. Each identity selects one connector and one external identity, such as an
email address, a Slack or Lark user ID, or the phone number a voice or SMS connector calls.

After binding an identity:

1. send a test to confirm provider acceptance;
2. verify the identity after the organization confirms ownership;
3. enable the identity in the **Alert events**, **On-call events**, or **Reports** preference;
4. order multiple identities from primary to fallback;
5. optionally configure quiet hours and allow critical alerts to bypass the restriction.

### Move on when nobody acknowledges

In the order for alert events, every step after the first can wait a number of minutes:

| Setting | Effect |
|---|---|
| First step | Sent as soon as the alert fires or escalates to the person. |
| Wait N minutes | Used to send again if nobody has acknowledged the alert N minutes after the person was first notified. |
| Same minutes as the step before | Used only when the step before fails to send. |

For example, Lark at once, SMS after 3 minutes, a call after 5 minutes: once the alert is
acknowledged or resolved, no later step is sent, including those of the people its escalations
reached. A step that fails to send still moves on to the next at once. A step waits at most a day,
and only for alert events; the orders for on-call events and reports only fall back on failure.

Members can manage personal identities and preferences under **Account settings → Notify**.
Reading another member's settings requires `org.members.read`. Changing or attesting another
member's identity requires `org.members.update`.

<Note>
  Remove an identity from every delivery preference before deletion.
</Note>

## Replies to texts and calls

With **Act on replies** turned on in a voice or SMS connector (**Act on keypresses** for voice), whoever
gets an alert handles it without opening MoleSignal:

- **Text messages**: a text of a fired or escalated alert ends with "Reply 31 to acknowledge, 32 to
  resolve." Replying with either code is enough. The tens digit is a number from 0 to 9 the phone number
  rotates through, and the units digit is 1 to acknowledge or 2 to resolve; replying `1` or `2` alone
  acts on the latest text the number got. One code acts on every alert of a merged text. Codes are valid
  for a day.
- **Calls**: after the alert is read, press 1 to acknowledge or 2 to resolve, and the call says what was
  done.

A reply or a keypress acts as the member the message was sent to, who needs `alerts.incidents.acknowledge` and an
active account in an active organization; the timeline records it as an SMS reply or a phone keypress.
Only messages sent to a member carry codes, not those sent to a fixed number of a fallback route.

The provider sends replies and keypresses to a callback URL of MoleSignal, so the external URL
`http.external_url` must be set and the paths under `/api/v1/public/notify/` reachable from the
internet; see [Public access](/en-US/public-access). Once the switch is on and the connector saved, the
connector shows its callback URL, ready to copy:

| Connector | What to do | How the callback is checked |
|---|---|---|
| Twilio SMS | In the number's Messaging settings, set **A message comes in** to Webhook, HTTP POST, with the callback URL. | Twilio's `X-Twilio-Signature`, checked with the connector's Auth Token. |
| Twilio voice | Nothing: each call carries its keypress URL. | Twilio's signature. |
| AWS SMS | Turn on two-way SMS for the number with an SNS topic for the replies, and add an HTTPS subscription with the callback URL as its endpoint to the topic; the subscription is confirmed automatically. Put the topic in **Reply SNS topic ARN** to take replies from it only. | The SNS message signature, with certificates fetched from `sns.<region>.amazonaws.com` only. |
| Alibaba Cloud SMS | In SMS Service, have inbound messages pushed over HTTP to the callback URL. Alibaba Cloud sends approved templates only, so the codes go into the template: fill template parameters with the variables `{{reply.ack}}` and `{{reply.resolve}}`; see [Template variables](#template-variables). | The callback token in the URL. |
| Alibaba Cloud voice | Calls are placed as interactive voice (IvrCall) and need the **Caller ID**, a real number bought for IvrCall; in Voice Service, have receipts pushed over HTTP to the callback URL. After the template is read, a key is awaited for 10 seconds. | The callback token in the URL. |
| Tencent Cloud SMS | In the SMS console's callback settings, set the reply callback to the callback URL. The codes go into the template: fill template variables with `{{reply.ack}}` and `{{reply.resolve}}`. | The callback token in the URL. |
| Tencent Cloud voice | In the voice message console's event callback settings, set the keypress callback to the callback URL. Write "press 1 to acknowledge, 2 to resolve" in the template yourself. A keypress carries only the called number, so it applies to that number's latest call. | The callback token in the URL. |
| Huawei Cloud SMS | When creating the SMS application, set the inbound SMS address to the callback URL. The codes go into the template, as above. | The callback token, the last part of the URL. |
| Huawei Cloud voice | Under application management, set the call status address to the callback URL. One key is collected after the template is read; write "press 1 to acknowledge, 2 to resolve" in the template yourself. | The callback token, the last part of the URL. |
| Generic HTTP SMS | Have the gateway POST the texts it receives to the callback URL as JSON `{"phone": "…", "text": "…"}`, or an array of them. | The callback token in the URL. |

The callback token is derived per connector from the server's root key and is not stored; keep the URL
as a credential. AWS voice messages cannot take keypresses, so `aws_voice` has no such switch.

## Create templates and policies

Open **Settings → Notify → Templates** to create a reusable message body. Select a notification
category and a channel, insert [variables](#template-variables) or start from a
[preset template](#preset-templates), and use the preview event attributes to verify the rendered
message. Variables, preset templates and the preview event attributes on the right of the editor
start folded; select a title to open one. The template list is sorted by channel.

| Channel | Used for | Body |
|---|---|---|
| **General** | Every channel a notify policy chose no template for. | Text, Markdown, or HTML. |
| **Instant messaging**, **Email**, **Webhook** | That channel only. | Text, Markdown, or HTML; an instant messaging template can also be [sent as a card](#cards-in-instant-messaging-templates), and a webhook template can also be JSON: the values are escaped as JSON strings, the filled body must be valid JSON, and it is sent as the **Notify template body** of a [generic webhook](#generic-webhook). |
| **SMS**, **Phone** | That channel only. | Plain text that is all that is sent, without the notification title; an SMS sends 320 characters at most and a call reads 400, and the editor counts them. |

Then open **Policies** and create the routing rule:

1. select an event type and category;
2. add JSON matchers and set the policy priority; under **Time**, **Only inside these hours** or
   **Only outside these hours** limits the policy to weekly hours, judged at the moment the event
   happened, and the hours can count holidays by a [holiday calendar](/en-US/alerting/on-call#holiday-calendars).
   Outside the time the policy sends nothing, and the other policies still apply;
3. choose a recipient resolver and resolver configuration;
4. respect user preferences, force one connector, or send through multiple connectors;
5. select a general template, optionally a template of their own for instant messaging, phone, SMS
   and other channels, and enable user, team, or organization fallbacks;
6. optionally set an acknowledgement timeout and escalation route, and, for alert policies, a window to
   [merge notifications](#merge-notifications);
7. inspect the live delivery preview, which resolves actual members and routes and names the
   template of each step, without sending.

A delivery picks the template by the channel of its connector: the template chosen for that channel,
otherwise the general template, and the event's own message when there is neither. A template a
notify policy uses cannot be deleted, nor moved to another channel.

Policies currently cover alert lifecycle and on-call schedule events. The policy editor lists the
event types and recipient resolvers supported by the running backend. Policies hold back the alert
events of incidents that a [silence](/en-US/alerting/silences) matches; see
[Notifications during a silence](/en-US/alerting/silences#notifications-during-a-silence).

### Merge notifications

When alerts pile up, one person or one group may get a string of notifications within seconds. Notify
policies of the alert and escalation categories have **Merge notifications**: choose 30 seconds, or 1, 2,
or 5 minutes (the API takes 10 seconds to 10 minutes), and the alert notifications to one recipient
through one connector within the window go out as one: the first is sent at once, the rest together when
the window ends, and those acknowledged meanwhile are left out.

- Instant messaging and email send one list: the title is the first title with "(+N)", and the body
  lists the alerts, each linked to its incident when the external URL is set; the cards of a Feishu app
  or Slack app carry **Acknowledge all**; see [Alert cards](/en-US/im#alert-cards).
- Texts and calls write and read each title in turn, and one SMS reply acts on them all; calls are
  merged for at least 60 seconds anyway.
- Webhooks are never merged.

The built-in policies for fired, recovered and escalated alerts merge for 1 minute by default; other
policies **Do not merge** by default.

### Template variables

The body, the values of a provider template and every part of a card can name variables such
as `{{rule.name}}`, filled with the notification's values when it is sent. **Variables** on the
right of the editor lists those of the template's category; select one to insert it at the cursor.
A name ending in `_at` is a timestamp in microseconds, one ending in `_time` a time in UTC such as
`2026-07-29 00:00:00 UTC`. A variable the event does not have stays in the text as written.

Variables of alerts and escalations:

| Variable | Value |
|---|---|
| `{{rule.name}}`, `{{rule.description}}` | The rule's name and description. |
| `{{severity}}`, `{{incident.status}}` | The severity and the alert's status. |
| `{{urgency}}`, `{{priority}}` | The key of the urgency level (`high`, `low`, or a level the organization added) and the priority (`P1` to `P9`, empty when none); see [Urgency](/en-US/alerting/on-call#urgency). Notification policies can match the event attributes `urgency` and `priority` too. |
| `{{urgency_name}}`, `{{priority_name}}` | The names the organization gave the urgency level and the priority under [Urgency and priority levels](/en-US/alerting/on-call#urgency-and-priority-levels); empty when not named. |
| `{{value}}`, `{{threshold}}` | The value that triggered and the threshold. A rule with severity tiers gives the threshold of the alert's severity; anomaly rules have none and write `null`. |
| `{{incident.url}}` | The alert's address in MoleSignal; it needs the external URL `http.external_url`. |
| `{{incident.started_time}}`, `{{incident.duration}}` | When the alert started and how long it has lasted, such as `1h 5m`; a resolved alert counts until it was resolved. |
| `{{incident.acknowledged_time}}`, `{{incident.acknowledged_by}}` | When it was acknowledged and the user ID of who did, once it is. |
| `{{incident.resolved_time}}`, `{{incident.resolved_by}}` | When it was resolved and the user ID of who did, once it is; an alert that recovered by itself has no resolver. |
| `{{incident.assignees}}`, `{{affected_services}}` | The assignees' user IDs and the affected services, comma-separated. |
| `{{service}}`, `{{environment}}` | The service and environment, from the alert's labels or annotations. |
| `{{labels}}`, `{{labels.<key>}}` | Every label (`service=api, env=production`) and the value of one; annotations are `{{annotations.<key>}}`. |
| `{{escalation.step}}`, `{{escalation.loop}}`, `{{escalation.target}}` | The step and round of an escalation, counted from 1, and whom the step notifies (`user`, `schedule` or `team`); escalations only. |
| `{{escalation.reason}}` | Why the escalation notification went out: `step` (the policy moved on), `manual` (escalated now), `reassigned`, `responder_added`, `snooze_ended`, `ack_timeout` (acknowledged but unresolved too long), `severity_raised`, or `urgency_raised`; see [Act on an incident](/en-US/alerting/incidents#act-on-an-incident). |
| `{{reply.ack}}`, `{{reply.resolve}}` | The codes a reply acknowledges and resolves with, such as `31` and `32`; filled in only in alert texts sent by SMS connectors with [Act on replies](#replies-to-texts-and-calls) on, and left as written elsewhere. |

On-call schedules have `{{schedule.*}}`, `{{oncall.*}}` and `{{override.*}}`; besides the
microsecond `_at` values, the handover and the override window are written as
`{{oncall.transition_time}}`, `{{override.start_time}}` and `{{override.end_time}}`. Every category
has `{{event.time}}`, `{{message.title}}`, `{{message.text}}`, and any attribute of the event as
`{{event.attributes.<key>}}`.

### Conditions

A body can hold condition blocks, whose content is kept only when the condition holds:

```text
{{#if severity == "critical"}}Act now{{else}}Take a look{{/if}}: {{rule.name}}
{{#if event.type == "alert.resolved"}}Recovered after {{incident.duration}}{{/if}}
{{#if annotations.runbook_url}}Runbook: {{annotations.runbook_url}}{{/if}}
```

- `{{#if variable == "value"}}` and `!=` compare a variable's value; a variable alone holds when it has
  a value that is not empty;
- `{{else}}` is what is kept when the condition does not hold, and can be left out;
- blocks nest up to 5 deep; a block left open (without `{{/if}}`) cannot be saved, and the editor points
  out what is wrong under the body;
- the preview decides the conditions with the preview event attributes. **Conditions** on the right of
  the editor has a few common ones; select one to insert it.

### Preset templates

**Preset templates** are written bodies to start from, and a body applied stays editable. They are
listed by category and channel: SMS and phone templates get the presets written for their channel,
and instant messaging and email templates also get their own, such as instant messaging Markdown
with a link to the alert or an alert email laid out as a table. Alerts have presets for triggered,
acknowledged and resolved notifications; applying an acknowledged or resolved one previews an
acknowledged or resolved sample alert. Preset bodies follow the interface language, so the Chinese
interface applies Chinese bodies.

### Provider templates in notify templates

Alibaba Cloud, Tencent Cloud and Huawei Cloud only send templates they approved. An SMS or phone
template can carry one for each of them:

- **Template code** — the code the provider gave: for Alibaba Cloud starting with `SMS_` for SMS and
  `TTS_` for voice, for Tencent Cloud and Huawei Cloud their template ID;
- **Variables** — what each variable is filled with. A value is written like the body and may use
  variables, such as `{{rule.name}}`. Alibaba Cloud names them as inside the template's `${…}`;
  Tencent Cloud and Huawei Cloud fill them by position, so the names are `1`, `2`, `3`;
- **Characters per variable** — longer values are cut. Empty takes the default: Alibaba Cloud 35,
  Tencent Cloud SMS 6 and voice 20, Huawei Cloud SMS 20 and voice 32 (voice is also cut at 32 bytes).

These three providers' connectors send the template written for them, other SMS and phone connectors
the template body. When the template a notify policy chose for the channel has none for that
provider, its delivery fails and the delivery log says why.

A test of one of these connectors sends a template of its channel that has one for that provider,
with sample values for the placeholders; testing a member's number bound on such a connector uses the
first such template by name. What scheduled inspections, automations and other direct sends deliver
is not a notify template, so they cannot use these connectors.

### Cards in instant messaging templates

An instant messaging template can turn on **Send as a card**: apps and group bots then send a card,
and turned off they send text as before. The card's text is the template's message body; besides it,
a card has:

- **Card title** — empty uses the notification title;
- **Title color** — by severity (critical red, error orange, warning yellow, the rest blue, and
  green once resolved), or one color;
- **Fields** — a name and a value, such as `{{labels.service}}` for `Service`, at most 10;
- **Link buttons** — button text and an address, such as `{{annotations.runbook_url}}` for
  `Runbook`, at most 5;
- **Footer** — a line of small text at the bottom of the card.

Every part takes variables. A field or link an event cannot fill is left out, and so is a link
whose address is not http(s). The preview in the editor is the rough shape; each platform sends a
card of its own:

| Platform | Sent as |
|---|---|
| **Lark** | An interactive card: the title band in color, fields in two columns, the footer under a rule; in the app, link buttons sit beside the alert's Acknowledge and Resolve buttons. |
| **Slack** | A Block Kit card with a color bar; in the app, link buttons sit beside the alert buttons. |
| **DingTalk** | An ActionCard: the title in color, links as buttons under the card, at most 5; Markdown when there are no links. When the app has a card template ID, alert notifications are interactive cards from that template, with the alert buttons. |
| **WeCom** | Markdown laid out like a card, the title in color (WeCom has only green, grey and orange text). With the alert buttons, a template card of the button interaction kind: fields as subtitles with text, at most 6, and pressing the card opens MoleSignal. |
| **Teams** | An Adaptive Card: the title band in color, fields as facts, links as buttons, the footer under a rule; the bot's link buttons sit with the alert buttons. |
| **Google Chat** | A card: fields as labeled lines, links as buttons, the app's link buttons sitting with the alert buttons; Google Chat card titles have no color. |

Group bots receive no clicks, so their cards carry no Acknowledge or Resolve buttons. A test of a
connector can pick an instant messaging template to send its card, with sample values for the
variables.

### Built-in policies

Every organization starts with the notify policies below, so alerts and on-call events reach people
before any policy is written. They all **Respect user preference**; when a message cannot be sent,
they use the user fallback endpoints, then the team and organization fallback routes. They choose no
template and send the event's own message.

| Built-in policy | Event | Notifies | Starts |
|---|---|---|---|
| Alert fired: notify the owner | Alert triggered | The alert's owner, or its assignees when it has none | On |
| Alert resolved: notify the owner | Alert resolved | The alert's owner, or its assignees when it has none | On |
| Escalation: notify the people of the step | Alert escalated, to people | The people the step names | On |
| Escalation: notify the team of the step | Alert escalated, to a team | The members of that team | On |
| On-call handover: notify both people | On-call shift starting | The person going off call and the person coming on | On |
| On-call gap: notify the schedule managers | On-call coverage missing | The schedule's managers | On |
| Alert acknowledged: notify the owner | Alert acknowledged | The alert's owner, or its assignees when it has none | Off |
| On-call override: notify the people involved | On-call override created | The person covering and the person who was on call | Off |
| Shift swap: notify the people involved | Shift swap updated | Whoever needs to know about the step; see [Shift swaps](/en-US/alerting/on-call#shift-swaps) | On |
| Unreachable on-call member: notify them and the schedule managers | On-call member cannot be reached (30 minutes before a shift) | The person taking the shift and the schedule's managers; see [Members who cannot get alerts](/en-US/alerting/on-call#members-who-cannot-get-alerts) | On |
| Intake budget nearly used: notify the people it names | Intake budget nearly used | The people the budget names; see [Set a budget](/en-US/streams#set-a-budget) | On |
| Intake budget exceeded: notify the people it names | Intake budget exceeded | The people the budget names; see [Set a budget](/en-US/streams#set-a-budget) | On |
| Major incident update: notify the stakeholders | Major incident update | The incident's assignees, roles, and stakeholders; see [Post an update](/en-US/alerting/major-incidents#post-an-update) | On |

Built-in policies are marked **Built-in** in the **Notify policies** list. They can be changed and
turned off, not deleted, and their names stay; a changed one goes back to the settings above with
**Restore default** in the editor. Escalation steps to a schedule have no built-in policy: write one
per schedule with **Current on-call user** as the recipient.

## Configure fallback routes

Open **Settings → Notify → Fallback routes**. Select an organization or team scope and
a notification category. Add one or more enabled connectors, choose `fixed_address` or
`fixed_group`, and enter the provider target.

MoleSignal tries routes in the displayed order after the enabled personal route stages fail. The
policy decides whether to use user, team, and organization fallbacks.

## Inspect and retry deliveries

Open **Settings → Notify → Delivery log**. Filter by event ID, status, or stage. Select an
attempt to inspect the masked target, connector, latency, provider error, and complete delivery
chain.

- `notify.deliveries.read` can inspect delivery history.
- `notify.deliveries.acknowledge` can acknowledge the source event.
- `notify.deliveries.retry` can retry failed routes.

Retries create a new attempt. Existing delivery history remains unchanged.

A delivery with the stage **Direct** comes from a feature that names its connector and target
itself, such as a [scheduled log inspection](/en-US/logs/inspections). A direct delivery passes
through no policy and cannot be retried.

## Connector lifecycle and status

| Status | Meaning |
|---|---|
| **Unknown** | The connector has not completed a successful or failed test yet. |
| **Connected** | The most recent test succeeded. |
| **Error** | The most recent test failed; normal routing skips the connector until a later test succeeds. |
| **Disabled** | MoleSignal does not test or deliver through the connector. |

Disabling a connector does not remove references. Deletion remains blocked while a user identity,
policy, fallback route, or scheduled log inspection still references the connector. Move all
references before deleting the connector.

## Troubleshoot delivery

| Symptom | Check |
|---|---|
| SMTP authentication or TLS failure | Verify host, port, credentials, TLS mode, sender address, DNS, and outbound network access. |
| Slack returns an API error | Verify the bot token, `chat.postMessage` permission, target ID, and channel membership. |
| Lark rejects the message | Verify app permissions, recipient ID type, chat membership, webhook secret, and server clock. |
| Webhook returns an error | Verify the URL, method, header JSON, timeout, and a 2xx endpoint response. |
| No user delivery occurs | Verify the identity and connector are enabled, the category preference contains the identity, and quiet hours do not suppress delivery. |
| Fallback never runs | Verify the policy enables that fallback level and the category has an enabled route. |
| A call or text is not sent | Verify the number starts with + and the country code, the template and signature are approved, the template the notify policy chose for the channel carries an Alibaba Cloud template, the variable names match, and the provider's rate limits and account sandbox. |
| A reply or keypress does nothing | Verify the connector has **Act on replies** on, the provider's callback points at the URL the connector shows, that URL is reachable from the internet, the number got an alert text with codes, the code is less than a day old, and the member it was sent to has `alerts.incidents.acknowledge`. |
