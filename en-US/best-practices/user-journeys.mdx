Customers do not care which service failed, only that checkout does not work. Pick the few journeys
that matter most, and watch each one from three sides: a synthetic check that tries it from outside,
real users who go through it, and the backend that serves it.

| Side | Tool | Catches | Misses |
|---|---|---|---|
| Outside | [Synthetic checks](/en-US/synthetics) | Outages at any hour, even without traffic; expired certificates; DNS failures. | Problems that only some users, devices, or data hit. |
| Real users | [RUM](/en-US/rum) | Slow pages, frontend errors, frustration, and what users really do. | Nothing when nobody uses the journey. |
| Backend | [APM SLOs](/en-US/apm#service-level-objectives) | Errors and latency of the endpoints behind the journey, with an error budget. | Failures that happen before a request reaches the backend. |

## Name the journey and what success means

Write the journey as steps, for example: open the product page, add to cart, pay, see the confirmation.
For each step, name the page or the endpoint, and what counts as success: the status, the content, and a
time limit such as "payment confirmed within 3 seconds".

Keep names stable in every tool: the same view names in RUM, the same route templates in APM, and the
journey name in the synthetic checks.

## Probe it from outside

1. Create an **HTTP / API** check for each critical API step, and a **Browser** check for the whole
   journey. See [Create and publish a check](/en-US/synthetics#create-and-publish-a-check).
2. Assert what success means: a **Critical** assertion for the status and the confirmation text, a
   **Warning** assertion for the time limit.
3. Run it from at least two locations, so one broken network path does not count as an outage, and set
   the failure and recovery thresholds to avoid flapping.
4. **Test revision**, then **Publish revision**. Edits create a new draft, so the published check keeps
   running until the new one is proven.

Browser checks run at most once a minute; API checks can run more often. Use test accounts and test
payment methods, never real customer data.

## Watch real users

With the [Browser RUM SDK](/en-US/rum/browser-sdk) in the application:

- On [Performance](/en-US/rum/performance), follow LCP, INP, and CLS at the 75th percentile for the pages of
  the journey.
- On [Frustration](/en-US/rum/frustration), look for rage clicks, dead clicks, and error clicks on the
  steps of the journey.
- On [Errors](/en-US/rum/errors), assign the issues of the journey to its team.
- Open [session replays](/en-US/rum/session-replay) of failed journeys to see what users saw, with the
  [privacy settings](/en-US/rum/privacy) that mask personal data.

Create [RUM alerts](/en-US/rum/alerts) on the figures that mean the journey is broken for many people,
such as the error rate or a vital of its key page.

## Track the backend with an SLO

Create an [SLO](/en-US/apm#service-level-objectives) on the endpoint behind the critical step, for
example the payment endpoint, with **Succeeds within a threshold** and a latency threshold that matches
the time limit of the journey. Add the [burn-rate alerts](/en-US/apm#burn-rate-alerts): the fast burn
pages, and the slow burn warns.

## Tell customers

Create a [status page](/en-US/status-pages) component for the journey, such as "Checkout". Connect it with
[publication automation](/en-US/status-pages#publication-automation) to the synthetic checks and alert
rules of the journey, with **Manual approval** at first: a confirmed failure becomes a draft update that a
responder approves.

## Review it every week

Copy the built-in RUM dashboard of the application with **Create copy**, add the synthetic results and
the SLO, and schedule a weekly [report](/en-US/reports) to the team. Look at trends, not only at
incidents: a vital that worsens a little each week is a release away from a broken journey.

## Acceptance criteria

- Each critical journey has at least one synthetic check from two locations, published and passing.
- RUM covers the pages of the journey, and its errors have an owner.
- The backend step has an SLO with burn-rate alerts.
- The status page has a component for the journey, connected to its checks or rules.
- A failure of the check in a test environment reaches the on-call person and creates a draft update.
