Apply privacy controls in the browser so sensitive values never reach the network. Start with the
default masked mode and allow additional content only after reviewing the recorded result.

## Privacy-safe defaults

```ts
init({
  applicationId: 'checkout-web',
  clientToken: 'msrum_your_client_token',
  site: 'https://molesignal.example.com',
  defaultPrivacyLevel: 'mask',
  trackUrlQueryString: false,
});
```

With these defaults:

- URL query strings and fragments are removed;
- keys such as `password`, `secret`, `token`, `authorization`, `cookie`, `api_key`, and credit-card
  fields are recursively redacted from user, account, and context data;
- action names are `Click <structural selector>`, and selectors carry no IDs, test IDs, or classes. The text of an
  element names an action only with `defaultPrivacyLevel: 'allow'`;
- DOM text is masked during session replay;
- all input and `contenteditable` values are masked, as they are with `mask-user-input`.

<Warning>
  Field-name redaction is a safety net, not a data-classification system. Do not add credentials,
  payment data, health data, or unnecessary personal information to user or custom context objects.
</Warning>

## Block or mask DOM content

The SDK recognizes privacy attributes without application-specific recorder code:

```html
<section data-molesignal-block>
  <!-- The entire subtree becomes a placeholder. -->
</section>

<span data-molesignal-mask>Account holder name</span>

<div data-molesignal-ignore>
  <!-- Mutations and events for this element are ignored. -->
</div>
```

Replace the default selectors when needed:

```ts
sessionReplay: {
  blockSelector: '.payment-form, [data-private-panel]',
  maskTextSelector: '.customer-name, [data-molesignal-mask]',
  ignoreSelector: '.animation-layer, [data-molesignal-ignore]',
},
```

Use blocking for secrets or large sensitive widgets, masking for text whose layout is useful, and
ignoring for noisy elements that have no investigation value.

## Show the page and hide what people type

`defaultPrivacyLevel: 'mask-user-input'` records the text of the page and masks what people type: the values of inputs and
`contenteditable` elements. It suits pages whose text is the same for everyone. The configured `maskTextSelector` stays masked.

Under `mask`, a region can be shown, for text known to be safe:

```html
<nav data-molesignal-allow>Pricing · Docs · Sign in</nav>
```

`data-molesignal-allow` shows the text of the element and what is inside it. What is blocked, ignored, or marked with
`maskTextSelector` inside it stays so, and inputs and `contenteditable` elements stay masked.

## Allow visible page text carefully

Set `defaultPrivacyLevel: 'allow'` only after marking every sensitive region. It also shows what people type, but for passwords, e-mail
addresses, telephone numbers, fields whose `autocomplete` says they hold a card or a one-time code, and fields inside
`data-molesignal-mask`. The configured `maskTextSelector` stays masked.

```ts
defaultPrivacyLevel: 'allow',
sessionReplay: {
  blockSelector: '[data-molesignal-block], .payment-details',
  maskTextSelector: '[data-molesignal-mask], .customer-identity',
},
```

## Control URLs and network collection

Keep `trackUrlQueryString: false` unless the application guarantees that queries never contain
identifiers or secrets. Exclude sensitive routes or network endpoints before collection:

```ts
excludedUrls: [
  '/account/security',
  /^https:\/\/api\.example\.com\/private\//,
  (url) => url.includes('/token-exchange'),
],
```

`allowedTracingUrls` controls which origins can contribute trace context. The option does not enable request
or response body capture; the SDK records timing and sanitized URL metadata.

## Take sensitive text out at intake

The SDK is the first line of defense and the server is the second. An application takes the kinds of sensitive text it chooses out
of every event before anything is stored, whatever SDK or client sent it. Open the application in
**RUM → Applications** and turn the kinds of **Sensitive data** on or off. All of them are on for a new application.

| Kind | What is taken out | Replaced with |
|---|---|---|
| **Tokens, keys, and passwords** | Bearer and Basic tokens, JWTs, the keys of cloud and code services (AWS access keys, GitHub, GitLab, Slack, Stripe, OpenAI, Google, and npm tokens), private keys, the value after `password=`, `secret:`, `api_key=`, `authorization:` and similar words, and the values of the `Authorization`, `Cookie`, `Set-Cookie`, `Proxy-Authorization`, `X-API-Key`, `X-Auth-Token`, and `X-CSRF-Token` headers. | `[secret]` |
| **Email addresses** | Addresses such as `jane@example.com`. | `[email]` |
| **Phone numbers** | International numbers that begin with `+` and have 8 to 15 digits, 11-digit Chinese mobile numbers, and North American numbers such as `(415) 555-2671`. | `[phone]` |
| **Payment card numbers** | Numbers of 13 to 19 digits, with spaces or dashes between groups, that begin as the numbers of the card networks do and pass the check digit. | `[card]` |
| **Identity numbers** | Chinese resident ID numbers that pass their check character, and US social security numbers. | `[id]` |
| **Sensitive URL parameters** | The values of the query and fragment parameters whose name is `code`, `key`, `sig`, `sid`, `otp`, `ticket`, `email`, `phone`, and similar, or holds `token`, `secret`, `password`, `auth`, `signature`, `api_key`, `credential`, `jwt`, or `session`. The user and password before a host. The name of the parameter stays. | `[redacted]` |

Text is taken out of the addresses an event was at and came from (`view.url`, `view.referrer`, `resource.url`, and the address of an
error), the message and the stack of an error and its causes, the name of a view and of what was clicked, the GraphQL operation, payload,
and variables of a request, the headers of a request and a response, and the `context` object. An address that appears inside text
is scrubbed like an address, and the position a stack gives after it (`:10:5`) stays. `user` and `account` are what the application
chose to send about a person, and are left as they are.

Taking the text out happens before the event is made into rows, so what is derived from it is derived from what is kept:
`view.url_path` and `view.url_path_group` of an address that held an email, and the [issue](/en-US/rum/errors) an error belongs to. Errors that
differ only in the email or the number in their message become one issue.

<Warning>
  The kinds are shapes and checks, not a classification of data. A number that looks like a phone number, such as an 11-digit
  order number that begins with `13`, is taken out as one, and a name or an address typed into free text is not recognized. Turn a kind off when it takes out
  what an investigation needs, and keep sensitive values out of events at the SDK.
</Warning>

A change applies to the events that arrive after it. What was stored before stays as it was. Session replay segments are not
scrubbed: their text is masked by the SDK according to the privacy level above.

## Review before production

<Steps>
  <Step title="Record a controlled test session">
    Exercise sign-in, checkout, profile, search, and error flows with non-production test data.
  </Step>
  <Step title="Inspect every event surface">
    Review session metadata, action names, URLs, error stacks, custom context, and DOM replay.
  </Step>
  <Step title="Add selectors and exclusions">
    Block sensitive subtrees and exclude routes that do not need collection.
  </Step>
  <Step title="Repeat after UI changes">
    Treat privacy selectors as production configuration and test selector behavior after markup changes.
  </Step>
</Steps>
