The **Data security** group of **Settings** holds **Cipher keys**, **Regex patterns**,
**Field masking**, **Domain management**, and **Audit**. Reading the first four requires
`org.field_masking.read`, and changing them requires `org.field_masking.manage`. **Audit** requires
`audit.read`. The retention of audit records is a [platform setting](/en-US/settings/platform#audit-retention).

## Cipher keys

**Cipher keys** lists the data keys of the workspace, with the algorithm, the version, and the time of
the last rotation. MoleSignal creates the key of [encrypted fields](/en-US/streams#encrypted-fields)
by itself the first time a stream writes one; it appears as `__field_default__`. Every key is wrapped
with the cipher root key `MS_CIPHER_KEY`, and its material never leaves the server.

| Action | How |
|---|---|
| **New key** | Enter a **Name** and 32 bytes of key material encoded in base64 (`key_material_b64`). |
| **Rotate** | Paste new 32-byte key material in base64. Rotation adds a version: new data uses it, and the older versions still decrypt what they encrypted. |
| Delete | Data encrypted with the key becomes unreadable. |

<Warning>
  Losing `MS_CIPHER_KEY` makes every encrypted field unrecoverable. See
  [Field-level encryption](/en-US/security#field-level-encryption).
</Warning>

## Regex patterns

A regex pattern finds sensitive text, such as card numbers or tokens, and replaces it.

1. Select **New pattern**.
2. Enter a **Name**, the **Pattern**, and a **Description**. The server checks the pattern when it is
   saved.
3. Enter the **Replacement**. `$1` and other capture groups work, and an empty replacement deletes
   the match.
4. Choose where it applies with **Redact on intake**, then select **Create**.

| **Redact on intake** | Effect |
|---|---|
| On | Every string value of every incoming event is redacted after the pipelines and before it is stored. The original text is gone for good. |
| Off | Stored data keeps the original. A query that calls `mask(<column>)` in SQL gets the column with the patterns applied. |

`mask()` applies every pattern of the workspace. The **Masking** column of the list shows
**On intake** or **Query-only** for each pattern.

## Field masking

Field masking hides parts of field values in query results, while queries still compute on the raw
values. It never applies to metrics streams.

1. Select **New rule** and enter a **Rule name**.
2. **Field match**: an exact field name, or a name with `*` and `?` wildcards such as `user.*`.
   Regular expressions are not accepted.
3. Optionally narrow it with **Stream match**, for example `customer-*`, and **Stream type**.
4. Choose the **Algorithm**, keep **Enable rule** on, and save.

| Algorithm | Effect |
|---|---|
| **Full mask** | Replaces the whole value with the **Replacement**. |
| **Range mask** | Masks the characters from **Start character** up to **End character (exclusive)**. |
| **Inner mask** | Keeps a number of **Visible prefix characters** and **Visible suffix characters**, and masks the middle. |
| **Outer mask** | Keeps only the characters from **Start character** to **End character (exclusive)**, and masks both sides. |
| **HMAC-SHA-256 hash** | Replaces the value with a digest made with a key of the workspace that the server manages. The same value gives the same digest, so results can still be grouped and joined. |

The first enabled rule that matches a field wins. Drag rows to change the order. The field settings of
a [stream](/en-US/streams#schema-and-fields) can override the inherited rule or turn masking off for a
field.

## Domain management

**Domain management** serves the workspace under a hostname of its own, with a certificate that
MoleSignal obtains and renews.

1. Enable `[http.tls]` with an `account_email`. See [HTTP TLS and ACME](/en-US/configuration#http-tls-and-acme).
2. Point the DNS of the hostname at MoleSignal, so that the ACME service reaches
   `/.well-known/acme-challenge/` on the plain HTTP port.
3. Select **Add domain**, enter the **Hostname**, and select **Add domain**.

The list shows the **State** of each hostname, the expiry of its certificate, and the **Last error**.
A new hostname waits as `pending` until the certificate is issued, and becomes `active`. Certificates
renew by themselves within 30 days of expiry. Removing a hostname stops serving it.

## Audit

**Audit** searches the audit trail of the workspace: security-relevant actions and changes to
resources and settings, each with the actor, the action, the target, the status, and the time.

| Filter | Use |
|---|---|
| **From** / **To** | The time range, absolute or relative such as `now-24h`. |
| **Actor kind** / **Actor** | A kind of actor, or one user. |
| **Action** | An action key, such as `audit_retention.update`. |
| **Target kind** / **Target id** | The kind and the ID of the changed resource. |

Select **Apply** to search and **Reset** to clear the filters. Select a row to see the whole event and
**Copy id**. An event of a Mole Agent chat shows the history of that chat. The head of the page says
how long records are kept; **Change retention** opens the platform setting in `_sys`.

Credentials, model keys, sensitive webhook headers, and signing material never appear in audit
records. See [Audit](/en-US/security#audit).

### Audit stream

Every audit event is also written as a row of the workspace's `_audit` logs stream, so it can be
searched in **Logs** and delivered elsewhere, such as to a SIEM, with a
[scheduled pipeline](/en-US/pipelines#platform-streams). The row is cleaned the same way as the record
on this page, and its time is the time of the event.

| Field | Content |
|---|---|
| `audit_id` | The ID of the event, as **Copy id** gives it. |
| `actor_kind`, `actor_id` | Who acted. |
| `action` | The action key. |
| `target_kind`, `target_id` | The changed resource, when the event has one. |
| `ip`, `user_agent` | Where the request came from, when the event records it. |
| `payload` | The details of the event, when it has any. |

This page and the [audit API](/en-US/api/admin/audit) read the authoritative records. Each node writes
the rows in the background, in batches, and holds at most 4,096 events waiting; when that queue is
full, the row is left out of the stream and the record stays. The rows follow the retention of the
stream, like the rows of any stream.

Reading `_audit` needs `audit.read`, like this page:

- Without it, the stream is not in the list of streams and cannot be opened, changed, or deleted, and
  a query of it answers `403`. This holds for queries in the product, the query API with its NDJSON
  streaming, Flight SQL, and federated search, where the remote cluster checks the `audit.read` of the
  caller's token.
- A query of `_audit` always runs in the request: it never becomes a search job, even with
  `Prefer: respond-async`, and submitting a search job for it answers `400`.
- What runs in the background without a person cannot read it, whoever saved it. An alert rule that
  reads `_audit`, through its stream or anywhere in its statement, and a scheduled log inspection of it
  cannot be saved: the call answers `400`, for the owner too. Reports cannot read it either.
- Mole Agent tools and [Inbound MCP](/en-US/inbound-mcp) cannot read it with any credential: neither
  its rows nor its fields.

A [scheduled pipeline](/en-US/pipelines#platform-streams) reads `_audit` with the access of one person:
whoever last saved it. Pausing and resuming do not count as saving. The head of the pipeline's page
shows that person as **Reads \_audit as**, and so does the source in the editor, which tells someone
else who holds `audit.read` and can save: **After you save, it reads with your access.**

- Saving a change needs `audit.read`. A service account token answers `403`, because its
  access cannot be checked again when the pipeline runs. A personal token counts as the person it was
  issued to.
- Before each read, the run checks that the person can still sign in, is still in the organization, and
  still holds `audit.read`. Otherwise the read fails and the run says who and why, for example
  `` `_audit` is read with the access of admin@example.com, who no longer holds audit.read ``. The
  pipeline stays on and its read position stays where it is, so no event is skipped.
- The pipeline goes on from there once the person holds `audit.read` again, or once someone who holds
  it saves the pipeline, even without changing anything. Saving it unchanged without `audit.read`, or
  with a service account token, changes nothing and reports no error.
- Pausing and resuming need only `pipelines.pause`, and do not change whose access the pipeline reads
  with. Resuming [starts over](/en-US/pipelines#schedule-and-read-positions) like any pipeline, so leave
  the pipeline on to keep its read position.
- A backfill reads with the access of whoever submits it. That person needs `audit.read` when
  submitting, and the job checks them again when it runs.

The rows that a pipeline copies are ordinary rows of its destinations, readable by whoever can read
those.
