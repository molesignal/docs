A role is a named set of permissions. A permission policy is one too, kept apart so that several
roles can attach it and API tokens can follow it. A member receives a role for the whole workspace
under [Users](/en-US/identity/members#users). An access grant gives a user or a team a role for the
whole organization or for selected resources, optionally until a date. Open **Identity & Access →
Roles**, **Permission policies**, or **Access grants**.

## Roles

**Roles** lists the built-in and the custom roles of the workspace, with the policies each attaches,
the permissions it grants, and where it is used: members, service accounts, invitations, and
bindings. Built-in roles are read only. See [Built-in roles](/en-US/identity#built-in-roles).

To create a custom role:

1. Select **New role**.
2. Enter a **Key** of lowercase letters, digits, and underscores. It cannot change later.
3. Enter a **Name** and a **Description**.
4. Under **Permission policies**, tick the policies the role attaches. The role holds every
   permission of these policies, and follows them as they change.
5. Under **Permissions of its own**, tick any permission the role needs besides its policies. Each
   permission shows what it allows; one that a ticked policy grants is ticked already, with the
   policy it comes from, and cannot be unticked there.
6. Select **Create role**.

A role grants its own permissions and those of its policies. Select a custom role to change either.
**Delete** removes a custom role only while nothing uses it: no membership, service account,
invitation, or binding. Reading roles requires `iam.roles.read`, changing them requires
`iam.roles.manage`, and deleting them requires `iam.roles.delete`.

## Permission policies

**Permission policies** lists the built-in policies and the custom policies of the workspace, with
the permissions of each and the roles and tokens that use it. A role attaches policies, and an API
token can follow one: see [What a token may do](/en-US/identity/tokens#what-a-token-may-do).

| Built-in policy | Permissions |
|---|---|
| **Read-only observer** | Reads observability data, dashboards, alerts, schedules, saved views, pipelines, functions, reports, status pages, synthetics, service levels, and postmortems. |
| **Data analyst** | Explores observability data, and creates dashboards and saved views. |
| **Pipeline developer** | Reads observability data, and manages streams, pipelines, and functions. |
| **Alert administrator** | Reads observability data, and manages alert rules, schedules, status pages, synthetics, and postmortems. |
| **Organization administrator** | Manages organization settings, members, roles, access grants, API tokens, service accounts, and audit, plus status pages, synthetics, service levels, and postmortems. |
| **Data intake** | Writes data and reports deployments: `logs.write`, `metrics.write`, `traces.write`, `profiles.write`, and `apm.deploy`. Intake tokens follow it. |

Built-in policies are read only and follow the product. Open one and select **Copy as custom
policy** to start a policy of your own from it.

To create a custom policy:

1. Select **New policy**.
2. Enter a **Name**, a **Key** of lowercase letters, digits, and underscores that cannot change
   later, and a **Description**.
3. Under **Permissions**, either tick permissions in **Visual**, or write the document in **JSON**.
   Both edit the same document. JSON names the first thing wrong with it, where it is, and lists
   what a valid document allows before it is saved.
4. Select **Create policy**.

A policy document is written after the AWS IAM policy language:

```json
{
  "Version": "1",
  "Statement": [
    { "Sid": "Dashboards", "Effect": "Allow", "Action": "dashboards.*" },
    { "Effect": "Allow", "Action": ["streams.read", "streams.query"] }
  ]
}
```

- `Version` is `"1"`, and a policy allows at least one permission.
- `Effect` is always `"Allow"`: a policy only allows, and there is no deny.
- `Action` is a permission, or a list of them. `*` stands for any run of characters, so
  `dashboards.*` is every dashboard permission and `*` every organization permission. An action
  that names no permission is refused.
- `Sid` is an optional name for the statement.
- `Resource`, `Condition`, `Principal`, and `NotAction` are refused: a policy applies to the whole
  organization. To give a role over single resources or with conditions, use an
  [access grant](#access-grants).

A policy saves the permissions its document allows at that time. A pattern also covers permissions
added to the catalog later: they join the policy when MoleSignal starts. Ticking in **Visual**
rewrites a document with patterns, a `Sid`, or several statements as one statement listing each
permission, and says so first.

Changing a policy changes every role that attaches it and every token that follows it at once.
**Delete** removes a custom policy only while no role attaches it and no working token follows it. A
revoked or expired token that followed it keeps the permissions it had, as a list. Reading policies
requires `iam.policies.read`, changing them requires `iam.policies.manage`, and deleting them requires `iam.policies.delete`.

## Access grants

An access grant is a role binding: a role for a principal, in an organization, over a scope of
resources. Use one when access should follow a person, a team, or a resource, instead of widening a
broad role.

1. Open **Access grants** and select **New access grant**.
2. **Principal**: choose a **User** or a **Team**, and select it.
3. **Organization**: the current workspace, shown for reference.
4. **Resource scope**: **Entire organization**, or a resource type (**Dashboard** or **Stream**) with
   one resource or **All resources of this type**.
5. **Role and permissions**: the role that the grant gives.
6. **Constraints**: optionally an **Environment** that requests must match exactly, such as `prod`,
   and an **Expires at** time.
7. Select **Create grant**.

**Delete** ends a grant at once. Reading grants requires `iam.grants.read`, and creating or
deleting them requires `iam.grants.manage`.

## Share resources across organizations

A cross-organization share gives another organization access to selected resources of this one. It
is explicit and not transitive: it applies only to the chosen organization and resources, and is
never inherited or passed on.

1. In **Access grants**, select **Share across organizations**.
2. Choose the **Target organization**.
3. Choose the resource type and the resource: a **Dashboard**, or a **Stream**.
4. Choose the permissions: `dashboards.read` and `dashboards.edit` for a dashboard, `streams.read`
   and `streams.query` for a stream.
5. Optionally set **Expires at**, then select **Create share**.

The share starts as **Pending acceptance**. An administrator of the target organization selects
**Accept** in its own **Access grants**, and the share becomes **Active**. Either side can **Revoke**
it. Creating, accepting, and revoking shares requires `iam.cross_org.manage`.

## Roles, policies, and grants API

| Operation | Endpoint | Permission |
|---|---|---|
| List the permission catalog | `GET /api/v1/iam/permissions` | `iam.roles.read` or `iam.policies.read` |
| List roles | `GET /api/v1/roles` | `iam.roles.read` |
| Create a custom role | `POST /api/v1/roles` | `iam.roles.manage` |
| Update a custom role | `PATCH /api/v1/roles/{id}` | `iam.roles.manage` |
| Delete an unused custom role | `DELETE /api/v1/roles/{id}` | `iam.roles.manage` |
| List permission policies, or read one | `GET /api/v1/iam/policies`, `GET /api/v1/iam/policies/{id}` | `iam.roles.read` |
| Create a custom policy | `POST /api/v1/iam/policies` | `iam.roles.manage` |
| Update a custom policy | `PATCH /api/v1/iam/policies/{id}` | `iam.roles.manage` |
| Delete an unused custom policy | `DELETE /api/v1/iam/policies/{id}` | `iam.roles.manage` |
| List or create access grants | `GET /api/v1/iam/role-bindings`, `POST /api/v1/iam/role-bindings` | `iam.policies.read`, `iam.policies.manage` |
| Delete an access grant | `DELETE /api/v1/iam/role-bindings/{id}` | `iam.policies.manage` |
| List or create cross-organization shares | `GET /api/v1/iam/cross-org-grants`, `POST /api/v1/iam/cross-org-grants` | `iam.policies.read`, `iam.policies.manage` |
| Accept or revoke a share | `POST /api/v1/iam/cross-org-grants/{id}/accept`, `POST /api/v1/iam/cross-org-grants/{id}/revoke` | `iam.policies.manage` |

A role's body carries its own `permissions` and the `policy_ids` it attaches; a response adds
`effective_permissions`, everything the role grants. A policy's body carries `key` (on create only),
`name`, `description`, and `document`; a response adds `builtin`, the resolved `permissions`, and
`usage`, the roles that attach it and the working tokens that follow it. A document that is not
valid returns `400` with the place of the problem, such as
``Statement[0].Action[1]: no permission is called `alerts.rules.reed` ``; a policy still in use returns
`409` on delete.
