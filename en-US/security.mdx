MoleSignal applies tenant and authorization controls in the API and data plane, below the web
navigation.

## Tenant isolation

Every organization stream and product resource has an owning `org_id`. Query planning injects the
authorized organization boundary before execution. Resource handlers also load the target and
verify the organization before reads or mutations.

Cross-workspace access must use an explicit IAM grant or supported resource share. A mismatched
resource lookup does not silently switch organizations.

The `_sys` organization is a protected platform scope. Tenant sessions and `ms_*` API tokens cannot
enumerate platform administrators, or MoleSignal self-telemetry.

## Authentication and authorization

MoleSignal accepts:

- browser sessions in HttpOnly cookies, rewritten for the new scope after a workspace switch;
- API tokens shaped `ms_<prefix>_<secret>` in the `Authorization` header;
- dedicated self-authenticating tokens for narrowly scoped public or integration routes.

Users sign in with a password or through an OIDC, OAuth 2.0, SAML, or LDAP provider that an administrator configures under **Identity & Access → SSO providers**.

The API-token prefix is stored for lookup, and the secret is hashed. The complete token is shown
only at creation.

After authentication, the server resolves database-backed permissions, roles, bindings, resource
relationships, target ownership. See [Identity & access](/en-US/identity).

## Browser sessions

A sign-in sets two cookies: an access token that every API request carries, valid for 15 minutes,
and a refresh token that renews it until the session ends after `[auth].session_ttl_secs`. Both are
`HttpOnly`, so page scripts cannot read them, `SameSite=Strict`, and `Secure` over HTTPS. A request
that changes data with the session must come from a MoleSignal page, as the browser marks it with
`Sec-Fetch-Site`. Cross-origin calls to the API never carry credentials.

The server keeps no session records: both tokens are signed JWTs. Signing out deletes the cookies of
that browser, and a token copied out of a browser stays valid until it expires. To cut a user off at
once, disable the account, which every request and every renewal checks. A rotation of the signing
keys ends every session after its 24-hour grace period.

## JWT signing keys

JWT signing keys are bootstrapped into the database on the first start. Raw key bytes are never returned by the
metadata endpoint. A rotation signs new tokens with a new key, and tokens signed with the retired key stay valid for 24 hours.
Every node picks up the new key without a restart.

Listing or rotating signing keys requires the platform permission `sys.signing_keys.rotate`:

```text
GET  /api/v1/auth/jwt/secrets
POST /api/v1/auth/jwt/rotate
```

Use `MS_AUTH_JWT_SECRET_OVERRIDE` only when deployment policy requires a fixed bootstrap key.

## Audit

Security-relevant and product mutation paths record actor, organization, action, target, time, and
safe metadata. Query organization events under **Settings → Audit** with `audit.read`. The same events
are rows of the `_audit` stream; see [Audit stream](/en-US/settings/data-security#audit-stream).

Audit records are kept for 90 days by default. Once a day, records older than the retention period
are deleted for every organization and for the platform, and cannot be recovered. Set the period
under **Settings → Audit retention** in the `_sys` organization, which requires
`sys.settings.retention.manage`; `0` keeps records forever. Each change of the period is recorded in the
platform audit as `audit_retention.update`.

Credentials, model keys, sensitive webhook headers, and raw signing material are
excluded from audit payloads.

## Resource sharing

Public dashboard and report links are bearer credentials, but public links do not become organization
tokens. MoleSignal exchanges a link for a short-lived HttpOnly share session and constrains access
to one saved resource.

Public dashboard panels can execute only server-stored queries through a restricted proxy. Shares
can expire, require a password, enforce a maximum view count, disable downloads, and be revoked or
rotated. See [Resource sharing](/en-US/resource-sharing).

## Field-level encryption

Mark fields as encrypted when creating a stream. MoleSignal encrypts them with AES-256-GCM before
the values reach Parquet, and a plain query returns ciphertext. SQL restores the plaintext with
`decrypt(field)`. See [Streams](/en-US/streams#encrypted-fields).

Organization data keys are wrapped with the cipher root key from `MS_CIPHER_KEY`, and key material
is not returned after creation. Reading key metadata requires `org.cipher_keys.read`; creating,
rotating, or deleting keys requires `org.cipher_keys.manage`.

<Warning>
  Losing `MS_CIPHER_KEY` can make encrypted fields unrecoverable. Store the key in a secrets manager
  and back up the key independently of PostgreSQL and object storage.
</Warning>

## Secret and telemetry hygiene

- Store database, object-store, SMTP, SSO, model-provider, and webhook credentials in a secret
  manager.
- Use `env:` or `secret:` references for sensitive external trace-export headers.
- Keep internal gRPC `5082` on a trusted network because the port includes cluster protocols.
- Put TLS in front of external HTTP, OTLP gRPC `4317`, and Flight SQL `5083`.
- Keep the pprof listener on loopback unless remote diagnostics are explicitly protected.
- Backend tracing excludes request bodies, SQL values, credentials, prompts, model output, and
  tool arguments.

## Rate and size limits

The `router` role applies per-organization token buckets to intake and query requests and answers
`429` with a `Retry-After` header. A `standalone` node does not apply them. See
[Role-based deployment](/en-US/deployment/role-based#rate-limiting). An intake request body above
2 MiB is rejected with `413`.

Password sign-in counts failures per account and per source address. At a limit it answers `429` with
`Retry-After` and no longer checks the password. A lock falls only on the address that made the requests;
the account itself is only slowed down, so nobody can lock someone else out by getting a password wrong.
An account that does not exist counts and answers the same way. See
[Sign-in limits](/en-US/settings/platform#sign-in-limits).

## Hardening for production

Replace the sandbox defaults before real data arrives: the root account, `MS_CIPHER_KEY`, database
and object storage credentials. See the
[Production checklist](/en-US/deployment/production-checklist). On an internal network, open only external
callbacks and public pages to the internet, see [Public access](/en-US/public-access).
