MoleSignal reads one TOML file and `MS_` environment variables. Start from the sample `conf/config.toml` that ships with each release. The sample lists every setting, and this page documents each one.

```bash
molesignal --config /etc/molesignal/config.toml
```

## How configuration is loaded

Settings apply in this order. Later sources override earlier ones.

1. Built-in defaults.
2. The TOML file passed with `--config`.
3. `MS_` environment variables.

Restart the process after changing a setting. A running process logs changes to the file and does not apply them.

<Note>
  Most sections ignore keys that they do not define, so a typo has no effect and produces no warning. The sections `[meta_database]`, `[object_store]` (including `[object_store.retry]`), `[telemetry]` (including `[telemetry.trace]` and `[telemetry.self_collect]`), `[apm]`, `[probe]`, `[otlp_grpc]`, `[notify]`, and `[scheduled_reports.renderer]` reject unknown keys, so a typo stops the process at startup.
</Note>

The **Default** column in the reference tables shows the value from the sample `conf/config.toml`. Where the built-in value used for a missing key differs, the description says so.

## Environment variables

Every setting has an environment variable. Write the `MS_` prefix, then each level of the setting path in upper case, joined by single underscores.

| Setting | Environment variable |
|---|---|
| `[http].port` | `MS_HTTP_PORT` |
| `[meta_database].dsn` | `MS_META_DATABASE_DSN` |
| `[cluster].advertise_addr` | `MS_CLUSTER_ADVERTISE_ADDR` |
| `[node].roles` | `MS_NODE_ROLES` |

Write lists in TOML syntax, for example `MS_NODE_ROLES='["intake","querier"]'`. Names that contain a dot or a double underscore are not recognized.

These variables are read separately from the settings:

| Variable | Purpose |
|---|---|
| `MS_CIPHER_KEY` | Root key for the secrets that MoleSignal encrypts in PostgreSQL. Provide 32 random bytes encoded as base64. Without it, the process falls back to an all-zero development key and logs a warning. Never change the key without running `rewrap-kek`. See [Production checklist](/en-US/production-checklist). |
| `MS_AUTH_JWT_SECRET_OVERRIDE` | Pins the JWT signing secret instead of the one generated in PostgreSQL on first start. |
| `MS_SELF_TELEMETRY_CLUSTER_TOKEN` | Shared secret that authenticates the trace candidates and self-telemetry that role-split nodes forward to each other. Set the same value on every role-split node while [trace capture](#trace-capture-and-tail-sampling) (on by default) or `[telemetry.self_collect]` is enabled. A node without the `intake` role refuses to start without it. |
| `MS_AGENT_OPENAI_API_KEY`, `MS_AGENT_ANTHROPIC_API_KEY`, `MS_AGENT_COMPATIBLE_API_KEY` | Development fallback API keys for Mole Agent model providers. Each has a matching `_BASE_URL` variable. Configure production providers in the product instead. |
| `RELEASE_CHANNEL` | Labels the deployment maturity: `alpha`, `beta`, `rc`, or `stable`. |
| `RUST_LOG` | Overrides `[telemetry].log_level` when set. |
| `AZURE_STORAGE_ACCOUNT`, `AZURE_STORAGE_ACCESS_KEY` | Azure Blob credentials for the `azure` object backend. |
| `GOOGLE_APPLICATION_CREDENTIALS` | Path to the service account JSON for the `gcs` object backend. |

## Minimal production settings

A production node needs these settings at a minimum. The rest of the file can stay at its defaults.

```toml
[http]
external_url = "https://molesignal.example.com"

[meta_database]
dsn = "postgres://molesignal:<password>@db.internal:5432/molesignal"

[object_store]
backend = "s3"
bucket = "molesignal"
region = "us-east-1"
endpoint = ""          # empty for AWS S3, the service URL for S3-compatible storage
access_key = ""        # prefer MS_OBJECT_STORE_ACCESS_KEY
secret_key = ""        # prefer MS_OBJECT_STORE_SECRET_KEY

[wal]
dir = "/var/lib/molesignal/wal"

[auth]
root_email = "admin@example.com"
root_password = "<initial password>"
```

Also set `MS_CIPHER_KEY` in the environment. See the [Production checklist](/en-US/production-checklist) for the full list of steps before going live.

## Node

`[node]` selects the roles that a process runs. See [Role-based deployment](/en-US/distributed-deployment).

| Key | Default | Description |
|---|---|---|
| `roles` | `["standalone"]` | Roles to run: `standalone`, `router`, `intake`, `querier`, `compactor`, `alert`. `standalone` runs all of them in one process. |
| `id` | empty | Node id, at most 64 characters. An empty value uses the OS hostname. Set a distinct id for every process when several run on one host. |
| `drain_timeout_secs` | `30` | Time to wait for pending intake data to flush after `SIGTERM` or `SIGINT`. The process exits when the time elapses. |

## Storage

### Metadata database

`[meta_database]` configures the PostgreSQL database that holds metadata, identities, the file catalog, and product resources.

| Key | Default | Description |
|---|---|---|
| `dsn` | `postgres://molesignal:molesignal@localhost:5432/molesignal` | PostgreSQL connection string. Replace the sample credentials. |
| `min_connections` | `2` | Connections opened at startup. Limited to `max_connections`. |
| `max_connections` | `16` | Connection pool limit. |

MoleSignal applies its embedded schema migrations to the database on start. See [Upgrade](/en-US/upgrade).

### Object storage

`[object_store]` configures the store for Parquet files, search indexes, and profile blobs. Backends: `local`, `s3`, `azure`, `gcs`. Use `s3` for AWS S3 and S3-compatible services such as RustFS, Cloudflare R2, and Alibaba Cloud OSS.

| Key | Default | Description |
|---|---|---|
| `backend` | `local` | `local`, `s3`, `azure`, or `gcs`. |
| `root` | `./data/objects` | Directory of the `local` backend. Ignored by the other backends. |
| `bucket` | empty | Bucket name for `s3` and `gcs`, container name for `azure`. Required for those backends. |
| `region` | empty | S3 region. S3-compatible services state the value that they expect. |
| `endpoint` | empty | S3 endpoint URL. Leave empty for AWS S3. Use `http://host:9000` style URLs for RustFS and similar services. |
| `path_style` | `false` | `false` uses virtual-hosted addressing, which AWS S3 and Huawei Cloud OBS need. Set `true` for path-style addressing, which RustFS and most self-hosted services need. |
| `access_key` | empty | S3 access key, or the Azure storage access key. |
| `secret_key` | empty | S3 secret key. |
| `credentials_file` | empty | Path of a file with the lines `access_key=<value>` and `secret_key=<value>`. See the order below. |
| `multipart_threshold_mb` | `32` | Objects at least this large, in MiB, upload in parts. Manifest objects and writes with a version condition always upload in one request. The minimum is 1. |
| `multipart_part_size_mb` | `8` | Size of one part of a multipart upload, in MiB, from 5 to 1024. Very large objects use larger parts so that an upload stays within 10,000 parts. |
| `range_threshold_mb` | `16` | A read of a byte range at least this large, in MiB, splits into chunk requests that run in parallel. The minimum is 1. |
| `range_chunk_mb` | `8` | Size of one chunk request, in MiB, from 1 to 1024. |
| `max_concurrency` | `8` | Concurrent object store operations per process. |
| `op_timeout_secs` | `30` | Timeout for waiting for a concurrency slot and for one backend operation. |
| `health_probe_interval_secs` | `30` | Interval of the background write, read, and delete probe. The minimum is 5. |

The S3 and Azure clients take their credentials from the first of these sources that provides both an access key and a secret key:

1. The variables `MS_OBJECT_STORE_ACCESS_KEY` and `MS_OBJECT_STORE_SECRET_KEY`.
2. The file that `credentials_file` names.
3. The keys `access_key` and `secret_key`.

The startup log reports the winner as `object_store_credentials_source`: `env`, `file`, `inline`, or `none`. Prefer an environment variable or a credentials file over `config.toml` for the secret.

Every part of a multipart upload and every chunk of a ranged read is an object store operation that takes a concurrency slot, retries on its own, and shows in the `object_store_*` metrics. One transfer holds at most half of the slots, so large objects do not starve other operations.

Transient errors of the cloud backends are retried with exponential backoff:

| Key | Default | Description |
|---|---|---|
| `[object_store.retry].max_attempts` | `4` | Total attempts per operation. |
| `[object_store.retry].base_backoff_ms` | `100` | First wait. |
| `[object_store.retry].max_backoff_ms` | `5000` | Largest wait. |
| `[object_store.retry].jitter_ratio` | `0.2` | Random jitter applied to each wait, from `0` to `1`. |

### Write-ahead log

`[wal]` configures the write-ahead log of nodes that run the `intake` role. Put the directory on a persistent local volume. See [Backup and restore](/en-US/backup-restore).

| Key | Default | Description |
|---|---|---|
| `dir` | `./data/wal` | WAL directory. |
| `segment_size_mb` | `256` | Segment size in MB. A full segment starts a new one. |
| `flush_strategy` | `batch` | When to `fsync`. `none` never syncs and relies on the page cache. `every_write` syncs each record, which gives the strongest durability and the highest latency. `batch` syncs after `batch_max_pending` records or `batch_max_delay_ms`. |
| `sync_level` | `data` | Depth of each sync. `none` skips it. `data` syncs file data. `all` also syncs metadata and the parent directory. |
| `batch_max_pending` | `64` | Records that trigger a sync in `batch` mode. |
| `batch_max_delay_ms` | `50` | Longest time between syncs in `batch` mode. |
| `encrypt` | `false` | Encrypts each record payload with the root key (`MS_CIPHER_KEY`) before writing it to disk. Absent from the sample file. |
| `max_replay_mb` | `512` | Memory limit for startup replay. Replay flushes once the limit is exceeded. |

### Caches

Each layer is an LRU cache with a time-to-live. A capacity of `0` disables the layer. Hit ratios appear at `/metrics` as `cache_<layer>_hit_ratio`.

| Section | Default capacity | Default TTL | Holds |
|---|---|---|---|
| `[cache.index_handle]` | `10000` | `600` s | Opened search index handles. |
| `[cache.query_result]` | `1000` | `60` s | Results of SQL over closed time windows. |
| `[cache.tantivy_result]` | `1000000` | `600` s | Term counts that prune files. |
| `[cache.tantivy_footer]` | `100000` | `3600` s | Index footers that save range reads. |

Each section takes `capacity` and `ttl_secs`.

`[cache.object]` caches byte ranges of remote objects on local disk. The `local` object backend bypasses it.

| Key | Default | Description |
|---|---|---|
| `enabled` | `true` | Enables the cache. A `max_bytes` of `0` also disables it. |
| `root` | `./data/cache/objects` | Cache directory. |
| `max_bytes` | `10737418240` | Largest cache size, 10 GiB. |
| `block_size_bytes` | `4194304` | Block size, from 1 MiB to 16 MiB. |
| `min_free_bytes` | `1073741824` | Free disk space to keep, 1 GiB. |
| `max_concurrent_fetches` | `16` | Concurrent block fetches. Must be greater than zero. |
| `max_concurrent_fetches_per_object` | `4` | Concurrent fetches for one object. Must be greater than zero. |

### Incremental range cache

`[search.stream_agg_cache]` caches closed windows of range PromQL queries such as `rate(metric[5m])`, so a dashboard refresh recomputes only the newest window. It is disabled by default.

| Key | Default | Description |
|---|---|---|
| `capacity` | `0` | Number of cached query fingerprints. `0` disables the cache. |
| `ttl_secs` | `300` | Entry lifetime. Covers late data beyond `safe_lookback_secs`. |
| `safe_lookback_secs` | `300` | Only windows that end before now minus this value are cached. |
| `max_series_per_query` | `10000` | Series cached per fingerprint. `0` removes the limit. |

| `root_email` | `admin@example.com` | Email of the root account. The built-in value is empty. |
| `root_password` | `admin` | Password of the root account. The built-in value is empty. Replace the sample value. |

MoleSignal creates the root account on the first start, when the database holds no users and both values are set. Changing `root_password` later does not change the password of an existing account. Change it in the web UI instead. At every start, the account with `root_email` becomes the platform administrator, so `root_email` must belong to an existing user.

The JWT signing secret is generated on first start and stored in PostgreSQL. The `[auth].jwt_secret` key from older releases is ignored. Use `MS_AUTH_JWT_SECRET_OVERRIDE` to pin a secret, and `POST /api/v1/auth/jwt/rotate` to rotate it.

## Settings stored in the database

These settings live in PostgreSQL, and the web UI or API changes them. They have no TOML keys:

- SSO providers (OIDC, SAML, and LDAP).
- Remote clusters for federated queries.
- Status page domains and certificates.
- Notification channels, schedules, and escalation policies.
- Mole Agent model providers, prompts, tools, and approval policy.
- Organization cipher keys, field masking rules, and sharing policy.
