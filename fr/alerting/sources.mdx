Une source d’alertes transforme les alertes envoyées par un autre système en [incidents](/fr/alerting/incidents). Comme pour les incidents déclenchés par des règles, une [politique d’escalade](/fr/alerting/on-call#politiques-d’escalade) alerte les équipes d’astreinte et les [politiques de notification](/fr/notification-channels) envoient les notifications. Les incidents se résolvent lorsque la source signale un retour à la normale. Ouvrez **Alertes → Sources**. La consultation nécessite `alerts.sources.read` ; la création, la modification, la suppression et le renouvellement des jetons nécessitent `alerts.sources.manage`.

## Types de sources

Le type de chaque source détermine le format utilisé pour lire le corps de la requête.

| Type | Émetteur | Un incident par |
|---|---|---|
| **API** | Scripts, pipelines CI et systèmes internes qui appellent l’API MoleSignal | Clé de déduplication |
| **Alertmanager** | Un récepteur webhook de Prometheus Alertmanager | Groupe de notifications |
| **Grafana** | Un point de contact webhook de Grafana Alerting | Groupe de notifications |
| **Datadog** | L’intégration Webhooks de Datadog | Moniteur ; chaque groupe d’un moniteur à alertes multiples |
| **PagerDuty** | Un abonnement webhook PagerDuty V3 | Incident PagerDuty |
| **Alibaba Cloud CloudMonitor** | Rappels d’alarme sur seuil et canaux push d’abonnement aux événements | Objet d’une règle d’alarme ou événement système |
| **Tencent Cloud Observability Platform** | Rappels API d’un modèle de notification | Métrique ou événement d’un objet couvert par une politique, avec un incident par niveau si la politique comporte plusieurs niveaux |
| **Amazon CloudWatch** | Alarmes envoyées à une rubrique SNS, via l’abonnement HTTPS de la rubrique | Alarme |
| **Zabbix** | Un type de média webhook Zabbix | Problème |
| **Adresse e-mail** | Une boîte aux lettres IMAP ou des e-mails bruts provenant d’un système de messagerie existant | Série d’e-mails ayant le même objet |

Les systèmes compatibles avec le webhook Alertmanager, comme l’Alertmanager de Thanos, Cortex ou Mimir, utilisent le type **Alertmanager**.

## Créer une source

1. Ouvrez **Alertes → Sources**, puis cliquez sur **Nouvelle source d’alertes**.
2. Sélectionnez le **Type** et saisissez un **Nom**.
3. Sélectionnez la **Politique d’escalade**. L’option par défaut est **Selon le routage (par défaut)**, comme dans l’éditeur de règles : le [routage des alertes](/fr/alerting/routing) détermine l’équipe et la politique d’escalade à partir des règles de routage, de l’équipe responsable du service et de l’étiquette d’équipe. À défaut, il applique la [politique par défaut](/fr/alerting/on-call#politique-par-défaut) nommée `default`. Si vous sélectionnez une politique, elle s’applique aux incidents et le routage détermine uniquement l’équipe. Avec **Sans escalade, politiques de notification uniquement**, les incidents s’ouvrent et déclenchent des notifications, mais aucune politique d’escalade n’alerte l’astreinte.
4. Sélectionnez la **Gravité par défaut**, qui s’applique lorsqu’une alerte ne précise pas sa gravité.
5. Ajoutez des **Étiquettes supplémentaires** si nécessaire, par exemple `team=payments`. La source les ajoute à chaque incident qu’elle ouvre. En cas de conflit, l’étiquette de l’alerte prévaut.
6. Cliquez sur **Créer**. La page de la source s’ouvre et une boîte de dialogue affiche le jeton et la configuration préremplie avec celui-ci. Alibaba Cloud CloudMonitor n’a besoin que de l’adresse d’ingestion : la boîte de dialogue affiche donc cette adresse avec le jeton intégré.

<Warning>
  MoleSignal affiche le jeton uniquement à la création de la source ou au renouvellement du jeton. Après la fermeture de la boîte de dialogue, seul le préfixe commençant par `mspat-` reste visible. En cas de perte du jeton, cliquez sur **Renouveler le jeton** pour en obtenir un nouveau ; l’ancien cesse immédiatement de fonctionner.
</Warning>

## Adresse d’ingestion et jeton

Toutes les sources partagent la même adresse d’ingestion. Le jeton identifie la source à laquelle appartient une alerte :

```text
https://<molesignal-host>/api/v1/intake/alerts
```

Un jeton a la forme `mspat-<36>`, comme un jeton d’API. Il sert uniquement à recevoir des alertes, tandis qu’un jeton d’API ne permet pas d’en recevoir. L’émetteur place le jeton dans un en-tête :

```text
Authorization: Bearer <token>
```

Si l’émetteur ne peut pas définir d’en-têtes (Alibaba Cloud CloudMonitor, Tencent Cloud Observability Platform, Amazon CloudWatch via SNS), il inclut le jeton dans l’adresse : `https://<molesignal-host>/api/v1/intake/alerts?token=<token>`.

L’émetteur doit pouvoir accéder à cette adresse. Si un pare-feu protège MoleSignal, autorisez les adresses IP de sortie du site ou de la région de l’émetteur : Datadog les indique par site dans la section `webhooks` de ses `ip-ranges`, PagerDuty les publie pour ses régions de service aux États-Unis et dans l’UE, et Alibaba Cloud CloudMonitor répertorie les plages d’adresses utilisées par ses services push dans la documentation sur les rappels d’alarme. Si MoleSignal fonctionne sur un réseau interne, consultez [Accès public](/fr/public-access) pour exposer uniquement cette adresse à Internet.

## Configurer l’expéditeur

La section **Réception** de la page de la source affiche l’adresse de réception, le jeton et la procédure de configuration en trois étapes pour chaque type d’expéditeur. Remplacez `<TOKEN>` par le jeton de la source. À la première requête reçue par la source, les trois étapes apparaissent comme terminées.

### API

```bash
curl -X POST https://<molesignal-host>/api/v1/intake/alerts \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{"dedupKey": "disk-full/web-1", "summary": "Disk almost full on web-1", "severity": "critical", "labels": {"host.name": "web-1"}}'
```

`action` accepte `trigger` (par défaut), `acknowledge` ou `resolve`. Utilisez la même valeur de `dedupKey` pour acquitter ou résoudre la même alerte. La page [Envoyer des alertes](/fr/api/alerting/send-alerts) décrit chaque champ.

### Alertmanager

Ajoutez un récepteur dans `alertmanager.yml` et acheminez les alertes vers ce récepteur :

```yaml
route:
  receiver: molesignal
receivers:
  - name: molesignal
    webhook_configs:
      - url: https://<molesignal-host>/api/v1/intake/alerts
        send_resolved: true
        http_config:
          authorization:
            credentials: <token>
```

Laissez `send_resolved` à `true`, sinon Alertmanager n’envoie pas les notifications de résolution. Configurez la même valeur de `--web.external-url` sur tous les réplicas d’un même cluster Alertmanager : l’URL externe fait partie de la clé de déduplication. Ainsi, des groupes de même nom issus d’instances Alertmanager de régions différentes ne fusionnent pas en un seul incident, même si leur routage est identique.

### Grafana

1. Dans Grafana, ouvrez **Alertes → Points de contact**, puis cliquez sur **Ajouter un point de contact**.
2. Sélectionnez **Webhook** dans **Intégration** et saisissez l’adresse de réception dans **URL**.
3. Sous **Paramètres facultatifs du webhook**, définissez **Schéma de l’en-tête d’authentification** sur `Bearer` et saisissez le jeton dans **Identifiants de l’en-tête d’authentification**.
4. Laissez **Désactiver le message de résolution** décoché, enregistrez, puis utilisez le point de contact dans une politique de notification.

Pour une configuration par fichier :

```yaml
apiVersion: 1
contactPoints:
  - orgId: 1
    name: molesignal
    receivers:
      - uid: molesignal
        type: webhook
        settings:
          url: https://<molesignal-host>/api/v1/intake/alerts
          httpMethod: POST
          authorization_scheme: Bearer
          authorization_credentials: <token>
```

### Datadog

1. Dans Datadog, ouvrez **Intégrations → Webhooks** et ajoutez un webhook nommé, par exemple, `molesignal`.
2. Saisissez l’adresse de réception dans **URL** et `{"Authorization": "Bearer <token>"}` dans **En-têtes personnalisés**. Laissez **Encoder au format formulaire** décoché.
3. Renseignez **Charge utile** avec le modèle ci-dessous. Les noms de champs correspondent à ceux de MoleSignal et les valeurs sont des variables Datadog. MoleSignal refuse toute requête qui n’utilise pas ce modèle.

```json
{
  "alert_id": "$ALERT_ID",
  "alert_cycle_key": "$ALERT_CYCLE_KEY",
  "transition": "$ALERT_TRANSITION",
  "alert_type": "$ALERT_TYPE",
  "priority": "$ALERT_PRIORITY",
  "title": "$ALERT_TITLE",
  "event_title": "$EVENT_TITLE",
  "message": "$TEXT_ONLY_MSG",
  "scope": "$ALERT_SCOPE",
  "tags": "$TAGS",
  "hostname": "$HOSTNAME",
  "link": "$LINK",
  "snapshot": "$SNAPSHOT",
  "query": "$ALERT_QUERY",
  "org_id": "$ORG_ID",
  "last_updated": "$LAST_UPDATED"
}
```

4. Mentionnez `@webhook-molesignal` dans le message de notification d’un moniteur.

Tous les sites Datadog (`datadoghq.com`, `datadoghq.eu`, `us3`, `us5`, `ap1` et les autres) peuvent envoyer des alertes à une même source. MoleSignal extrait le site du domaine de `$LINK` et l’inclut dans la clé de déduplication avec l’identifiant de l’organisation.

### PagerDuty

1. Dans PagerDuty, ouvrez **Intégrations → Webhooks génériques (v3)**, puis cliquez sur **Nouveau webhook**.
2. Saisissez l’adresse de réception dans **URL du webhook** et choisissez le **Type de périmètre** (compte, service ou équipe).
3. Sous **Abonnement aux événements**, sélectionnez `incident.triggered`, `incident.acknowledged`, `incident.resolved`, `incident.reopened` et `incident.priority_updated`.
4. Ajoutez l’en-tête personnalisé `Authorization` avec la valeur `Bearer <token>`.

Les comptes des régions de service américaine et européenne peuvent envoyer des alertes à une même source. MoleSignal inclut le domaine du compte (`<subdomain>.pagerduty.com` ou `<subdomain>.eu.pagerduty.com`) dans la clé de déduplication et l’enregistre dans le label `pagerduty.region`.

### Alibaba Cloud CloudMonitor

Ajoutez le jeton à l’adresse de réception :

```text
https://<molesignal-host>/api/v1/intake/alerts?token=<token>
```

- **Alarmes de seuil** : saisissez cette adresse dans le champ **Rappel d’alarme** d’une règle d’alarme. CloudMonitor envoie une requête POST avec des données encodées au format formulaire. MoleSignal accepte aussi le format JSON.
- **Événements système** : sous **Centre d’événements → Abonnement aux événements → Canaux push**, créez un canal avec le type de cible **Webhook**, la méthode de requête **POST** et le format de données **JSON**. Saisissez cette adresse, puis utilisez le canal dans une politique d’abonnement.

CloudMonitor attend 5 secondes la réponse au rappel d’un événement système et réessaie 3 fois. MoleSignal attend au maximum 3 secondes lorsqu’il transmet une requête au [cluster de réception](#plusieurs-clusters). Si le délai expire, MoleSignal renvoie `503` pour que CloudMonitor réessaie. Les sites chinois et internationaux utilisent le même format dans toutes les régions. MoleSignal enregistre la région dans le label `aliyun.region` et inclut le `userId` du compte dans la clé de déduplication.

### Tencent Cloud Observability Platform

Dans Tencent Cloud Observability Platform (anciennement Cloud Monitor), modifiez ou créez un modèle sous **Gestion des alarmes → Modèles de notification**. Saisissez l’adresse de réception dans **Rappel API**, puis associez le modèle aux politiques d’alarme. Le rappel de Tencent Cloud ne permet pas de définir des en-têtes : placez donc le jeton dans l’adresse. Traitez cette adresse comme un secret : le rappel ne comporte aucune signature et seule l’adresse identifie la source. Les alarmes de métriques et d’événements sont prises en charge. Tencent Cloud transmet les déclenchements et les résolutions.

- **Déduplication** : à compte, politique d’alarme, nom de métrique ou d’événement et objet identiques, MoleSignal crée une seule alerte. Comme dans Tencent Cloud, une politique à plusieurs niveaux génère un incident par niveau, et chaque incident se résout indépendamment.
- **Gravité** : pour `alarmLevel`, Sérieux (`Serious`) correspond à critique, Sévère (`Warn`) à erreur et Rappel (`Remind`) à information. Une politique sans niveaux utilise la gravité par défaut de la source.
- **Événements sans état** (`alarmStatus` vaut `5`) : ces événements ouvrent un incident sans notification de résolution. Résolvez l’incident manuellement.
- **Horodatages** : le rappel ne précise aucun fuseau horaire. MoleSignal interprète les horodatages selon l’heure de Pékin.

### Amazon CloudWatch

Les alarmes CloudWatch ne contactent pas directement les adresses externes. Elles passent par SNS :

1. Dans les notifications de l’alarme, envoyez le passage à l’état **En alarme** (`ALARM`) et le retour à l’état **OK** vers le même sujet SNS. Sans `OK`, les incidents ne se résolvent pas automatiquement. Pour les alertes liées à une absence de données, envoyez aussi l’état **Données insuffisantes** (`INSUFFICIENT_DATA`).
2. Ajoutez un abonnement HTTPS au sujet. Utilisez l’adresse de réception avec le jeton comme point de terminaison :

   ```bash
   aws sns subscribe \
     --topic-arn <ARN of the topic> \
     --protocol https \
     --notification-endpoint 'https://<molesignal-host>/api/v1/intake/alerts?token=<token>'
   ```

3. L’abonnement se confirme automatiquement : MoleSignal vérifie la signature du message de confirmation, puis accède à son `SubscribeURL`.

MoleSignal vérifie la signature de chaque message SNS. Laissez donc **Livraison brute des messages** désactivée. Si cette option est activée, MoleSignal refuse les messages et indique le motif dans la section Réceptions récentes de la page de la source. Le certificat de signature provient de `sns.<region>.amazonaws.com`. Le nœud qui reçoit la requête doit pouvoir accéder à cette adresse.

Les alarmes CloudWatch n’ont pas de gravité : les incidents utilisent la gravité par défaut de la source. L’ARN de l’alarme sert de clé de déduplication, y compris pour les alarmes composites. MoleSignal place la description de l’alarme et le motif du changement d’état dans les annotations. Il place la région, le compte, l’espace de noms, la métrique et les dimensions dans les labels. Un label comme `aws.region` peut ainsi servir au routage.

### Zabbix

Compatible avec Zabbix à partir de la version 6.0. Zabbix n’impose aucun format de requête : le script du type de média envoie la requête. La page de la source et la boîte de dialogue de création proposent donc un type de média avec l’adresse et le jeton préremplis :

1. Enregistrez le type de média au format YAML, puis importez-le sous **Alertes → Types de médias → Importer**. Vérifiez le paramètre `token`.
2. Définissez la macro globale `{$ZABBIX.URL}` sur l’adresse de l’interface Web de Zabbix. MoleSignal l’inclut dans la clé de déduplication, ce qui permet à une même source de recevoir les alertes de plusieurs serveurs Zabbix et d’ajouter des liens vers Zabbix aux incidents. Cette macro reste facultative.
3. Attribuez ce média à un compte utilisateur. Saisissez n’importe quelle valeur dans **Envoyer à** : le script n’utilise pas ce champ.
4. Ajoutez une action de déclencheur dont les **opérations**, les **opérations de résolution** et les **opérations de mise à jour** ciblent toutes ce compte. Sans opérations de résolution, les incidents ne se résolvent pas automatiquement.

Le bouton **Tester** du type de média nécessite des valeurs réelles. Si Zabbix ne remplace pas les macros par leurs valeurs (`{EVENT.ID}` arrive tel quel), MoleSignal renvoie `400` et invite à utiliser le type de média fourni dans la documentation.

### E-mail

Les e-mails peuvent arriver de deux façons. Les deux produisent les mêmes alertes.

**Lire une boîte mail** (recommandé) : MoleSignal relève une boîte mail IMAP à intervalles réguliers. Une connexion sortante et une boîte mail suffisent : aucune adresse publique, aucun enregistrement MX, aucun port 25 ni aucun certificat ne sont nécessaires. C’est l’option la plus simple pour un déploiement auto-hébergé. Envoyez les e-mails d’alerte du système de supervision à cette boîte mail ou transférez-les à l’aide d’une règle de messagerie.

Sur la page de la source, sous **Lire une boîte mail**, renseignez **Serveur IMAP**, **Port**, **Chiffrement**, **Nom d’utilisateur**, **Mot de passe**, **Dossier** (`INBOX` par défaut) et **Intervalle de lecture** (de 15 à 3600 secondes, 60 par défaut). Cliquez sur **Tester la connexion**, puis sur **Enregistrer la boîte mail**.

- **Lecture seule** : MoleSignal utilise `EXAMINE` et `BODY.PEEK[]`. Aucun message n’est marqué comme lu ni supprimé. Un compte en lecture seule suffit.
- **Pas de reprise de l’historique** : à la première connexion, MoleSignal mémorise la position actuelle et ne lit que les nouveaux messages. En cas de changement de serveur, de compte ou de dossier, ou si le serveur reconstruit la boîte mail (changement de `UIDVALIDITY`), MoleSignal repart de la position actuelle. Tant que la source est désactivée, MoleSignal ne lit rien et ne conserve aucune position. La lecture repart de la position actuelle à la réactivation.
- **Liste d’expéditeurs obligatoire** : toute personne qui connaît l’adresse peut y envoyer des e-mails. Sous **Expéditeurs autorisés** dans les paramètres de la source, saisissez des adresses ou `@example.com` pour autoriser tout un domaine. `*` autorise tous les expéditeurs. Le filtre se fonde sur l’en-tête `From`, qui peut être falsifié. Laissez donc le filtre antispam et DMARC du fournisseur de messagerie activés. Tout autre e-mail apparaît comme **Refusée** et n’ouvre aucun incident.
- **Authentification** : utilisez un mot de passe ou un mot de passe d’application fourni par le service de messagerie. Microsoft 365 n’accepte plus les mots de passe : sélectionnez **OAuth 2.0** et renseignez l’URL de jeton `https://login.microsoftonline.com/<tenant>/oauth2/v2.0/token`, l’identifiant client, le secret client et la portée `https://outlook.office365.com/.default`. L’application doit disposer de l’autorisation `IMAP.AccessAsApp` et d’un accès à cette boîte mail.
- **Aucun chiffrement** : n’utilisez cette option que sur un réseau de confiance. Le mot de passe y transite en clair.
- Si la lecture échoue, la page de la source indique la raison. MoleSignal réessaie au cycle suivant. Si plusieurs nœuds gèrent les alertes, un seul lit chaque boîte mail. Avec la fédération, configurez la boîte mail sur le cluster de réception de la source. La configuration ne se synchronise pas, ce qui laisse le mot de passe sur ce cluster.

**Envoyer le message brut par POST** : si un système de messagerie est déjà en place (`pipe` de Postfix, SES ou MIME brut de Mailgun), envoyez le message brut à l’adresse de réception par une requête POST :

```bash
curl -X POST 'https://<molesignal-host>/api/v1/intake/alerts' \
  -H 'Authorization: Bearer <token>' \
  -H 'Content-Type: message/rfc822' \
  --data-binary @alert.eml
```

Le système de messagerie doit pouvoir atteindre l’adresse de réception. La liste d’expéditeurs est facultative dans ce cas, car le jeton identifie déjà l’appelant. Si une liste est configurée, MoleSignal l’applique.

MoleSignal n’intègre pas de récepteur SMTP. Il faudrait ouvrir le port 25 et disposer d’un enregistrement MX, d’un certificat TLS et d’un filtre antispam dédié, ce que la plupart des déploiements auto-hébergés ne peuvent pas fournir.

**Lecture des e-mails** : configurez les règles sous **Mode de lecture des e-mails** dans les paramètres de la source :

| Paramètre | Description |
|---|---|
| **Objets signalant une résolution** | Expression régulière. Laissez le champ vide pour utiliser l’expression intégrée, qui reconnaît `resolved`, `recovered`, `recovery`, `cleared`, `恢复`, `已解决` ainsi que `OK` en début d’objet. Les autres e-mails déclenchent une alerte. |
| **Clé de déduplication extraite de l’objet** | Expression régulière. MoleSignal utilise le premier groupe capturé, par exemple `host=(\S+)`. Si le champ est vide ou si l’expression ne correspond pas, MoleSignal utilise l’objet normalisé : sans `Re:` ni `Fwd:`, sans mots d’état (`PROBLEM`, `RECOVERY`, `告警`, `恢复`, etc.), ni gravités, ni dates, ni heures, ni pourcentages, et sans tenir compte de la casse. Ainsi, « CRITICAL: disk full on web-1 (91%) » et « RECOVERY: disk full on web-1 (40%) » correspondent à une seule alerte, tandis que `web-1` et `web-2` correspondent à deux alertes distinctes. Le domaine de l’expéditeur fait aussi partie de la clé. |
| **Objets à ignorer** | Expression régulière. MoleSignal ignore les e-mails correspondants, mais les affiche dans la section Réceptions récentes. |

MoleSignal détermine la gravité à partir des mots de l’objet (`critical`, `fatal`, `disaster` et `P1` pour critique ; `error` et `P2` pour erreur ; `warning` et `P3` pour avertissement ; `info`, `notice`, `P4` et `P5` pour information). À défaut, MoleSignal utilise la gravité par défaut de la source. Les mots « High » et « Low » dans `High CPU` et `Low disk` ne comptent pas. MoleSignal place le corps du message dans l’annotation `message` (le HTML est converti en texte, limité à 4096 caractères), l’expéditeur dans le label `email.from` et l’annotation `from`, et extrait l’horodatage de l’en-tête `Date`. Les réponses automatiques (`Auto-Submitted: auto-replied`) et les avis de non-remise (`multipart/report`) ne déclenchent pas d’alerte. MoleSignal prend en charge GBK, GB2312 et d’autres jeux de caractères. Au-delà de 4 MiB, MoleSignal indique **Refusée** sans lire le corps du message.

## Comment les alertes deviennent des incidents

| Type | Clé de déduplication | Déclenchement | Résolution | Gravité |
|---|---|---|---|---|
| **API** | `dedupKey` | `trigger` | `resolve` | `severity` |
| **Alertmanager** | URL externe et `groupKey` | `status` du groupe à `firing` | `status` du groupe à `resolved` : toutes les alertes du groupe sont revenues à la normale | Valeur d’étiquette `severity` la plus élevée parmi les alertes actives du groupe |
| **Grafana** | URL externe, organisation et `groupKey` | Comme pour Alertmanager | Comme pour Alertmanager | Comme pour Alertmanager |
| **Datadog** | Site, organisation, ID du moniteur et périmètre | Tout changement d’état sauf `Recovered` | `Recovered` | `$ALERT_PRIORITY` ; à défaut, Warn et No Data correspondent à un avertissement et les autres états suivent `$ALERT_TYPE` |
| **PagerDuty** | Domaine du compte et ID de l’incident PagerDuty | `incident.triggered`, `incident.reopened` ; `incident.priority_updated` modifie la gravité | `incident.resolved` | Priorité de P1 à P5 ; à défaut, une urgence élevée correspond à une erreur et une urgence faible à un avertissement |
| **Alibaba Cloud CloudMonitor** | Compte, ID de la règle et `dimensions` ; pour les événements système, compte et `dedupId` | `ALERT`, `INSUFFICIENT_DATA` ; événement système `TRIGGERED` | `OK` ; événement système `RESOLVED` | `triggerLevel` ; `severity` de l’événement système |
| **Tencent Cloud Observability Platform** | Compte, politique, nom de la métrique ou de l’événement, niveau et objet | `alarmStatus` vaut `1` ou `5` | `alarmStatus` vaut `0` | `alarmLevel` |
| **Amazon CloudWatch** | `AlarmArn` | `NewStateValue` vaut `ALARM` ou `INSUFFICIENT_DATA` | `NewStateValue` vaut `OK` | Aucune : MoleSignal applique la gravité par défaut de la source |
| **Zabbix** | Hôte de `{$ZABBIX.URL}` et `{EVENT.ID}` | `{EVENT.VALUE}` vaut 1 ; les opérations de mise à jour déclenchent aussi l’incident, dont la gravité suit celle de l’alerte | `{EVENT.VALUE}` vaut 0 ou une opération de mise à jour a clôturé le problème | `{EVENT.NSEVERITY}` : Disaster correspond à une gravité critique, High à une erreur, Average et Warning à un avertissement, Information à une information |
| **Adresse e-mail** | Domaine de l’expéditeur et partie extraite de l’objet | Tout autre e-mail | Objet indiquant un retour à la normale | Mots de l’objet |

MoleSignal traite la priorité et l’urgence séparément : `priority` et `urgency` pour l’API, `$ALERT_PRIORITY` pour Datadog, et la priorité et l’urgence pour PagerDuty définissent les valeurs correspondantes de l’incident. En l’absence d’urgence, la politique d’escalade de la source fixe le niveau. Une alerte qui n’indique aucune gravité reçoit un niveau d’urgence élevé. Consultez [Urgence](/fr/alerting/on-call#urgence).

Une alerte sans gravité prend la **Gravité par défaut** de la source. MoleSignal interprète les valeurs de gravité sans tenir compte de la casse, quel que soit l’expéditeur : `critical`, `crit`, `fatal`, `page` et `P1` correspondent à une gravité critique ; `error`, `major`, `high` et `P2` à une erreur ; `warning`, `warn`, `minor`, `medium` et `P3` à un avertissement ; `info`, `low`, `P4` et `P5` à une information. Toute autre valeur prend la gravité par défaut.

- **Ouverture** : une source a au plus un incident actif par clé de déduplication. L’incident porte les étiquettes `alert.source=external` et `external.kind=<kind>`, les étiquettes de l’alerte (les `commonLabels` du groupe pour Alertmanager et Grafana) et les étiquettes supplémentaires de la source. L’étiquette `service.name` ou `service` identifie un service affecté, et `host.name`, `host` ou `hostname` identifie un hôte.
- **Titre** : l’API utilise `summary` ; Alertmanager et Grafana utilisent l’annotation `summary` ou, à défaut, `alertname` ; Datadog utilise `$ALERT_TITLE` ; PagerDuty utilise le titre de l’incident ; Alibaba Cloud CloudMonitor utilise « nom de l’alarme · nom de l’instance ».
- **Liens** : MoleSignal enregistre les URL vers le système émetteur dans des annotations telles que `alertmanager_url`, `generator_url`, `dashboard_url`, `datadog_url` et `pagerduty_url`. La page de l’incident les affiche sous forme de liens. MoleSignal enregistre les entrées de `links` de l’API dans des annotations en utilisant `name` comme clé.
- **Alertes d’un groupe** : un incident issu d’Alertmanager ou de Grafana conserve toutes les alertes du groupe (jusqu’à 100) et actualise leur état à chaque notification. La section **Alerte externe** de la page de l’incident affiche ces alertes avec les étiquettes qui les distinguent.
- **Changements de gravité** : tant que l’incident n’est pas acquitté, sa gravité suit celle que les [pipelines d’alertes](/fr/pipelines/alert-events#changements-de-gravité) attribuent à l’alerte. Si la gravité augmente, l’escalade reprend à la première étape. Une gravité définie manuellement reste inchangée.
- **Acquittement** : `acknowledge` dans l’API, `incident.acknowledged` dans PagerDuty et les opérations de mise à jour qui acquittent un problème dans Zabbix acquittent l’incident et interrompent les étapes d’escalade et les appels restants. MoleSignal n’associe aucun compte utilisateur à cet acquittement.
- **Résolution** : MoleSignal résout l’incident dès que la source signale un retour à la normale, même si l’incident est déjà acquitté. MoleSignal n’associe aucun compte utilisateur à cette résolution et indique le retour à la normale dans la chronologie.
- **Messages tardifs** : pour chaque clé de déduplication, MoleSignal conserve le dernier horodatage pris en compte parmi ceux fournis par l’expéditeur et ignore tout message antérieur. Un déclenchement tardif n’ouvre pas d’incident zombie et un retour à la normale tardif ne clôture pas un nouvel incident. L’API ne fournit pas d’horodatage : MoleSignal traite donc ses messages dans leur ordre d’arrivée.
- **Résolution manuelle avant le retour à la normale** : si la source signale toujours l’alerte, le prochain renvoi ouvre un nouvel incident, comme pour les règles.
- **Aucune donnée** : les incidents déclenchés par `INSUFFICIENT_DATA` dans CloudMonitor ou par No Data dans Datadog portent l’étiquette `alert.condition=no_data`. Le titre de leurs notifications commence par `NO DATA`.
- **Désactivation et suppression** : une source désactivée refuse les alertes (`409`) et ses incidents ouverts le restent. La suppression d’une source invalide immédiatement son jeton et résout ses incidents ouverts.

Les [politiques de mise en silence](/fr/alerting/silences), les [groupes sémantiques](/fr/alerting/silences#groupes-sémantiques) et les [politiques de notification](/fr/notification-channels) s’appliquent aux incidents externes comme aux autres incidents. Utilisez `external.kind`, les étiquettes supplémentaires de la source ou les étiquettes de l’alerte comme critères de correspondance.

## Requêtes reçues récemment

Le haut de la page de la source indique son état : **En attente de la première requête**, **Reçoit des requêtes**, **Dernière requête refusée**, **Aucune requête depuis 7 jours** ou **Désactivée**. À côté figurent les requêtes et les alertes des dernières 24 heures, ainsi que les incidents ouverts par la source et toujours en cours.

Après réception des premières requêtes, la section **Requêtes reçues récemment** de la page de la source affiche, pour chaque requête, l’heure, le résultat (**Traitée**, **Refusée** ou **Transmise**), le statut HTTP, le nombre d’alertes et leur résultat (**Ouverte**, **Dernière mise à jour**, **Inchangée**, **Acquitté**, **Résolu** ou **Ignoré**). Cliquez sur une ligne pour afficher le titre, la gravité, l’action, le résultat et l’incident de chaque alerte. Pour une requête refusée, la page affiche aussi le motif du refus et le début du corps de la requête (jusqu’à 16 KiB). MoleSignal conserve les 500 dernières requêtes de chaque source pendant 7 jours au maximum.

## Plusieurs clusters

Lorsque la [fédération inter-clusters](/fr/settings/data-plane#fédération-de-clusters) est active :

- MoleSignal synchronise les sources entre les clusters, jetons compris, comme le reste de la configuration des alertes. Un même jeton fonctionne donc à l’adresse de réception de chaque cluster.
- Les incidents d’une source s’ouvrent uniquement sur son **Cluster de réception** : le cluster sur lequel la source a été créée, sauf modification dans ses paramètres. Si un autre cluster reçoit une alerte de cette source, il la transmet via gRPC au cluster de réception, puis renvoie la réponse de ce dernier à l’expéditeur. Une alerte externe correspond donc à un seul incident, quelle que soit l’adresse du cluster qui la reçoit.
- Si le cluster de réception est inaccessible, MoleSignal renvoie `503` et l’expéditeur réessaie. Si la région du cluster de réception reste indisponible, choisissez un cluster opérationnel dans le champ **Cluster de réception** des paramètres de la source.
- MoleSignal enregistre les données de **Requêtes reçues récemment** sur le cluster qui a traité la requête. La page de la source le précise lors d’une consultation depuis un autre cluster.

## Limites

| Élément | Limite |
|---|---|
| Corps d’une requête ou d’un e-mail | 4 MiB maximum. |
| Lecture d’une boîte de réception | 50 e-mails maximum par lecture. Les e-mails restants sont traités à la lecture suivante. |
| Une requête API | 100 alertes. `dedupKey` accepte jusqu’à 255 caractères et `summary` jusqu’à 1024 caractères. |
| Une alerte | 64 étiquettes et 64 annotations. L’API rejette les alertes qui dépassent ces limites. Pour les autres types de sources, MoleSignal ignore les étiquettes et annotations excédentaires et tronque les titres et annotations trop longs. |
| Alertes d’un groupe | MoleSignal conserve jusqu’à 100 alertes. |
| Étiquettes supplémentaires d’une source | 32. Aucune clé ne peut commencer par `alert.` ni être égale à `external.kind`. |
| Requêtes reçues récemment | MoleSignal conserve les 500 dernières requêtes de chaque source pendant 7 jours maximum. |

MoleSignal ne vérifie ni la signature HMAC de Grafana ni la signature de PagerDuty : le jeton identifie déjà la source. Lorsque vous accusez réception d’un incident ou le résolvez dans MoleSignal, l’expéditeur ne reçoit pas cette mise à jour.
