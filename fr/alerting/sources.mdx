Une source d'alertes transforme les alertes envoyées par un autre système en [incidents](/fr/alerting/incidents). Elle alerte les personnes via une [politique d'escalade](/fr/alerting/on-call#politiques-d’escalade) et notifie via des [politiques de notification](/fr/notification-channels) de la même manière que les incidents des règles, et elle passe en résolu lorsque la source signale un rétablissement. Ouvrez **Alertes → Sources**. La consultation nécessite `alerts.sources.read` ; la création, la modification, la suppression et le renouvellement de jetons nécessitent `alerts.sources.manage`.

## Types de sources

Chaque source a un type, qui détermine dans quel format le corps de la requête est lu.

| Type | Émetteur | Un incident par |
|---|---|---|
| **API** | Scripts, CI et systèmes internes appelant l'API MoleSignal | Clé de déduplication |
| **Alertmanager** | Un récepteur webhook de Prometheus Alertmanager | Groupe de notifications |
| **Grafana** | Un point de contact webhook de Grafana Alerting | Groupe de notifications |
| **Datadog** | L'intégration Datadog Webhooks | Moniteur ; chaque groupe d'un moniteur multi-alertes |
| **PagerDuty** | Un abonnement webhook PagerDuty V3 | Incident PagerDuty |
| **Alibaba Cloud CloudMonitor** | Rappels d'alarme de seuil et canaux de push d'abonnement aux événements | Objet d'une règle d'alarme, ou événement système |
| **Tencent Cloud Observability Platform** | Rappels API d'un modèle de notification | Une métrique ou un événement d'un objet sous une politique, un par niveau sur une politique à niveaux |
| **Amazon CloudWatch** | Alarmes envoyées vers un sujet SNS, via l'abonnement HTTPS du sujet | Une alarme |
| **Zabbix** | Un type de média webhook Zabbix | Un problème |
| **Azure Monitor** | L'action webhook d'un groupe d'actions, au schéma d'alerte commun | Une alerte |
| **Google Cloud Monitoring** | Un canal de notification webhook, ou le canal Pub/Sub via un abonnement push | Un incident Monitoring |
| **Huawei Cloud Eye** | Alarmes envoyées vers un sujet SMN, via l'abonnement HTTPS du sujet | Une règle d'alarme sur une ressource |
| **Adresse e-mail** | Une boîte aux lettres IMAP, ou des e-mails bruts provenant d'un système de messagerie déjà en place | Une série d'e-mails avec le même objet |

Les systèmes qui parlent le webhook Alertmanager, comme l'Alertmanager de Thanos, Cortex ou Mimir, utilisent le type **Alertmanager**.

## Créer une source

1. Ouvrez **Alertes → Sources** et cliquez sur **Nouvelle source d’alertes**.
2. Choisissez le **Type** et saisissez un **Nom**.
3. Choisissez la **Politique d'escalade**. La valeur par défaut est **Selon le routage (par défaut)**, comme dans l'atelier de règles : le [routage des alertes](/fr/alerting/routing) choisit l'équipe et la politique d'escalade selon les règles de routage, l'équipe propriétaire du service et l'étiquette d'équipe, et sinon la [politique par défaut](/fr/alerting/on-call#politique-par-défaut) nommée `default`. Avec une politique choisie, les incidents l'adoptent et le routage ne choisit plus que l'équipe. Avec **Sans escalade, politiques de notification uniquement**, les incidents s'ouvrent et notifient toujours, mais aucune politique d'escalade n'alerte personne.
4. Choisissez la **Gravité par défaut**, utilisée lorsqu'une alerte ne porte pas de gravité propre.
5. Ajoutez des **Étiquettes supplémentaires** si nécessaire, par exemple `team=payments`. Elles sont ajoutées à chaque incident ouvert par la source. Une étiquette portée par l'alerte elle-même l'emporte.
6. Cliquez sur **Créer**. La page de la source s'ouvre avec une boîte de dialogue qui affiche son jeton et la configuration avec le jeton déjà renseigné ; Alibaba Cloud CloudMonitor n'a besoin que de l'adresse d'ingestion, la boîte de dialogue affiche donc l'adresse avec le jeton intégré.

<Warning>
  Le jeton n'est affiché qu'à la création de la source ou au renouvellement de son jeton. Une fois la boîte de dialogue fermée, seul le préfixe commençant par `mspat-` reste visible. Si le jeton est perdu, cliquez sur **Renouveler le jeton** pour en obtenir un nouveau ; l'ancien jeton cesse immédiatement de fonctionner.
</Warning>

## Adresse d'ingestion et jeton

Toutes les sources partagent une même adresse d'ingestion. Le jeton indique à quelle source appartient une alerte :

```text
https://<molesignal-host>/api/v1/intake/alerts
```

Un jeton ressemble à `mspat-<36>`, de la même forme qu'un jeton d'API, mais il ne reçoit que des alertes, et un jeton d'API ne peut pas recevoir d'alertes. L'émetteur le place dans un en-tête :

```text
Authorization: Bearer <token>
```

Un émetteur qui ne peut pas définir d'en-têtes (Alibaba Cloud CloudMonitor, Tencent Cloud Observability Platform, Amazon CloudWatch via SNS, Azure Monitor, Google Cloud Monitoring, Huawei Cloud Eye via SMN) transporte le jeton dans l'adresse : `https://<molesignal-host>/api/v1/intake/alerts?token=<token>`.

L'émetteur doit pouvoir joindre cette adresse. Lorsqu'un pare-feu se trouve devant MoleSignal, autorisez les adresses de sortie du site ou de la région de l'émetteur : Datadog les liste par site dans la section `webhooks` de ses `ip-ranges`, PagerDuty les publie pour ses régions de service US et UE, et Alibaba Cloud CloudMonitor liste ses plages de push dans sa documentation sur les rappels d'alarme. Lorsque MoleSignal s'exécute sur un réseau interne, consultez [Accès public](/fr/public-access) pour n'ouvrir que cette adresse à Internet.

## Configurer l’expéditeur

**Réception** sur la page de la source donne l’adresse de réception, le jeton et la configuration de chaque type en trois étapes. Remplacez `<TOKEN>` par le jeton de la source. Une fois que la source reçoit sa première requête, les trois étapes sont cochées.

### API

```bash
curl -X POST https://<molesignal-host>/api/v1/intake/alerts \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{"dedupKey": "disk-full/web-1", "summary": "Disk almost full on web-1", "severity": "critical", "labels": {"host.name": "web-1"}}'
```

`action` vaut `trigger` (valeur par défaut), `acknowledge` ou `resolve`. Utilisez le même `dedupKey` pour accuser réception de la même alerte ou la résoudre. [Envoyer des alertes](/fr/api/alerting/send-alerts) décrit chaque champ.

### Alertmanager

Ajoutez un récepteur à `alertmanager.yml` et acheminez les alertes vers celui-ci :

```yaml
route:
  receiver: molesignal
receivers:
  - name: molesignal
    webhook_configs:
      - url: https://<molesignal-host>/api/v1/intake/alerts
        send_resolved: true
        http_config:
          authorization:
            credentials: <token>
```

Conservez `send_resolved` à `true`, sinon les résolutions ne sont jamais envoyées. Donnez à chaque réplica d’un même cluster Alertmanager la même valeur `--web.external-url` : l’URL externe fait partie de la clé de déduplication, ainsi les groupes de même nom provenant d’Alertmanagers de plusieurs régions avec le même routage ne sont pas fusionnés en un seul incident.

### Grafana

1. Dans Grafana, ouvrez **Alertes → Points de contact** et cliquez sur **Ajouter un point de contact**.
2. Définissez **Intégration** sur **Webhook** et **URL** sur l’adresse de réception.
3. Sous **Paramètres de webhook facultatifs**, définissez **Schéma d’en-tête d’authentification** sur `Bearer` et **Informations d’identification de l’en-tête d’authentification** sur le jeton.
4. Laissez **Désactiver le message de résolution** décoché, enregistrez, puis utilisez le point de contact dans une politique de notification.

Avec le provisionnement par fichier :

```yaml
apiVersion: 1
contactPoints:
  - orgId: 1
    name: molesignal
    receivers:
      - uid: molesignal
        type: webhook
        settings:
          url: https://<molesignal-host>/api/v1/intake/alerts
          httpMethod: POST
          authorization_scheme: Bearer
          authorization_credentials: <token>
```

### Datadog

1. Dans Datadog, ouvrez **Intégrations → Webhooks** et ajoutez un webhook, nommé par exemple `molesignal`.
2. Définissez **URL** sur l’adresse de réception et **En-têtes personnalisés** sur `{"Authorization": "Bearer <token>"}`. Laissez **Encoder comme formulaire** décoché.
3. Définissez **Charge utile** sur le modèle ci-dessous. Les noms de champs sont ceux de MoleSignal et les valeurs sont des variables Datadog ; une requête sans ce modèle est refusée.

```json
{
  "alert_id": "$ALERT_ID",
  "alert_cycle_key": "$ALERT_CYCLE_KEY",
  "transition": "$ALERT_TRANSITION",
  "alert_type": "$ALERT_TYPE",
  "priority": "$ALERT_PRIORITY",
  "title": "$ALERT_TITLE",
  "event_title": "$EVENT_TITLE",
  "message": "$TEXT_ONLY_MSG",
  "scope": "$ALERT_SCOPE",
  "tags": "$TAGS",
  "hostname": "$HOSTNAME",
  "link": "$LINK",
  "snapshot": "$SNAPSHOT",
  "query": "$ALERT_QUERY",
  "org_id": "$ORG_ID",
  "last_updated": "$LAST_UPDATED"
}
```

4. Mentionnez `@webhook-molesignal` dans le message de notification d’un monitor.

Chaque site Datadog (`datadoghq.com`, `datadoghq.eu`, `us3`, `us5`, `ap1` et les autres) peut envoyer vers une même source : le site est déduit du domaine de `$LINK` et fait partie de la clé de déduplication, avec l’ID de l’organisation.

### PagerDuty

1. Dans PagerDuty, ouvrez **Intégrations → Webhooks génériques (v3)** et cliquez sur **Nouveau webhook**.
2. Définissez **URL du webhook** sur l’adresse de réception et choisissez le **Type de périmètre** (le compte, un service ou une équipe).
3. Sous **Abonnement aux événements**, sélectionnez `incident.triggered`, `incident.acknowledged`, `incident.resolved`, `incident.reopened` et `incident.priority_updated`.
4. Ajoutez l’en-tête personnalisé `Authorization` avec la valeur `Bearer <token>`.

Les comptes des régions de service États-Unis et UE peuvent envoyer vers une même source : le domaine du compte (`<subdomain>.pagerduty.com` ou `<subdomain>.eu.pagerduty.com`) fait partie de la clé de déduplication et est écrit dans l’étiquette `pagerduty.region`.

### Alibaba Cloud CloudMonitor

Ajoutez le jeton à l’adresse de réception :

```text
https://<molesignal-host>/api/v1/intake/alerts?token=<token>
```

- **Alarmes de seuil** : saisissez cette adresse comme **callback d’alarme** d’une règle d’alarme. CloudMonitor envoie le callback encodé en formulaire via POST ; MoleSignal lit aussi le JSON.
- **Événements système** : sous **Centre d’événements → Abonnement aux événements → Canaux de diffusion**, créez un canal avec le type de cible **Webhook**, la méthode de requête **POST** et le format de données **JSON**, saisissez cette adresse, puis utilisez le canal dans une politique d’abonnement.

CloudMonitor attend 5 secondes pour un callback d’événement système et réessaie 3 fois. MoleSignal attend au plus 3 secondes lorsqu’il transmet une requête au [cluster de réception](#plusieurs-clusters), et répond `503` en cas de délai d’attente pour que CloudMonitor réessaie. Les sites Chine et international et toutes les régions envoient le même format ; la région est écrite dans l’étiquette `aliyun.region`, et le `userId` du compte fait partie de la clé de déduplication.

### Tencent Cloud Observability Platform

Dans Tencent Cloud Observability Platform (anciennement Cloud Monitor), modifiez ou créez un modèle sous **Gestion des alarmes → Modèles de notification**, saisissez l’adresse de réception comme **callback API**, puis associez le modèle à vos politiques d’alarme. Le callback de Tencent Cloud ne peut pas définir d’en-têtes, le jeton se trouve donc dans l’adresse. Conservez l’adresse comme un identifiant : le callback ne porte aucune signature, et c’est l’adresse qui identifie la source. Les alarmes de métrique et d’événement fonctionnent toutes deux, et les déclenchements comme les résolutions sont poussés.

- **Déduplication** : un même compte, une même politique d’alarme, un même nom de métrique ou d’événement et un même objet forment une seule alerte. Une politique à niveaux a un incident par niveau, chacun se résout de son côté, comme dans Tencent Cloud.
- **Gravité** : `alarmLevel` Serious (`Serious`) correspond à critique, Severe (`Warn`) à erreur et Reminder (`Remind`) à information. Une politique sans niveaux prend la gravité par défaut de la source.
- **Événements sans état** (`alarmStatus` vaut `5`) ouvrent un incident sans résolution à attendre, qu’une personne doit donc résoudre.
- **Heures** : le callback ne porte pas de fuseau horaire et les heures sont lues comme heure de Pékin.

### Amazon CloudWatch

Les alarmes CloudWatch n’appellent pas elles-mêmes d’adresses externes ; elles passent par SNS :

1. Dans les notifications de l’alarme, envoyez à la même rubrique SNS le passage en **En alarme** (`ALARM`) et le retour à **OK**. Sans `OK`, les incidents ne se résolvent pas d’eux-mêmes. Pour les alertes sans données, envoyez aussi **Données insuffisantes** (`INSUFFICIENT_DATA`).
2. Ajoutez un abonnement HTTPS à la rubrique avec l’adresse de réception comme point de terminaison, le jeton dans l’adresse :

   ```bash
   aws sns subscribe \
     --topic-arn <ARN of the topic> \
     --protocol https \
     --notification-endpoint 'https://<molesignal-host>/api/v1/intake/alerts?token=<token>'
   ```

3. L’abonnement se confirme lui-même : MoleSignal vérifie la signature du message de confirmation, puis visite son `SubscribeURL`.

MoleSignal vérifie la signature de chaque message SNS, donc **Livraison des messages bruts** doit rester désactivée. Si elle est activée, les messages sont refusés, et la section Reçus récemment de la page de la source en indique la raison. Le certificat de signature provient de `sns.<region>.amazonaws.com`, donc le nœud qui reçoit la requête doit pouvoir joindre cette adresse.

Les alarmes CloudWatch n’ont pas de gravité, les incidents prennent donc la gravité par défaut de la source. L’ARN de l’alarme est la clé de déduplication, y compris pour les alarmes composites. La description de l’alarme et la raison du changement d’état vont dans les annotations ; la région, le compte, l’espace de noms, la métrique et les dimensions vont dans les étiquettes, une étiquette comme `aws.region` peut donc piloter le routage.

### Azure Monitor

Les alertes Azure Monitor atteignent MoleSignal via l’action webhook d’un groupe d’actions :

1. Dans le groupe d’actions utilisé par vos règles d’alerte, ajoutez une action de type **Webhook** avec l’adresse de réception comme URI, le jeton dans l’adresse.
2. Définissez **Activer le schéma d’alerte commun** sur **Oui**. Sans cela, les requêtes sont refusées, et la section Reçus récemment de la page de la source en indique la raison.

La même chose avec Azure CLI :

```bash
az monitor action-group update \
  --resource-group <resource group> \
  --name <action group> \
  --add-action webhook molesignal 'https://<molesignal-host>/api/v1/intake/alerts?token=<token>' usecommonalertschema
```

- **Déduplication** : l’`alertId` de l’alerte est la clé de déduplication, et il contient l’abonnement Azure.
- **Déclenchement et résolution** : `monitorCondition` `Fired` ouvre l’incident et `Resolved` le résout. Les alertes qui ne conservent aucun état, comme les alertes de journal d’activité, ne font que se déclencher, et doivent donc être résolues par une personne.
- **Gravité** : `Sev0` correspond à critique, `Sev1` à erreur, `Sev2` à avertissement, et `Sev3` et `Sev4` à information.
- **Étiquettes** : les propriétés personnalisées de la règle d’alerte, les dimensions de la métrique, `azure.subscription_id`, `azure.resource_group`, `azure.resource`, `azure.signal_type`, `azure.monitoring_service` et `azure.metric`. La description, la condition, la valeur et les cibles vont dans les annotations, avec le lien d’investigation comme `azure_url`.

### Google Cloud Monitoring

1. Dans la console Google Cloud, ouvrez **Monitoring → Alertes → Modifier les canaux de notification**, et ajoutez un canal **Webhook** avec l’adresse de réception comme **URL du point de terminaison**, le jeton dans l’adresse.
2. Ajoutez le canal aux notifications de vos politiques d’alerte. Les incidents qui se ferment sont aussi envoyés, les incidents se résolvent donc d’eux-mêmes.

Le canal **Pub/Sub** publie la même notification. Pour l’utiliser, créez un abonnement push sur son sujet avec l’adresse de réception comme point de terminaison push ; MoleSignal désencapsule l’enveloppe Pub/Sub.

- **Déduplication** : le projet de portée et `incident_id`. Un incident Monitoring est un incident.
- **Déclenchement et résolution** : `state` `open` ouvre l’incident et `closed` le résout.
- **Gravité** : le niveau de gravité de la politique, `Critical`, `Error` ou `Warning`. Une politique sans niveau prend la gravité par défaut de la source.
- **Étiquettes** : les étiquettes de la ressource et de la métrique, les étiquettes utilisateur de la politique et de la ressource surveillée, `gcp.project_id`, `gcp.resource_type`, `gcp.metric` et `gcp.policy`. Le résumé, la condition, la valeur observée, le seuil et la documentation vont dans les annotations, avec l’adresse de la console de l’incident comme `gcp_url`.

### Huawei Cloud Eye

Les alarmes Cloud Eye (CES) n’appellent pas elles-mêmes d’adresses externes ; elles passent par SMN :

1. Dans Simple Message Notification, ajoutez un abonnement à un sujet avec le protocole **HTTPS** et l’adresse de réception comme point de terminaison, le jeton dans l’adresse.
2. L’abonnement se confirme lui-même : MoleSignal vérifie la signature du message de confirmation, puis visite son `subscribe_url`.
3. Dans les notifications d’alarme de vos règles d’alarme Cloud Eye, choisissez ce sujet, et notifiez à la fois l’alarme et sa résolution. Sans la résolution, les incidents ne se résolvent pas d’eux-mêmes.

MoleSignal vérifie la signature de chaque message SMN. Le certificat de signature provient de `smn.<region>.myhuaweicloud.com`, donc le nœud qui reçoit la requête doit pouvoir joindre cette adresse.

- **Déduplication** : le projet du sujet, l’`alarm_id` de la règle d’alarme et la ressource. Une règle sur plusieurs ressources ouvre un incident par ressource.
- **Déclenchement et résolution** : `alarm_status` `alarm` ouvre l’incident, `insufficient_data` l’ouvre comme absence de données, et `ok` le résout.
- **Gravité** : le niveau de l’alarme : Critical correspond à critique, Major à erreur, Minor à avertissement et Informational à information.
- **Étiquettes** : les dimensions, comme `instance_id`, et `huawei.region`, `huawei.project_id`, `huawei.namespace`, `huawei.metric`, `huawei.alarm_id` et `huawei.resource_id`. Le texte de l’alarme, la valeur actuelle et le seuil vont dans les annotations, avec l’adresse de la console de l’alarme comme `huawei_url`.

### Zabbix

Fonctionne à partir de Zabbix 6.0. Zabbix n’a pas de format de requête propre : le script d’un type de média envoie la requête. La page de la source, et la boîte de dialogue lors de sa création, fournissent donc un type de média avec l’adresse et le jeton déjà renseignés :

1. Enregistrez-le au format YAML et importez-le sous **Alertes → Types de média → Importer**. Vérifiez le paramètre `token`.
2. Définissez la macro globale `{$ZABBIX.URL}` sur l’adresse de l’interface Zabbix. Elle entre dans la clé de déduplication, ainsi une source peut accueillir plusieurs serveurs Zabbix, et les incidents renvoient vers Zabbix. Cela fonctionne aussi sans elle.
3. Attribuez ce média à un utilisateur. **Envoyer à** peut contenir n’importe quoi ; le script ne l’utilise pas.
4. Ajoutez une action de déclencheur dont les **opérations**, les **opérations de récupération** et les **opérations de mise à jour** vont toutes à cet utilisateur. Sans opérations de récupération, les incidents ne se résolvent pas d’eux-mêmes.

Le bouton **Tester** du type de média a besoin de valeurs réelles : lorsque les macros ne sont pas développées (`{EVENT.ID}` arrive tel quel), MoleSignal répond `400` et indique d’utiliser le type de média de la documentation.

### E-mail

Deux modes d’entrée existent, et les deux lisent les e-mails pour créer les mêmes alertes.

**Lire une boîte mail** (recommandé) : MoleSignal lit une boîte mail IMAP périodiquement. Il lui suffit d’un accès sortant et d’une boîte mail : aucune adresse publique, enregistrement MX, port 25 ni certificat, ce qui en fait le choix le plus simple en auto-hébergement. Envoyez les e-mails d’alerte de votre système de supervision à cette boîte mail, ou transférez-les vers cette boîte avec une règle de messagerie.

Sur la page de la source, sous **Lire une boîte mail**, renseignez **Serveur IMAP**, **Port**, **Chiffrement**, **Nom d’utilisateur**, **Mot de passe**, **Dossier** (`INBOX` par défaut) et **Lire toutes les** (15 à 3600 secondes, 60 par défaut). Cliquez sur **Tester la connexion**, puis sur **Enregistrer la boîte mail**.

- **Lecture seule** : elle utilise `EXAMINE` et `BODY.PEEK[]`, donc rien n’est marqué comme lu ou supprimé. Un compte en lecture seule suffit.
- **Pas de rattrapage** : à la première connexion, elle mémorise la position et ne lit que ce qui arrive ensuite. Un changement d’hôte, de compte ou de dossier, ou un serveur qui a reconstruit la boîte mail (`UIDVALIDITY` modifié), repart de ce moment. Tant que la source est désactivée, rien n’est lu et aucune position n’est conservée : elle repart du moment où elle est réactivée.
- **La liste des expéditeurs est obligatoire** : toute personne qui connaît l’adresse peut lui écrire. Sous **Expéditeurs autorisés** dans les paramètres de la source, saisissez des adresses ou `@example.com` pour tout un domaine ; `*` accepte tout le monde. La liste lit l’en-tête `From`, qui peut être falsifié, donc conservez le filtrage antispam et DMARC de votre fournisseur de messagerie activés. Les e-mails de toute autre personne sont enregistrés comme **Refusée** et n’ouvrent rien.
- **Connexion** : un mot de passe, ou un mot de passe d’application fourni par le fournisseur. Microsoft 365 n’accepte plus les mots de passe : choisissez **OAuth 2.0** et renseignez l’adresse du jeton `https://login.microsoftonline.com/<tenant>/oauth2/v2.0/token`, l’ID client, le secret client et l’étendue `https://outlook.office365.com/.default`. L’application a besoin de l’autorisation `IMAP.AccessAsApp` et de l’accès à cette boîte mail.
- **Aucun chiffrement** ne convient que sur un réseau de confiance : le mot de passe y circule en clair.
- Lorsqu’une lecture échoue, la page de la source en indique la raison, et la tentative suivante réessaie. Avec plusieurs nœuds d’alerte, chaque boîte mail est lue par un seul d’entre eux. Avec la fédération, la boîte mail est configurée sur le cluster de réception de la source et n’est pas synchronisée, le mot de passe reste donc sur ce cluster.

**Envoyer l’e-mail brut en POST** : si vous exploitez déjà un système de messagerie (le `pipe` de Postfix, SES, le MIME brut de Mailgun), envoyez le message brut en POST à l’adresse de réception :

```bash
curl -X POST 'https://<molesignal-host>/api/v1/intake/alerts' \
  -H 'Authorization: Bearer <token>' \
  -H 'Content-Type: message/rfc822' \
  --data-binary @alert.eml
```

Cela nécessite que l’adresse de réception soit joignable depuis ce système de messagerie. La liste des expéditeurs est facultative ici, puisque le jeton indique déjà qui appelle ; elle s’applique si vous en renseignez une.

MoleSignal n’a pas de récepteur SMTP intégré : cela exigerait un port 25 ouvert, un enregistrement MX, un certificat TLS et son propre filtrage antispam, ce que la plupart des déploiements auto-hébergés ne peuvent pas offrir.

Le **mode de lecture des e-mails** se définit sous **Mode de lecture des e-mails** dans les paramètres de la source :

| Paramètre | Description |
|---|---|
| **Objets signalant une résolution** | Une expression régulière. Vide reprend celle intégrée : `resolved`, `recovered`, `recovery`, `cleared`, `恢复`, `已解决`, et `OK` au début. Les autres e-mails déclenchent. |
| **Clé de déduplication extraite de l’objet** | Une expression régulière ; son premier groupe est repris, comme `host=(\S+)`. Vide ou sans correspondance utilise l’objet nettoyé : sans `Re:` et `Fwd:`, les mots d’état (`PROBLEM`, `RECOVERY`, `告警`, `恢复` et ainsi de suite), les gravités, les dates et heures, et les pourcentages, sans tenir compte de la casse. Ainsi « CRITICAL: disk full on web-1 (91%) » et « RECOVERY: disk full on web-1 (40%) » forment une seule alerte, tandis que `web-1` et `web-2` en font deux. Le domaine de l’expéditeur entre aussi dans la clé. |
| **Objets à ignorer** | Une expression régulière. Les e-mails qui correspondent sont ignorés et apparaissent sous Reçus récemment. |

La gravité provient des mots de l’objet (`critical`, `fatal`, `disaster`, `P1` sont critiques ; `error`, `P2` erreur ; `warning`, `P3` avertissement ; `info`, `notice`, `P4`, `P5` information), ou sinon de la valeur par défaut de la source ; les termes high et low de `High CPU` et `Low disk` ne comptent pas. Le corps va dans l’annotation `message` (e-mail HTML en texte, 4096 caractères au maximum), l’expéditeur dans l’étiquette `email.from` et l’annotation `from`, et l’heure provient de l’en-tête `Date`. Les réponses automatiques (`Auto-Submitted: auto-replied`) et les rebonds (`multipart/report`) ne sont pas des alertes. Les jeux de caractères GBK, GB2312 et autres sont pris en charge. Les e-mails de plus de 4 MiB sont enregistrés comme **Refusée** sans que leur corps soit lu.

## Comment les alertes deviennent des incidents

| Type | Clé de déduplication | Déclenchement | Résolution | Gravité |
|---|---|---|---|---|
| **API** | `dedupKey` | `trigger` | `resolve` | `severity` |
| **Alertmanager** | URL externe et `groupKey` | `status` du groupe `firing` | `status` du groupe `resolved` : toutes les alertes du groupe sont rétablies | Le label `severity` le plus élevé parmi les alertes du groupe en firing |
| **Grafana** | URL externe, organisation et `groupKey` | Idem | Idem | Idem |
| **Datadog** | Site, organisation, ID du monitor et scope | Toute transition sauf `Recovered` | `Recovered` | `$ALERT_PRIORITY` ; à défaut, Warn et No Data donnent un avertissement et le reste suit `$ALERT_TYPE` |
| **PagerDuty** | Domaine du compte et ID d'incident PagerDuty | `incident.triggered`, `incident.reopened` ; `incident.priority_updated` modifie la gravité | `incident.resolved` | Priorité P1 à P5 ; à défaut, l'urgence high correspond à une erreur et low à un avertissement |
| **Alibaba Cloud CloudMonitor** | Compte, ID de règle et `dimensions` ; pour les événements système, compte et `dedupId` | `ALERT`, `INSUFFICIENT_DATA` ; événement système `TRIGGERED` | `OK` ; événement système `RESOLVED` | `triggerLevel` ; événement système `severity` |
| **Tencent Cloud Observability Platform** | Compte, politique, nom de métrique ou d'événement, niveau et objet | `alarmStatus` vaut `1` ou `5` | `alarmStatus` vaut `0` | `alarmLevel` |
| **Amazon CloudWatch** | `AlarmArn` | `NewStateValue` vaut `ALARM` ou `INSUFFICIENT_DATA` | `NewStateValue` vaut `OK` | Aucune : la gravité par défaut de la source |
| **Azure Monitor** | `alertId` | `monitorCondition` vaut `Fired` | `monitorCondition` vaut `Resolved` | `severity` : `Sev0` critique, `Sev1` erreur, `Sev2` avertissement, `Sev3` et `Sev4` info |
| **Google Cloud Monitoring** | Projet de périmètre et `incident_id` | `state` vaut `open` | `state` vaut `closed` | `severity` ; `No severity` prend la valeur par défaut de la source |
| **Huawei Cloud Eye** | Projet du topic SMN, `alarm_id` et ressource | `alarm_status` vaut `alarm` ou `insufficient_data` | `alarm_status` vaut `ok` | Niveau d'alarme : Critical, Major, Minor, Informational |
| **Zabbix** | Hôte de `{$ZABBIX.URL}` et `{EVENT.ID}` | `{EVENT.VALUE}` vaut 1 ; les opérations de mise à jour aussi, la gravité suivant | `{EVENT.VALUE}` vaut 0, ou une opération de mise à jour a clos le problème | `{EVENT.NSEVERITY}` : Disaster correspond à critique, High à erreur, Average et Warning à avertissement, Information à info |
| **Adresse e-mail** | Le domaine de l'expéditeur et la partie extraite de l'objet | Un autre e-mail | Un objet rédigé comme un rétablissement | Les mots de l'objet |

La priorité et l'urgence sont lues séparément : la `priority` et l'`urgency` de l'API, `$ALERT_PRIORITY` de Datadog, ainsi que la priorité et l'urgence de PagerDuty deviennent la priorité et l'urgence de l'incident. Sans urgence, la politique d'escalade de la source décide, et une alerte qui ne signale aucune gravité est d'urgence high ; voir [Urgence](/fr/alerting/on-call#urgence).

Une alerte sans gravité prend la **Gravité par défaut** de la source. Les mots de gravité de chaque expéditeur sont insensibles à la casse : `critical`, `crit`, `fatal`, `page` et `P1` sont critiques ; `error`, `major`, `high` et `P2` sont des erreurs ; `warning`, `warn`, `minor`, `medium` et `P3` sont des avertissements ; `info`, `low`, `P4` et `P5` sont de niveau info. Tout autre mot prend la gravité par défaut.

- **Ouverture** : une source a au plus un incident actif par clé de déduplication. L'incident porte les labels `alert.source=external` et `external.kind=<kind>`, les labels propres à l'alerte (pour Alertmanager et Grafana, les `commonLabels` du groupe) et les labels supplémentaires de la source. Le label `service.name` ou `service` devient un service affecté, et `host.name`, `host` ou `hostname` devient un hôte.
- **Titre** : l'API utilise `summary` ; Alertmanager et Grafana utilisent l'annotation `summary`, ou `alertname` à défaut ; Datadog utilise `$ALERT_TITLE` ; PagerDuty utilise le titre de l'incident ; Alibaba Cloud CloudMonitor utilise « alarm name · instance name ».
- **Liens** : les adresses de retour vers l'expéditeur sont écrites dans des annotations, comme `alertmanager_url`, `generator_url`, `dashboard_url`, `datadog_url` et `pagerduty_url`, et la page de l'incident les affiche sous forme de liens. Les `links` de l'API sont écrits dans les annotations sous `name`.
- **Alertes d'un groupe** : un incident issu d'Alertmanager ou de Grafana conserve toutes les alertes du groupe (jusqu'à 100) avec leur statut, mis à jour à chaque notification. **Alerte externe** sur la page de l'incident les liste, avec les labels qui les distinguent.
- **Changements de gravité** : un incident qui n'est pas encore acquitté suit la gravité de l'alerte, telle que la décident les [pipelines d'alertes](/fr/pipelines/alert-events#changements-de-gravité). Lorsqu'elle augmente, l'escalade reprend depuis la première étape. Une gravité définie à la main reste inchangée.
- **Acquittement** : l'`acknowledge` de l'API, l'`incident.acknowledged` de PagerDuty et les opérations de mise à jour Zabbix qui acquittent un problème acquittent l'incident et arrêtent les étapes d'escalade et les appels suivants. Aucun utilisateur n'est enregistré comme auteur de l'acquittement.
- **Résolution** : l'incident se résout lorsque la source signale un rétablissement, incidents acquittés compris. Aucun utilisateur n'est enregistré comme auteur de la résolution, et la chronologie l'affiche comme rétabli.
- **Messages tardifs** : chaque clé de déduplication retient la dernière heure d'envoi qu'elle a utilisée, et un message plus ancien est ignoré. Un déclenchement tardif n'ouvre pas d'incident zombie, et un rétablissement tardif ne ferme pas un nouvel incident. L'API ne transporte pas d'heure, ses messages sont donc pris dans l'ordre d'arrivée.
- **Résolu d'abord par une personne** : lorsque la source signale encore l'alerte, son prochain renvoi ouvre un nouvel incident, comme pour les règles.
- **Aucune donnée** : les incidents ouverts par `INSUFFICIENT_DATA` de CloudMonitor, `insufficient_data` de Cloud Eye et No Data de Datadog portent `alert.condition=no_data`, et le titre de leurs notifications commence par `NO DATA`.
- **Désactivation et suppression** : une source désactivée refuse les alertes (`409`), et ses incidents ouverts restent. Supprimer une source fait cesser immédiatement le fonctionnement de son jeton et résout ses incidents ouverts.

Les [politiques de silence](/fr/alerting/silences), les [groupes sémantiques](/fr/alerting/silences#groupes-sémantiques) et les [politiques de notification](/fr/notification-channels) s'appliquent aux incidents externes comme à tous les autres. Faites la correspondance par `external.kind`, les labels supplémentaires d'une source ou les labels propres à l'alerte.

## Requêtes reçues récemment

Le haut de la page de la source indique l'état de la source : **En attente de la première requête**, **Reçoit des requêtes**, **Dernière requête refusée**, **Aucune requête depuis 7 jours** ou **Désactivée**. À côté figurent les requêtes et alertes des dernières 24 heures, ainsi que les incidents ouverts par la source qui sont encore ouverts.

Une fois que des requêtes sont arrivées, **Requêtes reçues récemment** sur la page de la source liste les requêtes reçues par la source : l'heure, le résultat (**Traitée**, **Refusée** ou **Transmise**), le statut HTTP, le nombre d'alertes et ce qu'elles sont devenues (**Ouverte**, **Dernière mise à jour**, **Inchangée**, **Acquitté**, **Résolu** ou **Ignoré**). Cliquez sur une ligne pour voir le titre, la gravité, l'action, le résultat et l'incident de chaque alerte ; une requête refusée affiche aussi la raison et le début de son corps (jusqu'à 16 KiB). Les 500 dernières requêtes de chaque source sont conservées, pendant 7 jours au maximum.

## Plusieurs clusters

Avec la [fédération inter-clusters](/fr/settings/data-plane#fédération-de-clusters) activée :

- Les sources se synchronisent entre les clusters comme le reste de la configuration d'alerte, jetons inclus : un même jeton fonctionne donc à l'adresse d'ingestion de chaque cluster.
- Les incidents d'une source ne s'ouvrent que sur son **Cluster de réception** : le cluster sur lequel elle a été créée, sauf modification dans les paramètres de la source. Un autre cluster qui reçoit une alerte de la source la transmet par gRPC au cluster de réception, puis renvoie la réponse du cluster de réception à l'expéditeur. Une alerte externe correspond donc à un seul incident, quelle que soit l'adresse du cluster par laquelle elle arrive.
- Lorsque le cluster de réception est injoignable, la réponse est `503` et l'expéditeur réessaie. Si la région du cluster de réception reste indisponible, remplacez le **Cluster de réception** dans les paramètres de la source par un cluster disponible.
- Les **Requêtes reçues récemment** sont enregistrées sur le cluster qui a traité la requête. La page de la source l'indique lorsqu'elle est ouverte sur un autre cluster.

## Limites

| Élément | Limite |
|---|---|
| Corps de la requête, un message | 4 MiB au maximum. |
| Lecture d'une boîte aux lettres | 50 messages au maximum à la fois ; les suivants au tour suivant. |
| Une requête API | 100 alertes ; `dedupKey` jusqu'à 255 caractères, `summary` jusqu'à 1024 caractères. |
| Une alerte | 64 labels et 64 annotations. L'API refuse au-delà ; pour les autres types de sources, le surplus est ignoré, et les titres et annotations trop longs sont tronqués. |
| Alertes d'un groupe | 100 sont conservées. |
| Labels supplémentaires d'une source | 32, sans clé commençant par `alert.` et sans `external.kind`. |
| Requêtes reçues récemment | Les 500 dernières requêtes de chaque source, sur 7 jours au maximum. |

La signature HMAC de Grafana et la signature de PagerDuty ne sont pas vérifiées ; le jeton identifie déjà la source. L'acquittement ou la résolution d'un incident dans MoleSignal n'est pas renvoyé à l'expéditeur.
