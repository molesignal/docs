Un connecteur de tickets synchronise les incidents avec Jira (Cloud ou Data Center / Server), ServiceNow ou Meegle (Feishu Project en
Chine). Créez un ticket pour un incident ou configurez une règle pour en créer un à chaque nouvel incident correspondant. Le ticket
suit ensuite l’incident : les prises en compte, les résolutions et les notes deviennent des commentaires, et la résolution de l’incident
marque le ticket comme terminé. MoleSignal récupère le statut du ticket toutes les 5 minutes. Jira peut aussi transmettre ce statut
immédiatement via un webhook.

Ouvrez **Alertes → Tickets**. La consultation nécessite `alerts.tickets.read`, la gestion des connecteurs nécessite `alerts.tickets.manage`,
et la création de tickets pour les incidents nécessite `alerts.incidents.tickets`.

## Connecter Jira

Sélectionnez **Nouveau connecteur de tickets**, puis **Jira** :

| Paramètre | Remarques |
|---|---|
| **Adresse du site** | Par exemple `https://example.atlassian.net`. |
| Déploiement | Pour **Jira Cloud**, utilisez l’**Adresse e-mail du compte** et un **Jeton d’API** (à créer sur la page de sécurité des paramètres du compte Atlassian). Pour **Jira Data Center / Server**, utilisez un **Jeton d’accès personnel**. |
| **Clé du projet**, **Type de ticket** | Par exemple `OPS` et `Incident`. |
| **Priorité du ticket selon celle de l’incident** | Indiquez un nom de priorité Jira pour chaque priorité d’incident de l’organisation (P1 à P5 par défaut), puis pour chaque niveau de gravité, par exemple `Highest` pour P1. Si l’incident n’a pas de priorité ou si la valeur correspondante est vide, le connecteur utilise la gravité. Si tous les champs sont vides, le connecteur ne définit aucune priorité. |
| **Étiquettes** | Étiquettes à ajouter aux tickets. Tous les tickets reçoivent aussi l’étiquette `molesignal`. |
| **Transition à la résolution** | Nom ou ID d’une transition. Si le champ est vide, le connecteur utilise la première transition vers un statut de fin. |
| **Secret du webhook** | Le webhook Jira nécessite un secret. Consultez [Synchronisation du statut](#synchronisation-du-statut). |

Le compte doit pouvoir créer des tickets, ajouter des commentaires et appliquer des transitions dans le projet. Après l’enregistrement, sélectionnez
**Tester la connexion**. Si le test réussit, MoleSignal affiche le compte utilisé pour la connexion.

## Connecter ServiceNow

Cliquez sur **Nouveau connecteur de tickets**, puis sélectionnez **ServiceNow**. Le connecteur utilise l’API Table : chaque ticket correspond à un enregistrement dans un tableau.

| Paramètre | Description |
|---|---|
| **Adresse de l’instance**, **Tableau** | Par exemple `https://example.service-now.com` et `incident`. Le tableau doit hériter de `task`. |
| Authentification | **Nom d’utilisateur et mot de passe** ; **Identifiants du client OAuth** (l’instance doit autoriser ce type d’octroi via la propriété `glide.oauth.inbound.client.credential.grant_type.enabled`) ; **Clé API** (disponible à partir de la version Washington DC, dans l’en-tête `x-sn-apikey`). Le compte doit pouvoir lire le tableau et y écrire. |
| **Groupe d’affectation**, **Demandeur**, **Catégorie** | Le connecteur renseigne ces champs à la création du ticket. Indiquez les identifiants `sys_id` du groupe et du demandeur. Si un champ est vide, le connecteur n’y définit aucune valeur. Pour les autres champs, utilisez `settings.fields` dans l’API. |
| **Priorité du ticket selon celle de l’incident** | ServiceNow calcule la priorité à partir de l’impact et de l’urgence. Saisissez les valeurs au format `impact/urgency`, par exemple `2/1`. Un seul nombre définit les deux valeurs. Le connecteur consulte d’abord la priorité de l’incident, puis sa gravité. Par défaut, les valeurs sont `1/1` pour Critique, `2/1` pour Erreur, `2/2` pour Avertissement et `3/3` pour Information. |
| **Valeur de l’état à la résolution**, **Code de résolution** | À la résolution de l’incident, le connecteur renseigne `state` et `close_code`, avec `6` et `Solution provided` par défaut. La stratégie de données par défaut exige un code et des notes de résolution. Les valeurs possibles de `close_code` varient selon l’instance. Les notes indiquent que la résolution a eu lieu dans MoleSignal, dans la langue par défaut de l’espace de travail. |
| **États considérés comme terminés** | Valeurs de `state` séparées par des virgules : `6, 7, 8` par défaut (Résolu, Fermé, Annulé). |

Le connecteur consigne les modifications de l’incident dans les notes internes `work_notes` pour ne pas déranger le demandeur. Le champ `correlation_id` contient l’ID de l’incident, et `correlation_display` contient `MoleSignal`. **Tester la connexion** effectue une lecture du tableau.

## Connecter Meegle

Sélectionnez **Nouveau connecteur de tickets**, puis **Meegle**. Créez d’abord un plugin dans la console développeur de Meegle
pour obtenir un ID et un secret de plugin. Installez ensuite le plugin dans l’espace de destination des tickets.

| Paramètre | Remarques |
|---|---|
| **Plateforme**, **Adresse du site** | **Feishu** (Feishu Project, `https://project.feishu.cn`) ou **Lark** (Meegle, `https://meegle.com`). L’adresse du site dépend de la plateforme. Copiez-la si nécessaire ; le champ n’est pas modifiable. |
| **ID du plugin**, **Secret du plugin** | Le connecteur échange ces valeurs contre un jeton de plugin. |
| **Agir au nom de (user_key)** | Le connecteur crée les tickets et publie les commentaires au nom du compte indiqué. |
| **Espace (project_key)**, **Type d’élément de travail (work_item_type_key)** | Indiquez le type d’élément de travail à créer et l’espace de destination. |
| **Clé du champ de priorité**, correspondance des priorités | Indiquez une valeur d’option de priorité pour chaque priorité d’incident de l’organisation, puis pour chaque niveau de gravité. Si l’incident n’a pas de priorité ou si la valeur correspondante est vide, le connecteur utilise la gravité. Si tous les champs sont vides, le connecteur ne définit aucune priorité. |
| **ID de la transition à la résolution** | Pour les éléments de travail dont le workflow repose sur des états. |
| **Nœud à marquer comme terminé à la résolution** | Pour les éléments de travail dont le workflow repose sur des nœuds. |
| **États considérés comme terminés** | Clés d’état séparées par des virgules. Un ticket dans l’un de ces états compte comme terminé. |

**Tester la connexion** lit le type d’élément de travail une fois. Le test réussit si les identifiants, l’espace et le type sont
valides.

## Suivi de l’incident

La section **Suivi de l’incident** du connecteur définit comment les tickets suivent l’incident :

| Paramètre | Effet |
|---|---|
| **Ajouter un commentaire à la prise en compte de l’incident**, **Ajouter un commentaire à la résolution de l’incident** | Ajoute un commentaire qui indique la prise en compte ou la résolution de l’incident dans MoleSignal. |
| **Publier les notes de l’incident sous forme de commentaires** | Les nouvelles [notes](/fr/alerting/incidents#notes) de l’incident deviennent des commentaires sur le ticket. |
| **Marquer le ticket comme terminé à la résolution de l’incident** | Ferme le ticket avec la transition définie ci-dessus. |
| **Résoudre l’incident lorsque le ticket est terminé** | Résout l’incident dès que le ticket est terminé, que l’incident soit ouvert ou pris en compte. Option inactive par défaut. |
| **Créer un ticket lorsqu’un incident majeur est déclaré** | Crée un ticket avec ce connecteur lors de la déclaration d’un [incident majeur](/fr/alerting/major-incidents). |

Le titre du ticket suit le format `[severity] incident summary`. Le corps indique la gravité et le statut de l’incident,
les services, les étiquettes, la requête à l’origine du déclenchement et le résumé de la cause racine établi par l’IA. Il contient aussi un lien vers la page de l’incident.
Le corps et les commentaires utilisent la langue par défaut de l’espace de travail.

## Création automatique de tickets

Activez **Créer automatiquement des tickets** pour que le connecteur crée un ticket pour tout nouvel incident dont la gravité atteint ou dépasse la **Gravité minimale** et dont le service
figure dans **Services**. Laissez **Services** vide pour inclure tous les services. Chaque connecteur crée
au plus un ticket par incident.

## Créer un ticket pour un incident

Dans les détails de l’incident, **Tickets** affiche la clé de chaque ticket (cliquez dessus pour l’ouvrir), son
statut, l’heure de la dernière synchronisation et les éventuelles erreurs de synchronisation ou de publication de commentaires. Sélectionnez **Créer un ticket**, ou
**Créer dans …** si plusieurs connecteurs sont disponibles. MoleSignal consigne la création du ticket dans la chronologie de l’incident et
dans le journal d’audit.

Créez aussi un ticket pour chaque action d’un [post-mortem](/fr/alerting/major-incidents#bilans-d’incident) si nécessaire. Ces tickets
ne reçoivent ni commentaires ni transitions de l’incident, et leur clôture ne résout pas l’incident.

## Synchronisation du statut

MoleSignal synchronise les tickets non terminés toutes les 5 minutes et consigne les changements de statut dans la chronologie de l’incident. Pour déterminer si un ticket est terminé, MoleSignal utilise la catégorie de statut dans Jira et les états définis dans le connecteur pour Meegle et ServiceNow.

Jira peut transmettre les changements immédiatement. Définissez un **Secret du webhook** dans le connecteur. La liste des connecteurs
affiche alors l’adresse du webhook Jira et le bouton **Copier l’adresse**. Dans **Paramètres système → Webhooks** de Jira, créez un
webhook avec cette URL et le même secret pour les mises à jour de tickets. MoleSignal vérifie `X-Hub-Signature` à l’aide du
secret et refuse les requêtes dont la signature ne correspond pas. L’adresse du webhook ne nécessite pas d’authentification. Consultez
[Accès public](/fr/public-access).
