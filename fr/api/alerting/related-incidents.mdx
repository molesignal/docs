Both calls require `alerts.incidents.read` on the incident.

## Incidents similaires

```http
GET /api/v1/alerts/incidents/{id}/similar
```

Recherche les incidents ouverts dans la même organisation au cours des 90 jours précédant le déclenchement de celui-ci qui
lui ressemblent le plus : au plus 5, score le plus élevé en premier, plus récent en premier en cas d'égalité. Les incidents fusionnés dans celui-ci et
l'incident dans lequel il est fusionné sont exclus. Le score est la somme des lignes ci-dessous, et un incident doit atteindre
au moins 2 pour être listé :

| Motif | Valeur dans `reasons` | Score |
|---|---|---|
| La même empreinte d'alerte | `fingerprint` | 5 |
| La même règle (lorsque l'empreinte diffère) | `rule` | 3 |
| Services partagés | `services` | chevauchement × 2 |
| Étiquettes similaires : les paires clé-valeur partagées représentent au moins 0,3 de toutes les paires des deux côtés | `labels` | proportion × 2 |
| Un titre similaire : similarité de trigrammes d'au moins 0,3, calculée comme le fait PostgreSQL `pg_trgm`, chinois inclus | `title` | similarité × 2 |
| Routé vers la même équipe | `team` | 1 |

Le chevauchement est l'intersection des deux côtés rapportée à leur union.

<RequestExample>
```bash cURL
curl http://localhost:5080/api/v1/alerts/incidents/$INCIDENT_ID/similar \
  -H "authorization: Bearer $MS_TOKEN"
```
</RequestExample>

<ResponseExample>
```json 200
{
  "incidents": [
    {
      "id": "3KEDNEyqouYJeBDTLTMTBui7XHW",
      "summary": "High error rate · checkout",
      "severity": "critical",
      "status": "resolved",
      "createdAt": 1789400000000000,
      "resolvedAt": 1789401800000000,
      "resolvedBy": "<user-id>",
      "score": 7.6,
      "reasons": ["fingerprint", "services", "labels", "team"],
      "notes": 2,
      "rootCause": "Connection pool exhausted after the payments client stopped releasing connections."
    }
  ]
}
```
</ResponseExample>

| Champ | Description |
|---|---|
| `score`, `reasons` | Le score et son origine ; voir le tableau ci-dessus. |
| `resolvedBy` | Qui l'a résolu ; `null` lorsque sa règle s'est rétablie d'elle-même ou qu'il est toujours actif. |
| `notes` | Combien de [notes](/fr/api/alerting/add-incident-note) il comporte. |
| `rootCause` | La première phrase qui apporte une information dans sa [cause racine par IA](/fr/api/alerting/incident-rca) (titres et lignes vides ignorés), au plus 200 caractères ; omis lorsqu'il n'a pas d'analyse. |

## Modifications récentes

```http
GET /api/v1/alerts/incidents/{id}/changes
```

Liste les [modifications signalées](/fr/apm/deployments#signaler-des-déploiements-depuis-la-ci) de 30
minutes avant le déclenchement de l'incident à 10 minutes après, pour les services de l'incident (ses services affectés
et son étiquette `service`) et les services en aval de ceux-ci : au plus 20, les plus anciennes en premier.
Les services en aval proviennent de la carte des services APM, pour au plus les 3 premiers services de l'incident ; sans
carte des services, seuls les services de l'incident comptent. Lorsque la règle de l'incident a été modifiée dans les 24 heures
précédant le déclenchement, une modification `rule` est également listée.

<RequestExample>
```bash cURL
curl http://localhost:5080/api/v1/alerts/incidents/$INCIDENT_ID/changes \
  -H "authorization: Bearer $MS_TOKEN"
```
</RequestExample>

<ResponseExample>
```json 200
{
  "from": 1789998200000000,
  "to": 1790000600000000,
  "changes": [
    {
      "kind": "deployment",
      "at": 1789999100000000,
      "service": "payments",
      "downstream": true,
      "version": "v2026.10.28",
      "status": "succeeded",
      "commit": "9f2c1e4",
      "author": "dana",
      "link": "https://ci.example.com/pipelines/4821"
    },
    {
      "kind": "rule",
      "at": 1789960000000000,
      "downstream": false,
      "ruleId": "3KEDBLvTYO6DnWi8H9S9MNLpPT7",
      "ruleName": "Checkout error rate"
    }
  ]
}
```
</ResponseExample>

| Champ | Description |
|---|---|
| `from`, `to` | La plage de temps examinée, en microsecondes Unix. |
| `kind` | `deployment`, `configuration`, `feature_flag`, ou `rule` (la règle de l'incident a été modifiée). |
| `downstream` | `true` lorsque la modification appartient à un service en aval, et non à l'un des services de l'incident. |
| `version`, `status`, `commit`, `description`, `author` | Ce que le rapport contenait ; omis lorsqu'il ne le contenait pas. |
| `link` | L'adresse du pipeline signalé, ou sinon l'adresse de la pull request. |
| `ruleId`, `ruleName` | La règle d'une modification `rule`. |

**Erreurs**

| Statut | Raison |
|---|---|
| `403` | Le token ne dispose pas de `alerts.incidents.read`, ou ne peut pas accéder à cet incident. |
| `404` | L'incident n'existe pas. |

## Impact métier

```http
GET /api/v1/alerts/incidents/{id}/business-impact
```

Pour chaque [clé métier](/fr/business-context) portée par les spans, liste les valeurs dont les requêtes vers les
services de l'incident ont le plus échoué, de 30 minutes avant le déclenchement de l'incident à 10 minutes après
(au plus tard maintenant) : au plus 5 valeurs par clé, les valeurs avec le plus de requêtes échouées en premier, puis celles avec le plus de requêtes. Un
incident sans services lit les requêtes de tous les services. Les requêtes sont les spans où un service a reçu
une requête.

<RequestExample>
```bash cURL
curl http://localhost:5080/api/v1/alerts/incidents/$INCIDENT_ID/business-impact \
  -H "authorization: Bearer $MS_TOKEN"
```
</RequestExample>

<ResponseExample>
```json 200
{
  "from": 1789998200000000,
  "to": 1790000600000000,
  "services": ["checkout"],
  "declared": true,
  "keys": [
    {
      "key": "tenant",
      "label": "Tenant",
      "field": "tenant.id",
      "more": true,
      "values": [
        { "value": "acme", "requests": 300, "errors": 120, "important": true },
        { "value": "globex", "requests": 90, "errors": 4, "important": false }
      ]
    }
  ]
}
```
</ResponseExample>

| Champ | Description |
|---|---|
| `services` | Les services de l'incident, dont les requêtes ont été lues. Vide lorsqu'il n'en nomme aucun. |
| `declared` | `false` lorsqu'aucune clé métier ne nomme un champ de span : `keys` est alors vide. |
| `field` | Le champ de span à partir duquel la clé a été lue. |
| `important` | La valeur fait partie de celles que l'organisation a marquées comme importantes pour la clé. |
| `more` | Davantage de valeurs ont eu des requêtes que celles listées. |

Une clé dont le flux de traces ne possède pas le champ ou le garde chiffré, ou dont aucune requête n'avait de valeur, est omise.

**Erreurs**

| Statut | Raison |
|---|---|
| `403` | Le token ne dispose pas de `alerts.incidents.read` ou ne peut pas accéder à cet incident, ou ne dispose ni de `streams.query` ni de `sys.telemetry.read`. |
| `404` | L'incident n'existe pas. |
