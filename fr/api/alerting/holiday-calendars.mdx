```http
GET    /api/v1/alerts/holiday-calendars
POST   /api/v1/alerts/holiday-calendars
GET    /api/v1/alerts/holiday-calendars/{id}
PUT    /api/v1/alerts/holiday-calendars/{id}

GET    /api/v1/alerts/holiday-calendars/{id}/references
POST   /api/v1/alerts/holiday-calendars/parse
```

La consultation requiert `alerts.calendars.read` ; la création, la modification, la suppression et la lecture d’un fichier requièrent `alerts.calendars.manage`.
Consultez [Calendriers des jours fériés](/fr/alerting/on-call#calendriers-des-jours-fériés) pour savoir comment ces calendriers s’appliquent aux plages horaires hebdomadaires.

## Créer ou modifier un calendrier

`POST` crée un calendrier et `PUT` en remplace un. La réponse contient le calendrier avec les champs `id`,
`orgId`, `createdBy`, `createdAt` et `updatedAt`.

| Champ | Type | Obligatoire | Description |
|---|---|---|---|
| `name` | chaîne | Oui | 80 caractères maximum. Le nom doit être unique dans l’organisation. |
| `description` | chaîne | Non | 500 caractères maximum. |
| `days` | tableau | Non | 2 000 jours maximum, chacun au format `{"date": "2026-10-01", "kind": "holiday", "name": "National Day"}`. `kind` vaut `holiday` (jour chômé) ou `workday` (jour travaillé de rattrapage, traité comme un lundi) ; `name` est limité à 80 caractères. Chaque date ne peut apparaître qu’une fois. |

<RequestExample>
```bash cURL
curl -X POST http://localhost:5080/api/v1/alerts/holiday-calendars \
  -H "authorization: Bearer $MS_TOKEN" \
  -H "content-type: application/json" \
  -d '{"name": "China 2026", "days": [{"date": "2026-10-01", "kind": "holiday", "name": "National Day"}, {"date": "2026-10-10", "kind": "workday", "name": "Make-up workday"}]}'
```
</RequestExample>

Pour utiliser un calendrier, indiquez son identifiant dans le champ `calendar` des plages horaires hebdomadaires :
`{"calendarId": "<id>", "holidays": "exclude"}` exclut les jours chômés, tandis que `"holidays": "only"`
applique les plages horaires uniquement aux jours chômés. Les plages horaires hebdomadaires acceptent ce paramètre dans les horaires d’assistance des
[politiques d’escalade](/fr/api/alerting/create-escalation), les conditions horaires des
[règles de routage](/fr/api/alerting/create-routing-rule) et des politiques de notification, les rotations des plannings
d’astreinte, les pipelines d’alertes et les périodes hebdomadaires de mise en sourdine. Toute tentative d’enregistrement avec un calendrier qui n’appartient pas à
l’organisation renvoie `400`.

## Lire un fichier ICS

`POST /parse` accepte `{"content": "<the .ics text>"}` dans la limite de 2 MiB et renvoie `{"days": [...]}` sans
rien enregistrer : chaque événement qui dure toute la journée ajoute un jour, un événement qui s’étend sur plusieurs jours ajoute chacun de ces jours,
et tout jour dont le nom contient 补班 ou 上班, ou se termine par 班, prend le type `workday`.

## Voir où un calendrier est utilisé

`GET /{id}/references` répertorie les éléments qui utilisent le calendrier, au format `{"kind", "id", "name"}` ; `kind` vaut
`routing_rule`, `escalationPolicy`, `schedule`, `mute_rule`, `notify_policy` ou `alert_pipeline`.
`DELETE` renvoie `409` tant que la liste n’est pas vide.

**Erreurs**

| Statut | Motif |
|---|---|
| `400` | Un champ ne respecte pas les limites, une date apparaît deux fois ou la lecture du fichier échoue. |
| `403` | Le jeton ne dispose pas de l’autorisation requise. |
| `404` | Ce calendrier n’existe pas dans l’organisation. |
| `409` | Un autre calendrier porte ce nom ou le calendrier est en cours d’utilisation. |
