```http
GET /api/v1/alerts/rules
GET /api/v1/alerts/rules/{id}
```

Le premier appel renvoie toutes les règles d’alerte de l’organisation sous forme de tableau. Le second renvoie une seule règle. Les deux appels nécessitent `alerts.rules.read`.

<RequestExample>
```bash cURL
curl http://localhost:5080/api/v1/alerts/rules \
  -H "authorization: Bearer $MS_TOKEN"
```
</RequestExample>

<ResponseExample>
```json 200
[
  {
    "id": "3KEDBLvTYO6DnWi8H9S9MNLpPT7",
    "orgId": "<organization-id>",
    "name": "High error rate",
    "description": "More than 100 errors in five minutes",
    "enabled": true,
    "kind": "scheduled",
    "query": {
      "language": "sql",
      "statement": "SELECT count(*) AS c FROM app WHERE level = 'error'",
```

Une règle contient les champs décrits dans [Créer une règle](/fr/api/alerting/create-rule), ainsi que les champs en lecture seule suivants :

| Champ | Remarques |
|---|---|
| `id`, `orgId` | Identifiants de la règle et de l’organisation. |
| `createdAt`, `updatedAt` | Microsecondes écoulées depuis l’époque Unix. |
| `lastEvalAt` | Horodatage de la dernière évaluation terminée, en microsecondes. La valeur reste à `null` jusqu’à la première évaluation terminée. Si la requête échoue ou dépasse le délai imparti, la valeur ne change pas. |
| `lastState` | Résultat de cette évaluation : `{"kind": "healthy"}` si la condition n’est pas remplie, `{"kind": "pending", "consecutive": 1}` si elle est remplie depuis moins de `forPeriods` évaluations consécutives, `{"kind": "firing"}` dès qu’elle l’est depuis suffisamment longtemps et `{"kind": "dropped"}` si l’alerte se déclenche, mais qu’un [pipeline d’alertes](/fr/pipelines/alert-events#devenir-d’un-événement) écarte l’incident que la règle aurait ouvert. Une règle à l’état `firing` n’ouvre aucun nouvel incident pendant le délai de temporisation `silenceSecs`. |

Si l’`id` est inconnu, l’appel renvoie `404`.
