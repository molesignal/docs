```http
POST /api/v1/_bulk
```

Ingestion NDJSON compatible avec l’API `_bulk` d’Elasticsearch pour Filebeat, Logstash et la destination `elasticsearch` de Vector. L’appel nécessite `logs.write`. Le point de terminaison accepte les corps de requête avec `Content-Encoding: gzip`.

| Action | Traitement |
|---|---|
| `index`, `create`, `update` | Le point de terminaison enregistre le document source comme événement de journal. |
| `delete` | Le point de terminaison ignore l’action sans renvoyer d’élément de réponse. Il ne supprime jamais de données de télémétrie. |

Le champ `_index` d’une action sélectionne le flux de journaux cible. À défaut, le point de terminaison utilise l’en-tête `stream-name` ou, si cet en-tête est absent, le flux `default`.

<RequestExample>
```bash cURL
curl -X POST http://localhost:5080/api/v1/_bulk \
  -H "authorization: Bearer $MS_TOKEN" \
  -H 'content-type: application/x-ndjson' \
  --data-binary $'{"index":{"_index":"app"}}\n{"level":"info","msg":"hello"}\n'
```
</RequestExample>

<ResponseExample>
```json 200
{ "took": 0, "errors": false, "items": [ { "index": { "status": 201 } } ] }
```
</ResponseExample>

## Choisir ce point de terminaison

Utilisez ce point de terminaison si un expéditeur existant peut envoyer du NDJSON au format de l’API `_bulk` d’Elasticsearch. Ce point de terminaison est un adaptateur d’ingestion, pas un cluster Elasticsearch : cette API ne gère ni la recherche, ni les modèles d’index, ni les identifiants de documents, ni les mises à jour sur place. Utilisez des [requêtes SQL](/fr/query) pour lire les événements enregistrés.

## Construire un lot valide

- Envoyez un objet d’action et un objet de document sur deux lignes distinctes pour chaque opération `index` ou `create`. Terminez le lot par un saut de ligne.
- Pour `update`, placez les champs de l’événement sous `doc`. Ces champs forment un nouvel événement au lieu de modifier un événement enregistré.
- Définissez `_index` dans l’action pour choisir un flux. Sinon, utilisez `stream-name` ou laissez le point de terminaison utiliser le flux `default`.
- Pour conserver l’heure de l’événement, indiquez dans `_timestamp` un horodatage Unix entier en microsecondes. Sinon, le récepteur utilise l’heure actuelle.
- Le point de terminaison ignore les actions `delete`. Ces actions ne suppriment aucune donnée de télémétrie et n’ajoutent aucun élément d’événement enregistré à la réponse.

## Vérifier l’ingestion

Pour un lot contenant un seul événement, vérifiez que la réponse contient `errors: false` et un seul élément avec `status: 201`. Comparez le nombre d’éléments renvoyés au nombre d’événements à ingérer. Un code de succès HTTP ne suffit pas à confirmer que le lot correspond à ce qui était prévu.

Ouvrez **Journaux**, sélectionnez le flux indiqué par `_index` et utilisez une plage temporelle qui inclut l’horodatage de l’événement. Lancez une requête sur un champ distinctif de l’exemple. Si l’événement n’apparaît pas, vérifiez le flux sélectionné et l’unité de l’horodatage avant de renvoyer le lot entier. Cette interface n’utilise pas les identifiants de documents Elasticsearch pour éviter les doublons lors des nouvelles tentatives.

## Diagnostiquer une requête rejetée

| Symptôme | Vérification |
|---|---|
| Erreur d’authentification ou d’autorisation | Utilisez un jeton d’API de l’organisation cible doté de l’autorisation `logs.write`. |
| L’action ou le document n’est pas un objet JSON | Vérifiez les sauts de ligne du NDJSON. N’envoyez ni tableau JSON ni objet mis en forme sur plusieurs lignes. |
| Action inconnue | Utilisez les noms d’action pris en charge indiqués ci-dessus. |
| Erreur de décompression | Définissez `Content-Encoding: gzip` uniquement si le corps de la requête est compressé. |
| Succès, mais moins d’événements que prévu | Vérifiez que chaque action d’écriture a sa ligne de document et distinguez les actions de suppression ignorées des événements enregistrés. |
