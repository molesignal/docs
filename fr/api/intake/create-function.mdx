```http
POST /api/v1/functions
```

Crée une transformation réutilisable dans les pipelines. À la création de la fonction, MoleSignal compile le code source VRL ou JavaScript et rejette la fonction si le code est invalide. Le binaire intègre les deux environnements d’exécution. Cet appel nécessite l’autorisation `functions.create`.

**Corps**

| Champ | Type | Obligatoire | Remarques |
|---|---|---|---|
| `name` | chaîne | Oui | Nom de la fonction. |
| `language` | chaîne | Oui | `vrl`, `js` ou `llm`. Une fonction `llm` nécessite l’activation de `[functions].llm_eval_enabled` et un fournisseur de modèles. |
| `source` | chaîne | Oui | Code source VRL ou JavaScript, ou instruction de la fonction `llm`. |
| `paramsSchema` | objet | Non | Paramètres. Pour `llm`, `outputField` définit le champ de sortie, qui est `_llm_eval` par défaut. |

<RequestExample>
```bash cURL
curl -X POST http://localhost:5080/api/v1/functions \
  -H "authorization: Bearer $MS_TOKEN" \
  -H 'content-type: application/json' \
  -d '{
    "name": "lowercase-level",
    "language": "vrl",
    "source": ".level = downcase!(string!(.level))"
  }'
```
</RequestExample>

En cas d’erreur de syntaxe, l’API renvoie `400`, par exemple `js syntax error: Uncaught SyntaxError: Unexpected token '}'`. Avant d’enregistrer la fonction, testez le code source avec `POST /api/v1/functions/run`. Cet appel prend `language`, `source` et un exemple d’entrée `input`, puis renvoie `output`. Consultez [Fonctions](/fr/functions).

Autres routes de l’API des fonctions : `GET /api/v1/functions`, ainsi que `GET`, `PUT` et `DELETE` sur `/api/v1/functions/{id}`. Les fonctions prédéfinies intégrées sont en lecture seule.

## Tester la transformation avant de l’enregistrer

Le point de terminaison de simulation nécessite l’autorisation `functions.run`, distincte de `functions.create`. Testez la transformation avec des données d’entrée représentatives, notamment des événements aux champs manquants ou mal formés, avant de l’appliquer à des données entrantes en production.

```bash
curl -X POST http://localhost:5080/api/v1/functions/run \
  -H "authorization: Bearer $MS_TOKEN" \
  -H 'content-type: application/json' \
  -d '{"language":"vrl","source":".level = downcase!(string!(.level))","input":{"level":"ERROR","message":"example"}}'
```

Pour cette entrée, vérifiez que `output.level` vaut `error`, que la transformation conserve le champ `message`, qui n’est pas concerné, et que `dropped` vaut `false`. Une compilation réussie ne garantit pas que tous les événements en production respectent les conditions attendues par la transformation. Par exemple, la conversion en chaîne ci-dessus peut échouer si `level` n’est pas une chaîne.

## Ajouter la fonction à un pipeline

La création d’une fonction enregistre une définition réutilisable sans transformer automatiquement les événements entrants. Notez l’identifiant de fonction renvoyé, ajoutez l’étape qui exécute la fonction depuis [Pipelines](/fr/pipelines), puis testez le pipeline complet avant de l’activer sur un flux en production.

Conservez un exemple d’entrée représentatif et la sortie attendue avec la modification. Après avoir activé le pipeline, ingérez un événement de test et interrogez le flux de destination pour vérifier les champs stockés. Le résultat d’une simulation ne suffit pas à valider le parcours d’ingestion en production.

## Problèmes courants

| Symptôme | Action |
|---|---|
| Nom de fonction vide | Renseignez `name` avec une valeur non vide. |
| Rejet du code source à la création | Corrigez les erreurs de syntaxe ou de compilation avant de réessayer. |
| Simulation refusée | Vérifiez l’autorisation `functions.run` : elle est distincte de l’autorisation de création. |
| Erreur à l’exécution avec certaines entrées | Dans une simulation, reproduisez la structure du champ qui provoque l’erreur et gérez les champs absents ou dont le type diffère du type attendu. |
| Aucun effet de la fonction enregistrée sur les nouveaux logs | Vérifiez que le pipeline inclut la fonction et que le flux de destination est correct. |
