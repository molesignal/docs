```http
POST /api/v1/_kinesis_firehose
```

Ce point de terminaison accepte les envois d’AWS Data Firehose par HTTP. Il n’utilise pas de jeton Bearer. Créez un connecteur de type `aws_kinesis_firehose` avec un `pushToken` d’au moins 16 caractères et un `target_stream`, puis indiquez ce jeton à Firehose comme clé d’accès. Le point de terminaison lit le jeton dans `X-Amz-Firehose-Access-Key` et accepte aussi `X-Connector-Token` et `?token=`. Si le jeton est incorrect, le point de terminaison renvoie `401`.

Chaque enregistrement contient un champ `data` encodé en base64. Le point de terminaison décode son contenu, le découpe en lignes et convertit chaque ligne non vide en événement de journal dans `target_stream` (`kinesis` par défaut). Une ligne contenant un objet JSON est convertie en champs, tandis qu’une ligne de texte brut devient le champ `message`.

<RequestExample>
```bash cURL
curl -X POST http://localhost:5080/api/v1/_kinesis_firehose \
  -H 'X-Amz-Firehose-Access-Key: <pushToken>' \
  -H 'content-type: application/json' \
  -d '{"requestId":"req-1","timestamp":1790000000000,"records":[{"data":"eyJsZXZlbCI6ImluZm8ifQo="}]}'
```
</RequestExample>

<ResponseExample>
```json 200
{ "requestId": "req-1", "timestamp": 1790000000123 }
```
</ResponseExample>

La réponse reprend `requestId` et contient un `timestamp` en millisecondes, comme l’exige Firehose. Consultez la page [Connecteurs](/fr/connectors) pour configurer le connecteur.

## Vérifier la livraison et la sélection du flux

1. Vérifiez que le connecteur est activé et que l’expéditeur utilise le jeton d’envoi du connecteur. Un jeton d’API standard ne remplace pas un jeton d’envoi.
2. Si vous définissez la valeur brute de `configJson` via l’API des connecteurs, utilisez `target_stream` pour le flux de destination, et non `targetStream`. La clé du jeton reste `pushToken`, en casse camel.
3. Envoyez un événement de test avec un marqueur unique et notez l’heure de réception. Dans **Journaux**, sélectionnez le flux voulu et une plage horaire qui inclut l’heure de réception, puis recherchez le marqueur.
4. Si la requête aboutit mais que le flux voulu est vide, vérifiez le flux par défaut correspondant et la valeur enregistrée dans le champ de destination. Un accusé de réception HTTP ne remplace pas une requête sur le flux de destination prévu.

Protégez le jeton comme un secret d’authentification. Si le jeton figure dans un paramètre de requête de l’URL, ne consignez pas l’URL complète dans les journaux et ne l’incluez pas dans les tickets ni les captures d’écran. Avant de relancer une requête qui a échoué, distinguez les problèmes liés au jeton ou à l’état du connecteur des erreurs de format ou de compression de la charge utile.
