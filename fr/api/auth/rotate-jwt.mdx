Les deux routes exigent une session à portée système avec l’autorisation `sys.signing_keys.rotate`. Une session à portée d’organisation ou un jeton d’API reçoit une réponse `403`. Basculez la session vers l’organisation `_sys` avec [Sélectionner un espace de travail](/fr/api/auth/select-organization).

## Lister les clés de signature

```http
GET /api/v1/auth/jwt/secrets
```

Renvoie les métadonnées des clés de signature. La route ne renvoie jamais les octets bruts des clés.

<ResponseExample>
```json 200
[
  {
    "id": "3JtcPZ3AZJFyvBvSkJUia0N7wqo",
    "isPrimary": true,
    "createdAt": 1790000000000000,
    "retiredAt": null
  }
]
```
</ResponseExample>

## Effectuer une rotation

```http
POST /api/v1/auth/jwt/rotate
```

Crée une nouvelle clé principale et retire l’ancienne. La route signe les nouveaux jetons avec la nouvelle clé. Les jetons signés avec une clé retirée restent valides pendant 24 heures après son retrait.

Aucun nœud ne nécessite de redémarrage. Chaque nœud accepte dès la première requête les sessions signées avec la nouvelle clé et commence à signer avec cette clé au bout d’environ 10 secondes. Les nœuds cessent d’utiliser la clé retirée pour vérifier les signatures 5 minutes après la fin des 24 heures. Cette marge couvre le délai de transition et les écarts d’horloge entre les nœuds.

<ResponseExample>
```json 200
{
  "newKid": "<new-key-id>",
  "retiredKid": "<previous-key-id>",
  "activeCount": 2
}
```
</ResponseExample>

`activeCount` indique le nombre de clés actuellement utilisées pour vérifier les jetons. Un déploiement qui fixe la clé de signature avec `MS_AUTH_JWT_SECRET_OVERRIDE` suit sa propre politique de rotation. Consultez [Sécurité et architecture multilocataire](/fr/security#clés-de-signature-jwt).
