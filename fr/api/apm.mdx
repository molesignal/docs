The APM API exposes organization-scoped aggregates derived from trace spans. All endpoints use the
`/api/v1/apm` prefix and require a bearer token.

```http
Authorization: Bearer <token>
```

An organization workspace requires the read permission of the area: `apm.services.read`, `apm.errors.read`,
`apm.error_rules.read`, `apm.definitions.read`, `apm.slos.read`, `apm.deployments.read`, or `apm.settings.read`. A platform caller can use
`sys.telemetry.read` in the protected `_sys` scope. Each call that writes names what it requires. Reporting a deployment requires
`apm.deploy`.

## Points de terminaison

| Méthode et chemin | Réponse |
|---|---|
| `GET /api/v1/apm/overview` | Synthèse et tendance RED de tous les services, santé des services et sa tendance, classements, déploiements, environnements, lacunes d'instrumentation, principales transactions, dépendances et erreurs. |
| `GET /api/v1/apm/insights` | Ce qui a changé par rapport à la période précédente et à la même période une semaine plus tôt, les versions qui ont fait moins bien, où du temps peut être regagné et les changements à proximité de chacun. |
| `GET /api/v1/apm/services` | Catalogue paginé des services avec instrumentation, versions, santé, métriques RED et filtres de trace. |
| `GET /api/v1/apm/services/{service}` | Synthèse du service, tendance, transactions, dépendances, erreurs et versions. |
| `GET /api/v1/apm/services/{service}/instances` | Les instances d'un service dans un environnement, avec leur version, leurs attributs de ressource et ce que chacune a servi. |
| `GET /api/v1/apm/services/{service}/coverage` | Si les logs, métriques, profils et sessions navigateur du service parviennent à MoleSignal, sur la journée précédant `to`. |
| `GET /api/v1/apm/correlation` | Dans quelle mesure chaque service affiché est relié à ses logs, métriques, traces et changements, ainsi que les noms de services présents dans les logs et les métriques qu'APM ne connaît pas. |
| `GET /api/v1/apm/transactions` | Métriques RED paginées des transactions et classement par temps total. |
| `GET /api/v1/apm/transactions/{transaction}` | Tendance de la transaction, erreurs affectées, versions et filtres de trace. |
| `GET /api/v1/apm/dependencies` | Métriques RED paginées appelant/dépendance et classement par temps total. |
| `GET /api/v1/apm/map` | La carte des services d'un environnement et d'un namespace : services, ce qu'ils appellent, topics et appels entre eux. |
| `GET /api/v1/apm/map/edge` | Un appel de la carte : sa tendance, ce qui a été demandé le long de cet appel et les erreurs d'un service appelé. |
| `GET /api/v1/apm/blast-radius` | Ce qu'un service atteint sur la carte : ce qui l'appelle et ce qu'il appelle, saut par saut. |
| `GET /api/v1/apm/errors` | Groupes d'erreurs backend assainis et paginés, avec les lieux où les groupes listés se sont produits. |
| `GET /api/v1/apm/errors/{fingerprint}` | Tendance de l'erreur, transactions et versions affectées, lieux où le groupe s'est produit, pile représentative et échantillons bornés. |
| `GET /api/v1/apm/versions/compare` | Métriques RED de référence et candidates, écarts, statut de suffisance et régressions. |
| `GET /api/v1/apm/health` | Statut de projection du tenant, santé d'exécution, limites et lacunes. |
| `GET /api/v1/apm/service-definitions` | Toutes les définitions de service de l'organisation. |
| `PUT /api/v1/apm/service-definitions/{service}?namespace=` | Crée ou remplace la définition d'un service. Exige `apm.definitions.manage`. |
| `DELETE /api/v1/apm/service-definitions/{service}?namespace=` | Supprime la définition d'un service. Exige `apm.definitions.manage`. |
| `POST /api/v1/apm/service-definitions/{service}/key-transactions?namespace=` | Marque un point de terminaison comme transaction clé du service, ou retire cette marque. Exige `apm.definitions.manage`. |
| `PUT /api/v1/apm/errors/{fingerprint}/issue` | Définit l'état, l'équipe et le responsable d'un groupe d'erreurs. Exige `apm.errors.manage`. |
| `GET /api/v1/apm/error-rules` | Les règles de regroupement d'erreurs de l'organisation, dans l'ordre où elles sont essayées. |
| `POST /api/v1/apm/error-rules` | Crée une règle de regroupement, essayée après les autres. Exige `apm.error_rules.manage`. |
| `PUT /api/v1/apm/error-rules/{id}` | Remplace une règle de regroupement. Exige `apm.error_rules.manage`. |
| `DELETE /api/v1/apm/error-rules/{id}` | Supprime une règle de regroupement. Exige `apm.error_rules.manage`. |
| `PUT /api/v1/apm/error-rules/order` | Définit l'ordre dans lequel les règles sont essayées. Exige `apm.error_rules.manage`. |
| `GET /api/v1/apm/slos` | Chaque objectif de niveau de service avec son état, ce qu'il a atteint, le budget d'erreur restant et les taux de consommation. |
| `GET /api/v1/apm/slos/{id}` | Le statut d'un objectif de niveau de service et chaque jour de sa fenêtre. |
| `POST /api/v1/apm/slos` | Crée un objectif de niveau de service. Exige `apm.slos.manage`. |
| `PUT /api/v1/apm/slos/{id}` | Remplace un objectif de niveau de service. Exige `apm.slos.manage`. |
| `DELETE /api/v1/apm/slos/{id}` | Supprime un objectif de niveau de service. Exige `apm.slos.delete`. |
| `POST /api/v1/apm/deployments` | Signale un déploiement. Exige `apm.deploy`. |
| `GET /api/v1/apm/settings` | Les paramètres APM de l'organisation, ou les valeurs par défaut si aucun n'a été enregistré. |
| `PUT /api/v1/apm/settings` | Remplace les paramètres APM de l'organisation. Exige `apm.settings.manage`. |

Les paramètres de chemin doivent être encodés en URL. Utilisez le nom `transaction` exact ou le `fingerprint` d'erreur
renvoyé par une réponse de liste.

## Paramètres de requête communs

| Paramètre | Type | Comportement |
|---|---|---|
| `from` | integer | Début de la plage en microsecondes depuis l'époque Unix. Par défaut, 24 heures avant `to`. |
| `to` | integer | Fin de la plage en microsecondes depuis l'époque Unix. Par défaut, l'heure actuelle. |
| `namespace` | string | Filtre exact sur le namespace de service. |
| `service` | string | Filtre exact sur le nom de service. Le chemin de détail du service remplace cette valeur. |
| `environment` | string | Filtre exact sur l'environnement de déploiement. |
| `version` | string | Filtre exact sur la version du service. |
| `resolution` | enum | `auto`, `minute` ou `hour`. `auto` sélectionne la résolution conservée pour la plage. |
| `sort` | string | Champ de tri propre au point de terminaison. |
| `direction` | enum | `asc` ou `desc`. Par défaut, `desc`. |
| `limit` | integer | Taille de page de 1 à 200. Par défaut, 50. |
| `cursor` | string | Curseur opaque issu d'une réponse de liste précédente. |
| `status` | enum | `/errors` uniquement : `all` (par défaut), `unresolved` (groupes ouverts, en investigation et résolus revus), `investigating`, `resolved` ou `ignored`. |

Les filtres doivent être non vides et ne pas dépasser 192 octets. La plage ne peut pas dépasser le maximum
configuré, qui vaut 30 jours par défaut (`[apm].max_query_range_days`).

### Champs de tri

| Point de terminaison | Valeurs `sort` prises en charge | Par défaut |
|---|---|---|
| `/services` | `requestCount`, `errorRate`, `p95`, `name` | `requestCount` |
| `/transactions` | `requestCount`, `errorRate`, `p95`, `total_time` | `requestCount` |
| `/dependencies` | `requestCount`, `errorRate`, `p95`, `total_time` | `total_time` |
| `/errors` | `occurrenceCount`, `errorRate`, `lastSeen` | `occurrenceCount` |

`/overview` accepte les mêmes filtres et la même résolution, mais ne pagine pas. Les points de terminaison de détail, de comparaison et
de santé ne renvoient pas de listes paginées.

## Interroger une vue d'ensemble

<RequestExample>
```bash cURL
NOW=$(date +%s)000000
curl --get 'http://localhost:5080/api/v1/apm/overview' \
  --header "Authorization: Bearer $MS_TOKEN" \
  --data-urlencode "from=$((NOW-86400000000))" \
  --data-urlencode "to=$NOW" \
  --data-urlencode 'environment=production' \
  --data-urlencode 'resolution=auto'
```
</RequestExample>

La réponse contient `red`, `trend`, `serviceHealth`, `services`, `topTransactions`,
`topDependencies`, `topErrors` et `recentVersions`, ainsi qu'un objet `meta` commun, et :

| Champ | Remarques |
|---|---|
| `serviceCount`, `activeServiceCount` | Services vus sur la période, et ceux d'entre eux qui ont servi au moins une requête. |
| `healthTrend` | Combien de services étaient dans chaque état, créneau par créneau : la période en 48 créneaux au maximum, aucun plus court qu'un bucket. Un service sans requête dans un créneau y compte comme `noTraffic`. |
| `rankings` | `slowest` (par p95), `mostErrors` (par taux d'erreur) et `busiest` (par requêtes), cinq services chacun. Les deux premiers listent les services ayant au moins 20 requêtes. |
| `deployments` | Versions vues pour la première fois sur la période, de la plus récente à la plus ancienne, 20 au maximum, chacune avec son `red` et son `verdict` comme dans [les versions d'un service](#lire-les-versions-d’un-service). |
| `environments`, `availableEnvironments` | Services et requêtes par environnement dans la vue, et tous les environnements dans lesquels les services tournent, quel que soit le filtre `environment`. |
| `instrumentation` | Services par langage et par SDK, et combien ne rapportent ni `deployment.environment`, ni `service.version`, ni `service.instance.id`. |

## Consulter les insights

`GET /api/v1/apm/insights` prend les paramètres communs de période et de filtre et renvoie `meta` et :

| Champ | Remarques |
|---|---|
| `now`, `previous`, `lastWeek` | Les services dans la vue sur la période, sur la période de même longueur qui précède et sur la même période une semaine plus tôt : `requestCount`, `throughput` en requêtes par seconde, `errorRate`, `p95Time` et `apdex`. Une période sans requête est absente. |
| `insights` | 30 constats au maximum, les plus urgents en premier. |

Chaque constat porte :

| Champ | Remarques |
|---|---|
| `kind` | `anomaly`, `regression`, `slow_dependency`, `repeated_call`, `slowQuery`, `hot_endpoint` ou `log_errors`. |
| `severity` | `critical`, `warning` ou `info` pour une suggestion. |
| `service` | `namespace`, `name` et `environment`. |
| `transaction`, `dependency` | L'endpoint concerné, pour un endpoint chaud ; la dépendance concernée, pour un goulot d'étranglement, un appel répété ou une instruction lente. |
| `metric` | Ce qui a bougé ou s'est dégradé : `errorRate`, `p95` ou `throughput`. |
| `value` | La valeur actuelle : un taux d'erreur sous forme de ratio, un P95 en microsecondes ou des requêtes par seconde. Un goulot d'étranglement ou un endpoint chaud donne sa part du temps, un appel répété son nombre d'appels par requête, une instruction lente son P95 en microsecondes, et `log_errors` ses lignes de log de niveau erreur par minute, avec `metric` `log_errors`. |
| `previous`, `lastWeek` | La même valeur sur la période précédente et sur la même période une semaine plus tôt ; pour une régression, la valeur de la version précédente. |
| `since` | Quand un changement a commencé, ou quand une version régressée a été vue pour la première fois. |
| `version`, `previousVersion` | La version d'une régression et la version qui la précède. |
| `calls`, `p95Time` | Les appels ou requêtes sur lesquels repose une suggestion, et leur P95. |
| `changes` | Les changements proches de `since`, les plus proches en premier : `kind`, `source` (`reported` ou `observed`), `service`, `version`, `status`, `at`, `downstream` (`true` pour un service appelé par celui qui change), `commit` et `description`. |

Les seuils sont décrits dans [Insights et investigations](/fr/apm/insights#what-insights-find).

## Lire les métriques RED

Chaque résumé porte un objet `red` avec les chiffres de requêtes, d'erreurs et de durée de la période.

| Champ | Remarques |
|---|---|
| `requestCount`, `errorCount`, `errorRate` | Requêtes, requêtes en échec, et le ratio des requêtes en échec sur le total des requêtes, de 0 à 1. |
| `durationSum`, `durationAverage` | La durée totale et la durée moyenne en microsecondes. La moyenne vaut `null` sans requête. |
| `p50Time`, `p90Time`, `p95Time`, `p99Time` | Percentiles de latence en microsecondes, lus dans le bucket d'histogramme où tombe le rang. Avec la disposition par défaut, une valeur est à environ 4 % près de la durée exacte. `null` sans requête. |
| `apdex` | Requêtes sous le seuil T plus la moitié des requêtes sous 4T, rapportées à toutes les requêtes, de 0 à 1. T est l'`apdexThreshold` du service, sinon 500 ms ; les chiffres de la vue d'ensemble pour tous les services réunis utilisent 500 ms. Les requêtes en échec ne sont jamais satisfaites. `null` sans requête. |
| `latencyPartial` | `true` quand certains buckets utilisent une disposition de latence impossible à déduire à partir d'eux. Les buckets d'une disposition antérieure (`[apm.histogram].schema_version`) sont convertis et comptés. Les percentiles excluent les buckets illisibles, tandis que les comptages, la somme et la moyenne les incluent toujours. |
| `timeoutCount`, `retryCount` | Requêtes arrivées à expiration (un type d'erreur de timeout, gRPC `DEADLINE_EXCEEDED`, HTTP 408 ou 504) et requêtes renvoyées (`http.request.resend_count` supérieur à 0). Absent quand il n'y en a pas. |
| `statusCodes` | Réponses par code de statut, sous la forme `http:<code>` (100 à 599) ou `grpc:<code>` (0 à 16). Un bucket conserve jusqu'à 24 codes ; les codes suivants comptent comme `http:other` ou `grpc:other`. Absent quand aucun code n'a été compté, par exemple pour des agrégats écrits avant que les codes ne soient comptés. |
| `exemplars` | Jusqu'à 8 spans échantillons de la période, les plus lents en premier. Un span est projeté avant que le [tail sampling](/fr/configuration#capture-des-traces-et-échantillonnage-en-fin-de-trace) ne décide du sort de sa trace, donc `traceAvailable` est généralement `false` ; recherchez la trace pour savoir si elle a été conservée. L'agrégat reste valide. |

Les résumés de service et de transaction portent `apdexThreshold`, le T avec lequel leur Apdex a été calculé.
Un résumé de service porte aussi `health` et `healthReasons` : chaque valeur au-delà d'une ligne, sous la forme `metric`
(`errorRate` ou `p95`), `level`, `value` et `threshold`. Il porte `sparkline`, le nombre de requêtes, le nombre d'erreurs et le p95 de chaque bucket,
ainsi que `currentVersion` avec `currentVersionSince`, la version vue le plus récemment et quand elle a été
vue pour la première fois. Le détail d'un service ou d'une transaction porte `latencyDistribution` : l'histogramme
des buckets qui contiennent des requêtes, chacun sous la forme `lowerTime`, `upperTime` et `count`, resserré sur la
requête la plus rapide et la plus lente.

## Conserver les définitions de service

Une définition indique qui possède un service et quelle est son importance. Elle est indexée par `namespace` et par le
nom du service : elle vaut donc dans tous les environnements et peut exister avant que le service ne remonte des données.

```http
PUT /api/v1/apm/service-definitions/checkout?namespace=shop
Content-Type: application/json

{"description": "Takes orders and payments.", "teamId": "<team id>", "ownerId": "<user id>", "tier": "p0", "lifecycle": "production", "repositoryUrl": "https://github.com/acme/checkout", "tags": {"domain": "orders", "pci": ""}, "apdexThreshold": 300000, "aliases": ["order_service", "Order Center"], "dataSources": {"logs": [{"stream": "default", "filter": "service_name = 'order_service'"}], "metrics": [{"selector": "{service=\"checkout\"}"}], "dashboards": ["<dashboard id>"], "links": [{"name": "Runbook", "url": "https://wiki.example.com/checkout"}]}, "archived": false}
```

| Champ | Remarques |
|---|---|
| `description` | Jusqu'à 2 000 caractères. |
| `teamId` | Une équipe de l'organisation, ou `null`. La suppression de l'équipe le remet à `null`. |
| `ownerId` | Un membre de l'organisation, ou `null`. |
| `tier` | `p0`, le plus important, jusqu'à `p5`, ou `null`. |
| `lifecycle` | `production`, `staging`, `experimental`, `deprecated`, ou `null`. |
| `repositoryUrl` | Une URL `http`, `https`, `ssh`, `git` ou `git+ssh`, ou `user@host:path`, sans espaces, jusqu'à 2 048 caractères, ou `null`. Un mot de passe est enregistré comme `****`, tout comme la partie utilisateur d'une adresse http(s). Affiché quand le service ne remonte aucun dépôt. |
| `tags` | Jusqu'à 32 tags sous la forme `{ "key": "value" }`. Une clé fait 1 à 64 lettres minuscules, chiffres et `_ . - /` ; une valeur fait jusqu'à 128 caractères sans espaces autour, vide pour une clé seule. |
| `apdexThreshold` | Le seuil T de l'Apdex du service, supérieur à 0 et au plus 60 000 000 (une minute), ou `null` pour 500 ms. |
| `aliases` | Jusqu'à 20 autres noms sous lesquels le service apparaît dans les logs, les métriques et d'autres systèmes, chacun de 1 à 128 caractères sans espaces autour. La casse est ignorée : aucun nom en double, jamais le nom du service lui-même, et jamais le nom ou un autre nom d'un autre service de l'organisation. Omis, une définition enregistrée conserve ses noms. |
| `dataSources` | Où se trouvent les données du service : `logs` (`stream` et un `filter` facultatif, une expression SQL booléenne jusqu'à 2 000 caractères), `metrics` (`selector`, un sélecteur PromQL tel que `{service="checkout"}`), `dashboards` (ID de tableaux de bord) et `links` (`name` et une `url` `http` ou `https`), jusqu'à 10 de chaque. Omis, une définition enregistrée conserve ses sources. |
| `archived` | `true` exclut le service de la vue par défaut du catalogue. Omis, une définition enregistrée conserve son état. |

Un enregistrement conserve les `keyTransactions` de la définition, qui changent une à une. La réponse est la
définition enregistrée avec `namespace`, `name`, `keyTransactions`, `updatedBy` et `updatedAt`.
`DELETE` répond `204`, ou `404` quand le service n'a pas de définition.

### Marquer des transactions clés

```http
POST /api/v1/apm/service-definitions/checkout/key-transactions?namespace=shop
Content-Type: application/json

{"transaction": {"name": "POST /orders", "kind": "http"}, "key": true}
```

`key: true` ajoute le point de terminaison à `keyTransactions`, `false` le retire ; demander ce qui est déjà
le cas ne change rien. Un service sans définition en reçoit une. Un service conserve jusqu'à 50
transactions clés, et la ligne de débordement `__other__` ne peut pas en faire partie. La réponse est la définition après
la modification.

## Vérifier la corrélation des services avec les autres données

`GET /api/v1/apm/correlation` prend les paramètres de plage et de filtre courants (`from`, `to`,
`namespace`, `environment`, `service`) et indique, pour chaque service affiché, dans quelle mesure il est corrélé à ses
logs, métriques, traces et changements. Les services sont lus sur la plage, les logs et les métriques sur la dernière
heure avant `to`, et les changements sur la semaine avant `to`. Seuls des comptages et des noms sont lus dans les
flux, jamais les lignes. Chaque rapport est conservé cinq minutes.

```json
{
  "from": 1792312896695000,
  "to": 1792316496695000,
  "changesSince": 1791711696695000,
  "services": [
    {
      "service": { "namespace": "shop", "name": "checkout", "environment": "prod" },
      "logs": { "state": "reported", "streams": ["default"], "lines": 1200, "traced": 480, "sampled": 10, "matched": 9 },
      "metrics": "missing",
      "resource": { "environment": true, "version": true, "instance": true, "placement": false },
      "changes": { "count": 3, "lastAt": 1792312896695000 },
      "grades": { "traceIds": "partial", "resource": "partial", "metrics": "missing", "changes": "good" }
    }
  ],
  "unmatched": [{ "name": "checkout-svc", "signal": "logs", "streams": ["default"], "lines": 640 }]
}
```

| Champ | Signification |
|---|---|
| `logs` | Les lignes du service dans les flux de logs ayant un champ `service.name`, `service_name` ou `service`, au plus huit flux, `default` en premier. `traced` compte les lignes portant un `trace_id`, `traceId` ou `trace.id`. Jusqu'à dix ID de trace récents du service, 200 au total, sont recherchés parmi les traces : `sampled` et `matched`. |
| `metrics` | Indique si un flux de métriques contient une série portant le `service.name` du service. |
| `resource` | Indique si les spans remontent un environnement, une version et une instance, et si une instance remonte `host.name`, `k8s.pod.name`, `k8s.node.name` ou `container.id` (`placement`). |
| `changes` | Les déploiements, changements de configuration et feature flags remontés pour le service depuis `changesSince`. |
| `unmatched` | Jusqu'à 20 noms de service présents dans les logs ou les métriques auxquels aucun service APM ne correspond, règles de nommage et alias appliqués, ceux qui ont le plus de lignes en premier. |

Chaque note est `good`, `partial`, `missing` ou `unknown` :

| Note | `good` | `partial` | `missing` |
|---|---|---|---|
| `traceIds` | Au moins 90 % des lignes portent un ID de trace, et au moins 80 % de celles échantillonnées sont retrouvées. | Certaines lignes en portent un. | Aucune ligne n'en porte, ou le service n'a écrit aucune ligne. |
| `resource` | Les quatre éléments de `resource` sont vrais. | Certains le sont. | Aucun ne l'est. |
| `metrics` | Les métriques portent le nom. | | Aucune ne le porte. |
| `changes` | Au moins un changement. | | Aucun. |

`unknown` signifie qu'une recherche a échoué ou a pris plus de trois secondes ; un nom introuvable alors qu'un flux n'a pas pu
être lu est `unknown`, jamais `missing`. Mole Agent lit le même rapport avec
`get_correlation_quality`.

## Lire la couverture d'un service

`GET /api/v1/apm/services/{service}/coverage` prend `namespace` et `environment`, tous deux obligatoires, et
facultativement `to`, la fin de la plage affichée en microsecondes (maintenant par défaut). Il examine la journée
précédant `to` et conserve chaque réponse cinq minutes.

```json
{
  "from": 1792230096695000,
  "to": 1792316496695000,
  "logs": { "state": "reported", "found": ["default"] },
  "metrics": { "state": "missing" },
  "profiles": { "state": "reported", "found": ["cpu", "alloc_space"] },
  "rum": { "state": "unknown" }
}
```

| Signal | `reported` lorsque | `found` |
|---|---|---|
| `logs` | Un flux de logs ayant un champ `service.name`, `service_name` ou `service` contient une ligne du service. Au plus huit flux sont examinés, `default` en premier. | Les flux. |
| `metrics` | `count(last_over_time({"service.name"="<service>"}[1h]))` à `to` est supérieur à zéro. | Le nombre de séries. |
| `profiles` | Le flux de profils contient un profil du service. | Les types de profil. |
| `rum` | Une action de navigateur portait l'une des cinq traces échantillons les plus récentes du service. | La session. |

`missing` signifie que la recherche n'a rien trouvé. `unknown` signifie que la recherche a échoué ou a pris plus de trois
secondes. `rum` n'est jamais `missing` : un échantillon de traces peut montrer que des sessions atteignent un service, pas qu'aucune
ne le fait.

## Lire ce sur quoi tourne un service

`GET /api/v1/apm/services` et `GET /api/v1/apm/services/{service}` ajoutent à chaque résumé de service un
`profile`, lu à partir des instances ayant remonté des données dans la plage, celles de `version` seule quand le
paramètre est défini. Chaque liste est classée par nombre d'instances partageant une valeur, au plus cinq, sous la forme
`{ "value": "1.8.2", "instances": 4 }`.

| Champ | Remarques |
|---|---|
| `instanceCount`, `hostCount` | Instances et valeurs `host.name` distinctes. |
| `versions` | Les versions exécutées par les instances. Un déploiement progressif en liste deux. |
| `languages`, `runtimes`, `frameworks` | `telemetry.sdk.language` ; `process.runtime.name` avec sa version ; le framework nommé par la bibliothèque d'instrumentation des spans d'entrée. |
| `regions`, `clusters`, `k8sNamespaces`, `workloads` | `cloud.region`, `k8s.cluster.name`, `k8s.namespace.name` et `k8s.deployment.name` ou `k8s.statefulset.name`. |
| `repositories`, `commits` | `vcs.repository.url.full` ou `git.repository_url`, conservés sans identifiants ; `vcs.ref.head.revision` ou `git.commit.sha`. |
| `entryKinds` | `http`, `rpc`, `messaging`, `span` : les types d'entrée servis par le service. |

`GET /api/v1/apm/services/{service}/instances` liste les instances une à une, les plus récemment
vues en premier, au plus 500. Il prend `namespace`, `environment` et, facultativement, `version`, `from` et
`to` ; sans service ni environnement, il répond `400`. Chaque élément a `instanceId` (le
`service.instance.id`, sinon `k8s.pod.name`, sinon `host.name`), `version`, `firstSeenAt`,
`lastSeenAt`, `attributes`, une table des attributs remontés en dernier par l'instance, et ce qu'elle a servi
dans la plage : `red`, comme dans les résumés avec l'Apdex au seuil du service, et `sparkline`. Au-delà de la
limite d'instances, le reste est compté dans un élément dont l'`instanceId` est `__other__`. Une instance qui
a servi dans la plage avant que quoi que ce soit ne soit conservé à son sujet est listée avec des `attributes` vides.

## Définir l'état d'un groupe d'erreurs

```http
PUT /api/v1/apm/errors/<fingerprint>/issue
Content-Type: application/json

{"status": "investigating", "assigneeId": "<user id>", "teamId": "<team id>", "lastSeenAt": 1792316496695000}
```

`status` vaut `open`, `investigating`, `resolved` ou `ignored`. `assigneeId` est un membre de l'organisation ou `null`, et `teamId` une équipe de l'organisation ou `null`. `lastSeenAt`, facultatif, est la date à laquelle le lecteur a vu le groupe pour la dernière fois, en microsecondes. Définir `resolved` enregistre l'heure sous `resolvedAt`.

Les résumés d'erreurs portent l'état sous `issue`, ou `null` tant que personne ne l'a défini. `issue.regressed` vaut `true` lorsqu'un groupe résolu s'est reproduit après `resolvedAt` ; le filtre `unresolved` conserve ces groupes. Définir l'état d'une empreinte que la projection ne connaît pas renvoie `404`.

## Gérer les objectifs de niveau de service

Un objectif de niveau de service (SLO) promet une part de requêtes réussies d'un service dans un environnement, ou de l'un de ses points de terminaison, sur une fenêtre glissante. Voir
[Objectifs de niveau de service](/fr/apm#objectifs-de-niveau-de-service) pour la signification de chaque chiffre.

```http
POST /api/v1/apm/slos
Content-Type: application/json

{"name": "Checkout availability", "namespace": "shop", "service": "checkout", "environment": "production", "transaction": null, "kind": "availability", "objective": 0.999, "windowDays": 30}
```

| Champ | Remarques |
|---|---|
| `name` | Obligatoire, jusqu'à 255 octets. |
| `description` | Facultatif, jusqu'à 2 000 octets. |
| `namespace`, `service`, `environment` | Obligatoires. Le service tel qu'APM le nomme. Un service sans `service.namespace` se trouve dans l'espace de noms `default`. |
| `transaction` | Un point de terminaison, `{ "name": "POST /orders", "kind": "http" }`, ou `null` pour tout le service. |
| `kind` | `availability` : une requête est réussie lorsqu'elle n'a pas échoué. `latency` : une requête est réussie lorsqu'elle n'a pas échoué et a pris au plus `latencyThreshold`. |
| `latencyThreshold` | Obligatoire et positif pour `latency`. Doit être `null` ou absent pour `availability`. |
| `objective` | La part de requêtes réussies, supérieure à 0 et inférieure à 1, par exemple `0.999`. |
| `windowDays` | `7`, `28` ou `30`. |

`POST` et `PUT` renvoient le SLO enregistré avec `id`, `createdBy`, `createdAt`, `updatedBy` et
`updatedAt`. `GET /api/v1/apm/slos` renvoie chaque SLO de l'organisation sous forme de statut. Passer
`namespace`, `service` et `environment` ensemble pour conserver les SLO d'un seul service. La fenêtre se termine
au moment de l'appel, donc les paramètres de plage habituels ne s'appliquent pas.

| Champ du statut | Remarques |
|---|---|
| `slo` | Le SLO tel qu'enregistré. |
| `state` | `healthy`, `at_risk`, `breached` ou `noData`. |
| `sli` | Les requêtes réussies sur toutes les requêtes de la fenêtre, ou `null` sans requêtes. |
| `goodRequests`, `totalRequests` | Les décomptes derrière `sli`. Un SLO de latence estime `goodRequests` à partir des histogrammes de latence, il peut donc être fractionnaire. |
| `budgetRemaining` | `1 - (1 - sli) / (1 - objective)`, inférieur à zéro une fois l'objectif non tenu, ou `null` sans requêtes. |
| `burnRates` | `oneHour`, `sixHours` et `oneDay` : `(1 - sli) / (1 - objective)` sur la dernière heure, les six dernières heures et les 24 dernières heures, ou `null` sans requêtes. |

`GET /api/v1/apm/slos/{id}` renvoie `status` et `history`, une entrée pour chaque jour UTC de la fenêtre
comportant des requêtes, de la plus ancienne à la plus récente. Chaque entrée contient `dayStart` en microsecondes, `sli`, `goodRequests`
et `totalRequests`.

`DELETE` renvoie `204`. Il renvoie `409` tant que des règles d'alerte surveillent le SLO, comme ses alertes
de taux de consommation : supprimer d'abord ces règles. Les règles d'alerte sur un SLO sont des règles APM avec la métrique
`slo_burn_rate`. Voir [Créer une règle](/fr/api/alerting/create-rule#règles-apm).

## Lever l'ambiguïté d'une transaction

Deux types de transaction peuvent partager un nom. Passer le paramètre facultatif `kind` pour en sélectionner un :

```http
GET /api/v1/apm/transactions/POST%20%2Fcheckout?kind=http&service=checkout
```

Les valeurs de type prises en charge sont `http`, `rpc`, `messaging`, `span` et `other`. Un nom partagé par plusieurs
services ou types renvoie `400` avec `APM transaction identity is ambiguous; provide service,
namespace, environment, and kind`.

## Comparer des versions

Fournir des valeurs `baseline` et `candidate` différentes. Ajouter un filtre `service` pour comparer un seul service.

```bash
curl --get 'http://localhost:5080/api/v1/apm/versions/compare' \
  --header "Authorization: Bearer $MS_TOKEN" \
  --data-urlencode 'service=checkout' \
  --data-urlencode 'environment=production' \
  --data-urlencode 'baseline=2.3.1' \
  --data-urlencode 'candidate=2.4.0'
```

La réponse contient les côtés `baseline` et `candidate`, chacun avec `version`, `sampleCount` et
`red`, plus un `delta`, un `status`, `regressedTransactions` et `regressedErrors`. Chaque liste
de régressions contient au plus 20 entrées.

| Champ | Remarques |
|---|---|
| `sufficientData` | `true` uniquement lorsque les deux versions atteignent le seuil d'échantillons configuré, qui vaut par défaut 1 000 requêtes par version (`[apm.version_comparison].min_requests_per_version`). |
| `status` | `insufficient_data`, `regressed`, `improved` ou `neutral`. `regressed` lorsque le taux d'erreur du candidat a augmenté d'au moins un point et atteint au moins 1,5 fois celui de la référence, ou que son p95 a augmenté d'au moins un cinquième et de 50 ms ; `improved` lorsque l'un des deux a baissé d'autant et qu'aucun n'a augmenté d'autant ; `insufficient_data` lorsque `sufficientData` vaut `false`. |
| `delta` | `requestCountAbsolute` et `requestCountRelative`, `errorRateAbsolute` et `errorRateRelative`, et `p95AbsoluteTime` et `p95Relative`. Une valeur relative vaut `null` lorsque la référence est nulle ou absente. |

Un `candidate` ou un `baseline` absent, ou deux versions identiques, renvoie `400`.

## Lire les versions d'un service

`GET /api/v1/apm/services/{service}` renvoie `versions`, les versions vues dans la plage. Chacune porte
`red`, ce qu'elle a servi dans la plage, et `verdict`, son comportement par rapport à la version du même service
vue pour la première fois avant elle, jugé comme l'est [une comparaison](#comparer-des-versions) :

| Champ | Remarques |
|---|---|
| `previous` | La version à laquelle elle est comparée. |
| `status` | `regressed`, `improved`, `neutral` ou `insufficient_data`. |
| `worse` | Ce qui s'est dégradé lorsque `status` vaut `regressed` : `errorRate`, `latency` ou les deux. |
| `delta` | Comme dans une comparaison, la version antérieure servant de référence. |

La première version vue n'a pas de `verdict`. Un filtre de version sur la requête ne réduit pas les
chiffres : chaque version est lue sur tout le service.

## Lire où les erreurs se sont produites

`GET /api/v1/apm/errors` renvoie un `breakdown` à côté de la page, sur tous les groupes que le filtre `status`
conserve (pas seulement ceux de la page), et `GET /api/v1/apm/errors/{fingerprint}` renvoie le `breakdown` du
groupe. Il contient `versions`, `environments` et `languages`, chacun une liste de `value` et `count`,
les occurrences, de la plus grande à la plus petite. Une valeur est vide lorsque les spans ne l'ont pas rapportée ; au-delà des sept
premières valeurs, le reste est compté ensemble sous `__other__`. La langue est le `telemetry.sdk.language` du service.

## Gérer les règles de regroupement des erreurs

Une règle regroupe les erreurs autrement que par leur type, leur cadre et leur point de terminaison au moment où elles sont vues. Les règles sont
essayées dans l'ordre de `position` et la première qui correspond s'applique.

```http
POST /api/v1/apm/error-rules
Content-Type: application/json

{"name": "Upstream timeouts", "serviceNamespace": "shop", "serviceName": "checkout",
 "errorType": "*Timeout*", "message": "", "frame": "", "endpoint": "", "action": "merge", "enabled": true}
```

| Champ | Remarques |
|---|---|
| `name` | Jusqu'à 128 caractères. Un groupe fusionné porte ce nom. |
| `serviceNamespace`, `serviceName` | Le service visé par la règle. Un `serviceName` vide signifie tous les services ; un espace de noms nécessite un nom. |
| `errorType`, `message`, `frame`, `endpoint` | Motifs pour le type d'erreur, le message de l'exception, le premier cadre applicatif et le point de terminaison, chacun jusqu'à 256 caractères. Un motif correspond au texte entier, sans tenir compte de la casse, avec `*` pour n'importe quel texte. Un motif vide correspond à tout ; au moins un doit être défini. |
| `action` | `merge` : les erreurs correspondantes d'un service forment un seul groupe. `ignore` : elles ne forment aucun groupe, et leurs requêtes restent comptées comme échouées. |
| `enabled` | Une règle désactivée est conservée mais n'est pas essayée. Vaut `true` par défaut. |

La réponse est la règle avec son `id`, sa `position`, `updatedBy` et `updatedAt`. Une organisation
conserve au plus 100 règles. `PUT /api/v1/apm/error-rules/order` prend `{"ids": [...]}`, place ces règles
en premier dans cet ordre et les autres ensuite, et renvoie les règles dans leur nouvel ordre.

Une modification s'applique immédiatement sur le nœud qui l'enregistre et sous 30 secondes sur les autres, aux
erreurs vues à partir de ce moment ; les groupes déjà constitués restent tels quels.

## Lire la carte des services

`GET /api/v1/apm/map` accepte les paramètres communs de plage, `environment` et `namespace`, et renvoie
`nodes`, `edges`, `namespaces` (des services de l'environnement), `environments` (tous) et
`truncated` (`true` lorsque seuls les 400 nœuds les plus sollicités sont conservés).

| Champ | Remarques |
|---|---|
| `nodes[].id` | `service:<name>`, `topic:<name>` ou `<category>:<target>` pour ce que les services appellent. |
| `nodes[].kind` | `service`, `external` ou `topic`. Un nœud externe porte sa `category`. |
| `nodes[].red` | `requestCount`, `errorCount`, `errorRate` et `p95Time` : ce qu'un service a servi, ou ce qui a été demandé à un nœud externe ou à un topic. Un service porte aussi `health`, `namespace` et `environments`. |
| `edges[].kind` | `call`, `publish` (vers un topic) ou `consume` (depuis un topic). |
| `change` | Sur une arête ou un nœud, par rapport à la période de même durée juste avant : `new` quand il n'était pas là, `gone` quand il ne l'est plus. Absent quand il n'y avait rien auparavant. |

Les appels entre services proviennent du graphe de services, avec le P95 de leur minute la plus lente ; le reste
provient des buckets APM. `GET /api/v1/apm/map/edge` accepte les ids de nœuds `source` et `target` en plus des mêmes
paramètres et renvoie `kind`, `red`, `trend`, `operations` (`name`, `kind`, `red`), `everyCaller`
(`true` lorsque les opérations sont les points de terminaison du service appelé, tous appelants confondus) et `errors`, les
groupes d'erreurs du service appelé.

## Lire le rayon d'impact d'un service

`GET /api/v1/apm/blast-radius` accepte `service`, obligatoire, ainsi que les paramètres communs de plage et
`environment`. Il lit toute la carte de l'environnement, quel que soit le namespace, et
renvoie `meta`, `service` (le nœud du service lui-même, absent lorsque la carte ne le situe nulle part sur la plage),
`upstream` (ce qui l'appelle, jusqu'à trois sauts) et `downstream` (ce qu'il appelle ou vers quoi il publie, jusqu'à deux
sauts). Chaque côté contient au plus 30 nœuds, les nœuds en mauvaise santé en premier ; les appels disparus par rapport à la période précédente sont
laissés de côté.

| Champ | Remarques |
|---|---|
| `id`, `kind`, `name`, `namespace`, `category` | Le nœud tel que [la carte des services](#lire-la-carte-des-services) le nomme. |
| `hops` | Appels entre le nœud et le service : `1` pour un appelant ou un appelé direct. |
| `via` | Le nœud par lequel il est atteint, un saut plus près du service. |
| `health` | La santé du service lui-même. Pour ce qui est appelé, la santé que donnent ses appels en échec. |
| `red`, `call` | Ce qu'il a servi ou ce qui lui a été demandé, et les appels entre lui et `via`. |

## Signaler les déploiements

`POST /api/v1/apm/deployments` accepte le déploiement en JSON et renvoie `201` avec celui-ci, son `id`,
`createdBy` et `createdAt` ajoutés. Les champs, leurs limites et des exemples CI figurent dans
[Déploiements](/fr/apm/deployments#signaler-des-déploiements-depuis-la-ci). Le service et l'environnement
sont nommés comme les lisent les règles de nommage, le mapping d'environnement et les alias de l'organisation. Une
adresse de dépôt est conservée avec son mot de passe masqué. Un changement de configuration ou un feature flag définit
`kind` sur `configuration` ou `feature_flag` et ne nécessite pas de `version`.

Un changement d'échelle ou d'infrastructure définit `kind` sur `scaling` ou `infrastructure`. Les changements signalés
sont listés par [`GET /api/v1/changes`](/fr/api/changes).

## Conserver les paramètres APM

`GET /api/v1/apm/settings` renvoie les paramètres de l'organisation ; `PUT` les remplace en bloc et
renvoie ce qui a été conservé :

```json
{
  "health": {
    "errorRateWarning": 0.02,
    "errorRateCritical": 0.1,
    "p95WarningTime": 500000,
    "p95CriticalTime": 2000000
  },
  "apdexThreshold": 500000,
  "longTaskTime": 1000000,
  "namingRules": [{ "pattern": "^(checkout)-[a-z0-9]{5}$", "replacement": "$1" }],
  "environmentMap": [{ "from": "Production", "to": "production" }],
  "aliases": [{ "aliasNamespace": "shop", "alias": "checkout-v1", "namespace": "shop", "service": "checkout" }],
  "metadataRules": { "teamFromTier": "p1", "ownerFromTier": "p0", "repositoryFromTier": null }
}
```

Un champ omis prend sa valeur par défaut. Les espaces superflus des noms sont supprimés, et un namespace d'alias vide vaut `default`. Les
limites et l'effet de chaque paramètre figurent dans [Paramètres APM](/fr/apm/settings). Un enregistrement s'applique immédiatement
sur le nœud qui l'enregistre et en 30 secondes sur les autres.

Les limites de cardinalité de la plateforme se lisent et se remplacent avec `GET` et `PUT
/api/v1/settings/apm_limits`, qui exigent `sys.settings.limits.manage`. Le corps porte
`servicesPerOrgHour`, `transactionsPerServiceHour`, `dependenciesPerServiceHour`,
`operationsPerDependencyHour`, `errorGroupsPerServiceHour`, `versionsPerServiceHour` et
`instancesPerServiceHour`, chacun de 1 à 100000.

## Lire les métadonnées de réponse

Chaque point de terminaison renvoie un objet `meta` commun :

```json
{
  "range": {
    "from": 1785801600000000,
    "to": 1785888000000000
  },
  "resolution": "minute",
  "projectionStartedAt": 1785798000000000,
  "lastCompleteBucketAt": 1785887940000000,
  "dataQuality": {
    "partial": false,
    "gaps": [],
    "overflowDimensions": []
  },
  "activationBoundary": false
}
```

- Traitez `activationBoundary: true` comme une couverture incomplète avant `projectionStartedAt`.
- Traitez `dataQuality.partial: true` comme des données incomplètes, et non comme un zéro complet.
- Inspectez `gaps` pour les échecs de file d'attente, de dépôt, de flush, de données tardives, de cardinalité ou d'arrêt.
- Utilisez `lastCompleteBucketAt` pour déterminer si les données récentes sont encore en cours de finalisation.
- Inspectez `overflowDimensions` avant de faire confiance à une répartition à forte cardinalité.

## Erreurs

| Statut | Cause |
|---|---|
| `400` | Un paramètre est invalide : un `sort` non pris en charge (`unsupported APM sort field`), un `limit` hors de la plage 1 à 200, un filtre vide ou trop volumineux (`invalid APM service filter`), une plage plus longue que le maximum (`APM query range exceeds configured maximum`), une fin antérieure au début (`APM range end precedes start`), un `direction` ou une `resolution` inconnu, un SLO qui échoue aux vérifications ci-dessus (`SLO objective must be between 0 and 1, exclusive`), ou un filtre de liste SLO sans la totalité de `namespace`, `service` et `environment`. |
| `403` | Le token ne dispose pas de la permission requise par l'appel. |
| `404` | L'empreinte d'erreur, la transaction, le service ou le SLO n'existe pas sur la plage. |
| `409` | Des règles d'alerte surveillent encore le SLO en cours de suppression. |
