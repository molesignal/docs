L’API RUM reçoit les événements des clients web et mobiles et permet de les consulter. Tous les points de terminaison utilisent le
préfixe `/api/v1/rum` et exigent un jeton Bearer.

```http
Authorization: Bearer <token>
```

L’écriture d’événements et de segments de replay exige `rum.write`. Un [jeton client](/fr/api/auth/rum-token) lié à une application possède
uniquement cette autorisation, pour une seule application. La lecture exige l’autorisation correspondant au domaine : `rum.events.read`, `rum.sessions.read`, `rum.replay.read`, `rum.issues.read`, `rum.analytics.read`, `rum.applications.read` ou `rum.playlists.read`. Un appel émis par la plateforme peut utiliser `sys.telemetry.read`
dans la portée protégée `_sys`. La création, la modification et la suppression d’une application exigent `rum.applications.manage`. La modification du statut, de l’équipe
ou de la personne responsable d’un problème exige `rum.playlists.manage`.

Les lignes correspondent à des utilisateurs réels. L’API exclut les sessions de type `synthetics` ou `ci_test`, sauf si un filtre mentionne `session.type`, `synthetics.*` ou `ci_test.*`. Consultez la section [Trafic de test](/fr/rum/test-traffic). Un champ peut aussi désigner une clé d’une colonne JSON : `feature_flags.<key>`, `context.<key>`, `usr.extra.<key>` ou `view.custom_timings.<key>`.

Un **type** indique la catégorie de lignes que traite un point de terminaison : `sessions`, `views`, `actions`, `errors`, `resources`, `longTasks`,
`vitals` ou `logs`. Chaque type reprend le nom du [flux](/fr/rum/events#où-sont-stockés-les-événements) correspondant, sans le préfixe
`rum_`.

## Envoyer un segment de replay

```http
POST /api/v1/rum/replay
```

```json
{
  "application": "checkout-web",
  "sessionId": "6f1c2b7e-1d5a-4c6b-9a3e-0a1b2c3d4e5f",
  "seq": 1,
  "events": [{ "type": 2, "timestamp": 1790000000000, "data": { "node": {} } }]
}
```

Les champs `sessionId`, `seq` et `events` sont obligatoires. Envoyez aussi `env`, `service` et `version` si la configuration du SDK les définit :
ces champs fournissent les caractéristiques de la session aux [filtres de conservation](/fr/rum/sampling#filtres) de l’application. L’API ne stocke aucun segment d’une
session que les filtres ne conservent pas. L’API n’accepte aucun autre champ. `events` contient des événements rrweb. Un jeton client permet d’écrire
uniquement dans l’application à laquelle il est lié : omettez `application` ou indiquez cette application. Toute autre valeur entraîne une réponse `403`. Avec un autre moyen d’authentification,
indiquez l’application. Si l’application n’existe pas, l’API renvoie `404`. La réponse décrit le segment stocké :
elle contient `id`, `seq`, `eventCount` et `hasFullSnapshot`.

`GET /api/v1/rum/replay/{sessionId}` renvoie `sessionId`, `segmentCount` et `events`, qui contient les événements de tous les
segments de la session dans l’ordre.

## Gérer les applications

Une application possède les champs `id`, `name`, `platform` et `settings` :

```json
{
  "id": "checkout-web",
  "name": "Checkout web",
  "platform": "browser",
  "settings": {
    "collectIp": true,
    "collectGeo": true,
    "defaultPrivacy": "mask",
    "issuesPerHour": 100,
    "scrub": ["secrets", "emails", "phones", "cards", "national_ids", "url_params"],
    "sessionSampleRate": 100,
    "retentionFilters": [],
    "keepErrors": true,
    "sdk": { "sessionReplaySampleRate": 20, "forwardConsoleLogs": ["warn", "error"] },
    "segments": [{ "id": "enterprise", "name": "Enterprise", "conditions": [{ "field": "usr.extra.plan", "op": "is", "values": ["enterprise"] }] }]
  },
  "createdBy": "<user-id>",
  "createdAt": 1790000000000000,
  "updatedAt": 1790000000000000
}
```

| Champ | Règle |
|---|---|
| `id` | Uniquement à la création. De 1 à 64 caractères parmi `A-Z`, `a-z`, `0-9`, `.`, `_`, `:` et `-`. Le serveur le génère à partir du nom si le champ est absent. L’identifiant ne peut pas changer. |
| `name` | Obligatoire à la création. De 1 à 128 caractères. |
| `platform` | `browser` (par défaut), `android`, `ios`, `flutter`, `react-native` ou `other`. |
| `settings` | `collectIp` et `collectGeo` sont des booléens qui valent `true` par défaut. `defaultPrivacy` vaut `mask` (par défaut), `mask-user-input` ou `allow`. `issuesPerHour` définit le nombre de nouveaux [problèmes](/fr/rum/errors#nouveaux-problèmes-par-heure) que l’application ouvre par heure, de 1 à 10 000. La valeur par défaut est 100. `scrub` répertorie les catégories de texte sensible à retirer d’un événement avant son stockage, parmi `secrets`, `emails`, `phones`, `cards`, `national_ids` et `url_params`. Par défaut, la liste contient toutes les catégories. Une liste vide ne retire rien (voir [Confidentialité des données RUM](/fr/rum/privacy#retirer-les-données-sensibles-à-l’ingestion)). `sessionSampleRate` est le pourcentage de sessions ne correspondant à aucun filtre de rétention à conserver. Il s’agit d’un entier compris entre 0 et 100, avec 100 par défaut (voir [Échantillonnage des données RUM](/fr/rum/sampling#conserver-une-part-des-sessions-côté-serveur)). Une valeur supérieure à 100 entraîne une réponse `400`. `retentionFilters` contient jusqu’à 10 [filtres](/fr/rum/sampling#filtres). Chaque filtre suit la structure `{ "name", "rate", "conditions" }` et possède un `id` que le serveur génère à partir du nom s’il est absent et conserve si le filtre change de nom. Une requête `PATCH` remplace toute la liste. `rate` est un entier compris entre 0 et 100. Une condition suit la structure `{ "field", "op", "values" }`, avec un `field` parmi `env`, `service`, `version`, `source`, `session.type`, `geo.country_iso_code`, `browser.name`, `os.name` ou `device.type`, un `op` égal à `is` ou `is_not` et de 1 à 20 `values`. Un filtre contient au maximum 5 conditions. Chaque nom doit être unique, sans distinction de casse, et les identifiants `default` et `errors` sont réservés. `keepErrors` conserve les erreurs des sessions non retenues et vaut `true` par défaut. Une liste non valide entraîne une réponse `400`. `segments` contient jusqu’à 20 [segments](/fr/rum/analytics#segments). Chaque segment suit la structure `{ "name", "conditions" }` et possède un `id` généré à partir du nom s’il est absent et conservé si le segment change de nom. Une requête `PATCH` remplace toute la liste. Une condition suit la structure `{ "field", "op", "values" }`, avec un `field` parmi `service`, `version`, `source`, `usr.id`, `usr.email`, `account.id`, `browser.name`, `os.name`, `device.type`, `geo.country_iso_code`, `geo.continent_code`, `geo.city` ou `usr.extra.<key>`, un `op` égal à `is` ou `is_not` et de 1 à 20 `values`. Un segment contient de 1 à 5 conditions. `sdk` définit la configuration que `GET /api/v1/rum/config` renvoie à un SDK initialisé avec `remoteConfiguration`. Elle peut inclure `sessionSampleRate` et `sessionReplaySampleRate` (de 0 à 100), `defaultPrivacyLevel`, `trackUserInteractions` et `forwardConsoleLogs` (une liste de niveaux parmi `debug`, `log`, `info`, `warn` et `error`). Pour les options absentes de `sdk`, le SDK utilise la configuration fournie par la page. Chaque paramètre absent prend sa valeur par défaut à la création et conserve sa valeur lors d’une requête `PATCH`. |

`POST` renvoie la nouvelle application. Un identifiant ou un nom déjà utilisé entraîne une réponse `409`. `PATCH` accepte les champs `name`, `platform` et
`settings`. `DELETE` renvoie `{ "deleted": true }`. Les événements déjà envoyés par l’application restent dans les flux jusqu’à
la fin de leur période de rétention.

## Rechercher des lignes

```http
GET /api/v1/rum/search?type=errors&from=1790000000000000&to=1790003600000000&filters=[{"field":"env","op":"=","value":"production"}]&limit=100
```

`POST` accepte les mêmes noms de paramètres dans un corps JSON et convient aux requêtes trop longues pour une URL. Dans une URL, `filters`, `freeText` et
`columns` sont des listes encodées en JSON.

| Paramètre | Type | Comportement |
|---|---|---|
| `type` | chaîne | Obligatoire. Type des lignes. |
| `from`, `to` | entier | Bornes de l’intervalle, en microsecondes depuis l’époque Unix. Par défaut, `to` correspond à l’instant présent et `from` à 24 heures avant `to`. `to` doit être supérieur à `from`. |
| `filters` | liste | Conditions que chaque ligne doit remplir. Voir ci-dessous. |
| `freeText` | liste de chaînes | Jusqu’à 8 mots. Chaque mot doit figurer dans l’une des colonnes de texte du type, sans distinction de casse. |
| `columns` | liste de chaînes | Colonnes à renvoyer. Si le paramètre est absent, la réponse contient les colonnes par défaut du type. La réponse inclut toujours la colonne qui identifie la ligne. |
| `limit` | entier | Taille de page, de 1 à 5 000. La valeur par défaut est 100. |
| `cursor` | chaîne | Valeur de `nextCursor` ou de `previousCursor` issue d’une réponse précédente. Omettez tous les autres paramètres ou répétez-les à l’identique. |

Un **filtre** contient un `field`, un `op` et une `value`. Utilisez au maximum 32 filtres et limitez chaque valeur à 512 caractères.

| `op` | Signification |
|---|---|
| `=`, `!=` | Égalité et inégalité. Si `value` est vide, `=` vérifie l’absence de valeur et `!=` vérifie sa présence. |
| `in`, `not_in` | La valeur du champ figure ou non dans une liste de valeurs. `value` est une liste JSON de 1 à 100 valeurs, par exemple `["Chrome","Safari"]`. |
| `contains` | Le champ contient le texte, sans distinction de casse. S’applique aux colonnes de texte et aux documents JSON. |
| `>`, `>=`, `<`, `<=` | Comparaison d’un nombre ou d’un instant. |
| `exists`, `missing` | Le champ contient une valeur ou n’en contient pas. |

Un champ absent du type ou un opérateur incompatible avec le champ entraîne une réponse `400`.

La réponse contient les lignes d’une page, de la plus récente à la plus ancienne :

```json
{
  "items": [
    { "timestamp": 1790000001600000, "error.message": "Payment provider timeout", "error.id": "0a9b8c7d-6e5f-4a3b-8c1d-2e3f4a5b6c70" }
  ],
  "hasMore": true,
  "nextCursor": "<cursor>",
  "previousCursor": null
}
```

Chaque ligne contient `timestamp` et les colonnes demandées. Une colonne JSON contient le document. Les vues et les sessions
n’apparaissent qu’une fois, dans leur version la plus récente.

## Compter et décrire les lignes

`facets` accepte les paramètres de `search` hors pagination, ainsi que `field` (obligatoire) et `limit` (de 1 à 100, avec 10 par défaut).
La réponse contient les valeurs les plus fréquentes du champ dans les lignes correspondantes :

```json
{ "field": "browser.name", "values": [{ "value": "Chrome", "count": 812 }, { "value": "Safari", "count": 247 }] }
```

Si le comptage prend trop de temps ou si le système est occupé, la réponse contient une liste vide et `unavailable` vaut respectivement `time_budget` ou `busy`.
Un champ contenant un document JSON entraîne une réponse `400`. Pour une clé de ce document, comme `feature_flags.checkout_v2`, le comptage s’effectue par valeur. Les facettes de `session.type` comptent tous les types de sessions.

`keys` accepte les paramètres de sélection, `column` (obligatoire : `feature_flags`, `context`, `usr.extra` ou `view.custom_timings`) et `limit` (de 1 à 500, avec 100 par défaut). `type` vaut `views` par défaut. La réponse classe les clés par nombre décroissant de sessions dans lesquelles elles figurent :

```json
{ "column": "feature_flags", "keys": [{ "key": "checkout_v2", "sessions": 812 }] }
```

`distribution` accepte les paramètres de sélection, `field` (obligatoire : un champ numérique ou la clé d’une colonne JSON contenant un nombre) et `bars` (de 1 à 100, avec 40 par défaut). Il compte les lignes stockées. Les barres ont la même largeur entre la valeur minimale et le 99e percentile. La dernière barre compte les valeurs au-delà de ce percentile et sa borne `to` correspond à la valeur maximale. Si toutes les valeurs sont identiques, une seule barre s’affiche.

```json
{
  "field": "view.loading_time",
  "unit": "ns",
  "rows": 812,
  "min": 90000000,
  "max": 41000000000,
  "p50": 800000000,
  "p75": 1400000000,
  "p95": 3100000000,
  "p99": 6000000000,
  "bars": [{ "from": 90000000, "to": 237750000, "rows": 12 }]
}
```

`histogram` accepte les mêmes paramètres de sélection ainsi que les paramètres des intervalles de comptage : `bucketTime` (au moins 1000) et `originTime`, le début de
la première barre. `originTime` vaut `from` par défaut et ne peut pas être postérieur à `from`. Une plage contient au maximum 512 barres. Chaque intervalle suit la structure `{ startTime, total, errors }`. `errors` compte les lignes
associées à un problème : les sessions et les vues avec des erreurs, les actions avec des signaux de frustration et les requêtes dont le code d’état est supérieur ou égal à `400` ou vaut
`0`. `split` vaut `false` pour les types qui ne comportent pas de telles lignes.

`GET /api/v1/rum/schema/{type}` répertorie les colonnes que les autres points de terminaison acceptent et renvoient :

```json
{
  "type": "views",
  "stream": "rum_views",
  "idField": "view.id",
  "versioned": true,
  "defaultColumns": ["view.id", "view.url_path", "view.loading_time"],
  "fields": [
    { "name": "view.loading_time", "dataType": "int64", "unit": "ns", "facetable": true, "indexed": false }
  ]
}
```

`dataType` vaut `bool`, `int64`, `float64`, `utf8` ou `json`. `unit` vaut `ns`, `ms`, `epoch_ms`, `bytes`, `count`,
`score`, `percent`, `per_second`, `px` ou `none` : le serveur stocke les durées en nanosecondes telles que le SDK les transmet, et le client
les met en forme. `epoch_ms` désigne un instant en millisecondes depuis l’époque Unix, par exemple `session.start` et
`session.last_activity`. Le client l’affiche sous forme de date et d’heure. Un champ `facetable` permet un comptage par valeur, un
champ `indexed` permet de filtrer sans lire chaque ligne et `idField` indique la colonne qui identifie chaque ligne.

## Mesurer les lignes

`aggregate` reprend la sélection de `search` et calcule des mesures sur toutes les lignes correspondantes. Cette fonction fournit les chiffres qui alimentent les graphiques,
les tableaux et les cartes : nombre de sessions, 75e percentile d’un indicateur Web essentiel, par page ou par heure.

```http
GET /api/v1/rum/aggregate?type=views&groupBy=["view.url_path_group"]&measures=[{"fn":"count","name":"views"},{"fn":"p75","field":"view.performance.lcp.timestamp","name":"lcp"}]&limit=5
```

| Paramètre | Type | Comportement |
|---|---|---|
| `type`, `from`, `to`, `filters`, `freeText` | | Comme dans `search`. |
| `measures` | liste | Obligatoire. Jusqu’à 16 mesures. Voir ci-dessous. |
| `groupBy` | liste de chaînes | Jusqu’à 2 champs, avec une ligne par combinaison de valeurs. Le regroupement ne peut pas porter sur un champ contenant un document JSON, mais peut porter sur une clé de ce document, par exemple `feature_flags.checkout_v2`. |
| `bucketTime`, `originTime` | entier | Comme dans `histogram`. Avec ces paramètres, chaque groupe comporte une ligne par barre. |
| `orderBy` | chaîne | Nom d’une mesure, d’un champ de regroupement ou `time` (barres sans regroupement). Par défaut, la première mesure détermine le classement des groupes et les barres suivent l’ordre chronologique. |
| `order` | `asc` ou `desc` | Par défaut, ordre décroissant pour une mesure et ordre croissant pour un groupe ou pour le temps. |
| `limit` | entier | Nombre de groupes, de 1 à 250. Valeur par défaut : 10. Avec des barres, la limite est de 20 et le résultat suit chaque groupe sur toutes les barres. |
| `estimate` | booléen | Valeur par défaut : `true`. Les décomptes, les sommes et les moyennes portent sur l’ensemble des sessions : chaque ligne représente un nombre de lignes égal à l’inverse de son taux de conservation (`retention.rate`). Le calcul des percentiles utilise la même pondération. Avec `false`, seuls les enregistrements stockés entrent dans le calcul, comme dans l’explorateur. |

Une **mesure** comporte un `fn` et un `field`, et peut aussi comporter un `name`, un `where` et un `fallback`.

| `fn` | Signification |
|---|---|
| `count` | Nombre de lignes. Avec `field`, seules les lignes qui contiennent une valeur dans ce champ comptent. Avec `estimate`, le calcul extrapole le nombre de lignes à partir de leur taux de conservation. |
| `stored` | Nombre de lignes stockées, quel que soit leur taux de conservation. |
| `count_distinct` | Nombre de valeurs distinctes de `field`. `fallback` indique le champ à utiliser lorsque `field` ne contient aucune valeur, afin de distinguer les utilisateurs sans identifiant grâce à leur identifiant anonyme. Le calcul compte les utilisateurs et les autres valeurs tels qu’ils apparaissent dans les données. Avec `estimate`, il extrapole le nombre de sessions (`session.id`). |
| `sum`, `avg`, `min`, `max` | Somme, moyenne, minimum ou maximum d’une valeur numérique. |
| `p50`, `p75`, `p90`, `p95`, `p99` | Percentile estimé d’une valeur numérique. |

`where` contient une liste de filtres, comme dans `search`. La mesure ne prend en compte que les lignes qui répondent à ces filtres :
`{"fn":"count","where":[{"field":"session.error.count","op":"=","value":"0"}]}` compte les sessions sans erreur. Une mesure
prend le nom `name` s’il est fourni, sinon `fn(field)` ou simplement `fn` en l’absence de champ. Chaque nom de mesure doit être unique. Si le champ
n’existe pas pour le type demandé ou si le calcul exige une valeur numérique dans un champ qui n’en contient pas, la requête renvoie `400`.

```json
{
  "groupBy": ["view.url_path_group"],
  "measures": [
    { "name": "views", "fn": "count", "unit": "count" },
    { "name": "lcp", "fn": "p75", "field": "view.performance.lcp.timestamp", "unit": "ns" }
  ],
  "rows": [
    { "group": ["/checkout"], "values": [8031, 3400000000.0] },
    { "group": [null], "values": [212, null] }
  ]
}
```

Chaque ligne contient son `group`, dont les champs suivent l’ordre de `groupBy`, et les `values` des mesures, dans l’ordre demandé. Pour un résultat par intervalle de temps, la ligne
contient aussi `startTime`, le début de sa barre. Un groupe dont aucune ligne ne contient de valeur vaut `null`, tout comme un percentile calculé sans
valeurs. `unit` vaut `count` ou reprend l’unité du champ définie par `schema`. Le calcul ne compte les vues et les sessions qu’une fois, dans leur
version la plus récente. Si aucune ligne ne correspond, une réponse avec des groupes ou des barres ne contient aucune ligne. Sans groupe ni barre, la réponse contient une ligne : les décomptes valent `0` et les autres mesures valent `null`. Si les droits d’accès ne permettent pas d’afficher une valeur, la réponse renvoie le texte de masquage. Si le décompte prend trop de temps ou si
le système est occupé, la réponse ne contient aucune ligne et `unavailable` vaut `time_budget` ou `busy`.

## Requête SQL d’un panneau de tableau de bord

```http
POST /api/v1/rum/panel-statement
```

Renvoie la requête SQL qu’un panneau de [tableau de bord](/fr/dashboards) exécute pour reproduire la visualisation de l’[explorateur](/fr/rum/explorer#ajouter-au-tableau-de-bord)
avec les mêmes résultats calculés sur les mêmes lignes, comme avec `aggregate` lorsque `estimate` vaut `false`. Cette opération ne lit aucune donnée. La
requête ne précise aucune plage temporelle : le tableau de bord l’exécute sur la plage sélectionnée. Cette opération nécessite l’autorisation `rum.events.read`.

```json
{
  "type": "views",
  "filters": [{ "field": "env", "op": "=", "value": "production" }],
  "chart": "timeseries",
  "measures": [{ "fn": "p75", "field": "view.loading_time", "name": "p75 Loading" }],
  "groupBy": ["browser.name"],
  "groupNames": ["Browser"],
  "limit": 5,
  "interval": "${interval}"
}
```

| Champ | Type | Comportement |
|---|---|---|
| `type`, `filters`, `freeText` | | Comme dans `search`. |
| `chart` | chaîne | Obligatoire. `timeseries`, `toplist`, `table` ou `distribution`. |
| `measures`, `groupBy`, `orderBy`, `order`, `limit` | | Comme dans `aggregate`, à l’exception de `estimate` et du comportement des barres. Un graphique `toplist` accepte un seul champ de regroupement. Un graphique `timeseries` suit au maximum 20 groupes. Chaque mesure forme une colonne qui porte son `name`. |
| `groupNames` | liste de chaînes | Noms des colonnes de regroupement, dans l’ordre. Sans nom explicite, la colonne porte le nom de son champ. |
| `field` | chaîne | Obligatoire pour `distribution` : champ numérique dont le graphique montre la distribution. Sa colonne porte le premier nom de `groupNames`, et la colonne de décompte porte le `name` de la première mesure. |
| `interval` | chaîne | Obligatoire pour `timeseries` : durée de chaque intervalle, exprimée par une variable de tableau de bord comme `${interval}` ou par une durée comme `15 minutes`. |

```json
{
  "stream": "rum_views",
  "statement": "WITH \"__top\" AS (SELECT … LIMIT 5) SELECT date_bin(INTERVAL '${interval}', _timestamp) AS \"time\", … FROM \"rum_views_latest\" JOIN \"__top\" ON … GROUP BY 1, 2 ORDER BY 1, 2",
  "columns": [
    { "name": "time", "role": "time", "unit": "none" },
    { "name": "Browser", "role": "group", "unit": "none" },
    { "name": "p75 Loading", "role": "measure", "unit": "ms" }
  ],
  "limit": 10000
}
```

La requête lit `stream`, ainsi que la version la plus récente d’une vue ou d’une session, via `rum_views_latest` ou
`rum_sessions_latest`. Elle reprend les conditions de la sélection et exclut les sessions issues des tests synthétiques et de l’intégration continue,
sauf si les filtres mentionnent `session.type`, `synthetics.*` ou `ci_test.*`. `columns` énumère les colonnes que la requête renvoie, dans l’ordre :
`time` pour le début d’une barre, puis les groupes et les mesures. Le champ `unit` d’une mesure indique son unité d’affichage : une durée s’affiche donc en `ms`.

- Un graphique `timeseries` renvoie une ligne par barre et par groupe. Il retient les groupes les mieux classés selon la première mesure sur
  toute la plage temporelle.
- Un graphique `toplist` ou `table` renvoie une ligne par groupe, dans l’ordre demandé et dans la limite de `limit`.
- Un graphique `distribution` renvoie 40 barres, de la valeur minimale au 99e percentile. La dernière compte aussi les valeurs au-delà de ce percentile. Chaque
  barre porte comme nom sa borne inférieure, exprimée dans l’unité d’affichage de la valeur.

`limit` définit le nombre de lignes que le panneau demande. Un champ absent du type demandé, un graphique incompatible avec les paramètres fournis
(un graphique `toplist` sans exactement un champ de regroupement ou un graphique `timeseries` sans `interval`), ou un `interval` qui n’est ni une variable ni
une durée entraîne une réponse `400`.

## Entonnoirs, parcours et rétention

Les trois points de terminaison sous `/api/v1/rum/analytics` répondent aux requêtes de l’[analyse RUM](/fr/rum/analytics). Chacun reprend les
paramètres de sélection de `search` qui s’appliquent aux sessions, aux vues et aux actions : `from` et `to` en microsecondes, ainsi que `filters`, les critères que chaque
ligne doit respecter, généralement l’application (`application.id`) et l’environnement (`env`). Avec `GET`, les listes sont encodées en JSON dans les
paramètres, ce qui permet de partager la requête sous forme de lien ; `POST` accepte les mêmes noms dans un corps JSON. Ces points de terminaison exigent `rum.analytics.read` ou `sys.telemetry.read`
dans le périmètre protégé `_sys`. Si le comptage prend trop de temps ou si le système est occupé, la réponse ne contient aucun chiffre et `unavailable` vaut
`time_budget` ou `busy`. Les réponses indiquent les valeurs `from` et `to` de la période couverte.

### Entonnoir

```http
GET /api/v1/rum/analytics/funnel?filters=[{"field":"application.id","op":"=","value":"shop-web"}]&steps=[{"type":"views","filters":[{"field":"view.url_path_group","op":"=","value":"/cart"}]},{"type":"actions","name":"Paid","filters":[{"field":"action.target.name","op":"=","value":"Pay now"}]}]&windowSecs=1800&breakdown=browser.name
```

| Paramètre | Type | Comportement |
|---|---|---|
| `from`, `to` | entier | Microsecondes. Par défaut, les 7 derniers jours. |
| `filters` | liste | Critères que chaque étape doit respecter en plus de ses propres filtres. |
| `steps` | liste | Obligatoire. De 2 à 8 étapes. Chaque étape comporte un `type`, `views` ou `actions`, une liste de `filters` au format de `search` qui s’appliquent aux lignes de ce type, et un `name` facultatif, qui prend par défaut la valeur du premier filtre. |
| `windowSecs` | entier | Durée maximale entre la première étape et une étape ultérieure, en secondes. Sans ce paramètre, aucune limite de durée ne s’applique. |
| `breakdown` | chaîne | Champ textuel des lignes de la première étape. Chaque valeur donne lieu à un entonnoir distinct. La réponse conserve les 10 valeurs qui comptent le plus de sessions. |

Pour chaque session, la première étape retient la première ligne qui satisfait ses critères. Chaque étape suivante retient la première ligne de la même session qui satisfait ses critères et qui survient après
la ligne de l’étape précédente.

```json
{
  "groups": [
    {
      "value": null,
      "steps": [
        { "name": "/cart", "sessions": 4, "conversion": 1.0, "fromPrevious": null, "medianMs": null },
        { "name": "Paid", "sessions": 2, "conversion": 0.5, "fromPrevious": 0.5, "medianMs": 210000.0 }
      ]
    }
  ],
  "from": 1779400000000000,
  "to": 1780000000000000
}
```

Chaque groupe présente l’entonnoir des sessions qui partagent une valeur de `breakdown`. Les groupes sont classés par nombre de sessions à la première étape,
et `value` vaut `null` pour le groupe qui réunit toutes les sessions ou pour celui dont les lignes n’ont pas de valeur. `conversion` indique la proportion des
sessions de la première étape, `fromPrevious` la proportion des sessions de l’étape précédente et `medianMs` le délai médian
depuis l’étape précédente ; chaque champ vaut `null` s’il ne s’applique pas. Si le champ n’est pas textuel ou n’existe pas pour le type de ligne,
la requête échoue avec le code `400`.

### Parcours

| Paramètre | Type | Comportement |
|---|---|---|
| `from`, `to`, `filters` | | Comme pour `funnel`. Les lignes correspondent aux vues. |
| `anchor` | chaîne | Page de départ des parcours, ou page d’arrivée en remontant le parcours. Sans ce paramètre, utilise la première page de chaque session, ou la dernière en remontant le parcours. |
| `backward` | booléen | Remonte le parcours vers les pages qui précèdent la page de référence. Valeur par défaut : `false`. |
| `depth` | entier | De 1 à 6 pages après ou avant la page de référence. Valeur par défaut : 3. |
| `by` | chaîne | Champ qui identifie une page : `view.url_path_group` (par défaut), `view.url_path` ou `view.name`. |

```json
{
  "columns": 3,
  "sessions": 9,
  "backward": false,
  "nodes": [
    { "column": 0, "page": "/products", "sessions": 2, "ends": 0 },
    { "column": 1, "page": "/cart", "sessions": 2, "ends": 0 },
    { "column": 2, "page": "/checkout", "sessions": 1, "ends": 1 }
  ],
  "links": [
    { "column": 0, "source": "/products", "target": "/cart", "sessions": 2 },
    { "column": 1, "source": "/cart", "target": "/checkout", "sessions": 1 }
  ],
  "from": 1779400000000000,
  "to": 1780000000000000
}
```

`columns` contient les pages, avec une colonne de plus que `depth`. La page de référence occupe la colonne 0 (la dernière colonne si le parcours est remonté).
Un nœud représente une page dans une colonne. `sessions` compte les sessions qui sont passées par cette page et `ends` celles qui s’y sont terminées (ou qui y ont commencé
si le parcours est remonté). Un lien relie une page de `column` à une page de la colonne suivante dans l’ordre chronologique, même si le parcours est remonté, et indique le nombre de
sessions qui ont suivi cette transition. Les pages suivent leur ordre d’ouverture. Les ouvertures consécutives d’une même page ne comptent qu’une fois. Chaque
colonne nomme les 8 pages qui comptent le plus de sessions et regroupe les autres sous `__other__`. `sessions` indique le nombre de sessions qui comprennent
la page de référence.

### Rétention

| Paramètre | Type | Comportement |
|---|---|---|
| `from`, `to`, `filters` | | Comme pour `funnel`. Les lignes correspondent aux sessions. Sans `from` ni `to`, l’historique remonte assez loin pour constituer des cohortes : deux fois `periods` périodes avant l’instant présent, avec un minimum de 14 jours (8 semaines pour `week`). |
| `period` | `day` ou `week` | Jour en UTC ou semaine en UTC commençant le lundi. Valeur par défaut : `day`. |
| `periods` | entier | De 1 à 30 périodes après la première. Valeur par défaut : 7. |

```json
{
  "period": "day",
  "periods": 3,
  "cohorts": [
    { "startTime": 1779408000000000, "users": 1, "returned": [1, 0, null] },
    { "startTime": 1779494400000000, "users": 6, "returned": [0, null, null] }
  ],
  "from": 1779408000000000,
  "to": 1779753600000000
}
```

Une cohorte regroupe les utilisateurs observés pour la première fois pendant la période qui commence à `startTime`, dans l’intervalle demandé. Chaque utilisateur correspond à
la valeur `usr.id` d’une session ou, à défaut, à sa valeur `usr.anonymous_id`. Pour chaque période suivante, `returned` indique combien d’utilisateurs de la
cohorte sont revenus ; la valeur est `null` pour toute période qui n’est pas terminée à `to`.

## Cartes de chaleur

Les points de terminaison sous `/api/v1/rum/heatmaps` renvoient les données des [cartes de chaleur RUM](/fr/rum/heatmaps). Ils acceptent `from` et `to` en microsecondes, ainsi que `filters`, généralement `application.id`, `view.url_path_group` et la largeur de la fenêtre (`display.viewport.width`) ; avec `GET`, le paramètre contient la liste au format JSON. `clicks` et `scroll` acceptent aussi `limit` et exigent `rum.analytics.read`. Ils comptent les lignes stockées, sans estimation.

```json
{
  "clicks": 148,
  "elements": [
    {
      "element": "body>main>button:nth-of-type(2)",
      "name": "Pay now",
      "selector": "button.pay",
      "clicks": 92,
      "sessions": 60,
      "frustrated": 4,
      "pageX": 640.5,
      "pageY": 720.0,
      "cells": [[5, 4, 31], [6, 4, 28]]
    }
  ],
  "from": 1779400000000000,
  "to": 1780000000000000
}
```

`clicks` renvoie les éléments qui ont reçu le plus de clics, de 1 à 300 éléments et 100 par défaut. `element` indique l’emplacement de l’élément sur la page. `pageX` et `pageY` donnent les coordonnées moyennes des clics sur l’élément. `cells` divise l’élément en une grille de 10 × 10 cellules, chacune au format `[column, row, clicks]`.

```json
{
  "views": 310,
  "pageHeight": 4200,
  "medianDepth": 1800,
  "bands": [{ "depth": 800, "reached": 1.0 }, { "depth": 900, "reached": 0.97 }],
  "from": 1779400000000000,
  "to": 1780000000000000
}
```

`scroll` renvoie le nombre de vues pour lesquelles une profondeur de défilement est disponible, la hauteur de la page et la profondeur atteinte par la moitié de ces vues. Chaque bande mesure 100 pixels : `reached` indique la proportion des vues qui ont atteint cette profondeur. Cette proportion ne peut pas augmenter à mesure que la profondeur augmente.

`snapshot` accepte `viewId`, l’identifiant d’une des vues candidates, et exige `rum.replay.read`. La réponse contient `candidates`, jusqu’à 20 vues de la page avec un enregistrement de session, de la plus récente à la plus ancienne, chacune avec `sessionId`, `viewId`, `atTime` et les dimensions `width` et `height` de sa fenêtre. Elle contient aussi `snapshot`, avec les mêmes champs pour la vue affichée et les `events` rrweb qui permettent de la reconstituer à `atTime` à partir du dernier instantané complet antérieur à cet instant. `snapshot` vaut `null` si aucun enregistrement ne couvre une session ayant ouvert la page.

## Listes de lecture

Une [liste de lecture](/fr/rum/playlists) est une liste nommée de sessions d’une même application, avec pour chaque session le moment pertinent où commencer la lecture.

```json
{
  "id": "2xT9bQ1kLw5nVf8cZ0aR7mHpJd3",
  "application": "checkout-web",
  "name": "Checkout failures",
  "description": "Sessions that ended at the checkout with an error.",
  "createdBy": "<user-id>",
  "createdAt": 1790000000000000,
  "updatedAt": 1790000100000000,
  "sessionCount": 2,
  "sessions": [
    { "sessionId": "3f6c9a52-1b7e-4d08-a5c3-90e2d41f7b68", "atTime": 1790000005000000, "addedBy": "<user-id>", "addedAt": 1790000000000000 },
    { "sessionId": "9d41e7b0-62fa-4c3d-8e15-b7a09c52d3f4", "atTime": null, "addedBy": "<user-id>", "addedAt": 1790000100000000 }
  ]
}
```

`GET /api/v1/rum/playlists` renvoie les listes de lecture sans `sessions`, par ordre de modification décroissant. Le paramètre `application` permet de
limiter les résultats à une seule application. La lecture exige `rum.playlists.read`. Un appel effectué au niveau de la plateforme peut utiliser `sys.telemetry.read`. Les autres requêtes modifient une liste de lecture
et exigent `rum.playlists.manage`. Elles renvoient toutes la liste de lecture avec ses sessions, sauf `DELETE`, qui renvoie `{ "deleted": true }`.

| Requête | Corps | Règle |
|---|---|---|
| `POST /rum/playlists` | `application`, `name` et, facultativement, `description` et `sessions` | L’application doit exister (`404`). Le nom contient de 1 à 128 caractères et doit être unique au sein de l’application, sans distinction de casse (`409`). La description peut contenir jusqu’à 1 000 caractères. |
| `PATCH /rum/playlists/{id}` | `name` et `description`, tous deux facultatifs | Un champ omis conserve sa valeur. L’application ne peut pas changer. |
| `POST /rum/playlists/{id}/sessions` | `sessions` | Une session ajoutée de nouveau prend la valeur `atTime` fournie et conserve sa place. Une liste de lecture contient au maximum 500 sessions (`400`). |

Dans une requête, une session prend la forme `{ "sessionId": "...", "atTime": 1790000005000000 }` : l’identifiant contient de 1 à 128 caractères et `atTime`, si
le champ est renseigné, indique l’instant où commence la lecture, en microsecondes depuis l’époque Unix. Sans ce champ, la lecture commence au début de la session. La
liste de lecture stocke les identifiants, pas les sessions : elle ne vérifie pas l’existence d’une session. Si la politique de rétention supprime les lignes d’une session, celle-ci reste
dans la liste. `GET /api/v1/rum/sessions/{id}/playlists` renvoie les listes de lecture qui contiennent cette session, sans inclure leurs sessions.

## Lire une ligne ou une session

`GET /api/v1/rum/{type}/{id}` renvoie une ligne avec toutes ses colonnes, ou `404`. `from` et `to` délimitent la période de recherche ; sans
ces paramètres, la recherche couvre les 30 derniers jours. `{id}` correspond à la valeur du champ `idField` du type.

`GET /api/v1/rum/sessions/{id}/timeline` renvoie :

| Champ | Contenu |
|---|---|
| `session` | La ligne de la session, ou `null` tant qu’aucune ligne n’a été générée pour cette session. |
| `items` | Les lignes de tous les autres types qui appartiennent à la session, de la plus ancienne à la plus récente. Chaque ligne contient un champ `type` : `view`, `action`, `error`, `resource`, `long_task`, `vital` ou `log`. |
| `truncated` | Les types dont le nombre de lignes dépasse la capacité de la chronologie. |

`GET /api/v1/rum/sessions/{id}/related-traces` répertorie les traces backend d’une session. La réponse indique les traces dont une requête
de la session contenait l’ID (`relation: direct`) ou, à défaut, les traces qui se sont déroulées pendant la session
(`relation: time-correlated`). Chaque trace contient `trace_id`, `service`, `spanCount`, `durationMs` et
`startedAt`, et la réponse contient `primaryService`. `GET /api/v1/rum/traces/{traceId}/session` effectue la recherche inverse
et renvoie la session, ou `null`.

## Commentaires

```http
POST /api/v1/rum/sessions/{id}/comments
```

```json
{ "application": "checkout-web", "atTime": 1790000005000000, "body": "The button does nothing here." }
```

`atTime` indique un instant de la session en microsecondes depuis l’époque Unix, et `body` contient de 1 à 2 000 caractères. Une session peut contenir jusqu’à 500 commentaires. `GET` renvoie `{ "comments": [...] }`, du plus ancien au plus récent, et nécessite l’autorisation `rum.replay.read`.

```json
{
  "id": "2xT9bQ1kLw5nVf8cZ0aR7mHpJd3",
  "application": "checkout-web",
  "sessionId": "3f6c9a52-1b7e-4d08-a5c3-90e2d41f7b68",
  "atTime": 1790000005000000,
  "body": "The button does nothing here.",
  "authorId": "<user-id>",
  "authorName": "Ada",
  "createdAt": 1790000010000000,
  "updatedAt": 1790000010000000,
  "editable": true
}
```

`POST` nécessite l’autorisation `rum.replay.comments.write`. `PATCH` accepte `body`. `PATCH` et `DELETE` nécessitent cette même autorisation pour un commentaire dont le compte appelant est l’auteur, et `rum.replay.comments.manage` pour tout autre commentaire. `editable` indique si le compte appelant peut modifier le commentaire. `DELETE` renvoie `{ "deleted": true }`.

## Résumé

`GET /api/v1/rum/sessions/{id}/summary` renvoie `{ "summary": ... }` avec le résumé enregistré dans la langue du compte appelant, ou `null`. Cette requête nécessite `rum.replay.read`. `POST` génère un résumé à l’aide d’un modèle et nécessite `rum.replay.summaries.generate`. Si un résumé existe déjà, l’API le renvoie sans appeler le modèle. Avec `{ "regenerate": true }`, l’API appelle le modèle, sauf si la session n’a pas changé.

```json
{
  "summary": {
    "sessionId": "3f6c9a52-1b7e-4d08-a5c3-90e2d41f7b68",
    "language": "en-us",
    "summary": "The user filled the cart and could not pay: the payment call failed three times.",
    "chapters": [{ "atTime": 1790000005000000, "title": "Fills the cart", "summary": "Adds two items." }],
    "model": "<model>",
    "promptTokens": 1820,
    "completionTokens": 240,
    "generatedAt": 1790000020000000
  }
}
```

L’appel est décompté du budget quotidien de Mole Agent avec l’origine `replay_summary`. Si le budget est épuisé, l’API renvoie `429`. Si l’organisation ne dispose d’aucun fournisseur de modèles activé et configuré avec une clé, ou si la session ne contient rien à résumer, l’API renvoie `400`.

## Problèmes

MoleSignal regroupe les erreurs similaires en [problèmes](/fr/rum/errors). Chaque ligne d’erreur contient l’identifiant de son problème dans `error.issue_id`.
MoleSignal calcule les compteurs d’un problème à partir des erreurs survenues dans la période demandée. Le statut et l’historique du problème sont stockés séparément.
Les horodatages sont exprimés en microsecondes depuis l’époque Unix.

```http
GET /api/v1/rum/issues?application=checkout-web&status=unresolved&sort=sessions&limit=50
```

| Paramètre | Type | Comportement |
|---|---|---|
| `application` | chaîne | Obligatoire. |
| `env`, `source` | chaîne | Limite le résultat aux erreurs de cet environnement ou à celles envoyées par cette source (`browser`, `flutter`, etc.). |
| `filters` | liste | Ajoute des conditions aux erreurs comptabilisées, comme dans `search`. |
| `from`, `to` | entier | Comme dans `search`. |
| `status` | chaîne | `unresolved` (par défaut : ouverts, en cours d’investigation ou réapparus), `all` ou l’une des valeurs suivantes : `open`, `investigating`, `regressed`, `resolved`, `ignored`. |
| `assignee`, `team` | chaîne | Identifiant d’un compte utilisateur ou d’une équipe, ou `none` pour les problèmes non attribués. |
| `search` | chaîne | Recherche des mots dans le type, le message ou l’emplacement du problème, sans distinction de casse. |
| `fresh` | booléen | Limite le résultat aux problèmes apparus pour la première fois ou réapparus pendant la période. |
| `sort` | chaîne | `sessions` (par défaut), `users`, `occurrences`, `lastSeen`, `firstSeen` ou `status`. |
| `order` | `asc` ou `desc` | Ordre décroissant par défaut, sauf pour `status`. |
| `limit` | entier | De 1 à 100. Valeur par défaut : 50. |

```json
{
  "issues": [
    {
      "id": "3f9c2a71e0b4c8d1",
      "applicationId": "checkout-web",
      "status": "regressed",
      "assigneeId": "<user-id>",
      "teamId": null,
      "overflow": false,
      "source": "source",
      "errorType": "ChunkLoadError",
      "message": "Loading chunk 482 failed.",
      "location": "src/router/lazy.ts:34 · loadChunk",
      "firstSeenAt": 1789300000000000,
      "lastSeenAt": 1790000000000000,
      "firstVersion": "2.2.0",
      "lastVersion": "2.4.1",
      "resolvedAt": 1789600000000000,
      "resolvedVersion": "2.3.0",
      "resolvedBy": "<user-id>",
      "regressedAt": 1789900000000000,
      "regressedVersion": "2.4.1",
      "regressedEnvironment": "production",
      "updatedBy": null,
      "updatedAt": 1789900000000000,
      "sessions": 612,
      "users": 498,
      "occurrences": 1530,
      "trend": [3, 5, 4, 9, 40, 120]
    }
  ],
  "total": 8
}
```

`regressedEnvironment` indique l’environnement de l’erreur qui a fait réapparaître le problème, ou `null` si cette erreur ne précise aucun environnement. Un problème
concerne l’ensemble de l’application, quel que soit l’environnement de ses erreurs. Le serveur enregistre aussi la première apparition du problème dans chaque environnement.
Les [règles d’alerte](/fr/rum/alerts#filtrer-une-règle) utilisent cette date pour comptabiliser les nouveaux problèmes de chaque environnement.

L’API sélectionne les 250 problèmes qui comptent le plus de sessions, d’utilisateurs ou d’occurrences selon `sort`, puis les filtre selon `status`, `assignee`,
`team`, `search` et `fresh`. `total` indique le nombre de problèmes après filtrage, avant l’application de `limit`. `trend` indique le nombre d’occurrences
dans chacun des 12 intervalles de durée égale au maximum qui composent la période, du plus ancien au plus récent. `overflow` signale le problème qui comptabilise les erreurs d’une application au-delà
du [nombre de problèmes qu’elle peut ouvrir en une heure](/fr/rum/errors#nouveaux-problèmes-par-heure). Si le comptage prend trop de temps ou si le système est occupé,
l’API ne renvoie aucun problème et définit `unavailable` sur `time_budget` ou `busy`.

`GET /api/v1/rum/issues/{id}` renvoie le problème au même format que dans la liste, sans `trend`, avec `sessions`, `users` et `occurrences`
comptabilisés entre `from` et `to`, ainsi que deux champs supplémentaires :

| Champ | Contenu |
|---|---|
| `samples` | Les trois dernières sessions qui ont rencontré le problème, de la plus récente à la plus ancienne : `timestamp`, `sessionId`, `userId`, `anonymousId`, `page`, `browser`, `system`, `version`, `hasReplay` et `retained`. `retained` vaut `false` pour une erreur issue d’une session non conservée : aucune session ne peut alors être ouverte. |
| `stack` | La trace de pile de l’erreur la plus récente qui contient des trames. Si aucune erreur ne contient de trames, l’API renvoie la trace de pile de la dernière erreur avec `frames` vide, ou `null` si la période ne contient aucune erreur liée au problème. La trace contient `message`, `text`, `frames`, `symbolication`, `handling`, `isCrash` et `category`. Chaque trame contient `raw` (la valeur envoyée par le SDK), `restored` (la valeur obtenue à partir d’un artefact de débogage, ou `null`) et `inApp`. Si l’API a tenté la symbolication, `symbolication` vaut `completed`, `partial` ou `missing`. |

Si le problème n’existe pas, l’API renvoie `404`.

`PATCH /api/v1/rum/issues/{id}` accepte les champs `status`, `assigneeId` et `teamId`, et renvoie le problème après modification.

```json
{ "status": "resolved", "assigneeId": "<user-id>", "teamId": null }
```

`status` accepte `open`, `investigating`, `resolved` ou `ignored`. Les règles définissent `regressed` lorsqu’un problème résolu réapparaît dans
une version plus récente. Si la requête spécifie `regressed`, l’API renvoie `400`. `assigneeId` doit correspondre à un membre de l’organisation et `teamId` à l’une de ses équipes. Utilisez `null` ou une
chaîne vide pour retirer l’attribution au membre ou à l’équipe. Les champs omis restent inchangés. La résolution enregistre `resolvedAt`, `resolvedBy` et la version la plus récente de
l’application dans `resolvedVersion`. Tout changement de statut efface les informations de résolution ou de réapparition précédentes. Si la requête ne précise aucun champ à modifier, l’API renvoie `400`. Si les valeurs sont déjà définies à l’identique, l’API renvoie `200` sans rien modifier. L’API inscrit chaque modification dans le journal d’audit sous `rum.issue.update`.

## Prévisualiser une règle d’alerte

```http
POST /api/v1/rum/alerts/preview
```

Utilise le code d’évaluation pour afficher ce qu’une [règle d’alerte sur une métrique RUM](/fr/rum/alerts) aurait observé sur la période récente,
une fenêtre à la fois. Nécessite `rum.events.read`.

```json
{
  "query": { "applicationId": "checkout-web", "environment": "production", "page": "/checkout", "metric": "lcp_p75" },
  "periodSecs": 3600
}
```

| Champ | Type | Comportement |
|---|---|---|
| `query` | objet | Obligatoire. Définit la métrique avec `applicationId` et `metric`, ainsi que `environment`, `page`, `version` et `minSamples` si ces champs sont renseignés. Le point de terminaison refuse `page` ou `version` si la métrique ne peut pas être filtrée sur ce champ, et `minSamples` s’il s’agit d’un comptage. `custom_vital` et `custom_timing` acceptent aussi `statistic` et exigent `customName`. `query` exige `search`, qui contient `type`, l’expression `statement` telle qu’elle a été saisie, les `filters` et le `freeText` extraits de cette expression, ainsi que `measure` (`fn` et `field`). Consultez [Créer une règle](/fr/api/alerting/create-rule#règles-rum). |
| `periodSecs` | entier | Obligatoire. Durée de la fenêtre d’évaluation de la règle, de 60 à 21 600. Chaque point correspond à une fenêtre. |
| `from`, `to` | entier | Bornes de la période en microsecondes depuis l’époque Unix. Seules les fenêtres complètes sont prises en compte. Par défaut, `to` correspond à l’instant présent. Par défaut, `from` se situe six heures avant `to`, avec un minimum de 12 fenêtres, un maximum de 72 fenêtres et une durée maximale d’un jour. Une période contient au maximum 360 fenêtres. |

```json
{
  "metric": "lcp_p75",
  "unit": "milliseconds",
  "minSamples": 50,
  "periodSecs": 3600,
  "from": 1789956800000000,
  "to": 1790000000000000,
  "points": [
    { "at": 1789956800000000, "value": null, "samples": null },
    { "at": 1789960400000000, "value": 2480, "samples": 612 }
  ],
  "current": { "at": 1789996400000000, "value": 2310, "samples": 540 }
}
```

`unit` vaut `count`, `percent`, `milliseconds`, `score`, `bytes` ou `none`. Pour chaque point, `at` indique le début de la fenêtre, `value` contient la valeur de la métrique et
`samples` indique le nombre de lignes utilisées pour la calculer. Si la fenêtre contient moins de lignes que le seuil `minSamples`, le point ne contient ni `value` ni `samples`. `current` correspond au dernier point,
celui de la fenêtre qui se termine à `to`. Si le comptage prend trop de temps ou si le système est occupé, le point de terminaison ne renvoie aucun point et définit `unavailable` sur
`time_budget` ou `busy`. Le point de terminaison renvoie `404` si l’application n’existe pas et `400` si la règle est incompatible avec la métrique.

## Erreurs

| Statut | Cause |
|---|---|
| `400` | Un paramètre, un filtre, une colonne ou un curseur ne convient pas à la requête. |
| `401`, `403` | Le jeton est manquant ou invalide, ou ne dispose pas de l’autorisation requise par le point de terminaison. |
| `404` | La ligne, la session ou l’application n’existe pas. |
| `409` | Une application porte déjà cet identifiant ou ce nom. |
| `413` | La requête dépasse les limites de [`events`](/fr/rum/events#envoyer-des-événements). |
