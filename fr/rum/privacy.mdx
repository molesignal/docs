Appliquez les contrôles de confidentialité dans le navigateur pour empêcher l’envoi de valeurs sensibles sur le réseau. Commencez par le
mode masqué par défaut et n’autorisez du contenu supplémentaire qu’après examen de l’enregistrement.

## Paramètres par défaut pour protéger la confidentialité

```ts
init({
  applicationId: 'checkout-web',
  clientToken: 'mspat-your-client-token',
  site: 'https://molesignal.example.com',
  defaultPrivacyLevel: 'mask',
  trackUrlQueryString: false,
});
```

Avec ces paramètres par défaut :

- Le SDK supprime les chaînes de requête et les fragments des URL ;
- Le SDK masque à tous les niveaux les clés telles que `password`, `secret`, `token`, `authorization`, `cookie`, `api_key` et les champs de carte de
  paiement dans les données d’utilisateur, de compte et de contexte ;
- Le SDK nomme les actions `Click <structural selector>`. Les sélecteurs ne contiennent ni identifiants, ni identifiants de test, ni classes. Le texte d’un
  élément ne sert à nommer une action qu’avec `defaultPrivacyLevel: 'allow'` ;
- Le SDK masque le texte du DOM lors de la relecture de session ;
- Le SDK masque toutes les valeurs des champs de saisie et des éléments `contenteditable`, comme avec `mask-user-input`.

<Warning>
  Le masquage par nom de champ est un filet de sécurité, pas un système de classification des données. N’ajoutez ni identifiants de connexion,
  ni données de paiement, ni données de santé, ni informations personnelles superflues aux objets utilisateur ou de contexte personnalisé.
</Warning>

## Bloquer ou masquer le contenu du DOM

Le SDK reconnaît les attributs de confidentialité sans code d’enregistrement propre à l’application :

```html
<section data-molesignal-block>
  <!-- The entire subtree becomes a placeholder. -->
</section>

<span data-molesignal-mask>Account holder name</span>

<div data-molesignal-ignore>
  <!-- Mutations and events for this element are ignored. -->
</div>
```

Remplacez les sélecteurs par défaut si nécessaire :

```ts
sessionReplay: {
  blockSelector: '.payment-form, [data-private-panel]',
  maskTextSelector: '.customer-name, [data-molesignal-mask]',
  ignoreSelector: '.animation-layer, [data-molesignal-ignore]',
},
```

Bloquez les secrets et les composants volumineux qui contiennent des données sensibles, masquez le texte dont la mise en page est utile et
ignorez les éléments parasites qui n’apportent rien à l’analyse.

## Afficher la page et masquer les saisies

`defaultPrivacyLevel: 'mask-user-input'` enregistre le texte de la page et masque les saisies : les valeurs des champs de saisie et des
éléments `contenteditable`. Ce mode convient aux pages dont le texte est identique pour tout le monde. Le texte ciblé par le `maskTextSelector` configuré reste masqué.

En mode `mask`, affichez une zone si son texte ne contient pas de données sensibles :

```html
<nav data-molesignal-allow>Pricing · Docs · Sign in</nav>
```

`data-molesignal-allow` affiche le texte de l’élément et de ses descendants. Dans cette zone, le SDK continue de bloquer ou d’ignorer les éléments concernés et de masquer le texte ciblé par
`maskTextSelector`, ainsi que les champs de saisie et les éléments `contenteditable`.

## Autoriser l’affichage du texte de la page avec précaution

N’activez `defaultPrivacyLevel: 'allow'` qu’après avoir marqué toutes les zones sensibles. Ce mode affiche aussi les saisies, sauf les mots de passe, les adresses
e-mail, les numéros de téléphone, les champs dont l’attribut `autocomplete` indique une carte de paiement ou un code à usage unique, et les champs à l’intérieur d’un élément marqué
`data-molesignal-mask`. Le texte ciblé par le `maskTextSelector` configuré reste masqué.

```ts
defaultPrivacyLevel: 'allow',
sessionReplay: {
  blockSelector: '[data-molesignal-block], .payment-details',
  maskTextSelector: '[data-molesignal-mask], .customer-identity',
},
```

## Contrôler les URL et la collecte des données réseau

Conservez `trackUrlQueryString: false`, sauf si l’application garantit que les chaînes de requête ne contiennent jamais
d’identifiants ni de secrets. Excluez les routes ou les points de terminaison réseau sensibles avant la collecte :

```ts
excludedUrls: [
  '/account/security',
  /^https:\/\/api\.example\.com\/private\//,
  (url) => url.includes('/token-exchange'),
],
```

`allowedTracingUrls` définit les origines qui peuvent fournir un contexte de trace. Cette option n’active pas la capture du corps des requêtes
ni des réponses. Le SDK enregistre les mesures de temps et les métadonnées d’URL nettoyées.

## Retirer les données sensibles à l’ingestion

Le SDK constitue la première ligne de défense, et le serveur la seconde. Pour chaque application, le serveur retire de chaque événement les types de données sensibles sélectionnés,
avant tout stockage, quel que soit le SDK ou le client qui a envoyé l’événement. Ouvrez l’application dans
**RUM → Applications**, puis activez ou désactivez les types de **Données sensibles**. Tous sont actifs pour une nouvelle application.

| Type | Données retirées | Valeur de remplacement |
|---|---|---|
| **Jetons, clés et mots de passe** | Les jetons Bearer et Basic, les JWT, les clés des services cloud et de développement (clés d’accès AWS et jetons GitHub, GitLab, Slack, Stripe, OpenAI, Google et npm), les clés privées, les valeurs qui suivent `password=`, `secret:`, `api_key=`, `authorization:` et les termes similaires, ainsi que les valeurs des en-têtes `Authorization`, `Cookie`, `Set-Cookie`, `Proxy-Authorization`, `X-API-Key`, `X-Auth-Token` et `X-CSRF-Token`. | `[secret]` |
| **Adresses e-mail** | Les adresses telles que `jane@example.com`. | `[email]` |
| **Numéros de téléphone** | Les numéros internationaux qui commencent par `+` et comportent de 8 à 15 chiffres, les numéros de mobile chinois à 11 chiffres et les numéros nord-américains tels que `(415) 555-2671`. | `[phone]` |
| **Numéros de carte de paiement** | Les numéros de 13 à 19 chiffres, avec des espaces ou des tirets entre les groupes, qui commencent par un préfixe de réseau de cartes et dont le chiffre de contrôle est valide. | `[card]` |
| **Numéros d’identification** | Les numéros d’identification des résidents chinois dont le caractère de contrôle est valide et les numéros de sécurité sociale américains. | `[id]` |
| **Paramètres d’URL sensibles** | Les valeurs des paramètres de requête et de fragment qui portent un nom comme `code`, `key`, `sig`, `sid`, `otp`, `ticket`, `email` ou `phone`, ou dont le nom contient `token`, `secret`, `password`, `auth`, `signature`, `api_key`, `credential`, `jwt` ou `session`. Le nom d’utilisateur et le mot de passe qui précèdent l’hôte. Le nom du paramètre reste inchangé. | `[redacted]` |

Le serveur nettoie les URL associées à l’événement (`view.url`, `view.referrer`, `resource.url` et l’URL d’une
erreur), le message et la trace de pile d’une erreur et de ses causes, le nom de la vue et de l’élément cliqué, l’opération, la charge utile
et les variables GraphQL d’une requête, les en-têtes de requête et de réponse et l’objet `context`. Le serveur nettoie aussi les URL présentes dans du texte
et conserve les positions qui les suivent dans les traces de pile (`:10:5`). Il laisse `user` et `account` tels quels : ces objets contiennent les informations
que l’application a choisi d’envoyer sur une personne.

Le serveur retire ces données avant de convertir l’événement en lignes. Il calcule donc les valeurs dérivées à partir des données restantes :
`view.url_path` et `view.url_path_group` pour une URL qui contenait une adresse e-mail, ou le [problème](/fr/rum/errors) auquel une erreur appartient. Les erreurs qui
ne diffèrent que par l’adresse e-mail ou le numéro dans leur message sont regroupées dans un même problème.

<Warning>
  Les types reposent sur des formats et des contrôles, pas sur une classification des données. Le serveur traite un numéro qui ressemble à un numéro de téléphone, par exemple un numéro de commande à 11 chiffres
  commençant par `13`, comme un numéro de téléphone. En revanche, il ne reconnaît pas les noms ni les adresses saisis en texte libre. Désactivez un type s’il retire
  des données nécessaires à l’analyse et empêchez l’envoi de valeurs sensibles dans les événements dès le SDK.
</Warning>

Toute modification s’applique uniquement aux événements reçus après celle-ci. Les données déjà stockées restent inchangées. Le serveur ne nettoie pas
les segments de relecture de session : le SDK masque leur texte selon le niveau de confidentialité décrit ci-dessus.

## Vérifier avant la mise en production

<Steps>
  <Step title="Enregistrer une session de test contrôlée">
    Testez les parcours de connexion, de paiement, de gestion du profil et de recherche, ainsi que les scénarios d’erreur, avec des données hors production.
  </Step>
  <Step title="Examiner toutes les données collectées">
    Vérifiez les métadonnées de session, les noms des actions, les URL, les traces de pile des erreurs, le contexte personnalisé et la relecture du DOM.
  </Step>
  <Step title="Ajouter des sélecteurs et des exclusions">
    Bloquez les sous-arbres sensibles et excluez les routes pour lesquelles la collecte est inutile.
  </Step>
  <Step title="Répéter les vérifications après toute modification de l’interface">
    Traitez les sélecteurs de confidentialité comme des paramètres de production et vérifiez leur comportement après toute modification du balisage.
  </Step>
</Steps>
