Consultez d'abord le journal du processus. Il indique la cause d'un échec de démarrage, et le corps de l'erreur HTTP d'une requête rejetée contient un message. Le niveau de journalisation provient de `[telemetry].log_level` ou de `RUST_LOG`.

## Démarrage

| Symptôme | Cause | Correctif |
|---|---|---|
| `... password authentication failed for user` | L'utilisateur ou le mot de passe du DSN est incorrect. | Corrigez `[meta_database].dsn`. |
| `... pool timed out while waiting for an open connection` | PostgreSQL est inaccessible depuis le nœud. | Vérifiez l'hôte, le port, le pare-feu et les exigences de `sslmode`. |
| `startup_ping put: ... SignatureDoesNotMatch` | Le stockage d'objets rejette les identifiants. | Vérifiez `access_key` et `secret_key`. Définissez-les avec `MS_OBJECT_STORE_ACCESS_KEY` et `MS_OBJECT_STORE_SECRET_KEY`. |
| `startup_ping put: ... NoSuchBucket` | Le bucket n'existe pas. | Créez le bucket ou corrigez `[object_store].bucket`. |
| Lignes `Encountered transport error` répétées, puis arrêt | Le point de terminaison est inaccessible, ou aucun identifiant n'atteint le client. | Vérifiez `endpoint`, le DNS et le réseau. Les identifiants doivent provenir de `access_key` et `secret_key`. |
| `unknown field: found ...` | Une clé d'une section stricte est mal orthographiée ou non prise en charge. | Supprimez ou corrigez la clé. Voir [Configuration](/fr/configuration#ordre-de-chargement-de-la-configuration). |
| `MS_SELF_TELEMETRY_CLUSTER_TOKEN must be set when split-role self intake is enabled` | Un nœud à rôles séparés sans le rôle `intake` démarre sans le jeton partagé alors que la capture de traces ou l'auto-collecte est activée. | Définissez le même jeton sur chaque nœud. Désactiver `[telemetry.self_collect]` seul ne suffit pas, car la capture de traces est activée par défaut. |
| `open Probe CA key` | `MS_CIPHER_KEY` diffère de la clé qui a chiffré la base de données. | Restaurez la clé d'origine. Voir [Liste de contrôle de production](/fr/deployment/production-checklist). |
| `migration ... was previously applied but is missing in the resolved migrations` ou `... has been modified` | Le binaire et la base de données proviennent de versions incompatibles. | Exécutez la version correspondante, ou restaurez une sauvegarde. Voir [Mise à niveau](/fr/upgrade). |
| `address already in use` | Un autre processus utilise un port configuré. | Changez le port. |
| `profiling.port and ... are both ...` | L'écouteur pprof partage un port avec un autre écouteur. | Définissez `[profiling].port` sur un port qu'aucun autre écouteur n'utilise. |
| Un paramètre défini par variable d'environnement n'a aucun effet | Le nom de la variable contient un point, un double underscore ou une faute de frappe. | Reliez le chemin avec des underscores simples, comme dans `MS_META_DATABASE_DSN`. |

## Connexion

| Symptôme | Cause | Correctif |
|---|---|---|
| `admin@example.com` avec `admin` est rejeté | La base de données contenait déjà des utilisateurs, donc le compte racine n'a pas été recréé, ou `root_email` et `root_password` étaient vides. | Connectez-vous avec un compte existant. Définissez les deux valeurs et démarrez sur une base de données vide pour créer le compte racine. |
| L'e-mail de réinitialisation du mot de passe n'arrive jamais | SMTP ou `http.external_url` n'est pas configuré. La requête est acceptée sans rien envoyer. | Définissez `[notify.smtp].host` et `[http].external_url`. |
| Un script qui se connecte et envoie `Authorization: Bearer` reçoit `401` | La connexion définit des cookies de session pour l'interface web et ne renvoie aucun jeton. L'en-tête n'accepte que les jetons d'API. | Émettez un jeton d'API pour le script. Voir [Jetons d'API](/fr/identity/tokens). |
| L'interface web demande de se reconnecter chaque jour | Une session de connexion se termine après `[auth].session_ttl_secs` (24 heures). | Augmentez `[auth].session_ttl_secs`. |

## Envoi de données

| Symptôme | Cause | Correctif |
|---|---|---|
| `401` | Le jeton est absent ou invalide, ou l'en-tête porte un jeton de session de connexion. | Envoyez `Authorization: Bearer <token>` avec un jeton d'ingestion par défaut ou un jeton de compte de service. |
| `403` | Le jeton ne dispose pas de la permission d'écriture du signal, comme `logs.write`, par exemple un jeton client RUM envoyé vers un chemin d'ingestion. | Utilisez un jeton disposant de la permission d'écriture du signal. |
| `413` | Le corps de la requête dépasse la limite du point de terminaison : 16 MiB pour l'ingestion JSON native, 2 MiB pour les autres. | Envoyez des lots plus petits. Augmentez la limite du proxy à au moins la limite du point de terminaison. |
| `400` depuis un point de terminaison OTLP over HTTP | L'émetteur a compressé le corps. | Définissez `compression: none` sur l'exportateur OpenTelemetry Collector. |
| `404` depuis un point de terminaison OTLP over HTTP | Le point de terminaison de l'exportateur omet le chemin de base `/api`, donc les requêtes vont vers `/v1/logs`. | Utilisez `http://host:5080/api` comme point de terminaison OTLP. |
| `429` avec `Retry-After` | La limite de débit du rôle `router` pour l'organisation s'applique. | Ralentissez, ou augmentez `[router.rate_limit]`. |
| Le JSON natif signale des enregistrements `rejected` | Une valeur de champ ne correspond pas au schéma du flux, par exemple `type mismatch on field level: expected Utf8, got Number`. La réponse liste la raison par index. Les nombres avec une fraction dans un champ `int64` n'en font pas partie : le champ devient `float64`. | Envoyez le type que le flux stocke déjà pour le champ. |
| `400` avec `event #1 must be a JSON object` | Le tableau contient un élément qui n'est pas un objet JSON. La requête entière est rejetée. | Envoyez un tableau d'objets. |
| Promtail ou Grafana Alloy ne peut pas pousser | Le point de terminaison Loki ne décode que du JSON, et ces émetteurs utilisent du protobuf compressé avec snappy. | Envoyez via OpenTelemetry Collector, Vector ou Fluent Bit. |
| Les enregistrements sont acceptés mais introuvables | La requête utilise un autre nom ou type de flux, ou une plage de temps qui les exclut. | Vérifiez le nom du flux et le type de signal. Voir la section suivante pour les horodatages. |

## Données manquantes ou anormales

- **Horodatages.** `_timestamp` compte les microsecondes depuis l'époque Unix. Une valeur en secondes, millisecondes ou nanosecondes place les événements dans la mauvaise année ou dans un futur lointain, et les requêtes sur une période récente ne les renvoient pas. Omettez `_timestamp` pour utiliser l'heure de réception du serveur.
- **Plage de temps.** Une requête qui couvre une longue plage devient une tâche asynchrone. Utilisez un `timeRange` borné pour les requêtes interactives. Voir [Requête](/fr/query#plages-temporelles-et-tâches-asynchrones).
- **Conservation.** Les données plus anciennes que la conservation du flux, ou que la valeur par défaut de la plateforme dans **Paramètres → Conservation des données** pour un flux sans conservation propre, sont supprimées.
- **Type de flux.** Un flux est identifié par un nom et un type. `default` peut exister à la fois pour les logs, les métriques et les traces.

## Requêtes

| Symptôme | Cause | Correctif |
|---|---|---|
| La réponse est `202` avec un `jobId` et un chemin `monitor` | La taille estimée atteint `[querier].auto_async_threshold_rows`, donc la requête s'exécute comme une tâche de recherche asynchrone. Avec les valeurs par défaut, cela correspond à une plage d'environ 13,9 heures ou plus. | Interrogez le chemin `monitor` jusqu'à ce que la tâche soit terminée, puis récupérez son `/results`. Ou réduisez la plage de temps, ou envoyez `Prefer: respond-sync`. Voir [Requête](/fr/query#plages-temporelles-et-tâches-asynchrones). |
| Le client Flight SQL ne peut pas se connecter | `[flight_sql]` est désactivé par défaut. | Définissez `enabled = true`, exposez le port `5083` et authentifiez-vous avec un jeton d'API. |

## Opérations

| Symptôme | Cause | Correctif |
|---|---|---|
| `GET /api/v1/healthz` renvoie `503` | Le stockage objet est injoignable. Le corps de la réponse contient un `reason`. | Corrigez la connexion au stockage objet. |
| Le répertoire WAL grossit | Les vidages échouent, généralement parce que le stockage objet est injoignable. | Corrigez le stockage objet. L'intake vide ensuite l'arriéré. |
| L'intake répond `429` avec `intake buffer memory limit exceeded` | Les tampons du processus contiennent plus que `[intake].max_buffer_memory_size`, généralement parce que les vidages continuent d'échouer. | Recherchez la cause dans les lignes de journal `intake flush failed`, puis corrigez le stockage objet ou la base de données. Les lignes qui ne pourront jamais être publiées cessent d'être comptées dans la limite (voir les deux lignes suivantes). L'intake JSON natif envoie `Retry-After` avec cette réponse ; réessayez après ce délai. |
| Le journal affiche `dataset no longer exists; buffered rows discarded` | Un flux a été supprimé, ou supprimé puis recréé, alors que certaines de ses lignes étaient encore en tampon. Ces lignes n'ont nulle part où aller : l'intake les abandonne et libère leur mémoire. Le compteur `intake_flush_errors_total` enregistre chaque abandon sous l'étape `stream_gone` ou `dataset_gone`. | Rien à corriger. Renvoyez les données si elles sont importantes. |
| Les écritures répondent `503` avec `fenced by a newer writer epoch` | Un autre processus publie le même dataset avec le même `[node].id`. Le processus écarté (fenced) ne peut pas publier ses données, abandonne les lignes qu'il détient en mémoire et refuse les écritures vers ce dataset. Son WAL reste sur disque. Le compteur `intake_flush_errors_total` enregistre cet isolement sous l'étape `writer_fenced`. | Attribuez un `[node].id` unique à chaque processus et redémarrez le processus écarté. Voir [Déploiement par rôle](/fr/deployment/role-based). |
| Les rapports PDF ou PNG planifiés échouent | Chrome est absent, ou `[scheduled_reports.renderer].base_url` n'atteint pas l'interface web. | Utilisez l'image de version, qui inclut Chromium, et définissez `base_url` sur l'adresse de l'interface web que le nœud peut atteindre. |
| Les extraits d'intégration affichent un hôte erroné | `http.external_url` est vide derrière un proxy. | Définissez `[http].external_url` sur l'adresse publique et redémarrez. |
| Les requêtes répondent `503` avec `no querier node is available` | Aucun nœud avec le rôle `querier` n'a de heartbeat récent. | Démarrez un nœud `querier` et vérifiez que son `advertise_addr` est joignable depuis le routeur. Voir [Déploiement par rôle](/fr/deployment/role-based#appartenance-au-cluster). |
| Les écritures via le routeur répondent `503` avec `no intake node is available` | Aucun nœud avec le rôle `intake` n'a de heartbeat récent. | Démarrez un nœud `intake` et vérifiez son `advertise_addr`. Voir [Déploiement par rôle](/fr/deployment/role-based#appartenance-au-cluster). |
| Les requêtes répondent `503` avec `no metadata database connection` | Le nœud a attendu 10 secondes une connexion PostgreSQL sans en obtenir : PostgreSQL est surchargé ou injoignable, ou toutes les connexions de `[meta_database].max_connections` sont utilisées. | Réessayez la requête. Si le problème persiste, vérifiez d'abord la charge et la joignabilité de PostgreSQL. Si PostgreSQL est inactif, augmentez `[meta_database].max_connections` en fonction de la charge, dans la limite du `max_connections` de PostgreSQL. |
| Le port gRPC OTLP est injoignable depuis l'hôte | Le fichier Compose ne publie pas le port `4317`. | Ajoutez un mappage `4317:4317`. |
