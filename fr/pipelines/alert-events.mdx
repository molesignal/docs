Un **pipeline d’alertes** traite les événements d’alerte avant l’ouverture des incidents correspondants. Ses étapes peuvent réécrire le titre de l’incident, modifier son niveau de gravité, ajouter ou supprimer des étiquettes et des annotations, indiquer les services touchés ou ignorer l’événement pour empêcher l’ouverture d’un incident. Le [routage](/fr/alerting/routing) et les notifications utilisent ensuite l’incident tel qu’il résulte du traitement par les pipelines.

Un événement d’alerte provient de l’une des quatre sources suivantes :

| Source | Événements |
|---|---|
| **Règles d’alerte** | Une [règle d’alerte](/fr/alerting/rules) se déclenche. |
| **Sources externes** | Une [source d’alertes](/fr/alerting/sources) reçoit une alerte d’un autre système. |
| **Tests synthétiques** | Un [test synthétique](/fr/synthetics#incidents-d’alerte) échoue ou ne renvoie aucun résultat. |
| **Aucune donnée** | Une règle ouvre un [incident pour absence de données](/fr/alerting/rules#retour-à-la-normale-et-absence-de-données). |

Un incident ouvert manuellement ne passe par aucun pipeline d’alertes avant son ouverture.

Un pipeline peut aussi s’exécuter [avant une notification](#avant-une-notification) : il traite une copie de l’événement et modifie uniquement le contenu envoyé par une seule politique de notification.

## Créer un pipeline d’alertes

Ouvrez **Pipelines**, sélectionnez **Nouveau pipeline**, puis choisissez **Événements d’alerte** comme **Mode d’exécution**. Le champ **Type de signal** affiche **Événements d’alerte**, et les paramètres proposent un champ [**Ordre**](#ordre) au lieu d’une planification. Le flux comporte trois nœuds :

| Nœud | Signification |
|---|---|
| **Événements d’alerte** | Les événements d’alerte que le pipeline prend en charge. Voir [Conditions](#conditions). |
| **En cours de traitement** | Les étapes, dans leur ordre d’exécution. Voir [Étapes](#étapes). |
| **Application à l’incident** | L’incident s’ouvre à partir de l’événement dans l’état où les étapes l’ont laissé. |

**Tester** exécute les étapes sur un exemple d’événement d’alerte avant l’enregistrement. Les étapes le traitent comme un événement issu d’une règle d’alerte dont l’incident est sur le point de s’ouvrir : `%source` vaut `rule` et `%event` vaut `opened`. Pour essayer d’autres valeurs, modifiez l’**Exemple d’événement**, puis sélectionnez **Lancer le test**. Le résultat affiche l’état de l’événement après chaque étape ou indique l’étape qui l’a écarté. Le test ne stocke rien et n’effectue aucun appel externe : les étapes **Résumé par IA** et **Ajouter les résultats d’une requête** inscrivent `…` dans leurs annotations, tandis que l’étape **Appeler une API** transmet l’événement sans le modifier et affiche la mention **non appelé pendant le test**.

**Utiliser un événement d’alerte récent** donne accès aux 20 incidents les plus récents des 7 derniers jours avec l’autorisation `alerts.incidents.read`. Sélectionnez un incident pour remplir l’**Exemple d’événement** avec l’événement correspondant. Les étapes lisent la règle et la source de cet événement. L’incident apparaît dans son état enregistré, qui reflète déjà les modifications apportées par les pipelines à son ouverture.

Dans les paramètres, activez ou désactivez le pipeline à l’aide de l’interrupteur **Traiter les événements d’alerte**. Un pipeline désactivé laisse passer tous les événements d’alerte. Sélectionnez **Créer un pipeline** pour enregistrer. Toute modification enregistrée se propage à tous les nœuds en 10 secondes maximum.

## Conditions

Sélectionnez le nœud **Événements d’alerte** pour choisir les événements à traiter :

- **Sources** : **Règles d’alerte**, **Sources externes**, **Tests synthétiques** et **Aucune donnée**. Un incident pour absence de données issu d’une règle relève d’**Aucune donnée**, et non de **Règles d’alerte**. Un incident pour absence de résultats issu d’un test synthétique relève de **Tests synthétiques**.
- **Niveaux de gravité** : **Critique**, **Erreur**, **Avertissement** et **Information**.
- **Étiquettes** : **Ajouter une condition sur une étiquette** ajoute une étiquette et une valeur. L’événement doit comporter chaque étiquette avec exactement la valeur indiquée.
- **Heure** : choisissez **À tout moment**, **Uniquement pendant ces plages horaires** ou **Uniquement en dehors de ces plages horaires**. Définissez les plages hebdomadaires dans un seul fuseau horaire. Le pipeline vérifie la condition à l’ouverture de l’incident. Par exemple, écartez un type d’alerte uniquement pendant les deux heures d’exécution d’une tâche ETL nocturne.

Au-dessus des conditions, **Quand** indique à quel moment le pipeline s’exécute : **Avant l’ouverture de l’incident** (par défaut) ou [**Avant une notification**](#avant-une-notification).

Si aucune case n’est cochée dans une liste, le pipeline accepte toutes les sources ou tous les niveaux de gravité de cette liste. Sans condition, le pipeline traite tous les événements d’alerte. Il laisse passer sans modification tout événement qui ne remplit pas ses conditions.

## Ordre

Les pipelines d’alertes s’exécutent l’un après l’autre, par valeur croissante du champ **Ordre**. Les pipelines de même ordre s’exécutent dans l’ordre de leurs noms. Chaque pipeline reçoit l’événement tel que les pipelines précédents l’ont laissé et vérifie ses propres conditions sur cette version. Un pipeline qui augmente le niveau de gravité peut donc faire en sorte que l’événement remplisse les conditions d’un pipeline suivant.

## Étapes

**Ajouter une étape** propose les étapes d’analyse et de traitement des champs des autres pipelines, dont **Consulter une table d’enrichissement**, ainsi que **Filtrer les événements**, **Résumé par IA**, **Appeler une API**, **Ajouter les résultats d’une requête** et **VRL personnalisé**. Consultez [Étapes de traitement](/fr/pipelines#étapes-de-traitement). Dans un pipeline d’alertes, **Renommer selon un motif** et **Ne conserver que ces champs** s’appliquent par défaut à `labels`. Un pipeline d’alertes ne prend en charge ni l’échantillonnage ni le routage : si un pipeline contient une étape **Échantillon** ou **Acheminer vers un flux**, supprimez-la avant d’enregistrer le pipeline en tant que pipeline d’alertes.

### L’événement d’alerte

Les étapes reçoivent l’événement d’alerte au format JSON :

```json
{
  "summary": "Checkout error rate above 5%",
  "severity": "error",
  "labels": { "service": "checkout", "env": "prod", "host_name": "web-01" },
  "annotations": { "runbook": "https://wiki.example.com/checkout" },
  "affected_services": ["checkout"]
}
```

| Champ | Contenu | Valeurs qu’une étape peut définir |
|---|---|---|
| `summary` | Le titre de l’incident. | Un texte non vide. Le pipeline tronque le texte au-delà de 512 caractères. |
| `severity` | La gravité de l’incident. | `info`, `warning`, `error` ou `critical`, sans distinction de casse. Le pipeline interprète `warn` comme `warning` et `crit` comme `critical`. |
| `labels` | Les étiquettes de l’incident. | Un objet dont les valeurs sont des chaînes de caractères. Le pipeline convertit les nombres et les booléens en texte. La valeur `null` supprime l’étiquette. |
| `annotations` | Les annotations de l’incident. | Mêmes règles que pour `labels`. |
| `affected_services` | Les noms des services affectés. | Une liste de noms. Le pipeline ignore les doublons et les noms vides. |

Le pipeline ignore tout champ supplémentaire qu’une étape ajoute et conserve la valeur de tout champ qu’une étape supprime. Pour effacer les étiquettes, définissez `.labels = {}`. Une valeur qui ne respecte pas ces règles, comme un objet imbriqué dans `labels`, fait échouer le pipeline. Consultez [Devenir d’un événement](#devenir-d’un-événement).

MoleSignal conserve les étiquettes qu’il définit lui-même, comme `alert.source` et `external.kind`, quelles que soient les modifications apportées par une étape. Ces étiquettes indiquent la provenance de l’incident. Une étape peut les lire.

### Provenance de l’événement

Une étape lit la provenance de l’événement dans les métadonnées. Ces valeurs ne deviennent pas des champs de l’incident.

| Métadonnée | Valeur |
|---|---|
| `%source` | `rule`, `external`, `synthetic` ou `no_data`. |
| `%rule_id` | L’identifiant de la règle, de la source d’alerte ou du contrôle synthétique. |
| `%rule_name` | Le nom de la règle, de la source d’alerte ou du contrôle synthétique. |
| `%event` | `opened` avant l’ouverture de l’incident et `severity_changed` lorsque la source se déclenche de nouveau alors que l’incident est ouvert. Consultez [Changements de gravité](#changements-de-gravité). |

```ruby
# alerts from staging page no higher than warning
if .labels.env == "staging" && (.severity == "critical" || .severity == "error") {
  .severity = "warning"
}

# the team that owns the host, from the extend table host_owner
owner = lookup("host_owner", .labels.host_name)
if is_object(owner) {
  .labels.team = owner.team
}

# a known false alarm opens no incident
if %rule_name == "Disk inode usage" && .labels.mount == "/boot" {
  abort
}
```

L’étiquette `team` que définit la deuxième étape peut acheminer l’incident vers l’équipe correspondante. Consultez [Ordre de routage](/fr/alerting/routing#ordre-de-routage). `lookup` et `geoip_lookup` fonctionnent dans les pipelines d’alertes comme dans toute étape VRL. Consultez [Rechercher dans les tables et les adresses IP](/fr/functions#interroger-les-tables-et-géolocaliser-les-adresses-ip).

### Résumé par IA

Une étape **Résumé par IA** envoie au modèle de l’organisation l’événement d’alerte tel qu’il ressort des étapes précédentes, avec son **Instruction**. Elle écrit la réponse dans l’annotation indiquée dans **Annotation**, `ai_summary` par défaut. Voici un exemple d’instruction :

```text
Summarize this alert for the on-call engineer in two sentences: what is wrong, and what to check first.
```

- L’étape interroge le modèle une seule fois, à l’ouverture de l’incident. Un [changement de gravité](#changements-de-gravité) ne déclenche pas de nouvelle requête.
- L’étape utilise le [fournisseur de modèles](/fr/agent#configurer-un-fournisseur-de-modèles) actif qui dispose d’une clé API et dont la configuration a été mise à jour le plus récemment, avec son **Modèle par défaut**. La réponse respecte le **Nombre maximal de jetons de sortie** du fournisseur, ou une limite de 512 jetons si aucun maximum n’est défini.
- L’étape envoie au fournisseur de modèles le titre, la gravité, les étiquettes, les annotations et les services affectés de l’alerte.
- Les appels sont décomptés du [budget quotidien de jetons](/fr/agent#utilisation-et-budget) de l’organisation et apparaissent sous **Fonctions LLM** dans l’utilisation par source. `[functions].llm_eval_enabled` ne s’applique pas à ces appels.
- Si le modèle ne peut pas répondre parce qu’aucun fournisseur n’est configuré, que le budget quotidien est épuisé ou que l’appel échoue, l’étape fait échouer tout le pipeline. Le pipeline ignore alors aussi les autres modifications. Pour conserver ces modifications dans tous les cas, placez l’étape **Résumé par IA** dans un pipeline distinct qui s’exécute après les autres.

### Appeler une API

Une étape **Appeler une API** envoie l’événement d’alerte par POST à l’un des [connecteurs HTTP](/fr/connectors#destinations) de l’organisation et applique les modifications renvoyées dans la réponse. L’étape utilise l’adresse et les informations d’authentification du connecteur et applique ses contrôles sur les connexions sortantes : elle résout d’abord le nom d’hôte, se connecte uniquement à l’adresse obtenue, refuse les adresses des services de métadonnées cloud et ne suit pas les redirections.

Le corps de la requête contient l’événement tel qu’il ressort des étapes précédentes et indique sa provenance au même niveau que ses champs :

```json
{
  "summary": "Checkout error rate above 5%",
  "severity": "error",
  "priority": null,
  "urgency": null,
  "labels": { "service": "checkout" },
  "annotations": {},
  "affected_services": ["checkout"],
  "metadata": { "rule_id": "…", "rule_name": "Checkout errors", "source": "rule", "event": "opened" }
}
```

- Dans l’objet JSON renvoyé, l’étape ne retient que `summary`, `severity`, `priority`, `urgency`, `labels`, `annotations` et `affected_services`, selon les règles de [L’événement d’alerte](#l’événement-d’alerte). L’étape fusionne `labels` et `annotations` clé par clé, et `null` supprime une clé. Le service peut donc renvoyer uniquement ses ajouts. Une réponse vide ne change rien.
- L’appel dispose de 5 secondes et s’exécute une seule fois, à l’ouverture de l’incident. Un [changement de gravité](#changements-de-gravité) ne déclenche pas de nouvel appel.
- Si l’appel échoue (délai dépassé, code d’état hors de la plage 2xx, corps qui n’est pas un objet JSON ou qui dépasse 1 MiB, champ non conforme ou connecteur désactivé ou supprimé), le pipeline considère que seule cette étape n’a pas abouti. L’événement poursuit son traitement dans l’état où il se trouvait avant l’étape. Les étapes suivantes s’exécutent et le pipeline conserve les modifications précédentes. La [chronologie](#devenir-d’un-événement) et les [décomptes](#compteurs-quotidiens) indiquent la cause de l’échec.

### Ajouter les résultats d’une requête

Une étape **Ajouter les résultats d’une requête** exécute une requête qui utilise les valeurs de l’événement et écrit les lignes obtenues dans une annotation :

```sql
SELECT count(*) AS errors FROM app_logs WHERE level = 'error' AND host = '{{labels.host_name}}'
```

| Champ | Signification |
|---|---|
| **Langage** | SQL ou PromQL. PromQL interroge un flux de métriques. |
| **Type de flux**, **Flux** | Le flux que la requête interroge. L’étape ne peut pas lire `_audit`, car elle s’exécute sans bénéficier de la permission `audit.read` de quiconque. |
| **Requête** | Une seule requête, avec des paramètres de substitution. |
| **Fenêtre rétrospective (secondes)** | La durée sur laquelle porte la requête avant l’ouverture de l’incident. 300 par défaut, 86 400 au maximum. |
| **Lignes** | Le nombre de lignes à écrire dans l’annotation. 5 par défaut, 50 au maximum. |
| **Annotation** | L’annotation dans laquelle écrire les lignes, `query_result` par défaut. |

Chaque paramètre de substitution représente une valeur de l’événement : `{{labels.<key>}}`, `{{annotations.<key>}}`, `{{summary}}`, `{{severity}}`, `{{priority}}`, `{{urgency}}`, `{{rule_id}}`, `{{rule_name}}` ou `{{source}}`. Les étiquettes peuvent provenir d’autres systèmes. Placez donc chaque paramètre dans une chaîne entre guillemets dans la requête, afin que l’étape échappe sa valeur. À tout autre emplacement, l’enregistrement renvoie `400`.

- L’annotation contient une ligne par résultat : une valeur seule si le résultat n’en contient qu’une, ou plusieurs sous la forme `column=value, column=value`. Elle contient au maximum 4 000 caractères. Si la requête ne renvoie aucune ligne, l’étape n’ajoute pas l’annotation.
- La requête dispose de 10 secondes et s’exécute une seule fois, à l’ouverture de l’incident.
- Si la requête échoue ou si l’événement ne fournit aucune valeur pour un paramètre de substitution, le pipeline considère que seule cette étape n’a pas abouti, comme pour [**Appeler une API**](#appeler-une-api).

## Devenir d’un événement

Chaque pipeline qui prend en charge un événement aboutit à l’un des trois résultats suivants :

| Résultat | Cause | Effet |
|---|---|---|
| **Traité** | Toutes les étapes se sont terminées. | L’événement poursuit son parcours avec les modifications apportées par les étapes. |
| **Ignorés** | Une étape a exécuté `abort`. | Aucun incident ne s’ouvre et les pipelines suivants ne s’exécutent pas. |
| **Échec** | Une étape a échoué ou les étapes ont laissé un champ qui ne respecte pas les règles de [L’événement d’alerte](#l’événement-d’alerte). L’échec d’une étape **Appeler une API** ou **Ajouter les résultats d’une requête** compte aussi comme un échec. | Le pipeline ne conserve aucune modification, sauf si seule une étape de ce type a échoué : dans ce cas, les modifications des autres étapes restent en place. L’événement passe au pipeline suivant et l’incident s’ouvre quand même. |

La [chronologie](/fr/alerting/incidents#détails-de-l’incident) de l’incident affiche une ligne pour chaque pipeline qui a apporté une modification ou qui a échoué : **Passage par le pipeline Routage des paiements : gravité error → critical, étiquettes +team=payments**. En cas d’échec, la ligne en indique la raison. Un pipeline qui n’a rien modifié n’ajoute aucune ligne, pas plus qu’un [changement de gravité](#changements-de-gravité). Chaque ligne affiche jusqu’à 40 modifications et indique le nombre de modifications restantes. Les valeurs longues sont tronquées à 200 caractères.

Si une règle continue de se déclencher, le pipeline ignore de nouveau l’événement à chaque évaluation. La [liste des règles](/fr/alerting/rules#liste-des-règles) indique l’état **Ignorée par le pipeline**, et l’API renvoie `{"kind": "dropped"}` dans `last_state`. Le pipeline comptabilise l’événement ignoré et sa **Vue d’ensemble** indique la règle du dernier événement ignoré. Lorsqu’un pipeline ignore une alerte externe, la section [**Requêtes reçues récemment**](/fr/alerting/sources#requêtes-reçues-récemment) de la source d’alerte affiche **Ignoré** à côté du pipeline et de l’étape concernés.

## Changements de gravité

Tant qu’un incident reste ouvert, les pipelines d’alerte réévaluent sa gravité chaque fois que sa règle d’alerte se déclenche à nouveau, que sa source externe renvoie l’alerte ou que son contrôle synthétique change d’état :

- MoleSignal reconstruit l’événement comme à l’ouverture de l’incident, avec la gravité que la source signale à présent. L’événement traverse les pipelines qui le prennent en charge, sans exécuter les étapes **Résumé par IA**, **Appeler une API** et **Ajouter les résultats d’une requête**. `%event` vaut `severity_changed`.
- MoleSignal ne retient que la gravité issue des étapes et met à jour l’incident si elle diffère. Le titre, les étiquettes, les annotations et les services conservent les valeurs définies à l’ouverture de l’incident.
- Si un pipeline ignore l’événement ou échoue, rien ne change : l’incident reste ouvert et le pipeline suivant s’exécute.

Une étape qui réduit la gravité des alertes de préproduction continue donc de le faire si la règle signale ensuite une gravité supérieure. Un incident acquitté ou dont la gravité a été définie manuellement conserve sa gravité.

## Avant une notification

Réglez **Quand** sur **Avant une notification** dans le nœud **Événements d’alerte**. Le pipeline s’exécute alors sur une copie de l’événement pour chaque [politique de notification](/fr/notification-channels) concernée et à chaque envoi lié à cet événement d’alerte, y compris lors des étapes suivantes de la politique et de son escalade. Utilisez ce pipeline pour raccourcir un titre dans une politique d’envoi par SMS, ajouter une étiquette au webhook d’une équipe ou suspendre les envois d’une politique la nuit, sans modifier l’incident lui-même.

- **Politiques de notification** indique les politiques auxquelles le pipeline s’applique. Si aucune politique n’est cochée, le pipeline s’applique à toutes les politiques de l’événement d’alerte. À ce stade, la politique a déjà sélectionné l’événement tel qu’il a été reçu.
- Les autres conditions s’appliquent comme précédemment et s’évaluent sur l’événement associé à la notification : l’heure correspond à celle de l’événement et **Sources** propose aussi **Incidents ouverts manuellement**.
- Les étapes s’exécutent uniquement dans MoleSignal. Les étapes **Résumé par IA**, **Appeler une API** et **Ajouter les résultats d’une requête** ne s’exécutent qu’à l’ouverture d’un incident. Un pipeline qui inclut l’une de ces étapes renvoie `400` à ce stade.
- Le flux se termine par **Dans la notification**. La politique utilise le titre, la gravité, la priorité, l’urgence, les étiquettes, les annotations et les services issus des étapes dans ses [modèles](/fr/notification-channels#variables-de-modèle), dans le corps de ses webhooks et dans le texte par défaut. La politique détermine les destinataires à partir de l’événement tel qu’il a été reçu.
- Une étape qui exécute `abort` bloque l’envoi de cette politique. Le journal des envois affiche une entrée **Ignoré**. Le motif indique le pipeline et l’étape dans la langue par défaut de l’espace de travail (`error_code` `dropped_by_pipeline`). La chronologie de l’incident signale aussi l’envoi ignoré. Il ne s’agit pas d’un échec : la politique ne retente pas l’envoi et l’escalade liée au délai d’acquittement ne se poursuit pas.
- Si un pipeline échoue, MoleSignal écarte ses modifications et la notification part sans changement. L’échec apparaît dans les [compteurs](#compteurs-quotidiens), mais pas dans la chronologie.

En plus de `%rule_id`, `%rule_name` et `%source`, les étapes lisent `%policy_id` et `%policy_name`. `%event` vaut `triggered`, `escalated`, `acknowledged` ou `resolved`. `%rule_name` contient le nom de la règle ou, si aucune règle n’a ouvert l’incident, le titre de l’événement. **Tester** utilise les valeurs d’exemple `triggered` et `On-call alerts`.

```ruby
# on-call alerts of the staging environment go out only for what is critical
if %policy_name == "On-call alerts" && .labels.env == "staging" && .severity != "critical" {
  abort
}
```

## Compteurs quotidiens

Un pipeline d’alerte ne génère aucune exécution enregistrée. Il n’a donc pas d’historique d’exécution et l’option **Plus → Traitement rétroactif** n’est pas disponible. À la place, il comptabilise les événements du jour en cours (UTC) :

- Dans la liste, le **Statut** d’un pipeline d’alerte activé est **En attente d’événements d’alerte**, et la colonne **Dernière exécution** affiche les compteurs, par exemple **Aujourd’hui : 41 traités · 3 ignorés · 0 échec**.
- Dans la **Vue d’ensemble** du pipeline, **Traité**, **Ignorés** et **Échec** affichent les mêmes compteurs. **Ignorés** indique la règle ou la source du dernier événement ignoré, ainsi que l’heure à laquelle le pipeline l’a ignoré. **Échec** indique le motif du dernier échec.

Les compteurs repartent de zéro à minuit UTC. Ils ne comptabilisent ni les événements qui ne remplissent pas les conditions ni les passages liés à un [changement de gravité](#changements-de-gravité). L’API renvoie les compteurs dans `alert_record`. Consultez [Gérer les pipelines](/fr/api/intake/scheduled-pipelines#récupérer).

| Limite | Valeur |

| Réponse d’une étape **Appeler une API** | 1 MiB, en 5 secondes maximum |

## Créer un pipeline d’alerte via l’API

Enregistrez un pipeline d’alerte comme n’importe quel pipeline : définissez `functionSteps.mode` sur `alert` et laissez les flux et la planification vides :

```bash
curl -X POST http://localhost:5080/api/v1/scheduled_pipelines \
  -H "authorization: Bearer $MS_TOKEN" \
  -H 'content-type: application/json' \
  -d '{
    "name": "staging-alerts",
    "sourceStream": "",
    "targetStream": "",
    "cron": "",
    "enabled": true,
    "functionSteps": {
      "mode": "alert",
      "alert": {
        "sources": ["rule", "external"],
        "severities": [],
        "labels": { "env": "staging" },
        "order": 10
      },
      "steps": [
        { "transformName": "cap-severity", "kind": "vrl",
          "script": "if .severity == \"critical\" { .severity = \"warning\" }" },
        { "transformName": "summary", "kind": "ai_summary",
          "prompt": "Summarize this alert in two sentences for the on-call engineer.",
          "annotation": "ai_summary" }
      ]
    }
  }'
```

Pour un pipeline qui s’exécute avant les notifications, définissez `alert.stage` sur `notify` et, si nécessaire, indiquez les politiques dans `alert.policies` :

```json
{
  "mode": "alert",
  "alert": { "stage": "notify", "policies": ["<policy id>"], "labels": { "env": "staging" }, "order": 10 },
  "steps": [
    { "transformName": "quiet", "kind": "vrl", "script": "if .severity != \"critical\" { abort }" }
  ]
}
```

Consultez [Créer un pipeline](/fr/api/intake/create-pipeline) pour connaître tous les champs. Les [autorisations communes à tous les pipelines](/fr/pipelines#autorisations) s’appliquent aux pipelines d’alerte.
