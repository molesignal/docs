A **connecteur** est une intégration managée avec une plateforme externe. Les connecteurs fonctionnent dans deux directions :

- **Sources** : importent des données depuis un autre service et les écrivent dans un flux. MoleSignal récupère CloudWatch Logs, les topics Kafka et les objets S3 selon une planification. Amazon Data Firehose, Google Cloud Pub/Sub, Cloudflare Logpush et Heroku poussent vers MoleSignal ; Firehose transporte aussi les métriques CloudWatch.
- **Destinations** : reçoivent la sortie d'un [pipeline planifié](/fr/pipelines#destinations-et-envoi-via-les-connecteurs) : Amazon S3 et le stockage compatible S3, Apache Kafka et tout endpoint HTTP.

| Type | Connecteur | Direction | Authentification |
|---|---|---|---|
| `aws_cloudwatch_logs` | AWS CloudWatch Logs | Source, récupérée toutes les 30 secondes | [Identifiants AWS](#authentification-aws) |
| `kafka_source` | Topic Kafka | Source, récupérée toutes les 30 secondes | Aucune, SASL ou un certificat client |
| `s3_source` | Objets S3 | Source, récupérée toutes les 30 secondes | Identifiants AWS |
| `gcp_pubsub_pull` | Abonnement Google Cloud Pub/Sub | Source, récupérée toutes les 30 secondes | Clé de compte de service |
| `aws_cloudwatch_metrics`, `azure_monitor_metrics`, `gcp_monitoring_metrics`, `aliyun_cms_metrics`, `tencent_monitor_metrics`, `huawei_ces_metrics` | [Métriques cloud](#métriques-cloud) | Source, récupérée à chaque période | Les identifiants du cloud |
| `aws_kinesis_firehose` | Amazon Data Firehose | Source, poussée | [Jeton de push](#sources-push) |
| `gcp_pubsub_push` | Push Google Cloud Pub/Sub | Source, poussée | Jeton de push, éventuellement avec le jeton OIDC de l'abonnement |
| `cloud_events` | Bus d'événements cloud | Source, poussée | Jeton de push |
| `cloudflare_logpush` | Cloudflare Logpush | Source, poussée | Jeton de push |
| `heroku_drain` | Drain de logs Heroku | Source, poussée | Jeton de push |
| `s3` | Amazon S3 | Destination | Identifiants AWS |
| `kafka` | Apache Kafka | Destination | Aucune, SASL ou un certificat client |
| `http` | HTTP / Webhook | Destination | Aucune, un jeton bearer, une authentification Basic, un en-tête personnalisé ou une signature HMAC |

## Créer un connecteur

<Steps>
  <Step title="Ouvrir les connecteurs">
    Accédez à **Pipelines → Connecteurs**. La page liste les **Sources** et les **Destinations**.
  </Step>
  <Step title="Choisir le type">
    Cliquez sur **Nouveau connecteur** et choisissez la cible à connecter.
  </Step>
  <Step title="Renseigner les paramètres">
    Saisissez un **Nom** unique dans l'organisation, renseignez la source de lecture ou la cible de livraison du connecteur, puis choisissez l'**Authentification**.
  </Step>
  <Step title="Tester et créer">
    Cliquez sur **Tester la connexion** pour essayer les paramètres avant de les enregistrer, puis cliquez sur **Créer le connecteur**. Une source poussée n'a rien à connecter et ne propose pas de test.
  </Step>
</Steps>

Via l'API, un connecteur est un `name`, un `kind` et un `configJson` dont les clés dépendent du type. `auth` dans `configJson` nomme le mode d'authentification, et chaque mode utilise ses propres clés. Les paramètres qui ne peuvent pas fonctionner renvoient `400` lors de l'enregistrement : une clé obligatoire manquante, la moitié d'une paire d'identifiants, ou une clé que l'`auth` choisie n'utilise pas.

```bash
curl -X POST http://localhost:5080/api/v1/connectors \
  -H "authorization: Bearer $MS_TOKEN" \
  -H 'content-type: application/json' \
  -d '{
        "name": "archive",
        "kind": "s3",
        "configJson": {
          "bucket": "acme-logs",
          "region": "eu-west-1",
          "prefix": "pipelines/checkout/",
          "auth": "assume_role",
          "roleArn": "arn:aws:iam::123456789012:role/molesignal-delivery"
        }
      }'
```

## Secrets

Ces clés de `configJson` contiennent des secrets :

| Type | Clés secrètes |
|---|---|
| `s3`, `aws_cloudwatch_logs` | `accessKey`, `secretKey`, `sessionToken` |
| `aws_kinesis_firehose`, `gcp_pubsub_push`, `cloud_events`, `cloudflare_logpush`, `heroku_drain` | `pushToken` |
| `aws_cloudwatch_metrics` | `accessKey`, `secretKey`, `sessionToken` |
| `azure_monitor_metrics` | `clientSecret` |
| `gcp_monitoring_metrics`, `gcp_pubsub_pull` | `serviceAccountKey` |
| `aliyun_cms_metrics`, `tencent_monitor_metrics`, `huawei_ces_metrics` | `accessKey`, `secretKey` |
| `kafka` | `saslPassword`, `tlsClientKey` |
| `http` | `url`, `bearerToken`, `basicPassword`, `headerValue`, `hmacSecret` |

Un secret ne sort jamais par l'API. Une réponse affiche `***` à sa place et nomme les secrets qui détiennent une valeur dans `secretKeys` :

```json
{
  "kind": "kafka",
  "configJson": {
    "brokers": "b-1.example.com:9096",
    "topic": "logs",
    "tls": true,
    "auth": "sasl_scram_sha_512",
    "saslUsername": "molesignal",
    "saslPassword": "***"
  },
  "secretKeys": ["saslPassword"]
}
```

- Une mise à jour qui renvoie `***` conserve la valeur stockée : un connecteur peut donc être renommé, désactivé ou redirigé sans saisir à nouveau ses identifiants. Dans l'interface, un secret enregistré laissé vide conserve sa valeur.
- Un secret absent d'une mise à jour est supprimé.
- Une mise à jour qui change le `kind` ne conserve aucun des secrets stockés.

MoleSignal scelle les secrets avec la clé racine issue de `MS_CIPHER_KEY` (AES-256-GCM), séparément des autres paramètres, et ne stocke aucun secret en clair. Une source poussée est retrouvée par le SHA-256 de son jeton. `molesignal rewrap-kek` rescelle les secrets des connecteurs avec les autres secrets lorsque la clé racine est renouvelée. Voir [Checklist de production](/fr/deployment/production-checklist).

## Sources

### Sources push

Les cinq sources push partagent un modèle : créez un connecteur avec un **`pushToken`** et un **`targetStream`**, puis pointez la plateforme vers le point de terminaison correspondant. Ces points de terminaison n’utilisent pas le JWT. La requête s’authentifie avec le jeton push, fourni de la manière autorisée par la plateforme :

| Méthode | Utilisé par |
|---|---|
| En-tête `X-Connector-Token` | Plateformes avec en-têtes configurables, comme Cloudflare |
| En-tête `X-Amz-Firehose-Access-Key` | Amazon Data Firehose, qui l’envoie automatiquement |
| En-tête `X-EventBridge-Signature-Token` | Alibaba Cloud EventBridge |
| Paramètre de requête `?token=` | Plateformes qui ne peuvent pas définir d’en-têtes, comme Heroku et Pub/Sub |
| Mot de passe de `Authorization: Basic` | Plateformes qui placent les identifiants dans l’adresse |

L’interface génère le jeton lorsqu’elle crée le connecteur et l’affiche une seule fois, avec le point de terminaison à fournir à la plateforme. Le jeton ne peut pas être relu. **Générer un nouveau jeton** le remplace lorsque le connecteur est enregistré. Via l’API, fournissez un `pushToken` d’au moins 16 caractères. Un jeton ouvre un connecteur d’un type : un jeton déjà utilisé répond `409`. Une requête avec un jeton manquant ou inconnu, ou pour un connecteur désactivé, répond `401`. Un connecteur sans jeton n’accepte rien. Un nœud conserve pendant 30 secondes un connecteur qu’il a résolu, de sorte que la désactivation d’un connecteur ou le remplacement de son jeton prend effet dans ce délai.

Les corps envoyés avec `Content-Encoding: gzip` sont décompressés automatiquement. Un corps Firehose peut atteindre 64 MiB, tout autre 16 MiB, également comptés après décompression. Les événements passent par le même chemin d’ingestion que tout le reste : le schéma à l’écriture, les [pipelines](/fr/pipelines) et le [masquage](/fr/security) s’appliquent tous.

<Tabs>
  <Tab title="Amazon Data Firehose">
    Créez le connecteur avec `kind: "aws_kinesis_firehose"`, puis choisissez la destination **Point de terminaison HTTP** pour le flux Firehose :

    - **URL du point de terminaison HTTP** : `https://molesignal.example.com/api/v1/_kinesis_firehose`
    - **Clé d’accès** : le jeton push. Firehose l’envoie comme `X-Amz-Firehose-Access-Key`.

    Firehose ne livre qu’en HTTPS sur le port 443 avec un certificat approuvé publiquement, donc un déploiement sur un réseau privé nécessite un point d’entrée public, voir [Accès public](/fr/public-access). Maintenez le tampon du flux entre 1 et 4 MiB.

    MoleSignal lit chaque enregistrement individuellement, selon son contenu :

    | Enregistrement | Devient |
    |---|---|
    | Un message d’abonnement CloudWatch Logs, compressé avec gzip comme l’envoie le filtre d’abonnement | Un événement de journal par entrée de `logEvents`, à l’heure propre de l’entrée, avec `message`, `log_group`, `log_stream`, `account_id`, `region`, `event_id` et `source: "cloudwatch"`. Le contrôle de santé que l’abonnement envoie lors de sa création est ignoré. |
    | Un enregistrement CloudWatch Metric Streams au format de sortie JSON, OpenTelemetry 1.0 ou OpenTelemetry 0.7 | Des échantillons de métrique dans le flux de métriques, voir ci-dessous. |
    | Tout autre texte | Un événement de journal par ligne : un objet JSON fournit les champs, le texte brut va dans `message`. |

    Un flux de métriques envoie un agrégat par métrique et par minute. Chaque statistique devient un échantillon de jauge nommé `aws_<namespace>_<metric>_<statistic>`, comme les nomme yet-another-cloudwatch-exporter : `aws_ec2_cpuutilization_average`, `aws_ec2_cpuutilization_maximum`, `aws_applicationelb_request_count_sum`. L’espace de noms perd son préfixe `AWS/`, et le nom de la métrique se découpe en mots là où une lettre minuscule rencontre une majuscule. Les statistiques sont `average` (la somme sur le nombre d’échantillons), `sum`, `sample_count`, `minimum`, `maximum`, et tout centile ajouté par le flux, comme `p99` ou `p99_9`. Les libellés sont `account_id`, `region`, et un `dimension_<Name>` par dimension, comme `dimension_InstanceId` ; `metric_unit` conserve l’unité.

    ```promql
    max by (dimension_InstanceId) (aws_ec2_cpuutilization_average)
    ```

    `X-Amz-Firehose-Common-Attributes`, défini comme paramètre du flux, ajoute ses clés à chaque événement et échantillon ; un champ déjà présent dans l’enregistrement l’emporte. `X-Amz-Firehose-Source-Arn` fournit la `region` des événements CloudWatch Logs, qui n’en portent pas.

    La réponse suit la spécification de livraison Firehose : `application/json` avec le `requestId` de la requête, un `timestamp` et un `errorMessage` en cas d’échec. Les enregistrements qui ne peuvent pas être lus sont omis, et le reste de la requête est tout de même écrit avec `200`. Une écriture qui échoue momentanément répond `429` ou `5xx`, que Firehose réessaie. Un corps de plus de 64 MiB répond `413`, que Firehose ne réessaie pas et ne sauvegarde pas. Une livraison réessayée dans les 30 minutes suivant son écriture, avec le même `X-Amz-Firehose-Request-Id`, reçoit une réponse `200` sans être écrite de nouveau.
  </Tab>
  <Tab title="Google Cloud Pub/Sub">
    Créez le connecteur avec `kind: "gcp_pubsub_push"`. Acheminez les journaux vers un topic Pub/Sub avec un récepteur Log Router, puis créez un abonnement push sur le topic. Pub/Sub ne peut pas définir d’en-têtes personnalisés, donc le jeton passe dans l’URL :

    ```bash
    gcloud pubsub subscriptions create molesignal-push --topic=molesignal-logs --push-endpoint="https://molesignal.example.com/api/v1/_gcp_pubsub?token=<pushToken>"
    ```

    Pour vérifier aussi le jeton OIDC de l’abonnement, définissez `oidcServiceAccount` sur le connecteur avec l’adresse e-mail d’un compte de service et créez l’abonnement avec `--push-auth-service-account=<email>`. MoleSignal vérifie alors le jeton auprès des clés de Google et n’accepte que ce compte de service. Définissez `oidcAudience` pour vérifier aussi l’audience, et passez la même valeur à `--push-auth-token-audience`.

    Chaque message constitue une requête. Le corps enveloppé et la charge utile non enveloppée sont acceptés. Une `LogEntry` Cloud Logging devient un événement de journal :

    | `LogEntry` | Événement |
    |---|---|
    | `jsonPayload` | Ses champs |
    | `textPayload` | `message` |
    | `protoPayload` (journaux d’audit) | `proto_payload`, avec `method_name`, `service_name` et `principal_email` extraits |
    | `severity` | `level`, en minuscules |
    | `logName`, `resource.type`, `insertId` | `log_name`, `resource_type`, `insert_id` |
    | `resource.labels`, `labels` | Champs sous leurs propres noms |
    | `trace`, `spanId` | `trace_id` sans le préfixe `projects/<id>/traces/`, `span_id` |
    | `httpRequest` | `http_request` |
    | `timestamp` | L’heure de l’événement ; `receiveTimestamp` ou l’heure de publication lorsqu’elle manque |

    Toute autre donnée de message devient un événement, les champs d’un objet JSON ou le texte dans `message`. Le point de terminaison répond `204 No Content`, que Pub/Sub considère comme un accusé de réception. Un message qui ne peut pas être lu est acquitté et omis ; une écriture qui échoue momentanément ne l’est pas, donc Pub/Sub le livre de nouveau. Un message livré de nouveau dans les 30 minutes suivant son écriture est acquitté sans être écrit de nouveau.
  </Tab>
  <Tab title="Bus d’événements cloud">
    Créez le connecteur avec `kind: "cloud_events"`, puis pointez le bus d’événements vers `https://molesignal.example.com/api/v1/_cloud_events` :

    | Expéditeur | Configuration |
    |---|---|
    | Amazon EventBridge | Une destination API avec une connexion **Clé API** ; le nom de l’en-tête est `X-Connector-Token` et sa valeur le jeton push. |
    | Azure Event Grid | Un abonnement webhook dont le point de terminaison se termine par `?token=<pushToken>`. La poignée de main de validation, et la poignée de main `OPTIONS` du schéma CloudEvents, sont traitées automatiquement. |
    | Alibaba Cloud EventBridge | Une cible HTTPS avec le jeton push comme jeton, envoyé comme `X-EventBridge-Signature-Token`. |
    | Huawei Cloud EventGrid | Une cible webhook avec l’en-tête `X-Connector-Token`. |
    | Autres expéditeurs CloudEvents | L’une des méthodes de jeton ci-dessus. Un expéditeur qui ne peut placer les identifiants que dans l’adresse, comme `https://user:<pushToken>@host/...`, est aussi accepté. |

    Un corps contient un événement ou un tableau d’événements, en CloudEvents 1.0 en mode structuré ou binaire, en événements Amazon EventBridge ou au schéma Event Grid. Chaque événement devient un événement de journal dans `targetStream` (par défaut `cloud_events`) :

    | Champ | Provenance |
    |---|---|
    | `event_id`, `event_source`, `event_type`, `event_subject` | CloudEvents `id`, `source`, `type`, `subject` ; EventBridge `id`, `source`, `detail-type` ; Event Grid `id`, `topic`, `eventType`, `subject` |
    | `account_id`, `region` | EventBridge `account`, `region` ; Alibaba Cloud `aliyunaccountid`, `aliyunregionid` ; l’abonnement d’un topic Event Grid |
    | `resources` | EventBridge `resources` |
    | `data` | La charge utile comme un champ JSON ; une charge utile texte va dans `message` |
    | `event_format` | `cloudevents`, `eventbridge` ou `event_grid` |

    Les attributs d’extension conservent leurs noms. L’heure propre de l’événement est son heure. Tout autre objet JSON devient un événement avec ses champs tels quels. Un événement livré de nouveau dans les 30 minutes, avec la même source et le même id, n’est pas écrit deux fois. Le point de terminaison répond `200`, ou `400` pour un corps qui n’est pas du JSON.
  </Tab>
  <Tab title="Cloudflare Logpush">
    Créez le connecteur avec `kind: "cloudflare_logpush"`, puis créez une tâche Logpush avec une destination HTTP. Cloudflare transforme un paramètre de requête `header_` en en-tête de requête, donc le jeton passe dans `X-Connector-Token` :

    ```text
    https://molesignal.example.com/api/v1/_cloudflare?header_X-Connector-Token=<pushToken>
    ```

    Cloudflare envoie du NDJSON compressé en gzip, et chaque ligne devient un événement. Le point de terminaison répond `204 No Content`.
  </Tab>
  <Tab title="Heroku">
    Créez le connecteur avec `kind: "heroku_drain"`, puis ajoutez le drain. Heroku ne peut pas définir d’en-têtes personnalisés, donc le jeton passe dans l’URL :

    ```bash
    heroku drains:add "https://molesignal.example.com/api/v1/_heroku?token=<pushToken>"
    ```

    Chaque ligne de journal devient un événement avec `message` et `source: "heroku"`. Le point de terminaison répond `204 No Content`.
  </Tab>
</Tabs>

<Tip>
  Le `targetStream` est créé à la première livraison, et le schéma évolue à mesure que de nouveaux champs apparaissent, comme pour tout autre flux. Omettez `targetStream` pour revenir à une valeur par défaut propre à la source : `kinesis`, `gcp`, `cloud_events`, `cloudflare` ou `heroku`. Un connecteur Firehose écrit les échantillons de métrique dans `metricsStream`, `cloudwatch` par défaut.
</Tip>

### CloudWatch Logs

CloudWatch Logs est une source **pull** : MoleSignal appelle `FilterLogEvents` toutes les 30 secondes au lieu de recevoir un push. La première exécution lit les 5 dernières minutes. Chaque exécution suivante reprend là où la dernière exécution réussie s’est arrêtée, de sorte que les événements qui n’ont pas pu être lus ou écrits sont relus à l’exécution suivante.

```bash
curl -X POST http://localhost:5080/api/v1/connectors \
  -H "authorization: Bearer $MS_TOKEN" \
  -H 'content-type: application/json' \
  -d '{
        "name": "cw-prod",
        "kind": "aws_cloudwatch_logs",
        "configJson": {
          "region": "ap-southeast-1",
          "logGroup": "/aws/lambda/checkout",
          "auth": "node_role",
          "targetStream": "cloudwatch"
        }
      }'
```

| Champ | Remarques |
|---|---|
| `region` / `logGroup` | Requis. La région CloudWatch et le groupe de journaux à lire. |
| `auth` et ses clés | Les identifiants, qui nécessitent `logs:FilterLogEvents` sur le groupe de journaux. Voir [Authentification AWS](#authentification-aws). |
| `targetStream` | Flux de destination. Par défaut `default`. |

Un seul nœud interroge un connecteur à la fois. Les nœuds `alert` se répartissent les connecteurs, et un nœud revendique un connecteur avant de l’interroger. Voir [Répartition du travail entre les nœuds d’alerte](/fr/deployment/role-based#répartition-des-tâches-entre-les-nœuds-d’alerte). Chaque événement devient un journal avec `message`, `log_stream` et `log_group`. Un connecteur désactivé n’est pas interrogé.

### Topics Kafka

Un connecteur `kafka_source` lit un topic toutes les 30 secondes et reprend là où la dernière lecture écrite s’est arrêtée. Il prend les partitions par affectation, pas en tant que membre d’un groupe de consommateurs, et conserve ses offsets dans MoleSignal, donc il ne nécessite que l’autorisation de lire le topic, et aucun groupe de consommateurs n’apparaît sur le cluster.

```bash
curl -X POST http://localhost:5080/api/v1/connectors \
  -H "authorization: Bearer $MS_TOKEN" \
  -H 'content-type: application/json' \
  -d '{
        "name": "orders",
        "kind": "kafka_source",
        "configJson": {
          "brokers": "b-1.example.com:9096,b-2.example.com:9096",
          "topic": "orders",
          "tls": true,
          "auth": "sasl_scram_sha_512",
          "saslUsername": "molesignal",
          "saslPassword": "<password>",
          "targetStream": "orders",
          "startFrom": "latest"
        }
      }'
```

| Champ | Remarques |
|---|---|
| `brokers`, `topic`, `tls`, `tlsCaCert`, `auth` et ses clés | Comme pour une [destination Kafka](#apache-kafka). |
| `targetStream` | Flux de destination. Par défaut `default`. |
| `messageFormat` | `json`, par défaut, ou `azure_records` pour ce qu’Azure Monitor exporte vers un event hub, voir ci-dessous. Interface : **Format du message**. |
| `startFrom` | Où commence la première lecture : `latest`, par défaut, pour ce qui arrive à partir de maintenant, ou `earliest` pour tout ce que les brokers conservent. Une partition ajoutée plus tard est lue depuis son début. Interface : **Commencer à partir de**. |

- Un message dont la valeur est un objet JSON fournit les champs du journal. Toute autre valeur devient son `message`. Chaque journal possède aussi `kafka_topic`, `kafka_partition`, `kafka_offset`, `kafka_key` lorsque le message a une clé, et `source`. Son heure est l’horodatage du message.
- Une lecture prend jusqu’à 10 000 messages ou 32 MiB, et la suivante enchaîne aussitôt tant qu’il en reste, pendant au plus 2 minutes dans un pull.
- Les offsets n’avancent qu’une fois les journaux écrits. Une lecture ou une écriture qui échoue est réessayée au même endroit 30 secondes plus tard, donc un message peut être écrit deux fois mais pas perdu. Les offsets que les brokers ont expirés reprennent à partir du plus ancien message qu’ils conservent encore.
- Changer le `topic` repart de `startFrom`, car les offsets appartiennent au topic.

Les paramètres de diagnostic Azure, l’exportation de données Log Analytics et les règles de collecte de données exportent vers Azure Event Hubs, qu’une source Kafka lit via le point de terminaison Kafka du hub : `brokers` `<namespace>.servicebus.windows.net:9093`, `topic` l’event hub, `tls` activé, `auth: sasl_plain` avec le nom d’utilisateur `$ConnectionString` et la chaîne de connexion comme mot de passe. Le niveau Basic n’a pas de point de terminaison Kafka. Avec `messageFormat: azure_records`, chaque message `{"records": [...]}` est dépaqueté : un enregistrement de journal devient un événement de journal à son `time`, et un enregistrement de métrique devient un échantillon par statistique dans le `metricsStream` du connecteur (par défaut `default`), nommé comme les [métriques Azure Monitor](#métriques-cloud).

### Objets S3

Un connecteur `s3_source` liste un bucket toutes les 30 secondes et lit les objets qu’il n’a pas lus, du plus ancien au plus récent, depuis AWS S3 ou un stockage compatible S3.

```bash
curl -X POST http://localhost:5080/api/v1/connectors \
  -H "authorization: Bearer $MS_TOKEN" \
  -H 'content-type: application/json' \
  -d '{
        "name": "elb-logs",
        "kind": "s3_source",
        "configJson": {
          "bucket": "acme-logs",
          "region": "us-east-1",
          "prefix": "AWSLogs/123456789012/",
          "auth": "node_role",
          "targetStream": "elb",
          "startFrom": "latest"
        }
      }'
```

| Champ | Remarques |
|---|---|
| `bucket`, `region`, `endpoint`, `virtualHostedStyle`, `auth` et ses clés | Comme pour une [destination S3](#amazon-s3). Les identifiants nécessitent `s3:ListBucket` sur le bucket et `s3:GetObject` sur les objets. |
| `prefix` | Seuls les objets sous ce préfixe sont lus. Chaque pull le liste en entier, donc donnez à une source son propre préfixe. |
| `targetStream` | Flux de destination. Par défaut `default`. |
| `startFrom` | Où commence la première lecture : `latest`, par défaut, pour les objets qui apparaissent à partir de maintenant et dans les 5 minutes précédentes, ou `earliest` pour tout ce qui se trouve sous le préfixe. Interface : **Commencer à partir de**. |

- Un objet est lu par lignes. Une ligne qui est un objet JSON fournit les champs d’un journal, une ligne qui ne contient que `Records`, comme l’écrit CloudTrail, donne un journal par enregistrement, et toute autre ligne devient un `message`. Les objets `.gz` et `.zst` sont décompressés d’après leur nom. Chaque journal possède aussi `s3_bucket`, `s3_key` et `source`. Son heure est celle de la dernière modification de l’objet.
- Un pull lit jusqu’à 100 objets ou jusqu’à 50 000 journaux, et le suivant enchaîne aussitôt tant qu’il en reste, pendant au plus 2 minutes.
- L’état de lecture n’avance qu’une fois les journaux écrits. Un objet qui ne peut pas être récupéré arrête le pull à cet endroit et est réessayé 30 secondes plus tard, donc un journal peut être écrit deux fois mais pas perdu.
- Un objet qui ne peut pas être lu est ignoré et signalé sur le connecteur, car le réessayer bloquerait tout ce qui suit. Il s’agit d’un objet corrompu, de plus de 256 MiB, de plus de 512 MiB une fois décompressé, de plus d’un million de journaux, ou comportant une ligne de plus de 64 MiB.
- Un objet est reconnu par sa clé et son heure de modification, avec une marge de 5 minutes. Un objet réécrit sous la même clé dans cette marge n’est pas relu, et un objet dont l’heure de modification est de plus de 5 minutes antérieure au plus récent objet lu n’est pas lu du tout. S3 date un envoi multipart à partir de son début, donc un envoi plus lent que cela n’est pas lu.

### Abonnements Google Cloud Pub/Sub

Un connecteur `gcp_pubsub_pull` lit un abonnement Pub/Sub toutes les 30 secondes, jusqu’à 1 000 messages par requête et enchaîne aussitôt tant qu’il en reste, et n’accuse réception des messages qu’une fois ceux-ci écrits. Ce qui n’est pas écrit est livré de nouveau à l’expiration de son délai d’accusé de réception, donc un message peut être écrit deux fois mais pas perdu. Il convient mieux à de plus grands volumes de journaux qu’un [abonnement push](#sources-push), qui envoie un message par requête.

| Champ | Remarques |
|---|---|
| `serviceAccountKey` | Le fichier de clé JSON d’un compte de service disposant de `roles/pubsub.subscriber` sur l’abonnement. |
| `subscription` | `projects/<project>/subscriptions/<name>`, ou le nom d’un abonnement dans le projet de la clé. Donnez-lui un délai d’accusé de réception de 60 secondes ou plus. |
| `targetStream` | Flux de destination. Par défaut `default`. |

Chaque message est lu comme un message poussé : une `LogEntry` Cloud Logging avec le mappage de l’onglet push, tout autre objet JSON comme ses champs, tout le reste comme `message`. **Tester la connexion** vérifie si la clé peut consommer l’abonnement, sans prendre de message.

### Déroulement d’un pull

La page du connecteur indique quand une source a reçu pour la dernière fois. Une source dont la dernière lecture a échoué affiche un avertissement à côté, avec la raison dans son infobulle et dans les paramètres du connecteur, et ce que la source a ignoré en dernier y est aussi indiqué. Via l’API, `readState` contient `lastError` et `lastWarning`, chacun avec `atTime` et `text`, ainsi que `position`, où il en est. L’enregistrement d’un connecteur conserve sa position.

## Destinations

Une destination reçoit chaque événement qui traverse les étapes d'un pipeline planifié. Ajoutez le connecteur aux **Destinations** du flux avec **Ajouter une destination → Connecteur**. Une livraison qui échoue est réessayée pendant l'exécution, et les événements que le connecteur ne prend toujours pas partent vers le flux de lettres mortes. Voir [Nouvelles tentatives et lettres mortes](/fr/pipelines#nouvelles-tentatives-et-rejets).

Une destination désactivée ne reçoit rien. Chaque exécution ignore le connecteur et le nomme dans le `warning` de l'exécution. Les événements ignorés ne comptent pas comme des échecs, ne deviennent pas des lettres mortes et ne sont pas envoyés lorsque le connecteur est réactivé. Dans l'éditeur, un connecteur désactivé affiche **Désactivé**.

| Type | Charge utile |
|---|---|
| `s3` | Un objet JSON Lines par lot, `PUT` vers `s3://<bucket>/<prefix><id>.jsonl`. |
| `kafka` | Un message par événement sur le topic, avec l'événement comme charge utile JSON. |
| `http` | Le lot en une requête, ou en plusieurs lorsqu'il est volumineux, en NDJSON ou en un tableau JSON. |

### HTTP / Webhook

| Champ | Remarques |
|---|---|
| `url` | Obligatoire. Une URL absolue `http://` ou `https://`. Une URL porte souvent un identifiant, comme une clé dans le chemin ou la requête, elle est donc conservée comme secret. Les réponses n'affichent que `urlOrigin`, le schéma, l'hôte et le port. Un nom d'utilisateur et un mot de passe dans l'URL sont refusés : utilisez `basic`. |
| `method` | `post` (par défaut) ou `put`. |
| `format` | `ndjson` (par défaut) envoie un événement par ligne en `application/x-ndjson`. `json` envoie un tableau JSON en `application/json`. |

| `auth` | Interface | Clés | Requête |
|---|---|---|---|
| `none` | **Aucun** | | Aucun identifiant. |
| `bearer` | **Jeton Bearer** | `bearerToken` | `Authorization: Bearer <token>` |
| `basic` | **Authentification de base** | `basicUsername`, `basicPassword` | Autorisation HTTP Basic. À utiliser sur `https`. |
| `header` | **En-tête personnalisé** | `headerName`, `headerValue` | La valeur dans l'en-tête nommé, par exemple `X-API-Key` ou `DD-API-KEY`. |
| `hmac` | **Signature HMAC** | `hmacSecret` | Une signature du corps. Le secret doit contenir au moins 16 caractères. |

Un en-tête personnalisé ne peut pas être l'un de ceux que la livraison définit elle-même : `Host`, `Content-Type`, `Content-Length`, `Content-Encoding`, `Transfer-Encoding`, `Connection`, `X-MoleSignal-Timestamp` ou `X-MoleSignal-Sign`.

Une livraison suit ces règles :

- Un lot supérieur à 4 MiB est découpé en plusieurs requêtes. Un événement plus volumineux part dans une requête à lui seul.
- Tout statut `2xx` compte comme livré. Tout autre statut fait échouer la livraison, et une redirection aussi : les redirections ne sont pas suivies.
- Une requête expire au bout de 30 secondes.
- MoleSignal résout l'hôte avant la requête et se connecte uniquement aux adresses résolues. Une adresse sur laquelle répondent des services de métadonnées cloud est refusée, qu'elle apparaisse dans l'URL ou qu'elle vienne du DNS : `169.254.0.0/16`, `fe80::/10`, `fd00:ec2::254` et `100.100.100.200`. Les autres adresses privées sont autorisées.

#### Vérifier une signature HMAC

Avec `hmac`, chaque requête porte deux en-têtes :

| En-tête | Contenu |
|---|---|
| `X-MoleSignal-Timestamp` | L'heure de la requête en secondes Unix. |
| `X-MoleSignal-Sign` | `sha256=<hex>`, le HMAC-SHA256 de `<timestamp>.<body>` avec le secret partagé. |

Pour vérifier une requête, calculez le HMAC-SHA256 de l'horodatage, d'un `.` et des octets bruts du corps avec le même secret, puis comparez le résultat à la signature en temps constant. Refusez un horodatage vieux de plus de quelques minutes, afin qu'une requête capturée ne puisse pas être renvoyée plus tard.

```python
import hashlib
import hmac
import time


def verify(secret: bytes, timestamp: str, signature: str, body: bytes, tolerance: int = 300) -> bool:
    if abs(time.time() - int(timestamp)) > tolerance:
        return False
    signed = timestamp.encode() + b"." + body
    expected = "sha256=" + hmac.new(secret, signed, hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, signature)
```

## Authentification AWS

S3 et CloudWatch Logs s’authentifient auprès d’AWS de cinq façons :

| `auth` | Interface | Clés | Identifiants |
|---|---|---|---|
| `access_key` | **Clé d’accès** | `accessKey`, `secretKey` | Clé de longue durée d’un utilisateur IAM. |
| `temporary_key` | **Clé temporaire** | `accessKey`, `secretKey`, `sessionToken` | Clé de courte durée issue d’AWS STS, valable uniquement avec son jeton de session. Remplacez-la avant son expiration. |
| `node_role` | **Identité du nœud** | | Identité du nœud sur lequel MoleSignal s’exécute. Aucune clé n’est stockée. |
| `assume_role` | **Endosser un rôle** | `roleArn`, éventuellement `accessKey` et `secretKey` | Rôle endossé via AWS STS avec l’ID externe de l’organisation. |
| `web_identity` | **Identité web** | `roleArn` | Rôle endossé avec le jeton d’identité web du nœud. |

Sans `auth`, ce sont les clés stockées qui décident : une clé d’accès correspond à `access_key`, un `roleArn` à `assume_role`, et ni l’un ni l’autre à `node_role`. Un `roleArn` a la forme `arn:aws:iam::<account>:role/<name>`.

### Identité du nœud

`node_role` utilise l’identité que les SDK AWS trouvent sur le nœud : les rôles IAM EKS pour les comptes de service (IRSA) ou EKS Pod Identity, un rôle de tâche ECS, ou un profil d’instance EC2. Une clé statique dans l’environnement du nœud, telle que `AWS_ACCESS_KEY_ID`, n’est jamais utilisée pour les connecteurs.

<Warning>
  L’identité du nœud et son jeton d’identité web appartiennent au déploiement. Chaque organisation du déploiement peut choisir `node_role` et `web_identity` ; tout ce que l’identité du nœud peut atteindre, ainsi que chaque rôle qui fait confiance au jeton du nœud, est donc accessible aux connecteurs de toutes les organisations. Accordez-leur uniquement les accès que toutes les organisations peuvent avoir.
</Warning>

### Endosser un rôle

`assume_role` demande à AWS STS une clé du rôle valable une heure et renouvelle la clé 5 minutes avant son expiration. Les identifiants de base qui endossent le rôle sont ceux de l’identité du nœud. Pour un déploiement qui ne s’exécute pas sur AWS, sélectionnez **Endosser le rôle avec une clé d’accès plutôt qu’avec l’identité du nœud** et saisissez la clé d’un utilisateur IAM.

Chaque organisation endosse des rôles avec son propre ID externe, `molesignal-<organization ID>`, qui ne peut pas être modifié. Le formulaire l’affiche sous **ID externe**, et `GET /api/v1/connectors/aws-external-id` le renvoie. Exigez l’ID externe dans la politique de confiance du rôle, afin qu’aucune autre organisation ne puisse endosser le rôle même si elle apprend l’ARN :

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": { "AWS": "<ARN of the node role or IAM user>" },
      "Action": "sts:AssumeRole",
      "Condition": { "StringEquals": { "sts:ExternalId": "molesignal-<organization ID>" } }
    }
  ]
}
```

La session est nommée `molesignal-<connector ID>`, ce qui correspond à son nom dans AWS CloudTrail. La requête est envoyée au point de terminaison STS régional de la `region` du connecteur : `us-east-1` lorsque la région est vide, et le domaine `amazonaws.com.cn` pour les régions de Chine.

### Identité web

`web_identity` endosse le rôle avec le jeton d’identité web dont le chemin est fourni par `AWS_WEB_IDENTITY_TOKEN_FILE` du nœud, comme le jeton de compte de service qu’EKS projette pour IRSA. Un connecteur ne peut pas désigner un autre fichier. La politique de confiance du rôle doit faire confiance au fournisseur OIDC qui émet le jeton. Sur un nœud dépourvu de `AWS_WEB_IDENTITY_TOKEN_FILE`, le connecteur n’a aucun identifiant.

Le jeton est échangé auprès du point de terminaison STS régional de la `region` du connecteur, ou auprès de `AWS_ENDPOINT_URL_STS` lorsque l’environnement du nœud le définit. Il en va de même pour une identité de nœud issue d’IRSA.

## Tester une connexion

**Tester la connexion** teste les paramètres tels qu’ils figurent dans le formulaire, avant leur enregistrement. Un secret laissé vide correspond à celui qui est enregistré. Chaque type effectue le minimum qui prouve qu’une livraison ou une extraction peut fonctionner :

| Type | Test |
|---|---|
| `s3` | Écrit l’objet `.molesignal-connection-test` sous le préfixe, puis le supprime lorsque la politique l’autorise. |
| `kafka` | Lit les métadonnées du topic auprès des brokers, ce qui prouve la connexion, TLS et l’authentification, ainsi que l’existence du topic. N’écrit aucun message. |
| `http` | Envoie un événement marqué comme test : `"message": "MoleSignal connection test"` et `"molesignal_connection_test": true`. |
| `aws_cloudwatch_logs` | Lit au plus un événement de la dernière minute du groupe de logs. N’écrit rien dans le flux et laisse la position de lecture inchangée. |
| `kafka_source` | Lit les métadonnées du topic auprès des brokers, comme pour `kafka`. Ne lit aucun message et laisse la position de lecture inchangée. |
| `s3_source` | Liste un objet sous le préfixe, ce qui prouve les identifiants et `s3:ListBucket`. Ne lit rien et laisse la position de lecture inchangée. |

Un test s’interrompt au bout de 25 secondes. Via l’API, `POST /api/v1/connectors/test` prend le `kind` et le `configJson` à essayer. Avec l’`id` d’un connecteur enregistré du même type, `***` représente le secret que détient le connecteur. Les paramètres qui ne peuvent pas fonctionner renvoient `400`, comme à l’enregistrement.

```bash
curl -X POST http://localhost:5080/api/v1/connectors/test \
  -H "authorization: Bearer $MS_TOKEN" \
  -H 'content-type: application/json' \
  -d '{
        "id": "<connector id>",
        "kind": "kafka",
        "configJson": {
          "brokers": "b-1.example.com:9096",
          "topic": "logs",
          "tls": true,
          "auth": "sasl_scram_sha_512",
          "saslUsername": "molesignal",
          "saslPassword": "***"
        }
      }'
```

```json
{ "ok": true, "code": "ok", "detail": null, "elapsedMs": 412 }
```

`elapsedMs` indique la durée du test. Un test échoué nomme la cause dans `code`, et `detail` contient les propos de l’autre partie, jusqu’à 600 caractères :

| `code` | Signification |
|---|---|
| `ok` | Connexion réussie. |
| `invalid` | Les paramètres ne peuvent pas fonctionner, ou le connecteur est une source push, qui n’a aucune cible à laquelle se connecter. |
| `no_credentials` | Aucun identifiant AWS n’a pu être obtenu : le nœud n’a pas d’identité, ou aucune identité du type demandé. |
| `denied` | L’autre partie a refusé les identifiants ou les actions qu’ils sont autorisés à effectuer. |
| `not_found` | Le bucket, le topic, le groupe de logs ou l’adresse n’existent pas. |
| `tls` | La négociation TLS a échoué : certificat non approuvé ou non présenté. |
| `unreachable` | L’hôte n’a pas pu être résolu ou joint. |
| `timeout` | Aucune réponse dans le délai imparti. |
| `failed` | Toute autre erreur. |

Un connecteur est renvoyé avec `id`, `name`, `kind`, `configJson` avec les secrets masqués, `secretKeys`, `enabled`, `lastRunAt`, `readState`, `createdAt` et `updatedAt`.

## Autorisations

`pipelines.read` liste et inspecte les connecteurs et lit l’ID externe. `pipelines.edit` crée, met à jour, supprime et teste les connecteurs. Un test nécessite `pipelines.edit`, car il utilise les secrets stockés et se connecte à un autre système pour le compte de l’appelant. Les récepteurs push s’authentifient avec le jeton push et n’acceptent pas un JWT de connexion normal en remplacement.
