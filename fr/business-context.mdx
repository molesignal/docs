Les clés métier relient la télémétrie à ce qu'elle a servi : un locataire, une offre, un niveau d'utilisateur ou un groupe d'expérimentation. Une fois les clés déclarées, la page de service APM répartit les requêtes selon ces clés, un incident liste les valeurs touchées par le problème, et l'analyse des causes racines sait quels locataires ont échoué. MoleSignal ne réécrit jamais les données pour cela : les applications placent les clés sur leur télémétrie, et le serveur lit les champs nommés par la déclaration.

## Déclarer les clés

Ouvrez **APM → Paramètres** et utilisez la carte **Contexte métier**. Chaque clé possède :

| Champ | Remarques |
|---|---|
| **Clé** | Le nom utilisé dans les liens et par Mole Agent : lettres minuscules, chiffres et `_`, par exemple `tenant`. |
| **Étiquette** | Ce que voient les lecteurs, par exemple `Tenant`. |
| **Attribut de span** | Le champ du flux de traces qui la porte, par exemple `tenant.id`. |
| **Champ de log** | Le champ de log qui la porte. |
| **Champ RUM** | Le champ RUM, une clé d'un champ JSON inclus, par exemple `context.tenant`. |
| **Valeurs importantes** | Les valeurs qui comptent le plus, comme les clients clés, séparées par des virgules. Elles sont signalées partout où l'impact d'un incident est affiché. |

Une clé nomme le champ d'au moins un signal ; jusqu'à 8 clés. La gestion de la carte nécessite `apm.settings.manage`. La même déclaration peut être définie via l'[API](/fr/api/business-context).

## Placer les clés sur la télémétrie

Les attributs de span et de log deviennent des champs de leur flux à l'ingestion, si bien qu'une clé définie comme attribut sert immédiatement de critère de répartition. La méthode habituelle pour la définir sur chaque span et chaque enregistrement de log d'une requête est le baggage W3C : définir la clé une fois à l'entrée de la requête, puis un processeur de baggage la copie sur chaque span (et, lorsque le SDK en dispose, chaque enregistrement de log) produit par la requête, dans chaque service qu'elle atteint.

<Warning>
Le baggage voyage vers chaque service en aval dans les en-têtes de requête, y compris les tiers. Ne copiez que les clés déclarées, et ne placez jamais de secrets ni de données personnelles dans le baggage.
</Warning>

| Langage | Ce qui copie le baggage sur les spans |
|---|---|
| Java | L'agent Java OpenTelemetry, ou `io.opentelemetry.contrib:opentelemetry-baggage-processor` avec autoconfigure : définir `otel.java.experimental.span-attributes.copy-from-baggage.include=tenant.id` (et `otel.java.experimental.log-attributes.copy-from-baggage.include` pour les logs). |
| Go | `go.opentelemetry.io/contrib/processors/baggagecopy` : `baggagecopy.NewSpanProcessor(filter)` sur le tracer provider. |
| Node.js | `@opentelemetry/baggage-span-processor` (`BaggageSpanProcessor`) et `@opentelemetry/baggage-log-record-processor` (`BaggageLogRecordProcessor`). |
| Python | `opentelemetry-processor-baggage` : `BaggageSpanProcessor(predicate)` sur le tracer provider. |
| .NET | `OpenTelemetry.Extensions` : le processeur d'activité de baggage, enregistré avant tout processeur d'export. |
| Ruby | La gem `opentelemetry-processor-baggage`. |
| PHP, Rust, Erlang/Elixir | Lire la clé depuis le baggage à l'entrée de la requête, puis la définir manuellement comme attribut de span et attribut de log. |

Chaque processeur prend un prédicat qui choisit les clés à copier ; passez un prédicat qui ne conserve que les clés déclarées plutôt qu'un prédicat qui copie tout. Par exemple, en Python :

```python
from opentelemetry.processor.baggage import BaggageSpanProcessor

declared = {"tenant.id", "plan"}
tracer_provider.add_span_processor(BaggageSpanProcessor(lambda key: key in declared))
```

et à l'entrée de la requête :

```python
from opentelemetry import baggage, context

token = context.attach(baggage.set_baggage("tenant.id", tenant_id))
```

Pour le RUM, définissez la clé dans le contexte du SDK navigateur, par exemple `context.tenant`, et nommez ce champ comme **champ RUM** de la clé.

## Où les clés sont utilisées

| Page | Ce qu'elle affiche |
|---|---|
| Page de service [APM](/fr/apm) | **Requêtes par clé métier** : requêtes, taux d'erreur et P95 de chaque valeur, valeurs importantes signalées, et un lien pour répartir selon n'importe quel autre champ de la page Traces. |
| [Incidents](/fr/alerting/incidents#détails-de-l’incident) | **Impact métier** : pour chaque clé, les valeurs dont les requêtes vers les services de l'incident ont le plus échoué autour de son déclenchement. Affiché aux lecteurs disposant de `streams.query` ou `sys.telemetry.read`. |
| [Analyse des causes racines](/fr/alerting/incidents) | Un élément de preuve **Impact métier** pour chaque clé ayant des valeurs en échec. |

La vue RED [Traces](/fr/traces) répartit selon n'importe quel champ de span, clés métier incluses, et sa carte **Comparer** indique quelles valeurs de champ distinguent les requêtes en échec ou lentes.
