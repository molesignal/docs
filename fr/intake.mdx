Chaque signal entre dans MoleSignal par l’API d’ingestion. La page **Source de données** de l’interface web génère le point de terminaison, le jeton et l’extrait de configuration de chaque source. Les mêmes protocoles peuvent être configurés à la main.

## Page Source de données

Ouvrez **Source de données** pour intégrer une source :

1. Recherchez dans le catalogue ou filtrez-le par catégorie : **Recommandé**, **Infrastructure**, **Cloud**, **Bases de données**, **Messagerie**, **Applications et langages**, **Sécurité** et **Personnalisé**. Les onglets de signal (**Journaux**, **Métriques**, **Traces**, **Profils**) affinent encore la liste.
2. Sélectionnez une source telle que Kubernetes, un hôte Linux, AWS, un SDK OpenTelemetry ou Web RUM.
3. Suivez les trois étapes du guide :
   - **Point de terminaison et jeton** indique où envoyer les données et le jeton à utiliser pour s’authentifier. **Afficher le jeton** révèle le jeton, avec sa portée, son espace de travail et sa date d’expiration. Pour une source RUM, choisissez d’abord l’**Application RUM** : son jeton client apparaît une fois l’application choisie.
   - **Configurer la source** affiche les commandes et la configuration avec le point de terminaison et le jeton réels déjà renseignés.
   - **Vérifier la réception des données** contrôle le récepteur, puis recherche les données reçues au cours de la dernière heure. **Vérifier la connexion** lance un contrôle immédiat, et les chiffres se rafraîchissent toutes les 30 secondes.
4. Lisez le résultat de la vérification :
   - **Données détectées** : des données sont arrivées au cours de la dernière heure et les signaux de la source sont sains. **Voir les données reçues** ouvre les données, et **Créer un pipeline** démarre un pipeline pour celles-ci.
   - **Le récepteur fonctionne, mais les données sont à vérifier** : le récepteur répond, mais aucune donnée n’est arrivée, ou tous les signaux ne sont pas sains. Vérifiez le déploiement ou attendez le prochain lot.
   - **Échec de la vérification** : le récepteur n’a pas pu être contrôlé. **Causes possibles** cite un collecteur qui ne tourne pas, un jeton invalide ou expiré, et un réseau ou un proxy qui bloque le point de terminaison.

Le point de terminaison provient de `http.external_url` lorsqu’elle est définie, et sinon de l’adresse du navigateur. Définissez `http.external_url` derrière un proxy inverse pour que les extraits générés pointent vers l’adresse publique. Voir [Configuration](/fr/configuration).

## Jetons d’ingestion

Les émetteurs s’authentifient avec un jeton bearer : `Authorization: Bearer <token>`. Un émetteur qui ne sait faire que l’authentification Basic, comme l’export remote write du Prometheus managé d’un fournisseur cloud, place le jeton d’API dans le mot de passe de `Authorization: Basic` avec n’importe quel nom d’utilisateur. Les autres identifiants Basic sont ignorés, de sorte qu’un proxy inverse qui demande les siens fonctionne toujours. Un émetteur Splunk HEC présente le jeton sous la forme `Authorization: Splunk <token>`.

| Jeton | Permission | Créé par | Utilisation |
|---|---|---|---|
| Jeton d’ingestion par défaut | `logs.write`, `metrics.write`, `traces.write`, `profiles.write` et `apm.deploy` uniquement : la politique **Ingestion de données** | Page Source de données, ou `GET /api/v1/me/api-tokens/default` | Collecteurs, agents et exportateurs SDK qui envoient des journaux, des métriques et des traces, et pipelines qui [signalent des déploiements](/fr/apm/deployments#signaler-des-déploiements-depuis-la-ci). N’expire pas. |
| Jeton client RUM | `rum.write` uniquement, lié à une seule application | Page Source de données pour les sources Web RUM et RUM mobile, ou `GET /api/v1/auth/tokens/rum?applicationId=<id>` | Code navigateur et mobile. Le jeton est visible par les utilisateurs finaux. |
| Jeton personnel ou de compte de service | Ce que son membre ou son compte de service peut faire, restreint par sa portée | **Paramètres du compte → Jetons d’API**, ou **Identité et accès → Jetons d’API** pour les comptes de service | Automatisation, scripts et clients MCP. |

Utilisez le jeton d’ingestion par défaut, ou un jeton de compte de service qui suit la politique **Ingestion de données**, pour les émetteurs qui tournent en continu. Révoquez un jeton depuis **Paramètres du compte → Jetons d’API** ou **Identité et accès → Jetons d’API** pour l’arrêter immédiatement. Une session de connexion de l’interface web ne peut pas envoyer de données : elle vit dans les cookies du navigateur, et l’en-tête `Authorization` ne l’accepte pas.

La page **Source de données** crée un jeton client RUM lorsqu’un identifiant d’application est saisi. Un identifiant d’application contient de 1 à 128 caractères parmi `A-Z`, `a-z`, `0-9`, `.`, `_`, `:` et `-`. Utilisez le même identifiant comme `applicationId` dans le SDK. Voir [SDK RUM navigateur](/fr/rum/browser-sdk).

## Points de terminaison et protocoles

| Protocole | Point de terminaison | Émetteurs compatibles | Flux cible |
|---|---|---|---|
| JSON HTTP natif | `POST /api/v1/intake/{logs,metrics,traces}/{stream}` | `curl`, code applicatif, sink `http` de Vector, sortie `http` de Fluent Bit | Le segment de chemin `{stream}` |
| OTLP sur HTTP | `POST /api/v1/logs`, `/api/v1/metrics`, `/api/v1/traces` | SDK OpenTelemetry et Collector | En-tête `stream-name`, sinon `default` |
| OTLP sur gRPC | `:4317` | SDK OpenTelemetry et Collector | Métadonnées `stream-name`, sinon `default` |
| remote_write de Prometheus | `POST /api/v1/prometheus/api/v1/write` | Prometheus, VictoriaMetrics, exports Prometheus managés par le cloud, tout émetteur remote_write v1 | En-tête `stream-name`, sinon `?stream=`, sinon `default` |
| `_bulk` d'Elasticsearch | `POST /api/v1/_bulk` | Filebeat, Logstash, sink `elasticsearch` de Vector | `_index` de chaque action, sinon en-tête `stream-name`, sinon `default` |
| Splunk HEC | `POST /api/v1/services/collector/event`, `/api/v1/services/collector/raw` | CLS de Tencent Cloud, sorties Splunk de Vector et Fluent Bit, redirecteurs SIEM | `index` de chaque événement, sinon `?index=`, sinon en-tête `stream-name`, sinon `default` |
| push Loki (JSON) | `POST /api/v1/loki/api/v1/push` | Émetteurs capables d'envoyer en POST la structure JSON de Loki | En-tête `stream-name`, sinon `default` |
| Amazon Data Firehose, push Google Cloud Pub/Sub, bus d'événements cloud, Cloudflare Logpush, Heroku | `/api/v1/_kinesis_firehose`, `/api/v1/_gcp_pubsub`, `/api/v1/_cloud_events`, `/api/v1/_cloudflare`, `/api/v1/_heroku` | CloudWatch Logs et CloudWatch Metric Streams via Firehose, Cloud Logging via Pub/Sub, émetteurs EventBridge, Event Grid et CloudEvents, Cloudflare, Heroku | Configuré sur le connecteur. Voir [Connecteurs](/fr/connectors). |

Tous les points de terminaison sauf les connecteurs push exigent un jeton Bearer portant la permission d'écriture du signal : `logs.write`, `metrics.write`, `traces.write` ou `profiles.write`. L'organisation provient du jeton et n'apparaît jamais dans une URL.

### Limites qui affectent les émetteurs

- **Taille des requêtes.** L'ingestion JSON native et les connecteurs push acceptent des corps de requête jusqu'à 16 MiB, et Firehose jusqu'à 64 MiB, comptés après décompression ; les autres points de terminaison d'ingestion acceptent jusqu'à 2 MiB. Un corps plus volumineux est rejeté avec `413`. Gardez des lots en dessous de cette taille.
- **Compression.** OTLP sur HTTP n'accepte pas les corps de requête compressés et répond `400`. Désactivez la compression dans l'émetteur ; l'exportateur `otlphttp` du Collector OpenTelemetry compresse en gzip par défaut et nécessite `compression: none`. L'ingestion JSON native, `_bulk` d'Elasticsearch, le push Loki et les connecteurs push acceptent `Content-Encoding: gzip`.
- **Encodage Loki.** Seule la structure de requête JSON est décodée. Promtail et Grafana Alloy envoient du protobuf compressé en snappy par défaut et ne peuvent pas envoyer vers ce point de terminaison.
- **Limite de débit.** Le rôle `router` limite les requêtes par organisation et répond `429` avec un en-tête `Retry-After`. Un nœud `standalone` n'applique pas cette limite. Voir [Déploiement par rôle](/fr/deployment/role-based#limitation-du-débit).
- **Événements refusés.** Un événement dont une valeur ne correspond pas au type de son champ dans le flux est refusé isolément, et le reste de la requête est écrit. Les nombres à virgule dans un champ `int64` ne sont pas refusés : le champ devient `float64` (voir [Schéma et champs](/fr/streams#schéma-et-champs)). Chaque point de terminaison indique ce qu'il a refusé : JSON natif dans `rejected` et `errors`, OTLP dans `partialSuccess`, `_bulk` d'Elasticsearch sous forme d'éléments avec le statut `400`, Splunk HEC avec le code `6`, et remote_write de Prometheus et push Loki avec `400`. Les émetteurs ne les réessaient pas. Les connecteurs push répondent en succès, car les plateformes renverraient la requête entière, et le connecteur indique ce qui a été refusé.
- **Flux de plateforme.** Les [flux de plateforme](/fr/streams#flux-de-plateforme), tels que `_molesignal` pour la télémétrie du service lui-même et `_audit` pour la piste d'audit, sont écrits par MoleSignal uniquement et rejettent l'ingestion publique avec `403`.

## Flux et schéma

Un flux est créé lors de sa première écriture, et le schéma évolue à mesure que de nouveaux champs apparaissent. Un flux est identifié par son nom et son type de signal, si bien que `default` peut exister en même temps pour les logs, les métriques et les traces. Voir [Flux](/fr/streams).

Chaque événement possède un horodatage en microsecondes depuis l'époque Unix. Le JSON natif et `_bulk` d'Elasticsearch lisent le champ `_timestamp`. Un événement sans `_timestamp` reçoit l'heure à laquelle le serveur l'a accepté.

## JSON HTTP natif

Envoyez un tableau d'enregistrements en POST vers `/api/v1/intake/{logs,metrics,traces}/{stream}` :

```bash
curl -X POST http://localhost:5080/api/v1/intake/logs/app \
  -H "authorization: Bearer $MS_TOKEN" \
  -H 'content-type: application/json' \
  -d "[{\"_timestamp\":$(date +%s)000000,\"level\":\"error\",\"msg\":\"db pool exhausted\",\"trace_id\":\"abc123\"}]"
```

La réponse indique combien d'enregistrements ont été acceptés et rejetés, avec une raison pour chaque index rejeté :

```json
{"accepted":1,"rejected":0,"errors":[]}
```

## OpenTelemetry

Configurez un SDK OpenTelemetry ou un Collector sur le chemin de base `/api`. L'exportateur ajoute `/v1/logs`, `/v1/metrics` et `/v1/traces`, qui correspondent à `/api/v1/logs`, `/api/v1/metrics` et `/api/v1/traces`.

<Tabs>
  <Tab title="OTLP sur HTTP">
    Variables d'environnement du SDK :

    ```bash
    export OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf
    export OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:5080/api
    export OTEL_EXPORTER_OTLP_HEADERS="authorization=Bearer ${MS_TOKEN}"
    ```

    Collector OpenTelemetry :

    ```yaml
    exporters:
      otlphttp/molesignal:
        endpoint: http://localhost:5080/api
        compression: none
        headers:
          authorization: "Bearer ${env:MS_TOKEN}"
    ```

    Envoyez du protobuf (`application/x-protobuf`), l'encodage par défaut des SDK et du Collector. Les logs, les métriques et les traces acceptent aussi du JSON (`application/json`). Ajoutez un en-tête `stream-name` pour sélectionner un flux autre que `default`. L'en-tête s'applique à chaque signal envoyé via cet exportateur.
  </Tab>
  <Tab title="OTLP sur gRPC">
    Le récepteur OTLP gRPC écoute sur le port `4317` et sert les services logs, metrics, traces et profiles. Il ne termine pas TLS. Terminez TLS devant lui pour le trafic qui quitte un réseau de confiance.

    ```bash
    export OTEL_EXPORTER_OTLP_PROTOCOL=grpc
    export OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4317
    export OTEL_EXPORTER_OTLP_HEADERS="authorization=Bearer ${MS_TOKEN}"
    ```

    Collector OpenTelemetry :

    ```yaml
    exporters:
      otlp/molesignal:
        endpoint: localhost:4317
        tls:
          insecure: true
        headers:
          authorization: "Bearer ${env:MS_TOKEN}"
    ```

    Supprimez `insecure: true` lorsqu'un proxy qui termine TLS se trouve devant le port. Le port `5082` est le port gRPC interne du cluster et n'est pas un récepteur OTLP.
  </Tab>
</Tabs>

Les métriques OTLP sont stockées sous forme d'un événement par point de données. Voir le [contrat de stockage des métriques](/fr/query#champs-des-métriques-otlp) pour les champs stockés.

## remote_write de Prometheus

Ajoutez MoleSignal comme cible remote write dans `prometheus.yml` :

```yaml
remote_write:
  - url: http://localhost:5080/api/v1/prometheus/api/v1/write
    authorization:
      credentials: "${MS_TOKEN}"
```

Un flux de métriques contient les métriques d'une seule source : attribuez donc à chaque serveur Prometheus son propre flux avec l'en-tête `stream-name` (`headers:` dans l'entrée `remote_write`) ; sans cela, les échantillons vont dans `default`. Un émetteur qui ne peut pas définir d'en-têtes nomme le flux dans l'URL, comme dans `/api/v1/prometheus/api/v1/write?stream=aliyun`. Chaque échantillon devient une ligne dont `metric_name` est son `__name__`. Les autres labels deviennent des champs, et un label nommé comme un champ de métrique, tel que `metric_name`, est conservé sous la forme `exported_<name>`. Les histogrammes natifs et les métadonnées de métriques sont ignorés, et les exemplars sont stockés à côté des échantillons.

## Bulk Elasticsearch

Les émetteurs qui parlent le protocole bulk d'Elasticsearch fonctionnent sans dépendance à Loki ni à OTLP :

```bash
curl -X POST http://localhost:5080/api/v1/_bulk \
  -H "authorization: Bearer $MS_TOKEN" \
  -H 'content-type: application/x-ndjson' \
  --data-binary $'{"index":{"_index":"app"}}\n{"level":"info","msg":"hello"}\n'
```

Le champ `_index` de chaque action sélectionne le flux cible. À défaut, l'en-tête `stream-name` s'applique, puis `default`.

## push Loki

Le point de terminaison accepte la structure de requête JSON de Loki :

```json
{"streams":[{"stream":{"service":"checkout","level":"error"},"values":[["1700000000000000000","payment failed"]]}]}
```

Les labels deviennent des champs, la ligne de log devient le champ `message` et l'horodatage en nanosecondes est converti en microsecondes. La réponse est `204`. Sélectionnez le flux cible avec l'en-tête `stream-name`.

## Splunk HEC

Les émetteurs qui parlent le protocole HTTP Event Collector de Splunk, comme Tencent Cloud CLS qui exporte vers Splunk ou les sorties Splunk de Vector et de Fluent Bit, peuvent envoyer vers MoleSignal sans modification. Fournissez-leur `https://molesignal.example.com/api/v1` comme adresse HEC et un API Token autorisé à écrire des logs comme token HEC, transmis via `Authorization: Splunk <token>`.

| Endpoint | Body |
|---|---|
| `POST /api/v1/services/collector/event`, également `/services/collector` | Des objets JSON à la suite, chacun `{"time", "host", "source", "sourcetype", "index", "event", "fields"}` |
| `POST /api/v1/services/collector/raw` | Du texte, un événement de log par ligne ; `host`, `source`, `sourcetype` et `index` proviennent de la requête |
| `GET /api/v1/services/collector/health` | Répond `{"text":"HEC is healthy","code":17}` sans token |

Un `event` qui est un objet JSON fournit les champs du log ; tout autre `event` devient `message`. `fields`, `host`, `source` et `sourcetype` deviennent des champs, et `time`, en secondes, devient l'horodatage. `index` désigne le flux, sinon le paramètre de requête `index`, sinon l'en-tête `stream-name`, sinon `default`. La réponse est `{"text":"Success","code":0}`, ou les codes d'erreur propres à HEC avec `400`. Lorsqu'un flux refuse des événements parce qu'une valeur ne correspond pas au type de son champ, les autres événements sont écrits et la réponse est le code `6`, avec la position du premier événement refusé dans le corps en `invalid-event-number` et la raison dans `text`. L'accusé de réception d'indexeur n'est pas proposé.
