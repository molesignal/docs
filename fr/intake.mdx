Chaque signal entre dans MoleSignal par l’API d’ingestion. La page **Source de données** de l’interface web génère le point de terminaison, le jeton et l’extrait de configuration pour chaque source. Les mêmes protocoles peuvent être configurés manuellement.

## Page Source de données

Ouvrez **Source de données** pour intégrer une source :

1. Recherchez dans le catalogue ou filtrez-le par catégorie : **Recommandé**, **Infrastructure**, **Cloud**, **Bases de données**, **Messagerie**, **Applications et langages**, **Sécurité** et **Personnalisé**. Les onglets de signal (**Journaux**, **Métriques**, **Traces**, **Profils**) affinent encore la liste.
2. Sélectionnez une source comme Kubernetes, un hôte Linux, AWS, un SDK OpenTelemetry ou Web RUM.
3. Suivez les trois étapes du guide :
   - **Point de terminaison et jeton** indique où envoyer les données et le jeton permettant de s’authentifier. **Afficher le jeton** révèle le jeton, avec sa portée, son espace de travail et sa date d’expiration. Pour une source RUM, choisissez d’abord l’**Application RUM** : son jeton client apparaît dès qu’elle est choisie.
   - **Configurer la source** affiche des commandes et une configuration avec le point de terminaison et le jeton réels déjà renseignés.
   - **Vérifier la réception des données** contrôle le récepteur, puis recherche les données reçues au cours de la dernière heure. **Vérifier la connexion** effectue le contrôle immédiatement, et les chiffres s’actualisent toutes les 30 secondes.
4. Lisez le résultat de la vérification :
   - **Données détectées** : des données sont arrivées au cours de la dernière heure, et les signaux de la source sont en bon état. **Voir les données reçues** ouvre les données, et **Créer un pipeline** démarre un pipeline pour celles-ci.
   - **Le récepteur fonctionne, mais les données sont à vérifier** : le récepteur répond, mais aucune donnée n’est arrivée, ou certains signaux ne sont pas en bon état. Vérifiez le déploiement, ou attendez le prochain lot.
   - **Échec de la vérification** : le récepteur n’a pas pu être vérifié. **Causes possibles** liste un collecteur qui ne fonctionne pas, un jeton invalide ou expiré, et un réseau ou proxy qui bloque le point de terminaison.

Le point de terminaison provient de `http.external_url` lorsqu’il est défini, et de l’adresse du navigateur sinon. Définissez `http.external_url` derrière un proxy inverse pour que les extraits générés pointent vers l’adresse publique. Voir [Configuration](/fr/configuration).

## Jetons d’ingestion

Les émetteurs s’authentifient avec un jeton Bearer : `Authorization: Bearer <token>`. Un émetteur qui ne peut utiliser que l’authentification Basic, comme l’export remote write du Prometheus géré d’un fournisseur cloud, place le jeton d’API dans le mot de passe de `Authorization: Basic` avec n’importe quel nom d’utilisateur. Les autres identifiants Basic sont ignorés, de sorte qu’un proxy inverse qui demande ses propres identifiants fonctionne toujours. Un émetteur Splunk HEC présente le jeton sous la forme `Authorization: Splunk <token>`.

| Jeton | Permission | Créé par | Utilisation |
|---|---|---|---|
| Jeton d’ingestion par défaut | `logs.write`, `metrics.write`, `traces.write`, `profiles.write`, et `apm.deploy` uniquement : la politique **Ingestion de données** | Page Source de données, ou `GET /api/v1/me/api-tokens/default` | Collecteurs, agents et exportateurs SDK qui envoient des journaux, des métriques et des traces, et pipelines qui [signalent des déploiements](/fr/apm/deployments#signaler-les-déploiements-depuis-la-ci). N’expire pas. |
| Jeton client RUM | `rum.write` uniquement, lié à une seule application | Page Source de données pour les sources Web RUM et RUM mobile, ou `GET /api/v1/auth/tokens/rum?applicationId=<id>` | Code navigateur et mobile. Le jeton est visible par les utilisateurs finaux. |
| Jeton personnel ou de compte de service | Ce que son membre ou son compte de service est autorisé à faire, restreint par sa portée | **Paramètres du compte → Jetons d’API**, ou **Identité et accès → Jetons d’API** pour les comptes de service | Automatisation, scripts et clients MCP. |

Utilisez le jeton d’ingestion par défaut, ou un jeton de compte de service qui suit la politique **Ingestion de données**, pour les émetteurs qui fonctionnent en continu. Révoquez un jeton depuis **Paramètres du compte → Jetons d’API** ou **Identité et accès → Jetons d’API** pour l’arrêter immédiatement. Une session de connexion de l’interface web ne peut pas envoyer de données : elle réside dans les cookies du navigateur, et l’en-tête `Authorization` ne l’accepte pas.

La page **Source de données** crée un jeton client RUM lorsqu’un identifiant d’application est saisi. Un identifiant d’application contient de 1 à 128 caractères parmi `A-Z`, `a-z`, `0-9`, `.`, `_`, `:`, et `-`. Utilisez le même identifiant comme `applicationId` dans le SDK. Voir [SDK RUM pour navigateur](/fr/rum/browser-sdk).

## Points de terminaison et protocoles

| Protocole | Point de terminaison | Émetteurs compatibles | Flux cible |
|---|---|---|---|
| HTTP JSON natif | `POST /api/v1/intake/{logs,metrics,traces}/{stream}` | `curl`, code d’application, sink `http` de Vector, sortie `http` de Fluent Bit | Le segment de chemin `{stream}` |
| OTLP sur HTTP | `POST /api/v1/logs`, `/api/v1/metrics`, `/api/v1/traces` | SDK et Collector OpenTelemetry | En-tête `stream-name`, sinon `default` |
| OTLP sur gRPC | `:4317` | SDK et Collector OpenTelemetry | Métadonnées `stream-name`, sinon `default` |
| remote_write Prometheus | `POST /api/v1/prometheus/api/v1/write` | Prometheus, VictoriaMetrics, exports de Prometheus géré dans le cloud, tout émetteur remote_write v1 | En-tête `stream-name`, sinon `?stream=`, sinon `default` |
| `_bulk` Elasticsearch | `POST /api/v1/_bulk` | Filebeat, Logstash, sink `elasticsearch` de Vector | `_index` de chaque action, sinon en-tête `stream-name`, sinon `default` |
| Splunk HEC | `POST /api/v1/services/collector/event`, `/api/v1/services/collector/raw` | Tencent Cloud CLS, sorties Splunk de Vector et Fluent Bit, redirecteurs SIEM | `index` de chaque événement, sinon `?index=`, sinon en-tête `stream-name`, sinon `default` |
| Loki push (JSON) | `POST /api/v1/loki/api/v1/push` | Émetteurs capables d’envoyer par POST la structure JSON de Loki | En-tête `stream-name`, sinon `default` |
| Amazon Data Firehose, Google Cloud Pub/Sub push, bus d’événements cloud, Cloudflare Logpush, Heroku | `/api/v1/_kinesis_firehose`, `/api/v1/_gcp_pubsub`, `/api/v1/_cloud_events`, `/api/v1/_cloudflare`, `/api/v1/_heroku` | CloudWatch Logs et CloudWatch Metric Streams via Firehose, Cloud Logging via Pub/Sub, émetteurs EventBridge, Event Grid et CloudEvents, Cloudflare, Heroku | Configuré sur le connecteur. Voir [Connecteurs](/fr/connectors). |

Tous les points de terminaison, sauf les connecteurs push, exigent un jeton Bearer avec la permission d’écriture du signal : `logs.write`, `metrics.write`, `traces.write` ou `profiles.write`. L’organisation provient du jeton et n’apparaît jamais dans une URL.

### Limites qui affectent les émetteurs

- **Taille des requêtes.** L’ingestion JSON native et les connecteurs push acceptent des corps de requête jusqu’à 16 MiB, et Firehose jusqu’à 64 MiB, comptés après décompression ; les autres points de terminaison d’ingestion acceptent jusqu’à 2 MiB. Un corps plus volumineux est rejeté avec `413`. Gardez des lots inférieurs à cette taille.
- **Compression.** OTLP sur HTTP n’accepte pas les corps de requête compressés et répond `400`. Désactivez la compression dans l’émetteur ; l’exportateur `otlphttp` du Collector OpenTelemetry compresse par défaut avec gzip et nécessite `compression: none`. L’ingestion JSON native, `_bulk` Elasticsearch, Loki push et les connecteurs push acceptent `Content-Encoding: gzip`.
- **Encodage Loki.** Seule la forme de requête JSON est décodée. Promtail et Grafana Alloy envoient par défaut du protobuf compressé avec snappy et ne peuvent pas envoyer vers ce point de terminaison.
- **Limite de débit.** Le rôle `router` limite les requêtes par organisation et répond `429` avec un en-tête `Retry-After`. Un nœud `standalone` n’applique pas cette limite. Voir [Déploiement basé sur les rôles](/fr/deployment/role-based#limitation-du-débit).
- **Flux de plateforme.** Les [flux de plateforme](/fr/streams#flux-de-la-plateforme), comme `_molesignal` pour la télémétrie propre au service et `_audit` pour la piste d’audit, sont écrits uniquement par MoleSignal et rejettent l’ingestion publique avec `403`.

## Flux et schéma

Un flux est créé lors de sa première écriture, et le schéma évolue à mesure que de nouveaux champs apparaissent. Un flux est identifié par son nom et son type de signal, donc `default` peut exister pour les journaux, les métriques et les traces en même temps. Voir [Flux](/fr/streams).

Chaque événement possède un horodatage en microsecondes depuis l’époque Unix. L’ingestion JSON native et `_bulk` Elasticsearch lisent le champ `_timestamp`. Un événement sans `_timestamp` reçoit l’heure à laquelle le serveur l’a accepté.

## JSON HTTP natif

Envoyez un tableau d'enregistrements à `/api/v1/intake/{logs,metrics,traces}/{stream}` :

```bash
curl -X POST http://localhost:5080/api/v1/intake/logs/app \
  -H "authorization: Bearer $MS_TOKEN" \
  -H 'content-type: application/json' \
  -d "[{\"_timestamp\":$(date +%s)000000,\"level\":\"error\",\"msg\":\"db pool exhausted\",\"trace_id\":\"abc123\"}]"
```

La réponse indique combien d'enregistrements ont été acceptés et rejetés, avec un motif pour chaque index rejeté :

```json
{"accepted":1,"rejected":0,"errors":[]}
```

## OpenTelemetry

Dirigez un SDK ou un Collector OpenTelemetry vers le chemin de base `/api`. L'exportateur ajoute `/v1/logs`, `/v1/metrics` et `/v1/traces`, qui correspondent à `/api/v1/logs`, `/api/v1/metrics` et `/api/v1/traces`.

<Tabs>
  <Tab title="OTLP via HTTP">
    Variables d'environnement du SDK :

    ```bash
    export OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf
    export OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:5080/api
    export OTEL_EXPORTER_OTLP_HEADERS="authorization=Bearer ${MS_TOKEN}"
    ```

    Collector OpenTelemetry :

    ```yaml
    exporters:
      otlphttp/molesignal:
        endpoint: http://localhost:5080/api
        compression: none
        headers:
          authorization: "Bearer ${env:MS_TOKEN}"
    ```

    Envoyez du protobuf (`application/x-protobuf`), l'encodage par défaut des SDK et du Collector. Les logs, les métriques et les traces acceptent aussi du JSON (`application/json`). Ajoutez un en-tête `stream-name` pour choisir un flux autre que `default`. Cet en-tête s'applique à tous les signaux envoyés via cet exportateur.
  </Tab>
  <Tab title="OTLP via gRPC">
    Le récepteur gRPC OTLP écoute sur le port `4317` et sert les services logs, métriques, traces et profils. Il ne termine pas TLS. Terminez TLS en amont pour le trafic qui quitte un réseau de confiance.

    ```bash
    export OTEL_EXPORTER_OTLP_PROTOCOL=grpc
    export OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4317
    export OTEL_EXPORTER_OTLP_HEADERS="authorization=Bearer ${MS_TOKEN}"
    ```

    Collector OpenTelemetry :

    ```yaml
    exporters:
      otlp/molesignal:
        endpoint: localhost:4317
        tls:
          insecure: true
        headers:
          authorization: "Bearer ${env:MS_TOKEN}"
    ```

    Supprimez `insecure: true` lorsqu'un proxy qui termine TLS se trouve devant le port. Le port `5082` est le port gRPC interne du cluster et n'est pas un récepteur OTLP.
  </Tab>
</Tabs>

Les métriques OTLP sont stockées sous forme d'un événement par point de données. Consultez le [contrat de stockage des métriques](/fr/query#champs-des-métriques-otlp) pour connaître les champs stockés.

## Prometheus remote_write

Ajoutez MoleSignal comme cible de remote write dans `prometheus.yml` :

```yaml
remote_write:
  - url: http://localhost:5080/api/v1/prometheus/api/v1/write
    authorization:
      credentials: "${MS_TOKEN}"
```

Un flux de métriques contient les métriques d'une seule source : donnez donc à chaque serveur Prometheus son propre flux avec l'en-tête `stream-name` (`headers:` dans l'entrée `remote_write`) ; sans cela, les échantillons vont vers `default`. Un émetteur qui ne peut pas définir d'en-têtes nomme le flux dans l'URL, comme dans `/api/v1/prometheus/api/v1/write?stream=aliyun`. Chaque échantillon devient une ligne dont `metric_name` est son `__name__`. Les autres labels deviennent des champs, et un label portant le nom d'un champ de métrique, comme `metric_name`, est conservé sous la forme `exported_<name>`. Les histogrammes natifs et les métadonnées de métriques sont ignorés, et les exemplars sont stockés à côté des échantillons.

## Elasticsearch bulk

Les émetteurs qui parlent le protocole bulk d'Elasticsearch fonctionnent sans dépendance à Loki ou à OTLP :

```bash
curl -X POST http://localhost:5080/api/v1/_bulk \
  -H "authorization: Bearer $MS_TOKEN" \
  -H 'content-type: application/x-ndjson' \
  --data-binary $'{"index":{"_index":"app"}}\n{"level":"info","msg":"hello"}\n'
```

Le champ `_index` de chaque action sélectionne le flux cible. Sans lui, l'en-tête `stream-name` s'applique, puis `default`.

## Loki push

Le point de terminaison accepte le format de requête JSON de Loki :

```json
{"streams":[{"stream":{"service":"checkout","level":"error"},"values":[["1700000000000000000","payment failed"]]}]}
```

Les labels deviennent des champs, la ligne de log devient le champ `message` et l'horodatage en nanosecondes est converti en microsecondes. La réponse est `204`. Choisissez le flux cible avec l'en-tête `stream-name`.

## Splunk HEC

Les émetteurs qui parlent le protocole Splunk HTTP Event Collector, comme Tencent Cloud CLS qui expédie vers Splunk ou les sorties Splunk de Vector et de Fluent Bit, peuvent envoyer vers MoleSignal sans modification. Indiquez-leur `https://molesignal.example.com/api/v1` comme adresse HEC et un API Token autorisé à écrire des logs comme jeton HEC, envoyé via `Authorization: Splunk <token>`.

| Point de terminaison | Corps |
|---|---|
| `POST /api/v1/services/collector/event`, ainsi que `/services/collector` | Objets JSON à la suite, chacun `{"time", "host", "source", "sourcetype", "index", "event", "fields"}` |
| `POST /api/v1/services/collector/raw` | Texte, un événement de log par ligne ; `host`, `source`, `sourcetype` et `index` proviennent de la requête |
| `GET /api/v1/services/collector/health` | Répond `{"text":"HEC is healthy","code":17}` sans jeton |

Un `event` qui est un objet JSON fournit les champs du log ; tout autre `event` devient `message`. `fields`, `host`, `source` et `sourcetype` deviennent des champs, et `time`, en secondes, devient l'horodatage. `index` nomme le flux, sinon le paramètre de requête `index`, sinon l'en-tête `stream-name`, sinon `default`. La réponse est `{"text":"Success","code":0}`, ou les codes d'erreur propres à HEC avec `400`. L'acquittement d'indexeur n'est pas proposé.
