Every signal enters MoleSignal through the intake API. The **Source de données** page in the web UI generates the endpoint, token, and configuration snippet for each source. The same protocols can be configured by hand.

## Source de données page

Open **Source de données** to onboard a source:

1. Search the catalog or filter it by category: **Recommended**, **Infrastructure**, **Cloud**, **Bases de données**, **Messaging**, **Apps & languages**, **Security**, and **Custom**. The signal tabs (**Journaux**, **Métriques**, **Traces**, **Profils**) narrow the list further.
2. Select a source such as Kubernetes, a Linux host, AWS, an OpenTelemetry SDK, or Web RUM.
3. Follow the three steps of the guide:
   - **Point de terminaison et jeton** shows where to send data and the token to authenticate with. **Afficher le jeton** reveals the token, with its scope, workspace, and expiry. For a RUM source, choose the **Application RUM** first: its client token appears once it is chosen.
   - **Configurer la source** shows commands and configuration with the real endpoint and token already filled in.
   - **Vérifier la réception des données** checks the receiver, then looks for data received in the last hour. **Vérifier la connexion** checks at once, and the figures refresh every 30 seconds.
4. Read the result of the verification:
   - **Données détectées** : data arrived in the last hour, and the signals of the source are healthy. **Voir les données reçues** opens the data, and **Créer un pipeline** starts a pipeline for it.
   - **Le récepteur fonctionne, mais les données sont à vérifier** : the receiver answers, but no data arrived, or not every signal is healthy. Check the deployment, or wait for the next batch.
   - **Échec de la vérification** : the receiver could not be checked. **Causes possibles** lists a collector that is not running, a token that is invalid or expired, and a network or proxy that blocks the endpoint.

The endpoint comes from `http.external_url` when it is set, and from the address of the browser otherwise. Set `http.external_url` behind a reverse proxy so generated snippets point at the public address. See [Configuration](/fr/configuration).

## Intake tokens

Senders authenticate with a bearer token: `Authorization: Bearer <token>`. A sender that can only do Basic authentication, such as the remote write export of a cloud provider's managed Prometheus, puts the API Token in the password of `Authorization: Basic` with any user name. Other Basic credentials are ignored, so a reverse proxy that asks for its own still works. A Splunk HEC sender presents the token as `Authorization: Splunk <token>`.

| Token | Permission | Created by | Use |
|---|---|---|---|
| Default intake token | `logs.write`, `metrics.write`, `traces.write`, `profiles.write`, and `apm.deploy` only: the **Data intake** policy | Datasource page, or `GET /api/v1/me/api-tokens/default` | Collectors, agents, and SDK exporters that send logs, metrics, and traces, and pipelines that [report deployments](/fr/apm/deployments#signaler-des-déploiements-depuis-la-ci). Does not expire. |
| RUM client token | `rum.write` only, bound to one application | Datasource page for Web RUM and mobile RUM sources, or `GET /api/v1/auth/tokens/rum?applicationId=<id>` | Browser and mobile code. The token is visible to end users. |
| Personal or service account token | What its member or service account may do, narrowed by its scope | **Account settings → API tokens**, or **Identity & Access → API tokens** for service accounts | Automation, scripts, and MCP clients. |

Use the default intake token, or a service account token that follows the **Data intake** policy, for senders that run continuously. Revoke a token from **Account settings → API tokens** or **Identity & Access → API tokens** to stop it immediately. A sign-in session of the web UI cannot send data: it lives in browser cookies, and the `Authorization` header does not accept it.

The **Source de données** page creates a RUM client token when an application id is entered. An application id contains 1 to 128 characters from `A-Z`, `a-z`, `0-9`, `.`, `_`, `:`, and `-`. Use the same id as `applicationId` in the SDK. See [Browser RUM SDK](/fr/rum/browser-sdk).

## Points de terminaison et protocoles

| Protocole | Point de terminaison | Émetteurs compatibles | Flux cible |
|---|---|---|---|
| HTTP JSON natif | `POST /api/v1/intake/{logs,metrics,traces}/{stream}` | `curl`, code applicatif, sink `http` de Vector, sortie `http` de Fluent Bit | Le segment de chemin `{stream}` |
| OTLP sur HTTP | `POST /api/v1/logs`, `/api/v1/metrics`, `/api/v1/traces` | SDK et Collector OpenTelemetry | En-tête `stream-name`, sinon `default` |
| OTLP sur gRPC | `:4317` | SDK et Collector OpenTelemetry | Métadonnée `stream-name`, sinon `default` |
| remote_write Prometheus | `POST /api/v1/prometheus/api/v1/write` | Prometheus, VictoriaMetrics, exports Prometheus managés dans le cloud, tout émetteur remote_write v1 | En-tête `stream-name`, sinon `?stream=`, sinon `default` |
| Elasticsearch `_bulk` | `POST /api/v1/_bulk` | Filebeat, Logstash, sink `elasticsearch` de Vector | `_index` de chaque action, sinon en-tête `stream-name`, sinon `default` |
| HEC Splunk | `POST /api/v1/services/collector/event`, `/api/v1/services/collector/raw` | Tencent Cloud CLS, sorties Splunk de Vector et Fluent Bit, redirecteurs SIEM | `index` de chaque événement, sinon `?index=`, sinon en-tête `stream-name`, sinon `default` |
| Push Loki (JSON) | `POST /api/v1/loki/api/v1/push` | Émetteurs capables d'envoyer la forme JSON de Loki en POST | En-tête `stream-name`, sinon `default` |
| Amazon Data Firehose, push Google Cloud Pub/Sub, bus d'événements cloud, Cloudflare Logpush, Heroku | `/api/v1/_kinesis_firehose`, `/api/v1/_gcp_pubsub`, `/api/v1/_cloud_events`, `/api/v1/_cloudflare`, `/api/v1/_heroku` | CloudWatch Logs et CloudWatch Metric Streams via Firehose, Cloud Logging via Pub/Sub, EventBridge, Event Grid et émetteurs CloudEvents, Cloudflare, Heroku | Configuré sur le connecteur. Voir [Connecteurs](/fr/connectors). |

Tous les points de terminaison, à l'exception des connecteurs push, exigent un jeton bearer portant la permission d'écriture du signal : `logs.write`, `metrics.write`, `traces.write` ou `profiles.write`. L'organisation provient du jeton et n'apparaît jamais dans une URL.

### Limites qui affectent les émetteurs

- **Taille des requêtes.** L'ingestion JSON native et les connecteurs push acceptent des corps de requête jusqu'à 16 MiB, et Firehose jusqu'à 64 MiB, comptés après décompression ; les autres points de terminaison d'ingestion acceptent jusqu'à 2 MiB. Un corps plus volumineux est refusé avec `413`. Gardez des lots en dessous de cette taille.
- **Compression.** OTLP sur HTTP n'accepte pas les corps de requête compressés et répond `400`. Désactivez la compression dans l'émetteur ; l'exportateur `otlphttp` du Collector OpenTelemetry compresse en gzip par défaut et nécessite `compression: none`. L'ingestion JSON native, Elasticsearch `_bulk`, le push Loki et les connecteurs push acceptent `Content-Encoding: gzip`.
- **Encodage Loki.** Seule la forme de requête JSON est décodée. Promtail et Grafana Alloy envoient du protobuf compressé en snappy par défaut et ne peuvent pas envoyer vers ce point de terminaison.
- **Limite de débit.** Le rôle `router` limite les requêtes par organisation et répond `429` avec un en-tête `Retry-After`. Un nœud `standalone` n'applique pas cette limite. Voir [Déploiement par rôle](/fr/deployment/role-based#limitation-du-débit).
- **Événements refusés.** Un événement dont une valeur ne correspond pas au type de son champ dans le flux est refusé seul, et le reste de la requête est écrit. Les nombres avec une partie fractionnaire dans un champ `int64` ne sont pas refusés : le champ devient `float64` (voir [Schéma et champs](/fr/streams#schéma-et-champs)). Chaque point de terminaison indique ce qu'il a refusé : le JSON natif dans `rejected` et `errors`, OTLP dans `partialSuccess`, Elasticsearch `_bulk` sous forme d'éléments avec le statut `400`, HEC Splunk avec le code `6`, et remote_write Prometheus et push Loki avec `400`. Les émetteurs ne les réessaient pas. Les connecteurs push répondent par un succès, car les plateformes renverraient la requête entière, et le connecteur indique ce qui a été refusé.
- **Flux de plateforme.** Les [flux de plateforme](/fr/streams#flux-de-plateforme), tels que `_molesignal` pour la télémétrie propre au service et `_audit` pour la piste d'audit, sont écrits uniquement par MoleSignal et refusent l'ingestion publique avec `403`.

## Flux et schéma

Un flux est créé lors de sa première écriture, et le schéma évolue à mesure que de nouveaux champs apparaissent. Un flux est identifié par son nom et son type de signal, de sorte que `default` peut exister pour les logs, les métriques et les traces en même temps. Voir [Flux](/fr/streams).

Chaque événement porte un horodatage en microsecondes depuis l'epoch Unix. Le JSON natif et Elasticsearch `_bulk` lisent le champ `_timestamp`. Un événement sans `_timestamp` reçoit l'heure à laquelle le serveur l'a accepté.

## HTTP JSON natif

Envoyez un tableau d'enregistrements en POST vers `/api/v1/intake/{logs,metrics,traces}/{stream}` :

```bash
curl -X POST http://localhost:5080/api/v1/intake/logs/app \
  -H "authorization: Bearer $MS_TOKEN" \
  -H 'content-type: application/json' \
  -d "[{\"_timestamp\":$(date +%s)000000,\"level\":\"error\",\"msg\":\"db pool exhausted\",\"trace_id\":\"abc123\"}]"
```

La réponse indique combien d'enregistrements ont été acceptés et refusés, avec une raison pour chaque index refusé :

```json
{"accepted":1,"rejected":0,"errors":[]}
```

## OpenTelemetry

Configurez un SDK ou un Collector OpenTelemetry sur le chemin de base `/api`. L'exportateur ajoute `/v1/logs`, `/v1/metrics` et `/v1/traces`, qui correspondent à `/api/v1/logs`, `/api/v1/metrics` et `/api/v1/traces`.

<Tabs>
  <Tab title="OTLP sur HTTP">
    Variables d'environnement du SDK :

    ```bash
    export OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf
    export OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:5080/api
    export OTEL_EXPORTER_OTLP_HEADERS="authorization=Bearer ${MS_TOKEN}"
    ```

    Collector OpenTelemetry :

    ```yaml
    exporters:
      otlphttp/molesignal:
        endpoint: http://localhost:5080/api
        compression: none
        headers:
          authorization: "Bearer ${env:MS_TOKEN}"
    ```

    Envoyez du protobuf (`application/x-protobuf`), l'encodage par défaut des SDK et du Collector. Les logs, les métriques et les traces acceptent aussi JSON (`application/json`). Ajoutez un en-tête `stream-name` pour choisir un flux autre que `default`. L'en-tête s'applique à chaque signal envoyé via cet exportateur.
  </Tab>
  <Tab title="OTLP sur gRPC">
    Le récepteur OTLP gRPC écoute sur le port `4317` et sert les services logs, métriques, traces et profils. Il ne termine pas TLS. Terminez TLS devant lui pour le trafic qui quitte un réseau de confiance.

    ```bash
    export OTEL_EXPORTER_OTLP_PROTOCOL=grpc
    export OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4317
    export OTEL_EXPORTER_OTLP_HEADERS="authorization=Bearer ${MS_TOKEN}"
    ```

    Collector OpenTelemetry :

    ```yaml
    exporters:
      otlp/molesignal:
        endpoint: localhost:4317
        tls:
          insecure: true
        headers:
          authorization: "Bearer ${env:MS_TOKEN}"
    ```

    Supprimez `insecure: true` lorsqu'un proxy terminant TLS se trouve devant le port. Le port `5082` est le port gRPC interne du cluster et n'est pas un récepteur OTLP.
  </Tab>
</Tabs>

Les métriques OTLP sont stockées sous forme d'un événement par point de données. Voir le [contrat de stockage des métriques](/fr/query#champs-des-métriques-otlp) pour les champs stockés.

## remote_write Prometheus

Ajoutez MoleSignal comme cible de remote write dans `prometheus.yml` :

```yaml
remote_write:
  - url: http://localhost:5080/api/v1/prometheus/api/v1/write
    authorization:
      credentials: "${MS_TOKEN}"
```

Un flux de métriques contient les métriques d'une seule source : attribuez donc à chaque serveur Prometheus son propre flux avec l'en-tête `stream-name` (`headers:` dans l'entrée `remote_write`) ; sans cela, les échantillons vont dans `default`. Un émetteur qui ne peut pas définir d'en-têtes nomme le flux dans l'URL, comme dans `/api/v1/prometheus/api/v1/write?stream=aliyun`. Chaque échantillon devient une ligne dont `metric_name` est son `__name__`. Les autres labels deviennent des champs, et un label nommé comme un champ de métrique, tel que `metric_name`, est conservé sous la forme `exported_<name>`. Les histogrammes natifs et les métadonnées de métrique sont ignorés, et les exemplars sont stockés à côté des échantillons.

## Bulk Elasticsearch

Les émetteurs qui parlent le protocole bulk d'Elasticsearch fonctionnent sans dépendance à Loki ni à OTLP :

```bash
curl -X POST http://localhost:5080/api/v1/_bulk \
  -H "authorization: Bearer $MS_TOKEN" \
  -H 'content-type: application/x-ndjson' \
  --data-binary $'{"index":{"_index":"app"}}\n{"level":"info","msg":"hello"}\n'
```

Le `_index` de chaque action sélectionne le flux cible. Sans lui, l'en-tête `stream-name` s'applique, puis `default`.

## Push Loki

Le point de terminaison accepte la forme de requête JSON de Loki :

```json
{"streams":[{"stream":{"service":"checkout","level":"error"},"values":[["1700000000000000000","payment failed"]]}]}
```

Les labels deviennent des champs, la ligne de log devient le champ `message`, et l'horodatage en nanosecondes est converti en microsecondes. La réponse est `204`. Sélectionnez le flux cible avec l'en-tête `stream-name`.

## Splunk HEC

Les émetteurs qui parlent le protocole Splunk HTTP Event Collector, comme Tencent Cloud CLS envoyant vers Splunk ou les sorties Splunk de Vector et de Fluent Bit, peuvent envoyer vers MoleSignal sans modification. Indiquez-leur `https://molesignal.example.com/api/v1` comme adresse HEC et un API Token autorisé à écrire des logs comme jeton HEC, transmis via `Authorization: Splunk <token>`.

| Endpoint | Corps |
|---|---|
| `POST /api/v1/services/collector/event`, aussi `/services/collector` | Objets JSON les uns après les autres, chacun `{"time", "host", "source", "sourcetype", "index", "event", "fields"}` |
| `POST /api/v1/services/collector/raw` | Texte, un événement de log par ligne ; `host`, `source`, `sourcetype` et `index` proviennent de la requête |
| `GET /api/v1/services/collector/health` | Répond `{"text":"HEC is healthy","code":17}` sans jeton |

Un `event` qui est un objet JSON fournit les champs du log ; tout autre `event` devient `message`. `fields`, `host`, `source` et `sourcetype` deviennent des champs, et `time`, en secondes, devient l'horodatage. `index` désigne le flux, sinon le paramètre de requête `index`, sinon l'en-tête `stream-name`, sinon `default`. La réponse est `{"text":"Success","code":0}`, ou les codes d'erreur propres à HEC avec `400`. Lorsqu'un flux refuse des événements parce qu'une valeur ne correspond pas au type de son champ, les autres événements sont écrits et la réponse porte le code `6`, avec la position du premier événement refusé dans le corps sous `invalid-event-number` et la raison dans `text`. L'acquittement d'indexation n'est pas proposé.
