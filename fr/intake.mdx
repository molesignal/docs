Chaque signal entre dans MoleSignal par l’API d’ingestion. La page **Source de données** de l’interface web génère le point de terminaison, le jeton et l’extrait de configuration pour chaque source. Les mêmes protocoles peuvent aussi se configurer manuellement.

## Page Source de données

Ouvrez **Source de données** pour ajouter une source :

1. Recherchez dans le catalogue ou filtrez-le par catégorie : **Recommandé**, **Infrastructure**, **Cloud**, **Bases de données**, **Messagerie**, **Applications et langages**, **Sécurité** et **Personnalisé**. Les onglets de signal (**Journaux**, **Métriques**, **Traces**, **Profils**) affinent la liste.
2. Sélectionnez une source, par exemple Kubernetes, un hôte Linux, AWS, un SDK OpenTelemetry ou le RUM web.
3. Suivez les trois étapes du guide :
   - **Point de terminaison et jeton** indique où envoyer les données et quel jeton utiliser pour l’authentification. **Afficher le jeton** révèle le jeton, sa portée, son espace de travail et sa date d’expiration. Pour une source RUM, sélectionnez d’abord l’**Application RUM** : son jeton client s’affiche après la sélection.
   - **Configurer la source** affiche les commandes et la configuration avec le point de terminaison et le jeton déjà renseignés.
   - **Vérifier la réception des données** contrôle le récepteur, puis recherche les données reçues au cours de la dernière heure. **Vérifier la connexion** lance la vérification immédiatement. Les chiffres s’actualisent toutes les 30 secondes.
4. Consultez le résultat de la vérification :
   - **Données détectées** : le récepteur a reçu des données au cours de la dernière heure et tous les signaux de la source fonctionnent correctement. **Voir les données reçues** ouvre les données et **Créer un pipeline** lance la création d’un pipeline pour ces données.
   - **Le récepteur fonctionne, mais les données sont à vérifier** : le récepteur répond, mais n’a reçu aucune donnée ou certains signaux présentent des problèmes. Vérifiez le déploiement ou attendez le prochain lot.
   - **Échec de la vérification** : la vérification du récepteur n’a pas abouti. **Causes possibles** répertorie les cas suivants : un collecteur à l’arrêt, un jeton non valide ou expiré, ou un réseau ou un proxy qui bloque l’accès au point de terminaison.

MoleSignal utilise `http.external_url` comme point de terminaison si ce paramètre est défini. Sinon, MoleSignal utilise l’adresse affichée dans le navigateur. Si MoleSignal se trouve derrière un proxy inverse, définissez `http.external_url` pour que les extraits générés utilisent l’adresse publique. Consultez [Configuration](/fr/configuration).

## Jetons d’ingestion

Les émetteurs s’authentifient avec un jeton Bearer : `Authorization: Bearer <token>`.

| Jeton | Autorisation | Création | Utilisation |
|---|---|---|---|
| Jeton d’ingestion par défaut | `logs.write`, `metrics.write`, `traces.write`, `profiles.write` et `apm.deploy` uniquement : stratégie **Ingestion de données** | Page **Source de données** ou `GET /api/v1/me/api-tokens/default` | Collecteurs, agents et exportateurs de SDK qui envoient des journaux, des métriques et des traces, ainsi que pipelines qui [signalent les déploiements](/fr/apm/deployments#signaler-les-déploiements-depuis-la-ci). N’expire pas. |
| Jeton client RUM | `rum.write` uniquement, pour une seule application | Page **Source de données** pour les sources RUM web et mobiles, ou `GET /api/v1/auth/tokens/rum?applicationId=<id>` | Code exécuté dans le navigateur ou dans une application mobile. Les utilisateurs finaux peuvent voir le jeton. |
| Jeton personnel ou de compte de service | Autorisations du membre ou du compte de service, dans les limites de la portée du jeton | **Paramètres du compte → Jetons d’API** ou **Identité et accès → Jetons d’API** pour les comptes de service | Automatisation, scripts et clients MCP. |

Pour les émetteurs qui fonctionnent en continu, utilisez le jeton d’ingestion par défaut ou un jeton de compte de service qui respecte la stratégie **Ingestion de données**. Pour empêcher immédiatement toute utilisation d’un jeton, révoquez-le depuis **Paramètres du compte → Jetons d’API** ou **Identité et accès → Jetons d’API**. Une session de l’interface web ne permet pas d’envoyer des données : le navigateur la conserve dans des cookies et l’en-tête `Authorization` ne l’accepte pas.

La page **Source de données** crée un jeton client RUM à la saisie d’un identifiant d’application. Un identifiant d’application contient de 1 à 128 caractères parmi `A-Z`, `a-z`, `0-9`, `.`, `_`, `:` et `-`. Utilisez le même identifiant pour `applicationId` dans le SDK. Consultez le [SDK RUM pour navigateur](/fr/rum/browser-sdk).

## Points de terminaison et protocoles

| Protocole | Point de terminaison | Émetteurs compatibles | Flux cible |
|---|---|---|---|
| HTTP JSON natif | `POST /api/v1/intake/{logs,metrics,traces}/{stream}` | `curl`, code d’application, sortie `http` de Vector, sortie `http` de Fluent Bit | Segment de chemin `{stream}` |
| OTLP sur HTTP | `POST /api/v1/logs`, `/api/v1/metrics`, `/api/v1/traces` | SDK et collecteur OpenTelemetry | En-tête `stream-name`, sinon `default` |
| OTLP sur gRPC | `:4317` | SDK et collecteur OpenTelemetry | Métadonnée `stream-name`, sinon `default` |
| Prometheus remote_write | `POST /api/v1/prometheus/api/v1/write` | Prometheus, VictoriaMetrics, tout émetteur remote_write v1 | En-tête `stream-name`, sinon `default` |
| Elasticsearch `_bulk` | `POST /api/v1/_bulk` | Filebeat, Logstash, sortie `elasticsearch` de Vector | `_index` de chaque action, sinon en-tête `stream-name`, sinon `default` |
| Loki push (JSON) | `POST /api/v1/loki/api/v1/push` | Émetteurs capables d’envoyer une requête POST au format JSON de Loki | En-tête `stream-name`, sinon `default` |
| Kinesis Firehose, Cloudflare Logpush, Heroku | `/api/v1/_kinesis_firehose`, `/api/v1/_cloudflare`, `/api/v1/_heroku` | AWS, Cloudflare, Heroku | À configurer sur le connecteur. Consultez [Connecteurs](/fr/connectors). |

À l’exception des connecteurs push, tous les points de terminaison exigent un jeton Bearer doté de l’autorisation d’écriture du signal : `logs.write`, `metrics.write`, `traces.write` ou `profiles.write`. Le jeton identifie l’organisation, qui ne figure jamais dans l’URL.

### Limites applicables aux émetteurs

- **Taille des requêtes.** L’ingestion JSON native accepte les corps de requête jusqu’à 16 MiB après décompression. Les autres points de terminaison d’ingestion les acceptent jusqu’à 2 MiB. Si le corps dépasse la limite, le point de terminaison renvoie `413`. Gardez les lots en dessous de la limite applicable.
- **Compression.** OTLP sur HTTP refuse les corps de requête compressés et renvoie `400`. Désactivez la compression côté émetteur. L’exportateur `otlphttp` du collecteur OpenTelemetry utilise gzip par défaut : définissez `compression: none`. L’ingestion JSON native, Elasticsearch `_bulk`, Loki push et les connecteurs push acceptent `Content-Encoding: gzip`.
- **Encodage Loki.** Le point de terminaison ne décode que les requêtes au format JSON. Promtail et Grafana Alloy envoient par défaut du protobuf compressé avec Snappy et ne peuvent pas envoyer de données à ce point de terminaison.
- **Limite de débit.** Le rôle `router` limite le nombre de requêtes par organisation et renvoie `429` avec un en-tête `Retry-After` en cas de dépassement. Un nœud `standalone` n’applique pas cette limite. Consultez [Déploiement par rôle](/fr/deployment/role-based#limitation-du-débit).
- **Flux de la plateforme.** Seul MoleSignal écrit dans les [flux de la plateforme](/fr/streams#flux-de-la-plateforme), tels que `_molesignal` pour la télémétrie du service et `_audit` pour la piste d’audit. Toute tentative d’écriture via l’ingestion publique renvoie `403`.

## Flux et schéma

MoleSignal crée un flux à la première écriture et fait évoluer son schéma à mesure que de nouveaux champs apparaissent. Le nom et le type de signal identifient le flux : `default` peut donc exister en même temps pour les journaux, les métriques et les traces. Consultez [Flux](/fr/streams).

Chaque événement porte un horodatage en microsecondes depuis l’époque Unix. L’ingestion JSON native et Elasticsearch `_bulk` lisent le champ `_timestamp`. Sans champ `_timestamp`, le serveur attribue à l’événement l’heure à laquelle il l’a accepté.

## HTTP JSON natif

Envoyez un tableau d’enregistrements par requête POST à `/api/v1/intake/{logs,metrics,traces}/{stream}` :

```bash
curl -X POST http://localhost:5080/api/v1/intake/logs/app \
  -H "authorization: Bearer $MS_TOKEN" \
  -H 'content-type: application/json' \
  -d "[{\"_timestamp\":$(date +%s)000000,\"level\":\"error\",\"msg\":\"db pool exhausted\",\"trace_id\":\"abc123\"}]"
```

La réponse indique le nombre d’enregistrements acceptés et rejetés, ainsi que le motif du rejet pour chaque index concerné :

```json
{"accepted":1,"rejected":0,"errors":[]}
```

## OpenTelemetry

Configurez un SDK ou un Collector OpenTelemetry pour utiliser le chemin de base `/api`. L’exportateur y ajoute `/v1/logs`, `/v1/metrics` et `/v1/traces` pour obtenir `/api/v1/logs`, `/api/v1/metrics` et `/api/v1/traces`.

<Tabs>
  <Tab title="OTLP sur HTTP">
    Variables d’environnement du SDK :

    ```bash
    export OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf
    export OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:5080/api
    export OTEL_EXPORTER_OTLP_HEADERS="authorization=Bearer ${MS_TOKEN}"
    ```

    Collector OpenTelemetry :

    ```yaml
    exporters:
      otlphttp/molesignal:
        endpoint: http://localhost:5080/api
        compression: none
        headers:
          authorization: "Bearer ${env:MS_TOKEN}"
    ```

    Utilisez protobuf (`application/x-protobuf`), l’encodage par défaut des SDK et du Collector. Les journaux, les métriques et les traces peuvent aussi être envoyés au format JSON (`application/json`). Ajoutez un en-tête `stream-name` pour sélectionner un flux autre que `default`. Cet en-tête s’applique à tous les signaux envoyés par cet exportateur.
  </Tab>
  <Tab title="OTLP sur gRPC">
    Le récepteur OTLP gRPC écoute sur le port `4317` et fournit les services de journaux, de métriques, de traces et de profils. Il ne gère pas la terminaison TLS. Configurez la terminaison TLS en amont du récepteur pour le trafic qui quitte un réseau de confiance.

    ```bash
    export OTEL_EXPORTER_OTLP_PROTOCOL=grpc
    export OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4317
    export OTEL_EXPORTER_OTLP_HEADERS="authorization=Bearer ${MS_TOKEN}"
    ```

    Collector OpenTelemetry :

    ```yaml
    exporters:
      otlp/molesignal:
        endpoint: localhost:4317
        tls:
          insecure: true
        headers:
          authorization: "Bearer ${env:MS_TOKEN}"
    ```

    Supprimez `insecure: true` si un proxy assure la terminaison TLS en amont de ce port. Le port `5082` est le port gRPC interne du cluster et ne reçoit pas de trafic OTLP.
  </Tab>
</Tabs>

MoleSignal stocke les métriques OTLP à raison d’un événement par point de données. Consultez le [contrat de stockage des métriques](/fr/query#champs-des-métriques-otlp) pour connaître les champs stockés.

## Prometheus remote_write

Ajoutez MoleSignal comme cible d’écriture distante dans `prometheus.yml` :

```yaml
remote_write:
  - url: http://localhost:5080/api/v1/prometheus/api/v1/write
    authorization:
      credentials: "${MS_TOKEN}"
```

Un flux de métriques regroupe les métriques d’une seule source. Attribuez à chaque serveur Prometheus son propre flux à l’aide de l’en-tête `stream-name` (`headers:` dans l’entrée `remote_write`). Sans cet en-tête, les échantillons vont dans `default`. Chaque échantillon devient une ligne dont le champ `metric_name` contient la valeur de `__name__`. Les autres libellés deviennent des champs. Si un libellé porte le même nom qu’un champ de métrique, comme `metric_name`, MoleSignal le conserve sous le nom `exported_<name>`. MoleSignal ignore les histogrammes natifs et les métadonnées des métriques, et stocke les exemplaires avec les échantillons.

## Elasticsearch bulk

Les clients qui utilisent le protocole bulk d’Elasticsearch fonctionnent sans dépendance à Loki ni à OTLP :

```bash
curl -X POST http://localhost:5080/api/v1/_bulk \
  -H "authorization: Bearer $MS_TOKEN" \
  -H 'content-type: application/x-ndjson' \
  --data-binary $'{"index":{"_index":"app"}}\n{"level":"info","msg":"hello"}\n'
```

Le champ `_index` de chaque action détermine le flux cible. En son absence, MoleSignal utilise l’en-tête `stream-name`, ou `default` si cet en-tête est absent.

## Loki push

Le point de terminaison accepte les requêtes au format JSON de Loki :

```json
{"streams":[{"stream":{"service":"checkout","level":"error"},"values":[["1700000000000000000","payment failed"]]}]}
```

MoleSignal transforme les libellés en champs, place la ligne de journal dans le champ `message` et convertit l’horodatage de nanosecondes en microsecondes. Le point de terminaison renvoie `204`. Sélectionnez le flux cible avec l’en-tête `stream-name`.
