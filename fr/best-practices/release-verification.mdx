La plupart des incidents commencent par un changement. Avec une mise en production consignée dans les données, la comparaison avec la
version précédente prend quelques minutes. Sans trace de la mise en production, il faut parfois une heure de tâtonnements pour la repérer.
Consignez chaque mise en production, comparez les versions pendant le déploiement et fixez à l’avance les critères de
retour arrière.

## Rendez chaque mise en production visible

| Étape | Procédure | Résultat |
|---|---|---|
| Associez chaque span à une version | Définissez `service.version` dans la ressource OpenTelemetry de chaque service. | La [chronologie des déploiements](/fr/apm/deployments#chronologie-des-déploiements) affiche les versions et leur verdict, même sans déclaration depuis la CI. |
| Déclarez le déploiement depuis la CI | Appelez `POST /api/v1/apm/deployments` avec le service, la version, l’environnement, le commit et l’exécution de CI. Utilisez le jeton d’ingestion par défaut. Consultez [Déclarer les déploiements depuis la CI](/fr/apm/deployments#signaler-les-déploiements-depuis-la-ci). | La chronologie affiche le commit, l’auteur et l’exécution de CI à côté de la version, ainsi que les déploiements en échec ou ayant fait l’objet d’un retour arrière. |
| Déclarez les changements de configuration et de feature flags | Utilisez le même point de terminaison avec `kind` défini sur `configuration` ou `feature_flag`. | Les changements hors mise en production apparaissent à côté des observations de l’APM. |
| Associez le frontend à une version | Renseignez `version` dans le SDK RUM et importez les source maps ou les symboles depuis la même tâche de CI. Consultez [Source maps et symboles](/fr/rum/source-maps). | Les traces de pile sont lisibles et les problèmes RUM indiquent dans quelle version ils sont réapparus. |

Utilisez la même chaîne de version partout : dans le tag de l’image, dans `service.version`, dans la déclaration de déploiement
et comme version RUM.

## Établissez une référence avant la mise en production

Avant le déploiement, relevez les indicateurs du service : le taux d’erreur et la latence P95 des principaux points de terminaison, le
taux de consommation du budget d’erreur des [SLO](/fr/apm#objectifs-de-niveau-de-service) et les problèmes RUM ouverts. Lancez les
[tests synthétiques](/fr/synthetics) des parcours critiques avec **Exécuter maintenant** pour distinguer un échec après la
mise en production d’un échec préexistant.

Consignez les critères de retour arrière, par exemple : le verdict de la version est **Régression** pour les erreurs, un test
synthétique critique échoue deux fois ou une alerte de consommation rapide du budget d’erreur se déclenche.

## Comparez les versions pendant le déploiement

- Tant que deux versions fonctionnent en parallèle, la carte **Canaris** de la section
  [Déploiements](/fr/apm/deployments#versions-canary) les compare côte à côte : la part des requêtes traitées
  par chaque version, les erreurs et la latence, avec le verdict de la nouvelle version.
- Chaque version reçoit un verdict par rapport à la précédente : **Régression**, **Amélioration**, **Aucun changement**
  ou **Nombre de requêtes insuffisant**. La comparaison exige un minimum de 1 000 requêtes par défaut. Maintenez le canari
  assez longtemps pour atteindre ce seuil.
- Sélectionnez un verdict pour ouvrir **Comparer deux versions**. Cette vue indique les points de terminaison dont la latence a augmenté et les
  erreurs devenues plus fréquentes.
- Dans RUM, filtrez l’explorateur et les problèmes d’erreur sur la nouvelle version. Surveillez les problèmes portant le verdict
  **Régression** : ils avaient été résolus, mais sont réapparus dans une version plus récente.

## Automatisez la surveillance de la mise en production

La tâche de CI peut lancer une [automatisation](/fr/automations#lancer-une-automatisation-depuis-la-ci/cd) de Mole Agent pour une
première analyse : l’étape de déploiement active le déclencheur de l’automatisation en lui transmettant une description du changement. Mole Agent suit les
instructions de l’automatisation, par exemple en comparant la nouvelle version à la précédente, puis publie le résultat dans une
conversation. Confiez la décision à une personne.

## Décidez et consignez la décision

Effectuez un retour arrière dès qu’un critère est rempli, sans attendre de confirmation. Déclarez le retour arrière depuis la CI avec
`status` défini sur `rolled_back` pour que la chronologie l’affiche et que les comparaisons suivantes utilisent la bonne référence.

Si la version reste en production, vérifiez les SLO au cours des 24 heures suivantes. Les régressions progressives, comme une fuite de mémoire ou
une file d’attente qui s’allonge, n’apparaissent souvent qu’après plusieurs heures.

## Critères d’acceptation

- Chaque service envoie `service.version` et chaque déploiement en production apparaît dans la chronologie
  des déploiements avec son commit.
- Pour chaque mise en production du frontend, les source maps ou les symboles importés correspondent à la version déclarée.
- Les critères de retour arrière sont consignés avant le déploiement.
- Chaque mise en production reçoit un verdict ou passe par un canari maintenu assez longtemps pour atteindre le seuil de requêtes.
