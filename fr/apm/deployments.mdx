The **Déploiements** section of a service page puts two sources side by side: the deployments that
pipelines report, and the versions that the service's spans carry in `service.version`. A version
that no pipeline reported still appears, from the spans alone.

## La chronologie des déploiements

The timeline lists what happened to the service in the time range, the newest first:

| Événement | Moment |
|---|---|
| **Déployé** | Un pipeline a signalé un déploiement réussi. |
| **Échec** | Un pipeline a signalé un déploiement en échec. Un déploiement en échec ne change pas la version en cours. |
| **État antérieur rétabli** | Un pipeline a signalé un retour arrière, ou signalé le déploiement d'une version qui a tourné avant une autre version. La ligne nomme la version dont le service est revenu. |
| **Retour à la version précédente** | Les spans sont revenus à une version plus ancienne qu'aucun pipeline n'a signalée : la version vue en dernier a été vue pour la première fois avant une version plus récente qui s'est arrêtée plus de cinq minutes auparavant. |
| **Première occurrence** | Les spans portaient une version qu'aucun pipeline n'a signalée. |
| **Configuration** | Un pipeline ou un outil a signalé un changement de configuration. Sa description s'affiche dans la ligne. |
| **Indicateur de fonctionnalité** | Un pipeline ou un outil a signalé un changement d'indicateur de fonctionnalité. Sa description s'affiche dans la ligne. |

Un changement de configuration ou d'indicateur de fonctionnalité ne change pas la version en cours et n'a pas de chiffres
qui lui soient propres. Il figure parmi les changements proches d'un constat ; voir
[Changements proches d'un constat](/fr/apm/insights#changes-near-a-finding).

Un déploiement signalé affiche son commit, sa pull request, son exécution CI et son auteur. Quand le dépôt est une
adresse http ou https, le commit s'ouvre sur sa page web, de la manière dont GitHub, GitLab ou Bitbucket
adressent un commit.

Les requêtes, le taux d'erreur et le p95 de chaque version sur la plage s'affichent sur sa ligne la plus récente, avec le verdict
comparé à la version vue pour la première fois avant elle :

| Verdict | Moment |
|---|---|
| **Régression** | Le taux d'erreur a augmenté d'au moins un point et atteint au moins 1,5 fois, ou le p95 a augmenté d'au moins un cinquième et d'au moins 50 ms. La partie qui s'est dégradée suit le verdict. |
| **Amélioration** | L'un des deux a baissé d'autant, et aucun des deux ne s'est dégradé. |
| **Aucun changement** | Aucun des deux n'a bougé d'autant. |
| **Nombre de requêtes insuffisant** | L'une des versions a servi moins de requêtes qu'une comparaison de versions n'en demande, 1 000 par défaut. |

Sélectionner un verdict ouvre ses deux versions dans **Comparer deux versions**, qui liste les endpoints qui
sont devenus plus lents et les erreurs qui ont augmenté. Une version en régression ou en amélioration est aussi signalée parmi les
déploiements récents de la vue d'ensemble.

## Canaris

Quand deux versions tournent en même temps, comme un canari tourne à côté de la version qu'il remplace, une carte au-dessus de la
chronologie les présente côte à côte. Deux versions tournent en même temps quand les deux ont été vues dans les cinq minutes
qui précèdent le dernier span du service. La carte compare les deux plus récentes, à partir du moment où la plus récente a été
vue pour la première fois :

- la part des requêtes servies par chaque version ;
- les requêtes, le taux d'erreur, le p50, le p95 et le p99 de chaque version ;
- le verdict de la version la plus récente par rapport à la plus ancienne.

## Signaler des déploiements depuis la CI

Un pipeline signale un déploiement avec `POST /api/v1/apm/deployments`. La requête nécessite un jeton d'API
autorisé à utiliser `apm.deploy`. Les propriétaires, administrateurs et éditeurs le possèdent, et la politique **Ingestion de données**
que suivent les jetons d'ingestion l'inclut.

```bash
curl -X POST "https://<host>/api/v1/apm/deployments" \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{"service": "checkout", "environment": "production", "version": "2.4.0", "commit": "9f2c1e7a4b3d", "repository": "https://github.com/acme/checkout", "ciUrl": "https://ci.example.com/runs/7"}'
```

| Champ | Obligatoire | Description |
|---|---|---|
| `service` | Oui | Le service, tel que ses spans le nomment dans `service.name`. Jusqu'à 255 caractères. |
| `version` | Pour un déploiement | La version déployée, telle que ses spans la rapportent dans `service.version`. Jusqu'à 192 caractères. |
| `kind` | Non | `deployment` (valeur par défaut), `configuration`, `feature_flag`, `scaling` ou `infrastructure`. |
| `namespace` | Non | Le `service.namespace` du service. Un déploiement sans namespace s'affiche dans tous les namespaces. |
| `environment` | Non | L'environnement, selon `deployment.environment.name`. Un déploiement sans environnement s'affiche dans tous les environnements. |
| `status` | Non | `succeeded` (valeur par défaut), `failed` ou `rolled_back` quand le déploiement a ramené le service à `version`. |
| `commit` | Non | Le commit déployé : jusqu'à 64 lettres et chiffres. |
| `repository` | Non | Où vit le code : une adresse https, http, ssh ou git de 512 caractères maximum. Un mot de passe présent dans l'adresse est conservé sous la forme `****`, tout comme la partie utilisateur d'une adresse https. |
| `pullRequest` | Non | Un lien http ou https vers la pull request. |
| `author` | Non | Qui a déployé, jusqu'à 128 caractères. |
| `ciUrl` | Non | Un lien http ou https vers l'exécution CI. |
| `description` | Non | Jusqu'à 1 000 caractères. Elle s'affiche quand le pointeur survole l'événement. |
| `deployedAt` | Non | Quand le déploiement a eu lieu, en microsecondes depuis l'epoch. Vaut par défaut l'heure d'arrivée de la requête. |

Le service et l'environnement sont nommés comme APM les nomme : les règles de nommage de l'organisation,
le mappage d'environnements et les alias s'y appliquent, comme ils s'appliquent aux spans. Voir
[Paramètres APM](/fr/apm/settings).

La page **Source de données** reprend les étapes ci-dessous sous **GitHub Actions**, **GitLab CI/CD** et
**Jenkins**, avec l'adresse du workspace renseignée.

### GitHub Actions

Conservez le jeton comme secret de dépôt, puis ajoutez une étape au job qui déploie. `if: always()`
signale aussi un déploiement en échec.

```yaml
- name: Report the deployment to MoleSignal
  if: always()
  env:
    MOLESIGNAL_TOKEN: ${{ secrets.MOLESIGNAL_TOKEN }}
    DEPLOY_STATUS: ${{ job.status == 'success' && 'succeeded' || 'failed' }}
  run: |
    cat > deployment.json <<EOF
    {
      "service": "checkout",
      "environment": "production",
      "version": "${GITHUB_SHA::12}",
      "status": "$DEPLOY_STATUS",
      "commit": "$GITHUB_SHA",
      "repository": "$GITHUB_SERVER_URL/$GITHUB_REPOSITORY",
      "author": "$GITHUB_ACTOR",
      "ciUrl": "$GITHUB_SERVER_URL/$GITHUB_REPOSITORY/actions/runs/$GITHUB_RUN_ID"
    }
    EOF
    curl -fsS -X POST "https://<host>/api/v1/apm/deployments" \
      -H "Authorization: Bearer $MOLESIGNAL_TOKEN" \
      -H "Content-Type: application/json" \
      --data-binary @deployment.json
```

### GitLab CI/CD

Ajoutez le jeton comme variable CI/CD masquée nommée `MOLESIGNAL_TOKEN`, puis signalez depuis le
`after_script` du job de déploiement, qui s'exécute que le déploiement ait réussi ou non.

```yaml
deploy:
  stage: deploy
  environment: production
  script:
    - ./deploy.sh
  after_script:
    - |
      if [ "$CI_JOB_STATUS" = "success" ]; then DEPLOY_STATUS=succeeded; else DEPLOY_STATUS=failed; fi
      cat > deployment.json <<EOF
      {
        "service": "checkout",
        "environment": "$CI_ENVIRONMENT_NAME",
        "version": "$CI_COMMIT_SHORT_SHA",
        "status": "$DEPLOY_STATUS",
        "commit": "$CI_COMMIT_SHA",
        "repository": "$CI_PROJECT_URL",
        "author": "$GITLAB_USER_LOGIN",
        "ciUrl": "$CI_PIPELINE_URL"
      }
      EOF
      curl -fsS -X POST "https://<host>/api/v1/apm/deployments" \
        -H "Authorization: Bearer $MOLESIGNAL_TOKEN" \
        -H "Content-Type: application/json" \
        --data-binary @deployment.json
```

### Jenkins

Ajoutez le jeton comme identifiant **Texte secret** avec l'ID `molesignal-token`, puis signalez dans le
bloc `post` du pipeline. `post { always }` signale aussi une build en échec. Un mot de passe dans `GIT_URL` est
masqué quand le déploiement est conservé.

```groovy
post {
  always {
    script {
      writeFile file: 'deployment.json', text: groovy.json.JsonOutput.toJson([
        service: 'checkout',
        environment: 'production',
        version: env.GIT_COMMIT.take(12),
        status: currentBuild.currentResult == 'SUCCESS' ? 'succeeded' : 'failed',
        commit: env.GIT_COMMIT,
        repository: env.GIT_URL,
        ci_url: env.BUILD_URL,
      ])
    }
    withCredentials([string(credentialsId: 'molesignal-token', variable: 'MOLESIGNAL_TOKEN')]) {
      sh '''
        curl -fsS -X POST "https://<host>/api/v1/apm/deployments" \
          -H "Authorization: Bearer $MOLESIGNAL_TOKEN" \
          -H "Content-Type: application/json" \
          --data-binary @deployment.json
      '''
    }
  }
}
```

## Signaler des changements de configuration et des indicateurs de fonctionnalité

Signalez un changement de configuration, un indicateur de fonctionnalité, un changement d'échelle ou un changement d'infrastructure
sous un service avec le même endpoint, en définissant `kind` et une description de ce qui a changé. Aucune
version n'est nécessaire.

Chaque changement signalé est aussi listé par [`GET /api/v1/changes`](/fr/api/changes), marqué sur les
histogrammes de Logs et Traces et sous le graphique Metrics, ainsi que sur la page **Changements** d'Alerts.

```bash
curl -X POST "https://<host>/api/v1/apm/deployments" \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{"service": "checkout", "environment": "production", "kind": "feature_flag", "description": "new_checkout on for 10% of users"}'
```

## Signaler des changements depuis des webhooks

Un outil dont le webhook peut définir le corps et un en-tête, comme les notifications Argo CD, Spinnaker ou
le module complémentaire webhook d'Unleash avec un modèle de corps, appelle `POST /api/v1/apm/deployments` comme ci-dessus. Un outil qui
envoie son propre corps, ou qui ne peut pas définir d'en-tête, appelle plutôt `POST /api/v1/intake/changes`. Le jeton d'API
se place dans `Authorization: Bearer` ou, lorsque aucun en-tête ne peut être défini, dans `?token=`, et doit porter
la portée `apm.deploy`. Un jeton dans une adresse peut finir dans les journaux du proxy : donnez à un tel outil un jeton à part,
limité à `apm.deploy` uniquement.

| Paramètre | Remarques |
|---|---|
| `format` | `generic` (la valeur par défaut), `launchdarkly`, `unleash`, `nacos` ou `apollo`. |
| `service`, `namespace`, `environment` | Ce que le corps ne précise pas. Un changement qui ne nomme aucun service est refusé. |
| `kind` | `deployment`, `configuration`, `feature_flag`, `scaling` ou `infrastructure` ; prévaut sur ce que dit le corps. |
| `serviceField`, `environmentField`, `versionField`, `descriptionField`, `authorField` | Pour `generic` : un pointeur JSON tel que `/app/name`, ou un nom de champ de premier niveau. Sans cela, c'est le champ de même nom accepté par `POST /api/v1/apm/deployments` qui est lu. |

| Format | Interprété comme |
|---|---|
| `launchdarkly` | Un feature flag. L'environnement est la partie `env/` de la ressource auditée, la description le titre de l'entrée, l'auteur l'e-mail du membre. |
| `unleash` | Un feature flag : le type d'événement et le nom du toggle, son environnement, et qui l'a effectué. |
| `nacos` | Un changement de configuration du data ID et du groupe ; l'espace de noms Nacos correspond au paramètre `namespace`. |
| `apollo` | Un changement de configuration : l'ID d'application est le service, le cluster l'environnement, et l'espace de noms et le titre de release ce qui a changé. |

**Sources de données → DevOps** propose un guide pour chacun de LaunchDarkly, Unleash, Nacos et Apollo, avec
l'adresse préremplie pour l'espace de travail.

Un corps peut contenir un changement ou une liste de 100 au maximum. La réponse est `201` avec les changements conservés. Les
préréglages ont été écrits d'après les charges utiles documentées des outils et n'ont pas été vérifiés sur des
comptes réels ; lorsque la charge utile d'un outil diffère, utilisez `generic` avec des pointeurs.

```bash
curl -X POST "https://<host>/api/v1/intake/changes?format=launchdarkly&service=checkout&token=<token>" \
  -H "Content-Type: application/json" \
  -d @launchdarkly-event.json
```

## Dépannage

| Symptôme | Vérification |
|---|---|
| Un déploiement signalé est absent de la chronologie | La plage de temps doit inclure `deployedAt`, et `service` doit nommer le service comme le fait l'APM. Un déploiement signalé avec un environnement n'apparaît que dans cet environnement. |
| Un déploiement et la version qu'il a déployée apparaissent sur deux lignes | La `version` signalée diffère de `service.version` portée par les spans. Signalez la même valeur. |
| `403` renvoyé par le point de terminaison des déploiements | Le jeton n'a peut-être pas le droit d'utiliser `apm.deploy` : sa portée l'exclut, ou son membre ou compte de service ne le possède pas. |
| `400` renvoyé par le point de terminaison des déploiements | Un champ dépasse une limite du tableau ci-dessus ; l'erreur indique lequel. |
