La section **Déploiements** de la page d’un service présente côte à côte deux sources : les déploiements que
les pipelines signalent et les versions que les spans du service indiquent dans `service.version`. Une version
qu’aucun pipeline n’a signalée apparaît quand même, d’après les seuls spans.

## Chronologie des déploiements

La chronologie répertorie les événements du service sur la période sélectionnée, du plus récent au plus ancien :

| Événement | Quand |
|---|---|
| **Déployé** | Un pipeline a signalé un déploiement réussi. |
| **Échec** | Un pipeline a signalé l’échec d’un déploiement. Un échec de déploiement ne change pas la version en cours d’exécution. |
| **État antérieur rétabli** | Un pipeline a signalé un retour à une version antérieure ou le déploiement d’une version qui s’exécutait avant une autre. La ligne indique la version que ce retour a remplacée. |
| **Retour à la version précédente** | Les spans indiquent un retour à une version antérieure qu’aucun pipeline n’a signalée : la dernière version observée est apparue pour la première fois avant une version plus récente qui a cessé de s’exécuter plus de cinq minutes auparavant. |
| **Première occurrence** | Les spans indiquent une version qu’aucun pipeline n’a signalée. |
| **Configuration** | Un pipeline ou un outil a signalé une modification de la configuration. La ligne affiche sa description. |
| **Indicateur de fonctionnalité** | Un pipeline ou un outil a signalé une modification d’un indicateur de fonctionnalité. La ligne affiche sa description. |

Ni une modification de la configuration ni un changement d’indicateur de fonctionnalité ne modifient la version en cours d’exécution ni ne donnent lieu à des
statistiques propres. Ces événements figurent parmi les changements proches d’un constat. Consultez
[Changements proches d’un constat](/fr/apm/insights#changements-autour-d’un-constat).

Un déploiement signalé affiche son commit, sa pull request, son exécution CI et son auteur. Si le dépôt a une
adresse http ou https, le lien ouvre la page du commit selon le format d’URL que GitHub, GitLab ou Bitbucket
utilise pour les commits.

La ligne la plus récente de chaque version affiche le nombre de requêtes, le taux d’erreur et le p95 sur la période, ainsi que le verdict
de la comparaison avec la version dont la première occurrence précède celle de cette version :

| Verdict | Quand |
|---|---|
| **Régression** | Le taux d’erreur a augmenté d’au moins un point et atteint au moins 1,5 fois sa valeur précédente, ou le p95 a augmenté d’au moins 20 % et d’au moins 50 ms. La mesure qui s’est dégradée figure après le verdict. |
| **Amélioration** | L’une des deux mesures a baissé d’autant, sans dégradation de l’autre. |
| **Aucun changement** | Aucune des deux mesures n’a varié à ce point. |
| **Nombre de requêtes insuffisant** | Au moins une des deux versions a traité moins de requêtes que le minimum nécessaire à la comparaison, soit 1 000 par défaut. |

Sélectionnez un verdict pour ouvrir les deux versions dans **Comparer deux versions**. Cette vue répertorie les points de terminaison
qui ont ralenti et les erreurs qui sont devenues plus fréquentes. La vue d’ensemble signale aussi les versions en régression ou en amélioration parmi
les déploiements récents.

## Versions canary

Lorsque deux versions s’exécutent en même temps, par exemple une version canary et celle qu’elle remplace, une carte au-dessus de la
chronologie les compare côte à côte. Deux versions s’exécutent en même temps si chacune apparaît dans les cinq minutes qui précèdent
le dernier span du service. La carte compare les deux versions les plus récentes à partir de la
première occurrence de la plus récente :

- la part des requêtes que chaque version a traitées ;
- le nombre de requêtes, le taux d’erreur, le p50, le p95 et le p99 de chaque version ;
- le verdict de la comparaison entre la version la plus récente et la plus ancienne.

## Signaler les déploiements depuis la CI

Un pipeline signale un déploiement avec `POST /api/v1/apm/deployments`. La requête nécessite un jeton d’API
autorisé à utiliser `apm.deploy`. Les propriétaires, les administrateurs et les éditeurs disposent de cette autorisation. La politique **Ingestion de données**
qui s’applique aux jetons d’ingestion l’inclut aussi.

```bash
curl -X POST "https://<host>/api/v1/apm/deployments" \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{"service": "checkout", "environment": "production", "version": "2.4.0", "commit": "9f2c1e7a4b3d", "repository": "https://github.com/acme/checkout", "ciUrl": "https://ci.example.com/runs/7"}'
```

| Champ | Obligatoire | Description |
|---|---|---|
| `service` | Oui | Le nom du service tel que ses spans l’indiquent dans `service.name`. Jusqu’à 255 caractères. |
| `version` | Pour un déploiement | La version déployée telle que ses spans l’indiquent dans `service.version`. Jusqu’à 192 caractères. |
| `kind` | Non | `deployment` (par défaut), `configuration` ou `feature_flag`. |
| `namespace` | Non | La valeur de `service.namespace` du service. Un déploiement sans espace de noms apparaît dans tous les espaces de noms. |
| `environment` | Non | L’environnement, tel qu’indiqué dans `deployment.environment.name`. Un déploiement sans environnement apparaît dans tous les environnements. |
| `status` | Non | `succeeded` (par défaut), `failed` ou `rolled_back` si le déploiement a rétabli la version `version` du service. |
| `commit` | Non | Le commit déployé : jusqu’à 64 lettres et chiffres. |
| `repository` | Non | L’adresse https, http, ssh ou git du dépôt de code, jusqu’à 512 caractères. MoleSignal enregistre les mots de passe présents dans l’adresse sous la forme `****`, tout comme la partie utilisateur d’une adresse https. |
| `pullRequest` | Non | Un lien http ou https vers la pull request. |
| `author` | Non | L’auteur du déploiement, jusqu’à 128 caractères. |
| `ciUrl` | Non | Un lien http ou https vers l’exécution CI. |
| `description` | Non | Jusqu’à 1 000 caractères. Survolez l’événement pour afficher la description. |
| `deployedAt` | Non | La date et l’heure du déploiement, en microsecondes depuis l’époque Unix. Par défaut, la valeur correspond à l’heure de réception de la requête. |

Utilisez les mêmes noms de service et d’environnement que dans l’APM : les règles de nommage de l’organisation,
les correspondances d’environnements et les alias s’appliquent comme pour les spans. Consultez
[Paramètres APM](/fr/apm/settings).

La page **Source de données** reprend les étapes ci-dessous dans les sections **GitHub Actions**, **GitLab CI/CD** et
**Jenkins**, avec l’adresse de l’espace de travail déjà renseignée.

### GitHub Actions

Enregistrez le jeton comme secret du dépôt, puis ajoutez une étape à la tâche de déploiement. `if: always()`
permet aussi de signaler un échec de déploiement.

```yaml
- name: Report the deployment to MoleSignal
  if: always()
  env:
    MOLESIGNAL_TOKEN: ${{ secrets.MOLESIGNAL_TOKEN }}
    DEPLOY_STATUS: ${{ job.status == 'success' && 'succeeded' || 'failed' }}
  run: |
    cat > deployment.json <<EOF
    {
      "service": "checkout",
      "environment": "production",
      "version": "${GITHUB_SHA::12}",
      "status": "$DEPLOY_STATUS",
      "commit": "$GITHUB_SHA",
      "repository": "$GITHUB_SERVER_URL/$GITHUB_REPOSITORY",
      "author": "$GITHUB_ACTOR",
      "ciUrl": "$GITHUB_SERVER_URL/$GITHUB_REPOSITORY/actions/runs/$GITHUB_RUN_ID"
    }
    EOF
    curl -fsS -X POST "https://<host>/api/v1/apm/deployments" \
      -H "Authorization: Bearer $MOLESIGNAL_TOKEN" \
      -H "Content-Type: application/json" \
      --data-binary @deployment.json
```

### GitLab CI/CD

Ajoutez le jeton comme variable CI/CD masquée nommée `MOLESIGNAL_TOKEN`, puis signalez le déploiement depuis le bloc
`after_script` de la tâche de déploiement. Ce bloc s’exécute que le déploiement réussisse ou échoue.

```yaml
deploy:
  stage: deploy
  environment: production
  script:
    - ./deploy.sh
  after_script:
    - |
      if [ "$CI_JOB_STATUS" = "success" ]; then DEPLOY_STATUS=succeeded; else DEPLOY_STATUS=failed; fi
      cat > deployment.json <<EOF
      {
        "service": "checkout",
        "environment": "$CI_ENVIRONMENT_NAME",
        "version": "$CI_COMMIT_SHORT_SHA",
        "status": "$DEPLOY_STATUS",
        "commit": "$CI_COMMIT_SHA",
        "repository": "$CI_PROJECT_URL",
        "author": "$GITLAB_USER_LOGIN",
        "ciUrl": "$CI_PIPELINE_URL"
      }
      EOF
      curl -fsS -X POST "https://<host>/api/v1/apm/deployments" \
        -H "Authorization: Bearer $MOLESIGNAL_TOKEN" \
        -H "Content-Type: application/json" \
        --data-binary @deployment.json
```

### Jenkins

Ajoutez le jeton comme identifiant de type **Secret text** avec l’ID `molesignal-token`, puis signalez le déploiement dans le
bloc `post` du pipeline. `post { always }` permet aussi de signaler un échec de compilation. MoleSignal masque tout mot de passe dans `GIT_URL`
lors de l’enregistrement du déploiement.

```groovy
post {
  always {
    script {
      writeFile file: 'deployment.json', text: groovy.json.JsonOutput.toJson([
        service: 'checkout',
        environment: 'production',
        version: env.GIT_COMMIT.take(12),
        status: currentBuild.currentResult == 'SUCCESS' ? 'succeeded' : 'failed',
        commit: env.GIT_COMMIT,
        repository: env.GIT_URL,
        ci_url: env.BUILD_URL,
      ])
    }
    withCredentials([string(credentialsId: 'molesignal-token', variable: 'MOLESIGNAL_TOKEN')]) {
      sh '''
        curl -fsS -X POST "https://<host>/api/v1/apm/deployments" \
          -H "Authorization: Bearer $MOLESIGNAL_TOKEN" \
          -H "Content-Type: application/json" \
          --data-binary @deployment.json
      '''
    }
  }
}
```

## Signaler les modifications de configuration et d’indicateurs de fonctionnalité

Utilisez le même point de terminaison pour signaler une modification de la configuration ou d’un indicateur de fonctionnalité. Renseignez `kind` et
décrivez le changement. Aucune version n’est nécessaire.

```bash
curl -X POST "https://<host>/api/v1/apm/deployments" \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{"service": "checkout", "environment": "production", "kind": "feature_flag", "description": "new_checkout on for 10% of users"}'
```

## Dépannage

| Symptôme | Vérification |
|---|---|
| Un déploiement signalé n’apparaît pas dans la chronologie | Vérifiez que la période sélectionnée inclut `deployedAt` et que `service` reprend le nom du service dans l’APM. Un déploiement signalé avec un environnement n’apparaît que dans cet environnement. |
| Un déploiement et la version qu’il a déployée apparaissent sur deux lignes | La valeur de `version` signalée diffère de celle de `service.version` dans les spans. Signalez la même valeur. |
| Le point de terminaison des déploiements renvoie `403` | Le jeton ne peut pas utiliser `apm.deploy` : son périmètre n’inclut pas cette autorisation, ou le membre ou le compte de service associé ne la possède pas. |
| Le point de terminaison des déploiements renvoie `400` | Un champ ne respecte pas une limite du tableau ci-dessus. Le message d’erreur indique lequel. |
