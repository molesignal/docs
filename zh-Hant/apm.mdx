MoleSignal APM 把後端 OpenTelemetry trace span 轉換成有界 RED 聚合，無需另行維護指標埋點，即可發現慢服務、失敗端點、高開銷相依性、重複出現的後端錯誤，以及部署版本之間的效能回退。服務目錄記錄每個服務由誰負責、有多重要。

<Note>
  APM 不需要另一套 SDK，也不會新增遙測資料流。發送完整埋點的 trace 後，MoleSignal 會在呼叫鏈去重之後、尾端取樣之前衍生 APM 資料。因此，最終因取樣而被丟棄的 trace 仍可計入 APM 指標，被[即時管線](/zh-Hant/pipelines#鏈路)丟掉的 span 也一樣。
</Note>

## 頁面

APM 以總覽為首頁，每個服務有自己的頁面。

| 頁面 | 主要用途 |
|---|---|
| **總覽** | 所有服務一起看：活躍服務、輸送量、錯誤率、p95 及 p50、p90、p99 和平均耗時、Apdex；服務健康的分佈和變化；最慢、錯誤率最高和流量最大的服務；洞察，即和上一時段、上週同時段相比有變化的指標、附近的變更，以及可以節省時間的地方；指向服務的進行中警示；時間範圍內部署的版本；環境分佈；以及服務在埋點中缺少什麼。 |
| **服務** | 服務目錄：APM 看到的每個服務和已登記的服務，含負責人、等級、標籤、進行中警示、輸送量、錯誤率、延遲、版本和最近部署。收藏的服務排在最前，已封存的服務預設不顯示。 |
| **服務地圖** | 一個環境中的服務及其相互呼叫、它們呼叫的物件，以及發布和取用的 Topic；與上一時段相比新增或消失的呼叫會標出來。見 [APM 服務地圖](/zh-Hant/apm/service-map#apm-服務地圖)。 |
| **錯誤** | 所有服務的後端錯誤分組，含狀態、團隊和處理人、錯誤發生的分佈，以及分組用的聚合規則。 |
| **SLO** | 服務等級目標：每個目標在視窗內的達成率、剩餘錯誤預算、預算消耗速度和狀態。 |
| **設定** | 組織的健康判定線、預設 Apdex 閾值、長時間工作、服務目錄要求、命名規則、環境對應和服務別名，以及過去一天的資料對這些設定的提示；平台的基數上限和呼叫鏈取樣。見 [APM 設定](/zh-Hant/apm/settings)。 |

服務頁面包含以下分區：

| 分區 | 主要用途 |
|---|---|
| **總覽** | 並排展示請求、錯誤率和延遲，以及這個服務的洞察、SLO，宣告了[業務鍵](/zh-Hant/business-context)時按業務鍵拆分的請求，延遲分佈、下游耗時、耗時最多的端點和最常見的錯誤。 |
| **端點** | 按請求數、錯誤、延遲或耗時佔比排列 HTTP、RPC、訊息和背景工作入口。端點在抽屜中開啟，含狀態碼、耗時拆解和最慢的請求。以星號標出關鍵交易，列表也可以只顯示關鍵交易或長時間工作。 |
| **呼叫鏈** | 這個服務參與的 trace，使用 Traces 頁面的呼叫鏈表格。 |
| **相依性** | 呼叫這個服務的服務，以及按目標分組的下游呼叫，操作列在目標下；每個目標的健康評分、逾時和重試的呼叫，以及最慢的 SQL 語句。 |
| **錯誤** | 這個服務的錯誤分組。 |
| **部署** | 管線上報的發布與 Span 中觀測到的版本放在一起，標出回滾，每個版本與上一版本相比的結論，同時執行的兩個版本並排比較，以及兩個版本的比較。見[部署](/zh-Hant/apm/deployments)。 |
| **執行階段** | 執行這個服務的執行個體及每個執行個體的請求情況，來自處理程序和服務所用語言執行階段指標的圖表，以及來自 Profile 的火焰圖。 |
| **設定** | 服務目錄項目和關鍵交易，以及執行個體上報的資訊。 |

服務名稱後面的一行說明服務的基本情況，並跟隨目前選擇的環境和版本：

| 資訊 | 來源 |
|---|---|
| 健康狀態 | 時間範圍內的 RED 指標，懸停可查看原因。時間範圍內沒有請求時顯示**此時間範圍內沒有資料**：沒有收到遙測不代表服務不健康。 |
| 等級 | 服務目錄項目。 |
| 所屬系統和環境 | `service.namespace` 和 `deployment.environment.name`。 |
| 服務類型 | 服務承接的入口 Span：**HTTP**、**RPC**、訊息的**訊息取用**、內部入口 Span 的**背景工作**。 |
| 語言 / 框架 | `telemetry.sdk.language`，以及服務入口 Span 的插樁程式庫，例如 Axum、Spring 或 Express。 |
| 版本 | 選取的版本；未選擇時為時間範圍內執行個體曾執行的所有版本，執行個體數最多的在前。漸進式發布時會同時顯示兩個版本。 |
| 負責團隊 | 服務目錄項目。懸停可查看負責人和目前值班人。 |
| 執行個體數 | 目前版本在時間範圍內上報過的執行個體數。點擊開啟**執行階段**。 |
| 最近部署 | 目前版本（未選擇時為最新版本）首次出現的時間。 |
| 部署區域 | 執行個體的 `cloud.region`。 |
| 程式碼儲存庫 | 執行個體的 `vcs.repository.url.full` 或 `git.repository_url`；沒有上報時使用服務目錄項目中的儲存庫。 |
| 其他叫法 | 服務目錄項目中的其他叫法：顯示第一個，以及還有幾個。 |

已封存的服務在這一列還會顯示**已封存**。標題列末尾的**收藏**把服務加入自己的收藏。

導覽卡片末尾會連結到服務的日誌、指標和 Profiles。在目前時間範圍終點前的一天內，某個訊號帶有這個服務時，對應連結會點亮。MoleSignal 每五分鐘重新查看一次：

| 訊號 | 點亮條件 |
|---|---|
| 日誌 | 某個含 `service.name`、`service_name` 或 `service` 欄位的日誌資料流中有這個服務的日誌。連結在該資料流上開啟日誌頁面。 |
| 指標 | 最近一小時內有帶這個服務 `service.name` 的指標序列。 |
| Profiles | Profile 資料流中有這個服務的 Profile。 |
| RUM | 服務的樣本呼叫鏈中有來自瀏覽器工作階段的請求。只在這種情況下顯示，點擊開啟該工作階段。 |

沒有資料的訊號會變暗，點擊開啟**資料來源**中對應的串接頁面。檢視失敗或超過三秒時，連結既不點亮也不變暗。

## 串接前提

- 把 OpenTelemetry trace 傳送到 MoleSignal 的[呼叫鏈收集端點](/zh-Hant/intake)；
- 在組織工作區擁有 `apm.services.read`；或者
- 在受保護的 `_sys` 遙測範圍擁有 `sys.telemetry.read`。

## 為服務串接 APM

<Steps>
  <Step title="設定穩定的服務資源屬性">
    每個服務都要設定 `service.name`。如果需要篩選服務或比較部署，再新增命名空間、環境、版本和執行個體屬性。

    ```bash
    export OTEL_SERVICE_NAME=checkout
    export OTEL_RESOURCE_ATTRIBUTES="service.namespace=shop,deployment.environment.name=production,service.version=2.4.0,service.instance.id=checkout-01"
    ```

    具體設定方式取決於使用的 OpenTelemetry SDK 或 Collector。
  </Step>
  <Step title="使用正確的 span kind">
    為入站請求建立 `SERVER` span，為取用的訊息建立 `CONSUMER` span。為下游呼叫建立 `CLIENT` 或 `PRODUCER` span。MoleSignal 透過 span kind 區分交易與相依性。
  </Step>
  <Step title="記錄狀態與例外">
    設定 OpenTelemetry span 狀態、HTTP 或 RPC 狀態屬性，並記錄 exception event。MoleSignal 用這些資訊區分成功與失敗，並建立後端錯誤群組。
  </Step>
  <Step title="傳送 trace 並開啟 APM">
    傳送 OTLP trace，然後開啟 **應用程式效能 → 服務**。將全域時間範圍保持在近期有流量的區間，等待投影器寫入首批資料桶。
  </Step>
</Steps>

### 建議的資源屬性

| 屬性 | 作用 | 缺失時 |
|---|---|---|
| `service.name` | 穩定的服務識別。每個服務都應明確設定。 | `unknown_service` |
| `service.namespace` | 區分不同系統或團隊中的同名服務。 | `default` |
| `deployment.environment.name` | 篩選正式、預發等環境。 | 依序使用舊屬性 `deployment.environment` 和 `unknown` |
| `service.version` | 支援版本歷程與部署比較。 | 不提供版本拆分 |
| `service.instance.id` | 區分執行個體。 | 依序使用 `k8s.pod.name` 和 `host.name` |
| `telemetry.sdk.language` | 在服務目錄中顯示執行階段語言。 | 存在時使用 `process.runtime.name` |
| `cloud.region`、`k8s.*`、`host.name`、`container.name`、`container.id` | 說明每個執行個體執行在哪裡。 | 不顯示 |
| `process.runtime.name`、`process.runtime.version` | 顯示每個執行個體的執行階段。 | 不顯示 |
| `vcs.repository.url.full`、`vcs.ref.head.revision` | 連結程式碼儲存庫並顯示提交。也支援 `git.repository_url` 和 `git.commit.sha`。 | 服務目錄項目中的儲存庫 |

Kubernetes 屬性和 `cloud.region` 通常由 OpenTelemetry Collector 的 `k8sattributes` 和 `resourcedetection` 處理器新增，而不是由 SDK 設定。

請使用低基數值。不要把請求 ID、原始 URL、使用者 ID 或其他無界值放進服務、環境、版本、路由、操作或相依性屬性。

## APM 資料如何衍生

### 服務與端點

`SERVER` 和 `CONSUMER` span 會計入服務與端點 RED 指標。API 把端點稱為交易（transaction）。沒有 kind 且沒有父 span 的資料可作為服務總量的相容回退，但明確的 span kind 才能產生更完整的頁面。

MoleSignal 會從語意屬性建構有界端點名稱：

- HTTP 方法與 `http.route`，例如 `POST /checkout`；
- RPC 服務與方法；
- 訊息操作與目標端；
- 沒有更強語意識別時，使用安全、低基數的 span 名稱。

請使用 `/orders/{id}` 這樣的路由範本，不要使用 `/orders/83921` 這樣的原始路徑。

### 相依性

`CLIENT` 和 `PRODUCER` span 會計入相依性 RED 指標。MoleSignal 會把目標分類為服務、資料庫、快取、訊息系統、外部 HTTP、外部 RPC 或其他相依性。標準的 `peer.service`、`db.*`、`messaging.*`、`rpc.*`、`server.*` 和 HTTP 語意屬性可以提升相依性識別的品質。

沒有 `peer.service` 的資料庫或快取呼叫以資料庫系統為目標，例如 `postgresql` 或 `redis`。設定了 [`MS_TRACE_FINGERPRINT_KEY`](/zh-Hant/configuration#環境變數) 時，目標還會帶上 `db.namespace`（沒有時取 `db.name` 或 `db.collection.name`）的帶金鑰指紋，例如 `postgresql:<指纹>`，這樣同一系統的不同資料庫可以分開統計，又不儲存資料庫名稱。

SQL 資料庫呼叫的操作名稱是語句範本：取 `db.query.summary`，沒有時取 `db.query.text` 或 `db.statement`，所有字面值都替換為 `?`，移除註解，值清單合併為一個 `?`，最多保留 512 位元組。雙引號中的文字只在把它當作資料表名稱或資料行名稱的資料庫（如 PostgreSQL、Oracle）中保留，在其他資料庫中當作值處理。沒有語句的呼叫使用 `db.operation.name`，快取呼叫使用其命令名稱。一個服務對同一目標每小時最多區分 32 個操作，其餘操作在同一目標下合併為**其他**。

逾時的請求（錯誤類型為逾時、gRPC `DEADLINE_EXCEEDED`、HTTP 408 或 504）和重送的請求（`http.request.resend_count` 大於 0）會在 RED 指標旁單獨計數。

### 錯誤

span 包含例外、OpenTelemetry 狀態為 `ERROR`、HTTP 狀態碼不低於 500，或 RPC 狀態非零時，MoleSignal 會把該 span 判定為錯誤。錯誤群組的穩定指紋由錯誤類型、第一個應用程式堆疊影格和交易名稱組成；經常變化的錯誤訊息不參與指紋計算。[聚合規則](#使用規則彙總錯誤)可以把錯誤合併為一組，或讓它們不再成組。

## 理解 RED 指標

| 指標 | 含義 |
|---|---|
| **請求數** | 符合的服務、端點或相依性觀測數量。 |
| **錯誤率** | 錯誤數除以請求數。 |
| **延遲** | 從合併後的延遲直方圖讀出的 p50、p90、p95 和 p99，以及平均耗時。 |
| **Apdex** | 不超過閾值 T 的請求加上不超過 4T 的請求的一半，除以全部請求。T 為組織的預設值（未在 [APM 設定](/zh-Hant/apm/settings#健康判定與閾值)中修改時為 500 ms），服務目錄項目也可以為服務設定自己的 T，延遲分布會註明目前使用的 T。總覽會把所有服務合在一起，按組織的預設值計算。出錯的請求一律不算滿意：錯誤按比例從各個耗時中扣除。 |
| **總耗時** | 所有觀測耗時之和，用於發現整體影響最大的工作。 |

錯誤率達到 2% 或 p95 達到 500 ms 的服務為**警告**，達到 10% 或 2 s 為**嚴重**；[APM 設定](/zh-Hant/apm/settings#健康判定與閾值)可以改用其他判定線。服務頁面和目錄中的狀態點會說明是哪項指標超過了哪條線。

**洞察**卡片列出和上一段同樣長的時間、上週同時段相比有突變的服務，見[洞察的種類](/zh-Hant/apm/insights#洞察的類型)。

延遲直方圖把延遲每翻一倍分成八個桶，涵蓋 125 微秒到約 131 秒，分位數在所在桶內插值讀出，與精確值的誤差約 ±4%。用舊的固定分桶寫入的聚合仍可讀取，但精度較粗。

總覽和端點抽屜的**比較**控制項會把前一天或上週同一時間段畫成虛線，延遲分布也會描繪出比較期的輪廓。在服務頁面上，這個控制項還會列出服務的其他環境：選擇後，虛線改為同一時間段在那個環境中的資料。

端點的最慢請求取自 Trace 儲存，列出的每個請求都能開啟其呼叫鏈。錯誤樣本指向的 trace 可能已被尾端取樣丟棄，此時呼叫鏈抽屜會說明找不到這條 trace。

## 服務目錄

目錄會為 APM 看到的每個服務依環境各列一列，也會列出尚未回報、已登記的服務。使用服務目錄中的**登記服務**與服務頁的**設定**區段記錄：

| 欄位 | 說明 |
|---|---|
| **負責團隊** | 工作區內的團隊。團隊的第一個已啟用值班排班決定目前的值班人員。 |
| **負責人** | 負責該服務的工作區成員。 |
| **等級** | P0 到 P5，P0 是最重要的服務。 |
| **生命週期** | 生產、預備、實驗或已棄用。 |
| **程式碼儲存庫** | 程式碼所在的位址，服務未回報儲存庫時使用：https 位址，或 git 位址，例如 `git@github.com:acme/checkout.git`、`ssh://git@git.example.com/team/checkout.git`。位址中的密碼會儲存為 `****`；https 位址中的使用者部分常被 git 用來攜帶權杖，也會同樣儲存為 `****`。服務頁會將 git 位址以相同路徑開啟為 https 頁面。 |
| **標籤** | `key=value`，或只寫 key，以逗號分隔。key 最多 64 個字元，只能使用小寫字母、數字和 `_ . - /`；value 最多 128 個字元。最多 32 個。 |
| **Apdex 閾值 T** | 服務 Apdex 的閾值，單位為毫秒，最長一分鐘。留空時使用組織的預設值，未在 APM 設定中修改時為 500 ms。 |
| **職責** | 顯示在服務名稱下方的簡短說明。 |
| **其他稱呼** | 日誌、指標和其他系統對此服務的稱呼，以逗號分隔，例如 `order_service`、訂單中心。最多 20 個，每個最多 128 個字元。稱呼不能是服務自己的名稱，也不能是另一個服務的名稱或稱呼。在服務目錄中搜尋這些稱呼也能找到此服務。 |
| **資料入口** | 存放服務日誌的日誌串流，每個可附帶一個從資料串流中篩出此服務日誌的 SQL 條件；服務指標的 PromQL 選擇器，例如 `{service="checkout"}`；顯示此服務的儀表板；以及其他位置的頁面連結，例如 Runbook 或 CMDB 項目。每類最多 10 筆。每一列都可以開啟對應的資料：**日誌**、**指標**、儀表板，或在新的分頁中開啟連結。 |

**其他稱呼**和**資料入口**既供人檢視，也供 Mole Agent 使用。向 Mole Agent 詢問此服務時，它會連同這些資訊讀取服務目錄項目；使用其他稱呼查詢 APM 時，讀取的是該稱呼所屬的服務。這些資訊不會合併資料：若要將舊服務名稱回報的資料算作此服務，請改用[服務別名](/zh-Hant/apm/settings#服務別名)。

同一表單中的**封存**會讓服務不再出現在服務目錄的預設檢視中，資料仍照常收集，服務頁仍照常開啟。服務目錄中的**已封存**會同時列出已封存的服務。

[服務目錄要求](/zh-Hant/apm/settings#服務目錄要求)可以要求某個等級及以上的服務填寫團隊、負責人或程式碼儲存庫。缺少要求項目的服務會在目錄中顯示**缺少**及缺少的項目。

服務定義依命名空間和服務名稱儲存，在所有環境中都適用。服務目錄和端點表的**欄位設定**可以選擇和排序欄位，排列會依使用者儲存。除指標和目錄欄位外，服務目錄還提供**服務類型**、**語言 / 框架**、**執行個體**和**區域**欄位，取自時間範圍內的執行個體，以及**標籤**和**上次活躍**欄位。

**關聯度**欄位預設顯示，以四個圓點表示服務與其他資料的關聯情形：日誌中的 TraceID、資源屬性、指標和回報的變更。綠色表示關聯良好，黃色表示部分關聯，灰色表示沒有關聯，最淺的表示讀取失敗。滑鼠懸停時可以看到背後的數字。需要處理的問題列在[收集品質](/zh-Hant/apm/settings#收集品質)裡。

服務目錄每一列的星號會將服務加入自己的收藏，收藏的服務會排在目錄最前面；**收藏**只列出收藏的服務。收藏會依使用者儲存。**分組**會依團隊、命名空間、等級或某個標籤的值分組。服務目錄可以依環境和團隊篩選；服務分布在多個命名空間或帶有標籤時，還可以依命名空間和標籤篩選。篩選和分組都會寫入位址中，分享連結會開啟相同的檢視。在時間範圍內出現過、但到時間範圍終點已超過一天沒有回報的服務會標為**未活躍**。

關鍵交易是最重要的端點。在端點清單或端點抽屜中點選星號即可標記，**設定**會列出服務的關鍵交易，以及每個關鍵交易在時間範圍內的請求情形。每個服務最多 50 個關鍵交易。

服務文件和 Runbook 放在 Mole Agent 知識庫的 `services/<服務名>/` 下，可以放在組織知識庫或負責團隊的知識庫。服務頁上的**文件**會列出這些檔案，並可新增 Runbook。Mole Agent 調查此服務時也會讀取這些檔案。

編輯服務定義和關鍵交易需要 `apm.definitions.manage`，編輯錯誤狀態需要 `apm.errors.manage`。擁有者、管理員和編輯者具有這些權限。

## 執行個體

每個為服務回報資料的處理程序是一個執行個體，依序以 `service.instance.id`、`k8s.pod.name`、`host.name` 區分。MoleSignal 每分鐘查看一次執行個體的 Span，儲存其執行的版本和上表中的屬性，每項取最後一次回報的值。程式碼儲存庫連結會儲存為不含使用者名稱、密碼和查詢參數的 https 位址。每個執行個體處理的請求、錯誤和延遲會分開分桶統計，來源與服務的指標相同。

**執行階段**會列出目前時間範圍和版本下的執行個體，最近回報的在前，包含吞吐量、錯誤率和 p95，以及執行個體的日誌（依 Pod，沒有 Pod 時依主機）和指標（依區分執行個體的標籤）連結。每個服務每小時超過執行個體基數上限的執行個體會合併為**其他執行個體** 一列，所有執行個體加起來等於服務。點選執行個體後，執行階段圖表只會顯示此執行個體，這個選擇會寫入位址中。超過小時級彙總保留期仍未出現的執行個體會被刪除。

## 深入端點

端點抽屜在 RED 圖表之外還有兩張卡片：

- **狀態碼**依狀態碼統計回應：HTTP 狀態碼取自 `http.response.status_code`（舊版插樁為 `http.status_code`），gRPC 狀態碼取自 `rpc.grpc.status_code`，依類別著色，並附上趨勢。每個分桶最多記錄 24 個狀態碼，更多的會計入**其他 HTTP** 或**其他 gRPC**。開始統計狀態碼之前寫入的彙總沒有狀態碼。
- **耗時明細**會從 Trace 儲存區讀取該端點在時間範圍內最近的請求（最多 200 個）及其下的 span。呼叫的耗時依呼叫對象歸類：資料庫（`db.system.name`）、快取（Redis、Memcached、Valkey）、HTTP、RPC、訊息，未說明呼叫對象的會計入**其他**。內部 span 計為內部處理，請求下沒有任何 span 涵蓋的時間是請求本身的耗時。每一項會顯示佔比和每個請求的平均耗時。並行的呼叫加起來可能超過請求時長，此時各項會依請求時長等比例縮放。只會讀取到尾端取樣保留的 Trace。

端點清單的**長時間工作**只顯示 p99 不低於 1 秒的端點。內部類型的入口 span，例如排程工作和沒有訊息操作的佇列消費者，會列為**背景工作**。

## 部署

服務頁的**部署**索引標籤會將管線回報的發布與服務 Span 中帶的版本放在一起，標出回滾，將每個版本與其之前的版本比較，並將同時執行的兩個版本並排顯示。管線透過 `POST /api/v1/apm/deployments` 回報發布。請見[部署](/zh-Hant/apm/deployments)。

## 相依性

服務**相依性**索引標籤中的每個目標都有一個從 100 開始的健康評分：呼叫失敗率每 1% 扣 4 分（最多 60 分），逾時呼叫佔比每 1% 扣 4 分（最多 20 分）；選擇比較時段時，P95 增長超過五分之一的部分每 1% 扣半分（最多 20 分）。90 分及以上為良好，70 分及以上需要留意。評分的提示會說明扣分原因。設定**比較**後，每個目標還會顯示錯誤率和 P95 的變化。**慢速 SQL** 會依 P95 列出最慢的資料庫語句範本。

## 調查效能問題

<Steps>
  <Step title="找到服務">
    開啟 **應用程式效能 → 服務**，依錯誤率或 p95 排序，再依環境或團隊縮小範圍。
  </Step>
  <Step title="閱讀概觀">
    開啟服務，與前一天或上週比較請求、錯誤率和延遲，並查看時間花在哪些下游。**洞察**卡片會寫明與上一時段、上週同時段相比有哪些指標改變、從什麼時候開始，以及附近的變更。請見[洞察與調查](/zh-Hant/apm/insights)。
  </Step>
  <Step title="縮小原因範圍">
    使用**端點**尋找慢速入口，使用**相依性**檢查下游耗時，使用**錯誤**分析重複失敗。當延遲與流量都很重要時，依耗時佔比排序端點。
  </Step>
  <Step title="開啟證據">
    開啟端點的最慢請求、錯誤樣本，或**呼叫鏈**中的 Trace，鏈路會在頁面上的抽屜中開啟。服務範圍列末尾的**日誌**、**指標**和**效能剖析**會為相同服務和時間範圍開啟對應訊號。
  </Step>
  <Step title="檢查部署">
    開啟**部署**，找出結論為變差的版本。點選其結論或選擇兩個版本，查看差異以及變慢的端點和增多的錯誤。請求不足表示結論尚不可靠，不能直接判定沒有迴歸。
  </Step>
  <Step title="交給 Mole Agent">
    在服務頁標題列、端點或錯誤抽屜中，或在某則發現上點選**調查**。Mole Agent 會開啟，問題已經寫好，並附上該服務。請見[讓 Mole Agent 調查](/zh-Hant/apm/insights#讓-mole-agent-調查)。
  </Step>
</Steps>

## 追蹤後端錯誤

錯誤群組在被設為**調查中**、**已解決**或**忽略**之前都是待處理狀態。每個群組都可以交給一個團隊，並指派給工作區成員。已解決的群組再次出現時會顯示為**迴歸**。**應用程式效能 → 錯誤**預設顯示未解決的群組：待處理、調查中和迴歸的群組。

清單上方的**分布**會依版本、環境和服務的語言統計所列群組的出現次數；錯誤群組的抽屜則統計它自己的出現次數。抽屜裡的**相關日誌**會依服務和時間範圍開啟日誌，樣本旁的**日誌**會開啟該樣本所在 Trace 的日誌。

### 使用規則彙總錯誤

錯誤清單上的**彙總規則**決定錯誤在類型、拋出位置和端點之外如何分組。規則會指定一個服務或全部服務，以及錯誤類型、錯誤訊息、拋出位置和端點的相符模式。每個模式會比對整段文字，不區分大小寫，`*` 代表任意文字；留空表示不限，但規則至少要填寫一項。

| 動作 | 效果 |
|---|---|
| **合併為一組** | 規則在一個服務中比對到的錯誤會合併為一個群組，並以規則名稱命名。 |
| **不再歸組** | 規則比對到的錯誤不會形成群組。它們的請求在 RED 指標中仍計為失敗。 |

規則會依序比對，第一條比對到的規則生效；上移或下移規則可以調整順序。規則會對儲存之後出現的錯誤生效，並在半分鐘內於所有節點生效，已有的群組保持不變。編輯規則時，表單會顯示所列群組中有多少個符合此規則。錯誤群組抽屜中的**依此錯誤建立規則**會以該群組的類型和服務開始一條新規則。

## 服務等級目標

服務等級目標（SLO）承諾在 7、28 或 30 天的滾動時間視窗內達標請求所佔的比例，對象是某個環境中的一個服務，或其中的一個端點。開啟 **應用程式效能 → SLO** 並點選**新增 SLO**，或在服務概觀的**服務等級目標** 卡片中點選**新增 SLO**。

| 欄位 | 說明 |
|---|---|
| **服務**與**環境** | 目標涵蓋的服務，限定在一個環境。 |
| **端點** | 服務的某個端點。留空則依整個服務計算。 |
| **達標條件** | **請求成功**：請求沒有失敗即為達標。**成功且不超過閾值**：請求沒有失敗且耗時不超過**延遲閾值（毫秒）**即為達標。 |
| **目標（%）** | 承諾的達標比例，大於 0 且小於 100，例如 `99.9`。 |
| **時間視窗** | 截至目前的 7、28 或 30 天。 |

SLO 會讀取服務的 APM 彙總，因此統計的是尾端取樣之前的全部請求。

| 指標 | 說明 |
|---|---|
| **達成率** | 時間視窗內達標請求數除以全部請求數。 |
| **剩餘錯誤預算** | `1 - (1 - 達成率) / (1 - 目標)`。錯誤預算是目標允許不達標的請求比例。目標被打破後，該值低於零。 |
| **燃燒率** | 最近 1 小時、6 小時和 24 小時的 `(1 - 達成率) / (1 - 目標)`。為 `1×` 時，預算恰好用滿整個時間視窗。 |
| **每日達成情形** | 時間視窗內每個 UTC 自然日，標為達標、未達標或無請求。 |

| 狀態 | 說明 |
|---|---|
| **已違約** | **達成率**低於目標。 |
| **有風險** | 剩餘預算不足 25%，或最近 1 小時燃燒率超過 14.4，或最近 6 小時超過 6。 |
| **健康狀態** | 以上都不滿足。 |
| **無資料** | 時間視窗內沒有請求。 |

延遲目標會讀取延遲直方圖，因此閾值內請求數的精度與分位數相同，誤差約在 4% 以內。時間視窗會讀取小時級彙總，燃燒率則讀取分鐘級彙總。時間視窗長於小時級彙總的保留期時，只統計保留的天數。

### 燃燒率警示

在 SLO 抽屜中點選**建立消耗率警示**，會新增 Google SRE workbook 推薦的兩條警示規則。兩條都是針對該目標的 APM 警示規則，會透過規則的升級策略傳送通知。

| 規則 | 時間視窗 | 觸發條件 | 嚴重等級 |
|---|---|---|---|
| 快速燃燒 | 1 小時，及其最後 5 分鐘 | 兩個時間視窗的燃燒率都超過 14.4 | 嚴重 |
| 慢速燃燒 | 6 小時，及其最後 30 分鐘 | 兩個時間視窗的燃燒率都超過 6 | 警告 |

短時間視窗可讓規則不會因為已經過去的尖峰而觸發。有規則監控該 SLO 後，抽屜會列出這些規則，不再顯示按鈕。建立規則需要 `alerts.rules.manage`。

編輯 SLO 需要 `apm.slos.manage`，刪除需要 `apm.slos.delete`。刪除 SLO 時會先刪除其燃燒率警示，因此還需要 `alerts.rules.manage`。

## 依 APM 指標警示

APM 警示規則會監控服務或其端點的某項指標，讀取的是 APM 頁面使用的同一份彙總，無需撰寫查詢。

<Steps>
  <Step title="開啟規則編輯器">
    在服務頁或端點抽屜的標題列開啟**新增警示**，選擇**閾值警示**。編輯器會以 **APM 警示**資料來源開啟，並預先填入服務、環境和端點。在**警示 → 警示規則**中新增規則時，也可以選擇 **APM 警示**資料來源。建立規則需要 `alerts.rules.manage`。
  </Step>
  <Step title="選擇指標">
    選擇**服務**、**環境**或**所有環境**、**端點**或**整個服務**，以及**指標**。依編輯器在指標下方標註的單位設定閾值。
  </Step>
  <Step title="測試並儲存">
    點選**測試規則**，查看最近 6 小時的指標與閾值的比較，然後建立規則。
  </Step>
</Steps>

| 指標 | 單位 |
|---|---|
| **錯誤率** | 百分比，0 到 100 |
| **P50 延遲**、**P90 延遲**、**P95 延遲**、**P99 延遲**、**平均耗時** | 毫秒 |
| **吞吐量** | 每秒請求數 |
| **請求數**、**錯誤數** | 規則時間視窗內的次數 |
| **新錯誤群組** | 規則時間視窗內首次出現的服務（或端點）錯誤群組數 |
| **Apdex** | 0 到 1 |
| **SLO 燃燒率** | 相對於目標允許速度的倍數，從 SLO 建立。 |

每次評估會讀取規則的時間視窗：24 小時以內讀取分鐘級彙總，更長的時間視窗讀取小時級彙總。時間視窗內沒有請求時，**請求數**、**錯誤數**、**新錯誤群組**和**吞吐量**的讀數為 `0`，因此規則可以發現流量中斷。其他指標此時沒有讀數，不會觸發任何閾值，進行中的事件也會隨之恢復。

在編輯器中或從 SLO 建立的規則會帶有 `service.name`、`service.namespace`、`deployment.environment` 和 `apm.endpoint` 標籤（取決於規則指定了哪些對象），事件會複製這些標籤。所有 APM 規則的事件還帶有 `service` 標籤、`affected_services` 中的服務，以及取自彙總的一個樣本 Trace ID。服務目錄的**警示**欄位、服務頁標題列和端點抽屜會統計指向該服務的已開啟和已確認事件；事件指定了環境時，只統計該服務所在環境的事件。端點抽屜只統計帶有該端點標籤的事件。點選數量會開啟**警示 → 事件**。

同一選單中的**異常偵測警示**會在指標明顯偏離過去幾天同一時刻時發出警示，不需要設定閾值。請見[對 APM 指標設定異常偵測警示](/zh-Hant/apm/insights#為-apm-指標設定異常偵測警示)。

## 篩選、解析度與保留

APM 頁面共用全域時間範圍。服務目錄可依環境和團隊篩選，服務頁可依環境和版本篩選。清單支援搜尋和排序。範圍會編碼進 URL，方便分享或重新開啟。

使用預設部署設定時：

- API 未指定範圍時查詢最近 24 小時；
- `auto` 對不超過 24 小時的範圍使用分鐘桶，對更長範圍使用小時桶；
- 分鐘彙總保留 24 小時；
- 小時彙總和最大查詢範圍為 30 天。

管理員可以調整這些部署限制。只有比較雙方都達到設定的請求量閾值時，版本比較才會標記為資料充足；預設閾值是每個版本 1,000 個請求。

## 閱讀資料品質提示

每個 APM 回應都帶有資料品質中繼資料。有需要說明的情況時，導覽卡片中會出現簡短提示，點選即可查看詳細資料。

| 提示 | 含義 |
|---|---|
| **資料起點在此範圍內** | APM 投影在所選範圍內才啟動，更早的流量沒有被統計。 |
| **資料不完整** | 佇列、儲存庫、刷寫、延遲抵達的資料、基數或關閉流程在部分時間造成缺口。不要把缺失的資料解讀為零。 |
| **資料延遲** | `lastCompleteBucketAt` 落後於所選範圍，最近的聚合可能仍在關閉或彙總。 |
| **部分名稱計入「其他」** | 達到基數上限，超出上限的名稱會合併計入名為**其他**的一行。上限在 [APM 設定](/zh-Hant/apm/settings#基數上限)中設定。 |

請先縮短時間範圍並收窄篩選條件。如果部分或延遲狀態持續存在，再檢查 APM 健康端點與 [APM 投影指標](/zh-Hant/self-observability#apm-投影)。

## 隱私與有界資料

APM 會保存聚合以及少量去識別化後的證據。APM 聚合不會保留請求主體、回應主體、URL 查詢參數值、Header 或 SQL 參數；SQL 語句只以範本形式保留，所有常值都會替換為 `?`。識別值、代表性訊息和堆疊框架都有長度限制；疑似敏感或容易變動的值會在持久化之前刪除或遮罩。

這些保護不能取代良好的埋點習慣。不要把金鑰或個人資料放入 span 名稱、狀態描述、例外訊息或資源屬性。

## 疑難排解

| 現象 | 檢查項目 |
|---|---|
| 沒有 APM 資料 | 確認 trace 已進入同一個工作區、時間範圍包含最近的流量，且角色具有 `apm.services.read`。 |
| 出現 `unknown_service` | 在匯出 span 前設定穩定的 `service.name` 資源屬性。 |
| 缺少端點 | 新增 `SERVER` 或 `CONSUMER` span kind，以及標準 HTTP、RPC 或訊息屬性。 |
| 缺少相依性 | 為下游呼叫新增 `CLIENT` 或 `PRODUCER` span，並附帶目標端的語意屬性。 |
| 缺少版本 | 在同一個部署的每個執行個體上一致設定 `service.version`。 |
| 缺少錯誤 | 依 OpenTelemetry 約定記錄 exception event，並設定 span、HTTP 或 RPC 狀態。 |
| 找不到錯誤樣本的 trace | Trace 已被取樣丟棄或過期，但在取樣前產生的 APM 聚合仍然有效。 |
| 沒有執行階段圖表 | 使用相同的 `service.name` 上報 OpenTelemetry 執行階段指標。 |
| 結果不完整或過時 | 查看資料品質提示和 `GET /api/v1/apm/health`。 |
| 服務停止後 APM 警示未觸發 | 沒有請求時，錯誤率、延遲和 Apdex 沒有讀數。用**請求數**或**吞吐量**監控流量中斷。 |
| SLO 顯示**無資料** | 確認服務在 SLO 指定的環境中有上報，且端點名稱與**端點**列表一致。 |
