MoleSignal APM 將後端 OpenTelemetry trace span 轉換成有界的 RED 彙總。不必另外維護指標埋點，即可找出緩慢的服務、失敗的端點、高開銷的相依性、反覆出現的後端錯誤，以及部署版本之間的效能退步。服務目錄記錄每個服務的負責人和重要程度。

<Note>
  APM 不需要另一套 SDK，也不會新增遙測資料流。傳送已完整埋點的 trace 後，MoleSignal 會在呼叫鏈去重後、尾端取樣前衍生 APM 資料。因此，最終因取樣而捨棄的 trace 仍可計入 APM 指標，[即時管線](/zh-Hant/pipelines#追蹤)捨棄的 span 也一樣。
</Note>

## 頁面

APM 以總覽為首頁，每個服務都有專屬頁面。

| 頁面 | 主要用途 |
|---|---|
| **總覽** | 集中檢視所有服務：活躍服務、輸送量、錯誤率、p95 與 p50、p90、p99 和平均耗時、Apdex；服務健康狀態的分布與變化；最慢、錯誤率最高和流量最大的服務；洞察，包括相較於上一時段或上週同時段有所變化的指標、相近時間發生的變更，以及可節省時間之處；與服務相關的進行中警示；時間範圍內部署的版本；環境分布；以及各服務缺少哪些埋點。 |
| **服務** | 服務目錄：列出 APM 觀測到的每個服務和已登記的服務，包括負責人、等級、標籤、進行中的警示、輸送量、錯誤率、延遲、版本和最近部署。收藏的服務排在最前面，預設不顯示已封存的服務。 |
| **服務地圖** | 顯示單一環境中的服務、服務之間的呼叫關係、呼叫的目標，以及發佈和取用的 Topic；標示相較於上一時段新增或消失的呼叫。請參閱 [APM 服務地圖](/zh-Hant/apm/service-map#apm-服務地圖)。 |
| **錯誤** | 所有服務的後端錯誤群組，包括狀態、團隊和處理人員、錯誤發生的分布，以及用於分組的彙總規則。 |
| **SLO** | 服務等級目標：每個目標在時間區間內的達成率、剩餘錯誤預算、預算消耗速度和狀態。 |
| **設定** | 組織的健康判定門檻、預設 Apdex 閾值、長時間工作、服務目錄要求、命名規則、環境對應和服務別名，以及根據過去一天的資料提供的設定提示；也包括平台的基數上限和呼叫鏈取樣。請參閱 [APM 設定](/zh-Hant/apm/settings)。 |

服務頁面包含以下區段：

| 區段 | 主要用途 |
|---|---|
| **總覽** | 並排顯示請求、錯誤率和延遲，並顯示服務的洞察、延遲分布、下游耗時、最耗時的端點、最常見的錯誤，以及服務的 SLO。 |
| **端點** | 依請求數、錯誤、延遲或耗時占比排列 HTTP、RPC、訊息和背景工作的進入點。端點會在側欄中開啟，顯示狀態碼、耗時明細和最慢的請求。星號標示關鍵交易，清單也可只顯示關鍵交易或長時間工作。 |
| **呼叫鏈** | 使用 Traces 頁面的呼叫鏈表格，顯示此服務參與的 trace。 |
| **相依性** | 顯示呼叫此服務的服務，以及依目標分組的下游呼叫，並在各目標下列出操作；另顯示各目標的健康評分、逾時和重試的呼叫，以及最慢的 SQL 陳述式。 |
| **錯誤** | 此服務的錯誤群組。 |
| **部署** | 將管線回報的發行版本與 Span 中觀測到的版本一併顯示，標示回復至先前版本的情況，提供各版本與前一版本的比較結論、同時執行的兩個版本的並排比較，以及兩個版本的比較。請參閱[部署](/zh-Hant/apm/deployments)。 |
| **執行階段** | 顯示執行此服務的執行個體及各執行個體的請求情況、根據處理程序和服務所用語言的執行階段指標繪製的圖表，以及來自 Profile 的火焰圖。 |
| **設定** | 服務目錄項目、關鍵交易，以及執行個體回報的資訊。 |

服務名稱後方的一行會依目前選取的環境和版本顯示服務的基本資訊：

| 資訊 | 來源 |
|---|---|
| 健康狀態 | 時間範圍內的 RED 指標，將游標移上即可查看原因。時間範圍內沒有請求時，顯示**此時間範圍內沒有資料**：未收到遙測資料不代表服務不健康。 |
| 等級 | 服務目錄項目。 |
| 所屬系統和環境 | `service.namespace` 和 `deployment.environment.name`。 |
| 服務類型 | 依服務處理的進入 Span 顯示：**HTTP**、**RPC**、訊息的**訊息取用**，以及內部進入 Span 的**背景工作**。 |
| 語言 / 框架 | `telemetry.sdk.language`，以及服務進入 Span 使用的埋點程式庫，例如 Axum、Spring 或 Express。 |
| 版本 | 顯示選取的版本；未選取時，顯示執行個體在時間範圍內執行過的所有版本，執行個體數量最多的版本排在最前面。漸進式部署期間會同時顯示兩個版本。 |
| 負責團隊 | 服務目錄項目。將游標移上即可查看負責人和目前的值班人員。 |
| 執行個體數 | 在時間範圍內回報過目前版本的執行個體數。點選即可開啟**執行階段**。 |
| 最近部署 | 目前版本（未選取時為最新版本）首次出現的時間。 |
| 部署區域 | 執行個體的 `cloud.region`。 |
| 程式碼存放庫 | 執行個體的 `vcs.repository.url.full` 或 `git.repository_url`；未回報時，使用服務目錄項目中的存放庫。 |
| 別名 | 服務目錄項目中的別名：顯示第一個別名，以及其餘別名的數量。 |

已封存的服務在這一行還會顯示**已封存**。點選標題列末尾的**收藏**，即可將服務加入個人收藏。

導覽卡片末尾提供服務的日誌、指標和 Profiles 連結。如果在目前時間範圍結束前的一天內，某個訊號包含此服務的資料，對應連結就會亮起。MoleSignal 每五分鐘重新檢查一次：

| 訊號 | 亮起條件 |
|---|---|
| 日誌 | 某個包含 `service.name`、`service_name` 或 `service` 欄位的日誌資料流中有此服務的日誌。連結會開啟該資料流的日誌頁面。 |
| 指標 | 最近一小時內有帶有此服務 `service.name` 的指標序列。 |
| Profiles | Profile 資料流中有此服務的 Profile。 |
| RUM | 服務的呼叫鏈樣本中有來自瀏覽器工作階段的請求。僅在此情況下顯示，點選即可開啟該工作階段。 |

沒有資料的訊號會變暗，點選即可開啟**資料來源**中對應的接入頁面。檢查失敗或超過三秒時，連結既不亮起也不變暗。

## 接入前提

- 將 OpenTelemetry trace 傳送至 MoleSignal 的[呼叫鏈收集端點](/zh-Hant/intake)；
- 在組織工作區具有 `apm.services.read` 權限；或者
- 在受保護的 `_sys` 遙測範圍內具有 `sys.telemetry.read` 權限。

## 為服務接入 APM

<Steps>
  <Step title="設定穩定的服務資源屬性">
    為每個服務設定 `service.name`。如需篩選服務或比較部署，請再加上命名空間、環境、版本和執行個體屬性。

    ```bash
    export OTEL_SERVICE_NAME=checkout
    export OTEL_RESOURCE_ATTRIBUTES="service.namespace=shop,deployment.environment.name=production,service.version=2.4.0,service.instance.id=checkout-01"
    ```

    具體設定方式取決於使用的 OpenTelemetry SDK 或 Collector。
  </Step>
  <Step title="使用正確的 span kind">
    為傳入的請求建立 `SERVER` span，為取用的訊息建立 `CONSUMER` span。為下游呼叫建立 `CLIENT` 或 `PRODUCER` span。MoleSignal 透過 span kind 區分交易與相依性。
  </Step>
  <Step title="記錄狀態與例外狀況">
    設定 OpenTelemetry span 狀態、HTTP 或 RPC 狀態屬性，並記錄 exception event。MoleSignal 使用這些資訊區分成功與失敗，並建立後端錯誤群組。
  </Step>
  <Step title="傳送 trace 並開啟 APM">
    傳送 OTLP trace，然後開啟 **應用程式效能 → 服務**。將全域時間範圍維持在有近期流量的區間，等待投影器寫入第一批資料桶。
  </Step>
</Steps>

### 建議的資源屬性

| 屬性 | 用途 | 缺少屬性時 |
|---|---|---|
| `service.name` | 穩定的服務識別碼。請為每個服務明確設定。 | `unknown_service` |
| `service.namespace` | 區分不同系統或團隊中名稱相同的服務。 | `default` |
| `deployment.environment.name` | 篩選正式、預備等環境。 | 依序使用舊屬性 `deployment.environment` 和 `unknown` |
| `service.version` | 支援版本記錄與部署比較。 | 不依版本區分 |
| `service.instance.id` | 區分執行個體。 | 依序使用 `k8s.pod.name` 和 `host.name` |
| `telemetry.sdk.language` | 在服務目錄中顯示執行階段語言。 | 若有 `process.runtime.name`，則使用該屬性 |
| `cloud.region`、`k8s.*`、`host.name`、`container.name`、`container.id` | 說明各執行個體在哪裡執行。 | 不顯示 |
| `process.runtime.name`、`process.runtime.version` | 顯示每個執行個體的執行階段。 | 不顯示 |
| `vcs.repository.url.full`、`vcs.ref.head.revision` | 連結至程式碼存放庫並顯示提交。也支援 `git.repository_url` 和 `git.commit.sha`。 | 服務目錄項目中的存放庫 |

Kubernetes 屬性和 `cloud.region` 通常由 OpenTelemetry Collector 的 `k8sattributes` 和 `resourcedetection` 處理器新增，而不是由 SDK 設定。

請使用低基數值。不要將請求 ID、原始 URL、使用者 ID 或其他無界值放入服務、環境、版本、路由、操作或相依性屬性。

## APM 資料如何衍生

### 服務與端點

`SERVER` 和 `CONSUMER` span 會計入服務與端點的 RED 指標。API 將端點稱為交易（transaction）。若資料沒有 kind 也沒有父 span，仍可計入服務總量以維持相容性，但必須明確指定 span kind 才能產生更完整的頁面。

MoleSignal 會從語意屬性建構有界的端點名稱：

- HTTP 方法與 `http.route`，例如 `POST /checkout`；
- RPC 服務與方法；
- 訊息操作與目的地；
- 沒有更明確的語意識別資訊時，使用安全、低基數的 span 名稱。

請使用 `/orders/{id}` 這類路由範本，不要使用 `/orders/83921` 這類原始路徑。

### 相依性

`CLIENT` 和 `PRODUCER` span 會計入相依性的 RED 指標。MoleSignal 會將目標分類為服務、資料庫、快取、訊息系統、外部 HTTP、外部 RPC 或其他相依性。標準的 `peer.service`、`db.*`、`messaging.*`、`rpc.*`、`server.*` 和 HTTP 語意屬性有助於更準確地識別相依性。

沒有 `peer.service` 的資料庫或快取呼叫會以資料庫系統為目標，例如 `postgresql` 或 `redis`。設定 [`MS_TRACE_FINGERPRINT_KEY`](/zh-Hant/configuration#環境變數) 後，目標還會包含使用金鑰產生的 `db.namespace` 指紋（若無此屬性，則取 `db.name` 或 `db.collection.name`），例如 `postgresql:<指紋>`。如此即可分開統計同一系統中的不同資料庫，而不必儲存資料庫名稱。

SQL 資料庫呼叫採用陳述式範本作為操作名稱：取 `db.query.summary`，若無此屬性，則取 `db.query.text` 或 `db.statement`。將所有常值替換為 `?`、移除註解，並將值清單合併為單一 `?`，最多保留 512 位元組。只有在資料庫將雙引號內的文字視為資料表名稱或欄位名稱時（例如 PostgreSQL、Oracle），才會保留該文字；在其他資料庫中則視為值處理。沒有陳述式的呼叫使用 `db.operation.name`，快取呼叫則使用其命令名稱。單一服務對同一目標每小時最多區分 32 種操作，其餘操作會在同一目標下合併為**其他**。

逾時的請求（錯誤類型為逾時、gRPC `DEADLINE_EXCEEDED`、HTTP 408 或 504）和重新傳送的請求（`http.request.resend_count` 大於 0）會在 RED 指標旁個別計數。

### 錯誤

span 包含例外狀況、OpenTelemetry 狀態為 `ERROR`、HTTP 狀態碼大於或等於 500，或 RPC 狀態不為零時，MoleSignal 會將該 span 判定為錯誤。錯誤群組的穩定指紋由錯誤類型、第一個應用程式堆疊框架和交易名稱組成；經常變動的錯誤訊息不納入指紋計算。[彙總規則](#使用規則彙總錯誤)可將錯誤合併成一組，或讓這些錯誤不再分組。

## 瞭解 RED 指標

| 指標 | 意義 |
|---|---|
| **請求數** | 符合條件的服務、端點或相依性的觀測次數。 |
| **錯誤率** | 錯誤數除以請求數。 |
| **延遲** | 從合併後的延遲直方圖讀出的 p50、p90、p95 和 p99，以及平均耗時。 |
| **Apdex** | 將耗時不超過閾值 T 的請求數，加上耗時超過 T 但不超過 4T 的請求數的一半，再除以全部請求數。T 採用組織的預設值（未在 [APM 設定](/zh-Hant/apm/settings#健康狀態判定與閾值)中修改時為 500 ms）。也可在服務目錄項目中為服務設定專屬的 T，延遲分布會標示目前使用的 T。總覽會合併所有服務，並依組織的預設值計算。出錯的請求一律不算滿意：各耗時區間會按比例扣除錯誤請求。 |
| **總耗時** | 所有觀測耗時的總和，用來找出整體影響最大的工作。 |

錯誤率達到 2% 或 p95 達到 500 ms 的服務標示為**警告**，錯誤率達到 10% 或 p95 達到 2 s 則標示為**嚴重**；可在 [APM 設定](/zh-Hant/apm/settings#健康狀態判定與閾值)中變更判定門檻。服務頁面和目錄中的狀態圓點會指出哪個指標超過了哪個門檻。

**洞察**卡片會列出相較於前一個等長時段或上週同時段出現突變的服務，請參閱[洞察的類型](/zh-Hant/apm/insights#洞察的類型)。

延遲直方圖在延遲每加倍的範圍內劃分八個桶，涵蓋 125 微秒到約 131 秒。分位數以所在桶內的插值求得，與精確值的誤差約為 ±4%。以舊版固定分桶寫入的彙總資料仍可讀取，但精確度較低。

總覽和端點側欄的**比較**控制項會以虛線顯示前一天或上週同一時段的資料，延遲分布也會描繪比較時段的輪廓。在服務頁面上，這個控制項也會列出服務的其他環境。選取後，虛線會改為顯示該環境在同一時段的資料。

端點最慢的請求取自 Trace 儲存空間，清單中的每筆請求都可開啟對應的呼叫鏈。錯誤樣本所指向的 trace 可能已因尾端取樣而捨棄，此時呼叫鏈側欄會顯示找不到該 trace。

## 服務目錄

目錄會將 APM 偵測到的每個服務依環境各列一行，也會列出已登記但尚未回報資料的服務。使用服務目錄中的**登記服務**和服務頁面的**設定**區段記錄下列資訊：

| 欄位 | 意義 |
|---|---|
| **負責團隊** | 工作區內的團隊。團隊的第一個已啟用值班表決定目前的值班人員。 |
| **負責人** | 負責該服務的工作區成員。 |
| **等級** | P0 到 P5，P0 代表最重要的服務。 |
| **生命週期** | 正式、預備、實驗或已淘汰。 |
| **程式碼儲存庫** | 程式碼所在的位址，在服務未回報儲存庫時使用。可填寫 https 位址或 git 位址，例如 `git@github.com:acme/checkout.git`、`ssh://git@git.example.com/team/checkout.git`。位址中的密碼會儲存為 `****`；git 常在 https 位址的使用者名稱部分放入權杖，這部分也會儲存為 `****`。服務頁面會以相同路徑將 git 位址開啟為 https 頁面。 |
| **標籤** | 填寫 `key=value` 或只填 key，以逗號分隔。key 最多 64 個字元，只能使用小寫字母、數字和 `_ . - /`；value 最多 128 個字元。最多可填 32 個標籤。 |
| **Apdex 閾值 T** | 服務的 Apdex 閾值，單位為毫秒，上限為一分鐘。留空即使用組織的預設值；若未在 APM 設定中修改，則為 500 ms。 |
| **職責** | 顯示在服務名稱下方的簡短說明。 |
| **其他稱呼** | 日誌、指標和其他系統對此服務的稱呼，以逗號分隔，例如 `order_service`、訂單中心。最多 20 個，每個最多 128 個字元。其他稱呼不得與此服務的名稱重複，也不得與其他服務的名稱或稱呼重複。在服務目錄中搜尋這些稱呼也能找到此服務。 |
| **資料入口** | 包含存放服務日誌的日誌串流（各串流可附上 SQL 條件，從中篩出此服務的日誌）、服務指標的 PromQL 選擇器（例如 `{service="checkout"}`）、顯示此服務的儀表板，以及其他頁面的連結（例如 Runbook 或 CMDB 項目）。每類最多 10 筆。每一行都能開啟對應的**日誌**、**指標**或儀表板，連結則會在新分頁開啟。 |

**其他稱呼**和**資料入口**可供查閱，也可供 Mole Agent 使用。向 Mole Agent 詢問此服務時，Mole Agent 會讀取服務目錄項目及這些資訊；以其他稱呼查詢 APM 時，APM 會讀取該稱呼所屬的服務。這些資訊不會合併資料。若要將使用舊服務名稱回報的資料計入此服務，請改用[服務別名](/zh-Hant/apm/settings#服務別名)。

使用同一份表單中的**封存**，可將服務從服務目錄的預設檢視中移除。MoleSignal 仍會照常收集資料，服務頁面也能照常開啟。服務目錄中的 **已封存**會一併列出已封存的服務。

[服務目錄要求](/zh-Hant/apm/settings#服務目錄要求)可要求達到指定等級的服務填寫團隊、負責人或程式碼儲存庫。若服務缺少必填項目，目錄會顯示**缺少**及缺少的項目。

MoleSignal 依命名空間和服務名稱儲存服務定義，並套用至所有環境。在服務目錄和端點表格的**欄位設定**中，可選擇要顯示的欄位並調整順序。MoleSignal 會依使用者儲存欄位配置。除了指標和目錄欄位，服務目錄也提供取自時間範圍內執行個體的**服務類型**、**語言 / 框架**、**執行個體**和 **區域**欄位，以及**標籤**和**上次活躍**欄位。

點選服務目錄每一行的星號，即可將服務加入收藏。收藏的服務會排在目錄最前面；**收藏**只會列出已收藏的服務。MoleSignal 會依使用者儲存收藏。使用**分組**可依團隊、命名空間、等級或指定標籤的值分組。服務目錄可依環境和團隊篩選；若服務分布在多個命名空間或帶有標籤，也可依命名空間和標籤篩選。篩選和分組都會記錄在網址中，開啟分享的連結即可看到相同檢視。若服務曾在時間範圍內出現，但到時間範圍結束時已有超過一天未回報資料，目錄會將其標為**未活躍**。

關鍵交易是最重要的端點。在端點清單或端點側邊面板中點選星號即可標記。**設定**會列出服務的關鍵交易，以及各關鍵交易在時間範圍內的請求情形。每個服務最多可有 50 個關鍵交易。

將服務文件和 Runbook 放在 Mole Agent 知識庫的 `services/<服务名>/` 下，可使用組織或負責團隊的知識庫。服務頁面上的**文件**會列出這些檔案，也可在此新增 Runbook。Mole Agent 調查此服務時也會讀取這些檔案。

編輯服務定義和關鍵交易需要 `apm.definitions.manage`，編輯錯誤狀態需要 `apm.errors.manage`。擁有者、管理員和編輯者具備這些權限。

## 執行個體

每個為服務回報資料的處理程序都是一個執行個體，依序以 `service.instance.id`、`k8s.pod.name`、`host.name` 區分。MoleSignal 每分鐘檢查一次執行個體的 Span，儲存其執行版本和上表中的屬性。每個項目都採用上次回報的值。MoleSignal 會將程式碼儲存庫連結儲存為不含使用者名稱、密碼和查詢參數的 https 位址。MoleSignal 會對各執行個體處理的請求、錯誤和延遲分別按時間桶統計，資料來源與服務指標相同。

**執行階段**會列出目前時間範圍和版本的執行個體，最近回報的排在最前面。清單包含吞吐量、錯誤率和 p95，以及各執行個體的日誌連結（依 Pod，若沒有 Pod 則依主機）和指標連結（依區分執行個體的標籤）。每個服務每小時超出執行個體數量上限的部分會合併為**其他執行個體** 一行。所有執行個體的統計加總等於服務的統計。點選執行個體後，執行階段圖表只會顯示該執行個體，並將選擇記錄在網址中。若執行個體在小時層級彙總資料的保留期限內未再出現，MoleSignal 就會刪除該執行個體。

## 深入查看端點

除了 RED 圖表，端點側邊面板還有兩張卡片：

- **狀態碼**依狀態碼統計回應。HTTP 狀態碼取自 `http.response.status_code`（舊版埋點使用 `http.status_code`），gRPC 狀態碼取自 `rpc.grpc.status_code`。卡片會依類別標示顏色，並顯示趨勢。每個時間桶最多記錄 24 個狀態碼，超出的部分計入**其他 HTTP** 或**其他 gRPC**。開始統計狀態碼前寫入的彙總資料不含狀態碼。
- **耗時明細**會從 Trace 儲存空間讀取此端點在時間範圍內最近的請求（最多 200 個）及其下的 span。卡片依呼叫對象將耗時分為資料庫（`db.system.name`）、快取（Redis、Memcached、Valkey）、HTTP、RPC 和訊息。未標明呼叫對象的項目計入**其他**。內部 span 計為內部處理，請求中未被任何 span 涵蓋的時間則是請求本身的耗時。每個項目都會顯示占比和每個請求的平均耗時。若平行呼叫的總耗時超過請求耗時，卡片會依請求耗時等比例縮放各項數值。卡片只會讀取尾端取樣保留的 trace。

端點清單中的**長時間工作**只顯示 p99 不低於 1 秒的端點。內部類型的入口 span，例如排程工作和沒有訊息作業的佇列消費者，會列為**背景工作**。

## 部署

服務頁面的**部署**分頁會將部署管線回報的發佈紀錄與服務 Span 中的版本一併顯示，標示復原紀錄，將各版本與其上一個版本比較，並並排顯示同時執行的兩個版本。部署管線透過 `POST /api/v1/apm/deployments` 回報發佈紀錄。請參閱[部署](/zh-Hant/apm/deployments)。

## 相依性

服務頁面的**相依性**分頁會為每個目標提供初始值為 100 分的健康評分。呼叫失敗率每 1% 扣 4 分（最多扣 60 分），逾時呼叫占比每 1% 扣 4 分（最多扣 20 分）。選取比較時段後，P95 增幅超過 20% 的部分，每 1% 扣 0.5 分（最多扣 20 分）。90 分以上為良好，70 分以上但未達 90 分則需留意。評分提示會說明扣分原因。設定**比較**後，每個目標也會顯示錯誤率和 P95 的變化。**慢速 SQL** 會依 P95 列出最慢的資料庫陳述式範本。

## 調查效能問題

<Steps>
  <Step title="找出服務">
    開啟 **應用程式效能 → 服務**，依錯誤率或 p95 排序，再依環境或團隊縮小範圍。
  </Step>
  <Step title="查看概覽">
    開啟服務，將請求、錯誤率和延遲與前一天或上週比較，並查看時間花在哪些下游服務。**洞察**卡片會說明與上一時段及上週同一時段相比，哪些指標有所變化、變化何時開始，以及有哪些變更發生在相近時間。請參閱[洞察與調查](/zh-Hant/apm/insights)。
  </Step>
  <Step title="縮小可能原因的範圍">
    使用**端點**找出速度慢的入口，使用**相依性**檢查下游耗時，並使用**錯誤**分析重複發生的失敗。若延遲和流量都很重要，請依耗時占比排序端點。
  </Step>
  <Step title="開啟佐證資料">
    開啟端點最慢的請求、錯誤樣本或**呼叫鏈**中的 trace。Trace 會在頁面上的側邊面板中開啟。服務範圍列末尾的**日誌**、**指標**和 **效能剖析**會開啟同一服務和時間範圍的對應訊號。
  </Step>
  <Step title="檢查部署">
    開啟**部署**，找出判定為變差的版本。點選該版本的結論或選取兩個版本，查看差異、變慢的端點和增加的錯誤。請求數不足表示結論尚不可靠，不能據此判定效能沒有退步。
  </Step>
  <Step title="交給 Mole Agent">
    在服務頁面的標題列、端點或錯誤側邊面板中，或在任一調查發現上點選**調查**。Mole Agent 開啟時會預先填入問題，並附上該服務。請參閱[讓 Mole Agent 調查](/zh-Hant/apm/insights#讓-mole-agent-調查)。
  </Step>
</Steps>

## 追蹤後端錯誤

錯誤群組在設為**調查中**、**已解決**或**忽略**之前，會維持待處理狀態。可將各群組交由一個團隊處理，並指派給工作區成員。已解決的群組再次出現時會顯示為**迴歸**。**應用程式效能 → 錯誤**預設會顯示未解決的群組，包括待處理、調查中和迴歸的群組。

清單上方的**分布**會依版本、環境和服務語言統計所列群組的出現次數。錯誤群組的側邊面板只會統計該群組的出現次數。面板中的**相關日誌**會依服務和時間範圍開啟日誌；樣本旁的**日誌**會開啟該樣本所在 trace 的日誌。

### 使用規則彙總錯誤

錯誤清單上的**彙總規則**決定除了類型、擲出位置和端點之外，還要如何對錯誤分組。規則可指定一個服務或所有服務，以及錯誤類型、錯誤訊息、擲出位置和端點的比對模式。各模式都會比對整段文字，不區分大小寫，`*` 代表任意文字。留空表示不限，但每條規則至少要填寫一項比對模式。

| 動作 | 效果 |
|---|---|
| **合併為一組** | 將規則在同一服務中比對到的錯誤合併為一個群組，並以規則名稱命名。 |
| **不再歸組** | 符合規則的錯誤不會形成群組。這些錯誤的請求在 RED 指標中仍計為失敗。 |

MoleSignal 會依序比對規則，並套用第一條符合的規則。可向上或向下移動規則以調整順序。規則只適用於儲存後出現的錯誤，並在半分鐘內於所有節點生效。既有群組不會變更。編輯規則時，表單會顯示所列群組中有多少符合這條規則。在錯誤群組的側邊面板中點選**依此錯誤建立規則**，即可用該群組的類型和服務建立新規則。

## 服務等級目標

服務等級目標（SLO）承諾在 7、28 或 30 天的滾動時間視窗內，有一定比例的請求達標。目標適用於特定環境中的一個服務或該服務的某個端點。開啟 **應用程式效能 → SLO** 並點選**新增 SLO**，或在服務概覽的**服務等級目標** 卡片中點選**新增 SLO**。

| 欄位 | 意義 |
|---|---|
| **服務**與**環境** | 目標涵蓋的服務，以單一環境為限。 |
| **端點** | 服務的某個端點。留空則按整個服務計算。 |
| **達標條件** | **請求成功**：請求未失敗即達標。**成功且不超過閾值**：請求未失敗且耗時不超過**延遲閾值（毫秒）**即達標。 |
| **目標（%）** | 承諾的達標比例，大於 0 且小於 100，例如 `99.9`。 |
| **時間視窗** | 截至目前的 7、28 或 30 天。 |

SLO 讀取服務的 APM 彙總資料，因此會統計尾端取樣前的所有請求。

| 指標 | 意義 |
|---|---|
| **達成率** | 時間視窗內的達標請求數除以請求總數。 |
| **剩餘錯誤預算** | `1 - (1 - 达成率) / (1 - 目标)`。錯誤預算是目標允許未達標的請求比例。未達目標時，此值低於零。 |
| **燃燒率** | 最近 1 小時、6 小時和 24 小時的 `(1 - 达成率) / (1 - 目标)`。燃燒率為 `1×` 時，預算恰好在整個時間視窗結束時用完。 |
| **每日達成情形** | 時間視窗內的每個 UTC 日曆日，標示為達標、未達標或無請求。 |

| 狀態 | 意義 |
|---|---|
| **已違約** | **達成率**低於目標。 |
| **有風險** | 剩餘預算低於 25%，或最近 1 小時的燃燒率超過 14.4，或最近 6 小時的燃燒率超過 6。 |
| **健康狀態** | 不符合上述任何條件。 |
| **無資料** | 時間視窗內沒有請求。 |

延遲目標讀取延遲直方圖，因此閾值內請求數的精確度與分位數相同，誤差約在 4% 以內。時間視窗讀取小時層級的彙總資料，燃燒率則讀取分鐘層級的彙總資料。若時間視窗長於小時層級彙總資料的保留期限，則只統計保留期限內的天數。

### 燃燒率警示

在 SLO 側邊面板中點選**建立消耗率警示**，即可新增 Google SRE workbook 建議的兩條警示規則。兩條都是針對此目標的 APM 警示規則，會依規則的升級策略傳送通知。

| 規則 | 時間視窗 | 觸發條件 | 嚴重程度 |
|---|---|---|---|
| 快速燃燒 | 1 小時及其中最後 5 分鐘 | 兩個時間視窗的燃燒率都超過 14.4 | 嚴重 |
| 慢速燃燒 | 6 小時及其中最後 30 分鐘 | 兩個時間視窗的燃燒率都超過 6 | 警告 |

較短的時間視窗可避免規則因已過去的尖峰而觸發。有規則監控該 SLO 後，側邊面板會列出這些規則，不再顯示按鈕。建立規則需要 `alerts.rules.manage`。

編輯 SLO 需要 `apm.slos.manage`，刪除則需要 `apm.slos.delete`。刪除 SLO 時，MoleSignal 會先刪除其燃燒率警示，因此還需要 `alerts.rules.manage`。

## 依 APM 指標觸發警示

APM 警示規則會監控服務或其端點的特定指標。規則讀取與 APM 頁面相同的彙總資料，不必撰寫查詢。

<Steps>
  <Step title="開啟規則編輯器">
    在服務頁面或端點側邊面板的標題列開啟**新增警示**，選擇**閾值警示**。編輯器會以 **APM 警示**資料來源開啟，並預先填入服務、環境和端點。在**警示 → 警示規則**中新增規則時，也可選擇 **APM 警示**資料來源。建立規則需要 `alerts.rules.manage`。
  </Step>
  <Step title="選擇指標">
    選擇**服務**、**環境**或**所有環境**、**端點**或**整個服務**，以及**指標**。依編輯器在指標下方標示的單位設定閾值。
  </Step>
  <Step title="測試並儲存">
    點選**測試規則**，比較最近 6 小時的指標與閾值，再建立規則。
  </Step>
</Steps>

| 指標 | 單位 |
|---|---|
| **錯誤率** | 百分比，0 到 100 |
| **P50 延遲**、**P90 延遲**、**P95 延遲**、**P99 延遲**、**平均耗時** | 毫秒 |
| **吞吐量** | 每秒請求數 |
| **請求數**、**錯誤數** | 規則時間視窗內的次數 |
| **新錯誤群組** | 規則時間視窗內首次出現的服務或端點錯誤群組數 |
| **Apdex** | 0 到 1 |
| **SLO 燃燒率** | 相對於目標允許消耗速率的倍數，從 SLO 建立。 |

每次評估都會讀取規則時間視窗內的資料：24 小時以內讀取分鐘層級的彙總資料，更長的時間視窗則讀取小時層級的彙總資料。時間視窗內沒有請求時，**請求數**、**錯誤數**、**新錯誤群組**和**吞吐量**的讀值為 `0`，因此規則能偵測流量中斷。此時其他指標沒有讀值，不會符合任何閾值條件，進行中的事件也會隨之恢復。

在編輯器中或從 SLO 建立的規則會依指定對象加上 `service.name`、`service.namespace`、`deployment.environment` 和 `apm.endpoint` 標籤。事件會複製這些標籤。所有 APM 規則的事件也會包含 `service` 標籤、列於 `affected_services` 的服務，以及從彙總資料取出的一筆樣本 trace ID。服務目錄的**警示**欄位、服務頁面的標題列和端點側邊面板會統計該服務已開啟和已確認的事件。若事件指定了環境，則只統計該服務所在環境的事件。端點側邊面板只會統計帶有該端點標籤的事件。點選數量即可開啟**警示 → 事件**。

同一選單中的**異常偵測警示**會在指標明顯偏離前幾天同一時刻的數值時發出警示，不必設定閾值。請參閱[為 APM 指標設定異常偵測警示](/zh-Hant/apm/insights#為-apm-指標設定異常偵測警示)。

## 篩選、解析度與保留期限

APM 頁面共用全域時間範圍。服務目錄可依環境和團隊篩選，服務頁面則可依環境和版本篩選。清單支援搜尋和排序。範圍會編碼至 URL，方便分享或重新開啟。

使用預設部署設定時：

- API 未指定範圍時，查詢最近 24 小時；
- `auto` 對不超過 24 小時的範圍採用分鐘時間桶，對更長的範圍採用小時時間桶；
- 分鐘層級的彙總資料保留 24 小時；
- 小時層級的彙總資料保留 30 天，查詢範圍最長也是 30 天。

管理員可調整這些部署限制。只有比較的兩個版本都達到設定的請求量閾值時，版本比較才會標記為資料充足。預設閾值為每個版本 1,000 個請求。

## 閱讀資料品質提示

每個 APM 回應都包含資料品質中繼資料。需要補充說明時，導覽卡片會顯示簡短提示，按一下即可查看詳細資訊。

| 提示 | 含義 |
|---|---|
| **資料起點在此範圍內** | APM 投影在所選範圍內才啟動，未統計更早的流量。 |
| **資料不完整** | 佇列、儲存庫、寫入、延遲抵達的資料、基數或關閉程序在部分時段造成資料缺口。請勿將缺少的資料視為零。 |
| **資料延遲** | `lastCompleteBucketAt` 落後於所選範圍，最近的彙總可能仍在關閉或彙整中。 |
| **部分名稱計入「其他」** | 達到基數上限時，系統會將超出上限的名稱合併計入名為**其他**的一列。請在 [APM 設定](/zh-Hant/apm/settings#基數上限)中設定上限。 |

請先縮短時間範圍並縮小篩選條件。如果資料仍不完整或延遲，再檢查 APM 健康狀態端點與 [APM 投影指標](/zh-Hant/self-observability#apm-投影)。

## 隱私權與資料限制

APM 會儲存彙總資料和少量已去識別化的證據。APM 彙總不會保留請求本文、回應本文、URL 查詢參數值、Header 或 SQL 參數；SQL 陳述式僅以範本形式保留，並以 `?` 取代所有常值。識別值、代表性訊息和堆疊框架都有長度限制；APM 會在永久儲存之前刪除或遮蔽疑似敏感或容易變動的值。

這些保護措施無法取代良好的遙測埋點做法。請勿將金鑰或個人資料放入 span 名稱、狀態描述、例外訊息或資源屬性。

## 疑難排解

| 現象 | 檢查項目 |
|---|---|
| 沒有 APM 資料 | 確認 trace 已進入同一個工作區、時間範圍包含近期流量，且角色具備 `apm.services.read` 權限。 |
| 出現 `unknown_service` | 匯出 span 前，請設定穩定的 `service.name` 資源屬性。 |
| 缺少端點 | 新增 `SERVER` 或 `CONSUMER` span kind，以及標準 HTTP、RPC 或訊息屬性。 |
| 缺少相依服務 | 為下游呼叫新增 `CLIENT` 或 `PRODUCER` span，並附上目標端的語意屬性。 |
| 缺少版本 | 為同一部署中的所有執行個體設定相同的 `service.version`。 |
| 缺少錯誤 | 依 OpenTelemetry 慣例記錄 exception event，並設定 span、HTTP 或 RPC 狀態。 |
| 找不到錯誤樣本的 trace | Trace 因取樣而遭捨棄，或已過期，但取樣前產生的 APM 彙總仍然有效。 |
| 沒有執行階段圖表 | 使用相同的 `service.name` 回報 OpenTelemetry 執行階段指標。 |
| 結果不完整或不是最新 | 查看資料品質提示和 `GET /api/v1/apm/health`。 |
| 服務停止後未觸發 APM 警示 | 沒有請求時，錯誤率、延遲和 Apdex 都沒有讀值。請使用**請求數**或**吞吐量**監控流量中斷。 |
| SLO 顯示**無資料** | 確認服務在 SLO 指定的環境中有回報資料，且端點名稱與**端點**清單中的名稱一致。 |
