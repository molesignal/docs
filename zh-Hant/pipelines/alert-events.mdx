**警示處理流程** 在建立事件前處理警示事件。處理步驟可以改寫事件標題、調整嚴重程度、新增或刪除標籤和註解、指定受影響的服務，也可以捨棄警示事件，不建立事件。[路由](/zh-Hant/alerting/routing)和通知使用的都是管線處理後的事件。

警示事件有四種來源：

| 來源 | 事件 |
|---|---|
| **警示規則** | [警示規則](/zh-Hant/alerting/rules)觸發。 |
| **外部來源** | [警示來源](/zh-Hant/alerting/sources)收到其他系統傳來的警示。 |
| **合成監控** | [合成監控](/zh-Hant/synthetics#警示事件)檢查失敗或沒有結果。 |
| **無資料** | 規則建立[無資料事件](/zh-Hant/alerting/rules#復原條件與無資料處理)。 |

手動建立的事件在建立前不經過警示處理流程。

管線也可以在[傳送通知前](#傳送通知前)執行：只處理事件的副本，僅修改單一通知策略傳送的內容。

## 新增警示處理流程

開啟 **管線**，選擇 **新增管線**，將 **執行模式** 設為 **警示事件**。**訊號類型** 顯示為 **警示事件**，設定中以[**執行順序**](#執行順序)取代排程。流程有三個節點：

| 節點 | 說明 |
|---|---|
| **警示事件** | 這條管線要處理的警示事件，請參閱[條件](#條件)。 |
| **處理步驟** | 依執行順序排列的各個步驟，請參閱[步驟](#步驟)。 |
| **寫回事件** | 根據各步驟修改後的內容建立事件。 |

**試執行** 可在儲存前讓一筆範例警示事件跑完各個步驟。各步驟會將它視為警示規則即將建立事件時的警示事件：`%source` 為 `rule`，`%event` 為 `opened`。若要測試其他值，請修改 **範例事件**，再選擇 **執行**。結果會顯示每個步驟處理後的事件，或顯示捨棄事件的步驟。試執行不儲存任何資料，也不呼叫任何外部服務：**AI 摘要** 和 **透過查詢補充資料** 步驟會在各自的註解中寫入 `…`，**呼叫 API 以補充資料** 步驟則會將事件原樣傳給下一步，並標示 **試執行時不呼叫**。

具備 `alerts.incidents.read` 權限時，**使用一筆近期警示事件** 會列出最近 7 天內最新的 20 筆事件。選取一筆事件後，系統會將其內容填入 **範例事件**，各步驟也會讀取該事件的規則和來源。這是事件儲存時的內容，已包含建立事件時管線所做的修改。

使用設定中的 **處理告警事件** 開關啟用或停用這條管線。停用時，所有警示事件都會原樣通過。選擇 **建立管線** 儲存。儲存的變更會在 10 秒內套用至所有節點。

## 條件

選擇 **警示事件** 節點，設定這條管線要處理的警示事件：

- **來源**：**警示規則**、**外部來源**、**合成監控** 和 **無資料**。規則建立的無資料事件歸類為 **無資料**，而非 **警示規則**；合成監控檢查沒有結果時建立的事件歸類為 **合成監控**。
- **嚴重程度**：**嚴重**、**錯誤**、**警告** 和 **提示**。
- **標籤**：使用 **新增標籤條件** 新增一組標籤和值。事件必須包含指定的每個標籤，且值必須完全相符。
- **時間**：選擇 **任何時間**，或選擇 **僅限這些時段內**、**僅限這些時段外**，並依同一個時區設定每週的時段。管線會依事件建立的時間判斷。例如，只在夜間執行 ETL 的兩小時內捨棄某類警示。

這些條件上方的 **執行時機** 決定管線何時執行：預設為 **建立事件前**，也可選擇 [**傳送通知前**](#傳送通知前)。

未選取任何來源或嚴重程度時，管線會處理所有來源或所有嚴重程度的事件。未設定任何條件的管線會處理所有警示事件。不符合條件的事件會原樣通過這條管線。

## 執行順序

警示處理流程會逐條執行。**執行順序** 的值較小者先執行，值相同時依名稱排序。每條管線都會接收前面的管線修改後的事件，並依該事件判斷條件。因此，若某條管線調高嚴重程度，事件可能因此符合後續管線的條件。

## 步驟

**新增步驟** 提供其他管線中的剖析類和欄位類步驟（包括 **查詢擴充表以補充資料**），以及 **篩選事件**、**AI 摘要**、**呼叫 API 以補充資料**、**透過查詢補充資料** 和 **自訂 VRL**。請參閱[處理步驟](/zh-Hant/pipelines#處理步驟)。在警示處理流程中，**依規則運算式批次重新命名** 和 **僅保留指定欄位** 預設處理 `labels`。警示處理流程不支援取樣或分流。將管線改為警示處理流程時，請先刪除現有的 **取樣** 或 **資料分流** 步驟，再儲存。

### 步驟接收的警示事件

步驟接收的警示事件採用下列 JSON 格式：

```json
{
  "summary": "Checkout error rate above 5%",
  "severity": "error",
  "labels": { "service": "checkout", "env": "prod", "host_name": "web-01" },
  "annotations": { "runbook": "https://wiki.example.com/checkout" },
  "affected_services": ["checkout"]
}
```

| 欄位 | 內容 | 步驟可寫入的值 |
|---|---|---|
| `summary` | 事件標題。 | 非空白字串。系統會截去超過 512 個字元的部分。 |
| `severity` | 事件的嚴重程度。 | `info`、`warning`、`error` 或 `critical`，不區分大小寫。系統會將 `warn` 和 `crit` 分別解讀為 `warning` 和 `critical`。 |
| `labels` | 事件的標籤。 | 值為字串的物件。系統會將數字和布林值轉為字串，並在值為 `null` 時刪除該標籤。 |
| `annotations` | 事件的註解。 | 同 `labels`。 |
| `affected_services` | 受影響服務的名稱。 | 名稱清單。系統會移除重複或空白的名稱。 |

系統不會將步驟新增的其他欄位寫入事件。若步驟刪除整個欄位，該欄位會保留原值。若要清空標籤，請寫入 `.labels = {}`。不符合這些規則的值（例如在 `labels` 中巢狀置入物件）會使這條管線發生錯誤，請參閱[處理結果](#處理結果)。

無論步驟如何修改，MoleSignal 寫入的標籤（例如 `alert.source`、`external.kind`）都會維持原樣，因為這些標籤會指出事件的來源。步驟可以讀取這些標籤。

### 事件來源

步驟會從中繼資料讀取警示事件的來源資訊。這些值不會成為事件欄位。

| 中繼資料 | 值 |
|---|---|
| `%source` | `rule`、`external`、`synthetic` 或 `no_data`。 |
| `%rule_id` | 警示規則、警示來源或合成監控檢查的 ID。 |
| `%rule_name` | 警示規則、警示來源或合成監控檢查的名稱。 |
| `%event` | 建立事件前為 `opened`；事件仍開啟且來源再次觸發時為 `severity_changed`，請參閱[嚴重程度變更](#嚴重程度變更)。 |

```ruby
# 预发环境的告警最多按警告通知
if .labels.env == "staging" && (.severity == "critical" || .severity == "error") {
  .severity = "warning"
}

# 从扩展表 host_owner 查出主机所属的团队
owner = lookup("host_owner", .labels.host_name)
if is_object(owner) {
  .labels.team = owner.team
}

# 已知的误报不开事件
if %rule_name == "Disk inode usage" && .labels.mount == "/boot" {
  abort
}
```

第二個步驟設定的 `team` 標籤可將事件指派給該團隊，請參閱[指派順序](/zh-Hant/alerting/routing#分派順序)。`lookup` 與 `geoip_lookup` 在警示處理流程中的用法與其他 VRL 步驟相同，請參閱[查詢擴充表與 IP 位址](/zh-Hant/functions#查詢擴充表與-ip-位址)。

### AI 摘要

**AI 摘要** 步驟會將前面步驟修改後的警示事件連同 **提示詞** 傳給組織的模型，並將回覆寫入 **寫入的註解** 所指定的註解，預設為 `ai_summary`。提示詞可寫成：

```text
用两句话为值班工程师总结这条告警：出了什么问题，先查什么。
```

- 只在建立事件時呼叫模型一次，[嚴重程度變更](#嚴重程度變更)時不再呼叫。
- 使用最近更新、已啟用且已填寫 API 金鑰的[模型服務](/zh-Hant/agent#設定模型服務)及其 **預設模型**。回覆不會超過該模型服務的 **最大輸出 Token 數**，未設定時不會超過 512 個 token。
- 這個步驟會將警示的標題、嚴重程度、標籤、註解和受影響的服務傳給模型服務供應商。
- 呼叫會計入組織的[每日 token 預算](/zh-Hant/agent#用量與預算)，並在依來源統計的用量中列為 **LLM 函式**。`[functions].llm_eval_enabled` 不會影響這個步驟。
- 如果模型無法回覆（未設定模型服務、當天預算已用完或呼叫失敗），這個步驟會發生錯誤，導致整條管線發生錯誤，其他步驟的修改也會一併作廢。若要確保其他修改不受影響，請將 **AI 摘要** 步驟單獨放在執行順序較後的管線中。

### 呼叫 API 以補充資料

**呼叫 API 以補充資料** 步驟會透過 POST 將警示事件傳至組織的一個 [HTTP 連接器](/zh-Hant/connectors#目標)，並採用回應中的修改。這個步驟使用該連接器的位址、憑證和對外連線防護：先解析主機名稱，只連線至解析出的位址，拒絕存取雲端中繼資料位址，也不跟隨重新導向。

要求本文包含前面步驟修改後的事件欄位，以及事件的來源：

```json
{
  "summary": "Checkout error rate above 5%",
  "severity": "error",
  "priority": null,
  "urgency": null,
  "labels": { "service": "checkout" },
  "annotations": {},
  "affected_services": ["checkout"],
  "metadata": { "rule_id": "…", "rule_name": "Checkout errors", "source": "rule", "event": "opened" }
}
```

- 只從回應的 JSON 物件讀取 `summary`、`severity`、`priority`、`urgency`、`labels`、`annotations` 和 `affected_services`。規則與[步驟接收的警示事件](#步驟接收的警示事件)相同。`labels` 和 `annotations` 會依鍵合併，值為 `null` 時會刪除該鍵，因此服務只需回傳要新增的內容。空白回應不會做任何修改。
- 呼叫的時間上限為 5 秒，只在建立事件時呼叫一次，[嚴重程度變更](#嚴重程度變更)時不再呼叫。
- 如果呼叫失敗（逾時、狀態碼不是 2xx、回應不是 JSON 物件或超過 1 MiB、欄位不符合規則、連接器已停用或不存在），只略過這個步驟的修改。事件會以進入這個步驟前的內容繼續處理，後續步驟照常執行，先前的修改也會保留。[時間軸](#處理結果)和[計數](#當天的計數)會記錄原因。

### 透過查詢補充資料

**透過查詢補充資料** 步驟會執行一條使用事件欄位值的查詢，並將結果寫入註解：

```sql
SELECT count(*) AS errors FROM app_logs WHERE level = 'error' AND host = '{{labels.host_name}}'
```

| 欄位 | 說明 |
|---|---|
| **語言** | SQL 或 PromQL。PromQL 讀取指標串流。 |
| **資料類型**、**資料串流** | 指定查詢要讀取的資料串流。這裡無法讀取 `_audit`，因為這個步驟執行時無法使用任何使用者的 `audit.read` 權限。 |
| **查詢** | 一條可包含預留位置的查詢。 |
| **回溯時間（秒）** | 從事件建立時間往前回溯的秒數。預設為 300，最多 86,400。 |
| **列數** | 寫入註解的列數。預設為 5，最多 50。 |
| **寫入的註解** | 指定寫入結果的註解，預設為 `query_result`。 |

預留位置代表事件中的值：`{{labels.<key>}}`、`{{annotations.<key>}}`、`{{summary}}`、`{{severity}}`、`{{priority}}`、`{{urgency}}`、`{{rule_id}}`、`{{rule_name}}` 或 `{{source}}`。標籤可能來自其他系統，因此請將預留位置放在查詢陳述式的字串引號內，系統才會對值進行逸出處理。若放在其他位置，儲存時會傳回 `400`。

- 註解中每列結果各占一行：只有一個值時直接寫入該值，多個值則寫成 `column=value, column=value`。最多 4,000 個字元。查詢沒有結果時，不寫入這個註解。
- 查詢的時間上限為 10 秒，只在建立事件時執行一次。
- 如果查詢失敗，或事件缺少預留位置需要的值，系統只會略過這個步驟的修改，與[**呼叫 API 以補充資料**](#呼叫-api-以補充資料)相同。

## 處理結果

每條處理事件的管線會產生下列三種結果之一：

| 結果 | 原因 | 影響 |
|---|---|---|
| **處理** | 所有步驟皆已執行完畢。 | 事件會保留這些修改並繼續處理。 |
| **捨棄** | 某個步驟執行了 `abort`。 | 不建立事件，也不再執行後續管線。 |
| **錯誤** | 某個步驟失敗，或修改後的欄位不符合[步驟接收的警示事件](#步驟接收的警示事件)中的規則。**呼叫 API 以補充資料** 或 **透過查詢補充資料** 步驟失敗也歸類為錯誤。 | 這條管線的修改會作廢；若只有上述兩種步驟失敗，則保留其他步驟的修改。事件會交給下一條管線，並照常建立。 |

在事件的[時間軸](/zh-Hant/alerting/incidents#事件詳細資料)中，每條修改內容或發生錯誤的管線各有一行記錄，例如 **經過管線 Payments routing：嚴重程度 error → critical，標籤 +team=payments**。發生錯誤時，記錄會說明原因。未做任何修改的管線和[嚴重程度變更](#嚴重程度變更)時的處理都不留下記錄。每行最多顯示 40 處修改，其餘只計入總數。超過 200 個字元的值會截斷。

規則持續觸發時，管線會在每次評估時再次捨棄事件。[規則清單](/zh-Hant/alerting/rules#規則清單)會將規則狀態顯示為 **已由處理管線捨棄**，API 中該規則的 `last_state` 為 `{"kind": "dropped"}`。捨棄事件的管線會記錄這次捨棄，並在 **總覽** 中指出最近一次捨棄的事件來自哪條規則。管線捨棄的外部警示會在警示來源的[**近期收到的請求**](/zh-Hant/alerting/sources#近期收到的請求)中顯示為 **忽略**，旁邊會列出捨棄警示的管線和步驟。

## 嚴重程度變更

事件仍開啟時，每當警示規則再次觸發、外部來源再次傳送同一筆警示，或合成監控檢查的狀態改變，警示處理流程都會重新判定事件的嚴重程度：

- 依建立事件時的方式重新組成警示事件，採用來源目前回報的嚴重程度，並交由符合條件的管線處理，但略過其中的 **AI 摘要**、**呼叫 API 以補充資料** 和 **透過查詢補充資料** 步驟。此時 `%event` 為 `severity_changed`。
- 只採用步驟最終決定的嚴重程度。若與事件目前的嚴重程度不同，就更新事件的嚴重程度。標題、標籤、註解和受影響的服務維持事件建立時的內容。
- 若某條管線此時捨棄事件或發生錯誤，事件內容不變，並保持開啟。下一條管線照常執行。

因此，即使規則後續回報更高的嚴重程度，調低預備環境警示嚴重程度的步驟仍會生效。已確認的事件和手動設定過嚴重程度的事件都會維持原有的嚴重程度。

## 傳送通知前

在 **警示事件** 節點將 **執行時機** 設為 **傳送通知前**，管線就會在[通知策略](/zh-Hant/notification-channels)傳送警示通知前執行。管線會處理事件的副本，每項適用的策略每次傳送通知時都會執行一次，包括後續步驟及升級所傳送的通知。可用於縮短簡訊策略的標題、為特定團隊的 Webhook 加上標籤，或讓特定策略在夜間不傳送通知，而不改變事件本身。

- 使用 **通知策略** 選擇這條管線適用的策略。未選取任何策略時，管線會套用至警示事件的所有通知策略。此時，系統已依事件進入管線時的內容完成策略比對。
- 其他條件照常依通知所對應的事件判斷。時間以事件發生的時間為準，**來源** 多了 **手動建立的事件**。
- 步驟只在 MoleSignal 內部執行。**AI 摘要**、**呼叫 API 以補充資料** 和 **透過查詢補充資料** 只在建立事件時執行。如果管線包含這些步驟，儲存時會傳回 `400`。
- 流程以 **寫入通知** 結束。策略會傳送步驟處理後的標題、嚴重程度、優先順序、緊急程度、標籤、註解和服務。[範本](/zh-Hant/notification-channels#範本變數)、Webhook 要求本文和預設文字都會使用相同的內容。系統仍依事件進入管線時的內容判定通知對象。
- 步驟執行 `abort` 時，這項策略不會傳送通知。傳送記錄會新增一筆 **已略過** 記錄，並以工作區的預設語言寫明管線和步驟（`error_code` 為 `dropped_by_pipeline`）。事件的時間軸也會記錄。這不算傳送失敗，因此這項策略不會重試，也不會繼續執行確認逾時後的升級。
- 管線發生錯誤時，修改會作廢，通知會以進入管線時的內容繼續傳送。[計數](#當天的計數)會記錄錯誤，但時間軸不會留下記錄。

除了 `%rule_id`、`%rule_name` 和 `%source`，步驟還可讀取 `%policy_id` 和 `%policy_name`。`%event` 為 `triggered`、`escalated`、`acknowledged` 或 `resolved`。`%rule_name` 是規則名稱；若事件不是由規則建立，則為事件標題。**試執行** 使用的範例值為 `triggered` 和 `On-call alerts`。

```ruby
# 预发环境的值班告警只发严重的
if %policy_name == "On-call alerts" && .labels.env == "staging" && .severity != "critical" {
  abort
}
```

## 當天的計數

警示處理流程沒有獨立的執行紀錄，因此沒有執行歷程，也無法使用 **更多 → 回填**。系統改為統計當天（UTC）的處理情況：

- 清單中，已啟用的警示處理流程會在 **狀態** 欄顯示 **等待警示事件**，並在 **最近一次執行** 欄顯示計數，例如 **今天：處理 41 · 捨棄 3 · 錯誤 0**。
- 管線 **總覽** 上的 **處理**、**捨棄** 和 **錯誤** 會顯示相同的計數。**捨棄** 下方會顯示最近一次捨棄的事件來自哪條規則或哪個來源，以及捨棄的時間。**錯誤** 下方會顯示最近一次錯誤的原因。

計數會在 UTC 午夜歸零。不符合條件的事件和[嚴重程度變更](#嚴重程度變更)時重新處理的事件都不計入。API 會在 `alert_record` 中傳回這些計數，請參閱[管理管線](/zh-Hant/api/intake/scheduled-pipelines#檢視)。

## 限制

| 限制 | 值 |
|---|---|
| 單條警示處理流程的步驟數 | 20 |
| **AI 摘要** 步驟的提示詞 | 8 KiB |
| 註解名稱 | 255 位元組 |
| **呼叫 API 以補充資料** 步驟的回應 | 1 MiB，5 秒內 |
| **透過查詢補充資料** 步驟的查詢陳述式 | 8 KiB |
| **透過查詢補充資料** 步驟的列數 | 50 列，10 秒內 |
| **透過查詢補充資料** 步驟寫入的文字 | 4,000 個字元 |

## 透過 API 建立

警示處理流程的儲存方式與其他管線相同。將 `functionSteps.mode` 設為 `alert`，並將資料串流和排程留空：

```bash
curl -X POST http://localhost:5080/api/v1/scheduled_pipelines \
  -H "authorization: Bearer $MS_TOKEN" \
  -H 'content-type: application/json' \
  -d '{
    "name": "staging-alerts",
    "sourceStream": "",
    "targetStream": "",
    "cron": "",
    "enabled": true,
    "functionSteps": {
      "mode": "alert",
      "alert": {
        "sources": ["rule", "external"],
        "severities": [],
        "labels": { "env": "staging" },
        "order": 10
      },
      "steps": [
        { "transformName": "cap-severity", "kind": "vrl",
          "script": "if .severity == \"critical\" { .severity = \"warning\" }" },
        { "transformName": "summary", "kind": "ai_summary",
          "prompt": "用两句话为值班工程师总结这条告警。",
          "annotation": "ai_summary" }
      ]
    }
  }'
```

若要在傳送通知前執行管線，請將 `alert.stage` 設為 `notify`，並可使用 `alert.policies` 指定策略：

```json
{
  "mode": "alert",
  "alert": { "stage": "notify", "policies": ["<policy id>"], "labels": { "env": "staging" }, "order": 10 },
  "steps": [
    { "transformName": "quiet", "kind": "vrl", "script": "if .severity != \"critical\" { abort }" }
  ]
}
```

如需完整欄位清單，請參閱[建立管線](/zh-Hant/api/intake/create-pipeline)。警示處理流程使用與其他管線相同的[權限](/zh-Hant/pipelines#權限)。
