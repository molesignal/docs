[規則](/zh-Hant/alerting/rules)觸發、[合成監控檢查失敗](/zh-Hant/synthetics#警示事件)，或[警示來源](/zh-Hant/alerting/sources)收到外部警示時，系統會開啟事件。事件會記錄規則、取值、標籤，以及結束前的每個步驟。開啟 **警示 → 警示事件**，或按 `⌘⌥A`。讀取事件需要 `alerts.incidents.read`；確認、解決和暫緩需要 `alerts.incidents.acknowledge`；[處理事件](#處理事件)中的其他操作需要 `alerts.incidents.update`，升級和合併需要 `alerts.incidents.escalate`；靜默需要 `alerts.incidents.silence`。透過飛書 App 或 Slack App 收到警示通知時，也可直接在卡片上確認、解決或暫緩，請參閱[警示卡片](/zh-Hant/im#告警卡片)；收到簡訊或電話時，可回覆代碼或按鍵處理，請參閱[回覆簡訊與電話按鍵](/zh-Hant/notification-channels#簡訊回覆與電話按鍵)。

## 事件狀態

| 狀態 | 清單中的標籤 | 含義 |
|---|---|---|
| `open` | **等待確認** | 正在觸發，尚未有人確認，升級會繼續進行。 |
| `acknowledged` | **處理中** | 已有人接手，升級停止。 |
| `resolved` | **已恢復** | 已結束：規則已恢復，或已有成員解決事件。 |
| `closed` | **已關閉** | 已結束。 |

規則符合[恢復條件](/zh-Hant/alerting/rules#復原條件與無資料處理)時，系統會自動解決尚未結束的事件。外部來源回報恢復時，系統也會解決該來源的對應事件，包括已確認的事件。請參閱[外部警示如何轉為事件](/zh-Hant/alerting/sources#外部警報如何成為事件)。已確認的事件會維持該狀態，直到有成員解決事件。若升級策略設有[確認後仍未解決](/zh-Hant/alerting/on-call#確認後仍未解決)，事件超過設定時間後會回到 **等待確認**，並重新發送通知。暫緩中的事件會顯示為 **處理中**。每條規則（或依維度拆分的規則中的每一組）同一時間最多只有一個進行中的事件。

## 事件清單

**警示事件** 頁面頂端會統計受影響的服務數、等待確認的事件數，以及最近 24 小時內恢復的事件數。摘要會顯示目前有多少事件正在觸發、最早觸發的事件已持續多久，以及系統正在評估多少條規則。**最近恢復** 會列出近期結束的事件。

可在 **觸發中** 與 **等待確認**（尚未有人接手的事件）之間切換。目前的使用者若隸屬團隊，也會看到 **我的團隊**，只列出[分派](/zh-Hant/alerting/routing)給所屬團隊的事件。右側可依優先順序篩選，或只查看優先順序為 **不設定** 的事件。事件先依嚴重程度排序，同一嚴重程度再依優先順序排序，最後依開始時間排序。每列會顯示層級、事件及其服務（低緊急程度的事件會標示 **低緊急程度**）、優先順序、狀態、持續時間、負責人和受指派的團隊，並提供三項操作：

| 操作 | 效果 |
|---|---|
| **確認** | 接手事件。事件會變為 **處理中**，升級停止。 |
| **靜默** | 只暫停這個事件的後續通知與升級。請參閱[靜默單一事件](/zh-Hant/alerting/silences#靜默單一事件)。 |
| **Runbook** | 開啟規則的處理指南（如有）。 |

勾選多列後（可勾選表頭的核取方塊以全選），清單上方會顯示批次處理工具列：**確認**、**解決**、**暫緩**、**轉派**、**調整**（嚴重程度、優先順序或緊急程度）。勾選兩個以上的事件時，還會顯示 **合併**。在對話框中選擇要保留的主事件。一次最多可處理 100 個事件。若有無法處理的事件（例如已恢復），系統會顯示失敗數量及第一個失敗原因，其餘事件照常處理。

### 新增事件

客戶通報的故障或成員發現的異常若未觸發規則，也可建立事件，照常通知和升級。按一下清單上方的 **新增事件**（需要 `alerts.incidents.create`）：

1. 在 **發生了什麼事** 中填寫 **標題**（必填）和 **說明**（支援 Markdown），選擇 **嚴重程度**（預設為錯誤）、**優先順序** 和 **緊急程度**（預設依升級策略）。視需要填寫 **受影響的服務**（以逗號分隔）和 **標籤**（每列一個 `key=value`）。
2. 在 **交給誰** 中選擇一個選項：

   | 選項 | 效果 |
   |---|---|
   | **依路由分派** | 和規則開啟的事件一樣，依[警示路由](/zh-Hant/alerting/routing)分派。 |
   | **交給團隊** | 使用團隊的值班策略。若團隊未設定，則使用預設策略。 |
   | **交由升級策略處理** | 從這項策略的第 1 級開始通知。 |
   | **指定成員** | 直接通知最多 10 位成員，不使用升級策略。 |

3. 視需要勾選 **同時宣告為重大事件**，再按一下 **建立事件**。系統會開啟事件詳細資料頁面。

手動建立的事件帶有 `alert.source=manual` 標籤，`created_by` 註解記錄建立者，`description` 註解記錄說明。這類事件不經過警示管線，每次都會建立新事件，不會與其他事件去重，也不會自動恢復，必須由成員手動解決。詳細資料頁面頂端的 **手動建立** 會顯示建立者，洞察則將這類事件歸為 **手動建立**。Mole Agent 的 `create_incident` 工具也能建立事件（需一人核准）。

## 事件詳細資料

按一下事件即可開啟詳細資料。頁面頂端會顯示狀態、觸發時間、規則和持續時間，並提供 **確認**、**解決** 和 **更多操作**。**更多操作** 包含[處理事件](#處理事件)的各項操作及 **靜默**。

| 區塊 | 內容 |
|---|---|
| **時間軸** | 顯示觸發時間、通知對象、操作者及操作（確認、轉派、增派、升級、暫緩、變更嚴重程度、合併、解決，以及修復動作、工單和重大事件的各個步驟）、[警示管線](/zh-Hant/pipelines/alert-events#處理結果)在開啟事件前做的變更、操作管道（介面、IM、回覆簡訊、電話按鍵、Mole Agent），以及各步驟之間經過的時間。底部可新增[備註](#備註)，下方會列出併入此事件的其他事件。 |
| **調查** | **開啟觸發查詢** 會在探索頁面重新執行當時使用的確切查詢。**相關日誌** 和 **相關指標** 會開啟相同時間範圍內受影響的相關資料。RUM 指標觸發的事件另提供 **在 RUM 中開啟**。 |
| **排查線索** | 規則的[排查線索](/zh-Hant/alerting/rules#排查線索)：排查步驟、依事件時間範圍開啟的排查查詢，以及相關儀表板。規則未設定排查線索時，不顯示此區塊。 |
| **AI 根因** | Mole Agent 的分析。請參閱 [AI 根因](#ai-根因)。 |
| **跨訊號參照** | 可按一下證據中出現的服務、Trace ID 或主機，前往對應項目。 |
| **觸發查詢** | 查詢及其傳回的值。**展開樣本值** 會顯示樣本列。 |
| **中繼資料** | 事件的標籤與註解。 |
| **負責人** | 升級通知的對象，以及[分派](/zh-Hant/alerting/routing#事件的分派結果)的團隊和依據。若事件已暫緩、已併入其他事件，或嚴重程度由成員手動設定，這裡也會註明。 |
| **影響範圍** | 若事件與服務相關聯，會顯示該服務在服務地圖上的影響範圍。請參閱[事件的影響範圍](/zh-Hant/apm/insights#事件的影響範圍)。 |
| **工作階段樣本** | 針對 RUM 指標觸發的事件，列出可看出問題的工作階段，每個都可回放。請參閱 [RUM 警示](/zh-Hant/rum/alerts#事件)。 |
| **相似事件** | 過去 90 天內的相似事件及其結束方式。請參閱[相似事件與最近變更](#相似事件與最近變更)。 |
| **最近變更** | 事件觸發前後，相關服務及下游服務回報的部署、設定和開關變更，以及這條規則在觸發前一天內的變更。 |
| **修復動作** | 適用於此事件的修復動作，以及已發起的執行和核准流程。請參閱[修復動作](/zh-Hant/alerting/remediation)。 |
| **工單** | 顯示此事件在 Jira、ServiceNow 或飛書專案中的工單及狀態，也可在此建立工單。請參閱[工單](/zh-Hant/alerting/tickets)。 |
| **重大事件** | 宣告重大事件、指派角色、進入作戰室和會議、分派任務並發布進度。請參閱[重大事件與事後檢討](/zh-Hant/alerting/major-incidents)。 |
| **事後檢討** | 事件的內部事後檢討：選擇 **撰寫事後檢討** 可依範本起草，選擇 **開啟事後檢討** 可繼續撰寫。請參閱[事後檢討](/zh-Hant/alerting/major-incidents#事後檢討)。 |

## 處理事件

系統會將 **更多操作** 中的各項操作記錄在時間軸上。也可透過 [API](#事件-api) 執行這些操作。Mole Agent 也能執行這些操作：新增備註須由提問者確認，其餘操作須由一人核准。請參閱[核准與執行](/zh-Hant/agent#核准與執行)。Mole Agent 還能建立工單、指派重大事件的角色、新增任務和起草事後檢討（須由提問者確認），也能宣告重大事件和發布進度（須由一人核准），以及提議執行修復動作（須由兩人核准，符合[預先核准](/zh-Hant/alerting/remediation#預先核准)條件的動作除外）。已恢復或已併入其他事件的事件不能再執行這些操作，但仍可[新增備註](#備註)。

| 操作 | 效果 |
|---|---|
| **轉派** | 轉派給成員（最多 10 位）：指定成員會成為負責人並收到通知。事件會回到 **等待確認**，若仍無人確認，則照常升級。轉派給團隊：從第 1 級重新套用該團隊的值班策略。若團隊未設定策略，則使用預設策略。轉派給升級策略：改用指定策略，從第 1 級重新開始，團隊不變。可附上一則備註，系統會將其記錄在時間軸上。 |
| **增派** | 將選取的成員加入負責人名單並發送通知，事件狀態維持不變。 |
| **立即升級** | 選擇一個層級，立即通知該層級的對象，預設為下一級。清單只會顯示適用於事件嚴重程度的層級。已確認的事件會回到 **等待確認**。 |
| **暫緩** | 選擇 1、4、8 或 24 小時，或選擇 **自訂…**（1 分鐘至 7 天）。若事件仍在等待確認，系統會先將它標為已確認。暫緩期間不發送通知。暫緩到期後，事件會回到 **等待確認**，負責人會再次收到通知。選擇 **取消暫緩** 可立即結束暫緩。 |
| **嚴重程度** | 手動設定後，規則、警示來源和合成監控檢查都不再變更嚴重程度。調高等待確認事件的嚴重程度時，系統會依新的嚴重程度從第 1 級重新發送通知；調低時只變更嚴重程度。 |
| **優先順序** | 從組織的[優先順序等級](/zh-Hant/alerting/on-call#緊急度與優先順序等級)中選擇一級（預設為 P1 至 P5），或選擇 **不設定**。只變更優先順序，不會重新發送通知。優先順序用於清單欄位和篩選、[路由規則](/zh-Hant/alerting/routing)的條件、自動宣告重大事件、工單優先順序對應和洞察分類。 |
| **緊急程度** | 選擇 **高緊急程度** 或 **低緊急程度**，請參閱[緊急程度](/zh-Hant/alerting/on-call#緊急程度)。從低調高時，系統會對等待確認的事件從第 1 級重新發送通知。調低時只變更緊急程度，後續不再升級。手動變更後，支援時段不再調整緊急程度。 |
| **合併** | 將其他進行中的事件併入此事件，請參閱[合併事件](#合併事件)。 |
| **靜默** | 請參閱[靜默單一事件](/zh-Hant/alerting/silences#靜默單一事件)。 |

這些操作發出的通知屬於升級通知。範本中的 `{{escalation.reason}}` 會說明原因：`reassigned`（轉派）、`responder_added`（增派）、`manual`（立即升級）、`snooze_ended`（暫緩到期）、`severity_raised`（調高嚴重程度）、`urgency_raised`（調為高緊急程度），或 `ack_timeout`（確認後逾時仍未解決）。範本也可使用 `{{urgency}}` 和 `{{priority}}`。請參閱[範本變數](/zh-Hant/notification-channels#範本變數)。

### 合併事件

同一個問題若開啟多個事件（例如一次故障觸發多條規則），可將這些事件併入同一個主事件。併入的事件不再個別發送通知或升級，也不再出現在事件清單及洞察中，而會列在主事件的時間軸下方。主事件解決時，系統會一併解決併入的事件。若併入的事件先自行恢復，系統會在主事件的時間軸上留下紀錄。一次最多可併入 50 個事件，合併後無法拆分。

在詳細資料頁面的 **更多操作 → 合併** 中勾選要併入的事件。也可在事件清單中勾選多個事件，按一下 **合併**，再選擇主事件。

### 備註

在時間軸底部的輸入框新增備註，最多 4000 字。記下發現的問題和採取的措施，讓接手的成員一目瞭然。轉派時附上的備註也會記錄在此。Mole Agent 讀取事件時，也會讀取最近幾則備註。

## AI 根因

為 Mole Agent 設定模型服務後，Mole Agent 會在背景分析新事件，並將有證據支持的結果儲存到事件中。選擇 **產生** 可立即請求分析，選擇 **重新產生** 可取代現有結果。可選擇 **有幫助** 或 **沒有幫助** 評價結果，評價會記錄在[品質](/zh-Hant/quality)中。

產生分析需要 Mole Agent 權限。組織當天的 Mole Agent token 預算用完後，系統會暫停自動分析，並依預算設定處理手動產生的請求。請參閱[用量與預算](/zh-Hant/agent#用量與預算)。

## 相似事件與最近變更

**相似事件** 會在同一組織過去 90 天的事件中，找出最多 5 個最相似的事件，並標註相似原因：**相同警示**（指紋相同）、**相同規則**、**相同服務**、**標籤相似**、**標題相似**（也可比對中文標題）或 **同一團隊**。每個事件都會顯示持續時間、解決事件的成員、備註數量，以及 AI 根因的第一句，方便接手的成員參考先前的處理方式。

**最近變更** 會列出事件觸發前 30 分鐘至觸發後 10 分鐘內，事件相關服務及其在服務地圖上的下游服務[回報的變更](/zh-Hant/apm/deployments#從-ci-回報發佈)，包括部署（會標示失敗或復原的部署）、設定和開關變更。清單會標明變更是否來自下游服務；若附有管線連結，可按一下開啟。若事件的規則在觸發前一天內有變更，也會列在這裡。沒有服務地圖時，只列出事件相關服務的變更。

## 事件分組

[語意分組](/zh-Hant/alerting/silences#語意分組)會將相關事件（例如某個服務的所有嚴重事件）歸為一組。使用 `POST /api/v1/alerts/incident_groups/{id}/ack` 或 `/resolve` 確認或解決分組時，系統會對組內每個事件套用同樣的操作。

## 歷史紀錄

**警示 → 歷史紀錄** 會列出過去的事件，包括目前狀態、觸發和恢復時間，以及持續時間。可依事件名稱、服務或事件 ID 搜尋，並依層級和狀態篩選。

## 洞察

**警示 → 洞察** 會顯示工作區在最近 24 小時、7 天或 30 天內的應變情況：

| 區塊 | 顯示內容 |
|---|---|
| 摘要 | 仍須處理的事件數、已恢復事件的 **平均恢復時間**，以及 **快速恢復的事件**：顯示 60 秒內恢復的事件比例，比例偏高可能表示規則產生較多雜訊。 |
| **事件時間趨勢** | 顯示事件數。24 小時範圍按小時統計，較長的範圍按天統計。使用瀏覽器時區，並標示峰值。 |
| **主要受影響的服務** | 事件中最常出現的服務。規則須帶有 `service` 標籤。 |
| **主要觸發規則** | 開啟最多事件的規則。建議優先調整這些規則。 |
| **應變** | 平均接手時間（P50、P90）、恢復時間中位數、升級率和有人接手的事件比例，並與前一個同樣長度的時段比較；各層級的確認率；首次接手的管道（網頁、介面、IM 卡片、回覆簡訊、電話按鍵或 Mole Agent）；以及依團隊、服務、個人和優先順序分類的接手、恢復和升級資料（未設定優先順序的事件不納入該分類統計）。以第一次確認的時間為首次接手時間；若成員未確認就直接解決事件，則以解決時間計算。 |
| **值班負擔** | 顯示每位成員的值班時數、收到警示通知的次數（包括夜間和週末各收到幾次）、有幾晚被通知吵醒，以及首次接手的事件數和平均接手時間。夜間依各排班的時區計算，為 22:00 至隔日 08:00。排班詳細資料也會顯示該排班成員的值班負擔。 |
