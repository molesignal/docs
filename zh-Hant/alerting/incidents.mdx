[規則](/zh-Hant/alerting/rules)觸發、[撥測失敗](/zh-Hant/synthetics#警示事件)或[警示來源](/zh-Hant/alerting/sources)收到外部警示時會開啟事件。事件記錄規則、取值、標籤以及結束前的每一步。開啟 **警示 → 警示事件**，或按 `⌘⌥A`。讀取事件需要 `alerts.incidents.read`；確認、解決和暫緩需要 `alerts.incidents.acknowledge`；[處理事件](#處理事件)裡的其他操作需要 `alerts.incidents.update`，升級和合併需要 `alerts.incidents.escalate`；靜默需要 `alerts.incidents.silence`。經飛書 App、Slack App 收到的警示通知也能在卡片上直接確認、解決或暫緩，見[警示卡片](/zh-Hant/im#告警卡片)；簡訊和電話能回覆代碼或按鍵處理，見[回覆簡訊與電話按鍵](/zh-Hant/notification-channels#簡訊回覆與電話按鍵)。

## 事件狀態

| 狀態 | 列表中的標籤 | 含義 |
|---|---|---|
| `open` | **等待確認** | 正在觸發，還沒有人確認，升級繼續進行。 |
| `acknowledged` | **處理中** | 已有人接手，升級停止。 |
| `resolved` | **已恢復** | 已結束：規則已恢復，或有人解決了它。 |
| `closed` | **已關閉** | 已結束。 |

規則滿足[恢復條件](/zh-Hant/alerting/rules#復原條件與無資料處理)時，開啟的事件會自動解決；外部來源回報恢復時，它的事件也會解決，已確認的一起解決，見[外部警示如何變成事件](/zh-Hant/alerting/sources#外部警報如何變成事件)。已確認的事件保持已確認，直到有人解決它；升級策略設了[確認後仍未解決](/zh-Hant/alerting/on-call#確認後仍未解決)時，超過這個時間會退回 **等待確認** 並重新通知。暫緩中的事件是 **處理中**。每條規則（或依維度拆分的規則的每一組）同一時間最多只有一個活動事件。

## 事件列表

**警示事件** 頁面頂部統計受影響的服務數、等待確認的事件數，以及最近 24 小時恢復的事件數。摘要說明目前有多少事件在觸發、最早的一個已持續多久，以及正在評估多少條規則。**最近恢復** 列出最近結束的事件。

在 **觸發中** 與 **等待確認**（尚無人接手的事件）之間切換；目前使用者屬於某個團隊時還有 **我的團隊**，只列出[分派](/zh-Hant/alerting/routing)給這些團隊的事件。右側可以依優先順序篩選，或只看 **不設定** 優先順序的。事件依嚴重程度排序，同樣嚴重的依優先順序、再依開始的早晚。每一行顯示級別、事件及其服務（低緊急程度的事件在這裡標出 **低緊急程度**）、優先順序、狀態、持續時間，以及負責人和分派到的團隊，並提供三個操作：

| 操作 | 效果 |
|---|---|
| **確認** | 接手事件。事件變為 **處理中**，升級停止。 |
| **靜默** | 只暫停這個事件的後續通知與升級。參見[靜默單一事件](/zh-Hant/alerting/silences#靜默單一事件)。 |
| **Runbook** | 開啟規則的處理指南（如果有）。 |

勾選幾行（表頭的勾選框全選）後，列表上方出現批次處理列：**確認**、**解決**、**暫緩**、**轉派**、**調整**（嚴重程度、優先順序或緊急程度），選取兩個以上時還有 **合併**，在彈出的對話方塊裡選出要保留的主事件。一次最多處理 100 個事件；有處理不了的（例如已經恢復）時，提示失敗的數量和第一個原因，其餘照常處理。

### 新增事件

規則沒抓到的問題，例如客戶回報問題、有人發現的異常，也可以開一個事件，照常通知和升級。點選列表上方的 **新增事件**（需要 `alerts.incidents.create`）：

1. 在 **發生了什麼事** 中填寫 **標題**（必填）和 **說明**（支援 Markdown），選 **嚴重程度**（預設錯誤）、**優先順序** 和 **緊急程度**（預設依升級策略），需要時填 **受影響的服務**（逗號分開）和 **標籤**（每行一個 `key=value`）。
2. 在 **交給誰** 中選一種：

   | 選項 | 效果 |
   |---|---|
   | **依路由分派** | 和規則開的事件一樣依[警示路由](/zh-Hant/alerting/routing)分派。 |
   | **交給團隊** | 用團隊的值班策略，未設定時用預設策略。 |
   | **交由升級策略處理** | 從這條策略的第 1 級開始通知。 |
   | **指定成員** | 直接通知最多 10 個人，不用升級策略。 |

3. 需要時勾選 **同時宣告為重大事件**，然後點選 **建立事件**，頁面跳到事件詳情。

手動建立的事件帶有標籤 `alert.source=manual`，註解 `created_by` 記建立人，說明記在註解 `description`；它不經過警示流水線，每次都是新事件，不和別的事件去重，也不會自動恢復，要人來解決。詳情頁首的 **手動建立** 顯示建立人，洞察裡這類事件歸成一項 **手動建立**。Mole Agent 的 `create_incident` 工具也能建立事件（需一人審批）。

## 事件詳情

點選事件即可開啟詳情。頁首顯示狀態、觸發時間、規則和已持續時間，並提供 **確認**、**解決** 和 **更多操作**：**更多操作** 裡是[處理事件](#處理事件)的各項操作和 **靜默**。

| 分區 | 內容 |
|---|---|
| **時間軸** | 何時觸發、通知了誰、誰做了什麼（確認、轉派、增派、升級、暫緩、改嚴重程度、合併、解決，以及修復動作、工單和重大事件的各步驟）、[警示流水線](/zh-Hant/pipelines/alert-events#處理結果)在開啟事件之前改了什麼，在哪裡做的（介面、IM、回覆簡訊、電話按鍵、Mole Agent），以及其間經過的時間。底部可以新增[備註](#備註)，下方列出併入這裡的事件。 |
| **調查** | **開啟觸發查詢** 在探索頁中重放當時的精確查詢。**相關日誌** 和 **相關指標** 在同一時間範圍開啟受影響的上下文。RUM 指標的事件還有 **在 RUM 中開啟**。 |
| **排查線索** | 規則的[排查線索](/zh-Hant/alerting/rules#排查線索)：排查步驟、依事件的時間段開啟的排查查詢，以及相關儀表板。規則沒有排查線索時不顯示。 |
| **AI 根因** | Mole Agent 的分析。參見 [AI 根因](#ai-根因)。 |
| **跨訊號參照** | 證據中出現的服務、Trace ID 和主機，均可點選跳轉。 |
| **觸發查詢** | 查詢及其傳回的值。**展開樣本值** 顯示樣本行。 |
| **中繼資料** | 事件的標籤與註解。 |
| **負責人** | 升級通知到的人員，以及[分派](/zh-Hant/alerting/routing#事件的分派結果)到的團隊和依據；事件暫緩、併入了別的事件或嚴重程度由人設定時，在這裡註明。 |
| **影響範圍** | 關聯到某個服務的事件，顯示該服務沿服務地圖影響到的範圍。參見[事件的影響範圍](/zh-Hant/apm/insights#事件的影響範圍)。 |
| **業務影響** | 對每個[業務鍵](/zh-Hant/business-context)，列出事件觸發前後送往事件相關服務的請求中失敗最多的取值（租戶、方案），並標出重點取值；每個取值可以在 Trace 頁面開啟它的請求。只對有 `streams.query` 或 `sys.telemetry.read` 的讀者顯示。 |
| **工作階段樣本** | RUM 指標的事件，列出體現問題的工作階段，每個都有重播。參見 [RUM 警示](/zh-Hant/rum/alerts#事件)。 |
| **相似事件** | 近 90 天裡像它的事件，以及當時怎麼結束的。參見[相似事件與最近變更](#相似事件與最近變更)。 |
| **最近變更** | 觸發前後它的服務和下游服務上報的部署、設定和開關變更，以及前一天改過的這條規則。 |
| **修復動作** | 適用於這個事件的修復動作，以及發起過的執行和審批。參見[修復動作](/zh-Hant/alerting/remediation)。 |
| **工單** | 事件在 Jira、ServiceNow 或飛書專案裡的工單和它們的狀態，可以在這裡建立工單。參見[工單](/zh-Hant/alerting/tickets)。 |
| **重大事件** | 宣告重大事件，指派角色，進入作戰室和會議，依任務分工，發布進展。參見[重大事件與事後檢討](/zh-Hant/alerting/major-incidents)。 |
| **事後檢討** | 事件的內部事後檢討：**撰寫事後檢討** 依範本起草，**開啟事後檢討** 繼續寫。參見[事後檢討](/zh-Hant/alerting/major-incidents#事後檢討)。 |

## 處理事件

**更多操作** 裡的操作都記在時間軸上，也能透過 [API](#事件-api) 完成。Mole Agent 也能做這些操作：新增備註需提問的人確認，其餘需一人審批，見[審批與執行](/zh-Hant/agent#核准與執行)。Mole Agent 還能建立工單、指派重大事件的角色、新增任務和起草事後檢討（需提問的人確認），宣告重大事件和發布進展（需一人審批），以及提議執行修復動作（需兩人審批，[預先核准](/zh-Hant/alerting/remediation#預先核准)涵蓋的除外）。已恢復的事件和併入別處的事件不能再這樣處理，但仍可以[新增備註](#備註)。

| 操作 | 效果 |
|---|---|
| **轉派** | 轉給成員（最多 10 個）：他們成為負責人並收到通知，事件回到 **等待確認**，仍沒人確認時照常往下升級。轉給團隊：改用這個團隊的值班策略，團隊未設定時用預設策略，從第 1 級重新開始。轉給升級策略：改用這條策略從第 1 級重新開始，團隊不變。可以附一條備註，記在時間軸上。 |
| **增派** | 選取的人加入負責人並收到通知，事件狀態不變。 |
| **立即升級** | 選一級，立即通知這一級的目標，預設是下一級；只列出適用於事件嚴重程度的級別。已確認的事件退回 **等待確認**。 |
| **暫緩** | 1、4、8 或 24 小時，或 **自訂…**（1 分鐘到 7 天）。等待確認的事件先被確認；暫緩期間不發通知，到期後事件退回 **等待確認**，負責人重新收到通知。**取消暫緩** 立即結束。 |
| **嚴重程度** | 手動設定後，規則、警示來源和撥測檢查都不再變更它。調高等待確認的事件時，依新的嚴重程度從第 1 級重新通知；調低只變更嚴重程度。 |
| **優先順序** | 組織的[優先順序等級](/zh-Hant/alerting/on-call#緊急度與優先順序等級)之一，預設 P1 到 P5，或 **不設定**。只變更優先順序，不重新通知。優先順序用於列表的欄位和篩選、[路由規則](/zh-Hant/alerting/routing)的條件、重大事件的自動宣告、工單的優先順序對應和洞察的拆分裡。 |
| **緊急程度** | **高緊急程度** 或 **低緊急程度**，見[緊急程度](/zh-Hant/alerting/on-call#緊急程度)。從低調高時，等待確認的事件從第 1 級重新通知；調低只變更緊急程度，之後不再往下升。手動改過以後，支援時段不再變更它。 |
| **合併** | 把其他進行中的事件併入這個事件，見[合併事件](#合併事件)。 |
| **靜默** | 見[靜默單一事件](/zh-Hant/alerting/silences#靜默單一事件)。 |

這些操作發出的通知是升級通知，範本裡的 `{{escalation.reason}}` 說明原因：`reassigned`（轉派）、`responder_added`（增派）、`manual`（立即升級）、`snooze_ended`（暫緩到期）、`severity_raised`（調高嚴重程度）、`urgency_raised`（緊急程度升為高），或 `ack_timeout`（確認後逾時未解決）。範本還能用 `{{urgency}}` 和 `{{priority}}`。見[範本變數](/zh-Hant/notification-channels#範本變數)。

### 合併事件

同一個問題開出了幾個事件時（例如一次故障讓幾條規則都觸發），把它們併入一個主事件：併入的事件不再單獨通知和升級，也不再出現在事件列表和洞察中，而是列在主事件時間軸的下方。主事件解決時，併入的事件一併解決；併入的事件先自己恢復時，主事件的時間軸記一筆。一次最多併入 50 個事件，合併後不能拆開。

在詳情頁的 **更多操作 → 合併** 裡勾選要併入的事件；在事件列表裡勾選幾個後點選 **合併**，再選出主事件。

### 備註

時間軸底部的輸入框新增備註，最多 4000 字，記下發現了什麼、做了什麼，接手的人一眼能看到。轉派時附的備註也記在這裡。Mole Agent 讀取事件時會帶上最近的幾條備註。

## AI 根因

為 Mole Agent 設定模型服務後，它會在背景分析新事件，並把有證據支持的結果儲存到事件中。**產生** 立即請求一次分析，**重新產生** 取代已有結果。可以用 **有幫助** 或 **沒有幫助** 評價結果，評價會進入[品質](/zh-Hant/quality)。

分析依據帶編號的證據寫成。證據依事件涉及的服務及其下游服務讀取，時間從事件開始前 30 分鐘到開始後 10 分鐘：

| 證據 | 內容 |
|---|---|
| **APM 洞察** | 和前一段、上週同期相比有突變的指標、回歸的版本，或耗時集中的地方。 |
| **新錯誤群組** | 這段時間裡首次出現的錯誤群組及其次數。 |
| **Trace 樣本** | APM 留作樣本的 Trace 中最慢的幾條及其耗時。 |
| **錯誤日誌** | 服務的錯誤層級日誌行數，以及上週同一時段的行數。 |
| **新出現的錯誤日誌模式** | 事件相關服務的錯誤層級日誌中、之前同樣長的一段沒有出現過的訊息模式，以及它在這段時間內的行數；最多 3 條。 |
| **失敗請求的差異欄位** | 失敗請求與其他請求取值分布明顯不同的欄位，以及失敗請求集中的取值和它在兩組中的占比；基於取樣，最多 3 條。 |
| **業務影響** | 每個業務鍵裡有失敗請求的取值及失敗數，重點取值排在前面。 |
| **變更** | 上報的部署、設定變更或 Feature Flag 變更，或警示規則被修改。 |
| **相似事件** | 和這個事件相似的歷史事件。 |

分析在每個論斷後標註證據編號，例如 **[E2]**，沒有證據支持的原因標為推測。分析下方的**證據**列出每條證據，點選可開啟它的來源。來自 APM、Trace 或日誌的數字只對能讀取這些資料的人顯示，其他人只看到證據是關於什麼的，以及**數字已隱藏**。從 Mole Agent 調查寫回的分析列出調查引用的證據。

產生需要 Mole Agent 權限。組織當天的 Mole Agent token 預算用完後，自動分析會暫停，手動產生依預算設定處理。參見[用量與預算](/zh-Hant/agent#用量與預算)。

## 相似事件與最近變更

**相似事件** 在同一組織近 90 天的事件裡找出最像這個事件的，最多 5 個，並註明像在哪裡：**相同警示**（同一指紋）、**相同規則**、**相同服務**、**標籤相似**、**標題相似**（中文標題相同也能比）或 **同一團隊**。每個都顯示持續了多久、誰解決的、有幾條備註，以及 AI 根因的第一句，接手的人能先看看上次是怎麼處理的。

**最近變更** 列出觸發前 30 分鐘到觸發後 10 分鐘之間，事件的服務和它在服務地圖上的下游服務[上報的變更](/zh-Hant/apm/deployments#從-ci-回報發佈)：部署（失敗或回滾的會標出）、設定和開關，標明是不是下游的，有流水線連結的可以點開。事件的規則在觸發前一天裡改過時也列出來。沒有服務地圖時只看事件自己的服務。

## 事件分組

[語意分組](/zh-Hant/alerting/silences#語意分組)把相關事件（例如某個服務的所有嚴重事件）收成一組。用 `POST /api/v1/alerts/incident_groups/{id}/ack` 或 `/resolve` 確認或解決分組時，組內每個事件都會同樣處理。

## 歷史紀錄

**警示 → 歷史紀錄** 列出過去的事件，包括目前狀態、觸發和恢復時間以及持續時間。可以依事件名稱、服務或事件 ID 搜尋，並依級別和狀態篩選。

## 變更

**警示 → 變更** 依時間從新到舊列出最近 24 小時、7 天或 30 天的所有變更：流水線上報的發布、設定變更、功能開關、擴縮容和基礎設施變更，以及註解、APM 從 Span 中首次看到的版本和警示規則修改。每種類型依你的權限顯示。列表上方的標記條在時間軸上標出這些變更，滑鼠懸停可以看到誰改了什麼，以及提交、合併請求和 CI 執行。可以依類型篩選，依服務、版本、標題、作者或提交搜尋。同樣的變更也標記在日誌和 Trace 的直方圖上、指標圖表下方。參見 [`GET /api/v1/changes`](/zh-Hant/api/changes)。

## 洞察

**警示 → 洞察** 展示工作區在最近 24 小時、7 天或 30 天內的應變情況：

| 部分 | 顯示內容 |
|---|---|
| 摘要 | 仍需處理的事件數、已恢復事件的 **平均恢復時間**，以及 **快速恢復的事件**：60 秒內恢復的佔比，是規則雜訊較大的訊號。 |
| **事件時間趨勢** | 24 小時內依小時、更長範圍依天統計的事件數，使用瀏覽器時區，並標出峰值。 |
| **主要受影響的服務** | 事件中出現最多的服務。規則需要帶 `service` 標籤。 |
| **主要觸發規則** | 開啟事件最多的規則，調校應從這裡開始。 |
| **應變** | 平均接手時間（P50、P90）、恢復時間中位數、升級率和有人接手的比例，與前一段同樣長的時間相比；各級確認率；第一次接手是在哪裡完成的（網頁、介面、IM 卡片、回覆簡訊、電話按鍵或 Mole Agent）；以及依團隊、服務、個人和優先順序拆分的接手、恢復和升級（未設定優先順序的事件不計入優先順序）。第一次接手是第一次確認；沒有人確認、而是由其他人解決的，計在解決的那一刻。 |
| **值班負擔** | 每個人值了多久的班、收到幾次警示通知，其中幾次在夜裡（依各自排班的時區 22:00 到次日 08:00）、幾次在週末，被吵醒幾個晚上，以及先接手的事件數和平均接手時間。排班詳情也會顯示這位排班成員的負擔。 |
