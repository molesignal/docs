規則說明什麼不該發生。MoleSignal 會依間隔評估規則，條件成立時開啟[事件](/zh-Hant/alerting/incidents)。開啟 **警示 → 規則**。讀取規則需要 `alerts.rules.read`，建立或修改規則需要 `alerts.rules.manage`。

## 規則類型

| 類型 | 評估對象 | 建立位置 |
|---|---|---|
| **閾值規則** | SQL 或 PromQL 查詢、[APM 指標](/zh-Hant/apm#依-apm-指標警示)或 [RUM 指標](/zh-Hant/rum/alerts)，依間隔與固定閾值比較。 | 規則工作台。 |
| **預測規則** | 查詢、APM 指標或 RUM 指標的走勢，預測在預測時長內越過閾值就觸發。參見[預測規則](#預測規則)。 | 規則工作台的 **判定方式**。 |
| **離群規則** | 依維度分組的查詢，各組相互比較，明顯偏離其餘組的組別會觸發。參見[離群規則](#離群規則)。 | 規則工作台的 **判定方式**。 |
| **組合規則** | 其他規則是否有進行中的事件，並以 AND、OR、NOT 組合。參見[組合規則](#組合規則)。 | 規則工作台的 **判定方式**。 |
| **心跳規則** | 排程工作、備份指令碼這類作業是否準時打卡。參見[心跳規則](#心跳規則)。 | 規則工作台的 **判定方式**。 |
| **異常偵測** | 查詢、APM 指標或 RUM 指標，與根據其歷史學到的基準線比較。 | 異常規則編輯器。 |
| **即時規則** | 在接入路徑上對到達的記錄計數。 | 僅限 API。參見[即時規則](#即時規則)。 |

## 規則列表

**規則** 列出每條規則的資料來源、觸發條件、狀態和最近評估時間。可以依規則、服務或資料來源搜尋，並在 **全部**、**已啟用** 和 **已停用** 之間切換。

| 狀態 | 含義 |
|---|---|
| **尚未評估** | 規則還沒有執行過。 |
| **正常** | 最近一次評估沒有滿足條件。 |
| **等待達到持續時間** | 條件已成立，但持續時間還不夠。 |
| **觸發中** | 規則有開啟的事件。 |
| **已由處理管線捨棄** | 規則已觸發，但要開啟的事件被[警示處理管線](/zh-Hant/pipelines/alert-events#處理結果)捨棄了。 |
| **已停用** | 規則儲存為草稿，不會執行。 |

點擊規則，或點擊列中的 **編輯**，即可開啟規則。

## 建立閾值規則

點擊 **新增規則 → 閾值規則** 開啟規則工作台。

<Steps>
  <Step title="選擇規則類型">
    選擇 **指標告警**、**日誌告警**、**追蹤告警**、**APM 告警** 或 **RUM 告警**。**快速開始** 中的預設會填入典型查詢，例如 **錯誤率過高**、**P95 延遲過高**、**錯誤日誌激增** 或 **無資料警報**。APM 告警和 RUM 告警會選擇服務或應用程式以及一項指標，而不是寫查詢；參見[依 APM 指標告警](/zh-Hant/apm#依-apm-指標警示)與 [RUM 告警](/zh-Hant/rum/alerts)。
  </Step>
  <Step title="填寫基本資訊">
    **規則名稱** 用作事件標題，例如 `api_high_error_rate`。**服務** 會把規則關聯到某個服務，用於歸屬和跨訊號上下文。**說明** 描述規則保護的內容。
  </Step>
  <Step title="選擇判定方式">
    在 **查詢與觸發條件** 頂部選擇 **判定方式**：**閾值**（預設）、[**預測**](#預測規則)、[**離群**](#離群規則)、[**組合**](#組合規則)或[**心跳**](#心跳規則)。組合和心跳不寫查詢，下方的查詢、測試和閾值會換成各自的設定。
  </Step>
  <Step title="撰寫查詢">
    設定 **目標資料流**、**評估間隔**（每 1、5 或 10 分鐘）、**查詢語言**（指標用 **PromQL**，其他用 **SQL**）和 **查詢**。查詢要傳回一個數值：評估器會讀取第一列的第一欄。可以視需要填寫[**依維度分組**](#依維度分組)。規則不能讀取 [`_audit` 資料串流](/zh-Hant/settings/data-security#稽核資料流)，儲存時會傳回 `400`。
  </Step>
  <Step title="設定觸發條件">
    每一列是一個嚴重度：**當結果** 以運算子與 **閾值** 比較，**並持續** 若干分鐘。**新增等級** 可以再加一列。命中的最高嚴重度生效，高嚴重度不能比低嚴重度更容易命中。分鐘數會換算為評估次數。在下方設定 [**復原條件** 和 **沒有資料時**](#復原條件與沒有資料)。
  </Step>
  <Step title="新增處理指南">
    在 **Notify 與處理** 中填寫 **處理指南 / Runbook URL**，事件處理人員可以從事件列表直接開啟。通知對象由[升級策略](/zh-Hant/alerting/on-call#升級策略)和[通知策略](/zh-Hant/notification-channels#建立範本和策略)決定，而不是由規則決定。
  </Step>
  <Step title="新增排查線索">
    可以在 **排查線索** 裡寫下 **排查步驟**、新增 **排查查詢**、選擇 **相關儀表板**，說明有人排查這條規則的事件時先做什麼。參見[排查線索](#排查線索)。
  </Step>
  <Step title="測試規則">
    點擊 **測試規則**。查詢會在最近 6 小時的真實資料上執行，**查詢預覽** 會繪製結果，並顯示閾值線、目前值、預計觸發次數、掃描列數和耗時。依維度分組的規則會顯示分成多少組。
  </Step>
  <Step title="儲存">
    **建立前檢查** 必須全部通過：已填寫名稱、目前查詢測試成功、閾值有效、Runbook URL 有效。然後點擊 **儲存並啟用**，或點擊 **儲存草稿** 只儲存不執行。
  </Step>
</Steps>

在規則工作台中建立的規則不會指定升級策略，事件由[警示路由](/zh-Hant/alerting/routing)分派，路由無法決定時會使用名為 `default` 的升級策略。組織中沒有這條策略時，這類事件不會升級給任何人，請先建立它。參見[預設策略](/zh-Hant/alerting/on-call#預設策略)。

## 依維度分組

以 SQL 或 PromQL 查詢為基礎的定時規則可以依結果中的欄位分組，例如依主機或服務。在規則工作台填寫**依維度分組**，或在[建立規則](/zh-Hant/api/alerting/create-rule#依欄位分組的規則)時設定 `query.group_by`。之後每組取值都像一條獨立的規則。

| 部分 | 行為 |
|---|---|
| 組別 | 這些欄位取值相同的列。欄位名稱與結果的欄位名稱比對時不區分大小寫。 |
| 值 | 組內第一列提供值：除了這些欄位和時間欄位以外的第一個數值欄位。 |
| 觸發條件 | 每組各自與觸發條件或各級閾值比較，各自累計 `for_periods`。 |
| 事件 | 每組會開啟自己的事件，標籤和標題會帶上這一組的取值，例如 `Errors per host · web-1`。這一組滿足復原條件時，事件會被解決。不在結果裡的組別算作沒有值，並依規則的沒有資料處理方式處理。 |
| 上限 | 最多 8 欄，每輪最多 100 組。超過 100 組時其餘組別這一輪不評估，結果裡沒有的組別這一輪也會保留其事件。 |

每組傳回一列，最嚴重的排在前面：

```sql
SELECT host, count(*) AS errors
FROM app_logs
WHERE level = 'error'
GROUP BY host
ORDER BY errors DESC
```

在 PromQL 裡，序列的標籤就是它的欄位，因此 `sum by (instance) (rate(http_requests_total{status=~"5.."}[5m]))` 會依 `instance` 分組。結果有列卻沒有這個名稱的欄位時，這一輪評估會失敗，什麼都不會改變。在規則工作台測試查詢時會檢查這些欄位。APM、RUM、即時與異常規則不能分組；[離群規則](#離群規則)必須分組。

## 復原條件與沒有資料

每條規則都要說清楚開啟的事件何時復原，以及一次評估沒有值時算作什麼。在規則工作台的**復原條件**和**沒有資料時**裡設定，或在[建立規則](/zh-Hant/api/alerting/create-rule#恢復條件與無資料)時設定 `trigger.recovery` 和 `trigger.no_data`。

- **復原閾值：**開啟的事件要等值越過這條線才復原，例如高於 90 觸發的規則要低於 80 才復原。數值在閾值附近來回時，不會再反覆觸發、反覆復原。
- **復原持續時間：**值要在健康的一側維持這麼久，事件才復原。
- **沒有資料時：**查詢沒有傳回值，或依維度分組的規則裡某一組不在結果裡。

| 處理方式 | 結果 |
|---|---|
| 當作復原 | 這次評估算作不命中，開啟的事件會復原。預設選項。 |
| 保持原狀態 | 什麼都不變，規則會顯示**無資料**。異常規則的預設選項。 |
| 開啟無資料事件 | 保持原狀態，沒有資料持續夠了時間就開啟一個標示為**無資料**的事件，通知標題為 `NO DATA · <标题>`。資料回來時它會自動解決。主機或服務確實離線時請手動解決它：資料回來之前不會再開啟。 |
| 以 0 計算 | 把缺少的值當作 0 比較，適合計數。 |

即時規則不能設定這兩項：計數一回落就復原。

## 異常規則

異常規則會在數值偏離其歷史所預測的範圍時觸發，因此不需要固定閾值。點擊 **新增規則 → 異常偵測規則**。

| 分組 | 欄位 | 規則 |
|---|---|---|
| 識別 | **規則名稱**、**層級**、**服務** | 服務為選填，用於提供跨訊號上下文。 |
| 偵測查詢 | **資料來源** | **查詢**、某個服務或端點的 **APM 指標**，或某個應用程式的 **RUM 指標**。參見[對 APM 指標設定異常偵測警示](/zh-Hant/apm/insights#對-apm-指標設定異常偵測警示)與 [RUM 異常規則](/zh-Hant/rum/alerts#異常規則)。 |
| | **資料串流**、**資料串流類型**、**查詢語言**、**查詢** | 傳回單一數值的查詢，例如平均值、P95 或計數。 |
| | **評估時段** | 1、5 或 15 分鐘，或 1 小時。 |
| 偵測器 | **演算法** | **MAD**（穩健中位數）或 **EWMA**（追蹤近期漂移）。 |
| | **回溯天數** | 同一時段 1 到 30 天的歷史，預設 7 天。 |
| | **靈敏度（k·σ）** | 與基準線的距離超過 k 倍離散度時觸發。數值越大越不敏感，預設 3。 |
| | **平滑係數（α）** | 僅 EWMA，取值 `(0, 1]`。數值越大越看重近期樣本。 |
| | **觸發所需的連續週期數** | 開啟事件前需要連續異常的評估次數。 |
| | **每週季節性** | 只與相同星期幾的歷史比較，避免工作日與週末之間的誤報。需要至少 7 天回溯，28 天以上效果最好。 |

## 預測規則

預測規則會依指標過去的走勢往後推算，預測在預測時長內越過閾值就觸發，適合磁碟、配額、連線數這類慢慢逼近上限的指標。在 **判定方式** 裡選 **預測**，像閾值規則一樣寫查詢，再設定：

| 設定 | 說明 |
|---|---|
| **預測** | 運算子和閾值，例如預測 `> 90`。 |
| **預測時長** | 預測在多久之內越線就觸發：1、6、12 小時，或 1、2、3、7 天，預設 1 天。 |
| **回溯期間** | 用過去幾天的走勢來推算：1、3、7、14 或 30 天，預設 7 天。 |
| **外推方式** | **線性趨勢**；**每日規律** 或 **每週規律**：在一天或一週前同一時刻的值上加上趨勢，適合有日、週起伏的指標。按週要回溯至少 7 天。 |

規則每輪會把目前值記進一條序列；剛建好或改了查詢時，會先查一批過去的時刻補上歷史點。點不夠時（不到 6 個，或按天、按週還不滿一個週期）這一輪不下結論。事件會註明預測越線的時刻和那時的值。預測規則只有一個嚴重度和持續分鐘，沒有復原閾值，可以設定[沒有資料時](#復原條件與沒有資料)。

## 離群規則

離群規則不會和固定閾值比較，而是讓依維度分組出的各組相互比較：例如依主機分組錯誤數時，某台主機的錯誤明顯多於其餘主機就觸發，整體一起升高則不觸發。在 **判定方式** 裡選 **離群**，寫好查詢並填寫[**依維度分組**](#依維度分組)，再設定：

| 設定 | 說明 |
|---|---|
| **容差** | 偏離多少個尺度算離群，0.5 到 10，預設 3。越小越敏感。 |
| **判斷方向** | **偏高或偏低**、**只看偏高** 或 **只看偏低**。 |

偏離程度會依各組的中位數和中位數絕對偏差（MAD）計算，各組幾乎一樣時也不會把小波動當成離群。離群的組會各開啟一個事件，事件會註明偏離程度；有值的組少於 3 個時這一輪不判斷。離群規則不能用 APM 和 RUM 指標，只有一個嚴重度和持續分鐘。

## 組合規則

組合規則會把幾條規則合起來看：被組合的規則有進行中的事件就算成立，再用運算式組合。例如 `A && B` 在錯誤率和延遲同時觸發警示時才通知，`A && !B` 在下游正常時才算上游的問題。在 **判定方式** 裡選 **組合**：

| 設定 | 說明 |
|---|---|
| **規則** | 選最多 10 條規則，依次記為 A、B、C…… |
| **運算式** | 用字母和 `&&`（AND）、`\|\|`（OR）、`!`（NOT）、括號組合，例如 `A && (B \|\| C)`。 |
| **將這些規則的事件納入組合規則的事件** | 組合規則開啟事件以後，被組合的規則進行中的事件會[併入](/zh-Hant/alerting/incidents#合併事件)它，不再單獨通知；之後新開啟的也會併進來。 |

組合規則不執行查詢，不能測試，也沒有[沒有資料時](#復原條件與沒有資料)。被組合的規則不能是組合規則，組合規則也不能被其他組合規則組合；被組合的規則刪除後算不成立。事件會註明當時哪些字母成立。

## 心跳規則

心跳規則反過來等作業回報：排程工作、備份指令碼、批次處理每次執行完會請求一次打卡網址，過了週期加寬限時間還沒打卡，或打卡回報失敗，規則就會觸發。在 **判定方式** 裡選 **心跳**：

| 設定 | 說明 |
|---|---|
| **打卡週期** | 作業多久執行一次，1 分鐘到 7 天，預設 60 分鐘。 |
| **寬限時間** | 過了週期再等多久才算沒打卡，最多 1 天，預設 5 分鐘。 |

儲存後會彈出打卡網址和 `curl` 範例，網址只顯示這一次。讓作業成功時請求它（`GET` 或 `POST`）；失敗時加上 `?status=fail`，規則會馬上觸發。`POST` 的請求主體開頭會作為這次打卡附帶的訊息記進事件，適合附上最後幾行日誌。

```bash
if ./backup.sh; then
  curl -fsS "$HEARTBEAT_URL"
else
  curl -fsS "$HEARTBEAT_URL?status=fail"
fi
```

編輯心跳規則時可以看到最後一次打卡和最晚的下一次打卡時間。**重設打卡網址** 會換一個新網址，舊網址馬上失效。打卡網址不用登入，靠網址裡的 Token，參見[公開存取](/zh-Hant/public-access)和[心跳打卡](/zh-Hant/api/alerting/heartbeats)。心跳規則不執行查詢，不能測試，也沒有[沒有資料時](#復原條件與沒有資料)。

## 即時規則

即時規則在接入路徑上執行，而不是依計時器執行。intake 節點接收的每筆記錄都會與所在資料串流的即時規則比對，比對結果進入長度為 `periodSecs` 秒的滑動視窗。負責這條規則的 alert 節點每秒向各個接收寫入的節點拉取一次視窗內的相符數並加總，加總達到觸發條件時開啟事件，不再符合條件時事件會解決，比記錄寫入最多晚 1 秒。

| 部分 | 行為 |
|---|---|
| 語句 | SQL 的 `SELECT count(*) FROM <stream> [WHERE <condition>]`。資料表名稱是規則的 `stream`。條件用欄位與字面值比較（`=`、`!=`、`<`、`<=`、`>`、`>=`），並支援 `IN`、`BETWEEN`、`LIKE`、`ILIKE` 與 `IS [NOT] NULL`，用 `AND`、`OR`、`NOT` 與括號連接。欄位的位置也可以寫 `json_text(<field>, '<key>')`，與查詢一樣把 JSON 欄位的一個鍵讀成文字：`json_text(body, 'type') LIKE 'Uncorrected%'`。缺少或為 null 的欄位在比較中永遠不會相符。 |
| 視窗 | `periodSecs` 取 1 到 3600。 |
| 觸發條件 | `operator` 為 `gt` 或 `gte`，`for_periods` 為 `0` 或 `1`。`thresholds` 中的各級距依計數決定嚴重度。 |
| 事件 | 事件遵循一般的生命週期：每條規則只有一個進行中的事件、`silence_secs` 冷卻、升級與通知。 |

[建立規則](/zh-Hant/api/alerting/create-rule)會以 `400` 拒絕超出上述限制的即時規則。計數儲存在每個接收寫入的節點記憶體中，每個節點每 5 秒把視窗存一份快照到中繼資料庫。節點重新啟動時會讀回自己的快照，最多遺失最後 5 秒的計數。節點停止或沒有回應時，負責彙總的 alert 節點會用最近的快照頂替，直到這些計數超出視窗。負責彙總的節點更換時不會遺失，接手的節點會依進行中的事件接續已觸發的狀態。叢集裡各節點之間拉取計數要設定叢集 bearer（`MS_SELF_TELEMETRY_CLUSTER_TOKEN`，與角色分離部署共用），沒設定時其他節點只能靠快照。

### 聯邦中的即時規則

在[跨叢集聯邦](/zh-Hant/settings/data-plane#跨叢集聯邦)裡，每個叢集各自統計寫入自己的記錄，預設各叢集依自己的計數判斷。要把各叢集加總起來，就指定彙總叢集：API 裡的 `query.home_cluster`，或在規則工作台開啟這條規則時的 **彙總叢集**（可選本叢集和已啟用的遠端叢集）。只有彙總叢集會開啟、解決這條規則的事件：它負責這條規則的 alert 節點每秒會用組織的 per-org token，向對應到此組織的各叢集要求計數，加上自己的計數後再判斷，其他叢集只負責計數。800 毫秒內沒有回應的叢集，依它上一次回應的計數計算，最多 30 秒，之後以 0 計算；偶爾一秒沒回應不會讓事件解決；指標 `realtime_federated_counts_failed_total{cluster}` 會記下次數。規則會隨聯邦同步、id 不變，每個叢集都依它計數。

## 評估延遲

角色分離叢集裡，查詢只讀取 intake 已經刷寫的資料，intake 緩衝裡的記錄最多要等 `[intake].flush_interval_secs`（預設 30 秒）才看得到，所以最近一個視窗的數值會偏低。規則工作台 **進階** 裡的 **評估延遲** 會把每一輪的視窗整體往回位移：設 5 分鐘、週期 5 分鐘時，07:00 評估的是 06:50 到 06:55 的資料。

| 取值 | 效果 |
|---|---|
| **自動**（預設） | 以單一程序執行全部角色的單機不位移；角色分離叢集依 **設定 → 警示評估** 的 **評估延遲**，預設 60 秒。 |
| **不延遲** | 看到目前為止。 |
| 30 秒到 1 小時 | 依這條規則自己的延遲。API 可以設 0 到 3600 秒（`query.delay_secs`）。 |

無資料判定、恢復條件、異常偵測的基準、預測規則的序列、依維度拆分和離群都依同一個延遲往回位移。位移過視窗時，開啟的事件會在註解 `evaluated_window` 裡記下這一輪查看的區間。即時規則不評估查詢，沒有評估延遲。

## 優先順序與緊急程度

規則工作台 **Notify 與處理** 裡的 **優先順序** 和 **緊急程度** 決定這條規則開啟的事件：

- **優先順序**：組織的[優先順序檔位](/zh-Hant/alerting/on-call#緊急度與優先順序等級)之一，預設 P1 到 P5，P1 最重，未設定時事件沒有優先順序（[警示流水線](/zh-Hant/pipelines)還可以設定）。優先順序不會從嚴重度推導。
- **緊急程度**：**依升級策略**（預設）時，依事件所套用的[升級策略的緊急程度](/zh-Hant/alerting/on-call#緊急程度)決定；選了高或低就始終是這個等級。

## 排查線索

規則工作台的 **排查線索** 說明有人排查這條規則的事件時要先做什麼。每個部分都可以不填：

| 部分 | 內容 | 上限 |
|---|---|---|
| **排查步驟** | Markdown：先查什麼、依什麼順序查。 | 8,000 個字元 |
| **排查查詢** | **名稱**、查詢語言（**promql** 或 **sql**）、SQL 查詢的 **資料串流** 和 **資料類型**，以及 **查詢陳述式**。 | 10 條，每條最多 4,000 個字元 |
| **相關儀表板** | 從事件開啟的儀表板。 | 5 個 |

這條規則的每個事件都會在 **排查線索** 裡顯示它：排查步驟依格式顯示；每條查詢是一個連結，依事件的時間範圍開啟指標（PromQL）、追蹤（讀取追蹤資料串流的 SQL）或日誌（其他 SQL）；每個儀表板也是一個連結。[Mole Agent](/zh-Hant/agent) 調查事件前會先讀取排查線索並先執行其中的查詢，事件的 [AI 根因](/zh-Hant/alerting/incidents#ai-根因)也會參考它。

透過 API 設定時，排查線索是規則的 `guide` 欄位，參見[建立規則](/zh-Hant/api/alerting/create-rule#排查線索)。匯出會帶上排查線索；匯入時，組織裡沒有的儀表板會被移除。

## 自動探索規則

[自動探索](/zh-Hant/alerting/discovery)找到的問題只會進入清單。要通知，在 **警示 → 自動探索** 點擊 **建立自動發現規則**，或在一筆發現上點擊 **為這類發現建立規則**：選取發現的種類、服務或應用程式、環境和最低嚴重度，以及升級策略和緊急程度。命中的每筆發現各開啟一個事件，嚴重度就是發現的嚴重度，未設定緊急程度時依低緊急程度；發現結束時，事件就會恢復。規則清單裡這類規則的來源是 **自動探索**，開啟時會回到自動探索頁面編輯。

## 匯入與匯出

規則清單的 **匯入與匯出** 會把規則存成檔案，或從檔案匯入：

- **匯出所有規則**，或篩選後 **匯出這 N 條規則**：下載一個 JSON 規則包（`"format": "molesignal.alert-rules/v1"`）。規則會帶上全部定義，但不帶 id、組織、評估狀態和時間；升級策略和組合規則的子規則依名稱參照，所以同一個包能搬到其他工作區或叢集。心跳規則的打卡位址不在包裡，匯入後在規則上重設。
- **匯入規則…**：貼上或選擇規則包，或 Prometheus 的警示規則檔案（也支援 Prometheus Operator 的 `PrometheusRule`），先點擊 **試跑**，查看每條規則會是 **新增**、**更新**（列出變更的欄位）、**未變更** 還是 **錯誤**，再點擊 **匯入 N 條**。規則依名稱比對：沒有同名規則就新增，正好一條就更新，同名規則有好幾條時會報錯，檔案裡同一個名稱出現兩次也會報錯（匯出時有同名規則的，先改名再匯入）。勾選 **只新增，不變更現有的同名規則** 時，現有規則會 **跳過**。有一條發生錯誤時，整包都不會寫入；沒有錯誤時會一次寫入，全部寫入或全部不寫。

Prometheus 規則這樣轉換成 MoleSignal 的規則：

| Prometheus | MoleSignal |
|---|---|
| `alert` | 規則名稱。同名的警示出現在幾個規則群組裡時，後面的名稱會帶上群組名稱。 |
| `expr` | PromQL 規則，陳述式是 `count(<expr>)`、條件是 `>= 1`：運算式傳回序列時就發出警示。註解或標籤裡用到 `{{ $labels.x }}` 時，陳述式是 `count by (x) (<expr>)`，並依 `x` [拆分](#依維度分組)，每組各開啟一個事件。資料串流取運算式裡第一個指標名稱。 |
| 規則群組的 `interval` | 週期，沒有時為 60 秒。 |
| `for` | 連續命中的週期數，向上取整。 |
| 標籤 `severity` | 嚴重度：`critical`、`page` 為嚴重，`error`、`high` 為錯誤，`warning`、`warn` 為警告，`info`、`low`、`none` 為提示；其餘標籤原樣帶上。 |
| `annotations` | 原樣帶上；說明取 `description` 或 `summary`。 |
| `record` | 記錄規則不匯入，會在試跑結果下方列出。 |
| `keep_firing_for` | 不支援，列在試跑結果下方。 |

匯入的規則會使用預設升級策略，需要時在匯入前改好規則包裡的 `escalation_policy`。Alertmanager 自己的設定檔（`alertmanager.yml` 的路由和接收器）不是規則，不能這樣匯入，請改用[警示路由](/zh-Hant/alerting/routing)和[通知策略](/zh-Hant/notification-channels)。

在 CI 裡可以使用 [CLI](/zh-Hant/cli) 的 `molesignal alerts rules export` 和 `molesignal alerts rules apply -f rules.json [--dry-run]`：試跑結果會列印成表格，有錯誤的規則時以 1 結束。

## 修改、暫停或刪除規則

開啟規則即可修改，修改後再次 **測試規則** 並儲存。**儲存草稿** 讓規則保持停用，**儲存並啟用** 重新啟用它。刪除規則請呼叫[刪除規則](/zh-Hant/api/alerting/delete-rule)。如果只想暫時遮蔽某條規則的通知而不修改它，請使用[靜默](/zh-Hant/alerting/silences)。

[警示規則 API](/zh-Hant/api/alerting/create-rule) 可以在指令碼中建立、測試和觸發規則。
