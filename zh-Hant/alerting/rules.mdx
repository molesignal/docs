規則說明什麼情況不該發生。MoleSignal 定期評估規則，條件成立時開啟[事件](/zh-Hant/alerting/incidents)。開啟 **警示 → 規則**。讀取規則需要 `alerts.rules.read`，建立或修改規則需要 `alerts.rules.manage`。

## 規則類型

| 類型 | 評估對象 | 建立位置 |
|---|---|---|
| **閾值規則** | 定期將 SQL 或 PromQL 查詢、[APM 指標](/zh-Hant/apm#依-apm-指標觸發警示)或 [RUM 指標](/zh-Hant/rum/alerts)的結果與固定閾值比較。 | 規則工作台。 |
| **預測規則** | 根據查詢、APM 指標或 RUM 指標的趨勢，預測在指定的預測時長內越過閾值時觸發。請參閱[預測規則](#預測規則)。 | 規則工作台的 **判定方式**。 |
| **離群規則** | 將查詢結果依維度分組，再比較各組。明顯偏離其他組的組別會觸發。請參閱[離群規則](#離群規則)。 | 規則工作台的 **判定方式**。 |
| **組合規則** | 檢查其他規則是否有進行中的事件，並用 AND、OR、NOT 組合條件。請參閱[組合規則](#組合規則)。 | 規則工作台的 **判定方式**。 |
| **心跳規則** | 檢查排程工作、備份指令碼等作業是否準時打卡。請參閱[心跳規則](#心跳規則)。 | 規則工作台的 **判定方式**。 |
| **異常偵測** | 將查詢、APM 指標或 RUM 指標的結果，與根據歷史資料學得的基準線比較。 | 異常規則編輯器。 |
| **即時規則** | 在資料接收路徑上對傳入的記錄計數。 | 僅限 API。請參閱[即時規則](#即時規則)。 |

## 規則清單

**規則** 列出每條規則的資料來源、觸發條件、狀態和最近一次評估的時間。可依規則、服務或資料來源搜尋，並在 **全部**、**已啟用** 和 **已停用** 之間切換。

| 狀態 | 含義 |
|---|---|
| **尚未評估** | 規則尚未執行。 |
| **正常** | 最近一次評估未符合條件。 |
| **等待達到持續時間** | 條件已成立，但尚未達到指定的持續時間。 |
| **觸發中** | 規則有尚未解決的事件。 |
| **已由處理管線捨棄** | 規則已觸發，但[警示處理管線](/zh-Hant/pipelines/alert-events#處理結果)捨棄了原本要開啟的事件。 |
| **已停用** | 規則儲存為草稿，不會執行。 |

點選規則或該列的 **編輯**，即可開啟規則。

## 建立閾值規則

點選 **新增規則 → 閾值規則**，開啟規則工作台。

<Steps>
  <Step title="選擇規則類型">
    選擇 **指標告警**、**日誌告警**、**追蹤告警**、**APM 警示** 或 **RUM 警示**。**快速開始** 中的預設項目會填入常用查詢，例如 **錯誤率過高**、**P95 延遲過高**、**錯誤日誌激增** 或 **無資料警報**。設定 APM 警示和 RUM 警示時，選擇服務或應用程式，再選擇一項指標，不必撰寫查詢。請參閱[依 APM 指標發出警示](/zh-Hant/apm#依-apm-指標觸發警示)和 [RUM 警示](/zh-Hant/rum/alerts)。
  </Step>
  <Step title="填寫基本資訊">
    **規則名稱** 作為事件標題，例如 `api_high_error_rate`。**服務** 將規則與特定服務關聯，用於標示歸屬並提供跨訊號的脈絡。**說明** 描述規則要保護的內容。
  </Step>
  <Step title="選擇判定方式">
    在 **查詢與觸發條件** 頂端選擇 **判定方式**：**閾值**（預設）、[**預測**](#預測規則)、[**離群**](#離群規則)、[**組合**](#組合規則)或[**心跳**](#心跳規則)。組合和心跳不必撰寫查詢，下方的查詢、測試和閾值會換成各自的設定。
  </Step>
  <Step title="撰寫查詢">
    設定 **目標資料流**、**評估間隔**（每 1、5 或 10 分鐘）、**查詢語言**（指標使用 **PromQL**，其他使用 **SQL**）和 **查詢**。查詢須傳回一個數值：評估器讀取第一列的第一個欄位。可視需要填寫[**依維度分組**](#依維度分組)。規則無法讀取 [`_audit` 資料串流](/zh-Hant/settings/data-security#稽核資料流)，儲存時會傳回 `400`。
  </Step>
  <Step title="設定觸發條件">
    每一列代表一個嚴重程度：**當結果** 透過運算子與 **閾值** 比較，**並持續** 指定的分鐘數。點選 **新增等級** 可再加一列。以符合條件的最高嚴重程度為準，高嚴重程度的條件不得比低嚴重程度的條件更容易符合。系統會將分鐘數換算為評估次數。在下方設定 [**復原條件** 和 **沒有資料時**](#復原條件與無資料處理)。
  </Step>
  <Step title="新增處理指南">
    在 **Notify 與處理** 中填寫 **處理指南 / Runbook URL**，事件處理人員即可從事件清單直接開啟指南。[升級策略](/zh-Hant/alerting/on-call#升級策略)和[通知策略](/zh-Hant/notification-channels#建立範本和策略)決定通知對象，規則本身不指定對象。
  </Step>
  <Step title="新增排查線索">
    可在 **排查線索** 中填寫 **排查步驟**、新增 **排查查詢**、選擇 **相關儀表板**，說明排查這條規則觸發的事件時應先做什麼。請參閱[排查線索](#排查線索)。
  </Step>
  <Step title="測試規則">
    點選 **測試規則**。系統會針對最近 6 小時的實際資料執行查詢，**查詢預覽** 會繪製結果，並顯示閾值線、目前值、預計觸發次數、掃描列數和執行時間。依維度分組的規則也會顯示組數。
  </Step>
  <Step title="儲存">
    **建立前檢查** 必須全部通過：已填寫名稱、目前的查詢已通過測試、閾值有效、Runbook URL 有效。接著點選 **儲存並啟用**，或點選 **儲存草稿**，只儲存而不執行。
  </Step>
</Steps>

在規則工作台建立的規則不指定升級策略。[警示路由](/zh-Hant/alerting/routing)會分派事件；若路由無法決定如何分派，則使用名為 `default` 的升級策略。若組織沒有這項策略，這類事件就不會升級給任何人。請先建立這項策略。請參閱[預設策略](/zh-Hant/alerting/on-call#預設策略)。

## 依維度分組

以 SQL 或 PromQL 查詢為基礎的定期規則，可依結果中的欄位分組，例如依主機或服務分組。在規則工作台填寫**依維度分組**，或在[建立規則](/zh-Hant/api/alerting/create-rule#依欄位分組的規則)時設定 `query.group_by`。之後，每組值都會視為一條獨立的規則。

| 項目 | 行為 |
|---|---|
| 組 | 指定欄位的值相同的資料列歸為一組。比對指定欄位與結果的欄位名稱時，不區分大小寫。 |
| 值 | 取組內第一列的值：使用分組欄位和時間欄位以外的第一個數值欄位。 |
| 觸發條件 | 各組分別比對觸發條件或各級閾值，並各自累計 `for_periods`。 |
| 事件 | 各組各自開啟事件，並在標籤和標題中帶入該組的值，例如 `Errors per host · web-1`。該組符合復原條件時，系統會將事件標為已解決。未出現在結果中的組視為沒有值，依規則對無資料的設定處理。 |
| 上限 | 最多 8 個欄位，每輪最多評估 100 組。超過 100 組時，本輪不評估其餘組別。未出現在結果中的組，本輪也會保留其事件。 |

每組傳回一列，最嚴重的排在前面：

```sql
SELECT host, count(*) AS errors
FROM app_logs
WHERE level = 'error'
GROUP BY host
ORDER BY errors DESC
```

在 PromQL 中，序列的標籤就是欄位，因此 `sum by (instance) (rate(http_requests_total{status=~"5.."}[5m]))` 會依 `instance` 分組。如果結果有資料列，卻沒有指定名稱的欄位，本輪評估就會失敗，不會變更任何狀態。在規則工作台測試查詢時，系統會檢查這些欄位。APM、RUM、即時與異常規則不能分組；[離群規則](#離群規則)必須分組。

## 復原條件與無資料處理

每條規則都須指定未解決的事件何時復原，以及評估沒有值時如何處理。在規則工作台的**復原條件**和**沒有資料時**中設定，或在[建立規則](/zh-Hant/api/alerting/create-rule#恢復條件與無資料)時設定 `trigger.recovery` 和 `trigger.no_data`。

- **復原閾值：**未解決的事件要等數值越過這個閾值才會復原。例如，高於 90 時觸發的規則，要等數值低於 80 才會復原。數值在閾值附近波動時，就不會反覆觸發與復原。
- **復原持續時間：**數值須在正常範圍內維持指定時間，事件才會復原。
- **沒有資料時：**適用於查詢未傳回值，或依維度分組的規則有某一組未出現在結果中。

| 處理方式 | 結果 |
|---|---|
| 視為復原 | 將本次評估視為未符合條件，讓未解決的事件復原。這是預設選項。 |
| 保持原狀態 | 不變更狀態，規則顯示**無資料**。這是異常規則的預設選項。 |
| 開啟無資料事件 | 維持原狀態。無資料狀態達到指定的持續時間後，開啟標示為**無資料**的事件，通知標題為 `NO DATA · <標題>`。資料恢復時，系統會自動將事件標為已解決。如果主機或服務確定已下線，請手動將事件標為已解決。資料恢復前不會再次開啟事件。 |
| 以 0 計算 | 將缺少的值視為 0 來比較，適合計數。 |

即時規則無法設定這兩項：計數一回落就會復原。

## 異常規則

當數值偏離根據歷史資料預測的範圍時，異常規則就會觸發，不需要固定閾值。點選 **新增規則 → 異常偵測規則**。

| 分組 | 欄位 | 規則 |
|---|---|---|
| 識別 | **規則名稱**、**層級**、**服務** | **服務** 為選填，用於提供跨訊號的脈絡。 |
| 偵測查詢 | **資料來源** | **查詢**、特定服務或端點的 **APM 指標**，或特定應用程式的 **RUM 指標**。請參閱[為 APM 指標設定異常偵測警示](/zh-Hant/apm/insights#為-apm-指標設定異常偵測警示)和 [RUM 異常規則](/zh-Hant/rum/alerts#異常規則)。 |
| | **資料串流**、**資料流類型**、**查詢語言**、**查詢** | 查詢須傳回單一數值，例如平均值、P95 或計數。 |
| | **評估時段** | 1、5 或 15 分鐘，或 1 小時。 |
| 偵測器 | **演算法** | **MAD**（穩健的中位數方法）或 **EWMA**（追蹤近期漂移）。 |
| | **回溯天數** | 同一時段的歷史資料，範圍為 1 到 30 天，預設為 7 天。 |
| | **靈敏度（k·σ）** | 與基準線的距離超過離散程度的 k 倍時觸發。數值越大，靈敏度越低。預設為 3。 |
| | **平滑係數（α）** | 僅適用於 EWMA，值的範圍為 `(0, 1]`。數值越大，近期樣本的權重越高。 |
| | **觸發所需的連續週期數** | 開啟事件前，評估結果須連續異常的次數。 |
| | **每週季節性** | 只與同一星期幾的歷史資料比較，避免平日與週末的差異造成誤報。至少須回溯 7 天，回溯 28 天以上效果最佳。 |

## 預測規則

預測規則根據指標過去的趨勢向前推估，若預測會在指定的預測時長內越過閾值，就會觸發。適合磁碟用量、配額用量、連線數等逐漸接近上限的指標。在 **判定方式** 中選擇 **預測**，比照閾值規則撰寫查詢，再設定：

| 設定 | 說明 |
|---|---|
| **預測** | 運算子和閾值，例如預測 `> 90`。 |
| **預測時長** | 預測在這段時間內越過閾值就會觸發：1、6、12 小時，或 1、2、3、7 天，預設為 1 天。 |
| **回溯期間** | 根據過去幾天的趨勢推估：1、3、7、14 或 30 天，預設為 7 天。 |
| **外推方式** | **線性趨勢**；**每日規律** 或 **每週規律**：將趨勢加到一天前或一週前同一時間的值上，適合有每日或每週波動的指標。採用每週規律時，至少須回溯 7 天。 |

規則每輪都會將目前值記錄到序列中。剛建立規則或修改查詢時，會先查詢多個過去時間點，補上歷史資料點。若資料點不足（少於 6 個，或採用每日或每週規律時未滿一個週期），本輪不做判定。事件會註明預計越過閾值的時間和當時的值。預測規則只能設定一個嚴重程度和一個以分鐘計的持續時間，沒有復原閾值，但可設定[沒有資料時](#復原條件與無資料處理)。

## 離群規則

離群規則不與固定閾值比較，而是比較依維度分組後的各組。例如，依主機分組統計錯誤數時，若一台主機的錯誤明顯多於其他主機，就會觸發；若所有主機的錯誤數一起上升，則不會觸發。在 **判定方式** 中選擇 **離群**，撰寫查詢並填寫[**依維度分組**](#依維度分組)，再設定：

| 設定 | 說明 |
|---|---|
| **容差** | 偏離多少個尺度單位才算離群，範圍為 0.5 到 10，預設為 3。數值越小，靈敏度越高。 |
| **判斷方向** | **偏高或偏低**、**只看偏高** 或 **只看偏低**。 |

離群規則依各組的中位數和中位數絕對偏差（MAD）計算偏離程度。即使各組的值幾乎相同，也不會將小幅波動視為離群。每個離群組別各開啟一個事件，並在事件中註明偏離程度。若有值的組別少於 3 組，本輪不做判定。離群規則不能使用 APM 和 RUM 指標，且只能設定一個嚴重程度和一個以分鐘計的持續時間。

## 組合規則

組合規則會一併評估多條規則：有進行中事件的規則視為成立，再以運算式組合各規則的結果。例如，`A && B` 只在錯誤率和延遲同時發出警示時通知；`A && !B` 只在下游正常時，才判定上游有問題。在 **判定方式** 中選擇 **組合**：

| 設定 | 說明 |
|---|---|
| **規則** | 最多選擇 10 條規則，依序標記為 A、B、C…… |
| **運算式** | 使用字母、`&&`（且）、`\|\|`（或）、`!`（非）和括號組合，例如 `A && (B \|\| C)`。 |
| **將這些規則的事件納入組合規則的事件** | 組合規則開啟事件後，所納入規則的進行中事件會[併入](/zh-Hant/alerting/incidents#合併事件)該事件，不再個別通知。之後新開啟的事件也會併入。 |

組合規則不執行查詢，無法測試，也沒有[沒有資料時](#復原條件與無資料處理)的設定。組合規則不能納入其他組合規則，也不能讓其他組合規則納入。納入的規則一旦刪除，就視為不成立。事件會註明當時哪些字母代表的規則成立。

## 心跳規則

心跳規則會等待作業回報：排程工作、備份指令碼或批次處理每次執行完畢後，都會向打卡網址傳送一次請求。如果超過週期加上寬限時間仍未打卡，或打卡回報失敗，規則就會觸發。在 **判定方式** 中選擇 **心跳**：

| 設定 | 說明 |
|---|---|
| **打卡週期** | 作業執行的間隔，範圍為 1 分鐘到 7 天，預設為 60 分鐘。 |
| **寬限時間** | 週期結束後，再等多久才視為未打卡。最多 1 天，預設為 5 分鐘。 |

儲存後會顯示打卡網址和 `curl` 範例，網址只會顯示這一次。設定作業在成功時向該網址傳送請求（`GET` 或 `POST`）；失敗時加上 `?status=fail`，規則就會立即觸發。`POST` 要求本文開頭的內容會作為本次打卡的附註記入事件，適合附上最後幾列日誌。

```bash
if ./backup.sh; then
  curl -fsS "$HEARTBEAT_URL"
else
  curl -fsS "$HEARTBEAT_URL?status=fail"
fi
```

編輯心跳規則時，可查看上次打卡時間及下次打卡的最晚時間。點選 **重設打卡網址** 可取得新網址，舊網址會立即失效。打卡網址不需登入，使用網址中的 Token 驗證。請參閱[公開存取](/zh-Hant/public-access)和[心跳打卡](/zh-Hant/api/alerting/heartbeats)。心跳規則不執行查詢，無法測試，也沒有[沒有資料時](#復原條件與無資料處理)的設定。

## 即時規則

即時規則在資料擷取路徑上執行，不依計時器執行。intake 節點收到每筆記錄時，都會比對該筆記錄與所屬資料串流的即時規則，並將比對結果納入長度為 `periodSecs` 秒的滑動視窗。負責這條規則的 alert 節點每秒向各個接收寫入的節點擷取一次視窗內的符合筆數並加總。總數達到觸發條件時開立事件，不再符合條件時則將事件標為已解決。與記錄寫入的時間相比，最多延遲 1 秒。

| 部分 | 行為 |
|---|---|
| 陳述式 | SQL 的 `SELECT count(*) FROM <stream> [WHERE <condition>]`。資料表名稱為規則的 `stream`。條件會比較欄位與常值（`=`、`!=`、`<`、`<=`、`>`、`>=`），並支援 `IN`、`BETWEEN`、`LIKE`、`ILIKE` 與 `IS [NOT] NULL`，以 `AND`、`OR`、`NOT` 與括號組合條件。缺少的欄位或值為 null 的欄位一律不符合比較條件。 |
| 視窗 | `periodSecs` 的範圍為 1 到 3600。 |
| 觸發條件 | `operator` 為 `gt` 或 `gte`，`for_periods` 為 `0` 或 `1`。`thresholds` 中的各級門檻依計數決定嚴重程度。 |
| 事件 | 事件遵循一般的生命週期：每條規則只有一個進行中的事件，並套用 `silence_secs` 冷卻時間、升級與通知。 |

[建立規則](/zh-Hant/api/alerting/create-rule)會以 `400` 拒絕超出上述限制的即時規則。各個接收寫入的節點將計數保存在記憶體中，並每 5 秒將視窗快照寫入中繼資料庫。節點重新啟動時會讀回自己的快照，最多遺失最後 5 秒的計數。節點停止或未回應時，負責彙總的 alert 節點會改用該節點最近的快照，直到這些計數移出視窗。更換彙總節點不會遺失已觸發的狀態，接手的節點會根據進行中的事件接續處理。叢集內的節點需要設定叢集 bearer 權杖（`MS_SELF_TELEMETRY_CLUSTER_TOKEN`，與分角色部署共用），才能向其他節點擷取計數；未設定時只能使用快照。

### 聯邦中的即時規則

在[跨叢集聯邦](/zh-Hant/settings/data-plane#跨叢集聯邦)中，每個叢集各自統計寫入該叢集的記錄，預設依各自的計數判斷。若要加總各叢集的計數，請指定彙總叢集：在 API 中設定 `query.home_cluster`，或在規則工作台開啟這條規則後設定 **彙總叢集**（可選擇本機叢集或已啟用的遠端叢集）。只有彙總叢集會開立這條規則的事件或將其標為已解決：負責這條規則的 alert 節點每秒使用該組織專屬的權杖，向已對應該組織的各叢集取得計數，加上彙總叢集自己的計數後再判斷。其他叢集只負責計數。未在 800 毫秒內回應的叢集會沿用上次回傳的計數，最多沿用 30 秒，之後以 0 計算。因此，偶爾有一秒未回應不會使事件被標為已解決；指標 `realtime_federated_counts_failed_total{cluster}` 會記錄未回應的次數。規則會透過聯邦同步，ID 不變，各叢集都依該規則計數。

## 評估延遲

在分角色叢集中，查詢只會讀取 intake 已寫入的資料。intake 緩衝區中的記錄最多要等 `[intake].flush_interval_secs`（預設 30 秒）才能查到，因此最近一個視窗的數值會偏低。規則工作台 **進階** 中的 **評估延遲** 會將每輪評估的整個視窗往前移：延遲和週期都設為 5 分鐘時，07:00 會評估 06:50 到 06:55 的資料。

| 值 | 效果 |
|---|---|
| **自動**（預設） | 由單一程序執行所有角色的單機部署不會移動視窗；分角色叢集會套用 **設定 → 警示評估** 中的 **評估延遲**，預設為 60 秒。 |
| **不延遲** | 評估截至目前的資料。 |
| 30 秒到 1 小時 | 套用這條規則的延遲。API 可設定 0 到 3600 秒（`query.delay_secs`）。 |

無資料判定、恢復條件、異常偵測的基準線、預測規則的序列、依維度拆分和離群值偵測都會依相同的延遲往前移。視窗往前移時，開立的事件會在註解 `evaluated_window` 中記錄該輪評估的時間區間。即時規則不會評估查詢，因此沒有評估延遲。

## 優先順序與緊急程度

在規則工作台的 **Notify 與處理** 中，使用 **優先順序** 和 **緊急程度** 設定這條規則開立的事件：

- **優先順序**：選擇組織的其中一個[優先順序等級](/zh-Hant/alerting/on-call#緊急度與優先順序等級)。預設為 P1 到 P5，P1 最高。未設定時，事件沒有優先順序（也可透過[警示管線](/zh-Hant/pipelines)設定）。優先順序不由嚴重程度推導。
- **緊急程度**：選擇 **依升級策略**（預設）時，套用事件所用的[升級策略的緊急程度](/zh-Hant/alerting/on-call#緊急程度)；選擇高或低時，一律套用所選等級。

## 排查線索

規則工作台的 **排查線索** 說明排查這條規則的事件時應先做什麼。各部分皆可留空：

| 部分 | 內容 | 上限 |
|---|---|---|
| **排查步驟** | Markdown：先查什麼，以及依什麼順序排查。 | 8,000 個字元 |
| **排查查詢** | **名稱**、查詢語言（**promql** 或 **sql**）、SQL 查詢的 **資料串流** 和 **資料類型**，以及 **查詢陳述式**。 | 10 筆，每筆最多 4,000 個字元 |
| **相關儀表板** | 可從事件開啟的儀表板。 | 5 個 |

這條規則的每個事件都會在 **排查線索** 中顯示這些內容：排查步驟會依格式呈現；每筆查詢都是連結，會依事件的時間範圍開啟指標（PromQL）、追蹤（讀取追蹤資料串流的 SQL）或日誌（其他 SQL）；每個儀表板也是連結。[Mole Agent](/zh-Hant/agent) 在調查事件前會先讀取排查線索並執行其中的查詢，事件的 [AI 根本原因](/zh-Hant/alerting/incidents#ai-根因)也會參考排查線索。

透過 API 設定時，請使用規則的 `guide` 欄位設定排查線索，請參閱[建立規則](/zh-Hant/api/alerting/create-rule#排查線索)。匯出時會包含排查線索；匯入時會移除組織中沒有的儀表板。

## 自動探索規則

[自動探索](/zh-Hant/alerting/discovery)找到的問題只會加入清單。若要傳送通知，請在 **警示 → 自動探索** 中按一下 **建立自動發現規則**，或在一筆發現上按一下 **為這類發現建立規則**：選擇發現的類型、服務或應用程式、環境、最低嚴重程度、升級策略與緊急程度。每筆符合條件的發現都會各自開立一個事件，並沿用該筆發現的嚴重程度。未設定緊急程度時，套用低緊急程度；發現結束時，事件就會恢復。這類規則在規則清單中的來源顯示為 **自動探索**；開啟規則時會返回自動探索頁面進行編輯。

## 匯入與匯出

使用規則清單中的 **匯入與匯出** 將規則儲存為檔案，或從檔案匯入規則：

- **匯出所有規則**，或篩選後選擇 **匯出這 N 條規則**：下載 JSON 規則套件（`"format": "molesignal.alert-rules/v1"`）。套件包含規則的完整定義，但不包含 ID、組織、評估狀態及時間。套件依名稱參照升級策略和組合規則的子規則，因此可將同一份套件移至其他工作區或叢集。套件不含心跳規則的簽到網址，請在匯入後於規則中重設。
- **匯入規則…**：貼上或選取規則套件或 Prometheus 警示規則檔案（也支援 Prometheus Operator 的 `PrometheusRule`）。先按一下 **試跑**，查看每條規則會 **新增**、**更新**（列出變更的欄位）、**未變更** 或出現 **錯誤**，再按一下 **匯入 N 條**。系統依名稱比對規則：沒有同名規則就新增，恰有一條就更新，有多條同名規則就回報錯誤。同一個名稱在檔案中出現兩次也會回報錯誤（如果匯出的規則有同名項目，請先重新命名再匯入）。勾選 **只新增，不變更現有的同名規則** 時，現有規則會標為 **跳過**。只要有一條規則出錯，就不寫入整份套件；若無錯誤，則一次寫入，確保全部寫入或全部不寫入。

Prometheus 規則會依下列方式轉換成 MoleSignal 規則：

| Prometheus | MoleSignal |
|---|---|
| `alert` | 規則名稱。同名警示出現在多個規則群組中時，後續的規則名稱會加上群組名稱。 |
| `expr` | PromQL 規則，陳述式為 `count(<expr>)`，條件為 `>= 1`：運算式傳回序列就發出警示。註解或標籤使用 `{{ $labels.x }}` 時，陳述式為 `count by (x) (<expr>)`，並依 `x` [拆分](#依維度分組)，每組各開立一個事件。資料串流採用運算式中的第一個指標名稱。 |
| 規則群組的 `interval` | 週期，未設定時為 60 秒。 |
| `for` | 連續符合條件的週期數，無條件進位至整數。 |
| 標籤 `severity` | 嚴重程度：`critical`、`page` 為嚴重，`error`、`high` 為錯誤，`warning`、`warn` 為警告，`info`、`low`、`none` 為提示；其餘標籤原樣保留。 |
| `annotations` | 原樣保留；說明取自 `description` 或 `summary`。 |
| `record` | 不匯入記錄規則，並在試跑結果下方列出。 |
| `keep_firing_for` | 不支援，在試跑結果下方列出。 |

匯入的規則會使用預設升級策略。如有需要，請在匯入前修改規則套件中的 `escalation_policy`。Alertmanager 本身的設定檔（`alertmanager.yml` 中的路由和接收端）不屬於規則，無法用這種方式匯入。請改用[警示路由](/zh-Hant/alerting/routing)和[通知策略](/zh-Hant/notification-channels)。

在 CI 中可使用 [CLI](/zh-Hant/cli) 的 `molesignal alerts rules export` 和 `molesignal alerts rules apply -f rules.json [--dry-run]`：試跑結果會以表格輸出。如果有規則出錯，指令會以結束代碼 1 結束。

## 修改、暫停或刪除規則

開啟規則即可修改。修改後，再次按一下 **測試規則** 並儲存。選擇 **儲存草稿** 可讓規則維持停用；選擇 **儲存並啟用** 可重新啟用規則。若要刪除規則，請呼叫[刪除規則](/zh-Hant/api/alerting/delete-rule)。若只想暫時停止某條規則的通知而不修改規則，請使用[靜音](/zh-Hant/alerting/silences)。

可在指令碼中使用[警示規則 API](/zh-Hant/api/alerting/create-rule) 建立、測試及觸發規則。
