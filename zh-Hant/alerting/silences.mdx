靜默會暫停符合條件的事件通知與升級，但仍會記錄事件本身。語意分組會將相關事件歸在一起，方便一次處理。兩者都不會修改規則。若要在有更嚴重的事件時壓制次要事件，請使用[抑制](/zh-Hant/alerting/inhibition)。

## 靜默策略

開啟 **警示 → 靜默策略**。每條策略都會顯示狀態、時段和比對條件。

| 狀態 | 含義 |
|---|---|
| **靜默中** | 符合條件的事件目前處於靜默狀態。 |
| **尚未開始** | 時段尚未開始。 |
| **未到靜默時段** | 目前不在週期性重複時段的生效範圍內。 |
| **已結束** | 時段已結束。 |
| **已關閉** | 策略已停用。 |

建立策略：

1. 按一下 **新增靜默規則** 並填寫 **名稱**，保持 **啟用** 開啟。
2. 在 **比對條件** 中，針對事件標籤的每個條件按一下 **新增比對器**，例如 `service` `=` `checkout`。事件必須符合所有比對器，`=~` 與 `!~` 用於規則運算式比對。如果沒有比對器，策略會比對 **所有事件**。
3. 在 **時段** 中選取 **時段類型**：
   - **固定區間**：設定一個 **開始** 和一個 **結束**；
   - **每週重複**：設定一個 **時區** 和一或多個時段。每個時段選取 **星期**，填寫 **開始（HH:MM）** 和 **結束（HH:MM）**，精確到分鐘，例如每週六 02:00 到 06:00；結束時間不晚於開始時間，表示時段跨越午夜。在 **假日** 中，可以依照[假日行事曆](/zh-Hant/alerting/on-call#假日行事曆)排除放假日，或只在放假日生效；
   - **假日**：設定一個 **時區** 和一份 **假日行事曆**。行事曆上的每個放假日都會全天靜默，例如測試環境在國定假日不傳送警示；
   - **每月一次**：設定一個 **時區**，依 **每月幾號**（若當月沒有該日期，則使用當月最後一天），或依 **第幾個**（第 1 到第 5 個，或最後一個）**星期幾** 排程，再設定 **開始時間（HH:MM）** 和 **持續時間（分鐘）**，最長 7 天。例如每月第一個星期日 02:00 起持續 240 分鐘。若當月沒有第五個指定的星期幾，就跳過該月。
4. 在 **備註** 中填寫 **原因**，再按一下 **建立靜默**。

清單會標示週期性靜默的 **下次開始** 或 **結束** 時間，由伺服器依照時區和日光節約時間計算。

靜默會比對事件帶有的標籤，包括規則的標籤，以及[依維度拆分](/zh-Hant/alerting/rules#依維度分組)的規則中各組的標籤值。[外部警示](/zh-Hant/alerting/sources)建立的事件帶有 `alert.source=external`、`external.kind`（例如 `alertmanager`）、警示本身的標籤和來源的附加標籤。例如，使用 `external.kind` `=` `grafana` 可靜默 Grafana 傳來的所有警示。每個預先排定的靜默都應註明受影響的服務和結束時間，並設定到期自動結束，而不是事後再刪除。

<Warning>
  靜默只會隱藏通知，無法證明服務已恢復。時段結束時，請查看事件清單。
</Warning>

### 靜默期間的通知

靜默生效時，系統仍會照常開啟並記錄符合條件的事件，並依通知類型按下列方式處理：

| 通知 | 靜默期間 | 靜默結束後 |
|---|---|---|
| 警示觸發、警示已升級 | 不傳送通知，升級停在目前層級。 | 若事件仍未確認且尚未恢復，系統會補發觸發通知並繼續升級；若目前層級的確認期限已在靜默期間屆滿，系統會接著通知下一層級。靜默期間已確認或已恢復的事件不會補發通知。 |
| 接收順序中的後續步驟、通知策略的確認逾時升級 | 不傳送通知。 | 若事件仍未確認，系統會繼續傳送通知。 |
| 警示已確認、警示已恢復 | 若系統在靜默開始前已傳送觸發通知，則照常傳送；若靜默擋下了觸發通知，則不傳送。 | 照常傳送。 |

時段結束、停用策略或刪除策略，都會結束靜默。

### 靜默單一事件

事件上的 **靜默** 只會暫停該事件的通知與升級。可選擇 **1 小時**、**4 小時**、**24 小時** 或 **7 天**，也可填寫 **原因**。這項操作不會停用規則，也不會靜默同一服務的其他事件。這筆靜默會顯示在 **靜默策略** 中，可在該處修改或提前移除。

建立、修改和移除靜默需要 `alerts.mutes.manage`。

## 語意分組

開啟 **警示 → 分組**。語意分組會將標籤值相同的事件歸為一組，類似 Alertmanager 的 `group_by`。透過 API 確認或解決分組時，系統會對組內每個事件執行相同的操作，請參閱[事件分組](/zh-Hant/alerting/incidents#事件分組)。

1. 按一下 **新增分組** 並填寫 **名稱**，例如 `critical-by-service`，保持 **啟用** 開啟。
2. 在 **比對條件** 中新增事件必須符合的條件，例如 `severity` = `critical`。事件必須符合所有條件；若未設定條件，分組會套用至所有事件。
3. 在 **分組鍵** 中填寫 **分組標籤鍵**，以逗號分隔，例如 `service, region`。這些標籤的值相同的事件會歸為同一組。
4. 按一下 **建立分組**。

系統會略過已停用的分組。刪除分組時，系統只會移除分組規則，並保留事件。

使用 **匯入** 從 JSON 建立分組：可使用分組陣列，或包含 `groups` 陣列的物件。

```json
[
  {
    "name": "crit-by-service",
    "enabled": true,
    "matchers": [{ "label": "severity", "op": "eq", "value": "critical" }],
    "groupBy": ["service"]
  }
]
```

管理分組需要 `alerts.semantic_groups.manage`。
