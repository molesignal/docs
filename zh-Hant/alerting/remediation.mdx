修復動作是事先定義的單一步驟處置：向 Jenkins、GitHub Actions、Argo、Rundeck 等系統的位址發出一次請求，或在已登記的 Kubernetes 叢集上重新啟動、擴縮工作負載，或將工作負載回復至上一版本。處理事件時，可在事件上按一下即可啟動動作。每次執行都須審核（組織啟用[預先核准](#預先核准)時，可事先核准），核准後立即執行，結果和驗證都會記錄在事件的時間軸上。

開啟 **警示 → 修復動作**。檢視需要 `alerts.remediation.read`，定義動作和登記叢集需要 `alerts.remediation.manage`，在事件上啟動動作需要 `alerts.incidents.remediate`，核准需要 `agent.approve`。

## 定義修復動作

按一下 **新增修復動作**，填寫：

| 區段 | 設定 |
|---|---|
| **基本資訊** | **名稱** 和 **說明**。 |
| **執行方式** | **HTTP 請求** 或 **Kubernetes**，請參閱下文。 |
| **啟動時填寫的參數** | 啟動時要填寫的值，最多 10 個：**名稱**（在範本中寫入 `{{params.name}}`，將 name 換成此名稱）、**顯示名稱**、**類型**（**文字**、**數字** 或 **選項**）、**選項**、**預設值** 和 **必填**。 |
| **適用範圍與審核** | **適用的服務**（以逗號分隔，留空時適用於所有事件）；**風險等級**：**L2 · 一人核准** 或 **L3 · 兩人核准**；**執行後驗證**：設定幾分鐘後檢查結果，0 表示不驗證；**有效的判定條件**：**事件已解除** 或 **規則恢復正常**；**啟用**。 |

清單會顯示每個動作適用的服務（未限定時顯示 **所有事件**）和風險等級。停用的動作標示為 **已停用**，不會出現在事件上。

### HTTP 請求

| 設定 | 說明 |
|---|---|
| **方法**、**位址** | `GET`、`POST`、`PUT` 或 `PATCH`，位址以 `http://` 或 `https://` 開頭。 |
| **請求標頭** | 例如 `Authorization`。值會加密儲存，儲存後不再顯示；編輯時留空即可保留原值。 |
| **請求本文** | 在 JSON 編輯器中撰寫 JSON。帶入的值會依 JSON 規則逸出。將預留位置放在引號內會視為字串，不加引號則可當作數字使用，例如 `{"replicas": {{params.replicas}}}`。將所有預留位置換成 0 後，結果必須是有效的 JSON，否則無法儲存。 |
| **簽章金鑰** | 設定後，請求會帶上 `X-MoleSignal-Timestamp` 和 `X-MoleSignal-Sign`，與[通用 Webhook 的簽章](/zh-Hant/notification-channels/webhooks#請求標頭與簽章)相同，接收端可驗證請求是否來自 MoleSignal。 |

位址、請求標頭和請求本文可使用 `{{incident.id}}`、`{{incident.summary}}`、`{{incident.severity}}`、`{{incident.status}}`、`{{incident.service}}`、`{{incident.url}}` 和 `{{params.name}}`。帶入位址的值會採用百分比編碼。

請求只會連線至位址解析出的 IP，不會連線至雲端供應商的中繼資料位址，也不會跟隨重新導向，逾時時間為 30 秒。傳回 2xx 即視為執行成功，回應的開頭會寫入執行記錄。

### Kubernetes

| 設定 | 說明 |
|---|---|
| **叢集** | 已登記的叢集，請參閱[登記 Kubernetes 叢集](#登記-kubernetes-叢集)。 |
| **操作** | **重新啟動**（滾動式重新啟動，等同 `kubectl rollout restart`）、**擴縮** 或 **回復至上一版本**（等同 `kubectl rollout undo`）。 |
| **工作負載類型** | Deployment、StatefulSet 或 DaemonSet。只有 Deployment 能回復至上一版本，DaemonSet 無法擴縮。 |
| **命名空間**、**工作負載名稱** | 可使用範本，例如 `{{incident.service}}`。 |
| **複本數** | 擴縮時的複本數。可使用 `{{params.replicas}}`，在啟動時填寫。 |

## 登記 Kubernetes 叢集

在 **Kubernetes 叢集** 中按一下 **新增叢集**，填寫 **名稱**、**API Server 位址**、**CA 憑證**（PEM 格式，留空則使用系統信任的根憑證）和 **ServiceAccount Token**。Token 會加密儲存，之後不再顯示。**測試連線** 會讀取一次叢集版本。

為 MoleSignal 建立專用的 ServiceAccount，只授予必要權限：目標工作負載的 `get` 和 `patch` 權限；擴縮還需要 `scale` 子資源的權限，回復至上一版本還需要列出 ReplicaSet 的權限。例如，只允許操作 `shop` 命名空間中的工作負載：

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: molesignal-remediation
  namespace: shop
rules:
  - apiGroups: ["apps"]
    resources: ["deployments", "statefulsets", "daemonsets", "deployments/scale", "statefulsets/scale"]
    verbs: ["get", "patch"]
  - apiGroups: ["apps"]
    resources: ["replicasets"]
    verbs: ["list"]
```

只會連線至 API Server 位址解析出的 IP，不會連線至雲端供應商的中繼資料位址。仍有動作使用的叢集無法刪除。

## 在事件上執行

事件詳細資料中的 **修復動作** 會列出適用於該事件的動作：動作未限定服務，或事件的服務符合動作設定。按一下動作旁的 **執行**，填妥參數，簡述 **原因**（例如「checkout 連線池已耗盡，先重新啟動」），然後按一下 **送審**。事件已解除時，無法啟動動作。

送審後，這次執行會等待審核：L2 需要一位、L3 需要兩位具備 `agent.approve` 權限的人核准。啟動者不能核准自己提出的請求。審核者可在同一張卡片上按一下 **核准** 或 **駁回**，也可在 [Mole Agent 的審核](/zh-Hant/agent#核准與執行)中處理。達到所需的核准人數後，動作會立即執行。

| 狀態 | 含義 |
|---|---|
| **等待審核** | 尚未達到所需的核准人數。 |
| **執行中** | 正在向位址發出請求或操作叢集。 |
| **已執行**、**執行失敗** | 執行已結束，旁邊會顯示回應或錯誤訊息的開頭。 |
| **未執行** | 審核請求遭駁回、已過期或已撤銷。 |
| **等待驗證** | 執行成功，經過設定的分鐘數後會檢查結果。 |
| **驗證通過**、**驗證未通過** | 到達驗證時間時，事件已解除（或規則已恢復正常）即視為通過。 |

啟動、執行和驗證都會記錄在事件的[時間軸](/zh-Hant/alerting/incidents#事件詳細資料)上，啟動也會記錄在稽核日誌中。

Mole Agent 可列出適用於事件的修復動作，也可提議執行。除非適用預先核准，否則不論動作設定的風險等級為何，Mole Agent 提議的執行一律需要兩人核准。

## 預先核准

預先核准讓動作在部分事件上無須等待審核即可直接執行。此功能預設停用，須在 **警示 → 修復動作** 頂端啟用 **允許已預先核准的動作無須等待審核即可直接執行** 才會生效。啟用、停用或設定預先核准都需要 `alerts.remediation.preapprove`（Owner 和 Admin 預設具備此權限）。如同一般審核，設定預先核准還需要 `agent.approve`。必須登入後才能給予預先核准，不能使用 API Token。

按一下動作旁的 **預先核准**，設定：

| 設定 | 含義 |
|---|---|
| **適用的服務** | 預先核准涵蓋這些服務的事件。若動作已限定服務，這裡選的每個服務都必須在動作的適用範圍內。 |
| **最多執行次數**、**時段** | 在任一指定長度的時段內，最多可執行的次數。次數可設為 1 到 20 次，時段可設為 15 分鐘到 7 天。 |
| **有效期限** | 1、7、30 或 90 天，或 **長期有效**。 |
| **執行後通知** | 最多五個管道，每個對應通知連接器上的一個群組或位址。每次依預先核准執行後，無論成功或失敗，都會透過這些管道傳送通知。 |

儲存即視為一人核准。L2 動作需要一人核准，預先核准會立即生效；L3 動作需要兩人核准，還須由另一位具備預先核准權限的人按一下 **確認預先核准** 才會生效。預先核准不會減少所需的核准人數。修改動作的執行方式、參數、適用的服務或團隊，或風險等級後，原有核准會失效，預先核准須重新等待核准。

使用者或 Mole Agent 在預先核准涵蓋的事件上啟動此動作時，系統會直接將請求記錄為已由提供預先核准的人核准，並以啟動者的身分立即執行。啟動者仍須具備 `alerts.incidents.remediate`。和一般審核一樣，啟動者不能核准自己提出的請求，因此啟動者給予的預先核准不計入該次請求的核准人數。排除啟動者後，若核准人數不足（L2 一人、L3 兩人），仍須等待審核。組織未啟用預先核准、預先核准已過期或仍在等待第二人確認、事件不屬於適用的服務，或時段內的次數已用完，也都須照常等待審核。這次執行會在事件上標示 **預先核准**，時間軸和稽核日誌會註明依預先核准執行，並透過設定的管道傳送通知。

| 動作旁的狀態 | 含義 |
|---|---|
| **未預先核准** | 動作沒有預先核准。 |
| **已預先核准 · 時段內已執行 N/M 次** | 目前有效，時段內已執行 N 次。 |
| **已預先核准 · 等待第二人確認** | L3 動作，目前只有一人核准。 |
| **已預先核准 · 次數已用完** | 須等先前的執行不再計入目前時段，才能再次執行。 |
| **預先核准已過期** | 已超過有效期限，重新設定即可續期。 |
| **已預先核准 · 組織尚未啟用** | 頂端的開關尚未開啟。 |

## API

| 操作 | 端點 |
|---|---|
| 管理修復動作和叢集 | [`/api/v1/alerts/remediation/actions`、`/clusters`](/zh-Hant/api/alerting/remediation) |
| 在事件上啟動動作 | [`POST /api/v1/alerts/incidents/{id}/remediations`](/zh-Hant/api/alerting/remediation#從事件執行) |
| 讀取、啟用或停用預先核准 | `GET`、`PUT /api/v1/alerts/remediation/preapproval` |
| 設定、取消或確認動作的預先核准 | `PUT`、`DELETE /api/v1/alerts/remediation/actions/{id}/preapproval`、`POST /api/v1/alerts/remediation/actions/{id}/preapproval/confirm` |
