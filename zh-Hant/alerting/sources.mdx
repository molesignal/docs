告警來源可將其他系統傳來的警示建立為[事件](/zh-Hant/alerting/incidents)。如同規則建立的事件，依[升級策略](/zh-Hant/alerting/on-call#升級策略)聯絡值班人員，並依[通知策略](/zh-Hant/notification-channels)傳送通知。來源回報恢復時，事件會自動解決。開啟 **警示 → 告警來源**。檢視需要 `alerts.sources.read`；新增、修改、刪除及更換 Token 需要 `alerts.sources.manage`。

## 來源類型

每個來源都有一種類型，決定要用哪一種格式讀取請求本文。

| 類型 | 傳送端 | 一個事件對應 |
|---|---|---|
| **API** | 指令碼、CI、自行開發的系統，呼叫 MoleSignal 的介面 | 一個去重鍵 |
| **Alertmanager** | Prometheus Alertmanager 的 webhook 接收器 | 一個通知群組 |
| **Grafana** | Grafana 警示的 Webhook 聯絡點 | 一個通知群組 |
| **Datadog** | Datadog 的 Webhooks 整合 | 一個監控項目；多重警示監控的每個群組各對應一個事件 |
| **PagerDuty** | PagerDuty 的 Webhook（v3）訂閱 | 一個 PagerDuty 事件 |
| **阿里雲雲監控** | 閾值警報回呼、事件訂閱的推送管道 | 一條警報規則下的一個物件，或一筆系統事件 |
| **騰訊雲可觀測平台** | 通知範本中的介面回呼 | 一條策略下某個物件的一項指標或事件；若有分級，每個層級各對應一個事件 |
| **Amazon CloudWatch** | 接收警示的 SNS 主題所使用的 HTTPS 訂閱 | 一則警示 |
| **Zabbix** | Zabbix 的 Webhook 媒體類型 | 一個問題 |
| **電子郵件** | 一個 IMAP 信箱，或現有郵件系統轉送的原始郵件 | 一串主旨相同的郵件 |

相容於 Alertmanager webhook 的系統，例如 Thanos、Cortex、Mimir 的 Alertmanager，請選用 **Alertmanager** 類型。

## 新增來源

1. 開啟 **警示 → 告警來源**，按一下 **新增警示來源**。
2. 選擇 **類型**，填寫 **名稱**。
3. 選擇 **升級策略**。預設為 **依路由分派（預設）**，與規則工作台相同：[警示路由](/zh-Hant/alerting/routing)依路由規則、服務的負責團隊和 team 標籤選出團隊及升級策略。若都沒有，則使用名為 `default` 的[預設策略](/zh-Hant/alerting/on-call#預設策略)。選擇特定策略時，事件會使用該策略，路由只決定團隊。選擇 **不升級，只依通知策略傳送通知** 時，系統照常建立事件並傳送通知，但不會依升級策略聯絡值班人員。
4. 選擇 **預設嚴重程度**：警示未指定嚴重程度時，使用此等級。
5. 視需要新增 **附加標籤**，例如 `team=payments`。系統會將標籤加到此來源建立的每個事件。若警示已帶有同名標籤，以警示的標籤為準。
6. 按一下 **建立**。系統會開啟來源詳細資料，並在彈出視窗顯示此來源的 Token 和已填入 Token 的設定。阿里雲雲監控只需要接收網址，因此視窗會顯示含有 Token 的接收網址。

<Warning>
  系統只在新增來源或更換 Token 時顯示完整的 Token。關閉彈出視窗後，只能看到以 `mspat-` 開頭的前綴。若忘記 Token，請按一下 **更換 Token**。舊 Token 會立即失效。
</Warning>

## 接收網址與 Token

所有來源共用同一個接收網址，由 Token 識別來源：

```text
https://<molesignal-host>/api/v1/intake/alerts
```

Token 的格式為 `mspat-<36 位>`，外觀與 API Token 相同，但只能用於接收警示。API Token 無法用於接收警示。傳送端須將 Token 放在請求標頭中：

```text
Authorization: Bearer <token>
```

無法設定請求標頭的傳送端（阿里雲雲監控、騰訊雲可觀測平台、透過 SNS 傳送的 Amazon CloudWatch）須將 Token 放在網址中：`https://<molesignal-host>/api/v1/intake/alerts?token=<token>`。

傳送端必須能存取此網址。如果 MoleSignal 前方有防火牆，請依傳送端所在的站點或區域允許其對外 IP。Datadog 各站點的 IP 清單見 `ip-ranges` 的 `webhooks` 一節；PagerDuty 分別公布美國區與歐洲區的 IP；阿里雲雲監控的推送網段請參閱其警報回呼文件。若在內部網路部署 MoleSignal，請參閱[公開網路存取](/zh-Hant/public-access)，瞭解如何只對外開放此網址。

## 設定傳送端

來源詳細資料中的 **接收方式** 分三個步驟列出各類型的接收網址、Token 和設定。在 `<TOKEN>` 處填入此來源的 Token。此來源收到第一筆請求後，三個步驟都會顯示勾號。

### API

```bash
curl -X POST https://<molesignal-host>/api/v1/intake/alerts \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{"dedupKey": "disk-full/web-1", "summary": "web-1 磁盘使用率 95%", "severity": "critical", "labels": {"host.name": "web-1"}}'
```

`action` 可為 `trigger`（預設）、`acknowledge` 或 `resolve`。使用同一個 `dedupKey` 確認或恢復同一則警示。欄位說明請參閱[接收外部警示](/zh-Hant/api/alerting/send-alerts)。

### Alertmanager

在 `alertmanager.yml` 中新增接收器，並在路由中將警示傳給此接收器：

```yaml
route:
  receiver: molesignal
receivers:
  - name: molesignal
    webhook_configs:
      - url: https://<molesignal-host>/api/v1/intake/alerts
        send_resolved: true
        http_config:
          authorization:
            credentials: <token>
```

請將 `send_resolved` 維持為 `true`，否則不會傳送恢復通知。同一個 Alertmanager 叢集的各個副本必須設定相同的 `--web.external-url`。外部網址是去重鍵的一部分，因此不同區域的 Alertmanager 即使採用相同的路由，同名群組也不會合併為同一個事件。

### Grafana

1. 在 Grafana 中開啟 **Alerting → Contact points**，按一下 **Add contact point**。
2. 在 **Integration** 選擇 **Webhook**，並在 **URL** 填入接收網址。
3. 在 **Optional Webhook settings** 中，將 **Authentication Header Scheme** 設為 `Bearer`，並在 **Authentication Header Credentials** 填入 Token。
4. 請勿勾選 **Disable resolved message**。儲存後，在通知策略中使用此聯絡點。

若用設定檔管理：

```yaml
apiVersion: 1
contactPoints:
  - orgId: 1
    name: molesignal
    receivers:
      - uid: molesignal
        type: webhook
        settings:
          url: https://<molesignal-host>/api/v1/intake/alerts
          httpMethod: POST
          authorization_scheme: Bearer
          authorization_credentials: <token>
```

### Datadog

1. 在 Datadog 中開啟 **Integrations → Webhooks**，新增 Webhook，名稱可設為 `molesignal`。
2. 在 **URL** 填入接收網址，在 **Custom Headers** 填入 `{"Authorization": "Bearer <token>"}`，請勿勾選 **Encode as form**。
3. 在 **Payload** 填入下方範本。欄位名稱來自 MoleSignal，值使用 Datadog 的變數。MoleSignal 會拒收不符合此範本的請求。

```json
{
  "alert_id": "$ALERT_ID",
  "alert_cycle_key": "$ALERT_CYCLE_KEY",
  "transition": "$ALERT_TRANSITION",
  "alert_type": "$ALERT_TYPE",
  "priority": "$ALERT_PRIORITY",
  "title": "$ALERT_TITLE",
  "event_title": "$EVENT_TITLE",
  "message": "$TEXT_ONLY_MSG",
  "scope": "$ALERT_SCOPE",
  "tags": "$TAGS",
  "hostname": "$HOSTNAME",
  "link": "$LINK",
  "snapshot": "$SNAPSHOT",
  "query": "$ALERT_QUERY",
  "org_id": "$ORG_ID",
  "last_updated": "$LAST_UPDATED"
}
```

4. 在監控項目的通知訊息中加入 `@webhook-molesignal`。

各個 Datadog 站點（`datadoghq.com`、`datadoghq.eu`、`us3`、`us5`、`ap1` 等）都能傳送到同一個來源。MoleSignal 從 `$LINK` 的網域名稱判斷站點，並將站點與組織 ID 一併納入去重鍵。

### PagerDuty

1. 在 PagerDuty 中開啟 **Integrations → Generic Webhooks (v3)**，按一下 **New Webhook**。
2. 在 **Webhook URL** 填入接收網址，並視需要選擇 **Scope Type**（整個帳號、特定服務或特定團隊）。
3. 在 **Event Subscription** 勾選 `incident.triggered`、`incident.acknowledged`、`incident.resolved`、`incident.reopened` 和 `incident.priority_updated`。
4. 新增自訂請求標頭 `Authorization`，將值設為 `Bearer <token>`。

美國區和歐洲區的帳號都能傳送到同一個來源。MoleSignal 會將帳號網域名稱（`<子域>.pagerduty.com` 或 `<子域>.eu.pagerduty.com`）納入去重鍵，並寫入標籤 `pagerduty.region`。

### 阿里雲雲監控

在接收網址中附加 Token：

```text
https://<molesignal-host>/api/v1/intake/alerts?token=<token>
```

- **閾值警報**：在警報規則的 **警報回呼** 中填入此網址。雲監控以表單編碼傳送 POST 回呼，MoleSignal 也支援 JSON。
- **系統事件**：在 **事件中心 → 事件訂閱 → 推送管道** 中新增管道。將 **目標類型** 設為 **Webhook**、**請求方式** 設為 **POST**、**資料格式** 設為 **JSON**，填入上方的網址，再於訂閱策略中使用此管道。

雲監控的系統事件回呼只等候 5 秒，失敗時會重試 3 次。MoleSignal 將請求轉送到[接收叢集](#多個叢集)時最多等候 3 秒。逾時便傳回 `503`，讓雲監控重試。中國站和國際站以及各區域的回呼格式皆相同。MoleSignal 會將區域寫入標籤 `aliyun.region`，並將帳號 `userId` 納入去重鍵。

### 騰訊雲可觀測平台

在騰訊雲可觀測平台（原雲監控）的 **警示管理 → 通知範本** 中編輯或新增範本，將接收網址填入 **介面回呼**，再將範本繫結至警示策略。騰訊雲的回呼無法設定請求標頭，請將 Token 放在網址中，並將此網址視為憑證妥善保管。回呼不含簽章，MoleSignal 會透過網址中的 Token 識別來源。MoleSignal 可接收指標警示和事件警示，兩者在觸發和恢復時都會推送。

- **去重**：帳號、警示策略、指標或事件名稱，以及警示物件皆相同時，視為同一則警示。對於分級策略，每個層級各建立一個事件，並與騰訊雲一樣各自恢復。
- **嚴重程度**：`alarmLevel` 的緊急（`Serious`）對應 critical，嚴重（`Warn`）對應 error，提示（`Remind`）對應 info。未分級的策略使用來源的預設嚴重程度。
- **無狀態事件**（`alarmStatus` 為 `5`）建立後不會收到恢復通知，須手動解決。
- **時間**：回呼時間不含時區，以北京時間為準。

### Amazon CloudWatch

CloudWatch 警示不會直接呼叫外部網址，必須透過 SNS 傳送：

1. 在警示的通知設定中，將進入 **警示**（`ALARM`）和恢復 **正常**（`OK`）的通知都傳送到同一個 SNS 主題。若未收到 `OK`，事件不會自動解決。若要接收無資料警示，也請傳送 **資料不足**（`INSUFFICIENT_DATA）的通知。
2. 為主題新增 HTTPS 訂閱，並在端點填入含有 Token 的接收網址：

   ```bash
   aws sns subscribe \
     --topic-arn <主题的 ARN> \
     --protocol https \
     --notification-endpoint 'https://<molesignal-host>/api/v1/intake/alerts?token=<token>'
   ```

3. 系統會自動確認訂閱：MoleSignal 驗證確認訊息的簽章後，會存取訊息中的 `SubscribeURL`。

MoleSignal 會驗證每則 SNS 訊息的簽章，因此請關閉 **Raw message delivery**。若啟用，MoleSignal 會拒收訊息，並在來源詳細資料的近期接收紀錄中說明原因。驗證簽章時須從 `sns.<region>.amazonaws.com` 取得憑證，因此接收請求的節點必須能存取此網址。

CloudWatch 的警示沒有嚴重程度，因此事件使用來源的預設嚴重程度。MoleSignal 以警示的 ARN 為去重鍵，組合警示也一樣。MoleSignal 會將警示說明和狀態變更原因寫入註解，並將區域、帳號、命名空間、指標和維度寫入標籤。可使用 `aws.region` 等標籤進行路由分派。

### Zabbix

支援 Zabbix 6.0 以上版本。Zabbix 不限定請求本文的格式，由媒體類型中的指令碼傳送。因此，來源詳細資料和新增來源時的彈出視窗都會提供已填好網址和 Token 的媒體類型設定：

1. 將設定存成 YAML，在 **Alerts → Media types → Import** 匯入，並確認 `token` 參數。
2. 設定全域巨集 `{$ZABBIX.URL}`（Zabbix 前端的網址）。MoleSignal 會將此網址納入去重鍵，以區分同一來源接收的不同 Zabbix 執行個體，事件也能連回 Zabbix。不設定也能使用。
3. 為一位使用者新增此媒體。**傳送至** 可填任意值，指令碼不會使用此欄位。
4. 新增一個觸發器動作：將 **操作**、**恢復操作** 和 **更新操作** 都傳送給這位使用者。若未設定恢復操作，事件不會自動解決。

使用媒體類型的 **測試** 按鈕時，請填入實際值。若巨集未展開（例如原樣傳送 `{EVENT.ID}`），MoleSignal 會傳回 `400`，並提示使用文件提供的媒體類型。

### 電子郵件

有兩種接收方式，兩者都會將郵件解析成相同的警示。

**讀取信箱**（建議）：MoleSignal 會定期讀取 IMAP 信箱。只需要有一個信箱，且 MoleSignal 能對外連線，不需公開網路位址、MX 記錄、25 連接埠或憑證，是自架部署最簡便的方式。將監控系統的警示郵件直接寄到此信箱，或設定郵件規則轉寄。

在來源詳細資料的 **讀取信箱** 中，填寫 **IMAP 伺服器**、**連接埠**、**加密**、**使用者名稱**、**密碼或授權碼**、**資料夾**（預設為 `INBOX`）及 **讀取間隔**（15 至 3600 秒，預設為 60 秒）。按一下 **測試連線**，再按一下 **儲存信箱設定**。

- **唯讀**：使用 `EXAMINE` 和 `BODY.PEEK[]`，不變更已讀狀態，也不刪除郵件。可使用唯讀帳號。
- **不讀取既有郵件**：首次連線時會記錄當下的位置，只讀取之後收到的郵件。更換主機、帳號或資料夾，或伺服器重新整理信箱（`UIDVALIDITY` 變更）時，會從當下的位置重新開始。來源停用期間不讀取郵件，也不保留位置；重新啟用後，從當下的位置開始。
- **必須填寫寄件者清單**：知道信箱地址的人都能寄信。在來源設定的 **接受哪些寄件者** 填入完整地址，或填入 `@example.com` 以接受整個網域。若要接受所有寄件者，請填入 `*`。清單依 `From` 比對，但此欄位可能遭偽造，因此仍須啟用郵件服務商的垃圾郵件防護與 DMARC。不在清單上的郵件會記為 **已拒收**，不建立事件。
- **登入方式**：使用密碼、郵件服務提供的授權碼，或應用程式專用密碼。Microsoft 365 不再支援密碼登入。請選擇 **OAuth 2.0**，填入權杖網址 `https://login.microsoftonline.com/<tenant>/oauth2/v2.0/token`、用戶端 ID、用戶端密碼和 Scope `https://outlook.office365.com/.default`。應用程式須具備 `IMAP.AccessAsApp` 權限，且獲准存取此信箱。
- **不加密** 僅適用於受信任的內部網路，因為密碼會以明文透過網路傳送。
- 讀取失敗時，來源詳細資料會顯示原因，系統會在下一輪重試。若有多個警示節點，每個信箱只由一個節點讀取。啟用聯邦時，請在來源的接收叢集上設定信箱。信箱設定不會透過聯邦同步，密碼也不會離開叢集。

**傳送原始郵件**：若已有郵件系統（例如 Postfix 的 `pipe`、SES、Mailgun 的 raw MIME），請以 POST 將原始郵件傳送到接收網址：

```bash
curl -X POST 'https://<molesignal-host>/api/v1/intake/alerts' \
  -H 'Authorization: Bearer <token>' \
  -H 'Content-Type: message/rfc822' \
  --data-binary @alert.eml
```

此方式需要讓公開網路或郵件系統能存取接收網址。Token 已能識別來源，因此可以不填寄件者清單。若有填寫，系統仍會比對。

MoleSignal 未內建 SMTP 收信功能。SMTP 收信需要開放 25 連接埠、設定 MX 記錄和 TLS 憑證，還須自行攔截垃圾郵件，多數自架部署難以滿足這些條件。

**郵件解析方式**可在來源設定的 **郵件讀取規則** 中指定：

| 設定 | 說明 |
|---|---|
| **哪些主旨表示恢復** | 使用規則運算式。留白時使用內建規則：`resolved`、`recovered`、`recovery`、`cleared`、`恢复`、`已解决`，或開頭的 `OK`。其餘郵件視為觸發。 |
| **從主旨擷取去重鍵** | 使用規則運算式，取第一個擷取群組，例如 `host=(\S+)`。留白或未比對到時，使用正規化後的主旨：移除 `Re:`、`Fwd:`、狀態詞（如 `PROBLEM`、`RECOVERY`、`告警`、`恢复`）、嚴重程度、日期時間及百分比，並忽略大小寫。因此，「CRITICAL: disk full on web-1 (91%)」和「RECOVERY: disk full on web-1 (40%)」視為同一則警示，但 `web-1` 和 `web-2` 不會合併。寄件者的網域名稱也會納入去重鍵。 |
| **哪些主旨不算警示** | 使用規則運算式。系統會直接略過符合的郵件，並將其記在近期接收紀錄中。 |

系統依主旨中的詞判斷嚴重程度（`critical`、`fatal`、`disaster`、`P1` 對應 critical；`error`、`P2` 對應 error；`warning`、`P3` 對應 warning；`info`、`notice`、`P4`、`P5` 對應 info）。若無相符的詞，則使用來源的預設嚴重程度。`High CPU` 和 `Low disk` 中的 high 和 low 不列入判斷。系統會將內文寫入註解 `message`（HTML 郵件會轉為純文字，最多 4096 個字元），將寄件者寫入標籤 `email.from` 和註解 `from`，並從 `Date` 標頭取得寄送時間。自動回覆（`Auto-Submitted: auto-replied`）和退信（`multipart/report`）不視為警示。支援 GBK、GB2312 等字元集。郵件若超過 4 MiB，系統不會擷取內文，並會將郵件記為 **已拒收**。

## 外部警報如何成為事件

| 類型 | 去重鍵 | 觸發 | 解決 | 嚴重程度 |
|---|---|---|---|---|
| **API** | `dedupKey` | `trigger` | `resolve` | `severity` |
| **Alertmanager** | 外部位址加上 `groupKey` | 群組的 `status` 為 `firing` | 群組的 `status` 為 `resolved`，也就是群組內的警報都已復原 | 取群組內仍在觸發的警報中最高的 `severity` 標籤值 |
| **Grafana** | 外部位址、組織加上 `groupKey` | 同上 | 同上 | 同上 |
| **Datadog** | 站點、組織、監控 ID 加上 scope | `Recovered` 以外的狀態轉換 | `Recovered` | `$ALERT_PRIORITY`；未提供時，Warn、No Data 為 warning，其餘依 `$ALERT_TYPE` 判定 |
| **PagerDuty** | 帳號網域加上 PagerDuty 事件 ID | `incident.triggered`、`incident.reopened`；`incident.priority_updated` 調整嚴重程度 | `incident.resolved` | 優先順序 P1…P5；未提供時，緊急程度 high 為 error，low 為 warning |
| **阿里雲雲監控** | 帳號、規則 ID 加上 `dimensions`；系統事件則為帳號加上 `dedupId` | `ALERT`、`INSUFFICIENT_DATA`；系統事件為 `TRIGGERED` | `OK`；系統事件為 `RESOLVED` | `triggerLevel`；系統事件為 `severity` |
| **騰訊雲可觀測平台** | 帳號、策略、指標或事件名稱、層級和物件 | `alarmStatus` 為 `1` 或 `5` | `alarmStatus` 為 `0` | `alarmLevel` |
| **Amazon CloudWatch** | `AlarmArn` | `NewStateValue` 為 `ALARM`、`INSUFFICIENT_DATA` | `NewStateValue` 為 `OK` | 未提供，使用來源的預設嚴重程度 |
| **Zabbix** | `{$ZABBIX.URL}` 的主機名稱加上 `{EVENT.ID}` | `{EVENT.VALUE}` 為 1；更新操作也納入處理，嚴重程度隨之變更 | `{EVENT.VALUE}` 為 0，或更新操作已關閉問題 | `{EVENT.NSEVERITY}`：災難為 critical，嚴重為 error，一般嚴重和警告為 warning，資訊為 info |
| **電子郵件** | 寄件者的網域加上從主旨擷取的部分 | 其餘電子郵件 | 主旨符合復原格式 | 主旨中的詞彙 |

系統會另外讀取優先順序和緊急程度：API 的 `priority`、`urgency`，Datadog 的 `$ALERT_PRIORITY`，以及 PagerDuty 的優先順序和緊急程度，都直接用於設定事件的優先順序和緊急程度。未提供緊急程度時，依來源的升級策略判定。未回報嚴重程度的警報視為高緊急程度，請參閱[緊急程度](/zh-Hant/alerting/on-call#緊急程度)。

警報未提供嚴重程度時，使用來源的 **預設嚴重程度**。各來源的嚴重程度詞彙不區分大小寫：`critical`、`crit`、`fatal`、`page`、`P1` 為 critical，`error`、`major`、`high`、`P2` 為 error，`warning`、`warn`、`minor`、`medium`、`P3` 為 warning，`info`、`low`、`P4`、`P5` 為 info。無法辨識的值使用預設嚴重程度。

- **建立事件**：同一個來源的同一個去重鍵，同時最多只能有一個進行中的事件。事件包含 `alert.source=external` 和 `external.kind=<类型>`，也會加入警報本身的標籤（Alertmanager 與 Grafana 使用群組的 `commonLabels`）和來源的附加標籤。系統將 `service.name` 或 `service` 填入受影響服務，將 `host.name`、`host` 或 `hostname` 填入主機。
- **標題**：API 使用 `summary`；Alertmanager 與 Grafana 使用 `summary` 註解，沒有時使用 `alertname`；Datadog 使用 `$ALERT_TITLE`；PagerDuty 使用事件標題；阿里雲雲監控使用「警報名稱 · 執行個體名稱」。
- **連結**：系統將指向傳送端的位址寫入註解，例如 `alertmanager_url`、`generator_url`、`dashboard_url`、`datadog_url`、`pagerduty_url`，並在事件詳細資料中顯示為連結。API 的 `links` 依 `name` 寫入註解。
- **群組內的警報**：Alertmanager 與 Grafana 的事件會記錄群組內每筆警報（最多 100 筆）及其狀態，每收到一次通知就更新一次。事件詳細資料的 **外部警報** 區段會列出這些警報，並標示用來區分各筆警報的標籤。
- **嚴重程度變更**：尚未確認的事件會隨警報變更嚴重程度，並由[警報管線](/zh-Hant/pipelines/alert-events#嚴重程度變更)重新判定。嚴重程度升至更高層級時，升級流程會從第一步重新開始。手動設定的嚴重程度維持不變。
- **確認**：API 的 `acknowledge`、PagerDuty 的 `incident.acknowledged`，以及 Zabbix 確認問題的更新操作，都會確認事件並停止後續升級和來電。確認者欄位留空。
- **解決**：來源回報復原時，系統會解決事件，包括已確認的事件。解決者欄位留空，時間軸顯示為已復原。
- **延遲送達的舊訊息**：系統會為每個去重鍵記錄已採用的傳送端時間，直接忽略早於該時間的訊息。延遲送達的觸發訊息不會建立殭屍事件，延遲送達的復原訊息也不會關閉新事件。API 不含時間，系統依收到的順序處理。
- **事件已先解決**：如果來源仍在回報這筆警報，下次重送時會建立新事件，與規則的行為相同。
- **無資料**：阿里雲雲監控的 `INSUFFICIENT_DATA` 和 Datadog 的 No Data 所建立的事件會帶有 `alert.condition=no_data`，通知標題以 `NO DATA` 開頭。
- **停用與刪除**：停用來源後，系統會拒收該來源的警報（`409`），並保留已建立的事件。刪除來源時，該來源的 Token 立即失效，系統會解決該來源所有尚未關閉的事件。

[靜音策略](/zh-Hant/alerting/silences)、[語意分組](/zh-Hant/alerting/silences#語意分組)和[通知策略](/zh-Hant/notification-channels)同樣適用於外部事件，可依 `external.kind`、來源的附加標籤或警報本身的標籤比對。

## 近期收到的請求

來源詳細資料頁面頂端會顯示來源狀態：**等待第一筆請求**、**正常接收**、**最近一筆請求遭拒收**、**近 7 天沒有請求** 或 **已停用**。旁邊會顯示近 24 小時的請求數和警報數，以及此來源建立但尚未關閉的事件數。

來源收到請求後，詳細資料中的 **近期收到的請求** 會列出收到的請求，包含時間、結果（**已處理**、**已拒收** 或 **已轉送**）、HTTP 狀態碼、警報筆數及各筆警報的結果（**建立事件**、**更新**、**未變更**、**確認**、**復原** 或 **忽略**）。按一下任一列即可展開，查看每筆警報的標題、嚴重程度、動作、結果和對應事件。遭拒收的請求還會顯示拒收原因和請求本文的開頭（最多 16 KiB）。每個來源保留最近 500 筆請求，最長保留 7 天。

## 多個叢集

啟用[跨叢集聯邦](/zh-Hant/settings/data-plane#跨叢集聯邦)時：

- 來源和其他警報設定一樣會在叢集之間同步，Token 也會一併同步，因此每個叢集的接收位址都能使用同一個 Token。
- 系統只會在來源的 **接收叢集** 建立事件。預設為建立來源的叢集，可在來源設定中變更。其他叢集收到此來源的警報時，會透過叢集間的 gRPC 將警報轉送至接收叢集，再將接收叢集的回應傳回傳送端。因此，無論外部警報從哪個叢集的位址送入，都只會對應到一個事件。
- 無法連線至接收叢集時，系統會回傳 `503`，傳送端會重試。如果接收叢集所在區域長時間無法使用，請在來源設定中將 **接收叢集** 改為可用的叢集。
- **近期收到的請求** 記錄在處理請求的叢集上。在其他叢集開啟來源詳細資料時，頁面會說明這一點。

## 限制

| 項目 | 限制 |
|---|---|
| 請求本文、單封電子郵件 | 最大 4 MiB。 |
| 讀取信箱 | 每次最多處理 50 封，其餘留到下一輪讀取。 |
| 單次 API 請求 | 最多 100 筆警報；`dedupKey` 最多 255 個字元，`summary` 最多 1024 個字元。 |
| 單筆警報 | 最多 64 個標籤、64 個註解。超過上限時，API 會拒收，其他類型則會捨棄超出的項目。系統會截斷過長的標題和註解。 |
| 群組內的警報 | 最多記錄 100 筆。 |
| 來源的附加標籤 | 最多 32 個，不得使用以 `alert.` 開頭的鍵或 `external.kind`。 |
| 近期收到的請求 | 每個來源保留最近 500 筆請求，最長保留 7 天。 |

系統使用 Token 辨識來源，不驗證 Grafana 的 HMAC 簽章或 PagerDuty 的簽章。在 MoleSignal 中確認或解決事件，不會將結果回寫至傳送端。
