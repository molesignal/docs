告警來源讓其他系統送來的警示也能建立成[事件](/zh-Hant/alerting/incidents)，與規則建立的事件一樣依[升級策略](/zh-Hant/alerting/on-call#升級策略)通知人員、依[通知策略](/zh-Hant/notification-channels)傳送通知，來源回報恢復時自動解決。開啟 **警示 → 告警來源**。檢視需要 `alerts.sources.read`，新增、修改、刪除和更換 Token 需要 `alerts.sources.manage`。

## 來源類型

每個來源有一個類型，類型決定依哪家的格式讀取請求內容。

| 類型 | 傳送方 | 一個事件對應 |
|---|---|---|
| **API** | 指令碼、CI、自研系統，呼叫 MoleSignal 的介面 | 一個去重鍵 |
| **Alertmanager** | Prometheus Alertmanager 的 webhook 接收器 | 一個通知群組 |
| **Grafana** | Grafana 警示的 Webhook 聯絡點 | 一個通知群組 |
| **Datadog** | Datadog 的 Webhooks 整合 | 一個監控；多警示監控的每個群組各一個 |
| **PagerDuty** | PagerDuty 的 Webhook（v3）訂閱 | 一個 PagerDuty 事件 |
| **阿里雲雲監控** | 閾值警示回呼、事件訂閱的推送管道 | 一條警示規則下的一個物件，或一條系統事件 |
| **騰訊雲可觀測平台** | 通知範本裡的介面回呼 | 一條策略下一個物件的一個指標或事件，分級別的每個等級各一個 |
| **Amazon CloudWatch** | 警示傳送到 SNS 主題，主題的 HTTPS 訂閱 | 一個警示 |
| **Zabbix** | Zabbix 的 Webhook 媒介類型 | 一個問題 |
| **Azure Monitor** | 動作群組的 Webhook 動作，使用一般警示結構描述 | 一個警示 |
| **Google Cloud Monitoring** | Webhook 通知管道，或經推送訂閱的 Pub/Sub 通知管道 | 一個 Monitoring 事件 |
| **華為雲雲監控** | 警示傳送到 SMN 主題，主題的 HTTPS 訂閱 | 一條警示規則下的一個資源 |
| **電子郵件** | 一個 IMAP 信箱，或既有郵件系統轉來的原始郵件 | 主旨相同的一串郵件 |

相容於 Alertmanager webhook 的系統，例如 Thanos、Cortex、Mimir 的 Alertmanager，以 **Alertmanager** 類型接入。

## 新增來源

1. 開啟 **警示 → 告警來源**，點選 **新增警示來源**。
2. 選擇 **類型**，填寫 **名稱**。
3. 選擇 **升級策略**。預設是 **依路由分派（預設）**，與規則工作台相同：[警示路由](/zh-Hant/alerting/routing)依路由規則、服務的負責團隊和 team 標籤選出團隊和升級策略，都沒有時使用名為 `default` 的[預設策略](/zh-Hant/alerting/on-call#預設策略)。選擇某條策略時，事件會使用該策略，路由只決定團隊。選擇 **不升級，只依通知策略傳送通知** 時，事件照常開啟和通知，只是不會依升級策略通知人員。
4. 選擇 **預設嚴重程度**：警示本身未帶嚴重程度時使用這一級。
5. 視需要新增 **附加標籤**，例如 `team=payments`。這些標籤會加在此來源建立的每個事件上，警示本身帶有同名標籤時以警示的為準。
6. 點選 **建立**。頁面會開啟來源詳細資料，並彈出這個來源的 Token 和已填入 Token 的設定；阿里雲雲監控只需要接入位址，彈出的是帶 Token 的接入位址。

<Warning>
  Token 只在新增和更換時顯示這一次。關閉彈出視窗後只能看到 `mspat-` 開頭的前綴；忘記了就點選 **更換 Token** 換一個，舊 Token 立即失效。
</Warning>

## 接入位址與 Token

所有來源共用一個接入位址，Token 決定是哪個來源：

```text
https://<molesignal-host>/api/v1/intake/alerts
```

Token 形如 `mspat-<36 位>`，與 API Token 的樣子相同，但只能用來接入警示，API Token 也不能用來接入警示。傳送方將它放在請求標頭裡：

```text
Authorization: Bearer <token>
```

無法設定請求標頭的傳送方（阿里雲雲監控、騰訊雲可觀測平台、經 SNS 的 Amazon CloudWatch、Azure Monitor、Google Cloud Monitoring、經 SMN 的華為雲雲監控）將 Token 放在位址上：`https://<molesignal-host>/api/v1/intake/alerts?token=<token>`。

傳送方要能存取這個位址。MoleSignal 前面有防火牆時，依傳送方所在的站點或區域放行它的出口 IP：Datadog 每個站點的 IP 清單在 `ip-ranges` 的 `webhooks` 一節，PagerDuty 依美國區和歐洲區分別公布，阿里雲雲監控的推送網段請見它的警示回呼文件。MoleSignal 部署在內網時，只將這個位址開放至公網的做法請見[公網存取](/zh-Hant/public-access)。

## 設定傳送方

來源詳情的 **接收方式** 會分三步提供每種類型的接收位址、Token 和設定，`<TOKEN>` 處填入這個來源的 Token。這個來源收到第一個請求後，三步都會打勾。

### API

```bash
curl -X POST https://<molesignal-host>/api/v1/intake/alerts \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{"dedupKey": "disk-full/web-1", "summary": "web-1 磁盘使用率 95%", "severity": "critical", "labels": {"host.name": "web-1"}}'
```

`action` 為 `trigger`（預設）、`acknowledge` 或 `resolve`。使用同一個 `dedupKey` 確認、恢復同一則警示。欄位請見[接收外部警示](/zh-Hant/api/alerting/send-alerts)。

### Alertmanager

在 `alertmanager.yml` 中新增一個接收器，並在路由中將警示交給它：

```yaml
route:
  receiver: molesignal
receivers:
  - name: molesignal
    webhook_configs:
      - url: https://<molesignal-host>/api/v1/intake/alerts
        send_resolved: true
        http_config:
          authorization:
            credentials: <token>
```

`send_resolved` 要保持 `true`，否則恢復不會送過來。同一個 Alertmanager 叢集的各個副本要設定同一個 `--web.external-url`：外部位址是去重鍵的一部分，幾個 region 的 Alertmanager 使用同一套路由時，同名的群組也不會合併成一個事件。

### Grafana

1. 在 Grafana 中開啟 **Alerting → Contact points**，點擊 **Add contact point**。
2. **Integration** 選 **Webhook**，**URL** 填接收位址。
3. 在 **Optional Webhook settings** 中，**Authentication Header Scheme** 填 `Bearer`，**Authentication Header Credentials** 填 Token。
4. 不要勾選 **Disable resolved message**，儲存後在通知策略中使用這個聯絡點。

使用設定檔管理時：

```yaml
apiVersion: 1
contactPoints:
  - orgId: 1
    name: molesignal
    receivers:
      - uid: molesignal
        type: webhook
        settings:
          url: https://<molesignal-host>/api/v1/intake/alerts
          httpMethod: POST
          authorization_scheme: Bearer
          authorization_credentials: <token>
```

### Datadog

1. 在 Datadog 中開啟 **Integrations → Webhooks**，新建一個 Webhook，名稱例如 `molesignal`。
2. **URL** 填接收位址，**Custom Headers** 填 `{"Authorization": "Bearer <token>"}`，不要勾選 **Encode as form**。
3. **Payload** 填下面的範本。欄位名稱是 MoleSignal 的，值是 Datadog 的變數；不是這個範本的請求會被拒收。

```json
{
  "alert_id": "$ALERT_ID",
  "alert_cycle_key": "$ALERT_CYCLE_KEY",
  "transition": "$ALERT_TRANSITION",
  "alert_type": "$ALERT_TYPE",
  "priority": "$ALERT_PRIORITY",
  "title": "$ALERT_TITLE",
  "event_title": "$EVENT_TITLE",
  "message": "$TEXT_ONLY_MSG",
  "scope": "$ALERT_SCOPE",
  "tags": "$TAGS",
  "hostname": "$HOSTNAME",
  "link": "$LINK",
  "snapshot": "$SNAPSHOT",
  "query": "$ALERT_QUERY",
  "org_id": "$ORG_ID",
  "last_updated": "$LAST_UPDATED"
}
```

4. 在監控的通知訊息中寫 `@webhook-molesignal`。

各個 Datadog 網站（`datadoghq.com`、`datadoghq.eu`、`us3`、`us5`、`ap1` 等）都可以傳送到同一個來源：網站取自 `$LINK` 的網域，與組織 ID 一起計入去重鍵。

### PagerDuty

1. 在 PagerDuty 中開啟 **Integrations → Generic Webhooks (v3)**，點擊 **New Webhook**。
2. **Webhook URL** 填接收位址，視需要選擇 **Scope Type**（整個帳號、某個服務或某個團隊）。
3. **Event Subscription** 勾選 `incident.triggered`、`incident.acknowledged`、`incident.resolved`、`incident.reopened` 和 `incident.priority_updated`。
4. 新增自訂請求標頭 `Authorization`，值為 `Bearer <token>`。

美國區和歐洲區的帳號都可以傳送到同一個來源：帳號網域（`<子域>.pagerduty.com` 或 `<子域>.eu.pagerduty.com`）會計入去重鍵，並寫入標籤 `pagerduty.region`。

### 阿里雲雲監控

接收位址帶上 Token：

```text
https://<molesignal-host>/api/v1/intake/alerts?token=<token>
```

- **閾值警示**：在警示規則的 **警示回呼** 中填寫這個位址。雲監控以表單編碼 POST 回呼，MoleSignal 也接受 JSON。
- **系統事件**：在 **事件中心 → 事件訂閱 → 推送管道** 中新建管道，**目標類型** 選 **Webhook**，**請求方式** 選 **POST**，**資料格式** 選 **JSON**，位址填上面這個位址，再在訂閱策略中使用這個管道。

雲監控的系統事件回呼只等 5 秒、失敗重試 3 次。MoleSignal 轉送到[接收叢集](#多個叢集)最多等 3 秒，逾時回應 `503`，讓雲監控重試。中國站和國際站、各個區域的回呼格式相同；區域會寫入標籤 `aliyun.region`，帳號 `userId` 會計入去重鍵。

### 騰訊雲可觀測平台

在騰訊雲可觀測平台（原雲監控）的 **警示管理 → 通知範本** 編輯或新建範本，將接收位址填入 **介面回呼**，再把範本綁定到警示策略上。騰訊雲的回呼無法設定請求標頭，Token 寫在位址裡，這個位址要當作憑證保管：回呼沒有簽章，靠它辨識來源。指標警示和事件警示都能接收，觸發和恢復都會推送。

- **去重**：帳號、警示策略、指標或事件名稱和警示對象相同的是同一個警示。有分等級的策略，每個等級一個事件，跟騰訊雲一樣各自恢復。
- **嚴重程度**：`alarmLevel` 的緊急（`Serious`）為 critical，嚴重（`Warn`）為 error，提示（`Remind`）為 info；不分等級的策略使用來源的預設嚴重程度。
- **無狀態的事件**（`alarmStatus` 為 `5`）開啟事件後不會等到恢復，需要人工解決。
- **時間**：回呼的時間不帶時區，以北京時間計算。

### Amazon CloudWatch

CloudWatch 警示不直接呼叫外部位址，要經由 SNS：

1. 在警示的通知中，將進入 **警示**（`ALARM`）和回到 **正常**（`OK`）都傳送到同一個 SNS 主題。沒有 `OK` 時事件不會自動解決。要接收無資料警示，也把 **資料不足**（`INSUFFICIENT_DATA`）傳送過去。
2. 為主題新增一個 HTTPS 訂閱，端點填接收位址，Token 寫在位址裡：

   ```bash
   aws sns subscribe \
     --topic-arn <主题的 ARN> \
     --protocol https \
     --notification-endpoint 'https://<molesignal-host>/api/v1/intake/alerts?token=<token>'
   ```

3. 訂閱會自動確認：MoleSignal 驗證確認訊息的簽章後，會存取它的 `SubscribeURL`。

MoleSignal 會驗證每則 SNS 訊息的簽章，所以 **Raw message delivery** 要維持關閉；開啟後會被拒收，來源詳情的最近收到中會寫明原因。驗證簽章要從 `sns.<region>.amazonaws.com` 取得憑證，接收請求的節點要能存取這個位址。

CloudWatch 的警示沒有嚴重程度，事件會使用來源的預設嚴重程度。警示的 ARN 是去重鍵，複合警示也一樣。警示的說明和狀態變更原因會放入註解，區域、帳號、命名空間、指標和維度會放入標籤，`aws.region` 這類標籤可用於路由。

### Azure Monitor

Azure Monitor 的警示會經由動作群組的 Webhook 動作傳送過來：

1. 在警示規則使用的動作群組中新增一個 **Webhook** 類型的動作，URI 填接收位址，Token 寫在位址裡。
2. **啟用通用警示結構** 選 **是**。不開啟會被拒收，來源詳情的最近收到中會寫明原因。

使用 Azure CLI 時如下：

```bash
az monitor action-group update \
  --resource-group <资源组> \
  --name <操作组> \
  --add-action webhook molesignal 'https://<molesignal-host>/api/v1/intake/alerts?token=<token>' usecommonalertschema
```

- **去重**：警示的 `alertId` 是去重鍵，其中包含 Azure 訂閱。
- **觸發與解決**：`monitorCondition` 為 `Fired` 時開啟事件，為 `Resolved` 時解決。活動記錄警示這類不記錄狀態的警示只會觸發，需要人工解決。
- **嚴重程度**：`Sev0` 為 critical，`Sev1` 為 error，`Sev2` 為 warning，`Sev3`、`Sev4` 為 info。
- **標籤**：警示規則的自訂屬性、指標維度，以及 `azure.subscription_id`、`azure.resource_group`、`azure.resource`、`azure.signal_type`、`azure.monitoring_service`、`azure.metric`。說明、條件、目前值和目標資源會放入註解，調查連結會寫成 `azure_url`。

### Google Cloud Monitoring

1. 在 Google Cloud 控制台開啟 **Monitoring → Alerting → Edit notification channels**，新建 **Webhook** 管道，**Endpoint URL** 填接收位址，Token 寫在位址裡。
2. 將管道加到警示政策的通知中。事件關閉時也會通知，事件會自動解決。

**Pub/Sub** 管道發布的是同一份通知。要使用它，就在它的主題上建立推送訂閱，推送端點填接收位址；MoleSignal 會解開 Pub/Sub 的信封。

- **去重**：範圍專案加上 `incident_id`，一個 Monitoring 事件對應一個事件。
- **觸發與解決**：`state` 為 `open` 時開啟事件，為 `closed` 時解決。
- **嚴重程度**：警示政策設定的嚴重等級 `Critical`、`Error`、`Warning`；未設定的使用來源的預設嚴重程度。
- **標籤**：資源和指標的標籤、警示政策和受監控資源的使用者標籤，以及 `gcp.project_id`、`gcp.resource_type`、`gcp.metric`、`gcp.policy`。摘要、條件、觀測值、閾值和文件會放入註解，事件的控制台位址會寫成 `gcp_url`。

### 華為雲雲監控

雲監控（CES）的警示不直接呼叫外部位址，要經由訊息通知服務 SMN：

1. 在 SMN 中為一個主題新增訂閱，通訊協定選 **HTTPS**，訂閱端點填接收位址，Token 寫在位址裡。
2. 訂閱會自動確認：MoleSignal 驗證確認訊息的簽章後，會存取它的 `subscribe_url`。
3. 在雲監控警示規則的警示通知中選擇這個主題，警示和恢復都要通知。不通知恢復時，事件不會自動解決。

MoleSignal 會驗證每則 SMN 訊息的簽章。驗證簽章要從 `smn.<region>.myhuaweicloud.com` 取得憑證，接收請求的節點要能存取這個位址。

- **去重**：主題所在的專案、警示規則的 `alarm_id` 加上資源。一條規則監控多個資源時，每個資源一個事件。
- **觸發與解決**：`alarm_status` 為 `alarm` 時開啟事件，為 `insufficient_data` 時依無資料開啟事件，為 `ok` 時解決。
- **嚴重程度**：警示等級的緊急為 critical，重要為 error，次要為 warning，提示為 info。
- **標籤**：維度（例如 `instance_id`），以及 `huawei.region`、`huawei.project_id`、`huawei.namespace`、`huawei.metric`、`huawei.alarm_id`、`huawei.resource_id`。警示內容、目前值和閾值會放入註解，警示的控制台位址會寫成 `huawei_url`。

### Zabbix

Zabbix 6.0 起都能使用。Zabbix 不定義請求主體，由媒體類型中的指令碼送出，所以來源詳情（和新建時的彈出視窗）會提供一份填好位址和 Token 的媒體類型：

1. 將它儲存成 YAML，在 **Alerts → Media types → Import** 匯入，確認 `token` 參數。
2. 設定好全域巨集 `{$ZABBIX.URL}`（Zabbix 前端的位址）。它會計入去重鍵，一個來源接收幾台 Zabbix 時不會衝突，事件上也能連結回 Zabbix；未設定也能使用。
3. 為一個使用者加上這個媒體，**傳送至** 隨意填寫（指令碼不會用到它）。
4. 新建一個觸發器動作：**操作**、**復原操作** 和 **更新操作** 都傳送給這個使用者。沒有復原操作，事件不會自動解決。

媒體類型的 **測試** 按鈕要填真實的值：巨集未展開時（`{EVENT.ID}` 原樣送來）MoleSignal 會回應 `400`，表示要使用文件提供的媒體類型。

### 郵件

有兩種接收方式，都會讀成相同的警示。

**讀取信箱**（建議）：MoleSignal 會定時讀取一個 IMAP 信箱。只要連得出去、有一個信箱，不用公網位址、MX 記錄、25 連接埠和憑證，所以自託管時最省事。將監控系統的警示郵件傳送到這個信箱，或用郵件規則轉送過去。

在來源詳情的 **讀取信箱** 填寫 **IMAP 伺服器**、**連接埠**、**加密**、**使用者名稱**、**密碼或授權碼**、**資料夾**（預設 `INBOX`）和 **多久讀取一次**（15 到 3600 秒，預設 60），點擊 **測試連線**，再點擊 **儲存信箱設定**。

- **唯讀**：使用 `EXAMINE` 和 `BODY.PEEK[]`，不會變更已讀狀態，也不會刪除郵件。可以給它一個唯讀的帳號。
- **不讀取既有郵件**：第一次連線時記下當下的位置，只讀取這之後送達的郵件。更換主機、帳號或資料夾，或伺服器重新排序信箱（`UIDVALIDITY` 變更）時，都會重新從當時開始。來源停用期間不讀取、也不保留位置，重新啟用後從那時開始。
- **寄件者名單必填**：知道位址的人都能寄信到信箱。在來源設定的 **接受哪些寄件者** 填寫完整位址或 `@example.com` 整個網域；要接受任何人就寫 `*`。名單看的是 `From`，它可以被偽造：信箱服務商的垃圾郵件防護和 DMARC 仍要開啟。不在名單上的郵件會記錄成 **已拒收**，不會開啟事件。
- **登入方式**：密碼，或信箱服務提供的授權碼、應用程式專用密碼。Microsoft 365 不再接受密碼登入，選 **OAuth 2.0**，填寫權杖位址 `https://login.microsoftonline.com/<tenant>/oauth2/v2.0/token`、用戶端 ID、用戶端密碼和 Scope `https://outlook.office365.com/.default`，應用程式要有 `IMAP.AccessAsApp` 權限並被授予這個信箱的存取權。
- **不加密** 只該用在可信任的內部網路：密碼會以明文傳輸。
- 讀取失敗時，來源詳情會寫明原因，下一輪再試。有多個警示節點時，每個信箱由一個節點負責讀取。開啟聯邦時，信箱設定在來源的接收叢集上，不隨聯邦同步，密碼不會離開叢集。

**將原始郵件傳送過來**：已有郵件系統（Postfix 的 `pipe`、SES、Mailgun 的 raw MIME）時，將原始郵件 POST 到接收位址：

```bash
curl -X POST 'https://<molesignal-host>/api/v1/intake/alerts' \
  -H 'Authorization: Bearer <token>' \
  -H 'Content-Type: message/rfc822' \
  --data-binary @alert.eml
```

這種接收方式需要公網（或郵件系統）能存取接收位址，寄件者名單可以留空，Token 已經辨識出來源；有填寫也仍會檢查。

沒有內建 SMTP 收信：它要開啟 25 連接埠、設定 MX 記錄和 TLS 憑證，還要自行阻擋垃圾郵件，自託管的部署大多過不了這一關。

**一封郵件如何讀取**，寫在來源設定的 **郵件讀取規則** 裡：

| 設定 | 說明 |
|---|---|
| **哪些主旨表示恢復** | 正規表示式。留空時使用內建的：`resolved`、`recovered`、`recovery`、`cleared`、`恢复`、`已解决`，以及開頭的 `OK`。其餘郵件視為觸發。 |
| **從主旨擷取去重鍵** | 正規表示式，取第一個擷取群組，例如 `host=(\S+)`。留空或未相符時，使用整理後的主旨：移除 `Re:`、`Fwd:`、狀態詞（`PROBLEM`、`RECOVERY`、`告警`、`恢复` 等）、嚴重程度、日期時間和百分比，且不區分大小寫。因此「CRITICAL: disk full on web-1 (91%)」和「RECOVERY: disk full on web-1 (40%)」是同一個警示，`web-1` 和 `web-2` 不是。寄件者的網域也會計入去重鍵。 |
| **哪些主旨不算警示** | 正規表示式。相符的郵件會直接略過，並記錄在最近收到中。 |

嚴重程度依主旨中的詞彙判定（`critical`、`fatal`、`disaster`、`P1` 為 critical，`error`、`P2` 為 error，`warning`、`P3` 為 warning，`info`、`notice`、`P4`、`P5` 為 info），沒有時使用來源的預設嚴重程度；`High CPU`、`Low disk` 中的 high、low 不算。內文會放入註解 `message`（HTML 郵件會轉成文字，最多 4096 個字元），寄件者會放入標籤 `email.from` 和註解 `from`，寄件時間取自 `Date` 標頭。自動回覆（`Auto-Submitted: auto-replied`）和退信（`multipart/report`）不算警示。GBK、GB2312 等字元集都支援。超過 4 MiB 的郵件不會擷取內文，會記錄成 **已拒收**。

## 外部警報如何變成事件

| 類型 | 去重鍵 | 觸發 | 解決 | 嚴重程度 |
|---|---|---|---|---|
| **API** | `dedupKey` | `trigger` | `resolve` | `severity` |
| **Alertmanager** | 外部位址加 `groupKey` | 分組的 `status` 為 `firing` | 分組的 `status` 為 `resolved`，即分組裡的警報都復原了 | 分組裡正在觸發的警報的 `severity` 標籤，取最高一級 |
| **Grafana** | 外部位址、組織加 `groupKey` | 同上 | 同上 | 同上 |
| **Datadog** | 站點、組織、監控 ID 加 scope | `Recovered` 以外的轉換 | `Recovered` | `$ALERT_PRIORITY`；沒有時 Warn、No Data 為 warning，其餘依 `$ALERT_TYPE` |
| **PagerDuty** | 帳號網域加 PagerDuty 事件 ID | `incident.triggered`、`incident.reopened`；`incident.priority_updated` 調整嚴重程度 | `incident.resolved` | 優先級 P1…P5；沒有時緊急度 high 為 error，low 為 warning |
| **阿里雲雲監控** | 帳號、規則 ID 加 `dimensions`；系統事件為帳號加 `dedupId` | `ALERT`、`INSUFFICIENT_DATA`；系統事件 `TRIGGERED` | `OK`；系統事件 `RESOLVED` | `triggerLevel`；系統事件 `severity` |
| **騰訊雲可觀測平台** | 帳號、策略、指標或事件名稱、等級和物件 | `alarmStatus` 為 `1` 或 `5` | `alarmStatus` 為 `0` | `alarmLevel` |
| **Amazon CloudWatch** | `AlarmArn` | `NewStateValue` 為 `ALARM`、`INSUFFICIENT_DATA` | `NewStateValue` 為 `OK` | 沒有時使用來源的預設嚴重程度 |
| **Azure Monitor** | `alertId` | `monitorCondition` 為 `Fired` | `monitorCondition` 為 `Resolved` | `severity`：`Sev0` 為 critical，`Sev1` 為 error，`Sev2` 為 warning，`Sev3`、`Sev4` 為 info |
| **Google Cloud Monitoring** | 範圍專案加 `incident_id` | `state` 為 `open` | `state` 為 `closed` | `severity`；`No severity` 用來源的預設嚴重程度 |
| **華為雲雲監控** | SMN 主題所在的專案、`alarm_id` 加資源 | `alarm_status` 為 `alarm`、`insufficient_data` | `alarm_status` 為 `ok` | 警報等級：緊急、重要、次要、提示 |
| **Zabbix** | `{$ZABBIX.URL}` 的主機名稱加 `{EVENT.ID}` | `{EVENT.VALUE}` 為 1；更新操作也算，嚴重程度跟著變 | `{EVENT.VALUE}` 為 0，或更新操作關閉了問題 | `{EVENT.NSEVERITY}`：災難為 critical，嚴重為 error，一般嚴重和警告為 warning，資訊為 info |
| **電子郵件** | 寄件人的網域加主旨裡取出的部分 | 其餘的電子郵件 | 主旨符合復原的寫法 | 主旨裡的詞 |

優先級和緊急度另外讀取：API 的 `priority`、`urgency`，Datadog 的 `$ALERT_PRIORITY`，PagerDuty 的優先級和緊急度直接成為事件的優先級和緊急度；未提供緊急度時依來源的升級策略決定，未回報嚴重程度的警報會以高緊急度處理，請見[緊急度](/zh-Hant/alerting/on-call#緊急程度)。

警報本身未帶嚴重程度時，使用來源的 **預設嚴重程度**。各家的嚴重程度用詞不分大小寫：`critical`、`crit`、`fatal`、`page`、`P1` 為 critical，`error`、`major`、`high`、`P2` 為 error，`warning`、`warn`、`minor`、`medium`、`P3` 為 warning，`info`、`low`、`P4`、`P5` 為 info，無法辨識時使用預設嚴重程度。

- **建立事件**：同一個來源、同一個去重鍵同時最多只會有一個進行中的事件。事件帶有標籤 `alert.source=external` 和 `external.kind=<類型>`，加上警報本身的標籤（Alertmanager 與 Grafana 為分組的 `commonLabels`）和來源的附加標籤。標籤 `service.name` 或 `service` 會歸入受影響服務，`host.name`、`host` 或 `hostname` 會歸入主機。
- **標題**：API 使用 `summary`；Alertmanager 與 Grafana 使用 `summary` 註解，沒有時使用 `alertname`；Datadog 使用 `$ALERT_TITLE`；PagerDuty 使用事件標題；阿里雲雲監控為「警報名稱 · 執行個體名稱」。
- **連結**：回到傳送方的位址會寫進註解，例如 `alertmanager_url`、`generator_url`、`dashboard_url`、`datadog_url`、`pagerduty_url`，事件詳細資料會將它們顯示為連結。API 的 `links` 依 `name` 寫進註解。
- **分組裡的警報**：Alertmanager 與 Grafana 的事件會記住分組裡的每條警報（最多 100 條）和它們的狀態，每收到一次通知就更新一次，事件詳細資料的 **外部警報** 一節會列出它們，並標出區分它們的標籤。
- **嚴重程度變化**：尚未確認的事件的嚴重程度會跟著警報變動，經[警報管線](/zh-Hant/pipelines/alert-events#嚴重程度變更)重新判定；升到更高一級時，升級會從第一步重新開始。手動設定過的嚴重程度保持不變。
- **確認**：API 的 `acknowledge`、PagerDuty 的 `incident.acknowledged` 和 Zabbix 確認問題的更新操作會確認事件，停止後續升級和來電。確認人為空。
- **解決**：來源回報復原時解決事件，已確認的事件也會一併解決。解決人為空，時間軸顯示為已復原。
- **晚到的舊訊息**：每個去重鍵會記住用過的傳送方時間，比它早的訊息直接忽略。遲到的觸發不會建立殭屍事件，遲到的復原也不會關閉新事件。API 不帶時間，依收到的先後順序處理。
- **有人先解決了**：來源還在回報這條警報時，下一次重送會建立一個新事件，行為與規則相同。
- **無資料**：阿里雲雲監控的 `INSUFFICIENT_DATA`、華為雲雲監控的 `insufficient_data`、Datadog 的 No Data 所建立的事件帶有 `alert.condition=no_data`，通知標題以 `NO DATA` 開頭。
- **停用與刪除**：停用的來源會拒收警報（`409`），已建立的事件會保留。刪除來源時，它的 Token 立即失效，它開著的事件都會被解決。

[靜默策略](/zh-Hant/alerting/silences)、[語意分組](/zh-Hant/alerting/silences#語意分組)和[通知策略](/zh-Hant/notification-channels)對外部事件照常生效，可以依 `external.kind`、來源的附加標籤或警報本身的標籤進行比對。

## 最近收到

來源詳細資料的頂部寫著這個來源的狀態：**等待第一筆請求**、**正常接收**、**最近一筆請求遭拒收**、**近 7 天沒有請求** 或 **已停用**，旁邊是近 24 小時的請求數和警報數，以及這個來源建立、尚未關閉的事件數。

收到過請求後，來源詳細資料的 **最近收到** 列出這個來源收到的請求：時間、結果（**已處理**、**已拒收** 或 **已轉送**）、HTTP 狀態碼、警報筆數和各筆的結果（**建立事件**、**更新**、**未變更**、**確認**、**復原** 或 **忽略**）。點選一列展開，查看每筆警報的標題、嚴重程度、動作、結果和對應事件；遭拒收的請求還會顯示原因和請求主體開頭（最多 16 KiB）。每個來源保留最近 500 筆請求，最長 7 天。

## 多個叢集

開啟了[跨叢集聯邦](/zh-Hant/settings/data-plane#跨叢集聯邦)時：

- 來源和其他警報設定一樣會在叢集之間同步，Token 也會一起同步，所以同一個 Token 在每個叢集的接入位址上都能使用。
- 一個來源的事件只會在它的 **接收叢集** 上建立，預設是建立它的叢集，可以在來源設定中變更。其他叢集收到這個來源的警報時，會經由叢集之間的 gRPC 轉給接收叢集，再把接收叢集的回覆傳回給傳送方。所以一條外部警報無論從哪個叢集的位址進來，都只會對應一個事件。
- 接收叢集連不上時會回傳 `503`，傳送方會重試。接收叢集所在的區域長時間無法使用時，在來源設定中把 **接收叢集** 改成可用的叢集。
- **最近收到** 會記錄在處理請求的叢集上。在其他叢集開啟來源詳細資料時會說明這一點。

## 限制

| 項目 | 限制 |
|---|---|
| 請求主體、一封電子郵件 | 最大 4 MiB。 |
| 讀取信箱 | 一次最多處理 50 封，多出的下一輪繼續讀取。 |
| API 一次請求 | 最多 100 筆警報；`dedupKey` 最多 255 個字元，`summary` 最多 1024 個字元。 |
| 一筆警報 | 最多 64 個標籤、64 個註解；API 超出時會拒收，其他類型多出的會丟棄，過長的標題和註解會截斷。 |
| 分組裡的警報 | 最多記錄 100 筆。 |
| 來源的附加標籤 | 最多 32 個，不能使用以 `alert.` 開頭的鍵和 `external.kind`。 |
| 最近收到 | 每個來源最近 500 筆請求，最長 7 天。 |

不驗證 Grafana 的 HMAC 簽章和 PagerDuty 的簽章，Token 已經識別出來源。在 MoleSignal 裡確認、解決事件不會回寫到傳送方。
