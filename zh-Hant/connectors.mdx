**連接器**是與外部平台的託管整合，分兩個方向：

- **來源**從其他服務接入資料並寫入資料流。CloudWatch Logs、Kafka 主題和 S3 物件由 MoleSignal 定時拉取；Amazon Data Firehose、Google Cloud Pub/Sub、Cloudflare Logpush、Heroku 推送給 MoleSignal，其中 Firehose 也能帶來 CloudWatch 指標。
- **目標**接收[定時管線](/zh-Hant/pipelines#目標與連接器出口)的產出：Amazon S3 及 S3 相容儲存、Apache Kafka，以及任意 HTTP 端點。

| Kind | 連接器 | 方向 | 驗證 |
|---|---|---|---|
| `aws_cloudwatch_logs` | AWS CloudWatch Logs | 來源，每 30 秒拉取一次 | [AWS 憑證](#aws-認證) |
| `kafka_source` | Kafka 主題 | 來源，每 30 秒拉取一次 | 無、SASL 或用戶端憑證 |
| `s3_source` | S3 物件 | 來源，每 30 秒拉取一次 | AWS 憑證 |
| `gcp_pubsub_pull` | Google Cloud Pub/Sub 訂閱 | 來源，每 30 秒拉取一次 | 服務帳號金鑰 |
| `aws_cloudwatch_metrics`、`azure_monitor_metrics`、`gcp_monitoring_metrics`、`aliyun_cms_metrics`、`tencent_monitor_metrics`、`huawei_ces_metrics` | [雲端監控指標](#雲端監控指標) | 來源，每個週期拉取一次 | 雲端平台的憑證 |
| `aws_kinesis_firehose` | Amazon Data Firehose | 來源，推送 | [推送 Token](#推送來源) |
| `gcp_pubsub_push` | Google Cloud Pub/Sub 推送 | 來源，推送 | 推送 Token，可再驗證訂閱的 OIDC Token |
| `cloud_events` | 雲端事件匯流排 | 來源，推送 | 推送 Token |
| `cloudflare_logpush` | Cloudflare Logpush | 來源，推送 | 推送 Token |
| `heroku_drain` | Heroku 日誌 Drain | 來源，推送 | 推送 Token |
| `s3` | Amazon S3 | 目標 | AWS 憑證 |
| `kafka` | Apache Kafka | 目標 | 無、SASL 或用戶端憑證 |
| `http` | HTTP / Webhook | 目標 | 無、Bearer Token、Basic 驗證、自訂請求標頭或 HMAC 簽章 |

## 建立連接器

<Steps>
  <Step title="開啟連接器頁面">
    進入 **管線 → 連接器**。頁面分 **來源** 和 **目標** 兩部分列出連接器。
  </Step>
  <Step title="選擇類型">
    點擊 **新增連接器**，選擇要連線到哪裡。
  </Step>
  <Step title="填寫設定">
    填寫在組織內唯一的 **名稱**，填寫讀取或投遞的位置，並選擇 **驗證方式**。
  </Step>
  <Step title="測試並建立">
    點擊 **測試連線**，在儲存前試用目前設定，然後點擊 **建立連接器**。推送來源沒有可連線的物件，不提供測試。
  </Step>
</Steps>

透過 API 建立時，連接器由 `name`、`kind` 和 `configJson` 組成，`configJson` 的鍵隨 kind 而定。`configJson` 中的 `auth` 指定驗證方式，每種方式有各自的鍵。無法生效的設定在儲存時傳回 `400`：缺少必填的鍵、成對的憑證只填了一半，或填了所選 `auth` 用不到的鍵。

```bash
curl -X POST http://localhost:5080/api/v1/connectors \
  -H "authorization: Bearer $MS_TOKEN" \
  -H 'content-type: application/json' \
  -d '{
        "name": "archive",
        "kind": "s3",
        "configJson": {
          "bucket": "acme-logs",
          "region": "eu-west-1",
          "prefix": "pipelines/checkout/",
          "auth": "assume_role",
          "roleArn": "arn:aws:iam::123456789012:role/molesignal-delivery"
        }
      }'
```

## 密鑰

`configJson` 中以下鍵保存的是密鑰：

| Kind | 密鑰鍵 |
|---|---|
| `s3`、`aws_cloudwatch_logs` | `accessKey`、`secretKey`、`sessionToken` |
| `aws_kinesis_firehose`、`gcp_pubsub_push`、`cloud_events`、`cloudflare_logpush`、`heroku_drain` | `pushToken` |
| `aws_cloudwatch_metrics` | `accessKey`、`secretKey`、`sessionToken` |
| `azure_monitor_metrics` | `clientSecret` |
| `gcp_monitoring_metrics`、`gcp_pubsub_pull` | `serviceAccountKey` |
| `aliyun_cms_metrics`、`tencent_monitor_metrics`、`huawei_ces_metrics` | `accessKey`、`secretKey` |
| `kafka` | `saslPassword`、`tlsClientKey` |
| `http` | `url`、`bearerToken`、`basicPassword`、`headerValue`、`hmacSecret` |

密鑰不會透過 API 傳回。回應中密鑰顯示為 `***`，`secretKeys` 列出已儲存值的密鑰：

```json
{
  "kind": "kafka",
  "configJson": {
    "brokers": "b-1.example.com:9096",
    "topic": "logs",
    "tls": true,
    "auth": "sasl_scram_sha_512",
    "saslUsername": "molesignal",
    "saslPassword": "***"
  },
  "secretKeys": ["saslPassword"]
}
```

- 更新時原樣傳回 `***` 表示保留已儲存的值。因此重新命名、停用連接器或修改投遞位置時，不必重新填寫憑證。介面上留空的已儲存密鑰同樣保持不變。
- 更新時未包含的密鑰會被刪除。
- 更新時變更了 `kind`，已儲存的密鑰一個都不保留。

MoleSignal 用 `MS_CIPHER_KEY` 中的根密鑰（AES-256-GCM）把密鑰與其餘設定分開密封，不以明文儲存任何密鑰。推送來源會依其 Token 的 SHA-256 查找。輪換根密鑰時，`molesignal rewrap-kek` 會把連接器密鑰與其他密文一起重新密封，參見[生產檢查清單](/zh-Hant/deployment/production-checklist)。

## 來源

### 推送來源

五種推送來源共用一套模型：建立帶 **`pushToken`** 和 **`targetStream`** 的連接器，再把平台指向對應的端點。這些端點不使用 JWT，請求以推送權杖驗證，依平台允許的方式傳入：

| 方式 | 適用平台 |
|---|---|
| `X-Connector-Token` 請求標頭 | 可以設定自訂請求標頭的平台，如 Cloudflare |
| `X-Amz-Firehose-Access-Key` 請求標頭 | Amazon Data Firehose，自動傳送 |
| `X-EventBridge-Signature-Token` 請求標頭 | 阿里雲 EventBridge |
| `?token=` 查詢參數 | 無法設定請求標頭的平台，如 Heroku 和 Pub/Sub |
| `Authorization: Basic` 的密碼 | 將憑證寫進位址的平台 |

介面會在建立連接器時產生權杖，並連同要交給平台的端點只顯示一次，之後無法再讀取。**產生新權杖** 會在儲存連接器時取代目前的權杖。透過 API 建立時，自行提供至少 16 個字元的 `pushToken`。一個權杖只對應同一個 kind 的一個連接器：已使用的權杖會回傳 `409`。缺少或無法辨識權杖的請求，以及傳送給已停用連接器的請求，都會回傳 `401`。沒有權杖的連接器不接受任何推送。節點會將查到的連接器保留 30 秒，因此停用連接器或更換權杖最多 30 秒後生效。

帶 `Content-Encoding: gzip` 的請求主體會被自動解壓縮。Firehose 的請求主體上限為 64 MiB，其他為 16 MiB，解壓縮後同樣以此上限計算。事件會走與其他資料接入相同的路徑：schema-on-write、[管線](/zh-Hant/pipelines)、[資料遮罩](/zh-Hant/security)一併生效。

<Tabs>
  <Tab title="Amazon Data Firehose">
    使用 `kind: "aws_kinesis_firehose"` 建立連接器，然後為 Firehose 串流選擇 **HTTP 端點** 目標：

    - **HTTP 端點 URL**：`https://molesignal.example.com/api/v1/_kinesis_firehose`
    - **存取金鑰**：推送權杖。Firehose 以 `X-Amz-Firehose-Access-Key` 傳送它。

    Firehose 只會投遞到 443 埠的 HTTPS，憑證必須由公開 CA 簽發。部署在內網時需要一個公網入口，參見[公網存取](/zh-Hant/public-access)。Firehose 串流的緩衝大小請設為 1 到 4 MiB。

    MoleSignal 會逐筆讀取 record，並依內容處理：

    | Record | 結果 |
    |---|---|
    | CloudWatch Logs 訂閱訊息，也就是訂閱篩選器送出的 gzip 壓縮 JSON | `logEvents` 的每一項都會成為一筆日誌事件，時間取該項自己的時間，並帶有 `message`、`log_group`、`log_stream`、`account_id`、`region`、`event_id` 和 `source: "cloudwatch"`。建立訂閱時送來的連通性檢查訊息會被略過。 |
    | 採用 JSON、OpenTelemetry 1.0 或 OpenTelemetry 0.7 輸出格式的 CloudWatch Metric Streams record | 寫入指標資料流的指標樣本，請見下文。 |
    | 其他文字 | 每行一筆日誌事件：JSON 物件作為欄位，純文字放入 `message`。 |

    指標串流每分鐘會為每個指標送出一個聚合值。每個統計量會成為一個 gauge 樣本，依 yet-another-cloudwatch-exporter 的方式命名為 `aws_<命名空间>_<指标>_<统计量>`，例如 `aws_ec2_cpuutilization_average`、`aws_ec2_cpuutilization_maximum`、`aws_applicationelb_request_count_sum`。命名空間會去掉 `AWS/` 前綴；指標名稱會在小寫字母後接大寫字母的位置斷詞。統計量有 `average`（總和除以樣本數）、`sum`、`sample_count`、`minimum`、`maximum`，以及指標串流額外選取的百分位，例如 `p99`、`p99_9`。標籤為 `account_id`、`region`，以及每個維度一個 `dimension_<名称>`，例如 `dimension_InstanceId`；`metric_unit` 儲存單位。

    ```promql
    max by (dimension_InstanceId) (aws_ec2_cpuutilization_average)
    ```

    `X-Amz-Firehose-Common-Attributes`（即 Firehose 串流上設定的參數）中的鍵會加到每筆事件和每個樣本上，record 自帶的同名欄位優先。CloudWatch Logs 事件本身不帶區域，`region` 取自 `X-Amz-Firehose-Source-Arn`。

    回應遵循 Firehose 的投遞規範：`application/json`，帶回請求的 `requestId`、一個 `timestamp`，失敗時附上 `errorMessage`。無法讀取的 record 會被略過，請求其餘部分照常寫入並回傳 `200`。暫時無法寫入時會回傳 `429` 或 `5xx`，Firehose 會重試。超過 64 MiB 的請求主體會回傳 `413`，Firehose 對它既不重試也不備份。同一個 `X-Amz-Firehose-Request-Id` 在寫入後 30 分鐘內重試，會直接回傳 `200`，不會再重複寫入。
  </Tab>
  <Tab title="Google Cloud Pub/Sub">
    使用 `kind: "gcp_pubsub_push"` 建立連接器。使用日誌路由器的接收器將日誌路由到 Pub/Sub 主題，再於主題上建立推送訂閱。Pub/Sub 無法設定自訂請求標頭，因此將權杖放在 URL 中：

    ```bash
    gcloud pubsub subscriptions create molesignal-push --topic=molesignal-logs --push-endpoint="https://molesignal.example.com/api/v1/_gcp_pubsub?token=<pushToken>"
    ```

    如果還要驗證訂閱的 OIDC 權杖，將連接器的 `oidcServiceAccount` 設為服務帳戶的電子郵件地址，並使用 `--push-auth-service-account=<邮箱>` 建立訂閱。MoleSignal 隨後會用 Google 的公開金鑰驗證權杖，只接受這個服務帳戶。設定 `oidcAudience` 可再驗證目標對象，訂閱的 `--push-auth-token-audience` 填同一個值。

    每則訊息是一個請求，預設的封裝格式與解封裝後的酬載都能接收。Cloud Logging 的 `LogEntry` 會成為一筆日誌事件：

    | `LogEntry` | 事件 |
    |---|---|
    | `jsonPayload` | 其中的欄位 |
    | `textPayload` | `message` |
    | `protoPayload`（稽核日誌） | `proto_payload`，並從中取出 `method_name`、`service_name`、`principal_email` |
    | `severity` | `level`，轉為小寫 |
    | `logName`、`resource.type`、`insertId` | `log_name`、`resource_type`、`insert_id` |
    | `resource.labels`、`labels` | 以原始名稱作為欄位 |
    | `trace`、`spanId` | 去掉 `projects/<id>/traces/` 前綴的 `trace_id`、`span_id` |
    | `httpRequest` | `http_request` |
    | `timestamp` | 事件時間；缺少時取 `receiveTimestamp` 或發布時間 |

    其他訊息資料會成為一筆事件：JSON 物件作為欄位，文字放入 `message`。端點回傳 `204 No Content`，Pub/Sub 會視為確認。無法讀取的訊息會被確認並略過；暫時無法寫入的訊息不會確認，Pub/Sub 會重新投遞。寫入後 30 分鐘內重新投遞的同一則訊息會直接確認，不會再重複寫入。
  </Tab>
  <Tab title="雲端事件匯流排">
    使用 `kind: "cloud_events"` 建立連接器，再將事件匯流排指向 `https://molesignal.example.com/api/v1/_cloud_events`：

    | 傳送方 | 設定 |
    |---|---|
    | Amazon EventBridge | API 目的地，連線選 **API 金鑰**，請求標頭名稱填 `X-Connector-Token`，值為推送權杖。 |
    | Azure Event Grid | Webhook 訂閱，端點位址末尾加上 `?token=<pushToken>`。驗證握手和 CloudEvents schema 的 `OPTIONS` 握手會自動回應。 |
    | 阿里雲 EventBridge | HTTPS 目標，權杖欄位填推送權杖，並以 `X-EventBridge-Signature-Token` 傳送。 |
    | 華為雲 EventGrid | Webhook 目標，加上請求標頭 `X-Connector-Token`。 |
    | 其他 CloudEvents 傳送方 | 上述任一權杖方式。只能將憑證寫進位址（`https://user:<pushToken>@host/...`）的傳送方也能接收。 |

    請求主體是一個事件或事件陣列，可以是結構化或二進位模式的 CloudEvents 1.0、Amazon EventBridge 事件或 Event Grid schema。每個事件會成為 `targetStream`（預設 `cloud_events`）中的一筆日誌事件：

    | 欄位 | 來源 |
    |---|---|
    | `event_id`、`event_source`、`event_type`、`event_subject` | CloudEvents 的 `id`、`source`、`type`、`subject`；EventBridge 的 `id`、`source`、`detail-type`；Event Grid 的 `id`、`topic`、`eventType`、`subject` |
    | `account_id`、`region` | EventBridge 的 `account`、`region`；阿里雲的 `aliyunaccountid`、`aliyunregionid`；Event Grid 主題所屬的訂閱 |
    | `resources` | EventBridge 的 `resources` |
    | `data` | 酬載，作為一個 JSON 欄位；文字酬載放入 `message` |
    | `event_format` | `cloudevents`、`eventbridge` 或 `event_grid` |

    擴充屬性保留原始名稱。事件時間取事件自己的時間。其他 JSON 物件會原樣成為一筆事件。30 分鐘內來源和 id 都相同的重複投遞不會重複寫入。端點回傳 `200`，請求主體不是 JSON 時回傳 `400`。
  </Tab>
  <Tab title="Cloudflare Logpush">
    使用 `kind: "cloudflare_logpush"` 建立連接器，然後建立一個 HTTP 目標的 Logpush 任務。Cloudflare 會將以 `header_` 開頭的查詢參數轉為請求標頭，因此將權杖放在 `X-Connector-Token` 中：

    ```text
    https://molesignal.example.com/api/v1/_cloudflare?header_X-Connector-Token=<pushToken>
    ```

    Cloudflare 會傳送 gzip 壓縮的 NDJSON，每行會成為一筆事件。端點回傳 `204 No Content`。
  </Tab>
  <Tab title="Heroku">
    使用 `kind: "heroku_drain"` 建立連接器，然後新增 Drain。Heroku 無法設定自訂請求標頭，因此將權杖放在 URL 中：

    ```bash
    heroku drains:add "https://molesignal.example.com/api/v1/_heroku?token=<pushToken>"
    ```

    每行日誌會成為一筆帶有 `message` 和 `source: "heroku"` 的事件。端點回傳 `204 No Content`。
  </Tab>
</Tabs>

<Tip>
  `targetStream` 會在首次投遞時建立，schema 會隨新欄位出現而演化，與其他資料流一致。省略 `targetStream` 時會回退到依來源區分的預設資料流：`kinesis`、`gcp`、`cloud_events`、`cloudflare` 或 `heroku`。Firehose 連接器會將指標樣本寫入 `metricsStream`，預設為 `cloudwatch`。
</Tip>

### CloudWatch Logs

CloudWatch Logs 是**拉取**來源：MoleSignal 每 30 秒呼叫一次 `FilterLogEvents`，而不是等待推送。首次執行會讀取最近 5 分鐘。之後每次執行都會從上一次成功執行結束的位置開始，因此未能讀取或寫入的事件會在下次執行時重新讀取。

```bash
curl -X POST http://localhost:5080/api/v1/connectors \
  -H "authorization: Bearer $MS_TOKEN" \
  -H 'content-type: application/json' \
  -d '{
        "name": "cw-prod",
        "kind": "aws_cloudwatch_logs",
        "configJson": {
          "region": "ap-southeast-1",
          "logGroup": "/aws/lambda/checkout",
          "auth": "node_role",
          "targetStream": "cloudwatch"
        }
      }'
```

| 欄位 | 說明 |
|---|---|
| `region` / `logGroup` | 必填，要讀取的 CloudWatch 區域與日誌群組。 |
| `auth` 及其鍵 | 憑證，需要對該日誌群組有 `logs:FilterLogEvents` 權限，參見 [AWS 驗證](#aws-認證)。 |
| `targetStream` | 寫入的資料流，預設 `default`。 |

同一時間只會有一個節點輪詢某個連接器。`alert` 節點之間會依連接器分工，節點會先認領連接器再輪詢，參見 [alert 節點之間的分工](/zh-Hant/deployment/role-based#alert-節點之間的分工)。每筆事件會成為一筆帶有 `message`、`log_stream`、`log_group` 的日誌。已停用的連接器不會被輪詢。

### Kafka 主題

`kafka_source` 連接器每 30 秒讀取一個主題，從上一次寫入成功的位置接著讀。它會依指定分區讀取，不加入消費者群組，讀取位移會保存在 MoleSignal 中，因此只需要這個主題的讀取權限，叢集上也不會多出消費者群組。

```bash
curl -X POST http://localhost:5080/api/v1/connectors \
  -H "authorization: Bearer $MS_TOKEN" \
  -H 'content-type: application/json' \
  -d '{
        "name": "orders",
        "kind": "kafka_source",
        "configJson": {
          "brokers": "b-1.example.com:9096,b-2.example.com:9096",
          "topic": "orders",
          "tls": true,
          "auth": "sasl_scram_sha_512",
          "saslUsername": "molesignal",
          "saslPassword": "<password>",
          "targetStream": "orders",
          "startFrom": "latest"
        }
      }'
```

| 欄位 | 說明 |
|---|---|
| `brokers`、`topic`、`tls`、`tlsCaCert`、`auth` 及其鍵 | 同 [Kafka 目標](#apache-kafka)。 |
| `targetStream` | 寫入的資料流，預設 `default`。 |
| `messageFormat` | `json`（預設），或 `azure_records` 表示讀取 Azure Monitor 匯出到事件中樞的資料，請見下文。介面：**訊息格式**。 |
| `startFrom` | 第一次從哪裡讀取：`latest`（預設）會讀取從現在起到達的訊息，`earliest` 會讀取 Broker 保存的全部訊息。之後新增的分區會從頭讀取。介面：**從哪裡開始**。 |

- 值為 JSON 物件的訊息，物件欄位就是日誌欄位；其他值會成為 `message`。每筆日誌還會帶有 `kafka_topic`、`kafka_partition`、`kafka_offset`、`source`，訊息有 key 時會帶 `kafka_key`。日誌時間取訊息的時間戳記。
- 一次讀取最多 10,000 則訊息或 32 MiB，還有更多時會馬上接著讀，一次拉取最多持續 2 分鐘。
- 日誌寫入成功後讀取位移才會前進。讀取或寫入失敗時，會在 30 秒後從同一位置重試，因此訊息可能寫入兩次，但不會遺失。位移對應的訊息已被 Broker 清理時，會從 Broker 保存的最早訊息接著讀。
- 變更 `topic` 會依 `startFrom` 重新開始，因為位移屬於主題。

Azure 的診斷設定、Log Analytics 資料匯出和資料收集規則都會匯出到 Azure 事件中樞，Kafka 來源可以透過事件中樞的 Kafka 端點讀取：`brokers` 填 `<命名空间>.servicebus.windows.net:9093`，`topic` 填事件中樞名稱，開啟 `tls`，`auth: sasl_plain`，使用者名稱為 `$ConnectionString`，密碼為連接字串。Basic 層沒有 Kafka 端點。設定 `messageFormat: azure_records` 後，每則 `{"records": [...]}` 訊息都會被拆分：日誌記錄會依其 `time` 成為一筆日誌事件，指標記錄會依每個統計量成為一個樣本，寫入連接器的 `metricsStream`（預設 `default`），命名方式與 [Azure Monitor 指標](#雲端監控指標)相同。

### S3 物件

`s3_source` 連接器每 30 秒會列出一次儲存貯體，依從舊到新讀取尚未讀取過的物件，支援 AWS S3 與 S3 相容儲存。

```bash
curl -X POST http://localhost:5080/api/v1/connectors \
  -H "authorization: Bearer $MS_TOKEN" \
  -H 'content-type: application/json' \
  -d '{
        "name": "elb-logs",
        "kind": "s3_source",
        "configJson": {
          "bucket": "acme-logs",
          "region": "us-east-1",
          "prefix": "AWSLogs/123456789012/",
          "auth": "node_role",
          "targetStream": "elb",
          "startFrom": "latest"
        }
      }'
```

| 欄位 | 說明 |
|---|---|
| `bucket`、`region`、`endpoint`、`virtualHostedStyle`、`auth` 及其鍵 | 同 [S3 目標](#amazon-s3)。憑證需要儲存貯體的 `s3:ListBucket` 和物件的 `s3:GetObject` 權限。 |
| `prefix` | 只讀取此前綴下的物件。每次拉取都必須完整列出它，因此請給來源一個專用的前綴。 |
| `targetStream` | 寫入的資料流，預設 `default`。 |
| `startFrom` | 第一次從哪裡讀取：`latest`（預設）會讀取從現在起出現的物件和此前 5 分鐘內的物件，`earliest` 會讀取前綴下的全部物件。介面：**從哪裡開始**。 |

- 物件會依行讀取。JSON 物件的一行就是日誌的欄位；只含 `Records` 的一行（CloudTrail 的寫法）會讓每筆記錄成為一筆日誌；其他行會成為 `message`。`.gz` 和 `.zst` 物件會依檔案名稱解壓縮。每筆日誌還會帶有 `s3_bucket`、`s3_key` 和 `source`。日誌時間取物件的最後修改時間。
- 一次拉取最多讀取 100 個物件或讀到 50,000 筆日誌，還有更多時會馬上接著讀，最多持續 2 分鐘。
- 日誌寫入成功後讀取狀態才會前進。無法取得的物件會讓這次拉取停在該處，並在 30 秒後重試，因此日誌可能寫入兩次，但不會遺失。
- 無法讀取的物件會被略過，並在連接器上註明，因為反覆重試會擋住後面的所有物件。這包括損毀、超過 256 MiB、解壓縮後超過 512 MiB、超過一百萬筆日誌，或有一行超過 64 MiB 的物件。
- 物件會依鍵和修改時間識別，並保留 5 分鐘餘量。在此餘量內以同一個鍵重新寫入的物件不會再讀取一次；修改時間比已讀取到的最新物件早 5 分鐘以上的物件不會被讀取。S3 會將分段上傳的時間記為開始上傳的時間，因此比這更慢的上傳不會被讀取。

### Google Cloud Pub/Sub 訂閱

`gcp_pubsub_pull` 連接器每 30 秒會讀取一次 Pub/Sub 訂閱，每個請求最多 1000 則訊息，還有剩餘時會立即接著讀，訊息寫入後才會確認。寫入失敗的訊息會在確認期限過後重新投遞，因此一則訊息可能寫入兩次，但不會遺失。它適合[推送訂閱](#推送來源)無法承載的日誌量：推送訂閱每個請求只會送出一個訊息。

| 欄位 | 說明 |
|---|---|
| `serviceAccountKey` | 服務帳戶的 JSON 金鑰檔案，該帳戶需要訂閱上的 `roles/pubsub.subscriber` 角色。 |
| `subscription` | `projects/<项目>/subscriptions/<名称>`，或金鑰所屬專案中的訂閱名稱。確認期限請設為 60 秒或更長。 |
| `targetStream` | 寫入的資料流，預設 `default`。 |

每則訊息會依推送訊息的方式讀取：Cloud Logging 的 `LogEntry` 會依推送標籤頁中的對應方式處理，其他 JSON 物件會作為欄位，其餘內容會放入 `message`。**測試連線** 只會詢問金鑰能否消費這個訂閱，不會取走訊息。

六種來源會依排程拉取雲端平台監控服務的指標，並寫入指標資料流：

| Kind | 雲端平台 | API | 驗證 | 權限 | 預設 `metricsStream` |
|---|---|---|---|---|---|
| `aws_cloudwatch_metrics` | Amazon CloudWatch | `ListMetrics`、`GetMetricData` | [AWS 憑證](#aws-認證) | `cloudwatch:ListMetrics`、`cloudwatch:GetMetricData` | `cloudwatch` |
| `azure_monitor_metrics` | Azure Monitor | Resource Graph、`metrics:getBatch` | 應用程式註冊的 `tenantId`、`clientId`、`clientSecret` | 訂閱上的 **Monitoring Reader** | `azure` |
| `gcp_monitoring_metrics` | Google Cloud Monitoring | `timeSeries.list` | `serviceAccountKey`，即 JSON 金鑰檔案 | 專案上的 `roles/monitoring.viewer` | `gcp` |
| `aliyun_cms_metrics` | 阿里雲雲監控 | `DescribeMetricList` | `accessKey`、`secretKey` | `AliyunCloudMonitorReadOnlyAccess` | `aliyun` |
| `tencent_monitor_metrics` | 騰訊雲可觀測平台 | `GetMonitorData` | `accessKey`（SecretId）、`secretKey`（SecretKey） | `QcloudMonitorReadOnlyAccess`；自動探索 CVM 執行個體時另需 `QcloudCVMReadOnlyAccess` | `tencentcloud` |
| `huawei_ces_metrics` | 華為雲雲監控 | `ListMetrics`、`BatchListMetricData` | `accessKey`（AK）、`secretKey`（SK） | `CES ReadOnlyAccess` | `huaweicloud` |

每次拉取會讀取數個完整週期：週期長度為 `period` 秒，結束時間至少晚 `delay` 秒，從上一次寫入成功的拉取結束處接著讀。雲端平台要在週期結束幾分鐘後才會算完一個聚合值，而每個週期只會讀取一次，之後才修正的值會保持讀取時的樣子。新連接器會從前一個週期開始。一次拉取最多讀取 12 個週期，其餘會在下一個排程繼續；停用超過 6 小時的連接器會略過較早的部分，並顯示提示。

每個序列的每個統計量會成為一個 gauge 樣本，依 yet-another-cloudwatch-exporter 命名 CloudWatch 指標的方式命名為 `<云>_<命名空间>_<指标>_<统计量>`，時間為週期的開始：

| 來源 | 範例 | 標籤 |
|---|---|---|
| CloudWatch | `aws_ec2_cpuutilization_average` | `region`、`dimension_<名称>` |
| Azure Monitor | `azure_compute_virtualmachines_percentage_cpu_average` | `subscription_id`、`resource_group`、`resource_name`、`resource_id`、`region`、`dimension_<名称>`、`tag_<键>` |
| Cloud Monitoring | `gcp_compute_instance_cpu_utilization_mean` | `project_id`、`resource_type`，以及資源和指標的標籤 |
| 阿里雲雲監控 | `aliyun_ecs_dashboard_cpuutilization_average` | `region`、`user_id`、`dimension_<键>` |
| 騰訊雲可觀測平台 | `tencentcloud_cvm_cpu_usage_avg` | `region`、`dimension_<名称>` |
| 華為雲雲監控 | `huaweicloud_sys_ecs_cpu_util_average` | `region`、`dimension_<名称>` |

透過 Firehose 的 [CloudWatch 指標串流](#推送來源)寫出的名稱與此相同，同一條 PromQL 兩邊都能用：

```promql
max by (dimension_InstanceId) (aws_ec2_cpuutilization_average)
```

| 欄位 | 來源 | 說明 |
|---|---|---|
| `metricsStream` | 全部 | 寫入的指標資料流。 |
| `period` | 全部 | 秒，必須為整分鐘，預設 300。Azure 採用 60、300、900、1800、3600、21600、43200、86400；華為雲採用 300、1200、3600、14400、86400。 |
| `delay` | 全部 | 週期結束後多少秒再讀取。CloudWatch 和 Azure 預設 600，其他預設 300。 |
| `region` | 除 Google Cloud 外 | 例如 `us-east-1`、`eastus`、`cn-hangzhou`、`ap-guangzhou`、`cn-north-4`。 |
| `namespace` | CloudWatch、阿里雲、騰訊雲、華為雲 | 例如 `AWS/EC2`、`acs_ecs_dashboard`、`QCE/CVM`、`SYS.ECS`。 |
| `metrics` | 全部 | 指標名稱，以逗號或換行分隔。除 CloudWatch 外為必填；CloudWatch 留空時會讀取命名空間中最近三小時有資料的全部指標，最多 2000 個序列。Google Cloud 請填指標類型，例如 `compute.googleapis.com/instance/cpu/utilization`。 |
| `statistics` | CloudWatch、阿里雲、騰訊雲、華為雲 | CloudWatch：`Average`、`Sum`、`Minimum`、`Maximum`、`SampleCount` 和 `p99` 這類百分位，預設 `Average`、`Maximum`。阿里雲：`Average`、`Maximum`、`Minimum`、`Sum`，預設 `Average`、`Maximum`。騰訊雲：`avg`、`max`、`min`，預設 `avg`。華為雲：`average`、`max`、`min`、`sum`、`variance`，預設 `average`。 |
| `subscriptionId`、`resourceType`、`aggregations`、`filter`、`top` | Azure | 資源類型也是指標命名空間，例如 `Microsoft.Compute/virtualMachines`。聚合方式：`average`（預設）、`minimum`、`maximum`、`total`、`count`。`filter` 依維度拆分，例如 `LUN eq '*'`；`top` 限制拆分出的序列數，預設 100。 |
| `projectId`、`filter` | Google Cloud | 專案預設採用金鑰所屬的專案。`filter` 是附加到每個指標篩選條件的子句。gauge 讀取 `mean`，delta 讀取 `sum`，counter 讀取 `rate`，distribution 讀取 `count` 和 `mean`。 |
| `dimensions` | 阿里雲 | 選用，作為 `Dimensions` 傳入的 JSON；留空時會讀取帳號下全部執行個體。 |
| `instances` | 騰訊雲 | 每行一個執行個體，寫成 `Name=Value`，多個維度用 `&` 連接。除 `QCE/CVM` 外為必填；`QCE/CVM` 留空時會自動探索本地區域的執行個體。 |
| `projectId` | 華為雲 | 該區域的專案 ID。 |

每次查詢都會由雲端平台計費：CloudWatch 會將每個序列的每個統計量以一次指標請求計費，Google Cloud 會依傳回的序列計費，其他平台則在超過每月免費額度後依呼叫次數計費。`metrics` 和 `statistics` 只選需要的，`period` 越長費用越低。**測試連線** 會用已儲存的設定送出一個小請求，不會變更讀取位置。

<Tip>
  儲存庫的 `deploy/cloud` 目錄提供了在雲端平台側建立資源的範本：包含 Firehose 串流、指標串流與 CloudWatch Logs 訂閱的 CloudFormation 堆疊，包含日誌路由器接收器與 Pub/Sub 訂閱的 Terraform 模組，以及建立 Kafka 來源所讀取 Event Hubs 命名空間的 Bicep 檔案。
</Tip>

### 拉取狀態

連接器頁面會顯示來源最近一次收到資料的時間。上次讀取失敗的來源旁邊會有警告，原因會寫在提示與連接器設定中，最近略過的內容也會寫在那裡。資料流因值與欄位類型不符而拒收的事件不會重新傳送：來源會繼續往後讀取，推送端點仍會回傳成功，因為平台會重新傳送整個請求。連接器最近略過的內容會一併註明拒收的筆數和第一個原因。透過 API 讀取時，`readState` 包含 `lastError`、`lastWarning`（各有 `atTime` 和 `text`）以及讀到哪裡的 `position`。儲存連接器不會變更讀取位置。

## 目標

目標會接收排程管線經過各步驟後的所有事件。使用 **新增目標 → 連接器** 將連接器加入管線的 **目標**。投遞失敗時會在本次執行內重試；連接器仍未接收的事件會寫入死信資料流，參見[重試與死信](/zh-Hant/pipelines#重試與死信)。

已停用的目標不會收到任何事件。每次執行都會跳過該連接器，並在該次執行的 `warning` 中註明。被跳過的事件不計為失敗，不會寫入死信，重新啟用連接器後也不會補發。編輯器中已停用的連接器會標示 **停用**。

| Kind | 投遞負載 |
|---|---|
| `s3` | 每批事件會建立一個 JSON Lines 物件，並以 `PUT` 寫入 `s3://<bucket>/<prefix><id>.jsonl`。 |
| `kafka` | 每則事件會在主題上產生一則訊息，訊息內容為該事件的 JSON。 |
| `http` | 每批事件會以一個要求傳送；批次較大時會拆成多個要求，格式為 NDJSON 或一個 JSON 陣列。 |

### Amazon S3

`s3` 也可以投遞到 MinIO、Cloudflare R2、阿里雲 OSS 等 S3 相容儲存空間。在介面上開啟 **S3 相容儲存空間** 即可填寫端點。

| 欄位 | 說明 |
|---|---|
| `bucket` | 必填。 |
| `region` | 儲存桶所在的區域。S3 相容儲存空間可能不需要。 |
| `prefix` | 物件會命名為 `<prefix><id>.jsonl`。開頭的 `/` 會被移除，結尾會補上 `/`。 |
| `endpoint` | S3 相容儲存空間的 S3 API 位址，開頭為 `http://` 或 `https://`。 |
| `virtualHostedStyle` | 為 `true` 時會在主機名稱中指定儲存桶，而不是將儲存桶放在路徑中；阿里雲 OSS 等儲存空間要求這麼做。介面上為 **在主機名稱中指定儲存桶**。 |
| `auth` 及其鍵 | 憑證，需要對儲存桶有 `s3:PutObject` 權限，參見 [AWS 認證](#aws-認證)。 |

### Apache Kafka

| 欄位 | 說明 |
|---|---|
| `brokers` | 必填。主機和連接埠，多個請以逗號分隔。 |
| `topic` | 必填。 |
| `tls` | 為 `true` 時會使用 TLS 加密連線。請連線到 Broker 的 TLS 連接埠，常見為 9093、9094 或 9096。介面上為 **TLS 加密連線**。 |
| `tlsCaCert` | 當 Broker 憑證由私有 CA 簽發時，填寫該 CA 的 PEM 憑證，僅在開啟 `tls` 時可用。不填則信任系統的 CA。 |

| `auth` | 介面 | 鍵 | 說明 |
|---|---|---|---|
| `none` | **無** | | 用於不要求憑證的 Broker。 |
| `sasl_plain` | **SASL/PLAIN** | `saslUsername`、`saslPassword` | 密碼會原樣傳送。未開啟 TLS 時只應在內網使用。 |
| `sasl_scram_sha_256` | **SCRAM-SHA-256** | `saslUsername`、`saslPassword` | 密碼本身不會經由網路傳輸。 |
| `sasl_scram_sha_512` | **SCRAM-SHA-512** | `saslUsername`、`saslPassword` | Amazon MSK 使用的機制。 |
| `mtls` | **用戶端憑證** | `tlsClientCert`、`tlsClientKey` | 雙向 TLS，需要開啟 `tls`。兩者都是 PEM 格式，私鑰不能加密。 |

TLS 與 SASL 可以搭配使用：以 TLS 為基礎的 SCRAM 會以 `SASL_SSL` 連線。

### HTTP / Webhook

| 欄位 | 說明 |
|---|---|
| `url` | 必填，為開頭是 `http://` 或 `https://` 的絕對位址。位址常帶有憑證，例如路徑或查詢參數中的金鑰，因此會以金鑰形式儲存。回應中只會顯示 `urlOrigin`，即通訊協定、主機和連接埠。位址中帶有使用者名稱和密碼會被拒絕，請改用 `basic`。 |
| `method` | `post`（預設）或 `put`。 |
| `format` | `ndjson`（預設）會以 `application/x-ndjson` 每行傳送一則事件；`json` 會以 `application/json` 傳送一個 JSON 陣列。 |

| `auth` | 介面 | 鍵 | 要求 |
|---|---|---|---|
| `none` | **無** | | 不帶憑證。 |
| `bearer` | **Bearer 權杖** | `bearerToken` | `Authorization: Bearer <token>` |
| `basic` | **基本驗證** | `basicUsername`、`basicPassword` | HTTP Basic 驗證標頭，請搭配 `https` 使用。 |
| `header` | **自訂要求標頭** | `headerName`、`headerValue` | 將值放在指定的要求標頭中，例如 `X-API-Key` 或 `DD-API-KEY`。 |
| `hmac` | **HMAC 簽章** | `hmacSecret` | 對要求主體簽章，共用金鑰至少 16 個字元。 |

自訂要求標頭不能是投遞本身設定的要求標頭：`Host`、`Content-Type`、`Content-Length`、`Content-Encoding`、`Transfer-Encoding`、`Connection`、`X-MoleSignal-Timestamp`、`X-MoleSignal-Sign`。

投遞會遵循下列規則：

- 大於 4 MiB 的批次會拆成多個要求傳送。單則事件超過這個大小時，會單獨佔用一個要求。
- 任何 `2xx` 狀態碼都算投遞成功。其他狀態碼都算投遞失敗，重新導向也一樣：投遞不會跟隨重新導向。
- 每個要求會在 30 秒後逾時。
- MoleSignal 會在要求前解析主機，只連線到解析得到的位址。雲端中繼資料服務所在的位址一律拒絕，無論是寫在位址中或由 DNS 解析得到：`169.254.0.0/16`、`fe80::/10`、`fd00:ec2::254`、`100.100.100.200`。其他私有位址可以使用。

#### 驗證 HMAC 簽章

`auth` 為 `hmac` 時，每個要求會帶有兩個要求標頭：

| 要求標頭 | 內容 |
|---|---|
| `X-MoleSignal-Timestamp` | 要求時間，Unix 秒。 |
| `X-MoleSignal-Sign` | `sha256=<十六进制>`，使用共用金鑰對 `<timestamp>.<body>` 計算的 HMAC-SHA256。 |

驗證要求時，使用同一把金鑰對時間戳記、一個 `.` 和原始要求主體位元組計算 HMAC-SHA256，再與簽章進行常數時間比較。請拒絕超過幾分鐘的時間戳記，讓攔截到的要求無法在之後重送。

```python
import hashlib
import hmac
import time


def verify(secret: bytes, timestamp: str, signature: str, body: bytes, tolerance: int = 300) -> bool:
    if abs(time.time() - int(timestamp)) > tolerance:
        return False
    signed = timestamp.encode() + b"." + body
    expected = "sha256=" + hmac.new(secret, signed, hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, signature)
```

## AWS 認證

S3 與 CloudWatch Logs 會以下列五種方式之一向 AWS 認證：

| `auth` | 介面 | 鍵 | 憑證 |
|---|---|---|---|
| `access_key` | **存取金鑰** | `accessKey`、`secretKey` | IAM 使用者的長期金鑰。 |
| `temporary_key` | **暫時金鑰** | `accessKey`、`secretKey`、`sessionToken` | AWS STS 簽發的短期金鑰，必須與工作階段權杖一起使用。請在到期前更換。 |
| `node_role` | **節點身分** | | MoleSignal 所在節點的身分，不會儲存任何金鑰。 |
| `assume_role` | **擔任角色** | `roleArn`，可選 `accessKey` 與 `secretKey` | 使用組織外部 ID、透過 AWS STS 擔任的角色。 |
| `web_identity` | **Web Identity** | `roleArn` | 使用節點的 Web Identity Token 擔任的角色。 |

未提供 `auth` 時，會依已填寫的鍵判斷：有存取金鑰即為 `access_key`，有 `roleArn` 即為 `assume_role`，兩者都沒有則為 `node_role`。`roleArn` 的格式為 `arn:aws:iam::<account>:role/<name>`。

### 節點身分

`node_role` 會使用 AWS SDK 在節點上能找到的身分：EKS 的服務帳號 IAM 角色（IRSA）或 EKS Pod Identity、ECS 任務角色，或 EC2 執行個體設定檔。節點環境中的靜態金鑰（例如 `AWS_ACCESS_KEY_ID`）不會用於連接器。

<Warning>
  節點身分及其 Web Identity Token 屬於整個部署。部署中的每個組織都可以選用 `node_role` 和 `web_identity`，因此節點身分能存取的一切，以及信任節點權杖的每個角色，都對所有組織的連接器開放。請只授予每個組織都可以擁有的存取權限。
</Warning>

### 擔任角色

`assume_role` 會向 AWS STS 申請該角色有效期一小時的金鑰，並在到期前 5 分鐘更換。擔任角色所用的基礎憑證是節點身分。部署不在 AWS 上執行時，請勾選 **使用存取金鑰而非節點身分擔任角色**，並填寫一個 IAM 使用者的金鑰。

每個組織都會以自己的外部 ID `molesignal-<组织 ID>` 擔任角色，該值無法修改。表單會在 **外部 ID** 處顯示它，`GET /api/v1/connectors/aws-external-id` 也會傳回它。請在角色的信任策略中要求該外部 ID，這樣其他組織即使知道角色的 ARN 也無法擔任角色：

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": { "AWS": "<节点角色或 IAM 用户的 ARN>" },
      "Action": "sts:AssumeRole",
      "Condition": { "StringEquals": { "sts:ExternalId": "molesignal-<组织 ID>" } }
    }
  ]
}
```

工作階段會命名為 `molesignal-<连接器 ID>`，在 AWS CloudTrail 中會以此名稱出現。要求會送往連接器 `region` 所在區域的 STS 端點：區域為空時為 `us-east-1`，中國區域會使用 `amazonaws.com.cn` 網域。

### Web Identity

`web_identity` 會使用節點 `AWS_WEB_IDENTITY_TOKEN_FILE` 所提供路徑的 Web Identity Token 擔任角色，例如 EKS 為 IRSA 投射的服務帳號權杖。連接器無法指定其他檔案。角色的信任策略需要信任簽發該權杖的 OIDC 提供者。節點沒有設定 `AWS_WEB_IDENTITY_TOKEN_FILE` 時，連接器會拿不到憑證。

權杖會在連接器 `region` 所在區域的 STS 端點兌換；節點環境設定了 `AWS_ENDPOINT_URL_STS` 時會改用該端點。來自 IRSA 的節點身分同樣如此。

## 測試連線

**測試連線** 會在儲存前試用表單中目前的設定，留空的金鑰會使用已儲存的值。每種類型只會執行足以證明可投遞或可提取的最少操作：

| Kind | 測試內容 |
|---|---|
| `s3` | 在前綴下寫入物件 `.molesignal-connection-test`，權限允許時再刪除。 |
| `kafka` | 向 Broker 讀取主題中繼資料，以此驗證連線、TLS 與認證，並確認主題存在。不會寫入訊息。 |
| `http` | 傳送一則標記為測試的事件：`"message": "MoleSignal connection test"`、`"molesignal_connection_test": true`。 |
| `aws_cloudwatch_logs` | 讀取日誌群組最近一分鐘內最多一則事件。不會寫入資料流，讀取位置保持不變。 |
| `kafka_source` | 向 Broker 讀取主題中繼資料，同 `kafka`。不會讀取訊息，讀取位置保持不變。 |
| `s3_source` | 列出前綴下的一個物件，以此驗證憑證和 `s3:ListBucket`。不會讀取任何內容，讀取位置保持不變。 |

測試會在 25 秒後放棄。透過 API 測試時，`POST /api/v1/connectors/test` 會接收要試用的 `kind` 與 `configJson`。帶上同一 kind 的已儲存連接器 `id` 時，`***` 代表該連接器儲存的金鑰。無法生效的設定會與儲存時一樣傳回 `400`。

```bash
curl -X POST http://localhost:5080/api/v1/connectors/test \
  -H "authorization: Bearer $MS_TOKEN" \
  -H 'content-type: application/json' \
  -d '{
        "id": "<connector id>",
        "kind": "kafka",
        "configJson": {
          "brokers": "b-1.example.com:9096",
          "topic": "logs",
          "tls": true,
          "auth": "sasl_scram_sha_512",
          "saslUsername": "molesignal",
          "saslPassword": "***"
        }
      }'
```

```json
{ "ok": true, "code": "ok", "detail": null, "elapsedMs": 412 }
```

`elapsedMs` 是測試耗時。測試失敗時，`code` 會指出原因，`detail` 會附上對方的原話，最多 600 個字元：

| `code` | 含義 |
|---|---|
| `ok` | 連線成功。 |
| `invalid` | 設定無法生效，或連接器是沒有可連線對象的推送來源。 |
| `no_credentials` | 無法取得 AWS 憑證：節點沒有身分，或沒有所需類型的身分。 |
| `denied` | 對方拒絕了憑證或憑證所需的權限。 |
| `not_found` | 儲存桶、主題、日誌群組或位址不存在。 |
| `tls` | TLS 握手失敗：憑證不受信任，或沒有出示憑證。 |
| `unreachable` | 無法解析或連線主機。 |
| `timeout` | 等待回應逾時。 |
| `failed` | 其他失敗。 |

## API

| 端點 | 權限 | 用途 |
|---|---|---|
| `GET /api/v1/connectors` | `pipelines.read` | 列出組織的連接器。 |
| `POST /api/v1/connectors` | `pipelines.edit` | 建立連接器，`enabled` 預設為 `true`。 |
| `GET /api/v1/connectors/{id}` | `pipelines.read` | 讀取連接器。 |
| `PUT /api/v1/connectors/{id}` | `pipelines.edit` | 整體取代 `name`、`kind`、`configJson` 與 `enabled`，四者均為必填。 |
| `DELETE /api/v1/connectors/{id}` | `pipelines.edit` | 刪除連接器。 |
| `POST /api/v1/connectors/test` | `pipelines.edit` | 在儲存前測試設定。 |
| `GET /api/v1/connectors/aws-external-id` | `pipelines.read` | 以 `externalId` 傳回組織的外部 ID。 |

連接器的讀取結果包含 `id`、`name`、`kind`、金鑰已遮罩的 `configJson`、`secretKeys`、`enabled`、`lastRunAt`、`readState`、`createdAt` 與 `updatedAt`。

## 權限

`pipelines.read` 用於列出和檢視連接器，以及讀取外部 ID。`pipelines.edit` 用於建立、更新、刪除和測試連接器。測試需要 `pipelines.edit`，因為它會使用已儲存的金鑰，並代替呼叫方連線其他系統。推送接收端點以推送權杖驗證，不能用一般登入 JWT 取代。
