Mole Agent 寫下的每個回答都會被評分。規則會立即評分，不呼叫模型：工具是否成功、是否引用證據、查詢能否解析、回答是否符合要求的形狀，以及提問人的評價。你設定的評審會用模型、依照你寫的評分標準為一部分回答評分。分數低的、被評為沒有幫助的與隨機抽中的回答會進入待審；審核人採納的會組成迴歸集。組織 Prompt 設為預設前，檢查會用新版本和目前的版本把其中一些問題各回答一次，並由評審為兩份回答評分。

分數以 0 到 100 顯示。**品質**頁籤裡能看到這些分數，每個分數也會寫進串流 `_agent_score_traces`。

## 開始之前

- **品質**頁籤需要 `agent.quality.read`，預設授予擁有者與管理員。這兩個角色本來就能讀取所有團隊對話；個人對話只計入合計，任何人都看不到它們的內容。
- 評審會使用組織的一個模型服務，參見 [Mole Agent](/zh-Hant/agent#設定模型服務)。沒有評審時，每個回答仍會依規則評分。

## 為哪些內容評分

| 來源 | 是什麼 |
|---|---|
| **團隊對話** | 團隊對話裡的回答。 |
| **個人對話** | 個人對話裡的回答。只依規則評分，只計入合計。 |
| **自動化** | 組織與團隊自動化每次執行時的回答，參見[自動化](/zh-Hant/automations)。個人自動化的執行算作個人對話。 |
| **事件 RCA** | 根本原因分析自動或隨需產生的 RCA，以及有人評價過的 RCA。 |

回答寫下時評分；提問人評價或撤回評價後再評一次。

## 規則

規則會查看回答和它在那一輪留下的內容，為下列每一項打 0 到 100 分。一個回答的規則分是適用各項的平均。

| 規則項 | 分數 | 適用於 |
|---|---|---|
| **工具呼叫** | 沒有出錯的工具呼叫所佔的比例。 | 呼叫過工具的回答。 |
| **證據** | 沒有引用證據為 0；引用了證據但沒有成功的工具呼叫支撐為 50；引用一條為 75，兩條及以上為 100。事件 RCA：引用了未提供給它的編號為 0，提供了證據卻一條都沒引用為 25，只引用提供給它的證據為 100。 | 符合要求的形狀且呼叫過工具的回答；提供了證據或引用了編號的事件 RCA。 |
| **查詢** | 工具呼叫裡能解析的 SQL 與 PromQL 所佔的比例。 | 工具執行過查詢的回答。 |
| **格式** | 回答符合要求的形狀時為 100。 | 除只產生查詢以外的所有對話回答。 |
| **已完成** | 已完成者為 100；自動化執行途中需要人處理的為 50；失敗、被停止或沒有回答的為 0。 | 所有回答。 |
| **評價** | **有幫助**為 100，**沒有幫助**為 0。RCA 只要有一個**沒有幫助**就算沒有幫助。 | 有人評價過的回答。 |

## 評審

評審會依評分標準為回答打 1 到 5 分，並用一兩句話說明理由；分數顯示為 0、25、50、75 或 100。它會讀取問題、工具查到的結果與回答；RCA 則讀取事件的事實與 RCA。

- 評審會評新回答中你設定的百分比，依回答抽取：同一個回答抽幾次結果都一樣。
- 被評為**沒有幫助**的回答一定會評，評審已經評過的除外。
- 評審給的分數低於待審門檻時會再評一次，取兩次的平均。
- 評審從不評個人對話。
- 評審撰寫理由時，會使用最後儲存它的人的介面語言。
- 評審的模型呼叫會計入組織的每日 token 預算，在用量的來源分布中顯示為**品質評分**。預算用完時，評審不會評新回答。

所有評審都以內建 Prompt **回答評審**（用途 `evaluation`）為指令，組織可以在**設定 → Prompt 管理**中覆寫它。不論 Prompt 怎麼寫，評審都會依固定格式傳回分數。

一個回答的分數：有評審評過時取評審的平均，否則取規則分。

## 品質頁籤

開啟 **Mole Agent → 品質**。**總覽**與**回答**會看最近 7、30 或 90 天，可以只查看一個來源。

| 檢視 | 內容 |
|---|---|
| **總覽** | 已評分的回答數、規則與評審的平均分、被評為有幫助與沒有幫助的回答數，以及待審數。下方是每天的分數、各規則項，以及依來源、Prompt 版本、Skill 與模型的分組。 |
| **回答** | 已評分的回答，新的在前；**只看低分**只保留低於待審門檻的。點開一行能看到完整的問題與回答、每個規則項查到的事實、每個評審的分數與理由，以及這個回答的待審。**開啟對話**或**開啟事件**會前往它所在的地方。 |
| **待審** | 等待審核、已採納與已駁回的回答。 |
| **資料缺口** | 從回答呼叫工具的過程查看資料缺了什麼。見[資料缺口](#資料缺口)。 |
| **演練** | 把已解決的事件重新調查一遍，拿結論和確認過的根本原因比對評分。見[演練](#演練)。 |
| **評審** | 評審與設定。 |

### 審核回答

回答會在下列情況進入待審：

| 原因 | 時機 |
|---|---|
| **分數低** | 評審再評一次後分數仍低於待審門檻；沒有評審評過的回答，規則分低於門檻。 |
| **被評為沒有幫助** | 提問人評為**沒有幫助**。 |
| **隨機抽中** | 依**隨機複審**的比例抽中，用來查看分數是否可信。 |

一個回答只會進入待審一次。點開它，在**備註**裡寫清楚錯在哪裡、好的回答應該答對什麼，然後選擇：

- **採納**：回答有問題。它會加入迴歸集；Prompt 檢查重新回答這個問題時，備註會交給評審參考。
- **駁回**：回答沒有問題。

### 評審與設定

在**評審**中選擇**新增評審**開啟表單：

| 欄位 | 說明 |
|---|---|
| **名稱** | 在組織內唯一。 |
| **評分標準** | 好的回答該做到什麼、什麼會扣分，最長 4000 個字元。表單裡已預先填好一份可以修改的。 |
| **回答** | 團隊對話、自動化、事件 RCA。 |
| **抽樣比例** | 新回答中評分的百分比，0 到 100。 |
| **模型服務**與**模型** | 留空時使用組織第一個可用的模型服務與它的預設模型。 |
| **溫度** | 0 到 1；0 讓分數更穩定。 |
| **啟用** | 停用的評審不會評任何回答。 |

一個組織最多有 10 個評審。刪除評審後，它給過的分數會保留。

評審下方的設定：

| 設定 | 預設 | 說明 |
|---|---|---|
| **待審門檻** | 60 | 分數低於它的回答會進入待審。 |
| **隨機複審** | 0 | 其餘回答中隨機抽進待審的百分比。 |
| **將 Prompt 設為預設前** | 檢查，品質下降時再次確認 | 見下文。 |

### 資料缺口

回答依規則評分時，也會讀取它呼叫工具的過程，查看 Mole Agent 手上的資料缺了什麼。這不影響分數：缺口說的是資料，不是回答。**資料缺口**會彙總最近 7、30 或 90 天的情況。

| 類型 | 何時算有缺口 | 怎麼補 |
|---|---|---|
| **資料在哪裡** | 同一個資料流查詢了 3 次以上、多半為空或報錯，或者看了 3 次以上結構（資料流的結構、資料流列表、指標名稱與標籤）。 | 寫清楚每個服務的資料在哪裡、怎麼過濾：寫進服務目錄的資料入口，或知識裡的 `MOLE.md`。 |
| **服務名稱** | 在指標或 APM 裡查到某個服務的資料，依同一個名稱查日誌或追蹤卻為空，這個資料流也沒有其他查詢查到它。 | 讓同一個服務在各類資料裡使用同一個名稱（`service.name`），或在服務目錄裡把它的其他名稱記為別名。 |
| **先扼要整理再看** | 取得 2 次以上原始日誌或原始序列，每次行數很多，沒有使用**分析日誌模式**或**分析指標趨勢**。 | 檢查組織的 Agent Profile 工具集有沒有把這兩個工具排除在外。 |

檢視畫面會依資料流與服務列出反覆出現的缺口，以及有多少個回答遇到、最近一次是什麼時候。點開下方的回答能看到它的分數。個人對話只計入合計，它們查了什麼不會列出。

### 演練

演練是把已經解決的事件當作正在發生，讓 Mole Agent 重新調查一遍，再拿結論和事後確認的根本原因比對評分。換了模型、Prompt 或工具之後把演練全部重跑一遍，就能看出調查有沒有變好。

**新增演練**會列出最近 180 天已解決、事後檢討裡寫了根本原因（**根本原因**一節下的內容）的事件。預設拿事後檢討裡的根本原因作為參考，也可以自行撰寫。**其他事件**填事件 ID，自行撰寫根本原因。一個事件只有一個演練，一個組織最多 100 個。

一次執行：

- 以發起執行的人的身分執行，這個人必須能讀取這個事件；沒有人值守，唯讀，最長 10 分鐘。
- 取得事件觸發時的事實（摘要、嚴重度、服務、標籤、觸發它的查詢）與告警規則的疑難排解線索，查看事件開始前 1 小時到開始後半小時的資料。
- 讀不到事件之後查到和做過的事：它的備註、時間軸、RCA、事後檢討、工單、核准，以及和它相似的事件。
- 是一個不在對話列表裡的對話。在執行記錄裡選擇**查看調查**開啟，只能查看。

調查結束後，由模型拿它找到的根本原因和參考根本原因比對，打 1 到 5 分（顯示為 0 到 100），理由用發起執行的人的介面語言撰寫。模型會使用第一個啟用評審所用的模型，沒有時則使用組織第一個可用的模型服務；呼叫會計入每日 token 預算，來源記為**品質評分**。調查失敗、被停止或沒有寫出回答的執行沒有分數，會註明原因。

**執行**會開始一個演練；**全部重跑**會開始所有未在執行的演練，一次最多 50 個。新增、執行與刪除演練需要 `agent.quality.manage`。

## 將 Prompt 設為預設前先檢查

在對話用的（**系統指令**）或事件 RCA 用的（**找出根本原因**）組織 Prompt 上選擇**設為預設**時，會依組織的設定處理：

| 設定 | Prompt 沒檢查過，或檢查發現品質下降時 |
|---|---|
| **檢查，品質下降時再次確認** | 對話框提供**開始檢查**，也可以**仍設為預設**。 |
| **檢查，品質下降時禁止設為預設** | 只有檢查過且沒有變差的 Prompt 才能設為預設。 |
| **不檢查** | 直接設為預設。 |

一次檢查最多取 8 個回答：先取迴歸集，再取評這類回答的第一個評審最近評過的。每個回答會用目前的預設與新版本各重新回答一次，使用同一個模型，不再呼叫工具：模型拿到的是原來的問題和那一輪工具查到的結果；RCA 則由兩個版本各依事件的事實寫一份。之後評審會為每一對回答評分。新版本的平均分比目前的預設低 5 分以上為**變差了**，高 5 分以上為**更好**，否則為**沒有變差**。能比較的回答少於 3 個時無法判定，不影響設為預設。

對話框裡會先顯示進度，再顯示每個回答的結果。一次檢查只針對 Prompt 的一個版本和一個預設：Prompt 改過或預設換了之後要重新檢查。檢查的模型呼叫會計入**品質評分**。

其他用途的 Prompt 設為預設時不檢查。直接修改已經是預設的 Prompt 也不檢查；要檢查一處改動，請把它存成新的 Prompt，再設為預設。

## 串流裡的分數

每個分數也是內部串流 `_agent_score_traces` 中的一行，可以在**日誌**中查詢：

| 欄位 | 說明 |
|---|---|
| `target_kind`、`target_id` | `chat_answer` 與訊息 ID，或 `incident_rca` 與事件 ID。 |
| `source` | `personal_chat`、`team_chat`、`automation` 或 `incident_rca`。 |
| `scorer`、`scorer_kind` | `rules`，或評審的 ID 與 `evaluator`。 |
| `score`、`samples` | 0 到 1 的分數，以及它是幾次評分的平均。 |
| `tool_success`、`evidence`、`query_validity`、`answer_format`、`completion`、`feedback` | 適用的規則項，0 到 1。 |
| `reason`、`evaluator_model` | 評審的理由與模型。 |
| `chat_id`、`team_id`、`automation_id`、`user_id`、`prompt_template_id`、`prompt_version`、`prompt_key`、`provider_id`、`model`、`skill`、`skill_version` | 回答出自哪裡、用了什麼。 |

想在品質下降時收到告警，可以在這個串流上建立一條[異常偵測告警規則](/zh-Hant/alerting)，例如查看評審的平均分：

```sql
SELECT avg(score) AS value FROM "_agent_score_traces" WHERE scorer_kind = 'evaluator'
```
