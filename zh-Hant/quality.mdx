Mole Agent 產生的每個回答都會評分。規則會立即評分，不呼叫模型：檢查工具是否成功、是否引用證據、查詢能否剖析、回答是否符合要求的格式，以及提問者的評價。設好的評審會使用模型，依照指定的評分標準為部分回答評分。分數低、被評為沒有幫助及隨機抽中的回答會進入待審；審核者採納的回答會組成迴歸集。將組織 Prompt 設為預設前，檢查會以新版本和目前版本各回答一次其中部分問題，再由評審為兩份回答評分。

分數以 0 到 100 顯示。可在**品質**頁籤查看這些分數，每個分數也會寫入資料流 `_agent_score_traces`。

## 開始之前

- **品質**頁籤需要 `agent.quality.read`，預設授予擁有者與管理員。這兩個角色原本就能讀取所有團隊對話；個人對話只計入總計，任何人都無法查看其內容。
- 評審使用組織的其中一個模型服務，請參閱 [Mole Agent](/zh-Hant/agent#設定模型服務)。沒有評審時，仍會依規則為每個回答評分。

## 評分對象

| 來源 | 說明 |
|---|---|
| **團隊對話** | 團隊對話中的回答。 |
| **個人對話** | 個人對話中的回答。只依規則評分，只計入總計。 |
| **自動化** | 組織與團隊自動化每次執行產生的回答，請參閱[自動化](/zh-Hant/automations)。個人自動化的執行計為個人對話。 |
| **事件 RCA** | 系統自動或按需產生的根本原因分析（RCA），以及已有評價的 RCA。 |

系統會在產生回答時評分，並在提問者給予或撤回評價後再評一次。

## 規則

規則會檢查回答及該輪留下的資料，為下列各項給出 0 到 100 分。回答的規則分數為所有適用項目的平均分數。

| 規則項目 | 分數 | 適用於 |
|---|---|---|
| **工具呼叫** | 未出錯的工具呼叫所占的比例。 | 曾呼叫工具的回答。 |
| **證據** | 未引用證據為 0 分；引用證據但沒有成功的工具呼叫佐證為 50 分；引用一項證據為 75 分，兩項以上為 100 分。 | 符合要求的格式且曾呼叫工具的回答。 |
| **查詢** | 工具呼叫中可剖析的 SQL 與 PromQL 所占的比例。 | 曾透過工具執行查詢的回答。 |
| **格式** | 回答符合要求的格式時為 100 分。 | 除僅產生查詢外的所有對話回答。 |
| **已完成** | 已完成為 100 分；自動化執行期間需要人工處理為 50 分；失敗、停止或沒有回答為 0 分。 | 所有回答。 |
| **評價** | **有幫助**為 100 分，**沒有幫助**為 0 分。RCA 只要收到一則**沒有幫助**的評價，就算沒有幫助。 | 已有評價的回答。 |

## 評審

評審依評分標準為回答給出 1 到 5 分，並用一兩句話說明理由；分數顯示為 0、25、50、75 或 100。評審會讀取問題、工具查詢結果與回答；評審 RCA 時會讀取事件事實與 RCA。

- 評審依設定的百分比從新回答中抽樣。同一個回答無論抽樣幾次，結果都相同。
- 回答若被評為**沒有幫助**，評審一定會評分，但已評過的回答不會重評。
- 評審給的分數低於待審門檻時，會再評一次，取兩次的平均分數。
- 評審不會為個人對話評分。
- 評審會以最後儲存該評審的使用者所用的介面語言撰寫理由。
- 評審的模型呼叫計入組織的每日 token 預算，並在用量的來源分布中顯示為**品質評分**。預算用完時，評審不會為新回答評分。

所有評審都以內建 Prompt **回答評審**（用途為 `evaluation`）作為指令，組織可在**設定 → Prompt 管理**中覆寫。不論 Prompt 如何撰寫，評審都會以固定格式傳回分數。

回答若經評審評分，就取評審分數的平均值，否則取規則分數。

## 品質頁籤

開啟 **Mole Agent → 品質**。**總覽**與**回答**可查看最近 7、30 或 90 天的資料，也可篩選單一來源。

| 檢視 | 內容 |
|---|---|
| **總覽** | 顯示已評分的回答數、規則與評審的平均分數、評為有幫助與沒有幫助的回答數，以及待審數。下方顯示每日分數、各規則項目，以及依來源、Prompt 版本、Skill 與模型分組的結果。 |
| **回答** | 顯示已評分的回答，最新的排在前面；**只看低分**只顯示分數低於待審門檻的回答。點選任一列，即可查看完整的問題與回答、各規則項目查得的事實、各評審的分數與理由，以及該回答的待審紀錄。選擇**開啟對話**或**開啟事件**，即可前往對應的對話或事件。 |
| **待審** | 等待審核、已採納與已駁回的回答。 |
| **資料缺口** | 從回答的工具呼叫過程找出缺少的資料。請參閱[資料缺口](#資料缺口)。 |
| **演練** | 重新調查已解決的事件，比對調查結論與已確認的根本原因後評分。請參閱[演練](#演練)。 |
| **評審** | 評審與設定。 |

### 審核回答

回答在下列情況會進入待審：

| 原因 | 時機 |
|---|---|
| **分數低** | 評審重評後，分數仍低於待審門檻；未經評審評分的回答，則看規則分數是否低於門檻。 |
| **被評為沒有幫助** | 提問者評為**沒有幫助**。 |
| **隨機抽中** | 依**隨機複審**的比例抽中，用來確認分數是否可信。 |

每個回答只會進入待審一次。開啟回答，在**備註**中寫明錯誤之處與正確回答應涵蓋的重點，然後選擇：

- **採納**：回答有問題，將其加入迴歸集。Prompt 檢查重新回答這個問題時，會提供備註供評審參考。
- **駁回**：回答沒有問題。

### 評審與設定

在**評審**中選擇**新增評審**，開啟表單：

| 欄位 | 說明 |
|---|---|
| **名稱** | 在組織內不得重複。 |
| **評分標準** | 說明好的回答應符合哪些要求，以及哪些情況會扣分，最多 4000 個字元。表單已預填一份可編輯的評分標準。 |
| **回答** | 團隊對話、自動化、事件 RCA。 |
| **抽樣比例** | 新回答中要評分的百分比，範圍為 0 到 100。 |
| **模型服務**與**模型** | 留空時，使用組織中第一個可用的模型服務及其預設模型。 |
| **溫度** | 0 到 1；設為 0 可讓分數更穩定。 |
| **啟用** | 停用的評審不會為任何回答評分。 |

每個組織最多可有 10 個評審。刪除評審後，系統會保留該評審給過的分數。

評審下方的設定：

| 設定 | 預設 | 說明 |
|---|---|---|
| **待審門檻** | 60 | 分數低於此門檻的回答會進入待審。 |
| **隨機複審** | 0 | 從其餘回答中隨機抽入待審的百分比。 |
| **將 Prompt 設為預設前** | 檢查，品質下降時再次確認 | 請參閱下文。 |

### 資料缺口

依規則為回答評分時，系統也會檢查工具呼叫過程，找出 Mole Agent 缺少的資料。這不影響分數：缺口反映的是資料問題，而非回答本身。**資料缺口**彙整最近 7、30 或 90 天的情況。

| 類型 | 判定條件 | 如何補足 |
|---|---|---|
| **資料在哪裡** | 查詢同一個資料流達 3 次以上，且多數查詢沒有結果或出錯；或檢視結構達 3 次以上（例如資料流結構、資料流清單、指標名稱與標籤）。 | 在服務目錄的資料入口或知識庫中的 `MOLE.md`，寫明各服務的資料位置與篩選方式。 |
| **服務名稱** | 在指標或 APM 中查到某個服務的資料，但以同一名稱查詢日誌或追蹤時沒有結果，且沒有其他查詢在該資料流中找到此服務。 | 在各類資料中為同一服務使用相同的名稱（`service.name`），或在服務目錄中將其他名稱設為別名。 |
| **先扼要整理再看** | 擷取原始日誌或原始序列達 2 次以上，每次都傳回大量資料列，但未使用**分析日誌模式**或**分析指標趨勢**。 | 確認組織的 Agent Profile 工具集是否排除了這兩個工具。 |

此檢視依資料流與服務列出反覆出現的缺口，並顯示遇到缺口的回答數及最近一次出現的時間。點選下方的回答即可查看分數。個人對話只計入總計，不會列出查詢內容。

### 演練

演練會將已解決的事件視為正在發生，讓 Mole Agent 重新調查，再比對結論與事後確認的根本原因並評分。更換模型、Prompt 或工具後，重新執行所有演練，即可確認調查品質是否改善。

**新增演練**會列出最近 180 天內已解決，且事後檢討中記載根本原因（**根本原因**一節的內容）的事件。預設以事後檢討中的根本原因為參考，也可自行填寫。選擇**其他事件**時，請填寫事件 ID 與根本原因。每個事件只能有一個演練，每個組織最多可有 100 個。

每次執行：

- 以發起者的身分執行，發起者須有事件的讀取權限。無須人工值守，僅讀取資料，最長 10 分鐘。
- 取得事件觸發時的事實（摘要、嚴重程度、服務、標籤、觸發事件的查詢）與告警規則提供的排查線索，查看事件開始前 1 小時到開始後 30 分鐘的資料。
- 無法讀取事後的調查結果與處置紀錄，包括事件備註、時間軸、RCA、事後檢討、工單與核准紀錄，也無法讀取相似事件。
- 產生一則不會列在對話清單中的對話。在執行紀錄中選擇**查看調查**即可開啟，僅供檢視。

調查結束後，模型會比對調查找出的根本原因與參考根本原因，給出 1 到 5 分（顯示為 0 到 100），並以發起者所用的介面語言撰寫理由。系統會使用第一個已啟用評審的模型；如果沒有已啟用的評審，則使用組織中第一個可用的模型服務。模型呼叫計入每日 token 預算，來源記為**品質評分**。如果調查失敗、停止或未產生回答，系統不會評分，並會記錄原因。

選擇**執行**以啟動單一演練；選擇**全部重新執行**以啟動所有未在執行的演練，一次最多 50 個。新增、執行與刪除演練需要 `agent.quality.manage`。

## 將 Prompt 設為預設前先檢查

對用於對話（**系統指令**）或事件 RCA（**找出根本原因**）的組織 Prompt 選擇**設為預設**時，系統會依組織設定處理：

| 設定 | 尚未檢查 Prompt，或檢查發現品質下降時 |
|---|---|
| **檢查，品質下降時再次確認** | 可在對話框中選擇**開始檢查**或**仍設為預設**。 |
| **檢查，品質下降時禁止設為預設** | 只有通過檢查且品質未下降的 Prompt 才能設為預設。 |
| **不檢查** | 直接設為預設。 |

每次檢查最多取 8 個回答：先從迴歸集挑選，再從負責評分這類回答的第一個評審近期評過的回答中挑選。針對每個回答，使用同一個模型，以目前的預設版本和新版本各重新回答一次，不再呼叫工具。模型會收到原始問題以及該輪工具查得的結果；若為 RCA，則由兩個版本各依事件事實撰寫一份。接著由評審為每一對回答評分。新版本的平均分數比目前的預設版本低 5 分以上，判定為**品質下降**；高 5 分以上，判定為**更好**；其餘判定為**品質未下降**。可比較的回答少於 3 個時，無法判定，不影響設為預設。

對話框會先顯示進度，再顯示每個回答的結果。每次檢查只比較一個 Prompt 版本與一個預設版本：修改 Prompt 或更換預設版本後，須重新檢查。檢查的模型呼叫計入**品質評分**。

其他用途的 Prompt 設為預設時不會檢查。直接修改已設為預設的 Prompt 也不會檢查；如要檢查改動，請另存為新的 Prompt，再設為預設。

## 資料流中的分數

每個分數都會記為內部資料流 `_agent_score_traces` 中的一列，可在**日誌**中查詢：

| 欄位 | 說明 |
|---|---|
| `target_kind`、`target_id` | `chat_answer` 與訊息 ID，或 `incident_rca` 與事件 ID。 |
| `source` | `personal_chat`、`team_chat`、`automation` 或 `incident_rca`。 |
| `scorer`、`scorer_kind` | `rules`，或評審的 ID 與 `evaluator`。 |
| `score`、`samples` | 0 到 1 的分數，以及計算平均分數所用的評分次數。 |
| `tool_success`、`evidence`、`query_validity`、`answer_format`、`completion`、`feedback` | 適用規則項目的分數，範圍為 0 到 1。 |
| `reason`、`evaluator_model` | 評審的理由與使用的模型。 |
| `chat_id`、`team_id`、`automation_id`、`user_id`、`prompt_template_id`、`prompt_version`、`prompt_key`、`provider_id`、`model`、`skill`、`skill_version` | 回答的來源與產生回答時使用的項目。 |

若要在品質下降時收到告警，可在此資料流中建立[異常偵測告警規則](/zh-Hant/alerting)，例如監控評審的平均分數：

```sql
SELECT avg(score) AS value FROM "_agent_score_traces" WHERE scorer_kind = 'evaluator'
```
