大多數事件都始於一次變更。在資料中留下標記的部署，幾分鐘內就能與先前的版本比較；沒有記錄的部署，往往得花上一小時反覆猜測才會被發現。記錄每次部署，在漸進式發布期間比較版本，並事先訂好復原條件。

## 讓每次部署都看得見

| 步驟 | 做法 | 帶來的效益 |
|---|---|---|
| 為每個 Span 標註版本 | 在每個服務的 OpenTelemetry 資源中設定 `service.version`。 | 即使 CI 沒有回報部署，也能在[部署時間軸](/zh-Hant/apm/deployments#發佈時間軸)中查看版本及各版本的比較結果。 |
| 從 CI 回報部署 | 使用預設的接入權杖呼叫 `POST /api/v1/apm/deployments`，附上服務、版本、環境、提交和 CI 執行記錄。請參閱[從 CI 回報部署](/zh-Hant/apm/deployments#從-ci-回報發佈)。 | 在版本旁顯示提交、作者和 CI 執行記錄，並記錄失敗或已復原的部署。 |
| 回報設定與功能開關 | 使用同一個端點，將 `kind` 設為 `configuration` 或 `feature_flag`。 | 即使不是部署，變更也會顯示在應用程式效能的分析結果旁。 |
| 為前端標註版本 | 設定使用者體驗 SDK 的 `version`，並在同一個 CI 工作中上傳 Source Map 或 Symbols。請參閱 [RUM Source Maps 與 Symbols](/zh-Hant/rum/source-maps)。 | 取得可讀的堆疊追蹤，並辨識使用者體驗問題是在哪個版本發生迴歸。 |

在所有地方使用相同的版本字串：映像標籤、`service.version`、部署回報和使用者體驗版本。

## 部署前掌握基準

開始漸進式發布前，先記下服務目前的表現：主要端點的錯誤率和 P95、[SLO](/zh-Hant/apm#服務等級目標) 的消耗速率，以及尚未解決的使用者體驗問題。針對關鍵路徑的[合成監控檢查](/zh-Hant/synthetics)，選取 **立即執行** 執行一次檢查，以免把部署前就存在的失敗誤認為是部署造成的。

記下復原條件，例如：版本的錯誤率評為 **變差**、某項關鍵合成監控檢查連續失敗兩次，或觸發高消耗速率警示。

## 在漸進式發布期間比較版本

- 兩個版本同時執行時，[部署](/zh-Hant/apm/deployments#金絲雀)頁面的 Canary 卡片會並排比較各版本處理的請求比例、錯誤和延遲，並顯示新版本的比較結果。
- 每個版本都會與前一個版本比較，得出 **變差**、**變好**、**無明顯變化** 或 **請求數不足** 的結果。比較需要足夠的請求數，預設為 1,000 個；請讓 Canary 部署執行到達到所需的請求數。
- 按一下比較結果以開啟 **比較兩個版本**，查看哪些端點變慢、哪些錯誤變多。
- 在使用者體驗中，依新版本篩選探索頁面和錯誤問題，並留意標為 **迴歸** 的問題：這些問題先前已解決，卻在較新的版本中再次出現。

## 使用自動化監看部署

透過 CI 工作啟動 Mole Agent [自動化](/zh-Hant/automations#從-ci/cd-啟動)，即可先檢查部署：在部署步驟中呼叫自動化的觸發介面並附上變更說明。Mole Agent 會依照自動化指示執行，例如比較新舊版本，然後在對話中回報結果。是否復原仍由人工決定。

## 做出決定並記錄

符合復原條件就執行復原，不必等到完全確認。從 CI 回報復原，將 `status` 設為 `rolled_back`，讓時間軸顯示這次復原，後續比較也能使用正確的基準。

若決定保留新版本，請在接下來一天內持續查看 SLO。記憶體洩漏、佇列逐漸堆積等緩慢的效能衰退，往往要幾小時後才會顯現。

## 驗收標準

- 每個服務都傳送 `service.version`，每次正式環境部署都會連同提交顯示在部署時間軸中。
- 每次前端部署都已上傳與回報版本相符的 Source Map 或 Symbols。
- 開始漸進式發布前，已記下復原條件。
- 每次部署都已取得比較結果，或已讓 Canary 部署執行到達到所需的請求數。
