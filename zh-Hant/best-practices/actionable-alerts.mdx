服務頻繁觸發緊急通知，卻很少帶來有效處置時，請同時檢查偵測策略與回應策略。從客戶能察覺的故障著手，為每條需要立即回應的規則明確定義處置動作。

## 根據影響決定是否通知值班人員

優先關注業務請求失敗、延遲持續升高或關鍵路徑的[合成監控測試](/zh-Hant/synthetics)失敗。[SLO 燃燒率告警](/zh-Hant/apm#燃燒率警示)依錯誤預算發出通知，而不是每次出現尖峰都通知。將有助於診斷的症狀放在儀表板和調查檢視中；只有及時處置能避免影響客戶時，才直接觸發緊急通知。

查詢低流量服務的錯誤率時，也要設定最低請求量。只有一次請求且失敗時，錯誤率雖然很高，卻不足以證明發生大範圍故障。根據具代表性的正常時段與故障時段選擇閾值，避免直接複製其他服務的數值；規則工作台中的 **測試規則** 會以最近 6 小時的資料繪出查詢結果和閾值線。

## 根據問題選擇規則

| 情境 | 建議規則 | 注意事項 |
|---|---|---|
| 錯誤率或延遲持續升高 | [閾值規則](/zh-Hant/alerting/rules#建立閾值規則)，**並持續** 幾分鐘 | 延長確認時間能減少短暫波動造成的雜訊，但也會延後偵測。 |
| 同一故障出現在多部主機或多個服務上 | 設定了[**依維度分組**](/zh-Hant/alerting/rules#依維度分組)的閾值規則 | 每組各建立一個事件，因此只使用穩定的欄位分組。 |
| 有歷史資料且基準線持續變動 | [異常規則](/zh-Hant/alerting/rules#異常規則)，流量呈現每週週期時啟用 **每週季節性** | 發布、週期性波動與流量變化都可能改變基準線。 |
| 符合條件的事件突然增加，需要立即處理 | 透過 API 建立的[即時規則](/zh-Hant/alerting/rules#即時規則) | 每個接入節點獨立計數，重新啟動後從零開始。 |

**並持續** 的分鐘數會換算成評估次數，因此請一併規劃評估間隔和查詢視窗。重疊的視窗會重複使用觀測資料，連續符合條件不代表樣本彼此獨立。即時規則的 `for_periods` 只允許 `0` 或 `1`，無法直接套用跨多個週期的防抖做法。

將[恢復閾值](/zh-Hant/alerting/rules#復原條件與無資料處理)設在觸發閾值較接近正常值的一側，避免數值在閾值附近來回波動時反覆觸發和恢復。先釐清沒有資料代表什麼：**以 0 計算** 適合計數，**建立無資料事件** 適合資料流不能中斷的資料來源。

## 明確指定負責對象與升級路徑

每條會通知值班人員的規則都要填寫 **服務** 和 **處理指南 / Runbook URL**。[升級策略](/zh-Hant/alerting/on-call#升級策略)決定通知對象，而不是由規則決定；在規則工作台中儲存的規則使用名為 `default` 的策略。優先使用穩定的分組欄位和標籤。將唯一的請求識別碼用於調查，不要依請求識別碼分組，以免每次觸發都建立個別事件。

根據嚴重程度與人員安排設定確認逾時。使用各排班的 **未來 7 天預覽**，檢查跨時區和交接時段是否都有值班人員。在受控演練中刻意不確認事件，驗證是否會進入下一階段的升級流程。

計畫性維護期間，使用範圍明確且有時間限制的[靜默策略](/zh-Hant/alerting/silences#靜默策略)，註明受影響的服務，並讓策略在到期時自動結束。靜默會阻止通知傳送，但不能證明服務已恢復。

## 演練完整回應流程

連接器的 **測試連線** 成功，只能驗證流程的一部分。使用[觸發規則](/zh-Hant/api/alerting/trigger-rule) API 觸發一條受控規則，檢查事件建立、通知路由、收件人是否實際收到通知，以及事件的確認與恢復。檢查確認事件後是否停止升級，以及故障排除後事件是否如預期進入已解決狀態。

在演練中加入主要傳送路徑失敗的情境。向預期收件人確認已設定的[備援路由](/zh-Hant/notification-channels#設定備援路由)是否有效，並在[傳送記錄](/zh-Hant/notification-channels#檢視和重試傳送)中檢查每次傳送嘗試。不要把已設定備援路由當成傳送成功。

## 在事件結束後進行事後檢討

比較偵測延遲、確認延遲、重複通知和未偵測到的客戶影響。[告警 → 洞察](/zh-Hant/alerting/incidents#洞察)列出 **主要觸發規則**，也會顯示 **快速恢復的事件** 所占比例（比例偏高可能代表規則產生較多雜訊）；[自動化](/zh-Hant/automations)的 **告警降噪週報** 範本會讓 Mole Agent 為每條產生雜訊的規則提供調整建議。

刪除沒有有效回應動作的規則，調整造成雜訊的閾值，並保留每次調整的依據。同時使用正常流量與已知故障情境驗證新策略。

## 驗收標準

- 每條會通知值班人員的規則都以客戶影響為出發點：請求失敗、延遲、合成監控測試失敗或 SLO 錯誤預算消耗。
- 每條會通知值班人員的規則都註明服務和 Runbook，且升級策略能確實通知相關人員。
- 規則在觸發閾值較接近正常值的一側恢復，且無資料時的處理方式經過明確選擇。
- 受控演練能通知值班人員，無人確認時會升級，事件最終會進入已解決狀態。
- 每週檢查主要觸發規則。
