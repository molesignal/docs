客戶不在意是哪個服務發生故障，只在意能不能結帳。選出最重要的幾條旅程，從三個面向監控每條旅程：從外部模擬操作的合成監控、實際走過旅程的使用者，以及支援旅程的後端。

| 面向 | 工具 | 能偵測 | 無法偵測 |
|---|---|---|---|
| 外部 | [合成監控](/zh-Hant/synthetics) | 任何時候發生的中斷（即使沒有流量）、憑證過期、DNS 故障。 | 只影響部分使用者、裝置或資料的問題。 |
| 真實使用者 | [使用者體驗](/zh-Hant/rum) | 載入緩慢的頁面、前端錯誤、操作受挫的行為，以及使用者的實際操作。 | 沒有使用者走過這條旅程時，無法偵測到問題。 |
| 後端 | [應用程式效能 SLO](/zh-Hant/apm#服務等級目標) | 支援旅程的端點錯誤、延遲，以及錯誤預算。 | 請求抵達後端前發生的故障。 |

## 定義旅程與成功標準

將旅程拆成步驟，例如：開啟商品頁、加入購物車、付款、看到確認頁。為每個步驟列出對應的頁面或端點，以及成功標準：狀態碼、頁面內容和時間上限，例如「3 秒內確認付款」。

在各項工具中維持命名一致：使用者體驗使用相同的檢視名稱，應用程式效能使用相同的路由範本，合成監控則使用旅程名稱。

## 從外部探測

1. 為每個關鍵 API 步驟建立 **HTTP / API** 檢查，並為整條旅程建立 **瀏覽器** 檢查。請參閱[建立並發布檢查](/zh-Hant/synthetics#建立並發布檢查)。
2. 為成功標準設定斷言：狀態碼和確認文字使用 **嚴重** 斷言，時間上限使用 **警告** 斷言。
3. 至少從兩個地點執行檢查，避免將單一網路路徑故障誤判為整體中斷。設定失敗和復原閾值，避免狀態反覆切換。
4. 先執行 **測試修訂版本**，再執行 **發布修訂**。編輯時會建立新草稿，已發布的檢查會持續執行，直到新版本通過驗證。

瀏覽器檢查每分鐘最多執行一次，API 檢查可執行得更頻繁。使用測試帳號和測試付款方式，切勿使用真實的客戶資料。

## 關注真實使用者

在應用程式中整合 [Browser RUM SDK](/zh-Hant/rum/browser-sdk) 後：

- 在[效能](/zh-Hant/rum/performance)中，查看旅程各頁面的 LCP、INP 和 CLS 第 75 百分位數。
- 在[受挫訊號](/zh-Hant/rum/frustration)中，查看旅程各步驟的連續快速點擊、無反應點擊和錯誤點擊。
- 在[錯誤](/zh-Hant/rum/errors)中，將旅程的問題指派給負責團隊。
- 開啟失敗旅程的[工作階段重播](/zh-Hant/rum/session-replay)，查看使用者當時看到的畫面，並透過[隱私權設定](/zh-Hant/rum/privacy)遮蔽個人資料。

針對能反映旅程對許多使用者失效的指標建立 [RUM 警示](/zh-Hant/rum/alerts)，例如錯誤率或關鍵頁面的某項 Vital 指標。

## 使用 SLO 追蹤後端

為支援關鍵步驟的端點（例如付款端點）建立 [SLO](/zh-Hant/apm#服務等級目標)，選取 **成功且不超過閾值**，並將延遲閾值設為旅程的時間上限。接著新增[消耗速率警示](/zh-Hant/apm#燃燒率警示)：錯誤預算消耗得快時發出緊急通知，消耗得慢時發出警告。

## 通知客戶

在[狀態頁面](/zh-Hant/status-pages)上為這條旅程建立元件，例如「結帳」。透過[自動化發布](/zh-Hant/status-pages#自動化發布)將元件與旅程的合成監控檢查和警示規則連結起來。起初選取 **手動核准**：確認故障後，系統會產生一則更新草稿，由應變人員核准後發布。

## 每週檢視

在應用程式內建的使用者體驗儀表板上按一下 **建立副本**，加入合成監控結果和 SLO，並每週傳送一份[報告](/zh-Hant/reports)給團隊。不只要看事件，也要留意趨勢：如果某項 Vital 指標每週都變差一點，下一次發布就可能讓旅程中斷。

## 驗收標準

- 每條關鍵旅程至少有一項已發布的合成監控檢查，且從兩個地點執行時皆通過。
- 使用者體驗監控涵蓋旅程的所有頁面，且每項錯誤都有負責人。
- 支援關鍵步驟的後端設有 SLO 和消耗速率警示。
- 狀態頁面上有這條旅程的元件，且已連結至對應的合成監控檢查或警示規則。
- 在測試環境中讓檢查失敗時，值班人員會收到通知，系統也會產生一則更新草稿。
