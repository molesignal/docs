事件之所以讓人緊張，是因為好幾件事必須同時進行：要有人接手、要通知客戶，還要找出原因。始終以 **警示** 中的該事件為主軸。從狀態頁到事後檢討，其他項目都連回該事件。

## 接手事件

從通知開啟事件，或開啟 **警示 → 警示事件** 中的 **等待確認** 分頁。在確認逾時前按一下 **確認**。確認後會停止升級通知，且開啟事件時會顯示負責人，避免重複處理。

多個事件由同一個原因引起時，確認最能說明原因的事件，並在處理期間[靜默](/zh-Hant/alerting/silences#靜默單一事件)其餘事件。透過[語意分組](/zh-Hant/alerting/silences#語意分組)歸在同一組的事件，可以透過 API 一併確認。

## 評估影響

進行任何變更前，先閱讀[事件詳細資料](/zh-Hant/alerting/incidents#事件詳細資料)：

| 區塊 | 回答的問題 |
|---|---|
| **觸發查詢** | 哪個數值超過門檻、超過多少、從何時開始？ |
| **影響範圍** | 受影響的服務會波及哪些服務和頁面？ |
| **工作階段樣本** | 若事件影響使用者體驗，實際使用者看到了什麼？每個工作階段都可以重播。 |
| **跨訊號參照** | 涉及哪些服務、主機和追蹤？ |

查看受影響服務的 [SLO](/zh-Hant/apm#服務等級目標)：錯誤預算消耗速率高，表示客戶現在就感受得到問題。

## 儘早通知客戶

若客戶受到影響，在查明原因前就發布一則[狀態頁事件](/zh-Hant/status-pages#事件生命週期)：

1. 建立事件草稿，選擇受影響的元件及其影響程度。
2. 以 **調查中** 狀態發布第一則更新，說明客戶看到了什麼，以及何時會發布下一則更新。
3. 每次狀態變更都新增一則更新：**已確認**、**監控中**、**已解決**。發布後無法修改更新，只能再發布新的更新。

[自動化發布](/zh-Hant/status-pages#自動化發布)可以根據警示起草狀態頁事件並等待核准，讓第一則更新在幾秒內準備就緒。

## 找出原因

沿用事件的時間範圍，從症狀一路追查到原因：

- 使用 **開啟觸發查詢** 重新執行觸發事件的查詢，再用 **相關日誌** 和 **相關指標** 查看前後脈絡。若要在日誌、追蹤、指標和工作階段之間切換，請參閱[跨訊號關聯](/zh-Hant/correlation)。
- 查找近期變更：查看服務的[發布時間軸](/zh-Hant/apm/deployments#發佈時間軸)，以及[應用程式效能發現前後的變更](/zh-Hant/apm/insights#發現前後的變更)。
- 閱讀 [AI 根因](/zh-Hant/alerting/incidents#ai-根因)，或按一下 **產生**。將結果視為待驗證的線索，並評為 **有幫助** 或 **沒有幫助**。
- 在服務頁面使用 **調查** 向 [Mole Agent](/zh-Hant/agent) 提問。Mole Agent 會將服務健康狀態、上下游服務和發現附加到對話中。

排查時，在團隊的事件頻道記錄每項假設及其證據。事後檢討需要這份時間軸。

## 先止血，再復原

優先採取最快且安全的止血措施，例如回復到先前版本或關閉功能開關，而不是在壓力下修正問題。止血後：

- 觀察觸發查詢的結果是否恢復正常。規則符合恢復條件時，尚未確認的事件會自動解決；已確認的事件則需手動按一下 **解決**。
- 如果相關事件只是重複反映已知問題，請使用[靜默單一事件](/zh-Hant/alerting/silences#靜默單一事件)，而不是靜默規則本身。
- 將狀態頁更新為 **監控中**，等服務穩定一段時間後，再更新為 **已解決**。

## 整理經驗

在幾天內為狀態頁事件撰寫[事後檢討](/zh-Hant/status-pages#事件事後檢討)，記錄事件經過、影響、時間軸、原因及後續改善措施。審閱期間先儲存為草稿，等事件解決後再發布。Mole Agent 可以根據事件記錄起草事後檢討。

接著用[洞察](/zh-Hant/alerting/incidents#洞察)改善偵測：透過 **快速恢復的事件** 和 **主要觸發規則** 找出造成警示雜訊的規則。如果通知太晚，表示缺少規則，或規則觸發得太慢。請參閱[讓正式環境的警示指引應變行動](/zh-Hant/best-practices/actionable-alerts)。

## 驗收標準

- 每個事件都在確認逾時前指派了負責人。
- 若事件影響客戶，客戶在詢問前就已從狀態頁得知情況。
- 事後檢討載明原因、影響、時間軸，以及每項後續工作的負責人。
- 每項改善偵測的後續工作都有一項具體的規則變更，且已使用實際資料測試。
