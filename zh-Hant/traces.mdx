開啟**追蹤**，在完整 trace、單一 span、RED 下鑽和服務圖之間切換。

## 瀏覽 trace 與 span

**追蹤**分頁每個請求一列：結束狀態（根 span 的 HTTP 狀態碼，或**正常**、**錯誤**）、開始時間、服務與操作、相對於本頁最長 trace 的耗時、span 數、錯誤數和 trace ID。點擊**開始時間**、**耗時**、**Span 數**或**錯誤**欄標題，即可依該欄排序。表格上方的直方圖會統計符合查詢的全部 trace，旁邊的圖表則繪製這些 trace 耗時的 p50、p95 和 p99。

**Span** 分頁每個符合的 span 一列，帶有 span 種類和自身耗時。在這裡，對 span 欄位的篩選條件會針對 span 本身。

查詢編輯器有 **代碼** 和 **查詢建構器** 兩種模式，用標題旁的兩個圖示切換（`</>` 是代碼，積木是查詢建構器）。**代碼** 模式接受欄位查詢（例如 `status_code = 'ERROR'`，或表示耗時超過 500 毫秒的 `duration_ns > 500000000`），也接受針對 trace 串流的 SQL；**查詢建構器** 模式會將欄位查詢顯示為多行篩選條件，每個分支一行。與[日誌](/zh-Hant/logs#查詢分頁)一樣，查詢會在分頁中執行，並可分成兩欄並排，欄位清單可以開啟欄位分析，**分享** 可以複製查詢的連結。網址列同樣帶有已套用的查詢，複製網址即可分享（參見[分享查詢](/zh-Hant/logs#分享查詢)）。

對 span 欄位的比較會保留含有符合 span 的 trace；`!=` 則保留所有 span 都不含該值的 trace。`trace_id`、`duration_ns`、`span_count` 和 `error_count` 會直接在 trace 上比較。`in` 會符合多個值中的任意一個：`service.name in ('checkout', 'payments')`。

與[日誌](/zh-Hant/logs#撰寫查詢)一樣，比較可以用 `AND` 和 `OR` 連接，`AND` 優先，括號可以分組。比較在 `OR` 中的意義不變：`service.name = 'checkout' OR span_count > 50` 會保留含有 `checkout` span 的 trace，以及 span 數超過 50 的 trace。未指定欄位的文字（例如 `timeout`）會在 trace ID、span ID、服務、操作和狀態中尋找。**Span** 分頁和 RED 下鑽會依單一 span 解讀同一條查詢：span 符合 `a` 或 `b` 即符合 `a OR b`。

欄位清單與結果並排。**常用欄位**排在最前面：`service.name`、`name`、`status_code`、HTTP 狀態碼和 `duration_ns`。展開欄位可以看到已載入 trace 中的值。**只看這個值**會將該值加入查詢（含有多個分支的查詢會先加上括號，使該值套用至整條查詢）；同一欄位再選第二個值時，會與第一個值合併為 `in` 清單，因此可以勾選多個值。**排除這個值**會排除該值。

**追蹤**表格上方的**欄位設定**可以顯示、隱藏及調整欄位順序，也可以將每筆 trace 根 span 的欄位新增為欄位；欄位清單裡這類欄位的眼睛圖示作用相同。欄位安排會依資料流為每位使用者儲存，**還原預設值**可以回到表格的預設欄位。

## RED 下鑽

**RED** 分頁會讀取符合查詢之請求的速率、錯誤和耗時：預設為服務接收請求的 Span，也可以改為所有 Span。**拆分依據**可以選取任意 Span 欄位，包括租用戶這類[業務鍵](/zh-Hant/business-context)；點擊一個值會將查詢縮小到它並繼續往下一層拆分，在延遲圖上拖選則可將查詢縮小到一段耗時。

**比較**會將失敗的請求，或慢於 p95、p99 的請求，與查詢中的其他請求逐欄位比較。兩組值重疊最少的欄位會排在前面，每個欄位會列出佔比差距最大的值，以及兩組在這個欄位上的差距，從 0%（值組成相同）到 100%（沒有共同值）：慢請求集中在哪個地區、版本或租用戶，會排在最上面。ID、時間點和 JSON 欄位不參與比較，比較失敗請求時狀態也不參與。每組最多讀取 1,000 個 Span 作為樣本，卡片上會註明。點擊欄位會開啟它的拆分，點擊值則會將查詢縮小到它。Mole Agent 會使用 `compare_attribute_distributions` 進行相同的比較。

## 檢查單筆 trace

點擊一列，trace 會在清單上方的抽屜中開啟。拖曳抽屜左邊緣可調整寬度，寬度會保留給下一筆 trace。按 **J** 和 **K** 可切換到清單中的下一筆和上一筆 trace，抽屜也可以開啟該 trace 的詳細資料頁面。

trace 的標頭會固定顯示：根服務與操作、HTTP 狀態碼、錯誤數、耗時、開始時間、span 數、服務數、深度和 trace ID。**相關日誌** 和 **服務指標** 會開啟該 trace 前後的對應訊號。**效能剖析** 會開啟記錄了該 trace ID 的 profile；沒有這樣的 profile 時，則開啟該 trace 前後幾分鐘內的 profile。**使用者工作階段** 會開啟該 trace 所服務的 [RUM](/zh-Hant/rum) 工作階段：span 在 `session.id` 或 `session_id` 中寫明的工作階段；未寫明時，則是瀏覽器請求在 `traceparent` 中攜帶該 trace ID 的工作階段。

標頭末尾的 **下載追蹤** 會將 trace 儲存為檔案：

| 格式 | 內容 |
|---|---|
| **JSON** | span 會依[追蹤 API](/zh-Hant/api/web/trace#讀取單一追蹤)傳回的原樣儲存。 |
| **OTLP JSON** | OTLP/JSON 匯出請求，結構為 `resourceSpans` → `scopeSpans` → `spans`，可以重新交給 Collector 或 OTLP HTTP 接入。時間是以十進位字串表示的奈秒。 |

四種檢視會顯示 span：

| 檢視 | 顯示內容 |
|---|---|
| **瀑布圖** | 時間軸上的 span 樹，每個服務一種顏色。上方的縮圖可拖選一段時間放大時間軸。搜尋可逐一跳到符合的 span，開關則可只顯示失敗的 span，也可聚焦某個 span 及其下游。 |
| **火焰圖** | 每個 span 是呼叫方下方的一個區塊。按兩下可將時間軸放大到該 span。 |
| **Span 清單** | 依服務和操作分組的 span，包含數量、錯誤、耗時、自身耗時，以及佔 trace 自身耗時的比例。 |
| **服務地圖** | 該 trace 涉及的服務及其相互呼叫，包含呼叫次數、耗時和失敗數。 |

瀑布圖和火焰圖工具列中的 **關鍵路徑** 會繪出 trace 端到端耗時所等待的 span。關鍵路徑會從根 span 的結束時間開始向前回溯：每個時刻沿著在此之前最晚結束的子 span 走（子 span 依呼叫它的 span 截斷），再從這個子 span 的開始時間繼續回溯。在該時刻仍在執行的子 span 會與路徑上的子 span 平行，不在關鍵路徑上。沒有子 span 涵蓋的時間會算作呼叫方自身的時間。在瀑布圖中，每個長條上的一條線會標出該 span 位於關鍵路徑上的時段，其他 span 則會變淡。圖例會顯示關鍵路徑的長度，以及每個服務所佔的比例。開關開啟後，切換到其他 trace 時會保持開啟。

選取 span 的詳細資料會顯示在檢視旁邊，寬度可以拖曳調整。詳細資料有 **屬性**、**資源**、**事件**、**連結**、**日誌**、**指標** 和 **效能分析** 分頁。**連結** 還會列出其他 trace 中連結到該 span 的 span。**日誌** 會顯示攜帶該 trace ID 的日誌，範圍可以是該 span 或整筆 trace。**指標** 會繪製該 span 所屬服務與操作在前後幾分鐘內的請求數、錯誤數和 p95 耗時。

**效能分析** 會顯示該 span 執行期間 profiler 取樣的樣本。profiler 記錄樣本時會帶上追蹤脈絡（例如 [OTLP Profiles](/zh-Hant/profiles)），樣本才會關聯到 span。有相關樣本時，分頁會依自身消耗列出某一種 profile 類型中消耗最多的函式，**開啟火焰圖** 會繪製這些樣本，**在 Profiles 中開啟** 則會在 Profiles 頁面開啟它們。瀑布圖中帶火焰標記的列表示該 span 有相關樣本。沒有相關樣本時，**查看此 span 前後的 profile** 會開啟該 span 前後幾分鐘內的 profile。

每筆 trace 也有自己的詳細資料頁面，開啟 trace 連結時會進入。如果瀏覽器 RUM 工作階段帶有 session 識別碼，可以開啟**工作階段追蹤** 查看相關後端請求。

## 比較兩筆 trace

點擊**追蹤**表格上方的 **選取兩筆追蹤來比較**，再點擊兩列。先選取的 trace 是 **A**，後選取的是 **B**。點擊 **比較**，會在 A 的詳細資料頁面開啟比較。在 trace 標頭，**與另一筆追蹤比較** 會接受另一筆 trace 的 trace ID。只憑 trace ID 開啟的 trace，只要經 OTLP 寫入，且開始時間在最近 31 天內，就能找到。

比較頁會並列顯示兩筆 trace、各自的耗時，以及 B 比 A 慢或快多少。下方有三個分頁，都會將變化最大的排在最前面：

| 分頁 | 顯示內容 |
|---|---|
| **依服務** | 每個服務在 A 和 B 中的 span 數與自身耗時，以及從 A 到 B 的變化。 |
| **依操作** | 每個服務的每個操作的相同內容。 |
| **僅一側有** | 一筆 trace 有而另一筆沒有的呼叫。span 會依其上方各 span 的服務與操作進行比對，因此從兩個地方發出的同一個查詢會算作兩個呼叫。缺少的呼叫會將其下方呼叫的 span 計入自身。 |

自身耗時是 span 自己執行的時間，不含等待它所呼叫 span 的時間。頁面標頭有 **交換 A 和 B** 和 **結束比較**，頁面網址會保留兩筆 trace，因此可以分享比較結果。

## 服務圖與服務目錄

**服務圖**會從 trace span 自動衍生節點與邊，顯示請求率、錯誤率與延遲的關係，無需單獨維護拓撲。

**服務目錄**會依觀察到的服務與操作彙總，便於從服務進入目前的 trace。

## 接入與傳播

透過 OTLP HTTP 或外部 OTLP gRPC Receiver 傳送 trace。MoleSignal 會保留標準 W3C Trace Context 和 OpenTelemetry 語意屬性。受支援的應用程式請求會在回應中傳回 `X-Request-Id` 與 `X-Trace-Id`。

資料流上的[即時管線](/zh-Hant/pipelines#鏈路)會在尾端取樣之後、寫入之前修改或捨棄 span。trace 清單及其中的 span 數、錯誤數會依寫入的 span 顯示。

## 權限

組織工作區需要 `traces.read`。平台管理員在受保護的 `_sys` 遙測作用域中使用 `sys.telemetry.read`。
