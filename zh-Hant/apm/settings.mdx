**APM → 設定**儲存組織的 APM 設定。每張卡片分別用**儲存**儲存，**復原變更**放棄尚未儲存的輸入。儲存需要 `apm.settings.manage` 權限，擁有者、管理員和編輯者都具備該權限；沒有該權限時頁面只能檢視設定。

儲存的設定在儲存它的節點上立即生效，在其他節點上 30 秒內生效。命名規則和環境對應會作用於此後讀到的 Span，APM 已經儲存的資料會保留原來的名稱。健康判定線、預設 Apdex 閾值、服務別名和服務目錄要求會作用於每一次讀取，已儲存的資料也一樣。

## 收集品質

第一張卡片讀取過去一天的資料，列出需要處理的問題和可以透過設定改善的地方：

| 發現 | 含義 |
|---|---|
| 超過基數上限 | 某類名稱（例如端點）超過了每小時的上限，多出的部分計入**其他**。對於能管理平台設定的使用者，**調整基數上限**會跳至基數上限卡片。 |
| APM 漏讀了 Span | 投影在這一天中留下了缺口。 |
| APM 資料延遲 | 最近一個完整的分鐘已經是幾分鐘之前。 |
| 服務沒有回報某個屬性 | 服務沒有回報 `deployment.environment.name`、`service.version` 或 `service.instance.id`。**前往設定**開啟 OpenTelemetry 接入指南。 |
| 環境名稱只有大小寫不同 | 例如 `Production` 和 `production`。**全部讀作**會將對應加到環境對應卡片。 |
| 名稱帶有自動產生的後綴 | 服務名稱像 Pod 名稱，例如 `checkout-7d9f8b6c5-x2x7k`。**新增命名規則**會新增一條將它讀作 `checkout` 的規則。 |
| 日誌未帶 TraceID | 服務最近一小時的日誌都未帶 TraceID，日誌無法跳至對應的 Trace。**前往設定**開啟 OpenTelemetry 日誌接入指南。 |
| 只有部分日誌能對上 Trace | 服務最近一小時帶 TraceID 的日誌不到 90%，或者從中取樣的 TraceID 在留存的 Trace 裡找到的不到 80%。 |
| 服務沒有回報執行位置 | 服務的執行個體都沒有回報 `host.name`、`k8s.pod.name`、`k8s.node.name` 或 `container.id`。**前往設定**開啟 OpenTelemetry Trace 接入指南。 |
| APM 不認識的服務名稱 | 日誌或指標裡的服務名稱在套用命名規則和別名後，對不上任何 APM 服務。**命名規則**會跳至命名規則卡片。 |
| 沒有回報變更 | 服務過去一週沒有回報部署、設定變更或 Feature Flag 變更。**接入變更**開啟交付管線的接入指南。 |

後五項來自[關聯品質報告](/zh-Hant/api/apm#讀取服務的關聯品質)：日誌和指標看最近一小時，變更看過去一週。

加到卡片裡的建議在點擊**儲存**之前不會生效。

## 健康判定與閾值

| 設定 | 預設值 | 範圍 |
|---|---|---|
| 錯誤率的**警告**和**嚴重** | 2% 和 10% | 警告線大於 0 且小於嚴重線，嚴重線最多 100%。 |
| P95 的**警告**和**嚴重** | 500 毫秒和 2,000 毫秒 | 警告線大於 0 且小於嚴重線，嚴重線最多 10 分鐘。 |
| **預設 Apdex** T | 500 毫秒 | 大於 0，最多 1 分鐘。服務目錄中設定了自己 T 的服務保持不變。概覽會按這個 T 計算所有服務合在一起的 Apdex。 |
| **長時間工作**，P99 不低於 | 1,000 毫秒 | 1 毫秒到 10 分鐘。端點列表會將 P99 達到這個值的端點視為長時間工作。 |

這些線決定服務在目錄、服務頁面、服務地圖和概覽健康趨勢中的健康狀態。

## 服務目錄要求

**團隊**、**負責人**和**程式碼儲存庫**分別設定從哪個等級起必須填寫：**不要求**，或者某個等級及以上。缺少該項的服務會在目錄中顯示**缺少**及缺少的項目。沒有設定等級的服務不受此要求限制。

## 服務命名

命名規則會在讀到 Span 時改寫服務名稱。每條規則是一個正規表示式和一個取代文字，取代文字可以用 `$1` 或 `${name}` 參照表示式中的群組。規則會按順序嘗試，第一條符合的規則會改寫名稱；改寫成空名稱時會保持原名。**測試服務名稱**會顯示某個名稱會被讀作什麼。

一個組織最多 20 條規則。追蹤會保留 Span 回報的原名，因此在追蹤中搜尋時要用規則改寫之前的名稱。

## 環境對應

每筆對應會在讀到 Span 時將一個環境名稱讀作另一個，不區分大小寫，例如將 `Production` 和 `prod` 都讀作 `production`。同一個環境最多對應一次，一個組織最多 50 筆對應。

## 業務情境

組織讀取遙測資料時所依據的業務鍵，例如租用戶或方案，以及 Span、日誌和 RUM 事件裡承載每個鍵的欄位，還有最重要的值。服務頁面會依此拆分請求，事件會列出受影響的值。參見[業務情境](/zh-Hant/business-context)。

## 服務別名

別名用舊名稱指代一個服務，兩邊各有自己的 Namespace，留空即為 `default`。別名回報的資料在所有 APM 頁面都會按正式服務讀取，與正式服務自己回報的資料合併，已儲存的資料也一樣。服務地圖和發布回報也會按別名處理。刪除別名後兩者會重新分開。

服務不能是自己的別名，一個名稱只能作為一次別名，別名不能指向另一個別名。一個組織最多 100 個別名。從舊連結開啟別名本身的頁面時，讀取的仍是別名自己的資料。

## 基數上限

具有 `sys.settings.limits.manage` 權限的使用者可以檢視。這些上限對整個平台生效：每小時 APM 對每類名稱最多分別記錄這麼多個，其餘計入**其他**。

| 上限 | 預設值 |
|---|---|
| 每個組織的服務 | 200 |
| 每個服務的端點 | 32 |
| 每個服務的相依性 | 16 |
| 每個相依性的操作 | 32 |
| 每個服務的錯誤群組 | 16 |
| 每個服務的版本 | 16 |
| 每個服務的執行個體 | 256 |

每個上限都是 1 到 100,000 之間的整數。每個節點每 30 秒重新讀取一次。

## 追蹤取樣

具有 `sys.telemetry.read` 權限的使用者可以檢視，修改需要 `sys.telemetry.manage` 權限。取樣策略決定追蹤結束後平台保留哪些追蹤：

- **一般追蹤保留比例**是沒有被規則、錯誤或慢速呼叫保留的追蹤中，最終保留的比例，預設 10%。
- 每條規則會比對 Span 是否符合其**服務**、**路由**和**操作**，耗時不低於**耗時下限 ms**，且在勾選**僅限錯誤**時為錯誤，然後保留、捨棄或按比例保留符合的追蹤。規則會依序在一般比例之前嘗試。

儲存會向所有節點發布新版本的策略。APM 會在取樣之前統計全部追蹤，因此取樣策略不會改變 APM 指標，只會影響哪些追蹤可以開啟。
