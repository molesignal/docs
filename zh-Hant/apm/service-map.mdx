**服務地圖**顯示各服務如何互相呼叫，以及每筆呼叫的健康狀況：請求速率、錯誤率和延遲（即 **RED** 指標）。MoleSignal 根據已傳送的 trace 自動建構服務地圖，除了正常的分散式追蹤之外，不需要額外加入檢測程式碼。

<Info>
  服務地圖與 [APM](/zh-Hant/apm) 使用相同的 trace 輸入，但各自產生不同的投影。服務地圖透過跨服務的父子 span 配對建構拓撲；APM 則在限定範圍內彙總服務、交易、相依性、錯誤和版本。
</Info>

## 服務地圖如何建構

trace span 抵達時，MoleSignal 會將每個 span 與對應的父 span 配對。兩個 span 屬於**不同服務**時，就形成一條呼叫邊——*父服務 → 子服務*——邊的延遲與錯誤狀態取自子 span（被呼叫端）。同一服務內的父子 span 屬於內部呼叫，不會繪製成邊。邊歸入呼叫端所在的環境（`deployment.environment.name` 或 `deployment.environment`）；如果呼叫端沒有環境，則採用被呼叫端的環境。[即時管線](/zh-Hant/pipelines#追蹤)捨棄的 span 不會參與配對。

MoleSignal 會依服務對將邊累計到**一分鐘的時間桶**中，並在背景定期寫入資料庫，因此地圖約在半分鐘內就能反映最新流量。

### 記憶體模式與儲存模式

預設（`intake` 模式）會在接收 span 的節點上，直接在**記憶體**中配對，因此延遲較低。在多節點部署中，如果同一次呼叫的父子 span 由不同節點接收，就無法在記憶體中配對。地圖可能會漏算這些邊，但絕不會產生不存在的邊。

若要在多節點部署中取得完整地圖，請將 **設定 → 一般 → 服務圖資料來源**切換為 **storage（從儲存空間重新計算）**模式。單一節點會定期從**儲存空間中的 trace** 重建服務圖，不論哪個節點接收 span，都能納入計算，但延遲約為 1–2 分鐘。這項設定會儲存在資料庫中，變更後立即生效，不需要重新啟動。

## 需要傳送哪些資料

服務地圖需要符合下列條件的 trace：

- 每個 span 都包含 **`service.name`** 資源屬性（OTLP exporter 會自動設定），而且
- span 之間有**跨服務邊界的父子關係**，也就是一個服務中的 client span 對應到另一個服務中的子 server span。

使用標準的 OpenTelemetry 檢測方式即可產生這兩項資料。將 tracer 指向任一 [trace 接收端點](/zh-Hant/intake)，地圖就會自動顯示資料。

## 拓撲

拓撲端點會將一個時間範圍內的資料彙總成節點（服務）與邊（呼叫）：

```http
GET /api/v1/web/topology?from=2026-06-14T00:00:00Z&to=2026-06-14T01:00:00Z
Authorization: Bearer <jwt>
```

```json
{
  "nodes": [
    { "id": "checkout", "name": "checkout", "rps": 42.0, "errorRate": 0.01, "p95Ms": 120.0, "spanCount": 151200 }
  ],
  "edges": [
    { "source": "checkout", "target": "payments", "rps": 41.0, "errRate": 0.02, "p95Ms": 95.0 }
  ]
}
```

| 欄位 | 說明 |
|---|---|
| `rps` | 時間範圍內的每秒請求數。 |
| `errorRate` / `errRate` | 狀態為 `ERROR` 的請求比例（0–1）。 |
| `p95Ms` | 時間範圍內各分鐘的第 95 百分位延遲中，數值最高者，單位為毫秒。 |
| `spanCount` | 時間範圍內該節點的 span 總數。 |

## 原始服務圖

若要取得底層的逐分鐘邊快照，例如繪製某項相依性隨時間變化的圖表，可直接查詢服務圖：

```http
GET /api/v1/traces/service_graph?from=1717200000000000&to=1717286400000000&service=checkout
Authorization: Bearer <jwt>
```

`from` 和 `to` 是自 Unix 紀元起算的微秒數。使用選用的 `service` 篩選條件時，只會傳回指定服務位於呼叫任一端的邊。每列包含一組服務對在一分鐘內的 `environment`、`request_count`、`error_count`，以及 `p50_us` / `p95_us` / `p99_us`。

## 在介面中查看

- **應用程式效能 → 服務地圖**會繪製一個環境中的服務、服務之間的呼叫、服務呼叫的對象，以及服務發佈訊息至哪些 Topic、從哪些 Topic 取用訊息。請參閱 [APM 服務地圖](#apm-服務地圖)。
- 服務 APM 頁面的**相依性**區段會以 APM 服務地圖的方式繪製該服務及其上下游，並列出對該服務的呼叫。點選任一呼叫，即可開啟相同的呼叫抽屜。
- Traces 頁面的**服務圖**分頁會根據符合查詢條件的 trace 繪製地圖。

所有服務地圖都採用相同的繪製方式：節點以圓環表示，依健康狀況著色，中央顯示類型圖示，旁邊顯示名稱、每秒請求數、錯誤率和 P95。呼叫以箭頭表示，粗細隨流量變化。失敗率達 5% 時顯示紅色，達 1% 但未滿 5% 時顯示橘色。

從任一服務或邊，都能透過[跨訊號關聯](/zh-Hant/correlation)直接深入查看底層的 trace 與日誌。

## APM 服務地圖

**應用程式效能 → 服務地圖**會整合服務圖和 APM 投影，範圍為導覽卡片中選取的環境和命名空間：

| 節點 | 來源 |
|---|---|
| 服務 | 服務圖，附上 APM 摘要中的 RED 指標與健康狀態。 |
| 資料庫、快取、外部 HTTP 或 RPC | APM 相依性中的外部呼叫，依呼叫目標彙總。 |
| 未回報資料的服務 | 呼叫透過 `peer.service` 指定、但本身不傳送 span 的服務。 |
| Topic | 發佈至某個訊息目的地的呼叫，以及從該目的地取用訊息的端點。 |

呼叫線的粗細隨流量變化，顏色則反映失敗狀況。與前一段等長的時間範圍相比，只在目前出現的呼叫標為**新增**；不再出現的呼叫標為**已消失**，以虛線連同其節點一起顯示。選取節點後，地圖會醒目標示呼叫該節點的節點、該節點呼叫的節點，以及從該節點往下游延伸的**關鍵路徑**：每一步都選取 P95 最高的呼叫。地圖上的卡片會列出該節點的呼叫；點選任一呼叫，即可在抽屜中查看請求數、錯誤和延遲隨時間的變化，以及該呼叫所存取的內容：

- 呼叫服務時，顯示被呼叫服務的端點（含所有呼叫端的請求）與錯誤群組；
- 呼叫資料庫、快取或外部端點時，顯示該呼叫執行的作業；
- 經過 Topic 時，顯示訊息從發佈完成到開始取用的等待時間。資料取自 Trace 儲存空間中最近的訊息取用紀錄（最多 200 筆）。每筆紀錄都會透過 span links 尋找對應的發佈 span；若沒有 links，則使用父 span。

節點超過 60 個時，地圖預設會將每個命名空間摺疊成一個節點。選取節點即可展開。**依命名空間摺疊**可摺疊或展開所有命名空間。地圖最多繪製 400 個節點，並保留流量最高的節點。
