服務頁的**部署**標籤把兩種來源放在一起：管線回報的發佈事件，以及服務的 Span 在 `service.version` 裡帶的版本。沒有管線回報的版本，也會根據 Span 顯示出來。

## 發佈時間軸

時間軸依新到舊列出時間範圍內服務發生的變化：

| 事件 | 條件 |
|---|---|
| **發佈** | 管線回報了一次成功的發佈。 |
| **發佈失敗** | 管線回報了一次失敗的發佈。失敗的發佈不會改變目前執行中的版本。 |
| **復原** | 管線回報了復原，或者回報的發佈是在另一個版本之前執行過的版本。這一列會寫明從哪個版本復原。 |
| **退回** | Span 退回至沒有管線回報的舊版本：最後看到的版本首次出現在一個較新的版本之前，而那個較新的版本已停止超過五分鐘。 |
| **首次出現** | Span 帶來了沒有管線回報的版本。 |
| **設定變更** | 管線或工具回報了一次設定變更。這一列顯示它的描述。 |
| **功能開關** | 管線或工具回報了一次功能開關變更。這一列顯示它的描述。 |

設定變更和功能開關不會改變目前執行中的版本，也沒有自己的指標。它們會出現在洞察附近的變更裡，見[發現附近的變更](/zh-Hant/apm/insights#發現附近的變更)。

回報的發佈會顯示 commit、PR、CI 執行和作者。儲存庫是 http 或 https 網址時，點選 commit 會依 GitHub、GitLab 或 Bitbucket 的提交網址格式開啟這次提交的網頁。

每個版本在時間範圍內的請求數、錯誤率和 p95 顯示在它最新的一列，並附上與它之前首次出現的版本比較的結論：

| 結論 | 條件 |
|---|---|
| **變差** | 錯誤率至少上升 1 個百分點且達到原來的 1.5 倍，或 p95 至少變慢五分之一且至少 50 毫秒。結論後會寫明哪一項變差。 |
| **變好** | 其中一項下降了同樣的幅度，並且沒有一項變差。 |
| **無明顯變化** | 兩項變化都沒有達到上述幅度。 |
| **請求數不足** | 任一版本的請求數少於版本比較所需的數量，預設 1,000。 |

點選結論會在**比較兩個版本**中開啟這兩個版本，並列出變慢的端點和增多的錯誤。變差或變好的版本也會在概覽的最近部署中標示出來。

## 金絲雀

兩個版本同時執行時（例如金絲雀版本與它要取代的版本並存），時間軸上方會有一張卡片將它們並排比較。兩個版本都在服務最後一個 Span 之前五分鐘內出現過，就算同時執行。卡片比較最新的兩個版本，從較新版本首次出現時算起：

- 每個版本承接的請求佔比；
- 每個版本的請求數、錯誤率、p50、p95 和 p99；
- 較新版本相對較舊版本的結論。

## 從 CI 回報發佈

管線透過 `POST /api/v1/apm/deployments` 回報發佈。請求需要能使用 `apm.deploy` 的 API Token。擁有者、管理員和編輯者都具有該權限，接入 Token 跟隨的 **資料寫入** 策略也包含它。

```bash
curl -X POST "https://<host>/api/v1/apm/deployments" \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{"service": "checkout", "environment": "production", "version": "2.4.0", "commit": "9f2c1e7a4b3d", "repository": "https://github.com/acme/checkout", "ciUrl": "https://ci.example.com/runs/7"}'
```

| 欄位 | 必填 | 說明 |
|---|---|---|
| `service` | 是 | 服務名，與 Span 的 `service.name` 一致。最多 255 個字元。 |
| `version` | 發佈時必填 | 發佈的版本，與 Span 的 `service.version` 一致。最多 192 個字元。 |
| `kind` | 否 | `deployment`（預設）、`configuration`、`feature_flag`、`scaling` 或 `infrastructure`。 |
| `namespace` | 否 | 服務的 `service.namespace`。不填時在所有 Namespace 中顯示。 |
| `environment` | 否 | 環境，即 `deployment.environment.name`。不填時在所有環境中顯示。 |
| `status` | 否 | `succeeded`（預設）、`failed`，或 `rolled_back`，表示這次發佈把服務復原到 `version`。 |
| `commit` | 否 | 發佈的提交：最多 64 個字母和數字。 |
| `repository` | 否 | 程式碼儲存庫：https、http、ssh 或 git 網址，最多 512 個字元。網址中的密碼儲存為 `****`，https 網址中的使用者名稱部分也是如此。 |
| `pullRequest` | 否 | PR 的 http 或 https 連結。 |
| `author` | 否 | 發佈人，最多 128 個字元。 |
| `ciUrl` | 否 | CI 執行的 http 或 https 連結。 |
| `description` | 否 | 最多 1,000 個字元，滑鼠停在事件上時顯示。 |
| `deployedAt` | 否 | 發佈時間，自 Unix 紀元起的微秒數。預設為請求到達的時間。 |

服務名和環境依 APM 的方式命名：組織的命名規則、環境對應和別名對它們生效，與對 Span 的處理相同。參見 [APM 設定](/zh-Hant/apm/settings)。

**資料來源**頁面的 **GitHub Actions**、**GitLab CI/CD** 和 **Jenkins** 下有以下步驟，並已填好工作區的網址。

### GitHub Actions

將 Token 儲存為儲存庫 Secret，然後在負責部署的 job 裡加一個步驟。`if: always()` 讓失敗的發佈也會回報。

```yaml
- name: Report the deployment to MoleSignal
  if: always()
  env:
    MOLESIGNAL_TOKEN: ${{ secrets.MOLESIGNAL_TOKEN }}
    DEPLOY_STATUS: ${{ job.status == 'success' && 'succeeded' || 'failed' }}
  run: |
    cat > deployment.json <<EOF
    {
      "service": "checkout",
      "environment": "production",
      "version": "${GITHUB_SHA::12}",
      "status": "$DEPLOY_STATUS",
      "commit": "$GITHUB_SHA",
      "repository": "$GITHUB_SERVER_URL/$GITHUB_REPOSITORY",
      "author": "$GITHUB_ACTOR",
      "ciUrl": "$GITHUB_SERVER_URL/$GITHUB_REPOSITORY/actions/runs/$GITHUB_RUN_ID"
    }
    EOF
    curl -fsS -X POST "https://<host>/api/v1/apm/deployments" \
      -H "Authorization: Bearer $MOLESIGNAL_TOKEN" \
      -H "Content-Type: application/json" \
      --data-binary @deployment.json
```

### GitLab CI/CD

將 Token 新增為名為 `MOLESIGNAL_TOKEN` 的隱藏 CI/CD 變數，然後在部署 job 的 `after_script` 中回報。`after_script` 不論部署成敗都會執行。

```yaml
deploy:
  stage: deploy
  environment: production
  script:
    - ./deploy.sh
  after_script:
    - |
      if [ "$CI_JOB_STATUS" = "success" ]; then DEPLOY_STATUS=succeeded; else DEPLOY_STATUS=failed; fi
      cat > deployment.json <<EOF
      {
        "service": "checkout",
        "environment": "$CI_ENVIRONMENT_NAME",
        "version": "$CI_COMMIT_SHORT_SHA",
        "status": "$DEPLOY_STATUS",
        "commit": "$CI_COMMIT_SHA",
        "repository": "$CI_PROJECT_URL",
        "author": "$GITLAB_USER_LOGIN",
        "ciUrl": "$CI_PIPELINE_URL"
      }
      EOF
      curl -fsS -X POST "https://<host>/api/v1/apm/deployments" \
        -H "Authorization: Bearer $MOLESIGNAL_TOKEN" \
        -H "Content-Type: application/json" \
        --data-binary @deployment.json
```

### Jenkins

將 Token 新增為 ID 為 `molesignal-token` 的 **Secret text** 憑證，然後在管線的 `post` 區塊中回報。`post { always }` 在建置失敗時也會回報。`GIT_URL` 中帶的密碼在儲存時會被遮蔽。

```groovy
post {
  always {
    script {
      writeFile file: 'deployment.json', text: groovy.json.JsonOutput.toJson([
        service: 'checkout',
        environment: 'production',
        version: env.GIT_COMMIT.take(12),
        status: currentBuild.currentResult == 'SUCCESS' ? 'succeeded' : 'failed',
        commit: env.GIT_COMMIT,
        repository: env.GIT_URL,
        ci_url: env.BUILD_URL,
      ])
    }
    withCredentials([string(credentialsId: 'molesignal-token', variable: 'MOLESIGNAL_TOKEN')]) {
      sh '''
        curl -fsS -X POST "https://<host>/api/v1/apm/deployments" \
          -H "Authorization: Bearer $MOLESIGNAL_TOKEN" \
          -H "Content-Type: application/json" \
          --data-binary @deployment.json
      '''
    }
  }
}
```

## 回報設定變更與功能開關

設定變更、功能開關、擴縮容和服務所依賴的基礎設施變更都使用同一個介面回報，設定 `kind`，並在描述裡寫明改了什麼，不需要版本。

回報的變更也會出現在 [`GET /api/v1/changes`](/zh-Hant/api/changes) 中，標記在日誌和 Trace 的直方圖上、指標圖表下方，以及告警的**變更**頁裡。

```bash
curl -X POST "https://<host>/api/v1/apm/deployments" \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{"service": "checkout", "environment": "production", "kind": "feature_flag", "description": "new_checkout on for 10% of users"}'
```

## 從 Webhook 回報變更

能自訂請求主體和請求標頭的 Webhook（如 Argo CD notifications、Spinnaker、帶請求主體範本的 Unleash webhook 外掛）依上文呼叫 `POST /api/v1/apm/deployments`。請求主體固定、或者設定不了請求標頭的工具改為呼叫 `POST /api/v1/intake/changes`。API Token 放在 `Authorization: Bearer` 中；設定不了請求標頭時放在 `?token=` 中，Token 需要有 `apm.deploy` 權限。放在網址裡的 Token 可能被代理記進日誌：給這類工具單獨發一個只含 `apm.deploy` 的 Token。

| 參數 | 說明 |
|---|---|
| `format` | `generic`（預設）、`launchdarkly`、`unleash`、`nacos` 或 `apollo`。 |
| `service`、`namespace`、`environment` | 請求主體沒有說明時使用。沒有服務名的變更會被拒絕。 |
| `kind` | `deployment`、`configuration`、`feature_flag`、`scaling` 或 `infrastructure`，覆寫請求主體中的值。 |
| `serviceField`、`environmentField`、`versionField`、`descriptionField`、`authorField` | 用於 `generic`：JSON Pointer（如 `/app/name`）或頂層欄位名。不填時讀取與 `POST /api/v1/apm/deployments` 同名的欄位。 |

| 格式 | 讀取方式 |
|---|---|
| `launchdarkly` | 記為功能開關。環境取稽核資源中的 `env/` 部分，描述取記錄的標題，作者取成員電子郵件。 |
| `unleash` | 記為功能開關：事件類型與開關名、所在環境以及操作人。 |
| `nacos` | 記為設定變更，內容是 Data ID 和分組；Nacos 命名空間作為 Namespace。 |
| `apollo` | 記為設定變更：App ID 作為服務，叢集作為環境，命名空間和發佈標題說明改了什麼。 |

**資料接入 → DevOps** 下有 LaunchDarkly、Unleash、Nacos 和 Apollo 各自的接入指南，網址已依目前工作區填好。

請求主體可以是一個變更，也可以是至多 100 個變更的清單。回傳 `201` 和儲存下來的變更。這些預設依各工具文件中的請求主體編寫，還沒有在真實帳號上驗證；工具的請求主體不一致時，改用 `generic` 並指定 JSON Pointer。

```bash
curl -X POST "https://<host>/api/v1/intake/changes?format=launchdarkly&service=checkout&token=<token>" \
  -H "Content-Type: application/json" \
  -d @launchdarkly-event.json
```

## 疑難排解

| 現象 | 檢查 |
|---|---|
| 回報的發佈沒有出現在時間軸上 | 時間範圍要包含 `deployedAt`，`service` 要與 APM 中的服務名一致。帶環境回報的發佈只會在該環境中顯示。 |
| 一次發佈和它發佈的版本顯示成兩列 | 回報的 `version` 與 Span 的 `service.version` 不同。回報相同的值。 |
| 發佈介面回傳 `403` | Token 不能使用 `apm.deploy`：權限範圍不包含它，或所屬成員、服務帳號沒有這項權限。 |
| 發佈介面回傳 `400` | 某個欄位超出上表的限制，錯誤訊息會指出是哪個欄位。 |
