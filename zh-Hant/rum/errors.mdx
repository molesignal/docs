**使用者體驗 → 錯誤** 會依 issue 列出應用程式的錯誤。每個 issue 將相似的錯誤歸在一起，包含狀態、團隊、處理人，以及何時、在哪些版本出現過的記錄。每筆錯誤仍保留在 `rum_errors` 串流中，並在 `error.issue_id` 中帶有所屬 issue 的 ID，因此在[探索](/zh-Hant/rum/explorer)和查詢結果中都能看到。

## 錯誤如何歸入 issue

收到錯誤時，伺服器端會算出錯誤所屬的 issue。ID 是下列內容的雜湊值：

- 應用程式和 `error.source`，
- 錯誤的類型、類別，以及移除每次都會變動的部分後的訊息，
- 應用程式自身程式碼的前三個堆疊框架；若已上傳該版本的 source map、mapping 或符號檔案，則使用還原後的框架（見 [Source Maps 與符號](/zh-Hant/rum/source-maps)），
- 要求失敗時，使用要求的方法、路徑和狀態碼。

系統會移除訊息中的數字、UUID、八個字元以上的十六進位雜湊值、電子郵件地址，以及網址的查詢字串和片段，因此 `Loading chunk 482 failed.` 和 `Loading chunk 17 failed.` 會歸入同一個 issue。相依套件、框架和執行階段的堆疊框架不算應用程式自身的程式碼；如果有應用程式自身的堆疊框架，歸類時就不採用這些框架。

若要用其他方式歸類，請傳送 `error.fingerprint`（最長 128 個字元）。同一個應用程式中，fingerprint 相同的錯誤會歸入同一個 issue，無論訊息和堆疊是否相同。SDK 不會設定這個欄位；請在呼叫錯誤回報功能時傳入。

<Note>
  產生 ID 的規則有版本號。日後調整歸類方式會產生新的 ID，因此不會就地重新歸類現有的 issue。issue 出現前收到的錯誤沒有 `error.issue_id`，不會列出。若在上傳該版本的 source map 前收到錯誤，就依原始框架歸類；若在上傳後才收到，就依還原後的框架歸類。因此，同一個問題可能會分成兩個 issue。系統不會合併現有的 issue。
</Note>

## 清單

清單會列出指定的應用程式和環境在時間範圍內發生過錯誤的 issue。每列顯示：

| 欄位 | 內容 |
|---|---|
| **問題** | 第一筆錯誤的類型和訊息，以及應用程式自身程式碼的第一個堆疊框架。 |
| **狀態** | 目前的處理狀態。見[狀態](#狀態)。 |
| **指派** | 負責處理的人員；若未指派人員，則顯示團隊。 |
| **工作階段** | 時間範圍內遇到這個 issue 的工作階段數量。 |
| **使用者** | 遇到這個 issue 的人數。沒有使用者 ID 的訪客以 SDK 的匿名 ID 計算。 |
| **趨勢** | 將時間範圍等分為 12 段，顯示每段的出現次數。 |
| **版本** | 首次出現和最近一次出現的版本。 |
| **最近出現** | 最近一次出現的時間，不受時間範圍限制。 |

清單預設顯示**待處理**的 issue：待處理、調查中和迴歸。在篩選條件中選擇其他狀態，或選擇**全部 issue**。可依類型、訊息或位置中的關鍵字，以及處理人縮小清單範圍；若有多種用戶端回報錯誤，也可依來源篩選。點選**狀態**、**工作階段**、**使用者**或**最近出現**來排序，再點一次即可反轉排序。網址會保留頁面狀態，因此可以分享目前的檢視。

清單會依選取的排序，先讀取工作階段數、使用者數或出現次數最多的 250 個 issue，再套用篩選條件，因此不會篩選排名在這 250 個之後的 issue。清單最多顯示 100 個 issue。

清單上方的**出現在哪裡**會依版本、頁面和瀏覽器細分所列 issue 的工作階段。點選某個值，清單就只顯示在該處發生的錯誤，各欄位也會依篩選結果更新。再點一次即可取消篩選。

## issue

點選任一列，即可在側邊面板中開啟 issue。網址會包含這個 issue，因此可以透過網址再次開啟面板。

- 在頂端設定狀態、團隊和處理人。點選**在探索中檢視**，即可在探索中檢視這個 issue 的錯誤。
- 概況列會顯示狀態、時間範圍內的工作階段數和人數，以及 issue 首次和最近一次出現的時間與版本。
- **出現趨勢**會按天顯示最近 14 天的工作階段，並依版本堆疊。虛線標示設為已解決的當天。
- **出現在哪裡**會依瀏覽器、作業系統和國家細分這個 issue 的工作階段。
- **擲回位置**會列出最近一筆含堆疊的錯誤中的框架：應用程式自身的框架以粗體顯示，相依程式庫的框架則以淡色顯示。如果已透過偵錯產物還原框架，就可以在**還原後**和**原始**之間切換。
- **工作階段樣本**會列出最近三個遇到這個 issue 的工作階段，各自提供重播和時間軸的入口；**受影響的使用者**會列出遇到次數最多的使用者。系統會另外儲存未保留的工作階段中的錯誤，因此工作階段入口會顯示 *工作階段未保留*。見 [RUM 資料取樣](/zh-Hant/rum/sampling#保留所有錯誤)。

issue 清單中的類型、訊息和位置會保留第一筆錯誤寫入時經過遮罩處理的內容。

## 狀態

| 狀態 | 含義 | 設定者 |
|---|---|---|
| **待處理** | 尚未檢視。新 issue 一律從此狀態開始。 | 伺服器端和使用者。 |
| **調查中** | 正在調查。 | 使用者。 |
| **迴歸** | 已解決，但在較新的版本再次出現。 | 僅限伺服器端。 |
| **已解決** | 已修正根本原因。 | 使用者。 |
| **已忽略** | 不需要處理。 | 使用者。 |

待處理、調查中和迴歸的 issue 都是未解決的 issue。

### 迴歸

將 issue 標為已解決時，系統會記錄時間、操作者，以及當時應用程式的最新版本。系統依各版本首次出現的時間排序，不看版本號的寫法。只有在錯誤所屬版本比解決時記錄的版本更晚首次出現時，系統才會重新開啟已解決的 issue，並標為**迴歸**。尚未升級的使用者仍可能在舊版遇到錯誤，因此同一版本或更舊版本的錯誤不會重新開啟 issue。

未提供版本資訊的應用程式無從判斷版本先後：解決後出現的任何錯誤都會重新開啟 issue。若 issue 是在特定版本標為已解決，未指定版本的錯誤不會重新開啟它。

變更迴歸 issue 的狀態，即可結束這次迴歸。再次標為已解決時，系統會重新記錄最新版本。

issue 屬於整個應用程式，各環境共用同一個 issue。伺服器端會記錄觸發重新開啟的錯誤所在的環境，以及各環境首次出現該 issue 的時間。[警示規則](/zh-Hant/rum/alerts)會據此統計特定環境的新問題和迴歸問題。

接收錯誤的一端最多會快取 issue 一分鐘，因此使用者設定的狀態最多需要一分鐘才會傳到接收端。如果較新版本的錯誤在接收端仍使用舊狀態時抵達，就不會重新開啟這個 issue；快取到期後收到的下一筆此類錯誤才會重新開啟它。

## 每小時新增的 issue

每個應用程式每小時可新增的 issue 上限由**每小時新增的 issue 數量**設定，預設為 100。達到上限後，系統會將該小時內尚未歸入任何 issue 的錯誤合併計入名為**其餘錯誤**的 issue，避免訊息從不重複的應用程式塞滿清單。若要調整上限，請前往**使用者體驗 → 應用程式**，在**Issue** 區段設定，範圍為 1 到 10,000。變更會在半分鐘內生效。

## 權限

- `rum.issues.read` 可開啟清單和 issue。
- `rum.issues.manage` 可設定狀態、團隊和處理人。擁有者、管理員和編輯者具備此權限。沒有此權限時，控制項只會顯示目前的設定。
