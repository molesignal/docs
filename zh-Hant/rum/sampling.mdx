Browser RUM SDK 會在建立工作階段時決定是否取樣，並在整個工作階段維持相同的決定，應用程式的所有分頁也都一致。

## 設定取樣率

```ts
const rum = init({
  applicationId: 'checkout-web',
  clientToken: 'mspat-your-client-token',
  site: 'https://molesignal.example.com',
  sessionSampleRate: 25,
  sessionReplaySampleRate: 20,
});
```

兩個值都是 `0` 到 `100` 的百分比：

- `sessionSampleRate` 決定 SDK 是否回報該工作階段及相關的 RUM 事件，預設值為 `100`；
- `sessionReplaySampleRate` 只套用至已取樣的工作階段，預設值為 `0`。

實際的重播取樣率是兩個取樣率的乘積。在上方範例中，約 25% 的工作階段會回報 RUM 資料，約 5% 的工作階段會錄製重播（`25% × 20%`）。

<Note>
  `startSessionReplayRecording()` 可以為目前已取樣的工作階段啟用重播，但無法將 `sessionSampleRate` 排除的工作階段重新納入取樣。
</Note>

## 在伺服器端保留部分工作階段

除了 SDK 本身的取樣外，應用程式還可以只保留部分收到的工作階段，不論這些工作階段來自哪個用戶端。在 **RUM → 應用程式** 中開啟應用程式，找到 **保留的工作階段**。**工作階段保留比例（%）** 的範圍為 `0` 到 `100`，預設為 `100`，也就是保留所有工作階段。

伺服器會保留或捨棄整個工作階段。伺服器根據工作階段 ID 的雜湊值做決定，因此無論在哪個節點，同一工作階段的所有事件和重播片段都會一併保留或捨棄。保留的工作階段包含完整紀錄。捨棄工作階段時，不保留事件、`rum_sessions` 的資料列或重播，只有錯誤例外（請參閱[保留所有錯誤](#保留所有錯誤)）。

這個比例只適用於 SDK 已回報的工作階段。SDK 設為 `sessionSampleRate: 50`，且 **工作階段保留比例** 為 `20` 時，約 10% 的工作階段會儲存下來。設為 `0` 不會儲存任何工作階段，適合在不修改 SDK 的情況下暫停應用程式的資料保留。[資料接收](/zh-Hant/rum/events#回應)的回應中，`sampled` 表示有多少事件已捨棄，SDK 可據此確認資料並非遺失。未保留的工作階段若送來重播片段，伺服器會回傳 `200` 和 `sampled: true`。

變更只會影響之後收到的事件。已儲存的工作階段會繼續保留；變更前就已開始的工作階段，則從變更時起依新比例保留或捨棄。

[由測試驅動的工作階段](/zh-Hant/rum/test-traffic)會完整保留，除非應用程式有篩選器指定 `session.type`：合成監控不應因為針對真實使用者設定的比例而失去工作階段。

### 篩選器

篩選器可為符合條件的工作階段指定個別比例：例如保留正式環境的所有工作階段，其餘只保留十分之一。在 **保留的工作階段** 中新增篩選器。每個篩選器都有名稱、`0` 到 `100` 的比例，以及最多 5 個條件。工作階段必須符合所有條件。沒有條件的篩選器會比對所有工作階段。

每個條件會將工作階段的一項屬性與一組值比對：屬性值**是**其中之一，或**不是**其中任何一個（若屬性沒有值，就不是其中任何一個）。值不區分大小寫，`*` 代表任意文字，因此 `2.*` 會比對所有以 `2.` 開頭的版本。每個條件最多可列出 20 個值，每個應用程式最多可設定 10 個篩選器。

| 屬性 | 欄位 |
|---|---|
| 環境 | `env` |
| 服務 | `service` |
| 版本 | `version` |
| SDK 平台 | `source` |
| 工作階段類型 | `session.type` |
| 國家 | `geo.country_iso_code` |
| 瀏覽器 | `browser.name` |
| 作業系統 | `os.name` |
| 裝置類型 | `device.type` |

系統會依照清單順序逐一檢查篩選器，**第一個符合的篩選器會決定該工作階段的保留比例**，因此請把條件較具體的篩選器放在範圍較廣的篩選器之前。未符合任何篩選器的工作階段，會依篩選器下方的 **其餘工作階段的保留比例（%）** 保留。若未設定篩選器，這就是該應用程式唯一的保留比例。

<Note>
  同一工作階段的所有事件都必須一併保留或捨棄，因此條件只能使用工作階段進行期間不會變動的屬性。工作階段中的使用者操作，以及 SDK 後來才取得的身分資訊（例如登入後設定的使用者 ID），都不能用來決定是否保留工作階段。錯誤有獨立的開關，請參閱下方說明。
</Note>

系統會根據重播片段提供的工作階段資訊判斷是否保留，包括瀏覽器、地理位置，以及 Browser SDK 和 Flutter SDK 在要求本文中帶入的 `env`、`service` 和 `version`（SDK 未設定 `env` 或 `version` 時，會省略該欄位）。如果片段缺少部分屬性，只要有任何可能符合該工作階段的篩選器會保留它，系統就會保留該片段。

### 保留所有錯誤

即使未保留工作階段，系統仍會儲存其中的錯誤，除非關閉 **保留所有錯誤**。這樣一來，罕見錯誤不會隨工作階段一併捨棄，而會和其他問題一起計數。這類錯誤只會在 `rum_errors` 中留下一筆資料列；所屬的工作階段沒有資料列、檢視或重播，因此問題頁面會在原本應顯示工作階段連結的位置標示 *未保留工作階段*。

### 總數是估算值

每筆資料列都在 `retention.rate` 中記錄這類資料列的保留比例（例如依 25% 的篩選器保留的工作階段會記為 `25`），並在 `retention.filter` 中記錄保留依據：篩選器的 ID、代表其餘工作階段保留比例的 `default`，或代表未保留工作階段之錯誤的 `errors`。開啟 **保留所有錯誤** 時，系統會保留所有錯誤，因此無論錯誤屬於哪個工作階段，比例一律記為 `100`。

顯示總數的頁面會依每筆資料列的保留比例放大計數：依 25% 的比例保留的一個工作階段會算成四個。頁面會標示 **估算值**，並顯示工作階段的保留比例。總數代表保留所有工作階段時的估計數字。

- 數量、總和和平均值會放大，百分位數則依相同的比例加權。
- 實際觀察到的使用者人數、最小值和最大值不會放大，會以觀察值呈現。
- 漏斗和路徑會依比例計算工作階段數。留存分析的群組以使用者為單位，因此依實際觀察到的人數計算。
- 探索器會列出保留的資料列，並依這些資料列的實際筆數產生計數和圖表。在呼叫[彙總 API](/zh-Hant/api/rum#衡量資料列)時傳入 `estimate=false`，即可取得相同的數字。
- 需要達到 **最少樣本數** 的警示規則，以實際儲存的資料列筆數為準，而非這些資料列代表的數量。

取樣會造成誤差：如果只有幾個工作階段，取其中 10% 不足以得出結論。

## 選擇初始值

| 流量類型 | 工作階段取樣率 | 已取樣工作階段內的重播取樣率 |
|---|---:|---:|
| 開發或受控 QA | `100` | `100` |
| 低流量正式環境 | `100` | `10`–`25` |
| 高流量正式環境 | `10`–`50` | `1`–`10` |

這些值僅供初始設定參考，並非通用的預設值。發布前，請估算事件量、所需的物件儲存容量、保留時間，以及各瀏覽器和版本所需的工作階段數量。

## 工作階段邊界

SDK 會將取樣決定存入工作階段 Cookie `_msrum_s_<applicationId>`，由應用程式的各個分頁共用。達到下列任一條件時，SDK 會建立新的工作階段：

- `sessionInactivityTimeout`：預設為 15 分鐘；
- `maxSessionDuration`：預設為 4 小時。

兩個值都以毫秒為單位，允許範圍為 1 分鐘到 24 小時。

```ts
sessionInactivityTimeout: 15 * 60_000,
maxSessionDuration: 2 * 60 * 60_000,
```

修改取樣設定不會變更目前工作階段已儲存的取樣決定。測試新設定時，請呼叫 `stopSession()`，或清除 `_msrum_s_<applicationId>` Cookie。

## 限制用戶端資料量

使用傳輸設定，讓記憶體用量和要求大小維持在可預測的範圍：

```ts
flushInterval: 5_000,
batchSize: 50,
replayFlushInterval: 10_000,
replayBatchSize: 100,
maxQueueSize: 1_000,
```

每次調整後，請監控寫入速率、重播儲存用量、瀏覽器負擔和疑難排解的涵蓋率。請依應用程式和版本逐步推出取樣設定。
