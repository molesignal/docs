狀態頁可將維運狀態轉化為有管控的客戶溝通。開啟**狀態頁**建立頁面，再透過七個獨立工作區管理。

## 工作區

| 第一層分頁 | 用途 |
|---|---|
| **總覽** | 查看摘要、元件、進行中的事件與即將開始的維護。 |
| **元件** | 建立、分組、排序、隱藏、還原及更新面向客戶的服務元件。 |
| **事件** | 起草、發布、更新、監控及解決非計畫性事件。 |
| **維護** | 排程、發布、開始、完成或取消計畫內的工作。 |
| **歷史紀錄** | 搜尋及篩選已結束的事件與維護，不必在總覽中無限展開。 |
| **訂閱者** | 管理電子郵件、Webhook 與 Slack 訂閱，匯入訂閱者，以及查看確認狀態和投遞結果。 |
| **設定** | 設定一般行為、品牌、本地化、網域、存取權與自動化。 |

## 建立狀態頁

選擇**建立狀態頁**，然後設定：

- 顯示給客戶的名稱與全域唯一的 Slug；
- 一種或多種介面語言、預設語言與 IANA 時區；
- **公開**或**私人**的可見性；
- 投遞紀錄保留期限、私人工作階段有效期限與事件歷史紀錄範圍；
- 標誌、品牌色彩與選用的自訂網域。

英文和簡體中文的本地化僅適用於公開介面。元件名稱、事件訊息與維護更新會保留團隊輸入的原文。頁面寄出的電子郵件也會使用預設語言。

預設公開網址為 <code>/status/SLUG</code>。

## 元件

每個元件包含名稱、描述、順序、可見性與一個向客戶顯示的狀態：

- **正常**
- **效能下降**
- **部分中斷**
- **嚴重中斷**
- **維護中**

若仍需管理元件但不想公開，可隱藏元件。已隱藏的元件不會出現在公開頁面或訂閱通知中。元件從服務目錄移除時，再將其封存。這不會刪除既有的事件歷史紀錄。

公開頁面會逐一列出各元件的狀態和最近 90 天的狀態列。每個狀態列下方都有一行刻度標示：**90 天前**、該元件的可用性和**今天**。元件描述顯示在名稱旁 ⓘ 的工具提示中。

### 元件分組

如同用資料夾收納檔案，可將相關元件放入同一群組。選擇**新增元件**，將類型設為**分組**，再填寫名稱和描述。接著在元件的設定中，從**所屬群組**選擇要加入的群組。

- 群組沒有自己的狀態，會顯示群組內元件最差的狀態。群組狀態列上的每一天都會顯示當天群組內最差的元件狀態。
- 公開頁面上，每個群組各占一列，並標示元件數量。讀者展開群組後即可查看各個元件。群組內有元件異常時，群組預設會展開。
- 群組只能包含元件，不能巢狀包含其他群組。事件、維護、訂閱和自動化規則只能選擇元件，不能單獨選擇群組。
- 使用**上移**和**下移**調整同一群組內的元件順序。群組本身則與最外層的項目一起排序。
- 將群組內的元件全數移出或封存後，才能封存群組。

### 相依性

元件可以依賴技術服務、合成監測檢查和警示規則，並以各相依項目所傳遞的最差狀態作為健康度。警示事件或合成監測檢查發生變化後，MoleSignal 會在幾秒內重新計算，並且每分鐘執行一次完整計算。在元件設定的**相依性**中新增：

| 類型 | 對象 | 傳遞的狀態 |
|---|---|---|
| **技術服務** | 服務名稱，與追蹤和警示中的服務名稱一致。 | 符合條件且尚未關閉的警示事件中最嚴重的狀態：事件的 `service`、`service.name` 或 `service_name` 標籤指向該服務，或事件的查詢涵蓋該服務。比對服務名稱時不區分大小寫。 |
| **合成監測檢查** | 一項合成監測檢查。 | 檢查失敗時為**嚴重中斷**，速度變慢時為**效能下降**。不穩定、尚未執行、已暫停或已封存的檢查不會傳遞任何狀態。 |
| **警示規則** | 一條警示規則。 | 該規則尚未關閉的警示事件中最嚴重的狀態。 |

警示事件依嚴重程度傳遞狀態：**critical** 為嚴重中斷，**error** 為部分中斷，**warning** 為效能下降，**info** 不影響狀態。已靜音的事件不列入計算。每個相依項目都可以選擇**原樣傳遞影響**。若元件有降級方案，也可以選擇**最多視為效能下降**。每個元件最多可有 100 個相依項目，群組沒有自己的相依項目。

健康度如何影響元件：

| 方式 | 行為 |
|---|---|
| **跟隨健康度** | 元件狀態會隨健康度變化。**通知訂閱者**決定是否將這些變更通知訂閱者。手動設定的狀態會保留到健康度下一次變化為止。 |
| **交由自動化規則處理** | 將健康度變化作為此頁自動化規則的來源，依規則設定的延遲、核准流程和文案發布事件。 |

元件設定會顯示最近一次計算的健康度，以及影響該健康度的相依項目。

## 事件生命週期

先將事件儲存為草稿，選擇受影響的元件與影響程度，再撰寫第一則客戶更新。發布後，事件會公開，系統也會向符合條件的訂閱者投遞更新。

<Steps>
  <Step title="調查中">
    確認症狀，並告知客戶團隊正在調查。
  </Step>
  <Step title="已找出問題或處理中">
    說明已知原因或正在執行的復原作業。
  </Step>
  <Step title="監控中">
    說明服務已恢復，團隊正在驗證穩定性。
  </Step>
  <Step title="已解決">
    發布結案更新。MoleSignal 會恢復元件狀態，並在**歷史紀錄**中新增一列，記錄完整事件。
  </Step>
</Steps>

對客戶發布的更新無法變更。繼續處理事件時，請新增更新，不要改寫已投遞的內容。

### 下次更新與通知

每次發布更新時都可承諾下次更新的時間：在**下次更新**中選擇 15 或 30 分鐘內、1、2、4 或 24 小時內，或選擇**不承諾**。公開頁面會在事件詳細資料與進行中事件的通知上顯示這項承諾，電子郵件和 Webhook 也會一併提供。事件的結案更新與尚未開始的已排程維護不承諾下次更新。透過 API 發布時，以微秒表示的 `next_update_at` 必須落在未來 1 分鐘至 7 天內。

**通知訂閱者**決定是否將這次更新傳送給訂閱者。更正措辭時可關閉此選項：頁面照常更新，但不會傳送任何通知。工作區時間軸會將這類更新標為**未通知訂閱者**。手動修改元件狀態時也可使用相同的開關。透過 API 發布時，請傳入 `"notify": false`。

## 維護生命週期

建立計畫內工作時，設定公開標題、開始時間、受影響的元件和客戶更新。維護只有排程開始時間，沒有排程結束時間。請在客戶更新中註明預計所需時間。先發布為**已排程**，最後以**已完成**或**已取消**結束。結束的維護會以完整事件的形式，在**歷史紀錄**中各占一列。

已排程的維護會在排程開始時間自動開始。每項維護都有兩個選項，預設都會啟用：

| 選項 | API 欄位 | 預設值 | 行為 |
|---|---|---|---|
| 到時自動開始 | `auto_start` | `true` | 到達排程開始時間時，維護會切換為**進行中**，並以頁面的預設語言發布一則更新。訂閱者會像收到其他更新一樣收到通知。 |
| 提前提醒 | `reminder_minutes` | `60` | 訂閱者會在排程開始時間前指定的分鐘數收到一次提醒。提醒不會出現在時間軸上。`0` 表示不提醒，最多可提前 10080 分鐘。 |

關閉到時自動開始後，請在工作開始時手動將維護切換為**進行中**。

若在提醒時間過後才發布維護或變更排程，系統不會再寄送提醒，因為訂閱者剛收到通知。變更排程後，提醒時間會隨新的排程開始時間調整。修改維護時，若未指定這兩個選項，系統會保留原值。MoleSignal 約每 30 秒檢查一次排程開始時間。

## 事件事後檢討

已發布的事件可以附上一篇以 Markdown 撰寫的事件事後檢討，說明發生了什麼、原因為何，以及後續將如何改善。從**事件**或**歷史紀錄**開啟事件，並在**事件事後檢討**中撰寫。選擇**預覽**可查看讀者看到的內容。

| 操作 | 權限 | 效果 |
|---|---|---|
| **儲存草稿** | <code>status_pages.events.manage</code> | 內容不公開。事件仍在進行時，也可以先撰寫草稿。 |
| **發布事件檢討** | <code>status_pages.events.publish</code> | 事件解決後才能發布。事件檢討會顯示在事件頁面的進度更新下方，公開歷史紀錄中的該列事件也會標示**有事件檢討**。開啟**通知訂閱者**後，訂閱者會收到事件檢討。 |
| **發布修訂** | <code>status_pages.events.publish</code> | 取代已發布的內容，並記錄修訂時間。修訂時，**通知訂閱者**預設為關閉。 |
| **撤回為草稿** | <code>status_pages.events.publish</code> | 從公開頁面移除事件檢討。 |
| **刪除草稿** | <code>status_pages.events.manage</code> | 刪除尚未發布的事件檢討。 |

事件檢討最多可包含 20,000 個字元。電子郵件和 Webhook 會原樣傳送 Markdown 文字。

## 歷史紀錄

歷史紀錄只收錄已結束的事件與維護，也就是已解決的事件，以及已完成或已取消的維護。每列代表一個完整事件，包含類型、標題、結束狀態、受影響的元件與日期。可依搜尋字詞、類型、狀態、元件和日期篩選，並分頁瀏覽。點選標題即可開啟時間軸和更新，不會在表格內無限展開。

歷史紀錄範圍可將公開封存紀錄的回溯期間設為 1–365 天，不會讓總覽再度變成無限延伸的事件清單。

## 訂閱者與投遞

公開頁面的訪客可選擇**訂閱**，登記電子郵件地址、Webhook 或 Slack 頻道。每種方式都要先確認才能啟用。管理介面會區分待確認、有效與已取消訂閱的紀錄，並顯示各訂閱者的接收範圍。

在同一個彈出視窗中選擇 **RSS 訂閱**，即可取得兩種訂閱網址。將網址新增至閱讀器即可，無須確認：RSS 2.0 為 `/api/v1/public/status-pages/<slug>/feed.rss`，Atom 1.0 為 `/api/v1/public/status-pages/<slug>/feed.atom`。兩者都包含頁面上最近的 100 筆事件與維護，每筆都附上最新一則更新。私人頁面不提供訂閱來源。

頁面有多個元件時，訪客可選擇**整個頁面**或**指定元件**。只訂閱部分元件的訂閱者，只會收到涉及至少一個所訂閱元件的更新。元件群組會以標題顯示在群組內的元件上方。每封電子郵件末尾都有管理訂閱和取消訂閱兩個連結。管理連結會開啟頁面上的**管理訂閱**，可變更訂閱的元件或取消訂閱。使用已生效的地址再次訂閱時，系統會寄送一封**管理訂閱**郵件，而非新的確認郵件。

### Slack

| 方式 | 做法 |
|---|---|
| Incoming Webhook | 將接收方式選為 **Slack**，貼上該 Slack 頻道的 Incoming Webhook 網址（`https://hooks.slack.com/...`），然後選擇**寄送確認郵件**。系統會將確認訊息傳送至該頻道。 |
| **新增至 Slack** | 在頁面的**設定 → Slack** 中選用 Slack App 後才會顯示。訪客在 Slack 選擇頻道後返回頁面，該頻道的訂閱會立即生效，並收到一則歡迎訊息。私人頁面不提供此功能。 |

Slack 訊息以主旨為標題，內文為更新內容，並附上開啟頁面和管理訂閱的按鈕。

提供 **新增至 Slack** 的步驟：

1. 在 Slack 中建立應用程式，並授予 `incoming-webhook` 權限。在 **OAuth & Permissions → Redirect URLs** 中新增頁面**設定 → Slack** 顯示的重新導向網址，即 `<http.external_url>/api/v1/public/slack/callback`。`http.external_url` 必須是 `https` 網址。
2. 在**設定 → 通知 → 連接器**中建立 **Slack App** 連接器，填入該應用程式的 Client ID 和 Client Secret。系統會將 Client Secret 加密後隨連接器儲存。請參閱[通知管道](/zh-Hant/notification-channels#slack-app)。
3. 在頁面的**設定 → Slack** 中選擇該連接器並儲存。

同一個組織的多個頁面可共用一個連接器。頁面使用中的連接器無法刪除。連接器停用期間，頁面不提供 **新增至 Slack**。選擇**關閉**即可停止提供此功能。無論是哪種情況，已新增的頻道都會繼續收到更新。

### 匯入訂閱者

在**訂閱者 → 匯入訂閱者**中，移轉其他狀態頁的電子郵件訂閱者。選擇 CSV 檔案或直接貼上內容：

- 第一列可作為標題列，包含 `email` 和 `components` 兩欄，順序不限。若沒有標題列，第一欄為電子郵件地址，第二欄為元件。
- 填入元件名稱，若有多個元件則以 `;` 分隔。群組名稱代表群組內的所有元件。留空表示訂閱整個頁面。
- 每次最多可匯入 10,000 個地址，檔案大小上限為 2 MB。

| 匯入方式 | 效果 |
|---|---|
| **立即生效** | 適用於已在原狀態頁確認的地址。匯入後立即生效，不會寄送任何電子郵件。 |
| **寄送確認郵件** | 寄送確認郵件至每個地址，確認後才會開始接收更新。必須先設定電子郵件投遞。 |

**檢查檔案**只會回報匯入結果，不會修改任何資料。結果包含讀取的列數、將匯入的地址、已訂閱的地址、因曾取消訂閱而略過的地址，以及按列號列出的問題：缺少電子郵件地址、地址無效、地址在檔案中重複出現，或元件不存在於頁面上。

電子郵件訂閱者會以純文字郵件接收每則更新。郵件使用頁面的預設語言。郵件中的狀態名稱與頁面上的標籤一致，例如**效能下降**。

| 電子郵件 | 主旨 | 內文 |
|---|---|---|
| 確認訂閱 | `确认订阅 <页面名称> 的状态更新` | 確認連結與取消訂閱連結。 |
| 元件狀態變更 | `<页面名称>：<组件> · <状态>` | 元件、新狀態與頁面網址。 |
| 事件更新 | `<页面名称>：<标题> · <状态>` | 標題、狀態、客戶更新與頁面網址。 |
| 維護更新 | `<页面名称>：<标题> · <状态>` | 事件更新的所有內容，另加**排程時間**與排程開始時間。 |
| 維護提醒 | `<页面名称>：<标题> · 提醒` | 標題、**排程時間**與排程開始時間，以及頁面網址。 |
| 管理訂閱 | `管理 <页面名称> 的状态更新订阅` | 管理訂閱的連結。 |
| 事件事後檢討 | `<页面名称>：事故复盘 · <标题>` | Markdown 格式的事件檢討與事件網址。 |

若更新中承諾了下次更新的時間，郵件會多一行**下次更新不晚於**及對應時間。時間採用頁面時區。除了確認郵件，每封郵件末尾都有管理訂閱和取消訂閱連結。

**排程時間**會採用頁面時區並標示時差，例如 `2026-05-25 18:00 UTC+08:00 (Asia/Shanghai)`。

Webhook 訂閱者會透過 JSON 請求接收每則更新。關於請求格式、Payload 欄位與重試間隔，請參閱[狀態頁 Webhook 訂閱](/zh-Hant/status-pages/webhooks)。

每次發布事件或維護更新時，系統都會為符合條件的訂閱者建立有上限的投遞工作。**訂閱者**頁面會顯示嘗試次數、是否成功、最近一次錯誤與重試狀態。投遞紀錄保留期限可設為 30、60、90、180 或 365 天。

## 私人存取

私人狀態頁支援電子郵件地址與電子郵件網域的允許清單。獲准的訪客可先申請一次性 Magic Link，再取得有效期限為 1、7 或 30 天的狀態頁工作階段。含連結的電子郵件會使用頁面的預設語言，連結有效期限為 15 分鐘。管理員可以立即撤銷使用中的工作階段。私人存取限制適用於公開頁面、封存紀錄、事件詳細資料與訂閱流程。

## 自訂網域與 TLS

新增網域前，請先將 <code>http.external_url</code> 設為 MoleSignal 實際使用的公開 URL。網域面板接著會顯示驗證網域擁有權及設定路由所需建立的 DNS 記錄。

網域狀態依序為**等待 DNS**、**驗證中**、**已驗證**、**正在設定 TLS**與**有效**。處於**失敗**或**降級**狀態時，系統會顯示原因與重試選項，方便排除問題。

若要讓 MoleSignal 使用自動管理的憑證直接託管自訂主機名稱，請啟用 <code>http.tls</code> 並設定帳號的電子郵件地址：

```toml
[http]
external_url = "https://molesignal.example.com"

[http.tls]
enabled = true
account_email = "ops@example.com"
```

若在外部負載平衡器終止 TLS，仍須確保公開 URL 和 DNS 目標正確，並在網路邊緣管理憑證。

## 自動化發布

開啟**設定 → 自動化**，將維運事件轉為客戶更新。

1. 選擇**警示事件**、**合成監測檢查**或**元件相依性**作為來源。
2. 選擇特定資源、最低嚴重程度或 Monitor 狀態轉換，並填入必須符合的標籤。
3. 新增延遲，避免因瞬間故障直接發布客戶通知。
4. 對應事件影響與受影響的狀態頁元件。若未在**元件相依性**規則中選擇元件，系統會針對相依性發生變化且選擇「交由自動化規則處理」的元件發布事件。範本可用 `{{labels.component_name}}` 引用元件名稱，並用 `{{labels.dependency_status}}` 和 `{{labels.previous_dependency_status}}` 分別引用變更後及變更前的狀態。
5. 選擇**人工核准**或**自動發布**，並定義訊息範本。
6. 啟用前，請先在規則模擬器中測試。

系統依序比對規則，並由第一條完全符合的規則接管事件。Correlation Key 會將來源後續的狀態轉換連結至同一事件。人工模式會產生候選項目，供獲授權的使用者核准、拒絕或編輯。自動模式則會直接發布產生的事件。**暫停所有自動化**只會停止新的規則比對，不會修改已公開的事件。

<Note>
警示事件適用於由應變人員負責的偵測，合成監測 Monitor 則適用於直接驗證客戶使用服務的路徑。兩種來源都能更新同一套元件模型，但每條規則會保留各自的核准與延遲策略。
</Note>
