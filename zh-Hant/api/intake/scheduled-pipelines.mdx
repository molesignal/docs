| 操作 | 端點 | 權限 |
|---|---|---|
| 列出 | `GET /api/v1/scheduled_pipelines` | `pipelines.read` |
| 建立 | `POST /api/v1/scheduled_pipelines` | `pipelines.create`，讀取 `_audit` 時還需要 `audit.read` |
| 檢視 | `GET /api/v1/scheduled_pipelines/{id}` | `pipelines.read` |
| 更新 | `PUT /api/v1/scheduled_pipelines/{id}` | 修改設定需要 `pipelines.edit`，讀取 `_audit` 時還需要 `audit.read`；修改 `enabled` 需要 `pipelines.pause` |
| 刪除 | `DELETE /api/v1/scheduled_pipelines/{id}` | `pipelines.delete` |
| 執行記錄 | `GET /api/v1/scheduled_pipelines/{id}/runs` | `pipelines.read` |
| 今日配額與速率限制 | `GET /api/v1/scheduled_pipelines/{id}/limits` | `pipelines.read` |
| 回填 | `POST /api/v1/scheduled_pipelines/{id}/backfill` | `pipelines.run`，讀取 `_audit` 時還需要 `audit.read` |

## 列出

清單會傳回每條管線、最近一次執行的狀態，以及 24 小時摘要：

<ResponseExample>
```json 200
[
  {
    "id": "3KBHcb6imgQq7FXBsROGTIRHOyg",
    "name": "normalize-app",
    "sourceStream": "app_raw",
    "targetStream": "app",
    "functionSteps": { "mode": "scheduled", "signalType": "logs", "sources": ["app_raw", "nginx_raw"], "steps": [ ... ] },
    "cron": "every:5m",
    "lookbackSecs": 300,
    "enabled": true,
    "lastRunAt": 1790000000000000,
    "readUntil": { "appRaw": 1789999940000000, "nginxRaw": 1789999940000000 },
    "retry": null,
    "alertRecord": null,
    "auditReaderId": null,
    "auditReader": null,
    "createdAt": 1789900000000000,
    "updatedAt": 1789900000000000,
    "lastRunState": "succeeded",
    "lastRunStartedAt": 1790000000000000,
    "lastRunFinishedAt": 1790000000250000,
    "lastRunScannedRows": 1200,
    "lastRunError": null,
    "runs24h": 288,
    "succeededRuns24h": 288,
    "failedRuns24h": 0
  }
]
```
</ResponseExample>

每個項目都包含[檢視](#檢視)傳回的欄位、最近一次執行的 `lastRunState`、`lastRunStartedAt`、`lastRunFinishedAt`、`lastRunScannedRows`（讀入的事件數）與 `lastRunError`，以及過去 24 小時的執行次數。

## 檢視

```http
GET /api/v1/scheduled_pipelines/{id}
```

傳回管線、各來源的讀取位置，以及已排程的重試：

<ResponseExample>
```json 200
{
  "id": "3KBHcb6imgQq7FXBsROGTIRHOyg",
  "name": "normalize-app",
  "sourceStream": "app_raw",
  "targetStream": "app",
  "functionSteps": { "mode": "scheduled", "signalType": "logs", "sources": ["app_raw", "nginx_raw"], "steps": [ ... ] },
  "cron": "every:5m",
  "lookbackSecs": 300,
  "enabled": true,
  "lastRunAt": 1790000000000000,
  "readUntil": { "appRaw": 1789999940000000, "nginxRaw": 1789999640000000 },
  "retry": {
    "source": "nginx_raw",
    "attempt": 2,
    "nextAt": 1790000030000000,
    "error": "read: <reason>"
  },
  "alertRecord": null,
  "auditReaderId": null,
  "auditReader": null,
  "createdAt": 1789900000000000,
  "updatedAt": 1789900000000000
}
```
</ResponseExample>

| 欄位 | 說明 |
|---|---|
| `readUntil` | 各來源的讀取位置，單位為微秒。管線已處理該來源在這個時間之前的所有事件。清單不會列出尚未讀取的來源。 |
| `retry` | 已排程的失敗時段重試中，時間最早的一次。若無重試，則為 `null`。`source` 是來源，`attempt` 是這次重試的嘗試序號，`nextAt` 是重試時間，`error` 是上一次嘗試失敗的原因。 |
| `alertRecord` | 警示管線最近一次處理事件的 UTC 日期及當天的計數：`day`（`YYYY-MM-DD`）、`processed`、`dropped`、`failed`，以及當天最近一次捨棄與失敗的記錄 `last_dropped`、`last_failed`。兩筆記錄各包含 `atTime`、`rule`（警示規則、警示來源或合成監控檢查）和 `reason`。缺少的計數為 0。其他管線和尚未處理過事件的警示管線會傳回 `null`，請參閱[當天的計數](/zh-Hant/pipelines/alert-events#當天的計數)。 |
| `auditReaderId` | 管線讀取 `_audit` 時所用權限的使用者 ID，也就是最後儲存管線的使用者。若管線不讀取 `_audit`，則為 `null`。請參閱[稽核資料流](/zh-Hant/settings/data-security#稽核資料流)。 |
| `auditReader` | 該使用者的 `id`、`displayName` 和 `email`。具備 `pipelines.read` 權限即可檢視。若使用者已不存在或讀取失敗，則為 `null`，此時僅提供 `auditReaderId`。 |

請參閱[排程與讀取位置](/zh-Hant/pipelines#排程與讀取位置)和[重試與無法投遞的事件](/zh-Hant/pipelines#重試與死信)。

## 更新與刪除

`PUT` 的請求本文與[建立管線](/zh-Hant/api/intake/create-pipeline)相同，會取代整份設定。只修改 `enabled` 需要 `pipelines.pause`，其他 `PUT` 請求（包括未變更任何內容的請求）需要 `pipelines.edit`。將 `enabled` 從 `false` 改為 `true` 會重設讀取位置，並從 `lookbackSecs` 指定的回溯時間重新讀取各來源。`DELETE` 會傳回 `{"deleted": true}`。

如果管線讀取 `_audit`，`PUT` 也會決定管線使用哪個帳號的權限讀取。請參閱[稽核資料流](/zh-Hant/settings/data-security#稽核資料流)。

| `PUT` | 還需要 | 管線使用哪個帳號的權限讀取 `_audit` |
|---|---|---|
| 變更設定 | `audit.read`，且權杖不能屬於服務帳號 | 此後使用呼叫端的權限。 |
| 未變更任何內容 | 無 | 如果呼叫端具備 `audit.read` 且權杖不屬於服務帳號，此後使用呼叫端的權限。否則維持不變，也不會傳回錯誤。 |
| 只變更 `enabled` | 無 | 維持不變。 |

## 執行記錄

```http
GET /api/v1/scheduled_pipelines/{id}/runs?limit=50&beforeTime=<cursor>
```

依時間由新到舊傳回排程管線的執行記錄。即時管線和警示管線不會產生執行記錄。

<ResponseExample>
```json 200
[
  {
    "id": "3KE7Yq0d3jvXm5cJ8r2bWQzN1aP",
    "pipelineId": "3KBHcb6imgQq7FXBsROGTIRHOyg",
    "state": "succeeded",
    "startedAt": 1790000000000000,
    "finishedAt": 1790000000250000,
    "scannedRows": 1200,
    "writtenRows": 1150,
    "droppedRows": 48,
    "failedRows": 2,
    "attempt": 1,
    "error": null,
    "warning": "stream `app` rejected 2 event(s): <reason>"
  }
]
```
</ResponseExample>

| 欄位 | 說明 |
|---|---|
| `state` | `running`、`succeeded`、`failed` 或 `cancelled`。 |
| `startedAt`、`finishedAt` | 執行的開始與結束時間。執行期間，`finishedAt` 為 `null`。 |
| `scannedRows` | 這次執行從各來源讀入的事件數。 |
| `writtenRows` | 所有目標都已接收的事件數。 |
| `droppedRows` | 步驟以 `abort` 捨棄或在去除重複項目時移除的事件數。 |
| `failedRows` | 步驟處理失敗、轉送至來源，或至少有一個目標未接收的事件數。 |
| `attempt` | 第一次嘗試為 `1`。如果這次執行是在重試失敗的時段，則大於 `1`。 |
| `error` | 執行失敗的原因：失敗的時段及已排程的重試，或在沒有無法投遞事件資料流的情況下，某個目標資料流未接收任何事件。 |
| `warning` | 不會導致執行失敗的問題，例如處理失敗的事件、遭拒收或投遞失敗的事件，或達到重試上限後略過的時段。 |

`scannedRows` 等於 `writtenRows`、`droppedRows` 與 `failedRows` 的總和。

## 今日配額與速率限制

```http
GET /api/v1/scheduled_pipelines/{id}/limits
```

傳回即時管線的[配額與速率限制步驟](/zh-Hant/pipelines#計數與速率限制)今天（自 UTC 00:00 起）的放行量和超限量，包含所有節點的合計。各節點每 5 秒累加一次。今天沒有計數的步驟不會出現在結果中。

<ResponseExample>
```json 200
{
  "dayStart": 1790035200000000,
  "buckets": [
    {
      "step": "daily",
      "bucket": "[\"checkout\"]",
      "admittedEvents": 1000000,
      "admittedBytes": 524288000,
      "overEvents": 1240,
      "overBytes": 650117
    },
    {
      "step": "per-host",
      "bucket": "",
      "admittedEvents": 86400,
      "admittedBytes": 45298483,
      "overEvents": 12,
      "overBytes": 6291
    }
  ]
}
```
</ResponseExample>

| 欄位 | 說明 |
|---|---|
| `step` | 步驟名稱。 |
| `bucket` | 不分桶的配額與速率限制會將此欄留空。對於分桶的配額，此欄為 JSON 清單，依欄位順序列出各分桶欄位的值。若事件缺少欄位，則填入 `null`；超過 1000 個桶上限的其餘桶以 `*` 表示。 |
| `admittedEvents`、`admittedBytes` | 未超過上限而放行的數量。 |
| `overEvents`、`overBytes` | 超過上限的數量。步驟會依設定捨棄、繼續放行或轉送至其他資料流。 |

## 回填

```http
POST /api/v1/scheduled_pipelines/{id}/backfill
```

| 欄位 | 類型 | 說明 |
|---|---|---|
| `startTime` | integer | 時段的開始時間，單位為微秒。 |
| `endTime` | integer | 時段的結束時間，必須大於 `startTime`，且時段不得超過 31 天。 |

<RequestExample>
```bash cURL
curl -X POST http://localhost:5080/api/v1/scheduled_pipelines/$PIPELINE_ID/backfill \
  -H "authorization: Bearer $MS_TOKEN" \
  -H 'content-type: application/json' \
  -d '{"startTime": 1790000000000000, "endTime": 1790086400000000}'
```
</RequestExample>

<ResponseExample>
```json 202
{
  "jobs": [
    {
      "source": "app_raw",
      "jobId": "3KE6epTrWXts1oa2ePEKIHKxG19",
      "monitor": "/api/v1/query/jobs/3KE6epTrWXts1oa2ePEKIHKxG19"
    },
    {
      "source": "nginx_raw",
      "jobId": "3KE6eqAbXq0n2yLr7VvTq9cUo4D",
      "monitor": "/api/v1/query/jobs/3KE6eqAbXq0n2yLr7VvTq9cUo4D"
    }
  ]
}
```
</ResponseExample>

回填會為每個來源各提交一項搜尋工作。每項工作會讀取對應來源在指定時段內的事件、套用各個步驟，並依照排程執行的方式寫入和投遞事件，以及儲存無法投遞的事件。管線的讀取位置不變。使用各項工作的 `monitor` 路徑追蹤進度，請參閱[查詢](/zh-Hant/query#時間範圍與非同步工作)。

即時管線和警示管線會傳回 `400`（`realtime and alert pipelines do not support backfill`）。若管線讀取 `_audit`，而權杖缺少 `audit.read` 或屬於服務帳號，則會傳回 `403`。工作開始執行時，系統會再次檢查提交者的權限。若提交者已不具備 `audit.read`，工作就會失敗。
