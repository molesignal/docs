```http
POST /api/v1/scheduled_pipelines
```

建立管線。各種模式的路徑都沿用 `scheduled_pipelines` 這個名稱。此呼叫需要 `pipelines.create` 權限。

**請求本文**

| 欄位 | 類型 | 必填 | 說明 |
|---|---|---|---|
| `name` | string | 是 | 管線名稱。 |
| `sourceStream` | string | 是 | 管線讀取的第一個資料流。警示管線使用空字串。 |
| `targetStream` | string | 是 | 管線寫入的第一個資料流。若排程管線也讀取此資料流，呼叫會傳回 `409`。警示管線使用空字串。 |
| `functionSteps` | object | 是 | 步驟、模式、排程管線的設定或警示管線的條件，請參閱下文。 |
| `cron` | string | 是 | 排程管線使用 `every:30s`、`every:5m` 或 `every:1h`；即時管線和警示管線使用空字串。 |
| `lookbackSecs` | integer | 否 | 排程管線首次執行時，往回讀取各來源資料的秒數，預設為 300。排程管線須使用正數。 |
| `enabled` | boolean | 否 | 預設為 `true`。 |

`functionSteps` 的欄位：

| 欄位 | 說明 |
|---|---|
| `mode` | `scheduled`（預設）、`realtime` 或 `alert`。 |
| `signalType` | `logs`、`metrics` 或 `traces`，即時管線也可使用 `profiles`。指標、追蹤和效能剖析的即時管線直接在來源資料流中處理資料：`targetStream` 與 `sourceStream` 相同，不含路由步驟，也不能設定 `retainSource`。請參閱[指標與追蹤](/zh-Hant/pipelines#指標與追蹤)。效能剖析管線的來源為 `default`，請參閱[效能剖析](/zh-Hant/pipelines#效能剖析)。警示管線不含此欄位。 |
| `steps` | 依序執行的步驟。VRL 步驟包含 `transformName` 和 `script`，並將 `kind` 設為 `vrl`。路由步驟將 `kind` 設為 `builtin`、`operation` 設為 `route`，並包含 `routing` 物件。警示管線最多可有 20 個步驟，且不能包含路由步驟。AI 摘要步驟包含 `transformName`、`prompt` 和 `annotation`（用來寫入回答的註解，預設為 `ai_summary`），並將 `kind` 設為 `ai_summary`。呼叫 API 的步驟將 `kind` 設為 `http_enrich`，並包含 `connectorId`（組織的 HTTP 連接器）。查詢步驟將 `kind` 設為 `query_enrich`，並包含 `language`（`sql`（預設）或 `promql`）、`stream`、`streamType`（`logs`（預設）、`metrics` 或 `traces`）、`statement`、`windowSecs`（預設為 300，最多 86400）、`maxRows`（預設為 5，最多 50）和 `annotation`（預設為 `query_result`）。請參閱[警示管線的步驟](/zh-Hant/pipelines/alert-events#步驟)。即時管線也可使用計數步驟 `generate_metric`、`quota` 和 `throttle`，欄位請參閱下文。 |
| `alert` | 僅供警示管線使用，指定執行時機、條件與順序：`stage`（`open`（預設）或 `notify`）、`policies`（`notify` 管線適用的通知策略，留空表示警示事件的所有策略）、`sources`（`rule`、`external`、`synthetic`、`noData`，`notify` 也可使用 `manual`）、`severities`（`info`、`warning`、`error`、`critical`）、`labels`（事件必須包含此物件中的標籤，且值須相符）和 `order`（整數，預設為 0）。來源或嚴重程度清單留空時，會處理所有來源或所有嚴重程度的事件。請參閱[警示管線](/zh-Hant/pipelines/alert-events#透過-api-建立)。 |
| `sources` | 要讀取的資料流。管線先讀取 `sourceStream`，排程管線也會讀取清單中的其他資料流，合計最多 8 個。即時管線只接受 `[source_stream]`。 |
| `sinks` | 要寫入的資料流。`targetStream` 排在第一位，清單中的其他資料流也會收到所有事件，合計最多 8 個。即時管線只接受 `[target_stream]`。 |
| `sinkConnectors` | 僅供排程管線使用，指定接收所有事件的連接器 ID。 |
| `sinkTables` | 僅供排程管線使用，指定最多 8 張擴充表的名稱。每個事件都會在每張表中寫入一列。請參閱[寫入擴充表](/zh-Hant/pipelines#寫入擴充表)。 |
| `delaySecs` | 僅供排程管線使用，指定最近一段資料要保留多少秒以等待延遲抵達的事件，等候期結束後才會讀取。範圍為 0 到 3600，預設為 60。 |
| `retry` | 僅供排程管線使用。`runRetries` 指定讀取或寫入失敗的時間視窗可重試的次數，`deliveryRetries` 指定連接器傳送可重試的次數，兩者的範圍皆為 0 到 10，預設為 3。 |
| `deadLetterStream` | 僅供排程管線使用，指定儲存無法處理、寫入或傳送的事件的日誌資料流。不得使用管線讀取或寫入的資料流。 |
| `dedupeField` | 僅供排程管線使用。在同一次執行中，若事件的此欄位值已出現過，管線會捨棄該事件。 |
| `retainSource` | 僅供即時日誌管線使用，將原始事件保留在來源資料流中。 |

以下是計數步驟除了 `transformName` 和 `kind` 以外的欄位。同一條管線中的計數步驟不能同名。請參閱[計數與速率限制](/zh-Hant/pipelines#計數與速率限制)。

| 欄位 | 說明 |
|---|---|
| `conditions` | 指定步驟要處理的事件：最多 16 個條件，事件必須全部符合。每個條件包含 `field`、`test`（`equals`、`not_equals`、`contains`、`starts_with`、`matches`、`exists`、`missing`、`gt`、`gte`、`lt` 或 `lte`）和 `value`。`gt`、`gte`、`lt`、`lte` 用於數值比較，`matches` 使用規則運算式。留空時處理所有事件。 |
| `metric` | 僅適用於 `generate_metric`。包含 `name`、`type`（`count`、`gauge` 或 `histogram`）、`field`（取值和直方圖必填；計數若填寫則累加欄位值）、`groupBy`（最多 10 個欄位）、`buckets`（直方圖的 1 到 30 個遞增上界）、`stream`（指標資料流）和 `intervalSecs`（`10`、`30`、`60`（預設）或 `300`）。僅用於日誌、RUM 和追蹤管線。 |
| `quota` | 僅適用於 `quota`。包含 `unit`（`events` 或 `bytes`）、`limit`（以此單位計算的每日上限，1 到 10^15）、`partitionBy`（最多 5 個欄位）、`overrides`（最多 100 個 `{"values": {"<字段>": "<值>"}, "limit": <n>}`，`partitionBy` 的每個欄位都必須有值）、`action`（`drop`（預設）、`pass` 或 `route`）和 `target`（`route` 寫入的日誌資料流）。僅適用於日誌管線，以及 `rum_views` 和 `rum_vitals` 以外的 RUM 資料流；RUM 資料流不能使用 `route`。 |
| `throttle` | 僅適用於 `throttle`。包含 `limit`（每個時間視窗允許通過的事件數，1 到 1000000）、`windowSecs`（1 到 86400）、`groupBy`（最多 5 個欄位）、`action`（`drop`（預設）或 `route`）和 `target`。適用的管線與配額相同。 |

<RequestExample>
```bash cURL
curl -X POST http://localhost:5080/api/v1/scheduled_pipelines \
  -H "authorization: Bearer $MS_TOKEN" \
  -H 'content-type: application/json' \
  -d '{
    "name": "normalize-app",
    "sourceStream": "app_raw",
    "targetStream": "app",
    "functionSteps": {
      "mode": "scheduled",
      "signalType": "logs",
      "sources": ["app_raw", "nginx_raw"],
      "sinks": ["app", "app_archive"],
      "delaySecs": 60,
      "retry": { "runRetries": 3, "deliveryRetries": 3 },
      "deadLetterStream": "pipeline_dead_letters",
      "steps": [
        { "transformName": "normalize-level", "kind": "vrl",
          "script": ".level = downcase!(string!(.level))" }
      ]
    },
    "cron": "every:5m",
    "lookbackSecs": 300,
    "enabled": true
  }'
```
</RequestExample>

**錯誤**

| 狀態碼 | 原因 |
|---|---|
| `400` | 排程不符合 `every:Ns/m/h` 格式、回溯時間視窗不是正數、排程管線處理效能剖析資料、效能剖析管線的來源不是 `default`、指標、追蹤、效能剖析或 RUM 的即時管線寫入其他資料流、分流或保留原始事件、這類管線的步驟修改了範例中[必須維持不變的欄位](/zh-Hant/pipelines#指標與追蹤)、`rum_views` 或 `rum_vitals` 上的步驟可捨棄事件、VRL 步驟無法編譯、資料流名稱無效、讀取或寫入的資料流超過 8 個或擴充表超過 8 張、路由步驟的固定或備用資料流是來源資料流、無法投遞的事件所用的資料流也是管線讀取或寫入的資料流、嘗試寫入或路由至 [RUM 資料流](/zh-Hant/pipelines#rum-資料串流)、以 `rum_sessions` 作為即時管線的來源、嘗試寫入、路由至或即時修改[平台資料流](/zh-Hant/pipelines#平台資料串流)、`delaySecs` 或重試次數超出範圍。警示管線也可能有下列問題：來源或嚴重程度無法辨識、包含路由步驟、AI 摘要步驟沒有提示詞、呼叫 API 的步驟未使用組織的 HTTP 連接器、查詢步驟並非單一查詢、讀取 `_audit`、預留位置不在字串內或事件缺少對應的值、`notify` 管線包含向 MoleSignal 外部傳送資料的步驟、`open` 管線包含 `policies` 或 `manual` 來源，或步驟超過 20 個。其他原因包括排程或警示管線包含 `generate_metric`、`quota` 或 `throttle` 步驟、這類步驟用於不支援的資料、兩個這類步驟同名，或設定超出允許範圍，例如使用 PromQL 無法選取的指標名稱、使用每筆指標樣本都有的標籤（`value`、`le`、`metric_name` 等），或將 `target` 設為來源資料流。 |
| `403` | 管線讀取 `_audit`，但權杖缺少 `audit.read` 權限或屬於服務帳號。 |
| `409` | 排程管線會寫入它讀取的資料流，或同一資料類型的同一來源資料流已啟用一條即時管線（`a realtime pipeline is already enabled for this <signal> stream`）。 |

如需即時模式、路由步驟、讀取位置與重試的說明，請參閱[管線](/zh-Hant/pipelines)。
