```http
GET /api/v1/alerts/incidents
GET /api/v1/alerts/incidents/{id}
```

第一個呼叫依時間倒序列出事件，不包含[併入](/zh-Hant/api/alerting/merge-incidents)其他事件的事件；已併入的事件會列在主要事件的[時間軸](/zh-Hant/api/alerting/incident-timeline)中。第二個呼叫傳回單一事件，也能讀取已併入的事件。兩個呼叫都需要 `alerts.incidents.read`。

**清單的查詢參數**

| 參數 | 類型 | 說明 |
|---|---|---|
| `scope` | string | `active`（預設）傳回狀態為 `open` 或 `acknowledged` 的事件。`all` 傳回時間範圍內建立的事件，以及所有作用中的事件，不論事件已開啟多久。 |
| `windowSecs` | integer | `scope=all` 向前回溯的時間範圍。預設為 `604800`（7 天）。值必須介於 3600 到 31536000 之間。 |

清單項目採用精簡格式：`triggeringQuery` 為 `null`，`traceIds`、`hostIds` 與 `affectedServices` 各最多保留一個值。若要取得完整記錄，請讀取單一事件。

<RequestExample>
```bash cURL
curl "http://localhost:5080/api/v1/alerts/incidents?scope=all&windowSecs=86400" \
  -H "authorization: Bearer $MS_TOKEN"
```
</RequestExample>

## 事件欄位

| 欄位 | 說明 |
|---|---|
| `id`、`orgId`、`ruleId` | 事件、組織與規則的識別碼。 |
| `escalationPolicyId` | 在事件開啟時決定：採用來源指定的策略；若來源使用預設策略，則採用[警示路由](/zh-Hant/alerting/routing)選出的策略。開始升級時，會將別名 `default` 換成名稱為 `default` 的策略 ID。 |
| `status` | `open`、`acknowledged` 或 `resolved`。資料模型還有 `closed`，目前沒有任何呼叫會設定此狀態。 |
| `severity` | `info`、`warning`、`error` 或 `critical`。 |
| `summary` | 規則名稱，後接最多兩個受影響的服務，額外的服務數以 `+N` 表示。 |
| `fingerprint` | 規則 `id` 與 `labels` 的雜湊值。同一規則的每個指紋只會有一個作用中的事件。 |
| `currentStep`、`currentLoop`、`currentStepStartedAt` | 升級進度。步驟編號從 0 開始，時間單位為微秒。 |
| `assignees` | 獲指派處理事件的使用者：目前升級步驟直接指定的目標（該步驟的 `user` 目標，以及每個 `schedule` 目標目前的值班人員），加上確認事件的使用者。第一個步驟執行前，此欄位為空。只指定團隊的步驟會保留原先的負責人。 |
| `labels`、`annotations` | 事件開啟時的快照：規則的 `labels`，加上查詢結果中的 `service` 與 `host`。後續修改規則不會變更快照。 |
| `traceIds`、`hostIds`、`affectedServices` | 查詢結果中 `trace_id`、`host` 與 `service` 欄的值，已移除重複值，各最多 10 個。 |
| `triggeringQuery` | 包含 `language`、`statement` 與 `sampleValues`。每個樣本包含以微秒表示的 `ts`（結果沒有時間欄時為 `0`）、`value` 與 `labels`。只有讀取單一事件的呼叫會傳回此欄位。 |
| `createdAt` | 事件開啟的時間，單位為微秒。 |
| `acknowledgedAt`、`acknowledgedBy` | 最近一次確認事件的時間與使用者。 |
| `resolvedAt`、`resolvedBy` | 解決事件的時間與使用者。評估器因規則不再符合條件而將事件標記為已解決時，`resolvedBy` 為 `null`。 |
| `teamId` | 事件開啟時由[警示路由](/zh-Hant/alerting/routing)指派的團隊；若未指派，則為 `null`。 |
| `routing` | 指派依據。導入路由前開啟的事件，此欄位為 `null`。`reason` 為 `rule`（符合路由規則，包含 `ruleId` 和當時的 `ruleName`）、`service_owner`（服務的負責團隊，包含 `service`）、`team_label`（team 標籤）、`default`（預設策略）或 `source`（來源已指定升級策略，僅指派團隊）。 |
| `snoozedUntil`、`snoozedBy` | 事件[暫緩](/zh-Hant/api/alerting/snooze-incident)期間，分別記錄暫緩結束的時間（微秒）與設定暫緩的使用者；未暫緩時為 `null`。 |
| `severitySetBy` | 手動[設定嚴重程度](/zh-Hant/api/alerting/set-incident-severity)的使用者。設定後，規則不再變更嚴重程度；若未手動設定，則為 `null`。 |
| `mergedInto` | 此事件[併入](/zh-Hant/api/alerting/merge-incidents)的目標事件；若未併入其他事件，則為 `null`。 |
| `assigneesPinned` | 手動指定負責人時為 `true`；升級至下一級時才會更換負責人。 |
| `dispatchRound`、`dispatchReason` | 分別表示升級通知輪次與目前層級最近一次發送通知的原因。立即升級、改派團隊、改用其他策略或調高嚴重程度時，輪次加一，同一層級可以再次發送通知。原因為 `step`、`manual`、`reassigned`、`responder_added`、`snooze_ended`、`ack_timeout` 或 `severity_raised`。 |
| `revision` | 事件每變更一次，值就加一。 |

**錯誤**

| 狀態碼 | 原因 |
|---|---|
| `403` | 權杖缺少 `alerts.incidents.read` 權限。 |
| `404` | 事件不存在。 |
