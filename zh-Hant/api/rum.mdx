RUM API 接收來自瀏覽器和行動端用戶端的事件，也提供事件讀取功能。所有端點都使用 `/api/v1/rum` 前綴，且需要 Bearer Token。

```http
Authorization: Bearer <token>
```

寫入事件和重播片段需要 `rum.write`；與應用程式繫結的 [Client Token](/zh-Hant/api/auth/rum-token) 僅對單一應用程式有這項權限。讀取時需要對應內容的讀取權限：`rum.events.read`、`rum.sessions.read`、`rum.replay.read`、`rum.issues.read`、`rum.analytics.read`、`rum.applications.read` 或 `rum.playlists.read`。平台呼叫端可在受保護的 `_sys` 範圍內使用 `sys.telemetry.read`。建立、修改和刪除應用程式需要 `rum.applications.manage`，設定問題的狀態、團隊或負責人需要 `rum.issues.manage`。

**類型** 說明端點處理哪種資料列：`sessions`、`views`、`actions`、`errors`、`resources`、`longTasks`、`vitals` 或 `logs`。每種類型都對應一個[資料流](/zh-Hant/rum/events#事件的儲存位置)，類型名稱就是去掉 `rum_` 前綴後的資料流名稱。

這些資料列來自真實使用者。預設不包含 `synthetics` 或 `ci_test` 類型的工作階段，除非篩選條件指定 `session.type`、`synthetics.*` 或 `ci_test.*`。請參閱[測試流量](/zh-Hant/rum/test-traffic)。欄位也可以是 JSON 欄中的鍵：`feature_flags.<key>`、`context.<key>`、`usr.extra.<key>` 或 `view.custom_timings.<key>`。

## 傳送重播片段

```http
POST /api/v1/rum/replay
```

```json
{
  "application": "checkout-web",
  "sessionId": "6f1c2b7e-1d5a-4c6b-9a3e-0a1b2c3d4e5f",
  "seq": 1,
  "events": [{ "type": 2, "timestamp": 1790000000000, "data": { "node": {} } }]
}
```

`sessionId`、`seq` 和 `events` 為必填欄位。也可以附上 SDK 初始化時設定的 `env`、`service` 和 `version`。應用程式會根據這些值套用[保留篩選器](/zh-Hant/rum/sampling#篩選器)，不儲存未保留的工作階段的片段。不接受其他欄位。`events` 是 rrweb 事件。Client Token 只能寫入所繫結的應用程式：可以省略 `application`，指定其他值會傳回 `403`；使用其他憑證時，必須指定應用程式。應用程式不存在時傳回 `404`。回應包含已儲存片段的資訊：`id`、`seq`、`eventCount` 和 `hasFullSnapshot`。

`GET /api/v1/rum/replay/{sessionId}` 傳回 `sessionId`、`segmentCount` 和 `events`，其中 `events` 依序列出該工作階段所有片段的事件。

## 管理應用程式

應用程式包含 `id`、`name`、`platform` 和 `settings`：

```json
{
  "id": "checkout-web",
  "name": "Checkout web",
  "platform": "browser",
  "settings": {
    "collectIp": true,
    "collectGeo": true,
    "defaultPrivacy": "mask",
    "issuesPerHour": 100,
    "scrub": ["secrets", "emails", "phones", "cards", "national_ids", "url_params"],
    "sessionSampleRate": 100,
    "retentionFilters": [],
    "keepErrors": true,
    "sdk": { "sessionReplaySampleRate": 20, "forwardConsoleLogs": ["warn", "error"] },
    "segments": [{ "id": "enterprise", "name": "Enterprise", "conditions": [{ "field": "usr.extra.plan", "op": "is", "values": ["enterprise"] }] }]
  },
  "createdBy": "<user-id>",
  "createdAt": 1790000000000000,
  "updatedAt": 1790000000000000
}
```

| 欄位 | 規則 |
|---|---|
| `id` | 僅能在建立時設定。長度為 1 到 64 個字元，可使用 `A-Z`、`a-z`、`0-9`、`.`、`_`、`:` 和 `-`。省略時依名稱產生。無法修改。 |
| `name` | 建立時必填。長度為 1 到 128 個字元。 |
| `platform` | `browser`（預設）、`android`、`ios`、`flutter`、`react-native` 或 `other`。 |
| `settings` | `collectIp` 和 `collectGeo` 為布林值，預設為 `true`。`defaultPrivacy` 為 `mask`（預設）、`mask-user-input` 或 `allow`。`issuesPerHour` 是應用程式每小時新建的[問題](/zh-Hant/rum/errors#每小時新增的-issue)數量，範圍為 1 到 10000，預設為 100。`scrub` 是儲存事件前要移除的敏感文字類別清單，可選 `secrets`、`emails`、`phones`、`cards`、`national_ids` 和 `url_params`。預設移除所有類別，空清單表示不移除任何類別（請參閱 [RUM 隱私](/zh-Hant/rum/privacy#在接收事件時移除敏感文字)）。`sessionSampleRate` 是未符合任何保留篩選器的工作階段的保留百分比，為 0 到 100 的整數，預設為 100（請參閱 [RUM 資料取樣](/zh-Hant/rum/sampling#在伺服器端保留部分工作階段)）。超過 100 時傳回 `400`。`retentionFilters` 是[篩選器](/zh-Hant/rum/sampling#篩選器)清單，最多 10 個。每個篩選器包含 `{ "name", "rate", "conditions" }`，另有 `id`：省略時由伺服器依名稱產生，重新命名時保持不變。`PATCH` 會取代整份清單。`rate` 為 0 到 100 的整數。條件格式為 `{ "field", "op", "values" }`：`field` 可選 `env`、`service`、`version`、`source`、`session.type`、`geo.country_iso_code`、`browser.name`、`os.name` 和 `device.type`，`op` 為 `is` 或 `is_not`，`values` 包含 1 到 20 個值。每個篩選器最多有 5 個條件。名稱不得重複（不區分大小寫），`default` 和 `errors` 兩個 ID 已保留。`keepErrors` 決定是否保留未保留的工作階段中的錯誤，預設為 `true`。清單不符合規則時傳回 `400`。`segments` 是[分群](/zh-Hant/rum/analytics#分群)清單，最多 20 個。每個分群包含 `{ "name", "conditions" }`，省略 `id` 時依名稱產生，重新命名時保持不變。`PATCH` 會取代整份清單。條件格式為 `{ "field", "op", "values" }`，`field` 為 `service`、`version`、`source`、`usr.id`、`usr.email`、`account.id`、`browser.name`、`os.name`、`device.type`、`geo.country_iso_code`、`geo.continent_code`、`geo.city` 或 `usr.extra.<key>`，`op` 為 `is` 或 `is_not`，`values` 包含 1 到 20 個值。每個分群有 1 到 5 個條件。`sdk` 是 `GET /api/v1/rum/config` 傳回給以 `remoteConfiguration` 啟動的 SDK 的內容，可包含 `sessionSampleRate`、`sessionReplaySampleRate`（0 到 100）、`defaultPrivacyLevel`、`trackUserInteractions` 和 `forwardConsoleLogs`（由 `debug`、`log`、`info`、`warn`、`error` 組成的清單）。未指定的項目使用頁面提供的值。省略的項目在建立時使用預設值，在 `PATCH` 時保留原值。 |

`POST` 傳回新建的應用程式；識別碼或名稱已存在時傳回 `409`。`PATCH` 接受 `name`、`platform` 和 `settings` 中的任意組合。`DELETE` 傳回 `{ "deleted": true }`。應用程式已傳送的事件會留在資料流中，直到保留期限結束。

## 搜尋資料列

```http
GET /api/v1/rum/search?type=errors&from=1790000000000000&to=1790003600000000&filters=[{"field":"env","op":"=","value":"production"}]&limit=100
```

`POST` 在 JSON 請求主體中使用相同的參數名稱，適合無法放入網址的查詢。在網址中，`filters`、`freeText` 和 `columns` 是以 JSON 編碼的清單。

| 參數 | 類型 | 行為 |
|---|---|---|
| `type` | string | 必填。資料列的類型。 |
| `from`、`to` | integer | 時間範圍，以 Unix epoch 起算的微秒為單位。`to` 預設為目前時間，`from` 預設為 `to` 往前推 24 小時。`to` 必須大於 `from`。 |
| `filters` | list | 每筆資料列都必須符合的條件，請參閱下文。 |
| `freeText` | 字串清單 | 最多 8 個詞。每個詞都必須出現在該類型的至少一個文字欄中，不區分大小寫。 |
| `columns` | 字串清單 | 要傳回的欄位。省略時使用該類型的預設欄位。一律包含用來識別資料列的欄位。 |
| `limit` | integer | 每頁筆數，範圍為 1 到 5,000，預設為 100。 |
| `cursor` | string | 上一次回應的 `nextCursor` 或 `previousCursor`。省略其他參數，或原樣重複提供。 |

**篩選條件** 包含 `field`、`op` 和 `value`。最多 32 個條件，`value` 最長 512 個字元。

| `op` | 含義 |
|---|---|
| `=`、`!=` | 等於和不等於。`value` 為空時，分別檢查欄位是否無值或有值。 |
| `in`、`not_in` | 欄位值在清單中，或不在清單中。`value` 是包含 1 到 100 個值的 JSON 清單，例如 `["Chrome","Safari"]`。 |
| `contains` | 欄位包含這段文字，不區分大小寫。適用於文字欄和 JSON 文件。 |
| `>`、`>=`、`<`、`<=` | 比較數值或時間。 |
| `exists`、`missing` | 欄位有值或無值。 |

如果指定該類型沒有的欄位，或使用欄位不支援的運算子，請求會傳回 `400`。

回應包含一頁資料列，最新的排在最前面：

```json
{
  "items": [
    { "timestamp": 1790000001600000, "error.message": "Payment provider timeout", "error.id": "0a9b8c7d-6e5f-4a3b-8c1d-2e3f4a5b6c70" }
  ],
  "hasMore": true,
  "nextCursor": "<cursor>",
  "previousCursor": null
}
```

每筆資料列包含 `timestamp` 和要求的欄位。JSON 欄儲存文件。每個檢視和工作階段只會出現一次，且只傳回最新版本。

## 統計與描述資料列

`facets` 接受 `search` 的參數（不分頁），並新增必填的 `field` 和 `limit`（1 到 100，預設 10）。傳回相符資料列中該欄位最常見的值：

```json
{ "field": "browser.name", "values": [{ "value": "Chrome", "count": 812 }, { "value": "Safari", "count": 247 }] }
```

統計耗時過長或系統忙碌時，傳回空清單，並將 `unavailable` 設為 `time_budget` 或 `busy`。對儲存 JSON 文件的欄位執行統計會傳回 `400`。JSON 文件中的鍵（如 `feature_flags.checkout_v2`）可以依值統計。`session.type` 的 facet 統計所有類型的工作階段。

`keys` 接受相同的選取條件和 `column`（必填：`feature_flags`、`context`、`usr.extra` 或 `view.custom_timings`），以及 `limit`（1 到 500，預設 100）。`type` 預設為 `views`。傳回這些鍵，依含有各鍵的工作階段數由多至少排序：

```json
{ "column": "feature_flags", "keys": [{ "key": "checkout_v2", "sessions": 812 }] }
```

`distribution` 接受相同的選取條件、`field`（必填，指定數值欄位或 JSON 欄位中儲存數值的鍵）和 `bars`（1 到 100，預設 40）。依實際儲存的資料列計算。各柱等寬，從最小值排到第 99 百分位數，最後一柱納入更大的值，因此該柱的 `to` 是最大值。所有值都相同時，只有一柱。

```json
{
  "field": "view.loading_time",
  "unit": "ns",
  "rows": 812,
  "min": 90000000,
  "max": 41000000000,
  "p50": 800000000,
  "p75": 1400000000,
  "p95": 3100000000,
  "p99": 6000000000,
  "bars": [{ "from": 90000000, "to": 237750000, "rows": 12 }]
}
```

`histogram` 接受相同的選取條件，以及用來設定統計區間的 `bucketTime`（至少 1000）和 `originTime`（第一個區間的起點，省略時為 `from`，不得晚於 `from`）。每個範圍最多 512 個區間。每個區間都以 `{ startTime, total, errors }` 表示。`errors` 統計有問題的資料列：發生錯誤的工作階段和檢視、有挫折訊號的操作，以及狀態碼為 `400` 以上或 `0` 的請求。若資料類型沒有這類資料列，`split` 為 `false`。

`GET /api/v1/rum/schema/{type}` 列出其他端點接受和傳回的欄位：

```json
{
  "type": "views",
  "stream": "rum_views",
  "idField": "view.id",
  "versioned": true,
  "defaultColumns": ["view.id", "view.url_path", "view.loading_time"],
  "fields": [
    { "name": "view.loading_time", "dataType": "int64", "unit": "ns", "facetable": true, "indexed": false }
  ]
}
```

`dataType` 為 `bool`、`int64`、`float64`、`utf8` 或 `json`。`unit` 為 `ns`、`ms`、`epoch_ms`、`bytes`、`count`、`score`、`percent`、`per_second`、`px` 或 `none`：持續時間以 SDK 傳送的奈秒值儲存，由用戶端設定顯示格式。`epoch_ms` 表示時間點，即自 Unix 紀元起算的毫秒數，例如 `session.start` 和 `session.last_activity`。用戶端會將這類值顯示為日期和時間。`facetable` 欄位可以依值統計，篩選 `indexed` 欄位時不必讀取每筆資料列，`idField` 是用來識別各筆資料列的欄位。

## 衡量資料列

`aggregate` 接受 `search` 的選取條件，對相符的資料列計算衡量值。傳回圖表、表格和地圖所需的數值，例如工作階段數或某項 Web Vitals 指標的第 75 百分位數，並可依頁面或小時細分。

```http
GET /api/v1/rum/aggregate?type=views&groupBy=["view.url_path_group"]&measures=[{"fn":"count","name":"views"},{"fn":"p75","field":"view.performance.lcp.timestamp","name":"lcp"}]&limit=5
```

| 參數 | 類型 | 行為 |
|---|---|---|
| `type`、`from`、`to`、`filters`、`freeText` | | 與 `search` 相同。 |
| `measures` | 清單 | 必填。最多 16 個衡量項目，見下文。 |
| `groupBy` | 字串清單 | 最多 2 個欄位，每種值的組合各占一列。不能使用儲存 JSON 文件的欄位分組，但可以使用其中的鍵，例如 `feature_flags.checkout_v2`。 |
| `bucketTime`、`originTime` | 整數 | 與 `histogram` 相同。指定後，每個群組在每個時間區間各占一列。 |
| `orderBy` | 字串 | 衡量項目名稱、分組欄位，或 `time`（有時間區間但沒有分組時）。省略時，依第一個衡量項目排列群組，依時間排列區間。 |
| `order` | `asc` 或 `desc` | 省略時，衡量值遞減排序，群組和時間遞增排序。 |
| `limit` | 整數 | 群組數，1 到 250，預設 10。有時間區間時最多 20 個，每個群組都會展開至所有時間區間。 |
| `estimate` | 布林值 | 預設 `true`：估算所有工作階段的數量、總和與平均值，依各列的保留比例（`retention.rate`）放大，並依相同比例加權計算百分位數。`false` 只計算實際儲存的資料列，與探索工具相同。 |

每個**衡量項目**都有 `fn` 和 `field`，也可以包含 `name`、`where` 和 `fallback`。

| `fn` | 含義 |
|---|---|
| `count` | 資料列數。指定 `field` 時，只計算該欄位有值的資料列。啟用 `estimate` 時，依各列的保留比例放大。 |
| `stored` | 實際儲存的資料列數，不考慮保留比例。 |
| `count_distinct` | `field` 的相異值數量。`fallback` 指定 `field` 沒有值時改用的欄位，讓沒有 ID 的使用者仍可透過匿名 ID 區分。使用者和其他值依實際觀測到的數量計算；啟用 `estimate` 時，會放大工作階段（`session.id`）的數量。 |
| `sum`、`avg`、`min`、`max` | 計算數值的總和、平均值、最小值和最大值。 |
| `p50`、`p75`、`p90`、`p95`、`p99` | 數值的百分位數，為估計值。 |

`where` 是篩選條件清單，寫法與 `search` 相同。衡量項目只計算符合條件的資料列：`{"fn":"count","where":[{"field":"session.error.count","op":"=","value":"0"}]}` 統計沒有錯誤的工作階段。衡量項目以 `name` 命名；未指定時使用 `fn(field)`，若也未指定欄位，則使用 `fn`。衡量項目名稱不得重複。指定該類型沒有的欄位，或對非數值欄位執行數值運算時，傳回 `400`。

```json
{
  "groupBy": ["view.url_path_group"],
  "measures": [
    { "name": "views", "fn": "count", "unit": "count" },
    { "name": "lcp", "fn": "p75", "field": "view.performance.lcp.timestamp", "unit": "ns" }
  ],
  "rows": [
    { "group": ["/checkout"], "values": [8031, 3400000000.0] },
    { "group": [null], "values": [212, null] }
  ]
}
```

每列包含所屬的 `group`（順序與 `groupBy` 相同）和各衡量項目的 `values`（順序與 `measures` 相同）。依時間區間細分時，也包含該區間的起點 `startTime`。資料列沒有分組欄位值時，該分組值為 `null`；沒有數值可用於計算百分位數時，結果也為 `null`。`unit` 為 `count` 或 `schema` 提供的欄位單位。每個檢視和工作階段只計算一次，並採用最新版本。沒有相符的資料列時，若啟用分組或時間區間，回應不含資料列；兩者皆未啟用時，回應包含一列：計數為 `0`，其他衡量值為 `null`。若沒有權限查看某個值，則傳回遮蔽後的文字。統計耗時過長或系統忙碌時，傳回空的 `rows`，並將 `unavailable` 設為 `time_budget` 或 `busy`。

## 儀表板面板的陳述式

```http
POST /api/v1/rum/panel-statement
```

傳回[儀表板](/zh-Hant/dashboards)面板繪製[探索頁面](/zh-Hant/rum/explorer#加入儀表板)圖表所用的 SQL 陳述式：對相同的資料列產生相同的數值，計算方式與 `estimate` 為 `false` 的 `aggregate` 相同。此端點不讀取資料。陳述式不指定時間範圍，由儀表板依選取的時間範圍執行。需要 `rum.events.read`。

```json
{
  "type": "views",
  "filters": [{ "field": "env", "op": "=", "value": "production" }],
  "chart": "timeseries",
  "measures": [{ "fn": "p75", "field": "view.loading_time", "name": "p75 加载时间" }],
  "groupBy": ["browser.name"],
  "groupNames": ["浏览器"],
  "limit": 5,
  "interval": "${interval}"
}
```

| 欄位 | 類型 | 行為 |
|---|---|---|
| `type`、`filters`、`freeText` | | 與 `search` 相同。 |
| `chart` | string | 必填。`timeseries`、`toplist`、`table` 或 `distribution`。 |
| `measures`、`groupBy`、`orderBy`、`order`、`limit` | | 與 `aggregate` 相同，但不支援 `estimate` 和時間區間參數。`toplist` 只接受一個分組欄位。`timeseries` 最多追蹤 20 個群組。每個衡量項目各占一欄，以其 `name` 命名。 |
| `groupNames` | 字串清單 | 分組欄位的顯示名稱，順序與 `groupBy` 相同。未指定名稱時，使用欄位名稱。 |
| `field` | string | `distribution` 必填：指定要呈現分布的數值欄位。分布欄以 `groupNames` 的第一個名稱命名，計數欄以第一個衡量項目的 `name` 命名。 |
| `interval` | string | `timeseries` 必填：指定時間區間的長度，可使用 `${interval}` 這類儀表板變數，或 `15 minutes` 這類時長。 |

```json
{
  "stream": "rum_views",
  "statement": "WITH \"__top\" AS (SELECT … LIMIT 5) SELECT date_bin(INTERVAL '${interval}', _timestamp) AS \"time\", … FROM \"rum_views_latest\" JOIN \"__top\" ON … GROUP BY 1, 2 ORDER BY 1, 2",
  "columns": [
    { "name": "time", "role": "time", "unit": "none" },
    { "name": "浏览器", "role": "group", "unit": "none" },
    { "name": "p75 加载时间", "role": "measure", "unit": "ms" }
  ],
  "limit": 10000
}
```

陳述式讀取 `stream`，並透過 `rum_views_latest` 或 `rum_sessions_latest` 取得檢視和工作階段的最新版本。陳述式包含選取條件，且不計入合成監控和 CI 產生的工作階段，除非篩選條件提到 `session.type`、`synthetics.*` 或 `ci_test.*`。`columns` 依序列出傳回的欄位：時間區間起點 `time`、各分組欄位和各衡量項目。衡量項目的 `unit` 是顯示用的單位，因此持續時間使用 `ms`。

- `timeseries` 的每個群組在每個時間區間各占一列。群組是整個時間範圍內依第一個衡量項目排名最前的幾組。
- `toplist` 和 `table` 的每個群組各占一列，依指定順序排列，最多 `limit` 列。
- `distribution` 傳回 40 根柱，從最小值到第 99 百分位數，最後一柱納入更大的值。各柱以區間起點命名，採用該值的顯示單位。

`limit` 是面板要讀取的資料列數。指定該類型沒有的欄位、提供的內容無法繪製指定圖表（`toplist` 未恰好指定一個分組欄位，或 `timeseries` 未指定 `interval`），或 `interval` 既不是變數也不是時長時，都會傳回 `400`。

## 漏斗、路徑與留存

`/api/v1/rum/analytics` 下的三個端點提供 [RUM 分析](/zh-Hant/rum/analytics) 所需的資料。這些端點都接受 `search` 中適用於工作階段、檢視和操作的篩選參數：`from` 和 `to`（微秒），以及 `filters`，也就是每筆資料列都要符合的條件，通常是應用程式（`application.id`）和環境（`env`）。使用 `GET` 時，在查詢參數中以 JSON 傳入清單，便可用單一連結表示查詢；使用 `POST` 時，在 JSON 請求主體中使用相同的名稱。需要 `rum.analytics.read`，或受保護的 `_sys` 範圍內的 `sys.telemetry.read`。統計耗時過長或系統忙碌時，不傳回數值，並將 `unavailable` 設為 `time_budget` 或 `busy`。回應包含對應的 `from` 和 `to`。

### 漏斗

```http
GET /api/v1/rum/analytics/funnel?filters=[{"field":"application.id","op":"=","value":"shop-web"}]&steps=[{"type":"views","filters":[{"field":"view.url_path_group","op":"=","value":"/cart"}]},{"type":"actions","name":"Paid","filters":[{"field":"action.target.name","op":"=","value":"Pay now"}]}]&windowSecs=1800&breakdown=browser.name
```

| 參數 | 類型 | 行為 |
|---|---|---|
| `from`、`to` | integer | 微秒。省略時使用最近 7 天。 |
| `filters` | list | 除了各步驟自己的篩選條件，每一步也都必須符合這些條件。 |
| `steps` | list | 必填，2 到 8 步。每個步驟包含 `type`（`views` 或 `actions`）、套用至該類型資料列的 `filters`（與 `search` 相同），以及選填的 `name`；省略 `name` 時，使用該步驟第一個篩選條件的值。 |
| `windowSecs` | integer | 從第一步到後續任一步驟的最長秒數。省略時不限時間。 |
| `breakdown` | string | 第一步資料列中的文字欄位。每個欄位值各產生一個漏斗，保留工作階段數最多的 10 個值。 |

以每個工作階段中第一筆符合條件的資料列計入第一步。後續每一步都在同一工作階段中，找出時間晚於上一步資料列且符合該步驟條件的第一筆資料列，再計入該步驟。

```json
{
  "groups": [
    {
      "value": null,
      "steps": [
        { "name": "/cart", "sessions": 4, "conversion": 1.0, "fromPrevious": null, "medianMs": null },
        { "name": "Paid", "sessions": 2, "conversion": 0.5, "fromPrevious": 0.5, "medianMs": 210000.0 }
      ]
    }
  ],
  "from": 1779400000000000,
  "to": 1780000000000000
}
```

每個群組都是 `breakdown` 為特定值的工作階段所組成的漏斗，依第一步的工作階段數排序。`value` 為 `null` 表示合併所有工作階段，或表示資料列沒有此值的工作階段。`conversion` 是占第一步工作階段數的比例，`fromPrevious` 是占上一步工作階段數的比例，`medianMs` 是從上一步到這一步所需時間的中位數。不適用時皆為 `null`。如果欄位不是文字欄位，或該類型沒有此欄位，請求會傳回 `400`。

### 路徑

| 參數 | 類型 | 行為 |
|---|---|---|
| `from`、`to`、`filters` | | 與 `funnel` 相同。讀取的是檢視資料列。 |
| `anchor` | string | 路徑的起始頁面；回溯時則是終點頁面。省略時，使用每個工作階段的第一個頁面；回溯時使用最後一個頁面。 |
| `backward` | boolean | 追蹤錨點之前的頁面。預設 `false`。 |
| `depth` | integer | 錨點之後（或之前）的頁數，1 到 6 頁，預設 3。 |
| `by` | string | 用來區分頁面的欄位：`view.url_path_group`（預設）、`view.url_path` 或 `view.name`。 |

```json
{
  "columns": 3,
  "sessions": 9,
  "backward": false,
  "nodes": [
    { "column": 0, "page": "/products", "sessions": 2, "ends": 0 },
    { "column": 1, "page": "/cart", "sessions": 2, "ends": 0 },
    { "column": 2, "page": "/checkout", "sessions": 1, "ends": 1 }
  ],
  "links": [
    { "column": 0, "source": "/products", "target": "/cart", "sessions": 2 },
    { "column": 1, "source": "/cart", "target": "/checkout", "sessions": 1 }
  ],
  "from": 1779400000000000,
  "to": 1780000000000000
}
```

頁面分布在 `columns` 的各欄中，欄數比 `depth` 多一欄。錨點頁面位於第 0 欄（回溯時位於最後一欄）。每個節點代表某一欄中的一個頁面，包含該頁面的 `sessions`，以及未再前往下一頁的工作階段數 `ends`（回溯時則表示從這裡開始的工作階段數）。每條連線從 `column` 欄的一個頁面連到下一欄的一個頁面，並包含經過這條路徑的工作階段數。下一欄代表時間上較晚的一欄，回溯時也一樣。依開啟順序取得頁面，連續開啟同一頁面只算一次。每欄列出工作階段數最多的 8 個頁面，其餘歸入 `__other__`。`sessions` 是包含錨點頁面的工作階段數。

### 留存

| 參數 | 類型 | 行為 |
|---|---|---|
| `from`、`to`、`filters` | | 與 `funnel` 相同。讀取的是工作階段資料列。省略 `from` 和 `to` 時，預設涵蓋足以檢視同類群組的歷史範圍：從現在往前推 `periods` 的兩倍個週期，且至少 14 天（`week` 時至少 8 週）。 |
| `period` | `day` 或 `week` | UTC 的一天，或從週一開始的 UTC 一週。預設 `day`。 |
| `periods` | integer | 第一個週期之後的週期數，1 到 30。預設 7。 |

```json
{
  "period": "day",
  "periods": 3,
  "cohorts": [
    { "startTime": 1779408000000000, "users": 1, "returned": [1, 0, null] },
    { "startTime": 1779494400000000, "users": 6, "returned": [0, null, null] }
  ],
  "from": 1779408000000000,
  "to": 1779753600000000
}
```

同類群組包含在查詢時間範圍內，於 `startTime` 起算的週期中首次出現的使用者。以工作階段的 `usr.id` 識別使用者，若沒有此值，則使用 `usr.anonymous_id`。`returned` 提供後續每個週期中再次出現的群組成員數；截至 `to` 尚未結束的週期為 `null`。

## 熱圖

`/api/v1/rum/heatmaps` 下的端點提供 [RUM 熱圖](/zh-Hant/rum/heatmaps)的數值。這些端點接受以微秒為單位的 `from` 和 `to`，以及 `filters`，通常會依 `application.id`、`view.url_path_group` 和視窗大小（`display.viewport.width`）篩選。使用 `GET` 時，在查詢參數中以 JSON 傳入清單。`clicks` 和 `scroll` 也接受 `limit`，並需要 `rum.analytics.read`。這些端點依實際儲存的資料列計算，不使用估算值。

```json
{
  "clicks": 148,
  "elements": [
    {
      "element": "body>main>button:nth-of-type(2)",
      "name": "Pay now",
      "selector": "button.pay",
      "clicks": 92,
      "sessions": 60,
      "frustrated": 4,
      "pageX": 640.5,
      "pageY": 720.0,
      "cells": [[5, 4, 31], [6, 4, 28]]
    }
  ],
  "from": 1779400000000000,
  "to": 1780000000000000
}
```

`clicks` 傳回點擊次數最多的元素，1 到 300 個，預設 100 個。`element` 是元素在頁面中的位置。`pageX`、`pageY` 是該元素的點擊在頁面上的平均位置。`cells` 將元素劃分為 10×10 的格子，每項以 `[欄, 列, 點擊次數]` 表示。

```json
{
  "views": 310,
  "pageHeight": 4200,
  "medianDepth": 1800,
  "bands": [{ "depth": 800, "reached": 1.0 }, { "depth": 900, "reached": 0.97 }],
  "from": 1779400000000000,
  "to": 1780000000000000
}
```

`scroll` 傳回有捲動深度資料的檢視數、頁面高度，以及半數檢視到達的深度。每 100 像素為一級：`reached` 是到達該深度的檢視比例，深度越深，比例只會降低或維持不變。

`snapshot` 接受 `viewId`（其中一個候選檢視），需要 `rum.replay.read`。回應包含 `candidates`：此頁面最多 20 個可重播的檢視，依時間由新到舊排序，每個檢視包含 `sessionId`、`viewId`、`atTime` 和視窗的 `width`、`height`；以及 `snapshot`：包含所繪製檢視的相同欄位，以及將頁面呈現至 `atTime` 所需的 rrweb `events`，從該時間點之前最後一個完整快照開始。如果沒有錄製到開啟此頁面的工作階段，`snapshot` 為 `null`。

## 播放清單

[播放清單](/zh-Hant/rum/playlists)是某個應用程式的一組工作階段的具名清單，每個工作階段都附有一個適合開始觀看的時間點。

```json
{
  "id": "2xT9bQ1kLw5nVf8cZ0aR7mHpJd3",
  "application": "checkout-web",
  "name": "Checkout failures",
  "description": "Sessions that ended at the checkout with an error.",
  "createdBy": "<user-id>",
  "createdAt": 1790000000000000,
  "updatedAt": 1790000100000000,
  "sessionCount": 2,
  "sessions": [
    { "sessionId": "3f6c9a52-1b7e-4d08-a5c3-90e2d41f7b68", "atTime": 1790000005000000, "addedBy": "<user-id>", "addedAt": 1790000000000000 },
    { "sessionId": "9d41e7b0-62fa-4c3d-8e15-b7a09c52d3f4", "atTime": null, "addedBy": "<user-id>", "addedAt": 1790000100000000 }
  ]
}
```

`GET /api/v1/rum/playlists` 傳回不含 `sessions` 的播放清單，最近修改的排在前面，可用 `application` 將範圍縮小到單一應用程式。讀取需要 `rum.playlists.read`，平台呼叫端可使用 `sys.telemetry.read`。其餘請求會修改播放清單，需要 `rum.playlists.read`；除了傳回 `{ "deleted": true }` 的 `DELETE`，其餘都會傳回包含工作階段的播放清單。

| 請求 | 請求主體 | 規則 |
|---|---|---|
| `POST /rum/playlists` | `application`、`name`，以及選填的 `description` 和 `sessions` | 應用程式必須存在（`404`）。名稱長度為 1 到 128 個字元，且同一應用程式內不能有同名的播放清單，不區分大小寫（`409`）。說明不得超過 1000 個字元。 |
| `PATCH /rum/playlists/{id}` | `name` 和 `description`，兩者皆可選填 | 省略的欄位保留原值。無法變更應用程式。 |
| `POST /rum/playlists/{id}/sessions` | `sessions` | 重新加入的工作階段會採用新指定的 `atTime`，位置不變。每份播放清單最多可包含 500 個工作階段（`400`）。 |

請求中的工作階段格式為 `{ "sessionId": "...", "atTime": 1790000005000000 }`：ID 長度為 1 到 128 個字元。指定 `atTime` 時，會從該時間點開啟工作階段，以自 Unix 紀元起算的微秒數表示；省略時則從頭開啟。播放清單儲存的是 ID，而不是工作階段本身，因此不會檢查工作階段是否存在。即使工作階段的資料列已因保留期限屆滿而刪除，仍會留在清單中。`GET /api/v1/rum/sessions/{id}/playlists` 傳回包含指定工作階段的播放清單（不含各清單的工作階段）。

## 讀取一筆資料列或一個工作階段

`GET /api/v1/rum/{type}/{id}` 傳回一筆資料列及其所有欄位，找不到時傳回 `404`。可用 `from` 和 `to` 縮小查詢範圍，省略時查詢最近 30 天。`{id}` 是該類型的 `idField` 值。

`GET /api/v1/rum/sessions/{id}/timeline` 的回應：

| 欄位 | 內容 |
|---|---|
| `session` | 工作階段資料列；尚未產生工作階段資料列時為 `null`。 |
| `items` | 屬於該工作階段的其他類型資料列，最早的排在前面。每個項目都有 `type`：`view`、`action`、`error`、`resource`、`long_task`、`vital` 或 `log`。 |
| `truncated` | 資料列數量超過時間軸容量的類型。 |

`GET /api/v1/rum/sessions/{id}/related-traces` 列出工作階段的後端追蹤：優先列出工作階段請求所帶 ID 對應的追蹤（`relation: direct`）；若沒有這類追蹤，則列出工作階段期間執行的追蹤（`relation: time-correlated`）。每筆追蹤都有 `trace_id`、`service`、`spanCount`、`durationMs` 和 `startedAt`，回應也包含 `primaryService`。`GET /api/v1/rum/traces/{traceId}/session` 則反向查詢，傳回工作階段或 `null`。

## 留言

```http
POST /api/v1/rum/sessions/{id}/comments
```

```json
{ "application": "checkout-web", "atTime": 1790000005000000, "body": "这里按钮没有反应。" }
```

`atTime` 是工作階段中的時間點（自 Unix 紀元起算的微秒數），`body` 長度為 1 到 2,000 個字元。每個工作階段最多可有 500 則留言。`GET` 傳回 `{ "comments": [...] }`，依時間由早到晚排序，需要 `rum.replay.read`。

```json
{
  "id": "2xT9bQ1kLw5nVf8cZ0aR7mHpJd3",
  "application": "checkout-web",
  "sessionId": "3f6c9a52-1b7e-4d08-a5c3-90e2d41f7b68",
  "atTime": 1790000005000000,
  "body": "这里按钮没有反应。",
  "authorId": "<user-id>",
  "authorName": "Ada",
  "createdAt": 1790000010000000,
  "updatedAt": 1790000010000000,
  "editable": true
}
```

`POST` 需要 `rum.replay.comments.write`。`PATCH` 接受 `body`；使用 `PATCH` 或 `DELETE` 處理自己發表的留言時，需要上述權限，處理其他使用者的留言時則需要 `rum.replay.comments.manage`。`editable` 表示讀取者是否可修改該留言。`DELETE` 傳回 `{ "deleted": true }`。

## 摘要

`GET /api/v1/rum/sessions/{id}/summary` 傳回 `{ "summary": ... }`，其中包含以讀取者語言儲存的摘要，若無則為 `null`，需要 `rum.replay.read`。`POST` 呼叫模型產生摘要，需要 `rum.replay.summaries.generate`。若已有摘要，則直接傳回，不呼叫模型；傳入 `{ "regenerate": true }` 時會呼叫模型，但工作階段未變更時不會呼叫。

```json
{
  "summary": {
    "sessionId": "3f6c9a52-1b7e-4d08-a5c3-90e2d41f7b68",
    "language": "zh-cn",
    "summary": "用户加好购物车后无法付款：支付请求连续失败三次。",
    "chapters": [{ "atTime": 1790000005000000, "title": "加购物车", "summary": "加了两件商品。" }],
    "model": "<model>",
    "promptTokens": 1820,
    "completionTokens": 240,
    "generatedAt": 1790000020000000
  }
}
```

呼叫會計入 Mole Agent 的每日預算，用量來源為 `replay_summary`。預算用完時傳回 `429`；若組織沒有已啟用且已設定金鑰的模型服務，或工作階段沒有可供摘要的內容，則傳回 `400`。

## Issue

相似的錯誤會歸併成 [issue](/zh-Hant/rum/errors)，每筆錯誤資料列都在 `error.issue_id` 中記錄所屬 issue 的 ID。Issue 的統計數字根據查詢時間範圍內的錯誤計算，狀態和歷史記錄則另行儲存。所有時間都以自 Unix 紀元起算的微秒數表示。

```http
GET /api/v1/rum/issues?application=checkout-web&status=unresolved&sort=sessions&limit=50
```

| 參數 | 類型 | 行為 |
|---|---|---|
| `application` | string | 必填。 |
| `env`、`source` | string | 只計入指定環境中的錯誤，或由指定來源（`browser`、`flutter` 等）傳送的錯誤。 |
| `filters` | list | 對納入計算的錯誤套用更多條件，與 `search` 相同。 |
| `from`、`to` | integer | 與 `search` 相同。 |
| `status` | string | `unresolved`（預設：待處理、調查中和復發）、`all`，或 `open`、`investigating`、`regressed`、`resolved`、`ignored` 其中之一。 |
| `assignee`、`team` | string | 使用者 ID 或團隊 ID；`none` 表示未指派的 issue。 |
| `search` | string | 在 issue 的類型、訊息或位置中搜尋的字詞，不區分大小寫。 |
| `fresh` | boolean | 只列出在範圍內首次出現或復發的 issue。 |
| `sort` | string | `sessions`（預設）、`users`、`occurrences`、`lastSeen`、`firstSeen` 或 `status`。 |
| `order` | `asc` 或 `desc` | 省略時，除 `status` 外皆採遞減排序。 |
| `limit` | integer | 1 到 100，預設為 50。 |

```json
{
  "issues": [
    {
      "id": "3f9c2a71e0b4c8d1",
      "applicationId": "checkout-web",
      "status": "regressed",
      "assigneeId": "<user-id>",
      "teamId": null,
      "overflow": false,
      "source": "source",
      "errorType": "ChunkLoadError",
      "message": "Loading chunk 482 failed.",
      "location": "src/router/lazy.ts:34 · loadChunk",
      "firstSeenAt": 1789300000000000,
      "lastSeenAt": 1790000000000000,
      "firstVersion": "2.2.0",
      "lastVersion": "2.4.1",
      "resolvedAt": 1789600000000000,
      "resolvedVersion": "2.3.0",
      "resolvedBy": "<user-id>",
      "regressedAt": 1789900000000000,
      "regressedVersion": "2.4.1",
      "regressedEnvironment": "production",
      "updatedBy": null,
      "updatedAt": 1789900000000000,
      "sessions": 612,
      "users": 498,
      "occurrences": 1530,
      "trend": [3, 5, 4, 9, 40, 120]
    }
  ],
  "total": 8
}
```

`regressedEnvironment` 是造成 issue 復發的那筆錯誤所在的環境；若該筆錯誤未記錄環境，則為 `null`。Issue 屬於整個應用程式，不受錯誤所在環境影響。伺服器端也會記錄各環境首次出現該 issue 的時間，[警示規則](/zh-Hant/rum/alerts#縮小規則範圍)會據此計算各環境的新問題數量。

清單會先依 `sort` 讀取工作階段數、使用者數或出現次數最多的 250 個 issue，再用 `status`、`assignee`、`team`、`search` 和 `fresh` 進一步篩選。`total` 是篩選後剩餘的 issue 數量，在套用 `limit` 截斷清單之前計算。`trend` 將時間範圍等分為最多 12 段，依時間由早到晚列出各段的出現次數。`overflow` 標示一個特殊的 issue，用來統計應用程式超出[每小時可新增的 issue 數量](/zh-Hant/rum/errors#每小時新增的-issue)後發生的錯誤。計數耗時過長或系統忙碌時，會傳回空的 issue 清單，並將 `unavailable` 設為 `time_budget` 或 `busy`。

`GET /api/v1/rum/issues/{id}` 傳回與清單中格式相同的 issue（不含 `trend`），其中 `sessions`、`users` 和 `occurrences` 依 `from` 和 `to` 計算，另有兩個欄位：

| 欄位 | 內容 |
|---|---|
| `samples` | 最近三個遇到該 issue 的工作階段，由新到舊排列：`timestamp`、`sessionId`、`userId`、`anonymousId`、`page`、`browser`、`system`、`version`、`hasReplay` 和 `retained`。若錯誤所屬的工作階段未保留，`retained` 為 `false`，且沒有可開啟的工作階段。 |
| `stack` | 最近一筆包含堆疊框架的錯誤所對應的堆疊；若沒有包含框架的錯誤，則使用最近一筆錯誤，且 `frames` 為空；若範圍內沒有該 issue 的錯誤，則為 `null`。包含 `message`、`text`、`frames`、`symbolication`、`handling`、`isCrash` 和 `category`。框架包含 `raw`（由 SDK 傳送）、`restored`（從偵錯產物還原，若無則為 `null`）和 `inApp`。若曾嘗試還原，`symbolication` 為 `completed`、`partial` 或 `missing`。 |

Issue 不存在時傳回 `404`。

`PATCH /api/v1/rum/issues/{id}` 接受 `status`、`assigneeId` 和 `teamId` 中的任意欄位，並傳回修改後的 issue。

```json
{ "status": "resolved", "assigneeId": "<user-id>", "teamId": null }
```

`status` 可設為 `open`、`investigating`、`resolved` 或 `ignored`。已解決的 issue 在較新的版本中再次出現時，規則會將狀態設為 `regressed`；嘗試直接設定此狀態會傳回 `400`。`assigneeId` 必須是組織成員的 ID，`teamId` 必須是組織內團隊的 ID；`null` 或空字串表示取消指派負責人或團隊。省略的欄位保留原值。標記為已解決時，會記錄 `resolvedAt` 和 `resolvedBy`，並將應用程式當時的最新版本記為 `resolvedVersion`；任何新狀態都會結束先前的已解決或復發記錄。未指定任何要修改的欄位時，請求會傳回 `400`；重複設定現有值時，會傳回 `200`，不做任何變更。每次修改都會以 `rum.issue.update` 寫入稽核記錄。

## 預覽警示規則

```http
POST /api/v1/rum/alerts/preview
```

使用與評估規則相同的程式碼，逐一讀取 [RUM 指標的警示規則](/zh-Hant/rum/alerts) 在近期各時間視窗會看到的結果。需要 `rum.events.read`。

```json
{
  "query": { "applicationId": "checkout-web", "environment": "production", "page": "/checkout", "metric": "lcp_p75" },
  "periodSecs": 3600
}
```

| 欄位 | 類型 | 行為 |
|---|---|---|
| `query` | object | 必填。指標包含 `applicationId` 和 `metric`，以及指定的 `environment`、`page`、`version` 和 `minSamples`。若指標不支援依頁面或版本縮小範圍，指定 `page` 或 `version` 時會遭拒絕；計數指標指定 `minSamples` 時也會遭拒絕。`custom_vital` 和 `custom_timing` 還接受必填的 `customName` 和 `statistic`。`query` 接受必填的 `search`，包含 `type`、輸入的 `statement`、解析出的 `filters` 和 `freeText`，以及 `measure`（`fn` 和 `field`）。請參閱[建立規則](/zh-Hant/api/alerting/create-rule#rum-規則)。 |
| `periodSecs` | integer | 必填。評估規則使用的時間視窗，範圍為 60 到 21,600。每個資料點代表一個時間視窗。 |
| `from`、`to` | integer | 以自 Unix 紀元起算的微秒數表示範圍，按完整時間視窗讀取。`to` 預設為目前時間。`from` 預設為 `to` 往前 6 小時，但範圍不得少於 12 個時間視窗、不得多於 72 個時間視窗，也不得超過一天。每個範圍最多可包含 360 個時間視窗。 |

```json
{
  "metric": "lcp_p75",
  "unit": "milliseconds",
  "minSamples": 50,
  "periodSecs": 3600,
  "from": 1789956800000000,
  "to": 1790000000000000,
  "points": [
    { "at": 1789956800000000, "value": null, "samples": null },
    { "at": 1789960400000000, "value": 2480, "samples": 612 }
  ],
  "current": { "at": 1789996400000000, "value": 2310, "samples": 540 }
}
```

`unit` 為 `count`、`percent`、`milliseconds`、`score`、`bytes` 或 `none`。資料點的 `at` 是時間視窗的起點，`value` 是指標值，`samples` 是計算指標所用的資料列數；時間視窗內的資料列數少於 `minSamples` 時，兩者皆為 `null`。`current` 是最後一個資料點，代表截至 `to` 的時間視窗。計數耗時過長或系統忙碌時，會傳回空的 `points`，並將 `unavailable` 設為 `time_budget` 或 `busy`。應用程式不存在時傳回 `404`，規則與指標不相符時傳回 `400`。

## 錯誤

| 狀態 | 原因 |
|---|---|
| `400` | 參數、篩選條件、欄位或游標與請求不符。 |
| `401`、`403` | 缺少權杖、權杖無效，或缺少端點要求的權限。 |
| `404` | 資料列、工作階段或應用程式不存在。 |
| `409` | 已有相同識別碼或名稱的應用程式。 |
| `413` | 請求超出 [`events`](/zh-Hant/rum/events#傳送事件) 的限制。 |
