APM API 提供從 trace span 衍生的組織範圍彙總。所有端點都使用 `/api/v1/apm` 前綴，並要求 Bearer Token。

```http
Authorization: Bearer <token>
```

組織工作區需要所讀取內容的讀取權限：`apm.services.read`、`apm.errors.read`、`apm.error_rules.read`、`apm.definitions.read`、`apm.slos.read`、`apm.deployments.read` 或 `apm.settings.read`。平台呼叫端在受保護的 `_sys` 範圍可以使用 `sys.telemetry.read`。寫入呼叫各自寫明需要什麼。上報部署需要 `apm.deploy`。

## 端點

| 方法與路徑 | 回應內容 |
|---|---|
| `GET /api/v1/apm/overview` | 所有服務的 RED 彙總與趨勢、服務健康及其趨勢、排行、部署、環境、埋點缺失，以及 Top 交易、相依性和錯誤。 |
| `GET /api/v1/apm/insights` | 與上一時段、上週同時段相比有變化的指標，比上一個版本更差的版本，可節省時間的地方，以及每則發現附近的變更。 |
| `GET /api/v1/apm/services` | 分頁服務目錄，包括埋點資訊、版本、健康、RED 指標與 Trace 篩選條件。 |
| `GET /api/v1/apm/services/{service}` | 服務彙總、趨勢、交易、相依性、錯誤與版本。 |
| `GET /api/v1/apm/services/{service}/instances` | 某個環境中服務的執行個體，含版本、資源屬性和每個執行個體處理的請求情況。 |
| `GET /api/v1/apm/services/{service}/coverage` | 在 `to` 之前的一天內，服務的日誌、指標、Profiles 和瀏覽器工作階段是否已接入 MoleSignal。 |
| `GET /api/v1/apm/correlation` | 目前範圍內每個服務與日誌、指標、Trace 和變更的關聯情況，以及日誌和指標裡 APM 無法辨識的服務名稱。 |
| `GET /api/v1/apm/transactions` | 分頁交易 RED 指標與總耗時排名。 |
| `GET /api/v1/apm/transactions/{transaction}` | 交易趨勢、相關錯誤、版本與 Trace 篩選條件。 |
| `GET /api/v1/apm/dependencies` | 分頁呼叫端/相依性 RED 指標與總耗時排名。 |
| `GET /api/v1/apm/map` | 一個環境和命名空間的服務地圖：服務、它們呼叫的物件、Topic，以及相互之間的呼叫。 |
| `GET /api/v1/apm/map/edge` | 地圖上的一條呼叫：它的趨勢、沿著它存取的內容，以及被呼叫服務的錯誤。 |
| `GET /api/v1/apm/blast-radius` | 服務沿地圖影響到的範圍：呼叫它的和它呼叫的，逐層列出。 |
| `GET /api/v1/apm/errors` | 分頁且已去識別化的後端錯誤群組，以及所列群組的發生分佈。 |
| `GET /api/v1/apm/errors/{fingerprint}` | 錯誤趨勢、相關交易與版本、群組發生分佈、代表性堆疊和有界樣本。 |
| `GET /api/v1/apm/versions/compare` | 基準和候選 RED 指標、差異、資料充足狀態與退步項目。 |
| `GET /api/v1/apm/health` | 租用戶投影狀態、運作健康、邊界與缺口。 |
| `GET /api/v1/apm/service-definitions` | 組織的全部服務定義。 |
| `PUT /api/v1/apm/service-definitions/{service}?namespace=` | 建立或取代服務定義。需要 `apm.definitions.manage`。 |
| `DELETE /api/v1/apm/service-definitions/{service}?namespace=` | 刪除服務定義。需要 `apm.definitions.manage`。 |
| `POST /api/v1/apm/service-definitions/{service}/key-transactions?namespace=` | 將端點標示為服務的關鍵交易，或取消標示。需要 `apm.definitions.manage`。 |
| `PUT /api/v1/apm/errors/{fingerprint}/issue` | 設定錯誤群組的狀態、團隊和指派對象。需要 `apm.errors.manage`。 |
| `GET /api/v1/apm/error-rules` | 組織的錯誤彙總規則，依比對順序排列。 |
| `POST /api/v1/apm/error-rules` | 建立彙總規則，排在現有規則之後。需要 `apm.error_rules.manage`。 |
| `PUT /api/v1/apm/error-rules/{id}` | 取代一筆彙總規則。需要 `apm.error_rules.manage`。 |
| `DELETE /api/v1/apm/error-rules/{id}` | 刪除一筆彙總規則。需要 `apm.error_rules.manage`。 |
| `PUT /api/v1/apm/error-rules/order` | 設定規則的比對順序。需要 `apm.error_rules.manage`。 |
| `GET /api/v1/apm/slos` | 所有服務等級目標及其狀態、達成率、剩餘錯誤預算和燃燒率。 |
| `GET /api/v1/apm/slos/{id}` | 單一服務等級目標的狀態，以及視窗內每天的情況。 |
| `POST /api/v1/apm/slos` | 建立服務等級目標。需要 `apm.slos.manage`。 |
| `PUT /api/v1/apm/slos/{id}` | 取代服務等級目標。需要 `apm.slos.manage`。 |
| `DELETE /api/v1/apm/slos/{id}` | 刪除服務等級目標。需要 `apm.slos.delete`。 |
| `POST /api/v1/apm/deployments` | 上報一次部署。需要 `apm.deploy`。 |
| `GET /api/v1/apm/settings` | 組織的 APM 設定，尚未儲存過時傳回預設值。 |
| `PUT /api/v1/apm/settings` | 取代組織的 APM 設定。需要 `apm.settings.manage`。 |

路徑參數必須經過 URL 編碼。請使用列表回應傳回的確切 `transaction` 名稱或錯誤 `fingerprint`。

## 通用查詢參數

| 參數 | 類型 | 行為 |
|---|---|---|
| `from` | integer | Unix 紀元以來的微秒級開始時間。預設是 `to` 之前 24 小時。 |
| `to` | integer | Unix 紀元以來的微秒級結束時間。預設為目前時間。 |
| `namespace` | string | 精確比對服務命名空間。 |
| `service` | string | 精確比對服務名稱。服務詳情路徑中的值會覆寫此參數。 |
| `environment` | string | 精確比對部署環境。 |
| `version` | string | 精確比對服務版本。 |
| `resolution` | enum | `auto`、`minute` 或 `hour`。`auto` 會依範圍選擇可用解析度。 |
| `sort` | string | 端點支援的排序欄位。 |
| `direction` | enum | `asc` 或 `desc`，預設為 `desc`。 |
| `limit` | integer | 每頁筆數 1 到 200，預設為 50。 |
| `cursor` | string | 上一個列表回應傳回的不透明游標。 |
| `status` | enum | 僅 `/errors`：`all`（預設）、`unresolved`（待處理、調查中，以及已解決後再次出現的群組）、`investigating`、`resolved` 或 `ignored`。 |

篩選值不能為空，且不能超過 192 位元組。查詢範圍不能超過設定的最大值，預設是 30 天（`[apm].max_query_range_days`）。

### 排序欄位

| 端點 | 支援的 `sort` 值 | 預設值 |
|---|---|---|
| `/services` | `requestCount`、`errorRate`、`p95`、`name` | `requestCount` |
| `/transactions` | `requestCount`、`errorRate`、`p95`、`total_time` | `requestCount` |
| `/dependencies` | `requestCount`、`errorRate`、`p95`、`total_time` | `total_time` |
| `/errors` | `occurrenceCount`、`errorRate`、`lastSeen` | `occurrenceCount` |

`/overview` 接受相同的篩選條件與解析度，但不分頁。詳情、版本比較和健康端點也不會傳回分頁列表。

## 查詢概覽

<RequestExample>
```bash cURL
NOW=$(date +%s)000000
curl --get 'http://localhost:5080/api/v1/apm/overview' \
  --header "Authorization: Bearer $MS_TOKEN" \
  --data-urlencode "from=$((NOW-86400000000))" \
  --data-urlencode "to=$NOW" \
  --data-urlencode 'environment=production' \
  --data-urlencode 'resolution=auto'
```
</RequestExample>

回應包含 `red`、`trend`、`serviceHealth`、`services`、`topTransactions`、`topDependencies`、`topErrors` 和 `recentVersions`，以及通用 `meta` 物件，另外還有：

| 欄位 | 說明 |
|---|---|
| `serviceCount`、`activeServiceCount` | 時間範圍內出現過的服務數，以及其中有請求的服務數。 |
| `healthTrend` | 每個時間段裡各狀態的服務數：時間範圍最多分成 48 段，每段不短於一個時間桶。某段內沒有請求的服務在該段計為 `noTraffic`。 |
| `rankings` | `slowest`（依 p95）、`mostErrors`（依錯誤率）和 `busiest`（依請求數），各 5 個服務。前兩項只列出請求數不少於 20 的服務。 |
| `deployments` | 時間範圍內首次出現的版本，最新的在前，最多 20 個。每個版本帶有 `red` 和 `verdict`，含義同[服務的版本](#讀取服務的版本)。 |
| `environments`、`availableEnvironments` | 目前檢視內每個環境的服務數和請求數，以及不受 `environment` 篩選影響的全部環境。 |
| `instrumentation` | 依語言和 SDK 統計的服務數，以及未上報 `deployment.environment`、`service.version` 或 `service.instance.id` 的服務數。 |

## 讀取洞察

`GET /api/v1/apm/insights` 接受通用的時間範圍和篩選參數，傳回 `meta` 以及：

| 欄位 | 說明 |
|---|---|
| `now`、`previous`、`lastWeek` | 目前檢視內的服務在時間範圍內、之前同樣長的一段時間內，以及上週同時段內的資料：`requestCount`、`throughput`（每秒請求數）、`errorRate`、`p95Time` 和 `apdex`。沒有請求的時間段會省略。 |
| `insights` | 最多 30 則發現，最需要關注的在前。 |

每則發現包含：

| 欄位 | 說明 |
|---|---|
| `kind` | `anomaly`、`regression`、`slow_dependency`、`repeated_call`、`slowQuery`、`hot_endpoint` 或 `log_errors`。 |
| `severity` | `critical`、`warning`，建議為 `info`。 |
| `service` | `namespace`、`name` 和 `environment`。 |
| `transaction`、`dependency` | 熱點端點的端點；瓶頸、重複呼叫或慢查詢對應的相依性。 |
| `metric` | 變化或變差的指標：`errorRate`、`p95` 或 `throughput`。 |
| `value` | 現在的值：錯誤率為比值，P95 單位為微秒，輸送量為每秒請求數。瓶頸和熱點端點為耗時占比，重複呼叫為每個請求的呼叫次數，慢查詢為以微秒計的 P95，`log_errors` 為每分鐘錯誤等級日誌行數（`metric` 為 `log_errors`）。 |
| `previous`、`lastWeek` | 同一指標在上一時段和上週同時段的值；版本變差時為上一個版本的值。 |
| `since` | 突變開始的時間，或變差版本首次出現的時間。 |
| `version`、`previousVersion` | 變差的版本和它之前的版本。 |
| `calls`、`p95Time` | 建議所依據的呼叫數或請求數，以及它們的 P95。 |
| `changes` | `since` 附近的變更，最近的在前：`kind`、`source`（`reported` 或 `observed`）、`service`、`version`、`status`、`at`、`downstream`（當變更屬於突變服務所呼叫的服務時為 `true`）、`commit` 和 `description`。 |

判斷條件見[洞察與調查](/zh-Hant/apm/insights#洞察的類型)。

## 讀取 RED 指標

每個彙總都帶有 `red` 物件，包含範圍內的請求、錯誤和耗時資料。

| 欄位 | 說明 |
|---|---|
| `requestCount`、`errorCount`、`errorRate` | 請求數、失敗請求數，以及兩者的比值（0 到 1）。 |
| `durationSum`、`durationAverage` | 總耗時與平均耗時，單位為微秒。沒有請求時平均值為 `null`。 |
| `p50Time`、`p90Time`、`p95Time`、`p99Time` | 延遲百分位，單位為微秒，在排名所在的直方圖桶內以插值讀出。預設分桶下與精確耗時的誤差約 ±4%。沒有請求時為 `null`。 |
| `apdex` | 不超過閾值 T 的請求加上不超過 4T 的請求的一半，除以全部請求，取值 0 到 1。T 取自服務的 `apdexThreshold`，未設定時為 500 ms；概覽中所有服務合併在一起的指標依 500 ms 計算。出錯的請求一律不視為滿意。沒有請求時為 `null`。 |
| `latencyPartial` | 部分時間桶使用了無法辨識的延遲分桶時為 `true`。以早期分桶（`[apm.histogram].schema_version`）寫入的時間桶會被換算後計入。百分位會排除無法讀取的時間桶，而計數、總和與平均值仍然包含它們。 |
| `timeoutCount`、`retryCount` | 逾時的請求（錯誤類型為逾時、gRPC `DEADLINE_EXCEEDED`、HTTP 408 或 504）和重送的請求（`http.request.resend_count` 大於 0）。為 0 時省略。 |
| `statusCodes` | 依狀態碼統計的回應，鍵為 `http:<状态码>`（100 到 599）或 `grpc:<状态码>`（0 到 16）。每個分桶最多記錄 24 個狀態碼，更多的計入 `http:other` 或 `grpc:other`。沒有統計到狀態碼時省略，例如開始統計之前寫入的彙總。 |
| `exemplars` | 範圍內最多 8 個範例 Span，耗時最長的在前。Span 在[尾部採樣](/zh-Hant/configuration#追蹤擷取與尾端取樣)對其 Trace 做出決定之前就已投影，所以 `traceAvailable` 通常為 `false`；若要得知 Trace 是否保留，請查詢該 Trace。彙總結果仍然有效。 |

服務摘要和交易摘要帶有 `apdexThreshold`，即計算 Apdex 時使用的 T。服務摘要還帶有 `health` 和 `healthReasons`：每個超過閾值的指標，含 `metric`（`errorRate` 或 `p95`）、`level`、`value` 和 `threshold`。服務摘要還帶有 `sparkline`（每個時間桶的請求數、錯誤數和 p95），以及 `currentVersion` 和 `currentVersionSince`（最近出現的版本及其首次出現時間）。服務或交易詳情帶有 `latencyDistribution`：包含請求的直方圖桶，每個為 `lowerTime`、`upperTime` 和 `count`，並縮小至最快和最慢的請求。

## 維護服務定義

服務定義記錄服務由誰負責、有多重要。它以 `namespace` 和服務名稱儲存，適用於所有環境，且可在服務上報前存在。

```http
PUT /api/v1/apm/service-definitions/checkout?namespace=shop
Content-Type: application/json

{"description": "处理下单与支付。", "teamId": "<team id>", "ownerId": "<user id>", "tier": "p0", "lifecycle": "production", "repositoryUrl": "https://github.com/acme/checkout", "tags": {"domain": "orders", "pci": ""}, "apdexThreshold": 300000, "aliases": ["order_service", "订单中心"], "dataSources": {"logs": [{"stream": "default", "filter": "service_name = 'order_service'"}], "metrics": [{"selector": "{service=\"checkout\"}"}], "dashboards": ["<dashboard id>"], "links": [{"name": "Runbook", "url": "https://wiki.example.com/checkout"}]}, "archived": false}
```

| 欄位 | 說明 |
|---|---|
| `description` | 最多 2,000 個字元。 |
| `teamId` | 組織內的團隊，或 `null`。刪除團隊後會被清空。 |
| `ownerId` | 組織成員，或 `null`。 |
| `tier` | `p0`（最重要）到 `p5`，或 `null`。 |
| `lifecycle` | `production`、`staging`、`experimental`、`deprecated` 或 `null`。 |
| `repositoryUrl` | 不含空格的 `http`、`https`、`ssh`、`git` 或 `git+ssh` 位址，或 `user@host:path` 形式的位址，最多 2,048 個字元，或 `null`。密碼會儲存為 `****`，http(s) 位址中的使用者部分也會儲存為 `****`。服務未上報儲存庫時顯示。 |
| `tags` | 最多 32 個標籤，格式為 `{ "key": "value" }`。key 為 1 到 64 個小寫字母、數字和 `_ . - /`；value 最多 128 個字元，兩端不能有空格，只有 key 時為空字串。 |
| `apdexThreshold` | 服務的 Apdex 閾值 T，大於 0 且不超過 60,000,000（一分鐘），或 `null` 表示 500 ms。 |
| `aliases` | 日誌、指標和其他系統對這個服務的稱呼，最多 20 個，每個 1 到 128 個字元，兩端不能有空格。比較時不區分大小寫：不能重複，不能是服務自己的名稱，也不能是組織內另一個服務的名稱或稱呼。省略時，已儲存的定義會保留原有稱呼。 |
| `dataSources` | 服務的資料入口：`logs`（`stream`，以及可選的 `filter`，最多 2,000 個字元的布林 SQL 運算式）、`metrics`（`selector`，PromQL 選擇器，例如 `{service="checkout"}`）、`dashboards`（儀表板 ID）和 `links`（`name` 與 `http` 或 `https` 的 `url`），每類最多 10 筆。省略時，已儲存的定義會保留原有資料入口。 |
| `archived` | 為 `true` 時，服務不會出現在服務目錄的預設檢視中。省略時，已儲存的定義會維持原狀態。 |

儲存不會改動定義的 `keyTransactions`，關鍵事務每次只增減一個。回應是儲存後的定義，含 `namespace`、`name`、`keyTransactions`、`updatedBy` 和 `updatedAt`。`DELETE` 傳回 `204`；服務沒有定義時傳回 `404`。

### 標記關鍵事務

```http
POST /api/v1/apm/service-definitions/checkout/key-transactions?namespace=shop
Content-Type: application/json

{"transaction": {"name": "POST /orders", "kind": "http"}, "key": true}
```

`key: true` 會將端點加入 `keyTransactions`，`false` 則將其移除；狀態已經如此時不會做任何改動。服務尚未有定義時會自動建立。每個服務最多 50 個關鍵事務，溢位列 `__other__` 不能標記為關鍵事務。回應是改動後的定義。

## 讀取服務的關聯品質

`GET /api/v1/apm/correlation` 接受一般時間範圍與篩選參數（`from`、`to`、`namespace`、`environment`、`service`），傳回目前範圍內每個服務與日誌、指標、Trace 和變更的關聯情況。服務依整個時間範圍讀取，日誌和指標看 `to` 之前一小時，變更看 `to` 之前一週。僅從資料流讀取計數和名稱，不讀取日誌內容。每份報告保留五分鐘。

```json
{
  "from": 1792312896695000,
  "to": 1792316496695000,
  "changesSince": 1791711696695000,
  "services": [
    {
      "service": { "namespace": "shop", "name": "checkout", "environment": "prod" },
      "logs": { "state": "reported", "streams": ["default"], "lines": 1200, "traced": 480, "sampled": 10, "matched": 9 },
      "metrics": "missing",
      "resource": { "environment": true, "version": true, "instance": true, "placement": false },
      "changes": { "count": 3, "lastAt": 1792312896695000 },
      "grades": { "traceIds": "partial", "resource": "partial", "metrics": "missing", "changes": "good" }
    }
  ],
  "unmatched": [{ "name": "checkout-svc", "signal": "logs", "streams": ["default"], "lines": 640 }]
}
```

| 欄位 | 含義 |
|---|---|
| `logs` | 服務在含 `service.name`、`service_name` 或 `service` 欄位的日誌資料流中的行數，最多查看八個資料流，`default` 優先。`traced` 是帶 `trace_id`、`traceId` 或 `trace.id` 的行數。每個服務取最近的至多十個 TraceID（總共至多 200 個）到 Trace 中查找，即 `sampled` 和 `matched`。 |
| `metrics` | 是否有指標資料流中的序列帶有這個服務的 `service.name`。 |
| `resource` | Span 是否上報了環境、任意版本和執行個體，以及是否有執行個體上報 `host.name`、`k8s.pod.name`、`k8s.node.name` 或 `container.id`（`placement`）。 |
| `changes` | 從 `changesSince` 起為這個服務上報的部署、設定變更和 Feature Flag 變更。 |
| `unmatched` | 日誌或指標中套用命名規則和別名後，對不上任何 APM 服務的服務名稱，至多 20 個，行數多的在前。 |

每項評級為 `good`、`partial`、`missing` 或 `unknown`：

| 評級 | `good` | `partial` | `missing` |
|---|---|---|---|
| `traceIds` | 至少 90% 的日誌帶有 TraceID，且取樣的 TraceID 至少 80% 能找到。 | 部分日誌帶有 TraceID。 | 沒有日誌帶有 TraceID，或服務沒有寫日誌。 |
| `resource` | `resource` 的四項都為 true。 | 部分為 true。 | 都不為 true。 |
| `metrics` | 有指標帶有這個服務名稱。 | | 沒有。 |
| `changes` | 至少一次變更。 | | 沒有。 |

`unknown` 表示查看失敗或超過三秒；有資料流讀取失敗時，沒找到的服務名稱會記為 `unknown`，不會記為 `missing`。Mole Agent 使用 `get_correlation_quality` 讀取同一份報告。

## 讀取服務的資料涵蓋範圍

`GET /api/v1/apm/services/{service}/coverage` 需要 `namespace` 和 `environment`，可選 `to`（目前時間範圍的終點，單位微秒，預設為目前時間）。它查看 `to` 之前的一天，每個結果保留五分鐘。

```json
{
  "from": 1792230096695000,
  "to": 1792316496695000,
  "logs": { "state": "reported", "found": ["default"] },
  "metrics": { "state": "missing" },
  "profiles": { "state": "reported", "found": ["cpu", "alloc_space"] },
  "rum": { "state": "unknown" }
}
```

| 訊號 | 為 `reported` 的條件 | `found` |
|---|---|---|
| `logs` | 某個含 `service.name`、`service_name` 或 `service` 欄位的日誌資料流中有這個服務的日誌。最多查看八個資料流，`default` 優先。 | 這些資料流。 |
| `metrics` | 在 `to` 時刻，`count(last_over_time({"service.name"="<service>"}[1h]))` 大於零。 | 序列數。 |
| `profiles` | Profile 資料流中有這個服務的 Profile。 | Profile 類型。 |
| `rum` | 服務最近的五筆取樣呼叫鏈中，有一筆由瀏覽器動作帶上。 | 工作階段。 |

`missing` 表示沒有找到。`unknown` 表示查看失敗或超過三秒。`rum` 不會是 `missing`：取樣呼叫鏈只能說明有工作階段到達服務，不能說明沒有。

## 讀取服務的執行情況

`GET /api/v1/apm/services` 和 `GET /api/v1/apm/services/{service}` 傳回的每個服務摘要帶有 `profile`，取自時間範圍內上報過的執行個體；設定 `version` 參數時只統計該版本的執行個體。每個清單依共用該值的執行個體數排序，最多 5 項，格式為 `{ "value": "1.8.2", "instances": 4 }`。

| 欄位 | 說明 |
|---|---|
| `instanceCount`、`hostCount` | 執行個體數和不同 `host.name` 的數量。 |
| `versions` | 執行個體運行的版本。灰度發布時會有兩個。 |
| `languages`、`runtimes`、`frameworks` | `telemetry.sdk.language`；`process.runtime.name` 及其版本；由入口 Span 插樁程式庫辨識出的框架。 |
| `regions`、`clusters`、`k8sNamespaces`、`workloads` | `cloud.region`、`k8s.cluster.name`、`k8s.namespace.name`，以及 `k8s.deployment.name` 或 `k8s.statefulset.name`。 |
| `repositories`、`commits` | `vcs.repository.url.full` 或 `git.repository_url`（移除憑證後儲存）；`vcs.ref.head.revision` 或 `git.commit.sha`。 |
| `entryKinds` | `http`、`rpc`、`messaging`、`span`：服務承接的入口類型。 |

`GET /api/v1/apm/services/{service}/instances` 會逐一列出執行個體，最近上報的在前，最多 500 個。參數為 `namespace`、`environment`，以及可選的 `version`、`from`、`to`；缺少服務或環境時傳回 `400`。每項包含 `instanceId`（依序取 `service.instance.id`、`k8s.pod.name`、`host.name`）、`version`、`firstSeenAt`、`lastSeenAt`、`attributes`（執行個體最後一次上報的屬性），以及它在時間範圍內處理的請求：`red`（與摘要相同，Apdex 依服務的閾值計算）和 `sparkline`。超過執行個體上限的執行個體會合併為一項，其 `instanceId` 為 `__other__`。在儲存執行個體資訊之前就處理過請求的執行個體，`attributes` 為空。

## 設定錯誤群組的狀態

```http
PUT /api/v1/apm/errors/<fingerprint>/issue
Content-Type: application/json

{"status": "investigating", "assigneeId": "<user id>", "teamId": "<team id>", "lastSeenAt": 1792316496695000}
```

`status` 為 `open`、`investigating`、`resolved` 或 `ignored`。`assigneeId` 為組織成員或 `null`，`teamId` 為組織中的團隊或 `null`。`lastSeenAt` 可選，表示呼叫方最後看到該群組的時間，單位為微秒。設為 `resolved` 時會將目前時間記為 `resolvedAt`。

錯誤摘要以 `issue` 攜帶狀態，從未設定時為 `null`。已解決的群組在 `resolvedAt` 之後再次出現時，`issue.regressed` 為 `true`，`unresolved` 篩選會保留這些群組。為投影不認識的指紋設定狀態會傳回 `404`。

## 維護服務等級目標

服務等級目標（SLO）承諾某個環境中的一個服務或其某個端點，在滾動視窗內達標請求所占的比例。各項指標的含義請見[服務等級目標](/zh-Hant/apm#服務等級目標)。

```http
POST /api/v1/apm/slos
Content-Type: application/json

{"name": "Checkout availability", "namespace": "shop", "service": "checkout", "environment": "production", "transaction": null, "kind": "availability", "objective": 0.999, "windowDays": 30}
```

| 欄位 | 說明 |
|---|---|
| `name` | 必填，最多 255 位元組。 |
| `description` | 可選，最多 2,000 位元組。 |
| `namespace`、`service`、`environment` | 必填，即 APM 中的服務名稱。沒有 `service.namespace` 的服務屬於命名空間 `default`。 |
| `transaction` | 某個端點 `{ "name": "POST /orders", "kind": "http" }`，或用 `null` 表示整個服務。 |
| `kind` | `availability`：請求沒有失敗即為達標。`latency`：請求沒有失敗且耗時不超過 `latencyThreshold` 即為達標。 |
| `latencyThreshold` | `latency` 必填且為正數；`availability` 必須為 `null` 或省略。 |
| `objective` | 達標請求的比例，大於 0 且小於 1，例如 `0.999`。 |
| `windowDays` | `7`、`28` 或 `30`。 |

`POST` 和 `PUT` 傳回儲存後的 SLO，含 `id`、`createdBy`、`createdAt`、`updatedBy` 和 `updatedAt`。`GET /api/v1/apm/slos` 以狀態的形式傳回組織的所有 SLO；同時傳入 `namespace`、`service` 和 `environment` 可只保留一個服務的 SLO。視窗截至呼叫時刻，因此不適用一般時間範圍參數。

| 狀態欄位 | 說明 |
|---|---|
| `slo` | 儲存的 SLO。 |
| `state` | `healthy`、`at_risk`、`breached` 或 `noData`。 |
| `sli` | 視窗內達標請求數除以全部請求數；沒有請求時為 `null`。 |
| `goodRequests`、`totalRequests` | `sli` 背後的計數。延遲 SLO 的 `goodRequests` 由延遲直方圖估算，可能帶小數。 |
| `budgetRemaining` | `1 - (1 - sli) / (1 - objective)`，目標被打破後低於零；沒有請求時為 `null`。 |
| `burnRates` | `oneHour`、`sixHours` 和 `oneDay`：最近 1 小時、6 小時和 24 小時的 `(1 - sli) / (1 - objective)`；沒有請求時為 `null`。 |

`GET /api/v1/apm/slos/{id}` 傳回 `status` 和 `history`。`history` 依時間從早到晚，為視窗內每個有請求的 UTC 自然日給出一項，含微秒單位的 `dayStart`、`sli`、`goodRequests` 和 `totalRequests`。

`DELETE` 傳回 `204`。仍有告警規則監控該 SLO（例如它的燃燒率告警）時傳回 `409`，需先刪除這些規則。監控 SLO 的告警規則是指標為 `slo_burn_rate` 的 APM 規則，請見[建立規則](/zh-Hant/api/alerting/create-rule#apm-規則)。

## 區分同名事務

不同事務類型可能使用相同名稱。請傳入可選的 `kind` 參數指定目標：

```http
GET /api/v1/apm/transactions/POST%20%2Fcheckout?kind=http&service=checkout
```

支援的 kind 為 `http`、`rpc`、`messaging`、`span` 和 `other`。名稱被多個服務或類型共用時，傳回 `400`，訊息為 `APM transaction identity is ambiguous; provide service, namespace, environment, and kind`。

## 比較版本

請提供兩個不同的 `baseline` 和 `candidate`，並新增 `service` 篩選條件以比較單一服務。

```bash
curl --get 'http://localhost:5080/api/v1/apm/versions/compare' \
  --header "Authorization: Bearer $MS_TOKEN" \
  --data-urlencode 'service=checkout' \
  --data-urlencode 'environment=production' \
  --data-urlencode 'baseline=2.3.1' \
  --data-urlencode 'candidate=2.4.0'
```

回應包含 `baseline` 與 `candidate` 兩側（各有 `version`、`sampleCount` 和 `red`），以及 `delta`、`status`、`regressedTransactions` 和 `regressedErrors`。每個回退清單最多 20 項。

| 欄位 | 說明 |
|---|---|
| `sufficientData` | 只有兩個版本都達到設定的樣本閾值時才為 `true`，預設閾值是每個版本 1,000 個請求（`[apm.version_comparison].min_requests_per_version`）。 |
| `status` | `insufficient_data`、`regressed`、`improved` 或 `neutral`。候選版本的錯誤率至少上升 1 個百分點且達到基線的 1.5 倍，或 p95 至少變慢五分之一且至少 50 毫秒時為 `regressed`；其中一項下降同樣幅度且沒有一項變差時為 `improved`；`sufficientData` 為 `false` 時為 `insufficient_data`。 |
| `delta` | `requestCountAbsolute` 與 `requestCountRelative`、`errorRateAbsolute` 與 `errorRateRelative`、`p95AbsoluteTime` 與 `p95Relative`。基線為零或缺失時，相對值為 `null`。 |

缺少 `candidate` 或 `baseline`，或者兩個版本相同，都會傳回 `400`。

## 讀取服務的版本

`GET /api/v1/apm/services/{service}` 傳回 `versions`，即時間範圍內出現過的版本。每個版本帶有 `red`（它在時間範圍內的表現）和 `verdict`（與同一服務中在它之前首次出現的版本相比的結論），判定方式與[版本對比](#比較版本)相同：

| 欄位 | 說明 |
|---|---|
| `previous` | 對比的版本。 |
| `status` | `regressed`、`improved`、`neutral` 或 `insufficient_data`。 |
| `worse` | `status` 為 `regressed` 時變差的項目：`errorRate`、`latency` 或兩者。 |
| `delta` | 與版本對比相同，以較早的版本為基線。 |

最早出現的版本沒有 `verdict`。請求中的版本篩選不會縮小這些資料：每個版本都從整個服務讀取。

## 讀取錯誤發生的分佈

`GET /api/v1/apm/errors` 在分頁結果旁傳回 `breakdown`，統計 `status` 篩選保留的全部分組（不只是目前頁面），`GET /api/v1/apm/errors/{fingerprint}` 傳回該分組的 `breakdown`。它包含 `versions`、`environments` 和 `languages`，每項是 `value` 與 `count`（出現次數）的清單，次數多的在前。span 沒有回報的值為空字串；前七個值之後其餘值合計為 `__other__`。語言取自服務的 `telemetry.sdk.language`。

## 維護錯誤聚合規則

規則在錯誤出現時依類型、拋出位置和端點之外的方式分組。規則依 `position` 順序比對，第一條符合的規則生效。

```http
POST /api/v1/apm/error-rules
Content-Type: application/json

{"name": "Upstream timeouts", "serviceNamespace": "shop", "serviceName": "checkout",
 "errorType": "*Timeout*", "message": "", "frame": "", "endpoint": "", "action": "merge", "enabled": true}
```

| 欄位 | 說明 |
|---|---|
| `name` | 最多 128 個字元。合併後的分組以此命名。 |
| `serviceNamespace`、`serviceName` | 規則適用的服務。`serviceName` 為空表示全部服務；指定命名空間時必須同時指定服務名稱。 |
| `errorType`、`message`、`frame`、`endpoint` | 錯誤類型、例外訊息、第一個應用程式堆疊幀和端點的比對模式，每個最多 256 個字元。模式比對整段文字，不區分大小寫，`*` 代表任意文字。空模式不限；至少要設定一個。 |
| `action` | `merge`：一個服務中符合的錯誤合併為一個分組。`ignore`：符合的錯誤不形成分組，它們的請求仍計為失敗。 |
| `enabled` | 停用的規則會保留，但不參與比對。預設為 `true`。 |

回應為帶有 `id`、`position`、`updatedBy` 和 `updatedAt` 的規則。一個組織最多保留 100 條規則。`PUT /api/v1/apm/error-rules/order` 接收 `{"ids": [...]}`，把這些規則依給定順序排在最前，其餘規則排在其後，並依新順序傳回規則。

修改在儲存它的節點上立即生效，在其他節點上 30 秒內生效，作用於此後出現的錯誤；既有的分組維持不變。

## 讀取服務地圖

`GET /api/v1/apm/map` 接收通用的時間範圍、`environment` 和 `namespace` 參數，傳回 `nodes`、`edges`、`namespaces`（該環境中服務的命名空間）、`environments`（全部環境）和 `truncated`（只保留了最繁忙的 400 個節點時為 `true`）。

| 欄位 | 說明 |
|---|---|
| `nodes[].id` | `service:<名稱>`、`topic:<名稱>`，被呼叫的物件為 `<類別>:<目標>`。 |
| `nodes[].kind` | `service`、`external` 或 `topic`。外部節點帶有 `category`。 |
| `nodes[].red` | `requestCount`、`errorCount`、`errorRate` 和 `p95Time`：服務處理的請求，或外部節點、Topic 收到的請求。服務節點還帶有 `health`、`namespace` 和 `environments`。 |
| `edges[].kind` | `call`、`publish`（發佈到 Topic）或 `consume`（從 Topic 消費）。 |
| `change` | 邊或節點與之前同樣長的一段時間相比：之前沒有為 `new`，現在沒有為 `gone`。之前沒有任何資料時省略。 |

服務之間的呼叫取自服務圖，P95 取其最慢一分鐘的值；其餘取自 APM 分桶。`GET /api/v1/apm/map/edge` 在相同參數之外接收 `source` 和 `target` 兩個節點 id，傳回 `kind`、`red`、`trend`、`operations`（`name`、`kind`、`red`）、`everyCaller`（操作是被呼叫服務所有呼叫方的端點時為 `true`）和 `errors`（被呼叫服務的錯誤分組）。

## 讀取服務的影響範圍

`GET /api/v1/apm/blast-radius` 必須帶 `service`，另外接收通用的時間範圍和 `environment` 參數。它讀取該環境的整張地圖，不受 Namespace 限制，傳回 `meta`、`service`（服務自己的節點，時間範圍內地圖上沒有該服務時省略）、`upstream`（呼叫它的，最多三層）和 `downstream`（它呼叫或發佈到的，最多兩層）。每一側最多 30 個節點，不健康的在前；和上一時段相比已經消失的呼叫不計入。

| 欄位 | 說明 |
|---|---|
| `id`、`kind`、`name`、`namespace`、`category` | 節點，含義同[服務地圖](#讀取服務地圖)。 |
| `hops` | 節點和服務之間相隔的呼叫層數：直接呼叫方或被呼叫方為 `1`。 |
| `via` | 透過哪個節點到達它，即離服務近一層的節點。 |
| `health` | 服務自身的健康狀態。被呼叫的物件依呼叫失敗的情況給出。 |
| `red`、`call` | 它處理或收到的請求，以及它和 `via` 之間的呼叫。 |

## 上報發佈

`POST /api/v1/apm/deployments` 接收 JSON 格式的發佈，傳回 `201` 和這次發佈，並補上 `id`、`createdBy` 和 `createdAt`。欄位、限制和 CI 範例見[部署](/zh-Hant/apm/deployments#从-ci-上报发布)。服務名稱和環境依組織的命名規則、環境對應和別名處理。儲存庫位址儲存時會遮蔽其中的密碼。設定變更和功能旗標把 `kind` 設為 `configuration` 或 `feature_flag`，不需要 `version`。

擴縮容和基礎設施變更把 `kind` 設為 `scaling` 或 `infrastructure`。上報的變更由 [`GET /api/v1/changes`](/zh-Hant/api/changes) 列出。

## 維護 APM 設定

`GET /api/v1/apm/settings` 傳回組織的設定；`PUT` 整體取代設定，並傳回儲存後的內容：

```json
{
  "health": {
    "errorRateWarning": 0.02,
    "errorRateCritical": 0.1,
    "p95WarningTime": 500000,
    "p95CriticalTime": 2000000
  },
  "apdexThreshold": 500000,
  "longTaskTime": 1000000,
  "namingRules": [{ "pattern": "^(checkout)-[a-z0-9]{5}$", "replacement": "$1" }],
  "environmentMap": [{ "from": "Production", "to": "production" }],
  "aliases": [{ "aliasNamespace": "shop", "alias": "checkout-v1", "namespace": "shop", "service": "checkout" }],
  "metadataRules": { "teamFromTier": "p1", "ownerFromTier": "p0", "repositoryFromTier": null }
}
```

省略的欄位取預設值。名稱會去掉首尾空白，別名的 Namespace 留空時為 `default`。各項限制和作用見 [APM 設定](/zh-Hant/apm/settings)。儲存後在儲存它的節點上立即生效，在其他節點上 30 秒內生效。

平台的基數上限透過 `GET` 和 `PUT /api/v1/settings/apm_limits` 讀取和取代，需要 `sys.settings.limits.manage`。請求主體包含 `servicesPerOrgHour`、`transactionsPerServiceHour`、`dependenciesPerServiceHour`、`operationsPerDependencyHour`、`errorGroupsPerServiceHour`、`versionsPerServiceHour` 和 `instancesPerServiceHour`，每項範圍 1 到 100000。

## 閱讀回應中繼資料

每個端點都傳回通用 `meta` 物件：

```json
{
  "range": {
    "from": 1785801600000000,
    "to": 1785888000000000
  },
  "resolution": "minute",
  "projectionStartedAt": 1785798000000000,
  "lastCompleteBucketAt": 1785887940000000,
  "dataQuality": {
    "partial": false,
    "gaps": [],
    "overflowDimensions": []
  },
  "activationBoundary": false
}
```

- `activationBoundary: true` 表示 `projectionStartedAt` 之前的資料不完整。
- `dataQuality.partial: true` 表示資料不完整，不能按完整零值解讀。
- 檢查 `gaps`，確認是否發生佇列、儲存庫、刷寫、延遲資料、基數或關閉失敗。
- 使用 `lastCompleteBucketAt` 判斷最近資料是否仍在完成處理中。
- 依賴高基數明細前，請檢查 `overflowDimensions`。

## 錯誤

| 狀態碼 | 原因 |
|---|---|
| `400` | 參數無效：不支援的 `sort`（`unsupported APM sort field`）、超出 1 到 200 的 `limit`、為空或過長的篩選值（`invalid APM service filter`）、超過最大值的時間範圍（`APM query range exceeds configured maximum`）、結束早於開始（`APM range end precedes start`），未知的 `direction`、`resolution`，未通過上述驗證的 SLO（`SLO objective must be between 0 and 1, exclusive`），或缺少 `namespace`、`service`、`environment` 之一的 SLO 清單篩選條件。 |
| `403` | Token 缺少這個呼叫需要的權限。 |
| `404` | 範圍內不存在該錯誤指紋、交易、服務或 SLO。 |
| `409` | 要刪除的 SLO 仍有告警規則在監控。 |
