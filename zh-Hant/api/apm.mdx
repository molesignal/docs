APM API 提供從追蹤 Span 衍生的組織範圍彙總資料。所有端點都使用 `/api/v1/apm` 前綴，並要求 Bearer Token。

```http
Authorization: Bearer <token>
```

組織工作區須具備對應內容的讀取權限：`apm.services.read`、`apm.errors.read`、`apm.error_rules.read`、`apm.definitions.read`、`apm.slos.read`、`apm.deployments.read` 或 `apm.settings.read`。平台呼叫端可在受保護的 `_sys` 範圍內使用 `sys.telemetry.read`。各寫入操作會列出所需權限。回報發布需要 `apm.deploy`。

## 端點

| 方法與路徑 | 回應內容 |
|---|---|
| `GET /api/v1/apm/overview` | 所有服務的 RED 摘要與趨勢、服務健康狀態及其趨勢、排行榜、部署、環境、缺少的遙測檢測資訊，以及排名前列的交易、相依性和錯誤。 |
| `GET /api/v1/apm/insights` | 與上一時段和上週同時段相比有變化的指標、表現比上一個版本差的版本、可縮短耗時的地方，以及每項發現前後的變更。 |
| `GET /api/v1/apm/services` | 分頁的服務目錄，包含遙測檢測資訊、版本、健康狀態、RED 指標與追蹤篩選條件。 |
| `GET /api/v1/apm/services/{service}` | 服務摘要、趨勢、交易、相依性、錯誤與版本。 |
| `GET /api/v1/apm/services/{service}/instances` | 指定環境中的服務執行個體，包含版本、資源屬性和各執行個體處理請求的情況。 |
| `GET /api/v1/apm/services/{service}/coverage` | 在 `to` 之前的一天內，服務的日誌、指標、Profiles 和瀏覽器工作階段是否已接入 MoleSignal。 |
| `GET /api/v1/apm/transactions` | 分頁的交易 RED 指標與總耗時排名。 |
| `GET /api/v1/apm/transactions/{transaction}` | 交易趨勢、相關錯誤、版本與追蹤篩選條件。 |
| `GET /api/v1/apm/dependencies` | 分頁的呼叫端／相依性 RED 指標與總耗時排名。 |
| `GET /api/v1/apm/map` | 指定環境與命名空間的服務地圖：服務、服務呼叫的對象、Topic，以及彼此之間的呼叫。 |
| `GET /api/v1/apm/map/edge` | 地圖上的一條呼叫連線：呼叫趨勢、經由該連線存取的內容，以及被呼叫服務的錯誤。 |
| `GET /api/v1/apm/blast-radius` | 服務在地圖上的影響範圍：逐層列出呼叫該服務的對象及該服務呼叫的對象。 |
| `GET /api/v1/apm/errors` | 分頁且已去除敏感資訊的後端錯誤群組，以及所列群組的錯誤發生分布。 |
| `GET /api/v1/apm/errors/{fingerprint}` | 錯誤趨勢、相關交易與版本、群組的錯誤發生分布、代表性的堆疊追蹤和數量有限的樣本。 |
| `GET /api/v1/apm/versions/compare` | 基準與候選版本的 RED 指標、差異、資料是否充足，以及備援項目。 |
| `GET /api/v1/apm/health` | 租用戶投影狀態、運作健康狀態、界限與缺口。 |
| `GET /api/v1/apm/service-definitions` | 組織的所有服務定義。 |
| `PUT /api/v1/apm/service-definitions/{service}?namespace=` | 建立或取代服務定義。需要 `apm.definitions.manage`。 |
| `DELETE /api/v1/apm/service-definitions/{service}?namespace=` | 刪除服務定義。需要 `apm.definitions.manage`。 |
| `POST /api/v1/apm/service-definitions/{service}/key-transactions?namespace=` | 將端點標記為服務的關鍵交易，或取消標記。需要 `apm.definitions.manage`。 |
| `PUT /api/v1/apm/errors/{fingerprint}/issue` | 設定錯誤群組的狀態、團隊和負責人。需要 `apm.errors.manage`。 |
| `GET /api/v1/apm/error-rules` | 組織的錯誤彙總規則，依比對順序排列。 |
| `POST /api/v1/apm/error-rules` | 建立彙總規則，排在現有規則之後。需要 `apm.error_rules.manage`。 |
| `PUT /api/v1/apm/error-rules/{id}` | 取代一條彙總規則。需要 `apm.error_rules.manage`。 |
| `DELETE /api/v1/apm/error-rules/{id}` | 刪除一條彙總規則。需要 `apm.error_rules.manage`。 |
| `PUT /api/v1/apm/error-rules/order` | 設定規則的比對順序。需要 `apm.error_rules.manage`。 |
| `GET /api/v1/apm/slos` | 所有服務等級目標及其狀態、達成率、剩餘錯誤預算和消耗率。 |
| `GET /api/v1/apm/slos/{id}` | 單一服務等級目標的狀態，以及時間視窗內每天的情況。 |
| `POST /api/v1/apm/slos` | 建立服務等級目標。需要 `apm.slos.manage`。 |
| `PUT /api/v1/apm/slos/{id}` | 取代服務等級目標。需要 `apm.slos.manage`。 |
| `DELETE /api/v1/apm/slos/{id}` | 刪除服務等級目標。需要 `apm.slos.delete`。 |
| `POST /api/v1/apm/deployments` | 回報一次發布。需要 `apm.deploy`。 |
| `GET /api/v1/apm/deployments` | 部署管線回報的發布，依時間由新到舊排列。 |
| `GET /api/v1/apm/settings` | 組織的 APM 設定。若從未儲存設定，則傳回預設值。 |
| `PUT /api/v1/apm/settings` | 取代組織的 APM 設定。需要 `apm.settings.manage`。 |

路徑參數必須經過 URL 編碼。請使用清單回應傳回的確切 `transaction` 名稱或錯誤 `fingerprint`。

## 通用查詢參數

| 參數 | 類型 | 行為 |
|---|---|---|
| `from` | integer | 自 Unix 紀元起以微秒表示的開始時間。預設為 `to` 前 24 小時。 |
| `to` | integer | 自 Unix 紀元起以微秒表示的結束時間。預設為目前時間。 |
| `namespace` | string | 完全比對服務的命名空間。 |
| `service` | string | 完全比對服務名稱。服務詳細資料路徑中的值會覆寫此參數。 |
| `environment` | string | 完全比對部署環境。 |
| `version` | string | 完全比對服務版本。 |
| `resolution` | enum | `auto`、`minute` 或 `hour`。`auto` 會依時間範圍選擇可用的時間解析度。 |
| `sort` | string | 端點支援的排序欄位。 |
| `direction` | enum | `asc` 或 `desc`，預設為 `desc`。 |
| `limit` | integer | 每頁 1 到 200 筆，預設為 50 筆。 |
| `cursor` | string | 上一個清單回應傳回的不透明游標。 |
| `status` | enum | 僅適用於 `/errors`：`all`（預設）、`unresolved`（待處理、調查中，以及解決後再次出現的群組）、`investigating`、`resolved` 或 `ignored`。 |

篩選值不得為空，也不得超過 192 位元組。查詢範圍不得超過設定的上限，預設為 30 天（`[apm].max_query_range_days`）。

### 排序欄位

| 端點 | 支援的 `sort` 值 | 預設值 |
|---|---|---|
| `/services` | `requestCount`、`errorRate`、`p95`、`name` | `requestCount` |
| `/transactions` | `requestCount`、`errorRate`、`p95`、`total_time` | `requestCount` |
| `/dependencies` | `requestCount`、`errorRate`、`p95`、`total_time` | `total_time` |
| `/errors` | `occurrenceCount`、`errorRate`、`lastSeen` | `occurrenceCount` |

`/overview` 接受相同的篩選條件與時間解析度，但不分頁。詳細資料、版本比較與健康狀態端點也不會傳回分頁清單。

## 查詢概覽

<RequestExample>
```bash cURL
NOW=$(date +%s)000000
curl --get 'http://localhost:5080/api/v1/apm/overview' \
  --header "Authorization: Bearer $MS_TOKEN" \
  --data-urlencode "from=$((NOW-86400000000))" \
  --data-urlencode "to=$NOW" \
  --data-urlencode 'environment=production' \
  --data-urlencode 'resolution=auto'
```
</RequestExample>

回應包含 `red`、`trend`、`serviceHealth`、`services`、`topTransactions`、`topDependencies`、`topErrors` 和 `recentVersions`，以及通用的 `meta` 物件，另包含下列欄位：

| 欄位 | 說明 |
|---|---|
| `serviceCount`、`activeServiceCount` | 時間範圍內出現過的服務數，以及其中收到請求的服務數。 |
| `healthTrend` | 各時段內處於各狀態的服務數：時間範圍最多分成 48 段，每段至少涵蓋一個時間桶。某段內未收到請求的服務在該段歸為 `noTraffic`。 |
| `rankings` | `slowest`（依 p95）、`mostErrors`（依錯誤率）和 `busiest`（依請求數），各列出 5 個服務。前兩項只列出請求數至少為 20 的服務。 |
| `deployments` | 在時間範圍內首次出現的版本，由新到舊排列，最多 20 個。每個版本都包含 `red` 和 `verdict`，含義與[服務的版本](#讀取服務的版本)相同。 |
| `environments`、`availableEnvironments` | 目前檢視中各環境的服務數和請求數，以及不受 `environment` 篩選條件影響的所有環境。 |
| `instrumentation` | 依語言和 SDK 統計的服務數，以及未回報 `deployment.environment`、`service.version` 或 `service.instance.id` 的服務數。 |

## 讀取深入分析

`GET /api/v1/apm/insights` 接受通用的時間範圍和篩選參數，傳回 `meta` 與下列欄位：

| 欄位 | 說明 |
|---|---|
| `now`、`previous`、`lastWeek` | 目前檢視中各服務在指定時間範圍、前一個等長時段，以及上週同時段的資料：`requestCount`、`throughput`（每秒請求數）、`errorRate`、`p95Time` 和 `apdex`。省略沒有請求的時段。 |
| `insights` | 最多 30 項發現，優先列出最需要關注的項目。 |

每項發現包含：

| 欄位 | 說明 |
|---|---|
| `kind` | `anomaly`、`regression`、`slow_dependency`、`repeated_call`、`slowQuery` 或 `hot_endpoint`。 |
| `severity` | `critical`、`warning`；建議項目為 `info`。 |
| `service` | `namespace`、`name` 和 `environment`。 |
| `transaction`、`dependency` | 熱點端點所對應的端點；瓶頸、重複呼叫或緩慢陳述式所對應的相依性。 |
| `metric` | 發生變化或惡化的指標：`errorRate`、`p95` 或 `throughput`。 |
| `value` | 目前的值：錯誤率為比值，P95 以微秒計，輸送量為每秒請求數。瓶頸和熱點端點採耗時占比，重複呼叫採每個請求的呼叫次數，緩慢陳述式採以微秒計的 P95。 |
| `previous`、`lastWeek` | 同一指標在上一時段和上週同時段的值；如果版本表現變差，則為上一個版本的值。 |
| `since` | 突變開始的時間，或表現變差的版本首次出現的時間。 |
| `version`、`previousVersion` | 表現變差的版本及其前一個版本。 |
| `calls`、`p95Time` | 建議所依據的呼叫數或請求數，以及這些呼叫或請求的 P95。 |
| `changes` | `since` 前後的變更，最接近的在前：`kind`、`source`（`reported` 或 `observed`）、`service`、`version`、`status`、`at`、`downstream`（若變更發生在出現突變的服務所呼叫的服務上，則為 `true`）、`commit` 和 `description`。 |

如需判斷條件，請參閱[深入分析與調查](/zh-Hant/apm/insights#洞察的類型)。

## 讀取 RED 指標

每個摘要都包含 `red` 物件，其中有時間範圍內的請求、錯誤和耗時資料。

| 欄位 | 說明 |
|---|---|
| `requestCount`、`errorCount`、`errorRate` | 請求數、失敗請求數，以及失敗請求占全部請求的比值（0 到 1）。 |
| `durationSum`、`durationAverage` | 總耗時與平均耗時，單位為微秒。沒有請求時，平均值為 `null`。 |
| `p50Time`、`p90Time`、`p95Time`、`p99Time` | 延遲百分位數，單位為微秒。在對應排名所在的直方圖桶內以內插法估算。使用預設分桶時，與精確耗時的誤差約為 ±4%。沒有請求時為 `null`。 |
| `apdex` | 不超過門檻 T 的請求數，加上不超過 4T 的請求數的一半，再除以全部請求數，結果介於 0 到 1。T 採用服務的 `apdexThreshold`，未設定時為 500 ms；概覽中的全服務彙總指標以 500 ms 計算。發生錯誤的請求一律不計為滿意。沒有請求時為 `null`。 |
| `latencyPartial` | 部分時間桶使用無法辨識的延遲分桶時為 `true`。系統會換算並計入使用早期分桶方式（`[apm.histogram].schema_version`）寫入的時間桶。計算百分位數時會排除無法讀取的時間桶，但計數、總和與平均值仍會納入這些時間桶。 |
| `timeoutCount`、`retryCount` | 逾時的請求（錯誤類型為逾時、gRPC `DEADLINE_EXCEEDED`、HTTP 408 或 504）和重送的請求（`http.request.resend_count` 大於 0）。為 0 時省略。 |
| `statusCodes` | 依狀態碼統計的回應，索引鍵為 `http:<狀態碼>`（100 到 599）或 `grpc:<狀態碼>`（0 到 16）。每個桶最多記錄 24 個狀態碼，超出的部分計入 `http:other` 或 `grpc:other`。未統計到狀態碼時省略，例如在開始統計前寫入的彙總資料。 |
| `exemplars` | 時間範圍內最多 8 個範例 Span，耗時最長的在前。系統會在[尾端取樣](/zh-Hant/configuration#追蹤擷取與尾端取樣)決定是否保留對應的追蹤之前先投影 Span，因此 `traceAvailable` 通常為 `false`。若要確認是否保留追蹤，請查詢該追蹤。彙總結果仍然有效。 |

服務摘要和交易摘要包含 `apdexThreshold`，也就是計算 Apdex 時使用的 T。服務摘要還包含 `health` 和 `healthReasons`。每項超過門檻的指標都包含 `metric`（`errorRate` 或 `p95`）、`level`、`value` 和 `threshold`。服務摘要也包含 `sparkline`（每個時間桶的請求數、錯誤數和 p95），以及 `currentVersion` 和 `currentVersionSince`（最近出現的版本及其首次出現時間）。服務或交易的詳細資料包含 `latencyDistribution`，其中列出有請求的直方圖桶。每個桶都包含 `lowerTime`、`upperTime` 和 `count`，整體範圍縮限在最快與最慢的請求之間。

## 維護服務定義

服務定義記錄服務由誰負責，以及服務的重要程度。系統依 `namespace` 和服務名稱儲存定義，適用於所有環境，也可以在服務回報資料前建立。

```http
PUT /api/v1/apm/service-definitions/checkout?namespace=shop
Content-Type: application/json

{"description": "处理下单与支付。", "teamId": "<team id>", "ownerId": "<user id>", "tier": "p0", "lifecycle": "production", "repositoryUrl": "https://github.com/acme/checkout", "tags": {"domain": "orders", "pci": ""}, "apdexThreshold": 300000, "aliases": ["order_service", "订单中心"], "dataSources": {"logs": [{"stream": "default", "filter": "service_name = 'order_service'"}], "metrics": [{"selector": "{service=\"checkout\"}"}], "dashboards": ["<dashboard id>"], "links": [{"name": "Runbook", "url": "https://wiki.example.com/checkout"}]}, "archived": false}
```

| 欄位 | 說明 |
|---|---|
| `description` | 最多 2,000 個字元。 |
| `teamId` | 組織內的團隊，或 `null`。刪除團隊後，系統會清空此欄位。 |
| `ownerId` | 組織成員，或 `null`。 |
| `tier` | `p0`（最重要）到 `p5`，或 `null`。 |
| `lifecycle` | `production`、`staging`、`experimental`、`deprecated` 或 `null`。 |
| `repositoryUrl` | 不含空格的 `http`、`https`、`ssh`、`git` 或 `git+ssh` 網址，或 `user@host:path` 格式的位址，最多 2,048 個字元，或 `null`。系統將密碼儲存為 `****`，也將 http(s) 網址中的使用者部分儲存為 `****`。服務未回報儲存庫時，系統會顯示此欄位。 |
| `tags` | 最多 32 個標籤，格式為 `{ "key": "value" }`。key 由 1 到 64 個小寫字母、數字和 `_ . - /` 組成；value 最多 128 個字元，前後不能有空格。只有 key 時，value 為空字串。 |
| `apdexThreshold` | 服務的 Apdex 閾值 T，大於 0 且不超過 60,000,000（一分鐘），或以 `null` 表示 500 ms。 |
| `aliases` | 日誌、指標和其他系統使用的服務別名，最多 20 個，每個 1 到 128 個字元，前後不能有空格。比對時不區分大小寫：別名不能重複，不能與服務本身的名稱相同，也不能與組織內其他服務的名稱或別名相同。省略時，已儲存的定義會保留原有別名。 |
| `dataSources` | 服務的資料入口：`logs`（`stream`，以及選填的 `filter`，即最多 2,000 個字元的布林 SQL 運算式）、`metrics`（`selector`，即 PromQL 選擇器，例如 `{service="checkout"}`）、`dashboards`（儀表板 ID）和 `links`（`name` 與使用 `http` 或 `https` 的 `url`），每類最多 10 筆。省略時，已儲存的定義會保留原有資料入口。 |
| `archived` | 設為 `true` 時，服務不會出現在服務目錄的預設檢視中。省略時，已儲存的定義會保留原本的狀態。 |

儲存定義不會變更 `keyTransactions`，每次只能新增或移除一個關鍵交易。回應會傳回儲存後的定義，包含 `namespace`、`name`、`keyTransactions`、`updatedBy` 和 `updatedAt`。`DELETE` 傳回 `204`；服務沒有定義時傳回 `404`。

### 標記關鍵交易

```http
POST /api/v1/apm/service-definitions/checkout/key-transactions?namespace=shop
Content-Type: application/json

{"transaction": {"name": "POST /orders", "kind": "http"}, "key": true}
```

`key: true` 將端點加入 `keyTransactions`，`false` 則將端點移除；端點已處於指定狀態時，不會有任何變更。服務尚無定義時，系統會自動建立定義。每個服務最多有 50 個關鍵交易，彙整超額項目的 `__other__` 列不能標記為關鍵交易。回應會傳回變更後的定義。

## 讀取服務的資料涵蓋情況

`GET /api/v1/apm/services/{service}/coverage` 需要 `namespace` 和 `environment`，可選填 `to`（目前時間範圍的終點，單位為微秒，預設為目前時間）。系統會檢查 `to` 之前一天的資料，並將每筆結果保留五分鐘。

```json
{
  "from": 1792230096695000,
  "to": 1792316496695000,
  "logs": { "state": "reported", "found": ["default"] },
  "metrics": { "state": "missing" },
  "profiles": { "state": "reported", "found": ["cpu", "alloc_space"] },
  "rum": { "state": "unknown" }
}
```

| 訊號 | 判定為 `reported` 的條件 | `found` |
|---|---|---|
| `logs` | 至少有一個包含 `service.name`、`service_name` 或 `service` 欄位的日誌資料串流含有該服務的日誌。最多檢查八個資料串流，優先檢查 `default`。 | 這些資料串流。 |
| `metrics` | 在 `to` 時刻，`count(last_over_time({"service.name"="<service>"}[1h]))` 大於零。 | 時間序列數量。 |
| `profiles` | Profile 資料串流中有該服務的 Profile。 | Profile 類型。 |
| `rum` | 服務最近的五筆取樣追蹤中，至少有一筆由瀏覽器動作帶入。 | 工作階段。 |

`missing` 表示找不到資料。`unknown` 表示檢查失敗或耗時超過三秒。`rum` 不會是 `missing`：取樣追蹤只能確認有工作階段到達服務，無法確認沒有工作階段到達。

## 讀取服務的執行情況

`GET /api/v1/apm/services` 和 `GET /api/v1/apm/services/{service}` 傳回的每份服務摘要都包含 `profile`，資料來自在時間範圍內回報過的執行個體。設定 `version` 參數時，只統計該版本的執行個體。每份清單都依具有相同值的執行個體數量排序，最多 5 項，格式為 `{ "value": "1.8.2", "instances": 4 }`。

| 欄位 | 說明 |
|---|---|
| `instanceCount`、`hostCount` | 執行個體數量，以及不重複的 `host.name` 數量。 |
| `versions` | 執行個體執行的版本。採用灰度發布時會有兩個版本。 |
| `languages`、`runtimes`、`frameworks` | `telemetry.sdk.language`；`process.runtime.name` 及其版本；根據入口 Span 的探測程式庫辨識出的框架。 |
| `regions`、`clusters`、`k8sNamespaces`、`workloads` | `cloud.region`、`k8s.cluster.name`、`k8s.namespace.name`，以及 `k8s.deployment.name` 或 `k8s.statefulset.name`。 |
| `repositories`、`commits` | `vcs.repository.url.full` 或 `git.repository_url`（移除憑證後儲存）；`vcs.ref.head.revision` 或 `git.commit.sha`。 |
| `entryKinds` | `http`、`rpc`、`messaging`、`span`：服務接收請求的入口類型。 |

`GET /api/v1/apm/services/{service}/instances` 逐一列出執行個體，最近回報的排在前面，最多 500 個。參數為 `namespace`、`environment`，以及選填的 `version`、`from`、`to`；缺少服務或環境時，傳回 `400`。每項包含 `instanceId`（依序採用 `service.instance.id`、`k8s.pod.name`、`host.name`）、`version`、`firstSeenAt`、`lastSeenAt`、`attributes`（執行個體最後一次回報的屬性），以及時間範圍內處理的請求統計：`red`（與摘要相同，Apdex 依服務的閾值計算）和 `sparkline`。系統會將超過上限的執行個體合併為一項，其 `instanceId` 為 `__other__`。如果執行個體在系統儲存其資訊之前就已處理過請求，`attributes` 會是空的。

## 設定錯誤群組的狀態

```http
PUT /api/v1/apm/errors/<fingerprint>/issue
Content-Type: application/json

{"status": "investigating", "assigneeId": "<user id>", "teamId": "<team id>", "lastSeenAt": 1792316496695000}
```

`status` 為 `open`、`investigating`、`resolved` 或 `ignored`。`assigneeId` 為組織成員或 `null`，`teamId` 為組織內的團隊或 `null`。`lastSeenAt` 為選填，表示呼叫端最後看到該群組的時間，單位為微秒。設為 `resolved` 時，系統會將目前時間記為 `resolvedAt`。

錯誤摘要在 `issue` 中提供狀態，從未設定時為 `null`。已解決的群組在 `resolvedAt` 之後再次出現時，`issue.regressed` 為 `true`，`unresolved` 篩選條件會保留這些群組。若投影無法辨識指定的指紋，設定狀態時會傳回 `404`。

## 維護服務等級目標

服務等級目標（SLO）承諾特定環境中的服務或其端點，在滾動視窗內應達標的請求比例。各項指標的含義請參閱[服務等級目標](/zh-Hant/apm#服務等級目標)。

```http
POST /api/v1/apm/slos
Content-Type: application/json

{"name": "Checkout availability", "namespace": "shop", "service": "checkout", "environment": "production", "transaction": null, "kind": "availability", "objective": 0.999, "windowDays": 30}
```

| 欄位 | 說明 |
|---|---|
| `name` | 必填，最多 255 位元組。 |
| `description` | 選填，最多 2,000 位元組。 |
| `namespace`、`service`、`environment` | 必填，對應 APM 中的服務名稱。未設定 `service.namespace` 的服務屬於 `default` 命名空間。 |
| `transaction` | 指定端點，例如 `{ "name": "POST /orders", "kind": "http" }`，或以 `null` 表示整個服務。 |
| `kind` | `availability`：請求未失敗即達標。`latency`：請求未失敗且耗時不超過 `latencyThreshold` 即達標。 |
| `latencyThreshold` | `latency` 必填，且須為正數；`availability` 必須設為 `null` 或省略。 |
| `objective` | 達標請求的比例，大於 0 且小於 1，例如 `0.999`。 |
| `windowDays` | `7`、`28` 或 `30`。 |

`POST` 和 `PUT` 傳回儲存後的 SLO，包含 `id`、`createdBy`、`createdAt`、`updatedBy` 和 `updatedAt`。`GET /api/v1/apm/slos` 會以狀態資料的形式傳回組織的所有 SLO；同時傳入 `namespace`、`service` 和 `environment`，即可只傳回單一服務的 SLO。視窗截至呼叫當下，因此不適用通用的時間範圍參數。

| 狀態欄位 | 說明 |
|---|---|
| `slo` | 已儲存的 SLO。 |
| `state` | `healthy`、`at_risk`、`breached` 或 `noData`。 |
| `sli` | 視窗內達標的請求數除以全部請求數；沒有請求時為 `null`。 |
| `goodRequests`、`totalRequests` | 計算 `sli` 所用的計數。系統根據延遲直方圖估算延遲 SLO 的 `goodRequests`，結果可能包含小數。 |
| `budgetRemaining` | `1 - (1 - sli) / (1 - objective)`，未達目標時低於零；沒有請求時為 `null`。 |
| `burnRates` | `oneHour`、`sixHours` 和 `oneDay`：最近 1 小時、6 小時和 24 小時的 `(1 - sli) / (1 - objective)`；沒有請求時為 `null`。 |

`GET /api/v1/apm/slos/{id}` 傳回 `status` 和 `history`。`history` 依時間從早到晚排序，為視窗內每個有請求的 UTC 曆日提供一筆資料，包含以微秒為單位的 `dayStart`，以及 `sli`、`goodRequests` 和 `totalRequests`。

`DELETE` 傳回 `204`。若仍有警示規則監控該 SLO（例如消耗率警示），則傳回 `409`，請先刪除這些規則。監控 SLO 的警示規則是使用 `slo_burn_rate` 指標的 APM 規則，請參閱[建立規則](/zh-Hant/api/alerting/create-rule#apm-規則)。

## 區分同名交易

不同類型的交易可能使用相同名稱。請傳入選填的 `kind` 參數來指定目標：

```http
GET /api/v1/apm/transactions/POST%20%2Fcheckout?kind=http&service=checkout
```

支援的 kind 為 `http`、`rpc`、`messaging`、`span` 和 `other`。多個服務或類型共用同一名稱時，系統會傳回 `400`，訊息為 `APM transaction identity is ambiguous; provide service, namespace, environment, and kind`。

## 比較版本

請為 `baseline` 和 `candidate` 提供不同的版本，並加入 `service` 篩選條件以比較單一服務。

```bash
curl --get 'http://localhost:5080/api/v1/apm/versions/compare' \
  --header "Authorization: Bearer $MS_TOKEN" \
  --data-urlencode 'service=checkout' \
  --data-urlencode 'environment=production' \
  --data-urlencode 'baseline=2.3.1' \
  --data-urlencode 'candidate=2.4.0'
```

回應包含 `baseline` 與 `candidate` 兩組結果（各包含 `version`、`sampleCount` 和 `red`），以及 `delta`、`status`、`regressedTransactions` 和 `regressedErrors`。每份退化清單最多 20 項。

| 欄位 | 說明 |
|---|---|
| `sufficientData` | 只有兩個版本都達到設定的樣本閾值時才為 `true`，預設閾值為每個版本 1,000 個請求（`[apm.version_comparison].min_requests_per_version`）。 |
| `status` | `insufficient_data`、`regressed`、`improved` 或 `neutral`。候選版本的錯誤率至少上升 1 個百分點，且達到基準版本的 1.5 倍，或 p95 延遲至少增加五分之一且至少增加 50 毫秒時，為 `regressed`；其中一項下降相同幅度且兩項皆未惡化時，為 `improved`；`sufficientData` 為 `false` 時，為 `insufficient_data`。 |
| `delta` | `requestCountAbsolute` 與 `requestCountRelative`、`errorRateAbsolute` 與 `errorRateRelative`、`p95AbsoluteTime` 與 `p95Relative`。基準值為零或缺少基準值時，相對值為 `null`。 |

缺少 `candidate` 或 `baseline`，或兩個版本相同時，都會傳回 `400`。

## 讀取服務的版本

`GET /api/v1/apm/services/{service}` 傳回 `versions`，也就是時間範圍內出現過的版本。每個版本都包含 `red`（該版本在時間範圍內的表現）和 `verdict`（與同一服務中首次出現時間最接近且早於該版本的版本比較所得的結論），判定方式與[版本比較](#比較版本)相同：

| 欄位 | 說明 |
|---|---|
| `previous` | 用於比較的版本。 |
| `status` | `regressed`、`improved`、`neutral` 或 `insufficient_data`。 |
| `worse` | `status` 為 `regressed` 時惡化的項目：`errorRate`、`latency` 或兩者。 |
| `delta` | 與版本比較相同，以較早的版本為基準。 |

最早出現的版本沒有 `verdict`。請求中的版本篩選條件不會縮小這些資料的範圍：每個版本的資料都從整個服務讀取。

## 讀取錯誤發生的分布

`GET /api/v1/apm/errors` 除了分頁結果，也會傳回 `breakdown`，統計符合 `status` 篩選條件的所有群組，不限於目前頁面。`GET /api/v1/apm/errors/{fingerprint}` 則會傳回該群組的 `breakdown`。`breakdown` 包含 `versions`、`environments` 和 `languages`，各自列出 `value` 與 `count`（出現次數），次數較多的排在前面。span 未回報的值為空字串；前七個值以外的其餘值合計為 `__other__`。語言取自服務的 `telemetry.sdk.language`。

## 維護錯誤彙總規則

錯誤出現時，規則會採用不同於預設依類型、擲出位置和端點分類的方式來分組。系統依 `position` 順序比對規則，套用第一條相符的規則。

```http
POST /api/v1/apm/error-rules
Content-Type: application/json

{"name": "Upstream timeouts", "serviceNamespace": "shop", "serviceName": "checkout",
 "errorType": "*Timeout*", "message": "", "frame": "", "endpoint": "", "action": "merge", "enabled": true}
```

| 欄位 | 說明 |
|---|---|
| `name` | 最多 128 個字元。系統會以此名稱命名合併後的群組。 |
| `serviceNamespace`、`serviceName` | 規則適用的服務。`serviceName` 留空表示所有服務；指定命名空間時，必須同時指定服務名稱。 |
| `errorType`、`message`、`frame`、`endpoint` | 錯誤類型、例外訊息、第一個應用程式堆疊框架和端點的比對模式，每個最多 256 個字元。模式會比對整段文字，不區分大小寫，`*` 代表任意文字。留空的模式不限制比對結果；至少要設定一個模式。 |
| `action` | `merge`：將單一服務中相符的錯誤合併為一個群組。`ignore`：不為相符的錯誤建立群組，但仍將相關請求計為失敗。 |
| `enabled` | 系統會保留停用的規則，但不會用於比對。預設為 `true`。 |

回應會傳回包含 `id`、`position`、`updatedBy` 和 `updatedAt` 的規則。每個組織最多保留 100 條規則。`PUT /api/v1/apm/error-rules/order` 接收 `{"ids": [...]}`，將指定規則依給定順序排在最前面，其餘規則排在後面，並依新順序傳回規則。

變更會在儲存變更的節點上立即生效，並在其他節點上於 30 秒內生效。變更僅適用於之後出現的錯誤，既有群組維持不變。

## 讀取服務地圖

`GET /api/v1/apm/map` 接收通用的時間範圍、`environment` 和 `namespace` 參數，傳回 `nodes`、`edges`、`namespaces`（該環境中服務的命名空間）、`environments`（所有環境）和 `truncated`（只保留最繁忙的 400 個節點時為 `true`）。

| 欄位 | 說明 |
|---|---|
| `nodes[].id` | `service:<名称>`、`topic:<名称>`，被呼叫的物件為 `<类别>:<目标>`。 |
| `nodes[].kind` | `service`、`external` 或 `topic`。外部節點包含 `category`。 |
| `nodes[].red` | `requestCount`、`errorCount`、`errorRate` 和 `p95Time`：服務處理的請求，或外部節點和主題收到的請求。服務節點也包含 `health`、`namespace` 和 `environments`。 |
| `edges[].kind` | `call`、`publish`（發佈到主題）或 `consume`（從主題消費）。 |
| `change` | 將邊或節點與前一個等長時段比較：先前不存在時為 `new`，目前不存在時為 `gone`。先前完全沒有資料時省略。 |

服務之間的呼叫取自服務圖，P95 採用其中最慢的一分鐘的值；其餘資料取自 APM 分桶。`GET /api/v1/apm/map/edge` 除了接收相同參數，也接收 `source` 和 `target` 兩個節點 ID，並傳回 `kind`、`red`、`trend`、`operations`（`name`、`kind`、`red`）、`everyCaller`（操作是被呼叫服務的所有呼叫端所用的端點時為 `true`）和 `errors`（被呼叫服務的錯誤群組）。

## 讀取服務的影響範圍

`GET /api/v1/apm/blast-radius` 必須提供 `service`，另外也接收通用的時間範圍和 `environment` 參數。此端點讀取該環境的完整地圖，不受命名空間限制，並傳回 `meta`、`service`（服務本身的節點，若時間範圍內的地圖沒有該服務則省略）、`upstream`（呼叫該服務的節點，最多三層）和 `downstream`（該服務呼叫或發佈到的節點，最多兩層）。每側最多 30 個節點，健康狀態不佳的節點排在前面；不計入相較於上一時段已消失的呼叫。

| 欄位 | 說明 |
|---|---|
| `id`、`kind`、`name`、`namespace`、`category` | 節點，含義與[服務地圖](#讀取服務地圖)相同。 |
| `hops` | 節點與服務之間的呼叫層數：直接呼叫端或被呼叫端為 `1`。 |
| `via` | 通往此節點的上一個節點，也就是離服務近一層的節點。 |
| `health` | 服務本身的健康狀態。被呼叫物件的健康狀態依呼叫失敗情況判定。 |
| `red`、`call` | 此節點處理或收到的請求，以及此節點與 `via` 之間的呼叫。 |

## 回報與列出發佈

`POST /api/v1/apm/deployments` 接收 JSON 格式的發佈資料，傳回 `201` 和這次發佈的資料，並加上 `id`、`createdBy` 和 `createdAt`。欄位、限制和 CI 範例請參閱[部署](/zh-Hant/apm/deployments#從-ci-回報發佈)。服務名稱和環境依組織的命名規則、環境對應和別名處理。儲存儲存庫網址時會遮蔽其中的密碼。若是設定變更或功能開關，請將 `kind` 分別設為 `configuration` 或 `feature_flag`，不必提供 `version`。

`GET /api/v1/apm/deployments` 接收 `service`、`namespace`、`environment`、`from` 和 `to`（以微秒為單位的時間範圍），依時間由新到舊傳回最多 200 筆發佈。未指定命名空間或環境的發佈會出現在所有命名空間或環境的清單中。

## 維護 APM 設定

`GET /api/v1/apm/settings` 傳回組織的設定；`PUT` 會取代整份設定，並傳回儲存後的內容：

```json
{
  "health": {
    "errorRateWarning": 0.02,
    "errorRateCritical": 0.1,
    "p95WarningTime": 500000,
    "p95CriticalTime": 2000000
  },
  "apdexThreshold": 500000,
  "longTaskTime": 1000000,
  "namingRules": [{ "pattern": "^(checkout)-[a-z0-9]{5}$", "replacement": "$1" }],
  "environmentMap": [{ "from": "Production", "to": "production" }],
  "aliases": [{ "aliasNamespace": "shop", "alias": "checkout-v1", "namespace": "shop", "service": "checkout" }],
  "metadataRules": { "teamFromTier": "p1", "ownerFromTier": "p0", "repositoryFromTier": null }
}
```

省略的欄位採用預設值。系統會移除名稱前後的空白；別名的命名空間留空時採用 `default`。各項限制和用途請參閱 [APM 設定](/zh-Hant/apm/settings)。設定儲存後會立即在執行儲存的節點上生效，並在其他節點上於 30 秒內生效。

使用 `GET` 和 `PUT /api/v1/settings/apm_limits` 讀取和取代平台的基數上限，需要 `sys.settings.limits.manage` 權限。請求主體包含 `servicesPerOrgHour`、`transactionsPerServiceHour`、`dependenciesPerServiceHour`、`operationsPerDependencyHour`、`errorGroupsPerServiceHour`、`versionsPerServiceHour` 和 `instancesPerServiceHour`，每項的範圍為 1 到 100000。

## 讀取回應中繼資料

每個端點都會傳回通用的 `meta` 物件：

```json
{
  "range": {
    "from": 1785801600000000,
    "to": 1785888000000000
  },
  "resolution": "minute",
  "projectionStartedAt": 1785798000000000,
  "lastCompleteBucketAt": 1785887940000000,
  "dataQuality": {
    "partial": false,
    "gaps": [],
    "overflowDimensions": []
  },
  "activationBoundary": false
}
```

- `activationBoundary: true` 表示 `projectionStartedAt` 之前的資料不完整。
- `dataQuality.partial: true` 表示資料不完整，不可將缺少的資料解讀為零值。
- 檢查 `gaps`，確認是否發生佇列、儲存庫、寫入、資料延遲到達、基數或關閉相關的問題。
- 使用 `lastCompleteBucketAt` 判斷最新資料是否仍在處理中。
- 採用高基數明細前，請先檢查 `overflowDimensions`。

## 錯誤

| 狀態碼 | 原因 |
|---|---|
| `400` | 參數無效：不支援的 `sort`（`unsupported APM sort field`）、不在 1 到 200 範圍內的 `limit`、空白或過長的篩選值（`invalid APM service filter`）、超過上限的時間範圍（`APM query range exceeds configured maximum`）、結束時間早於開始時間（`APM range end precedes start`）、未知的 `direction` 或 `resolution`、未通過上述驗證的 SLO（`SLO objective must be between 0 and 1, exclusive`），或 SLO 清單的篩選條件缺少 `namespace`、`service`、`environment` 中的任一項。 |
| `403` | 權杖缺少此呼叫所需的權限。 |
| `404` | 範圍內沒有該錯誤指紋、交易、服務或 SLO。 |
| `409` | 仍有警示規則在監控要刪除的 SLO。 |
