請先查看處理程序日誌：啟動失敗的原因會列印在日誌裡，遭拒的 HTTP 請求，其回應主體中會帶有說明資訊。日誌等級來自 `[telemetry].log_level` 或 `RUST_LOG`。

## 啟動

| 現象 | 原因 | 解決方式 |
|---|---|---|
| `... password authentication failed for user` | DSN 中的使用者或密碼錯誤。 | 修正 `[meta_database].dsn`。 |
| `... pool timed out while waiting for an open connection` | 節點無法連線到 PostgreSQL。 | 檢查主機、連接埠、防火牆以及 `sslmode` 要求。 |
| `startup_ping put: ... SignatureDoesNotMatch` | 物件儲存拒絕了憑證。 | 檢查 `access_key` 與 `secret_key`，可使用 `MS_OBJECT_STORE_ACCESS_KEY` 與 `MS_OBJECT_STORE_SECRET_KEY` 設定。 |
| `startup_ping put: ... NoSuchBucket` | bucket 不存在。 | 建立 bucket，或修正 `[object_store].bucket`。 |
| 反覆出現 `Encountered transport error`，隨後處理程序結束 | 端點無法連線，或者沒有憑證傳到用戶端。 | 檢查 `endpoint`、DNS 與網路。憑證必須來自 `access_key` 與 `secret_key`。 |
| `unknown field: found ...` | 嚴格檢查的設定區段中有拼寫錯誤或不支援的鍵。 | 刪除或更正該鍵，參見[設定](/zh-Hant/configuration#如何載入設定)。 |
| `MS_SELF_TELEMETRY_CLUSTER_TOKEN must be set when split-role self intake is enabled` | 開啟追蹤擷取或自我收集時，沒有 `intake` 角色的分角色節點在啟動時沒有共用 Token。 | 在每個節點上設定相同的 Token。追蹤擷取預設為開啟，只關閉 `[telemetry.self_collect]` 並不足夠。 |
| `open Probe CA key` | `MS_CIPHER_KEY` 與加密該資料庫的金鑰不一致。 | 還原原本的金鑰，參見[生產檢查清單](/zh-Hant/deployment/production-checklist)。 |
| `migration ... was previously applied but is missing in the resolved migrations` 或 `... has been modified` | 二進位檔與資料庫來自互不相容的版本。 | 執行相符的版本，或還原備份，參見[升級](/zh-Hant/upgrade)。 |
| `address already in use` | 其他處理程序佔用了設定的連接埠。 | 修改連接埠。 |
| `profiling.port and ... are both ...` | pprof 監聽器與其他監聽器使用了同一個連接埠。 | 將 `[profiling].port` 改成其他監聽器都未使用的連接埠。 |
| 環境變數中的設定沒有生效 | 變數名稱包含句點、雙底線或拼寫錯誤。 | 以單一底線連接路徑，例如 `MS_META_DATABASE_DSN`。 |

## 登入

| 現象 | 原因 | 解決方式 |
|---|---|---|
| `admin@example.com` 加 `admin` 遭拒 | 資料庫中已有使用者，root 帳號不會再次建立；或 `root_email` 與 `root_password` 為空。 | 使用既有帳號登入。若要建立 root 帳號，請設定這兩項並對空資料庫啟動。 |
| 收不到密碼重設郵件 | 沒有設定 SMTP 或 `http.external_url`，請求會被接受，但不會寄送任何內容。 | 設定 `[notify.smtp].host` 與 `[http].external_url`。 |
| 指令碼登入後傳送 `Authorization: Bearer` 得到 `401` | 登入只會為 Web 介面寫下工作階段 Cookie，不會傳回 Token；該請求標頭只接受 API Token。 | 為指令碼簽發 API Token，參見 [API Token](/zh-Hant/identity/tokens)。 |
| Web 介面每天都要求重新登入 | 登入工作階段會在 `[auth].session_ttl_secs`（24 小時）之後結束。 | 調大 `[auth].session_ttl_secs`。 |

## 傳送資料

| 現象 | 原因 | 解決方式 |
|---|---|---|
| `401` | Token 缺少或無效，或請求標頭中帶的是登入工作階段的 Token。 | 傳送 `Authorization: Bearer <token>`，使用預設接入 Token 或服務帳號 Token。 |
| `403` | Token 沒有 `logs.write` 權限，例如將 RUM Client Token 傳送到接入路徑。 | 使用具備 `logs.write` 權限的 Token。 |
| `413` | 請求主體超過端點的上限：原生 JSON 接入 16 MiB，其他端點 2 MiB。 | 傳送更小的批次，並將代理的限制調到不低於端點的上限。 |
| OTLP over HTTP 端點傳回 `400` | 傳送端壓縮了請求主體。 | 在 OpenTelemetry Collector 匯出端設定 `compression: none`。 |
| OTLP over HTTP 端點傳回 `404` | 匯出端的 endpoint 缺少 `/api` 基礎路徑，請求被傳送到 `/v1/logs`。 | 使用 `http://host:5080/api` 作為 OTLP endpoint。 |
| `429` 並帶有 `Retry-After` | 觸發了 `router` 角色對該組織的速率限制。 | 降低傳送速率，或調高 `[router.rate_limit]`。 |
| 原生 JSON 傳回 `rejected` 記錄 | 欄位值與資料流的 schema 不一致，例如 `type mismatch on field level: expected Utf8, got Number`，回應會按下標列出原因。`int64` 欄位收到帶小數的數字不在此列，欄位會變成 `float64`。 | 傳送資料流中該欄位既有的類型。 |
| `400` 並提示 `event #1 must be a JSON object` | 陣列中包含不是 JSON 物件的元素，整個請求都會遭拒。 | 傳送由物件組成的陣列。 |
| Promtail 或 Grafana Alloy 無法推送 | Loki 端點只解碼 JSON，而這些傳送端使用 snappy 壓縮的 protobuf。 | 改用 OpenTelemetry Collector、Vector 或 Fluent Bit 傳送。 |
| 記錄已接收但查不到 | 查詢使用了其他資料流名稱或類型，或時間範圍將它們排除在外。 | 檢查資料流名稱與訊號類型，時間戳記問題見下一節。 |

## 資料缺失或異常

- **時間戳記。** `_timestamp` 是自 Unix 紀元起的微秒數。以秒、毫秒或奈秒表示的值，會把事件放到錯誤的年份或遙遠的未來，對近期時間的查詢會找不到它們。省略 `_timestamp` 則使用伺服器端接收時間。
- **時間範圍。** 涵蓋時間較長的查詢會轉為非同步工作。互動式查詢請使用有界的 `timeRange`，參見[查詢](/zh-Hant/query#時間範圍與非同步工作)。
- **保留期。** 超過資料流自身保留期的資料會被刪除；沒有個別設定保留期的資料流，會依 **設定 → 資料保留** 中的平台預設值處理。
- **訊號類型。** 資料流由名稱和類型共同識別，`default` 可以同時存在於日誌、指標和追蹤類型下。

## 查詢

| 現象 | 原因 | 解決方式 |
|---|---|---|
| 回應為 `202`，並帶有 `jobId` 與 `monitor` 路徑 | 估算規模達到 `[querier].auto_async_threshold_rows`，查詢會以非同步搜尋工作執行。在預設設定下，對應約 13.9 小時或更長的時間範圍。 | 請求 `monitor` 路徑直到工作完成，再取得其 `/results`；或縮小時間範圍，或傳送 `Prefer: respond-sync`，參見[查詢](/zh-Hant/query#時間範圍與非同步工作)。 |
| Flight SQL 用戶端無法連線 | `[flight_sql]` 預設為關閉。 | 設定 `enabled = true`，開放 `5083` 連接埠，並使用 API Token 驗證。 |

## 維運

| 現象 | 原因 | 解決方式 |
|---|---|---|
| `GET /api/v1/healthz` 傳回 `503` | 物件儲存無法連線，回應主體中帶有 `reason`。 | 修復物件儲存的連線。 |
| WAL 目錄持續增長 | 寫入失敗，通常是物件儲存無法連線。 | 修復物件儲存，intake 隨後會寫入積壓的資料。 |
| Intake 傳回 `429` 與 `intake buffer memory limit exceeded` | 處理程序的 buffer 佔用超過 `[intake].max_buffer_memory_size`，通常是因為寫入持續失敗。 | 從 `intake flush failed` 日誌中找出原因，修復物件儲存或資料庫。永遠無法發布的資料列不再佔用這個額度（見下面兩列）。原生 JSON 接入的這個回應帶有 `Retry-After`，請依其時間重試。 |
| 日誌出現 `dataset no longer exists; buffered rows discarded` | 資料流被刪除，或被刪除後又重新建立，而它的資料列還在 buffer 裡。這些資料列無處可去，intake 會丟棄它們並歸還記憶體。計數器 `intake_flush_errors_total` 會以 `stream_gone` 或 `dataset_gone` 兩個 step 記錄每次丟棄。 | 無須處理。若資料重要，請重新傳送。 |
| 寫入傳回 `503` 並帶有 `fenced by a newer writer epoch` | 另一個處理程序以同一個 `[node].id` 發布了同一個資料集。遭柵欄的處理程序無法發布資料，會丟棄記憶體中的資料列，並拒絕寫入該資料集，它的 WAL 會保留在磁碟上。計數器 `intake_flush_errors_total` 會以 `writer_fenced` 這個 step 記錄柵欄。 | 為每個處理程序設定唯一的 `[node].id`，並重新啟動遭柵欄的那個處理程序。參見[分角色部署](/zh-Hant/deployment/role-based)。 |
| 排程 PDF 或 PNG 報告失敗 | 沒有 Chrome，或 `[scheduled_reports.renderer].base_url` 無法存取網頁介面。 | 使用內建 Chromium 的發行映像檔，並將 `base_url` 設為節點可存取的網頁介面位址。 |
| 接入片段顯示了錯誤的主機 | 位於代理後方時 `http.external_url` 為空。 | 將 `[http].external_url` 設為對外位址並重新啟動。 |
| 查詢傳回 `503` 與 `no querier node is available` | 沒有具備 `querier` 角色且心跳夠新的節點。 | 啟動 `querier` 節點，並確認 router 能存取它的 `advertise_addr`。參見[分角色部署](/zh-Hant/deployment/role-based#叢集成員)。 |
| 經 router 寫入傳回 `503` 與 `no intake node is available` | 沒有具備 `intake` 角色且心跳夠新的節點。 | 啟動 `intake` 節點，並檢查它的 `advertise_addr`。參見[分角色部署](/zh-Hant/deployment/role-based#叢集成員)。 |
| 請求傳回 `503` 與 `no metadata database connection` | 節點等了 10 秒仍未取得 PostgreSQL 連線：PostgreSQL 過載或無法連線，或者 `[meta_database].max_connections` 個連線都在使用中。 | 重試請求。持續出現時，先檢查 PostgreSQL 的負載與連線能力；PostgreSQL 閒置時，依負載調大 `[meta_database].max_connections`，且不超過 PostgreSQL 的 `max_connections`。 |
| 無法從主機存取 OTLP gRPC 連接埠 | Compose 檔案沒有發布 `4317` 連接埠。 | 新增 `4317:4317` 對應。 |
