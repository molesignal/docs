Todo sinal entra no MoleSignal pela API de ingestão. A página **Fonte de dados** na interface web gera o endpoint, o token e o trecho de configuração para cada origem. Os mesmos protocolos podem ser configurados manualmente.

## Página Fonte de dados

Abra **Fonte de dados** para integrar uma origem:
1. Pesquise no catálogo ou filtre-o por categoria: **Recomendado**, **Infraestrutura**, **Nuvem**, **Bancos de dados**, **Mensageria**, **Apps e linguagens**, **Segurança** e **Personalizado**. As abas de sinais (**Logs**, **Métricas**, **Rastreamentos**, **Perfis**) restringem ainda mais a lista.
2. Selecione uma origem, como Kubernetes, um host Linux, AWS, um SDK do OpenTelemetry ou RUM para Web.
3. Siga as três etapas do guia:
   - **Endpoint e token** mostra para onde enviar os dados e o token para autenticação. **Mostrar token** revela o token, com o escopo, o espaço de trabalho e a validade. Para uma origem RUM, escolha primeiro o **Aplicativo RUM**: o token de cliente aparece assim que o aplicativo é escolhido.
   - **Configurar a origem** mostra comandos e configuração com o endpoint e o token reais já preenchidos.
   - **Verificar se os dados estão chegando** verifica o receptor e, depois, procura dados recebidos na última hora. **Verificar conexão** verifica imediatamente, e os números são atualizados a cada 30 segundos.
4. Leia o resultado da verificação:
   - **Dados detectados**: dados chegaram na última hora, e os sinais da origem estão saudáveis. **Ver dados recebidos** abre os dados, e **Criar pipeline** inicia um pipeline para eles.
   - **O receptor está funcionando, mas os dados precisam de atenção**: o receptor responde, mas não chegaram dados, ou nem todos os sinais estão saudáveis. Verifique a implantação ou aguarde o próximo lote.
   - **Falha na verificação**: não foi possível verificar o receptor. **Possíveis causas** lista um coletor que não está em execução, um token inválido ou expirado e uma rede ou proxy que bloqueia o endpoint.

O endpoint vem de `http.external_url` quando definido e, caso contrário, do endereço do navegador. Defina `http.external_url` atrás de um proxy reverso para que os trechos gerados apontem para o endereço público. Consulte [Configuração](/pt-BR/configuration).

## Tokens de ingestão

Remetentes se autenticam com um token bearer: `Authorization: Bearer <token>`. Um remetente que só consegue fazer autenticação Basic, como a exportação remote write do Prometheus gerenciado de um provedor de nuvem, coloca o Token de API na senha de `Authorization: Basic` com qualquer nome de usuário. Outras credenciais Basic são ignoradas, então um proxy reverso que solicita as próprias credenciais continua funcionando. Um remetente Splunk HEC apresenta o token como `Authorization: Splunk <token>`.

| Token | Permissão | Criado por | Uso |
|---|---|---|---|
| Token de ingestão padrão | `logs.write`, `metrics.write`, `traces.write`, `profiles.write` e `apm.deploy` somente: a política **Ingestão de dados** | Página Fonte de dados, ou `GET /api/v1/me/api-tokens/default` | Coletores, agentes e exportadores de SDK que enviam logs, métricas e rastreamentos, e pipelines que [relatam implantações](/pt-BR/apm/deployments#report-deployments-from-ci). Não expira. |
| Token de cliente RUM | `rum.write` somente, vinculado a um aplicativo | Página Fonte de dados para origens de RUM para Web e RUM para dispositivos móveis, ou `GET /api/v1/auth/tokens/rum?applicationId=<id>` | Código para navegador e dispositivos móveis. O token é visível para os usuários finais. |
| Token pessoal ou de conta de serviço | O que o membro ou a conta de serviço pode fazer, limitado pelo escopo | **Configurações da conta → Tokens de API**, ou **Identidade e acesso → Tokens de API** para contas de serviço | Automação, scripts e clientes MCP. |

Use o token de ingestão padrão, ou um token de conta de serviço que siga a política **Ingestão de dados**, para remetentes que operam continuamente. Revogue um token em **Configurações da conta → Tokens de API** ou **Identidade e acesso → Tokens de API** para interrompê-lo imediatamente. Uma sessão de login da interface web não pode enviar dados: ela fica em cookies do navegador, e o cabeçalho `Authorization` não a aceita.

A página **Fonte de dados** cria um token de cliente RUM quando um ID de aplicativo é informado. Um ID de aplicativo contém de 1 a 128 caracteres entre `A-Z`, `a-z`, `0-9`, `.`, `_`, `:` e `-`. Use o mesmo ID como `applicationId` no SDK. Consulte [SDK RUM para navegador](/pt-BR/rum/browser-sdk).

## Endpoints e protocolos

| Protocolo | Endpoint | Remetentes compatíveis | Stream de destino |
|---|---|---|---|
| HTTP JSON nativo | `POST /api/v1/intake/{logs,metrics,traces}/{stream}` | `curl`, código da aplicação, sink `http` do Vector, output `http` do Fluent Bit | O segmento de caminho `{stream}` |
| OTLP sobre HTTP | `POST /api/v1/logs`, `/api/v1/metrics`, `/api/v1/traces` | SDKs do OpenTelemetry e o Collector | Cabeçalho `stream-name`, caso contrário `default` |
| OTLP sobre gRPC | `:4317` | SDKs do OpenTelemetry e o Collector | Metadados `stream-name`, caso contrário `default` |
| Prometheus remote_write | `POST /api/v1/prometheus/api/v1/write` | Prometheus, VictoriaMetrics, exportações de Prometheus gerenciado na nuvem, qualquer remetente remote_write v1 | Cabeçalho `stream-name`, caso contrário `?stream=`, caso contrário `default` |
| `_bulk` do Elasticsearch | `POST /api/v1/_bulk` | Filebeat, Logstash, sink `elasticsearch` do Vector | `_index` de cada ação, caso contrário cabeçalho `stream-name`, caso contrário `default` |
| Splunk HEC | `POST /api/v1/services/collector/event`, `/api/v1/services/collector/raw` | CLS do Tencent Cloud, outputs Splunk do Vector e do Fluent Bit, encaminhadores de SIEM | `index` de cada evento, caso contrário `?index=`, caso contrário cabeçalho `stream-name`, caso contrário `default` |
| Loki push (JSON) | `POST /api/v1/loki/api/v1/push` | Remetentes que conseguem enviar o formato JSON do Loki via POST | Cabeçalho `stream-name`, caso contrário `default` |
| Amazon Data Firehose, push do Google Cloud Pub/Sub, barramentos de eventos na nuvem, Cloudflare Logpush, Heroku | `/api/v1/_kinesis_firehose`, `/api/v1/_gcp_pubsub`, `/api/v1/_cloud_events`, `/api/v1/_cloudflare`, `/api/v1/_heroku` | CloudWatch Logs e CloudWatch Metric Streams via Firehose, Cloud Logging via Pub/Sub, remetentes de EventBridge, Event Grid e CloudEvents, Cloudflare, Heroku | Configurado no conector. Consulte [Conectores](/pt-BR/connectors). |

Todos os endpoints, exceto os conectores de push, exigem um token bearer com a permissão de escrita do sinal: `logs.write`, `metrics.write`, `traces.write` ou `profiles.write`. A organização vem do token e nunca aparece em uma URL.

### Limites que afetam os remetentes

- **Tamanho da requisição.** A ingestão JSON nativa e os conectores de push aceitam corpos de requisição de até 16 MiB, e o Firehose de até 64 MiB, contados após a descompressão; os demais endpoints de ingestão aceitam até 2 MiB. Um corpo maior é rejeitado com `413`. Mantenha os lotes abaixo desse tamanho.
- **Compactação.** O OTLP sobre HTTP não aceita corpos de requisição compactados e responde `400`. Desative a compactação no remetente; o exporter `otlphttp` do OpenTelemetry Collector compacta com gzip por padrão e precisa de `compression: none`. A ingestão JSON nativa, o `_bulk` do Elasticsearch, o Loki push e os conectores de push aceitam `Content-Encoding: gzip`.
- **Codificação do Loki.** Apenas o formato JSON de requisição é decodificado. O Promtail e o Grafana Alloy enviam protobuf compactado com snappy por padrão e não conseguem enviar para este endpoint.
- **Limite de taxa.** O papel `router` limita as requisições por organização e responde `429` com um cabeçalho `Retry-After`. Um nó `standalone` não aplica esse limite. Consulte [Implantação baseada em papéis](/pt-BR/deployment/role-based#limitação-de-taxa).
- **Eventos recusados.** Um evento com um valor que não se ajusta ao tipo do seu campo no stream é recusado isoladamente, e o restante da requisição é gravado. Números com fração em um campo `int64` não são recusados: o campo passa a ser `float64` (consulte [Esquema e campos](/pt-BR/streams#esquema-e-campos)). Cada endpoint informa o que recusou: JSON nativo em `rejected` e `errors`, OTLP em `partialSuccess`, `_bulk` do Elasticsearch como itens com status `400`, Splunk HEC com código `6`, e Prometheus remote_write e Loki push com `400`. Os remetentes não os repetem. Os conectores de push respondem com sucesso, já que as plataformas reenviariam a requisição inteira, e o conector informa o que foi recusado.
- **Streams de plataforma.** Os [streams de plataforma](/pt-BR/streams#fluxos-da-plataforma), como `_molesignal` para a telemetria do próprio serviço e `_audit` para a trilha de auditoria, são gravados apenas pelo MoleSignal e rejeitam a ingestão pública com `403`.

## Streams e esquema

Um stream é criado na primeira gravação, e o esquema evolui conforme novos campos aparecem. Um stream é identificado pelo nome e pelo tipo de sinal, então `default` pode existir para logs, métricas e traces ao mesmo tempo. Consulte [Streams](/pt-BR/streams).

Todo evento tem um timestamp em microssegundos desde a época Unix. O JSON nativo e o `_bulk` do Elasticsearch leem o campo `_timestamp`. Um evento sem `_timestamp` recebe o horário em que o servidor o aceitou.

## HTTP JSON nativo

Envie via POST um array de registros para `/api/v1/intake/{logs,metrics,traces}/{stream}`:

```bash
curl -X POST http://localhost:5080/api/v1/intake/logs/app \
  -H "authorization: Bearer $MS_TOKEN" \
  -H 'content-type: application/json' \
  -d "[{\"_timestamp\":$(date +%s)000000,\"level\":\"error\",\"msg\":\"db pool exhausted\",\"trace_id\":\"abc123\"}]"
```

A resposta informa quantos registros foram aceitos e recusados, com um motivo por índice recusado:

```json
{"accepted":1,"rejected":0,"errors":[]}
```

## OpenTelemetry

Aponte um SDK ou Collector do OpenTelemetry para o caminho base `/api`. O exporter acrescenta `/v1/logs`, `/v1/metrics` e `/v1/traces`, que mapeiam para `/api/v1/logs`, `/api/v1/metrics` e `/api/v1/traces`.

<Tabs>
  <Tab title="OTLP sobre HTTP">
    Variáveis de ambiente do SDK:

    ```bash
    export OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf
    export OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:5080/api
    export OTEL_EXPORTER_OTLP_HEADERS="authorization=Bearer ${MS_TOKEN}"
    ```

    Collector do OpenTelemetry:

    ```yaml
    exporters:
      otlphttp/molesignal:
        endpoint: http://localhost:5080/api
        compression: none
        headers:
          authorization: "Bearer ${env:MS_TOKEN}"
    ```

    Envie protobuf (`application/x-protobuf`), a codificação padrão dos SDKs e do Collector. Logs, métricas e traces também aceitam JSON (`application/json`). Adicione um cabeçalho `stream-name` para selecionar um stream diferente de `default`. O cabeçalho se aplica a todo sinal enviado por esse exporter.
  </Tab>
  <Tab title="OTLP sobre gRPC">
    O receptor gRPC do OTLP escuta na porta `4317` e atende aos serviços de logs, métricas, traces e profiles. Ele não termina TLS. Termine o TLS à frente dele para o tráfego que sai de uma rede confiável.

    ```bash
    export OTEL_EXPORTER_OTLP_PROTOCOL=grpc
    export OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4317
    export OTEL_EXPORTER_OTLP_HEADERS="authorization=Bearer ${MS_TOKEN}"
    ```

    Collector do OpenTelemetry:

    ```yaml
    exporters:
      otlp/molesignal:
        endpoint: localhost:4317
        tls:
          insecure: true
        headers:
          authorization: "Bearer ${env:MS_TOKEN}"
    ```

    Remova `insecure: true` quando um proxy que termina TLS estiver à frente da porta. A porta `5082` é a porta gRPC interna do cluster e não é um receptor OTLP.
  </Tab>
</Tabs>

As métricas OTLP são armazenadas como um evento por ponto de dados. Consulte o [contrato de armazenamento de métricas](/pt-BR/query#campos-de-métricas-otlp) para os campos armazenados.

## Prometheus remote_write

Adicione o MoleSignal como destino de remote write no `prometheus.yml`:

```yaml
remote_write:
  - url: http://localhost:5080/api/v1/prometheus/api/v1/write
    authorization:
      credentials: "${MS_TOKEN}"
```

Um stream de métricas contém as métricas de uma origem, então dê a cada servidor Prometheus o seu próprio stream com o cabeçalho `stream-name` (`headers:` na entrada `remote_write`); sem ele, as amostras vão para `default`. Um remetente que não consegue definir cabeçalhos nomeia o stream na URL, como em `/api/v1/prometheus/api/v1/write?stream=aliyun`. Cada amostra se torna uma linha cujo `metric_name` é o seu `__name__`. Os demais rótulos se tornam campos, e um rótulo com o nome de um campo de métrica, como `metric_name`, é mantido como `exported_<name>`. Histogramas nativos e metadados de métricas são ignorados, e os exemplares são armazenados junto às amostras.

## Bulk do Elasticsearch

Remetentes que falam o protocolo bulk do Elasticsearch funcionam sem dependência de Loki ou OTLP:

```bash
curl -X POST http://localhost:5080/api/v1/_bulk \
  -H "authorization: Bearer $MS_TOKEN" \
  -H 'content-type: application/x-ndjson' \
  --data-binary $'{"index":{"_index":"app"}}\n{"level":"info","msg":"hello"}\n'
```

O `_index` de cada ação seleciona o stream de destino. Sem ele, aplica-se o cabeçalho `stream-name` e, em seguida, `default`.

## Loki push

O endpoint aceita o formato JSON de requisição do Loki:

```json
{"streams":[{"stream":{"service":"checkout","level":"error"},"values":[["1700000000000000000","payment failed"]]}]}
```

Os rótulos se tornam campos, a linha de log se torna o campo `message` e o timestamp em nanossegundos é convertido para microssegundos. A resposta é `204`. Selecione o stream de destino com o cabeçalho `stream-name`.

## Splunk HEC

Remetentes que falam o protocolo Splunk HTTP Event Collector, como o Tencent Cloud CLS enviando para o Splunk ou as saídas Splunk do Vector e do Fluent Bit, podem enviar para o MoleSignal sem alterações. Forneça `https://molesignal.example.com/api/v1` como endereço do HEC e um API Token que possa gravar logs como token do HEC, enviado como `Authorization: Splunk <token>`.

| Endpoint | Corpo |
|---|---|
| `POST /api/v1/services/collector/event`, também `/services/collector` | Objetos JSON um após o outro, cada um `{"time", "host", "source", "sourcetype", "index", "event", "fields"}` |
| `POST /api/v1/services/collector/raw` | Texto, um evento de log por linha; `host`, `source`, `sourcetype` e `index` vêm da consulta |
| `GET /api/v1/services/collector/health` | Responde `{"text":"HEC is healthy","code":17}` sem token |

Um `event` que é um objeto JSON fornece os campos do log; qualquer outro `event` se torna `message`. `fields`, `host`, `source` e `sourcetype` se tornam campos, e `time`, em segundos, se torna o horário. `index` nomeia o fluxo, caso contrário o parâmetro de consulta `index`, caso contrário o cabeçalho `stream-name`, caso contrário `default`. A resposta é `{"text":"Success","code":0}`, ou os próprios códigos de erro do HEC com `400`. Quando um fluxo recusa eventos porque um valor não se ajusta ao tipo do seu campo, os outros eventos são gravados e a resposta é o código `6`, com a posição do primeiro evento recusado no corpo como `invalid-event-number` e o motivo em `text`. A confirmação do indexador não é oferecida.
