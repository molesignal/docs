Todos os sinais entram no MoleSignal pela API de ingestão. A página **Fonte de dados** na interface web gera o endpoint, o token e o trecho de configuração de cada origem. Os mesmos protocolos podem ser configurados manualmente.

## Página Fonte de dados

Abra **Fonte de dados** para integrar uma origem:

1. Pesquise no catálogo ou filtre por categoria: **Recomendado**, **Infraestrutura**, **Nuvem**, **Bancos de dados**, **Mensageria**, **Apps e linguagens**, **Segurança** e **Personalizado**. As abas de sinais (**Logs**, **Métricas**, **Rastreamentos**, **Perfis**) restringem ainda mais a lista.
2. Selecione uma origem como Kubernetes, um host Linux, AWS, um SDK OpenTelemetry ou Web RUM.
3. Siga as três etapas do guia:
   - **Endpoint e token** mostra para onde enviar dados e o token para autenticação. **Mostrar token** revela o token, com seu escopo, workspace e expiração. Para uma origem RUM, escolha primeiro o **Aplicativo RUM**: o token de cliente aparece assim que o aplicativo for escolhido.
   - **Configurar a origem** mostra comandos e configuração com o endpoint e o token reais já preenchidos.
   - **Verificar se os dados estão chegando** verifica o receptor e depois procura dados recebidos na última hora. **Verificar conexão** verifica imediatamente, e os números são atualizados a cada 30 segundos.
4. Leia o resultado da verificação:
   - **Dados detectados**: os dados chegaram na última hora, e os sinais da origem estão em bom estado. **Ver dados recebidos** abre os dados, e **Criar pipeline** inicia um pipeline para eles.
   - **O receptor está funcionando, mas os dados precisam de atenção**: o receptor responde, mas nenhum dado chegou, ou nem todos os sinais estão em bom estado. Verifique a implantação ou aguarde o próximo lote.
   - **Falha na verificação**: não foi possível verificar o receptor. **Possíveis causas** lista um coletor que não está em execução, um token inválido ou expirado e uma rede ou proxy que bloqueia o endpoint.

O endpoint vem de `http.external_url` quando definido e, caso contrário, do endereço do navegador. Defina `http.external_url` atrás de um proxy reverso para que os trechos gerados apontem para o endereço público. Consulte [Configuração](/pt-BR/configuration).

## Tokens de ingestão

Os remetentes se autenticam com um token bearer: `Authorization: Bearer <token>`. Um remetente que só consegue fazer autenticação Basic, como a exportação remote write do Prometheus gerenciado de um provedor de nuvem, coloca o token de API na senha de `Authorization: Basic` com qualquer nome de usuário. Outras credenciais Basic são ignoradas, então um proxy reverso que pede as próprias credenciais continua funcionando. Um remetente Splunk HEC envia o token como `Authorization: Splunk <token>`.

| Token | Permissão | Criado por | Uso |
|---|---|---|---|
| Token de ingestão padrão | `logs.write`, `metrics.write`, `traces.write`, `profiles.write` e `apm.deploy` apenas: a política **Ingestão de dados** | Página Fonte de dados, ou `GET /api/v1/me/api-tokens/default` | Coletores, agentes e exportadores de SDK que enviam logs, métricas e rastreamentos, e pipelines que [relatam implantações](/pt-BR/apm/deployments#report-deployments-from-ci). Não expira. |
| Token de cliente RUM | `rum.write` apenas, vinculado a um aplicativo | Página Fonte de dados para origens Web RUM e RUM móvel, ou `GET /api/v1/auth/tokens/rum?applicationId=<id>` | Código de navegador e móvel. O token é visível para usuários finais. |
| Token pessoal ou de conta de serviço | O que o membro ou a conta de serviço pode fazer, restrito pelo escopo | **Configurações da conta → Tokens de API**, ou **Identidade e acesso → Tokens de API** para contas de serviço | Automação, scripts e clientes MCP. |

Use o token de ingestão padrão, ou um token de conta de serviço que siga a política **Ingestão de dados**, para remetentes que são executados continuamente. Revogue um token em **Configurações da conta → Tokens de API** ou **Identidade e acesso → Tokens de API** para interrompê-lo imediatamente. Uma sessão de login da interface web não pode enviar dados: ela fica em cookies do navegador, e o cabeçalho `Authorization` não a aceita.

A página **Fonte de dados** cria um token de cliente RUM quando um id de aplicativo é informado. Um id de aplicativo contém de 1 a 128 caracteres de `A-Z`, `a-z`, `0-9`, `.`, `_`, `:` e `-`. Use o mesmo id como `applicationId` no SDK. Consulte [SDK de RUM para navegador](/pt-BR/rum/browser-sdk).

## Endpoints e protocolos

| Protocolo | Endpoint | Remetentes compatíveis | Stream de destino |
|---|---|---|---|
| HTTP JSON nativo | `POST /api/v1/intake/{logs,metrics,traces}/{stream}` | `curl`, código da aplicação, sink `http` do Vector, output `http` do Fluent Bit | O segmento de caminho `{stream}` |
| OTLP sobre HTTP | `POST /api/v1/logs`, `/api/v1/metrics`, `/api/v1/traces` | SDKs e Collector do OpenTelemetry | Cabeçalho `stream-name`, caso contrário `default` |
| OTLP sobre gRPC | `:4317` | SDKs e Collector do OpenTelemetry | Metadado `stream-name`, caso contrário `default` |
| remote_write do Prometheus | `POST /api/v1/prometheus/api/v1/write` | Prometheus, VictoriaMetrics, exportações de Prometheus gerenciado na nuvem, qualquer remetente remote_write v1 | Cabeçalho `stream-name`, caso contrário `?stream=`, caso contrário `default` |
| `_bulk` do Elasticsearch | `POST /api/v1/_bulk` | Filebeat, Logstash, sink `elasticsearch` do Vector | `_index` de cada ação, caso contrário cabeçalho `stream-name`, caso contrário `default` |
| Splunk HEC | `POST /api/v1/services/collector/event`, `/api/v1/services/collector/raw` | Tencent Cloud CLS, outputs Splunk do Vector e do Fluent Bit, encaminhadores SIEM | `index` de cada evento, caso contrário `?index=`, caso contrário cabeçalho `stream-name`, caso contrário `default` |
| Loki push (JSON) | `POST /api/v1/loki/api/v1/push` | Remetentes que conseguem fazer POST do formato JSON do Loki | Cabeçalho `stream-name`, caso contrário `default` |
| Amazon Data Firehose, push do Google Cloud Pub/Sub, barramentos de eventos na nuvem, Cloudflare Logpush, Heroku | `/api/v1/_kinesis_firehose`, `/api/v1/_gcp_pubsub`, `/api/v1/_cloud_events`, `/api/v1/_cloudflare`, `/api/v1/_heroku` | CloudWatch Logs e CloudWatch Metric Streams via Firehose, Cloud Logging via Pub/Sub, remetentes EventBridge, Event Grid e CloudEvents, Cloudflare, Heroku | Configurado no conector. Consulte [Conectores](/pt-BR/connectors). |

Todos os endpoints, exceto os conectores de push, exigem um bearer token com a permissão de escrita do sinal: `logs.write`, `metrics.write`, `traces.write` ou `profiles.write`. A organização vem do token e nunca aparece em uma URL.

### Limites que afetam os remetentes

- **Tamanho da requisição.** A intake JSON nativa e os conectores de push aceitam corpos de requisição de até 16 MiB, e o Firehose de até 64 MiB, contados após a descompressão; os demais endpoints de intake aceitam até 2 MiB. Um corpo maior é rejeitado com `413`. Mantenha os lotes abaixo desse tamanho.
- **Compressão.** O OTLP sobre HTTP não aceita corpos de requisição comprimidos e responde `400`. Desative a compressão no remetente; o exporter `otlphttp` do OpenTelemetry Collector comprime com gzip por padrão e precisa de `compression: none`. A intake JSON nativa, o `_bulk` do Elasticsearch, o Loki push e os conectores de push aceitam `Content-Encoding: gzip`.
- **Codificação do Loki.** Apenas o formato de requisição JSON é decodificado. O Promtail e o Grafana Alloy enviam protobuf comprimido com snappy por padrão e não conseguem enviar para este endpoint.
- **Limite de taxa.** A role `router` limita as requisições por organização e responde `429` com um cabeçalho `Retry-After`. Um nó `standalone` não aplica esse limite. Consulte [Implantação baseada em roles](/pt-BR/deployment/role-based#limitação-de-taxa).
- **Eventos recusados.** Um evento com um valor que não se encaixa no tipo do seu campo na stream é recusado isoladamente, e o restante da requisição é gravado. Números com fração em um campo `int64` não são recusados: o campo passa a ser `float64` (consulte [Schema e campos](/pt-BR/streams#esquema-e-campos)). Cada endpoint informa o que recusou: a JSON nativa em `rejected` e `errors`, o OTLP em `partialSuccess`, o `_bulk` do Elasticsearch como itens com status `400`, o Splunk HEC com código `6`, e o remote_write do Prometheus e o Loki push com `400`. Os remetentes não tentam novamente. Os conectores de push respondem com sucesso, já que as plataformas reenviariam a requisição inteira, e o conector informa o que foi recusado.
- **Streams de plataforma.** As [streams de plataforma](/pt-BR/streams#fluxos-da-plataforma), como `_molesignal` para a telemetria do próprio serviço e `_audit` para a trilha de auditoria, são gravadas apenas pelo MoleSignal e rejeitam a intake pública com `403`.

## Streams e schema

Uma stream é criada na sua primeira escrita, e o schema evolui conforme novos campos aparecem. Uma stream é identificada pelo seu nome e tipo de sinal, então `default` pode existir para logs, métricas e traces ao mesmo tempo. Consulte [Streams](/pt-BR/streams).

Todo evento tem um timestamp em microssegundos desde a época Unix. A JSON nativa e o `_bulk` do Elasticsearch leem o campo `_timestamp`. Um evento sem `_timestamp` recebe o horário em que o servidor o aceitou.

## HTTP JSON nativo

Envie um array de registros para `/api/v1/intake/{logs,metrics,traces}/{stream}`:

```bash
curl -X POST http://localhost:5080/api/v1/intake/logs/app \
  -H "authorization: Bearer $MS_TOKEN" \
  -H 'content-type: application/json' \
  -d "[{\"_timestamp\":$(date +%s)000000,\"level\":\"error\",\"msg\":\"db pool exhausted\",\"trace_id\":\"abc123\"}]"
```

A resposta informa quantos registros foram aceitos e recusados, com um motivo por índice recusado:

```json
{"accepted":1,"rejected":0,"errors":[]}
```

## OpenTelemetry

Aponte um SDK ou Collector do OpenTelemetry para o caminho base `/api`. O exporter acrescenta `/v1/logs`, `/v1/metrics` e `/v1/traces`, que mapeiam para `/api/v1/logs`, `/api/v1/metrics` e `/api/v1/traces`.

<Tabs>
  <Tab title="OTLP sobre HTTP">
    Variáveis de ambiente do SDK:

    ```bash
    export OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf
    export OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:5080/api
    export OTEL_EXPORTER_OTLP_HEADERS="authorization=Bearer ${MS_TOKEN}"
    ```

    OpenTelemetry Collector:

    ```yaml
    exporters:
      otlphttp/molesignal:
        endpoint: http://localhost:5080/api
        compression: none
        headers:
          authorization: "Bearer ${env:MS_TOKEN}"
    ```

    Envie protobuf (`application/x-protobuf`), a codificação padrão dos SDKs e do Collector. Logs, métricas e traces também aceitam JSON (`application/json`). Adicione um cabeçalho `stream-name` para selecionar uma stream diferente de `default`. O cabeçalho se aplica a todos os sinais enviados por esse exporter.
  </Tab>
  <Tab title="OTLP sobre gRPC">
    O receptor OTLP gRPC escuta na porta `4317` e atende os serviços de logs, métricas, traces e profiles. Ele não encerra TLS. Encerre o TLS à frente dele para tráfego que sai de uma rede confiável.

    ```bash
    export OTEL_EXPORTER_OTLP_PROTOCOL=grpc
    export OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4317
    export OTEL_EXPORTER_OTLP_HEADERS="authorization=Bearer ${MS_TOKEN}"
    ```

    OpenTelemetry Collector:

    ```yaml
    exporters:
      otlp/molesignal:
        endpoint: localhost:4317
        tls:
          insecure: true
        headers:
          authorization: "Bearer ${env:MS_TOKEN}"
    ```

    Remova `insecure: true` quando um proxy que encerra TLS estiver à frente da porta. A porta `5082` é a porta gRPC interna do cluster e não é um receptor OTLP.
  </Tab>
</Tabs>

As métricas OTLP são armazenadas como um evento por data point. Consulte o [contrato de armazenamento de métricas](/pt-BR/query#campos-de-métricas-otlp) para os campos armazenados.

## Prometheus remote_write

Adicione o MoleSignal como destino de remote write no `prometheus.yml`:

```yaml
remote_write:
  - url: http://localhost:5080/api/v1/prometheus/api/v1/write
    authorization:
      credentials: "${MS_TOKEN}"
```

Uma stream de métricas contém as métricas de uma fonte, então dê a cada servidor Prometheus a sua própria stream com o cabeçalho `stream-name` (`headers:` na entrada `remote_write`); sem ele, as amostras vão para `default`. Um remetente que não consegue definir cabeçalhos nomeia a stream na URL, como em `/api/v1/prometheus/api/v1/write?stream=aliyun`. Cada amostra se torna uma linha cujo `metric_name` é o seu `__name__`. Outros labels se tornam campos, e um label com nome igual ao de um campo de métrica, como `metric_name`, é mantido como `exported_<name>`. Histogramas nativos e metadados de métricas são ignorados, e os exemplars são armazenados ao lado das amostras.

## Bulk do Elasticsearch

Remetentes que falam o protocolo bulk do Elasticsearch funcionam sem dependência de Loki ou OTLP:

```bash
curl -X POST http://localhost:5080/api/v1/_bulk \
  -H "authorization: Bearer $MS_TOKEN" \
  -H 'content-type: application/x-ndjson' \
  --data-binary $'{"index":{"_index":"app"}}\n{"level":"info","msg":"hello"}\n'
```

O `_index` de cada ação seleciona a stream de destino. Sem ele, o cabeçalho `stream-name` se aplica e, em seguida, `default`.

## Loki push

O endpoint aceita o formato de requisição JSON do Loki:

```json
{"streams":[{"stream":{"service":"checkout","level":"error"},"values":[["1700000000000000000","payment failed"]]}]}
```

Labels se tornam campos, a linha de log se torna o campo `message`, e o timestamp em nanossegundos é convertido para microssegundos. A resposta é `204`. Selecione a stream de destino com o cabeçalho `stream-name`.

## Splunk HEC

Remetentes que falam o protocolo Splunk HTTP Event Collector, como o Tencent Cloud CLS enviando para o Splunk ou as saídas Splunk do Vector e do Fluent Bit, podem enviar ao MoleSignal sem alterações. Forneça a eles `https://molesignal.example.com/api/v1` como o endereço HEC e um API Token que possa gravar logs como o token HEC, enviado como `Authorization: Splunk <token>`.

| Endpoint | Corpo |
|---|---|
| `POST /api/v1/services/collector/event`, também `/services/collector` | Objetos JSON um após o outro, cada um `{"time", "host", "source", "sourcetype", "index", "event", "fields"}` |
| `POST /api/v1/services/collector/raw` | Texto, um evento de log por linha; `host`, `source`, `sourcetype` e `index` vêm da query |
| `GET /api/v1/services/collector/health` | Responde `{"text":"HEC is healthy","code":17}` sem um token |

Um `event` que é um objeto JSON fornece os campos do log; qualquer outro `event` se torna `message`. `fields`, `host`, `source` e `sourcetype` se tornam campos, e `time`, em segundos, se torna o horário. `index` nomeia o stream; caso contrário, o parâmetro de query `index`; caso contrário, o cabeçalho `stream-name`; caso contrário, `default`. A resposta é `{"text":"Success","code":0}`, ou os próprios códigos de erro do HEC com `400`. Quando um stream recusa eventos porque um valor não se encaixa no tipo do campo, os demais eventos são gravados e a resposta é o código `6`, com a posição do primeiro evento recusado no corpo como `invalid-event-number` e o motivo em `text`. A confirmação do indexador não é oferecida.
