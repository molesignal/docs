O Mole Agent gera respostas e atribui uma pontuação a cada uma. As regras pontuam a resposta de imediato, sem usar um modelo. Elas verificam se as ferramentas funcionaram, se a resposta cita evidências, se as consultas são sintaticamente válidas, se a resposta segue o formato solicitado e qual avaliação recebeu. Os avaliadores configurados pontuam uma amostra das respostas com um modelo, seguindo critérios definidos na configuração. Respostas com pontuação baixa, avaliadas como **Não foi útil** ou selecionadas aleatoriamente aguardam revisão. As respostas aprovadas na revisão passam a compor o conjunto de testes de regressão. Antes de um prompt da organização se tornar o padrão, uma verificação usa a nova versão e a versão atual para responder novamente a algumas das perguntas desse conjunto. Um avaliador pontua as respostas das duas versões.

As pontuações vão de 0 a 100. A aba **Qualidade** exibe as pontuações, e o Mole Agent também registra cada uma no stream `_agent_score_traces`.

## Antes de começar

- Para acessar a aba **Qualidade**, é necessário ter a permissão `agent.quality.read`, que os papéis de proprietário e administrador têm por padrão. Esses papéis já podem ler todas as conversas da equipe. As conversas pessoais só entram nos totais, e o conteúdo não fica disponível nessa aba.
- Cada avaliador usa um dos provedores de modelos da organização. Consulte [Mole Agent](/pt-BR/agent#configure-um-provedor-de-modelos). Mesmo sem um avaliador, as regras pontuam todas as respostas.

## O que recebe pontuação

| Fonte | O que é |
|---|---|
| **Conversas da equipe** | Respostas em conversas da equipe. |
| **Conversas pessoais** | Respostas em conversas pessoais. Apenas as regras pontuam essas respostas, que só entram nos totais. |
| **Automações** | A resposta de cada execução de uma automação da organização ou da equipe. Consulte [Automações](/pt-BR/automations). As execuções de automações pessoais são conversas pessoais. |
| **Análises de causa raiz de incidentes** | Análises de causa raiz (RCAs) geradas automaticamente ou sob demanda, além de qualquer RCA que receba uma avaliação. |

O Mole Agent pontua a resposta quando a gera e calcula a pontuação novamente quando a resposta recebe uma avaliação ou quando essa avaliação é removida.

## Regras

As regras usam os dados da resposta e da execução para atribuir uma pontuação de 0 a 100 a cada critério abaixo. A pontuação por regras de uma resposta é a média das pontuações das regras aplicáveis.

| Regra | Pontuação | Aplica-se a |
|---|---|---|
| **Chamadas de ferramentas** | Proporção de chamadas de ferramentas que não falharam. | Respostas que usaram ferramentas. |
| **Evidências** | 0 se a resposta não cita evidências, 50 se nenhuma chamada de ferramenta bem-sucedida sustenta as evidências citadas, 75 se sustenta uma e 100 se sustenta duas ou mais. | Respostas no formato solicitado que usaram ferramentas. |
| **Consultas** | Proporção de consultas SQL e PromQL sintaticamente válidas nas chamadas de ferramentas. | Respostas que usaram ferramentas para executar consultas. |
| **Formato** | 100 se a resposta segue o formato solicitado. | Todas as respostas de conversas, exceto consultas geradas. |
| **Conclusão** | 100 para uma resposta concluída, 50 para uma execução de automação que exigiu intervenção humana e 0 se a resposta ou a execução falhou, foi interrompida ou ficou vazia. | Todas as respostas. |
| **Avaliação** | 100 para **Útil** e 0 para **Não foi útil**. Em uma RCA, basta uma avaliação **Não foi útil**. | Respostas que receberam uma avaliação. |

## Avaliadores

O avaliador atribui uma nota de 1 a 5 à resposta com base nos critérios definidos e justifica a nota em uma ou duas frases. As notas correspondem a pontuações de 0, 25, 50, 75 ou 100. O avaliador lê a pergunta, os resultados das ferramentas e a resposta. No caso de uma RCA, lê os fatos do incidente e a própria análise.

- O avaliador pontua a porcentagem configurada de novas respostas. A amostragem é determinística por resposta: repetir a seleção produz a mesma amostra.
- O avaliador sempre pontua respostas avaliadas como **Não foi útil**, a menos que já tenha pontuado essas respostas.
- Se a pontuação ficar abaixo do limite de revisão, o avaliador pontua a resposta mais uma vez e usa a média das duas pontuações.
- O avaliador nunca pontua conversas pessoais.
- O avaliador escreve as justificativas no idioma da interface usado no último salvamento da configuração.
- As chamadas de modelo dos avaliadores consomem o orçamento diário de tokens da organização e aparecem como **Pontuação de qualidade** no detalhamento do uso por fonte. Enquanto o orçamento estiver esgotado, os avaliadores não pontuam novas respostas.

Todos os avaliadores seguem inicialmente as instruções do prompt integrado **Avaliador de respostas** (finalidade `evaluation`). Para substituir esse prompt na organização, acesse **Configurações → Gerenciamento de prompts**. Independentemente das instruções do prompt, o avaliador retorna a pontuação em um formato fixo.

Se pelo menos um avaliador pontuar a resposta, a pontuação final será a média das pontuações dos avaliadores. Caso contrário, vale a pontuação por regras.

## A aba Qualidade

Abra **Mole Agent → Qualidade**. **Visão geral** e **Respostas** mostram os dados dos últimos 7, 30 ou 90 dias, de uma fonte ou de todas elas.

| Tela | O que mostra |
|---|---|
| **Visão geral** | As respostas pontuadas, as médias das notas das regras e dos avaliadores, as respostas marcadas como úteis ou não úteis e quantas aguardam revisão. Abaixo: a pontuação por dia, cada regra e as respostas por fonte, versão do prompt, Skill e modelo. |
| **Respostas** | As respostas pontuadas, da mais recente à mais antiga. Use **Apenas notas baixas** para exibir só as que ficaram abaixo do limite para revisão. Abra uma linha para ver a pergunta e a resposta completas, o que cada regra detectou, a nota e a justificativa de cada avaliador e a revisão da resposta. Selecione **Abrir chat** ou **Abrir incidente** para ir ao local em que a resposta foi escrita. |
| **Revisões** | As respostas que aguardam revisão, as aceitas e as rejeitadas. |
| **Lacunas nos dados** | O que as chamadas de ferramentas feitas para gerar as respostas indicam que falta nos dados. Consulte [Lacunas nos dados](#lacunas-nos-dados). |
| **Simulações** | Incidentes resolvidos que o agente investiga novamente e avalia com base na causa raiz conhecida. Consulte [Simulações](#simulações). |
| **Avaliadores** | Os avaliadores e as configurações. |

### Revisar respostas

Uma resposta aguarda revisão quando:

| Motivo | Quando |
|---|---|
| **Nota baixa** | A nota de um avaliador continua abaixo do limite para revisão após a segunda avaliação. Se nenhum avaliador pontuar a resposta, vale a nota das regras. |
| **Marcada como não útil** | A pessoa que fez a pergunta marcou a resposta como **Não foi útil**. |
| **Selecionada aleatoriamente** | O sistema selecionou a resposta com base no percentual de **Revisão aleatória** para verificar se as notas são confiáveis. |

Cada resposta passa por revisão uma única vez. Abra a resposta, descreva em **Observação** o que está errado e o que uma boa resposta deve acertar e selecione:

- **Aceitar**: a resposta está errada. Ela entra no conjunto de testes de regressão, e o avaliador recebe a observação quando uma verificação de prompt responde à pergunta novamente.
- **Rejeitar**: a resposta está adequada.

### Avaliadores e configurações

Em **Avaliadores**, selecione **Novo avaliador** para abrir o formulário:

| Campo | Descrição |
|---|---|
| **Nome** | Único na organização. |
| **Critérios de avaliação** | O que uma boa resposta deve fazer e o que reduz a nota, em até 4000 caracteres. O campo já vem preenchido com critérios iniciais. |
| **Respostas** | Chats de equipe, automações e análises de causa raiz de incidentes (RCAs). |
| **Amostra** | Percentual de novas respostas que o avaliador pontua, de 0 a 100. |
| **Provedor do modelo** e **Modelo** | Deixe os campos em branco para usar o primeiro provedor disponível na organização e o modelo padrão desse provedor. |
| **Temperatura** | De 0 a 1. Use 0 para manter as notas estáveis. |
| **Ativado** | Um avaliador desativado não pontua respostas. |

Cada organização pode ter até 10 avaliadores. Excluir um avaliador não apaga as notas que ele atribuiu.

Configurações abaixo dos avaliadores:

| Configuração | Padrão | Descrição |
|---|---|---|
| **Limite para revisão** | 60 | Respostas com nota abaixo desse limite aguardam revisão. |
| **Revisão aleatória** | 0 | Percentual das demais respostas que o sistema seleciona para revisão. |
| **Antes de definir um prompt como padrão** | Verificar e pedir confirmação novamente se o resultado piorar | Consulte a seção abaixo. |

### Lacunas nos dados

Ao pontuar uma resposta com regras, o sistema também analisa as chamadas de ferramentas para identificar o que elas revelam sobre os dados disponíveis para o Mole Agent. Isso não muda nenhuma nota: a lacuna aponta um problema nos dados, não na resposta. **Lacunas nos dados** resume as lacunas dos últimos 7, 30 ou 90 dias.

| Tipo | Quando ocorre | Como corrigir |
|---|---|---|
| **Onde estão os dados** | O agente consultou o mesmo fluxo pelo menos 3 vezes e a maioria das consultas não retornou resultados ou falhou, ou o agente consultou a estrutura pelo menos 3 vezes (esquemas e listas de fluxos, nomes e rótulos de métricas). | Registre onde estão os dados de cada serviço e como filtrá-los: nas fontes de dados do catálogo de serviços ou no arquivo `MOLE.md` da base de conhecimento. |
| **Um nome por serviço** | Havia dados de um serviço nas métricas ou no APM, mas uma consulta de logs ou traces com o mesmo nome de serviço não retornou resultados, e nenhuma outra consulta ao mesmo fluxo encontrou o serviço. | Use o mesmo nome para o serviço em todos os sinais (`service.name`) ou registre os outros nomes como aliases no catálogo de serviços. |
| **Resumo dos dados** | O agente buscou logs ou séries brutas pelo menos 2 vezes, retornando muitas linhas a cada vez, sem usar **Analisar padrões de logs** ou **Analisar tendência de métrica**. | Verifique se os conjuntos de ferramentas dos perfis de agente da organização incluem essas ferramentas. |

A tela agrupa as lacunas recorrentes por fluxo e serviço e mostra quantas respostas identificaram cada lacuna e quando ela apareceu pela última vez. Abra uma resposta na lista da lacuna para ver as notas. Os chats pessoais entram apenas nos totais: a tela não exibe as consultas desses chats.

### Simulações

Em um simulado, o Mole Agent investiga novamente um incidente resolvido como se ele estivesse acontecendo e recebe uma nota com base na causa raiz identificada após o incidente. Execute todos os simulados novamente após mudar o modelo, um prompt ou as ferramentas para verificar se as investigações melhoraram.

**Novo simulado** lista os incidentes resolvidos nos últimos 180 dias cujo post-mortem informa uma causa raiz (na seção **Causa raiz**). A causa raiz do post-mortem serve de referência, a menos que outra seja informada. Em **Outro incidente**, informe o ID do incidente e digite a causa raiz. Cada incidente tem um simulado, e cada organização mantém até 100.

Uma execução do simulado:

- Usa as permissões da conta que inicia a execução, que precisa ter acesso de leitura ao incidente. A execução não exige supervisão, tem acesso somente de leitura e dura até 10 minutos.
- Recebe os dados disponíveis no momento do disparo (resumo, gravidade, serviços, rótulos e a consulta que disparou o incidente) e o guia de investigação da regra de alerta. Analisa o período de uma hora antes do início do incidente até meia hora depois.
- Não tem acesso às descobertas nem às ações posteriores ao incidente: observações, linha do tempo, RCA, post-mortem, tickets, aprovações e incidentes semelhantes.
- Ocorre em um chat que não aparece na lista de chats. Na execução, selecione **Abrir investigação** para abrir o chat em modo somente leitura.

Ao fim da investigação, um modelo compara a causa raiz encontrada com a referência e atribui uma nota de 1 a 5, convertida para uma escala de 0 a 100. A justificativa aparece no idioma da interface da conta que iniciou a execução. O sistema usa o modelo do primeiro avaliador ativado ou, se não houver nenhum, o primeiro provedor de modelos da organização. As chamadas ao modelo contam para o orçamento diário de tokens como **Pontuação de qualidade**. Se a execução falhar, for interrompida ou não gerar resposta, o sistema informa o motivo e não atribui nota.

**Executar** inicia um simulado. **Executar todos novamente** inicia os simulados que não estão em execução, até 50 por vez. Para criar, executar e excluir simulados, é necessário ter a permissão `agent.quality.manage`.

## Verifique um prompt antes de defini-lo como padrão

Ao selecionar **Definir como padrão** em um prompt da organização para chats (**Instrução do sistema**) ou análises de causa raiz de incidentes (**Análise de causa raiz**), a configuração da organização determina o que acontece:

| Configuração | Quando o prompt não passou por uma verificação ou teve pontuação inferior |
|---|---|
| **Verificar e pedir confirmação se a pontuação cair** | A caixa de diálogo oferece as opções **Executar verificação** e **Definir como padrão mesmo assim**. |
| **Verificar e bloquear se a pontuação cair** | Só é possível definir como padrão um prompt cuja pontuação não caiu na verificação. |
| **Não verificar** | O prompt se torna o padrão imediatamente. |

A verificação usa até 8 respostas: primeiro, as do conjunto de regressão; depois, as que o primeiro avaliador a pontuar essas respostas avaliou mais recentemente. O mesmo modelo gera duas novas respostas para cada pergunta, uma com o prompt padrão atual e outra com a nova versão, sem executar as ferramentas de novo. O modelo recebe a pergunta e os resultados obtidos pelas ferramentas na execução original. Para uma análise de causa raiz, o modelo usa cada versão do prompt para redigir a análise com base nos fatos do incidente. Em seguida, o avaliador pontua cada par. A nova versão recebe **Pior** quando sua média fica mais de 5 pontos abaixo da média do padrão atual, **Melhor** quando fica mais de 5 pontos acima e **Sem piora** nos demais casos. Se for possível comparar menos de 3 respostas, a verificação fica inconclusiva e não impede que o prompt se torne o padrão.

A caixa de diálogo mostra o andamento e, em seguida, o resultado de cada resposta. Cada verificação compara uma versão do prompt com um único padrão. Se o prompt mudar ou outro prompt se tornar o padrão, execute a verificação novamente. As chamadas ao modelo durante a verificação contam como **Pontuação de qualidade**.

Prompts para outras finalidades se tornam o padrão sem verificação. Alterações no prompt que já é o padrão também não passam por verificação. Para verificar uma alteração, salve a versão editada como um novo prompt e defina-o como padrão.

## Pontuações em um fluxo

Cada pontuação também corresponde a uma linha do fluxo interno `_agent_score_traces`, disponível para consulta em **Logs**:

| Campo | Descrição |
|---|---|
| `target_kind`, `target_id` | `chat_answer` com o ID da mensagem ou `incident_rca` com o ID do incidente. |
| `source` | `personal_chat`, `team_chat`, `automation` ou `incident_rca`. |
| `scorer`, `scorer_kind` | `rules` ou o ID do avaliador com `evaluator`. |
| `score`, `samples` | Pontuação média de 0 a 1 e número de avaliações usadas para calculá-la. |
| `tool_success`, `evidence`, `query_validity`, `answer_format`, `completion`, `feedback` | Pontuações de 0 a 1 para as regras aplicáveis. |
| `reason`, `evaluator_model` | Justificativa e modelo do avaliador. |
| `chat_id`, `team_id`, `automation_id`, `user_id`, `prompt_template_id`, `prompt_version`, `prompt_key`, `provider_id`, `model`, `skill`, `skill_version` | Origem da resposta e recursos usados para gerá-la. |

Para receber avisos sobre quedas na qualidade, crie uma [regra de alerta de anomalia](/pt-BR/alerting) para o fluxo, por exemplo, com base na média das pontuações dos avaliadores:

```sql
SELECT avg(score) AS value FROM "_agent_score_traces" WHERE scorer_kind = 'evaluator'
```
