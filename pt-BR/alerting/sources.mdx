Uma fonte de alertas transforma alertas enviados por outro sistema em [incidentes](/pt-BR/alerting/incidents). Ela aciona pessoas por meio de uma [política de escalonamento](/pt-BR/alerting/on-call#políticas-de-escalonamento) e notifica por meio de [políticas de notificação](/pt-BR/notification-channels) da mesma forma que os incidentes de regras, e são resolvidos quando a fonte informa a recuperação. Abra **Alertas → Origens**. A leitura requer `alerts.sources.read`; criar, editar, excluir e substituir tokens requerem `alerts.sources.manage`.

## Tipos de fonte

Cada fonte tem um tipo, que determina em qual formato de remetente o corpo da requisição é interpretado.

| Tipo | Remetente | Um incidente por |
|---|---|---|
| **API** | Scripts, CI e sistemas próprios que chamam a API do MoleSignal | Chave de deduplicação |
| **Alertmanager** | Um receptor de webhook do Prometheus Alertmanager | Grupo de notificação |
| **Grafana** | Um ponto de contato de webhook do Grafana Alerting | Grupo de notificação |
| **Datadog** | A integração Webhooks do Datadog | Monitor; cada grupo de um monitor multi-alerta |
| **PagerDuty** | Uma assinatura de webhook V3 do PagerDuty | Incidente do PagerDuty |
| **Alibaba Cloud CloudMonitor** | Callbacks de alarme de limite e canais de push de assinatura de eventos | Objeto de uma regra de alarme, ou evento do sistema |
| **Tencent Cloud Observability Platform** | Callbacks de API de um modelo de notificação | Uma métrica ou evento de um objeto sob uma política, um por nível em uma política com níveis |
| **Amazon CloudWatch** | Alarmes enviados a um tópico do SNS, por meio da assinatura HTTPS do tópico | Um alarme |
| **Zabbix** | Um tipo de mídia de webhook do Zabbix | Um problema |
| **Azure Monitor** | A ação de webhook de um grupo de ações, no esquema de alerta comum | Um alerta |
| **Google Cloud Monitoring** | Um canal de notificação de webhook, ou o canal do Pub/Sub por meio de uma assinatura push | Um incidente do Monitoring |
| **Huawei Cloud Eye** | Alarmes enviados a um tópico do SMN, por meio da assinatura HTTPS do tópico | Uma regra de alarme em um recurso |
| **E-mail** | Uma caixa de correio IMAP, ou e-mail bruto de um sistema de e-mail já em operação | Uma sequência de e-mails com o mesmo assunto |

Sistemas compatíveis com o webhook do Alertmanager, como o Alertmanager do Thanos, Cortex ou Mimir, usam o tipo **Alertmanager**.

## Criar uma fonte

1. Abra **Alertas → Origens** e clique em **Nova fonte de alertas**.
2. Escolha o **Tipo** e informe um **Nome**.
3. Escolha a **Política de escalonamento**. O padrão é **Por roteamento (padrão)**, o mesmo da área de trabalho de regras: o [roteamento de alertas](/pt-BR/alerting/routing) escolhe a equipe e a política de escalonamento pelas regras de roteamento, pela equipe proprietária do serviço e pelo rótulo de equipe e, caso contrário, pela [política padrão](/pt-BR/alerting/on-call#política-padrão) chamada `default`. Com uma política escolhida, os incidentes passam a usá-la e o roteamento escolhe apenas a equipe. Com **Sem escalonamento, apenas políticas de notificação**, os incidentes ainda abrem e notificam, mas nenhuma política de escalonamento aciona ninguém.
4. Escolha a **Gravidade padrão**, usada quando um alerta não traz uma gravidade própria.
5. Adicione **Rótulos adicionais** se necessário, como `team=payments`. Eles são adicionados a todo incidente que a fonte abre. Um rótulo trazido pelo próprio alerta tem precedência.
6. Clique em **Criar**. A página da fonte abre com uma caixa de diálogo que mostra o token e a configuração com o token preenchido; o Alibaba Cloud CloudMonitor precisa apenas do endereço de ingestão, então a caixa de diálogo mostra o endereço com o token incluído.

<Warning>
  O token é mostrado apenas quando a fonte é criada ou quando o token é substituído. Depois que a caixa de diálogo fecha, só é possível ver o prefixo que começa com `mspat-`. Se o token for perdido, clique em **Substituir token** para obter um novo; o token antigo deixa de funcionar imediatamente.
</Warning>

## Endereço de ingestão e token

Todas as fontes compartilham um único endereço de ingestão. O token indica a qual fonte um alerta pertence:

```text
https://<molesignal-host>/api/v1/intake/alerts
```

Um token tem o formato `mspat-<36>`, o mesmo formato de um Token de API, mas só recebe alertas, e um Token de API não pode receber alertas. O remetente o coloca em um cabeçalho:

```text
Authorization: Bearer <token>
```

Um remetente que não consegue definir cabeçalhos (Alibaba Cloud CloudMonitor, Tencent Cloud Observability Platform, Amazon CloudWatch via SNS, Azure Monitor, Google Cloud Monitoring, Huawei Cloud Eye via SMN) inclui o token no endereço: `https://<molesignal-host>/api/v1/intake/alerts?token=<token>`.

O remetente precisa alcançar este endereço. Quando um firewall fica na frente do MoleSignal, permita os endereços de saída do site ou da região do remetente: o Datadog os lista por site na seção `webhooks` de seus `ip-ranges`, o PagerDuty os publica para suas regiões de serviço nos EUA e na UE, e o Alibaba Cloud CloudMonitor lista suas faixas de push na documentação de callback de alarme. Quando o MoleSignal roda em uma rede interna, consulte [Acesso público](/pt-BR/public-access) para abrir apenas este endereço para a internet.

## Configurar o remetente

**Recebimento** na página da origem fornece o endereço de recebimento, o token e a configuração de cada tipo em três etapas. Substitua `<TOKEN>` pelo token da origem. Assim que a origem recebe sua primeira requisição, as três etapas ficam marcadas.

### API

```bash
curl -X POST https://<molesignal-host>/api/v1/intake/alerts \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{"dedupKey": "disk-full/web-1", "summary": "Disk almost full on web-1", "severity": "critical", "labels": {"host.name": "web-1"}}'
```

`action` é `trigger` (o padrão), `acknowledge` ou `resolve`. Use o mesmo `dedupKey` para reconhecer ou resolver o mesmo alerta. [Enviar alertas](/pt-BR/api/alerting/send-alerts) descreve cada campo.

### Alertmanager

Adicione um receptor a `alertmanager.yml` e encaminhe os alertas para ele:

```yaml
route:
  receiver: molesignal
receivers:
  - name: molesignal
    webhook_configs:
      - url: https://<molesignal-host>/api/v1/intake/alerts
        send_resolved: true
        http_config:
          authorization:
            credentials: <token>
```

Mantenha `send_resolved` em `true`, ou as recuperações nunca são enviadas. Dê a cada réplica de um mesmo cluster do Alertmanager o mesmo `--web.external-url`: a URL externa faz parte da chave de deduplicação, então grupos de mesmo nome vindos de Alertmanagers em várias regiões com o mesmo roteamento não são mesclados em um único incidente.

### Grafana

1. No Grafana, abra **Alertas → Pontos de contato** e clique em **Adicionar ponto de contato**.
2. Defina **Integração** como **Webhook** e **URL** como o endereço de recebimento.
3. Em **Configurações opcionais do webhook**, defina **Esquema do cabeçalho de autenticação** como `Bearer` e **Credenciais do cabeçalho de autenticação** como o token.
4. Deixe **Desativar mensagem de resolução** desmarcado, salve e use o ponto de contato em uma política de notificação.

Com provisionamento por arquivo:

```yaml
apiVersion: 1
contactPoints:
  - orgId: 1
    name: molesignal
    receivers:
      - uid: molesignal
        type: webhook
        settings:
          url: https://<molesignal-host>/api/v1/intake/alerts
          httpMethod: POST
          authorization_scheme: Bearer
          authorization_credentials: <token>
```

### Datadog

1. No Datadog, abra **Integrações → Webhooks** e adicione um webhook, com o nome, por exemplo, `molesignal`.
2. Defina **URL** como o endereço de recebimento e **Cabeçalhos personalizados** como `{"Authorization": "Bearer <token>"}`. Deixe **Codificar como formulário** desmarcado.
3. Defina **Payload** como o modelo abaixo. Os nomes dos campos são do MoleSignal e os valores são variáveis do Datadog; uma requisição sem esse modelo é recusada.

```json
{
  "alert_id": "$ALERT_ID",
  "alert_cycle_key": "$ALERT_CYCLE_KEY",
  "transition": "$ALERT_TRANSITION",
  "alert_type": "$ALERT_TYPE",
  "priority": "$ALERT_PRIORITY",
  "title": "$ALERT_TITLE",
  "event_title": "$EVENT_TITLE",
  "message": "$TEXT_ONLY_MSG",
  "scope": "$ALERT_SCOPE",
  "tags": "$TAGS",
  "hostname": "$HOSTNAME",
  "link": "$LINK",
  "snapshot": "$SNAPSHOT",
  "query": "$ALERT_QUERY",
  "org_id": "$ORG_ID",
  "last_updated": "$LAST_UPDATED"
}
```

4. Mencione `@webhook-molesignal` na mensagem de notificação de um monitor.

Todos os sites do Datadog (`datadoghq.com`, `datadoghq.eu`, `us3`, `us5`, `ap1` e os demais) podem enviar para uma única origem: o site é obtido do domínio de `$LINK` e faz parte da chave de deduplicação, junto com o ID da organização.

### PagerDuty

1. No PagerDuty, abra **Integrações → Generic Webhooks (v3)** e clique em **Novo webhook**.
2. Defina a **URL do webhook** como o endereço de recebimento e escolha o **Tipo de escopo** (a conta, um serviço ou uma equipe).
3. Em **Assinatura de eventos**, selecione `incident.triggered`, `incident.acknowledged`, `incident.resolved`, `incident.reopened` e `incident.priority_updated`.
4. Adicione o cabeçalho personalizado `Authorization` com o valor `Bearer <token>`.

Contas da região de serviço dos EUA e da UE podem enviar para uma única origem: o domínio da conta (`<subdomain>.pagerduty.com` ou `<subdomain>.eu.pagerduty.com`) faz parte da chave de deduplicação e é gravado no rótulo `pagerduty.region`.

### Alibaba Cloud CloudMonitor

Adicione o token ao endereço de recebimento:

```text
https://<molesignal-host>/api/v1/intake/alerts?token=<token>
```

- **Alarmes de limite**: informe este endereço como o **callback de alarme** de uma regra de alarme. O CloudMonitor envia o callback codificado como formulário; o MoleSignal também lê JSON.
- **Eventos de sistema**: em **Central de eventos → Assinatura de eventos → Canais de push**, crie um canal com o tipo de destino **Webhook**, o método de requisição **POST** e o formato de dados **JSON**, informe este endereço e use o canal em uma política de assinatura.

O CloudMonitor espera 5 segundos por um callback de evento de sistema e tenta 3 vezes. O MoleSignal espera no máximo 3 segundos quando repassa uma requisição ao [cluster de recebimento](#vários-clusters) e responde `503` em caso de timeout, para que o CloudMonitor tente novamente. Os sites da China e internacional e todas as regiões enviam o mesmo formato; a região é gravada no rótulo `aliyun.region`, e o `userId` da conta faz parte da chave de deduplicação.

### Tencent Cloud Observability Platform

No Tencent Cloud Observability Platform (antigo Cloud Monitor), edite ou crie um modelo em **Gerenciamento de alarmes → Modelos de notificação**, informe o endereço de recebimento como o **callback de API** e vincule o modelo às suas políticas de alarme. O callback do Tencent Cloud não consegue definir cabeçalhos, então o token vai no endereço. Trate o endereço como uma credencial: o callback não traz assinatura, e é o endereço que identifica a origem. Alarmes de métrica e de evento funcionam, e tanto os disparos quanto as recuperações são enviados.

- **Deduplicação**: a mesma conta, política de alarme, nome de métrica ou de evento e objeto geram um alerta. Uma política com níveis tem um incidente por nível, cada um com recuperação própria, como no Tencent Cloud.
- **Gravidade**: `alarmLevel` Serious (`Serious`) é crítico, Severe (`Warn`) é erro e Reminder (`Remind`) é informativo. Uma política sem níveis usa a gravidade padrão da origem.
- **Eventos sem estado** (`alarmStatus` é `5`) abrem um incidente sem recuperação a esperar, então uma pessoa o resolve.
- **Horários** no callback não trazem fuso horário e são lidos como horário de Pequim.

### Amazon CloudWatch

Os alarmes do CloudWatch não chamam endereços externos diretamente; eles passam pelo SNS:

1. Nas notificações do alarme, envie tanto a entrada em **Em alarme** (`ALARM`) quanto o retorno para **OK** para o mesmo tópico do SNS. Sem `OK`, os incidentes não são resolvidos sozinhos. Para alertas de ausência de dados, envie **Dados insuficientes** (`INSUFFICIENT_DATA`) também.
2. Adicione uma assinatura HTTPS ao tópico com o endereço de recebimento como endpoint, o token no endereço:

   ```bash
   aws sns subscribe \
     --topic-arn <ARN of the topic> \
     --protocol https \
     --notification-endpoint 'https://<molesignal-host>/api/v1/intake/alerts?token=<token>'
   ```

3. A assinatura se confirma sozinha: o MoleSignal verifica a assinatura da mensagem de confirmação e então acessa o `SubscribeURL` dela.

O MoleSignal verifica a assinatura de toda mensagem do SNS, então **Entrega de mensagem bruta** deve ficar desativada. Com ela ativada, as mensagens são recusadas, e Recebidos recentemente na página da origem diz o motivo. O certificado de assinatura vem de `sns.<region>.amazonaws.com`, então o nó que recebe a requisição precisa conseguir acessar esse endereço.

Os alarmes do CloudWatch não têm gravidade, então os incidentes usam a padrão da origem. O ARN do alarme é a chave de deduplicação, inclusive para alarmes compostos. A descrição do alarme e o motivo da mudança de estado vão nas anotações; a região, a conta, o namespace, a métrica e as dimensões vão nos rótulos, então um rótulo como `aws.region` pode orientar o roteamento.

### Azure Monitor

Os alertas do Azure Monitor chegam ao MoleSignal pela ação de webhook de um grupo de ações:

1. No grupo de ações usado pelas suas regras de alerta, adicione uma ação do tipo **Webhook** com o endereço de recebimento como URI, o token no endereço.
2. Defina **Habilitar o esquema de alerta comum** como **Sim**. Sem isso, as requisições são recusadas, e Recebidos recentemente na página da origem diz o motivo.

O mesmo com a CLI do Azure:

```bash
az monitor action-group update \
  --resource-group <resource group> \
  --name <action group> \
  --add-action webhook molesignal 'https://<molesignal-host>/api/v1/intake/alerts?token=<token>' usecommonalertschema
```

- **Deduplicação**: o `alertId` do alerta é a chave de deduplicação, e ela contém a assinatura do Azure.
- **Disparo e resolução**: `monitorCondition` `Fired` abre o incidente e `Resolved` o resolve. Alertas que não mantêm estado, como alertas de log de atividades, apenas disparam, então uma pessoa os resolve.
- **Gravidade**: `Sev0` é crítico, `Sev1` erro, `Sev2` aviso, e `Sev3` e `Sev4` informativo.
- **Rótulos**: as propriedades personalizadas da regra de alerta, as dimensões da métrica, `azure.subscription_id`, `azure.resource_group`, `azure.resource`, `azure.signal_type`, `azure.monitoring_service` e `azure.metric`. A descrição, a condição, o valor e os destinos vão nas anotações, com o link de investigação como `azure_url`.

### Google Cloud Monitoring

1. No console do Google Cloud, abra **Monitoring → Alertas → Editar canais de notificação** e adicione um canal **Webhook** com o endereço de recebimento como **URL do endpoint**, o token no endereço.
2. Adicione o canal às notificações das suas políticas de alerta. Incidentes que se encerram também são enviados, então os incidentes são resolvidos sozinhos.

O canal **Pub/Sub** publica a mesma notificação. Para usá-lo, crie uma assinatura de push no tópico dele com o endereço de recebimento como endpoint de push; o MoleSignal desempacota o envelope do Pub/Sub.

- **Deduplicação**: o projeto de escopo e o `incident_id`. Um incidente do Monitoring é um incidente.
- **Disparo e resolução**: `state` `open` abre o incidente e `closed` o resolve.
- **Gravidade**: o nível de gravidade da política, `Critical`, `Error` ou `Warning`. Uma política sem nível usa a gravidade padrão da origem.
- **Rótulos**: os rótulos do recurso e da métrica, os rótulos de usuário da política e do recurso monitorado, `gcp.project_id`, `gcp.resource_type`, `gcp.metric` e `gcp.policy`. O resumo, a condição, o valor observado, o limite e a documentação vão nas anotações, com o endereço do incidente no console como `gcp_url`.

### Huawei Cloud Eye

Os alarmes do Cloud Eye (CES) não chamam endereços externos diretamente; eles passam pelo SMN:

1. No Simple Message Notification, adicione uma assinatura a um tópico com o protocolo **HTTPS** e o endereço de recebimento como endpoint, o token no endereço.
2. A assinatura se confirma sozinha: o MoleSignal verifica a assinatura da mensagem de confirmação e então acessa o `subscribe_url` dela.
3. Nas notificações de alarme das suas regras de alarme do Cloud Eye, escolha esse tópico e notifique tanto o alarme quanto a recuperação dele. Sem a recuperação, os incidentes não são resolvidos sozinhos.

O MoleSignal verifica a assinatura de toda mensagem do SMN. O certificado de assinatura vem de `smn.<region>.myhuaweicloud.com`, então o nó que recebe a requisição precisa conseguir acessar esse endereço.

- **Deduplicação**: o projeto do tópico, o `alarm_id` da regra de alarme e o recurso. Uma regra sobre vários recursos abre um incidente por recurso.
- **Disparo e resolução**: `alarm_status` `alarm` abre o incidente, `insufficient_data` o abre como ausência de dados, e `ok` o resolve.
- **Gravidade**: o nível do alarme: Critical é crítico, Major erro, Minor aviso e Informational informativo.
- **Rótulos**: as dimensões, como `instance_id`, e `huawei.region`, `huawei.project_id`, `huawei.namespace`, `huawei.metric`, `huawei.alarm_id` e `huawei.resource_id`. O texto do alarme, o valor atual e o limite vão nas anotações, com o endereço do alarme no console como `huawei_url`.

### Zabbix

Funciona a partir do Zabbix 6.0. O Zabbix não tem um formato de requisição próprio: um script de tipo de mídia envia a requisição. Por isso, a página da origem, e o diálogo ao criá-la, fornecem um tipo de mídia com o endereço e o token já preenchidos:

1. Salve-o como YAML e importe-o em **Alertas → Tipos de mídia → Importar**. Verifique o parâmetro `token`.
2. Defina a macro global `{$ZABBIX.URL}` com o endereço do frontend do Zabbix. Ela entra na chave de deduplicação, então uma origem pode receber vários servidores Zabbix, e os incidentes apontam de volta para o Zabbix. Também funciona sem ela.
3. Atribua esse tipo de mídia a um usuário. O **Enviar para** pode ser qualquer coisa; o script não o usa.
4. Adicione uma ação de trigger cujas **operações**, **operações de recuperação** e **operações de atualização** vão todas para esse usuário. Sem operações de recuperação, os incidentes não são resolvidos sozinhos.

O botão **Teste** do tipo de mídia precisa de valores reais: quando as macros não são expandidas (`{EVENT.ID}` chega como está), o MoleSignal responde `400` e diz para usar o tipo de mídia da documentação.

### E-mail

Há duas formas de entrada, e ambas leem e-mail para os mesmos alertas.

**Ler uma caixa de e-mail** (recomendado): o MoleSignal lê uma caixa de e-mail IMAP periodicamente. Só precisa de uma saída e de uma caixa de e-mail: nenhum endereço público, registro MX, porta 25 ou certificado, o que a torna a opção mais fácil para auto-hospedagem. Envie o e-mail de alerta do seu sistema de monitoramento para essa caixa de e-mail, ou encaminhe-o para lá com uma regra de e-mail.

Na página da origem, em **Ler uma caixa de e-mail**, preencha **Servidor IMAP**, **Porta**, **Criptografia**, **Nome de usuário**, **Senha**, **Pasta** (`INBOX` por padrão) e **Ler a cada** (15 a 3600 segundos, 60 por padrão). Clique em **Testar conexão** e depois em **Salvar caixa de e-mail**.

- **Somente leitura**: usa `EXAMINE` e `BODY.PEEK[]`, então nada é marcado como lido ou excluído. Uma conta somente leitura basta.
- **Sem backlog**: na primeira conexão ele anota a posição e lê apenas o que chega depois. Uma mudança de host, conta ou pasta, ou um servidor que reconstruiu a caixa de e-mail (`UIDVALIDITY` alterado), recomeça a partir daquele momento. Enquanto a origem está desligada nada é lido e nenhuma posição é guardada: ela começa a partir do momento em que é ligada de novo.
- **A lista de remetentes é obrigatória**: qualquer pessoa que saiba o endereço pode enviar e-mail para ele. Em **Aceitar e-mails de** nas configurações da origem, escreva endereços ou `@example.com` para um domínio inteiro; `*` aceita todos. A lista lê o `From`, que pode ser falsificado, então mantenha a filtragem de spam e o DMARC do provedor de e-mail ativos. E-mails de qualquer outra pessoa são registrados como **Recusada** e não abrem nada.
- **Autenticação**: uma senha, ou uma senha de aplicativo do provedor. O Microsoft 365 não aceita mais senhas: escolha **OAuth 2.0** e preencha o endereço do token `https://login.microsoftonline.com/<tenant>/oauth2/v2.0/token`, o ID do cliente, o segredo do cliente e o escopo `https://outlook.office365.com/.default`. O aplicativo precisa da permissão `IMAP.AccessAsApp` e de acesso a esta caixa de e-mail.
- **Sem criptografia** só é aceitável em uma rede confiável: a senha passa por ela em texto claro.
- Quando uma leitura falha, a página da origem diz o motivo, e a próxima rodada tenta de novo. Com vários nós de alerta, cada caixa de e-mail é lida por um deles. Com federação, a caixa de e-mail é configurada no cluster de recebimento da origem e não é sincronizada, então a senha fica lá.

**Enviar o e-mail bruto**: se você já opera um sistema de e-mail (o `pipe` do Postfix, SES, o MIME bruto do Mailgun), faça um POST da mensagem bruta para o endereço de recebimento:

```bash
curl -X POST 'https://<molesignal-host>/api/v1/intake/alerts' \
  -H 'Authorization: Bearer <token>' \
  -H 'Content-Type: message/rfc822' \
  --data-binary @alert.eml
```

Isso exige que o endereço de recebimento seja acessível a partir desse sistema de e-mail. A lista de remetentes é opcional aqui, já que o token já diz quem está chamando; ela se aplica se você escrever uma.

O MoleSignal não tem um receptor SMTP integrado: isso exigiria uma porta 25 aberta, um registro MX, um certificado TLS e filtragem de spam própria, o que a maioria das implantações auto-hospedadas não consegue oferecer.

**Como os e-mails são lidos** é definido em **Como os e-mails são lidos** nas configurações da origem:

| Configuração | Descrição |
|---|---|
| **Assuntos que indicam recuperação** | Uma expressão regular. Vazio usa a interna: `resolved`, `recovered`, `recovery`, `cleared`, `恢复`, `已解决` e `OK` no início. Os demais e-mails disparam. |
| **Chave de deduplicação extraída do assunto** | Uma expressão regular; o primeiro grupo dela é usado, como `host=(\S+)`. Vazio ou sem correspondência usa o assunto normalizado: sem `Re:` e `Fwd:`, palavras de status (`PROBLEM`, `RECOVERY`, `告警`, `恢复` e assim por diante), gravidades, datas e horas, e porcentagens, ignorando maiúsculas e minúsculas. Assim, "CRITICAL: disk full on web-1 (91%)" e "RECOVERY: disk full on web-1 (40%)" são um alerta, enquanto `web-1` e `web-2` são dois. O domínio do remetente também entra na chave. |
| **Assuntos que não geram alertas** | Uma expressão regular. Os e-mails que correspondem são ignorados e aparecem em Recebidos recentemente. |

A gravidade vem de palavras no assunto (`critical`, `fatal`, `disaster`, `P1` são crítico; `error`, `P2` erro; `warning`, `P3` aviso; `info`, `notice`, `P4`, `P5` informativo), ou então da padrão da origem; o high e o low de `High CPU` e `Low disk` não contam. O corpo vai na anotação `message` (e-mail HTML como texto, no máximo 4096 caracteres), o remetente no rótulo `email.from` e na anotação `from`, e o horário vem do cabeçalho `Date`. Respostas automáticas (`Auto-Submitted: auto-replied`) e retornos (`multipart/report`) não geram alertas. GBK, GB2312 e outros conjuntos de caracteres são compreendidos. E-mails com mais de 4 MiB são registrados como **Recusada** sem que o corpo seja lido.

## Como os alertas se tornam incidentes

| Tipo | Chave de deduplicação | Disparo | Resolução | Gravidade |
|---|---|---|---|---|
| **API** | `dedupKey` | `trigger` | `resolve` | `severity` |
| **Alertmanager** | URL externa e `groupKey` | `status` do grupo `firing` | `status` do grupo `resolved`: todo alerta do grupo recuperado | O rótulo `severity` mais alto entre os alertas em disparo do grupo |
| **Grafana** | URL externa, organização e `groupKey` | Igual | Igual | Igual |
| **Datadog** | Site, organização, ID do monitor e escopo | Qualquer transição exceto `Recovered` | `Recovered` | `$ALERT_PRIORITY`; sem ele, Warn e No Data recebem aviso e o restante segue `$ALERT_TYPE` |
| **PagerDuty** | Domínio da conta e ID do incidente do PagerDuty | `incident.triggered`, `incident.reopened`; `incident.priority_updated` altera a gravidade | `incident.resolved` | Prioridade P1 a P5; sem ela, urgência alta é erro e baixa é aviso |
| **Alibaba Cloud CloudMonitor** | Conta, ID da regra e `dimensions`; para eventos de sistema, conta e `dedupId` | `ALERT`, `INSUFFICIENT_DATA`; evento de sistema `TRIGGERED` | `OK`; evento de sistema `RESOLVED` | `triggerLevel`; `severity` do evento de sistema |
| **Tencent Cloud Observability Platform** | Conta, política, nome da métrica ou do evento, nível e objeto | `alarmStatus` é `1` ou `5` | `alarmStatus` é `0` | `alarmLevel` |
| **Amazon CloudWatch** | `AlarmArn` | `NewStateValue` é `ALARM` ou `INSUFFICIENT_DATA` | `NewStateValue` é `OK` | Nenhuma: a gravidade padrão da origem |
| **Azure Monitor** | `alertId` | `monitorCondition` é `Fired` | `monitorCondition` é `Resolved` | `severity`: `Sev0` crítico, `Sev1` erro, `Sev2` aviso, `Sev3` e `Sev4` informação |
| **Google Cloud Monitoring** | Projeto de escopo e `incident_id` | `state` é `open` | `state` é `closed` | `severity`; `No severity` usa a gravidade padrão da origem |
| **Huawei Cloud Eye** | Projeto do tópico SMN, `alarm_id` e recurso | `alarm_status` é `alarm` ou `insufficient_data` | `alarm_status` é `ok` | Nível do alarme: Crítico, Grave, Leve, Informativo |
| **Zabbix** | Host de `{$ZABBIX.URL}` e `{EVENT.ID}` | `{EVENT.VALUE}` é 1; operações de atualização também, com a gravidade correspondente | `{EVENT.VALUE}` é 0, ou uma operação de atualização fechou o problema | `{EVENT.NSEVERITY}`: Disaster é crítico, High erro, Average e Warning aviso, Information informação |
| **Email** | O domínio do remetente e a parte extraída do assunto | Outro e-mail | Um assunto escrito como recuperação | Palavras no assunto |

Prioridade e urgência são lidas separadamente: `priority` e `urgency` da API, `$ALERT_PRIORITY` do Datadog e a prioridade e a urgência do PagerDuty tornam-se a prioridade e a urgência do incidente. Sem uma urgência, a política de escalonamento da origem decide, e um alerta que não informa gravidade é de urgência alta; consulte [Urgência](/pt-BR/alerting/on-call#urgência).

Um alerta sem gravidade usa a **Gravidade padrão** da origem. As palavras de gravidade de cada remetente não diferenciam maiúsculas de minúsculas: `critical`, `crit`, `fatal`, `page` e `P1` são classificadas como críticas; `error`, `major`, `high` e `P2` como erro; `warning`, `warn`, `minor`, `medium` e `P3` como aviso; `info`, `low`, `P4` e `P5` como informação. Qualquer outra palavra usa a gravidade padrão.

- **Abertura**: uma origem tem no máximo um incidente ativo por chave de deduplicação. O incidente carrega os rótulos `alert.source=external` e `external.kind=<kind>`, os rótulos do próprio alerta (para Alertmanager e Grafana, os `commonLabels` do grupo) e os rótulos extras da origem. O rótulo `service.name` ou `service` torna-se um serviço afetado, e `host.name`, `host` ou `hostname` torna-se um host.
- **Título**: a API usa `summary`; Alertmanager e Grafana usam a anotação `summary`, ou `alertname` sem ela; o Datadog usa `$ALERT_TITLE`; o PagerDuty usa o título do incidente; o Alibaba Cloud CloudMonitor usa "nome do alarme · nome da instância".
- **Links**: os endereços de retorno ao remetente são gravados em anotações, como `alertmanager_url`, `generator_url`, `dashboard_url`, `datadog_url` e `pagerduty_url`, e a página do incidente os exibe como links. Os `links` da API são gravados em anotações por `name`.
- **Alertas de um grupo**: um incidente do Alertmanager ou do Grafana mantém todos os alertas do grupo (até 100) com seu status, atualizados a cada notificação. **Alerta externo** na página do incidente os lista, com os rótulos que os diferenciam.
- **Mudanças de gravidade**: um incidente que ainda não foi reconhecido segue a gravidade do alerta, conforme decidido pelos [pipelines de alerta](/pt-BR/pipelines/alert-events#alterações-de-severidade). Quando ela aumenta, o escalonamento recomeça da primeira etapa. Uma gravidade definida manualmente permanece.
- **Reconhecimento**: o `acknowledge` da API, o `incident.acknowledged` do PagerDuty e as operações de atualização do Zabbix que reconhecem um problema reconhecem o incidente e interrompem as etapas de escalonamento e as chamadas seguintes. Nenhum usuário é registrado como responsável pelo reconhecimento.
- **Resolução**: o incidente é resolvido quando a origem relata recuperação, inclusive incidentes reconhecidos. Nenhum usuário é registrado como responsável pela resolução, e a linha do tempo o mostra como recuperado.
- **Mensagens atrasadas**: cada chave de deduplicação memoriza o horário de envio mais recente que utilizou, e uma mensagem mais antiga é ignorada. Um disparo atrasado não abre um incidente zumbi, e uma recuperação atrasada não fecha um novo. A API não carrega horário, então suas mensagens são consideradas na ordem de chegada.
- **Resolvido primeiro por uma pessoa**: quando a origem ainda relata o alerta, o próximo reenvio abre um novo incidente, como nas regras.
- **Sem dados**: incidentes abertos por `INSUFFICIENT_DATA` do CloudMonitor, `insufficient_data` do Cloud Eye e No Data do Datadog carregam `alert.condition=no_data`, e os títulos de suas notificações começam com `NO DATA`.
- **Desativação e exclusão**: uma origem desativada recusa alertas (`409`), e seus incidentes abertos permanecem. Excluir uma origem faz seu token parar de funcionar imediatamente e resolve seus incidentes abertos.

[Políticas de silêncio](/pt-BR/alerting/silences), [grupos semânticos](/pt-BR/alerting/silences#grupos-semânticos) e [políticas de notificação](/pt-BR/notification-channels) se aplicam a incidentes externos como a qualquer outro. Combine-as por `external.kind`, pelos rótulos extras de uma origem ou pelos rótulos do próprio alerta.

## Solicitações recentes

O topo da página da origem mostra a situação da origem: **Aguardando a primeira solicitação**, **Recebendo solicitações**, **Última solicitação recusada**, **Sem solicitações nos últimos 7 dias** ou **Desativada**. Ao lado, ficam as solicitações e os alertas das últimas 24 horas, e os incidentes que a origem abriu e ainda estão abertos.

Depois que as solicitações chegam, **Solicitações recentes** na página da origem lista as solicitações recebidas pela origem: o horário, o resultado (**Processada**, **Recusada** ou **Encaminhada**), o status HTTP, o número de alertas e o que aconteceu com eles (**Aberto**, **Atualizado**, **Sem alterações**, **Reconhecido**, **Resolvido** ou **Ignorado**). Clique em uma linha para ver o título, a gravidade, a ação, o resultado e o incidente de cada alerta; uma solicitação recusada também mostra o motivo e o início do corpo (até 16 KiB). As últimas 500 solicitações de cada origem são mantidas, por até 7 dias.

## Vários clusters

Com a [federação entre clusters](/pt-BR/settings/data-plane#federação-de-clusters) ativada:

- As fontes são sincronizadas entre os clusters como as demais configurações de alerta, tokens incluídos, de modo que um mesmo token funciona no endereço de recebimento de todos os clusters.
- Os incidentes de uma fonte são abertos apenas no seu **Cluster receptor**: o cluster em que a fonte foi criada, a menos que isso seja alterado nas configurações da fonte. Outro cluster que recebe um alerta da fonte o repassa por gRPC ao cluster receptor e devolve a resposta do cluster receptor ao remetente. Assim, um alerta externo é um único incidente, seja qual for o endereço de cluster em que ele chegar.
- Quando o cluster receptor não pode ser alcançado, a resposta é `503` e o remetente tenta novamente. Se a região do cluster receptor continuar indisponível, altere o **Cluster receptor** nas configurações da fonte para um que esteja ativo.
- As **Solicitações recentes** são registradas no cluster que processou a requisição. A página da fonte informa isso quando é aberta em outro cluster.

## Limites

| Item | Limite |
|---|---|
| Corpo da requisição, um e-mail | No máximo 4 MiB. |
| Leitura de uma caixa de correio | No máximo 50 e-mails por vez; o restante na próxima rodada. |
| Uma requisição de API | 100 alertas; `dedupKey` com até 255 caracteres, `summary` com até 1024 caracteres. |
| Um alerta | 64 rótulos e 64 anotações. A API recusa mais; para os outros tipos, o restante é descartado, e títulos e anotações muito longos são cortados. |
| Alertas de um grupo | 100 são mantidos. |
| Rótulos extras de uma fonte | 32, sem nenhuma chave começando com `alert.` e sem `external.kind`. |
| Solicitações recentes | As últimas 500 requisições de cada fonte, por até 7 dias. |

A assinatura HMAC do Grafana e a assinatura do PagerDuty não são verificadas; o token já identifica a fonte. Reconhecer ou resolver um incidente no MoleSignal não é propagado de volta ao remetente.
