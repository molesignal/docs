The **Implantações** section of a service page puts two sources side by side: the deployments that
pipelines report, and the versions that the service's spans carry in `service.version`. A version
that no pipeline reported still appears, from the spans alone.

## The deployment timeline

The timeline lists what happened to the service in the time range, the newest first:

| Event | When |
|---|---|
| **Implantado** | A pipeline reported a deployment that succeeded. |
| **Falhou** | A pipeline reported a deployment that failed. A failed deployment does not change the running version. |
| **Revertido** | A pipeline reported a rollback, or reported a deployment of a version that ran before another version. The row names the version it went back from. |
| **Retornou** | The spans went back to an older version that no pipeline reported: the version seen last was first seen before a newer version that stopped more than five minutes earlier. |
| **Primeira ocorrência** | The spans carried a version that no pipeline reported. |
| **Configuração** | A pipeline or a tool reported a configuration change. Its description shows in the row. |
| **Flag de recurso** | A pipeline or a tool reported a feature flag change. Its description shows in the row. |

A configuration change or a feature flag does not change the running version and has no figures of
its own. It is listed among the changes near an insight; see
[Changes near a finding](/pt-BR/apm/insights#mudanças-perto-de-um-achado).

A reported deployment shows its commit, pull request, CI run, and author. When the repository is an
http or https address, the commit opens on its web page, in the way GitHub, GitLab, or Bitbucket
addresses a commit.

Each version's requests, error rate, and p95 in the range show on its newest row, with the verdict
against the version first seen before it:

| Verdict | When |
|---|---|
| **Reincidente** | The error rate rose by at least one point and to at least 1.5 times, or p95 rose by at least a fifth and at least 50 ms. The part that got worse follows the verdict. |
| **Melhorou** | One of the two fell as far, and neither got worse. |
| **Sem alteração** | Neither moved that far. |
| **Requisições insuficientes** | Either version served fewer requests than a version comparison needs, 1,000 by default. |

Selecting a verdict opens its two versions in **Compare two versions**, which lists the endpoints that
got slower and the errors that grew. A regressed or improved version is also flagged among the
overview's recent deployments.

## Canaries

When two versions run at once, as a canary runs beside the version it replaces, a card above the
timeline reads them side by side. Two versions run at once when both were seen within five minutes
of the last span of the service. The card compares the newest two, from when the newer one was
first seen:

- the share of the requests that each version served;
- requests, error rate, p50, p95, and p99 of each version;
- the verdict of the newer version against the older one.

## Report deployments from CI

A pipeline reports a deployment with `POST /api/v1/apm/deployments`. The request needs an API Token
that may use `apm.deploy`. Owners, administrators, and editors hold it, and the **Data intake**
policy that intake tokens follow includes it.

```bash
curl -X POST "https://<host>/api/v1/apm/deployments" \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{"service": "checkout", "environment": "production", "version": "2.4.0", "commit": "9f2c1e7a4b3d", "repository": "https://github.com/acme/checkout", "ciUrl": "https://ci.example.com/runs/7"}'
```

| Field | Required | Description |
|---|---|---|
| `service` | Yes | The service, as its spans name it in `service.name`. Up to 255 characters. |
| `version` | For a deployment | The version deployed, as its spans report it in `service.version`. Up to 192 characters. |
| `kind` | No | `deployment` (the default), `configuration`, `feature_flag`, `scaling`, or `infrastructure`. |
| `namespace` | No | The service's `service.namespace`. A deployment without one shows in every namespace. |
| `environment` | No | The environment, as `deployment.environment.name`. A deployment without one shows in every environment. |
| `status` | No | `succeeded` (the default), `failed`, or `rolled_back` when the deployment took the service back to `version`. |
| `commit` | No | The commit deployed: up to 64 letters and digits. |
| `repository` | No | Where the code lives: an https, http, ssh, or git address of up to 512 characters. A password in the address is kept as `****`, as is the user part of an https address. |
| `pullRequest` | No | An http or https link to the pull request. |
| `author` | No | Who deployed, up to 128 characters. |
| `ciUrl` | No | An http or https link to the CI run. |
| `description` | No | Up to 1,000 characters. It shows when the pointer rests on the event. |
| `deployedAt` | No | When the deployment happened, in microseconds since the epoch. Defaults to the time the request arrives. |

The service and the environment are named as APM names them: the organization's naming rules,
environment mapping, and aliases apply to them, as they apply to spans. See
[APM settings](/pt-BR/apm/settings).

The **Datasource** page has the steps below under **GitHub Actions**, **GitLab CI/CD**, and
**Jenkins**, with the address of the workspace filled in.

### GitHub Actions

Keep the token as a repository secret, then add a step to the job that deploys. `if: always()`
reports a failed deployment too.

```yaml
- name: Report the deployment to MoleSignal
  if: always()
  env:
    MOLESIGNAL_TOKEN: ${{ secrets.MOLESIGNAL_TOKEN }}
    DEPLOY_STATUS: ${{ job.status == 'success' && 'succeeded' || 'failed' }}
  run: |
    cat > deployment.json <<EOF
    {
      "service": "checkout",
      "environment": "production",
      "version": "${GITHUB_SHA::12}",
      "status": "$DEPLOY_STATUS",
      "commit": "$GITHUB_SHA",
      "repository": "$GITHUB_SERVER_URL/$GITHUB_REPOSITORY",
      "author": "$GITHUB_ACTOR",
      "ciUrl": "$GITHUB_SERVER_URL/$GITHUB_REPOSITORY/actions/runs/$GITHUB_RUN_ID"
    }
    EOF
    curl -fsS -X POST "https://<host>/api/v1/apm/deployments" \
      -H "Authorization: Bearer $MOLESIGNAL_TOKEN" \
      -H "Content-Type: application/json" \
      --data-binary @deployment.json
```

### GitLab CI/CD

Add the token as a masked CI/CD variable named `MOLESIGNAL_TOKEN`, then report from the deploy job's
`after_script`, which runs whether the deployment worked or not.

```yaml
deploy:
  stage: deploy
  environment: production
  script:
    - ./deploy.sh
  after_script:
    - |
      if [ "$CI_JOB_STATUS" = "success" ]; then DEPLOY_STATUS=succeeded; else DEPLOY_STATUS=failed; fi
      cat > deployment.json <<EOF
      {
        "service": "checkout",
        "environment": "$CI_ENVIRONMENT_NAME",
        "version": "$CI_COMMIT_SHORT_SHA",
        "status": "$DEPLOY_STATUS",
        "commit": "$CI_COMMIT_SHA",
        "repository": "$CI_PROJECT_URL",
        "author": "$GITLAB_USER_LOGIN",
        "ciUrl": "$CI_PIPELINE_URL"
      }
      EOF
      curl -fsS -X POST "https://<host>/api/v1/apm/deployments" \
        -H "Authorization: Bearer $MOLESIGNAL_TOKEN" \
        -H "Content-Type: application/json" \
        --data-binary @deployment.json
```

### Jenkins

Add the token as a **Secret text** credential with the ID `molesignal-token`, then report in the
pipeline's `post` block. `post { always }` reports a failed build too. A password in `GIT_URL` is
masked when the deployment is kept.

```groovy
post {
  always {
    script {
      writeFile file: 'deployment.json', text: groovy.json.JsonOutput.toJson([
        service: 'checkout',
        environment: 'production',
        version: env.GIT_COMMIT.take(12),
        status: currentBuild.currentResult == 'SUCCESS' ? 'succeeded' : 'failed',
        commit: env.GIT_COMMIT,
        repository: env.GIT_URL,
        ci_url: env.BUILD_URL,
      ])
    }
    withCredentials([string(credentialsId: 'molesignal-token', variable: 'MOLESIGNAL_TOKEN')]) {
      sh '''
        curl -fsS -X POST "https://<host>/api/v1/apm/deployments" \
          -H "Authorization: Bearer $MOLESIGNAL_TOKEN" \
          -H "Content-Type: application/json" \
          --data-binary @deployment.json
      '''
    }
  }
}
```

## Report configuration changes and feature flags

Report a configuration change, a feature flag, a change of scale, or a change of the infrastructure
under a service with the same endpoint, with `kind` set and a description of what changed. It needs no
version.

Every reported change is also listed by [`GET /api/v1/changes`](/pt-BR/api/changes), marked on the
histograms of Logs and Traces and under the Metrics chart, and on the **Changes** page of Alerts.

```bash
curl -X POST "https://<host>/api/v1/apm/deployments" \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{"service": "checkout", "environment": "production", "kind": "feature_flag", "description": "new_checkout on for 10% of users"}'
```

## Relatar mudanças de webhooks

Uma ferramenta cujo webhook consegue definir o corpo e um cabeçalho, como as notificações do Argo CD, o Spinnaker ou o
add-on de webhook do Unleash com um modelo de corpo, chama `POST /api/v1/apm/deployments` como acima. Uma ferramenta que
envia um corpo próprio, ou não consegue definir um cabeçalho, chama `POST /api/v1/intake/changes`. O token da API vai em `Authorization: Bearer` ou, onde não é possível definir um cabeçalho, em `?token=`, e deve ter
`apm.deploy`. Um token em um endereço pode acabar nos logs do proxy: dê a essa ferramenta um token próprio,
restrito apenas a `apm.deploy`.

| Parâmetro | Observações |
|---|---|
| `format` | `generic` (o padrão), `launchdarkly`, `unleash`, `nacos` ou `apollo`. |
| `service`, `namespace`, `environment` | O que o corpo não informa. Uma mudança que não nomeia nenhum serviço é recusada. |
| `kind` | `deployment`, `configuration`, `feature_flag`, `scaling` ou `infrastructure`; substitui o que o corpo informa. |
| `serviceField`, `environmentField`, `versionField`, `descriptionField`, `authorField` | Para `generic`: um ponteiro JSON como `/app/name`, ou um nome de campo de nível superior. Sem isso, é lido o campo de mesmo nome que `POST /api/v1/apm/deployments` aceita. |

| Formato | Lido como |
|---|---|
| `launchdarkly` | Um feature flag. O ambiente é a parte `env/` do recurso auditado, a descrição é o título da entrada e o autor é o e-mail do membro. |
| `unleash` | Um feature flag: o tipo de evento e o nome da toggle, seu ambiente e quem a alterou. |
| `nacos` | Uma mudança de configuração do data ID e do group; o namespace do Nacos é o namespace. |
| `apollo` | Uma mudança de configuração: o app ID é o serviço, o cluster é o ambiente, e o namespace e o título da release são o que mudou. |

**Data sources → DevOps** tem um guia para cada um de LaunchDarkly, Unleash, Nacos e Apollo, com o
endereço preenchido para o workspace.

Um corpo pode conter uma mudança ou uma lista de até 100. A resposta é `201` com as mudanças mantidas. Os
presets foram escritos com base nos payloads documentados das ferramentas e não foram verificados em contas
reais; onde o payload de uma ferramenta for diferente, use `generic` com ponteiros.

```bash
curl -X POST "https://<host>/api/v1/intake/changes?format=launchdarkly&service=checkout&token=<token>" \
  -H "Content-Type: application/json" \
  -d @launchdarkly-event.json
```

## Solução de problemas

| Sintoma | Verificação |
|---|---|
| Um deployment relatado está ausente na linha do tempo | O intervalo de tempo deve incluir `deployedAt`, e `service` deve nomear o serviço como o APM faz. Um deployment relatado com um ambiente aparece apenas nesse ambiente. |
| Um deployment e a versão que ele implantou aparecem como duas linhas | O `version` relatado difere do `service.version` que os spans carregam. Relate o mesmo valor. |
| `403` do endpoint de deployments | O token pode não usar `apm.deploy`: o escopo dele o deixa de fora, ou o membro ou a service account dele não o possui. |
| `400` do endpoint de deployments | Um campo viola um limite da tabela acima; o erro indica qual. |
