A seção **Implantações** da página de um serviço reúne duas fontes: as implantações que
os pipelines registram e as versões que os spans do serviço indicam em `service.version`. Uma versão
que nenhum pipeline registrou ainda aparece com base apenas nos spans.

## Linha do tempo de implantações

A linha do tempo lista o que aconteceu com o serviço no intervalo selecionado, do evento mais recente ao mais antigo:

| Evento | Quando |
|---|---|
| **Implantado** | Um pipeline registrou uma implantação bem-sucedida. |
| **Falhou** | Um pipeline registrou uma implantação que falhou. Uma falha na implantação não altera a versão em execução. |
| **Revertido** | Um pipeline registrou uma reversão ou a implantação de uma versão que já estava em execução antes de outra. A linha indica a versão que deu lugar à anterior. |
| **Retornou** | Os spans voltaram a indicar uma versão anterior que nenhum pipeline registrou: a versão vista por último apareceu pela primeira vez antes de uma versão mais recente que deixou de aparecer mais de cinco minutos antes. |
| **Primeira ocorrência** | Os spans indicaram uma versão que nenhum pipeline registrou. |
| **Configuração** | Um pipeline ou uma ferramenta registrou uma alteração de configuração. A descrição aparece na linha. |
| **Flag de recurso** | Um pipeline ou uma ferramenta registrou uma alteração em uma flag de recurso. A descrição aparece na linha. |

Uma alteração de configuração ou de flag de recurso não altera a versão em execução e não tem métricas
próprias. A alteração aparece na lista de mudanças próximas a uma descoberta; consulte
[Alterações próximas a uma descoberta](/pt-BR/apm/insights#mudanças-próximas-a-um-achado).

O registro de uma implantação mostra o commit, o pull request, a execução de CI e o autor. Quando o repositório tem um
endereço http ou https, o link do commit abre a página correspondente, conforme o formato de URL que GitHub, GitLab ou Bitbucket
usa para commits.

A linha mais recente de cada versão mostra as requisições, a taxa de erros e o p95 no intervalo, além do resultado
da comparação com a versão cuja primeira ocorrência veio logo antes:

| Resultado | Quando |
|---|---|
| **Reincidente** | A taxa de erros subiu pelo menos um ponto percentual e atingiu pelo menos 1,5 vez o valor anterior, ou o p95 subiu pelo menos 20% e pelo menos 50 ms. A métrica que piorou aparece após o resultado. |
| **Melhorou** | Uma das duas métricas caiu o suficiente para atingir os mesmos limites, e nenhuma piorou. |
| **Sem alteração** | Nenhuma das duas métricas variou o suficiente para atingir os limites. |
| **Requisições insuficientes** | Pelo menos uma das versões atendeu a menos requisições que o mínimo necessário para a comparação: 1.000 por padrão. |

Selecione um resultado para abrir as duas versões em **Comparar duas versões**. A tela lista os endpoints que
ficaram mais lentos e os erros que aumentaram. A visão geral também destaca a piora ou a melhora da versão
entre as implantações recentes.

## Implantação canário

Quando duas versões rodam ao mesmo tempo, como em uma implantação canário em que a nova versão roda ao lado da versão que vai substituir, um cartão acima da
linha do tempo mostra as duas lado a lado. As versões contam como simultâneas quando ambas aparecem nos cinco minutos que antecedem ou incluem
o último span do serviço. O cartão compara as duas versões mais recentes a partir da primeira ocorrência
da versão mais nova:

- a proporção de requisições que cada versão atendeu;
- as requisições, a taxa de erros, o p50, o p95 e o p99 de cada versão;
- o resultado da comparação da versão mais nova com a anterior.

## Registre implantações pela CI

Registre a implantação no pipeline com `POST /api/v1/apm/deployments`. A requisição exige um token de API
com a permissão `apm.deploy`. Proprietários, administradores e editores têm essa permissão, e a política
**Ingestão de dados** aplicada aos tokens de ingestão também a inclui.

```bash
curl -X POST "https://<host>/api/v1/apm/deployments" \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{"service": "checkout", "environment": "production", "version": "2.4.0", "commit": "9f2c1e7a4b3d", "repository": "https://github.com/acme/checkout", "ciUrl": "https://ci.example.com/runs/7"}'
```

| Campo | Obrigatório | Descrição |
|---|---|---|
| `service` | Sim | O nome do serviço conforme indicado em `service.name` nos spans. Até 255 caracteres. |
| `version` | Para uma implantação | A versão implantada, conforme indicada em `service.version` nos spans. Até 192 caracteres. |
| `kind` | Não | `deployment` (padrão), `configuration` ou `feature_flag`. |
| `namespace` | Não | O `service.namespace` do serviço. Uma implantação sem namespace aparece em todos os namespaces. |
| `environment` | Não | O ambiente, conforme indicado em `deployment.environment.name`. Uma implantação sem ambiente aparece em todos os ambientes. |
| `status` | Não | `succeeded` (padrão), `failed` ou `rolled_back` quando a implantação restaurou o serviço para a versão indicada em `version`. |
| `commit` | Não | O commit implantado: até 64 letras e dígitos. |
| `repository` | Não | O endereço do repositório do código: http, https, ssh ou git, com até 512 caracteres. O MoleSignal armazena a senha do endereço como `****`, assim como o nome de usuário em endereços https. |
| `pullRequest` | Não | Um link http ou https para o pull request. |
| `author` | Não | Nome de quem fez a implantação, com até 128 caracteres. |
| `ciUrl` | Não | Um link http ou https para a execução de CI. |
| `description` | Não | Até 1.000 caracteres. A descrição aparece ao passar o ponteiro sobre o evento. |
| `deployedAt` | Não | Momento da implantação, em microssegundos desde a época Unix. Por padrão, usa o horário de recebimento da requisição. |

Use os mesmos nomes de serviço e de ambiente do APM: as regras de nomenclatura, o
mapeamento de ambientes e os aliases da organização se aplicam da mesma forma que aos spans. Consulte
[Configurações do APM](/pt-BR/apm/settings).

Na página **Fonte de dados**, encontre as etapas abaixo nas seções **GitHub Actions**, **GitLab CI/CD** e
**Jenkins**, com o endereço do espaço de trabalho já preenchido.

### GitHub Actions

Armazene o token como um segredo do repositório e adicione uma etapa ao job de implantação. `if: always()`
também registra a implantação em caso de falha.

```yaml
- name: Report the deployment to MoleSignal
  if: always()
  env:
    MOLESIGNAL_TOKEN: ${{ secrets.MOLESIGNAL_TOKEN }}
    DEPLOY_STATUS: ${{ job.status == 'success' && 'succeeded' || 'failed' }}
  run: |
    cat > deployment.json <<EOF
    {
      "service": "checkout",
      "environment": "production",
      "version": "${GITHUB_SHA::12}",
      "status": "$DEPLOY_STATUS",
      "commit": "$GITHUB_SHA",
      "repository": "$GITHUB_SERVER_URL/$GITHUB_REPOSITORY",
      "author": "$GITHUB_ACTOR",
      "ciUrl": "$GITHUB_SERVER_URL/$GITHUB_REPOSITORY/actions/runs/$GITHUB_RUN_ID"
    }
    EOF
    curl -fsS -X POST "https://<host>/api/v1/apm/deployments" \
      -H "Authorization: Bearer $MOLESIGNAL_TOKEN" \
      -H "Content-Type: application/json" \
      --data-binary @deployment.json
```

### GitLab CI/CD

Adicione o token como uma variável mascarada de CI/CD chamada `MOLESIGNAL_TOKEN` e registre a implantação no
`after_script` do job de implantação, que roda mesmo em caso de falha.

```yaml
deploy:
  stage: deploy
  environment: production
  script:
    - ./deploy.sh
  after_script:
    - |
      if [ "$CI_JOB_STATUS" = "success" ]; then DEPLOY_STATUS=succeeded; else DEPLOY_STATUS=failed; fi
      cat > deployment.json <<EOF
      {
        "service": "checkout",
        "environment": "$CI_ENVIRONMENT_NAME",
        "version": "$CI_COMMIT_SHORT_SHA",
        "status": "$DEPLOY_STATUS",
        "commit": "$CI_COMMIT_SHA",
        "repository": "$CI_PROJECT_URL",
        "author": "$GITLAB_USER_LOGIN",
        "ciUrl": "$CI_PIPELINE_URL"
      }
      EOF
      curl -fsS -X POST "https://<host>/api/v1/apm/deployments" \
        -H "Authorization: Bearer $MOLESIGNAL_TOKEN" \
        -H "Content-Type: application/json" \
        --data-binary @deployment.json
```

### Jenkins

Adicione o token como uma credencial do tipo **Secret text** com o ID `molesignal-token` e registre a implantação no
bloco `post` do pipeline. `post { always }` também registra builds que falham. Se `GIT_URL` contiver uma senha,
o MoleSignal a mascara ao salvar a implantação.

```groovy
post {
  always {
    script {
      writeFile file: 'deployment.json', text: groovy.json.JsonOutput.toJson([
        service: 'checkout',
        environment: 'production',
        version: env.GIT_COMMIT.take(12),
        status: currentBuild.currentResult == 'SUCCESS' ? 'succeeded' : 'failed',
        commit: env.GIT_COMMIT,
        repository: env.GIT_URL,
        ci_url: env.BUILD_URL,
      ])
    }
    withCredentials([string(credentialsId: 'molesignal-token', variable: 'MOLESIGNAL_TOKEN')]) {
      sh '''
        curl -fsS -X POST "https://<host>/api/v1/apm/deployments" \
          -H "Authorization: Bearer $MOLESIGNAL_TOKEN" \
          -H "Content-Type: application/json" \
          --data-binary @deployment.json
      '''
    }
  }
}
```

## Registre alterações de configuração e de flags de recurso

Registre alterações de configuração ou de flags de recurso no mesmo endpoint. Defina `kind` e
descreva o que mudou. Não é necessário informar a versão.

```bash
curl -X POST "https://<host>/api/v1/apm/deployments" \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{"service": "checkout", "environment": "production", "kind": "feature_flag", "description": "new_checkout on for 10% of users"}'
```

## Solução de problemas

| Sintoma | O que verificar |
|---|---|
| Uma implantação registrada não aparece na linha do tempo | O intervalo deve incluir `deployedAt`, e `service` deve usar o mesmo nome de serviço do APM. Uma implantação registrada com um ambiente só aparece nesse ambiente. |
| Uma implantação e a versão implantada aparecem em duas linhas | O valor registrado em `version` difere do valor de `service.version` nos spans. Registre o mesmo valor. |
| O endpoint de implantações retorna `403` | O token não pode usar `apm.deploy`: a permissão está fora do escopo ou o membro ou a conta de serviço associados não têm essa permissão. |
| O endpoint de implantações retorna `400` | Um campo não respeita um dos limites da tabela acima. A mensagem de erro identifica o campo. |
