Um **pipeline de alertas** processa eventos de alerta antes da abertura dos incidentes correspondentes. As etapas podem reescrever o título do incidente, alterar o nível de severidade, adicionar ou remover rótulos e anotações, identificar os serviços afetados ou descartar o evento para impedir a abertura do incidente. Em seguida, o [roteamento](/pt-BR/alerting/routing) e as notificações usam o incidente com as alterações feitas pelos pipelines.

Um evento de alerta vem de uma destas quatro origens:

| Origem | Eventos |
|---|---|
| **Regras de alerta** | Uma [regra de alerta](/pt-BR/alerting/rules) dispara. |
| **Origens externas** | Uma [origem de alertas](/pt-BR/alerting/sources) recebe um alerta de outro sistema. |
| **Verificações sintéticas** | Uma [verificação sintética](/pt-BR/synthetics#incidentes-de-alerta) falha ou não tem resultados. |
| **Sem dados** | Uma regra abre um [incidente por falta de dados](/pt-BR/alerting/rules#recuperação-e-ausência-de-dados). |

Incidentes abertos manualmente não passam por pipelines de alertas antes da abertura.

Um pipeline também pode rodar [antes de uma notificação](#antes-de-uma-notificação). Nesse caso, ele processa uma cópia do evento e altera apenas o que uma política de notificação envia.

## Crie um pipeline de alertas

Abra **Pipelines**, selecione **Novo pipeline** e defina **Modo de execução** como **Eventos de alerta**. O **Tipo de sinal** mostra **Eventos de alerta**, e as configurações usam uma [**Ordem**](#ordem) em vez de um agendamento. O fluxo tem três nós:

| Nó | Significado |
|---|---|
| **Eventos de alerta** | Os eventos de alerta que o pipeline processa. Consulte [Condições](#condições). |
| **Em processamento** | As etapas, na ordem em que o pipeline as executa. Consulte [Etapas](#etapas). |
| **Aplicar ao incidente** | O incidente abre com os dados do evento após o processamento pelas etapas. |

**Teste** executa as etapas em um evento de alerta de exemplo antes de salvar o pipeline. As etapas tratam o evento como um disparo de regra de alerta cujo incidente está prestes a abrir: `%source` é `rule` e `%event` é `opened`. Edite o **Evento de exemplo** para experimentar outros valores e selecione **Executar teste**. O resultado mostra o evento após cada etapa ou indica qual etapa o descartou. O teste não armazena dados nem faz chamadas externas: as etapas **Resumo por IA** e **Adicionar resultados da consulta** escrevem `…` nas respectivas anotações, e a etapa **Chamar uma API** repassa o evento sem alterações, com a indicação **não chamado durante o teste**.

**Usar um evento de alerta recente** disponibiliza os 20 incidentes mais recentes dos últimos 7 dias para usuários com a permissão `alerts.incidents.read`. Selecione um incidente para preencher o **Evento de exemplo** com o evento correspondente. As etapas leem a regra e a origem desse evento. O incidente aparece tal como foi armazenado, com as alterações que os pipelines fizeram na abertura.

Nas configurações, use a opção **Processar eventos de alerta** para ativar ou desativar o pipeline. Quando desativado, o pipeline deixa todos os eventos de alerta passarem sem alterações. Selecione **Criar pipeline** para salvar. Cada alteração salva chega a todos os nós em até 10 segundos.

## Condições

Selecione o nó **Eventos de alerta** para escolher quais eventos o pipeline processa:

- **Origens**: **Regras de alerta**, **Origens externas**, **Verificações sintéticas** e **Sem dados**. Um incidente por falta de dados de uma regra conta como **Sem dados**, não como **Regras de alerta**. Um incidente por falta de resultados de uma verificação sintética conta como **Verificações sintéticas**.
- **Níveis de severidade**: **Crítico**, **Erro**, **Aviso** e **Informativo**.
- **Rótulos**: **Adicionar condição de rótulo** adiciona um rótulo e um valor. O evento precisa ter cada rótulo com o valor exato especificado.
- **Horário**: **A qualquer hora**, **Somente dentro desses horários** ou **Somente fora desses horários**. Defina intervalos semanais em um único fuso horário. O pipeline verifica o horário no momento da abertura do incidente. Por exemplo, descarte um tipo de alerta apenas durante as duas horas de execução de uma tarefa noturna de ETL.

Acima das condições, **Quando** indica em que momento o pipeline roda: **Antes da abertura do incidente**, a opção padrão, ou [**Antes de uma notificação**](#antes-de-uma-notificação).

Se nenhuma opção estiver marcada em uma lista, o pipeline aceita todas as origens ou todos os níveis de severidade, conforme a lista. Um pipeline sem condições processa todos os eventos de alerta. Se um evento não atender às condições, ele passa pelo pipeline sem alterações.

## Ordem

Os pipelines de alertas rodam em sequência, começando pelo menor valor de **Ordem**. Quando têm o mesmo valor, os pipelines rodam em ordem de nome. Cada pipeline recebe o evento com as alterações dos pipelines anteriores e verifica se ele atende às próprias condições. Assim, se um pipeline aumentar o nível de severidade, o evento pode passar a atender às condições de um pipeline posterior.

## Etapas

**Adicionar etapa** oferece as etapas de análise e de manipulação de campos dos outros pipelines, incluindo **Consultar uma tabela de extensão**, além de **Filtrar eventos**, **Resumo por IA**, **Chamar uma API**, **Adicionar resultados da consulta** e **VRL personalizado**. Consulte [Etapas de processamento](/pt-BR/pipelines#etapas-de-processamento). Em um pipeline de alertas, **Renomear por padrão** e **Manter apenas estes campos** começam em `labels`. Um pipeline de alertas não faz amostragem nem roteamento: ao converter um pipeline em pipeline de alertas, remova qualquer etapa **Amostra** ou **Rotear para um fluxo** antes de salvar.

### O evento de alerta

As etapas recebem o evento de alerta em JSON:

```json
{
  "summary": "Checkout error rate above 5%",
  "severity": "error",
  "labels": { "service": "checkout", "env": "prod", "host_name": "web-01" },
  "annotations": { "runbook": "https://wiki.example.com/checkout" },
  "affected_services": ["checkout"]
}
```

| Campo | Conteúdo | O que uma etapa pode definir |
|---|---|---|
| `summary` | O título do incidente. | Texto não vazio. O pipeline trunca o texto após 512 caracteres. |
| `severity` | A gravidade do incidente. | `info`, `warning`, `error` ou `critical`, sem distinção entre maiúsculas e minúsculas. O pipeline interpreta `warn` como `warning` e `crit` como `critical`. |
| `labels` | Os rótulos do incidente. | Um objeto com valores de texto. O pipeline converte números e booleanos em texto, e `null` remove o rótulo. |
| `annotations` | As anotações do incidente. | O mesmo que em `labels`. |
| `affected_services` | Os nomes dos serviços afetados. | Uma lista de nomes. O pipeline descarta nomes repetidos ou vazios. |

O pipeline ignora campos adicionais que uma etapa adiciona e preserva os valores dos campos que ela remove. Para limpar os rótulos, defina `.labels = {}`. Um valor fora dessas regras, como um objeto dentro de `labels`, faz o pipeline falhar. Consulte [O que acontece com um evento](#o-que-acontece-com-um-evento).

Os rótulos que o próprio MoleSignal define, como `alert.source` e `external.kind`, mantêm os valores originais independentemente do que uma etapa faça, pois indicam a origem do incidente. Uma etapa pode ler esses rótulos.

### De onde vem o evento

Uma etapa lê a origem do evento nos metadados. Os valores não se tornam campos do incidente.

| Metadado | Valor |
|---|---|
| `%source` | `rule`, `external`, `synthetic` ou `no_data`. |
| `%rule_id` | O ID da regra, da origem do alerta ou da verificação sintética. |
| `%rule_name` | O nome da regra, da origem do alerta ou da verificação sintética. |
| `%event` | `opened` antes da abertura do incidente e `severity_changed` quando a origem dispara outro alerta enquanto o incidente está aberto. Consulte [Mudanças de gravidade](#alterações-de-severidade). |

```ruby
# alerts from staging page no higher than warning
if .labels.env == "staging" && (.severity == "critical" || .severity == "error") {
  .severity = "warning"
}

# the team that owns the host, from the extend table host_owner
owner = lookup("host_owner", .labels.host_name)
if is_object(owner) {
  .labels.team = owner.team
}

# a known false alarm opens no incident
if %rule_name == "Disk inode usage" && .labels.mount == "/boot" {
  abort
}
```

O rótulo `team` que a segunda etapa define pode direcionar o incidente à equipe indicada. Consulte [Ordem de roteamento](/pt-BR/alerting/routing#ordem-de-roteamento). `lookup` e `geoip_lookup` funcionam em pipelines de alertas como em qualquer etapa de VRL. Consulte [Consultar tabelas e endereços IP](/pt-BR/functions#consultar-tabelas-e-endereços-ip).

### Resumo por IA

Uma etapa **Resumo por IA** envia o evento de alerta, no estado em que as etapas anteriores o deixaram, ao modelo da organização junto com o **Prompt**. A etapa grava a resposta na anotação indicada em **Anotação**, que por padrão é `ai_summary`. Exemplo de prompt:

```text
Summarize this alert for the on-call engineer in two sentences: what is wrong, and what to check first.
```

- A etapa consulta o modelo uma única vez, na abertura do incidente. Uma [mudança de gravidade](#alterações-de-severidade) não gera outra consulta.
- A etapa usa o [provedor de modelos](/pt-BR/agent#configure-um-provedor-de-modelos) habilitado com chave de API que recebeu a atualização mais recente e usa o **Modelo padrão** desse provedor. A resposta respeita o **Máximo de tokens de saída** do provedor ou o limite de 512 tokens se não houver configuração.
- A etapa envia ao provedor de modelos o título, a gravidade, os rótulos, as anotações e os serviços afetados do alerta.
- As chamadas consomem o [orçamento diário de tokens](/pt-BR/agent#uso-e-orçamento) da organização e aparecem como **Funções de LLM** no uso por origem. A configuração `[functions].llm_eval_enabled` não se aplica a essas chamadas.
- Se o modelo não puder responder por falta de um provedor configurado, por esgotamento do orçamento diário ou por falha na chamada, a etapa falha. Com isso, o pipeline inteiro falha e descarta também as demais alterações. Para preservar as alterações dos outros pipelines mesmo se o resumo falhar, coloque a etapa **Resumo por IA** em um pipeline separado e posicione esse pipeline depois dos demais.

### Chamar uma API

Uma etapa **Chamar uma API** envia o evento de alerta via POST a um dos [conectores HTTP](/pt-BR/connectors#destinos) da organização e aplica as alterações da resposta. A etapa usa o endereço e a credencial do conector e aplica as verificações de saída do conector: primeiro resolve o host e usa apenas o endereço obtido nessa resolução para se conectar, recusa endereços de metadados da nuvem e não segue redirecionamentos.

O corpo contém o evento no estado em que as etapas anteriores o deixaram, com a origem ao lado dos demais campos:

```json
{
  "summary": "Checkout error rate above 5%",
  "severity": "error",
  "priority": null,
  "urgency": null,
  "labels": { "service": "checkout" },
  "annotations": {},
  "affected_services": ["checkout"],
  "metadata": { "rule_id": "…", "rule_name": "Checkout errors", "source": "rule", "event": "opened" }
}
```

- A etapa usa apenas os campos `summary`, `severity`, `priority`, `urgency`, `labels`, `annotations` e `affected_services` do objeto JSON retornado, de acordo com as regras de [O evento de alerta](#o-evento-de-alerta). A etapa mescla `labels` e `annotations` chave por chave, e `null` remove uma chave. Assim, um serviço pode responder apenas com os dados que acrescenta. Uma resposta vazia não altera nada.
- A chamada tem um limite de 5 segundos e ocorre uma única vez, na abertura do incidente. Uma [mudança de gravidade](#alterações-de-severidade) não dispara outra chamada.
- Quando a chamada falha (sem resposta no prazo, código de status fora da faixa 2xx, corpo que não é um objeto JSON ou excede 1 MiB, campo que viola as regras ou conector desativado ou removido), o pipeline considera apenas essa etapa como não concluída. O evento segue como estava antes da etapa, as etapas seguintes são executadas e as alterações das etapas anteriores são preservadas. A [linha do tempo](#o-que-acontece-com-um-evento) e as [contagens](#contagens-diárias) indicam o motivo.

### Adicionar resultados da consulta

Uma etapa **Adicionar resultados da consulta** executa uma consulta com valores do evento e grava as linhas em uma anotação:

```sql
SELECT count(*) AS errors FROM app_logs WHERE level = 'error' AND host = '{{labels.host_name}}'
```

| Campo | Significado |
|---|---|
| **Linguagem** | SQL ou PromQL. PromQL lê um fluxo de métricas. |
| **Tipo de fluxo**, **Fluxo** | O fluxo que a consulta lê. A etapa não pode ler `_audit`, pois é executada sem que a permissão `audit.read` de qualquer usuário se aplique. |
| **Consulta** | Uma única consulta, com marcadores de substituição. |
| **Janela retrospectiva (segundos)** | Quanto tempo antes da abertura do incidente a consulta abrange. O padrão é 300, com máximo de 86.400. |
| **Linhas** | Quantas linhas entram na anotação. O padrão é 5, com máximo de 50. |
| **Anotação** | A anotação que recebe as linhas. O padrão é `query_result`. |

Um marcador de substituição representa um valor do evento: `{{labels.<key>}}`, `{{annotations.<key>}}`, `{{summary}}`, `{{severity}}`, `{{priority}}`, `{{urgency}}`, `{{rule_id}}`, `{{rule_name}}` ou `{{source}}`. Como os rótulos podem vir de outros sistemas, coloque cada marcador dentro de uma string da instrução, entre aspas. Nesse contexto, a etapa aplica o escape ao valor. Se o marcador estiver em qualquer outro lugar, o MoleSignal retorna `400` ao salvar.

- A anotação contém uma linha de texto por linha do resultado: se houver um único valor, mostra apenas esse valor; se houver vários, usa o formato `column=value, column=value`. A anotação comporta até 4.000 caracteres. Se a consulta não retornar nenhuma linha, a etapa não inclui a anotação.
- A consulta tem um limite de 10 segundos e é executada uma única vez, na abertura do incidente.
- Se a consulta falhar ou o evento não tiver um valor para um marcador de substituição, o pipeline considera apenas essa etapa como não concluída, assim como em [**Chamar uma API**](#chamar-uma-api).

## O que acontece com um evento

Cada pipeline que recebe um evento termina com um de três resultados:

| Resultado | Causa | Efeito |
|---|---|---|
| **Processado** | As etapas chegaram ao fim. | O evento segue com as alterações das etapas. |
| **Descartados** | Uma etapa executou `abort`. | Nenhum incidente é aberto, e os pipelines seguintes não são executados. |
| **Falhou** | Uma etapa falhou ou as etapas deixaram um campo que viola as regras de [O evento de alerta](#o-evento-de-alerta). Falhas nas etapas **Chamar uma API** e **Adicionar resultados da consulta** também contam aqui. | O pipeline descarta as próprias alterações, exceto quando apenas uma dessas etapas falha. Nesse caso, as alterações das outras etapas permanecem. O evento segue para o próximo pipeline, e o incidente ainda é aberto. |

A [linha do tempo](/pt-BR/alerting/incidents#detalhes-do-incidente) do incidente exibe uma linha para cada pipeline que fez alguma alteração ou falhou: **Passou pelo pipeline Roteamento de pagamentos: severidade error → critical, rótulos +team=payments**. Em caso de falha, a linha também mostra o motivo. A linha do tempo não registra pipelines que não fizeram alterações nem [alterações de severidade](#alterações-de-severidade). Cada linha mostra até 40 alterações e informa quantas ficaram de fora. Valores longos são truncados em 200 caracteres.

Quando uma regra continua disparando, o pipeline descarta o evento a cada avaliação. A [lista de regras](/pt-BR/alerting/rules#lista-de-regras) mostra o estado da regra como **Descartada pelo pipeline**, e o campo `last_state` na API tem o valor `{"kind": "dropped"}`. O pipeline que descartou o evento contabiliza o descarte, e a **Visão geral** identifica a regra do descarte mais recente. Quando um pipeline descarta um alerta externo, a seção [**Solicitações recentes**](/pt-BR/alerting/sources#solicitações-recentes) da origem do alerta mostra **Ignorado**, junto com o pipeline e a etapa que descartou o alerta.

## Alterações de severidade

Enquanto um incidente está aberto, os pipelines de alerta reavaliam a severidade sempre que a regra de alerta volta a disparar, a origem externa reenvia o alerta ou a verificação sintética muda de estado:

- O MoleSignal monta o evento da mesma forma que na abertura do incidente, com a severidade que a origem informa agora. O evento passa pelos pipelines que o aceitam, sem executar as etapas **Resumo por IA**, **Chamar uma API** e **Adicionar resultados da consulta**, e `%event` tem o valor `severity_changed`.
- O MoleSignal considera apenas a severidade resultante das etapas e atualiza o incidente se o valor for diferente. O título, os rótulos, as anotações e os serviços mantêm os valores definidos na abertura do incidente.
- Um descarte ou uma falha em um pipeline não altera o incidente: ele continua aberto, e o próximo pipeline é executado.

Assim, uma etapa que reduz a severidade dos alertas do ambiente de homologação continua fazendo isso mesmo que a regra informe uma severidade maior depois. Incidentes reconhecidos ou com severidade definida manualmente mantêm a severidade atual.

## Antes de uma notificação

Defina **Quando** como **Antes de uma notificação** no nó **Eventos de alerta** para executar o pipeline quando uma [política de notificação](/pt-BR/notification-channels) estiver prestes a enviar uma notificação sobre um evento de alerta. O pipeline usa uma cópia do evento a cada envio de cada política aplicável, inclusive nas etapas posteriores e no escalonamento. Use o pipeline para encurtar um título em uma política de SMS, adicionar um rótulo ao webhook de uma equipe ou silenciar uma política à noite, sem alterar o incidente.

- **Políticas de notificação** indica a quais políticas o pipeline se aplica. Se nenhuma estiver selecionada, o pipeline se aplica a todas as políticas do evento de alerta. Nesse momento, a política já verificou a correspondência com base no evento original.
- As outras condições funcionam como antes e são avaliadas com base no evento da notificação. O horário é o da ocorrência do evento, e **Origens** inclui a opção **Incidentes abertos manualmente**.
- As etapas são executadas apenas dentro do MoleSignal. **Resumo por IA**, **Chamar uma API** e **Adicionar resultados da consulta** só são executadas na abertura de um incidente. Um pipeline com qualquer uma dessas etapas retorna `400` nesse estágio.
- O fluxo termina em **Na notificação**. A política usa o título, a severidade, a prioridade, a urgência, os rótulos, as anotações e os serviços resultantes das etapas nos [modelos](/pt-BR/notification-channels#variáveis-do-modelo), no corpo dos webhooks e no texto padrão. A política determina os destinatários com base no evento original.
- Uma etapa que executa `abort` impede o envio pela política. O log de entregas mostra um registro **Ignorado** com o motivo, que identifica o pipeline e a etapa no idioma padrão do espaço de trabalho (`error_code` `dropped_by_pipeline`). A linha do tempo do incidente também registra o descarte. Isso não conta como falha: a política não tenta enviar de novo, e o escalonamento por tempo limite de reconhecimento não prossegue.
- Se um pipeline falhar, o MoleSignal descarta as alterações desse pipeline e envia a notificação sem essas alterações. A falha aparece nas [contagens](#contagens-diárias), não na linha do tempo.

Além de `%rule_id`, `%rule_name` e `%source`, as etapas leem `%policy_id` e `%policy_name`, e `%event` tem o valor `triggered`, `escalated`, `acknowledged` ou `resolved`. `%rule_name` contém o nome da regra ou, quando nenhuma regra abriu o incidente, o título do evento. **Teste** usa os valores de exemplo `triggered` e `On-call alerts`.

```ruby
# on-call alerts of the staging environment go out only for what is critical
if %policy_name == "On-call alerts" && .labels.env == "staging" && .severity != "critical" {
  abort
}
```

## Contagens diárias

Um pipeline de alerta não registra execuções. Por isso, não tem histórico de execuções nem oferece a opção **Mais → Preenchimento retroativo**. Em vez disso, contabiliza os resultados do dia atual (UTC):

- Na lista, o **Status** de um pipeline de alerta ativado é **Aguardando eventos de alerta**, e a coluna **Última execução** mostra as contagens, como **Hoje: 41 processados · 3 descartados · 0 falhas**.
- Na **Visão geral** do pipeline, **Processado**, **Descartados** e **Falhou** mostram as mesmas contagens. **Descartados** identifica a regra ou a origem do descarte mais recente e informa quando ocorreu. **Falhou** mostra o motivo da falha mais recente.

As contagens voltam a zero à meia-noite UTC. O MoleSignal não conta eventos que não atendem às condições nem execuções por [alteração de severidade](#alterações-de-severidade). A API retorna as contagens em `alert_record`. Consulte [Gerenciar pipelines](/pt-BR/api/intake/scheduled-pipelines#consultar).

## Limites

| Limite | Valor |
|---|---|
| Etapas por pipeline de alerta | 20 |
| Prompt de uma etapa **Resumo por IA** | 8 KiB |
| Nome da anotação | 255 bytes |
| Resposta de uma etapa **Chamar uma API** | 1 MiB, em até 5 segundos |
| Instrução de consulta de uma etapa **Adicionar resultados da consulta** | 8 KiB |
| Linhas de uma etapa **Adicionar resultados da consulta** | 50, em até 10 segundos |
| Texto gerado por uma etapa **Adicionar resultados da consulta** | 4.000 caracteres |

## Criar um pipeline de alerta pela API

Salve um pipeline de alerta como qualquer outro pipeline: defina `functionSteps.mode` como `alert` e deixe os fluxos e o agendamento vazios:

```bash
curl -X POST http://localhost:5080/api/v1/scheduled_pipelines \
  -H "authorization: Bearer $MS_TOKEN" \
  -H 'content-type: application/json' \
  -d '{
    "name": "staging-alerts",
    "sourceStream": "",
    "targetStream": "",
    "cron": "",
    "enabled": true,
    "functionSteps": {
      "mode": "alert",
      "alert": {
        "sources": ["rule", "external"],
        "severities": [],
        "labels": { "env": "staging" },
        "order": 10
      },
      "steps": [
        { "transformName": "cap-severity", "kind": "vrl",
          "script": "if .severity == \"critical\" { .severity = \"warning\" }" },
        { "transformName": "summary", "kind": "ai_summary",
          "prompt": "Summarize this alert in two sentences for the on-call engineer.",
          "annotation": "ai_summary" }
      ]
    }
  }'
```

Para executar o pipeline antes das notificações, defina `alert.stage` como `notify` e, se necessário, especifique `alert.policies`:

```json
{
  "mode": "alert",
  "alert": { "stage": "notify", "policies": ["<policy id>"], "labels": { "env": "staging" }, "order": 10 },
  "steps": [
    { "transformName": "quiet", "kind": "vrl", "script": "if .severity != \"critical\" { abort }" }
  ]
}
```

Consulte [Criar um pipeline](/pt-BR/api/intake/create-pipeline) para ver todos os campos. Os pipelines de alerta usam as mesmas [permissões dos demais pipelines](/pt-BR/pipelines#permissões).
