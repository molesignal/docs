```http
GET    /api/v1/alerts/holiday-calendars
POST   /api/v1/alerts/holiday-calendars
GET    /api/v1/alerts/holiday-calendars/{id}
PUT    /api/v1/alerts/holiday-calendars/{id}

GET    /api/v1/alerts/holiday-calendars/{id}/references
POST   /api/v1/alerts/holiday-calendars/parse
```

A leitura exige `alerts.calendars.read`; a criação, a alteração, a exclusão e a leitura de arquivos exigem `alerts.calendars.manage`.
Consulte [Calendários de feriados](/pt-BR/alerting/on-call#calendários-de-feriados) para saber como afetam os horários semanais.

## Crie ou altere um calendário

`POST` cria um calendário e `PUT` substitui um calendário existente. A resposta contém o calendário com os campos `id`,
`orgId`, `createdBy`, `createdAt` e `updatedAt`.

| Campo | Tipo | Obrigatório | Descrição |
|---|---|---|---|
| `name` | string | Sim | Até 80 caracteres. O nome deve ser único na organização. |
| `description` | string | Não | Até 500 caracteres. |
| `days` | array | Não | Até 2.000 dias, no formato `{"date": "2026-10-01", "kind": "holiday", "name": "National Day"}`. `kind` aceita `holiday` (dia de folga) ou `workday` (dia de trabalho compensatório, que conta como segunda-feira). `name` aceita até 80 caracteres. Cada data só pode aparecer uma vez. |

<RequestExample>
```bash cURL
curl -X POST http://localhost:5080/api/v1/alerts/holiday-calendars \
  -H "authorization: Bearer $MS_TOKEN" \
  -H "content-type: application/json" \
  -d '{"name": "China 2026", "days": [{"date": "2026-10-01", "kind": "holiday", "name": "National Day"}, {"date": "2026-10-10", "kind": "workday", "name": "Make-up workday"}]}'
```
</RequestExample>

Para usar um calendário, informe o ID no campo `calendar` dos horários semanais:
`{"calendarId": "<id>", "holidays": "exclude"}` exclui os dias de folga, e `"holidays": "only"`
aplica os horários apenas nos dias de folga. Os horários semanais aceitam calendários nos horários de atendimento das
[políticas de escalonamento](/pt-BR/api/alerting/create-escalation), nas condições de horário das
[regras de roteamento](/pt-BR/api/alerting/create-routing-rule) e das políticas de notificação, nos rodízios das escalas de
plantão, nos pipelines de alertas e nas janelas semanais de silenciamento. Se o calendário não pertencer à
organização, a tentativa de salvar qualquer um desses recursos retorna `400`.

## Leia um arquivo ICS

`POST /parse` aceita `{"content": "<the .ics text>"}` de até 2 MiB e retorna `{"days": [...]}` sem
salvar nada: cada evento de dia inteiro gera um dia, um evento de vários dias gera uma entrada por dia,
e um nome que contém 补班 ou 上班, ou termina em 班, gera um `workday`.

## Veja quais recursos usam um calendário

`GET /{id}/references` lista os recursos que usam o calendário no formato `{"kind", "id", "name"}`. Os valores de `kind` são
`routing_rule`, `escalationPolicy`, `schedule`, `mute_rule`, `notify_policy` ou `alert_pipeline`.
`DELETE` retorna `409` enquanto a lista não estiver vazia.

**Erros**

| Status | Motivo |
|---|---|
| `400` | Um campo está fora dos limites permitidos, uma data aparece duas vezes ou não é possível ler o arquivo. |
| `403` | O token não tem a permissão necessária. |
| `404` | O calendário não existe na organização. |
| `409` | Outro calendário tem o mesmo nome ou o calendário está em uso. |
