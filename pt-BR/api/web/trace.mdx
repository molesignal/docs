Todas as chamadas leem um único stream de rastreamentos da organização: o stream que tem todos os campos `trace_id`, `span_id`, `service.name`, `name`, `start_time_unix_nano`, `end_time_unix_nano` e `status_code`. Um stream chamado `default` prevalece sobre outros streams que se qualificam, e o nome do stream desempata os casos restantes. Uma organização sem esse stream recebe resultados vazios. Apenas os rastreamentos que sobreviveram à [amostragem de cauda](/pt-BR/configuration#captura-de-traces-e-amostragem-ao-final) podem ser lidos.

Todas as chamadas exigem `traces.read`, ou `sys.telemetry.read` no escopo do sistema.

## Listar resumos de rastreamentos

```http
GET /api/v1/web/traces
```

Retorna um resumo por rastreamento, com paginação por cursor. Um stream que ainda não tem resumos de rastreamentos responde com uma página vazia.

**Parâmetros de consulta**

| Parâmetro | Tipo | Observações |
|---|---|---|
| `from`, `to` | integer | A janela em microssegundos. Os padrões são as últimas 24 horas até agora. `to` deve ser maior que `from`. |
| `q` | string | Texto sem distinção entre maiúsculas e minúsculas que deve aparecer no `trace_id`, no `span_id`, no serviço, na operação ou no status de um span. Até 256 caracteres. |
| `filters` | string | Um array JSON de filtros. Consulte abaixo. |
| `where` | string | Uma árvore de condições JSON: filtros e texto unidos por AND e OR. Consulte abaixo. |
| `expression` | string | Uma consulta de campos como a página **Rastreamentos** a escreve. Ela equivale a `q`, `filters` e `where`: envie um ou outro. Consulte abaixo. |
| `sort` | string | `latest` (padrão), `earliest`, `duration_desc`, `duration_asc`, `span_count_desc` ou `errors_desc`. |
| `limit` | integer | Tamanho da página. Padrão `20`. O valor é limitado entre 1 e 5000. |
| `cursor` | string | O `nextCursor` ou `previousCursor` de uma página anterior. |
| `fields` | string | Campos do span raiz de cada rastreamento a retornar junto com ele, separados por vírgula, nomeados como o stream os nomeia. Até 12. Um campo desconhecido, um campo JSON ou um campo `molesignal.trace.*` responde `400`. |

Um filtro é um objeto com `field`, `op` e `value`, e uma requisição inclui no máximo 32 filtros. Todos os filtros devem corresponder. O operador `in` usa `values`, uma lista de valores, no lugar de `value`.

| Campo | Tipo | Operadores |
|---|---|---|
| `trace_id` | text | `=`, `!=`, `contains`, `in` |
| `duration_ns`, `span_count`, `error_count` | integer | `=`, `!=`, `>`, `>=`, `<`, `<=`, `in` |
| Qualquer outro campo escalar do stream de rastreamentos | pelo tipo do campo | Texto: `=`, `!=`, `contains`, `in`. Números e timestamps: `=`, `!=`, `>`, `>=`, `<`, `<=`, `in`. Booleanos: `=`, `!=`, `in`. |

Um filtro nomeia seu campo como o stream o nomeia, como `service.name` ou `name`; nenhum outro nome representa um campo. Os operadores `eq`, `ne` e `like` são aliases de `=`, `!=` e `contains`. Um campo JSON não é filtrável.

`trace_id`, `duration_ns`, `span_count` e `error_count` são comparados no rastreamento. Todo outro campo pertence a um span: um filtro nele corresponde a um rastreamento quando um de seus spans passa pelo filtro, e `!=` corresponde a um rastreamento quando nenhum de seus spans tem o valor. Um span sem o campo não tem o valor.

`in` corresponde a qualquer um de seus `values`: de 1 a 64 valores, cada um com até 512 bytes e do tipo do campo. Um valor listado duas vezes conta uma vez. Em um campo de span, `in` corresponde a um rastreamento quando um de seus spans tem um dos valores.

`where` expressa o que a lista de filtros não consegue: alternativas. Ele é um objeto JSON em uma de quatro formas:

| Forma | Corresponde a |
|---|---|
| Um filtro, como em `filters` | O filtro. |
| `{"text": "..."}` | O texto, como `q` corresponde a ele. |
| `{"and": [...]}` | Todas as condições da lista. |
| `{"or": [...]}` | Qualquer condição da lista. |

`filters`, `q` e `where` funcionam juntos. Um filtro na árvore mantém seu significado: um em um campo de span corresponde a um rastreamento quando um de seus spans passa por ele, e `!=` quando nenhum de seus spans tem o valor. Um rastreamento corresponde a `{"or": [A, B]}` quando corresponde a `A` ou corresponde a `B`. Os filtros de `filters` e `where` contam juntos para o limite de 32. Uma árvore procura texto no máximo 8 vezes, aninha grupos no máximo 8 níveis e tem pelo menos uma condição em cada grupo.

```bash
curl -G "http://localhost:5080/api/v1/web/traces" \
  -H "authorization: Bearer $MS_TOKEN" \
  --data-urlencode 'filters=[{"field":"status_code","op":"=","value":"ERROR"}]' \
  --data-urlencode 'where={"or":[{"field":"service.name","op":"=","value":"checkout"},{"field":"span_count","op":">","value":"50"}]}'
```

A requisição lista os rastreamentos com falha que têm um span de `checkout` ou mais de 50 spans.

`expression` usa o texto da página **Rastreamentos** em vez disso: comparações com `=`, `!=`, `>`, `>=`, `<`, `<=`, `contains` e `field in ('a', 'b')`, palavras a encontrar, uma frase entre aspas, `AND` e `OR` independentemente de maiúsculas e minúsculas, com `AND` tendo maior precedência, e colchetes. O servidor o lê para os `q`, `filters` e `where` que a página envia, e os verifica como acima. O texto tem no máximo 8 KiB e aninha colchetes no máximo 32 níveis. Uma parte que ele não consegue ler, como um colchete não fechado ou uma comparação sem nada, responde `400` e nomeia a parte.

```bash
curl -G "http://localhost:5080/api/v1/web/traces" \
  -H "authorization: Bearer $MS_TOKEN" \
  --data-urlencode "expression=status_code = 'ERROR' AND (service.name = 'checkout' OR span_count > 50)"
```

A requisição lista os mesmos rastreamentos que a anterior.

Um `cursor` vincula a página à consulta que a emitiu. Repetir uma requisição com um cursor e um `limit`, `sort`, `q`, `filters` ou `where` diferente responde `400`.

<RequestExample>
```bash cURL
curl -G "http://localhost:5080/api/v1/web/traces" \
  -H "authorization: Bearer $MS_TOKEN" \
  --data-urlencode 'sort=duration_desc' \
  --data-urlencode 'limit=2' \
  --data-urlencode 'fields=http.route' \
  --data-urlencode 'filters=[{"field":"service.name","op":"in","values":["checkout","payments"]}]'
```
</RequestExample>

<ResponseExample>
```json 200
{
  "items": [
    {
      "traceId": "0af7651916cd43dd8448eb211c80319c",
      "service": "checkout",
      "operation": "GET /checkout",
      "startNs": 1790000000000000000,
      "durationMs": 180.0,
      "spanCount": 3,
      "errorCount": 1,
      "status": "ERROR",
      "httpStatusCode": 502,
      "fields": { "http.route": "/checkout" }
    }
  ],
  "nextCursor": null,
  "previousCursor": null,
  "hasMore": false
}
```
</ResponseExample>

Cada item descreve um rastreamento pela sua raiz: o `service` e a `operation` do span raiz, o horário de início em nanossegundos, a duração em milissegundos, o número de spans e o número de spans com erro. `hasMore` é `true` quando `nextCursor` está definido.

| Campo | Observações |
|---|---|
| `status` | O status do span raiz: `OK`, `ERROR` ou `UNSET`. |
| `httpStatusCode` | O `http.response.status_code` do span raiz, ou seu `http.status_code`, quando contém um código de 100 a 599. Ausente caso contrário, e para rastreamentos armazenados antes de o resumo guardá-lo. |
| `fields` | Os campos solicitados em `fields` para os quais o span raiz tem um valor. Ausente quando não tem nenhum. A página é respondida sem eles quando a leitura deles falha. |

## Contar rastreamentos ao longo do tempo

```http
GET /api/v1/web/traces/histogram
```

Conta todos os rastreamentos encontrados por uma consulta de lista, em buckets de tempo, pelo horário de início do rastreamento. A chamada usa a janela, `q`, `filters` e `where` da lista, e encontra os mesmos rastreamentos. O chamador escolhe os buckets.

**Parâmetros de consulta**

| Parâmetro | Tipo | Observações |
|---|---|---|
| `from`, `to` | integer | A janela em microssegundos. Ambos são obrigatórios. `to` deve ser maior que `from`. |
| `q`, `filters`, `where`, `expression` | string | O mesmo que para a lista. |
| `bucketTime` | integer | A duração de um bucket em microssegundos. Pelo menos `1000`. |
| `originTime` | integer | O início do primeiro bucket em microssegundos. Não depois de `from`. |

Uma requisição cobre no máximo 512 buckets de `originTime` até `to`.

<RequestExample>
```bash cURL
curl -G "http://localhost:5080/api/v1/web/traces/histogram" \
  -H "authorization: Bearer $MS_TOKEN" \
  --data-urlencode 'from=1790000100000000' \
  --data-urlencode 'to=1790003700000000' \
  --data-urlencode 'bucketTime=900000000' \
  --data-urlencode 'originTime=1790000100000000' \
  --data-urlencode 'filters=[{"field":"service.name","op":"=","value":"checkout"}]'
```
</RequestExample>

<ResponseExample>
```json 200
{
  "bucketTime": 900000000,
  "originTime": 1790000100000000,
  "buckets": [
    { "startTime": 1790000100000000, "total": 42, "errors": 3, "p50Ns": 41000000, "p95Ns": 180000000, "p99Ns": 320000000 },
    { "startTime": 1790001900000000, "total": 17, "errors": 0, "p50Ns": 38000000, "p95Ns": 95000000, "p99Ns": 120000000 }
  ],
  "split": true
}
```
</ResponseExample>

`buckets` lista apenas os buckets que contêm um rastreamento, do mais antigo para o mais recente. `total` é o número de rastreamentos que começaram no bucket. `errors` é o número desses rastreamentos com pelo menos um span com erro. `p50Ns`, `p95Ns` e `p99Ns` são as durações mediana, do 95º e do 99º percentil desses rastreamentos em nanossegundos. São estimativas e ficam ausentes quando nenhuma duração foi contada.

A contagem lê os resumos de rastreamentos, e os spans quando há um filtro em um campo de span. A lista retorna um resumo para cada rastreamento. Um resumo que uma gravação repetida armazenou duas vezes conta duas vezes.

Quando a contagem não está disponível, a chamada ainda responde `200`. `buckets` fica então vazio, e `unavailable` informa o motivo.

| `unavailable` | Causa |
|---|---|
| `time_budget` | A contagem levou mais de 20 segundos. |
| `busy` | As consultas da função preenchem [`[search.admission]`](/pt-BR/configuration#controle-de-admissão) e nenhum slot ficou livre dentro de seu `max_wait_secs`. |
| `scan_limit` | A janela contém mais linhas do que `[querier].max_scan_rows` permite que uma consulta leia. |

## Ler métricas de requisições

```http
GET /api/v1/web/traces/red
GET /api/v1/web/traces/red/breakdown
```

Lê a taxa, os erros e a duração das requisições encontradas por uma consulta de lista: no total, bucket a bucket, e por quanto tempo levaram. O detalhamento lê as mesmas métricas para cada valor de um campo. Uma requisição é um span. Por padrão, as requisições são os spans em que um serviço recebeu uma requisição: um span de servidor ou consumidor, ou a raiz de um trace. `scope=all` lê todos os spans.

Um filtro em um campo de span vale para o próprio span, então `service.name = 'api'` lê as requisições que `api` atendeu. `trace_id` e `duration_ns` são lidos do span, e `span_count` e `error_count` do trace ao qual o span pertence.

**Parâmetros de consulta**

| Parâmetro | Tipo | Observações |
|---|---|---|
| `from`, `to`, `bucketTime`, `originTime` | integer | O mesmo que para a contagem de traces ao longo do tempo. |
| `q`, `filters`, `where`, `expression` | string | O mesmo que para a lista. |
| `scope` | string | `entry` (padrão) ou `all`. |
| `by` | string | Somente para detalhamento e obrigatório nele: o campo pelo qual agrupar as requisições, como o stream o nomeia. |

<RequestExample>
```bash cURL
curl -G "http://localhost:5080/api/v1/web/traces/red" \
  -H "authorization: Bearer $MS_TOKEN" \
  --data-urlencode 'from=1790000100000000' \
  --data-urlencode 'to=1790003700000000' \
  --data-urlencode 'bucketTime=60000000' \
  --data-urlencode 'originTime=1790000100000000' \
  --data-urlencode "expression=service.name = 'checkout'"
```
</RequestExample>

<ResponseExample>
```json 200
{
  "bucketTime": 60000000,
  "originTime": 1790000100000000,
  "scope": "entry",
  "total": { "requests": 1840, "errors": 12, "p50Ns": 41000000.0, "p95Ns": 180000000.0, "p99Ns": 320000000.0 },
  "buckets": [
    { "startTime": 1790000100000000, "requests": 31, "errors": 0, "p50Ns": 40000000.0, "p95Ns": 150000000.0, "p99Ns": 210000000.0 }
  ],
  "latency": [
    { "fromNs": 0, "toNs": 50000000, "requests": 1203, "errors": 2 },
    { "fromNs": 50000000, "toNs": null, "requests": 637, "errors": 10 }
  ]
}
```
</ResponseExample>

`buckets` lista os buckets que contêm uma requisição, mais antigos primeiro. `latency` lista as requisições por duração, mais curtas primeiro; o último intervalo não tem limite superior. `errors` é `null` onde não é possível distinguir falhas, e as durações estão em nanossegundos, `null` sem requisição e onde as durações estão mascaradas.

O detalhamento responde `field`, `bucketTime`, `originTime`, `scope` e `groups`: os 50 valores mais comuns primeiro, cada um com suas métricas e uma `series` de buckets com `requests`, `errors` e `p95Ns`. `value` é `null` para as requisições sem valor. `more` é `true` quando existem mais valores do que os listados.

Quando as métricas não estão disponíveis, as chamadas ainda respondem `200` com `unavailable`: `time_budget`, `busy` e `scan_limit` como para a contagem de traces, `timestamp_masked` quando o tempo está mascarado para o leitor, e `field_protected` quando o campo de detalhamento está mascarado ou criptografado.

`by` também pode nomear uma chave dentro de um campo JSON, escrita após o nome do campo, como `attributes.tenant`: as requisições são agrupadas pelo que essa chave contém.

## Comparar as requisições lentas ou com falha

```http
GET /api/v1/web/traces/red/compare
```

Compara as requisições escolhidas de uma consulta com suas outras requisições, campo a campo: as requisições que falharam, que levaram pelo menos ou menos que determinado tempo, ou que atendem a tudo o que é fornecido. Para cada campo, a proporção de cada valor nos dois conjuntos é comparada, e os campos são classificados pelo quão distantes as proporções estão, de `0` (a mesma mistura) a `1` (nenhum valor em comum). IDs, momentos, durações e campos JSON são deixados de fora, assim como um campo cujos valores são quase todos diferentes de linha para linha. Quando as requisições com falha são escolhidas, `status_code` também é deixado de fora. Cada conjunto é lido como uma amostra de seus primeiros 1.000 spans.

**Parâmetros de consulta**

Os parâmetros das métricas RED, sem `by`, e:

| Parâmetro | Tipo | Observações |
|---|---|---|
| `errors` | boolean | Escolha as requisições com falha. |
| `minDuration` | integer | Escolha as requisições que levaram pelo menos esta quantidade de nanossegundos. |
| `maxDuration` | integer | Escolha as requisições que levaram menos que esta quantidade de nanossegundos. |

Pelo menos um deles é obrigatório, e `minDuration` deve ser menor que `maxDuration`.

<ResponseExample>
```json 200
{
  "scope": "entry",
  "selected": 212,
  "baseline": 1000,
  "sampled": true,
  "dimensions": [
    {
      "field": "cloud.region",
      "score": 0.71,
      "values": [
        { "value": "eu-west-1", "selected": 0.83, "baseline": 0.12 },
        { "value": "us-east-1", "selected": 0.17, "baseline": 0.88 }
      ]
    }
  ]
}
```
</ResponseExample>

`selected` e `baseline` são os spans lidos de cada conjunto, e `sampled` é `true` quando qualquer um dos conjuntos tinha mais. `dimensions` lista no máximo 20 campos, os mais distantes primeiro, cada um com no máximo 5 valores cujas proporções mais diferem. `value` é `null` para as requisições sem valor. `unavailable` é respondido como para as métricas RED.

## Listar spans

```http
GET /api/v1/web/traces/spans
```

Retorna uma linha por span que atende a uma consulta, com paginação por cursor. A chamada usa a janela, `q`, `filters` e `where` da lista de traces, e os lê para cada span: um filtro em um campo de span vale para o próprio span, e `!=` mantém um span sem o campo. `duration_ns` é a duração do próprio span. `span_count` e `error_count` são os do trace ao qual o span pertence. Um span corresponde a `{"or": [A, B]}` quando corresponde a `A` ou corresponde a `B`.

**Parâmetros de consulta**

| Parâmetro | Tipo | Observações |
|---|---|---|
| `from`, `to` | integer | A janela em microssegundos. Os padrões são as últimas 24 horas até agora. `to` deve ser maior que `from`. |
| `q`, `filters`, `where`, `expression` | string | O mesmo que para a lista de traces. |
| `sort` | string | `latest` (padrão), `earliest`, `duration_desc` ou `duration_asc`. |
| `limit` | integer | Tamanho da página. Padrão `100`. O valor é limitado entre 1 e 5000. |
| `cursor` | string | O `nextCursor` ou `previousCursor` de uma página anterior. O cursor carrega a consulta da página dele; um `limit` diferente responde `400`. |

<ResponseExample>
```json 200
{
  "items": [
    {
      "traceId": "0af7651916cd43dd8448eb211c80319c",
      "spanId": "53995c3f42cd8ad8",
      "parentSpanId": "b7ad6b7169203331",
      "service": "payments",
      "operation": "POST /pay",
      "startNs": 1790000000020000000,
      "durationNs": 140000000,
      "status": "ERROR",
      "kind": 2,
      "httpStatusCode": 502
    }
  ],
  "nextCursor": null,
  "previousCursor": null,
  "hasMore": false
}
```
</ResponseExample>

`status` é `OK`, `ERROR` ou `UNSET`. `kind` numera o tipo de span como o OTLP faz: `1` interno, `2` servidor, `3` cliente, `4` produtor, `5` consumidor. `parent_span_id`, `kind` e `http_status_code` estão ausentes quando o span não os tem. A chamada executa como uma consulta rastreada e é admitida como qualquer outra consulta.

## Ler um trace

```http
GET /api/v1/web/trace/{traceId}
```

Retorna todos os spans de um trace, ordenados pelo horário de início. `trace_id` tem de 1 a 128 caracteres entre `A-Z`, `a-z`, `0-9`, `-` e `_`.

**Parâmetros de consulta**

| Parâmetro | Tipo | Observações |
|---|---|---|
| `from`, `to` | integer | A janela em microssegundos em que os spans do trace começaram. Informe ambos ou nenhum. No máximo 31 dias. Sem eles, o trace é procurado nas últimas 24 horas. |

A resposta é limitada a 100.000 spans e 32 MiB. `truncated` é `true` quando um limite cortou a lista de spans.

<ResponseExample>
```json 200
{
  "traceId": "0af7651916cd43dd8448eb211c80319c",
  "rootSpanId": "b7ad6b7169203331",
  "spans": [
    {
      "spanId": "53995c3f42cd8ad8",
      "parentSpanId": "b7ad6b7169203331",
      "service": "payments",
      "operation": "POST /pay",
      "startNs": 1790000000020000000,
      "endNs": 1790000000160000000,
      "durationNs": 140000000,
      "kind": 2,
      "status": "ERROR",
      "statusMessage": "upstream timeout",
      "attributes": { "http.method": "POST", "http.status_code": "502" },
      "events": [],
      "links": [],
      "samplingReason": "error",
      "partial": false,
      "late": false,
      "duplicate": false,
      "conflict": false
    }
  ],
  "truncated": false,
  "partial": false,
  "partialReasons": [],
  "samplingReasons": ["error"],
  "lateSpanCount": 0,
  "duplicateSpanCount": 0,
  "conflictSpanCount": 0
}
```
</ResponseExample>

O exemplo mostra um span com seus campos principais. Um span real também carrega `traceFlags`, `traceState`, `resource`, `scope`, os contadores `dropped_*_count`, `schemaVersion` e `semanticConventionsVersion`.

| Campo | Observações |
|---|---|
| `rootSpanId` | O primeiro span sem pai. Monte a árvore a partir de `span_id` e `parent_span_id`. |
| `spans[].status` | `OK`, `ERROR` ou `UNSET`. |
| `spans[].attributes` | Os atributos do span, mesclados com as colunas de atributos achatadas do stream. |
| `spans[].sampling_reason` | Por que o tail sampler manteve o trace, por exemplo `error`. |
| `partial`, `partialReasons` | Se faltam spans e por quê. |
| `lateSpanCount`, `duplicateSpanCount`, `conflictSpanCount` | Os spans que chegaram atrasados, repetidos ou em conflito. |

## Encontre os spans que se vinculam a um trace

```http
GET /api/v1/web/trace/{traceId}/linked
```

Um span mantém links para os spans dos quais deriva, e o detalhe do trace os retorna com o span. Esta chamada encontra a direção oposta: spans de outros traces cujos links fazem referência a um span deste trace. Ela recebe os mesmos `from` e `to` do detalhe do trace e pesquisa nessa janela.

<ResponseExample>
```json 200
{
  "spans": [
    {
      "traceId": "4bf92f3577b34da6a3ce929d0e0e4736",
      "spanId": "00f067aa0ba902b7",
      "service": "billing-worker",
      "operation": "process invoice",
      "startNs": 1790000005000000000,
      "durationNs": 30000000,
      "status": "OK",
      "linkedSpanId": "53995c3f42cd8ad8",
      "attributes": { "messaging.operation": "process" }
    }
  ],
  "more": false
}
```
</ResponseExample>

`spans` lista até 200 spans vinculados, dos mais recentes para os mais antigos, e `more` é `true` quando mais spans se vinculam ao trace. `linkedSpanId` é o span deste trace para o qual o link aponta, e `attributes` contém os atributos do link.

A pesquisa lê os links de cada span na janela como texto, dentro do orçamento de tempo da contagem de traces. Quando não consegue terminar, a chamada ainda responde `200` com `spans` vazio e um motivo `unavailable`: `time_budget`, `busy` ou `scan_limit`, como na contagem de traces.

**Erros**

| Status | Causa |
|---|---|
| `400` | Um parâmetro é inválido: `to` não é maior que `from`, um filtro usa um campo ou operador desconhecido (`unsupported trace filter field: nope`), um filtro `in` não tem valores ou tem mais de 64, `where` não é uma árvore de condições ou ultrapassa seus limites, `expression` vem com `q`, `filters` ou `where` ou tem uma parte que não consegue ler, o cursor não corresponde à consulta, um campo em `fields` é desconhecido ou é um documento, ou o `trace_id` tem caracteres ou comprimento inválidos.
