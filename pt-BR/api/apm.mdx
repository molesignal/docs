A API de APM expõe agregados no escopo da organização derivados de spans de trace. Todos os endpoints usam o
prefixo `/api/v1/apm` e exigem um token bearer.

```http
Authorization: Bearer <token>
```

Um espaço de trabalho da organização requer a permissão de leitura da área: `apm.services.read`, `apm.errors.read`,
`apm.error_rules.read`, `apm.definitions.read`, `apm.slos.read`, `apm.deployments.read` ou `apm.settings.read`. Um chamador de plataforma pode usar
`sys.telemetry.read` no escopo protegido `_sys`. Cada chamada que grava informa o que exige. Registrar uma implantação exige
`apm.deploy`.

## Endpoints

| Método e caminho | Resposta |
|---|---|
| `GET /api/v1/apm/overview` | Resumo RED e tendência de todos os serviços, saúde dos serviços e sua tendência, rankings, implantações, ambientes, lacunas de instrumentação, principais transações, dependências e erros. |
| `GET /api/v1/apm/insights` | O que mudou em relação ao período anterior e ao mesmo período de uma semana antes, versões que tiveram pior desempenho, onde é possível recuperar tempo e as mudanças próximas a cada item. |
| `GET /api/v1/apm/services` | Catálogo paginado de serviços com instrumentação, versões, saúde, métricas RED e filtros de trace. |
| `GET /api/v1/apm/services/{service}` | Resumo, tendência, transações, dependências, erros e versões do serviço. |
| `GET /api/v1/apm/services/{service}/instances` | As instâncias de um serviço em um ambiente, com sua versão, atributos de recurso e o que cada uma atendeu. |
| `GET /api/v1/apm/services/{service}/coverage` | Se os logs, as métricas, os perfis e as sessões de navegador do serviço chegam ao MoleSignal, ao longo do dia anterior a `to`. |
| `GET /api/v1/apm/correlation` | O quão bem cada serviço em exibição se conecta aos seus logs, métricas, traces e mudanças, e os nomes de serviço em logs e métricas que o APM não conhece. |
| `GET /api/v1/apm/transactions` | Métricas RED paginadas de transações e ranking por tempo total. |
| `GET /api/v1/apm/transactions/{transaction}` | Tendência da transação, erros afetados, versões e filtros de trace. |
| `GET /api/v1/apm/dependencies` | Métricas RED paginadas de chamador/dependência e ranking por tempo total. |
| `GET /api/v1/apm/map` | O mapa de serviços de um ambiente e namespace: serviços, o que eles chamam, tópicos e as chamadas entre eles. |
| `GET /api/v1/apm/map/edge` | Uma chamada do mapa: sua tendência, o que foi solicitado ao longo dela e os erros de um serviço chamado. |
| `GET /api/v1/apm/blast-radius` | O que um serviço alcança ao longo do mapa: o que o chama e o que ele chama, salto a salto. |
| `GET /api/v1/apm/errors` | Grupos de erros de backend sanitizados e paginados, com os locais onde os grupos listados ocorreram. |
| `GET /api/v1/apm/errors/{fingerprint}` | Tendência do erro, transações e versões afetadas, onde o grupo ocorreu, stack representativa e amostras limitadas. |
| `GET /api/v1/apm/versions/compare` | Métricas RED da linha de base e do candidato, deltas, status de suficiência e regressões. |
| `GET /api/v1/apm/health` | Status da projeção do tenant, saúde do runtime, limites e lacunas. |
| `GET /api/v1/apm/service-definitions` | Todas as definições de serviço da organização. |
| `PUT /api/v1/apm/service-definitions/{service}?namespace=` | Cria ou substitui a definição de um serviço. Exige `apm.definitions.manage`. |
| `DELETE /api/v1/apm/service-definitions/{service}?namespace=` | Exclui a definição de um serviço. Exige `apm.definitions.manage`. |
| `POST /api/v1/apm/service-definitions/{service}/key-transactions?namespace=` | Marca um endpoint com estrela como transação-chave do serviço ou remove a estrela. Exige `apm.definitions.manage`. |
| `PUT /api/v1/apm/errors/{fingerprint}/issue` | Define o estado, a equipe e o responsável de um grupo de erros. Exige `apm.errors.manage`. |
| `GET /api/v1/apm/error-rules` | As regras de agrupamento de erros da organização na ordem em que são tentadas. |
| `POST /api/v1/apm/error-rules` | Cria uma regra de agrupamento, tentada depois das outras. Exige `apm.error_rules.manage`. |
| `PUT /api/v1/apm/error-rules/{id}` | Substitui uma regra de agrupamento. Exige `apm.error_rules.manage`. |
| `DELETE /api/v1/apm/error-rules/{id}` | Exclui uma regra de agrupamento. Exige `apm.error_rules.manage`. |
| `PUT /api/v1/apm/error-rules/order` | Define a ordem em que as regras são tentadas. Exige `apm.error_rules.manage`. |
| `GET /api/v1/apm/slos` | Todos os objetivos de nível de serviço com seu estado, o que cumpriu, o orçamento de erro restante e as taxas de queima. |
| `GET /api/v1/apm/slos/{id}` | O status de um objetivo de nível de serviço e cada dia de sua janela. |
| `POST /api/v1/apm/slos` | Cria um objetivo de nível de serviço. Exige `apm.slos.manage`. |
| `PUT /api/v1/apm/slos/{id}` | Substitui um objetivo de nível de serviço. Exige `apm.slos.manage`. |
| `DELETE /api/v1/apm/slos/{id}` | Exclui um objetivo de nível de serviço. Exige `apm.slos.delete`. |
| `POST /api/v1/apm/deployments` | Registra uma implantação. Exige `apm.deploy`. |
| `GET /api/v1/apm/settings` | As configurações de APM da organização, com os padrões quando nenhuma foi salva. |
| `PUT /api/v1/apm/settings` | Substitui as configurações de APM da organização. Exige `apm.settings.manage`. |

Os parâmetros de caminho devem ser codificados em URL. Use o nome exato de `transaction` ou o `fingerprint` de erro
retornado por uma resposta de lista.

## Parâmetros de consulta comuns

| Parâmetro | Tipo | Comportamento |
|---|---|---|
| `from` | inteiro | Início do intervalo em microssegundos desde a época Unix. O padrão é 24 horas antes de `to`. |
| `to` | inteiro | Fim do intervalo em microssegundos desde a época Unix. O padrão é a hora atual. |
| `namespace` | string | Filtro exato de namespace de serviço. |
| `service` | string | Filtro exato de nome de serviço. O caminho de detalhe do serviço substitui este valor. |
| `environment` | string | Filtro exato de ambiente de implantação. |
| `version` | string | Filtro exato de versão do serviço. |
| `resolution` | enum | `auto`, `minute` ou `hour`. `auto` seleciona a resolução retida para o intervalo. |
| `sort` | string | Campo de ordenação específico do endpoint. |
| `direction` | enum | `asc` ou `desc`. O padrão é `desc`. |
| `limit` | inteiro | Tamanho da página de 1 a 200. O padrão é 50. |
| `cursor` | string | Cursor opaco de uma resposta de lista anterior. |
| `status` | enum | Somente `/errors`: `all` (padrão), `unresolved` (grupos abertos, em investigação e resolvidos vistos novamente), `investigating`, `resolved` ou `ignored`. |

Os filtros devem ser não vazios e ter no máximo 192 bytes. O intervalo não pode exceder o máximo configurado,
que tem como padrão 30 dias (`[apm].max_query_range_days`).

### Campos de ordenação

| Endpoint | Valores de `sort` compatíveis | Padrão |
|---|---|---|
| `/services` | `requestCount`, `errorRate`, `p95`, `name` | `requestCount` |
| `/transactions` | `requestCount`, `errorRate`, `p95`, `total_time` | `requestCount` |
| `/dependencies` | `requestCount`, `errorRate`, `p95`, `total_time` | `total_time` |
| `/errors` | `occurrenceCount`, `errorRate`, `lastSeen` | `occurrenceCount` |

`/overview` aceita os mesmos filtros e a mesma resolução, mas não pagina. Endpoints de detalhe, comparação e
saúde não retornam listas paginadas.

## Consultar uma visão geral

<RequestExample>
```bash cURL
NOW=$(date +%s)000000
curl --get 'http://localhost:5080/api/v1/apm/overview' \
  --header "Authorization: Bearer $MS_TOKEN" \
  --data-urlencode "from=$((NOW-86400000000))" \
  --data-urlencode "to=$NOW" \
  --data-urlencode 'environment=production' \
  --data-urlencode 'resolution=auto'
```
</RequestExample>

A resposta contém `red`, `trend`, `serviceHealth`, `services`, `topTransactions`,
`topDependencies`, `topErrors` e `recentVersions`, além de um objeto `meta` comum, e:

| Campo | Notas |
|---|---|
| `serviceCount`, `activeServiceCount` | Serviços vistos no intervalo e, entre eles, os que atenderam a alguma requisição. |
| `healthTrend` | Quantos serviços estavam em cada estado, faixa a faixa: o intervalo em no máximo 48 faixas, nenhuma menor que um bucket. Um serviço sem requisições em uma faixa conta como `noTraffic` nela. |
| `rankings` | `slowest` (por p95), `mostErrors` (por taxa de erro) e `busiest` (por requisições), cinco serviços cada. Os dois primeiros listam serviços com pelo menos 20 requisições. |
| `deployments` | Versões vistas pela primeira vez dentro do intervalo, mais recentes primeiro, no máximo 20, cada uma com seu `red` e `verdict` como em [versões de um serviço](#ler-as-versões-de-um-serviço). |
| `environments`, `availableEnvironments` | Serviços e requisições por ambiente em exibição, e todos os ambientes em que os serviços são executados, independentemente do filtro `environment`. |
| `instrumentation` | Serviços por linguagem e SDK, e quantos não informam `deployment.environment`, `service.version` ou `service.instance.id`. |

## Consultar insights

`GET /api/v1/apm/insights` recebe os parâmetros comuns de intervalo e de filtro e responde `meta` e:

| Campo | Notas |
|---|---|
| `now`, `previous`, `lastWeek` | Os serviços em exibição no intervalo, no trecho de mesma duração anterior e no mesmo trecho uma semana antes: `requestCount`, `throughput` em requisições por segundo, `errorRate`, `p95Time` e `apdex`. Um trecho sem requisições fica ausente. |
| `insights` | No máximo 30 achados, os mais urgentes primeiro. |

Cada achado traz:

| Campo | Notas |
|---|---|
| `kind` | `anomaly`, `regression`, `slow_dependency`, `repeated_call`, `slowQuery`, `hot_endpoint` ou `log_errors`. |
| `severity` | `critical`, `warning` ou `info` para uma sugestão. |
| `service` | `namespace`, `name` e `environment`. |
| `transaction`, `dependency` | O endpoint de um endpoint quente; a dependência de um gargalo, de uma chamada repetida ou de uma instrução lenta. |
| `metric` | O que mudou ou piorou: `errorRate`, `p95` ou `throughput`. |
| `value` | O número agora: uma taxa de erro como razão, um P95 em microssegundos ou requisições por segundo. Um gargalo ou um endpoint quente informa sua parcela do tempo, uma chamada repetida suas chamadas por requisição, uma instrução lenta seu P95 em microssegundos, e `log_errors` suas linhas de log de nível de erro por minuto, com `metric` `log_errors`. |
| `previous`, `lastWeek` | O mesmo número no trecho anterior e no mesmo trecho uma semana antes; para uma regressão, o número da versão anterior. |
| `since` | Quando uma mudança começou, ou quando uma versão com regressão foi vista pela primeira vez. |
| `version`, `previousVersion` | A versão de uma regressão e a versão anterior a ela. |
| `calls`, `p95Time` | As chamadas ou requisições em que uma sugestão se baseia, e seu P95. |
| `changes` | As mudanças próximas de `since`, as mais próximas primeiro: `kind`, `source` (`reported` ou `observed`), `service`, `version`, `status`, `at`, `downstream` (`true` para um serviço que o serviço que mudou chama), `commit` e `description`. |

Os limites estão em [Insights e investigações](/pt-BR/apm/insights#o-que-os-insights-encontram).

## Consultar métricas RED

Todo resumo traz um objeto `red` com os números de requisições, erros e duração do intervalo.

| Campo | Notas |
|---|---|
| `requestCount`, `errorCount`, `errorRate` | Requisições, requisições com falha e a razão entre requisições com falha e requisições totais, de 0 a 1. |
| `durationSum`, `durationAverage` | A duração total e a duração média em microssegundos. A média é `null` sem requisições. |
| `p50Time`, `p90Time`, `p95Time`, `p99Time` | Percentis de latência em microssegundos, lidos dentro do bucket do histograma em que o posto cai. Com o layout padrão, um valor fica dentro de cerca de 4% da duração exata. `null` sem requisições. |
| `apdex` | Requisições dentro do limite T mais metade das requisições dentro de 4T, sobre todas as requisições, de 0 a 1. T é o `apdexThreshold` do serviço ou, na falta dele, 500 ms; os números da visão geral de todos os serviços juntos usam 500 ms. Requisições com falha nunca contam como satisfeitas. `null` sem requisições. |
| `latencyPartial` | `true` quando alguns buckets usam um layout de latência que não pode ser identificado a partir deles. Buckets de um layout anterior (`[apm.histogram].schema_version`) são convertidos e contados. Os percentis deixam de fora os buckets que não podem ser lidos, enquanto as contagens, a soma e a média ainda os incluem. |
| `timeoutCount`, `retryCount` | Requisições que esgotaram o tempo (um tipo de erro de timeout, `DEADLINE_EXCEEDED` do gRPC, HTTP 408 ou 504) e requisições enviadas novamente (`http.request.resend_count` acima de 0). Ausentes quando não há nenhuma. |
| `statusCodes` | Respostas por código de status, como `http:<code>` (100 a 599) ou `grpc:<code>` (0 a 16). Um bucket mantém até 24 códigos; outros códigos contam como `http:other` ou `grpc:other`. Ausentes quando nenhum código foi contado, como em agregados gravados antes de os códigos serem contados. |
| `exemplars` | Até 8 spans de amostra do intervalo, os mais lentos primeiro. Um span é projetado antes de [tail sampling](/pt-BR/configuration#captura-de-traces-e-amostragem-ao-final) decidir sobre seu trace, então `traceAvailable` normalmente é `false`; consulte o trace para saber se ele foi mantido. O agregado continua válido. |

Os resumos de serviço e de transação trazem `apdexThreshold`, o T com que seu Apdex foi lido.
Um resumo de serviço também traz `health` e `healthReasons`: cada número acima de um limite, como `metric`
(`errorRate` ou `p95`), `level`, `value` e `threshold`. Ele traz `sparkline`, a contagem de requisições, a contagem de erros e o p95 de cada bucket,
e `currentVersion` com `currentVersionSince`, a versão vista mais recentemente e quando ela foi
vista pela primeira vez. O detalhe de um serviço ou de uma transação traz `latencyDistribution`: os buckets
do histograma que contêm requisições, cada um como `lowerTime`, `upperTime` e `count`, reduzidos à
requisição mais rápida e à mais lenta.

## Manter definições de serviço

Uma definição registra quem é responsável por um serviço e o quanto ele importa. Ela é indexada por `namespace` e o
nome do serviço, então vale em todo ambiente, e pode existir antes de o serviço reportar.

```http
PUT /api/v1/apm/service-definitions/checkout?namespace=shop
Content-Type: application/json

{"description": "Takes orders and payments.", "teamId": "<team id>", "ownerId": "<user id>", "tier": "p0", "lifecycle": "production", "repositoryUrl": "https://github.com/acme/checkout", "tags": {"domain": "orders", "pci": ""}, "apdexThreshold": 300000, "aliases": ["order_service", "Order Center"], "dataSources": {"logs": [{"stream": "default", "filter": "service_name = 'order_service'"}], "metrics": [{"selector": "{service=\"checkout\"}"}], "dashboards": ["<dashboard id>"], "links": [{"name": "Runbook", "url": "https://wiki.example.com/checkout"}]}, "archived": false}
```

| Campo | Observações |
|---|---|
| `description` | Até 2.000 caracteres. |
| `teamId` | Uma equipe da organização, ou `null`. Excluir a equipe limpa o valor. |
| `ownerId` | Um membro da organização, ou `null`. |
| `tier` | `p0`, o mais importante, até `p5`, ou `null`. |
| `lifecycle` | `production`, `staging`, `experimental`, `deprecated`, ou `null`. |
| `repositoryUrl` | Uma URL `http`, `https`, `ssh`, `git` ou `git+ssh`, ou `user@host:path`, sem espaços, de até 2.048 caracteres, ou `null`. Uma senha é salva como `****`, e a parte do usuário de um endereço http(s) também. Exibida quando o serviço não reporta repositório. |
| `tags` | Até 32 tags como `{ "key": "value" }`. Uma chave tem de 1 a 64 letras minúsculas, dígitos e `_ . - /`; um valor tem até 128 caracteres sem espaços ao redor, vazio para uma chave sozinha. |
| `apdexThreshold` | O limite T do Apdex do serviço, acima de 0 e no máximo 60.000.000 (um minuto), ou `null` para 500 ms. |
| `aliases` | Até 20 outros nomes pelos quais o serviço é conhecido em logs, métricas e outros sistemas, cada um com 1 a 128 caracteres sem espaços ao redor. Maiúsculas e minúsculas são ignoradas: nenhum nome duas vezes, nunca o próprio nome do serviço, e nunca o nome ou outro nome de um serviço diferente da organização. Se omitido, uma definição salva mantém seus nomes. |
| `dataSources` | Onde estão os dados do serviço: `logs` (`stream` e um `filter` opcional, uma expressão SQL booleana de até 2.000 caracteres), `metrics` (`selector`, um seletor PromQL como `{service="checkout"}`), `dashboards` (IDs de dashboard) e `links` (`name` e uma `url` `http` ou `https`), até 10 de cada. Se omitido, uma definição salva mantém suas fontes. |
| `archived` | `true` mantém o serviço fora da visualização padrão do catálogo. Se omitido, uma definição salva mantém seu estado. |

Um salvamento mantém os `keyTransactions` da definição, que mudam uma de cada vez. A resposta é a
definição salva com `namespace`, `name`, `keyTransactions`, `updatedBy` e `updatedAt`.
`DELETE` responde `204`, ou `404` quando o serviço não tem definição.

### Marcar transações principais

```http
POST /api/v1/apm/service-definitions/checkout/key-transactions?namespace=shop
Content-Type: application/json

{"transaction": {"name": "POST /orders", "kind": "http"}, "key": true}
```

`key: true` adiciona o endpoint a `keyTransactions`, `false` o remove; pedir o que já está
assim não muda nada. Um serviço sem definição recebe uma. Um serviço mantém até 50 transações
principais, e a linha de excedente `__other__` não pode ser uma. A resposta é a definição após
a mudança.

## Ler o quão bem os serviços se correlacionam com outros dados

`GET /api/v1/apm/correlation` recebe os parâmetros comuns de intervalo e filtro (`from`, `to`,
`namespace`, `environment`, `service`) e informa, para cada serviço em exibição, o quão bem ele se correlaciona com seus
logs, métricas, traces e mudanças. Os serviços são lidos no intervalo, os logs e as métricas na última
hora antes de `to`, e as mudanças na semana antes de `to`. Apenas contagens e nomes são lidos dos
streams, nunca linhas. Cada relatório é mantido por cinco minutos.

```json
{
  "from": 1792312896695000,
  "to": 1792316496695000,
  "changesSince": 1791711696695000,
  "services": [
    {
      "service": { "namespace": "shop", "name": "checkout", "environment": "prod" },
      "logs": { "state": "reported", "streams": ["default"], "lines": 1200, "traced": 480, "sampled": 10, "matched": 9 },
      "metrics": "missing",
      "resource": { "environment": true, "version": true, "instance": true, "placement": false },
      "changes": { "count": 3, "lastAt": 1792312896695000 },
      "grades": { "traceIds": "partial", "resource": "partial", "metrics": "missing", "changes": "good" }
    }
  ],
  "unmatched": [{ "name": "checkout-svc", "signal": "logs", "streams": ["default"], "lines": 640 }]
}
```

| Campo | Significado |
|---|---|
| `logs` | As linhas do serviço em streams de log com um campo `service.name`, `service_name` ou `service`, no máximo oito streams, `default` primeiro. `traced` conta as linhas com um `trace_id`, `traceId` ou `trace.id`. Até dez IDs de trace recentes do serviço, 200 no total, são procurados entre os traces: `sampled` e `matched`. |
| `metrics` | Se um stream de métricas contém uma série com o `service.name` do serviço. |
| `resource` | Se os spans reportam um ambiente, alguma versão e uma instância, e se uma instância reporta `host.name`, `k8s.pod.name`, `k8s.node.name` ou `container.id` (`placement`). |
| `changes` | As implantações, mudanças de configuração e feature flags reportadas para o serviço desde `changesSince`. |
| `unmatched` | Até 20 nomes de serviço em logs ou métricas aos quais nenhum serviço de APM responde, com regras de nomenclatura e aliases aplicados, os com mais linhas primeiro. |

Cada nota é `good`, `partial`, `missing` ou `unknown`:

| Nota | `good` | `partial` | `missing` |
|---|---|---|---|
| `traceIds` | Pelo menos 90% das linhas carregam um trace ID, e pelo menos 80% dos amostrados são encontrados. | Algumas linhas carregam um. | Nenhuma linha carrega um, ou o serviço não escreveu linhas. |
| `resource` | Todos os quatro de `resource` são verdadeiros. | Alguns são. | Nenhum é. |
| `metrics` | As métricas carregam o nome. | | Nenhuma carrega. |
| `changes` | Pelo menos uma mudança. | | Nenhuma. |

`unknown` significa que uma consulta falhou ou levou mais de três segundos; um nome não encontrado enquanto um stream não
pôde ser lido é `unknown`, nunca `missing`. O Mole Agent lê o mesmo relatório com
`get_correlation_quality`.

## Ler a cobertura de um serviço

`GET /api/v1/apm/services/{service}/coverage` recebe `namespace` e `environment`, ambos obrigatórios, e
`to` opcional, o fim do intervalo em exibição em microssegundos (agora por padrão). Ele consulta o dia
antes de `to` e mantém cada resposta por cinco minutos.

```json
{
  "from": 1792230096695000,
  "to": 1792316496695000,
  "logs": { "state": "reported", "found": ["default"] },
  "metrics": { "state": "missing" },
  "profiles": { "state": "reported", "found": ["cpu", "alloc_space"] },
  "rum": { "state": "unknown" }
}
```

| Sinal | `reported` quando | `found` |
|---|---|---|
| `logs` | Um stream de log com um campo `service.name`, `service_name` ou `service` contém uma linha do serviço. No máximo oito streams são consultados, `default` primeiro. | Os streams. |
| `metrics` | `count(last_over_time({"service.name"="<service>"}[1h]))` em `to` é maior que zero. | O número de séries. |
| `profiles` | O stream de perfis contém um perfil do serviço. | Os tipos de perfil. |
| `rum` | Uma ação de navegador carregou um dos cinco traces de amostra mais recentes do serviço. | A sessão. |

`missing` significa que a consulta não encontrou nada. `unknown` significa que a consulta falhou ou levou mais de três
segundos. `rum` nunca é `missing`: uma amostra de traces pode mostrar que sessões alcançam um serviço, não que
nenhuma alcança.

## Ler como um serviço é executado

`GET /api/v1/apm/services` e `GET /api/v1/apm/services/{service}` dão a cada resumo de serviço um
`profile`, lido das instâncias que reportaram no intervalo, somente as de `version` quando o
parâmetro é definido. Cada lista é classificada por quantas instâncias compartilham um valor, no máximo cinco, como
`{ "value": "1.8.2", "instances": 4 }`.

| Campo | Observações |
|---|---|
| `instanceCount`, `hostCount` | Instâncias e valores distintos de `host.name`. |
| `versions` | As versões que as instâncias executaram. Uma implantação gradual lista duas. |
| `languages`, `runtimes`, `frameworks` | `telemetry.sdk.language`; `process.runtime.name` com sua versão; o framework nomeado pela biblioteca de instrumentação dos spans de entrada. |
| `regions`, `clusters`, `k8sNamespaces`, `workloads` | `cloud.region`, `k8s.cluster.name`, `k8s.namespace.name` e `k8s.deployment.name` ou `k8s.statefulset.name`. |
| `repositories`, `commits` | `vcs.repository.url.full` ou `git.repository_url`, mantidos sem credenciais; `vcs.ref.head.revision` ou `git.commit.sha`. |
| `entryKinds` | `http`, `rpc`, `messaging`, `span`: os tipos de entrada que o serviço atende. |

`GET /api/v1/apm/services/{service}/instances` lista as instâncias uma a uma, as vistas mais recentemente
primeiro, no máximo 500. Recebe `namespace`, `environment` e `version`, `from` e
`to` opcionais; sem um serviço e um ambiente, responde `400`. Cada item tem `instanceId` (o
`service.instance.id`, senão `k8s.pod.name`, senão `host.name`), `version`, `firstSeenAt`,
`lastSeenAt`, `attributes`, um mapa dos atributos que a instância reportou por último, e o que ela atendeu
no intervalo: `red`, como nos resumos com Apdex no limite do serviço, e `sparkline`. Além do
limite de instâncias, o restante é contado em um item cujo `instanceId` é `__other__`. Uma instância que
atendeu no intervalo antes de qualquer dado ser mantido sobre ela é listada com `attributes` vazio.

## Definir o estado de um grupo de erros

```http
PUT /api/v1/apm/errors/<fingerprint>/issue
Content-Type: application/json

{"status": "investigating", "assigneeId": "<user id>", "teamId": "<team id>", "lastSeenAt": 1792316496695000}
```

`status` é `open`, `investigating`, `resolved` ou `ignored`. `assigneeId` é um membro da
organização ou `null`, e `teamId`, uma equipe da organização ou `null`. `lastSeenAt`, opcional, é quando o leitor viu o grupo pela última vez, em microssegundos. Definir
`resolved` registra o horário como `resolvedAt`.

Os resumos de erros trazem o estado como `issue`, ou `null` enquanto ninguém definiu um. `issue.regressed`
é `true` quando um grupo resolvido voltou a ocorrer após `resolvedAt`; o filtro `unresolved` mantém
esses grupos. Definir o estado de um fingerprint que a projeção não conhece retorna `404`.

## Manter objetivos de nível de serviço

Um objetivo de nível de serviço (SLO) promete uma fração de boas solicitações de um serviço em um ambiente, ou
de um de seus endpoints, ao longo de uma janela móvel. Consulte
[Objetivos de nível de serviço](/pt-BR/apm#objetivos-de-nível-de-serviço) para saber o que cada número significa.

```http
POST /api/v1/apm/slos
Content-Type: application/json

{"name": "Checkout availability", "namespace": "shop", "service": "checkout", "environment": "production", "transaction": null, "kind": "availability", "objective": 0.999, "windowDays": 30}
```

| Campo | Observações |
|---|---|
| `name` | Obrigatório, até 255 bytes. |
| `description` | Opcional, até 2.000 bytes. |
| `namespace`, `service`, `environment` | Obrigatório. O serviço como o APM o nomeia. Um serviço sem `service.namespace` fica no namespace `default`. |
| `transaction` | Um endpoint, `{ "name": "POST /orders", "kind": "http" }`, ou `null` para o serviço inteiro. |
| `kind` | `availability`: uma solicitação é boa quando não falhou. `latency`: uma solicitação é boa quando não falhou e levou no máximo `latencyThreshold`. |
| `latencyThreshold` | Obrigatório e positivo para `latency`. Deve ser `null` ou estar ausente para `availability`. |
| `objective` | A fração de boas solicitações, acima de 0 e abaixo de 1, como `0.999`. |
| `windowDays` | `7`, `28` ou `30`. |

`POST` e `PUT` retornam o SLO salvo com `id`, `createdBy`, `createdAt`, `updatedBy` e
`updatedAt`. `GET /api/v1/apm/slos` retorna cada SLO da organização como um status. Passe
`namespace`, `service` e `environment` juntos para manter os SLOs de um serviço. A janela termina
no momento da chamada, então os parâmetros de intervalo comuns não se aplicam.

| Campo de status | Observações |
|---|---|
| `slo` | O SLO como salvo. |
| `state` | `healthy`, `at_risk`, `breached` ou `noData`. |
| `sli` | Boas solicitações sobre todas as solicitações na janela, ou `null` sem solicitações. |
| `goodRequests`, `totalRequests` | As contagens por trás de `sli`. Um SLO de latência estima `goodRequests` a partir dos histogramas de latência, então pode ser fracionário. |
| `budgetRemaining` | `1 - (1 - sli) / (1 - objective)`, abaixo de zero quando o objetivo é violado, ou `null` sem solicitações. |
| `burnRates` | `oneHour`, `sixHours` e `oneDay`: `(1 - sli) / (1 - objective)` na última hora, nas últimas seis horas e nas últimas 24 horas, ou `null` sem solicitações. |

`GET /api/v1/apm/slos/{id}` retorna `status` e `history`, uma entrada para cada dia UTC da janela
com solicitações, da mais antiga para a mais recente. Cada entrada tem `dayStart` em microssegundos, `sli`, `goodRequests`
e `totalRequests`.

`DELETE` retorna `204`. Retorna `409` enquanto regras de alerta monitoram o SLO, como seus alertas de burn-rate:
exclua essas regras primeiro. Regras de alerta em um SLO são regras de APM com a métrica
`slo_burn_rate`. Consulte [Criar uma regra](/pt-BR/api/alerting/create-rule#regras-de-apm).

## Desambiguar uma transação

Dois tipos de transação podem compartilhar um nome. Passe o parâmetro opcional `kind` para selecionar um deles:

```http
GET /api/v1/apm/transactions/POST%20%2Fcheckout?kind=http&service=checkout
```

Os valores de `kind` com suporte são `http`, `rpc`, `messaging`, `span` e `other`. Um nome que vários
serviços ou tipos compartilham retorna `400` com `APM transaction identity is ambiguous; provide service,
namespace, environment, and kind`.

## Comparar versões

Informe valores diferentes para `baseline` e `candidate`. Adicione um filtro `service` para comparar um serviço.

```bash
curl --get 'http://localhost:5080/api/v1/apm/versions/compare' \
  --header "Authorization: Bearer $MS_TOKEN" \
  --data-urlencode 'service=checkout' \
  --data-urlencode 'environment=production' \
  --data-urlencode 'baseline=2.3.1' \
  --data-urlencode 'candidate=2.4.0'
```

A resposta contém os lados `baseline` e `candidate`, cada um com `version`, `sampleCount` e
`red`, além de um `delta`, um `status`, `regressedTransactions` e `regressedErrors`. Cada lista de regressão
tem no máximo 20 entradas.

| Campo | Observações |
|---|---|
| `sufficientData` | `true` somente quando ambas as versões atingem o limite de amostra configurado, cujo padrão é 1.000 solicitações por versão (`[apm.version_comparison].min_requests_per_version`). |
| `status` | `insufficient_data`, `regressed`, `improved` ou `neutral`. `regressed` quando a taxa de erros da candidata aumentou em pelo menos um ponto e atingiu pelo menos 1,5 vez a da baseline, ou seu p95 aumentou em pelo menos um quinto e 50 ms; `improved` quando um deles caiu na mesma medida e nenhum subiu dessa forma; `insufficient_data` quando `sufficientData` é `false`. |
| `delta` | `requestCountAbsolute` e `requestCountRelative`, `errorRateAbsolute` e `errorRateRelative`, e `p95AbsoluteTime` e `p95Relative`. Um valor relativo é `null` quando a baseline é zero ou está ausente. |

Um `candidate` ou `baseline` ausente, ou duas versões idênticas, retorna `400`.

## Ler as versões de um serviço

`GET /api/v1/apm/services/{service}` retorna `versions`, as versões vistas no intervalo. Cada uma traz
`red`, o que ela atendeu no intervalo, e `verdict`, como se saiu em relação à versão do mesmo serviço
vista pela primeira vez antes dela, julgada como [uma comparação](#comparar-versões):

| Campo | Observações |
|---|---|
| `previous` | A versão em relação à qual ela é avaliada. |
| `status` | `regressed`, `improved`, `neutral` ou `insufficient_data`. |
| `worse` | O que piorou quando `status` é `regressed`: `errorRate`, `latency` ou ambos. |
| `delta` | Como em uma comparação, com a versão anterior como baseline. |

A primeira versão vista não tem `verdict`. Um filtro de versão na solicitação não restringe os
números: cada versão é lida do serviço inteiro.

## Ler onde os erros ocorreram

`GET /api/v1/apm/errors` retorna um `breakdown` ao lado da página, sobre cada grupo que o filtro `status`
mantém (não apenas os da página), e `GET /api/v1/apm/errors/{fingerprint}` retorna o `breakdown` do
grupo. Ele contém `versions`, `environments` e `languages`, cada um uma lista de `value` e `count`,
as ocorrências, da maior para a menor. Um valor fica vazio quando os spans não o informaram; após os primeiros
sete valores, o restante conta junto como `__other__`. O idioma é o
`telemetry.sdk.language` do serviço.

## Manter regras de agrupamento de erros

Uma regra agrupa erros por um critério diferente de tipo, frame e endpoint quando eles são vistos. As regras são
testadas na ordem de `position`, e a primeira que corresponder prevalece.

```http
POST /api/v1/apm/error-rules
Content-Type: application/json

{"name": "Upstream timeouts", "serviceNamespace": "shop", "serviceName": "checkout",
 "errorType": "*Timeout*", "message": "", "frame": "", "endpoint": "", "action": "merge", "enabled": true}
```

| Campo | Observações |
|---|---|
| `name` | Até 128 caracteres. Um grupo mesclado recebe o nome dela. |
| `serviceNamespace`, `serviceName` | O serviço ao qual a regra se destina. Um `serviceName` vazio significa todos os serviços; um namespace precisa de um nome. |
| `errorType`, `message`, `frame`, `endpoint` | Padrões para o tipo de erro, a mensagem da exceção, o primeiro frame da aplicação e o endpoint, cada um com até 256 caracteres. Um padrão corresponde ao texto inteiro, ignorando maiúsculas e minúsculas, com `*` para qualquer texto. Um padrão vazio corresponde a qualquer coisa; pelo menos um deve ser definido. |
| `action` | `merge`: os erros correspondentes de um serviço formam um grupo. `ignore`: eles não formam grupo, e suas solicitações ainda contam como falhas. |
| `enabled` | Uma regra desativada é mantida, mas não é testada. O padrão é `true`. |

A resposta é a regra com seu `id`, `position`, `updatedBy` e `updatedAt`. Uma organização
mantém no máximo 100 regras. `PUT /api/v1/apm/error-rules/order` recebe `{"ids": [...]}`, coloca essas regras
primeiro nessa ordem e as demais depois delas, e retorna as regras na nova ordem.

Uma alteração se aplica imediatamente no nó que a salva e em até 30 segundos nos demais, aos
erros vistos a partir de então; grupos já formados permanecem como estão.

## Ler o mapa de serviços

`GET /api/v1/apm/map` recebe os parâmetros comuns de intervalo, `environment` e `namespace` e responde
`nodes`, `edges`, `namespaces` (dos serviços no ambiente), `environments` (todos) e
`truncated` (`true` quando apenas os 400 nós mais movimentados são mantidos).

| Campo | Observações |
|---|---|
| `nodes[].id` | `service:<name>`, `topic:<name>` ou `<category>:<target>` para o que os serviços chamam. |
| `nodes[].kind` | `service`, `external` ou `topic`. Um nó externo carrega sua `category`. |
| `nodes[].red` | `requestCount`, `errorCount`, `errorRate` e `p95Time`: o que um serviço atendeu, ou o que foi solicitado a um nó externo ou a um tópico. Um serviço também carrega `health`, `namespace` e `environments`. |
| `edges[].kind` | `call`, `publish` (para um tópico) ou `consume` (de um tópico). |
| `change` | Em uma aresta ou um nó, em comparação com o período de mesma duração anterior: `new` quando não existia, `gone` quando não existe mais. Ausente quando nada existia antes. |

As chamadas entre serviços vêm do grafo de serviços, com o P95 do minuto mais lento; o restante
vem dos buckets de APM. `GET /api/v1/apm/map/edge` recebe os ids de nó `source` e `target` além dos mesmos
parâmetros e responde `kind`, `red`, `trend`, `operations` (`name`, `kind`, `red`), `everyCaller`
(`true` quando as operações são os endpoints do serviço chamado de todos os chamadores) e `errors`, os
grupos de erros do serviço chamado.

## Ler o raio de impacto de um serviço

`GET /api/v1/apm/blast-radius` recebe `service`, que é obrigatório, e os parâmetros comuns de intervalo e
`environment`. Lê o mapa inteiro do ambiente, qualquer que seja o namespace, e
responde `meta`, `service` (o próprio nó do serviço, ausente quando o mapa não o tem em lugar nenhum do intervalo),
`upstream` (o que o chama, até três saltos) e `downstream` (o que ele chama ou para onde publica, até dois
saltos). Cada lado contém no máximo 30 nós, os não saudáveis primeiro; chamadas que desapareceram em relação ao período anterior ficam
de fora.

| Campo | Observações |
|---|---|
| `id`, `kind`, `name`, `namespace`, `category` | O nó como [o mapa de serviços](#ler-o-mapa-de-serviços) o nomeia. |
| `hops` | Chamadas entre o nó e o serviço: `1` para um chamador ou chamado direto. |
| `via` | O nó pelo qual ele é alcançado, um salto mais próximo do serviço. |
| `health` | A saúde do próprio serviço. Para o que é chamado, a saúde que suas chamadas com falha indicam. |
| `red`, `call` | O que ele atendeu ou o que lhe foi solicitado, e as chamadas entre ele e `via`. |

## Relatar implantações

`POST /api/v1/apm/deployments` recebe a implantação como JSON e responde `201` com ela, com seu `id`,
`createdBy` e `createdAt` adicionados. Os campos, seus limites e exemplos de CI estão em
[Implantações](/pt-BR/apm/deployments#report-deployments-from-ci). O serviço e o ambiente
são nomeados conforme as regras de nomenclatura, o mapeamento de ambientes e os aliases da organização os interpretam. Um
endereço de repositório é mantido com a senha mascarada. Uma mudança de configuração ou uma feature flag define
`kind` como `configuration` ou `feature_flag` e não precisa de `version`.

Uma mudança de escala ou de infraestrutura define `kind` como `scaling` ou `infrastructure`. As mudanças relatadas
são listadas por [`GET /api/v1/changes`](/pt-BR/api/changes).

## Manter as configurações de APM

`GET /api/v1/apm/settings` responde com as configurações da organização; `PUT` as substitui por completo e
responde com o que foi mantido:

```json
{
  "health": {
    "errorRateWarning": 0.02,
    "errorRateCritical": 0.1,
    "p95WarningTime": 500000,
    "p95CriticalTime": 2000000
  },
  "apdexThreshold": 500000,
  "longTaskTime": 1000000,
  "namingRules": [{ "pattern": "^(checkout)-[a-z0-9]{5}$", "replacement": "$1" }],
  "environmentMap": [{ "from": "Production", "to": "production" }],
  "aliases": [{ "aliasNamespace": "shop", "alias": "checkout-v1", "namespace": "shop", "service": "checkout" }],
  "metadataRules": { "teamFromTier": "p1", "ownerFromTier": "p0", "repositoryFromTier": null }
}
```

Um campo omitido assume seu valor padrão. Os espaços em branco dos nomes são removidos, e um namespace de alias em branco é `default`. Os
limites e o que cada configuração faz estão em [Configurações de APM](/pt-BR/apm/settings). Um salvamento é aplicado imediatamente
no nó que o salva e em até 30 segundos nos demais.

Os limites de cardinalidade da plataforma são lidos e substituídos com `GET` e `PUT
/api/v1/settings/apm_limits`, que exigem `sys.settings.limits.manage`. O corpo contém
`servicesPerOrgHour`, `transactionsPerServiceHour`, `dependenciesPerServiceHour`,
`operationsPerDependencyHour`, `errorGroupsPerServiceHour`, `versionsPerServiceHour` e
`instancesPerServiceHour`, cada um de 1 a 100000.

## Ler os metadados da resposta

Todo endpoint retorna um objeto `meta` comum:

```json
{
  "range": {
    "from": 1785801600000000,
    "to": 1785888000000000
  },
  "resolution": "minute",
  "projectionStartedAt": 1785798000000000,
  "lastCompleteBucketAt": 1785887940000000,
  "dataQuality": {
    "partial": false,
    "gaps": [],
    "overflowDimensions": []
  },
  "activationBoundary": false
}
```

- Trate `activationBoundary: true` como cobertura incompleta antes de `projectionStartedAt`.
- Trate `dataQuality.partial: true` como dados incompletos, não como zero completo.
- Inspecione `gaps` para falhas de fila, repositório, flush, dados atrasados, cardinalidade ou desligamento.
- Use `lastCompleteBucketAt` para determinar se os dados recentes ainda estão sendo finalizados.
- Inspecione `overflowDimensions` antes de confiar em uma análise de alta cardinalidade.

## Erros

| Status | Causa |
|---|---|
| `400` | Um parâmetro é inválido: um `sort` não suportado (`unsupported APM sort field`), um `limit` fora do intervalo de 1 a 200, um filtro vazio ou grande demais (`invalid APM service filter`), um intervalo maior que o máximo (`APM query range exceeds configured maximum`), um fim anterior ao início (`APM range end precedes start`), um `direction` ou `resolution` desconhecido, um SLO que falha nas verificações acima (`SLO objective must be between 0 and 1, exclusive`) ou um filtro de lista de SLOs sem todos os campos `namespace`, `service` e `environment`. |
| `403` | O token não tem a permissão da chamada. |
| `404` | A fingerprint de erro, a transação, o serviço ou o SLO não existe no intervalo. |
| `409` | Regras de alerta ainda observam o SLO sendo excluído. |
