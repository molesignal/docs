```http
POST /api/v1/functions
```

Cria uma transformação reutilizável para pipelines. Ao criar a função, o MoleSignal compila o código VRL ou JavaScript e rejeita código-fonte inválido. Os dois ambientes de execução fazem parte do binário. A chamada exige `functions.create`.

**Corpo**

| Campo | Tipo | Obrigatório | Observações |
|---|---|---|---|
| `name` | string | Sim | Nome da função. |
| `language` | string | Sim | `vrl`, `js` ou `llm`. Uma função `llm` exige `[functions].llm_eval_enabled` e um provedor de modelo. |
| `source` | string | Sim | Código-fonte em VRL ou JavaScript, ou a instrução de uma função `llm`. |
| `paramsSchema` | object | Não | Parâmetros. Para `llm`, `outputField` seleciona o campo de saída. O padrão é `_llm_eval`. |

<RequestExample>
```bash cURL
curl -X POST http://localhost:5080/api/v1/functions \
  -H "authorization: Bearer $MS_TOKEN" \
  -H 'content-type: application/json' \
  -d '{
    "name": "lowercase-level",
    "language": "vrl",
    "source": ".level = downcase!(string!(.level))"
  }'
```
</RequestExample>

Em caso de erro de sintaxe, a API retorna `400`. Exemplo: `js syntax error: Uncaught SyntaxError: Unexpected token '}'`. Antes de salvar, teste o código-fonte com `POST /api/v1/functions/run`. O endpoint recebe `language`, `source` e um `input` de exemplo, e retorna `output`. Consulte [Funções](/pt-BR/functions).

Outras rotas de funções: `GET /api/v1/functions`, `GET`, `PUT` e `DELETE /api/v1/functions/{id}`. As predefinições integradas são somente leitura.

## Teste a transformação antes de salvar

O endpoint de simulação exige `functions.run`, uma permissão distinta de `functions.create`. Use uma entrada representativa com campos ausentes e malformados antes de adicionar a transformação a um fluxo de ingestão ativo.

```bash
curl -X POST http://localhost:5080/api/v1/functions/run \
  -H "authorization: Bearer $MS_TOKEN" \
  -H 'content-type: application/json' \
  -d '{"language":"vrl","source":".level = downcase!(string!(.level))","input":{"level":"ERROR","message":"example"}}'
```

Para essa entrada, confirme que `output.level` é `error`, que a transformação preserva o campo `message`, que não faz parte da operação, e que `dropped` é `false`. Compilar sem erros não garante que todos os eventos de produção atendam às condições esperadas pela transformação. Por exemplo, a conversão para string acima pode falhar e exige que `level` seja uma string.

## Conecte a função a um pipeline

Criar uma função armazena uma definição reutilizável, mas não transforma automaticamente os eventos recebidos. Guarde o ID da função retornado, adicione a etapa correspondente em [Pipelines](/pt-BR/pipelines) e teste o pipeline completo antes de ativá-lo para um fluxo ativo.

Registre uma entrada representativa e a saída esperada junto com a alteração. Depois de ativar o pipeline, ingira um evento controlado e consulte o fluxo de destino para confirmar os campos armazenados. A resposta da simulação, por si só, não valida o caminho de ingestão em uso.

## Falhas comuns

| Sintoma | Ação |
|---|---|
| Nome da função vazio | Informe um `name` não vazio. |
| Rejeição do código-fonte na criação | Corrija os erros de sintaxe ou de compilação antes de tentar novamente. |
| Simulação negada | Verifique `functions.run`. A criação exige uma permissão separada. |
| A entrada causa uma falha durante a execução | Reproduza em uma simulação a estrutura do campo que causa a falha e trate campos ausentes ou de tipos diferentes. |
| A função salva não afeta os novos logs | Verifique se a função está vinculada ao pipeline e confira o fluxo de destino. |
