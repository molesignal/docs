```http
POST /api/v1/scheduled_pipelines
```

Cria um pipeline. O caminho mantém o nome `scheduled_pipelines` em todos os modos. A chamada exige `pipelines.create`.

**Corpo**

| Campo | Tipo | Obrigatório | Observações |
|---|---|---|---|
| `name` | string | Sim | Nome do pipeline. |
| `sourceStream` | string | Sim | Primeiro fluxo que o pipeline lê. Use uma string vazia para um pipeline de alertas. |
| `targetStream` | string | Sim | Primeiro fluxo em que o pipeline grava. Em um pipeline agendado, indicar um fluxo que o pipeline já lê retorna `409`. Use uma string vazia para um pipeline de alertas. |
| `functionSteps` | objeto | Sim | Etapas, modo e configurações de um pipeline agendado ou condições de um pipeline de alertas. Consulte os campos abaixo. |
| `cron` | string | Sim | `every:30s`, `every:5m` ou `every:1h` para um pipeline agendado. Use uma string vazia para um pipeline em tempo real ou de alertas. |
| `lookbackSecs` | inteiro | Não | Quantidade de segundos de dados anteriores que a primeira execução agendada lê de uma origem. Padrão: 300. Um pipeline agendado exige um valor positivo. |
| `enabled` | booleano | Não | Padrão: `true`. |

Campos de `functionSteps`:

| Campo | Observações |
|---|---|
| `mode` | `scheduled` (padrão), `realtime` ou `alert`. |
| `signalType` | `logs`, `metrics` ou `traces`. Pipelines em tempo real também aceitam `profiles`. Um pipeline de métricas, rastreamentos ou perfis em tempo real altera o próprio fluxo: `targetStream` é igual a `sourceStream`, sem etapa de roteamento nem `retainSource`. Consulte [Métricas e rastreamentos](/pt-BR/pipelines#métricas-e-traces). Um pipeline de perfis usa `default` como origem. Consulte [Perfis](/pt-BR/pipelines#perfis). Um pipeline de alertas não usa esse campo. |
| `steps` | Etapas em ordem de execução. Uma etapa de VRL tem `transformName`, `script` e `kind` definido como `vrl`. Uma etapa de roteamento tem `kind` definido como `builtin`, `operation` definido como `route` e um objeto `routing`. Um pipeline de alertas aceita até 20 etapas e não aceita etapas de roteamento. Uma etapa de resumo com IA tem `transformName`, `kind` definido como `ai_summary`, `prompt` e `annotation`, a anotação que recebe a resposta (padrão: `ai_summary`). Uma etapa de chamada de API tem `kind` definido como `http_enrich` e `connectorId`, que identifica um conector HTTP da organização. Uma etapa de consulta tem `kind` definido como `query_enrich`, `language` (`sql`, por padrão, ou `promql`), `stream`, `streamType` (`logs`, por padrão, `metrics` ou `traces`), `statement`, `windowSecs` (padrão: 300; máximo: 86400), `maxRows` (padrão: 5; máximo: 50) e `annotation` (padrão: `query_result`). Consulte [Etapas dos pipelines de alertas](/pt-BR/pipelines/alert-events#etapas). Um pipeline em tempo real também aceita as etapas de contagem `generate_metric`, `quota` e `throttle`, com os campos abaixo. |
| `alert` | Apenas para pipelines de alertas. Define quando o pipeline é executado, as condições e a ordem: `stage` (`open`, por padrão, ou `notify`), `policies` (políticas de notificação às quais um pipeline `notify` se aplica; se a lista estiver vazia, inclui todas as políticas do evento de alerta), `sources` (`rule`, `external`, `synthetic`, `noData` e, para `notify`, também `manual`), `severities` (`info`, `warning`, `error`, `critical`), `labels` (objeto com os rótulos e os valores que o evento deve ter) e `order` (inteiro; padrão: 0). Uma lista vazia aceita todas as origens ou todos os níveis de severidade. Consulte [Pipelines de alertas](/pt-BR/pipelines/alert-events#criar-um-pipeline-de-alerta-pela-api). |
| `sources` | Fluxos para leitura. O pipeline lê `sourceStream` primeiro. Um pipeline agendado também lê os demais fluxos da lista, até 8 no total. Um pipeline em tempo real aceita apenas `[source_stream]`. |
| `sinks` | Fluxos para gravação. `targetStream` vem primeiro, e todos os demais fluxos da lista recebem cada evento, até 8 fluxos no total. Um pipeline em tempo real aceita apenas `[target_stream]`. |
| `sinkConnectors` | Apenas para pipelines agendados. IDs dos conectores que recebem todos os eventos. |
| `sinkTables` | Apenas para pipelines agendados. Nomes de até 8 tabelas de extensão que recebem uma linha por evento. Consulte [Gravar em uma tabela de extensão](/pt-BR/pipelines#gravar-em-uma-tabela-de-extensão). |
| `delaySecs` | Apenas para pipelines agendados. Por esse número de segundos, a execução adia a leitura do intervalo mais recente para dar tempo de chegarem eventos atrasados. De 0 a 3600. Padrão: 60. |
| `retry` | Apenas para pipelines agendados. `runRetries` define o número de novas tentativas em uma janela cuja leitura ou gravação falhou. `deliveryRetries` define o número de novas tentativas de entrega a um conector. Cada valor vai de 0 a 10. Padrão: 3. |
| `deadLetterStream` | Apenas para pipelines agendados. Fluxo de logs que recebe eventos que o pipeline não conseguiu processar, gravar ou entregar. Use um fluxo que o pipeline não leia nem use para gravação. |
| `dedupeField` | Apenas para pipelines agendados. Durante uma execução, o pipeline descarta eventos cujo valor nesse campo já apareceu. |
| `retainSource` | Apenas para logs em tempo real. Mantém o evento original no fluxo de origem. |

Campos das etapas de contagem, além de `transformName` e `kind`. Use um nome diferente para cada etapa de contagem do pipeline. Consulte [Contagem e limites](/pt-BR/pipelines#contagem-e-limites).

| Campo | Observações |
|---|---|
| `conditions` | Seleciona os eventos aos quais a etapa se aplica. Defina até 16 testes, cada um com `field`, `test` (`equals`, `not_equals`, `contains`, `starts_with`, `matches`, `exists`, `missing`, `gt`, `gte`, `lt` ou `lte`) e `value`. O evento precisa passar em todos os testes. `gt`, `gte`, `lt` e `lte` comparam com um número. `matches` usa uma expressão regular. Uma lista vazia inclui todos os eventos. |
| `metric` | Apenas para `generate_metric`. `name`, `type` (`count`, `gauge` ou `histogram`), `field` (obrigatório para `gauge` e `histogram`; se definido para `count`, soma os valores do campo), `groupBy` (até 10 campos), `buckets` (de 1 a 30 limites superiores em ordem crescente para um histograma), `stream` (fluxo de métricas) e `intervalSecs` (`10`, `30`, `60`, que é o padrão, ou `300`). Apenas para pipelines de logs, RUM e rastreamentos. |
| `quota` | Apenas para `quota`. `unit` (`events` ou `bytes`), `limit` (limite diário nessa unidade, de 1 a 10^15), `partitionBy` (até 5 campos), `overrides` (até 100 entradas no formato `{"values": {"<field>": "<value>"}, "limit": <n>}`, com um valor para cada campo de `partitionBy`), `action` (`drop`, por padrão, `pass` ou `route`) e `target` (fluxo de logs para `route`). Apenas para pipelines de logs e para fluxos de RUM, exceto `rum_views` e `rum_vitals`. Fluxos de RUM não aceitam `route`. |
| `throttle` | Apenas para `throttle`. `limit` (eventos por janela, de 1 a 1.000.000), `windowSecs` (de 1 a 86.400), `groupBy` (até 5 campos), `action` (`drop`, por padrão, ou `route`) e `target`. Aplica-se aos mesmos pipelines que `quota`. |

**Erros**

| Status | Causa |
|---|---|
| `400` | Agendamento fora do formato `every:Ns/m/h`, intervalo de leitura retrospectiva menor ou igual a zero, pipeline agendado para perfis, pipeline de perfis em um fluxo diferente de `default`, pipeline de métricas, rastreamentos, perfis ou RUM em tempo real que grava em outro fluxo, roteia eventos ou mantém os eventos na origem, etapa de um desses pipelines que altera um [campo preservado](/pt-BR/pipelines#métricas-e-traces) de uma amostra, etapa que pode descartar eventos em `rum_views` ou `rum_vitals`, etapa de VRL que não compila, nome de fluxo inválido, mais de 8 fluxos para leitura ou gravação ou mais de 8 tabelas de extensão, etapa de roteamento cujo fluxo fixo ou alternativo é um fluxo de origem, fluxo de eventos com falha que o pipeline lê ou no qual grava, [fluxo de RUM](/pt-BR/pipelines#streams-de-rum) como destino de gravação ou roteamento, `rum_sessions` como origem de um pipeline em tempo real, [fluxo da plataforma](/pt-BR/pipelines#streams-da-plataforma) como destino de gravação ou roteamento ou como fluxo a ser alterado em tempo real, `delaySecs` ou número de novas tentativas fora do intervalo permitido. Esse erro também ocorre quando um pipeline de alertas tem origem ou severidade desconhecida, etapa de roteamento, etapa de resumo com IA sem prompt, etapa de chamada de API que não usa um conector HTTP da organização, etapa de consulta que não contém exatamente uma consulta, lê `_audit` ou usa um marcador de substituição fora de uma string ou sem correspondência no evento, uma etapa que acessa recursos externos ao MoleSignal em um pipeline `notify`, `policies` ou a origem `manual` em um pipeline `open`, ou mais de 20 etapas. O erro também ocorre quando um pipeline agendado ou de alertas usa uma etapa `generate_metric`, `quota` ou `throttle`, quando uma dessas etapas recebe dados que não aceita, quando duas dessas etapas têm o mesmo nome ou quando há configurações inválidas, como um nome de métrica que o PromQL não consegue selecionar, um rótulo presente em todas as amostras da métrica (`value`, `le`, `metric_name`…) ou um `target` igual ao fluxo de origem. |
| `403` | O pipeline lê `_audit`, e o token não tem a permissão `audit.read` ou pertence a uma conta de serviço. |
| `409` | Um pipeline agendado tenta gravar em um fluxo que também lê, ou já existe um pipeline em tempo real ativo para o mesmo tipo de dado e o mesmo fluxo de origem (`a realtime pipeline is already enabled for this <signal> stream`). |

Consulte [Pipelines](/pt-BR/pipelines) para saber mais sobre o modo em tempo real, a etapa de roteamento, as posições de leitura e as novas tentativas.
