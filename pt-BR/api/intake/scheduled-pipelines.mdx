| Operação | Endpoint | Permissão |
|---|---|---|
| Listar | `GET /api/v1/scheduled_pipelines` | `pipelines.read` |
| Criar | `POST /api/v1/scheduled_pipelines` | `pipelines.create` e `audit.read` se o pipeline ler `_audit` |
| Consultar | `GET /api/v1/scheduled_pipelines/{id}` | `pipelines.read` |
| Atualizar | `PUT /api/v1/scheduled_pipelines/{id}` | `pipelines.edit` para alterar a configuração, `audit.read` se o pipeline ler `_audit` e `pipelines.pause` se `enabled` mudar |
| Excluir | `DELETE /api/v1/scheduled_pipelines/{id}` | `pipelines.delete` |
| Histórico de execuções | `GET /api/v1/scheduled_pipelines/{id}/runs` | `pipelines.read` |
| Limites de hoje | `GET /api/v1/scheduled_pipelines/{id}/limits` | `pipelines.read` |
| Processamento retroativo | `POST /api/v1/scheduled_pipelines/{id}/backfill` | `pipelines.run` e `audit.read` se o pipeline ler `_audit` |

## Listar

A lista retorna todos os pipelines com o estado da execução mais recente e um resumo das últimas 24 horas:

<ResponseExample>
```json 200
[
  {
    "id": "3KBHcb6imgQq7FXBsROGTIRHOyg",
    "name": "normalize-app",
    "sourceStream": "app_raw",
    "targetStream": "app",
    "functionSteps": { "mode": "scheduled", "signalType": "logs", "sources": ["app_raw", "nginx_raw"], "steps": [ ... ] },
    "cron": "every:5m",
    "lookbackSecs": 300,
    "enabled": true,
    "lastRunAt": 1790000000000000,
    "readUntil": { "appRaw": 1789999940000000, "nginxRaw": 1789999940000000 },
    "retry": null,
    "alertRecord": null,
    "auditReaderId": null,
    "auditReader": null,
    "createdAt": 1789900000000000,
    "updatedAt": 1789900000000000,
    "lastRunState": "succeeded",
    "lastRunStartedAt": 1790000000000000,
    "lastRunFinishedAt": 1790000000250000,
    "lastRunScannedRows": 1200,
    "lastRunError": null,
    "runs24h": 288,
    "succeededRuns24h": 288,
    "failedRuns24h": 0
  }
]
```
</ResponseExample>

Cada item inclui os campos de [Consultar](#consultar), os dados da execução mais recente em `lastRunState`, `lastRunStartedAt`, `lastRunFinishedAt`, `lastRunScannedRows` (os eventos lidos) e `lastRunError`, além das contagens de execuções das últimas 24 horas.

## Consultar

```http
GET /api/v1/scheduled_pipelines/{id}
```

Retorna o pipeline com a posição de leitura de cada origem e a nova tentativa programada:

<ResponseExample>
```json 200
{
  "id": "3KBHcb6imgQq7FXBsROGTIRHOyg",
  "name": "normalize-app",
  "sourceStream": "app_raw",
  "targetStream": "app",
  "functionSteps": { "mode": "scheduled", "signalType": "logs", "sources": ["app_raw", "nginx_raw"], "steps": [ ... ] },
  "cron": "every:5m",
  "lookbackSecs": 300,
  "enabled": true,
  "lastRunAt": 1790000000000000,
  "readUntil": { "appRaw": 1789999940000000, "nginxRaw": 1789999640000000 },
  "retry": {
    "source": "nginx_raw",
    "attempt": 2,
    "nextAt": 1790000030000000,
    "error": "read: <reason>"
  },
  "alertRecord": null,
  "auditReaderId": null,
  "auditReader": null,
  "createdAt": 1789900000000000,
  "updatedAt": 1789900000000000
}
```
</ResponseExample>

| Campo | Observações |
|---|---|
| `readUntil` | A posição de leitura de cada origem, em microssegundos. O pipeline já tratou os eventos da origem anteriores a essa posição. Origens que o pipeline ainda não leu não têm entrada. |
| `retry` | A próxima tentativa programada para uma janela que falhou, ou `null`. `source` identifica a origem, `attempt` indica o número da próxima tentativa, `nextAt` indica o horário programado e `error` indica o erro da última tentativa. |
| `alertRecord` | Contagens do pipeline de alertas no dia mais recente em que recebeu um evento, em UTC: `day` (`YYYY-MM-DD`), `processed`, `dropped` e `failed`. `last_dropped` e `last_failed` registram o último descarte e a última falha do dia, respectivamente, com `atTime`, `rule` (a regra, a origem do alerta ou a verificação sintética) e `reason` em cada registro. Uma contagem ausente vale 0. O valor é `null` para outros pipelines e para pipelines de alertas que ainda não receberam eventos. Consulte [Contagens diárias](/pt-BR/pipelines/alert-events#contagens-diárias). |
| `auditReaderId` | Identifica o usuário cujas permissões o pipeline usa para ler `_audit`: o último usuário que salvou o pipeline. O valor é `null` se o pipeline não ler `_audit`. Consulte [Fluxo de auditoria](/pt-BR/settings/data-security#fluxo-de-auditoria). |
| `auditReader` | `id`, `displayName` e `email` desse usuário, disponíveis para quem tem `pipelines.read`. O valor é `null` se o usuário não existir mais ou se o sistema não puder consultar seus dados. Nesses casos, `auditReaderId` não muda. |

Consulte [Agendamento e posições de leitura](/pt-BR/pipelines#agendamento-e-posições-de-leitura) e [Novas tentativas e eventos não entregues](/pt-BR/pipelines#novas-tentativas-e-eventos-com-falha).

## Atualizar e excluir

`PUT` aceita o mesmo corpo de [Criar um pipeline](/pt-BR/api/intake/create-pipeline) e substitui a configuração. Alterar apenas `enabled` exige `pipelines.pause`. Qualquer outro `PUT` exige `pipelines.edit`, mesmo que nada mude. Alterar `enabled` de `false` para `true` redefine as posições de leitura. Assim, o pipeline volta a ler os últimos `lookbackSecs` de cada origem. `DELETE` retorna `{"deleted": true}`.

Em um pipeline que lê `_audit`, `PUT` também define quais permissões o pipeline usa para a leitura. Consulte [Fluxo de auditoria](/pt-BR/settings/data-security#fluxo-de-auditoria).

| O `PUT` | Também exige | Permissões que o pipeline usa para ler `_audit` |
|---|---|---|
| Altera a configuração | `audit.read` e um token que não pertença a uma conta de serviço | A partir daí, as permissões de quem fez a solicitação. |
| Não altera nada | Nada | A partir daí, as permissões de quem fez a solicitação, desde que tenha `audit.read` e o token não pertença a uma conta de serviço. Caso contrário, as permissões não mudam e a API não retorna erro. |
| Altera apenas `enabled` | Nada | Não mudam. |

## Histórico de execuções

```http
GET /api/v1/scheduled_pipelines/{id}/runs?limit=50&beforeTime=<cursor>
```

Retorna as execuções de um pipeline agendado, da mais recente à mais antiga. Pipelines em tempo real ou de alertas não registram execuções.

<ResponseExample>
```json 200
[
  {
    "id": "3KE7Yq0d3jvXm5cJ8r2bWQzN1aP",
    "pipelineId": "3KBHcb6imgQq7FXBsROGTIRHOyg",
    "state": "succeeded",
    "startedAt": 1790000000000000,
    "finishedAt": 1790000000250000,
    "scannedRows": 1200,
    "writtenRows": 1150,
    "droppedRows": 48,
    "failedRows": 2,
    "attempt": 1,
    "error": null,
    "warning": "stream `app` rejected 2 event(s): <reason>"
  }
]
```
</ResponseExample>

| Campo | Observações |
|---|---|
| `state` | `running`, `succeeded`, `failed` ou `cancelled`. |
| `startedAt`, `finishedAt` | Horários de início e término da execução. `finishedAt` é `null` enquanto a execução estiver em andamento. |
| `scannedRows` | Eventos que a execução leu das origens. |
| `writtenRows` | Eventos que todos os destinos aceitaram. |
| `droppedRows` | Eventos que uma etapa descartou com `abort` ou que a deduplicação removeu. |
| `failedRows` | Eventos que causaram falha em uma etapa, que o pipeline encaminhou para uma origem ou que algum destino não aceitou. |
| `attempt` | `1` na primeira tentativa. O valor aumenta a cada nova tentativa de processar uma janela que falhou. |
| `error` | Motivo da falha da execução: uma janela que falhou, com a nova tentativa programada, ou um fluxo de destino que não aceitou nenhum dos eventos enviados a ele quando o pipeline não tem um fluxo de eventos não entregues. |
| `warning` | Problemas que não fizeram a execução falhar, como eventos com falha, rejeitados ou não entregues, ou uma janela que o pipeline pulou após esgotar as tentativas. |

`scannedRows` equivale à soma de `writtenRows`, `droppedRows` e `failedRows`.

## Limites de hoje

```http
GET /api/v1/scheduled_pipelines/{id}/limits
```

Retorna o que as [etapas de cota e limitação de taxa](/pt-BR/pipelines#contagem-e-limites) de um pipeline em tempo real deixaram passar ou retiveram hoje, desde 00:00 UTC, com as contagens de todos os nós. Os nós somam suas contagens a cada 5 segundos. Se uma etapa não contabilizou nada hoje, o resultado não inclui uma linha para ela.

<ResponseExample>
```json 200
{
  "dayStart": 1790035200000000,
  "buckets": [
    {
      "step": "daily",
      "bucket": "[\"checkout\"]",
      "admittedEvents": 1000000,
      "admittedBytes": 524288000,
      "overEvents": 1240,
      "overBytes": 650117
    },
    {
      "step": "per-host",
      "bucket": "",
      "admittedEvents": 86400,
      "admittedBytes": 45298483,
      "overEvents": 12,
      "overBytes": 6291
    }
  ]
}
```
</ResponseExample>

| Campo | Observações |
|---|---|
| `step` | Nome da etapa. |
| `bucket` | Vazio para uma cota sem agrupamento e para uma etapa de limitação de taxa. Para uma cota com agrupamento, contém os valores dos campos de agrupamento em uma lista JSON, na ordem dos campos. Usa `null` quando falta um valor no evento e `*` para grupos acima do limite de 1.000. |
| `admittedEvents`, `admittedBytes` | O que passou dentro do limite. |
| `overEvents`, `overBytes` | O que excedeu o limite. Conforme a configuração, a etapa descarta esses dados, deixa que passem ou os envia a outro fluxo. |

## Processamento retroativo

```http
POST /api/v1/scheduled_pipelines/{id}/backfill
```

| Campo | Tipo | Observações |
|---|---|---|
| `startTime` | inteiro | Início da janela, em microssegundos. |
| `endTime` | inteiro | Fim da janela. O valor deve ser maior que `startTime`, e a janela não pode exceder 31 dias. |

<RequestExample>
```bash cURL
curl -X POST http://localhost:5080/api/v1/scheduled_pipelines/$PIPELINE_ID/backfill \
  -H "authorization: Bearer $MS_TOKEN" \
  -H 'content-type: application/json' \
  -d '{"startTime": 1790000000000000, "endTime": 1790086400000000}'
```
</RequestExample>

<ResponseExample>
```json 202
{
  "jobs": [
    {
      "source": "app_raw",
      "jobId": "3KE6epTrWXts1oa2ePEKIHKxG19",
      "monitor": "/api/v1/query/jobs/3KE6epTrWXts1oa2ePEKIHKxG19"
    },
    {
      "source": "nginx_raw",
      "jobId": "3KE6eqAbXq0n2yLr7VvTq9cUo4D",
      "monitor": "/api/v1/query/jobs/3KE6eqAbXq0n2yLr7VvTq9cUo4D"
    }
  ]
}
```
</ResponseExample>

O processamento retroativo envia uma tarefa de busca por origem. Cada tarefa lê os dados da origem na janela, aplica as etapas, grava e entrega os eventos e armazena os eventos não entregues da mesma forma que uma execução agendada. As posições de leitura do pipeline não mudam. Acompanhe cada tarefa pelo caminho em `monitor`. Consulte [Consulta](/pt-BR/query#intervalos-de-tempo-e-tarefas-assíncronas).

Um pipeline em tempo real ou de alertas retorna `400` (`realtime and alert pipelines do not support backfill`). Um pipeline que lê `_audit` retorna `403` se o token não tiver `audit.read` ou pertencer a uma conta de serviço. Ao executar, a tarefa verifica novamente as permissões de quem a enviou e falha se essa conta não tiver mais `audit.read`.
