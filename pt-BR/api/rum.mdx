A API de RUM recebe e permite consultar eventos de clientes web e móveis. Todos os endpoints usam o
prefixo `/api/v1/rum` e exigem um token de portador.

```http
Authorization: Bearer <token>
```

Gravar eventos e segmentos de reprodução exige `rum.write`. Um [token de cliente](/pt-BR/api/auth/rum-token) vinculado a uma aplicação tem
apenas essa permissão para essa aplicação. A leitura exige a permissão da área correspondente: `rum.events.read`, `rum.sessions.read`, `rum.replay.read`, `rum.issues.read`, `rum.analytics.read`, `rum.applications.read` ou `rum.playlists.read`. Um cliente da plataforma pode usar `sys.telemetry.read`
no escopo protegido `_sys`. Criar, alterar e excluir uma aplicação exige `rum.applications.manage`. Definir o status, a equipe
ou a pessoa responsável por um problema exige `rum.playlists.manage`.

As linhas correspondem a usuários reais. A API exclui sessões do tipo `synthetics` ou `ci_test`, a menos que um filtro especifique `session.type`, `synthetics.*` ou `ci_test.*`. Consulte [tráfego de teste](/pt-BR/rum/test-traffic). Um campo também pode ser uma chave de uma coluna JSON: `feature_flags.<key>`, `context.<key>`, `usr.extra.<key>` ou `view.custom_timings.<key>`.

Um **tipo** indica com que tipo de linha um endpoint trabalha: `sessions`, `views`, `actions`, `errors`, `resources`, `longTasks`,
`vitals` ou `logs`. Cada tipo corresponde ao [fluxo](/pt-BR/rum/events#onde-os-eventos-são-armazenados) de mesmo nome, sem o prefixo
`rum_`.

## Envie um segmento de reprodução

```http
POST /api/v1/rum/replay
```

```json
{
  "application": "checkout-web",
  "sessionId": "6f1c2b7e-1d5a-4c6b-9a3e-0a1b2c3d4e5f",
  "seq": 1,
  "events": [{ "type": 2, "timestamp": 1790000000000, "data": { "node": {} } }]
}
```

`sessionId`, `seq` e `events` são obrigatórios. Se esses campos estiverem configurados no SDK, envie também `env`, `service` e `version`:
os [filtros de retenção](/pt-BR/rum/sampling#filtros) da aplicação usam esses campos para avaliar a sessão. A API só armazena o segmento se
mantiver a sessão. A API não aceita nenhum outro campo. `events` contém eventos do rrweb. Um token de cliente só permite gravar
na aplicação à qual está vinculado: omita `application` ou informe a aplicação vinculada. Um valor diferente resulta em `403`. Com qualquer outra credencial,
informe a aplicação. Se a aplicação não existir, a API retorna `404`. A resposta descreve o segmento armazenado:
`id`, `seq`, `eventCount` e `hasFullSnapshot`.

`GET /api/v1/rum/replay/{sessionId}` retorna `sessionId`, `segmentCount` e `events`, que contém, em ordem, os eventos de todos os
segmentos da sessão.

## Gerencie aplicativos

Um aplicativo tem `id`, `name`, `platform` e `settings`:

```json
{
  "id": "checkout-web",
  "name": "Checkout web",
  "platform": "browser",
  "settings": {
    "collectIp": true,
    "collectGeo": true,
    "defaultPrivacy": "mask",
    "issuesPerHour": 100,
    "scrub": ["secrets", "emails", "phones", "cards", "national_ids", "url_params"],
    "sessionSampleRate": 100,
    "retentionFilters": [],
    "keepErrors": true,
    "sdk": { "sessionReplaySampleRate": 20, "forwardConsoleLogs": ["warn", "error"] },
    "segments": [{ "id": "enterprise", "name": "Enterprise", "conditions": [{ "field": "usr.extra.plan", "op": "is", "values": ["enterprise"] }] }]
  },
  "createdBy": "<user-id>",
  "createdAt": 1790000000000000,
  "updatedAt": 1790000000000000
}
```

| Campo | Regra |
|---|---|
| `id` | Aceito apenas na criação. De 1 a 64 caracteres entre `A-Z`, `a-z`, `0-9`, `.`, `_`, `:` e `-`. Se omitido, o servidor gera o identificador a partir do nome. Não é possível alterá-lo. |
| `name` | Obrigatório na criação. De 1 a 128 caracteres. |
| `platform` | `browser` (padrão), `android`, `ios`, `flutter`, `react-native` ou `other`. |
| `settings` | `collectIp` e `collectGeo` são valores booleanos e têm `true` como padrão. `defaultPrivacy` aceita `mask` (padrão), `mask-user-input` ou `allow`. `issuesPerHour` define quantos [problemas](/pt-BR/rum/errors#novos-problemas-por-hora) novos o aplicativo abre por hora, de 1 a 10000, com padrão de 100. `scrub` lista os tipos de texto sensível que o servidor remove de um evento antes de armazená-lo: `secrets`, `emails`, `phones`, `cards`, `national_ids` e `url_params`. Por padrão, o servidor remove todos os tipos. Uma lista vazia não remove nenhum (consulte [Privacidade no RUM](/pt-BR/rum/privacy#remova-texto-sensível-na-ingestão)). `sessionSampleRate` define o percentual de sessões que o servidor mantém entre aquelas que não correspondem a nenhum filtro de retenção. Use um número inteiro de 0 a 100. O padrão é 100 (consulte [Amostragem de dados do RUM](/pt-BR/rum/sampling#retenha-uma-porcentagem-das-sessões-no-servidor)). Um valor acima de 100 retorna `400`. `retentionFilters` é a lista de [filtros](/pt-BR/rum/sampling#filtros), com até 10 itens. Cada item tem o formato `{ "name", "rate", "conditions" }` e um `id`. Se o `id` não for informado, o servidor o gera a partir do nome e o mantém mesmo que o nome do filtro mude. Uma solicitação `PATCH` substitui toda a lista. `rate` é um número inteiro de 0 a 100. Uma condição tem o formato `{ "field", "op", "values" }`: `field` aceita `env`, `service`, `version`, `source`, `session.type`, `geo.country_iso_code`, `browser.name`, `os.name` ou `device.type`; `op` aceita `is` ou `is_not`; e `values` contém de 1 a 20 valores. Cada filtro tem no máximo 5 condições. Use cada nome uma única vez, sem distinção entre maiúsculas e minúsculas. Os identificadores `default` e `errors` são reservados. `keepErrors` mantém os erros das sessões descartadas e tem `true` como padrão. Uma lista inválida retorna `400`. `segments` é a lista de [segmentos](/pt-BR/rum/analytics#segmentos), com até 20 itens. Cada item tem o formato `{ "name", "conditions" }` e um `id`. Se o `id` não for informado, o servidor o gera a partir do nome e o mantém mesmo que o nome do segmento mude. Uma solicitação `PATCH` substitui toda a lista. Uma condição tem o formato `{ "field", "op", "values" }`: `field` aceita `service`, `version`, `source`, `usr.id`, `usr.email`, `account.id`, `browser.name`, `os.name`, `device.type`, `geo.country_iso_code`, `geo.continent_code`, `geo.city` ou `usr.extra.<key>`; `op` aceita `is` ou `is_not`; e `values` contém de 1 a 20 valores. Cada segmento tem de 1 a 5 condições. `sdk` define o que `GET /api/v1/rum/config` retorna a um SDK inicializado com `remoteConfiguration`. Aceita `sessionSampleRate` e `sessionReplaySampleRate` (de 0 a 100), `defaultPrivacyLevel`, `trackUserInteractions` e `forwardConsoleLogs` (uma lista com `debug`, `log`, `info`, `warn` e `error`). Para os campos que `sdk` omite, o SDK usa os valores fornecidos pela página. Para cada configuração omitida, o servidor usa o valor padrão na criação e mantém o valor atual em uma solicitação `PATCH`. |

`POST` retorna o novo aplicativo. Se o identificador ou o nome já existir, a solicitação retorna `409`. `PATCH` aceita `name`, `platform` e
`settings`. `DELETE` retorna `{ "deleted": true }`. Os eventos que o aplicativo já enviou permanecem nos fluxos até
o fim do período de retenção.

## Busque linhas

```http
GET /api/v1/rum/search?type=errors&from=1790000000000000&to=1790003600000000&filters=[{"field":"env","op":"=","value":"production"}]&limit=100
```

`POST` aceita os mesmos parâmetros no corpo JSON. Use esse método para consultas longas demais para uma URL. Na URL, `filters`, `freeText` e
`columns` são listas codificadas em JSON.

| Parâmetro | Tipo | Comportamento |
|---|---|---|
| `type` | string | Obrigatório. O tipo das linhas. |
| `from`, `to` | inteiro | O intervalo em microssegundos desde a época Unix. Por padrão, `to` é o momento atual e `from` é 24 horas antes de `to`. `to` deve ser maior que `from`. |
| `filters` | lista | Condições que todas as linhas devem atender. Consulte a seção abaixo. |
| `freeText` | lista de strings | Até 8 palavras. Cada palavra deve aparecer em pelo menos uma das colunas de texto do tipo, sem distinção entre maiúsculas e minúsculas. |
| `columns` | lista de strings | As colunas a retornar. Se omitido, a resposta inclui as colunas padrão do tipo. A resposta sempre inclui a coluna que identifica a linha. |
| `limit` | inteiro | O tamanho da página, de 1 a 5.000. O padrão é 100. |
| `cursor` | string | O `nextCursor` ou `previousCursor` de uma resposta anterior. Omita os demais parâmetros ou repita-os sem alterações. |

Um **filtro** contém `field`, `op` e `value`. Use até 32 filtros, com no máximo 512 caracteres por valor.

| `op` | Significado |
|---|---|
| `=`, `!=` | Igual e diferente, respectivamente. Com `value` vazio, `=` verifica se o campo não tem valor e `!=` verifica se tem valor. |
| `in`, `not_in` | O valor do campo está ou não na lista, respectivamente. `value` é uma lista JSON de 1 a 100 valores, como `["Chrome","Safari"]`. |
| `contains` | O campo contém o texto, sem distinção entre maiúsculas e minúsculas. Funciona com colunas de texto e documentos JSON. |
| `>`, `>=`, `<`, `<=` | Compara um número ou um instante. |
| `exists`, `missing` | O campo tem valor ou não tem valor, respectivamente. |

A solicitação retorna `400` se o tipo não incluir o campo ou se o campo não aceitar o operador.

A resposta contém as linhas de uma página, da mais recente para a mais antiga:

```json
{
  "items": [
    { "timestamp": 1790000001600000, "error.message": "Payment provider timeout", "error.id": "0a9b8c7d-6e5f-4a3b-8c1d-2e3f4a5b6c70" }
  ],
  "hasMore": true,
  "nextCursor": "<cursor>",
  "previousCursor": null
}
```

Cada linha contém `timestamp` e as colunas solicitadas. Uma coluna JSON contém o documento. Visualizações e sessões
aparecem uma única vez, na versão mais recente.

## Conte e descreva linhas

`facets` aceita os parâmetros de `search` sem paginação e acrescenta `field` (obrigatório) e `limit` (de 1 a 100, com padrão de 10).
Retorna os valores mais frequentes do campo nas linhas que correspondem à consulta:

```json
{ "field": "browser.name", "values": [{ "value": "Chrome", "count": 812 }, { "value": "Safari", "count": 247 }] }
```

Se a contagem exceder o limite de tempo ou o sistema estiver ocupado, a resposta retorna uma lista vazia com `unavailable` definido como `time_budget` ou `busy`.
A consulta a um campo que contém um documento JSON retorna `400`, mas é possível contar por valor usando uma chave do documento, como `feature_flags.checkout_v2`. As facetas de `session.type` contam todos os tipos de sessão.

`keys` aceita os parâmetros de seleção, `column` (obrigatório: `feature_flags`, `context`, `usr.extra` ou `view.custom_timings`) e `limit` (de 1 a 500, com padrão de 100). O padrão de `type` é `views`. Retorna as chaves em ordem decrescente pelo número de sessões em que aparecem:

```json
{ "column": "feature_flags", "keys": [{ "key": "checkout_v2", "sessions": 812 }] }
```

`distribution` aceita os parâmetros de seleção, `field` (obrigatório: um campo numérico ou uma chave numérica em uma coluna JSON) e `bars` (de 1 a 100, com padrão de 40). Conta as linhas armazenadas. As barras têm largura uniforme entre o menor valor e o percentil 99. A última também conta os valores acima desse percentil, de modo que seu `to` é o maior valor. Se todos os valores forem iguais, a resposta contém uma única barra.

```json
{
  "field": "view.loading_time",
  "unit": "ns",
  "rows": 812,
  "min": 90000000,
  "max": 41000000000,
  "p50": 800000000,
  "p75": 1400000000,
  "p95": 3100000000,
  "p99": 6000000000,
  "bars": [{ "from": 90000000, "to": 237750000, "rows": 12 }]
}
```

`histogram` aceita os mesmos parâmetros de seleção e os parâmetros que definem os intervalos da contagem: `bucketTime` (no mínimo 1000) e `originTime`, o início do
primeiro intervalo. Se omitido, `originTime` assume o valor de `from` e não pode ser posterior a ele. Cada faixa comporta no máximo 512 intervalos. Cada intervalo tem o formato `{ startTime, total, errors }`. `errors` conta as linhas
com problemas: sessões e visualizações com erros, ações com sinais de frustração e solicitações com status igual ou superior a `400` ou igual a
`0`. `split` é `false` para os tipos que não têm essas linhas.

`GET /api/v1/rum/schema/{type}` lista as colunas que os outros endpoints aceitam e retornam:

```json
{
  "type": "views",
  "stream": "rum_views",
  "idField": "view.id",
  "versioned": true,
  "defaultColumns": ["view.id", "view.url_path", "view.loading_time"],
  "fields": [
    { "name": "view.loading_time", "dataType": "int64", "unit": "ns", "facetable": true, "indexed": false }
  ]
}
```

`dataType` pode ser `bool`, `int64`, `float64`, `utf8` ou `json`. `unit` pode ser `ns`, `ms`, `epoch_ms`, `bytes`, `count`,
`score`, `percent`, `per_second`, `px` ou `none`. O servidor armazena as durações em nanossegundos, conforme enviadas pelo SDK, e o cliente
as formata. `epoch_ms` indica um instante em milissegundos desde a época Unix, como `session.start` e
`session.last_activity`. O cliente o exibe como data e hora. Um campo `facetable` permite contar ocorrências por valor, um
campo `indexed` permite filtrar sem ler todas as linhas e `idField` indica a coluna que distingue uma linha de outra.

## Medir linhas

`aggregate` usa a seleção de `search` e calcula medidas sobre todas as linhas correspondentes. Retorna os números por trás de gráficos,
tabelas e mapas: quantas sessões houve, qual é o 75º percentil de uma métrica vital, por página ou por hora.

```http
GET /api/v1/rum/aggregate?type=views&groupBy=["view.url_path_group"]&measures=[{"fn":"count","name":"views"},{"fn":"p75","field":"view.performance.lcp.timestamp","name":"lcp"}]&limit=5
```

| Parâmetro | Tipo | Comportamento |
|---|---|---|
| `type`, `from`, `to`, `filters`, `freeText` | | Como em `search`. |
| `measures` | lista | Obrigatório. Até 16 medidas. Veja abaixo. |
| `groupBy` | lista de strings | Até 2 campos, com uma linha para cada combinação de valores. Não é possível agrupar por um campo que contém um documento JSON, mas é possível agrupar por uma chave dele: `feature_flags.checkout_v2`. |
| `bucketTime`, `originTime` | inteiro | Como em `histogram`. Com esses parâmetros, há uma linha por grupo em cada barra. |
| `orderBy` | string | O nome de uma medida, um campo de agrupamento ou `time` (barras sem grupos). Sem esse parâmetro, a primeira medida define a ordem dos grupos e as barras seguem a ordem cronológica. |
| `order` | `asc` ou `desc` | Se omitido, usa ordem decrescente para medidas e crescente para grupos ou tempo. |
| `limit` | inteiro | O número de grupos, de 1 a 250. O padrão é 10. Com barras, o máximo é 20, e o resultado acompanha cada grupo ao longo de todas as barras. |
| `estimate` | booleano | O padrão é `true`: contagens, somas e médias representam todas as sessões. Cada linha recebe um peso com base na taxa de retenção (`retention.rate`), e os percentis usam os mesmos pesos. Com `false`, o cálculo usa apenas as linhas armazenadas, como no explorador. |

Uma **medida** tem `fn` e `field` e pode ter `name`, `where` e `fallback`.

| `fn` | Significado |
|---|---|
| `count` | Conta as linhas. Com `field`, conta apenas as linhas que têm um valor nesse campo. Ajusta a contagem pela taxa de retenção quando `estimate` está ativado. |
| `stored` | Conta as linhas armazenadas, independentemente da taxa de retenção. |
| `count_distinct` | Conta os valores distintos de `field`. `fallback` indica qual campo usar quando `field` não tem valor, o que permite distinguir usuários sem ID pelo ID anônimo. A contagem usa apenas os usuários e os demais valores observados. Quando `estimate` está ativado, ajusta a contagem de sessões (`session.id`). |
| `sum`, `avg`, `min`, `max` | Calcula a soma, a média, o mínimo ou o máximo de um valor numérico. |
| `p50`, `p75`, `p90`, `p95`, `p99` | Estima o percentil de um valor numérico. |

`where` é uma lista de filtros, como em `search`, e a medida considera apenas as linhas que atendem a esses filtros:
`{"fn":"count","where":[{"field":"session.error.count","op":"=","value":"0"}]}` conta as sessões sem erros. Uma medida
usa `name` como nome, ou `fn(field)` se não houver `name`, ou `fn` se não houver campo. Duas medidas não podem ter o mesmo nome. Um campo
que não existe no tipo ou uma operação numérica sobre um campo não numérico faz a solicitação falhar com `400`.

```json
{
  "groupBy": ["view.url_path_group"],
  "measures": [
    { "name": "views", "fn": "count", "unit": "count" },
    { "name": "lcp", "fn": "p75", "field": "view.performance.lcp.timestamp", "unit": "ns" }
  ],
  "rows": [
    { "group": ["/checkout"], "values": [8031, 3400000000.0] },
    { "group": [null], "values": [212, null] }
  ]
}
```

Cada linha contém o `group` ao qual pertence, na ordem de `groupBy`, e os `values` das medidas, na ordem em que aparecem. Em resultados ao longo do tempo,
a linha também tem `startTime`, o início da barra. Um grupo cujas linhas não têm valor é `null`, assim como um percentil calculado sem
valores. `unit` é `count` ou a unidade do campo indicada por `schema`. A contagem considera cada visualização e sessão uma única vez, na
versão mais recente. Se nenhuma linha corresponder, uma resposta com grupos ou barras não terá linhas. Sem grupos nem barras, a resposta terá uma linha: as contagens serão `0` e as demais medidas serão `null`. Se o usuário não tiver permissão para ver um valor, a resposta retornará o texto usado para mascará-lo. Se a contagem demorar demais ou se
o sistema estiver ocupado, a resposta não terá linhas e `unavailable` será `time_budget` ou `busy`.

## Instrução SQL de um painel do dashboard

```http
POST /api/v1/rum/panel-statement
```

Retorna a instrução SQL que um painel de [dashboard](/pt-BR/dashboards) executa para gerar a mesma visualização do [explorador](/pt-BR/rum/explorer#adicionar-ao-dashboard):
os mesmos números, calculados sobre as mesmas linhas, como em `aggregate` com `estimate` definido como `false`. A operação não lê dados. A
instrução não especifica um período, pois o dashboard a executa no intervalo selecionado pelo usuário. A operação exige `rum.events.read`.

```json
{
  "type": "views",
  "filters": [{ "field": "env", "op": "=", "value": "production" }],
  "chart": "timeseries",
  "measures": [{ "fn": "p75", "field": "view.loading_time", "name": "p75 Loading" }],
  "groupBy": ["browser.name"],
  "groupNames": ["Browser"],
  "limit": 5,
  "interval": "${interval}"
}
```

| Campo | Tipo | Comportamento |
|---|---|---|
| `type`, `filters`, `freeText` | | Como em `search`. |
| `chart` | string | Obrigatório. `timeseries`, `toplist`, `table` ou `distribution`. |
| `measures`, `groupBy`, `orderBy`, `order`, `limit` | | Como em `aggregate`, exceto por `estimate` e pelas barras. Um `toplist` tem um grupo. Um `timeseries` acompanha até 20 grupos. Cada medida gera uma coluna com o nome indicado por `name`. |
| `groupNames` | lista de strings | Nomes das colunas dos grupos, na ordem dos grupos. Se um grupo não tiver nome, a coluna usa o nome do campo. |
| `field` | string | Obrigatório para `distribution`: o campo numérico usado na distribuição. A coluna desse campo usa o primeiro nome de `groupNames`, e a coluna de contagem usa o `name` da primeira medida. |
| `interval` | string | Obrigatório para `timeseries`: o tamanho de cada intervalo de tempo, indicado por uma variável do dashboard como `${interval}` ou por uma duração como `15 minutes`. |

```json
{
  "stream": "rum_views",
  "statement": "WITH \"__top\" AS (SELECT … LIMIT 5) SELECT date_bin(INTERVAL '${interval}', _timestamp) AS \"time\", … FROM \"rum_views_latest\" JOIN \"__top\" ON … GROUP BY 1, 2 ORDER BY 1, 2",
  "columns": [
    { "name": "time", "role": "time", "unit": "none" },
    { "name": "Browser", "role": "group", "unit": "none" },
    { "name": "p75 Loading", "role": "measure", "unit": "ms" }
  ],
  "limit": 10000
}
```

A instrução lê `stream` e acessa a versão mais recente de uma visualização ou sessão por meio de `rum_views_latest` ou
`rum_sessions_latest`. Aplica as condições da seleção e exclui as sessões executadas por testes sintéticos e de CI,
a menos que os filtros mencionem `session.type`, `synthetics.*` ou `ci_test.*`. `columns` lista as colunas retornadas, na ordem: um
`time` que indica o início da barra, os grupos e as medidas. A `unit` de cada medida indica a unidade de exibição. Por exemplo, as durações aparecem em `ms`.

- Um `timeseries` retorna uma linha para cada combinação de barra e grupo. Inclui os grupos mais bem classificados pela primeira medida em todo o
  intervalo.
- Um `toplist` ou uma `table` retorna uma linha por grupo, na ordem solicitada, até `limit`.
- Uma `distribution` retorna 40 barras, do menor valor ao 99º percentil. A última barra conta os valores acima desse percentil. Cada
  barra usa como nome seu valor inicial, na unidade de exibição.

`limit` indica quantas linhas o painel solicita. A operação retorna `400` se o campo não existir no tipo, se os parâmetros não permitirem gerar o gráfico
(por exemplo, um `toplist` sem exatamente um grupo ou um `timeseries` sem `interval`) ou se `interval` não for uma variável nem
uma duração.

## Funis, caminhos e retenção

Os três endpoints em `/api/v1/rum/analytics` respondem às consultas de [análise de RUM](/pt-BR/rum/analytics). Cada um aceita os
parâmetros de seleção de `search` que se aplicam a sessões, visualizações e ações: `from` e `to` em microssegundos e `filters`, os critérios que cada
linha precisa atender, normalmente a aplicação (`application.id`) e o ambiente (`env`). Com `GET`, passe as listas em JSON nos
parâmetros para compartilhar a consulta como um link. `POST` aceita os mesmos nomes em um corpo JSON. Os endpoints exigem `rum.analytics.read` ou `sys.telemetry.read`
no escopo protegido `_sys`. Se a contagem demorar demais ou o sistema estiver ocupado, a resposta não traz números e define `unavailable`
como `time_budget` ou `busy`. As respostas incluem os valores de `from` e `to` do intervalo consultado.

### Funil

```http
GET /api/v1/rum/analytics/funnel?filters=[{"field":"application.id","op":"=","value":"shop-web"}]&steps=[{"type":"views","filters":[{"field":"view.url_path_group","op":"=","value":"/cart"}]},{"type":"actions","name":"Paid","filters":[{"field":"action.target.name","op":"=","value":"Pay now"}]}]&windowSecs=1800&breakdown=browser.name
```

| Parâmetro | Tipo | Comportamento |
|---|---|---|
| `from`, `to` | inteiro | Microssegundos. Se omitidos, abrangem os últimos 7 dias. |
| `filters` | lista | Critérios que todas as etapas precisam atender, além dos filtros próprios de cada etapa. |
| `steps` | lista | Obrigatória. De 2 a 8 etapas. Cada etapa tem um `type` (`views` ou `actions`), uma lista de `filters` no formato de `search` que se aplica às linhas desse tipo e um `name` opcional, que assume o valor do primeiro filtro se omitido. |
| `windowSecs` | inteiro | Intervalo máximo entre a primeira etapa e uma etapa posterior, em segundos. Se omitido, não há limite. |
| `breakdown` | string | Campo de texto das linhas da primeira etapa. Gera um funil para cada valor do campo. Considera apenas os 10 valores com mais sessões. |

Uma sessão conta na primeira etapa pela primeira linha que atende aos critérios dessa etapa. Nas demais, conta pela primeira linha que atende aos critérios e ocorre depois
da linha da etapa anterior, na mesma sessão.

```json
{
  "groups": [
    {
      "value": null,
      "steps": [
        { "name": "/cart", "sessions": 4, "conversion": 1.0, "fromPrevious": null, "medianMs": null },
        { "name": "Paid", "sessions": 2, "conversion": 0.5, "fromPrevious": 0.5, "medianMs": 210000.0 }
      ]
    }
  ],
  "from": 1779400000000000,
  "to": 1780000000000000
}
```

Cada grupo representa o funil das sessões com um mesmo valor de `breakdown`. Os grupos seguem a ordem da contagem de sessões na primeira etapa,
e `value` é `null` tanto no grupo que reúne todas as sessões quanto no grupo das sessões cuja linha não tem valor no campo. `conversion` indica a proporção em relação às
sessões da primeira etapa, `fromPrevious` indica a proporção em relação às sessões da etapa anterior e `medianMs` indica a mediana do tempo
decorrido desde a etapa anterior. Cada campo contém `null` quando não se aplica. Se o campo não for de texto ou não existir no tipo da linha,
a solicitação retorna `400`.

### Caminhos

| Parâmetro | Tipo | Comportamento |
|---|---|---|
| `from`, `to`, `filters` | | Como em `funnel`. As linhas representam visualizações. |
| `anchor` | string | Página de início dos caminhos, ou de término na análise retrospectiva. Se omitida, usa a primeira página de cada sessão, ou a última na análise retrospectiva. |
| `backward` | booleano | Analisa as páginas anteriores à âncora. O padrão é `false`. |
| `depth` | inteiro | De 1 a 6 páginas depois (ou antes) da âncora. O padrão é 3. |
| `by` | string | Campo que identifica a página: `view.url_path_group` (padrão), `view.url_path` ou `view.name`. |

```json
{
  "columns": 3,
  "sessions": 9,
  "backward": false,
  "nodes": [
    { "column": 0, "page": "/products", "sessions": 2, "ends": 0 },
    { "column": 1, "page": "/cart", "sessions": 2, "ends": 0 },
    { "column": 2, "page": "/checkout", "sessions": 1, "ends": 1 }
  ],
  "links": [
    { "column": 0, "source": "/products", "target": "/cart", "sessions": 2 },
    { "column": 1, "source": "/cart", "target": "/checkout", "sessions": 1 }
  ],
  "from": 1779400000000000,
  "to": 1780000000000000
}
```

As páginas aparecem em `columns`, com uma coluna a mais que o valor de `depth`. A página de referência dos caminhos fica na coluna 0 (na última coluna na análise retrospectiva).
Cada nó representa uma página em uma coluna, com `sessions` para as sessões que passaram por ela e `ends` para as que terminaram ali (ou começaram ali,
na análise retrospectiva). Cada ligação vai de uma página de `column` a uma página da coluna seguinte (a próxima em ordem cronológica, mesmo na análise retrospectiva) e inclui as
sessões que seguiram esse trajeto. A análise segue a ordem de abertura das páginas e conta uma única vez as aberturas consecutivas da mesma página. Cada
coluna identifica as 8 páginas com mais sessões e agrupa as demais em `__other__`. `sessions` é o número de sessões que incluem
a página de referência dos caminhos.

### Retenção

| Parâmetro | Tipo | Comportamento |
|---|---|---|
| `from`, `to`, `filters` | | Como em `funnel`. As linhas representam sessões. Sem `from` e `to`, a consulta usa um histórico suficiente para formar coortes: retrocede o dobro de `periods` a partir de agora, com um mínimo de 14 dias (8 semanas para `week`). |
| `period` | `day` ou `week` | Um dia em UTC ou uma semana em UTC que começa na segunda-feira. O padrão é `day`. |
| `periods` | inteiro | De 1 a 30 períodos após o primeiro. O padrão é 7. |

```json
{
  "period": "day",
  "periods": 3,
  "cohorts": [
    { "startTime": 1779408000000000, "users": 1, "returned": [1, 0, null] },
    { "startTime": 1779494400000000, "users": 6, "returned": [0, null, null] }
  ],
  "from": 1779408000000000,
  "to": 1779753600000000
}
```

Uma coorte reúne os usuários que apareceram pela primeira vez no período que começa em `startTime`, dentro do intervalo consultado. A análise identifica cada usuário pelo
`usr.id` da sessão ou, na ausência dele, pelo `usr.anonymous_id`. `returned` informa, para cada período posterior, quantos usuários da
coorte voltaram nesse período. O valor é `null` se o período ainda não tiver terminado em `to`.

## Mapas de calor

Os endpoints em `/api/v1/rum/heatmaps` retornam os dados dos [mapas de calor de RUM](/pt-BR/rum/heatmaps). Eles aceitam `from` e `to` em microssegundos e `filters`, normalmente `application.id`, `view.url_path_group` e a largura da janela (`display.viewport.width`). Com `GET`, passe a lista em JSON no parâmetro. `clicks` e `scroll` também aceitam `limit` e exigem `rum.analytics.read`. As contagens usam as linhas armazenadas, sem estimativas.

```json
{
  "clicks": 148,
  "elements": [
    {
      "element": "body>main>button:nth-of-type(2)",
      "name": "Pay now",
      "selector": "button.pay",
      "clicks": 92,
      "sessions": 60,
      "frustrated": 4,
      "pageX": 640.5,
      "pageY": 720.0,
      "cells": [[5, 4, 31], [6, 4, 28]]
    }
  ],
  "from": 1779400000000000,
  "to": 1780000000000000
}
```

`clicks` retorna de 1 a 300 dos elementos com mais cliques, com 100 por padrão. `element` indica onde o elemento fica na página. `pageX` e `pageY` indicam a posição média dos cliques no elemento em relação à página. `cells` divide o elemento em uma grade de 10 por 10, com cada célula no formato `[column, row, clicks]`.

```json
{
  "views": 310,
  "pageHeight": 4200,
  "medianDepth": 1800,
  "bands": [{ "depth": 800, "reached": 1.0 }, { "depth": 900, "reached": 0.97 }],
  "from": 1779400000000000,
  "to": 1780000000000000
}
```

`scroll` retorna as visualizações com dados de profundidade de rolagem, a altura da página e a profundidade que metade dessas visualizações atingiu. Cada faixa tem 100 pixels: `reached` indica a proporção de visualizações que atingiram essa profundidade e nunca aumenta nas faixas mais abaixo.

`snapshot` aceita o `viewId` de uma das visualizações candidatas e exige `rum.replay.read`. A resposta inclui `candidates`, com até 20 visualizações da página que têm uma gravação para reprodução, da mais recente para a mais antiga, cada uma com `sessionId`, `viewId`, `atTime`, `width` e `height` da janela. Inclui também `snapshot`, com os mesmos dados da visualização exibida e os `events` do rrweb que a reconstroem em `atTime` a partir do último snapshot completo anterior a esse momento. `snapshot` é `null` se não houver gravação de nenhuma sessão que abriu a página.

## Playlists

Uma [playlist](/pt-BR/rum/playlists) é uma lista com nome que reúne sessões de uma única aplicação e indica o momento de interesse para abrir cada sessão.

```json
{
  "id": "2xT9bQ1kLw5nVf8cZ0aR7mHpJd3",
  "application": "checkout-web",
  "name": "Checkout failures",
  "description": "Sessions that ended at the checkout with an error.",
  "createdBy": "<user-id>",
  "createdAt": 1790000000000000,
  "updatedAt": 1790000100000000,
  "sessionCount": 2,
  "sessions": [
    { "sessionId": "3f6c9a52-1b7e-4d08-a5c3-90e2d41f7b68", "atTime": 1790000005000000, "addedBy": "<user-id>", "addedAt": 1790000000000000 },
    { "sessionId": "9d41e7b0-62fa-4c3d-8e15-b7a09c52d3f4", "atTime": null, "addedBy": "<user-id>", "addedAt": 1790000100000000 }
  ]
}
```

`GET /api/v1/rum/playlists` retorna as playlists sem `sessions`, da última alterada para a primeira, e aceita `application` para
filtrar por uma aplicação. A leitura exige `rum.playlists.read`, mas clientes da plataforma podem usar `sys.telemetry.read`. Os demais endpoints alteram uma playlist
e exigem `rum.playlists.manage`. Todos retornam a playlist com suas sessões, exceto `DELETE`, que retorna `{ "deleted": true }`.

| Solicitação | Corpo | Regra |
|---|---|---|
| `POST /rum/playlists` | `application`, `name` e, opcionalmente, `description` e `sessions` | A aplicação precisa existir (`404`). O nome deve ter de 1 a 128 caracteres e ser único entre as playlists da aplicação, sem distinção entre maiúsculas e minúsculas (`409`). A descrição pode ter até 1.000 caracteres. |
| `PATCH /rum/playlists/{id}` | `name` e `description`, ambos opcionais | Campos omitidos mantêm o valor atual. Não é possível alterar a aplicação. |
| `POST /rum/playlists/{id}/sessions` | `sessions` | Ao adicionar novamente uma sessão, a API atualiza `atTime` com o valor informado e mantém a posição da sessão. Cada playlist aceita no máximo 500 sessões (`400`). |

Uma sessão na solicitação tem o formato `{ "sessionId": "...", "atTime": 1790000005000000 }`: o ID tem de 1 a 128 caracteres. Quando informado,
`atTime` indica o momento de abertura da sessão em microssegundos desde a época Unix. Se omitido, a sessão abre do início. A
playlist armazena IDs, não sessões: não verifica se a sessão existe e mantém na lista as sessões cujas linhas a política de retenção excluiu.
`GET /api/v1/rum/sessions/{id}/playlists` retorna as playlists que incluem a sessão, sem listar as sessões dessas playlists.

## Consulte uma linha ou uma sessão

`GET /api/v1/rum/{type}/{id}` retorna uma linha com todas as suas colunas ou `404`. `from` e `to` delimitam o intervalo da busca; sem
esses parâmetros, a busca cobre os últimos 30 dias. `{id}` é o valor de `idField` do tipo.

`GET /api/v1/rum/sessions/{id}/timeline` retorna:

| Campo | Conteúdo |
|---|---|
| `session` | A linha da sessão ou `null` enquanto o sistema ainda não tiver gerado essa linha. |
| `items` | As linhas de todos os outros tipos que pertencem à sessão, da mais antiga à mais recente. Cada linha tem um `type`: `view`, `action`, `error`, `resource`, `long_task`, `vital` ou `log`. |
| `truncated` | Os tipos que ultrapassaram o limite de linhas da linha do tempo. |

`GET /api/v1/rum/sessions/{id}/related-traces` lista os rastreamentos de backend de uma sessão. A resposta inclui os rastreamentos cujo ID constava em uma requisição
da sessão (`relation: direct`). Se não houver nenhum, inclui os rastreamentos executados durante a sessão
(`relation: time-correlated`). Cada rastreamento inclui `trace_id`, `service`, `spanCount`, `durationMs` e
`startedAt`, e a resposta inclui `primaryService`. `GET /api/v1/rum/traces/{traceId}/session` faz a consulta inversa
e retorna a sessão ou `null`.

## Comentários

```http
POST /api/v1/rum/sessions/{id}/comments
```

```json
{ "application": "checkout-web", "atTime": 1790000005000000, "body": "The button does nothing here." }
```

`atTime` indica um momento da sessão em microssegundos desde a época Unix, e `body` aceita de 1 a 2.000 caracteres. Cada sessão comporta no máximo 500 comentários. `GET` retorna `{ "comments": [...] }` em ordem cronológica e exige `rum.replay.read`.

```json
{
  "id": "2xT9bQ1kLw5nVf8cZ0aR7mHpJd3",
  "application": "checkout-web",
  "sessionId": "3f6c9a52-1b7e-4d08-a5c3-90e2d41f7b68",
  "atTime": 1790000005000000,
  "body": "The button does nothing here.",
  "authorId": "<user-id>",
  "authorName": "Ada",
  "createdAt": 1790000010000000,
  "updatedAt": 1790000010000000,
  "editable": true
}
```

`POST` exige `rum.replay.comments.write`. `PATCH` aceita `body`. Tanto `PATCH` quanto `DELETE` exigem essa permissão para comentários do próprio usuário e `rum.replay.comments.manage` para comentários de outros usuários. `editable` indica se o usuário pode alterar o comentário. `DELETE` retorna `{ "deleted": true }`.

## Resumo

`GET /api/v1/rum/sessions/{id}/summary` retorna `{ "summary": ... }` com o resumo salvo no idioma do usuário ou `null` e exige `rum.replay.read`. `POST` usa um modelo para gerar o resumo e exige `rum.replay.summaries.generate`. Se já houver um resumo salvo, a API o retorna sem chamar o modelo. Com `{ "regenerate": true }`, a API chama o modelo, a menos que a sessão não tenha mudado.

```json
{
  "summary": {
    "sessionId": "3f6c9a52-1b7e-4d08-a5c3-90e2d41f7b68",
    "language": "en-us",
    "summary": "The user filled the cart and could not pay: the payment call failed three times.",
    "chapters": [{ "atTime": 1790000005000000, "title": "Fills the cart", "summary": "Adds two items." }],
    "model": "<model>",
    "promptTokens": 1820,
    "completionTokens": 240,
    "generatedAt": 1790000020000000
  }
}
```

A chamada consome parte da cota diária do Mole Agent e tem a origem `replay_summary`. A API retorna `429` quando a cota acaba. Retorna `400` se a organização não tiver um provedor de modelos habilitado com uma chave ou se a sessão não tiver conteúdo para resumir.

## Problemas

O sistema agrupa erros semelhantes em [problemas](/pt-BR/rum/errors), e cada linha de erro contém o ID do problema em `error.issue_id`.
O sistema calcula as métricas do problema com base nos erros no intervalo solicitado. O sistema mantém o estado e o histórico do problema separadamente.
Os tempos são expressos em microssegundos desde a época Unix.

```http
GET /api/v1/rum/issues?application=checkout-web&status=unresolved&sort=sessions&limit=50
```

| Parâmetro | Tipo | Comportamento |
|---|---|---|
| `application` | string | Obrigatório. |
| `env`, `source` | string | Apenas os erros deste ambiente ou os que esta origem enviou (`browser`, `flutter` etc.). |
| `filters` | lista | Condições adicionais para a contagem de erros, como em `search`. |
| `from`, `to` | inteiro | Como em `search`. |
| `status` | string | `unresolved` (padrão: abertos, em investigação e recorrentes), `all` ou um dos valores `open`, `investigating`, `regressed`, `resolved`, `ignored`. |
| `assignee`, `team` | string | ID de usuário ou de equipe, ou `none` para problemas sem responsável. |
| `search` | string | Busca palavras no tipo, na mensagem ou no local do problema, sem distinguir maiúsculas de minúsculas. |
| `fresh` | booleano | Apenas problemas que apareceram pela primeira vez ou voltaram a ocorrer no intervalo. |
| `sort` | string | `sessions` (padrão), `users`, `occurrences`, `lastSeen`, `firstSeen` ou `status`. |
| `order` | `asc` ou `desc` | Se omitido, usa ordem decrescente, exceto para `status`. |
| `limit` | inteiro | De 1 a 100. O padrão é 50. |

```json
{
  "issues": [
    {
      "id": "3f9c2a71e0b4c8d1",
      "applicationId": "checkout-web",
      "status": "regressed",
      "assigneeId": "<user-id>",
      "teamId": null,
      "overflow": false,
      "source": "source",
      "errorType": "ChunkLoadError",
      "message": "Loading chunk 482 failed.",
      "location": "src/router/lazy.ts:34 · loadChunk",
      "firstSeenAt": 1789300000000000,
      "lastSeenAt": 1790000000000000,
      "firstVersion": "2.2.0",
      "lastVersion": "2.4.1",
      "resolvedAt": 1789600000000000,
      "resolvedVersion": "2.3.0",
      "resolvedBy": "<user-id>",
      "regressedAt": 1789900000000000,
      "regressedVersion": "2.4.1",
      "regressedEnvironment": "production",
      "updatedBy": null,
      "updatedAt": 1789900000000000,
      "sessions": 612,
      "users": 498,
      "occurrences": 1530,
      "trend": [3, 5, 4, 9, 40, 120]
    }
  ],
  "total": 8
}
```

`regressedEnvironment` indica o ambiente do erro que fez o problema voltar a ocorrer ou `null` se o erro não indicar um ambiente. Um problema
pertence à aplicação inteira, independentemente do ambiente dos erros. O servidor também registra quando o problema apareceu pela primeira vez em
cada ambiente. As [regras de alerta](/pt-BR/rum/alerts#filtrar-uma-regra) usam esse registro para contar os problemas novos de cada ambiente.

A consulta seleciona os 250 problemas com mais sessões (ou usuários ou ocorrências, conforme `sort`) e aplica os filtros `status`, `assignee`,
`team`, `search` e `fresh`. `total` indica quantos problemas passam pelos filtros antes da aplicação de `limit`. `trend` contém a contagem de ocorrências
em cada uma das até 12 partes iguais do intervalo, da mais antiga à mais recente. `overflow` identifica o problema que contabiliza os erros da aplicação após
atingir o [limite de novos problemas por hora](/pt-BR/rum/errors#novos-problemas-por-hora). Se a contagem demorar demais ou o sistema estiver ocupado, a API
não retorna problemas e define `unavailable` como `time_budget` ou `busy`.

`GET /api/v1/rum/issues/{id}` retorna o problema no mesmo formato da lista, sem `trend`, com `sessions`, `users` e `occurrences`
contabilizados no intervalo entre `from` e `to`, além de dois campos:

| Campo | Conteúdo |
|---|---|
| `samples` | As três últimas sessões em que o problema ocorreu, da mais recente à mais antiga: `timestamp`, `sessionId`, `userId`, `anonymousId`, `page`, `browser`, `system`, `version`, `hasReplay` e `retained`. O valor de `retained` é `false` quando o erro pertence a uma sessão que o sistema não reteve e que não pode ser aberta. |
| `stack` | A pilha do erro mais recente que contém frames. Se nenhum erro tiver frames, retorna o erro mais recente com `frames` vazio. Se não houver erros do problema no intervalo, retorna `null`. Campos: `message`, `text`, `frames`, `symbolication`, `handling`, `isCrash` e `category`. Cada frame contém `raw` (o que o SDK enviou), `restored` (o resultado obtido com um artefato de depuração ou `null`) e `inApp`. Quando o sistema tenta resolver os frames, `symbolication` assume `completed`, `partial` ou `missing`. |

Se o problema não existir, a API retorna `404`.

`PATCH /api/v1/rum/issues/{id}` aceita `status`, `assigneeId` e `teamId`, em qualquer combinação, e retorna o problema após a alteração.

```json
{ "status": "resolved", "assigneeId": "<user-id>", "teamId": null }
```

`status` aceita `open`, `investigating`, `resolved` ou `ignored`. As regras definem `regressed` quando um problema resolvido volta a ocorrer em
uma versão mais recente. Se a requisição enviar `regressed`, a API retorna `400`. `assigneeId` deve identificar um membro da organização, e `teamId`, uma equipe da mesma organização. Use `null` ou uma
string vazia para remover o responsável ou a equipe. A API mantém os campos omitidos. Ao resolver o problema, a API registra `resolvedAt`, `resolvedBy` e a versão mais recente da
aplicação em `resolvedVersion`. Qualquer mudança de estado encerra o registro anterior de resolução ou regressão. Se a requisição não indicar nenhum campo para alterar, a API retorna `400`. Se enviar apenas valores já definidos, retorna `200` sem alterar nada. A API registra cada alteração no log de auditoria como `rum.issue.update`.

## Pré-visualize uma regra de alerta

```http
POST /api/v1/rum/alerts/preview
```

Usa o código de avaliação para consultar os dados que uma [regra de alerta sobre uma métrica de RUM](/pt-BR/rum/alerts) teria recebido no período recente,
uma janela por vez. Requer `rum.events.read`.

```json
{
  "query": { "applicationId": "checkout-web", "environment": "production", "page": "/checkout", "metric": "lcp_p75" },
  "periodSecs": 3600
}
```

| Campo | Tipo | Comportamento |
|---|---|---|
| `query` | objeto | Obrigatório. Define a métrica com `applicationId` e `metric` e, se informados, `environment`, `page`, `version` e `minSamples`. O endpoint rejeita `page` ou `version` se a métrica não aceitar o filtro correspondente. Também rejeita `minSamples` para contagens. `custom_vital` e `custom_timing` também aceitam `customName` (obrigatório) e `statistic`. `query` exige `search`, que contém `type`, a expressão `statement` tal como foi escrita, os campos `filters` e `freeText` extraídos da expressão e `measure` (`fn` e `field`). Consulte [Crie uma regra](/pt-BR/api/alerting/create-rule#regras-de-rum). |
| `periodSecs` | inteiro | Obrigatório. Duração da janela de avaliação da regra, de 60 a 21.600 segundos. Cada ponto corresponde a uma janela. |
| `from`, `to` | inteiro | Intervalo em microssegundos desde a época Unix. A consulta considera apenas janelas completas. O padrão de `to` é o instante atual. Por padrão, `from` fica seis horas antes de `to`, com ajuste para manter o intervalo entre 12 e 72 janelas e não ultrapassar um dia. O intervalo aceita no máximo 360 janelas. |

```json
{
  "metric": "lcp_p75",
  "unit": "milliseconds",
  "minSamples": 50,
  "periodSecs": 3600,
  "from": 1789956800000000,
  "to": 1790000000000000,
  "points": [
    { "at": 1789956800000000, "value": null, "samples": null },
    { "at": 1789960400000000, "value": 2480, "samples": 612 }
  ],
  "current": { "at": 1789996400000000, "value": 2310, "samples": 540 }
}
```

`unit` pode ser `count`, `percent`, `milliseconds`, `score`, `bytes` ou `none`. Cada ponto contém o início da janela em `at`, o valor da métrica em `value` e
as linhas usadas para calcular a métrica em `samples`. Se a janela tiver menos linhas que `minSamples`, o ponto não inclui `value` nem `samples`. `current` é o último ponto,
correspondente à janela que termina em `to`. Se a contagem exceder o tempo disponível ou se o sistema estiver ocupado, a resposta não inclui pontos e define `unavailable` como
`time_budget` ou `busy`, respectivamente. O endpoint retorna `404` se a aplicação não existir e `400` se a regra for incompatível com a métrica.

## Erros

| Status | Causa |
|---|---|
| `400` | Um parâmetro, filtro, coluna ou cursor é incompatível com a solicitação. |
| `401`, `403` | O token está ausente, é inválido ou não tem a permissão exigida pelo endpoint. |
| `404` | A linha, a sessão ou a aplicação não existe. |
| `409` | Já existe uma aplicação com esse identificador ou nome. |
| `413` | A solicitação excede os limites de [`events`](/pt-BR/rum/events#envie-eventos). |
