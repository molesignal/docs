O grupo **Segurança de dados** de **Configurações** reúne **Chaves de criptografia**, **Padrões de regex**,
**Mascaramento de campos**, **Gerenciamento de domínios** e **Auditoria**. Para consultar os quatro primeiros, use a permissão
`org.field_masking.read`. Para alterá-los, use `org.field_masking.manage`. **Auditoria** exige
`audit.read`. O período de retenção dos registros de auditoria é uma [configuração da plataforma](/pt-BR/settings/platform#retenção-de-registros-de-auditoria).

## Chaves de criptografia

A tela **Chaves de criptografia** lista as chaves de dados do espaço de trabalho, com o algoritmo, a versão e o momento da
última rotação. O MoleSignal cria automaticamente a chave de [campos criptografados](/pt-BR/streams#campos-criptografados)
na primeira vez que um fluxo grava um desses campos. A chave aparece como `__field_default__`. A chave raiz de criptografia `MS_CIPHER_KEY`
protege cada chave, e o material de cada uma nunca sai do servidor.

| Ação | Como fazer |
|---|---|
| **Nova chave** | Insira um **Nome** e 32 bytes de material de chave codificado em base64 (`keyMaterialB64`). |
| **Rotacionar** | Cole um novo material de chave de 32 bytes em base64. A rotação adiciona uma versão: os novos dados usam essa versão, e as anteriores continuam descriptografando os dados que criptografaram. |
| Excluir | Os dados criptografados com a chave ficam ilegíveis. |

<Warning>
  Se a chave `MS_CIPHER_KEY` for perdida, não será possível recuperar nenhum campo criptografado. Consulte
  [Criptografia em nível de campo](/pt-BR/security#criptografia-no-nível-de-campo).
</Warning>

## Padrões de regex

Um padrão de regex localiza e substitui textos confidenciais, como números de cartão ou tokens.

1. Selecione **Novo padrão**.
2. Insira um **Nome**, o **Padrão** e uma **Descrição**. O servidor valida o padrão ao
   salvá-lo.
3. Insira a **Substituição**. Use `$1` e outros grupos de captura. Deixe a substituição vazia para remover
   o trecho correspondente.
4. Use **Ocultar dados na ingestão** para escolher quando aplicar o padrão e selecione **Criar**.

| **Ocultar dados na ingestão** | Efeito |
|---|---|
| Ativado | O MoleSignal oculta dados em todos os valores de texto de cada evento recebido, após o processamento pelos pipelines e antes do armazenamento. Não é possível recuperar o texto original. |
| Desativado | O armazenamento preserva o texto original. Uma consulta SQL que chama `mask(<column>)` retorna a coluna com os padrões aplicados. |

`mask()` aplica todos os padrões do espaço de trabalho. A coluna **Mascaramento** da lista mostra
**Na ingestão** ou **Apenas na consulta** para cada padrão.

## Mascaramento de campos

O mascaramento de campos oculta partes dos valores dos campos nos resultados das consultas, mas os cálculos continuam usando os valores
brutos. O mascaramento não se aplica a fluxos de métricas.

1. Selecione **Nova regra** e insira um **Nome da regra**.
2. **Padrão do campo**: insira o nome exato do campo ou use curingas `*` e `?`, como em `user.*`.
   Não use expressões regulares.
3. Se necessário, restrinja a regra com **Padrão do fluxo**, por exemplo, `customer-*`, e **Tipo de fluxo**.
4. Escolha o **Algoritmo**, mantenha **Ativar regra** habilitado e salve.

| Algoritmo | Efeito |
|---|---|
| **Mascaramento completo** | Substitui o valor inteiro pela **Substituição**. |
| **Mascaramento por intervalo** | Mascara os caracteres de **Caractere inicial** até **Caractere final (exclusivo)**. |
| **Mascaramento interno** | Mantém as quantidades definidas em **Caracteres visíveis do prefixo** e **Caracteres visíveis do sufixo** e mascara o trecho intermediário. |
| **Mascaramento externo** | Mantém apenas os caracteres de **Caractere inicial** até **Caractere final (exclusivo)** e mascara os dois lados. |
| **Hash HMAC-SHA-256** | Substitui o valor por um hash calculado com uma chave do espaço de trabalho que o servidor gerencia. Valores iguais geram o mesmo hash, o que permite agrupar e combinar resultados em junções. |

A primeira regra ativa que corresponde ao campo tem prioridade. Arraste as linhas para mudar a ordem. Nas configurações de campos de
um [fluxo](/pt-BR/streams#esquema-e-campos), é possível substituir a regra herdada ou desativar o mascaramento de um
campo.

## Gerenciamento de domínios

A seção **Gerenciamento de domínios** permite disponibilizar o espaço de trabalho em um nome de host próprio, com um certificado que
o MoleSignal obtém e renova.

1. Ative `[http.tls]` com um `account_email`. Consulte [TLS para HTTP e ACME](/pt-BR/configuration#tls-para-http-e-acme).
2. Aponte o DNS do nome de host para o MoleSignal, para que o serviço ACME acesse
   `/.well-known/acme-challenge/` pela porta HTTP sem TLS.
3. Selecione **Adicionar domínio**, insira o **Nome de host** e selecione **Adicionar domínio**.

A lista mostra o **Estado** de cada nome de host, a data de expiração do certificado e o **Último erro**.
Um novo nome de host fica em `pending` até a emissão do certificado e depois passa para `active`. Os certificados
são renovados automaticamente nos 30 dias que antecedem a expiração. Ao remover um nome de host, o MoleSignal deixa de atender solicitações nesse endereço.

## Auditoria

**Auditoria** permite pesquisar na trilha de auditoria do espaço de trabalho: ações relevantes para a segurança e alterações em
recursos e configurações. Cada evento inclui o responsável, a ação, o alvo, o status e o horário.

| Filtro | Uso |
|---|---|
| **De** / **Até** | O intervalo de tempo, absoluto ou relativo, como `now-24h`. |
| **Tipo de autor** / **Responsável** | Um tipo de autor ou um usuário específico. |
| **Ação** | Uma chave de ação, como `audit_retention.update`. |
| **Tipo de alvo** / **ID do alvo** | O tipo e o ID do recurso alterado. |

Selecione **Aplicar** para pesquisar e **Redefinir** para limpar os filtros. Selecione uma linha para ver o evento completo e
acessar **Copiar ID**. Um evento de conversa do Mole Agent mostra o histórico da conversa. O topo da página informa
por quanto tempo os registros ficam armazenados. **Alterar retenção** abre a configuração da plataforma em `_sys`.

Os registros de auditoria nunca incluem credenciais, chaves de modelos, cabeçalhos sensíveis de webhooks nem material
de assinatura. Consulte [Auditoria](/pt-BR/security#auditoria).

### Fluxo de auditoria

Cada evento de auditoria também gera uma linha no fluxo de logs `_audit` do espaço de trabalho. Assim, é possível
pesquisar o evento em **Logs** e enviá-lo a outro destino, como um SIEM, com um
[pipeline agendado](/pt-BR/pipelines#streams-da-plataforma). A linha passa pela mesma limpeza que o registro
desta página e usa o horário do evento.

| Campo | Conteúdo |
|---|---|
| `audit_id` | O ID do evento, no mesmo formato que **Copiar ID** fornece. |
| `actor_kind`, `actor_id` | Quem executou a ação. |
| `action` | A chave da ação. |
| `target_kind`, `target_id` | O recurso alterado, quando houver. |
| `ip`, `user_agent` | A origem da solicitação, quando o evento registra essa informação. |
| `payload` | Os detalhes do evento, quando houver. |

Esta página e a [API de auditoria](/pt-BR/api/admin/audit) consultam os registros oficiais. Cada nó grava
as linhas em segundo plano, em lotes, e mantém até 4.096 eventos na fila. Quando a fila
enche, o nó não grava a linha no fluxo, mas o registro permanece. As linhas seguem a política de retenção do
fluxo, como em qualquer outro fluxo.

A leitura de `_audit` exige `audit.read`, assim como o acesso a esta página:

- Sem essa permissão, o fluxo não aparece na lista de fluxos, não é possível abri-lo, alterá-lo nem excluí-lo, e
  qualquer consulta ao fluxo retorna `403`. Isso vale para consultas no produto, para a API de consultas com transmissão em NDJSON,
  para Flight SQL e para a pesquisa federada. Na pesquisa federada, o cluster remoto verifica a permissão `audit.read` no
  token de quem faz a consulta.
- Toda consulta a `_audit` é executada na própria solicitação, sem gerar uma tarefa de pesquisa, mesmo com
  `Prefer: respond-async`. O envio de uma tarefa de pesquisa para esse fluxo retorna `400`.
- Processos em segundo plano sem um usuário associado não podem ler o fluxo, independentemente de quem os salvou. Não é possível salvar uma regra de alerta que
  leia `_audit`, seja como fluxo da regra ou em qualquer parte da instrução, nem uma inspeção agendada dos logs desse fluxo:
  a chamada retorna `400`, mesmo para o proprietário. Relatórios também não podem ler o fluxo.
- As ferramentas do Mole Agent e o [MCP de entrada](/pt-BR/inbound-mcp) não podem ler as linhas nem
  os campos do fluxo com nenhuma credencial.

Um [pipeline agendado](/pt-BR/pipelines#streams-da-plataforma) lê `_audit` com as permissões de um único usuário:
quem salvou o pipeline por último. Pausar e retomar não contam como salvamento. O topo da página do pipeline
identifica esse usuário em **Lê \_audit como**, assim como a origem no editor. Para outro usuário
que tenha `audit.read` e possa salvar o pipeline, o editor exibe: **Depois que você salvar, o pipeline fará a leitura com as suas permissões.**

- Para salvar uma alteração, é preciso ter `audit.read`. Uma solicitação com token de conta de serviço retorna `403`, pois
  não é possível verificar novamente as permissões da conta durante a execução do pipeline. Um token pessoal representa o usuário que o
  recebeu.
- Antes de cada leitura, o pipeline verifica se o usuário ainda pode entrar, se ainda faz parte da organização e se
  ainda tem `audit.read`. Caso contrário, a leitura falha e a execução informa quem é o usuário e o motivo, por exemplo:
  `` `_audit` is read with the access of admin@example.com, who no longer holds audit.read ``. O
  pipeline continua ativo e mantém a posição de leitura para não pular nenhum evento.
- O pipeline retoma a leitura dessa posição quando o usuário recupera `audit.read` ou quando outro usuário com
  essa permissão salva o pipeline, mesmo sem alterar nada. Salvar sem alterações e sem `audit.read`, ou
  com um token de conta de serviço, não muda nada nem retorna erro.
- Para pausar ou retomar, basta ter `pipelines.pause`. Essas ações não mudam as permissões que o pipeline usa
  para ler. Ao retomar, o pipeline [reinicia a leitura](/pt-BR/pipelines#agendamento-e-posições-de-leitura), como qualquer outro pipeline. Por isso, deixe
  o pipeline ativo para manter a posição de leitura.
- Um preenchimento retroativo usa as permissões de quem o envia. O usuário precisa ter `audit.read` no momento
  do envio, e a tarefa verifica a permissão novamente durante a execução.

As linhas que um pipeline copia tornam-se linhas comuns dos destinos. Qualquer usuário com acesso de leitura a esses destinos pode
consultá-las.
