Uma função é um conjunto de permissões com nome. Uma política de permissão também é um conjunto desse tipo, mantido separadamente para que várias
funções possam usá-la e tokens de API possam segui-la. Atribua a um membro uma função para todo o espaço de trabalho
em [Usuários](/pt-BR/identity/members#usuários). Uma concessão de acesso atribui a um usuário ou a uma equipe uma função para
toda a organização ou para recursos selecionados, com data de expiração opcional. Abra **Identidade e acesso →
Funções**, **Políticas de permissão** ou **Concessões de acesso**.

## Funções

**Funções** lista as funções integradas e personalizadas do espaço de trabalho, com as políticas associadas a cada função,
as permissões concedidas e onde a função é usada: membros, contas de serviço, convites e
vínculos. As funções integradas são somente leitura. Consulte [Funções integradas](/pt-BR/identity#funções-integradas).

Para criar uma função personalizada:

1. Selecione **Nova função**.
2. Digite uma **Chave** com letras minúsculas, dígitos e underscores. Não é possível alterá-la depois.
3. Digite um **Nome** e uma **Descrição**.
4. Em **Políticas de permissão**, marque as políticas que deseja associar à função. A função inclui todas as
   permissões dessas políticas e acompanha as alterações nelas.
5. Em **Permissões próprias**, marque as permissões de que a função precisa além das incluídas nas políticas. Cada
   permissão indica o que permite. As permissões concedidas por uma política marcada já aparecem selecionadas, com a
   política de origem, e não podem ser desmarcadas nessa seção.
6. Selecione **Criar função**.

Uma função concede as permissões próprias e as das políticas associadas. Selecione uma função personalizada para alterar as permissões ou as políticas.
Use **Excluir** para remover uma função personalizada somente se nenhum vínculo de membro, conta de serviço,
convite ou vínculo de função a usar. Para consultar funções, é preciso ter `iam.roles.read`; para alterá-las,
`iam.roles.manage`; e para excluí-las, `iam.roles.delete`.

## Políticas de permissão

**Políticas de permissão** lista as políticas integradas e personalizadas do espaço de trabalho, com
as permissões de cada política e as funções e os tokens que a usam. Uma função pode ter várias políticas associadas, e um token
de API pode seguir uma política: consulte [O que um token pode fazer](/pt-BR/identity/tokens#o-que-um-token-pode-fazer).

| Política integrada | Permissões |
|---|---|
| **Observador com acesso somente leitura** | Consulta dados de observabilidade, dashboards, alertas, escalas, visualizações salvas, pipelines, funções, relatórios, páginas de status, monitoramento sintético, níveis de serviço e análises pós-incidente. |
| **Analista de dados** | Explora dados de observabilidade e cria dashboards e visualizações salvas. |
| **Desenvolvedor de pipelines** | Consulta dados de observabilidade e gerencia fluxos, pipelines e funções. |
| **Administrador de alertas** | Consulta dados de observabilidade e gerencia regras de alerta, escalas, páginas de status, monitoramento sintético e análises pós-incidente. |
| **Administrador da organização** | Gerencia configurações da organização, membros, funções, concessões de acesso, tokens de API, contas de serviço e auditoria, além de páginas de status, monitoramento sintético, níveis de serviço e análises pós-incidente. |
| **Ingestão de dados** | Grava dados e registra implantações: `logs.write`, `metrics.write`, `traces.write`, `profiles.write` e `apm.deploy`. Os tokens de ingestão seguem essa política. |

As políticas integradas são somente leitura e acompanham as atualizações do produto. Abra uma delas e selecione **Copiar como
política personalizada** para usá-la como base para uma nova política.

Para criar uma política personalizada:

1. Selecione **Nova política**.
2. Digite um **Nome**, uma **Chave** com letras minúsculas, dígitos e underscores que não pode ser alterada
   depois, e uma **Descrição**.
3. Em **Permissões**, marque as permissões em **Visual** ou escreva o documento em **JSON**.
   Os dois modos editam o mesmo documento. O modo **JSON** indica o primeiro erro e sua localização. Se o documento for válido, lista
   as permissões que ele concede antes de salvar.
4. Selecione **Criar política**.

O documento de política segue a linguagem de políticas do AWS IAM:

```json
{
  "Version": "1",
  "Statement": [
    { "Sid": "Dashboards", "Effect": "Allow", "Action": "dashboards.*" },
    { "Effect": "Allow", "Action": ["streams.read", "streams.query"] }
  ]
}
```

- `Version` é `"1"`, e a política deve conceder pelo menos uma permissão.
- `Effect` é sempre `"Allow"`: a política só concede permissões, sem opção de negá-las.
- `Action` é uma permissão ou uma lista de permissões. `*` corresponde a qualquer sequência de caracteres. Assim,
  `dashboards.*` abrange todas as permissões de dashboard, e `*`, todas as permissões da organização. O sistema rejeita ações
  que não correspondem a nenhuma permissão.
- `Sid` é um nome opcional para a instrução.
- O sistema rejeita `Resource`, `Condition`, `Principal` e `NotAction`: a política se aplica a toda a
  organização. Para atribuir uma função a recursos específicos ou impor condições, use uma
  [concessão de acesso](#concessões-de-acesso).

A política registra as permissões que o documento concede no momento em que é salvo. Um padrão também abrange permissões
adicionadas ao catálogo depois: o MoleSignal as inclui na política ao iniciar. Ao marcar uma permissão em **Visual**,
o editor avisa antes de converter um documento com padrões, um `Sid` ou várias instruções em uma única instrução que lista cada
permissão.

Alterar uma política atualiza imediatamente todas as funções associadas e todos os tokens que a seguem.
Use **Excluir** para remover uma política personalizada somente se nenhuma função estiver associada a ela e nenhum token válido a seguir. Um
token revogado ou expirado que seguia a política mantém a lista de permissões que tinha. Para consultar políticas,
é preciso ter `iam.policies.read`; para alterá-las, `iam.policies.manage`; e para excluí-las, `iam.policies.delete`.

## Concessões de acesso

Uma concessão de acesso vincula uma função a uma identidade em uma organização, dentro de um escopo de
recursos. Use uma concessão para dar acesso a uma pessoa, equipe ou recurso específico, sem ampliar as permissões de uma
função de uso geral.

1. Abra **Concessões de acesso** e selecione **Nova concessão de acesso**.
2. **Identidade**: escolha **Usuário** ou **Equipe** e selecione a identidade correspondente.
3. **Organização**: o espaço de trabalho atual aparece como referência.
4. **Escopo de recursos**: escolha **Toda a organização** ou um tipo de recurso (**Dashboard** ou **Fluxo**) e selecione
   um recurso ou **Todos os recursos deste tipo**.
5. **Função e permissões**: selecione a função que a concessão atribui.
6. **Restrições**: se necessário, defina um **Ambiente**, como `prod`, ao qual as solicitações devem corresponder exatamente,
   e indique quando a concessão expira em **Expira em**.
7. Selecione **Criar concessão de acesso**.

Use **Excluir** para encerrar uma concessão imediatamente. Para consultar concessões, é preciso ter `iam.grants.read`. Para criar ou
excluir concessões, é preciso ter `iam.grants.manage`.

## Compartilhar recursos entre organizações

Um compartilhamento entre organizações permite que outra organização acesse recursos selecionados da organização atual. O compartilhamento
é explícito e não transitivo: só vale para a organização e os recursos selecionados e
não pode ser herdado nem repassado.

1. Em **Concessões de acesso**, selecione **Compartilhar entre organizações**.
2. Escolha a **Organização de destino**.
3. Escolha o tipo de recurso e o recurso: um **Dashboard** ou um **Fluxo**.
4. Escolha as permissões: `dashboards.read` e `dashboards.edit` para um dashboard, `streams.read`
   e `streams.query` para um fluxo.
5. Se necessário, preencha **Expira em** e selecione **Criar compartilhamento**.

O compartilhamento começa como **Aguardando aceitação**. Na organização de destino, um administrador seleciona
**Aceitar** em **Concessões de acesso**, e o compartilhamento passa para **Ativo**. Qualquer uma das organizações pode selecionar **Revogar**
para encerrá-lo. Para criar, aceitar ou revogar compartilhamentos, é preciso ter `iam.cross_org.manage`.

e as políticas podem combinar quaisquer permissões da organização. As abas de um módulo listam as páginas que uma função pode abrir.
O módulo abre na primeira delas, então basta ter permissão para acessar uma das páginas.

O corpo da requisição de uma função contém as próprias `permissions` e os `policyIds` das políticas vinculadas. A resposta inclui
`effectivePermissions`, com todas as permissões que a função concede. O corpo da requisição de uma política contém `key` (apenas na criação),
`name`, `description` e `document`. A resposta inclui `builtin`, as `permissions` resultantes e
`usage`, que indica as funções vinculadas à política e os tokens ativos que a seguem. Se o documento for
inválido, a API retorna `400` e indica onde está o problema, como em
``Statement[0].Action[1]: no permission is called `alerts.rules.reed` ``. Ao tentar excluir uma política ainda em uso, a API retorna
`409`.
