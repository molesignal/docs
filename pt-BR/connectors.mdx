Um **conector** é uma integração gerenciada com uma plataforma externa. Os conectores funcionam em duas direções:

- **Origens** trazem dados de outro serviço e os gravam em um stream. O MoleSignal coleta CloudWatch Logs, tópicos do Kafka e objetos do S3 periodicamente. Amazon Data Firehose, Google Cloud Pub/Sub, Cloudflare Logpush e Heroku enviam para o MoleSignal; o Firehose também carrega métricas do CloudWatch.
- **Destinos** recebem a saída de um [pipeline agendado](/pt-BR/pipelines#destinos-e-saída-por-conectores): Amazon S3 e armazenamento compatível com S3, Apache Kafka e qualquer endpoint HTTP.

| Tipo | Conector | Direção | Autenticação |
|---|---|---|---|
| `aws_cloudwatch_logs` | AWS CloudWatch Logs | Origem, coletada a cada 30 segundos | [Credenciais da AWS](#autenticação-na-aws) |
| `kafka_source` | Tópico do Kafka | Origem, coletada a cada 30 segundos | Nenhuma, SASL ou certificado de cliente |
| `s3_source` | Objetos do S3 | Origem, coletada a cada 30 segundos | Credenciais da AWS |
| `gcp_pubsub_pull` | Assinatura do Google Cloud Pub/Sub | Origem, coletada a cada 30 segundos | Chave de conta de serviço |
| `aws_cloudwatch_metrics`, `azure_monitor_metrics`, `gcp_monitoring_metrics`, `aliyun_cms_metrics`, `tencent_monitor_metrics`, `huawei_ces_metrics` | [Métricas de nuvem](#métricas-de-nuvem) | Origem, coletada a cada período | As credenciais da nuvem |
| `aws_kinesis_firehose` | Amazon Data Firehose | Origem, por push | [Token de push](#fontes-de-push) |
| `gcp_pubsub_push` | Push do Google Cloud Pub/Sub | Origem, por push | Token de push, opcionalmente com o token OIDC da assinatura |
| `cloud_events` | Barramento de eventos de nuvem | Origem, por push | Token de push |
| `cloudflare_logpush` | Cloudflare Logpush | Origem, por push | Token de push |
| `heroku_drain` | Log drain do Heroku | Origem, por push | Token de push |
| `s3` | Amazon S3 | Destino | Credenciais da AWS |
| `kafka` | Apache Kafka | Destino | Nenhuma, SASL ou certificado de cliente |
| `http` | HTTP / Webhook | Destino | Nenhuma, token bearer, autenticação Basic, cabeçalho personalizado ou assinatura HMAC |

## Criar um conector

<Steps>
  <Step title="Abrir os conectores">
    Acesse **Pipelines → Conectores**. A página lista **Origens** e **Destinos**.
  </Step>
  <Step title="Escolher o tipo">
    Clique em **Novo conector** e escolha o que conectar.
  </Step>
  <Step title="Preencher as configurações">
    Informe um **Nome** exclusivo na organização, preencha de onde o conector lê ou para onde entrega e escolha a **Autenticação**.
  </Step>
  <Step title="Testar e criar">
    Clique em **Testar conexão** para experimentar as configurações antes de salvá-las e depois clique em **Criar conector**. Uma origem por push não tem a que se conectar e não oferece teste.
  </Step>
</Steps>

Pela API, um conector é um `name`, um `kind` e um `configJson` cujas chaves dependem do tipo. `auth` em `configJson` indica a forma de autenticação, e cada forma usa suas próprias chaves. Configurações que não podem funcionar respondem `400` ao serem salvas: uma chave obrigatória ausente, metade de um par de credenciais ou uma chave que o `auth` escolhido não usa.

```bash
curl -X POST http://localhost:5080/api/v1/connectors \
  -H "authorization: Bearer $MS_TOKEN" \
  -H 'content-type: application/json' \
  -d '{
        "name": "archive",
        "kind": "s3",
        "configJson": {
          "bucket": "acme-logs",
          "region": "eu-west-1",
          "prefix": "pipelines/checkout/",
          "auth": "assume_role",
          "roleArn": "arn:aws:iam::123456789012:role/molesignal-delivery"
        }
      }'
```

## Segredos

Estas chaves de `configJson` guardam segredos:

| Tipo | Chaves secretas |
|---|---|
| `s3`, `aws_cloudwatch_logs` | `accessKey`, `secretKey`, `sessionToken` |
| `aws_kinesis_firehose`, `gcp_pubsub_push`, `cloud_events`, `cloudflare_logpush`, `heroku_drain` | `pushToken` |
| `aws_cloudwatch_metrics` | `accessKey`, `secretKey`, `sessionToken` |
| `azure_monitor_metrics` | `clientSecret` |
| `gcp_monitoring_metrics`, `gcp_pubsub_pull` | `serviceAccountKey` |
| `aliyun_cms_metrics`, `tencent_monitor_metrics`, `huawei_ces_metrics` | `accessKey`, `secretKey` |
| `kafka` | `saslPassword`, `tlsClientKey` |
| `http` | `url`, `bearerToken`, `basicPassword`, `headerValue`, `hmacSecret` |

Um segredo nunca sai pela API. A resposta mostra `***` em seu lugar e nomeia em `secretKeys` os segredos que têm valor:

```json
{
  "kind": "kafka",
  "configJson": {
    "brokers": "b-1.example.com:9096",
    "topic": "logs",
    "tls": true,
    "auth": "sasl_scram_sha_512",
    "saslUsername": "molesignal",
    "saslPassword": "***"
  },
  "secretKeys": ["saslPassword"]
}
```

- Uma atualização que envia `***` de volta mantém o valor armazenado, então um conector pode ser renomeado, desativado ou apontado para outro lugar sem informar as credenciais novamente. Na interface, um segredo salvo deixado em branco mantém seu valor.
- Um segredo omitido em uma atualização é removido.
- Uma atualização que altera o `kind` não mantém nenhum dos segredos armazenados.

O MoleSignal sela os segredos com a chave raiz de `MS_CIPHER_KEY` (AES-256-GCM) separadamente das outras configurações e não armazena nenhum segredo em texto simples. Uma origem por push é localizada pelo SHA-256 do seu token. `molesignal rewrap-kek` ressela os segredos dos conectores junto com os outros segredos quando a chave raiz é rotacionada. Consulte o [Checklist de produção](/pt-BR/deployment/production-checklist).

## Fontes

### Fontes de push

As cinco fontes de push compartilham um modelo: crie um conector com um **`pushToken`** e um **`targetStream`**, depois aponte a plataforma para o endpoint correspondente. Esses endpoints não usam o JWT. A requisição se autentica com o token de push, fornecido da forma que a plataforma permitir:

| Método | Usado por |
|---|---|
| Cabeçalho `X-Connector-Token` | Plataformas com cabeçalhos configuráveis, como Cloudflare |
| Cabeçalho `X-Amz-Firehose-Access-Key` | Amazon Data Firehose, que o envia automaticamente |
| Cabeçalho `X-EventBridge-Signature-Token` | Alibaba Cloud EventBridge |
| Parâmetro de consulta `?token=` | Plataformas que não conseguem definir cabeçalhos, como Heroku e Pub/Sub |
| Senha de `Authorization: Basic` | Plataformas que colocam credenciais no endereço |

A UI gera o token quando cria o conector e o mostra uma vez, junto com o endpoint a ser fornecido à plataforma. O token não pode ser lido novamente. **Gerar novo token** o substitui quando o conector é salvo. Pela API, forneça um `pushToken` de pelo menos 16 caracteres. Um token abre um conector de um tipo: um token já em uso responde `409`. Uma requisição com um token ausente ou desconhecido, ou para um conector desativado, responde `401`. Um conector sem token não aceita nada. Um nó mantém um conector que ele consultou por 30 segundos, então desativar um conector ou substituir seu token tem efeito dentro desse tempo.

Corpos enviados com `Content-Encoding: gzip` são descompactados automaticamente. Um corpo do Firehose pode ter até 64 MiB, qualquer outro até 16 MiB, contados também após a descompactação. Os eventos fluem pelo mesmo caminho de ingestão que todo o resto: schema-on-write, [pipelines](/pt-BR/pipelines) e [mascaramento](/pt-BR/security) se aplicam.

<Tabs>
  <Tab title="Amazon Data Firehose">
    Crie o conector com `kind: "aws_kinesis_firehose"`, depois escolha o destino **Endpoint HTTP** para o stream do Firehose:

    - **URL do endpoint HTTP**: `https://molesignal.example.com/api/v1/_kinesis_firehose`
    - **Chave de acesso**: o token de push. O Firehose o envia como `X-Amz-Firehose-Access-Key`.

    O Firehose entrega apenas para HTTPS na porta 443 com um certificado confiável publicamente, então uma implantação em uma rede privada precisa de um ponto de entrada público, veja [Acesso público](/pt-BR/public-access). Mantenha o buffer do stream entre 1 e 4 MiB.

    O MoleSignal lê cada registro individualmente, pelo que ele contém:

    | Registro | Torna-se |
    |---|---|
    | Uma mensagem de assinatura do CloudWatch Logs, compactada com gzip como o filtro de assinatura envia | Um evento de log por entrada de `logEvents`, no horário da própria entrada, com `message`, `log_group`, `log_stream`, `account_id`, `region`, `event_id` e `source: "cloudwatch"`. A verificação de saúde que a assinatura envia quando é criada é ignorada. |
    | Um registro do CloudWatch Metric Streams no formato de saída JSON, OpenTelemetry 1.0 ou OpenTelemetry 0.7 | Amostras de métrica no stream de métricas, veja abaixo. |
    | Qualquer outro texto | Um evento de log por linha: um objeto JSON fornece os campos, texto simples vai para `message`. |

    Um stream de métricas envia um agregado por métrica por minuto. Cada estatística se torna uma amostra de gauge chamada `aws_<namespace>_<metric>_<statistic>`, da forma como o yet-another-cloudwatch-exporter as nomeia: `aws_ec2_cpuutilization_average`, `aws_ec2_cpuutilization_maximum`, `aws_applicationelb_request_count_sum`. O namespace perde seu prefixo `AWS/`, e o nome da métrica se divide em palavras onde uma letra minúscula encontra uma maiúscula. As estatísticas são `average` (a soma sobre a contagem de amostras), `sum`, `sample_count`, `minimum`, `maximum`, e qualquer percentil que o stream adicione, como `p99` ou `p99_9`. Os rótulos são `account_id`, `region`, e um `dimension_<Name>` por dimensão, como `dimension_InstanceId`; `metric_unit` mantém a unidade.

    ```promql
    max by (dimension_InstanceId) (aws_ec2_cpuutilization_average)
    ```

    `X-Amz-Firehose-Common-Attributes`, definido como os parâmetros do stream, adiciona suas chaves a cada evento e amostra; um campo que o registro já possui prevalece. `X-Amz-Firehose-Source-Arn` fornece a `region` dos eventos do CloudWatch Logs, que não a carregam.

    A resposta segue a especificação de entrega do Firehose: `application/json` com o `requestId` da requisição, um `timestamp` e um `errorMessage` em caso de falha. Registros que não podem ser lidos são omitidos, e o restante da requisição ainda é gravado com `200`. Uma gravação que falha temporariamente responde `429` ou `5xx`, que o Firehose tenta novamente. Um corpo acima de 64 MiB responde `413`, que o Firehose não tenta novamente nem faz backup. Uma entrega repetida dentro de 30 minutos após ser gravada, com o mesmo `X-Amz-Firehose-Request-Id`, é respondida com `200` sem ser gravada novamente.
  </Tab>
  <Tab title="Google Cloud Pub/Sub">
    Crie o conector com `kind: "gcp_pubsub_push"`. Roteie logs para um tópico do Pub/Sub com um sink do Log Router, depois crie uma assinatura push no tópico. O Pub/Sub não consegue definir cabeçalhos personalizados, então o token viaja na URL:

    ```bash
    gcloud pubsub subscriptions create molesignal-push --topic=molesignal-logs --push-endpoint="https://molesignal.example.com/api/v1/_gcp_pubsub?token=<pushToken>"
    ```

    Para também verificar o token OIDC da assinatura, defina `oidcServiceAccount` no conector com o e-mail de uma conta de serviço e crie a assinatura com `--push-auth-service-account=<email>`. O MoleSignal então verifica o token com as chaves do Google e aceita apenas essa conta de serviço. Defina `oidcAudience` para verificar também o público, e passe o mesmo valor como `--push-auth-token-audience`.

    Cada mensagem é uma requisição. Tanto o corpo encapsulado quanto um payload não encapsulado são aceitos. Um `LogEntry` do Cloud Logging se torna um evento de log:

    | `LogEntry` | Evento |
    |---|---|
    | `jsonPayload` | Seus campos |
    | `textPayload` | `message` |
    | `protoPayload` (logs de auditoria) | `proto_payload`, com `method_name`, `service_name` e `principal_email` extraídos dele |
    | `severity` | `level`, em minúsculas |
    | `logName`, `resource.type`, `insertId` | `log_name`, `resource_type`, `insert_id` |
    | `resource.labels`, `labels` | Campos sob seus próprios nomes |
    | `trace`, `spanId` | `trace_id` sem o prefixo `projects/<id>/traces/`, `span_id` |
    | `httpRequest` | `http_request` |
    | `timestamp` | O horário do evento; `receiveTimestamp` ou o horário de publicação quando estiver ausente |

    Qualquer outro dado de mensagem se torna um evento, os campos de um objeto JSON ou o texto como `message`. O endpoint responde `204 No Content`, que o Pub/Sub conta como confirmação. Uma mensagem que não pode ser lida é confirmada e omitida; uma gravação que falha temporariamente não é, então o Pub/Sub a entrega novamente. Uma mensagem entregue novamente dentro de 30 minutos após ser gravada é confirmada sem ser gravada novamente.
  </Tab>
  <Tab title="Barramento de eventos da nuvem">
    Crie o conector com `kind: "cloud_events"`, depois aponte o barramento de eventos para `https://molesignal.example.com/api/v1/_cloud_events`:

    | Remetente | Configuração |
    |---|---|
    | Amazon EventBridge | Um destino de API com uma conexão **Chave de API**; o nome do cabeçalho é `X-Connector-Token` e seu valor é o token de push. |
    | Azure Event Grid | Uma assinatura de webhook cujo endpoint termina com `?token=<pushToken>`. O handshake de validação, e o handshake `OPTIONS` do esquema CloudEvents, são respondidos automaticamente. |
    | Alibaba Cloud EventBridge | Um destino HTTPS com o token de push como seu token, enviado como `X-EventBridge-Signature-Token`. |
    | Huawei Cloud EventGrid | Um destino de webhook com o cabeçalho `X-Connector-Token`. |
    | Outros remetentes CloudEvents | Qualquer um dos métodos de token acima. Um remetente que só consegue colocar credenciais no endereço, como `https://user:<pushToken>@host/...`, também é aceito. |

    Um corpo contém um evento ou um array deles, como CloudEvents 1.0 em modo estruturado ou binário, eventos do Amazon EventBridge, ou o esquema do Event Grid. Cada evento se torna um evento de log em `targetStream` (padrão `cloud_events`):

    | Campo | De |
    |---|---|
    | `event_id`, `event_source`, `event_type`, `event_subject` | CloudEvents `id`, `source`, `type`, `subject`; EventBridge `id`, `source`, `detail-type`; Event Grid `id`, `topic`, `eventType`, `subject` |
    | `account_id`, `region` | EventBridge `account`, `region`; Alibaba Cloud `aliyunaccountid`, `aliyunregionid`; a assinatura de um tópico do Event Grid |
    | `resources` | EventBridge `resources` |
    | `data` | O payload como um campo JSON; um payload de texto vai para `message` |
    | `event_format` | `cloudevents`, `eventbridge` ou `event_grid` |

    Atributos de extensão mantêm seus nomes. O horário do próprio evento é seu horário. Qualquer outro objeto JSON se torna um evento com seus campos como estão. Um evento entregue novamente dentro de 30 minutos, com a mesma origem e id, não é gravado duas vezes. O endpoint responde `200`, ou `400` para um corpo que não é JSON.
  </Tab>
  <Tab title="Cloudflare Logpush">
    Crie o conector com `kind: "cloudflare_logpush"`, depois crie um job do Logpush com um destino HTTP. A Cloudflare transforma um parâmetro de consulta `header_` em um cabeçalho de requisição, então o token viaja em `X-Connector-Token`:

    ```text
    https://molesignal.example.com/api/v1/_cloudflare?header_X-Connector-Token=<pushToken>
    ```

    A Cloudflare envia NDJSON compactado com gzip, e cada linha se torna um evento. O endpoint responde `204 No Content`.
  </Tab>
  <Tab title="Heroku">
    Crie o conector com `kind: "heroku_drain"`, depois adicione o drain. O Heroku não consegue definir cabeçalhos personalizados, então o token viaja na URL:

    ```bash
    heroku drains:add "https://molesignal.example.com/api/v1/_heroku?token=<pushToken>"
    ```

    Cada linha de log se torna um evento com `message` e `source: "heroku"`. O endpoint responde `204 No Content`.
  </Tab>
</Tabs>

<Tip>
  O `targetStream` é criado na primeira entrega, e o esquema evolui conforme novos campos aparecem, da mesma forma que qualquer outro stream. Omita `targetStream` para usar um padrão por fonte: `kinesis`, `gcp`, `cloud_events`, `cloudflare` ou `heroku`. Um conector do Firehose grava amostras de métrica em `metricsStream`, `cloudwatch` por padrão.
</Tip>

### CloudWatch Logs

O CloudWatch Logs é uma fonte **pull**: o MoleSignal chama `FilterLogEvents` a cada 30 segundos em vez de receber um push. A primeira execução lê os últimos 5 minutos. Cada execução posterior começa onde a última execução bem-sucedida terminou, então eventos que não puderam ser lidos ou gravados são lidos novamente na execução seguinte.

```bash
curl -X POST http://localhost:5080/api/v1/connectors \
  -H "authorization: Bearer $MS_TOKEN" \
  -H 'content-type: application/json' \
  -d '{
        "name": "cw-prod",
        "kind": "aws_cloudwatch_logs",
        "configJson": {
          "region": "ap-southeast-1",
          "logGroup": "/aws/lambda/checkout",
          "auth": "node_role",
          "targetStream": "cloudwatch"
        }
      }'
```

| Campo | Observações |
|---|---|
| `region` / `logGroup` | Obrigatório. A região e o grupo de logs do CloudWatch a serem lidos. |
| `auth` e suas chaves | As credenciais, que precisam de `logs:FilterLogEvents` no grupo de logs. Veja [Autenticação na AWS](#autenticação-na-aws). |
| `targetStream` | Stream de destino. Padrão `default`. |

Um nó consulta um conector por vez. Os nós `alert` dividem os conectores entre si, e um nó reivindica um conector antes de consultá-lo. Veja [Divisão de trabalho entre nós de alerta](/pt-BR/deployment/role-based#divisão-do-trabalho-entre-nós-de-alertas). Cada evento se torna um log com `message`, `log_stream` e `log_group`. Um conector desativado não é consultado.

### Tópicos Kafka

Um conector `kafka_source` lê um tópico a cada 30 segundos e continua de onde a última leitura gravada parou. Ele assume as partições por atribuição, não como membro de um grupo de consumidores, e mantém seus offsets no MoleSignal, então precisa apenas da permissão para ler o tópico, e nenhum grupo de consumidores aparece no cluster.

```bash
curl -X POST http://localhost:5080/api/v1/connectors \
  -H "authorization: Bearer $MS_TOKEN" \
  -H 'content-type: application/json' \
  -d '{
        "name": "orders",
        "kind": "kafka_source",
        "configJson": {
          "brokers": "b-1.example.com:9096,b-2.example.com:9096",
          "topic": "orders",
          "tls": true,
          "auth": "sasl_scram_sha_512",
          "saslUsername": "molesignal",
          "saslPassword": "<password>",
          "targetStream": "orders",
          "startFrom": "latest"
        }
      }'
```

| Campo | Observações |
|---|---|
| `brokers`, `topic`, `tls`, `tlsCaCert`, `auth` e suas chaves | Como para um [destino Kafka](#apache-kafka). |
| `targetStream` | Stream de destino. Padrão `default`. |
| `messageFormat` | `json`, o padrão, ou `azure_records` para o que o Azure Monitor exporta para um event hub, veja abaixo. UI: **Formato da mensagem**. |
| `startFrom` | Onde a primeira leitura começa: `latest`, o padrão, para o que chega a partir de agora, ou `earliest` para tudo o que os brokers mantêm. Uma partição adicionada depois é lida desde o início. UI: **Começar a partir de**. |

- Uma mensagem cujo valor é um objeto JSON fornece os campos do log. Qualquer outro valor se torna seu `message`. Cada log também tem `kafka_topic`, `kafka_partition`, `kafka_offset`, `kafka_key` quando a mensagem tem uma chave, e `source`. Seu horário é o timestamp da mensagem.
- Uma leitura leva até 10.000 mensagens ou 32 MiB, e a próxima segue imediatamente enquanto houver mais, por até 2 minutos em um pull.
- Os offsets só avançam quando os logs são gravados. Uma leitura ou gravação que falha é tentada novamente do mesmo lugar 30 segundos depois, então uma mensagem pode ser gravada duas vezes, mas não perdida. Offsets que os brokers expiraram continuam a partir da mensagem mais antiga que ainda mantêm.
- Alterar o `topic` recomeça a partir de `startFrom`, já que os offsets pertencem ao tópico.

As configurações de diagnóstico do Azure, a exportação de dados do Log Analytics e as regras de coleta de dados exportam para o Azure Event Hubs, que uma fonte Kafka lê através do endpoint Kafka do hub: `brokers` `<namespace>.servicebus.windows.net:9093`, `topic` o event hub, `tls` ativado, `auth: sasl_plain` com o nome de usuário `$ConnectionString` e a cadeia de conexão como senha. O nível Basic não tem endpoint Kafka. Com `messageFormat: azure_records`, cada mensagem `{"records": [...]}` é desempacotada: um registro de log se torna um evento de log em seu `time`, e um registro de métrica se torna uma amostra por estatística no `metricsStream` do conector (padrão `default`), nomeada como as [métricas do Azure Monitor](#métricas-de-nuvem) são.

### Objetos S3

Um conector `s3_source` lista um bucket a cada 30 segundos e lê os objetos que ainda não leu, do mais antigo para o mais novo, do AWS S3 ou de um armazenamento compatível com S3.

```bash
curl -X POST http://localhost:5080/api/v1/connectors \
  -H "authorization: Bearer $MS_TOKEN" \
  -H 'content-type: application/json' \
  -d '{
        "name": "elb-logs",
        "kind": "s3_source",
        "configJson": {
          "bucket": "acme-logs",
          "region": "us-east-1",
          "prefix": "AWSLogs/123456789012/",
          "auth": "node_role",
          "targetStream": "elb",
          "startFrom": "latest"
        }
      }'
```

| Campo | Observações |
|---|---|
| `bucket`, `region`, `endpoint`, `virtualHostedStyle`, `auth` e suas chaves | Como para um [destino S3](#amazon-s3). As credenciais precisam de `s3:ListBucket` no bucket e `s3:GetObject` nos objetos. |
| `prefix` | Apenas objetos sob este prefixo são lidos. Cada pull o lista por inteiro, então dê a uma fonte um prefixo próprio. |
| `targetStream` | Stream de destino. Padrão `default`. |
| `startFrom` | Onde a primeira leitura começa: `latest`, o padrão, para objetos que aparecem a partir de agora e nos 5 minutos anteriores, ou `earliest` para tudo sob o prefixo. UI: **Começar a partir de**. |

- Um objeto é lido como linhas. Uma linha que é um objeto JSON fornece os campos de um log, uma que contém apenas `Records`, como o CloudTrail grava, fornece um log por registro, e qualquer outra linha se torna um `message`. Objetos `.gz` e `.zst` são descompactados por seus nomes. Cada log também tem `s3_bucket`, `s3_key` e `source`. Seu horário é quando o objeto foi modificado pela última vez.
- Um pull lê até 100 objetos ou até 50.000 logs, e o próximo segue imediatamente enquanto houver mais, por até 2 minutos.
- O estado de leitura só avança quando os logs são gravados. Um objeto que não pode ser buscado interrompe o pull ali e é tentado novamente 30 segundos depois, então um log pode ser gravado duas vezes, mas não perdido.
- Um objeto que não pode ser lido é ignorado e informado no conector, já que tentá-lo novamente atrasaria tudo depois dele. Trata-se de um objeto corrompido, com mais de 256 MiB, com mais de 512 MiB após a descompactação, com mais de um milhão de logs, ou com uma linha acima de 64 MiB.
- Um objeto é reconhecido por sua chave e seu horário de modificação, com uma margem de 5 minutos. Um objeto que é gravado novamente sob a mesma chave dentro dessa margem não é lido novamente, e um cujo horário de modificação seja mais de 5 minutos mais antigo que o objeto mais novo lido não é lido de forma alguma. O S3 data um upload multipart a partir de quando ele começou, então um upload mais lento que isso não é lido.

### Assinaturas do Google Cloud Pub/Sub

Um conector `gcp_pubsub_pull` lê uma assinatura do Pub/Sub a cada 30 segundos, até 1.000 mensagens por requisição, e continua imediatamente enquanto houver mais, e confirma as mensagens somente quando são gravadas. O que falha ao ser gravado é entregue novamente quando seu prazo de confirmação passa, então uma mensagem pode ser gravada duas vezes, mas não perdida. Ele é mais adequado para mais logs do que uma [assinatura push](#fontes-de-push), que envia uma mensagem por requisição, suporta bem.

| Campo | Observações |
|---|---|
| `serviceAccountKey` | O arquivo de chave JSON de uma conta de serviço com `roles/pubsub.subscriber` na assinatura. |
| `subscription` | `projects/<project>/subscriptions/<name>`, ou o nome de uma assinatura no projeto da chave. Dê a ela um prazo de confirmação de 60 segundos ou mais. |
| `targetStream` | Stream de destino. Padrão `default`. |

Cada mensagem é lida como uma mensagem enviada por push: um `LogEntry` do Cloud Logging com o mapeamento da aba de push, qualquer outro objeto JSON como seus campos, qualquer outra coisa como `message`. **Testar conexão** pergunta se a chave pode consumir a assinatura, sem retirar uma mensagem.

### Métricas de nuvem

Seis fontes coletam as métricas do serviço de monitoramento de uma nuvem periodicamente e as gravam em um stream de métricas:

| Tipo | Nuvem | API | Autenticação | Permissão | `metricsStream` padrão |
|---|---|---|---|---|---|
| `aws_cloudwatch_metrics` | Amazon CloudWatch | `ListMetrics`, `GetMetricData` | [Credenciais da AWS](#autenticação-na-aws) | `cloudwatch:ListMetrics`, `cloudwatch:GetMetricData` | `cloudwatch` |
| `azure_monitor_metrics` | Azure Monitor | Resource Graph, `metrics:getBatch` | `tenantId`, `clientId`, `clientSecret` de um registro de aplicativo | **Monitoring Reader** na assinatura | `azure` |
| `gcp_monitoring_metrics` | Google Cloud Monitoring | `timeSeries.list` | `serviceAccountKey`, o arquivo de chave JSON | `roles/monitoring.viewer` no projeto | `gcp` |
| `aliyun_cms_metrics` | Alibaba Cloud CloudMonitor | `DescribeMetricList` | `accessKey`, `secretKey` | `AliyunCloudMonitorReadOnlyAccess` | `aliyun` |
| `tencent_monitor_metrics` | Tencent Cloud Monitor | `GetMonitorData` | `accessKey` (SecretId), `secretKey` (SecretKey) | `QcloudMonitorReadOnlyAccess`, mais `QcloudCVMReadOnlyAccess` para encontrar instâncias CVM | `tencentcloud` |
| `huawei_ces_metrics` | Huawei Cloud Eye | `ListMetrics`, `BatchListMetricData` | `accessKey` (AK), `secretKey` (SK) | `CES ReadOnlyAccess` | `huaweicloud` |

Cada pull lê períodos inteiros de `period` segundos que terminaram pelo menos `delay` segundos atrás, começando onde o último pull gravado terminou. Uma nuvem conclui um agregado alguns minutos após o fim de seu período, e cada período é lido uma vez: um valor corrigido depois permanece como lido. Um novo conector começa um período atrás. Um pull lê no máximo 12 períodos e continua no próximo tick; um conector que ficou desligado por mais de 6 horas ignora o que é mais antigo e informa isso.

Cada estatística de cada série se torna uma amostra de gauge chamada `<cloud>_<namespace>_<metric>_<statistic>`, da forma como o yet-another-cloudwatch-exporter nomeia as métricas do CloudWatch, no início de seu período:

| Fonte | Exemplo | Rótulos |
|---|---|---|
| CloudWatch | `aws_ec2_cpuutilization_average` | `region`, `dimension_<Name>` |
| Azure Monitor | `azure_compute_virtualmachines_percentage_cpu_average` | `subscription_id`, `resource_group`, `resource_name`, `resource_id`, `region`, `dimension_<name>`, `tag_<key>` |
| Cloud Monitoring | `gcp_compute_instance_cpu_utilization_mean` | `project_id`, `resource_type`, os rótulos do recurso e da métrica |
| CloudMonitor | `aliyun_ecs_dashboard_cpuutilization_average` | `region`, `user_id`, `dimension_<key>` |
| Tencent Cloud Monitor | `tencentcloud_cvm_cpu_usage_avg` | `region`, `dimension_<Name>` |
| Cloud Eye | `huaweicloud_sys_ecs_cpu_util_average` | `region`, `dimension_<name>` |

Esses são os mesmos nomes que um [stream de métricas do CloudWatch via Firehose](#fontes-de-push) grava, então o PromQL funciona sobre ambos:

```promql
max by (dimension_InstanceId) (aws_ec2_cpuutilization_average)
```

| Campo | Fontes | Observações |
|---|---|---|
| `metricsStream` | Todas | Stream de métricas de destino. |
| `period` | Todas | Segundos, minutos inteiros. Padrão 300. O Azure aceita 60, 300, 900, 1800, 3600, 21600, 43200 ou 86400; a Huawei Cloud 300, 1200, 3600, 14400 ou 86400. |
| `delay` | Todas | Segundos após o fim de um período antes de ele ser lido. Padrão 600 para CloudWatch e Azure, 300 para os demais. |
| `region` | Todas exceto Google Cloud | Como `us-east-1`, `eastus`, `cn-hangzhou`, `ap-guangzhou`, `cn-north-4`. |
| `namespace` | CloudWatch, CloudMonitor, Tencent Cloud, Cloud Eye | Como `AWS/EC2`, `acs_ecs_dashboard`, `QCE/CVM`, `SYS.ECS`. |
| `metrics` | Todas | Nomes de métricas, separados por vírgula ou linha. Obrigatório, exceto para CloudWatch, que lê todas as métricas do namespace que tiveram dados nas últimas três horas quando deixado vazio, no máximo 2.000 séries. O Google Cloud aceita tipos de métrica, como `compute.googleapis.com/instance/cpu/utilization`. |
| `statistics` | CloudWatch, CloudMonitor, Tencent Cloud, Cloud Eye | CloudWatch: `Average`, `Sum`, `Minimum`, `Maximum`, `SampleCount`, e percentis como `p99`; padrão `Average`, `Maximum`. CloudMonitor: `Average`, `Maximum`, `Minimum`, `Sum`; padrão `Average`, `Maximum`. Tencent Cloud: `avg`, `max`, `min`; padrão `avg`. Cloud Eye: `average`, `max`, `min`, `sum`, `variance`; padrão `average`. |
| `subscriptionId`, `resourceType`, `aggregations`, `filter`, `top` | Azure | O tipo de recurso também é o namespace da métrica, como `Microsoft.Compute/virtualMachines`. Agregações: `average` (padrão), `minimum`, `maximum`, `total`, `count`. `filter` divide por uma dimensão, como `LUN eq '*'`; `top` limita as séries em que se divide, padrão 100. |
| `projectId`, `filter` | Google Cloud | O projeto padrão é o da chave. `filter` é uma cláusula adicionada ao filtro de cada métrica. Gauges são lidos como `mean`, deltas como `sum`, contadores como `rate`, distribuições como `count` e `mean`. |
| `dimensions` | CloudMonitor | JSON opcional passado como `Dimensions`; vazio lê todas as instâncias da conta. |
| `instances` | Tencent Cloud | Uma instância por linha como `Name=Value`, várias dimensões unidas com `&`. Obrigatório, exceto para `QCE/CVM`, cujas instâncias são encontradas na região quando deixado vazio. |
| `projectId` | Cloud Eye | O projeto da região. |

Toda consulta é cobrada pela nuvem: o CloudWatch cobra cada estatística de cada série como uma métrica solicitada, o Google Cloud cobra pelas séries retornadas, os demais por chamada de API além de uma cota mensal gratuita. Mantenha `metrics` e `statistics` no que for necessário, e um `period` mais longo custa menos. **Testar conexão** faz uma pequena requisição com as configurações salvas e não move nada.

### Como está o andamento de um pull

A página do conector mostra quando uma fonte recebeu pela última vez. Uma fonte cuja última leitura falhou mostra um aviso ao lado disso, com o motivo em seu tooltip e nas configurações do conector, e o que uma fonte ignorou pela última vez também é informado ali. Pela API, `readState` contém `lastError` e `lastWarning`, cada um com `atTime` e `text`, e `position`, onde ela chegou. Salvar um conector mantém seu lugar.

## Destinos

Um destino recebe todos os eventos que passam pelas etapas de um pipeline agendado. Adicione o conector aos **Destinos** do fluxo com **Adicionar destino → Conector**. Uma entrega que falha é repetida dentro da execução, e os eventos que o conector ainda assim não aceita vão para o stream de mensagens não entregues. Consulte [Novas tentativas e mensagens não entregues](/pt-BR/pipelines#novas-tentativas-e-eventos-com-falha).

Um destino desativado não recebe nada. Cada execução ignora o conector e o nomeia no `warning` da execução. Os eventos ignorados não contam como falha, não se tornam mensagens não entregues e não são enviados quando o conector é reativado. No editor, um conector desativado aparece como **Desativado**.

| Tipo | Payload |
|---|---|
| `s3` | Um objeto JSON Lines por lote, `PUT` para `s3://<bucket>/<prefix><id>.jsonl`. |
| `kafka` | Uma mensagem por evento no tópico, com o evento como payload JSON. |
| `http` | O lote em uma requisição, ou em várias quando for grande, como NDJSON ou como um array JSON. |

### Amazon S3

O tipo `s3` também entrega em armazenamento compatível com S3, como MinIO, Cloudflare R2 e Alibaba Cloud OSS. Na UI, ative **Armazenamento compatível com S3** para definir o endpoint.

| Campo | Observações |
|---|---|
| `bucket` | Obrigatório. |
| `region` | A região do bucket. Um armazenamento compatível com S3 pode não precisar de uma. |
| `prefix` | Os objetos são nomeados `<prefix><id>.jsonl`. Uma `/` inicial é removida, e uma `/` final é adicionada. |
| `endpoint` | O endereço da API S3 de um armazenamento compatível com S3, começando com `http://` ou `https://`. |

| `auth` e suas chaves | As credenciais, que precisam de `s3:PutObject` no bucket. Consulte [Autenticação na AWS](#autenticação-na-aws). |

### Apache Kafka

| Campo | Observações |

| `topic` | Obrigatório. |

### HTTP / Webhook

| Campo | Observações |
|---|---|
| `url` | Obrigatório. Uma URL absoluta `http://` ou `https://`. Uma URL frequentemente carrega uma credencial, como uma chave no caminho ou na query, então ela é mantida como segredo. As respostas mostram apenas `urlOrigin`, o esquema, o host e a porta. Um nome de usuário e uma senha na URL são recusados: use `basic`. |
| `method` | `post` (padrão) ou `put`. |
| `format` | `ndjson` (padrão) envia um evento por linha como `application/x-ndjson`. `json` envia um array JSON como `application/json`. |

| `auth` | UI | Chaves | Requisição |
|---|---|---|---|
| `none` | **Nenhum** | | Sem credencial. |
| `bearer` | **Token Bearer** | `bearerToken` | `Authorization: Bearer <token>` |
| `basic` | **Autenticação básica** | `basicUsername`, `basicPassword` | Autorização HTTP Basic. Use-a com `https`. |
| `header` | **Cabeçalho personalizado** | `headerName`, `headerValue` | O valor no cabeçalho nomeado, como `X-API-Key` ou `DD-API-KEY`. |
| `hmac` | **Assinatura HMAC** | `hmacSecret` | Uma assinatura do corpo. O segredo precisa de pelo menos 16 caracteres. |

Um cabeçalho personalizado não pode ser um dos que a própria entrega define: `Host`, `Content-Type`, `Content-Length`, `Content-Encoding`, `Transfer-Encoding`, `Connection`, `X-MoleSignal-Timestamp` ou `X-MoleSignal-Sign`.

Uma entrega segue estas regras:

- Um lote maior que 4 MiB é dividido em várias requisições. Um evento maior que isso vai em uma requisição própria.
- Qualquer status `2xx` conta como entregue. Qualquer outro status faz a entrega falhar, e um redirecionamento também: redirecionamentos não são seguidos.
- Uma requisição expira após 30 segundos.
- O MoleSignal resolve o host antes da requisição e se conecta apenas aos endereços que resolveu. Um endereço em que serviços de metadados de nuvem respondem é recusado, seja ele na URL ou vindo do DNS: `169.254.0.0/16`, `fe80::/10`, `fd00:ec2::254` e `100.100.100.200`. Outros endereços privados são permitidos.

#### Verificar uma assinatura HMAC

Com `hmac`, cada requisição carrega dois cabeçalhos:

| Cabeçalho | Conteúdo |
|---|---|
| `X-MoleSignal-Timestamp` | O horário da requisição em segundos Unix. |
| `X-MoleSignal-Sign` | `sha256=<hex>`, o HMAC-SHA256 de `<timestamp>.<body>` com o segredo compartilhado. |

Para verificar uma requisição, calcule o HMAC-SHA256 sobre o timestamp, um `.` e os bytes brutos do corpo com o mesmo segredo, e compare o resultado com a assinatura em tempo constante. Recuse um timestamp mais antigo que alguns minutos, para que uma requisição capturada não possa ser reenviada depois.

```python
import hashlib
import hmac
import time


def verify(secret: bytes, timestamp: str, signature: str, body: bytes, tolerance: int = 300) -> bool:
    if abs(time.time() - int(timestamp)) > tolerance:
        return False
    signed = timestamp.encode() + b"." + body
    expected = "sha256=" + hmac.new(secret, signed, hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, signature)
```

## Autenticação na AWS

O S3 e o CloudWatch Logs se autenticam na AWS de uma entre cinco formas:

| `auth` | UI | Chaves | Credenciais |
|---|---|---|---|
| `access_key` | **Chave de acesso** | `accessKey`, `secretKey` | A chave de longa duração de um usuário do IAM. |
| `temporary_key` | **Chave temporária** | `accessKey`, `secretKey`, `sessionToken` | Uma chave de curta duração do AWS STS, válida apenas com o token de sessão dela. Substitua a chave antes de ela expirar. |
| `node_role` | **Identidade do nó** | | A identidade do nó em que o MoleSignal é executado. Nenhuma chave é armazenada. |
| `assume_role` | **Assumir uma função** | `roleArn`, opcionalmente `accessKey` e `secretKey` | Uma função assumida pelo AWS STS com o ID externo da organização. |
| `web_identity` | **Identidade da web** | `roleArn` | Uma função assumida com o token de identidade da web do nó. |

Sem `auth`, as chaves armazenadas decidem: uma chave de acesso é lida como `access_key`, um `roleArn` como `assume_role` e nenhum dos dois como `node_role`. Um `roleArn` tem o formato `arn:aws:iam::<account>:role/<name>`.

### Identidade do nó

O `node_role` usa a identidade que os SDKs da AWS encontram no nó: funções do IAM do EKS para contas de serviço (IRSA) ou EKS Pod Identity, uma função de tarefa do ECS ou um perfil de instância do EC2. Uma chave estática no ambiente do nó, como `AWS_ACCESS_KEY_ID`, nunca é usada para conectores.

<Warning>
  A identidade do nó e o token de identidade da web dele pertencem à implantação. Toda organização na implantação pode escolher `node_role` e `web_identity`, portanto tudo o que a identidade do nó alcança, e toda função que confia no token do nó, fica aberto aos conectores de todas as organizações. Conceda a eles apenas o acesso que toda organização pode ter.
</Warning>

### Assumir uma função

O `assume_role` solicita ao AWS STS uma chave de uma hora da função e renova a chave 5 minutos antes de ela expirar. As credenciais base que assumem a função são a identidade do nó. Para uma implantação que não é executada na AWS, selecione **Assumir a função com uma chave de acesso em vez da identidade do nó** e informe a chave de um usuário do IAM.

Cada organização assume funções com o próprio ID externo, `molesignal-<organization ID>`, que não pode ser alterado. O formulário o exibe em **ID externo**, e `GET /api/v1/connectors/aws-external-id` o retorna. Exija o ID externo na política de confiança da função, para que nenhuma outra organização possa assumir a função mesmo que descubra o ARN:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": { "AWS": "<ARN of the node role or IAM user>" },
      "Action": "sts:AssumeRole",
      "Condition": { "StringEquals": { "sts:ExternalId": "molesignal-<organization ID>" } }
    }
  ]
}
```

A sessão recebe o nome `molesignal-<connector ID>`, que é como ela aparece no AWS CloudTrail. A solicitação vai para o endpoint regional do STS da `region` do conector: `us-east-1` quando a região está vazia, e o domínio `amazonaws.com.cn` para as regiões da China.

### Identidade da web

O `web_identity` assume a função com o token de identidade da web cujo caminho o `AWS_WEB_IDENTITY_TOKEN_FILE` do nó informa, como o token de conta de serviço que o EKS projeta para o IRSA. Um conector não pode indicar outro arquivo. A política de confiança da função precisa confiar no provedor OIDC que emite o token. Em um nó sem `AWS_WEB_IDENTITY_TOKEN_FILE`, o conector não tem credenciais.

O token é trocado no endpoint regional do STS da `region` do conector, ou em `AWS_ENDPOINT_URL_STS` quando o ambiente do nó o define. O mesmo vale para uma identidade do nó que vem do IRSA.

## Testar uma conexão

**Testar conexão** testa as configurações como estão no formulário, antes de serem salvas. Um segredo deixado em branco é o que está salvo. Cada tipo faz o mínimo que comprova que uma entrega ou uma leitura pode funcionar:

| Tipo | Teste |
|---|---|
| `s3` | Grava o objeto `.molesignal-connection-test` sob o prefixo e o remove quando a política permite. |
| `kafka` | Lê os metadados do tópico nos brokers, o que comprova a conexão, o TLS e a autenticação, e que o tópico existe. Não grava nenhuma mensagem. |
| `http` | Envia um evento marcado como teste: `"message": "MoleSignal connection test"` e `"molesignal_connection_test": true`. |
| `aws_cloudwatch_logs` | Lê no máximo um evento do último minuto do grupo de logs. Não grava nada no stream e deixa a posição de leitura onde estava. |
| `kafka_source` | Lê os metadados do tópico nos brokers, como em `kafka`. Não lê nenhuma mensagem e deixa a posição de leitura onde estava. |
| `s3_source` | Lista um objeto sob o prefixo, o que comprova as credenciais e `s3:ListBucket`. Não lê nada e deixa a posição de leitura onde estava. |

Um teste desiste após 25 segundos. Pela API, `POST /api/v1/connectors/test` recebe o `kind` e o `configJson` a testar. Com o `id` de um conector salvo do mesmo tipo, `***` representa o segredo que o conector mantém. Configurações que não podem funcionar respondem `400`, como ao salvar.

```bash
curl -X POST http://localhost:5080/api/v1/connectors/test \
  -H "authorization: Bearer $MS_TOKEN" \
  -H 'content-type: application/json' \
  -d '{
        "id": "<connector id>",
        "kind": "kafka",
        "configJson": {
          "brokers": "b-1.example.com:9096",
          "topic": "logs",
          "tls": true,
          "auth": "sasl_scram_sha_512",
          "saslUsername": "molesignal",
          "saslPassword": "***"
        }
      }'
```

```json
{ "ok": true, "code": "ok", "detail": null, "elapsedMs": 412 }
```

`elapsedMs` é quanto tempo o teste levou. Um teste com falha indica a causa em `code`, e `detail` traz as palavras do outro lado, até 600 caracteres:

| `code` | Significado |
|---|---|
| `ok` | Conectado. |
| `invalid` | As configurações não podem funcionar, ou o conector é uma origem push, que não tem a que se conectar. |
| `no_credentials` | Não foi possível obter credenciais da AWS: o nó não tem identidade, ou nenhuma do tipo solicitado. |
| `denied` | O outro lado recusou as credenciais ou o que elas têm permissão de fazer. |
| `not_found` | O bucket, o tópico, o grupo de logs ou o endereço não existe. |
| `tls` | O handshake TLS falhou: um certificado não confiável ou não apresentado. |
| `unreachable` | Não foi possível resolver o host ou conectar a ele. |
| `timeout` | Nenhuma resposta a tempo. |
| `failed` | Qualquer outra falha. |
