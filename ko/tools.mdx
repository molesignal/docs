MoleSignal은 AI가 조작할 수 있는 제품 기능을 프로토콜에 종속되지 않는 **도구 카탈로그**로 모델링합니다. Mole
Agent와 인바운드 MCP는 어댑터마다 비즈니스 로직을 중복 구현하는 대신 동일한 `ToolSpec` 계약과
서버 측 런타임을 사용합니다.

현재 카탈로그에는 **등록된 도구 254개**가 있습니다. 각 도구는 변경되지 않는 이름, 표준
설명, 입력 및 출력 스키마, 필수 IAM 권한, 위험 수준, 액세스 모드,
주석, 허용된 사용 환경을 정의합니다.

## 도구의 작업 단위

잘 설계한 MoleSignal 도구는 목적이 하나로 명확하고 결과의 범위가 제한적입니다.

- 단일 읽기, 사전 점검 또는 변경 작업마다 도구 하나를 사용합니다.
- 목록 조회, 단건 조회, 생성, 업데이트, 삭제, 테스트, 트리거, 취소, 재시도 작업을 구분합니다.
- 원시 라우트나 임의 요청 생성기 대신 제품 기능을 노출합니다.
- 모델과 감사 기록에 적합하도록 구조화하고 범위를 제한한 출력을 반환합니다.
- 평문 자격 증명, 바이너리 전송, 원시 데이터 수집, 셸 실행, 브라우저 제어는
  카탈로그에 포함하지 않습니다.

이렇게 작업을 나누면 IAM과 도구 정책에서 관련 HTTP 리소스 전체에 광범위한 액세스 권한을 부여하는 대신
개별 작업을 정확히 제어할 수 있습니다.

## 사용 환경

각 런타임 환경에서 노출할 도구를 명시적으로 지정합니다.

| 사용 환경 | 검색 및 실행 |
|---|---|
| Mole Agent | 자주 쓰는 도구를 제공합니다. 필요한 경우 `tool_search → tools_call`로 다른 기본 제공 도구와 권한이 있는 아웃바운드 MCP 도구를 검색하고 실행합니다. |
| 인바운드 MCP | 자주 쓰는 읽기 도구와 승인 제어 기능을 제공합니다. `tool_search → call_read_tool` 또는 `call_managed_tool`로 도구를 검색하고 실행합니다. |
| 자동화 | 자동화 환경에서 사용하도록 명시한 도구만 제공합니다. [예약된 로그 검사](/ko/logs/inspections)에 사용하는 `query_logs`, `get_stream_schema`, `search_field_values`, `analyze_log_patterns`가 이에 해당합니다. |

서버는 도구 목록을 생성할 때와 실행 직전에 해당 환경에서 도구를 사용할 수 있는지
확인합니다. `tools/list`를 거치지 않아도 사용 환경의 제한은 그대로 적용됩니다.

## 인바운드 MCP 도구 검색

인바운드 MCP는 `tools/list`에 포함하는 도구 수를 제한합니다. 권한에 따라 응답에 다음 항목을 포함할 수 있습니다.

- 고정 읽기 도구 7개: `query_logs`, `query_metrics`, `list_streams`,
  `get_stream_schema`, `list_traces`, `get_trace`, `get_incident`
- 승인 제어: `list_agent_approvals`, `get_agent_approval`,
  `execute_agent_approval`
- 실행 제어: `list_agent_executions`, `get_agent_execution`
- `tool_search`, `call_read_tool`, `call_managed_tool`

IAM과 도구 정책을 통해 이 목록에서 제품 도구를 개별적으로 제외할 수 있습니다.

### 권한이 있는 도구 검색

제품 관련 문구 또는 도메인을 입력해 `tool_search`를 호출합니다.

```json
{
  "query": "status page incident",
  "limit": 10,
  "includeSchema": true
}
```

결과에는 인바운드 MCP에서 사용할 수 있고, 워크스페이스 도구 정책에서 활성화했으며,
해당 자격 증명에 사용 권한이 있는 도구만 포함합니다. 요청 시 각 검색 결과에 스키마와 실제로 적용되는 실행
메타데이터를 포함합니다.

### 읽기 또는 사전 점검 실행

검색한 도구 이름과 인수를 `call_read_tool`에 전달합니다.

```json
{
  "name": "list_status_page_incidents",
  "arguments": {
    "pageId": "status-page-id",
    "view": "current"
  }
}
```

MCP 클라이언트가 Tasks 확장 지원을 알리면 `asTask`를 `true`로 설정해 상태가 유지되는 읽기 작업을
생성할 수 있습니다. MCP 작업 메서드로 반환된 작업의 상태를 주기적으로 조회하거나 작업을 업데이트 또는 취소합니다.

### 관리형 변경 실행

`call_managed_tool`에 고유한 멱등성 키를 전달합니다.

```json
{
  "name": "update_annotation",
  "arguments": {
    "annotationId": "annotation-id",
    "title": "Deployment rollback started"
  },
  "idempotencyKey": "8d7788d2-9b4e-44bd-bf35-61a5690f0064"
}
```

MoleSignal은 승인 요청을 생성하거나 변경을 실행하기 전에 인증된 주체에 해당 키를
예약합니다. 같은 요청을 반복하면 저장한 결과나 진행 중인
상태를 반환합니다. 같은 키를 다른 인수와 함께 사용하면 요청을 거부합니다.

## 위험 수준 및 실행 정책

도구 위험 수준에 따라 안전한 기본 실행 모드를 적용합니다. 워크스페이스 도구 정책에서 더 엄격한 실행
모드를 적용할 수 있습니다.

| 위험 수준 | 기본 모드 | 의미 |
|---|---|---|
| L0 | 자동 | 범위가 제한된 읽기 전용 작업입니다. |
| L1 | 확인 | 정책에서 자동 실행을 지정하지 않으면 위험이 낮은 변경에도 MCP 호스트의 확인이 필요합니다. |
| L2 | 단일 승인 | MoleSignal에서 한 번 승인해야 합니다. |
| L3 | 이중 승인 | MoleSignal에서 두 번 승인해야 합니다. |
| L4 | 비활성화 | 위험이 높거나 파괴적인 원격 작업은 기본적으로 사용할 수 없습니다. |

관리형 변경을 자동으로 실행해도 감사 가능한 승인 기록을 생성합니다. 확인 모드에서는
MCP의 다단계 입력 절차를 사용할 수 있습니다. 단일 승인과 이중 승인 모드에서는 MoleSignal에서 검토가 끝날 때까지 대기합니다.
필수 검토를 마치면 최초 요청자가 `execute_agent_approval`을 새
`idempotencyKey`와 함께 호출해 작업을 완료할 수 있습니다.

런타임은 실행 전에 다음 항목을 다시 검증합니다.

1. 인증된 주체와 조직의 상태
2. 필수 IAM 권한과 권한 모드
3. 해당 환경에서의 도구 노출 여부와 현재 도구 정책
4. 입력 스키마, 대상 리소스의 상태, 위험 수준
5. 시간 제한, 응답 크기 제한, 멱등성
6. 작업 후 검증 및 감사 기록

## 카탈로그 지원 범위

카탈로그는 AI 기반 조사 및 관리에 안전하고 유용한
제품 작업을 지원합니다.

| 영역 | 주요 기능 |
|---|---|
| 로그, 메트릭 및 스트림 | 텔레메트리를 쿼리하고, 스키마와 설정을 확인하며, 전후 이벤트를 검색하고, 메트릭 레이블이나 시계열을 탐색합니다. 로그를 패턴별로 그룹화해 기준 구간과 비교합니다. 메트릭이 언제부터 얼마나 변했는지, 어떤 시계열과 레이블이 변화를 주도했는지 요약합니다. 데이터 준비 상태를 확인합니다(서비스, 환경, 트레이스 ID가 기록되는지, 모든 신호에서 같은 서비스 이름을 사용하는지, 메트릭 이름에 단위가 포함되는지). 예약된 로그 검사와 보고서를 조회하거나 검사를 즉시 실행합니다. |
| 트레이스, APM, RUM 및 프로파일 | 트레이스, 서비스 토폴로지, 세션, 오류, 종속성, 플레임 그래프, 신호 간 상관관계를 확인합니다. APM 인사이트를 조회하고 서비스 맵에서 특정 서비스가 도달하는 대상을 확인합니다. 이름, 별칭, 설명 또는 태그로 서비스 카탈로그를 검색합니다. 페이지별로 Core Web Vitals를 요약합니다. RUM 애플리케이션을 요약하고, 이슈 목록과 세부 정보를 조회하며, 사용자가 겪는 불편 요인을 파악합니다. 개별 뷰의 워터폴을 확인하고, 모든 RUM 스트림을 집계할 수 있습니다. |
| 알림 및 인시던트 | 인시던트와 온콜 상태를 조회합니다. 최근 90일간 발생한 유사 인시던트를 찾고, 특정 시점이나 인시던트 전후의 배포, 설정 변경 및 기능 플래그를 나열합니다. 알림 규칙을 생성, 업데이트, 삭제, 테스트하거나 트리거합니다. 인시던트를 확인 처리하거나 해결합니다. |
| 대시보드, 보고서 및 주석 | 대시보드, 폴더, 패널, 주석, 보고서 템플릿, 일정 및 전송을 관리합니다. |
| 검색 작업 및 저장된 뷰 | 지속형 검색을 제출, 확인, 취소, 재시도하거나 삭제하고, 저장된 뷰를 관리합니다. |
| 파이프라인, 함수, 보강 및 커넥터 | 예약된 실행을 확인하고, 함수를 관리하며, 변환을 테스트하고, 보강 또는 커넥터 메타데이터를 조회합니다. |
| 신세틱 모니터링 및 상태 페이지 | 모니터와 결과를 확인하고, 모니터를 실행하거나 일시 중지합니다. 상태 페이지의 수명 주기와 자동화를 관리하고, 인시던트 사후 분석 보고서 초안을 작성합니다. |
| 알림 전송 | 커넥터, 정책, 템플릿 및 전송 내역을 확인하고, 전송을 재시도하거나 확인 처리합니다. |
| IAM 및 관리 | 사용자, 팀, 역할, 기능, 감사 이벤트, 서비스 계정 및 API 토큰 메타데이터를 조회합니다. 비밀값을 노출하지 않고 자격 증명 상태를 관리합니다. |
| Mole Agent 제어 | 조사, 승인, 실행 및 자동화를 확인한 다음, 권한이 있으면 승인된 작업을 실행합니다. |

`get_platform_capabilities`를 호출해 현재 인터페이스에 해당하는 기능 요약을 조회합니다. 정적 목록에 의존하지 말고
`tool_search`를 호출해 현재 권한으로 사용할 수 있는 도구 이름과 스키마를 조회합니다.

## ID 및 비밀값의 접근 경계

- 인증에 사용된 자격 증명에서 호출자의 `userId`와 `orgId`를 가져옵니다.
- `get_user_profile`과 `get_user_preferences`는 리소스를 선택하는 용도로만
  `target_user_id`를 선택적 인수로 받습니다. 다른 멤버의 정보를 조회하려면 `org.members.read` 권한이 필요하며,
  해당 멤버가 조직에 속하는지 확인해야 합니다.
- 조회 및 목록 도구는 자격 증명 메타데이터만 반환합니다.
- `create_api_token`과 `create_service_account`는 모두 한 번만 표시되는 평문 비밀값을 생성하므로
  인바운드 MCP에서 사용할 수 없습니다. 이 자격 증명은 웹 UI에서 생성합니다.
- 기존 서비스 계정과 API 토큰은 비밀값을 노출하지 않는 도구를 통해 권한이 있는 경우
  목록 조회, 업데이트, 활성화, 비활성화, 폐기 또는 삭제할 수 있습니다.
- `query_logs`, `search_around`, `search_field_values`, `get_stream_schema` 및 스트림 스키마
  리소스는 자격 증명과 관계없이 [`_audit` 스트림](/ko/settings/data-security#감사-스트림) 접근을 거부합니다.

카탈로그는 의도적으로 로그인, 등록, 비밀번호 재설정, 인증이 필요 없는 공개
경로, 원시 OTLP 또는 Prometheus 데이터 수집, 외부 웹훅, 바이너리 업로드 및 다운로드, 노드 드레이닝,
런타임 프로파일링, 임의의 HTTP 요청, 셸 및 브라우저 실행을 제외합니다.

## MCP 리소스, 프롬프트 및 작업

인바운드 MCP는 플랫폼 기능, 도구 카탈로그,
승인, 실행, 검색 작업 및 스트림 스키마에 대해서도 IAM 권한에 따라 필터링한 리소스를 제공합니다. 기본 제공 프롬프트와 조직 및 현재 사용자 범위의
Mole Agent 프롬프트는 `prompts/list` 및 `prompts/get`을 통해 사용할 수 있습니다.

오래 걸리는 조회 작업은 MCP 작업으로 실행할 수 있습니다. 협상된 MCP 프로토콜
