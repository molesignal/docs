[규칙](/ko/alerting/rules)이 발동하거나, [신세틱 점검이 실패](/ko/synthetics#알림-인시던트)하거나, [알림 소스](/ko/alerting/sources)가 외부 알림을 수신하면 인시던트가 생성됩니다. 인시던트에는 규칙, 값,
레이블과 종료까지의 모든 단계가 기록됩니다. **알림 → 인시던트**를 열거나 `⌘⌥A`를 누릅니다. 인시던트를 조회하려면
`alerts.incidents.read` 권한이 필요합니다. 확인, 해결, 일시 중지에는
`alerts.incidents.acknowledge` 권한이 필요합니다. [인시던트에 조치하기](#인시던트에-조치하기)의 나머지 작업에는
`alerts.incidents.update` 권한이 필요하지만, 에스컬레이션과 병합에는 `alerts.incidents.escalate` 권한이 필요합니다. 알림 음소거에는 `alerts.incidents.silence` 권한이 필요합니다. Feishu 또는 Slack 앱으로 받은 알림은
카드에서도 확인, 해결 또는 일시 중지할 수 있습니다.
[알림 카드](/ko/im#알림-카드)를 참조합니다. 문자 메시지에는 코드로, 전화에는 키 입력으로 응답할 수 있습니다.
[문자 및 전화에 응답하기](/ko/notification-channels#문자-메시지와-전화로-경보-처리)를 참조합니다.

## 인시던트 상태

| 상태 | 목록 레이블 | 의미 |
|---|---|---|
| `open` | **대기 중** | 발생 중이며 아직 확인한 담당자가 없습니다. 에스컬레이션을 계속합니다. |
| `acknowledged` | **진행 중** | 담당자가 지정되었습니다. 에스컬레이션을 중단합니다. |
| `resolved` | **복구됨** | 규칙이 복구 상태로 돌아갔거나 담당자가 해결하여 인시던트가 끝났습니다. |
| `closed` | **종료됨** | 인시던트가 끝났습니다. |

규칙이 [복구 조건](/ko/alerting/rules#복구-및-데이터-누락)을 충족하면 열린 인시던트가 자동으로 해결됩니다.
확인한 인시던트는 해결할 때까지 확인 상태를 유지합니다. 에스컬레이션 정책에
[확인했지만 미해결](/ko/alerting/on-call#확인-후-미해결-상태)이 설정되어 있으면, 설정된 시간이 지난 뒤
**대기 중**으로 돌아가고 호출 알림을 다시 보냅니다. 일시 중지한 인시던트는 **진행 중** 상태입니다. 외부 소스의
인시던트는 확인 여부와 관계없이 소스가 복구를 보고하면 해결됩니다.
[알림이 인시던트로 전환되는 방식](/ko/alerting/sources#경보가-인시던트로-전환되는-방식)을 참조합니다. 각 규칙 또는
분할된 규칙의 각 그룹에는 동시에 하나의 인시던트만 활성 상태일 수 있습니다.

## 인시던트 목록

**인시던트** 상단에는 영향을 받은 서비스 수, 확인 대기 중인 인시던트 수,
지난 24시간 동안 복구된 인시던트 수가 표시됩니다. 요약에는 현재 발생 중인 인시던트 수,
가장 오래된 인시던트의 지속 시간, 평가 중인 규칙 수가 표시됩니다. **최근 복구된 인시던트**에는 최근에 끝난
인시던트가 표시됩니다.

**발생 중**과 아직 담당자가 없는 인시던트를 모은 **대기 중** 사이를 전환합니다. 현재 사용자가
팀에 속해 있으면 **내 팀**에서 소속 팀으로 [라우팅된](/ko/alerting/routing) 인시던트를 확인할 수 있습니다.
오른쪽에서 우선순위로 필터링하거나 **없음**을 선택해 우선순위가 없는 인시던트를 표시합니다. 인시던트는 심각도,
우선순위, 발생 지속 시간 순으로 정렬됩니다. 각 행에는 심각도, 인시던트와 해당
서비스(긴급도가 낮으면 **낮은 긴급도** 표시), 우선순위, 상태, 지속 시간,
담당자와 라우팅된 팀이 표시됩니다. 다음 세 가지 작업을 수행할 수 있습니다.

| 작업 | 효과 |
|---|---|
| **확인** | 인시던트를 맡습니다. 상태가 **진행 중**으로 바뀌고 에스컬레이션을 중단합니다. |
| **알림 음소거** | 이 인시던트의 추가 알림과 에스컬레이션만 일시 중지합니다. [인시던트 하나의 알림 음소거](/ko/alerting/silences#단일-인시던트-음소거)를 참조합니다. |
| **런북** | 규칙에 대응 가이드가 있으면 해당 가이드를 엽니다. |

개별 행을 선택하거나 목록 헤더에서 모든 행을 선택하면 목록 위에 일괄 작업 표시줄이 나타납니다.
**확인**, **해결**, **일시 중지**, **재할당**, **조정**(심각도, 우선순위 또는 긴급도)을 사용할 수 있습니다.
두 개 이상 선택하면
**병합**을 사용할 수 있으며, 병합할 때 유지할 인시던트를 선택합니다. 요청 한 번으로 최대 100개의 인시던트를 처리합니다.
이미 복구되는 등의 이유로 처리할 수 없는 인시던트는 첫 번째 사유와 함께 집계하고, 나머지는
처리합니다.

### 인시던트 수동 생성

고객이 신고하거나 직접 발견한 문제처럼 규칙이 감지하지 못한 문제도 인시던트로 생성할 수 있습니다.
이 경우에도 일반 인시던트와 동일하게 호출 알림을 보내고 에스컬레이션합니다. 목록 위에서 **새 인시던트**를 선택합니다(`alerts.incidents.create`).

1. **발생 내용**에서 **제목**(필수)과 **설명**(Markdown 지원)을 입력하고
   **심각도**(기본값은 오류), **우선순위**, **긴급도**(기본값은
   에스컬레이션 정책에 따름)를 선택합니다. 필요한 경우 **영향을 받은 서비스**를 쉼표로 구분해 입력하고, **레이블**은
   한 줄에 하나씩 `key=value` 형식으로 입력합니다.
2. **담당자 지정**에서 다음 중 하나를 선택합니다.

   | 선택 항목 | 효과 |
   |---|---|
   | **자동 라우팅** | 규칙으로 생성된 인시던트와 동일하게 [알림 라우팅](/ko/alerting/routing)에 따라 라우팅합니다. |
   | **팀 지정** | 해당 팀의 온콜 정책을 적용합니다. 팀 정책이 없으면 기본 정책을 적용합니다. |
   | **에스컬레이션 정책** | 정책의 1단계부터 알림을 보냅니다. |
   | **지정된 사용자** | 에스컬레이션 정책을 적용하지 않고 최대 10명에게 직접 알림을 보냅니다. |

3. 필요한 경우 **중대 인시던트 선언**을 선택한 다음 **인시던트 생성**을 선택합니다. 인시던트 페이지가
   열립니다.

수동으로 생성한 인시던트에는 `alert.source=manual` 레이블이 붙습니다. `created_by` 어노테이션에는 개설자를,
`description` 어노테이션에는 인시던트 설명을 기록합니다. 수동 인시던트는 알림 파이프라인을 거치지 않으며, 다른 인시던트와
중복으로 처리하지 않습니다. 자동으로 복구되지 않으므로 직접 해결해야 합니다. 인시던트 페이지의 **개설자**에는
인시던트를 생성한 사용자가 표시되며, 인사이트에서는 이러한 인시던트를 **수동 생성**으로 집계합니다. Mole Agent의
`create_incident` 도구로도 한 번의 승인을 거쳐 인시던트를 생성할 수 있습니다.

## 인시던트 상세 정보

인시던트를 선택해 상세 정보를 엽니다. 상단에는 상태, 발생 시각, 규칙, 발생 후 경과 시간과
**확인**, **해결**, **추가 작업**이 표시됩니다. **추가 작업**에는
[인시던트에 조치하기](#인시던트에-조치하기)의 작업과 **알림 음소거**가 있습니다.

| 섹션 | 내용 |
|---|---|
| **타임라인** | 발생 시각, 알림 수신자, 작업 수행자와 작업 내용(확인, 재할당, 대응 담당자 추가, 에스컬레이션, 일시 중지, 심각도 변경, 병합, 해결, 문제 해결·티켓·주요 인시던트의 단계), 인시던트 생성 전에 [알림 파이프라인](/ko/pipelines/alert-events#이벤트-처리-결과)이 변경한 내용, 작업 경로(API, 채팅, SMS 회신, 전화 키 입력, Mole Agent)와 각 이벤트 사이의 경과 시간을 표시합니다. 하단에서 [메모](#메모)를 추가할 수 있으며, 그 아래에는 이 인시던트에 병합된 인시던트가 표시됩니다. |
| **조사** | **트리거 쿼리 열기**는 해당 탐색기에서 동일한 쿼리를 다시 실행합니다. **관련 로그**와 **관련 메트릭**은 같은 시간 범위에서 영향을 받은 컨텍스트를 엽니다. RUM 지표에서 발생한 인시던트에는 **RUM에서 열기**가 표시됩니다. |
| **조사 가이드** | 규칙의 [조사 가이드](/ko/alerting/rules#조사-가이드)에 지정된 단계, 인시던트의 시간 범위로 열리는 쿼리, 대시보드를 표시합니다. 규칙에 가이드가 있는 경우에만 표시합니다. |
| **AI 근본 원인 분석** | Mole Agent의 분석 결과입니다. [AI 근본 원인 분석](#ai-근본-원인-분석)을 참조합니다. |
| **신호 간 연결 정보** | 증거에서 찾은 서비스, 트레이스 ID, 호스트를 각각 링크로 표시합니다. |
| **트리거 쿼리** | 쿼리와 반환값을 표시합니다. **샘플 값 보기**를 선택하면 샘플 행이 표시됩니다. |
| **메타데이터** | 인시던트의 레이블과 어노테이션을 표시합니다. |
| **담당자** | 에스컬레이션 대상과 인시던트가 [라우팅된](/ko/alerting/routing#인시던트의-라우팅-정보) 팀 및 그 이유를 표시합니다. 일시 중지, 다른 인시던트로의 병합, 수동 심각도 설정도 여기에 표시합니다. |
| **영향 범위** | 서비스가 지정된 인시던트의 경우 서비스 맵을 따라 해당 서비스의 영향이 어디까지 미치는지 표시합니다. [인시던트의 영향 범위](/ko/apm/insights#인시던트의-영향-범위)를 참조합니다. |
| **샘플 세션** | RUM 지표에서 발생한 인시던트의 경우 해당 문제가 나타난 세션과 각 세션의 리플레이를 표시합니다. [RUM 알림](/ko/rum/alerts#인시던트)을 참조합니다. |
| **유사 인시던트** | 최근 90일간 발생한 유사 인시던트와 각 처리 결과를 표시합니다. [유사 인시던트 및 최근 변경 사항](#유사-인시던트-및-최근-변경-사항)을 참조합니다. |
| **최근 변경 사항** | 트리거 시점 전후에 관련 서비스와 다운스트림 서비스에서 보고된 배포, 구성 변경, 기능 플래그를 표시합니다. 트리거 전날 규칙을 수정했다면 해당 규칙도 표시합니다. |
| **문제 해결** | 인시던트에 적용할 수 있는 문제 해결 작업과 요청한 실행 및 승인을 표시합니다. [문제 해결](/ko/alerting/remediation)을 참조합니다. |
| **티켓** | 인시던트의 Jira 또는 Feishu Project 티켓과 상태를 표시합니다. 여기서 티켓을 생성할 수 있습니다. [티켓](/ko/alerting/tickets)을 참조합니다. |
| **주요 인시던트** | 주요 인시던트를 선언하고, 역할을 할당하고, 상황실과 회의에 참여하고, 작업을 태스크로 나누고, 진행 상황을 게시합니다. [주요 인시던트 및 사후 분석](/ko/alerting/major-incidents)을 참조합니다. |
| **사후 분석** | 인시던트의 내부 사후 분석을 관리합니다. **사후 분석 작성**은 템플릿으로 초안을 만들고, **사후 분석 열기**는 기존 문서에서 작업을 이어갑니다. [사후 분석](/ko/alerting/major-incidents#사후-분석)을 참조합니다. |

## 인시던트에 조치하기

**추가 작업**의 모든 작업은 타임라인에 기록되며
[API](#인시던트-api)로도 실행할 수 있습니다. Mole Agent도 이 작업을 수행할 수 있습니다. 메모를 추가하려면 요청자의
확인이 필요하고, 나머지 작업은 승인 1회가 필요합니다. [승인 및 실행](/ko/agent#승인-및-실행)을 참조합니다.
Mole Agent는 티켓 생성, 주요 인시던트 역할 할당, 태스크 추가, 사후 분석 초안 작성(요청자
확인 필요), 주요 인시던트 선언 및 진행 상황 게시(승인 1회 필요),
문제 해결 실행 제안([사전 승인](/ko/alerting/remediation#사전-승인)이 적용되지 않으면 승인 2회 필요)도 수행할 수 있습니다.
복구된 인시던트와 다른 인시던트에 병합된 인시던트에는 더 이상 이 작업을 수행할 수 없지만,
[메모](#메모)는 계속 추가할 수 있습니다.

| 작업 | 효과 |
|---|---|
| **재할당** | 개인에게 재할당: 최대 10명을 담당자로 지정하고 알림을 보냅니다. 인시던트는 **대기 중**으로 돌아가고 아무도 확인하지 않으면 에스컬레이션을 계속합니다. 팀에 재할당: 팀의 온콜 정책을 1단계부터 다시 시작합니다. 팀에 정책이 없으면 기본 정책을 사용합니다. 에스컬레이션 정책을 재할당: 해당 정책을 1단계부터 다시 시작하며 팀은 유지합니다. 재할당할 때 타임라인에 메모를 남길 수 있습니다. |
| **대응 담당자 추가** | 선택한 사람을 담당자에 추가하고 알림을 보냅니다. 상태는 그대로 유지합니다. |
| **지금 에스컬레이션** | 선택한 단계의 대상에게 즉시 알림을 보냅니다. 기본값은 다음 단계이며, 인시던트의 심각도에 해당하는 단계만 표시합니다. 확인한 인시던트는 **대기 중**으로 돌아갑니다. |
| **일시 중지** | 1시간, 4시간, 8시간, 24시간 또는 **사용자 지정…**(1분~7일)을 선택합니다. 대기 중인 인시던트는 먼저 확인 처리합니다. 일시 중지 중에는 알림을 보내지 않습니다. 일시 중지가 끝나면 인시던트는 **대기 중**으로 돌아가고 담당자에게 다시 알림을 보냅니다. **일시 중지 해제**를 선택하면 즉시 종료합니다. |
| **심각도** | 심각도를 수동으로 설정하면 규칙, 알림 소스, 신세틱 검사에서 더 이상 심각도를 변경하지 않습니다. 대기 중인 인시던트의 심각도를 높이면 새 심각도를 기준으로 1단계부터 다시 알림을 보냅니다. 심각도를 낮추면 심각도만 변경합니다. |
| **우선순위** | 조직의 [우선순위 수준](/ko/alerting/on-call#긴급도-및-우선순위-수준)(기본값은 P1~P5) 중 하나 또는 **없음**을 선택합니다. 우선순위만 변경하며 알림을 다시 보내지 않습니다. 우선순위는 인시던트 목록의 열과 필터, [라우팅 규칙](/ko/alerting/routing)의 조건, 주요 인시던트 자동 생성, 티켓 우선순위 매핑, 인사이트에 사용합니다. |
| **긴급도** | **높은 긴급도** 또는 **낮은 긴급도**를 선택합니다. [긴급도](/ko/alerting/on-call#긴급도)를 참조합니다. 대기 중인 인시던트를 높은 긴급도로 변경하면 1단계부터 다시 알림을 보냅니다. 긴급도를 낮추면 긴급도만 변경하고 추가 에스컬레이션을 중단합니다. 긴급도를 수동으로 설정하면 지원 시간에 따라 더 이상 긴급도를 변경하지 않습니다. |
| **병합** | 다른 활성 인시던트를 이 인시던트에 병합합니다. [인시던트 병합](#인시던트-병합)을 참조합니다. |
| **알림 음소거** | [단일 인시던트의 알림 음소거](/ko/alerting/silences#단일-인시던트-음소거)를 참조합니다. |

이 작업은 에스컬레이션 알림을 보냅니다. 템플릿의 `{{escalation.reason}}`은 알림 사유를
나타냅니다. 값은 `reassigned`, `responder_added`, `manual`(지금 에스컬레이션), `snooze_ended`,
`severity_raised`, `urgency_raised`, `ack_timeout`(확인 후에도 오랫동안 미해결) 중 하나입니다. 템플릿에는
`{{urgency}}`와 `{{priority}}`도 사용할 수 있습니다.
[템플릿 변수](/ko/notification-channels#템플릿-변수)를 참조합니다.

### 인시던트 병합

한 번의 장애로 여러 규칙이 트리거되는 등 한 문제에서 여러 인시던트가 발생하면
하나의 주 인시던트로 병합합니다. 병합된 인시던트는 개별적으로 알림을 보내거나 에스컬레이션하지 않으며,
인시던트 목록이나 인사이트에 더 이상 표시되지 않습니다. 대신 주 인시던트의 타임라인 아래에 표시됩니다.
주 인시던트를 해결하면 병합된 인시던트도 해결됩니다. 병합된 인시던트가 먼저 복구되면 주 인시던트의 타임라인에
기록합니다. 한 번에 최대 50개의 인시던트를 병합할 수 있으며, 병합은 취소할 수 없습니다.

상세 정보에서는 **추가 작업 → 병합**을 열고 병합할 인시던트를 선택합니다. 인시던트 목록에서는
여러 인시던트를 선택한 뒤 **병합**을 선택하고 주 인시던트를 지정합니다.

### 메모

타임라인 하단의 입력란에 확인한 내용과 수행한 작업을 최대 4,000자로 기록합니다.
이렇게 하면 다음 담당자가 바로 확인할 수 있습니다. 재할당할 때 작성한 메모도 여기에 표시합니다.
Mole Agent는 인시던트와 함께 최신 메모를 읽습니다.

## AI 근본 원인 분석

Mole Agent에 모델 제공업체를 설정하면 새 인시던트를 백그라운드에서 분석하고
근거를 바탕으로 도출한 결과를 인시던트에 저장합니다. **생성**을 선택하면 즉시 분석을 요청하고,
**다시 생성**을 선택하면 기존 결과를 교체합니다. **도움이 됨** 또는 **도움이 되지 않음**으로 결과를 평가합니다. 평가는
[품질](/ko/quality)에 반영됩니다.

분석 결과를 생성하려면 Mole Agent 권한이 필요합니다. 조직의 일일 Mole Agent 토큰 예산을
모두 소진하면 자동 분석을 일시 중지하고, 요청 시 생성에는 예산 설정을 적용합니다.
[사용량 및 예산](/ko/agent#사용량-및-예산)을 참조합니다.

## 유사 인시던트 및 최근 변경 사항

**유사 인시던트**는 조직에서 지난 90일 동안 발생한 인시던트 중 현재 인시던트와 가장 유사한 항목을
최대 5개까지 찾고 이유를 표시합니다. 이유는 **동일한 경고**(동일한 지문), **동일한 규칙**, **동일한 서비스**,
**유사한 레이블**, **유사한 제목**(중국어 제목 포함), **동일한 팀**입니다. 각 항목에는 인시던트의
지속 시간, 해결 담당자, 메모 수, AI 근본 원인 분석의 첫 문장을 표시합니다. 이를 통해
인시던트 담당자는 이전 대응 방식을 확인할 수 있습니다.

**최근 변경 사항**은 인시던트가 트리거되기 30분 전부터
트리거된 후 10분까지 인시던트 관련 서비스와 서비스 맵에서 해당 서비스의 다운스트림에 있는 서비스에 대해
[보고된 변경 사항](/ko/apm/deployments#ci에서-배포-보고)을 나열합니다. 배포(실패 및 롤백 표시), 구성 변경,
기능 플래그를 나열하고, 다운스트림 변경에는 표시를 추가하며 파이프라인 링크가 있으면 함께 표시합니다. 인시던트가
트리거되기 전 24시간 이내에 해당 규칙을 수정했다면 규칙도 나열합니다. 서비스 맵이 없으면
인시던트에 직접 연결된 서비스만 포함합니다.

## 인시던트 그룹

[시맨틱 그룹](/ko/alerting/silences#시맨틱-그룹)은 관련 인시던트를 하나의 그룹으로 묶습니다. 예를 들어
한 서비스의 모든 심각 인시던트를 묶을 수 있습니다. 그룹을 확인하거나 해결할 때
`POST /api/v1/alerts/incident_groups/{id}/ack` 또는 `/resolve`를 사용하면 그룹의 모든 인시던트에 같은 작업을 적용합니다.

## 기록

**알림 → 기록**에는 과거 인시던트의 현재 상태, 발생 및
복구 시각, 지속 시간이 표시됩니다. 인시던트, 서비스 또는 인시던트 ID로 검색하고
심각도와 상태로 필터링합니다.

## 인사이트

**알림 → 인사이트**는 최근 24시간, 7일 또는 30일 동안의 워크스페이스 대응 현황을 보여 줍니다.

| 항목 | 표시 내용 |
|---|---|
| 요약 | 아직 대응이 필요한 인시던트 수, 복구된 인시던트의 **평균 복구 시간**, 60초 이내에 복구된 인시던트의 비율인 **빠른 복구**를 표시합니다. 빠른 복구 비율이 높으면 규칙이 불필요한 알림을 자주 발생시킨다는 신호일 수 있습니다. |
| **인시던트 타임라인** | 브라우저의 시간대를 기준으로 24시간 범위에서는 시간별로, 더 긴 범위에서는 일별로 인시던트 수와 최댓값을 표시합니다. |
| **가장 많이 영향을 받은 서비스** | 인시던트에 가장 자주 표시된 서비스를 보여 줍니다. 이 항목을 표시하려면 규칙에 `service` 레이블이 필요합니다. |
| **인시던트를 가장 많이 생성한 규칙** | 인시던트를 가장 많이 생성한 규칙을 표시합니다. 이 규칙부터 조정합니다. |
| **응답** | 평균 인시던트 인수 시간(P50 및 P90 포함), 복구 시간의 중앙값, 에스컬레이션 비율, 인수된 인시던트 비율을 직전의 동일한 길이의 기간과 비교합니다. 에스컬레이션 단계별 확인 비율과 최초 인수 채널(웹, API, 채팅 카드, SMS 답장, 전화 키 입력 또는 Mole Agent)도 표시합니다. 팀, 서비스, 담당자, 우선순위별로 인수, 복구, 에스컬레이션 지표를 구분해 표시합니다(우선순위가 없는 인시던트는 제외). 최초 확인 시점을 인수 시점으로 간주합니다. 확인 없이 담당자가 인시던트를 해결하면 해결 시점을 인수 시점으로 간주합니다. |
| **온콜 업무량** | 담당자별 온콜 근무 시간, 수신한 알림 수, 야간(담당자 일정의 시간대 기준 22:00~08:00) 또는 주말에 수신한 알림 수, 알림으로 방해받은 야간 횟수, 최초로 인수한 인시던트 수와 인수까지 걸린 시간을 표시합니다. 일정 상세 정보에서도 구성원별로 같은 지표를 확인할 수 있습니다. |
