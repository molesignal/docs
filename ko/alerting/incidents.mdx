인시던트는 [규칙](/ko/alerting/rules)이 트리거되거나 [합성 검사가 실패](/ko/synthetics#알림-인시던트)하거나 [알림 소스](/ko/alerting/sources)가 외부 알림을 수신할 때 개설됩니다. 인시던트는 규칙, 값,
레이블 및 종료될 때까지의 모든 단계를 기록합니다. **알림 → 인시던트**를 열거나 `⌘⌥A`를 누릅니다. 인시던트를 읽으려면
`alerts.incidents.read` 권한이 필요합니다. 확인, 해결 및 일시 중지는
`alerts.incidents.acknowledge` 권한이 필요합니다. [인시던트 조치](#인시던트에-대한-조치)의 다른 작업에는
`alerts.incidents.update` 권한이 필요하며, 에스컬레이션 및 병합에는 `alerts.incidents.escalate` 권한이 필요합니다. 알림 음소거에는 `alerts.incidents.silence` 권한이 필요합니다. 수신한 알림은
Feishu 앱 또는 Slack 앱을 통해 카드에서도 확인, 해결 또는 일시 중지할 수 있습니다. 다음을 참조하세요
[알림 카드](/ko/im#알림-카드). 문자 메시지나 전화에는 코드 또는 키로 응답할 수 있습니다. 다음을 참조하세요
[문자 및 전화 응답](/ko/notification-channels#문자-메시지와-전화로-경보-처리).

## 인시던트 상태

| 상태 | 목록 레이블 | 의미 |
|---|---|---|
| `open` | **대기 중** | 발생 중이며 아직 아무도 확인하지 않았습니다. 에스컬레이션이 계속됩니다. |
| `acknowledged` | **진행 중** | 누군가 담당하고 있습니다. 에스컬레이션이 중지됩니다. |
| `resolved` | **복구됨** | 종료됨: 규칙이 복구되었거나 누군가 해결했습니다. |
| `closed` | **종료됨** | 종료되었습니다. |

`open` 상태의 인시던트는 규칙이 [복구 조건](/ko/alerting/rules#복구-및-데이터-누락)을 충족하면 자동으로 해결됩니다.
확인된 인시던트는 누군가 해결할 때까지 확인된 상태로 유지됩니다. 해당 에스컬레이션 정책이
[확인되었지만 해결되지 않음](/ko/alerting/on-call#확인-후-미해결-상태)을 설정하면 해당 시간이 지난 후
**대기 중**으로 돌아가며 다시 호출됩니다. 일시 중지된 인시던트는 **진행 중**입니다. 외부
소스의 인시던트는 확인 여부와 관계없이 소스가 복구를 보고하면 해결됩니다. 다음을 참조하세요
[알림이 인시던트가 되는 방식](/ko/alerting/sources#경보가-인시던트가-되는-방식). 각 규칙 또는 분할된 규칙의
각 그룹은 한 번에 최대 하나의 활성 인시던트를 가집니다.

## 인시던트 목록

**인시던트** 페이지 상단에는 영향을 받은 서비스 수, 확인을 기다리는 인시던트 수,
지난 24시간 동안 복구된 인시던트 수가 표시됩니다. 요약에는 현재 발생 중인 인시던트 수, 가장 오래된 인시던트의
발생 지속 시간과 평가 중인 규칙 수가 표시됩니다. **최근 복구된 인시던트**에는 최근에 종료된
인시던트가 나열됩니다.

**발생 중**과 **대기 중** 간에 전환할 수 있으며, **대기 중**은 아직 담당자가 없는 인시던트입니다. 현재 사용자가
팀에 속해 있으면 **내 팀**에는 해당 팀으로 [라우팅된](/ko/alerting/routing) 인시던트가 나열됩니다. 오른쪽에서
우선순위로 필터링하거나 **없음**에 해당하는 인시던트를 표시할 수 있습니다. 인시던트는 심각도, 그다음
우선순위, 그다음 발생 지속 시간 순으로 나열됩니다. 각 행에는 심각도, 인시던트 및 해당
서비스(긴급도가 낮은 인시던트에는 **낮은 긴급도** 표시), 우선순위, 상태, 지속 시간,
담당자와 라우팅된 팀이 표시되며, 세 가지 작업이 있습니다:

| 작업 | 효과 |
|---|---|
| **확인** | 소유권을 가져갑니다. 인시던트가 **진행 중**이 되고 에스컬레이션이 중지됩니다. |
| **알림 음소거** | 이 인시던트에 한해 추가 알림과 에스컬레이션을 일시 중지합니다. [단일 인시던트 음소거](/ko/alerting/silences#단일-인시던트-음소거) 참조. |
| **런북** | 규칙에 대응 가이드가 있으면 해당 가이드를 엽니다. |

행을 선택하거나 헤더에서 전체를 선택하면 목록 위에 일괄 작업 표시줄이 나타납니다:
**확인**, **해결**, **일시 중지**, **재할당**, **조정**(심각도, 우선순위 또는 긴급도) 및
두 개 이상 선택한 경우
**병합**이 표시되며, 유지할 인시던트를 묻습니다. 한 요청으로 최대 100개의 인시던트를 처리할 수 있습니다. 처리할 수
없는 인시던트(예: 복구된 인시던트)는 첫 번째 사유로 집계되며, 나머지는
처리됩니다.

### 수동으로 인시던트 개설

규칙이 포착하지 못한 문제(예: 고객의 신고 또는 누군가 목격한 상황)에도 인시던트를 만들 수 있으며,
다른 인시던트와 마찬가지로 호출 및 에스컬레이션이 수행됩니다. 목록 위에서 **새 인시던트**를 선택합니다(`alerts.incidents.create`):

1. **발생 내용**에서 **제목**(필수)과 **설명**(Markdown 사용 가능)을 입력하고,
   **심각도**(기본값: error), **우선순위**, **긴급도**(기본값: 에스컬레이션 정책에
   따름)를 선택합니다. 선택적으로 **영향을 받은 서비스**를 쉼표로 구분하여 입력하고, **레이블**은
   `key=value` 형식으로 한 줄에 하나씩 입력합니다.
2. **담당자 지정**에서 다음 중 하나를 선택합니다:

   | 선택지 | 효과 |
   |---|---|
   | **자동 라우팅** | 규칙의 인시던트와 마찬가지로 [알림 라우팅](/ko/alerting/routing)으로 라우팅됩니다. |
   | **팀 지정** | 해당 팀의 온콜 정책 또는 기본 정책을 사용합니다. |
   | **에스컬레이션 정책** | 정책의 1단계부터 알림을 받습니다. |
   | **지정된 사용자** | 에스컬레이션 정책 없이 최대 10명에게 직접 알림을 보냅니다. |

3. 선택적으로 **중대 인시던트 선언**을 선택한 다음 **인시던트 생성**을 선택하면 인시던트 페이지가
   열립니다.

수동으로 개설한 인시던트에는 `alert.source=manual` 레이블, 개설자를 나타내는 `created_by`
주석과 `description` 주석에 설명을 포함합니다. 알림 파이프라인을 건너뛰고, 다른 인시던트와
중복 제거되지 않으며, 자체적으로 복구되지 않습니다. 누군가 해결해야 합니다. 해당 페이지의 **개설자**에는
개설한 사람이 표시됩니다. 인사이트에서는 이러한 인시던트를 **수동 생성**으로 함께 집계합니다. Mole Agent의
`create_incident` 도구도 승인 한 번으로 인시던트를 개설합니다.

## 인시던트 상세 정보

인시던트를 선택해 상세 정보를 엽니다. 상단에는 상태, 발생 시각, 규칙, 발생 경과 시간이 표시되며,
**확인**, **해결**, **추가 작업**이 있고, **추가 작업**에는
[인시던트에 대한 조치](#인시던트에-대한-조치)의 작업과 **알림 음소거**가 포함됩니다.

| 섹션 | 내용 |
|---|---|
| **타임라인** | 발생 시점, 알림을 받은 사람, 수행한 작업(확인, 재할당, 대응 담당자 추가, 에스컬레이션, 일시 중지, 심각도 변경, 병합, 해결, 그리고 문제 해결, 티켓, 주요 인시던트의 단계), 인시던트가 열리기 전에 [알림 파이프라인](/ko/pipelines/alert-events#이벤트-처리-결과)이 변경한 사항, 그리고 수행 위치(API, 채팅, SMS 답장, 전화 키 입력, Mole Agent)와 그 사이의 시간이 표시됩니다. 타임라인 하단에는 [노트](#노트)가 추가되며, 이 인시던트에 병합된 인시던트는 그 아래에 나열됩니다. |
| **조사** | **트리거 쿼리 열기**는 해당 탐색기에서 정확한 쿼리를 다시 실행합니다. **관련 로그**와 **관련 메트릭**은 같은 시간 범위에서 영향을 받은 컨텍스트를 엽니다. RUM 수치의 인시던트에는 **RUM에서 열기**가 있습니다. |
| **조사 가이드** | 규칙의 [조사 가이드](/ko/alerting/rules#조사-가이드)가 요청하는 내용, 즉 단계, 인시던트의 시간 범위에 걸쳐 실행되는 쿼리, 대시보드가 표시됩니다. 규칙에 가이드가 있을 때만 표시됩니다. |
| **AI 근본 원인 분석** | Mole Agent의 분석입니다. [AI 근본 원인 분석](#ai-근본-원인)을 참조하세요. |
| **신호 간 연결 정보** | 증거에서 찾은 서비스, 트레이스 ID, 호스트이며, 각각 링크입니다. |
| **트리거 쿼리** | 쿼리와 쿼리가 반환한 값입니다. **샘플 값 보기**는 샘플 행을 표시합니다. |
| **메타데이터** | 인시던트의 레이블과 어노테이션입니다. |
| **담당자** | 에스컬레이션이 도달한 사람과 인시던트가 [라우팅](/ko/alerting/routing#인시던트의-라우팅-정보)된 팀 및 그 이유, 일시 중지, 다른 인시던트로의 병합, 수동으로 설정한 심각도가 여기에 기록됩니다. |
| **영향 범위** | 서비스를 지정한 인시던트의 경우, 서비스 맵을 따라 해당 서비스가 도달하는 범위입니다. [인시던트의 영향 범위](/ko/apm/insights#인시던트의-영향-범위)를 참조하세요. |
| **비즈니스 영향** | 각 [비즈니스 키](/ko/business-context)에 대해, 트리거 시점 전후로 인시던트의 서비스에 대한 요청이 가장 많이 실패한 값(테넌트, 플랜)과 플래그가 지정된 중요한 값을 표시하며, 각 값은 Traces 페이지에서 해당 요청을 엽니다. `streams.query` 또는 `sys.telemetry.read` 권한이 있는 사용자에게 표시됩니다. |
| **샘플 세션** | RUM 수치의 인시던트의 경우, 해당 수치를 보여 주는 세션과 각 세션의 리플레이가 표시됩니다. [RUM 알림](/ko/rum/alerts#인시던트)을 참조하세요. |
| **유사 인시던트** | 지난 90일 동안 이 인시던트와 유사한 인시던트와 그 종료 방식입니다. [유사 인시던트와 최근 변경 사항](#유사-인시던트-및-최근-변경-사항)을 참조하세요. |
| **최근 변경 사항** | 트리거 시점 전후에 해당 서비스와 다운스트림 서비스에 대해 보고된 배포, 구성 변경, 기능 플래그와, 전날 편집된 경우 해당 규칙입니다. |
| **문제 해결** | 인시던트에 적용되는 문제 해결 작업과 요청된 실행 및 승인입니다. [문제 해결](/ko/alerting/remediation)을 참조하세요. |
| **티켓** | 인시던트의 Jira 또는 Feishu Project 티켓과 상태이며, 여기에서 티켓을 만들 수 있습니다. [티켓](/ko/alerting/tickets)을 참조하세요. |
| **주요 인시던트** | 주요 인시던트를 선언하고, 역할을 할당하고, 워룸과 회의에 참여하고, 작업을 태스크로 나누고, 업데이트를 게시합니다. [주요 인시던트와 사후 분석](/ko/alerting/major-incidents)을 참조하세요. |
| **사후 분석** | 인시던트의 내부 사후 분석입니다. **사후 분석 작성**은 템플릿에서 초안을 작성하고, **사후 분석 열기**는 작성을 이어 갑니다. [사후 분석](/ko/alerting/major-incidents#사후-분석)을 참조하세요. |

## 인시던트에 대한 조치

**추가 작업**의 모든 작업은 타임라인에 기록되며 다음을 통해서도 사용할 수 있습니다.
[API](#인시던트-api). Mole Agent도 이러한 작업을 수행할 수 있습니다. 노트를 추가하려면 요청한 사람의
확인이 필요하고, 나머지는 한 번의 승인이면 됩니다. [승인 및 실행](/ko/agent#승인-및-실행)을 참조하세요.
Mole Agent는 티켓을 만들고, 주요 인시던트 역할을 할당하고, 태스크를 추가하고, 사후 분석 초안을 작성할 수 있습니다(요청한 사람의
확인이 필요함). 또한 주요 인시던트를 선언하고 업데이트를 게시하며(한 번의 승인 필요),
문제 해결 실행을 제안할 수 있습니다(두 번의 승인이 필요하며, [사전 승인](/ko/alerting/remediation#사전-승인)이 해당 실행을 포함하는 경우는 예외입니다).
복구된 인시던트와 다른 인시던트로 병합된 인시던트에는 더 이상 이 방식으로 조치할 수 없지만,
[노트](#노트)는 계속 추가할 수 있습니다.

| 작업 | 효과 |
|---|---|
| **재할당** | 개인에게: 최대 10명까지 지정할 수 있으며, 이들은 담당자가 되어 알림을 받고, 인시던트는 **대기 중**으로 돌아가며, 아무도 확인하지 않으면 에스컬레이션이 계속됩니다. 팀에게: 팀의 온콜 정책 또는 팀에 정책이 없으면 기본 정책이 1단계부터 다시 시작됩니다. 에스컬레이션 정책으로: 해당 정책이 1단계부터 다시 시작되고 팀은 유지됩니다. 재할당 시 노트를 함께 타임라인에 남길 수 있습니다. |
| **대응 담당자 추가** | 선택한 사람이 담당자에 합류하고 알림을 받으며, 상태는 그대로 유지됩니다. |
| **지금 에스컬레이션** | 선택한 단계의 대상에게 즉시 알림을 보내며, 기본값은 다음 단계입니다. 인시던트의 심각도에 적용되는 단계만 나열됩니다. 확인된 인시던트는 **대기 중**으로 돌아갑니다. |
| **일시 중지** | 1, 4, 8, 24시간 또는 **사용자 지정…**(1분~7일)입니다. 대기 중인 인시던트는 먼저 확인되며, 일시 중지 중에는 아무것도 전송되지 않고, 일시 중지가 끝나면 인시던트는 **대기 중**으로 돌아가 담당자에게 다시 알림이 전송됩니다. **일시 중지 해제**는 일시 중지를 즉시 종료합니다. |
| **심각도** | 수동으로 설정하면 규칙, 알림 소스, 합성 검사 모두 더 이상 심각도를 변경하지 않습니다. 대기 중인 인시던트의 심각도를 높이면 새 심각도로 1단계부터 다시 알림이 전송되고, 낮추면 심각도만 변경됩니다. |
| **우선순위** | 조직의 [우선순위 수준](/ko/alerting/on-call#긴급도-및-우선순위-수준) 중 하나이며, 기본값은 P1~P5 또는 **없음**입니다. 우선순위만 변경하고 누구에게도 다시 알리지 않습니다. 우선순위는 목록의 열과 필터, [라우팅 규칙](/ko/alerting/routing)의 조건, 자동 주요 인시던트, 티켓의 우선순위 매핑, 인사이트에 사용됩니다. |
| **긴급도** | **높은 긴급도** 또는 **낮은 긴급도**이며, [긴급도](/ko/alerting/on-call#긴급도)를 참조하세요. 대기 중인 인시던트의 긴급도를 높은 긴급도로 올리면 1단계부터 다시 알림이 전송되고, 낮추면 긴급도만 변경되고 추가 에스컬레이션이 중지됩니다. 수동으로 설정하면 지원 시간이 더 이상 긴급도를 변경하지 않습니다. |
| **병합** | 다른 활성 인시던트를 이 인시던트로 병합합니다. [인시던트 병합](#인시던트-병합)을 참조하세요. |
| **알림 음소거** | [인시던트 하나 음소거](/ko/alerting/silences#단일-인시던트-음소거)를 참조하세요. |

이 작업들이 보내는 알림은 에스컬레이션 알림이며, 템플릿의 `{{escalation.reason}}`은 그 이유를
다음과 같이 나타냅니다: `reassigned`, `responder_added`, `manual`(지금 에스컬레이션), `snooze_ended`,
`severity_raised`, `urgency_raised`, `ack_timeout`(확인되었지만 너무 오래 해결되지 않음). 템플릿은
`{{urgency}}`와 `{{priority}}`도 받습니다. 다음을 참조하세요:
[템플릿 변수](/ko/notification-channels#템플릿-변수).

### 인시던트 병합

하나의 문제가 여러 인시던트를 열 때, 예를 들어 장애가 여러 규칙을 트리거할 때는 이들을
하나의 주요 인시던트로 병합합니다. 병합된 인시던트는 더 이상 자체적으로 알림을 보내거나 에스컬레이션하지 않고, 더 이상
인시던트 목록이나 인사이트에 표시되지 않으며, 주요 인시던트의 타임라인 아래에 나열됩니다. 주요 인시던트를 해결하면
병합된 인시던트도 해결됩니다. 병합된 인시던트가 먼저 복구되면 주요 인시던트의 타임라인에
그 사실이 기록됩니다. 한 번에 최대 50개의 인시던트를 병합할 수 있으며, 병합은 취소할 수 없습니다.

상세 정보에서 **추가 작업 → 병합**에서 병합할 인시던트를 체크하고, 인시던트 목록에서는
여러 개를 체크한 뒤 **병합**을 선택하고 주요 인시던트를 선택합니다.

### 노트

타임라인 하단의 상자에 발견한 내용과 수행한 작업을 최대 4,000자까지 노트로 추가하여,
인수인계하는 사람이 즉시 볼 수 있게 합니다. 재할당과 함께 작성한 노트도 여기에 표시됩니다. Mole
Agent는 인시던트와 함께 최신 노트를 읽습니다.

## AI 근본 원인

Mole Agent에 모델 제공자가 설정되면 백그라운드에서 새 인시던트를 분석하고
인시던트와 함께 근거 기반 결과를 저장합니다. **생성**은 이를 즉시 요청하며,
**다시 생성**은 기존 결과를 대체합니다. 결과는 **도움이 됨** 또는 **도움이 되지 않음**으로 평가하며, 평가는
[품질](/ko/quality)로 이어집니다.

분석은 레이블이 지정된 근거로 작성되며, 인시던트의 서비스와 해당 서비스가
호출하는 서비스에 대해 시작 30분 전부터 10분 후까지의 데이터를 읽습니다:

| 근거 | 설명 |
|---|---|
| **APM 인사이트** | 이전 기간 및 일주일 전과 비교해 변동한 수치, 성능이 회귀한 버전 또는 시간이 어디에 쓰이는지입니다. |
| **새 오류 그룹** | 해당 기간에 처음 발견된 오류 그룹과 발생 횟수입니다. |
| **샘플 트레이스** | APM이 예시로 보관한 트레이스 중 가장 느린 트레이스와 해당 소요 시간입니다. |
| **오류 로그** | 일주일 전 동일한 기간과 비교한 서비스의 오류 수준 로그 라인입니다. |
| **새 오류 로그 패턴** | 인시던트 서비스의 오류 수준 로그에서 바로 직전 동일 길이 기간에는 없었던 메시지 패턴을 해당 기간의 라인과 함께 표시하며, 최대 3개입니다. |
| **실패한 요청이 다른 지점** | 실패한 요청이 다른 요청과 달리 보이는 필드 값과, 실패한 요청이 집중되는 값 및 각 값의 비중입니다. 샘플에서 최대 3개입니다. |
| **비즈니스 영향** | 각 비즈니스 키에 대해 요청이 실패한 값과 실패 건수를 표시하며, 중요한 값부터 나열합니다. |
| **변경** | 보고된 배포, 구성 변경, 기능 플래그 또는 경고 규칙 편집입니다. |
| **유사 인시던트** | 이 인시던트와 유사한 과거 인시던트입니다. |

분석은 각 주장을 **[E2]** 같은 레이블로 인용하고, 근거가
뒷받침하지 않는 원인은 추측으로 표시합니다. 분석 아래의 **근거**는 각 항목을 나열하며, 각 항목을 열면
출처가 표시됩니다. APM, 트레이스 또는 로그에서 읽은 수치는 해당 데이터를 읽을 권한이 있는 독자에게만 표시되며, 그렇지 않은 독자에게는
해당 항목의 주제와 **수치 숨김**이 표시됩니다. Mole Agent
조사에서 다시 작성된 분석은 조사가 인용한 내용을 나열합니다.

생성하려면 Mole Agent 권한이 필요합니다. 조직의 일일 Mole Agent 토큰 예산이
모두 사용되면 자동 분석이 일시 중지되고, 요청 시 생성은 예산 설정을 따릅니다. 자세한 내용은
[사용량 및 예산](/ko/agent#사용량-및-예산)을 참조하세요.

## 유사 인시던트 및 최근 변경 사항

**유사 인시던트**는 조직에서 지난 90일 동안 이 인시던트와 가장 유사한 인시던트를
최대 5개 찾고 그 이유를 표시합니다: **동일한 경고**(동일한 지문), **동일한 규칙**, **동일한 서비스**,
**유사한 레이블**, **유사한 제목**(중국어 제목 포함) 또는 **동일한 팀**입니다. 각 항목에는 지속
시간, 해결한 사람, 노트 수, AI 근본 원인의 첫 문장이 표시되어, 인시던트를
인수하는 사람이 이전에 어떻게 처리되었는지 확인할 수 있습니다.

**최근 변경 사항**은 [보고된 변경 사항](/ko/apm/deployments#ci에서-배포-보고)을 트리거
30분 전부터 10분 후까지, 인시던트의 서비스와 서비스 맵에서 해당 서비스의 다운스트림에 있는
서비스에 대해 나열합니다: 배포(실패 및 롤백된 배포는 표시됨), 구성 변경,
기능 플래그를 포함하며, 다운스트림일 때 표시되고 파이프라인 링크가 있으면 함께 표시합니다. 인시던트의
규칙은 트리거 전날에 편집된 경우에도 나열됩니다. 서비스 맵이 없으면
인시던트 자체 서비스만 집계합니다.

## 인시던트 그룹

[시맨틱 그룹](/ko/alerting/silences#시맨틱-그룹)은 관련 인시던트를, 예를 들어 한 서비스의 모든
심각 인시던트를 하나의 그룹으로 묶습니다. 그룹을
`POST /api/v1/alerts/incident_groups/{id}/ack` 또는 `/resolve`로 확인하거나 해결하면 모든 구성원에 동일하게 적용됩니다.

## 기록

**알림 → 기록**은 과거 인시던트를 현재 상태, 발생 및
복구 시각, 지속 시간과 함께 나열합니다. 인시던트, 서비스 또는 인시던트 ID로 검색하고
심각도 및 상태로 필터링합니다.

## 변경

**알림 → 변경**은 지난 24시간, 7일 또는 30일의 모든 변경 사항을 최신순으로 나열합니다:
파이프라인이 보고하는 배포, 구성 변경, 기능 플래그, 스케일링, 인프라 변경,
주석, APM이 스팬에서 처음 확인한 버전, 경고 규칙 편집이 포함됩니다. 각 유형은
권한이 허용하는 범위까지 표시됩니다. 목록 위의 레일은 범위 전체의 변경 사항을 표시하며,
변경 표시 위에 마우스를 올리면 누가 무엇을 변경했는지, 커밋, 풀 리퀘스트, CI 실행을 확인할 수 있습니다. 유형별로 필터링하고
서비스, 버전, 제목, 작성자 또는 커밋으로 검색합니다. 동일한 변경 사항은 로그 및
트레이스의 히스토그램과 메트릭 차트 아래에 표시됩니다. [`GET /api/v1/changes`](/ko/api/changes)를 참조하세요.

## 인사이트

**알림 → 인사이트**는 지난 24시간, 7일 또는 30일 동안 워크스페이스가 어떻게 대응하는지 보여줍니다:

| 항목 | 표시 내용 |
|---|---|
| 요약 | 아직 주의가 필요한 인시던트 수, 복구된 인시던트의 **평균 복구 시간**, **빠른 복구**: 60초 이내에 복구된 비율(노이즈가 많은 규칙의 징후)을 표시합니다. |
| **인시던트 타임라인** | 24시간 범위는 시간별로, 더 긴 범위는 일별로 브라우저 시간대에 따라 인시던트를 표시하며 최고점도 함께 표시합니다. |
| **가장 많이 영향을 받은 서비스** | 인시던트에서 가장 자주 언급되는 서비스입니다. 이를 위해서는 규칙에 `service` 레이블이 필요합니다. |
| **인시던트를 가장 많이 생성한 규칙** | 인시던트를 가장 많이 생성한 규칙입니다. 여기서부터 튜닝을 시작하세요. |
| **응답** | 인시던트를 인수하는 데 걸리는 평균 시간(P50 및 P90 포함), 복구까지 걸리는 중앙값 시간, 에스컬레이션 비율, 누군가 인수한 비율을 이전 동일 기간과 비교해 표시하고, 각 에스컬레이션 단계의 확인 비율, 인시던트를 처음 인수한 위치(웹, API, 채팅 카드, SMS 답장, 전화 키 입력 또는 Mole Agent), 팀, 서비스, 담당자, 우선순위별로 분할한 인수, 복구 및 에스컬레이션(우선순위가 없는 인시던트는 제외)을 표시합니다. 인시던트 인수는 첫 번째 확인을 의미하며, 확인 없이 사람이 해결한 인시던트는 해결된 시점에 집계됩니다. |
| **온콜 업무량** | 각 담당자가 온콜에 있었던 시간, 각자 받은 경고 알림 수, 야간(담당자의 스케줄 시간대 기준 22:00~08:00) 또는 주말에 도착한 알림 수, 방해받은 야간 수, 각자 처음 인수한 인시던트 수와 인수 속도를 표시합니다. 스케줄 세부 정보에서도 구성원에 대해 동일한 내용을 표시합니다. |
