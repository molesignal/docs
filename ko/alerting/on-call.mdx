에스컬레이션 정책은 인시던트 알림을 받을 대상과 알림 순서를 결정합니다. 각 단계에는
사용자, 팀 또는 온콜 일정을 지정할 수 있습니다. 온콜 일정을 지정하면 특정 사용자가 아니라 교대 일정에 따라 알림을 보냅니다. 다음 메뉴를 엽니다.
**알림 → 온콜 일정** 및 **알림 → 에스컬레이션**. 조회하려면 `schedules.read`와
`alerts.escalations.read`가 필요합니다. 일정을 생성, 수정, 삭제하려면 각각 `schedules.create`, `schedules.update`, `schedules.delete`가 필요하며, 정책을 변경하려면
`alerts.escalations.manage`가 필요합니다.

## 인시던트 알림 전달 방식

1. 규칙이 발동하면 인시던트가 열립니다. 인시던트에는 규칙의 에스컬레이션 정책을 적용합니다. 규칙이 기본 정책을 사용하면
   [알림 라우팅](/ko/alerting/routing)에서 적용할 정책을 선택합니다.
2. 정책의 1단계를 실행합니다. 각 대상에 알림 이벤트를 보냅니다. 대상이 사용자이면 해당 사용자에게,
   온콜 일정이면 현재 온콜 담당자에게, 팀이면 팀 전체에 보냅니다.
3. [알림 정책](/ko/notification-channels#템플릿-및-정책-만들기)은 각 이벤트의 전달 방식을 결정합니다.
   사용할 커넥터, 사용자별 전달 순서, 대체 경로를 지정합니다.
4. 해당 단계의 **확인 대기 시간** 내에 아무도 인시던트를 확인하지 않으면 다음 단계를 실행합니다. 인시던트를
   확인하거나 해결할 때까지, 또는 모든 단계를 실행할 때까지 반복합니다.
   [확인 후 미해결](#확인-후-미해결-상태)을 설정하면 확인한 인시던트가 해결되지 않은 경우
   미확인 상태로 되돌리고 알림을 다시 보냅니다.

인시던트에 적용되는 알림 음소거가 활성 상태인 동안에는 에스컬레이션을 일시 중지합니다. 음소거가 종료되면 에스컬레이션을
재개합니다. [음소거 중 알림](/ko/alerting/silences#음소거-중-알림)을 참조합니다.
`alert` 노드가 여러 개면 각 규칙은 하나의 노드에 속하며, 해당 노드가 그 규칙에서 발생한 인시던트의
에스컬레이션도 처리합니다. 다음 문서를 참조합니다.
[역할 기반 배포](/ko/deployment/role-based#알림-노드-간-작업-분담).

## 온콜 일정

**온콜 일정**에는 각 일정의 시간대, 교대, 멤버, 현재 당번,
다음 인계, 상태가 표시됩니다. 상단에는 일정, 현재 당번, 이번 주 인계,
임시 당번 요약이 표시됩니다. 일정, 팀, 소유자, 시간대 또는 상태로 필터링하거나
**내가 참여하는 일정만** 표시합니다. 목록 위의 **내 근무 구독**을 선택하면 현재 계정의 모든 일정에 걸친
근무를 캘린더 앱에 추가할 수 있습니다. [캘린더 구독](#캘린더-구독)을 참조합니다.
**근무 교대**에는 현재 계정에서 보낸 요청과 받은 요청이 표시되며,
응답 대기 중인 요청 수도 확인할 수 있습니다. [근무 교대](#근무-교대)를 참조합니다.

| 상태 | 의미 |
|---|---|
| **활성** | 현재 당번이 있습니다. |
| **교대 임박** | 2시간 이내에 인계합니다. |
| **시작 전** | 첫 교대가 아직 시작되지 않았습니다. |
| **일시 중지됨** | 일정이 일시 중지되어 당번을 배정하지 않습니다. |
| **당번 공백** | 현재 당번이 없습니다. |

### 일정 생성

1. **새 일정**을 선택합니다.
2. **기본 정보**에서 **일정 이름**, **설명**,
   **시간대**(예: `Asia/Shanghai`), **팀**을 입력합니다.
3. **교대 규칙**에서 각 교대를 설정합니다.

   | 필드 | 용도 |
   |---|---|
   | 교대 이름 | 예: `primary`. |
   | **교대 주기** | **매일**, **매주**, **근무일**(월요일부터 금요일까지 매일) 또는 **사용자 지정 주기**를 선택합니다. **사용자 지정 주기**에는 **주기 (시간)**를 지정합니다. |
   | **시작 날짜 및 시간**, **인계 시간** | 교대를 시작하는 날짜 및 시간과 당번이 바뀌는 시각을 지정합니다. |
   | **지정된 시간에 종료** | 선택 사항입니다. **종료 날짜 및 시간**이 지나면 이 교대에서 당번을 배정하지 않습니다. |
   | **멤버(순서대로 교대)** | 당번을 맡을 순서대로 멤버를 지정합니다. |
   | **특정 요일 및 시간대로 제한** | 한 주의 일부 시간대에만 당번을 배정합니다. 각 범위의 **요일**, **시작 시간 (HH:MM)**, **종료 시간 (HH:MM)**을 일정의 시간대 기준으로 분 단위까지 지정합니다. **시간 범위 추가**를 선택하면 9:30–12:00과 13:30–18:00처럼 여러 범위를 지정할 수 있습니다. 종료 시간이 시작 시간과 같거나 더 이르면 범위가 자정을 넘어가며, 시작한 요일에 속합니다. 하루 전체는 00:00–24:00으로 지정합니다. |
   | **공휴일** | **공휴일 캘린더**를 기준으로 **공휴일 여부 무시**(기본값), **공휴일 제외**, **공휴일에만 적용** 중 하나를 선택합니다. [공휴일 캘린더](#휴일-캘린더)를 참조합니다. 공휴일을 제외하는 평일 교대 아래에 공휴일 전용 교대를 추가하면 공휴일에도 당번을 배정할 수 있습니다. |

4. 필요하면 **근무 교환에 승인 필요**를 켭니다. 요청을 받은 멤버가 수락한 후
   일정 관리자가 승인해야 교대가 적용됩니다.
5. **향후 7일**에서 교대 순서, 인계 시간, 당번을 미리 확인합니다.
6. **일정 생성**을 선택하거나, 일시 중지 상태로 유지하려면 **초안 저장**을 선택합니다.

여러 교대가 같은 시간에 겹치면 목록에서 당번이 있는 첫 번째 교대가
당번을 결정합니다. 야간이나 주말에 별도 당번을 배정하려면 첫 번째 교대 아래에 두 번째 교대를 추가합니다.

인계는 일정에 설정한 시간대의 현지 시각을 따릅니다. 뉴욕에서 09:00에 인계하는 교대는
연중 09:00에 인계하며, 일광 절약 시간 전환을 포함하는 근무는 23시간 또는 25시간 동안 이어집니다.
시계를 앞으로 돌릴 때 건너뛰는 시간대에 인계 시각이 있으면, 건너뛴 직후에 인계합니다.
시계를 뒤로 돌릴 때 반복되는 시간대에 인계 시각이 있으면, 두 시각 중 이른 시각에 인계합니다.
서버는 미리 보기, 타임라인, 캘린더 구독, 온콜 업무량에 모두 동일한 계산 방식을 적용합니다.

### 임시 당번

휴가, 근무 교대 또는 인시던트가 발생하면 임시 재정의로 정해진 시간 동안 한 멤버에게
온콜을 맡길 수 있습니다. 일정에서 **재정의 추가**를 선택하고 **대체 근무자**를 지정한 다음,
**사유**, **시작 시간**, **종료 시간**을 입력하고 저장합니다. 재정의가 적용되는 동안에는
모든 교대보다 우선합니다.

같은 일정에서 두 재정의는 겹칠 수 없습니다. 시작 시간에 대체 근무자가 다른 일정의 당번이거나
시작 시간이 이미 지나 재정의가 즉시 적용되는 경우, 양식에 경고가 표시됩니다.
**대체 근무 종료**를 선택하면 진행 중인 재정의를 조기에 종료합니다.

### 근무 교대

근무 교대를 사용하면 관리자에게 재정의를 요청하지 않고 같은 일정의 다른 멤버에게
근무의 일부를 맡아 달라고 요청할 수 있습니다. 일정 상세 정보의 **근무 교대**에서 **교대 요청**을 선택하고,
요청자의 향후 30일 근무 중 하나를 선택하거나 시작 및 종료 시간을 입력합니다. 그런 다음 **교대 담당자**를 지정하고,
필요하면 메모를 추가한 뒤 **요청 보내기**를 선택합니다. 요청 기간 내내 해당 일정의 당번은
요청자 한 명뿐이어야 합니다. 처리 중인 교대 요청과 겹치는 기간은 요청할 수 없습니다.

| 상태 | 의미 |
|---|---|
| **응답 대기 중** | 요청을 받은 멤버는 **수락** 또는 **거절**할 수 있고, 요청자는 **철회**할 수 있습니다. |
| **승인 대기 중** | 일정에서 **근무 교환에 승인 필요**를 켰고 요청을 받은 멤버가 수락한 상태입니다. 일정 관리자는 **승인** 또는 **거부**할 수 있습니다. |
| **적용됨** | 교대를 맡은 멤버가 일정의 대체 근무자로 지정됩니다. |
| **거절됨**, **반려됨**, **철회됨** | 근무 교대 요청이 종료되었으며 일정은 변경되지 않습니다. |
| **만료됨** | 교대 요청 처리가 끝나기 전에 요청한 근무 기간이 종료되었습니다. |

각 단계에서 관련 멤버에게 알림을 보냅니다. 요청 시에는 요청을 받은 멤버에게, 거절 시에는 요청자에게 알립니다.
승인 대기 상태가 되면 일정 생성자, 마지막 편집자, 요청자에게 알립니다. 교대가 적용되거나
반려되면 요청자와 요청을 받은 멤버에게, 철회되면 요청을 받은 멤버에게 알립니다. 기본 제공 정책인
[근무 교대: 관련 멤버에게 알림](/ko/notification-channels#기본-제공-정책)이 이러한 알림을 보냅니다.
적용된 근무 교대는 다른 변경 사항과 함께 일정의 **변경 이력**에 표시됩니다.

### 캘린더 구독

일정의 **더 보기** 메뉴에서 **캘린더 구독**을 선택하면 해당 일정의 모든 근무를 Google Calendar,
Outlook, Apple Calendar 등의 캘린더 앱에 추가할 수 있는 구독 주소를 생성합니다.
목록 위의 **내 근무 구독**을 선택하면 현재 계정의 모든 일정에 걸친 근무를 구독합니다. 캘린더 앱은
약 1시간마다 구독을 새로 고치며, 구독 범위는 재정의와 근무 교대를 포함해 지난 30일부터 향후 90일까지입니다.

주소는 한 번만 표시되며, 주소를 아는 사람은 누구나 근무를 볼 수 있습니다. 주소를 조회할 때마다 구독자의 권한을
다시 확인합니다. 계정이 비활성화되거나 구독자가 조직에서 나가거나 일정을 볼 권한을 잃으면 해당
주소에서 더 이상 데이터를 제공하지 않습니다. **주소 재설정**은 새 주소를 발급하고 기존 주소를 즉시 무효화합니다.
**구독 중지**는 구독을 중지합니다. **캘린더 내보내기**로 받은 `.ics` 파일과 달리 구독에는
일정 변경 사항이 반영됩니다.

### 일정 상세 정보 및 작업

일정을 열면 현재 당번과 근무 시작 시각, 다음 인계, 교대 규칙,
임시 당번, [근무 교대](#근무-교대), **향후 7일** 타임라인, **멤버별 근무 부담(최근 30일)**,
일정의 **변경 이력**을 확인할 수 있습니다. 멤버별 근무 부담에는 각 멤버의 온콜 근무 시간,
수신한 경보 알림 수, 야간(일정의 시간대 기준 22:00~08:00) 또는 주말에 수신한 알림 수,
야간에 알림을 받은 날 수가 표시됩니다. 이는
[인사이트](/ko/alerting/incidents#인사이트)의 **온콜 업무량**과 동일한 지표입니다.
일정 메뉴에는 다음 작업이 있습니다.

| 작업 | 효과 |
|---|---|
| **일정 편집** | 일정과 교대를 변경합니다. |
| **임시 당번 추가** | 재정의를 추가합니다. |
| **일정 일시 중지** / **일정 재개** | 일시 중지된 일정은 당번을 배정하지 않으므로 해당 일정을 대상으로 하는 단계에서는 아무도 알림을 받지 않습니다. |
| **일정 복사** | `<name> copy`라는 이름으로 사본을 생성합니다. |
| **캘린더 구독** | 캘린더 구독 주소를 생성합니다. [캘린더 구독](#캘린더-구독)을 참조합니다. |
| **캘린더 내보내기** | 캘린더에 추가할 수 있도록 근무를 `.ics` 파일로 다운로드합니다. |
| **일정 삭제** | 일정을 삭제합니다. |

[홈](/ko/home#내-온콜)에는 계정의 현재 또는 다음 근무가 표시됩니다. 온콜 이벤트 알림을 받는 방법은
[계정 설정](/ko/account#알림)에서 선택합니다.

### 경보를 받을 수 없는 멤버

당번이 경보를 받을 수 없으면 인시던트가 열려도 해당 당번에게 경보가 전달되지 않습니다.
MoleSignal은 각 멤버의 개인 설정에서 긴급도 높음에 해당하는 단계를 기준으로 수신 상태를 분류합니다.

| 상태 | 의미 |
|---|---|
| 수신 가능 | 개인 경보 알림이 켜져 있으며, 하나 이상의 단계에서 활성화된 커넥터에 활성화 및 검증을 마친 알림 수단이 있습니다. |
| 그룹만 수신 가능 | 개인 알림 수단은 없지만 팀 또는 조직의 기본 라우팅으로 그룹 채팅에 알림을 보낼 수 있습니다. |
| 수신 불가 | 두 조건 모두 해당하지 않습니다. |

수신 불가 상태는 일정의 멤버 이름 옆과 에스컬레이션 정책의 각 단계에 표시됩니다.
다음 당번이 경보를 받을 수 없으면 일정 페이지 상단에 이 상태가 표시됩니다.
일정에 속한 멤버가 경보를 받을 수 없으면 [계정 설정](/ko/account#알림)과
[홈 페이지](/ko/home)의 온콜 패널에 안내가 표시됩니다. 다음 당번이
경보를 받을 수 없으면 근무 시작 30분 전에 기본 제공 정책인 [경보를 받을 수 없는 온콜 멤버:
해당 멤버와 일정 관리자에게 알림](/ko/notification-channels#기본-제공-정책)이 해당 멤버와 일정 관리자에게 알립니다.

인시던트가 에스컬레이션된 단계에서 온콜 당번을 포함해 경보를 받을 수 있는 멤버가 없으면
확인 응답 제한 시간까지 기다리지 않고 즉시 다음 단계로 넘어갑니다. 타임라인에는
**N단계에서 경보를 받을 수 있는 멤버가 없어 다음 단계로 넘어갔습니다**라고 표시됩니다. 정책 전체에서
경보를 받을 수 있는 멤버가 없으면 인시던트는 열린 상태로 유지되며 타임라인과 정책 페이지에 이 상태가 표시됩니다.

## 에스컬레이션 정책

**에스컬레이션**에는 알림 대상과 알림 시점을 포함한 정책 목록이 표시됩니다.

1. **새 정책**을 선택하고 **정책 이름**을 입력합니다.
2. 각 단계에서 **최소 적용 심각도**(**모든 심각도** 또는 특정 최소 심각도),
   **확인 대기 시간**(1분, 5분, 10분, 15분, 30분 또는 1시간), **대상**을 선택합니다. 대상은 **사용자**,
   **일정**, **팀** 중 하나입니다. 다음 단계를 추가하려면 **단계 추가**를 선택합니다.
3. 필요한 경우 **확인할 때까지 전체 정책 반복**을 켜고 **최대 반복 횟수**를 설정합니다.
4. 필요한 경우 **확인 후 미해결 상태**를 설정합니다. [아래 설명](#확인-후-미해결-상태)을 참조합니다.
5. **긴급도**에서 정책이 긴급도를 결정하는 방식을 선택합니다. [긴급도](#긴급도)를 참조합니다.
6. **정책 생성**을 선택합니다.

인시던트의 심각도가 단계의 최소 적용 심각도보다 낮으면 해당 단계를 건너뜁니다. 전송에 사용할 커넥터와
대체 경로는 **설정 → 알림 → 정책**에서 설정합니다. 에스컬레이션
정책에서는 설정하지 않습니다.

### 확인 후 미해결 상태

확인한 인시던트가 해결되지 않으면 **확인 후 미해결 상태** 설정에 따라
온콜 담당자에게 다시 알립니다. 30분, 1시간, 2시간, 4시간 중에서 선택합니다(API에서는 5분부터 24시간까지 설정할 수 있습니다).
확인 후 설정한 시간이 지나도 인시던트가 해결되지 않으면 **대기 중** 상태로 돌아갑니다.
담당자에게 다시 알림을 보내고, 템플릿의 `{{escalation.reason}}` 값은 `ack_timeout`이 됩니다. 이후에도
아무도 확인하지 않으면 평소대로 에스컬레이션을 진행합니다. 기본값인 **다시 알리지 않음**은
인시던트를 해결할 때까지 확인 상태로 유지합니다. 일시 중지한 인시던트는 대신
일시 중지가 끝날 때 **대기 중** 상태로 돌아갑니다.

### 긴급도

심각도는 신호가 얼마나 심각한지 나타내고, 긴급도는 지금 담당자를 깨워서라도 알릴지 결정합니다. 각 인시던트는
하나의 긴급도 수준으로 시작합니다. 기본 제공 수준 두 가지는 다음과 같이 동작합니다.

| | 높은 긴급도 | 낮은 긴급도 |
|---|---|---|
| 에스컬레이션 | 단계에 따라 호출합니다. | 첫 단계에만 알립니다. 다음 단계로 진행하거나 정책을 반복하지 않습니다. |
| 개인 알림 | 개인별 높은 긴급도 단계를 사용합니다. | 개인별 낮은 긴급도 단계를 사용합니다. 해당 단계가 없으면 높은 긴급도의 첫 단계에만 알립니다. |
| 알림 제한 시간 | 개인별 **알림 제한 시간에도 긴급도가 높은 경보 받기** 설정을 따릅니다. | 알림 제한 시간에는 알리지 않습니다. |

조직은 수준의 이름과 동작을 변경하고 수준을 추가할 수 있습니다.
[긴급도 및 우선순위 수준](#긴급도-및-우선순위-수준)을 참조합니다.

규칙, 외부 경보, 경보 파이프라인 또는 인시던트를 수동으로 생성할 때
지정한 긴급도가 우선합니다. 그 외에는 인시던트에 적용된 에스컬레이션 정책의 **긴급도** 설정으로 결정합니다.

| 선택 항목 | 동작 |
|---|---|
| **심각도 기준**(기본값) | 각 심각도에 조직이 지정한 긴급도 수준을 적용합니다. 설정을 변경하지 않으면 치명적과 오류는 높은 긴급도, 경고와 정보는 낮은 긴급도를 적용합니다. |
| **항상 동일한 수준** | 모든 인시던트에 **긴급도**에서 선택한 수준을 적용합니다. |
| **지원 시간 기준** | **지원 시간 내**와 **지원 시간 외**에 서로 다른 수준을 적용합니다. 기본값은 각각 높은 긴급도와 낮은 긴급도입니다. 지원 시간은 하나의 시간대를 기준으로 매주 반복되는 시간 범위이며, [휴일 캘린더](#휴일-캘린더)로 휴일을 제외할 수 있습니다. **지원 시간 시작 시 미확인 인시던트의 긴급도가 지원 시간 내 수준보다 낮으면 긴급도를 높이고 첫 단계부터 다시 호출**을 켜면, 야간에 생성되어 아침까지 아무도 확인하지 않은 인시던트의 긴급도를 지원 시간 시작 시 지원 시간 내 수준으로 높이고 1단계에 다시 알립니다. 타임라인에는 **지원 시간 시작: 긴급도를 …(으)로 높이고 1단계에 다시 알림**이 표시됩니다. |

**첫 단계에서 멈추는 긴급도 수준의 인시던트도 다음 단계로 에스컬레이션**을 켜면
이 정책에서 모든 수준이 높은 긴급도와 같은 방식으로 에스컬레이션됩니다. 심각도를 지정하지 않은 외부 경보에는 높은 긴급도를 적용합니다.
지정된 긴급도가 조직에 없는 수준이면 인시던트를 생성할 때 해당 값을 무시하고 정책에 따라 긴급도를 결정합니다.
정책 목록에서 심각도 기준이 아닌 긴급도 설정은 에스컬레이션 단계 뒤에 표시됩니다.

<Note>
심각도 기준으로 긴급도를 결정하면 심각도가 경고 또는 정보인 인시던트는 첫 단계에만 알리고, 알림 제한 시간에는
알리지 않습니다. 모든 인시던트에서 단계에 따라 호출하려면 정책의 긴급도를 **항상 동일한 수준**으로 설정하고
높은 긴급도를 선택합니다.
</Note>

### 긴급도 및 우선순위 수준

조직의 수준을 설정하려면 **설정 → 알림 → 우선순위 및 긴급도**를 엽니다. 수준을 조회하려면
`alerts.importance.read` 권한이 필요하고, 변경하려면 `alerts.importance.manage` 권한이 필요합니다.

**긴급도 수준**에는 긴급도가 높은 순서대로 수준이 표시됩니다. 화살표로 수준을 한 칸 위나 아래로 옮깁니다. 각 수준에는 다음 설정이 있습니다.

| 설정 | 용도 |
|---|---|
| 이름 | 목록, 필터, 메시지에 표시할 수준 이름입니다. |
| **다음 단계로 에스컬레이션** | 에스컬레이션 정책의 단계에 따라 호출합니다. 끄면 첫 단계에만 알립니다. |
| **방해 금지 시간대 동작** | **개인별 스위치 설정 따름**(**알림 제한 시간에도 긴급도가 높은 경보 받기**) 또는 **항상 알림 차단**을 선택합니다. |
| **개인별 단계** | 개인별 단계 그룹 중 **높은 긴급도 단계** 또는 **낮은 긴급도 단계**를 사용합니다. |
| **심각도 기준** | 정책이 심각도 기준으로 긴급도를 결정할 때 이 수준에 연결할 심각도를 지정합니다. 각 심각도는 정확히 하나의 수준에 연결됩니다. |

기본 제공 수준인 `high`와 `low`는 이름과 설정을 변경할 수 있지만 삭제할 수는 없습니다. **긴급도 수준 추가**로
최대 3개를 더해 총 5개를 사용할 수 있습니다. `urgent`와 같은 **새 수준의 키**는 영문 소문자로 시작하며,
영문 소문자, 숫자, 밑줄만 포함할 수 있습니다. 규칙, 외부 경보, 경보 파이프라인 및 API는
키로 수준을 지정합니다. 인시던트의 긴급도 수준을 나중에 삭제하면 해당 인시던트는 높은 긴급도로 동작합니다.

**우선순위 수준**에서 조직이 사용할 우선순위 개수(1~9개)와 각 수준의 이름 및 설명을
설정합니다. 연동과 가져오기 파일에서 사용하는 키는 `P1`, `P2` 등의 형태로 유지합니다. 외부 경보나 경보 파이프라인이
설정된 범위를 벗어나는 우선순위를 지정하면 가장 낮은 우선순위를 적용합니다. 템플릿에서는 수준 이름에
`{{urgency_name}}`과 `{{priority_name}}`으로 액세스합니다.
[템플릿 변수](/ko/notification-channels#템플릿-변수)를 참조합니다.

### 기본 정책

규칙은 `escalationPolicyId`로 에스컬레이션 정책을 지정합니다. 규칙 워크벤치에서 저장한 모든 규칙처럼
정책을 지정하지 않은 규칙은 `default` 별칭을 사용합니다. [경보 라우팅](/ko/alerting/routing)은
라우팅 규칙, 서비스 소유 팀, 팀 레이블을 기준으로 팀의 온콜 정책을 선택합니다. 해당하는 팀 정책이 없으면
대소문자를 구분하지 않고 이름이 `default`인 조직 정책을 선택합니다. 이 정책도 없으면 해당
인시던트는 누구에게도 에스컬레이션되지 않습니다.

첫 규칙을 만들기 전에 이름이 `default`인 정책을 생성합니다. 예를 들어 1단계에 기본 온콜 일정을,
2단계에 팀 리더를 지정합니다. 인시던트의 에스컬레이션이 시작되면 이후 `default` 정책의 이름을 변경해도
처음 선택한 정책을 계속 사용합니다.

## 휴일 캘린더

휴일 캘린더에 휴일과 보충 근무일을 등록하면 주간 시간대에서 공휴일을 제외하거나
공휴일에만 해당 시간대를 적용할 수 있습니다. **설정 → 알림 → 휴일 캘린더**를 엽니다. 캘린더를 조회하려면
`alerts.calendars.read` 권한이 필요하고, 변경하려면 `alerts.calendars.manage` 권한이 필요합니다. MoleSignal은 공휴일을 기본으로 제공하지 않습니다. 공휴일은
매년 달라지므로 각 조직에서 직접 입력하거나 가져옵니다.

1. **새 캘린더**를 선택하고 **이름**과 **설명**을 입력합니다.
2. **요일**에서 **연도**를 선택합니다. 각 **날짜**를 추가하고 **유형**으로 **휴일** 또는
   **보충 근무일**을 선택한 후 **날짜 이름**을 입력합니다. **ICS 가져오기**는 공휴일이 담긴
   `.ics` 파일을 읽습니다. 각 종일 이벤트를 날짜로 추가하고, 이름에 补班 또는 上班이 들어 있거나 이름이 班으로 끝나면
   보충 근무일로 분류합니다. 캘린더를 저장하기 전에는 아무 항목도 저장하지 않으므로 날짜를 먼저 확인합니다.
3. **캘린더 만들기**를 선택합니다.

주간 시간대의 **공휴일**에서 캘린더 적용 방식을 선택합니다.

| 옵션 | 동작 |
|---|---|
| **공휴일 여부 무시**(기본값) | 공휴일을 다른 날과 동일하게 처리합니다. |
| **공휴일 제외** | 휴일에는 시간대를 적용하지 않습니다. 보충 근무일은 월요일로 처리합니다. |
| **공휴일에만 적용** | 휴일에만 시간대를 적용합니다. |

날짜는 캘린더를 사용하는 기능의 시간대를 기준으로 해석하며, 자정을 넘기는 시간 범위는
시작일에 속합니다. 캘린더를 적용할 수 있는 항목에는 [온콜 일정](#일정-생성)의 순환 근무,
[긴급도](#긴급도)의 지원 시간, [라우팅 규칙](/ko/alerting/routing#규칙-생성)과
[알림 정책](/ko/notification-channels#템플릿-및-정책-만들기)의 시간 조건, 알림 파이프라인,
[알림 음소거](/ko/alerting/silences#음소거-정책)의 **공휴일** 시간 범위가 있습니다. 사용 중인
캘린더는 삭제할 수 없으며, 대화 상자에 해당 캘린더를 사용하는 항목이 표시됩니다. 변경 사항은 1분 이내에
모든 노드에 반영되며, 같은 조직의 캘린더는 페더레이션 내 다른 클러스터에도 동기화됩니다.

## 가져오기 및 내보내기

에스컬레이션 정책 목록과 온콜 일정 목록 위에 있는 **가져오기 / 내보내기**를 사용하면
알림 규칙과 마찬가지로 정책과 일정을 파일로 만들어 조직과 클러스터 간에 옮길 수 있습니다.

- **모든 에스컬레이션 정책 내보내기** 또는 **모든 일정 내보내기**를 선택하면 번들을 다운로드합니다. 일부 항목을 선택한 경우
  선택한 항목만 내보냅니다. 번들은 참조 대상을 식별할 때 사용자는 이메일 주소를 사용하고, 팀, 일정, 에스컬레이션
  정책, 휴일 캘린더는 이름을 사용합니다.
- **에스컬레이션 정책 가져오기…** 또는 **일정 가져오기…**는 JSON 또는 YAML 번들을 받아 먼저 가져오기 결과를 미리 확인하고,
  생성, 업데이트, 변경 없음, 오류로 분류해 항목을 표시합니다. **새 항목만 만들고, 같은 이름의 항목은
  그대로 유지**를 선택하면 기존 항목을 건너뜁니다. 각 항목은 이름으로 매칭하며, 모든 참조는 해당 조직에 있는
  대상을 가리켜야 합니다. 하나라도 오류가 있으면 아무 항목도 저장하지 않습니다.

번들에는 일정의 순환 근무와 설정만 포함되며, 임시 대체 근무나 교대 근무 교환은 포함되지 않습니다.
기존 일정을 가져와 업데이트할 때는 임시 대체 근무와 교대 근무 교환을 유지합니다. 정책을 가져오려면 `alerts.escalations.manage` 권한이 필요하고,
일정을 가져오려면 `schedules.create` 권한이 필요합니다. 라우팅 규칙도 같은 방식으로 가져오고 내보낼 수 있습니다.
[알림 라우팅](/ko/alerting/routing#가져오기-및-내보내기)을 참조합니다.

**일정 가져오기…**는 Opsgenie 및 PagerDuty API에서도 일정을 가져올 수 있습니다.
[Opsgenie 또는 PagerDuty에서 일정 마이그레이션](/ko/alerting/schedule-migration)을 참조합니다.
