탐색은 5분마다 각 조직을 검사하고 감지한 문제를 **탐지 결과**로 저장합니다. 다음 메뉴를 엽니다.
**알림 → 탐색**. 탐지 결과를 조회하려면 `alerts.discovery.read` 권한이, 규칙을 생성하려면 `alerts.rules.manage` 권한이 필요합니다.

## 탐지 대상

| 유형 | 소스 | 탐지 조건 |
|---|---|---|
| **서비스 지표 급변** | [APM 인사이트](/ko/apm/insights) | 비교에 충분한 요청이 있고, 최근 30분간 서비스의 오류율, P95 지연 시간 또는 트래픽이 직전 30분 및 일주일 전 같은 시간대와 비교해 모두 뚜렷하게 달라졌습니다. |
| **새 버전 성능 저하** | APM 인사이트 | 최근 30분 이내에 처음 나타난 버전의 성능이 이전 버전보다 낮습니다. |
| **새 프런트엔드 오류** | [RUM 오류](/ko/rum/errors) | 최근 30분 이내에 애플리케이션에서 처음 발생한 오류 이슈입니다. |
| **프런트엔드 오류 재발** | RUM 오류 | 해결된 오류 이슈가 더 최신 버전에서 다시 발생했습니다. |
| **오류 로그 급증** | 로그 | 최근 15분간 로그 스트림에 오류 로그가 20건 이상 기록되었고, 그 수가 직전 1시간의 15분당 평균 건수보다 3배 이상 많습니다. 스트림에 서비스 필드가 있으면 서비스별로 집계합니다. |
| **새 오류 로그** | 로그 | 스트림에서 직전 24시간 동안 나타나지 않았고 최근 15분간 3회 이상 나타난 오류 메시지입니다. 숫자와 16진수 문자열만 다른 메시지는 동일한 메시지로 간주합니다. 스트림당 최대 10개를 탐지합니다. |
| **리소스 용량 한계 임박** | 메트릭 | 파일 시스템 사용률이 90% 이상이거나 메모리 사용률이 95% 이상입니다. |
| **CPU 사용량 급증** | 메트릭 | 호스트의 CPU 사용률이 60% 이상이고 1시간 전보다 30%포인트 이상 높습니다. |
| **컨테이너 재시작** | 메트릭 | 최근 15분 이내에 컨테이너가 재시작되었습니다. |

로그: 레벨 필드(`level`, `severity`, `severity_text`,
`severity_number` 등)가 있는 로그 스트림을 조직별로 최근 변경 순서대로 최대 20개 검사합니다. Error, Fatal, Critical 및 이와
유사한 레벨과 `severity_number`가 17 이상인 로그는 오류로 간주합니다. 메트릭: OpenTelemetry
호스트 및 Kubernetes 리시버, Prometheus node_exporter, kube-state-metrics의 일반적인 리소스 메트릭 중 정해진 항목만 검사합니다.
해당 메트릭이 메트릭 디렉터리에 있을 때만 쿼리하며, 다른 메트릭은 검사하지 않습니다.

성능 개선 제안(느린 종속 서비스, N+1 호출, 느린 문, 부하가 집중되는 엔드포인트)은
문제로 간주하지 않아 제외합니다. 무시했거나 해결된 이슈도 제외합니다.

유형, 서비스 또는 애플리케이션, 환경, 메트릭이 모두 같은 문제는 한 번에 하나의 열린 탐지 결과로 유지합니다.
같은 문제가 다시 감지되면 수치와 마지막 감지 시간을 업데이트합니다. 3회 연속으로 감지되지 않으면
탐지 결과를 종료하고 30일간 보관합니다. 특정 소스를 읽을 수 없는 경우(예: APM 또는
RUM을 일시적으로 쿼리할 수 없거나 로그 스트림에 장애가 발생한 경우), 해당 검사에서는 그 소스의 열린 탐지 결과를
기존 상태로 유지합니다.
`alert` 노드가 여러 개면 조직 ID를 기준으로 각 노드에 조직을 배분합니다.

## 탐지 결과

**열기**와 **종료됨** 사이를 전환하고 유형별로 필터링합니다. 각 행은 감지한 내용을 한 문장으로 표시합니다.
예: "checkout의 오류율은 12.0%입니다(이전 0.40%)." 그 아래에는 심각도, 유형,
환경을 표시하고, 이어서 시작 시간과 마지막 감지 시간(또는 종료 시간)을 표시합니다.

행을 선택하면 유형, 현재·이전·일주일 전 수치, 버전, 오류 발생 위치,
시작 시간과 마지막 감지 시간을 확인할 수 있습니다. APM 탐지 결과에는 시작 시점 전후의 배포와
버전도 표시합니다. **APM에서 열기**, **RUM에서 열기**, **로그 열기**, **메트릭에서 열기**를 선택하면
각각 해당 서비스, 애플리케이션, 로그 스트림 또는 쿼리로 이동합니다.

**Mole Agent에 조사 요청**을 선택하면 상세 정보가 닫히고 해당 탐지 결과에 대한 [Mole Agent](/ko/agent) 채팅이 시작됩니다.
Mole Agent는 `get_discovery_finding`으로 탐지 결과를 읽고, 문제가 시작된 시점 전후의 로그, 메트릭, 트레이스,
변경 사항을 검토한 뒤 다음 조치를 안내합니다.

## 규칙으로 알림 받기

탐지 결과는 추론한 문제이므로 목록에만 표시합니다. 결과마다 호출 알림을 보내면 불필요한 알림이 많아질 수 있습니다.
알림을 받으려면 탐지 규칙을 생성합니다.

1. **새 탐지 규칙**을 선택하거나 탐지 결과의 상세 정보에서 **유사 탐지 결과에 대한 알림 설정**을 선택합니다. 상세 정보에서 선택하면
   해당 유형, 서비스, 환경을 자동으로 입력합니다.
2. **탐지 조건**에서 **이름**을 입력하고 **유형**을 선택합니다(선택하지 않으면 모든 유형이 포함됩니다).
   **서비스 또는 애플리케이션**(APM 서비스 이름 또는 RUM 애플리케이션 ID를 쉼표로 구분하며,
   비워 두면 모두 포함됩니다), **환경**, **최소 심각도**를 지정합니다.
3. **알림 대상**에서 **에스컬레이션 정책**과 **긴급도**를 선택합니다. **낮음 (기본값)**은
   첫 단계에만 알림을 보내며, 알림 제한 시간에는 알림을 보내지 않습니다.
4. **규칙 생성**을 선택합니다.

규칙은 매분 열린 탐지 결과를 확인합니다. 조건에 맞는 탐지 결과마다 동일한 심각도의 인시던트를 생성하고,
라우팅 규칙과 무음 설정에서 일치 조건으로 사용할 수 있는 `discovery.finding`, `discovery.kind`, `discovery.subject` 라벨을 추가합니다.
탐지 결과가 종료되면 인시던트는 복구 상태로 전환됩니다. [규칙 목록](/ko/alerting/rules#탐지-규칙)에서
이 규칙의 소스는 **탐색**으로 표시됩니다.

## Mole Agent로 새 탐지 결과 조사하기

**새 탐지 결과** 트리거를 사용하는 [자동화](/ko/automations#실행-조건)는 저장하거나 활성화한 후에 나타난 결과 중
설정한 **유형**(선택하지 않으면 모든 유형이 포함됩니다), **최소 심각도**,
**서비스, 호스트 또는 컨테이너**(쉼표로 구분하며, 비워 두면 모두 포함됩니다) 조건에 맞는
탐지 결과마다 실행됩니다. 각 탐지 결과는 한 번만 조사합니다. 기본적으로 탐지 결과는 자동화를 실행하지 않으므로
별도 설정 없이 추론한 문제에 토큰 예산을 사용하지 않습니다.
