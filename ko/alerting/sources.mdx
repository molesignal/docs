경보 소스는 다른 시스템에서 보낸 경보를 [인시던트](/ko/alerting/incidents)로 전환합니다. 인시던트는 규칙의 인시던트와 같은 방식으로 [에스컬레이션 정책](/ko/alerting/on-call#에스컬레이션-정책)을 통해 담당자를 호출하고 [알림 정책](/ko/notification-channels)을 통해 알리며, 소스가 복구를 보고하면 해결됩니다. **알림 → 소스**를 엽니다. 조회에는 `alerts.sources.read`가 필요하고, 생성, 편집, 삭제 및 토큰 교체에는 `alerts.sources.manage`가 필요합니다.

## 소스 유형

각 소스에는 유형이 있으며, 이 유형에 따라 요청 본문을 어떤 형식으로 읽을지 결정됩니다.

| 유형 | 발신자 | 인시던트 하나당 기준 |
|---|---|---|
| **API** | MoleSignal API를 호출하는 스크립트, CI 및 사내 시스템 | 중복 제거 키 |
| **Alertmanager** | Prometheus Alertmanager의 웹훅 수신기 | 알림 그룹 |
| **Grafana** | Grafana Alerting의 웹훅 연락 지점 | 알림 그룹 |
| **Datadog** | Datadog Webhooks 통합 | 모니터, 다중 경보 모니터의 각 그룹 |
| **PagerDuty** | PagerDuty V3 웹훅 구독 | PagerDuty 인시던트 |
| **Alibaba Cloud CloudMonitor** | 임계값 경보 콜백 및 이벤트 구독 푸시 채널 | 경보 규칙의 객체 또는 시스템 이벤트 |
| **Tencent Cloud Observability Platform** | 알림 템플릿의 API 콜백 | 정책 아래 한 객체의 메트릭 또는 이벤트 하나, 레벨이 있는 정책에서는 레벨당 하나 |
| **Amazon CloudWatch** | SNS 주제의 HTTPS 구독을 통해 해당 주제로 전송된 경보 | 경보 하나 |
| **Zabbix** | Zabbix 웹훅 미디어 유형 | 문제 하나 |
| **Azure Monitor** | 공통 경보 스키마에서 작업 그룹의 웹훅 작업 | 경보 하나 |
| **Google Cloud Monitoring** | 웹훅 알림 채널 또는 푸시 구독을 통한 Pub/Sub 채널 | Monitoring 인시던트 하나 |
| **Huawei Cloud Eye** | SMN 주제의 HTTPS 구독을 통해 해당 주제로 전송된 경보 | 한 리소스의 경보 규칙 하나 |
| **이메일** | IMAP 사서함 또는 이미 운영 중인 메일 시스템의 원시 메일 | 동일한 제목의 메일 묶음 |

Thanos, Cortex 또는 Mimir의 Alertmanager처럼 Alertmanager 웹훅을 사용하는 시스템은 **Alertmanager** 유형을 사용합니다.

## 소스 생성

1. **알림 → 소스**를 열고 **새 경보 소스**를 클릭합니다.
2. **유형**을 선택하고 **이름**을 입력합니다.
3. **에스컬레이션 정책**을 선택합니다. 기본값은 규칙 워크벤치와 동일한 **라우팅 적용(기본값)**입니다. [경보 라우팅](/ko/alerting/routing)은 라우팅 규칙, 서비스 소유 팀, 팀 레이블에 따라 팀과 에스컬레이션 정책을 선택하며, 그렇지 않으면 이름이 `default`인 [기본 정책](/ko/alerting/on-call#기본-정책)을 선택합니다. 정책을 선택하면 인시던트가 해당 정책을 사용하며, 라우팅은 팀만 선택합니다. **에스컬레이션 없음, 알림 정책만 적용**을 선택하면 인시던트는 계속 열리고 알림을 보내지만, 어떤 에스컬레이션 정책도 담당자를 호출하지 않습니다.
4. **기본 심각도**를 선택합니다. 이 값은 경보에 자체 심각도가 없을 때 사용됩니다.
5. 필요하면 `team=payments` 같은 **추가 레이블**을 추가합니다. 이 레이블은 소스가 여는 모든 인시던트에 추가됩니다. 경보 자체에 있는 레이블이 우선합니다.
6. **생성**을 클릭합니다. 소스 페이지가 열리며, 토큰과 토큰이 채워진 설정을 보여 주는 대화상자가 표시됩니다. Alibaba Cloud CloudMonitor는 수신 주소만 필요하므로 대화상자에는 토큰이 포함된 주소가 표시됩니다.

<Warning>
  토큰은 소스를 생성하거나 토큰을 교체할 때만 표시됩니다. 대화상자가 닫힌 후에는 `mspat-`로 시작하는 접두사만 볼 수 있습니다. 토큰을 분실한 경우 **토큰 교체**를 클릭해 새 토큰을 발급받습니다. 이전 토큰은 즉시 작동을 멈춥니다.
</Warning>

## 수신 주소 및 토큰

모든 소스는 하나의 수신 주소를 공유합니다. 토큰은 경보가 어느 소스에 속하는지 알려 줍니다:

```text
https://<molesignal-host>/api/v1/intake/alerts
```

토큰은 API Token과 같은 `mspat-<36>` 형태이지만, 경보만 수신합니다. API Token은 경보를 수신할 수 없습니다. 발신자는 토큰을 헤더에 넣습니다:

```text
Authorization: Bearer <token>
```

헤더를 설정할 수 없는 발신자(Alibaba Cloud CloudMonitor, Tencent Cloud Observability Platform, SNS를 통한 Amazon CloudWatch, Azure Monitor, Google Cloud Monitoring, SMN을 통한 Huawei Cloud Eye)는 주소에 토큰을 포함합니다: `https://<molesignal-host>/api/v1/intake/alerts?token=<token>`.

발신자는 이 주소에 도달할 수 있어야 합니다. MoleSignal 앞에 방화벽이 있는 경우 발신자 사이트 또는 리전의 이그레스 주소를 허용합니다: Datadog은 `ip-ranges`의 `webhooks` 섹션에 이를 사이트별로 나열하고, PagerDuty는 미국 및 EU 서비스 리전에 대해 이를 게시하며, Alibaba Cloud CloudMonitor는 경보 콜백 문서에 푸시 대역을 나열합니다. MoleSignal이 내부 네트워크에서 실행되는 경우, 이 주소만 인터넷에 공개하는 방법은 [공개 액세스](/ko/public-access)를 참조합니다.

## 발신자 설정

소스 페이지의 **수신**에는 수신 주소, 토큰, 각 종류의 설정이 세 단계로 나와 있습니다. `<TOKEN>`을 소스의 토큰으로 바꾸세요. 소스가 첫 요청을 받으면 세 단계에 체크 표시가 나타납니다.

### API

```bash
curl -X POST https://<molesignal-host>/api/v1/intake/alerts \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{"dedupKey": "disk-full/web-1", "summary": "Disk almost full on web-1", "severity": "critical", "labels": {"host.name": "web-1"}}'
```

`action`은 `trigger`(기본값), `acknowledge`, `resolve` 중 하나입니다. 같은 알림을 확인하거나 해결하려면 같은 `dedupKey`를 사용하세요. 모든 필드는 [알림 전송](/ko/api/alerting/send-alerts)에서 설명합니다.

### Alertmanager

`alertmanager.yml`에 수신자를 추가하고 알림을 그리로 라우팅하세요:

```yaml
route:
  receiver: molesignal
receivers:
  - name: molesignal
    webhook_configs:
      - url: https://<molesignal-host>/api/v1/intake/alerts
        send_resolved: true
        http_config:
          authorization:
            credentials: <token>
```

`send_resolved`를 `true`로 유지하세요. 그렇지 않으면 복구가 전송되지 않습니다. 하나의 Alertmanager 클러스터에 속한 모든 복제본에 같은 `--web.external-url`을 지정하세요. 외부 URL은 중복 제거 키의 일부이므로, 같은 라우팅을 사용하는 여러 리전의 Alertmanager에서 온 같은 이름의 그룹이 하나의 인시던트로 병합되지 않습니다.

### Grafana

1. Grafana에서 **Alerting → Contact points**를 열고 **Add contact point**를 클릭하세요.
2. **Integration**을 **Webhook**으로, **URL**을 수신 주소로 설정하세요.
3. **Optional Webhook settings**에서 **Authentication Header Scheme**을 `Bearer`로, **Authentication Header Credentials**를 토큰으로 설정하세요.
4. **Disable resolved message**를 선택 해제한 상태로 두고 저장한 뒤, 알림 정책에서 이 접점을 사용하세요.

파일 프로비저닝을 사용하는 경우:

```yaml
apiVersion: 1
contactPoints:
  - orgId: 1
    name: molesignal
    receivers:
      - uid: molesignal
        type: webhook
        settings:
          url: https://<molesignal-host>/api/v1/intake/alerts
          httpMethod: POST
          authorization_scheme: Bearer
          authorization_credentials: <token>
```

### Datadog

1. Datadog에서 **Integrations → Webhooks**를 열고 웹훅을 추가합니다. 이름은 예를 들어 `molesignal`로 지정합니다.
2. **URL**을 수신 주소로, **Custom Headers**를 `{"Authorization": "Bearer <token>"}`로 설정하세요. **Encode as form**은 선택 해제한 상태로 두세요.
3. **Payload**를 아래 템플릿으로 설정하세요. 필드 이름은 MoleSignal의 것이고 값은 Datadog 변수입니다. 이 템플릿이 없는 요청은 거부됩니다.

```json
{
  "alert_id": "$ALERT_ID",
  "alert_cycle_key": "$ALERT_CYCLE_KEY",
  "transition": "$ALERT_TRANSITION",
  "alert_type": "$ALERT_TYPE",
  "priority": "$ALERT_PRIORITY",
  "title": "$ALERT_TITLE",
  "event_title": "$EVENT_TITLE",
  "message": "$TEXT_ONLY_MSG",
  "scope": "$ALERT_SCOPE",
  "tags": "$TAGS",
  "hostname": "$HOSTNAME",
  "link": "$LINK",
  "snapshot": "$SNAPSHOT",
  "query": "$ALERT_QUERY",
  "org_id": "$ORG_ID",
  "last_updated": "$LAST_UPDATED"
}
```

4. 모니터의 알림 메시지에서 `@webhook-molesignal`을 멘션하세요.

모든 Datadog 사이트(`datadoghq.com`, `datadoghq.eu`, `us3`, `us5`, `ap1` 등)가 하나의 소스로 보낼 수 있습니다. 사이트는 `$LINK`의 도메인에서 가져오며, 조직 ID와 함께 중복 제거 키의 일부가 됩니다.

### PagerDuty

1. PagerDuty에서 **Integrations → Generic Webhooks (v3)**를 열고 **New Webhook**을 클릭하세요.
2. **Webhook URL**을 수신 주소로 설정하고 **Scope Type**(계정, 서비스 또는 팀)을 선택하세요.
3. **Event Subscription**에서 `incident.triggered`, `incident.acknowledged`, `incident.resolved`, `incident.reopened`, `incident.priority_updated`를 선택하세요.
4. 값이 `Bearer <token>`인 사용자 정의 헤더 `Authorization`을 추가하세요.

미국과 EU 서비스 리전의 계정이 하나의 소스로 보낼 수 있습니다. 계정 도메인(`<subdomain>.pagerduty.com` 또는 `<subdomain>.eu.pagerduty.com`)은 중복 제거 키의 일부이며 `pagerduty.region` 레이블에 기록됩니다.

### Alibaba Cloud CloudMonitor

수신 주소에 토큰을 추가하세요:

```text
https://<molesignal-host>/api/v1/intake/alerts?token=<token>
```

- **임계값 알람**: 이 주소를 알람 규칙의 **alarm callback**으로 입력하세요. CloudMonitor는 콜백을 폼 인코딩으로 POST하며, MoleSignal은 JSON도 읽습니다.
- **시스템 이벤트**: **Event Center → Event Subscription → Push channels**에서 대상 유형 **Webhook**, 요청 메서드 **POST**, 데이터 형식 **JSON**으로 채널을 만들고 이 주소를 입력한 뒤, 구독 정책에서 해당 채널을 사용하세요.

CloudMonitor는 시스템 이벤트 콜백을 5초 동안 기다리고 3회 재시도합니다. MoleSignal은 요청을 [수신 클러스터](#여러-클러스터)로 전달할 때 최대 3초를 기다리며, 시간 초과 시 `503`을 응답해 CloudMonitor가 재시도하도록 합니다. 중국 사이트와 국제 사이트, 모든 리전이 같은 형식을 전송합니다. 리전은 `aliyun.region` 레이블에 기록되고, 계정 `userId`는 중복 제거 키의 일부입니다.

### Tencent Cloud Observability Platform

Tencent Cloud Observability Platform(이전 Cloud Monitor)에서 **Alarm Management → Notification Templates**의 템플릿을 편집하거나 새로 만들고, **API callback**에 수신 주소를 입력한 뒤 템플릿을 알람 정책에 연결하세요. Tencent Cloud의 콜백은 헤더를 설정할 수 없으므로 토큰은 주소에 넣습니다. 주소를 자격 증명으로 취급하세요. 콜백에는 서명이 없고, 소스를 식별하는 것은 주소입니다. 메트릭 알람과 이벤트 알람 모두 동작하며, 트리거와 복구가 모두 푸시됩니다.

- **중복 제거**: 같은 계정, 알람 정책, 메트릭 또는 이벤트 이름, 객체는 하나의 알림이 됩니다. 레벨이 있는 정책은 Tencent Cloud에서처럼 레벨마다 하나의 인시던트를 만들고 각각 따로 복구됩니다.
- **심각도**: `alarmLevel`이 Serious(`Serious`)이면 critical, Severe(`Warn`)이면 error, Reminder(`Remind`)이면 info입니다. 레벨이 없는 정책은 소스의 기본 심각도를 사용합니다.
- **상태 없는 이벤트**(`alarmStatus`가 `5`)는 기다릴 복구 없이 인시던트를 열므로, 사람이 직접 해결합니다.
- 콜백의 **시간**에는 시간대가 없으며 베이징 시간으로 읽습니다.

### Amazon CloudWatch

CloudWatch 알람은 외부 주소를 직접 호출하지 않고 SNS를 거칩니다:

1. 알람의 알림에서 **In alarm**(`ALARM`) 진입과 **OK** 복귀를 모두 같은 SNS 주제로 보내세요. `OK`가 없으면 인시던트가 스스로 해결되지 않습니다. 데이터 없음 알림의 경우 **Insufficient data**(`INSUFFICIENT_DATA`)도 함께 보내세요.
2. 주제에 수신 주소를 엔드포인트로 하는 HTTPS 구독을 추가하고, 토큰은 주소에 넣습니다:

   ```bash
   aws sns subscribe \
     --topic-arn <ARN of the topic> \
     --protocol https \
     --notification-endpoint 'https://<molesignal-host>/api/v1/intake/alerts?token=<token>'
   ```

3. 구독은 스스로 확인됩니다. MoleSignal은 확인 메시지의 서명을 검증한 뒤 해당 `SubscribeURL`을 방문합니다.

MoleSignal은 모든 SNS 메시지의 서명을 검증하므로 **Raw message delivery**는 꺼 둬야 합니다. 켜져 있으면 메시지가 거부되며, 소스 페이지의 최근 수신에서 이유를 확인할 수 있습니다. 서명 인증서는 `sns.<region>.amazonaws.com`에서 오므로, 요청을 받는 노드가 해당 주소에 접근할 수 있어야 합니다.

CloudWatch 알람에는 심각도가 없으므로 인시던트는 소스의 기본 심각도를 사용합니다. 알람의 ARN이 중복 제거 키이며, 복합 알람도 마찬가지입니다. 알람 설명과 상태 변경 사유는 애노테이션에, 리전, 계정, 네임스페이스, 메트릭, 차원은 레이블에 들어가므로 `aws.region` 같은 레이블로 라우팅을 결정할 수 있습니다.

### Azure Monitor

Azure Monitor 알림은 작업 그룹의 웹훅 작업을 통해 MoleSignal에 도달합니다:

1. 알림 규칙에서 사용하는 작업 그룹에 **Webhook** 유형의 작업을 추가하고, URI에 수신 주소를 넣고 토큰은 주소에 포함하세요.
2. **Enable the common alert schema**를 **예**로 설정하세요. 설정하지 않으면 요청이 거부되며, 소스 페이지의 최근 수신에서 이유를 확인할 수 있습니다.

Azure CLI로도 같은 설정을 할 수 있습니다:

```bash
az monitor action-group update \
  --resource-group <resource group> \
  --name <action group> \
  --add-action webhook molesignal 'https://<molesignal-host>/api/v1/intake/alerts?token=<token>' usecommonalertschema
```

- **중복 제거**: 알림의 `alertId`가 중복 제거 키이며, 여기에는 Azure 구독이 포함됩니다.
- **트리거 및 해결**: `monitorCondition`이 `Fired`이면 인시던트를 열고 `Resolved`이면 해결합니다. 활동 로그 알림처럼 상태를 유지하지 않는 알림은 트리거만 되므로 사람이 직접 해결합니다.
- **심각도**: `Sev0`은 critical, `Sev1`은 error, `Sev2`는 warning, `Sev3`과 `Sev4`는 info입니다.
- **레이블**: 알림 규칙의 사용자 지정 속성, 메트릭 차원, `azure.subscription_id`, `azure.resource_group`, `azure.resource`, `azure.signal_type`, `azure.monitoring_service`, `azure.metric`입니다. 설명, 조건, 값, 대상은 애노테이션에 들어가며, 조사 링크는 `azure_url`로 제공됩니다.

### Google Cloud Monitoring

1. Google Cloud 콘솔에서 **Monitoring → Alerting → Edit notification channels**을 열고, **Endpoint URL**에 수신 주소를 넣은 **Webhook** 채널을 추가하세요. 토큰은 주소에 포함합니다.
2. 알림 정책의 알림에 이 채널을 추가하세요. 종료된 인시던트도 전송되므로 인시던트가 스스로 해결됩니다.

**Pub/Sub** 채널도 같은 알림을 게시합니다. 이를 사용하려면 해당 주제에 수신 주소를 푸시 엔드포인트로 하는 푸시 구독을 만드세요. MoleSignal이 Pub/Sub 봉투를 풀어서 처리합니다.

- **중복 제거**: 범위 지정 프로젝트와 `incident_id`입니다. Monitoring 인시던트 하나가 인시던트 하나가 됩니다.
- **트리거 및 해결**: `state`가 `open`이면 인시던트를 열고 `closed`이면 해결합니다.
- **심각도**: 정책의 심각도 수준인 `Critical`, `Error`, `Warning`입니다. 심각도가 없는 정책은 소스의 기본 심각도를 사용합니다.
- **레이블**: 리소스와 메트릭의 레이블, 정책과 모니터링 대상 리소스의 사용자 레이블, `gcp.project_id`, `gcp.resource_type`, `gcp.metric`, `gcp.policy`입니다. 요약, 조건, 관측값, 임계값, 문서는 애노테이션에 들어가며, 인시던트의 콘솔 주소는 `gcp_url`로 제공됩니다.

### Huawei Cloud Eye

Cloud Eye(CES) 알람은 외부 주소를 직접 호출하지 않고 SMN을 거칩니다:

1. Simple Message Notification에서 **HTTPS** 프로토콜과 수신 주소를 엔드포인트로 하는 구독을 주제에 추가하고, 토큰은 주소에 넣습니다.
2. 구독은 스스로 확인됩니다. MoleSignal은 확인 메시지의 서명을 검증한 뒤 해당 `subscribe_url`을 방문합니다.
3. Cloud Eye 알람 규칙의 알람 알림에서 해당 주제를 선택하고, 알람과 복구 모두에 대해 알리도록 설정하세요. 복구 알림이 없으면 인시던트가 스스로 해결되지 않습니다.

MoleSignal은 모든 SMN 메시지의 서명을 검증합니다. 서명 인증서는 `smn.<region>.myhuaweicloud.com`에서 오므로, 요청을 받는 노드가 해당 주소에 접근할 수 있어야 합니다.

- **중복 제거**: 주제의 프로젝트, 알람 규칙의 `alarm_id`, 리소스입니다. 여러 리소스에 적용된 하나의 규칙은 리소스마다 하나의 인시던트를 엽니다.
- **트리거 및 해결**: `alarm_status`가 `alarm`이면 인시던트를 열고, `insufficient_data`이면 데이터 없음으로 열며, `ok`이면 해결합니다.
- **심각도**: 알람 수준입니다. Critical은 critical, Major는 error, Minor는 warning, Informational은 info입니다.
- **레이블**: `instance_id` 같은 차원과 `huawei.region`, `huawei.project_id`, `huawei.namespace`, `huawei.metric`, `huawei.alarm_id`, `huawei.resource_id`입니다. 알람 텍스트, 현재 값, 임계값은 애노테이션에 들어가며, 알람의 콘솔 주소는 `huawei_url`로 제공됩니다.

### Zabbix

Zabbix 6.0 이상에서 동작합니다. Zabbix에는 자체 요청 형식이 없으므로 미디어 유형의 스크립트가 요청을 전송합니다. 따라서 소스 페이지와 소스를 만들 때의 대화 상자에서 주소와 토큰이 채워진 미디어 유형을 제공합니다:

1. YAML로 저장한 뒤 **Alerts → Media types → Import**에서 가져오세요. `token` 파라미터를 확인하세요.
2. 전역 매크로 `{$ZABBIX.URL}`을 Zabbix 프런트엔드 주소로 설정하세요. 이 값은 중복 제거 키에 포함되므로 하나의 소스가 여러 Zabbix 서버의 요청을 받을 수 있고, 인시던트에서 Zabbix로 다시 연결할 수 있습니다. 설정하지 않아도 동작합니다.
3. 사용자에게 이 미디어를 지정하세요. **전달 대상**은 아무 값이나 괜찮습니다. 스크립트가 사용하지 않습니다.
4. **operations**, **recovery operations**, **update operations**가 모두 해당 사용자로 가는 트리거 액션을 추가하세요. 복구 작업이 없으면 인시던트가 스스로 해결되지 않습니다.

미디어 유형의 **테스트** 버튼에는 실제 값이 필요합니다. 매크로가 확장되지 않아 `{EVENT.ID}`가 그대로 도착하면 MoleSignal은 `400`을 응답하고 문서의 미디어 유형을 사용하라고 안내합니다.

### 이메일

수신 방법은 두 가지이며, 둘 다 메일을 읽어 같은 알림으로 만듭니다.

**메일함 읽기**(권장): MoleSignal이 일정에 따라 IMAP 메일함을 읽습니다. 필요한 것은 외부로 나가는 연결과 메일함뿐입니다. 공인 주소, MX 레코드, 포트 25, 인증서가 필요 없으므로 셀프 호스팅에서 가장 쉬운 선택입니다. 모니터링 시스템의 알림 메일을 해당 메일함으로 보내거나, 메일 규칙으로 그곳에 전달하세요.

소스 페이지의 **메일함 읽기**에서 **IMAP 서버**, **포트**, **암호화**, **사용자 이름**, **비밀번호**, **폴더**(기본값 `INBOX`), **읽기 주기**(15~3600초, 기본값 60)를 입력하세요. **연결 테스트**를 클릭한 다음 **메일함 저장**을 클릭하세요.

- **읽기 전용**: `EXAMINE`과 `BODY.PEEK[]`를 사용하므로 읽음 처리되거나 삭제되는 메일이 없습니다. 읽기 전용 계정으로도 됩니다.
- **밀린 메일 없음**: 처음 연결할 때 위치를 기록하고 그 이후에 도착한 메일만 읽습니다. 호스트, 계정, 폴더를 변경하거나 서버가 메일함을 다시 만든 경우(`UIDVALIDITY` 변경)에는 그 시점부터 다시 시작합니다. 소스가 꺼져 있는 동안에는 아무것도 읽지 않고 위치도 저장하지 않으며, 다시 켠 시점부터 시작합니다.
- **발신자 목록은 필수입니다**: 주소를 아는 사람은 누구나 메일을 보낼 수 있습니다. 소스 설정의 **허용 발신자**에 주소를 적거나 도메인 전체를 `@example.com`처럼 적으세요. `*`는 모든 발신자를 허용합니다. 목록은 위조될 수 있는 `From`을 기준으로 하므로, 메일 제공업체의 스팸 필터링과 DMARC를 켜 두세요. 그 밖의 발신자가 보낸 메일은 **거부됨**으로 기록되고 아무것도 열지 않습니다.
- **로그인**: 비밀번호 또는 제공업체의 앱 비밀번호를 사용합니다. Microsoft 365는 더 이상 비밀번호를 허용하지 않습니다. **OAuth 2.0**을 선택하고 토큰 주소 `https://login.microsoftonline.com/<tenant>/oauth2/v2.0/token`, 클라이언트 ID, 클라이언트 암호, 범위 `https://outlook.office365.com/.default`를 입력하세요. 애플리케이션에는 `IMAP.AccessAsApp` 권한과 이 메일함에 대한 액세스 권한이 필요합니다.
- **암호화 없음**은 신뢰하는 네트워크에서만 사용하세요. 비밀번호가 평문으로 전송됩니다.
- 읽기에 실패하면 소스 페이지에 이유가 표시되고, 다음 주기에 다시 시도합니다. 알림 노드가 여러 개이면 각 메일함은 그중 하나만 읽습니다. 페더레이션을 사용하는 경우 메일함은 소스의 수신 클러스터에 설정되고 동기화되지 않으므로 비밀번호는 그곳에 남습니다.

**원본 메일 직접 전송**: 이미 메일 시스템(Postfix의 `pipe`, SES, Mailgun의 원본 MIME)을 운영하고 있다면 원본 메시지를 수신 주소로 POST하세요:

```bash
curl -X POST 'https://<molesignal-host>/api/v1/intake/alerts' \
  -H 'Authorization: Bearer <token>' \
  -H 'Content-Type: message/rfc822' \
  --data-binary @alert.eml
```

이 방법은 해당 메일 시스템에서 수신 주소에 접근할 수 있어야 합니다. 여기서는 토큰이 이미 호출자를 알려 주므로 발신자 목록은 선택 사항입니다. 목록을 작성하면 적용됩니다.

MoleSignal에는 내장 SMTP 수신기가 없습니다. 그렇게 하려면 열린 포트 25, MX 레코드, TLS 인증서, 자체 스팸 필터링이 필요하며, 대부분의 셀프 호스팅 배포에서는 제공할 수 없습니다.

**메일을 읽는 방식**은 소스 설정의 **이메일 수신 방식**에서 지정합니다:

| 설정 | 설명 |
|---|---|
| **복구로 처리할 제목** | 정규 표현식입니다. 비워 두면 내장된 것을 사용합니다: `resolved`, `recovered`, `recovery`, `cleared`, `恢复`, `已解决`, 그리고 앞부분의 `OK`. 그 밖의 메일은 트리거로 처리합니다. |
| **제목에서 추출할 중복 제거 키** | 정규 표현식이며, 첫 번째 그룹을 사용합니다(예: `host=(\S+)`). 비어 있거나 일치하지 않으면 정리된 제목을 사용합니다. `Re:`와 `Fwd:`를 제거하고, 상태 단어(`PROBLEM`, `RECOVERY`, `告警`, `恢复` 등), 심각도, 날짜와 시간, 백분율을 대소문자 구분 없이 제거한 제목입니다. 따라서 "CRITICAL: disk full on web-1 (91%)"과 "RECOVERY: disk full on web-1 (40%)"은 하나의 알림이 되고, `web-1`과 `web-2`는 두 개가 됩니다. 발신자의 도메인도 키에 포함됩니다. |
| **알림에서 제외할 제목** | 정규 표현식입니다. 일치하는 메일은 건너뛰고 최근 수신에 표시됩니다. |

심각도는 제목의 단어에서 가져옵니다(`critical`, `fatal`, `disaster`, `P1`은 critical, `error`, `P2`는 error, `warning`, `P3`는 warning, `info`, `notice`, `P4`, `P5`는 info). 해당하는 단어가 없으면 소스의 기본 심각도를 사용합니다. `High CPU`나 `Low disk`의 high와 low는 심각도로 계산하지 않습니다. 본문은 애노테이션 `message`에(HTML 메일은 텍스트로, 최대 4096자), 발신자는 레이블 `email.from`과 애노테이션 `from`에 들어가며, 시간은 `Date` 헤더에서 가져옵니다. 자동 응답(`Auto-Submitted: auto-replied`)과 반송 메일(`multipart/report`)은 알림이 아닙니다. GBK, GB2312 및 기타 문자 집합을 인식합니다. 4MiB를 초과하는 메일은 본문을 읽지 않고 **거부됨**으로 기록됩니다.

## 경보가 인시던트가 되는 방식

| 종류 | 중복 제거 키 | 트리거 | 해결 | 심각도 |
|---|---|---|---|---|
| **API** | `dedupKey` | `trigger` | `resolve` | `severity` |
| **Alertmanager** | 외부 URL 및 `groupKey` | 그룹 `status` `firing` | 그룹 `status` `resolved`: 그룹의 모든 경보가 복구됨 | 그룹의 firing 경보 중 가장 높은 `severity` 레이블 |
| **Grafana** | 외부 URL, 조직 및 `groupKey` | 동일 | 동일 | 동일 |
| **Datadog** | 사이트, 조직, 모니터 ID 및 범위 | `Recovered`를 제외한 모든 전환 | `Recovered` | `$ALERT_PRIORITY`; 없으면 Warn과 No Data는 warning이고 나머지는 `$ALERT_TYPE`을 따릅니다 |
| **PagerDuty** | 계정 도메인 및 PagerDuty 인시던트 ID | `incident.triggered`, `incident.reopened`; `incident.priority_updated`는 심각도를 변경합니다 | `incident.resolved` | 우선순위 P1~P5; 없으면 긴급도가 high이면 error, low이면 warning입니다 |
| **Alibaba Cloud CloudMonitor** | 계정, 규칙 ID 및 `dimensions`; 시스템 이벤트의 경우 계정 및 `dedupId` | `ALERT`, `INSUFFICIENT_DATA`; 시스템 이벤트 `TRIGGERED` | `OK`; 시스템 이벤트 `RESOLVED` | `triggerLevel`; 시스템 이벤트 `severity` |
| **Tencent Cloud Observability Platform** | 계정, 정책, 메트릭 또는 이벤트 이름, 수준 및 객체 | `alarmStatus`가 `1` 또는 `5` | `alarmStatus`가 `0` | `alarmLevel` |
| **Amazon CloudWatch** | `AlarmArn` | `NewStateValue`가 `ALARM` 또는 `INSUFFICIENT_DATA` | `NewStateValue`가 `OK` | 없음: 소스의 기본 심각도 |
| **Azure Monitor** | `alertId` | `monitorCondition`이 `Fired` | `monitorCondition`이 `Resolved` | `severity`: `Sev0`는 critical, `Sev1`은 error, `Sev2`는 warning, `Sev3` 및 `Sev4`는 info |
| **Google Cloud Monitoring** | 범위 지정 프로젝트 및 `incident_id` | `state`가 `open` | `state`가 `closed` | `severity`; `No severity`는 소스의 기본값을 사용합니다 |
| **Huawei Cloud Eye** | SMN 주제의 프로젝트, `alarm_id` 및 리소스 | `alarm_status`가 `alarm` 또는 `insufficient_data` | `alarm_status`가 `ok` | 경보 수준: Critical, Major, Minor, Informational |
| **Zabbix** | `{$ZABBIX.URL}`의 호스트 및 `{EVENT.ID}` | `{EVENT.VALUE}`가 1; 업데이트 작업도 포함되며 심각도는 이를 따릅니다 | `{EVENT.VALUE}`가 0 또는 업데이트 작업이 문제를 닫음 | `{EVENT.NSEVERITY}`: Disaster는 critical, High는 error, Average 및 Warning은 warning, Information은 info |
| **이메일** | 발신자 도메인 및 제목에서 가져온 부분 | 기타 메일 | 복구로 작성된 제목 | 제목의 단어 |

우선순위와 긴급도는 별도로 해석합니다: API의 `priority`와 `urgency`, Datadog의 `$ALERT_PRIORITY`, PagerDuty의 우선순위와 긴급도가 인시던트의 우선순위와 긴급도로 사용됩니다. 긴급도가 없으면 소스의 에스컬레이션 정책이 결정하며, 심각도를 보고하지 않는 경보는 긴급도가 high입니다. [긴급도](/ko/alerting/on-call#긴급도)를 참조하세요.

심각도가 없는 경보는 소스의 **기본 심각도**를 사용합니다. 모든 발신자의 심각도 단어는 대소문자를 구분하지 않습니다: `critical`, `crit`, `fatal`, `page` 및 `P1`은 critical이고, `error`, `major`, `high` 및 `P2`는 error이며, `warning`, `warn`, `minor`, `medium` 및 `P3`는 warning이고, `info`, `low`, `P4` 및 `P5`는 info입니다. 다른 단어는 기본 심각도를 사용합니다.

- **열기**: 하나의 소스는 중복 제거 키당 최대 하나의 활성 인시던트를 가집니다. 인시던트는 `alert.source=external` 및 `external.kind=<kind>` 레이블, 경보 자체의 레이블(Alertmanager와 Grafana의 경우 그룹의 `commonLabels`), 소스의 추가 레이블을 가집니다. `service.name` 또는 `service` 레이블은 영향을 받는 서비스가 되고, `host.name`, `host` 또는 `hostname`은 호스트가 됩니다.
- **제목**: API는 `summary`를 사용하고, Alertmanager와 Grafana는 `summary` 어노테이션을 사용하며, 어노테이션이 없으면 `alertname`을 사용합니다. Datadog는 `$ALERT_TITLE`을 사용하고, PagerDuty는 인시던트 제목을 사용하며, Alibaba Cloud CloudMonitor는 "경보 이름 · 인스턴스 이름"을 사용합니다.
- **링크**: 발신자로 연결되는 주소는 `alertmanager_url`, `generator_url`, `dashboard_url`, `datadog_url` 및 `pagerduty_url`과 같은 어노테이션에 기록되며, 인시던트 페이지에 링크로 표시됩니다. API의 `links`는 `name`별로 어노테이션에 기록됩니다.
- **그룹의 경보**: Alertmanager 또는 Grafana에서 생성된 인시던트는 그룹의 모든 경보(최대 100개)를 상태와 함께 유지하며, 각 알림마다 업데이트됩니다. 인시던트 페이지의 **외부 경보**에서 이들을 나열하며, 서로 구분할 수 있는 레이블도 함께 표시합니다.
- **심각도 변경**: 아직 확인되지 않은 인시던트는 [경보 파이프라인](/ko/pipelines/alert-events#심각도-변경)이 결정하는 대로 경보의 심각도를 따릅니다. 심각도가 상승하면 에스컬레이션이 첫 단계부터 다시 시작됩니다. 수동으로 설정한 심각도는 유지됩니다.
- **확인**: API의 `acknowledge`, PagerDuty의 `incident.acknowledged`, 문제를 확인하는 Zabbix 업데이트 작업은 인시던트를 확인 처리하고 추가 에스컬레이션 단계와 호출을 중지합니다. 확인자로 기록되는 사용자는 없습니다.
- **해결**: 소스가 복구를 보고하면 인시던트가 해결되며, 확인된 인시던트도 포함됩니다. 해결한 사용자는 기록되지 않으며, 타임라인에는 복구된 것으로 표시됩니다.
- **지연 메시지**: 각 중복 제거 키는 사용한 최신 발신 시간을 기억하며, 더 오래된 메시지는 무시됩니다. 지연된 트리거는 좀비 인시던트를 열지 않고, 지연된 복구는 새 인시던트를 닫지 않습니다. API는 시간을 포함하지 않으므로 메시지는 도착하는 순서대로 처리됩니다.
- **사람이 먼저 해결한 경우**: 소스가 여전히 경보를 보고하면 다음 재전송 시 새 인시던트가 열리며, 규칙의 경우와 같습니다.
- **데이터 없음**: CloudMonitor의 `INSUFFICIENT_DATA`, Cloud Eye의 `insufficient_data` 및 Datadog의 No Data로 열린 인시던트는 `alert.condition=no_data`를 가지며, 알림 제목은 `NO DATA`로 시작합니다.
- **비활성화 및 삭제**: 비활성화된 소스는 경보를 거부하며(`409`), 열린 인시던트는 유지됩니다. 소스를 삭제하면 해당 토큰이 즉시 작동을 중지하고 열린 인시던트가 해결됩니다.

[사일런스 정책](/ko/alerting/silences), [시맨틱 그룹](/ko/alerting/silences#시맨틱-그룹) 및 [알림 정책](/ko/notification-channels)은 다른 인시던트와 마찬가지로 외부 인시던트에 적용됩니다. `external.kind`, 소스의 추가 레이블 또는 경보 자체의 레이블로 일치시킵니다.

## 최근 수신 요청

소스 페이지 상단에는 소스의 상태가 표시됩니다: **첫 요청 대기 중**, **수신 중**, **마지막 요청 거부됨**, **최근 7일간 요청 없음** 또는 **비활성화됨**. 그 옆에는 최근 24시간의 요청과 경보, 소스가 열었으며 아직 열려 있는 인시던트가 표시됩니다.

요청이 들어오면 소스 페이지의 **최근 수신 요청**에 소스가 수신한 요청이 나열됩니다: 시간, 결과(**처리됨**, **거부됨** 또는 **전달됨**), HTTP 상태, 경보 수 및 경보의 상태(**열림**, **수정일**, **변경 없음**, **확인됨**, **해결됨** 또는 **무시됨**)가 표시됩니다. 행을 클릭하면 각 경보의 제목, 심각도, 작업, 결과 및 인시던트를 볼 수 있으며, 거부된 요청은 사유와 본문 시작 부분(최대 16 KiB)도 표시합니다. 각 소스의 최근 500개 요청이 최대 7일 동안 보관됩니다.

## 여러 클러스터

[클러스터 간 페더레이션](/ko/settings/data-plane#클러스터-페더레이션)이 켜져 있을 때:

- 소스는 다른 알림 구성과 마찬가지로 토큰을 포함해 클러스터 간에 동기화되므로, 하나의 토큰이 모든 클러스터의 수신 주소에서 동작합니다.
- 소스의 인시던트는 **수신 클러스터**에서만 열립니다. 수신 클러스터는 소스가 생성된 클러스터이며, 소스 설정에서 변경하지 않는 한 그대로 유지됩니다. 소스의 알림을 수신한 다른 클러스터는 gRPC로 수신 클러스터에 전달하고, 수신 클러스터의 응답을 발신자에게 반환합니다. 따라서 하나의 외부 알림은 어느 클러스터의 주소로 도착하든 하나의 인시던트가 됩니다.
- 수신 클러스터에 연결할 수 없으면 `503`을 반환하고 발신자가 재시도합니다. 수신 클러스터의 리전이 계속 다운 상태라면 소스 설정에서 **수신 클러스터**를 정상 동작 중인 클러스터로 변경합니다.
- **최근 수신 요청**은 요청을 처리한 클러스터에 기록됩니다. 다른 클러스터에서 소스 페이지를 열면 해당 사실이 표시됩니다.

## 제한

| 항목 | 제한 |
|---|---|
| 요청 본문, 메일 1건 | 최대 4 MiB. |
| 메일함 읽기 | 한 번에 최대 50건, 나머지는 다음 차례에 처리. |
| API 요청 1건 | 알림 100건, `dedupKey`는 최대 255자, `summary`는 최대 1024자. |
| 알림 1건 | 레이블 64개와 주석 64개. API는 초과분을 거부하며, 다른 종류의 경우 초과분은 삭제되고 너무 긴 제목과 주석은 잘립니다. |
| 그룹의 알림 | 100건까지 보관. |
| 소스의 추가 레이블 | 32개, `alert.`로 시작하는 키와 `external.kind`는 사용할 수 없음. |
| 최근 수신 요청 | 각 소스의 최근 요청 500건, 최대 7일간. |

Grafana의 HMAC 서명과 PagerDuty의 서명은 확인하지 않습니다. 토큰이 이미 소스를 알려주기 때문입니다. MoleSignal에서 인시던트를 확인하거나 해결해도 발신자에게 다시 기록되지 않습니다.
