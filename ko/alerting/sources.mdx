알림 소스는 다른 시스템에서 보낸 알림을 [인시던트](/ko/alerting/incidents)로 전환합니다. 규칙에서 생성한 인시던트와 마찬가지로 [에스컬레이션 정책](/ko/alerting/on-call#에스컬레이션-정책)에 따라 담당자를 호출하고 [알림 정책](/ko/notification-channels)에 따라 알림을 보냅니다. 소스에서 복구를 보고하면 인시던트를 해결 처리합니다. **알림 → 소스**를 엽니다. 조회에는 `alerts.sources.read` 권한이 필요하고, 생성, 편집, 삭제 및 토큰 교체에는 `alerts.sources.manage` 권한이 필요합니다.

## 소스 유형

소스 유형에 따라 요청 본문을 해석할 형식이 결정됩니다.

| 유형 | 발신자 | 인시던트 생성 단위 |
|---|---|---|
| **API** | MoleSignal API를 호출하는 스크립트, CI 및 사내 시스템 | 중복 제거 키 |
| **Alertmanager** | Prometheus Alertmanager의 웹훅 수신기 | 알림 그룹 |
| **Grafana** | Grafana Alerting의 웹훅 연락 지점 | 알림 그룹 |
| **Datadog** | Datadog Webhooks 연동 | 모니터(멀티 알림 모니터는 그룹별) |
| **PagerDuty** | PagerDuty V3 웹훅 구독 | PagerDuty 인시던트 |
| **Alibaba Cloud CloudMonitor** | 임곗값 경보 콜백 및 이벤트 구독 푸시 채널 | 경보 규칙의 객체 또는 시스템 이벤트 |
| **Tencent Cloud Observability Platform** | 알림 템플릿의 API 콜백 | 정책 내 객체별 메트릭 또는 이벤트(수준이 지정된 정책은 수준별) |
| **Amazon CloudWatch** | SNS 토픽에 게시되어 해당 토픽의 HTTPS 구독을 통해 전달되는 경보 | 경보 |
| **Zabbix** | Zabbix 웹훅 미디어 유형 | 문제 |
| **이메일** | IMAP 사서함 또는 이미 운영 중인 메일 시스템에서 가져온 원본 이메일 | 제목이 같은 연속 이메일 묶음 |

Thanos, Cortex, Mimir의 Alertmanager처럼 Alertmanager 웹훅 형식을 사용하는 시스템에는 **Alertmanager** 유형을 사용합니다.

## 소스 생성

1. **알림 → 소스**를 열고 **새 경보 소스**를 클릭합니다.
2. **유형**을 선택하고 **이름**을 입력합니다.
3. **에스컬레이션 정책**을 선택합니다. 규칙 작업 공간과 마찬가지로 기본값은 **라우팅 적용(기본값)**입니다. [알림 라우팅](/ko/alerting/routing)은 라우팅 규칙, 서비스 담당 팀, 팀 레이블을 기준으로 팀과 에스컬레이션 정책을 선택합니다. 적용할 정책이 없으면 이름이 `default`인 [기본 정책](/ko/alerting/on-call#기본-정책)을 사용합니다. 정책을 직접 선택하면 인시던트에 해당 정책을 적용하고, 라우팅은 팀만 선택합니다. **에스컬레이션 없음, 알림 정책만 적용**을 선택하면 인시던트를 생성하고 알림을 보내지만 에스컬레이션 정책에 따른 호출은 하지 않습니다.
4. 알림에 심각도가 지정되지 않았을 때 사용할 **기본 심각도**를 선택합니다.
5. 필요한 경우 `team=payments`와 같은 **추가 레이블**을 지정합니다. 소스가 생성하는 모든 인시던트에 이 레이블을 추가합니다. 같은 키의 레이블이 알림에 이미 있으면 알림의 값을 우선 적용합니다.
6. **생성**을 클릭합니다. 소스 페이지가 열리고, 대화 상자에 토큰과 토큰이 입력된 설정 예시가 표시됩니다. Alibaba Cloud CloudMonitor에는 수신 주소만 필요하므로 토큰이 포함된 주소를 표시합니다.

<Warning>
  토큰은 소스를 생성하거나 토큰을 교체할 때만 표시합니다. 대화 상자를 닫으면 `mspat-`로 시작하는 접두사만 확인할 수 있습니다. 토큰을 분실한 경우 **토큰 교체**를 클릭해 새 토큰을 발급합니다. 기존 토큰은 즉시 작동을 멈춥니다.
</Warning>

## 수신 주소와 토큰

모든 소스는 같은 수신 주소를 사용합니다. 토큰으로 알림이 어느 소스에 속하는지 식별합니다.

```text
https://<molesignal-host>/api/v1/intake/alerts
```

토큰은 API 토큰과 같은 `mspat-<36>` 형식을 사용하지만, 알림 수신에만 사용할 수 있습니다. API 토큰으로는 알림을 수신할 수 없습니다. 발신자는 토큰을 헤더에 넣습니다.

```text
Authorization: Bearer <token>
```

헤더를 설정할 수 없는 발신자(Alibaba Cloud CloudMonitor, Tencent Cloud Observability Platform, SNS를 사용하는 Amazon CloudWatch)는 주소에 토큰을 넣습니다: `https://<molesignal-host>/api/v1/intake/alerts?token=<token>`.

발신자는 이 주소에 연결할 수 있어야 합니다. MoleSignal 앞에 방화벽이 있으면 발신자 사이트 또는 리전의 발신 IP 주소를 허용합니다. Datadog은 `ip-ranges`의 `webhooks` 섹션에 사이트별 주소를 나열하고, PagerDuty는 미국 및 유럽 연합 서비스 리전의 주소를 공개하며, Alibaba Cloud CloudMonitor는 경보 콜백 문서에 푸시 IP 주소 범위를 나열합니다. MoleSignal을 내부 네트워크에서 실행하는 경우 이 주소만 인터넷에 공개하는 방법은 [공개 액세스](/ko/public-access)를 참조합니다.

## 발신 시스템 설정

소스 페이지의 **수신**에서 수신 주소, 토큰, 유형별 설정 방법을 세 단계로 안내합니다. `<TOKEN>`을 소스의 토큰으로 바꿉니다. 소스가 첫 요청을 받으면 세 단계가 모두 완료로 표시됩니다.

### API

```bash
curl -X POST https://<molesignal-host>/api/v1/intake/alerts \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{"dedupKey": "disk-full/web-1", "summary": "Disk almost full on web-1", "severity": "critical", "labels": {"host.name": "web-1"}}'
```

`action`에는 `trigger`(기본값), `acknowledge`, `resolve` 중 하나를 지정합니다. 동일한 알림을 확인하거나 해결하려면 같은 `dedupKey`를 사용합니다. [알림 보내기](/ko/api/alerting/send-alerts)에서 각 필드를 설명합니다.

### Alertmanager

`alertmanager.yml`에 수신기를 추가하고 알림을 해당 수신기로 라우팅합니다.

```yaml
route:
  receiver: molesignal
receivers:
  - name: molesignal
    webhook_configs:
      - url: https://<molesignal-host>/api/v1/intake/alerts
        send_resolved: true
        http_config:
          authorization:
            credentials: <token>
```

복구 알림을 보내려면 `send_resolved`를 `true`로 유지합니다. 같은 Alertmanager 클러스터의 모든 복제본에 동일한 `--web.external-url`을 지정합니다. 외부 URL은 중복 제거 키의 일부이므로, 라우팅이 동일하더라도 여러 리전의 Alertmanager에서 보낸 이름이 같은 그룹은 하나의 인시던트로 병합되지 않습니다.

### Grafana

1. Grafana에서 **알림 → 연락 지점**을 열고 **연락 지점 추가**를 클릭합니다.
2. **통합**을 **웹훅**으로 설정하고 **URL**에 수신 주소를 입력합니다.
3. **선택적 웹훅 설정**에서 **인증 헤더 방식**을 `Bearer`로 설정하고 **인증 헤더 자격 증명**에 토큰을 입력합니다.
4. **해결 메시지 비활성화**를 선택하지 않은 상태로 저장한 후 알림 정책에서 해당 연락 지점을 사용합니다.

파일로 프로비저닝하는 경우:

```yaml
apiVersion: 1
contactPoints:
  - orgId: 1
    name: molesignal
    receivers:
      - uid: molesignal
        type: webhook
        settings:
          url: https://<molesignal-host>/api/v1/intake/alerts
          httpMethod: POST
          authorization_scheme: Bearer
          authorization_credentials: <token>
```

### Datadog

1. Datadog에서 **통합 → 웹훅**을 열고 웹훅을 추가합니다. 이름은 예를 들어 `molesignal`로 지정합니다.
2. **URL**에 수신 주소를 입력하고 **사용자 지정 헤더**에 `{"Authorization": "Bearer <token>"}`을 설정합니다. **폼으로 인코딩**은 선택하지 않습니다.
3. **페이로드**에 아래 템플릿을 설정합니다. 필드 이름은 MoleSignal에서 정의하며, 값에는 Datadog 변수를 사용합니다. 이 템플릿을 사용하지 않는 요청은 거부합니다.

```json
{
  "alert_id": "$ALERT_ID",
  "alert_cycle_key": "$ALERT_CYCLE_KEY",
  "transition": "$ALERT_TRANSITION",
  "alert_type": "$ALERT_TYPE",
  "priority": "$ALERT_PRIORITY",
  "title": "$ALERT_TITLE",
  "event_title": "$EVENT_TITLE",
  "message": "$TEXT_ONLY_MSG",
  "scope": "$ALERT_SCOPE",
  "tags": "$TAGS",
  "hostname": "$HOSTNAME",
  "link": "$LINK",
  "snapshot": "$SNAPSHOT",
  "query": "$ALERT_QUERY",
  "org_id": "$ORG_ID",
  "last_updated": "$LAST_UPDATED"
}
```

4. 모니터의 알림 메시지에서 `@webhook-molesignal`을 멘션합니다.

모든 Datadog 사이트(`datadoghq.com`, `datadoghq.eu`, `us3`, `us5`, `ap1` 등)에서 하나의 소스로 알림을 보낼 수 있습니다. MoleSignal은 `$LINK`의 도메인에서 사이트를 식별하고, 조직 ID와 함께 중복 제거 키에 포함합니다.

### PagerDuty

1. PagerDuty에서 **통합 → 일반 웹훅(v3)**을 열고 **새 웹훅**을 클릭합니다.
2. **웹훅 URL**에 수신 주소를 입력하고 **범위 유형**(계정, 서비스 또는 팀)을 선택합니다.
3. **이벤트 구독**에서 `incident.triggered`, `incident.acknowledged`, `incident.resolved`, `incident.reopened`, `incident.priority_updated`를 선택합니다.
4. 값이 `Bearer <token>`인 사용자 지정 헤더 `Authorization`을 추가합니다.

미국 및 EU 서비스 리전의 계정에서 하나의 소스로 알림을 보낼 수 있습니다. MoleSignal은 계정 도메인(`<subdomain>.pagerduty.com` 또는 `<subdomain>.eu.pagerduty.com`)을 중복 제거 키에 포함하고 `pagerduty.region` 레이블에도 기록합니다.

### Alibaba Cloud CloudMonitor

수신 주소에 토큰을 추가합니다.

```text
https://<molesignal-host>/api/v1/intake/alerts?token=<token>
```

- **임계값 알림**: 알림 규칙의 **알림 콜백**에 이 주소를 입력합니다. CloudMonitor는 콜백을 폼 인코딩하여 POST로 전송합니다. MoleSignal은 JSON도 처리합니다.
- **시스템 이벤트**: **이벤트 센터 → 이벤트 구독 → 푸시 채널**에서 대상 유형을 **웹훅**, 요청 메서드를 **POST**, 데이터 형식을 **JSON**으로 지정하여 채널을 생성합니다. 이 주소를 입력하고 구독 정책에서 채널을 사용합니다.

CloudMonitor는 시스템 이벤트 콜백의 응답을 5초 동안 기다리고 3회 재시도합니다. MoleSignal은 요청을 [수신 클러스터](#여러-클러스터)에 전달할 때 최대 3초 동안 기다립니다. 시간이 초과되면 `503`으로 응답하여 CloudMonitor가 재시도하도록 합니다. 중국 사이트와 국제 사이트의 모든 리전은 같은 형식으로 전송합니다. MoleSignal은 리전을 `aliyun.region` 레이블에 기록하고 계정의 `userId`를 중복 제거 키에 포함합니다.

### Tencent Cloud Observability Platform

Tencent Cloud Observability Platform(이전 이름: Cloud Monitor)의 **알림 관리 → 알림 템플릿**에서 템플릿을 편집하거나 생성합니다. **API 콜백**에 수신 주소를 입력하고 템플릿을 알림 정책에 연결합니다. Tencent Cloud 콜백은 헤더를 설정할 수 없으므로 주소에 토큰을 포함합니다. 콜백에 서명이 없고 주소로 소스를 식별하므로 수신 주소를 자격 증명처럼 보호합니다. 메트릭 알림과 이벤트 알림을 모두 지원하며 발생과 복구를 모두 전송합니다.

- **중복 제거**: 계정, 알림 정책, 메트릭 또는 이벤트 이름, 대상 객체가 모두 같으면 하나의 알림으로 처리합니다. 단계가 있는 정책은 Tencent Cloud와 마찬가지로 단계마다 인시던트를 하나씩 생성하고 각각 독립적으로 복구합니다.
- **심각도**: `alarmLevel`이 Serious(`Serious`)이면 치명적, Severe(`Warn`)이면 오류, Reminder(`Remind`)이면 정보로 처리합니다. 단계가 없는 정책에는 소스의 기본 심각도를 적용합니다.
- **상태 없는 이벤트**(`alarmStatus`가 `5`)는 복구 없이 인시던트를 열므로 수동으로 해결해야 합니다.
- 콜백의 **시간**에는 시간대가 없으므로 베이징 시간으로 해석합니다.

### Amazon CloudWatch

CloudWatch 알림은 외부 주소를 직접 호출하지 않고 SNS를 통해 전송합니다.

1. 알림의 통지 설정에서 **알림 상태**(`ALARM`)로 전환될 때와 **정상**으로 돌아올 때 모두 같은 SNS 주제로 전송합니다. `OK`를 보내지 않으면 인시던트를 자동으로 해결하지 않습니다. 데이터 없음 알림이 필요하면 **데이터 부족**(`INSUFFICIENT_DATA`)도 전송합니다.
2. SNS 주제에 HTTPS 구독을 추가합니다. 수신 주소를 엔드포인트로 지정하고 주소에 토큰을 포함합니다.

   ```bash
   aws sns subscribe \
     --topic-arn <ARN of the topic> \
     --protocol https \
     --notification-endpoint 'https://<molesignal-host>/api/v1/intake/alerts?token=<token>'
   ```

3. MoleSignal이 구독을 자동으로 확인합니다. 확인 메시지의 서명을 검증한 다음 메시지의 `SubscribeURL`에 접속합니다.

MoleSignal은 모든 SNS 메시지의 서명을 검증하므로 **원시 메시지 전송**을 비활성화한 상태로 유지해야 합니다. 이 옵션을 활성화하면 MoleSignal은 메시지를 거부하고 소스 페이지의 최근 수신 내역에 이유를 표시합니다. 서명 인증서는 `sns.<region>.amazonaws.com`에서 가져오므로 요청을 받는 노드가 해당 주소에 접속할 수 있어야 합니다.

CloudWatch 알림에는 심각도가 없으므로 인시던트에 소스의 기본 심각도를 적용합니다. 복합 알림에도 알림의 ARN을 중복 제거 키로 사용합니다. 알림 설명과 상태 변경 사유는 주석에 기록합니다. 리전, 계정, 네임스페이스, 메트릭, 차원은 레이블에 기록하므로 `aws.region` 같은 레이블을 기준으로 라우팅할 수 있습니다.

### Zabbix

Zabbix 6.0부터 지원합니다. Zabbix에는 고유한 요청 형식이 없으며 미디어 유형의 스크립트가 요청을 전송합니다. 소스 페이지와 소스 생성 대화 상자에서 주소와 토큰이 채워진 미디어 유형을 제공합니다.

1. 미디어 유형을 YAML로 저장하고 **알림 → 미디어 유형 → 가져오기**에서 가져옵니다. `token` 매개변수를 확인합니다.
2. 전역 매크로 `{$ZABBIX.URL}`을 Zabbix 프런트엔드 주소로 설정합니다. 이 주소를 중복 제거 키에 포함하므로 한 소스에서 여러 Zabbix 서버의 알림을 받을 수 있으며, 인시던트에서 Zabbix로 이동할 수 있습니다. 이 매크로를 설정하지 않아도 알림 수신은 동작합니다.
3. 사용자에게 이 미디어를 할당합니다. 스크립트는 **전달 대상**을 사용하지 않으므로 아무 값이나 입력해도 됩니다.
4. 트리거 동작을 추가하고 **작업**, **복구 작업**, **업데이트 작업**을 모두 해당 사용자에게 보냅니다. 복구 작업이 없으면 인시던트가 자동으로 해결되지 않습니다.

미디어 유형의 **테스트** 버튼을 사용하려면 실제 값을 입력해야 합니다. 매크로가 치환되지 않아 `{EVENT.ID}`가 그대로 도착하면 MoleSignal은 `400`으로 응답하고 문서에서 제공하는 미디어 유형을 사용하라고 안내합니다.

### 이메일

이메일을 받는 방법은 두 가지이며, 두 방법 모두 같은 방식으로 이메일을 알림으로 처리합니다.

**메일함 읽기**(권장): MoleSignal은 일정한 간격으로 IMAP 메일함을 읽습니다. 아웃바운드 연결과 메일함만 있으면 됩니다. 공개 주소, MX 레코드, 25번 포트 또는 인증서가 필요하지 않아 자체 호스팅에서 가장 간편합니다. 모니터링 시스템의 알림 이메일을 해당 메일함으로 보내거나 메일 규칙으로 전달합니다.

소스 페이지의 **메일함 읽기**에서 **IMAP 서버**, **포트**, **암호화**, **사용자 이름**, **비밀번호**, **폴더**(기본값 `INBOX`), **읽기 간격**(15~3600초, 기본값 60초)을 입력합니다. **연결 테스트**를 클릭한 다음 **메일함 저장**을 클릭합니다.

- **읽기 전용**: `EXAMINE`과 `BODY.PEEK[]`를 사용하므로 이메일을 읽음으로 표시하거나 삭제하지 않습니다. 읽기 전용 계정으로 충분합니다.
- **기존 메일은 읽지 않음**: 처음 연결할 때 현재 위치를 기록하고 이후 도착한 이메일만 읽습니다. 호스트, 계정 또는 폴더를 변경하거나 서버가 메일함을 재구축한 경우(`UIDVALIDITY`가 변경된 경우) 해당 시점부터 다시 시작합니다. 소스를 비활성화하면 이메일을 읽지 않고 위치도 보관하지 않습니다. 소스를 다시 활성화한 시점부터 읽기 시작합니다.
- **발신자 목록 필수**: 메일함 주소를 아는 사람은 누구나 이메일을 보낼 수 있습니다. 소스 설정의 **허용 발신자**에 이메일 주소를 입력하거나 전체 도메인을 허용하려면 `@example.com` 형식으로 입력합니다. `*`는 모든 발신자를 허용합니다. 이 목록은 위조할 수 있는 `From` 헤더를 기준으로 검사하므로 메일 공급자의 스팸 필터링과 DMARC를 활성화한 상태로 유지합니다. 목록에 없는 발신자의 이메일은 **거부됨**으로 기록하며 인시던트를 열지 않습니다.
- **로그인**: 비밀번호 또는 메일 공급자가 발급한 앱 비밀번호를 사용합니다. Microsoft 365는 더 이상 비밀번호 인증을 지원하지 않습니다. **OAuth 2.0**을 선택하고 토큰 주소 `https://login.microsoftonline.com/<tenant>/oauth2/v2.0/token`, 클라이언트 ID, 클라이언트 시크릿, 범위 `https://outlook.office365.com/.default`를 입력합니다. 애플리케이션에는 `IMAP.AccessAsApp` 권한과 해당 메일함에 대한 액세스 권한이 필요합니다.
- **암호화 없음**은 신뢰할 수 있는 네트워크에서만 사용합니다. 이 설정에서는 네트워크를 통해 비밀번호를 평문으로 전송합니다.
- 메일을 읽지 못하면 소스 페이지에 이유를 표시하고 다음 주기에 다시 시도합니다. 알림 노드가 여러 개여도 각 메일함은 노드 하나만 읽습니다. 페더레이션 환경에서는 소스의 수신 클러스터에 메일함을 설정합니다. 메일함 설정을 동기화하지 않으므로 비밀번호는 해당 클러스터에만 저장합니다.

**원본 이메일 POST 전송**: 이미 메일 시스템(Postfix의 `pipe`, SES, Mailgun의 원시 MIME)을 운영 중이면 원본 메시지를 수신 주소로 POST 전송합니다.

```bash
curl -X POST 'https://<molesignal-host>/api/v1/intake/alerts' \
  -H 'Authorization: Bearer <token>' \
  -H 'Content-Type: message/rfc822' \
  --data-binary @alert.eml
```

이 방식을 사용하려면 메일 시스템에서 수신 주소에 접속할 수 있어야 합니다. 토큰으로 호출자를 식별하므로 발신자 목록은 선택 사항입니다. 목록을 설정하면 해당 목록을 적용합니다.

MoleSignal에는 SMTP 수신기가 내장되어 있지 않습니다. SMTP 수신에는 열린 25번 포트, MX 레코드, TLS 인증서, 자체 스팸 필터링이 필요하며, 대부분의 자체 호스팅 환경에서는 이러한 요건을 충족하기 어렵습니다.

**이메일 처리 방식**은 소스 설정의 **이메일 수신 방식**에서 지정합니다.

| 설정 | 설명 |
|---|---|
| **복구로 처리할 제목** | 정규식을 입력합니다. 비워 두면 내장 정규식을 사용합니다. 이 정규식은 `resolved`, `recovered`, `recovery`, `cleared`, `恢复`, `已解决` 또는 제목 맨 앞의 `OK`와 일치합니다. 그 외 이메일은 알림을 발생시킵니다. |
| **제목에서 추출할 중복 제거 키** | 정규식을 입력합니다. `host=(\S+)`처럼 첫 번째 캡처 그룹을 사용합니다. 비워 두거나 일치하는 항목이 없으면 정리된 제목을 사용합니다. 대소문자를 구분하지 않고 `Re:`와 `Fwd:`, 상태 단어(`PROBLEM`, `RECOVERY`, `告警`, `恢复` 등), 심각도, 날짜와 시간, 백분율을 제거합니다. 따라서 "CRITICAL: disk full on web-1 (91%)"과 "RECOVERY: disk full on web-1 (40%)"은 하나의 알림으로 처리하지만, `web-1`과 `web-2`는 별개로 처리합니다. 발신자 도메인도 키에 포함합니다. |
| **알림에서 제외할 제목** | 정규식을 입력합니다. 일치하는 이메일은 알림으로 처리하지 않으며 최근 수신 내역에 표시합니다. |

제목의 단어로 심각도를 결정합니다(`critical`, `fatal`, `disaster`, `P1`은 치명적, `error`, `P2`는 오류, `warning`, `P3`는 경고, `info`, `notice`, `P4`, `P5`는 정보). 해당 단어가 없으면 소스의 기본 심각도를 적용합니다. `High CPU`의 `High`와 `Low disk`의 `Low`는 심각도 판정에 사용하지 않습니다. 본문은 `message` 주석에 기록합니다(HTML 이메일은 텍스트로 변환하고 최대 4096자까지 기록합니다). 발신자는 `email.from` 레이블과 `from` 주석에 기록하고, 시간은 `Date` 헤더에서 가져옵니다. 자동 회신(`Auto-Submitted: auto-replied`)과 반송 메일(`multipart/report`)은 알림으로 처리하지 않습니다. GBK, GB2312 등의 문자 집합을 지원합니다. 4 MiB를 초과하는 이메일은 본문을 읽지 않고 **거부됨**으로 기록합니다.

## 경보가 인시던트로 전환되는 방식

| 유형 | 중복 제거 키 | 트리거 | 해결 | 심각도 |
|---|---|---|---|---|
| **API** | `dedupKey` | `trigger` | `resolve` | `severity` |
| **Alertmanager** | 외부 URL과 `groupKey` | 그룹의 `status`가 `firing` | 그룹의 `status`가 `resolved`: 그룹 내 모든 경보가 복구됨 | 그룹에서 발생 중인 경보의 `severity` 레이블 중 가장 높은 값 |
| **Grafana** | 외부 URL, 조직, `groupKey` | 위와 동일 | 위와 동일 | 위와 동일 |
| **Datadog** | 사이트, 조직, 모니터 ID, 범위 | `Recovered`를 제외한 모든 상태 전환 | `Recovered` | `$ALERT_PRIORITY`를 사용합니다. 값이 없으면 Warn과 No Data는 경고로 처리하고, 나머지는 `$ALERT_TYPE`을 따릅니다. |
| **PagerDuty** | 계정 도메인과 PagerDuty 인시던트 ID | `incident.triggered`, `incident.reopened`로 트리거합니다. `incident.priority_updated`는 심각도를 변경합니다. | `incident.resolved` | 우선순위 P1~P5를 사용합니다. 우선순위가 없으면 긴급도가 높을 때는 오류, 낮을 때는 경고로 처리합니다. |
| **Alibaba Cloud CloudMonitor** | 계정, 규칙 ID, `dimensions`. 시스템 이벤트는 계정과 `dedupId` | `ALERT`, `INSUFFICIENT_DATA`. 시스템 이벤트는 `TRIGGERED` | `OK`. 시스템 이벤트는 `RESOLVED` | `triggerLevel`. 시스템 이벤트는 `severity` |
| **Tencent Cloud Observability Platform** | 계정, 정책, 메트릭 또는 이벤트 이름, 수준, 객체 | `alarmStatus`가 `1` 또는 `5` | `alarmStatus`가 `0` | `alarmLevel` |
| **Amazon CloudWatch** | `AlarmArn` | `NewStateValue`가 `ALARM` 또는 `INSUFFICIENT_DATA` | `NewStateValue`가 `OK` | 없음: 소스의 기본 심각도 사용 |
| **Zabbix** | `{$ZABBIX.URL}`의 호스트와 `{EVENT.ID}` | `{EVENT.VALUE}`가 1이면 트리거합니다. 업데이트 작업도 트리거하며 심각도는 해당 업데이트를 따릅니다. | `{EVENT.VALUE}`가 0이거나 업데이트 작업이 문제를 종료함 | `{EVENT.NSEVERITY}`: Disaster는 심각, High는 오류, Average와 Warning은 경고, Information은 정보 |
| **이메일** | 발신자 도메인과 제목에서 추출한 부분 | 그 외 이메일 | 복구를 나타내는 제목 | 제목에 포함된 단어 |

우선순위와 긴급도를 별도로 읽습니다. API의 `priority`와 `urgency`, Datadog의 `$ALERT_PRIORITY`, PagerDuty의 우선순위와 긴급도를 인시던트의 해당 값으로 사용합니다. 긴급도가 없으면 소스의 에스컬레이션 정책을 따릅니다. 심각도를 보고하지 않는 경보는 긴급도를 높음으로 설정합니다. [긴급도](/ko/alerting/on-call#긴급도)를 참조합니다.

심각도가 없는 경보에는 소스의 **기본 심각도**를 적용합니다. 모든 발신자의 심각도 값은 대소문자를 구분하지 않습니다. `critical`, `crit`, `fatal`, `page`, `P1`은 심각, `error`, `major`, `high`, `P2`는 오류, `warning`, `warn`, `minor`, `medium`, `P3`는 경고, `info`, `low`, `P4`, `P5`는 정보로 처리합니다. 그 외의 값에는 기본 심각도를 적용합니다.

- **열기**: 소스마다 중복 제거 키별로 활성 인시던트를 최대 하나만 유지합니다. 인시던트에는 `alert.source=external`과 `external.kind=<kind>` 레이블, 경보 자체의 레이블(Alertmanager와 Grafana는 그룹의 `commonLabels`), 소스의 추가 레이블이 포함됩니다. `service.name` 또는 `service` 레이블은 영향을 받는 서비스로, `host.name`, `host`, `hostname` 레이블은 호스트로 표시합니다.
- **제목**: API는 `summary`를 사용합니다. Alertmanager와 Grafana는 `summary` 어노테이션을 사용하고, 없으면 `alertname`을 사용합니다. Datadog은 `$ALERT_TITLE`을, PagerDuty는 인시던트 제목을, Alibaba Cloud CloudMonitor는 "경보 이름 · 인스턴스 이름"을 사용합니다.
- **링크**: 발신 시스템으로 연결되는 주소를 `alertmanager_url`, `generator_url`, `dashboard_url`, `datadog_url`, `pagerduty_url` 등의 어노테이션에 기록하고 인시던트 페이지에 링크로 표시합니다. API의 `links`는 각 항목의 `name`을 키로 사용해 어노테이션에 기록합니다.
- **그룹 내 경보**: Alertmanager 또는 Grafana의 인시던트는 그룹 내 경보와 각 상태를 최대 100개까지 유지하고, 알림을 받을 때마다 업데이트합니다. 인시던트 페이지의 **외부 경보**에는 각 경보와 이를 구분하는 레이블이 표시됩니다.
- **심각도 변경**: 아직 확인하지 않은 인시던트는 [경보 파이프라인](/ko/pipelines/alert-events#심각도-변경)이 결정한 경보의 심각도를 따릅니다. 심각도가 높아지면 첫 단계부터 에스컬레이션을 다시 시작합니다. 수동으로 설정한 심각도는 유지합니다.
- **확인**: API의 `acknowledge`, PagerDuty의 `incident.acknowledged`, 문제를 확인하는 Zabbix 업데이트 작업은 인시던트를 확인 처리하고 이후 에스컬레이션 단계와 전화 호출을 중지합니다. 확인한 사용자는 기록하지 않습니다.
- **해결**: 소스가 복구를 보고하면 이미 확인한 인시던트도 해결 처리합니다. 해결한 사용자는 기록하지 않으며, 타임라인에는 복구로 표시합니다.
- **늦게 도착한 메시지**: 중복 제거 키별로 처리에 사용한 최신 발신 시각을 보관하고, 그보다 오래된 메시지는 무시합니다. 늦게 도착한 트리거는 이미 끝난 인시던트를 다시 열지 않고, 늦게 도착한 복구 메시지는 새 인시던트를 종료하지 않습니다. API 메시지에는 시각 정보가 없으므로 도착 순서대로 처리합니다.
- **수동으로 먼저 해결한 경우**: 소스가 계속 경보를 보고하면 규칙 기반 경보와 마찬가지로 다음 재전송 시 새 인시던트를 엽니다.
- **데이터 없음**: CloudMonitor의 `INSUFFICIENT_DATA`와 Datadog의 No Data로 열린 인시던트에는 `alert.condition=no_data` 레이블을 추가합니다. 해당 알림의 제목은 `NO DATA`로 시작합니다.
- **비활성화 및 삭제**: 비활성화한 소스는 경보를 거부하고(`409`), 기존 인시던트는 열린 상태로 유지합니다. 소스를 삭제하면 토큰이 즉시 무효화되고 해당 소스의 열린 인시던트를 해결 처리합니다.

[알림 음소거 정책](/ko/alerting/silences), [의미 기반 그룹](/ko/alerting/silences#시맨틱-그룹), [알림 정책](/ko/notification-channels)은 다른 인시던트와 마찬가지로 외부 인시던트에도 적용합니다. `external.kind`, 소스의 추가 레이블, 경보 자체의 레이블을 기준으로 매칭합니다.

## 최근 수신 요청

소스 페이지 상단에 소스 상태를 표시합니다. 상태는 **첫 요청 대기 중**, **수신 중**, **마지막 요청 거부됨**, **최근 7일간 요청 없음**, **비활성화됨** 중 하나입니다. 상태 옆에는 최근 24시간 동안의 요청 및 경보 수와 해당 소스가 연 인시던트 중 아직 열린 인시던트 수를 표시합니다.

요청을 수신하면 소스 페이지의 **최근 수신 요청**에 수신 시각, 처리 결과(**처리됨**, **거부됨**, **전달됨**), HTTP 상태, 경보 수와 경보별 처리 결과(**열림**, **수정일**, **변경 없음**, **확인됨**, **해결됨**, **무시됨**)를 표시합니다. 행을 클릭하면 각 경보의 제목, 심각도, 작업, 결과, 인시던트를 확인할 수 있습니다. 거부된 요청은 거부 사유와 요청 본문의 앞부분(최대 16 KiB)도 표시합니다. 소스별로 최근 요청 500건을 최대 7일간 보관합니다.

## 여러 클러스터

[클러스터 간 페더레이션](/ko/settings/data-plane#클러스터-페더레이션)을 활성화하면 다음과 같이 동작합니다.

- 다른 경보 설정과 마찬가지로 소스와 토큰을 클러스터 간에 동기화합니다. 따라서 하나의 토큰을 모든 클러스터의 수신 주소에서 사용할 수 있습니다.
- 소스의 인시던트는 해당 소스의 **수신 클러스터**에서만 엽니다. 소스 설정에서 변경하지 않으면 소스를 생성한 클러스터가 수신 클러스터가 됩니다. 다른 클러스터가 해당 소스의 경보를 받으면 gRPC로 수신 클러스터에 전달하고, 수신 클러스터의 응답을 발신자에게 반환합니다. 따라서 어느 클러스터 주소로 도착하든 외부 경보 하나는 인시던트 하나로 처리합니다.
- 수신 클러스터에 연결할 수 없으면 `503`을 반환하고 발신자가 재시도합니다. 수신 클러스터가 있는 리전의 장애가 지속되면 소스 설정에서 **수신 클러스터**를 정상 작동하는 클러스터로 변경합니다.
- **최근 수신 요청**은 요청을 처리한 클러스터에 기록합니다. 다른 클러스터에서 소스 페이지를 열면 이 사실을 안내합니다.

## 제한

| 항목 | 제한 |
|---|---|
| 메일 한 통의 요청 본문 | 최대 4 MiB입니다. |
| 메일함 읽기 | 한 번에 최대 50통을 읽고, 나머지는 다음 차례에 읽습니다. |
| API 요청 한 건 | 알림은 최대 100개, `dedupKey`는 최대 255자, `summary`는 최대 1024자입니다. |
| 알림 한 건 | 라벨과 주석은 각각 최대 64개입니다. API는 한도를 초과한 요청을 거부합니다. 다른 유형의 소스에서는 초과 항목을 무시하고, 길이 한도를 넘는 제목과 주석은 잘라냅니다. |
| 그룹 내 알림 | 최대 100개를 보관합니다. |
| 소스의 추가 라벨 | 최대 32개입니다. 키는 `alert.`로 시작할 수 없으며 `external.kind`를 사용할 수 없습니다. |
| 최근 수신 요청 | 소스별로 최근 요청 500건을 최대 7일간 보관합니다. |

토큰으로 소스를 식별하므로 Grafana의 HMAC 서명과 PagerDuty의 서명을 확인하지 않습니다. MoleSignal에서 인시던트를 확인하거나 해결해도 발신 측에는 반영하지 않습니다.
