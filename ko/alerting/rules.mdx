규칙은 발생하면 안 되는 상황을 정의합니다. MoleSignal은 일정한 간격으로 규칙을 평가하고 조건이 충족되면
[인시던트](/ko/alerting/incidents)를 생성합니다. **알림 → 규칙**을 엽니다. 규칙을 조회하려면
`alerts.rules.read` 권한이 필요하고, 규칙을 생성하거나 변경하려면 `alerts.rules.manage` 권한이 필요합니다.

## 규칙 유형

| 유형 | 평가 방식 | 생성 위치 |
|---|---|---|
| **임계값 규칙** | SQL 또는 PromQL 쿼리, [APM 지표](/ko/apm#apm-지표에-알림-설정), [RUM 지표](/ko/rum/alerts)를 일정한 간격으로 고정 임계값과 비교합니다. | 규칙 편집 화면. |
| **예측 규칙** | 쿼리 결과, APM 지표, RUM 지표의 추세를 평가합니다. 지정한 예측 시간 내에 임계값을 넘을 것으로 예상되면 트리거됩니다. [예측 규칙](#예측-규칙)을 참조합니다. | 규칙 편집 화면의 **트리거 유형**. |
| **이상치 규칙** | 쿼리 결과를 열 기준으로 그룹화하고 그룹을 서로 비교합니다. 다른 그룹과 뚜렷하게 다른 그룹이 있으면 해당 그룹에서 트리거됩니다. [이상치 규칙](#이상치-규칙)을 참조합니다. | 규칙 편집 화면의 **트리거 유형**. |
| **복합 규칙** | 다른 규칙에 미해결 인시던트가 있는지를 AND, OR, NOT 논리 연산으로 조합해 평가합니다. [복합 규칙](#복합-규칙)을 참조합니다. | 규칙 편집 화면의 **트리거 유형**. |
| **하트비트 규칙** | cron 작업이나 백업 스크립트가 정해진 시간에 실행 신호를 보냈는지 확인합니다. [하트비트 규칙](#하트비트-규칙)을 참조합니다. | 규칙 편집 화면의 **트리거 유형**. |
| **이상 탐지** | 쿼리 결과, APM 지표, RUM 지표를 과거 데이터에서 학습한 기준선과 비교합니다. | 이상 탐지 편집 화면. |
| **실시간 규칙** | 수집 경로로 들어오는 레코드를 도착 즉시 집계합니다. | API에서만 생성합니다. [실시간 규칙](#실시간-규칙)을 참조합니다. |

## 규칙 목록

**규칙**에는 모든 규칙의 데이터 소스, 트리거 조건, 상태, 마지막 평가가 표시됩니다.
규칙, 서비스 또는 소스로 검색하고 **전체**, **활성화**,
**비활성화됨** 사이를 전환합니다.

| 상태 | 의미 |
|---|---|
| **평가되지 않음** | 규칙을 아직 실행하지 않았습니다. |
| **정상** | 마지막 평가에서 조건을 충족하지 않았습니다. |
| **대기 중** | 조건을 충족했지만 필요한 시간만큼 유지되지 않았습니다. |
| **발생 중** | 규칙에 미해결 인시던트가 있습니다. |
| **파이프라인에서 제외됨** | 규칙이 트리거되었지만 [알림 파이프라인](/ko/pipelines/alert-events#이벤트-처리-결과)이 생성될 인시던트를 제외했습니다. |
| **비활성화됨** | 규칙이 초안으로 저장되어 실행되지 않습니다. |

규칙을 열려면 해당 규칙이나 해당 행의 **편집**을 선택합니다.

## 임계값 규칙 생성

**새 규칙 → 임계값 규칙**을 선택해 규칙 편집 화면을 엽니다.

<Steps>
  <Step title="규칙 유형 선택">
    **메트릭 알림**, **로그 알림**, **트레이스 알림**, **APM 알림**, **RUM 알림** 중 하나를 선택합니다.
    **빠른 시작**에서 **높은 오류율**, **높은 P95
    지연 시간**, **오류 로그 급증**, **데이터 없음** 등의 프리셋을 선택하면 일반적인 쿼리가 자동으로 입력됩니다. APM 및 RUM 알림에서는 쿼리 대신 서비스 또는 애플리케이션과
    지표를 선택합니다. [APM 지표에 대한 알림 설정](/ko/apm#apm-지표에-알림-설정) 및
    [RUM 알림](/ko/rum/alerts)을 참조합니다.
  </Step>
  <Step title="기본 정보 입력">
    **규칙 이름**은 인시던트 제목으로 사용합니다(예: `api_high_error_rate`). **서비스**는 규칙을 서비스에 연결해
    담당을 명확히 하고 여러 신호를 함께 살펴볼 수 있도록 합니다. **설명**에는 규칙으로 무엇을 보호하는지 적습니다.
  </Step>
  <Step title="트리거 유형 선택">
    **쿼리 및 트리거 조건** 상단에서 **트리거 유형**을 선택합니다. **임계값**(기본값),
    [**예측**](#예측-규칙), [**이상치**](#이상치-규칙), [**복합**](#복합-규칙),
    [**하트비트**](#하트비트-규칙) 중 하나를 선택합니다. 복합 및 하트비트 규칙은 쿼리를 사용하지 않습니다. 아래의 쿼리, 테스트,
    임계값 대신 각 규칙에 해당하는 설정이 표시됩니다.
  </Step>
  <Step title="쿼리 작성">
    **대상 스트림**, **평가 간격**(1분, 5분 또는 10분마다),
    **쿼리 언어**(메트릭은 **PromQL**, 그 외에는 **SQL**), **쿼리**를 설정합니다. 쿼리는 숫자를
    반환해야 합니다. 평가기는 첫 번째 행의 첫 번째 열을 읽습니다. 필요한 경우
    [**그룹화 기준**](#열-기준으로-규칙-그룹화)을 설정합니다. 규칙은
    [`_audit` 스트림](/ko/settings/data-security#감사-스트림)을 읽을 수 없습니다. 이 스트림을 대상으로 규칙을 저장하면 `400`을 반환합니다.
  </Step>
  <Step title="트리거 조건 설정">
    각 행은 심각도 하나를 나타냅니다. **결과 비교 조건**에서는 연산자로 결과를 **임계값**과 비교하고, **유지
    시간**에는 조건을 충족해야 하는 시간을 분 단위로 지정합니다. **심각도 추가**로 행을 추가합니다. 조건을 충족한 심각도 중 가장 높은
    심각도를 적용합니다. 높은 심각도의 조건은 낮은 심각도의 조건보다 충족하기 쉬워서는 안 됩니다. 분 단위로 지정한 시간은
    평가 횟수로 변환합니다. 아래에서 [**복구** 및 **데이터가 없을 때**](#복구-및-데이터-누락)를 설정합니다.
  </Step>
  <Step title="대응 가이드 추가">
    **Notify 및 대응**에서 **대응 가이드 / 런북 URL**을 입력합니다. 대응 담당자는 인시던트
    목록에서 가이드를 엽니다. 알림 수신자는 규칙이 아니라 [에스컬레이션 정책](/ko/alerting/on-call#에스컬레이션-정책)과
    [Notify 정책](/ko/notification-channels#템플릿-및-정책-만들기)에서 결정합니다.
  </Step>
  <Step title="조사 가이드 추가">
    필요한 경우 **조사 가이드**에 수행할 **조사 단계**를 작성하고, 실행할 **쿼리**를 추가하고,
    해당 규칙의 인시던트를 조사할 때 열 **대시보드**를 선택합니다.
    [조사 가이드](#조사-가이드)를 참조합니다.
  </Step>
  <Step title="규칙 테스트">
    **규칙 테스트**를 선택합니다. 최근 6시간의 실제 데이터로 쿼리를 실행합니다. **쿼리 미리 보기**는
    결과와 임계값 선을 그래프에 표시하고 현재 값, 예상 트리거 횟수,
    스캔한 행 수, 지연 시간을 보여 줍니다. 그룹화한 규칙은 찾은 그룹 수를 표시합니다.
  </Step>
  <Step title="저장">
    **생성 전 검사**의 모든 항목을 충족해야 합니다. 규칙 이름을 입력하고, 현재 쿼리의 테스트를 통과하고, 유효한
    임계값과 런북 URL을 설정합니다. 그런 다음 **저장 및 활성화**를 선택하거나, 규칙을 실행하지 않고 보관하려면 **초안 저장**을
    선택합니다.
  </Step>
</Steps>

규칙 편집 화면에서 생성한 규칙에는 에스컬레이션 정책을 지정하지 않습니다. [알림 라우팅](/ko/alerting/routing)이
인시던트를 배정하고, 라우팅으로 배정하지 못한 인시던트에는 `default` 정책을 적용합니다. 조직에
`default` 정책이 없으면 에스컬레이션할 대상 없이 인시던트가 생성됩니다. 먼저 이 정책을 생성합니다.
[기본 정책](/ko/alerting/on-call#기본-정책)을 참조합니다.

## 열 기준으로 규칙 그룹화

SQL 또는 PromQL 쿼리를 주기적으로 평가하는 규칙은 결과의 호스트나 서비스 같은 열을 기준으로 그룹화할 수 있습니다. 규칙 편집 화면에서 **그룹화 기준**을 설정하거나, [규칙을 생성할 때](/ko/api/alerting/create-rule#열별로-분할한-규칙) `query.group_by`를 설정합니다. 각 값 그룹은 독립된 규칙처럼 동작합니다.

| 항목 | 동작 |
|---|---|
| 그룹 | 지정한 열에서 값이 같은 행을 한 그룹으로 묶습니다. 열 이름은 대소문자를 구분하지 않고 결과의 열과 비교합니다. |
| 값 | 그룹의 첫 번째 행에서 지정한 열과 시간 열을 제외한 첫 번째 숫자 열을 값으로 사용합니다. |
| 트리거 | 각 그룹의 값을 트리거 조건 또는 심각도별 조건과 개별적으로 비교하고, `for_periods`에 해당하는 평가 횟수도 그룹별로 집계합니다. |
| 인시던트 | 각 그룹은 별도의 인시던트를 생성합니다. 그룹 값은 레이블과 `Errors per host · web-1` 같은 인시던트 제목에 표시됩니다. 그룹이 복구 조건을 충족하면 인시던트를 해결합니다. 결과에 없는 그룹에는 값이 없으므로 규칙의 데이터 누락 설정을 적용합니다. |
| 제한 | 평가 1회당 열은 최대 8개, 그룹은 최대 100개입니다. 100개를 초과한 그룹은 평가하지 않으며, 이 평가에서 결과에 없는 그룹의 인시던트는 그대로 유지합니다. |

그룹마다 한 행을 반환하고, 상태가 가장 나쁜 그룹을 맨 앞에 배치합니다.

```sql
SELECT host, count(*) AS errors
FROM app_logs
WHERE level = 'error'
GROUP BY host
ORDER BY errors DESC
```

PromQL에서는 시계열의 레이블이 열에 해당하므로 `sum by (instance) (rate(http_requests_total{status=~"5.."}[5m]))`는 `instance`를 기준으로 그룹화합니다. 결과에 행이 있지만 지정한 이름의 열이 없으면 해당 평가가 실패하고 아무것도 변경되지 않습니다. 규칙 편집 화면에서 쿼리를 테스트하면 열을 검사합니다. APM, RUM, 실시간, 이상 탐지 규칙은 그룹화할 수 없습니다. [이상치 규칙](#이상치-규칙)은 반드시 그룹화해야 합니다.

## 복구 및 데이터 누락

모든 규칙은 열린 인시던트가 언제 복구되는지와 값이 없는 평가를 어떻게 처리하는지 정의합니다. 규칙 작업대의 **복구** 및 **데이터가 없을 때**에서 설정하거나, [규칙을 생성할 때](/ko/api/alerting/create-rule#복구-및-데이터-누락) `trigger.recovery` 및 `trigger.no_data`로 설정합니다.

- **복구 임계값:** 값이 이 임계값을 넘어 정상 범위로 돌아오면 열린 인시던트가 복구됩니다. 예를 들어 90을 초과하면 트리거되는 규칙은 값이 80 미만으로 떨어지면 복구됩니다. 이렇게 하면 값이 임계값 근처에서 오르내릴 때 트리거와 복구가 반복되지 않습니다.
- **복구 지속 시간:** 값이 이 시간 동안 정상 범위에 머물러야 인시던트가 복구됩니다.
- **데이터가 없을 때:** 쿼리가 값을 반환하지 않거나 그룹화한 규칙의 특정 그룹이 결과에 없는 경우입니다.

| 옵션 | 동작 |
|---|---|
| 복구됨 | 평가 결과를 조건 불충족으로 처리하고 열린 인시던트를 복구합니다. 기본값입니다. |
| 상태 유지 | 상태를 변경하지 않고 규칙에 **데이터 없음**을 표시합니다. 이상 탐지 규칙의 기본값입니다. |
| 데이터 없음 인시던트 열기 | 상태를 유지하다가 데이터가 없는 상태가 설정한 시간 동안 지속되면 **데이터 없음**으로 표시된 인시던트를 열고 `NO DATA · <title>`로 알림을 보냅니다. 데이터가 다시 들어오면 인시던트를 해결합니다. 호스트나 서비스가 영구적으로 제거된 경우에는 수동으로 해결합니다. 데이터가 다시 들어오기 전까지는 인시던트를 다시 열지 않습니다. |
| 0 | 누락된 값을 0으로 간주해 비교합니다. 건수를 비교할 때 적합합니다. |

실시간 규칙에는 두 설정을 모두 적용하지 않습니다. 건수가 감소하면 즉시 인시던트를 해결합니다.

## 이상 탐지 규칙

이상 탐지 규칙은 값이 해당 지표의 과거 데이터로 예측한 범위를 벗어나면 트리거되므로 고정
임계값이 필요하지 않습니다. **새 규칙 → 이상 탐지 규칙**을 선택합니다.

| 섹션 | 필드 | 규칙 |
|---|---|---|
| 기본 정보 | **규칙 이름**, **심각도**, **서비스** | 서비스는 선택 사항이며 여러 신호를 연결하는 데 필요한 컨텍스트를 제공합니다. |
| 탐지 쿼리 | **데이터 소스** | **쿼리**, 서비스나 엔드포인트의 **APM 지표**, 또는 애플리케이션의 **RUM 지표**를 선택합니다. [APM 지표 이상 알림](/ko/apm/insights#apm-지표의-이상-감지-알림-설정) 및 [RUM 이상 탐지 규칙](/ko/rum/alerts#이상-탐지-규칙)을 참조합니다. |
| | **스트림**, **스트림 유형**, **쿼리 언어**, **쿼리** | 평균, P95, 건수 등 숫자 하나를 반환하는 쿼리입니다. |
| | **평가 구간** | 1분, 5분, 15분 또는 1시간입니다. |
| 탐지기 | **알고리즘** | 중앙값을 사용해 이상치의 영향을 줄이는 **MAD** 또는 최근 변화를 추적하는 **EWMA**를 선택합니다. |
| | **과거 데이터 참조 기간(일)** | 같은 시간대의 과거 데이터를 1~30일 범위에서 참조합니다. 기본값은 7일입니다. |
| | **민감도(k·σ)** | 값과 기준선의 차이가 산포의 k배를 초과하면 규칙이 트리거됩니다. 값이 높을수록 민감도가 낮아집니다. 기본값은 3입니다. |
| | **평활화(α)** | EWMA에만 적용하며 범위는 `(0, 1]`입니다. 값이 높을수록 최근 샘플을 더 많이 반영합니다. |
| | **트리거까지 필요한 구간 수** | 인시던트를 열기까지 연속으로 이상이 감지되어야 하는 평가 구간 수입니다. |
| | **주간 계절성** | 같은 요일의 데이터끼리만 비교해 평일과 주말의 차이로 인한 알림을 방지합니다. 과거 데이터가 최소 7일 필요하며, 28일 이상을 권장합니다. |

## 예측 규칙

예측 규칙은 지표의 추세를 미래로 연장하고, 설정한 예측 시간 안에 지표가
임계값을 넘어설 것으로 예상되면 트리거됩니다. 디스크 사용량, 할당량, 연결 수처럼 한도에 서서히
가까워지는 지표에 적합합니다. **트리거 유형**에서 **예측**을 선택하고 임계값 규칙과 같은 방식으로 쿼리를 작성한 후 다음을 설정합니다.

| 설정 | 참고 |
|---|---|
| **예측값** | `> 90`과 같이 연산자와 임계값을 설정합니다. |
| **예측 시점까지의 시간** | 임계값을 넘어설 것으로 예측될 때 규칙을 얼마나 미리 트리거할지 설정합니다. 1시간, 6시간, 12시간 또는 1일, 2일, 3일, 7일을 선택합니다. 기본값은 1일입니다. |
| **과거 데이터 조회 기간** | 추세 예측에 사용할 과거 데이터의 기간을 1일, 3일, 7일, 14일 또는 30일로 설정합니다. 기본값은 7일입니다. |
| **모델** | **선형 추세**, **일간 패턴** 또는 **주간 패턴**을 선택합니다. 일간 및 주간 패턴은 일별 또는 주별로 오르내리는 지표에 적합하며, 하루 또는 일주일 전 같은 시각의 값에 추세를 더해 예측합니다. 주간 패턴에는 최소 7일의 과거 데이터가 필요합니다. |

평가할 때마다 현재 값을 시계열에 추가합니다. 새 규칙이나 쿼리가 변경된 규칙은 먼저 과거의 일부
시점을 조회해 데이터를 채웁니다. 데이터 포인트가 6개 미만이거나 일간 및 주간 패턴에 필요한
한 주기 분량의 데이터가 없으면 해당 평가에서는 판단을 내리지 않습니다. 인시던트에는 임계값을 넘어설 예상 시점과
그 시점의 예측값을 표시합니다. 예측 규칙에는 심각도 하나와 지속 시간을 설정하며, 복구 임계값은 설정하지 않습니다.
[데이터가 없을 때](#복구-및-데이터-누락)의 동작은 설정할 수 있습니다.

## 이상치 규칙

이상치 규칙은 쿼리 결과를 고정 임계값과 비교하는 대신 그룹끼리 비교합니다.
예를 들어 오류 건수를 호스트별로 그룹화하면 다른 호스트보다 오류가 훨씬 많은 호스트에서 규칙이 트리거되지만, 모든
호스트의 오류가 함께 증가하면 트리거되지 않습니다. **트리거 유형**에서 **이상치**를 선택하고 쿼리를 작성한 후
[**그룹화 기준**](#열-기준으로-규칙-그룹화)을 입력하고 다음을 설정합니다.

| 설정 | 참고 |
|---|---|
| **허용 범위** | 표준화한 편차가 어느 정도일 때 이상치로 판단할지 0.5~10 범위에서 설정합니다. 기본값은 3입니다. 값이 작을수록 민감도가 높아집니다. |
| **감지 방향** | **높거나 낮은 값**, **높은 값만** 또는 **낮은 값만**을 선택합니다. |

그룹 값의 중앙값과 중앙값 절대 편차(MAD)를 기준으로 편차를 측정합니다. 그룹 값이 거의 같을 때
작은 변동을 이상치로 판단하지 않는 방식입니다. 이상치로 판단한 그룹마다 별도의
인시던트를 열고 편차의 크기를 표시합니다. 값이 있는 그룹이 3개 미만이면 해당 평가에서는
판단을 내리지 않습니다. 이상치 규칙은 APM 또는 RUM 지표를 사용하지 않으며, 심각도 하나와 지속 시간을 설정합니다.

## 복합 규칙

복합 규칙은 여러 규칙을 함께 평가합니다. 구성 규칙에 열린 인시던트가 있으면 해당 규칙을 참으로 간주하고
표현식으로 규칙을 결합합니다. 예를 들어 `A && B`는 오류율과 지연 시간에 모두 알림이 발생할 때만
알림을 보내고, `A && !B`는 다운스트림이 정상일 때만 업스트림 문제를 감지합니다. **복합**을
**트리거 유형**에서 선택합니다.

| 설정 | 참고 |
|---|---|
| **규칙** | 최대 10개의 규칙을 추가할 수 있으며 이름은 A, B, C 순으로 지정합니다. |
| **표현식** | `&&`(그리고), `\|\|`(또는), `!`(부정) 및 괄호로 문자를 결합합니다. 예: `A && (B \|\| C)`. |
| **이 규칙의 인시던트를 복합 인시던트 아래에 병합** | 복합 규칙이 인시던트를 열면 구성 규칙의 열린 인시던트를 해당 인시던트에 [병합](/ko/alerting/incidents#인시던트-병합)하고 개별 알림을 중단합니다. 이후에 열리는 인시던트도 병합합니다. |

복합 규칙은 쿼리를 실행하지 않고 테스트할 수 없으며
[데이터가 없을 때](#복구-및-데이터-누락)의 동작도 설정할 수 없습니다. 복합 규칙을 구성 규칙으로 사용할 수 없으므로
한 복합 규칙을 다른 복합 규칙에 포함할 수 없습니다. 삭제된 구성 규칙은 거짓으로 처리합니다.
인시던트에는 어떤 문자가 참이었는지 표시합니다.

## 하트비트 규칙

하트비트 규칙은 데이터를 조회하는 대신 작업이 체크인하기를 기다립니다. cron 작업, 백업 스크립트 또는
배치 작업은 실행할 때마다 체크인 주소로 요청을 보냅니다. 체크인 주기와
유예 시간을 합친 시간 안에 체크인이 도착하지 않거나 체크인이 실패를 보고하면 규칙이 트리거됩니다.
**트리거 유형**에서 **하트비트**를 선택합니다.

| 설정 | 참고 |
|---|---|
| **체크인 주기** | 작업 실행 주기를 1분~7일 범위에서 설정합니다. 기본값은 60분입니다. |
| **유예 시간** | 체크인 주기가 끝난 후 체크인 누락으로 처리하기까지 더 기다릴 시간을 설정합니다. 최대 1일이며 기본값은 5분입니다. |

저장하면 대화 상자에 체크인 주소와 `curl` 예시가 표시됩니다. 체크인 주소는 이때
한 번만 표시됩니다. 작업이 성공하면 해당 주소로 요청(`GET` 또는 `POST`)을 보내도록 설정하고, 실패하면 `?status=fail`을 추가해
규칙을 즉시 트리거합니다. `POST` 본문의 앞부분은 인시던트에 체크인 메시지로 저장되므로
로그의 마지막 몇 줄을 남기는 데 적합합니다.

```bash
if ./backup.sh; then
  curl -fsS "$HEARTBEAT_URL"
else
  curl -fsS "$HEARTBEAT_URL?status=fail"
fi
```

하트비트 규칙을 편집하면 마지막 체크인 시각과 다음 체크인 마감 시각을 확인할 수 있습니다.
**체크인 주소 재설정**을 선택하면 새 주소가 발급되고 기존 주소는 즉시 작동을 중단합니다. 체크인
주소는 로그인 없이 주소에 포함된 토큰만으로 사용할 수 있습니다. [공개 액세스](/ko/public-access) 및
[하트비트 체크인](/ko/api/alerting/heartbeats)을 참조합니다. 하트비트 규칙은 쿼리를 실행하지 않고 테스트할 수 없으며,
[데이터가 없을 때](#복구-및-데이터-누락)의 동작도 설정할 수 없습니다.

## 실시간 규칙

실시간 규칙은 타이머가 아니라 수집 경로에서 실행합니다. 수집 노드는 받아들인 모든 레코드를 해당 스트림의 실시간 규칙과 비교하고, 일치하는 레코드를 `periodSecs`초 길이의 슬라이딩 윈도우에 넣습니다. 규칙을 담당하는 알림 노드는 매초 쓰기를 받는 모든 노드에서 윈도우 내 일치 건수를 읽어 합산합니다. 레코드를 기록한 뒤 최대 1초 안에 합계가 트리거 조건을 충족하면 인시던트를 열고, 더 이상 충족하지 않으면 인시던트를 해결 처리합니다.

| 항목 | 동작 |
|---|---|
| 구문 | SQL 구문은 `SELECT count(*) FROM <stream> [WHERE <condition>]`입니다. 테이블은 규칙의 `stream`입니다. 조건은 필드를 리터럴과 비교하거나(`=`, `!=`, `<`, `<=`, `>`, `>=`) `IN`, `BETWEEN`, `LIKE`, `ILIKE`, `IS [NOT] NULL`을 사용합니다. `AND`, `OR`, `NOT`과 괄호로 조건을 조합합니다. 필드가 없거나 값이 null이면 비교 조건을 충족하지 않습니다. |
| 윈도우 | `periodSecs`는 1~3600입니다. |
| 트리거 | `operator`는 `gt` 또는 `gte`이고, `for_periods`는 `0` 또는 `1`입니다. `thresholds`의 각 단계는 건수에 따라 심각도를 지정합니다. |
| 인시던트 | 일반적인 수명 주기를 따릅니다. 규칙당 활성 인시던트는 하나이며, `silence_secs`에 따른 재알림 대기 시간, 에스컬레이션, 알림을 적용합니다. |

[규칙 생성](/ko/api/alerting/create-rule) API는 이러한 제한을 벗어난 실시간 규칙을 `400` 오류로 거부합니다. 쓰기를 받는 각 노드는 건수를 메모리에 보관하고 5초마다 윈도우 스냅샷을 메타데이터 데이터베이스에 저장합니다. 노드가 재시작하면 스냅샷을 불러오므로 손실은 최근 5초분을 넘지 않습니다. 노드가 중단되거나 응답하지 않으면 담당 알림 노드는 해당 건수가 윈도우에서 벗어날 때까지 그 노드의 마지막 스냅샷을 대신 사용합니다. 다른 알림 노드가 규칙을 인계받아도 상태는 유실되지 않습니다. 인계받은 노드는 열린 인시던트에서 알림 발동 상태를 가져옵니다. 노드는 클러스터 Bearer 토큰(`MS_SELF_TELEMETRY_CLUSTER_TOKEN`, 역할 분리 배포에서도 공유)을 사용해 다른 노드의 건수를 읽습니다. 이 토큰이 없으면 다른 노드의 건수는 스냅샷으로만 확인할 수 있습니다.

### 페더레이션의 실시간 규칙

[교차 클러스터 페더레이션](/ko/settings/data-plane#클러스터-페더레이션)에서는 각 클러스터가 자체적으로 기록된 레코드를 집계하고, 기본적으로 자체 건수를 기준으로 판정합니다. 여러 클러스터의 건수를 합산하려면 판정을 담당할 클러스터를 지정합니다. API에서는 `query.home_cluster`를 설정합니다. 규칙 편집기에서 규칙을 열면 **판정 클러스터**에서 현재 클러스터 또는 활성화된 원격 클러스터를 선택할 수 있습니다. 지정한 클러스터만 해당 규칙의 인시던트를 열고 해결 처리합니다. 해당 클러스터에서 규칙을 담당하는 알림 노드는 매초 조직별 토큰을 사용해 조직에 매핑된 각 클러스터에 건수를 요청하고 자체 건수에 더합니다. 다른 클러스터는 집계만 수행합니다. 클러스터가 800밀리초 안에 응답하지 않으면 최대 30초 동안 마지막으로 받은 건수를 사용하고, 그 이후에는 0으로 처리합니다. 따라서 한 차례 응답이 누락되어도 인시던트를 해결 처리하지 않습니다. `realtime_federated_counts_failed_total{cluster}` 메트릭은 요청 실패 횟수를 집계합니다. 규칙은 페더레이션 전체에서 동일한 ID를 유지하므로 모든 클러스터가 같은 규칙으로 집계합니다.

## 평가 지연

역할 분리 클러스터에서 쿼리는 수집 노드가 플러시한 데이터만 읽습니다. 수집 버퍼의 레코드가 표시되기까지 최대 `[intake].flush_interval_secs`(기본값 30초)가 걸리므로 최신 윈도우의 건수가 실제보다 적게 집계됩니다. 규칙 편집기의 **고급**에 있는 **평가 지연**은 각 평가의 윈도우를 과거로 이동합니다. 평가 지연과 평가 기간이 모두 5분이면 07:00 평가에서 06:50부터 06:55까지의 데이터를 읽습니다.

| 값 | 효과 |
|---|---|
| **자동** (기본값) | 단일 프로세스가 모든 역할을 실행하면 지연을 적용하지 않습니다. 역할 분리 클러스터에서는 **설정 → 알림 평가**의 **평가 지연**을 적용합니다. 기본값은 60초입니다. |
| **지연 없음** | 현재 시점까지의 데이터를 읽습니다. |
| 30초~1시간 | 규칙에 지정한 지연을 적용합니다. API의 `query.delay_secs`는 0~3600초를 허용합니다. |

데이터 없음 검사, 복구 조건, 이상 탐지 기준선, 예측 시계열, 분할 규칙, 이상치에도 같은 지연을 적용합니다. 윈도우를 과거로 이동한 경우 인시던트는 실제로 읽은 시간 범위를 `evaluated_window` 주석에 기록합니다. 실시간 규칙은 쿼리를 실행하지 않으며 평가 지연을 적용하지 않습니다.

## 우선순위 및 긴급도

규칙 편집기의 **Notify 및 대응**에서 **우선순위**와 **긴급도**를 설정하면 해당 규칙이 인시던트를 열 때 이 값을 적용합니다.

- **우선순위**: 조직의 [우선순위 수준](/ko/alerting/on-call#긴급도-및-우선순위-수준) 중 하나를 선택합니다. 기본 수준은 P1~P5이며, P1이 가장 높습니다. 값을 설정하지 않으면 인시던트에 우선순위가 지정되지 않습니다([알림 파이프라인](/ko/pipelines)에서 지정할 수 있음). 심각도로 우선순위를 결정하지 않습니다.
- **긴급도**: **에스컬레이션 정책에 따름**(기본값)은 [인시던트의 에스컬레이션 정책에 설정된 긴급도](/ko/alerting/on-call#긴급도)를 따릅니다. 높음 또는 낮음을 선택하면 모든 인시던트에 해당 값을 적용합니다.

## 조사 가이드

규칙 편집기의 **조사 가이드** 섹션은 해당 규칙의 인시던트를 조사할 때 먼저 수행할 작업을 안내합니다. 모든 항목은 선택 사항입니다.

| 항목 | 내용 | 제한 |
|---|---|---|
| **조사 단계** | 먼저 확인할 항목과 확인 순서를 Markdown으로 작성합니다. | 8,000자 |
| **쿼리** | **이름**, 쿼리 언어(**promql** 또는 **sql**), **쿼리**를 지정합니다. SQL의 경우 **스트림**과 **스트림 유형**도 지정합니다. | 최대 4,000자의 쿼리 10개 |
| **대시보드** | 인시던트에서 열 대시보드를 지정합니다. | 대시보드 5개 |

해당 규칙의 각 인시던트는 **조사 가이드** 아래에 조사 단계를 서식 있는 텍스트로 표시하고, 쿼리와 대시보드는 링크로 표시합니다. 쿼리 링크를 열면 인시던트의 시간 범위로 메트릭(PromQL), 트레이스(트레이스 스트림의 SQL), 또는 로그(기타 SQL)를 엽니다. [Mole Agent](/ko/agent)는 인시던트를 조사하기 전에 가이드를 읽고 가이드의 쿼리부터 실행합니다. 인시던트의 [AI 근본 원인 분석](/ko/alerting/incidents#ai-근본-원인-분석)에도 가이드를 반영합니다.

API에서는 규칙의 `guide` 필드로 가이드를 설정합니다. [규칙 생성](/ko/api/alerting/create-rule#조사-가이드)을 참조합니다. 규칙을 내보낼 때 가이드도 포함합니다. 가져올 때는 조직에 없는 대시보드를 가이드에서 제외합니다.

## 탐지 규칙

[탐색](/ko/alerting/discovery)은 탐지 결과를 목록에만 표시합니다. 알림을 받으려면 **알림 → 탐색**에서 **새 탐지 규칙**을 선택하거나, 탐지 결과에서 **유사 탐지 결과에 대한 알림 설정**을 선택합니다. 그런 다음 탐지 결과 유형, 서비스 또는 애플리케이션, 환경, 최소 심각도와 함께 에스컬레이션 정책 및 긴급도를 지정합니다. 규칙에 일치하는 탐지 결과마다 별도의 인시던트를 엽니다. 인시던트의 심각도는 탐지 결과와 같으며, 긴급도를 따로 설정하지 않으면 낮음으로 지정합니다. 탐지 상태가 종료되면 인시던트가 복구됩니다. 규칙 목록에는 이러한 규칙의 소스가 **탐색**으로 표시되며, 규칙을 열면 탐색 페이지로 이동합니다.

## 가져오기 및 내보내기

규칙 목록의 **가져오기/내보내기**에서 규칙을 파일로 저장하거나 파일에서 가져올 수 있습니다.

- **모든 규칙 내보내기**를 선택하거나, 필터링한 후 **이 규칙 N개 내보내기**를 선택하면 JSON 규칙 번들(`"format": "molesignal.alert-rules/v1"`)을 다운로드합니다. 번들은 각 규칙의 전체 정의를 유지하지만 ID, 조직, 평가 상태, 시간 정보는 포함하지 않습니다. 에스컬레이션 정책과 복합 규칙에 포함된 규칙은 이름으로 참조하므로 번들을 다른 워크스페이스나 클러스터로 옮길 수 있습니다. 번들에는 하트비트 규칙의 체크인 주소가 포함되지 않으므로 가져온 후 해당 규칙에서 주소를 다시 설정합니다.
- **규칙 가져오기…**에서 번들이나 Prometheus 알림 규칙 파일(Prometheus Operator의 `PrometheusRule` 포함)을 붙여넣거나 선택합니다. **테스트 실행**을 선택해 각 규칙이 생성, 업데이트, 변경 없음, 실패 중 어느 결과에 해당하는지 확인합니다. 업데이트되는 규칙은 변경되는 필드도 확인할 수 있습니다. 그런 다음 **N개 가져오기**를 선택합니다. 이름으로 규칙을 매칭합니다. 새 이름이면 규칙을 생성하고, 같은 이름의 규칙이 하나면 업데이트합니다. 같은 이름의 규칙이 여러 개 있거나 파일에 같은 이름이 두 번 나오면 실패합니다. 이름이 같은 규칙을 내보낸 파일을 가져오기 전에 중복된 규칙의 이름을 변경합니다. **새 규칙만 생성하고 같은 이름의 기존 규칙은 유지**를 선택하면 기존 규칙을 건너뜁니다. 규칙 하나라도 실패하면 아무 변경 사항도 저장하지 않습니다. 모두 성공하면 전체 변경 사항을 한 번에 저장합니다.

Prometheus 규칙을 MoleSignal 규칙으로 변환하는 방식은 다음과 같습니다.

| Prometheus | MoleSignal |
|---|---|
| `alert` | 규칙 이름입니다. 여러 그룹에 같은 알림 이름이 있으면 첫 번째 그룹을 제외한 각 그룹의 알림 이름 뒤에 해당 그룹 이름을 붙입니다. |
| `expr` | 쿼리문이 `count(<expr>)`이고 조건이 `>= 1`인 PromQL 규칙입니다. 표현식이 시계열을 반환하면 알림이 발생합니다. 주석이나 레이블에 `{{ $labels.x }}`를 사용하면 쿼리문은 `count by (x) (<expr>)`가 됩니다. 규칙을 `x` 기준으로 [분할](#열-기준으로-규칙-그룹화)하여 그룹마다 인시던트를 하나씩 생성합니다. 스트림은 표현식의 첫 번째 메트릭 이름입니다. |
| 그룹의 `interval` | 평가 주기입니다. 지정하지 않으면 60초입니다. |
| `for` | 연속 평가 주기 수입니다. 평가 주기 단위로 올림합니다. |
| `severity` 레이블 | 심각도입니다. `critical`과 `page`는 치명적, `error`와 `high`는 오류, `warning`과 `warn`은 경고, `info`, `low`, `none`은 정보로 매핑합니다. 다른 레이블은 그대로 유지합니다. |
| `annotations` | 주석을 그대로 유지합니다. `description` 또는 `summary` 주석을 설명으로 사용합니다. |
| `record` | 기록 규칙은 가져오지 않고 결과 아래에 표시합니다. |
| `keep_firing_for` | 지원하지 않으며 결과 아래에 표시합니다. |

가져온 규칙은 기본 에스컬레이션 정책을 사용합니다. 필요한 경우 가져오기 전에 번들에서 `escalation_policy`를 설정합니다. Alertmanager 자체 구성(`alertmanager.yml`의 라우트 및 수신자)은 규칙이 아니므로 이 방식으로 가져올 수 없습니다. 대신 [알림 라우팅](/ko/alerting/routing)과 [알림 정책](/ko/notification-channels)을 사용합니다.

CI에서는 [CLI](/ko/cli)로 `molesignal alerts rules export`와 `molesignal alerts rules apply -f rules.json [--dry-run]`을 실행합니다. CLI는 결과를 표로 출력하며 규칙 하나라도 실패하면 종료 코드 1을 반환합니다.

## 규칙 변경, 일시 중지 또는 삭제

규칙을 열어 변경한 후 **규칙 테스트**를 다시 실행하고 저장합니다. **초안 저장**을 선택하면 규칙을 비활성 상태로 유지하고,
**저장 및 활성화**를 선택하면 규칙을 다시 활성화합니다. 규칙을 삭제하려면
[규칙 삭제](/ko/api/alerting/delete-rule) API를 호출합니다. 규칙을 변경하지 않고 해당 규칙의 알림을 잠시 끄려면
[무음 설정](/ko/alerting/silences)을 사용합니다.

[알림 규칙 API](/ko/api/alerting/create-rule)를 사용하면 스크립트에서 규칙을 생성하거나 테스트하거나 트리거할 수 있습니다.
