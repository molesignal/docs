규칙은 발생하면 안 되는 상황을 정의합니다. MoleSignal은 일정 간격으로 규칙을 평가하고,
조건이 충족되면 [인시던트](/ko/alerting/incidents)를 엽니다. **알림 → 규칙**을 여세요. 규칙을 읽으려면
`alerts.rules.read`가 필요하고, 규칙을 생성하거나 변경하려면 `alerts.rules.manage`가 필요합니다.

## 규칙 유형

| 유형 | 평가 대상 | 생성 위치 |
|---|---|---|
| **임계값 규칙** | 고정 임계값과 비교하여 SQL 또는 PromQL 쿼리, [APM 수치](/ko/apm#apm-지표에-알림-설정) 또는 [RUM 수치](/ko/rum/alerts)를 일정 간격으로 평가합니다. | 규칙 워크벤치. |
| **예측 규칙** | 쿼리, APM 수치 또는 RUM 수치의 추세를 평가하며, 리드 타임 내에 임계값을 넘을 것으로 예상되면 발생합니다. [예측 규칙](#예측-규칙)을 참고하세요. | 규칙 워크벤치의 **트리거 유형**. |
| **이상치 규칙** | 컬럼을 기준으로 그룹화한 쿼리에서 각 그룹을 서로 비교하며, 다른 그룹과 동떨어진 그룹이 발생합니다. [이상치 규칙](#이상치-규칙)을 참고하세요. | 규칙 워크벤치의 **트리거 유형**. |
| **복합 규칙** | 다른 규칙에 열린 인시던트가 있는지 여부를 and, or, not으로 결합하여 평가합니다. [복합 규칙](#복합-규칙)을 참고하세요. | 규칙 워크벤치의 **트리거 유형**. |
| **하트비트 규칙** | cron 작업이나 백업 스크립트 같은 작업이 제시간에 체크인했는지 여부를 평가합니다. [하트비트 규칙](#하트비트-규칙)을 참고하세요. | 규칙 워크벤치의 **트리거 유형**. |
| **이상 탐지** | 이력에서 학습한 기준선과 비교하여 쿼리, APM 수치 또는 RUM 수치를 평가합니다. | 이상 탐지 편집기. |
| **실시간 규칙** | 수집 경로에 도착하는 즉시 레코드를 집계합니다. | API 전용입니다. [실시간 규칙](#실시간-규칙)을 참고하세요. |

## 규칙 목록

**규칙**은 모든 규칙을 데이터 소스, 트리거 조건, 상태 및 마지막
평가 결과와 함께 나열합니다. 규칙, 서비스 또는 소스를 기준으로 검색하고 **전체**, **활성화**,
**비활성화됨** 사이를 전환하세요.

| 상태 | 의미 |
|---|---|
| **평가되지 않음** | 규칙이 아직 실행되지 않았습니다. |
| **정상** | 마지막 평가에서 조건이 충족되지 않았습니다. |
| **대기 중** | 조건은 충족되지만 필요한 기간 동안 아직 유지되지 않았습니다. |
| **발생 중** | 규칙에 열린 인시던트가 있습니다. |
| **파이프라인에서 제외됨** | 규칙은 발생하지만, 열리게 될 인시던트를 [알림 파이프라인](/ko/pipelines/alert-events#이벤트-처리-결과)에서 제외했습니다. |
| **비활성화됨** | 규칙이 초안으로 저장되었으며 실행되지 않습니다. |

규칙을 선택하거나 해당 행의 **편집**을 선택해 엽니다.

## 임계값 규칙 생성

**새 규칙 → 임계값 규칙**을 선택하여 규칙 워크벤치를 엽니다.

<Steps>
  <Step title="규칙 유형 선택">
    **메트릭 알림**, **로그 알림**, **트레이스 알림**, **APM 알림** 또는 **RUM 알림**을 선택합니다. **빠른 시작**에서
    프리셋이 **높은 오류율**, **높은 P95
    지연 시간**, **오류 로그 급증** 또는 **데이터 없음** 같은 일반적인 쿼리를 채웁니다. APM 및 RUM 알림은 쿼리 대신
    서비스 또는 애플리케이션과 수치를 선택합니다. [APM 수치에 대한 알림](/ko/apm#apm-지표에-알림-설정) 및
    [RUM 알림](/ko/rum/alerts)을 참고하세요.
  </Step>
  <Step title="기본 정보 입력">
    **규칙 이름**은 인시던트의 제목이 됩니다(예: `api_high_error_rate`). **서비스**는 소유권 및 교차 신호 컨텍스트를 위해 규칙을
    서비스에 연결합니다. **설명**은 규칙이 보호하는 대상을 설명합니다.
  </Step>
  <Step title="트리거 유형 선택">
    **쿼리 및 트리거 조건** 상단에서 **트리거 유형**을 선택합니다: **임계값**(기본값),
    [**예측**](#예측-규칙), [**이상치**](#이상치-규칙), [**복합**](#복합-규칙) 또는
    [**하트비트**](#하트비트-규칙)입니다. 복합 및 하트비트 규칙에는 쿼리가 없으며, 아래의 쿼리, 테스트 및
    임계값 대신 해당 규칙의 설정을 사용합니다.
  </Step>
  <Step title="쿼리 작성">
    **대상 스트림**, **평가 간격**(1, 5 또는 10분마다),
    **쿼리 언어**(메트릭은 **PromQL**, 그 외는 **SQL**) 및 **쿼리**를 설정합니다. 쿼리는
    숫자를 반환해야 합니다. 평가기는 첫 번째 행의 첫 번째 컬럼을 읽습니다. 선택적으로
    [**그룹화 기준**](#컬럼별로-규칙-그룹화)을 입력합니다. 규칙은
    [`_audit` 스트림](/ko/settings/data-security#감사-스트림)을 읽을 수 없습니다. 규칙을 저장하면 `400`이 반환됩니다.
  </Step>
  <Step title="트리거 조건 설정">
    각 행은 심각도입니다: **결과 비교 조건**은 연산자로 **임계값**과 비교되고, **지속 시간**은
    분 단위로 지정됩니다. **심각도 추가**를 선택하면 행이 추가됩니다. 일치하는 가장 높은 심각도가
    적용되며, 높은 심각도가 낮은 심각도보다 더 쉽게 충족될 수는 없습니다. 분은 평가 횟수로
    변환됩니다. 아래에서 [**복구** 및 **데이터가 없을 때**](#복구-및-데이터-누락)를 설정하세요.
  </Step>
  <Step title="대응 지침 추가">
    **Notify 및 대응**에서 **대응 가이드 / 런북 URL**을 입력합니다. 대응 담당자는
    인시던트 목록에서 이를 엽니다. 누구에게 알릴지는 규칙이 아니라 [에스컬레이션 정책](/ko/alerting/on-call#에스컬레이션-정책)
    및 [Notify 정책](/ko/notification-channels#템플릿-및-정책-만들기)에서 결정합니다.
  </Step>
  <Step title="조사 가이드 추가">
    선택적으로 **조사 가이드**에서 수행할 **조사 단계**를 작성하고, 실행할 **쿼리**를 추가하며,
    규칙의 인시던트 중 하나를 조사할 때 열 **대시보드**를 선택합니다. [조사 가이드](#조사-가이드)를
    참고하세요.
  </Step>
  <Step title="규칙 테스트">
    **규칙 테스트**를 선택합니다. 쿼리는 지난 6시간의 실제 데이터에서 실행되며, **쿼리 미리 보기**는
    임계값 선, 현재 값, 예상 트리거 수, 스캔한 행 수 및 지연 시간과 함께 결과를
    표시합니다. 그룹화된 규칙은 찾은 그룹 수를 표시합니다.
  </Step>
  <Step title="저장">
    **생성 전 검사**가 모두 준비되어야 합니다: 이름, 현재 쿼리의 성공적인 테스트, 유효한
    임계값 및 유효한 런북 URL. 그런 다음 **저장 및 활성화**를 선택하거나, 규칙을 실행하지 않고 유지하려면
    **초안 저장**을 선택합니다.
  </Step>
</Steps>

워크벤치에서 생성한 규칙은 에스컬레이션 정책을 지정하지 않습니다. [알림 라우팅](/ko/alerting/routing)이
해당 인시던트를 배치하며, 라우팅으로 배치할 수 없는 인시던트는 `default` 정책이 처리합니다. 정책이 없는 조직에서는
이러한 인시던트가 에스컬레이션할 대상 없이 열리므로 먼저 정책을 생성하세요. 참고:
[기본 정책](/ko/alerting/on-call#기본-정책).

## 컬럼별로 규칙 그룹화

SQL 또는 PromQL 쿼리를 사용하는 예약된 규칙은 호스트나 서비스 같은 결과 컬럼을 기준으로 그룹화할 수 있습니다. 규칙 워크벤치에서 **그룹화 기준**을 설정하거나, [규칙을 생성](/ko/api/alerting/create-rule#열별로-분할한-규칙)할 때 `query.group_by`를 설정하세요. 그러면 각 값 그룹이 자체 규칙처럼 동작합니다.

| 부분 | 동작 |
|---|---|
| 그룹 | 지정된 컬럼에서 동일한 값을 가진 행입니다. 이름은 대소문자를 구분하지 않고 결과 컬럼과 일치합니다. |
| 값 | 그룹의 첫 번째 행이 값을 제공합니다. 값은 지정된 컬럼과 시간 컬럼을 제외한 첫 번째 숫자 컬럼입니다. |
| 트리거 | 각 그룹은 트리거 또는 심각도 단계와 개별적으로 비교되며, 자체 `for_periods`를 계산합니다. |
| 인시던트 | 각 그룹은 자체 값을 레이블 및 제목에 포함하여 자체 인시던트를 엽니다(예: `Errors per host · web-1`). 그룹이 복구 조건을 충족하면 인시던트가 해결됩니다. 결과에 없는 그룹은 값이 없으며, 데이터 누락 시 규칙의 설정에 따라 결정됩니다. |
| 제한 | 라운드당 최대 8개 컬럼과 100개 그룹입니다. 100개 그룹을 초과하면 나머지 그룹은 평가되지 않으며, 해당 라운드에서 결과에 없는 그룹은 인시던트를 유지합니다. |

각 그룹마다 한 행을 반환하며, 가장 나쁜 그룹이 먼저 오도록 정렬합니다:

```sql
SELECT host, count(*) AS errors
FROM app_logs
WHERE level = 'error'
GROUP BY host
ORDER BY errors DESC
```

PromQL에서 시계열의 레이블은 해당 컬럼이므로, `sum by (instance) (rate(http_requests_total{status=~"5.."}[5m]))`는 `instance`를 기준으로 그룹화됩니다. 결과에 행은 있지만 해당 이름의 컬럼이 없으면 해당 라운드는 실패하고 아무것도 변경되지 않습니다. 규칙 워크벤치에서 쿼리를 테스트하면 컬럼을 확인합니다. APM, RUM, 실시간 및 이상 탐지 규칙은 그룹화되지 않으며, [이상치 규칙](#이상치-규칙)은 그룹화해야 합니다.

## 복구 및 데이터 누락

모든 규칙은 열린 인시던트가 언제 복구되는지와 값이 없는 평가를 무엇으로 간주하는지를 정의합니다. 규칙 워크벤치의 **복구**와 **데이터가 없을 때**에서 설정하거나, [규칙을 생성](/ko/api/alerting/create-rule#복구-및-데이터-누락)할 때 `trigger.recovery`와 `trigger.no_data`로 설정합니다.

- **복구 임계값:** 열린 인시던트는 값이 이 선을 다시 넘어올 때까지 기다립니다. 예를 들어 90 초과에서 트리거되는 규칙은 80 미만에서 복구됩니다. 임계값 주변을 맴도는 값은 트리거와 복구를 반복합니다.
- **복구 지속 시간:** 인시던트가 복구되려면 값이 이 시간 동안 정상 범위에 머물러야 합니다.
- **데이터가 없을 때:** 쿼리가 값을 반환하지 않았거나, 그룹화 규칙의 그룹이 결과에 없는 경우입니다.

| 선택 항목 | 동작 |
|---|---|
| 복구됨 | 평가가 일치하지 않는 것으로 간주되어 열린 인시던트가 복구됩니다. 기본값입니다. |
| 상태 유지 | 아무것도 변경되지 않고 규칙에 **데이터 없음**이 표시됩니다. 이상 탐지 규칙의 기본값입니다. |
| 데이터 없음 인시던트 생성 | 상태를 유지하고, 데이터가 없는 시간이 이어지면 **데이터 없음**으로 표시된 인시던트를 생성하며 `NO DATA · <title>`로 알림합니다. 데이터가 돌아오면 해결됩니다. 호스트나 서비스가 영구적으로 사라진 경우에는 직접 해결해야 하며, 데이터가 돌아오기 전에는 다시 열리지 않습니다. |
| 0 | 누락된 값을 0으로 간주해 비교하며, 카운트에 적합합니다. |

실시간 규칙은 두 설정을 모두 사용하지 않으며, 카운트가 떨어지는 즉시 해결됩니다.

## 이상 탐지 규칙

이상 탐지 규칙은 값이 자체 이력이 예측한 범위를 벗어날 때 트리거되므로 고정
임계값이 필요하지 않습니다. **새 규칙 → 이상 탐지 규칙**을 선택합니다.

| 섹션 | 필드 | 규칙 |
|---|---|---|
| 식별 정보 | **규칙 이름**, **심각도**, **서비스** | 서비스는 선택 사항이며 신호 간 컨텍스트를 제공합니다. |
| 탐지 쿼리 | **데이터 소스** | **쿼리**, 서비스 또는 엔드포인트의 **APM 지표**, 애플리케이션의 **RUM 지표**입니다. [APM 지표의 이상 알림](/ko/apm/insights#apm-지표의-이상-징후에-대한-알림) 및 [RUM 이상 탐지 규칙](/ko/rum/alerts#이상-탐지-규칙)을 참조하세요. |
| | **스트림**, **스트림 유형**, **쿼리 언어**, **쿼리** | 평균, P95, 카운트처럼 하나의 숫자를 반환하는 쿼리입니다. |
| | **평가 구간** | 1분, 5분, 15분 또는 1시간입니다. |
| 탐지기 | **알고리즘** | 강건한 중앙값인 **MAD** 또는 최근 변화를 따라가는 **EWMA**입니다. |
| | **과거 데이터 참조 기간(일)** | 같은 시간대의 1~30일 이력입니다. 기본값은 7일입니다. |
| | **민감도(k·σ)** | 기준선과의 거리가 산포의 k배를 초과하면 규칙이 트리거됩니다. 값이 클수록 민감도가 낮습니다. 기본값은 3입니다. |
| | **평활화(α)** | EWMA 전용이며 `(0, 1]` 범위입니다. 값이 클수록 최근 샘플을 더 따릅니다. |
| | **트리거까지 필요한 구간 수** | 인시던트가 열리기 전까지 연속으로 이상으로 평가되어야 하는 횟수입니다. |
| | **주간 계절성** | 같은 요일과만 비교하므로 평일과 주말 사이의 오탐을 방지합니다. 최소 7일의 과거 데이터 참조 기간이 필요하며, 28일 이상이 가장 좋습니다. |

## 예측 규칙

예측 규칙은 지표의 추세를 앞으로 연장해, 예측 시점까지 지표가 임계값을 넘을 것으로 예상되면 트리거됩니다.
디스크 사용량, 할당량, 연결 수처럼 한계에 서서히 다가가는 지표에 적합합니다. **트리거 유형**에서 **예측**을 선택하고, 임계값 규칙과 동일하게 쿼리를 작성한 뒤 다음을 설정합니다:

| 설정 | 설명 |
|---|---|
| **예측값** | 연산자와 임계값입니다. 예: `> 90` 예측. |
| **예측 시점까지의 시간** | 임계값 초과가 얼마나 앞서 규칙을 트리거할지 지정합니다. 1시간, 6시간, 12시간 또는 1일, 2일, 3일, 7일입니다. 기본값은 1일입니다. |
| **과거 데이터 조회 기간** | 추세를 투영할 과거 일수입니다. 1, 3, 7, 14 또는 30입니다. 기본값은 7입니다. |
| **모델** | **선형 추세**, 또는 **일간 패턴**이나 **주간 패턴**입니다. 일간·주간 패턴은 하루 또는 일주일 전 같은 시점의 값에 추세를 더한 것으로, 하루나 일주일 주기로 오르내리는 지표에 사용합니다. 주간 패턴은 최소 7일의 과거 데이터 조회 기간이 필요합니다. |

각 라운드는 현재 값을 시계열에 추가합니다. 새 규칙이나 쿼리가 변경된 규칙은 이력을 채우기 위해 먼저 몇 개의
과거 시점을 쿼리합니다. 포인트가 너무 적으면(6개 미만, 또는 일간·주간 패턴의 전체 주기보다 적으면)
해당 라운드는 판정을 내리지 않습니다. 인시던트에는 초과가 예상되는 시점과
그때의 예측값이 표시됩니다. 예측 규칙은 심각도 하나와 지속 시간을 가지며, 복구 임계값이 없고
[데이터가 없을 때](#복구-및-데이터-누락)를 설정할 수 있습니다.

## 이상치 규칙

이상치 규칙은 그룹화 쿼리의 그룹을 고정 임계값이 아니라 서로 비교합니다.
예를 들어 호스트별로 오류 수를 그룹화하면 다른 호스트보다 오류가 훨씬 많은 호스트가 트리거되고, 모든
호스트가 함께 증가하는 경우에는 트리거되지 않습니다. **트리거 유형**에서 **이상치**를 선택하고, 쿼리를 작성한 뒤
[**그룹화 기준**](#컬럼별로-규칙-그룹화)을 입력하고 다음을 설정합니다:

| 설정 | 설명 |
|---|---|
| **허용 범위** | 몇 배의 편차까지 이상치로 볼지 지정합니다. 0.5~10이며 기본값은 3입니다. 작을수록 민감합니다. |
| **감지 방향** | **높거나 낮은 값**, **높은 값만**, **낮은 값만**입니다. |

편차는 그룹의 중앙값과 중앙값 절대 편차(MAD)를 기준으로 측정하며, 그룹이 거의 같을 때 작은 흔들림이
이상치가 되지 않도록 계산합니다. 각 이상치 그룹은 자체 인시던트를 열고, 얼마나 떨어져 있는지를
보여줍니다. 값을 가진 그룹이 3개 미만이면 해당 라운드는 판정을 내리지 않습니다.
이상치 규칙은 APM·RUM 지표를 사용하지 않으며 심각도 하나와 지속 시간을 가집니다.

## 복합 규칙

복합 규칙은 여러 규칙을 함께 살펴봅니다. 결합된 규칙은 열린 인시던트가 있는 동안 참으로 계산되고,
표현식이 이들을 조합합니다. 예를 들어 `A && B`는 오류율과 지연 시간이 모두
알림될 때만 알리며, `A && !B`는 하위가 정상일 때만 상위 문제를 참으로 계산합니다. **트리거 유형**에서
**복합**을 선택합니다:

| 설정 | 설명 |
|---|---|
| **규칙** | 최대 10개 규칙이며 A, B, C 등으로 이름이 지정됩니다. |
| **표현식** | 문자를 `&&`(그리고), `\|\|`(또는), `!`(부정) 및 괄호로 조합합니다. 예: `A && (B \|\| C)`. |
| **이 규칙의 인시던트를 복합 인시던트 아래에 병합** | 복합 규칙이 인시던트를 열면, 결합된 규칙의 열린 인시던트가 해당 인시던트로 [병합](/ko/alerting/incidents#인시던트-병합)되어 자체 알림을 중단합니다. 이후에 발생한 인시던트도 병합됩니다. |

복합 규칙은 쿼리를 실행하지 않고 테스트할 수 없으며,
[데이터가 없을 때](#복구-및-데이터-누락) 설정이 없습니다. 결합된 규칙은 복합 규칙이 될 수 없고,
복합 규칙은 다른 규칙에 결합될 수 없습니다. 삭제된 결합 규칙은 거짓으로 계산됩니다.
인시던트에는 어떤 문자가 참이었는지 표시됩니다.

## 하트비트 규칙

하트비트 규칙은 관점을 뒤집어 작업이 보고하기를 기다립니다. cron 작업, 백업 스크립트 또는
배치 작업이 실행될 때마다 체크인 주소를 요청하고, 주기와 유예 시간 안에 체크인이 도착하지 않으면
또는 체크인이 실패를 보고하면 규칙이 트리거됩니다. **트리거 유형**에서
**하트비트**를 선택합니다:

| 설정 | 설명 |
|---|---|
| **체크인 주기** | 작업이 실행되는 빈도이며 1분에서 7일까지입니다. 기본값은 60분입니다. |
| **유예 시간** | 주기가 지난 뒤 체크인을 누락으로 간주하기까지 추가로 기다리는 시간이며 최대 1일입니다. 기본값은 5분입니다. |

저장하면 대화 상자에 체크인 주소와 `curl` 예시가 표시되며, 주소는 이때 한 번만
표시됩니다. 작업이 성공하면 해당 주소를 요청(`GET` 또는 `POST`)하고, 실패하면 `?status=fail`을 추가해
규칙이 즉시 트리거되도록 합니다. `POST` 본문의 시작 부분은 체크인 메시지로 인시던트에 보관되며,
로그의 마지막 줄에 적합합니다.

```bash
if ./backup.sh; then
  curl -fsS "$HEARTBEAT_URL"
else
  curl -fsS "$HEARTBEAT_URL?status=fail"
fi
```

하트비트 규칙을 편집하면 마지막 체크인과 다음 체크인의 최종 기한이 표시됩니다.
**체크인 주소 재설정**은 새 주소를 발급하며, 이전 주소는 즉시 작동을 멈춥니다. 체크인
주소는 로그인이 필요 없고 주소에 포함된 토큰만 있으면 됩니다. [공개 액세스](/ko/public-access) 및
[하트비트 체크인](/ko/api/alerting/heartbeats)을 참조하세요. 하트비트 규칙은 쿼리를 실행하지 않고 테스트할 수 없으며,
[데이터가 없을 때](#복구-및-데이터-누락) 설정이 없습니다.

## 실시간 규칙

실시간 규칙은 타이머 대신 수집 경로에서 실행됩니다. 수집 노드가 받아들인 모든 레코드는 해당 스트림의 실시간 규칙과 대조되고, 일치 항목은 `periodSecs`초의 슬라이딩 윈도에 들어갑니다. 매초 규칙을 담당하는 알림 노드가 쓰기를 처리하는 모든 노드에서 윈도 내 일치 항목을 읽어 합산합니다. 합계가 트리거에 도달하면 인시던트가 열리고, 더 이상 도달하지 않으면 해결되며, 이는 레코드가 기록된 후 최대 1초 이내입니다.

| 항목 | 동작 |
|---|---|
| 명령문 | SQL의 `SELECT count(*) FROM <stream> [WHERE <condition>]`입니다. 테이블은 규칙의 `stream`입니다. 조건은 필드를 리터럴과 비교하며(`=`, `!=`, `<`, `<=`, `>`, `>=`), `IN`, `BETWEEN`, `LIKE`, `ILIKE`, `IS [NOT] NULL`을 사용하고 `AND`, `OR`, `NOT`과 괄호로 결합합니다. 필드 대신 `json_text(<field>, '<key>')`를 사용하면 쿼리와 마찬가지로 JSON 필드의 키 하나를 텍스트로 읽습니다: `json_text(body, 'type') LIKE 'Uncorrected%'`. 누락되었거나 null인 필드는 어떤 비교에도 일치하지 않습니다. |
| 윈도 | `periodSecs`는 1에서 3600까지입니다. |
| 트리거 | `operator`는 `gt` 또는 `gte`이고, `for_periods`는 `0` 또는 `1`입니다. `thresholds`의 단계는 개수에 따라 심각도를 설정합니다. |
| 인시던트 | 인시던트는 일반적인 수명 주기를 따릅니다. 규칙당 하나의 활성 인시던트, `silence_secs` 쿨다운, 에스컬레이션, 알림입니다. |

[규칙 만들기](/ko/api/alerting/create-rule)는 이러한 제한을 벗어난 실시간 규칙을 `400`으로 거부합니다. 개수는 쓰기를 처리하는 각 노드의 메모리에 유지되며, 각 노드는 5초마다 메타데이터 데이터베이스에 윈도 스냅샷을 저장합니다. 재시작한 노드는 스냅샷을 다시 읽고 최대 마지막 5초만 손실합니다. 노드가 다운되었거나 응답하지 않는 동안 담당 알림 노드는 해당 노드의 마지막 스냅샷을 대신 사용하며, 그 개수가 윈도를 벗어날 때까지 그렇게 합니다. 다른 알림 노드가 규칙을 이어받을 때 잃는 것은 없으며, 열려 있는 인시던트에서 발동 상태를 가져옵니다. 노드는 클러스터 베어러(`MS_SELF_TELEMETRY_CLUSTER_TOKEN`, 역할 분리 배포와 공유)로 서로의 개수를 읽으며, 이것이 없으면 다른 노드는 스냅샷으로만 알 수 있습니다.

### 연합 환경의 실시간 규칙

[클러스터 간 연합](/ko/settings/data-plane#클러스터-페더레이션)에서는 각 클러스터가 자신에게 기록된 레코드를 집계하며, 기본적으로 각 클러스터는 자체 집계로 판정합니다. 클러스터를 합산하려면 판정할 클러스터를 설정합니다. API에서는 `query.home_cluster`, 규칙 작업대에서 규칙을 열 때는 **판정 클러스터**이며, 이 클러스터와 활성화된 원격 클러스터가 제공됩니다. 해당 클러스터만 규칙의 인시던트를 열고 해결합니다. 매초 해당 클러스터에서 규칙을 담당하는 알림 노드가 조직이 매핑된 각 클러스터에 조직별 토큰으로 개수를 요청하고, 그 개수를 자기 개수에 더합니다. 다른 클러스터는 집계만 합니다. 800밀리초 안에 응답하지 않는 클러스터는 마지막으로 제공한 개수로 최대 30초 동안 집계되고, 그 이후에는 0으로 집계되므로 한 초를 놓쳐도 인시던트가 해결되지 않습니다. 메트릭 `realtime_federated_counts_failed_total{cluster}`가 누락 횟수를 집계합니다. 규칙은 동일한 id로 연합을 따르므로 모든 클러스터가 이를 집계합니다.

## 평가 지연

역할 분리 클러스터에서 쿼리는 수집이 플러시한 데이터만 읽으며, 수집 버퍼의 레코드는 최대 `[intake].flush_interval_secs`(기본값 30초) 이후에만 나타나므로 최신 윈도의 집계가 낮게 나옵니다. 규칙 작업대의 **고급** 아래에 있는 **평가 지연**은 각 라운드의 윈도를 뒤로 이동합니다. 5분과 5분 기간이면 07:00 라운드는 06:50부터 06:55까지의 데이터를 읽습니다.

| 값 | 효과 |
|---|---|
| **자동**(기본값) | 모든 역할을 실행하는 단일 프로세스에서는 없음, 역할 분리 클러스터에서는 **설정 → 알림 평가**의 **평가 지연**, 기본값 60초입니다. |
| **지연 없음** | 현재까지 읽습니다. |
| 30초에서 1시간 | 규칙 자체의 지연입니다. API는 0에서 3600초를 받습니다(`query.delay_secs`). |

데이터 없음 검사, 복구 조건, 이상 기준선, 예측 시계열, 분할 규칙, 이상치는 모두 같은 지연만큼 뒤로 이동합니다. 윈도가 이동한 경우 인시던트는 읽은 범위를 `evaluated_window` 어노테이션에 유지합니다. 실시간 규칙은 쿼리를 실행하지 않으며 평가 지연이 없습니다.

## 우선순위와 긴급도

규칙 작업대의 **Notify 및 대응** 아래에 있는 **우선순위**와 **긴급도**는 규칙의 인시던트가 어떤 값으로 열리는지 설정합니다.

- **우선순위**: 조직의 [우선순위 수준](/ko/alerting/on-call#긴급도-및-우선순위-수준) 중 하나이며, 기본값은 P1에서 P5이고 P1이 가장 높습니다. 설정하지 않으면 인시던트에 우선순위가 없습니다([알림 파이프라인](/ko/pipelines)이 여전히 설정할 수 있습니다). 우선순위는 심각도에서 파생되지 않습니다.
- **긴급도**: **에스컬레이션 정책에 따름**(기본값)은 [인시던트 에스컬레이션 정책의 긴급도](/ko/alerting/on-call#긴급도)를 따르며, 높음 또는 낮음은 모든 인시던트에 적용됩니다.

## 조사 가이드

규칙 작업대의 **조사 가이드** 섹션은 규칙의 인시던트를 조사할 때 무엇을 먼저 해야 하는지 알려줍니다. 각 항목은 선택 사항입니다.

| 항목 | 포함 내용 | 제한 |
|---|---|---|
| **조사 단계** | Markdown: 무엇을 먼저, 어떤 순서로 확인할지. | 8,000자 |
| **쿼리** | **이름**, 쿼리 언어(**promql** 또는 **sql**), SQL인 경우 **스트림**과 해당 **스트림 유형**, 그리고 **쿼리**입니다. | 최대 4,000자의 쿼리 10개 |
| **대시보드** | 인시던트에서 열 대시보드입니다. | 대시보드 5개 |

가이드는 규칙의 각 인시던트에서 **조사 가이드** 아래에 표시됩니다. 조사 단계는 서식 있는 텍스트로, 각 쿼리는 인시던트의 시간 범위에 걸쳐 Metrics(PromQL), Traces(트레이스 스트림의 SQL) 또는 Logs(기타 SQL)를 여는 링크로, 각 대시보드는 링크로 표시됩니다. [Mole Agent](/ko/agent)는 인시던트를 조사하기 전에 가이드를 읽고 해당 쿼리를 먼저 실행하며, 인시던트의 [AI 근본 원인](/ko/alerting/incidents#ai-근본-원인)이 이를 고려합니다.

API에서는 가이드가 규칙의 `guide` 필드입니다. [규칙 만들기](/ko/api/alerting/create-rule#조사-가이드)를 참조하세요. 내보내기에는 가이드가 포함됩니다. 가져오기 시 조직에 없는 대시보드는 가이드에서 제외됩니다.

## 탐지 규칙

[탐색](/ko/alerting/discovery)이 찾은 결과는 목록으로만 표시됩니다. 알림을 받으려면 **알림 → 탐색**에서 **새 탐지 규칙**을 선택하거나 탐지 결과에서 **유사 탐지 결과에 대한 알림 설정**을 선택한 다음, 탐지 결과의 종류, 서비스 또는 애플리케이션, 환경, 최소 심각도를 선택하고 에스컬레이션 정책과 긴급도를 지정합니다. 규칙이 처리하는 각 탐지 결과는 자체 인시던트를 열며, 심각도는 탐지 결과와 같고 긴급도는 설정하지 않는 한 낮음입니다. 탐지 결과가 종료되면 인시던트가 복구됩니다. 규칙 목록에는 해당 규칙의 소스로 **탐색**이 표시되며, 이를 열면 탐색 페이지로 이동합니다.

## 가져오기 및 내보내기

규칙 목록의 **가져오기/내보내기**는 규칙을 파일로 저장하거나 파일에서 가져옵니다:

- **모든 규칙 내보내기** 또는 필터링 후 **이 N개 규칙 내보내기**를 선택하면 JSON 규칙 번들(`"format": "molesignal.alert-rules/v1"`)을 다운로드합니다. 규칙은 전체 정의를 유지하지만 id, 조직, 평가 상태 또는 시간은 포함하지 않습니다. 에스컬레이션 정책과 복합 규칙의 규칙은 이름으로 참조되므로 번들을 다른 워크스페이스나 클러스터로 옮길 수 있습니다. 하트비트 규칙의 체크인 주소는 번들에 포함되지 않으므로 가져온 후 규칙에서 다시 설정해야 합니다.
- **규칙 가져오기…**는 번들 또는 Prometheus 알림 규칙 파일(Prometheus Operator의 `PrometheusRule` 포함)을 붙여넣거나 선택하여 가져옵니다. **테스트 실행**을 선택하면 각 규칙이 생성될지, 업데이트될지(변경되는 필드 포함), 그대로 유지될지, 실패할지 확인한 다음 **N개 가져오기**를 선택합니다. 규칙은 이름으로 매칭됩니다: 새 이름은 생성되고, 규칙이 하나인 이름은 업데이트되며, 규칙이 여러 개인 이름은 실패합니다. 파일에서 같은 이름이 두 번 나오는 경우도 마찬가지입니다(내보낸 파일을 가져오기 전에 같은 이름을 공유하는 규칙의 이름을 바꿔야 합니다). **새 규칙만 생성하고 같은 이름의 기존 규칙은 유지**를 선택하면 기존 규칙을 건너뜁니다. 규칙이 하나라도 실패하면 아무것도 기록되지 않으며, 그렇지 않으면 전체 가져오기가 한 번에 기록됩니다. 전부 아니면 전무 방식입니다.

Prometheus 규칙은 다음과 같은 방식으로 MoleSignal 규칙이 됩니다:

| Prometheus | MoleSignal |
|---|---|
| `alert` | 규칙의 이름입니다. 동일한 알림 이름이 여러 그룹에 있으면 첫 번째 이후에는 해당 그룹의 이름을 사용합니다. |
| `expr` | `count(<expr>)` 문과 `>= 1` 조건을 사용하는 PromQL 규칙입니다. 표현식이 시계열을 반환하면 알림이 발생합니다. 애너테이션이나 레이블에서 `{{ $labels.x }}`를 사용하면 문은 `count by (x) (<expr>)`가 되고 규칙은 `x` 기준으로 [분할](#컬럼별로-규칙-그룹화)되며 그룹당 인시던트 하나가 생성됩니다. 스트림은 표현식의 첫 번째 메트릭 이름입니다. |
| 그룹의 `interval` | 기간입니다. 지정하지 않으면 60초입니다. |
| `for` | 연속된 기간 수이며 올림 처리합니다. |
| `severity` 레이블 | 심각도입니다. `critical`과 `page`는 심각, `error`와 `high`는 오류, `warning`과 `warn`은 경고, `info`, `low`, `none`은 정보입니다. 다른 레이블은 유지됩니다. |
| `annotations` | 유지됩니다. 설명은 `description` 또는 `summary` 애너테이션입니다. |
| `record` | 레코딩 규칙은 가져오지 않으며 결과 아래에 나열됩니다. |
| `keep_firing_for` | 지원되지 않으며 결과 아래에 나열됩니다. |

가져온 규칙은 기본 에스컬레이션 정책을 사용합니다. 필요한 경우 가져오기 전에 번들에서 `escalation_policy`를 설정합니다. Alertmanager 자체 구성(`alertmanager.yml`의 라우트와 수신자)은 규칙이 아니며 이 방식으로 가져올 수 없습니다. 대신 [알림 라우팅](/ko/alerting/routing)과 [알림 정책](/ko/notification-channels)을 사용합니다.

CI에서는 [CLI](/ko/cli)가 `molesignal alerts rules export`와 `molesignal alerts rules apply -f rules.json [--dry-run]`를 실행합니다. 결과는 표로 출력되며, 규칙이 하나라도 실패하면 명령이 종료 코드 1로 종료됩니다.

## 규칙 변경, 일시 중지 또는 삭제

규칙을 열어 변경한 다음 **규칙 테스트**를 다시 실행하고 저장합니다. **초안 저장**은 규칙을 비활성 상태로 유지하며,
**저장 및 활성화**는 규칙을 다시 활성화합니다. 규칙을 삭제하려면
[규칙 삭제](/ko/api/alerting/delete-rule)를 호출합니다. 규칙의 알림을 잠시 음소거하려면
규칙을 변경하지 않고 [사일런스](/ko/alerting/silences)를 사용합니다.

[알림 규칙 API](/ko/api/alerting/create-rule)는 스크립트에서 규칙을 생성, 테스트, 트리거합니다.
