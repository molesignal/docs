서비스 페이지의 **배포** 섹션은 두 소스를 나란히 보여 줍니다. 즉, 파이프라인이 보고한 배포와
서비스의 스팬이 `service.version`에 담고 있는 버전입니다. 파이프라인이 보고하지 않은 버전도
스팬만으로 표시됩니다.

## 배포 타임라인

타임라인은 해당 기간에 서비스에 발생한 일을 최신순으로 나열합니다.

| 이벤트 | 시점 |
|---|---|
| **배포 완료** | 파이프라인이 성공한 배포를 보고했습니다. |
| **실패** | 파이프라인이 실패한 배포를 보고했습니다. 실패한 배포는 실행 중인 버전을 변경하지 않습니다. |
| **롤백됨** | 파이프라인이 롤백을 보고했거나, 다른 버전보다 먼저 실행된 버전의 배포를 보고했습니다. 해당 행에는 되돌리기 전에 실행 중이던 버전이 표시됩니다. |
| **이전 버전으로 복귀** | 스팬이 파이프라인이 보고하지 않은 이전 버전으로 돌아갔습니다. 마지막으로 확인된 버전은 5분 넘게 전에 중지된 더 새로운 버전보다 앞서 최초 발생했습니다. |
| **최초 발생** | 스팬이 파이프라인이 보고하지 않은 버전을 담고 있었습니다. |
| **구성** | 파이프라인 또는 도구가 구성 변경을 보고했습니다. 해당 행에 설명이 표시됩니다. |
| **기능 플래그** | 파이프라인 또는 도구가 기능 플래그 변경을 보고했습니다. 해당 행에 설명이 표시됩니다. |

구성 변경이나 기능 플래그는 실행 중인 버전을 변경하지 않으며 자체 수치가 없습니다.
인사이트 근처의 변경 사항에 나열됩니다. 자세한 내용은
[발견 사항 근처의 변경 사항](/ko/apm/insights#발견-항목-근처의-변경-사항)을 참조하세요.

보고된 배포에는 커밋, 풀 리퀘스트, CI 실행, 작성자가 표시됩니다. 리포지토리가
http 또는 https 주소이면 커밋은 GitHub, GitLab 또는 Bitbucket이 커밋을 링크하는 방식으로
웹 페이지에서 열립니다.

각 버전의 해당 기간 요청 수, 오류율, p95는 가장 최신 행에 표시되며,
바로 앞서 최초 발생한 버전과 비교한 판정도 함께 표시됩니다.

| 판정 | 기준 |
|---|---|
| **재발** | 오류율이 1포인트 이상이면서 1.5배 이상 상승했거나, p95가 1/5 이상이면서 50 ms 이상 상승했습니다. 악화된 부분은 판정 뒤에 표시됩니다. |
| **개선** | 두 지표 중 하나가 같은 폭으로 하락했고, 어느 쪽도 악화되지 않았습니다. |
| **변경 없음** | 어느 지표도 그만큼 움직이지 않았습니다. |
| **요청 수 부족** | 두 버전 중 하나가 버전 비교에 필요한 요청 수(기본값 1,000)보다 적은 요청을 처리했습니다. |

판정을 선택하면 **두 버전 비교**에서 해당 두 버전이 열리며, 느려진 엔드포인트와
증가한 오류가 나열됩니다. 재발 또는 개선된 버전은 개요의 최근 배포에서도
표시됩니다.

## 카나리

카나리가 대체하는 버전 옆에서 실행되는 것처럼 두 버전이 동시에 실행되면, 타임라인 위의 카드가
두 버전을 나란히 보여 줍니다. 두 버전이 동시에 실행되는 것은 둘 다 서비스의 마지막 스팬으로부터 5분 이내에 확인된 경우입니다. 카드는
가장 최신 두 버전을 더 새로운 버전이 최초 발생한 시점부터
비교합니다:

- 각 버전이 처리한 요청 비율;
- 각 버전의 요청 수, 오류율, p50, p95, p99;
- 더 새로운 버전의 이전 버전 대비 판정.

## CI에서 배포 보고

파이프라인은 `POST /api/v1/apm/deployments`로 배포를 보고합니다. 요청에는
`apm.deploy`를 사용할 수 있는 API 토큰이 필요합니다. 소유자, 관리자, 편집자에게 이 권한이 있으며,
수집 토큰이 따르는 **데이터 수집** 정책에도 이 권한이 포함됩니다.

```bash
curl -X POST "https://<host>/api/v1/apm/deployments" \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{"service": "checkout", "environment": "production", "version": "2.4.0", "commit": "9f2c1e7a4b3d", "repository": "https://github.com/acme/checkout", "ciUrl": "https://ci.example.com/runs/7"}'
```

| 필드 | 필수 | 설명 |
|---|---|---|
| `service` | 필수 | 스팬이 `service.name`에 지정하는 서비스입니다. 최대 255자입니다. |
| `version` | 배포 시 필수 | 배포된 버전으로, 스팬이 `service.version`에 보고하는 값입니다. 최대 192자입니다. |
| `kind` | 선택 | `deployment`(기본값), `configuration`, `feature_flag`, `scaling` 또는 `infrastructure`입니다. |
| `namespace` | 선택 | 서비스의 `service.namespace`입니다. 이 값이 없는 배포는 모든 네임스페이스에 표시됩니다. |
| `environment` | 선택 | `deployment.environment.name`으로 지정하는 환경입니다. 이 값이 없는 배포는 모든 환경에 표시됩니다. |
| `status` | 선택 | `succeeded`(기본값), `failed`, 또는 배포로 서비스가 `version`으로 되돌아간 경우 `rolled_back`입니다. |
| `commit` | 선택 | 배포된 커밋으로, 최대 64자의 영문자와 숫자입니다. |
| `repository` | 선택 | 코드가 있는 위치로, 최대 512자의 https, http, ssh 또는 git 주소입니다. 주소의 비밀번호와 https 주소의 사용자 부분은 `****`로 유지됩니다. |
| `pullRequest` | 선택 | 풀 리퀘스트에 대한 http 또는 https 링크입니다. |
| `author` | 선택 | 배포한 사람으로, 최대 128자입니다. |
| `ciUrl` | 선택 | CI 실행에 대한 http 또는 https 링크입니다. |
| `description` | 선택 | 최대 1,000자입니다. 이벤트 위에 포인터를 두면 표시됩니다. |
| `deployedAt` | 선택 | 배포가 발생한 시각으로, 에포크 이후 마이크로초 단위입니다. 기본값은 요청이 도착한 시각입니다. |

서비스와 환경은 APM에서 지정하는 방식으로 이름이 지정됩니다. 조직의 명명 규칙,
환경 매핑, 별칭이 스팬에 적용되는 것과 마찬가지로 서비스와 환경에도 적용됩니다. 자세한 내용은
[APM 설정](/ko/apm/settings)을 참조하세요.

**데이터 소스** 페이지에는 **GitHub Actions**, **GitLab CI/CD**, **Jenkins** 아래에 다음 단계가 있으며,
워크스페이스 주소가 입력되어 있습니다.

### GitHub Actions

토큰을 리포지토리 시크릿으로 저장한 다음, 배포하는 작업에 단계를 추가합니다. `if: always()`를 사용하면
실패한 배포도 보고됩니다.

```yaml
- name: Report the deployment to MoleSignal
  if: always()
  env:
    MOLESIGNAL_TOKEN: ${{ secrets.MOLESIGNAL_TOKEN }}
    DEPLOY_STATUS: ${{ job.status == 'success' && 'succeeded' || 'failed' }}
  run: |
    cat > deployment.json <<EOF
    {
      "service": "checkout",
      "environment": "production",
      "version": "${GITHUB_SHA::12}",
      "status": "$DEPLOY_STATUS",
      "commit": "$GITHUB_SHA",
      "repository": "$GITHUB_SERVER_URL/$GITHUB_REPOSITORY",
      "author": "$GITHUB_ACTOR",
      "ciUrl": "$GITHUB_SERVER_URL/$GITHUB_REPOSITORY/actions/runs/$GITHUB_RUN_ID"
    }
    EOF
    curl -fsS -X POST "https://<host>/api/v1/apm/deployments" \
      -H "Authorization: Bearer $MOLESIGNAL_TOKEN" \
      -H "Content-Type: application/json" \
      --data-binary @deployment.json
```

### GitLab CI/CD

토큰을 `MOLESIGNAL_TOKEN`이라는 마스킹된 CI/CD 변수로 추가한 다음, 배포 작업의
`after_script`에서 보고합니다. 이 스크립트는 배포 성공 여부와 관계없이 실행됩니다.

```yaml
deploy:
  stage: deploy
  environment: production
  script:
    - ./deploy.sh
  after_script:
    - |
      if [ "$CI_JOB_STATUS" = "success" ]; then DEPLOY_STATUS=succeeded; else DEPLOY_STATUS=failed; fi
      cat > deployment.json <<EOF
      {
        "service": "checkout",
        "environment": "$CI_ENVIRONMENT_NAME",
        "version": "$CI_COMMIT_SHORT_SHA",
        "status": "$DEPLOY_STATUS",
        "commit": "$CI_COMMIT_SHA",
        "repository": "$CI_PROJECT_URL",
        "author": "$GITLAB_USER_LOGIN",
        "ciUrl": "$CI_PIPELINE_URL"
      }
      EOF
      curl -fsS -X POST "https://<host>/api/v1/apm/deployments" \
        -H "Authorization: Bearer $MOLESIGNAL_TOKEN" \
        -H "Content-Type: application/json" \
        --data-binary @deployment.json
```

### Jenkins

토큰을 ID가 `molesignal-token`인 **Secret text** 자격 증명으로 추가한 다음,
파이프라인의 `post` 블록에서 보고합니다. `post { always }`를 사용하면 실패한 빌드도 보고됩니다. `GIT_URL`의 비밀번호는
배포를 저장할 때 마스킹됩니다.

```groovy
post {
  always {
    script {
      writeFile file: 'deployment.json', text: groovy.json.JsonOutput.toJson([
        service: 'checkout',
        environment: 'production',
        version: env.GIT_COMMIT.take(12),
        status: currentBuild.currentResult == 'SUCCESS' ? 'succeeded' : 'failed',
        commit: env.GIT_COMMIT,
        repository: env.GIT_URL,
        ci_url: env.BUILD_URL,
      ])
    }
    withCredentials([string(credentialsId: 'molesignal-token', variable: 'MOLESIGNAL_TOKEN')]) {
      sh '''
        curl -fsS -X POST "https://<host>/api/v1/apm/deployments" \
          -H "Authorization: Bearer $MOLESIGNAL_TOKEN" \
          -H "Content-Type: application/json" \
          --data-binary @deployment.json
      '''
    }
  }
}
```

## 구성 변경 및 기능 플래그 보고

구성 변경, 기능 플래그, 규모 변경 또는 인프라 변경은 서비스 아래에서 동일한 엔드포인트로 보고합니다.
`kind`를 설정하고 변경 내용에 대한 설명을 함께 전달합니다. 버전은 필요하지
않습니다.

보고된 모든 변경 사항은 [`GET /api/v1/changes`](/ko/api/changes)에도 나열되며, 다음 위치에 표시됩니다.
로그 및 트레이스의 히스토그램과 메트릭 차트 아래, 알림의 **변경 사항** 페이지.

```bash
curl -X POST "https://<host>/api/v1/apm/deployments" \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{"service": "checkout", "environment": "production", "kind": "feature_flag", "description": "new_checkout on for 10% of users"}'
```

## 웹훅에서 변경 사항 보고

웹훅에서 본문과 헤더를 설정할 수 있는 도구(예: Argo CD 알림, Spinnaker 또는
본문 템플릿을 사용하는 Unleash 웹훅 추가 기능)는 위와 같이 `POST /api/v1/apm/deployments`를 호출합니다. 자체
본문을 보내거나 헤더를 설정할 수 없는 도구는 대신 `POST /api/v1/intake/changes`를 호출합니다. API
토큰은 `Authorization: Bearer`에 넣거나, 헤더를 설정할 수 없는 경우 `?token=`에 넣으며, 다음 권한이 있어야 합니다:
`apm.deploy`. 주소에 포함된 토큰은 프록시 로그에 남을 수 있으므로, 이러한 도구에는 자체 토큰을 부여하고,
`apm.deploy`로만 범위를 제한합니다.

| 매개변수 | 비고 |
|---|---|
| `format` | `generic`(기본값), `launchdarkly`, `unleash`, `nacos` 또는 `apollo`입니다. |
| `service`, `namespace`, `environment` | 본문에 명시되지 않은 값을 보완합니다. 서비스를 지정하지 않은 변경은 거부됩니다. |
| `kind` | `deployment`, `configuration`, `feature_flag`, `scaling` 또는 `infrastructure`입니다. 본문에 지정된 값을 재정의합니다. |
| `serviceField`, `environmentField`, `versionField`, `descriptionField`, `authorField` | `generic`의 경우 `/app/name`과 같은 JSON 포인터 또는 최상위 필드 이름입니다. 지정하지 않으면 `POST /api/v1/apm/deployments`가 받는 동일한 이름의 필드를 읽습니다. |

| 형식 | 해석 방식 |
|---|---|
| `launchdarkly` | 기능 플래그입니다. 환경은 감사 대상 리소스의 `env/` 부분이고, 설명은 항목의 제목이며, 작성자는 멤버의 이메일입니다. |
| `unleash` | 기능 플래그입니다. 이벤트 유형과 토글 이름, 해당 환경, 변경한 주체를 읽습니다. |
| `nacos` | 데이터 ID와 그룹의 구성 변경입니다. Nacos 네임스페이스를 네임스페이스로 사용합니다. |
| `apollo` | 구성 변경입니다. 앱 ID가 서비스이고, 클러스터가 환경이며, 네임스페이스와 릴리스 제목이 변경 내용을 나타냅니다. |

**데이터 소스 → DevOps**에는 LaunchDarkly, Unleash, Nacos, Apollo 각각에 대한 가이드가 있으며,
워크스페이스에 맞는 주소가 채워져 있습니다.

본문에는 변경 하나 또는 최대 100개의 변경 목록을 담을 수 있습니다. 응답은 변경 사항이 저장된 상태의 `201`입니다.
프리셋은 도구의 문서화된 페이로드를 기준으로 작성되었으며 실제
계정에서는 검증되지 않았습니다. 도구의 페이로드가 다른 경우 포인터와 함께 `generic`을 사용합니다.

```bash
curl -X POST "https://<host>/api/v1/intake/changes?format=launchdarkly&service=checkout&token=<token>" \
  -H "Content-Type: application/json" \
  -d @launchdarkly-event.json
```

## 문제 해결

| 증상 | 확인 |
|---|---|
| 보고된 배포가 타임라인에 없음 | 시간 범위에 `deployedAt`이 포함되어야 하고, `service`는 APM에서 사용하는 서비스 이름과 일치해야 합니다. 환경과 함께 보고된 배포는 해당 환경에서만 표시됩니다. |
| 배포와 배포된 버전이 두 행으로 표시됨 | 보고된 `version`이 스팬에 포함된 `service.version`과 다릅니다. 동일한 값을 보고합니다. |
| 배포 엔드포인트에서 `403` | 토큰이 `apm.deploy`를 사용할 수 없습니다. 범위에 이 권한이 없거나, 토큰의 멤버 또는 서비스 계정에 이 권한이 없습니다. |
| 배포 엔드포인트에서 `400` | 필드가 위 표의 제한을 위반했습니다. 오류 메시지에 어떤 필드인지 표시됩니다. |
