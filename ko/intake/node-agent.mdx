MoleSignal Node Agent는 모든 Linux 호스트에서 실행되며 하나의 인테이크 토큰으로 세 가지 신호를 전송합니다:

| 신호 | 전송 위치 | 포함 내용 |
|---|---|---|
| 메트릭 | OTLP를 통한 메트릭 스트림 `host-metrics` | CPU, 부하, 메모리, 디스크, 네트워크 등이 `molesignal_host_*` 이름으로 제공됩니다. |
| 이벤트 | OTLP를 통한 로그 스트림 `host-events` | 커널 및 하드웨어 이벤트: OOM 종료, 패킷 드롭, TCP 재전송, 링크 변경, RAS 오류, 헝 태스크, 소프트 록업. |
| 프로필 | 프로필 인테이크, `/api/v1/profiles/intake` | 지속적 프로파일링이 켜져 있을 때 호스트 워크로드의 CPU 프로필(pprof 형식). |

**데이터 소스** 페이지는 아래 명령을 실제 주소와 토큰이 채워진 상태로 생성합니다. **데이터 소스 → 권장 → MoleSignal Node Agent**를 엽니다.

## 설치 전

- systemd가 있는 Linux 호스트 또는 Kubernetes 클러스터. 커널 이벤트에는 BTF(`/sys/kernel/btf/vmlinux`)와 tracefs가 필요합니다.
- 호스트의 root 권한 또는 권한 있는(privileged) 파드를 허용하는 네임스페이스.
- 워크스페이스의 [인테이크 토큰](/ko/intake#수집-토큰).
- 호스트에서 MoleSignal의 두 포트로의 네트워크 액세스: 메트릭과 이벤트용 OTLP gRPC `4317`, 폴백 및 프로필 업로드용 HTTP API.

## systemd로 설치

에이전트 릴리스에는 바이너리와 `deploy/systemd/install.sh`가 포함되어 있습니다. 각 호스트에서 root 권한으로 압축을 푼 릴리스에서:

1. 에이전트를 시작하지 않고 바이너리, 유닛, `/etc/molesignal-node-agent`를 설치합니다.

   ```bash
   sh deploy/systemd/install.sh install ./molesignal-node-agent --no-start
   ```

2. MoleSignal 주소와 토큰을 기록한 다음 에이전트를 시작합니다.

   ```bash
   cat > /etc/molesignal-node-agent/agent.env <<'ENV'
   MS_ENDPOINT=https://molesignal.example.com:4317
   MS_HTTP_ENDPOINT=https://molesignal.example.com
   MS_TOKEN_PATH=/etc/molesignal-node-agent/token
   ENV
   printf '%s' '<token>' > /etc/molesignal-node-agent/token
   chmod 0600 /etc/molesignal-node-agent/token
   systemctl enable --now molesignal-node-agent
   ```

gRPC가 TLS 없이 제공될 때는 `MS_ENDPOINT`에 `http://`를 사용합니다. `install.sh upgrade <binary>`는 업그레이드하며, 새 릴리스가 준비 상태가 되지 않으면 자동으로 롤백합니다. `install.sh uninstall`은 에이전트를 제거하고 구성과 대기 중인 배치를 유지합니다.

## Kubernetes에 설치

에이전트 릴리스에는 `deploy/kubernetes/node-agent.yaml`이 포함되어 있습니다. 이 파일은 `molesignal` 네임스페이스의 DaemonSet으로, 호스트의 PID 및 네트워크 네임스페이스를 사용하여 모든 노드에서 동일한 에이전트를 실행합니다.

```bash
kubectl apply -f deploy/kubernetes/node-agent.yaml
printf '%s' '<token>' > agent.token
kubectl -n molesignal create secret generic molesignal-node-agent-token --from-file=token=./agent.token
kubectl -n molesignal patch configmap molesignal-node-agent --type merge \
  -p '{"data":{"MS_ENDPOINT":"https://molesignal.example.com:4317","MS_HTTP_ENDPOINT":"https://molesignal.example.com"}}'
kubectl -n molesignal rollout restart daemonset/molesignal-node-agent
```

네임스페이스에는 `privileged` Pod Security 수준이 필요하며, 매니페스트에서 이를 설정합니다.

## 구성

에이전트는 환경에서 설정을 읽습니다. systemd에서는 `/etc/molesignal-node-agent/agent.env`, Kubernetes에서는 ConfigMap입니다.

| 변수 | 기본값 | 의미 |
|---|---|---|
| `MS_ENDPOINT` | 없음, 필수 | MoleSignal의 OTLP gRPC 주소, 포트 `4317`. 메트릭과 이벤트가 여기로 전송됩니다. |
| `MS_HTTP_ENDPOINT` | `MS_ENDPOINT` | HTTP API: 웹 UI의 주소. gRPC 응답이 없을 때와 프로필 업로드에 사용됩니다. |
| `MS_TOKEN_PATH` | 없음, 필수 | 인테이크 토큰이 들어 있는 파일이며 소유자만 읽을 수 있습니다. |
| `MS_STREAM_NAME` | `host-metrics` | 메트릭 스트림. |
| `MS_STREAM_EVENTS` | `host-events` | 이벤트의 로그 스트림. |
| `MS_PROFILING_CPU_ENABLED` | `false` | 전체 호스트의 지속적 CPU 프로파일링. |

아래 호스트 자산은 `host-metrics`와 `host-events`를 읽습니다. 이를 사용하려면 기본 스트림 이름을 유지합니다.

## 에이전트 확인

호스트 또는 파드에서 `doctor`를 실행합니다:

```bash
molesignal-node-agent doctor
```

```bash
kubectl -n molesignal exec ds/molesignal-node-agent -- molesignal-node-agent doctor
```

`doctor`는 커널, BTF, 권한, 마운트, cgroups, 컨테이너 런타임, 엔드포인트, 토큰을 확인합니다. 모든 줄이 `PASS`여야 합니다. `FAIL`은 에이전트가 실행되거나 전송할 수 없음을 의미하고, `WARN`은 저하된 상태로 실행되는 수집기를 나타냅니다. 출력에는 토큰이 표시되지 않습니다.

그런 다음 가이드의 **데이터 수신 확인** 단계에서 **연결 확인**을 클릭합니다. 최근 1시간 동안 수신된 메트릭, 로그, 프로필을 찾습니다.

## 이벤트

모든 이벤트는 다음 필드가 있는 `host-events`의 로그입니다:

| 필드 | 값 |
|---|---|
| `event.name` | 발생한 일: `oom`, `dropwatch`, `tcp_retransmit`, `net_rx_latency`, `netdev_events`, `netdev_txqueue_timeout`, `lacp`, `ras`, `hungtask`, `softlockup` 등. |
| `event.domain` | `host_kernel`, `host_autotracing` 또는 `host_tool`. |
| `event.kind` | `anomaly`, `state_change` 또는 `task_result`. |
| `severity_text` | `INFO`, `WARN` 또는 `ERROR`. |
| `host.id`, `host.name` | 호스트. |
| `container.id`, `container.name` | 컨테이너 이벤트인 경우 컨테이너. |
| `body` | 이벤트의 필드(JSON 객체): `json_text(body, 'key')`로 하나를 읽습니다. |

## 호스트 자산

가이드의 네 번째 단계인 **호스트 자산 설치**는 워크스페이스가 호스트에 필요로 하는 항목을 설치합니다. **설치**는 누락된 항목만 추가하며 변경 내용을 덮어쓰지 않습니다. 클릭한 사용자가 해당 권한을 보유한 경우에만 각 부분이 설치되며, 나머지는 알림에 이름이 표시됩니다.

| 자산 | 설명 | 권한 |
|---|---|---|
| 이벤트 인덱스 | `host-events`의 `host.id`, `container.id`, `event.name`, `event.domain`, `severity_text`에 대한 정확 인덱스. | `streams.configure` |
| 호스트 대시보드 | 읽기 전용 대시보드 **호스트 · 개요**(uid `host-overview`). | `dashboards.create` |
| 저장된 뷰 | 호스트 이벤트에 대한 네 가지 뷰. | `saved_views.create` |
| 알림 규칙 | 비활성화된 상태로 생성되는 6개의 실시간 규칙. | `alerts.rules.manage` |

API를 통해서도 동일하게 사용할 수 있습니다. `GET /api/v1/node-agent/assets`는 각 부분의 상태를 알려주고, `POST /api/v1/node-agent/assets`는 이를 설치합니다. 둘 모두 `streams.query` 또는 `sys.telemetry.read`가 필요합니다.

### 이벤트 인덱스

로그 스트림은 이 다섯 필드가 처음 도착할 때 정확 인덱스를 부여하므로 새 `host-events` 스트림에는 아무것도 필요하지 않습니다. 이전에 이 필드들을 수신한 스트림에는 인덱스 없이 필드가 있습니다. 설치하면 스트림 설정에서처럼 각 필드에 대한 필드 규칙을 추가하고, 이미 기록된 데이터는 백그라운드에서 다시 인덱싱됩니다. 이미 자체 규칙이 있는 필드는 활성화 여부와 관계없이 그대로 둡니다. [스키마 및 필드](/ko/streams#스키마-및-필드)를 참조하세요.

### 호스트 대시보드

**대시보드 → 호스트 · 개요**는 시간 범위 내에 부하를 전송한 호스트 중 **호스트**에서 선택한 호스트를 한 번에 하나씩 표시합니다:

- `host-metrics`의 CPU 사용량, 부하, 메모리, 디스크 처리량, 네트워크 처리량, 네트워크 오류 및 드롭. 호스트 자체 시리즈만 해당합니다. 컨테이너 시리즈에는 `container.id`가 포함되므로 제외됩니다. 메모리는 4 KiB 페이지 단위로 `/proc/vmstat`에서 읽습니다.
- 시간 경과에 따른 호스트 이벤트를 심각도별, 종류별로 표시하고 최신 50개를 보여줍니다.

대시보드는 읽기 전용입니다. 변경하려면 복사합니다. 대시보드를 변경하는 이후 릴리스에서는 최신 상태로 만들기 위해 **설치**를 다시 제공합니다.

### 저장된 뷰

| 뷰 | 이벤트 |
|---|---|
| 호스트 · OOM 이벤트 | `event.name = 'oom'` |
| 호스트 · 네트워크 이벤트 | `dropwatch`, `tcp_retransmit`, `netdev_events`, `net_rx_latency`, `netdev_txqueue_timeout`, `lacp` |
| 호스트 · RAS 및 커널 중단 | `ras`, `hungtask`, `softlockup` |
| 호스트 · 오류 이벤트 | `severity_text = 'ERROR'` |

각 뷰는 **로그**에서 최신 이벤트의 모든 필드와 함께 열립니다. 필드 목록에서 `host.name`, `container.id`, `event.name` 또는 `severity_text` 값을 클릭하여 뷰를 더 좁힙니다. [저장된 뷰](/ko/saved-views)를 참조하세요.

### 실시간 알림

각 규칙은 `host-events`에 대한 [실시간 규칙](/ko/alerting/rules#실시간-규칙)입니다. 5분 내에 일치하는 이벤트가 하나 발생하면 기본 에스컬레이션 정책으로 인시던트가 열리고, 해당 인시던트는 동일한 이벤트에 대해 30분 동안 알림을 보내지 않습니다. 해당 가이드에는 먼저 확인할 항목, 이벤트 쿼리, 호스트 대시보드가 나열됩니다.

| 규칙 | 집계 이벤트 | 심각도 |
|---|---|---|
| OOM 종료 | `"event.name" = 'oom'` | 오류 |
| 헝 태스크 | `"event.name" = 'hungtask'` | 오류 |
| 소프트 록업 | `"event.name" = 'softlockup'` | 심각 |
| 정정 불가 하드웨어 오류 | `"event.name" = 'ras' AND json_text(body, 'type') LIKE 'Uncorrected%'` | 심각 |
| 링크 캐리어 다운 | `"event.name" = 'netdev_events' AND json_text(body, 'linkstatus') = 'linkstatus_carrierdown'` | 오류 |
| 전송 큐 시간 초과 | `"event.name" = 'netdev_txqueue_timeout'` | 경고 |

규칙은 비활성화된 상태로 생성되므로, 활성화하기 전에는 호출이 발생하지 않습니다. 가이드의 **활성화**는 규칙을 켜고, **비활성화**는 끄며, **편집**은 **알림 규칙**에서 엽니다. 규칙에는 `node_agent.template` 레이블이 지정됩니다. 다시 설치하면 누락된 규칙만 생성됩니다.

## 문제 해결

먼저 `doctor`를 실행한 다음 증상별 점검을 진행합니다.

| 증상 | 점검 |
|---|---|
| 데이터가 전혀 없음 | `doctor`가 무엇이 실패했는지 알려 줍니다. 설정, 엔드포인트, 토큰 또는 커널입니다. 엔드포인트에서 `FAIL`이 나오면 호스트가 포트 `4317`에 연결할 수 없다는 뜻이므로 방화벽과 `MS_ENDPOINT`를 확인합니다. `journalctl -u molesignal-node-agent`에서 에이전트 로그를 볼 수 있습니다. |
| `401 Unauthorized` | 토큰이 잘못되었거나, 폐기되었거나, 읽을 수 없는 상태입니다. 워크스페이스의 수집 토큰을 사용하고, 토큰 파일에는 해당 토큰만 두며 root만 읽을 수 있게 합니다. `doctor`의 `auth` 줄에서 엔드포인트가 응답한 내용을 확인할 수 있습니다. |
| `intake unreachable (…)`와 함께 배치가 쌓임 | `MS_ENDPOINT`는 gRPC 포트 `4317`이어야 하고 `MS_HTTP_ENDPOINT`는 HTTP API여야 합니다. `MS_ENDPOINT`가 HTTP 포트를 가리키면 gRPC 요청에 `404`가 응답되고, 둘 다 `4317`을 가리키면 모든 프로필 업로드가 실패합니다. 대기 중인 배치는 수정 후 다시 전송됩니다. |
| 메트릭은 들어오는데 프로필이 없음 | 프로필은 HTTP로 전송되며 지속적 CPU 프로파일링은 기본적으로 꺼져 있습니다. `MS_HTTP_ENDPOINT`와 `MS_PROFILING_CPU_ENABLED=true`를 설정하고 에이전트를 재시작한 다음 **프로필**에서 호스트의 워크로드를 확인합니다. |
| 부하 또는 CPU 백분율이 없음 | 이전 MoleSignal 릴리스에서는 `value` 필드가 처음에 정수로 정의된 스트림으로 전송된 소수 값을 오류 없이 버렸습니다. 최신 릴리스는 이 필드를 `float64`로 확장하며, 모든 수집 응답이 거부한 값을 보고합니다. MoleSignal을 업그레이드합니다. 자세한 내용은 [스키마와 필드](/ko/streams#스키마-및-필드)를 참고합니다. |
| 메트릭은 들어오는데 이벤트가 없음 | 커널 이벤트에는 BTF, tracefs, BPF 권한이 필요하며, Kubernetes에서는 DaemonSet의 마운트도 필요합니다. `doctor`가 누락된 항목을 표시하고 `molesignal-node-agent capabilities`가 수집기를 나열합니다. 이벤트는 본질적으로 드물게 발생하므로 유휴 호스트는 아무 이벤트도 보내지 않을 수 있습니다. |
