브라우저 RUM SDK는 세션을 생성할 때 샘플링 여부를 결정합니다. 이 결정은
해당 세션이 지속되는 동안 애플리케이션의 모든 탭에서 동일하게 유지됩니다.

## 샘플링 비율 구성

```ts
const rum = init({
  applicationId: 'checkout-web',
  clientToken: 'mspat-your-client-token',
  site: 'https://molesignal.example.com',
  sessionSampleRate: 25,
  sessionReplaySampleRate: 20,
});
```

두 값 모두 `0`부터 `100`까지의 백분율입니다.

- `sessionSampleRate`는 SDK가 세션과 관련 RUM 이벤트를 보고할지 결정합니다. 기본값은 `100`입니다.
- `sessionReplaySampleRate`는 샘플링된 세션에만 적용됩니다. 기본값은 `0`입니다.

실제 리플레이 비율은 두 샘플링 비율을 곱한 값입니다. 예에서는 전체 세션의 약 25%가
RUM 데이터를 보고하고, 전체 세션의 약 5%에서 리플레이를 기록합니다(`25% × 20%`).

<Note>
  `startSessionReplayRecording()`을 호출하면 현재 샘플링된 세션의 리플레이를 활성화할 수 있습니다. 단, 이 메서드로는
  `sessionSampleRate`에서 제외된 세션을 샘플링 대상에 포함할 수 없습니다.
</Note>

## 서버에서 세션의 일부 보관

애플리케이션은 SDK 샘플링에 더해, 어떤 클라이언트가 보냈는지와 관계없이 수신한 세션 중 일부만 보관할 수 있습니다.
**RUM → 애플리케이션**에서 애플리케이션을 열고 **세션 보관**을 찾습니다. **세션 보관 비율 (%)**은 `0`부터 `100`까지이며, 기본값은
`100`으로 모든 세션을 보관합니다.

세션은 통째로 보관하거나 제외합니다. 서버는 세션 ID의 해시를 기준으로 결정하므로 모든 노드에서 해당 세션의 모든 이벤트와 리플레이
세그먼트에 동일한 결정을 적용합니다. 세션을 보관하면 관련 데이터도 모두 보관합니다. 제외된 세션은
오류를 제외하고는 이벤트, `rum_sessions` 행, 리플레이를 남기지 않습니다(
[모든 오류 보존](#모든-오류-보존) 참조).

보관 비율은 SDK가 보고한 세션을 기준으로 합니다. SDK에서 `sessionSampleRate: 50`을 설정하고 **세션 보관 비율**을 `20`으로 설정하면
전체 세션의 약 10%를 저장합니다. `0`으로 설정하면 아무 세션도 저장하지 않으므로 SDK 설정을 변경하지 않고
애플리케이션의 세션 저장을 일시 중지할 때 유용합니다. [수집 엔드포인트](/ko/rum/events#응답) 응답은 제외한 이벤트 수를 `sampled`로 표시하며,
SDK는 이 응답을 읽고 데이터 유실이 아님을 확인할 수 있습니다. 보관하지 않는 세션의 리플레이 세그먼트에 대해서는 `sampled: true`와 함께 `200`을 반환합니다.

변경 사항은 변경 후 도착하는 이벤트부터 적용합니다. 이미 저장한 세션은 그대로 유지하며, 변경 전에 시작한 세션에는
그 시점부터 새 비율을 적용해 보관 여부를 결정합니다.

애플리케이션 필터에 `session.type`을 지정하지 않으면 [테스트에서 생성한 세션](/ko/rum/test-traffic)은 통째로 보관합니다. 실제 사용자용 보관 비율 때문에 모니터링 검사에서 생성한 세션을 제외하지 않습니다.

### 필터

필터를 사용하면 조건에 맞는 세션에 별도의 보관 비율을 적용할 수 있습니다. 예를 들어 프로덕션 세션은 모두 보관하고 나머지는 10분의 1만 보관할 수 있습니다.
**세션 보관**에서 필터를 추가합니다. 필터에는 이름, `0`부터 `100`까지의 비율, 최대 5개의 조건을 지정합니다. 세션은
모든 조건을 충족해야 합니다. 조건이 없는 필터는 모든 세션과 일치합니다.

조건은 세션의 한 속성을 값 목록과 비교합니다. **일치**는 목록의 값 중 하나와 일치하는 경우를, **같지 않음**은 어떤 값과도
일치하지 않는 경우를 뜻합니다. 속성 값이 없는 세션은 목록의 어떤 값과도 일치하지 않습니다. 값은 대소문자를 구분하지 않으며, `*`는 임의의 문자열을 나타냅니다.
예를 들어 `2.*`는 모든 2.x 버전과 일치합니다. 조건 하나에 값을 최대 20개 지정할 수 있으며, 애플리케이션 하나에 필터를 최대 10개 추가할 수 있습니다.

| 속성 | 필드 |
|---|---|
| 환경 | `env` |
| 서비스 | `service` |
| 버전 | `version` |
| SDK 플랫폼 | `source` |
| 세션 유형 | `session.type` |
| 국가 | `geo.country_iso_code` |
| 브라우저 | `browser.name` |
| 운영 체제 | `os.name` |
| 기기 유형 | `device.type` |

목록 순서대로 필터를 평가하며 **세션과 처음 일치하는 필터가 보관 비율을 결정합니다**. 따라서 적용 범위가
좁은 필터를 넓은 필터보다 위에 배치합니다. 어떤 필터와도 일치하지 않는 세션에는 필터 아래의 **기타
세션 보관 비율 (%)**을 적용합니다. 필터가 없으면 이 비율을 애플리케이션의 모든 세션에 적용합니다.

<Note>
  같은 세션의 모든 이벤트에 동일한 보관 결정을 적용해야 하므로, 조건에는 세션이 지속되는 동안 변하지 않는 속성만 사용할 수 있습니다.
  세션 중에 수행한 작업이나 SDK가 세션 도중에야 확인한 사용자 식별 정보(예: 로그인 후 설정한 사용자 ID)는
  세션 보관 여부를 결정하는 데 사용할 수 없습니다. 오류 보관은 아래의 별도 설정으로 제어합니다.
</Note>

리플레이 세그먼트의 보관 여부는 세그먼트에 포함된 세션 정보로 결정합니다. 브라우저와 접속 위치, 그리고 브라우저 및 Flutter SDK가 요청 본문에 보내는 `env`, `service`,
`version`을 사용합니다(SDK는 설정하지 않은 `env` 또는 `version`을 생략합니다).
세그먼트에 속성 값이 없으면, 해당 세션과 일치할 수 있는 필터 중 하나라도 보관으로 판단할 때 세그먼트를 보관합니다.

### 모든 오류 보존

**모든 오류 보존**을 끄지 않는 한, 보관하지 않은 세션의 오류도 저장합니다. 따라서 드물게 발생하는 오류를
세션과 함께 잃지 않고, 다른 오류와 마찬가지로 이슈로 집계합니다. 이런 오류는 `rum_errors`에만 행을 남깁니다. 해당
세션의 행, 뷰, 리플레이는 없으므로 이슈 페이지는 세션 링크 대신 *세션을 보관하지 않음*을 표시합니다.

### 집계값은 추정치입니다

각 행의 `retention.rate`에는 같은 유형의 행에 적용한 보관 비율을 기록합니다(25% 필터로 보관한 세션이면 `25`). 보관 근거는
`retention.filter`에 기록합니다. 값은 필터 ID, 기타 세션 보관 비율을 뜻하는 `default`, 또는 보관하지 않은
세션의 오류를 뜻하는 `errors`입니다. **모든 오류 보존**을 켜면 모든 오류를 보존하므로, 어떤 세션에서 발생했든 오류의 `retention.rate`는 `100`입니다.

집계값을 표시하는 페이지는 보관 비율에 따라 각 행에 가중치를 부여합니다. 예를 들어 25% 비율로 보관한 세션 하나를 네 개로 계산합니다.
페이지에는 **추정치**와 세션 보관 비율이 표시됩니다. 집계값은 모든 세션을 보관했을 때의 값을 추정한 결과입니다.

- 건수, 합계, 평균을 보정하고 백분위수에도 같은 보관 비율을 기준으로 가중치를 적용합니다.
- 관측한 사용자 수와 최솟값, 최댓값은 보정하지 않고 관측값을 그대로 사용합니다.
- 퍼널과 경로에서는 보관 비율에 따라 세션을 집계합니다. 리텐션 코호트는 사용자 기준이므로 관측한 사용자 수를 그대로 집계합니다.
- 탐색기는 실제로 보관한 행을 나열하며, 건수와 차트에도 보정하지 않은 데이터를 사용합니다. 같은 수치를 얻으려면 `estimate=false`를
  [집계 API](/ko/api/rum#행-집계)에 전달합니다.
- **최소 샘플 수**를 사용하는 알림 규칙은 추정 건수가 아니라 실제로 저장한 행 수가 기준에 도달할 때까지 기다립니다.

샘플링에는 오차가 따릅니다. 소수의 세션으로 계산한 집계값은 아무리 보정해도 신뢰도가 낮습니다.

## 초기값 선택

| 트래픽 유형 | 세션 샘플링 비율 | 샘플링된 세션의 리플레이 비율 |
|---|---:|---:|
| 개발 또는 통제된 QA 환경 | `100` | `100` |
| 트래픽이 적은 프로덕션 환경 | `100` | `10`–`25` |
| 트래픽이 많은 프로덕션 환경 | `10`–`50` | `1`–`10` |

이 값은 초기 설정을 위한 참고값이며, 모든 환경에 적용하는 기본값은 아닙니다. 배포 전에 이벤트 수, 오브젝트 스토리지 용량, 보존 기간,
그리고 브라우저 및 릴리스별로 필요한 세션 수를 추정합니다.

## 세션 경계

SDK는 샘플링 결정을 애플리케이션의 탭이 공유하는 세션 쿠키 `_msrum_s_<applicationId>`에 저장합니다.
다음 두 시간 제한 중 하나에 도달하면 새 세션이 시작됩니다.

- `sessionInactivityTimeout`: 기본값 15분
- `maxSessionDuration`: 기본값 4시간

두 값 모두 밀리초 단위로 지정합니다. 허용 범위는 1분부터 24시간까지입니다.

```ts
sessionInactivityTimeout: 15 * 60_000,
maxSessionDuration: 2 * 60 * 60_000,
```

샘플링 옵션을 변경해도 현재 세션에 이미 저장된 결정은 바뀌지 않습니다. 새 구성을 테스트할 때는
`stopSession()`을 호출하거나 `_msrum_s_<applicationId>` 쿠키를 삭제합니다.

## 클라이언트 측 데이터 양 제한

전송 설정을 사용해 메모리 사용량과 요청 크기를 예측 가능한 수준으로 유지합니다.

```ts
flushInterval: 5_000,
batchSize: 50,
replayFlushInterval: 10_000,
replayBatchSize: 100,
maxQueueSize: 1_000,
```

설정을 변경할 때마다 수집률, 리플레이 저장 용량, 브라우저 부하, 조사에 활용할 수 있는 데이터 범위를
모니터링합니다. 샘플링 변경 사항을 애플리케이션과 릴리스별로 점진적으로 적용합니다.
