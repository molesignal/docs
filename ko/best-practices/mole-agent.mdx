Mole Agent는 첫 채팅부터 도움을 주지만, 신뢰를 쌓으려면 액세스 범위를 파악하고
답변이 정확한지 확인해야 합니다. 단계적으로 도입합니다. 먼저 데이터와 작업 범위를 제한하고 환경에 관한 지식을
제공한 다음, 반복 업무를 맡기고 사용량이 늘어남에 따라 비용과 품질을 모니터링합니다.

## 모델에 전달할 데이터 결정

Mole Agent는 도구 실행 결과를 포함한 대화 내용을 모델 공급자에게 전송합니다. 첫 채팅을 시작하기 전에
데이터 보호 담당자와 다음 제어 항목을 결정합니다.

| 제어 항목 | 설정 위치 | 권장 사항 |
|---|---|---|
| 모델 공급자 | **Mole Agent → 설정 → 모델 및 추론** | 데이터 정책에서 허용하는 공급자를 사용합니다. 사내 네트워크에 호스팅한 모델도 OpenAI 호환 엔드포인트로 연결할 수 있습니다. |
| 데이터 범위 | **Mole Agent → 설정 → 데이터 액세스** | 조사에 필요한 환경, 서비스, 스트림만 허용합니다. |
| 네트워크 액세스 | **Mole Agent → 설정 → 네트워크 정책** | 도구에 네트워크 액세스가 필요하지 않다면 새 프로필의 기본값대로 꺼 둡니다. |
| 개인정보 | [필드 마스킹](/ko/settings/data-security#필드-마스킹) 및 [정규식 패턴](/ko/settings/data-security#정규식-패턴) | 필드 마스킹은 일반 사용자 쿼리와 Mole Agent 쿼리에 동일하게 적용됩니다. **수집 시 마스킹**은 저장 전에 텍스트를 제거합니다. |

사용량에 비용이 표시되도록 공급자별 요금도 입력합니다.

## 먼저 제안하고 나중에 변경

Mole Agent가 어떤 제안을 하는지 파악하는 동안에는 권장 설정인 **제안 모드**로 채팅을 유지합니다.
이 모드에서는 데이터를 조회하고 변경을 제안하되 실제로 변경하지 않습니다. 제안이 타당하다고 확인되면
**승인 후 실행**으로 전환합니다. 이후에는 도구의 실행 모드에 따라 변경 전에 확인을 요청하거나 승인 절차로 보냅니다.
[실행 모드](/ko/agent#실행-모드)를 참조합니다.

- 공유 에이전트 프로필의 **승인 정책**에서 **권한 우회 허용**을 꺼 둡니다.
- L0 자동 실행부터 L4 비활성화까지 위험도별 기본 정책을 유지합니다.
  **도구 및 기능**의 **도구 정책 설정**에서 **프로덕션**에 다른 환경보다 엄격한 정책을 적용합니다. 예를 들어
  L1 변경에는 승인 한 건을 요구합니다.
- 승인에는 `agent.approve` 권한이 필요하며, Owner와 Admin 역할에 이 권한이 있습니다. 해당 변경을
  직접 수행할 담당자에게 사용자 지정 역할을 통해 이 권한을 부여합니다.
- MCP 서버의 새 도구는 활성화하기 전까지 꺼져 있습니다. 먼저
  **모든 읽기 전용 도구 활성화**로 읽기 전용 도구를 켭니다. 스킬과 MCP 도구는 정책의 허용 범위를 넓히지 않습니다.

## 환경에 관한 지식 제공

답변의 품질은 Mole Agent가 서비스에 대해 얼마나 알고 있는지에 달려 있습니다.

- `MOLE.md`에 조직의 지식을 작성하거나 `/init`을 실행해 작성합니다. 서비스와
  담당자, 환경, 주요 스트림과 대시보드, 런북 위치를 기록합니다.
  내용이 긴 파일은 `runbooks/checkout.md`와 같이 `@path`를 사용해 참조합니다.
  [지식 및 메모리](/ko/agent#지식-및-메모리)를 참조합니다.
- 팀마다 자체 지식을 관리하고 팀 채팅에서 이를 참조하도록 합니다. 인시던트는 팀 채팅에서 처리해
  온콜 담당자가 같은 조사 내용을 읽고 이어서 작업할 수 있게 합니다.
- **채팅 후 기억할 내용 추리기**를 켜서 채팅에서 얻은 지식을 보존합니다.
  주기적으로 **메모리**를 검토하고 잘못된 내용을 삭제합니다.
- 반복 절차를 [스킬](/ko/agent#스킬)로 만들어
  [스킬 리포지토리](/ko/agent#스킬-리포지토리)에 보관하고 **매일 동기화**를 켭니다. 이렇게 하면
  절차 변경 사항을 코드 변경처럼 검토할 수 있습니다.

## 반복 업무 맡기기

[자동화](/ko/automations)를 사용하면 채팅에 참여자가 없어도 Mole Agent가 작업할 수 있습니다. 다음 템플릿부터 사용합니다.

| 템플릿 | 용도 |
|---|---|
| **인시던트 분석** | 오류 및 심각 인시던트의 추정 근본 원인과 근거를 근본 원인 분석(RCA)으로 작성해 초기 대응자가 이를 바탕으로 조사를 시작할 수 있게 합니다. |
| **일일 상태 점검** | 평일 아침마다 확인이 필요한 항목을 알립니다. |
| **주간 알림 노이즈 검토** | 조정이 필요한 규칙을 나열합니다. [프로덕션 알림을 대응 가능하게 만들기](/ko/best-practices/actionable-alerts)를 참조합니다. |
| **주간 온콜 업무량** | 담당자별 호출 건수와 야간 호출 건수를 집계합니다. [온콜 및 알림 설정](/ko/best-practices/on-call-setup)을 참조합니다. |
| **변경 영향 점검** | 배포 후 CI에서 호출하면 실행합니다. [릴리스 검증](/ko/best-practices/release-verification)을 참조합니다. |

자동화는 마지막으로 저장한 사용자의 권한으로 실행됩니다. 해당 사용자가 조직을 떠나면
다른 사용자가 다시 저장할 때까지 실행이 실패하므로 공유 자동화마다 담당자를 기록합니다.

자동화 실행 중에는 확인 요청에 응답할 수 없습니다. 확인이 필요한 도구는 실행하지 않으며, 실행 상태는
**사용자 조치 필요**로 표시됩니다. 자동화는 조회와 보고에 사용하고, 변경은 채팅에서 진행합니다.

## 비용 모니터링

- **Mole Agent → 설정 → 사용량**에서 일일 예산을 설정합니다. 인스턴스 기본값인
  `[agent].daily_token_budget`을 사용하거나 **사용자 지정** 한도를 설정합니다. 최근 30일간의
  소스별 사용량을 바탕으로 인시던트가 몰릴 때를 대비해 여유를 둡니다. 예산을 모두 사용하면 자동 근본 원인 분석은
  다음 날까지 대기하고, 로그 점검은 실패하며, LLM 함수가 포함된 단계도 실패합니다.
- 기본값인 **모델 호출 중단**을 유지합니다. 예산을 초과한 뒤에도 채팅에서
  계속 응답해야 하는 경우에만 **경고만 표시하고 응답**을 선택합니다.
- 세부 정보는 **로그**에서 내부 스트림 `_agent_model_traces`를 쿼리해 확인합니다. 호출별 토큰 수, 지연 시간, 비용을
  `origin`, `model`, `user_id`별로 확인할 수 있습니다. [사용량 및 예산](/ko/agent#사용량-및-예산)을 참조합니다.

## 품질 측정 및 개선

- 사용자에게 답변을 평가하도록 요청합니다. **도움이 되지 않음** 평가와 함께 남긴 사유를 보면 개선할 항목을 파악할 수 있습니다.
- 팀 채팅과 RCA의 표본을 채점하는 [평가 도구](/ko/quality#평가기)를 추가하고,
  매주 **품질** 탭에서 점수가 낮은 항목을 검토합니다.
- `/insight`를 주간 자동화로 실행합니다. 작성할 지식 파일 등 적용할 만한 변경 사항을
  최대 5개 제안합니다.
- 프롬프트 검사를 **검사 후 점수가 낮아지면 지정 차단**으로 설정해 새 조직 프롬프트가
  답변 품질을 떨어뜨리지 않도록 합니다. [기본값으로 지정하기 전에 프롬프트 검사](/ko/quality#프롬프트를-기본값으로-설정하기-전에-검증하기)를 참조합니다.

## 완료 기준

- 데이터 정책에서 모델 공급자를 허용하고 공급자 요금을 설정했습니다.
- 기본 프로필은 네트워크에 액세스하지 않으며 필요한 환경, 서비스, 스트림만 읽습니다.
- 어떤 공유 프로필도 **권한 확인 건너뛰기**를 허용하지 않으며, **프로덕션**의 도구 정책을 별도로 설정했습니다.
- `MOLE.md`에 서비스, 담당자, 런북을 기록했으며 각 온콜 팀은 자체
  지식을 관리합니다.
- **인시던트 분석** 자동화가 오류 및 심각 인시던트의 RCA를 작성합니다.
- 일일 예산에는 자동 분석을 위한 여유가 있으며, 담당자가 매주 **품질** 탭을 검토합니다.
