고객에게 중요한 것은 어느 서비스에서 장애가 발생했는지가 아니라 결제가 되느냐입니다. 가장 중요한 여정 몇 가지를 고르고
각 여정을 세 가지 관점에서 모니터링합니다. 외부에서 여정을 실행하는 신테틱 검사,
여정을 실제로 이용하는 사용자, 여정을 처리하는 백엔드입니다.

| 관점 | 도구 | 감지하는 항목 | 놓치는 항목 |
|---|---|---|---|
| 외부 | [신테틱 검사](/ko/synthetics) | 트래픽이 없어도 시간대와 관계없이 발생하는 중단, 인증서 만료, DNS 장애를 감지합니다. | 일부 사용자나 기기, 특정 데이터에서만 발생하는 문제는 놓칩니다. |
| 실제 사용자 | [RUM](/ko/rum) | 느린 페이지, 프런트엔드 오류, 사용자 불편과 실제 사용자 행동을 파악합니다. | 여정을 이용하는 사용자가 없으면 데이터를 수집하지 못합니다. |
| 백엔드 | [APM SLO](/ko/apm#서비스-수준-목표) | 여정을 처리하는 엔드포인트의 오류와 지연 시간을 오류 예산과 함께 추적합니다. | 요청이 백엔드에 도달하기 전에 발생하는 장애는 놓칩니다. |

## 여정 이름과 성공 기준 정하기

여정을 단계별로 작성합니다. 예를 들어 상품 페이지 열기, 장바구니에 추가하기, 결제하기, 결제 확인 화면 보기로 나눕니다.
각 단계의 페이지나 엔드포인트를 지정하고 성공 기준을 정합니다. 상태, 콘텐츠,
그리고 "3초 이내에 결제 확인"과 같은 시간 제한을 명시합니다.

모든 도구에서 이름을 일관되게 유지합니다. RUM에서는 같은 뷰 이름을, APM에서는 같은 라우트 템플릿을 사용하고,
신테틱 검사에는 여정 이름을 사용합니다.

## 외부에서 검사하기

1. 중요한 API 단계마다 **HTTP / API** 검사를 만들고, 전체 여정에는
   **브라우저** 검사를 만듭니다. [검사 만들기 및 게시하기](/ko/synthetics#점검-생성-및-게시)를 참조합니다.
2. 성공 조건을 검증하도록 상태와 확인 문구에는 **심각** 어설션을,
   시간 제한에는 **경고** 어설션을 설정합니다.
3. 네트워크 경로 하나의 문제를 서비스 중단으로 판단하지 않도록 두 곳 이상의 위치에서 검사를 실행하고,
   실패와 복구 상태가 반복해서 바뀌지 않도록 실패 및 복구 임계값을 설정합니다.
4. **리비전 테스트**를 실행한 다음 **수정본 게시**를 선택합니다. 검사 내용을 수정하면 새 초안이 생기므로
   새 수정본의 검증을 마칠 때까지 기존에 게시한 검사가 계속 실행됩니다.

브라우저 검사는 최대 1분에 한 번 실행되며, API 검사는 더 자주 실행할 수 있습니다. 테스트 계정과 테스트
결제 수단을 사용하고, 실제 고객 데이터는 절대 사용하지 않습니다.

## 실제 사용자 모니터링하기

애플리케이션에 [브라우저 RUM SDK](/ko/rum/browser-sdk)를 적용한 후 다음을 수행합니다.

- [성능](/ko/rum/performance)에서 LCP, INP, CLS의 75번째 백분위수 값을
  여정에 포함된 페이지별로 추적합니다.
- [사용자 불편](/ko/rum/frustration)에서 분노 클릭, 무반응 클릭, 오류 클릭이 발생하는지
  여정 단계별로 확인합니다.
- [오류](/ko/rum/errors)에서 여정의 이슈를 담당 팀에 할당합니다.
- 실패한 여정의 [세션 리플레이](/ko/rum/session-replay)를 열어 사용자가 본 화면을 확인합니다.
  [개인정보 보호 설정](/ko/rum/privacy)으로 개인정보를 마스킹합니다.

많은 사용자가 여정을 완료하는 데 문제가 있음을 보여 주는 지표를 기준으로 [RUM 알림](/ko/rum/alerts)을 만듭니다.
예를 들어 오류율이나 핵심 페이지의 웹 바이탈을 사용합니다.

## SLO로 백엔드 추적하기

결제 엔드포인트처럼 중요한 단계를 처리하는 엔드포인트에
[SLO](/ko/apm#서비스-수준-목표)를 만듭니다. **임계값 이내에 성공**을 선택하고 지연 시간 임계값을
여정의 시간 제한과 일치시킵니다. [오류 예산 소진율 알림](/ko/apm#소진율-알림)을 추가합니다. 빠른 소진은
온콜 담당자에게 호출을 보내고, 느린 소진은 경고를 보냅니다.

## 고객에게 알리기

여정에 대해 "결제"와 같은 [상태 페이지](/ko/status-pages) 구성 요소를 만듭니다.
[게시 자동화](/ko/status-pages#게시-자동화)를 사용해 이 구성 요소를 여정의 신테틱 검사 및 알림
규칙에 연결합니다. 처음에는 **수동 승인**을 사용합니다. 장애가 확인되면 업데이트 초안이 생성되고,
대응 담당자가 승인합니다.

## 매주 검토하기

**사본 만들기**로 애플리케이션의 기본 제공 RUM 대시보드를 복사하고, 신테틱 검사 결과와
SLO를 추가합니다. 팀에 매주 [보고서](/ko/reports)를 보내도록 예약합니다. 인시던트뿐 아니라
추세도 확인합니다. 웹 바이탈이 매주 조금씩 악화되면 다음 릴리스 한 번으로도 여정에 장애가 발생할 수 있습니다.

## 완료 기준

- 각 중요 여정에 게시된 신테틱 검사가 하나 이상 있으며, 해당 검사는 두 위치에서 실행되어 통과합니다.
- RUM이 여정의 페이지를 모니터링하며, 오류마다 담당자가 지정되어 있습니다.
- 백엔드 단계에 SLO와 오류 예산 소진율 알림이 설정되어 있습니다.
- 상태 페이지에 여정의 구성 요소가 있으며, 해당 검사 또는 규칙에 연결되어 있습니다.
- 테스트 환경에서 검사가 실패하면 온콜 담당자에게 알림이 전달되고 업데이트 초안이 생성됩니다.
