예외가 쌓이면서 액세스 권한이 늘어납니다. 추가 권한이 필요한 구성원이 생기고, 외부 계약자에게 대시보드를 열어 줘야 하고,
스크립트에 토큰을 발급해야 할 수 있습니다. 계획 없이 권한을 주다 보면 1년 뒤에는 누가 스트림을 삭제할 수 있는지, 어떤 토큰이
아직 데이터를 쓰는지 알 수 없습니다. 액세스 모델을 먼저 정하고, 예외도 그 안에서 처리합니다.

## 업무에 역할 매핑하기

수행하는 업무를 기준으로 필요한 권한만 제공하는 역할을 선택합니다.
[권한 참조](/ko/identity/roles#권한-참조)에서 각 역할에 포함된 권한을 확인합니다.

| 업무 | 역할 | 참고 |
|---|---|---|
| 대시보드, 로그, 인시던트 조회 | **뷰어** | 대부분의 구성원에게 적용하는 기본 역할입니다. 뷰어는 Mole Agent와 채팅할 수도 있습니다. |
| 대시보드, 알림 규칙, 파이프라인 구성 및 호출 대응 | **편집기** | 편집기는 인시던트의 확인 및 음소거는 할 수 있지만, 구성원이나 토큰, 설정은 변경할 수 없습니다. |
| 워크스페이스 운영: 구성원, 역할, 토큰, 설정, 신세틱 검사, 상태 페이지 관리 | **관리자** | 워크스페이스마다 소수에게만 부여합니다. |
| 인스턴스 소유 | **소유자** | 모든 소유자는 플랫폼의 `_sys` 조직에도 액세스할 수 있습니다. 두세 명으로 제한합니다. |
| 기본 제공 역할로는 충족할 수 없는 업무(예: 알림 관리 또는 신세틱 검사도 수행하는 편집기) | [사용자 지정 역할](/ko/identity/roles#역할) | 업무에 가장 가까운 **권한 정책**을 연결한 후 부족한 권한을 선택합니다. |

개별 구성원에게 역할을 부여하는 대신,
[액세스 권한 부여](/ko/identity/roles#액세스-권한-부여)를 통해 [팀](/ko/identity/teams#팀)에 역할을 부여합니다. 그러면 팀 소속에 따라
액세스 권한이 적용됩니다.

## 싱글 사인온으로 로그인 허용하기

1. 다음 메뉴에서 회사의 ID 공급자를 연결합니다.
   [ID 및 액세스 → SSO 공급자](/ko/identity/sso)에서 ID 공급자의 그룹을 역할에 매핑할 때는
   **외부 그룹 → 역할**을 사용합니다. 로그인할 때마다 디렉터리의 그룹 정보에 따라 역할이 적용됩니다.
2. 어떤 그룹에도 속하지 않은 구성원의 **기본 역할**을 **뷰어**로 설정합니다.
3. 회사의 [이메일 도메인](/ko/identity/sso#이메일-도메인)을 추가합니다. 그러면 초대와 싱글 사인온에
   해당 도메인의 주소만 사용할 수 있습니다.
4. [셀프 서비스 가입](/ko/settings/organization#가입-및-액세스)을 끄거나, 켜 둔 상태에서
   **관리자 승인 필요**를 설정합니다.

루트 사용자는 `[auth].root_email`에 지정된 플랫폼 관리자 계정이며,
비밀번호로 로그인합니다. 비밀번호는 보안 금고에 보관하고, 싱글 사인온을 사용할 수 없을 때만 이 계정을 사용합니다.

## 특정 리소스에 한시적으로 액세스 허용하기

대시보드 하나를 조회하는 외부 계약자나 스트림 하나를 쿼리하는 분석가처럼, 일시적으로 특정 리소스에만
액세스해야 하는 경우가 있습니다. 워크스페이스 전체에 역할을 부여하는 대신, 해당 리소스에 [액세스 권한 부여](/ko/identity/roles#액세스-권한-부여)를 생성하고
**만료 일시**를 설정합니다. **환경** 조건을
`staging` 등으로 지정하면 해당 환경의 요청에만 권한이 적용됩니다.

다른 조직의 구성원에게는
[조직 간 공유](/ko/identity/roles#조직-간-리소스-공유)를 사용합니다. 상대 조직의 관리자가 공유를 수락하면
선택한 대시보드나 스트림에 액세스할 수 있습니다. 공유는 지정한 리소스와 조직에만 적용되며,
받은 조직에서 다시 공유할 수 없습니다.

## 팀에 운영 책임 부여하기

팀은 단순한 구성원 그룹이 아닙니다. [온콜 일정](/ko/alerting/on-call)과 에스컬레이션 단계,
[대체 라우트](/ko/notification-channels#대체-경로-구성), 그리고 [Mole Agent](/ko/agent#조직-팀-및-개인-리소스)의 팀 채팅,
지식, 스킬, MCP 서버는 모두 팀을 참조합니다.
서비스를 담당하고 호출에 대응하는 그룹마다 팀을 하나씩 만들고, 구성원이 이동하면
팀 구성원 목록을 갱신합니다.

## 프로그램마다 별도의 ID 부여하기

| 프로그램 | 자격 증명 |
|---|---|
| 데이터만 전송하는 수집기 또는 에이전트 | 쓰기 전용 기본 수집 토큰 |
| 브라우저 또는 모바일 코드 | 최종 사용자에게 노출되는 애플리케이션의 RUM 클라이언트 토큰 |
| 배포를 보고하는 CI | 배포도 보고할 수 있는 기본 수집 토큰 |
| 데이터를 읽거나 리소스를 변경하는 자동화 | 권한 범위를 좁힌 사용자 지정 역할을 부여한 [서비스 계정](/ko/identity/tokens#서비스-계정) |
| 스크립트나 MCP 클라이언트를 실행하는 사용자 | 만료 일시를 설정한 개인 API 토큰 |

통합마다 서비스 계정을 하나씩 만듭니다. 통합 사용을 중단하면 해당 계정을 비활성화합니다. 그러면 계정의 모든 토큰을
더 이상 사용할 수 없습니다. 사용자가 생성하는 모든 토큰에 만료 일시를 설정하고, 프로그램에는 사용자의 로그인 세션을
제공하지 않습니다.

## 정기적으로 액세스 검토하기

분기마다, 그리고 구성원이 조직을 떠날 때 다음을 수행합니다.

- [사용자](/ko/identity/members#사용자)에서 조직을 떠난 구성원의 계정을 비활성화하고, **마지막 활동**을 확인해
  더 이상 사용하지 않는 계정을 찾습니다.
- [API 토큰](/ko/identity/tokens#조직-토큰)에서 최근에 사용하지 않았거나
  조직을 떠난 구성원의 토큰을 취소합니다.
- [액세스 권한 부여](/ko/identity/roles#액세스-권한-부여)에서 더 이상 필요하지 않은 권한 부여를 삭제합니다.
- [감사](/ko/settings/data-security#감사)에서 역할, 액세스 권한 부여, 토큰, 설정의 변경 사항을 확인합니다.
- [공유 정책](/ko/settings/organization#공유-및-공개-액세스)과 현재 공개 링크를
  확인합니다.

규정 준수 요건에 맞게 [감사 로그 보존 기간](/ko/settings/platform#감사-기록-보존)을 설정합니다.

## 완료 기준

- 대부분의 구성원에게 **뷰어** 역할을 부여하고, **관리자**와 **소유자** 역할은 필요성을 검토한 후 부여합니다.
- 구성원은 SSO로 로그인하며 디렉터리 그룹에 따라 역할을 받습니다.
- 모든 프로그램은 서비스 계정이나 수집 토큰을 사용하며, 사용자의 로그인 세션을 사용하지 않습니다.
- 모든 API 토큰은 정책에서 정한 유효 기간을 준수하며, 사용하지 않는 토큰은 취소합니다.
- 분기별 검토에는 날짜와 담당자를 지정하고, 검토 내역을 감사 로그에 남깁니다.
