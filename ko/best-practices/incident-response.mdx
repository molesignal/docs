인시던트가 발생하면 담당자를 정하고, 고객에게 알리고, 원인을 찾는 일을 동시에 진행해야 하므로 부담이 큽니다.
**알림**의 인시던트를 중심으로 대응합니다. 상태 페이지에서 사후 분석 보고서에 이르기까지
모든 관련 기록은 이 인시던트에 연결됩니다.

## 인시던트 담당 맡기

호출 알림에서 인시던트를 열거나 **알림 → 인시던트**의 **대기 중** 탭에서 엽니다. 확인 제한 시간 안에
**확인**을 선택합니다. 확인하면 에스컬레이션이 중단되고 인시던트에 담당자가 표시되므로
같은 작업을 중복해서 시작하는 일을 방지할 수 있습니다.

하나의 원인으로 여러 인시던트가 발생하면 해당 원인을 설명하는 인시던트를 확인 처리하고,
대응을 진행하는 동안 나머지 인시던트는 [알림을 일시 중지](/ko/alerting/silences#단일-인시던트-음소거)합니다.
[의미 기반 그룹](/ko/alerting/silences#시맨틱-그룹)으로 묶인 인시던트는
API로 한꺼번에 확인 처리할 수 있습니다.

## 영향 범위 파악하기

변경하기 전에 [인시던트 세부 정보](/ko/alerting/incidents#인시던트-상세-정보)를 확인합니다.

| 섹션 | 확인할 수 있는 내용 |
|---|---|
| **트리거 쿼리** | 어떤 값이 언제부터 임계값을 얼마나 초과했습니까? |
| **영향 범위** | 영향을 받은 서비스의 문제가 어떤 서비스와 페이지까지 파급됩니까? |
| **샘플 세션** | RUM 인시던트에서 실제 사용자는 어떤 화면을 보았습니까? 각 세션을 재생할 수 있습니다. |
| **신호 간 연결 정보** | 어떤 서비스, 호스트, 트레이스가 관련되어 있습니까? |

영향을 받은 서비스의 [SLO](/ko/apm#서비스-수준-목표)를 확인합니다. 오류 예산 소진율이 높으면
고객이 이미 영향을 받고 있다는 뜻입니다.

## 고객에게 조기에 알리기

고객이 영향을 받는 경우 원인을 파악하기 전에
[상태 페이지 인시던트](/ko/status-pages#인시던트-수명-주기)를 게시합니다.

1. 인시던트를 초안으로 생성하고 영향을 받은 구성 요소와 영향 수준을 선택합니다.
2. **조사 중** 상태로 첫 업데이트를 게시합니다. 고객에게 나타나는 증상과
   다음 업데이트 예정 시각을 알립니다.
3. **원인 파악**, **모니터링 중**, **해결됨**으로 상태가 바뀔 때마다 업데이트를 추가합니다. 이미 게시한 업데이트는
   수정하지 않고 새 업데이트만 추가합니다.

[게시 자동화](/ko/status-pages#게시-자동화)를 사용하면 알림을 바탕으로 상태 페이지 인시던트 초안을 작성하고
승인 대기 상태로 둘 수 있습니다. 이렇게 하면 몇 초 안에 첫 업데이트를 준비할 수 있습니다.

## 원인 찾기

인시던트의 시간 범위를 유지하면서 증상부터 원인까지 추적합니다.

- **트리거 쿼리 열기**는 인시던트를 발생시킨 쿼리를 다시 실행합니다. **관련 로그**와 **관련 메트릭**은
  해당 시점의 맥락을 보여 줍니다. 로그, 트레이스, 메트릭, 세션 사이를 이동하는 방법은
  [신호 간 상관관계](/ko/correlation)를 참고합니다.
- 최근 변경 사항을 확인합니다. 서비스의 [배포 타임라인](/ko/apm/deployments#배포-타임라인)과
  [APM 탐지 항목 전후](/ko/apm/insights#감지-시점-전후의-변경-사항)에 표시된 변경 사항을 살펴봅니다.
- [AI 근본 원인 분석](/ko/alerting/incidents#ai-근본-원인-분석)을 읽거나 **생성**을 선택합니다. 분석 결과를
  검증할 단서로 활용하고 **도움이 됨** 또는 **도움이 되지 않음**으로 평가합니다.
- 서비스 페이지에서 **조사**를 선택해 [Mole Agent](/ko/agent)에 질문합니다.
  서비스 상태, 인접 서비스 정보, 탐지 항목이 채팅에 첨부됩니다.

조사를 진행하면서 각 가설과 근거를 팀의 인시던트 채널에 기록합니다.
이 타임라인은 사후 분석 보고서에 필요합니다.

## 영향 완화 후 복구하기

시간에 쫓겨 문제를 수정하기보다 롤백이나 기능 플래그처럼 가장 빠르고 안전한 완화 조치를 우선합니다.
완화 조치 후에는 다음을 수행합니다.

- 트리거 쿼리 결과가 정상으로 돌아오는지 확인합니다. 미확인 인시던트는 규칙의
  복구 조건이 충족되면 자동으로 해결됩니다. 확인한 인시던트는 **해결**을 선택해야 해결됩니다.
- 이미 파악한 문제를 반복해서 알리는 관련 인시던트는
  [인시던트 하나의 알림 일시 중지](/ko/alerting/silences#단일-인시던트-음소거)로 중지합니다. 규칙 자체는 중지하지 않습니다.
- 상태 페이지의 인시던트를 **모니터링 중**으로 전환하고, 서비스가 정상 상태를 유지하면 **해결됨**으로 전환합니다.

## 인시던트에서 교훈 얻기

며칠 안에 상태 페이지 인시던트에 [사후 분석 보고서](/ko/status-pages#사후-분석)를 작성합니다. 발생한 일,
영향, 타임라인, 원인, 후속 변경 사항을 기록합니다. 검토하는 동안에는 초안으로 저장하고
인시던트가 해결되면 게시합니다. Mole Agent는 인시던트 기록을 바탕으로
보고서 초안을 작성할 수 있습니다.

그런 다음 [인사이트](/ko/alerting/incidents#인사이트)를 활용해 탐지 방식을 개선합니다. **빠른 복구**와
**인시던트를 가장 많이 생성한 규칙**은 불필요한 알림이 잦은 규칙을 찾는 데 도움이 됩니다. 호출이 늦었다면 필요한 규칙이 없거나 탐지가 느린지 확인합니다.
[프로덕션 알림을 조치 가능하게 만들기](/ko/best-practices/actionable-alerts)를 참고합니다.

## 완료 기준

- 모든 인시던트에 확인 제한 시간 안에 담당자가 지정되었습니다.
- 고객이 문의하기 전에 상태 페이지를 통해 고객에게 영향을 주는 인시던트를 알렸습니다.
- 사후 분석 보고서에 원인, 영향, 타임라인, 각 후속 조치의 담당자를 명시했습니다.
- 탐지 개선을 위한 각 후속 조치를 구체적인 규칙 변경으로 정의하고 실제 데이터로 검증했습니다.
