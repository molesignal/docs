인시던트마다 내부 사후 분석 보고서를 최대 하나까지 Markdown으로 작성합니다.
[상태 페이지의 사후 분석 보고서](/ko/status-pages#사후-분석)와는 별도로 관리하며, 상태 페이지로 요약을 복사할 수 있습니다.
상태 페이지에서 이 보고서를 사용하는 방법은 [주요 인시던트 및 사후 분석 보고서](/ko/alerting/major-incidents#사후-분석)를 참조합니다.

| 메서드 및 경로 | 기능 | 권한 |
|---|---|---|
| `GET /api/v1/alerts/postmortems` | 조직의 사후 분석 보고서를 최신순으로 조회하고 각 보고서의 후속 조치 항목 수를 반환합니다. | `postmortems.read` |
| `GET /api/v1/alerts/incidents/{id}/postmortem` | 인시던트의 사후 분석 보고서와 후속 조치 항목을 조회합니다. | 해당 인시던트에 대한 `alerts.incidents.read` 및 `postmortems.read` |
| `POST /api/v1/alerts/incidents/{id}/postmortem` | 인시던트의 사후 분석 보고서를 생성합니다. | 해당 인시던트에 대한 `alerts.incidents.read` 및 `postmortems.manage` |
| `PUT /api/v1/alerts/postmortems/{id}` | 사후 분석 보고서의 제목, 본문, 상태, 담당자 및 검토자를 변경합니다. | `postmortems.manage` |
| `POST /api/v1/alerts/postmortems/{id}/actions` | 후속 조치 항목을 추가합니다. | `postmortems.manage` |
| `PUT /api/v1/alerts/postmortems/{id}/actions/{actionId}` | 후속 조치 항목을 변경합니다. | `postmortems.manage` |
| `DELETE /api/v1/alerts/postmortems/{id}/actions/{actionId}` | 후속 조치 항목을 삭제합니다. | `postmortems.manage` |
| `POST /api/v1/alerts/postmortems/{id}/actions/{actionId}/ticket` | 후속 조치 항목의 티켓을 생성합니다. | `postmortems.manage` |

## 사후 분석 보고서 생성 및 변경

```http
POST /api/v1/alerts/incidents/{id}/postmortem
```

| 필드 | 유형 | 필수 | 참고 |
|---|---|---|---|
| `title` | string | 예 | 1~200자입니다. |
| `body` | string | 아니요 | Markdown 본문입니다. 최대 100000자까지 입력할 수 있습니다. |

인시던트에 이미 사후 분석 보고서가 있으면 `409`를 반환합니다. 화면에서는 먼저 템플릿
(요약, 영향, 타임라인, 근본 원인, 잘된 점, 잘되지 않은 점, 후속 조치 항목)을 바탕으로 본문 초안을 작성한 뒤 이 API를 호출합니다.
생성 내역은 감사 로그에 기록합니다. 변경할 때는 변경할 필드만 전송합니다. 변경할 수 있는 필드는 `title`, `body`,
`status`, `ownerId` (`null`을 보내면 담당자 지정이 해제됨), `reviewerIds`입니다.

<RequestExample>
```bash cURL
curl -X PUT http://localhost:5080/api/v1/alerts/postmortems/$POSTMORTEM_ID \
  -H "authorization: Bearer $MS_TOKEN" \
  -H "content-type: application/json" \
  -d '{"status": "in_review", "reviewerIds": ["<user-id>"]}'
```
</RequestExample>

조회, 생성, 변경 요청은 `{ "postmortem": { ... }, "actions": [ ... ] }`를 반환합니다. 인시던트에 사후 분석 보고서가 없으면 `postmortem`의 값은
`null`입니다.

<ResponseExample>
```json 200
{
  "postmortem": {
    "id": "3KJbX2p8Lr0Ws4Nf6Qa1Hd9TcVe",
    "orgId": "<organization-id>",
    "incidentId": "<incident-id>",
    "title": "Checkout errors after the payments deploy",
    "status": "in_review",
    "body": "# Checkout errors after the payments deploy\n\n## Summary\n…",
    "ownerId": "<user-id>",
    "reviewerIds": ["<user-id>"],
    "createdBy": "<user-id>",

    "updatedAt": 1790003600000000,
    "publishedAt": null
  },
  "actions": [
    {
      "id": "3KJbZ7m1Qe5Rt9Va2Xc8Lw0NdHf",

      "title": "Alert on payments pool saturation",
```

| 필드 | 참고 |
|---|---|
| `status` | `draft`, `in_review`, `published` 중 하나입니다. 처음 `published`로 변경할 때 `publishedAt`을 기록합니다. |

목록의 각 행에는 사후 분석 보고서의 필드 외에 인시던트 요약 `incidentSummary`, 아직 미완료 상태인 후속 조치 항목 수 `openActions`,
기한이 지났는데도 미완료 상태인 후속 조치 항목 수 `overdueActions`가 포함됩니다.

## 후속 조치 항목

항목을 추가할 때는 `{ "title": "…", "ownerId": "<user-id>", "dueAt": 1790600000000000 }`를 전송합니다. 제목은
1~300자이며, 보고서마다 항목을 최대 50개까지 추가할 수 있습니다. `dueAt`은 Unix 타임스탬프를 마이크로초 단위로 지정합니다. 변경할 때는
변경할 필드만 전송합니다. 변경할 수 있는 필드는 `title`, `ownerId`와 `dueAt` (각각 `null`을 보내면 값이 지워짐), `status` (`open` 또는 `done`)입니다.
추가하거나 변경하면 후속 조치 항목을 반환하고, 삭제하면 `{ "deleted": true }`를 반환합니다.

```http
POST /api/v1/alerts/postmortems/{id}/actions/{actionId}/ticket
```

요청 본문은 `{ "connectorId": "<connector-id>" }`입니다. 지정한
[티켓 커넥터](/ko/api/alerting/tickets)로 후속 조치 항목의 티켓을 생성하고, 후속 조치 항목에 `ticketKey`와
`ticketUrl`을 포함해 반환합니다. 이미 티켓이 있는 항목은 그대로 반환합니다. 인시던트의 댓글이나 상태 변경은
티켓에 반영하지 않으며, 티켓을 완료해도 인시던트가 해결되지는 않습니다.

**오류**

| 상태 | 이유 |
|---|---|
| `400` | 필드 값이 허용 범위를 벗어났거나 티켓 커넥터가 비활성화되어 있습니다. |
| `403` | 필요한 권한이 없거나 해당 인시던트에 접근할 수 없습니다. |
| `404` | 인시던트, 사후 분석 보고서, 후속 조치 항목 또는 티켓 커넥터가 존재하지 않습니다. |
| `409` | 인시던트에 이미 사후 분석 보고서가 있습니다. |
