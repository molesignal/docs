복구 작업은 Jenkins 롤백 작업 호출이나
Deployment 재시작처럼 미리 정의한 조치입니다. 인시던트에서 복구 작업을 실행하려면 [승인](/ko/agent#승인-및-실행)을 받아야 합니다.
L2에는 승인자 1명, L3에는 승인자 2명이 필요하며 요청자는 승인자가 될 수 없습니다. 조직에서
[사전 승인](#사전-승인)을 활성화하면 같은 수의 승인을 미리 받을 수 있습니다. 승인하면 작업을
즉시 실행하고, 실행 결과와 후속 확인 결과를 인시던트의
[타임라인](/ko/api/alerting/incident-timeline)에 기록합니다. 화면에서 사용하는 방법은
[복구](/ko/alerting/remediation)를 참조합니다.

| 메서드 및 경로 | 설명 | 권한 |
|---|---|---|
| `GET /api/v1/alerts/remediation/actions` | 조직의 복구 작업을 조회합니다. | `alerts.remediation.read` |
| `POST /api/v1/alerts/remediation/actions` | 복구 작업을 생성합니다. | `alerts.remediation.manage` |
| `PUT /api/v1/alerts/remediation/actions/{id}` | 복구 작업을 교체합니다. | `alerts.remediation.manage` |
| `DELETE /api/v1/alerts/remediation/actions/{id}` | 복구 작업을 삭제합니다. | `alerts.remediation.manage` |
| `GET /api/v1/alerts/remediation/clusters` | 등록된 Kubernetes 클러스터를 조회합니다. | `alerts.remediation.read` |
| `POST /api/v1/alerts/remediation/clusters` | 클러스터를 등록합니다. | `alerts.remediation.manage` |
| `PUT /api/v1/alerts/remediation/clusters/{id}` | 클러스터를 변경합니다. | `alerts.remediation.manage` |
| `DELETE /api/v1/alerts/remediation/clusters/{id}` | 클러스터를 삭제합니다. | `alerts.remediation.manage` |
| `POST /api/v1/alerts/remediation/clusters/{id}/test` | 연결을 테스트하고 `{ "ok": true, "version": "v1.30.2" }`를 반환합니다. | `alerts.remediation.manage` |
| `GET /api/v1/alerts/incidents/{id}/remediations` | 인시던트에 적용되는 복구 작업과 실행 내역을 조회합니다. | 해당 인시던트의 `alerts.incidents.read` |
| `POST /api/v1/alerts/incidents/{id}/remediations` | 인시던트의 복구 작업 실행을 요청하고 승인을 받도록 제출합니다. | 해당 인시던트의 `alerts.incidents.remediate` |
| `GET /api/v1/alerts/remediation/preapproval` | 조직의 사전 승인 활성화 여부와 사전 승인이 설정된 각 작업의 해당 기간 내 실행 횟수 및 현재 상태를 조회합니다. | `alerts.remediation.read` |
| `PUT /api/v1/alerts/remediation/preapproval` | 조직의 사전 승인을 활성화하거나 비활성화합니다. 요청 본문은 `{ "enabled": true }`입니다. | `alerts.remediation.preapprove` |
| `PUT /api/v1/alerts/remediation/actions/{id}/preapproval` | 작업의 사전 승인을 설정하거나 교체합니다. | `alerts.remediation.preapprove` 및 `agent.approve` |
| `DELETE /api/v1/alerts/remediation/actions/{id}/preapproval` | 작업의 사전 승인을 제거합니다. | `alerts.remediation.preapprove` |
| `POST /api/v1/alerts/remediation/actions/{id}/preapproval/confirm` | 두 번째 승인자가 L3 작업의 사전 승인을 확인합니다. | `alerts.remediation.preapprove` 및 `agent.approve` |

작업 생성, 변경, 삭제 및 실행 요청을 감사 로그에 기록합니다. 사전 승인 활성화 및 비활성화와 개별 사전 승인 설정, 확인 및 제거도 기록합니다.

## 복구 작업

**요청 본문**

| 필드 | 유형 | 필수 | 참고 |
|---|---|---|---|
| `name` | string | 예 | 1~120자입니다. |
| `description` | string | 아니요 | 작업 설명입니다. |
| `target` | object | 예 | 작업의 실행 방식을 지정합니다. `kind`는 `http` 또는 `kubernetes`입니다. 나머지 필드는 아래에 설명합니다. |
| `parameters` | array | 아니요 | 작업을 실행할 때 입력할 파라미터입니다. 최대 10개까지 지정할 수 있습니다. 자세한 내용은 아래를 참조합니다. |
| `services` | array | 아니요 | 작업을 적용할 서비스입니다. `teamIds`도 비어 있으면 모든 인시던트에 적용합니다. 그렇지 않으면 인시던트의 서비스 또는 팀이 설정과 일치해야 합니다. |
| `teamIds` | array | 아니요 | 작업을 적용할 팀입니다. |
| `risk` | string | 아니요 | `l2`(기본값, 승인자 1명) 또는 `l3`(승인자 2명)입니다. |
| `verifyAfterSecs` | integer | 아니요 | 작업 실행이 성공한 뒤 확인하기까지 기다리는 시간입니다. 0~86400초로 지정합니다. 기본값은 `0`이며, 확인하지 않습니다. |
| `verifyBy` | string | 아니요 | 복구 성공을 판단하는 기준입니다. `incidentResolved`(기본값, 인시던트가 해결되거나 종료됨) 또는 `rule_healthy`(인시던트의 규칙이 정상 상태로 돌아옴)입니다. |
| `enabled` | boolean | 아니요 | 기본값은 `true`입니다. 비활성화된 작업은 실행할 수 없습니다. |

**`target`: HTTP 요청**

| 필드 | 유형 | 참고 |
|---|---|---|
| `kind` | string | `http`입니다. |
| `method` | string | `GET`, `POST`(기본값), `PUT` 또는 `PATCH`입니다. |
| `url` | string | 주소 템플릿입니다. `http://` 또는 `https://`로 시작해야 합니다. |
| `headers` | object | 요청 헤더입니다. 값은 템플릿이며 암호화하여 저장합니다. |
| `body` | string | 최대 16384자의 JSON 본문 템플릿입니다. 따옴표로 감싸지 않은 자리 표시자는 숫자를 나타낼 수 있습니다. 모든 자리 표시자를 `0`으로 간주했을 때 유효한 JSON이어야 합니다. 그렇지 않으면 호출은 `400`을 반환합니다. 본문은 `application/json`으로 전송합니다. 본문을 보내지 않으려면 비워 둡니다. |
| `signingSecret` | string | 서명 시크릿입니다. 암호화하여 저장합니다. 설정하면 요청에 `X-MoleSignal-Timestamp`와 `X-MoleSignal-Sign`을 포함합니다. 두 값은 [일반 웹훅 서명](/ko/notification-channels/webhooks#헤더-및-서명)과 같은 방식으로 계산합니다. |

요청은 주소를 확인해 얻은 IP 주소에만 연결하고, 클라우드 메타데이터 주소에 대한 연결을 거부하며,
리디렉션을 따르지 않습니다. 30초 후 시간 초과로 처리하며, 2xx 응답을 성공으로 간주합니다.

**`target`: Kubernetes**

| 필드 | 유형 | 참고 |
|---|---|---|
| `kind` | string | `kubernetes`입니다. |
| `clusterId` | string | 등록된 클러스터입니다. |
| `operation` | string | `restart`(`kubectl rollout restart`와 같은 롤링 재시작), `scale`(복제본 수 변경) 또는 `rollback`(`kubectl rollout undo`와 같이 이전 버전으로 롤백)입니다. |
| `workloadKind` | string | `Deployment`, `StatefulSet` 또는 `DaemonSet`입니다. Deployment만 롤백할 수 있으며 DaemonSet은 스케일링할 수 없습니다. |
| `namespace`, `workloadName` | string | 네임스페이스와 워크로드 이름입니다. 둘 다 템플릿으로 지정할 수 있습니다. |
| `replicas` | string | 스케일링 후의 복제본 수입니다. `{{params.replicas}}`와 같은 템플릿으로 지정할 수 있습니다. |

**`parameters[]`**

| 필드 | 유형 | 참고 |
|---|---|---|
| `key` | string | 템플릿에서는 `{{params.<key>}}`로 표기합니다. |
| `label` | string | 작업을 실행할 때 표시하는 이름입니다. |
| `kind` | string | `text`(기본값), `number` 또는 `select`입니다. |
| `options` | array | `select`의 선택 항목입니다. |
| `required` | boolean | 기본값은 `false`입니다. |
| `default` | string | 값을 지정하지 않으면 사용하는 값입니다. |

**템플릿 변수**: `{{incident.id}}`, `{{incident.summary}}`, `{{incident.severity}}`,
`{{incident.status}}`, `{{incident.service}}`(`service` 레이블 또는 레이블이 없으면 영향을 받는 첫 번째 서비스),
`{{incident.url}}`(인시던트 페이지), `{{params.<key>}}`를 사용할 수 있습니다. 주소에서는 값을 퍼센트 인코딩하고,
JSON 본문에서는 값을 JSON 문자열로 이스케이프합니다. 알 수 없는 변수는 빈 문자열로 대체합니다.

<RequestExample>
```bash cURL
curl -X POST http://localhost:5080/api/v1/alerts/remediation/actions \
  -H "authorization: Bearer $MS_TOKEN" \
  -H "content-type: application/json" \
  -d '{
    "name": "Roll back checkout",
    "target": {
      "kind": "http",
      "method": "POST",
      "url": "https://jenkins.example.com/job/rollback/buildWithParameters?service={{incident.service}}",
      "headers": { "Authorization": "Bearer <jenkins-token>" },
      "body": "{\"reason\": \"{{params.reason}}\", \"incident\": \"{{incident.url}}\"}"
    },
    "parameters": [{ "key": "reason", "label": "Why", "required": true }],
    "services": ["checkout"],
    "risk": "l3",
    "verifyAfterSecs": 600,
    "verifyBy": "incident_resolved"
  }'
```
</RequestExample>

응답은 저장된 작업을 반환합니다. 헤더 값과 서명 시크릿은 반환하지 않습니다.
`headers`의 값은 비어 있으며 `secretsSet`에는 설정된 시크릿이 나열됩니다. 예를 들어
`["header:Authorization", "signing_secret"]`입니다. 작업을 변경할 때 헤더 값을 비워 두거나
`signingSecret`을 생략하면 기존 값을 유지합니다. `signingSecret`에 빈 값을 지정하면 서명을 제거합니다.

## Kubernetes 클러스터

| 필드 | 유형 | 필수 | 참고 |
|---|---|---|---|
| `name` | string | 예 | 클러스터 이름입니다. |
| `apiServer` | string | 예 | API 서버 주소입니다. `https://`로 시작해야 합니다. |
| `caCert` | string | 아니요 | PEM 형식의 CA 인증서입니다. 비워 두면 시스템이 신뢰하는 루트 인증서를 사용합니다. |
| `token` | string | 생성 시 | ServiceAccount 토큰입니다. 암호화하여 저장하며 반환하지 않습니다. 변경 시 비워 두면 기존 값을 유지합니다. |

토큰에는 대상 워크로드에 대한 `get` 및 `patch` 권한이 필요합니다. 롤백하려면 ReplicaSet 목록을 조회할 권한도 필요합니다.
API 서버 주소를 확인해 얻은 IP 주소에만 연결하고, 클라우드 메타데이터 주소에 대한 연결을 거부하며,
30초 후 시간 초과로 처리합니다. 작업에서 아직 사용하는 클러스터는 삭제할 수 없습니다.

## 사전 승인

조직에서 사전 승인을 켜면(기본적으로 꺼져 있음) 작업을 사전 승인할 수 있습니다. 목록에 포함된 서비스에서는 실행할 때마다 승인을 기다리지 않고 지정된 기간 동안 정해진 횟수까지 작업을 실행할 수 있습니다. L2 작업의 사전 승인은 설정 즉시 적용되며, L3 작업의 사전 승인은 두 번째 승인자가 `confirm`으로 확인한 후에만 적용됩니다. 사전 승인은 승인 시점만 앞당기며 필요한 승인자 수는 줄이지 않습니다. 사전 승인을 설정하거나 확인하려면 로그인해야 하며, API 토큰은 사용할 수 없습니다.

**요청 본문** (`PUT /api/v1/alerts/remediation/actions/{id}/preapproval`)

| 필드 | 유형 | 필수 | 설명 |
|---|---|---|---|
| `services` | 배열 | 예 | 사전 승인을 적용할 서비스입니다. 최대 20개까지 지정할 수 있으며, 각 서비스는 작업 범위에 속해야 합니다. |
| `maxRuns` | 정수 | 예 | 지정된 기간 내 최대 실행 횟수입니다. 1~20회로 지정합니다. |
| `windowSecs` | 정수 | 예 | 실행 횟수를 집계하는 기간의 길이입니다. 300~604800초로 지정합니다. |
| `expiresAt` | 정수 | 아니요 | 에포크부터 경과한 마이크로초로 표시한 만료 시각입니다. 생략하면 만료되지 않습니다. |
| `channels` | 배열 | 아니요 | 실행 후 알림을 보낼 대상입니다. 최대 5개까지 지정할 수 있으며, 알림 정책의 대상과 마찬가지로 `connectorId`, `targetType`, `target`을 사용합니다. |

응답은 `{ "preapproval": { ... } }`이며, 요청 본문에 `approvers` (`[{ "userId", "at" }]`), `setBy`, `setAt`을 추가합니다. 사전 승인을 설정한 사람이 첫 번째 승인자가 됩니다. 기존 사전 승인을 교체하면 새로 설정한 사람만 승인자로 남습니다. 작업의 대상, 매개변수, 서비스, 팀 또는 위험도가 변경되면 승인자 목록이 초기화되므로 사전 승인을 다시 확인해야 합니다.

`GET /api/v1/alerts/remediation/preapproval`은 `{ "enabled": true, "actions": { "<action-id>": { "used": 1, "state": "active" } } }`을 반환합니다. `state`는 `off`(조직에서 사전 승인을 끔), `expired`(만료됨), `awaiting_approver`(L3 작업에 두 번째 승인자가 필요함), `used_up`(지정된 기간의 실행 횟수를 모두 사용함), `active`(활성 상태) 중 하나입니다.

사전 승인이 적용되는 서비스의 인시던트에서 작업 실행을 요청하면, 사전 승인을 설정하고 확인한 승인자가 승인한 것으로 기록하고 즉시 실행을 시작합니다. 요청자에게는 여전히 `alerts.incidents.remediate` 권한이 필요합니다. 요청자가 부여한 사전 승인은 해당 요청의 승인 수에 포함하지 않습니다. 요청자를 제외한 사전 승인자 수가 부족하면 일반 승인 절차에 따라 대기합니다. 승인 검토 기록에는 요청자를 포함하지 않습니다. 실행 횟수를 모두 사용했거나 사전 승인이 만료되었거나 조직에서 사전 승인을 껐다면 일반 승인 절차를 따릅니다. 실행이 끝나면 성공 여부와 관계없이 `channels`에 알림을 보냅니다.

## 인시던트에서 작업 실행

```http
GET /api/v1/alerts/incidents/{id}/remediations
```

`{ "actions": [ ... ], "runs": [ ... ] }`을 반환합니다. 이 인시던트에 적용되는 활성 작업 목록(시크릿
제외)과 인시던트의 실행 내역을 포함합니다. 승인이 거부되거나 만료 또는 취소된 실행은 상태를
`declined`로 표시합니다.

```http
POST /api/v1/alerts/incidents/{id}/remediations
```

| 필드 | 유형 | 필수 | 참고 |
|---|---|---|---|
| `actionId` | 문자열 | 예 | 실행할 작업입니다. 이 인시던트에 적용되는 작업이어야 합니다. |
| `inputs` | 객체 | 아니요 | 각 매개변수의 `key`를 키로 사용하는 매개변수 값입니다. 필수 값은 반드시 입력하고, 숫자 값은 숫자 타입으로 입력하고, 선택 값은 제공된 옵션 중에서 지정해야 합니다. 정의되지 않은 항목은 입력할 수 없으며, 생략한 항목에는 기본값을 적용합니다. 각 값은 최대 500자입니다. |
| `reason` | 문자열 | 아니요 | 승인 요청에 기록할 사유입니다. 최대 2000자까지 입력할 수 있으며, 생략하면 자동으로 생성합니다. |

<RequestExample>
```bash cURL
curl -X POST http://localhost:5080/api/v1/alerts/incidents/$INCIDENT_ID/remediations \
  -H "authorization: Bearer $MS_TOKEN" \
  -H "content-type: application/json" \
  -d '{"actionId": "<action-id>", "inputs": {"reason": "pool exhausted after v2026.10.28"}}'
```
</RequestExample>

응답은 `{ "run": { ... }, "approval": { ... } }`이며, 실행과 해당 실행에 대해 제출한 승인 요청을 포함합니다.
승인 요청의 위험도는 작업의 `risk`를 따릅니다. 영향 정보에는 호출할 주소 또는
어느 클러스터의 어떤 워크로드에 무슨 작업을 수행할지 표시합니다. 승인자는
`POST /api/v1/agent/approvals/{approvalId}/review`에 본문 `{ "approve": true, "comment": "…" }`을 보내 승인하거나 거부합니다.
이 요청에는 `agent.approve` 권한이 필요합니다. 필요한 승인 수를 채우면 즉시 실행을 시작합니다. 작업에
[사전 승인](#사전-승인)이 적용되면 응답을 반환하기 전에 실행을 완료합니다. 이 경우 응답에는
`"preapproved": true`와 `execution`도 포함되며, 실행의 `preapproved`는 `true`입니다.

**오류**

| 상태 | 사유 |
|---|---|
| `400` | 필드가 올바르지 않거나, 클러스터가 이 조직에 속하지 않거나, 작업이 이 인시던트에 적용되지 않거나 비활성 상태이거나, 입력값이 올바르지 않거나, 인시던트가 이미 해결되었습니다. |

| `404` | 작업, 클러스터 또는 인시던트가 존재하지 않습니다. |
