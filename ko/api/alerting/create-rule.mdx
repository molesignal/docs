```http
POST /api/v1/alerts/rules
```

알림 규칙을 생성합니다. 이 호출에는 `alerts.rules.manage` 권한이 필요합니다.

## 규칙 평가 방식

`alert` 역할은 `real_time` 규칙을 제외한 모든 활성 규칙을 `[alert].eval_interval_secs`(기본값 30초)마다 평가합니다. `real_time` 규칙은 수집 경로에서 조건을 확인하고 레코드가 들어오는 즉시 인시던트를 엽니다. 아래 단계는 `scheduled` 및 `anomaly` 규칙에 적용합니다. `forecast`, `outlier`, `composite`, `heartbeat` 규칙의 판정 방식은 각각 [예측 규칙](#예측-규칙), [이상치 규칙](#이상치-규칙), [복합 규칙](#복합-규칙), [하트비트 규칙](#하트비트-규칙)을 참조합니다. 판정 이후의 연속 충족, 복구, 인시던트 처리는 아래와 같습니다.

1. 평가기는 `now - period_secs`부터 `now`까지의 시간 범위에서 `query.statement`를 실행합니다. `sql` 문은 SQL 엔진에서 실행합니다. `promql` 문은 PromQL 엔진에서 `now` 시점의 인스턴트 쿼리로 실행합니다. 대신 APM 규칙은 해당 시간 범위의 APM 집계에서 값을 읽고, RUM 규칙은 해당 시간 범위의 RUM 데이터에서 값을 읽습니다. [APM 규칙](#apm-규칙)과 [RUM 규칙](#rum-규칙)을 참조합니다.
2. 평가기는 첫 번째 행의 첫 번째 열을 숫자로 읽습니다. 숫자가 없는 결과는 데이터 없음으로 처리하며, `trigger.no_data`로 처리 방식을 정합니다. [복구 및 데이터 누락](#복구-및-데이터-누락)을 참조합니다. `promql` 결과는 샘플 `value`를 먼저 나열하므로 첫 번째 시계열로 판정합니다. `sum(...)` 등을 사용해 표현식을 하나의 시계열로 집계하거나 `query.group_by`로 규칙을 레이블별로 나눕니다. [열별로 나눈 규칙](#열별로-분할한-규칙)을 참조합니다.
3. 평가기는 숫자를 `trigger`의 조건과 비교합니다. `thresholds` 배열이 비어 있지 않으면 각 심각도 단계의 조건과 비교합니다.
4. `forPeriods`회 연속으로 평가 조건을 충족하면 평가기가 인시던트를 엽니다. 규칙마다 활성 인시던트는 한 번에 최대 하나이며, 열별로 나눈 규칙은 그룹마다 최대 하나입니다. `silenceSecs`가 0보다 크면 이전 인시던트를 이미 해결했더라도 해당 규칙의 이전 인시던트를 생성한 시점부터 지정한 초가 지나기 전까지 새 인시던트를 열지 않습니다.
5. 복구 조건을 충족하면 평가기가 열린 인시던트를 해결합니다. 기본적으로 조건을 처음 충족하지 않는 평가에서 해결합니다. 확인한 인시던트는 사용자가 해결할 때까지 확인 상태를 유지합니다.
6. 평가를 완료할 때마다 평가기는 평가 시각을 `lastEvalAt`에, 결과를 `lastState`에 저장합니다. 쿼리가 실패하거나 시간 초과가 발생하면 두 필드를 변경하지 않습니다.

`scheduled` 및 `anomaly` 규칙의 경우 API 호출에서 스트림이나 문의 유효성을 검사하지 않습니다. 규칙을 활성화하기 전에 [규칙 테스트](/ko/api/alerting/test-rule)를 실행합니다. `real_time` 규칙은 저장할 때 아래 제한을 충족하는지 검사합니다.

**본문**

| 필드 | 유형 | 필수 | 참고 |
|---|---|---|---|
| `name` | string | 예 | 비워 둘 수 없습니다. 이름을 인시던트 요약으로 사용합니다. |
| `description` | string | 아니요 | 기본값은 빈 값입니다. |
| `enabled` | boolean | 아니요 | 기본값은 `true`입니다. 평가기는 비활성화한 규칙을 건너뜁니다. 테스트 및 트리거 호출은 계속 작동합니다. |
| `kind` | string | 아니요 | `scheduled`(기본값), `real_time`, `anomaly`, `forecast`, `outlier`, `composite`, `heartbeat` 중 하나입니다. `real_time` 규칙은 수집 경로에서 조건을 확인합니다. [실시간 규칙](/ko/alerting/rules#실시간-규칙)을 참조합니다. |
| `query` | object | 예 | 실행할 문과 시간 범위입니다. 아래를 참조합니다. |
| `trigger` | object | 예 | 조건입니다. 아래를 참조합니다. |
| `thresholds` | array | 아니요 | `scheduled` 및 `real_time` 규칙의 심각도 단계입니다. 배열이 비어 있지 않으면 각 단계가 `trigger`의 조건을 대체합니다. `anomaly` 규칙은 심각도 단계를 무시합니다. `forecast`, `outlier`, `composite`, `heartbeat` 규칙은 하나의 심각도로만 트리거되며, 심각도 단계를 지정하면 `400`을 반환합니다. |
| `severity` | string | 아니요 | `info`, `warning`, `error`, `critical` 중 하나입니다. `thresholds`가 비어 있을 때 적용합니다. |
| `anomalyParams` | object | `anomaly`에 필요 | 기준선 설정입니다. 다른 유형은 이 설정을 무시합니다. |
| `escalationPolicyId` | string | 아니요 | 기본값 `default`는 조직에서 이름이 `default`인 에스컬레이션 정책의 별칭입니다. ID를 명시할 경우 해당 조직의 정책에 속해야 합니다. 그렇지 않으면 호출이 `400`을 반환합니다. [에스컬레이션 정책 생성](/ko/api/alerting/create-escalation)을 참조합니다. |
| `labels` | object | 아니요 | 인시던트에 복사할 문자열 맵입니다. |
| `annotations` | object | 아니요 | 인시던트에 복사할 문자열 맵입니다. 예를 들어 런북 링크를 넣을 수 있습니다. |
| `guide` | object | 아니요 | 규칙이 연 인시던트를 조사할 때 가장 먼저 수행할 작업입니다. [조사 가이드](#조사-가이드)를 참조합니다. |

**`query`**

| 필드 | 유형 | 필수 | 참고 |
|---|---|---|---|
| `language` | string | 예 | `sql` 또는 `promql`입니다. 언어에 따라 문을 평가할 엔진을 선택합니다. `periodSecs`는 쿼리의 시간 범위만 설정하므로 `promql` 문의 데이터 범위는 `[5m]`과 같은 범위 선택자로 지정합니다. |
| `statement` | string | 예 | APM 또는 RUM 규칙이 아니면 비워 둘 수 없습니다. 첫 번째 행의 첫 번째 열을 평가값으로 사용합니다. `real_time` 규칙은 `SELECT count(*) FROM <stream> [WHERE <condition>]` 형식을 사용합니다. |
| `periodSecs` | integer | 예 | 시간 범위의 길이(초)입니다. `real_time` 규칙은 1~3600을 허용하며, 해당 시간 범위에서 조건을 충족하는 레코드 수를 셉니다. |
| `stream` | object | 예(APM 또는 RUM 규칙 제외) | `{ "name": "app", "streamType": "logs" }`. 문에서 사용하는 기본 스트림입니다. |
| `apm` | object | APM 규칙에 필요 | 문 대신 규칙이 모니터링하는 APM 수치입니다. [APM 규칙](#apm-규칙)을 참조합니다. |
| `rum` | object | RUM 규칙에 필요 | 문 대신 규칙이 모니터링하는 RUM 수치입니다. [RUM 규칙](#rum-규칙)을 참조합니다. |
| `groupBy` | array | 아니요 | `scheduled` 또는 `outlier` 규칙을 나누는 기준이 되는 결과 열입니다(예: `["host"]`). 이름은 중복 없이 최대 8개를 지정할 수 있으며, 각 이름은 1~128자입니다. [열별로 나눈 규칙](#열별로-분할한-규칙)을 참조합니다. |
| `forecast` | object | `forecast` 규칙에 필요 | [예측 규칙](#예측-규칙)을 참조합니다. |
| `outlier` | object | `outlier` 규칙에 필요 | [이상치 규칙](#이상치-규칙)을 참조합니다. |
| `composite` | object | `composite` 규칙에 필요 | [복합 규칙](#복합-규칙)을 참조합니다. |
| `heartbeat` | object | `heartbeat` 규칙에 필요 | [하트비트 규칙](#하트비트-규칙)을 참조합니다. |
| `delaySecs` | integer | 아니요 | 각 평가의 시간 범위를 과거로 이동하는 초 단위 값으로, 0~3600을 지정합니다. 생략하면 자동으로 설정합니다(단일 프로세스에서는 0, 역할을 분리한 클러스터에서는 인스턴스 설정값이며 기본값은 60). [평가 지연](/ko/alerting/rules#평가-지연)을 참조합니다. |
| `homeCluster` | string | 아니요 | 페더레이션의 실시간 규칙에서 판정을 담당할 클러스터의 ID입니다. 이 클러스터는 조직에 매핑된 클러스터들의 집계 건수를 합산합니다. 현재 클러스터 또는 활성화한 원격 클러스터를 지정할 수 있습니다. 생략하면 각 클러스터가 자체 집계 건수로 판정합니다. 다른 규칙 유형은 이 필드를 제거합니다. [페더레이션의 실시간 규칙](/ko/alerting/rules#페더레이션의-실시간-규칙)을 참조합니다. |
| `discovery` | object | 검색 규칙에 필요 | 규칙의 소스는 [검색](/ko/alerting/discovery)입니다. `{"kinds": [...], "subjects": [...], "environments": [...], "minSeverity": "warning"}`의 각 필드를 생략하면 해당 필드로 필터링하지 않습니다. 저장하면 규칙에 고정된 구성을 적용합니다(발견 항목별로 그룹을 나누고 각 항목의 심각도를 사용하며 `statement`를 `discovery`로 설정). [검색](/ko/api/alerting/discovery)을 참조합니다. |

`query`는 규칙 유형에 해당하는 매개변수만 유지합니다. 예를 들어 `scheduled` 규칙에 `forecast` 객체를 지정하면 제거합니다. `composite` 및 `heartbeat` 규칙은 쿼리를 실행하지 않으므로 `statement`, `stream`, `apm`, `rum`, `groupBy`를 사용하지 않습니다. `apm`, `rum`, `groupBy`를 지정하면 `400`을 반환합니다.

첫 번째 행에 `service`, `host`, `trace_id` 열이 있으면 인시던트에 세부 정보를 추가합니다. 이 열을 사용해 `service` 및 `host` 레이블을 추가하고 `affectedServices`, `hostIds`, `traceIds`를 채웁니다.

**`trigger`**

| 필드 | 유형 | 필수 | 참고 |
|---|---|---|---|
| `operator` | string | 예 | `gt`, `gte`, `lt`, `lte`, `eq`, `neq` 중 하나입니다. `real_time` 규칙은 `gt` 또는 `gte`를 사용합니다. |
| `threshold` | number | 예 | 비교에 사용할 값입니다. |
| `forPeriods` | integer | 예 | 인시던트를 열기 전에 조건을 연속으로 충족해야 하는 평가 횟수입니다. `0`은 `1`과 동일하게 작동합니다. `real_time` 규칙은 `0` 또는 `1`을 사용합니다. |
| `silenceSecs` | integer | 예 | 인시던트를 다시 열기까지의 대기 시간(초)입니다. 인시던트가 열린 후에는 해당 인시던트를 더 일찍 해결하더라도 지정한 시간이 지날 때까지 새 인시던트를 열지 않습니다. `0`은 대기 시간을 비활성화합니다. [수동 트리거](/ko/api/alerting/trigger-rule)는 이 값을 무시합니다. |
| `recovery` | object | 아니요 | 열린 인시던트를 복구하는 조건입니다. [복구 및 데이터 누락](#복구-및-데이터-누락)을 참조합니다. |
| `noData` | object | 아니요 | 평가값이 없을 때의 처리 방식입니다. [복구 및 데이터 누락](#복구-및-데이터-누락)을 참조합니다. |
| `priority` | string | 아니요 | 인시던트를 열 때 적용할 우선순위입니다. 조직의 우선순위(기본값은 `P1`~`P5`) 중 하나를 지정합니다. 생략하면 인시던트에 우선순위를 지정하지 않습니다. |
| `urgency` | string | 아니요 | 인시던트를 열 때 적용할 긴급도입니다. 조직의 [긴급도 수준](/ko/alerting/on-call#긴급도-및-우선순위-수준) 중 하나의 키를 지정합니다. 생략하면 인시던트의 에스컬레이션 정책에 따라 결정합니다. [긴급도](/ko/alerting/on-call#긴급도)를 참조합니다. 검색 규칙의 기본값은 `low`입니다. |

`anomaly`, `outlier`, `composite`, `heartbeat` 규칙은 `operator`와 `threshold`를 무시하지만 `forPeriods`는 사용합니다. `forecast` 규칙은 `operator`를 사용해 예측값과 `threshold`를 비교합니다. `thresholds`를 사용하는 규칙은 `trigger`의 `operator`, `threshold`, `forPeriods`를 무시하지만 `trigger` 객체는 여전히 필요합니다.

**`thresholds`**

각 단계에는 `severity`(`info`, `warning`, `error`, `critical` 중 하나), `operator`, `threshold`, `forPeriods`가 있습니다. 각 단계는 조건을 연속으로 충족한 횟수를 따로 셉니다. 트리거된 단계 중 가장 높은 심각도를 인시던트에 적용합니다. 열린 인시던트의 심각도가 높아지면 첫 번째 단계부터 에스컬레이션을 다시 시작합니다.

심각도 단계가 없으면 규칙의 `severity`, `severity` 레이블, `warning` 순서로 인시던트 심각도를 결정합니다. 규칙의 `severity`와 `severity` 레이블이 모두 없는 `anomaly` 규칙은 편차가 기준선의 10배 이상이면 `critical`, 3배 이상이면 `error`를 적용합니다.

**`anomalyParams`**

| 필드 | 유형 | 필수 | 참고 |
|---|---|---|---|
| `algorithm` | string | 예 | `mad` 또는 `ewma`입니다. |
| `lookbackDays` | integer | 예 | 1~30입니다. 같은 시간대를 비교할 과거 일수입니다. |
| `k` | number | 예 | 편차에 적용할 배수입니다. 양수여야 합니다. |
| `alpha` | number | 아니요 | `ewma`의 평활 계수입니다. 0보다 크고 1 이하여야 합니다. 기본값은 `0.3`입니다. |
| `weeklySeasonality` | boolean | 아니요 | 기본값은 `false`입니다. 같은 요일만 비교하며 `lookbackDays`는 7 이상이어야 합니다. |

## 조사 가이드

`guide`는 규칙에서 발생한 인시던트를 조사할 때 먼저 수행할 작업을 안내합니다. 해당 규칙의 인시던트에 가이드가 표시되며, Mole Agent는 조사에 앞서 가이드를 읽습니다. 모든 필드는 선택 사항이며, 가이드가 없는 규칙은 `guide` 없이 반환됩니다.

| 필드 | 유형 | 참고 사항 |
|---|---|---|
| `steps` | 문자열 | Markdown으로 작성합니다. 최대 8,000자입니다. |
| `queries` | 배열 | 최대 10개입니다. 각 쿼리에는 `name`(1~120자), `language`(`sql` 또는 `promql`), `stream`(`{ "name": "app_logs", "streamType": "logs" }`, `sql`에 필수), `statement`(1~4,000자)가 있습니다. |
| `dashboards` | 배열 | 대시보드 ID입니다. 최대 5개입니다. 중복 ID는 한 번만 저장합니다. |

텍스트는 앞뒤 공백을 제거한 후 저장합니다. 가이드가 제한을 초과하거나 `sql` 쿼리에 스트림이 없으면 `400`을 반환합니다. 규칙을 업데이트할 때(`PUT /api/v1/alerts/rules/{id}`) `guide`를 생략하면 기존 가이드를 유지하고, `"guide": {}`를 지정하면 가이드를 삭제합니다.

```json
{
  "guide": {
    "steps": "1. Check which routes return the 5xx.\n2. Look for an edge proxy change in the last hour.",
    "queries": [
      {
        "name": "5xx by route",
        "language": "promql",
        "statement": "sum by (route) (rate(http_requests_total{code=~\"5..\"}[5m]))"
      },
      {
        "name": "Gateway error logs",
        "language": "sql",
        "stream": { "name": "app_logs", "streamType": "logs" },
        "statement": "SELECT * FROM app_logs WHERE level = 'ERROR'"
      }
    ],
    "dashboards": ["d2"]
  }
}
```

## 복구 및 데이터 누락

`trigger.recovery`는 값이 정상 범위로 확실히 돌아올 때까지 인시던트를 열린 상태로 유지합니다. 이 설정이 없으면 값이 임계값 근처에서 오르내릴 때 인시던트가 반복해서 발생하고 복구합니다.

| 필드 | 유형 | 참고 사항 |
|---|---|---|
| `recovery.threshold` | 숫자 | 열린 인시던트가 복구되려면 값이 정상 방향으로 이 기준을 통과해야 합니다. 예를 들어 값이 `90`을 초과할 때 발생하는 규칙에는 `80`을 지정할 수 있습니다. 복구 임계값은 모든 임계값을 기준으로 정상 범위에 있어야 합니다. 초과 시 발생하는 임계값보다 높거나 미만일 때 발생하는 임계값보다 낮아서는 안 되며, 모든 단계의 발생 방향이 같아야 합니다. `anomaly`, `forecast`, `outlier`, `composite`, `heartbeat` 규칙에는 적용하지 않습니다. 지정하지 않으면 값이 임계값 조건을 더 이상 충족하지 않을 때 인시던트가 복구됩니다. |
| `recovery.for_periods` | 정수 | 인시던트가 복구되기 전에 값이 정상 범위에 있어야 하는 연속 평가 횟수입니다. `0`과 `1`은 모두 1회로 처리합니다. 최대 1440입니다. |

`trigger.no_data`는 값이 없는 평가를 어떻게 처리할지 결정합니다. 쿼리가 행이나 숫자 값을 반환하지 않거나, [열별로 분할한 규칙](#열별로-분할한-규칙)의 그룹이 결과에서 누락된 경우가 이에 해당합니다.

| `no_data.action` | 값이 없는 평가의 동작 |
|---|---|
| `resolve` | 조건을 충족하지 않은 것으로 처리합니다. 열린 인시던트는 복구 조건에 따라 복구됩니다. `scheduled` 규칙의 기본값입니다. |
| `keep` | 상태를 유지합니다. 조건 충족 횟수를 늘리지 않고 인시던트도 복구하지 않으며, `lastState`는 `noData`가 됩니다. `anomaly` 규칙의 기본값입니다. |
| `alert` | `keep`과 동일하게 동작하지만, 값이 없는 평가가 `no_data.for_periods`회 연속되면 데이터 없음 인시던트를 엽니다. 값이 있는 첫 평가에서 인시던트를 해결합니다. |
| `zero` | 누락된 값을 `0`으로 간주해 비교합니다. 시계열이나 행이 없으면 발생 건수가 0인 카운트에 적합합니다. |

데이터 없음 인시던트는 별도의 지문을 사용하므로 임계값에 따라 열린 인시던트와 동시에 열릴 수 있습니다. 이 인시던트에는 `alert.condition` = `noData` 라벨과 규칙 또는 그룹의 요약이 포함되며, 알림 제목은 `NO DATA · <summary>`입니다. 심각도는 규칙의 `severity`, `severity` 라벨, `warning` 순으로 적용합니다. `silenceSecs`도 적용합니다. 값이 여전히 누락된 상태에서 인시던트를 수동으로 해결하면 데이터가 돌아올 때까지 다시 열지 않으며, 분할 규칙의 그룹인 경우 해당 그룹을 더 이상 추적하지 않습니다. `real_time` 규칙은 `recovery`와 `noData`를 모두 지원하지 않습니다. `composite`와 `heartbeat` 규칙은 항상 평가 결과를 내므로 `noData`를 지원하지 않습니다.

## 열별로 분할한 규칙

`query.group_by`를 지정한 `scheduled` 규칙은 결과의 각 그룹을 개별적으로 평가합니다. 지정한 열과 결과 열의 이름은 대소문자를 구분하지 않고 일치시키며, 해당 열의 값이 같은 행을 하나의 그룹으로 묶습니다. APM 또는 RUM 규칙이나 `scheduled` 및 `outlier` 이외의 규칙에 `groupBy`를 지정하면 `400`을 반환합니다. `outlier` 규칙은 임계값이 아니라 그룹 간 값을 비교하므로 반드시 분할해야 합니다. [이상치 규칙](#이상치-규칙)을 참조합니다.

1. `sql` 문은 최대 101개 행으로 제한해 실행합니다. `promql` 문은 모든 시계열을 반환합니다. 그룹마다 행을 하나씩 반환하고, 상태가 가장 나쁜 그룹부터 정렬합니다.
2. 그룹의 첫 번째 행에서 값을 가져옵니다. 지정한 열과 `_timestamp`, `ts`, `time`, `timestamp`를 제외하고 처음 나오는 숫자 열을 사용합니다.
3. 값을 `trigger` 또는 `thresholds`와 비교하고, 그룹별로 `forPeriods`를 계산합니다.
4. 발생 조건을 충족한 그룹은 자체 인시던트를 엽니다. 그룹의 값을 인시던트 라벨로 사용하고, 규칙 이름 뒤에 그룹 값을 붙여 `Errors per host · web-1`과 같은 요약을 만듭니다. `silenceSecs`는 그룹마다 개별적으로 적용합니다.
5. 그룹이 복구 조건을 충족하면 해당 그룹의 열린 인시던트를 해결합니다. 이전 결과에는 있었지만 이번 결과에 없는 그룹은 이번 평가에서 값이 없는 것으로 간주하고, `trigger.no_data`에 따라 처리합니다.
6. `lastState`는 발생 조건을 충족한 그룹이 있으면 `firing`입니다. 단, 해당 평가에서 [알림 파이프라인](/ko/pipelines/alert-events#이벤트-처리-결과)이 그룹의 인시던트를 삭제하면 `dropped`입니다. 값이 없어 상태를 유지하는 그룹이 있으면 `noData`, 조건과 일치하는 그룹이 있으면 `pending`, 그 외에는 `healthy`입니다.

한 평가에서 최대 100개 그룹을 읽습니다. 결과에 그룹이 100개를 초과하면 나머지는 평가하지 않으며, 그 평가에서 결과에 누락된 그룹은 인시던트를 그대로 유지합니다. 결과에 행은 있지만 `groupBy`에 지정한 이름의 열이 없으면 평가가 실패하고 아무것도 변경하지 않습니다. [규칙 테스트](/ko/api/alerting/test-rule)는 모든 그룹을 보고합니다.

## 예측 규칙

`forecast` 규칙은 매 평가의 쿼리 값을 시계열에 추가하고 미래 값을 예측합니다.
예측 시점 범위 내에서 예측값이 `trigger.operator`와 `trigger.threshold`로 정의한 조건을 충족하면 해당 평가를 일치로 처리합니다.
규칙을 새로 만들거나 쿼리, 평가 구간 또는 조회 기간을 변경하면 먼저 과거 시점별로 쿼리를 한 번씩 실행해
최대 48개 데이터 포인트를 채웁니다. 쿼리가 처음 실패하면 채우기를 중단하고 다음 평가부터 시계열을 이어갑니다.
시계열은 데이터 포인트를 평가 구간 하나 이상의 간격으로 최대 168개 유지합니다.
데이터 포인트가 6개 미만이면 판단하지 않습니다.

| 필드 | 유형 | 참고 사항 |
|---|---|---|
| `forecast.lookback_days` | 정수 | 예측에 사용할 과거 시계열의 일수입니다. 범위는 1~30이며, 기본값은 `7`입니다. |
| `forecast.lead_secs` | 정수 | 예측 시점 범위입니다. 지정한 초 이내에 값이 임계값을 넘어설 것으로 예측하면 규칙이 발동합니다. 범위는 900~604800(7일)이며, 기본값은 `86400`입니다. |
| `forecast.model` | 문자열 | `linear`: 이상치의 영향을 적게 받는 Theil–Sen 추세를 사용합니다. `daily`, `weekly`: 일간 또는 주간 주기가 있는 지표에 사용하며, 한 주기 전 같은 시점의 값에 추세를 더합니다. `daily`에는 하루 전체의 시계열이 필요하고, `weekly`에는 `lookbackDays`가 7 이상이고 일주일 전체의 시계열이 있어야 합니다. |

이 규칙이 여는 인시던트에는 `forecast_crossing_at`(임계값을 넘어설 것으로 예측한
시점, UTC), `forecast_value`(해당 시점의 예측값), `forecast_model` 주석이 포함됩니다. 마지막 데이터 포인트가
이미 임계값을 넘어섰다면 해당 포인트의 시점을 사용합니다. APM 및 RUM 지표도 예측할 수 있지만, RUM의 신규 이슈와
회귀 이슈는 예측 대상에서 제외합니다.

## 이상치 규칙

`outlier` 규칙은 `query.group_by`로 결과를 분할하고 그룹 간 값을 비교합니다. 그룹의
편차는 해당 그룹의 값에서 전체 그룹 값의 중앙값을 뺀 뒤 척도로 나눈 값입니다. 척도는 중앙값
절대 편차(MAD)의 1.4826배와 중앙값 절댓값의 5% 중 큰 값입니다. 이렇게 하면 그룹 값이 거의 같을 때
작은 변동을 이상치로 판단하지 않습니다. 편차가 허용 범위를 벗어난 그룹마다 별도의
인시던트를 열고 `outlier_score` 주석을 추가합니다. 값이 있는 그룹이 3개 미만이면 해당 평가에서
판단하지 않습니다.

| 필드 | 유형 | 참고 사항 |
|---|---|---|
| `outlier.tolerance` | 숫자 | 이상치로 판단하는 거리를 척도의 배수로 지정합니다. 범위는 0.5~10이며, 기본값은 `3`입니다. 값이 작을수록 민감도가 높습니다. |
| `outlier.direction` | 문자열 | `both`(기본값, 높은 값과 낮은 값 모두), `above`(높은 값만), `below`(낮은 값만) 중 하나입니다. |

## 복합 규칙

`composite` 규칙은 다른 규칙을 결합합니다. 구성 규칙에 활성 인시던트가 있는 동안 해당 규칙은 참이며, 이 참·거짓 값이
표현식에 반영됩니다. 표현식이 참이면 해당 평가 회차가 조건을 충족합니다. 쿼리는 실행하지 않습니다.

| 필드 | 유형 | 참고 |
|---|---|---|
| `composite.expression` | 문자열 | 규칙을 대문자 한 글자로 나타내고, `&&`(논리곱), `\|\|`(논리합), `!`(부정), 괄호로 결합합니다. 예: `A && (B \|\| !C)`. 최대 200자입니다. |
| `composite.rules` | 객체 | 문자를 규칙 ID에 매핑합니다. 예: `{ "A": "<rule-id>", "B": "<rule-id>" }`. 최대 10개까지 지정할 수 있습니다. 표현식의 모든 문자에 규칙을 매핑하고, 매핑한 문자는 모두 표현식에 사용해야 합니다. 같은 규칙을 중복 지정하거나 복합 규칙 자체를 지정할 수 없습니다. |
| `composite.merge_children` | 불리언 | 기본값은 `false`입니다. `true`이면 복합 규칙이 인시던트를 열 때 구성 규칙의 활성 인시던트를 해당 인시던트에 [병합](/ko/api/alerting/merge-incidents)합니다. 이후 매 평가 회차마다 새 인시던트를 병합하므로 구성 규칙의 인시던트는 별도로 알림을 보내지 않습니다. |

복합 규칙을 다른 복합 규칙의 구성 규칙으로 사용할 수 없으므로
순환 참조가 발생하지 않습니다. 삭제된 구성 규칙은 거짓으로 처리합니다. 인시던트의 주석
`composite_active`에는 참으로 평가된 문자가 기록됩니다. 복합 규칙은
[테스트](/ko/api/alerting/test-rule)할 수 없습니다.

## 하트비트 규칙

`heartbeat` 규칙은 cron 작업이나 백업 스크립트와 같은 작업의 체크인을 기다립니다. 체크인 주기에 유예 시간을 더한 시간 내에
체크인이 없거나 마지막 체크인이 실패를 보고하면 해당 평가 회차가 조건을 충족합니다.
쿼리는 실행하지 않으며, 체크인을 받으면 평가 회차의 조건 충족 여부를 즉시 판정합니다.

| 필드 | 유형 | 참고 |
|---|---|---|
| `heartbeat.period_secs` | 정수 | 작업이 체크인하는 주기입니다. 60~604800초(7일)입니다. |
| `heartbeat.grace_secs` | 정수 | 체크인 주기가 지난 뒤 체크인 누락으로 처리하기까지 추가로 기다리는 시간입니다. 0~86400초이며 기본값은 `0`입니다. |

하트비트 규칙을 새로 만들거나 다른 유형의 규칙을 하트비트 규칙으로 변경하여 처음 저장하면
응답에 `heartbeat_address`가 추가됩니다.
`{ "path": "/api/v1/intake/heartbeats/<token>", "url": "<external address>/api/v1/intake/heartbeats/<token>" }`,
외부 주소를 설정하지 않으면 `url`은 `null`입니다. 주소는 이때 한 번만 제공되며, 분실한 주소는
[재설정](/ko/api/alerting/heartbeats)만 할 수 있습니다. 인시던트에는 `heartbeat_due_at`,
`heartbeat_last_checkin_at`, `heartbeat_status` 주석과 체크인 메시지인 `heartbeat_message` 주석이 포함됩니다.
하트비트 규칙은 [테스트](/ko/api/alerting/test-rule)할 수 없습니다. 체크인 방법은
[하트비트 체크인](/ko/api/alerting/heartbeats)을 참조합니다.

## APM 규칙

`query.apm`을 사용하는 규칙은 APM 페이지와 동일한 집계 데이터를 사용해 APM 서비스 또는
해당 서비스의 엔드포인트 하나에 대한 메트릭을 모니터링합니다. APM 규칙은 `scheduled` 유형이어야 합니다. API 호출은 `query.stream`을
`null`로 저장하고, `query.statement`가 비어 있으면 다음과 같은 설명을 채웁니다.
`apm:p95 checkout POST /orders`. `query.language`는 전달된 값 그대로 저장하며 동작에는 영향을 주지 않습니다.

| 필드 | 유형 | 필수 여부 | 참고 |
|---|---|---|---|
| `service` | 문자열 | 예 | 서비스 이름입니다. 최대 255바이트입니다. |
| `namespace` | 문자열 | 아니요 | 서비스의 네임스페이스입니다. 생략하면 해당 서비스 이름이 있는 모든 네임스페이스를 대상으로 합니다. |
| `environment` | 문자열 | 아니요 | 생략하면 서비스의 모든 환경을 대상으로 합니다. |
| `transaction` | 객체 | 아니요 | 엔드포인트 하나를 지정합니다. 예: `{ "name": "POST /orders", "kind": "http" }`. `kind`는 `http`, `rpc`, `messaging`, `span`, `other` 중 하나입니다. 생략하면 서비스 전체를 대상으로 합니다. |
| `metric` | 문자열 | 예 | 모니터링할 메트릭입니다. 아래 표를 참조합니다. |
| `sloId` | 문자열 | `slo_burn_rate` 사용 시 | 소진율을 조회할 SLO입니다. 다른 메트릭에서는 `sloId`를 사용하지 않습니다. |
| `shortWindowSecs` | 정수 | 아니요 | `slo_burn_rate`에만 사용하며 `periodSecs`보다 짧아야 합니다. 지정하면 전체 기간의 소진율과 해당 기간의 마지막 `shortWindowSecs` 동안의 소진율 중 낮은 값을 사용하므로 두 소진율이 모두 임계값 조건을 충족해야 합니다. |

| `metric` | 값 |
|---|---|
| `errorRate` | 전체 요청 중 실패한 요청의 비율입니다. 0~100%로 표시합니다. |
| `p50`, `p90`, `p95`, `p99`, `average` | 밀리초 단위의 지연 시간입니다. |
| `throughput` | 평가 기간의 초당 요청 수입니다. |
| `requestCount`, `errorCount` | 평가 기간의 전체 요청 수 또는 실패한 요청 수입니다. |
| `new_error_groups` | 평가 기간에 서비스 또는 `transaction`에서 처음 발견된 오류 그룹입니다. |
| `apdex` | 임계값을 500 ms로 적용한 Apdex입니다. 범위는 0~1입니다. |
| `slo_burn_rate` | SLO가 목표에서 허용하는 속도보다 몇 배 빠르게 오류 예산을 소진하는지 나타냅니다. `1`이면 SLO 기간에 오류 예산을 정확히 모두 소진합니다. |

평가 기간이 24시간 이하면 분 단위 집계 데이터를, 24시간을 초과하면 시간 단위 집계 데이터를 사용합니다. 평가 기간에 요청이
없으면 `requestCount`, `errorCount`, `new_error_groups`, `throughput`은 `0`이고, 나머지 메트릭에는 값이
없으므로 임계값 조건을 충족하지 않습니다. 결과에는 `value`, `service`, `trace_id` 열이 포함되므로
인시던트에 `service` 레이블과 `affectedServices`의 서비스 항목, 샘플 트레이스 ID가 추가됩니다.

## RUM 규칙

`query.rum`을 사용하는 규칙은 RUM 페이지와 동일한 방식으로 계산한 RUM 애플리케이션의 지표를 모니터링합니다. RUM 규칙은 `scheduled` 또는
`anomaly` 유형이며, 한 규칙에서 APM 지표와 RUM 지표 중 하나만 지정할 수 있습니다. API는 `query.stream`을 `null`로 저장하고,
`query.statement`가 비어 있으면 `rum:lcp_p75 checkout-web /checkout`과 같은 설명으로 채웁니다. `query.language`는
요청에 포함된 값 그대로 저장하며 규칙 동작에는 영향을 주지 않습니다. 애플리케이션이 존재하지 않으면 API는 `400`을 반환합니다.

| 필드 | 유형 | 필수 | 참고 |
|---|---|---|---|
| `applicationId` | string | 예 | [RUM 애플리케이션](/ko/rum/applications)입니다. |
| `environment` | string | 아니요 | 생략하면 애플리케이션의 모든 환경을 대상으로 합니다. |
| `page` | string | 아니요 | 페이지 또는 앱 화면 하나를 지정합니다. 생략하면 모든 페이지를 대상으로 합니다. 세션 및 이슈 지표에는 지정할 수 없습니다. |
| `version` | string | 아니요 | 애플리케이션 버전 하나를 지정합니다. 생략하면 모든 버전을 대상으로 합니다. 이슈 지표에는 지정할 수 없습니다. |
| `metric` | string | 예 | 모니터링할 지표입니다. 아래 목록을 참조합니다. |
| `minSamples` | integer | 아니요 | 평가 구간에서 지표 값을 계산하는 데 필요한 최소 행 수입니다. 생략하면 지표의 기본값을 사용합니다. 개수 지표에는 지정할 수 없습니다. |
| `customName`, `statistic` | string | `custom_vital` 및 `custom_timing`에 필수 | 바이탈 또는 타이밍의 이름과 집계 방식입니다. `p50`, `p75`(기본값), `p90`, `p95`, `p99`, `avg`, `count` 중 하나를 지정합니다. |
| `search` | object | `query`에 필수 | 탐색기 쿼리입니다. `type`(`sessions`, `views`, `actions`, `errors`, `resources`, `longTasks`, `logs` 중 하나), 작성한 그대로의 `statement`, 이를 파싱한 `filters`(`field`, `op`, `value`)와 `freeText`, 그리고 `measure`를 포함합니다. `measure`에는 `fn`(`count`, `count_distinct`, `sum`, `avg`, `min`, `max` 또는 `p50`~`p99`)과 집계 대상 `field`를 지정합니다. 해당 유형에 없는 필드를 지정하면 `400`을 반환합니다. `page` 또는 `version`과 함께 사용할 수 없으며, 개수나 합계를 집계할 때는 `minSamples`를 지정할 수 없습니다. |

`metric`에는 `sessionCount`, `viewCount`, `errorCount`, `errorRate`, `crash_free_sessions`, `frustration_rate`,
`failed_request_rate`, `lcp_p75`, `inp_p75`, `cls_p75`, `ttfb_p75`, `new_issues`, `regressed_issues`, `issue_impact`,
`custom_vital`, `custom_timing`, `query` 중 하나를 지정합니다. 각 지표의 의미와 단위, 계산에 필요한 행은
[RUM 알림](/ko/rum/alerts#rum-지표)에서 확인합니다. `anomaly` 규칙은 `new_issues`와 `regressed_issues`를 제외한 모든 지표를 지원합니다.
`periodSecs`는 60초부터 6시간까지 지정할 수 있습니다.

평가 구간에 행이 없으면 개수 지표는 `0`을 반환합니다. 그 외 지표는 값을 반환하지 않으므로 임계값 조건을 충족하지 않습니다. 결과는
`value`와 `application` 열을 포함하는 한 행입니다. 인시던트가 열리면 규칙은 샘플 세션을 최대 3개까지 찾아
인시던트와 함께 저장합니다. 자세한 내용은 [RUM 알림](/ko/rum/alerts#인시던트)을 참조합니다.

**오류**

| 상태 | 원인 |
|---|---|
| `400` | `name` 또는 `query.statement`가 비어 있거나, `query.stream`이 누락되었거나, 규칙이 `query.stream` 또는 `query.statement` 내 어느 위치에서든 [`_audit` 스트림](/ko/settings/data-security#감사-스트림)을 읽으면 발생합니다. APM 규칙이 `scheduled`가 아니거나 `query.apm`이 유효하지 않은 경우(`APM alert service is invalid`, `an SLO burn-rate alert names its SLO`)에도 발생합니다. RUM 규칙이 `real_time`이거나, 존재하지 않는 애플리케이션을 지정하거나, `query.rum`이 유효하지 않은 경우(지표가 지원하지 않는 `page` 또는 `version` 지정, 개수 지표에 `minSamples` 지정, 평가 구간이 60~21,600초 범위를 벗어남)에도 발생합니다. 그 밖에 `escalationPolicyId`가 조직에 없는 정책을 가리키거나, `anomaly` 규칙의 `anomalyParams`가 누락되었거나 유효하지 않거나, `real_time` 규칙이 위 제한을 위반하면 발생합니다. 응답은 `invalid_argument` 코드와 `anomaly detector not yet supported: prophet`과 같은 메시지를 포함하는 JSON입니다. |
| `403` | 토큰에 `alerts.rules.manage` 권한이 없습니다. |
| `422` | 필수 필드가 누락되었거나 값의 유형이 올바르지 않습니다. 예를 들어 지원하지 않는 `operator`를 지정한 경우입니다. 응답은 일반 텍스트입니다. |

콘솔에서 작업하는 방법은 [알림 및 인시던트 대응](/ko/alerting)을 참조합니다.
