A stream is the organization-scoped contract used by intake, query, pipelines, and retention.
Open **Streams** to see what arrives, and to inspect or configure each stream.

## Stream types

| Type | Typical content |
|---|---|
| `logs` | Structured events and application logs. |
| `metrics` | The metric samples of one source, such as one Prometheus server, told apart by `metric_name`. |
| `traces` | OpenTelemetry spans. |
| `profiles` | Profile metadata linked to pprof blobs. |
| `extend` | Lookup data managed as extend tables and used during processing. |

The same stream name may exist for different stream types. Always include `stream_type` in API
requests and automation.

### Platform streams

MoleSignal writes these streams itself:

| Stream | Content |
|---|---|
| `_molesignal` | The telemetry of MoleSignal itself, in the `_sys` organization. See [Self-observability](/ko/self-observability). |
| `_synthetic_results` | One row for each run of a synthetic check. See [Synthetic monitoring](/ko/synthetics#결과-스트림-및-보존). |
| `_audit` | The audit events of the workspace. See [Audit stream](/ko/settings/data-security#감사-스트림). |
| `_agent_model_traces` | The model calls of Mole Agent. See [Usage and budget](/ko/agent#사용량-및-예산). |
| `_agent_score_traces` | The quality scores of Mole Agent answers. See [Quality](/ko/quality#스트림의-점수). |

They are read like other streams. `_audit` needs `audit.read`: without it, the stream is in neither
the list nor the runtime figures, and opening, changing, or deleting it answers `403`. Nothing else writes them: a stream with one of these names cannot be created, intake
into one answers `403`, and no [pipeline](/ko/pipelines#플랫폼-스트림) writes one.

## The stream list

**Streams** lists every stream of the workspace. Switch the tabs to show **All** streams or one type,
search by name or description, and filter by runtime state. The head counts the streams that receive
normally and those that need attention, and sums the compressed data written in the period and the
current storage.

| Column | Shows |
|---|---|
| **Status** | **Healthy**, **Delayed**, **Interrupted**, **Idle**, **Unused**, or **Stats unavailable**. See below. |
| **Receive rate**, **Last received** | How fast data arrives, and when it last arrived. |
| Compressed data | The compressed bytes written in the period. |
| **Current storage**, **Retention** | The bytes stored now, and how many days data is kept. |
| **Records**, **Collected size**, **Stored size**, **Index size** | The records kept, the bytes received before transformations, the bytes of data files, and the bytes of indexes. |

| State | Meaning |
|---|---|
| **Healthy** | Data arrived in the last 15 minutes. |
| **Delayed** | The last data arrived between 15 minutes and 2 hours ago. |
| **Interrupted** | No data for more than 2 hours. |
| **Idle** | The stream of Mole Agent traces, which is quiet between answers. |
| **Unused** | The stream has never received data. |

A stream marked **Not queryable** keeps receiving data but is hidden from query selectors. Each row has
**Query** or **Explore**, **View details**, and **Copy stream ID**. **Search jobs** in the head opens
the [search jobs](#검색-작업).

## Create a stream

MoleSignal creates a stream on the first write to it, so most streams appear by themselves. Create one
in advance to set its retention, its encrypted fields, or its query access from the start. Select
**Create stream**:

| Field | Rule |
|---|---|
| **Stream name** | `snake_case`, up to 64 characters. |
| **Description** | Optional. What flows through the stream. |
| **Signal type** | **Logs**, **Metrics**, or **Traces**. |
| **Retention (days)** | How long data is kept. |
| **Indexed fields** | Comma-separated fields that get a full-text index. |
| **Encrypted fields** | Comma-separated fields that are encrypted before they are stored. This cannot be changed later. See [Encrypted fields](#암호화된-필드). |
| **Queryable** | Turn it off for a source stream that only feeds a routing pipeline. |

## Stream details

Select a stream to open it. **Query data** opens it in its explorer, and the menu has
**Copy stream ID** and **Delete stream**. The tabs:

| Tab | Content |
|---|---|
| **Overview** | The runtime state, the first data received, query access, and the trend of rows written and compressed data over 24 hours. A stream without data offers **Configure datasource** and **Send test data**. |
| **Fields & indexes** | The fields with their type, index type, and encryption. Edit a field to change its index or its masking. See [Schema and fields](#스키마-및-필드). |
| **Retention** | The retention of the stream, and the downsampling of a metrics stream. See [Retention and deletion](#리텐션-및-삭제). |
| **Usage** | What depends on the stream: the intake endpoint that writes it, pipelines, saved queries, and alert rules. Check it before a change or a deletion. |
| **Settings** | The **Description**, **Queryable**, **Max query range (hours)**, **Merge small files by day**, **Split by field**, and, for logs, **Cluster by field**. |

Changes on the tabs collect into a draft. **Save and apply** applies them at once, and
**Discard changes** drops them. Before saving, the page warns about changes that cannot be taken back:
a shorter retention deletes expired data, and downsampling deletes the original samples.

**Max query range** limits how many hours one SQL or PromQL query of the stream may cover. A query over
a longer range is rejected, so a mistaken "last 90 days" cannot scan a large stream end to end. Empty
or `0` means no limit.

Set **Queryable** off when a catch-all source should keep receiving but must not appear in query
selectors. A routing pipeline can still read the stream. Manage `extend` data through
**Extend tables** rather than the generic telemetry query path.

## 스키마 및 필드

필드에는 이름, 데이터 유형, `nullable` 플래그, 인덱스 유형, `encrypted` 플래그가 있습니다. 데이터 유형은 `bool`, `int64`, `float64`, `utf8`, `timestamp`, `json`입니다. 새 필드는 수신 데이터에 처음 나타날 때 스키마에 추가되며, 다른 유형의 값은 `type mismatch on field`와 함께 거부됩니다. 숫자는 예외입니다. 소수가 있는 숫자나 `int64` 범위를 넘는 정수를 받은 `int64` 필드는 같은 배치 또는 이후 배치에서 `float64`가 되며, 이전에 저장된 값은 `float64`로 읽힙니다.

인덱스 유형은 MoleSignal이 필드에 대해 어떤 보조 구조를 만드는지 결정합니다:

| 인덱스 유형 | 효과 |
|---|---|
| `none` | 보조 인덱스가 없습니다. 기본값입니다. |
| `exact` | 전체 값의 정확히 일치 역색인(텍스트가 아닌 필드의 경우 Parquet 블룸 필터)과 각 파일의 최솟값 및 최댓값입니다. `=` 및 `IN`은 파일을 열기 전에 해당 값이 없는 파일을 건너뛰고, 일치하는 행이 적을 때는 일치하는 행의 페이지만 읽습니다. 파일당 값이 최대 65,536개인 필드에 대한 `LIKE` 또는 `ILIKE`는 어떤 값도 해당 텍스트를 포함하지 않는 파일을 건너뜁니다. `trace_id`와 같은 식별자에 사용합니다. |
| `full_text` | 텍스트 검색을 위한 토큰화된 역색인입니다. 문자와 숫자가 연속된 부분이 단어가 되고, CJK 텍스트는 겹치는 두 문자 바이그램으로 잘립니다. 문장 부호와 CJK 텍스트를 포함한 `MATCH`, `MATCH_TEXT`, `LIKE`, `ILIKE`의 리터럴은 일치할 수 없는 파일을 건너뜁니다. `utf8` 필드에만 해당합니다. |
| `bloom` | Parquet 블룸 필터와, 텍스트 및 `int64` 필드의 파일별 전체 값 필터, 각 파일의 최솟값 및 최댓값입니다. `=` 및 `IN`은 파일을 열기 전에 해당 값이 확실히 없는 파일을 건너뜁니다. 요청 ID처럼 동등 조건으로만 조회되는 값이 많은 필드에 사용합니다. |
| `skip` | 각 파일의 최솟값 및 최댓값과, 파일에 최대 32개의 서로 다른 값만 있을 때 그 파일의 모든 값입니다. 비교, `IN`, `BETWEEN`, 접두사 `LIKE`는 이를 사용해 파일을 건너뜁니다. |
| `ngram` | 각 파일 값의 트라이그램과, 파일 내 1,024개 행 블록의 5바이트 조각을 대소문자와 관계없이 저장합니다. 파일에 없는 트라이그램이 포함된 `LIKE`, `ILIKE` 또는 `MATCH` 리터럴은 해당 파일을 건너뛰고, 블록에 없는 조각이 포함된 리터럴은 해당 블록을 건너뛰므로 ID 또는 다른 희귀 문자열 검색은 이를 포함할 수 있는 몇 개의 블록만 읽습니다. 5바이트보다 짧은 리터럴은 모든 블록을 읽습니다. `ngram` 필드가 있는 스트림은 파일을 1,024개 행 단위 페이지로 씁니다. 작은 페이지와 조각은 공간을 차지합니다. 이러한 필드가 각 행의 3분의 2를 차지한 테스트에서 스토리지가 약 14% 증가했습니다. 조각으로 검색하는 URL, 경로, 호스트 이름에 사용하고, 긴 자유 텍스트에는 사용하지 않습니다. `utf8` 필드에만 해당합니다. |
| `ip` | 각 파일 주소의 범위이며, IPv4는 IPv6에 매핑됩니다. `CIDR_MATCH(field, '10.0.0.0/8')` 및 주소에 대한 `=`는 해당 주소가 없는 파일을 건너뜁니다. `utf8` 필드에만 해당합니다. |
| `key_value` | JSON 개체의 1단계 키와 그 값입니다. `json_text(field, 'key') = 'value'`, `IN`, `IS NOT NULL`은 키나 값이 없는 파일을 건너뛰고, 일치하는 행이 적을 때는 일치하는 행의 페이지만 읽습니다. 값은 `json_text`가 반환하는 대로 일치합니다. 텍스트는 그대로, 숫자와 부울은 JSON으로 표시됩니다. `json` 필드에만 해당합니다. |
| `range` | 인덱스에 있는 각 행의 숫자와 각 파일의 최솟값 및 최댓값입니다. 조건이 `exact` 필드에 대한 `=`이고, `range` 필드에 대한 숫자와의 `>`, `>=`, `<`, `<=`이며, 시간 범위인 `count(*)`는 파일을 읽지 않고 인덱스에서 응답합니다. 다른 비교는 범위를 벗어난 파일을 건너뜁니다. `int64`, `float64`, `timestamp` 필드에만 해당합니다. |

인덱싱된 모든 필드는 각 파일에 대해 해당 행 중 필드를 비워 두는 행이 몇 개인지도 기록합니다. `IS NULL`은 필드에 항상 값이 있는 파일을 건너뛰고, `IS NOT NULL` 및 `!= ''`처럼 값이 있는지 묻는 조건을 포함해 필드에 대한 다른 모든 조건은 필드에 값이 없는 파일을 건너뜁니다.

`OR`로 결합된 조건은 각 분기가 해당 파일에서 배제될 때 파일도 건너뜁니다. 각 분기는 해당 분기를 처리하는 인덱스에 따라 판단합니다. `level = 'error' OR status >= 500`은 `level` 인덱스에 `error`가 없고 `status`가 500에 도달한 적이 없는 파일을 건너뜁니다.

수신 데이터에 처음 나타나는 필드는 이름에서 인덱스 유형을 가져옵니다:

| 스트림 유형 | 필드 | 인덱스 유형 |
|---|---|---|
| `logs` | `message` | `full_text` |
| `logs` | `_event_id`, `level`, `session_id`, `fingerprint`, `country`, `browser`, `application`, `environment` | `exact` |
| `traces` | `trace_id`, `span_id`, `parent_span_id`, `service.name` | `exact` |
| `metrics` | `metric_name` | `exact` |

다른 모든 새 필드는 스트림 자체 규칙에서 달리 지정하지 않는 한 `none`을 가집니다. [새 필드의 인덱스](#새-필드의-인덱스)를 참조하세요. `level`을 `exact`로 두면 로그 히스토그램이 파일을 읽지 않고 인덱스에서 오류를 집계할 수 있습니다. RUM 스트림은 `context`, `feature_flags`, `usr.extra`의 키를 `key_value`로 인덱싱합니다.

변경된 인덱스 유형은 이후에 기록되는 데이터에 즉시 적용됩니다. 이전에 기록된 데이터는 새 설정에 따라 백그라운드에서 다시 인덱싱됩니다. 각 sealed 파티션(기본적으로 종료 후 48시간 뒤 sealed됨)은 해당 파일에서 다시 작성되고, 더 새로운 파일은 sealed되거나 병합되면 다시 작성됩니다. 그때까지 파일은 기록될 때의 인덱스를 유지하며, 이는 쿼리 결과를 바꾸지 않고 쿼리가 읽는 파일 수만 바꿉니다. **개요**의 **인덱싱된 필드 비율**은 남은 파일 수를 보여줍니다. CJK 텍스트가 바이그램으로 잘리기 시작한 때처럼 전체 텍스트 인덱스 형식이 변경되면, 이전 파일의 인덱스도 같은 방식으로 백그라운드에서 새 형식으로 다시 작성됩니다.

필드를 변경하려면 **필드 및 인덱스**를 열고 해당 필드의 편집 작업을 선택한 다음 다음을 선택합니다:

- **인덱스 유형**: **인덱싱 안 함**, **전체 텍스트 검색**, **정확히 일치**, **블룸 필터**,
  **스킵 인덱스**, **N-gram 부분 문자열**, **IP 주소**, 또는 **JSON 키**입니다. 전체 텍스트 검색, N-gram
  부분 문자열, IP 주소는 텍스트 필드에, JSON 키는 JSON 필드에 적용됩니다.
- **결과 필드 마스킹**의 **스트림 수준 정책**: **전역 규칙 상속**, **사용자 지정 스트림 규칙**,
  또는 **이 스트림에서 마스킹 제외**입니다. [필드 마스킹](/ko/settings/data-security#필드-마스킹)을 참조하세요.
  메트릭 스트림은 마스킹에 참여하지 않습니다.

**초안에 적용**을 선택한 다음 **저장 및 적용**을 선택합니다. 필드의 유형은 절대 변경되지 않습니다.

### 새 필드의 인덱스

**설정** 탭의 **필드 인덱스**에서 규칙은 스트림에 처음 나타나는 필드에
이름에 따라 인덱스를 부여합니다. **규칙 추가**를 선택하고 필드 이름 패턴을 입력한 다음 인덱스 유형을 선택합니다:
`*`는 임의의 텍스트 연속을, `?`는 한 문자를 나타내므로 `*_id`는 `user_id` 및
`order_id`와 일치하고 `http.*`는 `http` 아래의 모든 필드와 일치합니다. 순서상 패턴이
이름과 일치하고 인덱스 유형이 필드의 데이터 유형에 맞는 첫 번째 규칙이 적용됩니다. 필드에
이름으로 **필드 및 인덱스**에서 설정한 인덱스가 우선하며, 어떤 규칙과도 일치하지 않는 필드는 위의 기본값을 가집니다.
규칙은 지금부터 나타나는 필드에만 영향을 줍니다. 기존 필드는 **필드 및
인덱스**에서 변경합니다. 스트림에는 최대 32개의 규칙이 있습니다.

### 필드별 분할

로그 또는 트레이스 스트림은 하나 또는 두 개의 텍스트 필드로 분할할 수 있습니다. **설정** 탭의
**필드별 분할**에서 **필드 추가**를 선택하고 필드를 고른 다음 분할 방식을 고릅니다. 이후에 기록되는
데이터는 필드 값에 따라 샤드로 분할되며, 각 샤드는 자체 파일에 기록됩니다.

- **해시**는 값을 해시에 따라 2~64개의 샤드로 균등하게 분할합니다. 필드에 대한 동등
  조건(`=` 또는 `IN`)이 있는 쿼리는 해당 값의 샤드 파일만 읽습니다.
- **첫 문자**는 값을 첫 문자에 따라 37개의 샤드로 분할합니다. 각 숫자와
  각 문자(대소문자 무관)에 하나씩, 빈 값을 포함한 나머지 모두에 하나씩입니다. 필드에 대한 동등
  조건이 있는 쿼리 또는 텍스트로 시작하는 `LIKE`(예: `'web-%'`)는 해당 문자의
  샤드 파일만 읽습니다. `ILIKE`는 나머지 모두의 샤드도 읽습니다. 샤드가 얼마나
  균등한지는 데이터에 따라 다릅니다. 16진수 트레이스 ID는 그중 16개만 사용합니다.

두 필드를 사용하면 파일은 두 필드의 샤드로 분할되므로 샤드 수가 곱해집니다. **필드별
분할**은 최대 256인 총계를 보여줍니다. 첫 문자(37개 샤드)는 최대 4개
샤드의 해시와 함께 사용됩니다. 어느 한 필드에 조건이 있는 쿼리는 더 적은 파일을 읽고, 두 필드 모두에 조건이 있는 쿼리는
더더욱 적게 읽습니다. 서비스, 네임스페이스, 테넌트처럼 거의 모든 쿼리가 지정하는 분할 필드를 사용하세요.
샤드가 많을수록 파일은 더 많고 작아집니다.

설정은 변경 이후에 기록되는 데이터에 적용됩니다. 기존 파일은 그대로 유지되며, 쿼리는
각 파일을 기록될 때 사용한 필드로 판단하고, 컴팩터는 같은
필드로 기록된 파일만 병합합니다. 분할 필드는 암호화되지 않은 텍스트 필드여야 하며, 두 필드는 서로 달라야 합니다.

### 필드별 클러스터링

로그 스트림은 파일 내부의 행을 하나 또는 두 개의 필드로 클러스터링할 수 있습니다. **설정** 탭의
**필드별 클러스터링**에서 **필드 추가**를 선택하고 필드를 고른 다음 **시간 구간**을 고릅니다. 이후에 기록되는 각
파일에서 행은 해당 너비의 시간 구간에 최신 순으로 놓이고, 구간 내에서는
필드 값에 따라 그다음 최신 순으로 놓입니다.

시간 순서에서는 서비스와 같은 값이 파일의 모든 페이지에 나타납니다. 클러스터링하면 각 구간에서
해당 값이 몇 개의 페이지에만 있으므로, 클러스터링 필드에 대한 동등 조건(`=` 또는 `IN`)이 있는 쿼리는
해당 페이지만 읽습니다. 쿼리가 자주 지정하고 값이 적은 필드를 사용하세요. 예:
서비스 또는 레벨.

각 클러스터링된 파일은 각 분에 속하는 행 수를 클러스터링 필드 값의 각 조합과 함께 유지합니다.
텍스트 클러스터링 필드에 대한 동등 조건이 있는 count, 그중 하나로 그룹화한 count
(`GROUP BY service`), 막대가 전체 분인 히스토그램은 파일을 읽지 않고 이 숫자에서 응답합니다.
쿼리 창이 파일 내부의 전체 분에서 시작하거나 끝나는 경우에도 마찬가지입니다. 분과 값의 조합이
65,536개를 초과하는 파일은 아무것도 유지하지 않습니다.
같은 숫자는 최신 또는 가장 오래된 행의 페이지가 어디에 있는지 알려 주므로, 클러스터링 필드에 대한 동등 조건이 있든
없든 이러한 페이지는 해당 행이 나오는 분만 읽습니다.

시간 구간은 1분, 5분, 10분이며 기본값은 1분입니다. 구간이 넓을수록 더 많은 페이지를 건너뛰지만,
짧은 시간 창을 조회하는 쿼리는 쿼리가 닿는 구간은 통째로 읽습니다.

클러스터링은 [필드별 분할](#필드별-분할)과 다릅니다. 분할은 각 샤드를 자체
파일에 기록하므로 쿼리는 더 적은 파일을 읽지만 스트림에는 더 많고 작은 파일이 생깁니다. 클러스터링은 파일을 유지하고
그 안의 행 순서를 정합니다. 두 기능은 함께 사용할 수 있습니다.

설정은 변경 이후에 기록되는 데이터에 적용됩니다. 기존 파일은 기록된
순서를 유지하며, 컴팩터는 동일하게 클러스터링된 파일만 병합합니다. 클러스터링 필드는
암호화되지 않은 텍스트, `int64`, `bool` 필드여야 하며, 두 필드는 서로 달라야 합니다.

### 암호화된 필드

스트림을 생성할 때 필드를 `encrypted`로 표시하면 Parquet에 기록되기 전에 암호화됩니다. 저장된 열에는 암호문이 들어가며, 일반 쿼리는 암호문을 반환합니다. SQL에서 `decrypt(field)`로 값을 다시 읽습니다:

```sql
SELECT user, decrypt(secret) AS secret FROM app
```

플래그는 나중에 변경할 수 없습니다. 기존 데이터를 읽을 수 없게 되기 때문입니다. 키는 조직 암호 키와 암호 루트 키 `MS_CIPHER_KEY`에서 가져옵니다. 루트 키를 잃으면 암호화된 필드를 복구할 수 없습니다. [보안 및 멀티테넌시](/ko/security#필드-수준-암호화)를 참조하세요.

## 리텐션 및 삭제

리텐션은 컴팩터가 데이터를 제거하는 시점을 제어합니다. **리텐션** 탭에서
**데이터 보존 기간(일)** 로 설정하거나, 비워 두어 플랫폼 기본값인 30일을 사용할 수 있습니다. 기본값은
[설정 → 데이터 보존 기간](/ko/settings/platform#데이터-보존)에서 `_sys` 조직에 대해 설정합니다. 리텐션보다
오래된 데이터는 다음 정리 작업에서 삭제되므로, 리텐션을 줄이면 그 시점에 리텐션을 넘긴 데이터가 삭제되며, 삭제된 파일은
되돌아오지 않습니다. 리텐션 기간 내에 수신되지 않은 메트릭 스트림의 메트릭도 메트릭 목록에서
제외됩니다.

메트릭 스트림의 **리텐션** 탭에서 **오래된 샘플 다운샘플링**은 스트림에 있는 모든 메트릭의 샘플 중
지정한 일수보다 오래된 것을 1분에서 1일까지의 시간 버킷으로 롤업합니다. 하나의 버킷에 속한 시리즈의 샘플은
하나의 포인트가 되고, 값은 평균을 내고 델타 카운트는 합산되며, 원본 샘플은 삭제됩니다.
그러면 긴 범위에 대한 쿼리가 훨씬 적게 읽고, 오래된 데이터는 버킷 해상도만 유지합니다.
원본 샘플은 복구할 수 없습니다.

로그와 트레이스의 경우, 스트림 설정 **작은 파일을 일별로 병합**(기본적으로 켜짐)은 종료된 하루의 파일들을
하루가 끝나고 한 시간 뒤에, 합친 크기가 컴팩터의 `[compactor].target_size`보다 크지 않으면 하나로 병합합니다.
그러면 여러 날에 걸친 쿼리가 훨씬 적은 파일을 엽니다. 리텐션은 그다음에는 일 단위로 적용됩니다.
병합된 파일은 해당 하루 전체가 만료되면 삭제됩니다. 시간별 파일을 유지하려면 스트림의 **설정** 탭에서
이 설정을 끄십시오.

**스트림 삭제**는 스트림과 그 구성을 삭제하며 되돌릴 수 없습니다. 대시보드, 저장된 뷰, 알림, 보고서,
파이프라인을 깨뜨릴 수 있으니 먼저 **사용량** 탭을 확인하십시오.

## 검색 작업

검색 작업은 백그라운드에서 실행되고 작업이 만료될 때까지 결과를 보관하는 쿼리입니다.
작업은 세 가지 경로로 생성됩니다.

- `Prefer: respond-async`로 보낸 쿼리, 또는 결과가 대화형 요청에 담기에는 너무 클 것으로 예상되는
  쿼리;
- 파이프라인의 백필;
- Mole Agent가 제출한 쿼리.

**스트림** 헤더에서 **검색 작업**을 선택하면 목록이 열립니다. 목록 상단의 뷰는 상태별로 필터링하며
각 뷰에 개수가 표시됩니다: **전체**, **대기 중**, **실행 중**, **완료**, **실패**,
**취소됨**. 작업이 대기 중이거나 실행 중이면 목록이 자동으로 새로 고쳐집니다.

각 행에는 작업 유형(**쿼리** 또는 **백필**), 구문, 상태, 쿼리 범위, 제출 시각, 소요 시간, 결과 행,
시도 횟수, 만료 시각이 표시됩니다. 작업 상태에 따라
사용할 수 있는 작업은 하나입니다:

| 상태 | 작업 |
|---|---|
| 대기 중 또는 실행 중 | **작업 취소** |
| 완료 | **결과 다운로드** |
| 실패 또는 취소됨 | **다시 시도** |

**삭제**는 상태와 관계없이 작업과 그 결과를 제거합니다.

멤버는 자신이 제출한 작업을 보고 관리합니다. `org.running_queries.cancel` 권한이 있는 관리자는
조직의 모든 작업을 보고 관리합니다. 작업 API는
[쿼리](/ko/query#시간-범위-및-비동기-작업)를 참조하십시오.

## 데이터 수집 사용량 및 예산

**스트림** 헤더에서 **데이터 수집 사용량**을 선택하면 각 소스가 지난 24시간, 7일, 30일 동안
얼마나 많은 데이터를 수집했는지 볼 수 있습니다. 동일한 수치가 세 가지 방식으로 나뉘며, 그
합계는 서로 일치합니다:

| 뷰 | 소스 |
|---|---|
| **인증 정보** | API 토큰, RUM 클라이언트 토큰, 커넥터 또는 로그인한 사용자입니다. **플랫폼 내부**는 플랫폼 자체의 텔레메트리입니다. |
| **스트림** | 이름과 유형으로 식별되는 하나의 스트림입니다. |
| **서비스** | 이벤트가 `service.name`에 지정한 서비스이며, 없으면 `service` 또는 `service_name`입니다. **서비스 이름 없음**은 이름을 지정하지 않은 이벤트를 모읍니다. |

수집량은 수락된 항목의 압축 해제된 요청 바이트를 셉니다. 거부된 이벤트는 집계되지 않으며,
발신자가 다시 시도한 요청은 한 번만 집계됩니다. 스팬은 도착 시점에, 테일 샘플링 전에 집계됩니다.
세션 리플레이는 **스트림** 뷰의 `rum_replay` 행에 집계됩니다. 하나의 요청이 여러
서비스나 스트림을 포함하면 해당 바이트는 이벤트 수에 따라 분배되므로, 이들 뷰는 정확한 값이 아니라
근사치입니다.

알 수 없는 수치는 0이 아니라 `–`로 표시됩니다. `≥` 표시가 있는 수치는 하한값입니다. 윈도 내에서
측정이 시작되었기 때문이며, 목록 위의 줄에 시작 시점이 표시됩니다. 수치는 약 1분 이내에 페이지에
반영됩니다. 갑자기 중지된 노드는 마지막 15초의 집계를 잃을 수 있습니다.

행을 선택하면 해당 소스를 시간별로 볼 수 있고, 나머지 두 뷰를 기준으로 무엇으로 구성되어 있는지도 볼 수 있습니다.

### 예산 설정

행에서 **예산 설정**을 선택하거나, 여러 행을 선택해 모두에 하나의 예산을 설정하십시오.

| 필드 | 의미 |
|---|---|
| **기간** | **매일** 또는 **매월**이며, UTC 달력을 기준으로 합니다. |
| **제한** | 1 MiB에서 1 PiB까지입니다. |
| **경고 임계값 (%)** | 한도 대비 이 비율에 도달하면 한 번, 한도를 모두 사용하면 한 번 더 알립니다. `0`은 한도를 모두 사용했을 때만 알립니다. 기본값: 80. |
| **알림 대상** | 조직의 멤버입니다. 기본값: 예산을 설정한 사람입니다. |

예산은 사람에게 알리기만 합니다. 소스가 예산을 초과해도 수집은 동일하게 응답하고 저장하며, 아무것도
버려지거나 느려지지 않습니다. 각 단계는 기간당 한 번 알립니다. 한도를 높이면 이후 평가에서
다시 알림이 발생합니다.

알림은 기본 제공 알림 정책인 **데이터 수집 예산 거의 소진**과 **데이터 수집**
**예산 초과**를 통해 전송되며, 상단 바의 알림 센터에 표시됩니다. 알림 대상과 방식을 바꾸려면
[알림 채널](/ko/notification-channels)을 참조하십시오.

`_sys` 조직은 알림 정책이 없으므로 예산도 없습니다. **플랫폼 내부**, **서비스 이름 없음**, **기타 서비스**에는
예산을 설정할 수 없습니다. 이들은 [플랫폼 설정](/ko/settings/platform#데이터-수집-사용량)의 한도를 초과한
서비스입니다.
