합성 모니터링은 고객이 장애를 신고하기 전에 외부에서 서비스를 테스트합니다.
**합성 모니터링**에서 점검을 생성하고, 일정을 게시하고, 실행 증거를 검토하고,
비공개 프로브 위치를 관리합니다.

## 모니터링할 수 있는 항목

| 점검 유형 | 용도 |
|---|---|
| **HTTP / API** | URL, 메서드, 헤더, 본문, 응답 상태, 콘텐츠, 소요 시간을 검증합니다. |
| **브라우저** | 브라우저에서 사용자 여정을 실행하고 페이지 또는 단계의 결과를 검증합니다. |
| **TCP** | 호스트의 지정된 포트에서 연결을 수락하는지 확인합니다. |
| **DNS** | 시스템 또는 지정한 리졸버로 모든 레코드 유형(A, AAAA, CNAME, MX, NS, TXT, SOA, SRV, CAA, PTR)을 조회하고 응답 레코드와 응답 코드를 검증합니다. 필요하면 DNSSEC를 필수로 설정합니다. |
| **ICMP / Ping** | Ping을 몇 차례 보내 패킷 손실과 평균 왕복 시간을 확인합니다. |
| **TLS** | TLS 핸드셰이크, 인증서의 신원 정보, 만료일을 검증합니다. |
| **gRPC** | gRPC 엔드포인트를 호출하고 응답을 검증합니다. |
| **하트비트** | 외부 작업 또는 서비스가 기한 내에 하트비트를 보내는지 확인합니다. |

gRPC 점검의 **주소**는 `host:port` 형식으로 입력합니다. 호출에 TLS를 사용할지는
**TLS 사용** 설정으로만 결정합니다. **TLS 사용**을 켠 상태에서 `http://`를 입력하는 등
스킴이 설정과 충돌하는 주소는 허용하지 않습니다.

## 점검 생성 및 게시

<Steps>
  <Step title="초안 생성">
    **합성 모니터링 → 점검**을 열고 **점검 생성**을 선택한 다음 유형을 선택합니다. 대상,
    제한 시간, 검증 조건, 일정, 실행 위치를 하나 이상 설정합니다. 새 점검은 초안으로 시작합니다.
  </Step>
  <Step title="리비전 테스트">
    **리비전 테스트**를 선택합니다. MoleSignal은 일정을 활성화하지 않고 초안을 실행합니다.
    확인된 대상, 실행 시도, 소요 시간, 검증 증거, 오류를 검토합니다.
  </Step>
  <Step title="수정본 게시">
    테스트에 성공하면 **수정본 게시**가 활성화됩니다. 수정본을 게시하면 해당 리비전이 활성화되고
    첫 예약 실행 시간이 계산됩니다.
  </Step>
  <Step title="모니터 운영">
    필요할 때 **지금 실행**을 선택해 점검을 실행합니다. 편집하면 새 리비전 초안이 생성되므로,
    새 리비전을 테스트하고 게시할 때까지 기존에 게시한 설정으로 점검을 계속 실행합니다.
    결과 기록을 삭제하지 않고 점검을 일시 중지하거나 재개하거나 보관할 수 있습니다.
  </Step>
</Steps>

<Note>
초안을 테스트해야 게시할 수 있으므로, 테스트하지 않은 대상이나 검증 조건이 정상적으로 작동하는
운영 일정을 예고 없이 대체하는 일을 방지합니다.
</Note>

## 일정 및 재시도

실행 간격을 설정하거나 시간대를 명시한 cron 표현식을 사용합니다. 대부분의 능동 점검은
실행 간격을 10초에서 1일까지 설정할 수 있으며, 브라우저 점검은 최소 60초부터 설정할 수 있습니다. 제한 시간은 100
밀리초에서 5분 사이로, 실행 간격보다 짧게 설정합니다. MoleSignal은 한 번의 실행에서 최대 두 번
재시도한 후 최종 결과를 기록합니다.

하트비트 점검은 외부로 요청을 보내는 일정 대신 보고 기한을 사용합니다. 작업을 담당하는
워크로드에서 하트비트를 전송한 다음, 결과 기록에서 보고 지연과
능동 프로브 실패를 구분합니다.

## 검증 조건 및 상태

검증 조건은 응답 상태, 본문, 헤더, DNS 응답 레코드,
인증서 속성, 브라우저 실행 결과 등 프로토콜별 필드를 검사합니다. **경고** 검증 조건을 충족하지 못하면 성능 저하로
판정하고, **심각** 검증 조건을 충족하지 못하면 실패로 판정합니다.

점검 유형별로 응답에서 다음 값을 검증에 사용할 수 있습니다.

| 점검 유형 | 검증 소스 |
|---|---|
| **HTTP / API** | `status`, `body`, `json:<JSONPath>`, `header:<name>`, `duration_ms`, `size_bytes`, `timing.dns_ms`, `timing.connect_ms`, `timing.tls_ms`, `timing.first_byte_ms` |
| **TCP** | `response`, `duration_ms` |
| **DNS** | `answers`, `answer_count`, `rcode`, `duration_ms` |
| **gRPC** | `status`(상태 확인 서비스가 반환하는 서비스 상태, 예: `SERVING`), `duration_ms` |

점검 유형에서 지원하지 않는 소스를 지정하면 리비전을 저장할 수 없습니다.

`json:`은 본문의 처음 4 MiB에 포함된 JSON을 JSONPath(RFC 9535)로 조회합니다. 결과가 문자열 하나이면
문자열 그대로, 그 외 단일 값이면 JSON으로, 여러 값이면 해당 값의 JSON 배열로 읽습니다. 일치하는 값이 없거나
본문이 JSON이 아니면 빈 값으로 처리합니다. `body`에서는 **JSON Schema와 일치** 검증 조건도 사용할 수 있습니다.
이 조건은 동일한 4 MiB를 읽고 본문이 스키마와 처음으로 일치하지 않는 위치를 표시합니다. 스키마에서
`$ref`로 외부 URL 또는 파일을 참조할 수 없습니다. `size_bytes`는 본문 크기를 최대 16 MiB까지 집계합니다. `timing.*`는 해당 단계의 처리 구간별 소요 시간을 나타내며,
거치지 않은 구간은 0으로 표시합니다. JSONPath로 값을 추출할 때는 패턴이 필요하지 않습니다. 찾은 값을 그대로 사용합니다.

대상의 주소를 확인할 수 없거나 대상에 연결할 수 없는 경우, 대상이 연결을 끊거나 TLS 핸드셰이크에 실패하는 경우,
또는 제한 시간 내에 응답하지 않는 경우에는 심각 검증 조건이 실패한 경우와 마찬가지로 실행이 실패합니다.
송신 정책이 대상을 차단하거나 시크릿이 누락되거나 설정을 지원하지 않아
구성대로 점검을 실행할 수 없는 경우에만 실행 결과를 알 수 없음으로 표시합니다.

선택한 위치에서 연속으로 성공하거나 실패한 횟수를 바탕으로 모니터의 상태를 계산합니다.
실패 임계값, 복구 임계값, 위치 정책을 설정해 상태가 자주 바뀌거나
한 네트워크에 국한된 문제를 전체 장애로 판단하는 일을 방지합니다.

## HTTP 연결

HTTP 점검의 **연결** 섹션에서 서버에 연결하는 방식을 설정합니다. 필드를 비워 두면
기본값을 사용합니다.

| 설정 | 효과 |
|---|---|
| **HTTP 버전** | **자동 협상**은 TLS 연결에서 HTTP/2와 HTTP/1.1을 제안하고 서버가 선택하도록 합니다. 암호화하지 않은 HTTP 연결에서는 HTTP/1.1을 사용합니다. **HTTP/1.1만 사용**은 HTTP/1.1만 제안합니다. **HTTP/2만 사용**은 서버가 HTTP/2에 동의하지 않으면 실행을 실패로 처리하고, 암호화하지 않은 HTTP 연결에서는 사전 협상 없이 HTTP/2(h2c)를 사용합니다. |
| **DNS 서버** | 지정한 서버에서 호스트 이름을 확인합니다. 서버를 `host` 또는 `host:port` 형식으로 입력합니다. 이 서버도 송신 정책을 충족해야 합니다. |
| **호스트 바인딩** | hosts 파일과 마찬가지로 호스트 이름을 지정한 IP 주소에 매핑합니다. Host 헤더와 인증서 검증에는 원래 호스트 이름을 사용하므로, 특정 오리진 서버나 CDN 노드를 점검할 때 유용합니다. |
| **클라이언트 인증서** | 서버가 상호 TLS를 요청하면 PEM 형식의 인증서 체인과 개인 키를 제시합니다. 파일로 업로드하거나 붙여넣습니다. 둘 다 포함한 파일을 업로드하면 두 필드를 모두 채웁니다. 키는 암호화하여 저장하고 다시 표시하지 않습니다. 점검을 편집할 때 키 필드를 비워 두면 기존 키를 유지합니다. |

각 단계의 결과에는 실제로 연결한 주소(`remote_address`)와 서버가 응답에 사용한
HTTP 버전(`http_version`)이 기록됩니다.

## 트레이스 컨텍스트 및 실패 진단

체크의 **진단** 섹션에는 두 가지 스위치가 있으며, 기본적으로 둘 다 켜져 있습니다.

**트레이스 컨텍스트**: 리디렉션을 포함한 HTTP 체크의 모든 요청과 모든 gRPC 호출에
W3C `traceparent`를 포함합니다. 한 시도의 모든 요청은 하나의 트레이스에 속하며, 각 요청은 해당 트레이스의 스팬입니다.
단계에서 자체 `traceparent` 헤더나 메타데이터를 설정하면 그 값을 유지합니다. 단계와 결과에는
`trace_id`를 기록합니다. 결과 상세에서 **트레이스 보기**를 선택하면 테스트 대상 서비스가
요청에 대해 저장한 트레이스가 열립니다. 서비스에서 트레이싱을 사용하지 않으면 표시할 트레이스가 없습니다. gRPC 체크에서 설정한 메타데이터도
호출과 함께 전송합니다.

**실패 시 traceroute 실행**: HTTP, TCP, TLS, gRPC, SSH 또는 ICMP 체크가 대상에 연결할 수 없으면
(연결 실패, 시간 초과, 연결 끊김, TLS 핸드셰이크 실패, ping 응답 없음 또는
손실) 에이전트는 마지막으로 연결을 시도한 주소에 ICMP traceroute를 한 번 실행합니다. 최대 30홉까지, 홉당 프로브 4개를 전송하며
최대 12초 동안 실행합니다. 결과 상세에는 홉별 주소, 손실률,
최소·평균·최대 왕복 시간을 표로 표시합니다. traceroute에는 raw 소켓(root 또는 `CAP_NET_RAW`)이나
권한 없는 ICMP 소켓(macOS 및 `net.ipv4.ping_group_range` 범위에 속하는 Linux 그룹)이 필요합니다. 둘 다 사용할 수 없으면
해당 단계에 실행하지 않은 이유를 표시합니다.

이전 버전의 에이전트는 `traceparent`를 전송하거나 traceroute를 실행하지 않습니다. 체크 결과에는 영향이 없습니다.

**RUM 세션**: 브라우저 체크는 페이지의 스크립트가 실행되기 전에 테스트임을 페이지에 알립니다. [브라우저 RUM SDK](/ko/rum/browser-sdk)를 실행하는 페이지는 `synthetics` 유형의 세션을 기록합니다. 해당 시도에서 **이 실행의 RUM 세션 열기**를 선택하면 세션 리플레이와 이벤트를 볼 수 있습니다. 이러한 세션은 [실제 사용자 지표에서 제외합니다](/ko/rum/test-traffic). SDK 실행 여부는 페이지에서 결정합니다. SDK를 실행하지 않는 페이지에는 아무것도 추가하지 않습니다.

## 시간 범위 및 가용성

개요, 체크 목록, 결과, 개별 체크의 개요에서는 탐색 카드 오른쪽에
시간 범위를 표시합니다. 기본 범위는 최근 24시간이며 변경할 수 있습니다.

- **가용성** = 가용 상태인 실행 수 ÷ 결과가 확정된 실행 수. 성공, 간헐적 실패, 성능 저하 상태의 실행은
  가용으로 분류하고, 실패한 실행은 비가용으로 분류합니다. 상태를 알 수 없거나 건너뛴 실행은 계산에서 제외합니다.
- 개요에는 선택한 범위의 전체 체크 가용성과 추세를 표시하고, 지도에는
  위치별 가용성을 색상으로 표시합니다. 체크 목록에는 체크별 가용성 열을 표시합니다. 개별 체크
  개요에는 선택한 범위의 가용성, 응답 시간 중앙값, p95를 표시하며, **위치별
  응답**에는 위치별 소요 시간 중앙값을 시간 간격별로 표시합니다.
- **최근 실행** 영역에는 시간 범위와 관계없이 가장 최근 실행을 표시합니다.

가용성은 `GET /api/v1/synthetics/availability`에서 가져옵니다. 이 API는 `from`과 `to`(마이크로초),
`monitor_id`, `location_id`, `step`(초 단위, 생략하면 시간 범위에 따라 결정)을 받습니다.
전체, 체크별, 위치별, 시간 간격별로 실행 수, 가용 실행 수, 실패 수, 결과 미확정 실행 수, 가용성, 소요 시간의 P50, P95, 최댓값을
반환합니다. 단일 체크를 조회하면 위치별 값도 시간 간격별로
반환합니다. 결과 목록 API `GET /api/v1/synthetics/results`는 `fromTime`과 `toTime`을 받습니다.

## 결과 스트림 및 보존

예약된 실행은 테스트 실행을 제외하고 전체 결과를 저장하는 것과 별도로, 실행 시작 시각을 기준으로 조직의
`_synthetic_results` 로그 스트림에 한 행으로 기록합니다. 실행에 값이 없는 필드는
생략합니다.

| 필드 | 내용 |
|---|---|
| `check_id`, `check_name`, `check_kind`, `revision_id` | 실행한 체크와 리비전 |
| `location_id`, `location_name`, `agent_id` | 실행 위치와 실행한 에이전트 |
| `result_id`, `outcome`, `available`, `attempts` | 실행 결과, 가용 여부(상태를 알 수 없거나 건너뛴 경우 생략), 시도 횟수 |
| `duration_ms`, `dns_ms`, `connect_ms`, `tls_ms`, `first_byte_ms` | 마지막 시도의 전체 및 단계별 소요 시간 |
| `status_code`, `error_category`, `skip_reason`, `trace_id` | HTTP 상태, 실패 유형, 건너뛴 이유, 트레이스 |
| `team_id`, `tags` | 체크의 팀과 태그(쉼표로 구분) |

대시보드 패널과 알림 규칙은 SQL로 스트림을 조회하며, 패널의 시간 범위는
쿼리에 적용됩니다. 다음은 체크별 가용성과 소요 시간 p95를 조회하는 예입니다.

```sql
SELECT check_name,
       avg(CASE WHEN available THEN 1.0 ELSE 0.0 END) AS availability,
       approx_percentile_cont(0.95) WITHIN GROUP (ORDER BY duration_ms) AS p95_ms
FROM _synthetic_results
WHERE available IS NOT NULL
GROUP BY check_name
```

예약된 알림 규칙도 같은 데이터를 조회하며, `location_name` 기준으로 규칙을 [분할](/ko/alerting/rules#열-기준으로-규칙-그룹화)하면
가용성이 임곗값보다 낮아진 위치마다 별도의
인시던트를 생성합니다.

기본적으로 전체 결과를 30일간 보존합니다. 플랫폼의
**데이터 보존** 페이지에서 **신세틱 테스트 결과**의 보존 기간을 설정합니다(0으로 설정하면 영구 보존). [플랫폼 설정](/ko/settings/platform#데이터-보존)을 참조합니다.
보존 기간이 지난 실행과 해당 아티팩트, 완료된 작업은 하루에 한 번 삭제합니다. `_synthetic_results`
스트림은 자체 보존 설정을 따르며, 해당 스트림 페이지에서 설정을 변경할 수 있습니다.

## 위치 및 Probe 에이전트

MoleSignal은 두 가지 위치 모델을 지원합니다.

| 위치 | 동작 |
|---|---|
| **내장 로컬** | Standalone 배포는 같은 프로세스에서 Probe 실행기를 자동으로 시작합니다. 로컬에서 기능을 평가하거나 MoleSignal과 같은 위치에서 점검을 실행할 때 유용합니다. |
| **에이전트 풀** | 하나 이상의 외부 <code>probe-agent</code> 프로세스가 프라이빗 네트워크, 리전 또는 엣지 위치에서 점검을 실행합니다. |

**합성 모니터링 → 위치**에서 에이전트 풀 위치를 생성합니다. 일회용 등록
토큰을 생성한 뒤 에이전트를 등록합니다.

```bash
probe-agent register \
  --endpoint https://molesignal.example.com:5084 \
  --token ONE_TIME_TOKEN \
  --ca-certificate-base64 BASE64_CA
```

그런 다음 제어 스트림을 시작합니다.

```bash
probe-agent run
```

등록에는 서버 인증 TLS를 사용합니다. 에이전트는 <code>--state-dir</code>로 지정한 경로에
비공개 ID를 저장하고, 포트 5085의 제어 스트림에는 mTLS를 사용합니다. 기본 상태
디렉터리는 <code>/var/lib/molesignal-probe</code>입니다.

<code>conf/config.toml</code>에서 서버 엔드포인트를 구성합니다.

Probe 제어 플레인은 **Standalone** 및 **알림** 노드에서 자동으로 시작합니다.
별도의 활성화 설정은 없습니다.

```toml
[probe]
bind = "0.0.0.0"
register_port = 5084
control_port = 5085
register_endpoint = "https://molesignal.example.com:5084"
control_endpoint = "https://molesignal.example.com:5085"
server_names = ["molesignal.example.com"]
```

<Warning>
모든 네트워크 요청 전에 아웃바운드 정책을 적용합니다. 선택한 위치의 정책에서 명시적으로 허용하지 않으면
루프백, 링크 로컬 또는 사설 주소로의 요청을 거부합니다. 이렇게 하면
서버 측 요청 위조로부터 MoleSignal 호스트와 프라이빗 네트워크를 보호할 수 있습니다.
</Warning>

HTTP 점검은 Probe 에이전트 환경의 `HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY`, `NO_PROXY`를
따릅니다. 프록시를 사용하면 결과에 표시되는 연결 시간은 터널 요청을 포함하여 프록시에
연결하는 데 걸린 시간입니다. 대상에는 프록시가 연결하므로, 아웃바운드 정책에서 승인한 주소를
대상 연결에 강제하지 않습니다. 프록시가 접근할 수 있는 대상을 제한합니다.

에이전트는 프로세스에 ping을 보낼 권한이 있을 때만 ICMP 점검을 지원합니다. Linux에서는 `CAP_NET_RAW`가 필요하거나,
`net.ipv4.ping_group_range` 범위에 속하는 그룹의 구성원이어야 합니다. 내장 로컬 위치의 프로세스 내 실행기에도
같은 규칙이 적용됩니다.

에이전트는 하트비트를 보낼 때마다 지원 기능 수준을 보고합니다. 이전 버전의 에이전트가 지원하지 않는 설정을 사용하는 점검은
실행 가능한 버전의 에이전트에만 할당합니다. 이러한 설정에는 A 및 AAAA 이외의 DNS 레코드 유형,
이름을 지정한 리졸버, DNSSEC, ICMP, TCP·DNS·gRPC 점검의 어설션이 포함됩니다. HTTP 점검의 경우
JSONPath, JSON Schema, 크기 및 타이밍 소스, HTTP/2 전용, DNS 서버, 호스트 바인딩,
클라이언트 인증서가 포함됩니다. 에이전트 풀에서 이러한 점검을 실행하기 전에 `probe-agent`를 업그레이드합니다.

1분 동안 하트비트가 없는 에이전트는 오프라인으로 표시합니다. 위치의 상태는 소속 에이전트의
상태에 따라 결정합니다. 모두 온라인이면 온라인, 일부만 온라인이면 성능 저하, 모두 오프라인이면 오프라인입니다.
기한까지 어떤 에이전트도 맡지 않은 실행은 **건너뜀**으로 기록하고 그 이유를 표시합니다. 온라인 에이전트 없음,
해당 유형의 점검을 실행할 에이전트 없음, 설정을 지원하는 버전의 에이전트 없음, 또는 모든 에이전트 사용 중입니다.

### Kubernetes에서 에이전트 실행

Helm 차트 `probe-agent`는 에이전트를 StatefulSet으로 실행합니다. 각 레플리카는 개별적으로 등록하고
자체 영구 볼륨에 ID와 미전송 결과를 보관합니다. 따라서 파드를 교체해도 동일한
에이전트로 유지됩니다. 이 차트는 서버를 배포하지 않습니다. 서버는 `molesignal` 차트로 동일한
클러스터나 다른 위치에 배포합니다.

<Warning>
외부 에이전트를 사용하려면 서버와 에이전트 이미지 모두 26.2.0.0보다 높은 버전이어야 합니다. 26.2.0.0에서는
서버가 에이전트를 등록할 수 없으며, 에이전트가 **등록됨** 상태를 벗어나지 못합니다.
</Warning>

<Steps>
  <Step title="에이전트가 접근할 수 있는 서버 주소 설정">
    에이전트는 **Standalone** 또는 **알림** 노드의 포트 5084 및 5085에 연결합니다. `server_names`에는
    에이전트가 사용하는 호스트 이름이 포함되어야 합니다. 기본값에는 `localhost`만 포함됩니다. 에이전트가 `molesignal` 차트와 동일한
    클러스터에 있으면 해당 차트의 값에 Service 이름을 설정합니다.
    `distributed` 모드에서는 `alert` 역할의 Service를 사용합니다.

    ```yaml
    config:
      probe:
        register_endpoint: https://molesignal.molesignal.svc.cluster.local:5084
        control_endpoint: https://molesignal.molesignal.svc.cluster.local:5085
        server_names: [molesignal.molesignal.svc.cluster.local]
    ```

    에이전트가 다른 위치에 있으면 `LoadBalancer` 또는 `NodePort` Service로 두 포트를 노출합니다.
    중간 구성 요소에서 TLS를 종료하면 안 됩니다. 에이전트는 서버의 CA만 신뢰하며, 제어 스트림에서는
    클라이언트 인증서로 에이전트를 인증합니다.
  </Step>
  <Step title="위치 및 토큰 생성">
    **합성 모니터링 → 위치**를 열고 **프라이빗 위치 추가**를 선택한 뒤 토큰을 생성합니다.

    | 토큰 | 메뉴 | 등록 범위 | 유효 기간 |
    |---|---|---|---|
    | 일회용 토큰 | **에이전트 등록** | 에이전트 1개 | 최대 60분 |
    | 에이전트 토큰 | **합성 모니터링 → 에이전트 → 에이전트 토큰 생성** | 만료되거나 비활성화될 때까지 에이전트 수 제한 없음 | 30일~1년 또는 만료 없음 |

    레플리카가 두 개 이상이면 에이전트 토큰을 사용합니다. 두 종류의 토큰 모두 등록 명령과 함께 한 번만 표시합니다.
    다음 단계에서는 해당 명령의 `--endpoint`와 `--ca-certificate-base64`를 사용합니다.
  </Step>
  <Step title="차트 설치">
    토큰을 Secret에 저장합니다. 차트에는 기본 토큰이 없으며 ConfigMap에 토큰을 쓰지 않습니다.

    ```bash
    kubectl create namespace probes
    ```

    ```bash
    kubectl --namespace probes create secret generic probe-agent-registration --from-literal=token=<token>
    ```

    ```bash
    helm repo add molesignal https://charts.molesignal.com
    ```

    ```bash
    helm install probe-agent molesignal/probe-agent --namespace probes --set registration.endpoint=<endpoint> --set registration.caCertificateBase64=<base64-ca> --set registration.existingSecret=probe-agent-registration
    ```

    엔드포인트와 CA를 확인합니다. 테스트는 서버가 거부하는 토큰으로 등록을 시도합니다.

    ```bash
    helm test probe-agent --namespace probes
    ```

    이후 **합성 모니터링 → 에이전트**에 에이전트가 표시됩니다.
  </Step>
</Steps>

| 동작 | 세부 정보 |
|---|---|
| 등록 | 초기화 컨테이너는 볼륨에 ID가 없을 때만 에이전트를 등록합니다. 따라서 일회용 토큰을 이미 사용했더라도 파드를 교체하는 데 문제가 없습니다. |
| 토큰 | 에이전트가 ID를 얻기 전까지만 토큰을 읽습니다. 토큰을 교체해도 재시작하지 않으며, 에이전트가 온라인 상태가 되면 Secret을 삭제할 수 있습니다. ID와 토큰이 모두 없는 레플리카는 `Init` 상태에서 대기하고 그 이유를 로그에 기록합니다. |
| 축소 및 제거 | 볼륨이 유지되므로 에이전트가 다시 시작해도 기존 ID를 사용합니다. 에이전트 사용을 중단하려면 에이전트를 폐기하고 해당 PersistentVolumeClaim인 `state-<release>-probe-agent-<ordinal>`을 삭제합니다. |
| 장기간 연결하지 않는 에이전트 | 인증서는 `[probe].certificate_days`로 지정한 기간(기본 30일) 동안 유효합니다. 에이전트가 유효 기간을 1주일 미만으로 남긴 상태에서 연결하면 인증서를 갱신합니다. 인증서가 만료되면 에이전트를 다시 연결할 수 없습니다. 에이전트를 폐기하고 볼륨을 삭제한 뒤 다시 등록합니다. |
| Ping | 차트가 파드에 `net.ipv4.ping_group_range`를 설정하므로 ICMP 점검에 별도의 권한이 필요하지 않습니다. |
| 이미지 | `ghcr.io/molesignal/probe-agent`입니다. `global.imageRegistry`로 레지스트리 호스트를 변경합니다. |

브라우저 점검을 실행하려면 Chromium 샌드박스 사용 여부를 결정해야 합니다. 차트는 기본적으로 Chromium을
`--no-sandbox`로 시작합니다. 샌드박스에 필요한 비특권 사용자 네임스페이스는 `RuntimeDefault`
seccomp 프로필이 차단합니다. 이 경우 파드가 Chromium을 격리합니다. Chromium은 루트로 실행되지 않고, 추가 권한과
서비스 계정 토큰이 없으며, 읽기 전용 루트 파일 시스템을 사용합니다. Chromium의 취약점을 악용하는 페이지는
에이전트의 개인 키에 대한 접근을 비롯해 해당 파드의 권한을 얻습니다. 샌드박스를 사용하려면
`browser.sandbox`를 `true`로, `securityContext.seccompProfile.type`을 `Unconfined`로 설정합니다. 이 경우 노드에서
비특권 사용자 네임스페이스를 허용해야 합니다. Ubuntu 23.10 이상에서는
`kernel.apparmor_restrict_unprivileged_userns=0`을 설정해야 합니다. `baseline` 및 `restricted` Pod Security Standards는
`Unconfined`를 허용하지 않습니다.

`/dev/shm`은 따로 구성할 필요가 없습니다. 에이전트는 Chromium을 `--disable-dev-shm-usage`로 시작하므로 공유
메모리는 `browser.tmp`로 구성하는 `/tmp`를 사용합니다. 기본 리소스 요청량은 512 MiB이고
한도는 2 GiB이며, 한 번에 브라우저 점검 1개를 실행하기에 적합합니다. `browser.maxConcurrent`를 1씩 늘릴 때마다 한도를 최소
1 GiB 늘립니다. `browser.maxConcurrent`를 `0`으로 설정하면 에이전트가 브라우저 점검을 지원하지 않습니다.

전체 설정값과 문제 해결 방법은 [차트 README](https://github.com/molesignal/molesignal-helm/tree/main/charts/probe-agent)를
참조합니다.

## 변수, 시크릿 및 증거

재사용할 민감하지 않은 값에는 변수를 사용하고, 자격 증명에는 암호화된 시크릿을 사용합니다. 시크릿
값은 쓰기 전용이며 API는 해당 값을 반환하지 않습니다. 결과 상세 정보에는 제한된 범위의 요청 및
응답 증거, 소요 시간, 시도 메타데이터, 선택한 위치, 활성 리비전을 기록하며
저장된 시크릿은 노출하지 않습니다.

## 알림 인시던트

점검이 실패하면 알림 인시던트를 열고 알림 규칙과 같은 방식으로 온콜 담당자를 호출합니다. 점검 양식의 **알림**에서 설정합니다.

| 점검 상태 | 인시던트 |
|---|---|
| **실패** | 심각도가 `error`인 인시던트를 엽니다. |
| **성능 저하** | **상태 저하 시 경보**를 켜면 심각도가 `warning`인 인시던트를 엽니다. |
| **간헐적 실패** | **결과 불안정 시 경보**를 켜면 심각도가 `warning`인 인시던트를 엽니다. |
| **통과** | 인시던트를 해결합니다. |
| **결과 없음** | **결과 없음 시 경보**를 켜면 심각도가 `warning`인 별도의 인시던트를 엽니다. 이 설정은 기본적으로 켜져 있습니다. 결과가 다시 들어오면 인시던트를 해결합니다. |

- 각 점검에는 상태에 대한 활성 인시던트가 최대 하나만 있습니다. 점검 상태가 실패, 성능 저하, 간헐적 실패 사이에서 바뀌면 [알림 파이프라인](/ko/pipelines/alert-events#심각도-변경)이 정한 새 심각도를 열린 인시던트에 적용합니다. 심각도를 수동으로 설정한 경우에는 변경하지 않습니다. 심각도가 높아지면 에스컬레이션을 다시 시작합니다. 확인 처리한 인시던트는 해결할 때까지 그대로 유지합니다.
- 기한 내에 실행을 맡는 에이전트가 없으면 해당 실행을 건너뛴 것으로 기록하고 위치 상태를 그대로 유지합니다. 한 위치에서 연속으로 건너뛴 실행 횟수가 해당 위치를 실패로 판정하는 데 필요한 연속 실패 횟수에 도달하면 그 위치에 결과가 없는 것으로 판단합니다. 결과가 없는 위치 수가 위치 정책에서 정한 기준에 도달하면 점검 상태가 **결과 없음**이 됩니다. 점검 페이지에는 이 상태와 함께 해당 위치 및 마지막 실행을 건너뛴 이유가 표시됩니다. 결과 없음 인시던트에는 `synthetic.state` = `no_data` 및 `alert.condition` = `no_data`가 포함되며, 상태 인시던트와 동시에 열려 있을 수 있습니다. 수동으로 해결하면 결과가 다시 들어오기 전까지는 다시 열리지 않습니다.
- 점검을 일시 중지하거나 보관하면 열린 인시던트와 확인 처리한 인시던트를 해결합니다. 이후에는 인시던트를 해결할 실행이 없기 때문입니다.
- 점검의 **에스컬레이션 정책**에 따라 담당자를 호출합니다. **라우팅됨**을 선택하면 [알림 라우팅](/ko/alerting/routing)이 팀과 에스컬레이션 정책을 선택합니다. **에스컬레이션 정책 없음**을 선택하면 담당자를 호출하지 않지만, 알림 전송 정책은 인시던트를 계속 전달합니다.
- 인시던트 제목에는 점검 이름을 사용합니다. 알림 전송 정책에서 인시던트를 라우팅할 수 있도록 `alert.source` = `synthetic`, `synthetic.kind`, `synthetic.state` 라벨을 추가합니다. 점검에 태그나 팀이 있으면 각각 `synthetic.tags`와 `team_id`도 추가합니다. 인시던트 상세 정보에는 점검으로 이동하는 링크가 있습니다.
- 알림 제목에는 `ERROR · Checkout API`처럼 심각도와 점검 이름을 표시하고, 본문에는 `Synthetic check Checkout API is failing.`과 같은 메시지를 표시합니다. 결과 없음 알림의 제목은 `NO DATA · Checkout API`이며, 본문에는 `Synthetic check Checkout API has no results from Frankfurt (3 missed in a row): no Agent was online there.`와 같이 결과가 없는 위치와 이유를 워크스페이스의 기본 언어로 표시합니다.
- 연속 실패, 복구, 위치 정책에 따라 결정하는 전체 점검 상태만 고려합니다. 단일 위치의 상태만으로는 인시던트를 열지 않습니다.

## 실패를 상태 페이지에 게시

상태 페이지 자동화 규칙에서 **신세틱 모니터**를 소스로 사용할 수 있습니다. 모니터를 선택하고,
일치시킬 상태 전이와 심각도를 지정한 다음, 영향을 구성 요소에 매핑하고 수동 승인
또는 자동 게시를 선택합니다. [상태 페이지](/ko/status-pages#게시-자동화)를 참조합니다.

## 권한

| 권한 | 허용 작업 |
|---|---|
| <code>synthetics.monitors.read</code> | 점검, 리비전, 일정을 조회합니다. |
| <code>synthetics.results.read</code> | 실행과 결과를 조회합니다. |
| <code>synthetics.locations.read</code> | 위치와 에이전트 상태를 조회합니다. |
| <code>synthetics.secrets.read</code> | 암호화된 신세틱 모니터링 시크릿의 이름을 조회합니다. |
| <code>synthetics.monitors.manage</code> | 점검을 생성, 테스트, 게시, 일시 중지, 재개합니다. |
| <code>synthetics.monitors.run</code>, <code>synthetics.monitors.archive</code> | 점검을 즉시 실행하거나 보관합니다. |
| <code>synthetics.locations.manage</code> | 위치, 에이전트 풀, 등록 토큰, 이그레스 정책을 관리합니다. |
| <code>synthetics.secrets.manage</code> | 암호화된 신세틱 모니터링 시크릿을 생성, 교체, 삭제합니다. |
