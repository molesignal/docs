상태 페이지는 서비스 운영 상태를 정해진 방식으로 고객에게 전달합니다. **상태 페이지**를 열어
페이지를 만들고, 용도별로 나뉜 7개 탭에서 관리합니다.

## 작업 공간

| 탭 | 용도 |
|---|---|
| **개요** | 요약, 구성 요소, 진행 중인 인시던트, 예정된 유지보수를 확인합니다. |
| **구성 요소** | 고객에게 표시할 서비스 구성 요소를 만들고, 그룹으로 묶고, 순서를 바꾸고, 숨기고, 복원하고, 업데이트합니다. |
| **인시던트** | 계획되지 않은 이벤트의 초안을 작성하고 게시한 뒤, 업데이트하고 모니터링하고 해결합니다. |
| **유지보수** | 계획된 작업을 예약, 게시, 시작, 완료 또는 취소합니다. |
| **기록** | 개요에서 항목을 펼치지 않고도 종료된 인시던트와 유지보수를 검색하고 필터링합니다. |
| **구독자** | 이메일, 웹훅, Slack 구독자를 관리하고, 가져오기, 구독 확인, 전송 결과를 관리합니다. |
| **설정** | 일반 동작, 브랜딩, 현지화, 도메인, 액세스, 자동화를 설정합니다. |

## 상태 페이지 만들기

**상태 페이지 만들기**를 선택한 다음 다음 항목을 설정합니다.

- 고객에게 표시할 이름과 전체에서 고유한 슬러그
- 하나 이상의 인터페이스 언어, 기본 언어, IANA 시간대
- **공개** 또는 **비공개** 표시 범위
- 전송 기록 보존 기간, 비공개 세션 유지 시간, 인시던트 기록 표시 기간
- 로고, 브랜드 색상, 사용자 지정 도메인(선택 사항)

공개 인터페이스는 영어와 중국어 간체를 지원합니다. 구성 요소 이름, 인시던트 메시지,
유지보수 업데이트는 팀이 작성한 그대로 표시합니다. 페이지에서 보내는 이메일에도
기본 언어를 사용합니다.

기본 공개 주소는 <code>/status/SLUG</code>입니다.

## 구성 요소

각 구성 요소에는 이름, 설명, 순서, 표시 여부가 있으며, 고객에게 표시하는 상태는 다음 중 하나입니다.

- **정상 작동**
- **성능 저하**
- **부분 중단**
- **주요 중단**
- **유지보수**

계속 관리하되 공개하지 않을 구성 요소는 숨깁니다. 숨긴 구성 요소는
공개 페이지에 표시하지 않으며 구독자 알림에도 포함하지 않습니다. 서비스 카탈로그에서 제외할 때는 보관 처리합니다.
기존 이벤트 기록은 그대로 유지합니다.

공개 페이지에는 각 구성 요소의 상태와 최근 90일간의 상태 막대가 표시됩니다. 각
막대 아래에는 **90일 전**, 해당 구성 요소의 가동률, **오늘**이 표시됩니다. 구성 요소의
설명은 이름 옆 ⓘ 아이콘의 툴팁에서 확인할 수 있습니다.

### 구성 요소 그룹

폴더에 파일을 모으듯 관련 구성 요소를 그룹으로 묶습니다. **구성 요소 추가**를 선택하고 유형을
**그룹**으로 지정한 다음 이름과 설명을 입력합니다. 그룹에 넣을 각 구성 요소의
설정에서 **그룹** 항목에 해당 그룹을 선택합니다.

- 그룹에는 자체 상태가 없습니다. 구성 요소 중 가장 나쁜 상태를 그룹 상태로 표시하며, 상태 막대에도
  날짜별로 구성 요소 중 가장 나빴던 상태를 표시합니다.
- 공개 페이지에서는 그룹을 구성 요소 수와 함께 한 행에 표시합니다. 그룹을 펼치면
  각 구성 요소를 볼 수 있습니다. 정상 작동하지 않는 구성 요소가 하나라도 있으면 그룹을 펼친 상태로 표시합니다.
- 그룹에는 구성 요소만 넣을 수 있으며 다른 그룹은 넣을 수 없습니다. 인시던트, 유지보수, 구독, 자동화
  규칙에는 구성 요소를 지정하며, 그룹 자체는 선택하지 않습니다.
- **위로 이동**과 **아래로 이동**으로 그룹 안에서 구성 요소의 순서를 바꾸거나,
  최상위 목록에서 그룹의 순서를 바꿉니다.
- 그룹의 모든 구성 요소를 다른 곳으로 옮기거나 보관 처리한 후에 그룹을 보관 처리합니다.

### 종속성

구성 요소는 기술 서비스, 신세틱 검사, 알림 규칙에 종속될 수 있습니다. 종속 항목이 전달하는 상태 중
가장 나쁜 상태를 구성 요소의 상태로 산정합니다. MoleSignal은 알림 인시던트나
신세틱 검사에 변경이 생기면 몇 초 이내에 상태를 산정하며, 변경이 없어도 1분마다 산정합니다. 구성 요소 설정의
**종속성**에서 종속 항목을 추가합니다.

| 유형 | 대상 | 전달하는 상태 |
|---|---|---|
| **기술 서비스** | 트레이스와 알림에 표시되는 서비스 이름입니다. | 미해결 알림 인시던트 중 `service`, `service.name`, `service_name` 라벨에 해당 서비스 이름이 있거나 쿼리 결과에 해당 서비스가 포함된 인시던트의 가장 나쁜 상태입니다. 이름을 비교할 때는 대소문자를 구분하지 않습니다. |
| **신세틱 검사** | 신세틱 검사입니다. | 검사에 실패하면 **주요 중단**, 검사 상태가 저하되면 **성능 저하**를 전달합니다. 결과가 불안정하거나 아직 실행하지 않았거나 일시 중지 또는 보관 처리한 검사는 상태를 전달하지 않습니다. |
| **알림 규칙** | 알림 규칙입니다. | 해당 규칙의 미해결 알림 인시던트 중 가장 나쁜 상태를 전달합니다. |

알림 인시던트는 심각도에 따라 상태를 전달합니다. **심각**은 주요 중단, **오류**는 부분
중단, **경고**는 성능 저하에 해당합니다. **정보**는 상태에 영향을 주지 않으며, 알림을 음소거한 인시던트는
제외합니다. 각 종속 항목에는 **상태 그대로 전달**을 적용하거나, 구성 요소가 해당 종속 항목의 문제를
우회할 수 있으면 **최대 성능 저하**를 적용합니다. 구성 요소에는 종속 항목을 최대 100개까지 추가할 수 있으며, 그룹에는 직접 추가할 수 없습니다.

산정한 상태를 구성 요소에 반영하는 방식은 다음과 같습니다.

| 모드 | 동작 |
|---|---|
| **종속 항목 상태 반영** | 구성 요소 상태에 산정 결과를 반영합니다. **구독자에게 알림 보내기**로 상태 변경을 구독자에게 알릴지 정합니다. 수동으로 설정한 상태는 산정 결과가 다시 바뀔 때까지 유지합니다. |
| **자동화 규칙 적용** | 페이지의 자동화 규칙은 산정 결과의 변경을 트리거로 사용합니다. 규칙에 지정한 지연 시간, 승인 조건, 문구에 따라 인시던트를 게시합니다. |

구성 요소 설정에서 마지막으로 산정한 상태와 그 상태를 결정한 종속 항목을 확인할 수 있습니다.

## 인시던트 수명 주기

인시던트 초안을 만들고, 영향을 받는 구성 요소를 선택해 영향 수준을 설정한 다음 고객에게 전달할 첫
업데이트를 작성합니다. 게시하면 이벤트가 공개되고 해당 이벤트를 구독하는 구독자에게 업데이트를 보냅니다.

<Steps>
  <Step title="조사 중">
    증상을 확인하고 팀에서 조사 중임을 알립니다.
  </Step>
  <Step title="원인 파악 또는 조치 중">
    파악한 원인이나 현재 진행 중인 조치를 설명합니다.
  </Step>
  <Step title="모니터링 중">
    서비스가 복구되었으며 팀에서 안정성을 확인 중임을 알립니다.
  </Step>
  <Step title="해결됨">
    종료 업데이트를 게시합니다. MoleSignal은 구성 요소의 상태를 복원하고 전체 인시던트 기록을 한 행으로
    **기록**에 추가합니다.
  </Step>
</Steps>

고객에게 게시한 업데이트는 변경할 수 없습니다. 인시던트가 계속 진행 중이면 이미 전달한 메시지를 수정하지 말고
새 업데이트를 추가합니다.

### 다음 업데이트 및 알림

업데이트를 게시할 때마다 다음 업데이트 시점을 안내할 수 있습니다. 게시할 때 **다음 업데이트**에서 15분 또는 30분
이내, 1시간, 2시간, 4시간 또는 24시간 이내, 또는 **다음 업데이트 시점 미지정**을 선택합니다. 공개 페이지의
인시던트와 진행 중인 이벤트 안내에 선택한 시점을 표시하고, 이메일과 웹훅에도 포함합니다.
이벤트를 종료하는 업데이트와 예약만 된 유지보수에는 다음 업데이트 시점을 지정하지 않습니다. API에서는
현재 시점보다 1분 이상 7일 이내인 `next_update_at` 값을 마이크로초 단위로 보냅니다.

**구독자에게 알림 보내기**로 업데이트를 구독자에게 보낼지 정합니다. 문구만
수정할 때는 이 옵션을 끕니다. 페이지에만 변경 사항을 반영하고 구독자에게는 알림을 보내지 않습니다. 작업 공간의 타임라인에는
해당 업데이트를 **구독자에게 알리지 않음**으로 표시합니다. 구성 요소 상태를 수동으로 변경할 때도
같은 옵션이 표시됩니다. API에서는 `"notify": false`.

## 유지보수 수명 주기

공개 제목, 시작 시간, 영향받는 구성 요소, 고객 안내를 지정해 유지보수를 생성합니다.
유지보수에는 예정된 시작 시간만 있고 예정된 종료 시간은 없으므로, 예상 소요 시간을
고객 안내에 명시합니다. **예정됨** 상태로 게시하고 **완료** 또는 **취소됨** 상태로 종료합니다.
종료된 유지보수는 **기록**에 한 행으로 표시됩니다.

예정된 유지보수는 예정된 시작 시간에 자동으로 시작할 수 있습니다. 각 유지보수에는 두 가지
옵션이 있으며, 둘 다 기본적으로 켜져 있습니다.

| 옵션 | API 필드 | 기본값 | 동작 |
|---|---|---|---|
| 자동 시작 | `auto_start` | `true` | 예정된 시작 시간에 유지보수 상태를 **진행 중**으로 변경하고 페이지의 기본 언어로 업데이트를 게시합니다. 다른 업데이트와 마찬가지로 구독자에게 알림을 보냅니다. |
| 미리 알림 | `reminder_minutes` | `60` | 예정된 시작 시간보다 지정한 분만큼 앞서 구독자에게 미리 알림을 보냅니다. 미리 알림은 타임라인에 추가하지 않습니다. `0`으로 설정하면 미리 알림을 보내지 않으며, 최대 10080분 전에 보낼 수 있습니다. |

자동 시작을 끈 경우 작업을 시작할 때 유지보수 상태를 **진행 중**으로 변경합니다.

미리 알림을 보낼 시간이 지난 뒤 유지보수를 공지하거나 일정을 변경하면 미리 알림을 보내지 않습니다.
구독자에게 방금 알렸기 때문입니다. 일정을 변경하면 예정된 시작 시간에 맞춰 미리 알림 시간도 변경합니다.
편집 시 두 옵션을 모두 지정하지 않으면 기존 값을 유지합니다. MoleSignal은 예정된 시작 시간을 약
30초마다 확인합니다.

## 사후 분석

게시된 인시던트에는 발생한 일, 원인, 후속 변경 사항을 Markdown으로 작성한 사후 분석을 하나 추가할 수 있습니다.
**인시던트** 또는 **기록**에서 인시던트를 열고 다음 항목에 사후 분석을 작성합니다.
**사후 분석**. **미리보기**에서 독자에게 표시되는 내용을 확인합니다.

| 작업 | 권한 | 결과 |
|---|---|---|
| **초안 저장** | <code>status_pages.events.manage</code> | 작성한 내용을 공개하지 않고 저장합니다. 인시던트가 진행 중일 때도 초안을 작성할 수 있습니다. |
| **인시던트 사후 분석 게시** | <code>status_pages.events.publish</code> | 인시던트를 해결한 후에 사용할 수 있습니다. 사후 분석은 인시던트 페이지의 업데이트 아래에 표시되며, 공개 기록의 해당 인시던트 행에는 **사후 분석**이 표시됩니다. **구독자에게 알림 보내기**를 켜면 구독자에게 사후 분석을 보냅니다. |
| **수정본 게시** | <code>status_pages.events.publish</code> | 게시된 내용을 교체하고 수정 시점을 기록합니다. 수정본을 게시할 때 **구독자에게 알림 보내기**는 기본적으로 꺼져 있습니다. |
| **초안으로 되돌리기** | <code>status_pages.events.publish</code> | 공개 페이지에서 사후 분석을 내립니다. |
| **초안 삭제** | <code>status_pages.events.manage</code> | 게시되지 않은 사후 분석을 삭제합니다. |

사후 분석은 최대 20,000자까지 작성할 수 있습니다. 이메일과 웹훅은 작성한 Markdown 텍스트를 그대로 전송합니다.

## 기록

기록에는 해결된 인시던트와 완료되거나 취소된 유지보수 등 종료된 이벤트만
표시됩니다. 각 행에는 이벤트 하나의 유형, 제목, 최종 상태, 영향받는
구성 요소, 날짜가 표시됩니다. 검색과 유형, 상태, 구성 요소, 날짜 필터를 사용하고 페이지 단위로 결과를 확인합니다.
제목을 선택하면 표를 펼치지 않고도 이벤트 타임라인과 업데이트를 열 수 있습니다.

보존 기간 설정에 따라 공개 인시던트 기록에서 최근 1~365일의 내역을 조회할 수 있습니다.
이 설정을 변경해도 개요에 이벤트를 무제한으로 표시하지는 않습니다.

## 구독자 및 알림 전송

공개 페이지 방문자는 **구독**을 선택하고 이메일 주소, 웹훅 또는 Slack
채널을 등록할 수 있습니다. 모든 채널은 확인을 거친 후 활성화됩니다. 관리 화면에서는 구독 기록을 대기 중,
활성, 구독 해지로 구분하고 각 구독자가 어떤 업데이트를 받는지 표시합니다.

같은 대화 상자의 **RSS 피드**에서는 별도의 확인 없이 피드 리더에 추가할 수 있도록 두 가지 형식으로 페이지 피드를 제공합니다.
RSS 2.0은 `/api/v1/public/status-pages/<slug>/feed.rss`에서, Atom 1.0은
`/api/v1/public/status-pages/<slug>/feed.atom`에서 제공합니다. 두 피드 모두 페이지의 최근 인시던트와 유지보수
일정을 합쳐 최대 100건을 제공하며, 각 항목의 최신 업데이트를 포함합니다. 비공개 페이지는 피드를 제공하지 않습니다.

구성 요소가 둘 이상인 페이지에서는 **페이지 전체** 또는 **일부 구성 요소**를 선택할 수 있습니다.
일부 구성 요소를 구독하면 선택한 구성 요소 중 하나 이상이 명시된 업데이트만 받습니다. 구성 요소 그룹 이름은
해당 구성 요소 위에 제목으로 표시됩니다. 모든 이메일 하단에는 구독을 관리하는 링크와
구독을 해지하는 링크가 있습니다. 관리 링크를 열면 페이지에 **구독 관리**가 표시되며,
여기에서 구성 요소를 변경하거나 구독을 해지할 수 있습니다. 이미 활성 상태인 이메일 주소를
등록하면 새 확인 이메일 대신 **업데이트 구독 관리** 이메일을 보냅니다.

### Slack

| 방법 | 절차 |
|---|---|
| 수신 웹훅 | 채널을 **Slack**으로 설정하고 Slack 채널의 수신 웹훅 URL(`https://hooks.slack.com/...`)을 붙여넣은 후 **확인 요청 보내기**를 선택합니다. 채널에 확인 요청 메시지가 게시됩니다. |
| **Slack에 추가** | 페이지의 **설정 → Slack**에서 Slack 앱을 지정하면 표시됩니다. 방문자는 Slack에서 채널을 선택한 후 페이지로 돌아옵니다. 채널은 즉시 구독을 시작하고 환영 메시지를 받습니다. 비공개 페이지에서는 이 옵션을 제공하지 않습니다. |

Slack 메시지는 제목을 헤더로 표시하고 업데이트 본문과 함께
페이지를 열거나 구독을 관리하는 버튼을 제공합니다.

**Slack에 추가**를 제공하려면 다음과 같이 설정합니다.

1. Slack에서 `incoming-webhook` 범위를 가진 앱을 만듭니다. **OAuth & Permissions → Redirect
   URLs**에 페이지의 **설정 → Slack**에 표시된 리디렉션 URL인
   `<http.external_url>/api/v1/public/slack/callback`을 추가합니다. `http.external_url`은 `https`
   주소여야 합니다.
2. **설정 → 알림 → 커넥터**에서 앱의 클라이언트 ID와
   클라이언트 시크릿을 사용해 **Slack 앱** 커넥터를 만듭니다. 클라이언트 시크릿은 암호화하여 커넥터에 저장합니다.
   [알림 채널](/ko/notification-channels#slack-앱)을 참조합니다.
3. 페이지의 **설정 → Slack**에서 커넥터를 선택하고 저장합니다.

한 조직의 여러 페이지에서 커넥터 하나를 공유할 수 있습니다. 페이지에서 지정한 커넥터는 삭제할 수 없으며,
커넥터를 끄면 해당 페이지에서 **Slack에 추가**를 제공하지 않습니다. **꺼짐**을 선택해도
이 옵션을 제공하지 않습니다. 두 경우 모두 이미 추가한 채널은 계속 업데이트를 받습니다.

### 구독자 가져오기

**구독자 → 구독자 가져오기**에서 다른 상태 페이지의 이메일 구독자를 가져옵니다.
CSV 파일을 선택하거나 파일 내용을 붙여넣습니다.

- 첫 행은 헤더로 사용할 수 있으며, `email`과 `components` 열은 순서에 관계없이 지정할 수 있습니다.
  헤더가 없으면 첫 번째 열에 이메일 주소를, 두 번째 열에 구성 요소 이름을 적습니다.
- 구성 요소는 이름으로 지정하고 `;`로 구분합니다. 그룹 이름을 지정하면 해당 그룹의
  구성 요소가 모두 포함됩니다. 셀을 비워 두면 해당 주소로 페이지 전체를 구독합니다.
- 한 번에 최대 10,000개의 주소를 가져올 수 있으며, 최대 크기는 2 MB입니다.

| 시작 방식 | 결과 |
|---|---|
| **즉시 활성화** | 기존 페이지에서 구독을 확인한 주소에 사용합니다. 구독을 즉시 활성화하며 이메일은 보내지 않습니다. |
| **구독 확인 요청** | 각 주소로 확인 이메일을 보내고, 구독을 확인할 때까지 대기 상태를 유지합니다. 이메일 전송을 미리 설정해야 합니다. |

**파일 확인**은 실제 변경 없이 가져오기 결과를 미리 보여 줍니다. 읽은 행, 가져올
주소, 이미 구독 중인 주소, 이전에 구독을 해지하여 건너뛸 주소를 표시합니다.
문제가 있는 행은 줄 번호와 함께 표시합니다. 주소 누락, 잘못된 이메일 주소, 파일 내 중복 주소,
페이지에 없는 구성 요소가 문제에 해당합니다.

이메일 구독자는 페이지의 기본 언어로 작성한 일반 텍스트 이메일로 각 업데이트를
받습니다. 이메일의 상태 이름은 **성능 저하**와 같이 페이지에 표시된 레이블과 일치합니다.

| 이메일 | 제목 | 본문 |
|---|---|---|
| 구독 확인 | `Confirm updates from <page name>` | 확인 링크와 구독 해지 링크입니다. |
| 구성 요소 상태 변경 | `<page name>: <component> · <status>` | 구성 요소, 변경된 상태, 페이지 주소입니다. |
| 인시던트 업데이트 | `<page name>: <title> · <status>` | 제목, 상태, 고객에게 공개하는 업데이트 내용, 페이지 주소입니다. |
| 유지보수 업데이트 | `<page name>: <title> · <status>` | 인시던트 업데이트와 같은 항목에 더해 **예정 일시**에 유지보수 시작 예정 시간을 표시합니다. |
| 유지보수 알림 | `<page name>: <title> · Reminder` | 제목, **예정 일시**에 표시한 시작 예정 시간, 페이지 주소입니다. |
| 구독 관리 | `Manage your updates from <page name>` | 구독 관리 링크입니다. |
| 사후 분석 | `<page name>: Postmortem · <title>` | Markdown 형식의 사후 분석과 인시던트 주소입니다. |

다음 업데이트 시점을 안내하는 업데이트에는 **다음 업데이트 기한**과
페이지의 시간대를 기준으로 한 시간이 표시됩니다. 확인 이메일을 제외한 모든 이메일 하단에는 구독 관리 및 해지 링크가 있습니다.

**예정 일시**는 페이지의 시간대를 사용하고 UTC 오프셋을 함께 표시합니다. 예:
`2026-05-25 12:00 UTC+02:00 (Europe/Berlin)`.

웹훅 구독자는 각 업데이트를 JSON 요청으로 받습니다. 요청 형식,
페이로드 필드, 재시도 일정은
[상태 페이지 웹훅 구독](/ko/status-pages/webhooks)을 참조합니다.

인시던트 또는 유지보수 업데이트를 게시할 때마다 알림 대상
구독자에 대해 처리 범위가 제한된 전송 작업을 생성합니다. **구독자**에는 전송 시도, 성공 여부, 마지막 오류, 재시도 상태가 표시됩니다. 전송 이력의
보존 기간은 30일, 60일, 90일, 180일, 365일 중에서 설정할 수 있습니다.

## 비공개 액세스

비공개 페이지에서는 이메일 주소와 이메일 도메인으로 허용 목록을 설정할 수 있습니다. 허용 목록에 포함된 방문자가
일회용 매직 링크를 요청해 사용하면 1일, 7일 또는 30일 동안 유효한 상태 페이지 세션을 받습니다.
링크가 담긴 이메일은 페이지의 기본 언어로 작성하며, 링크는 15분 동안 유효합니다.
관리자는 활성 세션을 즉시 취소할 수 있습니다. 비공개 액세스는 공개 페이지,
아카이브, 이벤트 상세 페이지, 구독 절차에 적용됩니다.

## 사용자 지정 도메인 및 TLS

도메인을 추가하기 전에 <code>http.external_url</code>을 외부에서 실제로 접속할 수 있는 MoleSignal URL로 설정합니다.
그러면 도메인 패널에 소유권 확인과 라우팅에 필요한 정확한 DNS 레코드가 표시됩니다.

도메인 상태는 **DNS 대기 중**, **확인 중**, **검증됨**, **TLS 프로비저닝 중**,
**활성** 순으로 진행됩니다. **실패** 또는 **성능 저하** 상태에서는 문제 해결에 필요한 원인과 재시도 옵션을 표시합니다.

MoleSignal이 자동으로 관리하는 인증서로 사용자 지정 호스트 이름을 제공하도록
<code>http.tls</code>를 활성화하고 계정 이메일을 설정합니다.

```toml
[http]
external_url = "https://molesignal.example.com"

[http.tls]
enabled = true
account_email = "ops@example.com"
```

외부 로드 밸런서에서 TLS를 종료하는 경우 공개 URL과 DNS 대상을 올바르게 유지하고
해당 로드 밸런서에서 인증서를 관리합니다.

## 게시 자동화

운영 이벤트를 고객 공지로 게시하려면 **설정 → 자동화**를 엽니다.

1. 소스로 **알림 인시던트**, **신세틱 검사**, **컴포넌트 종속성** 중 하나를 선택합니다.
2. 리소스, 최소 심각도 또는 모니터 상태 전환, 필수 레이블을 선택합니다.
3. 일시적인 장애로 고객 공지가 생성되지 않도록 지연 시간을 설정합니다.
4. 이벤트의 영향도와 영향을 받는 상태 페이지 컴포넌트를 매핑합니다. 컴포넌트를 지정하지 않은 **컴포넌트 종속성** 규칙은
   종속성이 변경된 컴포넌트가 해당 변경 사항을 자동화 규칙에 전달하면 그 컴포넌트에 공지를 게시합니다.
   규칙의 템플릿에서 컴포넌트 이름은
   `{{labels.component_name}}`으로, 현재 및 이전 종속성 상태는 `{{labels.dependency_status}}`와
   `{{labels.previous_dependency_status}}`로 표시할 수 있습니다.
5. **수동 승인** 또는 **자동 게시**를 선택하고 메시지 템플릿을 정의합니다.
6. 규칙을 활성화하기 전에 시뮬레이터에서 테스트합니다.

설정된 순서에서 모든 조건을 충족하는 첫 번째 규칙이 이벤트를 처리합니다. 상관관계 키는 이후 소스의
상태 전환을 같은 인시던트에 연결합니다. 수동 모드에서는 권한이 있는 사용자가
승인, 거부 또는 편집할 수 있는 게시 후보를 생성합니다. 자동 모드에서는 생성된 이벤트를 바로 게시합니다. **모든
자동화 일시 중지**는 새 이벤트에 대한 규칙 매칭을 중단하며, 이미 공개된 이벤트는 변경하지 않습니다.

<Note>
대응 담당자가 관리하는 탐지에는 알림 인시던트를 사용하고, 고객 이용 경로를 직접 검사하려면 신세틱
모니터를 사용합니다. 두 소스 모두 같은 컴포넌트 모델을 업데이트할 수 있지만, 각 규칙에는 별도의 승인 및
지연 정책이 적용됩니다.
</Note>
