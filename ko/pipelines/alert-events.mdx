**경보 파이프라인**은 인시던트가 생성되기 전에 경보 이벤트를 처리합니다. 각 단계에서는 인시던트 제목이나 심각도를 변경하고, 레이블과 주석을 추가하거나 삭제하고, 영향을 받는 서비스를 지정하거나, 이벤트를 폐기해 인시던트가 생성되지 않도록 할 수 있습니다. 이후 [라우팅](/ko/alerting/routing)과 알림은 파이프라인 처리 결과가 반영된 인시던트를 기준으로 동작합니다.

경보 이벤트는 다음 네 가지 소스 중 하나에서 발생합니다.

| 소스 | 이벤트 |
|---|---|
| **알림 규칙** | [알림 규칙](/ko/alerting/rules)이 발동합니다. |
| **외부 소스** | [경보 소스](/ko/alerting/sources)가 다른 시스템에서 경보를 수신합니다. |
| **합성 검사** | [합성 검사](/ko/synthetics#알림-인시던트)가 실패하거나 결과가 없습니다. |
| **데이터 없음** | 규칙이 [데이터 없음 인시던트](/ko/alerting/rules#복구-및-데이터-누락)를 생성합니다. |

인시던트를 수동으로 생성할 때는 생성 전에 경보 파이프라인을 실행하지 않습니다.

파이프라인은 [알림 전송 전](#알림-전송-전)에도 실행할 수 있습니다. 이때는 이벤트의 복사본을 처리하며, 해당 알림 정책이 전송하는 내용만 변경합니다.

## 경보 파이프라인 만들기

**파이프라인**을 열고 **새 파이프라인**을 선택한 다음, **실행 모드**를 **경보 이벤트**로 설정합니다. **신호 유형**에 **경보 이벤트**가 표시되며, 설정에서는 일정 대신 [**순서**](#순서)를 지정합니다. 흐름은 세 개의 노드로 구성됩니다.

| 노드 | 의미 |
|---|---|
| **경보 이벤트** | 파이프라인에서 처리할 경보 이벤트입니다. [조건](#조건)을 참조합니다. |
| **처리 중** | 각 단계를 실행 순서대로 표시합니다. [단계](#단계)를 참조합니다. |
| **인시던트에 반영** | 각 단계에서 처리한 이벤트를 바탕으로 인시던트를 생성합니다. |

**테스트**에서는 저장하기 전에 샘플 경보 이벤트로 각 단계를 실행합니다. 각 단계는 이 이벤트를 인시던트 생성 직전의 알림 규칙 이벤트로 처리합니다. 이때 `%source`는 `rule`이고 `%event`는 `opened`입니다. 다른 값을 테스트하려면 **샘플 이벤트**를 편집한 다음 **테스트 실행**을 선택합니다. 결과에는 각 단계의 처리 직후 이벤트가 표시되며, 이벤트가 폐기되면 해당 단계가 표시됩니다. 테스트는 데이터를 저장하거나 외부 서비스를 호출하지 않습니다. **AI 요약**과 **쿼리 결과 추가** 단계는 각각의 주석에 `…`를 기록하고, **API 호출** 단계는 이벤트를 변경하지 않고 다음 단계로 넘기며 **테스트에서는 호출되지 않음**으로 표시합니다.

**최근 알림 이벤트 사용**에서는 `alerts.incidents.read` 권한으로 최근 7일간의 인시던트 중 최신 20개를 조회할 수 있습니다. 인시던트를 선택하면 해당 이벤트가 **샘플 이벤트**에 채워지고, 각 단계는 이벤트의 규칙과 소스를 읽습니다. 저장된 상태의 인시던트를 사용하므로 생성 시 파이프라인에서 처리한 결과가 이미 반영되어 있습니다.

설정의 **경보 이벤트 처리** 스위치로 파이프라인을 켜거나 끕니다. 파이프라인을 끄면 모든 경보 이벤트가 처리 없이 통과합니다. 저장하려면 **파이프라인 만들기**를 선택합니다. 저장한 변경 사항은 10초 이내에 모든 노드에 반영됩니다.

## 조건

**경보 이벤트** 노드를 선택하여 파이프라인에서 처리할 이벤트를 지정합니다.

- **소스**: **알림 규칙**, **외부 소스**, **합성 검사**, **데이터 없음**. 규칙이 생성한 데이터 없음 인시던트는 **알림 규칙**이 아닌 **데이터 없음**으로 분류합니다. 합성 검사에서 결과가 없어 생성된 인시던트는 **합성 검사**로 분류합니다.
- **심각도**: **심각**, **오류**, **경고**, **정보**.
- **레이블**: **레이블 조건 추가**를 선택하여 레이블과 값을 추가합니다. 이벤트에는 조건에 지정한 모든 레이블이 있어야 하며 각 값이 정확히 일치해야 합니다.
- **시간**: **시간 제한 없음**, **지정 시간대에만 적용**, **지정 시간대 외에만 적용** 중에서 선택합니다. 시간 범위는 하나의 표준 시간대를 기준으로 주 단위로 지정하며, 인시던트가 생성되는 시점을 기준으로 판단합니다. 예를 들어, 매일 밤 ETL 작업이 실행되는 두 시간 동안에만 특정 유형의 경보를 폐기할 수 있습니다.

조건 위의 **실행 시점**에서 파이프라인을 언제 실행할지 지정합니다. 기본값은 **인시던트 생성 전**이며, [**알림 전송 전**](#알림-전송-전)으로 변경할 수 있습니다.

소스 또는 심각도 목록에서 아무 항목도 선택하지 않으면 해당 목록의 모든 항목이 대상이 됩니다. 조건이 없는 파이프라인은 모든 경보 이벤트를 처리합니다. 조건과 일치하지 않는 이벤트는 변경 없이 파이프라인을 통과합니다.

## 순서

경보 파이프라인은 **순서** 값이 낮은 것부터 차례대로 실행합니다. 순서 값이 같으면 이름순으로 실행합니다. 각 파이프라인은 앞선 파이프라인에서 처리한 이벤트를 받아 조건과 대조합니다. 따라서 앞선 파이프라인에서 심각도를 높이면 이벤트가 이후 파이프라인의 조건을 충족할 수 있습니다.

## 단계

**단계 추가**에서는 다른 파이프라인의 파싱 및 필드 처리 단계(**확장 테이블 조회** 포함)뿐 아니라 **이벤트 필터링**, **AI 요약**, **API 호출**, **쿼리 결과 추가**, **사용자 지정 VRL**도 선택할 수 있습니다. [처리 단계](/ko/pipelines#처리-단계)를 참조합니다. 알림 파이프라인에서 **패턴으로 이름 변경**과 **지정한 필드만 유지**는 `labels`를 대상으로 시작합니다. 알림 파이프라인은 샘플링이나 라우팅을 수행하지 않습니다. 기존 파이프라인을 알림 파이프라인으로 전환할 때 **샘플링 비율** 또는 **스트림으로 라우팅** 단계가 있다면 저장하기 전에 제거해야 합니다.

### 알림 이벤트

각 단계는 알림 이벤트를 JSON으로 읽습니다.

```json
{
  "summary": "Checkout error rate above 5%",
  "severity": "error",
  "labels": { "service": "checkout", "env": "prod", "host_name": "web-01" },
  "annotations": { "runbook": "https://wiki.example.com/checkout" },
  "affected_services": ["checkout"]
}
```

| 필드 | 내용 | 단계에서 설정할 수 있는 값 |
|---|---|---|
| `summary` | 인시던트 제목입니다. | 비어 있지 않은 텍스트입니다. 512자를 초과하는 부분은 잘라냅니다. |
| `severity` | 인시던트 심각도입니다. | `info`, `warning`, `error`, `critical` 중 하나이며 대소문자를 구분하지 않습니다. `warn`은 `warning`으로, `crit`은 `critical`로 처리합니다. |
| `labels` | 인시던트 레이블입니다. | 텍스트 값을 담은 객체입니다. 숫자와 불리언은 텍스트로 변환하며, `null`을 지정하면 해당 레이블을 제거합니다. |
| `annotations` | 인시던트 주석입니다. | `labels`와 동일합니다. |
| `affected_services` | 영향을 받는 서비스의 이름입니다. | 이름 목록입니다. 중복되거나 비어 있는 이름은 제외합니다. |

단계에서 위 목록에 없는 필드를 추가해도 결과에 포함하지 않습니다. 단계를 통해 필드를 제거해도 기존 값은 유지됩니다. 레이블을 모두 지우려면 `.labels = {}`를 설정합니다. `labels`의 값으로 객체를 지정하는 등 규칙에 맞지 않는 값을 사용하면 파이프라인이 실패합니다. [이벤트 처리 결과](#이벤트-처리-결과)를 참조합니다.

`alert.source`, `external.kind`처럼 MoleSignal이 직접 설정한 레이블은 인시던트의 출처를 나타내므로 단계에서 변경해도 원래 값을 유지합니다. 각 단계는 이 레이블을 읽을 수 있습니다.

### 이벤트 출처

각 단계는 메타데이터에서 이벤트 출처를 읽습니다. 이 값은 인시던트 필드에 포함하지 않습니다.

| 메타데이터 | 값 |
|---|---|
| `%source` | `rule`, `external`, `synthetic`, `no_data` 중 하나입니다. |
| `%rule_id` | 규칙, 알림 소스 또는 신세틱 검사 ID입니다. |
| `%rule_name` | 규칙, 알림 소스 또는 신세틱 검사 이름입니다. |
| `%event` | 인시던트를 열기 전에는 `opened`, 인시던트가 열린 상태에서 소스가 다시 트리거되면 `severity_changed`입니다. [심각도 변경](#심각도-변경)을 참조합니다. |

```ruby
# alerts from staging page no higher than warning
if .labels.env == "staging" && (.severity == "critical" || .severity == "error") {
  .severity = "warning"
}

# the team that owns the host, from the extend table host_owner
owner = lookup("host_owner", .labels.host_name)
if is_object(owner) {
  .labels.team = owner.team
}

# a known false alarm opens no incident
if %rule_name == "Disk inode usage" && .labels.mount == "/boot" {
  abort
}
```

두 번째 단계에서 설정한 `team` 레이블을 사용해 해당 팀으로 인시던트를 라우팅할 수 있습니다. [라우팅 순서](/ko/alerting/routing#라우팅-순서)를 참조합니다. 알림 파이프라인에서도 다른 VRL 단계와 동일하게 `lookup`과 `geoip_lookup`을 사용할 수 있습니다. [테이블 및 IP 주소 조회](/ko/functions#테이블과-ip-주소-조회)를 참조합니다.

### AI 요약

**AI 요약** 단계는 이전 단계에서 처리한 알림 이벤트를 **프롬프트**와 함께 조직의 모델에 보냅니다. 응답은 **주석**에 지정한 이름으로 기록합니다. 기본 이름은 `ai_summary`입니다. 다음은 프롬프트 예시입니다.

```text
Summarize this alert for the on-call engineer in two sentences: what is wrong, and what to check first.
```

- 인시던트가 열릴 때 모델을 한 번만 호출합니다. [심각도가 변경되어도](#심각도-변경) 다시 호출하지 않습니다.
- API 키가 설정된 활성 [모델 제공업체](/ko/agent#모델-공급자-설정) 중 가장 최근에 업데이트한 제공업체의 **기본 모델**을 사용합니다. 응답은 제공업체의 **최대 출력 토큰 수**를 넘지 않습니다. 설정하지 않은 경우 최대 512토큰입니다.
- 알림의 제목, 심각도, 레이블, 주석, 영향을 받는 서비스 목록을 모델 제공업체에 보냅니다.
- 호출에 사용한 토큰은 조직의 [일일 토큰 예산](/ko/agent#사용량-및-예산)에 포함합니다. 소스별 사용량에는 **LLM 함수**로 표시합니다. 이 호출에는 `[functions].llm_eval_enabled`를 적용하지 않습니다.
- 모델 제공업체를 설정하지 않았거나 일일 예산을 소진했거나 호출에 실패해 모델이 응답하지 못하면, 이 단계와 전체 파이프라인이 실패합니다. 다른 변경 사항도 적용하지 않습니다. AI 요약의 성공 여부와 관계없이 다른 변경 사항을 유지하려면 **AI 요약** 단계를 별도 파이프라인에 추가하고 다른 파이프라인보다 뒤에 실행되도록 배치합니다.

### API 호출

**API 호출** 단계는 조직의 [HTTP 커넥터](/ko/connectors#대상) 중 하나로 알림 이벤트를 POST하고 응답에 담긴 변경 사항을 적용합니다. 커넥터의 주소와 인증 정보를 사용하고 아웃바운드 검사도 적용합니다. 먼저 호스트 주소를 확인한 후 해당 주소로만 연결하며, 클라우드 메타데이터 주소는 차단하고 리디렉션은 따르지 않습니다.

요청 본문에는 이전 단계에서 처리한 이벤트의 필드와 이벤트 출처를 함께 담습니다.

```json
{
  "summary": "Checkout error rate above 5%",
  "severity": "error",
  "priority": null,
  "urgency": null,
  "labels": { "service": "checkout" },
  "annotations": {},
  "affected_services": ["checkout"],
  "metadata": { "rule_id": "…", "rule_name": "Checkout errors", "source": "rule", "event": "opened" }
}
```

- 응답 JSON 객체에서 `summary`, `severity`, `priority`, `urgency`, `labels`, `annotations`, `affected_services`만 가져오며, [알림 이벤트](#알림-이벤트)의 규칙을 적용합니다. `labels`와 `annotations`는 키별로 병합하고 값이 `null`인 키는 제거하므로, 서비스는 추가할 항목만 응답에 담을 수 있습니다. 응답이 비어 있으면 변경하지 않습니다.
- 호출 제한 시간은 5초이며 인시던트가 열릴 때 한 번 실행합니다. [심각도가 변경되어도](#심각도-변경) 다시 호출하지 않습니다.
- 호출에 실패하면 이 단계만 실행하지 않은 것으로 처리합니다. 제한 시간 내에 응답이 없거나, 상태 코드가 2xx가 아니거나, 본문이 JSON 객체가 아니거나 1 MiB를 초과하거나, 필드가 규칙을 위반하거나, 커넥터가 비활성화 또는 삭제된 경우에 해당합니다. 이벤트를 이 단계에 들어오기 전 상태로 다음 단계에 전달하며, 이전 단계의 변경 사항은 유지합니다. 실패 이유는 [타임라인](#이벤트-처리-결과)과 [집계](#일일-집계)에서 확인할 수 있습니다.

### 쿼리 결과 추가

**쿼리 결과 추가** 단계는 이벤트의 값을 사용해 쿼리를 실행하고 결과 행을 주석에 기록합니다.

```sql
SELECT count(*) AS errors FROM app_logs WHERE level = 'error' AND host = '{{labels.host_name}}'
```

| 필드 | 의미 |
|---|---|
| **언어** | SQL 또는 PromQL입니다. PromQL은 메트릭 스트림을 읽습니다. |
| **스트림 유형**, **스트림** | 쿼리가 읽을 스트림입니다. 이 단계에는 어떤 사용자의 `audit.read` 권한도 적용하지 않으므로 `_audit`를 읽을 수 없습니다. |
| **쿼리** | 자리 표시자를 포함하는 단일 쿼리입니다. |
| **조회 기간(초)** | 인시던트가 열린 시점을 기준으로 얼마나 이전까지 조회할지 지정합니다. 기본값은 300이며 최댓값은 86,400입니다. |
| **행** | 주석에 기록할 행 수입니다. 기본값은 5이며 최댓값은 50입니다. |
| **주석** | 결과 행을 기록할 주석의 이름입니다. 기본값은 `query_result`입니다. |

자리 표시자는 이벤트의 값을 나타냅니다. `{{labels.<key>}}`, `{{annotations.<key>}}`, `{{summary}}`, `{{severity}}`, `{{priority}}`, `{{urgency}}`, `{{rule_id}}`, `{{rule_name}}`, `{{source}}`를 사용할 수 있습니다. 레이블은 외부 시스템에서 가져올 수 있으므로 자리 표시자는 쿼리문의 따옴표로 감싼 문자열 안에만 배치해야 합니다. 이 위치에서는 자리 표시자에 대입하는 값을 이스케이프합니다. 다른 위치에 배치하면 저장 요청에 `400`을 반환합니다.

- 주석에는 결과 행마다 한 줄을 기록합니다. 값이 하나면 값만 기록하고, 여러 개면 `column=value, column=value` 형식으로 기록합니다. 최대 4,000자까지 기록합니다. 결과 행이 없으면 주석을 추가하지 않습니다.
- 쿼리 제한 시간은 10초이며 인시던트가 열릴 때 한 번 실행합니다.
- 쿼리가 실패하거나 이벤트에 자리 표시자에 해당하는 값이 없으면 [**API 호출**](#api-호출)과 마찬가지로 이 단계만 실행하지 않은 것으로 처리합니다.

## 이벤트 처리 결과

이벤트를 받는 각 파이프라인의 처리 결과는 다음 세 가지 중 하나입니다.

| 결과 | 원인 | 영향 |
|---|---|---|
| **처리 완료** | 모든 단계가 끝까지 실행되었습니다. | 변경 사항을 반영한 이벤트를 다음으로 넘깁니다. |
| **제외** | 한 단계에서 `abort`를 실행했습니다. | 인시던트를 개설하지 않으며 후속 파이프라인도 실행하지 않습니다. |
| **실패** | 단계가 실패했거나 단계 실행 후 [경보 이벤트](#알림-이벤트)의 규칙을 위반하는 필드가 남았습니다. **API 호출** 또는 **쿼리 결과 추가** 단계가 실패한 경우도 포함합니다. | 이 파이프라인의 변경 사항을 반영하지 않습니다. 단, **API 호출** 또는 **쿼리 결과 추가** 단계만 실패한 경우에는 다른 단계의 변경 사항을 유지합니다. 이벤트는 다음 파이프라인으로 넘어가며 인시던트는 정상적으로 개설됩니다. |

인시던트 [타임라인](/ko/alerting/incidents#인시던트-상세-정보)에는 이벤트를 변경했거나 실패한 파이프라인마다 행이 하나씩 표시됩니다. 예: **Payments routing 파이프라인 통과: 심각도 error → critical, 레이블 +team=payments**. 실패한 경우에는 실패 이유를 표시합니다. 변경 사항이 없는 파이프라인이나 [심각도 변경](#심각도-변경)에는 행을 추가하지 않습니다. 각 행에는 변경 사항을 최대 40개까지 표시하고 나머지는 개수로 표시합니다. 긴 값은 200자에서 자릅니다.

규칙이 계속 발동하면 평가할 때마다 다시 제외합니다. [규칙 목록](/ko/alerting/rules#규칙-목록)에는 규칙 상태가 **파이프라인에서 제외됨**으로 표시되며, API에서 `last_state` 값은 `{"kind": "dropped"}`입니다. 이벤트를 제외한 파이프라인은 이를 제외 건수에 반영하고 **개요**에 가장 최근에 제외한 규칙의 이름을 표시합니다. 파이프라인이 외부 경보를 제외하면 해당 경보 소스의 [**최근 수신 요청**](/ko/alerting/sources#최근-수신-요청)에 **무시됨** 상태와 함께 경보를 제외한 파이프라인 및 단계를 표시합니다.

## 심각도 변경

인시던트가 열려 있는 동안 경보 규칙이 다시 발동하거나, 외부 소스가 경보를 다시 보내거나, 신세틱 모니터링 점검의 상태가 바뀔 때마다 경보 파이프라인이 심각도를 다시 결정합니다.

- 인시던트를 개설할 때와 같은 방식으로 이벤트를 구성하되, 소스가 현재 보고하는 심각도를 사용합니다. 이벤트를 받는 파이프라인은 **AI 요약**, **API 호출**, **쿼리 결과 추가** 단계를 건너뛰고 실행하며, `%event` 값은 `severity_changed`입니다.
- 단계 실행 후의 심각도만 반영합니다. 기존 심각도와 다르면 인시던트의 심각도를 변경합니다. 제목, 레이블, 주석, 서비스는 인시던트를 개설할 때 설정한 값을 유지합니다.
- 파이프라인에서 이벤트를 제외하거나 파이프라인이 실패하면 아무것도 변경하지 않습니다. 인시던트는 열린 상태로 유지되며 다음 파이프라인을 실행합니다.

따라서 스테이징 환경 경보의 심각도를 낮추는 단계는 나중에 규칙이 더 높은 심각도를 보고해도 계속 심각도를 낮춥니다. 확인한 인시던트와 심각도를 수동으로 설정한 인시던트는 기존 심각도를 유지합니다.

## 알림 전송 전

**경보 이벤트** 노드에서 **실행 시점**을 **알림 전송 전**으로 설정하면 [알림 정책](/ko/notification-channels)이 경보 이벤트에 대한 알림을 보내기 직전에 파이프라인을 실행합니다. 적용 대상 정책마다 이벤트의 복사본에서 실행하며, 정책의 후속 단계나 에스컬레이션을 포함해 알림을 보낼 때마다 실행합니다. 인시던트 자체는 그대로 두고 SMS 정책의 제목을 줄이거나, 특정 팀의 웹훅에 레이블을 추가하거나, 야간에 특정 정책의 알림 전송을 막을 수 있습니다.

- **알림 정책**에서 파이프라인을 적용할 정책을 지정합니다. 아무 정책도 선택하지 않으면 경보 이벤트에 적용되는 모든 정책에서 파이프라인을 실행합니다. 이 시점에는 원본 이벤트를 기준으로 일치하는 정책을 이미 결정한 상태입니다.
- 나머지 조건은 이전과 같은 방식으로 알림에 사용되는 이벤트를 기준으로 평가합니다. 시간 조건에는 이벤트가 발생한 시각을 사용하며, **소스**에는 **수동으로 개설한 인시던트** 옵션이 추가됩니다.
- 단계는 MoleSignal 내부에서만 실행됩니다. **AI 요약**, **API 호출**, **쿼리 결과 추가**는 인시던트를 개설할 때만 실행합니다. 이 중 하나라도 포함한 파이프라인을 알림 전송 전에 사용하면 `400`을 반환합니다.
- 흐름은 **알림에 반영**에서 끝납니다. 정책은 단계 실행 후의 제목, 심각도, 우선순위, 긴급도, 레이블, 주석, 서비스를 [템플릿](/ko/notification-channels#템플릿-변수), 웹훅 본문, 기본 텍스트에 반영해 전송합니다. 수신자는 원본 이벤트를 기준으로 결정합니다.
- 단계에서 `abort`를 실행하면 해당 정책의 알림을 보내지 않습니다. 전송 로그에는 **건너뜀** 기록과 사유가 표시됩니다. 사유에는 워크스페이스의 기본 언어로 파이프라인과 단계의 이름을 표시합니다(`error_code`: `dropped_by_pipeline`). 인시던트 타임라인에도 이 내용을 표시합니다. 실패로 처리하지 않으므로 정책의 알림 전송을 재시도하지 않으며, 확인 시간 초과에 따른 에스컬레이션도 진행하지 않습니다.
- 파이프라인이 실패하면 변경 사항을 반영하지 않고 원래 내용으로 알림을 보냅니다. 실패는 타임라인에 표시하지 않고 [일일 집계](#일일-집계)에만 반영합니다.

각 단계에서는 `%rule_id`, `%rule_name`, `%source` 외에 `%policy_id`와 `%policy_name`도 읽을 수 있습니다. `%event` 값은 `triggered`, `escalated`, `acknowledged`, `resolved` 중 하나입니다. `%rule_name`은 규칙 이름이며, 규칙이 인시던트를 개설하지 않은 경우에는 이벤트 제목입니다. **테스트**는 샘플 값 `triggered`와 `On-call alerts`로 실행합니다.

```ruby
# on-call alerts of the staging environment go out only for what is critical
if %policy_name == "On-call alerts" && .labels.env == "staging" && .severity != "critical" {
  abort
}
```

## 일일 집계

경보 파이프라인에는 별도의 실행 기록이 없으므로 실행 내역이 표시되지 않으며 **더 보기 → 백필**을 사용할 수 없습니다. 대신 오늘(UTC)의 처리 결과를 집계합니다.

- 목록에서 활성화한 경보 파이프라인의 **상태**는 **알림 이벤트 대기 중**으로 표시됩니다. **마지막 실행** 열에는 **오늘: 처리 완료 41건 · 제외 3건 · 실패 0건**과 같이 집계 수치를 표시합니다.
- 파이프라인의 **개요**에서 **처리 완료**, **제외**, **실패**에 동일한 집계 수치를 표시합니다. **제외**에는 가장 최근에 제외한 이벤트의 규칙 또는 소스와 제외 시각을 표시합니다. **실패**에는 가장 최근의 실패 이유를 표시합니다.

집계는 UTC 자정에 0으로 초기화합니다. 조건에 일치하지 않는 이벤트와 [심각도 변경](#심각도-변경)을 위한 실행은 집계하지 않습니다. API는 집계 수치를 `alert_record`로 반환합니다. [파이프라인 관리](/ko/api/intake/scheduled-pipelines#조회)를 참조합니다.

## 제한

| 제한 항목 | 값 |
|---|---|
| 경보 파이프라인당 단계 수 | 20 |
| **AI 요약** 단계의 프롬프트 | 8 KiB |
| 주석 이름 | 255 bytes |
| **API 호출** 단계의 응답 | 1 MiB, 5 seconds 이내 |
| **쿼리 결과 추가** 단계의 쿼리문 | 8 KiB |
| **쿼리 결과 추가** 단계의 결과 행 수 | 50, 10 seconds 이내 |
| **쿼리 결과 추가** 단계가 작성하는 텍스트 길이 | 4,000자 |

## API로 경보 파이프라인 만들기

경보 파이프라인은 다른 파이프라인과 같은 방식으로 저장합니다. `functionSteps.mode`를 `alert`로 설정하고 스트림과 스케줄은 비워 둡니다.

```bash
curl -X POST http://localhost:5080/api/v1/scheduled_pipelines \
  -H "authorization: Bearer $MS_TOKEN" \
  -H 'content-type: application/json' \
  -d '{
    "name": "staging-alerts",
    "sourceStream": "",
    "targetStream": "",
    "cron": "",
    "enabled": true,
    "functionSteps": {
      "mode": "alert",
      "alert": {
        "sources": ["rule", "external"],
        "severities": [],
        "labels": { "env": "staging" },
        "order": 10
      },
      "steps": [
        { "transformName": "cap-severity", "kind": "vrl",
          "script": "if .severity == \"critical\" { .severity = \"warning\" }" },
        { "transformName": "summary", "kind": "ai_summary",
          "prompt": "Summarize this alert in two sentences for the on-call engineer.",
          "annotation": "ai_summary" }
      ]
    }
  }'
```

알림 전송 전에 실행하는 파이프라인은 `alert.stage`를 `notify`로 설정합니다. 필요하면 `alert.policies`를 지정합니다.

```json
{
  "mode": "alert",
  "alert": { "stage": "notify", "policies": ["<policy id>"], "labels": { "env": "staging" }, "order": 10 },
  "steps": [
    { "transformName": "quiet", "kind": "vrl", "script": "if .severity != \"critical\" { abort }" }
  ]
}
```

모든 필드의 설명은 [파이프라인 만들기](/ko/api/intake/create-pipeline)를 참조합니다. 경보 파이프라인에도 [모든 파이프라인에 공통으로 적용하는 권한](/ko/pipelines#권한)이 적용됩니다.
