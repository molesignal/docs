Compose 샌드박스와 예제 `conf/config.toml`은 빠른 시작에 맞춰져 있습니다. 배포 환경에 실제 데이터를 저장하기 전에 이 페이지의 절차를 따릅니다.

## 샌드박스 기본값 교체

| 항목 | 샌드박스 기본값 | 프로덕션 |
|---|---|---|
| 루트 계정 | `admin@example.com`, 비밀번호 `admin` | 처음 시작하기 전에 `[auth]`에서 고유한 이메일 주소와 강력한 비밀번호를 설정합니다. |
| `MS_CIPHER_KEY` | 미설정(모든 바이트가 0인 개발용 키) 또는 Compose 파일에 지정된 고정 개발용 키 | 시크릿 관리자에 보관하는 무작위 32바이트 키를 사용합니다. |
| PostgreSQL 자격 증명 | `molesignal` / `molesignal` | 전용 데이터베이스와 사용자를 만들고, 생성한 비밀번호를 사용합니다. |
| 오브젝트 스토리지 자격 증명 | `rustfsadmin` / `rustfsadmin` | 해당 버킷으로 권한을 제한한 전용 액세스 키를 사용합니다. |
| 오브젝트 스토리지 백엔드 | 컨테이너 볼륨의 RustFS | 내구성을 갖춘 스토리지와 함께 `s3`, `azure` 또는 `gcs`를 사용합니다. |
| `[http].external_url` | 비어 있음 | 공개 HTTPS 주소를 설정합니다. |
| TLS | 사용 안 함 | TLS를 종료하는 프록시 또는 `[http.tls]`를 사용합니다. |
| 이미지 태그 | `latest` | `26.1.0.0`과 같은 특정 버전 태그로 고정합니다. |

## 체크리스트

<Steps>
  <Step title="PostgreSQL 및 오브젝트 스토리지 프로비저닝">
    자동 백업을 설정한 PostgreSQL 17을 사용합니다. MoleSignal 전용 데이터베이스와 사용자를 생성합니다.

    `[meta_database].max_connections`에 노드 수를 곱한 값이 PostgreSQL의 `max_connections` 한도보다 작도록 유지합니다.

    노드와 동일한 리전에 비공개 버킷을 생성합니다. 오브젝트를 만료시키는 수명 주기 규칙은 추가하지 않습니다. MoleSignal이 보존 정책을 적용하고 오브젝트를 직접 삭제합니다.
  </Step>
  <Step title="암호화 키 생성 및 저장">
    `MS_CIPHER_KEY`는 MoleSignal이 PostgreSQL에 저장하는 시크릿의 루트 키입니다. 이 시크릿에는 API 토큰, 공유 링크, 원격 클러스터 토큰, 알림 커넥터 자격 증명, 파이프라인 커넥터 자격 증명, Mole Agent 공급자 키, 신세틱 모니터링 시크릿, 조직 필드 키가 포함됩니다. 키는 한 번만 생성합니다.

    ```bash
    openssl rand -base64 32
    ```

    값을 시크릿 관리자에 저장하고 모든 노드에 동일한 값을 전달합니다. 키는 데이터베이스와 별도로 백업합니다. 키 없이 데이터베이스를 복원하면 해당 시크릿을 읽을 수 없습니다.

    <Warning>
      기존 키를 새 키로 바로 덮어쓰지 않습니다. 이전 키로 암호화한 데이터를 읽을 수 없게 됩니다. 키를 교체하려면 모든 쓰기를 중지하고, 새 값을 환경 변수 `MS_CIPHER_KEY`로 내보낸 다음, 이전 키를 사용해 오프라인 명령을 실행합니다.

      ```bash
      molesignal --config /etc/molesignal/config.toml rewrap-kek --old-key "<old key, base64>"
      ```

      명령은 영향을 받는 모든 열을 다시 암호화하고 테이블별 행 수를 출력합니다. 이전 키를 폐기하기 전에 행 수를 확인합니다.
    </Warning>

    `MS_CIPHER_KEY` 없이 시작한 배포 환경은 모든 바이트가 0인 개발용 키를 사용합니다. 이러한 환경에서 실제 운영용 키로 전환하려면 `AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA=`를 `--old-key` 값으로 전달합니다.
  </Step>
  <Step title="루트 계정 보안 설정">
    빈 데이터베이스로 처음 시작할 때 MoleSignal은 `[auth].root_email`과 `[auth].root_password`를 사용해 루트 계정을 생성합니다. 처음 시작하기 전에 두 값을 모두 설정합니다. 이후에 `root_password`를 변경해도 기존 계정의 비밀번호는 바뀌지 않습니다.

    비밀번호 재설정과 **계정 설정 → 보안 및 로그인 → 비밀번호 변경**은 이메일을 사용합니다. 두 기능 모두 `[notify.smtp]`와 `[http].external_url`이 필요합니다. 두 설정이 없으면 이메일을 전송하지 않습니다. 이 기능을 사용하기 전에 두 설정을 모두 구성합니다.

    MoleSignal은 시작할 때마다 `root_email`에 해당하는 계정을 플랫폼 관리자로 지정합니다. `root_email`에는 기존 사용자의 이메일 주소를 유지합니다.
  </Step>
  <Step title="저장소에 시크릿을 저장하지 않기">
    데이터베이스 DSN, 오브젝트 스토리지 키, `MS_CIPHER_KEY`는 환경 변수나 시크릿 관리자를 통해 전달합니다. `MS_META_DATABASE_DSN`, `MS_OBJECT_STORE_ACCESS_KEY`, `MS_OBJECT_STORE_SECRET_KEY`를 사용합니다. `config.toml`의 해당 설정 키는 비워 둡니다.

    필요하면 `MS_AUTH_JWT_SECRET_OVERRIDE`로 JWT 서명 시크릿을 고정합니다. 설정하지 않으면 MoleSignal이 처음 시작할 때 PostgreSQL에 서명 시크릿을 생성합니다. 서명 시크릿을 교체하려면 `POST /api/v1/auth/jwt/rotate`를 호출합니다. 이 호출에는 `sys.signing_keys.rotate` 권한이 필요합니다. 교체 전 시크릿으로 서명한 토큰은 24시간 동안 유효합니다.
  </Step>
  <Step title="필요한 포트 공개">
    | 포트 | 공개 범위 |
    |---|---|
    | `5080` | TLS를 적용해 공개합니다. |
    | `4317` | TLS를 종료하는 프록시를 통해서만 공개합니다. |
    | `5082` | 사설 네트워크에서만 사용합니다. 이 포트는 인증되지 않은 노드 간 트래픽을 전달합니다. |
    | `5083` | SQL 클라이언트가 연결하는 경우 필요에 따라 TLS를 적용해 공개합니다. |
    | `5084`, `5085` | Probe Agent가 노드 외부에서 실행되는 경우에만 공개합니다. |

    `[http].external_url`을 공개 주소로 설정합니다. 온보딩 스니펫, 비밀번호 재설정 이메일, 상태 페이지 도메인, [패스키](/ko/identity/mfa#인스턴스-요구-사항)에서 이 주소를 사용합니다.
  </Step>
  <Step title="TLS 종료 및 프록시 구성">
    리버스 프록시에서 TLS를 종료하거나 `[http.tls]`를 활성화해 ACME 인증서를 자동으로 발급받습니다.

    기본 JSON 수집 기능은 최대 16 MiB 크기의 요청 본문을 받으므로 프록시의 요청 본문 크기 제한을 최소 16 MiB로 설정합니다. `/api/v1/query/stream`의 응답 버퍼링을 비활성화하고 긴 읽기 시간을 허용합니다. 프로젝트의 nginx 참조 구성에서는 이 경로의 타임아웃을 600초로 설정합니다.

    `/metrics`는 내부 호출만 허용합니다. 수집 경로 `/api/v1/_bulk`, `/api/v1/_kinesis_firehose`, `/api/v1/_cloudflare`, `/api/v1/_heroku`는 전송 측에서 필요한 경우에만 공개합니다.
  </Step>
  <Step title="노드 장애 대비">
    선행 기록 로그(WAL)는 오브젝트 스토리지에 저장합니다. 해당 WAL 오브젝트를 저장한 뒤에만 쓰기 성공을 응답하므로 노드에 영구 볼륨이 필요하지 않습니다. 노드가 사라지면 `[wal].lease_secs`(기본값 15초)에 최대 `[wal].takeover_interval_secs`를 더한 시간이 지난 뒤 다른 수집 노드가 해당 WAL을 인계받습니다. 그전까지는 해당 노드가 쓰기 성공을 응답했지만 아직 플러시하지 않은 레코드를 쿼리할 수 없습니다. 단일 노드가 재시작하면 자체적으로 이전 WAL을 인계받습니다. 각 쓰기는 오브젝트 쓰기 한 건이 완료될 때까지 대기하므로 오브젝트 스토리지의 지연 시간이 각 쓰기의 지연 시간에 더해집니다. [데이터 내구성 및 인계](/ko/architecture#내구성-및-인계)를 참조합니다.

    종료 시 프로세스가 진행 중인 작업을 마칠 시간을 확보합니다. 오케스트레이터의 종료 유예 기간을 `[node].drain_timeout_secs`보다 길게 설정합니다. 이 설정의 기본값은 30초입니다.
  </Step>
  <Step title="데이터 보존 기간 설정">
    기본 보존 기간은 30일이며 `_sys` 조직의 **설정 → 데이터 보존**에서 설정합니다. MoleSignal은 별도의 보존 기간을 설정하지 않은 모든 스트림에서 기본 보존 기간이 지난 데이터를 삭제합니다. 데이터가 쌓이기 전에 기본값을 늘리거나 스트림별로 보존 기간을 설정합니다. [스트림](/ko/streams)을 참조합니다.
  </Step>
  <Step title="알림 및 컴팩터 역할의 인스턴스 수 결정">
    `alert` 및 `compactor` 역할은 여러 인스턴스로 실행해 작업을 분담할 수 있습니다. `alert` 노드는 규칙, 보고서, 파이프라인, 커넥터 단위로 작업을 나누며, 한 번만 실행해야 하는 작업은 기본 노드 한 대가 실행합니다. `compactor` 노드는 스트림과 조직 단위로 작업을 나눕니다. 노드마다 고유한 `[node].id`를 설정하고 시계를 동기화합니다. `standalone` 노드에는 두 역할이 모두 포함됩니다. 역할 분리가 필요하지 않으면 `standalone`을 사용합니다. 역할을 분리하기 전에 [역할 기반 배포](/ko/deployment/role-based)를 읽습니다.
  </Step>
  <Step title="배포 환경 모니터링">
    Prometheus로 `/metrics`를 스크레이프합니다. 공개 엔드포인트인 `GET /api/v1/healthz`를 호출해 상태를 확인합니다. 이 엔드포인트는 오브젝트 스토리지에 연결할 수 없으면 `503`을 반환합니다. 컨테이너 이미지는 이미 이 검사를 `HEALTHCHECK`로 실행합니다.

    서비스가 자체 메트릭, 트레이스, 프로파일을 기록하도록 `[telemetry.self_collect]`를 활성화 상태로 유지합니다. 이 메트릭을 기준으로 알림 규칙을 생성합니다. [자체 옵저버빌리티](/ko/self-observability)를 참조합니다.
  </Step>
  <Step title="백업 및 업그레이드 계획">
    [백업 및 복원](/ko/backup-restore)에 설명된 절차에 따라 PostgreSQL, 오브젝트 스토리지, 암호화 키를 백업합니다. 실제로 복원이 필요한 상황에 대비해 미리 복원 절차를 연습합니다. 처음 버전을 변경하기 전에 [업그레이드](/ko/upgrade)를 읽습니다.
  </Step>
</Steps>

## 운영 시작 전 확인

- 공개 주소에서 `GET /api/v1/healthz`를 호출하면 `200`을 반환합니다.
- 시작 로그에 `object_store_credentials_source`가 표시되고 `MS_CIPHER_KEY missing`은 표시되지 않습니다.
- 서비스 계정 토큰으로 전송한 테스트 레코드가 쿼리 결과에 표시됩니다.
- 기본 계정 `admin@example.com`과 비밀번호 `admin`으로 로그인을 시도하면 실패합니다.
- 최신 PostgreSQL 백업을 임시 데이터베이스에 복원하는 데 성공합니다.
