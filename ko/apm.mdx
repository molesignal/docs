MoleSignal APM은 백엔드 OpenTelemetry 트레이스 스팬을 크기가 제한된 RED 집계로 변환합니다. 이를 통해 별도의 메트릭 계측 없이 느린
서비스, 실패하는 엔드포인트, 비용이 많이 드는 종속성, 반복되는 백엔드 오류, 배포 버전 간 성능 저하를
찾을 수 있습니다. 서비스 카탈로그에는 각 서비스의
소유자와 중요도를 기록합니다.

<Note>
  APM에는 별도의 SDK나 텔레메트리 스트림이 필요하지 않습니다. 계측이 잘 된 트레이스를 전송하면
  MoleSignal은 트레이스 중복 제거 후, 테일 샘플링 전에 APM 데이터를 생성합니다. 이후 샘플링에서
  제외된 트레이스도 APM 메트릭에 반영될 수 있습니다. 다음 파이프라인이 삭제한 스팬도 마찬가지입니다.
  [실시간 파이프라인](/ko/pipelines#트레이스)
</Note>

## 페이지

APM을 열면 개요가 표시됩니다. 각 서비스에는 전용 페이지가 있습니다.

| 페이지 | 용도 |
|---|---|
| **개요** | 전체 서비스를 한눈에 보여 줍니다. 활성 서비스, 처리량, 오류율, p50, p90, p95, p99 및 평균 지연 시간, Apdex를 확인합니다. 서비스 상태의 분포와 변화, 가장 느리거나 실패가 많거나 요청이 많은 서비스를 확인합니다. 직전 동일 길이의 기간 및 일주일 전 같은 기간 대비 달라진 점, 변화 시점 전후에 발생한 변경 사항, 지연 시간을 줄일 수 있는 구간에 대한 인사이트를 제공합니다. 서비스를 명시한 활성 알림, 선택한 기간에 배포한 버전, 환경, 서비스 계측에서 누락된 항목도 표시합니다. |
| **서비스** | 서비스 카탈로그에는 APM이 감지한 서비스와 명시적으로 등록한 서비스가 모두 표시됩니다. 소유자, 티어, 태그, 활성 알림, 처리량, 오류율, 지연 시간, 버전, 마지막 배포를 확인합니다. 즐겨찾기가 먼저 표시되며, 보관된 서비스는 표시하도록 설정하기 전까지 숨겨집니다. |
| **서비스 맵** | 환경 내 서비스와 서비스 간 호출, 호출 대상, 메시지를 발행하거나 소비하는 토픽을 표시합니다. 직전 동일 길이의 기간과 비교해 새로 생기거나 사라진 호출을 확인합니다. [APM 서비스 맵](/ko/apm/service-map#apm-서비스-맵)을 참조합니다. |
| **오류** | 모든 서비스의 백엔드 오류 그룹을 표시합니다. 그룹별 상태, 담당 팀, 담당자, 발생 위치, 그룹화 규칙을 확인합니다. |
| **SLO** | 서비스 수준 목표별로 평가 기간의 달성 실적, 남은 오류 예산, 오류 예산 소진율, 상태를 확인합니다. |
| **설정** | 조직의 상태 임계값, 기본 Apdex 임계값, 장기 작업, 카탈로그 요구 사항, 명명 규칙, 환경 매핑, 별칭을 최근 24시간 데이터에 따른 분석과 함께 확인합니다. 플랫폼의 카디널리티 한도와 트레이스 샘플링도 확인합니다. [APM 설정](/ko/apm/settings)을 참조합니다. |

서비스 페이지에는 다음 섹션이 있습니다.

| 섹션 | 용도 |
|---|---|
| **개요** | 요청 수, 오류율, 지연 시간을 나란히 비교합니다. 서비스 인사이트, 지연 시간 분포, 다운스트림에서 소요된 시간, 영향이 가장 큰 엔드포인트와 오류, 서비스의 SLO를 확인합니다. |
| **엔드포인트** | HTTP, RPC, 메시징, 워커의 진입점을 요청 수, 오류 수, 지연 시간, 소요 시간 비중을 기준으로 정렬합니다. 엔드포인트를 열면 측면 패널에 상태 코드, 소요 시간의 세부 내역, 가장 느린 요청이 표시됩니다. 별표로 주요 트랜잭션을 표시합니다. 목록에서 주요 트랜잭션이나 장기 작업만 표시할 수도 있습니다. |
| **트레이스** | 트레이스 페이지의 트레이스 테이블에서 해당 서비스가 참여한 트레이스를 확인합니다. |
| **종속성** | 해당 서비스를 호출하는 서비스와 해당 서비스의 발신 호출을 확인합니다. 발신 호출은 대상별로 그룹화하며, 각 대상 아래에 작업을 표시합니다. 대상별 상태, 시간 초과되거나 재시도된 호출, 가장 느린 SQL 문도 확인합니다. |
| **오류** | 서비스의 오류 그룹을 확인합니다. |
| **배포** | 파이프라인에서 보고한 배포와 스팬에 기록된 버전을 함께 표시하고, 롤백을 별도로 표시합니다. 각 버전을 직전 버전과 비교하거나, 동시에 실행 중인 두 버전을 나란히 확인하거나, 두 버전을 선택해 비교합니다. [배포](/ko/apm/deployments)를 참조합니다. |
| **런타임** | 서비스를 실행한 인스턴스와 각 인스턴스가 처리한 요청을 확인합니다. 프로세스와 서비스 언어의 런타임 메트릭 차트, 프로파일을 기반으로 한 플레임 그래프도 확인합니다. |
| **설정** | 서비스의 카탈로그 항목과 주요 트랜잭션을 인스턴스에서 보고한 정보와 함께 표시합니다. |

서비스 이름 아래 줄에는 서비스 정보가 표시됩니다. 이 정보는 현재 보고 있는 환경과 버전에
따라 달라집니다.

| 항목 | 출처 |
|---|---|
| 상태 | 선택한 기간의 RED 지표를 기준으로 표시합니다. 상태에 마우스를 올리면 해당 상태의 이유를 확인할 수 있습니다. 요청이 없는 기간에는 대신 **이 기간에 데이터가 없습니다**가 표시됩니다. 텔레메트리가 없다고 해서 서비스에 문제가 있는 것은 아닙니다. |
| 티어 | 카탈로그 항목입니다. |
| 시스템 및 환경 | `service.namespace` 및 `deployment.environment.name`입니다. |
| 유형 | 서비스가 처리하는 진입 스팬을 기준으로 표시합니다. **HTTP**, **RPC**, 메시지의 경우 **컨슈머**, 내부 진입 스팬의 경우 **워커**로 표시합니다. |
| 언어 및 프레임워크 | `telemetry.sdk.language`와 서비스의 진입 스팬을 계측하는 라이브러리입니다. 계측 라이브러리의 예로는 Axum, Spring, Express가 있습니다. |
| 버전 | 선택한 버전 또는 해당 기간에 인스턴스에서 실행한 모든 버전을 표시합니다. 가장 많이 실행한 버전을 먼저 표시합니다. 롤아웃 중에는 두 버전을 모두 표시합니다. |
| 팀 | 카탈로그 항목입니다. 팀에 마우스를 올리면 소유자와 온콜 담당자가 표시됩니다. |
| 인스턴스 | 선택한 기간에 현재 보고 있는 버전의 데이터를 보고한 인스턴스입니다. **런타임**을 엽니다. |
| 마지막 배포 | 현재 보고 있는 버전 또는 최신 버전을 처음 감지한 시점입니다. |
| 리전 | 인스턴스의 `cloud.region`입니다. |
| 저장소 | 인스턴스의 `vcs.repository.url.full` 또는 `git.repository_url`입니다. 둘 다 없으면 카탈로그 항목의 저장소를 표시합니다. |
| 별칭 | 카탈로그 항목에 등록된 첫 번째 별칭과 나머지 별칭의 수를 표시합니다. |

보관된 서비스에는 이 줄에 **보관됨**도 표시됩니다. 제목 줄 끝의 **즐겨찾기**를 선택하면
서비스를 즐겨찾기에 추가합니다.

탐색 카드 끝에는 서비스의 로그, 메트릭, 프로파일 링크가 있습니다. 현재 보고 있는 기간의 종료 시점 직전 24시간 동안
해당 시그널에 서비스 데이터가 있으면 링크를 강조 표시합니다. MoleSignal은
5분마다 다시 확인합니다.

| 시그널 | 강조 표시 조건 |
|---|---|
| 로그 | `service.name`, `service_name`, `service` 필드 중 하나가 있는 로그 스트림에 해당 서비스의 로그가 한 줄 이상 있습니다. 링크를 선택하면 해당 스트림의 로그 페이지가 열립니다. |
| 메트릭 | 최근 1시간의 시계열에 해당 서비스의 `service.name`이 있습니다. |
| 프로파일 | 프로파일 스트림에 해당 서비스의 프로파일이 있습니다. |
| RUM | 브라우저 세션에서 해당 서비스의 샘플 트레이스 중 하나를 생성했습니다. 이 경우에만 링크가 표시되며, 링크를 선택하면 해당 세션이 열립니다. |

데이터가 없는 시그널의 링크는 흐리게 표시됩니다. 링크를 선택하면 해당 시그널을 연결하는 **데이터 소스** 페이지가 열립니다. 확인에 실패하거나
3초 넘게 걸리면 링크를 강조하지도, 흐리게 표시하지도 않습니다.

## 사전 요구 사항

- MoleSignal [트레이스 수집 엔드포인트](/ko/intake)로 전송한 OpenTelemetry 트레이스
- 조직 워크스페이스의 `apm.services.read` 권한 또는
- 보호된 `_sys` 텔레메트리에 대한 `sys.telemetry.read` 권한

## APM을 위한 서비스 계측

<Steps>
  <Step title="변하지 않는 서비스 리소스 속성 설정">
    모든 서비스에 `service.name`을 설정합니다. 서비스를 필터링하거나 배포를 비교하려면 네임스페이스, 환경, 버전, 인스턴스
    속성을 추가합니다.

    ```bash
    export OTEL_SERVICE_NAME=checkout
    export OTEL_RESOURCE_ATTRIBUTES="service.namespace=shop,deployment.environment.name=production,service.version=2.4.0,service.instance.id=checkout-01"
    ```

    구체적인 설정 방법은 선택한 OpenTelemetry SDK 또는 Collector에 따라 다릅니다.
  </Step>
  <Step title="올바른 스팬 종류 사용">
    수신 요청에는 `SERVER` 스팬을, 소비한 메시지에는 `CONSUMER` 스팬을 생성합니다.
    다운스트림 호출에는 `CLIENT` 또는 `PRODUCER` 스팬을 생성합니다. MoleSignal은 이러한 스팬 종류를 사용해
    트랜잭션과 종속성을 구분합니다.
  </Step>
  <Step title="상태 및 예외 기록">
    OpenTelemetry 스팬 상태와 HTTP 또는 RPC 상태 속성을 설정하고 예외 이벤트를 기록합니다. MoleSignal은
    기록된 상태 데이터를 바탕으로 작업의 성공과 실패를 분류하고 백엔드 오류 그룹을 생성합니다.
  </Step>
  <Step title="트레이스 전송 및 APM 열기">
    OTLP 트레이스를 전송한 다음 **APM → 서비스**를 엽니다. 프로젝터가 첫 버킷을 저장하는 동안
    전역 시간 범위에 최근 트래픽이 포함되도록 유지합니다.
  </Step>
</Steps>

### 권장 리소스 속성

| 속성 | 용도 | 대체 값 |
|---|---|---|
| `service.name` | 서비스에 고정 식별자를 부여합니다. 모든 서비스에서 명시적으로 설정합니다. | `unknown_service` |
| `service.namespace` | 시스템이나 팀이 다른 동명 서비스를 구분합니다. | `default` |
| `deployment.environment.name` | 프로덕션, 스테이징 등의 환경을 필터링합니다. | 레거시 `deployment.environment`, 없으면 `unknown` |
| `service.version` | 버전 기록을 확인하고 배포를 비교할 수 있습니다. | 버전별 내역 없음 |
| `service.instance.id` | 인스턴스를 구분합니다. | `k8s.pod.name`, 없으면 `host.name` |
| `telemetry.sdk.language` | 서비스 카탈로그에 런타임 언어를 표시합니다. | `process.runtime.name`이 있으면 해당 값 사용 |
| `cloud.region`, `k8s.*`, `host.name`, `container.name`, `container.id` | 각 인스턴스의 실행 위치를 표시합니다. | 표시하지 않음 |
| `process.runtime.name`, `process.runtime.version` | 각 인스턴스의 런타임을 표시합니다. | 표시하지 않음 |
| `vcs.repository.url.full`, `vcs.ref.head.revision` | 리포지토리를 연결하고 커밋을 식별합니다. `git.repository_url`과 `git.commit.sha`도 사용할 수 있습니다. | 카탈로그 항목의 리포지토리 |

Kubernetes 속성과 `cloud.region`은 일반적으로 SDK가 아니라 OpenTelemetry Collector의
`k8sattributes` 및 `resourcedetection` 프로세서가 추가합니다.

카디널리티가 낮은 값을 사용합니다. 요청 ID, 원본 URL, 사용자 ID 등 가능한 값의 수에 제한이 없는 값은
서비스, 환경, 버전, 경로, 작업 또는 종속성 속성에 넣지 않습니다.

## MoleSignal이 APM 데이터를 산출하는 방식

### 서비스 및 엔드포인트

`SERVER` 및 `CONSUMER` 스팬은 서비스 및 엔드포인트의 RED 메트릭 집계에 반영됩니다. API에서는 엔드포인트를 트랜잭션이라고 부릅니다. 상위 스팬과
스팬 종류가 없는 스팬도 호환성을 위해 서비스 합계에 반영할 수 있지만, 스팬 종류를 명시하면
페이지에 더 완전한 데이터가 표시됩니다.

MoleSignal은 시맨틱 속성을 사용해 가능한 이름의 수가 제한된 엔드포인트 이름을 구성합니다:

- `POST /checkout`과 같이 HTTP 메서드와 `http.route`를 조합한 이름
- RPC 서비스와 메서드를 조합한 이름
- 메시징 작업과 대상을 조합한 이름
- 더 명확한 시맨틱 식별자가 없는 경우 안전하고 카디널리티가 낮은 스팬 이름

`/orders/83921`과 같은 원본 경로 대신 `/orders/{id}`와 같은 경로 템플릿을 사용합니다.

### 종속성

`CLIENT` 및 `PRODUCER` 스팬은 종속성의 RED 메트릭 집계에 반영됩니다. MoleSignal은 대상을
서비스, 데이터베이스, 캐시, 메시징 시스템, 외부 HTTP 엔드포인트, 외부 RPC 엔드포인트 또는 기타
종속성으로 분류합니다. 표준 시맨틱 속성인 `peer.service`, `db.*`, `messaging.*`, `rpc.*`, `server.*` 및 HTTP 속성을 사용하면
종속성을 더 정확히 식별할 수 있습니다.

`peer.service`가 없는 데이터베이스 또는 캐시 호출의 대상은 `postgresql`이나
`redis` 같은 시스템 자체입니다. [`MS_TRACE_FINGERPRINT_KEY`](/ko/configuration#환경-변수)를 설정하면 대상에
`db.namespace`(없으면 `db.name` 또는 `db.collection.name`)에서 키를 사용해 생성한
핑거프린트도 포함됩니다. 예를 들어 `postgresql:<fingerprint>`처럼 표시하므로 같은 시스템 내 데이터베이스의 이름을 저장하지 않고도
각 데이터베이스를 구분할 수 있습니다.

SQL 데이터베이스 호출의 작업은 SQL 문을 템플릿으로 변환한 값입니다. `db.query.summary`를 우선 사용하고, 없으면
`db.query.text` 또는 `db.statement`를 사용합니다. 모든 리터럴을 `?`로 바꾸고 주석을 제거하며 값 목록을
`?` 하나로 줄인 다음 최대 512 bytes만 유지합니다. 큰따옴표로 묶인 텍스트는 PostgreSQL이나 Oracle처럼
이를 테이블 또는 열 이름으로 해석하는 데이터베이스에서만 유지합니다. 그 외에는 값으로 처리합니다.
SQL 문이 없는 호출은 `db.operation.name`을, 캐시 호출은 명령을 사용합니다. 서비스는 대상별로 시간당 최대 32개의
작업을 개별 집계합니다. 이를 초과하는 작업은 같은 대상의 **기타**로 묶어 집계합니다.

시간이 초과된 요청(시간 초과 오류 유형, gRPC `DEADLINE_EXCEEDED`, HTTP 408 또는 504)과
재전송된 요청(`http.request.resend_count`가 0보다 큰 요청)은 RED 메트릭과 별도로 집계합니다.

### 오류

MoleSignal은 예외가 있거나 OpenTelemetry 상태가
`ERROR`이거나 HTTP 상태 코드가 500 이상이거나 RPC 상태 코드가 0이 아니면 스팬을 오류로 분류합니다. 오류 그룹은
오류 유형, 첫 번째 애플리케이션 스택 프레임, 트랜잭션 이름을 바탕으로 생성한 고정 핑거프린트를 사용합니다.
달라질 수 있는 오류 메시지는 핑거프린트에 포함하지 않습니다. [그룹화 규칙](#규칙으로-오류-그룹화)을 사용하면
여러 오류를 하나의 그룹으로 합치거나 그룹화에서 제외할 수 있습니다.

## RED 메트릭 이해하기

| 메트릭 | 의미 |
|---|---|
| **요청 수** | 해당 서비스, 엔드포인트 또는 종속성에서 관측한 요청 수입니다. |
| **오류율** | 오류 수를 요청 수로 나눈 값입니다. |
| **지연 시간** | 병합한 지연 시간 히스토그램에서 산출한 p50, p90, p95, p99와 평균 소요 시간입니다. |
| **Apdex** | 임계값 T 이내의 요청 수에 T를 초과하고 4T 이내인 요청 수의 절반을 더한 뒤 전체 요청 수로 나눈 값입니다. T는 조직의 기본값을 사용하되, 서비스 카탈로그 항목에 별도의 T가 설정되어 있으면 그 값을 사용합니다. 조직 기본값은 [APM 설정](/ko/apm/settings#상태-및-임계값)에서 변경하지 않으면 500 ms입니다. 지연 시간 분포에 현재 적용 중인 T가 표시됩니다. 개요에서는 조직 기본값을 적용해 모든 서비스를 함께 집계합니다. 실패한 요청은 만족으로 집계하지 않으며, 지연 시간 구간 전체에서 실패 건수를 균등하게 차감합니다. |
| **총 소요 시간** | 관측한 소요 시간의 합계로, 누적 영향이 가장 큰 작업을 보여 줍니다. |

[APM 설정](/ko/apm/settings#상태-및-임계값)에서 임계값을 변경하지 않으면 오류율이 2% 이상이거나 p95 지연 시간이 500 ms 이상일 때 **경고**, 오류율이 10% 이상이거나 p95 지연 시간이 2 s 이상일 때 **심각**으로 표시합니다.
서비스 페이지와
카탈로그의 상태 표시점은 어떤 지표가 어느 임계값에 도달했는지 보여 줍니다.

**인사이트** 카드는 현재 구간과 길이가 같은 직전 구간 및 일주일 전의 동일 구간을 각각 비교해
변화가 나타난 서비스를 보여 줍니다. [인사이트가 감지하는 항목](/ko/apm/insights#인사이트가-감지하는-항목)을 참조합니다.

지연 시간 히스토그램은 125 µs부터 약 131 s까지 지연 시간이 두 배가 되는 각 구간을 8개 버킷으로 나누고,
해당 버킷 내에서 백분위수 값을 산출합니다. 백분위수 값은 정확한 값과 약 4% 이내의 차이가 납니다.
이전의 고정 버킷으로 저장한 집계 데이터도 기존의 낮은 정밀도로 계속 조회할 수 있습니다.

개요와 엔드포인트 서랍의 **비교 대상** 컨트롤은 하루 전이나
일주일 전의 동일한 시간 범위를 점선으로 표시합니다. 지연 시간 분포에서는 비교 구간의 분포를 윤곽선으로 표시합니다.
서비스 페이지에서는 해당 서비스의 다른 환경도 목록에 표시합니다. 다른 환경을 선택하면
해당 환경의 동일한 시간 범위를 대신 점선으로 표시합니다.

엔드포인트에서 가장 느린 요청은 트레이스 저장소에서 가져오므로 목록의 각 요청에서
해당 트레이스를 열 수 있습니다. 오류 샘플은 테일 샘플링에서 제외된 트레이스를 가리킬 수 있습니다. 이 경우 트레이스 서랍에
트레이스를 찾을 수 없다는 메시지가 표시됩니다.

## 서비스 카탈로그

카탈로그에는 APM이 감지한 모든 서비스가 서비스와 환경의 조합별로 한 행씩 표시됩니다. 데이터를 보고하기 전에
등록한 서비스도 표시됩니다. 서비스 정보를 기록하려면 카탈로그의 **서비스 등록** 또는 서비스 페이지의
**설정** 섹션을 사용합니다.

| 필드 | 의미 |
|---|---|
| **담당 팀** | 워크스페이스의 팀입니다. 팀의 첫 번째 활성 온콜 일정에서 현재 온콜 담당자를 확인할 수 있습니다. |
| **소유자** | 서비스를 책임지는 워크스페이스 구성원입니다. |
| **등급** | 가장 중요한 서비스에 해당하는 P0부터 P5까지입니다. |
| **수명 주기** | 프로덕션, 스테이징, 실험 또는 지원 중단입니다. |
| **리포지토리** | 코드가 저장된 위치입니다. 서비스가 리포지토리를 보고하지 않을 때 사용합니다. https 주소 또는 `git@github.com:acme/checkout.git`이나 `ssh://git@git.example.com/team/checkout.git`과 같은 git 주소를 입력합니다. 주소의 비밀번호는 `****`로 저장합니다. git이 https 주소의 사용자 이름 부분에 토큰을 넣을 수 있으므로 이 부분도 `****`로 저장합니다. 서비스 페이지에서 git 주소를 열면 경로가 같은 https 페이지로 이동합니다. |
| **태그** | `key=value` 쌍이나 키만 입력하고 쉼표로 구분합니다. 키는 영문 소문자, 숫자, `_ . - /`로 최대 64자까지, 값은 최대 128자까지 입력할 수 있습니다. 태그는 최대 32개까지 추가할 수 있습니다. |
| **Apdex 임계값 T** | 서비스의 Apdex 임계값입니다. 밀리초 단위로 최대 1분까지 설정할 수 있습니다. 비워 두면 조직의 기본값을 사용합니다. APM 설정에서 변경하지 않았다면 기본값은 500 ms입니다. |
| **서비스 설명** | 서비스 이름 아래에 표시하는 짧은 설명입니다. |
| **다른 이름** | `order_service` 또는 Order Center처럼 로그, 메트릭, 기타 시스템에서 서비스를 부르는 이름입니다. 쉼표로 구분하며, 이름당 최대 128자로 최대 20개까지 추가할 수 있습니다. 서비스 자체의 이름이나 다른 서비스의 이름 또는 다른 이름과 중복할 수 없습니다. 카탈로그에서 이 이름으로도 서비스를 검색할 수 있습니다. |
| **데이터 소스** | 서비스 로그를 담은 로그 스트림, `{service="checkout"}`과 같은 메트릭용 PromQL 셀렉터, 서비스 데이터를 표시하는 대시보드, 런북이나 CMDB 항목과 같은 외부 페이지 링크입니다. 각 로그 스트림에는 서비스 로그를 골라내는 SQL 조건을 추가할 수 있습니다. 유형마다 최대 10개까지 추가할 수 있습니다. 각 행을 선택하면 **로그**, **메트릭**, 대시보드 또는 새 탭에서 해당 데이터를 엽니다. |

**다른 이름**과 **데이터 소스**는 카탈로그를 보는 사람뿐 아니라 Mole Agent도 사용합니다. Mole Agent는
서비스에 관한 질문을 받으면 두 필드를 포함한 카탈로그 항목을 읽습니다. APM 질문에서 다른 이름을 사용하면
해당 이름이 속한 서비스의 정보를 읽습니다. 두 필드는 데이터를 병합하지 않습니다. 이전 서비스 이름으로 보고한 데이터를
현재 서비스의 데이터로 보려면 대신 [서비스 별칭](/ko/apm/settings#서비스-별칭)을 추가합니다.

같은 양식에서 **보관**을 선택하면 서비스가 카탈로그 기본 보기에 표시되지 않습니다. 데이터는 계속
수집되며 서비스 페이지도 열 수 있습니다. 카탈로그에서 **보관됨**을 선택하면 보관한 서비스도 표시됩니다.

[카탈로그 요구 사항](/ko/apm/settings#카탈로그-요구-사항)에서는 지정한 등급부터 서비스에
담당 팀, 소유자 또는 리포지토리를 요구할 수 있습니다. 요구 사항을 충족하지 못한 서비스에는 카탈로그에서
누락된 항목과 함께 **필요**가 표시됩니다.

서비스 정의는 네임스페이스와 이름으로 식별하므로 모든 환경에 적용됩니다. 카탈로그와 엔드포인트 테이블의 **열** 메뉴에서
표시할 열과 순서를 지정합니다. 열 구성은 계정별로 저장됩니다.
카탈로그에는 지표와 카탈로그 필드 외에도 선택한 기간의 인스턴스에서 가져온 **유형**,
**언어 / 프레임워크**, **인스턴스**, **리전**과
**태그**, **마지막 발생** 열이 있습니다.

카탈로그 행의 별표를 선택하면 서비스를 즐겨찾기에 추가합니다. 카탈로그는 즐겨찾기를 먼저 표시하며,
**즐겨찾기**를 선택하면 즐겨찾기만 표시합니다. 즐겨찾기는 계정별로 저장됩니다. **그룹**에서
팀, 네임스페이스, 등급 또는 태그 값을 기준으로 행을 그룹화합니다. 카탈로그는 환경과 팀으로 필터링할 수 있으며,
서비스 전체에 네임스페이스나 태그 값이 여러 개 있으면 해당 항목으로도 필터링할 수 있습니다. 필터와 그룹화 설정은
주소에 포함되므로 링크를 공유하면 같은 보기를 열 수 있습니다. 선택한 기간에 감지된 서비스가 기간 종료 시점을 기준으로
하루 동안 데이터를 보고하지 않았으면 **비활성**으로 표시합니다.

주요 트랜잭션은 가장 중요한 엔드포인트입니다. 엔드포인트 목록이나
상세 패널에서 별표를 선택하면 주요 트랜잭션으로 지정합니다. **설정**에는 서비스의 주요 트랜잭션과 각 트랜잭션의
선택한 기간 내 처리 실적이 표시됩니다. 서비스당 최대 50개까지 지정할 수 있습니다.

서비스 문서와 런북은 Mole Agent의 조직 또는 담당 팀 지식 베이스에서 `services/<service name>/`
아래에 저장합니다. 서비스 페이지의 **문서**에서 목록을 확인하고 런북을 실행할 수 있습니다.
Mole Agent도 서비스를 조사할 때 같은 파일을 읽습니다.

서비스 정의와 주요 트랜잭션을 변경하려면 `apm.definitions.manage` 권한이 필요하며, 오류 상태를 변경하려면 `apm.errors.manage` 권한이 필요합니다. 소유자, 관리자,
편집자에게 이 권한이 있습니다.

## 인스턴스

서비스 데이터를 보고하는 각 프로세스는 인스턴스입니다. `service.instance.id`로 구분하며, 이 값이 없으면
`k8s.pod.name`, 그 값도 없으면 `host.name`을 사용합니다. MoleSignal은 스팬에서 분당 한 번 인스턴스를 확인하고
버전과 위 표의 속성을 마지막으로 보고된 값으로 저장합니다. 리포지토리 링크는 사용자 이름,
비밀번호, 쿼리를 제거한 https 주소로 저장합니다. 각 인스턴스의 처리 실적(요청,
오류, 지연 시간)은 서비스 지표와 동일한 스팬을 사용해 인스턴스별 버킷에 집계합니다.

**런타임**은 선택한 기간과 버전에 해당하는 인스턴스를 최근에 감지된 순서대로 표시합니다.
처리량, 오류율, p95와 함께 로그 및 메트릭 링크를 제공합니다. 로그는 파드로 찾고, 파드 정보가 없으면 호스트로 찾습니다.
메트릭은 인스턴스를 구분하는 레이블로 찾습니다. 서비스별 시간당 인스턴스 카디널리티 한도를 초과하면
나머지를 **기타 인스턴스**로 함께 집계합니다. 따라서 인스턴스 집계의 합계는 서비스 집계와 일치합니다.
인스턴스를 클릭하면 해당 인스턴스의 런타임 차트만 표시하며, 선택한 인스턴스는 주소에 반영됩니다. 시간별
집계 보존 기간 동안 감지되지 않은 인스턴스는 제거합니다.

## 엔드포인트 상세 정보

엔드포인트 상세 패널은 RED 차트에 카드 두 개를 추가합니다.

- **상태 코드**는 코드별로 응답을 집계합니다. HTTP 코드는 `http.response.status_code`
  (이전 계측에서는 `http.status_code`)에서, gRPC 코드는 `rpc.grpc.status_code`에서 가져옵니다.
  코드 클래스별로 색상을 구분하고 추세를 표시합니다. 버킷당 최대 24개 코드를 저장하며, 초과 코드는
  **기타 HTTP** 또는 **기타 gRPC**로 집계합니다. 상태 코드 집계를 시작하기 전에 저장한 집계에는 상태 코드가 없습니다.
- **소요 시간 내역**은 트레이스 저장소에서 선택한 기간에 해당하는 엔드포인트의 최신 요청을
  최대 200개까지 가져오고 각 요청의 하위 스팬을 읽습니다. 호출에 걸린 시간은 대상에 따라 데이터베이스
  (`db.system.name`), 캐시(Redis, Memcached, Valkey), HTTP, RPC 또는 메시징으로 분류합니다. 대상 정보가 없는
  호출은 **기타**로 분류합니다. 내부 스팬은 내부 작업으로 집계하고, 요청의 하위 스팬이
  포함하지 않는 시간은 요청 자체의 소요 시간으로 집계합니다. 각 항목에 비중과 요청당
  소요 시간을 표시합니다. 병렬 호출의 소요 시간 합계가 요청 시간을 넘으면 각 항목을 비례 조정해
  합계를 요청 시간에 맞춥니다. 테일 샘플링에서 보존한 트레이스만 읽습니다.

엔드포인트 목록의 **장기 작업**은 p99가 1초 이상인 엔드포인트만 표시합니다. 예약 작업이나
메시징 작업이 없는 큐 워커처럼 내부 유형의 진입 스팬은
**워커**로 표시합니다.

## 배포

서비스 페이지의 **배포** 섹션은 파이프라인이 보고한 배포를 서비스 스팬에 기록된
버전과 함께 표시합니다. 롤백을 표시하고, 각 버전을 직전 버전과 비교하며,
동시에 실행 중인 두 버전을 나란히 비교합니다. 파이프라인은
`POST /api/v1/apm/deployments`로 배포를 보고합니다. [배포](/ko/apm/deployments)를 참고합니다.

## 종속성

서비스의 **종속성** 탭에서 각 대상의 상태 점수는 100점에서 시작합니다. 호출 실패율이
1%p 높을 때마다 4점(최대 60점), 호출 시간 초과율이 1%p 높을 때마다 4점(최대
20점)을 뺍니다. 기간을 비교할 때는 P95 증가율이 20%를 초과하는 부분에 대해 1%p당 0.5점
(최대 20점)을 뺍니다. 90점 이상은 양호, 70점 이상 90점 미만은 확인이 필요한 상태입니다. 점수 제목에는 감점
사유가 표시됩니다. **비교 대상**을 설정하면 각 대상의 오류율과 P95 변화도 표시합니다. **느린 SQL**은
P95가 가장 높은 데이터베이스 문을 템플릿으로 나열합니다.

## 백엔드 오류 추적

오류 그룹의 상태를 **조사 중**, **해결됨**, **무시됨**으로 변경하기 전까지는 열린 상태로 유지됩니다. 각 그룹에
담당 팀과 워크스페이스 구성원을 지정할 수 있습니다. 해결된 그룹에서 오류가 다시 발생하면 상태가
**재발**로 표시됩니다. **APM → 오류**는 기본적으로 해결되지 않은 그룹, 즉 열린 상태이거나 조사 중이거나
재발한 그룹을 표시합니다.

목록 위의 **발생 위치**에서는 목록에 있는 그룹의 발생 횟수를 버전,
환경, 서비스의 프로그래밍 언어별로 집계합니다. 각 오류 그룹의 사이드 패널에서는 해당 그룹만 집계합니다. 사이드 패널의 **관련
로그**를 선택하면 해당 서비스와 시간 범위의 로그가 열리고, 샘플 옆의 **로그**를 선택하면
해당 샘플의 트레이스에 연결된 로그가 열립니다.

### 규칙으로 오류 그룹화

오류 목록의 **그룹화 규칙**에서 오류 유형, 프레임,
엔드포인트를 기준으로 하는 기본 그룹화 방식을 바꿀 수 있습니다. 규칙에서 특정 서비스 또는 모든 서비스를 대상으로 지정하고 오류 유형, 메시지,
오류가 발생한 프레임, 엔드포인트의 패턴을 설정합니다. 각 패턴은 대소문자를 구분하지 않고 전체 텍스트와 일치해야 합니다.
`*`는 임의의 텍스트와 일치하며 빈 패턴은 모든 값과 일치합니다. 규칙마다 패턴을 하나 이상 입력해야 합니다.

| 작업 | 효과 |
|---|---|
| **하나의 그룹으로 병합** | 서비스에서 규칙과 일치하는 오류를 규칙에 지정한 이름의 그룹 하나로 병합합니다. |
| **그룹화에서 제외** | 규칙과 일치하는 오류를 그룹화하지 않습니다. 해당 요청은 RED 메트릭에서 여전히 실패로 집계합니다. |

규칙을 순서대로 평가해 처음으로 일치하는 규칙을 적용합니다. 규칙을 위아래로 이동해
순서를 바꿉니다. 저장한 규칙은 30초 이내에 모든 노드에서 적용되며, 저장 후 발생한 오류에만 적용됩니다.
기존 그룹은 그대로 유지합니다. 규칙을 편집하는 동안 양식에는 목록에서 규칙과 일치하는
그룹 수가 표시됩니다. 오류 그룹의 사이드 패널에서 **이 오류로 규칙 만들기**를 선택하면
해당 그룹의 오류 유형과 서비스가 입력된 상태로 규칙 만들기를 시작합니다.

## 서비스 수준 목표

서비스 수준 목표(SLO)는 현재 시점까지 최근 7일, 28일 또는
30일 동안 성공 조건을 충족해야 하는 요청의 비율을 정합니다. 한 환경의 서비스 전체 또는 해당 서비스의 엔드포인트 하나에 적용합니다. **APM → SLO**를 열어
**새 SLO**를 클릭하거나, 서비스 개요의 **서비스 수준 목표** 카드에서 **새 SLO**를 클릭합니다.

| 필드 | 의미 |
|---|---|
| **서비스** 및 **환경** | 목표를 적용할 서비스와 해당 서비스의 환경입니다. |
| **엔드포인트** | 서비스의 엔드포인트 하나를 지정합니다. 서비스 전체에 적용하려면 비워 둡니다. |
| **성공 조건** | **요청 성공**: 요청이 실패하지 않으면 성공으로 집계합니다. **임계값 이내에 성공**: 요청이 실패하지 않고 처리 시간이 **지연 시간 임계값 (ms)** 이내이면 성공으로 집계합니다. |
| **목표 (%)** | 성공 조건을 충족해야 하는 요청의 비율입니다. `99.9`처럼 0보다 크고 100보다 작은 값을 입력합니다. |
| **기간** | 현재 시점까지 최근 7일, 28일 또는 30일입니다. |

SLO는 서비스의 APM 집계 데이터를 사용하므로 테일 샘플링 전의 모든 요청을 집계합니다.

| 지표 | 의미 |
|---|---|
| **성공률** | 기간 내 전체 요청 중 성공 조건을 충족한 요청의 비율입니다. |
| **남은 오류 예산** | `1 - (1 - met) / (1 - objective)`. 오류 예산은 목표를 지키면서 실패를 허용할 수 있는 요청의 비율입니다. 목표를 위반하면 이 값은 0보다 작아집니다. |
| **소진율** | 최근 1시간, 6시간, 24시간 각각의 `(1 - met) / (1 - objective)` 값입니다. `1×`이면 오류 예산이 설정한 기간과 정확히 같은 시간에 소진됩니다. |
| **일별 목표 달성 현황** | 기간 내 각 날짜의 상태를 UTC 기준으로 목표 달성, 목표 미달성 또는 요청 없음으로 표시합니다. |

| 상태 | 의미 |
|---|---|
| **목표 위반** | **성공률**이 목표보다 낮습니다. |
| **위험** | 남은 오류 예산이 25% 미만이거나, 최근 1시간의 소진율이 14.4를 초과하거나, 최근 6시간의 소진율이 6을 초과합니다. |
| **정상** | 위의 어떤 조건에도 해당하지 않습니다. |
| **데이터 없음** | 기간 내 요청이 없습니다. |

지연 시간 목표는 지연 시간 히스토그램을 사용합니다. 따라서 임계값 이내에 처리된 요청 수는
백분위수와 같은 정밀도로 계산하며 오차는 약 4% 이내입니다. 기간 집계에는 시간 단위 데이터를, 소진율 계산에는
분 단위 데이터를 사용합니다. 설정한 기간이 시간 단위 집계 데이터의 보존 기간보다 길면 보존된
날짜의 데이터만 집계합니다.

### 소진율 알림

SLO의 사이드 패널에서 **소진율 알림 만들기**를 선택하면 Google SRE
워크북에서 권장하는 알림 규칙 두 개가 추가됩니다. 두 규칙 모두 해당 목표에 대한 APM 알림 규칙이며, 각 규칙의 에스컬레이션 정책에 따라 알림을 보냅니다.

| 규칙 | 기간 | 트리거 조건 | 심각도 |
|---|---|---|---|
| 빠른 소진 | 최근 1시간 및 그중 마지막 5분 | 두 기간 모두 소진율이 14.4를 초과함 | 심각 |
| 느린 소진 | 최근 6시간 및 그중 마지막 30분 | 두 기간 모두 소진율이 6을 초과함 | 경고 |

짧은 기간을 함께 확인하면 이미 끝난 급증으로 알림이 발생하지 않습니다. 규칙이
SLO를 모니터링하기 시작하면 사이드 패널에 버튼 대신 규칙이 표시됩니다. 규칙을 만들려면 `alerts.rules.manage` 권한이 필요합니다.

SLO를 작성하려면 `apm.slos.manage` 권한이 필요하고, 삭제하려면 `apm.slos.delete` 권한이 필요합니다. SLO를 삭제할 때는 연결된 소진율 알림을 먼저 삭제하므로
`alerts.rules.manage` 권한도 필요합니다.

## APM 지표에 알림 설정

APM 알림 규칙은 APM 페이지와 동일한 집계 데이터를 사용해 서비스나 개별 엔드포인트의 지표를
모니터링하므로 쿼리가 필요하지 않습니다.

<Steps>
  <Step title="규칙 편집기 열기">
    서비스 페이지나 엔드포인트 드로어의 헤더에서 **새 알림**을 열고 **임계값
    알림**을 선택합니다. 편집기가 **APM 알림** 소스로 열리며 서비스, 환경, 엔드포인트가 자동으로 입력됩니다.
    **알림 → 알림 규칙**에서 새 규칙을 만들 때도 같은 소스인 **APM 알림**을 선택할 수 있습니다. 규칙을 만들려면
    `alerts.rules.manage` 권한이 필요합니다.
  </Step>
  <Step title="지표 선택">
    **서비스**, **환경** 또는 **모든 환경**, **엔드포인트** 또는 **서비스 전체**,
    그리고 **지표**를 선택합니다. 편집기의 지표 아래에 표시된 단위로 임계값을 설정합니다.
  </Step>
  <Step title="테스트 및 저장">
    **규칙 테스트**를 클릭해 최근 6시간의 지표를 임계값과 함께 그래프로 확인한 다음,
    규칙을 만듭니다.
  </Step>
</Steps>

| 지표 | 단위 |
|---|---|
| **오류율** | 백분율(0~100) |
| **P50 지연 시간**, **P90 지연 시간**, **P95 지연 시간**, **P99 지연 시간**, **평균 소요 시간** | 밀리초 |
| **처리량** | 초당 요청 수 |
| **요청 수**, **오류** | 규칙의 평가 구간 내 건수 |
| **새 오류 그룹** | 규칙의 평가 구간에 서비스나 엔드포인트에서 처음 발견한 오류 그룹 수 |
| **Apdex** | 0~1 |
| **SLO 소진율** | 목표에서 허용하는 소진 속도 대비 배수입니다. SLO에서 설정합니다. |

평가할 때마다 규칙의 평가 구간에 해당하는 집계 데이터를 읽습니다. 최대 24시간까지는 분 단위 집계를 사용하고,
더 긴 구간에는 시간 단위 집계를 사용합니다. 요청이 없는 구간에서는 **요청 수**, **오류**, **새 오류 그룹**,
**처리량**을 `0`으로 읽으므로 규칙으로 트래픽 중단을 감지할 수 있습니다. 이때 나머지 지표에는 값이 없으므로
임계값 조건을 충족하지 않으며, 열린 인시던트는 해결 상태로 전환됩니다.

편집기나 SLO에서 만든 규칙은 지정된 대상에 해당하는 `service.name`, `service.namespace`,
`deployment.environment`, `apm.endpoint` 라벨을 포함하며, 인시던트는 이 라벨을 복사합니다.
모든 APM 규칙의 인시던트에는 `service` 라벨, `affected_services`에 기록된 서비스,
집계 데이터의 샘플 트레이스 ID도 포함됩니다. 카탈로그의 **알림** 열, 서비스 헤더, 엔드포인트 드로어에는 해당 서비스의 열린 인시던트와
확인된 인시던트 수가 표시됩니다. 인시던트에 환경이 지정되어 있으면 해당 환경에서만 집계합니다.
엔드포인트 드로어는 해당 엔드포인트 라벨이 붙은 인시던트만 집계합니다. 건수를 클릭하면 **알림 →
인시던트**가 열립니다.

같은 메뉴의 **이상 감지 알림**은 지표가 이전 며칠의 같은 시간대에 관측된 패턴에서 벗어나면 알림을 보냅니다.
임계값을 설정할 필요가 없습니다. 자세한 내용은
[APM 지표의 이상 감지 알림 설정](/ko/apm/insights#apm-지표의-이상-감지-알림-설정)을 참조합니다.

## 필터, 해상도, 보존 기간

APM 페이지는 전역 시간 범위를 공유합니다. 카탈로그에서는 환경과 팀으로 필터링하고, 서비스
페이지에서는 환경과 버전으로 필터링합니다. 목록에서 검색과 정렬을 지원합니다. 보기 범위를 URL에 인코딩하므로
보기를 공유하거나 다시 열 수 있습니다.

기본 배포 설정에서는 다음과 같이 동작합니다.

- API 요청에서 시간 범위를 생략하면 최근 24시간을 사용합니다.
- 해상도가 `auto`이면 최대 24시간 범위에 분 단위 버킷을 사용하고, 그보다 긴
  범위에는 시간 단위 버킷을 사용합니다.
- 분 단위 집계는 24시간 동안 보존합니다.
- 시간 단위 집계 보존 기간과 최대 쿼리 범위는 모두 30일입니다.

관리자는 이러한 배포 한도를 변경할 수 있습니다. 버전 비교에서는 양쪽 모두 설정된 요청 수 임계값에 도달해야
데이터가 충분하다고 표시합니다. 기본 임계값은 버전별 1,000건입니다.

## 데이터 품질 알림 확인

모든 APM 응답에는 데이터 품질 메타데이터가 포함됩니다. 알릴 내용이 있으면 탐색 카드에 짧은 알림이 표시됩니다.
알림을 클릭하면 상세 내용이 열립니다.

| 알림 | 의미 |
|---|---|
| **이 범위 내에서 데이터 시작** | 선택한 범위 내에서 APM 프로젝션을 시작했으므로 시작 시점 이전의 트래픽은 반영하지 않습니다. |
| **일부 데이터 누락** | 큐, 저장소, 플러시, 지연 도착 데이터, 카디널리티 또는 종료로 인해 범위 일부에 데이터가 누락되었습니다. 누락된 데이터를 0으로 해석하지 않습니다. |
| **데이터 지연** | `lastCompleteBucketAt`이 선택한 범위의 끝 시점에 도달하지 못했습니다. 최근 집계 버킷을 아직 마감 중이거나 상위 단위로 집계 중일 수 있습니다. |
| **일부 이름이 기타로 집계됨** | 카디널리티 한도에 도달했습니다. 한도를 초과한 이름은 **기타** 행 하나로 묶어 집계합니다. 한도는 [APM 설정](/ko/apm/settings#카디널리티-한도)에서 확인합니다. |

먼저 시간 범위를 좁히고 필터로 조회 대상을 줄입니다. 데이터 누락이나 지연이 계속되면 APM
상태 확인 엔드포인트와 [APM 프로젝션 메트릭](/ko/self-observability#apm-프로젝션)을 확인합니다.

## 런타임 메트릭

**런타임** 섹션에서는 서비스가 `service.name`과 함께 전송하는 런타임 메트릭을 차트로 표시합니다.
먼저 모든 언어에 공통인 프로세스 메트릭을 표시한 다음, 서비스가
`telemetry.sdk.language`에 보고한 각 언어의 런타임 메트릭을 표시합니다. 언어를 보고하지 않으면 메트릭이 있는 모든 런타임을 표시합니다.
각 차트는 위에서 설명한 방식으로 인스턴스를 구분하고 인스턴스당 선 하나를 그립니다. 여기에 저장된 OpenTelemetry 규칙을 따르는 메트릭과
각 런타임에서 일반적으로 사용하는 Prometheus 클라이언트의 메트릭을 모두 읽습니다. 각 차트는 다음 목록에서 서비스가 전송하는

프로파일 페이지에서 계속 살펴볼 수 있습니다.

## 개인정보 보호 및 데이터 제한

APM은 집계 데이터와 민감한 내용을 제거한 소량의 증거 데이터를 저장합니다. APM 집계 데이터에는 요청이나
응답 본문, URL 쿼리 값, 헤더, SQL 매개변수를 보관하지 않습니다. SQL 문은 모든 리터럴을
`?`로 바꾼 템플릿으로만 보관합니다.
식별 값, 대표 메시지, 스택 프레임의 길이를 제한합니다. 민감해 보이거나 자주 바뀌는 값은
저장하기 전에 제거하거나 마스킹합니다.

이러한 보호 조치가 올바른 계측 방식을 대신하지는 않습니다. 스팬 이름, 상태 설명, 예외 메시지 또는
리소스 속성에 비밀 정보나 개인정보를 넣지 마십시오.

## 문제 해결

| 증상 | 확인 사항 |
|---|---|
| APM 데이터 없음 | 트레이스가 동일한 워크스페이스에 수신되는지, 시간 범위에 최근 트래픽이 포함되는지, 현재 역할에 `apm.services.read` 권한이 있는지 확인합니다. |
| `unknown_service` | 스팬을 내보내기 전에 `service.name` 리소스 속성을 일관된 값으로 설정합니다. |
| 엔드포인트 누락 | 스팬 종류를 `SERVER` 또는 `CONSUMER`로 지정하고 표준 HTTP, RPC 또는 메시징 속성을 추가합니다. |
| 종속성 누락 | 다운스트림 호출을 `CLIENT` 또는 `PRODUCER` 스팬으로 감싸고 호출 대상의 시맨틱 속성을 포함합니다. |
| 버전 누락 | 배포에 포함된 모든 인스턴스에서 `service.version`을 일관되게 설정합니다. |
| 오류 누락 | 예외 이벤트를 기록하고 OpenTelemetry 규칙에 따라 스팬, HTTP 또는 RPC 상태를 설정합니다. |
| 오류 샘플에서 트레이스를 찾을 수 없음 | 샘플링 과정에서 트레이스가 제외되었거나 보존 기간이 만료되었습니다. 샘플링 전에 집계한 APM 데이터는 여전히 유효합니다. |
| 런타임 차트 없음 | 동일한 `service.name`으로 OpenTelemetry 런타임 메트릭을 전송합니다. |
| 결과가 일부만 표시되거나 최신 상태가 아님 | 데이터 품질 알림과 `GET /api/v1/apm/health` 응답을 확인합니다. |

| SLO에 **데이터 없음**이 표시됨 | 서비스가 SLO에 지정된 환경에서 데이터를 전송하는지, 엔드포인트 이름이 **엔드포인트** 목록의 이름과 일치하는지 확인합니다. |
