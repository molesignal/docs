싱글 사인온을 사용하면 MoleSignal 비밀번호 대신 회사 디렉터리 또는 범용 플랫폼의 계정으로
로그인할 수 있습니다. **ID 및 액세스 → SSO 공급자**와 **이메일 도메인**을 엽니다.
공급자와 도메인을 조회하려면 `org.sso.read` 권한이 필요하고, 변경하려면
`org.sso.manage` 권한이 필요합니다.

## 공급자를 추가하기 전에

`[http].external_url`을 MoleSignal의 공개 주소로 설정합니다. OIDC와 OAuth 2.0의 **리디렉션 URI**,
SAML의 **어설션 소비자 서비스 URL(ACS)**, 기본 **SP 엔터티 ID**는 이 주소를 기준으로 생성합니다.
ID 공급자는 이 설정을 사용해 MoleSignal로 응답을 보내야 합니다. MoleSignal은 공급자 설정을 데이터베이스에 저장하고
재시작 없이 적용합니다.

## 공급자 추가

1. **SSO 공급자**를 열고 **공급자 추가**를 선택합니다.
2. **인기 플랫폼** 또는 **엔터프라이즈 디렉터리**에서 플랫폼을 선택하거나, **범용 프로토콜**에서 **OIDC**,
   **OAuth 2.0**, **SAML**, **LDAP** 중 하나를 선택합니다. 다시 선택하려면 **플랫폼 변경**을
   선택합니다.
3. 플랫폼에서 여러 프로토콜을 지원하면 **프로토콜**에서 사용할 프로토콜을 선택합니다.
4. 플랫폼에서 요구하는 정보를 입력합니다. 양식의 안내에 따라 양식에 표시된 **리디렉션 URI** 또는 **어설션 소비자 서비스
   URL(ACS)**을 ID 공급자에 등록합니다.
5. [ID 필드 매핑](#id-필드-매핑), [역할 바인딩](#역할-바인딩),
   [로그인 범위](#로그인-범위)를 확인합니다.
6. **공급자 생성**을 선택합니다.

## 사전 설정 플랫폼

사전 설정 플랫폼은 엔드포인트, 권한 범위, 필드 매핑을 자동으로 채웁니다. OIDC 또는 OAuth 2.0
플랫폼에서는 아래 필드와 **클라이언트 ID**, **클라이언트 시크릿**만 입력합니다. 입력값에 따라 생성되는 엔드포인트는
**엔드포인트 및 범위**에서 확인합니다.

| 플랫폼 | 프로토콜 | 필드 | 그룹 |
|---|---|---|---|
| Google | OIDC, SAML | OIDC는 추가 필드 없음 | OIDC는 없음, SAML은 그룹 멤버십 |
| Microsoft Entra ID | OIDC, SAML | **디렉터리(테넌트) ID** 및 **클라우드**(글로벌 또는 21Vianet 운영) | 그룹 개체 ID |
| GitHub | OAuth 2.0 | **배포**. GitHub Enterprise Server의 경우 **서버 호스트**도 입력 | 조직(`my-org`) 및 팀(`my-org/sre`) |
| GitLab | OIDC | **인스턴스 URL**, 기본값은 `https://gitlab.com` | `groups` |
| Okta | OIDC, SAML | **Okta 도메인** 및 **권한 부여 서버** | `groups` 클레임 |
| Auth0 | OIDC | **테넌트 도메인** | 사용자 지정 클레임 |
| Keycloak | OIDC | **서버 URL** 및 **렐름** | Group Membership 매퍼의 `groups` |
| authentik | OIDC | **서버 URL** 및 **애플리케이션 슬러그** | `groups` |
| Feishu / Lark | OAuth 2.0 | **에디션**(Feishu 또는 Lark) | 없음 |
| AD FS | SAML | IdP 메타데이터 | Token-Groups |
| JumpCloud | SAML | IdP 메타데이터 | `memberOf` |
| Active Directory, OpenLDAP, FreeIPA | LDAP | 서버 URL, 기본 DN, 검색 계정 | `memberOf` |

MoleSignal은 GitHub 계정의 숫자 ID를 주체 식별자로, 검증된
기본 이메일 주소를 이메일로 사용합니다. 조직과 팀을 조회하려면 `read:org` 권한이 필요합니다. 조직에서
OAuth 앱 액세스를 제한하는 경우, 조직 소유자가 앱을 승인해야 해당 조직과 팀을
조회할 수 있습니다. Feishu에서는 오픈 플랫폼에서 앱에 사용자 이메일 읽기 권한을 부여해야 합니다.

## 범용 프로토콜

| 프로토콜 | 설정 |
|---|---|
| OIDC | **발급자 URL**, **권한 부여 URL**, **토큰 URL**, **UserInfo URL**, **JWKS URL**, **클라이언트 ID**, **클라이언트 시크릿**, **권한 범위**를 입력합니다. 여러 권한 범위는 공백으로 구분합니다. **발급자 URL**을 입력한 후 **자동 검색**을 선택하면 `.well-known/openid-configuration`에서 나머지 엔드포인트를 가져와 채웁니다. |
| OAuth 2.0 | ID 토큰을 발급하지 않는 ID 공급자에는 **권한 부여 URL**, **토큰 URL**, **UserInfo URL**, **클라이언트 ID**, **클라이언트 시크릿**, **권한 범위**를 입력합니다. 로그인 후 MoleSignal은 액세스 토큰으로 **UserInfo URL**을 조회하고, 필드 매핑에 따라 응답에서 계정을 식별합니다. |
| SAML | **SP 엔터티 ID**, **IdP 엔터티 ID**, **IdP SSO URL**, **IdP 서명 인증서(PEM)**를 입력합니다. **IdP 메타데이터**에서 메타데이터 URL을 입력하거나 **XML 붙여넣기**를 선택해 메타데이터를 붙여넣습니다. 그런 다음 **가져오기**를 선택해 마지막 세 필드를 채웁니다. HTTP-Redirect 방식의 로그인 URL만 지원합니다. |
| LDAP | **LDAP 서버 URL**에는 `ldaps://`을 사용하거나 `ldap://`을 사용하고 **StartTLS**를 활성화합니다. **사용자 기본 DN**을 입력합니다. 예: `ou=people,dc=example,dc=com`. **사용자 검색 필터**에 `{username}`을 포함합니다. MoleSignal은 검색 전에 이 값을 이스케이프 처리합니다. **검색 바인드 DN**과 **검색 바인드 비밀번호**를 입력합니다. 디렉터리에서 익명 검색을 허용하는 경우에만 두 필드를 모두 비워 둡니다. |

공급자를 편집할 때 기존 값을 유지하려면 **클라이언트 시크릿** 또는 **검색 바인드 비밀번호**를
비워 둡니다.

## ID 필드 매핑

**ID 필드 매핑**은 MoleSignal이 다음 네 가지 사용자 필드의 값을 읽을 위치를 지정합니다.

| MoleSignal 필드 | OIDC 및 OAuth 2.0 | SAML | LDAP |
|---|---|---|---|
| **고정 주체 식별자** | 클레임 또는 JSON 필드. `realm_access.roles`처럼 점으로 구분한 경로도 사용할 수 있습니다. | 속성 이름 또는 어설션 주체를 나타내는 `NameID`. | 속성 또는 항목의 DN을 나타내는 `dn`. |
| **이메일** | 클레임 또는 JSON 필드. | 속성 이름. | 속성. |
| **표시 이름** | 클레임 또는 JSON 필드. | 속성 이름. | 속성. |
| **그룹** | 클레임 또는 JSON 필드. | 속성 이름. | 속성. |

OIDC와 OAuth 2.0에서는 `|`로 여러 소스를 나열하면 값이 있는 첫 번째 소스를 사용합니다.
예: `email | preferred_username`. 유효한 이메일이 없으면 로그인을 거부합니다.

## 역할 바인딩

**외부 그룹 → 역할**에는 **그룹** 값과 MoleSignal 역할 간의 매핑이 표시됩니다.
**매핑 추가**를 선택하고 `platform-admins`와 같은 **외부 그룹 값**을 입력한 후
역할을 선택합니다. MoleSignal은 일치하는 모든 매핑의 역할을 부여하고 로그인할 때마다
역할을 동기화합니다.

일치하는 매핑이 없으면 **기본 역할**을 적용합니다. 기본 역할을 설정하지 않으면 셀프 서비스 가입에 지정된 역할을
적용합니다. 플랫폼에서 그룹 정보를 보내지 않으면 기본 역할만 적용합니다.

## 로그인 범위

**로그인 허용 그룹**을 설정하면 해당 그룹 중 하나에 속한 계정만 이 공급자를 통해
로그인할 수 있습니다.

Google, GitHub.com, GitLab.com과 Microsoft의 테넌트 독립형 엔드포인트에서는 누구나 계정을
생성할 수 있습니다. 이러한 공급자는 워크스페이스에 [이메일 도메인](#이메일-도메인)이 있거나
공급자에 **로그인 허용 그룹**이 설정된 경우에만 활성화할 수 있습니다. 로그인할 때는
ID 공급자가 검증한 이메일 주소만 허용합니다. 활성화 후 이메일 도메인을 모두 삭제하면 해당 공급자를
통한 로그인을 거부합니다.

## 로그인 테스트

공급자를 사용하기 전에 확인합니다. 공급자 목록이나 해당 공급자의
설정에서 **테스트**를 선택합니다. 테스트는 저장된 설정으로 실제 로그인 절차를 진행하지만,
세션을 시작하거나 계정을 생성 또는 연결하거나 역할을 변경하지 않습니다. 현재 로그인 상태도 그대로
유지합니다. 비활성화된 공급자도 테스트할 수 있으므로 활성화하기 전에 테스트합니다. 테스트에는
`org.sso.manage` 권한이 필요하며, API 토큰으로는 시작할 수 없습니다. 공급자당 분당 10회까지 테스트할 수 있습니다.

| 공급자 | 테스트 진행 방식 |
|---|---|
| OIDC, OAuth 2.0, SAML | 새 탭에서 ID 공급자로 이동한 뒤 결과 페이지로 돌아옵니다. 로그인용으로 등록한 리디렉션 URI 또는 ACS URL을 사용합니다. |
| LDAP | 디렉터리 계정과 해당 비밀번호를 입력합니다. 실제로 바인딩하므로 잘못된 비밀번호를 입력하면 디렉터리의 계정 잠금 정책과 이 인스턴스의 로그인 시도 제한에 반영합니다. 비밀번호는 저장하지 않습니다. |

결과 페이지에는 다음 정보가 표시됩니다.

- **성공 여부.** 실패 시 원인, 해결 방법, 서버 또는 ID
  공급자의 메시지를 표시합니다. 로그인 허용 그룹, 이메일
  도메인, 계정 비활성화 상태 등 로그인 차단 규칙에 해당하면 테스트도 실패합니다.
- **공급자가 반환한 정보:** 이메일, 이름, 주체, 그룹을 표시합니다.
- **실제 로그인 시 처리 결과:** 대상 계정(기존 계정으로 로그인, 계정 소유자의 연결 확인 필요 또는
  새 계정 생성)과 로그인 후의 역할을 표시합니다. 기존 역할을 대체하는 경우 그 내역도 표시합니다.

ID 공급자가 자체 오류 페이지를 표시하면 브라우저가 돌아오지 않습니다. 10
분 뒤 결과에는 응답이 없었다고 표시합니다. 일반적으로 ID 공급자에 등록하지 않은
리디렉션 URI를 사용했을 때 발생합니다.

테스트 결과는 테스트에 사용한 설정에만 유효합니다. 엔드포인트, 시크릿, 매핑 또는
로그인 허용 그룹을 변경하면 결과가 무효화되고 목록에 **설정 변경됨**이 표시됩니다. 이름을 바꾸거나
공급자를 활성화 또는 비활성화해도 결과는 그대로 유지됩니다. 공급자마다 최근 테스트 20건을 보관합니다. 토큰, 어설션, 시크릿,
비밀번호는 표시하거나 저장하거나 로그에 남기지 않습니다. 각 테스트는 `org.sso_provider.test`로 감사 로그에 기록하며,
ID 정보는 포함하지 않습니다.

## 로그인 요구 사항

**ID 및 액세스 → SSO 공급자** 상단의 **로그인 요구 사항**에서 이
워크스페이스에 로그인할 때 충족해야 할 조건을 정합니다. 이 설정을 변경하려면 `org.sso.manage` 권한이 필요합니다. 변경 사항은 15분 이내에 모든 세션에 적용됩니다.
요구 사항을 충족하지 않는 세션은 다음 갱신 시 종료되므로 다시 로그인해야 합니다. 변경 사항은 감사 로그에 기록합니다.

| 요구 사항 | 효과 |
|---|---|
| **다단계 인증 필수** | 워크스페이스에 액세스하려면 세션에 [다단계 인증](/ko/identity/mfa)이 필요합니다. 이 워크스페이스의 OIDC, OAuth 2.0 또는 SAML 공급자를 통해 로그인한 세션은 요구 사항을 충족한 것으로 간주합니다. 다단계 인증은 ID 공급자가 담당합니다. LDAP 또는 다른 워크스페이스의 싱글 사인온은 인정하지 않습니다. |
| **싱글 사인온(SSO)만 허용** | 이 워크스페이스의 OIDC, OAuth 2.0 또는 SAML 공급자를 통해서만 로그인할 수 있습니다. 계정 비밀번호, 패스키, LDAP로는 로그인할 수 없습니다. 단, ID 공급자에 장애가 발생해도 액세스할 수 있도록 루트 사용자에게는 이 제한을 적용하지 않습니다. 이 설정을 사용하려면 해당 유형의 공급자를 하나 이상 활성화해야 하며, 설정이 켜져 있는 동안에는 마지막 공급자를 비활성화하거나 삭제할 수 없습니다. 현재 설정으로 [로그인 테스트](#로그인-테스트)를 통과한 활성 공급자가 없는 상태에서 이 설정을 켜면, 경고가 표시되고 워크스페이스 이름을 입력하라는 메시지가 표시됩니다. 감사 이벤트에는 `sso_tested: false`가 기록됩니다. |

로그인이 요구 사항을 충족하지 않으면 다음과 같이 처리합니다.

| 상황 | 결과 |
|---|---|
| 여러 워크스페이스에 속한 계정으로 로그인 | 로그인을 허용하는 첫 번째 워크스페이스에 액세스합니다. |
| 로그인 시 다단계 인증만 누락 | 즉시 패스키 또는 인증 앱을 설정합니다. 다단계 인증을 적용한 세션을 시작하고 복구 코드를 표시합니다. |
| SSO만 허용하는 워크스페이스에만 속한 계정으로 로그인 | 로그인을 거부하고 로그인 페이지에 이유를 표시합니다. |
| 다단계 인증이 필요한 워크스페이스로 전환 | 두 번째 인증 수단이 있으면 즉시 한 번 인증합니다. 없으면 먼저 **보안 및 로그인**에서 다단계 인증을 활성화합니다. |
| SSO만 허용하는 워크스페이스로 전환 | 해당 워크스페이스의 공급자를 통해 로그인할 수 있는 옵션을 표시합니다. |
| 셀프 서비스 가입 | SSO만 허용하는 워크스페이스에서는 가입을 거부합니다. 다단계 인증이 필요한 워크스페이스에서는 계정을 만든 뒤 로그인할 때 다단계 인증을 설정합니다. |
| 데이터베이스 클라이언트에서 계정으로 로그인 | 두 요구 사항 중 하나라도 적용하면 로그인을 거부합니다. 이미 연결된 클라이언트도 다음 요청부터 작동하지 않습니다. [API 토큰](/ko/identity/tokens)을 사용합니다. |
| API 토큰 | 영향을 받지 않습니다. |

계정이 속한 워크스페이스 중 하나라도 다단계 인증을 요구하면 계정 소유자는 마지막 두 번째
인증 수단을 제거할 수 없습니다. [관리자의 재설정](/ko/identity/mfa#관리자가-재설정)은 계속 가능하며,
멤버는 다음 로그인 시 두 번째 인증 수단을 설정합니다.

플랫폼 조직의 요구 사항은 `_sys`
조직의 **설정 → 로그인 요구 사항**에 있습니다. 이 설정을 변경하려면 `sys.settings.signin.manage` 권한이 필요하며, **다단계 인증 필수**만 설정할 수 있습니다.

## 로그인 처리 방식

로그인 페이지에는 활성화된 공급자마다 해당 플랫폼의 로고가 있는 행이 표시됩니다. LDAP
공급자의 경우 해당 행을 선택한 뒤 디렉터리 사용자 이름과 비밀번호를 차례로 입력합니다.

1. 브라우저가 ID 공급자로 이동하고 인증이 끝나면 MoleSignal로 돌아옵니다.
2. 공급자가 사용자 ID를 확인합니다. OIDC는 JWKS의 키(RSA, EC
   또는 EdDSA)나 클라이언트 시크릿(HMAC)으로 ID 토큰을 검증하고, OAuth 2.0은 사용자 엔드포인트에서 정보를 읽습니다. MoleSignal은
   매핑된 필드를 읽습니다.
3. **로그인 허용 그룹**에 속하지 않은 계정의 로그인을 거부합니다.
4. 이전에 로그인한 ID는 이미 계정에 연결되어 있으므로 해당 계정으로 로그인합니다. MoleSignal은
   이메일이 아니라 공급자와 ID의 주체를 기준으로 계정을 찾습니다.
5. 처음 로그인하는 ID가 기존 MoleSignal 계정과 같은 이메일을 사용하면
   해당 계정 소유자가 연결을 확인할 때까지 기다립니다. [기존 계정 연결](#기존-계정-연결)을 참조합니다.
6. MoleSignal 계정이 없고 이메일이
   워크스페이스의 [이메일 도메인](#이메일-도메인) 조건을 충족하면 계정을 생성합니다.
7. 아직 멤버가 아닌 경우 매핑된 역할이나
   기본 역할로 공급자의 워크스페이스에 가입합니다.
8. 기존 멤버의 경우 일치하는 매핑의 역할이 이전 역할을 대체합니다. 비활성화된
   계정은 로그인할 수 없습니다.
9. 브라우저가 로그인 페이지로 돌아와 로그인을 완료하고 로그인 전에 요청한
   페이지를 엽니다. 로그인에 실패하면 로그인 페이지에 이유를 표시합니다.

## 기존 계정 연결

공급자는 자체 워크스페이스 구성원의 신원만 보증합니다. 따라서 공급자가 전달한 이메일 주소만으로는
기존 계정에 로그인할 수 없습니다. 그 계정은 같은 이메일 주소를 사용하는 다른 사람의
계정일 수 있습니다. 공급자 ID로 기존 계정의 이메일 주소를 사용해 처음 로그인하면 로그인
페이지에서 계정 소유자에게 같은 브라우저에서 본인 확인을 요청합니다.

| 방법 | 표시 조건 | 확인 방법 |
|---|---|---|
| **비밀번호** | 계정에 비밀번호가 설정되어 있습니다. | 계정의 비밀번호를 입력합니다. |
| **이메일 인증 코드** | 인스턴스에서 [이메일을 전송](/ko/configuration#알림-설정-및-이메일)할 수 있습니다. | **인증 코드 전송**을 선택한 후 이메일에 있는 6자리 코드를 입력합니다. 코드는 1분에 한 번만 전송할 수 있습니다. |

코드는 전송을 요청한 페이지에서만 사용할 수 있습니다. 따라서
로그인을 시도하지 않았는데 코드가 이메일로 도착하면 무시해도 됩니다. 코드를 5회 잘못 입력하거나 30분이 지나면
공급자를 통해 다시 로그인합니다. 확인을 마치면 공급자 ID가 연결되고 이후에는 해당 ID로 바로
로그인할 수 있습니다. [다단계 인증](/ko/identity/mfa)을 사용하는 계정은 본인 확인 후
두 번째 인증 단계(패스키, 인증 앱 또는 복구 코드)를 완료해야 연결됩니다. 인스턴스가 이메일을 전송할 수 없고 계정에 비밀번호도 없다면 이 화면에서 본인 확인을 할 수 없습니다.
기존 방식으로 로그인하거나 관리자에게 이메일 전송을 설정해 달라고 요청합니다.

워크스페이스 자체 공급자를 통해 만든 계정은 이메일 주소를 확인할 때까지 해당 워크스페이스에만 속합니다.
관리자나 다른 공급자도 해당 계정을 다른 워크스페이스에 추가할 수 없습니다. 이메일로 받은 링크에서
비밀번호를 재설정하거나 이메일 인증 코드로 계정 연결을 확인하면 이메일 주소가 확인됩니다.
Google, GitHub.com, GitLab.com 또는 Microsoft의 테넌트 독립 엔드포인트를 통해 만든 계정에는 이 제한을
적용하지 않습니다. 이러한 공급자는 확인된 이메일 주소만 허용합니다.

연결된 공급자 ID는 다음 메뉴에서 확인하거나 연결을 해제할 수 있습니다.
[계정 설정 → 보안 및 로그인](/ko/account#보안-및-세션).

## 공급자 관리

목록에는 각 공급자의 플랫폼, 유형, 활성화 여부,
[테스트 로그인](#로그인-테스트) 상태, 변경 시점이 표시됩니다.

| 작업 | 결과 |
|---|---|
| **테스트** | [테스트 로그인](#로그인-테스트)을 실행합니다. |
| **편집** | 설정과 매핑을 변경합니다. |
| **비활성화** / **활성화** | 공급자를 비활성화하면 로그인 페이지에서 해당 공급자를 숨기고 해당 공급자를 통한 로그인을 차단합니다. |
| **삭제** | 공급자를 삭제합니다. 이후에는 해당 공급자를 통해 로그인할 수 없습니다. |

## 이메일 도메인

**이메일 도메인**은 다음 방법으로 워크스페이스에 가입할 수 있는 이메일 주소를 제한합니다.
[초대](/ko/identity/members#초대) 또는 싱글 사인온을 사용하는 경우에 적용합니다. **도메인 추가**를 선택하고
`example.com`과 같은 도메인을 입력합니다. 목록이 비어 있으면 모든 이메일 주소로 가입할 수 있지만
공개 계정을 허용하는 공급자는 활성화할 수 없습니다. **제거**를 선택하면 목록에서 도메인을 제거합니다.
