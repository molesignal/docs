**流水线** 用一组有序的步骤转换事件。步骤可以是 [VRL](/zh-Hans/functions) 转换，也可以是内置的路由步骤。流水线有三种运行模式：

| | 实时 | 定时 | 告警事件 |
|---|---|---|---|
| 运行时机 | 接入期间，在事件被存储之前。 | 按间隔运行，处理已经存储的数据。每次运行从上一次停下的地方接着读。 | 开事件之前，或通知策略发送之前。 |
| 信号 | 日志、指标、链路与性能剖析的元数据。 | 日志、指标与链路。 | 告警事件。 |
| 来源与目标 | 一个来源数据流。日志写入一个数据流目标，指标、链路、性能剖析元数据和 RUM 事件留在原来的流里。 | 最多 8 个来源数据流、最多 8 个目标数据流，以及可选的连接器和扩展表。 | 告警规则、外部来源和拨测的告警事件，结果写回事件。 |
| 典型用途 | 在日志到达时做标准化、脱敏并路由到不同数据流，精简指标的标签和 span 的属性。 | 对已存储的数据做扩展、过滤、采样或复制，填充扩展表，并回填历史数据。 | 补充告警事件、调整严重度或丢弃告警事件，并加上模型写的摘要。 |
| 回填与运行历史 | 不支持。 | 支持。 | 不支持，改为统计当天的处理情况。 |

本页介绍实时与定时流水线，[告警流水线](/zh-Hans/pipelines/alert-events)另有专页。

## 在编辑器中搭建流水线

打开 **流水线**，选择 **新建流水线**。编辑器分为三部分。

**设置。** 为流水线命名，选择信号类型，并把 **执行模式** 设为 **实时** 或 **定时**；设为 **告警事件** 则是[告警流水线](/zh-Hans/pipelines/alert-events)。定时流水线还需要设置 **运行间隔**（两次运行之间的间隔）、**首次运行往回读**（第一次运行往回读多久）和 **等待迟到数据**（最新的事件留多长时间等它们到达，再由运行读取）。其下一行是 **运行失败重试**、**投递失败重试**、**死信数据流** 和 **去重字段**，参见[定时与读取位点](#定时与读取位点)和[重试与死信](#重试与死信)。

**流程。** 流程按事件经过的顺序展示流水线：

| 节点 | 含义 |
|---|---|
| **来源** | 流水线读取的数据流。定时流水线可以用 **添加来源** 新增。 |
| **处理步骤** | 各个步骤，按执行顺序排列。用 **添加步骤** 新增。 |
| **目标** | 通过标准接入写入的数据流，以及可选的外部连接器和扩展表。定时流水线可以用 **添加目标** 新增 **数据流**、**连接器** 或 **扩展表**。 |

选择节点即可编辑。流程头部显示 **校验通过**、还有几处待填写，或阻止保存的问题：缺少来源或目标、步骤缺少名称或脚本，以及目标同时又是来源。第一个来源和第一个目标数据流会保存为流水线的 `source_stream` 与 `target_stream`，完整的列表保存为 `function_steps` 中的 `sources` 与 `sinks`。

**试运行。** 保存前让一条样例事件走完全部步骤，不会写入任何数据。编辑 **样例事件**，或从来源数据流取一条近期事件，然后选择 **运行**。有多个来源时，**样例来自** 指定样例来自哪个来源，步骤把它读作 `%source_stream`。结果显示每个步骤之后的事件，以及事件将写入的数据流或丢弃它的步骤。流水线运行时，在某一步失败的事件计为失败；配置了死信数据流时会写进去。

选择 **创建流水线** 保存。在已保存的流水线上，**更多** 提供运行历史、回填和删除。

## 步骤

### 处理步骤

**添加步骤** 提供以下几类步骤：

| 类别 | 步骤 |
|---|---|
| 解析 | **解析 JSON**、**解析键值对** 和 **正则提取**。 |
| 字段 | **重命名字段**、**按正则批量改名**、**删除字段**、**只保留字段**、**设置字段**、**字段脱敏**、**大小写转换**、**类型转换** 和 **查扩展表补充**，参见[查扩展表补充](#查扩展表补充)。 |
| 事件 | **过滤事件** 和 **采样**，参见[过滤与采样](#过滤与采样)。 |
| 分流 | **数据分流**，参见[路由](#路由)。 |
| 代码 | **自定义 VRL**。 |

告警流水线用 **AI 摘要**、**调用接口补充** 和 **查询补充** 代替 **数据分流**，也没有 **采样**，参见[告警流水线的步骤](/zh-Hans/pipelines/alert-events#步骤)。

**按正则批量改名** 和 **只保留字段** 处理一个对象的键，在 **范围** 里指定：留空表示事件的顶层，告警流水线默认 `labels`。**按正则批量改名** 把正则匹配到的键都改名，**替换为** 里的 `$1` 是正则的第一个分组，其余的键不变。**只保留字段** 删除没有列出的键，在事件顶层时 `_timestamp` 总会保留。字段不存在或不是对象时保持原样。

解析类、字段类和事件类步骤以表单方式填写，并以 VRL 执行。**查看生成的 VRL** 显示脚本，**转为 VRL 编辑** 把该步骤变成 **自定义 VRL** 步骤。

**自定义 VRL** 步骤是一段 [VRL](/zh-Hans/functions) 脚本。**从已保存的函数开始** 可以用内置预设或任意已保存的[函数](/zh-Hans/functions)填入脚本，之后仍可编辑。

内置预设随每个实例提供，且只读：

| 预设 | 作用 |
|---|---|
| `normalize-logs` | 解析 JSON 格式的 `message`，添加环境与集群字段，并把 `level` 转为小写。 |
| `route-by-service` | 规范 `service`，并派生出按服务划分的数据流名称（`logs_<service>`）作为路由提示。 |
| `parse-key-value` | 解析 `logfmt` 或 `key=value` 形式的 message，并把字段合并回事件。 |
| `redact-email` | 把 `message` 中的邮箱地址替换为占位符。 |
| `add-intake-time` | 添加接入时间戳，便于排查端到端延迟。 |

<Tip>
  预设与已保存的函数共用 **函数** 页面中的同一个目录。预设只读，在预设上选择 **以此为起点** 可以创建组织自己的函数。
</Tip>

### 过滤与采样

**过滤事件** 和 **采样** 用 VRL 的 `abort` 语句有意丢弃事件。被丢弃的事件不会写入任何目标，也不会进入死信数据流。运行时它计为丢弃，不算失败。

- **过滤事件** 检查一个字段，由 **匹配条件的事件** 决定处理方式：**保留，其余丢弃** 或 **丢弃**。条件可以把值与文本或正则表达式比较、检查字段是否存在，或比较数字。数字条件匹配数字，或能读成数字的文本。
- **采样** 按 **保留比例（%）** 保留事件，取值大于 0、不超过 100。设置 **按字段一致采样（可选）** 后，该字段取值相同的事件要么全部保留，要么全部丢弃，例如同一条链路的所有 Span。留空则逐条随机抽样。

**自定义 VRL** 步骤也可以用同样的方式丢弃事件，两种模式都适用：

```ruby
# 丢弃健康检查
if .path == "/healthz" {
  abort
}
```

在定时流水线中，步骤通过 `%source_stream` 读取事件来自哪个数据流。这个值不会成为事件的字段，除非步骤把它复制进去：

```ruby
# 记下每条事件来自哪个数据流
.origin = %source_stream
```

### 路由

内置的路由步骤决定每个事件写入哪个目标数据流，两种模式都支持。路由有两种形式：

- **固定数据流**；
- **按字段动态分流**：写入由事件中某个字段指定的数据流。可以设置 **流名前缀**，字段缺失、不是字符串，或指向的不是流水线可以写入的数据流时，事件写入 **兜底数据流**。

路由读取该步骤运行时事件中的字段，之后的步骤不会改变已经作出的决定。存在多个路由步骤时，以最后一个结果为准。数据流名称由 1 到 255 个字符组成，可使用 ASCII 字母、数字、`_`、`-` 与 `.`。`.`、`..`、[平台数据流](#平台数据流)以及 [RUM 数据流](#rum-数据流)会被拒绝。不存在的数据流会在首次写入时创建。

在定时流水线中，路由只替换第一个目标数据流，其余目标数据流不受路由影响，收到全部事件。路由不能把事件写回流水线读取的数据流：**固定数据流** 或 **兜底数据流** 是来源时，保存会以 `400` 拒绝；事件的字段指向某个来源时，该事件计为失败并写入死信数据流。

### 查扩展表补充

[扩展表](/zh-Hans/extend-tables)把键映射到一条记录。**查扩展表补充** 按事件里某个字段的值找到键相同的行，把行里的值带到事件中：

| 字段 | 含义 |
|---|---|
| **扩展表** | 到工作区的哪张表里查。 |
| **键字段** | 事件里哪个字段的值是行的键，例如 `host`。`labels.host` 这样带点的名称先找同名的完整字段，再找嵌套路径。 |
| **要带过来的值** | 每一项是 **行里的值** 和它写入的 **写入事件的字段**，用 **添加一项** 增加。 |

表里没有这个键的行时，这一步什么都不改。在 **自定义 VRL** 步骤里，`lookup` 函数返回整行，参见[查扩展表与 IP 地址](/zh-Hans/functions#查扩展表与-ip-地址)。定时流水线还可以把行写进扩展表，参见[写入扩展表](#写入扩展表)。

## 实时流水线

实时流水线在接入期间、存储之前处理日志、指标样本、span 或性能剖析的元数据。可以在编辑器中把 **执行模式** 设为 **实时** 并选择 **信号类型** 来创建，也可以通过 API。日志流水线可以把事件路由到其他数据流：

```bash
curl -X POST http://localhost:5080/api/v1/scheduled_pipelines \
  -H "authorization: Bearer $MS_TOKEN" \
  -H 'content-type: application/json' \
  -d '{
    "name": "route-app-logs",
    "source_stream": "default",
    "target_stream": "default",
    "cron": "",
    "lookback_secs": 300,
    "enabled": true,
    "function_steps": {
      "mode": "realtime",
      "signal_type": "logs",
      "sources": ["default"],
      "sinks": ["default"],
      "retain_source": false,
      "steps": [
        { "transform_name": "lowercase-level", "kind": "vrl",
          "script": ".level = downcase!(string!(.level))" },
        { "transform_name": "route-by-app", "kind": "builtin", "operation": "route",
          "routing": { "kind": "field", "field": "appname", "prefix": "app_", "fallback": "default" } }
      ]
    }
  }'
```

`appname` 为 `checkout` 的事件会进入数据流 `app_checkout`，没有 `appname` 的事件进入兜底数据流 `default`。

规划时需要了解的行为：

- 每个事件按顺序经过各个步骤。某个步骤失败，或结果不是对象，会拒绝该事件。接入响应会列出它，例如 `{"index":1,"reason":"realtime transform `needs-level` failed"}`，同一批中的其他事件仍会被接收。通过 OTLP 发送的 span 例外，参见[实时流水线在哪里运行](#实时流水线在哪里运行)。
- 对日志，**同时保留到源数据流** 会把原始事件与转换后的副本一起保留在来源数据流中，默认关闭。来源与目标是同一个数据流时，只写入转换后的事件。
- 步骤执行 `abort` 会有意丢弃该事件：不做路由，接入响应把它计为已接收，不报错误。来源与目标不同时，**同时保留到源数据流** 仍会保留原始事件。
- 每种数据的每个来源流只能启用一条实时流水线，因此同名的日志流和指标流可以各启用一条。同一个流上再启用第二条会返回 `409`。
- 配置变更对之后的批次生效，10 秒内对所有节点生效；已经开始处理的批次继续使用它读取到的配置。
- 流水线的输出不会再触发另一条流水线。
- 向多个目标数据流的写入不是原子的。整批重试可能让已经成功的数据流出现重复事件，因此该流水线不承诺恰好一次投递。
- 实时流水线不产生运行记录，也不能回填。列表中的 **等待接收** 状态表示配置已启用，并不表示数据已经到达。

### 指标与链路

指标和链路的实时流水线原地处理样本或 span：它们留在进来的那个流里。流程以 **写回原流** 结束，**添加步骤** 不提供 **数据分流**，**同时保留到源数据流** 也不适用。通过 API 创建时，`target_stream` 与 `source_stream` 不同、带有路由步骤或 `retain_source` 为 `true`，都会返回 `400`。RUM 数据流上的实时流水线也原地处理，参见[RUM 数据流](#rum-数据流)。

流水线让样本或 span 赖以成立的字段保持进来时的样子：

| 信号 | 保持不变的字段 |
|---|---|
| 指标 | `metric_name`、`value`、`_timestamp`、指标的元数据（`metric_kind`、`metric_description`、`metric_unit`、`metric_temporality`、`metric_monotonic` 和 `metric_start_time_unix_nano`）、exemplar、OTLP 直方图和摘要存成字段的 `count`、`sum`、`min` 和 `max`，以及标签 `le` 和 `quantile`（它们指明直方图的桶和摘要的分位）。名为 `count`、`sum`、`min` 或 `max` 的标签也保持不变。 |
| 链路 | `trace_id`、`span_id`、`parent_span_id`、`service.name`、`start_time_unix_nano`、`end_time_unix_nano` 和 `duration_ns`。 |

日志流水线不限制字段。指标流水线可以删除、改名或添加其他标签，例如用来降低指标的基数：标签变了的样本属于另一条序列。链路流水线可以丢弃 span、删除属性、改写 span 名称：

```ruby
# 指标：删掉每个样本的 pod 标签
del(.pod)
```

```ruby
# 链路：删除 SQL 文本，把 span 名称里的 ID 归并掉
del(."db.statement")
.name = replace(string!(.name), r'/\d+', "/{id}")
```

保持不变的字段在三处检查：

| 位置 | 检查 |
|---|---|
| 编辑器 | 表单步骤写到这些字段时报出阻止保存的问题；**运行** 试运行时，改动这些字段的步骤标为失败。 |
| 保存 | 每个 VRL 步骤在一条带齐这些字段的样例上运行一次，改动了其中任何一个的步骤以 `400` 拒绝，消息写明步骤和字段。只在样例不满足的条件下才改动的步骤可以保存。 |
| 写入 | 每一步之后都与进来时的字段比对。改动、删除或添加了其中任何一个的步骤，会让这条样本或这个 span 处理失败。 |

### 实时流水线在哪里运行

| 信号 | 接入方式 | 步骤运行的时机 | 处理失败的事件 |
|---|---|---|---|
| 日志 | 所有日志接入。 | 一批数据到达时，存储之前。 | 列在接入响应的 `errors` 中。 |
| 指标 | [`/api/v1/intake/metrics/{stream}`](/zh-Hans/api/intake/native-json)、[OTLP](/zh-Hans/api/intake/otlp) 指标和 [Prometheus remote write](/zh-Hans/api/intake/prometheus)。 | 一批数据到达时，存储之前。 | 列在接入响应的 `errors` 中。 |
| RUM | SDK 的 [RUM 接入](/zh-Hans/rum/events)。 | 一批数据到达时，存储之前。 | 列在 RUM 接入[应答](/zh-Hans/rum/events#应答)的 `rejected` 中。 |
| 链路 | [OTLP](/zh-Hans/api/intake/otlp)（HTTP 和 gRPC）。 | [尾部采样](/zh-Hans/configuration#链路捕获与尾部采样)之后、写入 span 之前。 | 不写入。发送方此前已收到应答，因此节点只在服务日志里记一条警告。 |
| 链路 | [`/api/v1/intake/traces/{stream}`](/zh-Hans/api/intake/native-json)。 | 写入 span 之前。 | 列在接入响应的 `errors` 中。 |
| 性能剖析 | 所有 [Profile 接入](/zh-Hans/profiles)，HTTP 和 OTLP 都算。 | Profile 存成对象之后、元数据行写入之前。 | 列在接入响应的 `errors` 里，这一行不写入。 |

### 链路

步骤每次看到一个 span，它的属性是 `http.method` 这样的字段。步骤改动或删除这样的字段时，span 的 `attributes` 和 `resource` 里的同名属性也跟着改动或删除；步骤新添的字段写进 `attributes`。

- 从 trace 中间丢掉的 span 会让它的子 span 失去父节点。要整条 trace 一起保留或丢弃，用 **采样** 步骤，把 **按字段一致采样（可选）** 设为 `trace_id`。
- trace 列表按写下的 span 计算摘要：span 数、出错数以及每条 trace 的起止时间。span 全部被丢掉的 trace 没有摘要。
- trace 列表和[服务地图](/zh-Hans/apm/service-map)只统计写下的 span。[应用性能](/zh-Hans/apm)的数据在尾部采样之前统计，因此仍然包含被流水线丢掉的 span。

### 性能剖析

**性能剖析** 上的实时流水线处理每条 Profile 的元数据行：服务、类型、时间、标签和对象的位置。Profile 本身是一个对象，步骤不会碰它。一个组织的 Profile 都进入 `default` 数据流，所以这是流水线唯一的来源，元数据行也留在这里。定时流水线不读 Profile。

步骤可以改 `service`，增改 `labels` 和其他字段，也可以丢弃一行，例如给所有 Profile 打上环境标签，或者去掉某个噪声大的服务。被丢弃的一行不再出现在[性能剖析](/zh-Hans/profiles)页面，它的对象留到数据流的保留期结束。

以下字段保持进来时的样子，规则同[指标与链路](#指标与链路)：`id`、`object_key`、`archived_bytes`、`_timestamp`、`profile_type`、`duration_nanos`、`sample_count`、`total_value`、`unsymbolized`、`trace_id` 和 `span_id`。火焰图和下载靠它们找到并合并对象。

## 定时流水线

定时流水线按间隔读取它的来源数据流，应用转换链，并把输出写入它的目标数据流。它还可以把同一批事件投递到连接器。

### 目标与连接器出口

定时流水线通过标准接入写入最多 8 个 **目标数据流**（写入后可被查询），投递到外部 **连接器**，并把行写进 **扩展表**：

- 每条事件写入第一个目标数据流，即 `target_stream`，除非路由步骤为它选了别的数据流。
- 其余每个目标数据流都收到经过各步骤的全部事件。
- 每个已启用的连接器都收到经过各步骤的全部事件。
- 经过各步骤的每条事件都在每张扩展表里写成一行，参见[写入扩展表](#写入扩展表)。

| 连接器 | 投递负载 |
|---|---|
| **S3** | 批量 JSON Lines `PUT` 到 `s3://<bucket>/<prefix><id>.jsonl`。 |
| **Kafka** | 每条事件向配置的 topic 产生一条 JSON 记录。 |
| **HTTP / Webhook** | 每批事件以 NDJSON 或 JSON 数组，用 `POST` 或 `PUT` 发送到配置的地址。 |

在 **流水线 → 连接器** 添加连接器，再用 **添加目标 → 连接器** 把它们加入流程的 **目标**。一条流水线在同一次运行里写入它的数据流并投递到它的连接器。流水线不能写入它读取的数据流：目标数据流同时是来源时，会以 `409` 拒绝。

目标数据流不必事先存在：第一次写入时按输出推断 schema 建流，之后的运行像其他数据流一样补充新字段。事件的字段类型与已有目标数据流的 schema 冲突时，只拒收该事件：它计为失败并写入死信数据流，同一次运行的其余事件照常写入。如果某个目标数据流拒收了一次运行的全部事件，而流水线没有死信数据流，这次运行会失败，原因出现在它的 `error` 中。回填的写入方式相同。

### 写入扩展表

用 **添加目标 → 扩展表** 可以让定时流水线持续更新工作区的一张[扩展表](/zh-Hans/extend-tables)，例如维护每台主机所属团队的表，再由其他流水线用 `lookup` 读取。一条流水线最多写入 8 张扩展表。

- 每条事件按表的 **查询键** 字段的值写成一行。`kubernetes.pod_name` 这样带点的键字段先找同名的完整字段，再找嵌套路径。文本原样作为键，数字和布尔值按字面写法作为键。
- 表定义了 **Value 字段** 时，按名称只写事件里的这些字段，事件没有或值为 `null` 的字段不写；表没有 Value 字段时写入整条事件。
- 新行替换键相同的已有行。同一次运行中多条事件的键相同时，以 `_timestamp` 最新的一条为准。
- 键字段缺失、为空、为 `null`、是对象或列表的事件不会写进这张表：它计为失败，写入死信数据流，`dead_letter_destination` 为 `table:<表名>`。表不存在时，所有要写进它的事件都这样处理。
- 存储收不下这些行时，这个窗口像写入数据流失败一样重试，参见[重试与死信](#重试与死信)。行按键写入，重写一遍不会改变结果。

### 把来源数据流从查询中隐藏

当一个兜底来源数据流扇出成每服务或每租户的目标流时，来源数据流会继续堆积原始事件。要让查询和仪表盘只对准路由后的数据流，把来源数据流标记为 **不可查询**：打开 **数据流 → 来源 → 设置**，关闭 **可查询**。

不可查询的数据流照常接收并保留数据，也照常为流水线供数。它会从查询选择器中隐藏，SQL 与 PromQL 搜索会以 `stream is not queryable` 拒绝它。随时可以再打开开关。

### 定时与读取位点

| 字段 | 编辑器 | 说明 |
|---|---|---|
| `cron` | **运行间隔** | 间隔简写：`every:30s`、`every:5m` 或 `every:1h`。 |
| `lookback_secs` | **首次运行往回读** | 每个来源第一次运行往回读多久，默认 300。 |
| `function_steps.delay_secs` | **等待迟到数据** | 最新一段时间留给迟到事件的秒数，过后才由运行读取。0 到 3600，默认 60。 |
| `enabled` | **按计划运行** | 暂停或恢复调度，无需删除流水线。 |

Runner 不解析标准 cron 表达式。不符合 `every:` 语法的计划会被拒绝并返回 `400`：`scheduled pipelines require every:Ns/m/h and a positive lookback`。

流水线为每个来源保存一个读取位点：该来源在这个时间之前的事件都已处理。每次运行从各来源的读取位点读到「运行时间减去等待迟到数据的时长」，应用转换链并写出结果。读取位点随后移到这次读到的地方，下一次运行从那里接着读。在等待时长内到达的事件只读取一次。更晚到达、时间戳已被运行越过的事件不会被读取，因此来源有迟到数据时，应调大 **等待迟到数据**。

- 每个来源第一次运行往回读 `lookback_secs`。之后新加的来源也一样。
- 每次运行对每个来源最多读取运行间隔、`lookback_secs` 与一小时三者中最长的一段。落后更多的来源会在下一次检查时再次运行，一段一段地追赶，直到赶上。
- 重新启用已暂停的流水线会从头开始：第一次运行从运行时刻往回读 `lookback_secs`，不管暂停前读到了哪里。这个窗口之外的时间可以提交[回填](#回填)来处理。

Runner 每 15 秒检查一次到期的流水线，因此很短的间隔按这个粒度运行。

<Note>
  定时 runner 在 `alert` 角色上运行（`standalone` 包含该角色）。存在多个 `alert` 节点时，每条流水线归一个节点负责，因此启用的流水线每个间隔只触发一次，而不是每个节点一次，参见[分角色部署](/zh-Hans/deployment/role-based#alert-节点之间的分工)。
</Note>

### 重试与死信

| 字段 | 编辑器 | 说明 |
|---|---|---|
| `function_steps.retry.run_retries` | **运行失败重试** | 读取或写入失败的窗口还会再尝试的次数。0 到 10，默认 3。 |
| `function_steps.retry.delivery_retries` | **投递失败重试** | 连接器投递在本次运行内还会再尝试的次数。0 到 10，默认 3。 |
| `function_steps.dead_letter_stream` | **死信数据流** | 保存无法处理、写入或投递的事件的日志数据流，可选。 |
| `function_steps.dedupe_field` | **去重字段** | 同一次运行中，该字段的值已经出现过的事件会被丢弃，可选。 |

读取某个来源或写入某个数据流失败时（例如存储不可用），该来源的读取位点保持不动：

- 同一个窗口在 30 秒后重试，之后每次等待时间加倍，最长不超过运行间隔。
- 重试只写入之前没有收下这个窗口的目标。
- 重试次数用完后跳过这个窗口：读取位点越过它，运行的 `warning` 写明是哪个来源、哪一段时间没有处理。
- 每次尝试都会遇到的失败（例如配置无效）会让读取位点停在原处，不安排重试。每次常规运行都从同一位置重新读取，因此修复流水线期间不会跳过任何数据。

连接器投递失败时，在本次运行内重试：先等 1 秒，之后每次等待时间加倍，最长 30 秒。连接器仍然没有收下的事件写入死信数据流。之后的运行（包括这个窗口的重试）不会再投递它们。

死信数据流是日志数据流，与流水线处理的信号无关，因此在 **日志** 中查看死信。它不能是流水线读取或写入的数据流。每条死信是原事件加上以下字段：

| 字段 | 内容 |
|---|---|
| `dead_letter_pipeline` | 流水线名称。 |
| `dead_letter_stage` | `transform`：某个步骤处理该事件失败，或把它路由到了来源；`write`：目标数据流或扩展表没有收下它；`deliver`：连接器没有收下它。 |
| `dead_letter_reason` | 出错原因。 |
| `dead_letter_source` | 事件读取自哪个数据流。 |
| `dead_letter_destination` | 没有收下该事件的数据流、连接器或扩展表（`table:<表名>`），仅 `write` 与 `deliver` 带有。 |

`transform` 死信保留事件读取时的样子，`write` 与 `deliver` 死信保留事件发送时的样子。没有死信数据流时，这些事件计为失败，不会保留。

**去重字段** 在各步骤之后生效，范围是同一次运行内的全部来源：保留该字段每个值的第一条事件，之后值相同的事件被丢弃。没有该字段的事件全部保留。事件中没有同名的完整字段时，`user.id` 这样的名称会访问嵌套对象。

### 运行历史

每次读取了窗口的运行都会记录。可以在流水线的 **运行历史** 标签页、编辑器的 **更多 → 运行历史** 中查看，也可以用 `GET /api/v1/scheduled_pipelines/{id}/runs`。

| 列 | 内容 |
|---|---|
| **状态** | 运行的状态；运行重试了失败的窗口时，附带第几次尝试。 |
| **开始时间** 和 **时长** | 运行何时开始、用了多久。 |
| **事件** | 这次运行读入多少事件，其中多少写出、丢弃或失败。 |
| **问题** | 失败运行的 `error`，或虽然完成但遇到问题的运行的 `warning`，例如事件被拒收、投递不成功或窗口被跳过。 |

运行读入的每条事件最终落入其中一项：

- **写出**：它应去的每个目标都收下了它。
- **丢弃**：某个步骤用 `abort` 丢弃了它，或 **去重字段** 去掉了它。
- **失败**：某个步骤处理它时失败、它被路由到了来源，或某个目标没有收下它。

窗口失败、某个目标数据流一条事件都没有收下且没有死信数据流，或流水线根本无法运行时，这次运行失败。计划了重试时，运行历史页面会写明哪个来源失败以及下一次尝试的时间。

### 回填

要按需处理历史窗口，在编辑器中打开 **更多 → 回填**，设置 **起始** 和 **结束**，然后选择 **提交回填**。也可以通过 API 提交：

```bash
curl -X POST http://localhost:5080/api/v1/scheduled_pipelines/$PIPELINE_ID/backfill \
  -H "authorization: Bearer $MS_TOKEN" \
  -H 'content-type: application/json' \
  -d '{"start_micros": 1790000000000000, "end_micros": 1790086400000000}'
```

窗口不能超过 31 天。请求返回 `202`，每个来源一个任务，各带 `job_id` 与 `monitor` 路径。每个任务通过异步[搜索任务](/zh-Hans/deployment/role-based#异步搜索任务) worker 运行：在窗口内读取它的来源，应用同一条转换链，并像运行一样写入、投递和保存死信。

回填不改变读取位点，因此定时运行照常读取原本要读的数据。回填窗口与运行已经处理过的时间重叠时，这些事件会再写一遍。

## RUM 数据流

[RUM 数据流](/zh-Hans/rum/events#事件的存储位置)（例如 `rum_views` 和 `rum_errors`）只由 RUM 接入写入，因为 RUM 页面按固定的结构读取其中的行。定时流水线可以读取它们，例如把错误复制到自己的数据流或连接器。RUM 数据流不能作目标数据流、路由选出的数据流或死信数据流：编辑器不会把它列为目标或死信数据流，手动输入的名称在保存前会被标出来，API 返回 `400`。

`rum_views`、`rum_actions`、`rum_errors`、`rum_resources`、`rum_long_tasks` 和 `rum_vitals` 上的实时流水线像[指标和链路](#指标与链路)的实时流水线一样原地处理事件：把 **信号类型** 设为 **日志**，再选 RUM 数据流作来源。`rum_sessions` 不能挂流水线，因为它由页面数据在到达时合成。

- 只能改 `context`、`usr.extra`、`feature_flags` 和 `extra`，以及它们里面的内容，例如 `.context.plan`。其余列是 RUM 页面读取的内容：改动、删除或添加其中任何一列的步骤会让这条事件处理失败。
- 操作、错误、资源和长任务可以丢弃。页面和 Web Vitals 不能丢：丢弃它们的步骤会让这条事件处理失败；能丢弃事件的步骤（例如带 `abort` 的 VRL 步骤、**过滤事件** 或 **采样**）不能保存在 `rum_views` 或 `rum_vitals` 上。
- 保存流水线时，每个 VRL 步骤在一条带齐各列的样例上运行一次，在样例上改动了其他列的步骤以 `400` 拒绝。

```ruby
# 删除应用写进自定义上下文的邮箱地址
del(.context.email)
```

## 平台数据流

[平台数据流](/zh-Hans/streams#平台数据流)（例如 `_audit` 和 `_synthetic_results`）只由 MoleSignal 写入。任何流水线都不能写入它们：平台数据流不能作目标数据流、路由选出的数据流、死信数据流，也不能作实时流水线的来源。编辑器不会把它列为目标、死信数据流或实时流水线的来源，手动输入的名称在保存前会被标出来。API 返回 `400`。

定时流水线可以读取除 `_molesignal` 以外的平台数据流，例如通过连接器把 `_audit` 里的审计事件投递到 SIEM。保存读取 `_audit` 的流水线或提交它的回填需要 `audit.read`，服务账号的 Token 返回 `403`。流水线用最后保存它的人的权限读取 `_audit`（暂停和恢复不算保存）：这个人失去 `audit.read` 时，流水线停在读取位点，这个人恢复权限或持有权限的人保存后，从那里接着读。流水线详情页顶部和编辑器的 **来源** 节点用 **读取 \_audit 的身份** 显示这个人。参见[审计数据流](/zh-Hans/settings/data-security#审计数据流)。

## 权限

- `pipelines.read`：列出流水线并读取运行历史。
- `pipelines.create`：创建流水线。
- `pipelines.edit`：修改流程、步骤、调度或回看窗口。
- `pipelines.pause`：启用或暂停流水线。
- `pipelines.run`：提交回填任务。
- `pipelines.delete`：删除流水线。

创建、修改或回填读取 `_audit` 的流水线还需要 `audit.read`，暂停或恢复它不需要。
