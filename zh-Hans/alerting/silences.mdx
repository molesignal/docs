静默会暂停匹配事件的通知与升级，事件本身仍会记录。语义分组把相关事件收拢到一起，让处理人员一次处理。两者都不会修改规则。要按「有更严重的事件在」来压住次要事件，用[抑制](/zh-Hans/alerting/inhibition)。

## 静默策略

打开 **告警 → 静默策略**。每条策略显示状态、时间窗和匹配条件。

| 状态 | 含义 |
|---|---|
| **正在静默** | 匹配的事件处于静默中。 |
| **尚未开始** | 时间窗尚未开始。 |
| **未到时段** | 周期重复的时间窗当前不在生效时段内。 |
| **已结束** | 时间窗已结束。 |
| **已关闭** | 策略已停用。 |

创建策略：

1. 点击 **新建静默策略** 并填写 **名称**，保持 **启用** 开启。
2. 在 **匹配** 中，为事件标签上的每个条件点击 **添加匹配器**，例如 `service` `=` `checkout`。所有匹配器都必须命中，`=~` 与 `!~` 为正则表达式。没有匹配器时，策略匹配 **所有事件**。
3. 在 **时间窗** 中选择 **窗口类型**：
   - **固定区间**：一个 **开始** 和一个 **结束**；
   - **每周重复**：一个 **时区**，加上一段或几段时间，每段选 **星期**，写 **开始（HH:MM）** 和 **结束（HH:MM）**，精确到分钟，例如每周六 02:00 到 06:00；结束不晚于开始表示跨午夜。在 **节假日** 里可以按[节假日日历](/zh-Hans/alerting/on-call#节假日日历)把放假的日子去掉，或只在放假的日子生效；
   - **节假日**：一个 **时区** 和一份 **节假日日历**：日历里每个放假的日子，整天静默，例如测试环境在法定节假日不发告警；
   - **每月一次**：一个 **时区**，按 **每月第几天**（这个月没有这一天时取最后一天），或按 **第几个**（第 1 到第 5 个，或最后一个）**星期几**，加上 **开始时刻（HH:MM）** 和 **持续（分钟）**，最长 7 天。例如每月第一个星期日 02:00 起 240 分钟。某个月没有第五个星期几时，这个月跳过。
4. 在 **备注** 中填写 **原因**，然后点击 **创建静默**。

列表里循环的静默标出 **下次开始** 或 **结束** 的时刻，由服务端按时区和夏令时算出。

静默匹配事件携带的标签：规则的标签，以及[按维度拆分](/zh-Hans/alerting/rules#按维度拆分)的规则中各组的取值。[外部告警](/zh-Hans/alerting/sources)开的事件带 `alert.source=external`、`external.kind`（例如 `alertmanager`）、告警自己的标签和来源的附加标签，例如用 `external.kind` `=` `grafana` 静默所有 Grafana 发来的告警。每个计划内的静默都应写明受影响的服务和结束时间，并让它到期自动结束，而不是事后再删除。

<Warning>
  静默只是隐藏通知，并不能证明服务已经恢复。时间窗结束时请查看事件列表。
</Warning>

### 静默期间的通知

静默生效时，匹配的事件照常开启和记录，通知按类型这样处理：

| 通知 | 静默期间 | 静默结束后 |
|---|---|---|
| 告警触发、告警已升级 | 不发，升级停在当前一级。 | 事件仍未确认、未恢复的，补发触发通知，升级接着推进；当前一级的确认超时在静默期间已过的，紧接着通知下一级。静默期间已确认或已恢复的事件不再补发。 |
| 接收顺序里的后续步骤、通知策略的确认超时升级 | 不发。 | 仍没人确认的，接着发。 |
| 告警已确认、告警已恢复 | 触发通知在静默开始前已经发出的，照常发；触发通知被静默挡下的，不发。 | 照常发。 |

时间窗结束、策略被停用或被删除，都算静默结束。

### 静默单个事件

事件上的 **静默** 只暂停这一个事件的通知与升级，时长可选 **1 小时**、**4 小时**、**24 小时** 或 **7 天**，还可以填写 **原因**。它不会停用规则，也不会静默同一服务的其他事件。这条静默会出现在 **静默策略** 中，可以在那里修改或提前移除。

创建、修改和移除静默需要 `alerts.mutes.manage`。

## 语义分组

打开 **告警 → 分组**。语义分组把标签取值相同的事件收成一组，类似 Alertmanager 的 `group_by`。通过 API 确认或解决分组时，组内每个事件都会同样处理，参见[事件分组](/zh-Hans/alerting/incidents#事件分组)。

1. 点击 **新建分组** 并填写 **名称**，例如 `critical-by-service`，保持 **启用** 开启。
2. 在 **匹配条件** 中添加事件必须满足的条件，例如 `severity` = `critical`。所有条件都必须命中；没有条件时，分组适用于所有事件。
3. 在 **分组键** 中填写 **分组标签键**，用逗号分隔，例如 `service, region`。这些标签取值相同的事件会收成同一组。
4. 点击 **创建分组**。

已禁用的分组会被跳过。删除分组会保留事件，只移除分组规则。

**导入** 从 JSON 创建分组：分组数组，或带 `groups` 数组的对象。

```json
[
  {
    "name": "crit-by-service",
    "enabled": true,
    "matchers": [{ "label": "severity", "op": "eq", "value": "critical" }],
    "group_by": ["service"]
  }
]
```

管理分组需要 `alerts.semantic_groups.manage`。
