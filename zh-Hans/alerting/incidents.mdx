[规则](/zh-Hans/alerting/rules)触发、[拨测失败](/zh-Hans/synthetics#告警事件)或[告警来源](/zh-Hans/alerting/sources)收到外部告警时会开启事件。事件记录规则、取值、标签以及结束前的每一步。打开 **告警 → 告警事件**，或按 `⌘⌥A`。读取事件需要 `alerts.incidents.read`；确认、解决和暂缓需要 `alerts.incidents.acknowledge`；[处理事件](#处理事件)里的其他操作需要 `alerts.incidents.update`，升级和合并需要 `alerts.incidents.escalate`；静默需要 `alerts.incidents.silence`。经飞书 App、Slack App 收到的告警通知也能在卡片上直接确认、解决或暂缓，见[告警卡片](/zh-Hans/im#告警卡片)；短信和电话能回复代码或按键处理，见[回复短信与电话按键](/zh-Hans/notification-channels#回复短信与电话按键)。

## 事件状态

| 状态 | 列表中的标签 | 含义 |
|---|---|---|
| `open` | **等待确认** | 正在触发，还没有人确认，升级继续进行。 |
| `acknowledged` | **处理中** | 已有人接手，升级停止。 |
| `resolved` | **已恢复** | 已结束：规则已恢复，或有人解决了它。 |
| `closed` | **已关闭** | 已结束。 |

规则满足[恢复条件](/zh-Hans/alerting/rules#恢复条件与没有数据)时，打开的事件会自动解决；外部来源报恢复时，它的事件也会解决，已确认的一起解决，见[外部告警怎样变成事件](/zh-Hans/alerting/sources#外部告警怎样变成事件)。已确认的事件保持已确认，直到有人解决它；升级策略设了[确认后仍未解决](/zh-Hans/alerting/on-call#确认后仍未解决)时，超过这个时间会退回 **等待确认** 并重新通知。暂缓中的事件是 **处理中**。每条规则（或按维度拆分的规则的每一组）同一时间最多只有一个活动事件。

## 事件列表

**告警事件** 页面顶部统计受影响的服务数、等待确认的事件数，以及最近 24 小时恢复的事件数。摘要说明当前有多少事件在触发、最早的一个已持续多久，以及正在评估多少条规则。**最近恢复** 列出最近结束的事件。

在 **触发中** 与 **等待确认**（尚无人接手的事件）之间切换；当前用户属于某个团队时还有 **我的团队**，只列[分派](/zh-Hans/alerting/routing)给这些团队的事件。右侧可以按优先级筛选，或只看 **不设** 优先级的。事件按严重度排，同样严重的按优先级、再按开始的早晚。每一行显示级别、事件及其服务（低紧急度的事件在这里标出 **低紧急度**）、优先级、状态、持续时间，以及负责人和分派到的团队，并提供三个操作：

| 操作 | 效果 |
|---|---|
| **确认** | 接手事件。事件变为 **处理中**，升级停止。 |
| **静默** | 只暂停这个事件的后续通知与升级。参见[静默单个事件](/zh-Hans/alerting/silences#静默单个事件)。 |
| **Runbook** | 打开规则的处理指南（如果有）。 |

勾选几行（表头的勾选框全选）后，列表上方出现批量处理栏：**确认**、**解决**、**暂缓**、**转派**、**调整**（严重度、优先级或紧急度），选中两个以上时还有 **合并**，在弹出的对话框里选出要保留的主事件。一次最多处理 100 个事件；有处理不了的（例如已经恢复）时，提示失败的个数和第一个原因，其余照常处理。

### 新建事件

规则没抓到的问题，比如客户报障、有人发现的异常，也可以开一个事件，照常通知和升级。点击列表上方的 **新建事件**（需要 `alerts.incidents.create`）：

1. 在 **发生了什么** 中填写 **标题**（必填）和 **说明**（支持 Markdown），选 **严重度**（默认错误）、**优先级** 和 **紧急度**（默认按升级策略），需要时填 **受影响的服务**（逗号分开）和 **标签**（每行一个 `key=value`）。
2. 在 **交给谁** 中选一种：

   | 选项 | 效果 |
   |---|---|
   | **按路由分派** | 和规则开的事件一样按[告警路由](/zh-Hans/alerting/routing)分派。 |
   | **交给团队** | 用团队的值班策略，没设时用默认策略。 |
   | **交给升级策略** | 从这条策略的第 1 级开始通知。 |
   | **指定成员** | 直接通知最多 10 个人，不用升级策略。 |

3. 需要时勾选 **同时宣布为重大事件**，然后点击 **创建事件**，页面跳到事件详情。

手动建的事件带标签 `alert.source=manual`，注解 `created_by` 记创建人，说明记在注解 `description`；它不经过告警流水线，每次都是新事件，不和别的事件去重，也不会自动恢复，要人来解决。详情页头的 **手动创建** 显示创建人，洞察里这类事件归成一项 **手动创建**。Mole Agent 的 `create_incident` 工具也能建事件（要一人审批）。

## 事件详情

点击事件即可打开详情。页头显示状态、触发时间、规则和已持续时间，并提供 **确认**、**解决** 和 **更多操作**：**更多操作** 里是[处理事件](#处理事件)的各项操作和 **静默**。

| 分区 | 内容 |
|---|---|
| **时间线** | 何时触发、通知了谁、谁做了什么（确认、转派、增派、升级、暂缓、改严重度、合并、解决，以及修复动作、工单和重大事件的各步）、[告警流水线](/zh-Hans/pipelines/alert-events#处理结果)在开事件之前改了什么、，在哪里做的（接口、IM、回复短信、电话按键、Mole Agent），以及其间经过的时间。底部可以添加[备注](#备注)，下方列出并入这里的事件。 |
| **调查** | **打开触发查询** 在探索页中重放当时的精确查询。**相关日志** 和 **相关指标** 在同一时间范围打开受影响的上下文。RUM 指标的事件还有 **在 RUM 中打开**。 |
| **AI 根因** | Mole Agent 的分析。参见 [AI 根因](#ai-根因)。 |
| **跨信号引用** | 证据中出现的服务、Trace ID 和主机，均可点击跳转。 |
| **触发查询** | 查询及其返回的值。**展开样本值** 显示样本行。 |
| **元数据** | 事件的标签与注解。 |
| **负责人** | 升级通知到的人员，以及[分派](/zh-Hans/alerting/routing#事件上的分派)到的团队和依据；事件暂缓、并入了别的事件或严重度由人设置时，在这里注明。 |
| **影响范围** | 关联到某个服务的事件，显示该服务沿服务地图影响到的范围。参见[事件的影响范围](/zh-Hans/apm/insights#事件的影响范围)。 |
| **样本会话** | RUM 指标的事件，列出体现问题的会话，每个都有回放。参见 [RUM 告警](/zh-Hans/rum/alerts#事件)。 |
| **相似事件** | 近 90 天里像它的事件，以及当时怎么结束的。参见[相似事件与最近变更](#相似事件与最近变更)。 |
| **最近变更** | 触发前后它的服务和下游服务上报的部署、配置和开关变更，以及前一天改过的这条规则。 |
| **修复动作** | 适用于这个事件的修复动作，以及发起过的执行和审批。参见[修复动作](/zh-Hans/alerting/remediation)。 |
| **工单** | 事件在 Jira、ServiceNow 或飞书项目里的工单和它们的状态，可以在这里建单。参见[工单](/zh-Hans/alerting/tickets)。 |
| **重大事件** | 宣布重大事件，指派角色，进入作战室和会议，按任务分工，发进展。参见[重大事件与复盘](/zh-Hans/alerting/major-incidents)。 |
| **复盘** | 事件的内部复盘：**写复盘** 按模板起草，**打开复盘** 继续写。参见[复盘](/zh-Hans/alerting/major-incidents#复盘)。 |

## 处理事件

**更多操作** 里的操作都记在时间线上，也能通过 [API](#事件-api) 完成。Mole Agent 也能做这些操作：添加备注要提问的人确认，其余要一人审批，见[审批与执行](/zh-Hans/agent#审批与执行)。Mole Agent 还能建工单、指派重大事件的角色、加任务和起草复盘（要提问的人确认），宣布重大事件和发进展（要一人审批），以及提议执行修复动作（一律要两人审批）。已恢复的事件和并入别处的事件不能再这样处理，但仍可以[添加备注](#备注)。

| 操作 | 效果 |
|---|---|
| **转派** | 转给成员（最多 10 个）：他们成为负责人并收到通知，事件回到 **等待确认**，仍没人确认时照常往下升级。转给团队：改用这个团队的值班策略，团队没设时用默认策略，从第 1 级重新开始。转给升级策略：改用这条策略从第 1 级重新开始，团队不变。可以附一条备注，记在时间线上。 |
| **增派** | 选中的人加进负责人并收到通知，事件状态不变。 |
| **立即升级** | 选一级，立即通知这一级的目标，默认是下一级；只列适用于事件严重度的级别。已确认的事件退回 **等待确认**。 |
| **暂缓** | 1、4、8 或 24 小时，或 **自定义…**（1 分钟到 7 天）。等待确认的事件先被确认；暂缓期间不发通知，到点后事件退回 **等待确认**，负责人重新收到通知。**取消暂缓** 立即结束。 |
| **严重度** | 手动设置后，规则、告警来源和拨测检查都不再改它。调高等待确认的事件时，按新的严重度从第 1 级重新通知；调低只改严重度。 |
| **优先级** | 组织的[优先级档位](/zh-Hans/alerting/on-call#紧急度与优先级档位)之一，默认 P1 到 P5，或 **不设**。只改优先级，不重新通知。优先级用在列表的列和筛选、[路由规则](/zh-Hans/alerting/routing)的条件、重大事件的自动宣布、工单的优先级映射和洞察的拆分里。 |
| **紧急度** | **高紧急度** 或 **低紧急度**，见[紧急度](/zh-Hans/alerting/on-call#紧急度)。从低调到高时，等待确认的事件从第 1 级重新通知；调低只改紧急度，之后不再往下升。手动改过以后，支持时段不再改它。 |
| **合并** | 把其他进行中的事件并入这个事件，见[合并事件](#合并事件)。 |
| **静默** | 见[静默单个事件](/zh-Hans/alerting/silences#静默单个事件)。 |

这些操作发出的通知是升级通知，模板里的 `{{escalation.reason}}` 说明原因：`reassigned`（转派）、`responder_added`（增派）、`manual`（立即升级）、`snooze_ended`（暂缓到点）、`severity_raised`（调高严重度）、`urgency_raised`（紧急度升为高），或 `ack_timeout`（确认后超时未解决）。模板还能用 `{{urgency}}` 和 `{{priority}}`。见[模板变量](/zh-Hans/notification-channels#模板变量)。

### 合并事件

同一个问题开出了几个事件时（例如一次故障让几条规则都触发），把它们并入一个主事件：并入的事件不再单独通知和升级，也不再出现在事件列表和洞察中，而是列在主事件时间线的下方。主事件解决时，并入的事件一并解决；并入的事件先自己恢复时，主事件的时间线记一笔。一次最多并入 50 个事件，合并后不能拆开。

在详情页的 **更多操作 → 合并** 里勾选要并入的事件；在事件列表里勾选几个后点 **合并**，再选出主事件。

### 备注

时间线底部的输入框添加备注，最多 4000 字，记下发现了什么、做了什么，接手的人一眼能看到。转派时附的备注也记在这里。Mole Agent 读取事件时会带上最近的几条备注。

## AI 根因

为 Mole Agent 配置模型服务后，它会在后台分析新事件，并把有证据支持的结果保存到事件中。**生成** 立即请求一次分析，**重新生成** 替换已有结果。可以用 **有帮助** 或 **没帮助** 评价结果，评价会进入[质量](/zh-Hans/quality)。

生成需要 Mole Agent 权限。组织当天的 Mole Agent token 预算用完后，自动分析会暂停，手动生成按预算设置处理。参见[用量与预算](/zh-Hans/agent#用量与预算)。

## 相似事件与最近变更

**相似事件** 在同一组织近 90 天的事件里找出最像这个事件的，最多 5 个，并注明像在哪里：**同一告警**（同一指纹）、**同规则**、**同服务**、**标签相近**、**标题相近**（中文标题一样能比）或 **同团队**。每个都显示持续了多久、谁解决的、有几条备注，以及 AI 根因的第一句，接手的人能先看看上次是怎么处理的。

**最近变更** 列出触发前 30 分钟到触发后 10 分钟之间，事件的服务和它在服务地图上的下游服务[上报的变更](/zh-Hans/apm/deployments#从-ci-上报发布)：部署（失败或回滚的会标出）、配置和开关，标明是不是下游的，有流水线链接的可以点开。事件的规则在触发前一天里改过时也列出来。没有服务地图时只看事件自己的服务。

## 事件分组

[语义分组](/zh-Hans/alerting/silences#语义分组)把相关事件（例如某个服务的所有严重事件）收成一组。用 `POST /api/v1/alerts/incident_groups/{id}/ack` 或 `/resolve` 确认或解决分组时，组内每个事件都会同样处理。

## 历史

**告警 → 历史** 列出过去的事件，包括当前状态、触发和恢复时间以及持续时间。可以按事件名称、服务或事件 ID 搜索，并按级别和状态筛选。

## 洞察

**告警 → 洞察** 展示工作区在最近 24 小时、7 天或 30 天内的响应情况：

| 部分 | 显示内容 |
|---|---|
| 摘要 | 仍需处理的事件数、已恢复事件的 **平均恢复时间**，以及 **快速恢复事件**：60 秒内恢复的占比，是规则噪声较大的信号。 |
| **事件时间趋势** | 24 小时内按小时、更长范围按天统计的事件数，使用浏览器时区，并标出峰值。 |
| **主要影响服务** | 事件中出现最多的服务。规则需要带 `service` 标签。 |
| **主要触发规则** | 开启事件最多的规则，调优应从这里开始。 |
| **响应** | 平均接手时间（P50、P90）、恢复时间中位数、升级率和有人接手的比例，与前一段同样长的时间相比；各级确认率；第一次接手在哪里做的（网页、接口、IM 卡片、回复短信、电话按键或 Mole Agent）；以及按团队、服务、个人和优先级拆开的接手、恢复和升级（没设优先级的事件不算在优先级里）。第一次接手是第一次确认，没人确认就被人解决的算在解决的那一刻。 |
| **值班负担** | 每个人值了多久的班、收到几次告警通知，其中几次在夜里（按各自排班的时区 22:00 到次日 08:00）、几次在周末，被吵醒了几个晚上，以及先接手的事件数和平均接手时间。排班详情里也有这个排班成员的负担。 |
