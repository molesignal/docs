MoleSignal APM 把后端 OpenTelemetry trace span 转换成有界 RED 聚合，无需另行维护指标埋点，即可发现慢服务、失败端点、高开销依赖、重复出现的后端错误，以及部署版本之间的性能回退。服务目录记录每个服务归谁负责、有多重要。

<Note>
  APM 不需要另一套 SDK，也不会新增遥测数据流。发送完整埋点的 trace 后，MoleSignal 会在链路去重之后、尾采样之前派生 APM 数据。因此，最终被采样丢弃的 trace 仍可计入 APM 指标，被[实时流水线](/zh-Hans/pipelines#链路)丢掉的 span 也一样。
</Note>

## 页面

APM 以概览为首页，每个服务有自己的页面。

| 页面 | 主要用途 |
|---|---|
| **概览** | 所有服务放在一起看：活跃服务、吞吐、错误率、p95 及 p50、p90、p99 和平均耗时、Apdex；服务健康的分布和变化；最慢、错误率最高和流量最大的服务；洞察，即和上一时段、上周同时段相比有变化的指标、附近的变更，以及可以省下时间的地方；指向服务的进行中告警；时间范围内部署的版本；环境分布；以及服务在埋点中缺了什么。 |
| **服务** | 服务目录：APM 看到的每个服务和已登记的服务，含负责人、等级、标签、进行中的告警、吞吐、错误率、时延、版本和最近部署。收藏的服务排在最前，已归档的服务默认不显示。 |
| **服务地图** | 一个环境中的服务及其相互调用、它们调用的对象，以及发布和消费的 Topic；与上一时段相比新增或消失的调用会标出来。见 [APM 服务地图](/zh-Hans/apm/service-map#apm-服务地图)。 |
| **错误** | 所有服务的后端错误分组，含状态、团队和处理人、错误发生的分布，以及分组用的聚合规则。 |
| **SLO** | 服务等级目标：每个目标在窗口内的达成率、剩余错误预算、预算消耗速度和状态。 |
| **设置** | 组织的健康判定线、默认 Apdex 阈值、长任务、服务目录要求、命名规则、环境映射和服务别名，以及过去一天的数据对这些设置的提示；平台的基数上限和链路采样。见 [APM 设置](/zh-Hans/apm/settings)。 |

服务页包含以下分区：

| 分区 | 主要用途 |
|---|---|
| **概览** | 并排展示请求、错误率和时延，以及这个服务的洞察、延迟分布、下游耗时、耗时最多的端点和最常见的错误，以及这个服务的 SLO。 |
| **端点** | 按请求数、错误、时延或耗时占比排列 HTTP、RPC、消息和后台任务入口。端点在抽屉中打开，含状态码、耗时拆解和最慢的请求。星标标出关键事务，列表也可以只显示关键事务或长任务。 |
| **调用链** | 这个服务参与的 trace，使用 Traces 页面的链路表格。 |
| **依赖** | 调用这个服务的服务，以及按目标分组的下游调用，操作列在目标下；每个目标的健康评分、超时和重试的调用，以及最慢的 SQL 语句。 |
| **错误** | 这个服务的错误分组。 |
| **部署** | 流水线上报的发布与 Span 中观测到的版本放在一起，标出回滚，每个版本与上一版本相比的结论，同时运行的两个版本并排对比，以及两个版本的对比。见[部署](/zh-Hans/apm/deployments)。 |
| **运行时** | 运行这个服务的实例及每个实例的请求情况，来自进程和服务所用语言运行时指标的图表，以及来自 Profile 的火焰图。 |
| **设置** | 服务目录条目和关键事务，以及实例上报的信息。 |

服务名后面的一行说明服务的基本情况，并跟随当前选择的环境和版本：

| 信息 | 来源 |
|---|---|
| 健康状态 | 时间范围内的 RED 指标，悬停可看原因。时间范围内没有请求时显示**该时间范围内无数据**：没有收到遥测不代表服务不健康。 |
| 等级 | 服务目录条目。 |
| 所属系统和环境 | `service.namespace` 和 `deployment.environment.name`。 |
| 服务类型 | 服务承接的入口 Span：**HTTP**、**RPC**、消息的**消息消费**、内部入口 Span 的**后台任务**。 |
| 语言 / 框架 | `telemetry.sdk.language`，以及服务入口 Span 的插桩库，例如 Axum、Spring 或 Express。 |
| 版本 | 选中的版本；未选择时为时间范围内实例运行过的所有版本，运行实例最多的在前。灰度发布时会同时显示两个版本。 |
| 负责团队 | 服务目录条目。悬停可看负责人和当前值班人。 |
| 实例数 | 当前版本在时间范围内上报过的实例数。点击打开**运行时**。 |
| 最近部署 | 当前版本（未选择时为最新版本）首次出现的时间。 |
| 部署区域 | 实例的 `cloud.region`。 |
| 代码仓库 | 实例的 `vcs.repository.url.full` 或 `git.repository_url`；没有上报时使用服务目录条目中的仓库。 |

已归档的服务在这一行还会显示**已归档**。标题行末尾的**收藏**把服务加入自己的收藏。

导航卡片末尾链接到服务的日志、指标和 Profiles。在当前时间范围终点之前的一天内，某个信号带有这个服务时，对应链接会点亮。MoleSignal 每五分钟重新查看一次：

| 信号 | 点亮条件 |
|---|---|
| 日志 | 某个含 `service.name`、`service_name` 或 `service` 字段的日志数据流中有这个服务的日志。链接在该数据流上打开日志页。 |
| 指标 | 最近一小时内有带这个服务 `service.name` 的指标序列。 |
| Profiles | Profile 数据流中有这个服务的 Profile。 |
| RUM | 服务的样本调用链中有来自浏览器会话的请求。只在这种情况下显示，点击打开该会话。 |

没有数据的信号会变暗，点击打开**数据源**中对应的接入页面。查看失败或超过三秒时，链接既不点亮也不变暗。

## 接入前提

- 把 OpenTelemetry trace 发送到 MoleSignal 的[链路采集端点](/zh-Hans/intake)；
- 在组织工作区拥有 `apm.services.read`；或者
- 在受保护的 `_sys` 遥测范围拥有 `sys.telemetry.read`。

## 为服务接入 APM

<Steps>
  <Step title="设置稳定的服务资源属性">
    每个服务都要设置 `service.name`。如果需要筛选服务或比较部署，再添加命名空间、环境、版本和实例属性。

    ```bash
    export OTEL_SERVICE_NAME=checkout
    export OTEL_RESOURCE_ATTRIBUTES="service.namespace=shop,deployment.environment.name=production,service.version=2.4.0,service.instance.id=checkout-01"
    ```

    具体配置方式取决于使用的 OpenTelemetry SDK 或 Collector。
  </Step>
  <Step title="使用正确的 span kind">
    为入站请求创建 `SERVER` span，为消费的消息创建 `CONSUMER` span。为下游调用创建 `CLIENT` 或 `PRODUCER` span。MoleSignal 通过 span kind 区分事务与依赖。
  </Step>
  <Step title="记录状态与异常">
    设置 OpenTelemetry span 状态、HTTP 或 RPC 状态属性，并记录 exception event。MoleSignal 用这些信息区分成功与失败，并建立后端错误组。
  </Step>
  <Step title="发送 trace 并打开 APM">
    发送 OTLP trace，然后打开 **应用性能 → 服务**。把全局时间范围保持在最近流量，等待投影器刷写首批数据桶。
  </Step>
</Steps>

### 推荐的资源属性

| 属性 | 作用 | 缺失时 |
|---|---|---|
| `service.name` | 稳定的服务标识。每个服务都应显式设置。 | `unknown_service` |
| `service.namespace` | 区分不同系统或团队中的同名服务。 | `default` |
| `deployment.environment.name` | 筛选生产、预发等环境。 | 依次使用旧属性 `deployment.environment` 和 `unknown` |
| `service.version` | 支持版本历史与部署对比。 | 不提供版本拆分 |
| `service.instance.id` | 区分实例。 | 依次使用 `k8s.pod.name` 和 `host.name` |
| `telemetry.sdk.language` | 在服务目录中显示运行时语言。 | 存在时使用 `process.runtime.name` |
| `cloud.region`、`k8s.*`、`host.name`、`container.name`、`container.id` | 说明每个实例运行在哪里。 | 不显示 |
| `process.runtime.name`、`process.runtime.version` | 显示每个实例的运行时。 | 不显示 |
| `vcs.repository.url.full`、`vcs.ref.head.revision` | 链接代码仓库并显示提交。也支持 `git.repository_url` 和 `git.commit.sha`。 | 服务目录条目中的仓库 |

Kubernetes 属性和 `cloud.region` 通常由 OpenTelemetry Collector 的 `k8sattributes` 和 `resourcedetection` 处理器添加，而不是由 SDK 设置。

请使用低基数值。不要把请求 ID、原始 URL、用户 ID 或其他无界值放进服务、环境、版本、路由、操作或依赖属性。

## APM 数据如何派生

### 服务与端点

`SERVER` 和 `CONSUMER` span 会计入服务与端点 RED 指标。API 把端点称为事务（transaction）。没有 kind 且没有父 span 的数据可作为服务总量的兼容回退，但显式 span kind 才能生成更完整的页面。

MoleSignal 会从语义属性构造有界端点名称：

- HTTP 方法与 `http.route`，例如 `POST /checkout`；
- RPC 服务与方法；
- 消息操作与目标端；
- 没有更强语义标识时，使用安全、低基数的 span 名称。

请使用 `/orders/{id}` 这样的路由模板，不要使用 `/orders/83921` 这样的原始路径。

### 依赖

`CLIENT` 和 `PRODUCER` span 会计入依赖 RED 指标。MoleSignal 会把目标分类为服务、数据库、缓存、消息系统、外部 HTTP、外部 RPC 或其他依赖。标准的 `peer.service`、`db.*`、`messaging.*`、`rpc.*`、`server.*` 和 HTTP 语义属性可以提高依赖标识质量。

SQL 数据库调用的操作名是语句模板：取 `db.query.summary`，没有时取 `db.query.text` 或 `db.statement`，所有字面量替换为 `?`，去掉注释，值列表合并为一个 `?`，最多保留 512 字节。双引号中的文字只在把它当作表名或列名的数据库（如 PostgreSQL、Oracle）中保留，在其他数据库中当作值处理。没有语句的调用使用 `db.operation.name`，缓存调用使用其命令名。一个服务对同一目标每小时最多区分 32 个操作，其余操作在同一目标下合并为**其他**。

超时的请求（错误类型为超时、gRPC `DEADLINE_EXCEEDED`、HTTP 408 或 504）和重发的请求（`http.request.resend_count` 大于 0）会在 RED 指标旁单独计数。

### 错误

span 包含异常、OpenTelemetry 状态为 `ERROR`、HTTP 状态码不低于 500，或 RPC 状态非零时，MoleSignal 会把该 span 判定为错误。错误组的稳定指纹由错误类型、第一个应用栈帧和事务名称组成；经常变化的错误消息不参与指纹计算。[聚合规则](#用规则聚合错误)可以把错误合并为一组，或让它们不再成组。

## 理解 RED 指标

| 指标 | 含义 |
|---|---|
| **请求数** | 匹配的服务、端点或依赖观测数量。 |
| **错误率** | 错误数除以请求数。 |
| **时延** | 从合并后的延迟直方图读出的 p50、p90、p95 和 p99，以及平均耗时。 |
| **Apdex** | 不超过阈值 T 的请求加上不超过 4T 的请求的一半，除以全部请求。T 为组织的默认值（未在 [APM 设置](/zh-Hans/apm/settings#健康判定与阈值)中修改时为 500 ms），服务目录条目也可以为服务设置自己的 T，延迟分布会注明当前使用的 T。概览把所有服务合在一起，按组织的默认值计算。出错的请求一律不算满意：错误按比例从各个耗时中扣除。 |
| **总耗时** | 所有观测耗时之和，用于发现整体影响最大的工作。 |

错误率达到 2% 或 p95 达到 500 ms 的服务为**警告**，达到 10% 或 2 s 为**严重**；[APM 设置](/zh-Hans/apm/settings#健康判定与阈值)可以改用其他判定线。服务页和目录里的状态点会说明是哪项指标超过了哪条线。

**洞察**卡片列出和上一段同样长的时间、上周同时段相比有突变的服务，见[洞察的种类](/zh-Hans/apm/insights#洞察的种类)。

延迟直方图把延迟每翻一倍分成八个桶，覆盖 125 微秒到约 131 秒，分位数在所在桶内插值读出，与精确值的误差约 ±4%。用旧的固定分桶写入的聚合仍可读取，但精度较粗。

概览和端点抽屉的**对比**控件会把前一天或上周同一时间段画成虚线，延迟分布也会勾出对比期的轮廓。在服务页面上，这个控件还会列出服务的其他环境：选择后，虚线改为同一时间段在那个环境中的数据。

端点的最慢请求取自 Trace 存储，列出的每个请求都能打开其调用链。错误样本指向的 trace 可能已被尾采样丢弃，此时链路抽屉会说明找不到这条 trace。

## 服务目录

目录为 APM 看到的每个服务按环境各列一行，也列出尚未上报、已经登记的服务。用服务目录中的**登记服务**和服务页的**设置**分区记录：

| 字段 | 含义 |
|---|---|
| **负责团队** | 工作区内的团队。团队的第一个启用的值班排班决定当前值班人。 |
| **负责人** | 对服务负责的工作区成员。 |
| **等级** | P0 到 P5，P0 是最重要的服务。 |
| **生命周期** | 生产、预发、试验或已弃用。 |
| **代码仓库** | 代码所在的地址，服务没有上报仓库时使用：https 地址，或 git 地址，例如 `git@github.com:acme/checkout.git`、`ssh://git@git.example.com/team/checkout.git`。地址中的密码保存为 `****`；https 地址中的用户部分常被 git 用来携带令牌，也同样保存为 `****`。服务页会把 git 地址按相同路径打开为 https 页面。 |
| **标签** | `key=value`，或只写 key，用逗号分隔。key 最多 64 个字符，只用小写字母、数字和 `_ . - /`；value 最多 128 个字符。最多 32 个。 |
| **Apdex 阈值 T** | 服务 Apdex 的阈值，单位毫秒，最长一分钟。留空使用组织的默认值，未在 APM 设置中修改时为 500 ms。 |
| **职责** | 显示在服务名下方的简短说明。 |

同一表单中的**归档**会让服务不再出现在服务目录的默认视图中，数据照常采集，服务页照常打开。服务目录中的 **已归档**会同时列出已归档的服务。

[服务目录要求](/zh-Hans/apm/settings#服务目录要求)可以要求某个等级及以上的服务填写团队、负责人或代码仓库。缺少要求项的服务会在目录中显示**缺少**及缺少的项。

服务定义按命名空间和服务名保存，在所有环境中都适用。服务目录和端点表的**列设置**可以选择和排序列，排列会按用户保存。除指标和目录字段外，服务目录还提供**服务类型**、**语言 / 框架**、**实例**和 **区域**列，取自时间范围内的实例，以及**标签**和**最后活跃**列。

服务目录每行的星标把服务加入自己的收藏，收藏的服务排在目录最前；**收藏**只列出收藏的服务。收藏按用户保存。**分组**按团队、命名空间、等级或某个标签的值分组。服务目录可以按环境和团队筛选；服务分布在多个命名空间或带有标签时，还可以按命名空间和标签筛选。筛选和分组都写在地址里，分享链接会打开同样的视图。在时间范围内出现过、但到时间范围终点已超过一天没有上报的服务标为**未活跃**。

关键事务是最重要的端点。在端点列表或端点抽屉中点星标即可标记，**设置**会列出服务的关键事务以及每个关键事务在时间范围内的请求情况。每个服务最多 50 个关键事务。

服务文档和 Runbook 放在 Mole Agent 知识库的 `services/<服务名>/` 下，可以放在组织知识库或负责团队的知识库。服务页上的**文档**会列出这些文件，并可新建 Runbook。Mole Agent 排查这个服务时也会读取这些文件。

编辑服务定义和关键事务需要 `apm.definitions.manage`，编辑错误状态需要 `apm.errors.manage`。所有者、管理员和编辑者拥有这些权限。

## 实例

每个为服务上报数据的进程是一个实例，依次用 `service.instance.id`、`k8s.pod.name`、`host.name` 区分。MoleSignal 每分钟查看一次实例的 Span，保存它运行的版本和上表中的属性，每项取最后一次上报的值。代码仓库链接保存为不含用户名、密码和查询参数的 https 地址。每个实例处理的请求、错误和延迟单独分桶统计，来源与服务的指标相同。

**运行时**列出当前时间范围和版本下的实例，最近上报的在前，含吞吐、错误率和 p95，以及实例的日志（按 Pod，没有 Pod 时按主机）和指标（按区分实例的标签）链接。每个服务每小时超过实例基数上限的实例合并为**其他实例** 一行，所有实例加起来等于服务。点击实例后，运行时图表只显示这个实例，这个选择会写在地址里。超过小时级聚合保留期仍未出现的实例会被删除。

## 深入端点

端点抽屉在 RED 图表之外还有两张卡片：

- **状态码**按状态码统计响应：HTTP 状态码取自 `http.response.status_code`（旧版插桩为 `http.status_code`），gRPC 状态码取自 `rpc.grpc.status_code`，按类别着色，并附趋势。每个分桶最多记录 24 个状态码，更多的计入**其他 HTTP** 或**其他 gRPC**。开始统计状态码之前写入的聚合没有状态码。
- **耗时拆解**从 Trace 存储读取该端点在时间范围内最近的请求（最多 200 个）及其下的 span。调用的耗时按调用对象归类：数据库（`db.system.name`）、缓存（Redis、Memcached、Valkey）、HTTP、RPC、消息，没有说明调用对象的计入**其他**。内部 span 计为内部处理，请求下没有任何 span 覆盖的时间是请求的自身耗时。每一项显示占比和每个请求的平均耗时。并行的调用加起来可能超过请求时长，此时各项会按请求时长等比缩放。只会读到尾采样保留下来的 trace。

端点列表的**长任务**只显示 p99 不低于 1 秒的端点。内部类型的入口 span，例如定时任务和没有消息操作的队列消费者，列为**后台任务**。

## 部署

服务页的**部署**标签把流水线上报的发布与服务 Span 中带的版本放在一起，标出回滚，把每个版本与它之前的版本对比，并把同时运行的两个版本并排展示。流水线通过 `POST /api/v1/apm/deployments` 上报发布。见[部署](/zh-Hans/apm/deployments)。

## 依赖

服务**依赖**标签中的每个目标都有一个从 100 开始的健康评分：调用失败率每 1% 扣 4 分（最多 60 分），超时调用占比每 1% 扣 4 分（最多 20 分）；选择了对比时段时，P95 增长超过五分之一的部分每 1% 扣半分（最多 20 分）。90 分及以上为良好，70 分及以上需要留意。评分的提示会说明扣分原因。设置**对比**后，每个目标还会显示错误率和 P95 的变化。**慢 SQL** 按 P95 列出最慢的数据库语句模板。

## 跟踪后端错误

错误分组在被设为**调查中**、**已解决**或**忽略**之前都是待处理状态。每个分组都可以交给一个团队，并指派给工作区成员。已解决的分组再次出现时显示为**回归**。**应用性能 → 错误**默认显示未解决的分组：待处理、调查中和回归的分组。

列表上方的**分布**按版本、环境和服务的语言统计所列分组的出现次数；错误分组的抽屉统计它自己的出现次数。抽屉里的**相关日志**按服务和时间范围打开日志，样本旁的**日志**打开该样本所在 trace 的日志。

### 用规则聚合错误

错误列表上的**聚合规则**决定错误在类型、抛出位置和端点之外如何分组。规则指定一个服务或全部服务，以及错误类型、错误消息、抛出位置和端点的匹配模式。每个模式匹配整段文字，不区分大小写，`*` 代表任意文字；留空表示不限，但规则至少要填写一项。

| 动作 | 效果 |
|---|---|
| **合并为一组** | 规则在一个服务中匹配到的错误合并为一个分组，以规则名称命名。 |
| **不再成组** | 规则匹配到的错误不形成分组。它们的请求在 RED 指标中仍计为失败。 |

规则按顺序匹配，第一条匹配的规则生效；上移或下移规则可以调整顺序。规则对保存之后出现的错误生效，半分钟内在所有节点生效，已有的分组保持不变。编辑规则时，表单会显示所列分组中有多少个符合这条规则。错误分组抽屉中的**按此错误建规则**会以该分组的类型和服务开始一条新规则。

## 服务等级目标

服务等级目标（SLO）承诺在 7、28 或 30 天的滚动窗口内达标请求所占的比例，对象是某个环境中的一个服务，或其中的一个端点。打开 **应用性能 → SLO** 并点击**新建 SLO**，或在服务概览的**服务等级目标** 卡片中点击**新建 SLO**。

| 字段 | 含义 |
|---|---|
| **服务**与**环境** | 目标覆盖的服务，限定在一个环境。 |
| **端点** | 服务的某个端点。留空则按整个服务计算。 |
| **达标条件** | **请求成功**：请求没有失败即为达标。**成功且不超过阈值**：请求没有失败且耗时不超过**延迟阈值（毫秒）**即为达标。 |
| **目标（%）** | 承诺的达标比例，大于 0 且小于 100，例如 `99.9`。 |
| **窗口** | 截至当前的 7、28 或 30 天。 |

SLO 读取服务的 APM 聚合，因此统计的是尾采样之前的全部请求。

| 指标 | 含义 |
|---|---|
| **达成率** | 窗口内达标请求数除以全部请求数。 |
| **剩余错误预算** | `1 - (1 - 达成率) / (1 - 目标)`。错误预算是目标允许不达标的请求比例。目标被打破后，该值低于零。 |
| **燃烧率** | 最近 1 小时、6 小时和 24 小时的 `(1 - 达成率) / (1 - 目标)`。为 `1×` 时，预算恰好用满整个窗口。 |
| **每日达成情况** | 窗口内每个 UTC 自然日，标为达标、未达标或无请求。 |

| 状态 | 含义 |
|---|---|
| **已违约** | **达成率**低于目标。 |
| **有风险** | 剩余预算不足 25%，或最近 1 小时燃烧率超过 14.4，或最近 6 小时超过 6。 |
| **健康** | 以上都不满足。 |
| **无数据** | 窗口内没有请求。 |

延迟目标读取延迟直方图，因此阈值内请求数的精度与分位数相同，误差约在 4% 以内。窗口读取小时级聚合，燃烧率读取分钟级聚合。窗口长于小时级聚合的保留期时，只统计保留的天数。

### 燃烧率告警

在 SLO 抽屉中点击**创建燃烧率告警**，会添加 Google SRE workbook 推荐的两条告警规则。两条都是针对该目标的 APM 告警规则，通过规则的升级策略发送通知。

| 规则 | 窗口 | 触发条件 | 严重级别 |
|---|---|---|---|
| 快速燃烧 | 1 小时，及其最后 5 分钟 | 两个窗口的燃烧率都超过 14.4 | 严重 |
| 慢速燃烧 | 6 小时，及其最后 30 分钟 | 两个窗口的燃烧率都超过 6 | 警告 |

短窗口让规则不会因为已经过去的尖峰而触发。有规则监控该 SLO 后，抽屉会列出这些规则，不再显示按钮。创建规则需要 `alerts.rules.manage`。

编辑 SLO 需要 `apm.slos.manage`，删除需要 `apm.slos.delete`。删除 SLO 时会先删除它的燃烧率告警，因此还需要 `alerts.rules.manage`。

## 按 APM 指标告警

APM 告警规则监控服务或其端点的某项指标，读取的是 APM 页面使用的同一份聚合，无需编写查询。

<Steps>
  <Step title="打开规则编辑器">
    在服务页或端点抽屉的标题栏打开**新建告警**，选择**阈值告警**。编辑器会以 **APM 告警**数据源打开，并预填服务、环境和端点。在**告警 → 告警规则**中新建规则时，也可以选择 **APM 告警**数据源。创建规则需要 `alerts.rules.manage`。
  </Step>
  <Step title="选择指标">
    选择**服务**、**环境**或**所有环境**、**端点**或**整个服务**，以及**指标**。按编辑器在指标下方标注的单位设置阈值。
  </Step>
  <Step title="测试并保存">
    点击**测试规则**，查看最近 6 小时的指标与阈值的对比，然后创建规则。
  </Step>
</Steps>

| 指标 | 单位 |
|---|---|
| **错误率** | 百分比，0 到 100 |
| **P50 延迟**、**P90 延迟**、**P95 延迟**、**P99 延迟**、**平均耗时** | 毫秒 |
| **吞吐** | 每秒请求数 |
| **请求数**、**错误数** | 规则窗口内的次数 |
| **新错误组** | 规则窗口内首次出现的服务（或端点）错误组数 |
| **Apdex** | 0 到 1 |
| **SLO 燃烧率** | 相对目标允许速度的倍数，从 SLO 创建。 |

每次评估读取规则的窗口：24 小时以内读取分钟级聚合，更长的窗口读取小时级聚合。窗口内没有请求时，**请求数**、**错误数**、**新错误组**和**吞吐**读数为 `0`，因此规则可以发现流量中断。其他指标此时没有读数，不会命中任何阈值，进行中的事件随之恢复。

在编辑器中或从 SLO 创建的规则带有 `service.name`、`service.namespace`、`deployment.environment` 和 `apm.endpoint` 标签（取决于规则指定了哪些对象），事件会复制这些标签。所有 APM 规则的事件还带有 `service` 标签、`affected_services` 中的服务，以及取自聚合的一个样本 trace ID。服务目录的**告警**列、服务页标题栏和端点抽屉统计指向该服务的已打开和已确认事件；事件指定了环境时，只统计该服务所在环境的事件。端点抽屉只统计带有该端点标签的事件。点击数量打开**告警 → 事件**。

同一菜单中的**异常检测告警**在指标明显偏离过去几天同一时刻时告警，不需要设置阈值。见[对 APM 指标设置异常检测告警](/zh-Hans/apm/insights#对-apm-指标设置异常检测告警)。

## 过滤、分辨率与保留

APM 页面共享全局时间范围。服务目录可按环境和团队筛选，服务页可按环境和版本筛选。列表支持搜索和排序。范围会编码进 URL，便于分享或重新打开。

使用默认部署设置时：

- API 未指定范围时查询最近 24 小时；
- `auto` 对不超过 24 小时的范围使用分钟桶，对更长范围使用小时桶；
- 分钟聚合保留 24 小时；
- 小时聚合和最大查询范围为 30 天。

管理员可以调整这些部署限制。只有对比双方都达到配置的请求量阈值时，版本对比才会标记为数据充足；默认阈值是每个版本 1,000 个请求。

## 隐私与有界数据

APM 保存聚合以及少量脱敏后的证据。APM 聚合不会保留请求体、响应体、URL 查询参数值、Header 或 SQL 参数；SQL 语句只以模板形式保留，所有字面量都替换为 `?`。标识值、代表性消息和栈帧都有长度限制；疑似敏感或易变化的值会在持久化之前删除或掩码。

这些保护不能替代良好的埋点习惯。不要把密钥或个人数据放入 span 名称、状态描述、异常消息或资源属性。

## 故障排查

| 现象 | 检查项 |
|---|---|
| 没有 APM 数据 | 确认 trace 已进入同一工作区，时间范围包含最近流量，并且角色拥有 `apm.services.read`。 |
| 出现 `unknown_service` | 在导出 span 前设置稳定的 `service.name` 资源属性。 |
| 缺少端点 | 添加 `SERVER` 或 `CONSUMER` span kind，以及标准 HTTP、RPC 或消息属性。 |
| 缺少依赖 | 为下游调用添加 `CLIENT` 或 `PRODUCER` span，并携带目标端语义属性。 |
| 缺少版本 | 在同一部署的每个实例上统一设置 `service.version`。 |
| 缺少错误 | 按 OpenTelemetry 约定记录 exception event，并设置 span、HTTP 或 RPC 状态。 |
| 错误样本的 trace 找不到 | Trace 已被采样丢弃或过期，但采样前生成的 APM 聚合仍然有效。 |
| 没有运行时图表 | 用相同的 `service.name` 上报 OpenTelemetry 运行时指标。 |
| 结果不完整或陈旧 | 查看数据质量提示和 `GET /api/v1/apm/health`。 |
| 服务停止后 APM 告警不触发 | 没有请求时，错误率、延迟和 Apdex 没有读数。用**请求数**或**吞吐**监控流量中断。 |
| SLO 显示**无数据** | 确认服务在 SLO 指定的环境中有上报，并且端点名与**端点**列表一致。 |
