```http
POST /api/v1/_kinesis_firehose
```

接受 AWS Data Firehose HTTP 端点的投递。该端点不使用 Bearer Token。请创建 `aws_kinesis_firehose` 类型的连接器，设置至少 16 个字符的 `pushToken` 与 `target_stream`，并把该 Token 作为访问密钥交给 Firehose。端点从 `X-Amz-Firehose-Access-Key` 读取 Token，也接受 `X-Connector-Token` 与 `?token=`。Token 错误时返回 `401`。

每条记录都带有 base64 编码的 `data`。端点会解码、按行拆分，并把每个非空行变成 `target_stream`（默认 `kinesis`）中的一条日志事件。JSON 对象的行会变成字段，纯文本的行会变成字段 `message`。

<RequestExample>
```bash cURL
curl -X POST http://localhost:5080/api/v1/_kinesis_firehose \
  -H 'X-Amz-Firehose-Access-Key: <pushToken>' \
  -H 'content-type: application/json' \
  -d '{"requestId":"req-1","timestamp":1790000000000,"records":[{"data":"eyJsZXZlbCI6ImluZm8ifQo="}]}'
```
</RequestExample>

<ResponseExample>
```json 200
{ "requestId": "req-1", "timestamp": 1790000000123 }
```
</ResponseExample>

响应会回显 `requestId`，并带有毫秒级 `timestamp`，这是 Firehose 的要求。连接器的配置参见[连接器](/zh-Hans/connectors)。

## 验证投递与目标数据流

1. 确认连接器已启用，推送 Token 与发送方配置一致。普通 API Token 不能替代推送 Token。
2. 通过连接器 API 设置原始 `configJson` 时，使用 `target_stream` 指定目标数据流；不要用 `targetStream` 代替此字段。`pushToken` 仍使用驼峰命名。
3. 发送一条带唯一标记的测试事件，记录接收时间。随后在 **Logs** 中选择预期数据流与覆盖接收时间的窗口，查询该标记。
4. 若请求成功但目标流没有数据，检查对应的默认流及实际保存的目标字段。HTTP 确认不能代替目标数据流中的查询验证。

Token 应视作凭据保护。使用 URL 查询参数传递时，避免将完整 URL 复制到日志、工单或截图中。请求失败时先区分 Token、连接器启用状态、请求格式与压缩设置，再决定是否重试。
