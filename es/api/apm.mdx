La API de APM ofrece agregados por organización calculados a partir de los spans de las trazas. Todos los endpoints usan el
prefijo `/api/v1/apm` y requieren un token de portador.

```http
Authorization: Bearer <token>
```

Un espacio de trabajo de la organización requiere el permiso de lectura del área correspondiente: `apm.services.read`, `apm.errors.read`,
`apm.error_rules.read`, `apm.definitions.read`, `apm.slos.read`, `apm.deployments.read` o `apm.settings.read`. Un cliente de la plataforma puede usar
`sys.telemetry.read` en el ámbito protegido `_sys`. Cada llamada de escritura indica qué permiso requiere. Para notificar un despliegue, se requiere
`apm.deploy`.

## Endpoints

| Método y ruta | Respuesta |
|---|---|
| `GET /api/v1/apm/overview` | Resumen y tendencias de las métricas RED de todos los servicios, estado de los servicios y su evolución, clasificaciones, despliegues, entornos, brechas de instrumentación, transacciones principales, dependencias y errores. |
| `GET /api/v1/apm/insights` | Qué cambió respecto al intervalo anterior y al mismo intervalo de la semana anterior, qué versiones empeoraron, dónde se podría ahorrar tiempo y qué cambios ocurrieron cerca de cada hallazgo. |
| `GET /api/v1/apm/services` | Catálogo paginado de servicios con instrumentación, versiones, estado, métricas RED y filtros de trazas. |
| `GET /api/v1/apm/services/{service}` | Resumen del servicio, tendencia, transacciones, dependencias, errores y versiones. |
| `GET /api/v1/apm/services/{service}/instances` | Instancias de un servicio en un entorno, con su versión, los atributos de sus recursos y las solicitudes que atendió cada una. |
| `GET /api/v1/apm/services/{service}/coverage` | Indica si los logs, las métricas, los perfiles y las sesiones de navegador del servicio llegan a MoleSignal durante las 24 horas anteriores a `to`. |
| `GET /api/v1/apm/transactions` | Métricas RED de las transacciones con paginación y clasificación por tiempo total. |
| `GET /api/v1/apm/transactions/{transaction}` | Tendencia de la transacción, errores asociados, versiones y filtros de trazas. |
| `GET /api/v1/apm/dependencies` | Métricas RED paginadas por par de servicio que llama y dependencia, y clasificación por tiempo total. |
| `GET /api/v1/apm/map` | Mapa de servicios de un entorno y un espacio de nombres: servicios, destinos de sus llamadas, temas y llamadas entre ellos. |
| `GET /api/v1/apm/map/edge` | Una llamada del mapa: su tendencia, qué se solicitó y los errores del servicio que recibió la llamada. |
| `GET /api/v1/apm/blast-radius` | Alcance de un servicio en el mapa: qué lo llama y a qué llama, un salto a la vez. |
| `GET /api/v1/apm/errors` | Lista paginada de grupos de errores del backend sin datos sensibles, con información sobre dónde ocurrieron. |
| `GET /api/v1/apm/errors/{fingerprint}` | Tendencia del error, transacciones y versiones afectadas, dónde ocurrieron los errores del grupo, una traza de pila representativa y un número limitado de muestras. |
| `GET /api/v1/apm/versions/compare` | Métricas RED de la versión de referencia y la candidata, diferencias, indicación de si hay datos suficientes y regresiones. |
| `GET /api/v1/apm/health` | Estado de la proyección del inquilino, estado en tiempo de ejecución, límites y brechas. |
| `GET /api/v1/apm/service-definitions` | Todas las definiciones de servicio de la organización. |
| `PUT /api/v1/apm/service-definitions/{service}?namespace=` | Crea o reemplaza la definición de un servicio. Requiere `apm.definitions.manage`. |
| `DELETE /api/v1/apm/service-definitions/{service}?namespace=` | Elimina la definición de un servicio. Requiere `apm.definitions.manage`. |
| `POST /api/v1/apm/service-definitions/{service}/key-transactions?namespace=` | Marca un endpoint como transacción clave del servicio o quita la marca. Requiere `apm.definitions.manage`. |
| `PUT /api/v1/apm/errors/{fingerprint}/issue` | Define el estado, el equipo y la persona asignada a un grupo de errores. Requiere `apm.errors.manage`. |
| `GET /api/v1/apm/error-rules` | Reglas de agrupación de errores de la organización, en el orden en que se evalúan. |
| `POST /api/v1/apm/error-rules` | Crea una regla de agrupación que se evalúa después de las demás. Requiere `apm.error_rules.manage`. |
| `PUT /api/v1/apm/error-rules/{id}` | Reemplaza una regla de agrupación. Requiere `apm.error_rules.manage`. |
| `DELETE /api/v1/apm/error-rules/{id}` | Elimina una regla de agrupación. Requiere `apm.error_rules.manage`. |
| `PUT /api/v1/apm/error-rules/order` | Define el orden de evaluación de las reglas. Requiere `apm.error_rules.manage`. |
| `GET /api/v1/apm/slos` | Todos los objetivos de nivel de servicio, con su estado, grado de cumplimiento, presupuesto de errores restante y tasas de consumo. |
| `GET /api/v1/apm/slos/{id}` | Estado de un objetivo de nivel de servicio y desglose por día de su ventana de evaluación. |
| `POST /api/v1/apm/slos` | Crea un objetivo de nivel de servicio. Requiere `apm.slos.manage`. |
| `PUT /api/v1/apm/slos/{id}` | Reemplaza un objetivo de nivel de servicio. Requiere `apm.slos.manage`. |
| `DELETE /api/v1/apm/slos/{id}` | Elimina un objetivo de nivel de servicio. Requiere `apm.slos.delete`. |
| `POST /api/v1/apm/deployments` | Notifica un despliegue. Requiere `apm.deploy`. |
| `GET /api/v1/apm/deployments` | Despliegues que notificaron los pipelines, del más reciente al más antiguo. |
| `GET /api/v1/apm/settings` | Configuración de APM de la organización. Devuelve los valores predeterminados si la organización no ha guardado ninguna configuración. |
| `PUT /api/v1/apm/settings` | Reemplaza la configuración de APM de la organización. Requiere `apm.settings.manage`. |

Codifica los parámetros de ruta en formato URL. Usa el nombre exacto de la transacción (`transaction`) o la huella digital exacta del error (`fingerprint`)
que devuelve la respuesta de un endpoint de listado.

## Parámetros de consulta comunes

| Parámetro | Tipo | Comportamiento |
|---|---|---|
| `from` | entero | Inicio del intervalo en microsegundos desde la época Unix. El valor predeterminado es 24 horas antes de `to`. |
| `to` | entero | Fin del intervalo en microsegundos desde la época Unix. El valor predeterminado es el momento actual. |
| `namespace` | cadena | Filtra por coincidencia exacta con el espacio de nombres del servicio. |
| `service` | cadena | Filtra por coincidencia exacta con el nombre del servicio. La ruta de detalles del servicio tiene prioridad sobre este valor. |
| `environment` | cadena | Filtra por coincidencia exacta con el entorno de despliegue. |
| `version` | cadena | Filtra por coincidencia exacta con la versión del servicio. |
| `resolution` | enumeración | `auto`, `minute` o `hour`. `auto` selecciona la resolución con la que se conservan los datos del intervalo. |
| `sort` | cadena | Campo de ordenamiento específico del endpoint. |
| `direction` | enumeración | `asc` o `desc`. El valor predeterminado es `desc`. |
| `limit` | entero | Tamaño de página de 1 a 200. El valor predeterminado es 50. |
| `cursor` | cadena | Cursor opaco de una respuesta de listado anterior. |
| `status` | enumeración | Solo para `/errors`: `all` (valor predeterminado), `unresolved` (grupos abiertos, en investigación o resueltos que volvieron a aparecer), `investigating`, `resolved` o `ignored`. |

Usa filtros que no estén vacíos y que no superen los 192 bytes. El intervalo no puede superar el máximo configurado,
que de forma predeterminada es de 30 días (`[apm].max_query_range_days`).

### Campos de ordenamiento

| Endpoint | Valores de `sort` admitidos | Valor predeterminado |
|---|---|---|
| `/services` | `requestCount`, `errorRate`, `p95`, `name` | `requestCount` |
| `/transactions` | `requestCount`, `errorRate`, `p95`, `total_time` | `requestCount` |
| `/dependencies` | `requestCount`, `errorRate`, `p95`, `total_time` | `total_time` |
| `/errors` | `occurrenceCount`, `errorRate`, `lastSeen` | `occurrenceCount` |

`/overview` admite los mismos filtros y la misma resolución, pero no usa paginación. Los endpoints de detalles, comparación y
estado no devuelven listas paginadas.

## Consulta el resumen general

<RequestExample>
```bash cURL
NOW=$(date +%s)000000
curl --get 'http://localhost:5080/api/v1/apm/overview' \
  --header "Authorization: Bearer $MS_TOKEN" \
  --data-urlencode "from=$((NOW-86400000000))" \
  --data-urlencode "to=$NOW" \
  --data-urlencode 'environment=production' \
  --data-urlencode 'resolution=auto'
```
</RequestExample>

La respuesta contiene `red`, `trend`, `serviceHealth`, `services`, `topTransactions`,
`topDependencies`, `topErrors` y `recentVersions`, además de un objeto `meta` común y los siguientes campos:

| Campo | Notas |
|---|---|
| `serviceCount`, `activeServiceCount` | Número de servicios detectados en el intervalo y número de esos servicios que atendieron al menos una solicitud. |
| `healthTrend` | Cantidad de servicios en cada estado por segmento de tiempo. El intervalo se divide en un máximo de 48 segmentos, ninguno más corto que un grupo de agregación. Si un servicio no recibe solicitudes en un segmento, cuenta como `noTraffic` en ese segmento. |
| `rankings` | `slowest` (por p95), `mostErrors` (por tasa de errores) y `busiest` (por volumen de solicitudes), con cinco servicios en cada clasificación. Las dos primeras incluyen servicios con al menos 20 solicitudes. |
| `deployments` | Hasta 20 versiones detectadas por primera vez en el intervalo, de la más reciente a la más antigua. Cada una incluye `red` y `verdict`, como en [las versiones de un servicio](#consulta-las-versiones-de-un-servicio). |
| `environments`, `availableEnvironments` | Servicios y solicitudes por entorno en la vista, y todos los entornos donde se ejecutan los servicios, independientemente del filtro `environment`. |
| `instrumentation` | Número de servicios por lenguaje y SDK, y cuántos no informan `deployment.environment`, `service.version` o `service.instance.id`. |

## Consulta los hallazgos

`GET /api/v1/apm/insights` acepta los parámetros comunes de intervalo y de filtro, y devuelve `meta` y los siguientes campos:

| Campo | Notas |
|---|---|
| `now`, `previous`, `lastWeek` | Métricas de los servicios de la vista en el intervalo consultado, en el intervalo inmediatamente anterior de igual duración y en el intervalo equivalente de una semana antes: `requestCount`, `throughput` en solicitudes por segundo, `errorRate`, `p95Time` y `apdex`. La respuesta omite los intervalos sin solicitudes. |
| `insights` | Hasta 30 hallazgos, con los más urgentes primero. |

Cada hallazgo incluye:

| Campo | Notas |
|---|---|
| `kind` | `anomaly`, `regression`, `slow_dependency`, `repeated_call`, `slowQuery` o `hot_endpoint`. |
| `severity` | `critical`, `warning` o `info` para una sugerencia. |
| `service` | `namespace`, `name` y `environment`. |
| `transaction`, `dependency` | El endpoint más activo o la dependencia asociada a un cuello de botella, una llamada repetida o una consulta lenta. |
| `metric` | La métrica que cambió o empeoró: `errorRate`, `p95` o `throughput`. |
| `value` | El valor actual: la tasa de errores como proporción, el P95 en microsegundos o las solicitudes por segundo. Para un cuello de botella o un endpoint más activo, indica la proporción del tiempo que representa. Para una llamada repetida, indica las llamadas por solicitud. Para una consulta lenta, indica su P95 en microsegundos. |
| `previous`, `lastWeek` | El mismo valor en el intervalo inmediatamente anterior y en el intervalo equivalente de una semana antes. Para una regresión, el valor de la versión anterior. |
| `since` | Momento en que empezó el cambio o en que se detectó por primera vez la versión que presenta la regresión. |
| `version`, `previousVersion` | La versión que presenta la regresión y la versión anterior. |
| `calls`, `p95Time` | Cantidad de llamadas o solicitudes en las que se basa la sugerencia y su P95. |
| `changes` | Los cambios más cercanos a `since` en el tiempo, por orden de proximidad: `kind`, `source` (`reported` u `observed`), `service`, `version`, `status`, `at`, `downstream` (`true` si el servicio donde se detectó el cambio llama a ese servicio), `commit` y `description`. |

Consulta los umbrales en [Hallazgos e investigaciones](/es/apm/insights#qué-detecta-análisis).

## Consulta las métricas RED

Cada resumen incluye un objeto `red` con las métricas de solicitudes, errores y duración del intervalo.

| Campo | Notas |
|---|---|
| `requestCount`, `errorCount`, `errorRate` | Solicitudes, solicitudes fallidas y proporción de solicitudes fallidas respecto al total, de 0 a 1. |
| `durationSum`, `durationAverage` | Duración total y media en microsegundos. La media es `null` si no hay solicitudes. |
| `p50Time`, `p90Time`, `p95Time`, `p99Time` | Percentiles de latencia en microsegundos, calculados dentro del intervalo del histograma que contiene la posición de cada percentil. Con la configuración predeterminada, el valor difiere de la duración exacta en aproximadamente un 4 % como máximo. `null` si no hay solicitudes. |
| `apdex` | Suma de las solicitudes dentro del umbral T y la mitad de las solicitudes que superan T sin superar 4T, dividida entre el total de solicitudes. El resultado va de 0 a 1. T es el valor de `apdexThreshold` del servicio, o 500 ms si no se define. Las métricas del resumen general para todos los servicios en conjunto usan 500 ms. Las solicitudes fallidas nunca cuentan como satisfactorias. `null` si no hay solicitudes. |
| `latencyPartial` | `true` si no se puede identificar el esquema de latencia a partir de algunos grupos de agregación. El sistema convierte y contabiliza los grupos con un esquema anterior (`[apm.histogram].schema_version`). Los percentiles excluyen los grupos que no se pueden leer, pero los recuentos, la suma y la media los incluyen. |
| `timeoutCount`, `retryCount` | Solicitudes que superaron el tiempo de espera (un tipo de error de tiempo de espera, gRPC `DEADLINE_EXCEEDED`, HTTP 408 o 504) y solicitudes reenviadas (`http.request.resend_count` mayor que 0). La respuesta omite cada campo si su recuento es cero. |
| `statusCodes` | Respuestas por código de estado, con el formato `http:<code>` (100 a 599) o `grpc:<code>` (0 a 16). Cada grupo de agregación conserva hasta 24 códigos. Los demás cuentan como `http:other` o `grpc:other`. La respuesta omite el campo si no se contabilizó ningún código, como ocurre con los datos agregados que se guardaron antes de que el sistema empezara a contabilizarlos. |
| `exemplars` | Hasta 8 spans de muestra del intervalo, de mayor a menor duración. El sistema prepara una representación del span antes de que el [muestreo al final de la traza](/es/configuration#captura-de-trazas-y-muestreo-al-final) decida si conserva la traza. Por eso, `traceAvailable` suele ser `false`. Busca la traza para comprobar si el sistema la conservó. El agregado sigue siendo válido. |

Los resúmenes de servicios y transacciones incluyen `apdexThreshold`, el umbral T que se usó para calcular el Apdex.
El resumen de un servicio también incluye `health` y `healthReasons`. Cada métrica que supera un umbral se indica mediante `metric`
(`errorRate` o `p95`), `level`, `value` y `threshold`. También incluye `sparkline` con el recuento de solicitudes, el recuento de errores y el p95 de cada grupo de agregación,
y `currentVersion` junto con `currentVersionSince`, que indican la versión detectada más recientemente y cuándo se
detectó por primera vez. La vista detallada de un servicio o una transacción incluye `latencyDistribution` con los intervalos del histograma
que contienen solicitudes. Cada intervalo incluye `lowerTime`, `upperTime` y `count`. La distribución abarca desde la
solicitud más rápida hasta la más lenta.

## Guarda las definiciones de servicio

Una definición registra quién es responsable de un servicio y qué importancia tiene. La clave combina `namespace` con el
nombre del servicio. La definición se aplica a todos los entornos y puede existir antes de que el servicio envíe datos.

```http
PUT /api/v1/apm/service-definitions/checkout?namespace=shop
Content-Type: application/json

{"description": "Takes orders and payments.", "teamId": "<team id>", "ownerId": "<user id>", "tier": "p0", "lifecycle": "production", "repositoryUrl": "https://github.com/acme/checkout", "tags": {"domain": "orders", "pci": ""}, "apdexThreshold": 300000, "aliases": ["order_service", "Order Center"], "dataSources": {"logs": [{"stream": "default", "filter": "service_name = 'order_service'"}], "metrics": [{"selector": "{service=\"checkout\"}"}], "dashboards": ["<dashboard id>"], "links": [{"name": "Runbook", "url": "https://wiki.example.com/checkout"}]}, "archived": false}
```

| Campo | Notas |
|---|---|
| `description` | Hasta 2000 caracteres. |
| `teamId` | Un equipo de la organización o `null`. Al eliminar el equipo, se borra el valor. |
| `ownerId` | Un miembro de la organización o `null`. |
| `tier` | De `p0` (el nivel más importante) a `p5`, o `null`. |
| `lifecycle` | `production`, `staging`, `experimental`, `deprecated` o `null`. |
| `repositoryUrl` | Una URL `http`, `https`, `ssh`, `git` o `git+ssh`, o `user@host:path`, sin espacios y con un máximo de 2048 caracteres, o `null`. MoleSignal guarda la contraseña como `****` y hace lo mismo con el usuario de una dirección HTTP(S). El catálogo muestra esta URL si el servicio no informa de ningún repositorio. |
| `tags` | Hasta 32 etiquetas con el formato `{ "key": "value" }`. Cada clave tiene entre 1 y 64 caracteres: letras minúsculas, dígitos y los símbolos `_ . - /`. Cada valor admite hasta 128 caracteres, sin espacios al principio ni al final. Déjalo vacío para usar solo la clave. |
| `apdexThreshold` | El umbral T de Apdex del servicio, mayor que 0 y menor o igual que 60 000 000 (un minuto), o `null` para usar 500 ms. |
| `aliases` | Hasta 20 nombres alternativos del servicio en logs, métricas y otros sistemas. Cada nombre admite entre 1 y 128 caracteres, sin espacios al principio ni al final. No se distingue entre mayúsculas y minúsculas: no repitas nombres ni uses el nombre del servicio, ni el nombre o un alias de otro servicio de la organización. Si omites el campo, la definición guardada conserva los nombres. |
| `dataSources` | Fuentes de datos del servicio: `logs` (`stream` y, opcionalmente, `filter`, una expresión booleana de SQL de hasta 2000 caracteres), `metrics` (`selector`, un selector PromQL como `{service="checkout"}`), `dashboards` (ID de paneles) y `links` (`name` y una `url` `http` o `https`). Admite hasta 10 elementos de cada tipo. Si omites el campo, la definición guardada conserva las fuentes. |
| `archived` | `true` oculta el servicio de la vista predeterminada del catálogo. Si omites el campo, la definición guardada conserva su estado. |

Al guardar la definición, MoleSignal conserva `keyTransactions`. Modifica esas transacciones de una en una. La respuesta contiene la
definición guardada con `namespace`, `name`, `keyTransactions`, `updatedBy` y `updatedAt`.
`DELETE` devuelve `204`, o `404` si el servicio no tiene una definición.

### Marca las transacciones clave

```http
POST /api/v1/apm/service-definitions/checkout/key-transactions?namespace=shop
Content-Type: application/json

{"transaction": {"name": "POST /orders", "kind": "http"}, "key": true}
```

`key: true` agrega el endpoint a `keyTransactions` y `false` lo quita. Si solicitas el estado
actual, no cambia nada. Si el servicio no tiene una definición, MoleSignal la crea. Cada servicio admite hasta 50 transacciones
clave. La fila `__other__`, que agrupa las restantes, no puede ser una transacción clave. La respuesta contiene la definición después del
cambio.

## Consulta la cobertura de un servicio

`GET /api/v1/apm/services/{service}/coverage` requiere `namespace` y `environment`, y
acepta `to` como parámetro opcional. `to` indica el fin del intervalo en microsegundos (el momento actual de forma predeterminada). La consulta abarca el día
anterior a `to` y conserva cada respuesta durante cinco minutos.

```json
{
  "from": 1792230096695000,
  "to": 1792316496695000,
  "logs": { "state": "reported", "found": ["default"] },
  "metrics": { "state": "missing" },
  "profiles": { "state": "reported", "found": ["cpu", "alloc_space"] },
  "rum": { "state": "unknown" }
}
```

| Señal | Cuándo devuelve `reported` | `found` |
|---|---|---|
| `logs` | Un flujo de logs con un campo `service.name`, `service_name` o `service` contiene una línea del servicio. La consulta revisa hasta ocho flujos, empezando por `default`. | Los flujos. |
| `metrics` | `count(last_over_time({"service.name"="<service>"}[1h]))` es mayor que cero en `to`. | El número de series. |
| `profiles` | El flujo de perfiles contiene un perfil del servicio. | Los tipos de perfil. |
| `rum` | Una acción del navegador incluyó una de las cinco trazas de muestra más recientes del servicio. | La sesión. |

`missing` indica que la consulta no encontró datos. `unknown` indica que la consulta falló o tardó más de tres
segundos. `rum` nunca devuelve `missing`: una muestra de trazas puede demostrar que hay sesiones que llegan a un servicio, pero no que
ninguna llegue.

## Consulta cómo se ejecuta un servicio

`GET /api/v1/apm/services` y `GET /api/v1/apm/services/{service}` incluyen en el resumen de cada servicio un
`profile` basado en las instancias que enviaron datos en el intervalo. Si especificas `version`, solo consideran las instancias de esa
versión. Cada lista ordena hasta cinco valores según cuántas instancias los comparten, con el formato
`{ "value": "1.8.2", "instances": 4 }`.

| Campo | Notas |
|---|---|
| `instanceCount`, `hostCount` | Cantidad de instancias y de valores distintos de `host.name`. |
| `versions` | Versiones que ejecutaron las instancias. Durante un despliegue gradual, la lista muestra dos. |
| `languages`, `runtimes`, `frameworks` | `telemetry.sdk.language`; `process.runtime.name` con su versión; el framework que identifica la biblioteca de instrumentación de los spans de entrada. |
| `regions`, `clusters`, `k8sNamespaces`, `workloads` | `cloud.region`, `k8s.cluster.name`, `k8s.namespace.name` y `k8s.deployment.name` o `k8s.statefulset.name`. |
| `repositories`, `commits` | `vcs.repository.url.full` o `git.repository_url`, sin credenciales; `vcs.ref.head.revision` o `git.commit.sha`. |
| `entryKinds` | `http`, `rpc`, `messaging`, `span`: los tipos de entrada que atiende el servicio. |

`GET /api/v1/apm/services/{service}/instances` enumera hasta 500 instancias, empezando por las que registraron actividad más
recientemente. Acepta `namespace` y `environment`, y los parámetros opcionales `version`, `from` y
`to`. Si falta el servicio o el entorno, devuelve `400`. Cada elemento incluye `instanceId` (el valor de
`service.instance.id` o, en su defecto, `k8s.pod.name` o `host.name`), `version`, `firstSeenAt`,
`lastSeenAt` y `attributes`, un mapa con los últimos atributos que envió la instancia. También incluye los datos de la actividad que atendió
en el intervalo: `red`, como en los resúmenes, con Apdex calculado según el umbral del servicio, y `sparkline`. Al superar el
límite de instancias, la respuesta agrupa las demás en un elemento con `instanceId` igual a `__other__`. Si una instancia
atendió solicitudes en el intervalo antes de que MoleSignal guardara datos sobre ella, aparece con `attributes` vacío.

## Establece el estado de un grupo de errores

```http
PUT /api/v1/apm/errors/<fingerprint>/issue
Content-Type: application/json

{"status": "investigating", "assigneeId": "<user id>", "teamId": "<team id>", "lastSeenAt": 1792316496695000}
```

`status` admite `open`, `investigating`, `resolved` o `ignored`. `assigneeId` identifica a un miembro de la
organización o es `null`, y `teamId` identifica a un equipo de la organización o es `null`. El campo opcional `lastSeenAt` indica, en microsegundos, la última vez que se vio el grupo. Al establecer
`resolved`, MoleSignal registra el momento en `resolvedAt`.

Los resúmenes de errores incluyen el estado en `issue` o devuelven `null` si aún no se ha establecido. `issue.regressed`
es `true` cuando un grupo resuelto vuelve a aparecer después de `resolvedAt`. El filtro `unresolved` incluye
esos grupos. Si intentas establecer el estado de una huella que no figura en la proyección, la API devuelve `404`.

## Gestiona los objetivos de nivel de servicio

Un objetivo de nivel de servicio (SLO) fija la proporción de solicitudes correctas de un servicio en un entorno o
de uno de sus endpoints durante una ventana móvil. Consulta
[Objetivos de nivel de servicio](/es/apm#objetivos-de-nivel-de-servicio) para saber qué significa cada valor.

```http
POST /api/v1/apm/slos
Content-Type: application/json

{"name": "Checkout availability", "namespace": "shop", "service": "checkout", "environment": "production", "transaction": null, "kind": "availability", "objective": 0.999, "windowDays": 30}
```

| Campo | Notas |
|---|---|
| `name` | Obligatorio. Hasta 255 bytes. |
| `description` | Opcional. Hasta 2,000 bytes. |
| `namespace`, `service`, `environment` | Obligatorios. Identifican el servicio tal como aparece en APM. Si el servicio no tiene `service.namespace`, pertenece al espacio de nombres `default`. |
| `transaction` | Un endpoint, `{ "name": "POST /orders", "kind": "http" }`, o `null` para todo el servicio. |
| `kind` | `availability`: una solicitud es correcta si no falló. `latency`: una solicitud es correcta si no falló y tardó como máximo `latencyThreshold`. |
| `latencyThreshold` | Obligatorio y positivo para `latency`. Para `availability`, debe ser `null` u omitirse. |
| `objective` | Proporción de solicitudes correctas, mayor que 0 y menor que 1, como `0.999`. |
| `windowDays` | `7`, `28` o `30`. |

`POST` y `PUT` devuelven el SLO guardado con `id`, `createdBy`, `createdAt`, `updatedBy` y
`updatedAt`. `GET /api/v1/apm/slos` devuelve el estado de cada SLO de la organización. Pasa
`namespace`, `service` y `environment` juntos para obtener los SLO de un solo servicio. La ventana termina
en el momento de la llamada, por lo que los parámetros de rango habituales no se aplican.

| Campo de estado | Notas |
|---|---|
| `slo` | El SLO tal como se guardó. |
| `state` | `healthy`, `at_risk`, `breached` o `noData`. |
| `sli` | Proporción de solicitudes correctas respecto al total de solicitudes de la ventana, o `null` si no hubo solicitudes. |
| `goodRequests`, `totalRequests` | Recuentos que se usan para calcular `sli`. Un SLO de latencia estima `goodRequests` a partir de los histogramas de latencia, por lo que el valor puede ser fraccionario. |
| `budgetRemaining` | `1 - (1 - sli) / (1 - objective)`. Es negativo si no se cumple el objetivo y `null` si no hubo solicitudes. |
| `burnRates` | `oneHour`, `sixHours` y `oneDay`: `(1 - sli) / (1 - objective)` durante la última hora, las últimas seis horas y las últimas 24 horas, respectivamente, o `null` si no hubo solicitudes. |

`GET /api/v1/apm/slos/{id}` devuelve `status` y `history`, con una entrada por cada día UTC de la ventana
en el que hubo solicitudes, en orden cronológico. Cada entrada incluye `dayStart` en microsegundos, `sli`, `goodRequests`
y `totalRequests`.

`DELETE` devuelve `204`. Devuelve `409` si alguna regla de alerta monitorea el SLO, como las alertas de tasa de
consumo del presupuesto de error. Elimina primero esas reglas. Las reglas de alerta de un SLO son reglas de APM con la métrica
`slo_burn_rate`. Consulta [Crea una regla](/es/api/alerting/create-rule#reglas-de-apm).

## Identifica una transacción sin ambigüedad

Dos tipos de transacción pueden compartir un nombre. Pasa el parámetro opcional `kind` para seleccionar uno:

```http
GET /api/v1/apm/transactions/POST%20%2Fcheckout?kind=http&service=checkout
```

Los valores admitidos para el tipo son `http`, `rpc`, `messaging`, `span` y `other`. Si varios
servicios o tipos comparten el nombre, la API devuelve `400` con el mensaje `APM transaction identity is ambiguous; provide service,
namespace, environment, and kind`.

## Compara versiones

Proporciona valores distintos para `baseline` y `candidate`. Agrega un filtro `service` para comparar las versiones de un solo servicio.

```bash
curl --get 'http://localhost:5080/api/v1/apm/versions/compare' \
  --header "Authorization: Bearer $MS_TOKEN" \
  --data-urlencode 'service=checkout' \
  --data-urlencode 'environment=production' \
  --data-urlencode 'baseline=2.3.1' \
  --data-urlencode 'candidate=2.4.0'
```

La respuesta incluye `baseline` y `candidate`, cada uno con `version`, `sampleCount` y
`red`, además de `delta`, `status`, `regressedTransactions` y `regressedErrors`. Cada lista de regresiones
contiene como máximo 20 entradas.

| Campo | Notas |
|---|---|
| `sufficientData` | `true` solo si ambas versiones alcanzan el umbral de muestras configurado. El valor predeterminado es de 1,000 solicitudes por versión (`[apm.version_comparison].min_requests_per_version`). |
| `status` | `insufficient_data`, `regressed`, `improved` o `neutral`. Devuelve `regressed` si la tasa de errores de la versión candidata aumenta al menos un punto porcentual y alcanza al menos 1.5 veces la de referencia, o si su p95 aumenta al menos un 20 % y 50 ms. Devuelve `improved` si una de las dos métricas disminuye al menos en la magnitud indicada y ninguna aumenta en esa medida. Devuelve `insufficient_data` si `sufficientData` es `false`. |
| `delta` | `requestCountAbsolute` y `requestCountRelative`, `errorRateAbsolute` y `errorRateRelative`, y `p95AbsoluteTime` y `p95Relative`. Un valor relativo es `null` si el valor de referencia es cero o no existe. |

Si falta `candidate` o `baseline`, o si las dos versiones son idénticas, la API devuelve `400`.

## Consulta las versiones de un servicio

`GET /api/v1/apm/services/{service}` devuelve en `versions` las versiones observadas en el rango. Cada una incluye
`red`, con las métricas del tráfico que atendió en el rango, y `verdict`, con el resultado frente a la versión del mismo servicio
cuya primera aparición fue inmediatamente anterior. El resultado sigue los criterios de [una comparación](#compara-versiones):

| Campo | Notas |
|---|---|
| `previous` | La versión anterior que sirve de referencia. |
| `status` | `regressed`, `improved`, `neutral` o `insufficient_data`. |
| `worse` | Lo que empeoró cuando `status` es `regressed`: `errorRate`, `latency` o ambos. |
| `delta` | Igual que en una comparación, con la versión anterior como referencia. |

La primera versión observada no tiene `verdict`. Un filtro de versión en la solicitud no limita
las cifras: la API consulta todas las versiones del servicio.

## Consulta dónde se produjeron los errores

`GET /api/v1/apm/errors` devuelve un `breakdown` junto con la página de resultados. Abarca todos los grupos que coinciden con el filtro `status`
(no solo los de esa página). `GET /api/v1/apm/errors/{fingerprint}` devuelve el `breakdown` del
grupo. Incluye `versions`, `environments` y `languages`, cada uno con una lista de entradas con `value` y `count`,
ordenadas de mayor a menor por número de ocurrencias. El valor está vacío si los spans no lo informaron. Después de los primeros
siete valores, el resto se agrupa en `__other__`. El lenguaje se obtiene del atributo
`telemetry.sdk.language` del servicio.

## Gestiona las reglas de agrupación de errores

Una regla agrupa los errores al detectarlos con criterios distintos de su tipo, su marco de pila y su endpoint. MoleSignal
evalúa las reglas en el orden de `position` y aplica la primera que coincide.

```http
POST /api/v1/apm/error-rules
Content-Type: application/json

{"name": "Upstream timeouts", "serviceNamespace": "shop", "serviceName": "checkout",
 "errorType": "*Timeout*", "message": "", "frame": "", "endpoint": "", "action": "merge", "enabled": true}
```

| Campo | Notas |
|---|---|
| `name` | Hasta 128 caracteres. Da nombre al grupo resultante de la unificación. |
| `serviceNamespace`, `serviceName` | Identifican el servicio al que se aplica la regla. Si `serviceName` está vacío, la regla se aplica a todos los servicios. Si indicas un espacio de nombres, indica también el nombre del servicio. |
| `errorType`, `message`, `frame`, `endpoint` | Patrones para el tipo de error, el mensaje de excepción, el primer marco de pila de la aplicación y el endpoint. Cada uno admite hasta 256 caracteres. El patrón debe coincidir con el texto completo, sin distinguir entre mayúsculas y minúsculas. Usa `*` para que coincida con cualquier texto. Un patrón vacío coincide con todo. Define al menos un patrón. |
| `action` | `merge`: los errores de un servicio que coinciden forman un solo grupo. `ignore`: no forman ningún grupo y sus solicitudes siguen contando como fallidas. |
| `enabled` | MoleSignal conserva las reglas desactivadas, pero no las evalúa. El valor predeterminado es `true`. |

La respuesta contiene la regla con su `id`, `position`, `updatedBy` y `updatedAt`. Cada organización
puede guardar hasta 100 reglas. `PUT /api/v1/apm/error-rules/order` recibe `{"ids": [...]}`, coloca esas reglas
primero en el orden indicado, deja las demás a continuación y devuelve las reglas en el nuevo orden.

El cambio surte efecto de inmediato en el nodo que lo guarda y en un máximo de 30 segundos en los demás. Solo afecta a los
errores detectados a partir de ese momento. Los grupos existentes no cambian.

## Consulta el mapa de servicios

`GET /api/v1/apm/map` acepta los parámetros comunes de intervalo, `environment` y `namespace`, y devuelve
`nodes`, `edges`, `namespaces` (los de los servicios del entorno), `environments` (todos los entornos) y
`truncated` (`true` cuando solo conserva los 400 nodos con más actividad).

| Campo | Notas |
|---|---|
| `nodes[].id` | `service:<name>`, `topic:<name>` o `<category>:<target>` para los destinos de las llamadas de los servicios. |
| `nodes[].kind` | `service`, `external` o `topic`. Un nodo externo incluye su `category`. |
| `nodes[].red` | `requestCount`, `errorCount`, `errorRate` y `p95Time`: métricas de las solicitudes que atendió un servicio o que recibió un nodo externo o un tema. Un servicio también incluye `health`, `namespace` y `environments`. |
| `edges[].kind` | `call`, `publish` (en un tema) o `consume` (desde un tema). |
| `change` | En una arista o un nodo, indica el cambio respecto al intervalo anterior de igual duración: `new` si antes no existía, `gone` si ya no existe. El campo no aparece si el intervalo anterior no tenía datos. |

Las llamadas entre servicios provienen del grafo de servicios y muestran el P95 del minuto más lento. El resto proviene
de los intervalos de agregación de APM. `GET /api/v1/apm/map/edge` acepta los identificadores de nodo `source` y `target` además de los mismos
parámetros y devuelve `kind`, `red`, `trend`, `operations` (`name`, `kind`, `red`), `everyCaller`
(`true` cuando las operaciones corresponden a los endpoints del servicio llamado e incluyen las llamadas de todos los orígenes) y `errors`, los
grupos de errores del servicio llamado.

## Consulta el alcance del impacto de un servicio

`GET /api/v1/apm/blast-radius` requiere `service` y acepta los parámetros comunes de intervalo y
`environment`. Consulta todo el mapa del entorno, sin importar el espacio de nombres, y
devuelve `meta`, `service` (el nodo del servicio, que no aparece si el mapa no lo incluye en el intervalo),
`upstream` (los nodos que llaman al servicio, hasta tres saltos) y `downstream` (los nodos a los que el servicio llama o en los que publica, hasta dos
saltos). Cada lado incluye como máximo 30 nodos y muestra primero los que tienen problemas. El resultado excluye las llamadas que desaparecieron respecto al intervalo
anterior.

| Campo | Notas |
|---|---|
| `id`, `kind`, `name`, `namespace`, `category` | El nodo tal como lo identifica el [mapa de servicios](#consulta-el-mapa-de-servicios). |
| `hops` | Número de llamadas que separan el nodo del servicio: `1` si el nodo llama al servicio o recibe llamadas de él directamente. |
| `via` | El nodo por el que pasa la ruta, un salto más cerca del servicio. |
| `health` | El estado del propio servicio. Para los destinos de las llamadas, el estado que reflejan las llamadas fallidas. |
| `red`, `call` | Las métricas de las solicitudes que el nodo atendió o recibió, y de las llamadas entre el nodo y `via`. |

## Registra y enumera los despliegues

`POST /api/v1/apm/deployments` acepta el despliegue en formato JSON y devuelve `201` con el despliegue y los campos
`id`, `createdBy` y `createdAt` añadidos. Consulta los campos, sus límites y ejemplos de CI en
[Despliegues](/es/apm/deployments#reporta-despliegues-desde-ci). MoleSignal determina los nombres del servicio y del entorno
según las reglas de nomenclatura, la asignación de entornos y los alias de la organización.
Al guardar la dirección del repositorio, MoleSignal oculta la contraseña. Para un cambio de configuración o una bandera de funcionalidad, establece
`kind` en `configuration` o `feature_flag`. No hace falta indicar `version`.

`GET /api/v1/apm/deployments` acepta `service`, `namespace`, `environment`, `from` y `to`. El
intervalo se expresa en microsegundos. Devuelve hasta 200 despliegues, del más reciente al más antiguo. Si registras un despliegue
sin indicar el espacio de nombres o el entorno, el despliegue aparece en todos los espacios de nombres o entornos, respectivamente.

## Guarda la configuración de APM

`GET /api/v1/apm/settings` devuelve la configuración de la organización. `PUT` la reemplaza por completo y
devuelve la configuración guardada:

```json
{
  "health": {
    "errorRateWarning": 0.02,
    "errorRateCritical": 0.1,
    "p95WarningTime": 500000,
    "p95CriticalTime": 2000000
  },
  "apdexThreshold": 500000,
  "longTaskTime": 1000000,
  "namingRules": [{ "pattern": "^(checkout)-[a-z0-9]{5}$", "replacement": "$1" }],
  "environmentMap": [{ "from": "Production", "to": "production" }],
  "aliases": [{ "aliasNamespace": "shop", "alias": "checkout-v1", "namespace": "shop", "service": "checkout" }],
  "metadataRules": { "teamFromTier": "p1", "ownerFromTier": "p0", "repositoryFromTier": null }
}
```

Si omites un campo, MoleSignal usa su valor predeterminado. MoleSignal elimina los espacios al inicio y al final de los nombres y usa `default` si el espacio de nombres de un alias está vacío.
Consulta los límites y la función de cada opción en [Configuración de APM](/es/apm/settings). Al guardar, los cambios se aplican de inmediato
en el nodo que los guarda y en un máximo de 30 segundos en los demás.

Consulta y reemplaza los límites de cardinalidad de la plataforma con `GET` y `PUT
/api/v1/settings/apm_limits`. Ambas operaciones requieren `sys.settings.limits.manage`. El cuerpo incluye
`servicesPerOrgHour`, `transactionsPerServiceHour`, `dependenciesPerServiceHour`,
`operationsPerDependencyHour`, `errorGroupsPerServiceHour`, `versionsPerServiceHour` e
`instancesPerServiceHour`, cada uno con un valor de 1 a 100000.

## Consulta los metadatos de la respuesta

Cada endpoint devuelve un objeto `meta` común:

```json
{
  "range": {
    "from": 1785801600000000,
    "to": 1785888000000000
  },
  "resolution": "minute",
  "projectionStartedAt": 1785798000000000,
  "lastCompleteBucketAt": 1785887940000000,
  "dataQuality": {
    "partial": false,
    "gaps": [],
    "overflowDimensions": []
  },
  "activationBoundary": false
}
```

- Interpreta `activationBoundary: true` como cobertura incompleta antes de `projectionStartedAt`.
- Interpreta `dataQuality.partial: true` como datos incompletos, no como un cero confirmado.
- Revisa `gaps` para detectar fallas en la cola, el repositorio, el vaciado, el procesamiento de datos tardíos, el control de cardinalidad o el apagado.
- Usa `lastCompleteBucketAt` para determinar si aún se están procesando los datos recientes.
- Revisa `overflowDimensions` antes de basarte en un desglose de alta cardinalidad.

## Errores

| Estado | Causa |
|---|---|
| `400` | Un parámetro no es válido: un `sort` no admitido (`unsupported APM sort field`), un `limit` fuera del intervalo de 1 a 200, un filtro vacío o demasiado grande (`invalid APM service filter`), un intervalo que supera el máximo (`APM query range exceeds configured maximum`), un fin anterior al inicio (`APM range end precedes start`), un `direction` o `resolution` desconocido, un SLO que no supera las validaciones anteriores (`SLO objective must be between 0 and 1, exclusive`) o un filtro de lista de SLO que no incluye los tres campos: `namespace`, `service` y `environment`. |
| `403` | El token no tiene el permiso necesario para hacer la llamada. |
| `404` | La huella del error, la transacción, el servicio o el SLO no existe en el intervalo. |
| `409` | Aún hay reglas de alerta que supervisan el SLO que intentas eliminar. |
