| Operación | Endpoint | Permiso |
|---|---|---|
| Listar | `GET /api/v1/scheduled_pipelines` | `pipelines.read` |
| Crear | `POST /api/v1/scheduled_pipelines` | `pipelines.create` y `audit.read` si el pipeline lee `_audit` |
| Obtener | `GET /api/v1/scheduled_pipelines/{id}` | `pipelines.read` |
| Actualizar | `PUT /api/v1/scheduled_pipelines/{id}` | `pipelines.edit` para cambiar la configuración, con `audit.read` si el pipeline lee `_audit`, y `pipelines.pause` si cambia `enabled` |
| Eliminar | `DELETE /api/v1/scheduled_pipelines/{id}` | `pipelines.delete` |
| Historial de ejecuciones | `GET /api/v1/scheduled_pipelines/{id}/runs` | `pipelines.read` |
| Límites de hoy | `GET /api/v1/scheduled_pipelines/{id}/limits` | `pipelines.read` |
| Procesamiento retroactivo | `POST /api/v1/scheduled_pipelines/{id}/backfill` | `pipelines.run` y `audit.read` si el pipeline lee `_audit` |

## Listar

Devuelve todos los pipelines con el estado de su última ejecución y un resumen de las últimas 24 horas:

<ResponseExample>
```json 200
[
  {
    "id": "3KBHcb6imgQq7FXBsROGTIRHOyg",
    "name": "normalize-app",
    "sourceStream": "app_raw",
    "targetStream": "app",
    "functionSteps": { "mode": "scheduled", "signalType": "logs", "sources": ["app_raw", "nginx_raw"], "steps": [ ... ] },
    "cron": "every:5m",
    "lookbackSecs": 300,
    "enabled": true,
    "lastRunAt": 1790000000000000,
    "readUntil": { "appRaw": 1789999940000000, "nginxRaw": 1789999940000000 },
    "retry": null,
    "alertRecord": null,
    "auditReaderId": null,
    "auditReader": null,
    "createdAt": 1789900000000000,
    "updatedAt": 1789900000000000,
    "lastRunState": "succeeded",
    "lastRunStartedAt": 1790000000000000,
    "lastRunFinishedAt": 1790000000250000,
    "lastRunScannedRows": 1200,
    "lastRunError": null,
    "runs24h": 288,
    "succeededRuns24h": 288,
    "failedRuns24h": 0
  }

```
</ResponseExample>

Cada elemento incluye los campos de [Obtener](#obtener), los datos de la última ejecución en `lastRunState`, `lastRunStartedAt`, `lastRunFinishedAt`, `lastRunScannedRows` (los eventos que leyó) y `lastRunError`, y los recuentos de ejecuciones de las últimas 24 horas.

## Obtener

```http
GET /api/v1/scheduled_pipelines/{id}
```

Devuelve el pipeline con la posición de lectura de cada fuente y el reintento previsto:

<ResponseExample>
```json 200
{
  "id": "3KBHcb6imgQq7FXBsROGTIRHOyg",
  "name": "normalize-app",
  "sourceStream": "app_raw",
  "targetStream": "app",
  "functionSteps": { "mode": "scheduled", "signalType": "logs", "sources": ["app_raw", "nginx_raw"], "steps": [ ... ] },
  "cron": "every:5m",
  "lookbackSecs": 300,
  "enabled": true,
  "lastRunAt": 1790000000000000,
  "readUntil": { "appRaw": 1789999940000000, "nginxRaw": 1789999640000000 },
  "retry": {
    "source": "nginx_raw",
    "attempt": 2,
    "nextAt": 1790000030000000,
    "error": "read: <reason>"
  },
  "alertRecord": null,
  "auditReaderId": null,
  "auditReader": null,
  "createdAt": 1789900000000000,
  "updatedAt": 1789900000000000
}
```
</ResponseExample>

| Campo | Notas |
|---|---|
| `readUntil` | Posición de lectura de cada fuente, en microsegundos. El pipeline ya procesó los eventos de la fuente anteriores a esa posición. No hay ninguna entrada para las fuentes que el pipeline aún no ha leído. |
| `retry` | El reintento previsto más próximo para una ventana que falló, o `null`. `source` indica el nombre de la fuente, `attempt` indica el número del próximo intento, `nextAt` indica cuándo está previsto y `error` indica por qué falló el último intento. |
| `alertRecord` | Recuentos de un pipeline de alertas para el último día en UTC en que recibió algún evento: `day` (`YYYY-MM-DD`), `processed`, `dropped` y `failed`. Incluye el último descarte y el último fallo de ese día en `last_dropped` y `last_failed`, respectivamente, cada uno con `atTime`, `rule` (la regla, la fuente de alertas o la comprobación sintética) y `reason`. Si falta un recuento, vale 0. El valor es `null` para los demás pipelines y para los pipelines de alertas que aún no han recibido ningún evento. Consulta [Recuentos diarios](/es/pipelines/alert-events#recuentos-diarios). |
| `auditReaderId` | ID de quien guardó el pipeline por última vez. El pipeline usa sus permisos para leer `_audit`. El valor es `null` si el pipeline no lee `_audit`. Consulta [Flujo de auditoría](/es/settings/data-security#flujo-de-auditoría). |
| `auditReader` | Campos `id`, `displayName` y `email` de la cuenta indicada en `auditReaderId`, disponibles para quien tenga `pipelines.read`. Si la cuenta ya no existe o no es posible consultar sus datos, el valor es `null` y `auditReaderId` no cambia. |

Consulta [Programación y posiciones de lectura](/es/pipelines#programación-y-posiciones-de-lectura) y [Reintentos y eventos no entregados](/es/pipelines#reintentos-y-eventos-fallidos).

## Actualizar y eliminar

`PUT` acepta el mismo cuerpo que [Crear un pipeline](/es/api/intake/create-pipeline) y reemplaza la configuración. Cambiar solo `enabled` requiere `pipelines.pause`. Cualquier otra solicitud `PUT`, incluso si no cambia nada, requiere `pipelines.edit`. Cambiar `enabled` de `false` a `true` restablece las posiciones de lectura, así que el pipeline vuelve a leer los últimos `lookbackSecs` de cada fuente. `DELETE` devuelve `{"deleted": true}`.

Si el pipeline lee `_audit`, una solicitud `PUT` también determina con qué permisos lo lee. Consulta [Flujo de auditoría](/es/settings/data-security#flujo-de-auditoría).

| La solicitud `PUT` | También requiere | Permisos que usa el pipeline para leer `_audit` |
|---|---|---|
| Cambia la configuración | `audit.read` y un token que no pertenezca a una cuenta de servicio | A partir de ese momento, usa los permisos de quien hizo la solicitud. |
| No cambia nada | Nada | A partir de ese momento, usa los permisos de quien hizo la solicitud si tiene `audit.read` y el token no pertenece a una cuenta de servicio. De lo contrario, conserva los permisos anteriores sin devolver ningún error. |
| Solo cambia `enabled` | Nada | Conserva los permisos anteriores. |

## Historial de ejecuciones

```http
GET /api/v1/scheduled_pipelines/{id}/runs?limit=50&beforeTime=<cursor>
```

Devuelve las ejecuciones de un pipeline programado, de la más reciente a la más antigua. Los pipelines en tiempo real y los de alertas no registran ejecuciones.

<ResponseExample>
```json 200
[
  {
    "id": "3KE7Yq0d3jvXm5cJ8r2bWQzN1aP",
    "pipelineId": "3KBHcb6imgQq7FXBsROGTIRHOyg",
    "state": "succeeded",
    "startedAt": 1790000000000000,
    "finishedAt": 1790000000250000,
    "scannedRows": 1200,
    "writtenRows": 1150,
    "droppedRows": 48,
    "failedRows": 2,
    "attempt": 1,
    "error": null,
    "warning": "stream `app` rejected 2 event(s): <reason>"
  }
]
```
</ResponseExample>

| Campo | Notas |
|---|---|
| `state` | `running`, `succeeded`, `failed` o `cancelled`. |
| `startedAt`, `finishedAt` | Momento en que empezó y terminó la ejecución. `finishedAt` es `null` mientras la ejecución está en curso. |
| `scannedRows` | Eventos que la ejecución leyó de sus fuentes. |
| `writtenRows` | Eventos que aceptaron todos los destinos. |
| `droppedRows` | Eventos que un paso descartó con `abort` o que eliminó la deduplicación. |
| `failedRows` | Eventos que provocaron un fallo en un paso, que el pipeline dirigió a una fuente o que algún destino no aceptó. |
| `attempt` | `1` para el primer intento. El valor es mayor si la ejecución volvió a procesar una ventana que falló. |
| `error` | Motivo del fallo de la ejecución: una ventana que falló, con el reintento previsto, o un flujo de destino que no aceptó ninguno de los eventos que le correspondían cuando el pipeline no tiene un flujo de eventos no entregados. |
| `warning` | Problemas que no hicieron fallar la ejecución, como eventos que no se pudieron procesar, eventos rechazados o no entregados, o una ventana que el pipeline omitió después de agotar los reintentos. |

`scannedRows` equivale a la suma de `writtenRows`, `droppedRows` y `failedRows`.

## Límites de hoy

```http
GET /api/v1/scheduled_pipelines/{id}/limits
```

Devuelve lo que los [pasos de cuota y limitación de tasa](/es/pipelines#recuento-y-límites) de un pipeline en tiempo real dejaron pasar y lo que quedó fuera del límite desde las 00:00 UTC de hoy, según los recuentos de todos los nodos. Los nodos suman sus recuentos cada 5 segundos. Si un paso no contabilizó nada hoy, no aparece ninguna fila para ese paso.

<ResponseExample>
```json 200
{
  "dayStart": 1790035200000000,
  "buckets": [
    {
      "step": "daily",
      "bucket": "[\"checkout\"]",
      "admittedEvents": 1000000,
      "admittedBytes": 524288000,
      "overEvents": 1240,
      "overBytes": 650117
    },
    {
      "step": "per-host",
      "bucket": "",
      "admittedEvents": 86400,
      "admittedBytes": 45298483,
      "overEvents": 12,
      "overBytes": 6291
    }
  ]
}
```
</ResponseExample>

| Campo | Notas |
|---|---|
| `step` | Nombre del paso. |
| `bucket` | Vacío para una cuota sin agrupar o un paso de limitación de tasa. Para una cuota agrupada, contiene una lista JSON con los valores de los campos de agrupación en el orden de esos campos. Usa `null` cuando un evento no tiene valor para un campo y `*` para los grupos que superan el máximo de 1.000. |
| `admittedEvents`, `admittedBytes` | Eventos y bytes que pasaron dentro del límite. |
| `overEvents`, `overBytes` | Eventos y bytes que superaron el límite y que, según la configuración del paso, este descartó, dejó pasar o envió a otro flujo. |

## Procesamiento retroactivo

```http
POST /api/v1/scheduled_pipelines/{id}/backfill
```

| Campo | Tipo | Notas |
|---|---|---|
| `startTime` | entero | Inicio de la ventana, en microsegundos. |
| `endTime` | entero | Fin de la ventana. Debe ser mayor que `startTime` y la ventana no debe superar los 31 días. |

<RequestExample>
```bash cURL
curl -X POST http://localhost:5080/api/v1/scheduled_pipelines/$PIPELINE_ID/backfill \
  -H "authorization: Bearer $MS_TOKEN" \
  -H 'content-type: application/json' \
  -d '{"startTime": 1790000000000000, "endTime": 1790086400000000}'
```
</RequestExample>

<ResponseExample>
```json 202
{
  "jobs": [
    {
      "source": "app_raw",
      "jobId": "3KE6epTrWXts1oa2ePEKIHKxG19",
      "monitor": "/api/v1/query/jobs/3KE6epTrWXts1oa2ePEKIHKxG19"
    },
    {
      "source": "nginx_raw",
      "jobId": "3KE6eqAbXq0n2yLr7VvTq9cUo4D",
      "monitor": "/api/v1/query/jobs/3KE6eqAbXq0n2yLr7VvTq9cUo4D"
    }
  ]
}
```
</ResponseExample>

El procesamiento retroactivo envía un trabajo de búsqueda por cada fuente. Cada trabajo lee su fuente durante la ventana, aplica los pasos y escribe, entrega y guarda los eventos no entregados del mismo modo que una ejecución programada. Las posiciones de lectura del pipeline no cambian. Usa la ruta `monitor` de cada trabajo para seguir su progreso. Consulta [Consultas](/es/query#rangos-de-tiempo-y-tareas-asincrónicas).

Un pipeline en tiempo real o de alertas devuelve `400` (`realtime and alert pipelines do not support backfill`). Un pipeline que lee `_audit` devuelve `403` si el token no tiene `audit.read` o pertenece a una cuenta de servicio. Al ejecutarse, el trabajo vuelve a comprobar los permisos de quien lo envió y falla si ya no tiene `audit.read`.
