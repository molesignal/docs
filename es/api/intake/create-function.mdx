```http
POST /api/v1/functions
```

Crea una transformación reutilizable para pipelines. Al crear la función, el sistema compila el código VRL o JavaScript y rechaza la función si el código no es válido. El binario incluye ambos entornos de ejecución. La llamada requiere `functions.create`.

**Cuerpo**

| Campo | Tipo | Obligatorio | Notas |
|---|---|---|---|
| `name` | string | Sí | Nombre de la función. |
| `language` | string | Sí | `vrl`, `js` o `llm`. Una función `llm` requiere `[functions].llm_eval_enabled` y un proveedor de modelos. |
| `source` | string | Sí | Código fuente en VRL o JavaScript, o instrucción de una función `llm`. |
| `paramsSchema` | object | No | Parámetros. Para `llm`, `outputField` selecciona el campo de salida, que es `_llm_eval` de forma predeterminada. |

<RequestExample>
```bash cURL
curl -X POST http://localhost:5080/api/v1/functions \
  -H "authorization: Bearer $MS_TOKEN" \
  -H 'content-type: application/json' \
  -d '{
    "name": "lowercase-level",
    "language": "vrl",
    "source": ".level = downcase!(string!(.level))"
  }'
```
</RequestExample>

Si hay un error de sintaxis, la API devuelve `400`, por ejemplo `js syntax error: Uncaught SyntaxError: Unexpected token '}'`. Prueba el código fuente antes de guardarlo con `POST /api/v1/functions/run`, que recibe `language`, `source` y un `input` de ejemplo, y devuelve `output`. Consulta [Funciones](/es/functions).

Otras rutas de funciones: `GET /api/v1/functions`, `GET`, `PUT` y `DELETE /api/v1/functions/{id}`. Las configuraciones predefinidas incluidas son de solo lectura.

## Prueba la transformación antes de guardarla

El endpoint de ejecución de prueba requiere `functions.run`, un permiso independiente de `functions.create`. Antes de agregar una transformación a la ingesta activa, usa una entrada representativa con campos ausentes y campos con formato incorrecto.

```bash
curl -X POST http://localhost:5080/api/v1/functions/run \
  -H "authorization: Bearer $MS_TOKEN" \
  -H 'content-type: application/json' \
  -d '{"language":"vrl","source":".level = downcase!(string!(.level))","input":{"level":"ERROR","message":"example"}}'
```

Para esta entrada, comprueba que `output.level` sea `error`, que la transformación conserve el campo `message`, que no interviene en ella, y que `dropped` sea `false`. Una compilación exitosa no garantiza que todos los eventos de producción cumplan las condiciones que da por sentadas la transformación. Por ejemplo, la conversión a cadena del ejemplo anterior puede fallar: requiere que `level` sea una cadena.

## Conecta la función a un pipeline

Al crear una función, el sistema guarda una definición reutilizable, pero no transforma automáticamente los eventos entrantes. Guarda el ID de la función que devuelve la API, agrega el paso de función correspondiente desde [Pipelines](/es/pipelines) y prueba el pipeline completo antes de activarlo para un flujo de datos en vivo.

Conserva una entrada representativa y la salida esperada junto con el cambio. Después de activar el pipeline, ingiere un evento controlado y consulta el flujo de destino para confirmar los campos almacenados. La respuesta de una ejecución de prueba no basta para validar la ruta de ingesta desplegada.

## Errores comunes

| Síntoma | Acción |
|---|---|
| Nombre de función vacío | Proporciona un `name` que no esté vacío. |
| El sistema rechaza el código fuente al crear la función | Corrige los errores de sintaxis o compilación antes de volver a intentarlo. |
| El sistema deniega la ejecución de prueba | Verifica el permiso `functions.run`; el permiso de creación es independiente. |
| La entrada provoca un error en tiempo de ejecución | Reproduce en una ejecución de prueba la estructura del campo que causa el error y contempla los campos ausentes o de otro tipo. |
| La función guardada no tiene efecto en los registros nuevos | Comprueba que la función esté asociada al pipeline y verifica el flujo de destino. |
