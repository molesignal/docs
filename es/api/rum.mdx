La API de RUM recibe los eventos de clientes web y móviles y permite consultarlos. Todos los endpoints usan el
prefijo `/api/v1/rum` y requieren un token de portador.

```http
Authorization: Bearer <token>
```

Para escribir eventos y segmentos de reproducción se requiere `rum.write`. Un [token de cliente](/es/api/auth/rum-token) vinculado a una aplicación concede
solo este permiso para esa aplicación. Para leer datos se requiere el permiso de lectura del área correspondiente: `rum.events.read`, `rum.sessions.read`, `rum.replay.read`, `rum.issues.read`, `rum.analytics.read`, `rum.applications.read` o `rum.playlists.read`. Las solicitudes de la plataforma pueden usar `sys.telemetry.read`
en el ámbito protegido `_sys`. Para crear, modificar y eliminar una aplicación se requiere `rum.applications.manage`. Para cambiar el estado, el equipo
o la persona asignada a una incidencia se requiere `rum.playlists.manage`.

Las filas corresponden a usuarios reales. Los resultados excluyen las sesiones de tipo `synthetics` o `ci_test`, a menos que un filtro indique `session.type`, `synthetics.*` o `ci_test.*`. Consulta [Tráfico de prueba](/es/rum/test-traffic). Un campo también puede ser una clave de una columna JSON: `feature_flags.<key>`, `context.<key>`, `usr.extra.<key>` o `view.custom_timings.<key>`.

Un **tipo** identifica la clase de fila que procesa un endpoint: `sessions`, `views`, `actions`, `errors`, `resources`, `longTasks`,
`vitals` o `logs`. Cada tipo corresponde al [flujo](/es/rum/events#dónde-se-almacenan-los-eventos) del mismo nombre, sin el prefijo
`rum_`.

## Envía un segmento de reproducción

```http
POST /api/v1/rum/replay
```

```json
{
  "application": "checkout-web",
  "sessionId": "6f1c2b7e-1d5a-4c6b-9a3e-0a1b2c3d4e5f",
  "seq": 1,
  "events": [{ "type": 2, "timestamp": 1790000000000, "data": { "node": {} } }]
}
```

`sessionId`, `seq` y `events` son obligatorios. También puedes enviar `env`, `service` y `version` con los valores que configuraste en el SDK:
estos campos describen la sesión a los [filtros de retención](/es/rum/sampling#filtros) de la aplicación. Así, la API no almacena segmentos de una
sesión que los filtros descartan. La API no acepta ningún otro campo. `events` contiene eventos de rrweb. Un token de cliente escribe
en la aplicación a la que está vinculado: puedes omitir `application`. Si indicas otro valor, la API devuelve `403`. Con cualquier otra credencial,
indica la aplicación. Si la aplicación no existe, la API devuelve `404`. La respuesta describe el segmento almacenado:
incluye `id`, `seq`, `eventCount` y `hasFullSnapshot`.

`GET /api/v1/rum/replay/{sessionId}` devuelve `sessionId`, `segmentCount` y `events`, que contiene los eventos de todos los
segmentos de la sesión en orden.

## Administra las aplicaciones

Una aplicación tiene un `id`, un `name`, una `platform` y `settings`:

```json
{
  "id": "checkout-web",
  "name": "Checkout web",
  "platform": "browser",
  "settings": {
    "collectIp": true,
    "collectGeo": true,
    "defaultPrivacy": "mask",
    "issuesPerHour": 100,
    "scrub": ["secrets", "emails", "phones", "cards", "national_ids", "url_params"],
    "sessionSampleRate": 100,
    "retentionFilters": [],
    "keepErrors": true,
    "sdk": { "sessionReplaySampleRate": 20, "forwardConsoleLogs": ["warn", "error"] },
    "segments": [{ "id": "enterprise", "name": "Enterprise", "conditions": [{ "field": "usr.extra.plan", "op": "is", "values": ["enterprise"] }] }]
  },
  "createdBy": "<user-id>",
  "createdAt": 1790000000000000,
  "updatedAt": 1790000000000000
}
```

| Campo | Regla |
|---|---|
| `id` | Solo al crear la aplicación. De 1 a 64 caracteres del conjunto `A-Z`, `a-z`, `0-9`, `.`, `_`, `:` y `-`. Si lo omites, el servidor lo genera a partir del nombre. No se puede cambiar. |
| `name` | Obligatorio al crear la aplicación. De 1 a 128 caracteres. |
| `platform` | `browser` (valor predeterminado), `android`, `ios`, `flutter`, `react-native` u `other`. |
| `settings` | `collectIp` y `collectGeo` son valores booleanos y su valor predeterminado es `true`. `defaultPrivacy` admite `mask` (valor predeterminado), `mask-user-input` o `allow`. `issuesPerHour` indica cuántas [incidencias](/es/rum/errors#problemas-nuevos-por-hora) nuevas abre la aplicación en una hora. Admite valores de 1 a 10000 y su valor predeterminado es 100. `scrub` enumera los tipos de texto confidencial que el servidor elimina de un evento antes de almacenarlo: `secrets`, `emails`, `phones`, `cards`, `national_ids` y `url_params`. De forma predeterminada, incluye todos los tipos. Si la lista está vacía, el servidor no elimina ninguno (consulta [Privacidad de RUM](/es/rum/privacy#elimina-el-texto-confidencial-al-recibir-los-eventos)). `sessionSampleRate` indica el porcentaje de sesiones que se conservan entre las que no coinciden con ningún filtro de retención. Es un número entero de 0 a 100 y su valor predeterminado es 100 (consulta [Muestreo de datos de RUM](/es/rum/sampling#conserva-un-porcentaje-de-las-sesiones-en-el-servidor)). Si el valor supera 100, el servidor devuelve `400`. `retentionFilters` es una lista de hasta 10 [filtros](/es/rum/sampling#filtros). Cada filtro tiene la estructura `{ "name", "rate", "conditions" }` y un `id` que el servidor genera a partir del nombre si lo omites y que conserva si cambias el nombre del filtro. Una solicitud `PATCH` reemplaza toda la lista. `rate` es un número entero de 0 a 100. Cada condición tiene la estructura `{ "field", "op", "values" }`. `field` admite `env`, `service`, `version`, `source`, `session.type`, `geo.country_iso_code`, `browser.name`, `os.name` o `device.type`; `op` admite `is` o `is_not`, y `values` admite de 1 a 20 valores. Cada filtro admite hasta 5 condiciones. Los nombres deben ser únicos, sin distinguir entre mayúsculas y minúsculas, y los identificadores `default` y `errors` están reservados. `keepErrors` conserva los errores de las sesiones que no se retienen y su valor predeterminado es `true`. Si la lista no es válida, el servidor devuelve `400`. `segments` es una lista de hasta 20 [segmentos](/es/rum/analytics#segmentos). Cada segmento tiene la estructura `{ "name", "conditions" }` y un `id` que el servidor genera a partir del nombre si lo omites y que conserva si cambias el nombre del segmento. Una solicitud `PATCH` reemplaza toda la lista. Cada condición tiene la estructura `{ "field", "op", "values" }`. `field` admite `service`, `version`, `source`, `usr.id`, `usr.email`, `account.id`, `browser.name`, `os.name`, `device.type`, `geo.country_iso_code`, `geo.continent_code`, `geo.city` o `usr.extra.<key>`; `op` admite `is` o `is_not`, y `values` admite de 1 a 20 valores. Cada segmento admite de 1 a 5 condiciones. `sdk` contiene la configuración que `GET /api/v1/rum/config` devuelve a un SDK que se inicia con `remoteConfiguration`. Puede incluir `sessionSampleRate` y `sessionReplaySampleRate` (de 0 a 100), `defaultPrivacyLevel`, `trackUserInteractions` y `forwardConsoleLogs` (una lista de `debug`, `log`, `info`, `warn` y `error`). Para las opciones que no incluye, el SDK usa los valores que proporciona la página. Si omites un campo al crear la aplicación, el servidor usa su valor predeterminado. Si lo omites en una solicitud `PATCH`, conserva su valor actual. |

`POST` devuelve la nueva aplicación. Si el identificador o el nombre ya existe, el servidor devuelve `409`. `PATCH` acepta cualquiera de estos campos: `name`, `platform` y
`settings`. `DELETE` devuelve `{ "deleted": true }`. Los eventos que ya envió la aplicación permanecen en los flujos hasta que
vence su período de retención.

## Busca filas

```http
GET /api/v1/rum/search?type=errors&from=1790000000000000&to=1790003600000000&filters=[{"field":"env","op":"=","value":"production"}]&limit=100
```

`POST` acepta los mismos parámetros en el cuerpo de la solicitud en formato JSON y sirve para consultas demasiado largas para una URL. En una URL, `filters`, `freeText` y
`columns` son listas codificadas en JSON.

| Parámetro | Tipo | Comportamiento |
|---|---|---|
| `type` | cadena | Obligatorio. Indica el tipo de filas. |
| `from`, `to` | entero | Intervalo en microsegundos desde la época Unix. De forma predeterminada, `to` es el momento actual y `from` es 24 horas antes de `to`. `to` debe ser mayor que `from`. |
| `filters` | lista | Condiciones que deben cumplir todas las filas. Consulta los detalles a continuación. |
| `freeText` | lista de cadenas | Hasta 8 palabras. Cada palabra debe aparecer en alguna de las columnas de texto del tipo, sin distinguir entre mayúsculas y minúsculas. |
| `columns` | lista de cadenas | Columnas que devuelve la respuesta. Si omites el parámetro, la respuesta incluye las columnas predeterminadas del tipo. La respuesta siempre incluye la columna que identifica la fila. |
| `limit` | entero | Tamaño de página, de 1 a 5,000. El valor predeterminado es 100. |
| `cursor` | cadena | El `nextCursor` o `previousCursor` de una respuesta anterior. Omite los demás parámetros o repítelos sin cambios. |

Un **filtro** tiene un `field`, un `op` y un `value`. Usa hasta 32 filtros y limita cada valor a 512 caracteres.

| `op` | Significado |
|---|---|
| `=`, `!=` | Igual y distinto, respectivamente. Si `value` está vacío, comprueban si el campo no tiene valor o si lo tiene, respectivamente. |
| `in`, `not_in` | El valor del campo coincide con uno de los valores de la lista o con ninguno, respectivamente. `value` es una lista JSON de 1 a 100 valores, como `["Chrome","Safari"]`. |
| `contains` | El campo contiene el texto, sin distinguir entre mayúsculas y minúsculas. Se aplica a columnas de texto y documentos JSON. |
| `>`, `>=`, `<`, `<=` | Comparan un valor numérico o temporal. |
| `exists`, `missing` | El campo tiene un valor o no lo tiene, respectivamente. |

Si el campo no existe para el tipo o no admite el operador, el servidor rechaza la solicitud con `400`.

La respuesta contiene las filas de una página, de la más reciente a la más antigua:

```json
{
  "items": [
    { "timestamp": 1790000001600000, "error.message": "Payment provider timeout", "error.id": "0a9b8c7d-6e5f-4a3b-8c1d-2e3f4a5b6c70" }
  ],
  "hasMore": true,
  "nextCursor": "<cursor>",
  "previousCursor": null
}
```

Cada fila incluye `timestamp` y las columnas solicitadas. Cada columna JSON contiene el documento. Las vistas y las sesiones
aparecen una sola vez, en su versión más reciente.

## Cuenta y describe las filas

`facets` acepta los parámetros de `search` sin paginación y agrega `field` (obligatorio) y `limit` (de 1 a 100, con 10 como valor predeterminado).
Devuelve los valores más frecuentes del campo entre las filas que coinciden con la consulta:

```json
{ "field": "browser.name", "values": [{ "value": "Chrome", "count": 812 }, { "value": "Safari", "count": 247 }] }
```

Si el recuento tarda demasiado o el sistema está ocupado, la respuesta contiene una lista vacía con `unavailable` establecido en `time_budget` o `busy`, respectivamente.
Si el campo contiene un documento JSON, el servidor devuelve `400`. Si indicas una clave del documento, como `feature_flags.checkout_v2`, el servidor hace el recuento por valor. Las facetas de `session.type` cuentan todos los tipos de sesión.

`keys` acepta los parámetros de selección, `column` (obligatorio: `feature_flags`, `context`, `usr.extra` o `view.custom_timings`) y `limit` (de 1 a 500, con 100 como valor predeterminado). El valor predeterminado de `type` es `views`. Devuelve las claves, empezando por la que aparece en más sesiones:

```json
{ "column": "feature_flags", "keys": [{ "key": "checkout_v2", "sessions": 812 }] }
```

`distribution` acepta los parámetros de selección, `field` (obligatorio: un campo numérico o una clave de una columna JSON que contenga un número) y `bars` (de 1 a 100, con 40 como valor predeterminado). Solo cuenta las filas almacenadas. Las barras cubren intervalos de igual amplitud desde el valor mínimo hasta el percentil 99, y la última también cuenta los valores que superan ese percentil, por lo que su `to` es el valor máximo. Si todos los valores son iguales, aparecen en una sola barra.

```json
{
  "field": "view.loading_time",
  "unit": "ns",
  "rows": 812,
  "min": 90000000,
  "max": 41000000000,
  "p50": 800000000,
  "p75": 1400000000,
  "p95": 3100000000,
  "p99": 6000000000,
  "bars": [{ "from": 90000000, "to": 237750000, "rows": 12 }]
}
```

`histogram` acepta los mismos parámetros de selección y los parámetros que definen los intervalos del recuento: `bucketTime` (como mínimo, 1000) y `originTime`, el inicio del
primer intervalo. Si omites `originTime`, toma el valor de `from` y no puede ser posterior a `from`. El rango admite hasta 512 intervalos. Cada intervalo tiene la estructura `{ startTime, total, errors }`. `errors` cuenta las filas
con problemas: sesiones y vistas con errores, acciones con señales de frustración y solicitudes con un código de estado de `400` o superior, o de
`0`. `split` es `false` para los tipos que no tienen filas de esa clase.

`GET /api/v1/rum/schema/{type}` enumera las columnas que los demás endpoints aceptan y devuelven:

```json
{
  "type": "views",
  "stream": "rum_views",
  "idField": "view.id",
  "versioned": true,
  "defaultColumns": ["view.id", "view.url_path", "view.loading_time"],
  "fields": [
    { "name": "view.loading_time", "dataType": "int64", "unit": "ns", "facetable": true, "indexed": false }
  ]
}
```

`dataType` admite `bool`, `int64`, `float64`, `utf8` o `json`. `unit` admite `ns`, `ms`, `epoch_ms`, `bytes`, `count`,
`score`, `percent`, `per_second`, `px` o `none`. El servidor almacena las duraciones en los nanosegundos que envía el SDK, y el cliente
les da formato. `epoch_ms` indica un instante en milisegundos desde la época Unix, como `session.start` y
`session.last_activity`, y el cliente lo muestra como fecha y hora. Un campo `facetable` admite recuentos por valor, un
campo `indexed` permite filtrar sin leer todas las filas e `idField` indica qué columna identifica cada fila.

## Medir filas

`aggregate` toma la selección de `search` y calcula medidas a partir de todas las filas que coinciden. Devuelve los valores que muestran los gráficos,
las tablas y los mapas, como el número de sesiones o el percentil 75 de una métrica vital, por página o por hora.

```http
GET /api/v1/rum/aggregate?type=views&groupBy=["view.url_path_group"]&measures=[{"fn":"count","name":"views"},{"fn":"p75","field":"view.performance.lcp.timestamp","name":"lcp"}]&limit=5
```

| Parámetro | Tipo | Comportamiento |
|---|---|---|
| `type`, `from`, `to`, `filters`, `freeText` | | Igual que en `search`. |
| `measures` | lista | Obligatorio. Hasta 16 medidas. Consulta los detalles a continuación. |
| `groupBy` | lista de cadenas | Hasta 2 campos. Devuelve una fila por cada combinación de sus valores. No puedes agrupar por un campo que contiene un documento JSON, pero sí por una de sus claves: `feature_flags.checkout_v2`. |
| `bucketTime`, `originTime` | entero | Igual que en `histogram`. Con estos parámetros, devuelve una fila por grupo y por barra. |
| `orderBy` | cadena | Nombre de una medida, de un campo de agrupación o `time` (barras sin grupos). Si lo omites, ordena los grupos por la primera medida y las barras en orden cronológico. |
| `order` | `asc` o `desc` | Si lo omites, usa el orden descendente para las medidas y el ascendente para los grupos o el tiempo. |
| `limit` | entero | Número de grupos, de 1 a 250. El valor predeterminado es 10. Con barras, el máximo es 20 y cada grupo aparece en todas las barras. |
| `estimate` | booleano | El valor predeterminado es `true`: estima los recuentos, las sumas y los promedios de todas las sesiones. Pondera cada fila según la tasa con la que se conservó (`retention.rate`) y usa la misma ponderación para los percentiles. Con `false`, cuenta las filas almacenadas, como en el explorador. |

Una **medida** tiene un `fn` y un `field`, y puede incluir un `name`, un `where` y un `fallback`.

| `fn` | Significado |
|---|---|
| `count` | Cuenta las filas. Si especificas un `field`, solo cuenta las filas con un valor en ese campo. Si activas `estimate`, ajusta el recuento según las tasas de retención. |
| `stored` | Cuenta las filas almacenadas, sin importar la tasa con la que se conservaron. |
| `count_distinct` | Cuenta los valores distintos de `field`. `fallback` indica qué campo usar cuando `field` no tiene valor, para distinguir a los usuarios sin ID por su ID anónimo. Cuenta los usuarios y los demás valores tal como se observaron. Si activas `estimate`, ajusta el recuento de sesiones (`session.id`). |
| `sum`, `avg`, `min`, `max` | Calcula la suma, el promedio, el mínimo o el máximo de un campo numérico. |
| `p50`, `p75`, `p90`, `p95`, `p99` | Estima el percentil de un campo numérico. |

`where` es una lista de filtros, como en `search`, y la medida solo usa las filas que los cumplen:
`{"fn":"count","where":[{"field":"session.error.count","op":"=","value":"0"}]}` cuenta las sesiones sin errores. Una medida
usa `name` como nombre si lo especificas; si no, usa `fn(field)` o, si no tiene campo, `fn`. Dos medidas no pueden tener el mismo nombre. Si solicitas un campo
que el tipo no tiene o un cálculo numérico sobre un campo que no es numérico, la solicitud devuelve `400`.

```json
{
  "groupBy": ["view.url_path_group"],
  "measures": [
    { "name": "views", "fn": "count", "unit": "count" },
    { "name": "lcp", "fn": "p75", "field": "view.performance.lcp.timestamp", "unit": "ns" }
  ],
  "rows": [
    { "group": ["/checkout"], "values": [8031, 3400000000.0] },
    { "group": [null], "values": [212, null] }
  ]
}
```

Cada fila contiene su `group`, en el orden de `groupBy`, y los `values` de las medidas, en el orden en que se especificaron. Si hay barras temporales,
también incluye `startTime`, el inicio de su barra. Un grupo cuyas filas no tienen valor devuelve `null`, al igual que un percentil sin
valores. `unit` es `count` o la unidad que `schema` indica para el campo. Solo se cuenta la versión más reciente de cada vista y sesión.
Si ninguna fila coincide, la respuesta no contiene filas cuando hay grupos o barras. Si no hay ni grupos ni barras, devuelve una fila con `0` en los recuentos y `null` en las demás medidas. Si faltan permisos para ver un valor, devuelve el texto que lo enmascara. Si un recuento tarda demasiado o
el sistema está ocupado, no devuelve filas y establece `unavailable` en `time_budget` o `busy`.

## Consulta de un panel de un dashboard

```http
POST /api/v1/rum/panel-statement
```

Devuelve la consulta SQL que ejecuta un panel de un [dashboard](/es/dashboards) para mostrar lo mismo que el [explorador](/es/rum/explorer#agregar-al-tablero):
los mismos valores de las mismas filas, tal como los calcula `aggregate` con `estimate` en `false`. No lee datos. La
consulta no especifica un rango de tiempo, porque el dashboard la ejecuta para el rango seleccionado. Requiere `rum.events.read`.

```json
{
  "type": "views",
  "filters": [{ "field": "env", "op": "=", "value": "production" }],
  "chart": "timeseries",
  "measures": [{ "fn": "p75", "field": "view.loading_time", "name": "p75 Loading" }],
  "groupBy": ["browser.name"],
  "groupNames": ["Browser"],
  "limit": 5,
  "interval": "${interval}"
}
```

| Campo | Tipo | Comportamiento |
|---|---|---|
| `type`, `filters`, `freeText` | | Igual que en `search`. |
| `chart` | cadena | Obligatorio. `timeseries`, `toplist`, `table` o `distribution`. |
| `measures`, `groupBy`, `orderBy`, `order`, `limit` | | Igual que en `aggregate`, excepto por `estimate` y las barras. Un `toplist` tiene un solo campo de agrupación. Una `timeseries` sigue hasta 20 grupos. Cada medida ocupa una columna con el nombre indicado en `name`. |
| `groupNames` | lista de cadenas | Nombres de las columnas de agrupación, en orden. Si no especificas un nombre, la columna usa el nombre de su campo. |
| `field` | cadena | Obligatorio para una `distribution`: el campo numérico que se distribuye. Su columna usa el primer nombre de `groupNames` y la columna de recuento usa el `name` de la primera medida. |
| `interval` | cadena | Obligatorio para una `timeseries`: intervalo en el que se divide el tiempo, indicado mediante una variable del dashboard como `${interval}` o una duración como `15 minutes`. |

```json
{
  "stream": "rum_views",
  "statement": "WITH \"__top\" AS (SELECT … LIMIT 5) SELECT date_bin(INTERVAL '${interval}', _timestamp) AS \"time\", … FROM \"rum_views_latest\" JOIN \"__top\" ON … GROUP BY 1, 2 ORDER BY 1, 2",
  "columns": [
    { "name": "time", "role": "time", "unit": "none" },
    { "name": "Browser", "role": "group", "unit": "none" },
    { "name": "p75 Loading", "role": "measure", "unit": "ms" }
  ],
  "limit": 10000
}
```

La consulta lee `stream` y la versión más reciente de cada vista o sesión, mediante `rum_views_latest` o
`rum_sessions_latest`. Aplica las condiciones de la selección y excluye las sesiones de pruebas sintéticas y de CI,
a menos que los filtros incluyan `session.type`, `synthetics.*` o `ci_test.*`. `columns` enumera las columnas que devuelve, en orden:
`time` con el inicio de la barra, los grupos y las medidas. El `unit` de cada medida indica en qué unidad se muestra. Por ejemplo, una duración se muestra en `ms`.

- Una `timeseries` devuelve una fila por cada barra y grupo. Incluye los grupos que ocupan los primeros lugares según la primera medida en
  todo el rango.
- Un `toplist` o una `table` devuelve una fila por grupo, en el orden solicitado, hasta `limit`.
- Una `distribution` devuelve 40 barras desde el valor mínimo hasta el percentil 99. La última también cuenta los valores que superan ese percentil. Cada
  barra lleva como nombre su valor inicial, expresado en la unidad en que se muestra.

`limit` indica cuántas filas solicita el panel. La solicitud devuelve `400` si el campo no existe para el tipo, si el gráfico no se puede generar con los parámetros indicados
(un `toplist` sin exactamente un campo de agrupación o una `timeseries` sin `interval`) o si `interval` no es una variable ni
una duración.

## Embudos, rutas y retención

Los tres endpoints de `/api/v1/rum/analytics` responden a las consultas de [análisis de RUM](/es/rum/analytics). Cada uno acepta los
parámetros de selección de `search` que se aplican a sesiones, vistas y acciones: `from` y `to` en microsegundos, y `filters`, que define los criterios que debe cumplir cada
fila, normalmente la aplicación (`application.id`) y el entorno (`env`). Con `GET`, las listas se pasan como JSON en sus
parámetros, de modo que la consulta se puede compartir como enlace; `POST` acepta los mismos nombres en un cuerpo JSON. Los endpoints requieren `rum.analytics.read` o `sys.telemetry.read`
en el ámbito protegido `_sys`. Si el recuento tarda demasiado o el sistema está ocupado, la respuesta no incluye cifras y establece `unavailable`
en `time_budget` o `busy`. Las respuestas incluyen los valores de `from` y `to` a los que corresponden.

### Embudo

```http
GET /api/v1/rum/analytics/funnel?filters=[{"field":"application.id","op":"=","value":"shop-web"}]&steps=[{"type":"views","filters":[{"field":"view.url_path_group","op":"=","value":"/cart"}]},{"type":"actions","name":"Paid","filters":[{"field":"action.target.name","op":"=","value":"Pay now"}]}]&windowSecs=1800&breakdown=browser.name
```

| Parámetro | Tipo | Comportamiento |
|---|---|---|
| `from`, `to` | entero | Microsegundos. Si se omiten, se usan los últimos 7 días. |
| `filters` | lista | Criterios que debe cumplir cada paso, además de sus propios filtros. |
| `steps` | lista | Obligatoria. De 2 a 8 pasos. Cada paso tiene un `type` (`views` o `actions`), una lista de `filters` como en `search` que se aplica a las filas de ese tipo y un `name` opcional. Si se omite `name`, se usa el valor del primer filtro. |
| `windowSecs` | entero | Tiempo máximo, en segundos, entre el primer paso y cualquier paso posterior. Si se omite, no hay límite. |
| `breakdown` | cadena | Campo de texto de las filas del primer paso. Genera un embudo por cada valor del campo. Solo conserva los 10 valores con más sesiones. |

Para el primer paso, la sesión cuenta a partir de la primera fila que cumple sus filtros. Para cada paso posterior, cuenta a partir de la primera fila que cumple sus filtros y aparece después
de la fila del paso anterior en la misma sesión.

```json
{
  "groups": [
    {
      "value": null,
      "steps": [
        { "name": "/cart", "sessions": 4, "conversion": 1.0, "fromPrevious": null, "medianMs": null },
        { "name": "Paid", "sessions": 2, "conversion": 0.5, "fromPrevious": 0.5, "medianMs": 210000.0 }
      ]
    }
  ],
  "from": 1779400000000000,
  "to": 1780000000000000
}
```

Cada grupo contiene el embudo de las sesiones con un mismo valor de `breakdown`, en el orden en que alcanzaron el primer paso,
y `value` es `null` para el conjunto de todas las sesiones o para las sesiones cuya fila no tiene valor. `conversion` es la proporción respecto a las
sesiones del primer paso, `fromPrevious` es la proporción respecto a las sesiones del paso anterior y `medianMs` es la mediana del tiempo transcurrido
desde el paso anterior. Cada valor es `null` cuando no aplica. Si el campo no es de texto o no existe para ese tipo de fila,
la solicitud devuelve `400`.

### Rutas

| Parámetro | Tipo | Comportamiento |
|---|---|---|
| `from`, `to`, `filters` | | Igual que en `funnel`. Las filas corresponden a las vistas. |
| `anchor` | cadena | Página donde empiezan las rutas o donde terminan al analizar hacia atrás. Si se omite, se usa la primera página de cada sesión o la última al analizar hacia atrás. |
| `backward` | booleano | Sigue las páginas anteriores al ancla. El valor predeterminado es `false`. |
| `depth` | entero | De 1 a 6 páginas después del ancla (o antes). El valor predeterminado es 3. |
| `by` | cadena | Campo que identifica cada página: `view.url_path_group` (el predeterminado), `view.url_path` o `view.name`. |

```json
{
  "columns": 3,
  "sessions": 9,
  "backward": false,
  "nodes": [
    { "column": 0, "page": "/products", "sessions": 2, "ends": 0 },
    { "column": 1, "page": "/cart", "sessions": 2, "ends": 0 },
    { "column": 2, "page": "/checkout", "sessions": 1, "ends": 1 }
  ],
  "links": [
    { "column": 0, "source": "/products", "target": "/cart", "sessions": 2 },
    { "column": 1, "source": "/cart", "target": "/checkout", "sessions": 1 }
  ],
  "from": 1779400000000000,
  "to": 1780000000000000
}
```

Las páginas se organizan en `columns`. Hay una columna más que el valor de `depth`. La columna 0 corresponde a la página de referencia de las rutas y es la última al analizar hacia atrás.
Cada nodo representa una página de una columna. `sessions` indica cuántas sesiones pasaron por ella y `ends` cuántas terminaron allí (o empezaron allí
al analizar hacia atrás). Un enlace conecta una página de `column` con una página de la columna siguiente en orden cronológico, incluso al analizar hacia atrás, e indica cuántas
sesiones siguieron esa ruta. Las páginas aparecen en el orden en que se abrieron. Si una página se vuelve a abrir de inmediato, solo cuenta una vez. Cada
columna muestra las 8 páginas con más sesiones y agrupa las demás en `__other__`. `sessions` indica cuántas sesiones incluyen
la página de referencia de las rutas.

### Retención

| Parámetro | Tipo | Comportamiento |
|---|---|---|
| `from`, `to`, `filters` | | Igual que en `funnel`. Las filas corresponden a las sesiones. Si se omiten `from` y `to`, el historial abarca el doble de `periods` desde el momento actual hacia atrás, con un mínimo de 14 días (8 semanas para `week`), para formar cohortes. |
| `period` | `day` o `week` | Un día en UTC o una semana en UTC que empieza el lunes. El valor predeterminado es `day`. |
| `periods` | entero | De 1 a 30 períodos después del primero. El valor predeterminado es 7. |

```json
{
  "period": "day",
  "periods": 3,
  "cohorts": [
    { "startTime": 1779408000000000, "users": 1, "returned": [1, 0, null] },
    { "startTime": 1779494400000000, "users": 6, "returned": [0, null, null] }
  ],
  "from": 1779408000000000,
  "to": 1779753600000000
}
```

Una cohorte agrupa a las personas cuya primera aparición dentro del intervalo solicitado ocurre en el período que comienza en `startTime`. Cada persona se identifica
mediante el `usr.id` de la sesión o, si no existe, mediante `usr.anonymous_id`. `returned` indica, para cada período posterior, cuántas personas de la
cohorte volvieron a aparecer. El valor es `null` si el período aún no había terminado en `to`.

## Mapas de calor

Los endpoints de `/api/v1/rum/heatmaps` devuelven los datos de los [mapas de calor de RUM](/es/rum/heatmaps). Aceptan `from` y `to` en microsegundos y `filters`, normalmente `application.id`, `view.url_path_group` y el ancho de la ventana (`display.viewport.width`). Con `GET`, la lista se pasa como JSON en su parámetro. `clicks` y `scroll` también aceptan `limit` y requieren `rum.analytics.read`. Cuentan las filas almacenadas, sin estimaciones.

```json
{
  "clicks": 148,
  "elements": [
    {
      "element": "body>main>button:nth-of-type(2)",
      "name": "Pay now",
      "selector": "button.pay",
      "clicks": 92,
      "sessions": 60,
      "frustrated": 4,
      "pageX": 640.5,
      "pageY": 720.0,
      "cells": [[5, 4, 31], [6, 4, 28]]
    }
  ],
  "from": 1779400000000000,
  "to": 1780000000000000
}
```

`clicks` devuelve los elementos con más clics. El límite va de 1 a 300 y el valor predeterminado es 100. `element` indica dónde se encuentra el elemento en la página. `pageX` y `pageY` son las coordenadas promedio de los clics en la página. `cells` divide el elemento en una cuadrícula de 10 por 10 celdas, cada una con el formato `[column, row, clicks]`.

```json
{
  "views": 310,
  "pageHeight": 4200,
  "medianDepth": 1800,
  "bands": [{ "depth": 800, "reached": 1.0 }, { "depth": 900, "reached": 0.97 }],
  "from": 1779400000000000,
  "to": 1780000000000000
}
```

`scroll` devuelve el número de vistas con datos de profundidad de desplazamiento, la altura de la página y la profundidad que alcanzó la mitad de esas vistas. Cada franja mide 100 píxeles. `reached` indica la proporción de vistas que alcanzaron esa profundidad y nunca aumenta a medida que se desciende.

`snapshot` acepta `viewId`, el identificador de una de las vistas candidatas, y requiere `rum.replay.read`. Devuelve `candidates`, hasta 20 vistas de la página con una grabación, de la más reciente a la más antigua, cada una con `sessionId`, `viewId`, `atTime` y las dimensiones de la ventana (`width` y `height`). También devuelve `snapshot`, con los mismos datos para la vista que se muestra y los `events` de rrweb que la reconstruyen en `atTime` a partir de la última captura completa anterior. `snapshot` es `null` si no se grabó ninguna sesión en la que se abrió la página.

## Listas de reproducción

Una [lista de reproducción](/es/rum/playlists) es una lista con nombre que agrupa sesiones de una aplicación e indica en qué momento conviene abrir cada una.

```json
{
  "id": "2xT9bQ1kLw5nVf8cZ0aR7mHpJd3",
  "application": "checkout-web",
  "name": "Checkout failures",
  "description": "Sessions that ended at the checkout with an error.",
  "createdBy": "<user-id>",
  "createdAt": 1790000000000000,
  "updatedAt": 1790000100000000,
  "sessionCount": 2,
  "sessions": [
    { "sessionId": "3f6c9a52-1b7e-4d08-a5c3-90e2d41f7b68", "atTime": 1790000005000000, "addedBy": "<user-id>", "addedAt": 1790000000000000 },
    { "sessionId": "9d41e7b0-62fa-4c3d-8e15-b7a09c52d3f4", "atTime": null, "addedBy": "<user-id>", "addedAt": 1790000100000000 }
  ]
}
```

`GET /api/v1/rum/playlists` devuelve las listas de reproducción sin `sessions`, de la modificada más recientemente a la más antigua, y acepta `application` para
filtrar por una aplicación. La lectura requiere `rum.playlists.read`, aunque las solicitudes de la plataforma pueden usar `sys.telemetry.read`. Las demás solicitudes modifican una lista de reproducción
y requieren `rum.playlists.manage`. Todas devuelven la lista con sus sesiones, excepto `DELETE`, que devuelve `{ "deleted": true }`.

| Solicitud | Cuerpo | Regla |
|---|---|---|
| `POST /rum/playlists` | `application`, `name` y, opcionalmente, `description` y `sessions` | La aplicación debe existir (`404`). El nombre debe tener entre 1 y 128 caracteres y no puede coincidir con el de otra lista de la misma aplicación, sin distinguir entre mayúsculas y minúsculas (`409`). La descripción admite hasta 1000 caracteres. |
| `PATCH /rum/playlists/{id}` | `name` y `description`, ambos opcionales | Los campos omitidos conservan su valor. La aplicación no se puede cambiar. |
| `POST /rum/playlists/{id}/sessions` | `sessions` | Si agregas de nuevo una sesión, se actualiza su `atTime` y conserva su posición. Una lista de reproducción admite como máximo 500 sesiones (`400`). |

En una solicitud, una sesión tiene el formato `{ "sessionId": "...", "atTime": 1790000005000000 }`. El identificador debe tener entre 1 y 128 caracteres. Si especificas `atTime`,
indica en microsegundos desde la época Unix el momento en que se abre la sesión. Si lo omites, la sesión se abre desde el inicio. La
lista guarda identificadores, no sesiones: no comprueba si la sesión existe. Si la política de retención elimina las filas de una sesión, esta permanece
en la lista. `GET /api/v1/rum/sessions/{id}/playlists` devuelve, sin sus sesiones, las listas de reproducción que contienen la sesión indicada.

## Consulta una fila o una sesión

`GET /api/v1/rum/{type}/{id}` devuelve una fila con todas sus columnas o `404`. `from` y `to` acotan la búsqueda; sin
estos parámetros, la búsqueda abarca los últimos 30 días. `{id}` es el valor de `idField` del tipo.

`GET /api/v1/rum/sessions/{id}/timeline` devuelve:

| Campo | Contenido |
|---|---|
| `session` | La fila de la sesión o `null` si aún no se ha generado. |
| `items` | Las filas de los demás tipos que pertenecen a la sesión, de la más antigua a la más reciente. Cada fila tiene un `type`: `view`, `action`, `error`, `resource`, `long_task`, `vital` o `log`. |
| `truncated` | Los tipos cuyo número de filas supera el límite de la cronología. |

`GET /api/v1/rum/sessions/{id}/related-traces` enumera las trazas del backend de una sesión. Incluye las trazas cuyo ID figura en una solicitud
de la sesión (`relation: direct`) o, si no hay ninguna, las trazas que se ejecutaron durante la sesión
(`relation: time-correlated`). Cada traza incluye `trace_id`, `service`, `spanCount`, `durationMs` y
`startedAt`, y la respuesta incluye `primaryService`. `GET /api/v1/rum/traces/{traceId}/session` hace la consulta inversa
y devuelve la sesión o `null`.

## Comentarios

```http
POST /api/v1/rum/sessions/{id}/comments
```

```json
{ "application": "checkout-web", "atTime": 1790000005000000, "body": "The button does nothing here." }
```

`atTime` indica el momento de la sesión en microsegundos desde la época Unix y `body` contiene de 1 a 2000 caracteres. Una sesión admite hasta 500 comentarios. `GET` devuelve `{ "comments": [...] }` en orden cronológico y requiere `rum.replay.read`.

```json
{
  "id": "2xT9bQ1kLw5nVf8cZ0aR7mHpJd3",
  "application": "checkout-web",
  "sessionId": "3f6c9a52-1b7e-4d08-a5c3-90e2d41f7b68",
  "atTime": 1790000005000000,
  "body": "The button does nothing here.",
  "authorId": "<user-id>",
  "authorName": "Ada",
  "createdAt": 1790000010000000,
  "updatedAt": 1790000010000000,
  "editable": true
}
```

`POST` requiere `rum.replay.comments.write`. `PATCH` acepta `body`. Tanto `PATCH` como `DELETE` requieren ese permiso para los comentarios propios y `rum.replay.comments.manage` para los ajenos. `editable` indica si se puede modificar el comentario. `DELETE` devuelve `{ "deleted": true }`.

## Resumen

`GET /api/v1/rum/sessions/{id}/summary` devuelve `{ "summary": ... }` con el resumen guardado en el idioma de lectura o con `null`, y requiere `rum.replay.read`. `POST` genera un resumen con un modelo y requiere `rum.replay.summaries.generate`. Si hay un resumen guardado, devuelve ese resumen sin llamar al modelo. Con `{ "regenerate": true }`, llama al modelo, salvo que la sesión no haya cambiado.

```json
{
  "summary": {
    "sessionId": "3f6c9a52-1b7e-4d08-a5c3-90e2d41f7b68",
    "language": "en-us",
    "summary": "The user filled the cart and could not pay: the payment call failed three times.",
    "chapters": [{ "atTime": 1790000005000000, "title": "Fills the cart", "summary": "Adds two items." }],
    "model": "<model>",
    "promptTokens": 1820,
    "completionTokens": 240,
    "generatedAt": 1790000020000000
  }
}
```

La llamada consume parte del presupuesto diario de Mole Agent con el origen `replay_summary`. Si se agota el presupuesto, la API devuelve `429`. Devuelve `400` si la organización no tiene un proveedor de modelos habilitado con una clave o si la sesión no contiene nada que resumir.

## Problemas

MoleSignal agrupa los errores similares en [problemas](/es/rum/errors). Cada fila de error incluye el ID de su problema en `error.issue_id`.
MoleSignal calcula las cifras de cada problema a partir de sus errores en el intervalo solicitado. Guarda el estado y el historial por separado.
Las marcas de tiempo se expresan en microsegundos desde la época Unix.

```http
GET /api/v1/rum/issues?application=checkout-web&status=unresolved&sort=sessions&limit=50
```

| Parámetro | Tipo | Comportamiento |
|---|---|---|
| `application` | cadena | Obligatorio. |
| `env`, `source` | cadena | Incluye solo los errores de este entorno o los que envía este origen (`browser`, `flutter`, etc.). |
| `filters` | lista | Condiciones adicionales para filtrar los errores que se cuentan, igual que en `search`. |
| `from`, `to` | entero | Igual que en `search`. |
| `status` | cadena | `unresolved` (valor predeterminado: abiertos, en investigación y reaparecidos), `all` o uno de estos valores: `open`, `investigating`, `regressed`, `resolved`, `ignored`. |
| `assignee`, `team` | cadena | ID de usuario o de equipo, o `none` para los problemas sin asignar. |
| `search` | cadena | Palabras que aparecen en el tipo, el mensaje o la ubicación del problema, sin distinguir entre mayúsculas y minúsculas. |
| `fresh` | booleano | Incluye solo los problemas detectados por primera vez o que reaparecieron en el intervalo. |
| `sort` | cadena | `sessions` (valor predeterminado), `users`, `occurrences`, `lastSeen`, `firstSeen` o `status`. |
| `order` | `asc` o `desc` | Si se omite, el orden es descendente, salvo para `status`. |
| `limit` | entero | De 1 a 100. El valor predeterminado es 50. |

```json
    }
  ],
  "total": 8
}
```

`regressedEnvironment` indica el entorno del error que hizo reaparecer el problema, o `null` si ese error no especifica un entorno. Un problema
pertenece a toda la aplicación, independientemente del entorno en el que ocurran sus errores. El servidor también registra cuándo se detectó por primera
vez en cada entorno. Las [reglas de alerta](/es/rum/alerts#limitar-el-alcance-de-una-regla) usan esa marca de tiempo para contar los problemas nuevos de cada entorno.

La consulta selecciona los 250 problemas con más sesiones (o usuarios u ocurrencias, según `sort`) y los filtra por `status`, `assignee`,
`team`, `search` y `fresh`. `total` indica cuántos problemas quedan tras aplicar los filtros y antes de aplicar `limit`. `trend` contiene las ocurrencias
de cada una de las hasta 12 partes iguales del intervalo, de la más antigua a la más reciente. `overflow` identifica el problema que agrupa los errores de una aplicación una vez que esta alcanza
el [límite de problemas que puede abrir por hora](/es/rum/errors#problemas-nuevos-por-hora). Si el recuento tarda demasiado o el sistema está ocupado,
la consulta no devuelve problemas y establece `unavailable` en `time_budget` o `busy`.

`GET /api/v1/rum/issues/{id}` devuelve el problema con el mismo formato que la lista, sin `trend`, con `sessions`, `users` y `occurrences`
calculados para el intervalo entre `from` y `to`, y con dos campos adicionales:

| Campo | Contenido |
|---|---|
| `samples` | Las tres sesiones más recientes en las que ocurrió el problema, de la más reciente a la más antigua: `timestamp`, `sessionId`, `userId`, `anonymousId`, `page`, `browser`, `system`, `version`, `hasReplay` y `retained`. `retained` es `false` si el error corresponde a una sesión que no se conservó y que, por tanto, no se puede abrir. |
| `stack` | La traza de pila del error más reciente que tenga marcos. Si ningún error tiene marcos, devuelve la del error más reciente con `frames` vacío. Si no hay errores del problema en el intervalo, devuelve `null`. Incluye `message`, `text`, `frames`, `symbolication`, `handling`, `isCrash` y `category`. Cada marco incluye `raw` (los datos enviados por el SDK), `restored` (los datos que resolvió un artefacto de depuración, o `null`) e `inApp`. Si se intentó resolver los marcos, `symbolication` es `completed`, `partial` o `missing`. |

Si el problema no existe, la API devuelve `404`.

`PATCH /api/v1/rum/issues/{id}` acepta `status`, `assigneeId` y `teamId` en cualquier combinación y devuelve el problema actualizado.

```json
{ "status": "resolved", "assigneeId": "<user-id>", "teamId": null }
```

`status` admite `open`, `investigating`, `resolved` o `ignored`. Las reglas establecen `regressed` cuando un problema resuelto reaparece en
una versión más reciente. Si intentas establecer ese valor, la API devuelve `400`. `assigneeId` debe identificar a un miembro de la organización y `teamId` a un equipo de la misma organización. Usa `null` o una
cadena vacía para quitar la asignación correspondiente. Si omites un campo, conserva su valor. Al resolver un problema, la API registra `resolvedAt`, `resolvedBy` y la versión más reciente de
la aplicación en `resolvedVersion`. Cualquier cambio de estado da por terminado el registro de la resolución o reaparición anterior. Si la solicitud no indica ningún campo que modificar, la API devuelve `400`. Si los valores coinciden con los actuales, devuelve `200` sin hacer cambios. La API registra cada cambio en el registro de auditoría como `rum.issue.update`.

## Vista previa de una regla de alerta

```http
POST /api/v1/rum/alerts/preview
```

Consulta qué habría detectado una [regla de alerta sobre una métrica de RUM](/es/rum/alerts) durante el último intervalo, ventana por ventana, con
el mismo código que evalúa la regla. Requiere `rum.events.read`.

```json
{
  "query": { "applicationId": "checkout-web", "environment": "production", "page": "/checkout", "metric": "lcp_p75" },
  "periodSecs": 3600
}
```

| Campo | Tipo | Comportamiento |
|---|---|---|
| `query` | objeto | Obligatorio. Define la métrica con `applicationId` y `metric`, y con `environment`, `page`, `version` y `minSamples` si se especifican. Rechaza `page` o `version` si la métrica no admite ese filtro, y `minSamples` si la métrica es un recuento. `custom_vital` y `custom_timing` también aceptan `customName` (obligatorio) y `statistic`. `query` requiere `search`, que incluye `type`, la instrucción original en `statement`, los `filters` y el `freeText` extraídos de la instrucción, y `measure` (`fn` y `field`). Consulta [Crear una regla](/es/api/alerting/create-rule#reglas-de-rum). |
| `periodSecs` | entero | Obligatorio. Define la ventana de evaluación de la regla, de 60 a 21 600. Cada punto corresponde a una ventana. |
| `from`, `to` | entero | Intervalo en microsegundos desde la época de Unix. Solo se consultan ventanas completas. `to` toma la hora actual de forma predeterminada. `from` toma de forma predeterminada un valor de seis horas antes de `to`, ajustado para abarcar entre 12 y 72 ventanas sin superar un día. Un intervalo abarca como máximo 360 ventanas. |

```json
{
  "metric": "lcp_p75",
  "unit": "milliseconds",
  "minSamples": 50,
  "periodSecs": 3600,
  "from": 1789956800000000,
  "to": 1790000000000000,
  "points": [
    { "at": 1789956800000000, "value": null, "samples": null },
    { "at": 1789960400000000, "value": 2480, "samples": 612 }
  ],
  "current": { "at": 1789996400000000, "value": 2310, "samples": 540 }
}
```

`unit` puede ser `count`, `percent`, `milliseconds`, `score`, `bytes` o `none`. Cada punto indica el inicio de la ventana en `at`, el valor de la métrica en `value` y la
cantidad de filas que contribuyen a la métrica en `samples`. Si una ventana tiene menos filas que `minSamples`, el punto no incluye `value` ni `samples`. `current` es el último punto:
la ventana que termina en `to`. Si un recuento tarda demasiado o el sistema está ocupado, la respuesta no incluye puntos e indica en `unavailable`
`time_budget` o `busy`, respectivamente. Si la aplicación no existe, la respuesta es `404`. Si la regla no es compatible con la métrica, la respuesta es `400`.

## Errores

| Estado | Causa |
|---|---|
| `400` | Un parámetro, filtro, columna o cursor no es válido para la solicitud. |
| `401`, `403` | Falta el token, no es válido o no tiene el permiso que exige el endpoint. |
| `404` | La fila, la sesión o la aplicación no existe. |
| `409` | Ya existe una aplicación con ese identificador o nombre. |
| `413` | La solicitud supera los límites de [`events`](/es/rum/events#envía-eventos). |
