Ambas llamadas requieren `alerts.incidents.read` sobre el incidente.

## Incidentes similares

```http
GET /api/v1/alerts/incidents/{id}/similar
```

Encuentra los incidentes abiertos en la misma organización en los 90 días anteriores al momento en que se disparó este que más se le parecen: como máximo 5, primero los de mayor puntuación y, en caso de empate, primero los más recientes. Quedan fuera los incidentes fusionados en él y el incidente en el que está fusionado. La puntuación es la suma de las filas de abajo, y un incidente necesita al menos 2 para aparecer en la lista:

| Criterio | Valor en `reasons` | Puntuación |
|---|---|---|
| La misma huella de alerta | `fingerprint` | 5 |
| La misma regla (cuando la huella es distinta) | `rule` | 3 |
| Servicios compartidos | `services` | coincidencia × 2 |
| Etiquetas similares: los pares clave-valor compartidos son al menos 0,3 de todos los pares en ambos | `labels` | proporción × 2 |
| Un título similar: similitud de trigramas de al menos 0,3, calculada como lo hace `pg_trgm` de PostgreSQL, chino incluido | `title` | similitud × 2 |
| Enrutado al mismo equipo | `team` | 1 |

La coincidencia es la intersección de ambos lados sobre su unión.

<RequestExample>
```bash cURL
curl http://localhost:5080/api/v1/alerts/incidents/$INCIDENT_ID/similar \
  -H "authorization: Bearer $MS_TOKEN"
```
</RequestExample>

<ResponseExample>
```json 200
{
  "incidents": [
    {
      "id": "3KEDNEyqouYJeBDTLTMTBui7XHW",
      "summary": "High error rate · checkout",
      "severity": "critical",
      "status": "resolved",
      "createdAt": 1789400000000000,
      "resolvedAt": 1789401800000000,
      "resolvedBy": "<user-id>",
      "score": 7.6,
      "reasons": ["fingerprint", "services", "labels", "team"],
      "notes": 2,
      "rootCause": "Connection pool exhausted after the payments client stopped releasing connections."
    }
  ]
}
```
</ResponseExample>

| Campo | Descripción |
|---|---|
| `score`, `reasons` | La puntuación y de dónde salió; consulta la tabla de arriba. |
| `resolvedBy` | Quién lo resolvió; `null` cuando su regla se recuperó por sí sola o sigue activo. |
| `notes` | Cuántas [notas](/es/api/alerting/add-incident-note) tiene. |
| `rootCause` | La primera frase que dice algo en su [causa raíz con IA](/es/api/alerting/incident-rca) (se omiten los encabezados y las líneas en blanco), como máximo 200 caracteres; se omite cuando no tiene análisis. |

## Cambios recientes

```http
GET /api/v1/alerts/incidents/{id}/changes
```

Lista los [cambios reportados](/es/apm/deployments#reporta-despliegues-desde-ci) desde 30
minutos antes de que se disparara el incidente hasta 10 minutos después, para los servicios del incidente (sus servicios
afectados y su etiqueta `service`) y los servicios que dependen de ellos: como máximo 20, primero los más antiguos.
Los servicios que dependen de ellos provienen del mapa de servicios de APM, para como máximo los primeros 3 servicios del incidente; sin
un mapa de servicios solo cuentan los servicios propios del incidente. Cuando la regla del incidente se editó en las 24 horas
anteriores al disparo, también se lista un cambio de tipo `rule`.

<RequestExample>
```bash cURL
curl http://localhost:5080/api/v1/alerts/incidents/$INCIDENT_ID/changes \
  -H "authorization: Bearer $MS_TOKEN"
```
</RequestExample>

<ResponseExample>
```json 200
{
  "from": 1789998200000000,
  "to": 1790000600000000,
  "changes": [
    {
      "kind": "deployment",
      "at": 1789999100000000,
      "service": "payments",
      "downstream": true,
      "version": "v2026.10.28",
      "status": "succeeded",
      "commit": "9f2c1e4",
      "author": "dana",
      "link": "https://ci.example.com/pipelines/4821"
    },
    {
      "kind": "rule",
      "at": 1789960000000000,
      "downstream": false,
      "ruleId": "3KEDBLvTYO6DnWi8H9S9MNLpPT7",
      "ruleName": "Checkout error rate"
    }
  ]
}
```
</ResponseExample>

| Campo | Descripción |
|---|---|
| `from`, `to` | El intervalo de tiempo consultado, en microsegundos Unix. |
| `kind` | `deployment`, `configuration`, `feature_flag` o `rule` (se editó la regla del incidente). |
| `downstream` | `true` cuando el cambio pertenece a un servicio que depende del incidente, no a uno de los suyos. |
| `version`, `status`, `commit`, `description`, `author` | Lo que traía el reporte; se omite cuando no lo traía. |
| `link` | La dirección de la canalización reportada o, en su defecto, la dirección de la solicitud de extracción. |
| `ruleId`, `ruleName` | La regla de un cambio `rule`. |

**Errores**

| Estado | Motivo |
|---|---|
| `403` | Al token le falta `alerts.incidents.read` o no puede acceder a este incidente. |
| `404` | El incidente no existe. |

## Impacto en el negocio

```http
GET /api/v1/alerts/incidents/{id}/business-impact
```

Para cada [clave de negocio](/es/business-context) que llevan los spans, lista los valores cuyas solicitudes a los
servicios del incidente fallaron más, desde 30 minutos antes de que se disparara el incidente hasta 10 minutos después
(no más tarde que ahora): como máximo 5 valores por clave, primero los que tienen más solicitudes fallidas y luego los que tienen más solicitudes. Un
incidente sin servicios lee las solicitudes de todos los servicios. Las solicitudes son los spans en los que un servicio recibió
una solicitud.

<RequestExample>
```bash cURL
curl http://localhost:5080/api/v1/alerts/incidents/$INCIDENT_ID/business-impact \
  -H "authorization: Bearer $MS_TOKEN"
```
</RequestExample>

<ResponseExample>
```json 200
{
  "from": 1789998200000000,
  "to": 1790000600000000,
  "services": ["checkout"],
  "declared": true,
  "keys": [
    {
      "key": "tenant",
      "label": "Tenant",
      "field": "tenant.id",
      "more": true,
      "values": [
        { "value": "acme", "requests": 300, "errors": 120, "important": true },
        { "value": "globex", "requests": 90, "errors": 4, "important": false }
      ]
    }
  ]
}
```
</ResponseExample>

| Campo | Descripción |
|---|---|
| `services` | Los servicios del incidente, cuyas solicitudes se leyeron. Vacío cuando no nombra ninguno. |
| `declared` | `false` cuando ninguna clave de negocio nombra un campo de span: `keys` queda entonces vacío. |
| `field` | El campo de span del que se leyó la clave. |
| `important` | El valor está entre los que la organización marcó como importantes para la clave. |
| `more` | Había más valores con solicitudes que los listados. |

Se omite una clave cuyo campo falte en el flujo de trazas o se mantenga cifrado, o de la que ninguna solicitud tuviera un valor.

**Errores**

| Estado | Motivo |
|---|---|
| `403` | Al token le falta `alerts.incidents.read` o no puede acceder a este incidente, o le faltan tanto `streams.query` como `sys.telemetry.read`. |
| `404` | El incidente no existe. |
