```http
GET /api/v1/alerts/rules
GET /api/v1/alerts/rules/{id}
```

La primera llamada devuelve todas las reglas de alerta de la organización en un arreglo. La segunda llamada devuelve una sola regla. Ambas llamadas requieren `alerts.rules.read`.

<RequestExample>
```bash cURL
curl http://localhost:5080/api/v1/alerts/rules \
  -H "authorization: Bearer $MS_TOKEN"
```
</RequestExample>

<ResponseExample>

Una regla incluye los campos de [Crear una regla](/es/api/alerting/create-rule) y los siguientes campos de solo lectura:

| Campo | Notas |
|---|---|
| `id`, `orgId` | Identificadores de la regla y de la organización. |
| `createdAt`, `updatedAt` | Microsegundos desde la época de Unix. |
| `lastEvalAt` | Momento en que finalizó la última evaluación, en microsegundos. El valor es `null` hasta que finaliza la primera evaluación. Si una consulta falla o agota el tiempo de espera, el valor no cambia. |
| `lastState` | Resultado de esa evaluación: `{"kind": "healthy"}` cuando no se cumplió la condición, `{"kind": "pending", "consecutive": 1}` mientras la condición se cumple durante menos de `forPeriods` evaluaciones, `{"kind": "firing"}` cuando se cumple durante suficientes evaluaciones y `{"kind": "dropped"}` cuando se activó la regla, pero un [pipeline de alertas](/es/pipelines/alert-events#qué-ocurre-con-un-evento) descartó el incidente que habría abierto. Una regla en estado `firing` no abre otro incidente durante el período de espera de `silenceSecs`. |

Si el `id` no existe, la API devuelve `404`.
