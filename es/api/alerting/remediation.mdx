Una acción de remediación es una corrección predefinida, como ejecutar un trabajo de reversión en Jenkins o reiniciar un
Deployment. Para ejecutarla en un incidente, se requiere [aprobación](/es/agent#aprobaciones-y-ejecuciones):
L2 requiere una persona que apruebe y L3 requiere dos. Quien solicita la ejecución no puede aprobarla. Si la organización
activa la [aprobación previa](#aprobación-previa), se puede otorgar el mismo número de aprobaciones por adelantado. Tras la aprobación, la acción se ejecuta
de inmediato. El resultado y la verificación posterior quedan registrados en la
[cronología](/es/api/alerting/incident-timeline) del incidente. Consulta cómo se usa en las páginas en
[Remediación](/es/alerting/remediation).

| Método y ruta | Qué hace | Permiso |
|---|---|---|
| `GET /api/v1/alerts/remediation/actions` | Devuelve las acciones de remediación de la organización. | `alerts.remediation.read` |
| `POST /api/v1/alerts/remediation/actions` | Crea una acción de remediación. | `alerts.remediation.manage` |
| `PUT /api/v1/alerts/remediation/actions/{id}` | Reemplaza una acción de remediación. | `alerts.remediation.manage` |
| `DELETE /api/v1/alerts/remediation/actions/{id}` | Elimina una acción de remediación. | `alerts.remediation.manage` |
| `GET /api/v1/alerts/remediation/clusters` | Devuelve los clústeres de Kubernetes registrados. | `alerts.remediation.read` |
| `POST /api/v1/alerts/remediation/clusters` | Registra un clúster. | `alerts.remediation.manage` |
| `PUT /api/v1/alerts/remediation/clusters/{id}` | Modifica un clúster. | `alerts.remediation.manage` |
| `DELETE /api/v1/alerts/remediation/clusters/{id}` | Elimina un clúster. | `alerts.remediation.manage` |
| `POST /api/v1/alerts/remediation/clusters/{id}/test` | Prueba la conexión y devuelve `{ "ok": true, "version": "v1.30.2" }`. | `alerts.remediation.manage` |
| `GET /api/v1/alerts/incidents/{id}/remediations` | Devuelve las acciones que se aplican al incidente y las ejecuciones de esas acciones en el incidente. | `alerts.incidents.read` en el incidente |
| `POST /api/v1/alerts/incidents/{id}/remediations` | Solicita una ejecución en el incidente y la envía para su aprobación. | `alerts.incidents.remediate` en el incidente |
| `GET /api/v1/alerts/remediation/preapproval` | Indica si la organización tiene activada la aprobación previa. Para cada acción con aprobación previa, devuelve el número de ejecuciones en su período de vigencia y su estado. | `alerts.remediation.read` |
| `PUT /api/v1/alerts/remediation/preapproval` | Activa o desactiva la aprobación previa para la organización. Cuerpo: `{ "enabled": true }`. | `alerts.remediation.preapprove` |
| `PUT /api/v1/alerts/remediation/actions/{id}/preapproval` | Establece o reemplaza la aprobación previa de una acción. | `alerts.remediation.preapprove` y `agent.approve` |
| `DELETE /api/v1/alerts/remediation/actions/{id}/preapproval` | Elimina la aprobación previa de una acción. | `alerts.remediation.preapprove` |
| `POST /api/v1/alerts/remediation/actions/{id}/preapproval/confirm` | Permite que una segunda persona confirme la aprobación previa de una acción L3. | `alerts.remediation.preapprove` y `agent.approve` |

El registro de auditoría guarda las operaciones de creación, modificación y eliminación, así como las solicitudes de ejecución. También registra la activación y desactivación de la aprobación previa y cuándo se establece, confirma o elimina una aprobación previa.

## Acciones de remediación

**Cuerpo de la solicitud**

| Campo | Tipo | Obligatorio | Notas |
|---|---|---|---|
| `name` | cadena | Sí | De 1 a 120 caracteres. |
| `description` | cadena | No | Una descripción. |
| `target` | objeto | Sí | Define cómo se ejecuta la acción: `kind` admite `http` o `kubernetes`. Los demás campos se describen a continuación. |
| `parameters` | arreglo | No | Parámetros que se completan al ejecutar la acción. Admite hasta 10. Consulta los detalles a continuación. |
| `services` | arreglo | No | Servicios a los que se aplica la acción. Si este campo y `teamIds` están vacíos, la acción se aplica a todos los incidentes. De lo contrario, debe coincidir algún servicio o el equipo del incidente. |
| `teamIds` | arreglo | No | Equipos a los que se aplica la acción. |
| `risk` | cadena | No | `l2` (valor predeterminado, una persona que aprueba) o `l3` (dos personas que aprueban). |
| `verifyAfterSecs` | entero | No | Segundos que deben transcurrir desde una ejecución exitosa hasta la verificación, de 0 a 86400. Valor predeterminado: `0` (sin verificación). |
| `verifyBy` | cadena | No | Criterio de éxito: `incidentResolved` (valor predeterminado, el incidente está resuelto o cerrado) o `rule_healthy` (la regla del incidente vuelve a estar en buen estado). |
| `enabled` | booleano | No | Valor predeterminado: `true`. Las acciones desactivadas no se pueden ejecutar. |

**`target`: una solicitud HTTP**

| Campo | Tipo | Notas |
|---|---|---|
| `kind` | cadena | `http`. |
| `method` | cadena | `GET`, `POST` (valor predeterminado), `PUT` o `PATCH`. |
| `url` | cadena | Plantilla de la dirección. Debe comenzar con `http://` o `https://`. |
| `headers` | objeto | Encabezados de la solicitud. Sus valores son plantillas y se almacenan cifrados. |
| `body` | cadena | Plantilla del cuerpo en JSON, de hasta 16384 caracteres. Un marcador sin comillas puede representar un número. Si al interpretar todos los marcadores como `0` el resultado no es JSON válido, la llamada devuelve `400`. El cuerpo se envía como `application/json`. Deja el campo vacío para enviar la solicitud sin cuerpo. |
| `signingSecret` | cadena | Secreto de firma que se almacena cifrado. Si lo configuras, la solicitud incluye `X-MoleSignal-Timestamp` y `X-MoleSignal-Sign`, que se calculan igual que en la [firma del webhook genérico](/es/notification-channels/webhooks#encabezados-y-firma). |

La solicitud solo se conecta a las IP a las que resuelve la dirección, rechaza las direcciones de metadatos de la nube, no sigue
redirecciones y agota el tiempo de espera tras 30 segundos. Una respuesta 2xx indica que la solicitud se completó correctamente.

**`target`: Kubernetes**

| Campo | Tipo | Notas |
|---|---|---|
| `kind` | cadena | `kubernetes`. |
| `clusterId` | cadena | Un clúster registrado. |
| `operation` | cadena | `restart` (reinicio gradual, como `kubectl rollout restart`), `scale` (cambio del número de réplicas) o `rollback` (reversión a la versión anterior, como `kubectl rollout undo`). |
| `workloadKind` | cadena | `Deployment`, `StatefulSet` o `DaemonSet`. Solo se puede revertir un Deployment y no se puede escalar un DaemonSet. |
| `namespace`, `workloadName` | cadena | El espacio de nombres y el nombre de la carga de trabajo. Ambos admiten plantillas. |
| `replicas` | cadena | Número de réplicas al que se quiere escalar. Admite una plantilla como `{{params.replicas}}`. |

**`parameters[]`**

| Campo | Tipo | Notas |
|---|---|---|
| `key` | cadena | Escribe `{{params.<key>}}` en las plantillas. |
| `label` | cadena | Nombre que se muestra al ejecutar la acción. |
| `kind` | cadena | `text` (valor predeterminado), `number` o `select`. |
| `options` | arreglo | Opciones de un `select`. |
| `required` | booleano | Valor predeterminado: `false`. |
| `default` | cadena | Valor que se usa si no se proporciona otro. |

**Variables de la plantilla**: `{{incident.id}}`, `{{incident.summary}}`, `{{incident.severity}}`,
`{{incident.status}}`, `{{incident.service}}` (la etiqueta `service` o, en su defecto, el primer servicio afectado),
`{{incident.url}}` (la página del incidente) y `{{params.<key>}}`. Los valores se codifican con porcentajes en la dirección
y se escapan como cadenas JSON en un cuerpo JSON. Las variables desconocidas se sustituyen por cadenas vacías.

<RequestExample>
```bash cURL
curl -X POST http://localhost:5080/api/v1/alerts/remediation/actions \
  -H "authorization: Bearer $MS_TOKEN" \
  -H "content-type: application/json" \
  -d '{
    "name": "Roll back checkout",
    "target": {
      "kind": "http",
      "method": "POST",
      "url": "https://jenkins.example.com/job/rollback/buildWithParameters?service={{incident.service}}",
      "headers": { "Authorization": "Bearer <jenkins-token>" },
      "body": "{\"reason\": \"{{params.reason}}\", \"incident\": \"{{incident.url}}\"}"
    },
    "parameters": [{ "key": "reason", "label": "Why", "required": true }],
    "services": ["checkout"],
    "risk": "l3",
    "verifyAfterSecs": 600,
    "verifyBy": "incident_resolved"
  }'
```
</RequestExample>

La respuesta contiene la acción guardada. La API nunca devuelve los valores de los encabezados ni el secreto de firma: los valores de
`headers` están vacíos y `secretsSet` enumera los secretos configurados, por ejemplo,
`["header:Authorization", "signing_secret"]`. Al modificar una acción, deja vacío un encabezado u omite
`signingSecret` para conservar sus valores. Envía `signingSecret` vacío para eliminar la firma.

## Clústeres de Kubernetes

| Campo | Tipo | Obligatorio | Notas |
|---|---|---|---|
| `name` | cadena | Sí | Un nombre. |
| `apiServer` | cadena | Sí | Dirección del servidor de la API. Debe comenzar con `https://`. |
| `caCert` | cadena | No | Certificado de CA en formato PEM. Si dejas el campo vacío, se usan los certificados raíz de confianza del sistema. |
| `token` | cadena | Al crear | Token de ServiceAccount. La API lo almacena cifrado y nunca lo devuelve. Si dejas el campo vacío al modificar un clúster, se conserva el valor existente. |

El token necesita los permisos `get` y `patch` en las cargas de trabajo de destino. Para una reversión, también necesita permiso para listar ReplicaSets.
Las conexiones solo se establecen con las IP a las que resuelve la dirección del servidor de la API, rechazan las direcciones de metadatos de la nube y
agotan el tiempo de espera tras 30 segundos. No se puede eliminar un clúster que todavía usa alguna acción.

## Aprobación previa

Cuando la organización activa la aprobación previa (desactivada de forma predeterminada), puede aprobar una acción por adelantado. Para los servicios indicados, la acción puede ejecutarse hasta un número determinado de veces dentro de un intervalo sin esperar una aprobación cada vez. La aprobación previa de una acción L2 se aplica en cuanto se configura. Para una acción L3, solo se aplica cuando una segunda persona la confirma con `confirm`. La aprobación previa adelanta la aprobación, pero nunca reduce el número de personas que deben aprobar. Para configurarla o confirmarla, una persona debe iniciar sesión. No se puede usar un token de API.

**Cuerpo de la solicitud** (`PUT /api/v1/alerts/remediation/actions/{id}/preapproval`)

| Campo | Tipo | Obligatorio | Descripción |
|---|---|---|---|
| `services` | matriz | Sí | Hasta 20 servicios cubiertos, todos dentro del alcance de la acción. |
| `maxRuns` | entero | Sí | Número máximo de ejecuciones dentro del intervalo, de 1 a 20. |
| `windowSecs` | entero | Sí | Duración del intervalo, de 300 a 604800 segundos. |
| `expiresAt` | entero | No | Momento de vencimiento, en microsegundos desde la época Unix. Si se omite, la aprobación previa no vence. |
| `channels` | matriz | No | Hasta 5 destinos a los que se envía un aviso después de cada ejecución. Usa `connectorId`, `targetType` y `target`, al igual que en los destinos de una política de notificaciones. |

La respuesta es `{ "preapproval": { ... } }` y agrega `approvers` (`[{ "userId", "at" }]`), `setBy` y `setAt` al cuerpo. Quien configura la aprobación previa es la primera persona en aprobarla. Si alguien la reemplaza, solo queda registrada la aprobación de quien la reemplazó. Si cambia el destino, los parámetros, los servicios, los equipos o el riesgo de la acción, el sistema borra la lista de personas que aprobaron y exige una nueva confirmación.

`GET /api/v1/alerts/remediation/preapproval` devuelve `{ "enabled": true, "actions": { "<action-id>": { "used": 1, "state": "active" } } }`. `state` puede ser `off` (la organización desactivó la aprobación previa), `expired` (venció), `awaiting_approver` (una acción L3 aún requiere la confirmación de una segunda persona), `used_up` (se agotaron las ejecuciones del intervalo) o `active` (está activa).

Cuando la aprobación previa se aplica y se solicita la acción para un incidente de un servicio cubierto, el sistema registra la aprobación a nombre de quienes configuraron y confirmaron la aprobación previa e inicia la ejecución de inmediato. Quien solicita la acción aún necesita `alerts.incidents.remediate`. La aprobación previa de quien hace la solicitud no cuenta para esa solicitud. Si no hay suficientes aprobaciones previas de otras personas, la solicitud queda pendiente de aprobación como de costumbre. Quien hace la solicitud nunca figura entre las revisiones registradas. Si se agotan las ejecuciones, vence la aprobación previa o la organización la tiene desactivada, la solicitud sigue el proceso de aprobación habitual. Después de la ejecución, tenga éxito o no, el sistema envía un aviso a los destinos de `channels`.

## Ejecutar una acción en un incidente

```http
GET /api/v1/alerts/incidents/{id}/remediations
```

Devuelve `{ "actions": [ ... ], "runs": [ ... ] }`: las acciones habilitadas que se aplican a este incidente (sin los
secretos) y las ejecuciones del incidente. Si se rechazó o canceló la aprobación de una ejecución, o si venció, la ejecución aparece como
`declined`.

```http
POST /api/v1/alerts/incidents/{id}/remediations
```

| Campo | Tipo | Obligatorio | Notas |
|---|---|---|---|
| `actionId` | cadena | Sí | Acción que se va a ejecutar. Debe aplicarse a este incidente. |
| `inputs` | objeto | No | Valores de los parámetros, identificados por el `key` de cada parámetro. Incluye todos los parámetros obligatorios, usa valores numéricos para los parámetros numéricos, elige solo entre las opciones disponibles y no agregues parámetros adicionales. Los parámetros omitidos toman sus valores predeterminados. Cada valor admite hasta 500 caracteres. |
| `reason` | cadena | No | Motivo que figura en la aprobación, de hasta 2000 caracteres. Si se omite, el sistema lo genera. |

<RequestExample>
```bash cURL
curl -X POST http://localhost:5080/api/v1/alerts/incidents/$INCIDENT_ID/remediations \
  -H "authorization: Bearer $MS_TOKEN" \
  -H "content-type: application/json" \
  -d '{"actionId": "<action-id>", "inputs": {"reason": "pool exhausted after v2026.10.28"}}'
```
</RequestExample>

La respuesta es `{ "run": { ... }, "approval": { ... } }`: la ejecución y la solicitud de aprobación correspondiente.
El riesgo de la aprobación coincide con el `risk` de la acción. El impacto indica a qué dirección se enviará la solicitud o qué operación
se realizará, en qué carga de trabajo y en qué clúster. Quienes revisan la solicitud la aprueban o rechazan con
`POST /api/v1/agent/approvals/{approvalId}/review` y el cuerpo `{ "approve": true, "comment": "…" }`.
Esta operación requiere `agent.approve`. La ejecución comienza en cuanto se reúnen suficientes aprobaciones. Si se aplica la
[aprobación previa](#aprobación-previa) de la acción, la ejecución termina antes de que el sistema envíe la respuesta, que también incluye
`"preapproved": true` y `execution`. El campo `preapproved` de la ejecución es `true`.

| `status` | Significado |
|---|---|
| `awaiting_approval` | En espera de aprobación. |
| `running` | En ejecución. |
| `succeeded`, `failed` | La ejecución tuvo éxito o falló. `output` contiene el inicio de la respuesta o el error. |
| `declined` | La aprobación se rechazó, venció o se canceló, y la acción no se ejecutó. |
| `verifying` | La ejecución tuvo éxito y el sistema la verifica en el momento indicado por `verifyAt`. |
| `verified`, `verification_failed` | La verificación tuvo éxito o falló. `verification` indica el resultado. |

**Errores**

| Estado | Motivo |
|---|---|
| `400` | Un campo no es válido, el clúster no pertenece a esta organización, la acción no se aplica a este incidente o está deshabilitada, un valor de entrada no es válido o el incidente ya se resolvió. |
| `403` | Falta un permiso o el incidente está fuera del alcance autorizado. |
| `404` | La acción, el clúster o el incidente no existe. |
