A los clientes no les importa qué servicio falló, sino que no pueden finalizar la compra. Elige los recorridos
más importantes y monitorea cada uno desde tres perspectivas: una comprobación sintética que lo prueba desde fuera,
los usuarios reales que lo recorren y el backend que lo sustenta.

| Perspectiva | Herramienta | Qué detecta | Qué no detecta |
|---|---|---|---|
| Desde fuera | [Comprobaciones sintéticas](/es/synthetics) | Interrupciones a cualquier hora, incluso sin tráfico; certificados vencidos; fallas de DNS. | Problemas que solo afectan a ciertos usuarios, dispositivos o datos. |
| Usuarios reales | [RUM](/es/rum) | Páginas lentas, errores del frontend, señales de frustración y lo que realmente hacen los usuarios. | No detecta nada si nadie realiza el recorrido. |
| Backend | [SLO de APM](/es/apm#objetivos-de-nivel-de-servicio) | Errores y latencia de los endpoints del recorrido, con un presupuesto de errores. | Fallas que ocurren antes de que una solicitud llegue al backend. |

## Dale un nombre al recorrido y define cuándo se completa correctamente

Describe el recorrido paso a paso. Por ejemplo: abre la página del producto, agrégalo al carrito, paga y consulta la confirmación.
Para cada paso, indica la página o el endpoint y los criterios de éxito: el estado, el contenido y un
límite de tiempo, como «pago confirmado en un máximo de 3 segundos».

Mantén los nombres uniformes en todas las herramientas: usa los mismos nombres de vista en RUM, las mismas plantillas de ruta en APM y el
nombre del recorrido en las comprobaciones sintéticas.

## Comprueba el recorrido desde fuera

1. Crea una comprobación de **HTTP / API** para cada paso crítico de la API y una de **Navegador** para todo el
   recorrido. Consulta [Crear y publicar una comprobación](/es/synthetics#crea-y-publica-una-comprobación).
2. Define los criterios de éxito: configura una aserción de nivel **Crítico** para el estado y el texto de confirmación, y una de nivel
   **Advertencia** para el límite de tiempo.
3. Ejecuta las comprobaciones desde al menos dos ubicaciones para que una sola falla en una ruta de red no cuente como una interrupción. Configura
   los umbrales de falla y recuperación para evitar cambios de estado repetidos.
4. Selecciona **Probar revisión** y luego **Publicar revisión**. Los cambios crean un borrador, así que la comprobación publicada sigue
   ejecutándose hasta que valides la nueva revisión.

Las comprobaciones de navegador se ejecutan como máximo una vez por minuto. Las de API pueden ejecutarse con mayor frecuencia. Usa cuentas y
métodos de pago de prueba. Nunca uses datos reales de clientes.

## Monitorea a los usuarios reales

Con el [SDK de RUM para navegador](/es/rum/browser-sdk) en la aplicación:

- En [Rendimiento](/es/rum/performance), monitorea el percentil 75 de LCP, INP y CLS en las páginas del
  recorrido.
- En [Frustración](/es/rum/frustration), busca clics repetidos por frustración, clics sin efecto y clics que generan errores en los
  pasos del recorrido.
- En [Errores](/es/rum/errors), asigna los problemas del recorrido al equipo responsable.
- Abre las [reproducciones de sesiones](/es/rum/session-replay) de los recorridos fallidos para ver lo que vieron los usuarios. Usa la
  [configuración de privacidad](/es/rum/privacy) para ocultar los datos personales.

Crea [alertas de RUM](/es/rum/alerts) para las métricas que indican que el recorrido falla para muchos usuarios,
como la tasa de errores o una métrica web principal de la página clave del recorrido.

## Monitorea el backend con un SLO

Crea un [SLO](/es/apm#objetivos-de-nivel-de-servicio) para el endpoint del paso crítico, por
ejemplo, el endpoint de pago. Selecciona **La solicitud se completa correctamente dentro del límite de tiempo** y fija un umbral de latencia que coincida con
el límite de tiempo del recorrido. Agrega las [alertas de tasa de consumo del presupuesto de errores](/es/apm#alertas-de-tasa-de-consumo): el consumo rápido
notifica al personal de guardia y el consumo lento genera una advertencia.

## Informa a los clientes

Crea un componente en la [página de estado](/es/status-pages) para el recorrido, como «Finalizar compra». Usa la
[automatización de la publicación](/es/status-pages#automatización-de-publicaciones) para vincularlo con las comprobaciones sintéticas y las reglas de alerta
del recorrido. Empieza con **Aprobación manual**: una falla confirmada genera un borrador de actualización que debe aprobar
el personal de respuesta a incidentes.

## Revisa el recorrido cada semana

Copia el dashboard de RUM integrado de la aplicación con **Crear copia**. Agrega los resultados de las comprobaciones sintéticas y
el SLO, y programa un [informe](/es/reports) semanal para el equipo. Revisa las tendencias, no solo los
incidentes: si una métrica web principal empeora un poco cada semana, la próxima versión podría hacer que el recorrido falle.

## Criterios de aceptación

- Cada recorrido crítico tiene al menos una comprobación sintética publicada que se ejecuta correctamente desde dos ubicaciones.
- RUM cubre las páginas del recorrido y los errores tienen un responsable.
- El paso del backend tiene un SLO con alertas de tasa de consumo del presupuesto de errores.
- La página de estado tiene un componente para el recorrido, vinculado a sus comprobaciones o reglas.
- Si una comprobación falla en un entorno de prueba, el personal de guardia recibe una notificación y se genera un borrador de actualización.
