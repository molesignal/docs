El acceso se amplía con cada excepción: hace falta un permiso más para una tarea, un panel para un contratista o
un token para un script. Sin un plan, al cabo de un año nadie sabe quién puede eliminar un flujo ni qué token
sigue escribiendo datos. Define el modelo desde el principio y ajusta las excepciones a ese modelo.

## Asigna roles según las funciones

Parte de las tareas de cada puesto y elige el rol más restrictivo que permita realizarlas. Consulta la
[referencia de permisos](/es/identity/roles#referencia-de-permisos) para saber qué permisos incluye cada rol.

| Función | Rol | Nota |
|---|---|---|
| Consulta paneles, registros e incidentes | **Lector** | Es el rol predeterminado para la mayoría. Los lectores también pueden conversar con Mole Agent. |
| Crea paneles, reglas de alertas y canalizaciones; responde a avisos de guardia | **Editor** | Los editores pueden confirmar y silenciar incidentes, pero no pueden modificar miembros, tokens ni configuración. |
| Administra el espacio de trabajo: miembros, roles, tokens, configuración, comprobaciones sintéticas y páginas de estado | **Administrador** | Reserva este rol para un grupo reducido en cada espacio de trabajo. |
| Es responsable de la instancia | **Propietario** | Cada propietario también tiene acceso a la organización `_sys` de la plataforma. Limita este rol a dos o tres personas. |
| Cumple una función que no encaja en ningún rol integrado, como administrar alertas o combinar las tareas de edición con la ejecución de comprobaciones sintéticas | Un [rol personalizado](/es/identity/roles#roles) | Aplica la **Política de permisos** que más se ajuste y luego marca los permisos que falten. |

Asigna un rol a un [equipo](/es/identity/teams#equipos) mediante una
[concesión de acceso](/es/identity/roles#concesiones-de-acceso) en lugar de asignarlo a cada persona. Así, el acceso depende de la pertenencia al
equipo.

## Habilita el acceso mediante el inicio de sesión único

1. Conecta el proveedor de identidad de la empresa en
   [Identidad y acceso → Proveedores de SSO](/es/identity/sso) y asigna sus grupos a roles con
   **Grupo externo → rol**. Así, los roles se ajustan al directorio en cada inicio de sesión.
2. Establece **Lector** como **Rol predeterminado** para quienes no pertenezcan a ningún grupo asociado.
3. Agrega los [dominios de correo electrónico](/es/identity/sso#dominios-de-correo-electrónico) de la empresa para que las invitaciones y el inicio de sesión único
   solo admitan direcciones de esos dominios.
4. Desactiva el [registro de autoservicio](/es/settings/organization#registro-y-acceso) o mantenlo activo con
   **Requerir la aprobación de un administrador**.

El usuario raíz, cuya cuenta se define en `[auth].root_email`, administra la plataforma e inicia sesión con una
contraseña. Guarda esa contraseña en una bóveda y usa la cuenta solo cuando el inicio de sesión único no esté disponible.

## Concede acceso temporal a un solo recurso

Algunas necesidades son específicas y temporales: un contratista que consulta un panel o un analista que consulta un
flujo. En lugar de asignar un rol para todo el espacio de trabajo, crea una [concesión de acceso](/es/identity/roles#concesiones-de-acceso) para ese recurso y define la fecha en
**Vence el**. Una restricción de **Entorno**, como
`staging`, limita aún más la concesión a las solicitudes de ese entorno.

Para dar acceso a miembros de otra organización, usa la opción de
[compartir recursos entre organizaciones](/es/identity/roles#compartir-recursos-entre-organizaciones). El acceso a
los paneles o flujos elegidos se habilita cuando un administrador de esa organización acepta la solicitud. El acceso se limita a
los recursos y la organización seleccionados, y no se puede transferir.

## Asigna la responsabilidad a los equipos

Los equipos son más que grupos de personas: los [horarios de guardia](/es/alerting/on-call) y los pasos de escalamiento,
las [rutas de respaldo](/es/notification-channels#configura-las-rutas-de-respaldo), así como los chats, los
conocimientos, las habilidades y los servidores MCP de equipo de [Mole Agent](/es/agent#recursos-de-la-organización-de-equipo-y-personales),
se vinculan a los equipos. Crea un equipo por cada grupo que se encargue de los servicios y responda a los avisos de guardia, y actualiza
la lista de miembros cuando alguien cambie de equipo.

## Asigna a cada programa su propia identidad

| Programa | Credencial |
|---|---|
| Un recopilador o agente que solo envía datos | El token de ingesta predeterminado, con permiso de solo escritura. |
| Código que se ejecuta en el navegador o en un dispositivo móvil | El token de cliente RUM de la aplicación, visible para los usuarios finales. |
| Un sistema de CI que informa sobre despliegues | El token de ingesta predeterminado, que también permite informar sobre despliegues. |
| Una automatización que lee datos o modifica recursos | Una [cuenta de servicio](/es/identity/tokens#cuentas-de-servicio) con un rol personalizado de alcance limitado. |
| Una persona que ejecuta scripts o usa un cliente MCP | Un token de API personal con fecha de vencimiento. |

Usa una cuenta de servicio por integración. Al retirar una integración, desactiva su cuenta para que todos sus tokens
dejen de funcionar. Define una fecha de vencimiento para cada token que cree una persona y nunca permitas que un
programa use una sesión de usuario.

## Revisa el acceso con regularidad

Cada trimestre y cada vez que alguien deje la organización:

- En [Usuarios](/es/identity/members#usuarios), desactiva las cuentas de quienes se hayan ido y consulta **Última actividad** para
  detectar las cuentas que ya no se usan.
- En [Tokens de API](/es/identity/tokens#tokens-de-la-organización), revoca los tokens que no se hayan usado recientemente o
  que pertenezcan a quienes se hayan ido.
- En [Concesiones de acceso](/es/identity/roles#concesiones-de-acceso), elimina las concesiones vencidas.
- En [Auditoría](/es/settings/data-security#auditoría), revisa los cambios en roles, concesiones, tokens y configuración.
- Revisa la [política de uso compartido](/es/settings/organization#uso-compartido-y-acceso-público) y los enlaces públicos
  existentes.

Configura la [retención de registros de auditoría](/es/settings/platform#retención-de-registros-de-auditoría) según los requisitos de cumplimiento.

## Criterios de aceptación

- La mayoría tiene el rol de **Lector** y cada asignación de **Administrador** o **Propietario** tiene una justificación.
- El inicio de sesión se realiza mediante SSO y los roles corresponden a los grupos del directorio.
- Cada programa usa una cuenta de servicio o un token de ingesta, nunca una sesión de usuario.
- Ningún token de API supera el plazo que establece su política de vencimiento y los tokens sin uso quedan revocados.
- Cada revisión trimestral tiene una fecha, una persona responsable y una entrada en el registro de auditoría.
