MoleSignal APM convierte los spans de traza de OpenTelemetry del backend en agregados RED acotados para encontrar servicios lentos,
endpoints con fallos, dependencias costosas, errores recurrentes del backend y regresiones
entre versiones desplegadas sin instrumentación de métricas por separado. Su catálogo de servicios registra quién
es propietario de cada servicio y su importancia.

<Note>
  APM no requiere otro SDK ni otro flujo de telemetría. Envía trazas bien instrumentadas y
  MoleSignal deriva los datos de APM después de la deduplicación de trazas y antes del muestreo de cola. Una traza que
  más tarde se excluya por muestreo aún puede contribuir a las métricas de APM, y también pueden hacerlo los spans que
  descarta una [canalización en tiempo real](/es/pipelines#trazas).
</Note>

| **Servicios** | El catálogo de servicios: cada servicio que APM ve y cada servicio declarado, con propietario, nivel, etiquetas, alertas en curso, rendimiento, tasa de errores, latencia, versión y último despliegue. Los favoritos aparecen primero y los servicios archivados quedan fuera hasta que se muestran. |

Consulta [el mapa de servicios de APM](/es/apm/service-map#el-mapa-de-servicios-de-apm). |
| **Errores** | Grupos de errores del backend de cada servicio, con estado, equipo y responsable, dónde ocurrieron y las reglas que los agrupan. |
| **SLO** | Objetivos de nivel de servicio con lo que cumplió cada uno durante su ventana, el presupuesto de errores restante, la rapidez con que se consume el presupuesto y el estado. |
| **Configuración** | Las líneas de salud de la organización, el umbral de Apdex predeterminado, las tareas largas, los requisitos del catálogo, las reglas de nomenclatura, la asignación de entornos y los alias, con lo que indican los datos del último día sobre ellos; los límites de cardinalidad de la plataforma y el muestreo de trazas. Un endpoint se abre en un panel lateral con sus códigos de estado, en qué se emplea su tiempo y sus solicitudes más lentas. Una estrella marca las transacciones clave, y la lista puede mostrar solo esas transacciones o solo las tareas largas. |

| **Dependencias** | Los servicios que llaman al servicio y sus llamadas salientes agrupadas por destino, con cada operación bajo el destino, el estado de cada destino, las llamadas que agotaron el tiempo de espera o se reenviaron, y las sentencias SQL más lentas. |
| **Errores** | Los grupos de errores del servicio. |

Consulta [Despliegues](/es/apm/deployments). |

| **Configuración** | La entrada del catálogo del servicio y las transacciones clave junto a lo que informan sus instancias. |

servicio entre los favoritos de quien consulta.

El final de la tarjeta de navegación enlaza los logs, las métricas y los perfiles del servicio. Cada enlace se ilumina cuando
la señal incluye el servicio durante el día anterior al final del intervalo en vista, y MoleSignal vuelve
a comprobar cada cinco minutos:

| Señal | Se ilumina cuando |
|---|---|
| Logs | Un flujo de logs con un campo `service.name`, `service_name` o `service` contiene una línea del servicio. El enlace abre Logs en ese flujo. |
| Métricas | Una serie de la última hora incluye el `service.name` del servicio. |
| Perfiles | El flujo de perfiles contiene un perfil del servicio. |
| RUM | Una sesión de navegador originó una de las trazas de muestra del servicio. El enlace solo se muestra entonces y abre esa sesión. |

Una señal sin datos se atenúa y abre la página **Fuente de datos** que la conecta. Una comprobación que falla
o tarda más de tres segundos deja el enlace sin iluminar ni atenuar.

## Requisitos previos

- Trazas de OpenTelemetry enviadas a un [endpoint de ingesta de trazas](/es/intake) de MoleSignal;
- `apm.services.read` en un espacio de trabajo de la organización; o
- `sys.telemetry.read` para telemetría `_sys` protegida.

## Instrumenta servicios para APM

<Steps>
  <Step title="Configura atributos de recurso estables para el servicio">
    Configura `service.name` en cada servicio. Agrega atributos de espacio de nombres, entorno, versión e instancia
    para filtrar servicios o comparar despliegues.

    ```bash
    export OTEL_SERVICE_NAME=checkout
    export OTEL_RESOURCE_ATTRIBUTES="service.namespace=shop,deployment.environment.name=production,service.version=2.4.0,service.instance.id=checkout-01"
    ```

    La configuración exacta depende del SDK o Collector de OpenTelemetry seleccionado.
  </Step>
  <Step title="Usa los tipos de span correctos">
    Crea spans `SERVER` para solicitudes entrantes y spans `CONSUMER` para mensajes consumidos. Crea
    spans `CLIENT` o `PRODUCER` para llamadas descendentes. MoleSignal usa estos tipos de span para separar
    las transacciones de las dependencias.
  </Step>
  <Step title="Registra el estado y las excepciones">
    Configura el estado del span de OpenTelemetry, los atributos de estado HTTP o RPC y los eventos de excepción. MoleSignal
    usa los datos de estado registrados para clasificar las operaciones exitosas y fallidas y crear grupos de errores de backend.
  </Step>
  <Step title="Envía trazas y abre APM">
    Envía trazas OTLP y luego abre **APM → Servicios**. Mantén el rango de tiempo global en tráfico reciente
    mientras el proyector vacía los primeros buckets.
  </Step>
</Steps>

### Atributos de recurso recomendados

| Atributo | Propósito | Alternativa |
|---|---|---|
| `service.name` | Identidad estable del servicio. Configúrala explícitamente en cada servicio. | `unknown_service` |
| `service.namespace` | Separa servicios con el mismo nombre entre sistemas o equipos. | `default` |
| `deployment.environment.name` | Filtra producción, staging y otros entornos. | `deployment.environment` heredado y, luego, `unknown` |
| `service.version` | Habilita el historial de versiones y la comparación de despliegues. | Sin desglose por versión |
| `service.instance.id` | Distingue las instancias entre sí. | `k8s.pod.name` y, luego, `host.name` |
| `telemetry.sdk.language` | Muestra el lenguaje de ejecución en el catálogo de servicios. | `process.runtime.name` cuando está presente |
| `cloud.region`, `k8s.*`, `host.name`, `container.name`, `container.id` | Indican dónde se ejecuta cada instancia. | No se muestran |
| `process.runtime.name`, `process.runtime.version` | Muestran el runtime de cada instancia. | No se muestran |
| `vcs.repository.url.full`, `vcs.ref.head.revision` | Vinculan el repositorio e indican el commit. `git.repository_url` y `git.commit.sha` también funcionan. | El repositorio de la entrada del catálogo |

Los atributos de Kubernetes y `cloud.region` suelen agregarse con los
procesadores `k8sattributes` y `resourcedetection` del Collector de OpenTelemetry, en lugar de con el SDK.

Usa valores de baja cardinalidad. No incluyas IDs de solicitud, URL sin procesar, IDs de usuario ni otros valores no acotados en
los atributos de servicio, entorno, versión, ruta, operación o dependencia.

## Cómo deriva MoleSignal los datos de APM

### Servicios y endpoints

Los spans `SERVER` y `CONSUMER` aportan métricas RED de servicio y de endpoint. La API denomina transacción a un endpoint. Un span sin padre
sin tipo puede contribuir a los totales del servicio como alternativa de compatibilidad, pero los tipos de span
explícitos producen páginas más completas.

MoleSignal crea nombres de endpoint acotados a partir de atributos semánticos:

- método HTTP más `http.route`, como `POST /checkout`;
- servicio RPC más método;
- operación de mensajería más destino;
- un nombre de span seguro y de baja cardinalidad cuando no existe una identidad semántica más fuerte.

Prefiere plantillas de ruta como `/orders/{id}` en lugar de rutas sin procesar como `/orders/83921`.

### Dependencias

Los spans `CLIENT` y `PRODUCER` aportan métricas RED de dependencias. MoleSignal clasifica los destinos como
servicio, base de datos, caché, sistema de mensajería, endpoint HTTP externo, endpoint RPC externo u otra
dependencia. Los atributos semánticos estándar `peer.service`, `db.*`, `messaging.*`, `rpc.*`, `server.*` y HTTP
mejoran la identidad de la dependencia.

Una llamada a base de datos o caché sin `peer.service` tiene como destino su sistema, como `postgresql` o
`redis`. Cuando se configura [`MS_TRACE_FINGERPRINT_KEY`](/es/configuration#variables-de-entorno), el destino
también lleva una huella con clave de `db.namespace` (o, en su defecto, `db.name` o `db.collection.name`), como
`postgresql:<fingerprint>`, de modo que las bases de datos de un mismo sistema se distingan sin que sus nombres
se almacenen.

La operación de una llamada a una base de datos SQL es su sentencia como plantilla: `db.query.summary` o, en su defecto,
`db.query.text` o `db.statement`, con cada literal reemplazado por `?`, los comentarios eliminados, las listas de valores
reducidas a un solo `?` y un máximo de 512 bytes conservados. El texto entre comillas dobles se conserva solo para las bases de datos en las que
nombra una tabla o una columna, como PostgreSQL y Oracle; para las demás, es un valor. Una llamada
sin sentencia conserva `db.operation.name`, y una llamada a caché, su comando. Un servicio conserva hasta 32
operaciones de un mismo destino por hora; las demás se cuentan juntas como **Otros**, bajo el mismo destino.

Las solicitudes que agotaron el tiempo de espera (un tipo de error de timeout, `DEADLINE_EXCEEDED` de gRPC, HTTP 408 o 504) y
las solicitudes reenviadas (`http.request.resend_count` mayor que 0) se cuentan junto a las métricas RED.

### Errores

MoleSignal clasifica un span como error cuando hay una excepción, el estado de OpenTelemetry es
`ERROR`, el estado HTTP es 500 o superior, o el estado RPC no es cero. Los grupos de errores usan
una huella estable basada en el tipo de error, el primer frame de la pila de la aplicación y el nombre de la transacción.
El mensaje de error cambiante no forma parte de la huella. Las [reglas de agrupación](#agrupa-errores-con-reglas)
pueden combinar errores en un solo grupo o mantenerlos fuera de los grupos.

## Entiende las métricas RED

| Métrica | Significado |
|---|---|
| **Solicitudes** | Número de observaciones coincidentes de servicio, endpoint o dependencia. |
| **Tasa de errores** | Número de errores dividido por el número de solicitudes. |
| **Latencia** | p50, p90, p95 y p99 leídos de histogramas de latencia combinados, y la duración promedio. |
| **Apdex** | Solicitudes dentro del umbral T más la mitad de las solicitudes dentro de 4T, sobre todas las solicitudes. T es el valor predeterminado de la organización, 500 ms, a menos que lo cambie la [configuración de APM](/es/apm/settings#estado-y-umbrales), o el T que establece la entrada del catálogo del servicio; la distribución de latencia indica el T en uso. La vista general calcula todos los servicios juntos con el valor predeterminado de la organización. Una solicitud fallida nunca se considera satisfactoria: las fallas se reparten de manera uniforme entre las latencias. |
| **Tiempo total** | Suma de la duración observada, que resalta el trabajo con el mayor impacto agregado. |

Un servicio está en **advertencia** a partir de una tasa de errores del 2% o un p95 de 500 ms, y en **crítica** a partir del 10% o 2 s,
a menos que la [configuración de APM](/es/apm/settings#estado-y-umbrales) defina otras líneas. La página del servicio y
el punto del catálogo indican qué cifra superó qué línea.

La tarjeta **Análisis** indica qué servicios cambiaron respecto al periodo de la misma duración anterior y
respecto al mismo periodo de hace una semana; consulta [Qué encuentran los análisis](/es/apm/insights#what-insights-find).

Los histogramas de latencia dividen cada duplicación de la latencia en ocho buckets, de 125 µs a unos 131 s, y un
percentil se lee dentro de su bucket. Un percentil está dentro de aproximadamente el 4% del valor exacto. Los agregados
escritos con los buckets fijos anteriores siguen siendo legibles con su menor precisión.

El control **Comparar con** de la vista general y del panel lateral del endpoint dibuja el mismo rango de hace un día o una
semana como una línea discontinua, y la distribución de latencia delinea la dispersión de ese rango. En la
página de un servicio, también enumera los otros entornos del servicio: el mismo rango en ese entorno se
dibuja como línea discontinua en su lugar.

Las solicitudes más lentas de un endpoint provienen del almacén de trazas, por lo que cada solicitud de la lista abre su
traza. Una muestra de error puede apuntar a una traza que el muestreo de cola descartó; el panel lateral de la traza indica entonces
que no se encontró la traza.

## Catálogo de servicios

El catálogo enumera todos los servicios que APM ve, una fila por servicio y entorno, y todos los servicios
declarados antes de que informen. **Declarar un servicio** en el catálogo; la sección **Configuración** de una
página de servicio registra:

| Campo | Significado |
|---|---|
| **Equipo responsable** | Un equipo del espacio de trabajo. El primer horario de guardia habilitado del equipo indica quién está de guardia. |
| **Propietario** | Un miembro del espacio de trabajo responsable del servicio. |
| **Nivel** | P0, los servicios que más importan, hasta P5. |
| **Ciclo de vida** | Producción, staging, experimental u obsoleto. |
| **Repositorio** | Dónde vive el código, que se usa cuando el servicio no informa uno: una dirección https, o una dirección git como `git@github.com:acme/checkout.git` o `ssh://git@git.example.com/team/checkout.git`. Una contraseña en la dirección se conserva como `****`, al igual que la parte del usuario de una dirección https, donde git transporta tokens. La página del servicio abre una dirección git en la página https de la misma ruta. |
| **Etiquetas** | Pares `key=value`, o una clave sola, separados por comas. Una clave tiene hasta 64 letras minúsculas, dígitos y `_ . - /`; un valor tiene hasta 128 caracteres. Como máximo 32. |
| **Umbral de Apdex T** | El umbral del Apdex del servicio en milisegundos, hasta un minuto. Si está vacío, se usa el valor predeterminado de la organización, 500 ms a menos que la configuración de APM lo cambie. |
| **Qué hace** | Una descripción breve que se muestra bajo el nombre del servicio. |
| **También conocido como** | Cómo llaman al servicio los registros, las métricas y otros sistemas, separados por comas, como `order_service` o Order Center. Hasta 20, cada uno de hasta 128 caracteres. Un nombre nunca es el propio del servicio, ni el nombre ni otro nombre de un servicio distinto. La búsqueda del catálogo también encuentra el servicio por estos nombres. |
| **Dónde están los datos** | Los flujos de registros que contienen los registros del servicio, cada uno con una condición SQL opcional que los extrae del flujo; selectores PromQL de sus métricas, como `{service="checkout"}`; paneles que lo muestran; y enlaces a páginas externas, como un runbook o una entrada de CMDB. Hasta 10 de cada uno. Cada fila abre sus datos en **Registros**, **Métricas**, el panel o una pestaña nueva. |

**También conocido como** y **Dónde están los datos** sirven tanto a Mole Agent como a las personas. Cuando se
pregunta a Mole Agent por el servicio, lee la entrada del catálogo con ambos, y una pregunta de APM sobre uno de los
otros nombres lee el servicio al que pertenece el nombre. No fusionan datos: para leer lo que un nombre de servicio antiguo
informaba como el propio servicio, añade un [alias de servicio](/es/apm/settings#alias-de-servicios) en su lugar.

**Archivar** en el mismo formulario saca el servicio de la vista predeterminada del catálogo. Sus datos se siguen
recopilando y su página se sigue abriendo. **Archivado** en el catálogo también muestra los servicios archivados.

[Requisitos del catálogo](/es/apm/settings#requisitos-del-catálogo) exigen un equipo, un propietario o un repositorio
para los servicios a partir de un nivel. Un servicio al que le falta uno muestra **Necesita** con lo que le falta en el
catálogo.

Una definición tiene como clave el espacio de nombres y el nombre, por lo que se mantiene en todos los entornos. El menú **Columnas**
del catálogo y de la tabla de endpoints elige y ordena las columnas, y la disposición se conserva
para cada usuario. Además de las cifras y los campos del catálogo, el catálogo ofrece **Tipo**,
**Lenguaje / framework**, **Instancias** y **Región**, leídos de las instancias del intervalo, y
**Etiquetas** y **Última detección**.

**Correlación**, que se muestra de forma predeterminada, dibuja un punto por cada forma en que el servicio se vincula con el resto de sus datos:
IDs de traza en sus registros, sus atributos de recurso, sus métricas y sus cambios informados. Verde se vincula bien,
amarillo en parte, gris no se vincula y el más tenue no se pudo leer. Al pasar el cursor sobre los puntos se muestran las
cifras que hay detrás. [Calidad de recopilación](/es/apm/settings#calidad-de-la-recolección) enumera lo que hay que corregir.

La estrella de una fila del catálogo mantiene el servicio entre los favoritos del lector, que aparecen primero en el
catálogo; **Favoritos** los muestra solos. Los favoritos se conservan para cada usuario. **Grupo** agrupa las filas por
equipo, espacio de nombres, nivel o el valor de una etiqueta. El catálogo filtra por entorno y equipo, y por
espacio de nombres y etiqueta cuando los servicios tienen más de uno. Los filtros y la agrupación forman parte de la
dirección, por lo que un enlace compartido abre la misma vista. Un servicio visto en el intervalo que no había informado durante un
día al final del intervalo muestra **Inactivos**.

Las transacciones clave son los endpoints que más importan. La estrella de un endpoint en la lista de endpoints o en
su panel lateral lo marca, y **Configuración** enumera las transacciones clave del servicio con lo que atendió cada una en el
intervalo. Un servicio conserva hasta 50.

Los documentos de servicio y los runbooks viven en la base de conocimiento de Mole Agent bajo `services/<service name>/`,
en la base de la organización o en la del equipo responsable. **Documentación** en una página de servicio los enumera y inicia un
runbook. Mole Agent lee los mismos archivos cuando investiga el servicio.

Escribir definiciones y transacciones clave requiere `apm.definitions.manage`, y los estados de error, `apm.errors.manage`. Los propietarios, administradores
y editores lo tienen.

## Instancias

Cada proceso que informa para un servicio es una instancia, que se distingue por `service.instance.id`; si no,
por `k8s.pod.name`; si no, por `host.name`. MoleSignal analiza una instancia una vez por minuto a partir de sus spans y conserva
su versión y los atributos de la tabla anterior, cada uno con el último valor informado. Un enlace de repositorio se
conserva como una dirección https sin usuario, contraseña ni consulta. Lo que atendió cada instancia (solicitudes,
errores y latencia) se cuenta en sus propios buckets, a partir de los mismos spans que las cifras del servicio.

**Entorno de ejecución** enumera las instancias del intervalo y de la versión en vista, las vistas más recientemente primero, con
rendimiento, tasa de errores y p95, y enlaces a los registros de la instancia, por su pod, si no por su host, y a sus
métricas, por la etiqueta que la distingue. Superado el límite de cardinalidad de instancias por servicio y hora,
el resto se cuenta junto como **Otras instancias**, para que las instancias sumen el total del servicio. Al hacer clic
en una instancia, los gráficos del entorno de ejecución se limitan a ella, y la elección forma parte de la dirección. Una instancia que no
se ha visto durante el tiempo que se conservan los agregados por hora se elimina.

## Endpoints en profundidad

El panel lateral del endpoint añade dos tarjetas a los gráficos RED:

- **Códigos de estado** cuenta las respuestas por código: códigos HTTP de `http.response.status_code`
  (`http.status_code` en instrumentación anterior) y códigos gRPC de `rpc.grpc.status_code`, cada uno
  coloreado por clase, con su tendencia. Un bucket conserva hasta 24 códigos; los códigos adicionales se cuentan como
  **Otros HTTP** u **Otros gRPC**. Los agregados escritos antes de que se contaran los códigos de estado no tienen ninguno.
- **En qué se va el tiempo** lee las últimas solicitudes del endpoint en el intervalo del almacén de trazas,
  como máximo 200, y los spans bajo cada una. El tiempo de una llamada se desglosa en lo que llama: una base de datos
  (`db.system.name`), una caché (Redis, Memcached, Valkey), HTTP, RPC o mensajería, y **Otros** para
  una llamada que no dice nada de su destino. Los spans internos cuentan como trabajo interno, y el tiempo que ningún span
  bajo la solicitud cubre es su tiempo propio. Cada parte se muestra con su proporción y su tiempo por
  solicitud. Las llamadas realizadas en paralelo pueden sumar más que la duración de una solicitud; las partes se escalan entonces a
  ella. Solo se leen las trazas que conservó el muestreo de cola.

**Tareas largas** en la lista de endpoints conserva los endpoints cuyo p99 es de 1 segundo o más. Los spans de entrada
de tipo interno, como trabajos programados y workers de cola sin una operación de mensajería, se
listan como **Workers**.

## Despliegues

La sección **Despliegues** de una página de servicio pone los despliegues que informan las canalizaciones junto a las
versiones que llevan los spans del servicio, identifica las reversiones, compara cada versión con la versión
anterior y muestra en paralelo dos versiones que se ejecutan a la vez. Las canalizaciones informan los despliegues con
`POST /api/v1/apm/deployments`. Consulta [Despliegues](/es/apm/deployments).

## Dependencias

Cada destino en la pestaña **Dependencias** de un servicio tiene una puntuación de estado que parte de 100: se restan cuatro puntos por
cada porcentaje de llamadas fallidas (como máximo 60), cuatro por cada porcentaje de llamadas que agotaron el tiempo de espera (como
máximo 20) y, mientras se compara un periodo, medio punto por cada porcentaje que el P95 creció por encima de un quinto
(como máximo 20). A partir de 90, un destino es bueno; a partir de 70, merece una revisión. El título de la puntuación indica qué restó
puntos. Con **Comparar con** configurado, cada destino también indica cómo variaron su tasa de errores y su P95. **Consultas SQL lentas**
enumera las sentencias de base de datos con el P95 más alto, como plantillas.

## Investigar un problema de rendimiento

<Steps>
  <Step title="Encuentra el servicio">

  </Step>
  <Step title="Revisa la descripción general">

    el mismo periodo una semana antes, desde cuándo y los cambios cercanos a ese momento. Consulta
    [Análisis e investigaciones](/es/apm/insights).
  </Step>
  <Step title="Acota la causa">
    Usa **Puntos de conexión** para los puntos de entrada lentos, **Dependencias** para el tiempo en sentido descendente y **Errores** para

  </Step>
  <Step title="Abre la evidencia">

  </Step>
  <Step title="Revisa el despliegue">

  </Step>
  <Step title="Pásalo a Mole Agent">

## Seguimiento de errores de backend

Los grupos de errores están abiertos hasta que se establecen como **En investigación**, **Resuelto** o **Ignorado**. Cada uno puede
asignarse a un equipo y a un miembro del espacio de trabajo. Un grupo resuelto que vuelve a ocurrir se muestra
como **Reaparecido**. **APM → Errores** muestra los grupos sin resolver de forma predeterminada: abiertos, en investigación
y reaparecidos.

Encima de la lista, **Dónde ocurrieron** cuenta las ocurrencias de los grupos listados por versión,
entorno y el lenguaje del servicio; el panel lateral de un grupo de errores cuenta las suyas. **Registros
relacionados** en el panel lateral abre Registros para el servicio y el intervalo, y **Registros** junto a una muestra abre los registros
de la traza de la muestra.

### Agrupa errores con reglas

**Reglas de agrupación** en la lista de errores establecen cómo se agrupan los errores más allá de su tipo, marco y
punto de conexión. Una regla nombra un servicio, o todos los servicios, y patrones para el tipo de error, el mensaje, el
marco donde se produjo el error y el punto de conexión. Cada patrón coincide con el texto completo, sin distinguir mayúsculas y minúsculas,
con `*` para cualquier texto; un patrón vacío coincide con cualquier cosa y una regla necesita al menos uno.

| Acción | Efecto |
|---|---|
| **Combinar en un solo grupo** | Los errores que coinciden con la regla en un servicio se convierten en un solo grupo con el nombre de la regla. |
| **Dejar fuera de los grupos** | Los errores que coinciden con la regla no forman ningún grupo. Sus solicitudes siguen contando como fallidas en las métricas RED. |

Las reglas se prueban en orden y prevalece la primera que coincida; mueve una regla hacia arriba o hacia abajo para cambiar el
orden. Una regla se aplica a los errores vistos después de guardarse, en cada nodo en menos de medio minuto, y
deja los grupos ya creados tal como están. Mientras se edita una regla, el formulario indica cuántos grupos de la lista
coinciden con ella. **Crear regla a partir de este error** en el panel lateral de un grupo de errores inicia una
regla con el tipo y el servicio del grupo.

## Objetivos de nivel de servicio

Un objetivo de nivel de servicio (SLO) promete una proporción de solicitudes correctas durante una ventana móvil de 7, 28 o
30 días. Cubre un servicio en un entorno, o un punto de conexión de este. Abre **APM → SLO** y haz clic
en **Nuevo SLO**, o haz clic en **Nuevo SLO** en la tarjeta **Objetivos de nivel de servicio** de la descripción general de un servicio.

| Campo | Significado |
|---|---|
| **Servicio** y **Entorno** | El servicio que cubre el objetivo, en un entorno. |
| **Punto de conexión** | Un punto de conexión del servicio. Déjalo vacío para todo el servicio. |
| **Criterio de éxito** | **La solicitud se completa correctamente**: una solicitud es correcta cuando no falló. **La solicitud se completa correctamente dentro del límite de tiempo**: una solicitud es correcta cuando no falló y no tardó más que el **Umbral de latencia (ms)**. |
| **Objetivo (%)** | La proporción de solicitudes correctas prometida, mayor que 0 y menor que 100, como `99.9`. |
| **Ventana** | 7, 28 o 30 días, que termina ahora. |

Un SLO usa los agregados de APM de su servicio, por lo que cuenta cada solicitud antes del muestreo de cola.

| Valor | Significado |
|---|---|
| **Cumplimiento** | Solicitudes correctas sobre todas las solicitudes de la ventana. |
| **Presupuesto de error restante** | `1 - (1 - met) / (1 - objective)`. El presupuesto es la proporción de solicitudes que el objetivo permite que sean incorrectas. La cifra cae por debajo de cero una vez que se incumple el objetivo. |
| **Tasa de consumo** | `(1 - met) / (1 - objective)` durante la última hora, seis horas y 24 horas. Con `1×`, el presupuesto dura exactamente la ventana. |
| **Cumplimiento diario** | Cada día UTC de la ventana, marcado como cumplido, incumplido o sin solicitudes. |

| Estado | Significado |
|---|---|
| **Incumplido** | El **Cumplimiento** está por debajo del objetivo. |
| **En riesgo** | Queda menos del 25 % del presupuesto, la tasa de consumo supera 14,4 durante la última hora o supera 6 durante las últimas seis horas. |
| **Operativo** | Ninguna de las anteriores. |
| **Sin datos** | La ventana no tiene solicitudes. |

Un objetivo de latencia lee los histogramas de latencia, por lo que el recuento de solicitudes dentro del umbral es
tan preciso como un percentil, con un margen de alrededor del 4 %. La ventana usa agregados por hora y las tasas de consumo usan
agregados por minuto. Una ventana más larga que la retención de los agregados por hora cuenta solo los días
retenidos.

### Alertas de tasa de consumo

**Crear alertas de tasa de consumo** en el panel lateral de un SLO agrega las dos reglas de alerta recomendadas por el
manual de SRE de Google. Ambas son reglas de alerta de APM sobre el objetivo y notifican mediante la política de escalado de la regla.

| Regla | Ventana | Se activa cuando | Gravedad |
|---|---|---|---|
| Consumo rápido | 1 hora, y sus últimos 5 minutos | La tasa de consumo supera 14,4 en ambas ventanas | Crítica |
| Consumo lento | 6 horas, y sus últimos 30 minutos | La tasa de consumo supera 6 en ambas ventanas | Advertencia |

La ventana corta evita que una regla se active ante un pico que ya pasó. Una vez que una regla vigila el
SLO, el panel lateral la muestra en lugar del botón. Para crear las reglas se requiere `alerts.rules.manage`.

Escribir SLO requiere `apm.slos.manage`, y eliminar uno, `apm.slos.delete`. Eliminar un SLO elimina primero sus alertas de tasa de consumo, lo que también
requiere `alerts.rules.manage`.

## Alertar sobre métricas de APM

Una regla de alerta de APM vigila una métrica de un servicio o de uno de sus puntos de conexión, leída de los mismos
agregados que las páginas de APM, por lo que no necesita ninguna consulta.

<Steps>
  <Step title="Abrir el editor de reglas">
    Abre **Nueva alerta** en el encabezado de una página de servicio o del panel lateral de un punto de conexión y elige **Alerta de
    umbral**. El editor se abre en el origen **Alerta de APM** con el servicio, el entorno y el punto de conexión completados. Una regla nueva en
    **Alertas → Reglas de alerta** ofrece el mismo origen que **Alerta de APM**. Crear una regla requiere
    `alerts.rules.manage`.
  </Step>
  <Step title="Elegir la métrica">
    Elige **Servicio**, **Entorno** o **Todos los entornos**, **Punto de conexión** o **Servicio completo**,
    y **Métrica**. Define los umbrales en la unidad que el editor indica bajo la métrica.
  </Step>
  <Step title="Probar y guardar">
    Haz clic en **Probar regla** para trazar la métrica de las últimas seis horas frente a los umbrales y, después,
    crear la regla.
  </Step>
</Steps>

| Métrica | Unidad |
|---|---|
| **Tasa de errores** | Porcentaje, de 0 a 100 |
| **Latencia P50**, **Latencia P90**, **Latencia P95**, **Latencia P99**, **Duración promedio** | Milisegundos |
| **Tasa de solicitudes** | Solicitudes por segundo |
| **Solicitudes**, **Errores** | Un recuento durante la ventana de la regla |
| **Nuevos grupos de errores** | Grupos de errores del servicio, o del punto de conexión, detectados por primera vez en la ventana de la regla |
| **Apdex** | De 0 a 1 |
| **Tasa de consumo del SLO** | Veces más rápido de lo que permite el objetivo. Se define desde un SLO. |

Cada evaluación lee la ventana de la regla: agregados por minuto para ventanas de hasta 24 horas y agregados por hora
para una ventana más larga. Una ventana sin solicitudes devuelve `0` para **Solicitudes**, **Errores**, **Nuevos grupos de errores**,
y **Tasa de solicitudes**, por lo que una regla puede detectar tráfico que se detuvo. Las demás métricas no tienen valor en ese caso, ningún
umbral coincide y un incidente abierto se resuelve.

Una regla creada en el editor o a partir de un SLO lleva las etiquetas `service.name`, `service.namespace`,
`deployment.environment` y `apm.endpoint` para aquello que nombra, y sus incidentes las copian. Los
incidentes de cada regla de APM también llevan la etiqueta `service`, el servicio en `affected_services` y un
ID de traza de muestra de los agregados. La columna **Alertas** del catálogo, el encabezado del servicio y el panel lateral del punto de conexión cuentan los incidentes abiertos y
reconocidos que nombran el servicio, en su entorno cuando un incidente nombra uno. El
panel lateral del punto de conexión cuenta solo los incidentes etiquetados con su punto de conexión. Un recuento abre **Alertas →
Incidentes**.

**Alerta de anomalía** en el mismo menú alerta cuando una métrica se desvía de la misma hora de los días anteriores,
sin necesidad de definir un umbral. Consulta
[Alertar sobre anomalías de las métricas de APM](/es/apm/insights#alertar-sobre-anomalías-de-métricas-de-apm).

## Filtros, resolución y retención

Las páginas de APM comparten el intervalo de tiempo global. El catálogo filtra por entorno y equipo, y una página
de servicio por entorno y versión. Las listas admiten búsqueda y ordenación. El alcance se codifica en la URL para
compartir o volver a visitar la vista.

Con la configuración de implementación predeterminada:

- si no se especifica un intervalo de API, se usan las últimas 24 horas;
- la resolución `auto` usa intervalos de un minuto para rangos de hasta 24 horas y de una hora para rangos
más largos;
- los agregados por minuto se conservan durante 24 horas;
- los agregados por hora y el intervalo máximo de consulta abarcan 30 días.

Los administradores pueden cambiar estos límites de implementación. Una comparación de versiones se marca como suficiente solo
después de que ambos lados alcancen el umbral de solicitudes configurado, que por defecto es de 1000 solicitudes en cada lado.

## Leer avisos de calidad de datos

Cada respuesta de APM incluye metadatos de calidad de datos. Cuando hay algo que indicar, un aviso breve
aparece en la tarjeta de navegación y abre sus detalles.

| Aviso | Significado |
|---|---|
| **Los datos empiezan en este intervalo** | La proyección de APM comenzó dentro del intervalo seleccionado, por lo que el tráfico anterior no está representado. |
| **Datos parciales** | Una interrupción en una cola, un repositorio, un vaciado, datos tardíos, la cardinalidad o un apagado afectó a parte del intervalo. No interpretes los datos faltantes como cero. |
| **Datos con retraso** | `lastCompleteBucketAt` está por detrás del intervalo seleccionado. Es posible que los agregados recientes aún se estén cerrando o consolidando. |
| **Algunos nombres se agrupan en «Otros»** | Se alcanzó un límite de cardinalidad. Los nombres que superan el límite se cuentan juntos en una fila llamada **Otros**. Los límites están en la [configuración de APM](/es/apm/settings#límites-de-cardinalidad). |

Reduce primero el intervalo de tiempo y los filtros. Si los estados parciales o con retraso persisten, inspecciona el
punto de conexión de estado de APM y las [métricas de proyección de APM](/es/self-observability#proyección-de-apm).

## Privacidad y datos acotados

APM almacena agregados y una pequeña cantidad de evidencia saneada. APM no conserva cuerpos de solicitud ni de
respuesta, valores de consulta de URL, encabezados ni parámetros SQL en los agregados de APM; una sentencia SQL se
conserva solo como su plantilla, con cada literal como `?`.
Los valores de identidad, los mensajes representativos y los marcos de pila tienen una longitud limitada. Los valores
que parecen sensibles y los volátiles se eliminan o se enmascaran antes de persistirlos.

Estas protecciones no sustituyen una buena higiene de instrumentación. Evita incluir secretos o datos personales en
nombres de span, descripciones de estado, mensajes de excepción o atributos de recursos.

## Solución de problemas

| Síntoma | Comprobación |
|---|---|
| Sin datos de APM | Confirma que las trazas llegan al mismo espacio de trabajo, que el intervalo de tiempo incluye tráfico reciente y que el rol activo tiene `apm.services.read`. |
| `unknown_service` | Define un atributo de recurso `service.name` estable antes de exportar los spans. |
| Faltan endpoints | Añade tipos de span `SERVER` o `CONSUMER` y atributos estándar de HTTP, RPC o mensajería. |
| Faltan dependencias | Añade spans `CLIENT` o `PRODUCER` alrededor de las llamadas posteriores e incluye atributos semánticos de destino. |
| Faltan versiones | Define `service.version` de forma coherente en cada instancia del despliegue. |
| Faltan errores | Registra eventos de excepción y define el estado de span, HTTP o RPC según las convenciones de OpenTelemetry. |
| No se encuentra la traza de una muestra de error | La traza se descartó por muestreo o caducó, mientras que el agregado de APM previo al muestreo sigue siendo válido. |
| Sin gráficos de runtime | Envía métricas de runtime de OpenTelemetry con el mismo `service.name`. |
| Resultados parciales o desactualizados | Revisa el aviso de calidad de datos y `GET /api/v1/apm/health`. |
| Una alerta de APM nunca se activa en un servicio que se detuvo | La tasa de errores, la latencia y Apdex no tienen valor sin solicitudes. Vigila **Solicitudes** o **Tasa de solicitudes** para detectar tráfico que se detiene. |
| Un SLO muestra **Sin datos** | Comprueba que el servicio reporte en el entorno del SLO y que el nombre del endpoint coincida con la lista **Endpoints**. |
