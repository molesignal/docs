**RUM → Errores** muestra los errores de una aplicación agrupados por problema. Cada problema reúne errores similares.
Cada problema tiene un estado, un equipo, un responsable y un registro de cuándo y en qué versiones se detectó. Cada error permanece en el
flujo `rum_errors` con el ID de su problema en `error.issue_id`, de modo que tanto el [explorador](/es/rum/explorer) como las consultas pueden acceder al error y a su ID.

## Cómo se agrupan los errores en problemas

El servidor determina a qué problema pertenece cada error cuando lo recibe. El ID es un hash de:

- la aplicación y `error.source`,
- el tipo, la categoría y el mensaje del error sin los fragmentos que varían de un error a otro,
- los tres primeros marcos de pila del código propio de la aplicación, que el servidor resuelve con el mapa de código fuente, el archivo de mapeo o el archivo de símbolos de la versión si se ha cargado alguno (consulta [Mapas de código fuente y símbolos](/es/rum/source-maps)),
- en las solicitudes fallidas, el método, la ruta y el código de estado.

El servidor quita del mensaje los números, los UUID, los hashes de ocho o más dígitos hexadecimales, las direcciones de correo electrónico y la cadena de consulta o el fragmento de una
dirección web. Así, `Loading chunk 482 failed.` y `Loading chunk 17 failed.` se agrupan en un solo problema. Los marcos de pila de un
paquete, un framework o el entorno de ejecución no forman parte del código propio de la aplicación y no cuentan mientras haya marcos
propios.

Envía `error.fingerprint` (hasta 128 caracteres) para agrupar los errores de otra manera. Los errores de una misma aplicación que tienen la misma
huella digital se agrupan en un solo problema, sin importar sus mensajes ni sus trazas de pila. Los SDK no asignan este valor. Pásalo en la llamada que notifica el
error.

<Note>
  Las reglas que generan el ID tienen su propia versión. Si cambia la forma de agrupar los errores, el servidor genera nuevos ID en lugar de
  reagrupar los problemas existentes. Los errores que llegaron antes de que el servidor empezara a registrar problemas no tienen `error.issue_id` y no
  aparecen en la lista. Si un error llega antes de que se cargue el mapa de código fuente de su versión, el servidor lo agrupa por sus marcos originales. Si
  llega después, lo agrupa por sus marcos restaurados. Una misma falla puede aparecer como dos problemas. El servidor no combina problemas existentes.
</Note>

## La lista

La lista muestra los problemas con errores en el intervalo de tiempo seleccionado para una aplicación y un entorno. Cada fila muestra:

| Columna | Qué muestra |
|---|---|
| **Problema** | El tipo y el mensaje del primer error, y el primer marco de pila del código propio de la aplicación. |
| **Estado** | En qué etapa se encuentra el problema. Consulta [Estados](#estados). |
| **Responsable** | La persona asignada o, si no hay ninguna, el equipo. |
| **Sesiones** | El número de sesiones en las que ocurrió el problema durante el intervalo de tiempo. |
| **Usuarios** | El número de personas afectadas. Si una visita no tiene ID de usuario, la lista usa el ID anónimo del SDK para contarla. |
| **Tendencia** | Cuántas veces ocurrió el problema en cada uno de los 12 segmentos iguales del intervalo de tiempo. |
| **Versiones** | La primera y la última versión en las que se detectó el problema. |
| **Última detección** | La última vez que se detectó el problema, sin limitarse al intervalo seleccionado. |

De forma predeterminada, la lista muestra los problemas **Sin resolver**: abiertos, en investigación o reaparecidos. Elige otro estado o
**Todos los problemas** en el filtro. Filtra la lista por palabras del tipo, el mensaje o la ubicación del error, o por el responsable del problema. Si
más de un tipo de cliente envió errores, también puedes filtrar por origen. Haz clic en **Estado**, **Sesiones**, **Usuarios** o **Última detección** para ordenar las filas.
Haz clic de nuevo para invertir el orden. La URL conserva el estado de la página, así que puedes compartir la vista.

La lista carga los 250 problemas con más sesiones, usuarios u ocurrencias, según el criterio de orden seleccionado, y luego aplica
los filtros. Los filtros no incluyen problemas fuera de esos 250. La lista muestra hasta 100 problemas.

**Dónde ocurre**, encima de la lista, desglosa las sesiones de los problemas de la lista por versión, página y
navegador. Haz clic en un valor para mostrar solo los errores asociados a ese valor. El filtro se aplica a todas las columnas. Vuelve a hacer clic en el
valor para quitar el filtro.

## El problema

Haz clic en una fila para abrir el problema en un panel lateral. La URL incluye el problema, así que puedes volver a abrir el panel desde esa misma URL.

- En el encabezado, cambia el estado, el equipo y el responsable. **Ver en el explorador** abre el explorador con los errores del problema.
- La línea de resumen muestra el estado, las sesiones y las personas afectadas en el intervalo de tiempo, cuándo se detectó el problema por primera y última vez,
  y las versiones en las que se detectó.
- **Evolución en el tiempo** muestra las sesiones de los últimos 14 días, agrupadas por día y apiladas por versión. Una línea discontinua marca el día en que se
  resolvió el problema.
- **Dónde ocurre** desglosa las sesiones de este problema por navegador, sistema operativo y país.
- **Dónde se produjo el error** muestra los marcos de pila del error más reciente que tiene una traza de pila: los marcos propios de la aplicación aparecen en negrita;
  los de las bibliotecas, atenuados. Si un artefacto de depuración permitió restaurar los marcos, alterna entre **Restaurados** y **Originales**.
- **Sesiones recientes** muestra las últimas tres sesiones en las que ocurrió el problema, con acceso a la reproducción y a la cronología de cada una.
  **Personas afectadas** muestra quiénes experimentaron el problema con mayor frecuencia. Si el sistema no conservó la sesión, solo guarda el error y muestra
  *Sesión no conservada* en lugar del acceso a la sesión. Consulta [Muestreo de datos de RUM](/es/rum/sampling#conservar-todos-los-errores).

El tipo, el mensaje y la ubicación que aparecen en la lista quedan tal como estaban al llegar el primer error del problema, después de aplicar las
reglas de enmascaramiento al guardar los datos.

## Estados

| Estado | Significado | Quién lo establece |
|---|---|---|
| **Abrir** | Nadie ha revisado el problema. Los problemas nuevos comienzan en este estado. | El servidor o una persona. |
| **En investigación** | Hay una investigación en curso. | Una persona. |
| **Reaparecido** | El problema se resolvió y volvió a ocurrir en una versión más reciente. | Solo el servidor. |
| **Resuelto** | Ya se corrigió la causa. | Una persona. |
| **Ignorado** | No requiere atención. | Una persona. |

Los problemas abiertos, en investigación y reaparecidos se consideran sin resolver.

### Regresión

Al resolver un problema, el servidor registra el momento, quién lo resolvió y la versión más reciente que tenía la aplicación en ese momento. El servidor ordena las versiones por
el momento en que detectó cada una por primera vez, sin importar su nombre. Si llega otro error de un problema resuelto, el servidor lo reabre como **Reaparecido** solo cuando el
error ocurre en una versión que el servidor detectó por primera vez después de la versión registrada. Quienes no actualizaron siguen usando la versión anterior y
un error en la misma versión o en una anterior nunca reabre el problema.

Si la aplicación no envía datos de versión, el servidor no puede ordenar las versiones. Cualquier error posterior a la resolución reabre el problema. Un error que
no indica la versión no reabre un problema que se resolvió con una versión registrada.

Cambiar el estado de un problema reaparecido pone fin a la regresión. Al resolverlo de nuevo, el servidor vuelve a registrar la versión más reciente.

Cada problema pertenece a toda la aplicación y abarca todos los entornos. El servidor guarda el entorno del error que reabrió el problema y
el momento en que detectó el problema por primera vez en cada entorno. Las [reglas de alerta](/es/rum/alerts) usan estos datos para contar los problemas nuevos y reaparecidos
de un entorno.

El componente del servidor que recibe los errores conserva el estado de un problema en caché durante un máximo de un minuto. Los cambios de estado manuales llegan a ese componente en ese plazo. Si llega un error de una versión más reciente mientras el componente conserva el estado anterior, el problema no se reabre. Se reabre con el siguiente error que cumpla los criterios una vez transcurrido el minuto.

## Problemas nuevos por hora

Cada aplicación puede abrir por hora como máximo la cantidad indicada en **Problemas nuevos por hora** (100 de forma predeterminada). Una vez alcanzado ese límite, el servidor agrupa durante el resto de
la hora los errores que aún no pertenecen a ningún problema en un solo problema llamado **Otros errores**. Así, una aplicación cuyos
mensajes nunca se repiten no puede llenar la lista. Para cambiar el límite, ve a **RUM → Aplicaciones** y elige un valor
entre 1 y 10 000 en la sección **Problemas**. El cambio se aplica en un máximo de 30 segundos.

## Permisos

- `rum.issues.read` permite abrir la lista y el problema.
- `rum.issues.manage` permite cambiar el estado y asignar el problema a un equipo y a una persona. Los roles de propietario, administrador y editor incluyen este permiso. Sin él, los controles solo
  muestran los valores establecidos.

Los endpoints están en la [API de RUM](/es/api/rum#problemas).
