MoleSignal lee un archivo TOML y las variables de entorno con el prefijo `MS_`. Usa como punto de partida el archivo de ejemplo `conf/config.toml` que se incluye en cada versión. El ejemplo enumera todos los parámetros y esta página documenta cada uno.

```bash
molesignal --config /etc/molesignal/config.toml
```

## Cómo se carga la configuración

MoleSignal aplica la configuración en este orden. Cada fuente reemplaza los valores de las anteriores.

1. Valores predeterminados integrados.
2. El archivo TOML que especifiques con `--config`.
3. Variables de entorno con el prefijo `MS_`.

Reinicia el proceso después de cambiar un parámetro. Mientras está en ejecución, el proceso registra los cambios en el archivo, pero no los aplica.

<Note>
  La mayoría de las secciones ignoran las claves que no definen. Por eso, un error tipográfico no tiene efecto ni genera una advertencia. Las secciones `[meta_database]`, `[object_store]` (incluida `[object_store.retry]`), `[telemetry]` (incluidas `[telemetry.trace]` y `[telemetry.self_collect]`), `[apm]`, `[probe]`, `[otlp_grpc]`, `[notify]` y `[scheduled_reports.renderer]` rechazan las claves desconocidas. En esas secciones, un error tipográfico impide que el proceso se inicie.
</Note>

La columna **Predeterminado** de las tablas de referencia muestra el valor del archivo de ejemplo `conf/config.toml`. Si el valor integrado que se usa cuando falta una clave es distinto, la descripción lo indica.

## Variables de entorno

Cada parámetro tiene una variable de entorno. Escribe el prefijo `MS_` seguido de cada nivel de la ruta del parámetro en mayúsculas. Separa los niveles con un solo guion bajo.

| Parámetro | Variable de entorno |
|---|---|
| `[http].port` | `MS_HTTP_PORT` |
| `[meta_database].dsn` | `MS_META_DATABASE_DSN` |
| `[cluster].advertise_addr` | `MS_CLUSTER_ADVERTISE_ADDR` |
| `[node].roles` | `MS_NODE_ROLES` |

Escribe las listas con sintaxis TOML, por ejemplo, `MS_NODE_ROLES='["intake","querier"]'`. MoleSignal no reconoce los nombres que contienen un punto o dos guiones bajos consecutivos.

MoleSignal lee estas variables por separado de los parámetros:

| Variable | Propósito |
|---|---|
| `MS_CIPHER_KEY` | Clave raíz de los secretos que MoleSignal cifra en PostgreSQL. Proporciona 32 bytes aleatorios codificados en base64. Si no la defines, el proceso usa una clave de desarrollo compuesta solo por ceros y registra una advertencia. Nunca cambies la clave sin ejecutar `rewrap-kek`. Consulta la [lista de verificación para producción](/es/deployment/production-checklist). |
| `MS_AUTH_JWT_SECRET_OVERRIDE` | Fija el secreto de firma de JWT en lugar de usar el que MoleSignal genera en PostgreSQL durante el primer inicio. |
| `MS_SELF_TELEMETRY_CLUSTER_TOKEN` | Secreto compartido que autentica las trazas candidatas y la telemetría interna que los nodos con roles separados se reenvían entre sí. Define el mismo valor en todos los nodos con roles separados si está habilitada la [captura de trazas](#captura-de-trazas-y-muestreo-al-final) (habilitada de forma predeterminada) o si está habilitado `[telemetry.self_collect]`. Los nodos sin el rol `intake` no se inician sin este secreto. |
| `MS_TRACE_FINGERPRINT_KEY` | Clave de las huellas HMAC-SHA-256 que sustituyen a valores que MoleSignal nunca almacena: la estructura de las sentencias SQL y las claves de objeto en los [spans del propio MoleSignal](/es/self-observability#rastreo-distribuido-del-backend), y los nombres de las bases de datos en las [dependencias de APM](/es/apm#dependencias). Usa al menos 16 bytes. MoleSignal ignora los valores más cortos. Define el mismo valor en todos los nodos, ya que las claves distintas generan huellas distintas. Sin la clave, MoleSignal no guarda ninguna huella ni la sustituye por un hash sin clave. MoleSignal solo lee la clave del entorno y nunca la incluye en las respuestas de la API, los registros ni los spans. |
| `MS_AGENT_OPENAI_API_KEY`, `MS_AGENT_ANTHROPIC_API_KEY`, `MS_AGENT_COMPATIBLE_API_KEY` | Claves de API de respaldo para los proveedores de modelos de Mole Agent en entornos de desarrollo. Cada una tiene una variable `_BASE_URL` correspondiente. Para producción, configura los proveedores en el producto. |
| `RELEASE_CHANNEL` | Indica el nivel de madurez de la implementación: `alpha`, `beta`, `rc` o `stable`. |
| `RUST_LOG` | Reemplaza `[telemetry].log_level` si defines esta variable. |
| `AZURE_STORAGE_ACCOUNT`, `AZURE_STORAGE_ACCESS_KEY` | Credenciales de Azure Blob para el backend de almacenamiento de objetos `azure`. |
| `GOOGLE_APPLICATION_CREDENTIALS` | Ruta al archivo JSON de la cuenta de servicio para el backend de almacenamiento de objetos `gcs`. |

## Configuración mínima para producción

Un nodo de producción necesita, como mínimo, estos parámetros. Conserva los valores predeterminados en el resto del archivo.

```toml
[http]
external_url = "https://molesignal.example.com"

[meta_database]
dsn = "postgres://molesignal:<password>@db.internal:5432/molesignal"

[object_store]
backend = "s3"
bucket = "molesignal"
region = "us-east-1"
endpoint = ""          # empty for AWS S3, the service URL for S3-compatible storage
access_key = ""        # prefer MS_OBJECT_STORE_ACCESS_KEY
secret_key = ""        # prefer MS_OBJECT_STORE_SECRET_KEY

[wal]
dir = "/var/lib/molesignal/wal"

[auth]
root_email = "admin@example.com"
root_password = "<initial password>"
```

Define también `MS_CIPHER_KEY` en el entorno. Consulta la [lista de verificación para producción](/es/deployment/production-checklist) para ver todos los pasos antes de poner el nodo en producción.

## Nodo

`[node]` determina qué roles ejecuta un proceso. Consulta la [implementación basada en roles](/es/deployment/role-based).

| Clave | Predeterminado | Descripción |
|---|---|---|
| `roles` | `["standalone"]` | Roles que se pueden ejecutar: `standalone`, `router`, `intake`, `querier`, `compactor`, `alert`. `standalone` ejecuta todos los roles en un solo proceso. |
| `id` | vacío | ID del nodo, de hasta 64 caracteres. Si dejas el valor vacío, MoleSignal usa el nombre de host del sistema operativo. Define un ID distinto para cada proceso si ejecutas varios en el mismo host. |
| `drain_timeout_secs` | `30` | Tiempo de espera para que se escriban los datos de ingesta pendientes después de recibir `SIGTERM` o `SIGINT`. Cuando se agota el tiempo, el proceso termina y otro nodo de ingesta se encarga de los datos que quedaron pendientes. |

## Servicios de escucha

### HTTP

| Clave | Valor predeterminado | Descripción |
|---|---|---|
| `bind` | `0.0.0.0` | Dirección de escucha. |
| `port` | `5080` | Puerto HTTP cuando `[http.tls]` está desactivado. |
| `gzip` | `true` | Comprime con gzip los archivos de la interfaz web que sirve el proceso para los clientes que aceptan esa compresión. Las respuestas de la API se envían sin comprimir. Usa `false` si un proxy inverso se encarga de la compresión. |
| `external_url` | vacío | Origen público, por ejemplo, `https://molesignal.example.com`. Si está vacío, la interfaz web usa el origen del navegador. Los fragmentos de código generados para la configuración inicial usan este valor, y los dominios personalizados de las páginas de estado lo usan como destino del CNAME. Los enlaces de cuenta y de chat de Mole Agent en la mensajería instantánea usan este origen. La dirección de devolución de llamada de Microsoft Teams también se basa en este origen, que debe usar HTTPS; consulta [Mole Agent en la mensajería instantánea](/es/im#seguridad-en-teams). Las [claves de acceso](/es/identity/mfa#requisitos-de-la-instancia) se vinculan al nombre de host del origen y requieren un nombre de dominio accesible mediante HTTPS. Reinicia el proceso después de cambiar este valor. |

### TLS para HTTP y ACME

`[http.tls]` inicia un servicio de escucha TLS que obtiene certificados automáticamente de un servicio ACME como Let's Encrypt.

| Clave | Valor predeterminado | Descripción |
|---|---|---|
| `enabled` | `false` | Interruptor principal. Si el valor es `false`, el servicio ignora todas las demás claves. |
| `plain_port` | `80` | Puerto HTTP sin cifrar para los desafíos ACME HTTP-01 y la redirección a HTTPS. |
| `port` | `443` | Puerto HTTPS. |
| `acme_directory` | `production` | `production`, `staging` (entorno de pruebas de Let's Encrypt) o una URL de directorio personalizada. |
| `account_email` | vacío | Correo electrónico de la cuenta de ACME. Let's Encrypt lo requiere. |
| `key_storage_dir` | `/var/lib/molesignal/acme` | Directorio de la clave de la cuenta de ACME y de las claves de cada dominio. |
| `issue_poll_secs` | `60` | Intervalo entre revisiones de los dominios pendientes de un certificado. |
| `renewal_retry_secs` | `21600` | Intervalo entre reintentos de renovación y comprobaciones de vencimiento. |

### gRPC interno

`[grpc]` transporta el tráfico entre nodos. Mantén el puerto en una red de confianza.

| Clave | Valor predeterminado | Descripción |
|---|---|---|
| `bind` | `0.0.0.0` | Dirección de escucha. |
| `port` | `5082` | Puerto. Los otros nodos también lo usan mediante `[cluster].advertise_addr`. |
| `max_message_size` | `32` | Tamaño máximo de los mensajes gRPC en MiB. |

### OTLP gRPC

`[otlp_grpc]` configura el receptor OTLP gRPC. El receptor no tiene un interruptor de activación y escucha en todos los nodos con el rol `intake`, incluidos los nodos `standalone`.

| Clave | Valor predeterminado | Descripción |
|---|---|---|
| `bind` | `0.0.0.0` | Dirección de escucha. |
| `port` | `4317` | Puerto. |
| `max_message_size` | `32` | Tamaño máximo de los mensajes gRPC en MiB. |

### Arrow Flight SQL

`[flight_sql]` atiende a clientes SQL como DBeaver, JDBC y ADBC. Cada llamada requiere un token de API. Consulta [Clientes de bases de datos](/es/query/database-clients).

| Clave | Valor predeterminado | Descripción |
|---|---|---|
| `enabled` | `false` | Inicia el servicio de escucha. |
| `bind` | `0.0.0.0` | Dirección de escucha. |
| `port` | `5083` | Puerto. |
| `default_lookback_hours` | `24` | Ventana retrospectiva en horas para las consultas SQL sin filtro de tiempo. |
| `max_message_size` | `32` | Tamaño máximo de los mensajes en MiB. |

### Probe Agent

`[probe]` configura los puntos de conexión de registro y control de los agentes Probe Agent. Los puntos de conexión se activan en los nodos `standalone` y `alert`. El registro usa TLS con autenticación del servidor y el flujo de control usa identidades de corta duración con TLS mutuo. Consulta [Monitoreo sintético](/es/synthetics).

| Clave | Valor predeterminado | Descripción |
|---|---|---|
| `bind` | `0.0.0.0` | Dirección de escucha. |
| `register_port` | `5084` | Puerto de registro. Debe ser distinto de `control_port`. |
| `control_port` | `5085` | Puerto del flujo de control. |
| `register_endpoint` | `https://localhost:5084` | URL pública `https://` que usan los agentes para registrarse. El comando de registro de un solo uso muestra esta URL. Configúrala si el servicio está detrás de un proxy o un balanceador de carga. |
| `control_endpoint` | `https://localhost:5085` | URL pública `https://` del flujo de control. |
| `server_names` | `["localhost", "127.0.0.1"]` | Nombres DNS y direcciones IP del certificado del servidor. Incluye los nombres de host públicos de los puntos de conexión. |
| `certificate_days` | `30` | Vigencia de los certificados emitidos, de 1 a 365 días. |
| `max_message_size` | `32` | Tamaño máximo de los mensajes en MiB. |

### pprof

`[profiling]` inicia un servicio de escucha de pprof local al nodo para diagnósticos.

| Clave | Valor predeterminado | Descripción |
|---|---|---|
| `enabled` | `false` | Inicia el servicio de escucha. |
| `bind` | `127.0.0.1` | Dirección de escucha. Debe ser una dirección de bucle invertido, a menos que `allow_remote` sea `true`. |
| `port` | `5086` | Puerto. Debe ser distinto de los puertos de los demás servicios de escucha habilitados, incluidos los de los roles que el nodo no ejecuta. |
| `allow_remote` | `false` | Permite que `bind` use una dirección que no sea de bucle invertido. El acceso remoto puede exponer información sobre la ejecución del proceso. |

## Almacenamiento

### Base de datos de metadatos

`[meta_database]` configura la base de datos PostgreSQL que almacena los metadatos, las identidades, el catálogo de archivos y los recursos del producto.

| Clave | Valor predeterminado | Descripción |
|---|---|---|
| `dsn` | `postgres://molesignal:molesignal@localhost:5432/molesignal` | Cadena de conexión de PostgreSQL. Reemplaza las credenciales de ejemplo. |
| `min_connections` | `2` | Conexiones que abre al iniciar. No supera `max_connections`. |
| `max_connections` | `16` | Límite del grupo de conexiones. |

Al iniciar, MoleSignal aplica a la base de datos las migraciones de esquema que incluye. Consulta [Actualización](/es/upgrade).

### Almacenamiento de objetos

`[object_store]` configura el almacén de archivos Parquet, índices de búsqueda y objetos binarios de perfiles. Backends: `local`, `s3`, `azure`, `gcs`. Usa `s3` para AWS S3 y servicios compatibles con S3, como RustFS, Cloudflare R2 y Alibaba Cloud OSS.

| Clave | Valor predeterminado | Descripción |
|---|---|---|
| `backend` | `local` | `local`, `s3`, `azure` o `gcs`. |
| `root` | `./data/objects` | Directorio del backend `local`. Los demás backends ignoran esta opción. |
| `bucket` | vacío | Nombre del bucket para `s3` y `gcs`, o del contenedor para `azure`. Es obligatorio para esos backends. |
| `region` | vacío | Región de S3. Los servicios compatibles con S3 indican el valor que esperan. |
| `endpoint` | vacío | URL del punto de conexión de S3. Déjala vacía para AWS S3. Usa URL del tipo `http://host:9000` para RustFS y servicios similares. |
| `path_style` | `false` | `false` usa direccionamiento por host virtual, que requieren AWS S3 y Huawei Cloud OBS. Establece `true` para usar direccionamiento por ruta, que requieren RustFS y la mayoría de los servicios autoalojados. |
| `access_key` | vacío | Clave de acceso de S3 o del almacenamiento de Azure. |
| `secret_key` | vacío | Clave secreta de S3. |
| `credentials_file` | vacío | Ruta de un archivo con las líneas `access_key=<value>` y `secret_key=<value>`. Consulta el orden de prioridad a continuación. |
| `multipart_threshold_size` | `32` | Tamaño mínimo, en MiB, a partir del cual el almacén carga los objetos por partes. Siempre carga los objetos de manifiesto y realiza las escrituras con una condición de versión en una sola solicitud. El mínimo es 1. |
| `multipart_part_size` | `8` | Tamaño de cada parte de una carga, en MiB, de 5 a 1024. Los objetos muy grandes usan partes de mayor tamaño para que la carga no supere las 10 000 partes. |
| `range_threshold_size` | `16` | Tamaño mínimo, en MiB, a partir del cual el almacén divide la lectura de un rango de bytes en solicitudes de fragmentos que ejecuta en paralelo. El mínimo es 1. |
| `range_chunk_size` | `8` | Tamaño del fragmento por solicitud, en MiB, de 1 a 1024. |
| `max_concurrency` | `8` | Operaciones simultáneas del almacén de objetos por proceso. |
| `op_timeout_secs` | `30` | Tiempo de espera máximo para obtener un cupo de concurrencia y para ejecutar una operación del backend. |
| `health_probe_interval_secs` | `30` | Intervalo de la comprobación en segundo plano que escribe, lee y elimina un objeto. El mínimo es 5. |

Los clientes de S3 y Azure toman las credenciales de la primera fuente de esta lista que proporciona tanto una clave de acceso como una clave secreta:

1. Las variables `MS_OBJECT_STORE_ACCESS_KEY` y `MS_OBJECT_STORE_SECRET_KEY`.
2. El archivo que indica `credentials_file`.
3. Las claves `access_key` y `secret_key`.

El registro de inicio indica la fuente elegida en `object_store_credentials_source`: `env`, `file`, `inline` o `none`. Para la clave secreta, usa una variable de entorno o un archivo de credenciales en lugar de `config.toml`.

Cada parte de una carga y cada fragmento de una lectura por rango cuenta como una operación del almacén de objetos. Cada operación ocupa un cupo de concurrencia, se reintenta de forma independiente y aparece en las métricas `object_store_*`. Cada transferencia ocupa como máximo la mitad de los cupos, para que los objetos grandes no bloqueen las demás operaciones.

Ante errores transitorios de los backends en la nube, MoleSignal reintenta las operaciones con espera exponencial:

| Clave | Valor predeterminado | Descripción |
|---|---|---|
| `[object_store.retry].max_attempts` | `4` | Total de intentos por operación. |
| `[object_store.retry].base_backoff_ms` | `100` | Espera inicial. |
| `[object_store.retry].max_backoff_ms` | `5000` | Espera máxima. |
| `[object_store.retry].jitter_ratio` | `0.2` | Factor de variación aleatoria que se aplica a cada espera, de `0` a `1`. |

### Registro de escritura anticipada

`[wal]` configura el registro de escritura anticipada (WAL), que cada nodo mantiene en el almacén de objetos. El nodo solo confirma una escritura después de almacenar el objeto WAL correspondiente, así que no necesita un volumen persistente. Consulta [Arquitectura](/es/architecture#durabilidad-y-recuperación).

| Clave | Valor predeterminado | Descripción |
|---|---|---|
| `lease_secs` | `15` | Duración de la concesión de escritura en segundos, como mínimo `3`. Si un nodo deja de renovarla, otro nodo de ingesta toma el relevo una vez transcurrido este tiempo desde la última renovación, más un retraso de hasta un intervalo de `takeover_interval_secs`. El nodo solo lee este valor al iniciar. |
| `max_group_size` | `8` | Tamaño máximo de un objeto WAL en MiB. El nodo agrupa las escrituras que llegan mientras escribe el objeto anterior del mismo conjunto de datos en el siguiente objeto, hasta alcanzar este tamaño. |
| `put_timeout_secs` | `10` | Tiempo máximo para escribir un objeto. |
| `put_attempts` | `3` | Intentos por escritura de objeto. Si todos fallan, el nodo rechaza con `503` las escrituras agrupadas en el objeto. El cliente puede reintentarlas. |
| `takeover_interval_secs` | `5` | Frecuencia con la que un nodo de ingesta busca nodos con concesiones de escritura vencidas para tomar el relevo. |
| `encrypt` | `false` | Cifra cada objeto WAL con la clave raíz (`MS_CIPHER_KEY`). |
| `max_takeover_size` | `512` | Memoria que ocupa el nodo de relevo, en MiB, antes de publicar un segmento. `0` cuenta como `1`. |

### Ingesta

`[intake]` controla los búferes en memoria de un nodo de ingesta.

| Clave | Valor predeterminado | Descripción |
|---|---|---|
| `buffer_max_size` | `256` | Límite estricto del búfer de datos sin codificar de un flujo, en MiB. El umbral adaptativo nunca lo supera. |
| `max_buffer_memory_size` | `1024` | Memoria total que reservan los búferes activos y desvinculados del proceso, en MiB. |
| `flush_interval_secs` | `30` | Tiempo máximo entre vaciados de búfer. |
| `flush_parallelism` | `4` | Vaciados de búfer simultáneos. |

`[intake.rotation]` ajusta de forma adaptativa el tamaño de los archivos Parquet:

| Clave | Valor predeterminado | Descripción |
|---|---|---|
| `adaptive_enabled` | `true` | Ajusta el próximo umbral de datos sin codificar de cada flujo según la relación entre el tamaño codificado y el tamaño sin codificar de los archivos completados. |
| `target_file_size` | `128` | Tamaño objetivo de los archivos Parquet codificados, en MiB. |
| `min_buffer_size` | `16` | Límite inferior del umbral adaptativo, en MiB. |
| `ewma_alpha` | `0.2` | Factor de suavizado de la relación, mayor que 0 y menor o igual que 1. |

`[intake.prometheus]` limita la entrada de `remote_write` de Prometheus:

| Clave | Valor predeterminado | Descripción |
|---|---|---|
| `max_labels_per_series` | `64` | Etiquetas por serie, sin contar `__name__`. |
| `max_label_name_length` | `128` | Longitud máxima del nombre de una etiqueta, en bytes UTF-8. |
| `max_label_value_length` | `2048` | Longitud máxima del valor de una etiqueta, en bytes UTF-8. |
| `max_samples_per_batch` | `16384` | Muestras por lote interno. |

`[intake.prometheus.cardinality]` controla la admisión de series en el proceso que recibe la solicitud `remote_write`, antes de que reenvíe el lote a un nodo de ingesta. Cada proceso cuenta las series que recibe. Si hay varios enrutadores, cada uno aplica los límites de forma independiente:

| Clave | Valor predeterminado | Descripción |
|---|---|---|
| `enabled` | `true` | Aplica los límites. |
| `max_active_series_per_process` | `1000000` | Series activas por proceso. |
| `max_new_series_per_minute` | `20000` | Series nuevas que el proceso acepta por minuto. |
| `idle_ttl_secs` | `900` | Tiempo de inactividad tras el cual una serie libera el cupo que ocupa. |

Los límites por organización y por métrica se configuran a nivel de plataforma en **Configuración → Cardinalidad de métricas** de la organización `_sys`. Cada nodo vuelve a leerlos cada 30 segundos y los aplica a las series que cuenta.

### Compactación y retención

`[compactor]` combina archivos y aplica la retención. Se ejecuta en los nodos `standalone` y `compactor`.

| Clave | Valor predeterminado | Descripción |
|---|---|---|
| `interval_secs` | `300` | Tiempo entre rondas de compactación. |
| `target_size` | `512` | Tamaño total máximo, en MiB, de los archivos que combina una operación, de `1` a `65536`. El archivo resultante tiene aproximadamente ese tamaño o menos. La operación lee los archivos de entrada y carga el resultado por partes, por lo que el consumo de memoria no aumenta con este tamaño. Cada operación lee como máximo 128 archivos y combina el resto con el resultado en una ronda posterior. Si un archivo supera el tamaño de todos los demás archivos de la operación juntos, la operación lo excluye. La compactación lo incorpora cuando los archivos nuevos alcanzan su tamaño total, para evitar reescribir un archivo grande por unos pocos datos nuevos. |
| `max_concurrent_groups` | `4` | Flujos que un nodo procesa en paralelo en una ronda. |

Para los flujos sin un período de retención propio, la plataforma usa el valor de **Configuración → Retención de datos** en la organización `_sys`. El valor predeterminado es de 30 días. Configura la reducción de muestreo de cada flujo de métricas en su pestaña **Retención**. Consulta [Flujos](/es/streams).

### Mantenimiento del catálogo

Las secciones `[storage.*]` controlan el mantenimiento en segundo plano del catálogo de archivos y del almacén de objetos.

| Clave | Valor predeterminado | Descripción |
|---|---|---|
| `[storage.catalog].seal_after_hours` | `48` | Sella una partición cuando transcurre este número de horas desde que termina. ### Control de admisión

`[search.admission]` limita cuántas consultas de un grupo de trabajo se ejecutan a la vez en un nodo. Si el grupo de trabajo alcanza su límite, las consultas se ponen en cola y se inician en orden de llegada. Si una consulta espera más de `max_wait_secs`, recibe un `429`. Las consultas que obtienen una respuesta de la caché de resultados no esperan. El límite se aplica a las consultas enviadas a través de la API de consultas y Flight SQL, a los gráficos y las estadísticas de campos del explorador, a los recursos compartidos públicamente y a los trabajos de búsqueda. La evaluación de alertas y otras tareas en segundo plano no se ponen en cola. El archivo de ejemplo no incluye esta sección.

| Clave | Valor predeterminado | Descripción |
|---|---|---|
| `default_max_concurrent` | El doble del número de CPU | Límite por nodo para los grupos de trabajo sin entrada en `groups`. `0` significa que no hay límite. |
| `groups` | Vacío | Tabla que asigna a cada nombre de grupo de trabajo su límite por nodo. |
| `role_map` | Vacío | Tabla que asigna un rol (`owner`, `admin`, `editor`, `viewer`) a un grupo de trabajo. Los roles sin asignación usan `default`. |
| `max_wait_secs` | `60` | Tiempo que espera una consulta a que se libere un cupo antes de recibir un `429`. Con `0`, la consulta recibe un `429` en cuanto el grupo de trabajo alcanza su límite. |
| `cluster_default_max_concurrent` | `0` | Límite flexible para todo el clúster que se aplica a los grupos de trabajo sin entrada en `cluster_groups`. Si el grupo ya alcanzó este límite, la consulta recibe un `429` de inmediato. `0` significa que no hay límite. |
| `cluster_groups` | Vacío | Tabla que asigna a cada nombre de grupo de trabajo su límite flexible para todo el clúster. |
| `cluster_sync_interval_secs` | `0` | Intervalo de publicación de la carga del nodo. `0` usa 5. |
| `cluster_stale_secs` | `0` | Los nodos que no envían señales durante más tiempo dejan de aparecer en la vista del clúster. `0` usa 30. |

`/metrics` muestra el estado de la cola de cada grupo de trabajo mediante `query_admission_running`, `query_admission_waiting`, `query_admission_wait_seconds` y `query_admission_refusals_total`.

### Cachés

Cada capa es una caché LRU con un tiempo de vida. Una capacidad de `0` desactiva la capa. Las tasas de aciertos aparecen en `/metrics` como `cache_<layer>_hit_ratio`.

| Sección | Capacidad predeterminada | TTL predeterminado | Contenido |
|---|---|---|---|
| `[cache.index_handle]` | `10000` | `600` s | Referencias a índices de búsqueda abiertos. |
| `[cache.query_result]` | `1000` | `60` s | Resultados de consultas SQL sobre ventanas de tiempo cerradas. |
| `[cache.tantivy_result]` | `1000000` | `600` s | Recuentos de términos que permiten descartar archivos. |
| `[cache.tantivy_footer]` | `100000` | `3600` s | Pies de índice que evitan lecturas por rangos. |

Cada sección admite `capacity` y `ttl_secs`.

`[cache.parquet_metadata]` conserva en memoria los pies de archivo de Parquet ya analizados, incluidos los índices de páginas. Al abrir un archivo que está en la caché, la consulta omite la lectura del pie. Su única clave es `max_size`, en MiB, con un valor predeterminado de `256`. `0` desactiva la caché.

`[cache.object]` guarda en caché rangos de bytes de objetos remotos en el disco local. El backend de objetos `local` no usa esta caché.

| Clave | Valor predeterminado | Descripción |
|---|---|---|
| `enabled` | `true` | Activa la caché. Un valor de `0` en `max_size` también la desactiva. |
| `root` | `./data/cache/objects` | Directorio de la caché. |
| `max_size` | `10240` | Tamaño máximo de la caché en MiB, equivalente a 10 GiB. |
| `block_size` | `4` | Tamaño de bloque en MiB, de 1 a 16. |
| `memory_size` | `256` | Espacio en memoria para bloques verificados, en MiB. Las lecturas posteriores de un bloque no acceden al disco. `0` conserva los bloques solo en disco. |
| `min_free_size` | `1024` | Espacio que se debe mantener libre en disco, en MiB, equivalente a 1 GiB. |
| `max_concurrent_fetches` | `16` | Número de recuperaciones simultáneas de bloques. Debe ser mayor que cero. |
| `max_concurrent_fetches_per_object` | `4` | Número de recuperaciones simultáneas para un mismo objeto. Debe ser mayor que cero. |

Cuando la caché supera `max_size` o el espacio libre en disco cae por debajo de `min_free_size`, la caché elimina primero los bloques que llevan más tiempo sin usarse. Cuando el recolector de basura elimina un objeto, el nodo que lo elimina también retira de la caché los bloques del objeto si lo ha leído desde que se inició. Los demás nodos retiran esos bloques de la caché como cualquier otro bloque.

### Caché incremental de rangos

`[search.stream_agg_cache]` guarda en caché las ventanas cerradas de consultas de rango de PromQL como `rate(metric[5m])`. Así, al actualizar un panel, solo se vuelve a calcular la ventana más reciente.

| Clave | Valor predeterminado | Descripción |
|---|---|---|
| `max_size` | `256` | Memoria para la caché en MiB, estimada a partir de las series y ventanas que conserva cada consulta. `0` desactiva la caché. |
| `ttl_secs` | `300` | Tiempo de vida de las entradas. Cubre los datos que llegan con un retraso superior a `safe_lookback_secs`. |
| `safe_lookback_secs` | `300` | La caché solo guarda las ventanas que terminan antes del momento actual menos este valor. |
| `max_series_per_query` | `10000` | Número de series que se guardan en caché por huella digital. `0` elimina el límite. |

## Configuración almacenada en la base de datos

MoleSignal almacena estos ajustes en PostgreSQL. Modifícalos desde la interfaz web o la API. No tienen claves TOML:

- Proveedores de SSO (OIDC, OAuth 2.0, SAML y LDAP).
- Clústeres remotos para consultas federadas.
- Dominios y certificados de las páginas de estado, y la aplicación de Slack que permite a los visitantes agregar una página a Slack.
- Canales de notificación, horarios y políticas de escalamiento.
- Proveedores de modelos, instrucciones, herramientas y política de aprobación de Mole Agent.
- Claves de cifrado, reglas de enmascaramiento de campos y política de uso compartido de la organización.
