The **Despliegues** section of a service page puts two sources side by side: the deployments that
pipelines report, and the versions that the service's spans carry in `service.version`. A version
that no pipeline reported still appears, from the spans alone.

## La cronología de despliegues

The timeline lists what happened to the service in the time range, the newest first:

| Evento | Cuándo |
|---|---|
| **Desplegado** | A pipeline reported a deployment that succeeded. |
| **Fallido** | A pipeline reported a deployment that failed. A failed deployment does not change the running version. |
| **Revertido** | A pipeline reported a rollback, or reported a deployment of a version that ran before another version. The row names the version it went back from. |
| **Volvió a la versión anterior** | The spans went back to an older version that no pipeline reported: the version seen last was first seen before a newer version that stopped more than five minutes earlier. |
| **Primera aparición** | The spans carried a version that no pipeline reported. |
| **Configuración** | A pipeline or a tool reported a configuration change. Its description shows in the row. |
| **Indicador de funcionalidad** | A pipeline or a tool reported a feature flag change. Its description shows in the row. |

A configuration change or a feature flag does not change the running version and has no figures of
its own. It is listed among the changes near an insight; see
[Cambios cerca de un hallazgo](/es/apm/insights#changes-near-a-finding).

A reported deployment shows its commit, pull request, CI run, and author. When the repository is an
http or https address, the commit opens on its web page, in the way GitHub, GitLab, or Bitbucket
addresses a commit.

Each version's requests, error rate, and p95 in the range show on its newest row, with the verdict
against the version first seen before it:

| Veredicto | Cuándo |
|---|---|
| **Reaparecido** | The error rate rose by at least one point and to at least 1.5 times, or p95 rose by at least a fifth and at least 50 ms. The part that got worse follows the verdict. |
| **Mejoró** | One of the two fell as far, and neither got worse. |
| **Sin cambios** | Neither moved that far. |
| **Solicitudes insuficientes** | Either version served fewer requests than a version comparison needs, 1,000 by default. |

Selecting a verdict opens its two versions in **Comparar dos versiones**, which lists the endpoints that
got slower and the errors that grew. A regressed or improved version is also flagged among the
overview's recent deployments.

## Canarios

When two versions run at once, as a canary runs beside the version it replaces, a card above the
timeline reads them side by side. Two versions run at once when both were seen within five minutes
of the last span of the service. The card compares the newest two, from when the newer one was
first seen:

- the share of the requests that each version served;
- requests, error rate, p50, p95, and p99 of each version;
- the verdict of the newer version against the older one.

## Reporta despliegues desde CI

A pipeline reports a deployment with `POST /api/v1/apm/deployments`. The request needs an API Token
that may use `apm.deploy`. Owners, administrators, and editors hold it, and the **Ingesta de datos**
policy that intake tokens follow includes it.

```bash
curl -X POST "https://<host>/api/v1/apm/deployments" \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{"service": "checkout", "environment": "production", "version": "2.4.0", "commit": "9f2c1e7a4b3d", "repository": "https://github.com/acme/checkout", "ciUrl": "https://ci.example.com/runs/7"}'
```

| Campo | Obligatorio | Descripción |
|---|---|---|
| `service` | Sí | The service, as its spans name it in `service.name`. Up to 255 characters. |
| `version` | For a deployment | The version deployed, as its spans report it in `service.version`. Up to 192 characters. |
| `kind` | No | `deployment` (the default), `configuration`, `feature_flag`, `scaling`, or `infrastructure`. |
| `namespace` | No | The service's `service.namespace`. A deployment without one shows in every namespace. |
| `environment` | No | The environment, as `deployment.environment.name`. A deployment without one shows in every environment. |
| `status` | No | `succeeded` (the default), `failed`, or `rolled_back` when the deployment took the service back to `version`. |
| `commit` | No | The commit deployed: up to 64 letters and digits. |
| `repository` | No | Where the code lives: an https, http, ssh, or git address of up to 512 characters. A password in the address is kept as `****`, as is the user part of an https address. |
| `pullRequest` | No | An http or https link to the pull request. |
| `author` | No | Who deployed, up to 128 characters. |
| `ciUrl` | No | An http or https link to the CI run. |
| `description` | No | Up to 1,000 characters. It shows when the pointer rests on the event. |
| `deployedAt` | No | When the deployment happened, in microseconds since the epoch. Defaults to the time the request arrives. |

The service and the environment are named as APM names them: the organization's naming rules,
environment mapping, and aliases apply to them, as they apply to spans. See
[Configuración de APM](/es/apm/settings).

The **Fuente de datos** page has the steps below under **GitHub Actions**, **GitLab CI/CD**, and
**Jenkins**, with the address of the workspace filled in.

### GitHub Actions

Keep the token as a repository secret, then add a step to the job that deploys. `if: always()`
reports a failed deployment too.

```yaml
- name: Report the deployment to MoleSignal
  if: always()
  env:
    MOLESIGNAL_TOKEN: ${{ secrets.MOLESIGNAL_TOKEN }}
    DEPLOY_STATUS: ${{ job.status == 'success' && 'succeeded' || 'failed' }}
  run: |
    cat > deployment.json <<EOF
    {
      "service": "checkout",
      "environment": "production",
      "version": "${GITHUB_SHA::12}",
      "status": "$DEPLOY_STATUS",
      "commit": "$GITHUB_SHA",
      "repository": "$GITHUB_SERVER_URL/$GITHUB_REPOSITORY",
      "author": "$GITHUB_ACTOR",
      "ciUrl": "$GITHUB_SERVER_URL/$GITHUB_REPOSITORY/actions/runs/$GITHUB_RUN_ID"
    }
    EOF
    curl -fsS -X POST "https://<host>/api/v1/apm/deployments" \
      -H "Authorization: Bearer $MOLESIGNAL_TOKEN" \
      -H "Content-Type: application/json" \
      --data-binary @deployment.json
```

### GitLab CI/CD

Add the token as a masked CI/CD variable named `MOLESIGNAL_TOKEN`, then report from the deploy job's
`after_script`, which runs whether the deployment worked or not.

```yaml
deploy:
  stage: deploy
  environment: production
  script:
    - ./deploy.sh
  after_script:
    - |
      if [ "$CI_JOB_STATUS" = "success" ]; then DEPLOY_STATUS=succeeded; else DEPLOY_STATUS=failed; fi
      cat > deployment.json <<EOF
      {
        "service": "checkout",
        "environment": "$CI_ENVIRONMENT_NAME",
        "version": "$CI_COMMIT_SHORT_SHA",
        "status": "$DEPLOY_STATUS",
        "commit": "$CI_COMMIT_SHA",
        "repository": "$CI_PROJECT_URL",
        "author": "$GITLAB_USER_LOGIN",
        "ciUrl": "$CI_PIPELINE_URL"
      }
      EOF
      curl -fsS -X POST "https://<host>/api/v1/apm/deployments" \
        -H "Authorization: Bearer $MOLESIGNAL_TOKEN" \
        -H "Content-Type: application/json" \
        --data-binary @deployment.json
```

### Jenkins

Add the token as a **Secret text** credential with the ID `molesignal-token`, then report in the
pipeline's `post` block. `post { always }` reports a failed build too. A password in `GIT_URL` is
masked when the deployment is kept.

```groovy
post {
  always {
    script {
      writeFile file: 'deployment.json', text: groovy.json.JsonOutput.toJson([
        service: 'checkout',
        environment: 'production',
        version: env.GIT_COMMIT.take(12),
        status: currentBuild.currentResult == 'SUCCESS' ? 'succeeded' : 'failed',
        commit: env.GIT_COMMIT,
        repository: env.GIT_URL,
        ci_url: env.BUILD_URL,
      ])
    }
    withCredentials([string(credentialsId: 'molesignal-token', variable: 'MOLESIGNAL_TOKEN')]) {
      sh '''
        curl -fsS -X POST "https://<host>/api/v1/apm/deployments" \
          -H "Authorization: Bearer $MOLESIGNAL_TOKEN" \
          -H "Content-Type: application/json" \
          --data-binary @deployment.json
      '''
    }
  }
}
```

## Reporta cambios de configuración e indicadores de funcionalidad

Report a configuration change, a feature flag, a change of scale, or a change of the infrastructure
under a service with the same endpoint, with `kind` set and a description of what changed. It needs no
version.

Every reported change is also listed by [`GET /api/v1/changes`](/es/api/changes), marked on the
histograms of Logs and Traces and under the Metrics chart, and on the **Changes** page of Alerts.

```bash
curl -X POST "https://<host>/api/v1/apm/deployments" \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{"service": "checkout", "environment": "production", "kind": "feature_flag", "description": "new_checkout on for 10% of users"}'
```

## Informa de los cambios desde webhooks

Una herramienta cuyo webhook pueda definir el cuerpo y una cabecera, como las notificaciones de Argo CD, Spinnaker o el complemento de webhook de Unleash con una plantilla de cuerpo, llama a `POST /api/v1/apm/deployments` como se indica más arriba. Una herramienta que envía un cuerpo propio, o que no puede definir una cabecera, llama a `POST /api/v1/intake/changes` en su lugar. El token de API va en `Authorization: Bearer` o, cuando no se puede definir ninguna cabecera, en `?token=`, y debe tener `apm.deploy`. Un token en una dirección puede acabar en los registros del proxy: asigna a esa herramienta un token propio, con alcance únicamente a `apm.deploy`.

| Parámetro | Notas |
|---|---|
| `format` | `generic` (el predeterminado), `launchdarkly`, `unleash`, `nacos` o `apollo`. |
| `service`, `namespace`, `environment` | Lo que el cuerpo no indica. Se rechaza un cambio que no nombre ningún servicio. |
| `kind` | `deployment`, `configuration`, `feature_flag`, `scaling` o `infrastructure`; tiene prioridad sobre lo que indica el cuerpo. |
| `serviceField`, `environmentField`, `versionField`, `descriptionField`, `authorField` | Para `generic`: un puntero JSON como `/app/name`, o el nombre de un campo de nivel superior. Sin uno, se lee el campo del mismo nombre que acepta `POST /api/v1/apm/deployments`. |

| Formato | Se interpreta como |
|---|---|
| `launchdarkly` | Un feature flag. El entorno es la parte `env/` del recurso auditado, la descripción es el título de la entrada y el autor es el correo del miembro. |
| `unleash` | Un feature flag: el tipo de evento y el nombre del toggle, su entorno y quién lo hizo. |
| `nacos` | Un cambio de configuración del data ID y el grupo; el espacio de nombres de Nacos es el espacio de nombres. |
| `apollo` | Un cambio de configuración: el ID de la app es el servicio, el clúster es el entorno, y el espacio de nombres y el título del release son lo que cambió. |

**Orígenes de datos → DevOps** tiene una guía para cada uno de LaunchDarkly, Unleash, Nacos y Apollo, con la dirección ya rellenada para el espacio de trabajo.

Un cuerpo puede contener un cambio o una lista de hasta 100. La respuesta es `201` con los cambios guardados. Los preajustes se escribieron a partir de las cargas útiles documentadas de las herramientas y no se han comprobado con cuentas reales; cuando la carga útil de una herramienta sea distinta, usa `generic` con punteros.

```bash
curl -X POST "https://<host>/api/v1/intake/changes?format=launchdarkly&service=checkout&token=<token>" \
  -H "Content-Type: application/json" \
  -d @launchdarkly-event.json
```

## Solución de problemas

| Síntoma | Comprobación |
|---|---|
| Un despliegue informado no aparece en la línea de tiempo | El intervalo de tiempo debe incluir `deployedAt`, y `service` debe nombrar el servicio tal como lo hace APM. Un despliegue informado con un entorno solo se muestra en ese entorno. |
| Un despliegue y la versión que desplegó aparecen como dos filas | La `version` informada difiere de la `service.version` que llevan los spans. Informa del mismo valor. |
| `403` del endpoint de despliegues | Puede que el token no pueda usar `apm.deploy`: su alcance lo excluye, o su miembro o cuenta de servicio no lo tiene. |
| `400` del endpoint de despliegues | Algún campo incumple un límite de la tabla anterior; el error indica cuál. |
