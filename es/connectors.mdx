A **connector** is a managed integration with an external platform. Connectors work in two directions:

- **Sources** bring data in from another service and write it to a stream. MoleSignal pulls CloudWatch Logs, Kafka topics, and S3 objects on a schedule. Amazon Data Firehose, Google Cloud Pub/Sub, Cloudflare Logpush, and Heroku push to MoleSignal; Firehose also carries CloudWatch metrics.
- **Destinations** receive the output of a [scheduled pipeline](/es/pipelines#destinos-de-escritura-y-salida-de-conectores): Amazon S3 and S3-compatible storage, Apache Kafka, and any HTTP endpoint.

| Kind | Connector | Direction | Authentication |
|---|---|---|---|
| `aws_cloudwatch_logs` | AWS CloudWatch Logs | Source, pulled every 30 seconds | [AWS credentials](#autenticación-de-aws) |
| `kafka_source` | Kafka topic | Source, pulled every 30 seconds | None, SASL, or a client certificate |
| `s3_source` | S3 objects | Source, pulled every 30 seconds | AWS credentials |
| `gcp_pubsub_pull` | Google Cloud Pub/Sub subscription | Source, pulled every 30 seconds | Service account key |
| `aws_cloudwatch_metrics`, `azure_monitor_metrics`, `gcp_monitoring_metrics`, `aliyun_cms_metrics`, `tencent_monitor_metrics`, `huawei_ces_metrics` | [Cloud metrics](#métricas-de-la-nube) | Source, pulled every period | The cloud's credentials |
| `aws_kinesis_firehose` | Amazon Data Firehose | Source, pushed | [Push token](#orígenes-push) |
| `gcp_pubsub_push` | Google Cloud Pub/Sub push | Source, pushed | Push token, optionally with the subscription's OIDC token |
| `cloud_events` | Cloud event bus | Source, pushed | Push token |
| `cloudflare_logpush` | Cloudflare Logpush | Source, pushed | Push token |
| `heroku_drain` | Heroku log drain | Source, pushed | Push token |
| `s3` | Amazon S3 | Destination | AWS credentials |
| `kafka` | Apache Kafka | Destination | None, SASL, or a client certificate |
| `http` | HTTP / Webhook | Destination | None, a bearer token, Basic auth, a custom header, or an HMAC signature |

## Create a connector

<Steps>
  <Step title="Open the connectors">
    Go to **Pipelines → Connectors**. The page lists **Sources** and **Destinations**.
  </Step>
  <Step title="Choose the kind">
    Click **New connector** and choose what to connect to.
  </Step>
  <Step title="Fill in the settings">
    Enter a **Name** that is unique within the organization, fill in where the connector reads from or delivers to, and choose the **Authentication**.
  </Step>
  <Step title="Test and create">
    Click **Test connection** to try the settings before saving them, then click **Create connector**. A push source has nothing to connect to and offers no test.
  </Step>
</Steps>

Over the API, a connector is a `name`, a `kind`, and a `configJson` whose keys depend on the kind. `auth` in `configJson` names the way of authenticating, and each way takes its own keys. Settings that cannot work answer `400` when they are saved: a missing required key, half of a credential pair, or a key that the chosen `auth` does not use.

```bash
curl -X POST http://localhost:5080/api/v1/connectors \
  -H "authorization: Bearer $MS_TOKEN" \
  -H 'content-type: application/json' \
  -d '{
        "name": "archive",
        "kind": "s3",
        "configJson": {
          "bucket": "acme-logs",
          "region": "eu-west-1",
          "prefix": "pipelines/checkout/",
          "auth": "assume_role",
          "roleArn": "arn:aws:iam::123456789012:role/molesignal-delivery"
        }
      }'
```

## Secrets

These keys of `configJson` hold secrets:

| Kind | Secret keys |
|---|---|
| `s3`, `aws_cloudwatch_logs` | `accessKey`, `secretKey`, `sessionToken` |
| `aws_kinesis_firehose`, `gcp_pubsub_push`, `cloud_events`, `cloudflare_logpush`, `heroku_drain` | `pushToken` |
| `aws_cloudwatch_metrics` | `accessKey`, `secretKey`, `sessionToken` |
| `azure_monitor_metrics` | `clientSecret` |
| `gcp_monitoring_metrics`, `gcp_pubsub_pull` | `serviceAccountKey` |
| `aliyun_cms_metrics`, `tencent_monitor_metrics`, `huawei_ces_metrics` | `accessKey`, `secretKey` |
| `kafka` | `saslPassword`, `tlsClientKey` |
| `http` | `url`, `bearerToken`, `basicPassword`, `headerValue`, `hmacSecret` |

A secret never leaves through the API. A response shows `***` in its place and names the secrets that hold a value in `secretKeys`:

```json
{
  "kind": "kafka",
  "configJson": {
    "brokers": "b-1.example.com:9096",
    "topic": "logs",
    "tls": true,
    "auth": "sasl_scram_sha_512",
    "saslUsername": "molesignal",
    "saslPassword": "***"
  },
  "secretKeys": ["saslPassword"]
}
```

- An update that sends `***` back keeps the stored value, so a connector can be renamed, turned off, or pointed elsewhere without entering its credentials again. In the UI, a saved secret left empty keeps its value.
- A secret left out of an update is removed.
- An update that changes the `kind` keeps none of the stored secrets.

MoleSignal seals the secrets with the root key from `MS_CIPHER_KEY` (AES-256-GCM) apart from the other settings, and stores no secret in plain text. A push source is found by the SHA-256 of its token. `molesignal rewrap-kek` re-seals the connector secrets together with the other secrets when the root key rotates. See [Production checklist](/es/deployment/production-checklist).

## Orígenes

### Orígenes push

Los cinco orígenes push comparten un modelo: crea un conector con un **`pushToken`** y un **`targetStream`**, y luego apunta la plataforma al punto de conexión correspondiente. Estos puntos de conexión no usan el JWT. La solicitud se autentica con el token push, suministrado de la forma que permita la plataforma:

| Método | Usado por |
|---|---|
| Cabecera `X-Connector-Token` | Plataformas con cabeceras configurables, como Cloudflare |
| Cabecera `X-Amz-Firehose-Access-Key` | Amazon Data Firehose, que la envía automáticamente |
| Cabecera `X-EventBridge-Signature-Token` | Alibaba Cloud EventBridge |
| Parámetro de consulta `?token=` | Plataformas que no pueden establecer cabeceras, como Heroku y Pub/Sub |
| Contraseña de `Authorization: Basic` | Plataformas que ponen las credenciales en la dirección |

La interfaz genera el token cuando crea el conector y lo muestra una vez, junto con el punto de conexión que se debe dar a la plataforma. El token no se puede volver a leer. **Generar un token nuevo** lo reemplaza cuando se guarda el conector. A través de la API, suministra un `pushToken` de al menos 16 caracteres. Un token abre un conector de un tipo: un token que ya está en uso responde `409`. Una solicitud con un token faltante o desconocido, o para un conector que está desactivado, responde `401`. Un conector sin token no acepta nada. Un nodo conserva un conector que ha consultado durante 30 segundos, así que desactivar un conector o reemplazar su token surte efecto dentro de ese tiempo.

Los cuerpos enviados con `Content-Encoding: gzip` se descomprimen automáticamente. Un cuerpo de Firehose puede ser de hasta 64 MiB; cualquier otro, de hasta 16 MiB, contado también después de la descompresión. Los eventos fluyen por la misma ruta de ingesta que todo lo demás: se aplican el esquema en la escritura, las [canalizaciones](/es/pipelines) y el [enmascaramiento](/es/security).

<Tabs>
  <Tab title="Amazon Data Firehose">
    Crea el conector con `kind: "aws_kinesis_firehose"`, luego elige el destino **punto de conexión HTTP** para el flujo de Firehose:

    - **URL del punto de conexión HTTP**: `https://molesignal.example.com/api/v1/_kinesis_firehose`
    - **Clave de acceso**: el token push. Firehose lo envía como `X-Amz-Firehose-Access-Key`.

    Firehose entrega solo a HTTPS en el puerto 443 con un certificado de confianza pública, así que una implementación en una red privada necesita un punto de entrada público; consulta [Acceso público](/es/public-access). Mantén el búfer del flujo en 1 a 4 MiB.

    MoleSignal lee cada registro por separado, según lo que contiene:

    | Registro | Se convierte en |
    |---|---|
    | Un mensaje de suscripción de CloudWatch Logs, comprimido con gzip como lo envía el filtro de suscripción | Un evento de log por cada entrada de `logEvents`, en la hora propia de la entrada, con `message`, `log_group`, `log_stream`, `account_id`, `region`, `event_id` y `source: "cloudwatch"`. Se omite la comprobación de estado que envía la suscripción cuando se crea. |
    | Un registro de CloudWatch Metric Streams en el formato de salida JSON, OpenTelemetry 1.0 u OpenTelemetry 0.7 | Muestras de métricas en el flujo de métricas; consulta abajo. |
    | Cualquier otro texto | Un evento de log por línea: un objeto JSON proporciona los campos; el texto sin formato va a `message`. |

    Un flujo de métricas envía un agregado por métrica por minuto. Cada estadística se convierte en una muestra de gauge llamada `aws_<namespace>_<metric>_<statistic>`, tal como las nombra yet-another-cloudwatch-exporter: `aws_ec2_cpuutilization_average`, `aws_ec2_cpuutilization_maximum`, `aws_applicationelb_request_count_sum`. El espacio de nombres pierde su prefijo `AWS/`, y el nombre de la métrica se divide en palabras donde una letra minúscula se encuentra con una mayúscula. Las estadísticas son `average` (la suma sobre el recuento de muestras), `sum`, `sample_count`, `minimum`, `maximum` y cualquier percentil que agregue el flujo, como `p99` o `p99_9`. Las etiquetas son `account_id`, `region` y una `dimension_<Name>` por dimensión, como `dimension_InstanceId`; `metric_unit` conserva la unidad.

    ```promql
    max by (dimension_InstanceId) (aws_ec2_cpuutilization_average)
    ```

    `X-Amz-Firehose-Common-Attributes`, establecido como los parámetros del flujo, agrega sus claves a cada evento y muestra; prevalece el campo que ya tiene el registro. `X-Amz-Firehose-Source-Arn` proporciona la `region` de los eventos de CloudWatch Logs, que no la llevan.

    La respuesta sigue la especificación de entrega de Firehose: `application/json` con el `requestId` de la solicitud, un `timestamp` y un `errorMessage` en caso de fallo. Los registros que no se pueden leer se omiten, y el resto de la solicitud se escribe igualmente con `200`. Una escritura que falla por ahora responde `429` o `5xx`, que Firehose reintenta. Un cuerpo de más de 64 MiB responde `413`, que Firehose no reintenta ni guarda copia. Una entrega reintentada dentro de los 30 minutos posteriores a su escritura, con el mismo `X-Amz-Firehose-Request-Id`, se responde `200` sin volver a escribirla.
  </Tab>
  <Tab title="Google Cloud Pub/Sub">
    Crea el conector con `kind: "gcp_pubsub_push"`. Enruta los logs a un tema de Pub/Sub con un sumidero de Log Router y luego crea una suscripción push en el tema. Pub/Sub no puede establecer cabeceras personalizadas, así que el token viaja en la URL:

    ```bash
    gcloud pubsub subscriptions create molesignal-push --topic=molesignal-logs --push-endpoint="https://molesignal.example.com/api/v1/_gcp_pubsub?token=<pushToken>"
    ```

    Para comprobar también el token OIDC de la suscripción, establece `oidcServiceAccount` en el conector con el correo de una cuenta de servicio y crea la suscripción con `--push-auth-service-account=<email>`. MoleSignal entonces verifica el token con las claves de Google y acepta solo esa cuenta de servicio. Establece `oidcAudience` para comprobar también la audiencia, y pasa el mismo valor como `--push-auth-token-audience`.

    Cada mensaje es una solicitud. Se aceptan tanto el cuerpo envuelto como una carga útil sin envolver. Un `LogEntry` de Cloud Logging se convierte en un evento de log:

    | `LogEntry` | Evento |
    |---|---|
    | `jsonPayload` | Sus campos |
    | `textPayload` | `message` |
    | `protoPayload` (logs de auditoría) | `proto_payload`, con `method_name`, `service_name` y `principal_email` extraídos de él |
    | `severity` | `level`, en minúsculas |
    | `logName`, `resource.type`, `insertId` | `log_name`, `resource_type`, `insert_id` |
    | `resource.labels`, `labels` | Campos con sus propios nombres |
    | `trace`, `spanId` | `trace_id` sin el prefijo `projects/<id>/traces/`, `span_id` |
    | `httpRequest` | `http_request` |
    | `timestamp` | La hora del evento; `receiveTimestamp` o la hora de publicación cuando falta |

    Cualquier otro dato del mensaje se convierte en un evento: los campos de un objeto JSON o el texto como `message`. El punto de conexión responde `204 No Content`, que Pub/Sub cuenta como confirmación. Un mensaje que no se puede leer se confirma y se omite; una escritura que falla por ahora no, así que Pub/Sub lo entrega de nuevo. Un mensaje entregado de nuevo dentro de los 30 minutos posteriores a su escritura se confirma sin volver a escribirlo.
  </Tab>
  <Tab title="Bus de eventos en la nube">
    Crea el conector con `kind: "cloud_events"` y luego apunta el bus de eventos a `https://molesignal.example.com/api/v1/_cloud_events`:

    | Remitente | Configuración |
    |---|---|
    | Amazon EventBridge | Un destino de API con una conexión de **Clave de API**; el nombre de la cabecera es `X-Connector-Token` y su valor, el token push. |
    | Azure Event Grid | Una suscripción de webhook cuyo punto de conexión termina con `?token=<pushToken>`. El handshake de validación y el handshake `OPTIONS` del esquema de CloudEvents se responden automáticamente. |
    | Alibaba Cloud EventBridge | Un destino HTTPS con el token push como su token, enviado como `X-EventBridge-Signature-Token`. |
    | Huawei Cloud EventGrid | Un destino de webhook con la cabecera `X-Connector-Token`. |
    | Otros remitentes de CloudEvents | Cualquiera de los métodos de token anteriores. También se acepta un remitente que solo puede poner las credenciales en la dirección, como `https://user:<pushToken>@host/...`. |

    Un cuerpo contiene un evento o un arreglo de ellos, como CloudEvents 1.0 en modo estructurado o binario, eventos de Amazon EventBridge o el esquema de Event Grid. Cada evento se convierte en un evento de log en `targetStream` (predeterminado, `cloud_events`):

    | Campo | Origen |
    |---|---|
    | `event_id`, `event_source`, `event_type`, `event_subject` | `id`, `source`, `type`, `subject` de CloudEvents; `id`, `source`, `detail-type` de EventBridge; `id`, `topic`, `eventType`, `subject` de Event Grid |
    | `account_id`, `region` | `account`, `region` de EventBridge; `aliyunaccountid`, `aliyunregionid` de Alibaba Cloud; la suscripción de un tema de Event Grid |
    | `resources` | `resources` de EventBridge |
    | `data` | La carga útil como un campo JSON; una carga útil de texto va a `message` |
    | `event_format` | `cloudevents`, `eventbridge` o `event_grid` |

    Los atributos de extensión conservan sus nombres. La hora propia del evento es su hora. Cualquier otro objeto JSON se convierte en un evento con sus campos tal como están. Un evento entregado de nuevo dentro de los 30 minutos, con el mismo origen e id, no se escribe dos veces. El punto de conexión responde `200`, o `400` para un cuerpo que no es JSON.
  </Tab>
  <Tab title="Cloudflare Logpush">
    Crea el conector con `kind: "cloudflare_logpush"` y luego crea un trabajo de Logpush con un destino HTTP. Cloudflare convierte un parámetro de consulta `header_` en una cabecera de solicitud, así que el token viaja en `X-Connector-Token`:

    ```text
    https://molesignal.example.com/api/v1/_cloudflare?header_X-Connector-Token=<pushToken>
    ```

    Cloudflare envía NDJSON comprimido con gzip, y cada línea se convierte en un evento. El punto de conexión responde `204 No Content`.
  </Tab>
  <Tab title="Heroku">
    Crea el conector con `kind: "heroku_drain"` y luego agrega el drain. Heroku no puede establecer cabeceras personalizadas, así que el token viaja en la URL:

    ```bash
    heroku drains:add "https://molesignal.example.com/api/v1/_heroku?token=<pushToken>"
    ```

    Cada línea de log se convierte en un evento con `message` y `source: "heroku"`. El punto de conexión responde `204 No Content`.
  </Tab>
</Tabs>

<Tip>
  El `targetStream` se crea en la primera entrega, y el esquema evoluciona a medida que aparecen campos nuevos, igual que en cualquier otro flujo. Omite `targetStream` para usar un valor predeterminado por origen: `kinesis`, `gcp`, `cloud_events`, `cloudflare` o `heroku`. Un conector de Firehose escribe las muestras de métricas en `metricsStream`, `cloudwatch` de forma predeterminada.
</Tip>

### CloudWatch Logs

CloudWatch Logs es un origen **pull**: MoleSignal llama a `FilterLogEvents` cada 30 segundos en lugar de recibir un push. La primera ejecución lee los últimos 5 minutos. Cada ejecución posterior comienza donde terminó la última ejecución correcta, así que los eventos que no se pudieron leer o escribir se leen de nuevo en la siguiente ejecución.

```bash
curl -X POST http://localhost:5080/api/v1/connectors \
  -H "authorization: Bearer $MS_TOKEN" \
  -H 'content-type: application/json' \
  -d '{
        "name": "cw-prod",
        "kind": "aws_cloudwatch_logs",
        "configJson": {
          "region": "ap-southeast-1",
          "logGroup": "/aws/lambda/checkout",
          "auth": "node_role",
          "targetStream": "cloudwatch"
        }
      }'
```

| Campo | Notas |
|---|---|
| `region` / `logGroup` | Obligatorio. La región y el grupo de logs de CloudWatch que se van a leer. |
| `auth` y sus claves | Las credenciales, que necesitan `logs:FilterLogEvents` en el grupo de logs. Consulta [Autenticación de AWS](#autenticación-de-aws). |
| `targetStream` | Flujo de destino. Predeterminado, `default`. |

Un nodo sondea un conector a la vez. Los nodos `alert` se dividen los conectores entre ellos, y un nodo reclama un conector antes de sondearlo. Consulta [División del trabajo entre nodos de alerta](/es/deployment/role-based#distribución-del-trabajo-entre-nodos-de-alertas). Cada evento se convierte en un log con `message`, `log_stream` y `log_group`. Un conector desactivado no se sondea.

### Temas de Kafka

Un conector `kafka_source` lee un tema cada 30 segundos y continúa desde donde se quedó la última lectura que se escribió. Toma las particiones por asignación, no como miembro de un grupo de consumidores, y guarda sus offsets en MoleSignal, así que solo necesita el permiso para leer el tema, y no aparece ningún grupo de consumidores en el clúster.

```bash
curl -X POST http://localhost:5080/api/v1/connectors \
  -H "authorization: Bearer $MS_TOKEN" \
  -H 'content-type: application/json' \
  -d '{
        "name": "orders",
        "kind": "kafka_source",
        "configJson": {
          "brokers": "b-1.example.com:9096,b-2.example.com:9096",
          "topic": "orders",
          "tls": true,
          "auth": "sasl_scram_sha_512",
          "saslUsername": "molesignal",
          "saslPassword": "<password>",
          "targetStream": "orders",
          "startFrom": "latest"
        }
      }'
```

| Campo | Notas |
|---|---|
| `brokers`, `topic`, `tls`, `tlsCaCert`, `auth` y sus claves | Igual que para un [destino de Kafka](#apache-kafka). |
| `targetStream` | Flujo de destino. Predeterminado, `default`. |
| `messageFormat` | `json`, el predeterminado, o `azure_records` para lo que Azure Monitor exporta a un centro de eventos; consulta abajo. Interfaz: **Formato del mensaje**. |
| `startFrom` | Dónde comienza la primera lectura: `latest`, el predeterminado, para lo que llega desde ahora, o `earliest` para todo lo que guardan los brokers. Una partición agregada después se lee desde su inicio. Interfaz: **Empezar desde**. |

- Un mensaje cuyo valor es un objeto JSON proporciona los campos del log. Cualquier otro valor se convierte en su `message`. Cada log también tiene `kafka_topic`, `kafka_partition`, `kafka_offset`, `kafka_key` cuando el mensaje tiene una clave, y `source`. Su hora es la marca de tiempo del mensaje.
- Una lectura toma hasta 10.000 mensajes o 32 MiB, y la siguiente sigue de inmediato mientras haya más, durante hasta 2 minutos en un pull.
- Los offsets se mueven solo cuando se escriben los logs. Una lectura o una escritura que falla se vuelve a intentar desde el mismo lugar 30 segundos después, así que un mensaje se puede escribir dos veces pero no perderse. Los offsets que los brokers han dejado obsoletos continúan desde el mensaje más antiguo que todavía conservan.
- Cambiar el `topic` comienza de nuevo desde `startFrom`, ya que los offsets pertenecen al tema.

La configuración de diagnóstico de Azure, la exportación de datos de Log Analytics y las reglas de recopilación de datos exportan a Azure Event Hubs, que un origen de Kafka lee a través del punto de conexión de Kafka del centro: `brokers` `<namespace>.servicebus.windows.net:9093`, `topic` el centro de eventos, `tls` activado, `auth: sasl_plain` con el nombre de usuario `$ConnectionString` y la cadena de conexión como contraseña. El nivel Básico no tiene punto de conexión de Kafka. Con `messageFormat: azure_records`, cada mensaje `{"records": [...]}` se desempaqueta: un registro de log se convierte en un evento de log en su `time`, y un registro de métrica se convierte en una muestra por estadística en el `metricsStream` del conector (predeterminado, `default`), con el nombre que tienen las [métricas de Azure Monitor](#métricas-de-la-nube).

### Objetos de S3

Un conector `s3_source` lista un bucket cada 30 segundos y lee los objetos que no ha leído, del más antiguo al más reciente, desde AWS S3 o un almacén compatible con S3.

```bash
curl -X POST http://localhost:5080/api/v1/connectors \
  -H "authorization: Bearer $MS_TOKEN" \
  -H 'content-type: application/json' \
  -d '{
        "name": "elb-logs",
        "kind": "s3_source",
        "configJson": {
          "bucket": "acme-logs",
          "region": "us-east-1",
          "prefix": "AWSLogs/123456789012/",
          "auth": "node_role",
          "targetStream": "elb",
          "startFrom": "latest"
        }
      }'
```

| Campo | Notas |
|---|---|
| `bucket`, `region`, `endpoint`, `virtualHostedStyle`, `auth` y sus claves | Igual que para un [destino de S3](#amazon-s3). Las credenciales necesitan `s3:ListBucket` en el bucket y `s3:GetObject` en los objetos. |
| `prefix` | Solo se leen los objetos bajo este prefijo. Cada pull lo lista entero, así que asigna a un origen un prefijo propio. |
| `targetStream` | Flujo de destino. Predeterminado, `default`. |
| `startFrom` | Dónde comienza la primera lectura: `latest`, el predeterminado, para los objetos que aparecen desde ahora y en los 5 minutos anteriores, o `earliest` para todo lo que hay bajo el prefijo. Interfaz: **Empezar desde**. |

- Un objeto se lee como líneas. Una línea que es un objeto JSON proporciona los campos de un log; una que solo contiene `Records`, como escribe CloudTrail, proporciona un log por registro; y cualquier otra línea se convierte en un `message`. Los objetos `.gz` y `.zst` se descomprimen según sus nombres. Cada log también tiene `s3_bucket`, `s3_key` y `source`. Su hora es la de la última modificación del objeto.
- Un pull lee hasta 100 objetos o hasta 50.000 logs, y el siguiente sigue de inmediato mientras haya más, durante hasta 2 minutos.
- El estado de lectura se mueve solo cuando se escriben los logs. Un objeto que no se puede obtener detiene el pull allí y se vuelve a intentar 30 segundos después, así que un log se puede escribir dos veces pero no perderse.
- Un objeto que no se puede leer se omite y se indica en el conector, ya que intentarlo de nuevo retrasaría todo lo que viene después. Se trata de uno que está corrupto, supera los 256 MiB, supera los 512 MiB una vez descomprimido, supera un millón de logs o tiene una línea de más de 64 MiB.
- Un objeto se reconoce por su clave y su hora de modificación, con un margen de 5 minutos. Un objeto que se vuelve a escribir con la misma clave dentro de ese margen no se lee de nuevo, y uno cuya hora de modificación sea más de 5 minutos anterior al objeto más nuevo leído no se lee en absoluto. S3 fecha una carga multiparte desde que comenzó, así que una carga más lenta que eso queda sin leer.

### Suscripciones de Google Cloud Pub/Sub

Un conector `gcp_pubsub_pull` lee una suscripción de Pub/Sub cada 30 segundos, hasta 1000 mensajes por solicitud y de inmediato mientras haya más, y confirma los mensajes solo cuando se escriben. Lo que no se puede escribir se entrega de nuevo cuando vence su plazo de confirmación, así que un mensaje se puede escribir dos veces pero no perderse. Admite más logs de los que una [suscripción push](#orígenes-push), que envía un mensaje por solicitud, puede manejar bien.

| Campo | Notas |
|---|---|
| `serviceAccountKey` | El archivo de clave JSON de una cuenta de servicio con `roles/pubsub.subscriber` en la suscripción. |
| `subscription` | `projects/<project>/subscriptions/<name>`, o el nombre de una suscripción en el proyecto de la clave. Asígnale un plazo de confirmación de 60 segundos o más. |
| `targetStream` | Flujo de destino. Predeterminado, `default`. |

Cada mensaje se lee como uno enviado por push: un `LogEntry` de Cloud Logging con la correspondencia de la pestaña push, cualquier otro objeto JSON como sus campos, cualquier otra cosa como `message`. **Probar conexión** pregunta si la clave puede consumir la suscripción, sin tomar un mensaje.

Seis orígenes extraen las métricas del servicio de monitoreo de una nube según una programación y las escriben en un flujo de métricas:

Cada pull lee periodos completos de `period` segundos que terminaron al menos `delay` segundos antes, comenzando donde terminó el último pull escrito. Una nube completa un agregado algunos minutos después de que termina su periodo, y cada periodo se lee una vez: un valor corregido después se queda como se leyó. Un conector nuevo comienza un periodo atrás. Un pull lee como máximo 12 periodos y continúa en el siguiente ciclo; un conector que estuvo desactivado más de 6 horas omite lo más antiguo y lo indica.

Cada estadística de cada serie se convierte en una muestra de gauge llamada `<cloud>_<namespace>_<metric>_<statistic>`, tal como yet-another-cloudwatch-exporter nombra las métricas de CloudWatch, al inicio de su periodo:

| Origen | Ejemplo | Etiquetas |
|---|---|---|

| Cloud Monitoring | `gcp_compute_instance_cpu_utilization_mean` | `project_id`, `resource_type`, las etiquetas del recurso y de la métrica |
| CloudMonitor | `aliyun_ecs_dashboard_cpuutilization_average` | `region`, `user_id`, `dimension_<key>` |

|---|---|---|

Limita `metrics` y `statistics` a lo necesario, y un `period` más largo cuesta menos. **Probar conexión** hace una solicitud pequeña con la configuración guardada y no mueve nada.

### Cómo va un pull

La página del conector muestra cuándo recibió por última vez un origen. Un origen cuya última lectura falló muestra una advertencia junto a eso, con el motivo en su información emergente y en la configuración del conector, y allí también se indica lo último que omitió un origen. Los eventos que su flujo rechaza porque un valor no encaja con el tipo de su campo no se envían de nuevo: un origen continúa, y un punto de conexión push sigue respondiendo con éxito, ya que la plataforma reenviaría toda la solicitud. Entonces, lo último que omitió el conector indica cuántos eventos se rechazaron y el primer motivo. A través de la API, `readState` contiene `lastError` y `lastWarning`, cada uno con `atTime` y `text`, y `position`, donde ha llegado. Guardar un conector conserva su lugar.

## Destinos

Un destino recibe cada evento que pasa por los pasos de un pipeline programado. Agrega el conector a los **Destinos** del flujo con **Agregar destino → Conector**. Una entrega que falla se reintenta dentro de la ejecución, y los eventos que el conector todavía no acepta van al flujo de mensajes no entregados. Consulta [Reintentos y mensajes no entregados](/es/pipelines#reintentos-y-eventos-fallidos).

Un destino desactivado no recibe nada. Cada ejecución omite el conector y lo nombra en el `warning` de la ejecución. Los eventos omitidos no cuentan como fallidos, no se convierten en mensajes no entregados y no se envían cuando el conector se vuelve a activar. En el editor, un conector desactivado se muestra como **Desactivado**.

| Tipo | Carga útil |
|---|---|
| `s3` | Un objeto JSON Lines por lote, `PUT` a `s3://<bucket>/<prefix><id>.jsonl`. |
| `kafka` | Un mensaje por evento en el tema, con el evento como carga útil JSON. |
| `http` | El lote en una sola solicitud, o en varias cuando es grande, como NDJSON o como un único arreglo JSON. |

### HTTP / Webhook

| Campo | Notas |
|---|---|
| `url` | Obligatorio. Una URL absoluta `http://` o `https://`. A menudo una URL lleva una credencial, como una clave en la ruta o en la consulta, así que se guarda como secreto. Las respuestas muestran solo `urlOrigin`: el esquema, el host y el puerto. Se rechaza un nombre de usuario y contraseña en la URL: usa `basic`. |
| `method` | `post` (predeterminado) o `put`. |
| `format` | `ndjson` (predeterminado) envía un evento por línea como `application/x-ndjson`. `json` envía un arreglo JSON como `application/json`. |

| `auth` | Interfaz | Claves | Solicitud |
|---|---|---|---|
| `none` | **Ninguno** | | Sin credencial. |
| `bearer` | **Token de portador** | `bearerToken` | `Authorization: Bearer <token>` |
| `basic` | **Autenticación básica** | `basicUsername`, `basicPassword` | Autorización HTTP Basic. Úsala sobre `https`. |
| `header` | **Encabezado personalizado** | `headerName`, `headerValue` | El valor en el encabezado indicado, como `X-API-Key` o `DD-API-KEY`. |
| `hmac` | **Firma HMAC** | `hmacSecret` | Una firma del cuerpo. El secreto necesita al menos 16 caracteres. |

Un encabezado personalizado no puede ser uno que la entrega establezca por sí misma: `Host`, `Content-Type`, `Content-Length`, `Content-Encoding`, `Transfer-Encoding`, `Connection`, `X-MoleSignal-Timestamp` o `X-MoleSignal-Sign`.

Una entrega sigue estas reglas:

- Un lote de más de 4 MiB se divide en varias solicitudes. Un evento de más de ese tamaño va en una solicitud propia.
- Cualquier estado `2xx` cuenta como entregado. Cualquier otro estado hace fallar la entrega, y también una redirección: no se siguen las redirecciones.
- Una solicitud agota el tiempo de espera tras 30 segundos.
- MoleSignal resuelve el host antes de la solicitud y se conecta solo a las direcciones que resolvió. Se rechaza una dirección donde responden los servicios de metadatos de la nube, ya sea que aparezca en la URL o provenga del DNS: `169.254.0.0/16`, `fe80::/10`, `fd00:ec2::254` y `100.100.100.200`. Se permiten otras direcciones privadas.

#### Verificar una firma HMAC

Con `hmac`, cada solicitud lleva dos encabezados:

| Encabezado | Contenido |
|---|---|
| `X-MoleSignal-Timestamp` | La hora de la solicitud en segundos Unix. |
| `X-MoleSignal-Sign` | `sha256=<hex>`, el HMAC-SHA256 de `<timestamp>.<body>` con el secreto compartido. |

Para verificar una solicitud, calcula el HMAC-SHA256 de la marca de tiempo, un `.` y los bytes sin procesar del cuerpo con el mismo secreto, y compara el resultado con la firma en tiempo constante. Rechaza una marca de tiempo de hace más de unos minutos, para que una solicitud capturada no se pueda enviar de nuevo más tarde.

```python
import hashlib
import hmac
import time


def verify(secret: bytes, timestamp: str, signature: str, body: bytes, tolerance: int = 300) -> bool:
    if abs(time.time() - int(timestamp)) > tolerance:
        return False
    signed = timestamp.encode() + b"." + body
    expected = "sha256=" + hmac.new(secret, signed, hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, signature)
```

## Autenticación de AWS

S3 y CloudWatch Logs se autentican en AWS de una de estas cinco formas:

| `auth` | Interfaz | Claves | Credenciales |
|---|---|---|---|
| `access_key` | **Clave de acceso** | `accessKey`, `secretKey` | La clave de larga duración de un usuario de IAM. |
| `temporary_key` | **Clave temporal** | `accessKey`, `secretKey`, `sessionToken` | Una clave de corta duración de AWS STS, válida solo con su token de sesión. Reemplázala antes de que expire. |
| `node_role` | **Identidad del nodo** | | La identidad del nodo en el que se ejecuta MoleSignal. No se almacena ninguna clave. |
| `assume_role` | **Asumir un rol** | `roleArn`, opcionalmente `accessKey` y `secretKey` | Un rol que se asume mediante AWS STS con el ID externo de la organización. |
| `web_identity` | **Identidad web** | `roleArn` | Un rol que se asume con el token de identidad web del nodo. |

Sin `auth`, deciden las claves almacenadas: una clave de acceso se lee como `access_key`, un `roleArn` como `assume_role` y ninguno de los dos como `node_role`. Un `roleArn` tiene la forma `arn:aws:iam::<account>:role/<name>`.

### Identidad del nodo

`node_role` usa la identidad que los SDK de AWS encuentran en el nodo: roles de IAM para cuentas de servicio de EKS (IRSA) o EKS Pod Identity, un rol de tarea de ECS o un perfil de instancia de EC2. Para los conectores nunca se usa una clave estática del entorno del nodo, como `AWS_ACCESS_KEY_ID`.

<Warning>
  La identidad del nodo y su token de identidad web pertenecen al despliegue. Cualquier organización del despliegue puede elegir `node_role` y `web_identity`, así que todo lo que alcanza la identidad del nodo, y todos los roles que confían en el token del nodo, quedan abiertos a los conectores de todas las organizaciones. Concédeles solo el acceso que pueda tener cualquier organización.
</Warning>

### Asumir un rol

`assume_role` solicita a AWS STS una clave del rol con una hora de duración y renueva la clave 5 minutos antes de que expire. Las credenciales base que asumen el rol son la identidad del nodo. En un despliegue que no se ejecuta en AWS, selecciona **Asumir el rol con una clave de acceso en lugar de la identidad del nodo** e introduce la clave de un usuario de IAM.

Cada organización asume roles con su propio ID externo, `molesignal-<organization ID>`, que no se puede cambiar. El formulario lo muestra en **ID externo**, y `GET /api/v1/connectors/aws-external-id` lo devuelve. Exige el ID externo en la política de confianza del rol, para que ninguna otra organización pueda asumir el rol incluso cuando conozca el ARN:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": { "AWS": "<ARN of the node role or IAM user>" },
      "Action": "sts:AssumeRole",
      "Condition": { "StringEquals": { "sts:ExternalId": "molesignal-<organization ID>" } }
    }
  ]
}
```

La sesión se llama `molesignal-<connector ID>`, que es como aparece en AWS CloudTrail. La solicitud va al endpoint regional de STS de la `region` del conector: `us-east-1` cuando la región está vacía, y el dominio `amazonaws.com.cn` para las regiones de China.

### Identidad web

`web_identity` asume el rol con el token de identidad web cuya ruta indica `AWS_WEB_IDENTITY_TOKEN_FILE` del nodo, como el token de cuenta de servicio que EKS proyecta para IRSA. Un conector no puede indicar otro archivo. La política de confianza del rol debe confiar en el proveedor de OIDC que emite el token. En un nodo sin `AWS_WEB_IDENTITY_TOKEN_FILE`, el conector no tiene credenciales.

El token se intercambia en el endpoint regional de STS de la `region` del conector, o en `AWS_ENDPOINT_URL_STS` cuando lo establece el entorno del nodo. Lo mismo se aplica a una identidad de nodo que proviene de IRSA.

## Probar una conexión

**Probar conexión** prueba los ajustes tal como están en el formulario, antes de guardarlos. Un secreto que se deja vacío es el guardado. Cada tipo hace lo mínimo que demuestra que una entrega o una lectura pueden funcionar:

| Tipo | Prueba |
|---|---|
| `s3` | Escribe el objeto `.molesignal-connection-test` bajo el prefijo y lo elimina cuando la política lo permite. |
| `kafka` | Lee los metadatos del tema de los brokers, lo que demuestra la conexión, TLS y la autenticación, y que el tema existe. No escribe ningún mensaje. |
| `http` | Envía un evento marcado como prueba: `"message": "MoleSignal connection test"` y `"molesignal_connection_test": true`. |
| `aws_cloudwatch_logs` | Lee como máximo un evento del último minuto del grupo de logs. No escribe nada en el flujo y deja la posición de lectura donde estaba. |
| `kafka_source` | Lee los metadatos del tema de los brokers, como en `kafka`. No lee ningún mensaje y deja la posición de lectura donde estaba. |
| `s3_source` | Lista un objeto bajo el prefijo, lo que demuestra las credenciales y `s3:ListBucket`. No lee nada y deja la posición de lectura donde estaba. |

Una prueba se abandona a los 25 segundos. A través de la API, `POST /api/v1/connectors/test` recibe el `kind` y el `configJson` que se van a probar. Con el `id` de un conector guardado del mismo tipo, `***` representa el secreto que tiene el conector. Los ajustes que no pueden funcionar responden `400`, igual que al guardar.

```bash
curl -X POST http://localhost:5080/api/v1/connectors/test \
  -H "authorization: Bearer $MS_TOKEN" \
  -H 'content-type: application/json' \
  -d '{
        "id": "<connector id>",
        "kind": "kafka",
        "configJson": {
          "brokers": "b-1.example.com:9096",
          "topic": "logs",
          "tls": true,
          "auth": "sasl_scram_sha_512",
          "saslUsername": "molesignal",
          "saslPassword": "***"
        }
      }'
```

```json
{ "ok": true, "code": "ok", "detail": null, "elapsedMs": 412 }
```

`elapsedMs` es lo que tardó la prueba. Una prueba fallida indica la causa en `code`, y `detail` lleva las palabras de la otra parte, hasta 600 caracteres:

| `code` | Significado |
|---|---|
| `ok` | Conectado. |
| `invalid` | Los ajustes no pueden funcionar, o el conector es una fuente push, que no tiene nada con lo que conectar. |
| `no_credentials` | No se pudieron obtener credenciales de AWS: el nodo no tiene identidad, o ninguna del tipo solicitado. |
| `denied` | La otra parte rechazó las credenciales o lo que estas tienen permitido hacer. |
| `not_found` | El bucket, el tema, el grupo de logs o la dirección no existen. |
| `tls` | Falló el handshake de TLS: un certificado no es de confianza o no se presentó. |
| `unreachable` | No se pudo resolver el host ni conectarse a él. |
| `timeout` | No hubo respuesta a tiempo. |
| `failed` | Cualquier otro fallo. |
