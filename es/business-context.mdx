Las claves de negocio vinculan la telemetría con a quién sirvió: un inquilino, un plan, un nivel de usuario o un grupo de experimento. Una vez
declaradas las claves, la página de servicio de APM divide las solicitudes por ellas, un incidente enumera los valores que su
problema afectó, y el análisis de causa raíz recibe información sobre qué inquilinos fallaron. MoleSignal nunca reescribe datos para
esto: las aplicaciones ponen las claves en su telemetría, y el servidor lee los campos que indica la declaración.

## Declara las claves

Abre **APM → Configuración** y usa la tarjeta **Contexto de negocio**. Cada clave tiene:

| Campo | Notas |
|---|---|
| **Clave** | El nombre que se usa en los enlaces y por Mole Agent: letras minúsculas, dígitos y `_`, como `tenant`. |
| **Etiqueta** | Lo que ven los lectores, como `Tenant`. |
| **Atributo de span** | El campo del flujo de trazas que lo transporta, como `tenant.id`. |
| **Campo de log** | El campo de log que lo transporta. |
| **Campo de RUM** | El campo de RUM, una clave de un campo JSON incluido, como `context.tenant`. |
| **Valores importantes** | Los valores que más importan, como clientes clave, separados por comas. Se destacan siempre que se muestra el impacto de un incidente. |

Una clave designa el campo de al menos una señal; se admiten hasta 8 claves. Gestionar la tarjeta requiere
`apm.settings.manage`. La misma declaración se puede configurar mediante la [API](/es/api/business-context).

## Pon las claves en la telemetría

Los atributos de span y de log se convierten en campos de su flujo en la ingesta, así que una clave definida como atributo se puede
dividir por ella de inmediato. La forma habitual de definirla en cada span y registro de log de una solicitud es el baggage de W3C:
define la clave una vez donde entra la solicitud, y un procesador de baggage la copia en cada span (y,
donde el SDK tenga uno, en cada registro de log) que genera la solicitud, en cada servicio al que llega.

<Warning>
El baggage viaja a cada servicio descendente en las cabeceras de las solicitudes, incluidos los terceros. Copia solo las
claves que declaraste y nunca pongas secretos ni datos personales en el baggage.
</Warning>

| Lenguaje | Qué copia el baggage a los spans |
|---|---|
| Java | El agente Java de OpenTelemetry, o `io.opentelemetry.contrib:opentelemetry-baggage-processor` con autoconfigure: define `otel.java.experimental.span-attributes.copy-from-baggage.include=tenant.id` (y `otel.java.experimental.log-attributes.copy-from-baggage.include` para los logs). |
| Go | `go.opentelemetry.io/contrib/processors/baggagecopy`: `baggagecopy.NewSpanProcessor(filter)` en el proveedor de trazas. |
| Node.js | `@opentelemetry/baggage-span-processor` (`BaggageSpanProcessor`) y `@opentelemetry/baggage-log-record-processor` (`BaggageLogRecordProcessor`). |
| Python | `opentelemetry-processor-baggage`: `BaggageSpanProcessor(predicate)` en el proveedor de trazas. |
| .NET | `OpenTelemetry.Extensions`: el procesador de actividades de baggage, registrado antes de cualquier procesador de exportación. |
| Ruby | La gema `opentelemetry-processor-baggage`. |
| PHP, Rust, Erlang/Elixir | Lee la clave del baggage donde entra la solicitud y defínela como atributo de span y atributo de log de forma manual. |

Cada procesador acepta un predicado que elige las claves que se copian; pasa uno que conserve solo las claves
declaradas en lugar de uno que copie todo. Por ejemplo, en Python:

```python
from opentelemetry.processor.baggage import BaggageSpanProcessor

declared = {"tenant.id", "plan"}
tracer_provider.add_span_processor(BaggageSpanProcessor(lambda key: key in declared))
```

y donde entra la solicitud:

```python
from opentelemetry import baggage, context

token = context.attach(baggage.set_baggage("tenant.id", tenant_id))
```

Para RUM, define la clave en el contexto del SDK del navegador, como `context.tenant`, y nombra ese campo como el
**Campo de RUM** de la clave.

## Dónde se usan las claves

| Página | Qué muestra |
|---|---|
| Página de servicio de [APM](/es/apm) | **Solicitudes por clave de negocio**: solicitudes, tasa de error y P95 de cada valor, valores importantes destacados y un enlace para dividir por cualquier otro campo en la página de Traces. |
| [Incidentes](/es/alerting/incidents#detalles-del-incidente) | **Impacto de negocio**: para cada clave, los valores cuyas solicitudes a los servicios del incidente fallaron en mayor medida cerca de su desencadenante. Se muestra a quienes tengan `streams.query` o `sys.telemetry.read`. |
| [Análisis de causa raíz](/es/alerting/incidents) | Una evidencia de **Impacto de negocio** para cada clave con valores fallidos. |

La vista RED de [Traces](/es/traces) divide por cualquier campo de span, incluidas las claves de negocio, y su
tarjeta **Comparar** indica qué valores de campo diferencian las solicitudes fallidas o lentas.
