Un rol es un conjunto de permisos con nombre. Una política de permisos también lo es, pero se mantiene por separado para que varios
roles puedan asociarla y los tokens de API puedan regirse por ella. En [Usuarios](/es/identity/members#usuarios) se asigna a cada miembro un rol para todo el espacio de trabajo.
Una concesión de acceso otorga a un usuario o equipo un rol para
toda la organización o para determinados recursos, con una fecha de vencimiento opcional. Abre **Identidad y acceso →
Roles**, **Políticas de permisos** o **Concesiones de acceso**.

## Roles

**Roles** muestra los roles integrados y personalizados del espacio de trabajo, las políticas asociadas a cada rol,
los permisos que concede y dónde se usa: miembros, cuentas de servicio, invitaciones y
vinculaciones. Los roles integrados son de solo lectura. Consulta [Roles integrados](/es/identity#roles-predefinidos).

Para crear un rol personalizado:

1. Selecciona **Nuevo rol**.
2. Ingresa una **Clave** con letras minúsculas, dígitos y guiones bajos. No podrás cambiarla después.
3. Ingresa un **Nombre** y una **Descripción**.
4. En **Políticas de permisos**, marca las políticas que quieras asociar al rol. El rol incluye todos los
   permisos de esas políticas y se actualiza cuando cambian.
5. En **Permisos propios**, marca los permisos que el rol necesite además de los que aportan sus políticas. Cada
   permiso indica qué permite. Si una política marcada concede un permiso, este ya aparece marcado junto con
   la política que lo concede y no puedes desmarcarlo aquí.
6. Selecciona **Crear rol**.

Un rol concede sus permisos propios y los de sus políticas. Selecciona un rol personalizado para cambiar sus permisos propios o sus políticas.
**Eliminar** solo borra un rol personalizado si no lo usa ninguna membresía, cuenta de servicio,
invitación ni vinculación. Para consultar roles necesitas `iam.roles.read`; para modificarlos,
`iam.roles.manage`; y para eliminarlos, `iam.roles.delete`.

## Políticas de permisos

**Políticas de permisos** muestra las políticas integradas y personalizadas del espacio de trabajo, con
los permisos de cada una y los roles y tokens que la usan. Un rol puede asociar políticas y un token de API
puede regirse por una de ellas. Consulta [Qué puede hacer un token](/es/identity/tokens#qué-puede-hacer-un-token).

| Política integrada | Permisos |
|---|---|
| **Observador de solo lectura** | Consulta datos de observabilidad, paneles, alertas, calendarios, vistas guardadas, pipelines, funciones, informes, páginas de estado, monitores sintéticos, niveles de servicio y análisis post mortem. |
| **Analista de datos** | Explora datos de observabilidad y crea paneles y vistas guardadas. |
| **Desarrollador de pipelines** | Consulta datos de observabilidad y administra flujos, pipelines y funciones. |
| **Administrador de alertas** | Consulta datos de observabilidad y administra reglas de alerta, calendarios, páginas de estado, monitores sintéticos y análisis post mortem. |
| **Administrador de la organización** | Administra la configuración de la organización, los miembros, los roles, las concesiones de acceso, los tokens de API, las cuentas de servicio y la auditoría, además de las páginas de estado, los monitores sintéticos, los niveles de servicio y los análisis post mortem. |
| **Ingesta de datos** | Escribe datos y notifica despliegues: `logs.write`, `metrics.write`, `traces.write`, `profiles.write` y `apm.deploy`. Los tokens de ingesta se rigen por esta política. |

Las políticas integradas son de solo lectura y se actualizan con el producto. Abre una y selecciona **Copiar como política
personalizada** para crear una a partir de ella.

Para crear una política personalizada:

1. Selecciona **Nueva política**.
2. Ingresa un **Nombre**, una **Clave** con letras minúsculas, dígitos y guiones bajos que no podrás cambiar
   después, y una **Descripción**.
3. En **Permisos**, marca los permisos en **Visual** o escribe el documento en **JSON**.
   Ambas opciones editan el mismo documento. JSON indica el primer error y dónde se encuentra, y enumera
   los permisos que concede un documento válido antes de guardarlo.
4. Selecciona **Crear política**.

El formato de un documento de política se basa en el lenguaje de políticas de AWS IAM:

```json
{
  "Version": "1",
  "Statement": [
    { "Sid": "Dashboards", "Effect": "Allow", "Action": "dashboards.*" },
    { "Effect": "Allow", "Action": ["streams.read", "streams.query"] }
  ]
}
```

- `Version` es `"1"` y la política debe conceder al menos un permiso.
- `Effect` siempre es `"Allow"`: una política solo concede permisos y no puede denegarlos.
- `Action` especifica un permiso o una lista de permisos. `*` representa cualquier secuencia de caracteres, así que
  `dashboards.*` incluye todos los permisos de paneles y `*` incluye todos los permisos de la organización. Una acción
  que no coincide con ningún permiso no es válida.
- `Sid` es un nombre opcional para la declaración.
- No se admiten `Resource`, `Condition`, `Principal` ni `NotAction`: la política se aplica a toda la
  organización. Para otorgar un rol sobre recursos específicos o con condiciones, usa una
  [concesión de acceso](#concesiones-de-acceso).

La política guarda los permisos que concede su documento en ese momento. Un patrón también abarca los permisos
que se agreguen al catálogo más adelante: se incorporan a la política cuando arranca MoleSignal. Al marcar permisos en **Visual**,
el editor avisa antes de convertir un documento con patrones, un `Sid` o varias declaraciones en una sola declaración que enumera cada
permiso.

Modificar una política actualiza de inmediato todos los roles que la tienen asociada y todos los tokens que se rigen por ella.
**Eliminar** solo borra una política personalizada si ningún rol la tiene asociada y ningún token vigente se rige por ella.
Los tokens revocados o vencidos que se regían por esa política conservan en una lista los permisos que tenían. Para consultar políticas,
necesitas `iam.policies.read`; para modificarlas, `iam.policies.manage`; y para eliminarlas, `iam.policies.delete`.

## Concesiones de acceso

Una concesión de acceso vincula un rol a una identidad dentro de una organización y limita su alcance a determinados
recursos. Usa una concesión para dar acceso a una persona o equipo concretos, o limitarlo a un recurso, en lugar de ampliar
un rol de alcance general.

1. Abre **Concesiones de acceso** y selecciona **Otorgar acceso**.
2. **Identidad**: elige **Usuario** o **Equipo** y selecciona la identidad correspondiente.
3. **Organización**: muestra el espacio de trabajo actual como referencia.
4. **Alcance de los recursos**: elige **Toda la organización** o un tipo de recurso (**Panel** o **Flujo**) y selecciona
   un recurso o **Todos los recursos de este tipo**.
5. **Rol y permisos**: selecciona el rol que otorga la concesión.
6. **Restricciones**: si lo necesitas, indica un **Entorno** con el que las solicitudes deban coincidir exactamente, como `prod`,
   y una fecha y hora de vencimiento en **Vence el**.
7. Selecciona **Conceder acceso**.

**Eliminar** pone fin de inmediato a una concesión. Para consultar concesiones necesitas `iam.grants.read`; para crearlas o
eliminarlas, necesitas `iam.grants.manage`.

## Compartir recursos entre organizaciones

Al compartir recursos entre organizaciones, das a otra organización acceso a determinados recursos de la organización actual. El acceso
es explícito y no es transitivo: solo se aplica a la organización y los recursos seleccionados, y
no se hereda ni se transfiere.

1. En **Concesiones de acceso**, selecciona **Compartir entre organizaciones**.
2. Elige la **Organización de destino**.
3. Elige el tipo de recurso, **Panel** o **Flujo**, y selecciona el recurso.
4. Elige los permisos: `dashboards.read` y `dashboards.edit` para un panel, o `streams.read`
   y `streams.query` para un flujo.
5. Si lo necesitas, define el vencimiento en **Vence el** y selecciona **Compartir recurso**.

El acceso compartido tiene el estado **Pendiente de aceptación** al crearse. Cuando un administrador de la organización de destino selecciona
**Aceptar** en **Concesiones de acceso** de esa organización, el acceso pasa a **Activo**. Cualquiera de las organizaciones puede seleccionar **Revocar**
para poner fin al acceso. Para compartir recursos, aceptar el acceso o revocarlo, necesitas `iam.cross_org.manage`.

y las políticas personalizados pueden combinar cualquier permiso de la organización. Las pestañas de cada módulo muestran las páginas que el rol permite abrir.
El módulo se abre en la primera de esas páginas, así que basta con tener permiso para acceder a una de ellas.

## API de roles, políticas y concesiones de acceso

| Operación | Endpoint | Permiso |
|---|---|---|
| Listar el catálogo de permisos | `GET /api/v1/iam/permissions` | `iam.roles.read` o `iam.policies.read` |
| Listar los roles | `GET /api/v1/roles` | `iam.roles.read` |
| Crear un rol personalizado | `POST /api/v1/roles` | `iam.roles.manage` |
| Actualizar un rol personalizado | `PATCH /api/v1/roles/{id}` | `iam.roles.manage` |
| Eliminar un rol personalizado que no esté en uso | `DELETE /api/v1/roles/{id}` | `iam.roles.manage` |
| Listar las políticas de permisos o consultar una | `GET /api/v1/iam/policies`, `GET /api/v1/iam/policies/{id}` | `iam.roles.read` |
| Crear una política personalizada | `POST /api/v1/iam/policies` | `iam.roles.manage` |

| Listar o crear concesiones de acceso | `GET /api/v1/iam/role-bindings`, `POST /api/v1/iam/role-bindings` | `iam.policies.read`, `iam.policies.manage` |
| Eliminar una concesión de acceso | `DELETE /api/v1/iam/role-bindings/{id}` | `iam.policies.manage` |
| Listar o crear accesos compartidos entre organizaciones | `GET /api/v1/iam/cross-org-grants`, `POST /api/v1/iam/cross-org-grants` | `iam.policies.read`, `iam.policies.manage` |
| Aceptar o revocar un acceso compartido | `POST /api/v1/iam/cross-org-grants/{id}/accept`, `POST /api/v1/iam/cross-org-grants/{id}/revoke` | `iam.policies.manage` |

El cuerpo de un rol incluye sus propios `permissions` y los `policyIds` de las políticas asociadas. La respuesta agrega
`effectivePermissions`, que incluye todos los permisos que otorga el rol. El cuerpo de una política incluye `key` (solo al crearla),
`name`, `description` y `document`. La respuesta agrega `builtin`, los `permissions` que resultan de evaluar la política y
`usage`, que indica qué roles tienen asociada la política y qué tokens activos se rigen por ella. Si el documento no es
válido, la API devuelve `400` e indica dónde está el problema, por ejemplo:
``Statement[0].Action[1]: no permission is called `alerts.rules.reed` ``. Si intentas eliminar una política que aún está en uso, la API devuelve
`409`.
