El inicio de sesión único permite usar cuentas del directorio de la empresa o de una plataforma común en lugar
de una contraseña de MoleSignal. Abre **Identidad y acceso → Proveedores de SSO** y **Dominios de correo electrónico**. Para consultar
los proveedores y los dominios, necesitas `org.sso.read`; para modificarlos, necesitas
`org.sso.manage`.

## Antes de agregar un proveedor

Configura `[http].external_url` con la dirección pública de MoleSignal. La **URI de redirección** de OIDC y
OAuth 2.0, la **URL del servicio consumidor de aserciones (ACS)** de SAML y el **ID de entidad del SP** predeterminado se derivan
de esa dirección. El proveedor de identidad debe usar esos valores al responder. MoleSignal guarda la configuración del proveedor en la base de datos
y la aplica sin reiniciar.

## Agregar un proveedor

1. Abre **Proveedores de SSO** y selecciona **Nuevo proveedor**.
2. Elige la plataforma en **Plataformas populares** o **Directorios empresariales**, o elige **OIDC**,
   **OAuth 2.0**, **SAML** o **LDAP** en **Protocolos genéricos**. Selecciona **Cambiar plataforma** para
   elegir otra opción.
3. Si la plataforma ofrece más de un protocolo, elige uno en **Protocolo**.
4. Completa los campos que solicita la plataforma y registra la **URI de redirección** o la **URL del servicio consumidor de aserciones
   (ACS)** que muestra el formulario en el proveedor de identidad, según las indicaciones del formulario.
5. Revisa la [asignación de campos de identidad](#asignación-de-campos-de-identidad), la [vinculación de roles](#vinculación-de-roles)
   y el [ámbito de inicio de sesión](#ámbito-de-inicio-de-sesión).
6. Selecciona **Crear proveedor**.

## Plataformas preconfiguradas

Una plataforma preconfigurada completa los endpoints, los ámbitos y la asignación de campos. En una plataforma OIDC u OAuth 2.0
solo necesitas los campos siguientes, además del **ID de cliente** y el **Secreto de cliente**. Consulta los endpoints que
se derivan de esos campos en **Endpoints y ámbitos**.

| Plataforma | Protocolos | Campos | Grupos |
|---|---|---|---|
| Google | OIDC, SAML | Ningún campo adicional para OIDC | Ninguno para OIDC; pertenencia a grupos para SAML |
| Microsoft Entra ID | OIDC, SAML | **ID de directorio (inquilino)** y **Nube** (global u operada por 21Vianet) | ID de objeto de los grupos |
| GitHub | OAuth 2.0 | **Despliegue**; **Host del servidor** para GitHub Enterprise Server | Organizaciones (`my-org`) y equipos (`my-org/sre`) |
| GitLab | OIDC | **URL de la instancia**, `https://gitlab.com` de forma predeterminada | `groups` |
| Okta | OIDC, SAML | **Dominio de Okta** y **Servidor de autorización** | La declaración `groups` |
| Auth0 | OIDC | **Dominio del inquilino** | Una declaración personalizada |
| Keycloak | OIDC | **URL del servidor** y **Dominio de autenticación** | `groups` de un mapeador de pertenencia a grupos (Group Membership) |
| authentik | OIDC | **URL del servidor** y **Slug de la aplicación** | `groups` |
| Feishu / Lark | OAuth 2.0 | **Edición** (Feishu o Lark) | Ninguno |
| AD FS | SAML | Metadatos del IdP | Token-Groups |
| JumpCloud | SAML | Metadatos del IdP | `memberOf` |
| Active Directory, OpenLDAP, FreeIPA | LDAP | URL del servidor, DN base y cuenta de búsqueda | `memberOf` |

MoleSignal consulta GitHub de una forma fija: el sujeto es el ID numérico de la cuenta, el correo electrónico es la dirección principal
verificada y la consulta de organizaciones y equipos requiere `read:org`. Si una organización
restringe el acceso de las aplicaciones OAuth, alguien con el rol de propietario debe aprobar la aplicación para que pueda
consultar las organizaciones y los equipos. En Feishu, concede a la aplicación el permiso para leer el correo electrónico de los usuarios en la plataforma abierta.

## Protocolos genéricos

| Protocolo | Configuración |
|---|---|
| OIDC | **URL del emisor**, **URL de autorización**, **URL del token**, **URL de UserInfo**, **URL de JWKS**, **ID de cliente**, **Secreto de cliente** y **Ámbitos** separados por espacios. Después de ingresar la **URL del emisor**, selecciona **Detectar** para completar los demás endpoints a partir de `.well-known/openid-configuration`. |
| OAuth 2.0 | Para proveedores de identidad que no emiten un token de ID: **URL de autorización**, **URL del token**, **URL de UserInfo**, **ID de cliente**, **Secreto de cliente** y **Ámbitos**. Después del inicio de sesión, MoleSignal consulta la **URL de UserInfo** con el token de acceso e identifica la cuenta en la respuesta mediante la asignación de campos. |
| SAML | **ID de entidad del SP**, **ID de entidad del IdP**, **URL de SSO del IdP** y **Certificado de firma del IdP (PEM)**. En **Metadatos del IdP**, ingresa la URL de los metadatos o selecciona **Pegar XML** y pega los metadatos. Luego selecciona **Importar** para completar los últimos tres campos. Solo se admite una URL de inicio de sesión con HTTP-Redirect. |
| LDAP | **URL del servidor LDAP**: `ldaps://` o `ldap://` con **StartTLS** activado. **DN base de usuarios**, por ejemplo `ou=people,dc=example,dc=com`. Un **Filtro de búsqueda de usuarios** que contiene `{username}`, cuyo valor se escapa antes de la búsqueda. Un **DN de enlace para la búsqueda** y su **Contraseña de enlace para la búsqueda**: deja ambos campos vacíos solo si el directorio permite búsquedas anónimas. |

Al editar un proveedor, deja vacío el campo **Secreto de cliente** o **Contraseña de enlace para la búsqueda** para conservar el valor
guardado.

## Asignación de campos de identidad

La **Asignación de campos de identidad** indica a MoleSignal dónde leer cuatro campos de la identidad:

| Campo de MoleSignal | OIDC y OAuth 2.0 | SAML | LDAP |
|---|---|---|---|
| **Identificador estable del sujeto** | Una declaración o un campo JSON. Se admiten rutas con puntos como `realm_access.roles`. | El nombre de un atributo o `NameID` para el sujeto de la aserción. | Un atributo o `dn` para el DN de la entrada. |
| **Correo electrónico** | Una declaración o un campo JSON. | El nombre de un atributo. | Un atributo. |
| **Nombre visible** | Una declaración o un campo JSON. | El nombre de un atributo. | Un atributo. |
| **Grupos** | Una declaración o un campo JSON. | El nombre de un atributo. | Un atributo. |

En OIDC y OAuth 2.0, separa varias fuentes con `|`. MoleSignal usa la primera que contiene un valor, por
ejemplo `email | preferred_username`. MoleSignal rechaza el inicio de sesión si no hay una dirección de correo electrónico válida.

## Vinculación de roles

**Grupo externo → rol** muestra las asignaciones de un valor de **Grupos** a un rol de MoleSignal. Selecciona
**Agregar asignación**, ingresa el **Valor del grupo externo**, por ejemplo `platform-admins`, y elige el
rol. La cuenta recibe el rol de cada asignación que coincide. MoleSignal sincroniza los roles en
cada inicio de sesión.

El **Rol predeterminado** se aplica cuando ninguna asignación coincide. Si no lo configuras, MoleSignal aplica el rol asignado al unirse
por autoservicio. Si una plataforma no envía grupos, solo se usa el rol predeterminado.

## Ámbito de inicio de sesión

Si configuras **Grupos autorizados para iniciar sesión**, solo las cuentas de uno de esos grupos pueden iniciar sesión a través del
proveedor.

Cualquiera puede crear una cuenta en Google, GitHub.com, GitLab.com y los endpoints de Microsoft que no dependen de un inquilino
específico. Solo puedes habilitar un proveedor de este tipo si el espacio de trabajo tiene [dominios de correo electrónico](#dominios-de-correo-electrónico)
o si el proveedor tiene **Grupos autorizados para iniciar sesión**. El inicio de sesión solo admite direcciones de correo electrónico que
el proveedor de identidad haya verificado. Si eliminas todos los dominios de correo electrónico después de habilitarlo, el proveedor
rechaza los inicios de sesión.

## Prueba de inicio de sesión

Comprueba el proveedor antes de usarlo: selecciona **Prueba** en la lista de proveedores o en la
configuración del proveedor. La prueba realiza un inicio de sesión real con la configuración guardada y no deja cambios: no
inicia ninguna sesión, no crea ni vincula cuentas, no cambia roles y mantiene intacta la sesión
actual. También puedes probar un proveedor deshabilitado, así que haz la prueba antes de habilitarlo. La prueba requiere
`org.sso.manage`, no se puede iniciar con un token de API y admite hasta 10 pruebas por minuto por proveedor.

| Proveedor | Cómo se ejecuta la prueba |
|---|---|
| OIDC, OAuth 2.0, SAML | Se abre una pestaña nueva que lleva al proveedor de identidad y luego vuelve a la página de resultados. La URI de redirección o la URL de ACS es la que está registrada para los inicios de sesión. |
| LDAP | Ingresa una cuenta del directorio y su contraseña. La prueba realiza una operación de enlace real, por lo que una contraseña incorrecta cuenta para la política de bloqueo del directorio y para los límites de inicio de sesión de esta instancia. La prueba no guarda la contraseña. |

La página de resultados muestra:

- **Si la prueba se completó correctamente.** Si falló, muestra el motivo, qué hacer y el mensaje del servidor o del
  proveedor de identidad. La prueba también falla si una regla impide el inicio de sesión, por ejemplo, por los grupos autorizados, los dominios
  de correo electrónico o una cuenta deshabilitada.
- **Qué devolvió el proveedor:** el correo electrónico, el nombre, el identificador del sujeto y los grupos.
- **Qué ocurriría en un inicio de sesión real:** con qué cuenta se continuaría (inicio de sesión en una cuenta existente, confirmación de la vinculación por parte del titular o
  creación de una cuenta) y qué roles quedarían asignados, incluidos los que reemplazarían a los anteriores.

Si el proveedor de identidad muestra su propia página de error, el navegador no vuelve. Después de 10
minutos, el resultado indica que no hubo respuesta. La causa habitual es que el proveedor no tiene registrada
la URI de redirección.

El resultado solo es válido para la configuración con la que se ejecutó la prueba. Cambiar los puntos de conexión, un secreto, las asignaciones o
los grupos autorizados invalida el resultado y la lista muestra **La configuración cambió**. Cambiar el nombre, habilitar o deshabilitar
el proveedor no invalida el resultado. Cada proveedor conserva sus últimas 20 pruebas. La prueba no muestra, almacena ni registra tokens, aserciones, secretos ni
contraseñas. El registro de auditoría incluye cada prueba como `org.sso_provider.test`, sin
incluir la identidad.

## Requisitos de inicio de sesión

Los **Requisitos de inicio de sesión**, en la parte superior de **Identidad y acceso → Proveedores de SSO**, definen qué condiciones debe cumplir el inicio de sesión para entrar en este
espacio de trabajo. Para cambiarlos, se requiere `org.sso.manage`. Los cambios se aplican a todas las sesiones en un máximo de 15 minutos:
si una sesión no cumple los requisitos, termina cuando le toca renovarse y es necesario volver a iniciar sesión. El registro de auditoría incluye los cambios.

| Requisito | Efecto |
|---|---|
| **Requerir autenticación multifactor** | Para entrar en el espacio de trabajo, la sesión requiere [autenticación multifactor](/es/identity/mfa). Una sesión iniciada mediante el proveedor OIDC, OAuth 2.0 o SAML de este espacio de trabajo cumple el requisito: el proveedor de identidad se encarga de la autenticación multifactor. Ni LDAP ni el inicio de sesión único de otro espacio de trabajo cumplen el requisito. |
| **Permitir solo el inicio de sesión único** | Solo se puede acceder a través del proveedor OIDC, OAuth 2.0 o SAML de este espacio de trabajo. No se admiten contraseñas de cuenta, claves de acceso ni LDAP. El usuario raíz es la excepción: puede acceder si el proveedor de identidad no está disponible. Para activar este requisito, debe haber al menos un proveedor compatible habilitado. Mientras el requisito esté activo, no se puede deshabilitar ni eliminar el último de esos proveedores. Si activas el requisito sin que ningún proveedor habilitado haya superado una [prueba de inicio de sesión](#prueba-de-inicio-de-sesión) con su configuración actual, MoleSignal muestra una advertencia y solicita el nombre del espacio de trabajo. El evento de auditoría registra `sso_tested: false`. |

Si el inicio de sesión no cumple los requisitos:

| Caso | Resultado |
|---|---|
| Inicio de sesión con una cuenta en varios espacios de trabajo | La sesión abre el primer espacio de trabajo que permite el acceso. |
| Inicio de sesión cuando solo falta la autenticación multifactor | Configura una clave de acceso o una aplicación de autenticación en el momento. La sesión incorpora el segundo factor y la página muestra los códigos de recuperación. |
| Inicio de sesión con una cuenta que solo pertenece a espacios de trabajo que exigen el inicio de sesión único | La página de inicio de sesión deniega el acceso e indica el motivo. |
| Cambio a un espacio de trabajo que requiere autenticación multifactor | Si ya hay un segundo factor configurado, verifícalo una vez en el momento. Si no hay ninguno, configúralo primero en **Seguridad e inicio de sesión**. |
| Cambio a un espacio de trabajo que solo permite el inicio de sesión único | MoleSignal ofrece iniciar sesión mediante los proveedores de ese espacio de trabajo. |
| Registro de autoservicio | MoleSignal rechaza el registro en los espacios de trabajo que solo permiten el inicio de sesión único. Si el espacio de trabajo exige autenticación multifactor, MoleSignal crea la cuenta y solicita configurarla al iniciar sesión. |
| Inicio de sesión con una cuenta desde un cliente de base de datos | MoleSignal rechaza el inicio de sesión si se aplica cualquiera de los dos requisitos. Los clientes que ya están conectados dejan de funcionar en la siguiente solicitud. Usa un [token de API](/es/identity/tokens). |
| Tokens de API | Los requisitos no afectan a los tokens de API. |

Mientras algún espacio de trabajo de la cuenta requiera autenticación multifactor, el titular no puede eliminar el último
segundo factor. El [restablecimiento por parte de un administrador](/es/identity/mfa#restablecimiento-por-parte-de-un-administrador) sigue disponible,
y el miembro configura un segundo factor en el siguiente inicio de sesión.

El requisito de la organización de la plataforma está en **Configuración → Requisitos de inicio de sesión**, en la organización
`_sys`. Para cambiarlo, se requiere `sys.settings.signin.manage`. La única opción es **Requerir autenticación multifactor**.

## Qué ocurre al iniciar sesión

La página de inicio de sesión muestra una fila con el logotipo de la plataforma de cada proveedor habilitado. Para un proveedor
LDAP, selecciona su fila e ingresa el nombre de usuario del directorio y la contraseña, uno a la vez.

1. El navegador abre la página del proveedor de identidad y vuelve a MoleSignal después de la autenticación.
2. El proveedor confirma la identidad: MoleSignal verifica el token de ID de OIDC con una clave del JWKS (RSA, EC
   o EdDSA) o con el secreto del cliente (HMAC). Con OAuth 2.0, consulta el punto de conexión de usuario. MoleSignal lee
   los campos asignados.
3. MoleSignal deniega el acceso a las cuentas que no pertenecen a los **Grupos autorizados para iniciar sesión**.
4. Si la identidad ya inició sesión antes, MoleSignal inicia sesión en la cuenta vinculada. MoleSignal
   encuentra la cuenta por el proveedor y el identificador del sujeto de la identidad, no por el correo electrónico.
5. Si una identidad inicia sesión por primera vez con el correo electrónico de una cuenta de MoleSignal existente, el inicio de sesión queda pendiente
   hasta que el titular confirme la vinculación. Consulta [Vincular una cuenta existente](#vincular-una-cuenta-existente).
6. Si no existe una cuenta de MoleSignal, MoleSignal crea una cuando el correo electrónico cumple la restricción de
   [dominios de correo electrónico](#dominios-de-correo-electrónico) del espacio de trabajo.
7. Si la cuenta aún no pertenece al espacio de trabajo del proveedor, MoleSignal la agrega con los roles asignados o con
   el rol predeterminado.
8. Si la cuenta ya pertenece al espacio de trabajo, los roles de las asignaciones que coinciden reemplazan a los anteriores. Una cuenta deshabilitada
   no puede iniciar sesión.
9. El navegador vuelve a la página de inicio de sesión, completa el inicio de sesión y abre la página solicitada antes
   de iniciar sesión. Si el inicio de sesión falla, la página de inicio de sesión indica el motivo.

## Vincular una cuenta existente

Cada proveedor solo avala a los miembros de su propio espacio de trabajo. Por eso, la dirección de correo que envía no basta para
acceder a una cuenta existente: la cuenta podría pertenecer a otra persona con la misma
dirección. La primera vez que alguien inicia sesión con una identidad que usa el correo de una cuenta existente, la página de
inicio de sesión solicita al titular de la cuenta que confirme la vinculación en el mismo navegador.

| Método | Cuándo está disponible | Cómo usarlo |
|---|---|---|
| **Contraseña** | La cuenta tiene una contraseña. | Ingresa la contraseña de la cuenta. |
| **Código por correo** | La instancia puede [enviar correo electrónico](/es/configuration#alertas-y-correo-electrónico). | Selecciona **Enviar código** e ingresa los seis dígitos del correo. Se puede solicitar un código por minuto. |

El código solo funciona en la página que lo solicitó. Si recibes un código por correo sin haber intentado iniciar
sesión, ignóralo. Después de cinco intentos fallidos o de 30 minutos, vuelve a iniciar sesión con el
proveedor. Una vez que confirmes la vinculación, podrás iniciar sesión directamente con esa
identidad. Si la cuenta tiene [autenticación multifactor](/es/identity/mfa), después de confirmar, completa el
segundo paso (con una clave de acceso, el autenticador o un código de recuperación) para vincular la identidad. Si la cuenta no tiene contraseña y la instancia no puede enviar correos, no puedes confirmar la vinculación aquí:
inicia sesión con el método anterior o solicita a un administrador que configure el correo electrónico.

Si el proveedor de un espacio de trabajo crea una cuenta, la cuenta permanece en ese espacio hasta que se verifique su dirección de correo:
ni un administrador ni otro proveedor pueden agregarla a otro espacio de trabajo. Para verificar la dirección,
restablece la contraseña desde el enlace enviado por correo o confirma la vinculación con un código por correo. Esta restricción no se aplica a las cuentas
que se crean mediante Google, GitHub.com, GitLab.com o los endpoints de Microsoft que no están asociados a un inquilino específico,
porque estos proveedores solo aceptan direcciones de correo verificadas.

Consulta y desvincula tus identidades vinculadas en
[Configuración de la cuenta → Seguridad e inicio de sesión](/es/account#seguridad-y-sesiones).

## Administrar proveedores

La lista muestra la plataforma y el tipo de cada proveedor, si está habilitado, el estado del
[inicio de sesión de prueba](#prueba-de-inicio-de-sesión) y la fecha del último cambio.

| Acción | Efecto |
|---|---|
| **Prueba** | Realiza un [inicio de sesión de prueba](#prueba-de-inicio-de-sesión). |
| **Editar** | Cambia la configuración y las asignaciones. |
| **Desactivar** / **Habilitar** | Al desactivar un proveedor, deja de aparecer en la página de inicio de sesión y rechaza los intentos de inicio de sesión. |
| **Eliminar** | Elimina el proveedor. Quienes dependan de ese proveedor ya no podrán usarlo para iniciar sesión. |

## Dominios de correo electrónico

**Dominios de correo electrónico** limita qué direcciones de correo pueden unirse al espacio de trabajo mediante una
[invitación](/es/identity/members#invitaciones) o el inicio de sesión único. Selecciona **Agregar dominio** e ingresa un
dominio como `example.com`. Mientras la lista esté vacía, se admite cualquier dirección, pero no puedes habilitar
proveedores que acepten cuentas públicas. Selecciona **Quitar** para eliminar un dominio de la lista.
