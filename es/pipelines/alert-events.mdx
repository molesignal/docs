Un **flujo de procesamiento de alertas** se ejecuta sobre los eventos de alerta antes de que se abran sus incidentes. Sus pasos pueden reescribir el título del incidente, cambiar su nivel de gravedad, agregar o quitar etiquetas y anotaciones, indicar los servicios afectados o descartar el evento para que no se abra ningún incidente. El [enrutamiento](/es/alerting/routing) y las notificaciones actúan después sobre el incidente tal como lo dejaron los flujos de procesamiento de alertas.

Un evento de alerta proviene de uno de estos cuatro orígenes:

| Origen | Eventos |
|---|---|
| **Reglas de alerta** | Se activa una [regla de alerta](/es/alerting/rules). |
| **Orígenes externos** | Un [origen de alertas](/es/alerting/sources) recibe una alerta de otro sistema. |
| **Comprobaciones sintéticas** | Una [comprobación sintética](/es/synthetics#incidentes-de-alerta) falla o no devuelve resultados. |
| **Sin datos** | Una regla abre un [incidente por falta de datos](/es/alerting/rules#recuperación-y-datos-faltantes). |

Si abres un incidente manualmente, no pasa por los flujos de procesamiento de alertas antes de abrirse.

Un flujo de procesamiento también puede ejecutarse [antes de una notificación](#antes-de-una-notificación): trabaja sobre una copia del evento y solo modifica lo que envía una política de notificación.

## Crear un flujo de procesamiento de alertas

Abre **Canalizaciones**, selecciona **Nuevo pipeline** y configura **Modo de ejecución** como **Eventos de alerta**. El **Tipo de señal** muestra **Eventos de alerta** y, en la configuración, se define un [**Orden**](#orden) en lugar de un horario. El flujo tiene tres nodos:

| Nodo | Significado |
|---|---|
| **Eventos de alerta** | Los eventos de alerta que procesa el flujo. Consulta [Condiciones](#condiciones). |
| **En proceso** | Los pasos, en el orden en que se ejecutan. Consulta [Pasos](#pasos). |
| **Aplicar cambios al incidente** | El incidente se abre con los cambios que los pasos aplicaron al evento. |

**Prueba** ejecuta los pasos sobre un evento de alerta de ejemplo antes de guardar. Los pasos lo tratan como un evento de una regla de alerta cuyo incidente está por abrirse: `%source` es `rule` y `%event` es `opened`. Edita el **Evento de ejemplo** para probar otros valores y selecciona **Ejecutar prueba**. El resultado muestra el evento después de cada paso o el paso que lo descartó. La prueba no almacena nada ni hace llamadas externas: los pasos **Resumen con IA** y **Agregar resultados de la consulta** escriben `…` en sus anotaciones, y el paso **Llamar a una API** deja pasar el evento sin cambios y muestra la indicación **no se invoca durante la prueba**.

**Usar un evento de alerta reciente** muestra los 20 incidentes más recientes de los últimos 7 días a quienes tengan el permiso `alerts.incidents.read`. Al seleccionar uno, su evento rellena el **Evento de ejemplo** y los pasos leen la regla y el origen. Se usa el incidente tal como quedó almacenado, por lo que ya refleja los cambios que aplicaron los flujos de procesamiento de alertas cuando se abrió.

El interruptor **Procesar eventos de alerta** de la configuración activa o desactiva el flujo: si está desactivado, deja pasar todos los eventos de alerta. Selecciona **Crear pipeline** para guardar. Los cambios guardados llegan a todos los nodos en un máximo de 10 segundos.

## Condiciones

Selecciona el nodo **Eventos de alerta** para elegir los eventos que procesa el flujo:

- **Orígenes**: **Reglas de alerta**, **Orígenes externos**, **Comprobaciones sintéticas** y **Sin datos**. Un incidente de una regla por falta de datos cuenta como **Sin datos**, no como **Reglas de alerta**, y un incidente de una comprobación sintética sin resultados cuenta como **Comprobaciones sintéticas**.
- **Niveles de gravedad**: **Crítico**, **Error**, **Advertencia** e **Información**.
- **Etiquetas**: **Agregar una condición de etiqueta** agrega una etiqueta y un valor. El evento debe tener cada etiqueta con ese valor exacto.
- **Tiempo**: **En cualquier momento**, **Solo dentro de este horario** o **Solo fuera de este horario**. Define intervalos semanales en una sola zona horaria. El flujo evalúa la condición en el momento en que se abre el incidente. Por ejemplo, descarta un tipo de alerta solo durante las dos horas que dura una tarea nocturna de ETL.

**Cuándo**, encima de las condiciones, indica cuándo se ejecuta el flujo: **Antes de que se abra el incidente** (la opción predeterminada) o [**Antes de una notificación**](#antes-de-una-notificación).

Si no marcas ninguna opción en una lista, se incluyen todos los orígenes o todos los niveles de gravedad. Un flujo sin condiciones procesa todos los eventos de alerta. Si un evento no cumple las condiciones, pasa por el flujo sin cambios.

## Orden

Los flujos de procesamiento de alertas se ejecutan uno tras otro, empezando por el de menor **Orden**. Los flujos con el mismo orden se ejecutan por orden de nombre. Cada flujo recibe el evento tal como lo dejaron los anteriores y evalúa sus condiciones con ese evento. Así, si un flujo aumenta el nivel de gravedad de un evento, este puede pasar a cumplir las condiciones de un flujo posterior.

## Pasos

**Agregar paso** ofrece los pasos de análisis y de gestión de campos de otros pipelines, incluido **Consultar una tabla de enriquecimiento**, además de **Filtrar eventos**, **Resumen con IA**, **Llamar a una API**, **Agregar resultados de la consulta** y **VRL personalizado**. Consulta [Pasos de procesamiento](/es/pipelines#pasos-de-procesamiento). En un pipeline de alertas, **Cambiar nombres según un patrón** y **Conservar solo estos campos** operan inicialmente sobre `labels`. Un pipeline de alertas no realiza muestreo ni enrutamiento. Al convertir un pipeline en uno de alertas, elimina los pasos **Muestra** o **Dirigir a un flujo** que tenga antes de guardarlo.

### El evento de alerta

Los pasos reciben el evento de alerta en formato JSON:

```json
{
  "summary": "Checkout error rate above 5%",
  "severity": "error",
  "labels": { "service": "checkout", "env": "prod", "host_name": "web-01" },
  "annotations": { "runbook": "https://wiki.example.com/checkout" },
  "affected_services": ["checkout"]
}
```

| Campo | Contenido | Qué puede establecer un paso |
|---|---|---|
| `summary` | El título del incidente. | Texto no vacío. El pipeline trunca el texto a 512 caracteres. |
| `severity` | La severidad del incidente. | `info`, `warning`, `error` o `critical`, sin distinguir entre mayúsculas y minúsculas. El pipeline interpreta `warn` como `warning` y `crit` como `critical`. |
| `labels` | Las etiquetas del incidente. | Un objeto con valores de texto. El pipeline convierte los números y los valores booleanos en texto, y elimina la etiqueta si el valor es `null`. |
| `annotations` | Las anotaciones del incidente. | Lo mismo que para `labels`. |
| `affected_services` | Los nombres de los servicios afectados. | Una lista de nombres. El pipeline descarta los nombres repetidos y vacíos. |

El pipeline ignora los campos adicionales que agregue un paso y conserva el valor de los campos que un paso elimine. Asigna `.labels = {}` para borrar las etiquetas. Un valor que incumpla estas reglas, como un objeto dentro de `labels`, hace fallar el pipeline. Consulta [Qué ocurre con un evento](#qué-ocurre-con-un-evento).

Las etiquetas que establece MoleSignal, como `alert.source` y `external.kind`, conservan sus valores sin importar lo que haga un paso, porque identifican el origen del incidente. Los pasos pueden leerlas.

### Origen del evento

Los pasos leen el origen del evento a partir de los metadatos. Estos valores no pasan a ser campos del incidente.

| Metadatos | Valor |
|---|---|
| `%source` | `rule`, `external`, `synthetic` o `no_data`. |
| `%rule_id` | El ID de la regla, de la fuente de alertas o de la comprobación sintética. |
| `%rule_name` | El nombre de la regla, de la fuente de alertas o de la comprobación sintética. |
| `%event` | `opened` antes de que se abra el incidente y `severity_changed` cuando la fuente vuelve a disparar una alerta mientras el incidente sigue abierto. Consulta [Cambios de severidad](#cambios-de-gravedad). |

```ruby
# alerts from staging page no higher than warning
if .labels.env == "staging" && (.severity == "critical" || .severity == "error") {
  .severity = "warning"
}

# the team that owns the host, from the extend table host_owner
owner = lookup("host_owner", .labels.host_name)
if is_object(owner) {
  .labels.team = owner.team
}

# a known false alarm opens no incident
if %rule_name == "Disk inode usage" && .labels.mount == "/boot" {
  abort
}
```

La etiqueta `team` que establece el segundo paso permite dirigir el incidente a ese equipo. Consulta [Orden de enrutamiento](/es/alerting/routing#orden-de-enrutamiento). `lookup` y `geoip_lookup` funcionan en los pipelines de alertas igual que en cualquier paso de VRL. Consulta [Consultar tablas y direcciones IP](/es/functions#consulta-tablas-y-direcciones-ip).

### Resumen con IA

Un paso **Resumen con IA** envía al modelo de la organización el evento de alerta tal como lo dejaron los pasos anteriores, junto con la **Instrucción**. El paso escribe la respuesta en la anotación indicada en **Anotación**, que de forma predeterminada es `ai_summary`. Ejemplo de instrucción:

```text
Summarize this alert for the on-call engineer in two sentences: what is wrong, and what to check first.
```

- El paso consulta al modelo una sola vez, cuando se abre el incidente. Un [cambio de severidad](#cambios-de-gravedad) no genera otra consulta.
- El paso usa el **Modelo predeterminado** del [proveedor de modelos](/es/agent#configura-un-proveedor-de-modelos) habilitado que tiene una clave de API y cuya configuración se actualizó más recientemente. La respuesta no supera el **Máximo de tokens de salida** del proveedor, o 512 tokens si no hay un máximo configurado.
- El paso envía al proveedor del modelo el título, la severidad, las etiquetas, las anotaciones y los servicios afectados de la alerta.
- Las llamadas consumen el [presupuesto diario de tokens](/es/agent#uso-y-presupuesto) de la organización y aparecen como **Funciones LLM** en el desglose de uso por origen. `[functions].llm_eval_enabled` no se aplica a estas llamadas.
- Si el modelo no puede responder porque no hay un proveedor configurado, se agotó el presupuesto diario o falló la llamada, el paso y todo el pipeline fallan. El pipeline tampoco aplica los demás cambios. Si los cambios de los otros pipelines deben conservarse aunque falle este paso, coloca **Resumen con IA** en un pipeline separado y ordénalo después de los demás.

### Llamar a una API

Un paso **Llamar a una API** envía el evento de alerta mediante POST a uno de los [conectores HTTP](/es/connectors#destinos) de la organización y aplica los cambios que devuelve la respuesta. El paso usa la dirección y la credencial del conector y aplica sus controles de salida: primero resuelve el host y solo se conecta a la dirección obtenida, rechaza las direcciones de metadatos de la nube y no sigue redirecciones.

El cuerpo contiene el evento tal como lo dejaron los pasos anteriores y su origen junto a los demás campos:

```json
{
  "summary": "Checkout error rate above 5%",
  "severity": "error",
  "priority": null,
  "urgency": null,
  "labels": { "service": "checkout" },
  "annotations": {},
  "affected_services": ["checkout"],
  "metadata": { "rule_id": "…", "rule_name": "Checkout errors", "source": "rule", "event": "opened" }
}
```

- Del objeto JSON que devuelve el conector, el paso solo toma `summary`, `severity`, `priority`, `urgency`, `labels`, `annotations` y `affected_services`, según las reglas de [El evento de alerta](#el-evento-de-alerta). El paso combina `labels` y `annotations` clave por clave y elimina las claves con valor `null`. Así, un servicio puede responder solo con lo que agrega. Una respuesta vacía no cambia nada.
- El paso hace la llamada una sola vez, cuando se abre el incidente, con un límite de 5 segundos. Un [cambio de severidad](#cambios-de-gravedad) no genera otra llamada.
- Si la llamada falla (no llega una respuesta a tiempo, el código de estado no es 2xx, el cuerpo no es un objeto JSON o supera 1 MiB, un campo incumple las reglas, o el conector está desactivado o ya no existe), el pipeline solo da por no ejecutado este paso. El evento continúa en el estado previo al paso, el pipeline ejecuta los pasos posteriores y conserva los cambios de los anteriores. La [cronología](#qué-ocurre-con-un-evento) y los [recuentos](#recuentos-diarios) indican el motivo.

### Agregar resultados de la consulta

Un paso **Agregar resultados de la consulta** ejecuta una consulta con valores del evento y escribe las filas en una anotación:

```sql
SELECT count(*) AS errors FROM app_logs WHERE level = 'error' AND host = '{{labels.host_name}}'
```

| Campo | Significado |
|---|---|
| **Lenguaje** | SQL o PromQL. PromQL lee un flujo de métricas. |
| **Tipo de flujo**, **Flujo** | El flujo que lee la consulta. El paso no puede leer `_audit` porque se ejecuta sin el permiso `audit.read` de ningún usuario. |
| **Consulta** | Una sola consulta con marcadores de posición. |
| **Ventana retrospectiva (segundos)** | Cuántos segundos antes de la apertura del incidente abarca la consulta. 300 de forma predeterminada, con un máximo de 86,400. |
| **Filas** | Cuántas filas incluye la anotación. 5 de forma predeterminada, con un máximo de 50. |
| **Anotación** | La anotación que recibe las filas, `query_result` de forma predeterminada. |

Un marcador de posición representa un valor del evento: `{{labels.<key>}}`, `{{annotations.<key>}}`, `{{summary}}`, `{{severity}}`, `{{priority}}`, `{{urgency}}`, `{{rule_id}}`, `{{rule_name}}` o `{{source}}`. Como las etiquetas pueden venir de otros sistemas, coloca cada marcador de posición dentro de una cadena entre comillas en la consulta. Allí, el paso aplica el escape al valor. Si un marcador aparece en otro lugar, MoleSignal devuelve `400` al guardar.

- La anotación contiene una línea por fila: si hay un solo valor, lo muestra por sí solo; si hay varios, usa el formato `column=value, column=value`. Admite un máximo de 4,000 caracteres. Si la consulta no devuelve filas, el paso omite la anotación.
- El paso ejecuta la consulta una sola vez, cuando se abre el incidente, con un límite de 10 segundos.
- Si la consulta falla o el evento no tiene un valor para un marcador de posición, el pipeline solo da por no ejecutado este paso, al igual que con [**Llamar a una API**](#llamar-a-una-api).

## Qué ocurre con un evento

Cada flujo de procesamiento que recibe un evento termina con uno de tres resultados:

| Resultado | Causa | Efecto |
|---|---|---|
| **Procesado** | Los pasos se ejecutaron hasta el final. | El evento continúa con los cambios de esos pasos. |
| **Descartados** | Un paso ejecutó `abort`. | No se abre ningún incidente ni se ejecutan los flujos de procesamiento posteriores. |
| **Fallido** | Un paso falló o dejó un campo que incumple las reglas de [El evento de alerta](#el-evento-de-alerta). Esto incluye los fallos de los pasos **Llamar a una API** y **Agregar resultados de la consulta**. | El flujo de procesamiento descarta sus cambios, salvo si solo falló un paso de esos dos tipos. En ese caso, conserva los cambios de los demás pasos. El evento continúa al siguiente flujo de procesamiento y el incidente se abre de todos modos. |

La [cronología](/es/alerting/incidents#detalles-del-incidente) del incidente muestra una fila por cada flujo de procesamiento que hizo algún cambio o falló: **Pasó por el flujo de procesamiento Enrutamiento de pagos: gravedad de error → crítica, etiquetas +team=payments**. Si hubo un fallo, la fila indica el motivo. Los flujos de procesamiento que no hacen cambios no generan filas, y los [cambios de gravedad](#cambios-de-gravedad) tampoco. Cada fila muestra hasta 40 cambios e indica cuántos más hubo. Los valores largos se truncan a los 200 caracteres.

Si una regla se sigue activando, el flujo de procesamiento vuelve a descartar su evento en cada evaluación. La [lista de reglas](/es/alerting/rules#lista-de-reglas) muestra su estado como **Descartada por el flujo de procesamiento** y su `last_state` en la API es `{"kind": "dropped"}`. El flujo de procesamiento contabiliza el descarte y su **Vista general** indica la regla asociada al más reciente. Si un flujo de procesamiento descarta una alerta externa, aparece como **Ignorado** en [**Solicitudes recientes**](/es/alerting/sources#solicitudes-recientes) de su origen, junto al flujo de procesamiento y al paso que la descartó.

## Cambios de gravedad

Mientras un incidente está abierto, los flujos de procesamiento de alertas vuelven a determinar su gravedad cada vez que la regla de alerta se activa de nuevo, el origen externo vuelve a enviar la alerta o la comprobación sintética cambia de estado:

- MoleSignal vuelve a construir el evento tal como lo hizo al abrir el incidente, pero con la gravedad que informa el origen en ese momento. El evento pasa por los flujos de procesamiento que lo aceptan, sin ejecutar los pasos **Resumen con IA**, **Llamar a una API** ni **Agregar resultados de la consulta**. El valor de `%event` es `severity_changed`.
- MoleSignal solo toma la gravedad resultante de los pasos y actualiza la del incidente si es distinta. El título, las etiquetas, las anotaciones y los servicios conservan los valores definidos al abrir el incidente.
- Si un flujo de procesamiento descarta el evento o falla, nada cambia: el incidente sigue abierto y el siguiente flujo de procesamiento se ejecuta.

Por lo tanto, un paso que reduce la gravedad de las alertas del entorno de preproducción sigue haciéndolo si la regla informa de una gravedad mayor más adelante. Un incidente con acuse de recibo conserva su gravedad, al igual que un incidente cuya gravedad se configuró manualmente.

## Antes de una notificación

Configura **Cuándo** como **Antes de una notificación** en el nodo **Eventos de alerta** para que el flujo de procesamiento se ejecute justo antes de que una [política de notificación](/es/notification-channels) envíe una notificación sobre un evento de alerta. El flujo trabaja sobre una copia del evento para cada política a la que se aplica y en cada envío, incluidos los pasos posteriores y el escalamiento. Usa esta opción para acortar el título de una notificación por SMS, agregar una etiqueta al webhook de un equipo o silenciar una política durante la noche, sin modificar el incidente.

- **Políticas de notificación** indica a qué políticas se aplica el flujo de procesamiento. Si no seleccionas ninguna, se aplica a todas las políticas del evento de alerta. En ese momento, la política ya ha determinado que el evento original cumple sus condiciones.
- Las demás condiciones funcionan como antes y se evalúan con el evento de la notificación: se usa la hora en que ocurrió el evento y **Orígenes** incluye **Incidentes abiertos manualmente**.
- Los pasos se ejecutan dentro de MoleSignal. Los pasos **Resumen con IA**, **Llamar a una API** y **Agregar resultados de la consulta** solo se ejecutan al abrir un incidente. Si el flujo de procesamiento incluye alguno de ellos, devuelve `400` en esta etapa.
- El flujo termina en **A la notificación**. La política usa el título, la gravedad, la prioridad, la urgencia, las etiquetas, las anotaciones y los servicios resultantes de los pasos en sus [plantillas](/es/notification-channels#variables-de-plantilla), en el cuerpo de sus webhooks y en el texto predeterminado. La política determina los destinatarios a partir del evento original.
- Si un paso ejecuta `abort`, la política no envía la notificación. El registro de entregas muestra una entrada con estado **Omitido** y un motivo que indica el flujo de procesamiento y el paso en el idioma predeterminado del espacio de trabajo (`error_code` `dropped_by_pipeline`). La cronología del incidente también registra la omisión. No es un fallo: la política no reintenta el envío ni continúa con el escalamiento por falta de acuse de recibo.
- Si un flujo de procesamiento falla, MoleSignal descarta sus cambios y envía la notificación sin modificaciones. El fallo aparece en los [recuentos](#recuentos-diarios), no en la cronología.

Además de `%rule_id`, `%rule_name` y `%source`, los pasos pueden leer `%policy_id` y `%policy_name`. El valor de `%event` es `triggered`, `escalated`, `acknowledged` o `resolved`. `%rule_name` contiene el nombre de la regla o el título del evento si ninguna regla abrió el incidente. **Prueba** usa los valores de ejemplo `triggered` y `On-call alerts`.

```ruby
# on-call alerts of the staging environment go out only for what is critical
if %policy_name == "On-call alerts" && .labels.env == "staging" && .severity != "critical" {
  abort
}
```

## Recuentos diarios

Los flujos de procesamiento de alertas no registran ejecuciones, por lo que no tienen historial de ejecuciones y no ofrecen la opción **Más → Carga retroactiva**. En su lugar, contabilizan los resultados del día en curso (UTC):

- En la lista, el **Estado** de un flujo de procesamiento de alertas habilitado es **En espera de eventos de alerta** y la columna **Última ejecución** muestra los recuentos, por ejemplo: **Hoy: 41 procesados · 3 descartados · 0 fallidos**.
- En la **Vista general** del flujo de procesamiento, **Procesado**, **Descartados** y **Fallido** muestran los mismos recuentos. **Descartados** indica la regla o el origen del descarte más reciente y cuándo ocurrió. **Fallido** muestra el motivo del fallo más reciente.

Los recuentos se reinician a medianoche UTC. No incluyen los eventos que no cumplen las condiciones ni las ejecuciones por un [cambio de gravedad](#cambios-de-gravedad). La API devuelve los recuentos como `alert_record`. Consulta [Administrar flujos de procesamiento](/es/api/intake/scheduled-pipelines#obtener).

## Crear un flujo de procesamiento mediante la API

Guarda el flujo de procesamiento de alertas como cualquier otro flujo: configura `functionSteps.mode` como `alert` y deja vacíos los flujos de datos y la programación:

```bash
curl -X POST http://localhost:5080/api/v1/scheduled_pipelines \
  -H "authorization: Bearer $MS_TOKEN" \
  -H 'content-type: application/json' \
  -d '{
    "name": "staging-alerts",
    "sourceStream": "",
    "targetStream": "",
    "cron": "",
    "enabled": true,
    "functionSteps": {
      "mode": "alert",
      "alert": {
        "sources": ["rule", "external"],
        "severities": [],
        "labels": { "env": "staging" },
        "order": 10
      },
      "steps": [
        { "transformName": "cap-severity", "kind": "vrl",
          "script": "if .severity == \"critical\" { .severity = \"warning\" }" },
        { "transformName": "summary", "kind": "ai_summary",
          "prompt": "Summarize this alert in two sentences for the on-call engineer.",
          "annotation": "ai_summary" }
      ]
    }
  }'
```

Para un flujo de procesamiento previo a las notificaciones, configura `alert.stage` como `notify` e indica las políticas en `alert.policies` si corresponde:

```json
{
  "mode": "alert",
  "alert": { "stage": "notify", "policies": ["<policy id>"], "labels": { "env": "staging" }, "order": 10 },
  "steps": [
    { "transformName": "quiet", "kind": "vrl", "script": "if .severity != \"critical\" { abort }" }
  ]
}
```
