Una fuente de alertas convierte las alertas que envía otro sistema en [incidentes](/es/alerting/incidents). Al igual que los incidentes que generan las reglas, estos incidentes avisan al personal de guardia mediante una [política de escalamiento](/es/alerting/on-call#políticas-de-escalamiento) y envían notificaciones mediante [políticas de notificación](/es/notification-channels). Se resuelven cuando la fuente informa de la recuperación. Abre **Alertas → Orígenes**. Para consultar las fuentes, necesitas `alerts.sources.read`. Para crearlas, editarlas, eliminarlas o rotar sus tokens, necesitas `alerts.sources.manage`.

## Tipos de fuentes

El tipo de cada fuente determina qué formato se usa para interpretar el cuerpo de la solicitud.

| Tipo | Remitente | Un incidente por |
|---|---|---|
| **API** | Scripts, sistemas de CI y sistemas internos que llaman a la API de MoleSignal | Clave de deduplicación |
| **Alertmanager** | Un receptor de tipo webhook de Prometheus Alertmanager | Grupo de notificaciones |
| **Grafana** | Un punto de contacto de tipo webhook de Grafana Alerting | Grupo de notificaciones |
| **Datadog** | La integración Webhooks de Datadog | Monitor; cada grupo si el monitor genera varias alertas |
| **PagerDuty** | Una suscripción a webhooks V3 de PagerDuty | Incidente de PagerDuty |
| **Alibaba Cloud CloudMonitor** | Callbacks de alarmas de umbral y canales push de suscripciones a eventos | Objeto de una regla de alarma o evento del sistema |
| **Tencent Cloud Observability Platform** | Callbacks de API de una plantilla de notificación | Métrica o evento de un objeto sujeto a una política; uno por nivel si la política tiene varios niveles |
| **Amazon CloudWatch** | Alarmas que llegan a través de la suscripción HTTPS del tema de SNS al que se envían | Alarma |
| **Zabbix** | Un tipo de medio webhook de Zabbix | Problema |
| **Correo electrónico** | Un buzón IMAP o mensajes sin procesar de un sistema de correo que ya administras | Serie de mensajes con el mismo asunto |

Los sistemas compatibles con el webhook de Alertmanager, como el Alertmanager de Thanos, Cortex o Mimir, usan el tipo **Alertmanager**.

## Crea una fuente

1. Abre **Alertas → Orígenes** y haz clic en **Nueva fuente de alertas**.
2. Elige el **Tipo** e ingresa un **Nombre**.
3. Elige la **Política de escalamiento**. Al igual que en el editor de reglas, la opción predeterminada es **Con enrutamiento (predeterminado)**. El [enrutamiento de alertas](/es/alerting/routing) selecciona el equipo y la política de escalamiento según las reglas de enrutamiento, el equipo responsable del servicio y la etiqueta de equipo. Si no encuentra una coincidencia, usa la [política predeterminada](/es/alerting/on-call#política-predeterminada) llamada `default`. Si eliges una política, los incidentes la usan y el enrutamiento solo selecciona el equipo. Con **Sin escalamiento, solo políticas de notificación**, los incidentes se abren y envían notificaciones, pero ninguna política de escalamiento avisa al personal de guardia.
4. Elige la **Gravedad predeterminada**. Se aplica si la alerta no especifica una gravedad.
5. Agrega **Etiquetas adicionales** si hace falta, como `team=payments`. La fuente las agrega a cada incidente que abre. Si la alerta ya incluye una etiqueta con la misma clave, prevalece el valor de la alerta.
6. Haz clic en **Crear**. La página de la fuente se abre con un cuadro de diálogo que muestra el token y la configuración con el token incluido. Alibaba Cloud CloudMonitor solo necesita la dirección de recepción, así que el cuadro de diálogo muestra esa dirección con el token incluido.

<Warning>
  MoleSignal solo muestra el token al crear la fuente o al rotar su token. Después de cerrar el cuadro de diálogo, solo queda visible el prefijo que empieza por `mspat-`. Si pierdes el token, haz clic en **Rotar token** para obtener uno nuevo. El token anterior deja de funcionar de inmediato.
</Warning>

## Dirección de recepción y token

Todas las fuentes comparten una sola dirección de recepción. El token identifica a qué fuente pertenece cada alerta:

```text
https://<molesignal-host>/api/v1/intake/alerts
```

El token tiene el formato `mspat-<36>`, igual que un token de API, pero solo sirve para recibir alertas. Los tokens de API no sirven para recibir alertas. El remitente incluye el token en un encabezado:

```text
Authorization: Bearer <token>
```

Si el remitente no puede configurar encabezados (Alibaba Cloud CloudMonitor, Tencent Cloud Observability Platform o Amazon CloudWatch a través de SNS), incluye el token en la dirección: `https://<molesignal-host>/api/v1/intake/alerts?token=<token>`.

El remitente debe poder acceder a esta dirección. Si un firewall protege MoleSignal, permite las conexiones desde las direcciones IP de salida del sitio o la región del remitente. Datadog las enumera por sitio en la sección `webhooks` de `ip-ranges`, PagerDuty las publica para sus regiones de servicio de EE. UU. y la UE, y Alibaba Cloud CloudMonitor enumera los rangos de envío en la documentación de callbacks de alarmas. Si ejecutas MoleSignal en una red interna, consulta [Acceso público](/es/public-access) para exponer solo esta dirección a Internet.

## Configura el emisor

En la página de la fuente, **Recepción** muestra la dirección de recepción, el token y los tres pasos de configuración para cada tipo de emisor. Reemplaza `<TOKEN>` por el token de la fuente. Cuando la fuente recibe su primera solicitud, MoleSignal marca los tres pasos como completados.

### API

```bash
curl -X POST https://<molesignal-host>/api/v1/intake/alerts \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{"dedupKey": "disk-full/web-1", "summary": "Disk almost full on web-1", "severity": "critical", "labels": {"host.name": "web-1"}}'
```

`action` admite `trigger` (el valor predeterminado), `acknowledge` o `resolve`. Usa la misma `dedupKey` para confirmar o resolver la misma alerta. [Enviar alertas](/es/api/alerting/send-alerts) describe todos los campos.

### Alertmanager

Agrega un receptor a `alertmanager.yml` y dirige las alertas a ese receptor:

```yaml
route:
  receiver: molesignal
receivers:
  - name: molesignal
    webhook_configs:
      - url: https://<molesignal-host>/api/v1/intake/alerts
        send_resolved: true
        http_config:
          authorization:
            credentials: <token>
```

Mantén `send_resolved` en `true`; de lo contrario, Alertmanager no enviará las recuperaciones. Configura el mismo `--web.external-url` en todas las réplicas de un clúster de Alertmanager. La URL externa forma parte de la clave de deduplicación, así que MoleSignal no fusiona en un solo incidente los grupos con el mismo nombre de instancias de Alertmanager en distintas regiones, aunque usen el mismo enrutamiento.

### Grafana

1. En Grafana, abre **Alertas → Puntos de contacto** y haz clic en **Agregar punto de contacto**.
2. Selecciona **Webhook** en **Integración** e ingresa la dirección de recepción en **URL**.
3. En **Configuración opcional del webhook**, establece `Bearer` en **Esquema del encabezado de autenticación** e ingresa el token en **Credenciales del encabezado de autenticación**.
4. Deja sin marcar **Desactivar mensaje de resolución**, guarda los cambios y usa el punto de contacto en una política de notificación.

Con aprovisionamiento mediante archivos:

```yaml
apiVersion: 1
contactPoints:
  - orgId: 1
    name: molesignal
    receivers:
      - uid: molesignal
        type: webhook
        settings:
          url: https://<molesignal-host>/api/v1/intake/alerts
          httpMethod: POST
          authorization_scheme: Bearer
          authorization_credentials: <token>
```

### Datadog

1. En Datadog, abre **Integraciones → Webhooks** y agrega un webhook con un nombre como `molesignal`.
2. Ingresa la dirección de recepción en **URL** y `{"Authorization": "Bearer <token>"}` en **Encabezados personalizados**. Deja sin marcar **Codificar como formulario**.
3. Usa la siguiente plantilla en **Carga útil**. Los nombres de los campos son de MoleSignal y los valores son variables de Datadog. MoleSignal rechaza las solicitudes que no usan esta plantilla.

```json
{
  "alert_id": "$ALERT_ID",
  "alert_cycle_key": "$ALERT_CYCLE_KEY",
  "transition": "$ALERT_TRANSITION",
  "alert_type": "$ALERT_TYPE",
  "priority": "$ALERT_PRIORITY",
  "title": "$ALERT_TITLE",
  "event_title": "$EVENT_TITLE",
  "message": "$TEXT_ONLY_MSG",
  "scope": "$ALERT_SCOPE",
  "tags": "$TAGS",
  "hostname": "$HOSTNAME",
  "link": "$LINK",
  "snapshot": "$SNAPSHOT",
  "query": "$ALERT_QUERY",
  "org_id": "$ORG_ID",
  "last_updated": "$LAST_UPDATED"
}
```

4. Menciona `@webhook-molesignal` en el mensaje de notificación de un monitor.

Todos los sitios de Datadog (`datadoghq.com`, `datadoghq.eu`, `us3`, `us5`, `ap1` y los demás) pueden enviar alertas a una misma fuente. MoleSignal identifica el sitio a partir del dominio de `$LINK` y lo incluye en la clave de deduplicación junto con el ID de la organización.

### PagerDuty

1. En PagerDuty, abre **Integraciones → Webhooks genéricos (v3)** y haz clic en **Nuevo webhook**.
2. Ingresa la dirección de recepción en **URL del webhook** y elige el **Tipo de alcance** (la cuenta, un servicio o un equipo).
3. En **Suscripción a eventos**, selecciona `incident.triggered`, `incident.acknowledged`, `incident.resolved`, `incident.reopened` e `incident.priority_updated`.
4. Agrega el encabezado personalizado `Authorization` con el valor `Bearer <token>`.

Las cuentas de las regiones de servicio de EE. UU. y de la UE pueden enviar alertas a una misma fuente. El dominio de la cuenta (`<subdomain>.pagerduty.com` o `<subdomain>.eu.pagerduty.com`) forma parte de la clave de deduplicación. MoleSignal también lo guarda en la etiqueta `pagerduty.region`.

### Alibaba Cloud CloudMonitor

Agrega el token a la dirección de recepción:

```text
https://<molesignal-host>/api/v1/intake/alerts?token=<token>
```

- **Alarmas de umbral**: ingresa esta dirección en **Callback de alarma** en la regla de alarma. CloudMonitor envía una solicitud POST con datos codificados como formulario. MoleSignal también admite JSON.
- **Eventos del sistema**: en **Centro de eventos → Suscripción a eventos → Canales de envío**, crea un canal con **Webhook** como tipo de destino, **POST** como método de solicitud y **JSON** como formato de datos. Ingresa esta dirección y usa el canal en una política de suscripción.

CloudMonitor espera 5 segundos por la respuesta al callback de un evento del sistema y vuelve a intentarlo 3 veces. MoleSignal espera como máximo 3 segundos al reenviar una solicitud al [clúster receptor](#varios-clústeres). Si se agota el tiempo de espera, responde con `503` para que CloudMonitor vuelva a intentarlo. Los sitios de China y los internacionales usan el mismo formato en todas las regiones. MoleSignal guarda la región en la etiqueta `aliyun.region` e incluye el `userId` de la cuenta en la clave de deduplicación.

### Tencent Cloud Observability Platform

En Tencent Cloud Observability Platform (antes Cloud Monitor), edita o crea una plantilla en **Administración de alarmas → Plantillas de notificación**. Ingresa la dirección de recepción en **Callback de API** y vincula la plantilla a las políticas de alarma. El callback de Tencent Cloud no admite encabezados, así que incluye el token en la dirección. Trata la dirección como una credencial: el callback no incluye una firma y la dirección identifica la fuente. La integración admite alarmas de métricas y de eventos, y recibe tanto las activaciones como las recuperaciones.

- **Deduplicación**: las alarmas con la misma cuenta, política de alarma, nombre de métrica o evento y objeto generan una sola alerta. En una política con niveles, cada nivel genera un incidente y se recupera por separado, como en Tencent Cloud.
- **Gravedad**: para `alarmLevel`, Grave (`Serious`) equivale a crítica, Severa (`Warn`) a error y Recordatorio (`Remind`) a información. Si la política no tiene niveles, MoleSignal usa la gravedad predeterminada de la fuente.
- **Eventos sin estado** (`alarmStatus` tiene el valor `5`): abren un incidente que no recibe una notificación de recuperación, por lo que requiere resolución manual.
- **Horas**: el callback no incluye la zona horaria. MoleSignal interpreta las horas como hora de Pekín.

### Amazon CloudWatch

Las alarmas de CloudWatch no envían solicitudes directamente a direcciones externas. Lo hacen a través de SNS:

1. En las notificaciones de la alarma, envía al mismo tema de SNS tanto el cambio a **En alarma** (`ALARM`) como el regreso a **Aceptar**. Sin `OK`, los incidentes no se resuelven automáticamente. Para las alertas por falta de datos, envía también **Datos insuficientes** (`INSUFFICIENT_DATA`).
2. Agrega al tema una suscripción HTTPS. Usa como punto de conexión la dirección de recepción e incluye el token en la dirección:

   ```bash
   aws sns subscribe \
     --topic-arn <ARN of the topic> \
     --protocol https \
     --notification-endpoint 'https://<molesignal-host>/api/v1/intake/alerts?token=<token>'
   ```

3. MoleSignal confirma la suscripción automáticamente: verifica la firma del mensaje de confirmación y luego accede a su `SubscribeURL`.

MoleSignal verifica la firma de todos los mensajes de SNS, así que deja desactivada la opción **Entrega de mensajes sin procesar**. Si la activas, MoleSignal rechaza los mensajes y muestra el motivo en la sección Recibidos recientemente de la página de la fuente. El certificado de firma proviene de `sns.<region>.amazonaws.com`, así que el nodo que recibe la solicitud debe poder acceder a esa dirección.

Las alarmas de CloudWatch no tienen gravedad, así que MoleSignal asigna a los incidentes la gravedad predeterminada de la fuente. El ARN de la alarma es la clave de deduplicación, incluso para las alarmas compuestas. MoleSignal guarda la descripción de la alarma y el motivo del cambio de estado en anotaciones, y la región, la cuenta, el espacio de nombres, la métrica y las dimensiones en etiquetas. Así, puedes usar una etiqueta como `aws.region` para controlar el enrutamiento.

### Zabbix

Compatible con Zabbix 6.0 y versiones posteriores. Zabbix no define un formato propio de solicitud: envía la solicitud a través del script de un tipo de medio. La página de la fuente y el cuadro de diálogo para crearla proporcionan un tipo de medio con la dirección y el token ya configurados:

1. Guarda el tipo de medio como YAML e impórtalo en **Alertas → Tipos de medios → Importar**. Verifica el parámetro `token`.
2. Configura la macro global `{$ZABBIX.URL}` con la dirección de la interfaz web de Zabbix. MoleSignal la incluye en la clave de deduplicación, de modo que una misma fuente puede recibir alertas de varios servidores Zabbix y los incidentes incluyen enlaces a Zabbix. La integración también funciona sin esta macro.
3. Asigna este medio a un usuario. Puedes ingresar cualquier valor en **Enviar a**: el script no lo usa.
4. Agrega una acción de disparador y dirige todas sus **operaciones**, **operaciones de recuperación** y **operaciones de actualización** a ese usuario. Sin operaciones de recuperación, los incidentes no se resuelven automáticamente.

El botón **Prueba** del tipo de medio requiere valores reales. Si Zabbix no expande las macros (por ejemplo, si envía `{EVENT.ID}` tal cual), MoleSignal responde con `400` e indica que uses el tipo de medio de la documentación.

### Correo electrónico

Hay dos formas de recibir correos y ambas generan el mismo tipo de alerta.

**Leer un buzón** (recomendado): MoleSignal consulta un buzón IMAP a intervalos regulares. Solo necesita una conexión saliente y un buzón. No requiere una dirección pública, un registro MX, el puerto 25 ni un certificado, lo que simplifica la configuración en instalaciones autogestionadas. Envía los correos de alerta del sistema de monitoreo a ese buzón o reenvíalos con una regla de correo.

En la página de la fuente, en **Leer un buzón**, completa **Servidor IMAP**, **Puerto**, **Cifrado**, **Nombre de usuario**, **Contraseña**, **Carpeta** (`INBOX` de forma predeterminada) y **Leer cada** (de 15 a 3600 segundos, 60 de forma predeterminada). Haz clic en **Probar conexión** y luego en **Guardar buzón**.

- **Solo lectura**: MoleSignal usa `EXAMINE` y `BODY.PEEK[]`, así que no marca mensajes como leídos ni los elimina. Una cuenta de solo lectura es suficiente.
- **Sin leer correos anteriores**: en la primera conexión, MoleSignal registra la posición y solo lee los mensajes que llegan después. Si cambia el servidor, la cuenta o la carpeta, o si el servidor reconstruye el buzón (cambia `UIDVALIDITY`), MoleSignal vuelve a empezar desde ese momento. Si desactivas la fuente, MoleSignal no lee mensajes ni conserva la posición. Cuando la vuelves a activar, solo lee los mensajes que llegan a partir de ese momento.
- **Lista de remitentes obligatoria**: cualquiera que conozca la dirección puede enviarle correo. En **Aceptar correos de**, en la configuración de la fuente, ingresa direcciones o usa `@example.com` para aceptar un dominio completo. Usa `*` para aceptar cualquier remitente. MoleSignal comprueba el encabezado `From`, que admite falsificaciones. Mantén activos el filtro de correo no deseado y DMARC en el proveedor de correo. MoleSignal registra como **Rechazada** la recepción de correos de otros remitentes y no abre incidentes.
- **Autenticación**: usa una contraseña o una contraseña de aplicación del proveedor. Microsoft 365 ya no admite contraseñas. Selecciona **OAuth 2.0** y completa la dirección del token `https://login.microsoftonline.com/<tenant>/oauth2/v2.0/token`, el ID de cliente, el secreto de cliente y el alcance `https://outlook.office365.com/.default`. La aplicación necesita el permiso `IMAP.AccessAsApp` y acceso al buzón.
- **Sin cifrado**: usa esta opción solo en una red de confianza. La contraseña viaja en texto sin formato.
- Si falla una lectura, MoleSignal muestra el motivo en la página de la fuente y vuelve a intentarlo en el siguiente ciclo. Si hay varios nodos de alertas, solo uno lee cada buzón. En una instalación federada, configura el buzón en el clúster receptor de la fuente. MoleSignal no sincroniza esa configuración, así que la contraseña permanece en ese clúster.

**Enviar el correo sin procesar mediante POST**: si ya administras un sistema de correo (`pipe` de Postfix, SES o MIME sin procesar de Mailgun), envía el mensaje sin procesar a la dirección de recepción mediante POST:

```bash
curl -X POST 'https://<molesignal-host>/api/v1/intake/alerts' \
  -H 'Authorization: Bearer <token>' \
  -H 'Content-Type: message/rfc822' \
  --data-binary @alert.eml
```

El sistema de correo debe poder acceder a la dirección de recepción. En este caso, la lista de remitentes es opcional porque el token ya identifica al emisor de la solicitud. Si configuras una lista, MoleSignal la aplica.

MoleSignal no incluye un receptor SMTP. Para ofrecerlo necesitaría un puerto 25 abierto, un registro MX, un certificado TLS y un filtro propio de correo no deseado. La mayoría de las instalaciones autogestionadas no pueden cumplir estos requisitos.

**Cómo se procesa un correo**: ajusta estas opciones en **Lectura del correo**, en la configuración de la fuente:

| Configuración | Descripción |
|---|---|
| **Asuntos que indican recuperación** | Una expresión regular. Si dejas el campo vacío, MoleSignal usa la expresión integrada: `resolved`, `recovered`, `recovery`, `cleared`, `恢复`, `已解决` y `OK` al inicio. Los demás correos activan alertas. |
| **Clave de deduplicación a partir del asunto** | Una expresión regular. MoleSignal usa el primer grupo de captura, como en `host=(\S+)`. Si el campo está vacío o no hay coincidencias, usa el asunto normalizado: quita `Re:` y `Fwd:`, las palabras de estado (`PROBLEM`, `RECOVERY`, `告警`, `恢复`, entre otras), las indicaciones de gravedad, las fechas y horas, y los porcentajes. No distingue entre mayúsculas y minúsculas. Así, «CRITICAL: disk full on web-1 (91%)» y «RECOVERY: disk full on web-1 (40%)» corresponden a una sola alerta, mientras que `web-1` y `web-2` corresponden a dos alertas distintas. La clave también incluye el dominio del remitente. |
| **Asuntos que no generan alertas** | Una expresión regular. MoleSignal no genera alertas para los correos que coinciden y los muestra en Recibidos recientemente. |

MoleSignal determina la gravedad a partir de las palabras del asunto (`critical`, `fatal`, `disaster` y `P1` indican gravedad crítica; `error` y `P2`, error; `warning` y `P3`, advertencia; `info`, `notice`, `P4` y `P5`, información). Si no encuentra ninguna, usa la gravedad predeterminada de la fuente. Las palabras `High` y `Low` de `High CPU` y `Low disk` no cuentan. MoleSignal guarda el cuerpo en la anotación `message` (convierte los correos HTML en texto y conserva hasta 4096 caracteres), guarda el remitente en la etiqueta `email.from` y en la anotación `from`, y toma la hora del encabezado `Date`. Las respuestas automáticas (`Auto-Submitted: auto-replied`) y los mensajes de rebote (`multipart/report`) no generan alertas. MoleSignal admite GBK, GB2312 y otros juegos de caracteres. Si un correo supera los 4 MiB, MoleSignal registra la recepción como **Rechazada** sin leer el cuerpo.

## Cómo se convierten las alertas en incidentes

| Tipo | Clave de deduplicación | Activación | Resolución | Gravedad |
|---|---|---|---|---|
| **API** | `dedupKey` | `trigger` | `resolve` | `severity` |
| **Alertmanager** | URL externa y `groupKey` | El `status` del grupo es `firing` | El `status` del grupo es `resolved`: todas las alertas del grupo se han recuperado | El valor más alto de la etiqueta `severity` entre las alertas activas del grupo |
| **Grafana** | URL externa, organización y `groupKey` | Igual | Igual | Igual |
| **Datadog** | Sitio, organización, ID del monitor y alcance | Cualquier transición salvo `Recovered` | `Recovered` | `$ALERT_PRIORITY`; en su ausencia, Warn y No Data se clasifican como advertencia y el resto sigue `$ALERT_TYPE` |
| **PagerDuty** | Dominio de la cuenta e ID del incidente de PagerDuty | `incident.triggered`, `incident.reopened`; `incident.priority_updated` cambia la gravedad | `incident.resolved` | Prioridad de P1 a P5; sin prioridad, la urgencia alta se clasifica como error y la baja como advertencia |
| **Alibaba Cloud CloudMonitor** | Cuenta, ID de la regla y `dimensions`; para eventos del sistema, cuenta y `dedupId` | `ALERT`, `INSUFFICIENT_DATA`; para eventos del sistema, `TRIGGERED` | `OK`; para eventos del sistema, `RESOLVED` | `triggerLevel`; para eventos del sistema, `severity` |
| **Tencent Cloud Observability Platform** | Cuenta, política, nombre de la métrica o del evento, nivel y objeto | `alarmStatus` es `1` o `5` | `alarmStatus` es `0` | `alarmLevel` |
| **Amazon CloudWatch** | `AlarmArn` | `NewStateValue` es `ALARM` o `INSUFFICIENT_DATA` | `NewStateValue` es `OK` | Ninguna: se usa la gravedad predeterminada de la fuente |
| **Zabbix** | Host de `{$ZABBIX.URL}` y `{EVENT.ID}` | `{EVENT.VALUE}` es 1; las operaciones de actualización también activan el incidente y determinan su gravedad | `{EVENT.VALUE}` es 0 o una operación de actualización cerró el problema | `{EVENT.NSEVERITY}`: Disaster corresponde a crítica; High, a error; Average y Warning, a advertencia; Information, a informativa |
| **Correo electrónico** | Dominio del remitente y fragmento extraído del asunto | Cualquier otro correo | Un asunto que indica una recuperación | Palabras del asunto |

MoleSignal lee la prioridad y la urgencia por separado: `priority` y `urgency` de la API, `$ALERT_PRIORITY` de Datadog y la prioridad y la urgencia de PagerDuty determinan los valores del incidente. Si no se indica la urgencia, la política de escalamiento de la fuente la determina. Una alerta que no indica la gravedad tiene urgencia alta. Consulta [Urgencia](/es/alerting/on-call#urgencia).

Una alerta sin gravedad toma la **Gravedad predeterminada** de la fuente. MoleSignal interpreta los términos de gravedad de cualquier remitente sin distinguir entre mayúsculas y minúsculas: `critical`, `crit`, `fatal`, `page` y `P1` corresponden a crítica; `error`, `major`, `high` y `P2`, a error; `warning`, `warn`, `minor`, `medium` y `P3`, a advertencia; `info`, `low`, `P4` y `P5`, a informativa. Cualquier otro término toma la gravedad predeterminada.

- **Apertura**: cada fuente tiene como máximo un incidente activo por clave de deduplicación. El incidente incluye las etiquetas `alert.source=external` y `external.kind=<kind>`, las etiquetas de la alerta (en Alertmanager y Grafana, `commonLabels` del grupo) y las etiquetas adicionales de la fuente. La etiqueta `service.name` o `service` identifica un servicio afectado, y `host.name`, `host` o `hostname` identifica un host.
- **Título**: la API usa `summary`; Alertmanager y Grafana usan la anotación `summary` o, si falta, `alertname`; Datadog usa `$ALERT_TITLE`; PagerDuty usa el título del incidente; Alibaba Cloud CloudMonitor usa «nombre de la alarma · nombre de la instancia».
- **Enlaces**: MoleSignal guarda las direcciones que apuntan al remitente en anotaciones como `alertmanager_url`, `generator_url`, `dashboard_url`, `datadog_url` y `pagerduty_url`. La página del incidente las muestra como enlaces. MoleSignal guarda los `links` de la API en anotaciones según su `name`.
- **Alertas de un grupo**: un incidente de Alertmanager o Grafana conserva todas las alertas del grupo (hasta 100) con su estado y las actualiza con cada notificación. En la página del incidente, **Alerta externa** muestra las alertas con las etiquetas que las distinguen.
- **Cambios de gravedad**: mientras el incidente no esté confirmado, adopta la gravedad de la alerta según los [pipelines de alertas](/es/pipelines/alert-events#cambios-de-gravedad). Si la gravedad aumenta, el escalamiento vuelve a empezar desde el primer paso. La gravedad que se fija manualmente se mantiene.
- **Confirmación**: `acknowledge` de la API, `incident.acknowledged` de PagerDuty y las operaciones de actualización de Zabbix que confirman un problema confirman el incidente y detienen los pasos de escalamiento y las llamadas pendientes. MoleSignal no registra quién confirmó el incidente.
- **Resolución**: MoleSignal resuelve el incidente cuando la fuente informa de la recuperación, aunque el incidente ya esté confirmado. MoleSignal no registra quién resolvió el incidente y lo marca como recuperado en la cronología.
- **Mensajes tardíos**: para cada clave de deduplicación, MoleSignal guarda la última marca de tiempo que procesó del remitente e ignora los mensajes anteriores a ella. Una activación tardía no abre un incidente zombi y una recuperación tardía no cierra un incidente nuevo. La API no incluye marcas de tiempo, por lo que MoleSignal procesa sus mensajes en orden de llegada.
- **Resolución manual previa**: si la fuente sigue notificando la alerta, el siguiente reenvío abre un incidente nuevo, igual que con las reglas.
- **Sin datos**: los incidentes que abre CloudMonitor con `INSUFFICIENT_DATA` o Datadog con No Data incluyen `alert.condition=no_data`, y los títulos de sus notificaciones empiezan con `NO DATA`.
- **Desactivación y eliminación**: una fuente desactivada rechaza las alertas (`409`), pero sus incidentes abiertos siguen abiertos. Al eliminar una fuente, su token deja de funcionar de inmediato y MoleSignal resuelve sus incidentes abiertos.

Las [políticas de silenciamiento](/es/alerting/silences), los [grupos semánticos](/es/alerting/silences#grupos-semánticos) y las [políticas de notificación](/es/notification-channels) se aplican a los incidentes externos igual que a los demás. Usa `external.kind`, las etiquetas adicionales de la fuente o las etiquetas de la alerta como criterios de coincidencia.

## Solicitudes recientes

La parte superior de la página de la fuente muestra su estado: **En espera de la primera solicitud**, **Recibiendo solicitudes**, **Última solicitud rechazada**, **Sin solicitudes en los últimos 7 días** o **Desactivada**. Al lado aparecen las solicitudes y alertas de las últimas 24 horas y los incidentes que abrió la fuente y siguen abiertos.

Cuando llegan solicitudes, la sección **Solicitudes recientes** de la página de la fuente muestra la hora, el resultado (**Procesada**, **Rechazada** o **Reenviada**), el estado HTTP, la cantidad de alertas y el resultado de cada una (**Abierta**, **Última actualización**, **Sin cambios**, **Confirmado**, **Resuelto** o **Ignorado**). Haz clic en una fila para ver el título, la gravedad, la acción, el resultado y el incidente de cada alerta. Si la solicitud se rechazó, también verás el motivo y el inicio de su cuerpo (hasta 16 KiB). MoleSignal conserva las últimas 500 solicitudes de cada fuente durante un máximo de 7 días.

## Varios clústeres

Con la [federación entre clústeres](/es/settings/data-plane#federación-de-clústeres) activada:

- Los clústeres sincronizan las fuentes y sus tokens igual que el resto de la configuración de alertas. Así, el mismo token funciona en la dirección de recepción de todos los clústeres.
- Los incidentes de una fuente solo se abren en su **Clúster receptor**, que es el clúster donde se creó la fuente, a menos que lo cambies en la configuración de la fuente. Si otro clúster recibe una alerta de la fuente, la reenvía por gRPC al clúster receptor y devuelve la respuesta de ese clúster al remitente. Así, una alerta externa genera un solo incidente, sin importar a qué dirección de clúster llegue.
- Si el clúster receptor no está disponible, MoleSignal responde con `503` y el remitente vuelve a intentar el envío. Si la región del clúster receptor sigue sin servicio, cambia el **Clúster receptor** en la configuración de la fuente a uno que esté disponible.
- MoleSignal registra las **Solicitudes recientes** en el clúster que procesó la solicitud. La página de la fuente lo indica cuando la abres en otro clúster.

## Límites

| Elemento | Límite |
|---|---|
| Cuerpo de la solicitud para un correo | Hasta 4 MiB. |
| Lectura de un buzón | Hasta 50 correos a la vez. El resto se lee en la siguiente ronda. |
| Una solicitud a la API | 100 alertas. Hasta 255 caracteres en `dedupKey` y 1024 caracteres en `summary`. |
| Una alerta | 64 etiquetas y 64 anotaciones. La API rechaza las solicitudes que superan estos límites. Para otros tipos de alertas, MoleSignal descarta las etiquetas y anotaciones sobrantes y recorta los títulos y las anotaciones demasiado largos. |
| Alertas de un grupo | MoleSignal conserva 100. |
| Etiquetas adicionales de una fuente | 32. Las claves no pueden empezar por `alert.` ni ser `external.kind`. |
| Solicitudes recibidas recientemente | Las últimas 500 solicitudes de cada fuente, durante un máximo de 7 días. |

MoleSignal no verifica la firma HMAC de Grafana ni la firma de PagerDuty: el token ya identifica la fuente. MoleSignal no notifica al remitente cuando alguien confirma o resuelve un incidente.
