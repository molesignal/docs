Una fuente de alertas convierte las alertas que envía otro sistema en [incidentes](/es/alerting/incidents). Avisa a las personas mediante una [política de escalamiento](/es/alerting/on-call#políticas-de-escalamiento) y notifica mediante [políticas de notificación](/es/notification-channels) de la misma forma que lo hacen los incidentes de las reglas, y se resuelven cuando la fuente informa de la recuperación. Abre **Alertas → Orígenes**. La lectura requiere `alerts.sources.read`; crear, editar, eliminar y rotar tokens requieren `alerts.sources.manage`.

## Tipos de origen

Cada origen tiene un tipo, que determina en qué formato se lee el cuerpo de la solicitud.

| Tipo | Remitente | Un incidente por |
|---|---|---|
| **API** | Scripts, CI y sistemas internos que llaman a la API de MoleSignal | Clave de deduplicación |
| **Alertmanager** | Un receptor de webhook de Prometheus Alertmanager | Grupo de notificación |
| **Grafana** | Un punto de contacto de webhook de Grafana Alerting | Grupo de notificación |
| **Datadog** | La integración Webhooks de Datadog | Monitor; cada grupo de un monitor de alertas múltiples |
| **PagerDuty** | Una suscripción de webhook V3 de PagerDuty | Incidente de PagerDuty |
| **Alibaba Cloud CloudMonitor** | Devoluciones de llamada de alarmas de umbral y canales push de suscripciones a eventos | Objeto de una regla de alarma o evento del sistema |
| **Tencent Cloud Observability Platform** | Devoluciones de llamada de API de una plantilla de notificación | Una métrica o evento de un objeto de una política, uno por nivel en una política con niveles |
| **Amazon CloudWatch** | Alarmas enviadas a un tema de SNS, mediante la suscripción HTTPS del tema | Una alarma |
| **Zabbix** | Un tipo de medio de webhook de Zabbix | Un problema |
| **Azure Monitor** | La acción de webhook de un grupo de acciones, en el esquema común de alertas | Una alerta |
| **Google Cloud Monitoring** | Un canal de notificación de webhook o el canal de Pub/Sub mediante una suscripción push | Un incidente de Monitoring |
| **Huawei Cloud Eye** | Alarmas enviadas a un tema de SMN, mediante la suscripción HTTPS del tema | Una regla de alarma en un recurso |
| **Correo electrónico** | Un buzón IMAP o correo sin procesar de un sistema de correo que ya tengas en ejecución | Una serie de correos con el mismo asunto |

Los sistemas compatibles con el webhook de Alertmanager, como el Alertmanager de Thanos, Cortex o Mimir, usan el tipo **Alertmanager**.

## Crear un origen

1. Abre **Alertas → Orígenes** y haz clic en **Nueva fuente de alertas**.
2. Elige el **Tipo** e introduce un **Nombre**.
3. Elige la **Política de escalamiento**. La predeterminada es **Con enrutamiento (predeterminado)**, igual que en el espacio de trabajo de reglas: el [enrutamiento de alertas](/es/alerting/routing) elige el equipo y la política de escalamiento según las reglas de enrutamiento, el equipo propietario del servicio y la etiqueta de equipo y, en caso contrario, la [política predeterminada](/es/alerting/on-call#política-predeterminada) llamada `default`. Con una política elegida, los incidentes la adoptan y el enrutamiento solo elige el equipo. Con **Sin escalamiento, solo políticas de notificación**, los incidentes se abren y notifican igualmente, pero ninguna política de escalamiento avisa a nadie.
4. Elige la **Gravedad predeterminada**, que se usa cuando una alerta no trae una gravedad propia.
5. Añade **Etiquetas adicionales** si es necesario, como `team=payments`. Se añaden a cada incidente que abre el origen. Una etiqueta que la propia alerta trae tiene prioridad.
6. Haz clic en **Crear**. La página del origen se abre con un diálogo que muestra su token y la configuración con el token ya incluido; Alibaba Cloud CloudMonitor solo necesita la dirección de recepción, así que el diálogo muestra la dirección con el token incluido.

<Warning>
  El token solo se muestra al crear el origen o al rotar su token. Después de cerrar el diálogo, solo se puede ver el prefijo que empieza por `mspat-`. Si se pierde el token, haz clic en **Rotar token** para obtener uno nuevo; el token anterior deja de funcionar de inmediato.
</Warning>

## Dirección de recepción y token

Todos los orígenes comparten una misma dirección de recepción. El token indica a qué origen pertenece una alerta:

```text
https://<molesignal-host>/api/v1/intake/alerts
```

Un token tiene el formato `mspat-<36>`, la misma estructura que un token de API, pero solo recibe alertas, y un token de API no puede recibir alertas. El remitente lo incluye en una cabecera:

```text
Authorization: Bearer <token>
```

Un remitente que no puede establecer cabeceras (Alibaba Cloud CloudMonitor, Tencent Cloud Observability Platform, Amazon CloudWatch mediante SNS, Azure Monitor, Google Cloud Monitoring, Huawei Cloud Eye mediante SMN) lleva el token en la dirección: `https://<molesignal-host>/api/v1/intake/alerts?token=<token>`.

El remitente debe poder alcanzar esta dirección. Cuando haya un firewall delante de MoleSignal, permite las direcciones de salida del sitio o la región del remitente: Datadog las enumera por sitio en la sección `webhooks` de sus `ip-ranges`, PagerDuty las publica para sus regiones de servicio de EE. UU. y la UE, y Alibaba Cloud CloudMonitor enumera sus rangos de envío en la documentación de devoluciones de llamada de alarmas. Cuando MoleSignal se ejecute en una red interna, consulta [Acceso público](/es/public-access) para abrir solo esta dirección a internet.

## Configurar el remitente

**Recepción** en la página de la fuente proporciona la dirección de recepción, el token y la configuración de cada tipo en tres pasos. Sustituye `<TOKEN>` por el token de la fuente. Cuando la fuente recibe su primera solicitud, se comprueban los tres pasos.

### API

```bash
curl -X POST https://<molesignal-host>/api/v1/intake/alerts \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{"dedupKey": "disk-full/web-1", "summary": "Disk almost full on web-1", "severity": "critical", "labels": {"host.name": "web-1"}}'
```

`action` es `trigger` (el valor predeterminado), `acknowledge` o `resolve`. Usa el mismo `dedupKey` para reconocer o resolver la misma alerta. [Enviar alertas](/es/api/alerting/send-alerts) describe cada campo.

### Alertmanager

Añade un receptor a `alertmanager.yml` y enruta las alertas hacia él:

```yaml
route:
  receiver: molesignal
receivers:
  - name: molesignal
    webhook_configs:
      - url: https://<molesignal-host>/api/v1/intake/alerts
        send_resolved: true
        http_config:
          authorization:
            credentials: <token>
```

Mantén `send_resolved` en `true` o las recuperaciones nunca se enviarán. Asigna a cada réplica de un mismo clúster de Alertmanager el mismo `--web.external-url`: la URL externa forma parte de la clave de deduplicación, de modo que los grupos con el mismo nombre de Alertmanagers en varias regiones con el mismo enrutamiento no se fusionan en un solo incidente.

### Grafana

1. En Grafana, abre **Alertas → Puntos de contacto** y haz clic en **Añadir punto de contacto**.
2. Establece **Integración** en **Webhook** y **URL** en la dirección de recepción.
3. En **Ajustes opcionales del webhook**, establece **Esquema de encabezado de autenticación** en `Bearer` y **Credenciales del encabezado de autenticación** en el token.
4. Deja **Desactivar mensaje de resolución** sin marcar, guarda y usa el punto de contacto en una política de notificación.

Con aprovisionamiento por archivo:

```yaml
apiVersion: 1
contactPoints:
  - orgId: 1
    name: molesignal
    receivers:
      - uid: molesignal
        type: webhook
        settings:
          url: https://<molesignal-host>/api/v1/intake/alerts
          httpMethod: POST
          authorization_scheme: Bearer
          authorization_credentials: <token>
```

### Datadog

1. En Datadog, abre **Integraciones → Webhooks** y añade un webhook, llamado por ejemplo `molesignal`.
2. Establece **URL** en la dirección de recepción y **Encabezados personalizados** en `{"Authorization": "Bearer <token>"}`. Deja **Codificar como formulario** sin marcar.
3. Establece **Carga útil** en la plantilla de abajo. Los nombres de los campos son de MoleSignal y los valores son variables de Datadog; una solicitud sin esta plantilla se rechaza.

```json
{
  "alert_id": "$ALERT_ID",
  "alert_cycle_key": "$ALERT_CYCLE_KEY",
  "transition": "$ALERT_TRANSITION",
  "alert_type": "$ALERT_TYPE",
  "priority": "$ALERT_PRIORITY",
  "title": "$ALERT_TITLE",
  "event_title": "$EVENT_TITLE",
  "message": "$TEXT_ONLY_MSG",
  "scope": "$ALERT_SCOPE",
  "tags": "$TAGS",
  "hostname": "$HOSTNAME",
  "link": "$LINK",
  "snapshot": "$SNAPSHOT",
  "query": "$ALERT_QUERY",
  "org_id": "$ORG_ID",
  "last_updated": "$LAST_UPDATED"
}
```

4. Menciona `@webhook-molesignal` en el mensaje de notificación de un monitor.

Todos los sitios de Datadog (`datadoghq.com`, `datadoghq.eu`, `us3`, `us5`, `ap1` y los demás) pueden enviar a una misma fuente: el sitio se toma del dominio de `$LINK` y forma parte de la clave de deduplicación, junto con el ID de organización.

### PagerDuty

1. En PagerDuty, abre **Integraciones → Webhooks genéricos (v3)** y haz clic en **Nuevo webhook**.
2. Establece **URL del webhook** en la dirección de recepción y elige el **Tipo de ámbito** (la cuenta, un servicio o un equipo).
3. En **Suscripción a eventos**, selecciona `incident.triggered`, `incident.acknowledged`, `incident.resolved`, `incident.reopened` e `incident.priority_updated`.
4. Añade el encabezado personalizado `Authorization` con el valor `Bearer <token>`.

Las cuentas de la región de servicio de EE. UU. y de la UE pueden enviar a una misma fuente: el dominio de la cuenta (`<subdomain>.pagerduty.com` o `<subdomain>.eu.pagerduty.com`) forma parte de la clave de deduplicación y se escribe en la etiqueta `pagerduty.region`.

### Alibaba Cloud CloudMonitor

Añade el token a la dirección de recepción:

```text
https://<molesignal-host>/api/v1/intake/alerts?token=<token>
```

- **Alarmas de umbral**: introduce esta dirección como la **devolución de llamada de alarma** de una regla de alarma. CloudMonitor envía la devolución de llamada mediante POST con codificación de formulario; MoleSignal también lee JSON.
- **Eventos del sistema**: en **Centro de eventos → Suscripción a eventos → Canales push**, crea un canal con el tipo de destino **Webhook**, el método de solicitud **POST** y el formato de datos **JSON**, introduce esta dirección y usa el canal en una política de suscripción.

CloudMonitor espera 5 segundos una devolución de llamada de evento del sistema y reintenta 3 veces. MoleSignal espera como máximo 3 segundos cuando remite una solicitud al [clúster de recepción](#varios-clústeres), y responde `503` si se agota el tiempo de espera para que CloudMonitor reintente. Los sitios de China e internacionales y todas las regiones envían el mismo formato; la región se escribe en la etiqueta `aliyun.region`, y el `userId` de la cuenta forma parte de la clave de deduplicación.

### Tencent Cloud Observability Platform

En Tencent Cloud Observability Platform (antes Cloud Monitor), edita o crea una plantilla en **Gestión de alarmas → Plantillas de notificación**, introduce la dirección de recepción como su **devolución de llamada de API** y vincula la plantilla a tus políticas de alarma. La devolución de llamada de Tencent Cloud no puede establecer encabezados, así que el token va en la dirección. Trata la dirección como una credencial: la devolución de llamada no lleva firma y la dirección es lo que identifica a la fuente. Funcionan tanto las alarmas de métricas como las de eventos, y se envían tanto los disparos como las recuperaciones.

- **Deduplicación**: la misma cuenta, política de alarma, nombre de métrica o de evento, y objeto forman una alerta. Una política con niveles tiene un incidente por nivel, y cada uno se recupera por su cuenta, como en Tencent Cloud.
- **Gravedad**: `alarmLevel` Serious (`Serious`) es crítica, Severe (`Warn`) es error y Reminder (`Remind`) es información. Una política sin niveles toma la gravedad predeterminada de la fuente.
- **Eventos sin estado** (`alarmStatus` es `5`) abren un incidente sin recuperación que esperar, así que una persona lo resuelve.
- **Marcas de tiempo** en la devolución de llamada no incluyen zona horaria y se leen como hora de Pekín.

### Amazon CloudWatch

Las alarmas de CloudWatch no llaman a direcciones externas por sí mismas; pasan por SNS:

1. En las notificaciones de la alarma, envía tanto la entrada en **En alarma** (`ALARM`) como la vuelta a **OK** al mismo tema de SNS. Sin `OK`, los incidentes no se resuelven solos. Para las alertas sin datos, envía también **Datos insuficientes** (`INSUFFICIENT_DATA`).
2. Añade una suscripción HTTPS al tema con la dirección de recepción como punto de conexión y el token en la dirección:

   ```bash
   aws sns subscribe \
     --topic-arn <ARN of the topic> \
     --protocol https \
     --notification-endpoint 'https://<molesignal-host>/api/v1/intake/alerts?token=<token>'
   ```

3. La suscripción se confirma sola: MoleSignal comprueba la firma del mensaje de confirmación y luego visita su `SubscribeURL`.

MoleSignal comprueba la firma de cada mensaje de SNS, así que **Entrega de mensajes sin procesar** debe permanecer desactivada. Si está activada, los mensajes se rechazan, y Recibidos recientemente en la página de la fuente indica por qué. El certificado de firma procede de `sns.<region>.amazonaws.com`, así que el nodo que recibe la solicitud debe poder acceder a esa dirección.

Las alarmas de CloudWatch no tienen gravedad, así que los incidentes toman la predeterminada de la fuente. El ARN de la alarma es la clave de deduplicación, también para las alarmas compuestas. La descripción de la alarma y el motivo del cambio de estado van en las anotaciones; la región, la cuenta, el espacio de nombres, la métrica y las dimensiones van en las etiquetas, así que una etiqueta como `aws.region` puede dirigir el enrutamiento.

### Azure Monitor

Las alertas de Azure Monitor llegan a MoleSignal mediante la acción de webhook de un grupo de acciones:

1. En el grupo de acciones que usan tus reglas de alerta, añade una acción de tipo **Webhook** con la dirección de recepción como URI y el token en la dirección.
2. Establece **Habilitar el esquema de alertas comunes** en **Sí**. Sin él, las solicitudes se rechazan, y Recibidos recientemente en la página de la fuente indica por qué.

Lo mismo con la CLI de Azure:

```bash
az monitor action-group update \
  --resource-group <resource group> \
  --name <action group> \
  --add-action webhook molesignal 'https://<molesignal-host>/api/v1/intake/alerts?token=<token>' usecommonalertschema
```

- **Deduplicación**: el `alertId` de la alerta es la clave de deduplicación y contiene la suscripción de Azure.
- **Disparo y resolución**: `monitorCondition` `Fired` abre el incidente y `Resolved` lo resuelve. Las alertas que no mantienen estado, como las del registro de actividad, solo se disparan, así que una persona las resuelve.
- **Gravedad**: `Sev0` es crítica, `Sev1` error, `Sev2` advertencia, y `Sev3` y `Sev4` información.
- **Etiquetas**: las propiedades personalizadas de la regla de alerta, las dimensiones de la métrica, `azure.subscription_id`, `azure.resource_group`, `azure.resource`, `azure.signal_type`, `azure.monitoring_service` y `azure.metric`. La descripción, la condición, el valor y los destinos van en las anotaciones, con el enlace de investigación como `azure_url`.

### Google Cloud Monitoring

1. En la consola de Google Cloud, abre **Monitoreo → Alertas → Editar canales de notificación** y añade un canal **Webhook** con la dirección de recepción como **URL del punto de conexión** y el token en la dirección.
2. Añade el canal a las notificaciones de tus políticas de alertas. También se envían los incidentes que se cierran, así que los incidentes se resuelven solos.

El canal **Pub/Sub** publica la misma notificación. Para usarlo, crea una suscripción push en su tema con la dirección de recepción como punto de conexión push; MoleSignal desempaqueta el sobre de Pub/Sub.

- **Deduplicación**: el proyecto de ámbito y `incident_id`. Un incidente de Monitoring es un incidente.
- **Disparo y resolución**: `state` `open` abre el incidente y `closed` lo resuelve.
- **Gravedad**: el nivel de gravedad de la política, `Critical`, `Error` o `Warning`. Una política sin nivel toma la gravedad predeterminada de la fuente.
- **Etiquetas**: las etiquetas del recurso y de la métrica, las etiquetas de usuario de la política y del recurso monitoreado, `gcp.project_id`, `gcp.resource_type`, `gcp.metric` y `gcp.policy`. El resumen, la condición, el valor observado, el umbral y la documentación van en las anotaciones, con la dirección de la consola del incidente como `gcp_url`.

### Huawei Cloud Eye

Las alarmas de Cloud Eye (CES) no llaman a direcciones externas por sí mismas; pasan por SMN:

1. En Simple Message Notification, añade una suscripción a un tema con el protocolo **HTTPS** y la dirección de recepción como punto de conexión, con el token en la dirección.
2. La suscripción se confirma sola: MoleSignal comprueba la firma del mensaje de confirmación y luego visita su `subscribe_url`.
3. En las notificaciones de alarma de tus reglas de alarma de Cloud Eye, elige ese tema y notifica tanto la alarma como su recuperación. Sin la recuperación, los incidentes no se resuelven solos.

MoleSignal comprueba la firma de cada mensaje de SMN. El certificado de firma procede de `smn.<region>.myhuaweicloud.com`, así que el nodo que recibe la solicitud debe poder acceder a esa dirección.

- **Deduplicación**: el proyecto del tema, el `alarm_id` de la regla de alarma y el recurso. Una regla sobre varios recursos abre un incidente por recurso.
- **Disparo y resolución**: `alarm_status` `alarm` abre el incidente, `insufficient_data` lo abre como sin datos, y `ok` lo resuelve.
- **Gravedad**: el nivel de alarma: Critical es crítica, Major error, Minor advertencia e Informational información.
- **Etiquetas**: las dimensiones, como `instance_id`, y `huawei.region`, `huawei.project_id`, `huawei.namespace`, `huawei.metric`, `huawei.alarm_id` y `huawei.resource_id`. El texto de la alarma, el valor actual y el umbral van en las anotaciones, con la dirección de la consola de la alarma como `huawei_url`.

### Zabbix

Funciona desde Zabbix 6.0. Zabbix no tiene un formato de solicitud propio: el script de un tipo de medio envía la solicitud. Así, la página de la fuente, y el diálogo al crearla, te dan un tipo de medio con la dirección y el token ya rellenados:

1. Guárdalo como YAML e impórtalo en **Alertas → Tipos de medios → Importar**. Comprueba el parámetro `token`.
2. Establece la macro global `{$ZABBIX.URL}` en la dirección del frontend de Zabbix. Cuenta en la clave de deduplicación, así que una fuente puede recibir varios servidores de Zabbix, y los incidentes enlazan de vuelta a Zabbix. También funciona sin ella.
3. Asigna este medio a un usuario. **Enviar a** puede ser cualquier cosa; el script no lo usa.
4. Añade una acción de trigger cuyas **operaciones**, **operaciones de recuperación** y **operaciones de actualización** vayan todas a ese usuario. Sin operaciones de recuperación, los incidentes no se resuelven solos.

El botón **Prueba** del tipo de medio necesita valores reales: cuando las macros no se expanden (`{EVENT.ID}` llega tal cual), MoleSignal responde `400` e indica que se use el tipo de medio de la documentación.

### Correo electrónico

Hay dos formas de entrada, y ambas leen el correo para generar las mismas alertas.

**Leer un buzón** (recomendado): MoleSignal lee un buzón IMAP de forma programada. Solo necesita una salida y un buzón: ni una dirección pública, ni un registro MX, ni el puerto 25, ni un certificado, lo que lo convierte en la opción más sencilla cuando se autohospeda. Envía el correo de alertas de tu sistema de monitoreo a ese buzón, o reenvíalo allí con una regla de correo.

En la página de la fuente, en **Leer un buzón**, rellena **Servidor IMAP**, **Puerto**, **Cifrado**, **Nombre de usuario**, **Contraseña**, **Carpeta** (`INBOX` de forma predeterminada) y **Leer cada** (de 15 a 3600 segundos, 60 de forma predeterminada). Haz clic en **Probar conexión** y luego en **Guardar buzón**.

- **Solo lectura**: usa `EXAMINE` y `BODY.PEEK[]`, así que nada se marca como leído ni se elimina. Sirve una cuenta de solo lectura.
- **Sin acumulación**: al conectarse por primera vez, anota la posición y lee solo lo que llega después. Un cambio de host, de cuenta o de carpeta, o un servidor que reconstruyó el buzón (`UIDVALIDITY` cambió), empieza de nuevo desde ese momento. Mientras la fuente está apagada no se lee nada y no se guarda ninguna posición: empieza desde el momento en que se vuelve a encender.
- **La lista de remitentes es obligatoria**: cualquiera que conozca la dirección puede enviar correo a ella. En **Aceptar correos de**, en los ajustes de la fuente, escribe direcciones o `@example.com` para un dominio completo; `*` acepta a todos. La lista lee `From`, que se puede falsificar, así que mantén activados el filtrado de spam y DMARC del proveedor de correo. El correo de cualquier otra persona se registra como **Rechazada** y no abre nada.
- **Inicio de sesión**: una contraseña o una contraseña de aplicación del proveedor. Microsoft 365 ya no acepta contraseñas: elige **OAuth 2.0** y rellena la dirección del token `https://login.microsoftonline.com/<tenant>/oauth2/v2.0/token`, el ID de cliente, el secreto de cliente y el ámbito `https://outlook.office365.com/.default`. La aplicación necesita el permiso `IMAP.AccessAsApp` y acceso a este buzón.
- **Sin cifrado** solo debe usarse en una red de confianza: la contraseña la atraviesa sin cifrar.
- Cuando falla una lectura, la página de la fuente indica por qué y la siguiente ronda vuelve a intentarlo. Con varios nodos de alertas, cada buzón lo lee uno de ellos. Con federación, el buzón se configura en el clúster de recepción de la fuente y no se sincroniza, así que la contraseña permanece allí.

**Envía el correo sin procesar por POST**: si ya ejecutas un sistema de correo (el `pipe` de Postfix, SES, el MIME sin procesar de Mailgun), envía el mensaje sin procesar por POST a la dirección de recepción:

```bash
curl -X POST 'https://<molesignal-host>/api/v1/intake/alerts' \
  -H 'Authorization: Bearer <token>' \
  -H 'Content-Type: message/rfc822' \
  --data-binary @alert.eml
```

Esto requiere que la dirección de recepción sea accesible desde ese sistema de correo. La lista de remitentes es opcional aquí, ya que el token ya indica quién llama; se aplica si escribes una.

MoleSignal no tiene un receptor SMTP integrado: eso requeriría un puerto 25 abierto, un registro MX, un certificado TLS y su propio filtrado de spam, algo que la mayoría de las implementaciones autohospedadas no pueden ofrecer.

**Cómo se lee un correo** se configura en **Lectura del correo**, en los ajustes de la fuente:

| Ajuste | Descripción |
|---|---|
| **Asuntos que indican recuperación** | Una expresión regular. Si está vacía, se usa la integrada: `resolved`, `recovered`, `recovery`, `cleared`, `恢复`, `已解决`, y `OK` al principio. El resto del correo dispara. |
| **Clave de deduplicación a partir del asunto** | Una expresión regular; se toma su primer grupo, como `host=(\S+)`. Si está vacía o no hay coincidencia, se usa el asunto simplificado: sin `Re:` ni `Fwd:`, sin palabras de estado (`PROBLEM`, `RECOVERY`, `告警`, `恢复`, etc.), sin gravedades, fechas y horas, ni porcentajes, sin distinguir mayúsculas y minúsculas. Así, "CRITICAL: disk full on web-1 (91%)" y "RECOVERY: disk full on web-1 (40%)" son una alerta, mientras que `web-1` y `web-2` son dos. El dominio del remitente también cuenta en la clave. |
| **Asuntos que no generan alertas** | Una expresión regular. El correo que coincide se omite y aparece en Recibidos recientemente. |

La gravedad procede de palabras del asunto (`critical`, `fatal`, `disaster`, `P1` son crítica; `error`, `P2` error; `warning`, `P3` advertencia; `info`, `notice`, `P4`, `P5` información), o, si no, de la predeterminada de la fuente; las palabras high y low de `High CPU` y `Low disk` no cuentan. El cuerpo va en la anotación `message` (el correo HTML como texto, como máximo 4096 caracteres), el remitente en la etiqueta `email.from` y la anotación `from`, y la hora procede de la cabecera `Date`. Las respuestas automáticas (`Auto-Submitted: auto-replied`) y los rebotes (`multipart/report`) no son alertas. Se entienden GBK, GB2312 y otros conjuntos de caracteres. El correo de más de 4 MiB se registra como **Rechazada** sin leer su cuerpo.

## Cómo se convierten las alertas en incidentes

| Tipo | Clave de deduplicación | Disparador | Resolución | Gravedad |
|---|---|---|---|---|
| **API** | `dedupKey` | `trigger` | `resolve` | `severity` |
| **Alertmanager** | URL externa y `groupKey` | `status` del grupo `firing` | `status` del grupo `resolved`: todas las alertas del grupo se recuperaron | La etiqueta `severity` más alta entre las alertas activas del grupo |
| **Grafana** | URL externa, organización y `groupKey` | Lo mismo | Lo mismo | Lo mismo |
| **Datadog** | Sitio, organización, ID del monitor y alcance | Cualquier transición excepto `Recovered` | `Recovered` | `$ALERT_PRIORITY`; sin ella, Warn y No Data son warning y el resto sigue a `$ALERT_TYPE` |
| **PagerDuty** | Dominio de la cuenta e ID de incidente de PagerDuty | `incident.triggered`, `incident.reopened`; `incident.priority_updated` cambia la gravedad | `incident.resolved` | Prioridad P1 a P5; sin ella, la urgencia high es error y la low es warning |
| **Alibaba Cloud CloudMonitor** | Cuenta, ID de regla y `dimensions`; para eventos del sistema, cuenta y `dedupId` | `ALERT`, `INSUFFICIENT_DATA`; evento del sistema `TRIGGERED` | `OK`; evento del sistema `RESOLVED` | `triggerLevel`; evento del sistema `severity` |
| **Tencent Cloud Observability Platform** | Cuenta, política, nombre de métrica o evento, nivel y objeto | `alarmStatus` es `1` o `5` | `alarmStatus` es `0` | `alarmLevel` |
| **Amazon CloudWatch** | `AlarmArn` | `NewStateValue` es `ALARM` o `INSUFFICIENT_DATA` | `NewStateValue` es `OK` | Ninguna: la gravedad predeterminada del origen |
| **Azure Monitor** | `alertId` | `monitorCondition` es `Fired` | `monitorCondition` es `Resolved` | `severity`: `Sev0` critical, `Sev1` error, `Sev2` warning, `Sev3` y `Sev4` info |
| **Google Cloud Monitoring** | Proyecto de ámbito e `incident_id` | `state` es `open` | `state` es `closed` | `severity`; `No severity` toma la predeterminada del origen |
| **Huawei Cloud Eye** | Proyecto del tema de SMN, `alarm_id` y recurso | `alarm_status` es `alarm` o `insufficient_data` | `alarm_status` es `ok` | Nivel de alarma: Critical, Major, Minor, Informational |
| **Zabbix** | Host de `{$ZABBIX.URL}` y `{EVENT.ID}` | `{EVENT.VALUE}` es 1; también las operaciones de actualización, con la gravedad correspondiente | `{EVENT.VALUE}` es 0, o una operación de actualización cerró el problema | `{EVENT.NSEVERITY}`: Disaster es critical, High error, Average y Warning warning, Information info |
| **Correo electrónico** | El dominio del remitente y la parte tomada del asunto | Otro correo | Un asunto redactado como recuperación | Palabras del asunto |

La prioridad y la urgencia se leen por separado: el `priority` y el `urgency` de la API, el `$ALERT_PRIORITY` de Datadog y la prioridad y la urgencia de PagerDuty se convierten en la prioridad y la urgencia del incidente. Sin urgencia, decide la política de escalado del origen, y una alerta que no informa ninguna gravedad es de urgencia high; consulta [Urgencia](/es/alerting/on-call#urgencia).

Una alerta sin gravedad toma la **Gravedad predeterminada** del origen. Las palabras de gravedad de todos los remitentes no distinguen mayúsculas de minúsculas: `critical`, `crit`, `fatal`, `page` y `P1` son critical; `error`, `major`, `high` y `P2` son error; `warning`, `warn`, `minor`, `medium` y `P3` son warning; `info`, `low`, `P4` y `P5` son info. Cualquier otra palabra toma la gravedad predeterminada.

- **Apertura**: un origen tiene como máximo un incidente activo por clave de deduplicación. El incidente lleva las etiquetas `alert.source=external` y `external.kind=<kind>`, las etiquetas propias de la alerta (para Alertmanager y Grafana, los `commonLabels` del grupo) y las etiquetas adicionales del origen. La etiqueta `service.name` o `service` se convierte en un servicio afectado, y `host.name`, `host` o `hostname` se convierte en un host.
- **Título**: la API usa `summary`; Alertmanager y Grafana usan la anotación `summary`, o `alertname` si no la hay; Datadog usa `$ALERT_TITLE`; PagerDuty usa el título del incidente; Alibaba Cloud CloudMonitor usa "nombre de la alarma · nombre de la instancia".
- **Enlaces**: las direcciones que apuntan al remitente se escriben en anotaciones, como `alertmanager_url`, `generator_url`, `dashboard_url`, `datadog_url` y `pagerduty_url`, y la página del incidente las muestra como enlaces. Los `links` de la API se escriben en anotaciones por `name`.
- **Alertas de un grupo**: un incidente de Alertmanager o Grafana conserva todas las alertas del grupo (hasta 100) con su estado, actualizadas con cada notificación. **Alerta externa** en la página del incidente las lista, con las etiquetas que las distinguen.
- **Cambios de gravedad**: un incidente que aún no se ha confirmado sigue la gravedad de la alerta, tal como la deciden los [pipelines de alertas](/es/pipelines/alert-events#cambios-de-gravedad). Cuando sube, el escalado vuelve a empezar desde el primer paso. Una gravedad establecida a mano se mantiene.
- **Confirmación**: el `acknowledge` de la API, el `incident.acknowledged` de PagerDuty y las operaciones de actualización de Zabbix que confirman un problema confirman el incidente y detienen los siguientes pasos de escalado y las llamadas. No se registra ningún usuario como autor de la confirmación.
- **Resolución**: el incidente se resuelve cuando el origen informa la recuperación, incluidos los incidentes confirmados. No se registra ningún usuario como autor de la resolución, y la línea de tiempo lo muestra como recuperado.
- **Mensajes tardíos**: cada clave de deduplicación recuerda la hora del remitente más reciente que usó, y un mensaje más antiguo se ignora. Un disparador tardío no abre un incidente zombi, y una recuperación tardía no cierra uno nuevo. La API no lleva hora, así que sus mensajes se toman en el orden en que llegan.
- **Resuelto antes por una persona**: cuando el origen sigue informando la alerta, su siguiente reenvío abre un incidente nuevo, como en las reglas.
- **Sin datos**: los incidentes abiertos por `INSUFFICIENT_DATA` de CloudMonitor, `insufficient_data` de Cloud Eye y No Data de Datadog llevan `alert.condition=no_data`, y sus títulos de notificación empiezan por `NO DATA`.
- **Desactivación y eliminación**: un origen desactivado rechaza las alertas (`409`), y sus incidentes abiertos permanecen. Eliminar un origen hace que su token deje de funcionar de inmediato y resuelve sus incidentes abiertos.

Las [políticas de silencio](/es/alerting/silences), los [grupos semánticos](/es/alerting/silences#grupos-semánticos) y las [políticas de notificación](/es/notification-channels) se aplican a los incidentes externos como a cualquier otro. Hazlas coincidir por `external.kind`, por las etiquetas adicionales de un origen o por las etiquetas propias de la alerta.

## Solicitudes recientes

La parte superior de la página del origen indica cómo está el origen: **En espera de la primera solicitud**, **Recibiendo solicitudes**, **Última solicitud rechazada**, **Sin solicitudes en los últimos 7 días** o **Desactivada**. Junto a ella están las solicitudes y alertas de las últimas 24 horas, y los incidentes que el origen abrió y siguen abiertos.

Una vez que han llegado solicitudes, **Solicitudes recientes** en la página del origen lista las solicitudes que recibió el origen: la hora, el resultado (**Procesada**, **Rechazada** o **Reenviada**), el estado HTTP, el número de alertas y qué ha sido de ellas (**Abierta**, **Última actualización**, **Sin cambios**, **Confirmado**, **Resuelto** o **Ignorado**). Haz clic en una fila para ver el título, la gravedad, la acción, el resultado y el incidente de cada alerta; una solicitud rechazada también muestra el motivo y el inicio de su cuerpo (hasta 16 KiB). Se conservan las últimas 500 solicitudes de cada origen, durante un máximo de 7 días.

## Varios clústeres

Con la [federación entre clústeres](/es/settings/data-plane#federación-de-clústeres) activada:

- Las fuentes se sincronizan entre clústeres como el resto de la configuración de alertas, tokens incluidos, así que un token funciona en la dirección de ingesta de todos los clústeres.
- Los incidentes de una fuente se abren solo en su **Clúster receptor**: el clúster en el que se creó, salvo que se cambie en la configuración de la fuente. Otro clúster que recibe una alerta de la fuente la pasa por gRPC al clúster receptor y devuelve al remitente la respuesta del clúster receptor. Por tanto, una alerta externa es un solo incidente, sin importar a la dirección de qué clúster llegue.
- Cuando no se puede alcanzar el clúster receptor, la respuesta es `503` y el remitente reintenta. Si la región del clúster receptor sigue caída, cambia el **Clúster receptor** en la configuración de la fuente por uno que esté activo.
- **Solicitudes recientes** se registra en el clúster que atendió la solicitud. La página de la fuente lo indica cuando se abre en otro clúster.

## Límites

| Elemento | Límite |
|---|---|
| Cuerpo de la solicitud, un correo | Como máximo 4 MiB. |
| Lectura de un buzón | Como máximo 50 correos a la vez; el resto en la siguiente ronda. |
| Una solicitud a la API | 100 alertas; `dedupKey` de hasta 255 caracteres, `summary` de hasta 1024 caracteres. |
| Una alerta | 64 etiquetas y 64 anotaciones. La API rechaza más; en los demás tipos se descartan las restantes, y los títulos y las anotaciones demasiado largos se recortan. |
| Alertas de un grupo | Se conservan 100. |
| Etiquetas adicionales de una fuente | 32, sin ninguna clave que empiece por `alert.` ni `external.kind`. |
| Solicitudes recientes | Las últimas 500 solicitudes de cada fuente, durante un máximo de 7 días. |

La firma HMAC de Grafana y la firma de PagerDuty no se verifican; el token ya identifica la fuente. Reconocer o resolver un incidente en MoleSignal no se escribe de vuelta al remitente.
