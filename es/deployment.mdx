MoleSignal se distribuye como un único binario y una única imagen de contenedor. La configuración determina qué [roles](/es/deployment/role-based) ejecuta un proceso: un solo proceso puede ejecutar todos los roles o puedes repartirlos entre varios procesos. Cada implementación necesita dos servicios externos: PostgreSQL y almacenamiento de objetos.

## Requisitos

| Componente | Requisito |
|---|---|
| PostgreSQL | Almacena los metadatos, las identidades, el catálogo de archivos y los recursos del producto. PostgreSQL es la única base de datos de metadatos compatible. El entorno de pruebas de Compose y los manifiestos de Kubernetes usan PostgreSQL 17. |
| Almacenamiento de objetos | Almacena archivos Parquet, índices de búsqueda y blobs de perfiles. Usa `s3` (AWS S3 o un servicio compatible con S3 como RustFS, Cloudflare R2 o Alibaba Cloud OSS), `azure` o `gcs`. Usa el backend `local` solo en implementaciones de un nodo o para desarrollo. |
| Recursos de cómputo | Linux en x86-64 o arm64 con la imagen de contenedor (`linux/amd64` y `linux/arm64`). El entorno de pruebas necesita unos 2 GB de memoria. |
| Disco local | Solo almacena cachés, que se pueden reconstruir. MoleSignal confirma cada escritura cuando el objeto de su registro de escritura anticipada (WAL) ya está en el almacenamiento de objetos. Por eso, ningún nodo necesita un volumen persistente. Consulta [Durabilidad y toma de control](/es/architecture#durabilidad-y-recuperación). |

El consumo de memoria y de disco depende del volumen de ingesta, de la cantidad de flujos activos y de los ajustes de caché en [Configuración](/es/configuration). Dimensiona los recursos según el uso observado: el [uso de ingesta](/es/streams#uso-de-ingesta-y-presupuestos) muestra cuánto ingiere cada fuente y el proceso expone métricas de Prometheus en `/metrics`. Consulta la [Lista de verificación para producción](/es/deployment/production-checklist).

## Imagen de contenedor

La imagen está disponible como `ghcr.io/molesignal/molesignal`. Cada versión incluye una etiqueta de versión (por ejemplo, `26.1.0.0`) y una etiqueta de canal (por ejemplo, `alpha`). Fija la etiqueta de versión en producción.

```bash
docker pull ghcr.io/molesignal/molesignal:26.1.0.0
```

La misma imagen sirve para todos los roles. La variable de entorno de ejecución `RELEASE_CHANNEL` (`alpha`, `beta`, `rc` o `stable`) indica el nivel de madurez de la implementación y no modifica el binario. El binario incorpora la interfaz web y la sirve en el puerto HTTP.

## Opciones de implementación

<Tabs>
  <Tab title="Docker Compose">
    El repositorio incluye el archivo `deploy/docker/docker-compose.yaml` con dos perfiles. Ambos inician PostgreSQL 17 y RustFS, y ejecutan la imagen de MoleSignal de `ghcr.io/molesignal/molesignal`.

    ```bash
    # Everything in one process: serves the complete product
    docker compose -f deploy/docker/docker-compose.yaml --profile standalone up

    # One container per role
    docker compose -f deploy/docker/docker-compose.yaml --profile multirole up
    ```

    El perfil `multirole` implementa un contenedor por rol. El enrutador publica la interfaz web y la API HTTP en el puerto `5080`, y el receptor OTLP gRPC en el puerto `4317`. Consulta [Implementación por roles](/es/deployment/role-based).

    El servicio autónomo publica los puertos `5080` y `5082`. No publica el puerto `4317` de OTLP gRPC. Para enviar datos por OTLP gRPC desde el host, agrega la asignación `4317:4317` al servicio.

    El archivo de Compose configura un entorno de pruebas: usa credenciales predeterminadas, una clave de cifrado de desarrollo y un token `MS_SELF_TELEMETRY_CLUSTER_TOKEN` de desarrollo para el perfil `multirole`. Reemplázalos antes de almacenar datos reales. Consulta la [Lista de verificación para producción](/es/deployment/production-checklist). El bucket del entorno de pruebas es privado.
  </Tab>
  <Tab title="Binario y systemd">
    Instala el binario de la versión publicada, el archivo de configuración y la base de datos GeoIP. Luego, ejecuta MoleSignal como servicio de systemd.

    ```bash
    sudo useradd --system --home-dir /var/lib/molesignal \
      --shell /usr/sbin/nologin molesignal
    sudo install -Dm755 bin/molesignal /usr/local/bin/molesignal
    sudo install -d -o root -g molesignal -m 0750 /etc/molesignal
    sudo install -o root -g molesignal -m 0640 \
      conf/config.toml /etc/molesignal/config.toml
    sudo install -Dm644 deploy/systemd/molesignal.service \
      /etc/systemd/system/molesignal.service
    sudo install -Dm644 mmdb/dbip-city-lite.mmdb \
      /usr/share/molesignal/mmdb/dbip-city-lite.mmdb
    ```

    Configura el canal de ejecución en `/etc/molesignal/molesignal.env`:

    ```ini
    RELEASE_CHANNEL=alpha
    ```

    Edita `/etc/molesignal/config.toml` para configurar PostgreSQL, el almacenamiento de objetos y los secretos. Luego, inicia el servicio:

    ```bash
    sudo systemctl daemon-reload
    sudo systemctl enable --now molesignal
    sudo systemctl status molesignal
    ```

    La unidad usa `/var/lib/molesignal` como directorio de estado y concede `CAP_NET_BIND_SERVICE` para que el receptor TLS integrado pueda escuchar en los puertos `80` y `443`.
  </Tab>
  <Tab title="Helm">
    El chart oficial implementa MoleSignal en Kubernetes 1.27 o posterior con Helm 3.8 o posterior. Requiere MoleSignal 26.2.0.0 o posterior. El repositorio del chart es `https://charts.molesignal.com`. También puedes obtener el mismo chart en `oci://ghcr.io/molesignal/charts/molesignal`.

    De forma predeterminada, el chart ejecuta un solo proceso con todos los roles, una instancia de PostgreSQL 17 y una de RustFS. Ninguna de las dos instancias tiene copias de seguridad ni conmutación por error, así que usa esta configuración solo para evaluación.

    ```bash
    helm repo add molesignal https://charts.molesignal.com
    helm repo update
    helm install molesignal molesignal/molesignal --namespace molesignal --create-namespace
    ```

    Para abrir la interfaz web, configura el reenvío de puertos y luego ve a `http://127.0.0.1:5080`:

    ```bash
    kubectl --namespace molesignal port-forward svc/molesignal 5080:5080
    ```

    Para producción, ejecuta los roles como cargas de trabajo independientes, desactiva los servicios incluidos y configura el chart para usar instancias externas de PostgreSQL y de almacenamiento de objetos. Crea primero los dos objetos Secret: `molesignal-db` contiene la clave `database-dsn` y `molesignal-s3` contiene `access-key` y `secret-key`.

    ```yaml
    mode: distributed

    postgresql:
      enabled: false
    externalDatabase:
      existingSecret: molesignal-db

    rustfs:
      enabled: false
    objectStore:
      bucket: example-telemetry
      region: eu-west-1
      existingSecret: molesignal-s3
    ```

    [`examples/production.yaml`](https://github.com/molesignal/molesignal-helm/blob/main/examples/production.yaml) agrega TLS, escalado automático y presupuestos de interrupción. El [README del chart](https://github.com/molesignal/molesignal-helm/tree/main/charts/molesignal) enumera todos los valores.

    | Tema | Detalle |
    |---|---|
    | Clave de cifrado | El chart genera la clave en la primera instalación y la conserva tras las actualizaciones y `helm uninstall`. Guarda una copia de seguridad: sin la clave no puedes leer los campos cifrados. Si usas Argo CD u otra herramienta que genera manifiestos con `helm template`, configura `secrets.cipherKey` y `secrets.clusterToken` o haz que `secrets.existingSecret` apunte a un Secret. |
    | Imágenes | Todas las imágenes, salvo la de PostgreSQL, usan `latest` y se descargan cada vez que se inicia un pod. Para producción, fija `image.tag` y establece `image.pullPolicy` en `IfNotPresent`. |
    | Ingress | Configura `ingress.enabled`. Si usas un Ingress, registra la red de los pods del controlador como proxy de confianza en [Reconocimiento de IP del cliente](/es/settings/platform#identificación-de-la-ip-del-cliente). |
    | Configuración de la aplicación | Agrega los ajustes en `config` con la estructura de `conf/config.toml`. |

    Consulta la clave de cifrado de la instalación predeterminada:

    ```bash
    kubectl --namespace molesignal get secret molesignal-secret -o jsonpath='{.data.cipher-key}' | base64 --decode
    ```
  </Tab>
  <Tab title="Manifiestos de Kubernetes">
    Los manifiestos de [`deploy/k8s/`](https://github.com/molesignal/molesignal/tree/main/deploy/k8s) usan la misma imagen para todos los roles. Hacen referencia a la imagen de ejemplo `molesignal:dev`. Reemplázala por `ghcr.io/molesignal/molesignal:<version>` en todas las cargas de trabajo.

    Los manifiestos no incluyen PostgreSQL ni almacenamiento de objetos. Proporciona PostgreSQL 17 con el nombre de servicio `postgresql` (o edita `meta_database.dsn` en el ConfigMap) y un almacenamiento de objetos compatible con S3 (edita `object_store` en el ConfigMap).

    Los manifiestos implementan una topología con roles separados: la carga de trabajo `router` sirve la interfaz web y la API HTTP, y las demás ejecutan los roles de datos y de procesamiento en segundo plano. Para ejecutar todos los roles en un solo proceso, parte de `40-intake.yaml` (un Deployment sin volumen persistente), establece `MS_NODE_ROLES` en `["standalone"]`, agrega el puerto `5080` al Service y usa `/api/v1/healthz` como sonda.

    | Carga de trabajo | Tipo | Réplicas | Rol |
    |---|---|---|---|
    | `router` | Deployment | 2 | `router`: la interfaz web, la API HTTP y OTLP gRPC |
    | `intake` | Deployment | 2 | `intake`, sin volumen persistente; en una actualización gradual, se inicia un pod nuevo antes de detener uno anterior |
    | `querier` | Deployment | 2 | `querier` |
    | `compactor` | Deployment | 1 | `compactor`, admite más réplicas |
    | `alert` | Deployment | 1 | `alert`, admite más réplicas |

    Los nodos con roles separados usan un token `MS_SELF_TELEMETRY_CLUSTER_TOKEN` compartido para autenticar las trazas candidatas y la telemetría propia que se reenvían entre sí. La captura de trazas está activa de forma predeterminada, por lo que todas las cargas de trabajo leen el mismo valor de la clave `self_telemetry_cluster_token` de `molesignal-secret`. Crea el espacio de nombres, la configuración y el secreto. Luego, aplica las cargas de trabajo:

    ```bash
    kubectl apply -f 00-namespace.yaml
    kubectl apply -f 10-configmap.yaml
    kubectl create secret generic molesignal-secret -n molesignal \
      --from-literal=object_store_access_key="<access-key>" \
      --from-literal=object_store_secret_key="<secret-key>" \
      --from-literal=cipher_key="$(openssl rand -base64 32)" \
      --from-literal=self_telemetry_cluster_token="$(openssl rand -base64 32)" \
      --dry-run=client -o yaml | kubectl apply -f -
    kubectl apply -f 30-router.yaml -f 40-intake.yaml -f 50-querier.yaml \
                  -f 60-compactor.yaml -f 70-alert.yaml
    ```

    Las cargas de trabajo seleccionan su rol con la variable de entorno `MS_NODE_ROLES`. Verifica el clúster a través del enrutador:

    ```bash
    kubectl -n molesignal port-forward svc/router 5080:5080
    curl http://127.0.0.1:5080/api/v1/healthz
    ```

    El binario incluye la interfaz web. Expón el puerto `5080` de la carga de trabajo `router` mediante un Ingress o un balanceador de carga.

    La carga de trabajo `router` sirve la API completa en el puerto `5080` y su sonda de disponibilidad envía `GET /api/v1/healthz`. Las demás cargas de trabajo escuchan en el puerto `5080` para ofrecer comprobaciones de estado y disponibilidad, así como métricas, y usan `GET /api/v1/readyz` como sonda de disponibilidad. Un pod `intake` acepta escrituras en cuanto está listo. No reprocesa el WAL al iniciar, porque los demás pods de ingesta se hacen cargo del WAL del pod perdido. El período de gracia de 45 segundos le permite volcar los datos pendientes y liberar su WAL antes de detenerse.
  </Tab>
</Tabs>

## Agentes de sondeo

Un agente de sondeo ejecuta comprobaciones sintéticas desde una red privada, una región o una ubicación perimetral. Solo abre conexiones salientes a los puertos `5084` y `5085` de un nodo `standalone` o `alert`. Usa su propia imagen, `ghcr.io/molesignal/probe-agent`, que se publica con las mismas etiquetas que la imagen de MoleSignal.

| Entorno de ejecución | Instalación | Dónde conserva su identidad |
|---|---|---|
| Kubernetes | Chart de Helm `probe-agent` de `https://charts.molesignal.com` o de `oci://ghcr.io/molesignal/charts/probe-agent` | Un volumen persistente por réplica |
| Docker | Imagen `ghcr.io/molesignal/probe-agent` | Un volumen montado en `/var/lib/molesignal-probe` |
| Linux | Binario publicado `probe-agent` | El directorio indicado con `--state-dir` |

Consulta [Ejecutar agentes en Kubernetes](/es/synthetics#ejecuta-agentes-en-kubernetes) para obtener información sobre el chart y [Ubicaciones y agentes de sondeo](/es/synthetics#ubicaciones-y-agentes-de-sondeo) para obtener información sobre el registro y la configuración del servidor.

## Puertos

| Puerto | Propósito | Exposición |
|---|---|---|
| `5080` | Interfaz web, API HTTP, `/metrics` y endpoint de estado. En todos los roles excepto `router` y `standalone`, solo ofrece comprobaciones de estado y disponibilidad, y métricas. | Público detrás de TLS en `router` y `standalone`. Privado en los demás roles. |
| `4317` | Receptor OTLP gRPC. gRPC sin TLS. | Público solo detrás de un proxy que termina TLS o dentro de una red de confianza. |
| `5082` | gRPC interno para el tráfico entre nodos: reenvío de escrituras, reenvío de consultas y escaneo de fragmentos | Privado. No lo expongas nunca. |
| `5083` | Arrow Flight SQL para clientes de bases de datos. Desactivado de forma predeterminada. | Opcional, detrás de TLS. |
| `5084`, `5085` | Registro y control de Probe Agent para ubicaciones privadas de monitoreo sintético | Solo cuando los Probe Agent se ejecutan fuera del nodo. |
| `80`, `443` | Receptor TLS integrado con certificados automáticos cuando `[http.tls].enabled` tiene el valor `true` | Público. |

## Estado y métricas

- `GET /api/v1/healthz` es público. Devuelve `200` con `{"status":"ok"}` o `503` con un campo `reason` si no puede acceder al almacenamiento de objetos. Úsalo para las comprobaciones de los contenedores y los balanceadores de carga.
- `GET /metrics` es público y devuelve métricas de Prometheus. Restringe el acceso en el proxy o en la capa de red.
- `GET /api/v1/readyz` y `GET /api/v1/version` requieren un token de tipo bearer en un nodo `standalone` o `router`. `version` devuelve la versión, el commit, el ID de compilación, el canal de lanzamiento y la edición.
- En un clúster con roles separados, un nodo que no ofrece la API completa responde a `GET /api/v1/healthz`, `GET /api/v1/readyz` y `GET /metrics` sin autenticación en el mismo puerto.

Consulta [Autoobservabilidad](/es/self-observability) para conocer las métricas y la telemetría integrada del propio servicio.
