El monitoreo sintético comprueba un servicio desde el exterior antes de que un cliente informe de una falla. Abre
**Monitoreo sintético** para crear comprobaciones, publicar programaciones, revisar la evidencia de ejecución y administrar
las ubicaciones privadas de las sondas.

## Qué puedes monitorear

| Tipo de comprobación | Para qué sirve |
|---|---|
| **HTTP / API** | Valida la URL, el método, los encabezados, el cuerpo, el estado de la respuesta, el contenido y los tiempos. |
| **Navegador** | Ejecuta un recorrido en el navegador y valida los resultados de las páginas o de los pasos. |
| **TCP** | Confirma que un host y un puerto aceptan una conexión. |
| **DNS** | Resuelve cualquier tipo de registro (A, AAAA, CNAME, MX, NS, TXT, SOA, SRV, CAA, PTR) con el resolutor del sistema o con uno específico, exige DNSSEC de forma opcional y valida las respuestas y el código de respuesta. |
| **ICMP / Ping** | Envía algunos pings y comprueba la pérdida de paquetes y el tiempo promedio de ida y vuelta. |
| **TLS** | Valida la negociación TLS, la identidad del certificado y su vencimiento. |
| **gRPC** | Llama a un endpoint gRPC y valida la respuesta. |
| **Señal de actividad** | Comprueba que una tarea o un servicio externo envíe una señal antes del plazo. |

Para una comprobación gRPC, escribe la **Dirección** como `host:port`. Solo **Usar TLS** determina si la llamada
usa TLS. MoleSignal rechaza las direcciones cuyo esquema contradice esa opción, como `http://` con **Usar TLS**
habilitado.

## Crea y publica una comprobación

<Steps>
  <Step title="Crea un borrador">
    Abre **Monitoreo sintético → Comprobaciones**, selecciona **Crear comprobación** y elige un tipo. Configura el destino,
    el tiempo de espera, las aserciones, la programación y una o más ubicaciones. Toda comprobación nueva empieza como borrador.
  </Step>
  <Step title="Prueba la revisión">
    Selecciona **Probar revisión**. MoleSignal ejecuta el borrador sin activar su programación. Revisa el
    destino resuelto, los intentos, los tiempos, la evidencia de las aserciones y los errores.
  </Step>
  <Step title="Publica la revisión">
    Si la prueba tiene éxito, MoleSignal habilita **Publicar revisión**. Al publicar, MoleSignal activa la revisión y
    calcula su primera ejecución programada.
  </Step>
  <Step title="Administra el monitor">
    Usa **Ejecutar ahora** para iniciar una ejecución bajo demanda. Al editar la comprobación, creas otra revisión en borrador, por lo que la
    configuración publicada sigue en uso hasta que pruebes y publiques la revisión nueva.
    Pausa, reanuda o archiva la comprobación sin borrar su historial de resultados.
  </Step>
</Steps>

<Note>
El requisito de probar el borrador impide que un destino o una aserción sin probar reemplace sin aviso una programación
de producción que funciona.
</Note>

## Programación y reintentos

Usa un intervalo o una expresión cron con una zona horaria explícita. La mayoría de las comprobaciones activas aceptan intervalos
de 10 segundos a un día; las de navegador tienen un mínimo de 60 segundos. Configura un tiempo de espera de entre 100
milisegundos y cinco minutos, siempre menor que el intervalo. MoleSignal puede reintentar una ejecución hasta dos
veces antes de registrar el resultado final.

Las comprobaciones de señal de actividad usan un plazo de recepción en lugar de una programación de solicitudes salientes. Envía la señal de actividad desde
la carga de trabajo responsable de la tarea y consulta el historial de resultados para distinguir una señal tardía de una
sonda activa fallida.

## Aserciones y estado

Las aserciones inspeccionan campos específicos del protocolo, como el estado de la respuesta, el cuerpo, los encabezados, las respuestas DNS,
las propiedades del certificado o los resultados del navegador. Si una aserción de nivel **Advertencia** falla, el resultado es degradado;
si falla una de nivel **Crítico**, el resultado es fallido.

Cada tipo de comprobación ofrece los valores que incluye su respuesta:

| Tipo de comprobación | Fuentes de las aserciones |
|---|---|
| **HTTP / API** | `status`, `body`, `json:<JSONPath>`, `header:<name>`, `duration_ms`, `size_bytes`, `timing.dns_ms`, `timing.connect_ms`, `timing.tls_ms`, `timing.first_byte_ms` |
| **TCP** | `response`, `duration_ms` |
| **DNS** | `answers`, `answer_count`, `rcode`, `duration_ms` |
| **gRPC** | `status` (el estado operativo que devuelve el servicio de salud, como `SERVING`), `duration_ms` |

Al guardar la revisión, MoleSignal rechaza cualquier fuente que la comprobación no admita.

`json:` usa una expresión JSONPath (RFC 9535) para consultar el JSON en los primeros 4 MiB del cuerpo: devuelve una cadena tal
cual, cualquier otro valor como JSON y varios valores en un arreglo JSON; si no encuentra valores o
el cuerpo no es JSON, devuelve un resultado vacío. `body` también admite la aserción **Cumple con el JSON Schema**, que
lee esos mismos 4 MiB e indica el primer punto donde el cuerpo no cumple con el esquema. El esquema no puede usar
`$ref` para referenciar una URL o un archivo externo. `size_bytes` cuenta los bytes del cuerpo hasta 16 MiB. Los campos `timing.*` registran los tiempos de cada fase del paso, con un valor de 0 para
las fases que no se ejecutaron. La extracción con JSONPath no requiere un patrón: usa el valor encontrado.

La ejecución falla si MoleSignal no puede resolver o alcanzar el destino, si el destino interrumpe la conexión, si falla la negociación TLS o si el destino no
responde dentro del tiempo de espera. También falla si no se cumple una aserción de nivel crítico. El resultado solo es desconocido
cuando MoleSignal no puede ejecutar la comprobación con la configuración actual: la política de tráfico saliente bloquea el destino, falta un secreto
o un ajuste no es compatible.

MoleSignal calcula el estado del monitor a partir de los éxitos y fallas consecutivos en las
ubicaciones seleccionadas. Configura el umbral de fallas, el umbral de recuperación y la política de ubicaciones para evitar
cambios de estado repetidos o que un problema aislado de red se interprete como una interrupción global.

## Conexión HTTP

La sección **Conexión** de una comprobación HTTP determina cómo se conecta al servidor. Si dejas campos vacíos, MoleSignal conserva los
valores predeterminados:

| Ajuste | Efecto |
|---|---|
| **Versión de HTTP** | **Negociar** ofrece HTTP/2 y HTTP/1.1 en conexiones TLS y deja que el servidor elija. En conexiones HTTP sin cifrar, usa HTTP/1.1. **Solo HTTP/1.1** no ofrece otras versiones. **Solo HTTP/2** hace que la ejecución falle si el servidor no acepta HTTP/2 y usa HTTP/2 en conexiones HTTP sin cifrar por conocimiento previo (h2c). |
| **Servidor DNS** | Resuelve los nombres de host con este servidor. Escríbelo como `host` o `host:port`. El servidor también debe cumplir con la política de tráfico saliente. |
| **Asignaciones de host** | Asigna un nombre de host a las direcciones IP que elijas, como en un archivo de hosts. El encabezado Host y la validación del certificado siguen usando el nombre original. Esto permite comprobar un servidor de origen o un nodo de CDN específico. |
| **Certificado de cliente** | Configura la cadena de certificados y la clave privada que el cliente presenta si el servidor solicita TLS mutuo. Carga archivos en formato PEM o pega su contenido. Si cargas un archivo que contiene ambos elementos, MoleSignal completa los dos campos. MoleSignal guarda la clave cifrada y no vuelve a mostrarla. Al editar la comprobación, deja vacío el campo de la clave para conservarla. |

El resultado de cada paso registra la dirección a la que se conectó (`remote_address`) y la versión de HTTP que
usó el servidor para responder (`http_version`).

## Contexto de la traza y diagnóstico de fallos

La sección **Diagnóstico** de una comprobación tiene dos interruptores, ambos activados de forma predeterminada.

**Contexto de la traza**: cada solicitud de una comprobación HTTP, incluidas las redirecciones, y cada llamada gRPC llevan un
`traceparent` de W3C. Las solicitudes de un mismo intento pertenecen a una sola traza y cada solicitud constituye un span de esa traza. Si un
paso define su propio encabezado o metadato `traceparent`, lo conserva. Los pasos y los resultados registran el
`trace_id`. En el detalle del resultado, **Ver traza** abre la traza que el servicio probado guardó para
la solicitud. Si el servicio no genera trazas, no aparece ninguna. Los metadatos que define una comprobación gRPC también se envían
con la llamada.

**Traceroute en caso de fallo**: cuando una comprobación HTTP, TCP, TLS, gRPC, SSH o ICMP no puede comunicarse con su destino
(la conexión falla, se agota su tiempo de espera o se interrumpe, falla la negociación TLS o los pings no reciben respuesta o
se pierden), el agente ejecuta un traceroute ICMP a la última dirección que probó: hasta 30 saltos, 4 sondas
por salto y un máximo de 12 segundos. El detalle del resultado muestra una tabla con la dirección de cada salto, la pérdida y
los tiempos de ida y vuelta mínimo, promedio y máximo. Traceroute requiere sockets sin procesar (root o `CAP_NET_RAW`) o
sockets ICMP sin privilegios (macOS y grupos de Linux dentro de `net.ipv4.ping_group_range`). Si no están
disponibles, el paso indica por qué no se ejecutó traceroute.

Una versión anterior del agente no envía `traceparent` ni ejecuta traceroute. El resultado de la comprobación no cambia.

**Sesión de RUM**: una comprobación de navegador avisa a la página de que es una prueba antes de que se ejecute cualquier script de la página. Si la página ejecuta el [SDK de RUM para navegadores](/es/rum/browser-sdk), registra una sesión de tipo `synthetics`. En el intento, **Abrir la sesión de RUM de esta ejecución** abre la sesión con su reproducción y sus eventos. Esta sesión [no se incluye en las métricas de usuarios reales](/es/rum/test-traffic). La página decide si ejecuta el SDK. Si no lo ejecuta, la comprobación no agrega nada a la página.

## Rango de tiempo y disponibilidad

La vista general, la lista de comprobaciones, los resultados y la vista general de cada comprobación incluyen un selector de rango de tiempo a la
derecha de la tarjeta de navegación. De forma predeterminada, muestran las últimas 24 horas. Puedes cambiar el rango.

- **Disponibilidad** = ejecuciones disponibles ÷ ejecuciones con resultado. Las ejecuciones correctas, intermitentes y degradadas cuentan como
  disponibles; las fallidas cuentan como no disponibles. Las ejecuciones con resultado desconocido y las omitidas no cuentan.
- La vista general muestra la disponibilidad de todas las comprobaciones y su tendencia en el rango seleccionado, y colorea el
  mapa por ubicación. La lista incluye una columna con la disponibilidad de cada comprobación. La
  vista general de cada comprobación muestra su disponibilidad, la mediana del tiempo de respuesta y el p95 en ese rango. **Respuesta por
  ubicación** grafica la mediana de la duración de cada ubicación por intervalo.
- La sección **Últimas ejecuciones** sigue mostrando las ejecuciones más recientes, independientemente del rango.

Para consultar la disponibilidad, usa `GET /api/v1/synthetics/availability` con `from` y `to` (microsegundos),
`monitor_id`, `location_id` y `step` (segundos; si lo omites, la API lo determina a partir del rango). Devuelve
el número de ejecuciones totales, disponibles, fallidas y sin resultado definido, la disponibilidad, y el P50, el P95 y la duración máxima
para el conjunto, por comprobación, por ubicación y por intervalo. Si consultas una sola comprobación, también devuelve los datos de cada ubicación por
intervalo. La lista de resultados `GET /api/v1/synthetics/results` acepta `fromTime` y `toTime`.

## Flujo de resultados y retención

Además de guardar el resultado completo, MoleSignal registra cada ejecución programada (excepto las ejecuciones de prueba) como una fila en el
flujo de logs `_synthetic_results` de la organización, con la marca de tiempo de inicio de la ejecución. Si la ejecución no tiene un valor para un campo,
MoleSignal omite ese campo.

| Campo | Contenido |
|---|---|
| `check_id`, `check_name`, `check_kind`, `revision_id` | La comprobación y la revisión que se ejecutó |
| `location_id`, `location_name`, `agent_id` | La ubicación y el agente que ejecutó la comprobación |
| `result_id`, `outcome`, `available`, `attempts` | El resultado, si la ejecución estuvo disponible (se omite si el resultado es desconocido o si se omitió la ejecución) y los intentos |
| `duration_ms`, `dns_ms`, `connect_ms`, `tls_ms`, `first_byte_ms` | La duración total y la de cada fase del último intento |
| `status_code`, `error_category`, `skip_reason`, `trace_id` | El código de estado HTTP, la categoría del fallo, el motivo de la omisión y la traza |
| `team_id`, `tags` | El equipo de la comprobación y las etiquetas (separadas por comas) |

Los paneles y las reglas de alerta consultan el flujo con SQL. El rango de tiempo de cada panel se aplica a su
consulta. Por ejemplo, para consultar la disponibilidad y el p95 de la duración de cada comprobación:

```sql
SELECT check_name,
       avg(CASE WHEN available THEN 1.0 ELSE 0.0 END) AS availability,
       approx_percentile_cont(0.95) WITHIN GROUP (ORDER BY duration_ms) AS p95_ms
FROM _synthetic_results
WHERE available IS NOT NULL
GROUP BY check_name
```

Una regla de alerta programada hace la misma consulta y se [divide](/es/alerting/rules#agrupar-una-regla-por-columnas)
por `location_name`. Así, si la disponibilidad de una ubicación cae por debajo del umbral, la regla abre un incidente
para esa ubicación.

De forma predeterminada, MoleSignal conserva los resultados completos durante 30 días. Cambia el plazo en **Resultados de pruebas sintéticas**, en la página
**Retención de datos** de la plataforma (0 los conserva indefinidamente). Consulta [Configuración de la plataforma](/es/settings/platform#retención-de-datos).
Una vez al día, MoleSignal elimina las ejecuciones que superan ese plazo, sus artefactos y las tareas finalizadas. El flujo `_synthetic_results`
usa su propio plazo de retención. Cámbialo en la página del flujo.

## Ubicaciones y agentes de sondeo

MoleSignal admite dos modelos de ubicación:

| Ubicación | Comportamiento |
|---|---|
| **Local integrada** | Un despliegue independiente inicia automáticamente un ejecutor de sondeos en el mismo proceso. Sirve para evaluaciones locales y comprobaciones que deben partir del mismo entorno que MoleSignal. |
| **Grupo de agentes** | Uno o más procesos externos <code>probe-agent</code> ejecutan comprobaciones desde una red privada, una región o una ubicación perimetral. |

Crea una ubicación de tipo Grupo de agentes en **Monitoreo sintético → Ubicaciones**, genera un token
de registro de un solo uso y registra el agente:

```bash
probe-agent register \
  --endpoint https://molesignal.example.com:5084 \
  --token ONE_TIME_TOKEN \
  --ca-certificate-base64 BASE64_CA
```

Luego inicia su flujo de control:

```bash
probe-agent run
```

El registro usa TLS con autenticación del servidor. El agente guarda una identidad privada en
<code>--state-dir</code> y usa mTLS para el flujo de control en el puerto 5085. El directorio de estado
predeterminado es <code>/var/lib/molesignal-probe</code>.

Configura los endpoints del servidor en <code>conf/config.toml</code>:

El plano de control de sondeos se inicia automáticamente en los nodos **Independiente** y **Alerta**. No tiene
un ajuste de activación propio.

```toml
[probe]
bind = "0.0.0.0"
register_port = 5084
control_port = 5085
register_endpoint = "https://molesignal.example.com:5084"
control_endpoint = "https://molesignal.example.com:5085"
server_names = ["molesignal.example.com"]
```

<Warning>
Antes de cada solicitud de red, se aplica una política de salida. Se rechazan las direcciones de bucle invertido, locales de enlace o privadas
salvo que la política de la ubicación seleccionada las permita explícitamente. Esto protege al
host de MoleSignal y a la red privada frente a la falsificación de solicitudes del lado del servidor.
</Warning>

Las comprobaciones HTTP respetan `HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY` y `NO_PROXY` en el entorno del
agente de sondeo. Cuando se usa un proxy, el tiempo de conexión del resultado mide la conexión al proxy,
incluida la solicitud para establecer el túnel. El proxy se conecta al destino, por lo que no se le exige
que use la dirección que aprobó la política de salida. Limita los destinos a los que puede acceder el proxy.

Un agente solo ofrece comprobaciones ICMP si su proceso puede enviar pings. En Linux, necesita `CAP_NET_RAW`
o pertenecer a un grupo dentro de `net.ipv4.ping_group_range`. El ejecutor en proceso de la ubicación local integrada
sigue la misma regla.

Los agentes informan su nivel de compatibilidad con cada señal de actividad. Si una comprobación usa opciones que los agentes más antiguos no
admiten, solo se asigna a agentes con una versión lo bastante reciente para ejecutarla. Esto incluye un tipo de registro DNS distinto de A y AAAA,
un resolvedor con nombre, DNSSEC, ICMP, aserciones en comprobaciones TCP, DNS y gRPC y, en comprobaciones HTTP,
JSONPath, JSON Schema, las fuentes de tamaño y de tiempos, el uso exclusivo de HTTP/2, un servidor DNS, las asociaciones de hosts
y un certificado de cliente. Actualiza `probe-agent` antes de ejecutar estas comprobaciones en un grupo de agentes.

Si un agente no envía una señal de actividad durante un minuto, se marca como desconectado. El estado de una ubicación depende del de sus
agentes: en línea si todos están en línea, degradada si solo algunos lo están y desconectada si ninguno lo está.
Si ningún agente toma una ejecución antes de su plazo, se registra como **Omitido** junto con el motivo: no hay agentes
en línea, ninguno ejecuta ese tipo de comprobación, sus versiones son demasiado antiguas para la configuración o todos están ocupados.

### Ejecuta agentes en Kubernetes

El chart de Helm `probe-agent` ejecuta los agentes como un StatefulSet. Cada réplica se registra por separado y guarda
su identidad y los resultados pendientes de envío en su propio volumen persistente. Así, un pod de reemplazo conserva la misma identidad
de agente. El chart no despliega el servidor. El chart `molesignal` despliega el servidor en el mismo
clúster o en otro entorno.

<Warning>
Los agentes externos requieren una versión posterior a la 26.2.0.0 tanto en el servidor como en la imagen del agente. En la versión 26.2.0.0,
el servidor no puede registrar un agente y el agente no avanza más allá del estado **Registrado**.
</Warning>

<Steps>
  <Step title="Asigna al servidor una dirección accesible para los agentes">
    Los agentes se conectan a los puertos 5084 y 5085 de un nodo **Independiente** o **Alerta**. `server_names` debe
    incluir el nombre de host que usan los agentes. De forma predeterminada, solo contiene `localhost`. Si los agentes están en el mismo
    clúster que el chart `molesignal`, configura el nombre del Service en los valores de ese chart. En
    modo `distributed`, usa el Service del rol `alert`.

    ```yaml
    config:
      probe:
        register_endpoint: https://molesignal.molesignal.svc.cluster.local:5084
        control_endpoint: https://molesignal.molesignal.svc.cluster.local:5085
        server_names: [molesignal.molesignal.svc.cluster.local]
    ```

    Si los agentes están en otro entorno, expón ambos puertos con un Service de tipo `LoadBalancer` o `NodePort`. Ningún intermediario
    debe terminar TLS: el agente solo confía en la CA del servidor y el flujo de control
    autentica al agente con un certificado de cliente.
  </Step>
  <Step title="Crea una ubicación y un token">
    Abre **Monitoreo sintético → Ubicaciones**, selecciona **Agregar ubicación privada** y crea un token:

    | Token | Dónde | Registra | Validez |
    |---|---|---|---|
    | Token de un solo uso | **Registrar agente** | Un agente | Hasta 60 minutos |
    | Token de agente | **Monitoreo sintético → Agentes → Crear token de agente** | Cualquier cantidad de agentes, hasta que el token caduque o se desactive | De 30 días a un año, o sin caducidad |

    Usa un token de agente si hay más de una réplica. Cada token se muestra una sola vez, junto con un comando de registro.
    El siguiente paso usa `--endpoint` y `--ca-certificate-base64` de ese comando.
  </Step>
  <Step title="Instala el chart">
    Guarda el token en un Secret. El chart no incluye un token predeterminado y nunca escribe un token en un ConfigMap.

    ```bash
    kubectl create namespace probes
    ```

    ```bash
    kubectl --namespace probes create secret generic probe-agent-registration --from-literal=token=<token>
    ```

    ```bash
    helm repo add molesignal https://charts.molesignal.com
    ```

    ```bash
    helm install probe-agent molesignal/probe-agent --namespace probes --set registration.endpoint=<endpoint> --set registration.caCertificateBase64=<base64-ca> --set registration.existingSecret=probe-agent-registration
    ```

    Verifica el endpoint y la CA. La prueba intenta registrar un agente con un token que el servidor rechaza.

    ```bash
    helm test probe-agent --namespace probes
    ```

    Los agentes aparecen después en **Monitoreo sintético → Agentes**.
  </Step>
</Steps>

| Comportamiento | Detalle |
|---|---|
| Registro | Un contenedor de inicialización registra el agente si el volumen no contiene una identidad. Si ya la contiene, no hace nada. Por eso, un token de un solo uso ya utilizado no causa problemas al reemplazar un pod. |
| Token | El agente solo lee el token hasta que obtiene una identidad. Un token nuevo no provoca reinicios. Puedes eliminar el Secret cuando los agentes estén en línea. Una réplica sin identidad ni token espera en `Init` y lo indica en su registro. |
| Reducción de réplicas y desinstalación | Los volúmenes se conservan, así que el agente vuelve con su identidad. Para retirar un agente, revócalo y elimina su PersistentVolumeClaim, `state-<release>-probe-agent-<ordinal>`. |
| Agente desconectado durante un periodo prolongado | Su certificado tiene una validez de `[probe].certificate_days` días, 30 de forma predeterminada, y se renueva si el agente se conecta cuando queda menos de una semana. Una vez que caduca, el agente no puede volver a conectarse: revócalo, elimina su volumen y deja que se registre de nuevo. |
| Pings | El chart configura `net.ipv4.ping_group_range` para el pod, por lo que las comprobaciones ICMP no requieren capacidades. |
| Imagen | `ghcr.io/molesignal/probe-agent`. `global.imageRegistry` reemplaza el host del registro. |

Para las comprobaciones de navegador, decide si usar el entorno aislado de Chromium. De forma predeterminada, el chart inicia Chromium con
`--no-sandbox`. El entorno aislado requiere espacios de nombres de usuario sin privilegios, que el perfil
seccomp `RuntimeDefault` bloquea. En ese caso, el pod aísla a Chromium: Chromium no se ejecuta como root, no tiene capacidades
ni token de cuenta de servicio y usa un sistema de archivos raíz de solo lectura. Una página que explote una vulnerabilidad de Chromium obtiene
los permisos del pod, incluido el acceso a la clave privada del agente. Para usar el entorno aislado, configura
`browser.sandbox` en `true` y `securityContext.seccompProfile.type` en `Unconfined`. Los nodos deben entonces
permitir espacios de nombres de usuario sin privilegios. En Ubuntu 23.10 y versiones posteriores, esto requiere
`kernel.apparmor_restrict_unprivileged_userns=0`. Los estándares de seguridad de pods `baseline` y `restricted`
no permiten `Unconfined`.

`/dev/shm` no requiere configuración. El agente inicia Chromium con `--disable-dev-shm-usage`, así que la memoria
compartida usa `/tmp`, que se configura con `browser.tmp`. Los recursos predeterminados, una solicitud de 512 MiB y
un límite de 2 GiB, permiten ejecutar una comprobación de navegador a la vez. Aumenta el límite en al menos 1 GiB por cada incremento de una unidad en
`browser.maxConcurrent`. Si configuras `browser.maxConcurrent` en `0`, el agente no ofrece comprobaciones de navegador.

Consulta el [README del chart](https://github.com/molesignal/molesignal-helm/tree/main/charts/probe-agent) para ver
todos los valores y resolver problemas.

## Variables, secretos y evidencias

Usa variables para valores reutilizables que no sean sensibles y secretos cifrados para las credenciales. Los valores de los
secretos son de solo escritura y la API nunca los devuelve. El detalle del resultado registra una cantidad limitada de evidencias de la solicitud y
la respuesta, los tiempos, los metadatos del intento, la ubicación seleccionada y la revisión activa,
sin exponer los secretos almacenados.

## Incidentes de alerta

Si una comprobación falla, abre un incidente de alerta que avisa al personal de guardia del mismo modo que una regla. Configura este comportamiento en **Alertas**, en el formulario de la comprobación.

| Estado de la comprobación | Incidente |
|---|---|
| **Fallido** | Abre un incidente con severidad `error`. |
| **Degradado** | Abre un incidente con severidad `warning` si está activada la opción **Alertar si la comprobación está degradada**. |
| **Intermitente** | Abre un incidente con severidad `warning` si está activada la opción **Alertar si la comprobación es inestable**. |
| **Verificación superada** | Resuelve el incidente. |
| **Sin resultados** | Abre un incidente independiente con severidad `warning` si está activada la opción **Alertar si no hay resultados** (activada de forma predeterminada). Lo resuelve cuando vuelven a llegar resultados. |

- Una comprobación tiene como máximo un incidente activo asociado a su estado. Cuando la comprobación pasa de un estado fallido, degradado o intermitente a otro de esos estados, el incidente abierto adopta la severidad que determinan las [canalizaciones de alertas](/es/pipelines/alert-events#cambios-de-gravedad), salvo que se haya fijado manualmente. Si aumenta la severidad, se reinicia el escalamiento. Un incidente confirmado no cambia hasta que se resuelve.
- Si ningún agente toma una ejecución a tiempo, el sistema la registra como omitida y mantiene el estado de la ubicación. Una ubicación deja de tener resultados cuando acumula tantas omisiones consecutivas como fallos consecutivos se necesitan para marcarla como fallida. Cuando la cantidad de ubicaciones sin resultados alcanza el umbral de la política de ubicaciones, la comprobación pasa a **Sin resultados**. La página de la comprobación indica ese estado, las ubicaciones afectadas y el motivo por el que se omitió la última ejecución. El incidente por falta de resultados incluye `synthetic.state` = `no_data` y `alert.condition` = `no_data`, y puede permanecer abierto junto con el incidente de estado. Si se resuelve manualmente, no vuelve a abrirse hasta que se reciban resultados de nuevo.
- Al pausar o archivar una comprobación, se resuelven sus incidentes abiertos y confirmados, ya que no habrá más ejecuciones que puedan resolverlos.
- La **Política de escalamiento** de la comprobación avisa al personal de guardia. Con **Enrutada**, el [enrutamiento de alertas](/es/alerting/routing) selecciona el equipo y la política de escalamiento. Con **Sin política de escalamiento**, el personal de guardia no recibe avisos, pero las políticas de notificación siguen enviando el incidente.
- El incidente lleva el nombre de la comprobación como título. Incluye las etiquetas `alert.source` = `synthetic`, `synthetic.kind` y `synthetic.state`, además de `synthetic.tags` y `team_id` si la comprobación tiene etiquetas y un equipo asignado. Así, las políticas de notificación pueden enrutar el incidente. La vista de detalles del incidente incluye un enlace a la comprobación.
- Las notificaciones incluyen la severidad y el nombre de la comprobación en el título, por ejemplo, `ERROR · Checkout API`, y muestran el mensaje `Synthetic check Checkout API is failing.` Una notificación por falta de resultados lleva el título `NO DATA · Checkout API` e indica dónde faltan resultados y por qué en el idioma predeterminado del espacio de trabajo, por ejemplo, `Synthetic check Checkout API has no results from Frankfurt (3 missed in a row): no Agent was online there.`
- Solo cuenta el estado global de la comprobación, que se determina a partir de los fallos consecutivos, las recuperaciones y la política de ubicaciones. Una sola ubicación no abre un incidente.

## Publicar fallos en una página de estado

Una regla de automatización de la página de estado puede usar **Monitor sintético** como origen. Selecciona el monitor,
especifica la transición y la severidad que debe detectar la regla, asigna el impacto a los componentes y elige entre la aprobación manual
o la publicación automática. Consulta [Páginas de estado](/es/status-pages#automatización-de-publicaciones).

## Permisos

| Permiso | Capacidad |
|---|---|
| <code>synthetics.monitors.read</code> | Leer comprobaciones, revisiones y programaciones. |
| <code>synthetics.results.read</code> | Leer ejecuciones y resultados. |
| <code>synthetics.locations.read</code> | Leer las ubicaciones y el estado de los agentes. |
| <code>synthetics.secrets.read</code> | Leer los nombres de los secretos cifrados del monitoreo sintético. |
| <code>synthetics.monitors.manage</code> | Crear, probar, publicar, pausar y reanudar comprobaciones. |
| <code>synthetics.monitors.run</code>, <code>synthetics.monitors.archive</code> | Ejecutar una comprobación de inmediato o archivarla. |
| <code>synthetics.locations.manage</code> | Administrar ubicaciones, grupos de agentes, tokens de registro y políticas de tráfico saliente. |
| <code>synthetics.secrets.manage</code> | Crear, rotar y eliminar secretos cifrados del monitoreo sintético. |
