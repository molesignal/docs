El grupo **Seguridad de los datos** de **Configuración** incluye **Claves de cifrado**, **Patrones de expresiones regulares**,
**Enmascaramiento de campos**, **Administración de dominios** y **Auditoría**. Para consultar las primeras cuatro secciones, necesitas el permiso
`org.field_masking.read`; para hacer cambios, necesitas `org.field_masking.manage`. **Auditoría** requiere
`audit.read`. La retención de los registros de auditoría es una [opción de configuración de la plataforma](/es/settings/platform#retención-de-registros-de-auditoría).

## Claves de cifrado

**Claves de cifrado** muestra las claves de datos del espacio de trabajo, con el algoritmo, la versión y la fecha y hora de
la última rotación. MoleSignal crea automáticamente la clave de los [campos cifrados](/es/streams#campos-cifrados)
la primera vez que un flujo escribe uno de esos campos. La clave aparece como `__field_default__`. MoleSignal protege cada clave
con la clave raíz de cifrado `MS_CIPHER_KEY`. El material de la clave nunca sale del servidor.

| Acción | Cómo funciona |
|---|---|
| **Nueva clave** | Ingresa un **Nombre** y 32 bytes de material de clave codificado en base64 (`keyMaterialB64`). |
| **Rotar** | Pega 32 bytes de material de clave nuevo en base64. La rotación agrega una versión para cifrar los datos nuevos. Las versiones anteriores siguen descifrando los datos que cifraron. |
| Eliminar | Los datos cifrados con la clave quedan ilegibles. |

<Warning>
  Si pierdes `MS_CIPHER_KEY`, no podrás recuperar ningún campo cifrado. Consulta
  [Cifrado a nivel de campo](/es/security#cifrado-a-nivel-de-campo).
</Warning>

## Patrones de expresiones regulares

Un patrón de expresión regular busca texto confidencial, como números de tarjeta o tokens, y lo reemplaza.

1. Selecciona **Nuevo patrón**.
2. Ingresa un **Nombre**, el **Patrón** y una **Descripción**. El servidor valida el patrón al
   guardarlo.
3. Ingresa el **Reemplazo**. Puedes usar `$1` y otros grupos de captura. Si dejas el reemplazo vacío, se elimina
   la coincidencia.
4. Usa **Ocultar datos durante la ingesta** para elegir cuándo aplicar el patrón y selecciona **Crear**.

| **Ocultar datos durante la ingesta** | Efecto |
|---|---|
| Activado | El sistema aplica el patrón a cada valor de tipo cadena de cada evento entrante, después de procesarlo en las canalizaciones y antes de almacenarlo. El texto original no se puede recuperar. |
| Desactivado | Los datos almacenados conservan el texto original. Una consulta SQL que llama a `mask(<column>)` devuelve la columna con los patrones aplicados. |

`mask()` aplica todos los patrones del espacio de trabajo. La columna **Enmascaramiento** de la lista muestra
**Durante la ingesta** o **Solo en consultas** para cada patrón.

## Enmascaramiento de campos

El enmascaramiento de campos oculta partes de los valores de campo en los resultados de las consultas. Las consultas siguen operando sobre los valores
originales. El enmascaramiento nunca se aplica a los flujos de métricas.

1. Selecciona **Nueva regla** e ingresa un **Nombre de la regla**.
2. **Patrón de campo**: ingresa un nombre de campo exacto o un nombre con los comodines `*` y `?`, como `user.*`.
   No uses expresiones regulares.
3. Si quieres limitar el alcance, usa **Patrón de flujo**, por ejemplo `customer-*`, y **Tipo de flujo**.
4. Elige el **Algoritmo**, deja activada la opción **Activar regla** y guarda los cambios.

| Algoritmo | Efecto |
|---|---|
| **Enmascaramiento completo** | Sustituye todo el valor por el **Reemplazo**. |
| **Enmascaramiento por rango** | Enmascara los caracteres desde **Carácter inicial** hasta **Carácter final (excluido)**. |
| **Enmascaramiento interno** | Conserva la cantidad indicada en **Caracteres visibles del prefijo** y **Caracteres visibles del sufijo**, y enmascara la parte central. |
| **Enmascaramiento externo** | Conserva solo los caracteres desde **Carácter inicial** hasta **Carácter final (excluido)** y enmascara ambos extremos. |
| **Hash HMAC-SHA-256** | Sustituye el valor por un hash calculado con una clave del espacio de trabajo que administra el servidor. Un mismo valor genera el mismo hash, así que puedes seguir agrupando y uniendo los resultados. |

Se aplica la primera regla activa que coincide con el campo. Arrastra las filas para cambiar el orden. En la configuración de campos de
un [flujo](/es/streams#esquema-y-campos), puedes reemplazar la regla heredada o desactivar el enmascaramiento de un
campo.

## Administración de dominios

**Administración de dominios** permite acceder al espacio de trabajo mediante un nombre de host propio, con un certificado que
MoleSignal obtiene y renueva.

1. Activa `[http.tls]` con un `account_email`. Consulta [TLS para HTTP y ACME](/es/configuration#tls-para-http-y-acme).
2. Configura el DNS del nombre de host para que apunte a MoleSignal. Así, el servicio ACME podrá acceder a
   `/.well-known/acme-challenge/` por el puerto HTTP sin cifrar.
3. Selecciona **Agregar dominio**, ingresa el **Nombre de host** y selecciona **Agregar dominio**.

La lista muestra el **Estado** de cada nombre de host, la fecha de vencimiento del certificado y el **Último error**.
Un nombre de host nuevo permanece en estado `pending` hasta que se emite el certificado. Luego pasa a `active`. MoleSignal renueva los certificados
automáticamente durante los 30 días previos al vencimiento. Si eliminas un nombre de host, MoleSignal deja de atender solicitudes en ese nombre.

## Auditoría

**Auditoría** permite buscar en el historial de auditoría del espacio de trabajo: acciones relevantes para la seguridad y cambios en
recursos y configuraciones. Cada evento incluye el autor del cambio, la acción, el objetivo, el estado y la hora.

| Filtro | Uso |
|---|---|
| **Desde** / **Hasta** | El intervalo de tiempo, absoluto o relativo, como `now-24h`. |
| **Tipo de actor** / **Autor del cambio** | Un tipo de actor o un usuario específico. |
| **Acción** | Una clave de acción, como `audit_retention.update`. |
| **Tipo de objetivo** / **ID del objetivo** | El tipo y el ID del recurso modificado. |

Selecciona **Aplicar** para buscar y **Restablecer** para borrar los filtros. Selecciona una fila para ver el evento completo y
acceder a **Copiar ID**. Si el evento corresponde a un chat de Mole Agent, muestra el historial de ese chat. El encabezado de la página indica
cuánto tiempo se conservan los registros. **Cambiar la retención** abre la configuración de la plataforma en `_sys`.

Los registros de auditoría nunca incluyen credenciales, claves de modelos, encabezados confidenciales de webhooks ni material criptográfico
de firma. Consulta [Auditoría](/es/security#auditoría).

### Flujo de auditoría

El sistema también escribe cada evento de auditoría como una fila en el flujo de registros `_audit` del espacio de trabajo. Así puedes
buscar el evento en **Registros** y enviarlo a otro destino, como un SIEM, mediante un
[pipeline programado](/es/pipelines#flujos-de-plataforma). El sistema depura la fila igual que el registro
de esta página y le asigna la hora del evento.

| Campo | Contenido |
|---|---|
| `audit_id` | El ID del evento que proporciona **Copiar ID**. |
| `actor_kind`, `actor_id` | Quién realizó la acción. |
| `action` | La clave de la acción. |
| `target_kind`, `target_id` | El recurso modificado, si el evento incluye uno. |
| `ip`, `user_agent` | El origen de la solicitud, si el evento lo registra. |
| `payload` | Los detalles del evento, si los hay. |

Esta página y la [API de auditoría](/es/api/admin/audit) leen los registros de referencia. Cada nodo escribe
las filas en segundo plano, por lotes, y mantiene un máximo de 4096 eventos en espera. Si la cola está
llena, el nodo omite la fila del flujo, pero conserva el registro. Las filas siguen la política de retención del
flujo, como en cualquier otro flujo.

Para leer `_audit` y acceder a esta página, necesitas `audit.read`:

- Sin ese permiso, el flujo no aparece en la lista de flujos. No puedes abrirlo, modificarlo ni eliminarlo, y
  consultarlo devuelve `403`. Esto se aplica a las consultas en el producto, a la API de consultas con transmisión en NDJSON,
  a Flight SQL y a la búsqueda federada, donde el clúster remoto comprueba que el token de quien realiza la consulta tenga
  `audit.read`.
- Toda consulta a `_audit` se ejecuta dentro de la solicitud. Nunca se convierte en una tarea de búsqueda, ni siquiera con
  `Prefer: respond-async`. Si envías una tarea de búsqueda para ese flujo, la solicitud devuelve `400`.
- Las tareas que se ejecutan en segundo plano sin intervención humana no pueden leer ese flujo, sin importar quién las haya guardado. No puedes guardar una regla de alerta que
  lea `_audit`, ya sea como flujo de origen o en cualquier parte de la consulta, ni una inspección programada de sus registros:
  la llamada devuelve `400`, incluso si la realiza el propietario. Los informes tampoco pueden leer el flujo.
- Las herramientas de Mole Agent y [MCP entrante](/es/inbound-mcp) no pueden leer el flujo con ninguna credencial: ni
  sus filas ni sus campos.

Un [pipeline programado](/es/pipelines#flujos-de-plataforma) lee `_audit` con los permisos de una sola persona:
quien lo guardó por última vez. Pausar y reanudar no cuentan como guardar. El encabezado de la página del pipeline
identifica a esa persona con la etiqueta **Lee \_audit como**. El origen en el editor también la identifica y muestra este aviso a otra persona
que tenga `audit.read` y pueda guardar el pipeline: **Al guardar, el pipeline usará tus permisos para leer _audit.**

- Para guardar un cambio, necesitas `audit.read`. Si usas un token de cuenta de servicio, la solicitud devuelve `403` porque el pipeline
  no puede volver a comprobar sus permisos al ejecutarse. Un token personal representa a la persona a la que el sistema
  lo emitió.
- Antes de cada lectura, el pipeline comprueba que la persona aún pueda iniciar sesión, siga en la organización y
  conserve `audit.read`. De lo contrario, la lectura falla y la ejecución indica quién y por qué. Por ejemplo:
  `` El pipeline lee `_audit` con los permisos de admin@example.com, que ya no tiene audit.read ``. El
  pipeline sigue activo y conserva su posición de lectura para no omitir ningún evento.
- El pipeline retoma la lectura desde ese punto cuando la persona recupera `audit.read` o cuando alguien con ese permiso
  guarda el pipeline, incluso sin hacer cambios. Si guardas el pipeline sin cambios y no tienes `audit.read` o
  usas un token de cuenta de servicio, el sistema no cambia nada ni informa de ningún error.
- Para pausar y reanudar, solo necesitas `pipelines.pause`. Estas acciones no cambian los permisos que usa el pipeline
  para leer. Al reanudarlo, [empieza desde el principio](/es/pipelines#programación-y-posiciones-de-lectura), como cualquier pipeline. Déjalo
  activo para conservar su posición de lectura.
- Una carga retroactiva lee con los permisos de quien la envía. Esa persona necesita `audit.read` al
  enviarla, y la tarea vuelve a comprobar el permiso al ejecutarse.

Las filas que copia el pipeline son filas normales en sus destinos. Puede leerlas cualquiera que tenga permiso de lectura
en esos destinos.
