Todas las señales entran en MoleSignal a través de la API de ingesta. La página **Fuente de datos** de la interfaz web genera el endpoint, el token y el fragmento de configuración de cada origen. Los mismos protocolos se pueden configurar a mano.

## Página Fuente de datos

Abre **Fuente de datos** para incorporar un origen:

1. Busca en el catálogo o fíltralo por categoría: **Recomendado**, **Infraestructura**, **Nube**, **Bases de datos**, **Mensajería**, **Aplicaciones y lenguajes**, **Seguridad** y **Personalizado**. Las pestañas de señales (**Registros**, **Métricas**, **Trazas**, **Perfiles**) acotan más la lista.
2. Selecciona un origen como Kubernetes, un host Linux, AWS, un SDK de OpenTelemetry o Web RUM.
3. Sigue los tres pasos de la guía:
   - **Endpoint y token** muestra dónde enviar los datos y el token con el que autenticarse. **Mostrar token** revela el token, con su ámbito, su espacio de trabajo y su caducidad. Para un origen RUM, elige primero la **Aplicación RUM**: su token de cliente aparece en cuanto se elige.
   - **Configura el origen** muestra comandos y configuración con el endpoint y el token reales ya rellenados.
   - **Verifica que lleguen los datos** comprueba el receptor y después busca datos recibidos en la última hora. **Verificar conexión** comprueba al instante, y las cifras se actualizan cada 30 segundos.
4. Lee el resultado de la verificación:
   - **Datos detectados**: llegaron datos en la última hora y las señales del origen están correctas. **Ver datos recibidos** abre los datos y **Crear pipeline** inicia un pipeline para ellos.
   - **El receptor funciona correctamente, pero los datos requieren atención**: el receptor responde, pero no llegaron datos o no todas las señales están correctas. Revisa el despliegue o espera al siguiente lote.
   - **Falló la verificación**: no se pudo comprobar el receptor. **Posibles causas** enumera un colector que no está en ejecución, un token no válido o caducado y una red o un proxy que bloquea el endpoint.

El endpoint proviene de `http.external_url` cuando está definido y, en caso contrario, de la dirección del navegador. Define `http.external_url` detrás de un proxy inverso para que los fragmentos generados apunten a la dirección pública. Consulta [Configuración](/es/configuration).

## Tokens de ingesta

Los emisores se autentican con un token de portador: `Authorization: Bearer <token>`. Un emisor que solo admite autenticación Basic, como la exportación remote write del Prometheus gestionado de un proveedor de nube, coloca el Token de API en la contraseña de `Authorization: Basic` con cualquier nombre de usuario. Las demás credenciales Basic se ignoran, de modo que un proxy inverso que solicita las suyas propias sigue funcionando. Un emisor Splunk HEC presenta el token como `Authorization: Splunk <token>`.

| Token | Permiso | Creado por | Uso |
|---|---|---|---|
| Token de ingesta predeterminado | Solo `logs.write`, `metrics.write`, `traces.write`, `profiles.write` y `apm.deploy`: la política **Ingesta de datos** | Página Fuente de datos, o `GET /api/v1/me/api-tokens/default` | Colectores, agentes y exportadores de SDK que envían registros, métricas y trazas, y pipelines que [notifican despliegues](/es/apm/deployments#reporta-despliegues-desde-ci). No caduca. |
| Token de cliente RUM | Solo `rum.write`, vinculado a una aplicación | Página Fuente de datos para orígenes Web RUM y RUM móvil, o `GET /api/v1/auth/tokens/rum?applicationId=<id>` | Código de navegador y móvil. El token es visible para los usuarios finales. |
| Token personal o de cuenta de servicio | Lo que su miembro o cuenta de servicio puede hacer, acotado por su ámbito | **Configuración de la cuenta → Tokens de API**, o **Identidad y acceso → Tokens de API** para cuentas de servicio | Automatización, scripts y clientes MCP. |

Usa el token de ingesta predeterminado, o un token de cuenta de servicio que siga la política **Ingesta de datos**, para los emisores que se ejecutan de forma continua. Revoca un token desde **Configuración de la cuenta → Tokens de API** o **Identidad y acceso → Tokens de API** para detenerlo de inmediato. Una sesión iniciada de la interfaz web no puede enviar datos: vive en cookies del navegador y el encabezado `Authorization` no la acepta.

La página **Fuente de datos** crea un token de cliente RUM cuando se introduce un id de aplicación. Un id de aplicación contiene de 1 a 128 caracteres de `A-Z`, `a-z`, `0-9`, `.`, `_`, `:` y `-`. Usa el mismo id como `applicationId` en el SDK. Consulta [SDK de RUM para navegador](/es/rum/browser-sdk).

## Endpoints y protocolos

| Protocolo | Endpoint | Emisores compatibles | Flujo de destino |
|---|---|---|---|
| HTTP JSON nativo | `POST /api/v1/intake/{logs,metrics,traces}/{stream}` | `curl`, código de aplicación, sink `http` de Vector, salida `http` de Fluent Bit | El segmento `{stream}` de la ruta |
| OTLP sobre HTTP | `POST /api/v1/logs`, `/api/v1/metrics`, `/api/v1/traces` | SDK de OpenTelemetry y Collector | Encabezado `stream-name`; si no, `default` |
| OTLP sobre gRPC | `:4317` | SDK de OpenTelemetry y Collector | Metadatos `stream-name`; si no, `default` |
| remote_write de Prometheus | `POST /api/v1/prometheus/api/v1/write` | Prometheus, VictoriaMetrics, exportaciones de Prometheus gestionado en la nube, cualquier emisor remote_write v1 | Encabezado `stream-name`; si no, `?stream=`; si no, `default` |
| `_bulk` de Elasticsearch | `POST /api/v1/_bulk` | Filebeat, Logstash, sink `elasticsearch` de Vector | `_index` de cada acción; si no, encabezado `stream-name`; si no, `default` |
| Splunk HEC | `POST /api/v1/services/collector/event`, `/api/v1/services/collector/raw` | Tencent Cloud CLS, salidas Splunk de Vector y Fluent Bit, reenviadores SIEM | `index` de cada evento; si no, `?index=`; si no, encabezado `stream-name`; si no, `default` |
| Loki push (JSON) | `POST /api/v1/loki/api/v1/push` | Emisores que pueden hacer POST de la estructura JSON de Loki | Encabezado `stream-name`; si no, `default` |
| Amazon Data Firehose, Google Cloud Pub/Sub push, buses de eventos en la nube, Cloudflare Logpush, Heroku | `/api/v1/_kinesis_firehose`, `/api/v1/_gcp_pubsub`, `/api/v1/_cloud_events`, `/api/v1/_cloudflare`, `/api/v1/_heroku` | CloudWatch Logs y CloudWatch Metric Streams a través de Firehose, Cloud Logging a través de Pub/Sub, emisores de EventBridge, Event Grid y CloudEvents, Cloudflare, Heroku | Se configura en el conector. Consulta [Conectores](/es/connectors). |

Todos los endpoints excepto los conectores push requieren un token de portador con el permiso de escritura de la señal: `logs.write`, `metrics.write`, `traces.write` o `profiles.write`. La organización proviene del token y nunca aparece en una URL.

### Límites que afectan a los emisores

- **Tamaño de la solicitud.** La ingesta JSON nativa y los conectores push aceptan cuerpos de solicitud de hasta 16 MiB, y Firehose hasta 64 MiB, contados después de la descompresión; los demás endpoints de ingesta aceptan hasta 2 MiB. Un cuerpo mayor se rechaza con `413`. Mantén los lotes por debajo de ese tamaño.
- **Compresión.** OTLP sobre HTTP no acepta cuerpos de solicitud comprimidos y responde `400`. Desactiva la compresión en el emisor; el exportador `otlphttp` de OpenTelemetry Collector comprime con gzip de forma predeterminada y necesita `compression: none`. La ingesta JSON nativa, `_bulk` de Elasticsearch, Loki push y los conectores push aceptan `Content-Encoding: gzip`.
- **Codificación de Loki.** Solo se decodifica la estructura de solicitud JSON. Promtail y Grafana Alloy envían protobuf comprimido con snappy de forma predeterminada y no pueden enviar a este endpoint.
- **Límite de tasa.** El rol `router` limita las solicitudes por organización y responde `429` con un encabezado `Retry-After`. Un nodo `standalone` no aplica este límite. Consulta [Despliegue basado en roles](/es/deployment/role-based#límites-de-solicitudes).
- **Flujos de la plataforma.** Los [flujos de la plataforma](/es/streams#flujos-de-la-plataforma), como `_molesignal` para la telemetría del propio servicio y `_audit` para el registro de auditoría, solo los escribe MoleSignal y rechazan la ingesta pública con `403`.

## Flujos y esquema

Un flujo se crea en su primera escritura, y el esquema evoluciona a medida que aparecen nuevos campos. Un flujo se identifica por su nombre y su tipo de señal, así que `default` puede existir para registros, métricas y trazas al mismo tiempo. Consulta [Flujos](/es/streams).

Cada evento tiene una marca de tiempo en microsegundos desde la época Unix. La ingesta JSON nativa y `_bulk` de Elasticsearch leen el campo `_timestamp`. Un evento sin `_timestamp` recibe la hora a la que el servidor lo aceptó.

## JSON nativo por HTTP

Envía un arreglo de registros a `/api/v1/intake/{logs,metrics,traces}/{stream}`:

```bash
curl -X POST http://localhost:5080/api/v1/intake/logs/app \
  -H "authorization: Bearer $MS_TOKEN" \
  -H 'content-type: application/json' \
  -d "[{\"_timestamp\":$(date +%s)000000,\"level\":\"error\",\"msg\":\"db pool exhausted\",\"trace_id\":\"abc123\"}]"
```

La respuesta indica cuántos registros se aceptaron y cuántos se rechazaron, con un motivo por índice rechazado:

```json
{"accepted":1,"rejected":0,"errors":[]}
```

## OpenTelemetry

Configura un SDK de OpenTelemetry o un Collector para que apunte a la ruta base `/api`. El exportador agrega `/v1/logs`, `/v1/metrics` y `/v1/traces`, que se asignan a `/api/v1/logs`, `/api/v1/metrics` y `/api/v1/traces`.

<Tabs>
  <Tab title="OTLP sobre HTTP">
    Variables de entorno del SDK:

    ```bash
    export OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf
    export OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:5080/api
    export OTEL_EXPORTER_OTLP_HEADERS="authorization=Bearer ${MS_TOKEN}"
    ```

    OpenTelemetry Collector:

    ```yaml
    exporters:
      otlphttp/molesignal:
        endpoint: http://localhost:5080/api
        compression: none
        headers:
          authorization: "Bearer ${env:MS_TOKEN}"
    ```

    Envía protobuf (`application/x-protobuf`), la codificación predeterminada de los SDK y del Collector. Los logs, las métricas y las trazas también aceptan JSON (`application/json`). Agrega un encabezado `stream-name` para seleccionar un flujo distinto de `default`. El encabezado se aplica a cada señal enviada a través de ese exportador.
  </Tab>
  <Tab title="OTLP sobre gRPC">
    El receptor gRPC de OTLP escucha en el puerto `4317` y atiende los servicios de logs, métricas, trazas y perfiles. No termina TLS. Termina TLS delante del receptor para el tráfico que sale de una red confiable.

    ```bash
    export OTEL_EXPORTER_OTLP_PROTOCOL=grpc
    export OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4317
    export OTEL_EXPORTER_OTLP_HEADERS="authorization=Bearer ${MS_TOKEN}"
    ```

    OpenTelemetry Collector:

    ```yaml
    exporters:
      otlp/molesignal:
        endpoint: localhost:4317
        tls:
          insecure: true
        headers:
          authorization: "Bearer ${env:MS_TOKEN}"
    ```

    Elimina `insecure: true` cuando un proxy que termina TLS esté delante del puerto. El puerto `5082` es el puerto gRPC interno del clúster y no es un receptor de OTLP.
  </Tab>
</Tabs>

Las métricas de OTLP se almacenan como un evento por punto de datos. Consulta el [contrato de almacenamiento de métricas](/es/query#campos-de-métricas-otlp) para conocer los campos almacenados.

## remote_write de Prometheus

Agrega MoleSignal como destino de escritura remota en `prometheus.yml`:

```yaml
remote_write:
  - url: http://localhost:5080/api/v1/prometheus/api/v1/write
    authorization:
      credentials: "${MS_TOKEN}"
```

Un flujo de métricas contiene las métricas de una fuente, así que asigna a cada servidor de Prometheus su propio flujo con el encabezado `stream-name` (`headers:` en la entrada `remote_write`); sin este, las muestras se envían a `default`. Un emisor que no puede establecer encabezados indica el flujo en la URL en su lugar, como en `/api/v1/prometheus/api/v1/write?stream=aliyun`. Cada muestra se convierte en una fila cuyo `metric_name` es su `__name__`. Las demás etiquetas se convierten en campos, y una etiqueta con el mismo nombre que un campo de métrica, como `metric_name`, se conserva como `exported_<name>`. Los histogramas nativos y los metadatos de métricas se omiten, y los exemplars se almacenan junto a las muestras.

## Carga masiva de Elasticsearch

Los emisores que usan el protocolo de carga masiva de Elasticsearch funcionan sin depender de Loki ni de OTLP:

```bash
curl -X POST http://localhost:5080/api/v1/_bulk \
  -H "authorization: Bearer $MS_TOKEN" \
  -H 'content-type: application/x-ndjson' \
  --data-binary $'{"index":{"_index":"app"}}\n{"level":"info","msg":"hello"}\n'
```

El `_index` de cada acción selecciona el flujo de destino. Si no se especifica, se aplica el encabezado `stream-name` y, después, `default`.

## Envío a Loki

El punto de conexión acepta la estructura de solicitud JSON de Loki:

```json
{"streams":[{"stream":{"service":"checkout","level":"error"},"values":[["1700000000000000000","payment failed"]]}]}
```

Las etiquetas se convierten en campos, la línea de log se convierte en el campo `message` y la marca de tiempo en nanosegundos se convierte a microsegundos. La respuesta es `204`. Selecciona el flujo de destino con el encabezado `stream-name`.

## Splunk HEC

Los emisores que usan el protocolo Splunk HTTP Event Collector, como Tencent Cloud CLS al enviar a Splunk o las salidas de Splunk de Vector y Fluent Bit, pueden enviar a MoleSignal sin cambios. Configura `https://molesignal.example.com/api/v1` como dirección de HEC y un token de API que pueda escribir logs como token de HEC, enviado como `Authorization: Splunk <token>`.

| Punto de conexión | Cuerpo |
|---|---|
| `POST /api/v1/services/collector/event`, también `/services/collector` | Objetos JSON uno después de otro, cada uno `{"time", "host", "source", "sourcetype", "index", "event", "fields"}` |
| `POST /api/v1/services/collector/raw` | Texto, un evento de log por línea; `host`, `source`, `sourcetype` e `index` provienen de la consulta |
| `GET /api/v1/services/collector/health` | Responde `{"text":"HEC is healthy","code":17}` sin token |

Un `event` que es un objeto JSON proporciona los campos del log; cualquier otro `event` se convierte en `message`. `fields`, `host`, `source` y `sourcetype` se convierten en campos, y `time`, en segundos, se convierte en la hora. `index` determina el flujo; si no se indica, se usa el parámetro de consulta `index`; si tampoco, el encabezado `stream-name`; y si no, `default`. La respuesta es `{"text":"Success","code":0}`, o los códigos de error propios de HEC con `400`. No se ofrece la confirmación del indexador.
