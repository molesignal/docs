Todas las señales ingresan a MoleSignal a través de la API de ingesta. La página **Fuente de datos** de la interfaz web genera el endpoint, el token y el fragmento de configuración para cada origen. También puedes configurar esos mismos protocolos manualmente.

## Página Fuente de datos

Abre **Fuente de datos** para incorporar un origen:

1. Busca en el catálogo o fíltrelo por categoría: **Recomendado**, **Infraestructura**, **Nube**, **Bases de datos**, **Mensajería**, **Aplicaciones y lenguajes**, **Seguridad** y **Personalizado**. Usa las pestañas de señales (**Registros**, **Métricas**, **Trazas**, **Perfiles**) para acotar aún más la lista.
2. Selecciona un origen, como Kubernetes, un host Linux, AWS, un SDK de OpenTelemetry o RUM web.
3. Sigue los tres pasos de la guía:
   - **Endpoint y token** muestra adónde enviar los datos y qué token usar para autenticar el envío. **Mostrar token** revela el token, su alcance, su espacio de trabajo y su fecha de vencimiento. Para un origen RUM, elige primero la **Aplicación RUM**. Al seleccionarla, aparece su token de cliente.
   - **Configura el origen** muestra los comandos y la configuración con el endpoint y el token ya incorporados.
   - **Verifica que lleguen los datos** comprueba el receptor y luego busca datos recibidos en la última hora. **Verificar conexión** ejecuta la comprobación de inmediato. Las cifras se actualizan cada 30 segundos.
4. Revisa el resultado de la verificación:
   - **Datos detectados**: llegaron datos en la última hora y las señales del origen están en buen estado. **Ver datos recibidos** abre los datos y **Crear pipeline** inicia un pipeline para procesarlos.
   - **El receptor funciona correctamente, pero los datos requieren atención**: el receptor responde, pero no llegaron datos o algunas señales no están en buen estado. Revisa el despliegue o espera el siguiente lote.
   - **Falló la verificación**: la comprobación del receptor no pudo completarse. **Posibles causas** enumera un colector que no está en ejecución, un token no válido o vencido y una red o un proxy que bloquea el endpoint.

Si `http.external_url` tiene un valor, MoleSignal lo usa como endpoint. De lo contrario, usa la dirección del navegador. Si usas un proxy inverso, configura `http.external_url` para que los fragmentos generados apunten a la dirección pública. Consulta [Configuración](/es/configuration).

## Tokens de ingesta

Los emisores se autentican con un token de portador: `Authorization: Bearer <token>`.

| Token | Permiso | Dónde se crea | Uso |
|---|---|---|---|
| Token de ingesta predeterminado | Solo `logs.write`, `metrics.write`, `traces.write`, `profiles.write` y `apm.deploy`: la política **Ingesta de datos** | Página Fuente de datos o `GET /api/v1/me/api-tokens/default` | Colectores, agentes y exportadores de SDK que envían registros, métricas y trazas, y pipelines que [notifican despliegues](/es/apm/deployments#reporta-despliegues-desde-ci). No vence. |
| Token de cliente RUM | Solo `rum.write`, vinculado a una sola aplicación | Página Fuente de datos para orígenes RUM web y móvil o `GET /api/v1/auth/tokens/rum?applicationId=<id>` | Código de navegador y de aplicaciones móviles. El token es visible para los usuarios finales. |
| Token personal o de cuenta de servicio | Los permisos del miembro o de la cuenta de servicio, limitados por el alcance del token | **Configuración de la cuenta → Tokens de API** o **Identidad y acceso → Tokens de API** para las cuentas de servicio | Automatizaciones, scripts y clientes MCP. |

Para emisores que se ejecutan de forma continua, usa el token de ingesta predeterminado o un token de cuenta de servicio que siga la política **Ingesta de datos**. Revoca un token desde **Configuración de la cuenta → Tokens de API** o **Identidad y acceso → Tokens de API** para invalidarlo de inmediato. No puedes enviar datos con una sesión de la interfaz web: el navegador la guarda en cookies y el encabezado `Authorization` no la acepta.

La página **Fuente de datos** crea un token de cliente RUM al ingresar el ID de una aplicación. El ID de una aplicación contiene entre 1 y 128 caracteres de este conjunto: `A-Z`, `a-z`, `0-9`, `.`, `_`, `:` y `-`. Usa ese mismo ID como `applicationId` en el SDK. Consulta [SDK de RUM para navegadores](/es/rum/browser-sdk).

## Endpoints y protocolos

| Protocolo | Endpoint | Emisores compatibles | Flujo de destino |
|---|---|---|---|
| JSON nativo por HTTP | `POST /api/v1/intake/{logs,metrics,traces}/{stream}` | `curl`, código de aplicación, destino `http` de Vector, salida `http` de Fluent Bit | El segmento de ruta `{stream}` |
| OTLP por HTTP | `POST /api/v1/logs`, `/api/v1/metrics`, `/api/v1/traces` | SDK y colector de OpenTelemetry | Encabezado `stream-name` o, si no está presente, `default` |
| OTLP por gRPC | `:4317` | SDK y colector de OpenTelemetry | Metadato `stream-name` o, si no está presente, `default` |
| Prometheus remote_write | `POST /api/v1/prometheus/api/v1/write` | Prometheus, VictoriaMetrics y cualquier emisor de remote_write v1 | Encabezado `stream-name` o, si no está presente, `default` |
| Elasticsearch `_bulk` | `POST /api/v1/_bulk` | Filebeat, Logstash, destino `elasticsearch` de Vector | `_index` de cada acción; en su defecto, el encabezado `stream-name`; si tampoco está presente, `default` |
| Loki push (JSON) | `POST /api/v1/loki/api/v1/push` | Emisores que pueden hacer solicitudes POST con la estructura JSON de Loki | Encabezado `stream-name` o, si no está presente, `default` |
| Kinesis Firehose, Cloudflare Logpush, Heroku | `/api/v1/_kinesis_firehose`, `/api/v1/_cloudflare`, `/api/v1/_heroku` | AWS, Cloudflare, Heroku | Se configura en el conector. Consulta [Conectores](/es/connectors). |

Todos los endpoints, excepto los conectores push, requieren un token de portador con el permiso de escritura correspondiente a la señal: `logs.write`, `metrics.write`, `traces.write` o `profiles.write`. MoleSignal obtiene la organización del token y nunca la incluye en una URL.

### Límites que afectan a los emisores

- **Tamaño de la solicitud.** La ingesta de JSON nativo acepta cuerpos de solicitud de hasta 16 MiB después de descomprimirlos. Los demás endpoints de ingesta aceptan hasta 2 MiB. Si el cuerpo supera el límite, el endpoint responde con `413`. Mantén los lotes por debajo del tamaño máximo.
- **Compresión.** OTLP por HTTP no acepta cuerpos de solicitud comprimidos y responde con `400`. Desactiva la compresión en el emisor. El exportador `otlphttp` de OpenTelemetry Collector usa gzip de forma predeterminada y requiere `compression: none`. La ingesta de JSON nativo, Elasticsearch `_bulk`, Loki push y los conectores push aceptan `Content-Encoding: gzip`.
- **Codificación de Loki.** El endpoint solo decodifica solicitudes con estructura JSON. Promtail y Grafana Alloy envían protobuf comprimido con snappy de forma predeterminada y no pueden enviar datos a este endpoint.
- **Límite de solicitudes.** El rol `router` limita la frecuencia de solicitudes por organización y responde con `429` y un encabezado `Retry-After`. Un nodo `standalone` no aplica este límite. Consulta [Despliegue por roles](/es/deployment/role-based#límites-de-solicitudes).
- **Flujos de la plataforma.** Solo MoleSignal escribe en los [flujos de la plataforma](/es/streams#flujos-de-la-plataforma), como `_molesignal` para la telemetría del propio servicio y `_audit` para el registro de auditoría. Estos flujos rechazan la ingesta pública con `403`.

## Flujos y esquema

MoleSignal crea un flujo con la primera escritura y actualiza el esquema a medida que aparecen campos nuevos. El nombre y el tipo de señal identifican el flujo, por lo que `default` puede existir al mismo tiempo para registros, métricas y trazas. Consulta [Flujos](/es/streams).

Cada evento tiene una marca de tiempo en microsegundos desde la época de Unix. La ingesta de JSON nativo y Elasticsearch `_bulk` leen el campo `_timestamp`. Si un evento no incluye `_timestamp`, MoleSignal le asigna la hora en que el servidor lo aceptó.

## JSON nativo por HTTP

Envía un arreglo de registros mediante POST a `/api/v1/intake/{logs,metrics,traces}/{stream}`:

```bash
curl -X POST http://localhost:5080/api/v1/intake/logs/app \
  -H "authorization: Bearer $MS_TOKEN" \
  -H 'content-type: application/json' \
  -d "[{\"_timestamp\":$(date +%s)000000,\"level\":\"error\",\"msg\":\"db pool exhausted\",\"trace_id\":\"abc123\"}]"
```

La respuesta indica cuántos registros aceptó y cuántos rechazó, con el motivo de rechazo para cada índice:

```json
{"accepted":1,"rejected":0,"errors":[]}
```

## OpenTelemetry

Configura un SDK de OpenTelemetry u OpenTelemetry Collector para que use la ruta base `/api`. El exportador agrega `/v1/logs`, `/v1/metrics` y `/v1/traces`, que corresponden a `/api/v1/logs`, `/api/v1/metrics` y `/api/v1/traces`.

<Tabs>
  <Tab title="OTLP sobre HTTP">
    Variables de entorno del SDK:

    ```bash
    export OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf
    export OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:5080/api
    export OTEL_EXPORTER_OTLP_HEADERS="authorization=Bearer ${MS_TOKEN}"
    ```

    OpenTelemetry Collector:

    ```yaml
    exporters:
      otlphttp/molesignal:
        endpoint: http://localhost:5080/api
        compression: none
        headers:
          authorization: "Bearer ${env:MS_TOKEN}"
    ```

    Envía los datos en protobuf (`application/x-protobuf`), la codificación predeterminada de los SDK y OpenTelemetry Collector. Los registros, las métricas y las trazas también admiten JSON (`application/json`). Agrega el encabezado `stream-name` para seleccionar un flujo distinto de `default`. El encabezado se aplica a todas las señales que envía ese exportador.
  </Tab>
  <Tab title="OTLP sobre gRPC">
    El receptor OTLP sobre gRPC escucha en el puerto `4317` y ofrece los servicios de registros, métricas, trazas y perfiles. No termina las conexiones TLS. Termina las conexiones TLS antes de que lleguen al receptor si el tráfico sale de una red de confianza.

    ```bash
    export OTEL_EXPORTER_OTLP_PROTOCOL=grpc
    export OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4317
    export OTEL_EXPORTER_OTLP_HEADERS="authorization=Bearer ${MS_TOKEN}"
    ```

    OpenTelemetry Collector:

    ```yaml
    exporters:
      otlp/molesignal:
        endpoint: localhost:4317
        tls:
          insecure: true
        headers:
          authorization: "Bearer ${env:MS_TOKEN}"
    ```

    Elimina `insecure: true` si hay un proxy delante del puerto que termina las conexiones TLS. El puerto `5082` es el puerto gRPC interno del clúster y no funciona como receptor OTLP.
  </Tab>
</Tabs>

MoleSignal almacena las métricas OTLP como un evento por punto de datos. Consulta el [contrato de almacenamiento de métricas](/es/query#campos-de-métricas-otlp) para ver qué campos almacena.

## Prometheus remote_write

Agrega MoleSignal como destino de escritura remota en `prometheus.yml`:

```yaml
remote_write:
  - url: http://localhost:5080/api/v1/prometheus/api/v1/write
    authorization:
      credentials: "${MS_TOKEN}"
```

Cada flujo de métricas contiene las métricas de una sola fuente, así que asigna un flujo propio a cada servidor de Prometheus con el encabezado `stream-name` (`headers:` en la entrada `remote_write`). Sin ese encabezado, las muestras van a `default`. Cada muestra se convierte en una fila cuyo campo `metric_name` toma el valor de `__name__`. Las demás etiquetas se convierten en campos. Si una etiqueta tiene el mismo nombre que un campo de métricas, como `metric_name`, MoleSignal la conserva como `exported_<name>`. MoleSignal omite los histogramas nativos y los metadatos de métricas, y almacena los ejemplares junto a las muestras.

## Elasticsearch bulk

Los clientes que usan el protocolo bulk de Elasticsearch funcionan sin depender de Loki ni de OTLP:

```bash
curl -X POST http://localhost:5080/api/v1/_bulk \
  -H "authorization: Bearer $MS_TOKEN" \
  -H 'content-type: application/x-ndjson' \
  --data-binary $'{"index":{"_index":"app"}}\n{"level":"info","msg":"hello"}\n'
```

El campo `_index` de cada acción selecciona el flujo de destino. Si falta ese campo, se usa el encabezado `stream-name`. Si también falta ese encabezado, se usa `default`.

## Loki push

El endpoint acepta la estructura de solicitud JSON de Loki:

```json
{"streams":[{"stream":{"service":"checkout","level":"error"},"values":[["1700000000000000000","payment failed"]]}]}
```

Las etiquetas se convierten en campos y la línea del registro pasa al campo `message`. El endpoint convierte la marca de tiempo de nanosegundos a microsegundos y responde con `204`. Selecciona el flujo de destino con el encabezado `stream-name`.
