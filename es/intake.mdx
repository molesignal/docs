Every signal enters MoleSignal through the intake API. The **Datasource** page in the web UI generates the endpoint, token, and configuration snippet for each source. The same protocols can be configured by hand.

## Datasource page

Open **Datasource** to onboard a source:

1. Search the catalog or filter it by category: **Recommended**, **Infrastructure**, **Cloud**, **Databases**, **Messaging**, **Apps & languages**, **Security**, and **Custom**. The signal tabs (**Logs**, **Metrics**, **Traces**, **Profiles**) narrow the list further.
2. Select a source such as Kubernetes, a Linux host, AWS, an OpenTelemetry SDK, or Web RUM.
3. Follow the three steps of the guide:
   - **Endpoint and token** shows where to send data and the token to authenticate with. **Show token** reveals the token, with its scope, workspace, and expiry. For a RUM source, choose the **RUM application** first: its client token appears once it is chosen.
   - **Set up the source** shows commands and configuration with the real endpoint and token already filled in.
   - **Verify data is arriving** checks the receiver, then looks for data received in the last hour. **Verify connection** checks at once, and the figures refresh every 30 seconds.
4. Read the result of the verification:
   - **Data detected**: data arrived in the last hour, and the signals of the source are healthy. **View received data** opens the data, and **Create pipeline** starts a pipeline for it.
   - **Receiver is healthy, but data needs attention**: the receiver answers, but no data arrived, or not every signal is healthy. Check the deployment, or wait for the next batch.
   - **Verification failed**: the receiver could not be checked. **Possible causes** lists a collector that is not running, a token that is invalid or expired, and a network or proxy that blocks the endpoint.

The endpoint comes from `http.external_url` when it is set, and from the address of the browser otherwise. Set `http.external_url` behind a reverse proxy so generated snippets point at the public address. See [Configuration](/es/configuration).

## Intake tokens

Senders authenticate with a bearer token: `Authorization: Bearer <token>`. A sender that can only do Basic authentication, such as the remote write export of a cloud provider's managed Prometheus, puts the API Token in the password of `Authorization: Basic` with any user name. Other Basic credentials are ignored, so a reverse proxy that asks for its own still works. A Splunk HEC sender presents the token as `Authorization: Splunk <token>`.

| Token | Permission | Created by | Use |
|---|---|---|---|
| Default intake token | `logs.write`, `metrics.write`, `traces.write`, `profiles.write`, and `apm.deploy` only: the **Data intake** policy | Datasource page, or `GET /api/v1/me/api-tokens/default` | Collectors, agents, and SDK exporters that send logs, metrics, and traces, and pipelines that [report deployments](/es/apm/deployments#reporta-despliegues-desde-ci). Does not expire. |
| RUM client token | `rum.write` only, bound to one application | Datasource page for Web RUM and mobile RUM sources, or `GET /api/v1/auth/tokens/rum?applicationId=<id>` | Browser and mobile code. The token is visible to end users. |
| Personal or service account token | What its member or service account may do, narrowed by its scope | **Account settings → API tokens**, or **Identity & Access → API tokens** for service accounts | Automation, scripts, and MCP clients. |

Use the default intake token, or a service account token that follows the **Data intake** policy, for senders that run continuously. Revoke a token from **Account settings → API tokens** or **Identity & Access → API tokens** to stop it immediately. A sign-in session of the web UI cannot send data: it lives in browser cookies, and the `Authorization` header does not accept it.

The **Datasource** page creates a RUM client token when an application id is entered. An application id contains 1 to 128 characters from `A-Z`, `a-z`, `0-9`, `.`, `_`, `:`, and `-`. Use the same id as `applicationId` in the SDK. See [Browser RUM SDK](/es/rum/browser-sdk).

## Endpoints y protocolos

| Protocolo | Endpoint | Remitentes compatibles | Stream de destino |
|---|---|---|---|
| HTTP JSON nativo | `POST /api/v1/intake/{logs,metrics,traces}/{stream}` | `curl`, código de la aplicación, sink `http` de Vector, salida `http` de Fluent Bit | El segmento de ruta `{stream}` |
| OTLP sobre HTTP | `POST /api/v1/logs`, `/api/v1/metrics`, `/api/v1/traces` | SDKs de OpenTelemetry y Collector | cabecera `stream-name`; de lo contrario, `default` |
| OTLP sobre gRPC | `:4317` | SDKs de OpenTelemetry y Collector | metadatos `stream-name`; de lo contrario, `default` |
| remote_write de Prometheus | `POST /api/v1/prometheus/api/v1/write` | Prometheus, VictoriaMetrics, exportaciones de Prometheus gestionado en la nube, cualquier remitente de remote_write v1 | cabecera `stream-name`; de lo contrario, `?stream=`; de lo contrario, `default` |
| `_bulk` de Elasticsearch | `POST /api/v1/_bulk` | Filebeat, Logstash, sink `elasticsearch` de Vector | `_index` de cada acción; de lo contrario, cabecera `stream-name`; de lo contrario, `default` |
| Splunk HEC | `POST /api/v1/services/collector/event`, `/api/v1/services/collector/raw` | Tencent Cloud CLS, salidas Splunk de Vector y Fluent Bit, reenviadores SIEM | `index` de cada evento; de lo contrario, `?index=`; de lo contrario, cabecera `stream-name`; de lo contrario, `default` |
| Push de Loki (JSON) | `POST /api/v1/loki/api/v1/push` | Remitentes que pueden hacer POST de la estructura JSON de Loki | cabecera `stream-name`; de lo contrario, `default` |
| Amazon Data Firehose, push de Google Cloud Pub/Sub, buses de eventos en la nube, Cloudflare Logpush, Heroku | `/api/v1/_kinesis_firehose`, `/api/v1/_gcp_pubsub`, `/api/v1/_cloud_events`, `/api/v1/_cloudflare`, `/api/v1/_heroku` | CloudWatch Logs y CloudWatch Metric Streams a través de Firehose, Cloud Logging a través de Pub/Sub, remitentes de EventBridge, Event Grid y CloudEvents, Cloudflare, Heroku | Se configura en el conector. Consulta [Conectores](/es/connectors). |

Todos los endpoints excepto los conectores push requieren un token de portador con el permiso de escritura de la señal: `logs.write`, `metrics.write`, `traces.write` o `profiles.write`. La organización proviene del token y nunca aparece en una URL.

### Límites que afectan a los remitentes

- **Tamaño de la solicitud.** La ingesta JSON nativa y los conectores push aceptan cuerpos de solicitud de hasta 16 MiB, y Firehose de hasta 64 MiB, contados después de la descompresión; los demás endpoints de ingesta aceptan hasta 2 MiB. Un cuerpo más grande se rechaza con `413`. Mantén los lotes por debajo de ese tamaño.
- **Compresión.** OTLP sobre HTTP no acepta cuerpos de solicitud comprimidos y responde `400`. Desactiva la compresión en el remitente; el exportador `otlphttp` de OpenTelemetry Collector comprime con gzip de forma predeterminada y necesita `compression: none`. La ingesta JSON nativa, `_bulk` de Elasticsearch, el push de Loki y los conectores push aceptan `Content-Encoding: gzip`.
- **Codificación de Loki.** Solo se decodifica la estructura de solicitud JSON. Promtail y Grafana Alloy envían protobuf comprimido con snappy de forma predeterminada y no pueden enviar a este endpoint.
- **Límite de velocidad.** El rol `router` limita las solicitudes por organización y responde `429` con una cabecera `Retry-After`. Un nodo `standalone` no aplica este límite. Consulta [Despliegue basado en roles](/es/deployment/role-based#límites-de-solicitudes).
- **Eventos denegados.** Un evento con un valor que no encaja en el tipo de su campo en el stream se deniega por sí solo, y el resto de la solicitud se escribe. Los números con una fracción en un campo `int64` no se deniegan: el campo pasa a ser `float64` (consulta [Esquema y campos](/es/streams#esquema-y-campos)). Cada endpoint informa qué denegó: JSON nativo en `rejected` y `errors`, OTLP en `partialSuccess`, `_bulk` de Elasticsearch como elementos con estado `400`, Splunk HEC con código `6`, y remote_write de Prometheus y push de Loki con `400`. Los remitentes no los reintentan. Los conectores push responden con éxito, ya que las plataformas reenviarían toda la solicitud, y el conector indica qué se denegó.
- **Streams de plataforma.** Los [streams de plataforma](/es/streams#flujos-de-plataforma), como `_molesignal` para la telemetría propia del servicio y `_audit` para el registro de auditoría, solo los escribe MoleSignal y rechazan la ingesta pública con `403`.

## Streams y esquema

Un stream se crea en su primera escritura, y el esquema evoluciona a medida que aparecen nuevos campos. Un stream se identifica por su nombre y tipo de señal, por lo que `default` puede existir para logs, métricas y trazas al mismo tiempo. Consulta [Streams](/es/streams).

Cada evento tiene una marca de tiempo en microsegundos desde la época Unix. JSON nativo y `_bulk` de Elasticsearch leen el campo `_timestamp`. Un evento sin `_timestamp` recibe la hora en que el servidor lo aceptó.

## HTTP JSON nativo

Envía un array de registros a `/api/v1/intake/{logs,metrics,traces}/{stream}`:

```bash
curl -X POST http://localhost:5080/api/v1/intake/logs/app \
  -H "authorization: Bearer $MS_TOKEN" \
  -H 'content-type: application/json' \
  -d "[{\"_timestamp\":$(date +%s)000000,\"level\":\"error\",\"msg\":\"db pool exhausted\",\"trace_id\":\"abc123\"}]"
```

La respuesta informa cuántos registros se aceptaron y rechazaron, con un motivo por índice rechazado:

```json
{"accepted":1,"rejected":0,"errors":[]}
```

## OpenTelemetry

Apunta un SDK o Collector de OpenTelemetry a la ruta base `/api`. El exportador añade `/v1/logs`, `/v1/metrics` y `/v1/traces`, que se asignan a `/api/v1/logs`, `/api/v1/metrics` y `/api/v1/traces`.

<Tabs>
  <Tab title="OTLP sobre HTTP">
    Variables de entorno del SDK:

    ```bash
    export OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf
    export OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:5080/api
    export OTEL_EXPORTER_OTLP_HEADERS="authorization=Bearer ${MS_TOKEN}"
    ```

    OpenTelemetry Collector:

    ```yaml
    exporters:
      otlphttp/molesignal:
        endpoint: http://localhost:5080/api
        compression: none
        headers:
          authorization: "Bearer ${env:MS_TOKEN}"
    ```

    Envía protobuf (`application/x-protobuf`), la codificación predeterminada de los SDKs y del Collector. Logs, métricas y trazas también aceptan JSON (`application/json`). Añade una cabecera `stream-name` para seleccionar un stream distinto de `default`. La cabecera se aplica a cada señal enviada a través de ese exportador.
  </Tab>
  <Tab title="OTLP sobre gRPC">
    El receptor gRPC de OTLP escucha en el puerto `4317` y sirve los servicios de logs, métricas, trazas y perfiles. No termina TLS. Termina TLS delante de él para el tráfico que sale de una red de confianza.

    ```bash
    export OTEL_EXPORTER_OTLP_PROTOCOL=grpc
    export OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4317
    export OTEL_EXPORTER_OTLP_HEADERS="authorization=Bearer ${MS_TOKEN}"
    ```

    OpenTelemetry Collector:

    ```yaml
    exporters:
      otlp/molesignal:
        endpoint: localhost:4317
        tls:
          insecure: true
        headers:
          authorization: "Bearer ${env:MS_TOKEN}"
    ```

    Elimina `insecure: true` cuando un proxy que termina TLS esté delante del puerto. El puerto `5082` es el puerto gRPC interno del clúster y no es un receptor OTLP.
  </Tab>
</Tabs>

Las métricas OTLP se almacenan como un evento por punto de datos. Consulta el [contrato de almacenamiento de métricas](/es/query#campos-de-métricas-otlp) para conocer los campos almacenados.

## remote_write de Prometheus

Añade MoleSignal como destino de remote_write en `prometheus.yml`:

```yaml
remote_write:
  - url: http://localhost:5080/api/v1/prometheus/api/v1/write
    authorization:
      credentials: "${MS_TOKEN}"
```

Un stream de métricas contiene las métricas de una fuente, así que asigna a cada servidor de Prometheus su propio stream con la cabecera `stream-name` (`headers:` en la entrada `remote_write`); sin ella, las muestras van a `default`. Un remitente que no puede establecer cabeceras nombra el stream en la URL, como en `/api/v1/prometheus/api/v1/write?stream=aliyun`. Cada muestra se convierte en una fila cuyo `metric_name` es su `__name__`. Otras etiquetas se convierten en campos, y una etiqueta con el mismo nombre que un campo de métrica, como `metric_name`, se conserva como `exported_<name>`. Los histogramas nativos y los metadatos de métricas se omiten, y los exemplars se almacenan junto a las muestras.

## Bulk de Elasticsearch

Los remitentes que hablan el protocolo bulk de Elasticsearch funcionan sin dependencia de Loki u OTLP:

```bash
curl -X POST http://localhost:5080/api/v1/_bulk \
  -H "authorization: Bearer $MS_TOKEN" \
  -H 'content-type: application/x-ndjson' \
  --data-binary $'{"index":{"_index":"app"}}\n{"level":"info","msg":"hello"}\n'
```

El `_index` de cada acción selecciona el stream de destino. Sin él, se aplica la cabecera `stream-name` y, después, `default`.

## Push de Loki

El endpoint acepta la estructura de solicitud JSON de Loki:

```json
{"streams":[{"stream":{"service":"checkout","level":"error"},"values":[["1700000000000000000","payment failed"]]}]}
```

Las etiquetas se convierten en campos, la línea de log se convierte en el campo `message` y la marca de tiempo en nanosegundos se convierte a microsegundos. La respuesta es `204`. Selecciona el stream de destino con la cabecera `stream-name`.

## Splunk HEC

Los emisores que hablan el protocolo HTTP Event Collector de Splunk, como Tencent Cloud CLS enviando a Splunk o las salidas de Splunk de Vector y Fluent Bit, pueden enviar a MoleSignal sin cambios. Indica `https://molesignal.example.com/api/v1` como dirección HEC y un token de API con permiso para escribir logs como token HEC, enviado como `Authorization: Splunk <token>`.

| Endpoint | Cuerpo |
|---|---|
| `POST /api/v1/services/collector/event`, también `/services/collector` | Objetos JSON uno tras otro, cada uno `{"time", "host", "source", "sourcetype", "index", "event", "fields"}` |
| `POST /api/v1/services/collector/raw` | Texto, un evento de log por línea; `host`, `source`, `sourcetype` e `index` provienen de la consulta |
| `GET /api/v1/services/collector/health` | Responde `{"text":"HEC is healthy","code":17}` sin token |

Un `event` que es un objeto JSON aporta los campos del log; cualquier otro `event` se convierte en `message`. `fields`, `host`, `source` y `sourcetype` se convierten en campos, y `time`, en segundos, se convierte en la hora. `index` nombra el stream; si no, el parámetro de consulta `index`; si no, la cabecera `stream-name`; si no, `default`. La respuesta es `{"text":"Success","code":0}`, o los propios códigos de error de HEC con `400`. Cuando un stream rechaza eventos porque un valor no encaja con el tipo de su campo, los demás eventos se escriben y la respuesta es el código `6`, con la posición del primer evento rechazado en el cuerpo como `invalid-event-number` y el motivo en `text`. No se ofrece la confirmación del indexador.
