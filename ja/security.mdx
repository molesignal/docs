MoleSignal は、ウェブのナビゲーションより下位のレイヤーである API とデータプレーンで、テナント分離と認可を適用します。

## テナント分離

組織のすべてのストリームと製品リソースに、所有する組織を示す `org_id` があります。クエリプランナーは、実行前にクエリの範囲を認可された組織に限定します。リソースハンドラーも対象を読み込み、読み取りや変更の前に所属組織を検証します。

ワークスペースをまたいでアクセスするには、IAM で権限を明示的に付与するか、サポート対象のリソース共有を使用します。検索対象のリソースが現在の組織に属していなくても、別の組織に自動で切り替わることはありません。

`_sys` 組織は、保護されたプラットフォームスコープです。テナントセッションや `mspat-*` API トークンでは、プラットフォーム管理者や MoleSignal 自体のテレメトリを列挙できません。

## 認証と認可

MoleSignal は、次の認証方法に対応しています。

- HttpOnly Cookie に保存したブラウザーセッション。ワークスペースを切り替えると、新しいスコープに合わせて Cookie を書き換えます。
- `Authorization` ヘッダーに指定する `mspat-<36>` 形式の API トークン。
- アクセス範囲を限定した公開ルートやインテグレーション用ルート向けの、トークン自体で認証できる専用トークン。

パスワードでサインインするか、管理者が **ID とアクセス → SSOプロバイダー** で設定した OIDC、OAuth 2.0、SAML、LDAP のいずれかのプロバイダーを使用します。

検索に使用する API トークンのプレフィックスを保存し、シークレットはハッシュ化します。トークン全体を表示するのは作成時のみです。

認証後、サーバーはデータベースを参照し、権限、ロール、バインディング、リソース間の関係、対象の所有者を特定します。[ID とアクセス](/ja/identity)を参照してください。

## ブラウザーセッション

サインイン時に 2 つの Cookie を設定します。1 つはすべての API リクエストに付与する有効期間 15 分のアクセストークン、もう 1 つは `[auth].session_ttl_secs` の経過でセッションが終了するまでアクセストークンを更新するリフレッシュトークンです。どちらにも `HttpOnly` を設定するため、ページのスクリプトでは読み取れません。また、`SameSite=Strict` を設定し、HTTPS では `Secure` も設定します。セッションを使ってデータを変更するリクエストは、MoleSignal のページから送信する必要があります。ブラウザーは送信元を `Sec-Fetch-Site` で示します。オリジンをまたぐ API 呼び出しには認証情報を付与しません。

サーバーはセッションレコードを保持しません。どちらのトークンも署名付き JWT です。サインアウトすると、そのブラウザーの Cookie が削除されます。ブラウザーからコピーしたトークンは、有効期限が切れるまで有効です。アクセスをすぐに遮断するには、アカウントを無効にしてください。サーバーはリクエストとトークンの更新のたびにアカウントの状態を確認します。署名キーをローテーションすると、 24 時間の猶予期間が過ぎた時点ですべてのセッションが終了します。

## JWT 署名キー

初回起動時に JWT 署名キーを生成し、データベースに保存します。メタデータのエンドポイントはキーの生バイト列を返しません。ローテーション後は新しいキーでトークンに署名し、旧キーで署名したトークンも 24 時間は有効です。すべてのノードが再起動せずに新しいキーを取り込みます。

署名キーの一覧表示やローテーションには、プラットフォーム権限 `sys.signing_keys.rotate` が必要です。

```text
GET  /api/v1/auth/jwt/secrets
POST /api/v1/auth/jwt/rotate
```

デプロイポリシーで固定の初期キーが必要な場合にのみ、`MS_AUTH_JWT_SECRET_OVERRIDE` を使用してください。

## 監査

セキュリティに関わる操作や製品内のデータを変更する操作では、実行者、組織、アクション、対象、時刻、安全に記録できるメタデータを記録します。`audit.read` 権限があれば、**設定 → 監査**で組織のイベントを検索できます。同じイベントは `_audit` ストリームにも行として記録します。[監査ストリーム](/ja/settings/data-security#監査ストリーム)を参照してください。

監査ログはデフォルトで 90 日間保持します。1 日に 1 回、保持期間を超えたログをすべての組織とプラットフォームから削除します。削除したログは復元できません。保持期間は `_sys` 組織の **設定 → 監査ログの保持** で設定します。設定には `sys.settings.retention.manage` が必要です。`0` を指定すると無期限に保持します。保持期間を変更するたびに、プラットフォームの監査ログに `audit_retention.update` として記録します。

認証情報、モデルキー、機密性の高い Webhook ヘッダー、署名キーの生データは監査ペイロードに含めません。

## リソース共有

ダッシュボードやレポートの公開リンクは、リンクを知っていればアクセスできる認証情報ですが、組織のトークンにはなりません。MoleSignal はリンクを短時間だけ有効な HttpOnly の共有セッションに交換し、アクセスを保存済みのリソース 1 件に限定します。

公開ダッシュボードのパネルでは、サーバーに保存したクエリのみを、機能を制限したプロキシ経由で実行できます。共有には有効期限、パスワード、閲覧回数の上限、ダウンロードの無効化を設定できます。また、共有リンクの取り消しやローテーションもできます。[リソース共有](/ja/resource-sharing)を参照してください。

## フィールドレベルの暗号化

ストリームを作成するときに、暗号化するフィールドを指定してください。MoleSignal は対象フィールドの値を AES-256-GCM で暗号化してから Parquet に書き込みます。通常のクエリは暗号文を返します。SQL では `decrypt(field)` で平文に戻せます。[ストリーム](/ja/streams#暗号化フィールド)を参照してください。

組織のデータキーは `MS_CIPHER_KEY` の暗号化ルートキーでラップし、作成後にキー自体を返すことはありません。キーメタデータの読み取りには `org.cipher_keys.read`、キーの作成、ローテーション、削除には `org.cipher_keys.manage` が必要です。

<Warning>
  `MS_CIPHER_KEY` を紛失すると、暗号化したフィールドを復元できなくなる場合があります。キーはシークレットマネージャーに保存し、 PostgreSQL やオブジェクトストレージとは別にバックアップしてください。
</Warning>

## シークレットとテレメトリの安全管理

- データベース、オブジェクトストレージ、SMTP、SSO、モデルプロバイダー、Webhook の認証情報は、シークレットマネージャーに保存してください。
- 外部へのトレースエクスポートで機密性の高いヘッダーを指定する場合は、`env:` または `secret:` の参照を使用してください。
- 内部 gRPC ポート `5082` はクラスターのプロトコルにも使用するため、信頼できるネットワーク内に限定してください。
- 外部向けの HTTP、OTLP gRPC `4317`、Flight SQL `5083` は TLS で保護してください。
- リモート診断を明示的に保護している場合を除き、pprof リスナーはループバックでのみ待ち受けるようにしてください。
- バックエンドのトレースには、リクエストボディ、SQL の値、認証情報、プロンプト、モデル出力、ツールの引数を含めません。

## レート制限とサイズ制限

`router` ロールは組織ごとのトークンバケットを取り込みリクエストとクエリリクエストに適用し、制限を超えると `Retry-After` ヘッダー付きの `429` を返します。`standalone` ノードではこの制限を適用しません。 [ロールベースのデプロイ](/ja/deployment/role-based#レート制限)を参照してください。取り込みリクエストのボディが 2 MiB（ネイティブ JSON の取り込みでは 16 MiB）を超えると、`413` を返して拒否します。

パスワードによるサインインでは、アカウントと送信元アドレスごとに失敗回数をカウントします。上限に達すると、 `Retry-After` 付きの `429` を返し、パスワードの照合を行いません。ロックするのはリクエストの送信元アドレスだけです。アカウント自体にはサインイン試行の頻度制限のみを適用するため、別の利用者のパスワードを繰り返し間違えても、そのアカウントをロックすることはできません。存在しないアカウントへの試行も同じ方法でカウントし、同じレスポンスを返します。 [サインイン制限](/ja/settings/platform#サインイン制限)を参照してください。

## 本番環境のセキュリティ強化

実データを取り込む前に、サンドボックスのデフォルト設定を置き換えてください。対象は root アカウント、`MS_CIPHER_KEY`、データベースとオブジェクトストレージの認証情報です。 [本番環境のチェックリスト](/ja/deployment/production-checklist)を参照してください。内部ネットワークからインターネットに公開するのは、外部からのコールバックと公開ページのみにしてください。[パブリックアクセス](/ja/public-access)を参照してください。
