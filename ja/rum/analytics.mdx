**RUM → 分析**では、セッション中のユーザー行動を分析します。一度に分析するのは 1 つのアプリケーションで、単一の環境またはすべての環境を対象に、表示中の時間範囲で集計します。時間範囲を指定せずにページを開くと、過去 7 日間が対象になります。ビューは **ファネル**、 **パス**、**リテンション**の 3 つです。どのビューもブラウザーアプリケーションとアプリに対応します。アプリでは「ページ」の代わりに「画面」と表示します。4 つ目の[**ヒートマップ**](/ja/rum/heatmaps)は、ブラウザーアプリケーションの 1 ページを対象にします。

ビューの分析条件はすべて URL に含まれるため、リンクで共有できます。

## ファネル

ファネルは、一連のステップを指定の順序で通過したセッションを集計します。購入手続きなどのフローで、ユーザーがどこで離脱したかを確認できます。

### ステップ

ファネルには 2～8 個のステップを設定できます。**ステップを追加**で追加し、ステップの末尾にある × で削除します。ステップには 2 つの種類があります。

| 種類 | 内容 | 照合できるフィールド |
|---|---|---|
| **ページ**（アプリでは**画面**） | 開いたページまたは画面です。 | **ページグループ**（`view.url_path_group`、ID などの可変部分をまとめたパス）、**完全一致パス**（`view.url_path`）、**ビュー名**（`view.name`）。ブラウザーのページではページグループ、アプリの画面ではビュー名が初期設定です。 |
| **アクション** | クリック、タップ、カスタムアクションなどのユーザー操作です。 | **ターゲット名**（`action.target.name`）、**ターゲットセレクター**（`action.target.selector`）、**タイプ**（`action.type`）。 |

各ステップでは、指定したフィールドの値を照合します。値は、時間範囲内のデータで出現頻度の高い候補から選ぶか、直接入力します。**一致する**は値全体を照合し、`*` は任意の文字列を表します。**含む**は、大文字と小文字を区別せず、指定した文字列を含む値に一致します。

### セッションの集計方法

最初のステップでは、条件を満たす最初の行でセッションを集計します。以降のステップでは、同じセッション内で直前のステップの行より後にあり、そのステップの条件を満たす最初の行で集計します。ステップの間に別のページの閲覧やアクションがあっても、集計には影響しません。たとえば、カートと購入手続きの間に別のページを 5 つ開いたセッションも、購入手続きに到達したとみなします。

- **制限時間**を設定すると、最初のステップから指定の時間内に到達したステップでのみ、セッションを集計します。5 分、30 分、1 時間、1 日から選択できます。**時間制限なし**では、経過時間にかかわらずセッションを集計します。
- **セッションの集計軸**では、最初のステップでセッションを集計した行のフィールド値ごとにファネルを表示します。ブラウザー、システム、デバイスタイプ、バージョン、国から選択できます。セッション数が多い上位 10 件の値を表示します。 **全セッションをまとめて集計**では、ファネルを 1 つ表示します。

### 表示内容

ステップごとに 1 行を表示します。バーの長さは、最初のステップのセッション数に対する割合を示します。

| 列 | 意味 |
|---|---|
| **セッション** | ステップに到達したセッション数です。 |
| **初回ステップからの到達率** | 最初のステップに到達したセッションのうち、このステップに到達した割合です。 |
| **離脱率** | 直前のステップに到達したセッションのうち、このステップに到達しなかった割合です。離脱率が 50% を超えると赤で表示します。 |
| **所要時間の中央値** | 直前のステップからこのステップまでの所要時間の中央値です。 |

フィールド別に集計するファネルでは、値ごとに 1 行のテーブルも表示します。各行には、各ステップのセッション数とその隣に直前のステップからの到達率、さらに最初のステップに到達したセッションのうち全ステップに到達した割合を示す**最初から最後まで**を表示します。

最初のステップに到達したセッションがない場合は、その旨を表示し、時間範囲を広げるよう案内します。ステップ、制限時間、集計軸のフィールドは、それぞれ URL の `steps`、`win`、`by` に対応します。各ステップは、ページなら `v:`、アクションなら `a:` に続けて、フィールド、`=` または `~`（含む）、URL エンコードした値の順に記述します。ステップは `|` でつなぎます。

## パス

パスは、セッションで開いたページをたどります。各列にはセッション数が多いページを並べ、ページ間を結ぶ帯の太さで一方のページからもう一方のページに遷移したセッション数を示します。

- **基準ページ以降**では基準ページの後に開いたページを、**基準ページ以前**ではその前に開いたページをたどります。基準ページを指定しない場合、各セッションの最初のページを起点にし、さかのぼる場合は最後のページを終点にします。
- データ内で出現頻度の高いページから選ぶか、直接入力します。選択を解除するには **クリア**を使用します。チャート上のページをクリックすると、そのページを基準にパスを表示します。
- **表示するページ数**では、基準ページの後（または前）に表示するページ数を 1～6 ページの範囲で指定します。デフォルトは 3 ページです。
- **ページの集計単位**では、ページグループ、完全一致パス、ビュー名を選択できます（ブラウザーアプリケーションの場合）。

各ページの高さは、そのページを開いたセッション数を表します。各列にはセッション数が多い上位 8 ページの名前を表示し、残りは **その他のページ**にまとめます。再読み込みなどで同じページを続けて開いても、1 回として集計します。基準ページは最初の列に、さかのぼる場合は最後の列に表示します。どのセッションも到達しなかった列は表示しません。ツールチップには、そのページから先に進まなかったセッション数（さかのぼる場合は、そのページから始まったセッション数）を表示します。

基準ページ、方向、ページ数、フィールドは、それぞれ URL の `pivot`、`dir`（`before`）、`depth`、`page` に対応します。

## リテンション

リテンションは、再訪したユーザーを集計します。時間範囲内の同じ日または週に初めて確認されたユーザーをコホートとしてまとめ、各セルにはそのセルに対応する期間数が経過した時点で再訪したユーザーの割合を表示します。

- 最初に **日**または **週**を選択します。日は UTC を基準とし、週は UTC の月曜日に始まります。表示する側のタイムゾーンにかかわらず、コホートには開始日を表示します。
- 次に、追跡する期間数を選択します。日単位のコホートでは **7 日後**、**14 日後**、**30 日後**から選択し、週単位のコホートでは週数で指定します。
- ユーザーは、セッションのユーザー ID で識別します。ユーザー ID がない訪問者には、SDK がデバイスに保存する匿名 ID を使用します。
- 初回訪問の判定には、指定した時間範囲内の履歴だけを使用します。時間範囲より前に訪問していたユーザーも、範囲内で初めて確認された日に新規ユーザーとして扱います。
- 時間範囲の終了時点でまだ終わっていない期間は集計せず、セルにダッシュを表示します。
- **平均**では、集計可能なコホートの全ユーザーを母数として再訪率を算出します。そのため、ユーザー数の多いコホートほど結果に大きく影響します。

期間の単位と期間数は、それぞれ URL の `period` と `periods` に対応します。

## セグメント

セグメントは、特定のプランの顧客や特定の国からの訪問者など、指定したセッションのグループにすべてのビューを絞り込みます。ページ上部の **セグメント**で選択します。選択内容は URL（`segment`）に含まれるため、セグメントを指定した分析もリンクで共有できます。タブ内の各ビューと、選択候補に表示するページや値には、選択したセグメントを適用します。

セグメントの名前は、[アプリケーションの設定](/ja/rum/applications#セグメント)で指定します。セグメントは、ユーザーや地域など、セッション中に変化せず、すべての行に記録される属性でセッションを分類します。セッション中の行動では分類しません。

## 集計方法

RUM の他のクエリを処理するエンジンが、ビュー、セッション、アクションを対象に 1 つのステートメントを実行し、各ビューを集計します。ビューの数値が変わるたびに新しいリビジョンを書き込み、ビューに紐づくユーザーを調べるときは最新のリビジョンを使います。ページ、アプリケーション、環境、リリース、ブラウザーなど、どのリビジョンでも値が変わらない項目だけを参照するステップでは、書き込まれたビューをそのまま読み取ります。これにより、ビューごとに最新のリビジョンを選ぶ処理を省けます。エラー数や Web Vitals などの数値や、ビューに紐づくユーザーを参照するステップでは、最新のリビジョンを使います。エンジンが閲覧者に対してマスクするデータは、そのままマスクします。集計が制限時間を超えると、ページを表示したままその旨を通知します。時間範囲を絞って再実行してください。同じクエリは、API の [`/api/v1/rum/analytics`](/ja/api/rum#ファネル、パス、リテンション) でも実行できます。

目安として、CPU が 10 コアの単一ノードで、対象期間に 100 万セッション（1,800 万イベント）がある場合、4 ページのファネルは約 2 秒、8 ページのファネルは約 5 秒、パスは約 6 秒、リテンションは約 1.5 秒で結果を返しました。処理コストは対象期間内のセッション数が増えるほど高くなります。ファネルでは、ステップ数が増えても処理コストが高くなります。

アプリケーションが[一部のセッションだけを保持する](/ja/rum/sampling)場合、ファネルとパスでは、保持した各セッションをサンプリング率の逆数で重み付けして全セッションの件数を推定し、ページに **推定値** と表示します。リテンションでは、保持したセッションで確認できたユーザーを数えます。サンプリングを使う場合、コホートには保持したセッションのユーザーだけが含まれ、訪問頻度の高いユーザーほどコホートに含まれやすくなります。

このページを表示するには `rum.analytics.read` 権限が必要です。[RUM](/ja/rum#権限) を参照してください。

## Mole Agent

Mole Agent は `get_rum_funnel`、`get_rum_paths`、`get_rum_retention` を使って同じクエリを実行します。組み込みスキル `/rum-triage` は、ユーザーの遷移フローに関する問題を調査するときにこれらを使い、参照したファネルやパスをこのページへのリンクとして示します。
