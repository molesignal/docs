ブラウザー RUM SDK は、セッションの作成時にサンプリング対象とするかどうかを決定します。この判定は、そのセッションが続く間、アプリケーションのすべてのタブで変わりません。

## サンプリング率を設定する

```ts
const rum = init({
  applicationId: 'checkout-web',
  clientToken: 'mspat-your-client-token',
  site: 'https://molesignal.example.com',
  sessionSampleRate: 25,
  sessionReplaySampleRate: 20,
});
```

どちらの値も `0` から `100` までのパーセンテージです。

- `sessionSampleRate` は、SDK がセッションと関連する RUM イベントを送信するかどうかを制御します。デフォルトは `100` です。
- `sessionReplaySampleRate` は、サンプリング対象になったセッションにのみ適用します。デフォルトは `0` です。

実効リプレイ率は、2 つのサンプリング率の積です。この例では、全セッションの約 25% が RUM データを送信し、全セッションの約 5% がリプレイを記録します（`25% × 20%`）。

<Note>
  `startSessionReplayRecording()` を呼び出すと、サンプリング対象の現在のセッションでリプレイを有効にできます。ただし、このメソッドで `sessionSampleRate` によって除外されたセッションをサンプリング対象に戻すことはできません。
</Note>

## セッションの一部をサーバー側で保持する

SDK 側のサンプリングに加えて、アプリケーションでは、送信元のクライアントを問わず、受信したセッションの一部を保持できます。 **RUM → アプリケーション**で対象のアプリケーションを開き、**セッションの保持**を探してください。**セッションの保持率（%）**は `0` から `100` まで指定できます。デフォルトは `100` で、すべてのセッションを保持します。

サーバーはセッション単位で保持または破棄します。セッション ID のハッシュに基づいて判定するため、どのノードでも、同じセッションのすべてのイベントとリプレイセグメントに同じ判定を適用します。セッションを保持する場合は、これらのデータをすべて保持します。セッションを破棄する場合は、エラーを除き、イベント、`rum_sessions` の行、リプレイのいずれも残しません（ [すべてのエラーを保持](#すべてのエラーを保持)を参照）。

保持率は、SDK が送信したセッションに対する割合です。SDK で `sessionSampleRate: 50` を指定し、**セッションの保持率**を `20` に設定すると、全セッションの約 10% を保存します。`0` に設定するとセッションを保存しないため、 SDK の設定を変えずにアプリケーションを一時停止する場合に適しています。[取り込み API](/ja/rum/events#レスポンス) のレスポンスは、サンプリングで除外したイベント数を `sampled` で返します。 SDK はこのレスポンスから、データが失われたのではなく除外されたと判断できます。保持しないセッションのリプレイセグメントには、`sampled: true` を含む `200` を返します。

変更は、変更後に到着したイベントに適用します。保存済みのセッションはそのまま残り、変更前に開始したセッションは、変更時点から新しい保持率に基づいて保持または破棄します。

アプリケーションのフィルターに `session.type` を指定しない限り、[テストで生成したセッション](/ja/rum/test-traffic)のデータはすべて保持します。実ユーザー向けの保持率によって、チェックのセッションが失われるのを防ぐためです。

### フィルター

フィルターを使うと、条件に一致するセッションに個別の保持率を設定できます。たとえば、本番環境のセッションをすべて保持し、それ以外を 10% だけ保持できます。 **セッションの保持**でフィルターを追加してください。フィルターには名前、`0` から `100` までの保持率、最大 5 つの条件を設定できます。セッションがフィルターに一致するには、すべての条件を満たす必要があります。条件のないフィルターは、すべてのセッションに一致します。

条件では、セッションの 1 つの属性を値のリストと比較します。属性がいずれかの値に**一致する**か、どの値にも**一致しない**かを指定します（属性に値がないセッションは、どの値にも一致しません）。値の大文字と小文字は区別しません。`*` は任意の文字列を表すため、 `2.*` は 2 系のすべてのバージョンに一致します。1 つの条件に最大 20 個の値を指定でき、1 つのアプリケーションに最大 10 個のフィルターを設定できます。

| 属性 | フィールド |
|---|---|
| 環境 | `env` |
| サービス | `service` |
| バージョン | `version` |
| SDK のプラットフォーム | `source` |
| セッションタイプ | `session.type` |
| 国 | `geo.country_iso_code` |
| ブラウザー | `browser.name` |
| OS | `os.name` |
| デバイスタイプ | `device.type` |

フィルターはリストの順に評価し、**セッションに最初に一致したフィルターで保持率を決定します**。適用範囲が狭いフィルターは、広いフィルターより上に配置してください。どのフィルターにも一致しないセッションには、フィルターの下にある**その他のセッションの保持率（%）**を適用します。フィルターがない場合は、この保持率をアプリケーション全体に適用します。

<Note>
  同じセッションのすべてのイベントに同じ判定を適用する必要があるため、条件に指定できるのはセッション中に変わらない属性だけです。セッション中のユーザーの操作や、SDK が後から取得するユーザー情報（サインイン後に設定するユーザー ID など）を、セッションを保持するかどうかの判定には使用できません。エラーの保持は、後述の専用スイッチで設定します。
</Note>

リプレイセグメントは、そのセグメントに含まれるセッション情報に基づいて判定します。判定に使うのは、ブラウザーとアクセス元の地域、およびブラウザーと Flutter の SDK がリクエストボディで送信する `env`、`service`、`version` です（SDK は、設定されていない `env` や `version` を送信しません）。セグメントに属性の値がない場合は、セッションに一致する可能性があるフィルターのうち、いずれかで保持の判定となれば、そのセグメントを保持します。

### すべてのエラーを保持

**すべてのエラーを保持**をオフにしない限り、保持しないセッションのエラーも保存します。これにより、まれなエラーがセッションとともに失われず、他のエラーと同様にイシューとして集計されます。このようなエラーは `rum_errors` にのみ行を作成します。対応するセッションの行、ビュー、リプレイは存在しないため、イシューページではセッションへのリンクの代わりに*セッションは保持されていません*と表示します。

### 集計値は推定値です

各行の `retention.rate` には、その行に適用した保持率を記録します（保持率 25% のフィルターで保持したセッションなら `25`）。保持した理由は `retention.filter` に記録します。値は、フィルターの ID、その他のセッションの保持率を適用した場合は `default`、保持しなかったセッションのエラーの場合は `errors` です。**すべてのエラーを保持**がオンの場合は、すべてのエラーを保持するため、どのセッションのエラーでも `100` を記録します。

集計値を表示するページでは、保持率の逆数で各行を重み付けします。たとえば、保持率 25% で保持したセッション 1 件は 4 件として数えます。ページには **推定値**とセッションの保持率を表示します。集計値は、すべてのセッションを保持した場合の値を推定したものです。

- 件数、合計、平均は保持率に基づいて補正し、パーセンタイルも同じ保持率に基づいて重み付けします。
- 観測したユーザー数、最小値、最大値は補正せず、観測値をそのまま表示します。
- ファネルとパスでは、保持率に基づいてセッション数を補正します。リテンションのコホートはユーザー単位のため、観測したユーザー数をそのまま集計します。
- エクスプローラーは保持した行を一覧表示し、件数やチャートも実際に保持した行に基づいて集計します。同じ数値を取得するには、`estimate=false` を [集計 API](/ja/api/rum#行の集計) に渡してください。
- **最小サンプル数**を設定したアラートルールは、推定件数ではなく、保存済みの行数がしきい値に達するまで待機します。

サンプリングにはばらつきが伴います。少数のセッションに基づく集計値は、どれだけ補正しても信頼性が低くなります。

## 初期値を選ぶ

| トラフィックの特性 | セッションのサンプリング率 | サンプリング対象セッション内のリプレイ率 |
|---|---:|---:|
| 開発環境またはトラフィックを制御した QA 環境 | `100` | `100` |
| トラフィックが少ない本番環境 | `100` | `10`–`25` |
| トラフィックが多い本番環境 | `10`–`50` | `1`–`10` |

これらは初期設定の目安であり、すべての環境に適したデフォルト値ではありません。ロールアウト前に、イベント量、オブジェクトストレージの必要容量、保持期間、ブラウザーおよびリリースごとに必要なセッション数を見積もってください。

## セッションの切り替え

SDK はサンプリングの判定結果をセッションクッキー `_msrum_s_<applicationId>` に保存します。このクッキーはアプリケーションの各タブで共有します。次のいずれかの時間に達すると、新しいセッションを開始します。

- `sessionInactivityTimeout`：デフォルトは 15 分です。
- `maxSessionDuration`：デフォルトは 4 時間です。

どちらの値もミリ秒単位で指定します。指定できる範囲は 1 分から 24 時間までです。

```ts
sessionInactivityTimeout: 15 * 60_000,
maxSessionDuration: 2 * 60 * 60_000,
```

サンプリングオプションを変更しても、現在のセッションに保存済みの判定結果は変わりません。新しい設定をテストするときは、`stopSession()` を呼び出すか、`_msrum_s_<applicationId>` クッキーを削除してください。

## クライアント側のデータ量を制限する

メモリ使用量とリクエストサイズを予測できる範囲に収めるには、送信設定を使用してください。

```ts
flushInterval: 5_000,
batchSize: 50,
replayFlushInterval: 10_000,
replayBatchSize: 100,
maxQueueSize: 1_000,
```

設定を変更するたびに、取り込みレート、リプレイのストレージ使用量、ブラウザーの負荷、調査に必要なデータのカバレッジを監視してください。サンプリング設定の変更は、アプリケーションとリリースごとに段階的に適用してください。
