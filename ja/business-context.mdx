ビジネスキーは、テレメトリーを、それがサービスを提供した相手（テナント、プラン、ユーザー階層、実験グループなど）に結び付けます。キーを宣言すると、APM サービスページではリクエストがキー別に分割され、インシデントには、その障害が影響した値が一覧表示され、根本原因分析ではどのテナントが失敗したかが示されます。MoleSignal はこの目的のためにデータを書き換えません。アプリケーションがテレメトリーにキーを設定し、サーバーが宣言で指定されたフィールドを読み取ります。

## キーを宣言する

**APM → 設定**を開き、**ビジネスコンテキスト**カードを使用します。各キーには次の項目があります:

| フィールド | メモ |
|---|---|
| **キー** | リンクおよび Mole Agent で使用される名前。小文字、数字、`_` を使用します（例: `tenant`）。 |
| **ラベル** | 閲覧者に表示される名前（例: `Tenant`）。 |
| **スパン属性** | それを保持するトレースストリームのフィールド（例: `tenant.id`）。 |
| **ログフィールド** | それを保持するログフィールド。 |
| **RUM フィールド** | RUM フィールド。含まれる JSON フィールドのキー（例: `context.tenant`）。 |
| **重要な値** | 特に重要な値（主要顧客など）。カンマで区切ります。インシデントの影響が表示されるすべての場所でフラグが付けられます。 |

キーは少なくとも1つのシグナルのフィールドを指定します。キーは最大8個までです。カードの管理には `apm.settings.manage` が必要です。同じ宣言は [API](/ja/api/business-context) で設定できます。

## テレメトリーにキーを設定する

スパン属性とログ属性は取り込み時にそれぞれのストリームのフィールドになるため、属性として設定したキーですぐに分割できます。リクエストのすべてのスパンとログレコードにキーを設定する通常の方法は W3C baggage です: リクエストが入ってくる場所でキーを一度設定すると、baggage プロセッサが、リクエストが生成するすべてのスパン（および、 SDK に対応するものがある場合はすべてのログレコード）にコピーします。これはリクエストが到達するすべてのサービスで行われます。

<Warning>
baggage はリクエストヘッダーで、第三者を含むすべてのダウンストリームサービスに伝わります。コピーするのは宣言したキーだけにしてください。シークレットや個人データを baggage に入れないでください。
</Warning>

| 言語 | baggage をスパンにコピーするもの |
|---|---|
| Java | OpenTelemetry Java エージェント、または autoconfigure とともに使用する `io.opentelemetry.contrib:opentelemetry-baggage-processor`。`otel.java.experimental.span-attributes.copy-from-baggage.include=tenant.id` を設定します（ログには `otel.java.experimental.log-attributes.copy-from-baggage.include` も設定します）。 |
| Go | `go.opentelemetry.io/contrib/processors/baggagecopy`: トレーサープロバイダーで `baggagecopy.NewSpanProcessor(filter)` を使用します。 |
| Node.js | `@opentelemetry/baggage-span-processor`（`BaggageSpanProcessor`）と `@opentelemetry/baggage-log-record-processor`（`BaggageLogRecordProcessor`）。 |
| Python | `opentelemetry-processor-baggage`: トレーサープロバイダーで `BaggageSpanProcessor(predicate)` を使用します。 |
| .NET | `OpenTelemetry.Extensions`: baggage アクティビティプロセッサ。エクスポート用プロセッサより前に登録します。 |
| Ruby | `opentelemetry-processor-baggage` gem を使用します。 |
| PHP, Rust, Erlang/Elixir | リクエストが入ってくる場所で baggage からキーを読み取り、スパン属性とログ属性として手動で設定します。 |

各プロセッサはコピーするキーを選択する述語を受け取ります。すべてをコピーする述語ではなく、宣言したキーだけを保持する述語を渡してください。たとえば Python では次のようになります:

```python
from opentelemetry.processor.baggage import BaggageSpanProcessor

declared = {"tenant.id", "plan"}
tracer_provider.add_span_processor(BaggageSpanProcessor(lambda key: key in declared))
```

また、リクエストが入ってくる場所では次のようにします:

```python
from opentelemetry import baggage, context

token = context.attach(baggage.set_baggage("tenant.id", tenant_id))
```

RUM の場合は、ブラウザ SDK のコンテキストでキーを設定します（例: `context.tenant`）。そのフィールドをキーの **RUM フィールド**として指定します。

## キーが使用される場所

| ページ | 表示内容 |
|---|---|
| [APM](/ja/apm) サービスページ | **ビジネスキー別のリクエスト**: 各値のリクエスト数、エラー率、P95。重要な値にはフラグが付き、トレースページで他の任意のフィールドで分割するためのリンクがあります。 |
| [インシデント](/ja/alerting/incidents#インシデントの詳細) | **ビジネスインパクト**: 各キーについて、インシデントのトリガー前後に、インシデント対象サービスへのリクエストが最も多く失敗した値。`streams.query` または `sys.telemetry.read` の権限を持つ閲覧者に表示されます。 |
| [根本原因分析](/ja/alerting/incidents) | 失敗した値がある各キーについて、**ビジネスインパクト**の証拠が表示されます。 |

[トレース](/ja/traces)の RED ビューは、ビジネスキーを含む任意のスパンフィールドで分割でき、その **比較**カードは、失敗したリクエストや遅いリクエストを区別するフィールド値を示します。
