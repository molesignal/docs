リアルユーザーモニタリング（RUM）は、Webとモバイルのユーザー体験を記録し、フロントエンドのテレメトリをバックエンドのオブザーバビリティと関連付けます。

## データの流れ

<Steps>
  <Step title="アプリケーションを作成する">
    [アプリケーション](/ja/rum/applications)は、データを送信するWebサイトまたはアプリです。アプリケーションにはクライアントトークンが付属し、そのアプリケーションへのイベントの書き込みにのみ使用できます。
  </Step>
  <Step title="イベントを送信する">
    ブラウザーSDKとFlutter SDKは、JSON形式の[イベント](/ja/rum/events)を単一のエンドポイントに送信します。SDKを使わないクライアントは、 HTTPリクエストで同じイベントを送信します。
  </Step>
  <Step title="データを調べる">
    MoleSignalは各イベントを検証し、位置情報、ブラウザー情報、デバイス情報を追加してRUM ストリームに書き込み、ビューからセッションを生成します。データは[エクスプローラー](/ja/rum/explorer)で検索できます。
  </Step>
</Steps>

| エンドポイント | 用途 |
|---|---|
| `POST /api/v1/rum/events` | ビュー、アクション、エラー、リクエスト、ロングタスク、バイタル指標を[イベント形式](/ja/rum/events)で受け取ります。 |
| `POST /api/v1/rum/replay` | ブラウザーのDOMまたはFlutterの画面のリプレイセグメントを受け取ります。 |

どちらのエンドポイントにも、アプリケーションのクライアントトークンを指定します。RUMのエンドポイントの全一覧は [RUM API](/ja/api/rum)を参照してください。

## データモデル

イベントの種類ごとに、固定スキーマの通常のログストリームがあります。ビューからセッションを生成します。

| ストリーム | 行 |
|---|---|
| `rum_sessions` | セッションごとに1行です。 |
| `rum_views` | ページビューまたは画面ビューごとに1行です。 |
| `rum_actions` | クリック、タップ、カスタムアクションごとに1行です。 |
| `rum_errors` | エラーごとに1行です。対応する[イシュー](/ja/rum/errors)のIDは `error.issue_id` に格納します。 |
| `rum_resources` | リクエストごとに1行です。 |
| `rum_long_tasks` | ロングタスクごとに1行です。 |
| `rum_vitals` | バイタル指標の測定値ごとに1行です。 |

ビューとセッションは、変更があるたびに再送信されます。エクスプローラーの各行と各クエリは、ビューまたはセッションの最新バージョンを参照します。SQLでは、`rum_views_latest` と `rum_sessions_latest` が最新バージョンのみを含むストリームです（[クエリ](/ja/query#rum-の行の最新バージョン)を参照してください）。

## 概要

**RUM**を開くと、まず**概要**が表示されます。一度に1つのアプリケーションを対象とし、単一の環境またはすべての環境について、選択した期間のデータを表示します。概要の先頭に、セッション数、ユーザー数、エラーがなかったセッション数を1文で表示します。 Webバイタルを送信しないアプリでは、代わりにクラッシュがなかったセッション数とユーザー数を表示します。その下には、ブラウザーアプリケーションのCore Web Vitalsを指標ごとに評価スケール（良好、改善が必要、不良）で示し、ビューの75パーセンタイル値をマークします。指標を選択すると、その指標の[パフォーマンス](/ja/rum/performance)が開きます。

続いて、閲覧数が多いページ（アプリでは画面）について、ビュー数、各バイタル指標の75パーセンタイル値、エラーが発生したビューの割合を表示します。セッションの発生元を示す地図とセッション数の多い国のほか、セッションで使用されたブラウザー、OS、デバイスの種類、フラストレーションが最も多く見られた要素と、その要素に対する主なアクションも表示します。テーブルの行やグラフのバーを選択すると、集計対象の行をエクスプローラーで開きます。

概要のヘッダーにある**ダッシュボードで開く**を選択すると、アプリケーションのプラットフォームに対応する[組み込みRUMダッシュボード](/ja/dashboards#組み込み-rum-ダッシュボード)が開きます。アプリケーションと環境には、元のページでの選択が引き継がれます。

[`/api/v1/rum/aggregate`](/ja/api/rum#行の集計)は、条件に一致するすべての行を集計します。集計に時間がかかりすぎたカードにはその旨を表示し、ほかのカードはそのまま表示します。セッションの国はIPジオロケーションデータベースで特定するため、イベントに位置情報を保持しないアプリケーションには地図が表示されません。

## エラー

**エラー**は、アプリケーションのエラーをイシューとして一覧表示します。類似するエラーを1つのイシューにまとめ、ステータス（未解決、調査中、再発、解決済み、無視）、チーム、担当者、発生日時と該当バージョンを記録します。解決済みのイシューが新しいバージョンで再び発生すると、ステータスが再発に変わります。イシューを選択するとドロワーが開き、発生傾向、発生箇所、復元したスタックトレース、最新のセッション、影響を受けたユーザーを確認できます。[RUMのエラーとイシュー](/ja/rum/errors)を参照してください。

## パフォーマンス

**パフォーマンス**では、ブラウザーアプリケーションのページを開いたユーザーが体験したパフォーマンスを確認できます。概要の1文に、LCP、INP、 CLSの75パーセンタイル値を評価に応じた色で表示し、初回コンテンツ描画（FCP）と最初のバイトまでの時間（TTFB）も併記します。チャートは選択中の指標の推移を示し、指標ごとのバーはビューを良好、改善が必要、不良に分類します。テーブルはページ（またはブラウザー、国、バージョン）ごとの測定値を表示します。行を選択するとドロワーが開き、測定値の内訳、測定値を左右した要素、パフォーマンスが最も悪かったビューを確認できます。**リソース**ではページが読み込んだリソースを、 **ロングタスク**ではページの処理をブロックしたタスクを確認できます。ブラウザーのビューを開くと、そのページの読み込み状況を確認できます。[RUMのパフォーマンス](/ja/rum/performance)を参照してください。

## フラストレーション

**フラストレーション**では、アプリケーションの利用中に何がユーザーのフラストレーションにつながったかを確認できます。概要の1文に、兆候（レイジクリック、デッドクリック、エラークリック。アプリではレイジタップとエラータップ）が見られたセッションの割合と、兆候ごとのアクション数とセッション数を表示します。テーブルには、該当するセッション数に基づいて要素、ページ、バージョン、ブラウザーを一覧表示します。行を選択するとパネルが開き、該当セッション数の推移、兆候、バージョンとページ、最新のセッションを確認できます。各セッションを選択すると、兆候が現れる5秒前からリプレイを再生します。[RUMのフラストレーション](/ja/rum/frustration)を参照してください。

## 分析

**分析**では、3つのビューでセッション中のユーザー行動を調べます。**ファネル**では、指定された順序でページを開き、アクションを実行したセッションを集計します。ステップごとの通過率と所要時間を表示し、ブラウザー、OS、デバイスの種類、バージョン、国ごとにも同じ指標を確認できます。**パス**では、あるページの後または前に開いたページをたどり、アクセスの多いページをステップごとに列で表示します。**リテンション**では、日または週ごとに初めて訪れたユーザー数を集計し、以後の各期間に再訪したユーザーの割合を表示します。初期表示は過去7日間です。[RUMの分析](/ja/rum/analytics)を参照してください。**ヒートマップ**では、特定のページでのクリック位置とスクロール到達位置を、ページの記録に重ねて表示します。[RUMのヒートマップ](/ja/rum/heatmaps)を参照してください。

## 機能フラグ

**機能フラグ**は、セッションで評価されたフラグを一覧表示し、フラグの値ごとにセッションのエラー、フラストレーション、バイタル指標を比較します。 `feature_flags.<key>` を使って、どこでもフラグでのフィルタリング、グループ化、集計ができます。[RUMの機能フラグ](/ja/rum/feature-flags)を参照してください。

## アラート

[アラートルール](/ja/alerting)では、アプリケーションのエラー、クラッシュがなかったセッション、フラストレーションの兆候があったセッションの割合、失敗したリクエスト、Core Web Vitalsの各指標の75パーセンタイル値、新規または再発したイシューを監視できます。ルールは各ページと同じ方法で集計するため、監視する値はページに表示する値と一致します。環境、ページ、バージョンで対象を絞り込めます。 [RUMのアラート](/ja/rum/alerts)を参照してください。

概要、エラー、パフォーマンス、フラストレーションの各ページで、絞り込み条件を指定する行の末尾にある**アラート**には、対象アプリケーションで進行中のインシデントの件数が表示されます。選択すると、インシデント、ルール、ワンクリックでルールを作成できるテンプレートが開きます。 [ページからアラートを作成する](/ja/rum/alerts#ページからアラートを作成する)を参照してください。

## Mole Agent で調査

**Mole Agent で調査**を選ぶと、表示中の内容について Mole Agent で新しいチャットが開きます。このボタンは、概要、エラー、パフォーマンス、フラストレーションの各ページのヘッダーや、個別項目の詳細画面に表示されます。

| 表示場所 | 質問に含まれる内容 |
|---|---|
| **概要**のヘッダー | アプリケーション、環境、時間範囲です。 |
| **エラー**のヘッダー | 同じ範囲で発生したアプリケーションのエラーです。 |
| **パフォーマンス**のヘッダー | Web Vitals ビューでは表示中の Core Web Vital、**リソース**と**ロングタスク**ではページの速度です。 |
| パフォーマンステーブルの行 | ページ、ブラウザー、国、バージョンのいずれかがその行の値に一致するビューです。ビュー数が十分な場合は、表示中の指標の 75 パーセンタイルも含まれます。ボタンは行にポインターを重ねると表示され、タッチスクリーンでは常に表示されます。 |
| **フラストレーション**のヘッダー | アプリケーションのユーザーがフラストレーションを感じる要因です。 |
| イシューのドロワー（**調査**） | イシュー、その ID、エラーです。 |
| フラストレーショングループのパネル（**この要素を調査**、**調査**） | 要素とそのセレクター、またはグループのページ、バージョン、ブラウザー、システムです。 |
| セッションのヘッダー（**このセッションを調査**） | 開始から終了までのセッションです。 |
| RUM 指標に対するルールのインシデント（**Mole Agent で調査**） | アラート、アプリケーション、インシデントの発生時刻、検出のもとになったセッションです。チャットはインシデントに紐付いたままなので、回答を根本原因分析（RCA）としてインシデントに書き戻せます。 |

チャットにはアプリケーションが紐付きます。質問はメッセージ入力欄に表示され、確認や編集をしてから送信できます。送信ボタンをクリックするまでは何も送信しません。ボタンは `agent.use` 権限がある場合に表示されます。チャットの開始には、`rum.events.read` または `_sys` スコープの `sys.telemetry.read` が必要です。開始すると、アプリケーションの[調査](/ja/agent#調査)を記録します。

どの質問にも `@` でアプリケーションを紐付けられます。名前を入力し、**RUM アプリケーション**から選択してください。 RUM の読み取り権限がない場合はメッセージを送信できません。質問で指定した時間範囲（指定がなければ過去 24 時間）について、モデルに以下の情報を渡します。

- セッション数とユーザー数、エラーが発生しなかったセッションとクラッシュが発生しなかったセッションの割合、フラストレーションが見られたセッション。
- ブラウザーアプリケーションの場合は、Core Web Vitals の 75 パーセンタイルとその評価、および閲覧数が最も多いページ。
- 影響を受けたセッション数が多い順に最大 3 件の未解決イシューと、それぞれの初回検出時および再発時のバージョン。
- `alerts.rules.read` 権限がある場合は、アプリケーションで発報中のアラート。

Mole Agent は `get_rum_overview`、`list_rum_issues`、`get_rum_issue`、`get_rum_vitals`、`get_rum_frustration`、 `get_rum_view_waterfall`、`aggregate_rum`、`get_rum_funnel`、`get_rum_paths`、`get_rum_retention`、`get_rum_heatmap`、`get_rum_feature_flags`、`get_rum_session_notes` に加え、セッション、アクション、エラー、関連トレース用のツールで RUM データを読み取ります。各ツールはページと同じデータを読み取り、閲覧者に適用されるフィールドマスキングを維持します。組み込みスキル `/rum-triage` は、概要、イシュー、表示が遅いビューや動作が止まったビュー、フロー内の遷移経路、セッション、セッション内のリクエストのトレースの順に調べます。調査結果には、根拠となるページへのリンクを添えます。

## エクスプローラー

メインナビゲーションから **RUM** を開きます。**エクスプローラー**には、実ユーザーのセッション、ビュー、アクション、エラー、リソース、ロングタスクが一覧表示されます。フィールドクエリで絞り込み、ヒストグラムで件数の推移を確認し、行を選んでドロワーで詳細を開きます。アプリケーションがまだないワークスペースには、作成手順が表示されます。[RUM エクスプローラー](/ja/rum/explorer)を参照してください。

**アプリケーション**では、アプリケーションの一覧やクライアントトークンを確認し、各イベントに保存する情報を設定できます。詳しくは、 [RUM アプリケーション](/ja/rum/applications)を参照してください。

## セッションとリプレイ

エクスプローラーからセッションを開くと、リプレイ、ユーザーコンテキスト、イシュー、イベントタイムライン、関連するバックエンドトレースを確認できます。DOM リプレイを記録したセッションには `session.has_replay` フィールドがあるため、 `session.has_replay = true` で該当するセッションだけを表示できます。

セッションのヘッダーにある**この再生位置へのリンクをコピー**を選ぶと、現在の位置からリプレイを開くリンクをコピーできます。 [プレイリスト](/ja/rum/playlists)に確認したいセッションをまとめると、順番に再生できます。リプレイでは [コメントとチャプター付きの AI 要約](/ja/rum/session-replay#コメント)を利用できます。セッションには、ページが[ログに出力した内容](/ja/rum/logs)が一覧表示されます。

シンセティックチェックや CI テストで生成したセッションにはその旨を示すマークが付き、実ユーザーの指標には含まれません。[テストトラフィック](/ja/rum/test-traffic)を参照してください。

リプレイは機密性の高いユーザーデータとして扱ってください。SDK で収集を制御し、シークレットや個人情報を含むフィールドは記録せず、実用上可能な最短の保持期間を設定してください。

## エラー、ソースマップ、シンボル

エラーは構造化されたスタックフレームとともに届きます。エラーの種類とメッセージ、およびアプリケーション自身のコードに由来する先頭のスタックフレームに基づいて、エラーを[イシュー](/ja/rum/errors)にグループ化します。ブラウザーのソースマップやモバイルアプリのシンボルは、 **RUM → RUM 設定 → ソースマップとシンボル**からアップロードします。MoleSignal はアップロードされたデバッグアーティファクトを使い、ミニファイや難読化を施したコードのフレームや、ネイティブコードのフレームを復元します。アーティファクトのメタデータを読み取るには `debug_artifacts.read` が必要です。アップロードと削除には `debug_artifacts.manage` が必要です。

## 関連するバックエンドトレース

リクエストに W3C の `traceparent` が含まれている場合、そのリクエストの `resource.trace_id` からバックエンドのスパンに直接移動できます。セッションには、各リクエストに紐付くトレースが一覧表示されます。どのリクエストにもトレース ID がない場合は、セッションの詳細画面でセッションの時間範囲内にある関連トレースを検索します。

応答が遅いフロントエンドのリクエストからは、対応するサービスのトレース、ログ、メトリクスに直接移動できます。移動しても調査コンテキストは維持されます。

逆方向にも移動できます。セッション内のリクエストがトレース ID を送信していた場合は、**トレース**のトレース詳細画面のヘッダーに **ユーザーセッション**が表示されます。選択すると該当するセッションが開きます。

## プロキシ経由のクライアント IP

RUM イベントは、公開インターネット上のブラウザーやデバイスから届きます。デフォルトでは、MoleSignal は直接接続している相手の IP アドレスを記録します。MoleSignal の前段にリバースプロキシや CDN があると、すべてのイベントにプロキシの IP アドレスが記録され、地理情報が不正確になります。**設定 → クライアントIPの識別**を開き、単一の値を持つヘッダーまたは転送元の IP アドレスのチェーンを選択し、信頼するプロキシの CIDR を指定してください。MoleSignal は、指定したネットワークからの接続でのみヘッダーを信頼します。この設定は再起動なしでデプロイ全体に適用されます。

## 権限

- `rum.write` は RUM イベントを送信する権限です。アプリケーションに紐づくクライアントトークンは、そのアプリケーションに対してこの権限のみを付与します。
- `rum.events.read` で、概要、エクスプローラー、パフォーマンス、フラストレーションの各ページを開けます。
- `rum.issues.read` でエラー、`rum.analytics.read` で分析、`rum.applications.read` でアプリケーション一覧、`rum.playlists.read` でプレイリストを開けます。
- `rum.sessions.read` でセッションページを開けます。`rum.replay.read` でセッションのリプレイを再生し、そのコメントと要約を閲覧できます。
- `rum.replay.comments.write` でリプレイにコメントを投稿し、投稿したコメントを編集できます。`rum.replay.comments.manage` ですべてのコメントを編集でき、`rum.replay.summaries.generate` で AI に要約をリクエストできます。
- `rum.issues.manage` でイシューのステータス、チーム、担当者を設定できます。オーナー、管理者、編集者がこの権限を持ちます。
- `agent.use` があると、これらのページに **Mole Agent で調査** が表示され、`@` でアプリケーションを添付できます。
- `alerts.rules.read` があると、概要、エラー、パフォーマンス、フラストレーションの各ページに **アラート** が表示されます。`alerts.rules.manage` があると、これらのページからルールを作成できます。[RUM アラート](/ja/rum/alerts#権限)を参照してください。
- `rum.applications.manage` でアプリケーションを作成、変更、削除し、クライアントトークンを表示できます。
- `debug_artifacts.read` でデバッグアーティファクトのメタデータを一覧表示できます。
- `debug_artifacts.manage` でソースマップとモバイルシンボルをアップロードまたは削除できます。
