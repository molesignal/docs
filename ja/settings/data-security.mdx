**設定**の**データセキュリティ**グループには、**暗号化キー**、**正規表現パターン**、 **フィールドマスキング**、**ドメイン管理**、**監査**があります。最初の4項目を閲覧するには `org.field_masking.read`、変更するには `org.field_masking.manage` が必要です。**監査**を閲覧するには `audit.read` が必要です。監査レコードの保持期間は[プラットフォーム設定](/ja/settings/platform#監査ログの保持)で指定します。

## 暗号化キー

**暗号化キー**には、ワークスペースのデータキーと、各キーのアルゴリズム、バージョン、最終ローテーション日時が表示されます。ストリームが[暗号化フィールド](/ja/streams#暗号化フィールド)に初めて書き込むと、 MoleSignal がキーを自動作成し、`__field_default__` として表示します。すべてのキーを暗号化ルートキーでラップします。暗号化ルートキーは `MS_CIPHER_KEY` です。キー素材がサーバーの外に出ることはありません。

| 操作 | 手順 |
|---|---|
| **新しいキー** | **名前**と、base64 でエンコードした32バイトのキー素材（`keyMaterialB64`）を入力します。 |
| **ローテーション** | 新しい32バイトのキー素材を base64 形式で貼り付けます。ローテーションでバージョンが追加されます。新しいデータには新しいバージョンを使用し、以前のバージョンで暗号化したデータは引き続きそのバージョンで復号できます。 |
| 削除 | キーで暗号化したデータは読み取れなくなります。 |

<Warning>
  `MS_CIPHER_KEY` を失うと、すべての暗号化フィールドを復元できなくなります。 [フィールドレベルの暗号化](/ja/security#フィールドレベルの暗号化)を参照してください。
</Warning>

## 正規表現パターン

正規表現パターンは、カード番号やトークンなどの機密テキストを検出して置き換えます。

1. **新しいパターン**を選択します。
2. **名前**、**パターン**、**説明**を入力します。サーバーは保存時にパターンを検証します。
3. **置換文字列**を入力します。`$1` などでキャプチャグループを参照できます。置換文字列を空にすると、一致したテキストを削除します。
4. **取り込み時にマスキング**で適用タイミングを指定し、**作成**を選択します。

| **取り込み時にマスキング** | 効果 |
|---|---|
| オン | 取り込むすべてのイベントの文字列値を、パイプライン処理後、保存前にマスキングします。元のテキストは復元できません。 |
| オフ | 保存データには元のテキストが残ります。SQL クエリで `mask(<column>)` を呼び出すと、パターンを適用した列が返ります。 |

`mask()` は、ワークスペースのすべてのパターンを適用します。一覧の**マスキング**列には、各パターンについて**取り込み時**または**クエリ時のみ**と表示されます。

## フィールドマスキング

フィールドマスキングは、クエリ結果に表示するフィールド値の一部を隠します。クエリの計算には引き続き元の値を使用します。メトリクスストリームには適用しません。

1. **新規ルール**を選択し、**ルール名**を入力します。
2. **フィールドの一致条件**には、完全一致するフィールド名か、`user.*` のようにワイルドカード `*` や `?` を含む名前を指定します。正規表現は使用できません。
3. 必要に応じて、`customer-*` などの**ストリームの一致条件**と**ストリームタイプ**を指定して対象を絞り込みます。
4. **アルゴリズム**を選択し、**ルールを有効化**をオンにしたまま保存します。

| アルゴリズム | 効果 |
|---|---|
| **全体マスク** | 値全体を**置換文字列**で置き換えます。 |
| **範囲マスク** | **開始文字の位置**から**終了文字の位置（その文字は含まない）**までの文字をマスクします。 |
| **内側マスク** | **先頭に残す文字数**と**末尾に残す文字数**で指定した文字を残し、その間をマスクします。 |
| **外側マスク** | **開始文字の位置**から**終了文字の位置（その文字は含まない）**までの文字だけを残し、その両側をマスクします。 |
| **HMAC-SHA-256 ハッシュ** | サーバーが管理するワークスペースのキーでダイジェストを生成し、値を置き換えます。同じ値からは同じダイジェストが生成されるため、引き続き結果をグループ化したり結合したりできます。 |

フィールドに一致する有効なルールのうち、一覧で最初のルールが適用されます。行をドラッグして順序を変更します。 [ストリーム](/ja/streams#スキーマとフィールド)のフィールド設定では、継承したルールの上書きや、フィールド単位でのマスキングの無効化が可能です。

## ドメイン管理

**ドメイン管理**では、ワークスペースを独自のホスト名で公開できます。使用する証明書は MoleSignal が取得し、更新します。

1. `account_email` を指定して `[http.tls]` を有効にします。[HTTP TLS と ACME](/ja/configuration#http-tls-と-acme) を参照してください。
2. ホスト名の DNS レコードを MoleSignal に向け、ACME サービスが暗号化されていない HTTP ポートで `/.well-known/acme-challenge/` にアクセスできるようにします。
3. **ドメインを追加**を選択し、**ホスト名**を入力して、**ドメインを追加**を選択します。

一覧には、各ホスト名の**状態**、証明書の有効期限、**直近のエラー**が表示されます。新しいホスト名の状態は、証明書の発行までは `pending` で、発行後は `active` に変わります。証明書は有効期限までの残り期間が30日以内になると自動更新されます。ホスト名を削除すると、そのホスト名での公開を停止します。

## 監査

**監査**では、ワークスペースの監査証跡を検索できます。監査証跡には、セキュリティに関わるアクションやリソースと設定の変更について、実行者、アクション、対象、ステータス、時刻が記録されます。

| フィルター | 用途 |
|---|---|
| **開始** / **終了** | 時間範囲を指定します。絶対時刻または `now-24h` などの相対時刻を使用できます。 |
| **実行者の種類** / **実行者** | 実行者の種類または特定のユーザーを指定します。 |
| **アクション** | `audit_retention.update` などのアクションキーを指定します。 |
| **対象の種類** / **対象 ID** | 変更されたリソースの種類と ID を指定します。 |

検索するには **適用**、フィルターをクリアするには **リセット**を選択します。行を選択すると、イベントの詳細と **IDをコピー**が表示されます。Mole Agent のチャットイベントには、そのチャットの履歴が表示されます。ページ上部にはレコードの保持期間が表示されます。**保持期間を変更**を選択すると、`_sys` のプラットフォーム設定が開きます。

監査レコードには、認証情報、モデルキー、機密性の高い Webhook ヘッダー、署名に使用する機密情報は記録されません。[監査](/ja/security#監査)を参照してください。

### 監査ストリーム

各監査イベントは、ワークスペースの `_audit` ログストリームにも行として書き込まれます。このため、 **ログ**で検索したり、SIEM などの外部宛先に [スケジュール済みパイプライン](/ja/pipelines#プラットフォームストリーム)で転送したりできます。各行からは、このページのレコードと同じ方法で機密情報を除去します。行の時刻には、イベントの発生時刻を使用します。

| フィールド | 内容 |
|---|---|
| `audit_id` | イベントの ID。**IDをコピー**で取得する値と同じです。 |
| `actor_kind`, `actor_id` | アクションの実行者。 |
| `action` | アクションキー。 |
| `target_kind`, `target_id` | 変更されたリソース（イベントに対象がある場合）。 |
| `ip`, `user_agent` | リクエストの送信元（イベントに記録されている場合）。 |
| `payload` | イベントの詳細（詳細がある場合）。 |

このページと[監査 API](/ja/api/admin/audit)は、正式な監査レコードを読み取ります。各ノードはバックグラウンドで行をバッチ単位で書き込み、書き込み待ちのイベントを最大 4,096 件保持します。キューがいっぱいになると、行はストリームに書き込まれませんが、監査レコードは残ります。他のストリームと同様に、各行にはストリームの保持期間が適用されます。

このページと同様に、`_audit` の読み取りには `audit.read` が必要です。

- この権限がない場合、ストリームは一覧に表示されず、開くことも変更や削除もできません。クエリを実行すると `403` が返ります。この制限は、製品内のクエリ、NDJSON ストリーミングを使用するクエリ API、 Flight SQL、フェデレーション検索に適用されます。フェデレーション検索では、リモートクラスターが呼び出し元のトークンに `audit.read` があるか確認します。
- `_audit` に対するクエリは常にリクエスト内で実行されます。 `Prefer: respond-async` を指定しても検索ジョブにはなりません。検索ジョブとして送信すると `400` が返ります。
- ユーザーの操作なしでバックグラウンド実行される処理は、保存したユーザーにかかわらず `_audit` を読み取れません。ストリームの指定やステートメント内の参照を通じて `_audit` を読み取るアラートルールと、`_audit` を対象とするスケジュール済みログ検査は保存できません。所有者が保存を試みても `400` が返ります。レポートからも読み取れません。
- Mole Agent のツールと[インバウンド MCP](/ja/inbound-mcp)は、どの認証情報を使用しても `_audit` を読み取れません。行もフィールドも読み取れません。

[スケジュール済みパイプライン](/ja/pipelines#プラットフォームストリーム)は、最後に保存したユーザーの権限で `_audit` を読み取ります。一時停止と再開は保存として扱いません。パイプラインページの上部とエディター内のソースには、そのユーザーが **\_audit の読み取りに使用するユーザー**として表示されます。`audit.read` を持ち、保存できる別のユーザーには、エディターに **保存すると、あなたの権限で読み取ります。** と表示されます。

- 変更を保存するには `audit.read` が必要です。サービスアカウントのトークンを使用すると `403` が返ります。パイプラインの実行時に、その権限を再確認できないためです。個人トークンを使用する場合は、発行先のユーザーとして扱います。
- 読み取りのたびに、パイプラインは対象ユーザーが引き続きサインインでき、組織に所属し、 `audit.read` を持っていることを確認します。いずれかの条件を満たさないと読み取りに失敗し、対象ユーザーと理由が表示されます。例： `` `_audit` is read with the access of admin@example.com, who no longer holds audit.read ``。パイプラインは有効なままで読み取り位置も維持されるため、イベントはスキップされません。
- 対象ユーザーが `audit.read` を再取得するか、その権限を持つ別のユーザーがパイプラインを保存すると、同じ位置から処理を再開します。設定を変更せずに保存するだけでも再開できます。`audit.read` がないユーザーやサービスアカウントのトークンで設定を変更せずに保存しても、何も変わらず、エラーも表示されません。
- 一時停止と再開に必要なのは `pipelines.pause` のみです。読み取りに使用するユーザーの権限は変わりません。他のパイプラインと同様に、再開すると[最初から処理します](/ja/pipelines#スケジュールと読み取り位置)。読み取り位置を維持するには、パイプラインを有効にしたままにしてください。
- バックフィルは、ジョブを送信したユーザーの権限で読み取ります。送信時には `audit.read` が必要です。ジョブの実行時にも、この権限を再確認します。

パイプラインがコピーした行は、転送先の通常の行として扱います。転送先を読み取れるユーザーは、コピーされた行も読み取れます。
