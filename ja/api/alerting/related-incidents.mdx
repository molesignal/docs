どちらの呼び出しにも、対象のインシデントに対する `alerts.incidents.read` 権限が必要です。

## 類似インシデント

```http
GET /api/v1/alerts/incidents/{id}/similar
```

対象のインシデントがトリガーされる前の90日間に、同じ組織でオープンされたインシデントから、最も類似するものを最大5件、スコアの高い順に取得します。同点の場合は新しい順に並べます。対象にマージされたインシデントと、対象のマージ先は除外します。スコアは以下の各行の点数の合計です。スコアが2以上のインシデントだけを一覧に含めます。

| 判定基準 | `reasons` の値 | スコア |
|---|---|---|
| アラートのフィンガープリントが同じ | `fingerprint` | 5 |
| ルールが同じ（フィンガープリントが異なる場合） | `rule` | 3 |
| 共通するサービスがある | `services` | 重複率 × 2 |
| ラベルが類似している：共通するキーと値のペアが、両方のインシデントでそれぞれ全ペアの0.3以上を占める | `labels` | 共通ペアの割合 × 2 |
| タイトルが類似している：トライグラム類似度が0.3以上。中国語も含め、PostgreSQL の `pg_trgm` と同じ方法で算出 | `title` | 類似度 × 2 |
| 同じチームにルーティングされた | `team` | 1 |

重複率は、両方の集合の積集合の要素数を和集合の要素数で割った値です。

<RequestExample>
```bash cURL
curl http://localhost:5080/api/v1/alerts/incidents/$INCIDENT_ID/similar \
  -H "authorization: Bearer $MS_TOKEN"
```
</RequestExample>

<ResponseExample>
```json 200
{
  "incidents": [
    {
      "id": "3KEDNEyqouYJeBDTLTMTBui7XHW",
      "summary": "High error rate · checkout",
      "severity": "critical",
      "status": "resolved",
      "createdAt": 1789400000000000,
      "resolvedAt": 1789401800000000,
      "resolvedBy": "<user-id>",
      "score": 7.6,
      "reasons": ["fingerprint", "services", "labels", "team"],
      "notes": 2,
      "rootCause": "Connection pool exhausted after the payments client stopped releasing connections."
    }
  ]
}
```
</ResponseExample>

| フィールド | 説明 |
|---|---|
| `score`, `reasons` | スコアとその算出根拠です。上の表を参照してください。 |
| `resolvedBy` | インシデントを解決したユーザーです。ルールが自動で復旧した場合や、インシデントがまだアクティブな場合は `null` です。 |
| `notes` | インシデントに追加された[ノート](/ja/api/alerting/add-incident-note)の数です。 |
| `rootCause` | [AI による根本原因分析](/ja/api/alerting/incident-rca)の最初の本文の文です。見出しと空行はスキップし、最大200文字を返します。分析がない場合は省略します。 |

## 最近の変更

```http
GET /api/v1/alerts/incidents/{id}/changes
```

インシデントがトリガーされる30分前から10分後までに[報告された変更](/ja/apm/deployments#ci-からデプロイを報告する)を一覧表示します。対象は、インシデントのサービス（影響を受けたサービスと `service` ラベルで指定されたサービス）と、そのダウンストリームサービスです。変更は古い順に最大20件表示します。ダウンストリームサービスは、インシデントの先頭3件までのサービスについて、APM サービスマップから取得します。サービスマップがない場合は、インシデント自体のサービスだけを対象とします。トリガー前の24時間以内にインシデントのルールを編集した場合は、`rule` の変更も一覧に含めます。

<RequestExample>
```bash cURL
curl http://localhost:5080/api/v1/alerts/incidents/$INCIDENT_ID/changes \
  -H "authorization: Bearer $MS_TOKEN"
```
</RequestExample>

<ResponseExample>
```json 200
{
  "from": 1789998200000000,
  "to": 1790000600000000,
  "changes": [
    {
      "kind": "deployment",
      "at": 1789999100000000,
      "service": "payments",
      "downstream": true,
      "version": "v2026.10.28",
      "status": "succeeded",
      "commit": "9f2c1e4",
      "author": "dana",
      "link": "https://ci.example.com/pipelines/4821"
    },
    {
      "kind": "rule",
      "at": 1789960000000000,
      "downstream": false,
      "ruleId": "3KEDBLvTYO6DnWi8H9S9MNLpPT7",
      "ruleName": "Checkout error rate"
    }
  ]
}
```
</ResponseExample>

| フィールド | 説明 |
|---|---|
| `from`, `to` | 対象期間の開始時刻と終了時刻です。Unix 時刻をマイクロ秒単位で表します。 |
| `kind` | `deployment`、`configuration`、`feature_flag`、`rule`（インシデントのルールを編集した場合）のいずれかです。 |
| `downstream` | インシデント自体のサービスではなく、ダウンストリームサービスの変更の場合は `true` です。 |
| `version`, `status`, `commit`, `description`, `author` | レポートに含まれていた値です。レポートにないフィールドは省略します。 |
| `link` | 報告されたパイプラインのアドレスです。報告されていない場合は、プルリクエストのアドレスです。 |
| `ruleId`, `ruleName` | `rule` の変更対象となったルールの ID と名前です。 |

**エラー**

| ステータス | 理由 |
|---|---|
| `403` | トークンに `alerts.incidents.read` 権限がないか、対象のインシデントにアクセスできません。 |
| `404` | インシデントが存在しません。 |
