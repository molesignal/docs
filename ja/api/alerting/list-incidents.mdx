```http
GET /api/v1/alerts/incidents
GET /api/v1/alerts/incidents/{id}
```

最初の呼び出しは、インシデントを新しい順に一覧表示します。他のインシデントに[マージされた](/ja/api/alerting/merge-incidents)インシデントは一覧に含めず、マージ先の[タイムライン](/ja/api/alerting/incident-timeline)に表示します。2 番目の呼び出しは、マージの有無にかかわらず、インシデントを 1 件返します。どちらの呼び出しにも `alerts.incidents.read` が必要です。

**一覧取得のクエリパラメーター**

| パラメーター | 型 | 説明 |
|---|---|---|
| `scope` | string | `active`（デフォルト）は、ステータスが `open` または `acknowledged` のインシデントを返します。`all` は、指定期間内に作成されたインシデントと、作成時期を問わずすべてのアクティブなインシデントを返します。 |
| `windowSecs` | integer | `scope=all` でさかのぼる期間です。デフォルトは `604800`（7 日間）です。値が 3600 未満の場合は 3600、31536000 を超える場合は 31536000 に補正します。 |

一覧の各項目には概要だけが含まれます。`triggeringQuery` は `null` です。`traceIds`、`hostIds`、`affectedServices` にはそれぞれ最大 1 件の値が入ります。完全なレコードを確認するには、インシデントを個別に取得してください。

<RequestExample>
```bash cURL
curl "http://localhost:5080/api/v1/alerts/incidents?scope=all&windowSecs=86400" \
  -H "authorization: Bearer $MS_TOKEN"
```
</RequestExample>

## インシデントのフィールド

| フィールド | 説明 |
|---|---|
| `id`, `orgId`, `ruleId` | インシデント、組織、ルールの識別子です。 |
| `escalationPolicyId` | インシデントが開いた時点で、発生元が指定したポリシーを設定します。発生元がデフォルトポリシーを使用する場合は、[アラートルーティング](/ja/alerting/routing)で選択したポリシーを設定します。エスカレーションが始まると、エイリアス `default` を `default` という名前のポリシーの ID に置き換えます。 |
| `status` | `open`、`acknowledged`、`resolved` のいずれかです。モデルには `closed` もありますが、どの呼び出しもこの値を設定しません。 |
| `severity` | `info`、`warning`、`error`、`critical` のいずれかです。 |
| `summary` | ルール名に続けて、影響を受けるサービスを最大 2 件表示します。さらにサービスがある場合は、残りの件数を `+N` で表示します。 |
| `fingerprint` | ルールの `id` と `labels` のハッシュです。1 つのルールにつき、同じフィンガープリントを持つアクティブなインシデントは 1 件までです。 |
| `currentStep`, `currentLoop`, `currentStepStartedAt` | エスカレーションの進行状況です。ステップ番号は 0 から始まり、時刻はマイクロ秒単位です。 |
| `assignees` | インシデントの担当者です。現在のエスカレーションステップで直接指定されたユーザー（`user` ターゲットと各 `schedule` ターゲットのオンコール担当者）に加え、インシデントを確認したユーザーも含みます。最初のステップを実行するまでは空です。チームのみを対象とするステップでは、それまでの担当者を維持します。 |
| `labels`, `annotations` | インシデントが開いた時点のスナップショットです。ルールの `labels` と、クエリ結果の `service` および `host` が含まれます。その後にルールを編集しても、スナップショットは変わりません。 |
| `traceIds`, `hostIds`, `affectedServices` | クエリ結果の `trace_id`、`host`、`service` 列から重複を除いた値です。それぞれ最大 10 件です。 |
| `triggeringQuery` | `language`、`statement`、`sampleValues` が含まれます。各サンプルには、マイクロ秒単位の `ts`（結果に時刻列がない場合は `0`）、`value`、`labels` が含まれます。このフィールドは個別取得の呼び出しでのみ返します。 |
| `createdAt` | インシデントが開いた時刻です。単位はマイクロ秒です。 |
| `acknowledgedAt`, `acknowledgedBy` | 最後にインシデントを確認した時刻とユーザーです。 |
| `resolvedAt`, `resolvedBy` | インシデントを解決した時刻とユーザーです。ルールの条件に一致しなくなり、評価処理でインシデントを解決した場合、`resolvedBy` は `null` です。 |
| `teamId` | インシデントが開いた時点で[アラートルーティング](/ja/alerting/routing)が割り当てたチームです。割り当てがない場合は `null` です。 |
| `routing` | チームの割り当て理由です。ルーティングの導入前に開いたインシデントでは `null` です。`reason` は `rule`（ルーティングルールに一致。その時点の `ruleId` と `ruleName` を含む）、`service_owner`（サービスの所有チーム。`service` を含む）、`team_label`（チームラベル）、`default`（デフォルトポリシー）、`source`（発生元がエスカレーションポリシーを選択したため、ルーティングではチームのみを割り当て）のいずれかです。 |
| `snoozedUntil`, `snoozedBy` | インシデントを[スヌーズ](/ja/api/alerting/snooze-incident)している間は、スヌーズの終了時刻（マイクロ秒単位）とスヌーズを設定したユーザーを示します。それ以外は `null` です。 |
| `severitySetBy` | [重大度を手動で設定した](/ja/api/alerting/set-incident-severity)ユーザーです。手動設定後は、ルールで重大度を変更しません。手動で設定していない場合は `null` です。 |
| `mergedInto` | このインシデントの[マージ先](/ja/api/alerting/merge-incidents)のインシデントです。マージしていない場合は `null` です。 |
| `assigneesPinned` | 手動で指定した担当者を使用している間は `true` です。エスカレーションでは、次のステップに進んだ時点でのみ担当者を置き換えます。 |
| `dispatchRound`, `dispatchReason` | `dispatchRound` はエスカレーション通知のラウンド番号です。手動でエスカレーションした場合、チームやポリシーへの割り当てを変更した場合、または重大度を引き上げた場合に増え、同じステップで再度通知できます。`dispatchReason` は、現在のステップで最後に通知を送信した理由です。`step`、`manual`、`reassigned`、`responder_added`、`snooze_ended`、`ack_timeout`、`severity_raised` のいずれかです。 |
| `revision` | インシデントを変更するたびに増えます。 |

**エラー**

| ステータス | 原因 |
|---|---|
| `403` | トークンに `alerts.incidents.read` 権限がありません。 |
| `404` | インシデントが存在しません。 |
