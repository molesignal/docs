どちらのルートでも、`sys.signing_keys.rotate` 権限を持つシステムスコープのセッションが必要です。組織スコープのセッションまたは API トークンを使用すると、`403` が返ります。[ワークスペースを選択](/ja/api/auth/select-organization)で、セッションの組織を `_sys` に切り替えてください。

## 署名キーの一覧を取得

```http
GET /api/v1/auth/jwt/secrets
```

署名キーのメタデータを返します。キーの生バイト列は一切返しません。

<ResponseExample>
```json 200
[
  {
    "id": "3JtcPZ3AZJFyvBvSkJUia0N7wqo",
    "isPrimary": true,
    "createdAt": 1790000000000000,
    "retiredAt": null
  }
]
```
</ResponseExample>

## 署名キーをローテーション

```http
POST /api/v1/auth/jwt/rotate
```

新しいプライマリキーを作成し、それまでのプライマリキーを廃止します。新しいトークンには新しいキーで署名します。廃止済みのキーで署名したトークンは、そのキーの廃止後も 24 時間は有効です。

ノードの再起動は不要です。各ノードは、最初のリクエストから新しいキーで署名したセッションを受け入れ、約 10 秒以内に新しいキーでの署名を開始します。この遅延とノード間の時刻のずれを考慮し、廃止済みのキーによる署名の検証は、廃止から 24 時間と 5 分が経過した時点で終了します。

<ResponseExample>
```json 200
{
  "newKid": "<new-key-id>",
  "retiredKid": "<previous-key-id>",
  "activeCount": 2
}
```
</ResponseExample>

`activeCount` は、現在トークンの検証に使用できるキーの数です。`MS_AUTH_JWT_SECRET_OVERRIDE` で署名キーを固定するデプロイ環境では、独自のローテーションポリシーに従います。[セキュリティとマルチテナンシー](/ja/security#jwt-署名キー)を参照してください。
