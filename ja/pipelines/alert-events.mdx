**アラートパイプライン**は、インシデントを作成する前にアラートイベントを処理します。各ステップでは、インシデントのタイトルを書き換えたり、重大度を変更したり、ラベルやアノテーションを追加または削除したり、影響を受けるサービスを指定したりできます。イベントを破棄して、インシデントを作成しないようにすることもできます。[ルーティング](/ja/alerting/routing)と通知には、パイプラインの処理結果を反映したインシデントを使用します。

アラートイベントは、次の4つのソースのいずれかから発生します。

| ソース | イベント |
|---|---|
| **アラートルール** | [アラートルール](/ja/alerting/rules)が発火します。 |
| **外部ソース** | [アラートソース](/ja/alerting/sources)が別のシステムからアラートを受信します。 |
| **シンセティックチェック** | [シンセティックチェック](/ja/synthetics#アラートインシデント)が失敗するか、結果がありません。 |
| **データなし** | ルールが[データなしインシデント](/ja/alerting/rules#復旧と欠損データ)を作成します。 |

手動で作成するインシデントは、作成前にアラートパイプラインを通りません。

パイプラインは[通知の送信前](#通知の送信前)にも実行できます。この場合はイベントのコピーを処理し、1つの通知ポリシーが送信する内容だけを変更します。

## アラートパイプラインを作成する

**パイプライン**を開き、**新規パイプライン**を選択して、**実行モード**を**アラートイベント**に設定します。**シグナルタイプ**には**アラートイベント**が表示され、設定ではスケジュールの代わりに[**実行順序**](#実行順序)を指定します。フローには3つのノードがあります。

| ノード | 説明 |
|---|---|
| **アラートイベント** | パイプラインが処理するアラートイベントです。[条件](#条件)を参照してください。 |
| **処理中** | ステップが実行順に並びます。[ステップ](#ステップ)を参照してください。 |
| **インシデントへの反映** | ステップで処理したイベントの内容を反映して、インシデントを作成します。 |

**テスト**では、保存する前にサンプルのアラートイベントに対してステップを実行します。各ステップは、インシデントの作成直前にあるアラートルールのイベントとして扱います。`%source` は `rule`、`%event` は `opened` です。別の値を試すには、**サンプルイベント**を編集して **テストを実行**を選択します。結果には、各ステップの実行後のイベント、またはイベントを破棄したステップが表示されます。テストではデータを保存せず、外部への呼び出しも行いません。**AIによる要約**と**クエリ結果を追加**のステップは、それぞれのアノテーションに `…` を書き込みます。**APIを呼び出す**ステップはイベントを変更せずに渡し、**テストでは呼び出されません**と表示します。

**最近のアラートイベントを使用**では、`alerts.incidents.read` 権限があれば、過去7日間のインシデントを新しい順に最大20件確認できます。インシデントを選択すると、そのイベントが**サンプルイベント**に入力され、各ステップがそのルールとソースを読み取ります。保存済みのインシデントを使うため、作成時にパイプラインが行った処理はすでに反映されています。

設定の**アラートイベントを処理**スイッチで、パイプラインのオンとオフを切り替えます。オフにすると、すべてのアラートイベントがこのパイプラインを処理されずに通過します。保存するには、**パイプラインを作成**を選択します。保存した変更は10秒以内にすべてのノードに反映されます。

## 条件

**アラートイベント**ノードを選択して、パイプラインで処理するイベントを指定します。

- **ソース**: **アラートルール**、**外部ソース**、**シンセティックチェック**、**データなし**から選択します。ルールのデータなしインシデントは**アラートルール**ではなく**データなし**に分類します。結果がないシンセティックチェックのインシデントは**シンセティックチェック**に分類します。
- **重大度**: **重大**、**エラー**、**警告**、**情報**から選択します。
- **ラベル**: **ラベル条件を追加**でラベルと値を指定します。イベントには、指定したすべてのラベルがあり、それぞれの値が完全に一致している必要があります。
- **時刻**: **時間指定なし**、**指定した時間帯内のみ**、**指定した時間帯外のみ**から選択します。時間帯は1つのタイムゾーンで曜日ごとに指定し、インシデントの作成時刻を基準に判定します。たとえば、夜間のETLジョブが実行される2時間だけ、特定の種類のアラートを破棄できます。

条件の上にある**いつ**では、パイプラインを実行するタイミングを指定します。デフォルトは**インシデントの作成前**です。[**通知の送信前**](#通知の送信前)も選択できます。

ソースや重大度を1つも選択しない場合は、その項目のすべての値が対象になります。条件を設定しないパイプラインは、すべてのアラートイベントを処理します。条件に一致しないイベントは、変更されずにパイプラインを通過します。

## 実行順序

アラートパイプラインは、**実行順序**の値が小さいものから順に実行します。値が同じ場合は、パイプライン名の順に実行します。各パイプラインは、それまでの処理結果を反映したイベントを受け取り、条件を判定します。このため、先に実行するパイプラインが重大度を引き上げることで、後続のパイプラインの条件に一致する場合があります。

## ステップ

**ステップを追加**では、**拡張テーブルを参照**を含む他のパイプラインのパースやフィールド操作のステップに加え、**イベントをフィルタリング**、**AIによる要約**、**APIを呼び出す**、**クエリ結果を追加**、**カスタムVRL**を選択できます。[処理ステップ](/ja/pipelines#処理ステップ)を参照してください。アラートパイプラインでは、**パターンでフィールド名を変更**と**指定したフィールドのみ保持**は、`labels`を起点に処理します。アラートパイプラインでは、サンプリングもルーティングも行いません。既存のパイプラインをアラートパイプラインに変更する場合は、保存する前に**サンプリング率**や**ストリームにルーティング**のステップを削除してください。

### アラートイベント

各ステップはアラートイベントをJSONとして処理します。

```json
{
  "summary": "Checkout error rate above 5%",
  "severity": "error",
  "labels": { "service": "checkout", "env": "prod", "host_name": "web-01" },
  "annotations": { "runbook": "https://wiki.example.com/checkout" },
  "affected_services": ["checkout"]
}
```

| フィールド | 内容 | ステップで設定できる値 |
|---|---|---|
| `summary` | インシデントのタイトルです。 | 空でない文字列です。512文字を超える部分は切り捨てます。 |
| `severity` | インシデントの重大度です。 | `info`、`warning`、`error`、`critical`のいずれかです。大文字と小文字は区別しません。`warn`は`warning`、`crit`は`critical`として扱います。 |
| `labels` | インシデントのラベルです。 | 値が文字列のオブジェクトです。数値や真偽値は文字列に変換し、`null`を指定するとラベルを削除します。 |
| `annotations` | インシデントのアノテーションです。 | `labels`と同じです。 |
| `affected_services` | 影響を受けるサービスの名前です。 | 名前のリストです。重複や空の名前は除外します。 |

ステップが上記以外のフィールドを追加しても反映しません。ステップがフィールドを削除しても元の値を保持します。ラベルをすべてクリアするには、`.labels = {}`を設定してください。`labels`の値にオブジェクトを指定するなど、これらのルールに違反する値を設定すると、パイプラインは失敗します。[イベントの処理結果](#イベントの処理結果)を参照してください。

`alert.source`や`external.kind`など、MoleSignalが自動で設定するラベルはインシデントの発生元を示すため、ステップの処理にかかわらず元の値を保持します。ステップはこれらのラベルを読み取れます。

### イベントの発生元

ステップはメタデータからイベントの発生元を読み取ります。これらの値はインシデントのフィールドには追加しません。

| メタデータ | 値 |
|---|---|
| `%source` | `rule`、`external`、`synthetic`、`no_data`のいずれかです。 |
| `%rule_id` | ルール、アラートソース、またはシンセティックチェックのIDです。 |
| `%rule_name` | ルール、アラートソース、またはシンセティックチェックの名前です。 |
| `%event` | インシデントを開く前は`opened`、インシデントが開いている間に発生元が再度アラートを発報すると`severity_changed`です。[重大度の変更](#重大度の変更)を参照してください。 |

```ruby
# alerts from staging page no higher than warning
if .labels.env == "staging" && (.severity == "critical" || .severity == "error") {
  .severity = "warning"
}

# the team that owns the host, from the extend table host_owner
owner = lookup("host_owner", .labels.host_name)
if is_object(owner) {
  .labels.team = owner.team
}

# a known false alarm opens no incident
if %rule_name == "Disk inode usage" && .labels.mount == "/boot" {
  abort
}
```

2番目のステップが設定する`team`ラベルを使って、インシデントをそのチームにルーティングできます。[ルーティングの順序](/ja/alerting/routing#ルーティングの順序)を参照してください。アラートパイプラインでも、他のVRLステップと同じように`lookup`と`geoip_lookup`を使えます。[テーブルとIPアドレスの検索](/ja/functions#テーブルとipアドレスを検索する)を参照してください。

### AIによる要約

**AIによる要約**ステップは、それまでのステップで処理したアラートイベントを**プロンプト**とともに組織のモデルに送信し、回答を**アノテーション**で指定したアノテーションに書き込みます。デフォルトのアノテーション名は`ai_summary`です。プロンプトの例を以下に示します。

```text
Summarize this alert for the on-call engineer in two sentences: what is wrong, and what to check first.
```

- インシデントを開くときに、モデルに1回だけ問い合わせます。[重大度が変更](#重大度の変更)されても、再度問い合わせることはありません。
- APIキーを設定済みで有効な[モデルプロバイダー](/ja/agent#モデルプロバイダーを設定する)のうち、最後に更新したプロバイダーの**デフォルトモデル**を使います。回答の上限はプロバイダーの**最大出力トークン数**で、未設定の場合は512トークンです。
- ステップは、アラートのタイトル、重大度、ラベル、アノテーション、影響を受けるサービスをモデルプロバイダーに送信します。
- 呼び出しは組織の[1日あたりのトークン予算](/ja/agent#使用状況と予算)に計上し、ソース別の使用量に**LLM 関数**として表示します。これらの呼び出しに`[functions].llm_eval_enabled`は適用しません。
- プロバイダーが未設定、1日の予算を使い切った、呼び出しに失敗したなどの理由でモデルから回答を得られない場合は、ステップが失敗し、パイプライン全体も失敗します。同じパイプライン内の他の変更も反映しません。要約の成否にかかわらず他の変更を反映するには、**AIによる要約**ステップを別のパイプラインに配置し、そのパイプラインを他のパイプラインの後に実行してください。

### APIを呼び出す

**APIを呼び出す**ステップは、組織の[HTTPコネクター](/ja/connectors#送信先)のいずれかにアラートイベントをPOSTし、レスポンスで指定された変更を反映します。コネクターのアドレスと認証情報を使い、送信時のセキュリティチェックも適用します。まずホストの名前を解決し、解決したアドレスにのみ接続します。クラウドメタデータのアドレスへの接続は拒否し、リダイレクトには従いません。

リクエストボディには、それまでのステップで処理したイベントのフィールドと、イベントの発生元の情報を含めます。

```json
{
  "summary": "Checkout error rate above 5%",
  "severity": "error",
  "priority": null,
  "urgency": null,
  "labels": { "service": "checkout" },
  "annotations": {},
  "affected_services": ["checkout"],
  "metadata": { "rule_id": "…", "rule_name": "Checkout errors", "source": "rule", "event": "opened" }
}
```

- レスポンスのJSONオブジェクトからは、`summary`、`severity`、`priority`、`urgency`、`labels`、`annotations`、`affected_services`のみを、[アラートイベント](#アラートイベント)のルールに従って反映します。`labels`と`annotations`はキー単位でマージし、値が`null`のキーは削除します。そのため、サービスは追加する項目だけを返せます。空のレスポンスでは何も変更しません。
- 呼び出しのタイムアウトは5秒で、インシデントを開くときに1回だけ実行します。[重大度が変更](#重大度の変更)されても、再度呼び出すことはありません。
- 時間内にレスポンスがない、ステータスコードが2xx以外、ボディがJSONオブジェクトではないか1 MiBを超える、フィールドがルールに違反する、コネクターが無効または存在しないといった理由で呼び出しが失敗した場合は、このステップだけを未実行として扱います。イベントをステップの実行前の状態のまま後続のステップに渡し、それまでの変更も保持します。失敗の理由は[タイムライン](#イベントの処理結果)と[集計](#日次集計)で確認できます。

### クエリ結果を追加

**クエリ結果を追加**ステップは、イベントの値を使ってクエリを実行し、結果の行をアノテーションに書き込みます。

```sql
SELECT count(*) AS errors FROM app_logs WHERE level = 'error' AND host = '{{labels.host_name}}'
```

| フィールド | 意味 |
|---|---|
| **言語** | SQLまたはPromQLです。PromQLはメトリクスストリームを読み取ります。 |
| **ストリームタイプ**、**ストリーム** | クエリが読み取るストリームです。このステップにはどのユーザーの`audit.read`権限も適用されないため、`_audit`は読み取れません。 |
| **クエリ** | プレースホルダーを含む1つのクエリです。 |
| **ルックバック期間（秒）** | クエリがインシデントを開いた時点からどこまでさかのぼるかを指定します。デフォルトは300、最大は86,400です。 |
| **行数** | アノテーションに書き込む行数です。デフォルトは5、最大は50です。 |
| **アノテーション** | 結果の行を書き込むアノテーションです。デフォルトは`query_result`です。 |

プレースホルダーはイベントの値を表します。`{{labels.<key>}}`、`{{annotations.<key>}}`、`{{summary}}`、`{{severity}}`、`{{priority}}`、`{{urgency}}`、`{{rule_id}}`、`{{rule_name}}`、`{{source}}`を使えます。ラベルは他のシステムから渡される場合があるため、プレースホルダーはクエリ文の引用符で囲まれた文字列の中に配置してください。そこでは値をエスケープします。それ以外の場所に配置すると、保存時に`400`を返します。

- クエリ結果の各行を、アノテーションの1行に書き込みます。値が1つなら値だけを、複数なら`column=value, column=value`の形式で記録します。上限は4,000文字です。クエリ結果が0行の場合は、アノテーションを追加しません。
- クエリのタイムアウトは10秒で、インシデントを開くときに1回だけ実行します。
- クエリが失敗した場合や、プレースホルダーに対応する値がイベントにない場合は、[**APIを呼び出す**](#apiを呼び出す)と同様に、このステップだけを未実行として扱います。

## イベントの処理結果

イベントを受け取った各パイプラインの処理結果は、次の3つのいずれかです。

| 結果 | 原因 | 影響 |
|---|---|---|
| **処理済み** | ステップが最後まで実行されました。 | イベントはステップによる変更を保持したまま後続の処理に進みます。 |
| **破棄** | ステップが `abort` を実行しました。 | インシデントは作成されず、後続のパイプラインも実行されません。 |
| **失敗** | ステップが失敗したか、処理後のフィールドが[アラートイベント](#アラートイベント)のルールに違反しています。**APIを呼び出す**または**クエリ結果を追加**ステップの失敗も含みます。 | このパイプラインによる変更は反映しません。ただし、**APIを呼び出す**または**クエリ結果を追加**ステップだけが失敗した場合は、ほかのステップによる変更を保持します。イベントは次のパイプラインに進み、インシデントも作成されます。 |

インシデントの[タイムライン](/ja/alerting/incidents#インシデントの詳細)には、変更を加えたか失敗したパイプラインごとに1行が表示されます。たとえば、**パイプライン Payments routing を通過: 重大度 error → critical、ラベル +team=payments** と表示され、失敗した場合はその理由が表示されます。変更のないパイプラインや[重大度の変更](#重大度の変更)の処理では、行は追加されません。1行には最大40件の変更を表示し、それ以降は件数のみを表示します。長い値は200文字で切り詰めます。

ルールが発火し続ける場合は、評価のたびにイベントを破棄します。[ルールリスト](/ja/alerting/rules#ルール一覧)にはルールの状態として**パイプラインで破棄**が表示され、APIの `last_state` は `{"kind": "dropped"}` になります。イベントを破棄したパイプラインは破棄件数を集計し、**概要**に直近の破棄に該当するルールを表示します。パイプラインが外部アラートを破棄した場合は、アラートソースの[**最近の受信リクエスト**](/ja/alerting/sources#最近の受信リクエスト)に**無視**と表示され、破棄したパイプラインとステップも併記されます。

## 重大度の変更

インシデントがオープンしている間は、アラートルールが再び発火するか、外部ソースがアラートを再送するか、外形監視チェックの状態が変わるたびに、アラートパイプラインが重大度を再判定します。

- インシデントの作成時と同じ方法でイベントを組み立て、ソースが現在報告している重大度を設定します。該当するパイプラインを実行しますが、**AIによる要約**、**APIを呼び出す**、**クエリ結果を追加**の各ステップは実行しません。`%event` は `severity_changed` になります。
- ステップの処理結果から重大度だけを取得し、現在の重大度と異なる場合はインシデントを更新します。タイトル、ラベル、アノテーション、サービスは、インシデントの作成時に設定したままです。
- パイプラインでイベントを破棄した場合や処理が失敗した場合は、何も変更しません。インシデントはオープンしたままで、次のパイプラインが実行されます。

たとえば、ステージング環境のアラートの重大度を下げるステップは、ルールが後からより高い重大度を報告した場合でも、重大度を引き下げます。確認済みのインシデントや、重大度を手動で設定したインシデントの重大度は変わりません。

## 通知の送信前

**アラートイベント**ノードの**いつ**を**通知の送信前**に設定します。[通知ポリシー](/ja/notification-channels)がアラートイベントの通知を送信する直前に、イベントのコピーに対してパイプラインが実行されます。パイプラインは、対象のポリシーごとに、後続ステップやエスカレーションを含む送信のたびに実行されます。インシデント自体を変更せずに、SMS通知のタイトルを短くしたり、特定のチームのWebhook用にラベルを追加したり、特定のポリシーの夜間通知を抑制したりできます。

- **通知ポリシー**で、パイプラインを適用するポリシーを指定します。何も選択しない場合は、アラートイベントのすべての通知ポリシーに適用します。この時点で、ポリシーのマッチングは変更前のイベントに対して完了しています。
- ほかの条件はこれまでと同様に、通知対象のイベントに対して評価します。時刻にはイベントの発生時刻を使い、**ソース**には**手動で作成されたインシデント**が加わります。
- ステップの処理はMoleSignal内で完結します。**AIによる要約**、**APIを呼び出す**、**クエリ結果を追加**は、インシデントの作成時にのみ実行します。これらのステップを含むパイプラインを通知の送信前に設定すると、`400` を返します。
- フローは**通知に反映**で終了します。ポリシーは、処理後のタイトル、重大度、優先度、緊急度、ラベル、アノテーション、サービスを[テンプレート](/ja/notification-channels#テンプレート変数)、Webhookの本文、デフォルトの通知文に反映します。通知先は変更前のイベントに基づいて決定します。
- ステップが `abort` を実行すると、このポリシーは通知を送信しません。配信ログには**スキップ済み**のレコードが表示されます。その理由には、パイプラインとステップがワークスペースのデフォルト言語で記録されます（`error_code` は `dropped_by_pipeline`）。インシデントのタイムラインにも記録します。これは失敗ではないため、ポリシーは送信を再試行せず、確認タイムアウトによるエスカレーションも続行しません。
- パイプラインが失敗した場合は変更を反映せず、元の内容で通知を送信します。失敗は[集計](#日次集計)に反映しますが、タイムラインには表示しません。

ステップは `%rule_id`、`%rule_name`、`%source` に加えて、`%policy_id` と `%policy_name` を参照できます。`%event` は `triggered`、`escalated`、`acknowledged`、`resolved` のいずれかです。`%rule_name` はルール名です。ルールによってインシデントが作成されていない場合は、イベントのタイトルになります。**テスト**では、サンプル値 `triggered` と `On-call alerts` を使用します。

```ruby
# on-call alerts of the staging environment go out only for what is critical
if %policy_name == "On-call alerts" && .labels.env == "staging" && .severity != "critical" {
  abort
}
```

## 日次集計

アラートパイプラインには実行履歴がなく、**その他 → バックフィル**も利用できません。代わりに、当日（UTC）の処理結果を集計します。

- リストでは、有効なアラートパイプラインの**ステータス**は**アラートイベント待機中**です。**最終実行**列には、**今日: 処理済み41件 · 破棄3件 · 失敗0件**のように件数を表示します。
- パイプラインの**概要**では、**処理済み**、**破棄**、**失敗**に同じ件数を表示します。**破棄**には直近の破棄に該当するルールまたはソースと発生時刻を表示し、**失敗**には直近の失敗理由を表示します。

件数はUTCの午前0時にゼロにリセットされます。条件に一致しなかったイベントや、[重大度の変更](#重大度の変更)に伴う処理は集計しません。APIは件数を `alert_record` として返します。[パイプラインの管理](/ja/api/intake/scheduled-pipelines#取得)を参照してください。

## 上限

| 項目 | 上限 |
|---|---|
| 1つのアラートパイプラインのステップ数 | 20 |
| **AIによる要約**ステップのプロンプト | 8 KiB |
| アノテーション名 | 255 bytes |
| **APIを呼び出す**ステップのレスポンス | 1 MiB、5秒以内 |
| **クエリ結果を追加**ステップのクエリ文 | 8 KiB |
| **クエリ結果を追加**ステップが取得する行数 | 50行、10秒以内 |
| **クエリ結果を追加**ステップが書き込むテキスト | 4,000文字 |

## APIで作成する

アラートパイプラインは、ほかのパイプラインと同じ方法で保存します。`functionSteps.mode` を `alert` に設定し、ストリームとスケジュールは空にします。

```bash
curl -X POST http://localhost:5080/api/v1/scheduled_pipelines \
  -H "authorization: Bearer $MS_TOKEN" \
  -H 'content-type: application/json' \
  -d '{
    "name": "staging-alerts",
    "sourceStream": "",
    "targetStream": "",
    "cron": "",
    "enabled": true,
    "functionSteps": {
      "mode": "alert",
      "alert": {
        "sources": ["rule", "external"],
        "severities": [],
        "labels": { "env": "staging" },
        "order": 10
      },
      "steps": [
        { "transformName": "cap-severity", "kind": "vrl",
          "script": "if .severity == \"critical\" { .severity = \"warning\" }" },
        { "transformName": "summary", "kind": "ai_summary",
          "prompt": "Summarize this alert in two sentences for the on-call engineer.",
          "annotation": "ai_summary" }
      ]
    }
  }'
```

通知の送信前に実行するパイプラインでは、`alert.stage` を `notify` に設定します。必要に応じて `alert.policies` を指定します。

```json
{
  "mode": "alert",
  "alert": { "stage": "notify", "policies": ["<policy id>"], "labels": { "env": "staging" }, "order": 10 },
  "steps": [
    { "transformName": "quiet", "kind": "vrl", "script": "if .severity != \"critical\" { abort }" }
  ]
}
```

各フィールドについては、[パイプラインを作成する](/ja/api/intake/create-pipeline)を参照してください。アラートパイプラインにも[すべてのパイプラインに共通する権限](/ja/pipelines#権限)が適用されます。
