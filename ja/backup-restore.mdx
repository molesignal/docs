MoleSignal は、状態を PostgreSQL、オブジェクトストレージ、設定とシークレットに保持します。各ノードのディスクに保持するのはキャッシュのみです。それぞれをバックアップし、バックアップを運用で使う前に復元手順をリハーサルしてください。

## バックアップ対象

| 状態 | 保存内容 | バックアップ |
|---|---|---|
| PostgreSQL | ユーザー、組織、トークン、ストリーム、ダッシュボード、アラートルール、ストリームとオブジェクトを対応付けるファイルカタログ | 必須 |
| オブジェクトストレージ | Parquet データファイル、検索インデックス、プロファイルの BLOB、未フラッシュのレコードの先行書き込みログ (WAL) オブジェクト (`wal/v1/`) | 必須 |
| `MS_CIPHER_KEY` | PostgreSQL 内のシークレットのルートキー | 必須。データベースのバックアップとは別に保管してください。 |
| 設定 | `config.toml`、環境変数、使用している場合は `MS_AUTH_JWT_SECRET_OVERRIDE` | 必須 |
| ACME ディレクトリ (`[http.tls].key_storage_dir`) | ACME アカウントキーとドメインキー | 任意。証明書は再発行できます。 |
| キャッシュディレクトリ (`[cache.object].root`) | リモートオブジェクトの範囲データのローカルコピー | バックアップしないでください。 |

## データベースとオブジェクトの整合性を保つ

PostgreSQL のファイルカタログは、バケット内のオブジェクトを参照します。フラッシュ時は、オブジェクトを先にアップロードしてからカタログに登録します。コンパクションや保持ポリシーによる削除では、先にカタログから参照を削除します。ガベージコレクターは、`[storage.gc].grace_period_secs`（デフォルトは 3600 秒）の経過後にオブジェクトを削除します。

整合性のあるバックアップを作成するには、次の順序で作業します。

1. PostgreSQL のバックアップを取得します。
2. その直後にバケットのコピーを開始し、猶予期間内に完了します。

猶予期間内にコピーが完了すれば、データベースのバックアップが参照するすべてのオブジェクトがコピーに含まれます。コピーにそれ以上かかる場合は、バックアップ前に `grace_period_secs` を増やすか、バケットのバージョニングを有効にして、データベースのバックアップ取得時点のオブジェクトを復元してください。

## PostgreSQL をバックアップする

ポイントインタイムリカバリに対応した定期スナップショットなど、PostgreSQL サービスのバックアップ機能を使用します。データベースを自主管理している小規模なデプロイメントでは、論理ダンプを利用できます。

```bash
pg_dump --format=custom --file=molesignal.dump "postgres://molesignal@db.internal:5432/molesignal"
```

## オブジェクトストレージをバックアップする

プロバイダーのバケットレプリケーションまたはバージョニングを使用します。別のバケットへの定期コピーでもバックアップできます。

```bash
aws s3 sync s3://molesignal s3://molesignal-backup
```

RustFS などの S3 互換サービスでは、`--endpoint-url` を追加します。バックアップ先のバケットで削除権限を持たない認証情報を使用してください。

## 復元する

<Steps>
  <Step title="すべてのノードを停止する">
    データの入れ替え中に書き込みが行われないように、すべての MoleSignal プロセスを停止します。
  </Step>
  <Step title="PostgreSQL を復元する">
    空のデータベースにバックアップを復元します。

    ```bash
    pg_restore --no-owner --dbname "postgres://molesignal@db.internal:5432/molesignal" molesignal.dump
    ```
  </Step>
  <Step title="オブジェクトを復元する">
    ノードが使用するバケットにバックアップをコピーします。バケットを、データベースのバックアップ取得時点か、それより後の時点の状態に復元します。

    リコンサイラーは、復元したカタログに参照がないオブジェクトを孤立オブジェクトとしてキューに追加します。ガベージコレクターは、`[storage.reconciler].orphan_grace_secs`（デフォルトは 24 時間）の経過後にそれらを削除します。バックアップ取得後のオブジェクトがまだ必要な可能性がある場合は、先に別の場所へコピーしてください。
  </Step>
  <Step title="シークレットと設定を復元する">
    バックアップ元のデプロイメントで使用していた設定と、同じ `MS_CIPHER_KEY` を指定します。キーが異なると、ノードは保存済みのシークレットを復号できず、`open Probe CA key` などのエラーが発生して起動に失敗します。
  </Step>
  <Step title="取り込みノードに WAL を引き継がせる">
    WAL オブジェクトはバケットとともに復元されます。ノードが稼働すると、取り込みノードは、復元したデータベースに登録されている各ライターのリースが切れた後に、そのライターの WAL を公開します。データベースのバックアップ取得後に登録されたライターの WAL オブジェクトは公開されません。
  </Step>
  <Step title="起動して確認する">
    ノードを起動し、`GET /api/v1/healthz` が `200` を返すまで待ちます。サインインしてストリームを開き、復元した範囲を対象にクエリを実行します。

    `/metrics` で、`reason="missing"` が付いた `storage_reconciler_issues_total` を確認します。このようなエントリは、カタログがバケットに存在しないオブジェクトを参照していることを示します。
  </Step>
</Steps>

## 障害シナリオ

| 喪失したもの | 影響 | 復旧方法 |
|---|---|---|
| ノードのローカルディスク | 受領確認済みのデータは失われません。キャッシュは再構築されます。 | ノードを交換します。別の取り込みノードが `[wal].lease_secs` の経過後に、そのノードの WAL を公開します。[耐久性と引き継ぎ](/ja/architecture#データの耐久性と引き継ぎ)を参照してください。 |
| PostgreSQL | すべてのメタデータが失われ、オブジェクトにアクセスできなくなります。 | 最新のバックアップを復元します。バックアップ取得後に書き込まれたデータは、対応するオブジェクトがカタログに登録されていないため、復旧できません。 |
| バケット | 失われた範囲を対象とするクエリが失敗します。 | バケットを復元します。対応するオブジェクトがないカタログエントリは、`/metrics` に `missing` として表示されます。 |
| `MS_CIPHER_KEY` | 保存済みのシークレットを復号できず、ノードの起動に失敗します。 | シークレットマネージャーからキーを復元します。キーがないと、暗号化された列は復旧できません。 |
