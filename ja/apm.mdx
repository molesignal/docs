MoleSignal APMは、バックエンドのOpenTelemetryトレーススパンを、遅いサービス、失敗しているエンドポイント、コストの高い依存関係、繰り返し発生するバックエンドエラー、デプロイ済みバージョン間のリグレッションを個別のメトリクス計装なしで見つけるための上限付きRED集計に変換します。そのサービスカタログには、各サービスの所有者と重要度が記録されます。

<Note>
  APMには別のSDKやテレメトリストリームは必要ありません。適切に計装されたトレースを送信すると、 MoleSignalはトレースの重複排除後、テールサンプリング前にAPMデータを導出します。後でサンプリング対象外になるトレースもAPMメトリクスに貢献でき、また、 [リアルタイムパイプライン](/ja/pipelines#トレース)がドロップするスパンも同様です。
</Note>

## ページ

APMは概要で開きます。各サービスには専用のページがあります。

| ページ | 目的 |
|---|---|
| **概要** | 全サービスをまとめて表示: アクティブなサービス、スループット、エラー率、p95（p50、p90、p99、平均を含む）、Apdex。サービスヘルスの内訳と推移。最も遅いサービス、最も失敗が多いサービス、最も負荷の高いサービス。直前の期間および1週間前の同じ期間と比較して何が変化したか、当時の変更、時間を短縮できる箇所に関するインサイト。サービス名を含むアクティブなアラート。期間内にデプロイされたバージョン。環境。サービスが計装から除外している内容。 |
| **サービス** | サービスカタログ: APMが認識するすべてのサービスと宣言済みのすべてのサービスを、所有者、ティア、タグ、発生中のアラート、スループット、エラー率、レイテンシ、バージョン、最終デプロイとともに表示します。お気に入りが先頭に表示され、アーカイブ済みサービスは表示するまで除外されます。 |
| **サービスマップ** | 環境内のサービスとそれらの間の呼び出し、各サービスが呼び出すもの、発行および消費するトピック。直前の期間と比較して新規または消失した呼び出し。[APMサービスマップ](/ja/apm/service-map#apm-のサービスマップ)を参照してください。 |
| **エラー** | すべてのサービスのバックエンドエラーグループを、状態、チーム、担当者、発生箇所、グループ化のルールとともに表示します。 |
| **SLO** | サービスレベル目標を、各目標が対象期間中に達成した内容、残りのエラーバジェット、バジェットの消費速度、状態とともに表示します。 |
| **設定** | 組織のヘルスライン、デフォルトのApdexしきい値、長時間タスク、カタログ要件、命名ルール、環境マッピング、エイリアスを、過去1日間のデータが示す内容とともに表示します。プラットフォームのカーディナリティ制限とトレースサンプリング。[APM設定](/ja/apm/settings)を参照してください。 |

サービスページには次のセクションがあります:

| セクション | 目的 |
|---|---|
| **概要** | リクエスト、エラー率、レイテンシを並べて表示し、サービスのインサイト、サービスのSLO、宣言されている場合に[ビジネスキー](/ja/business-context)で分割したリクエスト、レイテンシ分布、ダウンストリームでの所要時間、最も比重の大きいエンドポイントとエラーを表示します。 |
| **エンドポイント** | HTTP、RPC、メッセージング、ワーカーのエントリポイントを、リクエスト数、エラー数、レイテンシ、時間の割合でランク付けします。エンドポイントを開くとドロワーにステータスコード、時間の内訳、最も遅いリクエストが表示されます。スターは重要トランザクションを示し、リストはそれらのみ、または長時間タスクのみに絞り込めます。 |
| **トレース** | サービスが関与したトレースを、トレースページのトレーステーブルに表示します。 |
| **依存関係** | サービスを呼び出すサービスと、ターゲット別にグループ化した外向き呼び出し（各ターゲットの下に各オペレーション）、各ターゲットのヘルス、タイムアウトした呼び出しまたは再送された呼び出し、最も遅いSQL文を表示します。 |
| **エラー** | サービスのエラーグループ。 |
| **デプロイ** | パイプラインが報告した内容を、スパンが保持するバージョンの横に表示し、ロールバックはそのように示し、各バージョンを直前のバージョンと比較し、同時に実行中の2バージョンを並べ、2バージョンを比較します。[デプロイ](/ja/apm/deployments)を参照してください。 |
| **ランタイム** | サービスを実行したインスタンスと各インスタンスが処理した内容、プロセスおよびサービスの言語のランタイムメトリクスからのチャート、プロファイルからのフレームグラフを表示します。 |
| **設定** | サービスのカタログエントリと重要トランザクションを、インスタンスが報告する内容と並べて表示します。 |

サービス名の次の行には、サービスが何であるかが表示され、表示中の環境とバージョンに追従します:

| 項目 | ソース |
|---|---|
| ヘルス | 期間のRED指標。ポイントすると理由が表示されます。リクエストのない期間では代わりに**この期間のデータはありません**と表示されます。テレメトリの欠落は、サービスが異常であることを意味しません。 |
| ティア | カタログエントリ。 |
| システムと環境 | `service.namespace` と `deployment.environment.name`。 |
| 種類 | サービスが処理するエントリスパン: **HTTP**、**RPC**、メッセージ用の**コンシューマー**、内部エントリスパン用の**ワーカー**。 |
| 言語とフレームワーク | `telemetry.sdk.language`、およびAxum、Spring、Expressなど、サービスのエントリスパンの計装ライブラリ。 |
| バージョン | 選択したバージョン、または期間内にインスタンスが実行したすべてのバージョン（最も広く実行されたものが先頭）。ロールアウトでは両方が表示されます。 |
| チーム | カタログエントリ。チームをポイントすると、所有者とオンコール担当が表示されます。 |
| インスタンス | 期間内に報告した、表示中バージョンのインスタンス。**ランタイム**を開きます。 |
| 最終デプロイ | 表示中のバージョン、または最新バージョンが最初に確認された日時。 |
| リージョン | インスタンスの`cloud.region`。 |
| リポジトリ | インスタンスの`vcs.repository.url.full`または`git.repository_url`。ない場合はカタログエントリのリポジトリ。 |
| 別名 | カタログエントリの他の名前: 最初の名前と、他にいくつあるか。 |

アーカイブ済みサービスはそこに**アーカイブ済み**とも表示されます。タイトル行の末尾にある**お気に入り**を押すと、そのサービスが閲覧者のお気に入りに保持されます。

ナビゲーションカードの末尾には、サービスのログ、メトリクス、プロファイルへのリンクがあります。各リンクは、表示中の期間の終了前1日間にシグナルがサービスを保持している場合に点灯し、MoleSignalは 5分ごとに再確認します:

| シグナル | 点灯条件 |
|---|---|
| ログ | `service.name`、`service_name`、または`service`フィールドを持つログストリームに、そのサービスの行が含まれている場合。リンクはそのストリームでログを開きます。 |
| メトリクス | 直近1時間のシリーズにサービスの`service.name`が含まれている場合。 |
| プロファイル | プロファイルストリームにサービスのプロファイルが含まれている場合。 |
| RUM | ブラウザセッションがサービスのサンプルトレースの1つを生成した場合。リンクはその場合にのみ表示され、そのセッションを開きます。 |

データのないシグナルは淡色表示になり、そのシグナルを接続する**データソース**ページを開きます。参照が失敗した場合、または3秒を超える場合は、リンクは点灯も淡色表示もされません。

## 前提条件

- MoleSignalの[トレース取り込みエンドポイント](/ja/intake)に送信されたOpenTelemetryトレース。
- 組織ワークスペースの`apm.services.read`。または
- 保護された`_sys`テレメトリの`sys.telemetry.read`。

## APM のためのサービスを計装する

<Steps>
  <Step title="安定したサービスのリソース属性を設定する">
    すべてのサービスに `service.name` を設定します。namespace、environment、version、instance の属性を、サービスフィルタリングやデプロイ比較のために追加します。

    ```bash
    export OTEL_SERVICE_NAME=checkout
    export OTEL_RESOURCE_ATTRIBUTES="service.namespace=shop,deployment.environment.name=production,service.version=2.4.0,service.instance.id=checkout-01"
    ```

    正確な設定方法は、選択した OpenTelemetry SDK または Collector によって異なります。
  </Step>
  <Step title="正しいスパン種別を使用する">
    受信リクエストには `SERVER` スパンを、消費メッセージには `CONSUMER` スパンを作成します。下流呼び出しには `CLIENT` または `PRODUCER` スパンを作成します。MoleSignal はこれらのスパン種別を使用して、トランザクションと依存関係を分離します。
  </Step>
  <Step title="ステータスと例外を記録する">
    OpenTelemetry のスパンステータス、HTTP または RPC のステータス属性、例外イベントを設定します。MoleSignal は記録されたステータスデータを使用して、成功した処理と失敗した処理を分類し、バックエンドのエラーグループを構築します。
  </Step>
  <Step title="トレースを送信して APM を開く">
    OTLP トレースを送信してから、**APM → サービス** を開きます。プロジェクターが最初のバケットをフラッシュする間は、グローバル時間範囲を直近のトラフィックに合わせておきます。
  </Step>
</Steps>

### 推奨されるリソース属性

| 属性 | 目的 | フォールバック |
|---|---|---|
| `service.name` | 安定したサービスの識別子。すべてのサービスで明示的に設定します。 | `unknown_service` |
| `service.namespace` | システムやチームをまたいで同じ名前のサービスを分離します。 | `default` |
| `deployment.environment.name` | 本番、ステージング、その他の環境をフィルタリングします。 | レガシーの `deployment.environment`、次に `unknown` |
| `service.version` | バージョン履歴とデプロイ比較を有効にします。 | バージョン別の内訳なし |
| `service.instance.id` | インスタンスを識別します。 | `k8s.pod.name`、次に `host.name` |
| `telemetry.sdk.language` | サービスカタログにランタイム言語を表示します。 | 存在する場合は `process.runtime.name` |
| `cloud.region`、`k8s.*`、`host.name`、`container.name`、`container.id` | 各インスタンスがどこで実行されているかを示します。 | 表示されません |
| `process.runtime.name`、`process.runtime.version` | 各インスタンスのランタイムを表示します。 | 表示されません |
| `vcs.repository.url.full`、`vcs.ref.head.revision` | リポジトリをリンクし、コミットを特定します。`git.repository_url` と `git.commit.sha` も使用できます。 | カタログエントリのリポジトリ |

Kubernetes 属性と `cloud.region` は通常、SDK ではなく OpenTelemetry Collector の `k8sattributes` と `resourcedetection` プロセッサによって追加されます。

カーディナリティの低い値を使用します。リクエスト ID、生の URL、ユーザー ID、その他の上限のない値を、サービス、環境、バージョン、ルート、オペレーション、依存関係の属性に入れないでください。

## MoleSignal が APM データを導出する方法

### サービスとエンドポイント

`SERVER` スパンと `CONSUMER` スパンは、サービスとエンドポイントの RED メトリクスに寄与します。API はエンドポイントをトランザクションと呼びます。種別のない親のないスパンは互換性のフォールバックとしてサービスの合計に寄与できますが、明示的なスパン種別の方がより完全なページを生成します。

MoleSignal は、セマンティック属性からカーディナリティを抑えたエンドポイント名を構築します:

- HTTP メソッドと `http.route` の組み合わせ（例: `POST /checkout`）。
- RPC サービスとメソッドの組み合わせ。
- メッセージング操作と送信先の組み合わせ。
- より強いセマンティック ID が存在しない場合の、安全でカーディナリティの低いスパン名。

`/orders/{id}` のようなルートテンプレートを、`/orders/83921` のような生のパスより優先します。

### 依存関係

`CLIENT` スパンと `PRODUCER` スパンは、依存関係の RED メトリクスに寄与します。MoleSignal はターゲットをサービス、データベース、キャッシュ、メッセージングシステム、外部 HTTP エンドポイント、外部 RPC エンドポイント、その他の依存関係として分類します。標準の `peer.service`、`db.*`、`messaging.*`、`rpc.*`、`server.*`、HTTP セマンティック属性は依存関係の識別を改善します。

`peer.service` のないデータベースまたはキャッシュ呼び出しでは、`postgresql` や `redis` など、そのシステムがターゲットになります。[`MS_TRACE_FINGERPRINT_KEY`](/ja/configuration#環境変数) が設定されている場合、ターゲットはさらに `db.namespace`（なければ `db.name` または `db.collection.name`）のキー付きフィンガープリントも保持します（例: `postgresql:<fingerprint>`）。これにより、あるシステムのデータベースを、その名前を保存せずに区別できます。

SQL データベース呼び出しのオペレーションは、そのステートメントをテンプレートとして使用します。`db.query.summary`、なければ `db.query.text` または `db.statement` を使用し、すべてのリテラルを `?` に置き換え、コメントを削除し、値のリストを 1 つの `?` にまとめ、最大 512 バイトを保持します。二重引用符で囲まれたテキストは、PostgreSQL や Oracle など、テーブル名または列名を表すデータベースでのみ保持されます。それ以外では値として扱われます。ステートメントのない呼び出しは `db.operation.name` を保持し、キャッシュ呼び出しではそのコマンドを保持します。サービスは 1 時間あたり 1 つのターゲットの最大 32 オペレーションを保持します。それを超えるオペレーションは、同じターゲットの下で **その他** としてまとめてカウントされます。

タイムアウトしたリクエスト（タイムアウトエラータイプ、gRPC `DEADLINE_EXCEEDED`、HTTP 408 または 504）と、再送信されたリクエスト（`http.request.resend_count` が 0 より大きい）は、RED メトリクスとは別にカウントされます。

### エラー

MoleSignal は、例外が存在する場合、OpenTelemetry ステータスが `ERROR` の場合、HTTP ステータスが 500 以上の場合、または RPC ステータスが 0 以外の場合に、スパンをエラーとして分類します。エラーグループは、エラータイプ、最初のアプリケーションスタックフレーム、トランザクション名に基づく安定したフィンガープリントを使用します。変動するエラーメッセージはフィンガープリントの一部ではありません。[グループ化ルール](#ルールでエラーをグループ化する) により、エラーを 1 つのグループにマージしたり、グループから除外したりできます。

## RED メトリクスを理解する

| メトリクス | 意味 |
|---|---|
| **リクエスト数** | 一致するサービス、エンドポイント、または依存関係の観測数。 |
| **エラー率** | エラー数をリクエスト数で割った値。 |
| **レイテンシー** | マージされたレイテンシーヒストグラムから読み取った p50、p90、p95、p99、および平均継続時間。 |
| **Apdex** | しきい値 T 以内のリクエストに、4T 以内のリクエストの半分を加えたものを、全リクエストで割った値。T は組織のデフォルト（[APM 設定](/ja/apm/settings#ヘルスとしきい値) で変更されない限り 500 ms）か、サービスのカタログエントリが設定する T です。レイテンシー分布には使用中の T が表示されます。概要は、組織のデフォルトで全サービスをまとめて読み取ります。失敗したリクエストは決して満足扱いになりません。失敗はレイテンシー全体に均等に除外されます。 |
| **合計時間** | 観測された継続時間の合計で、集計への影響が最も大きい処理を強調表示します。 |

サービスは、エラー率 2% または p95 500 ms から **警告** になり、10% または 2 秒から **クリティカル** になります。ただし、[APM 設定](/ja/apm/settings#ヘルスとしきい値) で別のしきい値が設定されている場合を除きます。サービスページとカタログのドットは、どの数値がどのしきい値を超えたかを示します。

**インサイト** カードは、前の同じ長さの期間と比較して、また 1 週間前の同じ期間と比較して、どのサービスが変化したかを示します。詳細は [インサイトが検出する内容](/ja/apm/insights#インサイトで検出される内容) を参照してください。

レイテンシーヒストグラムは、レイテンシーの各 2 倍の範囲を 8 つのバケットに分割します（125 µs から約 131 秒まで）。パーセンタイルはそのバケット内で読み取られます。パーセンタイルは正確な値の約 4% 以内です。以前の固定バケットで書き込まれた集計は、より粗い精度で引き続き読み取れます。

概要とエンドポイントドロワーの **比較対象** コントロールは、1 日前または 1 週間前の同じ範囲を破線で描画し、レイテンシー分布はその範囲の広がりを輪郭表示します。サービスページでは、そのコントロールがサービスの他の環境も一覧表示します。その環境の同じ範囲は、代わりに破線で描画されます。

エンドポイントの最も遅いリクエストはトレースストアから取得されるため、一覧表示された各リクエストはそのトレースを開きます。エラーサンプルは、テールサンプリングでドロップされたトレースを指す場合があります。その場合、トレースドロワーにはトレースが見つからなかったことが表示されます。

## サービスカタログ

カタログには、APM が認識するすべてのサービスが、サービスと環境ごとに 1 行で一覧表示されます。また、レポートを送信する前に登録されたサービスも表示されます。カタログで**サービスを登録**し、サービスページの**設定**セクションで記録します:

| フィールド | 意味 |
|---|---|
| **担当チーム** | ワークスペースのチーム。チームで最初に有効化されたオンコールスケジュールが、オンコール担当者を示します。 |
| **オーナー** | サービスの責任を負うワークスペースのメンバー。 |
| **ティア** | P0（最も重要なサービス）から P5 まで。 |
| **ライフサイクル** | 本番、ステージング、実験的、または非推奨。 |
| **リポジトリ** | コードの所在。サービスがリポジトリをレポートしない場合に使用します。https アドレス、または `git@github.com:acme/checkout.git` や `ssh://git@git.example.com/team/checkout.git` のような git アドレスを指定します。アドレス内のパスワードは `****` として保持されます。git がトークンを伝える https アドレスでは、ユーザー部分も同様に `****` として保持されます。サービスページでは、git アドレスを同じパスの https ページで開きます。 |
| **タグ** | `key=value` のペア、またはキーのみをカンマで区切って指定します。キーは最大 64 文字で、小文字の英字、数字、および `_ . - /` を使用できます。値は最大 128 文字です。最大 32 個まで指定できます。 |
| **Apdex しきい値 T** | サービスの Apdex のしきい値（ミリ秒、最大 1 分）。空欄の場合は組織のデフォルトを使用します。APM 設定で変更しない限り 500 ms です。 |
| **サービスの機能** | サービス名の下に表示される簡単な説明。 |
| **別名** | ログ、メトリクス、その他のシステムがサービスを呼ぶ際の名前をカンマで区切って指定します（例: `order_service`、Order Center）。最大 20 個、各名前は最大 128 文字です。名前はサービス自身の名前にはできず、別のサービスの名前または別名にもできません。カタログの検索では、これらの名前でもサービスを検索できます。 |
| **データソース** | サービスのログを保持するログストリーム。それぞれに、ストリームからログを抽出する任意の SQL 条件を指定できます。サービスのメトリクスの PromQL セレクター（例: `{service="checkout"}`）。サービスを表示するダッシュボード。およびランブックや CMDB エントリなど、外部ページへのリンク。それぞれ最大 10 個まで指定できます。各行は、**ログ**、**メトリクス**、ダッシュボード、または新しいタブでデータを開きます。 |

**別名**と**データソース**は、人と同じように Mole Agent にも役立ちます。Mole Agent がサービスについて質問されると、両方を含むカタログエントリを読み取り、別名のいずれかについての APM の質問では、その名前が属するサービスを読み取ります。データは統合されません。古いサービス名がサービス自体としてレポートした内容を読み取るには、代わりに[サービスエイリアス](/ja/apm/settings#サービスのエイリアス)を追加します。

同じフォームの**アーカイブ**は、サービスをカタログのデフォルトビューから除外します。そのデータは引き続き収集され、ページも引き続き開くことができます。カタログの**アーカイブ済み**では、アーカイブ済みのサービスも一覧表示されます。

[カタログの要件](/ja/apm/settings#カタログ要件)では、担当チーム、オーナー、またはリポジトリを特定のティア以上のサービスに求めます。いずれかが不足しているサービスは、不足している内容とともに**要対応**とカタログに表示されます。

定義は名前空間と名前をキーとするため、すべての環境で有効です。**列**メニューはカタログとエンドポイントテーブルの列を選択および並べ替えます。配置はユーザーごとに保持されます。数値とカタログのフィールドに加えて、カタログには**タイプ**、 **言語 / フレームワーク**、**インスタンス**、**リージョン**が表示され、これらは範囲内のインスタンスから読み取られ、 **タグ**と**最終検出**も表示されます。

**相関**はデフォルトで表示され、サービスが他のデータと結び付く各方法についてドットを描画します: ログ内のトレース ID、リソース属性、メトリクス、およびレポートされた変更です。緑は適切に結び付いていること、黄色は一部、灰色はまったく結び付いていないこと、最も淡い色は読み取れなかったことを示します。ドットにホバーすると、その背景にある数値が表示されます。[収集品質](/ja/apm/settings#収集品質)には修正すべき項目が一覧表示されます。

カタログ行の星は、サービスを閲覧者のお気に入りに追加します。お気に入りはカタログの先頭に表示され、 **お気に入り**ではお気に入りのみが一覧表示されます。お気に入りはユーザーごとに保持されます。**グループ**は行をチーム、名前空間、ティア、またはタグの値でグループ化します。カタログは環境とチームでフィルターでき、サービスが複数ある場合は名前空間とタグでもフィルターできます。フィルターとグループ化はアドレスの一部であるため、共有リンクを開くと同じビューが表示されます。範囲内で検出されたものの、範囲の終了時点で 1 日間レポートがなかったサービスは**非アクティブ**と表示されます。

キートランザクションは、最も重要なエンドポイントです。エンドポイントリストまたはそのドロワーでエンドポイントの星を付けると、そのエンドポイントがマークされ、**設定**にサービスのキートランザクションが、範囲内でそれぞれが処理した内容とともに一覧表示されます。 1 つのサービスで最大 50 個まで保持されます。

サービスドキュメントとランブックは、Mole Agent のナレッジベースの `services/<service name>/` 以下にあります。組織のベースまたは担当チームのベースに置かれます。サービスページの**ドキュメント**では、それらを一覧表示し、ランブックを開始できます。Mole Agent はサービスを調査するときに同じファイルを読み取ります。

定義とキートランザクションの書き込みには `apm.definitions.manage` が必要で、エラー状態の書き込みには `apm.errors.manage` が必要です。オーナー、管理者、および編集者がこの権限を持ちます。

## インスタンス

サービスに対してレポートする各プロセスがインスタンスです。インスタンスは `service.instance.id`、なければ `k8s.pod.name`、それもなければ `host.name` で区別されます。MoleSignal はインスタンスのスパンを 1 分に 1 回確認し、そのバージョンと上記の表の属性を保持します。各属性は最後にレポートされた値です。リポジトリリンクはユーザー、パスワード、クエリを含まない https アドレスとして保持されます。各インスタンスが処理した内容（リクエスト、エラー、レイテンシ）は、サービスの数値と同じスパンから、インスタンス独自のバケットで集計されます。

**ランタイム**では、表示中の範囲とバージョンに該当するインスタンスを、最終検出が新しい順に一覧表示します。各インスタンスにはスループット、エラー率、p95、およびインスタンスのログ（ポッド、なければホスト別）とメトリクス（区別に使用するラベル別）へのリンクが表示されます。サービスおよび 1 時間あたりのインスタンスカーディナリティ制限を超えると、残りは**その他のインスタンス**としてまとめて集計されるため、インスタンスの合計がサービスと一致します。インスタンスをクリックすると、ランタイムチャートがそのインスタンスに絞り込まれ、選択内容はアドレスの一部になります。インスタンスが 1 時間単位の集計が保持される期間にわたって検出されなかった場合に削除されます。

## エンドポイントの詳細

エンドポイントドロワーは、RED チャートに 2 つのカードを追加します:

- **ステータスコード**は、レスポンスをコード別に集計します: HTTP コードは `http.response.status_code` から、（古い計装では `http.status_code`）、gRPC コードは `rpc.grpc.status_code` から取得し、それぞれをクラス別に色分けし、トレンドも表示します。1 つのバケットには最大 24 個のコードを保持し、それ以降のコードは **その他の HTTP** または **その他の gRPC** として集計されます。ステータスコードの集計開始前に書き込まれた集計には、ステータスコードが含まれません。
- **処理時間の内訳**は、トレースストアから範囲内のエンドポイントの最新リクエストを読み取ります（最大 200 件）。各リクエスト配下のスパンも読み取ります。呼び出しの時間は、呼び出し先に応じて分類されます: データベース（`db.system.name`）、キャッシュ（Redis、Memcached、Valkey）、HTTP、RPC、またはメッセージング、および**その他**は呼び出し先を特定できない呼び出しです。内部スパンは内部処理としてカウントされ、リクエスト配下のスパンでカバーされない時間は、リクエスト自身の時間です。各部分は、その割合とリクエストあたりの時間とともに表示されます。並列に行われた呼び出しは、リクエストの長さを超えて合算されることがあります。その場合、各部分はリクエストの長さに合わせてスケーリングされます。読み取られるのは、テールサンプリングで保持されたトレースのみです。

エンドポイントリストの**ロングタスク**では、p99 が 1 秒以上のエンドポイントを保持します。エントリースパンは内部種別（スケジュールされたジョブや、メッセージング操作のないキューワーカーなど）で、 **ワーカー**として一覧表示されます。

## デプロイメント

サービスページの**デプロイメント**セクションでは、パイプラインがレポートするデプロイメントを、サービスのスパンが持つバージョンと並べて表示し、ロールバックを特定し、各バージョンをその前のバージョンと比較し、同時に実行されている 2 つのバージョンを並べて表示します。パイプラインは次の API でデプロイメントをレポートします: `POST /api/v1/apm/deployments`。[デプロイメント](/ja/apm/deployments)を参照してください。

## 依存関係

サービスの**依存関係**タブにある各ターゲットには100点満点の健全性スコアが付きます。失敗した呼び出しの割合1%ごとに4点（最大60点）、時間切れになった呼び出しの割合1%ごとに4点（最大20点）、さらに比較期間中はP95が5分の1を超えて増加した割合1%ごとに0.5点（最大20点）が減点されます。90点以上で良好、70点以上で確認の価値ありです。スコアのタイトルには減点の理由が表示されます。**比較対象**を設定すると、各ターゲットのエラー率とP95の変化も表示されます。**遅いSQL**には、P95が最も高いデータベースステートメントがテンプレートとして一覧表示されます。

  </Step>

## バックエンドのエラーを追跡する

エラーグループは、誰かが**調査中**、**解決済み**、または**無視**に設定するまでオープンのままです。各グループはチームに割り当てたり、ワークスペースのメンバーにアサインしたりできます。解決済みのグループが再び発生すると**再発**として表示されます。**APM → エラー**には、デフォルトで未解決のグループ（オープン、調査中、再発）が表示されます。

リストの上部にある**発生箇所の内訳**には、一覧表示されたグループの発生回数がバージョン、環境、サービスの言語別に集計されます。エラーグループのドロワーでは、そのグループ自身の発生回数が集計されます。ドロワーの**関連ログ**をクリックすると、そのサービスと期間のログが開き、サンプルの横にある**ログ**をクリックすると、そのサンプルのトレースのログが開きます。

### ルールでエラーをグループ化する

エラー一覧の**グループ化ルール**では、エラーの種類、フレーム、エンドポイント以外の基準でエラーをグループ化する方法を設定します。ルールには、サービス（またはすべてのサービス）と、エラーの種類、メッセージ、エラーがスローされたフレーム、エンドポイントのパターンを指定します。各パターンは大文字と小文字を区別せずにテキスト全体と一致し、`*`は任意のテキストを表します。空のパターンは何にでも一致し、ルールには少なくとも1つのパターンが必要です。

| アクション | 効果 |
|---|---|
| **1つのグループに統合** | サービス内でルールに一致したエラーが、ルール名の1つのグループになります。 |
| **グループ化の対象外にする** | ルールに一致したエラーはグループを形成しません。それらのリクエストは引き続きREDメトリクスで失敗としてカウントされます。 |

ルールは順番に試行され、最初に一致したルールが適用されます。ルールを上下に移動して順序を変更できます。ルールは保存後に発生したエラーに適用され、すべてのノードで30分以内に反映され、既に作成されたグループには影響しません。ルールの編集中は、一覧表示されたグループのうち何件がルールに該当するかがフォームに表示されます。エラーグループのドロワーにある**このエラーからルールを作成**をクリックすると、グループの種類とサービスを引き継いだルールの作成が始まります。

## サービスレベル目標

サービスレベル目標（SLO）は、7日、28日、または30日のローリングウィンドウで、正常なリクエストの割合を保証するものです。1つの環境内のサービス、またはそのうち1つのエンドポイントを対象とします。**APM → SLO**を開いて**新規 SLO**をクリックするか、サービスの概要にある**サービスレベル目標**カードで**新規 SLO**をクリックします。

| フィールド | 意味 |
|---|---|
| **サービス**と**環境** | 目標が対象とするサービスを、1つの環境内で指定します。 |
| **エンドポイント** | サービスの1つのエンドポイントを指定します。サービス全体を対象とする場合は空のままにします。 |
| **成功条件** | **リクエストが成功**: リクエストが失敗しなかった場合に正常とみなします。**しきい値以内に成功**: リクエストが失敗せず、**レイテンシのしきい値 (ms)**以内に完了した場合に正常とみなします。 |
| **目標値 (%)** | 保証する正常なリクエストの割合で、0より大きく100未満の値です（例: `99.9`）。 |
| **適用期間** | 7日、28日、または30日で、現在を終点とします。 |

SLOはサービスのAPM集計データを参照するため、テールサンプリング前のすべてのリクエストをカウントします。

| 指標 | 意味 |
|---|---|
| **達成率** | ウィンドウ内の全リクエストに対する正常なリクエストの割合。 |
| **残りのエラーバジェット** | `1 - (1 - met) / (1 - objective)`。バジェットは、目標値が許容する異常なリクエストの割合です。目標値が破られると、この値はゼロ未満になります。 |
| **消費率** | 過去1時間、6時間、24時間における`(1 - met) / (1 - objective)`。`1×`の場合、バジェットはちょうどウィンドウと同じ期間持続します。 |
| **日別の達成状況** | ウィンドウ内の各UTC日を、達成、未達、またはリクエストなしとして示します。 |

| 状態 | 意味 |
|---|---|
| **違反** | **達成率**が目標値を下回っています。 |
| **違反のおそれあり** | 残りのバジェットが25%未満、過去1時間の消費率が14.4を超えている、または過去6時間の消費率が6を超えています。 |
| **正常** | 上記のいずれにも該当しません。 |
| **データなし** | ウィンドウにリクエストがありません。 |

レイテンシ目標はレイテンシのヒストグラムを参照するため、しきい値以内のリクエスト数はパーセンタイルと同程度（約4%以内）の精度です。ウィンドウは1時間ごとの集計データを参照し、消費率は1分ごとの集計データを参照します。1時間ごとの集計データの保持期間より長いウィンドウでは、保持されている日数のみがカウントされます。

### 消費率アラート

SLOのドロワーにある**消費率アラートを作成**をクリックすると、Google SREワークブックで推奨されている2つのアラートルールが追加されます。どちらも目標値に対するAPMアラートルールで、ルールのエスカレーションポリシーを通じて通知します。

| ルール | ウィンドウ | 発火条件 | 重要度 |
|---|---|---|---|
| 急速消費 | 1時間、およびその最後の5分 | 両方のウィンドウで消費率が14.4を超えている | Critical |
| 緩やかな消費 | 6時間、およびその最後の30分 | 両方のウィンドウで消費率が6を超えている | Warning |

短いウィンドウにより、既に収束したスパイクでルールが発火するのを防ぎます。ルールがSLOを監視するようになると、ドロワーにはボタンの代わりにそのルールが表示されます。ルールの作成には`alerts.rules.manage`が必要です。

SLOの作成には`apm.slos.manage`、削除には`apm.slos.delete`が必要です。SLOを削除すると、まずその消費率アラートが削除されます。これにも`alerts.rules.manage`が必要です。

## APM 指標のアラート

APMアラートルールは、サービスまたはそのエンドポイントの指標を監視します。指標はAPMページと同じ集計データから読み取られるため、クエリは不要です。

<Steps>
  <Step title="ルールエディタを開く">
    サービスページまたはエンドポイントドロワーのヘッダーで **新規アラート** を開き、**しきい値アラート** を選択します。エディタは **APMアラート** ソースで開き、サービス、環境、エンドポイントが入力された状態になります。 **アラート → アラートルール** から作成する新しいルールでも、同じソースを **APMアラート** として選択できます。ルールの作成には `alerts.rules.manage` が必要です。
  </Step>
  <Step title="指標を選択する">
    **サービス**、**環境** または **すべての環境**、**エンドポイント** または **サービス全体**、そして **指標** を選択します。しきい値は、エディタで指標の下に表示される単位で設定します。
  </Step>
  <Step title="テストして保存する">
    **ルールをテスト** をクリックすると、過去6時間の指標がしきい値とともにグラフに描画されます。その後ルールを作成します。
  </Step>
</Steps>

| 指標 | 単位 |
|---|---|
| **エラー率** | パーセント、0〜100 |
| **P50 レイテンシ**、**P90 レイテンシ**、**P95 レイテンシ**、**P99 レイテンシ**、**平均所要時間** | ミリ秒 |
| **スループット** | 1秒あたりのリクエスト数 |
| **リクエスト数**、**エラー** | ルールのウィンドウ内の件数 |
| **新規エラーグループ** | ルールのウィンドウ内で最初に検出された、サービスまたはエンドポイントのエラーグループ |
| **Apdex** | 0〜1 |
| **SLO バーンレート** | 目標で許容される速度の何倍か。SLOから設定します。 |

評価のたびにルールのウィンドウを読み取ります。24時間までは分単位の集計、それより長いウィンドウでは時間単位の集計を使用します。リクエストがないウィンドウでは、**リクエスト数**、**エラー**、**新規エラーグループ**、 **スループット** は `0` として読み取られるため、トラフィックが停止したことをルールで検知できます。その他の指標は値を持たず、しきい値に一致しないため、オープン中のインシデントは解決されます。

エディタまたはSLOから作成したルールには、指定した対象に対して `service.name`、`service.namespace`、 `deployment.environment`、`apm.endpoint` のラベルが付き、そのインシデントにも引き継がれます。すべてのAPMルールのインシデントには、`service` ラベル、`affected_services` 内のサービス、集計データから取得したサンプルトレースIDも付きます。カタログの **アラート** 列、サービスヘッダー、エンドポイントドロワーは、サービスを指定するオープン中および確認済みのインシデントを数えます。インシデントが環境を指定している場合はその環境内で数えます。エンドポイントドロワーは、そのエンドポイントのラベルが付いたインシデントのみを数えます。件数をクリックすると **アラート → インシデント** が開きます。

同じメニューの **異常検知アラート** は、指標が前日までの同じ時刻から外れたときにアラートを出します。設定するしきい値はありません。詳しくは [APM 指標の異常をアラートする](/ja/apm/insights#apm-指標の異常をアラートする) を参照してください。

## フィルター、解像度、保持期間

APMページはグローバルな時間範囲を共有します。カタログは環境とチームで、サービスページは環境とバージョンでフィルターできます。一覧は検索と並べ替えに対応しています。スコープはURLにエンコードされるため、ビューを共有したり再表示したりできます。

デフォルトのデプロイ設定では、次のようになります。

- APIで範囲を省略すると、過去24時間を使用します。
- `auto` 解像度では、24時間までの範囲は分単位のバケット、それより長い範囲は時間単位のバケットを使用します。
- 分単位の集計は24時間保持されます。
- 時間単位の集計とクエリの最大範囲は30日間です。

管理者はこれらのデプロイ上限を変更できます。バージョン比較は、両側が設定されたリクエストしきい値 (デフォルトでは各1,000リクエスト) に達した後にのみ十分とマークされます。

## データ品質の通知を確認する

すべてのAPMレスポンスにはデータ品質のメタデータが含まれます。通知すべき内容がある場合は、ナビゲーションカードに短い通知が表示され、クリックすると詳細が開きます。

| 通知 | 意味 |
|---|---|
| **範囲内にデータ開始時点あり** | APMの投影が選択した範囲内で開始されたため、それ以前のトラフィックは反映されていません。 |
| **データの一部欠損** | キュー、リポジトリ、フラッシュ、遅延データ、カーディナリティ、またはシャットダウンによる欠落が範囲の一部に影響しました。欠損データをゼロとして解釈しないでください。 |
| **データの遅延** | `lastCompleteBucketAt` が選択した範囲より前です。直近の集計はまだ確定中またはロールアップ中の可能性があります。 |
| **一部の名前を「その他」に集計** | カーディナリティの上限に達しました。上限を超えた名前は **その他** という行にまとめて集計されます。上限の設定は [APM 設定](/ja/apm/settings#カーディナリティ上限) にあります。 |

まず時間範囲とフィルターを絞ってください。一部欠損または遅延の状態が続く場合は、APM ヘルスエンドポイントと [APM 投影メトリクス](/ja/self-observability#apm-プロジェクション) を確認してください。

## プライバシーとデータの上限

APM は集計値と、サニタイズ済みの少量の証跡を保存します。APM は、リクエストボディ、レスポンスボディ、URL クエリの値、ヘッダー、SQL パラメータを APM の集計値に保持しません。SQL ステートメントはテンプレートとしてのみ保持され、すべてのリテラルは `?` になります。識別子の値、代表的なメッセージ、スタックフレームは長さが制限されます。機密性が高く見える値や変動の大きい値は、永続化の前に削除またはマスクされます。

これらの保護は、適切なインストルメンテーションの習慣に代わるものではありません。シークレットや個人データを、スパン名、ステータスの説明、例外メッセージ、リソース属性に配置しないでください。

## トラブルシューティング

| 症状 | 確認事項 |
|---|---|
| APM データがない | トレースが同じワークスペースに到達しているか、時間範囲に最近のトラフィックが含まれているか、アクティブなロールに `apm.services.read` があるかを確認してください。 |
| `unknown_service` | スパンがエクスポートされる前に、安定した `service.name` リソース属性を設定してください。 |
| エンドポイントが欠落している | `SERVER` または `CONSUMER` のスパン種別と、標準の HTTP、RPC、メッセージング属性を追加してください。 |
| 依存関係が欠落している | ダウンストリーム呼び出しの周囲に `CLIENT` または `PRODUCER` スパンを追加し、ターゲットのセマンティック属性を含めてください。 |
| バージョンが欠落している | デプロイ内のすべてのインスタンスで `service.version` を一貫して設定してください。 |
| エラーが欠落している | 例外イベントを記録し、OpenTelemetry の規約に従ってスパン、HTTP、RPC のステータスを設定してください。 |
| エラーサンプルからトレースが見つからない | トレースはサンプリング対象外または期限切れになっていますが、サンプリング前の APM 集計は有効なままです。 |
| ランタイムチャートがない | 同じ `service.name` で OpenTelemetry のランタイムメトリクスを送信してください。 |
| 結果が一部欠落または古い | データ品質の通知と `GET /api/v1/apm/health` を確認してください。 |
| 停止したサービスで APM アラートが発火しない | リクエストがない場合、エラー率、レイテンシ、Apdex には値がありません。トラフィックが停止する場合は **リクエスト数** または **スループット** を監視してください。 |
| SLO が **データなし** と表示される | サービスが SLO の環境でレポートしているか、エンドポイント名が **エンドポイント** リストと一致しているかを確認してください。 |
