MoleSignal APM は、バックエンドの OpenTelemetry トレーススパンを上限付きの RED 集計に変換します。メトリクスを別途計装せずに、応答の遅いサービス、エラーが発生するエンドポイント、処理負荷の高い依存先、繰り返し発生するバックエンドエラー、デプロイ済みバージョン間のリグレッションを特定できます。サービスカタログには、各サービスのオーナーと重要度を記録します。

<Note>
  APM に追加の SDK やテレメトリストリームは不要です。適切に計装されたトレースを送信してください。 MoleSignal は、トレースの重複排除後、テールサンプリング前に APM データを生成します。後からサンプリングで除外されるトレースも、APM メトリクスの集計に含まれます。 [リアルタイムパイプライン](/ja/pipelines#トレース)が破棄するスパンも同様です。
</Note>

## ページ

APM を開くと、概要が表示されます。各サービスには専用のページがあります。

| ページ | 用途 |
|---|---|
| **概要** | 全サービスの状況をまとめて確認できます。アクティブなサービス、スループット、エラー率、p95 と p50、p90、p99、平均値、Apdex、ヘルスステータスの内訳と推移、応答が最も遅いサービス、エラーが最も多いサービス、トラフィックが最も多いサービスを表示します。直前の同じ長さの期間および 1 週間前の同期間と比べた変動、その前後の変更、処理時間を短縮できる箇所についてのインサイトも表示します。サービスを指定したアクティブなアラート、期間内にデプロイされたバージョン、環境、各サービスで計装されていない項目も確認できます。 |
| **サービス** | APM が検出したサービスと明示的に登録したサービスをすべて表示するサービスカタログです。オーナー、ティア、タグ、アクティブなアラート、スループット、エラー率、レイテンシー、バージョン、最終デプロイを確認できます。お気に入りを先頭に表示し、アーカイブ済みのサービスは表示を有効にするまで非表示にします。 |
| **サービスマップ** | 環境内のサービスとサービス間の呼び出し、各サービスの呼び出し先、メッセージの発行先と購読元のトピックを表示します。直前の期間と比べて追加または消失した呼び出しも確認できます。[APM サービスマップ](/ja/apm/service-map#apm-のサービスマップ)を参照してください。 |
| **エラー** | 全サービスのバックエンドエラーグループと、そのステータス、チーム、担当者、発生箇所、グループ化ルールを表示します。 |
| **SLO** | サービスレベル目標と、各評価期間の達成状況、残りのエラーバジェット、バジェットの消費率、ステータスを表示します。 |
| **設定** | 組織のヘルス判定しきい値、デフォルトの Apdex しきい値、長時間タスク、カタログ要件、命名ルール、環境マッピング、エイリアスを、過去 1 日のデータに基づく情報とともに表示します。プラットフォームのカーディナリティ上限とトレースサンプリングも確認できます。[APM 設定](/ja/apm/settings)を参照してください。 |

サービスページには、次のセクションがあります。

| セクション | 用途 |
|---|---|
| **概要** | リクエスト数、エラー率、レイテンシーを並べて表示します。サービスのインサイト、レイテンシーの分布、ダウンストリームで費やした時間、影響の大きいエンドポイントとエラー、サービスの SLO も確認できます。 |
| **エンドポイント** | HTTP、RPC、メッセージング、ワーカーのエントリーポイントを、リクエスト数、エラー数、レイテンシー、処理時間の割合で並べ替えます。エンドポイントを開くと、ドロワーにステータスコード、処理時間の内訳、最も遅いリクエストが表示されます。主要トランザクションには星印が付きます。主要トランザクションまたは長時間タスクだけに絞り込めます。 |
| **トレース** | サービスが関与したトレースを、トレースページのトレーステーブルに表示します。 |
| **依存関係** | サービスの呼び出し元と、呼び出し先ごとにグループ化した外部呼び出しを表示します。呼び出し先ごとの操作とヘルスステータス、タイムアウトや再試行が発生した呼び出し、最も遅い SQL ステートメントも確認できます。 |
| **エラー** | サービスのエラーグループを表示します。 |
| **デプロイ** | パイプラインからの報告と、スパンに含まれるバージョンを並べて表示します。ロールバックを明示し、各バージョンと直前のバージョンの比較や、同時に稼働する 2 つのバージョンの並列表示、任意の 2 つのバージョンの比較ができます。[デプロイ](/ja/apm/deployments)を参照してください。 |
| **ランタイム** | サービスを実行したインスタンスと、各インスタンスが処理した内容を表示します。プロセスとサービスの実装言語のランタイムメトリクスを使ったグラフや、プロファイルから生成したフレームグラフも確認できます。 |
| **設定** | サービスのカタログエントリーと主要トランザクションを、インスタンスからの報告内容と並べて表示します。 |

サービス名の下の行には、表示中の環境とバージョンに応じてサービスの詳細が表示されます。

| 項目 | 情報源 |
|---|---|
| ヘルスステータス | 表示期間の RED 指標に基づきます。カーソルを合わせると判定理由を表示します。リクエストがない期間は、代わりに **この期間のデータはありません** と表示します。テレメトリがないことは、サービスに異常があることを意味しません。 |
| ティア | カタログエントリーの情報です。 |
| システムと環境 | `service.namespace` と `deployment.environment.name` です。 |
| タイプ | サービスが処理するエントリースパンの種類です。**HTTP**、**RPC**、メッセージの場合は **コンシューマー**、内部エントリースパンの場合は **ワーカー** と表示します。 |
| 言語とフレームワーク | `telemetry.sdk.language` と、サービスのエントリースパンを生成した計装ライブラリに基づきます。Axum、Spring、Express などが該当します。 |
| バージョン | 選択したバージョン、または期間内にインスタンスで稼働したすべてのバージョンを表示します。複数ある場合は、最も多くのインスタンスで稼働したバージョンが先頭です。ロールアウト中は両方のバージョンを表示します。 |
| チーム | カタログエントリーの情報です。チームにカーソルを合わせると、オーナーとオンコール担当者を表示します。 |
| インスタンス | 表示中のバージョンのうち、期間内にテレメトリを報告したインスタンスです。選択すると **ランタイム** が開きます。 |
| 最終デプロイ | 表示中のバージョン、または最新バージョンを最初に検出した日時です。 |
| リージョン | インスタンスの `cloud.region` です。 |
| リポジトリ | インスタンスの `vcs.repository.url.full` または `git.repository_url` です。どちらもない場合は、カタログエントリーのリポジトリを表示します。 |
| 別名 | カタログエントリーに登録された別名のうち、最初の 1 件と残りの件数を表示します。 |

アーカイブ済みのサービスには、同じ行に **アーカイブ済み** とも表示されます。タイトル行の末尾にある **お気に入り** を選択すると、サービスをお気に入りに登録できます。

ナビゲーションカードの末尾に、サービスのログ、メトリクス、プロファイルへのリンクがあります。表示期間の終了時点からさかのぼった 1 日間に、該当するシグナルにサービスのデータがあれば、リンクが強調表示されます。 MoleSignal は 5 分ごとにデータの有無を再確認します。

| シグナル | 強調表示の条件 |
|---|---|
| ログ | `service.name`、`service_name`、`service` のいずれかのフィールドを持つログストリームに、サービスのログ行が含まれています。リンクを選択すると、該当するストリームのログが開きます。 |
| メトリクス | 過去 1 時間の時系列データに、サービスの `service.name` が含まれています。 |
| プロファイル | プロファイルストリームにサービスのプロファイルが含まれています。 |
| RUM | ブラウザーセッションがサービスのサンプルトレースのいずれかを生成しています。この場合にのみリンクを表示し、選択すると該当するセッションが開きます。 |

データがないシグナルのリンクは薄く表示されます。選択すると、そのシグナルを接続する **データソース** ページが開きます。確認に失敗するか、 3 秒を超える場合は、リンクを強調表示も薄く表示もしません。

## 前提条件

- MoleSignal の[トレース取り込みエンドポイント](/ja/intake)への OpenTelemetry トレースの送信。
- 組織のワークスペースでの `apm.services.read` 権限、または
- 保護された `_sys` テレメトリに対する `sys.telemetry.read` 権限。

## APM 向けにサービスを計装する

<Steps>
  <Step title="サービスのリソース属性に安定した値を設定する">
    すべてのサービスに `service.name` を設定します。サービスのフィルタリングやデプロイの比較に使うため、名前空間、環境、バージョン、インスタンスの属性を追加します。

    ```bash
    export OTEL_SERVICE_NAME=checkout
    export OTEL_RESOURCE_ATTRIBUTES="service.namespace=shop,deployment.environment.name=production,service.version=2.4.0,service.instance.id=checkout-01"
    ```

    設定手順は、使用する OpenTelemetry SDK または Collector によって異なります。
  </Step>
  <Step title="適切なスパン種別を使用する">
    受信リクエストには `SERVER` スパンを、消費したメッセージには `CONSUMER` スパンを作成します。ダウンストリームへの呼び出しには `CLIENT` または `PRODUCER` スパンを作成します。MoleSignal はこれらのスパン種別を使ってトランザクションと依存関係を区別します。
  </Step>
  <Step title="ステータスと例外を記録する">
    OpenTelemetry のスパンステータスと HTTP または RPC のステータス属性を設定し、例外イベントを記録します。MoleSignal は記録したステータスデータを使って処理の成功と失敗を分類し、バックエンドのエラーグループを作成します。
  </Step>
  <Step title="トレースを送信して APM を開く">
    OTLP トレースを送信し、**APM → サービス**を開きます。プロジェクターが最初のバケットを書き出す間は、グローバル時間範囲に直近のトラフィックが含まれるようにしてください。
  </Step>
</Steps>

### 推奨リソース属性

| 属性 | 用途 | フォールバック |
|---|---|---|
| `service.name` | サービスを一貫して識別します。すべてのサービスで明示的に設定してください。 | `unknown_service` |
| `service.namespace` | システムやチームが異なる同名のサービスを区別します。 | `default` |
| `deployment.environment.name` | 本番、ステージングなどの環境でフィルタリングします。 | 旧属性の `deployment.environment`、なければ `unknown` |
| `service.version` | バージョン履歴の確認やデプロイの比較ができます。 | バージョン別の内訳なし |
| `service.instance.id` | インスタンスを区別します。 | `k8s.pod.name`、なければ `host.name` |
| `telemetry.sdk.language` | サービスカタログにランタイムの言語を表示します。 | `process.runtime.name` が設定されていればその値 |
| `cloud.region`, `k8s.*`, `host.name`, `container.name`, `container.id` | 各インスタンスの実行場所を示します。 | 表示なし |
| `process.runtime.name`, `process.runtime.version` | 各インスタンスのランタイムを表示します。 | 表示なし |
| `vcs.repository.url.full`, `vcs.ref.head.revision` | リポジトリにリンクし、コミットを特定します。`git.repository_url` と `git.commit.sha` も使えます。 | カタログエントリのリポジトリ |

Kubernetes の属性と `cloud.region` は通常、SDK ではなく OpenTelemetry Collector の `k8sattributes` と `resourcedetection` プロセッサーが追加します。

カーディナリティの低い値を使ってください。リクエスト ID、生の URL、ユーザー ID など、値の種類が際限なく増えるものは、サービス、環境、バージョン、ルート、オペレーション、依存関係の属性に設定しないでください。

## MoleSignal が APM データを生成する仕組み

### サービスとエンドポイント

`SERVER` スパンと `CONSUMER` スパンを、サービスとエンドポイントの RED メトリクスに集計します。API ではエンドポイントをトランザクションと呼びます。親も種別もないスパンは、互換性のためにサービス全体の集計に含める場合があります。ただし、種別を明示すると、ページにより完全なデータが表示されます。

MoleSignal はセマンティック属性から、種類が増えすぎないようにエンドポイント名を生成します。

- `POST /checkout` のような HTTP メソッドと `http.route` の組み合わせ
- RPC サービスとメソッドの組み合わせ
- メッセージングのオペレーションと宛先の組み合わせ
- より明確に識別できるセマンティック属性がない場合は、安全でカーディナリティの低いスパン名

`/orders/83921` のような生のパスよりも、`/orders/{id}` のようなルートテンプレートを優先してください。

### 依存関係

`CLIENT` スパンと `PRODUCER` スパンを、依存関係の RED メトリクスに集計します。MoleSignal はターゲットをサービス、データベース、キャッシュ、メッセージングシステム、外部 HTTP エンドポイント、外部 RPC エンドポイント、その他の依存関係に分類します。標準の `peer.service`、`db.*`、`messaging.*`、`rpc.*`、`server.*`、および HTTP のセマンティック属性を使うと、依存関係をより正確に識別できます。

`peer.service` がないデータベースやキャッシュの呼び出しでは、`postgresql` や `redis` など、システム名をターゲットに使います。[`MS_TRACE_FINGERPRINT_KEY`](/ja/configuration#環境変数) を設定すると、ターゲットには `db.namespace`（なければ `db.name` または `db.collection.name`）からキーを使って生成したフィンガープリントも付きます。たとえば `postgresql:<fingerprint>` のようになり、同じシステム内のデータベースを、名前を保存せずに区別できます。

SQL データベースの呼び出しでは、ステートメントをテンプレート化してオペレーション名に使います。`db.query.summary` を優先し、なければ `db.query.text` または `db.statement` を使います。すべてのリテラルを `?` に置き換え、コメントを削除し、値のリストは 1 つの `?` にまとめ、最大 512 bytes を保持します。二重引用符で囲まれたテキストは、 PostgreSQL や Oracle のようにテーブル名や列名を表すデータベースでのみ保持し、それ以外では値として扱います。ステートメントがない呼び出しでは `db.operation.name` を、キャッシュの呼び出しではコマンドを使います。サービスは 1 時間あたり、ターゲットごとに最大 32 件のオペレーションを保持し、それを超えた分は同じターゲットの **その他** にまとめて集計します。

タイムアウトしたリクエスト（タイムアウトのエラータイプ、gRPC の `DEADLINE_EXCEEDED`、HTTP 408 または 504）と、再送されたリクエスト（`http.request.resend_count` が 0 より大きいもの）は、RED メトリクスとは別に集計します。

### エラー

MoleSignal は、例外がある場合、OpenTelemetry のステータスが `ERROR` の場合、HTTP ステータスが 500 以上の場合、または RPC ステータスが 0 以外の場合に、スパンをエラーとして分類します。エラーグループには、エラータイプ、最初のアプリケーションスタックフレーム、トランザクション名に基づく安定したフィンガープリントを使います。変動するエラーメッセージはフィンガープリントに含めません。[グループ化ルール](#ルールでエラーをグループ化する)を使うと、エラーを 1 つのグループにまとめたり、グループ化の対象から除外したりできます。

## RED メトリクスについて

| メトリクス | 意味 |
|---|---|
| **リクエスト数** | 対象のサービス、エンドポイント、または依存関係で観測したリクエストの件数です。 |
| **エラー率** | エラー件数をリクエスト数で割った値です。 |
| **レイテンシー** | 統合したレイテンシーヒストグラムから算出する p50、p90、p95、p99 と、平均所要時間です。 |
| **Apdex** | しきい値 T 以内のリクエスト数に、T を超え 4T 以内のリクエスト数の半分を加え、全リクエスト数で割った値です。T には組織のデフォルト値（[APM 設定](/ja/apm/settings#ヘルスとしきい値)で変更していない場合は 500 ms）か、サービスのカタログエントリで設定した値を使います。レイテンシー分布には、使用中の T が表示されます。概要では、組織のデフォルト値ですべてのサービスをまとめて集計します。失敗したリクエストは満足とみなさず、失敗件数をレイテンシー分布全体に均等に割り振って差し引きます。 |
| **合計時間** | 観測した所要時間の合計です。累積の影響が最も大きい処理を把握できます。 |

[APM 設定](/ja/apm/settings#ヘルスとしきい値)でしきい値を変更していなければ、エラー率が 2% 以上または p95 が 500 ms 以上で **警告**、エラー率が 10% 以上または p95 が 2 s 以上で **クリティカル**になります。サービスページとカタログのステータスを示すドットでは、どの指標がどのしきい値に達したかを確認できます。

**インサイト**カードには、直前の同じ長さの期間および 1 週間前の同じ時間範囲と比べて、どのサービスに変化があったかが表示されます。[インサイトが検出する内容](/ja/apm/insights#インサイトの検出項目)を参照してください。

レイテンシーヒストグラムでは、125 µs から約 131 s まで、レイテンシーが 2 倍になるごとの区間を 8 個のバケットに分割し、該当するバケット内でパーセンタイルを算出します。パーセンタイルの誤差は正確な値の約 4% 以内です。以前の固定バケットで記録した集計値も、従来の粗い精度のまま参照できます。

概要とエンドポイントのドロワーにある **比較対象** では、1 日前または 1 週間前の同じ時間範囲のデータを破線で表示し、レイテンシー分布にはその範囲の分布を輪郭線で表示します。サービスページでは、そのサービスの他の環境も選べます。環境を選ぶと、その環境の同じ時間範囲のデータを代わりに破線で表示します。

エンドポイントで最も遅いリクエストはトレースストアから取得するため、一覧の各リクエストから対応するトレースを開けます。エラーサンプルが、テールサンプリングで破棄されたトレースを参照することがあります。その場合、トレースのドロワーにはトレースが見つからなかったことを示すメッセージが表示されます。

## サービスカタログ

カタログには、APM が検出したすべてのサービスがサービスと環境の組み合わせごとに 1 行ずつ表示されます。データをまだ送信していない登録済みサービスも表示されます。カタログの **サービスを登録** と、サービスページの **設定** セクションでは、次の項目を設定できます。

| フィールド | 説明 |
|---|---|
| **担当チーム** | ワークスペース内のチームです。チームで有効になっている最初のオンコールスケジュールで、現在のオンコール担当者を特定します。 |
| **オーナー** | サービスに責任を持つワークスペースのメンバーです。 |
| **ティア** | サービスの重要度です。最も重要な P0 から P5 まで設定できます。 |
| **ライフサイクル** | 本番、ステージング、実験段階、または非推奨です。 |
| **リポジトリ** | コードの保存先です。サービスがリポジトリを報告しない場合に使用します。HTTPS アドレス、または `git@github.com:acme/checkout.git` や `ssh://git@git.example.com/team/checkout.git` などの Git アドレスを指定します。アドレス内のパスワードは `****` として保存します。HTTPS アドレスのユーザー部分も、Git がトークンを含めることがあるため、同様にマスクします。サービスページで Git アドレスを開くと、同じパスの HTTPS ページが開きます。 |
| **タグ** | `key=value` のペアまたはキーのみを、カンマで区切って指定します。キーには小文字の英字、数字、`_ . - /` を最大 64 文字使用できます。値は最大 128 文字です。タグは最大 32 個です。 |
| **Apdex しきい値 T** | サービスの Apdex しきい値をミリ秒単位で指定します。上限は 1 分です。空欄の場合は組織のデフォルト値を使用します。APM の設定で変更していなければ 500 ms です。 |
| **サービスの機能** | サービス名の下に表示する短い説明です。 |
| **別名** | ログ、メトリクス、その他のシステムで使うサービス名です。`order_service` や Order Center などをカンマで区切って指定します。最大 20 個、各 128 文字までです。サービス自身の名前や、別のサービスの名前または別名は指定できません。カタログでは別名でもサービスを検索できます。 |
| **データソース** | サービスのログを含むログストリーム、`{service="checkout"}` などのメトリクス用 PromQL セレクター、サービスの情報を表示するダッシュボード、ランブックや CMDB エントリなどの外部ページへのリンクを指定します。ログストリームごとに、サービスのログを抽出する SQL 条件を任意で指定できます。各種類につき最大 10 件です。各行を選択すると、対応するデータが **ログ**、**メトリクス**、ダッシュボード、または新しいタブで開きます。 |

**別名** と **データソース** は、カタログで確認できるほか、Mole Agent も使用します。サービスについて質問を受けると、Mole Agent は両方の項目を含むカタログエントリを参照します。APM に関する質問で別名を指定した場合も、その別名に対応するサービスを参照します。これらの設定でデータが統合されることはありません。旧サービス名で報告されたデータを現在のサービスのデータとして参照するには、代わりに[サービスエイリアス](/ja/apm/settings#サービスエイリアス)を追加します。

同じフォームの **アーカイブ** を選択すると、サービスはカタログのデフォルトビューに表示されなくなります。データの収集は継続し、サービスページも引き続き開けます。カタログで **アーカイブ済み** を選択すると、アーカイブしたサービスも一覧に表示されます。

[カタログの要件](/ja/apm/settings#カタログの必須項目)では、指定したティア以上のサービスに対して、担当チーム、オーナー、またはリポジトリの登録を必須にできます。要件を満たしていないサービスには、カタログで **要対応** と表示され、不足している項目が示されます。

サービス定義は名前空間と名前で識別するため、すべての環境に適用されます。カタログとエンドポイントテーブルの **列** メニューでは、表示する列とその順序を設定できます。設定はユーザーごとに保存されます。カタログには、集計値とカタログの項目に加え、対象期間内のインスタンスから取得した **タイプ**、**言語 / フレームワーク**、**インスタンス**、**リージョン** や、 **タグ**、**最終検出** も表示できます。

カタログの行にある星を選択すると、サービスをお気に入りに追加できます。お気に入りのサービスはカタログの先頭に表示され、**お気に入り** を選択すると該当するサービスだけが表示されます。お気に入りはユーザーごとに保存されます。**グループ** では、行をチーム、名前空間、ティア、またはタグの値でグループ化できます。カタログは環境やチームで絞り込めます。名前空間やタグが複数ある場合は、それらでも絞り込めます。フィルターとグループ化の設定は URL に含まれるため、共有リンクを開くと同じビューが表示されます。対象期間内に検出されたサービスでも、期間終了時点で 1 日以上データを報告していなければ、**非アクティブ** と表示されます。

主要トランザクションは、特に重要なエンドポイントです。エンドポイント一覧または詳細ドロワーで星を選択すると登録できます。**設定** には、サービスの主要トランザクションと、対象期間内の各トランザクションの処理実績が表示されます。サービスごとに最大 50 件まで登録できます。

サービスのドキュメントとランブックは、Mole Agent のナレッジベースの `services/<service name>/` に格納します。組織または担当チームのナレッジベースを使用します。サービスページの **ドキュメント** にはこれらのファイルが一覧表示され、ここからランブックを開始できます。Mole Agent はサービスを調査するときに、同じファイルを参照します。

サービス定義と主要トランザクションの編集には `apm.definitions.manage`、エラーの状態の変更には `apm.errors.manage` が必要です。オーナー、管理者、編集者にはこれらの権限があります。

## インスタンス

サービスのデータを報告する各プロセスがインスタンスです。インスタンスは `service.instance.id` で識別し、なければ `k8s.pod.name`、それもなければ `host.name` を使用します。MoleSignal はインスタンスのスパンを 1 分に 1 回確認し、バージョンと上の表の属性について、最後に報告された値を保持します。リポジトリへのリンクは、ユーザー名、パスワード、クエリを含まない HTTPS アドレスとして保存します。各インスタンスの処理実績（リクエスト数、エラー数、レイテンシー）は、サービスの集計と同じスパンを使い、インスタンスごとに個別のバケットで集計します。

**ランタイム** には、表示中の期間とバージョンに該当するインスタンスが、最終検出日時の新しい順に並びます。スループット、エラー率、p95 に加え、Pod（なければホスト）で絞り込んだインスタンスのログへのリンクと、識別に使うラベルで絞り込んだメトリクスへのリンクが表示されます。サービスごとの 1 時間あたりのインスタンス数が上限を超えた場合、超過分は **その他のインスタンス** にまとめて集計します。これにより、インスタンスの合計はサービス全体の集計と一致します。インスタンスを選択すると、ランタイムのチャートがそのインスタンスに絞られ、選択内容は URL に反映されます。 1 時間単位の集計データの保持期間にわたって検出されなかったインスタンスは削除されます。

## エンドポイントの詳細

エンドポイントの詳細ドロワーでは、RED チャートに加えて 2 つのカードを表示します。

- **ステータスコード** は、レスポンスをコード別に集計します。HTTP コードは `http.response.status_code` （古い計装では `http.status_code`）、gRPC コードは `rpc.grpc.status_code` から取得します。それぞれクラス別に色分けし、推移を表示します。1 バケットあたり最大 24 種類のコードを保持し、それを超える分は **その他の HTTP** または **その他の gRPC** にまとめます。ステータスコードの集計を開始する前の集計データには、コードが含まれません。
- **処理時間の内訳** は、対象期間内にエンドポイントが処理した最新のリクエストをトレースストアから最大 200 件取得し、各リクエストの配下にあるスパンを読み取ります。呼び出しにかかった時間は、呼び出し先に応じてデータベース（`db.system.name`）、キャッシュ（Redis、Memcached、Valkey）、HTTP、RPC、メッセージングに分類します。呼び出し先の情報がない場合は **その他** に分類します。内部スパンは内部処理として集計し、リクエスト配下のどのスパンにも含まれない時間はリクエスト自体の処理時間として扱います。項目ごとに、全体に占める割合とリクエストあたりの処理時間を表示します。並列呼び出しの合計時間がリクエスト全体の処理時間を超える場合は、各項目を比例配分して全体の処理時間に合わせます。テールサンプリングで保持したトレースのみを読み取ります。

エンドポイント一覧の **ロングタスク** には、p99 が 1 秒以上のエンドポイントが表示されます。スケジュール済みジョブやメッセージング操作を伴わないキューワーカーなど、内部種別のエントリースパンは **ワーカー** として表示されます。

## デプロイ

サービスページの **デプロイ** セクションでは、パイプラインが報告したデプロイと、サービスのスパンに記録されたバージョンを並べて表示します。ロールバックを明示し、各バージョンを直前のバージョンと比較できます。同時に稼働する 2 つのバージョンも並べて確認できます。パイプラインは `POST /api/v1/apm/deployments` でデプロイを報告します。[デプロイ](/ja/apm/deployments)を参照してください。

## 依存関係

サービスの **依存関係** タブでは、依存先ごとに 100 点満点の健全性スコアを表示します。呼び出しの失敗率 1 パーセントポイントにつき 4 点（最大 60 点）、タイムアウト率 1 パーセントポイントにつき 4 点（最大 20 点）を差し引きます。期間を比較している場合は、P95 の増加率が 20% を超えた分について、1 パーセントポイントにつき 0.5 点（最大 20 点）を差し引きます。90 点以上は良好、70 点以上 90 点未満は要確認です。スコアのツールチップには減点理由が表示されます。 **比較対象** を設定すると、依存先ごとにエラー率と P95 の変化も表示されます。**遅いSQL** には、 P95 が最も高いデータベースステートメントがテンプレート形式で表示されます。

## バックエンドエラーを追跡する

エラーグループは、**調査中**、**解決済み**、**無視**のいずれかに設定するまで、未対応のままです。各グループにはチームと、担当者としてワークスペースのメンバーを割り当てられます。解決済みのグループでエラーが再び発生すると、 **再発**と表示されます。**APM → エラー**には、デフォルトで未解決のグループが表示されます。対象は未対応、調査中、再発のグループです。

一覧の上にある**発生箇所の内訳**には、一覧に含まれるグループの発生回数がバージョン、環境、サービスのプログラミング言語別に表示されます。各エラーグループのドロワーには、そのグループの内訳が表示されます。ドロワーの**関連ログ**を選択すると、対象サービスと時間範囲のログが開きます。サンプルの横にある**ログ**を選択すると、そのサンプルのトレースに対応するログが開きます。

### ルールでエラーをグループ化する

エラー一覧の**グループ化ルール**では、エラーの種類、フレーム、エンドポイントによる標準のグループ化に加えて、独自の条件を設定できます。ルールでは、特定のサービスまたはすべてのサービスを対象に、エラーの種類、メッセージ、エラーがスローされたフレーム、エンドポイントのパターンを指定します。各パターンは大文字と小文字を区別せず、文字列全体と照合します。 `*` は任意の文字列に一致します。空欄のパターンはどの値にも一致しますが、ルールには少なくとも1つのパターンを入力する必要があります。

| 操作 | 効果 |
|---|---|
| **1つのグループに統合** | サービス内でルールに一致するエラーを、ルールで指定した名前の1つのグループに統合します。 |
| **グループ化の対象外にする** | ルールに一致するエラーをグループ化しません。該当するリクエストは引き続き RED メトリクスで失敗としてカウントします。 |

ルールは上から順に評価し、最初に一致したルールを適用します。順序を変えるには、ルールを上下に移動します。保存後30秒以内にすべてのノードにルールが反映され、保存後に観測したエラーに適用されます。既存のグループは変更しません。ルールの編集中は、一覧にあるグループのうち条件に一致する件数をフォームに表示します。エラーグループのドロワーで**このエラーからルールを作成**を選択すると、グループのエラーの種類とサービスが設定された状態でルールの作成を開始できます。

## サービスレベル目標

サービスレベル目標 (SLO) は、直近7日間、28日間、または 30日間の適用期間について、成功条件を満たすリクエストの割合を定めます。対象は、1つの環境内のサービス全体またはそのエンドポイント1つです。**APM → SLO**を開いて **新規 SLO**をクリックするか、サービス概要の**サービスレベル目標**カードで**新規 SLO**をクリックします。

| フィールド | 意味 |
|---|---|
| **サービス**と**環境** | 目標の対象となるサービスと、その環境です。 |
| **エンドポイント** | サービスのエンドポイントを1つ指定します。サービス全体を対象にする場合は空欄にします。 |
| **成功条件** | **リクエストが成功**: リクエストが失敗しなければ、成功条件を満たします。**しきい値以内に成功**: リクエストが失敗せず、処理時間が**レイテンシのしきい値 (ms)** 以下であれば、成功条件を満たします。 |
| **目標値 (%)** | 成功条件を満たすリクエストの割合の目標値です。`99.9` など、0より大きく100未満の値を指定します。 |
| **適用期間** | 現在を終点とする7日間、28日間、または30日間です。 |

SLO は対象サービスの APM 集計データを使用するため、テールサンプリング前のすべてのリクエストをカウントします。

| 指標 | 意味 |
|---|---|
| **達成率** | 適用期間の全リクエストに占める、成功条件を満たしたリクエストの割合です。 |
| **残りのエラーバジェット** | `1 - (1 - met) / (1 - objective)`。エラーバジェットは、成功条件を満たさなくても目標を達成できるリクエストの割合です。目標に違反すると、この値は0を下回ります。 |
| **消費率** | 直近1時間、6時間、24時間それぞれの `(1 - met) / (1 - objective)` です。`1×` では、適用期間と同じ長さの時間でエラーバジェットを使い切ります。 |
| **日別の達成状況** | 適用期間内の各日 (UTC) を、達成、未達成、またはリクエストなしで表示します。 |

| 状態 | 意味 |
|---|---|
| **違反** | **達成率**が目標値を下回っています。 |
| **違反のおそれあり** | エラーバジェットの残りが25%未満、直近1時間の消費率が14.4超、または直近6時間の消費率が6超です。 |
| **正常** | 上記のいずれにも該当しません。 |
| **データなし** | 適用期間にリクエストがありません。 |

レイテンシの目標にはレイテンシのヒストグラムを使用します。そのため、しきい値以内のリクエスト数はパーセンタイルと同程度の精度で、誤差は約4%以内です。適用期間の集計には1時間単位のデータを、消費率の計算には 1分単位のデータを使用します。適用期間が1時間単位の集計データの保持期間より長い場合は、データが保持されている日だけを集計します。

### 消費率アラート

SLO のドロワーで**消費率アラートを作成**を選択すると、Google SRE ワークブックが推奨する2つのアラートルールを追加します。どちらも対象の SLO を監視する APM アラートルールで、各ルールのエスカレーションポリシーに従って通知します。

| ルール | 適用期間 | 発火条件 | 重大度 |
|---|---|---|---|
| 急速な消費 | 直近1時間と、その最後の5分間 | 両方の期間で消費率が14.4を超える | クリティカル |
| 緩やかな消費 | 直近6時間と、その最後の30分間 | 両方の期間で消費率が6を超える | 警告 |

短い期間も確認することで、すでに収まった急上昇でルールが発火するのを防ぎます。ルールが SLO を監視するようになると、ドロワーにはボタンの代わりにルールが表示されます。ルールの作成には `alerts.rules.manage` が必要です。

SLO の作成や更新には `apm.slos.manage`、削除には `apm.slos.delete` が必要です。SLO を削除すると、先に関連する消費率アラートを削除するため、 `alerts.rules.manage` も必要です。

## APMの指標でアラートを設定する

APMアラートルールは、サービスまたはそのエンドポイントの指標を監視します。APMページと同じ集計データを使うため、クエリは不要です。

<Steps>
  <Step title="ルールエディターを開く">
    サービスページのヘッダーまたはエンドポイントのドロワーで **新規アラート** を開き、**しきい値アラート** を選択します。エディターが開き、ソースに **APMアラート** が選択され、サービス、環境、エンドポイントが入力済みになります。 **アラート → アラートルール** で新規ルールを作成する場合も、ソースとして **APMアラート** を選択できます。ルールを作成するには `alerts.rules.manage` 権限が必要です。
  </Step>
  <Step title="指標を選択する">
    **サービス**、**環境** または **すべての環境**、**エンドポイント** または **サービス全体**、そして **指標** を選択します。エディターで指標の下に表示される単位でしきい値を設定します。
  </Step>
  <Step title="テストして保存する">
    **ルールをテスト** をクリックして過去6時間の指標の推移としきい値をグラフで確認し、ルールを作成します。
  </Step>
</Steps>

| 指標 | 単位 |
|---|---|
| **エラー率** | パーセント（0～100） |
| **P50 レイテンシ**、**P90 レイテンシ**、**P95 レイテンシ**、**P99 レイテンシ**、**平均所要時間** | ミリ秒 |
| **スループット** | 秒あたりのリクエスト数 |
| **リクエスト数**、**エラー** | ルールの評価期間内の件数 |
| **新規エラーグループ** | ルールの評価期間内に初めて検出された、サービスまたはエンドポイントのエラーグループ数 |
| **Apdex** | 0～1 |
| **SLO バーンレート** | 目標が許容するエラーバジェット消費速度に対する倍率。SLOから設定します。 |

評価のたびに、ルールの評価期間に対応する集計データを読み取ります。24時間までは分単位の集計を、それより長い期間には時間単位の集計を使います。リクエストがない期間は、**リクエスト数**、**エラー**、**新規エラーグループ**、 **スループット** が `0` になるため、ルールでトラフィックの停止を検知できます。この場合、その他の指標には値がなく、しきい値の条件は成立しません。オープン中のインシデントは解決済みになります。

エディターまたはSLOから作成したルールには、指定した対象に応じて `service.name`、`service.namespace`、 `deployment.environment`、`apm.endpoint` のラベルが付きます。インシデントにも同じラベルが引き継がれます。すべてのAPMルールのインシデントには、`service` ラベル、`affected_services` に記録されるサービス、集計データから取得したサンプルトレースIDも含まれます。カタログの **アラート** 列、サービスのヘッダー、エンドポイントのドロワーには、対象サービスを指定するオープン中および確認済みのインシデントの件数が表示されます。インシデントに環境の指定がある場合は、その環境でのみ集計します。エンドポイントのドロワーでは、そのエンドポイントのラベルが付いたインシデントのみを集計します。件数をクリックすると **アラート → インシデント** が開きます。

同じメニューの **異常検知アラート** は、過去数日の同じ時刻と比べて指標が通常の範囲から外れるとアラートを発報します。しきい値の設定は不要です。詳しくは、 [APM指標の異常をアラートで検知する](/ja/apm/insights#apm-指標の異常をアラートで通知する)を参照してください。

## フィルター、解像度、保持期間

APMページはグローバルの時間範囲を共有します。カタログでは環境とチームでフィルタリングでき、サービスページでは環境とバージョンでフィルタリングできます。一覧では検索と並べ替えができます。表示範囲はURLに含まれるため、同じビューを共有したり、後から開き直したりできます。

デフォルトのデプロイ設定では、次のようになります。

- APIで時間範囲を省略すると、過去24時間を使用します。
- 解像度が `auto` の場合、24時間までの範囲には分単位のバケットを、それより長い範囲には時間単位のバケットを使います。
- 分単位の集計データは24時間保持します。
- 時間単位の集計データの保持期間とクエリの最大範囲は、どちらも30日です。

管理者はこれらのデプロイ上の制限を変更できます。バージョン比較では、比較する両方のバージョンがリクエスト数のしきい値に達した場合にのみ、データが十分であると表示します。しきい値のデフォルトは、各バージョンで1,000リクエストです。

## データ品質の通知を確認する

すべてのAPMレスポンスには、データ品質のメタデータが含まれます。通知事項がある場合は、ナビゲーションカードに短い通知が表示されます。通知をクリックすると詳細が開きます。

| 通知 | 意味 |
|---|---|
| **範囲内にデータ開始時点あり** | 選択した範囲内でAPMプロジェクションが開始されたため、それより前のトラフィックは反映されていません。 |
| **データの一部欠損** | キュー、リポジトリ、フラッシュ、データの遅着、カーディナリティ、またはシャットダウンに起因する欠損が、範囲の一部に影響しました。欠損データをゼロとして扱わないでください。 |
| **データの遅延** | `lastCompleteBucketAt` が選択した範囲に追いついていません。直近の集計データは、バケットの確定や上位粒度への集約がまだ完了していない可能性があります。 |
| **一部の名前を「その他」に集計** | カーディナリティの上限に達しました。上限を超えた名前は **その他** という行にまとめて集計します。上限は [APM設定](/ja/apm/settings#カーディナリティの上限)を参照してください。 |

まず、時間範囲とフィルター条件を絞り込んでください。欠損や遅延が続く場合は、APMのヘルスエンドポイントと [APMプロジェクションのメトリクス](/ja/self-observability#apm-プロジェクション)を確認してください。

## プライバシーとデータの上限

APM は、集計データとサニタイズ済みの診断データを少量保存します。APM の集計データには、リクエストやレスポンスのボディ、URL のクエリパラメーターの値、ヘッダー、SQL パラメーターを保持しません。SQL 文は、すべてのリテラルを `?` に置き換えたテンプレートとしてのみ保存します。識別子の値、代表的なメッセージ、スタックフレームには長さの上限を適用します。機密情報とみられる値や変動しやすい値は、永続化する前に削除またはマスクします。

これらの保護対策を適用していても、適切な計装は必要です。スパン名、ステータスの説明、例外メッセージ、リソース属性には、シークレットや個人データを含めないでください。

## トラブルシューティング

| 症状 | 確認事項 |
|---|---|
| APM データが表示されない | トレースが同じワークスペースに届いていること、時間範囲に直近のトラフィックが含まれていること、現在のロールに `apm.services.read` 権限があることを確認してください。 |
| `unknown_service` | スパンをエクスポートする前に、リソース属性 `service.name` に一貫した値を設定してください。 |
| エンドポイントが表示されない | スパン種別に `SERVER` または `CONSUMER` を指定し、HTTP、RPC、またはメッセージングの標準属性を追加してください。 |
| 依存関係が表示されない | ダウンストリームへの呼び出しを囲む `CLIENT` または `PRODUCER` スパンを追加し、呼び出し先を示すセマンティック属性を設定してください。 |
| バージョンが表示されない | デプロイ内のすべてのインスタンスに `service.version` を一貫して設定してください。 |
| エラーが表示されない | 例外イベントを記録し、OpenTelemetry の規約に従ってスパン、HTTP、または RPC のステータスを設定してください。 |
| エラーサンプルからトレースが見つからない | サンプリングでトレースが除外されたか、トレースの保存期間が過ぎています。サンプリング前に算出した APM の集計値は引き続き有効です。 |
| ランタイムのグラフが表示されない | 同じ `service.name` を設定した OpenTelemetry のランタイムメトリクスを送信してください。 |
| 結果が一部しか表示されない、または古い | データ品質に関する通知と `GET /api/v1/apm/health` を確認してください。 |
| 停止したサービスの APM アラートが発報しない | リクエストがなければ、エラー率、レイテンシ、Apdex の値は得られません。トラフィックの停止を検知するには、**リクエスト数**または**スループット**を監視してください。 |
| SLO に**データなし**と表示される | サービスが SLO の対象環境でデータを送信していることと、エンドポイント名が**エンドポイント**一覧の名前と一致していることを確認してください。 |
