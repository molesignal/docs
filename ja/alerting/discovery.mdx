検出機能は5分ごとに各組織をスキャンし、見つかった問題を**検出結果**として保存します。 **アラート → 検出**を開きます。検出結果の閲覧には `alerts.discovery.read`、ルールの作成には `alerts.rules.manage` が必要です。

## 検出対象

| 種類 | データソース | 検出条件 |
|---|---|---|
| **サービス指標の急変** | [APMインサイト](/ja/apm/insights) | 直近30分間のサービスのエラー率、P95レイテンシー、トラフィックのいずれかが、直前の30分間と1週間前の同じ時間帯の両方と比べて明らかに変化しています。判定には十分なリクエスト数が必要です。 |
| **新バージョンでの悪化** | APMインサイト | 直近30分間に初めて観測されたバージョンで、前のバージョンよりも指標が悪化しています。 |
| **新規フロントエンドエラー** | [RUMエラー](/ja/rum/errors) | 直近30分間にアプリケーションで初めてエラーの問題が発生しています。 |
| **フロントエンドエラーの再発** | RUMエラー | 解決済みのエラーの問題が、より新しいバージョンで再発しています。 |
| **エラーログの急増** | ログ | ログストリームが直近15分間に20件以上のエラーログを出力し、その件数が直前1時間の15分あたりの平均件数の3倍以上です。ログストリームにサービスフィールドがある場合は、サービスごとに判定します。 |
| **新規エラーログ** | ログ | 直前の1日間にログストリームになかったエラーメッセージが、直近15分間に3回以上出現しています。数値や16進数の文字列だけが異なるメッセージは同一とみなし、ストリームごとに最大10件を検出します。 |
| **容量ひっ迫** | メトリクス | ファイルシステムの使用率が90%以上、またはメモリの使用率が95%以上です。 |
| **CPU使用率の急上昇** | メトリクス | ホストのCPU使用率が60%以上で、1時間前より30パーセントポイント以上上昇しています。 |
| **コンテナの再起動** | メトリクス | 直近15分間にコンテナが再起動しています。 |

ログ：各組織で、レベルを示すフィールド（`level`、`severity`、`severity_text`、 `severity_number` など）を持つログストリームを、最終変更日時が新しい順に20件調べます。error、fatal、criticalなどのレベルや、 `severity_number` が17以上のログをエラーとして扱います。メトリクス：一般的なリソースメトリクスのうち、対象はあらかじめ決まっています。 OpenTelemetryのホストレシーバーとKubernetesレシーバー、Prometheusのnode_exporter、kube-state-metricsが提供するメトリクスが対象です。メトリクスディレクトリにある場合にのみクエリを実行し、ほかのメトリクスはスキャンしません。

パフォーマンス改善の提案（遅い依存先、N+1呼び出し、遅いステートメント、負荷が集中するエンドポイント）は、問題として扱いません。無視または解決済みの問題も検出対象外です。

種類、サービスまたはアプリケーション、環境、メトリクスが同じ問題については、未終了の検出結果を一度に1件だけ保持します。同じ問題を再検出すると、値と最終検出日時を更新します。3回連続で検出しなかった場合は検出結果を終了し、30日間保持します。一時的にAPMや RUMにクエリを実行できない場合や、ログストリームの読み取りに失敗した場合は、その回のスキャンで該当するデータソースの未終了の検出結果を変更しません。 `alert` ノードが複数ある場合は、組織IDに基づいて各ノードに組織を割り当てます。

## 検出結果

**開く**と**終了日時**を切り替え、種類で絞り込みます。各行には「checkoutのエラー率は12.0%です（以前は0.40%）」のように、検出内容を1文で表示します。その下に重大度、種類、環境を表示し、続けて発生日時と最終検出日時（または終了日時）を表示します。

行を選択すると、種類、現在の値、直前の値、1週間前の値、バージョン、エラーの発生箇所、発生日時、最終検出日時を確認できます。APMの検出結果には、発生前後のデプロイとバージョンも表示します。**APMで開く**、**RUMで開く**、**ログを開く**、**メトリクスで開く**を選択すると、それぞれサービス、アプリケーション、ログストリーム、クエリを開きます。

**Mole Agentに調査を依頼**を選択すると、詳細を閉じ、その検出結果について[Mole Agent](/ja/agent)とのチャットを開始します。Mole Agentは `get_discovery_finding` で検出結果を読み取り、発生前後のログ、メトリクス、トレース、変更内容を調べて、次に取るべき対応を提案します。

## ルールで通知を受け取る

検出結果は推定に基づくため、そのままオンコール通知を送ると不要な通知が増えます。このため、検出結果は一覧に表示するだけで、通知は送信しません。通知を受け取るには、検出ルールを作成します。

1. **新規検出ルール**を選択します。検出結果の詳細で**同様の検出結果でアラートを作成**を選択すると、種類、サービス、環境が自動入力されます。
2. **対象の検出結果**で、**名前**を入力し、**種類**を選択します（未選択ならすべての種類が対象です）。 **サービスまたはアプリケーション**（APMサービス名またはRUMアプリケーションIDをカンマ区切りで入力します。空欄ならすべてが対象です）、**環境**、**最小重大度**を指定します。
3. **通知先**で、**エスカレーションポリシー**と**緊急度**を選択します。**低（デフォルト）**では、最初のステップにのみ通知し、通知抑制時間帯には通知しません。
4. **ルールを作成**を選択します。

ルールは毎分、未終了の検出結果を確認します。条件に一致する検出結果ごとに、同じ重大度のインシデントを作成し、ラベル `discovery.finding`、`discovery.kind`、`discovery.subject` を付けます。ルーティングルールやサイレンスでは、これらのラベルを照合条件に使えます。検出結果が終了すると、インシデントは復旧します。ルールは [ルール一覧](/ja/alerting/rules#検出ルール)に、ソースが**検出**のルールとして表示されます。

## 新しい検出結果をMole Agentで調査する

トリガーに**新しい発見**を指定した[オートメーション](/ja/automations#開始トリガー)は、保存または有効化した後に現れた検出結果のうち、**種類**（未選択ならすべての種類が対象）、**最低でも**で指定した重大度、**サービス、ホスト、またはコンテナ**（カンマ区切り。空欄ならすべてが対象）の条件を満たすものごとに実行します。調査は検出結果ごとに1回だけ実行します。デフォルトでは検出結果をきっかけに何も実行しないため、推定された問題の調査で意図せずトークン予算を消費することはありません。

## APIとMole Agent

| 操作 | エンドポイントまたはツール |
|---|---|
| 検出結果の一覧を取得 | [`GET /api/v1/alerts/discovery/findings`](/ja/api/alerting/discovery) |
| 検出結果を1件取得 | [`GET /api/v1/alerts/discovery/findings/{id}`](/ja/api/alerting/discovery) |
| 検出ルールを作成 | `query.discovery` を指定して[ルールを作成](/ja/api/alerting/create-rule) |
| Mole Agent | `list_discovery_findings` と `get_discovery_finding`（読み取り専用） |
