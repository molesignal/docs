アラートソースは、別のシステムから送信されたアラートを[インシデント](/ja/alerting/incidents)に変換します。ルールのインシデントと同様に、[エスカレーションポリシー](/ja/alerting/on-call#エスカレーションポリシー)を通じて担当者を呼び出し、[通知ポリシー](/ja/notification-channels)を通じて通知します。また、ソースが復旧を報告すると解決します。**アラート → ソース** を開きます。読み取りには `alerts.sources.read` が必要です。トークンの作成、編集、削除、ローテーションには `alerts.sources.manage` が必要です。

## ソースの種類

各ソースには種類があり、リクエスト本文をどの送信元の形式で読み取るかが決まります。

| 種類 | 送信元 | インシデントの単位 |
|---|---|---|
| **API** | MoleSignal API を呼び出すスクリプト、CI、社内システム | 重複排除キー |
| **Alertmanager** | Prometheus Alertmanager の Webhook レシーバー | 通知グループ |
| **Grafana** | Grafana Alerting の Webhook コンタクトポイント | 通知グループ |
| **Datadog** | Datadog Webhooks インテグレーション | モニター。マルチアラートモニターの各グループ |
| **PagerDuty** | PagerDuty V3 Webhook サブスクリプション | PagerDuty インシデント |
| **Alibaba Cloud CloudMonitor** | しきい値アラームのコールバックとイベントサブスクリプションのプッシュチャネル | アラームルールの対象オブジェクト、またはシステムイベント |
| **Tencent Cloud Observability Platform** | 通知テンプレートの API コールバック | ポリシー配下の 1 オブジェクトの 1 メトリクスまたはイベント。レベル付きポリシーではレベルごとに 1 件 |
| **Amazon CloudWatch** | SNS トピックに送信されたアラーム（トピックの HTTPS サブスクリプション経由） | アラーム 1 件 |
| **Zabbix** | Zabbix Webhook メディアタイプ | 問題 1 件 |
| **Azure Monitor** | アクション グループの Webhook アクション（共通アラートスキーマ） | アラート 1 件 |
| **Google Cloud Monitoring** | Webhook 通知チャネル、またはプッシュサブスクリプション経由の Pub/Sub チャネル | Monitoring インシデント 1 件 |
| **Huawei Cloud Eye** | SMN トピックに送信されたアラーム（トピックの HTTPS サブスクリプション経由） | 1 リソースのアラームルール 1 件 |
| **メールアドレス** | IMAP メールボックス、または既存のメールシステムからの生のメール | 同じ件名のメールの連続 |

Thanos、Cortex、Mimir の Alertmanager など、Alertmanager Webhook を扱うシステムは、**Alertmanager** 種類を使用します。

## ソースを作成する

1. **アラート → ソース** を開き、**新規アラートソース** をクリックします。
2. **種類** を選択し、**名前** を入力します。
3. **エスカレーションポリシー** を選択します。デフォルトは **ルーティングに従う（デフォルト）** で、ルールワークベンチと同じです。[アラートルーティング](/ja/alerting/routing)が、ルーティングルール、サービスを所有するチーム、チームラベルに基づいてチームとエスカレーションポリシーを選択し、それ以外の場合は `default` という名前の[デフォルトポリシー](/ja/alerting/on-call#デフォルトポリシー)が使用されます。ポリシーを選択した場合、インシデントはそのポリシーを使用し、ルーティングはチームのみを選択します。**エスカレーションなし（通知ポリシーのみ）** の場合、インシデントは引き続きオープンして通知されますが、エスカレーションポリシーによる呼び出しは行われません。
4. **デフォルトの重大度** を選択します。これはアラート自体に重大度がない場合に使用されます。
5. 必要に応じて **追加ラベル** を追加します（例: `team=payments`）。追加ラベルは、ソースがオープンするすべてのインシデントに追加されます。アラート自体が持つラベルが優先されます。
6. **作成** をクリックします。ソースのページが開き、トークンと、トークンを入力済みのセットアップを示すダイアログが表示されます。Alibaba Cloud CloudMonitor は取り込みアドレスのみが必要なため、ダイアログにはトークンを含むアドレスが表示されます。

<Warning>
  トークンは、ソースの作成時またはトークンのローテーション時にのみ表示されます。ダイアログを閉じた後は、`mspat-` で始まるプレフィックスのみを確認できます。トークンを紛失した場合は、**トークンをローテーション** をクリックして新しいトークンを取得してください。古いトークンはすぐに使用できなくなります。
</Warning>

## 取り込みアドレスとトークン

すべてのソースは 1 つの取り込みアドレスを共有します。トークンによって、アラートがどのソースに属するかが決まります:

```text
https://<molesignal-host>/api/v1/intake/alerts
```

トークンは `mspat-<36>` のような形式で、API トークンと同じ形ですが、アラートのみを取り込みます。API トークンはアラートを取り込めません。送信元はトークンをヘッダーに入れます:

```text
Authorization: Bearer <token>
```

ヘッダーを設定できない送信元（Alibaba Cloud CloudMonitor、Tencent Cloud Observability Platform、SNS 経由の Amazon CloudWatch、Azure Monitor、Google Cloud Monitoring、SMN 経由の Huawei Cloud Eye）は、トークンをアドレスに含めます: `https://<molesignal-host>/api/v1/intake/alerts?token=<token>`。

送信元はこのアドレスに到達できる必要があります。MoleSignal の前にファイアウォールがある場合は、送信元のサイトまたはリージョンのイグレスアドレスを許可します。Datadog は `ip-ranges` の `webhooks` セクションでサイトごとに一覧を提供し、PagerDuty は米国と EU のサービスリージョン向けに公開し、Alibaba Cloud CloudMonitor はアラームコールバックのドキュメントでプッシュ範囲を一覧表示します。MoleSignal が内部ネットワークで実行されている場合は、このアドレスのみをインターネットに公開する方法について[パブリックアクセス](/ja/public-access)を参照してください。

## 送信元を設定する

ソースのページの**受信**には、受信アドレス、トークン、および各種類のセットアップが3つのステップで表示されます。`<TOKEN>` をソースのトークンに置き換えます。ソースが最初のリクエストを受信すると、3つのステップにチェックが付きます。

### API

```bash
curl -X POST https://<molesignal-host>/api/v1/intake/alerts \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{"dedupKey": "disk-full/web-1", "summary": "Disk almost full on web-1", "severity": "critical", "labels": {"host.name": "web-1"}}'
```

`action` は `trigger`（デフォルト）、`acknowledge`、または `resolve` です。同じアラートを確認または解決するには、同じ `dedupKey` を使用します。[アラートを送信する](/ja/api/alerting/send-alerts)では、すべてのフィールドについて説明しています。

### Alertmanager

`alertmanager.yml` にレシーバーを追加し、アラートをそこにルーティングします：

```yaml
route:
  receiver: molesignal
receivers:
  - name: molesignal
    webhook_configs:
      - url: https://<molesignal-host>/api/v1/intake/alerts
        send_resolved: true
        http_config:
          authorization:
            credentials: <token>
```

`send_resolved` は `true` のままにします。そうしないと、復旧が送信されません。1つの Alertmanager クラスターのすべてのレプリカに同じ `--web.external-url` を設定します。外部 URL は重複排除キーの一部であるため、同じルーティングを持つ複数リージョンの Alertmanager からの同じ名前のグループは、1つのインシデントに統合されません。

### Grafana

1. Grafana で、**アラート → コンタクトポイント**を開き、**コンタクトポイントを追加**をクリックします。
2. **インテグレーション**を **Webhook** に、**URL** を受信アドレスに設定します。
3. **オプションの Webhook 設定**で、**認証ヘッダーのスキーム**を `Bearer` に、**認証ヘッダーの認証情報**をトークンに設定します。
4. **解決済みメッセージを無効にする**をオフのままにして保存し、通知ポリシーでそのコンタクトポイントを使用します。

ファイルプロビジョニングを使用する場合：

```yaml
apiVersion: 1
contactPoints:
  - orgId: 1
    name: molesignal
    receivers:
      - uid: molesignal
        type: webhook
        settings:
          url: https://<molesignal-host>/api/v1/intake/alerts
          httpMethod: POST
          authorization_scheme: Bearer
          authorization_credentials: <token>
```

### Datadog

1. Datadog で、**インテグレーション → Webhooks**を開き、たとえば `molesignal` という名前で Webhook を追加します。
2. **URL** を受信アドレスに、**カスタムヘッダー**を `{"Authorization": "Bearer <token>"}` に設定します。**フォームとしてエンコード**はオフのままにします。
3. **ペイロード**を以下のテンプレートに設定します。フィールド名は MoleSignal のもので、値は Datadog の変数です。このテンプレートのないリクエストは拒否されます。

```json
{
  "alert_id": "$ALERT_ID",
  "alert_cycle_key": "$ALERT_CYCLE_KEY",
  "transition": "$ALERT_TRANSITION",
  "alert_type": "$ALERT_TYPE",
  "priority": "$ALERT_PRIORITY",
  "title": "$ALERT_TITLE",
  "event_title": "$EVENT_TITLE",
  "message": "$TEXT_ONLY_MSG",
  "scope": "$ALERT_SCOPE",
  "tags": "$TAGS",
  "hostname": "$HOSTNAME",
  "link": "$LINK",
  "snapshot": "$SNAPSHOT",
  "query": "$ALERT_QUERY",
  "org_id": "$ORG_ID",
  "last_updated": "$LAST_UPDATED"
}
```

4. モニターの通知メッセージで `@webhook-molesignal` をメンションします。

すべての Datadog サイト（`datadoghq.com`、`datadoghq.eu`、`us3`、`us5`、`ap1` など）から1つのソースに送信できます。サイトは `$LINK` のドメインから取得され、組織 ID とともに重複排除キーの一部になります。

### PagerDuty

1. PagerDuty で、**インテグレーション → Generic Webhooks (v3)**を開き、**新しい Webhook**をクリックします。
2. **Webhook URL** を受信アドレスに設定し、**スコープタイプ**（アカウント、サービス、またはチーム）を選択します。
3. **イベントサブスクリプション**で、`incident.triggered`、`incident.acknowledged`、`incident.resolved`、`incident.reopened`、`incident.priority_updated` を選択します。
4. 値 `Bearer <token>` を持つカスタムヘッダー `Authorization` を追加します。

米国と EU のサービスリージョンのアカウントから1つのソースに送信できます。アカウントドメイン（`<subdomain>.pagerduty.com` または `<subdomain>.eu.pagerduty.com`）は重複排除キーの一部であり、ラベル `pagerduty.region` に書き込まれます。

### Alibaba Cloud CloudMonitor

受信アドレスにトークンを追加します：

```text
https://<molesignal-host>/api/v1/intake/alerts?token=<token>
```

- **しきい値アラーム**：アラームルールの**アラームコールバック**としてこのアドレスを入力します。CloudMonitor はコールバックをフォームエンコードで POST します。MoleSignal は JSON も読み取ります。
- **システムイベント**：**イベントセンター → イベントサブスクリプション → プッシュチャネル**で、ターゲットタイプ **Webhook**、リクエストメソッド **POST**、データ形式 **JSON** のチャネルを作成し、このアドレスを入力して、サブスクリプションポリシーでそのチャネルを使用します。

CloudMonitor はシステムイベントのコールバックを5秒待機し、3回再試行します。MoleSignal はリクエストを[受信クラスター](#複数のクラスター)に渡すとき、最大3秒待機し、タイムアウト時には `503` を返して CloudMonitor が再試行するようにします。中国サイトと国際サイト、およびすべてのリージョンは同じ形式で送信します。リージョンはラベル `aliyun.region` に書き込まれ、アカウントの `userId` は重複排除キーの一部になります。

### Tencent Cloud Observability Platform

Tencent Cloud Observability Platform（旧 Cloud Monitor）で、**アラーム管理 → 通知テンプレート**の下でテンプレートを編集または作成し、その**API コールバック**として受信アドレスを入力し、テンプレートをアラームポリシーにバインドします。Tencent Cloud のコールバックはヘッダーを設定できないため、トークンはアドレスに含めます。アドレスは認証情報として扱います。コールバックには署名がなく、ソースを識別するのはアドレスです。メトリックアラームとイベントアラームの両方が機能し、トリガーと復旧の両方がプッシュされます。

- **重複排除**：同じアカウント、アラームポリシー、メトリックまたはイベント名、およびオブジェクトは1つのアラートになります。レベル付きポリシーでは、レベルごとに1つのインシデントが作成され、それぞれが個別に復旧します（Tencent Cloud と同様）。
- **重大度**：`alarmLevel` の Serious（`Serious`）は critical、Severe（`Warn`）は error、Reminder（`Remind`）は info です。レベルがないポリシーは、ソースのデフォルトの重大度を使用します。
- **ステートレスイベント**（`alarmStatus` が `5`）は、復旧を待たないインシデントを開くため、人が解決します。
- **時刻**：コールバック内の時刻にはタイムゾーンがなく、北京時間として読み取られます。

### Amazon CloudWatch

CloudWatch アラームは外部アドレスを直接呼び出しません。SNS を経由します：

1. アラームの通知で、**In alarm**（`ALARM`）への遷移と **OK** への復帰の両方を同じ SNS トピックに送信します。`OK` がないと、インシデントは自動で解決しません。データなしアラートの場合は、**Insufficient data**（`INSUFFICIENT_DATA`）も送信します。
2. トピックに HTTPS サブスクリプションを追加し、エンドポイントとして受信アドレスを指定します。トークンはアドレスに含めます：

   ```bash
   aws sns subscribe \
     --topic-arn <ARN of the topic> \
     --protocol https \
     --notification-endpoint 'https://<molesignal-host>/api/v1/intake/alerts?token=<token>'
   ```

3. サブスクリプションは自動確認されます。MoleSignal は確認メッセージの署名を検証してから、その `SubscribeURL` にアクセスします。

MoleSignal はすべての SNS メッセージの署名を検証するため、**Raw message delivery** はオフのままにする必要があります。オンになっているとメッセージは拒否され、ソースのページの最近の受信に理由が表示されます。署名証明書は `sns.<region>.amazonaws.com` から取得されるため、リクエストを受け付けるノードはそのアドレスに到達できる必要があります。

CloudWatch アラームには重大度がないため、インシデントはソースのデフォルトを使用します。アラームの ARN は、複合アラームの場合も含めて重複排除キーです。アラームの説明と状態変更の理由はアノテーションに、リージョン、アカウント、名前空間、メトリック、ディメンションはラベルに格納されるため、`aws.region` のようなラベルでルーティングを制御できます。

### Azure Monitor

Azure Monitor のアラートは、アクショングループの Webhook アクションを通じて MoleSignal に到達します：

1. アラートルールで使用するアクショングループに、**Webhook** タイプのアクションを追加し、その URI として受信アドレスを指定します。トークンはアドレスに含めます。
2. **共通アラートスキーマを有効にする**を **はい** に設定します。これがないとリクエストは拒否され、ソースのページの最近の受信に理由が表示されます。

Azure CLI の場合も同様です：

```bash
az monitor action-group update \
  --resource-group <resource group> \
  --name <action group> \
  --add-action webhook molesignal 'https://<molesignal-host>/api/v1/intake/alerts?token=<token>' usecommonalertschema
```

- **重複排除**：アラートの `alertId` が重複排除キーで、Azure サブスクリプションが含まれます。
- **トリガーと解決**：`monitorCondition` が `Fired` の場合はインシデントを作成し、`Resolved` の場合は解決します。アクティビティログアラートのように状態を保持しないアラートは発火するだけなので、人が解決します。
- **重大度**：`Sev0` は critical、`Sev1` は error、`Sev2` は warning、`Sev3` と `Sev4` は info です。
- **ラベル**：アラートルールのカスタムプロパティ、メトリックディメンション、`azure.subscription_id`、`azure.resource_group`、`azure.resource`、`azure.signal_type`、`azure.monitoring_service`、`azure.metric`。説明、条件、値、ターゲットはアノテーションに格納され、調査リンクは `azure_url` として格納されます。

### Google Cloud Monitoring

1. Google Cloud コンソールで、**Monitoring → Alerting → Edit notification channels** を開き、**エンドポイント URL** として受信アドレスを指定した **Webhook** チャネルを追加します。トークンはアドレスに含めます。
2. チャネルをアラートポリシーの通知に追加します。クローズしたインシデントも送信されるため、インシデントは自動で解決します。

**Pub/Sub** チャネルは同じ通知をパブリッシュします。使用するには、そのトピックにプッシュサブスクリプションを作成し、プッシュエンドポイントとして受信アドレスを指定します。MoleSignal は Pub/Sub エンベロープを展開します。

- **重複排除**：スコープ対象のプロジェクトと `incident_id`。1つの Monitoring インシデントは1つのインシデントになります。
- **トリガーと解決**：`state` が `open` の場合はインシデントを作成し、`closed` の場合は解決します。
- **重大度**：ポリシーの重大度レベル（`Critical`、`Error`、`Warning`）。レベルがないポリシーは、ソースのデフォルトの重大度を使用します。
- **ラベル**：リソースとメトリックのラベル、ポリシーと監視対象リソースのユーザーラベル、`gcp.project_id`、`gcp.resource_type`、`gcp.metric`、`gcp.policy`。サマリー、条件、観測値、しきい値、ドキュメントはアノテーションに格納され、インシデントのコンソールアドレスは `gcp_url` として格納されます。

### Huawei Cloud Eye

Cloud Eye（CES）アラームは外部アドレスを直接呼び出しません。SMN を経由します：

1. Simple Message Notification で、**HTTPS** プロトコルのサブスクリプションをトピックに追加し、エンドポイントとして受信アドレスを指定します。トークンはアドレスに含めます。
2. サブスクリプションは自動確認されます。MoleSignal は確認メッセージの署名を検証してから、その `subscribe_url` にアクセスします。
3. Cloud Eye アラームルールのアラーム通知で、そのトピックを選択し、アラームとその復旧の両方で通知します。復旧がないと、インシデントは自動で解決しません。

MoleSignal はすべての SMN メッセージの署名を検証します。署名証明書は `smn.<region>.myhuaweicloud.com` から取得されるため、リクエストを受け付けるノードはそのアドレスに到達できる必要があります。

- **重複排除**：トピックのプロジェクト、アラームルールの `alarm_id`、およびリソース。複数のリソースに対する1つのルールは、リソースごとに1つのインシデントを作成します。
- **トリガーと解決**：`alarm_status` が `alarm` の場合はインシデントを作成し、`insufficient_data` の場合はデータなしとして作成し、`ok` の場合は解決します。
- **重大度**：アラームレベル。Critical は critical、Major は error、Minor は warning、Informational は info です。
- **ラベル**：`instance_id` などのディメンション、および `huawei.region`、`huawei.project_id`、`huawei.namespace`、`huawei.metric`、`huawei.alarm_id`、`huawei.resource_id`。アラームテキスト、現在値、しきい値はアノテーションに格納され、アラームのコンソールアドレスは `huawei_url` として格納されます。

### Zabbix

Zabbix 6.0 以降で動作します。Zabbix には独自のリクエスト形式がありません。メディアタイプのスクリプトがリクエストを送信します。そのため、ソースのページと、作成時のダイアログに、アドレスとトークンが入力済みのメディアタイプが表示されます：

1. YAML として保存し、**アラート → メディアタイプ → インポート**でインポートします。`token` パラメーターを確認します。
2. グローバルマクロ `{$ZABBIX.URL}` を Zabbix フロントエンドのアドレスに設定します。これは重複排除キーに含まれるため、1つのソースで複数の Zabbix サーバーを受け付けられ、インシデントから Zabbix にリンクできます。設定しなくても動作します。
3. ユーザーにこのメディアを割り当てます。**宛先**は任意で、スクリプトでは使用されません。
4. トリガーアクションを追加し、**オペレーション**、**復旧オペレーション**、**更新オペレーション**がすべてそのユーザーに送信されるようにします。復旧オペレーションがないと、インシデントは自動で解決しません。

メディアタイプの**テスト**ボタンには実際の値が必要です。マクロが展開されていない場合（`{EVENT.ID}` がそのまま届く場合）、MoleSignal は `400` を返し、ドキュメントのメディアタイプを使用するよう案内します。

### メール

取り込み方法は2つあり、どちらもメールを同じアラートとして読み取ります。

**メールボックスの読み取り**（推奨）：MoleSignal はスケジュールに従って IMAP メールボックスを読み取ります。必要なのは外部への接続とメールボックスだけで、公開アドレス、MX レコード、ポート 25、証明書は不要です。そのため、セルフホスト時に最も簡単な選択肢になります。監視システムのアラートメールをそのメールボックスに送信するか、メールルールでそこに転送します。

ソースのページで、**メールボックスの読み取り**の下にある **IMAP サーバー**、**ポート**、**暗号化**、**ユーザー名**、**パスワード**、**フォルダー**（デフォルトは `INBOX`）、**読み取り間隔**（15～3600秒、デフォルトは60）を入力します。**接続をテスト**をクリックし、次に**メールボックスを保存**をクリックします。

- **読み取り専用**：`EXAMINE` と `BODY.PEEK[]` を使用するため、既読や削除のマークは付きません。読み取り専用アカウントでも使用できます。
- **バックログなし**：初回接続時に位置を記録し、その後到着したものだけを読み取ります。ホスト、アカウント、フォルダーを変更した場合、またはサーバーがメールボックスを再構築した場合（`UIDVALIDITY` が変更された場合）は、その時点からやり直します。ソースがオフの間は何も読み取らず、位置も保持しません。再度オンにした時点から開始します。
- **送信元リストは必須です**：アドレスを知っている人は誰でもメールを送信できます。ソース設定の**許可する送信元**に、アドレスまたはドメイン全体を表す `@example.com` を記述します。`*` は全員を許可します。リストは `From` を読み取りますが、これは偽装できるため、メールプロバイダーのスパムフィルタリングと DMARC を有効にしてください。それ以外の送信元からのメールは**拒否済み**として記録され、何も作成しません。
- **サインイン**：パスワード、またはプロバイダーのアプリパスワードを使用します。Microsoft 365 はパスワードを受け付けなくなったため、**OAuth 2.0** を選択し、トークンアドレス `https://login.microsoftonline.com/<tenant>/oauth2/v2.0/token`、クライアント ID、クライアントシークレット、スコープ `https://outlook.office365.com/.default` を入力します。アプリケーションには `IMAP.AccessAsApp` 権限と、このメールボックスへのアクセス権が必要です。
- **暗号化なし**は信頼できるネットワークでのみ使用します。パスワードが平文で流れます。
- 読み取りに失敗すると、ソースのページに理由が表示され、次回の実行で再試行されます。複数のアラートノードがある場合、各メールボックスはそのうちの1つによって読み取られます。フェデレーションを使用する場合、メールボックスはソースの受信クラスターで設定され、同期されないため、パスワードはそこに保持されます。

**生のメールを POST する**：すでにメールシステム（Postfix の `pipe`、SES、Mailgun の raw MIME）を運用している場合は、生のメッセージを受信アドレスに POST します：

```bash
curl -X POST 'https://<molesignal-host>/api/v1/intake/alerts' \
  -H 'Authorization: Bearer <token>' \
  -H 'Content-Type: message/rfc822' \
  --data-binary @alert.eml
```

これには、そのメールシステムから受信アドレスに到達できる必要があります。ここでは送信元リストは任意です。トークンが呼び出し元を示すためです。リストを記述した場合は適用されます。

MoleSignal には組み込みの SMTP レシーバーはありません。それを実現するには、開いているポート 25、MX レコード、TLS 証明書、独自のスパムフィルタリングが必要になり、ほとんどのセルフホスト環境では提供できません。

**メールの読み取り方法**は、ソース設定の**メールの受信方法**で設定します：

| 設定 | 説明 |
|---|---|
| **復旧と判定する件名** | 正規表現。空の場合は組み込みのものを使用します：`resolved`、`recovered`、`recovery`、`cleared`、`恢复`、`已解决`、および先頭の `OK`。それ以外のメールはトリガーになります。 |
| **件名から抽出する重複排除キー** | 正規表現。最初のグループが取得されます（例：`host=(\S+)`）。空または一致しない場合は、整形された件名を使用します。`Re:` と `Fwd:` を除き、ステータス語（`PROBLEM`、`RECOVERY`、`告警`、`恢复` など）、重大度、日付と時刻、パーセンテージを大文字小文字を区別せずに除去します。したがって、「CRITICAL: disk full on web-1 (91%)」と「RECOVERY: disk full on web-1 (40%)」は1つのアラートになり、`web-1` と `web-2` は2つになります。送信者のドメインもキーに含まれます。 |
| **アラートの対象外とする件名** | 正規表現。一致するメールはスキップされ、最近の受信に表示されます。 |

重大度は件名内の語（`critical`、`fatal`、`disaster`、`P1` は critical、`error`、`P2` は error、`warning`、`P3` は warning、`info`、`notice`、`P4`、`P5` は info）から決定されます。該当しない場合はソースのデフォルトを使用します。`High CPU` や `Low disk` の high と low は対象外です。本文はアノテーション `message` に格納され（HTML メールはテキストとして、最大4096文字）、送信者はラベル `email.from` とアノテーション `from` に、時刻は `Date` ヘッダーから取得されます。自動応答（`Auto-Submitted: auto-replied`）とバウンス（`multipart/report`）はアラートの対象外です。GBK、GB2312 などの文字セットに対応しています。4 MiB を超えるメールは、本文を読み取らずに**拒否済み**として記録されます。

## アラートがインシデントになる仕組み

| 種類 | 重複排除キー | トリガー | 解決 | 重大度 |
|---|---|---|---|---|
| **API** | `dedupKey` | `trigger` | `resolve` | `severity` |
| **Alertmanager** | 外部 URL と `groupKey` | グループの `status` が `firing` | グループの `status` が `resolved`: グループ内のすべてのアラートが復旧 | グループ内で firing しているアラートのうち最も高い `severity` ラベル |
| **Grafana** | 外部 URL、組織、`groupKey` | 同上 | 同上 | 同上 |
| **Datadog** | サイト、組織、モニター ID、スコープ | `Recovered` 以外への遷移 | `Recovered` | `$ALERT_PRIORITY`。ない場合、Warn と No Data は warning、それ以外は `$ALERT_TYPE` に従う |
| **PagerDuty** | アカウントのドメインと PagerDuty インシデント ID | `incident.triggered`、`incident.reopened`。`incident.priority_updated` は重大度を変更 | `incident.resolved` | 優先度 P1〜P5。ない場合、urgency が high なら error、low なら warning |
| **Alibaba Cloud CloudMonitor** | アカウント、ルール ID、`dimensions`。システムイベントの場合はアカウントと `dedupId` | `ALERT`、`INSUFFICIENT_DATA`。システムイベントは `TRIGGERED` | `OK`。システムイベントは `RESOLVED` | `triggerLevel`。システムイベントは `severity` |
| **Tencent Cloud Observability Platform** | アカウント、ポリシー、メトリクス名またはイベント名、レベル、オブジェクト | `alarmStatus` が `1` または `5` | `alarmStatus` が `0` | `alarmLevel` |
| **Amazon CloudWatch** | `AlarmArn` | `NewStateValue` が `ALARM` または `INSUFFICIENT_DATA` | `NewStateValue` が `OK` | なし: 送信元のデフォルトの重大度 |
| **Azure Monitor** | `alertId` | `monitorCondition` が `Fired` | `monitorCondition` が `Resolved` | `severity`: `Sev0` は critical、`Sev1` は error、`Sev2` は warning、`Sev3` と `Sev4` は info |
| **Google Cloud Monitoring** | スコープ設定プロジェクトと `incident_id` | `state` が `open` | `state` が `closed` | `severity`。`No severity` は送信元のデフォルトを採用 |
| **Huawei Cloud Eye** | SMN トピックのプロジェクト、`alarm_id`、リソース | `alarm_status` が `alarm` または `insufficient_data` | `alarm_status` が `ok` | アラームレベル: Critical、Major、Minor、Informational |
| **Zabbix** | `{$ZABBIX.URL}` のホストと `{EVENT.ID}` | `{EVENT.VALUE}` が 1。更新オペレーションも同様で、重大度はそれに従う | `{EVENT.VALUE}` が 0、または更新オペレーションで問題がクローズ | `{EVENT.NSEVERITY}`: Disaster は critical、High は error、Average と Warning は warning、Information は info |
| **メールアドレス** | 送信者のドメインと件名から取得した部分 | その他のメール | 復旧として書かれた件名 | 件名内の語句 |

優先度と urgency は別々に判定します。API の `priority` と `urgency`、Datadog の `$ALERT_PRIORITY`、PagerDuty の優先度と urgency が、インシデントの優先度と urgency になります。urgency がない場合は送信元のエスカレーションポリシーが決定し、重大度を報告しないアラートは urgency が high になります。詳細は [Urgency](/ja/alerting/on-call#緊急度) を参照してください。

重大度のないアラートは、送信元の**デフォルトの重大度**を採用します。各送信元の重大度の語は大文字と小文字を区別しません。`critical`、`crit`、`fatal`、`page`、`P1` は critical、`error`、`major`、`high`、`P2` は error、`warning`、`warn`、`minor`、`medium`、`P3` は warning、`info`、`low`、`P4`、`P5` は info です。それ以外の語はデフォルトの重大度を採用します。

- **作成**: 1 つの送信元が持つアクティブなインシデントは、重複排除キーごとに最大 1 件です。インシデントには、ラベル `alert.source=external` と `external.kind=<kind>`、アラート自体のラベル (Alertmanager と Grafana の場合はグループの `commonLabels`)、および送信元の追加ラベルが付きます。ラベル `service.name` または `service` は影響を受けるサービスになり、`host.name`、`host`、`hostname` はホストになります。
- **タイトル**: API は `summary` を使用します。Alertmanager と Grafana は `summary` アノテーションを使用し、ない場合は `alertname` を使用します。Datadog は `$ALERT_TITLE` を使用します。PagerDuty はインシデントのタイトルを使用します。Alibaba Cloud CloudMonitor は「アラーム名 · インスタンス名」を使用します。
- **リンク**: 送信元へ戻るアドレスは、`alertmanager_url`、`generator_url`、`dashboard_url`、`datadog_url`、`pagerduty_url` などのアノテーションに書き込まれ、インシデントページにリンクとして表示されます。API の `links` は `name` ごとにアノテーションへ書き込まれます。
- **グループのアラート**: Alertmanager または Grafana からのインシデントは、グループ内のすべてのアラート (最大 100 件) をそのステータスとともに保持し、通知のたびに更新されます。インシデントページの**外部アラート**に、それらを見分けるためのラベルとともに一覧表示されます。
- **重大度の変更**: まだ確認されていないインシデントは、[アラートパイプライン](/ja/pipelines/alert-events#重大度の変更)が決定するアラートの重大度に従います。重大度が上がると、エスカレーションは最初のステップからやり直しになります。手動で設定した重大度はそのまま維持されます。
- **確認**: API の `acknowledge`、PagerDuty の `incident.acknowledged`、および問題を確認する Zabbix の更新オペレーションは、インシデントを確認済みにして、以降のエスカレーションステップと発信を停止します。確認したユーザーは記録されません。
- **解決**: 送信元が復旧を報告すると、確認済みのインシデントも含めて解決します。解決したユーザーは記録されず、タイムラインには復旧として表示されます。
- **遅延メッセージ**: 各重複排除キーは、使用した最新の送信者時刻を記憶しており、それより古いメッセージは無視されます。遅れて届いたトリガーがゾンビインシデントを作成することはなく、遅れて届いた復旧が新しいインシデントをクローズすることもありません。API は時刻を持たないため、メッセージは到着した順に処理されます。
- **先に人が解決した場合**: 送信元がまだそのアラートを報告している場合、次に再送されたときに新しいインシデントが作成されます。これはルールの場合と同じです。
- **データなし**: CloudMonitor の `INSUFFICIENT_DATA`、Cloud Eye の `insufficient_data`、Datadog の No Data によって作成されたインシデントには `alert.condition=no_data` が付き、通知のタイトルは `NO DATA` で始まります。
- **無効化と削除**: 無効にした送信元はアラートを拒否し (`409`)、開いているインシデントはそのまま残ります。送信元を削除すると、そのトークンは即座に機能しなくなり、開いているインシデントは解決します。

[サイレンスポリシー](/ja/alerting/silences)、[セマンティックグループ](/ja/alerting/silences#セマンティックグループ)、[通知ポリシー](/ja/notification-channels)は、他のインシデントと同様に外部インシデントにも適用されます。`external.kind`、送信元の追加ラベル、またはアラート自体のラベルでマッチさせます。

## 最近の受信リクエスト

送信元ページの上部には、送信元の状態が表示されます。**初回リクエスト待ち**、**受信中**、**直近のリクエストを拒否**、**過去7日間にリクエストなし**、**無効**のいずれかです。その横には、過去 24 時間のリクエストとアラート、および送信元が作成したインシデントのうちまだ開いているものが表示されます。

リクエストが届くと、送信元ページの**最近の受信リクエスト**に、送信元が受信したリクエストが一覧表示されます。時刻、結果 (**処理済み**、**拒否済み**、**転送済み**)、HTTP ステータス、アラート数、およびそれらの結果 (**新規作成**、**更新日時**、**変更なし**、**確認済み**、**解決済み**、**無視**) です。行をクリックすると、各アラートのタイトル、重大度、アクション、結果、インシデントを確認できます。拒否されたリクエストでは、理由とボディの先頭部分 (最大 16 KiB) も表示されます。各送信元の直近 500 件のリクエストが、最大 7 日間保持されます。

## 複数のクラスター

[クラスター間フェデレーション](/ja/settings/data-plane#クラスターフェデレーション)を有効にすると:

- ソースは、トークンを含め、他のアラート設定と同様にクラスター間で同期されるため、1つのトークンがすべてのクラスターの受信アドレスで機能します。
- ソースのインシデントは、その**受信クラスター**でのみオープンします。受信クラスターとは、ソースの設定で変更しない限り、そのソースが作成されたクラスターです。ソースのアラートを受信した別のクラスターは、gRPC で受信クラスターに転送し、受信クラスターの応答を送信元に返します。そのため、どのクラスターのアドレスに届いても、1つの外部アラートは1つのインシデントになります。
- 受信クラスターに到達できない場合、応答は `503` となり、送信元は再試行します。受信クラスターのリージョンがダウンしたままの場合は、ソースの設定で**受信クラスター**を稼働中のクラスターに変更します。
- **最近の受信リクエスト**は、リクエストを処理したクラスターに記録されます。ソースのページを別のクラスターで開くと、その旨が表示されます。

## 制限

| 項目 | 制限 |
|---|---|
| リクエストボディ、メール1通 | 最大 4 MiB。 |
| メールボックスの読み取り | 一度に最大 50 通。残りは次のラウンドで処理します。 |
| 1回の API リクエスト | アラート 100 件。`dedupKey` は最大 255 文字、`summary` は最大 1024 文字。 |
| 1件のアラート | ラベル 64 個、アノテーション 64 個。API はこれを超えると拒否します。その他の種類では超過分は破棄され、長すぎるタイトルとアノテーションは切り詰められます。 |
| グループのアラート | 100 件を保持します。 |
| ソースの追加ラベル | 32 個まで。`alert.` で始まるキーと `external.kind` は使用できません。 |
| 最近の受信リクエスト | 各ソースの直近 500 リクエストを最大 7 日間。 |

Grafana の HMAC 署名と PagerDuty の署名は検証されません。トークンによってすでにソースが特定されるためです。MoleSignal でインシデントを確認または解決しても、送信元には書き戻されません。
