インシデントは、[ルール](/ja/alerting/rules)が発報したとき、[シンセティックチェックが失敗したとき](/ja/synthetics#アラートインシデント)、または[アラートソース](/ja/alerting/sources)が外部アラートを受信したときに起票されます。インシデントはルール、値、ラベル、および終了するまでのすべてのステップを記録します。**アラート → インシデント**を開くか、`⌘⌥A` を押します。インシデントの閲覧には `alerts.incidents.read` が必要です。確認済みにする、解決済みにする、スヌーズには `alerts.incidents.acknowledge` が必要です。[インシデントへの対応](#インシデントへの操作)のその他のアクションには `alerts.incidents.update` が、エスカレーションと統合には `alerts.incidents.escalate` が必要です。サイレンスには `alerts.incidents.silence` が必要です。受信したアラート通知は Feishu アプリまたは Slack アプリを介して、カード上で確認済みにする、解決済みにする、スヌーズすることもできます。詳細は [アラートカード](/ja/im#アラートカード)を参照してください。テキストメッセージまたは通話には、コードまたはキーで応答できます。詳細は [テキストと通話への返信](/ja/notification-channels#メッセージへの返信と通話での応答)を参照してください。

## インシデントの状態

| 状態 | 一覧のラベル | 意味 |
|---|---|---|
| `open` | **レビュー待ち** | 発報中で、まだ誰も確認済みにしていません。エスカレーションは継続します。 |
| `acknowledged` | **対応中** | 誰かが対応を担当しています。エスカレーションは停止します。 |
| `resolved` | **復旧済み** | 終了：ルールが復旧したか、誰かが解決済みにしました。 |
| `closed` | **クローズ済み** | 終了。 |

オープンなインシデントは、ルールが[復旧条件](/ja/alerting/rules#復旧と欠損データ)を満たすと自動的に解決します。確認済みのインシデントは、誰かが解決済みにするまで確認済みのままです。エスカレーションポリシーで [確認済みだが未解決](/ja/alerting/on-call#確認済み・未解決)が設定されている場合は、その時間の経過後に **レビュー待ち**に戻り、再度ページ通知されます。スヌーズされたインシデントは**対応中**です。外部ソースのインシデントはソースが復旧を報告すると、確認済みかどうかに関係なく解決します。詳細は [アラートがインシデントになる仕組み](/ja/alerting/sources#アラートがインシデントになる仕組み)を参照してください。各ルール、または分割ルールの各グループは、同時に最大 1 つのアクティブなインシデントを持ちます。

## インシデント一覧

**インシデント**のヘッダーには、影響を受けたサービス、確認待ちのインシデント、過去 24 時間に復旧したインシデントの数が表示されます。サマリーには、現在発報中のインシデント数、最も古いインシデントが発報してからの時間、評価されているルールの数が表示されます。**最近復旧したインシデント**には、最近終了したインシデントが一覧表示されます。

**発報中**と**レビュー待ち**（まだ担当者のいないインシデント）を切り替えます。現在のユーザーがチームに所属している場合、**所属チーム**にはそれらのチームに[ルーティング](/ja/alerting/routing)されたインシデントが一覧表示されます。右側で優先度でフィルタリングするか、**なし**のインシデントを表示します。インシデントは重大度、次に優先度、次に発報してからの時間の順に一覧表示されます。各行には、重大度、インシデントとそのサービス（緊急度の低いインシデントの場合は**緊急度：低**）、優先度、状態、経過時間、および担当者とルーティングされたチームが、3 つのアクションとともに表示されます：

| アクション | 効果 |
|---|---|
| **確認済みにする** | 担当者になります。インシデントは**対応中**になり、エスカレーションが停止します。 |
| **サイレンス** | このインシデントのみ、以降の通知とエスカレーションを一時停止します。詳細は[1 つのインシデントをサイレンスにする](/ja/alerting/silences#1件のインシデントにサイレンスを適用する)を参照してください。 |
| **ランブック** | ルールに対応ガイドがある場合、それを開きます。 |

行にチェックを入れるか、ヘッダーからすべてにチェックを入れると、一覧の上に一括アクションのバーが表示されます： **確認済みにする**、**解決済みにする**、**スヌーズ**、**担当者の変更**、**調整**（重大度、優先度、または緊急度）、および 2 つ以上にチェックを入れた場合は **統合**が表示され、保持するインシデントを指定します。1 回のリクエストで最大 100 件のインシデントを処理できます。処理できないもの（復旧したためなど）は最初の理由とともにカウントされ、残りは処理されます。

### 手動でインシデントを起票する

ルールが捕捉しなかった問題（顧客からの報告や、誰かが目にしたことなど）もインシデントにでき、他のインシデントと同様にページ通知とエスカレーションが行われます。一覧の上にある**新規インシデント**を選択します（`alerts.incidents.create`）：

1. **発生内容**で、**タイトル**（必須）と**説明**（Markdown が使えます）を入力し、 **重大度**（デフォルトは error）、**優先度**、**緊急度**（デフォルトはエスカレーションポリシーによる）を選択します。任意で**影響を受けたサービス**をカンマ区切りで入力し、**ラベル**を 1 行に 1 つ `key=value` の形式で入力します。
2. **対応担当**で、次のいずれかを選択します：

   | 選択肢 | 効果 |
   |---|---|
   | **自動ルーティング** | ルールのインシデントと同様に[アラートルーティング](/ja/alerting/routing)でルーティングされます。 |
   | **チームを指定** | チームのオンコールポリシー、またはデフォルトのポリシーが適用されます。 |
   | **エスカレーションポリシーを指定** | ポリシーのステップ 1 から通知されます。 |
   | **担当者を個別に指定** | 最大 10 人に直接通知され、エスカレーションポリシーは使用されません。 |

3. 任意で**重大インシデントとして宣言**にチェックを入れ、**インシデントを作成**を選択します。インシデントのページが開きます。

手動で起票されたインシデントには、ラベル `alert.source=manual`、起票者を示すアノテーション `created_by`、および説明がアノテーション `description` として付与されます。アラートパイプラインは経由せず、他のインシデントと重複排除されることも、自動的に復旧することもありません。誰かが解決済みにする必要があります。インシデントのページの**起票者**には起票者が表示され、インサイトではそのようなインシデントが**手動起票**としてまとめてカウントされます。Mole Agent の `create_incident` ツールも、1 回の承認でインシデントを起票します。

## インシデントの詳細

インシデントを選択すると詳細が開きます。ヘッダーには、状態、発火した時刻、ルール、発火してからの経過時間が表示され、**確認済みにする**、**解決済みにする**、**その他の操作** が並びます。**その他の操作** には [インシデントへの操作](#インシデントへの操作) と **サイレンス** のアクションが含まれます。

| セクション | 内容 |
|---|---|
| **タイムライン** | 発火した時刻、誰が通知を受けたか、誰が何を行ったか（確認済みにした、担当者を変更した、対応者を追加した、エスカレーションした、スヌーズした、重大度を変更した、統合した、解決済みにした、および修復、チケット、重大インシデントのステップ）、インシデントが開く前に [アラートパイプライン](/ja/pipelines/alert-events#イベントの処理結果) が変更した内容、およびその場所（API、チャット、SMS返信、電話のキー操作、Mole Agent）と、その間の時刻を表示します。末尾には [ノート](#ノート) が追加され、このインシデントに統合されたインシデントがその下に一覧表示されます。 |
| **調査** | **トリガークエリを開く** は、そのエクスプローラーで正確なクエリを再生します。**関連ログ** と **関連メトリクス** は、同じ時間範囲で影響を受けたコンテキストを開きます。RUM の指標のインシデントには **RUMで開く** があります。 |
| **調査ガイド** | ルールの [調査ガイド](/ja/alerting/rules#調査ガイド) が求める内容（そのステップ、インシデントの時間範囲で開かれるクエリ、およびそのダッシュボード）を表示します。ルールにガイドがある場合にのみ表示されます。 |
| **AIによる根本原因分析** | Mole Agent による分析です。[AIによる根本原因分析](#ai-根本原因) を参照してください。 |
| **関連シグナルへのリンク** | 証拠から見つかったサービス、トレース ID、ホストで、それぞれがリンクになっています。 |
| **トリガークエリ** | クエリと、それが返した値です。**サンプル値を表示** はサンプル行を表示します。 |
| **メタデータ** | インシデントのラベルとアノテーションです。 |
| **担当者** | エスカレーションが到達した相手、およびインシデントが [ルーティング](/ja/alerting/routing#インシデントでのルーティング結果) されたチームとその理由です。スヌーズ、別のインシデントへの統合、手動で設定された重大度はここに記録されます。 |
| **影響範囲** | サービスを特定するインシデントの場合、サービスマップ上でそのサービスが及ぶ範囲を示します。[インシデントの影響範囲](/ja/apm/insights#インシデントの影響範囲) を参照してください。 |
| **ビジネスインパクト** | 各 [ビジネスキー](/ja/business-context) について、インシデントのサービスへのリクエストがトリガー付近で最も多く失敗した値（テナント、プラン）を表示し、重要な値にはフラグを付けます。それぞれをクリックすると、Traces ページでそのリクエストが開きます。`streams.query` または `sys.telemetry.read` を持つ読者に表示されます。 |
| **サンプルセッション** | RUM の指標のインシデントの場合、それを示すセッションをリプレイ付きで表示します。[RUM アラート](/ja/rum/alerts#インシデント) を参照してください。 |
| **類似インシデント** | 過去 90 日間のこのインシデントに似たインシデントと、その終了状況です。[類似インシデントと最近の変更](#類似インシデントと最近の変更) を参照してください。 |
| **最近の変更** | トリガー付近で、対象サービスと下流サービスについて報告されたデプロイ、設定変更、フィーチャーフラグ、および前日に編集された場合はそのルールです。 |
| **修復** | インシデントに適用される修復アクション、および要求された実行と承認です。[修復](/ja/alerting/remediation) を参照してください。 |
| **チケット** | インシデントの Jira または Feishu Project のチケットとそのステータスです。ここでチケットを作成できます。[チケット](/ja/alerting/tickets) を参照してください。 |
| **重大インシデント** | 重大インシデントを宣言し、役割を割り当て、ウォールームと会議に参加し、作業をタスクに分割し、更新を投稿します。[重大インシデントとポストモーテム](/ja/alerting/major-incidents) を参照してください。 |
| **ポストモーテム** | インシデントの内部ポストモーテムです。**ポストモーテムを作成** はテンプレートから下書きを作成し、**ポストモーテムを開く** で続きを進めます。[ポストモーテム](/ja/alerting/major-incidents#ポストモーテム) を参照してください。 |

## インシデントへの操作

**その他の操作** の各アクションはタイムラインに記録され、 [API](#インシデント-api) からも利用できます。Mole Agent もこれらのアクションを実行できます。ノートの追加には、依頼した人の確認が必要で、その他は 1 回の承認が必要です。[承認と実行](/ja/agent#承認と実行) を参照してください。 Mole Agent は、チケットの作成、重大インシデントの役割の割り当て、タスクの追加、ポストモーテムの下書き（依頼した人の確認あり）、重大インシデントの宣言と更新の投稿（1 回の承認あり）、および修復の実行の提案（[事前承認](/ja/alerting/remediation#事前承認) が適用される場合を除き、2 回の承認あり）も行えます。復旧したインシデントと別のインシデントに統合されたインシデントは、この方法では操作できなくなりますが、 [ノート](#ノート) は引き続き追加できます。

| アクション | 効果 |
|---|---|
| **担当者の変更** | 担当者を最大 10 人まで指定できます。指定した人は担当者になり、通知を受けます。インシデントは **レビュー待ち** に戻り、誰も確認済みにしない場合はエスカレーションが続きます。チームを指定した場合: そのチームのオンコールポリシー（チームにない場合はデフォルトポリシー）がステップ 1 からやり直されます。エスカレーションポリシーを指定した場合: そのポリシーがステップ 1 からやり直され、チームはそのままです。ノートを添えてタイムラインに記録できます。 |
| **対応者の追加** | 選択した人が担当者に加わり、通知を受けます。状態は変わりません。 |
| **今すぐエスカレーション** | 選択したステップの対象にすぐに通知します（デフォルトでは次のステップ）。インシデントの重大度に適用されるステップのみが一覧表示されます。確認済みのインシデントは **レビュー待ち** に戻ります。 |
| **スヌーズ** | 1、4、8、24 時間、または **カスタム…**（1 分から 7 日間）です。**レビュー待ち** のインシデントは最初に確認済みにされます。スヌーズ中は何も送信されず、スヌーズが終了するとインシデントは **レビュー待ち** に戻り、担当者に再び通知されます。**スヌーズの解除** で即座に終了します。 |
| **重大度** | 手動で設定すると、ルール、アラートソース、合成チェックのいずれもそれを変更しなくなります。**レビュー待ち** のインシデントの重大度を上げると、新しい重大度でステップ 1 から再び通知されます。下げる場合は重大度のみが変更されます。 |
| **優先度** | 組織の [優先度レベル](/ja/alerting/on-call#緊急度と優先度のレベル)（デフォルトでは P1 から P5）または **なし** のいずれかです。優先度のみを変更し、誰にも再通知しません。優先度は、一覧の列とフィルター、[ルーティングルール](/ja/alerting/routing) の条件、自動の重大インシデント、チケットの優先度マッピング、およびインサイトで使用されます。 |
| **緊急度** | **緊急度：高** または **緊急度：低** です。[緊急度](/ja/alerting/on-call#緊急度) を参照してください。**レビュー待ち** のインシデントを **緊急度：高** に上げるとステップ 1 から再び通知されます。低に下げると緊急度のみが変更され、以降のエスカレーションが停止します。手動で設定すると、サポート時間によって変更されなくなります。 |
| **統合** | 他のアクティブなインシデントをこのインシデントに統合します。[インシデントの統合](#インシデントの統合) を参照してください。 |
| **サイレンス** | [1 つのインシデントをサイレンスにする](/ja/alerting/silences#1件のインシデントにサイレンスを適用する) を参照してください。 |

これらのアクションが送信する通知はエスカレーション通知で、テンプレート内の `{{escalation.reason}}` は理由を示します: `reassigned`、`responder_added`、`manual`（今すぐエスカレーション）、`snooze_ended`、 `severity_raised`、`urgency_raised`、または `ack_timeout`（確認済みだが未解決のまま長すぎる）です。テンプレートでは `{{urgency}}` と `{{priority}}` も使用できます。 [テンプレート変数](/ja/notification-channels#テンプレート変数) を参照してください。

### インシデントの統合

1 つの問題で複数のインシデントが開かれる場合（たとえば、1 つの障害で複数のルールが発火する場合）は、それらを 1 つのメインインシデントに統合します。統合されたインシデントは、単独では通知やエスカレーションを行わず、インシデント一覧やインサイトにも表示されず、メインインシデントのタイムラインの下に一覧表示されます。メインインシデントを解決済みにすると、それらも解決済みになります。統合されたインシデントが先に復旧した場合は、メインインシデントのタイムラインにその旨が記録されます。一度に最大 50 個のインシデントを統合でき、統合は元に戻せません。

詳細では、**その他の操作 → 統合** で統合するインシデントにチェックを入れます。インシデント一覧では、複数にチェックを入れて **統合** を選択し、メインインシデントを選択します。

### ノート

タイムラインの下部にあるボックスに、判明した内容と行った内容を最大 4,000 文字でノートとして追加し、引き継いだ人がすぐに確認できるようにします。担当者の変更時に添えたノートもそこに記録されます。Mole Agent はインシデントとともに最新のノートを読み取ります。

## AI 根本原因

Mole Agent がモデルプロバイダーとともに設定されている場合、バックグラウンドで新しいインシデントを分析し、証拠に基づく結果をインシデントとともに保存します。**生成** は即時に1つの結果を要求し、 **再生成** はそれを置き換えます。結果は **役に立った** または **役に立たなかった** で評価します。評価は [品質](/ja/quality) に反映されます。

分析はラベル付きの証拠から書かれ、インシデントのサービスと、そのサービスが呼び出すサービスについて、インシデント発生の30分前から10分後までを読み取ります:

| 証拠 | 示す内容 |
|---|---|
| **APM インサイト** | 直前および1週間前の期間と比べて変化した指標、リグレッションしたバージョン、または時間の使われ方。 |
| **新しいエラーグループ** | その期間で初めて見られたエラーグループと、その発生回数。 |
| **サンプルトレース** | APM が例として保持したトレースのうち最も遅いものと、その所要時間。 |
| **エラーログ** | 1週間前の同じ期間と比較した、あるサービスのエラーレベルの行。 |
| **新しいエラーログパターン** | インシデントのサービスのエラーレベルのログのうち、直前の同じ長さの期間には存在しなかったメッセージパターンと、その期間内の行。最大3件。 |
| **失敗したリクエストの差分** | 失敗したリクエストが他のリクエストとは異なる値を持つフィールドと、それらが集中する値および各リクエストに占めるその割合。サンプルから最大3件。 |
| **ビジネスインパクト** | ビジネスキーごとに、リクエストが失敗した値と失敗件数。重要な値を先に示します。 |
| **変更** | 報告されたデプロイ、設定変更、機能フラグ、またはアラートルールの編集。 |
| **類似インシデント** | このインシデントに似た過去のインシデント。 |

分析は各主張を **[E2]** などのラベルで引用し、証拠に裏付けられない原因は推測として示します。分析の下の **証拠** には各項目が一覧表示され、それぞれ元の場所を開けます。 APM、トレース、ログから読み取った指標は、そのデータを読み取る権限のある読者にのみ表示され、それ以外の読者には項目の内容と **数値非表示** が表示されます。Mole Agent の調査から書き戻された分析は、調査が引用した内容を一覧表示します。

生成には Mole Agent の権限が必要です。組織の1日分の Mole Agent トークン予算を使い切ると、自動分析は一時停止し、オンデマンドの生成は予算設定に従います。次を参照してください: [使用量と予算](/ja/agent#使用状況と予算)。

## 類似インシデントと最近の変更

**類似インシデント** は、組織内の過去90日間のインシデントから、このインシデントに最も似たものを最大 5件見つけ、その理由を示します: **同じアラート**（同じフィンガープリント）、**同じルール**、**同じサービス**、 **類似のラベル**、**類似のタイトル**（中国語のタイトルを含む）、または **同じチーム**。各項目には、そのインシデントがどれだけ続いたか、誰が解決したか、ノートの数、AI 根本原因の最初の文が表示されるため、インシデントを引き継ぐ担当者は前回どのように処理されたかを確認できます。

**最近の変更** は、[報告された変更](/ja/apm/deployments#ci-からデプロイを報告する) を、トリガーの30 分前から10分後まで、インシデントのサービスと、サービスマップ上でその下流にあるサービスについて一覧表示します: デプロイ（失敗およびロールバックされたものには印が付きます）、設定変更、機能フラグ（下流にある場合は印が付き、パイプラインリンクがある場合はそれが表示されます）。インシデントのルールは、トリガーの前日に編集された場合にも一覧表示されます。サービスマップがない場合は、インシデントのサービスのみが対象になります。

## インシデントのグループ

[セマンティックグループ](/ja/alerting/silences#セマンティックグループ) は、関連するインシデントを1つのグループにまとめます。たとえば、あるサービスのすべてのクリティカルインシデントです。グループを承認または解決するには、 `POST /api/v1/alerts/incident_groups/{id}/ack` または `/resolve` を使用すると、すべてのメンバーに同じ操作が行われます。

## 履歴

**アラート → 履歴** は、過去のインシデントを、現在の状態、発報および復旧した時刻、継続時間とともに一覧表示します。インシデント、サービス、またはインシデント ID で検索し、重大度と状態でフィルターできます。

## 変更

**アラート → 変更** は、過去24時間、7日間、または30日間のすべての変更を、最新のものから順に一覧表示します: デプロイ、設定変更、機能フラグ、スケーリング、およびパイプラインが報告するインフラストラクチャの変更、アノテーション、APM がスパンで最初に確認したバージョン、アラートルールの編集。各種類は、読み取り権限の範囲で表示されます。リストの上のレールは範囲全体の変更を示します。マークにカーソルを合わせると、誰が何を変更したか、そのコミット、プルリクエスト、CI 実行が表示されます。種類でフィルターし、サービス、バージョン、タイトル、作成者、またはコミットで検索できます。同じ変更は、ログとトレースのヒストグラムおよびメトリクスチャートの下にマークされます。次を参照してください: [`GET /api/v1/changes`](/ja/api/changes)。

## インサイト

**アラート → インサイト** は、過去24時間、7日間、または30日間のワークスペースの対応状況を示します:

| 項目 | 表示内容 |
|---|---|
| サマリー | まだ対応が必要なインシデントの数、復旧したインシデントの **平均復旧時間**、および **短時間での復旧**: 60秒以内に復旧した割合で、ノイズの多いルールの兆候。 |
| **インシデントのタイムライン** | 24時間の場合は時間別、より長い期間の場合は日別に、ブラウザのタイムゾーンで、ピークとともにインシデントを表示します。 |
| **影響が最も多かったサービス** | インシデントで最も頻繁に名前が挙がるサービス。これにはルールに `service` ラベルが必要です。 |
| **発報数上位のルール** | 最も多くのインシデントをオープンしたルール。ここからチューニングを開始します。 |
| **レスポンス** | インシデントを引き受けるまでの平均時間（P50 および P90）、復旧までの中央値時間、エスカレーション率、および誰かが引き受けた割合を、直前の同じ長さの期間と比較して示します。各エスカレーションステップの承認率、インシデントが最初に引き受けられた場所（Web、API、チャットカード、SMS 返信、電話のキー押下、または Mole Agent）、およびチーム、サービス、個人、優先度別に分割した引き受け、復旧、エスカレーション（優先度のないインシデントは除外）も示します。インシデントの引き受けは最初の承認です。承認されずに担当者が解決したインシデントは、解決された時点でカウントされます。 |
| **オンコール負荷** | 各担当者がオンコールだった時間、各担当者が受け取ったアラート通知の数、夜間（担当者のスケジュールのタイムゾーンで22:00から08:00）または週末に届いた通知の数、中断された夜の数、各担当者が最初に引き受けたインシデントの数とその速さ。スケジュールの詳細では、そのメンバーについて同じ内容が表示されます。 |
