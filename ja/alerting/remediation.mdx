修復アクションは、事前に定義した修復処理です。Jenkins、GitHub Actions、Argo、Rundeck などのシステムを呼び出したり、登録済みの Kubernetes クラスター上でワークロードを再起動、スケーリング、ロールバックしたりできます。インシデントの対応時は、インシデントの画面からワンクリックで実行を開始できます。実行には毎回承認が必要です。 [事前承認](#事前承認)を有効にすると、あらかじめ承認できます。承認がそろい次第実行し、実行結果と実行後の確認結果をインシデントのタイムラインに記録します。

**アラート → 修復**を開きます。閲覧には `alerts.remediation.read`、アクションの定義とクラスターの登録には `alerts.remediation.manage`、インシデントでの実行開始には `alerts.incidents.remediate`、実行の承認には `agent.approve` が必要です。

## 修復アクションを定義する

**新規修復アクション**を選択し、以下の項目を入力します。

| セクション | 設定 |
|---|---|
| **基本設定** | **名前**と**説明**を入力します。 |
| **実行方法** | **HTTPリクエスト**または **Kubernetes** を選択します。詳細は以下を参照してください。 |
| **実行開始時の入力項目** | 実行開始時に値を入力する項目を最大 10 件設定できます。**名前**（テンプレートでは `{{params.name}}` と記述）、**ラベル**、**種類**（**テキスト**、**数値**、**選択肢**のいずれか）、**選択肢**、**デフォルト**、**必須**を設定します。 |
| **適用範囲と承認** | **サービス**はカンマ区切りで指定します。空欄の場合はすべてのインシデントが対象です。**リスク**は **L2 · 承認者1名**または **L3 · 承認者2名**を選択します。**確認までの待ち時間**は、実行から結果を確認するまでの分数です。確認しない場合は 0 を指定します。**成功の判定条件**は、**インシデントが解消済み**または**ルールが正常状態に復帰**を選択します。**有効**も設定します。 |

一覧には、各アクションの対象サービス（制限がない場合は**すべてのインシデント**）とリスクが表示されます。 **無効**と表示されるアクションは、インシデント画面では選択できません。

### HTTPリクエスト

| 設定 | 補足 |
|---|---|
| **メソッド**、**アドレス** | `GET`、`POST`、`PUT`、`PATCH` のいずれかと、`http://` または `https://` で始まるアドレスを指定します。 |
| **ヘッダー** | たとえば `Authorization` を指定します。値は暗号化して保存し、以降は表示しません。編集時に値を空欄にすると、既存の値を保持します。 |
| **ボディ** | JSON エディターで JSON を記述します。差し込む値は JSON のルールに従ってエスケープします。引用符で囲んだプレースホルダーは文字列になります。引用符なしのプレースホルダーは、`{"replicas": {{params.replicas}}}` のように数値として扱えます。すべてのプレースホルダーを 0 として解釈したときに有効な JSON にならない場合は、保存できません。 |
| **署名用シークレット** | 設定すると、[汎用 Webhook の署名](/ja/notification-channels/webhooks#ヘッダーと署名)と同様に、リクエストに `X-MoleSignal-Timestamp` と `X-MoleSignal-Sign` が付きます。受信側は、MoleSignal から送信されたことを確認できます。 |

アドレス、ヘッダー、ボディには `{{incident.id}}`、`{{incident.summary}}`、`{{incident.severity}}`、 `{{incident.status}}`、`{{incident.service}}`、`{{incident.url}}`、`{{params.name}}` を使用できます。アドレスに差し込む値はパーセントエンコードします。

リクエストは、アドレスの名前解決で得られた IP アドレスにのみ接続し、クラウドメタデータのアドレスには接続しません。リダイレクトには従わず、30 秒でタイムアウトします。2xx レスポンスを実行成功とみなし、レスポンスの先頭部分を実行記録に保存します。

### Kubernetes

| 設定 | 補足 |
|---|---|
| **クラスター** | 登録済みのクラスターを選択します。[Kubernetes クラスターを登録する](#kubernetes-クラスターを登録する)を参照してください。 |
| **オペレーション** | **再起動**（`kubectl rollout restart` と同様のローリング再起動）、**スケーリング**、**1つ前のリビジョンにロールバック**（`kubectl rollout undo` と同様）のいずれかを選択します。 |
| **ワークロードの種類** | Deployment、StatefulSet、DaemonSet のいずれかを選択します。ロールバックできるのは Deployment のみです。DaemonSet はスケーリングできません。 |
| **名前空間**、**ワークロード名** | `{{incident.service}}` などのテンプレートを使用できます。 |
| **レプリカ数** | スケーリング後のレプリカ数を指定します。`{{params.replicas}}` を指定して、実行開始時に入力することもできます。 |

## Kubernetes クラスターを登録する

**Kubernetes クラスター**で**クラスターを追加**を選択し、**名前**、**API サーバーのアドレス**、 **CA 証明書**（PEM 形式。空欄の場合はシステムの信頼済みルート証明書を使用）、**ServiceAccount トークン**を入力します。トークンは暗号化して保存し、以降は表示しません。**接続をテスト**は、クラスターのバージョンを 1 回取得します。

MoleSignal 専用の ServiceAccount を作成し、必要最小限の権限のみを付与します。対象ワークロードには `get` と `patch`、スケーリングには `scale` サブリソースへのアクセス、ロールバックには ReplicaSet の一覧取得権限が必要です。たとえば、 `shop` 名前空間のワークロードにのみアクセスを許可するには、次のように設定します。

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: molesignal-remediation
  namespace: shop
rules:
  - apiGroups: ["apps"]
    resources: ["deployments", "statefulsets", "daemonsets", "deployments/scale", "statefulsets/scale"]
    verbs: ["get", "patch"]
  - apiGroups: ["apps"]
    resources: ["replicasets"]
    verbs: ["list"]
```

接続先は、API サーバーのアドレスの名前解決で得られた IP アドレスに限ります。クラウドメタデータのアドレスには接続しません。アクションで使用中のクラスターは削除できません。

## インシデントでアクションを実行する

インシデント詳細の**修復**には、そのインシデントに適用できるアクションが表示されます。対象は、サービスの制限がないアクションと、対象サービスがインシデントのサービスと一致するアクションです。対象アクションの横にある**実行**を選択し、必要な値と**理由**（例：「チェックアウトで接続を使い切ったため、まず再起動する」）を入力して、 **承認を依頼**を選択します。解消済みのインシデントでは実行を開始できません。

承認を依頼すると、実行は承認待ちになります。`agent.approve` を持つ承認者が L2 では 1 名、L3 では 2 名必要です。依頼者は承認できません。同じカードで**承認**または**却下**を選択するか、 [Mole Agent の承認一覧](/ja/agent#承認と実行)で対応します。必要な数の承認がそろい次第、実行を開始します。

| ステータス | 意味 |
|---|---|
| **承認待ち** | 必要な数の承認がまだそろっていません。 |
| **実行中** | 指定したアドレスにリクエストを送信しているか、クラスターに変更を適用しています。 |
| **実行済み**、**失敗** | 実行が終了しました。ステータスの横にレスポンスの先頭部分またはエラーが表示されます。 |
| **未実行** | 承認依頼が却下、期限切れ、またはキャンセルになりました。 |
| **確認待ち** | 実行が完了し、設定した待ち時間の経過後に結果を確認します。 |
| **確認成功**、**確認失敗** | 確認時点までにインシデントが解消しているか、ルールが正常状態に戻っていれば、確認成功となります。 |

実行の開始、実行結果、確認結果はインシデントの[タイムライン](/ja/alerting/incidents#インシデントの詳細)に記録します。実行の開始は監査ログにも記録します。

Mole Agent は、インシデントに適用できる修復アクションを一覧表示し、実行を提案できます。提案された実行には、事前承認の対象でない限り、アクションのリスク設定にかかわらず、常に 2 名の承認が必要です。

## 事前承認

事前承認を設定すると、対象のインシデントで承認を待たずにアクションを実行できます。事前承認は、 **アラート → 修復**の上部にある**事前承認済みのアクションを待機せずに実行**をオンにするまで無効です。この設定のオン・オフの切り替えと事前承認には `alerts.remediation.preapprove` が必要です（デフォルトではオーナーと管理者が保有します）。事前承認には、通常の承認と同様に `agent.approve` も必要です。事前承認を行うにはサインインが必要で、 API トークンは使用できません。

アクションの横にある**事前承認**を選択し、以下を設定します。

| 設定 | 意味 |
|---|---|
| **サービス** | 選択したサービスのインシデントが対象です。アクションでサービスを指定している場合は、そのすべてを選択します。 |
| **最大実行回数**、**実行回数の集計期間** | 指定した長さの任意の期間内に許可する実行回数です。回数は 1〜20 回、期間は 15 分〜7 日で設定します。 |
| **有効期限** | 1 日後、7 日後、30 日後、90 日後、または**無期限**を選択します。 |
| **実行後の通知先** | 通知コネクターに登録されたグループまたはアドレスを、通知先として最大 5 件指定できます。事前承認による実行のたびに、成功・失敗にかかわらず結果を通知します。 |

保存すると、1 人分の承認としてカウントします。L2 アクションに必要な承認は 1 人分なので、事前承認はすぐに有効になります。L3 アクションには 2 人の承認が必要です。事前承認の権限を持つ別の人が**事前承認を確定**を選択すると有効になります。事前承認を使っても、必要な承認者の数は減りません。アクションの実行方法、要求内容、対象サービスやチーム、またはリスクを変更すると、既存の承認は取り消され、事前承認は再び承認待ちになります。

ユーザーまたは Mole Agent が事前承認の対象となるインシデントでアクションを開始すると、そのリクエストは事前承認者が承認したものとして記録され、開始したユーザーの権限ですぐに実行されます。開始したユーザーには引き続き `alerts.incidents.remediate` が必要です。通常の承認と同様に、自分のリクエストは承認できません。リクエストしたユーザー自身の事前承認はカウントされません。他の事前承認者が必要な人数に満たない場合（L2 は 1 人、L3 は 2 人）、リクエストは通常どおり承認待ちになります。組織で事前承認が無効になっている場合、事前承認の期限が切れているか 2 人目の承認を待っている場合、インシデントが対象サービスに属していない場合、または集計期間内の実行回数が上限に達している場合も、承認待ちになります。インシデントでは実行に**事前承認済み**と表示します。タイムラインと監査ログには事前承認による実行として記録し、指定した通知先に実行結果を通知します。

| アクションの横に表示される状態 | 意味 |
|---|---|
| **事前承認なし** | アクションに事前承認がありません。 |
| **事前承認済み · 集計期間内に N/M 回実行済み** | 事前承認は有効です。集計期間内に N 回実行しました。 |
| **事前承認済み · 2人目の承認待ち** | L3 アクションを承認した人がまだ 1 人だけです。 |
| **事前承認済み · 実行回数の上限に達しました** | 過去の実行が集計期間の対象外になるまで、事前承認では実行できません。 |
| **事前承認の期限切れ** | 有効期限が過ぎています。更新するには、事前承認を設定し直してください。 |
| **事前承認済み · 組織で無効** | ページ上部のスイッチがオフになっています。 |

## API

| 操作 | エンドポイント |
|---|---|
| アクションとクラスターを管理する | [`/api/v1/alerts/remediation/actions`, `/clusters`](/ja/api/alerting/remediation) |
| インシデントでアクションの実行を開始する | [`POST /api/v1/alerts/incidents/{id}/remediations`](/ja/api/alerting/remediation#インシデントでアクションを実行する) |
| 事前承認の設定を取得する、またはオン・オフを切り替える | `GET`, `PUT /api/v1/alerts/remediation/preapproval` |
| アクションの事前承認を設定、解除、または確定する | `PUT`, `DELETE /api/v1/alerts/remediation/actions/{id}/preapproval`, `POST /api/v1/alerts/remediation/actions/{id}/preapproval/confirm` |
