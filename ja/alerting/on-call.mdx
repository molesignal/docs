エスカレーションポリシーは、インシデントの通知先と通知順序を決めます。各ステップでは、個人、チーム、オンコールスケジュールを指定できます。スケジュールを指定すると、固定の担当者ではなく、当番に通知します。 **アラート → オンコールスケジュール**と**アラート → エスカレーション**を開きます。閲覧には、`schedules.read`と `alerts.escalations.read`が必要です。スケジュールの作成、変更、削除には、それぞれ`schedules.create`、`schedules.update`、`schedules.delete`が必要です。ポリシーの変更には、 `alerts.escalations.manage`が必要です。

## 通知が担当者に届くまで

1. ルールが発火し、インシデントを作成します。インシデントにはルールのエスカレーションポリシーが適用されます。ルールがデフォルトポリシーを使用する場合は、 [アラートルーティング](/ja/alerting/routing)がポリシーを選択します。
2. ポリシーのステップ1を実行し、各通知先に通知イベントを送ります。通知先がユーザーの場合はそのユーザーに、スケジュールの場合は現在のオンコール担当者に、チームの場合はチーム全体に送ります。
3. [通知ポリシー](/ja/notification-channels#テンプレートとポリシーを作成する)は、各イベントについて、使用するコネクター、担当者ごとの配信順序、フォールバックルートを決めます。
4. ステップの**確認タイムアウト**内に誰も確認しない場合、次のステップを実行します。この処理は、インシデントが確認または解決されるか、すべてのステップが完了するまで続きます。 [確認済みだが未解決](#確認済み・未解決)を設定すると、確認後も未解決のインシデントは未確認に戻り、再度通知します。

インシデントに一致するサイレンスが有効な間は、エスカレーションを一時停止します。サイレンスが終了すると、エスカレーションを再開します。[サイレンス中の通知](/ja/alerting/silences#サイレンス中の通知)を参照してください。 `alert`ノードが複数ある場合、各ルールは1つのノードに属し、そのノードがルールのインシデントもエスカレーションします。詳細は [ロールベースのデプロイ](/ja/deployment/role-based#アラートノード間の処理分担)を参照してください。

## オンコールスケジュール

**オンコールスケジュール**では、各スケジュールのタイムゾーン、ローテーション、メンバー、現在のオンコール担当者、次の引き継ぎ、ステータスを一覧で確認できます。一覧の上部には、スケジュール、現在のオンコール担当者、今週の引き継ぎ、臨時の担当の概要が表示されます。スケジュール、チーム、オーナー、タイムゾーン、ステータスで絞り込むか、 **自分が参加するスケジュールのみ**を選択します。一覧の上にある**自分のシフトを購読**を選択すると、ログイン中のアカウントのシフトをスケジュール横断でカレンダーアプリに追加できます。詳しくは[カレンダーの購読](#カレンダーの購読)を参照してください。 **シフト交代**には、送信した交代依頼と受信した交代依頼、および回答待ちの件数が表示されます。詳しくは[シフト交代](#シフト交代)を参照してください。

| ステータス | 意味 |
|---|---|
| **有効** | オンコール担当者がいます。 |
| **まもなく交代** | 次の引き継ぎまで2時間以内です。 |
| **開始前** | 最初のローテーションはまだ始まっていません。 |
| **一時停止中** | スケジュールは一時停止中で、オンコール担当者はいません。 |
| **担当者不在** | 現在、オンコール担当者はいません。 |

### スケジュールを作成する

1. **スケジュールを作成**を選択します。
2. **基本情報**で、**スケジュール名**、**説明**、**タイムゾーン**（例： `Asia/Shanghai`）、**チーム**を入力します。
3. **ローテーションルール**で、各ローテーションを設定します。

   | 項目 | 用途 |
   |---|---|
   | ローテーション名 | 例：`primary`。 |
   | **ローテーションの切り替え頻度** | **毎日**、**毎週**、**平日**（月曜から金曜まで毎日）、または**カスタム間隔**を選択します。**カスタム間隔**では**周期（時間）**を指定します。 |
   | **開始日時**、**引き継ぎ時刻** | ローテーションを開始する日時と、シフトを交代する時刻を指定します。 |
   | **指定した日時に終了** | 任意で**終了日時**を指定します。その日時以降、このローテーションにはオンコール担当者がいなくなります。 |
   | **メンバー（順番に担当）** | 担当する順番にメンバーを指定します。 |
   | **特定の曜日・時間帯に限定** | 週のうち指定した時間帯だけを対象にします。時間帯ごとに**曜日**、**開始時刻（HH:MM）**、**終了時刻（HH:MM）**を、スケジュールのタイムゾーンで分単位まで指定します。**時間帯を追加**を使うと、9:30–12:00と13:30–18:00のように複数の時間帯を設定できます。終了時刻が開始時刻以前の場合は翌日まで続き、開始した曜日の時間帯として扱います。終日を指定するには、00:00–24:00と設定します。 |
   | **祝日** | **祝日カレンダー**に基づいて、**祝日を区別しない**（デフォルト）、**祝日を除外**、**祝日のみ**のいずれかを選択します。詳しくは[祝日カレンダー](#休日カレンダー)を参照してください。祝日を除外する平日ローテーションの下に祝日用のローテーションを追加すると、祝日にも担当者を割り当てられます。 |

4. 必要に応じて**担当交代に承認が必要**をオンにします。依頼先のメンバーが交代を承認した後、スケジュールの管理者が承認すると、交代が反映されます。
5. **今後7日間**で、担当順、引き継ぎ時刻、各シフトの担当者をプレビューします。
6. **スケジュールを作成**を選択します。一時停止した状態で保存するには、**下書きを保存**を選択します。

複数のローテーションが同じ時間帯をカバーする場合は、一覧で最も上にある、オンコール担当者がいるローテーションが優先されます。夜間や週末などを担当するローテーションは、最初のローテーションの下に追加します。

引き継ぎには、スケジュールのタイムゾーンの現地時刻を使います。たとえば、ニューヨークの09:00に引き継ぐローテーションでは、年間を通して09:00に引き継ぎます。夏時間の切り替えをまたぐシフトは23時間または25時間になります。時計を進めたときに飛ばされる1時間に引き継ぎ時刻がある場合は、その直後の最初の時刻に引き継ぎます。時計を戻したときに繰り返される1時間に該当する場合は、早い方の時刻に引き継ぎます。プレビュー、タイムライン、カレンダーの購読、オンコール負荷は、すべてサーバーが同じルールで計算します。

### 臨時の担当

休暇、シフト交代、インシデントなどへの対応として、オーバーライドを使って一定期間のオンコールを特定のメンバーに割り当てられます。スケジュールで**オーバーライドを追加**を選択し、**代理担当者**を選びます。 **理由**、**開始時刻**、**終了時刻**を入力して保存します。指定した期間中は、オーバーライドがすべてのローテーションより優先されます。

同じスケジュール内で、複数のオーバーライドの期間を重複させることはできません。開始時点で代理担当者が別のスケジュールのオンコールを担当している場合や、開始時刻がすでに過ぎていてオーバーライドが即時に有効になる場合は、フォームに警告が表示されます。 **代替対応を終了**を選択すると、適用中のオーバーライドを予定より早く終了できます。

### シフト交代

シフト交代では、管理者にオーバーライドを依頼せずに、同じスケジュールの別のメンバーにシフト内の指定した時間帯の担当を依頼できます。スケジュールの詳細にある**シフト交代**で**交代を依頼**を選択し、依頼者の今後30日以内のシフトを1つ選択します（または開始日時と終了日時を入力します）。**交代するメンバー**を選び、必要に応じてメモを追加して、**依頼を送信**を選択します。依頼者は、指定した時間帯を通して、そのスケジュールの唯一のオンコール担当者である必要があります。結果が確定していない交代依頼と時間帯が重なる場合は、依頼できません。

| ステータス | 意味 |
|---|---|
| **回答待ち** | 依頼先のメンバーは**承認**または**辞退**を選択でき、依頼者は**取り下げ**を選択できます。 |
| **承認待ち** | **担当交代に承認が必要**がオンで、依頼先のメンバーが承認済みです。スケジュールの管理者は**承認**または**却下**を選択できます。 |
| **反映済み** | 交代を引き受けたメンバーを代理担当者とするオーバーライドがスケジュールに追加されています。 |
| **辞退**、**却下済み**、**取り下げ済み** | 交代依頼は終了し、スケジュールは変更されていません。 |
| **期限切れ** | 交代が確定する前に、指定した時間帯が終了しました。 |

各段階で関係者に通知します。依頼時は依頼先に、辞退時は依頼者に通知します。承認待ちになった場合は、スケジュールの作成者、最後に編集したメンバー、依頼者に通知します。交代が反映または却下された場合は依頼者と依頼先に、取り下げられた場合は依頼先に通知します。組み込みポリシー [シフト交代：関係者に通知](/ja/notification-channels#組み込みポリシー)がこれらの通知を送信します。反映済みの交代は、スケジュールの**変更履歴**に他の変更とともに表示されます。

### カレンダーの購読

スケジュールの**その他**メニューで**カレンダーを購読**を選択すると、スケジュール内のすべてのシフトを Google Calendar、Outlook、Apple Calendarなどのカレンダーアプリに追加できる購読アドレスが発行されます。一覧の上にある**自分のシフトを購読**を選択すると、ログイン中のアカウントのシフトをスケジュール横断で購読できます。カレンダーアプリは約1時間ごとにデータを更新します。対象期間は過去30日間から今後90日間までで、オーバーライドとシフト交代も含まれます。

アドレスは一度だけ表示されます。アドレスを知っていれば、誰でもシフトを閲覧できます。アクセスのたびに購読者の権限を確認します。購読者のアカウントが無効になった場合、組織から外れた場合、またはスケジュールの閲覧権限を失った場合、そのアドレスからシフトを取得できなくなります。**アドレスをリセット**を選択すると、新しいアドレスが発行され、古いアドレスは即座に無効になります。 **購読を停止**を選択すると、購読が停止します。**カレンダーをエクスポート**で取得する`.ics`ファイルとは異なり、購読にはスケジュールの変更が反映されます。

### スケジュールの詳細と操作

スケジュールを開くと、現在のオンコール担当者と担当開始時刻、次の引き継ぎ、ローテーションルール、臨時の担当、[シフト交代](#シフト交代)、**今後7日間**のタイムライン、**メンバー別の担当負荷（過去30日間）**、スケジュールの**変更履歴**を確認できます。メンバー別の担当負荷では、各メンバーのオンコール担当時間、受信したアラート通知の件数、夜間（スケジュールのタイムゾーンの22:00から08:00まで）や週末に受信した件数、通知を受けた夜の数がわかります。これは [インサイト](/ja/alerting/incidents#インサイト)の**オンコール負荷**と同じ指標です。スケジュールのメニューには、次の操作があります。

| 操作 | 効果 |
|---|---|
| **スケジュールの編集** | スケジュールとそのローテーションを変更します。 |
| **臨時の担当を追加** | オーバーライドを追加します。 |
| **スケジュールを一時停止** / **スケジュールを再開** | スケジュールを一時停止するとオンコール担当者がいなくなるため、そのスケジュールを対象とするステップでは誰にも通知されません。 |
| **スケジュールをコピー** | `<name> copy`という名前のコピーを作成します。 |
| **カレンダーを購読** | カレンダーの購読アドレスを発行します。詳しくは[カレンダーの購読](#カレンダーの購読)を参照してください。 |
| **カレンダーをエクスポート** | カレンダーに取り込める`.ics`ファイルとしてシフトをダウンロードします。 |
| **スケジュールを削除** | スケジュールを削除します。 |

[ホーム](/ja/home#自分のオンコール)には、ログイン中のアカウントの現在または次のシフトが表示されます。オンコールイベントの通知方法は、メンバーごとに[アカウント設定](/ja/account#通知)で選択できます。

### アラートを受信できないメンバー

オンコール担当者がアラートを受信できない場合、インシデントが発生しても、その担当者には通知が届きません。MoleSignalは、メンバーごとの個人設定にある緊急度の高い通知ステップに基づいて、各メンバーを分類します。

| ステータス | 意味 |
|---|---|
| 通知可能 | 個人向けのアラート通知がオンで、少なくとも1つのステップに、有効なコネクター上で有効かつ確認済みの通知方法が設定されています。 |
| グループのみ | 個人向けの通知方法はありませんが、チームまたは組織のデフォルトルートでグループチャットに通知できます。 |
| 通知不可 | どちらの方法でも通知できません。 |

通知不可のメンバーには、スケジュールのメンバー一覧とエスカレーションポリシーの各ステップにマークが表示されます。次のオンコール担当者がアラートを受信できない場合は、スケジュールページの上部にその旨が表示されます。スケジュールに参加しているメンバーがアラートを受信できない場合は、[アカウント設定](/ja/account#通知) と[ホームページ](/ja/home)のオンコールパネルに通知が表示されます。次のシフトの担当者がアラートを受信できない場合は、シフト開始の30分前に、組み込みポリシー[通知不可のオンコール担当者：担当者とスケジュール管理者に通知](/ja/notification-channels#組み込みポリシー)が担当者とスケジュール管理者に通知します。

インシデントがエスカレーションされ、オンコール担当者を含め、そのステップで誰もアラートを受信できない場合は、確認応答のタイムアウトを待たずに次のステップに進みます。タイムラインには **レベルNでは誰もアラートを受信できなかったため、次のレベルに進みました**と表示されます。ポリシー全体で誰もアラートを受信できない場合、インシデントは未解決のままになり、タイムラインとポリシーページにその旨が表示されます。

## エスカレーションポリシー

**エスカレーション**には、各ポリシーの通知先と通知タイミングが表示されます。

1. **新規ポリシー**を選択し、**ポリシー名**を入力します。
2. 各ステップで、**適用する最小重大度**（**任意の重大度**または最小重大度）、 **確認タイムアウト**（1、5、10、15、30分、または1時間）、**通知先**（**ユーザー**、 **スケジュール**、または**チーム**）を選択します。**ステップを追加**で次のステップを追加します。
3. 必要に応じて、**確認されるまでポリシー全体を繰り返す**をオンにし、**最大繰り返し回数**を設定します。
4. 必要に応じて、**確認済み・未解決**を設定します。[以下](#確認済み・未解決)を参照してください。
5. **緊急度**で、ポリシーが緊急度を設定する方法を選択します。[緊急度](#緊急度)を参照してください。
6. **ポリシーを作成**を選択します。

ステップの最小重大度がインシデントの重大度を上回る場合、そのステップをスキップします。各配信のコネクターとフォールバックルートは、エスカレーションポリシーではなく**設定 → 通知 → ポリシー**で設定します。

### 確認済み・未解決

インシデントが確認後も未解決の場合、**確認済み・未解決**の設定に従ってオンコール担当に差し戻します。30分、または1、2、4時間を選択します（APIでは5分から24時間まで指定できます）。確認から指定時間が経過しても未解決の場合、インシデントは**レビュー待ち**に戻り、担当者に再通知します。テンプレート内の `{{escalation.reason}}` は `ack_timeout` になります。再通知後も確認されない場合は、通常どおりエスカレーションを続けます。デフォルトの**再通知しない**では、インシデントが解決するまで確認済みの状態を維持します。スヌーズ中のインシデントは、代わりにスヌーズが終了した時点で**レビュー待ち**に戻ります。

### 緊急度

重大度はシグナルの深刻さを表し、緊急度は担当者に今すぐ対応を求めるかどうかを決めます。インシデントの作成時には、緊急度レベルを1つ割り当てます。組み込みの2つのレベルは次のように動作します。

| | 高緊急度 | 低緊急度 |
|---|---|---|
| エスカレーション | ステップを順に進めて呼び出します | 最初のステップだけ通知し、後続のステップには進まず、ポリシーも繰り返しません |
| ユーザー別通知 | ユーザーの高緊急度用ステップを使用します | ユーザーの低緊急度用ステップを使用します。未設定の場合は、高緊急度用の最初のステップだけを使用します |
| 通知抑制時間帯 | ユーザーの**通知を抑制する時間帯も緊急度の高いアラートを受信**の設定に従います | 通知抑制時間帯は通知しません |

組織ごとに、レベルの名前や動作を変更したり、レベルを追加したりできます。 [緊急度と優先度のレベル](#緊急度と優先度のレベル)を参照してください。

ルール、外部アラート、アラートパイプライン、またはインシデントを手動で作成したユーザーが指定した緊急度を優先します。指定がない場合は、インシデントのエスカレーションポリシーの**緊急度**で決まります。

| 選択肢 | 動作 |
|---|---|
| **重要度に応じて設定**（デフォルト） | 組織で設定した重大度ごとの緊急度レベルを割り当てます。変更しない限り、クリティカルとエラーは高緊急度、警告と情報は低緊急度です。 |
| **常に同じレベル** | すべてのインシデントに、**緊急度**で選択したレベルを割り当てます。 |
| **サポート時間帯に応じて設定** | **サポート時間内**と**サポート時間外**に別々のレベルを割り当てます。デフォルトはそれぞれ高緊急度と低緊急度です。サポート時間帯は1つのタイムゾーンで週ごとに設定し、[休日カレンダー](#休日カレンダー)で休日を除外できます。**サポート時間の開始時に、時間内のレベルより緊急度が低い未確認のインシデントの緊急度を引き上げ、最初のステップから再度呼び出す**をオンにすると、夜間に作成されて朝まで確認されなかったインシデントは、サポート時間の開始時に時間内のレベルに引き上げられ、レベル1に再通知します。タイムラインには**サポート時間開始：緊急度を…に引き上げ、レベル1に再通知しました**と表示されます。 |

**最初のステップで止まるレベルのインシデントも次のステップへエスカレーションする**をオンにすると、このポリシーではすべてのレベルが高緊急度と同じようにエスカレーションします。重大度を指定しない外部アラートは高緊急度として扱います。組織で定義していない緊急度はインシデントの作成時に無視し、ポリシーで緊急度を決定します。 **重要度に応じて設定**以外を選択すると、ポリシー一覧のステップの並びの後に選択した設定が表示されます。

<Note>
重大度に応じて緊急度を決める場合、警告と情報のインシデントは最初のステップだけで通知し、通知抑制時間帯には通知しません。すべてのインシデントでステップを順に進めて呼び出すには、ポリシーの緊急度を**常に同じレベル**に設定し、高緊急度を選択します。
</Note>

### 緊急度と優先度のレベル

**設定 → アラート → 優先度と緊急度**を開き、組織のレベルを設定します。レベルの参照には `alerts.importance.read`、変更には `alerts.importance.manage` が必要です。

**緊急度レベル**には、緊急度の高い順にレベルが表示されます。矢印でレベルを1つ上または下に移動できます。各レベルには次の設定があります。

| 設定 | 用途 |
|---|---|
| 名前 | 一覧、フィルター、メッセージに表示するレベル名です。 |
| **次のステップへエスカレーション** | エスカレーションポリシーのステップを順に進めて呼び出します。オフの場合は、最初のステップだけ通知します。 |
| **通知抑制時間帯の動作** | **ユーザーの設定に従う**（**通知を抑制する時間帯も緊急度の高いアラートを受信**）か、**常に通知しない**かを選択します。 |
| **ユーザー別ステップ** | ユーザーに設定された2組のステップのうち、**高緊急度用ステップ**と**低緊急度用ステップ**のどちらを使うかを選択します。 |
| **重要度に応じて設定** | ポリシーが重大度に応じて緊急度を設定する場合に、このレベルに割り当てる重大度を選択します。各重大度は1つのレベルにのみ割り当てます。 |

組み込みのレベル `high` と `low` は名前や設定を変更できますが、削除はできません。**緊急度レベルを追加**では、最大3つを追加でき、合計5つまで設定できます。`urgent` などの**新しいレベルのキー**は、小文字の英字で始まり、小文字の英字、数字、アンダースコアのみを使用できます。ルール、外部アラート、アラートパイプライン、APIでは、キーでレベルを指定します。割り当て済みのレベルを後から削除した場合、そのインシデントは高緊急度として扱います。

**優先度レベル**では、組織で使用する優先度レベルの数（1〜9）と、各レベルの名前と説明を設定します。インテグレーションやインポートしたファイルで使用するため、キーは `P1`、`P2` などのままです。外部アラートやアラートパイプラインが設定範囲外の優先度を指定した場合は、最も低いレベルを割り当てます。テンプレートでは、レベル名を `{{urgency_name}}` と `{{priority_name}}` で参照します。 [テンプレート変数](/ja/notification-channels#テンプレート変数)を参照してください。

### デフォルトポリシー

ルールでは、`escalationPolicyId` でエスカレーションポリシーを指定します。ルールワークベンチで保存するすべてのルールなど、ポリシーの指定がないルールでは、エイリアス `default` を使用します。[アラートルーティング](/ja/alerting/routing)は、ルーティングルール、サービスを所有するチーム、チームラベルに基づいてチームのオンコールポリシーを選択します。該当するポリシーがなければ、大文字と小文字を区別せず、組織内の `default` という名前のポリシーを選択します。そのポリシーもなければ、該当するインシデントはどの通知先にもエスカレーションしません。

最初のルールを作成する前に、`default` という名前のポリシーを作成します。たとえば、ステップ1にメインのオンコールスケジュール、ステップ2にチームリーダーを設定します。インシデントのエスカレーションが始まると、後から `default` ポリシーの名前を変更しても、最初に選択したポリシーを使い続けます。

## 休日カレンダー

休日カレンダーには、休日と振替出勤日を登録します。曜日ごとの適用時間から祝日を除外したり、祝日にのみ適用したりできます。**設定 → アラート → 休日カレンダー**を開きます。カレンダーの閲覧には `alerts.calendars.read`、変更には `alerts.calendars.manage` が必要です。MoleSignal には祝日があらかじめ登録されていません。祝日は年ごとに変わるため、組織ごとに入力またはインポートします。

1. **新規カレンダー**を選択し、**名前**と**説明**を入力します。
2. **曜日**で**年**を選択し、各**日付**を追加します。**種類**には**休日**または **振替出勤日**を指定し、**日の名称**を入力します。**ICSをインポート**では、祝日を収録した `.ics` ファイルを読み込みます。各終日イベントを1日分として追加し、名前に「补班」または「上班」が含まれるか、名前が「班」で終わる場合は、振替出勤日として扱います。カレンダーを保存するまでは何も保存されないため、先に登録内容を確認してください。
3. **カレンダーを作成**を選択します。

曜日ごとの適用時間の**祝日**で、カレンダーに基づく祝日の扱いを選択します。

| 選択肢 | 動作 |
|---|---|
| **祝日を区別しない**（デフォルト） | 祝日をほかの日と同じように扱います。 |
| **祝日を除外** | 休日には時間設定を適用しません。振替出勤日は月曜日として扱います。 |
| **祝日のみ** | 休日にのみ時間設定を適用します。 |

日付はカレンダーを使用する機能のタイムゾーンで解釈します。午前0時をまたぐ時間帯は、開始日に属します。カレンダーは、[オンコールスケジュール](#スケジュールを作成する)のローテーション、 [緊急度](#緊急度)のサポート時間、[ルーティングルール](/ja/alerting/routing#ルールを作成する)や [通知ポリシー](/ja/notification-channels#テンプレートとポリシーを作成する)の時間条件、アラートパイプライン、 [サイレンス](/ja/alerting/silences#サイレンスポリシー)の**祝日**の適用時間帯で使用できます。使用中のカレンダーは削除できません。ダイアログには、そのカレンダーを使用している項目が表示されます。変更は1分以内にすべてのノードに反映されます。フェデレーション内のほかのクラスターでも、組織のカレンダーを利用できます。

## インポートとエクスポート

エスカレーションポリシーとオンコールスケジュールの各一覧の上部にある**インポート / エクスポート**を使うと、アラートルールと同様に、ファイルを使って組織間やクラスター間で移行できます。

- **すべてのエスカレーションポリシーをエクスポート**または**すべてのスケジュールをエクスポート**を選択すると、バンドルをダウンロードできます。項目を選択している場合は、選択した項目のみをダウンロードします。バンドル内の参照では、ユーザーをメールアドレスで、チーム、スケジュール、エスカレーションポリシー、休日カレンダーを名前で指定します。
- **エスカレーションポリシーをインポート…**または**スケジュールをインポート…**では、JSONまたはYAMLのバンドルを先に検証し、作成、更新、変更なし、エラーの各項目を一覧表示します。**新規作成のみ行い、同じ名前の既存項目は変更しない**を選択すると、既存の項目をスキップします。各項目は名前で照合し、すべての参照先が組織内に存在する必要があります。1件でもエラーがあれば、何も書き込みません。

バンドルにはスケジュールのローテーションと設定が含まれますが、一時的な代替担当やシフト交換は含まれません。既存のスケジュールにインポートする場合は、一時的な代替担当とシフト交換を保持します。ポリシーのインポートには `alerts.escalations.manage` が必要です。スケジュールのインポートには `schedules.create` が必要です。ルーティングルールも同様にインポートとエクスポートができます。 [アラートルーティング](/ja/alerting/routing#インポートとエクスポート)を参照してください。

**スケジュールをインポート…**では、OpsgenieとPagerDutyのAPIからもスケジュールを読み込めます。 [OpsgenieまたはPagerDutyからスケジュールを移行する](/ja/alerting/schedule-migration)を参照してください。
