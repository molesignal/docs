ルールは、発生してはならない状態を定義します。MoleSignal はルールを一定の間隔で評価し、条件を満たすと [インシデント](/ja/alerting/incidents)を作成します。**アラート → ルール**を開きます。ルールの閲覧には `alerts.rules.read` が必要です。ルールの作成や変更には `alerts.rules.manage` が必要です。

## ルールの種類

| 種類 | 評価内容 | 作成場所 |
|---|---|---|
| **しきい値ルール** | SQL または PromQL のクエリ、[APM 指標](/ja/apm#apmの指標でアラートを設定する)、または [RUM 指標](/ja/rum/alerts)を一定の間隔で固定のしきい値と比較します。 | ルール設定画面。 |
| **予測ルール** | クエリ、APM 指標、または RUM 指標の傾向を評価し、リードタイム内にしきい値を超えると予測した場合に発報します。[予測ルール](#予測ルール)を参照してください。 | ルール設定画面の**発報方式**。 |
| **外れ値ルール** | クエリ結果を列の値でグループ化して相互に比較し、他のグループから外れたグループがあれば発報します。[外れ値ルール](#外れ値ルール)を参照してください。 | ルール設定画面の**発報方式**。 |
| **複合ルール** | 他のルールに未解決のインシデントがあるかどうかを、AND、OR、NOT で組み合わせて評価します。[複合ルール](#複合ルール)を参照してください。 | ルール設定画面の**発報方式**。 |
| **ハートビートルール** | cron タスクやバックアップスクリプトなどのジョブが、期限内にチェックインしたかどうかを評価します。[ハートビートルール](#ハートビートルール)を参照してください。 | ルール設定画面の**発報方式**。 |
| **異常検知** | クエリ、APM 指標、または RUM 指標を、過去のデータから学習したベースラインと比較します。 | 異常検知エディター。 |
| **リアルタイムルール** | 取り込み経路に到着したレコードを随時カウントして評価します。 | API のみ。[リアルタイムルール](#リアルタイムルール)を参照してください。 |

## ルール一覧

**ルール**には、すべてのルールのデータソース、トリガー条件、状態、最終評価が表示されます。ルール、サービス、ソースで検索し、**すべて**、**有効**、 **無効**を切り替えます。

| 状態 | 意味 |
|---|---|
| **未評価** | ルールはまだ実行されていません。 |
| **正常** | 前回の評価では条件を満たしませんでした。 |
| **待機中** | 条件を満たしていますが、指定した時間がまだ経過していません。 |
| **発報中** | ルールに未解決のインシデントがあります。 |
| **パイプラインで破棄** | ルールは発報しましたが、[アラートパイプライン](/ja/pipelines/alert-events#イベントの処理結果)が作成予定のインシデントを破棄しました。 |
| **無効** | ルールは下書きとして保存され、実行されません。 |

ルールを開くには、該当するルールまたは同じ行の**編集**を選択します。

## しきい値ルールを作成する

**新規ルール → しきい値ルール**を選択して、ルール設定画面を開きます。

<Steps>
  <Step title="ルールの種類を選択する">
    **メトリクスアラート**、**ログアラート**、**トレースアラート**、**APMアラート**、**RUMアラート**のいずれかを選択します。 **クイックスタート**で、**エラー率の上昇**、**P95 レイテンシの上昇**、**エラーログの急増**、**データなし**などのプリセットを選ぶと、一般的なクエリが入力されます。APM アラートと RUM アラートでは、クエリの代わりにサービスまたはアプリケーションと、指標を選択します。[APM 指標でアラートを発報する](/ja/apm#apmの指標でアラートを設定する)と [RUM アラート](/ja/rum/alerts)を参照してください。
  </Step>
  <Step title="基本情報を入力する">
    **ルール名**（例: `api_high_error_rate`）は、インシデントのタイトルになります。**サービス**でルールとサービスを関連付けて、担当を明確にし、異なるシグナル間でコンテキストを共有します。**説明**には、ルールが何を保護するかを記載します。
  </Step>
  <Step title="発報方式を選択する">
    **クエリとトリガー条件**の上部にある**発報方式**で、**しきい値**（デフォルト）、 [**予測**](#予測ルール)、[**外れ値**](#外れ値ルール)、[**複合**](#複合ルール)、 [**ハートビート**](#ハートビートルール)のいずれかを選択します。複合ルールとハートビートルールはクエリを使いません。下にあるクエリ、テスト、しきい値の項目は、それぞれのルール専用の設定に切り替わります。
  </Step>
  <Step title="クエリを記述する">
    **対象ストリーム**、**評価間隔**（1、5、10 分のいずれか）、 **クエリ言語**（メトリクスの場合は **PromQL**、それ以外は **SQL**）、**クエリ**を設定します。クエリは数値を返す必要があります。評価には、最初の行の最初の列の値を使用します。必要に応じて [**グループ化の基準**](#列でルールをグループ化する)を設定します。ルールでは [`_audit` ストリーム](/ja/settings/data-security#監査ストリーム)を読み取れません。このストリームを指定したルールを保存しようとすると、`400` が返ります。
  </Step>
  <Step title="トリガー条件を設定する">
    各行が 1 つの重大度に対応します。**結果の比較条件**では演算子で結果を**しきい値**と比較し、**継続時間**では条件を満たし続ける必要がある時間を分単位で指定します。**重大度を追加**で行を追加します。条件を満たした中で最も高い重大度を適用します。高い重大度の条件は、低い重大度の条件よりも満たしやすくできません。指定した分数は評価回数に換算します。下にある[**復旧**と**データがない場合**](#復旧と欠損データ)を設定します。
  </Step>
  <Step title="対応ガイドを追加する">
    **Notify と対応**で、**対応ガイド / ランブックURL**を入力します。対応担当者はインシデント一覧からその URL を開けます。通知先はルールではなく、[エスカレーションポリシー](/ja/alerting/on-call#エスカレーションポリシー) と [Notify ポリシー](/ja/notification-channels#テンプレートとポリシーを作成する)で決まります。
  </Step>
  <Step title="調査ガイドを追加する">
    必要に応じて**調査ガイド**に、このルールで発生したインシデントを調査する際の**手順**を記載し、実行する**クエリ**を追加して、開く**ダッシュボード**を選択します。 [調査ガイド](#調査ガイド)を参照してください。
  </Step>
  <Step title="ルールをテスト">
    **ルールをテスト**を選択します。過去 6 時間の実データに対してクエリを実行します。**クエリプレビュー**には結果としきい値の線がグラフに表示され、現在値、推定トリガー回数、スキャンした行数、レイテンシも確認できます。グループ化したルールでは、検出したグループ数も表示されます。
  </Step>
  <Step title="保存する">
    **作成前のチェック**の全項目を満たす必要があります。ルール名を入力し、現在のクエリのテストに成功し、有効なしきい値とランブック URL を設定します。その後、**保存して有効化**を選択します。実行せずに保存する場合は **下書きを保存**を選択します。
  </Step>
</Steps>

ルール設定画面で作成したルールには、エスカレーションポリシーを指定しません。[アラートルーティング](/ja/alerting/routing)がインシデントの振り分け先を決めます。振り分け先が見つからない場合は、`default` という名前のポリシーを適用します。組織にこのポリシーがない場合、該当するインシデントにはエスカレーション先が設定されません。先にポリシーを作成してください。 [デフォルトポリシー](/ja/alerting/on-call#デフォルトポリシー)を参照してください。

## 列でルールをグループ化する

SQL または PromQL クエリを定期的に評価するルールでは、ホストやサービスなど、クエリ結果の列でグループ化できます。ルール設定画面で**グループ化の基準**を設定するか、[ルールの作成](/ja/api/alerting/create-rule#列で分割するルール)時に `query.group_by` を指定します。値の組み合わせごとに、各グループが独立したルールとして動作します。

| 項目 | 動作 |
|---|---|
| グループ | 指定した列の値が同じ行をまとめます。指定した列名と結果の列名の照合では、大文字と小文字を区別しません。 |
| 値 | グループの最初の行から、グループ化に指定した列と時刻列を除く最初の数値列の値を取得します。 |
| トリガー | グループごとにトリガー条件または重大度ごとの条件と比較し、`for_periods` を個別にカウントします。 |
| インシデント | グループごとにインシデントを作成し、グループの値をラベルとタイトル（例: `Errors per host · web-1`）に含めます。グループが復旧条件を満たすと、インシデントを解決します。結果に含まれないグループには値がないため、データがない場合のルール設定に従います。 |
| 上限 | 1 回の評価につき最大 8 列、100 グループです。100 グループを超えた分は評価しません。その回の結果に含まれないグループのインシデントは、そのまま維持します。 |

グループごとに 1 行を、状態が悪い順に返します。

```sql
SELECT host, count(*) AS errors
FROM app_logs
WHERE level = 'error'
GROUP BY host
ORDER BY errors DESC
```

PromQL では、時系列のラベルが列に相当します。そのため、`sum by (instance) (rate(http_requests_total{status=~"5.."}[5m]))` は `instance` でグループ化します。結果に行があっても指定した名前の列がない場合、その回の評価は失敗し、状態は変わりません。ルール設定画面では、クエリのテスト時に列を検証します。APM、RUM、リアルタイム、異常検知のルールはグループ化できません。[外れ値ルール](#外れ値ルール)ではグループ化が必須です。

## 復旧と欠損データ

各ルールでは、未解決のインシデントが復旧する条件と、値が得られない評価の扱いを指定します。ルールのワークベンチで **復旧** と **データがない場合** を設定するか、[ルールを作成](/ja/api/alerting/create-rule#復旧とデータ欠損)するときに `trigger.recovery` と `trigger.no_data` を指定します。

- **復旧しきい値:** 値がこのしきい値を正常側に戻る方向に超えると、インシデントが復旧します。たとえば、90 を超えると発報するルールは、80 を下回ると復旧します。値が発報しきい値付近で変動しても、発報と復旧を繰り返しません。
- **復旧までの時間:** 値が正常側にとどまる時間がこの設定値に達すると、インシデントが復旧します。
- **データがない場合:** クエリが値を返さない場合や、グループ化したルールの結果に特定のグループが含まれない場合の動作を設定します。

| 選択肢 | 動作 |
|---|---|
| 復旧 | 評価を条件不一致として扱い、未解決のインシデントを復旧します。デフォルトの設定です。 |
| 状態を維持 | 状態は変わらず、ルールに **データなし** と表示されます。異常検知ルールのデフォルトです。 |
| データなしのインシデントを作成 | 状態を維持し、データがない状態が指定時間続くと、**データなし** のインシデントを作成して `NO DATA · <title>` として通知します。データが再び届くと解決します。ホストやサービスを廃止した場合は、手動でインシデントを解決してください。データが再び届くまでは、インシデントを再作成しません。 |
| ゼロ | 欠損値を 0 として比較します。件数の評価に適しています。 |

リアルタイムルールでは、どちらの設定も使用しません。カウントが発報条件を下回ると、すぐに解決します。

## 異常検知ルール

異常検知ルールは、値がその値自体の履歴から予測した範囲を外れると発報するため、固定のしきい値は不要です。 **新規ルール → 異常検知ルール** を選択します。

| セクション | フィールド | 設定内容 |
|---|---|---|
| 基本情報 | **ルール名**、**重大度**、**サービス** | サービスは任意です。指定すると、異なるシグナルを関連付けるためのコンテキストを追加できます。 |
| 検知クエリ | **データソース** | **クエリ**、サービスまたはエンドポイントの **APM 指標**、アプリケーションの **RUM 指標** から選択します。[APM 指標の異常に対するアラート](/ja/apm/insights#apm-指標の異常をアラートで通知する)と [RUM の異常検知ルール](/ja/rum/alerts#異常検知ルール)を参照してください。 |
| | **ストリーム**、**ストリームタイプ**、**クエリ言語**、**クエリ** | 平均値、P95、件数など、単一の数値を返すクエリを指定します。 |
| | **評価ウィンドウ** | 1 分、5 分、15 分、または 1 時間です。 |
| 検知方式 | **アルゴリズム** | 中央値に基づくロバストな **MAD**、または直近の変動に追従する **EWMA** を選択します。 |
| | **参照期間（日）** | 同じ時刻の履歴を 1〜30 日分参照します。デフォルトは 7 日です。 |
| | **感度（k·σ）** | ベースラインからの乖離がばらつきの k 倍を超えると発報します。値が大きいほど感度が下がります。デフォルトは 3 です。 |
| | **平滑化（α）** | EWMA のみに適用し、範囲は `(0, 1]` です。値が大きいほど、直近のサンプルに追従します。 |
| | **発報までの評価回数** | インシデントを作成するまでに、連続して異常と判定する必要がある評価回数です。 |
| | **週ごとの周期性** | 同じ曜日の値のみを比較し、平日と週末の違いによる発報を防ぎます。参照期間は 7 日以上が必要で、28 日以上を推奨します。 |

## 予測ルール

予測ルールは指標のトレンドを将来に延長し、リードタイム内にしきい値を超えると予測した場合に発報します。ディスク使用量、クォータ、接続数など、徐々に上限に近づく指標に適しています。 **発報方式** で **予測** を選択し、しきい値ルールと同じ方法でクエリを記述して、次の項目を設定します。

| 設定 | 補足 |
|---|---|
| **予測値** | `> 90` のように、比較演算子としきい値を指定します。 |
| **リードタイム** | しきい値を超えると予測した時点のどれくらい前に発報するかを指定します。1 時間、6 時間、12 時間、または 1 日、2 日、3 日、7 日から選択します。デフォルトは 1 日です。 |
| **参照期間** | 予測に使うトレンドを過去何日分参照するかを指定します。1 日、3 日、7 日、14 日、30 日から選択します。デフォルトは 7 日です。 |
| **モデル** | **線形トレンド**、 **日次パターン**、 **週次パターン** から選択します。日次または週次で変動する指標には、前日または前週の同じ時刻の値にトレンドを加えるパターンを使用します。週次パターンには 7 日以上の参照期間が必要です。 |

評価のたびに現在の値を時系列に追加します。新しいルールやクエリを変更したルールでは、最初に過去の複数の時点をクエリして履歴を補います。データポイントが 6 個未満の場合や、日次パターンまたは週次パターンで 1 周期分のデータがない場合は、その回の判定を行いません。インシデントには、しきい値を超えると予測した時刻とその時点の予測値が表示されます。予測ルールでは重大度を 1 つと継続時間を設定します。復旧しきい値はありませんが、 [データがない場合](#復旧と欠損データ)の動作は設定できます。

## 外れ値ルール

外れ値ルールは、固定のしきい値ではなく、クエリで分けたグループ同士を比較します。たとえばエラー件数をホスト別に集計すると、ほかのホストよりエラーが大幅に多いホストが発報の対象になりますが、全ホストで一斉に件数が増えても発報しません。 **発報方式** で **外れ値** を選択し、クエリを記述して [**グループ化の基準**](#列でルールをグループ化する)を入力し、次の項目を設定します。

| 設定 | 補足 |
|---|---|
| **許容範囲** | スケーリングした偏差の何倍離れると外れ値とみなすかを、0.5〜10 の範囲で指定します。デフォルトは 3 です。値が小さいほど感度が上がります。 |
| **検出方向** | **高い値と低い値の両方**、 **高い値のみ**、 **低い値のみ** から選択します。 |

グループの中央値と中央絶対偏差（MAD）を基に乖離を測定し、グループ間の差がほとんどない場合にわずかな変動を外れ値と判定しないようにします。外れ値を検出したグループごとにインシデントを作成し、乖離の大きさを表示します。値があるグループが 3 つ未満の場合は、その回の判定を行いません。外れ値ルールでは APM 指標や RUM 指標を使用できません。重大度を 1 つと継続時間を設定します。

## 複合ルール

複合ルールは、複数のルールをまとめて評価します。組み合わせた各ルールは未解決のインシデントがある間は真となり、式でそれらを組み合わせます。たとえば、`A && B` はエラー率とレイテンシの両方が発報した場合にのみ通知し、 `A && !B` は下流が正常な間に限り、上流に問題があると判定します。 **複合** を **発報方式** で選択します。

| 設定 | 補足 |
|---|---|
| **ルール** | 最大 10 個のルールを指定できます。各ルールには A、B、C のように名前が付きます。 |
| **式** | `A && (B \|\| C)` のように、各ルールを表す文字を `&&`（AND）、`\|\|`（OR）、`!`（NOT）と括弧で組み合わせます。 |
| **各ルールのインシデントを複合インシデントの配下にまとめる** | 複合ルールがインシデントを作成すると、組み合わせたルールの未解決のインシデントをその配下に[統合](/ja/alerting/incidents#インシデントを統合する)し、個別の通知を停止します。その後に作成したインシデントも統合します。 |

複合ルールはクエリを実行しません。テストはできず、 [データがない場合](#復旧と欠損データ)の設定もありません。複合ルールを別の複合ルールに組み込むことはできません。組み合わせたルールを削除すると、そのルールは偽として扱います。インシデントには、真になったルールを示す文字が表示されます。

## ハートビートルール

ハートビートルールでは、ジョブからの報告を待ちます。cron タスク、バックアップスクリプト、バッチジョブなどが実行のたびにチェックインアドレスへリクエストを送信します。チェックイン間隔に猶予期間を加えた時間内にチェックインがない場合や、チェックインで失敗が報告された場合に発報します。 **ハートビート** を **発報方式** で選択します。

| 設定 | 補足 |
|---|---|
| **チェックイン間隔** | ジョブの実行間隔を 1 分〜7 日の範囲で指定します。デフォルトは 60 分です。 |
| **猶予期間** | チェックイン間隔を過ぎてから未着とみなすまでの追加の待機時間です。最大 1 日で、デフォルトは 5 分です。 |

保存すると、ダイアログにチェックインアドレスと `curl` の例が表示されます。アドレスを表示するのはこのときだけです。ジョブが成功した場合は、このアドレスにリクエスト（`GET` または `POST`）を送信します。失敗した場合は `?status=fail` を追加してすぐに発報します。`POST` のボディの先頭部分をチェックインのメッセージとしてインシデントに保存するため、ログの末尾数行を送信する用途に適しています。

```bash
if ./backup.sh; then
  curl -fsS "$HEARTBEAT_URL"
else
  curl -fsS "$HEARTBEAT_URL?status=fail"
fi
```

ハートビートルールの編集画面には、前回のチェックインと次回のチェックイン期限が表示されます。 **チェックインアドレスをリセット** を選択すると、新しいアドレスを発行し、古いアドレスはすぐに無効になります。チェックインアドレスへのアクセスにサインインは不要で、アドレスに含まれるトークンのみが必要です。[パブリックアクセス](/ja/public-access)と [ハートビートのチェックイン](/ja/api/alerting/heartbeats)を参照してください。ハートビートルールはクエリを実行しません。テストはできず、 [データがない場合](#復旧と欠損データ)の設定もありません。

## リアルタイムルール

リアルタイムルールは、タイマーではなく取り込み処理の中で実行されます。取り込みノードが受け付けたすべてのレコードを、そのストリームのリアルタイムルールに照らして評価し、一致したレコードを `periodSecs` 秒のスライディングウィンドウに追加します。ルールを担当するアラートノードは、書き込みを受け付けるすべてのノードからウィンドウ内の一致件数を毎秒取得して合計します。合計がトリガー条件を満たすとインシデントをオープンし、満たさなくなると解決します。書き込みから反映までの遅延は最大 1 秒です。

| 項目 | 動作 |
|---|---|
| ステートメント | SQL の `SELECT count(*) FROM <stream> [WHERE <condition>]` を使用します。テーブルにはルールの `stream` を指定します。条件では、フィールドとリテラルを比較し（`=`, `!=`, `<`, `<=`, `>`, `>=`）、`IN`, `BETWEEN`, `LIKE`, `ILIKE`, `IS [NOT] NULL` を使用できます。`AND`, `OR`, `NOT` と丸括弧で条件を組み合わせます。フィールドが存在しないか null の場合、比較条件には一致しません。 |
| ウィンドウ | `periodSecs` に 1～3600 を指定します。 |
| トリガー | `operator` には `gt` または `gte`、`for_periods` には `0` または `1` を指定します。`thresholds` の段階ごとに、件数に応じた重大度を設定します。 |
| インシデント | インシデントは通常のライフサイクルに従います。ルールごとにアクティブなインシデントは 1 件で、`silence_secs` のクールダウン、エスカレーション、通知が適用されます。 |

[ルールの作成](/ja/api/alerting/create-rule) API は、この制限を外れるリアルタイムルールを `400` で拒否します。書き込みを受け付ける各ノードは、件数をメモリに保持し、5 秒ごとにウィンドウのスナップショットをメタデータデータベースに保存します。ノードは再起動時にスナップショットを読み込むため、失うのは最大で直近 5 秒分です。ノードが停止中または応答しない間、担当のアラートノードは、その件数がウィンドウの範囲外になるまで、代わりにそのノードの最新スナップショットを使用します。別のアラートノードがルールを引き継いでも情報は失われません。引き継いだノードは、オープン中のインシデントから発報状態を復元します。ノード間で件数を取得するには、クラスターベアラートークン（ロール分離構成でも共通の `MS_SELF_TELEMETRY_CLUSTER_TOKEN`）を使用します。トークンがない場合、他のノードの件数はスナップショットからのみ取得できます。

### フェデレーションでのリアルタイムルール

[クラスター間フェデレーション](/ja/settings/data-plane#クラスターフェデレーション)では、各クラスターが自身に書き込まれたレコードをカウントし、デフォルトでは自身の件数だけで判定します。クラスター間で件数を合算するには、判定を担当するクラスターを設定してください。API では `query.home_cluster` を指定します。ルールワークベンチでルールを開いた場合は、**判定クラスター**で現在のクラスターまたは有効なリモートクラスターを選択します。そのクラスターだけが、ルールのインシデントをオープンおよび解決します。ルールを担当するアラートノードは毎秒、組織ごとのトークンを使って、その組織にマッピングされた各クラスターから件数を取得し、自身の件数に加算します。他のクラスターはカウントのみを行います。800 ミリ秒以内に応答しないクラスターには、最後に返した件数を最大 30 秒間使用し、それ以降は 0 件として扱います。これにより、1 秒分の応答が欠けただけでインシデントが解決されることはありません。メトリクス `realtime_federated_counts_failed_total{cluster}` は、応答を取得できなかった回数を記録します。ルールはフェデレーション内で同じ ID を使用するため、すべてのクラスターがそのルールの件数をカウントします。

## 評価遅延

ロール分離クラスターでは、クエリは取り込みノードがフラッシュ済みのデータだけを読み取ります。取り込みバッファー内のレコードがクエリに反映されるまで、最大で `[intake].flush_interval_secs`（デフォルトは 30 秒）かかるため、最新のウィンドウでは件数が実際より少なくなります。ルールワークベンチの**詳細設定**にある**評価遅延**を使うと、各評価のウィンドウを過去にずらせます。たとえば、評価遅延と期間をどちらも 5 分に設定すると、07:00 の評価では 06:50 から 06:55 までのデータを読み取ります。

| 値 | 効果 |
|---|---|
| **自動**（デフォルト） | すべてのロールを単一プロセスで実行する場合は遅延なしです。ロール分離クラスターでは、**設定 → アラート評価**の**評価遅延**（デフォルトは 60 秒）を使用します。 |
| **遅延なし** | 現在時刻までのデータを読み取ります。 |
| 30 秒～1 時間 | ルール固有の遅延を使用します。API では 0～3600 秒を指定できます（`query.delay_secs`）。 |

データなしのチェック、復旧条件、異常検知のベースライン、予測系列、分割ルール、外れ値の評価も、すべて同じ遅延分だけ過去にずらします。ウィンドウをずらした場合、インシデントは読み取った時間範囲をアノテーション `evaluated_window` に記録します。リアルタイムルールはクエリを実行しないため、評価遅延はありません。

## 優先度と緊急度

ルールワークベンチの**Notify と対応**にある**優先度**と**緊急度**で、ルールがインシデントをオープンするときの値を設定します。

- **優先度**：組織の[優先度レベル](/ja/alerting/on-call#緊急度と優先度のレベル)から選択します。デフォルトは P1～P5 で、P1 が最も高い優先度です。未設定の場合、インシデントに優先度は付きません（[アラートパイプライン](/ja/pipelines)で設定することはできます）。重大度から優先度を決定することはありません。
- **緊急度**：**エスカレーションポリシーに従う**（デフォルト）を選ぶと、[インシデントのエスカレーションポリシーで定めた緊急度](/ja/alerting/on-call#緊急度)を適用します。「高」または「低」を選ぶと、すべてのインシデントにその値を適用します。

## 調査ガイド

ルールワークベンチの**調査ガイド**セクションには、そのルールのインシデントを調査する際に最初に行うことを記載します。各項目は任意です。

| 項目 | 内容 | 上限 |
|---|---|---|
| **手順** | 最初に確認する項目とその順序を Markdown で記載します。 | 8,000 文字 |
| **クエリ** | **名前**、クエリ言語（**promql** または **sql**）、SQL の場合は**ストリーム**とその**ストリームタイプ**、および**クエリ**を指定します。 | 1 件あたり最大 4,000 文字のクエリを 10 件 |
| **ダッシュボード** | インシデントから開くダッシュボードを指定します。 | ダッシュボード 5 件 |

ガイドは、ルールの各インシデントの**調査ガイド**に表示されます。手順は書式付きテキストで表示し、クエリとダッシュボードはそれぞれリンクで表示します。クエリのリンクを開くと、インシデントの時間範囲でメトリクス（PromQL）、トレース（トレースストリームに対する SQL）、またはログ（その他の SQL）を表示します。[Mole Agent](/ja/agent) はインシデントの調査前にガイドを読み、まずガイド内のクエリを実行します。インシデントの [AI による根本原因分析](/ja/alerting/incidents#aiによる根本原因分析)でもガイドを考慮します。

API では、ルールの `guide` フィールドでガイドを扱います。[ルールの作成](/ja/api/alerting/create-rule#調査ガイド)を参照してください。エクスポートにはガイドが含まれます。インポート時は、インポート先の組織に存在しないダッシュボードをガイドから除外します。

## 検出ルール

[検出](/ja/alerting/discovery)の結果は一覧に表示するだけで、通知しません。通知を受け取るには、**アラート → 検出**で**新規検出ルール**を選択するか、検出結果で**同様の検出結果でアラートを作成**を選択してください。検出結果の種類、サービスまたはアプリケーション、環境、最低重大度を選択し、エスカレーションポリシーと緊急度を設定します。ルールに一致する検出結果ごとに、検出結果と同じ重大度でインシデントをオープンします。緊急度を設定しない場合は「低」になります。検出結果が終了すると、インシデントは復旧します。ルール一覧では、この種のルールのソースを**検出**と表示します。ルールを開くと、検出ページに戻ります。

## インポートとエクスポート

ルール一覧の**インポート／エクスポート**では、ルールをファイルに保存したり、ファイルから読み込んだりできます。

- **すべてのルールをエクスポート**を選択すると、JSON 形式のルールバンドル（`"format": "molesignal.alert-rules/v1"`）をダウンロードできます。絞り込み後は**これらの N 件のルールをエクスポート**を選択します。ルールの定義はすべて保持しますが、ID、組織、評価状態、時刻情報は含めません。エスカレーションポリシーと複合ルールが参照するルールは名前で指定するため、バンドルを別のワークスペースやクラスターに移行できます。ハートビートルールのチェックインアドレスはバンドルに含まれません。インポート後にルールで再設定してください。
- **ルールをインポート…**では、ルールバンドルまたは Prometheus のアラートルールファイル（Prometheus Operator の `PrometheusRule` も可）を貼り付けるか、ファイルを選択します。**テストを実行**を選択して、各ルールが新規作成、更新（変更されるフィールドも表示）、変更なし、失敗のいずれになるかを確認し、**N 件をインポート**を選択します。ルールは名前で照合します。新しい名前なら作成し、同名の既存ルールが 1 件なら更新します。同名の既存ルールが複数ある場合や、ファイル内に同じ名前が 2 回出現する場合は失敗します。同名のルールをエクスポートしたファイルをインポートする前に、名前が重複しないように変更してください。**新規ルールのみ作成（同名の既存ルールは変更しない）**を選択すると、既存ルールをスキップします。1 件でも失敗すると何も書き込まず、すべて成功した場合にのみインポート内容を一括で書き込みます。

Prometheus のルールは、次のように MoleSignal のルールに変換します。

| Prometheus | MoleSignal |
|---|---|
| `alert` | ルール名になります。同じアラート名が複数のグループにある場合、2 件目以降はルール名にグループ名を付けます。 |
| `expr` | ステートメントが `count(<expr>)`、条件が `>= 1` の PromQL ルールになります。式が時系列を返すとアラートが発報します。アノテーションまたはラベルで `{{ $labels.x }}` を使用している場合、ステートメントは `count by (x) (<expr>)` となり、ルールを `x` で[分割](#列でルールをグループ化する)してグループごとに 1 件のインシデントを作成します。ストリームには、式の先頭にあるメトリクス名を使用します。 |
| グループの `interval` | 評価間隔になります。指定がなければ 60 秒です。 |
| `for` | 継続時間を評価間隔で割り、切り上げた値を連続評価回数に設定します。 |
| `severity` ラベル | 重大度になります。`critical` と `page` は `critical`、`error` と `high` は `error`、`warning` と `warn` は `warning`、`info`、`low`、`none` は `info` に変換します。それ以外のラベルはそのまま保持します。 |
| `annotations` | そのまま保持します。説明には `description` または `summary` アノテーションを使用します。 |
| `record` | レコーディングルールはインポートせず、結果の下に一覧表示します。 |
| `keep_firing_for` | サポートしていません。結果の下に一覧表示します。 |

インポートしたルールにはデフォルトのエスカレーションポリシーを適用します。必要に応じて、インポート前にバンドルの `escalation_policy` を設定してください。Alertmanager 自体の設定（`alertmanager.yml` のルートとレシーバー）はルールではないため、この方法ではインポートできません。代わりに[アラートルーティング](/ja/alerting/routing)と[通知ポリシー](/ja/notification-channels)を使用してください。

CI では、[CLI](/ja/cli) で `molesignal alerts rules export` と `molesignal alerts rules apply -f rules.json [--dry-run]` を実行できます。結果は表形式で出力され、1 件でも失敗するとコマンドは終了コード 1 で終了します。

## ルールの変更、一時停止、削除

ルールを開いて変更し、再度**ルールをテスト**を選択してから保存します。**下書きを保存**を選択するとルールは無効のままになり、 **保存して有効化**を選択すると再び有効になります。ルールを削除するには、 [ルールを削除](/ja/api/alerting/delete-rule) API を呼び出します。ルールを変更せずに通知を一時的にミュートするには、 [サイレンス](/ja/alerting/silences)を使用します。

[アラートルール API](/ja/api/alerting/create-rule) を使用すると、スクリプトからルールの作成、テスト、トリガーができます。
