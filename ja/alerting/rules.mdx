A rule says what must not happen. MoleSignal evaluates it on an interval, and opens an
[incident](/ja/alerting/incidents) when the condition holds. Open **Alerts → Rules**. Reading rules
requires `alerts.rules.read`, and creating or changing them requires `alerts.rules.manage`.

## ルールの種類

| 種類 | 評価対象 | 作成場所 |
|---|---|---|
| **しきい値ルール** | SQL または PromQL のクエリ、[APM の指標](/ja/apm#apm-指標のアラート)、または [RUM の指標](/ja/rum/alerts)を、一定の間隔で固定のしきい値と比較します。 | ルールワークベンチ。 |
| **予測ルール** | クエリ、APM の指標、または RUM の指標のトレンドを評価し、リードタイム内にしきい値を超えると予測されると発報します。[予測ルール](#予測ルール)を参照してください。 | ルールワークベンチの **発報方式**。 |
| **外れ値ルール** | カラムで分割したクエリのグループ同士を比較し、大きく外れたグループが発報します。[外れ値ルール](#外れ値ルール)を参照してください。 | ルールワークベンチの **発報方式**。 |
| **複合ルール** | 他のルールにオープンなインシデントがあるかどうかを、and、or、not で組み合わせて評価します。[複合ルール](#複合ルール)を参照してください。 | ルールワークベンチの **発報方式**。 |
| **ハートビートルール** | cron タスクやバックアップスクリプトなどのジョブが予定どおりにチェックインしたかどうかを評価します。[ハートビートルール](#ハートビートルール)を参照してください。 | ルールワークベンチの **発報方式**。 |
| **異常検知** | クエリ、APM の指標、または RUM の指標を、履歴から学習したベースラインと比較します。 | 異常検知エディター。 |
| **リアルタイムルール** | 取り込み経路に到着したレコードをその場でカウントします。 | API のみ。[リアルタイムルール](#リアルタイムルール)を参照してください。 |

## ルール一覧

**Rules** には、すべてのルールがデータソース、トリガー条件、状態、最終評価とともに一覧表示されます。ルール、サービス、またはソースで検索し、**すべて**、**有効**、**無効**を切り替えます。

| 状態 | 意味 |
|---|---|
| **未評価** | ルールはまだ実行されていません。 |
| **正常** | 直近の評価で条件を満たしませんでした。 |
| **待機中** | 条件は満たしていますが、必要な時間にまだ達していません。 |
| **発報中** | ルールにオープンなインシデントがあります。 |
| **パイプラインで破棄** | ルールは発報していますが、[アラートパイプライン](/ja/pipelines/alert-events#イベントの処理結果)が開かれるはずのインシデントを破棄しました。 |
| **無効** | ルールは下書きとして保存されており、実行されません。 |

ルールを選択するか、その行の **編集** を選択すると、ルールが開きます。

## しきい値ルールを作成する

**新規ルール → しきい値ルール** を選択すると、ルールワークベンチが開きます。

<Steps>
  <Step title="ルールの種類を選択する">
    **メトリクスアラート**、**ログアラート**、**トレースアラート**、**APMアラート**、または **RUMアラート** を選択します。**クイックスタート** では、**エラー率の上昇**、**P95 レイテンシの上昇**、**エラーログの急増**、**データなし** などの代表的なクエリがプリセットで入力されます。APM アラートと RUM アラートでは、クエリの代わりにサービスまたはアプリケーションと指標を選択します。[APM の指標でアラートを設定する](/ja/apm#apm-指標のアラート)および [RUM アラート](/ja/rum/alerts)を参照してください。
  </Step>
  <Step title="基本情報を入力する">
    **ルール名** はインシデントのタイトルになります（例: `api_high_error_rate`）。**サービス** は、所有権とシグナルをまたいだコンテキストのためにルールをサービスに関連付けます。**説明** には、そのルールが何を守るのかを記述します。
  </Step>
  <Step title="発報方式を選択する">
    **クエリとトリガー条件** の上部で、**発報方式** を選択します。**しきい値**（デフォルト）、[**予測**](#予測ルール)、[**外れ値**](#外れ値ルール)、[**複合**](#複合ルール)、または [**ハートビート**](#ハートビートルール)から選びます。複合ルールとハートビートルールにはクエリがなく、以下で説明するクエリ、テスト、しきい値の代わりに固有の設定を使用します。
  </Step>
  <Step title="クエリを記述する">
    **対象ストリーム**、**評価間隔**（1、5、10 分ごと）、**クエリ言語**（メトリクスには **PromQL**、それ以外は **SQL**）、**クエリ** を設定します。クエリは数値を 1 つ返す必要があります。評価エンジンは最初の行の最初の列を読み取ります。任意で [**グループ化の基準**](#ルールをカラムで分割する)を設定します。ルールは [`_audit` ストリーム](/ja/settings/data-security#監査ストリーム)を読み取ることはできません。読み取るように保存すると `400` が返されます。
  </Step>
  <Step title="トリガー条件を設定する">
    各行が重大度を表します。**結果の比較条件** が演算子によって **しきい値** と比較され、**〜分間継続** の時間が指定されます。**重大度を追加** で行を追加できます。一致した中で最も高い重大度が採用され、高い重大度が低い重大度より達成しやすくなることはありません。分は評価回数に変換されます。以下で [**復旧** と **データがない場合**](#復旧とデータ欠損)を設定します。
  </Step>
  <Step title="対応ガイダンスを追加する">
    **Notify と対応** で、**対応ガイド / ランブックURL** を入力します。対応者はインシデント一覧からこれを開きます。誰に通知するかはルールではなく、[エスカレーションポリシー](/ja/alerting/on-call#エスカレーションポリシー)と [Notify ポリシー](/ja/notification-channels#テンプレートとポリシーを作成する)によって決まります。
  </Step>
  <Step title="調査ガイドを追加する">
    任意で、**調査ガイド** に実施する **手順** を記述し、実行する **クエリ** を追加し、そのルールのインシデントを調査するときに開く **ダッシュボード** を選択します。[調査ガイド](#調査ガイド)を参照してください。
  </Step>
  <Step title="ルールをテストする">
    **ルールをテスト** を選択します。直近 6 時間の実際のデータでクエリが実行され、**クエリプレビュー** に結果がしきい値ライン、現在値、推定発報回数、スキャンされた行数、レイテンシとともに描画されます。分割ルールでは、検出されたグループの数が表示されます。
  </Step>
  <Step title="保存する">
    **作成前のチェック** がすべて満たされている必要があります。名前、現在のクエリのテスト成功、有効なしきい値、有効なランブック URL です。その後、**保存して有効化** を選択するか、**下書きを保存** を選択してルールを実行せずに保存します。
  </Step>
</Steps>

ワークベンチで作成したルールはエスカレーションポリシーを指定しません。[アラートルーティング](/ja/alerting/routing)がインシデントを振り分け、ルーティングで振り分けられないものは `default` という名前のポリシーが引き受けます。組織にこのポリシーがない場合、そのようなインシデントはエスカレーション先のない状態で開かれます。先にポリシーを作成してください。[デフォルトポリシー](/ja/alerting/on-call#デフォルトポリシー)を参照してください。

## ルールをカラムで分割する

SQL または PromQL のクエリに対するスケジュールルールは、結果のカラム（ホストやサービスなど）で分割できます。ルールワークベンチで **グループ化の基準** を設定するか、[ルールを作成する](/ja/api/alerting/create-rule#列で分割するルール)ときに `query.group_by` を設定します。その後、値のグループごとに独立したルールとして動作します。

| 部分 | 動作 |
|---|---|
| グループ | 指定したカラムの値が同じ行の集まりです。名前は大文字小文字を区別せずに結果のカラムと照合されます。 |
| 値 | グループの最初の行から値が決まります。指定したカラムと時間カラム以外の、最初の数値カラムです。 |
| トリガー | 各グループは個別にトリガーまたは段階と比較され、独自の `for_periods` をカウントします。 |
| インシデント | 各グループが独自のインシデントを開き、その値がラベルとして、またタイトルに含まれます（例: `Errors per host · web-1`）。グループが復旧条件を満たすとインシデントは解決します。結果に存在しないグループには値がなく、データがない場合のルール設定に従って判断されます。 |
| 制限 | 1 ラウンドあたり最大 8 カラム、100 グループです。100 グループを超えると残りは評価されず、そのラウンドでは結果に存在しないグループのインシデントは維持されます。 |

各グループについて 1 行を返します。最も深刻なものを先頭にします:

```sql
SELECT host, count(*) AS errors
FROM app_logs
WHERE level = 'error'
GROUP BY host
ORDER BY errors DESC
```

PromQL ではシリーズのラベルがそのカラムになるため、`sum by (instance) (rate(http_requests_total{status=~"5.."}[5m]))` は `instance` で分割されます。結果に行はあるもののその名前のカラムがない場合、ラウンドは失敗し、何も変更されません。ルールワークベンチでクエリをテストするとカラムが確認されます。APM、RUM、リアルタイム、異常検知のルールは分割されません。[外れ値ルール](#外れ値ルール)は分割する必要があります。

## 復旧とデータ欠損

すべてのルールは、オープンなインシデントがいつ復旧するかと、値がない評価を何とみなすかを規定します。ルールワークベンチの**復旧**と**データがない場合**で設定するか、[ルールを作成する](/ja/api/alerting/create-rule#復旧とデータ欠損)ときに `trigger.recovery` と `trigger.no_data` として設定します。

- **復旧しきい値:** オープンなインシデントは、値がこのしきい値を再びまたぐまで待機します。たとえば、90 を超えると発報するルールは 80 を下回ると復旧します。しきい値付近で値が上下しても、発報と復旧を繰り返すことはありません。
- **復旧までの継続時間:** 値がこの時間だけ正常側にとどまると、インシデントが復旧します。
- **データがない場合:** クエリが値を返さなかった場合、または分割ルールのグループが結果に含まれない場合です。

| 選択肢 | 動作 |
|---|---|
| 復旧 | 評価は不一致とみなされ、オープンなインシデントは復旧します。デフォルトです。 |
| 状態を保持 | 何も変更されず、ルールには**データなし**と表示されます。異常検知ルールのデフォルトです。 |
| データなしインシデントをオープン | 状態を保持し、データがない状態が一定時間続くと、**データなし**とマークされたインシデントをオープンして `NO DATA · <title>` として通知します。データが戻ると解決します。ホストやサービスが完全に失われた場合は手動で解決してください。データが戻るまで再オープンされません。 |
| ゼロ | 欠損値を 0 として比較します。カウントに適しています。 |

リアルタイムルールはどちらの設定も使用しません。カウントが下がるとすぐに解決します。

## 異常検知ルール

異常検知ルールは、値が自身の履歴から予測される範囲を外れたときに発報するため、固定のしきい値は不要です。**新規ルール → 異常検知ルール**を選択します。

| セクション | フィールド | ルール |
|---|---|---|
| 識別情報 | **ルール名**、**重大度**、**サービス** | サービスは任意で、シグナル横断的なコンテキストを提供します。 |
| 検出クエリ | **データソース** | **クエリ**、サービスまたはエンドポイントの **APM 指標**、またはアプリケーションの **RUM 指標**です。[APM 指標の異常をアラートする](/ja/apm/insights#apm-指標の異常をアラートする)と [RUM 異常検知ルール](/ja/rum/alerts#異常検知ルール)を参照してください。 |
| | **ストリーム**、**ストリームタイプ**、**クエリ言語**、**クエリ** | 平均値、P95、カウントなど、1 つの数値を返すクエリです。 |
| | **評価ウィンドウ** | 1 分、5 分、15 分、または 1 時間です。 |
| 検出器 | **アルゴリズム** | **MAD**（ロバストな中央値）、または **EWMA**（最近のドリフトに追従）です。 |
| | **参照期間（日）** | 同じ時刻の履歴を 1〜30 日分使用します。デフォルトは 7 です。 |
| | **感度（k·σ）** | ベースラインからの距離がばらつきの k 倍を超えると発報します。値が大きいほど感度は低くなります。デフォルトは 3 です。 |
| | **平滑化（α）** | EWMA のみで、`(0, 1]` の範囲です。値が大きいほど最近のサンプルに追従します。 |
| | **発報までの評価回数** | インシデントがオープンするまでの連続した異常評価の回数です。 |
| | **週ごとの周期性** | 同じ曜日とのみ比較するため、平日と週末の間のアラートを回避できます。参照期間が 7 日以上必要で、28 日以上が最も効果的です。 |

## 予測ルール

予測ルールは指標のトレンドを将来に延長し、指標がリードタイム内にしきい値を超えると予測されると発報します。ディスク使用量、クォータ、接続数など、上限に近づいていく指標に適しています。 **発報方式**で**予測**を選択し、しきい値ルールと同様にクエリを記述して、次を設定します:

| 設定 | 備考 |
|---|---|
| **予測値** | 演算子としきい値です。たとえば、予測値が `> 90` となるように指定します。 |
| **リードタイム** | しきい値超過をどれだけ先まで予測して発報するかです。1、6、12 時間、または 1、2、3、7 日です。デフォルトは 1 日です。 |
| **参照期間** | トレンドの予測に使用する過去の日数です。1、3、7、14、30 日です。デフォルトは 7 です。 |
| **モデル** | **線形トレンド**、または**日次パターン**もしくは**週次パターン**です。日次パターンと週次パターンは、同じ時刻の 1 日前または 1 週間前の値にトレンドを加えたもので、日単位または週単位で上下する指標に使用します。週次パターンには少なくとも 7 日の参照期間が必要です。 |

各評価ラウンドでは現在の値が系列に追加されます。新しいルール、またはクエリが変更されたルールは、まず過去のいくつかの時点をクエリして履歴を埋めます。ポイントが少なすぎる場合（6 未満、または日次パターンと週次パターンで 1 周期分未満）は、そのラウンドでは判定されません。インシデントには、しきい値超過が予測される時期と、その時点の予測値が表示されます。予測ルールには重大度が 1 つと継続時間があり、復旧しきい値はなく、 [データがない場合](#復旧とデータ欠損)を設定できます。

## 外れ値ルール

外れ値ルールは、分割クエリのグループを固定しきい値ではなく互いに比較します。たとえばエラー数をホスト別に分割すると、他のホストよりエラーが大幅に多いホストは発報しますが、すべてのホストが一斉に増加した場合は発報しません。**発報方式**で**外れ値**を選択し、クエリを記述して、 [**グループ化の基準**](#ルールをカラムで分割する)を入力し、次を設定します:

| 設定 | 備考 |
|---|---|
| **許容範囲** | スケーリングされた偏差がいくつ離れると外れ値とみなすかです。0.5〜10 の範囲です。デフォルトは 3 です。小さいほど感度が高くなります。 |
| **検出方向** | **高い値と低い値の両方**、**高い値のみ**、または**低い値のみ**です。 |

偏差はグループの中央値と中央絶対偏差（MAD）から測定され、グループがほぼ同じ場合に小さな変動を外れ値にしないようにします。外れ値のグループはそれぞれ独自のインシデントをオープンし、どの程度離れているかが示されます。値があるグループが 3 未満の場合、そのラウンドでは判定されません。外れ値ルールは APM 指標や RUM 指標を使用せず、重大度が 1 つと継続時間があります。

## 複合ルール

複合ルールは複数のルールをまとめて評価します。組み合わせるルールは、オープンなインシデントがある間は真とみなされ、式でそれらを組み合わせます。たとえば `A && B` は、エラー率とレイテンシの両方がアラート状態のときだけ通知し、`A && !B` は下流が正常な間だけ上流の問題を真とみなします。**発報方式**で **複合**を選択します:

| 設定 | 備考 |
|---|---|
| **ルール** | 最大 10 個のルールで、A、B、C などの名前を付けます。 |
| **式** | 文字を `&&`（AND）、`\|\|`（OR）、`!`（NOT）、および括弧で組み合わせます。たとえば `A && (B \|\| C)` です。 |
| **各ルールのインシデントを複合インシデントの配下にまとめる** | 複合ルールがインシデントをオープンすると、組み合わせたルールのオープンなインシデントはその配下に[マージ](/ja/alerting/incidents#インシデントの統合)され、単独での通知を停止します。後からオープンしたインシデントもマージされます。 |

複合ルールはクエリを実行せず、テストもできず、 [データがない場合](#復旧とデータ欠損)の設定はありません。組み合わせるルールを複合ルールにすることはできず、複合ルールを別のルールに組み合わせることもできません。削除された組み合わせ対象のルールは false とみなされます。インシデントには、どの文字が真だったかが表示されます。

## ハートビートルール

ハートビートルールは考え方を逆にして、ジョブからの報告を待ちます。cron タスク、バックアップスクリプト、またはバッチジョブが実行のたびにチェックインアドレスにリクエストを送信し、チェックイン間隔に猶予期間を加えた時間内にチェックインが届かない場合、またはチェックインが失敗を報告した場合にルールが発報します。**発報方式**で **ハートビート**を選択します:

| 設定 | 備考 |
|---|---|
| **チェックイン間隔** | ジョブの実行頻度です。1 分〜7 日です。デフォルトは 60 分です。 |
| **猶予期間** | チェックイン間隔の後、チェックインが未達とみなされるまでさらに待つ時間です。最大 1 日です。デフォルトは 5 分です。 |

保存後、ダイアログにチェックインアドレスと `curl` の例が表示されます。アドレスが表示されるのはその一度だけです。ジョブが成功したらアドレスにリクエスト（`GET` または `POST`）を送信し、失敗した場合は `?status=fail` を追加してすぐにルールを発報させます。`POST` 本文の先頭はチェックインのメッセージとしてインシデントに保持され、ログの最後の数行に適しています。

```bash
if ./backup.sh; then
  curl -fsS "$HEARTBEAT_URL"
else
  curl -fsS "$HEARTBEAT_URL?status=fail"
fi
```

ハートビートルールを編集すると、最後のチェックインと、次回のチェックインの期限が表示されます。 **チェックインアドレスをリセット**すると新しいアドレスが発行され、古いアドレスはすぐに使えなくなります。チェックインアドレスにはサインイン不要で、含まれているトークンのみが必要です。[パブリックアクセス](/ja/public-access)と [ハートビートのチェックイン](/ja/api/alerting/heartbeats)を参照してください。ハートビートルールはクエリを実行せず、テストもできず、 [データがない場合](#復旧とデータ欠損)の設定はありません。

## リアルタイムルール

リアルタイムルールは、タイマーではなく取り込みパスで実行されます。取り込みノードが受け付けるすべてのレコードは、そのストリームのリアルタイムルールに対してチェックされ、一致したものは `periodSecs` 秒のスライディングウィンドウに入ります。毎秒、ルールを担当するアラートノードが、書き込みを受け付けるすべてのノードからウィンドウ内の一致を読み取って合計します。合計がトリガーを満たすとインシデントがオープンし、満たさなくなると解決します。これはレコードが書き込まれてから最大1秒後です。

| 項目 | 動作 |
|---|---|
| ステートメント | SQL の `SELECT count(*) FROM <stream> [WHERE <condition>]`。テーブルはルールの `stream` です。条件はフィールドをリテラル（`=`, `!=`, `<`, `<=`, `>`, `>=`）と比較し、`IN`、`BETWEEN`、`LIKE`、`ILIKE`、`IS [NOT] NULL` を使用します。複数の条件は `AND`、`OR`、`NOT`、およびかっこで結合します。フィールドの代わりに `json_text(<field>, '<key>')` を指定すると、クエリと同様に、JSON フィールドの1つのキーをテキストとして読み取ります（例: `json_text(body, 'type') LIKE 'Uncorrected%'`）。欠落しているフィールドまたは null のフィールドは、比較に一致しません。 |
| ウィンドウ | `periodSecs` は 1 から 3600 です。 |
| トリガー | `operator` は `gt` または `gte`、`for_periods` は `0` または `1` です。`thresholds` の階層は件数に応じて重大度を設定します。 |
| インシデント | インシデントは通常のライフサイクルに従います。ルールごとに1つのアクティブなインシデント、`silence_secs` のクールダウン、エスカレーション、通知です。 |

[ルールを作成する](/ja/api/alerting/create-rule)では、これらの制限外のリアルタイムルールを `400` で拒否します。件数は、書き込みを受け付ける各ノードのメモリに保持され、各ノードは5秒ごとにウィンドウのスナップショットをメタデータデータベースに保存します。再起動したノードはスナップショットを読み戻し、最大で直近5秒分を失います。ノードが停止しているか応答しない間、担当のアラートノードは、そのノードの最後のスナップショットを代わりに使用します。これはそれらの件数がウィンドウから外れるまで続きます。別のアラートノードがルールを引き継いでも、何も失われません。オープンなインシデントから発火状態を引き継ぎます。ノードはクラスターベアラー（`MS_SELF_TELEMETRY_CLUSTER_TOKEN`、ロール分割デプロイメントと共有）を使用して互いの件数を読み取ります。これがない場合、他のノードはスナップショットによってのみ認識されます。

### フェデレーションでのリアルタイムルール

[クロスクラスターフェデレーション](/ja/settings/data-plane#クラスターフェデレーション)では、各クラスターが自身に書き込まれたレコードをカウントし、デフォルトでは各クラスターが自身のカウントで判定します。クラスターを合算するには、判定するクラスターを設定します。API の `query.home_cluster`、またはルールワークベンチでルールを開いたときの **判定クラスター** です。ルールワークベンチには、このクラスターと有効なリモートクラスターが選択肢として表示されます。そのクラスターのみがルールのインシデントをオープンおよび解決します。毎秒、ルールを担当するそのアラートノードが、組織がマッピングされている各クラスターに組織ごとのトークンで件数を問い合わせ、その件数を自身の件数に加算します。他のクラスターはカウントのみ行います。800ミリ秒以内に応答しないクラスターは、最大30秒間は最後に返した件数でカウントし、その後は0としてカウントします。これにより、1秒の欠落でインシデントが解決されることはありません。メトリクス `realtime_federated_counts_failed_total{cluster}` が欠落をカウントします。ルールは同じ ID でフェデレーションに従うため、すべてのクラスターがそのルールをカウントします。

## 評価遅延

ロール分割クラスターでは、クエリは取り込みがフラッシュしたデータのみを読み取るため、取り込みバッファ内のレコードは最大 `[intake].flush_interval_secs`（デフォルトでは30秒）後にのみ表示され、直近のウィンドウのカウントは少なくなります。ルールワークベンチの **詳細設定** にある **評価遅延** は、各ラウンドのウィンドウを過去に移動します。5分の遅延と5分の期間の場合、07:00 のラウンドは 06:50 から 06:55 までのデータを読み取ります。

| 値 | 効果 |
|---|---|
| **自動**（デフォルト） | すべてのロールを実行する単一プロセスでは遅延はありません。ロール分割クラスターでは、**設定 → アラート評価** の **評価遅延**、デフォルトでは60秒です。 |
| **遅延なし** | 現在までのデータを読み取ります。 |
| 30秒から1時間 | ルール固有の遅延です。API では 0 から 3600 秒（`query.delay_secs`）を受け付けます。 |

データなしチェック、復旧条件、異常ベースライン、予測シリーズ、分割ルール、外れ値はすべて、同じ遅延分だけ過去に移動します。ウィンドウが移動した場合、インシデントは読み取った範囲をアノテーション `evaluated_window` に保持します。リアルタイムルールはクエリを実行せず、評価遅延もありません。

## 優先度と緊急度

ルールワークベンチの **Notify と対応** にある **優先度** と **緊急度** は、ルールのインシデントをオープンする際の設定を指定します。

- **優先度**: 組織の[優先度レベル](/ja/alerting/on-call#緊急度と優先度のレベル)のいずれかで、デフォルトでは P1 から P5、P1 が最も高い優先度です。未設定の場合、インシデントに優先度はありません（[アラートパイプライン](/ja/pipelines)が設定する場合があります）。優先度が重大度から導出されることはありません。
- **緊急度**: **エスカレーションポリシーに従う**（デフォルト）は、[インシデントのエスカレーションポリシーの緊急度](/ja/alerting/on-call#緊急度)に従います。高または低を指定すると、すべてのインシデントに適用されます。

## 調査ガイド

ルールワークベンチの **調査ガイド** セクションには、ルールのインシデントを調査するときに最初に行うことが表示されます。各部分は任意です。

| 項目 | 内容 | 上限 |
|---|---|---|
| **手順** | Markdown: 最初に何をどの順序で確認するか。 | 8,000文字 |
| **クエリ** | **名前**、クエリ言語（**promql** または **sql**）、SQL の場合は **ストリーム** とその **ストリームタイプ**、および **クエリ**。 | 最大4,000文字のクエリを10個 |
| **ダッシュボード** | インシデントから開くダッシュボード。 | ダッシュボードを5個 |

ガイドは、ルールの各インシデントの **調査ガイド** の下に表示されます。手順は書式付きテキストとして、各クエリはインシデントの時間範囲でメトリクス（PromQL）、トレース（トレースストリームに対する SQL）、またはログ（その他の SQL）を開くリンクとして、各ダッシュボードはリンクとして表示されます。[Mole Agent](/ja/agent) はインシデントを調査する前にガイドを読み、最初にそのクエリを実行します。また、インシデントの [AI 根本原因](/ja/alerting/incidents#ai-根本原因)はそれを考慮します。

API 経由では、ガイドはルールの `guide` フィールドです。[ルールを作成する](/ja/api/alerting/create-rule#調査ガイド)を参照してください。エクスポートにはガイドが含まれます。インポート時、組織が持っていないダッシュボードはガイドから除外されます。

## 検出ルール

[検出](/ja/alerting/discovery)で見つかった内容は一覧表示されるだけです。通知を受けるには、**アラート → 検出** で **新規検出ルール** を選択するか、検出結果上で **同様の検出結果でアラートを作成** を選択し、検出結果の種類、サービスまたはアプリケーション、環境、最小重大度を選択して、エスカレーションポリシーと緊急度を設定します。ルールが対象とする各検出結果は、それぞれ独自のインシデントをオープンします。重大度は検出結果と同じで、設定しない限り緊急度は低です。検出結果が終了すると、インシデントは復旧します。ルール一覧では、そのようなルールのソースとして **検出** が表示され、これを開くと検出ページに戻ります。

## インポートとエクスポート

ルール一覧の**インポート／エクスポート**では、ルールをファイルとして保存したり、ファイルから取り込んだりできます:

- **すべてのルールをエクスポート**、またはフィルタ後に**これらの N 件のルールをエクスポート**すると、JSON ルールバンドル（`"format": "molesignal.alert-rules/v1"`）をダウンロードします。ルールは定義全体を保持しますが、id、組織、評価状態、時刻は含まれません。エスカレーションポリシーと複合ルール内のルールは名前で指定されるため、バンドルは別のワークスペースやクラスタに移動できます。ハートビートルールのチェックインアドレスはバンドルに含まれません。インポート後にルール上で再設定してください。
- **ルールをインポート…**では、バンドル、または Prometheus アラートルールファイル（Prometheus Operator の `PrometheusRule` も可）を貼り付けるか選択して取り込みます。**テストを実行**を選択すると、各ルールが作成、更新（変更されるフィールドを含む）、変更なし、失敗のいずれになるかを確認できます。その後、**N 件をインポート**します。ルールは名前で照合されます。新しい名前は作成され、1 件のルールがある名前は更新され、複数のルールがある名前は失敗します。ファイル内で同じ名前が 2 回指定された場合も失敗します（同じ名前を共有するルールは、それらのエクスポートをインポートする前に名前を変更してください）。**新規ルールのみ作成（同名の既存ルールは変更しない）**を指定すると、既存のルールはスキップされます。いずれかのルールが失敗した場合は何も書き込まれません。それ以外の場合は、インポート全体が一度に書き込まれ、すべて成功するかすべて失敗するかのどちらかです。

Prometheus ルールは次のように MoleSignal ルールになります:

| Prometheus | MoleSignal |
|---|---|
| `alert` | ルールの名前。複数のグループにまたがるアラート名は、最初のグループ以降ではグループ名が使われます。 |
| `expr` | `count(<expr>)` というステートメントと `>= 1` という条件を持つ PromQL ルール。式がシリーズを返すとアラートが発火します。アノテーションまたはラベルで `{{ $labels.x }}` を使用している場合、ステートメントは `count by (x) (<expr>)` になり、ルールは `x` で[分割](#ルールをカラムで分割する)され、グループごとに 1 つのインシデントになります。ストリームは式の最初のメトリック名です。 |
| グループの `interval` | 期間。指定しない場合は 60 秒。 |
| `for` | 連続する期間。切り上げられます。 |
| ラベル `severity` | 重要度: `critical` と `page` はクリティカル、`error` と `high` はエラー、`warning` と `warn` は警告、`info`、`low`、`none` は情報です。その他のラベルは保持されます。 |
| `annotations` | 保持されます。説明は `description` または `summary` アノテーションです。 |
| `record` | レコーディングルールはインポートされません。結果の下に一覧表示されます。 |
| `keep_firing_for` | サポートされていません。結果の下に一覧表示されます。 |

インポートされたルールはデフォルトのエスカレーションポリシーを使用します。必要に応じて、インポートする前にバンドル内で `escalation_policy` を設定してください。Alertmanager 自体の設定（`alertmanager.yml` のルートとレシーバー）はルールではなく、この方法ではインポートできません。代わりに[アラートルーティング](/ja/alerting/routing)と[通知ポリシー](/ja/notification-channels)を使用してください。

CI では、[CLI](/ja/cli) が `molesignal alerts rules export` と `molesignal alerts rules apply -f rules.json [--dry-run]` を実行します。結果は表として出力され、いずれかのルールが失敗するとコマンドは 1 で終了します。

## ルールの変更、一時停止、削除

ルールを開いて変更し、再度**ルールをテスト**して保存します。**下書きを保存**するとルールは無効のままになり、 **保存して有効化**すると再び有効になります。ルールを削除するには、 [ルールを削除](/ja/api/alerting/delete-rule)を呼び出します。ルールを変更せずに通知をしばらくミュートするには、[サイレンス](/ja/alerting/silences)を使用してください。

[アラートルール API](/ja/api/alerting/create-rule) は、スクリプトからルールを作成、テスト、トリガーします。
