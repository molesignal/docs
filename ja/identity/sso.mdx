シングルサインオンを使うと、MoleSignal のパスワードの代わりに、社内ディレクトリや一般的なプラットフォームのアカウントでサインインできます。**ID とアクセス → SSOプロバイダー**と**メールドメイン**を開きます。プロバイダーとドメインの参照には `org.sso.read` が必要です。変更には `org.sso.manage` が必要です。

## プロバイダーを追加する前に

`[http].external_url` に MoleSignal の公開アドレスを設定します。OIDC と OAuth 2.0 の**リダイレクトURI**、 SAML の**アサーションコンシューマーサービス（ACS）URL**、デフォルトの **SP エンティティ ID** は、このアドレスに基づいて決まります。 ID プロバイダーは、このアドレスのコールバック先にアクセスできる必要があります。MoleSignal はプロバイダー設定をデータベースに保存し、再起動せずに適用します。

## プロバイダーを追加する

1. **SSOプロバイダー**を開き、**新規プロバイダー**を選択します。
2. **よく使われるプラットフォーム**または**企業向けディレクトリ**からプラットフォームを選択するか、**汎用プロトコル**から **OIDC**、 **OAuth 2.0**、**SAML**、**LDAP** のいずれかを選択します。選び直すには、**プラットフォームを変更**を選択します。
3. プラットフォームが複数のプロトコルに対応している場合は、**プロトコル**で使用するものを選択します。
4. プラットフォームが求める項目を入力し、フォームの案内に従って、表示された**リダイレクトURI**または**アサーションコンシューマーサービス（ACS）URL** を ID プロバイダーに登録します。
5. [ID フィールドのマッピング](#id-フィールドのマッピング)、[ロールの割り当て](#ロールの割り当て)、 [サインインの範囲](#サインインの範囲)を確認します。
6. **プロバイダーを作成**を選択します。

## 事前設定済みのプラットフォーム

事前設定済みのプラットフォームでは、エンドポイント、スコープ、フィールドのマッピングが自動で入力されます。OIDC または OAuth 2.0 のプラットフォームでは、以下の項目と**クライアント ID**、**クライアントシークレット**だけを入力します。入力内容に基づくエンドポイントは **エンドポイントとスコープ**に表示されます。

| プラットフォーム | プロトコル | フィールド | グループ |
|---|---|---|---|
| Google | OIDC、SAML | OIDC では追加項目なし | OIDC ではなし、SAML では所属グループ |
| Microsoft Entra ID | OIDC、SAML | **ディレクトリ (テナント) ID** と**クラウド**（グローバルまたは 21Vianet 運営） | グループのオブジェクト ID |
| GitHub | OAuth 2.0 | **デプロイメント**、GitHub Enterprise Server の場合は**サーバーホスト** | 組織（`my-org`）とチーム（`my-org/sre`） |
| GitLab | OIDC | **インスタンス URL**（デフォルトは `https://gitlab.com`） | `groups` |
| Okta | OIDC、SAML | **Okta ドメイン**と**認可サーバー** | `groups` クレーム |
| Auth0 | OIDC | **テナントドメイン** | カスタムクレーム |
| Keycloak | OIDC | **サーバー URL** と**レルム** | Group Membership マッパーの `groups` |
| authentik | OIDC | **サーバー URL** と**アプリケーションスラッグ** | `groups` |
| Feishu / Lark | OAuth 2.0 | **エディション**（Feishu または Lark） | なし |
| AD FS | SAML | IdPメタデータ | Token-Groups |
| JumpCloud | SAML | IdPメタデータ | `memberOf` |
| Active Directory、OpenLDAP、FreeIPA | LDAP | サーバー URL、ベース DN、検索用アカウント | `memberOf` |

MoleSignal は GitHub から、サブジェクトとしてアカウントの数値 ID を、メールアドレスとして検証済みのプライマリアドレスを取得します。組織とチームの参照には `read:org` が必要です。組織が OAuth アプリのアクセスを制限している場合、組織やチームを参照するには、事前に組織のオーナーがアプリを承認する必要があります。 Feishu では、オープンプラットフォームでユーザーのメールアドレスを読み取る権限をアプリに付与します。

## 汎用プロトコル

| プロトコル | 設定 |
|---|---|
| OIDC | **発行者 URL**、**認可 URL**、**トークン URL**、**UserInfo URL**、**JWKS URL**、**クライアント ID**、**クライアントシークレット**、およびスペース区切りの**スコープ**を指定します。**発行者 URL** の入力後に**エンドポイントを検出**を選択すると、`.well-known/openid-configuration` からほかのエンドポイントを自動入力します。 |
| OAuth 2.0 | ID トークンを発行しない ID プロバイダー向けです。**認可 URL**、**トークン URL**、**UserInfo URL**、**クライアント ID**、**クライアントシークレット**、**スコープ**を指定します。サインイン後、MoleSignal はアクセストークンを使って **UserInfo URL** から情報を取得し、フィールドのマッピングに従ってアカウントを特定します。 |
| SAML | **SP エンティティ ID**、**IdP エンティティ ID**、**IdP SSO URL**、**IdP 署名証明書（PEM）**を指定します。**IdPメタデータ**でメタデータ URL を入力するか、**XMLを貼り付け**を選択してメタデータを貼り付けます。次に**インポート**を選択すると、最後の 3 項目が自動で入力されます。HTTP-Redirect のサインオン URL のみに対応します。 |
| LDAP | **LDAP サーバー URL** には `ldaps://`、または **StartTLS** を有効にして `ldap://` を指定します。**ユーザーベース DN** には、たとえば `ou=people,dc=example,dc=com` を指定します。**ユーザー検索フィルター**には `{username}` を含めます。MoleSignal は検索前にその値をエスケープします。**検索用バインド DN** と**検索用バインドパスワード**は、ディレクトリが匿名検索を許可する場合にのみ、両方とも空欄にします。 |

プロバイダーを編集する際、保存済みの値を保持するには、**クライアントシークレット**または **検索用バインドパスワード**を空欄にします。

## ID フィールドのマッピング

**ID フィールドのマッピング**では、MoleSignal がユーザーの 4 つのフィールドをどこから取得するかを指定します。

| MoleSignal のフィールド | OIDC と OAuth 2.0 | SAML | LDAP |
|---|---|---|---|
| **不変のサブジェクト** | クレームまたは JSON フィールド。`realm_access.roles` のようなドット区切りのパスも使えます。 | 属性名、またはアサーションのサブジェクトを示す `NameID`。 | 属性、またはエントリの DN を示す `dn`。 |
| **メールアドレス** | クレームまたは JSON フィールド。 | 属性名。 | 属性。 |
| **表示名** | クレームまたは JSON フィールド。 | 属性名。 | 属性。 |
| **グループ** | クレームまたは JSON フィールド。 | 属性名。 | 属性。 |

OIDC と OAuth 2.0 では、`|` で複数の取得元を並べると、値がある最初の取得元を使います。たとえば `email | preferred_username` と指定します。有効なメールアドレスがなければ、サインインできません。

## ロールの割り当て

**外部グループ → ロール**には、**グループ**の値と MoleSignal のロールの対応が表示されます。 **マッピングを追加**を選択し、`platform-admins` などの**外部グループの値**を入力して、ロールを選択します。MoleSignal は、一致するすべてのマッピングのロールを割り当て、サインインのたびにロールを同期します。

一致するマッピングがない場合は、**デフォルトロール**を適用します。未設定の場合は、セルフサービスで参加する際のロールを適用します。グループを送信しないプラットフォームでは、デフォルトロールのみを使用します。

## サインインの範囲

**サインインを許可するグループ**を設定すると、指定したグループのいずれかに所属するアカウントだけが、そのプロバイダー経由でサインインできます。

Google、GitHub.com、GitLab.com、および Microsoft のテナントに依存しないエンドポイントでは、誰でもアカウントを作成できます。このようなプロバイダーは、ワークスペースに[メールドメイン](#メールドメイン) が設定されているか、プロバイダーに**サインインを許可するグループ**が設定されている場合のみ有効にできます。サインインには、 ID プロバイダーが検証済みのメールアドレスのみ使用できます。有効化後にメールドメインをすべて削除すると、このようなプロバイダー経由ではサインインできなくなります。

## サインインをテストする

プロバイダーを本番で使用する前に、プロバイダー一覧またはプロバイダーの設定で **テスト** を選択して動作を確認します。テストでは保存済みの設定で実際のサインインを試しますが、セッションは開始せず、アカウントの作成やリンク、ロールの変更も行いません。現在のサインイン状態も変わりません。無効なプロバイダーもテストできるため、有効にする前にテストしてください。テストには `org.sso.manage` が必要です。APIトークンでは開始できません。テストはプロバイダーごとに1分あたり10回まで実行できます。

| プロバイダー | テスト方法 |
|---|---|
| OIDC, OAuth 2.0, SAML | 新しいタブでIDプロバイダーを開き、結果ページに戻ります。サインイン用に登録済みのリダイレクトURIまたはACS URLを使用します。 |
| LDAP | ディレクトリアカウントとそのパスワードを入力します。実際にバインドするため、パスワードを間違えると、ディレクトリのロックアウトポリシーとこのインスタンスのサインイン制限の両方で失敗としてカウントします。パスワードは保存しません。 |

結果ページには次の情報が表示されます。

- **サインインの成否。** 失敗した場合は、理由、対処方法、サーバーまたはID プロバイダーからのメッセージを表示します。許可グループやメールドメインの制限、アカウントの無効化など、サインインを拒否する条件に該当すると、テストも失敗します。
- **プロバイダーから返された情報：** メールアドレス、名前、サブジェクト、グループを表示します。
- **実際にサインインした場合の処理：** 対象アカウントの処理（サインイン、所有者によるリンクの確認、または新規アカウントの作成）と、処理後のロール（置き換え対象のロールを含む）を表示します。

IDプロバイダーが独自のエラーページを表示すると、ブラウザーは結果ページに戻りません。10 分後に、応答がなかったことを結果ページに表示します。通常は、IDプロバイダーにリダイレクトURIが登録されていないことが原因です。

テスト結果は、実行時の設定に対してのみ有効です。エンドポイント、シークレット、マッピング、または許可グループを変更すると結果は無効になり、一覧に **設定変更済み** と表示します。プロバイダーの名前の変更、有効化、無効化では結果は無効になりません。プロバイダーごとに直近20件のテスト結果を保持します。トークン、アサーション、シークレット、パスワードは表示も保存もログ出力もしません。各テストは `org.sso_provider.test` として監査ログに記録しますが、 ID情報は記録しません。

## サインイン要件

**ID とアクセス → SSOプロバイダー** の上部にある **サインイン要件** で、このワークスペースにアクセスするためのサインイン条件を設定します。設定には `org.sso.manage` が必要です。変更は15分以内にすべてのセッションに適用します。要件を満たさないセッションは、次回の更新時に終了し、再サインインが必要になります。変更は監査ログに記録します。

| 要件 | 動作 |
|---|---|
| **多要素認証を必須にする** | ワークスペースにアクセスするセッションには、[多要素認証](/ja/identity/mfa)が必要です。このワークスペースの OIDC、OAuth 2.0、SAML のいずれかのプロバイダーを経由したセッションは、IDプロバイダーが多要素認証を担うため、要件を満たすものとして扱います。LDAP や別のワークスペースのシングルサインオンは対象外です。 |
| **シングルサインオンのみ許可** | このワークスペースの OIDC、OAuth 2.0、SAML のいずれかのプロバイダーでのみアクセスできます。アカウントのパスワード、パスキー、LDAP ではアクセスできません。ルートユーザーは例外で、IDプロバイダーが停止していてもアクセスできます。この要件をオンにするには、対象のプロバイダーを少なくとも1つ有効にする必要があります。オンの間は、最後の有効なプロバイダーを無効化または削除できません。現在の設定で[サインインテスト](#サインインをテストする)に合格した有効なプロバイダーがない状態でオンにすると、警告が表示され、ワークスペース名の入力を求められます。監査イベントには `sso_tested: false` を記録します。 |

サインインが要件を満たさない場合の動作は次のとおりです。

| ケース | 結果 |
|---|---|
| 複数のワークスペースに所属するアカウントでサインインする | アクセスを許可する最初のワークスペースを開きます。 |
| サインイン時に多要素認証の要件だけを満たしていない | その場でパスキーまたは認証アプリを設定します。設定後に多要素認証済みのセッションが開始し、リカバリーコードが表示されます。 |
| シングルサインオンのみを許可するワークスペースにしか所属していないアカウントでサインインする | サインインを拒否し、サインインページに理由を表示します。 |
| 多要素認証が必須のワークスペースに切り替える | 第2の認証要素を設定済みの場合は、その場で1回認証します。未設定の場合は、先に **セキュリティとサインイン** で設定します。 |
| シングルサインオンのみを許可するワークスペースに切り替える | そのワークスペースのプロバイダーを使ったサインインを案内します。 |
| セルフサービスでサインアップする | シングルサインオンのみを許可するワークスペースでは、サインアップを拒否します。多要素認証が必須の場合はアカウントを作成し、サインイン時に多要素認証を設定します。 |
| データベースクライアントからアカウントでログインする | どちらか一方でも要件が有効な場合はログインを拒否します。接続済みのクライアントも、次回のリクエストから利用できなくなります。[APIトークン](/ja/identity/tokens)を使用してください。 |
| APIトークン | 影響はありません。 |

アカウントが所属するワークスペースのいずれかで多要素認証が必須になっている間は、アカウントの所有者は最後の第2認証要素を削除できません。[管理者によるリセット](/ja/identity/mfa#管理者によるリセット)は引き続き可能です。リセット後は、メンバーが次回のサインイン時に第2認証要素を設定します。

プラットフォーム組織のサインイン要件は、`_sys` 組織の **設定 → サインイン要件** にあります。設定には `sys.settings.signin.manage` が必要です。設定できるのは **多要素認証を必須にする** のみです。

## サインイン時の動作

サインインページには、有効なプロバイダーごとに、プラットフォームのロゴ付きの行が表示されます。LDAP プロバイダーの場合は、該当する行を選択し、ディレクトリのユーザー名とパスワードを順に入力します。

1. ブラウザーはIDプロバイダーに移動し、認証後に MoleSignal に戻ります。
2. プロバイダーを通じて本人確認を行います。OIDC では、JWKS のキー（RSA、EC、 EdDSA のいずれか）またはクライアントシークレット（HMAC）でIDトークンを検証します。OAuth 2.0 では、ユーザーエンドポイントから情報を取得します。MoleSignal はマッピングされたフィールドを読み取ります。
3. **サインインを許可するグループ** に属さないアカウントのサインインは拒否します。
4. サインイン履歴のあるIDは、リンク済みのアカウントにサインインします。MoleSignal はメールアドレスではなく、プロバイダーとIDのサブジェクトでアカウントを特定します。
5. 初めてサインインするIDのメールアドレスが既存の MoleSignal アカウントのものと一致する場合は、そのアカウントの所有者による確認を待ちます。[既存のアカウントをリンクする](#既存のアカウントを連携する)を参照してください。
6. MoleSignal アカウントがない場合は、メールアドレスがワークスペースの [メールドメイン](#メールドメイン)の条件を満たしていれば、アカウントを作成します。
7. まだメンバーでない場合は、プロバイダーのワークスペースに参加し、マッピングされたロールまたはデフォルトのロールが割り当てられます。
8. 既存のメンバーの場合は、一致するマッピングのロールで以前のロールを置き換えます。無効なアカウントはサインインできません。
9. ブラウザーはサインインページに戻ってサインインを完了し、サインイン前にアクセスしようとしたページを開きます。サインインに失敗した場合は、サインインページに理由を表示します。

## 既存のアカウントを連携する

プロバイダーが本人性を保証するのは、自身のワークスペースのメンバーだけです。そのため、プロバイダーから送られるメールアドレスだけでは、既存のアカウントにサインインできません。同じメールアドレスを持つ別のユーザーのアカウントである可能性があるためです。外部 ID で初めてサインインするときに、そのメールアドレスのアカウントがすでに存在する場合、サインインページはアカウントの所有者に同じブラウザーでの確認を求めます。

| 確認方法 | 利用できる条件 | 手順 |
|---|---|---|
| **パスワード** | アカウントにパスワードを設定している場合。 | アカウントのパスワードを入力します。 |
| **メールの確認コード** | インスタンスが[メールを送信](/ja/configuration#アラートとメール)できる場合。 | **コードを送信**を選択し、メールに記載された6桁のコードを入力します。コードの送信は1分に1回までです。 |

コードは、送信をリクエストしたページでのみ使えます。サインインの操作に心当たりがない場合、確認コードのメールは無視してかまいません。入力を5回間違えた場合や30分が経過した場合は、プロバイダー経由で再度サインインします。確認が完了すると外部 ID が連携され、次回からはその外部 ID でそのままサインインできます。[多要素認証](/ja/identity/mfa)を設定したアカウントでは、確認後に 2段階目の認証（パスキー、認証アプリ、またはリカバリーコード）を済ませると、外部 ID の連携が完了します。アカウントにパスワードがなく、インスタンスがメールを送信できない場合は、ここでは確認できません。以前と同じ方法でサインインするか、管理者にメール送信の設定を依頼してください。

ワークスペース独自のプロバイダーで作成したアカウントは、メールアドレスの所有を確認するまで、そのワークスペース内にとどまります。管理者も別のプロバイダーも、そのアカウントを別のワークスペースに追加できません。メールで届いたリンクからパスワードをリセットするか、メールの確認コードで連携を確認すると、メールアドレスの所有を証明できます。 Google、GitHub.com、GitLab.com、または Microsoft のテナント非依存エンドポイント経由で作成したアカウントには、この制限は適用されません。これらのプロバイダーは、確認済みのメールアドレスのみを受け付けるためです。

連携済みの外部 ID の確認や連携解除は、 [アカウント設定 → セキュリティとサインイン](/ja/account#セキュリティとセッション)で行います。

## プロバイダーを管理する

一覧には、各プロバイダーのプラットフォーム、種類、有効かどうか、 [サインインテスト](#サインインをテストする)の状態、最終変更日時が表示されます。

| 操作 | 結果 |
|---|---|
| **テスト** | [サインインテスト](#サインインをテストする)を実行します。 |
| **編集** | 設定とマッピングを変更します。 |
| **無効化** / **有効化** | 無効にしたプロバイダーはサインインページに表示されず、サインインを受け付けません。 |
| **削除** | プロバイダーを削除します。そのプロバイダーを利用していたユーザーは、それを使ってサインインできなくなります。 |

## メールドメイン

**メールドメイン**では、ワークスペースへの参加に使えるメールアドレスを制限します。対象となる参加方法は、 [招待](/ja/identity/members#招待)とシングルサインオンです。**ドメインを追加**を選択し、 `example.com` などのドメインを入力します。リストが空の場合は、どのメールアドレスでも参加できますが、一般公開のアカウントを受け付けるプロバイダーは有効化できません。**削除**を選択すると、ドメインをリストから削除します。
