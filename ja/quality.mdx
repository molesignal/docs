Mole Agentが生成するすべての回答にスコアが付きます。ルールによる採点では、モデルを使わずに、ツールの実行が成功したか、証拠を引用しているか、クエリを解析できるか、指定の形式に従っているか、質問者がどう評価したかを即時に確認します。設定した評価器は、回答の一部を抽出し、作成した評価基準に沿ってモデルで採点します。スコアが低い回答、役に立たなかったと評価された回答、無作為に抽出された回答はレビュー待ちになります。レビューで承認された回答は、回帰テストセットに追加されます。組織のプロンプトをデフォルトに設定する前に、セット内の質問の一部に新バージョンと現行バージョンで再回答し、評価器が両方の回答を採点します。

スコアは0〜100で表示します。**品質**タブでスコアを確認できます。すべてのスコアはストリーム `_agent_score_traces` にも記録します。

## 開始前に

- **品質**タブを表示するには `agent.quality.read` が必要です。オーナーと管理者のロールには、デフォルトでこの権限があります。これらのロールではすべてのチームチャットを閲覧できます。個人チャットは集計にのみ含まれ、このタブでは誰も内容を閲覧できません。
- 評価器は組織のモデルプロバイダーのいずれかを使用します。[Mole Agent](/ja/agent#モデルプロバイダーを設定する)を参照してください。評価器を設定しなくても、ルールですべての回答を採点します。

## 採点対象

| ソース | 説明 |
|---|---|
| **チームチャット** | チームチャット内の回答です。 |
| **個人チャット** | 個人チャット内の回答です。ルールのみで採点し、集計にのみ含めます。 |
| **オートメーション** | 組織またはチームのオートメーションを実行するたびに生成する回答です。[オートメーション](/ja/automations)を参照してください。個人のオートメーションの実行結果は個人チャットとして扱います。 |
| **インシデントRCA** | 根本原因分析が自動またはオンデマンドで生成するRCAと、ユーザーが評価したすべてのRCAです。 |

回答を生成した時点で採点し、質問者が評価を付けたり取り消したりしたときに再採点します。

## ルール

回答と実行時の記録に基づいて、各ルールで0〜100のスコアを付けます。該当するルールのスコアの平均を、回答のルールスコアとします。

| ルール | スコア | 適用対象 |
|---|---|---|
| **ツール呼び出し** | 失敗しなかったツール呼び出しの割合です。 | ツールを呼び出した回答です。 |
| **証拠** | 証拠の引用がなければ0、引用した証拠を裏付ける成功したツール呼び出しがなければ50、裏付けのある証拠が1件なら75、2件以上なら100です。 | ツールを呼び出し、指定の形式に従った回答です。 |
| **クエリ** | ツール呼び出しに含まれるSQLとPromQLのうち、解析できるクエリの割合です。 | ツールでクエリを実行した回答です。 |
| **形式** | 回答が指定の形式に従っていれば100です。 | 生成したクエリを除く、すべてのチャット回答です。 |
| **完了** | 回答が完了していれば100、オートメーションの実行に人の対応が必要なら50、失敗、中断、または回答が空なら0です。 | すべての回答です。 |
| **評価** | **役に立った**は100、**役に立たなかった**は0です。RCAでは、**役に立たなかった**が1件でもあれば、その評価を採用します。 | ユーザーが評価した回答です。 |

## 評価器

評価器は、評価基準に沿って回答を1〜5の5段階で採点し、その理由を1〜2文で示します。スコアは0、25、50、75、100のいずれかで表示します。評価器は質問、ツールの取得結果、回答を参照します。RCAの場合は、インシデントの事実関係とRCAを参照します。

- 評価器は、新しい回答から設定した割合で回答を抽出して採点します。回答ごとに抽出するかどうかが決まるため、抽出し直しても同じ回答が選ばれます。
- **役に立たなかった**と評価された回答は、評価器がすでに採点していない限り、必ず採点します。
- 評価器のスコアがレビューのしきい値を下回った場合は、もう一度採点し、2回のスコアの平均を採用します。
- 評価器は個人チャットを採点しません。
- 評価器は、最後に評価器を保存したユーザーのインターフェース言語で採点理由を記述します。
- 評価器によるモデル呼び出しは、組織の日次トークン予算を消費し、ソース別の使用量では**品質スコアリング**として計上します。予算を使い切っている間、評価器は新しい回答の採点をスキップします。

すべての評価器は、組み込みプロンプトの**回答評価**（用途は `evaluation`）を基本の指示として使用します。組織は**設定 → プロンプト管理**でこのプロンプトを上書きできます。プロンプトの内容にかかわらず、評価器は固定形式でスコアを返します。

評価器が採点した回答には、評価器によるスコアの平均を使用します。それ以外の回答には、ルールスコアを使用します。

## 品質タブ

**Mole Agent → 品質**を開きます。**概要**と**回答**では、過去7日間、30日間、90日間のいずれかを選び、1つのソースまたはすべてのソースを表示できます。

| ビュー | 表示内容 |
|---|---|
| **概要** | スコアリング済みの回答数、ルールと評価者それぞれの平均スコア、「役に立った」「役に立たなかった」と評価された回答数、レビュー待ちの回答数を表示します。その下に、日別スコア、ルールごとの結果、ソース、プロンプトのバージョン、スキル、モデル別の回答を表示します。 |
| **回答** | スコアリング済みの回答を新しい順に表示します。**低スコアのみ**を選ぶと、レビューのしきい値を下回る回答に絞り込めます。行を開くと、質問と回答の全文、各ルールの検出結果、各評価者のスコアと理由、回答のレビューを確認できます。**チャットを開く**または**インシデントを開く**を選ぶと、回答が作成された場所に移動します。 |
| **レビュー** | レビュー待ち、承認済み、または却下済みの回答を表示します。 |
| **データギャップ** | 回答時のツール呼び出しから判明したデータの不足を表示します。[データギャップ](#データギャップ)を参照してください。 |
| **ドリル** | 解決済みのインシデントを再調査し、判明している根本原因と照合して採点した結果を表示します。[ドリル](#ドリル)を参照してください。 |
| **評価者** | 評価者と設定を表示します。 |

### 回答をレビューする

次の場合に、回答がレビュー待ちになります。

| 理由 | 条件 |
|---|---|
| **低スコア** | 評価者による2回目のスコアリング後もスコアがレビューのしきい値を下回っています。評価者がスコアリングしない回答では、ルールによるスコアがしきい値を下回っています。 |
| **「役に立たなかった」と評価済み** | 質問者が回答を**役に立たなかった**と評価しました。 |
| **無作為抽出** | スコアの信頼性を確かめるため、**ランダムレビュー**で設定した割合に従って回答を無作為に抽出しました。 |

各回答がレビュー対象になるのは1回だけです。回答を開き、問題点と、適切な回答に含めるべき内容を**メモ**に記入して、次のいずれかを選びます。

- **承認**: 回答に問題があります。回答をリグレッションテストセットに追加します。プロンプトのチェックで同じ質問に再回答する際に、メモを評価者に渡します。
- **却下**: 回答に問題はありません。

### 評価者と設定

**評価者**で**新規評価器**を選ぶと、フォームが開きます。

| フィールド | 説明 |
|---|---|
| **名前** | 組織内で一意の名前を指定します。 |
| **評価基準** | 適切な回答の要件と減点の条件を、最大4000文字で指定します。ひな形となる評価基準があらかじめ入力されています。 |
| **回答** | チームチャット、自動化、インシデントの根本原因分析（RCA）が対象です。 |
| **サンプリング率** | 新しい回答のうちスコアリングする割合を、0～100の範囲で指定します。 |
| **モデルプロバイダー**と**モデル** | 空欄にすると、組織で最初に利用できるプロバイダーと、そのデフォルトモデルを使用します。 |
| **温度** | 0～1の範囲で指定します。0にするとスコアが安定します。 |
| **オン** | オフにした評価者はスコアリングを行いません。 |

1つの組織に最大10件の評価者を作成できます。評価者を削除しても、付けたスコアは残ります。

評価者の一覧の下に、次の設定があります。

| 設定 | デフォルト | 説明 |
|---|---|---|
| **レビューのしきい値** | 60 | この値を下回る回答はレビュー待ちになります。 |
| **ランダムレビュー** | 0 | ほかの理由でレビュー対象になっていない回答のうち、レビュー用に無作為抽出する割合です。 |
| **プロンプトをデフォルトに設定する前のチェック** | チェックし、結果が悪化した場合は再確認する | 下記を参照してください。 |

### データギャップ

ルールで回答をスコアリングするときは、ツール呼び出しも確認し、Mole Agentが利用できたデータに不足がないかを調べます。データギャップが示すのは回答ではなくデータの問題なので、スコアには影響しません。**データギャップ**では、過去7日間、30日間、90日間のいずれかについて、検出結果を集計します。

| 種類 | 検出条件 | 対処方法 |
|---|---|---|
| **データの所在** | 同じストリームに3回以上クエリを実行し、その大半が空の結果を返したか失敗した場合、またはデータ構造（ストリームのスキーマや一覧、メトリクス名やラベル）を3回以上参照した場合です。 | 各サービスのデータの所在とフィルタリング方法を、サービスカタログのデータソース、またはナレッジの`MOLE.md`に記載します。 |
| **サービスごとの名前** | メトリクスまたはAPMにサービスのデータはあるものの、同じサービス名を指定したログまたはトレースのクエリで結果が得られず、そのストリームへのほかのクエリでも見つからなかった場合です。 | すべてのシグナルでサービス名（`service.name`）を統一するか、別名をサービスカタログにエイリアスとして登録します。 |
| **データの要約** | **ログパターンの分析**や**メトリクスの傾向分析**を使わず、生ログまたは未集計の時系列データを2回以上取得し、毎回多数の行が返された場合です。 | 組織のエージェントプロファイルのツールセットに、これらのツールが含まれていることを確認してください。 |

繰り返し検出されたデータギャップをストリームとサービスごとにまとめ、検出した回答数と最終検出日時を表示します。各データギャップの下にある回答を開くと、スコアを確認できます。個人チャットは集計にのみ含め、クエリの内容は表示しません。

### ドリル

ドリルでは、Mole Agentが解決済みのインシデントを進行中のものとして再調査し、インシデント後に特定した根本原因と照合して結果を採点します。モデル、プロンプト、またはツールを変更した後にすべてのドリルを再実行すると、調査の質が向上したかを確認できます。

**新規ドリル**では、過去180日間に解決し、ポストモーテムの**根本原因**セクションに根本原因が記載されているインシデントを選べます。根本原因を別途入力しない限り、ポストモーテムの根本原因を採点の基準にします。**別のインシデント**では、インシデントIDと根本原因を手入力します。ドリルはインシデントごとに1件、組織ごとに最大100件まで保持できます。

ドリルを実行すると、次のように動作します。

- 実行を開始したユーザーの権限で、読み取り専用かつ無人で最大10分間実行します。開始にはインシデントの読み取り権限が必要です。
- インシデント発生時の情報（概要、重大度、サービス、ラベル、トリガーとなったクエリ）とアラートルールの調査ガイドを取得し、インシデント開始の1時間前から開始の30分後までを調査します。
- インシデントの発生後に判明した内容や実施した対応は参照できません。メモ、タイムライン、RCA、ポストモーテム、チケット、承認、類似インシデントが対象です。
- チャット一覧には表示されないチャットとして実行します。実行結果から**調査を開く**を選ぶと、読み取り専用でチャットを開けます。

調査が完了すると、モデルは調査で特定した根本原因を基準の根本原因と比較し、1～5の段階で採点します。スコアは0～100に換算し、実行を開始したユーザーのインターフェース言語で採点理由を表示します。最初に有効な評価者のモデルを使用し、有効な評価者がいなければ組織の最初のモデルプロバイダーを使用します。モデル呼び出しで消費するトークンは、**品質スコアリング**として1日のトークン予算に計上します。実行が失敗または停止した場合や、回答が生成されなかった場合は、スコアを付けずに理由を表示します。

**実行**は1件のドリルを開始します。**すべて再実行**は実行中でないドリルを一度に最大50件まで開始します。ドリルの作成、実行、削除には`agent.quality.manage`権限が必要です。

## プロンプトをデフォルトに設定する前にチェックする

チャット用（**システム指示**）またはインシデントの根本原因分析用（**根本原因分析**）の組織プロンプトで **デフォルトに設定** を選択すると、組織の設定に応じて次のように動作します。

| 設定 | プロンプトが未チェックの場合、またはチェックでスコアが下がった場合 |
|---|---|
| **チェックし、スコアが下がった場合は再確認** | ダイアログに **比較チェックを実行** と **そのまま設定** が表示されます。 |
| **チェックし、スコアが下がった場合は設定を拒否** | チェックで品質の低下がないと判定されたプロンプトのみ設定できます。 |
| **チェックしない** | プロンプトをすぐにデフォルトに設定します。 |

チェックでは、まずリグレッションセットから回答を取り、次に、これらの回答を採点する最初の評価器が直近に採点した回答を追加して、最大8件を比較します。各質問に対し、同じモデルが現在のデフォルトと新しいバージョンで1回ずつ回答を生成します。ツールは再実行せず、質問と前回のツール実行結果をモデルに渡します。根本原因分析では、どちらのバージョンもインシデントの事実に基づいて分析を作成します。その後、評価器が各ペアを採点します。新しいバージョンの平均スコアが現在のデフォルトより5ポイントを超えて低ければ **悪化**、5ポイントを超えて高ければ **改善**、それ以外は **悪化なし** と判定します。比較できた回答が3件未満の場合は判定せず、デフォルトへの設定もブロックしません。

ダイアログには、進捗状況に続いて回答ごとの結果が表示されます。チェックでは、プロンプトの1つのバージョンと、その時点のデフォルトを比較します。プロンプトを編集した場合や別のプロンプトをデフォルトに設定した場合は、チェックを再実行してください。チェック時のモデル呼び出しは **品質スコアリング** としてカウントされます。

その他の用途のプロンプトは、チェックせずにデフォルトに設定します。すでにデフォルトのプロンプトを編集してもチェックは実行されません。変更をチェックするには、新しいプロンプトとして保存し、デフォルトに設定してください。

## ストリーム内のスコア

各スコアは内部ストリーム `_agent_score_traces` に1行ずつ記録されます。このストリームは **ログ** でクエリできます。

| フィールド | 説明 |
|---|---|
| `target_kind`, `target_id` | `chat_answer` とメッセージID、または `incident_rca` とインシデントIDです。 |
| `source` | `personal_chat`、`team_chat`、`automation`、`incident_rca` のいずれかです。 |
| `scorer`, `scorer_kind` | `rules`、または評価器のIDと `evaluator` です。 |
| `score`, `samples` | 0〜1の平均スコアと、その算出に使った採点の回数です。 |
| `tool_success`, `evidence`, `query_validity`, `answer_format`, `completion`, `feedback` | 該当する場合に記録される、各ルールの0〜1のスコアです。 |
| `reason`, `evaluator_model` | 評価器が示した採点理由と、評価器が使用したモデルです。 |
| `chat_id`, `team_id`, `automation_id`, `user_id`, `prompt_template_id`, `prompt_version`, `prompt_key`, `provider_id`, `model`, `skill`, `skill_version` | 回答の生成元と、生成に使用した設定やリソースです。 |

品質の低下を通知するには、ストリームを対象に[異常検知アラートルール](/ja/alerting)を作成してください。たとえば、評価器の平均スコアを監視できます。

```sql
SELECT avg(score) AS value FROM "_agent_score_traces" WHERE scorer_kind = 'evaluator'
```
