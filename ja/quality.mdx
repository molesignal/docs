Mole Agent が作成するすべての回答はスコアリングされます。ルールはモデルを使わずに即座にスコアリングします。対象は、ツールが正常に動作したか、証拠を引用しているか、クエリが解析できるか、適切な形式で出力されたか、質問した人がどのように評価したかです。設定した評価者は、作成したルーブリックに基づき、モデルを使って回答のサンプルをスコアリングします。低いスコアの回答、誰かが役に立たなかったと評価した回答、またはランダムに抽出された回答はレビュー待ちになります。レビュー担当者が承認した回答は回帰セットになります。組織のプロンプトをデフォルトにする前に、チェックでこれらの質問の一部に新しいバージョンと現在のバージョンで再度回答し、評価者が両方をスコアリングします。

スコアは0～100の範囲です。**品質** タブに表示され、すべてのスコアはストリーム `_agent_score_traces` にも書き込まれます。

## 開始する前に

- **品質** タブには `agent.quality.read` が必要です。この権限はオーナーと管理者のロールにデフォルトで付与されています。オーナーと管理者はすべてのチームチャットをすでに読めます。個人チャットは合計にのみカウントされ、品質タブで読まれることはありません。
- 評価者は組織のモデルプロバイダーの1つを使用します。詳細は [Mole Agent](/ja/agent#モデルプロバイダーを設定する) を参照してください。評価者がいなくても、すべての回答はルールによってスコアリングされます。

## スコアリング対象

| ソース | 内容 |
|---|---|
| **チームチャット** | チームチャットの回答。 |
| **個人チャット** | 個人チャットの回答。ルールによってのみスコアリングされ、合計にのみカウントされます。 |
| **オートメーション** | 組織またはチームのオートメーションの各実行での回答。[オートメーション](/ja/automations) を参照してください。個人オートメーションの実行は個人チャットです。 |
| **インシデントRCA** | 根本原因分析が自動またはオンデマンドで生成するRCA、および誰かが評価したRCA。 |

回答は作成されたときにスコアリングされ、質問した人が評価したとき、または評価を取り消したときにも再度スコアリングされます。

## ルール

ルールは、回答とその実行が残した内容を確認し、それぞれを0から100で採点します。回答のルールスコアは、該当するルールのスコアの平均です。

| ルール | スコア | 適用対象 |
|---|---|---|
| **ツール呼び出し** | 失敗しなかったツール呼び出しの割合。 | ツールを呼び出した回答。 |
| **証拠** | 引用された証拠がない場合は0、成功したツール呼び出しに裏付けられていない証拠を引用した場合は50、1件の場合は75、2件以上の場合は100。インシデントRCAの場合、与えられていないラベルを引用すると0、与えられた証拠を1つも引用しないと25、与えられたものだけを引用すると100。 | 要求された形式でツールを呼び出した回答。証拠を渡された、または何らかの証拠を引用したインシデントRCA。 |
| **クエリ** | ツール呼び出し内のSQLおよびPromQLのうち、解析できるものの割合。 | ツールがクエリを実行した回答。 |
| **形式** | 回答が求められた形式になっている場合は100。 | 生成されたクエリを除くすべてのチャット回答。 |
| **完了** | 完了した回答は100、誰かの対応が必要だったオートメーション実行は50、失敗した、停止した、または空の回答は0。 | すべての回答。 |
| **評価** | **役に立った** は100、**役に立たなかった** は0。RCAでは **役に立たなかった** が1件でもカウントされます。 | 誰かが評価した回答。 |

## 評価者

評価者はルーブリックに従って回答を1～5で評価し、その理由を1～2文で示します。スコアは0、25、50、75、100のいずれかで表されます。評価者は、質問、ツールが見つけた内容、回答を読みます。RCAの場合は、インシデントの事実とRCAを読みます。

- 評価者は、設定した割合の新しい回答をスコアリングします。抽出は回答単位で行われるため、再度抽出しても同じ回答になります。
- **役に立たなかった** と評価された回答は、評価者がすでにスコアリングしていない限り、常にスコアリングされます。
- 評価者がレビューしきい値を下回るスコアを付けた回答は、もう一度スコアリングされ、2回のスコアの平均が採用されます。
- 評価者は個人チャットをスコアリングしません。
- 評価者は、最後に保存した人のインターフェース言語で理由を書き込みます。
- 評価者のモデル呼び出しは、ソース別使用量の **品質スコアリング** として、組織の1日あたりのトークン予算にカウントされます。予算を使い切っている間、評価者は新しい回答をスキップします。

すべての評価者が開始時に使用する指示は、組み込みプロンプト **回答評価**（目的 `evaluation`）です。組織は **設定 → プロンプト管理** でこれを上書きできます。プロンプトの内容にかかわらず、評価者は固定形式でスコアを返します。

回答のスコアは、評価者がスコアリングした場合はその評価者たちのスコアの平均、それ以外の場合はルールスコアです。

## 品質タブ

**Mole Agent → 品質**を開きます。**概要**と**回答**では、過去7日、30日、または90日間を対象に、1つのソースまたはすべてのソースを表示します。

| ビュー | 表示内容 |
|---|---|
| **概要** | スコアリングされた回答、ルールと評価者の平均、役に立った/役に立たなかったと評価された回答、レビュー待ちの件数。以下に、日別のスコア、各ルール、ソース・プロンプトバージョン・Skill・モデル別の回答。 |
| **回答** | スコアリングされた回答を新しい順に表示し、**低スコアのみ**でレビューのしきい値を下回るものに絞り込めます。行を開くと、質問と回答の全体、各ルールが見つけた内容、各評価者のスコアと理由、回答のレビューが表示されます。**チャットを開く**または**インシデントを開く**で、作成された場所に移動します。 |
| **レビュー** | レビュー待ち、承認済み、却下済みの回答。 |
| **データギャップ** | 回答のツール呼び出しから、データに欠けていると判明した内容。[データギャップ](#データギャップ)を参照してください。 |
| **ドリル** | 解決済みのインシデントを再度調査し、既知の根本原因と照合して採点したもの。[ドリル](#ドリル)を参照してください。 |
| **評価者** | 評価者と設定。 |

### 回答をレビューする

回答は次の場合にレビュー待ちになります。

| 原因 | 条件 |
|---|---|
| **低スコア** | 評価者のスコアが2回目のスコアリング後もレビューのしきい値を下回っている場合、または評価者がスコアリングしない回答ではルールのスコアがしきい値を下回っている場合。 |
| **「役に立たなかった」と評価済み** | 質問した人が**役に立たなかった**と評価した場合。 |
| **無作為抽出** | スコアが信頼できるかを確認するため、**ランダムレビュー**の割合で抽出された場合。 |

回答は一度だけレビューに回ります。開いて、**メモ**に何が問題で、良い回答なら何が正しいかを書き、次を選択します。

- **承認**: 回答は誤りです。回帰セットに加わり、プロンプトチェックが同じ質問に再び回答する際に、メモが評価者に渡されます。
- **却下**: 回答は問題ありません。

### 評価者と設定

**評価者**の下で、**新規評価器**をクリックするとフォームが開きます。

| フィールド | 説明 |
|---|---|
| **名前** | 組織内で一意です。 |
| **評価基準** | 良い回答が満たす内容と、減点対象となる内容を最大4000文字で記述します。開始用の評価基準があらかじめ入力されています。 |
| **回答** | チームチャット、自動化、インシデントのRCA。 |
| **サンプリング率** | 新しい回答をスコアリングする割合（0〜100）。 |
| **モデルプロバイダー**と**モデル** | 空欄の場合は、組織で最初に利用可能なプロバイダーとそのデフォルトモデルを使用します。 |
| **温度** | 0〜1。0にするとスコアが安定します。 |
| **オン** | オフの評価者は何もスコアリングしません。 |

1つの組織の評価者は最大10個までです。評価者を削除しても、その評価者が付けたスコアは保持されます。

評価者の下の設定:

| 設定 | デフォルト | 説明 |
|---|---|---|
| **レビューのしきい値** | 60 | これを下回るスコアの回答はレビュー待ちになります。 |
| **ランダムレビュー** | 0 | 他の回答のうちレビュー用に抽出する割合。 |
| **プロンプトをデフォルトに設定する前のチェック** | チェックし、悪化した場合は再度確認する | 以下を参照してください。 |

### データギャップ

回答がルールでスコアリングされると、そのツール呼び出しから、Mole Agent が扱えたデータについて何が言えるかも読み取られます。これはスコアを変更しません。ギャップは回答ではなくデータを指し示します。**データギャップ**は過去7日、30日、または90日間のギャップを集計します。

| 種類 | 検出条件 | 補う方法 |
|---|---|---|
| **データの所在** | 同じストリームが3回以上クエリされ、ほとんどのクエリが空または失敗で返った場合、または構造が3回以上参照された場合（ストリームスキーマ、ストリーム一覧、メトリクス名とラベル）。 | 各サービスのデータがどこにあり、どうフィルタリングするかを記録します。サービスカタログのデータソース、またはナレッジの `MOLE.md` に記載します。 |
| **サービスごとの名前** | あるサービスがメトリクスまたはAPMにデータを持っていたが、同じサービスを指定したログまたはトレースのクエリで何も見つからず、そのストリームの他のクエリでも見つからなかった場合。 | すべてのシグナルでサービスに1つの名前（`service.name`）を付けます。または、サービスカタログに他の名前をエイリアスとして登録します。 |
| **データの要約** | 生ログまたは生シリーズが2回以上取得され、それぞれ多数の行があり、**ログパターンの分析**または**メトリクスの傾向分析**が使われなかった場合。 | 組織の Agent Profile のツールセットからそれらのツールが除外されていないか確認します。 |

ビューには、繰り返し検出された各ギャップが、ストリームとサービスごとにグループ化されて表示され、何件の回答で検出されたか、最後に検出された日時も表示されます。その下の回答を開くとスコアが表示されます。個人チャットは合計にのみ含まれ、クエリの内容は表示されません。

### ドリル

ドリルは、解決済みのインシデントを Mole Agent がまるで発生中であるかのように再度調査し、インシデント後に確定した根本原因と照合して採点するものです。モデル、プロンプト、またはツールを変更した後にすべてのドリルを再実行すると、調査が改善されたかを確認できます。

**新規ドリル**では、ポストモーテムに根本原因（**根本原因**のセクション）が記載されている過去180日間に解決されたインシデントを選択できます。ポストモーテムの根本原因が参照として使用されますが、代わりに別の根本原因を記載することもできます。**別のインシデント**では、インシデントIDと手書きの根本原因を指定します。各インシデントには1つのドリルがあり、1つの組織で最大100個まで保持できます。

ドリルの実行:

- 開始したユーザーとして実行され、そのユーザーはインシデントを読み取れる必要があります。無人かつ読み取り専用で、最大10分間実行されます。
- インシデント発生時のファクト（サマリー、重大度、サービス、ラベル、発火したクエリ）とアラートルールの調査ガイドを取得し、インシデント開始の1時間前から終了の30分後までの期間を調べます。
- インシデントについて後から見つかった内容や実施された対応は読み取れません。メモ、タイムライン、RCA、ポストモーテム、チケット、承認、および類似のインシデントが該当します。
- チャット一覧に表示されないチャットです。**調査を開く**で、実行から読み取り専用で開けます。

調査が終了すると、モデルがその根本原因を参照と比較し、1〜5で採点して0〜100として読み取り、実行を開始したユーザーのインターフェース言語で理由を表示します。モデルは最初の有効な評価者のもの、なければ組織で最初のモデルプロバイダーのものが使用されます。その呼び出しは**品質スコアリング**として1日のトークン予算に計上されます。失敗した実行、停止された実行、または回答を書き込まなかった実行にはスコアが付かず、理由が表示されます。

**実行**でドリルを1つ開始します。**すべて再実行**では、実行中のドリルがないすべてのドリルを一度に最大50個まで開始します。ドリルの作成、実行、削除には `agent.quality.manage` が必要です。

## プロンプトがデフォルトになる前にチェックする

チャット用（**システム指示**）またはインシデント RCA 用（**根本原因分析**）の組織プロンプトで**デフォルトに設定**を選択した場合、組織の設定によって動作が決まります：

| 設定 | プロンプトが未チェックの場合、またはチェックで悪化が見つかった場合 |
|---|---|
| **チェックし、スコアが下がった場合は再確認** | ダイアログで**比較チェックを実行**または**そのまま設定**を選べます。 |
| **チェックし、スコアが下がった場合は設定を拒否** | チェックで悪化なしと判定されたプロンプトのみ設定できます。 |
| **チェックしない** | プロンプトはすぐに設定されます。 |

チェックでは最大 8 件の回答を使用します。最初に回帰セット、続いて、これらの回答をスコアリングする最初の評価者が直近にスコアリングした回答を使用します。各回答は、現在のデフォルトと新しいバージョンのそれぞれで、同じモデルによって、ツールを再実行せずにもう一度回答されます。モデルには質問と、そのときにツールが見つけた内容が渡されます。RCA の場合、両方のバージョンがインシデントの事実から RCA を作成します。次に評価者が各ペアをスコアリングします。新しいバージョンは、平均が現在のデフォルトより 5 を超えて低い場合は**悪化**、5 を超えて高い場合は**改善**、それ以外は**悪化なし**です。比較できた回答が 3 件未満の場合、チェックでは判断できず、プロンプトの設定を妨げません。

ダイアログには進捗と、各回答の結果が表示されます。チェックは、1 つのプロンプトバージョンを 1 つのデフォルトと比較するものです。プロンプトを編集した後、または別のデフォルトを設定した後は、再実行する必要があります。チェックでのモデル呼び出しは**品質スコアリング**としてカウントされます。

その他の用途のプロンプトは、チェックなしでデフォルトになります。すでにデフォルトになっているプロンプトを編集する場合もチェックされません。変更をチェックするには、新しいプロンプトとして保存し、それをデフォルトに設定してください。

## ストリーム内のスコア

各スコアは、内部ストリーム `_agent_score_traces` の行でもあり、**ログ**でクエリできます：

| フィールド | 説明 |
|---|---|
| `target_kind`, `target_id` | メッセージ ID が付いた `chat_answer`、またはインシデント ID が付いた `incident_rca`。 |
| `source` | `personal_chat`、`team_chat`、`automation`、または `incident_rca`。 |
| `scorer`, `scorer_kind` | `rules`、または `evaluator` を伴う評価者の ID。 |
| `score`, `samples` | 0 から 1、および何回のスコアリングの平均であるか。 |
| `tool_success`, `evidence`, `query_validity`, `answer_format`, `completion`, `feedback` | 適用される場合の、0 から 1 のルール。 |
| `reason`, `evaluator_model` | 評価者の理由とモデル。 |
| `chat_id`, `team_id`, `automation_id`, `user_id`, `prompt_template_id`, `prompt_version`, `prompt_key`, `provider_id`, `model`, `skill`, `skill_version` | 回答の出所と、回答が使用したもの。 |

品質の低下を通知するには、ストリームに対して[異常アラートルール](/ja/alerting)を作成します。たとえば、評価者の平均に対して作成します：

```sql
SELECT avg(score) AS value FROM "_agent_score_traces" WHERE scorer_kind = 'evaluator'
```
