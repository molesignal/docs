ほとんどのインシデントは変更をきっかけに発生します。データに記録したリリースなら、数分で直前のバージョンと比較できます。記録していないと、1時間も推測を重ねてようやくリリースにたどり着きます。すべてのリリースを記録し、ロールアウト中にバージョンを比較し、ロールバックの条件を事前に決めておきます。

## すべてのリリースを可視化する

| 手順 | 方法 | できること |
|---|---|---|
| すべてのスパンにバージョンを付ける | 各サービスの OpenTelemetry リソースに `service.version` を設定します。 | CI からの報告がなくても、[デプロイタイムライン](/ja/apm/deployments#デプロイのタイムライン)にバージョンが表示され、バージョンごとの判定を確認できます。 |
| CI からデプロイを報告する | デフォルトの取り込みトークンを使い、サービス、バージョン、環境、コミット、CI 実行情報を指定して `POST /api/v1/apm/deployments` を呼び出します。[CI からデプロイを報告する](/ja/apm/deployments#ci-からデプロイを報告する)を参照してください。 | バージョンと並べてコミット、作成者、CI 実行情報を確認できます。失敗したデプロイやロールバックしたデプロイも確認できます。 |
| 設定と機能フラグの変更を報告する | 同じエンドポイントを使い、`kind` に `configuration` または `feature_flag` を設定します。 | リリース以外の変更も APM の検出結果の近くに表示されます。 |
| フロントエンドにバージョンを付ける | RUM SDK の `version` を設定し、同じ CI ジョブからソースマップまたはシンボルをアップロードします。[ソースマップとシンボル](/ja/rum/source-maps)を参照してください。 | スタックトレースが読みやすくなり、RUM の問題がどのバージョンで再発したかを確認できます。 |

イメージタグ、`service.version`、デプロイ報告、 RUM のバージョンには、すべて同じバージョン文字列を使います。

## リリース前にベースラインを把握する

ロールアウト前に、サービスの現状を記録します。主要エンドポイントのエラー率と P95、 [SLO](/ja/apm#サービスレベル目標) のバーンレート、未解決の RUM の問題を確認します。重要な経路の [合成チェック](/ja/synthetics)を **今すぐ実行** で実行します。これにより、リリース後の失敗と以前からの失敗を区別できます。

ロールバックの基準を明文化します。たとえば、エラーの判定が **再発** になる、重要な合成チェックが2回失敗する、高バーンレートのアラートが発報する、といった条件を設定します。

## ロールアウト中に比較する

- 2つのバージョンが同時に稼働している間は、 [デプロイ](/ja/apm/deployments#カナリアデプロイ)セクションの **カナリア** カードに、各バージョンが処理したリクエストの割合、エラー、レイテンシが並んで表示されます。新しいバージョンの判定も表示されます。
- 各バージョンを直前のバージョンと比較し、**再発**、**改善**、**変化なし**、 **リクエスト数不足** のいずれかと判定します。比較にはデフォルトで1,000件のリクエストが必要です。必要な件数に達するまでカナリアを稼働させてください。
- 判定を選択すると **2つのバージョンを比較** が開き、遅くなったエンドポイントと発生件数が増えたエラーが一覧表示されます。
- RUM では、エクスプローラーとエラーの問題一覧を新しいバージョンで絞り込み、 **再発** と表示された問題を確認します。これは、以前に解決した問題が新しいバージョンで再び発生したことを示します。

## 自動化でリリースを監視する

CI ジョブから Mole Agent の[自動化](/ja/automations#ci/cdからオートメーションを起動する)を起動し、初回の確認を任せられます。デプロイステップで変更内容を添えてトリガーを呼び出します。Mole Agent は自動化の指示に従い、たとえば新旧バージョンを比較し、結果をチャットで報告します。最終判断は担当者が行います。

## 判断して記録する

基準を満たしたら、確証が得られるのを待たずにロールバックします。CI から報告する際は `status` を `rolled_back` に設定します。タイムラインにロールバックが表示され、以降の比較で正しいベースラインが使われます。

ロールバックしなかった場合も、リリース後の1日間は SLO を確認します。メモリリークやキューの滞留など、徐々に進む劣化は数時間たって初めて表面化することがあります。

## 受け入れ基準

- すべてのサービスが `service.version` を送信し、本番環境へのすべてのデプロイがコミットとともにデプロイタイムラインに表示されます。
- フロントエンドのリリースでは、報告したバージョンと同じバージョンのソースマップまたはシンボルをアップロードします。
- ロールアウト前にロールバックの基準を明文化します。
- リリースごとに判定を取得するか、比較に必要なリクエスト数に達するまでカナリアを稼働させます。
