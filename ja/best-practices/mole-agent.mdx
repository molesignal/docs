Mole Agent は最初のチャットから役立ちます。ただし、信頼するには、何にアクセスできるかを把握し、回答が正しいことを確かめる必要があります。段階的に導入します。まずデータと操作を制限し、環境の情報を与えてから定型作業を任せます。利用が増えるにつれて、コストと品質を確認します。

## モデルに渡すデータを決める

Mole Agent は、ツールの実行結果を含む会話をモデルプロバイダーに送信します。最初のチャットの前に、データ保護の担当者と次の設定を決めます。

| 管理項目 | 設定場所 | 推奨事項 |
|---|---|---|
| モデルプロバイダー | **Mole Agent → 設定 → モデルと推論** | データポリシーで許可されているプロバイダーを選びます。社内ネットワークでホストするモデルも、OpenAI 互換エンドポイント経由で利用できます。 |
| データの範囲 | **Mole Agent → 設定 → データアクセス** | 調査に必要な環境、サービス、ストリームだけを許可します。 |
| ネットワーク接続 | **Mole Agent → 設定 → ネットワークポリシー** | ツールが必要としない限り、新規プロファイルの既定値どおりオフにします。 |
| 個人データ | [フィールドのマスキング](/ja/settings/data-security#フィールドマスキング)と[正規表現パターン](/ja/settings/data-security#正規表現パターン) | フィールドのマスキングは、利用者のクエリと同様に Mole Agent のクエリにも適用されます。**取り込み時にマスキング**では、保存前に対象のテキストを除去します。 |

使用状況にコストが表示されるよう、各プロバイダーの料金も入力します。

## まず提案にとどめ、変更は後から行う

Mole Agent がどのような提案をするかを把握するまでは、推奨設定の**提案モード**でチャットを利用します。このモードでは、データをクエリして変更を提案しますが、変更は実行しません。提案が妥当だと確認できたら、**承認後に実行**に切り替えます。以降は、ツールの実行モードに従い、変更を実行する前に確認を求めるか、承認に回します。 [実行モード](/ja/agent#実行モード)を参照してください。

- 共有エージェントプロファイルの**承認ポリシー**では、**権限確認のスキップを許可**をオフのままにします。
- L0 の自動実行から L4 の無効化まで、リスクレベルごとのデフォルトポリシーを維持します。 **ツールと機能**の**ツールポリシーの設定**で、**本番**を他の環境より厳しくします。たとえば、 L1 の変更には 1 人の承認を必須にします。
- 承認には、オーナーと管理者が持つ `agent.approve` が必要です。対象の変更を自ら実施する担当者に、カスタムロールでこの権限を付与します。
- MCP サーバーの新しいツールは、明示的に有効にするまでオフのままです。まず、 **すべての読み取り専用ツールを有効にする**で読み取り専用ツールを有効にします。スキルや MCP ツールによってポリシーの許可範囲が広がることはありません。

## 環境の情報を与える

回答の質は、Mole Agent がサービスについてどれだけ把握しているかに左右されます。

- 組織のナレッジを `MOLE.md` に記載するか、`/init` を実行して作成します。サービスとそのオーナー、環境、重要なストリームやダッシュボード、ランブックの場所を記載します。 `runbooks/checkout.md` などの長いファイルは `@path` で参照します。 [ナレッジとメモリ](/ja/agent#ナレッジとメモリ)を参照してください。
- チームごとにナレッジを管理し、そのチームのチャットから参照できるようにします。インシデント対応もチームのチャットで行い、オンコール担当者が同じ調査の経緯を確認し、その続きを進められるようにします。
- **チャット後に記憶を抽出**をオンにして、チャットで得た情報を保持します。 **メモリ**を定期的に見直し、誤った情報を削除します。
- 繰り返し行う手順は[スキル](/ja/agent#スキル)にします。 [スキルリポジトリ](/ja/agent#スキルリポジトリ)で管理し、**毎日同期**を有効にして、手順の変更もコードと同じようにレビューします。

## 定型作業を任せる

[自動化](/ja/automations)を使うと、チャットに参加者がいなくても Mole Agent が作業します。まずはテンプレートを使います。

| テンプレート | 用途 |
|---|---|
| **インシデント分析** | エラーおよびクリティカルのインシデントについて、推定される根本原因とその根拠を根本原因分析（RCA）として記録します。初動対応者は、その内容をもとに調査を始められます。 |
| **毎日の健康チェック** | 平日の朝に、対応が必要な項目を報告します。 |
| **アラートノイズの週次レビュー** | 調整が必要なルールを一覧にします。[本番アラートを対応につなげる](/ja/best-practices/actionable-alerts)を参照してください。 |
| **オンコール負荷の週次集計** | 担当者別の呼び出し件数と夜間の呼び出し件数を集計します。[オンコールと通知を設定する](/ja/best-practices/on-call-setup)を参照してください。 |
| **変更の影響チェック** | デプロイ後に CI から呼び出されると実行します。[リリースを検証する](/ja/best-practices/release-verification)を参照してください。 |

自動化は、最後に保存した担当者の権限で実行します。その担当者が離任すると、別の担当者が保存し直すまで実行に失敗します。共有する自動化ごとにオーナーを記録してください。

実行中は確認に応答できないため、確認が必要なツールは実行されず、実行結果に **誰かが必要です**と表示されます。自動化はデータの読み取りと報告に使い、変更はチャットで行います。

## コストを把握する

- **Mole Agent → 設定 → 使用状況**で日次予算を設定します。インスタンスのデフォルト値 `[agent].daily_token_budget` を使うか、**カスタム**の上限を指定します。過去 30 日間の呼び出し元別の使用状況をもとに、インシデントが多発しても対応できる余裕を持たせます。予算を使い切ると、自動根本原因分析は翌日まで待機し、ログの調査は失敗します。LLM 関数を使うステップも失敗します。
- デフォルトの**モデルの呼び出しを停止**を維持します。予算を超えてもチャットで回答を続ける必要がある場合に限り、 **警告のみ表示して回答を続行**を選びます。
- 詳細を確認するには、**ログ**で内部ストリーム `_agent_model_traces` をクエリします。呼び出しごとのトークン数、レイテンシ、コストを `origin`、`model`、`user_id` 別に確認できます。[使用状況と予算](/ja/agent#使用状況と予算)を参照してください。

## 品質を測定して改善する

- 利用者に回答の評価を依頼します。**役に立たなかった**と評価した理由から、改善点を把握できます。
- チームのチャットと RCA のサンプルを採点する[評価器](/ja/quality#評価器)を追加し、 **品質**タブでスコアの低い項目を毎週確認します。
- `/insight` を週次の自動化として実行します。新たに作成すべきナレッジファイルなど、有効な改善案を最大 5 件提示します。
- プロンプトチェックを**チェックし、スコアが下がった場合は設定を拒否**に設定し、組織の新しいプロンプトによる回答品質の低下を防ぎます。[デフォルトに設定する前にプロンプトをチェックする](/ja/quality#プロンプトをデフォルトに設定する前にチェックする)を参照してください。

## 受け入れ基準

- データポリシーでモデルプロバイダーを許可し、そのプロバイダーの料金を登録しています。
- デフォルトのプロファイルは、ネットワーク接続なしで、必要な環境、サービス、ストリームだけを読み取ります。
- どの共有プロファイルでも**権限チェックをスキップ**を許可せず、**本番**のツールポリシーを明示的に設定しています。
- `MOLE.md` にサービス、そのオーナー、ランブックを記載し、オンコールチームごとにナレッジを管理しています。
- **インシデント分析**の自動化が、エラーおよびクリティカルのインシデントの RCA を作成します。
- 日次予算に自動分析を実行できる余裕があり、担当者が毎週**品質**タブを確認しています。
