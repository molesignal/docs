「権限をもう1つ追加したい」「委託先にダッシュボードを見せたい」「スクリプトにトークンが必要」といった例外対応が積み重なり、アクセス権限は増えていきます。計画がないと、1年後には誰がストリームを削除できるのか、どのトークンでまだデータを書き込めるのかが分からなくなります。最初にアクセス管理モデルを決め、例外もその枠組みの中で扱います。

## 業務に応じてロールを割り当てる

担当業務をもとに、必要な権限を満たす最小限のロールを選びます。各ロールの権限は[権限リファレンス](/ja/identity/roles#権限リファレンス)を参照してください。

| 業務 | ロール | 補足 |
|---|---|---|
| ダッシュボード、ログ、インシデントを閲覧する | **閲覧者** | 大半のユーザーに適したデフォルトのロールです。閲覧者は Mole Agent とチャットすることもできます。 |
| ダッシュボード、アラートルール、パイプラインを作成し、呼び出し通知に対応する | **エディター** | エディターはインシデントの確認とサイレンスができますが、メンバー、トークン、設定は変更できません。 |
| ワークスペースのメンバー、ロール、トークン、設定、外形監視チェック、ステータスページを管理する | **管理者** | ワークスペースごとに数名に絞ります。 |
| インスタンスを所有する | **オーナー** | すべてのオーナーは、プラットフォームの `_sys` 組織にもアクセスできます。2〜3名までに絞ります。 |
| アラート管理の担当者や、外形監視チェックも実行するエディターなど、組み込みロールでは対応できない業務 | [カスタムロール](/ja/identity/roles#ロール) | 要件に最も近い**権限ポリシー**を適用し、不足している権限にチェックを入れます。 |

ロールは個人ごとではなく、[チーム](/ja/identity/teams#チーム)に割り当てます。 [アクセス権の付与](/ja/identity/roles#アクセス権の付与)を通じて割り当てることで、アクセス権はチームの所属状況に連動します。

## シングルサインオンでアクセスを許可する

1. 次の画面で会社の ID プロバイダーを接続します。 [ID とアクセス → SSO プロバイダー](/ja/identity/sso)で接続したら、ディレクトリのグループをロールにマッピングします。 **外部グループ → ロール**で設定すると、サインインのたびにディレクトリのグループに応じたロールが適用されます。
2. どのグループにも該当しないユーザーの**デフォルトロール**を**閲覧者**に設定します。
3. 会社の[メールドメイン](/ja/identity/sso#メールドメイン)を追加します。これにより、招待とシングルサインオンでは、登録したドメインのメールアドレスのみを受け付けます。
4. [セルフサービスでの参加](/ja/settings/organization#登録とアクセス)を無効にするか、有効のままにする場合は **管理者の承認を必須にする**をオンにします。

`[auth].root_email` で指定するルートユーザーはプラットフォーム管理者で、パスワードを使ってサインインします。パスワードはシークレット保管庫に保存し、シングルサインオンを利用できない場合に限ってこのアカウントを使用します。

## 特定のリソースに期限付きでアクセスを許可する

委託先が1つのダッシュボードを閲覧する場合や、アナリストが1つのストリームにクエリを実行する場合など、対象と期間が限られることがあります。その場合は、ワークスペース全体のロールを割り当てる代わりに、対象リソースに[アクセス権の付与](/ja/identity/roles#アクセス権の付与)を作成し、 **有効期限**を設定します。**環境**の制約を設定すると、 `staging` など、指定した環境へのリクエストだけにアクセス権をさらに絞り込めます。

別の組織のユーザーには、 [組織間共有](/ja/identity/roles#組織間でリソースを共有する)を使って、指定したダッシュボードやストリームへのアクセスを許可できます。共有先の組織の管理者が承認すると、指定したリソースと組織に限ってアクセスが有効になります。共有先からさらに別の組織へ共有することはできません。

## チーム単位で担当を割り当てる

チームは単なるユーザーのグループではありません。[オンコールスケジュール](/ja/alerting/on-call)、エスカレーションステップ、 [フォールバックルート](/ja/notification-channels#フォールバックルートを設定する)に加え、 [Mole Agent](/ja/agent#組織、チーム、個人のリソース)のチームチャット、ナレッジ、スキル、MCP サーバーも、チームを参照します。サービスを担当し、呼び出し通知に対応するグループごとにチームを1つ作成します。担当者が異動したときは、チームのメンバー構成を更新します。

## プログラムには専用の認証情報を使う

| プログラム | 認証情報 |
|---|---|
| データの送信のみを行うコレクターまたはエージェント | 書き込み専用のデフォルトの取り込みトークン。 |
| ブラウザーまたはモバイルで実行するコード | アプリケーションの RUM クライアントトークン。エンドユーザーからも見えます。 |
| デプロイを報告する CI | デプロイの報告にも使えるデフォルトの取り込みトークン。 |
| データを読み取る、またはリソースを変更する自動処理 | 必要最小限の権限を持つカスタムロールを割り当てた[サービスアカウント](/ja/identity/tokens#サービスアカウント)。 |
| ユーザーが実行するスクリプトまたは MCP クライアント | 有効期限付きの個人用 API トークン。 |

インテグレーションごとにサービスアカウントを1つ作成します。インテグレーションの利用を終了したら、そのアカウントを無効にします。これにより、そのアカウントに属するすべてのトークンが使えなくなります。ユーザーが作成するトークンには、すべて有効期限を設定します。プログラムにはユーザーのログインセッションを使わせないでください。

## アクセス権を定期的に見直す

四半期ごと、およびメンバーの離任時に、次の点を確認します。

- [ユーザー](/ja/identity/members#ユーザー)で、離任したメンバーのアカウントを無効にします。**最終アクティブ日時**を確認し、使われなくなったアカウントを特定します。
- [API トークン](/ja/identity/tokens#組織のトークン)で、最近使われていないトークンや、離任したメンバーのトークンを失効させます。
- [アクセス権の付与](/ja/identity/roles#アクセス権の付与)で、期限切れのアクセス権を削除します。
- [監査](/ja/settings/data-security#監査)で、ロール、アクセス権の付与、トークン、設定の変更を確認します。
- [共有ポリシー](/ja/settings/organization#共有とパブリックアクセス)と、既存の公開リンクを確認します。

コンプライアンス要件に合わせて[監査ログの保持期間](/ja/settings/platform#監査ログの保持)を設定します。

## 受け入れ基準

- 大半のユーザーに**閲覧者**を割り当て、**管理者**と**オーナー**は必要性を確認したうえで割り当てています。
- ユーザーは SSO でサインインし、ディレクトリのグループに応じたロールが適用されます。
- すべてのプログラムがサービスアカウントまたは取り込みトークンを使用し、ユーザーのセッションを使っていません。
- 有効期限ポリシーで定めた期間を超えて有効な API トークンはなく、未使用のトークンは失効しています。
- 四半期ごとの見直しには実施日と担当者があり、監査ログに記録が残っています。
