テレメトリーは、それで答えられる問いよりも速く増えます。有効にしたままのデバッグログやユーザー ID を含むラベル、毎秒記録するヘルスチェックは、インシデントの解決に役立たないまま保存容量を倍増させることがあります。役に立たないデータを減らし、調査に必要なデータを残します。

## まず計測する

設定を変更する前に、データ量の多いストリームを特定します。

| 場所 | 確認できる内容 |
|---|---|
| [ホーム](/ja/home#データ取り込み) | 選択した期間におけるシグナルごとの取り込み量、保存量、受信量を確認できます。 |
| [ストリーム](/ja/streams#ストリーム一覧) | ストリームごとに、期間内の圧縮後のデータ量、変換前の**収集サイズ**、**保存サイズ**、**インデックスサイズ**、**レコード**数を確認できます。数値を比較して、データ量の多いストリームを特定します。 |
| [取り込み使用量](/ja/streams#データ取り込み量と予算) | トークン、コネクター、ストリーム、サービスごとの取り込み量を確認できます。ソースごとに予算を設定すると、使用量が予算に近づいたときや超過したときに通知します。 |
| [メトリクス](/ja/metrics#結果を分析する) | メトリクスの**カーディナリティ**（アクティブな時系列の数）を確認できます。 |
| [Mole Agent の使用量](/ja/agent#使用状況と予算) | ソース別・日別のモデルトークン使用量と、1 日あたりの予算を確認できます。 |

データ量が最も多いストリームの数値を記録します。この数値を基準に、各変更の効果を評価します。

## 使わないデータは保存前に除外する

保存しなければ、ストレージコストはかかりません。ログ用のリアルタイム [パイプライン](/ja/pipelines#リアルタイムパイプライン)は、保存前の取り込み時に実行されます。

- **イベントをフィルタリング**は、ヘルスチェック、Readiness プローブ、本番環境で参照しないデバッグログを除外します。
- **サンプリング率**は、発生頻度が高くても有用なイベントの一部を残します。**フィールドでサンプリング**では、同じリクエスト ID など、値が同じイベントをまとめて保持または除外します。
- **フィールドを削除**は、リクエストボディ全体など、クエリで使わない大きなフィールドを削除します。

可能であれば、送信側を先に変更します。本番環境のログレベルを `info` に設定するか、コレクターのプロセッサーで不要なイベントを除外すると、ネットワークの負荷も軽減できます。除外したイベントは復元できないため、繰り返し発生するイベントだけをサンプリングし、エラーは対象にしないでください。

トレースのデータ量は、送信元または OpenTelemetry Collector で削減することを推奨します。同じトレースに属するスパンはまとめて扱います。APM の指標と SLO の集計対象は、到着したスパンだけです。トレースストリームの [リアルタイムパイプライン](/ja/pipelines#トレース)では、テールサンプリングの後にサンプリングできます。 **フィールドでサンプリング**に `trace_id` を指定すると、トレース単位で保持または除外できます。APM の指標はパイプラインの実行前に算出するため、パイプラインで除外するスパンも集計対象に含まれます。RUM では、アプリケーションごとに [セッションサンプリング](/ja/rum/sampling)を設定します。

## データは必要な期間だけ保持する

| データ | リテンション | 設定方法 |
|---|---|---|
| デバッグログと詳細ログ | 数日 | 専用のストリームで**データ保持期間（日）**を短く設定します。 |
| アプリケーションログとアクセスログ | 数週間 | [プラットフォームのデフォルト値](/ja/settings/platform#データ保持)（30 日）を使うか、ストリームごとに設定します。 |
| 監査ログとコンプライアンスログ | 数か月または数年 | ストリームの保持期間を長くし、アクセスを制限します。 |
| メトリクス | 数か月 | メトリクスストリームの**リテンション**タブで**古いサンプルをダウンサンプリング**を有効にします。古いサンプルを時間枠ごとに集約し、長期間を対象とするクエリの読み取り量を大幅に減らします。 |

調査で実際にさかのぼる期間を基準にリテンションを設定し、問題の発見が遅れる場合に備えて余裕を持たせます。保持期間を短縮すると、変更後の期間を過ぎたデータを次回のクリーンアップで削除します。ダウンサンプリングでは元のサンプルを削除します。どちらも元に戻せません。ログとトレースでは**小さいファイルを日単位で統合**を有効にして、複数日にわたるクエリで開くファイルの数を減らします。

## メトリクスの時系列数を抑える

ラベル値の組み合わせごとに 1 つの時系列ができます。ユーザー ID、リクエスト ID、未加工の URL など、値の種類に上限がないラベルは、時系列を際限なく増やします。 [カーディナリティの上限](/ja/settings/platform#メトリクスのカーディナリティ)に達すると、組織全体で新しい時系列の作成を拒否します。

- ラベルを追加したら、メトリクス画面で**カーディナリティ**を確認します。
- 未加工のパスはルートテンプレートに、ID はプランやリージョンなどの分類に置き換えます。
- リクエストごとの詳細はログやスパンに記録します。値の種類が増えても、それ自体に追加コストはかかりません。
- 送信側を変更できない場合は、メトリクスストリームの[リアルタイムパイプライン](/ja/pipelines#メトリクスとトレース)で、サンプルを保存する前にラベルを削除または書き換えます。

## クエリのコストを抑える

| 推奨事項 | 効果 |
|---|---|
| データ量の多いストリームに**クエリの最大対象期間（時間）**を設定する | 誤って「過去 90 日間」を指定しても、全データをスキャンせずにクエリを拒否します。 |
| ダッシュボードの絞り込みに使うフィールドにインデックスを付ける | フィルターで不要なファイルの読み取りを省きます。[ストリームとフィールドを設計する](/ja/best-practices/stream-design#絞り込みに使うフィールドにインデックスを設定する)を参照してください。 |
| 最も短い期間から始める | まず対象期間を絞り、必要なときだけ広げます。 |
| 長時間のスキャンは[検索ジョブ](/ja/streams#検索ジョブ)で実行する | クエリをバックグラウンドで実行し、結果を保持します。ページを開いたままにする必要はありません。 |
| ダッシュボードの更新頻度を閲覧頻度に合わせる | **自動**更新は対象期間に合わせて更新間隔を調整します。負荷の高いパネルを壁面ディスプレイに表示する場合は、短い更新間隔を避けてください。 |

## 完了条件

- データ量が最も多い 5 つのストリームを特定し、変更前後の 1 日あたりのデータ量を把握しています。
- どのストリームにも、ヘルスチェック、Readiness プローブ、本番環境のデバッグログを意図せず保存していません。
- ストリームごとに用途に合ったリテンションを設定し、長期間保持するメトリクスをダウンサンプリングしています。
- メトリクスの時系列数が週ごとに安定しており、上限を大幅に下回っています。
- データ量の多いストリームにクエリの最大対象期間を設定し、よく使うフィルターの対象フィールドにインデックスを付けています。
