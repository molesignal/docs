外形監視は、顧客から障害の報告が届く前に、サービスを外部からテストします。 **外形監視**を開くと、チェックの作成、スケジュールの公開、実行時の証跡の確認、プライベートプローブロケーションの管理ができます。

## 監視できる対象

| チェックタイプ | 用途 |
|---|---|
| **HTTP / API** | URL、メソッド、ヘッダー、ボディ、レスポンスステータス、コンテンツ、タイミングを検証します。 |
| **ブラウザー** | ブラウザーで一連の操作を実行し、ページやステップの結果をアサーションで検証します。 |
| **TCP** | 指定したホストとポートが接続を受け付けることを確認します。 |
| **DNS** | システムのリゾルバーまたは指定したリゾルバーで任意のレコードタイプ（A、AAAA、CNAME、MX、NS、TXT、SOA、SRV、CAA、PTR）を解決し、応答内容と応答コードを検証します。必要に応じて DNSSEC を必須にできます。 |
| **ICMP / Ping** | ping を数回送信し、パケットロスと平均ラウンドトリップ時間を確認します。 |
| **TLS** | TLS ハンドシェイク、証明書の識別情報、有効期限を検証します。 |
| **gRPC** | gRPC エンドポイントを呼び出し、レスポンスを検証します。 |
| **ハートビート** | 外部ジョブやサービスから期限内に報告が届くかを確認します。 |

gRPC チェックでは、**アドレス**を `host:port` 形式で入力してください。呼び出しに TLS を使用するかどうかは、**TLS を使用**の設定だけで決まります。 **TLS を使用**がオンのときに `http://` を指定するなど、スキームが設定と矛盾するアドレスは拒否されます。

## チェックを作成して公開する

<Steps>
  <Step title="ドラフトを作成する">
    **外形監視 → チェック**を開き、**チェックを作成**を選択して、チェックタイプを選択します。監視対象、タイムアウト、アサーション、スケジュール、1 つ以上のロケーションを設定します。新規チェックはドラフトとして作成されます。
  </Step>
  <Step title="リビジョンをテストする">
    **リビジョンをテスト**を選択します。MoleSignal はスケジュールを有効にせずにドラフトを実行します。解決された監視対象、試行、タイミング、アサーションの証跡、エラーを確認します。
  </Step>
  <Step title="リビジョンを公開する">
    テストに成功すると、**改訂版を公開**を選択できます。公開するとリビジョンが有効になり、最初の実行予定時刻が決まります。
  </Step>
  <Step title="モニターを運用する">
    必要に応じて、**今すぐ実行**を選択してチェックを実行します。編集すると新しいドラフトリビジョンが作成されます。テストを済ませてそのリビジョンを公開するまでは、公開済みの設定でチェックが実行されます。実行結果の履歴を削除せずに、チェックを一時停止、再開、アーカイブできます。
  </Step>
</Steps>

<Note>
公開前のテストを必須にすることで、未検証の監視対象やアサーションを含むリビジョンが、正常に稼働している本番環境のスケジュールを意図せず上書きするのを防ぎます。
</Note>

## スケジュールと再試行

実行間隔、またはタイムゾーンを明示した cron 式を使用します。ほとんどのアクティブチェックでは、実行間隔を 10 秒から 1 日まで指定できます。ブラウザーチェックの最短間隔は 60 秒です。タイムアウトは 100 ミリ秒から 5 分までの範囲で、実行間隔より短く設定してください。 MoleSignal は、最終結果を記録する前に最大 2 回再試行できます。

ハートビートチェックでは、外部にリクエストを送るスケジュールではなく、報告期限を設定します。ジョブを実行するワークロードからハートビートを送信し、実行結果の履歴を確認して、報告の遅延とアクティブプローブの失敗を区別します。

## アサーションとヘルス状態

アサーションは、レスポンスステータス、ボディ、ヘッダー、DNS の応答内容、証明書のプロパティ、ブラウザー操作の結果など、プロトコル固有の項目を検証します。 **警告**のアサーションが失敗すると結果は劣化になり、**重大**のアサーションが失敗すると結果は失敗になります。

チェックタイプごとに、レスポンスから次の値をアサーションで使用できます。

| チェックタイプ | アサーションのソース |
|---|---|
| **HTTP / API** | `status`、`body`、`json:<JSONPath>`、`header:<name>`、`duration_ms`、`size_bytes`、`timing.dns_ms`、`timing.connect_ms`、`timing.tls_ms`、`timing.first_byte_ms` |
| **TCP** | `response`、`duration_ms` |
| **DNS** | `answers`、`answer_count`、`rcode`、`duration_ms` |
| **gRPC** | `status`（`SERVING` など、ヘルスサービスが返すサービス提供状態）、`duration_ms` |

チェックがサポートしていないソースを指定すると、リビジョンの保存時に拒否されます。

`json:` では、JSONPath（RFC 9535）を指定して、ボディの先頭 4 MiB に含まれる JSON から値を抽出します。値が 1 つなら、文字列はそのまま、それ以外は JSON として扱います。複数の値は JSON 配列として扱います。一致する値がない場合やボディが JSON でない場合は、空として扱います。`body` では **JSON Schemaに一致**アサーションも使用できます。このアサーションは同じ範囲の 4 MiB を読み取り、ボディがスキーマと一致しない最初の箇所を示します。スキーマの `$ref` で外部 URL やファイルは参照できません。`size_bytes` はボディのサイズを最大 16 MiB まで計測します。 `timing.*` はそのステップの各フェーズの所要時間を示し、経由しなかったフェーズは 0 になります。JSONPath による抽出にパターンは不要で、見つかった値をそのまま使用します。

監視対象を解決できない場合や到達できない場合、接続が切断された場合、TLS ハンドシェイクが失敗した場合、タイムアウトまでに応答がない場合は、重大なアサーションが失敗した場合と同様に、実行結果は失敗になります。結果が不明になるのは、送信ポリシーが監視対象への通信をブロックしている、シークレットが不足している、設定がサポートされていないなど、設定どおりにチェックを実行できない場合に限ります。

モニターのヘルス状態は、選択したロケーションでの連続した成功と失敗に基づいて判定します。状態が頻繁に切り替わったり、1 つのネットワークの問題を全体の障害と誤判定したりしないよう、失敗しきい値、復旧しきい値、ロケーションポリシーを設定してください。

## HTTP 接続

HTTP チェックの **接続**セクションでは、サーバーへの接続方法を設定します。空欄のフィールドにはデフォルト値が適用されます。

| 設定 | 動作 |
|---|---|
| **HTTP バージョン** | **自動ネゴシエーション**は、TLS 接続で HTTP/2 と HTTP/1.1 を提示し、サーバー側で選択します。平文 HTTP では HTTP/1.1 を使用します。**HTTP/1.1 のみ**は HTTP/1.1 だけを提示します。**HTTP/2 のみ**は、サーバーが HTTP/2 に同意しないと実行結果が失敗になります。平文 HTTP では事前知識に基づいて HTTP/2（h2c）で通信します。 |
| **DNS サーバー** | `host` または `host:port` 形式で指定したサーバーでホスト名を解決します。このサーバーも送信ポリシーの適用対象です。 |
| **ホストバインディング** | hosts ファイルと同様に、ホスト名を指定した IP アドレスに割り当てます。Host ヘッダーと証明書の検証では元のホスト名を使うため、特定のオリジンサーバーや CDN ノードのチェックに適しています。 |
| **クライアント証明書** | サーバーが相互 TLS を要求したときに使用する証明書チェーンと秘密鍵を、PEM 形式のファイルとしてアップロードするか、貼り付けます。両方を含むファイルを指定すると、両方のフィールドが入力されます。秘密鍵は暗号化して保存され、再表示できません。チェックを編集する際に既存の鍵を保持するには、秘密鍵のフィールドを空欄にしてください。 |

各ステップの実行結果には、接続先のアドレス（`remote_address`）と、サーバーが応答に使用した HTTP バージョン（`http_version`）が記録されます。

## トレースコンテキストと失敗時の診断

チェックの **診断** セクションには 2 つのスイッチがあり、どちらもデフォルトでオンになっています。

**トレースコンテキスト**: HTTP チェックのすべてのリクエスト（リダイレクトを含む）と、すべての gRPC 呼び出しに W3C の `traceparent` が付きます。1 回の試行のリクエストは同じトレースに属し、各リクエストが 1 つのスパンになります。ステップで `traceparent` ヘッダーやメタデータを独自に設定した場合は、その値を保持します。ステップと結果には `trace_id` が記録されます。結果の詳細で **トレースを表示** を選択すると、テスト対象のサービスがそのリクエストに対して記録したトレースが開きます。サービスがトレースを記録していない場合は何も表示されません。gRPC チェックで設定したメタデータも呼び出しとともに送信されます。

**失敗時のトレースルート**: HTTP、TCP、TLS、gRPC、SSH、ICMP のチェックが対象に到達できない場合（接続の失敗、タイムアウト、切断、TLS ハンドシェイクの失敗、ping の応答なしやパケット損失）、Mole Agent は最後に試行したアドレスに対して ICMP トレースルートを 1 回実行します。上限は 30 ホップ、各ホップ 4 プローブ、12 秒です。結果の詳細には、各ホップのアドレス、損失率、往復時間の最小値、平均値、最大値が表で表示されます。トレースルートには、raw ソケット（root または `CAP_NET_RAW`）か、特権不要の ICMP ソケット（macOS、または Linux で `net.ipv4.ping_group_range` の範囲内にあるグループ）が必要です。どちらも使用できない場合は、ステップに未実行の理由が表示されます。

古いバージョンの Mole Agent は `traceparent` を送信せず、トレースルートも実行しません。チェックの判定には影響しません。

**RUM セッション**: ブラウザーチェックは、ページのスクリプトが実行される前に、テストであることをページに通知します。[ブラウザー RUM SDK](/ja/rum/browser-sdk) を実行するページは、`synthetics` タイプのセッションを記録します。試行の **この実行の RUM セッションを開く** を選択すると、そのセッションのリプレイとイベントを確認できます。このセッションは[実ユーザーの集計から除外されます](/ja/rum/test-traffic)。SDK を実行するかどうかはページ側で決まり、実行しないページに SDK が追加されることはありません。

## 時間範囲と可用性

全体の概要、チェック一覧、結果、各チェックの概要では、ナビゲーションカードの右側に時間範囲が表示されます。初期表示は過去 24 時間です。範囲は変更できます。

- **可用性** = 可用と判定された実行数 ÷ 判定済みの実行数。成功、不安定、性能低下の実行は可用とみなし、失敗した実行は不可用とみなします。不明またはスキップされた実行は集計に含めません。
- 全体の概要には、指定範囲における全チェックの可用性とその推移が表示されます。マップはロケーションごとに色分けされます。チェック一覧には各チェックの可用性を示す列が追加され、各チェックの概要には範囲内の可用性、応答時間の中央値、p95 が表示されます。また、**ロケーション別の応答時間**では、各ロケーションの所要時間の中央値を時間間隔ごとにグラフで表示します。
- **最新の実行**欄には、時間範囲に関係なく最新の実行が表示されます。

可用性は `GET /api/v1/synthetics/availability` で取得します。パラメーターは `from` と `to`（マイクロ秒）、 `monitor_id`、`location_id`、`step`（秒。省略時は時間範囲に応じて決定）です。レスポンスには、実行数、可用と判定された実行数、失敗数、未判定の実行数、可用性、所要時間の P50、P95、最大値が含まれます。集計単位は全体、チェック別、ロケーション別、時間間隔別です。単一のチェックを指定すると、ロケーションごとの時間間隔別の集計も返します。結果一覧の `GET /api/v1/synthetics/results` には `fromTime` と `toTime` を指定します。

## 結果ストリームと保持期間

テスト実行を除くすべてのスケジュール実行は、詳細結果に加えて、組織の `_synthetic_results` ログストリームにも、実行開始時刻を持つ 1 行として記録されます。値のないフィールドは省略されます。

| フィールド | 内容 |
|---|---|
| `check_id`, `check_name`, `check_kind`, `revision_id` | 実行したチェックとそのリビジョン |
| `location_id`, `location_name`, `agent_id` | 実行したロケーションと Mole Agent |
| `result_id`, `outcome`, `available`, `attempts` | 実行結果、可用かどうか（不明またはスキップの場合は省略）、試行回数 |
| `duration_ms`, `dns_ms`, `connect_ms`, `tls_ms`, `first_byte_ms` | 最後の試行の合計所要時間と各フェーズの所要時間 |
| `status_code`, `error_category`, `skip_reason`, `trace_id` | HTTP ステータス、失敗カテゴリ、スキップ理由、トレース ID |
| `team_id`, `tags` | チェックのチームとタグ（タグはカンマ区切り） |

ダッシュボードパネルとアラートルールは SQL でストリームを読み取ります。パネルの時間範囲はクエリにも適用されます。次の例では、各チェックの可用性と所要時間の p95 を取得します。

```sql
SELECT check_name,
       avg(CASE WHEN available THEN 1.0 ELSE 0.0 END) AS availability,
       approx_percentile_cont(0.95) WITHIN GROUP (ORDER BY duration_ms) AS p95_ms
FROM _synthetic_results
WHERE available IS NOT NULL
GROUP BY check_name
```

スケジュールされたアラートルールも同じデータを読み取り、[ルールの分割](/ja/alerting/rules#列でルールをグループ化する) に `location_name` を使います。これにより、可用性がしきい値を下回ったロケーションごとに個別のインシデントが作成されます。

詳細結果のデフォルトの保持期間は 30 日です。プラットフォームの **データ保持**ページの **シンセティックテスト結果** で設定します（0 は無期限）。詳しくは、[プラットフォーム設定](/ja/settings/platform#データ保持)を参照してください。保持期間を過ぎた実行とそのアーティファクト、および完了済みのタスクは、1 日に 1 回削除されます。`_synthetic_results` ストリームには、ストリームのページで変更できる保持設定が適用されます。

## ロケーションとプローブエージェント

MoleSignal は、2 種類のロケーションをサポートします。

| ロケーション | 動作 |
|---|---|
| **組み込みローカル** | スタンドアロンデプロイでは、同じプロセス内でプローブランナーが自動的に起動します。ローカルでの評価や、MoleSignal と同じ環境から実行する必要があるチェックに適しています。 |
| **エージェントプール** | 1 つ以上の外部 <code>probe-agent</code> プロセスが、プライベートネットワーク、リージョン、またはエッジロケーションからチェックを実行します。 |

**外形監視 → ロケーション**でエージェントプールのロケーションを作成し、使い捨ての登録トークンを生成して、エージェントを登録します。

```bash
probe-agent register \
  --endpoint https://molesignal.example.com:5084 \
  --token ONE_TIME_TOKEN \
  --ca-certificate-base64 BASE64_CA
```

続いて、エージェントの制御ストリームを開始します。

```bash
probe-agent run
```

登録には、サーバー認証付き TLS を使用します。エージェントは自身の認証情報を
<code>--state-dir</code> に保存し、ポート 5085 の制御ストリームに mTLS を使用します。デフォルトの状態
ディレクトリは <code>/var/lib/molesignal-probe</code> です。

<code>conf/config.toml</code> でサーバーのエンドポイントを設定します。

プローブのコントロールプレーンは、**スタンドアロン**ノードと**アラート**ノードで自動的に起動します。個別の有効化設定はありません。

```toml
[probe]
bind = "0.0.0.0"
register_port = 5084
control_port = 5085
register_endpoint = "https://molesignal.example.com:5084"
control_endpoint = "https://molesignal.example.com:5085"
server_names = ["molesignal.example.com"]
```

<Warning>
すべてのネットワークリクエストに対して、送信前にエグレスポリシーを適用します。ループバック、リンクローカル、プライベートの各アドレスは、選択したロケーションのポリシーで明示的に許可されていない限り拒否します。これにより、 MoleSignal ホストとプライベートネットワークをサーバーサイドリクエストフォージェリ（SSRF）から保護します。
</Warning>

HTTP チェックは、プローブエージェントの環境変数 `HTTP_PROXY`、`HTTPS_PROXY`、`ALL_PROXY`、`NO_PROXY` に従います。プロキシを経由する場合、結果の接続時間には、プロキシへの接続とトンネル確立リクエストにかかった時間が含まれます。ターゲットへの接続はプロキシが行うため、ターゲットの接続先がエグレスポリシーで許可されたアドレスに限定されるわけではありません。プロキシが到達できる宛先を制限してください。

エージェントが ICMP チェックを提供するのは、プロセスが ping を送信できる場合に限ります。Linux では `CAP_NET_RAW` が必要です。または、プロセスを `net.ipv4.ping_group_range` の範囲内のグループに所属させます。組み込みローカルロケーションで同じプロセス内で動作するランナーにも、同じ条件が適用されます。

エージェントは、ハートビートを送信するたびに機能レベルを報告します。古いエージェントがサポートしない設定を使うチェックは、対応バージョンのエージェントにのみ割り当てます。対象は、A と AAAA 以外の DNS レコードタイプ、名前を指定したリゾルバー、DNSSEC、ICMP、TCP・DNS・gRPC チェックのアサーションです。HTTP チェックでは、 JSONPath、JSON Schema、サイズとタイミングの測定元、HTTP/2 のみの使用、DNS サーバー、ホストバインディング、クライアント証明書が対象です。エージェントプールでこれらのチェックを実行する前に、`probe-agent` をアップグレードしてください。

ハートビートが 1 分間途絶えると、エージェントをオフラインと判定します。ロケーションの健全性は、所属するエージェントの状態に応じて変わります。全台がオンラインならオンライン、一部のみなら低下、1 台もオンラインでなければオフラインです。期限までにどのエージェントも実行を引き受けなかった場合は、実行を**スキップ済み**として記録し、理由を示します。オンラインのエージェントがない、チェックの種類に対応するエージェントがない、設定に対応できる新しいエージェントがない、またはすべてのエージェントが処理中のいずれかです。

### Kubernetes でエージェントを実行する

Helm チャート `probe-agent` は、エージェントを StatefulSet として実行します。各レプリカは個別に登録し、自身の認証情報と未送信の結果を専用の永続ボリュームに保存します。そのため、Pod を置き換えても同じエージェントとして動作します。このチャートはサーバーをデプロイしません。サーバーは `molesignal` チャートを使って、同じクラスターまたは別の環境にデプロイします。

<Warning>
外部エージェントを使用するには、サーバーとエージェントイメージの両方に 26.2.0.0 より新しいバージョンが必要です。26.2.0.0 では、サーバーがエージェントを登録できず、エージェントは**登録済み**ステータスから先に進みません。
</Warning>

<Steps>
  <Step title="エージェントが到達できるアドレスをサーバーに設定する">
    エージェントは、**スタンドアロン**ノードまたは**アラート**ノードのポート 5084 と 5085 に接続します。`server_names` には、エージェントが使用するホスト名を含める必要があります。デフォルトでは `localhost` のみが含まれます。`molesignal` チャートのデプロイ先と同じクラスターにエージェントがある場合は、そのチャートの values に Service 名を設定します。 `distributed` モードでは、`alert` ロールの Service を使用します。

    ```yaml
    config:
      probe:
        register_endpoint: https://molesignal.molesignal.svc.cluster.local:5084
        control_endpoint: https://molesignal.molesignal.svc.cluster.local:5085
        server_names: [molesignal.molesignal.svc.cluster.local]
    ```

    エージェントが別の環境にある場合は、`LoadBalancer` または `NodePort` Service で 2 つのポートを公開します。通信経路の途中で TLS を終端しないでください。エージェントはサーバーの CA のみを信頼し、制御ストリームではクライアント証明書でエージェントを認証します。
  </Step>
  <Step title="ロケーションとトークンを作成する">
    **外形監視 → ロケーション**を開き、**プライベートロケーションを追加**を選択して、トークンを作成します。

    | トークン | 作成場所 | 登録できるエージェント | 有効期間 |
    |---|---|---|---|
    | 使い捨てトークン | **エージェントを登録** | 1 台 | 最大 60 分 |
    | エージェントトークン | **外形監視 → エージェント → エージェントトークンを作成** | 期限切れまたは無効化まで台数制限なし | 30 日から 1 年、または無期限 |

    複数のレプリカにはエージェントトークンを使用します。どちらのトークンも登録コマンドとともに一度だけ表示されます。次の手順では、そのコマンドの `--endpoint` と `--ca-certificate-base64` を使用します。
  </Step>
  <Step title="チャートをインストールする">
    トークンを Secret に保存します。このチャートにはデフォルトのトークンがなく、トークンを ConfigMap に書き込むこともありません。

    ```bash
    kubectl create namespace probes
    ```

    ```bash
    kubectl --namespace probes create secret generic probe-agent-registration --from-literal=token=<token>
    ```

    ```bash
    helm repo add molesignal https://charts.molesignal.com
    ```

    ```bash
    helm install probe-agent molesignal/probe-agent --namespace probes --set registration.endpoint=<endpoint> --set registration.caCertificateBase64=<base64-ca> --set registration.existingSecret=probe-agent-registration
    ```

    エンドポイントと CA を確認します。テストでは、サーバーが拒否するトークンを使って登録を試みます。

    ```bash
    helm test probe-agent --namespace probes
    ```

    その後、エージェントが**外形監視 → エージェント**に表示されます。
  </Step>
</Steps>

| 動作 | 詳細 |
|---|---|
| 登録 | 初期化コンテナは、ボリュームに認証情報がない場合にのみエージェントを登録します。そのため、使い捨てトークンが使用済みでも、Pod の置き換えには影響しません。 |
| トークン | エージェントは、認証情報を取得するまでの間だけトークンを読み取ります。トークンを更新しても再起動は発生しません。エージェントがオンラインになったら、Secret を削除できます。認証情報もトークンもないレプリカは `Init` 状態で待機し、その理由をログに記録します。 |
| スケールダウンとアンインストール | ボリュームは残るため、エージェントは元の認証情報で復帰します。エージェントを廃止するには、登録を取り消し、その PersistentVolumeClaim `state-<release>-probe-agent-<ordinal>` を削除します。 |
| 長期間接続しないエージェント | 証明書の有効期間は `[probe].certificate_days` で指定し、デフォルトは 30 日です。残りの有効期間が 1 週間未満のときにエージェントが接続すると、証明書を更新します。期限を過ぎるとエージェントは再接続できません。登録を取り消してボリュームを削除し、再登録させてください。 |
| ping | チャートが Pod の `net.ipv4.ping_group_range` を設定するため、ICMP チェックにケーパビリティは不要です。 |
| イメージ | `ghcr.io/molesignal/probe-agent`。`global.imageRegistry` でレジストリのホストを置き換えます。 |

ブラウザーチェックでは、Chromium のサンドボックスを使用するかどうかを決める必要があります。チャートはデフォルトで Chromium を `--no-sandbox` 付きで起動します。サンドボックスには非特権ユーザー名前空間が必要ですが、`RuntimeDefault` seccomp プロファイルはこれをブロックします。この構成では、Chromium を Pod 内に隔離します。root では実行せず、ケーパビリティもサービスアカウントトークンも付与せず、ルートファイルシステムは読み取り専用です。Chromium の脆弱性を悪用するページは、エージェントの秘密鍵へのアクセスを含め、その Pod と同じ権限を取得します。サンドボックスを使用するには、 `browser.sandbox` を `true` に、`securityContext.seccompProfile.type` を `Unconfined` に設定します。この場合、ノードで非特権ユーザー名前空間を許可する必要があります。Ubuntu 23.10 以降では、 `kernel.apparmor_restrict_unprivileged_userns=0` が必要です。Pod Security Standards の `baseline` と `restricted` では、 `Unconfined` は許可されません。

`/dev/shm` の設定は不要です。エージェントは Chromium を `--disable-dev-shm-usage` 付きで起動するため、共有メモリには `browser.tmp` で設定する `/tmp` を使用します。デフォルトのリソースはリクエストが 512 MiB、上限が 2 GiB で、ブラウザーチェックを一度に 1 件実行できます。同時実行数を 1 件増やすごとに、上限を少なくとも 1 GiB 増やしてください。同時実行数は `browser.maxConcurrent` で指定します。`browser.maxConcurrent` を `0` に設定すると、エージェントはブラウザーチェックを提供しません。

設定値の一覧とトラブルシューティングについては、 [チャートの README](https://github.com/molesignal/molesignal-helm/tree/main/charts/probe-agent) を参照してください。

## 変数、シークレット、エビデンス

再利用する機密性のない値には変数を、認証情報には暗号化されたシークレットを使用します。シークレットの値は書き込み専用で、API からは返しません。結果の詳細には、保存済みのシークレットを公開することなく、記録量を制限したリクエストとレスポンスのエビデンス、タイミング、試行のメタデータ、選択したロケーション、使用中のリビジョンを記録します。

## アラートインシデント

チェックが失敗すると、アラートインシデントが発生し、ルールと同じ方法でオンコール担当者に緊急通知が送られます。チェックのフォームの **アラート** で設定します。

| チェックの状態 | インシデント |
|---|---|
| **失敗** | 重大度 `error` のインシデントを発生させます。 |
| **劣化** | **状態悪化時にアラート** がオンの場合、重大度 `warning` のインシデントを発生させます。 |
| **不安定** | **不安定時にアラート** がオンの場合、重大度 `warning` のインシデントを発生させます。 |
| **成功** | インシデントを解決します。 |
| **結果なし** | **結果がない場合にアラート** がオンの場合、重大度 `warning` の別のインシデントを発生させます。デフォルトではオンです。結果を再び受信すると、そのインシデントを解決します。 |

- チェックの状態に対応するアクティブなインシデントは、チェックごとに最大1件です。チェックの状態が「失敗」「劣化」「不安定」の間で変わると、手動で重大度を設定していない限り、未解決のインシデントには[アラートパイプライン](/ja/pipelines/alert-events#重大度の変更)が決定した新しい重大度が適用されます。重大度が上がると、エスカレーションを最初からやり直します。確認済みのインシデントは、手動で解決するまでそのままです。
- 制限時間内にどのエージェントも引き受けなかった実行は、スキップとして記録します。そのロケーションの状態は変わりません。失敗と判定するための連続失敗回数と同じ回数だけ実行が連続でスキップされると、そのロケーションは結果が欠落した状態になります。結果が欠落したロケーションの数がロケーションポリシーの指定数に達すると、チェックは **結果なし** になります。チェックのページには、その状態、該当するロケーション、直近の実行をスキップした理由を表示します。結果なしのインシデントには `synthetic.state` = `no_data` と `alert.condition` = `no_data` が付き、チェックの状態に対応するインシデントと同時に存在できます。手動で解決した場合は、結果を再び受信するまで同じインシデントは発生しません。
- チェックを一時停止またはアーカイブすると、進行中および確認済みのインシデントを解決します。それらを解決する後続の実行がないためです。
- チェックの **エスカレーションポリシー** に従って、オンコール担当者に緊急通知を送ります。**ルーティング済み** の場合、[アラートルーティング](/ja/alerting/routing)がチームとエスカレーションポリシーを選択します。**エスカレーションポリシーなし** の場合、緊急通知は送信しませんが、通知ポリシーに従ってインシデントを通知します。
- インシデントのタイトルにはチェック名を使用します。通知ポリシーでルーティングできるように、`alert.source` = `synthetic`、`synthetic.kind`、`synthetic.state` のラベルを付けます。チェックにタグやチームが設定されている場合は、それぞれ `synthetic.tags` や `team_id` も付けます。インシデントの詳細からチェックに戻れます。
- 通知のタイトルには、`ERROR · Checkout API` のように重大度とチェック名を表示します。本文には `Synthetic check Checkout API is failing.` と表示します。結果なしの場合、通知のタイトルは `NO DATA · Checkout API` となり、本文には該当するロケーションと理由をワークスペースのデフォルト言語で表示します。例：`Synthetic check Checkout API has no results from Frankfurt (3 missed in a row): no Agent was online there.`
- 判定に使うのは、連続失敗、復旧、ロケーションポリシーに基づくチェック全体の状態だけです。個々のロケーションの状態ではインシデントは発生しません。

## 障害をステータスページに公開する

ステータスページの自動化ルールでは、ソースに **外形監視モニター** を使用できます。モニターを選択し、状態遷移と重大度の条件を指定し、影響をコンポーネントに割り当てます。公開方法として手動承認または自動公開を選択します。[ステータスページ](/ja/status-pages#公開の自動化)を参照してください。
