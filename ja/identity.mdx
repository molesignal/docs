MoleSignal は、ロール名の比較ではなく、権限キーに基づいて操作を認可します。ユーザーは複数の組織に所属でき、組織ごとに異なる権限を持つことができます。現在のワークスペースへのアクセスを管理するには、メニューから **ID とアクセス**を開きます。

| グループ | セクション | ガイド |
|---|---|---|
| メンバー | **ユーザー**、**招待**、**承認** | [メンバー](/ja/identity/members) |
| 組織 | **組織**、**チーム** | [組織とチーム](/ja/identity/teams) |
| 権限と制限 | **ロール**、**権限ポリシー**、**アクセス権の付与** | [ロール、ポリシー、アクセス権の付与](/ja/identity/roles) |
| 認証とアクセス | **API トークン**、**サービスアカウント** | [API トークンとサービスアカウント](/ja/identity/tokens) |
| | **SSOプロバイダー**、**メールドメイン** | [シングルサインオン](/ja/identity/sso) |

## 認可の仕組み

認証済みのリクエストに対して、MoleSignal は次の項目を特定します。

1. サブジェクト：ユーザー、サービスアカウント、または API トークン
2. アクティブな組織、または保護されたプラットフォームスコープ
3. サブジェクトに割り当てられたロールと付与されたアクセス権
4. リソース間の関連付けと、承諾済みの組織間アクセス権の付与
5. ルートと対象リソースが必要とする権限

権限カタログ、組み込みロール、権限ポリシーは PostgreSQL に保存されます。 `GET /api/v1/iam/capabilities` は有効な権限を返します。Web アプリケーションはその権限を使ってナビゲーションを構成します。

<Warning>
  ページが表示されたり、ロール名が付いていたりしても、操作が認可されているとは限りません。サーバーは保護された操作ごとに、必要な権限とリソースの所有権を確認します。
</Warning>

## 権限のスコープ

組織の権限は、1 つのワークスペースに適用されます。例は次のとおりです。

- `org.preferences.read` と `org.preferences.manage`
- `org.members.read` と `org.members.update`
- `iam.roles.read`、`iam.roles.manage`、`iam.grants.read`、`iam.grants.manage`
- ストリーム、ダッシュボード、アラート、スケジュール、保存済みビュー、パイプライン、関数、レポート、監査、ログ検査、Mole Agent の権限

プラットフォームの権限は `sys.` で始まり、`_sys` 組織にのみ適用されます。これらの権限は、インスタンス内の組織、システムテレメトリ、トレースのデバッグ、プラットフォーム管理者、プラットフォーム設定へのアクセスを制御します。

## 組み込みロール

| ロール | 権限 |
|---|---|
| **オーナー** | カタログにあるすべての組織の権限を持ちます。プラットフォームの権限は持ちません。 |
| **管理者** | すべての組織の権限を持ちます。製品の各機能領域に加え、設定、メンバー、ロール、アクセス権の付与、トークン、監査、ステータスページ、合成モニタリング、サービスレベル、ポストモーテム、Mole Agent の管理も対象です。 |
| **エディター** | ストリーム、ダッシュボード、アラートとスケジュール、保存済みビュー、パイプライン、関数、レポート、APM と RUM の設定を閲覧・変更できます。Mole Agent の自動化とログ検査も実行できます。 |
| **閲覧者** | データ、ダッシュボード、アラートとスケジュール、保存済みビュー、パイプライン、関数、レポートを閲覧できます。Mole Agent とのチャットも利用できます。 |

[権限リファレンス](/ja/identity/roles#権限リファレンス)には、各権限と、その権限を持つ組み込みロールを記載しています。組み込みロールは編集できません。アップグレードで追加された権限は、起動時にオーナーロールに付与されます。

担当範囲を限定するには、[カスタムロール](/ja/identity/roles#ロール)を作成します。

## プラットフォームへのアクセス

インスタンスに設定した `root` アカウントは、スーパー管理者です。ロールは不要です。どの組織でもその組織の権限を持ち、`_sys` ではプラットフォームの権限を持ちますが、どの組織のオーナーにもなりません。このアカウントの API トークンは、それぞれが所属する組織の権限を持ちますが、プラットフォームの権限は一切持ちません。

それ以外のアカウントがプラットフォームにアクセスするには、アクセス権の付与が必要です。`_sys` の **ID とアクセス**には、専用の **ロール**、**権限ポリシー**、**アクセス権の付与**があり、`sys.administrators.read` と `sys.administrators.manage` が必要です。組み込みのプラットフォームロールは 2 つあります。

| ロール | 権限 |
|---|---|
| `platform_admin` | プラットフォームのすべての権限を持ちます。 |
| `platform_viewer` | プラットフォームの読み取り専用権限をすべて持ちます。 |

メールアドレスでアカウントを検索し、アクセス権を付与します。アカウントが組織に所属している必要はありません。付与の対象は、プラットフォーム全体か、指定した 1 つの組織です。組織を指定すると、`sys.organizations.read`、`.update`、 `.disable`、`.delete` のみが、その組織に限って有効になります。プラットフォーム全体で保有していない権限は付与できません。付与を取り消すと、次のリクエストからアクセスできなくなります。

## ワークスペースをまたぐアクセス

アクセス権の付与により、ある組織のサブジェクトを別の組織のリソースに関連付けることができます。サーバーはその関連付けとリソースの権限の両方を確認します。アクセス権を付与しても、共有元の組織がサブジェクトのアクティブなワークスペースになることはありません。詳しくは、 [組織間でリソースを共有する](/ja/identity/roles#組織間でリソースを共有する)を参照してください。

ダッシュボードとレポートでは、[リソース共有](/ja/resource-sharing)も利用できます。公開共有では、組織のメンバー資格ではなく、権限を制限した共有セッションを付与します。

## プラットフォームの管理

`_sys` 組織は、各組織の IAM から分離されています。テナントセッションや `mspat-*` トークンでは、システムテレメトリやプラットフォーム管理者の一覧を取得できません。`_sys` で必要な `sys.*` 権限を持つセッションを使用してください。詳しくは、[管理の概要](/ja/administration)を参照してください。
