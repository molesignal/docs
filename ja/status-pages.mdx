ステータスページでは、稼働状況を顧客に伝える内容やタイミングを管理できます。**ステータスページ**を開いてページを作成し、用途別の7つのワークスペースで管理します。

## ワークスペース

| タブ | 用途 |
|---|---|
| **概要** | サマリー、コンポーネント、対応中のインシデント、今後のメンテナンスを確認します。 |
| **コンポーネント** | 顧客向けのサービスコンポーネントを作成、グループ化、並べ替え、非表示化、復元、更新します。 |
| **インシデント** | 予定外のイベントの下書きを作成し、公開、更新、監視、解決します。 |
| **メンテナンス** | 計画作業をスケジュールし、公開、開始、完了、またはキャンセルします。 |
| **履歴** | 終了したインシデントやメンテナンスを、概要で展開せずに検索やフィルタリングで絞り込みます。 |
| **購読者** | メール、Webhook、Slackの購読者と、インポート、購読確認、配信結果を管理します。 |
| **設定** | 全般の動作、ブランディング、ローカライズ、ドメイン、アクセス、自動化を設定します。 |

## ステータスページを作成する

**ステータスページを作成**を選択し、次の項目を設定します。

- 顧客に表示する名前と、全体で一意のスラッグ
- 1つ以上のインターフェース言語、デフォルト言語、IANAタイムゾーン
- 公開範囲（**公開**または**非公開**）
- 配信記録の保持期間、非公開ページのセッション有効期間、インシデント履歴の表示期間
- ロゴ、ブランドカラー、任意のカスタムドメイン

公開ページのインターフェースは英語と簡体字中国語に対応しています。コンポーネント名、インシデントのメッセージ、メンテナンスの更新内容は、チームが入力したとおりに表示されます。ページから送信するメールにもデフォルト言語を使用します。

デフォルトの公開アドレスは<code>/status/SLUG</code>です。

## コンポーネント

各コンポーネントには、名前、説明、表示順、公開範囲と、次のいずれかの顧客向けステータスがあります。

- **正常稼働**
- **パフォーマンス低下**
- **部分的な障害**
- **重大な障害**
- **メンテナンス**

管理対象のまま公開したくないコンポーネントは、非表示にします。非表示のコンポーネントは公開ページに表示せず、購読者への通知にも含めません。サービスカタログから外す場合は、アーカイブします。既存のイベント履歴はそのまま残ります。

公開ページには、各コンポーネントのステータスと過去90日間の履歴バーが表示されます。各履歴バーの下には、**90日前**、コンポーネントの稼働率、**今日**が表示されます。コンポーネントの説明は、名前の横にあるⓘのツールチップに表示されます。

### コンポーネントグループ

関連するコンポーネントを、フォルダーにファイルをまとめるようにグループ化します。**コンポーネントを追加**を選択し、種類を **グループ**に設定して、名前と説明を入力します。次に、グループに含める各コンポーネントの設定で、**グループ**から作成したグループを選択します。

- グループ自体にはステータスがありません。所属するコンポーネントのうち最も深刻なステータスを表示し、履歴バーには日ごとに最も深刻だったコンポーネントのステータスを表示します。
- 公開ページでは、グループをコンポーネント数とともに1行で表示します。グループを展開すると、各コンポーネントを確認できます。正常稼働していないコンポーネントがある場合は、グループを展開した状態で表示します。
- グループに含められるのはコンポーネントだけで、別のグループは含められません。インシデント、メンテナンス、購読、自動化ルールではコンポーネントを指定します。グループ自体は選択できません。
- **上に移動**と**下に移動**で、グループ内のコンポーネントや最上位の項目に並ぶグループの表示順を変更します。
- 所属するコンポーネントをすべてグループ外に移動するかアーカイブすると、グループもアーカイブされます。

### 依存関係

コンポーネントは、技術サービス、外形監視チェック、アラートルールに依存できます。コンポーネントの稼働状況は、依存関係から引き継いだステータスのうち最も深刻なものです。MoleSignalは、アラートインシデントや外形監視チェックの変化から数秒以内に稼働状況を算出し、変化がなくても1分ごとに算出します。コンポーネントの設定で、**依存関係**から依存先を追加します。

| 種類 | 対象 | 引き継ぐステータス |
|---|---|---|
| **技術サービス** | トレースやアラートに記録されるサービス名です。 | `service`、`service.name`、`service_name`のいずれかのラベルがサービス名を示すか、クエリ結果にそのサービスが含まれる未解決のアラートインシデントのうち、最も深刻なもののステータスです。名前の照合では大文字と小文字を区別しません。 |
| **外形監視チェック** | 外形監視チェックです。 | チェックの失敗中は**重大な障害**、性能が低下している間は**パフォーマンス低下**です。結果が不安定なチェック、未実行のチェック、一時停止中またはアーカイブ済みのチェックからは、ステータスを引き継ぎません。 |
| **アラートルール** | アラートルールです。 | ルールの未解決のアラートインシデントのうち、最も深刻なもののステータスです。 |

アラートインシデントは重要度に応じたステータスを引き継ぎます。**クリティカル**は重大な障害、**エラー**は部分的な障害、**警告**はパフォーマンス低下に対応します。**情報**はステータスに影響せず、ミュートしたインシデントは対象外です。依存関係ごとに**ステータスを引き継ぐ**を選ぶか、コンポーネントが影響を回避できる場合は **最大で性能低下**を選びます。コンポーネントには最大100件の依存関係を設定できます。グループ自体には設定できません。

コンポーネントに稼働状況を反映する方法は次のとおりです。

| モード | 動作 |
|---|---|
| **稼働状況に連動** | コンポーネントのステータスが稼働状況に連動します。**購読者に通知**で、変更を購読者に通知するかどうかを設定します。手動で設定したステータスは、稼働状況が再び変化するまで維持されます。 |
| **自動化ルールを使用** | 稼働状況の変化をステータスページの自動化ルールのトリガーにします。ルールに設定した遅延、承認条件、文面に従ってインシデントを公開します。 |

コンポーネントの設定には、最後に算出した稼働状況と、その判定の根拠となった依存関係が表示されます。

## インシデントのライフサイクル

インシデントの下書きを作成し、影響を受けるコンポーネントを選択して、影響度と顧客向けの初回更新を入力します。公開すると、インシデントが公開ページに表示され、該当する購読者に更新内容が送信されます。

<Steps>
  <Step title="調査中">
    症状を確認し、チームが調査中であることを伝えます。
  </Step>
  <Step title="原因特定済みまたは対応中">
    判明した原因、または実施中の復旧対応について説明します。
  </Step>
  <Step title="監視中">
    サービスが復旧し、チームが安定稼働を確認していることを伝えます。
  </Step>
  <Step title="解決済み">
    最終更新を公開します。MoleSignalはコンポーネントのステータスを元に戻し、 **履歴**にインシデント全体を1行で追加します。
  </Step>
</Steps>

公開した更新は、顧客向けの通知として変更できません。インシデントの続報を伝えるには、配信済みのメッセージを編集するのではなく、新しい更新を追加します。

### 次回の更新と通知

各更新では、次回の更新予定を案内できます。公開時に**次回の更新**で、15分以内、30分以内、 1時間以内、2時間以内、4時間以内、24時間以内、または**更新予定の案内なし**を選択します。公開ページでは、インシデントと進行中のイベントの告知に更新予定を表示します。メールとWebhookにも予定を含めます。イベントを終了する更新や、予定段階のメンテナンスでは、次回の更新を案内しません。APIでは、現在から1分後〜7日後の時刻をマイクロ秒単位で`next_update_at`に指定します。

**購読者に通知**で、更新を購読者に送信するかどうかを設定します。文面だけを修正する場合はオフにします。ページは更新されますが、通知は送信されません。ワークスペースのタイムラインでは、この更新に**購読者への通知なし**と表示します。コンポーネントのステータスを手動で変更する場合も、同じスイッチが表示されます。APIでは、`"notify": false`を送信します。

## メンテナンスのライフサイクル

公開用タイトル、開始時刻、影響を受けるコンポーネント、顧客向けのお知らせを指定して、計画メンテナンスを作成します。メンテナンスには予定開始時刻がありますが、予定終了時刻はありません。見込みの所要時間は顧客向けのお知らせに記載してください。ステータスを **スケジュール実行** として公開し、**完了** または **キャンセル済み** にして終了します。終了したメンテナンスは、**履歴** に1行で表示されます。

スケジュール済みのメンテナンスは、予定開始時刻に基づいて自動で処理されます。メンテナンスごとに2つのオプションがあり、どちらもデフォルトでオンです。

| オプション | API フィールド | デフォルト | 動作 |
|---|---|---|---|
| 自動開始 | `auto_start` | `true` | 予定開始時刻になると、メンテナンスが **対応中** になり、ページのデフォルト言語でお知らせを公開します。他のお知らせと同様に、購読者に通知します。 |
| リマインダー | `reminder_minutes` | `60` | 予定開始時刻の指定分数前に、購読者にリマインダーを送信します。リマインダーはタイムラインに追加しません。`0` を指定すると送信しません。最大で10080分前に送信できます。 |

自動開始をオフにしている場合は、作業開始時にメンテナンスのステータスを **対応中** に変更します。

リマインダーの送信予定時刻を過ぎてからメンテナンスを告知したり、予定を変更したりした場合は、購読者に通知した直後なので、リマインダーは送信しません。予定を変更すると、予定開始時刻に合わせてリマインダーの送信時刻も変わります。編集時にどちらのオプションも指定しなければ、両方とも現在の設定を維持します。MoleSignal は予定開始時刻を約30秒ごとに確認します。

## ポストモーテム

公開したインシデントには、Markdown でポストモーテムを1件作成できます。何が起きたか、その原因、その結果として何を変更するかを記載します。**インシデント** または **履歴** から対象のインシデントを開き、 **ポストモーテム** に記入します。**プレビュー** では、読者に表示される内容を確認できます。

| 操作 | 権限 | 動作 |
|---|---|---|
| **下書きを保存** | <code>status_pages.events.manage</code> | 本文を非公開のまま保存します。インシデントの対応中でも下書きを作成できます。 |
| **ポストモーテムを公開** | <code>status_pages.events.publish</code> | インシデントの解決後に利用できます。ポストモーテムはインシデントページのお知らせの下に表示され、公開履歴の該当行には **ポストモーテム** と表示されます。**購読者に通知** がオンの場合は、購読者にポストモーテムを送信します。 |
| **改訂版を公開** | <code>status_pages.events.publish</code> | 公開済みの本文を差し替え、改訂日時を記録します。改訂時は **購読者に通知** がデフォルトでオフです。 |
| **下書きに戻す** | <code>status_pages.events.publish</code> | ポストモーテムを公開ページから取り下げます。 |
| **下書きを削除** | <code>status_pages.events.manage</code> | 非公開のポストモーテムを削除します。 |

ポストモーテムは最大20,000文字です。メールと Webhook では、記入した Markdown の本文をそのまま送信します。

## 履歴

履歴には、終了したイベントのみが表示されます。対象は、解決済みのインシデントと、完了またはキャンセル済みのメンテナンスです。各行は1件のイベントを表し、種別、タイトル、終了時のステータス、影響を受けるコンポーネント、日付を表示します。検索や、種別、ステータス、コンポーネント、日付のフィルターとページ切り替えを利用できます。タイトルを選択すると、テーブルを展開せずに、イベントのタイムラインとお知らせを表示できます。

保持期間の設定では、公開インシデントアーカイブで過去何日分を表示するかを、1〜365日の範囲で指定します。この設定によって、概要ページが無制限のイベントフィードになることはありません。

## 購読者と配信

公開ページの訪問者は、**購読**を選択して、メールアドレス、Webhook、または Slack チャンネルを登録できます。どの配信先も、確認を経てから有効になります。管理画面では、確認待ち、有効、購読解除済みのレコードを分けて表示し、購読者ごとに受け取る通知の対象を確認できます。

同じダイアログの **RSS フィード**には、ページのフィードが 2 つの形式で用意されており、確認手続きなしでフィードリーダーに追加できます。RSS 2.0 は `/api/v1/public/status-pages/<slug>/feed.rss`、Atom 1.0 は `/api/v1/public/status-pages/<slug>/feed.atom` です。どちらにも、ページのインシデントとメンテナンス期間が最新の 100 件まで含まれ、各項目には最新の更新が表示されます。非公開ページにはフィードがありません。

複数のコンポーネントがあるページでは、訪問者は **ページ全体**または **一部のコンポーネント**を選択できます。一部のコンポーネントを購読すると、選択したコンポーネントのいずれかを対象とする更新のみを受け取ります。コンポーネントグループは、所属するコンポーネントの上に見出しとして表示されます。各メールの末尾には、購読の管理と解除のリンクがあります。管理リンクを開くと、ページに **購読の管理**が表示され、対象のコンポーネントを変更したり、購読を解除したりできます。すでに購読が有効なアドレスを登録すると、新しい確認メールの代わりに **更新通知の管理**メールを送信します。

### Slack

| 方法 | 手順 |
|---|---|
| Incoming Webhook | 配信先に **Slack** を選択し、対象の Slack チャンネルの Incoming Webhook URL（`https://hooks.slack.com/...`）を貼り付けて、**確認リクエストを送信**を選択します。確認メッセージがチャンネルに投稿されます。 |
| **Slackに追加** | ページの **設定 → Slack** で Slack アプリを指定すると表示されます。訪問者が Slack でチャンネルを選択すると、ページに戻ります。そのチャンネルの購読がすぐに開始され、ウェルカムメッセージが届きます。非公開ページでは利用できません。 |

Slack メッセージには、件名を使ったヘッダー、更新の本文、ページを開くボタンと購読を管理するボタンが含まれます。

**Slackに追加**を利用できるようにするには、次の手順を実行します。

1. Slack で `incoming-webhook` スコープを持つアプリを作成します。**OAuth & Permissions → Redirect URLs** に、ページの **設定 → Slack** に表示されるリダイレクト URL `<http.external_url>/api/v1/public/slack/callback` を追加します。`http.external_url` には `https` のアドレスを指定してください。
2. **設定 → 通知 → コネクター**で、アプリのクライアント ID とクライアントシークレットを使って **Slack アプリ**コネクターを作成します。シークレットは暗号化してコネクターに保存します。 [通知チャンネル](/ja/notification-channels#slack-アプリ)を参照してください。
3. ページの **設定 → Slack** でコネクターを選択して保存します。

同じ組織のページで、1 つのコネクターを共有できます。ページで指定しているコネクターは削除できません。コネクターを無効にしている間は、ページに **Slackに追加**が表示されません。**オフ**を選択した場合も表示されなくなります。どちらの場合も、追加済みのチャンネルには引き続き更新が届きます。

### 購読者をインポート

**購読者 → 購読者をインポート**を使って、別のステータスページのメール購読者を移行できます。 CSV ファイルを選択するか、内容を貼り付けます。

- 1 行目をヘッダーにする場合、`email` 列と `components` 列はどちらが先でも構いません。ヘッダーがない場合は、1 列目にメールアドレス、2 列目にコンポーネント名を指定します。
- コンポーネントは名前で指定し、`;` で区切ります。グループ名を指定すると、そのグループ内のコンポーネントが対象になります。セルを空欄にすると、そのメールアドレスはページ全体を購読します。
- 1 回のインポートの上限は、メールアドレス 10,000 件かつ 2 MB です。

| 購読開始方法 | 動作 |
|---|---|
| **すぐに購読開始** | 移行元のページで確認済みのアドレスに使用します。購読はすぐに有効になり、メールは送信しません。 |
| **確認後に購読開始** | 各アドレスに確認メールを送信し、確認が完了するまで確認待ちのままにします。メール配信の設定が必要です。 |

**ファイルを確認**を選択すると、データを変更せずにインポート結果を確認できます。読み込んだ行数、インポート対象のアドレス、購読済みのアドレス、過去に購読を解除したためスキップするアドレスを表示します。問題がある行は、行番号と理由を表示します。理由には、アドレスがない、メールアドレスの形式が無効、ファイル内の先行行とアドレスが重複、ページに存在しないコンポーネントが指定されている、などがあります。

メール購読者には、各更新をページのデフォルト言語で記載したプレーンテキストのメールが届きます。メール内のステータス名は、**パフォーマンス低下**など、ページのラベルと一致します。

| メール | 件名 | 本文 |
|---|---|---|
| 確認 | `Confirm updates from <page name>` | 確認リンクと購読解除リンクです。 |
| コンポーネントのステータス変更 | `<page name>: <component> · <status>` | コンポーネント、新しいステータス、ページの URL です。 |
| インシデントの更新 | `<page name>: <title> · <status>` | タイトル、ステータス、顧客向けの更新内容、ページの URL です。 |
| メンテナンスの更新 | `<page name>: <title> · <status>` | インシデントの更新と同じ項目に加え、開始予定時刻を **予定日時**として記載します。 |
| メンテナンスのリマインダー | `<page name>: <title> · Reminder` | タイトル、**予定日時**に記載した開始予定時刻、ページの URL です。 |
| 購読の管理 | `Manage your updates from <page name>` | 購読を管理するリンクです。 |
| ポストモーテム | `<page name>: Postmortem · <title>` | Markdown 形式のポストモーテムとインシデントの URL です。 |

次回の更新時刻を予告する場合は、**次回の更新期限**と、ページのタイムゾーンで表した時刻を追記します。確認メールを除くすべてのメールの末尾に、購読の管理と解除のリンクを記載します。

**予定日時**にはページのタイムゾーンを使用し、UTC オフセットも明記します。例： `2026-05-25 12:00 UTC+02:00 (Europe/Berlin)`。

Webhook の購読先には、更新ごとに JSON リクエストが届きます。リクエスト形式、ペイロードのフィールド、再試行スケジュールについては、 [ステータスページの Webhook 購読](/ja/status-pages/webhooks)を参照してください。

インシデントやメンテナンスの更新を公開するたびに、対象の購読者への配信タスクを上限付きで作成します。**購読者**では、配信の試行、成功、直近のエラー、再試行の状態を確認できます。配信履歴の保持期間は 30、60、90、180、365 日から選択できます。

## 非公開ページへのアクセス

非公開ページでは、メールアドレスやメールドメインの許可リストを設定できます。許可リストの対象となる訪問者は、 1 回限り有効なマジックリンクをリクエストし、1 日、7 日、または 30 日間有効なステータスページのセッションを取得します。リンクを送信するメールにはページのデフォルト言語を使用し、リンクは 15 分間有効です。管理者は、有効なセッションを即座に取り消せます。アクセス制限は、訪問者向けのページ、アーカイブ、イベント詳細、購読手続きに適用されます。

## カスタムドメインと TLS

ドメインを追加する前に、<code>http.external_url</code> に実際に公開する MoleSignal の URL を設定してください。ドメインパネルに、所有権の確認とルーティングのために作成する DNS レコードが表示されます。

ドメインの状態は、**DNS設定待ち**、**確認中**、**検証済み**、**TLS設定中**、 **有効**の順に進みます。**失敗**または **劣化**の場合は、対処に必要な理由と再試行の操作が表示されます。

MoleSignal が自動管理する証明書を使ってカスタムホスト名でページを配信するには、
<code>http.tls</code> を有効にして、アカウントのメールアドレスを設定します。

```toml
[http]
external_url = "https://molesignal.example.com"

[http.tls]
enabled = true
account_email = "ops@example.com"
```

外部ロードバランサーで TLS を終端する場合は、公開 URL と DNS の参照先を正しく設定し、そのロードバランサーで証明書を管理します。

## 公開の自動化

運用イベントを顧客向けのお知らせに変換するには、**設定 → 自動化**を開きます。

1. ソースとして**アラートインシデント**、**外形監視チェック**、または**コンポーネントの依存関係**を選択します。
2. リソース、最小重大度またはモニターの状態遷移、必須ラベルを選択します。
3. 一時的な障害で顧客向けのお知らせが作成されないように、遅延を設定します。
4. イベントの影響と、影響を受けるステータスページのコンポーネントをマッピングします。**コンポーネントの依存関係**ルールにコンポーネントを指定しない場合、依存関係が変化したコンポーネントがその変化を自動化ルールに渡すと、そのコンポーネントにイベントを公開します。テンプレートでは、コンポーネント名を `{{labels.component_name}}` で、現在と変更前の依存関係のステータスをそれぞれ `{{labels.dependency_status}}` と `{{labels.previous_dependency_status}}` で参照できます。
5. **手動承認**または**自動公開**を選択し、メッセージテンプレートを定義します。
6. ルールを有効にする前に、シミュレーターでテストします。

ルールは並び順に評価し、すべての条件を満たす最初のルールがイベントを処理します。相関キーにより、ソースで後から発生する状態遷移を同じインシデントに関連付けます。手動モードでは、権限を持つユーザーが承認、却下、編集できる公開候補を作成します。自動モードでは、生成したイベントを直接公開します。**すべての自動化を一時停止**すると、公開済みのイベントには変更を加えず、新たなルールの照合を停止します。

<Note>
対応担当者が管理する検知にはアラートインシデントを、顧客が利用する経路を直接確認するには外形監視モニターを使用します。どちらのソースも同じコンポーネントモデルを更新できますが、承認と遅延のポリシーはルールごとに管理します。
</Note>
