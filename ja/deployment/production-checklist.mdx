Compose サンドボックスとサンプルの `conf/config.toml` は、すぐに使い始められるように設定されています。デプロイ環境で実データを扱う前に、このページの手順を実施してください。

## サンドボックスのデフォルト設定を置き換える

| 項目 | サンドボックスのデフォルト | 本番環境 |
|---|---|---|
| ルートアカウント | `admin@example.com`、パスワードは `admin` | 初回起動前に、`[auth]` に固有のメールアドレスと強力なパスワードを設定します。 |
| `MS_CIPHER_KEY` | 未設定（すべてゼロの開発用キーを使用）、または Compose ファイル内の固定の開発用キー | ランダムな 32 バイトのキーをシークレットマネージャーに保管します。 |
| PostgreSQL の認証情報 | `molesignal` / `molesignal` | 専用のデータベースとユーザーを用意し、生成したパスワードを設定します。 |
| オブジェクトストレージの認証情報 | `rustfsadmin` / `rustfsadmin` | 対象バケットにのみアクセスできる専用のアクセスキーを使用します。 |
| オブジェクトストレージのバックエンド | コンテナボリューム上の RustFS | 永続ストレージを備えた `s3`、`azure`、または `gcs` を使用します。 |
| `[http].external_url` | 空 | 公開 HTTPS アドレスを設定します。 |
| TLS | 無効 | TLS を終端するプロキシまたは `[http.tls]` を使用します。 |
| イメージタグ | `latest` | `26.1.0.0` など、特定のバージョンタグに固定します。 |

## チェックリスト

<Steps>
  <Step title="PostgreSQL とオブジェクトストレージを用意する">
    自動バックアップを有効にした PostgreSQL 17 を使用します。MoleSignal 専用のデータベースとユーザーを作成します。

    `[meta_database].max_connections` にノード数を掛けた値が、PostgreSQL の `max_connections` の上限を下回るように設定します。

    ノードと同じリージョンにプライベートバケットを作成します。オブジェクトの有効期限を設定するライフサイクルルールは追加しないでください。MoleSignal が保持期間を適用し、オブジェクトを削除します。
  </Step>
  <Step title="暗号化キーを生成して保管する">
    `MS_CIPHER_KEY` は、MoleSignal が PostgreSQL に保存するシークレットのルートキーです。対象には、API トークン、共有リンク、リモートクラスタートークン、通知コネクターの認証情報、パイプラインコネクターの認証情報、Mole Agent のプロバイダーキー、外形監視のシークレット、組織フィールドのキーが含まれます。キーは一度だけ生成します。

    ```bash
    openssl rand -base64 32
    ```

    値をシークレットマネージャーに保管し、すべてのノードに同じ値を設定します。キーはデータベースとは別にバックアップします。キーなしでデータベースを復元すると、これらのシークレットを読み取れません。

    <Warning>
      キーをそのまま上書きしないでください。古いキーで暗号化したデータを読み取れなくなります。キーをローテーションするには、すべての書き込みを停止し、新しい値を `MS_CIPHER_KEY` としてエクスポートしてから、古いキーを指定してオフラインコマンドを実行します。

      ```bash
      molesignal --config /etc/molesignal/config.toml rewrap-kek --old-key "<old key, base64>"
      ```

      コマンドは対象の列をすべて再暗号化し、テーブルごとの行数を出力します。古いキーを廃止する前に、行数を確認してください。
    </Warning>

    `MS_CIPHER_KEY` を設定せずに起動した環境では、すべてゼロの開発用キーを使用しています。本番用のキーに移行するには、`--old-key` に `AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA=` を指定します。
  </Step>
  <Step title="ルートアカウントを保護する">
    MoleSignal は、空のデータベースで初めて起動するときに、`[auth].root_email` と `[auth].root_password` を使ってルートアカウントを作成します。初回起動前に両方を設定します。後から `root_password` を変更しても、既存のアカウントのパスワードは変わりません。

    パスワードのリセットと **アカウント設定 → セキュリティとサインイン → パスワードを変更** はメールを使用します。メールの送信には `[notify.smtp]` と `[http].external_url` の両方が必要です。未設定の場合、メールは送信されません。これらの機能を使う前に、両方を設定してください。

    MoleSignal は起動するたびに、`root_email` に該当するアカウントをプラットフォーム管理者に設定します。`root_email` には常に既存ユーザーのメールアドレスを指定してください。
  </Step>
  <Step title="シークレットをリポジトリに含めない">
    データベースの DSN、オブジェクトストレージのキー、`MS_CIPHER_KEY` は、環境変数またはシークレットマネージャー経由で渡します。`MS_META_DATABASE_DSN`、`MS_OBJECT_STORE_ACCESS_KEY`、`MS_OBJECT_STORE_SECRET_KEY` を使用します。`config.toml` の対応するキーは空のままにします。

    必要に応じて、`MS_AUTH_JWT_SECRET_OVERRIDE` で JWT 署名用シークレットを固定します。指定しない場合、MoleSignal は初回起動時に PostgreSQL 内にシークレットを生成します。ローテーションには `POST /api/v1/auth/jwt/rotate` を使用します。この操作には `sys.signing_keys.rotate` 権限が必要です。旧シークレットで署名したトークンは、ローテーション後も 24 時間有効です。
  </Step>
  <Step title="必要なポートを公開する">
    | ポート | 公開範囲 |
    |---|---|
    | `5080` | TLS で保護して公開します。 |
    | `4317` | TLS を終端するプロキシ経由でのみ公開します。 |
    | `5082` | プライベートネットワーク内に限定します。このポートでは、ノード間の通信に認証を使用しません。 |
    | `5083` | SQL クライアントが接続する場合に、必要に応じて TLS で保護して公開します。 |
    | `5084`, `5085` | プローブエージェントをノードの外部で実行する場合にのみ公開します。 |

    `[http].external_url` に公開アドレスを設定します。セットアップ用スニペット、パスワードリセットメール、ステータスページのドメイン、[パスキー](/ja/identity/mfa#インスタンスの要件) がこのアドレスを使用します。
  </Step>
  <Step title="TLS を終端してプロキシを設定する">
    リバースプロキシで TLS を終端するか、`[http.tls]` を有効にして ACME 証明書を自動取得します。

    ネイティブ JSON の取り込みは最大 16 MiB のリクエストボディを受け付けるため、プロキシのリクエストボディの上限を 16 MiB 以上に設定します。`/api/v1/query/stream` ではレスポンスのバッファリングを無効にし、長時間の読み取りを許可します。プロジェクトの nginx 設定例では、このパスのタイムアウトを 600 秒に設定しています。

    `/metrics` へのアクセスは内部からのリクエストに限定します。取り込み用のパス `/api/v1/_bulk`、`/api/v1/_kinesis_firehose`、`/api/v1/_cloudflare`、`/api/v1/_heroku` は、送信元が必要とする場合にのみ公開します。
  </Step>
  <Step title="ノードの障害に備える">
    MoleSignal は先行書き込みログ（WAL）をオブジェクトストレージに保存し、WAL オブジェクトの保存が完了してから書き込みの成功を応答します。そのため、ノードに永続ボリュームは不要です。ノードが停止すると、別の取り込みノードが `[wal].lease_secs`（デフォルトは 15 秒）に最大 `[wal].takeover_interval_secs` を加えた時間が経過した後に、その WAL を引き継ぎます。それまでは、停止したノードが書き込みの成功を応答したものの、まだフラッシュしていなかったレコードをクエリできません。単一ノードが再起動した場合は、そのノード自身が以前の WAL を引き継ぎます。書き込みごとにオブジェクトの書き込みを 1 回待つため、オブジェクトストレージのレイテンシーが各書き込みのレイテンシーに加わります。[耐久性と引き継ぎ](/ja/architecture#データの耐久性と引き継ぎ)を参照してください。

    シャットダウン時は、処理中のリクエストを完了できるように時間を確保します。オーケストレーターの終了猶予期間は、`[node].drain_timeout_secs`（デフォルトは 30 秒）より長く設定します。
  </Step>
  <Step title="保持期間を設定する">
    デフォルトの保持期間は 30 日です。`_sys` 組織の **設定 → データ保持** で設定します。MoleSignal は、個別の保持期間を設定していないすべてのストリームから、この期間を過ぎたデータを削除します。データが蓄積する前に、デフォルトの値を引き上げるか、ストリームごとに保持期間を設定します。[ストリーム](/ja/streams)を参照してください。
  </Step>
  <Step title="アラートとコンパクションのロールのインスタンス数を決める">
    `alert` ロールと `compactor` ロールは、複数のインスタンスで処理を分担できます。`alert` ノードはルール、レポート、パイプライン、コネクター単位で処理を分担し、1 回だけ実行する必要があるジョブは 1 台のプライマリノードが実行します。`compactor` ノードはストリームと組織単位で処理を分担します。各ノードに固有の `[node].id` を設定し、ノード間で時刻を同期します。`standalone` ノードには両方のロールが含まれています。ロールを分離する必要がない限り、`standalone` を使用します。分離する前に、[ロールベースのデプロイ](/ja/deployment/role-based)を参照してください。
  </Step>
  <Step title="デプロイ環境を監視する">
    Prometheus で `/metrics` をスクレイプします。公開エンドポイントの `GET /api/v1/healthz` をプローブします。このエンドポイントは、オブジェクトストレージに接続できない場合に `503` を返します。コンテナイメージは、このチェックを `HEALTHCHECK` として実行します。

    サービス自身のメトリクス、トレース、プロファイルを記録するため、`[telemetry.self_collect]` は有効のままにします。これらのメトリクスに対してアラートルールを作成します。[セルフオブザーバビリティ](/ja/self-observability)を参照してください。
  </Step>
  <Step title="バックアップとアップグレードを計画する">
    [バックアップと復元](/ja/backup-restore)の手順に従って、PostgreSQL、オブジェクトストレージ、暗号化キーをバックアップします。実際に復元が必要になる前に、復元手順をリハーサルしてください。初めてバージョンを変更する前に、[アップグレード](/ja/upgrade)を参照してください。
  </Step>
</Steps>

## 本番公開前の確認

- 公開アドレスに対する `GET /api/v1/healthz` が `200` を返します。
- 起動ログに `object_store_credentials_source` が記録され、`MS_CIPHER_KEY missing` は出力されません。
- サービスアカウントトークンで送信したテストレコードがクエリ結果に表示されます。
- デフォルトの認証情報（ユーザー名 `admin@example.com`、パスワード `admin`）でのサインインは拒否されます。
- 最新の PostgreSQL バックアップを一時データベースに正常に復元できます。
