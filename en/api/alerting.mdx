Three rule kinds, multi-step escalation, and PagerDuty-style incidents. See [Alerting](/en/alerting)
for the guide.

## Rules

```http
GET  /api/v1/alerts/rules        # list
POST /api/v1/alerts/rules        # create
PUT  /api/v1/alerts/rules/{id}   # update
DELETE /api/v1/alerts/rules/{id} # delete
```

A rule's `kind` is `scheduled`, `realtime`, or `anomaly`.

<Note>
  Changing a rule's threshold resets its consecutive-breach counter.
</Note>

<RequestExample>
```json POST body
{
  "name": "High error rate",
  "kind": "scheduled",
  "stream": "app",
  "statement": "SELECT count(*) AS c FROM app WHERE level = 'error'",
  "condition": { "op": ">", "value": 100 },
  "interval_secs": 60,
  "escalation_id": "esc_2abc..."
}
```
</RequestExample>

## Escalation policies

```http
POST /api/v1/alerts/escalations
```

A multi-step policy: each step has targets, an `ack_timeout`, and repeat behavior. Supports on-call
rotations (timezone-aware) and overrides.

## Notification channels

```http
POST /api/v1/alerts/channels
```

Channels deliver over Slack, webhook, or email, with template variables.

## Incidents

```http
GET  /api/v1/alerts/incidents              # list
POST /api/v1/alerts/incidents/{id}/ack     # acknowledge
POST /api/v1/alerts/incidents/{id}/resolve # resolve
```

Incidents carry `step`, `acknowledged_at`, and `resolved_at`, mirroring a PagerDuty incident
lifecycle.
