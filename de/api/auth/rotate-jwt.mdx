Beide Routen erfordern eine Sitzung auf Systemebene mit `sys.signing_keys.rotate`. Bei einer Sitzung auf Organisationsebene oder bei Verwendung eines API-Tokens geben die Routen `403` zurück. Wechseln Sie mit [Arbeitsbereich auswählen](/de/api/auth/select-organization) für die Sitzung zur Organisation `_sys`.

## Signaturschlüssel auflisten

```http
GET /api/v1/auth/jwt/secrets
```

Gibt die Metadaten der Signaturschlüssel zurück. Die Route gibt nie die Rohbytes der Schlüssel zurück.

<ResponseExample>
```json 200
[
  {
    "id": "3JtcPZ3AZJFyvBvSkJUia0N7wqo",
    "isPrimary": true,
    "createdAt": 1790000000000000,
    "retiredAt": null
  }
]
```
</ResponseExample>

## Signaturschlüssel rotieren

```http
POST /api/v1/auth/jwt/rotate
```

Erstellt einen neuen Primärschlüssel und setzt den bisherigen außer Betrieb. Das System signiert neue Tokens mit dem neuen Schlüssel. Mit dem außer Betrieb gesetzten Schlüssel signierte Tokens bleiben ab der Außerbetriebnahme 24 Stunden lang gültig.

Kein Knoten muss neu starten. Jeder Knoten akzeptiert bereits bei der ersten Anfrage Sitzungen, die mit dem neuen Schlüssel signiert sind, und signiert innerhalb von etwa 10 Sekunden selbst damit. Die Knoten verwenden den außer Betrieb gesetzten Schlüssel noch 5 Minuten über die 24 Stunden hinaus zur Prüfung. Das gleicht die Verzögerung und Zeitabweichungen zwischen den Knoten aus.

<ResponseExample>
```json 200
{
  "newKid": "<new-key-id>",
  "retiredKid": "<previous-key-id>",
  "activeCount": 2
}
```
</ResponseExample>

`activeCount` gibt an, wie viele Schlüssel das System derzeit zur Prüfung von Tokens verwendet. Ein Deployment, das den Signaturschlüssel mit `MS_AUTH_JWT_SECRET_OVERRIDE` fest vorgibt, folgt einer eigenen Rotationsrichtlinie. Siehe [Sicherheit und Mandantenfähigkeit](/de/security#jwt-signaturschlüssel).
