| Vorgang | Endpunkt | Berechtigung |
|---|---|---|
| Auflisten | `GET /api/v1/scheduled_pipelines` | `pipelines.read` |
| Erstellen | `POST /api/v1/scheduled_pipelines` | `pipelines.create` und `audit.read`, wenn die Pipeline `_audit` liest |
| Abrufen | `GET /api/v1/scheduled_pipelines/{id}` | `pipelines.read` |
| Aktualisieren | `PUT /api/v1/scheduled_pipelines/{id}` | `pipelines.edit` für Konfigurationsänderungen, zusätzlich `audit.read`, wenn die Pipeline `_audit` liest, und `pipelines.pause` bei einer Änderung von `enabled` |
| Löschen | `DELETE /api/v1/scheduled_pipelines/{id}` | `pipelines.delete` |
| Ausführungsverlauf | `GET /api/v1/scheduled_pipelines/{id}/runs` | `pipelines.read` |
| Heutige Limits | `GET /api/v1/scheduled_pipelines/{id}/limits` | `pipelines.read` |
| Backfill | `POST /api/v1/scheduled_pipelines/{id}/backfill` | `pipelines.run` und `audit.read`, wenn die Pipeline `_audit` liest |

## Auflisten

Die Liste enthält alle Pipelines mit dem Status der jeweils letzten Ausführung und einer Zusammenfassung der letzten 24 Stunden:

<ResponseExample>
```json 200
[
  {
    "id": "3KBHcb6imgQq7FXBsROGTIRHOyg",
    "name": "normalize-app",
    "sourceStream": "app_raw",
    "targetStream": "app",
    "functionSteps": { "mode": "scheduled", "signalType": "logs", "sources": ["app_raw", "nginx_raw"], "steps": [ ... ] },
    "cron": "every:5m",
    "lookbackSecs": 300,
    "enabled": true,
    "lastRunAt": 1790000000000000,
    "readUntil": { "appRaw": 1789999940000000, "nginxRaw": 1789999940000000 },
    "retry": null,
    "alertRecord": null,
    "auditReaderId": null,
    "auditReader": null,
    "createdAt": 1789900000000000,
    "updatedAt": 1789900000000000,
    "lastRunState": "succeeded",
    "lastRunStartedAt": 1790000000000000,
    "lastRunFinishedAt": 1790000000250000,
    "lastRunScannedRows": 1200,
    "lastRunError": null,
    "runs24h": 288,
    "succeededRuns24h": 288,
    "failedRuns24h": 0
  }
]
```
</ResponseExample>

Jeder Eintrag enthält die Felder aus [Abrufen](#abrufen), die Angaben zur letzten Ausführung in `lastRunState`, `lastRunStartedAt`, `lastRunFinishedAt`, `lastRunScannedRows` (Anzahl der gelesenen Ereignisse) und `lastRunError` sowie die Anzahl der Ausführungen in den letzten 24 Stunden.

## Abrufen

```http
GET /api/v1/scheduled_pipelines/{id}
```

Gibt die Pipeline mit der Leseposition jeder Quelle und dem geplanten Wiederholungsversuch zurück:

<ResponseExample>
```json 200
{
  "id": "3KBHcb6imgQq7FXBsROGTIRHOyg",
  "name": "normalize-app",
  "sourceStream": "app_raw",
  "targetStream": "app",
  "functionSteps": { "mode": "scheduled", "signalType": "logs", "sources": ["app_raw", "nginx_raw"], "steps": [ ... ] },
  "cron": "every:5m",
  "lookbackSecs": 300,
  "enabled": true,
  "lastRunAt": 1790000000000000,
  "readUntil": { "appRaw": 1789999940000000, "nginxRaw": 1789999640000000 },
  "retry": {
    "source": "nginx_raw",
    "attempt": 2,
    "nextAt": 1790000030000000,
    "error": "read: <reason>"
  },
  "alertRecord": null,
  "auditReaderId": null,
  "auditReader": null,
  "createdAt": 1789900000000000,
  "updatedAt": 1789900000000000
}
```
</ResponseExample>

| Feld | Hinweise |
|---|---|
| `readUntil` | Leseposition jeder Quelle in Mikrosekunden. Die Pipeline hat die Ereignisse der Quelle vor dieser Position bereits verarbeitet. Für eine Quelle, aus der die Pipeline noch nicht gelesen hat, fehlt der Eintrag. |
| `retry` | Frühester geplanter Wiederholungsversuch für ein fehlgeschlagenes Zeitfenster oder `null`. `source` gibt die Quelle an, `attempt` die Nummer des anstehenden Versuchs, `nextAt` den geplanten Zeitpunkt und `error` den Grund für das Scheitern des letzten Versuchs. |
| `alertRecord` | Zähler einer Alert-Pipeline für den letzten UTC-Tag, an dem die Pipeline ein Ereignis entgegengenommen hat: `day` (`YYYY-MM-DD`), `processed`, `dropped` und `failed`. `last_dropped` und `last_failed` enthalten die jeweils letzte Verwerfung und den letzten Fehler des Tages, jeweils mit `atTime`, `rule` (Regel, Alert-Quelle oder synthetische Prüfung) und `reason`. Ein fehlender Zähler entspricht 0. Andere Pipelines und Alert-Pipelines, die noch kein Ereignis entgegengenommen haben, liefern `null`. Siehe [Tageszähler](/de/pipelines/alert-events#tageszähler). |
| `auditReaderId` | ID des Kontos, dessen Berechtigungen die Pipeline zum Lesen von `_audit` nutzt: das Konto, das die Pipeline zuletzt gespeichert hat. `null` für Pipelines, die `_audit` nicht lesen. Siehe [Audit-Stream](/de/settings/data-security#audit-stream). |
| `auditReader` | `id`, `displayName` und `email` dieses Kontos. Der Zugriff erfordert `pipelines.read`. Wenn das Konto nicht mehr existiert oder sich nicht abrufen lässt, enthält das Feld `null`. `auditReaderId` bleibt unverändert. |

Siehe [Zeitplan und Lesepositionen](/de/pipelines#zeitplan-und-lesepositionen) und [Wiederholungsversuche und Dead Letters](/de/pipelines#wiederholungsversuche-und-dead-letters).

## Aktualisieren und löschen

`PUT` akzeptiert denselben Request-Body wie [Pipeline erstellen](/de/api/intake/create-pipeline) und ersetzt die Konfiguration. Ändert sich nur `enabled`, ist `pipelines.pause` erforderlich. Jeder andere `PUT`-Aufruf erfordert `pipelines.edit`, auch wenn sich nichts ändert. Der Wechsel von `enabled` von `false` zu `true` setzt die Lesepositionen zurück. Die Pipeline liest dann aus jeder Quelle erneut die letzten `lookbackSecs` Sekunden. `DELETE` antwortet mit `{"deleted": true}`.

Bei einer Pipeline, die `_audit` liest, legt `PUT` auch fest, mit welchen Berechtigungen die Pipeline liest. Siehe [Audit-Stream](/de/settings/data-security#audit-stream).

| Der `PUT`-Aufruf | Zusätzlich erforderlich | Berechtigungen zum Lesen von `_audit` |
|---|---|---|
| Ändert die Konfiguration | `audit.read` und ein Token, das nicht zu einem Dienstkonto gehört | Ab dann gelten die Berechtigungen des aufrufenden Kontos. |
| Ändert nichts | Nichts | Ab dann gelten die Berechtigungen des aufrufenden Kontos, wenn das Konto `audit.read` hat und das Token nicht zu einem Dienstkonto gehört. Andernfalls bleiben die Berechtigungen unverändert, ohne Fehlermeldung. |
| Ändert nur `enabled` | Nichts | Unverändert. |

## Ausführungsverlauf

```http
GET /api/v1/scheduled_pipelines/{id}/runs?limit=50&beforeTime=<cursor>
```

Gibt die Ausführungen einer geplanten Pipeline zurück, beginnend mit der neuesten. Echtzeit- und Alert-Pipelines zeichnen keine Ausführungen auf.

<ResponseExample>
```json 200
[
  {
    "id": "3KE7Yq0d3jvXm5cJ8r2bWQzN1aP",
    "pipelineId": "3KBHcb6imgQq7FXBsROGTIRHOyg",
    "state": "succeeded",
    "startedAt": 1790000000000000,
    "finishedAt": 1790000000250000,
    "scannedRows": 1200,
    "writtenRows": 1150,
    "droppedRows": 48,
    "failedRows": 2,
    "attempt": 1,
    "error": null,
    "warning": "stream `app` rejected 2 event(s): <reason>"
  }
]
```
</ResponseExample>

| Feld | Hinweise |
|---|---|
| `state` | `running`, `succeeded`, `failed` oder `cancelled`. |
| `startedAt`, `finishedAt` | Start- und Endzeit der Ausführung. Solange die Ausführung läuft, ist `finishedAt` gleich `null`. |
| `scannedRows` | Anzahl der Ereignisse, die die Ausführung aus ihren Quellen gelesen hat. |
| `writtenRows` | Anzahl der Ereignisse, die alle Ziele angenommen haben. |
| `droppedRows` | Anzahl der Ereignisse, die ein Schritt mit `abort` verworfen oder die Deduplizierung entfernt hat. |
| `failedRows` | Anzahl der Ereignisse, bei denen ein Schritt fehlgeschlagen ist, die an eine Quelle weitergeleitet wurden oder die ein Ziel nicht angenommen hat. |
| `attempt` | `1` für den ersten Versuch. Bei einem Wiederholungsversuch für ein fehlgeschlagenes Zeitfenster ist der Wert höher. |
| `error` | Grund für das Scheitern der Ausführung: ein fehlgeschlagenes Zeitfenster mit dem geplanten Wiederholungsversuch oder ein Zielstream, der keines der für ihn bestimmten Ereignisse angenommen hat, während die Pipeline keinen Dead-Letter-Stream hat. |
| `warning` | Probleme, bei denen die Ausführung nicht fehlschlägt, etwa fehlgeschlagene, abgelehnte oder nicht zugestellte Ereignisse oder ein nach den Wiederholungsversuchen übersprungenes Zeitfenster. |

`scannedRows` entspricht der Summe aus `writtenRows`, `droppedRows` und `failedRows`.

## Heutige Limits

```http
GET /api/v1/scheduled_pipelines/{id}/limits
```

Gibt zurück, was die [Kontingent- und Drosselungsschritte](/de/pipelines#zählen-und-begrenzen) einer Echtzeit-Pipeline heute seit 00:00 UTC durchgelassen und zurückgehalten haben. Jeder Knoten zählt mit und steuert alle 5 Sekunden seine Zählerstände bei. Für einen Schritt, der heute nichts gezählt hat, fehlt die Zeile.

<ResponseExample>
```json 200
{
  "dayStart": 1790035200000000,
  "buckets": [
    {
      "step": "daily",
      "bucket": "[\"checkout\"]",
      "admittedEvents": 1000000,
      "admittedBytes": 524288000,
      "overEvents": 1240,
      "overBytes": 650117
    },
    {
      "step": "per-host",
      "bucket": "",
      "admittedEvents": 86400,
      "admittedBytes": 45298483,
      "overEvents": 12,
      "overBytes": 6291
    }
  ]
}
```
</ResponseExample>

| Feld | Hinweise |
|---|---|
| `step` | Name des Schritts. |
| `bucket` | Leer bei einem nicht aufgeteilten Kontingent oder einer Drosselung. Bei einem aufgeteilten Kontingent enthält das Feld die Werte der Felder, nach denen das Kontingent aufgeteilt ist, in derselben Reihenfolge als JSON-Liste. `null` steht für einen im Ereignis fehlenden Wert und `*` für Buckets oberhalb der Obergrenze von 1.000. |
| `admittedEvents`, `admittedBytes` | Ereignisse und Bytes, die innerhalb des Limits durchgelassen wurden. |
| `overEvents`, `overBytes` | Ereignisse und Bytes oberhalb des Limits. Je nach Konfiguration verwirft der Schritt sie, lässt sie durch oder leitet sie an einen anderen Stream weiter. |

## Backfill

```http
POST /api/v1/scheduled_pipelines/{id}/backfill
```

| Feld | Typ | Hinweise |
|---|---|---|
| `startTime` | integer | Beginn des Zeitfensters in Mikrosekunden. |
| `endTime` | integer | Ende des Zeitfensters. Der Wert muss größer als `startTime` sein. Das Zeitfenster darf höchstens 31 Tage umfassen. |

<RequestExample>
```bash cURL
curl -X POST http://localhost:5080/api/v1/scheduled_pipelines/$PIPELINE_ID/backfill \
  -H "authorization: Bearer $MS_TOKEN" \
  -H 'content-type: application/json' \
  -d '{"startTime": 1790000000000000, "endTime": 1790086400000000}'
```
</RequestExample>

<ResponseExample>
```json 202
{
  "jobs": [
    {
      "source": "app_raw",
      "jobId": "3KE6epTrWXts1oa2ePEKIHKxG19",
      "monitor": "/api/v1/query/jobs/3KE6epTrWXts1oa2ePEKIHKxG19"
    },
    {
      "source": "nginx_raw",
      "jobId": "3KE6eqAbXq0n2yLr7VvTq9cUo4D",
      "monitor": "/api/v1/query/jobs/3KE6eqAbXq0n2yLr7VvTq9cUo4D"
    }
  ]
}
```
</ResponseExample>

Der Backfill startet einen Suchjob pro Quelle. Jeder Job liest die Daten seiner Quelle im angegebenen Zeitfenster und wendet die Schritte an. Wie bei einer geplanten Ausführung schreibt und liefert der Job die Ereignisse aus und speichert Dead Letters. Die Lesepositionen der Pipeline bleiben unverändert. Verfolgen Sie jeden Job über seinen `monitor`-Pfad. Siehe [Abfrage](/de/query#zeitbereiche-und-asynchrone-jobs).

Eine Echtzeit- oder Alert-Pipeline antwortet mit `400` (`realtime and alert pipelines do not support backfill`). Eine Pipeline, die `_audit` liest, antwortet mit `403`, wenn dem Token `audit.read` fehlt oder das Token zu einem Dienstkonto gehört. Bei der Ausführung prüft der Job erneut die Berechtigungen des Kontos, das den Job eingereicht hat. Fehlt `audit.read` inzwischen, schlägt der Job fehl.
