```http
POST /api/v1/_kinesis_firehose
```

Akzeptiert Datenlieferungen von AWS Data Firehose an einen HTTP-Endpunkt. Der Endpunkt verwendet kein Bearer-Token. Erstellen Sie einen Connector vom Typ `aws_kinesis_firehose` mit einem `pushToken` von mindestens 16 Zeichen und einem `target_stream`. Geben Sie das Token in Firehose als Zugriffsschlüssel an. Der Endpunkt liest das Token aus `X-Amz-Firehose-Access-Key` und akzeptiert auch `X-Connector-Token` und `?token=`. Bei einem falschen Token antwortet der Endpunkt mit `401`.

Jeder Datensatz enthält Base64-kodierte `data`. Der Endpunkt dekodiert die Daten, teilt sie in Zeilen auf und wandelt jede nicht leere Zeile in ein Log-Ereignis im `target_stream` um (Standard: `kinesis`). Aus einem JSON-Objekt in einer Zeile erzeugt der Endpunkt einzelne Felder. Den Inhalt einer Klartextzeile speichert er im Feld `message`.

<RequestExample>
```bash cURL
curl -X POST http://localhost:5080/api/v1/_kinesis_firehose \
  -H 'X-Amz-Firehose-Access-Key: <pushToken>' \
  -H 'content-type: application/json' \
  -d '{"requestId":"req-1","timestamp":1790000000000,"records":[{"data":"eyJsZXZlbCI6ImluZm8ifQo="}]}'
```
</RequestExample>

<ResponseExample>
```json 200
{ "requestId": "req-1", "timestamp": 1790000000123 }
```
</ResponseExample>

Wie von Firehose gefordert, gibt die Antwort `requestId` unverändert zurück und enthält einen `timestamp` in Millisekunden. Informationen zur Einrichtung finden Sie unter [Connectoren](/de/connectors).

## Datenlieferung und Stream-Auswahl prüfen

1. Prüfen Sie, ob der Connector aktiviert ist und der Sender das Push-Token des Connectors verwendet. Ein reguläres API-Token ersetzt kein Push-Token.
2. Wenn Sie `configJson` direkt über die Connector-API setzen, verwenden Sie `target_stream` für den Zielstream, nicht `targetStream`. Der Token-Schlüssel bleibt `pushToken` in CamelCase.
3. Senden Sie ein einzelnes Testereignis mit einer eindeutigen Markierung und notieren Sie die Empfangszeit. Wählen Sie unter **Logs** den vorgesehenen Stream und einen Zeitraum aus, der die Empfangszeit abdeckt. Suchen Sie dann nach der Markierung.
4. Wenn die Anfrage erfolgreich ist, der vorgesehene Stream aber leer bleibt, prüfen Sie den zugehörigen Standardstream und das gespeicherte Zielfeld. Eine HTTP-Bestätigung ersetzt keine Abfrage im vorgesehenen Zielstream.

Schützen Sie das Token wie andere Zugangsdaten. Wenn Sie das Token als URL-Abfrageparameter übergeben, halten Sie die vollständige URL aus Logs, Tickets und Screenshots heraus. Prüfen Sie vor dem erneuten Senden einer fehlgeschlagenen Anfrage, ob das Problem am Token oder am Connector-Status liegt oder ob ein Fehler im Format oder in der Komprimierung der Nutzdaten vorliegt.
