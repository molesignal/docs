Die APM-API stellt aus Trace-Spans abgeleitete Aggregate für die jeweilige Organisation bereit. Alle Endpunkte verwenden das
Präfix `/api/v1/apm` und erfordern ein Bearer-Token.

```http
Authorization: Bearer <token>
```

Für einen Organisations-Workspace ist die Leseberechtigung des jeweiligen Bereichs erforderlich: `apm.services.read`, `apm.errors.read`,
`apm.error_rules.read`, `apm.definitions.read`, `apm.slos.read`, `apm.deployments.read` oder `apm.settings.read`. Bei Aufrufen auf Plattformebene lässt sich
`sys.telemetry.read` im geschützten Scope `_sys` verwenden. Bei jedem Schreibaufruf steht die erforderliche Berechtigung. Zum Melden eines Deployments ist
`apm.deploy` erforderlich.

## Endpunkte

| Methode und Pfad | Antwort |
|---|---|
| `GET /api/v1/apm/overview` | RED-Übersicht und -Verlauf für alle Services, aktueller und bisheriger Zustand der Services, Ranglisten, Deployments, Umgebungen, Instrumentierungslücken, wichtigste Transaktionen, Abhängigkeiten und Fehler. |
| `GET /api/v1/apm/insights` | Änderungen gegenüber dem vorherigen Zeitraum und dem gleichen Zeitraum der Vorwoche, Versionen mit schlechterer Leistung, Möglichkeiten zur Zeiteinsparung und jeweils zeitlich benachbarte Änderungen. |
| `GET /api/v1/apm/services` | Paginierter Servicekatalog mit Instrumentierung, Versionen, Zustand, RED-Metriken und Trace-Filtern. |
| `GET /api/v1/apm/services/{service}` | Serviceübersicht, Verlauf, Transaktionen, Abhängigkeiten, Fehler und Versionen. |
| `GET /api/v1/apm/services/{service}/instances` | Instanzen eines Services in einer Umgebung mit Version, Ressourcenattributen und den jeweils verarbeiteten Anfragen. |
| `GET /api/v1/apm/services/{service}/coverage` | Gibt an, ob Logs, Metriken, Profile und Browsersitzungen des Services innerhalb der 24 Stunden vor `to` bei MoleSignal eingegangen sind. |
| `GET /api/v1/apm/transactions` | Paginierte RED-Metriken für Transaktionen und Rangliste nach Gesamtdauer. |
| `GET /api/v1/apm/transactions/{transaction}` | Transaktionsverlauf, zugehörige Fehler, Versionen und Trace-Filter. |
| `GET /api/v1/apm/dependencies` | Paginierte RED-Metriken für Aufrufer und Abhängigkeiten sowie Rangliste nach Gesamtdauer. |
| `GET /api/v1/apm/map` | Service-Map für eine Umgebung und einen Namespace: Services, deren Aufrufziele, Topics und die Aufrufe zwischen ihnen. |
| `GET /api/v1/apm/map/edge` | Eine Aufrufverbindung in der Service-Map: ihr Verlauf, die darüber gesendeten Anfragen und die Fehler des aufgerufenen Services. |
| `GET /api/v1/apm/blast-radius` | Reichweite eines Services in der Service-Map: direkte und indirekte Aufrufer und Aufrufziele, aufgeschlüsselt nach Anzahl der Verbindungen. |
| `GET /api/v1/apm/errors` | Paginierte, bereinigte Backend-Fehlergruppen mit Angaben dazu, wo sie auftraten. |
| `GET /api/v1/apm/errors/{fingerprint}` | Fehlerverlauf, betroffene Transaktionen und Versionen, Auftretensorte der Fehlergruppe, repräsentativer Stacktrace und eine begrenzte Anzahl von Beispielen. |
| `GET /api/v1/apm/versions/compare` | RED-Metriken für Referenz- und Vergleichsversion, Abweichungen, Status der Datengrundlage und Regressionen. |
| `GET /api/v1/apm/health` | Status der Mandantenprojektion, Laufzeitzustand, Grenzen und Lücken. |
| `GET /api/v1/apm/service-definitions` | Alle Service-Definitionen der Organisation. |
| `PUT /api/v1/apm/service-definitions/{service}?namespace=` | Erstellt oder ersetzt die Definition eines Services. Erfordert `apm.definitions.manage`. |
| `DELETE /api/v1/apm/service-definitions/{service}?namespace=` | Löscht die Definition eines Services. Erfordert `apm.definitions.manage`. |
| `POST /api/v1/apm/service-definitions/{service}/key-transactions?namespace=` | Markiert einen Endpunkt als Schlüsseltransaktion des Services oder hebt die Markierung auf. Erfordert `apm.definitions.manage`. |
| `PUT /api/v1/apm/errors/{fingerprint}/issue` | Legt den Status, das Team und die zuständige Person für eine Fehlergruppe fest. Erfordert `apm.errors.manage`. |
| `GET /api/v1/apm/error-rules` | Regeln der Organisation zur Fehlergruppierung in der Reihenfolge, in der die API sie prüft. |
| `POST /api/v1/apm/error-rules` | Erstellt eine Gruppierungsregel, die die API nach den anderen Regeln prüft. Erfordert `apm.error_rules.manage`. |
| `PUT /api/v1/apm/error-rules/{id}` | Ersetzt eine Gruppierungsregel. Erfordert `apm.error_rules.manage`. |
| `DELETE /api/v1/apm/error-rules/{id}` | Löscht eine Gruppierungsregel. Erfordert `apm.error_rules.manage`. |
| `PUT /api/v1/apm/error-rules/order` | Legt die Reihenfolge fest, in der die API die Regeln prüft. Erfordert `apm.error_rules.manage`. |
| `GET /api/v1/apm/slos` | Alle Service Level Objectives mit Status, erreichtem Wert, verbleibendem Fehlerbudget und Verbrauchsraten. |
| `GET /api/v1/apm/slos/{id}` | Status eines Service Level Objectives und Tageswerte für das gesamte Zeitfenster. |
| `POST /api/v1/apm/slos` | Erstellt ein Service Level Objective. Erfordert `apm.slos.manage`. |
| `PUT /api/v1/apm/slos/{id}` | Ersetzt ein Service Level Objective. Erfordert `apm.slos.manage`. |
| `DELETE /api/v1/apm/slos/{id}` | Löscht ein Service Level Objective. Erfordert `apm.slos.delete`. |
| `POST /api/v1/apm/deployments` | Meldet ein Deployment. Erfordert `apm.deploy`. |
| `GET /api/v1/apm/deployments` | Von Pipelines gemeldete Deployments, neueste zuerst. |
| `GET /api/v1/apm/settings` | APM-Einstellungen der Organisation oder Standardwerte, falls keine Einstellungen gespeichert sind. |
| `PUT /api/v1/apm/settings` | Ersetzt die APM-Einstellungen der Organisation. Erfordert `apm.settings.manage`. |

Kodieren Sie Pfadparameter per URL-Encoding. Verwenden Sie für `transaction` oder den Fehler-`fingerprint` exakt den Wert
aus einer Listenantwort.

## Gemeinsame Abfrageparameter

| Parameter | Typ | Verhalten |
|---|---|---|
| `from` | Ganzzahl | Beginn des Zeitraums in Mikrosekunden seit der Unix-Epoche. Standard: 24 Stunden vor `to`. |
| `to` | Ganzzahl | Ende des Zeitraums in Mikrosekunden seit der Unix-Epoche. Standard: aktueller Zeitpunkt. |
| `namespace` | Zeichenfolge | Filtert nach exakter Übereinstimmung mit dem Service-Namespace. |
| `service` | Zeichenfolge | Filtert nach exakter Übereinstimmung mit dem Servicenamen. Der Pfadparameter des Detailendpunkts für Services hat Vorrang vor diesem Wert. |
| `environment` | Zeichenfolge | Filtert nach exakter Übereinstimmung mit der Deployment-Umgebung. |
| `version` | Zeichenfolge | Filtert nach exakter Übereinstimmung mit der Serviceversion. |
| `resolution` | Enum | `auto`, `minute` oder `hour`. `auto` wählt die Auflösung, in der die Daten für den Zeitraum vorliegen. |
| `sort` | Zeichenfolge | Endpunktspezifisches Sortierfeld. |
| `direction` | Enum | `asc` oder `desc`. Standard: `desc`. |
| `limit` | Ganzzahl | Seitengröße von 1 bis 200. Standard: 50. |
| `cursor` | Zeichenfolge | Opaker Cursor aus einer vorherigen Listenantwort. |
| `status` | Enum | Nur für `/errors`: `all` (Standard), `unresolved` (offene Gruppen, Gruppen in Untersuchung und erneut aufgetretene, bereits behobene Gruppen), `investigating`, `resolved` oder `ignored`. |

Filter müssen mindestens 1 Byte und dürfen höchstens 192 Bytes lang sein. Der Zeitraum darf das konfigurierte Maximum nicht
überschreiten. Standard: 30 Tage (`[apm].max_query_range_days`).

### Sortierfelder

| Endpunkt | Unterstützte Werte für `sort` | Standard |
|---|---|---|
| `/services` | `requestCount`, `errorRate`, `p95`, `name` | `requestCount` |
| `/transactions` | `requestCount`, `errorRate`, `p95`, `total_time` | `requestCount` |
| `/dependencies` | `requestCount`, `errorRate`, `p95`, `total_time` | `total_time` |
| `/errors` | `occurrenceCount`, `errorRate`, `lastSeen` | `occurrenceCount` |

`/overview` akzeptiert dieselben Filter und denselben Auflösungsparameter, verwendet aber keine Paginierung. Endpunkte für Details, Vergleiche und
Zustandsinformationen geben keine paginierten Listen zurück.

## Übersicht abfragen

<RequestExample>
```bash cURL
NOW=$(date +%s)000000
curl --get 'http://localhost:5080/api/v1/apm/overview' \
  --header "Authorization: Bearer $MS_TOKEN" \
  --data-urlencode "from=$((NOW-86400000000))" \
  --data-urlencode "to=$NOW" \
  --data-urlencode 'environment=production' \
  --data-urlencode 'resolution=auto'
```
</RequestExample>

Die Antwort enthält `red`, `trend`, `serviceHealth`, `services`, `topTransactions`,
`topDependencies`, `topErrors` und `recentVersions`, dazu das gemeinsame Objekt `meta` und die folgenden Felder:

| Feld | Hinweise |
|---|---|
| `serviceCount`, `activeServiceCount` | Anzahl der im Zeitraum erfassten Services und Anzahl der Services, die mindestens eine Anfrage bearbeitet haben. |
| `healthTrend` | Anzahl der Services pro Zustand und Zeitabschnitt. Der Zeitraum umfasst höchstens 48 Abschnitte. Kein Abschnitt ist kürzer als ein Bucket. Ein Service ohne Anfragen zählt im jeweiligen Abschnitt als `noTraffic`. |
| `rankings` | Je fünf Services in `slowest` (nach p95), `mostErrors` (nach Fehlerrate) und `busiest` (nach Anfragezahl). Die ersten beiden Listen enthalten nur Services mit mindestens 20 Anfragen. |
| `deployments` | Bis zu 20 Versionen, die im Zeitraum erstmals erfasst wurden, absteigend nach Erfassungszeitpunkt. Jede enthält `red` und `verdict` wie unter [Versionen eines Service abrufen](#versionen-eines-dienstes-abrufen). |
| `environments`, `availableEnvironments` | Services und Anfragen pro Umgebung in der aktuellen Auswahl sowie alle Umgebungen, in denen die Services laufen, unabhängig vom Filter `environment`. |
| `instrumentation` | Anzahl der Services pro Programmiersprache und SDK sowie Anzahl der Services, die kein `deployment.environment`, kein `service.version` oder kein `service.instance.id` melden. |

## Erkenntnisse abrufen

`GET /api/v1/apm/insights` akzeptiert die gemeinsamen Zeitraum- und Filterparameter und gibt `meta` sowie die folgenden Felder zurück:

| Feld | Hinweise |
|---|---|
| `now`, `previous`, `lastWeek` | Kennzahlen für die ausgewählten Services im abgefragten Zeitraum, im unmittelbar davorliegenden gleich langen Zeitraum und im entsprechenden Zeitraum eine Woche zuvor: `requestCount`, `throughput` in Anfragen pro Sekunde, `errorRate`, `p95Time` und `apdex`. Zeiträume ohne Anfragen fehlen. |
| `insights` | Bis zu 30 Befunde, die dringendsten zuerst. |

Jeder Befund enthält:

| Feld | Hinweise |
|---|---|
| `kind` | `anomaly`, `regression`, `slow_dependency`, `repeated_call`, `slowQuery` oder `hot_endpoint`. |
| `severity` | `critical`, `warning` oder bei einer Empfehlung `info`. |
| `service` | `namespace`, `name` und `environment`. |
| `transaction`, `dependency` | Der betroffene Endpunkt bei einem Befund vom Typ `hot_endpoint` oder die betroffene Abhängigkeit bei einem Engpass, einem wiederholten Aufruf oder einer langsamen Anweisung. |
| `metric` | Die Kennzahl, die sich verändert oder verschlechtert hat: `errorRate`, `p95` oder `throughput`. |
| `value` | Der aktuelle Wert: Fehlerrate als Anteil, p95 in Mikrosekunden oder Anfragen pro Sekunde. Bei einem Engpass oder einem Befund vom Typ `hot_endpoint` ist es der Anteil an der Gesamtdauer, bei wiederholten Aufrufen die Zahl der Aufrufe pro Anfrage und bei einer langsamen Anweisung deren p95 in Mikrosekunden. |
| `previous`, `lastWeek` | Dieselbe Kennzahl für den unmittelbar davorliegenden Zeitraum und den entsprechenden Zeitraum eine Woche zuvor. Bei einer Regression gilt der Wert der vorherigen Version. |
| `since` | Zeitpunkt, zu dem die Veränderung begann oder die Version mit der Regression erstmals erfasst wurde. |
| `version`, `previousVersion` | Die Version mit der Regression und ihre Vorgängerversion. |
| `calls`, `p95Time` | Anzahl der Aufrufe oder Anfragen, auf denen die Empfehlung beruht, sowie deren p95. |
| `changes` | Änderungen im zeitlichen Umfeld von `since`, nach zeitlicher Nähe sortiert: `kind`, `source` (`reported` oder `observed`), `service`, `version`, `status`, `at`, `downstream` (`true` für einen Service, den der von der Veränderung betroffene Service aufruft), `commit` und `description`. |

Die Schwellenwerte stehen unter [Erkenntnisse und Untersuchungen](/de/apm/insights#welche-befunde-die-karte-zeigt).

## RED-Metriken abrufen

Jede Zusammenfassung enthält ein Objekt `red` mit Kennzahlen zu Anfragen, Fehlern und Dauer im abgefragten Zeitraum.

| Feld | Hinweise |
|---|---|
| `requestCount`, `errorCount`, `errorRate` | Anzahl der Anfragen, Anzahl der fehlgeschlagenen Anfragen und Anteil der fehlgeschlagenen Anfragen an allen Anfragen, von 0 bis 1. |
| `durationSum`, `durationAverage` | Gesamtdauer und durchschnittliche Dauer in Mikrosekunden. Ohne Anfragen ist der Durchschnitt `null`. |
| `p50Time`, `p90Time`, `p95Time`, `p99Time` | Latenzperzentile in Mikrosekunden, ermittelt innerhalb des Histogramm-Buckets, in den der jeweilige Rang fällt. Bei der Standardstruktur weicht der Wert um höchstens etwa 4 % von der exakten Dauer ab. Ohne Anfragen `null`. |
| `apdex` | Anzahl der Anfragen innerhalb des Schwellenwerts T plus die Hälfte der Anfragen oberhalb von T bis einschließlich 4T, geteilt durch die Gesamtzahl der Anfragen. Der Wert liegt zwischen 0 und 1. T entspricht `apdexThreshold` des Service, sonst 500 ms. Die Übersicht verwendet für die Gesamtwerte aller Services 500 ms. Fehlgeschlagene Anfragen gelten nie als zufriedenstellend. Ohne Anfragen `null`. |
| `latencyPartial` | `true`, wenn sich die Latenzstruktur einiger Buckets nicht aus den Buckets selbst ermitteln lässt. MoleSignal konvertiert Buckets mit einer älteren Struktur (`[apm.histogram].schema_version`) und berücksichtigt sie. Nicht lesbare Buckets fließen nicht in die Perzentile ein, zählen aber weiterhin für Anzahlen, Summe und Mittelwert. |
| `timeoutCount`, `retryCount` | Anzahl der Anfragen mit Zeitüberschreitung (Timeout-Fehlertyp, gRPC `DEADLINE_EXCEEDED`, HTTP 408 oder 504) beziehungsweise der erneut gesendeten Anfragen (`http.request.resend_count` größer als 0). Das jeweilige Feld fehlt, wenn keine solchen Anfragen vorliegen. |
| `statusCodes` | Antworten nach Statuscode, als `http:<code>` (100 bis 599) oder `grpc:<code>` (0 bis 16). Ein Bucket speichert bis zu 24 Codes. Weitere Codes zählen als `http:other` oder `grpc:other`. Das Feld fehlt, wenn kein Code gezählt wurde, etwa bei Aggregaten aus der Zeit vor der Erfassung von Statuscodes. |
| `exemplars` | Bis zu 8 Beispiel-Spans aus dem Zeitraum, die langsamsten zuerst. MoleSignal übernimmt den Span als Beispiel, bevor das [Tail-Sampling](/de/configuration#trace-erfassung-und-tail-sampling) entscheidet, ob der zugehörige Trace gespeichert wird. Deshalb ist `traceAvailable` meist `false`. Rufen Sie den Trace ab, um zu prüfen, ob er gespeichert wurde. Das Aggregat bleibt gültig. |

Zusammenfassungen für Services und Transaktionen enthalten in `apdexThreshold` den Schwellenwert T, der dem Apdex zugrunde liegt.
Eine Service-Zusammenfassung enthält auch `health` und `healthReasons`. Letzteres listet jede Schwellenwertüberschreitung mit `metric`
(`errorRate` oder `p95`), `level`, `value` und `threshold` auf. `sparkline` enthält Anfragezahl, Fehlerzahl und p95 pro Bucket.
`currentVersion` nennt die zuletzt erfasste Version und `currentVersionSince` den Zeitpunkt, zu dem diese Version
erstmals erfasst wurde. Die Detailansicht eines Service oder einer Transaktion enthält in `latencyDistribution` die Histogramm-Buckets
mit Anfragen, jeweils mit `lowerTime`, `upperTime` und `count`. Die äußeren Grenzen entsprechen der Dauer der
schnellsten und der langsamsten Anfrage.

## Service-Definitionen speichern

Eine Definition hält fest, wer für einen Service zuständig ist und wie wichtig der Service ist. `namespace` und
Service-Name bilden den Schlüssel. Die Definition gilt damit in jeder Umgebung und kann bereits vorliegen, bevor der Service Daten meldet.

```http
PUT /api/v1/apm/service-definitions/checkout?namespace=shop
Content-Type: application/json

{"description": "Takes orders and payments.", "teamId": "<team id>", "ownerId": "<user id>", "tier": "p0", "lifecycle": "production", "repositoryUrl": "https://github.com/acme/checkout", "tags": {"domain": "orders", "pci": ""}, "apdexThreshold": 300000, "aliases": ["order_service", "Order Center"], "dataSources": {"logs": [{"stream": "default", "filter": "service_name = 'order_service'"}], "metrics": [{"selector": "{service=\"checkout\"}"}], "dashboards": ["<dashboard id>"], "links": [{"name": "Runbook", "url": "https://wiki.example.com/checkout"}]}, "archived": false}
```

| Feld | Hinweise |
|---|---|
| `description` | Bis zu 2.000 Zeichen. |
| `teamId` | Ein Team der Organisation oder `null`. Beim Löschen des Teams wird das Feld geleert. |
| `ownerId` | Ein Mitglied der Organisation oder `null`. |
| `tier` | `p0` (höchste Priorität) bis `p5` oder `null`. |
| `lifecycle` | `production`, `staging`, `experimental`, `deprecated` oder `null`. |
| `repositoryUrl` | Eine `http`-, `https`-, `ssh`-, `git`- oder `git+ssh`-URL oder `user@host:path`, ohne Leerzeichen, mit bis zu 2.048 Zeichen, oder `null`. MoleSignal speichert das Passwort als `****`, bei einer HTTP(S)-Adresse auch den Benutzernamen. MoleSignal zeigt den Wert an, wenn der Service kein Repository meldet. |
| `tags` | Bis zu 32 Tags im Format `{ "key": "value" }`. Ein Schlüssel besteht aus 1 bis 64 Zeichen: Kleinbuchstaben, Ziffern und `_ . - /`. Ein Wert ist bis zu 128 Zeichen lang und hat keine führenden oder nachgestellten Leerzeichen. Für einen Schlüssel ohne Wert bleibt der Wert leer. |
| `apdexThreshold` | Der Apdex-Schwellenwert T des Service: größer als 0 und höchstens 60.000.000 (eine Minute) oder `null` für 500 ms. |
| `aliases` | Bis zu 20 weitere Namen, unter denen der Service in Logs, Metriken und anderen Systemen erscheint. Jeder Name umfasst 1 bis 128 Zeichen ohne führende oder nachgestellte Leerzeichen. Groß- und Kleinschreibung spielt keine Rolle: Ein Name darf weder doppelt vorkommen noch dem eigenen Namen oder einem Namen oder Alias eines anderen Service der Organisation entsprechen. Ohne Angabe behält eine gespeicherte Definition ihre Aliasse. |
| `dataSources` | Datenquellen des Service: `logs` (`stream` und ein optionaler `filter`, ein boolescher SQL-Ausdruck mit bis zu 2.000 Zeichen), `metrics` (`selector`, ein PromQL-Selektor wie `{service="checkout"}`), `dashboards` (Dashboard-IDs) und `links` (`name` und eine `http`- oder `https`-`url`), jeweils bis zu 10 Einträge. Ohne Angabe behält eine gespeicherte Definition ihre Datenquellen. |
| `archived` | Bei `true` blendet MoleSignal den Service in der Standardansicht des Katalogs aus. Ohne Angabe behält eine gespeicherte Definition ihren Status. |

Beim Speichern bleiben die `keyTransactions` der Definition unverändert. Ändern Sie diese einzeln. Die Antwort enthält die
gespeicherte Definition mit `namespace`, `name`, `keyTransactions`, `updatedBy` und `updatedAt`.
`DELETE` gibt `204` zurück oder `404`, wenn der Service keine Definition hat.

### Schlüsseltransaktionen markieren

```http
POST /api/v1/apm/service-definitions/checkout/key-transactions?namespace=shop
Content-Type: application/json

{"transaction": {"name": "POST /orders", "kind": "http"}, "key": true}
```

`key: true` fügt den Endpunkt zu `keyTransactions` hinzu, `false` entfernt ihn. Entspricht die Anfrage dem aktuellen Zustand,
ändert sich nichts. Fehlt die Definition für den Service, legt MoleSignal sie an. Ein Service kann bis zu 50 Schlüsseltransaktionen
haben. Die Sammelzeile `__other__` lässt sich nicht als Schlüsseltransaktion markieren. Die Antwort enthält die Definition nach
der Änderung.

## Signalabdeckung eines Service abrufen

`GET /api/v1/apm/services/{service}/coverage` erfordert `namespace` und `environment` und akzeptiert
optional `to`, das Ende des betrachteten Zeitraums in Mikrosekunden (standardmäßig der aktuelle Zeitpunkt). Der Endpunkt prüft die 24 Stunden
vor `to` und speichert jede Antwort fünf Minuten lang im Cache.

```json
{
  "from": 1792230096695000,
  "to": 1792316496695000,
  "logs": { "state": "reported", "found": ["default"] },
  "metrics": { "state": "missing" },
  "profiles": { "state": "reported", "found": ["cpu", "alloc_space"] },
  "rum": { "state": "unknown" }
}
```

| Signal | `reported`, wenn | `found` |
|---|---|---|
| `logs` | Ein Log-Stream mit dem Feld `service.name`, `service_name` oder `service` enthält einen Log-Eintrag des Service. Der Endpunkt prüft höchstens acht Streams, zuerst `default`. | Die Streams. |
| `metrics` | `count(last_over_time({"service.name"="<service>"}[1h]))` zum Zeitpunkt `to` größer als null ist. | Die Anzahl der Zeitreihen. |
| `profiles` | Der Profil-Stream ein Profil des Service enthält. | Die Profiltypen. |
| `rum` | Eine Browseraktion einen der fünf jüngsten Beispiel-Traces des Service enthielt. | Die Sitzung. |

`missing` bedeutet, dass die Prüfung nichts gefunden hat. `unknown` bedeutet, dass die Prüfung fehlgeschlagen ist oder länger als drei
Sekunden gedauert hat. Für `rum` gibt es nie `missing`: Eine Trace-Stichprobe kann zeigen, dass Sitzungen einen Service erreichen, aber nicht,
dass keine Sitzung ihn erreicht.

## Laufzeitprofil eines Service abrufen

`GET /api/v1/apm/services` und `GET /api/v1/apm/services/{service}` liefern für jede Service-Übersicht ein
`profile` aus den Instanzen, die im Zeitraum Daten gemeldet haben. Ist `version` gesetzt, zählen nur Instanzen dieser Version.
Jede Liste enthält bis zu fünf Werte, absteigend nach der Anzahl der Instanzen pro Wert sortiert, im Format
`{ "value": "1.8.2", "instances": 4 }`.

| Feld | Hinweise |
|---|---|
| `instanceCount`, `hostCount` | Anzahl der Instanzen und der unterschiedlichen `host.name`-Werte. |
| `versions` | Die Versionen, mit denen die Instanzen liefen. Bei einem Rollout erscheinen zwei Versionen. |
| `languages`, `runtimes`, `frameworks` | `telemetry.sdk.language`; `process.runtime.name` mit Versionsangabe; das Framework, das die Instrumentierungsbibliothek der Einstiegs-Spans angibt. |
| `regions`, `clusters`, `k8sNamespaces`, `workloads` | `cloud.region`, `k8s.cluster.name`, `k8s.namespace.name` und `k8s.deployment.name` oder `k8s.statefulset.name`. |
| `repositories`, `commits` | `vcs.repository.url.full` oder `git.repository_url`, jeweils ohne Zugangsdaten gespeichert; `vcs.ref.head.revision` oder `git.commit.sha`. |
| `entryKinds` | `http`, `rpc`, `messaging`, `span`: die Arten von Einstiegspunkten, die der Service bedient. |

`GET /api/v1/apm/services/{service}/instances` listet bis zu 500 Instanzen einzeln auf, beginnend mit den zuletzt
erfassten. Der Endpunkt akzeptiert `namespace`, `environment` sowie optional `version`, `from` und
`to`. Ohne Service oder Umgebung gibt er `400` zurück. Jeder Eintrag enthält `instanceId` (`service.instance.id`,
ersatzweise `k8s.pod.name`, sonst `host.name`), `version`, `firstSeenAt`,
`lastSeenAt` und `attributes` (eine Zuordnung der zuletzt von der Instanz gemeldeten Attribute). Zur Aktivität
im Zeitraum liefert der Eintrag `red` wie in den Übersichten, mit Apdex auf Basis des Service-Schwellenwerts, sowie `sparkline`. Bei Überschreitung des
Instanzlimits fasst der Endpunkt die übrigen Instanzen in einem Eintrag mit der `instanceId` `__other__` zusammen. War eine Instanz
im Zeitraum aktiv, bevor Daten zu ihr gespeichert wurden, erscheint sie mit leeren `attributes`.

## Status einer Fehlergruppe festlegen

```http
PUT /api/v1/apm/errors/<fingerprint>/issue
Content-Type: application/json

{"status": "investigating", "assigneeId": "<user id>", "teamId": "<team id>", "lastSeenAt": 1792316496695000}
```

`status` ist `open`, `investigating`, `resolved` oder `ignored`. `assigneeId` ist ein Mitglied der
Organisation oder `null`, `teamId` ein Team der Organisation oder `null`. Das optionale Feld `lastSeenAt` gibt in Mikrosekunden an, wann die Gruppe zuletzt gesehen wurde. Beim Setzen von
`resolved` speichert MoleSignal den Zeitpunkt als `resolvedAt`.

Fehlerübersichten enthalten den Status unter `issue` oder `null`, solange kein Status festgelegt ist. `issue.regressed`
ist `true`, wenn eine behobene Fehlergruppe nach `resolvedAt` erneut auftritt. Der Filter `unresolved` schließt
solche Gruppen ein. Ist der Fingerabdruck in der Projektion unbekannt, gibt der Endpunkt beim Setzen des Status `404` zurück.

## Service Level Objectives verwalten

Ein Service Level Objective (SLO) legt fest, welcher Anteil der Anfragen an einen Dienst in einer Umgebung oder
an einen seiner Endpunkte in einem gleitenden Zeitfenster die Kriterien erfüllen soll. Unter
[Service Level Objectives](/de/apm#service-level-ziele) finden Sie die Bedeutung der einzelnen Kennzahlen.

```http
POST /api/v1/apm/slos
Content-Type: application/json

{"name": "Checkout availability", "namespace": "shop", "service": "checkout", "environment": "production", "transaction": null, "kind": "availability", "objective": 0.999, "windowDays": 30}
```

| Feld | Hinweise |
|---|---|
| `name` | Pflichtfeld, bis zu 255 Bytes. |
| `description` | Optional, bis zu 2.000 Bytes. |
| `namespace`, `service`, `environment` | Pflichtfelder. Geben Sie den Dienst so an, wie er in APM heißt. Ein Dienst ohne `service.namespace` gehört zum Namespace `default`. |
| `transaction` | Ein einzelner Endpunkt, `{ "name": "POST /orders", "kind": "http" }`, oder `null` für den gesamten Dienst. |
| `kind` | `availability`: Eine Anfrage erfüllt das Kriterium, wenn sie nicht fehlschlägt. `latency`: Eine Anfrage erfüllt das Kriterium, wenn sie nicht fehlschlägt und höchstens `latencyThreshold` dauert. |
| `latencyThreshold` | Für `latency` erforderlich und größer als null. Für `availability` muss der Wert `null` sein oder fehlen. |
| `objective` | Anteil der Anfragen, die das Kriterium erfüllen. Der Wert liegt über 0 und unter 1, zum Beispiel `0.999`. |
| `windowDays` | `7`, `28` oder `30`. |

`POST` und `PUT` geben das gespeicherte SLO mit `id`, `createdBy`, `createdAt`, `updatedBy` und
`updatedAt` zurück. `GET /api/v1/apm/slos` gibt für jedes SLO der Organisation den Status zurück. Geben Sie
`namespace`, `service` und `environment` zusammen an, um nur die SLOs eines Dienstes abzurufen. Das Zeitfenster endet
zum Zeitpunkt des Aufrufs. Die üblichen Zeitraumparameter gelten daher nicht.

| Statusfeld | Hinweise |
|---|---|
| `slo` | Das gespeicherte SLO. |
| `state` | `healthy`, `at_risk`, `breached` oder `noData`. |
| `sli` | Anteil der Anfragen im Zeitfenster, die das Kriterium erfüllen, oder `null`, wenn keine Anfragen vorliegen. |
| `goodRequests`, `totalRequests` | Die Anzahlen, aus denen sich `sli` ergibt. Ein Latenz-SLO schätzt `goodRequests` anhand der Latenzhistogramme. Der Wert kann daher Nachkommastellen haben. |
| `budgetRemaining` | `1 - (1 - sli) / (1 - objective)`. Der Wert ist negativ, wenn das SLO verfehlt wurde, oder `null`, wenn keine Anfragen vorliegen. |
| `burnRates` | `oneHour`, `sixHours` und `oneDay`: jeweils `(1 - sli) / (1 - objective)` für die letzte Stunde, die letzten sechs Stunden und die letzten 24 Stunden oder `null`, wenn keine Anfragen vorliegen. |

`GET /api/v1/apm/slos/{id}` gibt `status` und `history` zurück. Der Verlauf enthält für jeden UTC-Tag im Zeitfenster,
an dem Anfragen vorliegen, einen Eintrag, beginnend mit dem ältesten. Jeder Eintrag enthält `dayStart` in Mikrosekunden, `sli`, `goodRequests`
und `totalRequests`.

`DELETE` gibt `204` zurück. Solange Alarmregeln das SLO überwachen, etwa Regeln zur Verbrauchsrate
des Fehlerbudgets, gibt `DELETE` den Statuscode `409` zurück. Löschen Sie zuerst diese Regeln. Alarmregeln für ein SLO sind APM-Regeln mit der Metrik
`slo_burn_rate`. Siehe [Regel erstellen](/de/api/alerting/create-rule#apm-regeln).

## Eine Transaktion eindeutig auswählen

Zwei Transaktionstypen können denselben Namen haben. Geben Sie den optionalen Parameter `kind` an, um einen Typ auszuwählen:

```http
GET /api/v1/apm/transactions/POST%20%2Fcheckout?kind=http&service=checkout
```

Die unterstützten Werte für `kind` sind `http`, `rpc`, `messaging`, `span` und `other`. Verwenden mehrere
Dienste oder Typen denselben Namen, gibt die API `400` mit der Meldung `APM transaction identity is ambiguous; provide service,
namespace, environment, and kind` zurück.

## Versionen vergleichen

Geben Sie unterschiedliche Werte für `baseline` und `candidate` an. Begrenzen Sie den Vergleich mit einem `service`-Filter auf einen Dienst.

```bash
curl --get 'http://localhost:5080/api/v1/apm/versions/compare' \
  --header "Authorization: Bearer $MS_TOKEN" \
  --data-urlencode 'service=checkout' \
  --data-urlencode 'environment=production' \
  --data-urlencode 'baseline=2.3.1' \
  --data-urlencode 'candidate=2.4.0'
```

Die Antwort enthält `baseline` und `candidate` mit jeweils `version`, `sampleCount` und
`red` sowie `delta`, `status`, `regressedTransactions` und `regressedErrors`. Jede Liste mit Regressionen
enthält höchstens 20 Einträge.

| Feld | Hinweise |
|---|---|
| `sufficientData` | Nur dann `true`, wenn beide Versionen die konfigurierte Mindestanzahl an Anfragen erreichen. Standardmäßig sind das 1.000 Anfragen pro Version (`[apm.version_comparison].min_requests_per_version`). |
| `status` | `insufficient_data`, `regressed`, `improved` oder `neutral`. `regressed`, wenn die Fehlerrate des Kandidaten gegenüber der Basisversion um mindestens einen Prozentpunkt auf mindestens das 1,5-Fache steigt oder seine p95-Latenz um mindestens 20 % und mindestens 50 ms steigt; `improved`, wenn eine der beiden Kennzahlen im entsprechenden Maß sinkt und keine im entsprechenden Maß steigt; `insufficient_data`, wenn `sufficientData` den Wert `false` hat. |
| `delta` | `requestCountAbsolute` und `requestCountRelative`, `errorRateAbsolute` und `errorRateRelative` sowie `p95AbsoluteTime` und `p95Relative`. Ein relativer Wert ist `null`, wenn der Bezugswert null ist oder fehlt. |

Fehlt `candidate` oder `baseline` oder sind beide Versionen identisch, gibt die API `400` zurück.

## Versionen eines Dienstes abrufen

`GET /api/v1/apm/services/{service}` gibt unter `versions` die im Zeitraum erfassten Versionen zurück. Jede Version enthält unter
`red` ihre Kennzahlen für den Zeitraum und unter `verdict` die Bewertung gegenüber der Version desselben Dienstes,
die unmittelbar vor ihr erstmals erfasst wurde. Für die Bewertung gelten dieselben Kriterien wie beim [Versionsvergleich](#versionen-vergleichen):

| Feld | Hinweise |
|---|---|
| `previous` | Die Version, die als Vergleichsbasis dient. |
| `status` | `regressed`, `improved`, `neutral` oder `insufficient_data`. |
| `worse` | Die Kennzahlen, die sich bei `status` gleich `regressed` verschlechtert haben: `errorRate`, `latency` oder beide. |
| `delta` | Wie beim Versionsvergleich dient die frühere Version als Basisversion. |

Die zuerst erfasste Version hat kein `verdict`. Ein Versionsfilter in der Anfrage schränkt die
Kennzahlen nicht ein: Für jede Version berücksichtigt die API die Daten des gesamten Dienstes.

## Aufschlüsselung nach Fehlerquellen abrufen

`GET /api/v1/apm/errors` gibt neben der Ergebnisseite unter `breakdown` eine Aufschlüsselung für alle Gruppen zurück, die dem `status`-Filter entsprechen
(nicht nur für die Gruppen auf der aktuellen Seite). `GET /api/v1/apm/errors/{fingerprint}` gibt unter `breakdown` die Aufschlüsselung für
die einzelne Gruppe zurück. Sie enthält `versions`, `environments` und `languages`, jeweils als Liste aus `value` und `count`,
absteigend nach Anzahl der Vorkommen sortiert. Ein Wert bleibt leer, wenn die Spans ihn nicht melden. Nach den ersten
sieben Werten fasst die API die übrigen unter `__other__` zusammen. Als Sprache dient der Wert von
`telemetry.sdk.language` des Dienstes.

## Regeln für die Fehlergruppierung verwalten

Mit einer Regel gruppieren Sie neu erfasste Fehler abweichend von der Standardgruppierung nach Fehlertyp, Frame und Endpunkt. MoleSignal prüft die Regeln
in der Reihenfolge von `position` und wendet die erste passende Regel an.

```http
POST /api/v1/apm/error-rules
Content-Type: application/json

{"name": "Upstream timeouts", "serviceNamespace": "shop", "serviceName": "checkout",
 "errorType": "*Timeout*", "message": "", "frame": "", "endpoint": "", "action": "merge", "enabled": true}
```

| Feld | Hinweise |
|---|---|
| `name` | Bis zu 128 Zeichen. Eine zusammengeführte Gruppe übernimmt diesen Namen. |
| `serviceNamespace`, `serviceName` | Der Dienst, für den die Regel gilt. Ein leeres `serviceName` steht für alle Dienste. Wenn Sie einen Namespace angeben, müssen Sie auch einen Dienstnamen angeben. |
| `errorType`, `message`, `frame`, `endpoint` | Muster für Fehlertyp, Ausnahmemeldung, ersten Anwendungs-Frame und Endpunkt, jeweils bis zu 256 Zeichen. Ein Muster muss zum gesamten Text passen. Groß- und Kleinschreibung spielen keine Rolle. `*` steht für beliebigen Text. Ein leeres Muster passt zu jedem Text. Geben Sie mindestens ein Muster an. |
| `action` | `merge`: MoleSignal fasst die passenden Fehler eines Dienstes in einer Gruppe zusammen. `ignore`: MoleSignal erstellt keine Gruppe für diese Fehler. Die zugehörigen Anfragen zählen weiterhin als fehlgeschlagen. |
| `enabled` | MoleSignal speichert deaktivierte Regeln, prüft sie aber nicht. Der Standardwert ist `true`. |

Die Antwort enthält die Regel mit `id`, `position`, `updatedBy` und `updatedAt`. Pro Organisation
lassen sich höchstens 100 Regeln speichern. `PUT /api/v1/apm/error-rules/order` akzeptiert `{"ids": [...]}`, setzt die angegebenen Regeln
in dieser Reihenfolge an den Anfang, hängt die übrigen Regeln an und gibt alle Regeln in der neuen Reihenfolge zurück.

Eine Änderung gilt auf dem Knoten, der sie speichert, sofort und auf den übrigen Knoten innerhalb von 30 Sekunden. Sie betrifft nur
Fehler, die ab diesem Zeitpunkt erfasst werden. Bestehende Gruppen bleiben unverändert.

## Service-Karte abrufen

`GET /api/v1/apm/map` akzeptiert die üblichen Zeitbereichsparameter sowie `environment` und `namespace` und gibt
`nodes`, `edges`, `namespaces` (der Services in der Umgebung), `environments` (alle Umgebungen) und
`truncated` (`true`, wenn nur die 400 Knoten mit der höchsten Aktivität enthalten sind) zurück.

| Feld | Hinweise |
|---|---|
| `nodes[].id` | `service:<name>`, `topic:<name>` oder `<category>:<target>` für Ziele, die Services aufrufen. |
| `nodes[].kind` | `service`, `external` oder `topic`. Ein externer Knoten enthält seine `category`. |
| `nodes[].red` | `requestCount`, `errorCount`, `errorRate` und `p95Time`: Kennzahlen zu Anfragen, die ein Service bearbeitet oder die an einen externen Knoten oder ein Topic gerichtet sind. Ein Service enthält außerdem `health`, `namespace` und `environments`. |
| `edges[].kind` | `call`, `publish` (in ein Topic) oder `consume` (aus einem Topic). |
| `change` | Änderung einer Kante oder eines Knotens gegenüber dem vorherigen gleich langen Zeitraum: `new`, wenn das Element vorher nicht vorhanden war, und `gone`, wenn es nicht mehr vorhanden ist. Das Feld fehlt, wenn im vorherigen Zeitraum keine Daten vorliegen. |

Aufrufe zwischen Services stammen aus dem Service-Graphen und enthalten den P95-Wert ihrer langsamsten Minute. Die übrigen Daten stammen
aus den APM-Zeitintervallen. `GET /api/v1/apm/map/edge` akzeptiert neben denselben Parametern die Knoten-IDs `source` und `target`
und gibt `kind`, `red`, `trend`, `operations` (`name`, `kind`, `red`), `everyCaller`
(`true`, wenn die Vorgänge die Endpunkte des aufgerufenen Service über alle Aufrufer hinweg abbilden) und `errors`, die
Fehlergruppen des aufgerufenen Service, zurück.

## Auswirkungsbereich eines Service abrufen

`GET /api/v1/apm/blast-radius` erfordert `service` und akzeptiert die üblichen Zeitbereichsparameter sowie
`environment`. Der Endpunkt liest die gesamte Karte der Umgebung unabhängig vom Namespace und
gibt `meta`, `service` (den Knoten des Service, sofern er im Zeitraum auf der Karte vorkommt),
`upstream` (Knoten, die den Service aufrufen, bis zu drei Hops entfernt) und `downstream` (Knoten, die der Service aufruft oder in die er publiziert, bis zu zwei
Hops entfernt) zurück. Jede Seite enthält bis zu 30 Knoten, zuerst die mit beeinträchtigtem Zustand. Aufrufe, die nur im vorherigen Zeitraum vorkamen,
fehlen.

| Feld | Hinweise |
|---|---|
| `id`, `kind`, `name`, `namespace`, `category` | Angaben zum Knoten gemäß der [Service-Karte](#service-karte-abrufen). |
| `hops` | Anzahl der Aufrufe zwischen dem Knoten und dem Service: `1` für einen direkten Aufrufer oder ein direktes Aufrufziel. |
| `via` | Knoten, über den der Service den Knoten erreicht oder umgekehrt. Er liegt einen Hop näher am Service. |
| `health` | Eigener Zustand eines Service. Bei Aufrufzielen ergibt sich der Zustand aus den fehlgeschlagenen Aufrufen. |
| `red`, `call` | Kennzahlen zu bearbeiteten oder eingegangenen Anfragen sowie zu Aufrufen zwischen dem Knoten und `via`. |

## Deployments melden und auflisten

`POST /api/v1/apm/deployments` akzeptiert das Deployment als JSON und gibt es mit Status `201` und den zusätzlichen Feldern `id`,
`createdBy` und `createdAt` zurück. Eine Übersicht der Felder und ihrer Grenzwerte sowie CI-Beispiele finden sich unter
[Deployments](/de/apm/deployments#deployments-aus-der-ci-melden). Die Namen von Service und Umgebung richten sich
nach den Benennungsregeln, der Umgebungszuordnung und den Aliasen der Organisation. Beim Speichern einer
Repository-Adresse maskiert der Endpunkt das Passwort. Setzen Sie bei einer Konfigurationsänderung oder einem Feature Flag
`kind` auf `configuration` bzw. `feature_flag`. `version` ist nicht erforderlich.

`GET /api/v1/apm/deployments` akzeptiert `service`, `namespace`, `environment` sowie `from` und `to` für den
Zeitbereich in Mikrosekunden. Der Endpunkt gibt bis zu 200 Deployments zurück, die neuesten zuerst. Deployments ohne
Namespace oder Umgebung erscheinen in allen Namespaces bzw. Umgebungen.

## APM-Einstellungen speichern

`GET /api/v1/apm/settings` gibt die Einstellungen der Organisation zurück. `PUT` ersetzt alle Einstellungen und
gibt die gespeicherten Werte zurück:

```json
{
  "health": {
    "errorRateWarning": 0.02,
    "errorRateCritical": 0.1,
    "p95WarningTime": 500000,
    "p95CriticalTime": 2000000
  },
  "apdexThreshold": 500000,
  "longTaskTime": 1000000,
  "namingRules": [{ "pattern": "^(checkout)-[a-z0-9]{5}$", "replacement": "$1" }],
  "environmentMap": [{ "from": "Production", "to": "production" }],
  "aliases": [{ "aliasNamespace": "shop", "alias": "checkout-v1", "namespace": "shop", "service": "checkout" }],
  "metadataRules": { "teamFromTier": "p1", "ownerFromTier": "p0", "repositoryFromTier": null }

```

Fehlt ein Feld, gilt sein Standardwert. Der Endpunkt entfernt Leerzeichen am Anfang und Ende von Namen und setzt einen leeren Alias-Namespace auf `default`. Die
Grenzwerte und die Funktion der einzelnen Einstellungen finden sich unter [APM-Einstellungen](/de/apm/settings). Gespeicherte Änderungen gelten sofort

Rufen Sie die Kardinalitätsgrenzen der Plattform mit `GET` ab und ersetzen Sie sie mit `PUT
/api/v1/settings/apm_limits`. Beide Aufrufe erfordern `sys.settings.limits.manage`. Der Request-Body enthält
`servicesPerOrgHour`, `transactionsPerServiceHour`, `dependenciesPerServiceHour`,
`operationsPerDependencyHour`, `errorGroupsPerServiceHour`, `versionsPerServiceHour` und
`instancesPerServiceHour`, jeweils mit einem Wert zwischen 1 und 100000.

## Antwortmetadaten auslesen

Jeder Endpunkt gibt ein `meta`-Objekt mit derselben Struktur zurück:

```json
{
  "range": {
    "from": 1785801600000000,
    "to": 1785888000000000
  },
  "resolution": "minute",
  "projectionStartedAt": 1785798000000000,
  "lastCompleteBucketAt": 1785887940000000,
  "dataQuality": {
    "partial": false,
    "gaps": [],
    "overflowDimensions": []
  },
  "activationBoundary": false
}
```

- Gehen Sie bei `activationBoundary: true` vor `projectionStartedAt` von unvollständiger Datenabdeckung aus.
- Interpretieren Sie `dataQuality.partial: true` als Hinweis auf unvollständige Daten, nicht als bestätigten Nullwert.
- Prüfen Sie `gaps` auf Fehler in der Warteschlange, im Repository, beim Schreiben gepufferter Daten oder beim Herunterfahren sowie auf verspätete Daten oder überschrittene Kardinalitätsgrenzen.
- Ermitteln Sie anhand von `lastCompleteBucketAt`, ob die Verarbeitung aktueller Daten noch läuft.
- Prüfen Sie `overflowDimensions`, bevor Sie eine Aufschlüsselung mit hoher Kardinalität verwenden.
