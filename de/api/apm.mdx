The APM API exposes organization-scoped aggregates derived from trace spans. All endpoints use the
`/api/v1/apm` prefix and require a bearer token.

```http
Authorization: Bearer <token>
```

An organization workspace requires the read permission of the area: `apm.services.read`, `apm.errors.read`,
`apm.error_rules.read`, `apm.definitions.read`, `apm.slos.read`, `apm.deployments.read`, or `apm.settings.read`. A platform caller can use
`sys.telemetry.read` in the protected `_sys` scope. Each call that writes names what it requires. Reporting a deployment requires
`apm.deploy`.

## Endpoints

| Method and path | Response |
|---|---|
| `GET /api/v1/apm/overview` | RED summary and trend of all services, service health and its trend, rankings, deployments, environments, instrumentation gaps, top transactions, dependencies, and errors. |
| `GET /api/v1/apm/insights` | What moved against the stretch before and the same stretch a week before, versions that did worse, where time could be won back, and the changes near each. |
| `GET /api/v1/apm/services` | Paginated service catalog with instrumentation, versions, health, RED metrics, and trace filters. |
| `GET /api/v1/apm/services/{service}` | Service summary, trend, transactions, dependencies, errors, and versions. |
| `GET /api/v1/apm/services/{service}/instances` | The instances of a service in an environment, with their version, resource attributes, and what each served. |
| `GET /api/v1/apm/services/{service}/coverage` | Whether the service's logs, metrics, profiles, and browser sessions reach MoleSignal, over the day before `to`. |
| `GET /api/v1/apm/correlation` | How well each service in view ties to its logs, metrics, traces, and changes, and the service names in logs and metrics APM does not know. |
| `GET /api/v1/apm/transactions` | Paginated transaction RED metrics and total-time ranking. |
| `GET /api/v1/apm/transactions/{transaction}` | Transaction trend, affected errors, versions, and trace filters. |
| `GET /api/v1/apm/dependencies` | Paginated caller/dependency RED metrics and total-time ranking. |
| `GET /api/v1/apm/map` | The service map of an environment and namespace: services, what they call, topics, and the calls between them. |
| `GET /api/v1/apm/map/edge` | One call of the map: its trend, what was asked along it, and the errors of a service called. |
| `GET /api/v1/apm/blast-radius` | What a service reaches along the map: what calls it and what it calls, a hop at a time. |
| `GET /api/v1/apm/errors` | Paginated sanitized backend error groups, with where the listed groups happened. |
| `GET /api/v1/apm/errors/{fingerprint}` | Error trend, affected transactions and versions, where the group happened, representative stack, and bounded samples. |
| `GET /api/v1/apm/versions/compare` | Baseline and candidate RED metrics, deltas, sufficiency status, and regressions. |
| `GET /api/v1/apm/health` | Tenant projection status, runtime health, boundaries, and gaps. |
| `GET /api/v1/apm/service-definitions` | Every service definition of the organization. |
| `PUT /api/v1/apm/service-definitions/{service}?namespace=` | Create or replace a service's definition. Requires `apm.definitions.manage`. |
| `DELETE /api/v1/apm/service-definitions/{service}?namespace=` | Delete a service's definition. Requires `apm.definitions.manage`. |
| `POST /api/v1/apm/service-definitions/{service}/key-transactions?namespace=` | Star an endpoint as a key transaction of the service, or take the star off. Requires `apm.definitions.manage`. |
| `PUT /api/v1/apm/errors/{fingerprint}/issue` | Set an error group's state, team, and assignee. Requires `apm.errors.manage`. |
| `GET /api/v1/apm/error-rules` | The organization's error grouping rules in the order they are tried. |
| `POST /api/v1/apm/error-rules` | Create a grouping rule, tried after the others. Requires `apm.error_rules.manage`. |
| `PUT /api/v1/apm/error-rules/{id}` | Replace a grouping rule. Requires `apm.error_rules.manage`. |
| `DELETE /api/v1/apm/error-rules/{id}` | Delete a grouping rule. Requires `apm.error_rules.manage`. |
| `PUT /api/v1/apm/error-rules/order` | Set the order the rules are tried in. Requires `apm.error_rules.manage`. |
| `GET /api/v1/apm/slos` | Every service level objective with its state, what it met, the error budget left, and burn rates. |
| `GET /api/v1/apm/slos/{id}` | One service level objective's status and each day of its window. |
| `POST /api/v1/apm/slos` | Create a service level objective. Requires `apm.slos.manage`. |
| `PUT /api/v1/apm/slos/{id}` | Replace a service level objective. Requires `apm.slos.manage`. |
| `DELETE /api/v1/apm/slos/{id}` | Delete a service level objective. Requires `apm.slos.delete`. |
| `POST /api/v1/apm/deployments` | Report a deployment. Requires `apm.deploy`. |
| `GET /api/v1/apm/settings` | The organization's APM settings, the defaults when none were saved. |
| `PUT /api/v1/apm/settings` | Replace the organization's APM settings. Requires `apm.settings.manage`. |

Path parameters must be URL-encoded. Use the exact `transaction` name or error `fingerprint`
returned by a list response.

## Common query parameters

| Parameter | Type | Behavior |
|---|---|---|
| `from` | integer | Range start in microseconds since the Unix epoch. Defaults to 24 hours before `to`. |
| `to` | integer | Range end in microseconds since the Unix epoch. Defaults to the current time. |
| `namespace` | string | Exact service namespace filter. |
| `service` | string | Exact service name filter. The service-detail path overrides this value. |
| `environment` | string | Exact deployment environment filter. |
| `version` | string | Exact service version filter. |
| `resolution` | enum | `auto`, `minute`, or `hour`. `auto` selects the retained resolution for the range. |
| `sort` | string | Endpoint-specific sort field. |
| `direction` | enum | `asc` or `desc`. Defaults to `desc`. |
| `limit` | integer | Page size from 1 to 200. Defaults to 50. |
| `cursor` | string | Opaque cursor from a previous list response. |
| `status` | enum | `/errors` only: `all` (default), `unresolved` (open, investigating, and resolved groups seen again), `investigating`, `resolved`, or `ignored`. |

Filters must be non-empty and no longer than 192 bytes. The range cannot exceed the configured
maximum, which defaults to 30 days (`[apm].max_query_range_days`).

### Sort fields

| Endpoint | Supported `sort` values | Default |
|---|---|---|
| `/services` | `requestCount`, `errorRate`, `p95`, `name` | `requestCount` |
| `/transactions` | `requestCount`, `errorRate`, `p95`, `total_time` | `requestCount` |
| `/dependencies` | `requestCount`, `errorRate`, `p95`, `total_time` | `total_time` |
| `/errors` | `occurrenceCount`, `errorRate`, `lastSeen` | `occurrenceCount` |

`/overview` accepts the same filters and resolution but does not paginate. Detail, comparison, and
health endpoints do not return paginated lists.

## Übersicht abfragen

<RequestExample>
```bash cURL
NOW=$(date +%s)000000
curl --get 'http://localhost:5080/api/v1/apm/overview' \
  --header "Authorization: Bearer $MS_TOKEN" \
  --data-urlencode "from=$((NOW-86400000000))" \
  --data-urlencode "to=$NOW" \
  --data-urlencode 'environment=production' \
  --data-urlencode 'resolution=auto'
```
</RequestExample>

Die Antwort enthält `red`, `trend`, `serviceHealth`, `services`, `topTransactions`, `topDependencies`, `topErrors` und `recentVersions` sowie ein gemeinsames `meta`-Objekt und:

| Feld | Hinweise |
|---|---|
| `serviceCount`, `activeServiceCount` | Services im Bereich und davon diejenigen, die mindestens eine Anfrage bedient haben. |
| `healthTrend` | Wie viele Services sich in welchem Zustand befanden, Slot für Slot: der Bereich in höchstens 48 Slots, keiner kürzer als ein Bucket. Ein Service ohne Anfragen in einem Slot zählt dort als `noTraffic`. |
| `rankings` | `slowest` (nach p95), `mostErrors` (nach Fehlerrate) und `busiest` (nach Anfragen), jeweils fünf Services. Die ersten beiden listen Services mit mindestens 20 Anfragen auf. |
| `deployments` | Versionen, die im Bereich erstmals gesehen wurden, neueste zuerst, höchstens 20, jeweils mit ihrem `red` und `verdict` wie in [den Versionen eines Services](#versionen-eines-dienstes-lesen). |
| `environments`, `availableEnvironments` | Services und Anfragen pro Umgebung in der Ansicht und jede Umgebung, in der die Services laufen, unabhängig vom Filter `environment`. |
| `instrumentation` | Services pro Sprache und SDK und wie viele kein `deployment.environment`, kein `service.version` oder keine `service.instance.id` melden. |

## Insights lesen

`GET /api/v1/apm/insights` akzeptiert die gemeinsamen Bereichs- und Filterparameter und liefert `meta` und:

| Feld | Hinweise |
|---|---|
| `now`, `previous`, `lastWeek` | Die Services in der Ansicht über den Bereich, über den gleich langen Zeitraum davor und über denselben Zeitraum eine Woche zuvor: `requestCount`, `throughput` in Anfragen pro Sekunde, `errorRate`, `p95Time` und `apdex`. Ein Zeitraum ohne Anfragen fehlt. |
| `insights` | Höchstens 30 Befunde, die dringendsten zuerst. |

Jeder Befund enthält:

| Feld | Hinweise |
|---|---|
| `kind` | `anomaly`, `regression`, `slow_dependency`, `repeated_call`, `slowQuery`, `hot_endpoint` oder `log_errors`. |
| `severity` | `critical`, `warning` oder `info` für eine Empfehlung. |
| `service` | `namespace`, `name` und `environment`. |
| `transaction`, `dependency` | Der Endpoint eines Hot-Endpoints; die Abhängigkeit eines Engpasses, eines wiederholten Aufrufs oder einer langsamen SQL-Anweisung. |
| `metric` | Was sich verändert oder verschlechtert hat: `errorRate`, `p95` oder `throughput`. |
| `value` | Der aktuelle Wert: eine Fehlerrate als Verhältnis, ein P95 in Mikrosekunden oder Anfragen pro Sekunde. Ein Engpass oder ein Hot-Endpoint gibt seinen Zeitanteil an, ein wiederholter Aufruf seine Aufrufe pro Anfrage, eine langsame SQL-Anweisung ihr P95 in Mikrosekunden und `log_errors` seine Logzeilen auf Fehlerstufe pro Minute, mit `metric` `log_errors`. |
| `previous`, `lastWeek` | Derselbe Wert über den Zeitraum davor und über denselben Zeitraum eine Woche zuvor; bei einer Regression der Wert der Version davor. |
| `since` | Wann eine Veränderung begann oder wann eine Version mit Regression erstmals gesehen wurde. |
| `version`, `previousVersion` | Die Version einer Regression und die Version davor. |
| `calls`, `p95Time` | Die Aufrufe oder Anfragen, auf denen eine Empfehlung beruht, und ihr P95. |
| `changes` | Die Änderungen in der Nähe von `since`, die nächsten zuerst: `kind`, `source` (`reported` oder `observed`), `service`, `version`, `status`, `at`, `downstream` (`true` für einen Service, den der sich verändernde Service aufruft), `commit` und `description`. |

Die Schwellenwerte stehen in [Insights und Untersuchungen](/de/apm/insights#was-erkenntnisse-finden).

## RED-Metriken lesen

Jede Zusammenfassung enthält ein `red`-Objekt mit den Anfrage-, Fehler- und Dauerwerten des Bereichs.

| Feld | Hinweise |
|---|---|
| `requestCount`, `errorCount`, `errorRate` | Anfragen, fehlgeschlagene Anfragen und das Verhältnis fehlgeschlagener zu allen Anfragen, von 0 bis 1. |
| `durationSum`, `durationAverage` | Die Gesamt- und die Durchschnittsdauer in Mikrosekunden. Der Durchschnitt ist `null` ohne Anfragen. |
| `p50Time`, `p90Time`, `p95Time`, `p99Time` | Latenzperzentile in Mikrosekunden, gelesen innerhalb des Histogramm-Buckets, in den der Rang fällt. Mit dem Standardlayout weicht ein Wert um etwa 4 % von der exakten Dauer ab. `null` ohne Anfragen. |
| `apdex` | Anfragen innerhalb des Schwellenwerts T plus die Hälfte der Anfragen innerhalb von 4T, geteilt durch alle Anfragen, von 0 bis 1. T ist der `apdexThreshold` des Services, sonst 500 ms; die Werte der Übersicht für alle Services zusammen verwenden 500 ms. Fehlgeschlagene Anfragen gelten nie als erfüllt. `null` ohne Anfragen. |
| `latencyPartial` | `true`, wenn einige Buckets ein Latenzlayout verwenden, das sich aus ihnen nicht ableiten lässt. Buckets eines früheren Layouts (`[apm.histogram].schema_version`) werden konvertiert und gezählt. Die Perzentile lassen die Buckets aus, die nicht gelesen werden können, während die Zählungen, die Summe und der Mittelwert sie weiterhin einschließen. |
| `timeoutCount`, `retryCount` | Anfragen, deren Zeit abgelaufen ist (ein Timeout-Fehlertyp, gRPC `DEADLINE_EXCEEDED`, HTTP 408 oder 504), und erneut gesendete Anfragen (`http.request.resend_count` über 0). Fehlen, wenn keine vorhanden sind. |
| `statusCodes` | Antworten nach Statuscode, als `http:<code>` (100 bis 599) oder `grpc:<code>` (0 bis 16). Ein Bucket speichert bis zu 24 Codes; weitere Codes zählen als `http:other` oder `grpc:other`. Fehlen, wenn kein Code gezählt wurde, etwa bei Aggregaten, die geschrieben wurden, bevor Codes gezählt wurden. |
| `exemplars` | Bis zu 8 Beispiel-Spans des Bereichs, die langsamsten zuerst. Ein Span wird projiziert, bevor [Tail Sampling](/de/configuration#trace-erfassung-und-tail-sampling) über seinen Trace entscheidet, daher ist `traceAvailable` normalerweise `false`; schlagen Sie den Trace nach, um zu erfahren, ob er behalten wurde. Das Aggregat bleibt gültig. |

Service- und Transaktionszusammenfassungen enthalten `apdexThreshold`, das T, mit dem der Apdex gelesen wurde.
Eine Service-Zusammenfassung enthält außerdem `health` und `healthReasons`: jeden Wert jenseits einer Grenze, als `metric`
(`errorRate` oder `p95`), `level`, `value` und `threshold`. Sie enthält `sparkline`, die Anfrageanzahl, die Fehleranzahl und das p95 jedes Buckets,
und `currentVersion` mit `currentVersionSince`, die zuletzt gesehene Version und wann sie
erstmals gesehen wurde. Das Detail eines Services oder einer Transaktion enthält `latencyDistribution`: die Histogramm-Buckets
mit Anfragen, jeweils als `lowerTime`, `upperTime` und `count`, eingegrenzt auf die
schnellste und langsamste Anfrage.

## Servicedefinitionen speichern

Eine Definition hält fest, wem ein Service gehört und wie wichtig er ist. Sie wird über `namespace` und den
Servicenamen adressiert, gilt daher in jeder Umgebung und kann existieren, bevor der Service Daten meldet.

```http
PUT /api/v1/apm/service-definitions/checkout?namespace=shop
Content-Type: application/json

{"description": "Takes orders and payments.", "teamId": "<team id>", "ownerId": "<user id>", "tier": "p0", "lifecycle": "production", "repositoryUrl": "https://github.com/acme/checkout", "tags": {"domain": "orders", "pci": ""}, "apdexThreshold": 300000, "aliases": ["order_service", "Order Center"], "dataSources": {"logs": [{"stream": "default", "filter": "service_name = 'order_service'"}], "metrics": [{"selector": "{service=\"checkout\"}"}], "dashboards": ["<dashboard id>"], "links": [{"name": "Runbook", "url": "https://wiki.example.com/checkout"}]}, "archived": false}
```

| Feld | Hinweise |
|---|---|
| `description` | Bis zu 2.000 Zeichen. |
| `teamId` | Ein Team der Organisation oder `null`. Beim Löschen des Teams wird es geleert. |
| `ownerId` | Ein Mitglied der Organisation oder `null`. |
| `tier` | `p0`, am wichtigsten, bis `p5`, oder `null`. |
| `lifecycle` | `production`, `staging`, `experimental`, `deprecated` oder `null`. |
| `repositoryUrl` | Eine URL mit `http`, `https`, `ssh`, `git` oder `git+ssh` oder `user@host:path`, ohne Leerzeichen, bis zu 2.048 Zeichen, oder `null`. Ein Passwort wird als `****` gespeichert, ebenso der Benutzerteil einer http(s)-Adresse. Wird angezeigt, wenn der Service kein Repository meldet. |
| `tags` | Bis zu 32 Tags als `{ "key": "value" }`. Ein Schlüssel besteht aus 1 bis 64 Kleinbuchstaben, Ziffern und `_ . - /`; ein Wert umfasst bis zu 128 Zeichen ohne umgebende Leerzeichen, leer, wenn nur ein Schlüssel angegeben ist. |
| `apdexThreshold` | Der Apdex-Schwellenwert T des Service, größer als 0 und höchstens 60.000.000 (eine Minute), oder `null` für 500 ms. |
| `aliases` | Bis zu 20 andere Namen, unter denen der Service in Logs, Metriken und anderen Systemen auftritt, jeweils 1 bis 128 Zeichen ohne umgebende Leerzeichen. Groß-/Kleinschreibung wird ignoriert: kein Name zweimal, niemals der eigene Name des Service und niemals der Name oder ein anderer Name eines anderen Services der Organisation. Bei Auslassung behält eine gespeicherte Definition ihre Namen. |
| `dataSources` | Wo die Daten des Service liegen: `logs` (`stream` und ein optionaler `filter`, ein boolescher SQL-Ausdruck bis zu 2.000 Zeichen), `metrics` (`selector`, ein PromQL-Selektor wie `{service="checkout"}`), `dashboards` (Dashboard-IDs) und `links` (`name` und eine `url` mit `http` oder `https`), jeweils bis zu 10. Bei Auslassung behält eine gespeicherte Definition ihre Quellen. |
| `archived` | `true` hält den Service aus der Standardansicht des Katalogs heraus. Bei Auslassung behält eine gespeicherte Definition ihren Zustand. |

Beim Speichern bleiben die `keyTransactions` der Definition erhalten, die sich jeweils einzeln ändern. Die Antwort ist die
gespeicherte Definition mit `namespace`, `name`, `keyTransactions`, `updatedBy` und `updatedAt`.
`DELETE` antwortet mit `204` oder `404`, wenn der Service keine Definition hat.

### Key Transactions mit Stern markieren

```http
POST /api/v1/apm/service-definitions/checkout/key-transactions?namespace=shop
Content-Type: application/json

{"transaction": {"name": "POST /orders", "kind": "http"}, "key": true}
```

`key: true` fügt den Endpunkt zu `keyTransactions` hinzu, `false` entfernt ihn; eine Anfrage für einen bereits
bestehenden Zustand ändert nichts. Ein Service ohne Definition erhält eine. Ein Service behält bis zu 50 Key
Transactions, und die Überlaufzeile `__other__` kann keine sein. Die Antwort ist die Definition nach
der Änderung.

## Lesen, wie gut Services mit anderen Daten verknüpft sind

`GET /api/v1/apm/correlation` akzeptiert die gemeinsamen Bereichs- und Filterparameter (`from`, `to`,
`namespace`, `environment`, `service`) und gibt für jeden Service in der Ansicht an, wie gut er mit seinen
Logs, Metriken, Traces und Änderungen verknüpft ist. Services werden über den Bereich gelesen, Logs und Metriken über die letzte
Stunde vor `to` und Änderungen über die Woche vor `to`. Aus den Streams werden nur Zählungen und Namen gelesen, niemals
Zeilen. Jeder Bericht wird fünf Minuten lang aufbewahrt.

```json
{
  "from": 1792312896695000,
  "to": 1792316496695000,
  "changesSince": 1791711696695000,
  "services": [
    {
      "service": { "namespace": "shop", "name": "checkout", "environment": "prod" },
      "logs": { "state": "reported", "streams": ["default"], "lines": 1200, "traced": 480, "sampled": 10, "matched": 9 },
      "metrics": "missing",
      "resource": { "environment": true, "version": true, "instance": true, "placement": false },
      "changes": { "count": 3, "lastAt": 1792312896695000 },
      "grades": { "traceIds": "partial", "resource": "partial", "metrics": "missing", "changes": "good" }
    }
  ],
  "unmatched": [{ "name": "checkout-svc", "signal": "logs", "streams": ["default"], "lines": 640 }]
}
```

| Feld | Bedeutung |
|---|---|
| `logs` | Die Zeilen des Service in Log-Streams mit einem Feld `service.name`, `service_name` oder `service`, höchstens acht Streams, `default` zuerst. `traced` zählt die Zeilen mit einer `trace_id`, `traceId` oder `trace.id`. Bis zu zehn jüngste Trace-IDs des Service, insgesamt 200, werden unter den Traces gesucht: `sampled` und `matched`. |
| `metrics` | Ob ein Metrik-Stream eine Zeitreihe mit dem `service.name` des Service enthält. |
| `resource` | Ob die Spans eine Umgebung, eine beliebige Version und eine Instanz melden und ob eine Instanz `host.name`, `k8s.pod.name`, `k8s.node.name` oder `container.id` meldet (`placement`). |
| `changes` | Die für den Service seit `changesSince` gemeldeten Deployments, Konfigurationsänderungen und Feature-Flags. |
| `unmatched` | Bis zu 20 Servicenamen in Logs oder Metriken, die keinem APM-Service zugeordnet sind, nach Anwendung der Namensregeln und Aliase, die meisten Zeilen zuerst. |

Jede Bewertung ist `good`, `partial`, `missing` oder `unknown`:

| Bewertung | `good` | `partial` | `missing` |
|---|---|---|---|
| `traceIds` | Mindestens 90 % der Zeilen enthalten eine Trace-ID und mindestens 80 % der gesampelten werden gefunden. | Einige Zeilen enthalten eine. | Keine Zeile enthält eine, oder der Service hat keine Zeilen geschrieben. |
| `resource` | Alle vier Werte von `resource` sind wahr. | Einige sind wahr. | Keine ist wahr. |
| `metrics` | Metriken tragen den Namen. | | Keine trägt ihn. |
| `changes` | Mindestens eine Änderung. | | Keine. |

`unknown` bedeutet, dass eine Abfrage fehlgeschlagen ist oder länger als drei Sekunden gedauert hat; ein Name, der nicht gefunden wurde, während ein Stream nicht
gelesen werden konnte, ist `unknown`, niemals `missing`. Mole Agent liest denselben Bericht mit
`get_correlation_quality`.

## Abdeckung eines Service lesen

`GET /api/v1/apm/services/{service}/coverage` akzeptiert `namespace` und `environment`, beide erforderlich, sowie
optional `to`, das Ende des betrachteten Bereichs in Mikrosekunden (standardmäßig jetzt). Die Abfrage betrachtet den Tag
vor `to` und bewahrt jede Antwort fünf Minuten lang auf.

```json
{
  "from": 1792230096695000,
  "to": 1792316496695000,
  "logs": { "state": "reported", "found": ["default"] },
  "metrics": { "state": "missing" },
  "profiles": { "state": "reported", "found": ["cpu", "alloc_space"] },
  "rum": { "state": "unknown" }
}
```

| Signal | `reported`, wenn | `found` |
|---|---|---|
| `logs` | Ein Log-Stream mit einem Feld `service.name`, `service_name` oder `service` enthält eine Zeile des Service. Es werden höchstens acht Streams betrachtet, `default` zuerst. | Die Streams. |
| `metrics` | `count(last_over_time({"service.name"="<service>"}[1h]))` ist bei `to` größer als null. | Die Anzahl der Zeitreihen. |
| `profiles` | Der Profil-Stream enthält ein Profil des Service. | Die Profiltypen. |
| `rum` | Eine Browseraktion enthielt einen der fünf neuesten Sample-Traces des Service. | Die Sitzung. |

`missing` bedeutet, dass die Abfrage nichts gefunden hat. `unknown` bedeutet, dass die Abfrage fehlgeschlagen ist oder länger als drei
Sekunden gedauert hat. `rum` ist niemals `missing`: eine Stichprobe von Traces kann zeigen, dass Sitzungen einen Service erreichen, nicht, dass
keine ihn erreichen.

## Lesen, womit ein Service läuft

`GET /api/v1/apm/services` und `GET /api/v1/apm/services/{service}` geben jeder Service-Zusammenfassung ein
`profile`, das aus den Instanzen gelesen wird, die im Bereich gemeldet haben, und zwar nur aus denen der `version`, wenn der
Parameter gesetzt ist. Jede Liste ist danach sortiert, wie viele Instanzen sich einen Wert teilen, höchstens fünf, als
`{ "value": "1.8.2", "instances": 4 }`.

| Feld | Hinweise |
|---|---|
| `instanceCount`, `hostCount` | Instanzen und verschiedene `host.name`-Werte. |
| `versions` | Die Versionen, auf denen die Instanzen liefen. Ein Rollout listet zwei. |
| `languages`, `runtimes`, `frameworks` | `telemetry.sdk.language`; `process.runtime.name` mit seiner Version; das Framework, das die Instrumentierungsbibliothek der Entry-Spans nennt. |
| `regions`, `clusters`, `k8sNamespaces`, `workloads` | `cloud.region`, `k8s.cluster.name`, `k8s.namespace.name` und `k8s.deployment.name` oder `k8s.statefulset.name`. |
| `repositories`, `commits` | `vcs.repository.url.full` oder `git.repository_url`, ohne Zugangsdaten gespeichert; `vcs.ref.head.revision` oder `git.commit.sha`. |
| `entryKinds` | `http`, `rpc`, `messaging`, `span`: die Arten von Einstieg, die der Service bedient. |

`GET /api/v1/apm/services/{service}/instances` listet die Instanzen einzeln auf, die zuletzt
gesehenen zuerst, höchstens 500. Der Endpunkt akzeptiert `namespace`, `environment` sowie optional `version`, `from` und
`to`; ohne Service und Umgebung antwortet er mit `400`. Jedes Element hat `instanceId` (die
`service.instance.id`, sonst `k8s.pod.name`, sonst `host.name`), `version`, `firstSeenAt`,
`lastSeenAt`, `attributes`, eine Zuordnung der zuletzt von der Instanz gemeldeten Attribute, und was sie
im Bereich bedient hat: `red`, wie in Zusammenfassungen mit Apdex am Schwellenwert des Service, und `sparkline`. Über die
Instanzgrenze hinaus werden die übrigen in einem Element gezählt, dessen `instanceId` `__other__` ist. Eine Instanz, die
im Bereich bedient hat, bevor etwas über sie gespeichert wurde, wird mit leeren `attributes` aufgeführt.

## Status einer Fehlergruppe setzen

```http
PUT /api/v1/apm/errors/<fingerprint>/issue
Content-Type: application/json

{"status": "investigating", "assigneeId": "<user id>", "teamId": "<team id>", "lastSeenAt": 1792316496695000}
```

`status` ist `open`, `investigating`, `resolved` oder `ignored`. `assigneeId` ist ein Mitglied der
Organisation oder `null`, und `teamId` ein Team der Organisation oder `null`. `lastSeenAt`, optional, gibt an, wann die Gruppe zuletzt gesehen wurde, in Mikrosekunden. Beim Setzen von
`resolved` wird die Zeit als `resolvedAt` gespeichert.

Fehlerzusammenfassungen tragen den Status als `issue` oder `null`, solange keiner gesetzt ist. `issue.regressed`
ist `true`, wenn eine als `resolved` markierte Gruppe nach `resolvedAt` erneut auftrat; der Filter `unresolved` behält
solche Gruppen. Das Setzen des Status eines Fingerabdrucks, den die Projektion nicht kennt, antwortet mit `404`.

## Service Level Objectives pflegen

Ein Service Level Objective (SLO) verspricht einen Anteil guter Anfragen eines Dienstes in einer Umgebung oder
eines seiner Endpunkte über ein rollierendes Fenster. Siehe
[Service Level Objectives](/de/apm#service-level-ziele) für die Bedeutung der einzelnen Werte.

```http
POST /api/v1/apm/slos
Content-Type: application/json

{"name": "Checkout availability", "namespace": "shop", "service": "checkout", "environment": "production", "transaction": null, "kind": "availability", "objective": 0.999, "windowDays": 30}
```

| Feld | Hinweise |
|---|---|
| `name` | Erforderlich, bis zu 255 Bytes. |
| `description` | Optional, bis zu 2.000 Bytes. |
| `namespace`, `service`, `environment` | Erforderlich. Der Dienst, wie APM ihn benennt. Ein Dienst ohne `service.namespace` liegt im Namespace `default`. |
| `transaction` | Ein Endpunkt, `{ "name": "POST /orders", "kind": "http" }`, oder `null` für den gesamten Dienst. |
| `kind` | `availability`: Eine Anfrage ist gut, wenn sie nicht fehlgeschlagen ist. `latency`: Eine Anfrage ist gut, wenn sie nicht fehlgeschlagen ist und höchstens `latencyThreshold` gedauert hat. |
| `latencyThreshold` | Erforderlich und positiv für `latency`. Muss bei `availability` `null` sein oder fehlen. |
| `objective` | Der Anteil guter Anfragen, größer als 0 und kleiner als 1, etwa `0.999`. |
| `windowDays` | `7`, `28` oder `30`. |

`POST` und `PUT` antworten mit dem gespeicherten SLO samt `id`, `createdBy`, `createdAt`, `updatedBy` und
`updatedAt`. `GET /api/v1/apm/slos` liefert jedes SLO der Organisation als Status. Übergeben Sie
`namespace`, `service` und `environment` gemeinsam, um die SLOs eines einzelnen Dienstes zu erhalten. Das Fenster endet
zum Zeitpunkt des Aufrufs, daher gelten die üblichen Bereichsparameter nicht.

| Statusfeld | Hinweise |
|---|---|
| `slo` | Das SLO wie gespeichert. |
| `state` | `healthy`, `at_risk`, `breached` oder `noData`. |
| `sli` | Gute Anfragen bezogen auf alle Anfragen im Fenster, oder `null` ohne Anfragen. |
| `goodRequests`, `totalRequests` | Die Zählwerte hinter `sli`. Ein Latenz-SLO schätzt `goodRequests` aus den Latenz-Histogrammen, daher kann der Wert gebrochen sein. |
| `budgetRemaining` | `1 - (1 - sli) / (1 - objective)`, unter null, sobald das Ziel verfehlt ist, oder `null` ohne Anfragen. |
| `burnRates` | `oneHour`, `sixHours` und `oneDay`: `(1 - sli) / (1 - objective)` über die letzte Stunde, sechs Stunden und 24 Stunden, oder `null` ohne Anfragen. |

`GET /api/v1/apm/slos/{id}` liefert `status` und `history`, einen Eintrag für jeden UTC-Tag des Fensters
mit Anfragen, den ältesten zuerst. Jeder Eintrag hat `dayStart` in Mikrosekunden, `sli`, `goodRequests`,
und `totalRequests`.

`DELETE` antwortet mit `204`. Es antwortet mit `409`, solange Alarmregeln das SLO überwachen, etwa seine Burn-Rate-
Alarme: Löschen Sie diese Regeln zuerst. Alarmregeln zu einem SLO sind APM-Regeln mit der Metrik
`slo_burn_rate`. Siehe [Regel erstellen](/de/api/alerting/create-rule#apm-regeln).

## Eine Transaktion eindeutig identifizieren

Zwei Transaktionsarten können denselben Namen tragen. Übergeben Sie den optionalen Parameter `kind`, um eine auszuwählen:

```http
GET /api/v1/apm/transactions/POST%20%2Fcheckout?kind=http&service=checkout
```

Die unterstützten `kind`-Werte sind `http`, `rpc`, `messaging`, `span` und `other`. Ein Name, den mehrere
Dienste oder Arten teilen, führt zu `400` mit `APM transaction identity is ambiguous; provide service,
namespace, environment, and kind`.

## Versionen vergleichen

Geben Sie unterschiedliche Werte für `baseline` und `candidate` an. Fügen Sie einen `service`-Filter hinzu, um einen einzelnen Dienst zu vergleichen.

```bash
curl --get 'http://localhost:5080/api/v1/apm/versions/compare' \
  --header "Authorization: Bearer $MS_TOKEN" \
  --data-urlencode 'service=checkout' \
  --data-urlencode 'environment=production' \
  --data-urlencode 'baseline=2.3.1' \
  --data-urlencode 'candidate=2.4.0'
```

Die Antwort enthält die Seiten `baseline` und `candidate`, jeweils mit `version`, `sampleCount` und
`red`, dazu ein `delta`, ein `status`, `regressedTransactions` und `regressedErrors`. Jede
Regressionsliste enthält höchstens 20 Einträge.

| Feld | Hinweise |
|---|---|
| `sufficientData` | `true` nur, wenn beide Versionen den konfigurierten Stichprobenschwellwert erreichen, standardmäßig 1.000 Anfragen pro Version (`[apm.version_comparison].min_requests_per_version`). |
| `status` | `insufficient_data`, `regressed`, `improved` oder `neutral`. `regressed`, wenn die Fehlerrate des Kandidaten um mindestens einen Prozentpunkt und auf mindestens das 1,5-Fache der Baseline gestiegen ist oder sein p95 um mindestens ein Fünftel und 50 ms; `improved`, wenn einer von beiden in diesem Maß gefallen ist und keiner so gestiegen ist; `insufficient_data`, wenn `sufficientData` gleich `false` ist. |
| `delta` | `requestCountAbsolute` und `requestCountRelative`, `errorRateAbsolute` und `errorRateRelative` sowie `p95AbsoluteTime` und `p95Relative`. Ein relativer Wert ist `null`, wenn die Baseline null ist oder fehlt. |

Ein fehlender `candidate` oder `baseline` oder zwei identische Versionen führen zu `400`.

## Versionen eines Dienstes lesen

`GET /api/v1/apm/services/{service}` liefert `versions`, die im Bereich gesehenen Versionen. Jede enthält
`red`, was sie im Bereich ausgeliefert hat, und `verdict`, wie sie sich gegenüber der Version desselben Dienstes
verhielt, die vor ihr zuerst gesehen wurde, bewertet wie bei [einem Vergleich](#versionen-vergleichen):

| Feld | Hinweise |
|---|---|
| `previous` | Die Version, gegen die sie verglichen wird. |
| `status` | `regressed`, `improved`, `neutral` oder `insufficient_data`. |
| `worse` | Was sich verschlechtert hat, wenn `status` gleich `regressed` ist: `errorRate`, `latency` oder beides. |
| `delta` | Wie bei einem Vergleich, mit der früheren Version als Baseline. |

Die zuerst gesehene Version hat kein `verdict`. Ein Versionsfilter in der Anfrage schränkt die
Werte nicht ein: Jede Version wird aus dem gesamten Dienst gelesen.

## Lesen, wo Fehler aufgetreten sind

`GET /api/v1/apm/errors` liefert neben der Seite eine `breakdown` über alle Gruppen, die der `status`-Filter
behält (nicht nur die der Seite), und `GET /api/v1/apm/errors/{fingerprint}` liefert die `breakdown` der
Gruppe. Sie enthält `versions`, `environments` und `languages`, jeweils eine Liste aus `value` und `count`,
den Vorkommnissen, das größte zuerst. Ein Wert ist leer, wenn die Spans ihn nicht gemeldet haben; nach den ersten
sieben Werten zählen die übrigen zusammen als `__other__`. Die Sprache ist die des Dienstes
`telemetry.sdk.language`.

## Regeln zur Fehlergruppierung pflegen

Eine Regel gruppiert Fehler beim Eintreffen anders als nach Typ, Frame und Endpunkt. Regeln werden
in der Reihenfolge von `position` geprüft, und die erste passende gilt.

```http
POST /api/v1/apm/error-rules
Content-Type: application/json

{"name": "Upstream timeouts", "serviceNamespace": "shop", "serviceName": "checkout",
 "errorType": "*Timeout*", "message": "", "frame": "", "endpoint": "", "action": "merge", "enabled": true}
```

| Feld | Hinweise |
|---|---|
| `name` | Bis zu 128 Zeichen. Eine zusammengeführte Gruppe wird danach benannt. |
| `serviceNamespace`, `serviceName` | Der Dienst, für den die Regel gilt. Ein leerer `serviceName` bedeutet jeden Dienst; ein Namespace benötigt einen Namen. |
| `errorType`, `message`, `frame`, `endpoint` | Muster für den Fehlertyp, die Exception-Meldung, den ersten Anwendungs-Frame und den Endpunkt, jeweils bis zu 256 Zeichen. Ein Muster gleicht den gesamten Text ab, ohne auf Groß-/Kleinschreibung zu achten, mit `*` für beliebigen Text. Ein leeres Muster passt auf alles; mindestens eines muss gesetzt sein. |
| `action` | `merge`: Die passenden Fehler eines Dienstes werden zu einer Gruppe. `ignore`: Sie bilden keine Gruppe, und ihre Anfragen zählen weiterhin als fehlgeschlagen. |
| `enabled` | Eine deaktivierte Regel bleibt erhalten, wird aber nicht geprüft. Standardwert ist `true`. |

Die Antwort ist die Regel mit ihrer `id`, `position`, `updatedBy` und `updatedAt`. Eine Organisation
hält höchstens 100 Regeln. `PUT /api/v1/apm/error-rules/order` nimmt `{"ids": [...]}`, stellt diese Regeln
in dieser Reihenfolge an den Anfang und die übrigen dahinter und liefert die Regeln in ihrer neuen Reihenfolge.

Eine Änderung gilt sofort auf dem Knoten, der sie speichert, und innerhalb von 30 Sekunden auf den anderen, für die
ab dann gesehenen Fehler; bereits gebildete Gruppen bleiben, wie sie sind.

## Die Service-Map lesen

`GET /api/v1/apm/map` nimmt den gemeinsamen `range`-Parameter sowie `environment` und `namespace` entgegen und liefert `nodes`, `edges`, `namespaces` (der Services in der Umgebung), `environments` (alle) und `truncated` (`true`, wenn nur die 400 verkehrsreichsten Knoten beibehalten werden).

| Feld | Hinweise |
|---|---|
| `nodes[].id` | `service:<name>`, `topic:<name>` oder `<category>:<target>` für das, was Services aufrufen. |
| `nodes[].kind` | `service`, `external` oder `topic`. Ein externer Knoten trägt seine `category`. |
| `nodes[].red` | `requestCount`, `errorCount`, `errorRate` und `p95Time`: was ein Service bedient hat oder was von einem externen Knoten oder einem Topic angefragt wurde. Ein Service trägt außerdem `health`, `namespace` und `environments`. |
| `edges[].kind` | `call`, `publish` (an ein Topic) oder `consume` (von einem Topic). |
| `change` | An einer Kante oder einem Knoten, im Vergleich zum gleich langen Zeitraum davor: `new`, wenn er vorher nicht vorhanden war, `gone`, wenn er es nicht mehr ist. Fehlt, wenn vorher nichts vorhanden war. |

Aufrufe zwischen Services stammen aus dem Service-Graph, mit dem P95 ihrer langsamsten Minute; der Rest aus den APM-Buckets. `GET /api/v1/apm/map/edge` nimmt neben denselben Parametern die Knoten-IDs `source` und `target` entgegen und liefert `kind`, `red`, `trend`, `operations` (`name`, `kind`, `red`), `everyCaller` (`true`, wenn die Operationen die Endpunkte des aufgerufenen Service von allen Aufrufern sind) und `errors`, die Fehlergruppen des aufgerufenen Service.

## Den Blast Radius eines Service lesen

`GET /api/v1/apm/blast-radius` nimmt `service` entgegen (erforderlich) sowie den gemeinsamen `range`-Parameter und `environment`. Der Endpunkt liest die gesamte Map der Umgebung, unabhängig vom Namespace, und liefert `meta`, `service` (der eigene Knoten des Service, fehlt, wenn die Map ihn nirgends im Zeitraum enthält), `upstream` (was ihn aufruft, bis zu drei Hops) und `downstream` (was er aufruft oder wohin er publiziert, bis zu zwei Hops). Jede Seite enthält höchstens 30 Knoten, die ungesunden zuerst; Aufrufe, die im Vergleich zum Zeitraum davor verschwunden sind, bleiben außen vor.

| Feld | Hinweise |
|---|---|
| `id`, `kind`, `name`, `namespace`, `category` | Der Knoten, wie ihn [die Service-Map](#die-service-map-lesen) benennt. |
| `hops` | Aufrufe zwischen dem Knoten und dem Service: `1` für einen direkten Aufrufer oder Aufgerufenen. |
| `via` | Der Knoten, über den er erreicht wird, ein Hop näher am Service. |
| `health` | Die eigene Health eines Service. Für Aufgerufenes die Health, die sich aus seinen fehlgeschlagenen Aufrufen ergibt. |
| `red`, `call` | Was er bedient hat oder angefragt wurde, und die Aufrufe zwischen ihm und `via`. |

## Deployments melden

`POST /api/v1/apm/deployments` nimmt das Deployment als JSON entgegen und antwortet mit `201` und dem Deployment, ergänzt um `id`, `createdBy` und `createdAt`. Die Felder, ihre Grenzen und CI-Beispiele stehen in [Deployments](/de/apm/deployments#deployments-aus-der-ci-melden). Service und Umgebung werden so benannt, wie die Namensregeln, das Environment-Mapping und die Aliase der Organisation sie lesen. Eine Repository-Adresse wird mit maskiertem Passwort gespeichert. Eine Konfigurationsänderung oder ein Feature Flag setzt `kind` auf `configuration` bzw. `feature_flag` und benötigt keine `version`.

Eine Skalierungs- oder Infrastrukturänderung setzt `kind` auf `scaling` bzw. `infrastructure`. Gemeldete Änderungen listet [`GET /api/v1/changes`](/de/api/changes) auf.

## APM-Einstellungen pflegen

`GET /api/v1/apm/settings` liefert die Einstellungen der Organisation; `PUT` ersetzt sie vollständig und liefert die gespeicherten Einstellungen zurück:

```json
{
  "health": {
    "errorRateWarning": 0.02,
    "errorRateCritical": 0.1,
    "p95WarningTime": 500000,
    "p95CriticalTime": 2000000
  },
  "apdexThreshold": 500000,
  "longTaskTime": 1000000,
  "namingRules": [{ "pattern": "^(checkout)-[a-z0-9]{5}$", "replacement": "$1" }],
  "environmentMap": [{ "from": "Production", "to": "production" }],
  "aliases": [{ "aliasNamespace": "shop", "alias": "checkout-v1", "namespace": "shop", "service": "checkout" }],
  "metadataRules": { "teamFromTier": "p1", "ownerFromTier": "p0", "repositoryFromTier": null }
}
```

Ein weggelassenes Feld erhält seinen Standardwert. Namen werden getrimmt, und ein leerer Alias-Namespace ist `default`. Die Grenzen und die Wirkung jeder Einstellung stehen in [APM settings](/de/apm/settings). Ein Speichern wirkt sofort auf dem Knoten, der es ausführt, und innerhalb von 30 Sekunden auf den anderen.

Die Kardinalitätsgrenzen der Plattform werden mit `GET` und `PUT
/api/v1/settings/apm_limits` gelesen und ersetzt; beide erfordern `sys.settings.limits.manage`. Der Body enthält
`servicesPerOrgHour`, `transactionsPerServiceHour`, `dependenciesPerServiceHour`,
`operationsPerDependencyHour`, `errorGroupsPerServiceHour`, `versionsPerServiceHour` und
`instancesPerServiceHour`, jeweils von 1 bis 100000.

## Response-Metadaten lesen

Jeder Endpunkt liefert ein gemeinsames `meta`-Objekt:

```json
{
  "range": {
    "from": 1785801600000000,
    "to": 1785888000000000
  },
  "resolution": "minute",
  "projectionStartedAt": 1785798000000000,
  "lastCompleteBucketAt": 1785887940000000,
  "dataQuality": {
    "partial": false,
    "gaps": [],
    "overflowDimensions": []
  },
  "activationBoundary": false
}
```

- Behandeln Sie `activationBoundary: true` als unvollständige Abdeckung vor `projectionStartedAt`.
- Behandeln Sie `dataQuality.partial: true` als unvollständige Daten, nicht als vollständige Null.
- Prüfen Sie `gaps` auf Fehler bei Queue, Repository, Flush, Late Data, Kardinalität oder Shutdown.
- Nutzen Sie `lastCompleteBucketAt`, um festzustellen, ob aktuelle Daten noch finalisiert werden.
- Prüfen Sie `overflowDimensions`, bevor Sie sich auf eine Aufschlüsselung mit hoher Kardinalität verlassen.

## Fehler

| Status | Ursache |
|---|---|
| `400` | Ein Parameter ist ungültig: ein nicht unterstütztes `sort` (`unsupported APM sort field`), ein `limit` außerhalb von 1 bis 200, ein leerer oder zu großer Filter (`invalid APM service filter`), ein Zeitraum länger als das Maximum (`APM query range exceeds configured maximum`), ein Ende vor dem Start (`APM range end precedes start`), eine unbekannte `direction` oder `resolution`, ein SLO, das die obigen Prüfungen nicht besteht (`SLO objective must be between 0 and 1, exclusive`), oder ein SLO-Listenfilter ohne alle von `namespace`, `service` und `environment`. |
| `403` | Dem Token fehlt die Berechtigung des Aufrufs. |
| `404` | Der Fehler-Fingerprint, die Transaktion, der Service oder das SLO existiert im Zeitraum nicht. |
| `409` | Alert-Regeln überwachen noch das zu löschende SLO. |
