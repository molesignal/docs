Beide Aufrufe erfordern `alerts.incidents.read` für den Incident.

## Ähnliche Incidents

```http
GET /api/v1/alerts/incidents/{id}/similar
```

Findet die Incidents, die in derselben Organisation in den 90 Tagen vor der Auslösung dieses Incidents eröffnet wurden und
ihm am ähnlichsten sind: höchstens 5, höchste Punktzahl zuerst, bei Gleichstand neuere zuerst. Incidents, die in ihn zusammengeführt wurden, und der
Incident, in den er zusammengeführt wurde, bleiben unberücksichtigt. Die Punktzahl ist die Summe der Zeilen unten, und ein Incident muss
mindestens 2 erreichen, um aufgeführt zu werden:

| Grundlage | Wert in `reasons` | Punktzahl |
|---|---|---|
| Derselbe Alert-Fingerprint | `fingerprint` | 5 |
| Dieselbe Regel (wenn der Fingerprint abweicht) | `rule` | 3 |
| Gemeinsame Services | `services` | Überschneidung × 2 |
| Ähnliche Labels: Die gemeinsamen Schlüssel-Wert-Paare machen auf beiden Seiten mindestens 0,3 aller Paare aus | `labels` | Anteil × 2 |
| Ein ähnlicher Titel: Trigramm-Ähnlichkeit von mindestens 0,3, berechnet wie bei PostgreSQL `pg_trgm`, Chinesisch eingeschlossen | `title` | Ähnlichkeit × 2 |
| An dasselbe Team weitergeleitet | `team` | 1 |

Die Überschneidung ist die Schnittmenge beider Seiten geteilt durch ihre Vereinigung.

<RequestExample>
```bash cURL
curl http://localhost:5080/api/v1/alerts/incidents/$INCIDENT_ID/similar \
  -H "authorization: Bearer $MS_TOKEN"
```
</RequestExample>

<ResponseExample>
```json 200
{
  "incidents": [
    {
      "id": "3KEDNEyqouYJeBDTLTMTBui7XHW",
      "summary": "High error rate · checkout",
      "severity": "critical",
      "status": "resolved",
      "createdAt": 1789400000000000,
      "resolvedAt": 1789401800000000,
      "resolvedBy": "<user-id>",
      "score": 7.6,
      "reasons": ["fingerprint", "services", "labels", "team"],
      "notes": 2,
      "rootCause": "Connection pool exhausted after the payments client stopped releasing connections."
    }
  ]
}
```
</ResponseExample>

| Feld | Beschreibung |
|---|---|
| `score`, `reasons` | Die Punktzahl und ihre Herkunft; siehe Tabelle oben. |
| `resolvedBy` | Wer ihn gelöst hat; `null`, wenn seine Regel von selbst wiederhergestellt wurde oder er noch aktiv ist. |
| `notes` | Wie viele [Notizen](/de/api/alerting/add-incident-note) er hat. |
| `rootCause` | Der erste Satz, der in seiner [KI-Ursachenanalyse](/de/api/alerting/incident-rca) eine Aussage enthält (Überschriften und Leerzeilen übersprungen), höchstens 200 Zeichen; wird weggelassen, wenn keine Analyse vorliegt. |

## Letzte Änderungen

```http
GET /api/v1/alerts/incidents/{id}/changes
```

Listet die [gemeldeten Änderungen](/de/apm/deployments#deployments-aus-der-ci-melden) von 30
Minuten vor der Auslösung des Incidents bis 10 Minuten danach auf, für die Services des Incidents (seine betroffenen
Services und sein `service`-Label) und die ihnen nachgelagerten Services: höchstens 20, älteste zuerst.
Nachgelagerte Services stammen aus der APM-Service-Map, für höchstens die ersten 3 Services des Incidents; ohne
eine Service-Map zählen nur die eigenen Services des Incidents. Wenn die Regel des Incidents in den 24 Stunden
vor der Auslösung bearbeitet wurde, wird auch eine `rule`-Änderung aufgeführt.

<RequestExample>
```bash cURL
curl http://localhost:5080/api/v1/alerts/incidents/$INCIDENT_ID/changes \
  -H "authorization: Bearer $MS_TOKEN"
```
</RequestExample>

<ResponseExample>
```json 200
{
  "from": 1789998200000000,
  "to": 1790000600000000,
  "changes": [
    {
      "kind": "deployment",
      "at": 1789999100000000,
      "service": "payments",
      "downstream": true,
      "version": "v2026.10.28",
      "status": "succeeded",
      "commit": "9f2c1e4",
      "author": "dana",
      "link": "https://ci.example.com/pipelines/4821"
    },
    {
      "kind": "rule",
      "at": 1789960000000000,
      "downstream": false,
      "ruleId": "3KEDBLvTYO6DnWi8H9S9MNLpPT7",
      "ruleName": "Checkout error rate"
    }
  ]
}
```
</ResponseExample>

| Feld | Beschreibung |
|---|---|
| `from`, `to` | Der betrachtete Zeitraum in Unix-Mikrosekunden. |
| `kind` | `deployment`, `configuration`, `feature_flag` oder `rule` (die Regel des Incidents wurde bearbeitet). |
| `downstream` | `true`, wenn die Änderung zu einem nachgelagerten Service gehört, nicht zu einem der eigenen Services des Incidents. |
| `version`, `status`, `commit`, `description`, `author` | Was der Bericht enthielt; wird weggelassen, wenn nicht vorhanden. |
| `link` | Die gemeldete Pipeline-Adresse oder andernfalls die Pull-Request-Adresse. |
| `ruleId`, `ruleName` | Die Regel einer `rule`-Änderung. |

**Fehler**

| Status | Grund |
|---|---|
| `403` | Dem Token fehlt `alerts.incidents.read`, oder es kann nicht auf diesen Incident zugreifen. |
| `404` | Der Incident existiert nicht. |

## Geschäftliche Auswirkung

```http
GET /api/v1/alerts/incidents/{id}/business-impact
```

Listet für jeden [Business-Key](/de/business-context), den die Spans tragen, die Werte auf, deren Anfragen an die
Services des Incidents am häufigsten fehlgeschlagen sind, von 30 Minuten vor der Auslösung des Incidents bis 10 Minuten danach
(spätestens bis jetzt): höchstens 5 Werte je Key, zuerst die meisten fehlgeschlagenen Anfragen, dann die meisten Anfragen. Ein
Incident ohne Services liest die Anfragen jedes Service. Anfragen sind die Spans, in denen ein Service eine
Anfrage entgegengenommen hat.

<RequestExample>
```bash cURL
curl http://localhost:5080/api/v1/alerts/incidents/$INCIDENT_ID/business-impact \
  -H "authorization: Bearer $MS_TOKEN"
```
</RequestExample>

<ResponseExample>
```json 200
{
  "from": 1789998200000000,
  "to": 1790000600000000,
  "services": ["checkout"],
  "declared": true,
  "keys": [
    {
      "key": "tenant",
      "label": "Tenant",
      "field": "tenant.id",
      "more": true,
      "values": [
        { "value": "acme", "requests": 300, "errors": 120, "important": true },
        { "value": "globex", "requests": 90, "errors": 4, "important": false }
      ]
    }
  ]
}
```
</ResponseExample>

| Feld | Beschreibung |
|---|---|
| `services` | Die Services des Incidents, deren Anfragen gelesen wurden. Leer, wenn keine genannt sind. |
| `declared` | `false`, wenn kein Business-Key ein Span-Feld benennt: `keys` ist dann leer. |
| `field` | Das Span-Feld, aus dem der Key gelesen wurde. |
| `important` | Der Wert gehört zu denen, die die Organisation für den Key als wichtig markiert hat. |
| `more` | Mehr Werte hatten Anfragen, als aufgeführt sind. |

Ein Key, dessen Feld im Traces-Stream fehlt oder verschlüsselt vorliegt, oder zu dem keine Anfrage einen Wert hatte, wird weggelassen.

**Fehler**

| Status | Grund |
|---|---|
| `403` | Dem Token fehlt `alerts.incidents.read`, oder es kann nicht auf diesen Incident zugreifen, oder ihm fehlen sowohl `streams.query` als auch `sys.telemetry.read`. |
| `404` | Der Incident existiert nicht. |
