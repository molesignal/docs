Beide Aufrufe erfordern die Berechtigung `alerts.incidents.read` für den Incident.

## Ähnliche Incidents

```http
GET /api/v1/alerts/incidents/{id}/similar
```

Findet in derselben Organisation die ähnlichsten Incidents, die in den 90 Tagen vor der Auslösung dieses Incidents eröffnet wurden:
höchstens 5, mit der höchsten Punktzahl zuerst. Bei Gleichstand stehen neuere Incidents zuerst. Die Suche schließt sowohl Incidents aus, die mit diesem Incident zusammengeführt wurden, als auch den
Incident, in den dieser Incident überführt wurde. Die Punktzahl ist die Summe der Werte in der folgenden Tabelle. Die Liste enthält nur Incidents mit
mindestens 2 Punkten:

| Kriterium | Wert in `reasons` | Punktzahl |
|---|---|---|
| Gleicher Alert-Fingerprint | `fingerprint` | 5 |
| Gleiche Regel (bei unterschiedlichem Fingerprint) | `rule` | 3 |
| Gemeinsame Services | `services` | Überschneidung × 2 |
| Ähnliche Labels: Der Anteil der gemeinsamen Schlüssel-Wert-Paare beträgt bei beiden Incidents mindestens 0,3 | `labels` | Anteil × 2 |
| Ähnlicher Titel: Trigrammähnlichkeit von mindestens 0,3, berechnet wie in PostgreSQL `pg_trgm`, auch für chinesische Titel | `title` | Ähnlichkeit × 2 |
| Weiterleitung an dasselbe Team | `team` | 1 |

Die Überschneidung ist das Verhältnis der Größe der Schnittmenge zur Größe der Vereinigungsmenge.

<RequestExample>
```bash cURL
curl http://localhost:5080/api/v1/alerts/incidents/$INCIDENT_ID/similar \
  -H "authorization: Bearer $MS_TOKEN"
```
</RequestExample>

<ResponseExample>
```json 200
{
  "incidents": [
    {
      "id": "3KEDNEyqouYJeBDTLTMTBui7XHW",
      "summary": "High error rate · checkout",
      "severity": "critical",
      "status": "resolved",
      "createdAt": 1789400000000000,
      "resolvedAt": 1789401800000000,
      "resolvedBy": "<user-id>",
      "score": 7.6,
      "reasons": ["fingerprint", "services", "labels", "team"],
      "notes": 2,
      "rootCause": "Connection pool exhausted after the payments client stopped releasing connections."
    }
  ]
}
```
</ResponseExample>

| Feld | Beschreibung |
|---|---|
| `score`, `reasons` | Punktzahl und die Kriterien, aus denen sie sich ergibt (siehe Tabelle oben). |
| `resolvedBy` | Gibt an, wer den Incident behoben hat. Der Wert ist `null`, wenn die Regel von selbst wieder in den Normalzustand zurückgekehrt ist oder der Incident noch aktiv ist. |
| `notes` | Anzahl der [Notizen](/de/api/alerting/add-incident-note) zum Incident. |
| `rootCause` | Erster inhaltlicher Satz der [KI-Ursachenanalyse](/de/api/alerting/incident-rca), ohne Überschriften und Leerzeilen, maximal 200 Zeichen. Ohne Analyse fehlt das Feld. |

## Letzte Änderungen

```http
GET /api/v1/alerts/incidents/{id}/changes
```

Listet die [gemeldeten Änderungen](/de/apm/deployments#deployments-aus-der-ci-melden) im Zeitraum von 30
Minuten vor der Auslösung des Incidents bis 10 Minuten danach auf. Die Liste umfasst die Services des Incidents (die betroffenen
Services und den Service aus dem Label `service`) sowie die nachgelagerten Services: höchstens 20 Änderungen, die ältesten zuerst.
Die APM-Service-Map liefert die nachgelagerten Services für höchstens die ersten 3 Services des Incidents. Ohne
Service-Map zählen nur die Services des Incidents selbst. Wenn sich die Regel des Incidents in den 24 Stunden
vor der Auslösung geändert hat, enthält die Liste auch eine Änderung vom Typ `rule`.

<RequestExample>
```bash cURL
curl http://localhost:5080/api/v1/alerts/incidents/$INCIDENT_ID/changes \
  -H "authorization: Bearer $MS_TOKEN"
```
</RequestExample>

<ResponseExample>
```json 200
{
  "from": 1789998200000000,
  "to": 1790000600000000,
  "changes": [
    {
      "kind": "deployment",
      "at": 1789999100000000,
      "service": "payments",
      "downstream": true,
      "version": "v2026.10.28",
      "status": "succeeded",
      "commit": "9f2c1e4",
      "author": "dana",
      "link": "https://ci.example.com/pipelines/4821"
    },
    {
      "kind": "rule",
      "at": 1789960000000000,
      "downstream": false,
      "ruleId": "3KEDBLvTYO6DnWi8H9S9MNLpPT7",
      "ruleName": "Checkout error rate"
    }
  ]
}
```
</ResponseExample>

| Feld | Beschreibung |
|---|---|
| `from`, `to` | Betrachteter Zeitraum als Unix-Zeitstempel in Mikrosekunden. |
| `kind` | `deployment`, `configuration`, `feature_flag` oder `rule` (die Regel des Incidents hat sich geändert). |
| `downstream` | `true`, wenn die Änderung einen nachgelagerten Service betrifft und keinen Service des Incidents selbst. |
| `version`, `status`, `commit`, `description`, `author` | Angaben aus der Meldung. Nicht gemeldete Felder fehlen. |
| `link` | Gemeldete URL der Pipeline oder ersatzweise die URL des Pull Requests. |
| `ruleId`, `ruleName` | Regel, auf die sich eine Änderung vom Typ `rule` bezieht. |

**Fehler**

| Status | Grund |
|---|---|
| `403` | Dem Token fehlt `alerts.incidents.read` oder der Zugriff auf diesen Incident. |
| `404` | Der Incident existiert nicht. |
