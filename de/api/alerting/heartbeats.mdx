Eine [Heartbeat-Regel](/de/api/alerting/create-rule#heartbeat-regeln) wartet nach jedem
Lauf auf einen Check-in des Jobs. Die Regel löst aus, wenn innerhalb des Intervalls plus Toleranzzeit kein Check-in eingeht oder ein Check-in einen
Fehler meldet.

| Methode und Pfad | Funktion | Berechtigung |
|---|---|---|
| `GET`, `POST /api/v1/intake/heartbeats/{token}` | Sendet einen Check-in ohne Anmeldung. | Das Token in der Adresse |
| `GET /api/v1/alerts/rules/{id}/heartbeat` | Gibt den letzten Check-in und die Fälligkeit des nächsten zurück. | `alerts.rules.read` für die Regel |
| `POST /api/v1/alerts/rules/{id}/heartbeat-token` | Setzt die Check-in-Adresse zurück. | `alerts.rules.manage` für die Regel |

## Check-in senden

```http
GET /api/v1/intake/heartbeats/{token}
POST /api/v1/intake/heartbeats/{token}
```

Beim ersten Speichern einer Heartbeat-Regel gibt die API die Adresse zurück. Siehe
[Regel erstellen](/de/api/alerting/create-rule#heartbeat-regeln). Rufen Sie die Adresse nach einem erfolgreichen Joblauf auf. Fügen Sie
`?status=fail` hinzu, wenn der Job fehlschlägt. Die Regel löst dann sofort aus, ohne das Ende des Intervalls abzuwarten. Den Anfang des
`POST`-Bodys (bis zu 1000 Zeichen) speichert die API als Check-in-Nachricht und zeigt ihn in der Incident-Annotation
`heartbeat_message` an. Bei einem Body über 64 KiB gibt die API `413` zurück. Bei jedem Check-in wertet die API die Regel sofort aus:
Bei einem Fehler löst die Regel aus. Bei Erfolg kann ein offener Incident gemäß der Wiederherstellungsbedingung in den Normalzustand zurückkehren.

<RequestExample>
```bash cURL
# The backup succeeded
curl -fsS https://molesignal.example.com/api/v1/intake/heartbeats/$HEARTBEAT_TOKEN

# The backup failed: send its last lines of output
tail -n 20 backup.log | curl -fsS -X POST --data-binary @- \
  "https://molesignal.example.com/api/v1/intake/heartbeats/$HEARTBEAT_TOKEN?status=fail"
```
</RequestExample>

<ResponseExample>
```json 200
{ "ok": true, "status": "fail" }
```
</ResponseExample>

Nur `status=fail` gilt als Fehler. Jeder andere oder ein fehlender Wert gilt als Erfolg. Bei einem falschen Token, einer
gelöschten Regel oder einer zurückgesetzten Adresse gibt die API `404` zurück.

## Check-in-Status abrufen

```http
GET /api/v1/alerts/rules/{id}/heartbeat
```

<ResponseExample>
```json 200
{
  "lastCheckinAt": 1790000000000000,
  "lastStatus": "ok",
  "lastMessage": "",
  "dueAt": 1790003900000000,
  "alarming": false,
  "issuedAt": 1789900000000000
}
```
</ResponseExample>

| Feld | Hinweise |
|---|---|
| `lastCheckinAt` | Zeitpunkt des letzten Check-ins in Unix-Mikrosekunden. Vor dem ersten Check-in: `null`. |
| `lastStatus`, `lastMessage` | Status (`ok` oder `fail`) und Nachricht des letzten Check-ins. |
| `dueAt` | Spätester Zeitpunkt für den nächsten Check-in: Zeitpunkt des letzten Check-ins (vor dem ersten Check-in: Ausgabezeitpunkt der Adresse) plus Intervall und Toleranzzeit. |
| `alarming` | Gibt an, ob die Regel jetzt auslösen soll: Der letzte Check-in hat einen Fehler gemeldet oder `dueAt` ist verstrichen. |
| `issuedAt` | Zeitpunkt der Ausgabe oder des Zurücksetzens der aktuellen Adresse. |

Wenn die Regel keine Heartbeat-Regel ist oder noch keine Adresse hat, gibt die API `404` zurück.

## Check-in-Adresse zurücksetzen

```http
POST /api/v1/alerts/rules/{id}/heartbeat-token
```

Die API gibt eine neue Adresse aus. Die alte Adresse wird sofort ungültig, und der Check-in-Verlauf bleibt erhalten. Die API gibt
`{ "path": "...", "url": "..." }` zurück. Die Adresse erscheint nur in dieser Antwort. `url` ist `null`, wenn keine externe
Adresse konfiguriert ist. Die API protokolliert das Zurücksetzen im Audit-Log. Wenn die Regel keine Heartbeat-Regel ist, gibt die API `400` zurück.
