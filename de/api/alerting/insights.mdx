```http
GET /api/v1/alerts/insights
```

Fasst die in einem Zeitfenster erstellten Incidents zusammen und zeigt, wie schnell die Übernahme
und Behebung erfolgten und wie viele Incidents eskalierten. Vergleicht diese Kennzahlen mit dem gleich langen
Zeitraum davor. In andere Incidents zusammengeführte Incidents zählen nicht. Der Aufruf erfordert `alerts.incidents.read`. Die Auslastung pro Person im Bereitschaftsdienst
steht unter [Auslastung im Bereitschaftsdienst](/de/api/alerting/oncall-load).

**Abfrageparameter**

| Parameter | Typ | Hinweise |
|---|---|---|
| `windowSecs` | Ganzzahl | Das rückblickende Zeitfenster in Sekunden. Standard: `604800` (7 Tage). Die API begrenzt den Wert auf den Bereich von 3600 bis 31536000. |

<RequestExample>
```bash cURL
curl "http://localhost:5080/api/v1/alerts/insights?windowSecs=86400" \
  -H "authorization: Bearer $MS_TOKEN"
```
</RequestExample>

**Antwort**

| Feld | Hinweise |
|---|---|
| `windowSecs` | Das Zeitfenster nach Anwendung der Grenzwerte. |
| `total` | Anzahl der im Zeitfenster erstellten Incidents. |
| `active` | Incidents mit dem Status `open` oder `acknowledged`. |
| `closed` | Incidents mit dem Status `resolved` oder `closed`. |
| `mttrSecs` | Durchschnittliche Zeit in Sekunden von der Erstellung bis zur Behebung, berechnet über alle behobenen Incidents. `0`, wenn keine Behebung vorliegt. |
| `noiseRate` | Anteil von 0 bis 1 der behobenen Incidents, deren Behebung innerhalb von 60 Sekunden erfolgte. `0`, wenn keine Behebung vorliegt. |
| `byHour` | 24 Anzahlen von Incidents, aufgeschlüsselt nach der UTC-Stunde ihrer Erstellung. |
| `bySeverity` | Anzahl pro Schweregrad. Schweregrade ohne Incidents fehlen. |
| `topServices`, `topRules` | Bis zu 8 Einträge mit `key` und `count`, nach Anzahl absteigend sortiert. Der Schlüssel ist ein Servicename oder eine Regel-ID. |
| `response.current`, `response.previous` | Kennzahlen zur Reaktion im Zeitfenster und im gleich langen Zeitraum davor. Die Felder stehen weiter unten. |
| `response.breakdown` | Aufschlüsselung des Zeitfensters nach Team (`teams`, mit Team-ID als Schlüssel), Service (`services`) und Person (`people`, mit der ersten Person, die den Incident übernimmt, als Schlüssel). Jeweils höchstens 20 Zeilen, nach Anzahl der Incidents absteigend sortiert. Ein Incident mit mehreren Services zählt einmal pro Service. Jede Zeile enthält `incidents`, die durchschnittliche Zeit bis zur Übernahme in Sekunden (`mttaSecs`), die durchschnittliche Zeit bis zur Behebung in Sekunden (`mttrSecs`) und die Eskalationsrate (`escalationRate`). |

**`response.current` und `response.previous`**

| Feld | Hinweise |
|---|---|
| `incidents` | Die im Zeitraum erstellten Incidents. |
| `responded` | Incidents, die eine Person übernommen hat. Als Übernahme gilt die erste Bestätigung. Behebt eine Person einen Incident ohne vorherige Bestätigung, zählt der Zeitpunkt der Behebung. Incidents, deren Regel von selbst in den Normalzustand zurückkehrt, zählen nicht. |
| `mtta` | Sekunden von der Auslösung bis zur ersten Übernahme des Incidents: der Mittelwert `meanSecs`, der Median `p50Secs` und das 90. Perzentil `p90Secs`. Alle Werte sind `0`, wenn keine Übernahme vorliegt. |
| `mttr` | Sekunden von der Auslösung bis zur Behebung, berechnet über alle behobenen Incidents, ebenfalls mit Mittelwert, P50 und P90. |
| `escalationRate` | Anteil von 0 bis 1 der eskalierten Incidents: Incidents, die den zweiten Schritt erreicht haben oder über [Jetzt eskalieren](/de/api/alerting/escalate-incident) eskaliert wurden. |
| `steps` | Kennzahlen pro Schritt. `step` beginnt bei 0. `reached` zählt die Incidents, die den Schritt erreicht haben, und `acknowledged` die in diesem Schritt bestätigten Incidents. Nur Incidents mit Eskalationen im zeitlichen Verlauf zählen. Ohne solche Incidents im Zeitraum bleibt das Feld leer. |
| `ackVia` | Kanal der ersten Übernahme: `web`, `api`, `im`, `sms`, `phone` oder `agent`, jeweils mit Anzahl. |
