```http
GET /api/v1/alerts/rules
GET /api/v1/alerts/rules/{id}
```

Der erste Aufruf gibt alle Alarmregeln der Organisation als Array zurück. Der zweite Aufruf gibt eine einzelne Regel zurück. Beide Aufrufe erfordern `alerts.rules.read`.

<RequestExample>
```bash cURL
curl http://localhost:5080/api/v1/alerts/rules \
  -H "authorization: Bearer $MS_TOKEN"
```
</RequestExample>

<ResponseExample>

Eine Regel enthält die Felder aus [Regel erstellen](/de/api/alerting/create-rule) und die folgenden schreibgeschützten Felder:

| Feld | Hinweise |
|---|---|
| `id`, `orgId` | Die IDs der Regel und der Organisation. |
| `createdAt`, `updatedAt` | Mikrosekunden seit Beginn der Unix-Epoche. |
| `lastEvalAt` | Zeitpunkt der letzten abgeschlossenen Auswertung in Mikrosekunden. Bis zur ersten abgeschlossenen Auswertung lautet der Wert `null`. Wenn eine Abfrage fehlschlägt oder das Zeitlimit überschreitet, bleibt der Wert unverändert. |
| `lastState` | Ergebnis dieser Auswertung: `{"kind": "healthy"}`, wenn die Bedingung nicht erfüllt war, `{"kind": "pending", "consecutive": 1}`, solange die Bedingung bei weniger als `forPeriods` aufeinanderfolgenden Auswertungen erfüllt ist, `{"kind": "firing"}`, sobald die Bedingung lange genug erfüllt war, und `{"kind": "dropped"}`, wenn die Regel ausgelöst hat, eine [Alarm-Pipeline](/de/pipelines/alert-events#was-mit-einem-ereignis-geschieht) aber den Incident verworfen hat, den die Regel sonst eröffnet hätte. Eine Regel im Zustand `firing` eröffnet während der Wartezeit `silenceSecs` keinen neuen Incident. |

Bei einer unbekannten `id` gibt die API `404` zurück.
