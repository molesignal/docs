```http
GET /api/v1/alerts/incidents
GET /api/v1/alerts/incidents/{id}
```

Der erste Aufruf listet Incidents auf, die neuesten zuerst. Incidents, die mit einem anderen Incident [zusammengeführt](/de/api/alerting/merge-incidents) wurden, erscheinen nur in der [Zeitleiste](/de/api/alerting/incident-timeline) des Haupt-Incidents. Der zweite Aufruf gibt einen einzelnen Incident zurück, unabhängig davon, ob er zusammengeführt wurde. Beide Aufrufe erfordern `alerts.incidents.read`.

**Abfrageparameter der Liste**

| Parameter | Typ | Hinweise |
|---|---|---|
| `scope` | string | `active` (Standard) gibt Incidents mit dem Status `open` oder `acknowledged` zurück. `all` gibt alle im Zeitfenster erstellten Incidents sowie alle aktiven Incidents unabhängig von ihrem Alter zurück. |
| `windowSecs` | integer | Rückblickzeitraum für `scope=all`. Standard: `604800` (7 Tage). Werte unter 3600 oder über 31536000 begrenzt die API auf den jeweiligen Grenzwert. |

Listeneinträge enthalten nur eine Kurzfassung. `triggeringQuery` ist `null`, und `traceIds`, `hostIds` und `affectedServices` enthalten jeweils höchstens einen Wert. Rufen Sie den einzelnen Incident ab, um den vollständigen Datensatz zu erhalten.

<RequestExample>
```bash cURL
curl "http://localhost:5080/api/v1/alerts/incidents?scope=all&windowSecs=86400" \
  -H "authorization: Bearer $MS_TOKEN"
```
</RequestExample>

## Incident-Felder

| Feld | Hinweise |
|---|---|
| `id`, `orgId`, `ruleId` | Die IDs des Incidents, der Organisation und der Regel. |
| `escalationPolicyId` | Beim Öffnen des Incidents legt die Quelle die Eskalationsrichtlinie fest. Verwendet die Quelle die Standardrichtlinie, wählt das [Alert-Routing](/de/alerting/routing) die Richtlinie aus. Sobald die Eskalation beginnt, ersetzt die API den Alias `default` durch die ID der Richtlinie namens `default`. |
| `status` | `open`, `acknowledged` oder `resolved`. Das Modell kennt auch `closed`, aber kein Aufruf setzt diesen Status. |
| `severity` | `info`, `warning`, `error` oder `critical`. |
| `summary` | Der Name der Regel, gefolgt von bis zu zwei betroffenen Services und `+N` für weitere Services. |
| `fingerprint` | Ein Hash aus der Regel-`id` und den zugehörigen `labels`. Pro Fingerabdruck hat eine Regel einen aktiven Incident. |
| `currentStep`, `currentLoop`, `currentStepStartedAt` | Der Fortschritt der Eskalation. Die Schrittnummerierung beginnt bei 0. Die Zeitangabe erfolgt in Mikrosekunden. |
| `assignees` | Die dem Incident zugewiesenen Benutzerkonten: die direkten Ziele des aktuellen Eskalationsschritts, also die `user`-Ziele und das jeweils diensthabende Konto für jedes `schedule`-Ziel. Hinzu kommt das Konto, das den Incident bestätigt hat. Das Feld bleibt leer, bis der erste Schritt ausgeführt wird. Richtet sich ein Schritt nur an Teams, bleiben die bisherigen Zuweisungen bestehen. |
| `labels`, `annotations` | Eine Momentaufnahme vom Öffnen des Incidents. Sie enthält die `labels` der Regel sowie `service` und `host` aus dem Abfrageergebnis. Spätere Regeländerungen wirken sich nicht auf die Momentaufnahme aus. |
| `traceIds`, `hostIds`, `affectedServices` | Werte aus den Spalten `trace_id`, `host` und `service` des Abfrageergebnisses, ohne Duplikate. Jeweils höchstens 10 Werte. |
| `triggeringQuery` | `language`, `statement` und `sampleValues`. Jeder Beispielwert enthält `ts` in Mikrosekunden (`0`, wenn das Ergebnis keine Zeitspalte enthält), `value` und `labels`. Nur der Einzelabruf gibt dieses Feld zurück. |
| `createdAt` | Zeitpunkt der Öffnung des Incidents in Mikrosekunden. |
| `acknowledgedAt`, `acknowledgedBy` | Zeitpunkt und Benutzerkonto der letzten Bestätigung. |
| `resolvedAt`, `resolvedBy` | Zeitpunkt und Benutzerkonto der Behebung. `resolvedBy` ist `null`, wenn die Regelauswertung den Incident automatisch als behoben markiert, weil die Regel nicht mehr zutrifft. |
| `teamId` | Das Team, dem das [Alert-Routing](/de/alerting/routing) den Incident beim Öffnen zugewiesen hat, oder `null`. |
| `routing` | Grund für die Zuweisung. Bei Incidents, die vor Einführung des Routings geöffnet wurden, ist der Wert `null`. `reason` ist `rule` (eine Routing-Regel traf zu; mit `ruleId` und dem damaligen `ruleName`), `service_owner` (das für den Service zuständige Team; mit `service`), `team_label` (das Team-Label), `default` (die Standardrichtlinie) oder `source` (die Quelle wählte die Eskalationsrichtlinie, daher wies das Routing nur das Team zu). |
| `snoozedUntil`, `snoozedBy` | Solange der Incident [zurückgestellt](/de/api/alerting/snooze-incident) ist: der Endzeitpunkt in Mikrosekunden und das Benutzerkonto, das die Zurückstellung vorgenommen hat. Andernfalls `null`. |
| `severitySetBy` | Das Benutzerkonto, das den [Schweregrad manuell festgelegt](/de/api/alerting/set-incident-severity) hat. Danach ändert die Regel den Schweregrad nicht mehr. Andernfalls `null`. |
| `mergedInto` | Der Incident, mit dem dieser Incident [zusammengeführt](/de/api/alerting/merge-incidents) wurde, oder `null`. |
| `assigneesPinned` | `true`, solange die manuell zugewiesenen Benutzerkonten festgelegt sind. Die Eskalation ersetzt sie erst beim nächsten Schritt. |
| `dispatchRound`, `dispatchReason` | `dispatchRound` zählt die Runden der Eskalationsbenachrichtigungen. Eine manuelle Eskalation, die Neuzuweisung zu einem Team oder einer Richtlinie oder die Erhöhung des Schweregrads startet eine neue Runde, damit ein Schritt erneut benachrichtigen kann. `dispatchReason` nennt den Grund für die letzte Benachrichtigung im aktuellen Schritt: `step`, `manual`, `reassigned`, `responder_added`, `snooze_ended`, `ack_timeout` oder `severity_raised`. |
| `revision` | Erhöht sich bei jeder Änderung am Incident. |

**Fehler**

| Status | Ursache |
|---|---|
| `403` | Dem Token fehlt die Berechtigung `alerts.incidents.read`. |
| `404` | Der Incident existiert nicht. |
