Die RUM-API nimmt Ereignisse von Browser- und Mobilclients entgegen und stellt sie zum Abruf bereit. Alle Endpunkte verwenden das
Präfix `/api/v1/rum` und erfordern ein Bearer-Token.

```http
Authorization: Bearer <token>
```

Zum Schreiben von Ereignissen und Replay-Segmenten ist `rum.write` erforderlich. Ein an eine Anwendung gebundenes [Client-Token](/de/api/auth/rum-token) hat
genau diese Berechtigung für eine einzige Anwendung. Zum Lesen ist die Leseberechtigung des jeweiligen Bereichs erforderlich: `rum.events.read`, `rum.sessions.read`, `rum.replay.read`, `rum.issues.read`, `rum.analytics.read`, `rum.applications.read` oder `rum.playlists.read`. Auf Plattformebene lässt sich `sys.telemetry.read`
im geschützten Geltungsbereich `_sys` verwenden. Zum Erstellen, Ändern und Löschen einer Anwendung ist `rum.applications.manage` erforderlich. Zum Festlegen des Status, des zuständigen Teams
oder der zuständigen Person eines Issues ist `rum.playlists.manage` erforderlich.

Die Zeilen stammen aus echten Nutzersitzungen. Sitzungen vom Typ `synthetics` oder `ci_test` bleiben ausgeschlossen, sofern kein Filter `session.type`, `synthetics.*` oder `ci_test.*` angibt. Siehe [Test-Traffic](/de/rum/test-traffic). Ein Feld kann auch ein Schlüssel in einer JSON-Spalte sein: `feature_flags.<key>`, `context.<key>`, `usr.extra.<key>` oder `view.custom_timings.<key>`.

Ein **Typ** gibt an, welche Art von Zeilen ein Endpunkt verarbeitet: `sessions`, `views`, `actions`, `errors`, `resources`, `longTasks`,
`vitals` oder `logs`. Der Name eines Typs entspricht dem Namen des zugehörigen [Streams](/de/rum/events#wo-die-ereignisse-gespeichert-werden) ohne das Präfix `rum_`
.

## Ein Replay-Segment senden

```http
POST /api/v1/rum/replay
```

```json
{
  "application": "checkout-web",
  "sessionId": "6f1c2b7e-1d5a-4c6b-9a3e-0a1b2c3d4e5f",
  "seq": 1,
  "events": [{ "type": 2, "timestamp": 1790000000000, "data": { "node": {} } }]
}
```

`sessionId`, `seq` und `events` sind Pflichtfelder. Senden Sie optional auch `env`, `service` und `version` mit den im SDK konfigurierten Werten:
Diese Werte liefern den [Aufbewahrungsfiltern](/de/rum/sampling#filter) der Anwendung die Merkmale der Sitzung. So speichert die API kein Segment einer
Sitzung, die der Filter von der Aufbewahrung ausschließt. Die API akzeptiert keine weiteren Felder. `events` enthält rrweb-Ereignisse. Ein Client-Token erlaubt Schreibzugriffe
nur auf die zugehörige Anwendung: Lassen Sie `application` weg oder geben Sie diese Anwendung an. Bei einem anderen Wert gibt die API `403` zurück. Geben Sie bei anderen Anmeldedaten
die Anwendung an. Wenn die Anwendung nicht existiert, gibt die API `404` zurück. Die Antwort enthält die Angaben zum gespeicherten Segment:
`id`, `seq`, `eventCount` und `hasFullSnapshot`.

`GET /api/v1/rum/replay/{sessionId}` gibt `sessionId`, `segmentCount` und `events` zurück. `events` enthält die Ereignisse aller
Segmente der Sitzung in der ursprünglichen Reihenfolge.

## Anwendungen verwalten

Eine Anwendung hat eine `id`, einen `name`, eine `platform` und `settings`:

```json
{
  "id": "checkout-web",
  "name": "Checkout web",
  "platform": "browser",
  "settings": {
    "collectIp": true,
    "collectGeo": true,
    "defaultPrivacy": "mask",
    "issuesPerHour": 100,
    "scrub": ["secrets", "emails", "phones", "cards", "national_ids", "url_params"],
    "sessionSampleRate": 100,
    "retentionFilters": [],
    "keepErrors": true,
    "sdk": { "sessionReplaySampleRate": 20, "forwardConsoleLogs": ["warn", "error"] },
    "segments": [{ "id": "enterprise", "name": "Enterprise", "conditions": [{ "field": "usr.extra.plan", "op": "is", "values": ["enterprise"] }] }]
  },
  "createdBy": "<user-id>",
  "createdAt": 1790000000000000,
  "updatedAt": 1790000000000000
}
```

| Feld | Regel |
|---|---|
| `id` | Nur beim Erstellen verfügbar. 1 bis 64 Zeichen aus `A-Z`, `a-z`, `0-9`, `.`, `_`, `:` und `-`. Fehlt die ID, leitet der Server sie aus dem Namen ab. Die ID lässt sich nicht ändern. |
| `name` | Beim Erstellen erforderlich. 1 bis 128 Zeichen. |
| `platform` | `browser` (Standard), `android`, `ios`, `flutter`, `react-native` oder `other`. |
| `settings` | `collectIp` und `collectGeo` sind boolesche Werte. Der Standardwert ist jeweils `true`. `defaultPrivacy` ist `mask` (Standard), `mask-user-input` oder `allow`. `issuesPerHour` gibt an, wie viele neue [Probleme](/de/rum/errors#neue-probleme-pro-stunde) die Anwendung pro Stunde eröffnet. Zulässig sind 1 bis 10000, der Standardwert ist 100. `scrub` listet die Arten sensibler Texte auf, die der Server vor dem Speichern aus einem Ereignis entfernt: `secrets`, `emails`, `phones`, `cards`, `national_ids` und `url_params`. Standardmäßig entfernt der Server alle diese Arten. Bei einer leeren Liste entfernt der Server keine (siehe [Datenschutz in RUM](/de/rum/privacy#sensible-texte-beim-empfang-bereinigen)). `sessionSampleRate` gibt an, welchen Prozentsatz der Sitzungen der Server speichert, auf die kein Aufbewahrungsfilter zutrifft. Zulässig sind ganze Zahlen von 0 bis 100, der Standardwert ist 100 (siehe [RUM-Datensampling](/de/rum/sampling#anteil-der-sitzungen-serverseitig-speichern)). Bei einem Wert über 100 antwortet der Server mit `400`. `retentionFilters` listet bis zu 10 [Filter](/de/rum/sampling#filter) auf. Jeder Filter hat die Form `{ "name", "rate", "conditions" }` und eine `id`. Fehlt die ID, leitet der Server sie aus dem Namen ab. Beim Umbenennen des Filters bleibt die ID erhalten. Ein `PATCH` ersetzt die gesamte Liste. `rate` ist eine ganze Zahl von 0 bis 100. Eine Bedingung hat die Form `{ "field", "op", "values" }`. Für `field` sind `env`, `service`, `version`, `source`, `session.type`, `geo.country_iso_code`, `browser.name`, `os.name` und `device.type` zulässig, für `op` die Werte `is` und `is_not`. `values` enthält 1 bis 20 Werte. Ein Filter hat höchstens 5 Bedingungen. Jeder Name darf unabhängig von der Groß- und Kleinschreibung nur einmal vorkommen. Die IDs `default` und `errors` sind reserviert. Mit `keepErrors` speichert der Server Fehler aus Sitzungen, die er nicht speichert. Der Standardwert ist `true`. Bei einer ungültigen Liste antwortet der Server mit `400`. `segments` listet bis zu 20 [Segmente](/de/rum/analytics#segmente) auf. Jedes Segment hat die Form `{ "name", "conditions" }` und eine `id`. Fehlt die ID, leitet der Server sie aus dem Namen ab. Beim Umbenennen des Segments bleibt die ID erhalten. Ein `PATCH` ersetzt die gesamte Liste. Eine Bedingung hat die Form `{ "field", "op", "values" }`. Für `field` sind `service`, `version`, `source`, `usr.id`, `usr.email`, `account.id`, `browser.name`, `os.name`, `device.type`, `geo.country_iso_code`, `geo.continent_code`, `geo.city` und `usr.extra.<key>` zulässig, für `op` die Werte `is` und `is_not`. `values` enthält 1 bis 20 Werte. Ein Segment hat 1 bis 5 Bedingungen. `sdk` enthält die Konfiguration, die `GET /api/v1/rum/config` an ein mit `remoteConfiguration` gestartetes SDK zurückgibt. Mögliche Felder sind `sessionSampleRate` und `sessionReplaySampleRate` (jeweils von 0 bis 100), `defaultPrivacyLevel`, `trackUserInteractions` und `forwardConsoleLogs` (eine Liste aus `debug`, `log`, `info`, `warn` und `error`). Für Felder, die in `sdk` fehlen, verwendet das SDK die Vorgaben der Seite. Fehlt eine Einstellung beim Erstellen, gilt der Standardwert. Fehlt sie bei einem `PATCH`, bleibt der bisherige Wert erhalten. |

`POST` gibt die neue Anwendung zurück. Wenn die ID oder der Name bereits existiert, antwortet der Server mit `409`. `PATCH` akzeptiert `name`, `platform` und
`settings` als optionale Felder. `DELETE` gibt `{ "deleted": true }` zurück. Bereits gesendete Ereignisse bleiben in den Streams, bis
ihre Aufbewahrungsfrist abläuft.

## Zeilen suchen

```http
GET /api/v1/rum/search?type=errors&from=1790000000000000&to=1790003600000000&filters=[{"field":"env","op":"=","value":"production"}]&limit=100
```

`POST` akzeptiert dieselben Parameter im JSON-Body und eignet sich für Abfragen, die für eine URL zu lang sind. In einer URL sind `filters`, `freeText` und
`columns` JSON-kodierte Listen.

| Parameter | Typ | Verhalten |
|---|---|---|
| `type` | Zeichenfolge | Erforderlich. Der Typ der Zeilen. |
| `from`, `to` | Ganzzahl | Der Zeitraum in Mikrosekunden seit der Unix-Epoche. Standardmäßig ist `to` der aktuelle Zeitpunkt und `from` liegt 24 Stunden vor `to`. `to` muss größer als `from` sein. |
| `filters` | Liste | Bedingungen, die jede Zeile erfüllt. Siehe unten. |
| `freeText` | Liste von Zeichenfolgen | Bis zu 8 Wörter. Jedes Wort muss in einer der Textspalten des Typs vorkommen. Groß- und Kleinschreibung spielen keine Rolle. |
| `columns` | Liste von Zeichenfolgen | Die zurückzugebenden Spalten. Ohne Angabe gibt der Server die Standardspalten des Typs zurück. Die Spalte mit dem Namen der Zeile ist immer enthalten. |
| `limit` | Ganzzahl | Die Seitengröße von 1 bis 5.000. Der Standardwert ist 100. |
| `cursor` | Zeichenfolge | Der `nextCursor` oder `previousCursor` aus einer früheren Antwort. Lassen Sie alle anderen Parameter weg oder geben Sie sie unverändert erneut an. |

Ein **Filter** hat ein `field`, einen `op` und einen `value`. Zulässig sind höchstens 32 Filter und ein Wert mit höchstens 512 Zeichen.

| `op` | Bedeutung |
|---|---|
| `=`, `!=` | Gleich bzw. ungleich. Bei leerem `value` prüft `=`, ob das Feld keinen Wert hat, und `!=`, ob es einen Wert hat. |
| `in`, `not_in` | Der Feldwert kommt in der Werteliste vor bzw. kommt darin nicht vor. `value` ist eine JSON-Liste mit 1 bis 100 Werten, zum Beispiel `["Chrome","Safari"]`. |
| `contains` | Das Feld enthält den Text unabhängig von der Groß- und Kleinschreibung. Gilt für Textspalten und JSON-Dokumente. |
| `>`, `>=`, `<`, `<=` | Vergleich einer Zahl oder eines Zeitpunkts. |
| `exists`, `missing` | Das Feld hat einen bzw. keinen Wert. |

Wenn der Typ das Feld nicht enthält oder das Feld den Operator nicht unterstützt, antwortet der Server mit `400`.

Die Antwort enthält die Zeilen einer Seite, beginnend mit der neuesten:

```json
{
  "items": [
    { "timestamp": 1790000001600000, "error.message": "Payment provider timeout", "error.id": "0a9b8c7d-6e5f-4a3b-8c1d-2e3f4a5b6c70" }
  ],
  "hasMore": true,
  "nextCursor": "<cursor>",
  "previousCursor": null
}
```

Eine Zeile enthält `timestamp` und die angeforderten Spalten. Eine JSON-Spalte enthält das Dokument. Ansichten und Sitzungen
erscheinen jeweils nur einmal, in ihrer neuesten Version.

## Zeilen zählen und beschreiben

`facets` akzeptiert die Parameter von `search` ohne Seitennavigation sowie `field` (erforderlich) und `limit` (1 bis 100, Standardwert 10).
Der Endpunkt gibt die häufigsten Werte des Felds in den passenden Zeilen zurück:

```json
{ "field": "browser.name", "values": [{ "value": "Chrome", "count": 812 }, { "value": "Safari", "count": 247 }] }
```

Wenn die Zählung zu lange dauert oder das System ausgelastet ist, gibt der Server eine leere Liste zurück und setzt `unavailable` auf `time_budget` bzw. `busy`.
Für ein Feld mit einem JSON-Dokument gibt der Server `400` zurück. Für einen Schlüssel darin, etwa `feature_flags.checkout_v2`, zählt der Server nach Wert. Facetten für `session.type` zählen alle Sitzungsarten.

`keys` akzeptiert die Auswahlparameter sowie `column` (erforderlich: `feature_flags`, `context`, `usr.extra` oder `view.custom_timings`) und `limit` (1 bis 500, Standardwert 100). Der Standardwert für `type` ist `views`. Der Endpunkt gibt die Schlüssel nach Anzahl der Sitzungen in absteigender Reihenfolge zurück:

```json
{ "column": "feature_flags", "keys": [{ "key": "checkout_v2", "sessions": 812 }] }
```

`distribution` akzeptiert die Auswahlparameter, `field` (erforderlich: ein numerisches Feld oder der Schlüssel eines numerischen Werts in einer JSON-Spalte) und `bars` (1 bis 100, Standardwert 40). Der Endpunkt zählt die gespeicherten Zeilen. Die Balken decken gleich breite Intervalle vom kleinsten Wert bis zum 99. Perzentil ab. Der letzte Balken zählt die Werte oberhalb dieses Perzentils und hat daher den größten Wert als `to`. Sind alle Werte gleich, gibt es nur einen Balken.

```json
{
  "field": "view.loading_time",
  "unit": "ns",
  "rows": 812,
  "min": 90000000,
  "max": 41000000000,
  "p50": 800000000,
  "p75": 1400000000,
  "p95": 3100000000,
  "p99": 6000000000,
  "bars": [{ "from": 90000000, "to": 237750000, "rows": 12 }]
}
```

`histogram` akzeptiert dieselben Auswahlparameter sowie die Parameter für die Zeitintervalle: `bucketTime` (mindestens 1000) und `originTime`, den Beginn
des ersten Intervalls. Ohne Angabe gilt `from`. `originTime` darf nicht nach `from` liegen. Ein Zeitraum umfasst höchstens 512 Intervalle. Jedes Intervall hat die Form `{ startTime, total, errors }`. `errors` zählt Zeilen mit Problemen:
Sitzungen und Ansichten mit Fehlern, Aktionen mit Frustrationssignalen und Anfragen mit einem Statuscode ab `400` oder dem Statuscode
`0`. Für Typen ohne solche Zeilen ist `split` auf `false` gesetzt.

`GET /api/v1/rum/schema/{type}` listet die Spalten auf, die die anderen Endpunkte akzeptieren und zurückgeben:

```json
{
  "type": "views",
  "stream": "rum_views",
  "idField": "view.id",
  "versioned": true,
  "defaultColumns": ["view.id", "view.url_path", "view.loading_time"],
  "fields": [
    { "name": "view.loading_time", "dataType": "int64", "unit": "ns", "facetable": true, "indexed": false }
  ]
}
```

`dataType` ist `bool`, `int64`, `float64`, `utf8` oder `json`. `unit` ist `ns`, `ms`, `epoch_ms`, `bytes`, `count`,
`score`, `percent`, `per_second`, `px` oder `none`. Der Server speichert Zeitdauern in Nanosekunden, wie vom SDK gesendet. Der Client
formatiert sie. `epoch_ms` kennzeichnet einen Zeitpunkt in Millisekunden seit der Unix-Epoche, etwa `session.start` oder
`session.last_activity`. Der Client zeigt ihn als Datum und Uhrzeit an. Bei einem als `facetable` gekennzeichneten Feld zählt der Server nach Wert. Bei einem als
`indexed` gekennzeichneten Feld filtert der Server, ohne jede Zeile zu lesen. `idField` bezeichnet die Spalte, die jede Zeile eindeutig identifiziert.

## Zeilen auswerten

`aggregate` übernimmt die Auswahl aus `search` und berechnet Kennzahlen über alle passenden Zeilen. So liefert es die Zahlen für Diagramme,
Tabellen und Karten, etwa die Anzahl der Sitzungen oder das 75. Perzentil einer Web-Vital-Metrik, jeweils pro Seite oder pro Stunde.

```http
GET /api/v1/rum/aggregate?type=views&groupBy=["view.url_path_group"]&measures=[{"fn":"count","name":"views"},{"fn":"p75","field":"view.performance.lcp.timestamp","name":"lcp"}]&limit=5
```

| Parameter | Typ | Verhalten |
|---|---|---|
| `type`, `from`, `to`, `filters`, `freeText` | | Wie bei `search`. |
| `measures` | Liste | Erforderlich. Bis zu 16 Kennzahlen. Details stehen weiter unten. |
| `groupBy` | Liste von Zeichenfolgen | Bis zu 2 Felder. Jede Kombination ihrer Werte ergibt eine Zeile. Die Gruppierung nach einem Feld mit einem JSON-Dokument ist nicht möglich, wohl aber nach einem Schlüssel darin: `feature_flags.checkout_v2`. |
| `bucketTime`, `originTime` | Ganzzahl | Wie bei `histogram`. Mit diesen Parametern entsteht pro Gruppe und Balken eine Zeile. |
| `orderBy` | Zeichenfolge | Name einer Kennzahl, eines Gruppierungsfelds oder `time` (für Balken ohne Gruppen). Ohne Angabe sortiert `aggregate` die Gruppen nach der ersten Kennzahl und die Balken chronologisch. |
| `order` | `asc` oder `desc` | Ohne Angabe sortiert `aggregate` bei einer Kennzahl absteigend, bei einer Gruppe oder nach Zeit aufsteigend. |
| `limit` | Ganzzahl | Anzahl der Gruppen, von 1 bis 250. Standard: 10. Bei Balken liegt das Maximum bei 20, und die Auswertung verfolgt jede Gruppe über alle Balken hinweg. |
| `estimate` | boolesch | Standard: `true`. Die Berechnung rechnet Anzahlen, Summen und Mittelwerte anhand der Speicherrate (`retention.rate`) jeder Zeile auf alle Sitzungen hoch und gewichtet auch Perzentile entsprechend. `false` zählt wie der Explorer nur die gespeicherten Zeilen. |

Eine **Kennzahl** hat `fn` und `field` und kann zusätzlich `name`, `where` und `fallback` haben.

| `fn` | Bedeutung |
|---|---|
| `count` | Anzahl der Zeilen. Mit `field` zählen nur Zeilen mit einem Wert in diesem Feld. Bei aktivem `estimate` rechnet die Funktion die Anzahl anhand der Speicherraten hoch. |
| `stored` | Anzahl der gespeicherten Zeilen, unabhängig von der Speicherrate. |
| `count_distinct` | Anzahl der unterschiedlichen Werte in `field`. `fallback` gibt das Ersatzfeld an, falls `field` keinen Wert enthält. So lassen sich Nutzer ohne ID anhand ihrer anonymen ID unterscheiden. Die Funktion zählt Nutzer und andere Werte wie erfasst. Bei aktivem `estimate` rechnet sie die Anzahl der Sitzungen (`session.id`) hoch. |
| `sum`, `avg`, `min`, `max` | Summe, Mittelwert, Minimum oder Maximum eines numerischen Felds. |
| `p50`, `p75`, `p90`, `p95`, `p99` | Geschätztes Perzentil eines numerischen Felds. |

`where` ist wie in `search` eine Liste von Filtern. Die Kennzahl berücksichtigt nur Zeilen, die diese Filter erfüllen:
`{"fn":"count","where":[{"field":"session.error.count","op":"=","value":"0"}]}` zählt Sitzungen ohne Fehler. Als Name einer Kennzahl
dient `name`, sonst `fn(field)` oder, ohne Feld, `fn`. Zwei Kennzahlen dürfen nicht denselben Namen haben. Fehlt ein Feld
im gewählten Typ oder verlangt die Berechnung einen Zahlenwert aus einem nicht numerischen Feld, schlägt die Anfrage mit `400` fehl.

```json
{
  "groupBy": ["view.url_path_group"],
  "measures": [
    { "name": "views", "fn": "count", "unit": "count" },
    { "name": "lcp", "fn": "p75", "field": "view.performance.lcp.timestamp", "unit": "ns" }
  ],
  "rows": [
    { "group": ["/checkout"], "values": [8031, 3400000000.0] },
    { "group": [null], "values": [212, null] }
  ]
}
```

Eine Zeile enthält die Gruppierungswerte in `group` in der Reihenfolge von `groupBy` und die Kennzahlwerte in `values` in der Reihenfolge der Kennzahlen. Bei einer Auswertung über die Zeit enthält sie
außerdem `startTime`, den Beginn des Balkens. Für eine Gruppe, deren Zeilen keine Werte enthalten, liefert die Auswertung `null`, ebenso für ein Perzentil ohne
Werte. `unit` ist `count` oder die von `schema` angegebene Einheit des Felds. Die Auswertung zählt Views und Sitzungen je einmal in ihrer
neuesten Version. Passt keine Zeile, enthält eine Antwort mit Gruppen oder Balken keine Zeilen. Ohne Gruppen und Balken enthält sie eine Zeile: Anzahlen sind `0`, die übrigen Kennzahlen `null`. Für Werte ohne Leseberechtigung liefert die Antwort den Maskierungstext. Dauert eine Zählung zu lange oder ist
das System ausgelastet, enthält die Antwort keine Zeilen und setzt `unavailable` auf `time_budget` oder `busy`.

## SQL-Anweisung eines Dashboard-Panels

```http
POST /api/v1/rum/panel-statement
```

Gibt die SQL-Anweisung zurück, mit der ein [Dashboard](/de/dashboards)-Panel dieselbe Darstellung wie der [Explorer](/de/rum/explorer#zum-dashboard-hinzufügen)
erzeugt: dieselben Kennzahlen aus denselben Zeilen wie bei `aggregate` mit `estimate` auf `false`. Die Anfrage liest keine Daten. Die
Anweisung enthält keine Zeitangaben, da das Dashboard sie für den ausgewählten Zeitraum ausführt. Die Anfrage erfordert `rum.events.read`.

```json
{
  "type": "views",
  "filters": [{ "field": "env", "op": "=", "value": "production" }],
  "chart": "timeseries",
  "measures": [{ "fn": "p75", "field": "view.loading_time", "name": "p75 Loading" }],
  "groupBy": ["browser.name"],
  "groupNames": ["Browser"],
  "limit": 5,
  "interval": "${interval}"
}
```

| Feld | Typ | Verhalten |
|---|---|---|
| `type`, `filters`, `freeText` | | Wie bei `search`. |
| `chart` | Zeichenfolge | Erforderlich. `timeseries`, `toplist`, `table` oder `distribution`. |
| `measures`, `groupBy`, `orderBy`, `order`, `limit` | | Wie bei `aggregate`, mit Ausnahme von `estimate` und den Balken. Eine `toplist` hat genau ein Gruppierungsfeld. Eine `timeseries` verfolgt höchstens 20 Gruppen. Jede Kennzahl ergibt eine Spalte mit ihrem `name` als Spaltennamen. |
| `groupNames` | Liste von Zeichenfolgen | Namen der Gruppierungsspalten in ihrer Reihenfolge. Ohne Angabe trägt die Spalte den Namen des Gruppierungsfelds. |
| `field` | Zeichenfolge | Erforderlich für `distribution`: das numerische Feld für die Verteilung. Der erste Eintrag in `groupNames` benennt die Feldspalte, und `name` der ersten Kennzahl benennt die Spalte für die Anzahl. |
| `interval` | Zeichenfolge | Erforderlich für `timeseries`: die Länge der Zeitabschnitte als Dashboard-Variable wie `${interval}` oder als Dauer wie `15 minutes`. |

```json
{
  "stream": "rum_views",
  "statement": "WITH \"__top\" AS (SELECT … LIMIT 5) SELECT date_bin(INTERVAL '${interval}', _timestamp) AS \"time\", … FROM \"rum_views_latest\" JOIN \"__top\" ON … GROUP BY 1, 2 ORDER BY 1, 2",
  "columns": [
    { "name": "time", "role": "time", "unit": "none" },
    { "name": "Browser", "role": "group", "unit": "none" },
    { "name": "p75 Loading", "role": "measure", "unit": "ms" }
  ],
  "limit": 10000
}
```

Die Anweisung liest `stream` und greift über `rum_views_latest` oder
`rum_sessions_latest` auf die neueste Version einer View oder Sitzung zu. Sie übernimmt die Auswahlbedingungen und schließt Sitzungen aus synthetischen Tests und CI aus,
sofern die Filter nicht `session.type`, `synthetics.*` oder `ci_test.*` angeben. `columns` enthält die Ausgabespalten in dieser Reihenfolge:
`time` für den Beginn eines Balkens, die Gruppierungsspalten und die Kennzahlen. `unit` gibt die Anzeigeeinheit einer Kennzahl an. Bei einer Dauer ist das `ms`.

- Eine `timeseries` liefert eine Zeile pro Balken und Gruppe. Sie berücksichtigt die Gruppen mit dem höchsten Rang nach der ersten Kennzahl über den
  gesamten Zeitraum.
- Eine `toplist` oder `table` liefert eine Zeile pro Gruppe in der angeforderten Reihenfolge, bis zu `limit`.
- Eine `distribution` liefert 40 Balken vom kleinsten Wert bis zum 99. Perzentil. Der letzte Balken zählt auch die Werte oberhalb des Perzentils.
  Als Name eines Balkens dient seine Untergrenze in der Anzeigeeinheit des Werts.

`limit` gibt an, wie viele Zeilen das Panel anfordert. Die Anfrage liefert `400`, wenn ein Feld im gewählten Typ fehlt, wenn die Angaben für das Diagramm nicht ausreichen
(etwa bei einer `toplist` ohne genau ein Gruppierungsfeld oder einer `timeseries` ohne `interval`) oder wenn `interval` weder eine Variable noch
eine Dauer ist.

## Funnels, Pfade und Nutzerbindung

Die drei Endpunkte unter `/api/v1/rum/analytics` beantworten die Fragen der [RUM-Analysen](/de/rum/analytics). Jeder akzeptiert die
Auswahlparameter von `search` für Sitzungen, Seitenaufrufe und Aktionen: `from` und `to` in Mikrosekunden sowie `filters`, die jede
Zeile erfüllen muss, in der Regel die Anwendung (`application.id`) und die Umgebung (`env`). Bei `GET` stehen die Listen als JSON in den
Parametern, sodass sich die Abfrage als Link weitergeben lässt. `POST` erwartet dieselben Parameternamen im JSON-Body. Die Endpunkte erfordern `rum.analytics.read` oder `sys.telemetry.read`
im geschützten Geltungsbereich `_sys`. Dauert die Zählung zu lange oder ist das System ausgelastet, liefert die Antwort keine Zahlen und setzt `unavailable`
auf `time_budget` oder `busy`. Die Antworten enthalten die zugehörigen Werte für `from` und `to`.

### Funnel

```http
GET /api/v1/rum/analytics/funnel?filters=[{"field":"application.id","op":"=","value":"shop-web"}]&steps=[{"type":"views","filters":[{"field":"view.url_path_group","op":"=","value":"/cart"}]},{"type":"actions","name":"Paid","filters":[{"field":"action.target.name","op":"=","value":"Pay now"}]}]&windowSecs=1800&breakdown=browser.name
```

| Parameter | Typ | Verhalten |
|---|---|---|
| `from`, `to` | Ganzzahl | Mikrosekunden. Ohne Angabe gelten die letzten 7 Tage. |
| `filters` | Liste | Filter, die jeder Schritt zusätzlich zu seinen eigenen Filtern erfüllen muss. |
| `steps` | Liste | Erforderlich. 2 bis 8 Schritte. Jeder Schritt hat einen `type` (`views` oder `actions`), eine Liste von `filters` wie in `search` für die Zeilen dieses Typs und optional einen `name`. Ohne `name` gilt der Wert des ersten Filters als Name. |
| `windowSecs` | Ganzzahl | Maximale Zeit vom ersten bis zu einem späteren Schritt in Sekunden. Ohne Angabe gibt es kein Zeitlimit. |
| `breakdown` | Zeichenfolge | Textfeld aus den Zeilen des ersten Schritts. Für jeden seiner Werte entsteht ein eigener Funnel. Nur die 10 Werte mit den meisten Sitzungen bleiben erhalten. |

Für den ersten Schritt zählt die erste passende Zeile einer Sitzung. Für jeden weiteren Schritt zählt die erste passende Zeile,
die in derselben Sitzung zeitlich nach der Zeile des vorherigen Schritts liegt.

```json
{
  "groups": [
    {
      "value": null,
      "steps": [
        { "name": "/cart", "sessions": 4, "conversion": 1.0, "fromPrevious": null, "medianMs": null },
        { "name": "Paid", "sessions": 2, "conversion": 0.5, "fromPrevious": 0.5, "medianMs": 210000.0 }
      ]
    }
  ],
  "from": 1779400000000000,
  "to": 1780000000000000
}
```

Eine Gruppe enthält den Funnel für die Sitzungen mit demselben `breakdown`-Wert. Die Gruppen sind nach der Anzahl der Sitzungen im ersten Schritt sortiert.
Für die Gesamtgruppe und für die Gruppe der Sitzungen ohne Feldwert ist `value` gleich `null`. `conversion` ist der Anteil an den
Sitzungen des ersten Schritts, `fromPrevious` der Anteil an den Sitzungen des vorherigen Schritts und `medianMs` der Median der Zeitabstände
zum vorherigen Schritt. Wo eine Kennzahl nicht anwendbar ist, lautet ihr Wert `null`. Wenn das Feld kein Textfeld ist oder beim gewählten Typ fehlt,
schlägt die Anfrage mit `400` fehl.

### Pfade

| Parameter | Typ | Verhalten |
|---|---|---|
| `from`, `to`, `filters` | | Wie in `funnel`. Die Zeilen entsprechen den Seitenaufrufen. |
| `anchor` | Zeichenfolge | Seite, an der die Pfade beginnen oder bei Rückwärtsanalyse enden. Ohne Angabe gilt die erste Seite jeder Sitzung, bei Rückwärtsanalyse die letzte. |
| `backward` | boolesch | Verfolgt die Seiten vor dem Anker. Standard: `false`. |
| `depth` | Ganzzahl | 1 bis 6 Seiten nach dem Anker oder bei Rückwärtsanalyse davor. Standard: 3. |
| `by` | Zeichenfolge | Feld zur Identifizierung einer Seite: `view.url_path_group` (Standard), `view.url_path` oder `view.name`. |

```json
{
  "columns": 3,
  "sessions": 9,
  "backward": false,
  "nodes": [
    { "column": 0, "page": "/products", "sessions": 2, "ends": 0 },
    { "column": 1, "page": "/cart", "sessions": 2, "ends": 0 },
    { "column": 2, "page": "/checkout", "sessions": 1, "ends": 1 }
  ],
  "links": [
    { "column": 0, "source": "/products", "target": "/cart", "sessions": 2 },
    { "column": 1, "source": "/cart", "target": "/checkout", "sessions": 1 }
  ],
  "from": 1779400000000000,
  "to": 1780000000000000
}
```

Die Seiten stehen in `columns`. Es gibt eine Spalte mehr als `depth`. Die Ankerseite steht in Spalte 0 (bei Rückwärtsanalyse in der letzten Spalte).
Ein Knoten steht für eine Seite in einer Spalte. `sessions` zählt die Sitzungen auf dieser Seite, `ends` die Sitzungen, die dort endeten
(bei Rückwärtsanalyse: die dort begannen). Eine Verbindung führt von einer Seite in `column` zu einer Seite in der nächsten Spalte (auch bei Rückwärtsanalyse
zur zeitlich folgenden) und zählt die Sitzungen mit diesem Übergang. Maßgeblich ist die Reihenfolge der Aufrufe. Direkt aufeinanderfolgende Aufrufe derselben Seite zählen nur einmal.
Jede Spalte führt die 8 Seiten mit den meisten Sitzungen einzeln auf und fasst die übrigen unter `__other__` zusammen. `sessions` ist die Anzahl der Sitzungen,
in denen die Ankerseite vorkommt.

### Nutzerbindung

| Parameter | Typ | Verhalten |
|---|---|---|
| `from`, `to`, `filters` | | Wie in `funnel`. Die Zeilen entsprechen den Sitzungen. Ohne `from` und `to` reicht der Zeitraum für die Kohortenbildung doppelt so viele Perioden zurück wie in `periods` angegeben, mindestens aber 14 Tage (8 Wochen bei `week`). |
| `period` | `day` oder `week` | Ein Tag nach UTC oder eine Woche nach UTC, die am Montag beginnt. Standard: `day`. |
| `periods` | Ganzzahl | 1 bis 30 Perioden nach der ersten. Standard: 7. |

```json
{
  "period": "day",
  "periods": 3,
  "cohorts": [
    { "startTime": 1779408000000000, "users": 1, "returned": [1, 0, null] },
    { "startTime": 1779494400000000, "users": 6, "returned": [0, null, null] }
  ],
  "from": 1779408000000000,
  "to": 1779753600000000
}
```

Eine Kohorte umfasst alle Personen, die im abgefragten Zeitraum erstmals in der Periode ab `startTime` erscheinen. Als Personenkennung dient
`usr.id` der Sitzung oder, falls dieser Wert fehlt, `usr.anonymous_id`. `returned` gibt für jede Folgeperiode an, wie viele Personen aus der
Kohorte erneut erschienen. Für Perioden, die zum Zeitpunkt `to` noch nicht abgeschlossen sind, lautet der Wert `null`.

## Heatmaps

Die Endpunkte unter `/api/v1/rum/heatmaps` liefern die Kennzahlen für [RUM-Heatmaps](/de/rum/heatmaps). Sie akzeptieren `from` und `to` in Mikrosekunden sowie `filters`, in der Regel `application.id`, `view.url_path_group` und die Fensterbreite (`display.viewport.width`). Bei `GET` steht die Liste als JSON im Parameter. `clicks` und `scroll` akzeptieren zusätzlich `limit` und erfordern `rum.analytics.read`. Sie zählen die gespeicherten Zeilen, statt die Werte zu schätzen.

```json
{
  "clicks": 148,
  "elements": [
    {
      "element": "body>main>button:nth-of-type(2)",
      "name": "Pay now",
      "selector": "button.pay",
      "clicks": 92,
      "sessions": 60,
      "frustrated": 4,
      "pageX": 640.5,
      "pageY": 720.0,
      "cells": [[5, 4, 31], [6, 4, 28]]
    }
  ],
  "from": 1779400000000000,
  "to": 1780000000000000
}
```

`clicks` liefert die Elemente mit den meisten Klicks. Zulässig sind 1 bis 300 Elemente, der Standard ist 100. `element` gibt die Position des Elements auf der Seite an. `pageX` und `pageY` geben die durchschnittliche Position der Klicks auf das Element in Seitenkoordinaten an. `cells` unterteilt das Element in ein Raster von 10 mal 10 Zellen, jeweils im Format `[column, row, clicks]`.

```json
{
  "views": 310,
  "pageHeight": 4200,
  "medianDepth": 1800,
  "bands": [{ "depth": 800, "reached": 1.0 }, { "depth": 900, "reached": 0.97 }],
  "from": 1779400000000000,
  "to": 1780000000000000
}
```

`scroll` liefert die Seitenaufrufe mit erfasster Scrolltiefe, die Seitenhöhe und die Scrolltiefe, die die Hälfte dieser Aufrufe erreichte. Ein Abschnitt ist 100 Pixel hoch. `reached` gibt den Anteil der Seitenaufrufe an, die diese Tiefe erreichten. Mit zunehmender Tiefe kann der Anteil nicht steigen.

`snapshot` akzeptiert die `viewId` eines Kandidaten und erfordert `rum.replay.read`. `candidates` enthält bis zu 20 Seitenaufrufe mit Sitzungsaufzeichnung, die neuesten zuerst. Jeder Eintrag enthält `sessionId`, `viewId`, `atTime` sowie `width` und `height` des Fensters. `snapshot` enthält dieselben Felder für den dargestellten Seitenaufruf sowie die rrweb-`events`, die den Zustand zum Zeitpunkt `atTime` ab dem letzten vollständigen Snapshot davor rekonstruieren. `snapshot` ist `null`, wenn keine Sitzung mit einem Aufruf der Seite aufgezeichnet wurde.

## Playlists

Eine [Playlist](/de/rum/playlists) ist eine benannte Liste von Sitzungen einer Anwendung. Zu jeder Sitzung gehört der Zeitpunkt, an dem sich das Öffnen lohnt.

```json
{
  "id": "2xT9bQ1kLw5nVf8cZ0aR7mHpJd3",
  "application": "checkout-web",
  "name": "Checkout failures",
  "description": "Sessions that ended at the checkout with an error.",
  "createdBy": "<user-id>",
  "createdAt": 1790000000000000,
  "updatedAt": 1790000100000000,
  "sessionCount": 2,
  "sessions": [
    { "sessionId": "3f6c9a52-1b7e-4d08-a5c3-90e2d41f7b68", "atTime": 1790000005000000, "addedBy": "<user-id>", "addedAt": 1790000000000000 },
    { "sessionId": "9d41e7b0-62fa-4c3d-8e15-b7a09c52d3f4", "atTime": null, "addedBy": "<user-id>", "addedAt": 1790000100000000 }
  ]
}
```

`GET /api/v1/rum/playlists` liefert die Playlists ohne `sessions`, die zuletzt geänderte zuerst. `application` grenzt die Ergebnisse auf
eine Anwendung ein. Lesezugriffe erfordern `rum.playlists.read`; Aufrufe auf Plattformebene können `sys.telemetry.read` verwenden. Die übrigen Anfragen ändern eine Playlist
und erfordern `rum.playlists.manage`. Sie liefern jeweils die Playlist mit ihren Sitzungen zurück. Nur `DELETE` liefert `{ "deleted": true }`.

| Anfrage | Body | Regel |
|---|---|---|
| `POST /rum/playlists` | `application`, `name` und optional `description` und `sessions` | Die Anwendung muss existieren (`404`). Der Name umfasst 1 bis 128 Zeichen und muss innerhalb der Anwendung eindeutig sein, unabhängig von der Groß- und Kleinschreibung (`409`). Die Beschreibung umfasst höchstens 1.000 Zeichen. |
| `PATCH /rum/playlists/{id}` | `name` und `description`, beide optional | Nicht angegebene Felder behalten ihren Wert. Die Anwendung lässt sich nicht ändern. |
| `POST /rum/playlists/{id}/sessions` | `sessions` | Beim erneuten Hinzufügen einer Sitzung übernimmt sie den neuen Wert für `atTime` und behält ihre Position. Eine Playlist enthält höchstens 500 Sitzungen (`400`). |

Eine Sitzung hat in einer Anfrage die Form `{ "sessionId": "...", "atTime": 1790000005000000 }`. Die ID umfasst 1 bis 128 Zeichen. Der optionale Wert `atTime`
gibt in Mikrosekunden seit der Unix-Epoche an, an welcher Stelle sich die Sitzung öffnet. Ohne ihn öffnet sich die Sitzung am Anfang. Die
Playlist speichert IDs, keine Sitzungen. Sie prüft nicht, ob eine Sitzung existiert. Löscht die Aufbewahrungsrichtlinie die Zeilen einer Sitzung, bleibt deren ID
in der Liste. `GET /api/v1/rum/sessions/{id}/playlists` liefert die Playlists, die diese Sitzung enthalten, ohne deren Sitzungslisten.

## Einzelne Zeile oder Sitzung abrufen

`GET /api/v1/rum/{type}/{id}` gibt eine Zeile mit allen Spalten oder `404` zurück. `from` und `to` grenzen den Suchzeitraum ein. Ohne
diese Angaben umfasst die Suche die letzten 30 Tage. `{id}` ist der Wert von `idField` des Typs.

`GET /api/v1/rum/sessions/{id}/timeline` gibt Folgendes zurück:

| Feld | Inhalt |
|---|---|
| `session` | Die Sitzungszeile oder `null`, solange noch keine Zeile für die Sitzung abgeleitet wurde. |
| `items` | Die zur Sitzung gehörenden Zeilen aller anderen Typen, beginnend mit der ältesten. Jede Zeile hat einen `type`: `view`, `action`, `error`, `resource`, `long_task`, `vital` oder `log`. |
| `truncated` | Die Typen, für die mehr Zeilen vorliegen, als die Zeitleiste aufnehmen kann. |

`GET /api/v1/rum/sessions/{id}/related-traces` listet die Backend-Traces einer Sitzung auf. Der Endpunkt gibt die Traces zurück, deren ID eine Anfrage
der Sitzung enthielt (`relation: direct`). Gibt es keine solchen Traces, gibt der Endpunkt die Traces zurück, die während der Sitzung liefen
(`relation: time-correlated`). Jeder Trace enthält `trace_id`, `service`, `spanCount`, `durationMs` und
`startedAt`. Die Antwort enthält außerdem `primaryService`. `GET /api/v1/rum/traces/{traceId}/session` sucht in umgekehrter Richtung
und gibt die Sitzung oder `null` zurück.

## Kommentare

```http
POST /api/v1/rum/sessions/{id}/comments
```

```json
{ "application": "checkout-web", "atTime": 1790000005000000, "body": "The button does nothing here." }
```

`atTime` bezeichnet einen Zeitpunkt innerhalb der Sitzung in Mikrosekunden seit der Unix-Epoche. `body` umfasst 1 bis 2.000 Zeichen. Eine Sitzung kann höchstens 500 Kommentare enthalten. `GET` gibt `{ "comments": [...] }` in chronologischer Reihenfolge zurück und erfordert `rum.replay.read`.

```json
{
  "id": "2xT9bQ1kLw5nVf8cZ0aR7mHpJd3",
  "application": "checkout-web",
  "sessionId": "3f6c9a52-1b7e-4d08-a5c3-90e2d41f7b68",
  "atTime": 1790000005000000,
  "body": "The button does nothing here.",
  "authorId": "<user-id>",
  "authorName": "Ada",
  "createdAt": 1790000010000000,
  "updatedAt": 1790000010000000,
  "editable": true
}
```

`POST` erfordert `rum.replay.comments.write`. `PATCH` akzeptiert `body`. Für `PATCH` und `DELETE` gilt: Eigene Kommentare erfordern diese Berechtigung, fremde Kommentare `rum.replay.comments.manage`. `editable` gibt an, ob der Kommentar bearbeitet werden darf. `DELETE` gibt `{ "deleted": true }` zurück.

## Zusammenfassung

`GET /api/v1/rum/sessions/{id}/summary` gibt `{ "summary": ... }` mit der gespeicherten Zusammenfassung in der Sprache der anfragenden Person oder `null` zurück und erfordert `rum.replay.read`. `POST` erstellt mit einem Modell eine Zusammenfassung und erfordert `rum.replay.summaries.generate`. Der Endpunkt gibt eine gespeicherte Zusammenfassung ohne Modellaufruf zurück. Mit `{ "regenerate": true }` ruft er das Modell auf, sofern sich die Sitzung geändert hat.

```json
{
  "summary": {
    "sessionId": "3f6c9a52-1b7e-4d08-a5c3-90e2d41f7b68",
    "language": "en-us",
    "summary": "The user filled the cart and could not pay: the payment call failed three times.",
    "chapters": [{ "atTime": 1790000005000000, "title": "Fills the cart", "summary": "Adds two items." }],
    "model": "<model>",
    "promptTokens": 1820,
    "completionTokens": 240,
    "generatedAt": 1790000020000000
  }
}
```

Der Aufruf zählt mit der Herkunft `replay_summary` zum Tagesbudget von Mole Agent. Bei ausgeschöpftem Budget gibt der Endpunkt `429` zurück. Fehlt in der Organisation ein aktivierter Modellanbieter mit hinterlegtem Schlüssel oder enthält die Sitzung keine zusammenfassbaren Daten, gibt er `400` zurück.

## Issues

MoleSignal fasst ähnliche Fehler zu [Issues](/de/rum/errors) zusammen. Jede Fehlerzeile enthält die ID des zugehörigen Issues in `error.issue_id`.
MoleSignal berechnet die Kennzahlen eines Issues anhand seiner Fehler im abgefragten Zeitraum. Status und Verlauf speichert MoleSignal separat.
Zeitangaben erfolgen in Mikrosekunden seit der Unix-Epoche.

```http
GET /api/v1/rum/issues?application=checkout-web&status=unresolved&sort=sessions&limit=50
```

| Parameter | Typ | Verhalten |
|---|---|---|
| `application` | String | Erforderlich. |
| `env`, `source` | String | Nur Fehler aus dieser Umgebung oder von dieser Quelle (`browser`, `flutter` usw.). |
| `filters` | Liste | Zusätzliche Bedingungen für die zu zählenden Fehler, wie in `search`. |
| `from`, `to` | Ganzzahl | Wie in `search`. |
| `status` | String | `unresolved` (Standard: offen, in Untersuchung oder erneut aufgetreten), `all` oder einer der Werte `open`, `investigating`, `regressed`, `resolved`, `ignored`. |
| `assignee`, `team` | String | Eine Benutzer-ID oder Team-ID oder `none` für nicht zugewiesene Issues. |
| `search` | String | Sucht nach Wörtern im Typ, in der Meldung oder am Ort des Issues, unabhängig von der Groß- und Kleinschreibung. |
| `fresh` | Boolean | Nur Issues, die im Zeitraum erstmals oder erneut aufgetreten sind. |
| `sort` | String | `sessions` (Standard), `users`, `occurrences`, `lastSeen`, `firstSeen` oder `status`. |
| `order` | `asc` oder `desc` | Ohne Angabe absteigend, außer bei `status`. |
| `limit` | Ganzzahl | 1 bis 100. Standardwert: 50. |

```json
{
  "issues": [
    {
      "id": "3f9c2a71e0b4c8d1",
      "applicationId": "checkout-web",
      "status": "regressed",
      "assigneeId": "<user-id>",
      "teamId": null,
      "overflow": false,
      "source": "source",
      "errorType": "ChunkLoadError",
      "message": "Loading chunk 482 failed.",
      "location": "src/router/lazy.ts:34 · loadChunk",
      "firstSeenAt": 1789300000000000,
      "lastSeenAt": 1790000000000000,
      "firstVersion": "2.2.0",
      "lastVersion": "2.4.1",
      "resolvedAt": 1789600000000000,
      "resolvedVersion": "2.3.0",
      "resolvedBy": "<user-id>",
      "regressedAt": 1789900000000000,
      "regressedVersion": "2.4.1",
      "regressedEnvironment": "production",
      "updatedBy": null,
      "updatedAt": 1789900000000000,
      "sessions": 612,
      "users": 498,
      "occurrences": 1530,
      "trend": [3, 5, 4, 9, 40, 120]
    }
  ],
  "total": 8
}
```

`regressedEnvironment` enthält die Umgebung des Fehlers, durch den das Issue erneut auftrat, oder `null`, wenn der Fehler keine Umgebung angibt. Ein Issue
gehört zur gesamten Anwendung, unabhängig davon, in welchen Umgebungen seine Fehler auftreten. Der Server speichert außerdem für jede Umgebung,
wann das Issue dort erstmals auftrat. Anhand dieser Zeitpunkte zählen [Alarmregeln](/de/rum/alerts#regel-eingrenzen) neue Issues pro Umgebung.

Der Endpunkt liest die 250 Issues mit den meisten Sitzungen (oder je nach `sort` mit den meisten Benutzern oder Vorkommen) und filtert sie nach `status`, `assignee`,
`team`, `search` und `fresh`. `total` gibt an, wie viele Issues nach dem Filtern und vor der Begrenzung durch `limit` verbleiben. `trend` enthält die Anzahl der Vorkommen
pro Teilzeitraum. Der Endpunkt teilt den Zeitraum in bis zu 12 gleich lange Abschnitte ein und beginnt mit dem ältesten. `overflow` kennzeichnet das Issue, das die Fehler einer Anwendung erfasst, nachdem die Anwendung
das [stündliche Limit für neue Issues](/de/rum/errors#neue-probleme-pro-stunde) erreicht hat. Dauert die Zählung zu lange oder ist das System ausgelastet,
gibt der Endpunkt keine Issues zurück und setzt `unavailable` auf `time_budget` bzw. `busy`.

`GET /api/v1/rum/issues/{id}` gibt das Issue im gleichen Format wie die Liste zurück, jedoch ohne `trend`. Der Endpunkt zählt `sessions`, `users` und `occurrences`
für den Zeitraum von `from` bis `to` und ergänzt zwei Felder:

| Feld | Inhalt |
|---|---|
| `samples` | Die letzten drei Sitzungen, in denen das Issue auftrat, beginnend mit der neuesten: `timestamp`, `sessionId`, `userId`, `anonymousId`, `page`, `browser`, `system`, `version`, `hasReplay` und `retained`. `retained` ist `false`, wenn die Sitzung zum Fehler nicht gespeichert wurde und sich daher nicht öffnen lässt. |
| `stack` | Der Stack des neuesten Fehlers mit Frames. Hat kein Fehler Frames, verwendet der Endpunkt den neuesten Fehler mit leerem `frames`. Gibt es im Zeitraum keinen Fehler des Issues, lautet der Wert `null`. Der Stack enthält `message`, `text`, `frames`, `symbolication`, `handling`, `isCrash` und `category`. Ein Frame enthält `raw` (die vom SDK gesendeten Daten), `restored` (das Ergebnis der Auflösung anhand eines Debug-Artefakts oder `null`) und `inApp`. Nach einem Auflösungsversuch lautet `symbolication` `completed`, `partial` oder `missing`. |

Existiert das Issue nicht, gibt der Endpunkt `404` zurück.

`PATCH /api/v1/rum/issues/{id}` akzeptiert `status`, `assigneeId` und `teamId` einzeln oder kombiniert und gibt das Issue nach der Änderung zurück.

```json
{ "status": "resolved", "assigneeId": "<user-id>", "teamId": null }
```

Gültige Werte für `status` sind `open`, `investigating`, `resolved` und `ignored`. Die Regeln setzen `regressed`, wenn ein behobenes Issue in
einer neueren Version erneut auftritt. Gibt die Anfrage `regressed` an, antwortet der Endpunkt mit `400`. `assigneeId` muss ein Mitglied der Organisation bezeichnen und `teamId` ein Team dieser Organisation. `null` oder eine
leere Zeichenfolge hebt die jeweilige Zuweisung auf. Nicht angegebene Felder bleiben unverändert. Beim Beheben speichert der Endpunkt `resolvedAt`, `resolvedBy` und die neueste Version
der Anwendung als `resolvedVersion`. Jeder Statuswechsel beendet den Eintrag zu einer früheren Behebung oder Regression. Gibt die Anfrage kein zu änderndes Feld an, antwortet der Endpunkt mit `400`. Stimmen alle angegebenen Werte mit den aktuellen Werten überein, antwortet er mit `200` und ändert nichts. Der Endpunkt protokolliert jede Änderung als `rum.issue.update` im Audit-Log.

## Vorschau für eine Alarmregel anzeigen

```http
POST /api/v1/rum/alerts/preview
```

Ermittelt Zeitfenster für Zeitfenster, welche Werte eine [Alarmregel für eine RUM-Kennzahl](/de/rum/alerts) im zurückliegenden Zeitraum ausgewertet hätte. Dazu verwendet der Endpunkt
denselben Code wie bei der Regelauswertung. Der Endpunkt erfordert `rum.events.read`.

```json
{
  "query": { "applicationId": "checkout-web", "environment": "production", "page": "/checkout", "metric": "lcp_p75" },
  "periodSecs": 3600
}
```

| Feld | Typ | Verhalten |
|---|---|---|
| `query` | Objekt | Pflichtfeld. Definiert die Kennzahl mit `applicationId` und `metric` sowie, falls angegeben, mit `environment`, `page`, `version` und `minSamples`. Der Endpunkt lehnt `page` und `version` ab, wenn sich die Kennzahl nicht danach filtern lässt. Bei einer Zählung lehnt er `minSamples` ab. Für `custom_vital` und `custom_timing` ist zusätzlich `customName` erforderlich. Beide unterstützen auch `statistic`. In `query` ist `search` erforderlich und enthält `type`, den unveränderten Ausdruck in `statement`, die daraus ermittelten `filters` und `freeText` sowie `measure` (`fn` und `field`). Siehe [Regel erstellen](/de/api/alerting/create-rule#rum-regeln). |
| `periodSecs` | Ganzzahl | Pflichtfeld. Dauer des Zeitfensters für die Regelauswertung in Sekunden, von 60 bis 21.600. Jeder Datenpunkt entspricht einem Zeitfenster. |
| `from`, `to` | Ganzzahl | Zeitraum in Mikrosekunden seit der Unix-Epoche. Der Endpunkt wertet nur vollständige Zeitfenster aus. `to` entspricht standardmäßig dem aktuellen Zeitpunkt. `from` liegt standardmäßig sechs Stunden vor `to`. Dabei begrenzt der Endpunkt den Standardzeitraum auf 12 bis 72 Zeitfenster und höchstens einen Tag. Ein Zeitraum umfasst höchstens 360 Zeitfenster. |

```json
{
  "metric": "lcp_p75",
  "unit": "milliseconds",
  "minSamples": 50,
  "periodSecs": 3600,
  "from": 1789956800000000,
  "to": 1790000000000000,
  "points": [
    { "at": 1789956800000000, "value": null, "samples": null },
    { "at": 1789960400000000, "value": 2480, "samples": 612 }
  ],
  "current": { "at": 1789996400000000, "value": 2310, "samples": 540 }
}
```

`unit` ist `count`, `percent`, `milliseconds`, `score`, `bytes` oder `none`. Ein Datenpunkt enthält in `at` den Beginn des Zeitfensters, in `value` den Kennzahlenwert und in
`samples` die Zeilen, aus denen der Endpunkt den Wert berechnet. Enthält ein Zeitfenster weniger Zeilen als in `minSamples` angegeben, fehlen `value` und `samples`. `current` ist der letzte Datenpunkt und gehört zu
dem Zeitfenster, das bei `to` endet. Dauert eine Zählung zu lange oder ist das System ausgelastet, liefert der Endpunkt keine Datenpunkte und setzt `unavailable` auf
`time_budget` bzw. `busy`. Existiert die Anwendung nicht, gibt der Endpunkt `404` zurück. Passt die Regel nicht zur Kennzahl, gibt er `400` zurück.

## Fehler

| Status | Ursache |
|---|---|
| `400` | Ein Parameter, Filter, eine Spalte oder ein Cursor passt nicht zur Anfrage. |
| `401`, `403` | Das Token fehlt, ist ungültig oder hat nicht die Berechtigung, die der Endpunkt erfordert. |
| `404` | Die Zeile, Sitzung oder Anwendung existiert nicht. |
| `409` | Eine Anwendung mit dieser ID oder diesem Namen existiert bereits. |
| `413` | Die Anfrage überschreitet die Grenzwerte für [`events`](/de/rum/events#ereignisse-senden). |
