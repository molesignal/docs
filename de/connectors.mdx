Ein **Konnektor** ist eine verwaltete Integration mit einer externen Plattform. Konnektoren arbeiten in zwei Richtungen:

- **Quellen** bringen Daten aus einem anderen Dienst ein und schreiben sie in einen Stream. MoleSignal ruft CloudWatch Logs, Kafka-Topics und S3-Objekte nach einem Zeitplan ab. Amazon Data Firehose, Google Cloud Pub/Sub, Cloudflare Logpush und Heroku senden an MoleSignal; Firehose überträgt außerdem CloudWatch-Metriken.
- **Ziele** empfangen die Ausgabe einer [geplanten Pipeline](/de/pipelines#schreibziele-und-zustellung-an-konnektoren): Amazon S3 und S3-kompatibler Speicher, Apache Kafka und jeder HTTP-Endpunkt.

| Art | Konnektor | Richtung | Authentifizierung |
|---|---|---|---|
| `aws_cloudwatch_logs` | AWS CloudWatch Logs | Quelle, alle 30 Sekunden abgerufen | [AWS-Anmeldedaten](#aws-authentifizierung) |
| `kafka_source` | Kafka-Topic | Quelle, alle 30 Sekunden abgerufen | Keine, SASL oder ein Client-Zertifikat |
| `s3_source` | S3-Objekte | Quelle, alle 30 Sekunden abgerufen | AWS-Anmeldedaten |
| `gcp_pubsub_pull` | Google Cloud Pub/Sub-Abonnement | Quelle, alle 30 Sekunden abgerufen | Dienstkonto-Schlüssel |
| `aws_cloudwatch_metrics`, `azure_monitor_metrics`, `gcp_monitoring_metrics`, `aliyun_cms_metrics`, `tencent_monitor_metrics`, `huawei_ces_metrics` | [Cloud-Metriken](#cloud-metriken) | Quelle, pro Zeitraum abgerufen | Die Anmeldedaten der jeweiligen Cloud |
| `aws_kinesis_firehose` | Amazon Data Firehose | Quelle, gepusht | [Push-Token](#push-quellen) |
| `gcp_pubsub_push` | Google Cloud Pub/Sub-Push | Quelle, gepusht | Push-Token, optional mit dem OIDC-Token des Abonnements |
| `cloud_events` | Cloud-Event-Bus | Quelle, gepusht | Push-Token |
| `cloudflare_logpush` | Cloudflare Logpush | Quelle, gepusht | Push-Token |
| `heroku_drain` | Heroku-Log-Drain | Quelle, gepusht | Push-Token |
| `s3` | Amazon S3 | Ziel | AWS-Anmeldedaten |
| `kafka` | Apache Kafka | Ziel | Keine, SASL oder ein Client-Zertifikat |
| `http` | HTTP / Webhook | Ziel | Keine, ein Bearer-Token, Basic-Auth, ein benutzerdefinierter Header oder eine HMAC-Signatur |

## Konnektor erstellen

<Steps>
  <Step title="Konnektoren öffnen">
    Gehen Sie zu **Pipelines → Konnektoren**. Die Seite listet **Quellen** und **Ziele** auf.
  </Step>
  <Step title="Art auswählen">
    Klicken Sie auf **Neuer Konnektor** und wählen Sie, womit verbunden werden soll.
  </Step>
  <Step title="Einstellungen ausfüllen">
    Tragen Sie unter **Name** einen innerhalb der Organisation eindeutigen Wert ein, geben Sie an, woher der Konnektor Daten bezieht oder wohin er sie liefert, und wählen Sie die **Authentifizierung**.
  </Step>
  <Step title="Testen und erstellen">
    Klicken Sie auf **Verbindung testen**, um die Einstellungen vor dem Speichern zu prüfen, und klicken Sie dann auf **Konnektor erstellen**. Eine Push-Quelle hat kein Verbindungsziel und bietet keinen Test.
  </Step>
</Steps>

Über die API besteht ein Konnektor aus einem `name`, einem `kind` und einem `configJson`, dessen Schlüssel von der Art abhängen. `auth` in `configJson` benennt die Art der Authentifizierung, und jede Art verwendet eigene Schlüssel. Einstellungen, die nicht funktionieren können, liefern beim Speichern `400`: ein fehlender erforderlicher Schlüssel, die Hälfte eines Anmeldedatenpaars oder ein Schlüssel, den das gewählte `auth` nicht verwendet.

```bash
curl -X POST http://localhost:5080/api/v1/connectors \
  -H "authorization: Bearer $MS_TOKEN" \
  -H 'content-type: application/json' \
  -d '{
        "name": "archive",
        "kind": "s3",
        "configJson": {
          "bucket": "acme-logs",
          "region": "eu-west-1",
          "prefix": "pipelines/checkout/",
          "auth": "assume_role",
          "roleArn": "arn:aws:iam::123456789012:role/molesignal-delivery"
        }
      }'
```

## Secrets

Diese Schlüssel von `configJson` enthalten Secrets:

| Art | Secret-Schlüssel |
|---|---|
| `s3`, `aws_cloudwatch_logs` | `accessKey`, `secretKey`, `sessionToken` |
| `aws_kinesis_firehose`, `gcp_pubsub_push`, `cloud_events`, `cloudflare_logpush`, `heroku_drain` | `pushToken` |
| `aws_cloudwatch_metrics` | `accessKey`, `secretKey`, `sessionToken` |
| `azure_monitor_metrics` | `clientSecret` |
| `gcp_monitoring_metrics`, `gcp_pubsub_pull` | `serviceAccountKey` |
| `aliyun_cms_metrics`, `tencent_monitor_metrics`, `huawei_ces_metrics` | `accessKey`, `secretKey` |
| `kafka` | `saslPassword`, `tlsClientKey` |
| `http` | `url`, `bearerToken`, `basicPassword`, `headerValue`, `hmacSecret` |

Ein Secret verlässt die API nie. Eine Antwort zeigt an seiner Stelle `***` und nennt in `secretKeys` die Secrets, die einen Wert enthalten:

```json
{
  "kind": "kafka",
  "configJson": {
    "brokers": "b-1.example.com:9096",
    "topic": "logs",
    "tls": true,
    "auth": "sasl_scram_sha_512",
    "saslUsername": "molesignal",
    "saslPassword": "***"
  },
  "secretKeys": ["saslPassword"]
}
```

- Eine Aktualisierung, die `***` zurücksendet, behält den gespeicherten Wert bei, sodass ein Konnektor umbenannt, deaktiviert oder auf ein anderes Ziel gerichtet werden kann, ohne seine Anmeldedaten erneut einzugeben. In der UI behält ein gespeichertes Secret, das leer gelassen wird, seinen Wert.
- Ein Secret, das in einer Aktualisierung fehlt, wird entfernt.
- Eine Aktualisierung, die den `kind` ändert, behält keines der gespeicherten Secrets bei.

MoleSignal versiegelt die Secrets getrennt von den anderen Einstellungen mit dem Stammschlüssel aus `MS_CIPHER_KEY` (AES-256-GCM) und speichert kein Secret im Klartext. Eine Push-Quelle wird anhand des SHA-256-Hashwerts ihres Tokens gefunden. `molesignal rewrap-kek` versiegelt die Konnektor-Secrets zusammen mit den anderen Secrets neu, wenn der Stammschlüssel rotiert wird. Siehe [Produktions-Checkliste](/de/deployment/production-checklist).

## Quellen

### Push-Quellen

Die fünf Push-Quellen teilen ein Modell: Erstellen Sie einen Connector mit einem **`pushToken`** und einem **`targetStream`** und richten Sie dann die Plattform auf den passenden Endpoint. Diese Endpoints verwenden nicht das JWT. Die Anfrage authentifiziert sich mit dem Push-Token, übergeben auf jede Weise, die die Plattform erlaubt:

| Methode | Verwendet von |
|---|---|
| `X-Connector-Token`-Header | Plattformen mit konfigurierbaren Headern, wie Cloudflare |
| `X-Amz-Firehose-Access-Key`-Header | Amazon Data Firehose, das ihn automatisch sendet |
| `X-EventBridge-Signature-Token`-Header | Alibaba Cloud EventBridge |
| `?token=`-Query-Parameter | Plattformen, die keine Header setzen können, wie Heroku und Pub/Sub |
| Passwort von `Authorization: Basic` | Plattformen, die Anmeldedaten in die Adresse setzen |

Die UI generiert das Token, wenn sie den Connector erstellt, und zeigt es einmal an, zusammen mit dem Endpoint, den Sie der Plattform geben. Das Token kann nicht erneut gelesen werden. **Neues Token generieren** ersetzt es, wenn der Connector gespeichert wird. Über die API übergeben Sie einen `pushToken` mit mindestens 16 Zeichen. Ein Token öffnet einen Connector einer Art: Ein bereits verwendetes Token antwortet mit `409`. Eine Anfrage mit fehlendem oder unbekanntem Token oder für einen Connector, der ausgeschaltet ist, antwortet mit `401`. Ein Connector ohne Token akzeptiert nichts. Ein Knoten behält einen Connector, den er nachgeschlagen hat, 30 Sekunden lang, sodass das Ausschalten eines Connectors oder das Ersetzen seines Tokens innerhalb dieser Zeit wirksam wird.

Anfragekörper, die mit `Content-Encoding: gzip` gesendet werden, werden automatisch dekomprimiert. Ein Firehose-Body darf bis zu 64 MiB groß sein, jeder andere bis zu 16 MiB, gezählt auch nach der Dekomprimierung. Ereignisse fließen durch denselben Aufnahmepfad wie alles andere: Schema-on-Write, [Pipelines](/de/pipelines) und [Maskierung](/de/security) gelten alle.

<Tabs>
  <Tab title="Amazon Data Firehose">
    Erstellen Sie den Connector mit `kind: "aws_kinesis_firehose"` und wählen Sie dann das Ziel **HTTP endpoint** für den Firehose-Stream:

    - **HTTP endpoint URL**: `https://molesignal.example.com/api/v1/_kinesis_firehose`
    - **Zugriffsschlüssel**: das Push-Token. Firehose sendet es als `X-Amz-Firehose-Access-Key`.

    Firehose liefert nur an HTTPS auf Port 443 mit einem öffentlich vertrauenswürdigen Zertifikat, daher benötigt eine Bereitstellung in einem privaten Netzwerk einen öffentlichen Einstiegspunkt, siehe [Öffentlicher Zugriff](/de/public-access). Halten Sie den Puffer des Streams bei 1 bis 4 MiB.

    MoleSignal liest jeden Datensatz einzeln, je nachdem, was er enthält:

    | Datensatz | Wird zu |
    |---|---|
    | Eine CloudWatch Logs-Abonnementnachricht, gzip-komprimiert, wie der Abonnementfilter sie sendet | Ein Log-Ereignis pro Eintrag von `logEvents`, zur eigenen Zeit des Eintrags, mit `message`, `log_group`, `log_stream`, `account_id`, `region`, `event_id` und `source: "cloudwatch"`. Der Health Check, den das Abonnement beim Erstellen sendet, wird übersprungen. |
    | Ein CloudWatch-Metric-Streams-Datensatz im JSON-, OpenTelemetry-1.0- oder OpenTelemetry-0.7-Ausgabeformat | Metrik-Samples im Metrik-Stream, siehe unten. |
    | Jeder andere Text | Ein Log-Ereignis pro Zeile: Ein JSON-Objekt liefert die Felder, reiner Text geht in `message`. |

    Ein Metrik-Stream sendet ein Aggregat pro Metrik pro Minute. Jede Statistik wird zu einem Gauge-Sample namens `aws_<namespace>_<metric>_<statistic>`, so wie yet-another-cloudwatch-exporter sie benennt: `aws_ec2_cpuutilization_average`, `aws_ec2_cpuutilization_maximum`, `aws_applicationelb_request_count_sum`. Der Namespace verliert sein Präfix `AWS/`, und der Metrikname wird an den Stellen in Wörter aufgeteilt, an denen ein Kleinbuchstabe auf einen Großbuchstaben trifft. Die Statistiken sind `average` (die Summe über die Sample-Anzahl), `sum`, `sample_count`, `minimum`, `maximum` und jedes Perzentil, das der Stream hinzufügt, wie `p99` oder `p99_9`. Die Labels sind `account_id`, `region` und ein `dimension_<Name>` pro Dimension, wie `dimension_InstanceId`; `metric_unit` behält die Einheit.

    ```promql
    max by (dimension_InstanceId) (aws_ec2_cpuutilization_average)
    ```

    `X-Amz-Firehose-Common-Attributes`, gesetzt als Parameter des Streams, fügt seine Schlüssel jedem Ereignis und Sample hinzu; ein Feld, das der Datensatz bereits hat, hat Vorrang. `X-Amz-Firehose-Source-Arn` liefert die `region` von CloudWatch-Logs-Ereignissen, die keine enthalten.

    Die Antwort folgt der Firehose-Zustellspezifikation: `application/json` mit der `requestId` der Anfrage, einem `timestamp` und einer `errorMessage` bei einem Fehler. Datensätze, die nicht gelesen werden können, bleiben aus, und der Rest der Anfrage wird dennoch mit `200` geschrieben. Ein Schreibvorgang, der vorerst fehlschlägt, antwortet mit `429` oder `5xx`, was Firehose erneut versucht. Ein Body über 64 MiB antwortet mit `413`, was Firehose weder erneut versucht noch sichert. Eine Zustellung, die innerhalb von 30 Minuten nach dem Schreiben erneut versucht wird, mit derselben `X-Amz-Firehose-Request-Id`, wird mit `200` beantwortet, ohne erneut geschrieben zu werden.
  </Tab>
  <Tab title="Google Cloud Pub/Sub">
    Erstellen Sie den Connector mit `kind: "gcp_pubsub_push"`. Leiten Sie Logs mit einem Log Router-Sink an ein Pub/Sub-Topic und erstellen Sie dann ein Push-Abonnement für das Topic. Pub/Sub kann keine benutzerdefinierten Header setzen, daher wird das Token in der URL übertragen:

    ```bash
    gcloud pubsub subscriptions create molesignal-push --topic=molesignal-logs --push-endpoint="https://molesignal.example.com/api/v1/_gcp_pubsub?token=<pushToken>"
    ```

    Um auch das OIDC-Token des Abonnements zu prüfen, setzen Sie `oidcServiceAccount` am Connector auf die E-Mail-Adresse eines Dienstkontos und erstellen Sie das Abonnement mit `--push-auth-service-account=<email>`. MoleSignal verifiziert das Token dann gegen die Schlüssel von Google und akzeptiert nur dieses Dienstkonto. Setzen Sie `oidcAudience`, um auch die Audience zu prüfen, und übergeben Sie denselben Wert als `--push-auth-token-audience`.

    Jede Nachricht ist eine Anfrage. Sowohl der umhüllte Body als auch eine unverpackte Payload werden akzeptiert. Ein Cloud Logging `LogEntry` wird zu einem Log-Ereignis:

    | `LogEntry` | Ereignis |
    |---|---|
    | `jsonPayload` | Seine Felder |
    | `textPayload` | `message` |
    | `protoPayload` (Audit-Logs) | `proto_payload`, wobei `method_name`, `service_name` und `principal_email` daraus entfernt werden |
    | `severity` | `level`, in Kleinbuchstaben |
    | `logName`, `resource.type`, `insertId` | `log_name`, `resource_type`, `insert_id` |
    | `resource.labels`, `labels` | Felder unter ihren eigenen Namen |
    | `trace`, `spanId` | `trace_id` ohne das Präfix `projects/<id>/traces/`, `span_id` |
    | `httpRequest` | `http_request` |
    | `timestamp` | Die Zeit des Ereignisses; `receiveTimestamp` oder die Veröffentlichungszeit, wenn sie fehlt |

    Alle anderen Nachrichtendaten werden zu einem Ereignis, die Felder eines JSON-Objekts oder der Text als `message`. Der Endpoint antwortet mit `204 No Content`, was Pub/Sub als Bestätigung zählt. Eine Nachricht, die nicht gelesen werden kann, wird bestätigt und bleibt aus; ein Schreibvorgang, der vorerst fehlschlägt, nicht, sodass Pub/Sub sie erneut zustellt. Eine Nachricht, die innerhalb von 30 Minuten nach dem Schreiben erneut zugestellt wird, wird bestätigt, ohne erneut geschrieben zu werden.
  </Tab>
  <Tab title="Cloud-Ereignisbus">
    Erstellen Sie den Connector mit `kind: "cloud_events"` und richten Sie den Ereignisbus dann auf `https://molesignal.example.com/api/v1/_cloud_events`:

    | Absender | Einrichtung |
    |---|---|
    | Amazon EventBridge | Ein API-Ziel mit einer **API-Schlüssel**-Verbindung; der Header-Name ist `X-Connector-Token` und sein Wert das Push-Token. |
    | Azure Event Grid | Ein Webhook-Abonnement, dessen Endpoint mit `?token=<pushToken>` endet. Der Validierungs-Handshake und der `OPTIONS`-Handshake des CloudEvents-Schemas werden automatisch beantwortet. |
    | Alibaba Cloud EventBridge | Ein HTTPS-Ziel mit dem Push-Token als Token, gesendet als `X-EventBridge-Signature-Token`. |
    | Huawei Cloud EventGrid | Ein Webhook-Ziel mit dem Header `X-Connector-Token`. |
    | Andere CloudEvents-Absender | Jede der oben genannten Token-Methoden. Ein Absender, der Anmeldedaten nur in die Adresse setzen kann, wie `https://user:<pushToken>@host/...`, wird ebenfalls akzeptiert. |

    Ein Body enthält ein Ereignis oder ein Array davon, als CloudEvents 1.0 im strukturierten oder binären Modus, Amazon EventBridge-Ereignisse oder das Event Grid-Schema. Jedes Ereignis wird zu einem Log-Ereignis in `targetStream` (Standard `cloud_events`):

    | Feld | Aus |
    |---|---|
    | `event_id`, `event_source`, `event_type`, `event_subject` | CloudEvents `id`, `source`, `type`, `subject`; EventBridge `id`, `source`, `detail-type`; Event Grid `id`, `topic`, `eventType`, `subject` |
    | `account_id`, `region` | EventBridge `account`, `region`; Alibaba Cloud `aliyunaccountid`, `aliyunregionid`; das Abonnement eines Event Grid-Topics |
    | `resources` | EventBridge `resources` |
    | `data` | Die Payload als ein JSON-Feld; eine Text-Payload geht in `message` |
    | `event_format` | `cloudevents`, `eventbridge` oder `event_grid` |

    Erweiterungsattribute behalten ihre Namen. Die eigene Zeit des Ereignisses ist seine Zeit. Jedes andere JSON-Objekt wird zu einem Ereignis mit seinen Feldern, wie sie sind. Ein Ereignis, das innerhalb von 30 Minuten erneut zugestellt wird, mit derselben Quelle und ID, wird nicht zweimal geschrieben. Der Endpoint antwortet mit `200` oder mit `400` für einen Body, der kein JSON ist.
  </Tab>
  <Tab title="Cloudflare Logpush">
    Erstellen Sie den Connector mit `kind: "cloudflare_logpush"` und erstellen Sie dann einen Logpush-Job mit einem HTTP-Ziel. Cloudflare wandelt einen `header_`-Query-Parameter in einen Anfrage-Header um, sodass das Token in `X-Connector-Token` übertragen wird:

    ```text
    https://molesignal.example.com/api/v1/_cloudflare?header_X-Connector-Token=<pushToken>
    ```

    Cloudflare liefert gzip-komprimiertes NDJSON, und jede Zeile wird zu einem Ereignis. Der Endpoint antwortet mit `204 No Content`.
  </Tab>
  <Tab title="Heroku">
    Erstellen Sie den Connector mit `kind: "heroku_drain"` und fügen Sie dann den Drain hinzu. Heroku kann keine benutzerdefinierten Header setzen, daher wird das Token in der URL übertragen:

    ```bash
    heroku drains:add "https://molesignal.example.com/api/v1/_heroku?token=<pushToken>"
    ```

    Jede Log-Zeile wird zu einem Ereignis mit `message` und `source: "heroku"`. Der Endpoint antwortet mit `204 No Content`.
  </Tab>

<Tip>
  Der `targetStream` wird bei der ersten Zustellung erstellt, und das Schema entwickelt sich weiter, wenn neue Felder erscheinen, genau wie bei jedem anderen Stream. Lassen Sie `targetStream` weg, um auf einen quellenspezifischen Standard zurückzufallen: `kinesis`, `gcp`, `cloud_events`, `cloudflare` oder `heroku`. Ein Firehose-Connector schreibt Metrik-Samples in `metricsStream`, standardmäßig `cloudwatch`.
</Tip>

### CloudWatch Logs

CloudWatch Logs ist eine **Pull**-Quelle: MoleSignal ruft alle 30 Sekunden `FilterLogEvents` auf, statt einen Push zu erhalten. Der erste Lauf liest die letzten 5 Minuten. Jeder spätere Lauf beginnt dort, wo der letzte erfolgreiche Lauf geendet hat, sodass Ereignisse, die nicht gelesen oder geschrieben werden konnten, beim nächsten Lauf erneut gelesen werden.

```bash
curl -X POST http://localhost:5080/api/v1/connectors \
  -H "authorization: Bearer $MS_TOKEN" \
  -H 'content-type: application/json' \
  -d '{
        "name": "cw-prod",
        "kind": "aws_cloudwatch_logs",
        "configJson": {
          "region": "ap-southeast-1",
          "logGroup": "/aws/lambda/checkout",
          "auth": "node_role",
          "targetStream": "cloudwatch"
        }
      }'
```

| Feld | Hinweise |
|---|---|
| `region` / `logGroup` | Erforderlich. Die CloudWatch-Region und Log-Gruppe, die gelesen werden sollen. |
| `auth` und seine Schlüssel | Die Anmeldedaten, die `logs:FilterLogEvents` für die Log-Gruppe benötigen. Siehe [AWS-Authentifizierung](#aws-authentifizierung). |
| `targetStream` | Ziel-Stream. Standard `default`. |

Ein Knoten fragt jeweils einen Connector ab. Die `alert`-Knoten teilen die Connectoren unter sich auf, und ein Knoten beansprucht einen Connector, bevor er ihn abfragt. Siehe [Arbeitsteilung zwischen Alert-Knoten](/de/deployment/role-based#aufgabenverteilung-zwischen-alert-knoten). Jedes Ereignis wird zu einem Log mit `message`, `log_stream` und `log_group`. Ein Connector, der ausgeschaltet ist, wird nicht abgefragt.

### Kafka-Topics

Ein `kafka_source`-Connector liest alle 30 Sekunden ein Topic und fährt dort fort, wo der letzte geschriebene Lesevorgang aufgehört hat. Er übernimmt die Partitionen per Zuweisung, nicht als Mitglied einer Consumer-Gruppe, und behält seine Offsets in MoleSignal, sodass er nur die Berechtigung zum Lesen des Topics benötigt und keine Consumer-Gruppe im Cluster erscheint.

```bash
curl -X POST http://localhost:5080/api/v1/connectors \
  -H "authorization: Bearer $MS_TOKEN" \
  -H 'content-type: application/json' \
  -d '{
        "name": "orders",
        "kind": "kafka_source",
        "configJson": {
          "brokers": "b-1.example.com:9096,b-2.example.com:9096",
          "topic": "orders",
          "tls": true,
          "auth": "sasl_scram_sha_512",
          "saslUsername": "molesignal",
          "saslPassword": "<password>",
          "targetStream": "orders",
          "startFrom": "latest"
        }
      }'
```

| Feld | Hinweise |
|---|---|
| `brokers`, `topic`, `tls`, `tlsCaCert`, `auth` und seine Schlüssel | Wie für ein [Kafka-Ziel](#apache-kafka). |
| `targetStream` | Ziel-Stream. Standard `default`. |
| `messageFormat` | `json`, der Standard, oder `azure_records` für das, was Azure Monitor in einen Event Hub exportiert, siehe unten. UI: **Nachrichtenformat**. |
| `startFrom` | Wo der erste Lesevorgang beginnt: `latest`, der Standard, für das, was ab jetzt eintrifft, oder `earliest` für alles, was die Broker halten. Eine später hinzugefügte Partition wird von ihrem Anfang an gelesen. UI: **Lesebeginn**. |

- Eine Nachricht, deren Wert ein JSON-Objekt ist, liefert die Felder des Logs. Jeder andere Wert wird zu ihrem `message`. Jedes Log hat außerdem `kafka_topic`, `kafka_partition`, `kafka_offset`, `kafka_key`, wenn die Nachricht einen Schlüssel hat, und `source`. Seine Zeit ist der Zeitstempel der Nachricht.
- Ein Lesevorgang nimmt bis zu 10.000 Nachrichten oder 32 MiB auf, und der nächste folgt sofort, solange es mehr gibt, für bis zu 2 Minuten in einem Pull.
- Die Offsets bewegen sich erst, wenn die Logs geschrieben sind. Ein Lese- oder Schreibvorgang, der fehlschlägt, wird 30 Sekunden später von derselben Stelle aus erneut versucht, sodass eine Nachricht zweimal geschrieben werden kann, aber nicht verloren geht. Offsets, die bei den Brokern veraltet sind, werden ab der ältesten noch gehaltenen Nachricht fortgesetzt.
- Das Ändern des `topic` beginnt von `startFrom` neu, da die Offsets zum Topic gehören.

Azure-Diagnoseeinstellungen, Log Analytics-Datenexport und Datensammlungsregeln exportieren in Azure Event Hubs, die eine Kafka-Quelle über den Kafka-Endpoint des Hubs liest: `brokers` `<namespace>.servicebus.windows.net:9093`, `topic` der Event Hub, `tls` an, `auth: sasl_plain` mit dem Benutzernamen `$ConnectionString` und der Verbindungszeichenfolge als Passwort. Der Basic-Tarif hat keinen Kafka-Endpoint. Mit `messageFormat: azure_records` wird jede `{"records": [...]}`-Nachricht entpackt: Ein Log-Datensatz wird zu einem Log-Ereignis zu seiner `time`, und ein Metrik-Datensatz wird zu einem Sample pro Statistik im `metricsStream` des Connectors (Standard `default`), benannt wie [Azure Monitor-Metriken](#cloud-metriken).

### S3-Objekte

Ein `s3_source`-Connector listet alle 30 Sekunden einen Bucket auf und liest die Objekte, die er noch nicht gelesen hat, beginnend mit dem ältesten, aus AWS S3 oder einem S3-kompatiblen Speicher.

```bash
curl -X POST http://localhost:5080/api/v1/connectors \
  -H "authorization: Bearer $MS_TOKEN" \
  -H 'content-type: application/json' \
  -d '{
        "name": "elb-logs",
        "kind": "s3_source",
        "configJson": {
          "bucket": "acme-logs",
          "region": "us-east-1",
          "prefix": "AWSLogs/123456789012/",
          "auth": "node_role",
          "targetStream": "elb",
          "startFrom": "latest"
        }
      }'
```

| Feld | Hinweise |
|---|---|
| `bucket`, `region`, `endpoint`, `virtualHostedStyle`, `auth` und seine Schlüssel | Wie für ein [S3-Ziel](#amazon-s3). Die Anmeldedaten benötigen `s3:ListBucket` für den Bucket und `s3:GetObject` für die Objekte. |
| `prefix` | Nur Objekte unter diesem Präfix werden gelesen. Jeder Pull listet es vollständig auf, daher sollte eine Quelle ein eigenes Präfix erhalten. |
| `targetStream` | Ziel-Stream. Standard `default`. |
| `startFrom` | Wo der erste Lesevorgang beginnt: `latest`, der Standard, für Objekte, die ab jetzt und in den 5 Minuten davor erscheinen, oder `earliest` für alles unter dem Präfix. UI: **Lesebeginn**. |

- Ein Objekt wird zeilenweise gelesen. Eine Zeile, die ein JSON-Objekt ist, liefert die Felder eines Logs, eine, die nur `Records` enthält, wie CloudTrail sie schreibt, liefert ein Log pro Datensatz, und jede andere Zeile wird zu einer `message`. `.gz`- und `.zst`-Objekte werden anhand ihrer Namen dekomprimiert. Jedes Log hat außerdem `s3_bucket`, `s3_key` und `source`. Seine Zeit ist die letzte Änderung des Objekts.
- Ein Pull liest bis zu 100 Objekte oder bis 50.000 Logs, und der nächste folgt sofort, solange es mehr gibt, für bis zu 2 Minuten.
- Der Lesestatus bewegt sich erst, wenn die Logs geschrieben sind. Ein Objekt, das nicht abgerufen werden kann, stoppt den Pull dort und wird 30 Sekunden später erneut versucht, sodass ein Log zweimal geschrieben werden kann, aber nicht verloren geht.
- Ein Objekt, das nicht gelesen werden kann, wird übersprungen und am Connector gemeldet, da ein erneuter Versuch alles danach aufhalten würde. Das ist eines, das beschädigt ist, über 256 MiB groß ist, nach der Dekomprimierung über 512 MiB groß ist, über eine Million Logs enthält oder eine Zeile über 64 MiB hat.
- Ein Objekt wird anhand seines Schlüssels und seiner Änderungszeit erkannt, mit einer Toleranz von 5 Minuten. Ein Objekt, das innerhalb dieser Toleranz erneut unter demselben Schlüssel geschrieben wird, wird nicht erneut gelesen, und eines, dessen Änderungszeit mehr als 5 Minuten älter ist als das neueste gelesene Objekt, wird gar nicht gelesen. S3 datiert einen Multipart-Upload ab dessen Beginn, sodass ein langsamerer Upload als dieser ungelesen bleibt.

### Google Cloud Pub/Sub-Abonnements

Ein `gcp_pubsub_pull`-Connector liest alle 30 Sekunden ein Pub/Sub-Abonnement, bis zu 1.000 Nachrichten pro Anfrage und sofort weiter, solange es mehr gibt, und bestätigt die Nachrichten erst, wenn sie geschrieben sind. Was nicht geschrieben werden kann, wird erneut zugestellt, wenn seine Bestätigungsfrist abläuft, sodass eine Nachricht zweimal geschrieben werden kann, aber nicht verloren geht. Er eignet sich für mehr Logs, als ein [Push-Abonnement](#push-quellen), das eine Nachricht pro Anfrage sendet, gut bewältigen kann.

| Feld | Hinweise |
|---|---|
| `serviceAccountKey` | Die JSON-Schlüsseldatei eines Dienstkontos mit `roles/pubsub.subscriber` für das Abonnement. |
| `subscription` | `projects/<project>/subscriptions/<name>` oder der Name eines Abonnements im Projekt des Schlüssels. Geben Sie ihm eine Bestätigungsfrist von 60 Sekunden oder mehr. |
| `targetStream` | Ziel-Stream. Standard `default`. |

Jede Nachricht wird gelesen wie eine gepushte: ein Cloud Logging `LogEntry` mit der Zuordnung des Push-Tabs, jedes andere JSON-Objekt als seine Felder, alles andere als `message`. **Verbindung testen** fragt ab, ob der Schlüssel das Abonnement konsumieren darf, ohne eine Nachricht zu entnehmen.

Sechs Quellen rufen die Metriken des Überwachungsdienstes einer Cloud nach einem Zeitplan ab und schreiben sie in einen Metrik-Stream:

Ein neuer Connector beginnt eine Periode zurück. Ein Pull liest höchstens 12 Perioden und fährt beim nächsten Tick fort; ein Connector, der länger als 6 Stunden aus war, überspringt das Ältere und meldet dies.

Jede Statistik jeder Reihe wird zu einem Gauge-Sample namens `<cloud>_<namespace>_<metric>_<statistic>`, so wie yet-another-cloudwatch-exporter CloudWatch-Metriken benennt, zu Beginn ihrer Periode:

| Quelle | Beispiel | Labels |
|---|---|---|
| CloudWatch | `aws_ec2_cpuutilization_average` | `region`, `dimension_<Name>` |

| Cloud Monitoring | `gcp_compute_instance_cpu_utilization_mean` | `project_id`, `resource_type`, die Ressourcen- und Metrik-Labels |
| CloudMonitor | `aliyun_ecs_dashboard_cpuutilization_average` | `region`, `user_id`, `dimension_<key>` |
| Tencent Cloud Monitor | `tencentcloud_cvm_cpu_usage_avg` | `region`, `dimension_<Name>` |

### Wie ein Pull läuft

Die Seite des Connectors zeigt, wann eine Quelle zuletzt empfangen hat. Eine Quelle, deren letzter Lesevorgang fehlgeschlagen ist, zeigt daneben eine Warnung an, mit dem Grund in ihrem Tooltip und in den Einstellungen des Connectors, und was eine Quelle zuletzt übersprungen hat, wird dort ebenfalls angezeigt. Über die API enthält `readState` `lastError` und `lastWarning`, jeweils mit `atTime` und `text`, sowie `position`, wo sie angelangt ist. Das Speichern eines Connectors lässt seine Position unverändert.

## Ziele

Ein Ziel empfängt jedes Ereignis, das die Schritte einer geplanten Pipeline durchläuft. Fügen Sie den Konnektor mit **Ziel hinzufügen → Konnektor** zu den **Zielen** des Flows hinzu. Eine fehlgeschlagene Zustellung wird innerhalb des Laufs wiederholt, und Ereignisse, die der Konnektor weiterhin nicht annimmt, gehen an den Dead-Letter-Stream. Siehe [Wiederholungen und Dead Letters](/de/pipelines#wiederholungsversuche-und-dead-letters).

Ein Ziel, das ausgeschaltet ist, empfängt nichts. Jeder Lauf überspringt den Konnektor und nennt ihn im `warning` des Laufs. Die übersprungenen Ereignisse zählen nicht als fehlgeschlagen, werden nicht zu Dead Letters und werden nicht gesendet, wenn der Konnektor wieder eingeschaltet wird. Im Editor wird ein ausgeschalteter Konnektor als **Aus** angezeigt.

| Typ | Payload |
|---|---|
| `s3` | Ein JSON-Lines-Objekt pro Batch, `PUT` an `s3://<bucket>/<prefix><id>.jsonl`. |
| `kafka` | Eine Nachricht pro Ereignis auf dem Topic, mit dem Ereignis als JSON-Payload. |
| `http` | Der Batch in einer Anfrage oder in mehreren, wenn er groß ist, als NDJSON oder als ein JSON-Array. |

Ein benutzerdefinierter Header darf keiner sein, den die Zustellung selbst setzt: `Host`, `Content-Type`, `Content-Length`, `Content-Encoding`, `Transfer-Encoding`, `Connection`, `X-MoleSignal-Timestamp` oder `X-MoleSignal-Sign`.

Für eine Zustellung gelten diese Regeln:

- Ein Batch, der größer als 4 MiB ist, wird in mehrere Anfragen aufgeteilt. Ein Ereignis, das größer ist, wird in einer eigenen Anfrage gesendet.
- Jeder `2xx`-Status zählt als zugestellt. Jeder andere Status lässt die Zustellung fehlschlagen, ebenso eine Weiterleitung: Weiterleitungen werden nicht verfolgt.
- Eine Anfrage läuft nach 30 Sekunden in ein Timeout.
- MoleSignal löst den Host vor der Anfrage auf und verbindet sich nur mit den aufgelösten Adressen. Eine Adresse, unter der Cloud-Metadatendienste antworten, wird abgelehnt, unabhängig davon, ob sie in der URL erscheint oder aus DNS stammt: `169.254.0.0/16`, `fe80::/10`, `fd00:ec2::254` und `100.100.100.200`. Andere private Adressen sind zulässig.

#### HMAC-Signatur überprüfen

Mit `hmac` enthält jede Anfrage zwei Header:

| Header | Inhalt |
|---|---|
| `X-MoleSignal-Timestamp` | Die Zeit der Anfrage in Unix-Sekunden. |
| `X-MoleSignal-Sign` | `sha256=<hex>`, der HMAC-SHA256 von `<timestamp>.<body>` mit dem gemeinsamen Secret. |

Um eine Anfrage zu überprüfen, berechnen Sie den HMAC-SHA256 aus dem Zeitstempel, einem `.` und den rohen Body-Bytes mit demselben Secret und vergleichen Sie das Ergebnis in konstanter Zeit mit der Signatur. Lehnen Sie einen Zeitstempel ab, der älter als einige Minuten ist, damit eine abgefangene Anfrage nicht später erneut gesendet werden kann.

```python
import hashlib
import hmac
import time


def verify(secret: bytes, timestamp: str, signature: str, body: bytes, tolerance: int = 300) -> bool:
    if abs(time.time() - int(timestamp)) > tolerance:
        return False
    signed = timestamp.encode() + b"." + body
    expected = "sha256=" + hmac.new(secret, signed, hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, signature)
```

## AWS-Authentifizierung

S3 und CloudWatch Logs authentifizieren sich auf eine von fünf Arten bei AWS:

| `auth` | UI | Schlüssel | Anmeldedaten |
|---|---|---|---|
| `access_key` | **Zugriffsschlüssel** | `accessKey`, `secretKey` | Der langlebige Schlüssel eines IAM-Benutzers. |
| `temporary_key` | **Temporärer Schlüssel** | `accessKey`, `secretKey`, `sessionToken` | Ein kurzlebiger Schlüssel von AWS STS, der nur mit seinem Sitzungstoken gültig ist. Ersetzen Sie ihn, bevor er abläuft. |
| `node_role` | **Knotenidentität** | | Die Identität des Knotens, auf dem MoleSignal läuft. Es wird kein Schlüssel gespeichert. |
| `assume_role` | **Rolle übernehmen** | `roleArn`, optional `accessKey` und `secretKey` | Eine über AWS STS mit der externen ID der Organisation übernommene Rolle. |
| `web_identity` | **Web-Identität** | `roleArn` | Eine mit dem Web-Identitätstoken des Knotens übernommene Rolle. |

Ohne `auth` entscheiden die gespeicherten Schlüssel: Ein Zugriffsschlüssel wird als `access_key` interpretiert, ein `roleArn` als `assume_role` und keines von beiden als `node_role`. Ein `roleArn` hat die Form `arn:aws:iam::<account>:role/<name>`.

### Knotenidentität

`node_role` verwendet die Identität, die die AWS SDKs auf dem Knoten finden: EKS-IAM-Rollen für Servicekonten (IRSA) oder EKS Pod Identity, eine ECS-Task-Rolle oder ein EC2-Instanzprofil. Ein statischer Schlüssel in der Umgebung des Knotens, etwa `AWS_ACCESS_KEY_ID`, wird für Connectoren nie verwendet.

<Warning>
  Die Identität des Knotens und sein Web-Identitätstoken gehören zur Bereitstellung. Jede Organisation in der Bereitstellung kann `node_role` und `web_identity` wählen, daher sind alles, was die Identität des Knotens erreichen kann, und jede Rolle, die dem Token des Knotens vertraut, für die Connectoren jeder Organisation offen. Gewähren Sie nur Zugriff, den jede Organisation haben darf.
</Warning>

### Rolle übernehmen

`assume_role` fordert bei AWS STS einen Schlüssel der Rolle mit einer Stunde Gültigkeit an und erneuert den Schlüssel 5 Minuten vor seinem Ablauf. Die Basis-Anmeldedaten, mit denen die Rolle übernommen wird, sind die Identität des Knotens. Wählen Sie für eine Bereitstellung, die nicht auf AWS läuft, **Rolle mit Zugriffsschlüssel statt Knotenidentität übernehmen** und geben Sie den Schlüssel eines IAM-Benutzers ein.

Jede Organisation übernimmt Rollen mit ihrer eigenen externen ID, `molesignal-<organization ID>`, die nicht geändert werden kann. Das Formular zeigt sie unter **Externe ID** an, und `GET /api/v1/connectors/aws-external-id` gibt sie zurück. Verlangen Sie die externe ID in der Vertrauensrichtlinie der Rolle, damit keine andere Organisation die Rolle übernehmen kann, selbst wenn sie den ARN kennt:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": { "AWS": "<ARN of the node role or IAM user>" },
      "Action": "sts:AssumeRole",
      "Condition": { "StringEquals": { "sts:ExternalId": "molesignal-<organization ID>" } }
    }
  ]
}
```

Die Sitzung heißt `molesignal-<connector ID>` und erscheint so in AWS CloudTrail. Die Anforderung geht an den regionalen STS-Endpunkt der `region` des Connectors: `us-east-1`, wenn die Region leer ist, und die Domain `amazonaws.com.cn` für die China-Regionen.

### Web-Identität

`web_identity` übernimmt die Rolle mit dem Web-Identitätstoken, dessen Pfad die Variable `AWS_WEB_IDENTITY_TOKEN_FILE` des Knotens angibt, etwa das Service-Account-Token, das EKS für IRSA projiziert. Ein Connector kann keine andere Datei angeben. Die Vertrauensrichtlinie der Rolle muss dem OIDC-Provider vertrauen, der das Token ausstellt. Auf einem Knoten ohne `AWS_WEB_IDENTITY_TOKEN_FILE` hat der Connector keine Anmeldedaten.

Das Token wird am regionalen STS-Endpunkt der `region` des Connectors eingetauscht oder an `AWS_ENDPOINT_URL_STS`, wenn die Umgebung des Knotens diese Variable setzt. Dasselbe gilt für eine Knotenidentität, die von IRSA stammt.

## Verbindung testen

**Verbindung testen** probiert die Einstellungen so aus, wie sie im Formular stehen, bevor sie gespeichert werden. Bleibt ein Secret leer, gilt das gespeicherte. Jede Art führt nur das Minimum aus, das belegt, dass eine Zustellung oder ein Abruf funktionieren kann:

| Art | Test |
|---|---|
| `s3` | Schreibt das Objekt `.molesignal-connection-test` unter dem Präfix und entfernt es, wenn die Richtlinie es erlaubt. |
| `kafka` | Liest die Metadaten des Topics von den Brokern, was die Verbindung, TLS und die Authentifizierung sowie die Existenz des Topics belegt. Schreibt keine Nachricht. |
| `http` | Sendet ein Ereignis, das als Test gekennzeichnet ist: `"message": "MoleSignal connection test"` und `"molesignal_connection_test": true`. |
| `aws_cloudwatch_logs` | Liest höchstens ein Ereignis der letzten Minute der Log-Gruppe. Schreibt nichts in den Stream und lässt die Leseposition unverändert. |
| `kafka_source` | Liest die Metadaten des Topics von den Brokern, wie bei `kafka`. Liest keine Nachricht und lässt die Leseposition unverändert. |
| `s3_source` | Listet ein Objekt unter dem Präfix auf, was die Anmeldedaten und `s3:ListBucket` belegt. Liest nichts und lässt die Leseposition unverändert. |

Ein Test wird nach 25 Sekunden abgebrochen. Über die API nimmt `POST /api/v1/connectors/test` den `kind` und die zu testende `configJson` entgegen. Mit der `id` eines gespeicherten Connectors derselben Art steht `***` für das Secret, das der Connector enthält. Einstellungen, die nicht funktionieren können, antworten mit `400`, wie beim Speichern.

```bash
curl -X POST http://localhost:5080/api/v1/connectors/test \
  -H "authorization: Bearer $MS_TOKEN" \
  -H 'content-type: application/json' \
  -d '{
        "id": "<connector id>",
        "kind": "kafka",
        "configJson": {
          "brokers": "b-1.example.com:9096",
          "topic": "logs",
          "tls": true,
          "auth": "sasl_scram_sha_512",
          "saslUsername": "molesignal",
          "saslPassword": "***"
        }
      }'
```

```json
{ "ok": true, "code": "ok", "detail": null, "elapsedMs": 412 }
```

`elapsedMs` gibt an, wie lange der Test gedauert hat. Ein fehlgeschlagener Test nennt die Ursache in `code`, und `detail` enthält die Antwort der Gegenseite, bis zu 600 Zeichen:

| `code` | Bedeutung |
|---|---|
| `ok` | Verbunden. |
| `invalid` | Die Einstellungen können nicht funktionieren, oder der Connector ist eine Push-Quelle, bei der es nichts zu verbinden gibt. |
| `no_credentials` | Es konnten keine AWS-Anmeldedaten beschafft werden: Der Knoten hat keine Identität oder keine der angeforderten Art. |
| `denied` | Die Gegenseite hat die Anmeldedaten oder die damit erlaubten Aktionen abgelehnt. |
| `not_found` | Der Bucket, das Topic, die Log-Gruppe oder die Adresse ist nicht vorhanden. |
| `tls` | Der TLS-Handshake ist fehlgeschlagen: Ein Zertifikat ist nicht vertrauenswürdig oder wurde nicht übermittelt. |
| `unreachable` | Der Host konnte nicht aufgelöst werden oder es konnte keine Verbindung zu ihm hergestellt werden. |
| `timeout` | Keine rechtzeitige Antwort. |
| `failed` | Jeder andere Fehler. |

## API

| Endpoint | Berechtigung | Zweck |
|---|---|---|
| `GET /api/v1/connectors` | `pipelines.read` | Listet die Connectoren der Organisation auf. |
| `POST /api/v1/connectors` | `pipelines.edit` | Erstellt einen Connector. `enabled` ist standardmäßig `true`. |
| `GET /api/v1/connectors/{id}` | `pipelines.read` | Liest einen Connector. |
| `PUT /api/v1/connectors/{id}` | `pipelines.edit` | Ersetzt `name`, `kind`, `configJson` und `enabled`; alle sind erforderlich. |
| `DELETE /api/v1/connectors/{id}` | `pipelines.edit` | Löscht einen Connector. |
| `POST /api/v1/connectors/test` | `pipelines.edit` | Testet Einstellungen, bevor sie gespeichert werden. |
| `GET /api/v1/connectors/aws-external-id` | `pipelines.read` | Gibt die externe ID der Organisation als `externalId` zurück. |

Ein Connector wird als `id`, `name`, `kind`, `configJson` mit maskierten Secrets, `secretKeys`, `enabled`, `lastRunAt`, `readState`, `createdAt` und `updatedAt` dargestellt.

## Berechtigungen

`pipelines.read` listet Connectoren auf, prüft sie und liest die externe ID. `pipelines.edit` erstellt, aktualisiert, löscht und testet Connectoren. Ein Test benötigt `pipelines.edit`, weil er die gespeicherten Secrets verwendet und im Auftrag des Aufrufers eine Verbindung zu einem anderen System herstellt. Push-Empfänger authentifizieren sich mit dem Push-Token und akzeptieren kein normales Login-JWT als Ersatz.
