Ein **Konnektor** ist eine verwaltete Integration mit einer externen Plattform. Konnektoren arbeiten in zwei Richtungen:

- **Quellen** bringen Daten aus einem anderen Dienst herein und schreiben sie in einen Stream. MoleSignal ruft CloudWatch Logs, Kafka-Topics und S3-Objekte nach Zeitplan ab. Amazon Data Firehose, Google Cloud Pub/Sub, Cloudflare Logpush und Heroku pushen an MoleSignal; Firehose überträgt außerdem CloudWatch-Metriken.
- **Ziele** empfangen die Ausgabe einer [geplanten Pipeline](/de/pipelines#sinks-und-konnektor-egress): Amazon S3 und S3-kompatibler Speicher, Apache Kafka und jeder HTTP-Endpunkt.

| Art | Konnektor | Richtung | Authentifizierung |
|---|---|---|---|
| `aws_cloudwatch_logs` | AWS CloudWatch Logs | Quelle, alle 30 Sekunden abgerufen | [AWS-Zugangsdaten](#aws-authentifizierung) |
| `kafka_source` | Kafka-Topic | Quelle, alle 30 Sekunden abgerufen | Keine, SASL oder ein Client-Zertifikat |
| `s3_source` | S3-Objekte | Quelle, alle 30 Sekunden abgerufen | AWS-Zugangsdaten |
| `gcp_pubsub_pull` | Google Cloud Pub/Sub-Abonnement | Quelle, alle 30 Sekunden abgerufen | Dienstkonto-Schlüssel |
| `aws_cloudwatch_metrics`, `azure_monitor_metrics`, `gcp_monitoring_metrics`, `aliyun_cms_metrics`, `tencent_monitor_metrics`, `huawei_ces_metrics` | [Cloud-Metriken](#cloud-metriken) | Quelle, pro Periode abgerufen | Die Zugangsdaten der Cloud |
| `aws_kinesis_firehose` | Amazon Data Firehose | Quelle, gepusht | [Push-Token](#push-quellen) |
| `gcp_pubsub_push` | Google Cloud Pub/Sub-Push | Quelle, gepusht | Push-Token, optional mit dem OIDC-Token des Abonnements |
| `cloud_events` | Cloud-Event-Bus | Quelle, gepusht | Push-Token |
| `cloudflare_logpush` | Cloudflare Logpush | Quelle, gepusht | Push-Token |
| `heroku_drain` | Heroku-Log-Drain | Quelle, gepusht | Push-Token |
| `s3` | Amazon S3 | Ziel | AWS-Zugangsdaten |
| `kafka` | Apache Kafka | Ziel | Keine, SASL oder ein Client-Zertifikat |
| `http` | HTTP / Webhook | Ziel | Keine, ein Bearer-Token, Basic Auth, ein benutzerdefinierter Header oder eine HMAC-Signatur |

## Konnektor erstellen

<Steps>
  <Step title="Konnektoren öffnen">
    Gehen Sie zu **Pipelines → Konnektoren**. Die Seite listet **Quellen** und **Ziele** auf.
  </Step>
  <Step title="Art auswählen">
    Klicken Sie auf **Neuer Konnektor** und wählen Sie aus, womit eine Verbindung hergestellt werden soll.
  </Step>
  <Step title="Einstellungen ausfüllen">
    Geben Sie unter **Name** einen innerhalb der Organisation eindeutigen Wert ein, geben Sie an, woher der Konnektor liest oder wohin er liefert, und wählen Sie die **Authentifizierung**.
  </Step>
  <Step title="Testen und erstellen">
    Klicken Sie auf **Verbindung testen**, um die Einstellungen vor dem Speichern zu prüfen, und klicken Sie dann auf **Konnektor erstellen**. Eine Push-Quelle hat kein Verbindungsziel und bietet keinen Test.
  </Step>
</Steps>

Über die API ist ein Konnektor ein `name`, ein `kind` und ein `configJson`, dessen Schlüssel von der Art abhängen. `auth` in `configJson` benennt die Art der Authentifizierung, und jede Art verwendet ihre eigenen Schlüssel. Einstellungen, die nicht funktionieren können, geben beim Speichern `400` zurück: ein fehlender erforderlicher Schlüssel, die Hälfte eines Zugangsdatenpaars oder ein Schlüssel, den das gewählte `auth` nicht verwendet.

```bash
curl -X POST http://localhost:5080/api/v1/connectors \
  -H "authorization: Bearer $MS_TOKEN" \
  -H 'content-type: application/json' \
  -d '{
        "name": "archive",
        "kind": "s3",
        "configJson": {
          "bucket": "acme-logs",
          "region": "eu-west-1",
          "prefix": "pipelines/checkout/",
          "auth": "assume_role",
          "roleArn": "arn:aws:iam::123456789012:role/molesignal-delivery"
        }
      }'
```

## Secrets

Diese Schlüssel von `configJson` enthalten Secrets:

| Art | Secret-Schlüssel |
|---|---|
| `s3`, `aws_cloudwatch_logs` | `accessKey`, `secretKey`, `sessionToken` |
| `aws_kinesis_firehose`, `gcp_pubsub_push`, `cloud_events`, `cloudflare_logpush`, `heroku_drain` | `pushToken` |
| `aws_cloudwatch_metrics` | `accessKey`, `secretKey`, `sessionToken` |
| `azure_monitor_metrics` | `clientSecret` |
| `gcp_monitoring_metrics`, `gcp_pubsub_pull` | `serviceAccountKey` |
| `aliyun_cms_metrics`, `tencent_monitor_metrics`, `huawei_ces_metrics` | `accessKey`, `secretKey` |
| `kafka` | `saslPassword`, `tlsClientKey` |
| `http` | `url`, `bearerToken`, `basicPassword`, `headerValue`, `hmacSecret` |

Ein Secret wird nie über die API ausgegeben. Eine Antwort zeigt an seiner Stelle `***` und benennt in `secretKeys` die Secrets, die einen Wert enthalten:

```json
{
  "kind": "kafka",
  "configJson": {
    "brokers": "b-1.example.com:9096",
    "topic": "logs",
    "tls": true,
    "auth": "sasl_scram_sha_512",
    "saslUsername": "molesignal",
    "saslPassword": "***"
  },
  "secretKeys": ["saslPassword"]
}
```

- Eine Aktualisierung, die `***` zurücksendet, behält den gespeicherten Wert bei, sodass ein Konnektor umbenannt, deaktiviert oder auf ein anderes Ziel ausgerichtet werden kann, ohne seine Zugangsdaten erneut einzugeben. In der Benutzeroberfläche behält ein gespeichertes Secret, das leer gelassen wird, seinen Wert.
- Ein Secret, das in einer Aktualisierung fehlt, wird entfernt.
- Eine Aktualisierung, die `kind` ändert, behält keines der gespeicherten Secrets.

MoleSignal verschlüsselt die Secrets mit dem Root-Schlüssel aus `MS_CIPHER_KEY` (AES-256-GCM) getrennt von den anderen Einstellungen und speichert kein Secret im Klartext. Eine Push-Quelle wird über den SHA-256-Wert ihres Tokens gefunden. `molesignal rewrap-kek` verschlüsselt die Konnektor-Secrets zusammen mit den anderen Secrets neu, wenn der Root-Schlüssel rotiert wird. Siehe [Produktions-Checkliste](/de/deployment/production-checklist).

## Quellen

### Push-Quellen

Die fünf Push-Quellen nutzen ein gemeinsames Modell: Erstellen Sie einen Connector mit einem **`pushToken`** und einem **`targetStream`** und richten Sie dann die Plattform auf den passenden Endpunkt. Diese Endpunkte verwenden nicht das JWT. Die Anfrage authentifiziert sich mit dem Push-Token, der auf dem Weg übergeben wird, den die Plattform zulässt:

| Methode | Verwendet von |
|---|---|
| `X-Connector-Token`-Header | Plattformen mit konfigurierbaren Headern, etwa Cloudflare |
| `X-Amz-Firehose-Access-Key`-Header | Amazon Data Firehose, das ihn automatisch sendet |
| `X-EventBridge-Signature-Token`-Header | Alibaba Cloud EventBridge |
| `?token=`-Query-Parameter | Plattformen, die keine Header setzen können, etwa Heroku und Pub/Sub |
| Passwort von `Authorization: Basic` | Plattformen, die Anmeldedaten in die Adresse schreiben |

Die UI generiert das Token beim Erstellen des Connectors und zeigt es einmal an, zusammen mit dem Endpunkt, den die Plattform erhält. Das Token lässt sich nicht erneut lesen. **Neues Token generieren** ersetzt es beim Speichern des Connectors. Über die API übergeben Sie einen `pushToken` mit mindestens 16 Zeichen. Ein Token öffnet genau einen Connector einer Art: Ein bereits verwendetes Token antwortet mit `409`. Eine Anfrage mit fehlendem oder unbekanntem Token oder für einen deaktivierten Connector antwortet mit `401`. Ein Connector ohne Token nimmt nichts an. Ein Node behält einen nachgeschlagenen Connector 30 Sekunden lang, daher wirken das Deaktivieren eines Connectors oder das Ersetzen seines Tokens innerhalb dieser Zeit.

Mit `Content-Encoding: gzip` gesendete Bodies werden automatisch dekomprimiert. Ein Firehose-Body darf bis zu 64 MiB groß sein, jeder andere bis zu 16 MiB, jeweils auch nach der Dekomprimierung gezählt. Events durchlaufen denselben Aufnahmepfad wie alles andere: Schema-on-Write, [Pipelines](/de/pipelines) und [Maskierung](/de/security) greifen alle.

<Tabs>
  <Tab title="Amazon Data Firehose">
    Erstellen Sie den Connector mit `kind: "aws_kinesis_firehose"` und wählen Sie dann das Ziel **HTTP-Endpunkt** für den Firehose-Stream:

    - **HTTP-Endpunkt-URL**: `https://molesignal.example.com/api/v1/_kinesis_firehose`
    - **Zugriffsschlüssel**: das Push-Token. Firehose sendet ihn als `X-Amz-Firehose-Access-Key`.

    Firehose liefert nur an HTTPS auf Port 443 mit einem öffentlich vertrauenswürdigen Zertifikat, daher braucht eine Bereitstellung in einem privaten Netzwerk einen öffentlichen Einstiegspunkt, siehe [Öffentlicher Zugriff](/de/public-access). Halten Sie den Puffer des Streams bei 1 bis 4 MiB.

    MoleSignal liest jeden Datensatz für sich, je nachdem, was er enthält:

    | Datensatz | Wird zu |
    |---|---|
    | Eine CloudWatch-Logs-Abonnementnachricht, gzip-komprimiert, wie der Abonnementfilter sie sendet | Ein Log-Event pro Eintrag von `logEvents`, zur Zeit des Eintrags, mit `message`, `log_group`, `log_stream`, `account_id`, `region`, `event_id` und `source: "cloudwatch"`. Der Health Check, den das Abonnement beim Erstellen sendet, wird übersprungen. |
    | Ein CloudWatch-Metric-Streams-Datensatz im Ausgabeformat JSON, OpenTelemetry 1.0 oder OpenTelemetry 0.7 | Metrik-Samples im Metrik-Stream, siehe unten. |
    | Beliebiger anderer Text | Ein Log-Event pro Zeile: Ein JSON-Objekt liefert die Felder, reiner Text geht in `message`. |

    Ein Metrik-Stream sendet ein Aggregat pro Metrik und Minute. Jede Statistik wird zu einem Gauge-Sample namens `aws_<namespace>_<metric>_<statistic>`, so wie yet-another-cloudwatch-exporter sie benennt: `aws_ec2_cpuutilization_average`, `aws_ec2_cpuutilization_maximum`, `aws_applicationelb_request_count_sum`. Der Namespace verliert sein Präfix `AWS/`, und der Metrikname wird an Stellen in Wörter getrennt, an denen ein Kleinbuchstabe auf einen Großbuchstaben trifft. Die Statistiken sind `average` (die Summe über die Sample-Anzahl), `sum`, `sample_count`, `minimum`, `maximum` und jedes Perzentil, das der Stream hinzufügt, etwa `p99` oder `p99_9`. Die Labels sind `account_id`, `region` und ein `dimension_<Name>` pro Dimension, etwa `dimension_InstanceId`; `metric_unit` behält die Einheit.

    ```promql
    max by (dimension_InstanceId) (aws_ec2_cpuutilization_average)
    ```

    `X-Amz-Firehose-Common-Attributes`, als Parameter des Streams gesetzt, fügt seine Schlüssel jedem Event und Sample hinzu; ein Feld, das der Datensatz bereits hat, hat Vorrang. `X-Amz-Firehose-Source-Arn` liefert die `region` von CloudWatch-Logs-Events, die keine mitführen.

    Die Antwort folgt der Firehose-Zustellspezifikation: `application/json` mit der `requestId` der Anfrage, einem `timestamp` und einer `errorMessage` bei einem Fehler. Datensätze, die nicht gelesen werden können, werden ausgelassen, und der Rest der Anfrage wird trotzdem mit `200` geschrieben. Ein Schreibvorgang, der vorerst fehlschlägt, antwortet mit `429` oder `5xx`, was Firehose erneut versucht. Ein Body über 64 MiB antwortet mit `413`, was Firehose weder erneut versucht noch sichert. Eine Zustellung, die innerhalb von 30 Minuten nach dem Schreiben erneut versucht wird, mit derselben `X-Amz-Firehose-Request-Id`, wird mit `200` beantwortet, ohne erneut geschrieben zu werden.
  </Tab>
  <Tab title="Google Cloud Pub/Sub">
    Erstellen Sie den Connector mit `kind: "gcp_pubsub_push"`. Leiten Sie Logs mit einem Log-Router-Sink an ein Pub/Sub-Topic und erstellen Sie dann ein Push-Abonnement für das Topic. Pub/Sub kann keine benutzerdefinierten Header setzen, daher reist das Token in der URL:

    ```bash
    gcloud pubsub subscriptions create molesignal-push --topic=molesignal-logs --push-endpoint="https://molesignal.example.com/api/v1/_gcp_pubsub?token=<pushToken>"
    ```

    Um auch das OIDC-Token des Abonnements zu prüfen, setzen Sie `oidcServiceAccount` am Connector auf die E-Mail-Adresse eines Service Accounts und erstellen Sie das Abonnement mit `--push-auth-service-account=<email>`. MoleSignal prüft das Token dann gegen Googles Schlüssel und akzeptiert nur diesen Service Account. Setzen Sie `oidcAudience`, um auch die Audience zu prüfen, und übergeben Sie denselben Wert als `--push-auth-token-audience`.

    Jede Nachricht ist eine Anfrage. Sowohl der umhüllte Body als auch eine nicht umhüllte Payload werden akzeptiert. Ein Cloud Logging `LogEntry` wird zu einem Log-Event:

    | `LogEntry` | Event |
    |---|---|
    | `jsonPayload` | Seine Felder |
    | `textPayload` | `message` |
    | `protoPayload` (Audit-Logs) | `proto_payload`, mit `method_name`, `service_name` und `principal_email` daraus entfernt |
    | `severity` | `level`, kleingeschrieben |
    | `logName`, `resource.type`, `insertId` | `log_name`, `resource_type`, `insert_id` |
    | `resource.labels`, `labels` | Felder unter ihren eigenen Namen |
    | `trace`, `spanId` | `trace_id` ohne das Präfix `projects/<id>/traces/`, `span_id` |
    | `httpRequest` | `http_request` |
    | `timestamp` | Die Zeit des Events; `receiveTimestamp` oder die Veröffentlichungszeit, wenn sie fehlt |

    Beliebige andere Nachrichtendaten werden zu einem Event, die Felder eines JSON-Objekts oder der Text als `message`. Der Endpunkt antwortet mit `204 No Content`, was Pub/Sub als Bestätigung zählt. Eine Nachricht, die nicht gelesen werden kann, wird bestätigt und ausgelassen; ein vorerst fehlschlagender Schreibvorgang wird nicht bestätigt, daher liefert Pub/Sub die Nachricht erneut. Eine Nachricht, die innerhalb von 30 Minuten nach dem Schreiben erneut zugestellt wird, wird bestätigt, ohne erneut geschrieben zu werden.
  </Tab>
  <Tab title="Cloud-Event-Bus">
    Erstellen Sie den Connector mit `kind: "cloud_events"` und richten Sie den Event-Bus dann auf `https://molesignal.example.com/api/v1/_cloud_events`:

    | Absender | Einrichtung |
    |---|---|
    | Amazon EventBridge | Ein API-Ziel mit einer **API-Schlüssel**-Verbindung; der Header-Name ist `X-Connector-Token` und sein Wert das Push-Token. |
    | Azure Event Grid | Ein Webhook-Abonnement, dessen Endpunkt mit `?token=<pushToken>` endet. Der Validierungs-Handshake und der `OPTIONS`-Handshake des CloudEvents-Schemas werden automatisch beantwortet. |
    | Alibaba Cloud EventBridge | Ein HTTPS-Ziel mit dem Push-Token als Token, gesendet als `X-EventBridge-Signature-Token`. |
    | Huawei Cloud EventGrid | Ein Webhook-Ziel mit dem Header `X-Connector-Token`. |
    | Andere CloudEvents-Absender | Eine der oben genannten Token-Methoden. Ein Absender, der Anmeldedaten nur in die Adresse schreiben kann, etwa `https://user:<pushToken>@host/...`, wird ebenfalls akzeptiert. |

    Ein Body enthält ein Event oder ein Array davon, als CloudEvents 1.0 im strukturierten oder binären Modus, Amazon EventBridge-Events oder das Event Grid-Schema. Jedes Event wird zu einem Log-Event in `targetStream` (Standard `cloud_events`):

    | Feld | Herkunft |
    |---|---|
    | `event_id`, `event_source`, `event_type`, `event_subject` | CloudEvents `id`, `source`, `type`, `subject`; EventBridge `id`, `source`, `detail-type`; Event Grid `id`, `topic`, `eventType`, `subject` |
    | `account_id`, `region` | EventBridge `account`, `region`; Alibaba Cloud `aliyunaccountid`, `aliyunregionid`; das Abonnement eines Event Grid-Topics |
    | `resources` | EventBridge `resources` |
    | `data` | Die Payload als ein JSON-Feld; eine Text-Payload geht in `message` |
    | `event_format` | `cloudevents`, `eventbridge` oder `event_grid` |

    Erweiterungsattribute behalten ihre Namen. Die eigene Zeit des Events ist seine Zeit. Jedes andere JSON-Objekt wird zu einem Event mit seinen Feldern, wie sie sind. Ein Event, das innerhalb von 30 Minuten erneut mit derselben Quelle und ID zugestellt wird, wird nicht zweimal geschrieben. Der Endpunkt antwortet mit `200` oder mit `400` für einen Body, der kein JSON ist.
  </Tab>
  <Tab title="Cloudflare Logpush">
    Erstellen Sie den Connector mit `kind: "cloudflare_logpush"` und erstellen Sie dann einen Logpush-Job mit einem HTTP-Ziel. Cloudflare wandelt einen `header_`-Query-Parameter in einen Anfrage-Header um, daher reist das Token in `X-Connector-Token`:

    ```text
    https://molesignal.example.com/api/v1/_cloudflare?header_X-Connector-Token=<pushToken>
    ```

    Cloudflare liefert gzip-komprimiertes NDJSON, und jede Zeile wird zu einem Event. Der Endpunkt antwortet mit `204 No Content`.
  </Tab>
  <Tab title="Heroku">
    Erstellen Sie den Connector mit `kind: "heroku_drain"` und fügen Sie dann den Drain hinzu. Heroku kann keine benutzerdefinierten Header setzen, daher reist das Token in der URL:

    ```bash
    heroku drains:add "https://molesignal.example.com/api/v1/_heroku?token=<pushToken>"
    ```

    Jede Log-Zeile wird zu einem Event mit `message` und `source: "heroku"`. Der Endpunkt antwortet mit `204 No Content`.
  </Tab>

<Tip>
  Der `targetStream` wird bei der ersten Zustellung erstellt, und das Schema entwickelt sich weiter, wenn neue Felder auftauchen, wie bei jedem anderen Stream. Lassen Sie `targetStream` weg, um auf einen quellenspezifischen Standard zurückzufallen: `kinesis`, `gcp`, `cloud_events`, `cloudflare` oder `heroku`. Ein Firehose-Connector schreibt Metrik-Samples in `metricsStream`, standardmäßig `cloudwatch`.
</Tip>

### CloudWatch Logs

CloudWatch Logs ist eine **Pull**-Quelle: MoleSignal ruft alle 30 Sekunden `FilterLogEvents` auf, statt einen Push zu erhalten. Der erste Lauf liest die letzten 5 Minuten. Jeder spätere Lauf beginnt dort, wo der letzte erfolgreiche Lauf endete, sodass Events, die nicht gelesen oder geschrieben werden konnten, beim nächsten Lauf erneut gelesen werden.

```bash
curl -X POST http://localhost:5080/api/v1/connectors \
  -H "authorization: Bearer $MS_TOKEN" \
  -H 'content-type: application/json' \
  -d '{
        "name": "cw-prod",
        "kind": "aws_cloudwatch_logs",
        "configJson": {
          "region": "ap-southeast-1",
          "logGroup": "/aws/lambda/checkout",
          "auth": "node_role",
          "targetStream": "cloudwatch"
        }
      }'
```

| Feld | Hinweise |
|---|---|
| `region` / `logGroup` | Erforderlich. Die zu lesende CloudWatch-Region und Log-Gruppe. |
| `auth` und seine Schlüssel | Die Anmeldedaten, die `logs:FilterLogEvents` für die Log-Gruppe benötigen. Siehe [AWS-Authentifizierung](#aws-authentifizierung). |
| `targetStream` | Zielstream. Standard `default`. |

Ein Node fragt jeweils einen Connector ab. Die `alert`-Nodes teilen die Connectors unter sich auf, und ein Node beansprucht einen Connector, bevor er ihn abfragt. Siehe [Arbeitsaufteilung zwischen Alert-Nodes](/de/deployment/role-based#aufgabenverteilung-zwischen-alert-knoten). Jedes Event wird zu einem Log mit `message`, `log_stream` und `log_group`. Ein deaktivierter Connector wird nicht abgefragt.

### Kafka-Topics

Ein `kafka_source`-Connector liest alle 30 Sekunden ein Topic und setzt dort fort, wo der letzte geschriebene Lesevorgang aufgehört hat. Er übernimmt die Partitionen per Zuweisung, nicht als Mitglied einer Consumer Group, und speichert seine Offsets in MoleSignal, daher braucht er nur die Berechtigung zum Lesen des Topics, und im Cluster taucht keine Consumer Group auf.

```bash
curl -X POST http://localhost:5080/api/v1/connectors \
  -H "authorization: Bearer $MS_TOKEN" \
  -H 'content-type: application/json' \
  -d '{
        "name": "orders",
        "kind": "kafka_source",
        "configJson": {
          "brokers": "b-1.example.com:9096,b-2.example.com:9096",
          "topic": "orders",
          "tls": true,
          "auth": "sasl_scram_sha_512",
          "saslUsername": "molesignal",
          "saslPassword": "<password>",
          "targetStream": "orders",
          "startFrom": "latest"
        }
      }'
```

| Feld | Hinweise |
|---|---|
| `brokers`, `topic`, `tls`, `tlsCaCert`, `auth` und seine Schlüssel | Wie für ein [Kafka-Ziel](#apache-kafka). |
| `targetStream` | Zielstream. Standard `default`. |
| `messageFormat` | `json`, der Standard, oder `azure_records` für das, was Azure Monitor an einen Event Hub exportiert, siehe unten. UI: **Nachrichtenformat**. |
| `startFrom` | Wo der erste Lesevorgang beginnt: `latest`, der Standard, für das, was ab jetzt eintrifft, oder `earliest` für alles, was die Broker halten. Eine später hinzugefügte Partition wird von ihrem Anfang an gelesen. UI: **Lesebeginn**. |

- Eine Nachricht, deren Wert ein JSON-Objekt ist, liefert die Felder des Logs. Jeder andere Wert wird zu ihrem `message`. Jedes Log hat außerdem `kafka_topic`, `kafka_partition`, `kafka_offset`, `kafka_key`, wenn die Nachricht einen Schlüssel hat, und `source`. Seine Zeit ist der Zeitstempel der Nachricht.
- Ein Lesevorgang nimmt bis zu 10.000 Nachrichten oder 32 MiB auf, und der nächste folgt sofort, solange mehr vorhanden ist, für bis zu 2 Minuten pro Pull.
- Die Offsets bewegen sich erst, wenn die Logs geschrieben sind. Ein fehlgeschlagener Lese- oder Schreibvorgang wird 30 Sekunden später von derselben Stelle erneut versucht, sodass eine Nachricht zweimal geschrieben werden kann, aber nicht verloren geht. Abgelaufene Offsets setzen bei der ältesten Nachricht fort, die die Broker noch halten.
- Ein Wechsel des `topic` beginnt erneut bei `startFrom`, da die Offsets zum Topic gehören.

Azure-Diagnoseeinstellungen, Log Analytics-Datenexport und Datensammlungsregeln exportieren an Azure Event Hubs, die eine Kafka-Quelle über den Kafka-Endpunkt des Hubs liest: `brokers` `<namespace>.servicebus.windows.net:9093`, `topic` der Event Hub, `tls` an, `auth: sasl_plain` mit dem Benutzernamen `$ConnectionString` und der Verbindungszeichenfolge als Passwort. Der Basic-Tarif hat keinen Kafka-Endpunkt. Mit `messageFormat: azure_records` wird jede `{"records": [...]}`-Nachricht entpackt: Ein Log-Datensatz wird zu einem Log-Event zu seiner `time`, und ein Metrik-Datensatz wird zu einem Sample pro Statistik im `metricsStream` des Connectors (Standard `default`), benannt wie die [Azure Monitor-Metriken](#cloud-metriken).

### S3-Objekte

Ein `s3_source`-Connector listet alle 30 Sekunden einen Bucket auf und liest die Objekte, die er noch nicht gelesen hat, beginnend mit den ältesten, aus AWS S3 oder einem S3-kompatiblen Speicher.

```bash
curl -X POST http://localhost:5080/api/v1/connectors \
  -H "authorization: Bearer $MS_TOKEN" \
  -H 'content-type: application/json' \
  -d '{
        "name": "elb-logs",
        "kind": "s3_source",
        "configJson": {
          "bucket": "acme-logs",
          "region": "us-east-1",
          "prefix": "AWSLogs/123456789012/",
          "auth": "node_role",
          "targetStream": "elb",
          "startFrom": "latest"
        }
      }'
```

| Feld | Hinweise |
|---|---|
| `bucket`, `region`, `endpoint`, `virtualHostedStyle`, `auth` und seine Schlüssel | Wie für ein [S3-Ziel](#amazon-s3). Die Anmeldedaten benötigen `s3:ListBucket` für den Bucket und `s3:GetObject` für die Objekte. |
| `prefix` | Nur Objekte unter diesem Präfix werden gelesen. Jeder Pull listet es vollständig auf, daher sollte eine Quelle ein eigenes Präfix erhalten. |
| `targetStream` | Zielstream. Standard `default`. |
| `startFrom` | Wo der erste Lesevorgang beginnt: `latest`, der Standard, für Objekte, die ab jetzt und in den 5 Minuten davor erscheinen, oder `earliest` für alles unter dem Präfix. UI: **Lesebeginn**. |

- Ein Objekt wird als Zeilen gelesen. Eine Zeile, die ein JSON-Objekt ist, liefert die Felder eines Logs, eine, die nur `Records` enthält, wie CloudTrail sie schreibt, liefert ein Log pro Datensatz, und jede andere Zeile wird zu einer `message`. `.gz`- und `.zst`-Objekte werden anhand ihrer Namen dekomprimiert. Jedes Log hat außerdem `s3_bucket`, `s3_key` und `source`. Seine Zeit ist der Zeitpunkt der letzten Änderung des Objekts.
- Ein Pull liest bis zu 100 Objekte oder bis 50.000 Logs, und der nächste folgt sofort, solange mehr vorhanden ist, für bis zu 2 Minuten.
- Der Lesestatus bewegt sich erst, wenn die Logs geschrieben sind. Ein Objekt, das nicht abgerufen werden kann, stoppt den Pull dort und wird 30 Sekunden später erneut versucht, sodass ein Log zweimal geschrieben werden kann, aber nicht verloren geht.
- Ein Objekt, das nicht gelesen werden kann, wird übersprungen und am Connector gemeldet, da ein erneuter Versuch alles danach aufhalten würde. Das betrifft ein Objekt, das beschädigt ist, über 256 MiB groß ist, nach der Dekomprimierung über 512 MiB groß ist, über eine Million Logs enthält oder eine Zeile über 64 MiB hat.
- Ein Objekt wird anhand seines Schlüssels und seiner Änderungszeit erkannt, mit einer Toleranz von 5 Minuten. Ein Objekt, das innerhalb dieser Toleranz erneut unter demselben Schlüssel geschrieben wird, wird nicht erneut gelesen, und eines, dessen Änderungszeit mehr als 5 Minuten älter als das neueste gelesene Objekt ist, wird überhaupt nicht gelesen. S3 datiert einen Multipart-Upload ab seinem Beginn, daher bleibt ein langsamerer Upload als das ungelesen.

### Google Cloud Pub/Sub-Abonnements

Ein `gcp_pubsub_pull`-Connector liest alle 30 Sekunden ein Pub/Sub-Abonnement, bis zu 1.000 Nachrichten pro Anfrage und sofort weiter, solange mehr vorhanden ist, und bestätigt die Nachrichten erst, wenn sie geschrieben sind. Was nicht geschrieben werden kann, wird erneut zugestellt, wenn seine Bestätigungsfrist abläuft, sodass eine Nachricht zweimal geschrieben werden kann, aber nicht verloren geht. Er eignet sich für mehr Logs, als ein [Push-Abonnement](#push-quellen) mit einer Nachricht pro Anfrage gut bewältigt.

| Feld | Hinweise |
|---|---|
| `serviceAccountKey` | Die JSON-Schlüsseldatei eines Service Accounts mit `roles/pubsub.subscriber` für das Abonnement. |
| `subscription` | `projects/<project>/subscriptions/<name>` oder der Name eines Abonnements im Projekt des Schlüssels. Geben Sie ihm eine Bestätigungsfrist von 60 Sekunden oder mehr. |
| `targetStream` | Zielstream. Standard `default`. |

Jede Nachricht wird gelesen wie eine gepushte: ein Cloud Logging `LogEntry` mit der Zuordnung des Push-Tabs, jedes andere JSON-Objekt als seine Felder, alles andere als `message`. **Verbindung testen** fragt ab, ob der Schlüssel das Abonnement konsumieren darf, ohne eine Nachricht zu entnehmen.

### Wie ein Pull läuft

Die Seite des Connectors zeigt an, wann eine Quelle zuletzt empfangen hat. Eine Quelle, deren letzter Lesevorgang fehlgeschlagen ist, zeigt daneben eine Warnung an, mit dem Grund in ihrem Tooltip und in den Einstellungen des Connectors, und auch was eine Quelle zuletzt übersprungen hat, wird dort angegeben. Events, die ihr Stream ablehnt, weil ein Wert nicht zum Typ seines Felds passt, werden nicht erneut gesendet: Eine Quelle fährt fort, und ein Push-Endpunkt antwortet weiterhin mit Erfolg, da die Plattform die gesamte Anfrage erneut senden würde. Was der Connector zuletzt übersprungen hat, gibt dann an, wie viele Events abgelehnt wurden, und nennt den ersten Grund. Über die API enthält `readState` `lastError` und `lastWarning`, jeweils mit `atTime` und `text`, sowie `position`, wo dieser angekommen ist. Das Speichern eines Connectors lässt seinen Stand unverändert.

## Ziele

Ein Ziel empfängt jedes Ereignis, das durch die Schritte einer geplanten Pipeline kommt. Fügen Sie den Konnektor mit **Ziel hinzufügen → Konnektor** den **Zielen** des Flows hinzu. Eine fehlgeschlagene Zustellung wird innerhalb des Laufs wiederholt, und Ereignisse, die der Konnektor weiterhin nicht annimmt, gehen in den Dead-Letter-Stream. Siehe [Wiederholungen und Dead Letters](/de/pipelines#wiederholungen-und-dead-letters).

Ein Ziel, das ausgeschaltet ist, empfängt nichts. Jeder Lauf überspringt den Konnektor und nennt ihn im `warning` des Laufs. Die übersprungenen Ereignisse zählen nicht als fehlgeschlagen, werden nicht zu Dead Letters und werden nicht gesendet, wenn der Konnektor wieder eingeschaltet wird. Im Editor zeigt ein ausgeschalteter Konnektor **Aus** an.

| Typ | Payload |
|---|---|
| `s3` | Ein JSON-Lines-Objekt pro Batch, `PUT` auf `s3://<bucket>/<prefix><id>.jsonl`. |
| `kafka` | Eine Nachricht pro Ereignis im Topic, mit dem Ereignis als JSON-Payload. |
| `http` | Der Batch wird in einer Anfrage oder, wenn er groß ist, in mehreren, als NDJSON oder als ein JSON-Array gesendet. |

|---|---|---|---|

Ein benutzerdefinierter Header darf kein Header sein, den die Zustellung selbst setzt: `Host`, `Content-Type`, `Content-Length`, `Content-Encoding`, `Transfer-Encoding`, `Connection`, `X-MoleSignal-Timestamp` oder `X-MoleSignal-Sign`.

Für eine Zustellung gelten diese Regeln:

- Ein Batch, der größer als 4 MiB ist, wird in mehrere Anfragen aufgeteilt. Ein Ereignis, das größer ist, wird in einer eigenen Anfrage gesendet.
- Jeder `2xx`-Status gilt als zugestellt. Jeder andere Status lässt die Zustellung fehlschlagen, ebenso eine Weiterleitung: Weiterleitungen werden nicht gefolgt.
- Eine Anfrage läuft nach 30 Sekunden in einen Timeout.
- MoleSignal löst den Host vor der Anfrage auf und stellt nur Verbindungen zu den aufgelösten Adressen her. Eine Adresse, unter der Cloud-Metadatendienste antworten, wird abgelehnt, ob sie in der URL erscheint oder aus DNS stammt: `169.254.0.0/16`, `fe80::/10`, `fd00:ec2::254` und `100.100.100.200`. Andere private Adressen sind zulässig.

#### HMAC-Signatur prüfen

Mit `hmac` enthält jede Anfrage zwei Header:

| Header | Inhalt |
|---|---|
| `X-MoleSignal-Timestamp` | Die Zeit der Anfrage in Unix-Sekunden. |
| `X-MoleSignal-Sign` | `sha256=<hex>`, der HMAC-SHA256 von `<timestamp>.<body>` mit dem gemeinsamen Secret. |

Um eine Anfrage zu prüfen, berechnen Sie den HMAC-SHA256 aus dem Zeitstempel, einem `.` und den rohen Body-Bytes mit demselben Secret und vergleichen Sie das Ergebnis in konstanter Zeit mit der Signatur. Lehnen Sie einen Zeitstempel ab, der älter als einige Minuten ist, damit eine abgefangene Anfrage nicht später erneut gesendet werden kann.

```python
import hashlib
import hmac
import time


def verify(secret: bytes, timestamp: str, signature: str, body: bytes, tolerance: int = 300) -> bool:
    if abs(time.time() - int(timestamp)) > tolerance:
        return False
    signed = timestamp.encode() + b"." + body
    expected = "sha256=" + hmac.new(secret, signed, hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, signature)
```

## AWS-Authentifizierung

S3 und CloudWatch Logs authentifizieren sich auf eine von fünf Arten bei AWS:

| `auth` | UI | Schlüssel | Anmeldedaten |
|---|---|---|---|
| `access_key` | **Zugriffsschlüssel** | `accessKey`, `secretKey` | Der langlebige Schlüssel eines IAM-Benutzers. |
| `temporary_key` | **Temporärer Schlüssel** | `accessKey`, `secretKey`, `sessionToken` | Ein kurzlebiger Schlüssel von AWS STS, nur zusammen mit seinem Sitzungstoken gültig. Ersetzen Sie ihn vor Ablauf. |
| `node_role` | **Knotenidentität** | | Die Identität des Knotens, auf dem MoleSignal läuft. Es wird kein Schlüssel gespeichert. |
| `assume_role` | **Rolle übernehmen** | `roleArn`, optional `accessKey` und `secretKey` | Eine über AWS STS mit der externen ID der Organisation übernommene Rolle. |
| `web_identity` | **Web-Identität** | `roleArn` | Eine mit dem Web-Identitätstoken des Knotens übernommene Rolle. |

Ohne `auth` entscheiden die gespeicherten Schlüssel: Ein Zugriffsschlüssel gilt als `access_key`, ein `roleArn` als `assume_role` und keines von beiden als `node_role`. Ein `roleArn` hat die Form `arn:aws:iam::<account>:role/<name>`.

### Knotenidentität

`node_role` verwendet die Identität, die die AWS SDKs auf dem Knoten finden: EKS-IAM-Rollen für Servicekonten (IRSA) oder EKS Pod Identity, eine ECS-Task-Rolle oder ein EC2-Instanzprofil. Ein statischer Schlüssel in der Umgebung des Knotens, etwa `AWS_ACCESS_KEY_ID`, wird für Connectoren nie verwendet.

<Warning>
  Die Identität des Knotens und sein Web-Identitätstoken gehören zum Deployment. Jede Organisation im Deployment kann `node_role` und `web_identity` wählen, daher können die Connectoren jeder Organisation auf alles zugreifen, was die Identität des Knotens erreichen kann, und jede Rolle übernehmen, die dem Token des Knotens vertraut. Gewähren Sie nur Zugriff, den jede Organisation haben darf.
</Warning>

### Rolle übernehmen

`assume_role` fordert bei AWS STS einen einstündigen Schlüssel der Rolle an und erneuert den Schlüssel 5 Minuten vor Ablauf. Die Basis-Anmeldedaten, mit denen die Rolle übernommen wird, sind die Identität des Knotens. Wählen Sie für ein Deployment, das nicht auf AWS läuft, **Rolle mit Zugriffsschlüssel statt Knotenidentität übernehmen** und geben Sie den Schlüssel eines IAM-Benutzers ein.

Jede Organisation übernimmt Rollen mit ihrer eigenen externen ID, `molesignal-<organization ID>`, die nicht geändert werden kann. Das Formular zeigt sie unter **Externe ID** an, und `GET /api/v1/connectors/aws-external-id` gibt sie zurück. Verlangen Sie die externe ID in der Vertrauensrichtlinie der Rolle, damit keine andere Organisation die Rolle übernehmen kann, selbst wenn sie den ARN kennt:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": { "AWS": "<ARN of the node role or IAM user>" },
      "Action": "sts:AssumeRole",
      "Condition": { "StringEquals": { "sts:ExternalId": "molesignal-<organization ID>" } }
    }
  ]
}
```

Die Sitzung heißt `molesignal-<connector ID>`; unter diesem Namen erscheint sie in AWS CloudTrail. Die Anfrage geht an den regionalen STS-Endpunkt der `region` des Connectors: an `us-east-1`, wenn die Region leer ist, und an die Domain `amazonaws.com.cn` für die China-Regionen.

### Web-Identität

`web_identity` übernimmt die Rolle mit dem Web-Identitätstoken, dessen Pfad die Variable `AWS_WEB_IDENTITY_TOKEN_FILE` des Knotens angibt, etwa das Servicekonto-Token, das EKS für IRSA projiziert. Ein Connector kann keine andere Datei angeben. Die Vertrauensrichtlinie der Rolle muss dem OIDC-Anbieter vertrauen, der das Token ausstellt. Auf einem Knoten ohne `AWS_WEB_IDENTITY_TOKEN_FILE` hat der Connector keine Anmeldedaten.

Das Token wird am regionalen STS-Endpunkt der `region` des Connectors eingetauscht oder an `AWS_ENDPOINT_URL_STS`, wenn die Umgebung des Knotens diese Variable setzt. Dasselbe gilt für eine Knotenidentität, die von IRSA stammt.

## Verbindung testen

**Verbindung testen** prüft die Einstellungen so, wie sie im Formular stehen, bevor sie gespeichert werden. Ein leer gelassenes Secret entspricht dem gespeicherten. Jede Art führt nur das Nötigste aus, um zu belegen, dass eine Zustellung oder ein Abruf funktionieren kann:

| Art | Test |
|---|---|
| `s3` | Schreibt das Objekt `.molesignal-connection-test` unter dem Präfix und entfernt es, wenn die Richtlinie es erlaubt. |
| `kafka` | Liest die Metadaten des Topics von den Brokern, was die Verbindung, TLS und die Authentifizierung sowie die Existenz des Topics belegt. Schreibt keine Nachricht. |
| `http` | Sendet ein als Test gekennzeichnetes Ereignis: `"message": "MoleSignal connection test"` und `"molesignal_connection_test": true`. |
| `aws_cloudwatch_logs` | Liest höchstens ein Ereignis aus der letzten Minute der Log-Gruppe. Schreibt nichts in den Stream und lässt die Leseposition unverändert. |
| `kafka_source` | Liest die Metadaten des Topics von den Brokern, wie bei `kafka`. Liest keine Nachricht und lässt die Leseposition unverändert. |
| `s3_source` | Listet ein Objekt unter dem Präfix auf, was die Anmeldedaten und `s3:ListBucket` belegt. Liest nichts und lässt die Leseposition unverändert. |

Ein Test bricht nach 25 Sekunden ab. Über die API erwartet `POST /api/v1/connectors/test` die Felder `kind` und `configJson` zum Testen.         "kind": "kafka",

```json
{ "ok": true, "code": "ok", "detail": null, "elapsedMs": 412 }
```

`elapsedMs` gibt an, wie lange der Test gedauert hat. Ein fehlgeschlagener Test nennt die Ursache in `code`, und `detail` enthält die Meldung der Gegenseite, bis zu 600 Zeichen:

| `code` | Bedeutung |
|---|---|
| `ok` | Verbunden. |
| `invalid` | Die Einstellungen können nicht funktionieren, oder der Connector ist eine Push-Quelle, bei der es nichts zu verbinden gibt. |
| `no_credentials` | Es konnten keine AWS-Anmeldedaten bezogen werden: Der Knoten hat keine Identität oder keine der angeforderten Art. |
| `denied` | Die Gegenseite hat die Anmeldedaten oder deren Berechtigungen abgelehnt. |
| `not_found` | Der Bucket, das Topic, die Log-Gruppe oder die Adresse existiert nicht. |
| `tls` | Der TLS-Handshake ist fehlgeschlagen: Ein Zertifikat wird nicht vertraut oder wurde nicht vorgelegt. |
| `unreachable` | Der Host konnte nicht aufgelöst werden oder es konnte keine Verbindung zu ihm hergestellt werden. |
| `timeout` | Keine rechtzeitige Antwort. |
| `failed` | Jeder andere Fehler. |

## API

| Endpoint | Berechtigung | Zweck |
|---|---|---|
| `GET /api/v1/connectors` | `pipelines.read` | Listet die Connectoren der Organisation auf. |
| `POST /api/v1/connectors` | `pipelines.edit` | Erstellt einen Connector. `enabled` ist standardmäßig `true`. |
| `GET /api/v1/connectors/{id}` | `pipelines.read` | Liest einen Connector. |
| `PUT /api/v1/connectors/{id}` | `pipelines.edit` | Ersetzt `name`, `kind`, `configJson` und `enabled`; alle sind erforderlich. |
| `DELETE /api/v1/connectors/{id}` | `pipelines.edit` | Löscht einen Connector. |
| `POST /api/v1/connectors/test` | `pipelines.edit` | Testet Einstellungen vor dem Speichern. |
| `GET /api/v1/connectors/aws-external-id` | `pipelines.read` | Gibt die externe ID der Organisation als `externalId` zurück. |

Ein Connector liefert `id`, `name`, `kind`, `configJson` mit maskierten Secrets, `secretKeys`, `enabled`, `lastRunAt`, `readState`, `createdAt` und `updatedAt`.

## Berechtigungen

`pipelines.read` listet Connectoren auf, prüft sie und liest die externe ID. `pipelines.edit` erstellt, aktualisiert, löscht und testet Connectoren. Ein Test benötigt `pipelines.edit`, weil er die gespeicherten Secrets verwendet und für den Aufrufer eine Verbindung zu einem anderen System herstellt. Push-Empfänger authentifizieren sich mit dem Push-Token und akzeptieren kein normales Login-JWT als Ersatz.
