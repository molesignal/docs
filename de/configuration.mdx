MoleSignal liest eine TOML-Datei und `MS_`-Umgebungsvariablen. Verwenden Sie die mit jeder Version ausgelieferte Beispieldatei `conf/config.toml` als Ausgangspunkt. Die Beispieldatei enthält alle Einstellungen. Diese Seite beschreibt jede davon.

```bash
molesignal --config /etc/molesignal/config.toml
```

## So lädt MoleSignal die Konfiguration

MoleSignal übernimmt die Einstellungen in dieser Reihenfolge. Spätere Quellen überschreiben frühere.

1. Integrierte Standardwerte.
2. Die mit `--config` angegebene TOML-Datei.
3. `MS_`-Umgebungsvariablen.

Starten Sie den Prozess nach einer Änderung der Einstellungen neu. Ein laufender Prozess protokolliert Änderungen an der Datei, übernimmt sie aber nicht.

<Note>
  Die meisten Abschnitte ignorieren Schlüssel, die sie nicht definieren. Ein Tippfehler hat dort keine Auswirkung und löst keine Warnung aus. Die Abschnitte `[meta_database]`, `[object_store]` (einschließlich `[object_store.retry]`), `[telemetry]` (einschließlich `[telemetry.trace]` und `[telemetry.self_collect]`), `[apm]`, `[probe]`, `[otlp_grpc]`, `[notify]` und `[scheduled_reports.renderer]` lehnen unbekannte Schlüssel ab. Ein Tippfehler verhindert dort den Prozessstart.
</Note>

Die Spalte **Standard** in den Referenztabellen zeigt den Wert aus der Beispieldatei `conf/config.toml`. Falls MoleSignal bei einem fehlenden Schlüssel einen anderen integrierten Standardwert verwendet, weist die Beschreibung darauf hin.

## Umgebungsvariablen

Für jede Einstellung gibt es eine Umgebungsvariable. Schreiben Sie zuerst das Präfix `MS_`. Schreiben Sie dann jede Ebene des Einstellungspfads in Großbuchstaben und trennen Sie die Ebenen durch jeweils einen Unterstrich.

| Einstellung | Umgebungsvariable |
|---|---|
| `[http].port` | `MS_HTTP_PORT` |
| `[meta_database].dsn` | `MS_META_DATABASE_DSN` |
| `[cluster].advertise_addr` | `MS_CLUSTER_ADVERTISE_ADDR` |
| `[node].roles` | `MS_NODE_ROLES` |

Schreiben Sie Listen in TOML-Syntax, zum Beispiel `MS_NODE_ROLES='["intake","querier"]'`. MoleSignal erkennt keine Namen mit einem Punkt oder einem doppelten Unterstrich.

MoleSignal liest diese Variablen getrennt von den Einstellungen:

| Variable | Zweck |
|---|---|
| `MS_CIPHER_KEY` | Stammschlüssel für die Geheimnisse, die MoleSignal in PostgreSQL verschlüsselt. Geben Sie 32 zufällige Bytes in Base64-Kodierung an. Ohne diesen Schlüssel verwendet der Prozess einen Entwicklungsschlüssel, der nur aus Nullbytes besteht, und protokolliert eine Warnung. Ändern Sie den Schlüssel nie, ohne `rewrap-kek` auszuführen. Siehe [Checkliste für den Produktivbetrieb](/de/deployment/production-checklist). |
| `MS_AUTH_JWT_SECRET_OVERRIDE` | Legt das JWT-Signaturgeheimnis fest und überschreibt damit das Geheimnis, das MoleSignal beim ersten Start in PostgreSQL erzeugt. |
| `MS_SELF_TELEMETRY_CLUSTER_TOKEN` | Gemeinsames Geheimnis zur Authentifizierung der Trace-Kandidaten und Eigentelemetriedaten, die Knoten bei einer rollenbasierten Bereitstellung untereinander weiterleiten. Legen Sie auf allen Knoten dieser Bereitstellung denselben Wert fest, solange die [Trace-Erfassung](#trace-erfassung-und-tail-sampling) (standardmäßig aktiv) oder `[telemetry.self_collect]` aktiv ist. Ein Knoten ohne die Rolle `intake` startet ohne diesen Wert nicht. |
| `MS_TRACE_FINGERPRINT_KEY` | Schlüssel für die HMAC-SHA-256-Fingerabdrücke, die anstelle von Werten gespeichert werden, die MoleSignal nie speichert: Strukturen von SQL-Anweisungen und Objektschlüssel in [MoleSignals eigenen Spans](/de/self-observability#verteiltes-tracing-im-backend) sowie Datenbanknamen in [APM-Abhängigkeiten](/de/apm#abhängigkeiten). Verwenden Sie mindestens 16 Bytes. MoleSignal ignoriert kürzere Werte. Legen Sie auf allen Knoten denselben Wert fest, da unterschiedliche Schlüssel unterschiedliche Fingerabdrücke erzeugen. Ohne Schlüssel schreibt MoleSignal keinen Fingerabdruck und verwendet auch keinen Hash ohne Schlüssel als Ersatz. MoleSignal liest den Schlüssel ausschließlich aus der Umgebung. Der Schlüssel erscheint nie in API-Antworten, Logs oder Spans. |
| `MS_AGENT_OPENAI_API_KEY`, `MS_AGENT_ANTHROPIC_API_KEY`, `MS_AGENT_COMPATIBLE_API_KEY` | Ersatz-API-Schlüssel für die Modellanbieter von Mole Agent in Entwicklungsumgebungen. Zu jedem Schlüssel gehört eine passende `_BASE_URL`-Variable. Konfigurieren Sie die Anbieter für den Produktivbetrieb stattdessen direkt im Produkt. |
| `RELEASE_CHANNEL` | Kennzeichnet den Reifegrad der Bereitstellung: `alpha`, `beta`, `rc` oder `stable`. |
| `RUST_LOG` | Überschreibt `[telemetry].log_level`, sofern gesetzt. |
| `AZURE_STORAGE_ACCOUNT`, `AZURE_STORAGE_ACCESS_KEY` | Azure Blob-Zugangsdaten für das Objektspeicher-Backend `azure`. |
| `GOOGLE_APPLICATION_CREDENTIALS` | Pfad zur JSON-Datei des Dienstkontos für das Objektspeicher-Backend `gcs`. |

## Mindesteinstellungen für den Produktivbetrieb

Ein Knoten im Produktivbetrieb benötigt mindestens diese Einstellungen. Behalten Sie für die übrigen Einstellungen in der Datei die Standardwerte bei.

```toml
[http]
external_url = "https://molesignal.example.com"

[meta_database]
dsn = "postgres://molesignal:<password>@db.internal:5432/molesignal"

[object_store]
backend = "s3"
bucket = "molesignal"
region = "us-east-1"
endpoint = ""          # empty for AWS S3, the service URL for S3-compatible storage
access_key = ""        # prefer MS_OBJECT_STORE_ACCESS_KEY
secret_key = ""        # prefer MS_OBJECT_STORE_SECRET_KEY

[wal]
dir = "/var/lib/molesignal/wal"

[auth]
root_email = "admin@example.com"
root_password = "<initial password>"
```

Setzen Sie außerdem `MS_CIPHER_KEY` als Umgebungsvariable. Die [Checkliste für den Produktivbetrieb](/de/deployment/production-checklist) enthält alle Schritte vor der Inbetriebnahme.

## Knoten

Legen Sie mit `[node]` fest, welche Rollen ein Prozess ausführt. Siehe [Rollenbasierte Bereitstellung](/de/deployment/role-based).

| Schlüssel | Standard | Beschreibung |
|---|---|---|
| `roles` | `["standalone"]` | Auszuführende Rollen: `standalone`, `router`, `intake`, `querier`, `compactor`, `alert`. Mit `standalone` laufen alle Rollen in einem Prozess. |
| `id` | leer | Knoten-ID mit maximal 64 Zeichen. Bei einem leeren Wert verwendet MoleSignal den Hostnamen des Betriebssystems. Legen Sie für jeden Prozess eine eigene ID fest, wenn mehrere Prozesse auf demselben Host laufen. |
| `drain_timeout_secs` | `30` | Wartezeit nach `SIGTERM` oder `SIGINT`, um noch ausstehende Daten aus der Datenannahme zu schreiben. Nach Ablauf der Wartezeit beendet sich der Prozess. Ein anderer Knoten mit der Rolle `intake` übernimmt die noch nicht geschriebenen Daten. |

## Listener

### HTTP

| Schlüssel | Standardwert | Beschreibung |
|---|---|---|
| `bind` | `0.0.0.0` | Bind-Adresse. |
| `port` | `5080` | HTTP-Port, wenn `[http.tls]` deaktiviert ist. |
| `gzip` | `true` | Komprimiert die vom Prozess bereitgestellten Dateien der Weboberfläche mit gzip, sofern der Client gzip akzeptiert. API-Antworten bleiben unkomprimiert. Setzen Sie den Wert auf `false`, wenn ein Reverse-Proxy die Komprimierung übernimmt. |
| `external_url` | leer | Öffentliche Origin, zum Beispiel `https://molesignal.example.com`. Ohne diesen Wert verwendet die Weboberfläche die Origin des Browsers. Generierte Onboarding-Snippets verwenden diesen Wert. Benutzerdefinierte Domains von Statusseiten verwenden ihn als CNAME-Ziel. Auch die Konto- und Chatlinks von Mole Agent in IM verwenden diese Origin. Die Callback-Adresse für Microsoft Teams liegt unter dieser Origin und erfordert daher HTTPS. Siehe [Mole Agent in IM](/de/im#sicherheit-für-teams). [Passkeys](/de/identity/mfa#voraussetzungen-für-die-instanz) sind an den Hostnamen dieser Origin gebunden und setzen einen Domainnamen mit HTTPS voraus. Starten Sie den Prozess nach einer Änderung neu. |

### HTTP mit TLS und ACME

`[http.tls]` startet einen TLS-Listener, der automatisch Zertifikate von einem ACME-Dienst wie Let's Encrypt bezieht.

| Schlüssel | Standardwert | Beschreibung |
|---|---|---|
| `enabled` | `false` | Hauptschalter. Bei `false` ignoriert der Listener alle anderen Schlüssel. |
| `plain_port` | `80` | Unverschlüsselter HTTP-Port für ACME-HTTP-01-Challenges und die Weiterleitung auf HTTPS. |
| `port` | `443` | HTTPS-Port. |
| `acme_directory` | `production` | `production`, `staging` (Staging-Umgebung von Let's Encrypt) oder eine benutzerdefinierte Verzeichnis-URL. |
| `account_email` | leer | E-Mail-Adresse des ACME-Kontos. Let's Encrypt verlangt diese Angabe. |
| `key_storage_dir` | `/var/lib/molesignal/acme` | Verzeichnis für den ACME-Kontoschlüssel und die Schlüssel der einzelnen Domains. |
| `issue_poll_secs` | `60` | Intervall für die Prüfung von Domains, für die noch ein Zertifikat aussteht. |
| `renewal_retry_secs` | `21600` | Intervall für erneute Verlängerungsversuche und die Prüfung der Ablaufdaten. |

### Internes gRPC

`[grpc]` überträgt Daten zwischen Knoten. Stellen Sie den Port nur in einem vertrauenswürdigen Netzwerk bereit.

| Schlüssel | Standardwert | Beschreibung |
|---|---|---|
| `bind` | `0.0.0.0` | Bind-Adresse. |
| `port` | `5082` | Port. Andere Knoten verwenden diesen Port auch über `[cluster].advertise_addr`. |
| `max_message_size` | `32` | Maximale Größe einer gRPC-Nachricht in MiB. |

### OTLP gRPC

`[otlp_grpc]` konfiguriert den OTLP-gRPC-Empfänger. Der Empfänger hat keinen separaten Schalter und lauscht auf allen Knoten mit der Rolle `intake`, einschließlich `standalone`-Knoten.

| Schlüssel | Standardwert | Beschreibung |
|---|---|---|
| `bind` | `0.0.0.0` | Bind-Adresse. |
| `port` | `4317` | Port. |
| `max_message_size` | `32` | Maximale Größe einer gRPC-Nachricht in MiB. |

### Arrow Flight SQL

`[flight_sql]` stellt einen Endpunkt für SQL-Clients wie DBeaver, JDBC und ADBC bereit. Jeder Aufruf erfordert ein API-Token. Siehe [Datenbankclients](/de/query/database-clients).

| Schlüssel | Standardwert | Beschreibung |
|---|---|---|
| `enabled` | `false` | Startet den Listener. |
| `bind` | `0.0.0.0` | Bind-Adresse. |
| `port` | `5083` | Port. |
| `default_lookback_hours` | `24` | Rückblickzeitraum in Stunden für SQL-Abfragen ohne Zeitfilter. |
| `max_message_size` | `32` | Maximale Nachrichtengröße in MiB. |

### Probe Agent

`[probe]` konfiguriert die Registrierungs- und Steuerungsendpunkte für Probe Agents. Die Endpunkte starten auf `standalone`- und `alert`-Knoten. Die Registrierung nutzt TLS mit Serverauthentifizierung. Der Steuerungsstream nutzt gegenseitiges TLS mit kurzlebigen Identitäten. Siehe [Synthetisches Monitoring](/de/synthetics).

| Schlüssel | Standardwert | Beschreibung |
|---|---|---|
| `bind` | `0.0.0.0` | Bind-Adresse. |
| `register_port` | `5084` | Registrierungsport. Muss sich von `control_port` unterscheiden. |
| `control_port` | `5085` | Port für den Steuerungsstream. |
| `register_endpoint` | `https://localhost:5084` | Öffentliche `https://`-URL, über die sich Agents registrieren. Der Befehl für die einmalige Registrierung gibt diese URL aus. Legen Sie diese URL fest, wenn der Endpunkt hinter einem Proxy oder Load Balancer liegt. |
| `control_endpoint` | `https://localhost:5085` | Öffentliche `https://`-URL des Steuerungsstreams. |
| `server_names` | `["localhost", "127.0.0.1"]` | DNS-Namen und IP-Adressen im Serverzertifikat. Geben Sie auch die öffentlichen Hostnamen der Endpunkte an. |
| `certificate_days` | `30` | Gültigkeitsdauer der ausgestellten Zertifikate in Tagen, von 1 bis 365. |
| `max_message_size` | `32` | Maximale Nachrichtengröße in MiB. |

### pprof

`[profiling]` startet auf dem Knoten einen lokalen pprof-Listener für die Diagnose.

| Schlüssel | Standardwert | Beschreibung |
|---|---|---|
| `enabled` | `false` | Startet den Listener. |
| `bind` | `127.0.0.1` | Bind-Adresse. Verwenden Sie eine Loopback-Adresse, sofern `allow_remote` nicht auf `true` steht. |
| `port` | `5086` | Port. Muss sich von den Ports aller anderen aktivierten Listener unterscheiden. Das gilt auch für Listener von Rollen, die auf diesem Knoten nicht ausgeführt werden. |
| `allow_remote` | `false` | Erlaubt für `bind` auch Adressen außerhalb des Loopback-Bereichs. Bei externem Zugriff können Laufzeitinformationen offengelegt werden. |

## Speicherung

### Metadatenbank

`[meta_database]` konfiguriert die PostgreSQL-Datenbank für Metadaten, Identitäten, den Dateikatalog und Produktressourcen.

| Schlüssel | Standardwert | Beschreibung |
|---|---|---|
| `dsn` | `postgres://molesignal:molesignal@localhost:5432/molesignal` | PostgreSQL-Verbindungszeichenfolge. Ersetzen Sie die Beispielzugangsdaten. |
| `min_connections` | `2` | Anzahl der Verbindungen, die MoleSignal beim Start öffnet. Der Wert ist auf `max_connections` begrenzt. |
| `max_connections` | `16` | Maximale Anzahl von Verbindungen im Verbindungspool. |

MoleSignal führt beim Start die integrierten Schemamigrationen für die Datenbank aus. Siehe [Upgrade](/de/upgrade).

### Objektspeicher

`[object_store]` konfiguriert den Speicher für Parquet-Dateien, Suchindizes und Profil-Blobs. Backends: `local`, `s3`, `azure`, `gcs`. Verwenden Sie `s3` für AWS S3 und S3-kompatible Dienste wie RustFS, Cloudflare R2 und Alibaba Cloud OSS.

| Schlüssel | Standardwert | Beschreibung |
|---|---|---|
| `backend` | `local` | `local`, `s3`, `azure` oder `gcs`. |
| `root` | `./data/objects` | Verzeichnis des `local`-Backends. Die anderen Backends ignorieren diesen Wert. |
| `bucket` | leer | Bucket-Name für `s3` und `gcs`, Containername für `azure`. Für diese Backends erforderlich. |
| `region` | leer | S3-Region. S3-kompatible Dienste geben an, welchen Wert sie erwarten. |
| `endpoint` | leer | URL des S3-Endpunkts. Lassen Sie den Wert für AWS S3 leer. Verwenden Sie für RustFS und ähnliche Dienste URLs nach dem Muster `http://host:9000`. |
| `path_style` | `false` | `false` verwendet die Adressierung im Virtual-Hosted-Stil, die AWS S3 und Huawei Cloud OBS benötigen. Setzen Sie den Wert auf `true` für die pfadbasierte Adressierung, die RustFS und die meisten selbst gehosteten Dienste benötigen. |
| `access_key` | leer | S3-Zugriffsschlüssel oder Azure-Speicherzugriffsschlüssel. |
| `secret_key` | leer | Geheimer S3-Schlüssel. |
| `credentials_file` | leer | Pfad zu einer Datei mit den Zeilen `access_key=<value>` und `secret_key=<value>`. Siehe die Reihenfolge unten. |
| `multipart_threshold_size` | `32` | Ab dieser Größe in MiB lädt MoleSignal Objekte in Teilen hoch. Bei Manifestobjekten und Schreibvorgängen mit Versionsbedingung verwendet MoleSignal immer eine einzige Anfrage. Der Mindestwert ist 1. |
| `multipart_part_size` | `8` | Größe eines Teils bei einem mehrteiligen Upload in MiB, von 5 bis 1024. Bei sehr großen Objekten verwendet MoleSignal größere Teile, damit ein Upload höchstens 10.000 Teile umfasst. |
| `range_threshold_size` | `16` | Ab dieser Größe in MiB teilt MoleSignal das Lesen eines Bytebereichs in parallele Anfragen für Teilbereiche auf. Der Mindestwert ist 1. |
| `range_chunk_size` | `8` | Größe des Bytebereichs pro Teilanfrage in MiB, von 1 bis 1024. |
| `max_concurrency` | `8` | Anzahl gleichzeitiger Objektspeichervorgänge pro Prozess. |
| `op_timeout_secs` | `30` | Zeitlimit für das Warten auf einen freien Platz für einen parallelen Vorgang und für einen einzelnen Backend-Vorgang. |
| `health_probe_interval_secs` | `30` | Intervall für die Funktionsprüfung im Hintergrund, die Schreib-, Lese- und Löschvorgänge testet. Der Mindestwert ist 5. |

Die S3- und Azure-Clients verwenden die erste der folgenden Quellen, die sowohl einen Zugriffsschlüssel als auch einen geheimen Schlüssel bereitstellt:

1. Die Variablen `MS_OBJECT_STORE_ACCESS_KEY` und `MS_OBJECT_STORE_SECRET_KEY`.
2. Die unter `credentials_file` angegebene Datei.
3. Die Schlüssel `access_key` und `secret_key`.

Das Start-Log gibt die verwendete Quelle als `object_store_credentials_source` aus: `env`, `file`, `inline` oder `none`. Hinterlegen Sie den geheimen Schlüssel bevorzugt in einer Umgebungsvariablen oder einer Zugangsdaten-Datei statt in `config.toml`.

Jeder Teil eines mehrteiligen Uploads und jede Teilanfrage beim Lesen eines Bytebereichs zählt als eigener Objektspeichervorgang. Jeder Vorgang belegt einen Platz für parallele Vorgänge, hat eigene Wiederholungsversuche und erscheint in den `object_store_*`-Metriken. Eine Übertragung belegt höchstens die Hälfte der verfügbaren Plätze, damit große Objekte andere Vorgänge nicht blockieren.

Bei vorübergehenden Fehlern der Cloud-Backends wiederholt MoleSignal den Vorgang mit exponentiell steigenden Wartezeiten:

| Schlüssel | Standardwert | Beschreibung |
|---|---|---|
| `[object_store.retry].max_attempts` | `4` | Gesamtzahl der Versuche pro Vorgang. |
| `[object_store.retry].base_backoff_ms` | `100` | Erste Wartezeit. |
| `[object_store.retry].max_backoff_ms` | `5000` | Maximale Wartezeit. |
| `[object_store.retry].jitter_ratio` | `0.2` | Faktor für die zufällige Abweichung jeder Wartezeit, von `0` bis `1`. |

### Write-Ahead-Log

`[wal]` konfiguriert das Write-Ahead-Log (WAL), das jeder Knoten im Objektspeicher ablegt. Ein Knoten bestätigt einen Schreibvorgang erst, wenn das zugehörige WAL-Objekt im Objektspeicher liegt. Deshalb benötigt der Knoten kein persistentes Volume. Siehe [Architektur](/de/architecture#dauerhaftigkeit-und-übernahme).

| Schlüssel | Standardwert | Beschreibung |
|---|---|---|
| `lease_secs` | `15` | Gültigkeitsdauer der Schreib-Lease in Sekunden, mindestens `3`. Verlängert ein Aufnahmeknoten die Lease nicht, übernimmt ein anderer Aufnahmeknoten nach Ablauf dieser Frist seit der letzten Verlängerung. Bis zur Übernahme kann bis zu ein weiteres Prüfintervall (`takeover_interval_secs`) verstreichen. MoleSignal liest den Wert nur beim Start. |
| `max_group_size` | `8` | Maximale Größe eines WAL-Objekts in MiB. Schreibvorgänge, die während des Schreibens des vorherigen Objekts desselben Datensatzes eintreffen, bündelt MoleSignal bis zu dieser Größe im nächsten Objekt. |
| `put_timeout_secs` | `10` | Maximale Dauer eines Schreibvorgangs für ein Objekt. |
| `put_attempts` | `3` | Anzahl der Versuche pro Schreibvorgang für ein Objekt. Schlagen alle Versuche fehl, lehnt MoleSignal die Schreibvorgänge im Objekt mit `503` ab. Die Schreibvorgänge lassen sich wiederholen. |
| `takeover_interval_secs` | `5` | Intervall, in dem ein Aufnahmeknoten nach abgelaufenen Schreib-Leases sucht, um die Schreibaufgaben zu übernehmen. |
| `encrypt` | `false` | Verschlüsselt jedes WAL-Objekt mit dem Hauptschlüssel (`MS_CIPHER_KEY`). |
| `max_takeover_size` | `512` | Speicher in MiB, den der Aufnahmeknoten bei einer Übernahme belegt, bevor er ein Segment veröffentlicht. `0` zählt als `1`. |

### Datenaufnahme

`[intake]` steuert die Arbeitsspeicherpuffer eines Aufnahmeknotens.

| Schlüssel | Standardwert | Beschreibung |
|---|---|---|
| `buffer_max_size` | `256` | Feste Obergrenze für den Rohdatenpuffer eines Streams in MiB. Der adaptive Schwellenwert überschreitet diese Grenze nie. |
| `max_buffer_memory_size` | `1024` | Gesamter Arbeitsspeicher, den die aktiven und abgetrennten Puffer des Prozesses reservieren, in MiB. |
| `flush_interval_secs` | `30` | Maximale Zeit zwischen zwei Schreibvorgängen aus dem Puffer. |
| `flush_parallelism` | `4` | Anzahl gleichzeitiger Schreibvorgänge aus den Puffern. |

`[intake.rotation]` passt die Größe der Parquet-Dateien dynamisch an:

| Schlüssel | Standardwert | Beschreibung |
|---|---|---|
| `adaptive_enabled` | `true` | Passt den nächsten Rohdatenschwellenwert jedes Streams anhand des Verhältnisses von kodierter Größe zu Rohdatengröße abgeschlossener Dateien an. |
| `target_file_size` | `128` | Zielgröße kodierter Parquet-Dateien in MiB. |
| `min_buffer_size` | `16` | Untergrenze des adaptiven Schwellenwerts in MiB. |
| `ewma_alpha` | `0.2` | Glättungsfaktor für das Verhältnis, größer als 0 und höchstens 1. |

`[intake.prometheus]` begrenzt die Aufnahme von Prometheus-Daten über `remote_write`:

| Schlüssel | Standardwert | Beschreibung |
|---|---|---|
| `max_labels_per_series` | `64` | Maximale Anzahl von Labels pro Zeitreihe, ohne `__name__`. |
| `max_label_name_length` | `128` | Maximale Länge eines Labelnamens in UTF-8-Bytes. |
| `max_label_value_length` | `2048` | Maximale Länge eines Labelwerts in UTF-8-Bytes. |
| `max_samples_per_batch` | `16384` | Maximale Anzahl von Messwerten pro internem Batch. |

`[intake.prometheus.cardinality]` prüft die Zulassung von Zeitreihen im Prozess, der die `remote_write`-Anfrage empfängt, bevor er den Batch an einen Aufnahmeknoten weiterleitet. Jeder Prozess zählt die Zeitreihen, die er empfängt. Bei mehreren Routern wendet daher jeder Router die Grenzwerte unabhängig an:

| Schlüssel | Standardwert | Beschreibung |
|---|---|---|
| `enabled` | `true` | Wendet die Grenzwerte an. |
| `max_active_series_per_process` | `1000000` | Maximale Anzahl aktiver Zeitreihen pro Prozess. |
| `max_new_series_per_minute` | `20000` | Maximale Anzahl neuer Zeitreihen, die der Prozess pro Minute annimmt. |
| `idle_ttl_secs` | `900` | Nach dieser Dauer ohne Aktivität zählt eine Zeitreihe nicht mehr zum Limit. |

Die Grenzwerte pro Organisation und pro Metrik sind eine Plattformeinstellung: **Einstellungen → Metrikkardinalität** in der Organisation `_sys`. Jeder Knoten liest die Grenzwerte alle 30 Sekunden neu ein und wendet sie auf die von ihm gezählten Zeitreihen an.

### Kompaktierung und Datenaufbewahrung

`[compactor]` führt Dateien zusammen und setzt die Aufbewahrungsregeln durch. Die Kompaktierung läuft auf `standalone`- und `compactor`-Knoten.

| Schlüssel | Standardwert | Beschreibung |
|---|---|---|
| `interval_secs` | `300` | Zeit zwischen Kompaktierungsrunden. |
| `target_size` | `512` | Maximale Gesamtgröße der Dateien pro Zusammenführung in MiB, von `1` bis `65536`. Die resultierende Datei ist ungefähr so groß oder kleiner. Bei der Zusammenführung liest MoleSignal die Eingabedateien abschnittsweise und lädt die Ausgabedatei in Teilen hoch. Dadurch steigt der Arbeitsspeicherbedarf nicht mit dieser Größe. Pro Zusammenführung liest MoleSignal höchstens 128 Dateien. Die übrigen Dateien führt MoleSignal in einer späteren Runde mit dem Ergebnis zusammen. Ist eine Datei größer als alle anderen Dateien der Zusammenführung zusammen, lässt MoleSignal sie aus. MoleSignal führt sie erst zusammen, wenn die neuen Dateien insgesamt ihre Größe erreichen. So schreibt MoleSignal eine große Datei nicht für wenige neue Daten neu. |
| `max_concurrent_groups` | `4` | Anzahl der Streams, die ein Knoten pro Runde gleichzeitig verarbeitet. |

Für Streams ohne eigene Aufbewahrungsdauer gilt die Plattformeinstellung **Einstellungen → Datenaufbewahrung** in der Organisation `_sys`. Der Standardwert beträgt 30 Tage. Legen Sie das Downsampling für jeden Metrik-Stream auf dessen Registerkarte **Nutzerbindung** fest. Siehe [Streams](/de/streams).

### Zulassungssteuerung

`[search.admission]` begrenzt, wie viele Abfragen einer Arbeitsgruppe gleichzeitig auf einem Knoten laufen. Wenn die Arbeitsgruppe ihr Limit erreicht, kommen weitere Abfragen in eine Warteschlange. Die Abfragen starten in der Reihenfolge ihres Eingangs. Wartet eine Abfrage länger als `max_wait_secs`, erhält sie `429`. Abfragen, die der Ergebnis-Cache beantwortet, warten nicht. Das Limit gilt für Abfragen über die Abfrage-API und Flight SQL, für Diagramme und Feldstatistiken im Explorer, für öffentliche Freigaben und für Suchjobs. Die Auswertung von Alerts und andere Hintergrundaufgaben umgehen die Warteschlange. Die Beispieldatei enthält diesen Abschnitt nicht.

| Schlüssel | Standardwert | Beschreibung |
|---|---|---|
| `default_max_concurrent` | Doppelte Anzahl der CPUs | Limit pro Knoten für Arbeitsgruppen ohne Eintrag in `groups`. `0` hebt das Limit auf. |
| `groups` | Leer | Tabelle, die dem Namen einer Arbeitsgruppe ihr Limit pro Knoten zuordnet. |
| `role_map` | Leer | Tabelle, die einer Rolle (`owner`, `admin`, `editor`, `viewer`) eine Arbeitsgruppe zuordnet. Rollen ohne Zuordnung verwenden `default`. |
| `max_wait_secs` | `60` | Maximale Wartezeit auf einen freien Platz, bevor MoleSignal `429` zurückgibt. Bei `0` gibt MoleSignal sofort `429` zurück, wenn die Arbeitsgruppe ihr Limit erreicht hat. |
| `cluster_default_max_concurrent` | `0` | Weiches clusterweites Limit für Arbeitsgruppen ohne Eintrag in `cluster_groups`. Ist das Limit erreicht, erhält die Abfrage sofort `429`. `0` hebt das Limit auf. |
| `cluster_groups` | Leer | Tabelle, die dem Namen einer Arbeitsgruppe ihr weiches clusterweites Limit zuordnet. |
| `cluster_sync_interval_secs` | `0` | Intervall zum Veröffentlichen der Knotenauslastung. Bei `0` gilt 5. |
| `cluster_stale_secs` | `0` | Knoten, die sich länger als hier angegeben nicht melden, fallen aus der Clusteransicht. Bei `0` gilt 30. |

`/metrics` zeigt den Status der Abfragen jeder Arbeitsgruppe mit den Metriken `query_admission_running`, `query_admission_waiting`, `query_admission_wait_seconds` und `query_admission_refusals_total` an.

### Caches

Jede Ebene ist ein LRU-Cache mit einer Gültigkeitsdauer. Eine Kapazität von `0` deaktiviert die Ebene. Unter `/metrics` erscheinen die Trefferquoten als `cache_<layer>_hit_ratio`.

| Abschnitt | Standardkapazität | Standard-TTL | Inhalt |
|---|---|---|---|
| `[cache.index_handle]` | `10000` | `600` s | Handles für geöffnete Suchindizes. |
| `[cache.query_result]` | `1000` | `60` s | Ergebnisse von SQL-Abfragen über abgeschlossene Zeitfenster. |
| `[cache.tantivy_result]` | `1000000` | `600` s | Häufigkeiten von Suchbegriffen, mit denen sich Dateien von der Suche ausschließen lassen. |
| `[cache.tantivy_footer]` | `100000` | `3600` s | Index-Footer, die das Lesen von Bytebereichen ersparen. |

Jeder Abschnitt unterstützt `capacity` und `ttl_secs`.

`[cache.parquet_metadata]` hält geparste Parquet-Footer einschließlich Seitenindizes im Arbeitsspeicher. Öffnet eine Abfrage eine Datei, deren Footer im Cache liegt, überspringt sie das Lesen des Footers. Der einzige Schlüssel ist `max_size` in MiB. Der Standardwert ist `256`. `0` deaktiviert den Cache.

`[cache.object]` speichert Bytebereiche entfernter Objekte auf dem lokalen Datenträger. Das Objekt-Backend `local` umgeht diesen Cache.

| Schlüssel | Standardwert | Beschreibung |
|---|---|---|
| `enabled` | `true` | Aktiviert den Cache. Ein Wert von `0` für `max_size` deaktiviert ihn ebenfalls. |
| `root` | `./data/cache/objects` | Cache-Verzeichnis. |
| `max_size` | `10240` | Maximale Cache-Größe in MiB, hier 10 GiB. |
| `block_size` | `4` | Blockgröße in MiB, von 1 bis 16. |
| `memory_size` | `256` | Speicherplatz für geprüfte Blöcke im Arbeitsspeicher in MiB. Beim erneuten Lesen eines solchen Blocks entfällt der Datenträgerzugriff. Bei `0` bleiben Blöcke nur auf dem Datenträger. |
| `min_free_size` | `1024` | Freizuhaltender Speicherplatz auf dem Datenträger in MiB, hier 1 GiB. |
| `max_concurrent_fetches` | `16` | Anzahl paralleler Blockabrufe. Der Wert muss größer als null sein. |
| `max_concurrent_fetches_per_object` | `4` | Anzahl paralleler Abrufe pro Objekt. Der Wert muss größer als null sein. |

Wenn der Cache `max_size` überschreitet oder der freie Speicherplatz auf dem Datenträger unter `min_free_size` fällt, entfernt der Cache zuerst die Blöcke, auf die am längsten nicht zugegriffen wurde. Löscht die Garbage Collection ein Objekt, entfernt der löschende Knoten auch dessen Blöcke aus dem Cache, sofern er das Objekt seit seinem Start gelesen hat. Andere Knoten entfernen diese Blöcke nach denselben Regeln wie alle anderen Blöcke.

Die Plattform legt fest, wie viele Dienste, Endpunkte, Abhängigkeiten, Operationen, Fehlergruppen, Versionen und Instanzen APM pro Stunde getrennt erfasst. Ändern Sie diese Grenzen unter **APM → Einstellungen → Kardinalitätsgrenzen** mit der Berechtigung `sys.settings.limits.manage`. Jeder Knoten liest sie alle 30 Sekunden neu ein. Siehe [APM-Einstellungen](/de/apm/settings#kardinalitätslimits). MoleSignal kann keine Konfigurationsdatei laden, die noch einen Abschnitt `[apm.cardinality]` enthält.

## Einstellungen in der Datenbank

MoleSignal speichert diese Einstellungen in PostgreSQL. Ändern Sie die Einstellungen über die Weboberfläche oder die API. Dafür gibt es keine TOML-Schlüssel:

- SSO-Anbieter (OIDC, OAuth 2.0, SAML und LDAP).
- Remote-Cluster für föderierte Abfragen.
- Domains und Zertifikate für Statusseiten sowie die Slack-App, mit der sich eine Statusseite zu Slack hinzufügen lässt.
- Benachrichtigungskanäle, Zeitpläne und Eskalationsrichtlinien.
- Modellanbieter, Prompts, Tools und Genehmigungsrichtlinie für Mole Agent.
- Verschlüsselungsschlüssel, Regeln zur Feldmaskierung und Freigaberichtlinie der Organisation.
