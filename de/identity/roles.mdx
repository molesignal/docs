Eine Rolle ist eine benannte Sammlung von Berechtigungen. Eine Berechtigungsrichtlinie ist ebenfalls eine solche Sammlung. Sie bleibt von den Rollen getrennt, damit mehrere
Rollen sie einbinden und API-Tokens ihr folgen können. Weisen Sie einem Mitglied eine Rolle für den gesamten Arbeitsbereich
unter [Benutzer](/de/identity/members#benutzer) zu. Eine Zugriffsfreigabe weist einem Benutzer oder einem Team eine Rolle für die
gesamte Organisation oder für ausgewählte Ressourcen zu, optional bis zu einem bestimmten Datum. Öffnen Sie **Identität und Zugriff →
Rollen**, **Berechtigungsrichtlinien** oder **Zugriffsfreigaben**.

## Rollen

**Rollen** listet die integrierten und benutzerdefinierten Rollen des Arbeitsbereichs auf. Die Liste zeigt die eingebundenen Richtlinien,
die gewährten Berechtigungen und die Verwendungsstellen der Rollen: Mitglieder, Dienstkonten, Einladungen und
Bindungen. Integrierte Rollen sind schreibgeschützt. Siehe [Integrierte Rollen](/de/identity#integrierte-rollen).

So erstellen Sie eine benutzerdefinierte Rolle:

1. Wählen Sie **Neue Rolle** aus.
2. Geben Sie einen **Schlüssel** aus Kleinbuchstaben, Ziffern und Unterstrichen ein. Der Schlüssel lässt sich später nicht ändern.
3. Geben Sie einen **Namen** und eine **Beschreibung** ein.
4. Aktivieren Sie unter **Berechtigungsrichtlinien** die Richtlinien, die die Rolle einbinden soll. Die Rolle übernimmt alle
   Berechtigungen dieser Richtlinien und übernimmt auch spätere Änderungen.
5. Aktivieren Sie unter **Eigene Berechtigungen** die Berechtigungen, die die Rolle zusätzlich zu den Richtlinien benötigt. Zu jeder
   Berechtigung steht, was sie erlaubt. Berechtigungen aus einer ausgewählten Richtlinie sind bereits aktiviert. Die Liste zeigt die
   zugehörige Richtlinie an. Diese Berechtigungen lassen sich hier nicht deaktivieren.
6. Wählen Sie **Rolle erstellen** aus.

Eine Rolle gewährt ihre eigenen Berechtigungen und die ihrer Richtlinien. Wählen Sie eine benutzerdefinierte Rolle aus, um ihre eigenen Berechtigungen oder ihre Richtlinien zu ändern.
Mit **Löschen** entfernen Sie eine benutzerdefinierte Rolle nur, wenn keine Mitgliedschaft, kein Dienstkonto,
keine Einladung und keine Bindung sie verwendet. Zum Lesen von Rollen benötigen Sie `iam.roles.read`, zum Ändern
`iam.roles.manage` und zum Löschen `iam.roles.delete`.

## Berechtigungsrichtlinien

**Berechtigungsrichtlinien** listet die integrierten und benutzerdefinierten Richtlinien des Arbeitsbereichs auf. Die Liste zeigt
die Berechtigungen jeder Richtlinie sowie die Rollen und Tokens, die sie verwenden. Eine Rolle bindet Richtlinien ein. Ein API-Token
kann einer Richtlinie folgen. Siehe [Was ein Token darf](/de/identity/tokens#berechtigungen-eines-tokens).

| Integrierte Richtlinie | Berechtigungen |
|---|---|
| **Beobachter mit Lesezugriff** | Liest Observability-Daten, Dashboards, Alerts, Bereitschaftspläne, gespeicherte Ansichten, Pipelines, Funktionen, Berichte, Statusseiten, synthetische Monitore, Servicelevel und Postmortems. |
| **Datenanalyst** | Analysiert Observability-Daten und erstellt Dashboards und gespeicherte Ansichten. |
| **Pipeline-Entwickler** | Liest Observability-Daten und verwaltet Streams, Pipelines und Funktionen. |
| **Alert-Administrator** | Liest Observability-Daten und verwaltet Alert-Regeln, Bereitschaftspläne, Statusseiten, synthetische Monitore und Postmortems. |
| **Organisationsadministrator** | Verwaltet Organisationseinstellungen, Mitglieder, Rollen, Zugriffsfreigaben, API-Tokens, Dienstkonten und Audit-Protokolle sowie Statusseiten, synthetische Monitore, Servicelevel und Postmortems. |
| **Datenerfassung** | Schreibt Daten und meldet Deployments: `logs.write`, `metrics.write`, `traces.write`, `profiles.write` und `apm.deploy`. Tokens für die Datenerfassung folgen dieser Richtlinie. |

Integrierte Richtlinien sind schreibgeschützt und ändern sich mit dem Produkt. Öffnen Sie eine integrierte Richtlinie und wählen Sie **Als benutzerdefinierte
Richtlinie kopieren** aus, um daraus eine eigene Richtlinie zu erstellen.

So erstellen Sie eine benutzerdefinierte Richtlinie:

1. Wählen Sie **Neue Richtlinie** aus.
2. Geben Sie einen **Namen**, einen **Schlüssel** aus Kleinbuchstaben, Ziffern und Unterstrichen und eine **Beschreibung** ein. Der Schlüssel lässt sich
   später nicht ändern.
3. Aktivieren Sie unter **Berechtigungen** die gewünschten Berechtigungen in **Visuell** oder schreiben Sie das Dokument in **JSON**.
   Beide Ansichten bearbeiten dasselbe Dokument. Die JSON-Ansicht zeigt den ersten Fehler und seine Position an. Bei einem gültigen Dokument listet sie
   vor dem Speichern die gewährten Berechtigungen auf.
4. Wählen Sie **Richtlinie erstellen** aus.

Ein Richtliniendokument orientiert sich an der Richtliniensprache von AWS IAM:

```json
{
  "Version": "1",
  "Statement": [
    { "Sid": "Dashboards", "Effect": "Allow", "Action": "dashboards.*" },
    { "Effect": "Allow", "Action": ["streams.read", "streams.query"] }
  ]
}
```

- `Version` ist `"1"`. Eine Richtlinie muss mindestens eine Berechtigung gewähren.
- `Effect` ist immer `"Allow"`: Eine Richtlinie kann Berechtigungen nur gewähren, nicht verweigern.
- `Action` gibt eine Berechtigung oder eine Liste von Berechtigungen an. `*` steht für eine beliebige Zeichenfolge. Damit steht
  `dashboards.*` für alle Dashboard-Berechtigungen und `*` für alle Berechtigungen der Organisation. Ein Eintrag in `Action`,
  der keiner Berechtigung entspricht, ist ungültig.
- `Sid` ist ein optionaler Name für die Anweisung.
- `Resource`, `Condition`, `Principal` und `NotAction` sind unzulässig: Eine Richtlinie gilt für die gesamte
  Organisation. Verwenden Sie eine
  [Zugriffsfreigabe](#zugriffsfreigaben), um eine Rolle für einzelne Ressourcen oder unter bestimmten Bedingungen zuzuweisen.

Eine Richtlinie speichert die Berechtigungen, die ihr Dokument zum Zeitpunkt des Speicherns gewährt. Ein Muster erfasst auch Berechtigungen,
die später zum Katalog hinzukommen. MoleSignal nimmt sie beim Start in die Richtlinie auf. Wenn Sie in **Visuell** eine Berechtigung auswählen,
ersetzt die Ansicht ein Dokument mit Mustern, einer `Sid` oder mehreren Anweisungen durch eine einzige Anweisung, die jede
Berechtigung einzeln aufführt. Die Ansicht weist vorab darauf hin.

Wenn Sie eine Richtlinie ändern, wirkt sich die Änderung sofort auf alle Rollen aus, die sie einbinden, und auf alle Tokens, die ihr folgen.
Mit **Löschen** entfernen Sie eine benutzerdefinierte Richtlinie nur, wenn keine Rolle sie einbindet und kein gültiges Token ihr folgt.
Ein widerrufenes oder abgelaufenes Token, das der Richtlinie folgte, behält seine bisherigen Berechtigungen als Liste. Zum Lesen von Richtlinien
benötigen Sie `iam.policies.read`, zum Ändern `iam.policies.manage` und zum Löschen `iam.policies.delete`.

## Zugriffsfreigaben

Eine Zugriffsfreigabe ist eine Rollenbindung: Sie weist einer Identität in einer Organisation eine Rolle für einen bestimmten
Ressourcenbereich zu. Verwenden Sie eine Zugriffsfreigabe, um den Zugriff an eine Person, ein Team oder eine Ressource zu binden, statt die Berechtigungen einer
allgemeinen Rolle zu erweitern.

1. Öffnen Sie **Zugriffsfreigaben** und wählen Sie **Neue Zugriffsfreigabe** aus.
2. **Identität**: Wählen Sie **Benutzer** oder **Team** und dann den gewünschten Eintrag aus.
3. **Organisation**: Das Feld zeigt zur Information den aktuellen Arbeitsbereich an.
4. **Ressourcenbereich**: Wählen Sie **Gesamte Organisation** oder einen Ressourcentyp (**Dashboard** oder **Stream**) und dann
   eine einzelne Ressource oder **Alle Ressourcen dieses Typs** aus.
5. **Rolle und Berechtigungen**: Wählen Sie die Rolle aus, die die Zugriffsfreigabe zuweist.
6. **Einschränkungen**: Geben Sie optional eine **Umgebung** an, mit der Anfragen exakt übereinstimmen müssen, etwa `prod`,
   und legen Sie unter **Läuft ab am** den Ablaufzeitpunkt fest.
7. Wählen Sie **Zugriffszuweisung erstellen** aus.

Mit **Löschen** beenden Sie eine Zugriffsfreigabe sofort. Zum Lesen von Zugriffsfreigaben benötigen Sie `iam.grants.read`, zum Erstellen oder
Löschen `iam.grants.manage`.

## Ressourcen organisationsübergreifend freigeben

Eine organisationsübergreifende Freigabe gewährt einer anderen Organisation Zugriff auf ausgewählte Ressourcen der aktuellen Organisation. Die Freigabe
ist explizit und nicht transitiv: Sie gilt nur für die ausgewählte Organisation und die ausgewählten Ressourcen. Sie lässt sich weder
vererben noch weitergeben.

1. Wählen Sie unter **Zugriffsfreigaben** die Option **Organisationsübergreifend freigeben** aus.
2. Wählen Sie die **Zielorganisation** aus.
3. Wählen Sie den Ressourcentyp und die Ressource aus: ein **Dashboard** oder einen **Stream**.
4. Wählen Sie die Berechtigungen aus: `dashboards.read` und `dashboards.edit` für ein Dashboard, `streams.read`
   und `streams.query` für einen Stream.
5. Legen Sie optional unter **Läuft ab am** einen Ablaufzeitpunkt fest und wählen Sie dann **Freigabe erstellen** aus.

Die Freigabe hat zunächst den Status **Annahme ausstehend**. Wählt ein Administrator der Zielorganisation
**Annehmen** im Bereich **Zugriffsfreigaben** der Zielorganisation aus, erhält die Freigabe den Status **Aktiv**. Beide Organisationen können die Freigabe über **Widerrufen**
beenden. Zum Erstellen, Annehmen und Widerrufen von Freigaben benötigen Sie `iam.cross_org.manage`.

## Berechtigungsreferenz

und Richtlinien können beliebige Organisationsberechtigungen kombinieren. Die Registerkarten eines Moduls zeigen die Seiten, die eine Rolle öffnen darf.
Das Modul öffnet die erste dieser Seiten. Für den Zugriff auf das Modul reicht daher die Berechtigung für eine einzige Seite.

## API für Rollen, Richtlinien und Zugriffszuweisungen

| Vorgang | Endpunkt | Berechtigung |
|---|---|---|
| Berechtigungskatalog auflisten | `GET /api/v1/iam/permissions` | `iam.roles.read` oder `iam.policies.read` |
| Rollen auflisten | `GET /api/v1/roles` | `iam.roles.read` |
| Benutzerdefinierte Rolle erstellen | `POST /api/v1/roles` | `iam.roles.manage` |
| Benutzerdefinierte Rolle aktualisieren | `PATCH /api/v1/roles/{id}` | `iam.roles.manage` |
| Nicht verwendete benutzerdefinierte Rolle löschen | `DELETE /api/v1/roles/{id}` | `iam.roles.manage` |
| Berechtigungsrichtlinien auflisten oder eine einzelne abrufen | `GET /api/v1/iam/policies`, `GET /api/v1/iam/policies/{id}` | `iam.roles.read` |
| Benutzerdefinierte Richtlinie erstellen | `POST /api/v1/iam/policies` | `iam.roles.manage` |
| Benutzerdefinierte Richtlinie aktualisieren | `PATCH /api/v1/iam/policies/{id}` | `iam.roles.manage` |
| Nicht verwendete benutzerdefinierte Richtlinie löschen | `DELETE /api/v1/iam/policies/{id}` | `iam.roles.manage` |
| Zugriffszuweisungen auflisten oder erstellen | `GET /api/v1/iam/role-bindings`, `POST /api/v1/iam/role-bindings` | `iam.policies.read`, `iam.policies.manage` |
| Zugriffszuweisung löschen | `DELETE /api/v1/iam/role-bindings/{id}` | `iam.policies.manage` |
| Organisationsübergreifende Freigaben auflisten oder erstellen | `GET /api/v1/iam/cross-org-grants`, `POST /api/v1/iam/cross-org-grants` | `iam.policies.read`, `iam.policies.manage` |
| Freigabe annehmen oder widerrufen | `POST /api/v1/iam/cross-org-grants/{id}/accept`, `POST /api/v1/iam/cross-org-grants/{id}/revoke` | `iam.policies.manage` |

Der Anfragebody einer Rolle enthält ihre eigenen `permissions` und die `policyIds` der zugeordneten Richtlinien. Die Antwort ergänzt
`effectivePermissions` mit allen Berechtigungen, die die Rolle gewährt. Der Anfragebody einer Richtlinie enthält `key` (nur beim Erstellen),
`name`, `description` und `document`. Die Antwort ergänzt `builtin`, die aufgelösten `permissions` und
`usage` mit den Rollen, denen die Richtlinie zugeordnet ist, und den aktiven Tokens, für die sie gilt. Bei einem ungültigen
Dokument gibt die API `400` zurück und nennt die Fehlerstelle, zum Beispiel
``Statement[0].Action[1]: no permission is called `alerts.rules.reed` ``. Ist die Richtlinie noch in Verwendung, gibt die API
beim Löschversuch `409` zurück.
