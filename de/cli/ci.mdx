Die Befehle auf dieser Seite rufen die MoleSignal-API auf und benötigen ein API-Token. Setzen Sie `MOLESIGNAL_URL` und
`MOLESIGNAL_TOKEN` in der Pipeline oder übergeben Sie `--url` und `--token`. Erstellen Sie das Token unter
**Identität und Zugriff → API-Token** mit einer Rolle, die über die beim jeweiligen Befehl genannte Berechtigung verfügt.

## Deployment melden

```bash
molesignal deploy --service checkout --version 2.4.0 --env production
```

Das Deployment erscheint auf der Zeitachse des Service in APM. APM vergleicht die bereitgestellte Version mit der
vorherigen Version. In CI stammen Commit, Repository, Pull Request, Autor und Link zum Lauf
aus der Umgebung von GitHub Actions, GitLab CI/CD, Jenkins, CircleCI, Buildkite,
Bitbucket Pipelines oder Azure Pipelines. Außerhalb von CI stammen Commit und Repository aus Git.
Die Rolle des Tokens benötigt `apm.deploy`.

Steht nach `--` ein Befehl, führt die CLI ihn zuerst aus. Je nach Ergebnis erfasst sie das Deployment als erfolgreich oder fehlgeschlagen und
beendet sich mit demselben Exit-Code wie der Befehl:

```bash
molesignal deploy --service checkout --version 2.4.0 --env production -- ./scripts/deploy.sh
```

| Option | Bedeutung |
|---|---|
| `--service <name>` | Name des Service, wie ihn seine Spans in `service.name` angeben. Pflichtangabe. |
| `--version <version>` | Bereitgestellte Version in `service.version`. Pflichtangabe für ein Deployment. |
| `--env <environment>` | Umgebung in `deployment.environment.name`. |
| `--namespace <namespace>` | `service.namespace` des Service. |
| `--kind <kind>` | `deployment` (Standard), `configuration` oder `feature_flag`. |
| `--status <status>` | `succeeded` (Standard), `failed` oder `rolled_back` auf `--version`. |
| `--commit`, `--repository`, `--pull-request`, `--author`, `--ci-url` | Überschreiben die Werte aus CI oder Git. |
| `--description <text>` | Erscheint beim Zeigen auf das Deployment. |
| `--time <time>` | Zeitpunkt des Deployments anstelle der aktuellen Zeit. |
| `--dry-run` | Zeigt die Daten an, die der Befehl erfassen würde, ohne sie zu speichern. |

Die Felder entsprechen denen unter [Deployments aus CI melden](/de/apm/deployments#deployments-aus-der-ci-melden).

## Source Maps hochladen

```bash
molesignal source-maps upload dist/assets --application checkout-web --service web-frontend --release "$VERSION"
```

Die CLI lädt jede `.map`-Datei in den Ordnern unter ihrem eigenen Namen hoch. Der Name muss dem Namen des bereitgestellten
Bundles mit der Endung `.map` entsprechen. Die CLI komprimiert die Dateien beim Upload mit gzip und verarbeitet standardmäßig vier gleichzeitig. Mit `--concurrency` ändern
Sie diese Anzahl. Gleichnamige Source Maps würden einander überschreiben. Daher lehnt der Befehl sie ab.
Die Werte für `--application`, `--service` und `--release` müssen den Angaben des RUM SDK entsprechen:
`applicationId`, `service` und `version`. Geben Sie für Flutter Web zusätzlich `--platform flutter` und die beim Build der App verwendete
`--debug-id` an. Die Rolle des Tokens benötigt `debug_artifacts.manage`.

`--dry-run` listet die Dateien auf, die der Befehl hochladen würde. `molesignal source-maps list` listet die hochgeladenen Source Maps auf,
und `molesignal source-maps delete <id>` löscht eine davon.

## Symbole für mobile Apps und nativen Code hochladen

```bash
molesignal symbols upload build/molesignal-symbols --application checkout-app --service checkout --release 2.4.0 --debug-id "$BUILD_ID"
```

Die CLI ordnet jede Datei anhand ihres Typs zu:

| Datei | Upload als |
|---|---|
| `app.android-arm64.symbols` aus `--split-debug-info` | Flutter-Symbole. Plattform und Architektur stammen aus dem Dateinamen. Geben Sie für `--debug-id` die beim Build der App verwendete `MOLESIGNAL_DEBUG_ID` an. |
| `mapping.txt` | Android-R8-Mapping. |
| Eine ELF-Bibliothek wie `libapp.so` | Native Android-Symbole. Die CLI liest Architektur und Build-ID aus der Datei. |
| Eine Apple-`.dSYM` | Ein Upload pro Architektur der Binärdatei. Die CLI liest die jeweilige UUID aus der Datei. |

`--debug-id`, `--platform` und `--arch` überschreiben die Angaben aus der Datei. Bei einer dSYM-Datei beschränkt `--arch` den Upload auf eine
Architektur. `--dry-run` listet alle Dateien mit den daraus gelesenen IDs auf. Mit `molesignal symbols list`
listen Sie Uploads auf, mit `molesignal symbols delete <id>` löschen Sie einen Upload. Die Rolle des Tokens benötigt
`debug_artifacts.manage`. Unter [Source Maps und Symbole für RUM](/de/rum/source-maps) steht, wie die CLI die Stack-Frames
zuordnet.

## Release prüfen

`molesignal synthetics run <check> --wait --yes` führt einen synthetischen Check an jedem seiner Standorte aus
und endet mit dem Exit-Code `1`, wenn ein Lauf fehlschlägt. `molesignal services compare <service> <baseline> <candidate>
--fail-on-regression` endet mit dem Exit-Code `1`, wenn die Kandidatenversion eine Regression aufweist. Siehe
[Incidents und Änderungen](/de/cli/changes#synthetische-checks-ausführen) und
[Metriken, Traces und Services](/de/cli/observe#zwei-versionen-vergleichen).

## Zeilen an einen Stream senden

`molesignal send` sendet jede Zeile der Standardeingabe an einen Log-Stream: Bei einem JSON-Objekt übernimmt der Befehl dessen Felder,
bei jeder anderen Zeile den Inhalt als `message`. Der Befehl sendet eingehende Logs fortlaufend in Batches und kann so neue Zeilen aus
einer Datei übertragen:

```bash
tail -f /var/log/app.log | molesignal send app_logs --field service=billing
```

`--field name=value` fügt jedem Log ein Feld hinzu, `--raw` sendet jede Zeile als Nachricht und
`--batch` legt fest, wie viele Logs eine Anfrage höchstens enthält. Der Standardwert ist `500`. Ist der Server ausgelastet, wiederholt der Befehl die Anfrage. Der
Befehl endet mit dem Exit-Code `1`, wenn MoleSignal Logs ablehnt. Die Rolle des Tokens benötigt `logs.write`, genau wie bei
einem Token für die Log-Aufnahme.

## Ausgabe eines Jobs speichern

`molesignal run` führt einen Befehl aus, zeigt dessen Ausgabe wie gewohnt an und sendet jede Zeile an einen Log-Stream.
Ein abschließender Log-Eintrag enthält den Exit-Code und die Laufzeit. Die CLI beendet sich mit demselben Exit-Code wie der Befehl:

```bash
molesignal run jobs --name nightly-backup -- ./backup.sh --full
```

Jeder Log-Eintrag enthält die Felder `message`, `output` (`stdout` oder `stderr`), `command`, `run_id` und
`host`. Der letzte Eintrag enthält zusätzlich `exit_code`, `duration_ms` und `level`. `--quiet` blendet die lokale Ausgabe aus,
und `--field` fügt ein Feld hinzu.

## GitHub Actions

Speichern Sie die Adresse und das Token als Repository-Secrets und fügen Sie dem Deployment-Job Schritte hinzu.
Mit `if: always()` meldet der Schritt auch ein fehlgeschlagenes Deployment:

```yaml
- name: Upload source maps
  run: npx -y @molesignal/cli source-maps upload dist/assets --application checkout-web --service web-frontend --release "${{ github.sha }}"
  env:
    MOLESIGNAL_URL: ${{ secrets.MOLESIGNAL_URL }}
    MOLESIGNAL_TOKEN: ${{ secrets.MOLESIGNAL_TOKEN }}

- name: Report the deployment
  if: always()
  run: npx -y @molesignal/cli deploy --service checkout --version "${{ github.sha }}" --env production --status "${{ job.status == 'success' && 'succeeded' || 'failed' }}"
  env:
    MOLESIGNAL_URL: ${{ secrets.MOLESIGNAL_URL }}
    MOLESIGNAL_TOKEN: ${{ secrets.MOLESIGNAL_TOKEN }}
```

## GitLab CI/CD

Fügen Sie `MOLESIGNAL_URL` und `MOLESIGNAL_TOKEN` als maskierte CI/CD-Variablen hinzu und führen Sie den Deployment-Befehl
über die CLI aus:

```yaml
deploy:
  stage: deploy
  environment: production
  script:
    - npx -y @molesignal/cli deploy --service checkout --version "$CI_COMMIT_SHORT_SHA" -- ./scripts/deploy.sh
```

Die Umgebung stammt aus `environment`. Commit, Merge Request und Job-Link stammen aus GitLab.
