Jede von Mole Agent geschriebene Antwort wird bewertet. Regeln bewerten sie sofort, ohne ein Modell: ob die Tools funktioniert haben, ob sie Belege zitiert, ob sich ihre Abfragen parsen lassen, ob sie im richtigen Format ausgegeben wurde und wie die Person, die sie angefordert hat, sie bewertet hat. Evaluatoren, die Sie einrichten, bewerten eine Stichprobe der Antworten mit einem Modell nach einem Bewertungsraster, das Sie erstellen. Antworten, die niedrig bewertet werden, die jemand als nicht hilfreich bewertet hat oder die zufällig ausgewählt werden, warten auf die Prüfung; die Antworten, die eine prüfende Person annimmt, bilden das Regressionsset. Bevor ein Organisations-Prompt zum Standard wird, beantwortet eine Prüfung einige dieser Fragen erneut mit der neuen Version und mit der aktuellen Version, und ein Evaluator bewertet beide.

Bewertungen reichen von 0 bis 100. Der Tab **Qualität** zeigt sie an, und jede Bewertung wird außerdem in den Stream `_agent_score_traces` geschrieben.

## Bevor Sie beginnen

- Der Tab **Qualität** benötigt `agent.quality.read`; die Rollen Owner und Admin haben diese Berechtigung standardmäßig. Sie können bereits jeden Team-Chat lesen; persönliche Chats fließen nur in die Gesamtsummen ein, und niemand liest sie dort.
- Ein Evaluator nutzt einen der Modellanbieter der Organisation. Siehe [Mole Agent](/de/agent#modellanbieter-einrichten). Ohne Evaluator werden alle Antworten weiterhin durch Regeln bewertet.

## Was bewertet wird

| Quelle | Was es ist |
|---|---|
| **Team-Chats** | Antworten in Team-Chats. |
| **Persönliche Chats** | Antworten in persönlichen Chats. Sie werden nur durch Regeln bewertet und fließen nur in die Gesamtsummen ein. |
| **Automatisierungen** | Die Antwort jedes Laufs einer Organisations- oder Team-Automatisierung. Siehe [Automatisierungen](/de/automations). Die Läufe einer persönlichen Automatisierung sind persönliche Chats. |
| **Ursachenanalysen zu Incidents** | Ursachenanalysen, die die Root-Cause-Analyse automatisch oder auf Anfrage erzeugt, sowie jede Ursachenanalyse, die jemand bewertet. |

Eine Antwort wird bewertet, wenn sie geschrieben wird, und erneut, wenn die Person, die sie angefordert hat, sie bewertet oder die Bewertung zurücknimmt.

## Regeln

Regeln betrachten, was die Antwort und ihr Lauf hinterlassen haben, und bewerten jedes davon mit 0 bis 100. Die Regelbewertung einer Antwort ist der Mittelwert derjenigen, die zutreffen.

| Regel | Bewertung | Gilt für |
|---|---|---|
| **Tool-Aufrufe** | Der Anteil der Tool-Aufrufe, die nicht fehlgeschlagen sind. | Antworten, die Tools aufgerufen haben. |
| **Belege** | Keine zitierten Belege ergeben 0, zitierte Belege, die kein erfolgreicher Tool-Aufruf stützt, 50, ein Beleg 75, zwei oder mehr 100. Für eine Ursachenanalyse zu einem Incident: Das Zitieren eines Labels, das ihr nicht übergeben wurde, ergibt 0; das Zitieren keines der Belege, die ihr übergeben wurden, ergibt 25; das Zitieren nur der Belege, die ihr übergeben wurden, ergibt 100. | Antworten im angeforderten Format, die Tools aufgerufen haben; Ursachenanalysen zu Incidents, denen Belege übergeben wurden oder die welche zitieren. |
| **Abfragen** | Der Anteil der SQL- und PromQL-Abfragen in den Tool-Aufrufen, die sich parsen lassen. | Antworten, deren Tools Abfragen ausgeführt haben. |
| **Formatieren** | 100, wenn die Antwort im Format vorliegt, das für Antworten gefordert wird. | Jede Chat-Antwort außer generierten Abfragen. |
| **Abschluss** | 100 für eine abgeschlossene Antwort, 50 für einen Automatisierungslauf, bei dem jemand eingreifen musste, 0 für eine fehlgeschlagene, gestoppte oder leere Antwort. | Jede Antwort. |
| **Nutzerbewertung** | 100 für **Hilfreich**, 0 für **Nicht hilfreich**. Bei einer Ursachenanalyse zählt eine Bewertung **Nicht hilfreich**. | Antworten, die jemand bewertet hat. |

## Evaluatoren

Ein Evaluator vergibt einer Antwort anhand seines Bewertungsrasters 1 bis 5 und begründet dies in ein bis zwei Sätzen; die Bewertung lautet 0, 25, 50, 75 oder 100. Er liest die Frage, was die Tools gefunden haben, und die Antwort; bei einer Ursachenanalyse die Fakten des Incidents und die Ursachenanalyse.

- Ein Evaluator bewertet den Prozentsatz neuer Antworten, den Sie festlegen; die Auswahl erfolgt anhand der Antwort, sodass ein erneutes Ziehen dieselben Antworten ergibt.
- Antworten, die als **Nicht hilfreich** bewertet wurden, werden immer bewertet, es sei denn, der Evaluator hat sie bereits bewertet.
- Eine Antwort, die der Evaluator unterhalb der Prüfschwelle bewertet, wird ein weiteres Mal bewertet, und der Mittelwert der beiden zählt.
- Ein Evaluator bewertet niemals persönliche Chats.
- Ein Evaluator schreibt seine Begründungen in der Oberflächensprache der Person, die ihn zuletzt gespeichert hat.
- Die Modellaufrufe von Evaluatoren zählen zum täglichen Token-Budget der Organisation, als **Qualitätsbewertung** in der Nutzung nach Quelle. Ist das Budget aufgebraucht, überspringen Evaluatoren neue Antworten.

Die Anweisungen, von denen jeder Evaluator ausgeht, sind der integrierte Prompt **Antwortbewertung** (Zweck `evaluation`); die Organisation kann ihn unter **Einstellungen → Prompt-Verwaltung** überschreiben. Unabhängig davon, was der Prompt vorgibt, gibt der Evaluator seine Bewertung in einem festen Format zurück.

Die Bewertung einer Antwort ist der Mittelwert der Bewertungen ihrer Evaluatoren, wenn ein Evaluator sie bewertet hat, andernfalls ihre Regelbewertung.

## Der Tab Qualität

Öffnen Sie **Mole Agent → Qualität**. **Übersicht** und **Antworten** betrachten die letzten 7, 30 oder 90 Tage und entweder eine Quelle oder alle.

| Ansicht | Was sie zeigt |
|---|---|
| **Übersicht** | Die bewerteten Antworten, der Mittelwert der Regeln und der Evaluatoren, die als hilfreich und als nicht hilfreich bewerteten Antworten und wie viele auf die Überprüfung warten. Darunter: die Bewertung pro Tag, jede Regel und die Antworten nach Quelle, Prompt-Version, Skill und Modell. |
| **Antworten** | Die bewerteten Antworten, neueste zuerst, mit **Nur niedrige Bewertungen**, um diejenigen unter dem Schwellenwert für die Überprüfung zu behalten. Eine Zeile öffnet die vollständige Frage und Antwort, jede Regel mit ihrem Befund, die Bewertung und Begründung jedes Evaluators und die Überprüfung der Antwort. **Chat öffnen** oder **Incident öffnen** führt dorthin, wo sie geschrieben wurde. |
| **Überprüfungen** | Die Antworten, die auf die Überprüfung warten, angenommen oder abgelehnt wurden. |
| **Datenlücken** | Was laut den Tool-Aufrufen der Antworten in den Daten fehlt. Siehe [Datenlücken](#datenlücken). |
| **Übungen** | Gelöste Incidents, die erneut untersucht und anhand ihrer bekannten Grundursache bewertet werden. Siehe [Übungen](#übungen). |
| **Evaluatoren** | Die Evaluatoren und die Einstellungen. |

### Antworten überprüfen

Eine Antwort wartet auf die Überprüfung, wenn:

| Ursache | Wann |
|---|---|
| **Niedrige Bewertung** | Die Bewertung eines Evaluators liegt auch nach der zweiten Bewertung noch unter dem Schwellenwert für die Überprüfung, oder bei einer Antwort, die kein Evaluator bewertet, liegt ihre Regelbewertung darunter. |
| **Als nicht hilfreich bewertet** | Die fragende Person hat sie als **Nicht hilfreich** bewertet. |
| **Zufällig ausgewählt** | Sie wurde anhand des Prozentsatzes der **Stichprobenprüfung** ausgewählt, um zu sehen, ob den Bewertungen vertraut werden kann. |

Eine Antwort kommt nur einmal zur Überprüfung. Öffnen Sie sie, schreiben Sie in **Notiz**, was falsch ist und was eine gute Antwort richtig macht, und wählen Sie:

- **Annehmen**: Die Antwort ist falsch. Sie wird in das Regressionsset aufgenommen, und ihre Notiz geht an den Evaluator, wenn eine Prompt-Prüfung die Frage erneut beantwortet.
- **Ablehnen**: Die Antwort ist in Ordnung.

### Evaluatoren und Einstellungen

Unter **Evaluatoren** öffnet **Neuer Evaluator** das Formular:

| Feld | Beschreibung |
|---|---|
| **Name** | Eindeutig in der Organisation. |
| **Bewertungsschema** | Was eine gute Antwort leistet und was gegen sie zählt, bis zu 4000 Zeichen. Ein Bewertungsschema als Ausgangspunkt ist vorausgefüllt. |
| **Antworten** | Team-Chats, Automatisierungen, Incident-RCAs. |
| **Stichprobe** | Der Prozentsatz neuer Antworten, die er bewertet, 0 bis 100. |
| **Modellanbieter** und **Modell** | Leer verwendet den ersten verfügbaren Anbieter der Organisation und dessen Standardmodell. |
| **Temperatur** | 0 bis 1; 0 hält die Bewertungen stabil. |
| **Aktiv** | Ein Evaluator, der ausgeschaltet ist, bewertet nichts. |

Eine Organisation hat höchstens 10 Evaluatoren. Beim Löschen eines Evaluators bleiben die von ihm vergebenen Bewertungen erhalten.

Die Einstellungen unterhalb der Evaluatoren:

| Einstellung | Standard | Beschreibung |
|---|---|---|
| **Schwellenwert für die Überprüfung** | 60 | Antworten, die darunter bewertet werden, warten auf die Überprüfung. |
| **Stichprobenprüfung** | 0 | Der Prozentsatz der anderen Antworten, die für die Überprüfung ausgewählt werden. |
| **Bevor ein Prompt zum Standard wird** | Prüfen und erneut fragen, wenn schlechter | Siehe unten. |

### Datenlücken

Wenn eine Antwort durch Regeln bewertet wird, werden auch ihre Tool-Aufrufe daraufhin gelesen, was sie über die Daten aussagen, mit denen Mole Agent arbeiten musste. Das ändert keine Bewertung: Eine Lücke weist auf die Daten hin, nicht auf die Antwort. **Datenlücken** fasst sie über die letzten 7, 30 oder 90 Tage zusammen.

| Art | Erkannt, wenn | Wodurch sie geschlossen wird |
|---|---|---|
| **Wo die Daten liegen** | Derselbe Stream wurde 3-mal oder öfter abgefragt und die meisten Abfragen kamen leer zurück oder schlugen fehl, oder die Struktur wurde 3-mal oder öfter nachgeschlagen (Stream-Schemas, Stream-Listen, Metriknamen und Labels). | Schreiben Sie auf, wo die Daten jedes Service liegen und wie sie gefiltert werden: in den Datenquellen des Service-Katalogs oder in `MOLE.md` der Wissensbasis. |
| **Ein Name pro Service** | Ein Service hatte Daten in Metriken oder APM, aber eine Log- oder Trace-Abfrage, die denselben Service nannte, fand nichts, und keine andere Abfrage dieses Streams fand ihn. | Geben Sie einem Service in jedem Signal denselben Namen (`service.name`), oder listen Sie seine anderen Namen als Aliase im Service-Katalog auf. |
| **Daten zusammenfassen** | Rohlogs oder Rohzeitreihen wurden 2-mal oder öfter abgerufen, jeweils mit vielen Zeilen, ohne **Log-Muster analysieren** oder **Metriktrend analysieren**. | Prüfen Sie, dass die Toolsets der Agent-Profile der Organisation diese Tools nicht auslassen. |

Die Ansicht listet jede Lücke auf, die immer wieder gefunden wurde, gruppiert nach Stream und Service, mit der Anzahl der Antworten, die sie gefunden haben, und wann sie zuletzt gesehen wurde. Eine darunter aufgeführte Antwort öffnet sich mit ihren Bewertungen. Persönliche Chats zählen nur in den Summen: Was in ihnen abgefragt wurde, wird nicht aufgeführt.

### Übungen

Eine Übung ist ein gelöster Incident, den Mole Agent erneut untersucht, als würde er gerade geschehen, und anhand der nach dem Incident ermittelten Grundursache bewertet. Alle Übungen erneut auszuführen, nachdem das Modell, ein Prompt oder die Tools geändert wurden, zeigt, ob die Untersuchungen besser geworden sind.

**Neue Übung** bietet die in den letzten 180 Tagen gelösten Incidents an, deren Postmortem eine Grundursache angibt (der Abschnitt unter **Grundursache**). Die Grundursache des Postmortems ist die Referenz, sofern nicht stattdessen eine geschrieben wird. **Anderer Incident** nimmt eine Incident-ID und eine von Hand geschriebene Grundursache. Jeder Incident hat eine Übung, und eine Organisation behält höchstens 100.

Ein Lauf einer Übung:

- Läuft als die Person, die ihn startet und den Incident lesen können muss, unbeaufsichtigt und schreibgeschützt, bis zu 10 Minuten.
- Erhält die Fakten, mit denen der Incident ausgelöst wurde (seine Zusammenfassung, Schweregrad, Services, Labels und die Abfrage, die ihn ausgelöst hat), sowie den Untersuchungsleitfaden der Alarmregel und betrachtet den Zeitraum von einer Stunde vor Beginn des Incidents bis eine halbe Stunde danach.
- Kann nicht lesen, was später über den Incident herausgefunden und unternommen wurde: seine Notizen, Timeline, RCA, das Postmortem, Tickets, Genehmigungen und ähnliche Incidents.
- Ist ein Chat, den die Chat-Liste nicht anzeigt. **Untersuchung öffnen** öffnet ihn aus dem Lauf heraus, schreibgeschützt.

Sobald die Untersuchung endet, vergleicht ein Modell ihre Grundursache mit der Referenz und bewertet sie von 1 bis 5, umgerechnet auf 0 bis 100, mit einer Begründung in der Oberflächensprache der Person, die den Lauf gestartet hat. Das Modell ist das des ersten aktivierten Evaluators oder andernfalls das des ersten Modellanbieters der Organisation; seine Aufrufe werden als **Qualitätsbewertung** auf das tägliche Token-Budget angerechnet. Ein Lauf, der fehlgeschlagen ist, gestoppt wurde oder keine Antwort geschrieben hat, hat keine Bewertung und nennt den Grund.

**Ausführen** startet eine Übung; **Alle erneut ausführen** startet jede Übung, für die kein Lauf läuft, höchstens 50 gleichzeitig. Das Erstellen, Ausführen und Löschen von Übungen erfordert `agent.quality.manage`.

## Prompt vor dem Festlegen als Standard prüfen

Wenn für einen Organisations-Prompt für Chats (**Systemanweisung**) oder für Incident-RCAs (**Ursachenanalyse**) **Als Standard festlegen** ausgewählt wird, entscheidet die Einstellung der Organisation, was passiert:

| Einstellung | Wenn der Prompt nicht geprüft wurde oder die Prüfung ihn als schlechter eingestuft hat |
|---|---|
| **Prüfen und bei schlechterem Ergebnis nachfragen** | Der Dialog bietet **Prüfung starten** und **Trotzdem als Standard festlegen** an. |
| **Prüfen und bei schlechterem Ergebnis blockieren** | Nur ein Prompt, den eine Prüfung als nicht schlechter eingestuft hat, kann festgelegt werden. |
| **Nicht prüfen** | Der Prompt wird sofort festgelegt. |

Eine Prüfung umfasst bis zu 8 Antworten: zuerst das Regressionsset, dann die Antworten, die der erste Evaluator, der diese Antworten bewertet, zuletzt bewertet hat. Jede Antwort wird erneut zweimal beantwortet, einmal mit dem aktuellen Standard und einmal mit der neuen Version, durch dasselbe Modell und ohne die Tools erneut auszuführen: Das Modell erhält die Frage und was die Tools damals ermittelt haben. Bei einer RCA erstellen beide Versionen die Analyse anhand der Fakten des Incidents. Der Evaluator bewertet dann jedes Paar. Die neue Version ist **Schlechter**, wenn ihr Mittelwert mehr als 5 unter dem des aktuellen Standards liegt, **Besser**, wenn er mehr als 5 darüber liegt, andernfalls **Nicht schlechter**. Wenn weniger als 3 Antworten verglichen werden konnten, kann die Prüfung keine Aussage treffen und verhindert das Festlegen des Prompts nicht.

Der Dialog zeigt den Fortschritt und anschließend das Ergebnis für jede Antwort. Eine Prüfung vergleicht eine Version des Prompts mit einem Standard: Nachdem der Prompt bearbeitet oder ein anderer Standard festgelegt wurde, muss sie erneut ausgeführt werden. Die Modellaufrufe einer Prüfung zählen als **Qualitätsbewertung**.

Prompts für andere Zwecke werden ohne Prüfung zum Standard. Auch das Bearbeiten des Prompts, der bereits der Standard ist, wird nicht geprüft; um eine Änderung zu prüfen, speichern Sie sie als neuen Prompt und legen Sie diesen als Standard fest.

## Bewertungen in einem Stream

Jede Bewertung ist auch eine Zeile des internen Streams `_agent_score_traces`, den Sie in **Logs** abfragen können:

| Feld | Beschreibung |
|---|---|
| `target_kind`, `target_id` | `chat_answer` mit der Nachrichten-ID oder `incident_rca` mit der Incident-ID. |
| `source` | `personal_chat`, `team_chat`, `automation` oder `incident_rca`. |
| `scorer`, `scorer_kind` | `rules` oder die ID des Evaluators mit `evaluator`. |
| `score`, `samples` | Von 0 bis 1 bzw. die Anzahl der Bewertungen, aus denen der Mittelwert gebildet wurde. |
| `tool_success`, `evidence`, `query_validity`, `answer_format`, `completion`, `feedback` | Die Regeln, von 0 bis 1, sofern sie zutreffen. |
| `reason`, `evaluator_model` | Begründung und Modell des Evaluators. |
| `chat_id`, `team_id`, `automation_id`, `user_id`, `prompt_template_id`, `prompt_version`, `prompt_key`, `provider_id`, `model`, `skill`, `skill_version` | Woher die Antwort stammt und was sie verwendet hat. |

Um über einen Qualitätsabfall benachrichtigt zu werden, erstellen Sie eine [Anomalie-Warnungsregel](/de/alerting) über den Stream, zum Beispiel auf den Mittelwert der Evaluatoren:

```sql
SELECT avg(score) AS value FROM "_agent_score_traces" WHERE scorer_kind = 'evaluator'
```
