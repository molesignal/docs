Streams und Felder lassen sich nur schwer ändern, sobald Daten, Dashboards und Alarmregeln von ihnen abhängen. Ein Feldtyp ist nach dem Schreiben festgelegt, ein verschlüsseltes Flag kann nicht nachträglich hinzugefügt werden, und ein umbenanntes Feld bricht jede gespeicherte Abfrage. Investieren Sie eine Stunde in das Design, bevor Sie die erste stark ausgelastete Quelle verbinden.

## Teilen Sie Streams nach ihren Unterschieden auf

Erstellen Sie nur dann einen separaten Stream, wenn die Daten einen anderen Vertrag benötigen: eine andere Aufbewahrungsdauer, eine andere Zugriffsregel, ein anderes Schema oder ein separates Abfragebereichslimit. Andernfalls halten Sie Daten zusammen und unterscheiden sie über Felder.

| Situation | Empfohlen | Kompromiss |
|---|---|---|
| Debug-Logs 3 Tage aufbewahrt, Audit-Logs ein Jahr | Zwei `logs`-Streams mit eigener Aufbewahrungsdauer. | Abfragen, die beide benötigen, verwenden zwei Streams. |
| Viele Dienste mit derselben Log-Struktur | Ein Stream, mit `service.name` bei jedem Ereignis. | Aufbewahrungsdauer und Zugriff können nicht pro Dienst abweichen. |
| Ein roher Firehose, den eine Pipeline in Streams sortiert | Ein Quell-Stream mit deaktiviertem **Abfragbar** und eine Routing-Pipeline. | Die rohen Ereignisse werden bis zum Ende ihrer Aufbewahrungsdauer behalten, halten Sie diese daher kurz. |
| Jeder Prometheus-Server | Ein `metrics`-Stream pro Quelle. | Eine Abfrage über mehrere Quellen nennt mehrere Streams. |
| Ein Stream pro Pod, Version oder Kunde | Vermeiden. Verwenden Sie stattdessen Felder. | Viele kleine Streams vervielfachen Dateien und brechen Dashboards bei jeder Änderung. |

MoleSignal erstellt einen Stream beim ersten Schreiben, sodass ein Tippfehler in einem Sender stillschweigend einen neuen Stream erzeugt. Prüfen Sie nach dem Verbinden jeder Quelle die [Stream-Liste](/de/streams#die-stream-liste) und erstellen Sie die wichtigen Streams im Voraus mit ihrer Aufbewahrungsdauer und ihren verschlüsselten Feldern.

## Einigen Sie sich auf Feldnamen, bevor Sie senden

Verwenden Sie die OpenTelemetry-Namen, wo immer sie existieren, und denselben Namen für dieselbe Sache in jedem Signal. Signalübergreifende Sprünge und APM hängen davon ab.

| Feld | Inhalt | Warum |
|---|---|---|
| `service.name` | Der Dienst, derselbe in Logs, Traces und Metriken. | Verknüpft jedes Signal mit einem Dienst. |
| `deployment.environment.name` | `production`, `staging` und so weiter. | Filtert jede Seite nach Umgebung. |
| `service.version` | Die veröffentlichte Version. | Treibt den Deployment-Vergleich in APM an. |
| `trace_id`, `span_id` | In jeder Logzeile gesetzt, die innerhalb einer Anfrage geschrieben wird. | Macht aus einer Logzeile einen Sprung zu ihrem Trace. |
| `level` | Eine Schreibweise, etwa kleingeschriebenes `error`, `warn`, `info`. | Das Log-Histogramm zählt Stufen aus seinem Index. |
| `host.name`, `k8s.pod.name` | Wo das Ereignis stattgefunden hat. | Grenzt ein Problem auf eine Maschine ein. |

Halten Sie den Typ eines Felds bei allen Sendern gleich: Ein Feld, das von einem Dienst als Zahl und von einem anderen als Text ankommt, wird mit `type mismatch on field` abgelehnt. Normalisieren Sie solche Felder in einer Pipeline mit **Datentyp umwandeln**, bevor sie gespeichert werden. Ganzzahlen und Zahlen mit einem Bruchteil können sich ein Feld teilen: Es wird zu `float64`. Verwenden Sie niemals einen vorhandenen Feldnamen für eine neue Bedeutung neu; fügen Sie stattdessen ein neues Feld hinzu.

## Indizieren Sie, was gefiltert wird

Der [Indextyp](/de/streams#schema-und-felder) entscheidet, wie schnell ein Filter ist. Neue Felder erhalten keinen, außer einigen bekannten Namen. Überprüfen Sie die Felder, nach denen Dashboards und Alarme filtern:

- **Exakte Übereinstimmung** für Bezeichner, die als Ganzes verglichen werden: `trace_id`, `user_id`, `order_id`, `service.name`.
- **Volltextsuche** für Fließtext wie `message`, der nach Wörtern durchsucht wird.
- **Skip-Index** für Zahlen und Zeiten, die mit `<` und `>` verglichen werden, etwa `duration_ms`.
- Nichts für Felder, die nur angezeigt werden.

Eine Indexänderung gilt für neue Daten; ältere Dateien erhalten sie, wenn der Compactor sie zusammenführt. Ändern Sie sie unter **Streams → Felder und Indizes** und dann **Speichern und anwenden**.

## Halten Sie Kardinalität aus Labels heraus

Ein Metrik-Label mit einem unbegrenzten Wert, etwa einer Benutzer-ID, einer Anfrage-ID oder einer vollständigen URL, erzeugt für jeden Wert eine neue Serie. Die [Kardinalitätslimits](/de/settings/platform#metrikkardinalität) verweigern dann neue Serien für die gesamte Organisation. Legen Sie solche Werte in Logs oder Span-Attributen ab, wo sie pro Wert nichts kosten, und beschränken Sie Metrik-Labels auf begrenzte Mengen wie Dienst, Routenvorlage, Methode und Statusklasse.

Referenzdaten, die sonst in jedes Ereignis kopiert würden, etwa das Team eines Dienstes oder der Plan eines Kunden, gehören in eine [Extend-Tabelle](/de/extend-tables): Eine Pipeline schlägt sie während der Verarbeitung nach.

## Schützen Sie sensible Werte von Anfang an

| Bedarf | Werkzeug | Wann es greift |
|---|---|---|
| Einen Wert niemals speichern, etwa eine Kartennummer | Ein [Regex-Muster](/de/settings/data-security#regex-muster) mit **Bei der Erfassung schwärzen** oder ein Pipeline-Schritt, der das Feld entfernt. | Bei der Erfassung, dauerhaft. |
| Einen Wert speichern, aber nur für wenige Leser | Ein verschlüsseltes Feld, das beim Erstellen des Streams deklariert und mit `decrypt()` gelesen wird. | Ab der Erstellung des Streams. |
| Einen Wert vor den meisten Abfrageergebnissen verbergen | [Feldmaskierung](/de/settings/data-security#feldmaskierung). | Zur Abfragezeit, im Ergebnis. |

Entfernen Sie einen Wert bevorzugt im Sender oder im Collector. Ein Wert, der die Quelle nie verlässt, kann nicht aus MoleSignal gelangen.

## Abnahmekriterien

- Jeder Stream hat einen Verantwortlichen, einen Grund zu existieren und eine bewusst festgelegte Aufbewahrungsdauer.
- Eine bekannte Anfrage lässt sich mit einem Klick von ihrer Logzeile zu ihrem Trace verfolgen.
- Felder, nach denen Dashboards und Regeln filtern, haben einen passenden Index.
- Kein Metrik-Label trägt einen unbegrenzten Wert, und **Kardinalität** unter Metriken zeigt stabile Serienanzahlen.
- Testereignisse mit sensiblen Markern kommen wie geplant geschwärzt, maskiert oder verschlüsselt an.
