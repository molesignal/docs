Zugriffsrechte wachsen mit jeder Ausnahme: Heute ist eine zusätzliche Berechtigung nötig, ein externer Auftrag erfordert Zugriff auf ein Dashboard, ein
Skript braucht ein Token. Ohne Plan ist nach einem Jahr unklar, wer einen Stream löschen kann oder welches Token
noch Daten schreibt. Legen Sie das Zugriffsmodell einmal fest und ordnen Sie Ausnahmen darin ein.

## Aufgaben Rollen zuordnen

Gehen Sie von den Aufgaben aus und wählen Sie die Rolle mit den geringsten dafür nötigen Berechtigungen. Welche Berechtigungen die einzelnen Rollen enthalten, steht in der
[Berechtigungsübersicht](/de/identity/roles#berechtigungsreferenz).

| Aufgabe | Rolle | Hinweis |
|---|---|---|
| Dashboards, Logs und Incidents ansehen | **Betrachter** | Die Standardrolle für die meisten Konten. Die Rolle erlaubt auch Chats mit Mole Agent. |
| Dashboards, Alarmregeln und Pipelines erstellen; auf Bereitschaftsalarme reagieren | **Bearbeiter** | Die Rolle erlaubt das Bestätigen und Stummschalten von Incidents, aber keine Änderungen an Mitgliedern, Tokens oder Einstellungen. |
| Den Arbeitsbereich verwalten: Mitglieder, Rollen, Tokens, Einstellungen, synthetische Prüfungen und Statusseiten | **Verwaltung** | Vergeben Sie diese Rolle nur an wenige Personen pro Arbeitsbereich. |
| Die Instanz verantworten | **Verantwortlich** | Die Rolle gewährt auch Zugriff auf die Plattformorganisation `_sys`. Vergeben Sie diese Rolle an zwei oder drei Personen, nicht mehr. |
| Aufgaben, für die keine integrierte Rolle passt, etwa die Alarmverwaltung oder die Bearbeitung mit zusätzlicher Zuständigkeit für synthetische Prüfungen | Eine [benutzerdefinierte Rolle](/de/identity/roles#rollen) | Weisen Sie die am besten passende **Berechtigungsrichtlinie** zu und aktivieren Sie die fehlenden Berechtigungen. |

Weisen Sie eine Rolle per
[Zugriffszuweisung](/de/identity/roles#zugriffsfreigaben) einem [Team](/de/identity/teams#teams) statt einzelnen Personen zu. Der Zugriff richtet sich dann nach der
Teammitgliedschaft.

## Anmeldung per Single Sign-on ermöglichen

1. Verbinden Sie den Identitätsanbieter des Unternehmens unter
   [Identität und Zugriff → SSO-Anbieter](/de/identity/sso) und ordnen Sie dessen Gruppen über
   **Externe Gruppe → Rolle** den Rollen zu. Bei jeder Anmeldung richten sich die Rollen nach den Gruppen im Verzeichnis.
2. Legen Sie **Betrachter** als **Standardrolle** für Konten ohne passende Gruppenzuordnung fest.
3. Fügen Sie die [E-Mail-Domains](/de/identity/sso#e-mail-domains) des Unternehmens hinzu. Einladungen und Single Sign-on
   akzeptieren dann nur Adressen aus diesen Domains.
4. Deaktivieren Sie den [eigenständigen Beitritt](/de/settings/organization#registrierung-und-zugriff) oder lassen Sie ihn mit der Option
   **Admin-Genehmigung erforderlich** zu.

Das unter `[auth].root_email` konfigurierte Root-Konto verwaltet die Plattform und verwendet zur Anmeldung ein
Passwort. Bewahren Sie das Passwort in einem Passworttresor auf und nutzen Sie das Konto nur, wenn Single Sign-on nicht verfügbar ist.

## Zeitlich begrenzten Zugriff auf eine Ressource gewähren

Manchmal ist der Bedarf eng begrenzt und vorübergehend: Für einen externen Auftrag reicht der Lesezugriff auf ein Dashboard, für eine Analyse der Zugriff auf einen
Stream. Erstellen Sie eine [Zugriffszuweisung](/de/identity/roles#zugriffsfreigaben) für diese Ressource und setzen Sie unter
**Läuft ab am** ein Ablaufdatum, statt eine Rolle für den gesamten Arbeitsbereich zu vergeben. Eine Einschränkung unter **Umgebung**, etwa auf
`staging`, begrenzt den Zugriff weiter auf Anfragen aus dieser Umgebung.

Für Mitglieder einer anderen Organisation gewährt eine
[organisationsübergreifende Freigabe](/de/identity/roles#ressourcen-organisationsübergreifend-freigeben) Zugriff auf
ausgewählte Dashboards oder Streams, sobald die Verwaltung der anderen Organisation die Freigabe annimmt. Die Freigabe gilt nur für
die ausgewählten Ressourcen und die ausgewählte Organisation. Die empfangende Organisation kann die Freigabe nicht weitergeben.

## Zuständigkeiten über Teams regeln

Teams bündeln mehr als nur Mitglieder: [Bereitschaftspläne](/de/alerting/on-call) und Eskalationsschritte,
[Ausweichrouten](/de/notification-channels#fallback-routen-konfigurieren) sowie Team-Chats,
Wissen, Skills und MCP-Server von [Mole Agent](/de/agent#ressourcen-für-organisationen-teams-und-einzelne-personen)
sind Teams zugeordnet. Erstellen Sie ein Team pro Gruppe, die Dienste betreut und auf Bereitschaftsalarme reagiert. Aktualisieren Sie die
Mitgliedschaften bei personellen Wechseln.

## Programmen eine eigene Identität geben

| Programm | Zugangsdaten |
|---|---|
| Collector oder Agent, der nur Daten sendet | Das Standard-Ingest-Token mit reinen Schreibrechten. |
| Code im Browser oder in einer mobilen App | Das RUM-Client-Token der Anwendung, das für Endnutzende sichtbar ist. |
| CI, die Deployments meldet | Das Standard-Ingest-Token, das auch das Melden von Deployments erlaubt. |
| Automatisierung, die Daten liest oder Ressourcen ändert | Ein [Dienstkonto](/de/identity/tokens#dienstkonten) mit einer benutzerdefinierten Rolle und möglichst wenigen Berechtigungen. |
| Manuell ausgeführte Skripte oder manuell genutzte MCP-Clients | Ein persönliches API-Token mit Ablaufdatum. |

Verwenden Sie pro Integration ein Dienstkonto. Legen Sie eine Integration still, deaktivieren Sie das zugehörige Dienstkonto. Damit verlieren alle
zugehörigen Tokens ihre Gültigkeit. Legen Sie für jedes manuell erstellte Token ein Ablaufdatum fest und überlassen Sie keinem
Programm eine Anmeldesitzung.

## Zugriff regelmäßig prüfen

Prüfen Sie den Zugriff jedes Quartal und bei Austritten:

- Deaktivieren Sie unter [Benutzer](/de/identity/members#benutzer) die Konten ausgeschiedener Mitglieder und prüfen Sie anhand von **Zuletzt aktiv**,
  welche Konten nicht mehr in Gebrauch sind.
- Widerrufen Sie unter [API-Tokens](/de/identity/tokens#tokens-der-organisation) Tokens, die zuletzt nicht genutzt wurden oder
  ausgeschiedenen Mitgliedern gehören.
- Entfernen Sie unter [Zugriffszuweisungen](/de/identity/roles#zugriffsfreigaben) abgelaufene Zugriffszuweisungen.
- Prüfen Sie unter [Audit](/de/settings/data-security#audit) Änderungen an Rollen, Zugriffszuweisungen, Tokens und Einstellungen.
- Prüfen Sie die [Freigaberichtlinie](/de/settings/organization#freigaben-und-öffentlicher-zugriff) und die bestehenden öffentlichen
  Links.

Legen Sie die [Aufbewahrungsdauer für Audit-Protokolle](/de/settings/platform#aufbewahrung-von-audit-einträgen) gemäß den Compliance-Vorgaben fest.

## Abnahmekriterien

- Die meisten Konten haben die Rolle **Betrachter**. Jede Vergabe von **Verwaltung** und **Verantwortlich** erfolgt bewusst.
- Die Anmeldung erfolgt per SSO. Die Rollen richten sich nach den Gruppen im Verzeichnis.
- Jedes Programm nutzt ein Dienstkonto oder ein Ingest-Token, nie eine persönliche Anmeldesitzung.
- Kein API-Token überschreitet die zulässige Gültigkeitsdauer. Nicht genutzte Tokens sind widerrufen.
- Für jede Quartalsprüfung sind ein Datum, eine zuständige Person und ein Eintrag im Audit-Protokoll vorhanden.
