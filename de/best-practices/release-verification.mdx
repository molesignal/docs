Die meisten Incidents beginnen mit einer Änderung. Ein in den Daten markiertes Release lässt sich innerhalb weniger Minuten mit der
Vorgängerversion vergleichen. Ohne Markierung fällt das Release erst nach einer Stunde
Rätselraten auf. Erfassen Sie jedes Release, vergleichen Sie es während des Rollouts und legen Sie vorab fest, wann
ein Rollback nötig ist.

## Jedes Release sichtbar machen

| Schritt | Vorgehen | Ergebnis |
|---|---|---|
| Jeden Span mit einer Version versehen | Setzen Sie `service.version` in der OpenTelemetry-Ressource jedes Dienstes. | Versionen in der [Deployment-Zeitleiste](/de/apm/deployments#die-deployment-zeitleiste) und Bewertungen pro Version, auch ohne CI-Meldung. |
| Deployment aus der CI melden | Senden Sie `POST /api/v1/apm/deployments` mit Dienst, Version, Umgebung, Commit und CI-Lauf. Verwenden Sie das Standard-Token für die Datenerfassung. Siehe [Deployments aus der CI melden](/de/apm/deployments#deployments-aus-der-ci-melden). | Commit, Autor und CI-Lauf stehen neben der Version. Auch fehlgeschlagene oder zurückgerollte Deployments sind sichtbar. |
| Konfigurationsänderungen und Feature-Flags melden | Verwenden Sie denselben Endpunkt und setzen Sie `kind` auf `configuration` oder `feature_flag`. | Änderungen außerhalb von Releases erscheinen neben den APM-Befunden. |
| Frontend versionieren | Setzen Sie `version` im RUM-SDK und laden Sie die Source Maps oder Symbole aus demselben CI-Job hoch. Siehe [Source Maps und Symbole](/de/rum/source-maps). | Lesbare Stacktraces und RUM-Probleme, bei denen die Version steht, in der sie erneut aufgetreten sind. |

Verwenden Sie überall dieselbe Versionszeichenfolge: im Image-Tag, in `service.version`, in der Deployment-Meldung
und in der RUM-Version.

## Ausgangswerte vor dem Release erfassen

Halten Sie vor dem Rollout die aktuellen Werte des Dienstes fest: die Fehlerrate und die P95-Latenz der wichtigsten Endpunkte, die
Burn Rate der [SLOs](/de/apm#service-level-ziele) und die offenen RUM-Probleme. Starten Sie die
[synthetischen Checks](/de/synthetics) für die kritischen Abläufe mit **Jetzt ausführen**. So verwechseln Sie einen Fehler nach dem
Release nicht mit einem bereits bestehenden Fehler.

Halten Sie die Rollback-Kriterien schriftlich fest. Beispiele: Bei den Fehlern lautet die Bewertung **Erneut aufgetreten**, ein kritischer
synthetischer Check schlägt zweimal fehl oder der Alarm für eine hohe Burn Rate löst aus.

## Versionen während des Rollouts vergleichen

- Wenn zwei Versionen gleichzeitig laufen, vergleicht die Karte **Canaries** im Abschnitt
  [Deployments](/de/apm/deployments#canaries) ihren jeweiligen Anteil an den bearbeiteten Anfragen,
  ihre Fehler und ihre Latenz. Die Karte zeigt auch die Bewertung der neuen Version.
- Jede Version erhält im Vergleich zur Vorgängerversion eine Bewertung: **Erneut aufgetreten**, **Verbessert**, **Keine Änderung**
  oder **Zu wenige Anfragen**. Für den Vergleich sind standardmäßig 1.000 Anfragen nötig. Lassen Sie das Canary-Deployment so lange laufen,
  bis genügend Anfragen vorliegen.
- Wählen Sie eine Bewertung aus, um **Zwei Versionen vergleichen** zu öffnen. Die Ansicht listet langsamere Endpunkte und
  häufiger auftretende Fehler auf.
- Filtern Sie in RUM den Explorer und die Fehlerprobleme nach der neuen Version. Achten Sie auf Probleme mit der Markierung
  **Erneut aufgetreten**: Diese Probleme waren bereits behoben und traten in einer neueren Version wieder auf.

## Release automatisch überwachen

Starten Sie aus dem CI-Job eine [Automatisierung](/de/automations#automatisierung-aus-ci/cd-starten) von Mole Agent für die erste
Prüfung. Der Deployment-Schritt ruft den Trigger mit einer Beschreibung der Änderung auf. Mole Agent folgt den
Anweisungen der Automatisierung, vergleicht beispielsweise die neue Version mit der alten und meldet das Ergebnis in einem
Chat. Überlassen Sie die Entscheidung einer verantwortlichen Person.

## Entscheiden und dokumentieren

Führen Sie ein Rollback durch, sobald ein Kriterium erfüllt ist. Warten Sie nicht auf Gewissheit. Melden Sie das Rollback aus der CI und setzen Sie
`status` auf `rolled_back`. So erscheint das Rollback in der Zeitleiste und spätere Vergleiche nutzen die richtigen Ausgangswerte.

Wenn das Release bestehen bleibt, prüfen Sie am folgenden Tag die SLOs. Schleichende Regressionen wie ein Speicherleck oder
eine wachsende Warteschlange zeigen sich oft erst Stunden später.

## Akzeptanzkriterien

- Jeder Dienst sendet `service.version` und jedes Produktions-Deployment erscheint mit dem zugehörigen Commit in der
  Deployment-Zeitleiste.
- Bei jedem Frontend-Release lädt der CI-Job Source Maps oder Symbole für die gemeldete Version hoch.
- Vor dem Rollout liegen die Rollback-Kriterien schriftlich vor.
- Jedes Release erhält eine Bewertung oder läuft als Canary-Deployment, bis genügend Anfragen vorliegen.
