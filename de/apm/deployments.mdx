Der Abschnitt **Deployments** einer Service-Seite stellt zwei Quellen nebeneinander: die Deployments, die
Pipelines melden, und die Versionen, die die Spans des Services in `service.version` tragen. Eine Version,
die keine Pipeline gemeldet hat, erscheint trotzdem – allein anhand der Spans.

## Die Deployment-Timeline

Die Timeline listet auf, was mit dem Service im Zeitraum passiert ist, das Neueste zuerst:

| Ereignis | Wann |
|---|---|
| **Bereitgestellt** | Eine Pipeline hat ein erfolgreiches Deployment gemeldet. |
| **Fehlgeschlagen** | Eine Pipeline hat ein fehlgeschlagenes Deployment gemeldet. Ein fehlgeschlagenes Deployment ändert die laufende Version nicht. |
| **Rückgängig gemacht** | Eine Pipeline hat ein Rollback gemeldet oder das Deployment einer Version, die vor einer anderen Version lief. Die Zeile nennt die Version, von der zurückgegangen wurde. |
| **Zur vorherigen Version gewechselt** | Die Spans sind zu einer älteren Version zurückgekehrt, die keine Pipeline gemeldet hat: Die zuletzt gesehene Version wurde erstmals vor einer neueren Version gesehen, die mehr als fünf Minuten früher endete. |
| **Erstmals aufgetreten** | Die Spans trugen eine Version, die keine Pipeline gemeldet hat. |
| **Konfiguration** | Eine Pipeline oder ein Tool hat eine Konfigurationsänderung gemeldet. Die Beschreibung wird in der Zeile angezeigt. |
| **Feature-Flag** | Eine Pipeline oder ein Tool hat eine Feature-Flag-Änderung gemeldet. Die Beschreibung wird in der Zeile angezeigt. |

Eine Konfigurationsänderung oder ein Feature-Flag ändert die laufende Version nicht und hat keine eigenen
Zahlen. Sie wird unter den Änderungen in der Nähe eines Insights aufgeführt; siehe
[Änderungen in der Nähe eines Findings](/de/apm/insights#änderungen-in-der-nähe-eines-befunds).

Ein gemeldetes Deployment zeigt Commit, Pull Request, CI-Lauf und Autor. Ist das Repository eine
http- oder https-Adresse, öffnet sich der Commit auf seiner Webseite, so wie GitHub, GitLab oder Bitbucket
einen Commit adressieren.

Anfragen, Fehlerrate und p95 jeder Version im Zeitraum stehen in ihrer neuesten Zeile, zusammen mit der Bewertung
gegenüber der Version, die davor erstmals aufgetreten ist:

| Bewertung | Wann |
|---|---|
| **Erneut aufgetreten** | Die Fehlerrate ist um mindestens einen Prozentpunkt und auf mindestens das 1,5-Fache gestiegen, oder p95 ist um mindestens ein Fünftel und mindestens 50 ms gestiegen. Der Teil, der sich verschlechtert hat, folgt der Bewertung. |
| **Verbessert** | Eine der beiden Größen ist ebenso stark gesunken, und keine ist schlechter geworden. |
| **Keine Änderung** | Keine der beiden hat sich so weit verändert. |
| **Zu wenige Anfragen** | Eine der beiden Versionen hat weniger Anfragen bedient, als ein Versionsvergleich benötigt, standardmäßig 1.000. |

Ein Klick auf eine Bewertung öffnet die beiden Versionen in **Zwei Versionen vergleichen**, das die Endpunkte auflistet, die
langsamer geworden sind, und die Fehler, die zugenommen haben. Eine erneut aufgetretene oder verbesserte Version wird außerdem unter den
letzten Deployments der Übersicht markiert.

## Canaries

Wenn zwei Versionen gleichzeitig laufen, etwa ein Canary neben der Version, die er ersetzt, zeigt eine Karte über der
Timeline beide nebeneinander. Zwei Versionen laufen gleichzeitig, wenn beide innerhalb von fünf Minuten
vor dem letzten Span des Services gesehen wurden. Die Karte vergleicht die beiden neuesten, gerechnet ab dem Zeitpunkt, an dem die neuere
erstmals aufgetreten ist:

- der Anteil der Anfragen, den jede Version bedient hat;
- Anfragen, Fehlerrate, p50, p95 und p99 jeder Version;
- die Bewertung der neueren Version gegenüber der älteren.

## Deployments aus der CI melden

Eine Pipeline meldet ein Deployment mit `POST /api/v1/apm/deployments`. Die Anfrage benötigt einen API-Token,
der `apm.deploy` verwenden darf. Owner, Administratoren und Editoren besitzen ihn, und die Richtlinie **Datenerfassung**,
der Intake-Token folgen, enthält ihn.

```bash
curl -X POST "https://<host>/api/v1/apm/deployments" \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{"service": "checkout", "environment": "production", "version": "2.4.0", "commit": "9f2c1e7a4b3d", "repository": "https://github.com/acme/checkout", "ciUrl": "https://ci.example.com/runs/7"}'
```

| Feld | Erforderlich | Beschreibung |
|---|---|---|
| `service` | Ja | Der Service, wie ihn seine Spans in `service.name` benennen. Bis zu 255 Zeichen. |
| `version` | Für ein Deployment | Die deployte Version, wie sie ihre Spans in `service.version` melden. Bis zu 192 Zeichen. |
| `kind` | Nein | `deployment` (Standard), `configuration`, `feature_flag`, `scaling` oder `infrastructure`. |
| `namespace` | Nein | Der `service.namespace` des Services. Ein Deployment ohne Namespace erscheint in jedem Namespace. |
| `environment` | Nein | Die Umgebung, als `deployment.environment.name`. Ein Deployment ohne Umgebung erscheint in jeder Umgebung. |
| `status` | Nein | `succeeded` (Standard), `failed` oder `rolled_back`, wenn das Deployment den Service auf `version` zurückgeführt hat. |
| `commit` | Nein | Der deployte Commit: bis zu 64 Buchstaben und Ziffern. |
| `repository` | Nein | Wo der Code liegt: eine https-, http-, ssh- oder git-Adresse mit bis zu 512 Zeichen. Ein Passwort in der Adresse wird als `****` gespeichert, ebenso der Benutzerteil einer https-Adresse. |
| `pullRequest` | Nein | Ein http- oder https-Link zum Pull Request. |
| `author` | Nein | Wer deployt hat, bis zu 128 Zeichen. |
| `ciUrl` | Nein | Ein http- oder https-Link zum CI-Lauf. |
| `description` | Nein | Bis zu 1.000 Zeichen. Wird angezeigt, wenn der Zeiger auf dem Ereignis ruht. |
| `deployedAt` | Nein | Wann das Deployment stattgefunden hat, in Mikrosekunden seit der Epoche. Standardmäßig der Zeitpunkt, an dem die Anfrage eintrifft. |

Service und Umgebung werden so benannt, wie APM sie benennt: Die Namensregeln der Organisation,
das Umgebungs-Mapping und die Aliase gelten für sie, wie sie für Spans gelten. Siehe
[APM-Einstellungen](/de/apm/settings).

Die Seite **Datenquelle** enthält die folgenden Schritte unter **GitHub Actions**, **GitLab CI/CD** und
**Jenkins**, mit eingetragener Adresse des Workspace.

### GitHub Actions

Hinterlegen Sie den Token als Repository-Secret und fügen Sie dann einen Schritt zum deployenden Job hinzu. `if: always()`
meldet auch ein fehlgeschlagenes Deployment.

```yaml
- name: Report the deployment to MoleSignal
  if: always()
  env:
    MOLESIGNAL_TOKEN: ${{ secrets.MOLESIGNAL_TOKEN }}
    DEPLOY_STATUS: ${{ job.status == 'success' && 'succeeded' || 'failed' }}
  run: |
    cat > deployment.json <<EOF
    {
      "service": "checkout",
      "environment": "production",
      "version": "${GITHUB_SHA::12}",
      "status": "$DEPLOY_STATUS",
      "commit": "$GITHUB_SHA",
      "repository": "$GITHUB_SERVER_URL/$GITHUB_REPOSITORY",
      "author": "$GITHUB_ACTOR",
      "ciUrl": "$GITHUB_SERVER_URL/$GITHUB_REPOSITORY/actions/runs/$GITHUB_RUN_ID"
    }
    EOF
    curl -fsS -X POST "https://<host>/api/v1/apm/deployments" \
      -H "Authorization: Bearer $MOLESIGNAL_TOKEN" \
      -H "Content-Type: application/json" \
      --data-binary @deployment.json
```

### GitLab CI/CD

Fügen Sie den Token als maskierte CI/CD-Variable mit dem Namen `MOLESIGNAL_TOKEN` hinzu und melden Sie dann aus dem
`after_script` des Deploy-Jobs, das unabhängig vom Erfolg des Deployments ausgeführt wird.

```yaml
deploy:
  stage: deploy
  environment: production
  script:
    - ./deploy.sh
  after_script:
    - |
      if [ "$CI_JOB_STATUS" = "success" ]; then DEPLOY_STATUS=succeeded; else DEPLOY_STATUS=failed; fi
      cat > deployment.json <<EOF
      {
        "service": "checkout",
        "environment": "$CI_ENVIRONMENT_NAME",
        "version": "$CI_COMMIT_SHORT_SHA",
        "status": "$DEPLOY_STATUS",
        "commit": "$CI_COMMIT_SHA",
        "repository": "$CI_PROJECT_URL",
        "author": "$GITLAB_USER_LOGIN",
        "ciUrl": "$CI_PIPELINE_URL"
      }
      EOF
      curl -fsS -X POST "https://<host>/api/v1/apm/deployments" \
        -H "Authorization: Bearer $MOLESIGNAL_TOKEN" \
        -H "Content-Type: application/json" \
        --data-binary @deployment.json
```

### Jenkins

Fügen Sie den Token als Credential vom Typ **Secret text** mit der ID `molesignal-token` hinzu und melden Sie dann im
`post`-Block der Pipeline. `post { always }` meldet auch einen fehlgeschlagenen Build. Ein Passwort in `GIT_URL` wird
maskiert, wenn das Deployment gespeichert wird.

```groovy
post {
  always {
    script {
      writeFile file: 'deployment.json', text: groovy.json.JsonOutput.toJson([
        service: 'checkout',
        environment: 'production',
        version: env.GIT_COMMIT.take(12),
        status: currentBuild.currentResult == 'SUCCESS' ? 'succeeded' : 'failed',
        commit: env.GIT_COMMIT,
        repository: env.GIT_URL,
        ci_url: env.BUILD_URL,
      ])
    }
    withCredentials([string(credentialsId: 'molesignal-token', variable: 'MOLESIGNAL_TOKEN')]) {
      sh '''
        curl -fsS -X POST "https://<host>/api/v1/apm/deployments" \
          -H "Authorization: Bearer $MOLESIGNAL_TOKEN" \
          -H "Content-Type: application/json" \
          --data-binary @deployment.json
      '''
    }
  }
}
```

## Konfigurationsänderungen und Feature-Flags melden

Melden Sie eine Konfigurationsänderung, ein Feature-Flag, eine Skalierungsänderung oder eine Änderung der Infrastruktur
unter einem Service mit demselben Endpoint, mit gesetztem `kind` und einer Beschreibung der Änderung. Eine Version ist dafür nicht
erforderlich.

Jede gemeldete Änderung wird außerdem von [`GET /api/v1/changes`](/de/api/changes) aufgeführt, auf den
Histogrammen von Logs und Traces und unter dem Metrics-Diagramm markiert sowie auf der Seite **Änderungen** von Alerts.

```bash
curl -X POST "https://<host>/api/v1/apm/deployments" \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{"service": "checkout", "environment": "production", "kind": "feature_flag", "description": "new_checkout on for 10% of users"}'
```

## Änderungen aus Webhooks melden

Ein Tool, dessen Webhook den Body und einen Header setzen kann, etwa Argo CD Notifications, Spinnaker oder das
Unleash-Webhook-Add-on mit einem Body-Template, ruft `POST /api/v1/apm/deployments` wie oben beschrieben auf. Ein Tool, das
einen eigenen Body sendet oder keinen Header setzen kann, ruft stattdessen `POST /api/v1/intake/changes` auf. Das API-Token
gehört in `Authorization: Bearer` oder, wo sich kein Header setzen lässt, in `?token=`, und muss
`apm.deploy` enthalten. Ein Token in einer Adresse kann in Proxy-Logs landen: Geben Sie einem solchen Tool ein eigenes Token,
das nur auf `apm.deploy` beschränkt ist.

| Parameter | Hinweise |
|---|---|
| `format` | `generic` (der Standard), `launchdarkly`, `unleash`, `nacos` oder `apollo`. |
| `service`, `namespace`, `environment` | Was der Body nicht angibt. Eine Änderung, die keinen Service nennt, wird abgelehnt. |
| `kind` | `deployment`, `configuration`, `feature_flag`, `scaling` oder `infrastructure`; überschreibt die Angabe im Body. |
| `serviceField`, `environmentField`, `versionField`, `descriptionField`, `authorField` | Für `generic`: ein JSON-Pointer wie `/app/name` oder ein Feldname auf oberster Ebene. Ohne Angabe wird das gleichnamige Feld gelesen, das `POST /api/v1/apm/deployments` entgegennimmt. |

| Format | Gelesen als |
|---|---|
| `launchdarkly` | Ein Feature Flag. Die Umgebung ist der Teil `env/` der auditierten Ressource, die Beschreibung der Titel des Eintrags, der Autor die E-Mail-Adresse des Mitglieds. |
| `unleash` | Ein Feature Flag: der Ereignistyp und der Name des Toggles, seine Umgebung und wer ihn geändert hat. |
| `nacos` | Eine Konfigurationsänderung an Data ID und Gruppe; der Nacos-Namespace ist der Namespace. |
| `apollo` | Eine Konfigurationsänderung: die App-ID ist der Service, das Cluster die Umgebung und der Namespace und der Release-Titel das, was geändert wurde. |

**Data sources → DevOps** enthält je eine Anleitung für LaunchDarkly, Unleash, Nacos und Apollo, mit der
für den Workspace bereits eingetragenen Adresse.

Ein Body kann eine Änderung oder eine Liste mit bis zu 100 Änderungen enthalten. Die Antwort ist `201` mit den übernommenen Änderungen. Die
Presets wurden anhand der dokumentierten Payloads der Tools geschrieben und nicht gegen Live-
Accounts geprüft; weicht der Payload eines Tools ab, verwenden Sie `generic` mit Pointern.

```bash
curl -X POST "https://<host>/api/v1/intake/changes?format=launchdarkly&service=checkout&token=<token>" \
  -H "Content-Type: application/json" \
  -d @launchdarkly-event.json
```

## Fehlerbehebung

| Symptom | Prüfen |
|---|---|
| Ein gemeldetes Deployment fehlt in der Timeline | Der Zeitraum muss `deployedAt` einschließen, und `service` muss den Service so benennen, wie APM es tut. Ein Deployment, das mit einer Umgebung gemeldet wurde, erscheint nur in dieser Umgebung. |
| Ein Deployment und die deployte Version erscheinen als zwei Zeilen | Die gemeldete `version` unterscheidet sich von der `service.version`, die die Spans tragen. Melden Sie denselben Wert. |
| `403` vom Deployments-Endpoint | Das Token darf `apm.deploy` nicht verwenden: Sein Scope lässt es aus, oder seinem Mitglied bzw. Service Account fehlt die Berechtigung. |
| `400` vom Deployments-Endpoint | Ein Feld überschreitet eine Grenze aus der obigen Tabelle; die Fehlermeldung nennt das betroffene Feld. |
