Der Abschnitt **Deployments** auf der Seite eines Dienstes stellt zwei Quellen gegenüber: die Deployments, die
Pipelines melden, und die Versionen, die in den Spans des Dienstes in `service.version` stehen. Eine Version,
die keine Pipeline gemeldet hat, erscheint trotzdem anhand der Spans.

## Die Deployment-Zeitleiste

Die Zeitleiste listet die Ereignisse für den Dienst im gewählten Zeitraum auf, die neuesten zuerst:

| Ereignis | Wann |
|---|---|
| **Bereitgestellt** | Eine Pipeline hat ein erfolgreiches Deployment gemeldet. |
| **Fehlgeschlagen** | Eine Pipeline hat ein fehlgeschlagenes Deployment gemeldet. Ein fehlgeschlagenes Deployment ändert die laufende Version nicht. |
| **Rückgängig gemacht** | Eine Pipeline hat einen Rollback oder das Deployment einer Version gemeldet, die schon vor einer anderen Version lief. Die Zeile nennt die Version, von der aus der Wechsel erfolgte. |
| **Zur vorherigen Version gewechselt** | Die Spans zeigen wieder eine ältere Version, die keine Pipeline gemeldet hat: Die zuletzt erfasste Version tauchte erstmals vor einer neueren Version auf, die seit mehr als fünf Minuten nicht mehr lief. |
| **Erstmals aufgetreten** | Die Spans enthielten eine Version, die keine Pipeline gemeldet hat. |
| **Konfiguration** | Eine Pipeline oder ein Tool hat eine Konfigurationsänderung gemeldet. Die Zeile enthält die Beschreibung. |
| **Feature-Flag** | Eine Pipeline oder ein Tool hat eine Änderung an einem Feature-Flag gemeldet. Die Zeile enthält die Beschreibung. |

Eine Konfigurationsänderung oder ein Feature-Flag ändert die laufende Version nicht und hat keine eigenen
Kennzahlen. Der Eintrag erscheint unter den Änderungen im Umfeld einer Erkenntnis. Siehe
[Änderungen im Umfeld eines Befunds](/de/apm/insights#änderungen-rund-um-einen-befund).

Ein gemeldetes Deployment zeigt den Commit, den Pull Request, den CI-Lauf und den Autor an. Bei einer
http- oder https-Adresse des Repositorys öffnet sich der Commit auf seiner Webseite. Der Link folgt dem Format, das GitHub, GitLab oder Bitbucket
für Commit-Adressen verwendet.

Die neueste Zeile jeder Version zeigt die Anfragen, die Fehlerrate und p95 für den Zeitraum sowie die Bewertung
im Vergleich zur Version, die unmittelbar davor erstmals aufgetreten ist:

| Bewertung | Wann |
|---|---|
| **Erneut aufgetreten** | Die Fehlerrate ist um mindestens einen Prozentpunkt und auf mindestens das 1,5-Fache gestiegen, oder p95 ist um mindestens ein Fünftel und mindestens 50 ms gestiegen. Nach der Bewertung steht, welche Kennzahl sich verschlechtert hat. |
| **Verbessert** | Eine der beiden Kennzahlen ist um mindestens die entsprechenden Schwellenwerte gesunken. Keine hat sich verschlechtert. |
| **Keine Änderung** | Keine der beiden Kennzahlen hat sich so stark verändert. |
| **Zu wenige Anfragen** | Mindestens eine Version hat weniger Anfragen verarbeitet, als der Versionsvergleich voraussetzt. Standardmäßig sind 1.000 Anfragen erforderlich. |

Wählen Sie eine Bewertung aus, um beide Versionen in **Zwei Versionen vergleichen** zu öffnen. Dort sehen Sie die Endpunkte, die
langsamer geworden sind, und die Fehler, die häufiger aufgetreten sind. Versionen mit einer Verschlechterung oder Verbesserung markiert auch die
Übersicht unter den letzten Deployments.

## Canaries

Wenn zwei Versionen gleichzeitig laufen, etwa eine Canary-Version neben der Version, die sie ablöst, stellt eine Karte oberhalb der
Zeitleiste beide gegenüber. Zwei Versionen gelten als gleichzeitig aktiv, wenn beide innerhalb der letzten fünf Minuten
vor oder zum Zeitpunkt des letzten Spans des Dienstes erfasst wurden. Die Karte vergleicht die beiden neuesten Versionen ab dem Zeitpunkt, zu dem die neuere erstmals
aufgetreten ist:

- den Anteil der Anfragen, die jede Version verarbeitet hat;
- Anfragen, Fehlerrate, p50, p95 und p99 je Version;
- die Bewertung der neueren Version im Vergleich zur älteren.

## Deployments aus der CI melden

Eine Pipeline meldet ein Deployment mit `POST /api/v1/apm/deployments`. Die Anfrage erfordert ein API-Token
mit der Berechtigung `apm.deploy`. Diese Berechtigung haben die Rollen „Eigentümer“, „Administrator“ und „Bearbeiter“. Auch die Richtlinie **Datenerfassung**
für Erfassungstoken enthält sie.

```bash
curl -X POST "https://<host>/api/v1/apm/deployments" \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{"service": "checkout", "environment": "production", "version": "2.4.0", "commit": "9f2c1e7a4b3d", "repository": "https://github.com/acme/checkout", "ciUrl": "https://ci.example.com/runs/7"}'
```

| Feld | Erforderlich | Beschreibung |
|---|---|---|
| `service` | Ja | Der Dienstname, wie er in den Spans unter `service.name` steht. Bis zu 255 Zeichen. |
| `version` | Bei einem Deployment | Die bereitgestellte Version, wie sie in den Spans unter `service.version` steht. Bis zu 192 Zeichen. |
| `kind` | Nein | `deployment` (Standard), `configuration` oder `feature_flag`. |
| `namespace` | Nein | Der Namespace des Dienstes aus `service.namespace`. Ein Deployment ohne Namespace erscheint in allen Namespaces. |
| `environment` | Nein | Die Umgebung aus `deployment.environment.name`. Ein Deployment ohne Umgebung erscheint in allen Umgebungen. |
| `status` | Nein | `succeeded` (Standard), `failed` oder `rolled_back`, wenn das Deployment den Dienst auf `version` zurückgesetzt hat. |
| `commit` | Nein | Der bereitgestellte Commit: bis zu 64 Buchstaben und Ziffern. |
| `repository` | Nein | Die Adresse des Codes: eine https-, http-, ssh- oder git-Adresse mit bis zu 512 Zeichen. MoleSignal speichert ein Passwort in der Adresse als `****`. Bei einer https-Adresse gilt das auch für den Benutzernamen. |
| `pullRequest` | Nein | Ein http- oder https-Link zum Pull Request. |
| `author` | Nein | Angabe zur ausführenden Person oder zum ausführenden Konto, bis zu 128 Zeichen. |
| `ciUrl` | Nein | Ein http- oder https-Link zum CI-Lauf. |
| `description` | Nein | Bis zu 1.000 Zeichen. Die Beschreibung erscheint, wenn der Mauszeiger über dem Ereignis steht. |
| `deployedAt` | Nein | Zeitpunkt des Deployments in Mikrosekunden seit der Unix-Epoche. Standardmäßig gilt der Zeitpunkt, zu dem die Anfrage eingeht. |

APM verwendet für Dienst und Umgebung dieselben Benennungsregeln,
Umgebungszuordnungen und Aliasse der Organisation wie für Spans. Siehe
[APM-Einstellungen](/de/apm/settings).

Auf der Seite **Datenquelle** stehen die folgenden Schritte unter **GitHub Actions**, **GitLab CI/CD** und
**Jenkins**. Die Adresse des Workspace ist dort bereits eingetragen.

### GitHub Actions

Speichern Sie das Token als Repository-Secret und fügen Sie dem Deployment-Job einen Schritt hinzu. `if: always()`
meldet auch ein fehlgeschlagenes Deployment.

```yaml
- name: Report the deployment to MoleSignal
  if: always()
  env:
    MOLESIGNAL_TOKEN: ${{ secrets.MOLESIGNAL_TOKEN }}
    DEPLOY_STATUS: ${{ job.status == 'success' && 'succeeded' || 'failed' }}
  run: |
    cat > deployment.json <<EOF
    {
      "service": "checkout",
      "environment": "production",
      "version": "${GITHUB_SHA::12}",
      "status": "$DEPLOY_STATUS",
      "commit": "$GITHUB_SHA",
      "repository": "$GITHUB_SERVER_URL/$GITHUB_REPOSITORY",
      "author": "$GITHUB_ACTOR",
      "ciUrl": "$GITHUB_SERVER_URL/$GITHUB_REPOSITORY/actions/runs/$GITHUB_RUN_ID"
    }
    EOF
    curl -fsS -X POST "https://<host>/api/v1/apm/deployments" \
      -H "Authorization: Bearer $MOLESIGNAL_TOKEN" \
      -H "Content-Type: application/json" \
      --data-binary @deployment.json
```

### GitLab CI/CD

Fügen Sie das Token als maskierte CI/CD-Variable namens `MOLESIGNAL_TOKEN` hinzu und melden Sie das Deployment im Abschnitt
`after_script` des Deployment-Jobs. Dieser Abschnitt läuft unabhängig davon, ob das Deployment erfolgreich war.

```yaml
deploy:
  stage: deploy
  environment: production
  script:
    - ./deploy.sh
  after_script:
    - |
      if [ "$CI_JOB_STATUS" = "success" ]; then DEPLOY_STATUS=succeeded; else DEPLOY_STATUS=failed; fi
      cat > deployment.json <<EOF
      {
        "service": "checkout",
        "environment": "$CI_ENVIRONMENT_NAME",
        "version": "$CI_COMMIT_SHORT_SHA",
        "status": "$DEPLOY_STATUS",
        "commit": "$CI_COMMIT_SHA",
        "repository": "$CI_PROJECT_URL",
        "author": "$GITLAB_USER_LOGIN",
        "ciUrl": "$CI_PIPELINE_URL"
      }
      EOF
      curl -fsS -X POST "https://<host>/api/v1/apm/deployments" \
        -H "Authorization: Bearer $MOLESIGNAL_TOKEN" \
        -H "Content-Type: application/json" \
        --data-binary @deployment.json
```

### Jenkins

Fügen Sie das Token als Zugangsdaten vom Typ **Secret text** mit der ID `molesignal-token` hinzu und melden Sie das Deployment im
`post`-Block der Pipeline. `post { always }` meldet auch einen fehlgeschlagenen Build. Ein Passwort in `GIT_URL`
maskiert MoleSignal beim Speichern des Deployments.

```groovy
post {
  always {
    script {
      writeFile file: 'deployment.json', text: groovy.json.JsonOutput.toJson([
        service: 'checkout',
        environment: 'production',
        version: env.GIT_COMMIT.take(12),
        status: currentBuild.currentResult == 'SUCCESS' ? 'succeeded' : 'failed',
        commit: env.GIT_COMMIT,
        repository: env.GIT_URL,
        ci_url: env.BUILD_URL,
      ])
    }
    withCredentials([string(credentialsId: 'molesignal-token', variable: 'MOLESIGNAL_TOKEN')]) {
      sh '''
        curl -fsS -X POST "https://<host>/api/v1/apm/deployments" \
          -H "Authorization: Bearer $MOLESIGNAL_TOKEN" \
          -H "Content-Type: application/json" \
          --data-binary @deployment.json
      '''
    }
  }
}
```

## Konfigurationsänderungen und Feature-Flags melden

Melden Sie eine Konfigurationsänderung oder ein Feature-Flag über denselben Endpunkt. Setzen Sie `kind` und geben Sie eine
Beschreibung der Änderung an. Eine Version ist nicht erforderlich.

```bash
curl -X POST "https://<host>/api/v1/apm/deployments" \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{"service": "checkout", "environment": "production", "kind": "feature_flag", "description": "new_checkout on for 10% of users"}'
```

## Fehlerbehebung

| Symptom | Prüfung |
|---|---|
| Ein gemeldetes Deployment fehlt in der Zeitleiste | Der Zeitraum muss `deployedAt` enthalten. Der Dienstname in `service` muss dem Namen in APM entsprechen. Ein Deployment mit Umgebungsangabe erscheint nur in dieser Umgebung. |
| Ein Deployment und die damit bereitgestellte Version erscheinen in zwei Zeilen | Der gemeldete Wert für `version` weicht von `service.version` in den Spans ab. Melden Sie denselben Wert. |
| `403` vom Deployment-Endpunkt | Das Token darf `apm.deploy` nicht verwenden: Die Berechtigung fehlt im Geltungsbereich des Tokens, oder das zugehörige Mitglied oder Dienstkonto hat sie nicht. |
| `400` vom Deployment-Endpunkt | Ein Feld verstößt gegen eine Vorgabe aus der obigen Tabelle. Die Fehlermeldung nennt das Feld. |
