**RUM → Fehler** listet die Fehler einer Anwendung als Probleme auf. Ein Problem fasst gleichartige Fehler zusammen.
Es hat einen Status, ein Team und eine zuständige Person. Außerdem erfasst es, wann und in welchen Versionen es auftrat. Jeder Fehler bleibt im
Stream `rum_errors`, der die Problem-ID in `error.issue_id` speichert. So stehen im [Explorer](/de/rum/explorer) und in Abfragen beide Informationen zur Verfügung.

## Wie aus Fehlern Probleme werden

Der Server ordnet jeden eingehenden Fehler einem Problem zu. Die ID ist ein Hash aus:

- der Anwendung und `error.source`,
- dem Typ, der Kategorie und der Meldung des Fehlers ohne die Bestandteile, die sich von Fehler zu Fehler ändern,
- den ersten drei Frames aus dem eigenen Code der Anwendung, aufgelöst anhand der Source Map, der Mapping-Datei oder der Symboldatei des Releases, sofern eine solche Datei hochgeladen wurde (siehe [Source Maps und Symbole](/de/rum/source-maps)),
- bei einer fehlgeschlagenen Anfrage der Methode, dem Pfad und dem Statuscode.

Der Server entfernt Zahlen, UUIDs, Hashes mit mindestens acht Hexadezimalstellen, E-Mail-Adressen sowie den Query-String oder das Fragment einer
Webadresse aus der Meldung. So gehören `Loading chunk 482 failed.` und `Loading chunk 17 failed.` zum selben Problem. Frames aus
Paketen, Frameworks oder Laufzeitumgebungen zählen nicht zum eigenen Code der Anwendung. Der Server berücksichtigt sie nur, wenn keine
anwendungseigenen Frames vorliegen.

Senden Sie `error.fingerprint` (bis zu 128 Zeichen), um Fehler anders zu gruppieren. Fehler derselben Anwendung mit demselben
Fingerabdruck gehören unabhängig von ihren Meldungen und Stacktraces zum selben Problem. Die SDKs setzen das Feld nicht. Übergeben Sie es beim Aufruf, der den
Fehler meldet.

<Note>
  MoleSignal versioniert die Regeln zur ID-Bildung. Änderungen an der Gruppierung erzeugen neue IDs. Ein bestehendes Problem
  behält daher seine bisherige Zuordnung. Fehler aus der Zeit vor der Einführung der Problemerfassung haben keine `error.issue_id` und fehlen
  in der Liste. Geht ein Fehler vor dem Upload der Source Map für sein Release ein, verwendet der Server die ursprünglichen Frames. Geht er
  danach ein, verwendet der Server die rekonstruierten Frames. So kann derselbe Fehler zu zwei Problemen führen. Der Server führt bestehende Probleme nicht zusammen.
</Note>

## Die Liste

Die Liste zeigt die Probleme einer Anwendung und einer Umgebung, für die im gewählten Zeitraum Fehler auftraten. Jede Zeile zeigt:

| Spalte | Inhalt |
|---|---|
| **Problem** | Typ und Meldung des ersten Fehlers sowie der erste Frame aus dem eigenen Code der Anwendung. |
| **Status** | Der Bearbeitungsstand. Siehe [Statuswerte](#statuswerte). |
| **Zuständig** | Die zuständige Person oder, falls keine Person zugewiesen ist, das zuständige Team. |
| **Sitzungen** | Die Anzahl der Sitzungen, in denen das Problem im gewählten Zeitraum auftrat. |
| **Benutzer** | Die Anzahl der betroffenen Personen. Bei Besuchen ohne Benutzer-ID zählt die anonyme ID des SDK. |
| **Trend** | Die Anzahl der Vorkommnisse in jedem der 12 gleich langen Abschnitte des Zeitraums. |
| **Versionen** | Die erste und die neueste Version, in der das Problem auftrat. |
| **Zuletzt aufgetreten** | Der Zeitpunkt des letzten Auftretens, unabhängig vom gewählten Zeitraum. |

Standardmäßig zeigt die Liste Probleme mit dem Filter **Nicht behoben**: offene, in Untersuchung befindliche oder erneut aufgetretene Probleme. Wählen Sie im Filter einen anderen Status oder
**Alle Probleme** aus. Filtern Sie nach Wörtern im Typ, in der Meldung oder an der Auslösestelle, nach der zuständigen Person und,
wenn mehrere Clienttypen Fehler gemeldet haben, nach der Quelle. Klicken Sie zum Sortieren auf **Status**, **Sitzungen**, **Benutzer** oder **Zuletzt aufgetreten**.
Klicken Sie erneut, um die Sortierreihenfolge umzukehren. Die URL speichert den aktuellen Zustand der Seite. So lässt sich die Ansicht teilen.

Die Liste lädt je nach Sortierung die 250 Probleme mit den meisten Sitzungen, Benutzern oder Vorkommnissen und wendet erst danach
die Filter an. Probleme unterhalb dieser Grenze bleiben bei der Filterung unberücksichtigt. Die Liste zeigt höchstens 100 Probleme an.

**Wo die Fehler auftreten** oberhalb der Liste schlüsselt die Sitzungen zu den aufgeführten Problemen nach Versionen, Seiten und
Browsern auf. Klicken Sie auf einen Wert, um die Liste auf die dort aufgetretenen Fehler zu beschränken. Der Filter gilt für alle Spalten. Klicken Sie erneut auf den
Wert, um den Filter aufzuheben.

## Das Problem

Klicken Sie auf eine Zeile, um das Problem in einem Seitenbereich zu öffnen. Die URL enthält das Problem und öffnet den Seitenbereich beim Aufrufen erneut.

- Legen Sie im Kopfbereich den Status, das Team und die zuständige Person fest. **Im Explorer anzeigen** öffnet die Fehler des Problems im Explorer.
- Die Infozeile zeigt den Status, die Anzahl der Sitzungen und betroffenen Personen im gewählten Zeitraum, das erste und letzte Auftreten
  sowie die Versionen.
- **Zeitlicher Verlauf** zeigt die Sitzungen der letzten 14 Tage pro Tag, gestapelt nach Version. Eine gestrichelte Linie markiert den Tag, an dem das Problem
  behoben wurde.
- **Wo die Fehler auftreten** schlüsselt die Sitzungen zu diesem Problem nach Browsern, Systemen und Ländern auf.
- **Auslösestelle** zeigt die Frames des jüngsten Fehlers mit einem Stacktrace. Frames aus dem eigenen Code der Anwendung erscheinen fett,
  Frames aus Bibliotheken abgeblendet. Wenn ein Debug-Artefakt die Frames rekonstruiert hat, wechseln Sie zwischen **Rekonstruiert** und **Original**.
- **Neueste Sitzungen** zeigt die letzten drei Sitzungen, in denen das Problem auftrat, jeweils mit einem Link zur Wiedergabe und zur Zeitleiste.
  **Betroffene Personen** zeigt die Personen, bei denen das Problem am häufigsten auftrat. Wenn MoleSignal nur den Fehler und nicht die zugehörige Sitzung speichert, steht
  *Sitzung nicht gespeichert* anstelle des Links zur Sitzung. Siehe [Sampling von RUM-Daten](/de/rum/sampling#alle-fehler-speichern).

Die Liste zeigt für jedes Problem den Typ, die Meldung und die Auslösestelle des ersten eingegangenen Fehlers an. Dabei gelten die
Maskierungsregeln, die beim Speichern des Fehlers aktiv waren.

## Statuswerte

| Status | Bedeutung | Festgelegt durch |
|---|---|---|
| **Öffnen** | Das Problem wurde noch nicht geprüft. Jedes neue Problem beginnt mit diesem Status. | Server oder zuständige Person. |
| **In Untersuchung** | Die Untersuchung läuft. | Manuell. |
| **Erneut aufgetreten** | Das Problem war behoben und trat in einer neueren Version erneut auf. | Nur der Server. |
| **Behoben** | Die Ursache ist behoben. | Manuell. |
| **Ignoriert** | Das Problem erfordert keine Bearbeitung. | Manuell. |

Offene, in Untersuchung befindliche und erneut aufgetretene Probleme gelten als nicht behoben.

### Regression

Beim Setzen des Status **Behoben** erfasst MoleSignal den Zeitpunkt, die Person und die zu diesem Zeitpunkt neueste Version der Anwendung. Die Reihenfolge der Versionen richtet sich nach
dem Zeitpunkt ihrer ersten Erfassung, nicht nach ihrem Namen. Ein Fehler zu einem behobenen Problem öffnet es nur dann mit dem Status **Erneut aufgetreten** wieder, wenn die
Version des Fehlers erst nach der beim Beheben erfassten Version zum ersten Mal registriert wurde. Ohne Update bleibt die alte Version im Einsatz.
Ein Fehler in derselben oder einer älteren Version öffnet das Problem nie erneut.

Wenn eine Anwendung keine Version meldet, fehlt die Grundlage für die Reihenfolge. Jeder Fehler nach dem Beheben öffnet das Problem dann erneut. Ein Fehler ohne
Versionsangabe öffnet ein Problem nicht erneut, wenn beim Beheben eine Version erfasst wurde.

Ändern Sie den Status eines erneut aufgetretenen Problems, um die Regression zu beenden. Markieren Sie es erneut als behoben, um die dann neueste Version zu erfassen.

Ein Problem gilt für die gesamte Anwendung und alle ihre Umgebungen. Der Server speichert die Umgebung des Fehlers, der das Problem erneut geöffnet hat, sowie
den Zeitpunkt des ersten Auftretens in jeder Umgebung. [Alarmregeln](/de/rum/alerts) nutzen diese Angaben, um neue und erneut aufgetretene Probleme
pro Umgebung zu zählen.

Der Serverteil, der die Fehler empfängt, hält ein Problem bis zu einer Minute im Cache. Manuelle Statusänderungen kommen dort innerhalb dieser Minute an. Solange der alte Status im Cache steht, öffnet ein Fehler in einer neueren Version das Problem nicht erneut. Erst der nächste Fehler nach Ablauf der Minute öffnet es erneut.

## Neue Probleme pro Stunde

Eine Anwendung legt pro Stunde höchstens so viele Probleme an, wie unter **Neue Probleme pro Stunde** festgelegt sind. Der Standardwert ist 100. Nach Überschreiten des Limits fasst MoleSignal für den Rest
der Stunde alle Fehler, die noch keinem Problem zugeordnet sind, unter **Weitere Fehler** zusammen. So kann eine Anwendung, deren
Meldungen sich nie wiederholen, die Liste nicht füllen. Ändern Sie den Wert unter **RUM → Anwendungen** im Abschnitt **Probleme**.
Wählen Sie einen Wert zwischen 1 und 10.000. Die Änderung greift innerhalb einer halben Minute.

## Berechtigungen

- `rum.issues.read` erlaubt den Zugriff auf die Issue-Liste und einzelne Issues.
- `rum.issues.manage` erlaubt das Ändern des Status sowie des zugewiesenen Teams und der zuständigen Person. Die Rollen „Eigentümer“, „Administrator“ und „Bearbeiter“ haben diese Berechtigung. Ohne sie zeigen die Bedienelemente nur
  die aktuellen Einstellungen an.

Die Endpunkte sind in der [RUM-API](/de/api/rum#issues) dokumentiert.
