Das MoleSignal Flutter App RUM SDK sendet mobile Telemetriedaten im selben [Ereignisformat](/de/rum/events) wie das Browser RUM
SDK. Die Flutter-native Instrumentierung ermöglicht denselben Analyseablauf, ohne browserspezifische Metriken nachzubilden.

## Funktionsvergleich

| Browserfunktion | Entsprechung im Flutter App SDK |
|---|---|
| Ansichten aus dem Navigationsverlauf | `RumNavigationObserver` oder `startView`; bei Änderungen meldet das SDK die jeweilige Ansicht erneut |
| Klicks | Automatisch erfasste Tippgesten über `RumApp` oder benannte `RumUserAction`-Widgets |
| Frust- und Fehlerklicks | Die Frustsignale `rage_tap` und `error_tap` an der Tippaktion |
| Laufzeit- und Promise-Fehler | `FlutterError`, `PlatformDispatcher.onError` (ein Absturz), `addError` und fehlgeschlagene Anfragen |
| Fetch- und XHR-Ressourcen | `MoleSignalHttpClient`, `startResource` und `stopResource` oder `addResource` |
| Lange Tasks | Langsame Frames und eingefrorene Frames mit der Kennzeichnung `is_frozen_frame` |
| Web Vitals | Die Kaltstartmetrik `app_launch`, der Abschluss des ersten Build-Vorgangs, Frame- und Speichermetriken der Ansicht sowie benutzerdefinierte Zeitmetriken |
| rrweb-DOM-Replay | Zum Schutz der Privatsphäre aufbereitete Screenshots, kodiert als rrweb-Snapshots und -Mutationen |
| W3C-Trace-Korrelation | `traceparent` aus der Anfrage, der Antwort oder `Server-Timing` in `resource.trace_id` und `resource.span_id` |

Das SDK erfasst für Flutter-Anwendungen keine browserspezifischen Metriken wie LCP und CLS. Flutter meldet Daten zum Build-Vorgang, zur Rasterung,
zur Bildwiederholrate, zu langsamen und eingefrorenen Frames sowie zum Speicher.

## Voraussetzungen

- Flutter 3.35 oder neuer;
- Dart 3.9 oder neuer;
- Android 24+ oder iOS 13+ bei Verwendung des standardmäßigen persistenten Identitätsspeichers.

Das SDK liest Gerätemarke, Modell, Betriebssystemversion, Akkustand und Netzwerkverbindung über `device_info_plus`,
`battery_plus` und `connectivity_plus` aus. Diese Pakete sind Abhängigkeiten des SDK. Setzen Sie `trackDeviceInfo: false`, um nur die Daten zu senden, die Flutter
selbst bereitstellt.

## Installieren und initialisieren

<Warning>
  `clientToken` wird mit der Anwendung ausgeliefert und muss als öffentlich gelten. Verwenden Sie das an die
  [RUM-Anwendung](/de/rum/applications#client-token) gebundene Client-Token.
</Warning>

<Steps>
  <Step title="Anwendung erstellen">
    Öffnen Sie **RUM → Anwendungen**, klicken Sie auf **Anwendung erstellen** und wählen Sie die Plattform **Flutter**. **Einrichtungsanleitung
    öffnen** zeigt den Endpunkt, das Token und die Konfiguration mit der bereits eingetragenen Kennung.
  </Step>
  <Step title="Paket hinzufügen">
    ```yaml
    dependencies:
      molesignal_flutter: ^0.3.0
    ```

    Führen Sie nach der Aktualisierung von `pubspec.yaml` den Befehl `flutter pub get` aus.
  </Step>
  <Step title="Vor runApp initialisieren">
    ```dart
    import 'package:flutter/material.dart';
    import 'package:molesignal_flutter/molesignal_flutter.dart';

    Future<void> main() async {
      WidgetsFlutterBinding.ensureInitialized();

      final rum = await initRum(
        const RumConfiguration(
          applicationId: 'checkout-mobile',
          clientToken: 'mspat-your-client-token',
          site: 'https://molesignal.example.com',
          service: 'checkout-app',
          env: 'production',
          version: String.fromEnvironment('MOLESIGNAL_VERSION'),
          architecture: String.fromEnvironment('MOLESIGNAL_ARCHITECTURE'),
          debugId: String.fromEnvironment('MOLESIGNAL_DEBUG_ID'),
          sessionSampleRate: 100,
          sessionReplaySampleRate: 20,
          trackUserInteractions: true,
        ),
      );

      runApp(
        RumApp(
          client: rum,
          child: MaterialApp(
            navigatorObservers: <NavigatorObserver>[
              RumNavigationObserver(rum),
            ],
            routes: <String, WidgetBuilder>{
              '/': (_) => const HomePage(),
              '/checkout': (_) => const CheckoutPage(),
            },
          ),
        ),
      );
    }
    ```

    Rufen Sie `initRum` so früh wie möglich auf: Die Kaltstartzeit reicht von diesem Aufruf bis zum ersten Frame. `RumApp` legt den
    Aufnahmebereich für Session Replay fest und aktiviert die automatische Erfassung von Tippgesten und Frustsignalen. Session Replay bleibt deaktiviert, außer
    das Sampling über `sessionReplaySampleRate` wählt die aktuelle Sitzung aus oder die Aufzeichnung startet manuell.
  </Step>
  <Step title="Erste Sitzung überprüfen">
    Öffnen Sie **RUM → Explorer**, wählen Sie einen Zeitraum, der die aktuelle Uhrzeit einschließt, und prüfen Sie, ob die Sitzung von
    `checkout-mobile` erscheint. Öffnen Sie die Sitzung, um die Ansichten und den Gerätekontext zu prüfen.
  </Step>
</Steps>

`site` akzeptiert den Origin von MoleSignal oder eine Basis-URL, die auf `/api`, `/api/v1` oder `/api/v1/rum` endet. Das SDK vervollständigt den Pfad
und sendet Ereignisse an `POST /api/v1/rum/events`. `applicationId` muss zur Anwendung des Tokens gehören: Das SDK sendet die ID als `application.id`,
und MoleSignal weist Ereignisse mit einer anderen Anwendungs-ID zurück.

## Sitzungen und Ansichten

Eine UUID in den gemeinsamen Einstellungen identifiziert die Sitzung. Sie endet nach 15 Minuten Inaktivität oder nach vier Stunden.
Das SDK entscheidet einmalig zu Beginn, ob es die Sitzung erfasst. Das SDK sendet kein Sitzungsereignis: MoleSignal leitet Sitzungen aus den Ansichten ab. Jedes Ereignis
enthält `session.id`, `session.type` und `session.start`. Eine Ansicht enthält zusätzlich `session.has_replay`. Das Feld ist wahr, sobald ein Abschnitt
der Sitzung aufgezeichnet wurde. Eine Ansicht gehört nie zu zwei Sitzungen: Beginnt bei sichtbarer Ansicht eine neue Sitzung, endet die bisherige Ansicht und
derselbe Bildschirm bleibt in einer neuen Ansicht mit `loading_type: session_renewal` sichtbar.

`RumNavigationObserver` erfasst sichtbare benannte Routen. Binden Sie den Observer für Anwendungen mit `Router` oder
`go_router` über die Router-Integration ein. Rufen Sie `startView` auf, wenn eine Route keinen stabilen Namen hat oder die Navigation außerhalb von `Navigator` erfolgt.

```dart
rum.startView('/checkout', name: 'Checkout');
rum.addTiming('cart_ready');          // view.custom_timings
rum.stopView('/checkout');
```

`view.url` enthält den Routenpfad. Ohne `trackUrlQueryString` fehlen Query-String und Fragment. `view.name` enthält den Namen. Beim Start
einer Ansicht endet die vorherige. Bei Änderungen meldet das SDK die Ansicht mit höherer `view.revision` und den aktuellen Zählerständen erneut:
höchstens einmal pro `flushInterval` und sofort beim Start oder Ende der Ansicht oder wenn die App gepufferte Daten sendet. Ansichten enden, wenn die App
in den Hintergrund wechselt. Bei der Rückkehr erscheinen sie erneut als `view_controller_redisplay`. Ereignisse vor dem ersten Aufruf von
`startView` gehören zu einer `ApplicationLaunch`-Ansicht.

## Benutzer identifizieren und Anwendungsaktivität erfassen

```dart
rum.setUser(const RumUser(id: 'user-42', attributes: {'plan': 'enterprise'}));
rum.setAccount(const RumAccount(id: 'acme', name: 'Acme'));
rum.setGlobalContextProperty('region', 'ap-southeast-1');
rum.addFeatureFlagEvaluation('new_checkout', true);

rum.addAction('Checkout submitted', context: {'cart_size': 3});

try {
  await submitOrder();
} catch (error, stackTrace) {
  rum.addError(error, stackTrace: stackTrace, context: {'step': 'payment'});
}

rum.startDurationVital('checkout_form_ready');
// ...
rum.stopDurationVital('checkout_form_ready');
rum.addDurationVital('cart_sync', const Duration(milliseconds: 640));
```

Das SDK bindet vorhandene Handler für `FlutterError.onError` und `PlatformDispatcher.onError` in die Aufrufkette ein. Leiten Sie Fehler aus weiteren Isolates an
das Haupt-Isolate weiter und rufen Sie `addError` auf. Rufen Sie nach der Abmeldung `clearUser()` auf, wenn nachfolgende Aktivitäten nicht mehr dem identifizierten Benutzer zugeordnet werden sollen.

**Aktionen** sind `tap`, `custom`, `back` und die automatische Aktion `application_start`. Automatisch erfasste Tippgesten heißen einheitlich `Tap`. Das SDK liest dabei keine
Bildschirminhalte aus. Umschließen Sie wichtige Bedienelemente mit `RumUserAction`, um einen stabilen fachlichen Namen zu vergeben, ohne die Steuerung der
Gesture Arena von Flutter zu übernehmen:

```dart
RumUserAction(
  client: rum,
  name: 'Pay now',
  child: ElevatedButton(
    onPressed: pay,
    child: const Text('Pay now'),
  ),
)
```

Eine Tippaktion bleibt offen, solange die dadurch ausgelösten Anfragen laufen, höchstens jedoch fünf Sekunden. Fehler, Abstürze und Ressourcen aus diesem Zeitraum
enthalten die zugehörige `action.id`. Die Aktion meldet deren Anzahl. Bei drei Tippgesten innerhalb einer Sekunde und innerhalb von 50 logischen Pixeln gilt die letzte als `rage_tap`.
Eine Tippgeste, die einen Fehler verursacht, gilt als `error_tap`. Setzen Sie `trackUserInteractions: true`, um Tippgesten zu erfassen. `trackFrustrations` übernimmt standardmäßig diesen Wert.

**Fehler** enthalten `source`, `type`, `message`, `stack`, strukturierte `frames` und `handling`. Framework-Fehler gelten als `unhandled`. Fehler aus
`PlatformDispatcher.onError` gelten zusätzlich als Abstürze. `addError` meldet einen `handled`-Fehler mit dem angegebenen `source`-Wert, standardmäßig `custom`. Schlägt eine Anfrage
vor Erhalt einer Antwort fehl, gilt sie als `network`-Fehler. Ein HTTP-Fehlerstatus zählt nur als Ressource. Das SDK setzt `error.fingerprint` nicht. Geben Sie
`fingerprint:` an, um die Gruppierung festzulegen.

## HTTP-Ressourcen und Backend-Traces überwachen

Umschließen Sie `package:http` mit `MoleSignalHttpClient`:

```dart
import 'package:http/http.dart' as http;

final http.Client httpClient = MoleSignalHttpClient(
  rum,
  inner: http.Client(),
);

await httpClient.get(Uri.parse('https://api.example.com/orders'));
```

Deklarieren Sie `http: ^1.6.0` als direkte Abhängigkeit der Anwendung, falls diese `package:http` noch nicht verwendet. Der Wrapper erfasst
die bereinigte URL, die Methode, die Dauer, den Statuscode, die Antwortgröße und verfügbare W3C-Trace-Kennungen. Die Zeitmessung endet, sobald der Client den Antworttext vollständig gelesen hat,
das Lesen fehlschlägt oder der Client es abbricht. Das SDK liest den Trace-Kontext in dieser Reihenfolge: `traceparent` aus der Antwort, ein `traceparent`-Eintrag in `Server-Timing`,
dann `traceparent` aus der Anfrage. Beschränken Sie das Auslesen von Trace-Headern auf die vertrauenswürdigen Dienste:

```dart
RumConfiguration(
  // ...
  allowedTracingUrls: <Pattern>[
    'https://api.example.com',
    RegExp(r'^https://edge-\w+\.example\.com/'),
  ],
)
```

Das SDK fängt den Netzwerkverkehr nicht global ab. Rufen Sie bei Dio und anderen Clients `startResource` und `stopResource` aus den Interceptors auf oder verwenden Sie
`addResource` für eine abgeschlossene Anfrage.

## Felder zur Rendering-Performance

| Feld | Bedeutung |
|---|---|
| `view.performance.fbc.timestamp` | Erster Build abgeschlossen: Nanosekunden vom Start der View bis zum Abschluss des ersten für sie erstellten Frames |
| `view.flutter_build_time`, `view.flutter_raster_time` | Minimale, maximale und durchschnittliche Dauer in Nanosekunden pro Frame für den Build im UI-Thread und die Rasterisierung im Raster-Thread |
| `view.refresh_rate_average`, `view.refresh_rate_min` | Erreichbare Bildrate in Frames pro Sekunde, begrenzt auf die Bildwiederholrate des Displays |
| `view.slow_frames_rate` | Millisekunden in langsamen Frames pro Sekunde der View-Dauer. Langsame Frames überschreiten das Frame-Zeitbudget, bleiben aber unter dem Schwellenwert für eingefrorene Frames |
| `view.freeze_rate` | Sekunden in eingefrorenen Frames pro Stunde der View-Dauer |
| `view.memory_average`, `view.memory_max` | Resident Set Size in Bytes, nicht verfügbar auf Flutter Web |
| `long_task.duration`, `long_task.is_frozen_frame` | Frame mit einer Dauer von mindestens `longFrameThreshold` (100 ms). Ab `frozenFrameThreshold` (700 ms) gilt er als eingefroren |
| `vital` vom Typ `app_launch` | Kaltstart: Nanosekunden von `initRum` bis zum Abschluss des ersten für die Anwendungsoberfläche erstellten Frames |

## Release-Symbole hochladen

Legen Sie `version`, `architecture` und `debugId` anhand unveränderlicher Werte aus der Release-Pipeline fest. Verwenden Sie dieselben Werte für alle Debug-Artefakte,
die dieser Build erzeugt. Zur Laufzeit ermittelte oder abgeleitete Ersatzwerte sind für die Entwicklung nützlich, liefern aber für Produktions-Builds keine stabile
Kennung für die Symbolzuordnung.

Erstellen Sie Android- und iOS-Releases mit `--obfuscate` und `--split-debug-info` und übergeben Sie die Kennung mit `--dart-define`:

```bash
flutter build apk \
  --release \
  --obfuscate \
  --split-debug-info=build/molesignal-symbols/android-arm64 \
  --target-platform=android-arm64 \
  --dart-define=MOLESIGNAL_VERSION=1.4.0+42 \
  --dart-define=MOLESIGNAL_ARCHITECTURE=arm64 \
  --dart-define=MOLESIGNAL_DEBUG_ID="$BUILD_ID"
```

Mit `--split-debug-info` enthält jeder Fehler-Frame `artifact_kind: flutter_symbols`, die absoluten und relativen Adressen, die eine Symboldatei auflöst,
und die beim Build konfigurierte `debug_id`. Laden Sie jede erzeugte `.symbols`-Datei mit `kind=flutter_symbols`, der passenden Plattform `android` oder
`ios`, der kanonischen Architektur und der Debug-ID hoch. Laden Sie native Android-ELF-Symbole und Apple-dSYM-DWARF-Dateien separat hoch, wenn der SDK
native Absturz-Frames mit `RumStackFrame` weiterleitet.

Für den Upload von Artefakten ist ein Verwaltungstoken mit `debug_artifacts.manage` erforderlich. Verwenden Sie für die Artefaktverwaltung niemals das an die Anwendung gebundene Client-Token.

## Session Replay aktivieren

Flutter hat kein DOM. Aus dem ersten erfassten Frame entstehen die rrweb-Ereignisse `Meta` und `FullSnapshot`. Aus geänderten Frames entstehen inkrementelle
Bildänderungen. Unveränderte Frames überspringt der SDK. Der vorhandene MoleSignal-Replay-Player kann deshalb Browser- und Flutter-Sitzungen
auf dieselbe Weise wiedergeben.

```dart
const RumConfiguration(
  // ...
  sessionReplaySampleRate: 20,
  sessionReplay: RumSessionReplayConfiguration(
    captureInterval: Duration(seconds: 2),
    captureOnAction: true,
    pixelRatio: 0.75,
    maximumImageDimension: 1200,
  ),
)

rum.startSessionReplayRecording();
rum.stopSessionReplayRecording();
```

`sessionReplaySampleRate` gilt nur für Sitzungen, die `sessionSampleRate` in die Stichprobe aufnimmt. Multiplizieren Sie beide Raten, um den tatsächlichen Anteil der Sitzungen mit Replay zu berechnen.
Auch die manuelle Aufzeichnung gilt nur für Sitzungen in der Stichprobe. Session Replay verwendet eine separate Warteschlange, ein Standard-Sendeintervall von 10 Sekunden,
Sequenznummern pro Sitzung, eine Zielgröße von etwa 1 MiB pro Segment und ein Limit von 8 MiB pro Anfrage. Der SDK sendet Segmente an `POST /api/v1/rum/replay`.

## Replay-Inhalte schützen

Standardmäßig maskiert `RumPrivacyLevel.mask` die Inhalte von `Text`, `RichText` und bearbeitbaren Bereichen vor der PNG-Kodierung. Eingabefelder bleiben auch im Modus `allow` maskiert.
Der SDK entfernt außerdem Query-Strings und Fragmente aus URLs und blendet gängige sensible Kontextschlüssel rekursiv aus. Unbearbeiteten Stack-Text sendet der SDK nur mit
`RumPrivacyLevel.allow`. Andernfalls baut der SDK `error.stack` aus den bereinigten Frames neu auf. Umschließen Sie sensible Bilder, Karten, benutzerdefiniert gezeichnete Inhalte,
Plattform-Views oder ganze Komponenten mit einer expliziten Datenschutzgrenze:

```dart
RumReplayBlock(
  child: AccountBalanceCard(),
)
```

Sowohl `RumReplayMask` als auch `RumReplayBlock` ersetzen den erfassten Bereich durch einen undurchsichtigen Block. Unmaskierte Rohpixel gelangen nie in die Ereigniswarteschlange.

<Warning>
  Der SDK kann anhand des Widget-Typs nicht erkennen, ob `CustomPainter` Text zeichnet. Umschließen Sie den benutzerdefiniert gezeichneten
  Bereich explizit. Die Erfassung von Plattform-Views hängt davon ab, wie die Plattform die Ansicht zusammensetzt. Prüfen Sie sensible
  Plattform-Views auf echten Android- und iOS-Geräten.
</Warning>

## Übermittlung

Der SDK fasst Ereignisse in einem JSON-Array zusammen und sendet es mit dem Client-Token an `POST {site}/api/v1/rum/events`. Batches mit mehr als 1 KiB
komprimiert der SDK mit gzip, sofern `dart:io` verfügbar ist. Deaktivieren Sie die Komprimierung mit `compressRequests: false`. Eine Anfrage enthält höchstens 48 KiB Ereignisdaten und bleibt damit weit unter
den 5000 Ereignissen und 5 MiB, die der Empfänger akzeptiert.

- Wenn MoleSignal ein Ereignis **ablehnt**, meldet der SDK es über `onError` und `RumFlushResult` und sendet es nicht erneut.
- Bei Netzwerkfehlern, Zeitüberschreitungen, `408`, `429` und `5xx` wiederholt der SDK die Anfrage mit exponentiell steigenden Wartezeiten und zufälliger Abweichung, jedoch frühestens nach der vom Empfänger per `Retry-After`
  vorgegebenen Wartezeit. Die Ereignisse bleiben in einer persistenten Offline-Warteschlange erhalten.
- Bei jedem anderen `4xx`-Status verwirft der SDK den Batch.

Die Warteschlange begrenzt die Anzahl, die Gesamtgröße und das Alter der Einträge (`maxQueueSize`, `maxQueueBytes`, `queueItemTtl`). Eine neuere Revision einer View ersetzt
ältere Revisionen in der Warteschlange. Daher kann MoleSignal Lücken in den Revisionsnummern sehen.

## Hauptkonfiguration

| Option | Standardwert | Zweck |
|---|---|---|
| `applicationId`, `clientToken`, `site` | Erforderlich | Anwendungskennung, Authentifizierung und Endpunkt |
| `service` | `applicationId` | Service, den der SDK in den Ereignissen speichert |
| `env`, `user`, `globalContext` | Nicht festgelegt | Deployment, Identität und benutzerdefinierte Dimensionen |
| `version`, `buildVersion` | `unknown`, nicht festgelegt | Release-Kennung für die Zuordnung von Debug-Artefakten und Build-Nummer |
| `architecture`, `debugId` | Erkannt oder als Ersatzwert abgeleitet | Kennung des mobilen Builds für die Symbolzuordnung |
| `sessionSampleRate` | `100` | Anteil der Sitzungen in der Stichprobe in Prozent |
| `sessionReplaySampleRate` | `0` | Anteil der Sitzungen mit Replay innerhalb der Stichprobe in Prozent |
| `sessionReplay` | Datenschutzfreundliche Standardwerte | Erfassungsintervall, Auflösung, Erfassung von Aktionen und Maskenfarbe |
| `trackUserInteractions` | `false` | Automatische Erfassung von Taps und `back`-Aktionen |
| `trackFrustrations` | Einstellung für die Interaktionserfassung | Erkennung von `rage_tap` und `error_tap` |
| `trackResources` | `true` | Erfassung von HTTP-Ressourcen |
| `trackLongTasks` | `true` | Erfassung langsamer und eingefrorener Frames als Long Tasks |
| `trackViewPerformance` | `true` | Metriken zu Start, erstem Build, Frames und Speicher |
| `trackDeviceInfo` | `true` | Marke, Modell, Akkustatus und Konnektivität über Plugins |
| `trackFlutterErrors`, `trackPlatformErrors` | `true` | Fehler im Framework und im Root-Isolate |
| `trackAppLifecycle` | `true` | Beim Wechsel in den Hintergrund beendet der SDK die Views und sendet ausstehende Ereignisse |
| `trackAnonymousUser` | `true` | Persistente anonyme Identität |
| `trackUrlQueryString` | `false` | Bei Aktivierung bleiben URL-Query-Strings erhalten |
| `defaultPrivacyLevel` | `mask` | Datenschutzregeln für Replay-Text und unbearbeitete Stack-Traces |
| `sessionInactivityTimeout`, `maxSessionDuration` | `15 min`, `4 h` | Zeitlimits für Sitzungen |
| `flushInterval`, `batchSize` | `5 s`, `50` | Standardübermittlung von Ereignissen |
| `replayFlushInterval`, `replayBatchSize` | `10 s`, `100` | Übermittlung von Replay-Ereignissen |
| `beforeSend` | Nicht festgelegt | Ereignisse jedes Typs einschließlich Replay ändern oder verwerfen |

`RumSessionReplayConfiguration` verwendet standardmäßig ein Erfassungsintervall von 5 Sekunden, erfasst Frames nach Aktionen und nutzt `0.5` Ausgabepixel pro logischem Pixel,
eine maximale Bildkantenlänge von 900 Pixeln und die Maskenfarbe `#6B7280`. Konfigurieren lassen sich auch `excludedUrls`, `allowedTracingUrls`, Warteschlangenlimits, Wartezeiten für Wiederholungsversuche, Zeitlimits,
Diagnose, benutzerdefinierte Übermittlung und Persistenz.

## Ereigniswarteschlangen leeren und SDK stoppen

Rufen Sie `flush()` vor einem kontrollierten Übergang auf, der auf die Verarbeitung der Ereignisse in der Warteschlange warten muss. Rufen Sie beim endgültigen Abbau `stop()` auf, um die aktive Ansicht
mit einem letzten Bericht zu beenden, die Instrumentierung zu entfernen und beide Ereigniswarteschlangen zu leeren. Beide Methoden geben ein `RumFlushResult` zurück. Es unterscheidet angenommene Ereignisse, Ereignisse mit erneutem Sendeversuch,
verworfene Ereignisse, verbleibende Ereignisse und Ereignisse mit Zeitüberschreitung.

```dart
await rum.flush();
await rum.stop();
```
