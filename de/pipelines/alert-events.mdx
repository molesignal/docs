Eine **Alert-Pipeline** verarbeitet Alarmereignisse, bevor sich die zugehörigen Incidents öffnen. Ihre Schritte können den Titel des Incidents umschreiben, den Schweregrad ändern, Labels und Annotationen hinzufügen oder entfernen, betroffene Dienste benennen oder das Ereignis verwerfen, sodass sich kein Incident öffnet. [Routing](/de/alerting/routing) und Benachrichtigungen verwenden anschließend den Incident in dem Zustand, in dem ihn die Pipelines hinterlassen haben.

Ein Alarmereignis stammt aus einer von vier Quellen:

| Quelle | Ereignisse |
|---|---|
| **Alarmregeln** | Eine [Alarmregel](/de/alerting/rules) löst aus. |
| **Externe Quellen** | Eine [Alarmquelle](/de/alerting/sources) empfängt einen Alarm von einem anderen System. |
| **Synthetische Prüfungen** | Eine [synthetische Prüfung](/de/synthetics#alarmvorfälle) schlägt fehl oder liefert keine Ergebnisse. |
| **Keine Daten** | Eine Regel öffnet einen [Incident aufgrund fehlender Daten](/de/alerting/rules#entwarnung-und-fehlende-daten). |

Wenn Sie einen Incident manuell öffnen, durchläuft er vorher keine Alert-Pipelines.

Eine Pipeline kann auch [vor einer Benachrichtigung](#vor-einer-benachrichtigung) laufen. Sie verarbeitet dann eine Kopie des Ereignisses und ändert nur, was eine einzelne Benachrichtigungsrichtlinie sendet.

## Alert-Pipeline erstellen

Öffnen Sie **Pipelines**, wählen Sie **Neue Pipeline** und stellen Sie den **Ausführungsmodus** auf **Alarmereignisse**. Unter **Signaltyp** steht **Alarmereignisse**. In den Einstellungen legen Sie statt eines Zeitplans die [**Reihenfolge**](#reihenfolge) fest. Der Ablauf besteht aus drei Knoten:

| Knoten | Bedeutung |
|---|---|
| **Alarmereignisse** | Die Alarmereignisse, die die Pipeline verarbeitet. Siehe [Bedingungen](#bedingungen). |
| **In Bearbeitung** | Die Schritte in der Reihenfolge ihrer Ausführung. Siehe [Schritte](#schritte). |
| **In den Incident zurückschreiben** | Der Incident öffnet sich mit den Ereignisdaten, die nach den Schritten vorliegen. |

Mit **Testen** führen Sie die Schritte vor dem Speichern an einem Beispiel für ein Alarmereignis aus. Die Schritte behandeln es als Ereignis einer Alarmregel, deren Incident sich gleich öffnet: `%source` ist `rule` und `%event` ist `opened`. Bearbeiten Sie das **Beispielereignis**, um andere Werte auszuprobieren, und wählen Sie dann **Test ausführen**. Das Ergebnis zeigt das Ereignis nach jedem Schritt oder den Schritt, der es verworfen hat. Der Test speichert nichts und ruft keine externen Dienste auf: Die Schritte **KI-Zusammenfassung** und **Abfrageergebnisse hinzufügen** schreiben `…` in ihre Annotationen. Der Schritt **API aufrufen** gibt das Ereignis unverändert weiter und trägt den Hinweis **im Test nicht aufgerufen**.

**Aktuelles Alarmereignis verwenden** zeigt mit der Berechtigung `alerts.incidents.read` die 20 neuesten Incidents der letzten 7 Tage an. Wählen Sie einen Incident aus, um sein Ereignis als **Beispielereignis** zu übernehmen. Die Schritte lesen dessen Regel und Quelle aus. Der Incident liegt in seinem gespeicherten Zustand vor und enthält daher bereits die Änderungen, die die Pipelines beim Öffnen vorgenommen haben.

Mit dem Schalter **Alarmereignisse verarbeiten** in den Einstellungen schalten Sie die Pipeline ein oder aus. Eine ausgeschaltete Pipeline lässt alle Alarmereignisse unverändert passieren. Wählen Sie **Pipeline erstellen**, um zu speichern. Eine gespeicherte Änderung erreicht innerhalb von 10 Sekunden alle Knoten.

## Bedingungen

Wählen Sie den Knoten **Alarmereignisse** aus, um festzulegen, welche Ereignisse die Pipeline verarbeitet:

- **Quellen**: **Alarmregeln**, **Externe Quellen**, **Synthetische Prüfungen** und **Keine Daten**. Ein Incident, den eine Regel wegen fehlender Daten öffnet, zählt als **Keine Daten**, nicht als **Alarmregeln**. Ein Incident aufgrund einer synthetischen Prüfung ohne Ergebnisse zählt als **Synthetische Prüfungen**.
- **Schweregrade**: **Kritisch**, **Fehler**, **Warnung** und **Info**.
- **Labels**: Mit **Label-Bedingung hinzufügen** fügen Sie ein Label und einen Wert hinzu. Das Ereignis muss jedes angegebene Label mit genau diesem Wert enthalten.
- **Zeit**: **Jederzeit**, **Nur innerhalb dieser Zeiten** oder **Nur außerhalb dieser Zeiten**. Die Zeitfenster wiederholen sich wöchentlich und gelten für eine Zeitzone. Entscheidend ist der Zeitpunkt, zu dem sich der Incident öffnet. Verwerfen Sie zum Beispiel eine bestimmte Art von Alarm nur während der zwei Stunden, in denen ein nächtlicher ETL-Job läuft.

Mit **Wann** legen Sie oberhalb der Bedingungen fest, wann die Pipeline läuft: **Vor dem Öffnen des Incidents** (Standard) oder [**Vor einer Benachrichtigung**](#vor-einer-benachrichtigung).

Wenn Sie in einer Liste nichts auswählen, berücksichtigt die Pipeline alle Quellen bzw. alle Schweregrade. Ohne Bedingungen verarbeitet sie alle Alarmereignisse. Erfüllt ein Ereignis die Bedingungen nicht, passiert es die Pipeline unverändert.

## Reihenfolge

Alert-Pipelines laufen nacheinander, beginnend mit dem niedrigsten Wert unter **Reihenfolge**. Bei gleichem Wert laufen die Pipelines in der Reihenfolge ihrer Namen. Jede Pipeline übernimmt das Ereignis so, wie es die vorherigen Pipelines hinterlassen haben, und prüft daran ihre Bedingungen. Wenn eine Pipeline den Schweregrad erhöht, kann das Ereignis dadurch die Bedingungen einer späteren Pipeline erfüllen.

## Schritte

**Schritt hinzufügen** bietet die Schritte zum Parsen und zur Feldbearbeitung aus anderen Pipelines, einschließlich **In Erweiterungstabelle nachschlagen**, sowie **Ereignisse filtern**, **KI-Zusammenfassung**, **API aufrufen**, **Abfrageergebnisse hinzufügen** und **Benutzerdefinierter VRL-Code**. Siehe [Verarbeitungsschritte](/de/pipelines#verarbeitungsschritte). In einer Alert-Pipeline setzen **Nach Muster umbenennen** und **Nur diese Felder behalten** bei `labels` an. Eine Alert-Pipeline zieht keine Stichproben und leitet keine Ereignisse weiter: Wenn Sie eine Pipeline in eine Alert-Pipeline umwandeln, entfernen Sie vor dem Speichern vorhandene Schritte vom Typ **Stichprobe** oder **An Stream weiterleiten**.

### Das Alert-Ereignis

Die Schritte erhalten das Alert-Ereignis als JSON:

```json
{
  "summary": "Checkout error rate above 5%",
  "severity": "error",
  "labels": { "service": "checkout", "env": "prod", "host_name": "web-01" },
  "annotations": { "runbook": "https://wiki.example.com/checkout" },
  "affected_services": ["checkout"]
}
```

| Feld | Inhalt | Was ein Schritt festlegen darf |
|---|---|---|
| `summary` | Der Titel des Incidents. | Nicht leerer Text. Die Pipeline kürzt den Text auf 512 Zeichen. |
| `severity` | Der Schweregrad des Incidents. | `info`, `warning`, `error` oder `critical`, unabhängig von der Groß- und Kleinschreibung. Die Pipeline interpretiert `warn` als `warning` und `crit` als `critical`. |
| `labels` | Die Labels des Incidents. | Ein Objekt mit Textwerten. Die Pipeline wandelt Zahlen und boolesche Werte in Text um. `null` entfernt das Label. |
| `annotations` | Die Annotationen des Incidents. | Dieselben Regeln wie für `labels`. |
| `affected_services` | Die Namen der betroffenen Dienste. | Eine Liste von Namen. Die Pipeline entfernt doppelte und leere Namen. |

Die Pipeline ignoriert zusätzliche Felder. Entfernt ein Schritt eines der aufgeführten Felder, behält es seinen Wert: Setzen Sie `.labels = {}`, um die Labels zu leeren. Verstößt ein Wert gegen diese Regeln, etwa ein Objekt in `labels`, schlägt die Pipeline fehl. Siehe [Was mit einem Ereignis passiert](#was-mit-einem-ereignis-geschieht).

Labels, die MoleSignal selbst setzt, etwa `alert.source` und `external.kind`, bleiben unverändert, da sie die Herkunft des Incidents angeben. Schritte können diese Labels lesen.

### Woher das Ereignis stammt

Ein Schritt liest die Herkunft des Ereignisses aus den Metadaten. Die Werte erscheinen nicht als Felder im Incident.

| Metadaten | Wert |
|---|---|
| `%source` | `rule`, `external`, `synthetic` oder `no_data`. |
| `%rule_id` | Die ID der Regel, der Alert-Quelle oder der synthetischen Prüfung. |
| `%rule_name` | Der Name der Regel, der Alert-Quelle oder der synthetischen Prüfung. |
| `%event` | `opened` vor dem Öffnen des Incidents und `severity_changed`, wenn die Quelle bei offenem Incident erneut auslöst. Siehe [Änderungen des Schweregrads](#schweregradänderungen). |

```ruby
# alerts from staging page no higher than warning
if .labels.env == "staging" && (.severity == "critical" || .severity == "error") {
  .severity = "warning"
}

# the team that owns the host, from the extend table host_owner
owner = lookup("host_owner", .labels.host_name)
if is_object(owner) {
  .labels.team = owner.team
}

# a known false alarm opens no incident
if %rule_name == "Disk inode usage" && .labels.mount == "/boot" {
  abort
}
```

Das Label `team` aus dem zweiten Schritt kann den Incident an das angegebene Team weiterleiten. Siehe [Routing-Reihenfolge](/de/alerting/routing#routing-reihenfolge). `lookup` und `geoip_lookup` funktionieren in Alert-Pipelines wie in jedem VRL-Schritt. Siehe [Tabellen und IP-Adressen nachschlagen](/de/functions#daten-zu-schlüsseln-und-ip-adressen-nachschlagen).

### KI-Zusammenfassung

Der Schritt **KI-Zusammenfassung** sendet das Alert-Ereignis in der von den vorherigen Schritten bearbeiteten Form zusammen mit dem **Prompt** an das Modell der Organisation. Der Schritt schreibt die Antwort in die unter **Annotation** angegebene Annotation, standardmäßig `ai_summary`. Ein Prompt kann so aussehen:

```text
Summarize this alert for the on-call engineer in two sentences: what is wrong, and what to check first.
```

- Der Schritt fragt das Modell einmal beim Öffnen des Incidents ab. Bei einer [Änderung des Schweregrads](#schweregradänderungen) fragt der Schritt das Modell nicht erneut ab.
- Der Schritt nutzt das **Standardmodell** des zuletzt aktualisierten aktivierten [Modellanbieters](/de/agent#modellanbieter-einrichten) mit API-Schlüssel. Die Antwort umfasst höchstens die unter **Max. Ausgabetokens** festgelegte Anzahl an Tokens. Ohne diese Einstellung gilt eine Obergrenze von 512 Tokens.
- Der Schritt sendet Titel, Schweregrad, Labels, Annotationen und betroffene Dienste des Alerts an den Modellanbieter.
- Die Aufrufe zählen zum [täglichen Tokenbudget](/de/agent#nutzung-und-budget) der Organisation und erscheinen in der Nutzung nach Quelle als **LLM-Funktionen**. `[functions].llm_eval_enabled` gilt für diese Aufrufe nicht.
- Kann das Modell nicht antworten, weil kein Anbieter eingerichtet ist, das Tagesbudget aufgebraucht ist oder der Aufruf fehlschlägt, schlägt der Schritt fehl. Damit schlägt die gesamte Pipeline fehl und verwirft auch ihre übrigen Änderungen. Legen Sie für **KI-Zusammenfassung** eine eigene Pipeline an und ordnen Sie diese nach den anderen Pipelines ein, damit deren Änderungen auch bei einem Fehlschlag erhalten bleiben.

### API aufrufen

Der Schritt **API aufrufen** sendet das Alert-Ereignis per POST an einen der [HTTP-Konnektoren](/de/connectors#ziele) der Organisation und übernimmt die Änderungen aus der Antwort. Der Schritt nutzt die Adresse und die Zugangsdaten des Konnektors und wendet dessen Prüfungen für ausgehende Verbindungen an: Er löst zuerst den Hostnamen auf, verwendet für die Verbindung nur die ermittelte Adresse, lehnt Cloud-Metadatenadressen ab und folgt keinen Weiterleitungen.

Der Request-Body enthält die Ereignisfelder in der von den vorherigen Schritten bearbeiteten Form sowie die Herkunft des Ereignisses:

```json
{
  "summary": "Checkout error rate above 5%",
  "severity": "error",
  "priority": null,
  "urgency": null,
  "labels": { "service": "checkout" },
  "annotations": {},
  "affected_services": ["checkout"],
  "metadata": { "rule_id": "…", "rule_name": "Checkout errors", "source": "rule", "event": "opened" }
}
```

- Aus dem JSON-Objekt der Antwort übernimmt der Schritt nur `summary`, `severity`, `priority`, `urgency`, `labels`, `annotations` und `affected_services` nach den Regeln unter [Das Alert-Ereignis](#das-alert-ereignis). Der Schritt führt `labels` und `annotations` schlüsselweise zusammen. `null` entfernt den jeweiligen Schlüssel. Ein Dienst kann daher nur die Änderungen zurückgeben. Eine leere Antwort ändert nichts.
- Für den Aufruf stehen 5 Sekunden zur Verfügung. Der Schritt ruft die API einmal beim Öffnen des Incidents auf. Bei einer [Änderung des Schweregrads](#schweregradänderungen) erfolgt kein weiterer Aufruf.
- Schlägt der Aufruf fehl, gilt nur dieser Schritt als nicht ausgeführt. Das gilt bei einer Zeitüberschreitung, einem Statuscode außerhalb von 2xx, einem Antwort-Body, der kein JSON-Objekt ist oder größer als 1 MiB ist, einem ungültigen Feld oder einem deaktivierten oder nicht mehr vorhandenen Konnektor. Das Ereignis geht unverändert an die nachfolgenden Schritte weiter. Änderungen aus vorherigen Schritten bleiben erhalten. Die [Zeitleiste](#was-mit-einem-ereignis-geschieht) und die [Zählwerte](#tageszähler) zeigen den Grund an.

### Abfrageergebnisse hinzufügen

Der Schritt **Abfrageergebnisse hinzufügen** führt eine Abfrage mit Werten aus dem Ereignis aus und schreibt die Ergebniszeilen in eine Annotation:

```sql
SELECT count(*) AS errors FROM app_logs WHERE level = 'error' AND host = '{{labels.host_name}}'
```

| Feld | Bedeutung |
|---|---|
| **Sprache** | SQL oder PromQL. PromQL liest aus einem Metrik-Stream. |
| **Stream-Typ**, **Stream** | Der Stream, aus dem die Abfrage liest. Der Schritt kann `_audit` nicht lesen, da bei seiner Ausführung keine `audit.read`-Berechtigung greift. |
| **Abfrage** | Eine einzelne Abfrage mit Platzhaltern. |
| **Rückblickzeitraum (Sekunden)** | Wie weit die Abfrage vom Zeitpunkt der Öffnung des Incidents zurückblickt. Standard: 300, maximal 86.400. |
| **Zeilen** | Anzahl der Zeilen, die der Schritt in die Annotation schreibt. Standard: 5, maximal 50. |
| **Annotation** | Die Annotation für die Ergebniszeilen, standardmäßig `query_result`. |

Ein Platzhalter steht für einen Wert aus dem Ereignis: `{{labels.<key>}}`, `{{annotations.<key>}}`, `{{summary}}`, `{{severity}}`, `{{priority}}`, `{{urgency}}`, `{{rule_id}}`, `{{rule_name}}` oder `{{source}}`. Da Labels aus anderen Systemen stammen können, müssen Platzhalter in der Abfrage innerhalb einer Zeichenfolge zwischen Anführungszeichen stehen. Dort maskiert der Schritt Sonderzeichen im eingesetzten Wert. Steht ein Platzhalter an einer anderen Stelle, schlägt das Speichern mit `400` fehl.

- Die Annotation enthält pro Ergebniszeile eine Textzeile: Einzelwerte stehen allein, mehrere Werte erscheinen als `column=value, column=value`. Die Annotation umfasst höchstens 4.000 Zeichen. Liefert die Abfrage keine Zeilen, lässt der Schritt die Annotation weg.
- Für die Abfrage stehen 10 Sekunden zur Verfügung. Der Schritt führt die Abfrage einmal beim Öffnen des Incidents aus.
- Schlägt die Abfrage fehl oder fehlt im Ereignis ein Wert für einen Platzhalter, gilt wie bei [**API aufrufen**](#api-aufrufen) nur dieser Schritt als nicht ausgeführt.

## Was mit einem Ereignis geschieht

Jede Pipeline, die ein Ereignis annimmt, endet mit einem von drei Ergebnissen:

| Ergebnis | Ursache | Auswirkung |
|---|---|---|
| **Verarbeitet** | Alle Schritte liefen bis zum Ende. | Das Ereignis wird mit den Änderungen weiterverarbeitet. |
| **Verworfen** | Ein Schritt führte `abort` aus. | Es wird kein Incident eröffnet, und die nachfolgenden Pipelines werden nicht ausgeführt. |
| **Fehlgeschlagen** | Ein Schritt schlug fehl, oder nach der Ausführung verstieß ein Feld gegen die Regeln unter [Das Alarmereignis](#das-alert-ereignis). Ein fehlgeschlagener Schritt vom Typ **API aufrufen** oder **Abfrageergebnisse hinzufügen** zählt ebenfalls dazu. | Die Änderungen dieser Pipeline entfallen. Schlägt jedoch nur ein solcher Schritt fehl, bleiben die Änderungen der übrigen Schritte erhalten. Das Ereignis geht an die nächste Pipeline, und der Incident wird trotzdem eröffnet. |

Die [Zeitleiste](/de/alerting/incidents#vorfalldetails) des Incidents enthält für jede Pipeline, die etwas geändert hat oder fehlgeschlagen ist, einen Eintrag: **Pipeline Payments routing durchlaufen: Schweregrad error → critical, Labels +team=payments**. Bei einem Fehler nennt der Eintrag den Grund. Pipelines ohne Änderungen und [Schweregradänderungen](#schweregradänderungen) erzeugen keinen Eintrag. Ein Eintrag zeigt bis zu 40 Änderungen und gibt die Anzahl der übrigen an. Lange Werte werden nach 200 Zeichen abgeschnitten.

Löst eine Regel weiterhin aus, verwirft die Pipeline das Ereignis bei jeder Auswertung erneut. Die [Regelliste](/de/alerting/rules#regelliste) zeigt den Status **Von der Pipeline verworfen** an. In der API lautet `last_state` für die Regel `{"kind": "dropped"}`. Die Pipeline zählt das verworfene Ereignis und nennt in der **Übersicht** die Regel des zuletzt verworfenen Ereignisses. Verwirft eine Pipeline einen externen Alarm, erscheint unter [**Zuletzt empfangen**](/de/alerting/sources#zuletzt-empfangen) bei der Alarmquelle der Status **Ignoriert**. Daneben stehen die Pipeline und der Schritt, der den Alarm verworfen hat.

## Schweregradänderungen

Solange ein Incident offen ist, bestimmen die Alarm-Pipelines seinen Schweregrad neu, sobald die Alarmregel erneut auslöst, die externe Quelle den Alarm erneut sendet oder sich der Status der synthetischen Prüfung ändert:

- MoleSignal erstellt das Ereignis wie bei der Eröffnung des Incidents, verwendet aber den aktuell von der Quelle gemeldeten Schweregrad. Das Ereignis durchläuft alle Pipelines, die es annehmen, jedoch ohne die Schritte **KI-Zusammenfassung**, **API aufrufen** und **Abfrageergebnisse hinzufügen**. `%event` hat den Wert `severity_changed`.
- MoleSignal übernimmt nur den Schweregrad, der nach den Schritten vorliegt. Weicht er vom aktuellen Schweregrad des Incidents ab, aktualisiert MoleSignal den Incident. Titel, Labels, Annotationen und Dienste bleiben auf dem Stand bei der Eröffnung.
- Verwirft eine Pipeline das Ereignis oder schlägt sie fehl, ändert sich nichts: Der Incident bleibt offen, und die nächste Pipeline wird ausgeführt.

Ein Schritt, der den Schweregrad von Staging-Alarmen senkt, senkt ihn also auch dann, wenn die Regel später einen höheren Schweregrad meldet. Bei bestätigten Incidents und Incidents mit manuell gesetztem Schweregrad bleibt der Schweregrad unverändert.

## Vor einer Benachrichtigung

Setzen Sie im Knoten **Alarmereignisse** die Option **Wann** auf **Vor einer Benachrichtigung**. Die Pipeline läuft dann auf einer Kopie des Ereignisses, bevor eine [Benachrichtigungsrichtlinie](/de/notification-channels) eine Nachricht dazu sendet. Das gilt für jede zutreffende Richtlinie und jeden Versand, auch in späteren Schritten und bei einer Eskalation. Kürzen Sie damit etwa den Titel für eine SMS-Richtlinie, fügen Sie für den Webhook eines Teams ein Label hinzu oder unterbinden Sie nachts den Versand über eine Richtlinie. Der Incident selbst bleibt unverändert.

- Wählen Sie unter **Benachrichtigungsrichtlinien** aus, für welche Richtlinien die Pipeline gilt. Ohne Auswahl gilt sie für alle Richtlinien, die auf das Alarmereignis zutreffen. Zu diesem Zeitpunkt steht bereits anhand des ursprünglichen Ereignisses fest, dass die Richtlinie zutrifft.
- Für die übrigen Bedingungen gilt weiterhin das Ereignis, auf dem die Benachrichtigung beruht. Als Zeitpunkt zählt der Zeitpunkt des Ereignisses. Unter **Quellen** steht zusätzlich **Manuell eröffnete Incidents** zur Auswahl.
- Alle Schritte laufen innerhalb von MoleSignal. **KI-Zusammenfassung**, **API aufrufen** und **Abfrageergebnisse hinzufügen** laufen nur beim Eröffnen eines Incidents. Enthält die Pipeline hier einen solchen Schritt, antwortet MoleSignal mit `400`.
- Der Ablauf endet in **In die Benachrichtigung**. Die Richtlinie verwendet Titel, Schweregrad, Priorität, Dringlichkeit, Labels, Annotationen und Dienste, die nach den Schritten vorliegen: in den [Vorlagen](/de/notification-channels#vorlagenvariablen), im Body der Webhooks und im Standardtext. Das ursprüngliche Ereignis bestimmt den Empfängerkreis.
- Führt ein Schritt `abort` aus, sendet die Richtlinie keine Benachrichtigung. Das Zustellprotokoll zeigt einen Eintrag mit dem Status **Übersprungen** und dem Grund an. Der Grund nennt die Pipeline und den Schritt in der Standardsprache des Arbeitsbereichs (`error_code` `dropped_by_pipeline`). Auch die Zeitleiste des Incidents vermerkt den unterdrückten Versand. Das zählt nicht als Fehler: Die Richtlinie unternimmt keinen weiteren Zustellversuch und setzt die Eskalation bei ausbleibender Bestätigung nicht fort.
- Schlägt eine Pipeline fehl, entfallen ihre Änderungen, und die Benachrichtigung wird unverändert gesendet. Der Fehler erscheint in den [Tageszählern](#tageszähler), nicht in der Zeitleiste.

Neben `%rule_id`, `%rule_name` und `%source` lesen die Schritte auch `%policy_id` und `%policy_name`. `%event` hat den Wert `triggered`, `escalated`, `acknowledged` oder `resolved`. `%rule_name` enthält den Namen der Regel. Hat keine Regel den Incident eröffnet, enthält die Variable den Titel des Ereignisses. **Testen** verwendet die Beispielwerte `triggered` und `On-call alerts`.

```ruby
# on-call alerts of the staging environment go out only for what is critical
if %policy_name == "On-call alerts" && .labels.env == "staging" && .severity != "critical" {
  abort
}
```

## Tageszähler

Für Alarm-Pipelines gibt es keine separaten Ausführungen und damit keinen Ausführungsverlauf. **Mehr → Nachverarbeitung** steht nicht zur Verfügung. Stattdessen zählt die Pipeline die Ergebnisse des laufenden Tages (UTC):

- In der Liste lautet der **Status** einer aktivierten Alarm-Pipeline **Wartet auf Alarmereignisse**. Die Spalte **Letzte Ausführung** zeigt die Zählerstände an, etwa **Heute: 41 verarbeitet · 3 verworfen · 0 fehlgeschlagen**.
- In der **Übersicht** der Pipeline zeigen **Verarbeitet**, **Verworfen** und **Fehlgeschlagen** dieselben Zählerstände an. **Verworfen** nennt die Regel oder Quelle und den Zeitpunkt des zuletzt verworfenen Ereignisses. **Fehlgeschlagen** zeigt den Grund des letzten Fehlers an.

Um Mitternacht (UTC) beginnen die Zähler wieder bei null. Ereignisse, die die Bedingungen nicht erfüllen, und Durchläufe für eine [Schweregradänderung](#schweregradänderungen) zählen nicht mit. Die API gibt die Zählerstände als `alert_record` zurück. Siehe [Pipelines verwalten](/de/api/intake/scheduled-pipelines#abrufen).

## Grenzwerte

| Grenzwert | Wert |
|---|---|
| Schritte pro Alarm-Pipeline | 20 |
| Prompt eines Schritts vom Typ **KI-Zusammenfassung** | 8 KiB |
| Name einer Annotation | 255 Bytes |
| Antwort eines Schritts vom Typ **API aufrufen** | 1 MiB, innerhalb von 5 Sekunden |
| Abfrageanweisung eines Schritts vom Typ **Abfrageergebnisse hinzufügen** | 8 KiB |
| Ergebniszeilen eines Schritts vom Typ **Abfrageergebnisse hinzufügen** | 50, innerhalb von 10 Sekunden |

## Alarm-Pipeline über die API erstellen

Speichern Sie eine Alarm-Pipeline wie jede andere Pipeline. Setzen Sie `functionSteps.mode` auf `alert` und lassen Sie Streams und Zeitplan leer:

```bash
curl -X POST http://localhost:5080/api/v1/scheduled_pipelines \
  -H "authorization: Bearer $MS_TOKEN" \
  -H 'content-type: application/json' \
  -d '{
    "name": "staging-alerts",
    "sourceStream": "",
    "targetStream": "",
    "cron": "",
    "enabled": true,
    "functionSteps": {
      "mode": "alert",
      "alert": {
        "sources": ["rule", "external"],
        "severities": [],
        "labels": { "env": "staging" },
        "order": 10
      },
      "steps": [
        { "transformName": "cap-severity", "kind": "vrl",
          "script": "if .severity == \"critical\" { .severity = \"warning\" }" },
        { "transformName": "summary", "kind": "ai_summary",
          "prompt": "Summarize this alert in two sentences for the on-call engineer.",
          "annotation": "ai_summary" }
      ]
    }
  }'
```

Setzen Sie für eine Pipeline, die vor Benachrichtigungen läuft, `alert.stage` auf `notify`. Geben Sie bei Bedarf die Richtlinien in `alert.policies` an:

```json
{
  "mode": "alert",
  "alert": { "stage": "notify", "policies": ["<policy id>"], "labels": { "env": "staging" }, "order": 10 },
  "steps": [
    { "transformName": "quiet", "kind": "vrl", "script": "if .severity != \"critical\" { abort }" }
  ]
}
```

Unter [Pipeline erstellen](/de/api/intake/create-pipeline) finden Sie alle Felder. Für Alarm-Pipelines gelten dieselben [Berechtigungen wie für alle anderen Pipelines](/de/pipelines#berechtigungen).
