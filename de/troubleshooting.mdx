Prüfen Sie zuerst das Prozesslog. Es nennt die Ursache eines Startfehlers. Bei einer abgelehnten Anfrage enthält der HTTP-Antworttext eine Fehlermeldung. `[telemetry].log_level` oder `RUST_LOG` legt den Log-Level fest.

## Start

| Symptom | Ursache | Lösung |
|---|---|---|
| `... password authentication failed for user` | Der Benutzername oder das Passwort im DSN ist falsch. | Korrigieren Sie `[meta_database].dsn`. |
| `... pool timed out while waiting for an open connection` | Der Knoten erreicht PostgreSQL nicht. | Prüfen Sie Host, Port, Firewall und die Anforderungen an `sslmode`. |
| `startup_ping put: ... SignatureDoesNotMatch` | Der Objektspeicher lehnt die Zugangsdaten ab. | Prüfen Sie `access_key` und `secret_key`. Legen Sie die Werte mit `MS_OBJECT_STORE_ACCESS_KEY` und `MS_OBJECT_STORE_SECRET_KEY` fest. |
| `startup_ping put: ... NoSuchBucket` | Der Bucket existiert nicht. | Erstellen Sie den Bucket oder korrigieren Sie `[object_store].bucket`. |
| Wiederholt `Encountered transport error`, danach beendet sich der Prozess | Der Client erreicht den Endpunkt nicht oder erhält keine Zugangsdaten. | Prüfen Sie `endpoint`, DNS und das Netzwerk. Der Client muss die Zugangsdaten aus `access_key` und `secret_key` beziehen. |
| `unknown field: found ...` | Ein Schlüssel in einem Abschnitt mit strikter Validierung ist falsch geschrieben oder nicht unterstützt. | Entfernen oder korrigieren Sie den Schlüssel. Siehe [Konfiguration](/de/configuration#so-lädt-molesignal-die-konfiguration). |
| `MS_SELF_TELEMETRY_CLUSTER_TOKEN must be set when split-role self intake is enabled` | Bei getrennten Rollen startet ein Knoten ohne die Rolle `intake` und ohne gemeinsames Token, obwohl die Trace-Erfassung oder die Erfassung eigener Telemetriedaten aktiv ist. | Legen Sie auf jedem Knoten dasselbe Token fest. Es reicht nicht aus, nur `[telemetry.self_collect]` zu deaktivieren, da die Trace-Erfassung standardmäßig aktiv ist. |
| `open Probe CA key` | `MS_CIPHER_KEY` stimmt nicht mit dem Schlüssel überein, mit dem die Datenbank verschlüsselt wurde. | Stellen Sie den ursprünglichen Schlüssel wieder her. Siehe [Checkliste für den Produktionsbetrieb](/de/deployment/production-checklist). |
| `migration ... was previously applied but is missing in the resolved migrations` oder `... has been modified` | Die Binärdatei und die Datenbank stammen aus inkompatiblen Versionen. | Verwenden Sie die passende Version oder stellen Sie ein Backup wieder her. Siehe [Upgrade](/de/upgrade). |
| `address already in use` | Ein anderer Prozess verwendet einen konfigurierten Port. | Ändern Sie den Port. |
| `profiling.port and ... are both ...` | Der pprof-Listener teilt sich einen Port mit einem anderen Listener. | Legen Sie für `[profiling].port` einen Port fest, den kein anderer Listener verwendet. |
| Eine Einstellung aus einer Umgebungsvariablen bleibt wirkungslos | Der Variablenname enthält einen Punkt, zwei aufeinanderfolgende Unterstriche oder einen Tippfehler. | Verbinden Sie die Pfadsegmente mit jeweils einem Unterstrich, wie in `MS_META_DATABASE_DSN`. |

## Anmeldung

| Symptom | Ursache | Lösung |
|---|---|---|
| Die Anmeldung mit `admin@example.com` und `admin` schlägt fehl | Die Datenbank enthielt bereits Benutzerkonten, daher hat MoleSignal das Root-Konto nicht erneut angelegt. Oder `root_email` und `root_password` waren leer. | Melden Sie sich mit einem vorhandenen Konto an. Legen Sie beide Werte fest und starten Sie MoleSignal mit einer leeren Datenbank, um das Root-Konto anzulegen. |
| Die E-Mail zum Zurücksetzen des Passworts kommt nicht an | Die SMTP-Konfiguration oder `http.external_url` fehlt. MoleSignal nimmt die Anfrage an, sendet aber keine E-Mail. | Legen Sie `[notify.smtp].host` und `[http].external_url` fest. |
| Ein Skript meldet sich an, sendet `Authorization: Bearer` und erhält `401` | Bei der Anmeldung setzt MoleSignal Sitzungscookies für die Weboberfläche und gibt kein Token zurück. Der Header akzeptiert nur API-Tokens. | Erstellen Sie ein API-Token für das Skript. Siehe [API-Tokens](/de/identity/tokens). |
| Die Weboberfläche fordert täglich eine erneute Anmeldung an | Eine Sitzung endet nach der in `[auth].session_ttl_secs` festgelegten Dauer (24 Stunden). | Erhöhen Sie `[auth].session_ttl_secs`. |

## Daten senden

| Symptom | Ursache | Lösung |
|---|---|---|
| `401` | Das Token fehlt, ist ungültig oder der Header enthält ein Sitzungstoken aus der Anmeldung. | Senden Sie `Authorization: Bearer <token>` mit einem Standard-Token für die Datenaufnahme oder einem Token für ein Dienstkonto. |
| `403` | Dem Token fehlt die Schreibberechtigung für den Signaltyp, etwa `logs.write`. Das passiert beispielsweise, wenn ein RUM-Client-Token an einen Pfad für die Datenaufnahme gesendet wird. | Verwenden Sie ein Token mit Schreibberechtigung für den Signaltyp. |
| `413` | Der Anfrageinhalt überschreitet das Limit des Endpunkts: 16 MiB für die native JSON-Aufnahme, 2 MiB für die übrigen Endpunkte. | Senden Sie kleinere Batches. Erhöhen Sie das Limit des Proxys mindestens auf das Limit des Endpunkts. |
| `400` von einem Endpunkt für OTLP über HTTP | Der Sender hat den Anfrageinhalt komprimiert. | Legen Sie `compression: none` im Exporter des OpenTelemetry Collectors fest. |
| `404` von einem Endpunkt für OTLP über HTTP | Im Exporter-Endpunkt fehlt der Basispfad `/api`. Deshalb gehen Anfragen an `/v1/logs`. | Verwenden Sie `http://host:5080/api` als OTLP-Endpunkt. |
| `429` mit `Retry-After` | Das Ratenlimit der Rolle `router` für die Organisation greift. | Senden Sie weniger Anfragen pro Zeiteinheit oder erhöhen Sie `[router.rate_limit]`. |
| Die native JSON-Aufnahme meldet Datensätze als `rejected` | Ein Feldwert entspricht nicht dem Stream-Schema, zum Beispiel `type mismatch on field level: expected Utf8, got Number`. Die Antwort nennt den Grund für jeden betroffenen Index. | Senden Sie den Datentyp, den der Stream bereits für dieses Feld verwendet. |
| `400` mit `event #1 must be a JSON object` | Das Array enthält ein Element, das kein JSON-Objekt ist. Der Endpunkt lehnt die gesamte Anfrage ab. | Senden Sie ein Array aus JSON-Objekten. |
| Promtail oder Grafana Alloy können keine Daten senden | Der Loki-Endpunkt dekodiert nur JSON. Diese Sender verwenden mit Snappy komprimiertes Protobuf. | Senden Sie die Daten über den OpenTelemetry Collector, Vector oder Fluent Bit. |
| Der Endpunkt nimmt Datensätze an, aber die Abfrage findet sie nicht | Die Abfrage verwendet einen anderen Stream-Namen oder -Typ oder schließt die Datensätze durch den gewählten Zeitraum aus. | Prüfen Sie den Stream-Namen und den Signaltyp. Hinweise zu Zeitstempeln finden Sie im nächsten Abschnitt. |

## Fehlende oder auffällige Daten

- **Zeitstempel.** `_timestamp` zählt Mikrosekunden seit der Unix-Epoche. Ein Wert in Sekunden, Millisekunden oder Nanosekunden ordnet Ereignisse dem falschen Jahr oder der fernen Zukunft zu. Abfragen für jüngere Zeiträume finden diese Ereignisse nicht. Lassen Sie `_timestamp` weg, um den Empfangszeitpunkt auf dem Server zu verwenden.
- **Zeitraum.** Eine Abfrage über einen langen Zeitraum läuft als asynchroner Job. Verwenden Sie für interaktive Abfragen einen begrenzten `timeRange`. Siehe [Abfragen](/de/query#zeitbereiche-und-asynchrone-jobs).
- **Aufbewahrung.** MoleSignal löscht Daten, sobald die Aufbewahrungsdauer des Streams abläuft. Hat ein Stream keine eigene Aufbewahrungsdauer, gilt der Standardwert unter **Einstellungen → Datenaufbewahrung**.
- **Stream-Typ.** Name und Typ identifizieren einen Stream. `default` kann gleichzeitig für Logs, Metriken und Traces existieren.

## Abfragen

| Symptom | Ursache | Lösung |
|---|---|---|
| Die Antwort lautet `202` und enthält eine `jobId` und einen `monitor`-Pfad | Die geschätzte Zeilenzahl erreicht `[querier].auto_async_threshold_rows`. Deshalb läuft die Abfrage als asynchroner Suchjob. Mit den Standardeinstellungen entspricht das einem Zeitraum von etwa 13,9 Stunden oder mehr. | Rufen Sie den `monitor`-Pfad wiederholt auf, bis der Job abgeschlossen ist. Rufen Sie dann `/results` für den Job auf. Grenzen Sie alternativ den Zeitraum ein oder senden Sie `Prefer: respond-sync`. Siehe [Abfragen](/de/query#zeitbereiche-und-asynchrone-jobs). |
| Der Flight SQL-Client kann keine Verbindung herstellen | `[flight_sql]` ist standardmäßig deaktiviert. | Setzen Sie `enabled = true`, geben Sie Port `5083` frei und verwenden Sie zur Authentifizierung ein API-Token. |

## Betrieb

| Symptom | Ursache | Lösung |
|---|---|---|
| `GET /api/v1/healthz` gibt `503` zurück | Der Objektspeicher ist nicht erreichbar. Der Antworttext enthält ein Feld `reason`. | Stellen Sie die Verbindung zum Objektspeicher wieder her. |
| Das WAL-Verzeichnis wächst | Das Leeren der Puffer schlägt fehl, meist weil der Objektspeicher nicht erreichbar ist. | Beheben Sie das Problem mit dem Objektspeicher. Die Datenaufnahme schreibt anschließend die gepufferten Daten. |
| Die Datenaufnahme antwortet mit `429` und `intake buffer memory limit exceeded` | Die Puffer des Prozesses belegen mehr Speicher als unter `[intake].max_buffer_memory_size` erlaubt, meist weil das Leeren der Puffer wiederholt fehlschlägt. | Suchen Sie die Ursache in den Logzeilen mit `intake flush failed` und beheben Sie das Problem mit dem Objektspeicher oder der Datenbank. Zeilen, die sich nicht mehr veröffentlichen lassen, zählen nicht mehr zum Limit (siehe die nächsten beiden Tabellenzeilen). Bei der nativen JSON-Datenaufnahme enthält diese Antwort `Retry-After`. Warten Sie die angegebene Zeit ab und wiederholen Sie die Anfrage. |
| Im Log steht `dataset no longer exists; buffered rows discarded` | Ein Stream wurde gelöscht oder nach dem Löschen neu erstellt, während noch Zeilen daraus im Puffer lagen. Für diese Zeilen gibt es kein Ziel mehr. Die Datenaufnahme verwirft die Zeilen und gibt den belegten Speicher frei. Der Zähler `intake_flush_errors_total` erfasst jeden Verwerfvorgang unter dem Schritt `stream_gone` oder `dataset_gone`. | Keine Maßnahme erforderlich. Senden Sie die Daten bei Bedarf erneut. |
| Schreibanfragen erhalten `503` mit `fenced by a newer writer epoch` | Ein anderer Prozess veröffentlicht denselben Datensatz mit derselben `[node].id`. Der gesperrte Prozess kann seine Daten nicht veröffentlichen, verwirft die Zeilen im Arbeitsspeicher und lehnt Schreibanfragen für diesen Datensatz ab. Sein WAL bleibt auf dem Datenträger erhalten. Der Zähler `intake_flush_errors_total` erfasst die Sperre unter dem Schritt `writer_fenced`. | Weisen Sie jedem Prozess eine eindeutige `[node].id` zu und starten Sie den gesperrten Prozess neu. Siehe [Rollenbasierte Bereitstellung](/de/deployment/role-based). |
| Geplante PDF- oder PNG-Berichte schlagen fehl | Chrome fehlt oder die Weboberfläche ist unter `[scheduled_reports.renderer].base_url` nicht erreichbar. | Verwenden Sie das Release-Image mit Chromium und setzen Sie `base_url` auf die Adresse, unter der der Knoten die Weboberfläche erreicht. |
| Die Codebeispiele zur Einrichtung zeigen den falschen Host | Hinter einem Proxy ist `http.external_url` leer. | Setzen Sie `[http].external_url` auf die öffentliche Adresse und starten Sie den Dienst neu. |
| Abfragen erhalten `503` mit `no querier node is available` | Von keinem Knoten mit der Rolle `querier` liegt ein aktuelles Heartbeat-Signal vor. | Starten Sie einen Knoten mit der Rolle `querier` und prüfen Sie, ob der Router dessen `advertise_addr` erreichen kann. Siehe [Rollenbasierte Bereitstellung](/de/deployment/role-based#cluster-mitgliedschaft). |
| Schreibanfragen über den Router erhalten `503` mit `no intake node is available` | Von keinem Knoten mit der Rolle `intake` liegt ein aktuelles Heartbeat-Signal vor. | Starten Sie einen Knoten mit der Rolle `intake` und prüfen Sie dessen `advertise_addr`. Siehe [Rollenbasierte Bereitstellung](/de/deployment/role-based#cluster-mitgliedschaft). |
| Anfragen erhalten `503` mit `no metadata database connection` | Der Knoten hat 10 Sekunden lang auf eine PostgreSQL-Verbindung gewartet, aber keine erhalten. PostgreSQL ist überlastet oder nicht erreichbar, oder alle durch `[meta_database].max_connections` erlaubten Verbindungen sind belegt. | Wiederholen Sie die Anfrage. Falls der Fehler weiterhin auftritt, prüfen Sie zuerst die Auslastung und Erreichbarkeit von PostgreSQL. Wenn PostgreSQL nicht ausgelastet ist, erhöhen Sie `[meta_database].max_connections` entsprechend der Last, ohne `max_connections` von PostgreSQL zu überschreiten. |
| Der OTLP-gRPC-Port ist vom Host aus nicht erreichbar | Die Compose-Datei gibt Port `4317` nicht frei. | Fügen Sie die Portzuordnung `4317:4317` hinzu. |
