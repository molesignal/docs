Prüfen Sie zuerst das Prozesslog. Es gibt die Ursache eines Startfehlers aus, und der HTTP-Fehlerbody einer abgelehnten Anfrage enthält eine Meldung. Der Log-Level stammt aus `[telemetry].log_level` oder `RUST_LOG`.

## Start

| Symptom | Ursache | Behebung |
|---|---|---|
| `... password authentication failed for user` | Der DSN-Benutzer oder das Passwort ist falsch. | Korrigieren Sie `[meta_database].dsn`. |
| `... pool timed out while waiting for an open connection` | PostgreSQL ist vom Node aus nicht erreichbar. | Prüfen Sie den Host, den Port, die Firewall und die Anforderungen an `sslmode`. |
| `startup_ping put: ... SignatureDoesNotMatch` | Der Objektspeicher lehnt die Zugangsdaten ab. | Prüfen Sie `access_key` und `secret_key`. Setzen Sie sie mit `MS_OBJECT_STORE_ACCESS_KEY` und `MS_OBJECT_STORE_SECRET_KEY`. |
| `startup_ping put: ... NoSuchBucket` | Der Bucket existiert nicht. | Erstellen Sie den Bucket oder korrigieren Sie `[object_store].bucket`. |
| Wiederholte Zeilen mit `Encountered transport error`, dann Beendigung | Der Endpunkt ist nicht erreichbar, oder es erreichen keine Zugangsdaten den Client. | Prüfen Sie `endpoint`, DNS und das Netzwerk. Zugangsdaten müssen aus `access_key` und `secret_key` stammen. |
| `unknown field: found ...` | Ein Schlüssel in einem strikten Abschnitt ist falsch geschrieben oder nicht unterstützt. | Entfernen Sie den Schlüssel oder korrigieren Sie ihn. Siehe [Konfiguration](/de/configuration#so-lädt-molesignal-die-konfiguration). |
| `MS_SELF_TELEMETRY_CLUSTER_TOKEN must be set when split-role self intake is enabled` | Ein Rollen-Split-Node ohne die Rolle `intake` startet ohne das gemeinsame Token, während Trace-Erfassung oder Self-Collection aktiviert ist. | Setzen Sie dasselbe Token auf jedem Node. Das alleinige Deaktivieren von `[telemetry.self_collect]` reicht nicht aus, da die Trace-Erfassung standardmäßig aktiviert ist. |
| `open Probe CA key` | `MS_CIPHER_KEY` unterscheidet sich von dem Schlüssel, mit dem die Datenbank verschlüsselt wurde. | Stellen Sie den ursprünglichen Schlüssel wieder her. Siehe [Produktions-Checkliste](/de/deployment/production-checklist). |
| `migration ... was previously applied but is missing in the resolved migrations` oder `... has been modified` | Die Binärdatei und die Datenbank stammen aus inkompatiblen Versionen. | Führen Sie die passende Version aus, oder stellen Sie ein Backup wieder her. Siehe [Upgrade](/de/upgrade). |
| `address already in use` | Ein anderer Prozess verwendet einen konfigurierten Port. | Ändern Sie den Port. |
| `profiling.port and ... are both ...` | Der pprof-Listener teilt sich einen Port mit einem anderen Listener. | Setzen Sie `[profiling].port` auf einen Port, den kein anderer Listener verwendet. |
| Eine Einstellung aus einer Umgebungsvariable hat keine Wirkung | Der Variablenname enthält einen Punkt, einen doppelten Unterstrich oder einen Tippfehler. | Verbinden Sie den Pfad mit einzelnen Unterstrichen, wie in `MS_META_DATABASE_DSN`. |

## Anmeldung

| Symptom | Ursache | Behebung |
|---|---|---|
| `admin@example.com` mit `admin` wird abgelehnt | Die Datenbank enthielt bereits Benutzer, daher wurde das Root-Konto nicht erneut erstellt, oder `root_email` und `root_password` waren leer. | Melden Sie sich mit einem vorhandenen Konto an. Setzen Sie beide Werte und starten Sie gegen eine leere Datenbank, um das Root-Konto zu erstellen. |
| Die E-Mail zum Zurücksetzen des Passworts kommt nie an | SMTP oder `http.external_url` ist nicht konfiguriert. Die Anfrage wird angenommen, ohne dass etwas gesendet wird. | Setzen Sie `[notify.smtp].host` und `[http].external_url`. |
| Ein Skript, das sich anmeldet und `Authorization: Bearer` sendet, erhält `401` | Die Anmeldung setzt Session-Cookies für die Web-UI und gibt kein Token zurück. Der Header akzeptiert nur API Tokens. | Stellen Sie ein API Token für das Skript aus. Siehe [API Tokens](/de/identity/tokens). |
| Die Web-UI verlangt jeden Tag eine erneute Anmeldung | Eine Anmeldesitzung endet nach `[auth].session_ttl_secs` (24 Stunden). | Erhöhen Sie `[auth].session_ttl_secs`. |

## Daten senden

| Symptom | Ursache | Behebung |
|---|---|---|
| `401` | Das Token fehlt oder ist ungültig, oder der Header enthält ein Anmeldesitzungs-Token. | Senden Sie `Authorization: Bearer <token>` mit einem Standard-Intake-Token oder einem Service-Account-Token. |
| `403` | Dem Token fehlt die Schreibberechtigung des Signals, etwa `logs.write`, zum Beispiel bei einem RUM-Client-Token, das an einen Intake-Pfad gesendet wird. | Verwenden Sie ein Token mit der Schreibberechtigung des Signals. |
| `413` | Der Anfrage-Body überschreitet das Limit des Endpunkts: 16 MiB für native JSON-Intake, 2 MiB für die anderen. | Senden Sie kleinere Batches. Erhöhen Sie das Limit des Proxys auf mindestens das Limit des Endpunkts. |
| `400` von einem OTLP-over-HTTP-Endpunkt | Der Sender hat den Body komprimiert. | Setzen Sie `compression: none` im OpenTelemetry-Collector-Exporter. |
| `404` von einem OTLP-over-HTTP-Endpunkt | Der Exporter-Endpunkt lässt den Basispfad `/api` weg, daher gehen Anfragen an `/v1/logs`. | Verwenden Sie `http://host:5080/api` als OTLP-Endpunkt. |
| `429` mit `Retry-After` | Das Ratenlimit der Rolle `router` für die Organisation greift. | Drosseln Sie die Anfragen, oder erhöhen Sie `[router.rate_limit]`. |
| Native JSON meldet `rejected`-Datensätze | Ein Feldwert entspricht nicht dem Schema des Streams, zum Beispiel `type mismatch on field level: expected Utf8, got Number`. Die Antwort listet den Grund pro Index auf. Zahlen mit einem Bruchteil in einem `int64`-Feld gehören nicht dazu: Das Feld wird zu `float64`. | Senden Sie den Typ, den der Stream bereits für das Feld speichert. |
| `400` mit `event #1 must be a JSON object` | Das Array enthält ein Element, das kein JSON-Objekt ist. Die gesamte Anfrage wird abgelehnt. | Senden Sie ein Array aus Objekten. |
| Promtail oder Grafana Alloy können nicht pushen | Der Loki-Endpunkt dekodiert nur JSON, und diese Sender verwenden snappy-komprimiertes Protobuf. | Senden Sie über den OpenTelemetry Collector, Vector oder Fluent Bit. |
| Datensätze werden angenommen, aber nicht gefunden | Die Abfrage verwendet einen anderen Stream-Namen oder -Typ oder einen Zeitbereich, der sie ausschließt. | Prüfen Sie den Stream-Namen und den Signaltyp. Siehe den nächsten Abschnitt zu Zeitstempeln. |

## Fehlende oder ungewöhnliche Daten

- **Zeitstempel.** `_timestamp` zählt Mikrosekunden seit der Unix-Epoche. Ein Wert in Sekunden, Millisekunden oder Nanosekunden ordnet Ereignisse dem falschen Jahr oder der fernen Zukunft zu, und Abfragen über die jüngste Zeit geben sie nicht zurück. Lassen Sie `_timestamp` weg, um die Empfangszeit des Servers zu verwenden.
- **Zeitbereich.** Eine Abfrage, die einen langen Bereich abdeckt, wird zu einem asynchronen Job. Verwenden Sie für interaktive Abfragen einen begrenzten `timeRange`. Siehe [Abfrage](/de/query#zeitbereiche-und-asynchrone-jobs).
- **Aufbewahrung.** Daten, die älter als die Aufbewahrung des Streams sind, oder bei einem Stream ohne eigene Aufbewahrung älter als der Plattformstandard in **Einstellungen → Datenaufbewahrung**, werden gelöscht.
- **Stream-Typ.** Ein Stream wird durch Name und Typ identifiziert. `default` kann gleichzeitig für Logs, Metriken und Traces existieren.

## Abfragen

| Symptom | Ursache | Behebung |
|---|---|---|
| Die Antwort ist `202` mit einer `jobId` und einem `monitor`-Pfad | Die geschätzte Größe erreicht `[querier].auto_async_threshold_rows`, daher läuft die Abfrage als asynchroner Suchjob. Mit den Standardwerten ist das ein Bereich von etwa 13,9 Stunden oder mehr. | Rufen Sie den `monitor`-Pfad auf, bis der Job abgeschlossen ist, und holen Sie dann seine `/results` ab. Oder verengen Sie den Zeitbereich, oder senden Sie `Prefer: respond-sync`. Siehe [Abfrage](/de/query#zeitbereiche-und-asynchrone-jobs). |
| Der Flight-SQL-Client kann keine Verbindung herstellen | `[flight_sql]` ist standardmäßig deaktiviert. | Setzen Sie `enabled = true`, geben Sie Port `5083` frei und authentifizieren Sie sich mit einem API Token. |

## Betrieb

| Symptom | Ursache | Lösung |
|---|---|---|
| `GET /api/v1/healthz` liefert `503` | Der Objektspeicher ist nicht erreichbar. Der Body enthält ein `reason`. | Beheben Sie die Verbindung zum Objektspeicher. |
| Das WAL-Verzeichnis wächst | Flushes schlagen fehl, meist weil der Objektspeicher nicht erreichbar ist. | Beheben Sie den Objektspeicher. Der Intake schreibt den Rückstau anschließend ab. |
| Der Intake antwortet mit `429` und `intake buffer memory limit exceeded` | Die Puffer des Prozesses halten mehr als `[intake].max_buffer_memory_size`, meist weil Flushes weiterhin fehlschlagen. | Finden Sie die Ursache in den Logzeilen `intake flush failed` und beheben Sie den Objektspeicher oder die Datenbank. Zeilen, die nie veröffentlicht werden können, zählen nicht mehr gegen das Limit (siehe die beiden nächsten Zeilen). Der native JSON-Intake sendet bei dieser Antwort `Retry-After`; wiederholen Sie den Versuch nach dieser Verzögerung. |
| Das Log zeigt `dataset no longer exists; buffered rows discarded` | Ein Stream wurde gelöscht oder gelöscht und neu erstellt, während noch Zeilen davon gepuffert waren. Diese Zeilen können nirgendwohin, deshalb verwirft der Intake sie und gibt ihren Speicher frei. Der Zähler `intake_flush_errors_total` erfasst jedes Verwerfen unter dem Schritt `stream_gone` oder `dataset_gone`. | Nichts zu beheben. Senden Sie die Daten erneut, wenn sie wichtig sind. |
| Schreibvorgänge antworten mit `503` und `fenced by a newer writer epoch` | Ein anderer Prozess veröffentlicht dasselbe Dataset unter derselben `[node].id`. Der gefencte Prozess kann seine Daten nicht veröffentlichen, verwirft die Zeilen im Speicher und lehnt Schreibvorgänge auf dieses Dataset ab. Sein WAL bleibt auf der Festplatte. Der Zähler `intake_flush_errors_total` erfasst das Fencing unter dem Schritt `writer_fenced`. | Geben Sie jedem Prozess eine eindeutige `[node].id` und starten Sie den gefencten Prozess neu. Siehe [Rollenbasierte Bereitstellung](/de/deployment/role-based). |
| Geplante PDF- oder PNG-Reports schlagen fehl | Chrome fehlt oder `[scheduled_reports.renderer].base_url` erreicht die Web-UI nicht. | Verwenden Sie das Release-Image, das Chromium enthält, und setzen Sie `base_url` auf die Adresse der Web-UI, die der Node erreichen kann. |
| Onboarding-Snippets zeigen den falschen Host | `http.external_url` ist hinter einem Proxy leer. | Setzen Sie `[http].external_url` auf die öffentliche Adresse und starten Sie neu. |
| Abfragen antworten mit `503` und `no querier node is available` | Kein Node mit der Rolle `querier` hat einen aktuellen Heartbeat. | Starten Sie einen `querier`-Node und prüfen Sie, ob seine `advertise_addr` vom Router aus erreichbar ist. Siehe [Rollenbasierte Bereitstellung](/de/deployment/role-based#cluster-mitgliedschaft). |
| Schreibvorgänge über den Router antworten mit `503` und `no intake node is available` | Kein Node mit der Rolle `intake` hat einen aktuellen Heartbeat. | Starten Sie einen `intake`-Node und prüfen Sie seine `advertise_addr`. Siehe [Rollenbasierte Bereitstellung](/de/deployment/role-based#cluster-mitgliedschaft). |
| Anfragen antworten mit `503` und `no metadata database connection` | Der Node hat 10 Sekunden auf eine PostgreSQL-Verbindung gewartet und keine erhalten: PostgreSQL ist überlastet oder nicht erreichbar, oder alle `[meta_database].max_connections` Verbindungen sind belegt. | Wiederholen Sie die Anfrage. Tritt das weiterhin auf, prüfen Sie zuerst Last und Erreichbarkeit von PostgreSQL. Ist PostgreSQL im Leerlauf, erhöhen Sie `[meta_database].max_connections` passend zur Last, innerhalb der `max_connections` von PostgreSQL. |
| Der OTLP-gRPC-Port ist vom Host aus nicht erreichbar | Die Compose-Datei veröffentlicht Port `4317` nicht. | Fügen Sie eine Zuordnung `4317:4317` hinzu. |
