Eine Alarmquelle wandelt Alarme, die ein anderes System sendet, in [Incidents](/de/alerting/incidents) um. Sie alarmiert Personen über eine [Eskalationsrichtlinie](/de/alerting/on-call#eskalationsrichtlinien) und benachrichtigt über [Benachrichtigungsrichtlinien](/de/notification-channels) auf dieselbe Weise wie Incidents von Regeln; die Incidents werden aufgelöst, wenn die Quelle eine Wiederherstellung meldet. Öffnen Sie **Alarme → Quellen**. Das Lesen erfordert `alerts.sources.read`; das Erstellen, Bearbeiten, Löschen und Rotieren von Tokens erfordert `alerts.sources.manage`.

## Quellentypen

Jede Quelle hat einen Typ, der bestimmt, in welchem Format der Request-Body des Absenders gelesen wird.

| Typ | Absender | Ein Incident pro |
|---|---|---|
| **API** | Skripte, CI und unternehmensinterne Systeme, die die MoleSignal-API aufrufen | Dedup-Schlüssel |
| **Alertmanager** | Ein Webhook-Empfänger von Prometheus Alertmanager | Benachrichtigungsgruppe |
| **Grafana** | Ein Webhook-Kontaktpunkt von Grafana Alerting | Benachrichtigungsgruppe |
| **Datadog** | Die Datadog-Webhooks-Integration | Monitor; jede Gruppe eines Multi-Alert-Monitors |
| **PagerDuty** | Ein PagerDuty-V3-Webhook-Abonnement | PagerDuty-Incident |
| **Alibaba Cloud CloudMonitor** | Schwellenwert-Alarm-Callbacks und Push-Kanäle für Ereignisabonnements | Objekt einer Alarmregel oder Systemereignis |
| **Tencent Cloud Observability Platform** | API-Callbacks einer Benachrichtigungsvorlage | Eine Metrik oder ein Ereignis eines Objekts unter einer Richtlinie, bei einer Richtlinie mit Ebenen eine pro Ebene |
| **Amazon CloudWatch** | Alarme, die über das HTTPS-Abonnement des Topics an ein SNS-Topic gesendet werden | Ein Alarm |
| **Zabbix** | Ein Zabbix-Webhook-Medientyp | Ein Problem |
| **Azure Monitor** | Die Webhook-Aktion einer Aktionsgruppe im Common Alert Schema | Ein Alarm |
| **Google Cloud Monitoring** | Ein Webhook-Benachrichtigungskanal oder der Pub/Sub-Kanal über ein Push-Abonnement | Ein Monitoring-Incident |
| **Huawei Cloud Eye** | Alarme, die über das HTTPS-Abonnement des Topics an ein SMN-Topic gesendet werden | Eine Alarmregel für eine Ressource |
| **E-Mail** | Ein IMAP-Postfach oder Roh-E-Mails aus einem bereits betriebenen E-Mail-System | Eine Folge von E-Mails mit demselben Betreff |

Systeme, die den Alertmanager-Webhook sprechen, wie etwa der Alertmanager von Thanos, Cortex oder Mimir, verwenden den Typ **Alertmanager**.

## Quelle erstellen

1. Öffnen Sie **Alarme → Quellen** und klicken Sie auf **Neue Alarmquelle**.
2. Wählen Sie den **Typ** und geben Sie einen **Namen** ein.
3. Wählen Sie die **Eskalationsrichtlinie**. Der Standard ist **Nach Routing-Regeln (Standard)**, wie in der Regel-Workbench: [Alarm-Routing](/de/alerting/routing) wählt anhand der Routing-Regeln, des zuständigen Teams des Services und des Team-Labels das Team und die Eskalationsrichtlinie aus und andernfalls die [Standardrichtlinie](/de/alerting/on-call#die-standardrichtlinie) namens `default`. Ist eine Richtlinie ausgewählt, übernehmen Incidents diese, und das Routing wählt nur das Team aus. Mit **Keine Eskalation, nur Benachrichtigungsrichtlinien** werden Incidents weiterhin geöffnet und Benachrichtigungen ausgelöst, aber es wird niemand über eine Eskalationsrichtlinie alarmiert.
4. Wählen Sie den **Standard-Schweregrad**, der verwendet wird, wenn ein Alarm keinen eigenen Schweregrad enthält.
5. Fügen Sie bei Bedarf **Zusätzliche Labels** hinzu, etwa `team=payments`. Sie werden jedem Incident hinzugefügt, den die Quelle öffnet. Ein Label, das der Alarm selbst enthält, hat Vorrang.
6. Klicken Sie auf **Erstellen**. Die Seite der Quelle öffnet sich mit einem Dialog, der das Token und die Einrichtung mit eingetragenem Token zeigt; Alibaba Cloud CloudMonitor benötigt nur die Intake-Adresse, daher zeigt der Dialog die Adresse mit dem Token darin.

<Warning>
  Das Token wird nur beim Erstellen der Quelle oder beim Rotieren ihres Tokens angezeigt. Nach dem Schließen des Dialogs ist nur das Präfix beginnend mit `mspat-` sichtbar. Wenn das Token verloren ist, klicken Sie auf **Token rotieren**, um ein neues zu erhalten; das alte Token funktioniert sofort nicht mehr.
</Warning>

## Intake-Adresse und Token

Alle Quellen teilen sich eine Intake-Adresse. Das Token gibt an, zu welcher Quelle ein Alarm gehört:

```text
https://<molesignal-host>/api/v1/intake/alerts
```

Ein Token sieht aus wie `mspat-<36>`, hat dieselbe Form wie ein API-Token, nimmt aber nur Alarme entgegen, und ein API-Token kann keine Alarme entgegennehmen. Der Absender setzt es in einen Header:

```text
Authorization: Bearer <token>
```

Ein Absender, der keine Header setzen kann (Alibaba Cloud CloudMonitor, Tencent Cloud Observability Platform, Amazon CloudWatch über SNS, Azure Monitor, Google Cloud Monitoring, Huawei Cloud Eye über SMN), überträgt das Token in der Adresse: `https://<molesignal-host>/api/v1/intake/alerts?token=<token>`.

Der Absender muss diese Adresse erreichen. Wenn eine Firewall vor MoleSignal steht, lassen Sie die Egress-Adressen des Standorts oder der Region des Absenders zu: Datadog listet sie pro Standort im Abschnitt `webhooks` seiner `ip-ranges` auf, PagerDuty veröffentlicht sie für seine US- und EU-Service-Regionen, und Alibaba Cloud CloudMonitor listet seine Push-Bereiche in seiner Dokumentation zu Alarm-Callbacks auf. Wenn MoleSignal in einem internen Netzwerk läuft, lesen Sie [Öffentlicher Zugriff](/de/public-access), um nur diese Adresse für das Internet zu öffnen.

## Absender einrichten

**Empfang** auf der Seite der Quelle liefert die Empfangsadresse, das Token und die Einrichtung jeder Art in drei Schritten. Ersetzen Sie `<TOKEN>` durch das Token der Quelle. Sobald die Quelle ihre erste Anfrage empfängt, hakt MoleSignal die drei Schritte ab.

### API

```bash
curl -X POST https://<molesignal-host>/api/v1/intake/alerts \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{"dedupKey": "disk-full/web-1", "summary": "Disk almost full on web-1", "severity": "critical", "labels": {"host.name": "web-1"}}'
```

`action` ist `trigger` (der Standard), `acknowledge` oder `resolve`. Verwenden Sie denselben `dedupKey`, um denselben Alarm zu bestätigen oder aufzulösen. [Alarme senden](/de/api/alerting/send-alerts) beschreibt jedes Feld.

### Alertmanager

Fügen Sie einen Receiver zu `alertmanager.yml` hinzu und leiten Sie Alarme an ihn weiter:

```yaml
route:
  receiver: molesignal
receivers:
  - name: molesignal
    webhook_configs:
      - url: https://<molesignal-host>/api/v1/intake/alerts
        send_resolved: true
        http_config:
          authorization:
            credentials: <token>
```

Lassen Sie `send_resolved` auf `true`, sonst werden Entwarnungen nie gesendet. Geben Sie jedem Replikat eines Alertmanager-Clusters dieselbe `--web.external-url`: Die externe URL ist Teil des Deduplizierungsschlüssels, daher führt MoleSignal Gruppen mit demselben Namen von Alertmanagern in mehreren Regionen mit demselben Routing nicht zu einem Incident zusammen.

### Grafana

1. Öffnen Sie in Grafana **Alarmierung → Kontaktpunkte** und klicken Sie auf **Kontaktpunkt hinzufügen**.
2. Setzen Sie **Integration** auf **Webhook** und **URL** auf die Empfangsadresse.
3. Legen Sie unter **Optionale Webhook-Einstellungen** das **Authentifizierungs-Header-Schema** auf `Bearer` und die **Authentifizierungs-Header-Anmeldedaten** auf das Token fest.
4. Lassen Sie **Entwarnungsnachricht deaktivieren** nicht aktiviert, speichern Sie, und verwenden Sie den Kontaktpunkt in einer Benachrichtigungsrichtlinie.

Mit Datei-Provisioning:

```yaml
apiVersion: 1
contactPoints:
  - orgId: 1
    name: molesignal
    receivers:
      - uid: molesignal
        type: webhook
        settings:
          url: https://<molesignal-host>/api/v1/intake/alerts
          httpMethod: POST
          authorization_scheme: Bearer
          authorization_credentials: <token>
```

### Datadog

1. Öffnen Sie in Datadog **Integrationen → Webhooks** und fügen Sie einen Webhook hinzu, beispielsweise mit dem Namen `molesignal`.
2. Setzen Sie **URL** auf die Empfangsadresse und **Benutzerdefinierte Header** auf `{"Authorization": "Bearer <token>"}`. Lassen Sie **Als Formular kodieren** nicht aktiviert.
3. Setzen Sie **Payload** auf die folgende Vorlage. Die Feldnamen stammen von MoleSignal und die Werte sind Datadog-Variablen; eine Anfrage ohne diese Vorlage wird abgelehnt.

```json
{
  "alert_id": "$ALERT_ID",
  "alert_cycle_key": "$ALERT_CYCLE_KEY",
  "transition": "$ALERT_TRANSITION",
  "alert_type": "$ALERT_TYPE",
  "priority": "$ALERT_PRIORITY",
  "title": "$ALERT_TITLE",
  "event_title": "$EVENT_TITLE",
  "message": "$TEXT_ONLY_MSG",
  "scope": "$ALERT_SCOPE",
  "tags": "$TAGS",
  "hostname": "$HOSTNAME",
  "link": "$LINK",
  "snapshot": "$SNAPSHOT",
  "query": "$ALERT_QUERY",
  "org_id": "$ORG_ID",
  "last_updated": "$LAST_UPDATED"
}
```

4. Erwähnen Sie `@webhook-molesignal` in der Benachrichtigungsnachricht eines Monitors.

Jede Datadog-Site (`datadoghq.com`, `datadoghq.eu`, `us3`, `us5`, `ap1` und die anderen) kann an eine Quelle senden: MoleSignal übernimmt die Site aus der Domain von `$LINK`; sie ist zusammen mit der Organisations-ID Teil des Deduplizierungsschlüssels.

### PagerDuty

1. Öffnen Sie in PagerDuty **Integrationen → Generic Webhooks (v3)** und klicken Sie auf **Neuer Webhook**.
2. Setzen Sie die **Webhook-URL** auf die Empfangsadresse und wählen Sie den **Scope-Typ** (das Konto, einen Service oder ein Team).
3. Wählen Sie unter **Ereignisabonnement** `incident.triggered`, `incident.acknowledged`, `incident.resolved`, `incident.reopened` und `incident.priority_updated` aus.
4. Fügen Sie den benutzerdefinierten Header `Authorization` mit dem Wert `Bearer <token>` hinzu.

Konten der US- und der EU-Service-Region können an eine Quelle senden: Die Kontodomain (`<subdomain>.pagerduty.com` oder `<subdomain>.eu.pagerduty.com`) ist Teil des Deduplizierungsschlüssels, und MoleSignal schreibt sie in das Label `pagerduty.region`.

### Alibaba Cloud CloudMonitor

Fügen Sie das Token zur Empfangsadresse hinzu:

```text
https://<molesignal-host>/api/v1/intake/alerts?token=<token>
```

- **Schwellenwertalarme**: Geben Sie diese Adresse als **Alarm-Callback** einer Alarmregel ein. CloudMonitor sendet den Callback per POST formularcodiert; MoleSignal liest auch JSON.
- **Systemereignisse**: Erstellen Sie unter **Event Center → Ereignisabonnement → Push-Kanäle** einen Kanal mit dem Zieltyp **Webhook**, der Anforderungsmethode **POST** und dem Datenformat **JSON**, geben Sie diese Adresse ein und verwenden Sie den Kanal in einer Abonnementrichtlinie.

CloudMonitor wartet bei einem Systemereignis-Callback 5 Sekunden und versucht es dreimal erneut. MoleSignal wartet höchstens 3 Sekunden, wenn es eine Anfrage an den [empfangenden Cluster](#mehrere-cluster) weiterleitet, und antwortet bei Zeitüberschreitung mit `503`, damit CloudMonitor es erneut versucht. Die chinesischen und internationalen Sites und jede Region senden dasselbe Format; MoleSignal schreibt die Region in das Label `aliyun.region`, und die `userId` des Kontos ist Teil des Deduplizierungsschlüssels.

### Tencent Cloud Observability Platform

Bearbeiten oder erstellen Sie in Tencent Cloud Observability Platform (früher Cloud Monitor) eine Vorlage unter **Alarmverwaltung → Benachrichtigungsvorlagen**, geben Sie die Empfangsadresse als **API-Callback** ein und binden Sie die Vorlage an Ihre Alarmrichtlinien. Der Callback von Tencent Cloud kann keine Header setzen, deshalb gehört das Token in die Adresse. Behandeln Sie die Adresse wie ein Zugangsdatum: Der Callback trägt keine Signatur, und die Adresse identifiziert die Quelle. Metrik- und Ereignisalarme funktionieren beide, und sowohl Auslösungen als auch Entwarnungen werden übertragen.

- **Deduplizierung**: Dasselbe Konto, dieselbe Alarmrichtlinie, derselbe Metrik- oder Ereignisname und dasselbe Objekt ergeben einen Alarm. Eine Richtlinie mit Stufen hat einen Incident pro Stufe, der sich jeweils selbst auflöst, wie in Tencent Cloud.
- **Schweregrad**: `alarmLevel` Serious (`Serious`) ist kritisch, Severe (`Warn`) ist Fehler und Reminder (`Remind`) ist Info. Eine Richtlinie ohne Stufen übernimmt den Standard-Schweregrad der Quelle.
- **Zustandslose Ereignisse** (`alarmStatus` ist `5`) öffnen einen Incident, auf dessen Entwarnung nicht gewartet wird, sodass ihn eine Person auflöst.
- **Zeiten** im Callback enthalten keine Zeitzone und werden als Pekinger Zeit gelesen.

### Amazon CloudWatch

CloudWatch-Alarme rufen keine externen Adressen selbst auf; sie laufen über SNS:

1. Senden Sie in den Benachrichtigungen des Alarms sowohl den Wechsel in **Im Alarmzustand** (`ALARM`) als auch die Rückkehr zu **OK** an dasselbe SNS-Topic. Ohne `OK` lösen sich Incidents nicht selbst auf. Senden Sie bei Alarmen wegen fehlender Daten auch **Unzureichende Daten** (`INSUFFICIENT_DATA`).
2. Fügen Sie dem Topic ein HTTPS-Abonnement mit der Empfangsadresse als Endpunkt hinzu, wobei das Token in der Adresse steht:

   ```bash
   aws sns subscribe \
     --topic-arn <ARN of the topic> \
     --protocol https \
     --notification-endpoint 'https://<molesignal-host>/api/v1/intake/alerts?token=<token>'
   ```

3. Das Abonnement bestätigt sich selbst: MoleSignal prüft die Signatur der Bestätigungsnachricht und ruft dann deren `SubscribeURL` auf.

MoleSignal prüft die Signatur jeder SNS-Nachricht, daher muss **Rohzustellung von Nachrichten** ausgeschaltet bleiben. Ist sie eingeschaltet, lehnt MoleSignal Nachrichten ab, und „Zuletzt empfangen“ auf der Seite der Quelle nennt den Grund. Das Signaturzertifikat stammt von `sns.<region>.amazonaws.com`, daher muss der Knoten, der die Anfrage annimmt, diese Adresse erreichen können.

CloudWatch-Alarme haben keinen Schweregrad, daher übernehmen Incidents den Standard der Quelle. Die ARN des Alarms ist der Deduplizierungsschlüssel, auch bei zusammengesetzten Alarmen. Die Beschreibung des Alarms und der Grund für die Zustandsänderung landen in Annotationen; Region, Konto, Namespace, Metrik und Dimensionen landen in Labels, sodass ein Label wie `aws.region` das Routing steuern kann.

### Azure Monitor

Azure Monitor-Alarme erreichen MoleSignal über die Webhook-Aktion einer Aktionsgruppe:

1. Fügen Sie in der Aktionsgruppe, die Ihre Alarmregeln verwenden, eine Aktion vom Typ **Webhook** mit der Empfangsadresse als URI hinzu, wobei das Token in der Adresse steht.
2. Setzen Sie **Allgemeines Warnschema aktivieren** auf **Ja**. Ohne es lehnt MoleSignal Anfragen ab, und „Zuletzt empfangen“ auf der Seite der Quelle nennt den Grund.

Dasselbe mit der Azure CLI:

```bash
az monitor action-group update \
  --resource-group <resource group> \
  --name <action group> \
  --add-action webhook molesignal 'https://<molesignal-host>/api/v1/intake/alerts?token=<token>' usecommonalertschema
```

- **Deduplizierung**: Die `alertId` des Alarms ist der Deduplizierungsschlüssel und enthält das Azure-Abonnement.
- **Auslösen und Auflösen**: `monitorCondition` `Fired` öffnet den Incident und `Resolved` löst ihn auf. Alarme ohne Zustand, etwa Aktivitätsprotokoll-Alarme, lösen nur aus, sodass sie eine Person auflöst.
- **Schweregrad**: `Sev0` ist kritisch, `Sev1` Fehler, `Sev2` Warnung und `Sev3` und `Sev4` Info.
- **Labels**: die benutzerdefinierten Eigenschaften der Alarmregel, die Metrikdimensionen, `azure.subscription_id`, `azure.resource_group`, `azure.resource`, `azure.signal_type`, `azure.monitoring_service` und `azure.metric`. Beschreibung, Bedingung, Wert und Ziele landen in Annotationen, der Untersuchungslink als `azure_url`.

### Google Cloud Monitoring

1. Öffnen Sie in der Google Cloud Console **Monitoring → Alarmierung → Benachrichtigungskanäle bearbeiten**, und fügen Sie einen **Webhook**-Kanal mit der Empfangsadresse als **Endpunkt-URL** hinzu, wobei das Token in der Adresse steht.
2. Fügen Sie den Kanal den Benachrichtigungen Ihrer Alarmierungsrichtlinien hinzu. Auch geschlossene Incidents werden gesendet, sodass sich Incidents selbst auflösen.

Der **Pub/Sub**-Kanal veröffentlicht dieselbe Benachrichtigung. Erstellen Sie dazu ein Push-Abonnement für dessen Topic mit der Empfangsadresse als Push-Endpunkt; MoleSignal entpackt den Pub/Sub-Umschlag.

- **Deduplizierung**: das Scoping-Projekt und `incident_id`. Ein Monitoring-Incident ist ein Incident.
- **Auslösen und Auflösen**: `state` `open` öffnet den Incident und `closed` löst ihn auf.
- **Schweregrad**: die Schweregradstufe der Richtlinie, `Critical`, `Error` oder `Warning`. Eine Richtlinie ohne Stufe übernimmt den Standard-Schweregrad der Quelle.
- **Labels**: die Labels der Ressource und der Metrik, die Benutzer-Labels der Richtlinie und der überwachten Ressource, `gcp.project_id`, `gcp.resource_type`, `gcp.metric` und `gcp.policy`. Zusammenfassung, Bedingung, beobachteter Wert, Schwellenwert und Dokumentation landen in Annotationen, die Konsolenadresse des Incidents als `gcp_url`.

### Huawei Cloud Eye

Cloud Eye-Alarme (CES) rufen keine externen Adressen selbst auf; sie laufen über SMN:

1. Fügen Sie in Simple Message Notification ein Abonnement für ein Topic mit dem Protokoll **HTTPS** und der Empfangsadresse als Endpunkt hinzu, wobei das Token in der Adresse steht.
2. Das Abonnement bestätigt sich selbst: MoleSignal prüft die Signatur der Bestätigungsnachricht und ruft dann deren `subscribe_url` auf.
3. Wählen Sie in den Alarmbenachrichtigungen Ihrer Cloud Eye-Alarmregeln dieses Topic aus, und benachrichtigen Sie sowohl beim Alarm als auch bei seiner Entwarnung. Ohne die Entwarnung lösen sich Incidents nicht selbst auf.

MoleSignal prüft die Signatur jeder SMN-Nachricht. Das Signaturzertifikat stammt von `smn.<region>.myhuaweicloud.com`, daher muss der Knoten, der die Anfrage annimmt, diese Adresse erreichen können.

- **Deduplizierung**: das Projekt des Topics, die `alarm_id` der Alarmregel und die Ressource. Eine Regel für mehrere Ressourcen öffnet einen Incident pro Ressource.
- **Auslösen und Auflösen**: `alarm_status` `alarm` öffnet den Incident, `insufficient_data` öffnet ihn als „keine Daten“, und `ok` löst ihn auf.
- **Schweregrad**: die Alarmstufe: Critical ist kritisch, Major Fehler, Minor Warnung und Informational Info.
- **Labels**: die Dimensionen wie `instance_id` sowie `huawei.region`, `huawei.project_id`, `huawei.namespace`, `huawei.metric`, `huawei.alarm_id` und `huawei.resource_id`. Alarmtext, aktueller Wert und Schwellenwert landen in Annotationen, die Konsolenadresse des Alarms als `huawei_url`.

### Zabbix

Funktioniert ab Zabbix 6.0. Zabbix hat kein eigenes Anforderungsformat: Das Skript eines Medientyps sendet die Anforderung. Die Seite der Quelle und der Dialog beim Erstellen liefern daher einen Medientyp mit ausgefüllter Adresse und ausgefülltem Token:

1. Speichern Sie ihn als YAML und importieren Sie ihn unter **Alarme → Medientypen → Importieren**. Prüfen Sie den Parameter `token`.
2. Setzen Sie das globale Makro `{$ZABBIX.URL}` auf die Adresse des Zabbix-Frontends. Das Makro fließt in den Deduplizierungsschlüssel ein, sodass eine Quelle mehrere Zabbix-Server bedienen kann und Incidents zurück auf Zabbix verweisen. Das funktioniert auch ohne.
3. Weisen Sie einem Benutzer diesen Medientyp zu. **Senden an** kann beliebig sein; das Skript verwendet es nicht.
4. Fügen Sie eine Trigger-Aktion hinzu, deren **Operationen**, **Wiederherstellungsoperationen** und **Aktualisierungsoperationen** alle an diesen Benutzer gehen. Ohne Wiederherstellungsoperationen lösen sich Incidents nicht selbst auf.

Die Schaltfläche **Testen** des Medientyps benötigt echte Werte: Wenn Makros nicht aufgelöst werden (`{EVENT.ID}` kommt unverändert an), antwortet MoleSignal mit `400` und verlangt, den Medientyp aus der Dokumentation zu verwenden.

### E-Mail

Es gibt zwei Eingangswege, und beide lesen E-Mail in dieselben Alarme ein.

**Postfach abrufen** (empfohlen): MoleSignal liest ein IMAP-Postfach nach Zeitplan. Benötigt werden nur ein ausgehender Netzwerkzugang und ein Postfach: keine öffentliche Adresse, kein MX-Eintrag, kein Port 25 und kein Zertifikat, was es zur einfachsten Wahl für Self-Hosting macht. Senden Sie die Alarm-E-Mail Ihres Monitoring-Systems an dieses Postfach oder leiten Sie sie mit einer E-Mail-Regel dorthin weiter.

Füllen Sie auf der Seite der Quelle unter **Postfach abrufen** **IMAP-Server**, **Port**, **Verschlüsselung**, **Benutzername**, **Passwort**, **Ordner** (`INBOX` standardmäßig) und **Abrufintervall** (15 bis 3600 Sekunden, 60 standardmäßig) aus. Klicken Sie auf **Verbindung testen** und dann auf **Postfach speichern**.

- **Nur lesen**: Es verwendet `EXAMINE` und `BODY.PEEK[]`, daher markiert es nichts als gelesen und löscht nichts. Ein schreibgeschütztes Konto genügt.
- **Kein Rückstand**: Beim ersten Verbinden merkt sich MoleSignal die Position und liest nur, was danach eintrifft. Ein Wechsel von Host, Konto oder Ordner oder ein Server, der das Postfach neu aufgebaut hat (`UIDVALIDITY` geändert), beginnt ab diesem Zeitpunkt von vorn. Solange die Quelle aus ist, liest MoleSignal nichts und speichert keine Position: Der Abruf beginnt ab dem Moment, in dem die Quelle wieder eingeschaltet wird.
- **Die Absenderliste ist erforderlich**: Jeder, der die Adresse kennt, kann E-Mails dorthin senden. Schreiben Sie unter **E-Mails annehmen von** in den Einstellungen der Quelle Adressen oder `@example.com` für eine ganze Domain; `*` nimmt alle an. Die Liste liest `From`, was gefälscht werden kann, daher halten Sie die Spamfilterung und DMARC des Mailanbieters aktiviert. E-Mail von allen anderen wird als **Abgelehnt** erfasst und öffnet nichts.
- **Anmeldung**: ein Passwort oder ein App-Passwort des Anbieters. Microsoft 365 akzeptiert keine Passwörter mehr: Wählen Sie **OAuth 2.0** und geben Sie die Token-Adresse `https://login.microsoftonline.com/<tenant>/oauth2/v2.0/token`, die Client-ID, das Client-Geheimnis und den Scope `https://outlook.office365.com/.default` ein. Die Anwendung benötigt die Berechtigung `IMAP.AccessAsApp` und Zugriff auf dieses Postfach.
- **Keine Verschlüsselung** gehört nur in ein Netzwerk, dem Sie vertrauen: Das Passwort wird darin im Klartext übertragen.
- Wenn ein Abruf fehlschlägt, nennt die Seite der Quelle den Grund, und der nächste Durchlauf versucht es erneut. Bei mehreren Alarm-Knoten ist jedes Postfach genau einem von ihnen zugeordnet. Bei Föderation steht das Postfach auf dem empfangenden Cluster der Quelle und wird nicht synchronisiert, sodass das Passwort dort bleibt.

**Rohmail per POST senden**: Wenn Sie bereits ein Mailsystem betreiben (`pipe` von Postfix, SES, Roh-MIME von Mailgun), senden Sie die Rohmail per POST an die Empfangsadresse:

```bash
curl -X POST 'https://<molesignal-host>/api/v1/intake/alerts' \
  -H 'Authorization: Bearer <token>' \
  -H 'Content-Type: message/rfc822' \
  --data-binary @alert.eml
```

Dafür muss die Empfangsadresse vom Mailsystem aus erreichbar sein. Die Absenderliste ist hier optional, da das Token bereits angibt, wer aufruft; sie gilt, wenn Sie eine eintragen.

MoleSignal hat keinen integrierten SMTP-Empfänger: Dieser würde einen offenen Port 25, einen MX-Eintrag, ein TLS-Zertifikat und eigene Spamfilterung erfordern, was die meisten selbst gehosteten Bereitstellungen nicht bieten können.

Die Art des **E-Mail-Empfangs** legen Sie unter **E-Mail-Empfang** in den Einstellungen der Quelle fest:

| Einstellung | Beschreibung |
|---|---|
| **Betreffzeilen für Entwarnungen** | Ein regulärer Ausdruck. Leer verwendet den eingebauten: `resolved`, `recovered`, `recovery`, `cleared`, `恢复`, `已解决` und `OK` am Anfang. Andere E-Mails lösen aus. |
| **Deduplizierungsschlüssel aus dem Betreff** | Ein regulärer Ausdruck; seine erste Gruppe wird genommen, etwa `host=(\S+)`. Leer oder keine Übereinstimmung verwendet den bereinigten Betreff: ohne `Re:` und `Fwd:`, Statuswörter (`PROBLEM`, `RECOVERY`, `告警`, `恢复` und so weiter), Schweregrade, Datums- und Zeitangaben sowie Prozentwerte, ohne Beachtung der Groß-/Kleinschreibung. So sind „CRITICAL: disk full on web-1 (91%)“ und „RECOVERY: disk full on web-1 (40%)“ ein Alarm, während `web-1` und `web-2` zwei sind. Die Domain des Absenders zählt ebenfalls zum Schlüssel. |
| **Zu ignorierende Betreffzeilen** | Ein regulärer Ausdruck. E-Mails, die übereinstimmen, werden übersprungen und unter „Zuletzt empfangen“ angezeigt. |

Der Schweregrad stammt aus Wörtern im Betreff (`critical`, `fatal`, `disaster`, `P1` sind kritisch; `error`, `P2` Fehler; `warning`, `P3` Warnung; `info`, `notice`, `P4`, `P5` Info), andernfalls gilt der Standard der Quelle; das High und Low von `High CPU` und `Low disk` zählen nicht. Der Body landet in der Annotation `message` (HTML-Mail als Text, höchstens 4096 Zeichen), der Absender im Label `email.from` und in der Annotation `from`, und die Zeit stammt aus dem Header `Date`. Automatische Antworten (`Auto-Submitted: auto-replied`) und Bounces (`multipart/report`) sind keine Alarme. GBK, GB2312 und andere Zeichensätze werden verstanden. E-Mails über 4 MiB werden als **Abgelehnt** erfasst, ohne dass ihr Body gelesen wird.

## Wie Alarme zu Incidents werden

| Art | Dedup-Schlüssel | Auslöser | Auflösen | Schweregrad |
|---|---|---|---|---|
| **API** | `dedupKey` | `trigger` | `resolve` | `severity` |
| **Alertmanager** | Externe URL und `groupKey` | Gruppen-`status` `firing` | Gruppen-`status` `resolved`: alle Alarme der Gruppe behoben | Das höchste Label `severity` unter den feuernden Alarmen der Gruppe |
| **Grafana** | Externe URL, Organisation und `groupKey` | Wie oben | Wie oben | Wie oben |
| **Datadog** | Site, Organisation, Monitor-ID und Scope | Jeder Übergang außer `Recovered` | `Recovered` | `$ALERT_PRIORITY`; ohne dieses sind Warn und No Data Warnung und der Rest folgt `$ALERT_TYPE` |
| **PagerDuty** | Kontodomain und PagerDuty-Incident-ID | `incident.triggered`, `incident.reopened`; `incident.priority_updated` ändert den Schweregrad | `incident.resolved` | Priorität P1 bis P5; ohne diese gilt: Dringlichkeit hoch ist Fehler, niedrig ist Warnung |
| **Alibaba Cloud CloudMonitor** | Konto, Regel-ID und `dimensions`; bei Systemereignissen Konto und `dedupId` | `ALERT`, `INSUFFICIENT_DATA`; Systemereignis `TRIGGERED` | `OK`; Systemereignis `RESOLVED` | `triggerLevel`; Systemereignis `severity` |
| **Tencent Cloud Observability Platform** | Konto, Richtlinie, Metrik- oder Ereignisname, Ebene und Objekt | `alarmStatus` ist `1` oder `5` | `alarmStatus` ist `0` | `alarmLevel` |
| **Amazon CloudWatch** | `AlarmArn` | `NewStateValue` ist `ALARM` oder `INSUFFICIENT_DATA` | `NewStateValue` ist `OK` | Keine: der Standard-Schweregrad der Quelle |
| **Azure Monitor** | `alertId` | `monitorCondition` ist `Fired` | `monitorCondition` ist `Resolved` | `severity`: `Sev0` kritisch, `Sev1` Fehler, `Sev2` Warnung, `Sev3` und `Sev4` Info |
| **Google Cloud Monitoring** | Scoping-Projekt und `incident_id` | `state` ist `open` | `state` ist `closed` | `severity`; `No severity` übernimmt den Standard der Quelle |
| **Huawei Cloud Eye** | Projekt des SMN-Themas, `alarm_id` und Ressource | `alarm_status` ist `alarm` oder `insufficient_data` | `alarm_status` ist `ok` | Alarmstufe: Kritisch, Schwerwiegend, Gering, Informativ |
| **Zabbix** | Host von `{$ZABBIX.URL}` und `{EVENT.ID}` | `{EVENT.VALUE}` ist 1; auch Update-Operationen, wobei der Schweregrad folgt | `{EVENT.VALUE}` ist 0 oder eine Update-Operation hat das Problem geschlossen | `{EVENT.NSEVERITY}`: Disaster ist kritisch, High Fehler, Average und Warning Warnung, Information Info |
| **E-Mail** | Die Domain des Absenders und der aus dem Betreff entnommene Teil | Sonstige E-Mail | Ein als Wiederherstellung formulierter Betreff | Wörter im Betreff |

Priorität und Dringlichkeit werden getrennt betrachtet: `priority` und `urgency` der API, `$ALERT_PRIORITY` von Datadog sowie Priorität und Dringlichkeit von PagerDuty werden zu Priorität und Dringlichkeit des Incidents. Ohne Dringlichkeit entscheidet die Eskalationsrichtlinie der Quelle, und ein Alarm ohne gemeldeten Schweregrad hat hohe Dringlichkeit; siehe [Dringlichkeit](/de/alerting/on-call#dringlichkeit).

Ein Alarm ohne Schweregrad übernimmt den **Standard-Schweregrad** der Quelle. Die Schweregrad-Bezeichnungen jedes Absenders sind unabhängig von Groß-/Kleinschreibung: `critical`, `crit`, `fatal`, `page` und `P1` sind kritisch; `error`, `major`, `high` und `P2` sind Fehler; `warning`, `warn`, `minor`, `medium` und `P3` sind Warnung; `info`, `low`, `P4` und `P5` sind Info. Jedes andere Wort übernimmt den Standard-Schweregrad.

- **Eröffnen**: Eine Quelle hat höchstens einen aktiven Incident pro Dedup-Schlüssel. Der Incident trägt die Labels `alert.source=external` und `external.kind=<kind>`, die eigenen Labels des Alarms (bei Alertmanager und Grafana die `commonLabels` der Gruppe) und die zusätzlichen Labels der Quelle. Das Label `service.name` oder `service` wird zu einem betroffenen Service, und `host.name`, `host` oder `hostname` wird zu einem Host.
- **Titel**: Die API verwendet `summary`; Alertmanager und Grafana verwenden die Annotation `summary` oder ohne diese `alertname`; Datadog verwendet `$ALERT_TITLE`; PagerDuty verwendet den Titel des Incidents; Alibaba Cloud CloudMonitor verwendet „Alarmname · Instanzname“.
- **Links**: Adressen zurück zum Absender werden in Annotationen geschrieben, etwa `alertmanager_url`, `generator_url`, `dashboard_url`, `datadog_url` und `pagerduty_url`, und die Incident-Seite zeigt sie als Links. Die `links` der API werden nach `name` in Annotationen geschrieben.
- **Alarme einer Gruppe**: Ein Incident aus Alertmanager oder Grafana behält jeden Alarm der Gruppe (bis zu 100) mit seinem Status bei und wird mit jeder Benachrichtigung aktualisiert. **Externer Alarm** auf der Incident-Seite listet sie mit den Labels auf, die sie unterscheiden.
- **Schweregrad-Änderungen**: Ein noch nicht bestätigter Incident folgt dem Schweregrad des Alarms, wie ihn die [Alarm-Pipelines](/de/pipelines/alert-events#schweregradänderungen) festlegen. Steigt er, beginnt die Eskalation wieder beim ersten Schritt. Ein manuell festgelegter Schweregrad bleibt bestehen.
- **Bestätigen**: `acknowledge` der API, `incident.acknowledged` von PagerDuty und Zabbix-Update-Operationen, die ein Problem bestätigen, bestätigen den Incident und stoppen weitere Eskalationsschritte und Anrufe. Es wird kein Benutzer als Bestätigender erfasst.
- **Beheben**: Der Incident wird behoben, wenn die Quelle eine Wiederherstellung meldet, auch bei bestätigten Incidents. Es wird kein Benutzer als Behebender erfasst, und die Timeline zeigt ihn als behoben.
- **Verspätete Nachrichten**: Jeder Dedup-Schlüssel merkt sich die zuletzt verwendete Absenderzeit, und eine ältere Nachricht wird ignoriert. Ein verspäteter Auslöser eröffnet keinen Zombie-Incident, und eine verspätete Wiederherstellung schließt keinen neuen. Die API überträgt keine Zeit, daher werden ihre Nachrichten in der Reihenfolge ihres Eintreffens verarbeitet.
- **Zuerst von einer Person behoben**: Wenn die Quelle den Alarm weiterhin meldet, eröffnet ihr nächstes erneutes Senden einen neuen Incident, wie bei Regeln.
- **Keine Daten**: Incidents, die durch `INSUFFICIENT_DATA` von CloudMonitor, `insufficient_data` von Cloud Eye und No Data von Datadog eröffnet wurden, tragen `alert.condition=no_data`, und ihre Benachrichtigungstitel beginnen mit `NO DATA`.
- **Deaktivieren und Löschen**: Eine deaktivierte Quelle lehnt Alarme ab (`409`), und ihre offenen Incidents bleiben bestehen. Das Löschen einer Quelle macht ihr Token sofort ungültig und behebt ihre offenen Incidents.

[Stummschaltungsrichtlinien](/de/alerting/silences), [semantische Gruppen](/de/alerting/silences#semantische-gruppen) und [Benachrichtigungsrichtlinien](/de/notification-channels) gelten für externe Incidents wie für alle anderen. Gleichen Sie sie anhand von `external.kind`, den zusätzlichen Labels einer Quelle oder den eigenen Labels des Alarms ab.

## Zuletzt empfangen

Der obere Bereich der Seite einer Quelle zeigt ihren Status: **Wartet auf die erste Anfrage**, **Empfängt Anfragen**, **Letzte Anfrage abgelehnt**, **Keine Anfragen in den letzten 7 Tagen** oder **Deaktiviert**. Daneben stehen die Anfragen und Alarme der letzten 24 Stunden sowie die Incidents, die die Quelle eröffnet hat und die noch offen sind.

Sobald Anfragen eingegangen sind, listet **Zuletzt empfangen** auf der Seite der Quelle die erhaltenen Anfragen auf: die Zeit, das Ergebnis (**Verarbeitet**, **Abgelehnt** oder **Weitergeleitet**), den HTTP-Status, die Anzahl der Alarme und was aus ihnen geworden ist (**Eröffnet**, **Aktualisiert**, **Unverändert**, **Bestätigt**, **Behoben** oder **Ignoriert**). Klicken Sie auf eine Zeile, um Titel, Schweregrad, Aktion, Ergebnis und Incident jedes Alarms zu sehen; eine abgelehnte Anfrage zeigt außerdem den Grund und den Anfang ihres Bodys (bis zu 16 KiB). Die letzten 500 Anfragen jeder Quelle werden bis zu 7 Tage lang aufbewahrt.

## Mehrere Cluster

Mit aktivierter [clusterübergreifender Föderation](/de/settings/data-plane#cluster-föderation):

- Quellen werden zwischen Clustern wie andere Alerting-Konfiguration synchronisiert, Tokens eingeschlossen, sodass ein Token an der Intake-Adresse jedes Clusters funktioniert.
- Die Incidents einer Quelle werden nur auf ihrem **Empfangscluster** geöffnet: dem Cluster, auf dem sie erstellt wurde, sofern dies nicht in den Einstellungen der Quelle geändert wurde. Ein anderes Cluster, das einen Alert der Quelle empfängt, leitet ihn per gRPC an das Empfangscluster weiter und gibt die Antwort des Empfangsclusters an den Absender zurück. Ein externer Alert ist daher ein Incident, unabhängig davon, an welche Cluster-Adresse er gelangt.
- Ist das Empfangscluster nicht erreichbar, lautet die Antwort `503` und der Absender versucht es erneut. Bleibt die Region des Empfangsclusters ausgefallen, ändern Sie das **Empfangscluster** in den Einstellungen der Quelle auf eines, das verfügbar ist.
- **Zuletzt empfangen** wird auf dem Cluster aufgezeichnet, das die Anfrage bearbeitet hat. Die Seite der Quelle weist darauf hin, wenn sie auf einem anderen Cluster geöffnet wird.

## Limits

| Element | Limit |
|---|---|
| Request-Body, eine Mail | Höchstens 4 MiB. |
| Lesen eines Postfachs | Höchstens 50 Mails auf einmal; der Rest im nächsten Durchlauf. |
| Eine API-Anfrage | 100 Alerts; `dedupKey` bis zu 255 Zeichen, `summary` bis zu 1024 Zeichen. |
| Ein Alert | 64 Labels und 64 Annotations. Die API lehnt mehr ab; bei anderen Typen werden die übrigen verworfen, und zu lange Titel und Annotations werden gekürzt. |
| Alerts einer Gruppe | 100 werden behalten. |
| Zusätzliche Labels einer Quelle | 32, wobei kein Schlüssel mit `alert.` beginnt und kein `external.kind` vorkommt. |
| Zuletzt empfangen | Die letzten 500 Anfragen jeder Quelle, für bis zu 7 Tage. |

Die HMAC-Signatur von Grafana und die Signatur von PagerDuty werden nicht geprüft; das Token identifiziert die Quelle bereits. Das Bestätigen oder Auflösen eines Incidents in MoleSignal wird nicht an den Absender zurückgeschrieben.
