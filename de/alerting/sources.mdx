Eine Alarmquelle wandelt Alarme aus einem anderen System in [Vorfälle](/de/alerting/incidents) um. Wie bei Vorfällen aus Regeln alarmiert eine [Eskalationsrichtlinie](/de/alerting/on-call#eskalationsrichtlinien) den Bereitschaftsdienst, und [Benachrichtigungsrichtlinien](/de/notification-channels) steuern die Benachrichtigungen. Die Vorfälle schließen sich, sobald die Quelle meldet, dass die Störung behoben ist. Öffnen Sie **Alarme → Quellen**. Zum Lesen ist `alerts.sources.read` erforderlich. Zum Erstellen, Bearbeiten und Löschen von Quellen sowie zum Rotieren von Tokens ist `alerts.sources.manage` erforderlich.

## Quelltypen

Jede Quelle hat einen Typ. Er legt fest, nach welchem Format MoleSignal den Anfrageinhalt ausliest.

| Typ | Absender | Ein Vorfall pro |
|---|---|---|
| **API** | Skripte, CI und interne Systeme, die die MoleSignal-API aufrufen | Deduplizierungsschlüssel |
| **Alertmanager** | Ein Webhook-Empfänger von Prometheus Alertmanager | Benachrichtigungsgruppe |
| **Grafana** | Ein Webhook-Kontaktpunkt von Grafana Alerting | Benachrichtigungsgruppe |
| **Datadog** | Die Webhooks-Integration von Datadog | Monitor bzw. Gruppe eines Multi-Alert-Monitors |
| **PagerDuty** | Ein V3-Webhook-Abonnement von PagerDuty | PagerDuty-Vorfall |
| **Alibaba Cloud CloudMonitor** | Rückrufe für Schwellenwertalarme und Push-Kanäle für Ereignisabonnements | Objekt einer Alarmregel oder Systemereignis |
| **Tencent Cloud Observability Platform** | API-Rückrufe einer Benachrichtigungsvorlage | Metrik oder Ereignis eines Objekts unter einer Richtlinie, bei mehrstufigen Richtlinien je Stufe |
| **Amazon CloudWatch** | Alarme an ein SNS-Thema über dessen HTTPS-Abonnement | Alarm |
| **Zabbix** | Ein Webhook-Medientyp von Zabbix | Problem |
| **E-Mail** | Ein IMAP-Postfach oder unverarbeitete E-Mails aus einem bereits betriebenen E-Mail-System | Folge von E-Mails mit demselben Betreff |

Systeme, die das Alertmanager-Webhook-Format unterstützen, etwa der Alertmanager von Thanos, Cortex oder Mimir, verwenden den Typ **Alertmanager**.

## Quelle erstellen

1. Öffnen Sie **Alarme → Quellen** und klicken Sie auf **Neue Alarmquelle**.
2. Wählen Sie den **Typ** aus und geben Sie einen **Namen** ein.
3. Wählen Sie die **Eskalationsrichtlinie** aus. Wie im Regeleditor gilt standardmäßig **Nach Routing-Regeln (Standard)**: Das [Alarmrouting](/de/alerting/routing) bestimmt das Team und die Eskalationsrichtlinie anhand der Routing-Regeln, des für den Dienst zuständigen Teams und des Team-Labels. Andernfalls greift die [Standardrichtlinie](/de/alerting/on-call#die-standardrichtlinie) namens `default`. Wenn Sie eine Richtlinie auswählen, gilt diese für die Vorfälle, und das Routing bestimmt nur das Team. Bei **Keine Eskalation, nur Benachrichtigungsrichtlinien** öffnet MoleSignal weiterhin Vorfälle und sendet Benachrichtigungen, alarmiert den Bereitschaftsdienst aber nicht über eine Eskalationsrichtlinie.
4. Wählen Sie den **Standard-Schweregrad** aus. Er gilt, wenn ein Alarm keinen eigenen Schweregrad enthält.
5. Fügen Sie bei Bedarf **Zusätzliche Labels** hinzu, etwa `team=payments`. MoleSignal fügt sie jedem Vorfall hinzu, den die Quelle öffnet. Hat der Alarm bereits ein Label mit demselben Schlüssel, hat dieses Vorrang.
6. Klicken Sie auf **Erstellen**. Die Seite der Quelle öffnet sich mit einem Dialog, der das Token und die Einrichtung mit bereits eingetragenem Token zeigt. Alibaba Cloud CloudMonitor benötigt nur die Empfangsadresse. Der Dialog zeigt daher die Adresse mit dem Token an.

<Warning>
  MoleSignal zeigt das Token nur beim Erstellen der Quelle oder beim Rotieren des Tokens an. Nach dem Schließen des Dialogs bleibt nur das Präfix sichtbar, das mit `mspat-` beginnt. Klicken Sie bei Verlust des Tokens auf **Token rotieren**, um ein neues zu erhalten. Das alte Token wird sofort ungültig.
</Warning>

## Empfangsadresse und Token

Alle Quellen nutzen dieselbe Empfangsadresse. Das Token gibt an, zu welcher Quelle ein Alarm gehört:

```text
https://<molesignal-host>/api/v1/intake/alerts
```

Ein Token hat die Form `mspat-<36>` und damit dasselbe Format wie ein API-Token. Es dient jedoch ausschließlich zur Annahme von Alarmen. Ein API-Token kann keine Alarme annehmen. Der Absender übermittelt das Token in einem Header:

```text
Authorization: Bearer <token>
```

Kann der Absender keine Header setzen (Alibaba Cloud CloudMonitor, Tencent Cloud Observability Platform, Amazon CloudWatch über SNS), übermittelt er das Token in der Adresse: `https://<molesignal-host>/api/v1/intake/alerts?token=<token>`.

Der Absender muss diese Adresse erreichen können. Wenn sich MoleSignal hinter einer Firewall befindet, lassen Sie die ausgehenden IP-Adressen des Standorts oder der Region des Absenders zu: Datadog listet sie pro Standort im Abschnitt `webhooks` seiner `ip-ranges` auf. PagerDuty veröffentlicht sie für seine US- und EU-Dienstregionen, und Alibaba Cloud CloudMonitor listet die IP-Bereiche für Push-Nachrichten in der Dokumentation zu Alarmrückrufen auf. Wenn MoleSignal in einem internen Netzwerk läuft, erfahren Sie unter [Öffentlicher Zugriff](/de/public-access), wie Sie nur diese Adresse für den Zugriff aus dem Internet freigeben.

## Absender einrichten

Unter **Empfang** auf der Seite der Quelle stehen die Empfangsadresse, das Token und drei Einrichtungsschritte für den jeweiligen Quelltyp. Ersetzen Sie `<TOKEN>` durch das Token der Quelle. Sobald die erste Anfrage bei der Quelle eingeht, markiert MoleSignal alle drei Schritte als abgeschlossen.

### API

```bash
curl -X POST https://<molesignal-host>/api/v1/intake/alerts \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{"dedupKey": "disk-full/web-1", "summary": "Disk almost full on web-1", "severity": "critical", "labels": {"host.name": "web-1"}}'
```

Für `action` sind `trigger` (Standard), `acknowledge` und `resolve` möglich. Verwenden Sie zum Bestätigen oder Auflösen desselben Alarms denselben `dedupKey`. [Alarme senden](/de/api/alerting/send-alerts) beschreibt alle Felder.

### Alertmanager

Fügen Sie in `alertmanager.yml` einen Empfänger hinzu und leiten Sie Alarme an diesen weiter:

```yaml
route:
  receiver: molesignal
receivers:
  - name: molesignal
    webhook_configs:
      - url: https://<molesignal-host>/api/v1/intake/alerts
        send_resolved: true
        http_config:
          authorization:
            credentials: <token>
```

Lassen Sie `send_resolved` auf `true`, damit Alertmanager Entwarnungen sendet. Legen Sie für alle Replikate desselben Alertmanager-Clusters dieselbe `--web.external-url` fest. Die externe URL ist Teil des Deduplizierungsschlüssels. So bleiben gleichnamige Gruppen aus Alertmanagern in verschiedenen Regionen auch bei identischem Routing getrennte Incidents.

### Grafana

1. Öffnen Sie in Grafana **Alarmierung → Kontaktpunkte** und klicken Sie auf **Kontaktpunkt hinzufügen**.
2. Wählen Sie unter **Integration** den Typ **Webhook** und tragen Sie unter **URL** die Empfangsadresse ein.
3. Tragen Sie unter **Optionale Webhook-Einstellungen** bei **Authentifizierungsschema** `Bearer` und bei **Anmeldedaten für den Authentifizierungsheader** das Token ein.
4. Lassen Sie **Entwarnungsmeldung deaktivieren** ausgeschaltet, speichern Sie den Kontaktpunkt und verwenden Sie ihn in einer Benachrichtigungsrichtlinie.

Bei dateibasierter Bereitstellung:

```yaml
apiVersion: 1
contactPoints:
  - orgId: 1
    name: molesignal
    receivers:
      - uid: molesignal
        type: webhook
        settings:
          url: https://<molesignal-host>/api/v1/intake/alerts
          httpMethod: POST
          authorization_scheme: Bearer
          authorization_credentials: <token>
```

### Datadog

1. Öffnen Sie in Datadog **Integrationen → Webhooks** und fügen Sie einen Webhook hinzu, beispielsweise mit dem Namen `molesignal`.
2. Tragen Sie unter **URL** die Empfangsadresse und unter **Custom Headers** `{"Authorization": "Bearer <token>"}` ein. Lassen Sie **Encode as form** ausgeschaltet.
3. Tragen Sie unter **Payload** die folgende Vorlage ein. Die Feldnamen stammen von MoleSignal, die Werte sind Datadog-Variablen. MoleSignal lehnt Anfragen ohne diese Vorlage ab.

```json
{
  "alert_id": "$ALERT_ID",
  "alert_cycle_key": "$ALERT_CYCLE_KEY",
  "transition": "$ALERT_TRANSITION",
  "alert_type": "$ALERT_TYPE",
  "priority": "$ALERT_PRIORITY",
  "title": "$ALERT_TITLE",
  "event_title": "$EVENT_TITLE",
  "message": "$TEXT_ONLY_MSG",
  "scope": "$ALERT_SCOPE",
  "tags": "$TAGS",
  "hostname": "$HOSTNAME",
  "link": "$LINK",
  "snapshot": "$SNAPSHOT",
  "query": "$ALERT_QUERY",
  "org_id": "$ORG_ID",
  "last_updated": "$LAST_UPDATED"
}
```

4. Erwähnen Sie `@webhook-molesignal` in der Benachrichtigungsnachricht eines Monitors.

Alle Datadog-Sites (`datadoghq.com`, `datadoghq.eu`, `us3`, `us5`, `ap1` und weitere) können an dieselbe Quelle senden. MoleSignal ermittelt die Site aus der Domain von `$LINK` und nimmt sie zusammen mit der Organisations-ID in den Deduplizierungsschlüssel auf.

### PagerDuty

1. Öffnen Sie in PagerDuty **Integrationen → Generic Webhooks (v3)** und klicken Sie auf **New Webhook**.
2. Tragen Sie unter **Webhook-URL** die Empfangsadresse ein und wählen Sie unter **Scope Type** das Konto, einen Dienst oder ein Team aus.
3. Wählen Sie unter **Event Subscription** `incident.triggered`, `incident.acknowledged`, `incident.resolved`, `incident.reopened` und `incident.priority_updated` aus.
4. Fügen Sie den benutzerdefinierten Header `Authorization` mit dem Wert `Bearer <token>` hinzu.

Konten aus den Serviceregionen USA und EU können an dieselbe Quelle senden. Die Kontodomain (`<subdomain>.pagerduty.com` oder `<subdomain>.eu.pagerduty.com`) ist Teil des Deduplizierungsschlüssels. MoleSignal schreibt sie in das Label `pagerduty.region`.

### Alibaba Cloud CloudMonitor

Fügen Sie das Token zur Empfangsadresse hinzu:

```text
https://<molesignal-host>/api/v1/intake/alerts?token=<token>
```

- **Schwellenwertalarme**: Tragen Sie diese Adresse als **Alarm-Callback** in einer Alarmregel ein. CloudMonitor sendet den Callback als formkodierte POST-Anfrage. MoleSignal liest auch JSON.
- **Systemereignisse**: Erstellen Sie unter **Event Center → Event Subscription → Push channels** einen Kanal mit dem Zieltyp **Webhook**, der Anfragemethode **POST** und dem Datenformat **JSON**. Tragen Sie diese Adresse ein und verwenden Sie den Kanal in einer Abonnementrichtlinie.

CloudMonitor wartet bei einem Systemereignis 5 Sekunden auf die Callback-Antwort und wiederholt die Anfrage bis zu 3-mal. Bei der Weiterleitung einer Anfrage an den [Empfangscluster](#mehrere-cluster) wartet MoleSignal höchstens 3 Sekunden. Bei einer Zeitüberschreitung antwortet MoleSignal mit `503`, damit CloudMonitor die Anfrage wiederholt. Die chinesische und die internationale Site sowie alle Regionen senden im selben Format. MoleSignal schreibt die Region in das Label `aliyun.region` und nimmt die `userId` des Kontos in den Deduplizierungsschlüssel auf.

### Tencent Cloud Observability Platform

Bearbeiten oder erstellen Sie in Tencent Cloud Observability Platform (ehemals Cloud Monitor) unter **Alarm Management → Notification Templates** eine Vorlage. Tragen Sie die Empfangsadresse als **API-Callback** ein und verknüpfen Sie die Vorlage mit den Alarmrichtlinien. Der Callback von Tencent Cloud unterstützt keine Header. Fügen Sie das Token deshalb zur Adresse hinzu. Behandeln Sie die Adresse wie ein Zugangsgeheimnis: Der Callback enthält keine Signatur, und die Adresse identifiziert die Quelle. Tencent Cloud unterstützt Metrik- und Ereignisalarme und sendet sowohl Auslösungen als auch Entwarnungen.

- **Deduplizierung**: Stimmen Konto, Alarmrichtlinie, Metrik- oder Ereignisname und Objekt überein, fasst MoleSignal die Meldungen zu einem Alarm zusammen. Bei einer Richtlinie mit mehreren Stufen entsteht wie in Tencent Cloud pro Stufe ein Incident, den die jeweilige Entwarnung unabhängig auflöst.
- **Schweregrad**: Bei `alarmLevel` entspricht Serious (`Serious`) dem Schweregrad Kritisch, Severe (`Warn`) dem Schweregrad Fehler und Reminder (`Remind`) dem Schweregrad Info. Bei Richtlinien ohne Stufen verwendet MoleSignal den Standardschweregrad der Quelle.
- **Zustandslose Ereignisse** (bei `alarmStatus` mit dem Wert `5`) öffnen einen Incident, für den keine Entwarnung folgt. Lösen Sie solche Incidents manuell auf.
- **Zeitangaben** im Callback enthalten keine Zeitzone. MoleSignal interpretiert sie als Pekinger Ortszeit.

### Amazon CloudWatch

CloudWatch-Alarme rufen externe Adressen nicht direkt auf, sondern nutzen SNS:

1. Senden Sie in den Alarmbenachrichtigungen sowohl den Wechsel zu **Im Alarmzustand** (`ALARM`) als auch die Rückkehr zu **OK** an dasselbe SNS-Thema. Ohne `OK` löst MoleSignal Incidents nicht automatisch auf. Senden Sie bei Alarmen wegen fehlender Daten auch **Unzureichende Daten** (`INSUFFICIENT_DATA`).
2. Fügen Sie dem Thema ein HTTPS-Abonnement hinzu. Verwenden Sie die Empfangsadresse einschließlich Token als Endpunkt:

   ```bash
   aws sns subscribe \
     --topic-arn <ARN of the topic> \
     --protocol https \
     --notification-endpoint 'https://<molesignal-host>/api/v1/intake/alerts?token=<token>'
   ```

3. Das Abonnement bestätigt sich automatisch: MoleSignal prüft die Signatur der Bestätigungsnachricht und ruft anschließend deren `SubscribeURL` auf.

MoleSignal prüft die Signatur jeder SNS-Nachricht. Lassen Sie deshalb **Rohnachrichtenübermittlung** ausgeschaltet. Ist die Option aktiv, lehnt MoleSignal die Nachrichten ab und zeigt den Grund auf der Seite der Quelle unter „Zuletzt empfangen“ an. Das Signaturzertifikat stammt von `sns.<region>.amazonaws.com`. Der Knoten, der die Anfrage entgegennimmt, muss diese Adresse erreichen können.

CloudWatch-Alarme haben keinen Schweregrad. MoleSignal verwendet daher für Incidents den Standardschweregrad der Quelle. Der ARN des Alarms dient als Deduplizierungsschlüssel, auch bei zusammengesetzten Alarmen. MoleSignal speichert die Alarmbeschreibung und den Grund für den Statuswechsel als Annotationen. Region, Konto, Namespace, Metrik und Dimensionen speichert MoleSignal als Labels. So kann ein Label wie `aws.region` das Routing steuern.

### Zabbix

Die Integration funktioniert ab Zabbix 6.0. Zabbix hat kein eigenes Anfrageformat: Das Skript eines Medientyps sendet die Anfrage. Auf der Seite der Quelle und im Dialog zum Anlegen einer Quelle steht deshalb ein Medientyp mit bereits eingetragener Adresse und eingetragenem Token bereit:

1. Speichern Sie den Medientyp als YAML und importieren Sie ihn unter **Alarme → Medientypen → Importieren**. Prüfen Sie den Parameter `token`.
2. Setzen Sie das globale Makro `{$ZABBIX.URL}` auf die Adresse des Zabbix-Frontends. Die Adresse fließt in den Deduplizierungsschlüssel ein. So kann eine Quelle Anfragen von mehreren Zabbix-Servern annehmen, und Incidents verlinken zurück zu Zabbix. Die Integration funktioniert auch ohne das Makro.
3. Weisen Sie das Medium einem Benutzerkonto zu. Unter **Senden an** können Sie einen beliebigen Wert eintragen. Das Skript verwendet ihn nicht.
4. Fügen Sie eine Trigger-Aktion hinzu, deren **Operationen**, **Wiederherstellungsoperationen** und **Aktualisierungsoperationen** an dieses Benutzerkonto gehen. Ohne Wiederherstellungsoperationen löst MoleSignal Incidents nicht automatisch auf.

Die Schaltfläche **Testen** des Medientyps benötigt echte Werte. Wenn Zabbix Makros nicht auflöst und beispielsweise `{EVENT.ID}` unverändert sendet, antwortet MoleSignal mit `400` und verweist auf den Medientyp aus der Dokumentation.

### E-Mail

MoleSignal kann E-Mails auf zwei Wegen empfangen. Beide verarbeiten E-Mails auf dieselbe Weise zu Alarmen.

**Postfach abrufen** (empfohlen): MoleSignal ruft ein IMAP-Postfach in regelmäßigen Abständen ab. Dafür reichen eine ausgehende Verbindung und ein Postfach. Eine öffentliche Adresse, ein MX-Eintrag, Port 25 und ein Zertifikat sind nicht nötig. Das macht diese Variante beim Self-Hosting am einfachsten. Senden Sie die Alarm-E-Mails des Monitoring-Systems an dieses Postfach oder leiten Sie sie per E-Mail-Regel dorthin weiter.

Füllen Sie auf der Seite der Quelle unter **Postfach abrufen** die Felder **IMAP-Server**, **Port**, **Verschlüsselung**, **Benutzername**, **Passwort**, **Ordner** (standardmäßig `INBOX`) und **Abrufintervall** (15 bis 3600 Sekunden, standardmäßig 60) aus. Klicken Sie auf **Verbindung testen** und anschließend auf **Postfach speichern**.

- **Nur Lesezugriff**: MoleSignal verwendet `EXAMINE` und `BODY.PEEK[]`. Dadurch markiert MoleSignal keine E-Mails als gelesen und löscht keine. Ein Konto mit reinem Lesezugriff reicht aus.
- **Keine älteren E-Mails**: Beim ersten Verbindungsaufbau merkt sich MoleSignal die aktuelle Position und liest nur E-Mails, die danach eingehen. Wenn sich Host, Konto oder Ordner ändern oder der Server das Postfach neu aufbaut (`UIDVALIDITY` ändert sich), beginnt MoleSignal an der dann aktuellen Position. Solange die Quelle deaktiviert ist, liest MoleSignal keine E-Mails und speichert keine Position. Nach dem erneuten Aktivieren liest MoleSignal nur neu eingehende E-Mails.
- **Absenderliste erforderlich**: Wer die Adresse kennt, kann E-Mails dorthin senden. Tragen Sie in den Einstellungen der Quelle unter **E-Mails annehmen von** einzelne Adressen oder `@example.com` für eine ganze Domain ein. Mit `*` akzeptieren Sie alle Absender. Die Liste prüft den Header `From`, der sich fälschen lässt. Lassen Sie daher den Spamfilter und DMARC beim E-Mail-Anbieter aktiviert. E-Mails von anderen Absendern protokolliert MoleSignal als **Abgelehnt**, ohne einen Incident zu öffnen.
- **Anmeldung**: Verwenden Sie ein Passwort oder ein App-Passwort des Anbieters. Microsoft 365 akzeptiert keine Passwörter mehr. Wählen Sie **OAuth 2.0** und tragen Sie die Token-Adresse `https://login.microsoftonline.com/<tenant>/oauth2/v2.0/token`, die Client-ID, das Client-Geheimnis und den Geltungsbereich `https://outlook.office365.com/.default` ein. Die Anwendung benötigt die Berechtigung `IMAP.AccessAsApp` und Zugriff auf das Postfach.
- **Keine Verschlüsselung**: Verwenden Sie diese Option nur in einem vertrauenswürdigen Netzwerk. Das Passwort wird im Klartext übertragen.
- Schlägt ein Abruf fehl, zeigt MoleSignal den Grund auf der Seite der Quelle an und versucht es beim nächsten Abruf erneut. Bei mehreren Alarmierungsknoten ruft jeweils ein Knoten das Postfach ab. Bei einer Föderation richten Sie das Postfach auf dem Empfangscluster der Quelle ein. MoleSignal synchronisiert die Postfachkonfiguration nicht, sodass das Passwort auf diesem Cluster bleibt.

**Rohnachricht per POST senden**: Wenn bereits ein E-Mail-System vorhanden ist (etwa Postfix mit `pipe`, SES oder Mailgun mit MIME-Rohnachrichten), senden Sie die unveränderte Nachricht per POST an die Empfangsadresse:

```bash
curl -X POST 'https://<molesignal-host>/api/v1/intake/alerts' \
  -H 'Authorization: Bearer <token>' \
  -H 'Content-Type: message/rfc822' \
  --data-binary @alert.eml
```

Die Empfangsadresse muss vom E-Mail-System aus erreichbar sein. Die Absenderliste ist hier optional, da das Token die Anfrage bereits authentifiziert. Wenn Sie eine Liste hinterlegen, wendet MoleSignal sie an.

MoleSignal enthält keinen integrierten SMTP-Empfänger. Dafür wären ein offener Port 25, ein MX-Eintrag, ein TLS-Zertifikat und ein eigener Spamfilter nötig. Die meisten selbst gehosteten Installationen können das nicht bereitstellen.

**So verarbeitet MoleSignal E-Mails**: Legen Sie die Regeln in den Einstellungen der Quelle unter **E-Mail-Empfang** fest:

| Einstellung | Beschreibung |
|---|---|
| **Betreffzeilen für Entwarnungen** | Ein regulärer Ausdruck. Bleibt das Feld leer, verwendet MoleSignal den integrierten Ausdruck: `resolved`, `recovered`, `recovery`, `cleared`, `恢复`, `已解决` und `OK` am Anfang des Betreffs. Andere E-Mails lösen einen Alarm aus. |
| **Deduplizierungsschlüssel aus dem Betreff** | Ein regulärer Ausdruck. MoleSignal verwendet die erste Erfassungsgruppe, etwa bei `host=(\S+)`. Ist das Feld leer oder gibt es keinen Treffer, verwendet MoleSignal den bereinigten Betreff: ohne `Re:` und `Fwd:`, Statuswörter (`PROBLEM`, `RECOVERY`, `告警`, `恢复` usw.), Schweregrade, Datums- und Zeitangaben sowie Prozentwerte. Groß- und Kleinschreibung spielt keine Rolle. So gehören „CRITICAL: disk full on web-1 (91%)“ und „RECOVERY: disk full on web-1 (40%)“ zum selben Alarm, während `web-1` und `web-2` zwei verschiedene Alarme auslösen. Auch die Domain des Absenders fließt in den Schlüssel ein. |
| **Zu ignorierende Betreffzeilen** | Ein regulärer Ausdruck. MoleSignal überspringt passende E-Mails und zeigt sie unter „Zuletzt empfangen“ an. |

MoleSignal ermittelt den Schweregrad anhand von Wörtern im Betreff (`critical`, `fatal`, `disaster`, `P1` für Kritisch; `error`, `P2` für Fehler; `warning`, `P3` für Warnung; `info`, `notice`, `P4`, `P5` für Info). Ohne Treffer gilt der Standardschweregrad der Quelle. „High“ in `High CPU` und „Low“ in `Low disk` gelten nicht als Schweregrad. MoleSignal speichert den Nachrichtentext in der Annotation `message` (HTML-E-Mails als Text, höchstens 4096 Zeichen) und den Absender im Label `email.from` sowie in der Annotation `from`. Die Zeitangabe stammt aus dem Header `Date`. Automatische Antworten (`Auto-Submitted: auto-replied`) und Unzustellbarkeitsmeldungen (`multipart/report`) lösen keine Alarme aus. MoleSignal unterstützt GBK, GB2312 und weitere Zeichensätze. E-Mails über 4 MiB protokolliert MoleSignal als **Abgelehnt**, ohne den Nachrichtentext zu lesen.

## Wie aus Alarmen Incidents werden

| Typ | Deduplizierungsschlüssel | Auslösen | Beheben | Schweregrad |
|---|---|---|---|---|
| **API** | `dedupKey` | `trigger` | `resolve` | `severity` |
| **Alertmanager** | Externe URL und `groupKey` | Gruppenstatus (`status`) ist `firing` | Gruppenstatus (`status`) ist `resolved`: Alle Alarme der Gruppe sind behoben | Der höchste Wert des Labels `severity` unter den aktiven Alarmen der Gruppe |
| **Grafana** | Externe URL, Organisation und `groupKey` | Wie bei Alertmanager | Wie bei Alertmanager | Wie bei Alertmanager |
| **Datadog** | Site, Organisation, Monitor-ID und Geltungsbereich | Jeder Statuswechsel außer `Recovered` | `Recovered` | `$ALERT_PRIORITY`; fehlt der Wert, gilt für Warn und No Data der Schweregrad Warnung und für alle anderen Fälle `$ALERT_TYPE` |
| **PagerDuty** | Kontodomain und PagerDuty-Incident-ID | `incident.triggered`, `incident.reopened`; `incident.priority_updated` ändert den Schweregrad | `incident.resolved` | Priorität P1 bis P5; fehlt die Priorität, gilt bei hoher Dringlichkeit Fehler und bei niedriger Dringlichkeit Warnung |
| **Alibaba Cloud CloudMonitor** | Konto, Regel-ID und `dimensions`; bei Systemereignissen Konto und `dedupId` | `ALERT`, `INSUFFICIENT_DATA`; bei Systemereignissen `TRIGGERED` | `OK`; bei Systemereignissen `RESOLVED` | `triggerLevel`; bei Systemereignissen `severity` |
| **Tencent Cloud Observability Platform** | Konto, Richtlinie, Name der Metrik oder des Ereignisses, Stufe und Objekt | `alarmStatus` ist `1` oder `5` | `alarmStatus` ist `0` | `alarmLevel` |
| **Amazon CloudWatch** | `AlarmArn` | `NewStateValue` ist `ALARM` oder `INSUFFICIENT_DATA` | `NewStateValue` ist `OK` | Keine Angabe: Es gilt der Standard-Schweregrad der Quelle |
| **Zabbix** | Host aus `{$ZABBIX.URL}` und `{EVENT.ID}` | `{EVENT.VALUE}` ist 1; auch Aktualisierungsvorgänge lösen aus und übernehmen dabei den Schweregrad | `{EVENT.VALUE}` ist 0 oder ein Aktualisierungsvorgang hat das Problem geschlossen | `{EVENT.NSEVERITY}`: Disaster entspricht Kritisch, High entspricht Fehler, Average und Warning entsprechen Warnung, Information entspricht Info |
| **E-Mail** | Absenderdomain und der aus dem Betreff extrahierte Teil | Alle anderen E-Mails | Ein Betreff, der die Behebung meldet | Wörter im Betreff |

MoleSignal wertet Priorität und Dringlichkeit getrennt aus. Die API liefert `priority` und `urgency`, Datadog liefert `$ALERT_PRIORITY`, und PagerDuty liefert Priorität und Dringlichkeit. MoleSignal übernimmt diese Werte in den Incident. Fehlt die Dringlichkeit, entscheidet die Eskalationsrichtlinie der Quelle. Ein Alarm ohne Schweregrad hat eine hohe Dringlichkeit. Siehe [Dringlichkeit](/de/alerting/on-call#dringlichkeit).

Für einen Alarm ohne Schweregrad gilt der **Standard-Schweregrad** der Quelle. MoleSignal ignoriert bei den Schweregradangaben aller Absender die Groß- und Kleinschreibung: `critical`, `crit`, `fatal`, `page` und `P1` entsprechen Kritisch; `error`, `major`, `high` und `P2` entsprechen Fehler; `warning`, `warn`, `minor`, `medium` und `P3` entsprechen Warnung; `info`, `low`, `P4` und `P5` entsprechen Info. Für alle anderen Angaben gilt der Standard-Schweregrad.

- **Eröffnen**: Pro Quelle und Deduplizierungsschlüssel gibt es höchstens einen aktiven Incident. Der Incident enthält die Labels `alert.source=external` und `external.kind=<kind>`, die Labels des Alarms (bei Alertmanager und Grafana die `commonLabels` der Gruppe) und die zusätzlichen Labels der Quelle. `service.name` oder `service` gibt einen betroffenen Dienst an. `host.name`, `host` oder `hostname` gibt einen Host an.
- **Titel**: Die API verwendet `summary`. Alertmanager und Grafana verwenden die Annotation `summary` oder, falls sie fehlt, `alertname`. Datadog verwendet `$ALERT_TITLE`. PagerDuty verwendet den Incident-Titel. Alibaba Cloud CloudMonitor verwendet „Alarmname · Instanzname“.
- **Links**: MoleSignal speichert Adressen zum Absendersystem in Annotationen wie `alertmanager_url`, `generator_url`, `dashboard_url`, `datadog_url` und `pagerduty_url`. Die Incident-Seite zeigt sie als Links an. MoleSignal speichert die `links` der API anhand von `name` als Annotationen.
- **Alarme einer Gruppe**: Ein Incident aus Alertmanager oder Grafana enthält alle Alarme der Gruppe (bis zu 100) samt Status. MoleSignal aktualisiert sie mit jeder Benachrichtigung. **Externer Alarm** listet auf der Incident-Seite die Alarme mit den Labels auf, anhand derer sich die Alarme unterscheiden lassen.
- **Änderungen des Schweregrads**: Solange der Incident unbestätigt ist, übernimmt er den Schweregrad, den die [Alarm-Pipelines](/de/pipelines/alert-events#schweregradänderungen) für den Alarm festlegen. Steigt der Schweregrad, beginnt die Eskalation wieder beim ersten Schritt. Ein manuell festgelegter Schweregrad bleibt unverändert.
- **Bestätigen**: Die API mit `acknowledge`, PagerDuty mit `incident.acknowledged` und Zabbix-Aktualisierungsvorgänge, die ein Problem bestätigen, bestätigen den Incident und stoppen weitere Eskalationsschritte und Anrufe. MoleSignal erfasst für diese Bestätigung kein Benutzerkonto.
- **Beheben**: Wenn die Quelle die Behebung meldet, markiert MoleSignal den Incident als behoben. Das gilt auch für bestätigte Incidents. MoleSignal erfasst dafür kein Benutzerkonto und zeigt die Behebung in der Zeitleiste an.
- **Verspätete Nachrichten**: MoleSignal merkt sich pro Deduplizierungsschlüssel den jüngsten verarbeiteten Absenderzeitstempel und ignoriert ältere Nachrichten. Eine verspätete Auslösung eröffnet keinen Zombie-Incident, und eine verspätete Behebungsmeldung schließt keinen neuen Incident. Die API übermittelt keinen Zeitstempel. MoleSignal verarbeitet ihre Nachrichten daher in der Reihenfolge ihres Eingangs.
- **Zuerst manuell behoben**: Meldet die Quelle den Alarm weiterhin, eröffnet die nächste erneute Meldung einen neuen Incident. Das gilt auch für Regeln.
- **Keine Daten**: Incidents, die CloudMonitor mit `INSUFFICIENT_DATA` oder Datadog mit No Data auslöst, tragen `alert.condition=no_data`. Die Titel ihrer Benachrichtigungen beginnen mit `NO DATA`.
- **Deaktivieren und Löschen**: Eine deaktivierte Quelle lehnt Alarme ab (`409`). Ihre offenen Incidents bleiben offen. Beim Löschen einer Quelle macht MoleSignal ihr Token sofort ungültig und markiert ihre offenen Incidents als behoben.

[Stummschaltungsrichtlinien](/de/alerting/silences), [semantische Gruppen](/de/alerting/silences#semantische-gruppen) und [Benachrichtigungsrichtlinien](/de/notification-channels) gelten für externe Incidents ebenso wie für alle anderen. Verwenden Sie `external.kind`, die zusätzlichen Labels der Quelle oder die Labels des Alarms als Auswahlkriterien.

## Zuletzt empfangen

Oben auf der Seite der Quelle steht ihr Status: **Wartet auf die erste Anfrage**, **Empfängt Anfragen**, **Letzte Anfrage abgelehnt**, **Keine Anfragen in den letzten 7 Tagen** oder **Deaktiviert**. Daneben stehen die Anzahl der Anfragen und Alarme der letzten 24 Stunden sowie die Anzahl der Incidents, die diese Quelle eröffnet hat und die noch offen sind.

Sobald Anfragen eingehen, listet **Zuletzt empfangen** auf der Seite der Quelle die empfangenen Anfragen auf: Zeitpunkt, Ergebnis (**Verarbeitet**, **Abgelehnt** oder **Weitergeleitet**), HTTP-Status, Anzahl der Alarme und deren Ergebnisse (**Eröffnet**, **Aktualisiert**, **Unverändert**, **Bestätigt**, **Behoben** oder **Ignoriert**). Klicken Sie auf eine Zeile, um für jeden Alarm Titel, Schweregrad, Aktion, Ergebnis und Incident anzuzeigen. Bei abgelehnten Anfragen zeigt die Seite zusätzlich den Grund und den Anfang des Anfrageinhalts (bis zu 16 KiB) an. MoleSignal speichert pro Quelle die letzten 500 Anfragen bis zu 7 Tage lang.

## Mehrere Cluster

Bei aktivierter [clusterübergreifender Föderation](/de/settings/data-plane#cluster-föderation) gilt:

- MoleSignal synchronisiert Quellen wie andere Alerting-Einstellungen zwischen den Clustern, einschließlich ihrer Tokens. Ein Token funktioniert daher an der Empfangsadresse jedes Clusters.
- MoleSignal eröffnet Incidents einer Quelle nur auf deren **Empfangscluster**. Standardmäßig ist das der Cluster, auf dem die Quelle angelegt wurde. Die Einstellung lässt sich in den Einstellungen der Quelle ändern. Empfängt ein anderer Cluster einen Alarm dieser Quelle, leitet er ihn per gRPC an den Empfangscluster weiter und gibt dessen Antwort an den Absender zurück. Ein externer Alarm führt daher nur zu einem Incident, unabhängig davon, an welcher Clusteradresse er eingeht.
- Ist der Empfangscluster nicht erreichbar, lautet die Antwort `503` und der Absender wiederholt die Anfrage. Bleibt die Region des Empfangsclusters außer Betrieb, wählen Sie in den Einstellungen der Quelle unter **Empfangscluster** einen erreichbaren Cluster aus.
- MoleSignal protokolliert Anfragen für **Zuletzt empfangen** auf dem Cluster, der sie verarbeitet hat. Beim Öffnen der Quellenseite auf einem anderen Cluster zeigt die Seite einen entsprechenden Hinweis an.

## Grenzwerte

| Element | Grenzwert |
|---|---|
| Anfrageinhalt pro E-Mail | Maximal 4 MiB. |
| Postfach abrufen | Maximal 50 E-Mails pro Abruf. Weitere E-Mails folgen beim nächsten Abruf. |
| Pro API-Anfrage | 100 Alarme; `dedupKey` bis zu 255 Zeichen, `summary` bis zu 1024 Zeichen. |
| Pro Alarm | 64 Labels und 64 Annotationen. Die API lehnt Anfragen ab, die diese Grenzwerte überschreiten. Bei anderen Quelltypen verwirft MoleSignal überschüssige Labels und Annotationen und kürzt zu lange Titel und Annotationen. |
| Alarme pro Gruppe | MoleSignal speichert 100 Alarme. |
| Zusätzliche Labels pro Quelle | 32. Kein Schlüssel darf mit `alert.` beginnen oder `external.kind` lauten. |
| Zuletzt empfangen | Die letzten 500 Anfragen pro Quelle für bis zu 7 Tage. |

MoleSignal prüft weder die HMAC-Signatur von Grafana noch die Signatur von PagerDuty. Das Token identifiziert die Quelle bereits. Wenn Sie einen Vorfall in MoleSignal bestätigen oder beheben, meldet MoleSignal die Statusänderung nicht an den Absender zurück.
